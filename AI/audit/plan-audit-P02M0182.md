AUDITOR'S REVIEW OF PLAN P02M0182 (2026-09-21T14:09:05Z):

**Rating: 3/10.** The service/transport policy split is appropriate, but the current outline does not establish its central PIN guarantee, a usable trusted-input dependency, or the ownership and lifecycle contracts needed for implementation. These are plan defects, not complaints that the new smart-card code has not yet been written.

### 1. High: Unrestricted APDU exchange contradicts the guarantee that no client path carries a PIN

**What is wrong:** The proposed client interface includes bounded APDU exchange, while the next requirement and definition of done say that PIN verification belongs to the service and no client path carries a PIN. No authenticated operation, supported card profile or APDU restriction connects these requirements. A PIN can be ordinary APDU command data: the PIV `VERIFY` command explicitly carries it in its data field. See [APDU and PIN requirements](/data/yellow/libersystem/docs/todo/P02M0182.md:16), [completion guarantee](/data/yellow/libersystem/docs/todo/P02M0182.md:33), and [NIST SP 800-73 Part 2, section 3.2.1](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-73pt2-5.pdf).

**Why it matters:** A generic byte-exchange client can submit a PIN-bearing command without using a future service verification operation. The implementation could therefore satisfy the listed APDU tests and still bypass its central security promise. A reader-scoped capability controls which reader is reachable; it does not establish which authentication operations the caller may issue.

**Required correction:** Resolve the API contract before implementation. Define service-owned verification operations and the supported card/application policy under which ordinary client commands cannot bypass them. If a separately privileged raw-APDU facility is intended, explicitly distinguish its authority and guarantees. Do not assume a universal opcode blacklist can interpret every proprietary card application; choose and document the bounded supported scope. Add a negative test that exercises the relevant PIN-bearing client command and proves the chosen boundary is enforced.

### 2. High: The mandatory trusted-input dependency has no implementable contract or completion path

**What is wrong:** The plan says it names trusted input as a dependency, but supplies no owner, referenced prerequisite or interface. Current InputService provides focus-scoped raw key streams and suppresses cooked console delivery; it does not provide a secret-entry broker. The related administrative-path milestone proposes an action/target confirmation and returns a capability, not secret input for smart-card verification. See [dependency statement](/data/yellow/libersystem/docs/todo/P02M0182.md:19), [current input boundary](/data/yellow/libersystem/src/user/services/core/src/input_service.rs:1), [input interface](/data/yellow/libersystem/src/idl/input.lsidl:51), and [administrative confirmation contract](/data/yellow/libersystem/docs/todo/P02M0188.md:21).

**Why it matters:** Supporting readers without pinpads requires substantial work outside this service. An implementer may either collect the PIN through the requesting application's ordinary UI, violating the stated boundary, or leave the path unfinished while treating the milestone as complete.

**Required correction:** Identify the owner and prerequisite for trusted secret entry and define its minimal contract with this service: which trusted component renders and receives input, how the requester is excluded, and how cancellation, timeout and loss of the trusted path terminate verification. Coordinate with P02M0188 if that mechanism is to be extended, rather than assuming its confirmation API already suffices. State the supported behavior before the dependency lands and whether the milestone remains blocked or explicitly delivers a pinpad-only first slice.

### 3. High: Transport ownership and supported CCID exchange modes are unresolved

**What is wrong:** P02M0099 assigns reader capability parsing, card power/parameter negotiation, APDU exchange, timeout/abort and sequence validation to the CCID transport. This milestone also requires T=0/T=1 protocol-state-machine tests without choosing where those machines live or what the service receives from the transport. CCID distinguishes character, TPDU and APDU exchange levels; an APDU-level reader performs the APDU-to-card transport itself. See [upstream CCID scope](/data/yellow/libersystem/docs/todo/P02M0099.md:5700), [service protocol tests](/data/yellow/libersystem/docs/todo/P02M0182.md:27), and [USB CCID 1.1, sections 3.2.1-3.2.3](https://www.usb.org/sites/default/files/DWG_Smart-Card_CCID_Rev110.pdf).

**Why it matters:** The service and later driver can duplicate protocol logic or choose incompatible boundaries. An APDU-level emulated reader cannot by itself validate a host character/TPDU state machine. Conversely, implementing every exchange mode merely to satisfy an unqualified test bullet can enlarge this service milestone into unnecessary transport work.

**Required correction:** Freeze the service/provider wire, supported exchange modes and the single owner of ATR/protocol parsing, card negotiation, CCID sequence handling and abort. Keep authentication decisions in the service and map required host tests to the layer that actually owns each state machine. Preserve the current in-controller USB class-module execution model ([existing architecture](/data/yellow/libersystem/src/user/drivers/core/src/usb_class.rs:1)). Identify which provider/fixture lets this service land before the CCID item that waits for it, and specify the emulated reader, card data and coverage of the guest gate rather than treating that gate as proof of every mode.

### 4. High: Transaction expiry does not define when the card is safe to hand to another client

**What is wrong:** The plan bounds transaction duration and names APDU timeout/abort and mid-transaction removal, but does not define their combined state machine. It does not say what happens to an in-flight command when the owner disconnects or expires, when a waiting client may acquire the slot, how late responses are rejected, or how reinsertion invalidates old transaction handles. The CCID abort protocol explicitly requires draining/discarding responses until the matching abort completion before sending a new slot command. See [transaction and removal requirements](/data/yellow/libersystem/docs/todo/P02M0182.md:22) and [USB CCID 1.1, section 5.3.1](https://www.usb.org/sites/default/files/DWG_Smart-Card_CCID_Rev110.pdf).

**Why it matters:** Releasing a software lock when its timer expires can interleave the next client's operation with an unfinished command, deliver a response to the wrong transaction, or let an old handle address a replacement card. Serialization alone also does not specify whether authentication state established for one client may be reused by the next.

**Required correction:** Define acquisition, active command, cancellation, drain/reset, removal and terminal states with bounded deadlines. Bind transactions to the reader/slot/card generation and client connection. Regrant only after the transport is safely quiescent, and define the supported card profile's authentication-state disposition at handoff. Test expiry during an APDU, owner death, late completion, removal/reinsertion and a second client waiting for the same slot. Assign the service and transport their respective transitions explicitly.

### 5. High: A reader capability is promised without a path that can mint and enforce its scope

**What is wrong:** The plan states that each reader is reached through a capability but defines neither the trusted minting operation nor the policy that selects the reader a client may reach. It also omits how the service discovers transport providers and tracks their withdrawal. Existing provider kinds are closed and contain no smart-card transport; application grants use an explicit capability vocabulary and per-launch minting for restricted clients. See [reader authorization claim](/data/yellow/libersystem/docs/todo/P02M0182.md:16), [closed provider set](/data/yellow/libersystem/src/idl/device.lsidl:151), [application capability contract](/data/yellow/libersystem/src/idl/security.lsidl:7), and [existing scoped-client minting example](/data/yellow/libersystem/src/user/services/core/src/permission_manager.rs:587).

**Why it matters:** Handing an application one global smart-card service connection and letting it pass arbitrary reader identifiers would not meet the per-reader guarantee. Handing applications the transport endpoint would additionally bypass service-owned transaction and authentication policy. Without the publication/bootstrap work, neither service nor application has a usable channel at all.

**Required correction:** Specify provider discovery and service bootstrap, then an admin/broker operation that mints a client connection restricted to an authorized reader and operation scope. Define grant delivery through the existing manifest/PermissionManager path and rejection of attempts to select another reader or use a withdrawn generation. Keep transport capabilities behind the service. Add tests proving that a grant for reader A cannot access reader B and that an old grant cannot silently attach to a replacement publication.
