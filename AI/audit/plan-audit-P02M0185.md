2. **High - “Monotonic timestamp” and “ordering preserved” do not specify a usable time/order contract.**

   The [event item](/data/yellow/libersystem/docs/todo/P02M0185.md:21) gives no timestamp unit, origin or sampling point, and neither it nor the [completion condition](/data/yellow/libersystem/docs/todo/P02M0185.md:38) defines the scope of ordering or equal timestamps. This matters in the current tree: [`clock()` and `clock_ns()`](/data/yellow/libersystem/src/user/runtime/rt/src/lib.rs:2336) are distinct clocks expressed in ticks and nanoseconds, while the existing [IDL `timestamp`](/data/yellow/libersystem/src/idl/time.lsidl:7) is wall-clock seconds. These cannot be interchanged under one unspecified timestamp field.

   USB MIDI 1.0's packet contains cable/CIN information and MIDI bytes, with no timestamp field. Consequently, a promise to retain original device event times requires a source that supplies them; ordinary USB packet decoding cannot recover them. [USB MIDI 1.0 specification, section 4](https://www.usb.org/sites/default/files/midi10.pdf#page=16). Independently, sorting equal-stamped events or merging sources without a declared rule can reorder events while superficially preserving monotonic timestamps.

   **Correct the vocabulary and ordering-test items** to specify the clock domain and units, when host-generated timestamps are taken, how they are retained across buffering, and whether order is guaranteed per endpoint, per cable or over a merged stream. Define stable order for equal timestamps and the meaning of any source-supplied time. Avoid claiming unavailable device timing or inventing an output scheduler unless output scheduling is explicitly in scope. Test delayed consumption, batched/equal timestamps and independent sources against that contract.

3. **High - The event unit and SysEx state machine are undecided, so the size cap cannot yet be enforced correctly.**

   The [bounded-payload and SysEx items](/data/yellow/libersystem/docs/todo/P02M0185.md:21) do not say whether a delivered event is a USB packet, a complete MIDI message, or a fragment of a larger message. That decision changes the meaning of the payload bound, the timestamp, and what a consumer may treat as complete. USB MIDI 1.0 represents SysEx through start/continuation/end packets and multiplexes cables within an endpoint. [USB MIDI 1.0 specification, sections 3.2.1 and 4](https://www.usb.org/sites/default/files/midi10.pdf#page=13).

   Merely limiting each event's payload leaves an arbitrarily long sequence of individually legal SysEx fragments; assembling everything instead can exceed the queue's intended memory bound or accidentally combine state from different cables. Refusing a malformed packet is also insufficient if the remaining parser state subsequently delivers a truncated message as complete.

   **Correct the event, SysEx and decoder-test items** to choose complete-message or explicit-fragment delivery and define the whole-message size cap and bounded assembly state per source/endpoint/cable. Specify what overflow, malformed continuation, truncation and reset do to an in-progress message and how valid traffic resumes. Place production decoding/state logic in a host-testable leaf, consistent with the [existing separation from the freestanding runtime](/data/yellow/libersystem/src/user/services/logic/Cargo.toml:8). Test interleaved cables, cap crossing across many packets, incomplete messages and successful recovery, not only isolated packet lengths.

4. **High - Queue saturation and source loss have no client-visible integrity/lifetime rule.**

   The [queue item](/data/yellow/libersystem/docs/todo/P02M0185.md:22) requires a declared full-queue behavior but permits a silent drop policy. The plan never requires the client to learn that events were lost or that its source disappeared. An ordered sequence with one missing state-changing event can still satisfy a simple ordering test while leaving the consumer in the wrong state. The [originating requirement](/data/yellow/libersystem/docs/todo/P02M0099.md:5725) also requires recovery from unplug, which needs a vocabulary-level lifecycle outcome even if USB detection belongs to the later driver.

   Existing [provider identity](/data/yellow/libersystem/src/idl/device.lsidl:179) includes generations and withdrawals specifically to prevent a reused slot from masquerading as the old source. The proposed bare “source identity” does not specify that distinction. Queued data or partial SysEx can otherwise survive removal and be attributed to a replacement endpoint, or a consumer can wait indefinitely on an endpoint that will never produce again.

   **Correct the queue, source-identity and completion items** to choose a bounded policy with observable loss or explicit endpoint termination, define how a slow consumer affects other consumers, and specify source removal/replacement and partial-message cleanup. Bind identity to the relevant connection/provider generation rather than only a reusable device or cable number. Add tests for a saturated queue, notification/termination under saturation itself, unplug during a message, and reattachment without delivery of stale events. A bounded queue and a small lifecycle protocol suffice; a general event broker is unnecessary.
