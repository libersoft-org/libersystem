AUDITOR'S REVIEW OF PLAN P02M0183 (2026-09-21T14:10:15Z):

**Rating: 3/10.** The intended authority split is sound, but the plan does not yet resolve the network integration, driver boundary, runtime lifecycle or executable proof needed to deliver it.

Reviewed [the plan](/data/yellow/libersystem/docs/todo/P02M0183.md), [the originating MBIM requirement](/data/yellow/libersystem/docs/todo/P02M0099.md:5706), current network and USB implementations, provider discovery, permission/bootstrap integration and verification infrastructure at commit `467f761df5a27b5409ffa3cd54e942485b4cf078`. This is a requirements checklist rather than an implementation design. The findings concern missing decisions that affect correctness and scope, not the expected absence of modem feature code.

1. **High - NetworkService cannot consume the link that context activation is supposed to grant.**

   The [activation item](/data/yellow/libersystem/docs/todo/P02M0183.md:25) and [definition of done](/data/yellow/libersystem/docs/todo/P02M0183.md:37) require IP traffic through NetworkService, but leave the attachment and configuration contract unspecified. Current [network bootstrap](/data/yellow/libersystem/src/user/services/core/src/network_service.rs:195) requires a `MAC` message, sizes Ethernet frames as MTU plus 14 bytes and constructs an Ethernet stack. It then [runs DHCP or applies its static fallback](/data/yellow/libersystem/src/user/services/core/src/network_service.rs:243). The [public network interface](/data/yellow/libersystem/src/idl/network.lsidl:403) exposes client networking operations, not an administrative operation for installing a context and its link configuration.

   Consequently, passing the IP datagrams named by the milestone to an ordinary network-provider channel will not establish a usable connection. The plan also leaves ownership of context-provided addresses, routes, DNS and MTU unanswered. Implementing those decisions inside the modem transport would violate the intended stack boundary; assuming existing Ethernet startup handles them would fail the completion condition.

   **Correct the activation item and definition of done** to identify the owner and versioned contract for context-specific link attachment, packet framing and address/route/DNS/MTU configuration. Choose a minimal supported network integration, including any necessary NetworkService changes, and name the privileged endpoint and grant issuer. Keep ordinary network clients unable to install or reconfigure links. Specify how activation succeeds or rolls back when network attachment is refused, and prove bidirectional traffic through the real NetworkService path.

2. **High - Activation after boot and context loss require network lifecycle work absent from the plan.**

   [NetworkService takes the first already-published NIC](/data/yellow/libersystem/src/user/services/core/src/network_service.rs:281), then [closes its subscription](/data/yellow/libersystem/src/user/services/core/src/network_service.rs:317). If no NIC exists at bootstrap, it [enters the unlinked serving path](/data/yellow/libersystem/src/user/services/core/src/network_service.rs:174). A modem context activated later is therefore not an attachment this implementation notices. With an existing virtio or USB Ethernet provider, publishing another provider also does not select it. The originating milestone explicitly identifies [NetworkService's missing persistent identity, link-state, detach/failover and reconnect ownership](/data/yellow/libersystem/docs/todo/P02M0099.md:6012).

   Even after fixing packet framing, a successful modem activation could leave traffic on the old NIC, and context deactivation or unplug could leave stale addresses and routes. This is an independent integration requirement, not something an explicit grant alone supplies.

   **Correct the context/device lifecycle and dependency scope** to allocate late attachment, provider/context identity and generation, selection policy, deactivation, withdrawal and reconnect work. Reuse [catalogue publication identities and withdrawals](/data/yellow/libersystem/src/idl/device.lsidl:179), and make old context handles and late events unable to affect replacements. State the supported active-context policy, including any one-context limit, and how it coexists with the existing NIC. Do not make completion depend on an unowned future network migration. Add guest assertions for activation after NetworkService is already online and for context loss/replacement.

3. **High - Separating subscriber identity does not settle authority for modem-management commands.**

   The [identity item](/data/yellow/libersystem/docs/todo/P02M0183.md:20) distinguishes identity reads from data use, but the adjacent [PIN/PUK item](/data/yellow/libersystem/docs/todo/P02M0183.md:23) never assigns those operations to a capability or identifies who may mint it. The parent requirement prohibits [ambient modem-management commands as well as subscriber identity](/data/yellow/libersystem/docs/todo/P02M0099.md:5711). A single modem connection with an identity-read restriction could still let every data client submit PIN/PUK attempts or change shared modem state.

   The existing [security vocabulary](/data/yellow/libersystem/src/idl/security.lsidl:12) has no modem grant, and the repository's established solution is a trusted factory that creates operation-restricted endpoints, as shown by [audio-admin](/data/yellow/libersystem/src/idl/audio.lsidl:42) and [PermissionManager's capture/playback grants](/data/yellow/libersystem/src/user/services/core/src/permission_manager.rs:574). A new LSIDL package does not register or grant itself through that path.

   **Correct the authority items and implementation scope** to define which endpoints permit state observation, data-context use, identity reads and PIN/PUK or other management operations. Name the trusted grant issuer, device/SIM/context scope and behavior when authority or the underlying device disappears. Include service deployment, bootstrap roles, generated protocol/client integration and PermissionManager policy. Require negative tests showing that an ordinary data client cannot read identity or invoke management operations, and that creating a service connection alone grants neither privilege.

4. **High - The service prerequisite also demands unfinished driver work without defining a shared boundary or staging.**

   The plan [claims to unblock USB CDC-MBIM](/data/yellow/libersystem/docs/todo/P02M0183.md:42), but requires [host tests of MBIM fragmentation and session/NDP tables](/data/yellow/libersystem/docs/todo/P02M0183.md:30), which the [waiting driver item](/data/yellow/libersystem/docs/todo/P02M0099.md:5706) itself owns. There is no modem provider in the [closed provider-kind vocabulary](/data/yellow/libersystem/src/idl/device.lsidl:151), and current [USB network transport](/data/yellow/libersystem/src/user/drivers/core/src/usb_net.rs:16) implements ECM while explicitly declining a live NCM path. Its existing [NCM parser](/data/yellow/libersystem/src/user/drivers/core/src/cdc.rs:530) is specifically built around NCM signatures, not a generic declaration that the requested MBIM path is already supported.

   Without deciding the driver-to-service wire and ownership of control framing, session demultiplexing and policy state, implementation can duplicate parsing in the service and xHCI or make each milestone wait for the other. The service's useful guest proof also has no stated backend: the [current USB attachment helper](/data/yellow/libersystem/src/harness/qemu-run.sh:868) and [gadget kinds](/data/yellow/libersystem/src/harness/usb-gadget.sh:73) provide no MBIM fixture.

   **Correct the interface, host-test and guest-gate items together** to stage the shared bounded provider contract before its consumers. Assign each parser/state machine to one production owner and put pure decisions in a host-testable leaf; the existing [service-logic contract](/data/yellow/libersystem/src/user/services/logic/Cargo.toml:8) explains the runtime restriction. Choose either a faithful service-side backend fixture for this milestone or an explicitly coordinated driver slice, and state which transport claims each proves. Identify a runnable guest scenario with observable activation, authorized traffic and identity denial, plus its image/backend prerequisites and [verification coverage registration](/data/yellow/libersystem/src/tools/verify-model/src/catalog.rs:892). A generic service-online marker would not prove the requested effect.

5. **Medium - Queue bounds do not define transaction completion or safe recovery of state-changing operations.**

   The [bounded-work item](/data/yellow/libersystem/docs/todo/P02M0183.md:28) addresses memory growth but leaves request correlation, fragment assembly expiry, command deadlines, cancellation, late replies and state invalidation unspecified. The [typed-state item](/data/yellow/libersystem/docs/todo/P02M0183.md:17) likewise provides no contract for learning registration/context changes after the first read. These decisions affect the PIN/PUK attempts and context activation explicitly required by the plan, not optional future features.

   A finite queue can remain permanently occupied by a silent modem. Retrying an uncertain PIN result can consume another attempt, while accepting a delayed activation reply after disconnect can resurrect a context that no longer exists. Host tests limited to malformed message shapes would not catch these validly framed but stale state transitions.

   **Correct the state, PIN/PUK, bounds and test items** to specify the minimum transaction/state machine: correlation and generation rules, byte/count ceilings for assemblies and pending work, bounded completion or an explicit uncertain outcome, cancellation/teardown, and handling of unsolicited state changes. State how fresh attempt counts are obtained and how unavailable or uncertain counts are represented, without automatic replay of attempt-consuming commands. Include host cases for timeouts, late/out-of-order replies, SIM/device replacement and queue exhaustion, alongside the framing tests.
