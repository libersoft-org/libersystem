1. **High - The public import interface has no defined provider boundary or capability delivery path.**

   The [interface item](/data/yellow/libersystem/docs/todo/P02M0187.md:17) describes what an application receives, but does not define what the service receives from the USB driver. The [PTP driver item](/data/yellow/libersystem/docs/todo/P02M0099.md:5734) is explicitly waiting for this milestone before implementing metadata enumeration, chunks and container/transaction validation. This plan also requires those validation tests without assigning their production ownership. The current [provider-kind vocabulary](/data/yellow/libersystem/src/idl/device.lsidl:151) contains no import/PTP provider, and [USB's public contract](/data/yellow/libersystem/src/idl/device.lsidl:386) only enumerates devices; it is not a PTP connection.

   Two implementations could therefore invent incompatible contracts or duplicate the same parsing and transaction state. Adding the package name alone also does not make a restricted import endpoint available to a client: the existing [permission granter](/data/yellow/libersystem/src/user/services/core/src/permission_manager.rs:113) requires both a declared capability and an actual boot-wired client.

   **Correct the interface, validation and dependency sections** to choose the driver/service split and bounded private provider protocol, identify the single owner of PTP container/session logic, and specify provider discovery, connection and withdrawal through the [existing catalogue](/data/yellow/libersystem/src/idl/device.lsidl:315). Name the IDL/generated-client, [deployment/bootstrap manifest](/data/yellow/libersystem/src/user/services/manifest.toml:1) and permission-grant changes. Define a read-only operation allowlist at the service boundary and keep any raw transport or future mutation authority private. Stage the contract/service work against the deferred transport so neither milestone requires the other to be complete before it can start.

2. **High - Paging the client response does not establish bounded memory for the device response.**

   The [pagination item](/data/yellow/libersystem/docs/todo/P02M0187.md:17) explains why returning all objects is unacceptable, but does not specify how handles are obtained or retained before the service emits pages. In the named [libgphoto2 PTP reference](https://raw.githubusercontent.com/gphoto/libgphoto2/master/camlibs/ptp2/ptp.c), `ptp_getobjecthandles` sends storage, format and association selectors, then receives an array; that request has no client-style page offset or page-size parameter. Its separate `ptp_getpartialobject` operation concerns object bytes, not enumeration pages. An implementation cannot assume its new page interface maps directly onto every supported camera.

   Collecting the entire handle list and metadata into a vector and then slicing pages would reproduce the allocation problem the plan is intended to prevent. The project's [complete-stream drainer](/data/yellow/libersystem/src/user/runtime/rt/src/lib.rs:1211) likewise collects all items, so selecting a generated stream type alone is insufficient. The instruction to preserve [all unnamed metadata](/data/yellow/libersystem/docs/todo/P02M0187.md:25) creates another unbounded input unless its opaque representation has explicit limits.

   **Correct the enumeration, metadata and chunked-read items** to select the supported PTP operation subset and a bounded strategy for responses without native paging: incremental parsing, bounded backing storage, or a declared limit with an honest refusal. Define page/metadata/chunk byte limits, retained cursor/session limits and aggregate memory accounting. Specify how downstream backpressure or an abandoned cursor cancels or drains the upstream transaction without blocking the entire service. Bound opaque metadata and keep unsupported MTP/vendor operations unsupported. Test a large enumeration and an over-limit response at the device-facing boundary, not only page slicing after allocation.

3. **High - Object identities and pagination cursors have no device/session lifetime.**

   The [metadata item](/data/yellow/libersystem/docs/todo/P02M0187.md:25) names an identity and parent, while the rest of the interface names devices, storages and chunked reads. It does not define which device/session owns those identifiers, whether a page cursor belongs to one caller, or what remains valid after removal, reset or a storage/object-set change. This matters directly to the [required mid-transfer removal behavior](/data/yellow/libersystem/docs/todo/P02M0187.md:28).

   A cached object number or continuation could otherwise resolve against a replacement session, mix objects from different devices, or silently continue against a changed enumeration. Transaction-ID validation alone does not establish the lifetime of an application-visible object or authorize one client to use another client's cursor. The repository already solves the analogous provider problem with [binding/provider generations and explicit withdrawal](/data/yellow/libersystem/src/idl/device.lsidl:179).

   **Correct the identity, enumeration and read contracts** to bind objects, parents, cursors and transfers to a specific provider/storage/session generation and the connection or capability that owns them. Choose snapshot semantics or explicit stale/restart behavior when an enumeration changes. Invalidate outstanding objects/cursors on loss of that session, serialize shared device transactions as required, and ensure reconnect never silently resumes an old object by numeric handle alone. Add cross-device, stale-cursor and reconnect tests using the production identity checks.

4. **High - "Partial import rather than a file" has no completion protocol or publication owner.**

   The [partial-import item](/data/yellow/libersystem/docs/todo/P02M0187.md:28) promises an outcome, but the interface only describes bounded reads. It does not define a transfer object, terminal success/error message, confirmed byte count, or who decides when bytes become a completed destination file. A short chunk or closed channel cannot distinguish successful EOF from a lost device. The runtime's [explicit stream-completion convention](/data/yellow/libersystem/src/user/runtime/rt/src/lib.rs:1205) documents exactly this ambiguity.

   If a consumer publishes whatever bytes arrived, unplugging can produce an ordinary-looking truncated photo even if the service eventually reports an error. If the service instead persists imports itself, that introduces a destination storage capability and lifecycle that the plan does not specify. Existing [transactional storage writers](/data/yellow/libersystem/src/idl/storage.lsidl:283) publish only on explicit commit and abort on close, with staging limits; those semantics cannot be assumed for every generic streaming write.

   **Correct the transfer item and definition of done** to choose the ownership boundary. A source-only service can return a typed terminal result carrying complete/partial status, bytes delivered and failure cause, with success dependent on the validated final device response. Name the consumer obligation to publish only after that result. If destination publication is owned here, specify scoped storage authority, staging limits and commit/abort behavior using existing storage mechanisms. Define cancellation, timeout and disconnect outcomes without implying automatic resume or rollback. Test a failure after some valid chunks and prove it is never reported or published as a successful complete import.

5. **Medium - The emulated-device gate has neither a selected fixture nor an observable acceptance contract.**

The [current QEMU USB setup](/data/yellow/libersystem/src/harness/qemu-run.sh:868) attaches no PTP/MTP device, and the PTP transport is still deferred. An emulator is feasible: [QEMU documents `usb-mtp` with a host directory](https://www.qemu.org/docs/master/system/devices/usb), and the installed `qemu-system-x86_64 -device help` lists it. Availability is not yet a configured PTP test, and does not justify expanding the service to MTP extensions.

   Without a selected fixture and protocol subset, a gate could prove only service startup or a hand-built in-process enumeration, while missing the real read-only boundary, response limits and unplug result.

   **Correct the host/guest test items** to select a PTP-capable emulated fixture and state which operations it proves; evaluate the common PTP subset of `usb-mtp` or use a bounded dedicated fixture. Declare source data and cleanup, dependency staging, multiple-page enumeration, known object-byte verification, stale identity handling, removal after a partial read, and attempted mutation through a read-only client. Name gate/test coverage and image prerequisites in the [verification catalogue](/data/yellow/libersystem/src/tools/verify-model/src/catalog.rs:892), including [gate-list/release-required consistency](/data/yellow/libersystem/src/tools/verify-model/src/main.rs:1591) where applicable.
