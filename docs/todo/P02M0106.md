# P02M0106 - Identity: accounts, authentication and per-user authority

Status: PROPOSED, NOT STARTED. The system has no notion of a person. It governs COMPONENTS
thoroughly - PermissionManager grants each one exactly what its manifest declares, Domains
account its resources, and every authority is a capability somebody handed over - and it
governs USERS not at all, because there are none. Nothing can be owned, nobody logs in, and
"who did this" has no answer.

This is what keeps P02M0006k open, and it is not console work: P02M0006's console is finished down to
PTYs, signals and job control. Its last sub-track wants a session that locks and a login that
gates one, and both are blocked on a layer that does not exist. That sub-track moves here.

## What already exists, which decides how much of this is new

Three foundations are in place and this milestone is largely about connecting them.

The capability model IS the authorisation mechanism, and it is complete. Nothing here needs a
new enforcement primitive: a handle carries rights, rights only narrow, and no ambient authority
exists. What is missing is not enforcement but the ANSWER to "which capabilities does this
person get" - policy, in the same mechanism/policy split PermissionManager already uses for
components.

LiberFS already carries the field this needs and deliberately does not read it: an
`owner_tag: [u8; 16]`, documented as "an opaque owner / ACL tag, stored but never interpreted
by the filesystem". Sixteen bytes per inode, on disk today, written and preserved by every
operation, waiting for something to give it meaning. That is a substantial head start - the
on-disk format does not have to change - and it is also a constraint worth reading carefully:
sixteen bytes is an identifier, not an access-control list, so whatever design lands here must
express ownership as a tag that a policy resolves rather than as permissions stored per file.

The building blocks for credentials are present. `SYS_RANDOM_GET` supplies entropy, and
`bootproto::sha256` is in the tree. Neither is sufficient on its own - see the password item
below, because SHA-256 is the wrong primitive for storing one - but the system is not starting
from nothing.

## The question this milestone has to answer first

What IS a user account in a capability system? This is not rhetorical, and getting it wrong is
the standard way these designs fail.

The Unix answer is a uid, a gid list, and permission bits interpreted by every filesystem
operation, with setuid as the escape hatch. It is familiar and it is a poor fit here: it makes
authority AMBIENT - a process acts with the authority of whoever started it, implicitly, for
every operation, which is precisely what the capability model exists to refuse. It is also the
source of the whole confused-deputy family of bugs that setuid programs are famous for.

The capability answer, which Fuchsia takes and KeyKOS took before it, is that a user is not a
subject the kernel checks against - it is the ROOT OF A CAPABILITY SET. Logging in does not
change what a process "is"; it hands a session the capabilities that person may use, and
everything launched from that session inherits a subset. There is no uid to check because there
is nothing to check against: a program either holds the handle or it does not.

The recommendation is the capability answer, with one concession to reality: an identifier is
still needed, because the filesystem stores a 16-byte tag and a log line saying "who" needs a
name. So an account has a stable identifier used for OWNERSHIP AND ATTRIBUTION, and authority
comes from the capabilities its session holds - never from the identifier. The identifier
answers "whose file is this" and "who ran that"; it never answers "may this be done".

## Scope

- [ ] The account model, as typed records. A stable identifier (which the filesystem's
  `owner_tag` can carry), a display name, the account's state (enabled, locked, expired), and
  the reference to what its sessions may be granted. Deliberately NOT: permission bits, a group
  list interpreted by the kernel, or anything the filesystem is expected to evaluate. Groups as
  a convenience for administering many accounts are reasonable; groups as a thing the storage
  layer checks are the Unix model arriving through the back door.
- [ ] Credential storage that is correct the first time, because this is the item where a
  plausible-looking mistake is permanent. Passwords are not stored, and are not hashed with
  SHA-256 either: a general-purpose hash is fast, which is exactly the property an attacker
  wants, so a memory-hard derivation (Argon2id, or scrypt) with a per-account random salt and
  recorded parameters is the requirement. The parameters go in the record so they can be raised
  later without invalidating existing credentials. Comparison is constant-time. `SYS_RANDOM_GET`
  supplies the salt; the derivation itself has to be written or vendored, and `bootproto::sha256`
  is a building block for it, never the answer by itself.
- [ ] An AuthService that owns credentials and answers one question: does this proof of identity
  match this account. It holds the credential store and nothing else reaches it - not the shell,
  not the console, not PermissionManager. Verification is rate-limited with a delay that grows
  on failure, because an unlimited-attempt check is a password of whatever length the attacker
  is willing to wait for. Failures are logged with the account and the source; successes too,
  because "when did this account last authenticate" is the question after an incident.
- [ ] Login as a governed component, not as shell logic. It runs before a session is usable,
  holds only the AuthService client and the console it prompts on, and on success asks for a
  session bound to the account. It must not be able to read the credential store, and putting
  it in the shell would give every shell that reach.
- [ ] Sessions carry identity and the authority derived from it. SessionService already mints a
  session per VT; a session gains the account it belongs to and the capability set that account
  is entitled to, which is what a launch inherits. This is the load-bearing item: it is where
  "logged in as" becomes "may do", and it is also where per-session locale from P02M0105 belongs,
  since both answer "for whom is this session".
- [ ] Lock and unlock, with an idle timeout. Locking detaches the display and input from the
  session without stopping what runs in it - a build must survive a lunch break - and unlocking
  requires the same verification as login. The timeout is a policy value, and what happens to a
  foreground job that writes while locked has to be decided rather than discovered: the
  recommendation is that output accumulates in the VT's scrollback exactly as when the VT is not
  in the foreground, which is machinery P02M0006d already has.
- [ ] File ownership: give `owner_tag` meaning. Files acquire the tag of the account that
  created them, StorageService reports it, and the tools that list files can show it. Note what
  this does NOT do: the tag does not grant or deny anything by itself, because a capability
  already decided whether the caller may open the file at all. Ownership here is attribution and
  the input to policy, not a second enforcement mechanism competing with the first.
- [ ] Home directories, or the honest reason there are none. A per-account directory that a
  session's storage capability is scoped to is the natural shape and it is small work once
  sessions carry identity - the capability is already scopeable, which is what makes this cheap
  rather than a new mechanism.
- [ ] Administration tools, one verb each, in the shape this tree uses. Creating, listing,
  enabling and disabling accounts, and changing a password - the last being the one operation an
  ordinary account may perform on ITSELF and on nothing else, which is a policy statement that
  must be expressible rather than a special case in a tool.
- [ ] The first-boot problem, decided rather than defaulted. A system with accounts and no
  accounts configured is either unusable or wide open. The options are a first-boot enrolment
  that creates the initial account interactively, or a build-time account whose credential must
  be changed on first login. Shipping a fixed default credential is the third option and it is
  how appliances end up on botnets; it is named here to be refused explicitly.
- [ ] Recovery, decided at the same time. An account whose credential is lost, or a system whose
  only administrator is gone, needs a defined path - a recovery credential, a console-only
  escape gated by physical presence, or a documented statement that reinstallation is the
  answer. Every one of those is defensible; leaving it undecided means the path gets invented
  under pressure by whoever hits it first, which is how a backdoor gets added and never removed.
- Done when: a console presents a login, an account authenticates against stored credentials
  that are salted and memory-hard, the resulting session carries that account's identity and
  capability set, what a program may do follows from the capabilities its session was granted
  and never from a checked identifier, files record their creator in the tag LiberFS already
  stores, a session locks and unlocks without disturbing what runs in it, accounts are
  administered by governed tools, the first-boot and recovery paths are decided and documented,
  and tests green on all three architectures.
- Explicitly deferred, with reasons: remote authentication and directory services (LDAP,
  Kerberos) are network policy on top of this layer, not part of it; multi-factor and hardware
  tokens need device support that can be added once one factor works; full ACLs on files are
  not proposed at all, because the capability model already answers "may this be opened" and a
  second mechanism answering the same question differently is how systems acquire security bugs
  nobody can reason about; and per-account resource quotas are a natural pairing with Domains
  but belong with P02M0010's policy work rather than here.
- Concept: the capability model (the authorisation mechanism this needs no addition to), P02M0009
  (PermissionManager, the same mechanism/policy split applied to components rather than people),
  P02M0006d/P02M0006k (the VT sessions this binds identity to, and the lock/login sub-track that moves
  here), P02M0013-P02M0027 (LiberFS, whose `owner_tag` this finally gives meaning), P02M0010 (Domains, if
  per-account quotas follow), and P02M0105 (per-session locale, which answers the same "for whom"
  question from the other side).
