# P02M0205 - A stored device policy holds from the first bind of every boot

Status: PLANNED (2026-10-15) - the owner's decision is recorded below; nothing is implemented yet, by his instruction
("neimplementuj").

THE OWNER'S DECISION (2026-10-15). The question came out of P02M0203's plan audit: should a stored `disable` keep a
device off after a reboot, for every driver? Today it does not. The owner chose that it should: "OK, volim B, sepis
ten milestone, neimplementuj".

WHAT IS WRONG TODAY (read from the tree on 2026-10-15):
  - THE VERBS. `lsdev --disable` tears a device down at once and stores `device.policy.<device> = disabled`.
    `lsdev --select` stores a preferred driver as `device.policy.<device>.select`. Both live in ConfigService under
    the reserved namespace only DeviceManager writes, through its `POLICYOWNER` connection.
  - THE ORDER AT BOOT. DeviceManager reads the stored records only when that connection arrives as `POLICYCFG`, and
    ServiceManager sends it after the whole bring-up loop. By then every driver has bound:
    - the bootstrap disks in phase one, before any volume exists;
    - every other driver in phase two, which `DRIVERS` starts the moment the system StorageService reports.
  - WHAT THE LATE READ DOES. `load_stored_policy` leaves a device that is already bound running: "is disabled in stored
    policy and is already bound; it stays up and will not bind again". Only the next bind is refused (`begin_bind`).
    A stored selection likewise waits for the next bind.
  - A DEVICE THAT ARRIVES LATER, through `admit_arrival` (hot-plug), is bound without its stored records being read at
    all.
  - THE RESULT. A disabled device is running again after every reboot, and a selected driver is not the one that binds
    at boot.

WHY THE POLICY IS NOT SIMPLY READ THROUGH CONFIGSERVICE EARLIER:
  - ConfigService is launched from the volume through ProcessService. It depends on ProcessService and StorageService,
    and it starts after phase two has begun.
  - Holding phase two until ConfigService answers would break a hibernation restore.
    - Until a hibernation image's verdict, only HibernationService's dependency closure starts: DeviceManager,
      LogService, ProcessService, StorageService and TpmService. ConfigService is not in it.
    - The TPM driver is volume-staged, so it binds in phase two. Holding phase two would keep the TPM from
      TpmService, and a TPM-sealed image could not be unsealed for the verdict.
  - Starting ConfigService before the verdict would put a service that writes the volume into the set the restore
    keeps minimal. It is kept minimal because anything written before a restore can contradict the image.

THE DESIGN: THE PERSISTED TREE IS READ ONCE, READ-ONLY, AT PHASE TWO.
  - ConfigService persists its tree to `vol://system/libexec/config_service/config.tree`: `LSCFGTR1`, a count, then
    length-prefixed keys and values. It is the file's only writer, it writes the whole file at once, and it starts only
    after phase two. Nothing can be writing the file while DeviceManager reads it.
  - The tree's codec moves into one shared library, used by ConfigService to read and write and by DeviceManager to
    read. The format keeps one definition, and an existing tree reads the same.
  - ServiceManager sends DeviceManager `POLICYTREE` with `DRIVERS`: a connection scoped to ConfigService's persistence
    directory (`open_storage_directory`) and narrowed to read. DeviceManager already holds a ConfigService connection
    that can read every key, so this exposes nothing new.
  - Before any phase-two bind, DeviceManager reads every node's `device.policy.` records from the tree. If the tree is
    missing, unreadable or has the wrong magic, this boot has no stored policy: drivers bind as today, and DeviceManager
    says so once.
  - THE RULES:
    1. A phase-two device with a stored disable is not bound. It goes from `Unbound` to `Disabled`, and its consumers
       never see a provider.
    2. A phase-two device with a stored selection binds its selected driver first. A selection naming a driver this
       image no longer declares for the device is reported and not applied, as `load_stored_policy` does today.
    3. A bootstrap device with a stored disable is stopped as the live verb stops it, before any media role is handed
       out. This holds only for a device that does not hold `vol://system` (P02M0203).
       - DeviceManager names the stopped disks in its answer to `DRIVERS`, a new tagged answer, by their hand-off
         index.
       - ServiceManager then closes those disks' role connections. The media, ISO or UDF instance receives the empty
         tag, as on a machine without that disk, so a disabled data disk is never mounted.
       - The device that holds `vol://system` is never stopped. A stored disable on it is kept and ignored while it
         holds the volume.
       - Until DeviceManager knows which device that is, no bootstrap device is stopped, which is P02M0203's safe
         default. ServiceManager therefore sends `SYSVOL` before `DRIVERS`.
    4. A device that arrives after phase two, through `admit_arrival`, has its records read before its first bind:
       from the boot read until `POLICYCFG` arrives, and through DeviceManager's owner connection after.
  - `POLICYCFG` still arrives at the end of bring-up. `load_stored_policy` then finds the same records and changes
    nothing for the devices already decided. `forget_absent_incidents` writes as it does today, after the verdict.
  - Nothing is written before ConfigService runs. The boot read is read-only, which keeps it out of a restore's way.

WHAT IT COSTS:
  - A bootstrap data disk with a stored disable is still bound in phase one, because its record is on the volume, and
    is stopped at phase two. It is never handed to a media instance.
  - DeviceManager reads one file once per boot, at phase two.
  - The facts in `DRIVERS`' answers (`NET`, `GPU`, `SND`, `INPUT`, `USB`) report a disabled device as absent, which is
    what it is for that boot.

CHANGES TO OTHER MILESTONES:
  - P02M0203. Its rule "WHAT DOES NOT CHANGE: WHEN A STORED POLICY TAKES EFFECT" holds until this milestone lands. This
    milestone changes its oracle's last step: after the cold boot, the disabled decoy is stopped at phase two and
    `lsdev` reads it `disabled`.
  - ORDER. This lands after P02M0203. It needs the volume's device (`SYSVOL`) and the node's mark.

- [ ] 1. THE TREE'S CODEC AS A SHARED LIBRARY.
  - ConfigService is switched to it with the format unchanged.
  - Host tests: a round trip, a truncated record, the wrong magic, an empty tree, and a tree written by today's
    ConfigService read back the same.
- [ ] 2. SERVICEMANAGER.
  - `SYSVOL` before `DRIVERS`.
  - The read-only `POLICYTREE` connection with `DRIVERS`.
  - The new tagged answer naming the stopped bootstrap disks, whose role connections it closes before any media
    instance starts.
  - The answer count in `drive_runtime_drivers` updated.
- [ ] 3. DEVICEMANAGER.
  - The boot read, and rules 1 to 4.
  - The decisions themselves in `driver_binding`, so a host test can drive them.
  - One console line per device decided: "is disabled in stored policy; it is not bound this boot", or "... it is
    stopped before its disk is handed out".
  - `load_stored_policy` at `POLICYCFG` leaves the devices already decided as they are.
- [ ] 4. HOST TESTS in `driver_binding`, each watched failing before it passes:
  - a phase-two disable;
  - a selection, and a stale selection;
  - a bootstrap disable against the volume's device, and before `SYSVOL`;
  - an arrival with a stored disable.
- [ ] 5. THE ORACLE, in QEMU: x86_64 first, the ports at the end of the job.
  - A PHASE-TWO DEVICE. The `qemu-tpm-tool` scenario already disables and re-enables the TPM. It gains a cold boot on
    its persistent disk between the two:
    - after that boot the TPM is not bound;
    - `tpm random 8` answers unavailable from the first moment;
    - `lsdev` shows the device disabled;
    - `lsdev --enable` binds it, and `tpm random 8` answers.
  - A BOOTSTRAP DATA DISK. `boot-volume-controllers` (with P02M0203's decoy case) gains a FAT data disk on a second
    controller of the same kind:
    - disabled live, then a cold boot: the disk is stopped at phase two, `vol://media` is absent, and no storage
      instance fails;
    - enabled, then the next boot: `vol://media` is there again;
    - the system disk is untouched throughout.
  - A HIBERNATION RESTORE. `hibernate` passes with a stored disable on an unrelated device present: the boot read runs
    before the verdict, writes nothing, and changes nothing for the restore.
  - A BOOT WITH NO STORED TREE, the first boot of a fresh disk. Every driver binds as before, and DeviceManager's line
    saying there is no stored policy is asserted by `boot-volume-controllers`' first boot.
