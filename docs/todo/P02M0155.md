# P02M0155 - The loader searches every disk in the machine for a file that is not there

Status: REOPENED (2026-08-26). Two independent audits of the closed milestones found 1 verified defect between them; they are the last two sections of this file. Was COMPLETE (2026-08-25). BOOT CORRECTNESS AND BOOT TIME. NOT A PHASE-2 COMPLETION GATE.

## Goal

Stop the loader spending half a minute looking for a file the medium was never built to carry, stop
it saying something false about the firmware while it does, and take the two structural costs that
made the search expensive out of the FAT reader for every caller - not just this one.

Then make the boot report say what actually happened: the DMA isolation summary that prints before
any device has bound, the topology fact printed twice, and seven services announcing themselves
with one indistinguishable line.

## What is there now

Measured on 2026-08-25, from an interactive `./run.sh --display spice` boot of
`.build/boot/libersystem.iso` on x86_64 under OVMF.

- **THE LOADER STALLS FOR ABOUT THIRTY SECONDS** on this line:

  ```
  loader: bootstrap set assembled from the system volume
  loader: the firmware did not mount the boot volume; reading it as FAT
  loader: packages loaded
  ```

- **THE MESSAGE IS FALSE.** The firmware did mount the boot volume. It had already read
  `etc/system-volume.uuid` through `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL` in `read_pairing` before the
  banner - had it not, that read would have printed this same line first, and `PAIRED_UUID` would be
  `None`, which prints `the boot medium names no system volume`. Neither happened.

- **THE FILE IS `volume.pkg`, AND THE SHIPPING MEDIUM DOES NOT CARRY ONE.** The message's position
  fixes which read it belongs to: it is after `bootstrap set assembled` (`main.rs`) and before
  `packages loaded` (the x86_64 backend), and the only unconditional `read_boot_file` between those
  two points is the factory-archive read. `mkimage.sh` stages `volume.pkg` on the TEST medium and
  `system-volume.img` on the shipping one; the split is deliberate and documented there.

- **THE LOADER CANNOT TELL "NOT THERE" FROM "COULD NOT BE READ".** `uefi::file::read_file` answers
  with an `Option` and drops the firmware's `Status`, so `read_boot_file` treats
  `EFI_NOT_FOUND` exactly like a firmware that declined to mount the medium - and falls back to the
  block-level FAT scan. The distinction already has a type: `blockio::FileRead::{Absent, Unreadable}`
  exists for it, and the comment on `FirmwareVolume` says in as many words that this backend cannot
  make it.

- **THE FALLBACK IS EXPENSIVE, AND IT IS PAID PER DEVICE.** `read_from_fat` walks every Block I/O
  handle and calls `fat::FatFs::mount` on each. Mount is not cheap:

  - `audit_ownership()` walks every directory and follows every cluster chain on the volume. Its own
    comment names the cost: "a metadata walk at mount: every directory read once, every chain
    followed once".
  - `mirrors_disagree()` then compares both FAT copies sector by sector.

  On this ESP, measured with `minfo`:

  | | |
  | --- | --- |
  | FAT16, cluster size | **1 sector = 512 bytes** |
  | FATs | 2 x 254 sectors |
  | `system-volume.img` | 18 264 064 B = 35 672 clusters |
  | staged `kernel` | 6 320 696 B = 12 345 clusters |
  | chain hops the audit walks | **~48 000** |

  Every one of those hops is a separate uncached read: `next_cluster` re-reads the FAT sector for
  each cluster and allocates a fresh `Vec` to do it, and `read_fs_sectors` under it issues **one
  512-byte device request per sector**, which `FirmwareDisk::read_block` turns into one firmware
  `ReadBlocks`. On an emulated ATAPI CD that is ~48 000 command round-trips per mount attempt.

- **AND THE SEARCH NEVER LATCHES.** `with_boot_medium` records `BOOT_MEDIUM` only when the visitor
  returns `true` - that is, only when the file was found. A search that misses pays the mount cost
  again on the next FAT device, and on the next read.

- **THE RESULT IS DISCARDED.** `volume_pkg` comes back `None` and the boot continues exactly as it
  would have had nothing been searched for. The half minute buys nothing at all.

- **THE SYSTEM VOLUME IS ASSEMBLED THREE TIMES.** `read_from_system_volume` calls
  `blockio::assemble_bootstrap` on every call, and `main` calls it for the kernel, then for
  `etc/boot.manifest2`, then possibly for `etc/boot.manifest`. Each assembly reads every program the
  bootstrap list names, off the volume, again. The boot log shows the receipt: `bootstrap set
  verified against a SIGNED etc/boot.manifest2` twice.

- **THE DMA SUMMARY PRINTS BEFORE ANY DEVICE HAS BOUND.** `dma_policy::report` says of itself "SAID
  AT THE END RATHER THAN PER DEVICE, because the question a reader has is 'is anything reaching
  memory untranslated', and the answer is a list rather than a scattering of lines" - and it is
  called from `report_machine()`, at the top of `boot_userspace`, before userspace exists. What a
  reader sees is:

  ```
  dma: DEGRADED ISOLATION - 0 device(s) master the bus untranslated (enforcing=false)
  dma: DEGRADED ISOLATION - device type 2 at 00:01.0 masters the bus UNTRANSLATED
  ...
  ```

  a summary that contradicts the ten lines under it, followed by the exact scattering it exists to
  replace. The types are printed as raw numbers - `2`, `18`, `256` - two lines above the same log
  writing `driver.virtio-blk`.

- **THE TOPOLOGY FACT IS PRINTED TWICE.** Discovery says `numa: this machine's firmware published no
  SRAT (rsdp 0x7f77e014)`; the boot report then says `numa: this machine reported no memory topology
  - one pool, no locality`. Two lines, one fact, on every machine without an SRAT - which is every
  ordinary QEMU boot.

- **SEVEN SERVICES REPORT ONE INDISTINGUISHABLE LINE.** `StorageService: online` seven times: the
  system volume, media, iso, udf, usb and the two memory volumes. The kernel boot suite already
  works around it - "They report the same line, so the count is what says the whole set came up" -
  so the test asserts a count where it could assert a set.

- **THERE IS NO IOMMU IN THE ORDINARY PROFILE.** `qemu-run.sh` attaches no `virtio-iommu-pci` on any
  architecture. The only profile that has one is the `qemu-virtio-iommu-x86_64` gate, which supplies
  it through `QEMU_EXTRA`. So the isolation this tree implements is exercised by one gate and by no
  ordinary run, and every developer boot prints eleven DEGRADED lines that describe the harness
  rather than the system.

## Work

- [x] **M1 - A file that is not there is not a firmware that did not mount the medium.**
  - `uefi::file` gains a reader that carries the firmware's own answer back: found, absent, or an
    error the firmware named. `read_file` keeps its `Option` shape for the callers that only want
    the bytes.
  - `read_boot_file` falls back to the block-level FAT scan only when the firmware could not be
    asked (no `root`) or answered with a real failure. `EFI_NOT_FOUND` ends the read.
  - The message goes with it: what is printed says which of the two happened, and it is printed
    where it is true.

- [x] **M2 - One FAT sector cache, so a chain walk stops re-reading the table.**
  - `next_cluster` keeps the sectors it read. A FAT16 sector holds 256 entries and a FAT32 sector
    128, so a walk down a chain reads the table once per 256 (or 128) clusters instead of once per
    cluster.
  - TWO SLOTS, not one, and finding that out is what the measurement was for. A single slot cut a
    2000-cluster walk from 3002 device requests to 1747 and no further: `ChainCursor` carries Floyd
    cycle detection, so every walk has TWO cursors half a chain apart, and they evicted each other
    on every hop. Two slots with an exact LRU is what the access pattern actually is - 11 requests.
  - The buffer is allocated once, not per call - the current code allocates a `Vec` for every hop.
  - Every write path invalidates it. A cache that can go stale under `set_fat_entry` is worse than
    no cache, because the driver would then allocate against its own out-of-date copy.

- [x] **M3 - Contiguous clusters are read in one request.**
  - `read_fs_sectors` issues one `BlockDevice::read_blocks` for the whole span instead of one
    `read_block` per 512-byte sector.
  - `read_chain` and `read_contiguous` coalesce consecutive clusters into a single read, bounded so
    one request never exceeds what a device stack will take. A file written contiguously - which is
    every file `mcopy` puts on an ESP - becomes a handful of requests rather than tens of thousands.
  - `FirmwareDisk` overrides `read_blocks` to make the whole span one firmware call, and falls back
    to the per-block loop when the driver demands an alignment that needs the bounce buffer.

- [x] **M4 - A read-only mount does not audit, and does not pretend it did.**
  - `FatFs::mount_read_only` skips `audit_ownership` and `mirrors_disagree`. The audit protects
    WRITES; the loader never writes, and everything it reads is checked against a signed manifest
    afterwards, which is a stronger statement about the bytes than a cross-link audit is.
  - The mount records WHY it will not write. `is_degraded` stays a `bool` and keeps every existing
    caller's behaviour, and a new accessor tells "not checked" from "checked and not sound" - which
    is the distinction the existing comment insists must not be collapsed.
  - Cycle safety is unaffected: `ChainCursor` carries Floyd detection on every walk, so an
    unaudited mount still cannot be made to loop forever by a crafted chain.

- [x] **M5 - The boot medium is latched when it mounts, not when it answers.**
  - `with_boot_medium` records the medium as soon as a FAT volume mounts on it. What identifies the
    boot medium is that it IS one, not that it happens to carry the file being asked for.

- [x] **M6 - The system volume is assembled once.**
  - `read_from_system_volume` assembles the bootstrap set on the first mount and not on the later
    ones. Three reads of one volume produced three assemblies, each reading every program the list
    names.

- [x] **M7 - The DMA report is printed once the devices have bound.**
  - The summary moves to after the service set is up, which is when the answer to "is anything
    reaching memory untranslated" is actually known. The per-device line stays where it is: it is
    immediate and it names the device.
  - Device types are printed by name. The table already exists in a userspace tool; it moves to
    `abi`, beside the constants it matches, and both callers use it.

- [x] **M8 - One line per fact in the boot report.**
  - The topology absence is recorded where it is discovered and printed once, by the report, with
    the reason in it. The refusal paths keep their own lines: they carry a payload the baseline
    cannot, and they appear only on unusual machines.
  - `StorageService` names the volume it came up on. The kernel boot suite then asserts the SET of
    volumes rather than a count of identical strings.

- [x] **M9 - The x86_64 profile can be booted with an IOMMU in it, and it is `--iommu` rather than
  the default - which is a MEASUREMENT, not caution.**
  - `qemu-run.sh` attaches `virtio-iommu-pci,boot-bypass=on` and gives every virtio endpoint
    `iommu_platform=on`, so it asks the guest for `VIRTIO_F_ACCESS_PLATFORM`. `run.sh` documents the
    switch.
  - Watched to boot before it was called done, which is what found the reason it cannot be the
    default - see Results.

## Results

Measured on 2026-08-25.

- **THE FAT READER, counted through a block device that records both sectors moved and REQUESTS
  made.** A 2000-cluster (1 MiB) file on a FAT16 volume with 512-byte clusters - `build_fat`'s
  geometry, which is also `mformat`'s for the ESP this system boots from:

  | | before | after |
  | --- | --- | --- |
  | mount (the ownership audit walks the volume) | 2049 requests | 53 |
  | walk the chain to its far end (a ranged read) | 3002 requests | 11 |
  | read the whole file | 5001 requests | 12 |

  The "before" column was measured on this tree with the cache forced to miss and the run bound set
  to one cluster - the two behaviours the milestone replaces - rather than estimated.

- **AND A READ-ONLY MOUNT DOES NOT WALK THE VOLUME AT ALL**: 84 sectors for the audited mount of
  that fixture against 8 for `mount_read_only`, pinned by a test at a factor of ten.

- **THE BOOT ITSELF**, `./run.sh` on the shipping ISO. No fallback line, no stall, and the loader
  goes straight from the bootstrap report to the packages:

  ```
  loader: bootstrap set verified against a SIGNED etc/boot.manifest2     <- once, not twice
  loader: kernel read from the system volume
  loader: signed manifest verified - release 0.0.1, key 7e570001, ...
  loader: kernel loaded
  loader: bootstrap set assembled from the system volume
  loader: packages loaded
  ```

  and the kernel's own report says one thing per fact:

  ```
  boot OK - kernel is up, starting userspace
  numa: no memory topology - one pool, no locality (this machine's firmware published no SRAT)
  ...
  userspace: StorageService: online (vol://system)
  userspace: StorageService: online (vol://media)          <- seven volumes, seven names
  ...
  dma: DEGRADED ISOLATION - 11 device(s) master the bus untranslated (enforcing=false)
  dma:   virtio-blk at 00:01.0                             <- named, and only at the end
  ...
  shell attached - type 'help', or 'exit' to halt
  ```

- **THE THREE NEW FAT TESTS AND THE THREE NEW FIRMWARE TESTS FAIL ON THE OLD BEHAVIOUR** by
  construction: two of them are request-count bounds two orders of magnitude under it, one asserts a
  `Trust` state that did not exist, and the firmware ones assert a `FirmwareRead` variant that did
  not either.

- **AND THE WHOLE MACHINE UNDER TRANSLATION, WHICH IS WHERE IT STOPS.** `./run.sh --iommu` on the
  shipping ISO:

  ```
  iommu: virtio-iommu is translating - bypass is off and read back as off
  iommu: virtio-iommu present, enforcing=true, healthy=true
  iommu: 00:02.0 attached to domain 1
  ...
  dma: every bus-mastering device is translated
  ```

  Nine endpoints bind and run behind it: four `virtio-blk`, `virtio-net`, `virtio-console`,
  `virtio-input`, `virtio-pointer`, `virtio-snd`. The DHCP exchange, the storage stack and the
  console all work.

- **`virtio-gpu` DOES NOT, and that is why the controller is not the default.** Behind a translating
  controller not one control-queue request completes: `GET_DISPLAY_INFO` times out into the driver's
  fallback size, `RESOURCE_CREATE_2D` then fails, the driver exits, and DeviceManager restarts it
  three times before giving up. The same with `virtio-gpu-pci` in place of `virtio-vga`, so it is
  not the VGA-compatible device model; and `iommu: map refused` never appears, so the kernel's
  mappings are made. What fails is the round-trip itself, on the one driver of seven that polls its
  queue instead of taking an interrupt on it. **This needs its own milestone; it is a defect the
  controller revealed rather than one it caused.**

- **`xhci` does not bind either - with the controller AND without it.** It was already failing on
  the tree as it stood, so it is not this profile's doing and not this milestone's to fix.

## What this milestone found on the way, and did not fix

- **TWO GATES TESTED WHATEVER MEDIUM WAS BUILT LAST, AND SAID NOTHING ABOUT IT.**
  `check-signed-boot.sh` and `check-secure-boot.sh` both read `.build/boot/efiboot.img`, which is a
  BY-PRODUCT: every medium this tree assembles writes that one path, so whichever `mkimage` ran last
  owns it. Any gate before them that runs the test suite leaves the TEST medium there - which
  carries the factory archive and no system volume - and `signed-boot` then failed on a file it
  never meant to read (`::/system-volume.img not found`). The worse outcome is the quiet one: a run
  in which it PASSES, having proved its refusal on a medium nobody ships.
  **FIXED HERE**: both gates extract the ESP from `libersystem.iso`, which is the artifact they
  already require two lines up. Verified by clobbering the by-product with the test medium's ESP and
  running both gates: they pass.

- **`./image.sh` AND `./test.sh` FIGHT OVER THE SYSTEM VOLUME, AND `check.sh` RUNS BOTH.**
  `image.sh` builds the volume WITH a kernel on it (a shipping medium's loader reads the kernel off
  the volume) and pairs the medium to that volume's uuid. `build.sh --part volume` builds it WITHOUT
  one and gives it a new uuid. They write the same file. So:
  - after `./image.sh`, a test run boots the SHIPPING kernel - the loader prefers the volume's - and
    the suite never runs. What the harness said about that was `TIMEOUT after 3m; last test:
    unknown`, three times, before the guest log was read closely enough to see which kernel booted.
  - after `./build.sh --part volume`, the medium's pairing names a volume that no longer exists, so
    `signed-boot`'s selected-source case boots with no volume at all and its refusal never happens.

  **PARTLY ADDRESSED**: the harness now says which of the two happened when a timed-out run produced
  no test at all - `the loader took its kernel off the SYSTEM VOLUME, not the medium this suite
  staged`, with the command that fixes it. The collision itself is not fixed: one artifact serving
  two incompatible shapes is a build-layout question, not a boot one, and it wants its own milestone.

## What this milestone refuses, and why

- **A LARGER CLUSTER ON THE ESP.** `mformat -c 8` (4 KiB clusters) was considered and is not done.
  - After M2 and M3 it optimises a cost that no longer exists: the chain hops are served from one
    cached sector and the data is read in coalesced runs, so the cluster size stops driving the
    number of device requests.
  - It changes the on-medium layout, which regenerates every staged fixture, every signed manifest
    and every reproducible-build digest - churn with no measured benefit behind it.
  - It is fragile at the sizes this tree actually builds. The FAT12/FAT16 boundary is 4085 clusters,
    and `fat-media.img` is 16 MiB: at 4 KiB clusters that is 4096, eleven clusters above the line
    where `mformat` would silently produce a FAT12 volume instead - a different code path in this
    driver and in the firmware's. The ESP is sized from its payload, so the number is not fixed.

- **AN IOMMU ON THE DEVICE-TREE PORTS.** M9 is x86_64 only. What this tree has proven with a gate is
  the x86_64 profile; adding a controller to aarch64 and riscv64 without one is a claim nothing
  checks.

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED for one line.

- [ ] **The boot medium is latched when a file is found, and M5 asks for the mount.**
  `with_boot_medium` stores `BOOT_MEDIUM` only when the visitor returns true, and the visitor returns
  true only when the file it wanted was read ([main.rs](../../src/boot/loader/src/main.rs)). A medium
  that mounted cleanly and does not carry THAT file is forgotten, so the next read walks and re-mounts
  every disk again - and on a machine with two FAT media it can settle on a different one for the next
  file, which is the split boot this loader refuses everywhere else. Latch on the successful mount,
  which means the visitor reports mounting separately from finding.

### Second independent audit (2026-08-26): the same latch, and where it is reachable

The finding above is confirmed independently, with two details worth keeping. The bootstrap fallback
repeats the pattern - a FAT volume without `etc/bootstrap.list` is treated as the wrong medium and
the scan moves to the next disk - so the fix has to cover both readers rather than the file one. And
the exposure is narrower than it looks: the ordinary UEFI path identifies the medium through the
LoadedImage device handle, so the loose scan is reached only on firmware that declines to mount its
own ESP, which is the case the fallback was written for in the first place.
