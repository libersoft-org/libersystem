# P02M0089 - Pre-phase-3 hardening (finish before the server platform)

Status: COMPLETE. A code-level audit of the whole repository (2026-07-11), taken before declaring
phase 2 done and starting the server platform. Everything listed was a real, verified gap rather
than phase-3 scope: a server runs unattended, for a long time, under memory and fault pressure, so
robustness and persistence came first and the daily-friction CLI items came after.

*Condensed 2026-08-08 to the defects, the decisions and the two bugs the new tests found.*

## Robustness

**Kernel OOM must degrade, not panic.** The intermediate page-table allocation in the map walk
panicked on all three architectures. Fixed with a fallible `try_map_page` / `try_map_page_in` per
arch - the shared walk returns `Result` and propagates `frame::allocate()?` - while the infallible
`map_page` stays as a thin `.expect()` wrapper for kernel bring-up (LAPIC/IOAPIC/heap/boot), where
OOM genuinely is unrecoverable. The four userspace map syscalls go through `map_pages_or_rollback`,
which unmaps every page mapped so far on the first failure, frees the reserved range and returns
`ERR_NO_MEMORY`.

**The userspace `rt` allocator's OOM path was already graceful** - the earlier note was stale. One
reachable panic was real: `size_align`'s `align_to(..).expect("alignment overflow")` on a degenerate
`Layout`. It returns `None` now and `alloc` maps that to a null return, which is contract-correct
rather than aborting the process.

**The page-table concurrency test paid for itself immediately.** P02M0088 had added `PT_LOCK` on all
three arches with no test.  `concurrent_maps_on_shared_tables_strand_nothing` pins two workers to
their own cores and races them, 128 barrier-synchronised rounds, into the *same* fresh 2 MiB group -
both trying to create the same leaf table under a shared mid-level, which is the exact geometry of
the historical riscv64 race. Each unmap must return exactly that worker's frame, and the pool must
reclaim at least one leaf-table frame per round.

It caught a **real latent aarch64 bug**: `free_address_space` descended `free_table_level(l1, 2)` on
a four-level tree (L0→L1→L2→L3), one level short, so **every L3 leaf table of every torn-down
address space leaked** - "reclaimed 3 frames, expected at least 128". On a server that is an
unbounded frame leak per process exit. Fixed to depth 3; x86 and riscv64 were verified correct,
their trees being one level shallower below the root.

## Persistence

**ConfigService was in-memory only.** The tree now persists to `vol://system/config.tree` as
structured versioned binary (`LSCFGTR1`, count, length-prefixed key/value records) - never parsed
text. `Config::load` overlays the persisted nodes on the seeded defaults, so a set value wins over
its default, a persisted key with no default is appended, and **a new default added in a later build
still appears** where no override exists. A missing file, wrong magic or truncated record degrades
to the defaults. Every successful SET writes the whole tree through before replying, so the
durability round trip completes inside the request; the tree is tiny and writes are rare.

## Where the test tags came from

This milestone introduced the tagging that everything since selects by. All 115 source test
descriptors register through `tagged_test!` against one canonical `define_test_tags!` declaration,
and no plain function implements the harness trait - so a bare `#[test_case] fn` fails to compile.
`TEST_TAGS` selects the union plus the smoke set; `slow` and `stress` are gated unless explicitly
requested; unknown and empty-result filters fail rather than quietly running nothing. The runner
prints requested and effective tags with selected/skipped/total counts.

*(P02M0118 later measured what this cannot do: tags say both what a test exercises and what it needs to
run, and the second kind is on a third of the suite, which is why tag selection alone cannot scope a
change.)*

## CLI and observability

- `lscpu --json` omitted the CPU name. Added `SYS_CPU_NAME` and `arch::cpu_brand` on all three
  arches: x86 reads the CPUID brand string with a vendor-id fallback; aarch64 decodes MIDR_EL1's
  implementer and part (`cortex-a72` → "ARM Cortex-A72"); riscv64 queries the SBI Base vendor id,
  because M-mode CSRs are unreadable from S-mode.
- `lsblk` gained an aligned header and a TYPE column reporting the filesystem the volume's service
  names; `lsirq` became an aligned table like `lsvol`.
- `du` is a new tool with its own sandboxed ELF and the `volumes` bundle, walking the volume `list`
  stream and printing cumulative bytes children-before-parent, the classic post-order.
- `lsdev` and `lssvc` printing JSON without `--json` was a stale audit note - both already took an
  `Option<JsonMode>`.
