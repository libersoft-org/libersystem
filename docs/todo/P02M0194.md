# P02M0194 - Bluetooth, complete: classic and LE, every desktop profile, audio and voice

Status: OPEN. It closes when every part below is done. NOTHING HERE IS STARTED: the owner asked for the plan
only (2026-09-25).

THE OWNER'S DECISION (2026-09-25), IN HIS WORDS: a new milestone that finishes the service COMPLETELY, for the
whole of Bluetooth. It follows his "yes" to Bluetooth voice: the SCO transport is planned in P02M0099, and he
was told that voice is useless without a host stack that can set a headset's call up - which P02M0180, scoped
to one LE mouse, does not have. So this milestone takes the service from "one encrypted LE boot mouse" to what
a desktop operating system's Bluetooth does.

WHAT EXISTS, and this milestone builds on it rather than beside it:
  - THE TRANSPORT (P02M0099): HCI over USB - commands, events and ACL with their bounds, stall and unplug
    recovery, epochs across a reset - and, planned there, SCO over the isochronous alternates. ISO is a
    reserved kind nothing carries yet.
  - THE SERVICE (P02M0180): a sandboxed process with no device authority; LE scanning, one LE central
    connection, LE Secure Connections pairing with Just Works, a durable bond store, ATT/GATT discovery for
    the HID-over-GATT boot mouse, the read / operator / profile scopes, bounded tables, and `btctl`.
  - THE FIXTURES: an in-guest HCI controller-and-peer provider on the production wire, and a FunctionFS
    controller in the harness.

WHAT "COMPLETE" MEANS HERE, stated so it can be checked: every profile a desktop user meets - input devices,
music, calls, serial links, file push, tethering and LE Audio - on both radios, with the pairing models the
specification defines and the security it requires. EXCLUDED as not a desktop's: Bluetooth Mesh, the
peripheral (server) role beyond what the profiles need, proprietary codecs (aptX, LDAC) and AAC, whose use
is licensed.

## P02M0194a - Classic (BR/EDR) foundations

- [ ] Inquiry with extended inquiry results (names, classes, service UUIDs), paging, and several ACL links at
  once, bounded like the LE tables.
- [ ] Secure Simple Pairing - Numeric Comparison, Passkey Entry and Just Works, and Out Of Band where a peer
  offers it - with the association model shown and confirmed on the protected screen P02M0188 built, never on
  an ordinary application surface; link keys in the bond store beside the LE keys, with the key type and its
  authentication recorded. Legacy PIN pairing only for a device that cannot do better, and reported as weaker.
- [ ] Encryption required on every link that carries user data; role switch; sniff mode with its parameters
  bounded, so an idle keyboard does not hold the radio awake.
- [ ] L2CAP for BR/EDR - basic mode, and enhanced retransmission and streaming modes where a profile needs
  them - and the SDP client every classic profile is found through.
- [ ] RFCOMM over L2CAP, with its credit-based flow control.

## P02M0194b - LE, beyond one mouse

- [ ] Several LE connections at once; LE privacy - peers' resolvable private addresses resolved with their
  identity keys, and this host's own address rotated.
- [ ] Every LE pairing model the specification defines, and LE legacy pairing only for a peer that has
  nothing better, reported as weaker.
- [ ] A general GATT client - discovery, read, write, notify and indicate - offered to applications through
  a typed contract and a grant scoped to one device and its services, so a third-party program can talk to a
  heart-rate strap or a sensor without the service knowing what it is.

## P02M0194c - Input

- [ ] Classic HID (keyboards, mice, gamepads over BR/EDR) and HID over GATT with arbitrary report maps, both
  through the shared report-descriptor parser, into InputService's key, pointer and gamepad streams - the
  last being P02M0192's vocabulary.
- [ ] Reconnection by the device after a restart of either side, with the bond the only thing that lets it in.

## P02M0194d - Music: A2DP and AVRCP

- [ ] A2DP source (this system plays to headphones and speakers) and sink (a phone plays to this system),
  with SBC, the codec every device has - its encoder and decoder written here as pure, host-tested leaves
  against published vectors.
- [ ] A Bluetooth audio device appears to AudioService as an output (and, as a sink, as an input), with its
  latency stated; AVRCP carries play, pause, next and absolute volume both ways.

## P02M0194e - Calls: HFP and HSP over SCO

- [ ] The Hands-Free Profile in the Audio Gateway role - this system is what a headset connects to - over
  RFCOMM: the AT command set's service level connection, codec negotiation, and CVSD (narrowband) and mSBC
  (wideband) voice over SCO/eSCO on the transport P02M0099 plans. The Headset Profile for devices that have
  nothing newer.
- [ ] The headset appears to AudioService as a voice device - a microphone and a speaker together - and a
  call's audio is routed to it while the link is up, with the underrun policy the owner chose for playback.
- [ ] The headset's battery level, where it reports one, in the device's status.

## P02M0194f - Serial, file push and tethering

- [ ] SPP over RFCOMM, published as a serial byte stream like every other serial port here.
- [ ] OBEX Object Push: RECEIVING only into a place the user chose and only after a confirmation on the
  protected screen - a file from a radio is untrusted input - and SENDING a file the user named.
- [ ] PAN (BNEP): this system as a PAN user tethered to a phone, published to NetworkService as an interface.

## P02M0194g - LE Audio

- [ ] The ISO transport the HCI contract has reserved: connected isochronous streams over the USB transport
  (P02M0099 carries the kind once this milestone defines its bounds).
- [ ] The LC3 codec, pure and host-tested against the published conformance vectors; the Basic Audio
  Profile's unicast client with its capabilities and stream control, and volume control - so LE Audio
  earbuds play, and their microphones record, through AudioService like any other device.
- [ ] Broadcast (Auracast) reception as the last item of the part.

## P02M0194h - Operator, verification and completion

- [ ] `btctl` grows with the stack: classic and LE devices in one list, pairing that shows its association
  model, connecting and disconnecting profiles, trust and forget.
- [ ] THE FIXTURE GROWS INTO A PEER SIMULATOR: the in-guest controller-and-peer provider plays a classic
  keyboard, a headset (HFP and A2DP sink with AVRCP), a phone (A2DP source, OPP, PAN), a serial device and an
  LE Audio earbud, each speaking the real protocols byte for byte, so every part has an oracle in the guest; the
  usbredir controller from P02M0099 carries SCO and ISO under them. Real hardware is recorded where it was
  used and never substituted for an oracle.
- [ ] Host suites for every pure leaf - SDP, RFCOMM, AT parsing, SBC, mSBC, LC3, the pairing state machines
  against the specification's sample data - and a guest gate per part, each registered like P02M0180's.
- [ ] The three cross-builds; the dynamic report; the service's Domain limits re-measured for the larger
  stack and restated.

EXCLUDES: Mesh; the peripheral role beyond what the profiles need; aptX, LDAC and AAC; the Bluetooth SIG's
qualification, which needs its proprietary tester - what this milestone claims is its own oracles.
