# M0106 - Ring-3 preemption: per-thread kernel entry stacks

Status: COMPLETE.

The kernel preempted ring-0 threads but ring 3 was still cooperative, because **`TSS.RSP0` - the
stack the CPU loads on a ring-3 interrupt - is per-core**. Context-switching away from an interrupted
user thread would have left two threads sharing one entry stack, so the timer ISR deliberately only
ticked when it fired in ring 3, and an infinite loop in a user program owned its core.

*Condensed 2026-08-08.*

**`TSS.RSP0` now travels with the thread.** The per-CPU block holds the address of its core's slot,
recovered once at bring-up by parsing the TSS descriptor out of the live GDTR - so no new bookkeeping
about where each core's area lives. Two writers keep the slot on the current thread's **parked** stack
position: the usermode entry stub mirrors the parked pointer in the same breath it parks it for the
syscall path, and the scheduler retargets the slot from the incoming thread's parked value on every
switch.

The distinction that matters: it is the parked position, **not the absolute stack top** - pointing at
the top would overwrite the parked ring-3 entry frame.

A thread that never entered ring 3 has a zero there and is left alone; it cannot take a ring-3
interrupt, and its first entry sets the slot itself.

With the frame guaranteed to land on the thread's own stack, the timer's ring-0-only gate is gone.
The interrupted privilege level rides along as a flag, which buys a second win: **a ring-3 thread
whose process was killed while it spun is retired at its next tick**, because user code holds no
kernel lock and there is nothing to unwind.
