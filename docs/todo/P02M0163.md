# P02M0163 - Every driver is selected by a vendor number the standards identity is sitting next to

Status: PLANNED AFTER P02M0162. DISCOVERY AND THE BINDING UNIT. FOURTH OF SEVEN - see P02M0098.

## Goal

Let the registry select drivers on what a device IS rather than on which vendor made it, and bind at
the unit that actually has one owner - a PCI function, a platform device, or one interface of a USB
composite.

## What is there now

- **THE REGISTRY IS BUILT AND WORKS.** `registry_candidates` returns every matching entry sorted most
  specific first, a tie is refused at registry-build time, and the choice is made from `DeviceInfo`
  alone. That was done under P02M0098 on 2026-08-12 and it is not repeated here.
- **AND EVERY RULE IN IT STILL MATCHES ON `device-type`.** All eight `[programs.driver]` rows in
  `src/user/services/manifest.toml` say `match = [{ device-type = N }]` - the vendor-defined virtio
  number. `pci-class`, `pci-subclass` and `pci-interface` reach the binder and nothing uses them, so
  the rule the original milestone wrote ("vendor/product IDs may never become the primary binding
  mechanism") is still broken by every driver in the image.
- **DISCOVERY HOLDS TWO KINDS OF DEVICE.** `DEVICES` records virtio functions and xHCI. Every other
  PCI function is in `PCI_FUNCTIONS` for `lspci` and nowhere else, so an unsupported device is absent
  from binding because the table is narrow rather than because a rule says so. There are no ACPI or
  FDT entries at all.
- **THE UNIT IS AN INDEX INTO THAT TABLE.** There is no notion of a child device, so a USB composite
  device has one owner and a controller cannot hand out one of its interfaces.

## Work

- [ ] **M1 - discovery records every PCI function.** One vocabulary, with the standards identity, the
  BAR and capability metadata a driver needs, for every function the scan resolved. A function no
  driver matches stays visible in the inventory and receives no MMIO and no bus-master capability -
  which becomes a rule rather than a consequence of the table's shape.

- [ ] **M2 - drivers match on what they are.** The virtio rows move to the standards identity where
  one exists, and `device-type` becomes what it should always have been: a narrower rule for a
  device that needs one, not the primary key. A rule that can only be written with a vendor number
  says so.

- [ ] **M3 - the binding unit is the thing with one owner.** A PCI function or a platform device
  normally has one claim. A controller publishes typed child devices, and DeviceManager applies the
  same registry to each arrival - so a USB composite device binds a class driver per interface and the
  interfaces cannot overlap. A child's authority is attenuated from the parent's claim, which
  P02M0098 made possible, and is revoked with it.

- [ ] **M4 - firmware-described devices join the vocabulary.** ACPI-enumerated devices and FDT
  `compatible` nodes are discovered and matchable, on the two ports that have a device tree and on
  x86_64 where ACPI describes one. This is what makes the registry mean anything on a machine that is
  not all PCI.

- [ ] **M5 - identity is canonical and paired with a generation.** A node's identity is its bus's
  canonical one - PCI domain:BDF, FDT node path, USB controller plus route - and always travels with
  the generation from P02M0098. Replugging at the same place is a new binding, not a continuation.

- [ ] **M6 - the tests are the ambiguous cases.** Two identical controllers, two same-class devices, a
  composite device whose interfaces must not collide, a function nothing matches, a device that
  disappears between discovery and claim.

## Definition of done

- Every PCI function is discoverable, and one nothing binds is visible and holds no device capability.
- No driver in the image is selected by a vendor number where a standards identity would do, and the
  ones that need one say why.
- A USB composite device binds a driver per interface with no claim overlap, and losing the parent
  revokes the children.
- ACPI and FDT devices are matched by the same registry as PCI ones.
- Two identical controllers produce two independent bindings, and a device replugged at the same
  address is a new generation.

## What this milestone refuses, and why

- **New hardware support.** This changes how a driver is chosen and what it is bound to. Every driver
  in the image at the end is one that was in it at the start; new device families are P02M0099's.
- **A device-tree or ACPI abstraction layer.** Both are already parsed in this tree. What is missing
  is that their results reach the binder, which is a plumbing change and not a new subsystem.
- **Hotplug policy.** Discovering an arrival and binding it is this milestone; deciding what to do
  when it keeps arriving and failing is supervision's.
