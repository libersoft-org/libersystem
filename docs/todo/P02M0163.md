# P02M0163 - Discovery holds two kinds of device and the binding unit is an index into that table

Status: PLANNED AFTER P02M0162. DISCOVERY AND THE BINDING UNIT. FOURTH OF SEVEN - see P02M0098.

## Goal

Put every PCI function in the inventory, let every rule name an identity its own standard defines,
and give a function an identity that carries a generation - so a device nothing supports is visible
and powerless rather than absent, and a replug is a new binding rather than the same row.

## What is there now

- **THE REGISTRY IS BUILT AND WORKS.** `registry_candidates` returns every matching entry sorted most
  specific first, a tie is refused at registry-build time, and the choice is made from `DeviceInfo`
  alone. That was done under P02M0098 on 2026-08-12 and it is not repeated here.
- **AND ONE RULE IN IT IS A SYNTHETIC NUMBER STANDING IN FOR A CLASS TRIPLE.** All eight
  `[programs.driver]` rows say `match = [{ device-type = N }]`, and seven of them are right: for a
  virtio device `device-type` IS the standards identity - the virtio specification's own device type,
  which `virtio_type()` derives as `device_id - 0x1040` and only for a function whose vendor is
  virtio's. This milestone's first draft called that "the vendor-defined virtio number", which is
  wrong, and prescribed moving those rows to PCI class - which for `virtio-net` (class `02/00`) would
  match ANY ethernet controller and hand a virtio driver hardware it cannot drive. That prescription
  is deleted rather than kept with a caveat.
  What IS wrong is the eighth row: `device-type = 256` is `DEVICE_TYPE_XHCI`, a LiberSystem constant
  invented for the table, while the standards identity discovery ALREADY matched on is the PCI class
  triple `0c/03/30` in `is_xhci()`. And no virtio row pins the transport, so the rule says "device
  type 1" where it means "a virtio-pci function whose virtio type is 1". `pci-class`, `pci-subclass`
  and `pci-interface` reach the binder and are checked there; no manifest row uses them.
- **DISCOVERY HOLDS TWO KINDS OF DEVICE.** `DEVICES` records virtio functions and xHCI. Every other
  PCI function is in `PCI_FUNCTIONS` for `lspci` and nowhere else, so an unsupported device is absent
  from binding because the table is narrow rather than because a rule says so. There are no ACPI or
  FDT entries at all.
- **THE UNIT IS AN INDEX INTO THAT TABLE.** A device is a row number, so there is nothing to hold a
  generation, and a function that is replugged is the same row.

## Work

- [ ] **M1 - discovery records every PCI function.** One vocabulary, with the standards identity, the
  BAR and capability metadata a driver needs, for every function the scan resolved. A function no
  driver matches stays visible in the inventory and receives no MMIO and no bus-master capability -
  which becomes a rule rather than a consequence of the table's shape.

- [ ] **M2 - every rule names the identity the standard defines, and says which standard.** A virtio
  row becomes transport plus virtio type - `virtio-pci` and the number - so the rule cannot match a
  function that is not a virtio device. The xHCI row becomes the class triple `0c/03/30` it was
  always standing in for, and `DEVICE_TYPE_XHCI` stops being an identity. Vendor and product numbers
  stay available and are for a quirk about a particular part, never for choosing a driver.

- [ ] **M3 - identity is canonical and paired with a generation.** A function's identity is PCI
  `domain:bus:dev.func` and it always travels with the generation from P02M0098. A device replugged
  at the same address is a new binding rather than a continuation of the old one.

- [ ] **M4 - the tests are the ambiguous cases this scope actually has.** Two identical controllers,
  two same-class functions, a function nothing matches, and a device that disappears between
  discovery and claim.

## Definition of done

- Every PCI function is discoverable, and one nothing binds is visible and holds no device capability.
- Every rule names an identity its standard defines: a virtio row pins the transport and the virtio
  type, the xHCI row is the class triple, and a rule written with a vendor number says which part it
  is a quirk for.
- Two identical controllers produce two independent bindings, and a device replugged at the same
  address is a new generation.

## What this milestone refuses, and why

- **New hardware support.** This changes how a driver is chosen and what it is bound to. Every driver
  in the image at the end is one that was in it at the start; new device families are P02M0099's.
- **Firmware-described devices, ACPI or FDT.** The first draft called this "a plumbing change,
  because both are already parsed" and that is not true of either. The FDT parser produces one
  purpose-built `BootInfo` - RAM banks, CPU ids, controller addresses - and not a device inventory
  with `compatible` strings a rule could match; and there is no AML namespace on x86_64 at all, so
  `_HID`, `_CID` and `_CRS` do not exist to be read. Both are real work with their own risks, and
  neither belongs in a milestone about which PCI function a driver is chosen for.
- **A binding unit below the PCI function, and USB interface drivers.** The first draft had a
  controller publishing typed children so a composite device could bind a class driver per interface.
  In this tree HID and mass storage are code INSIDE the xHCI driver, not processes - so that item was
  not discovery plumbing, it was splitting a driver into several and giving each its own authority.
  USB children stay what they are: an inventory the xHCI driver owns and publishes as providers,
  which is P02M0164's vocabulary. Process-level child binding is a milestone of its own when a driver
  actually needs to be split.
- **Hotplug policy.** Discovering an arrival and binding it is this milestone; deciding what to do
  when it keeps arriving and failing is supervision's.
