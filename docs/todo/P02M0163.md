# P02M0163 - Discovery holds two kinds of device and the binding unit is an index into that table

Status: COMPLETE (2026-08-27). DISCOVERY AND THE BINDING UNIT. FOURTH OF SEVEN - see P02M0098.

Proved by the boot: nine of nine devices online with the xHCI controller bound by the class triple
`0c/03/30` rather than by `DEVICE_TYPE_XHCI`, twelve `system-manifest` tests, three `driver-binding`
identity tests, and the relation checks watched to refuse.

WHAT THE MODEL WAS MISSING, found by the ambiguity checker rather than by reading: transport and
class are not independent, and a rule that names a class while saying nothing about the transport
can match a virtio function. Every virtio row therefore overlapped the xHCI row the moment the
vocabulary was split, and the checker said so with all six named. The answer is that "not a virtio
function" is a PREDICATE and not an absence - `transport = "plain-pci"` - because omitting the key
means "do not ask", and a rule that does not ask matches both. That is the one thing in this
milestone nobody had written down anywhere, and the check that found it exists because the rule set
is closed.

## Goal

Put every PCI function in the inventory, let every rule name an identity its own standard defines,
and give a function an identity that carries a generation - so a device nothing supports is visible
and powerless rather than absent, and a rebind is a new binding rather than a continuation of the
last one. This is the BOOT inventory: the scan runs once, and a replug is not something this tree can
observe.

## What is there now

- **THE REGISTRY IS BUILT AND WORKS.** `registry_candidates` returns every matching entry sorted most
  specific first, a tie is refused at registry-build time, and the choice is made from `DeviceInfo`
  alone. That was done under P02M0098 on 2026-08-12 and it is not repeated here.
- **AND ONE RULE IN IT IS A SYNTHETIC NUMBER STANDING IN FOR A CLASS TRIPLE.** All eight
  `[programs.driver]` rows say `match = [{ device-type = N }]`, and seven of them are right: for a
  virtio device `device-type` IS the standards identity - the virtio specification's own device type,
  which `virtio_type()` derives as `device_id - 0x1040` and only for a function whose vendor is
  virtio's. This milestone's first draft called that "the vendor-defined virtio number", which is
  wrong, and prescribed moving those rows to PCI class - which for `virtio-net` (class `02/00`) would
  match ANY ethernet controller and hand a virtio driver hardware it cannot drive. That prescription
  is deleted rather than kept with a caveat.
  What IS wrong is the eighth row: `device-type = 256` is `DEVICE_TYPE_XHCI`, a LiberSystem constant
  invented for the table, while the standards identity discovery ALREADY matched on is the PCI class
  triple `0c/03/30` in `is_xhci()`. And no virtio row pins the transport, so the rule says "device
  type 1" where it means "a virtio-pci function whose virtio type is 1". `pci-class`, `pci-subclass`
  and `pci-interface` reach the binder and are checked there; no manifest row uses them.
- **DISCOVERY HOLDS TWO KINDS OF DEVICE.** `DEVICES` records virtio functions and xHCI. Every other
  PCI function is in `PCI_FUNCTIONS` for `lspci` and nowhere else, so an unsupported device is absent
  from binding because the table is narrow rather than because a rule says so. There are no ACPI or
  FDT entries at all.
- **AND THE SCAN HAPPENS ONCE, AT BOOT.** `device::init` is called once after the heap is up and
  never again, so there is no arrival, no disappearance and no replug to observe. This milestone is
  therefore about the boot inventory; hotplug is a mechanism that does not exist yet and is not
  smuggled in through a test that would have to invent it.
- **AND THE ABI HAS NO PCI DOMAIN.** `PciInfo` carries bus, device and function. There are three PCI
  implementations here - `arch/x86_64/pci`, `arch/aarch64/pci.rs` and `arch/riscv64/pci.rs` over a
  shared `arch/common/pci` - and every one of them is single-segment, so BDF is the whole identity.
  Inventing a domain field would be modelling hardware this tree does not run on.
- **THE UNIT IS AN INDEX INTO THAT TABLE.** A device is a row number, so there is nothing to hold a
  generation, and a function rebound after its driver died is the same row as the one before it.

## Work

- [x] **M1 - discovery records every PCI function, in three layers - and the middle one cannot depend
  on the registry.** This item said the resolved resources are attached "only where a registry rule
  matched", and that ordering does not exist: `device::init` runs ONCE AT BOOT, in the kernel, and
  builds `DEVICES` from `scan_virtio()` long before DeviceManager - a userspace process - has read a
  registry at all. Making the profile conditional on a match would mean either moving the resolver
  into userspace or rescanning after the match, and neither is a discovery change. What the ordering
  does allow, and what the item is actually asking for, is three layers:

  | | |
  | --- | --- |
  | identity, for EVERY function | BDF, vendor, product, the class triple, and `transport`/`virtio_type` where the function is a virtio one - the fields a registry rule matches on, so a match needs nothing else |
  | resource profile, where the kernel can already build one | the resolved BARs, capability offsets and MSI-X table `DeviceEntry` holds today, for the virtio and xHCI functions its existing resolver understands. Not gated on a match, because it happens first |
  | the CAPABILITY, only after a match | `sys_device_acquire` mints it, and that is already gated on the DeviceManager privilege. This is where "a function no driver matched holds nothing" is true, and it is true today |

  `revision` is not in the identity: nothing consumes it and no match rule names it, so it would be a
  field added on the chance that something might. A function no driver matches is visible in the
  inventory and holds no capability - which becomes a rule rather than a consequence of the table's
  shape.

- [x] **M2 - every rule names the identity the standard defines, and says which standard.** The keys,
  exactly, so that two implementers do not invent two spellings:

  | key | means |
  | --- | --- |
  | `transport = "virtio-pci"` with `virtio-type = N` | a virtio-pci function whose virtio type is N |
  | `pci-class` / `pci-subclass` / `pci-interface` | the PCI class triple, subclass and interface optional |
  | `pci-address = { bus, dev, func }` | a location, not a kind - the development console only |
  | `pci-vendor` / `pci-product` | a NARROWING on a rule that already matched, never a rule on its own |

  AND THE KEYS HAVE RELATIONS, WHICH THE VALIDATOR CHECKS. A closed set is not the same as a coherent
  one: today's check is mostly that a rule is non-empty, so `{ pci-subclass = 3 }` with no class, or
  `{ pci-product = 0x1000 }` with no vendor, generates a rule that matches on a number whose meaning
  is defined by the field beside it. Five relations, refused at generation time with the entry named:
  `transport` and `virtio-type` appear together or not at all; `pci-subclass` requires `pci-class`
  and `pci-interface` requires both; `pci-product` requires `pci-vendor`; vendor, product and
  `pci-address` may only NARROW a rule that already names a standard identity, and there is NO
  exception for the development console. This item first wrote one, which would have undone a lesson
  the binder already carries in its own comment: *"the development console is selected by its virtio
  type AND its pinned address, which a set of single-question rules could only OR together - and
  OR-ing them would bind any device at that address to the console driver."* Its rule is
  `transport = "virtio-pci"`, `virtio-type = 3` and `pci-address` together, which is what the
  manifest row already says today. Each relation has a negative test, because a validator nobody has
  watched refuse is a validator that accepts.

  A virtio row becomes transport plus virtio type, so it cannot match a function that is not a virtio
  device. The xHCI row becomes the class triple `0c/03/30` it was always standing in for, and
  `DEVICE_TYPE_XHCI` stops being an identity. Vendor and product stay available for a quirk about a
  particular part, and a rule written with them says which part it is a quirk for.

- [x] **M3 - identity is canonical and paired with a generation.** `BindingId { bdf, generation }`: a
  function's identity is its BDF - the ABI has no domain and all three implementations are
  single-segment - and it always travels with the generation from P02M0098.

  THE ROW NUMBER IS NOT PART OF THE IDENTITY. P02M0098's `ClaimKey { device_index, generation }`
  addresses the same binding by the kernel's row number, and two identities for one thing with no
  stated way between them is how a revocation ends up unable to find what it is revoking. But the
  answer is a lookup, not a wider identity: the stable `DeviceNode` P02M0162 owns holds
  `device_index: Option<u32>` as its own field, absent for a function the kernel's resolver never
  gave a row. `BindingId` stays BDF plus generation, which is what makes it canonical - a name that
  grows a field for every table that wants to find it is not a name. A second generation is
  reached in this tree without any rescan at all: P02M0162 rebinds a node after a driver crashes, and
  P02M0098 gives that new claim a new generation. This item said the opposite, which would have made
  the generation look like dead weight until hotplug existed; it is load-bearing from the first
  crash-restart.

- [x] **M4 - the tests are the ambiguous cases this scope actually has.** Two identical controllers
  bind independently; two same-class functions do not collide; a function nothing matches is in the
  inventory and holds nothing. And the negative one that matters: an ordinary class-`02` Ethernet
  controller must NOT match the `virtio-net` rule - which is the bug the first draft of M2 would have
  introduced, so it is the test that keeps it out.

## Definition of done

- Every PCI function the boot scan resolved is discoverable, and one nothing binds is visible and
  holds no device capability.
- Every rule names an identity its standard defines: a virtio row pins the transport and the virtio
  type, the xHCI row is the class triple, and a rule written with a vendor number says which part it
  is a quirk for.
- Two identical controllers produce two independent bindings, and a non-virtio device of a class a
  virtio driver serves is not offered to it.
- A node rebound after its driver died keeps its BDF and gets a NEW generation, and a message stamped
  with the previous one is refused - which is the only place in this scope where a second generation
  exists, and therefore the only place the pairing can be shown to work at all.

## What this milestone refuses, and why

- **New hardware support.** This changes how a driver is chosen and what it is bound to. Every driver
  in the image at the end is one that was in it at the start; new device families are P02M0099's.
- **Firmware-described devices, ACPI or FDT.** The first draft called this "a plumbing change,
  because both are already parsed" and that is not true of either. The FDT parser produces one
  purpose-built `BootInfo` - RAM banks, CPU ids, controller addresses - and not a device inventory
  with `compatible` strings a rule could match; and there is no AML namespace on x86_64 at all, so
  `_HID`, `_CID` and `_CRS` do not exist to be read. Both are real work with their own risks, and
  neither belongs in a milestone about which PCI function a driver is chosen for.
- **A binding unit below the PCI function, and USB interface drivers.** The first draft had a
  controller publishing typed children so a composite device could bind a class driver per interface.
  In this tree HID and mass storage are code INSIDE the xHCI driver, not processes - so that item was
  not discovery plumbing, it was splitting a driver into several and giving each its own authority.
  USB children stay what they are: an inventory the xHCI driver owns and publishes as providers,
  which is P02M0164's vocabulary. Process-level child binding is a milestone of its own when a driver
  actually needs to be split.
- **Hotplug, replug and disappearance.** The PCI scan runs once at boot and there is no rescan, no
  arrival event and no removal event to observe - so a milestone that promised them would be
  specifying a mechanism it also had to build. This is the boot inventory. When something needs
  hotplug, the milestone that needs it builds the rescan and the events together.
- **One universal device record.** Widening today's `DeviceEntry` - which carries resolved BARs,
  capability offsets and MSI-X tables - to every function on the bus would mean resolving all of that
  for hardware nothing drives. Layers instead, as M1 states them - and NOT "the profile only for the
  ones a rule matched", which this refusal said and M1 had to correct: the kernel's resolver runs at
  boot, before any userspace registry has matched anything, so that ordering does not exist. The
  profile is built where the kernel's existing virtio/xHCI resolver can build one; what waits for the
  match is the CAPABILITY.
- **Hotplug policy.** This item said "discovering an arrival and binding it is this milestone", which
  contradicts the refusal above it: there is no arrival to discover. What to do about a device that
  keeps failing is supervision's, and it reaches that state through P02M0162's rebind rather than
  through arriving again.
