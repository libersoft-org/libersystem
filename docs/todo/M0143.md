# M0143 - LiberFS: what a mount may not do, and what a checksum does not prove

A fourth-party audit of LiberFS, verified claim by claim against the code on 2026-08-06 at
`0e2a353`. Twenty of its twenty-one findings were checked directly against the source and every one
of them held; the twenty-first is a list of gaps in `fsck` whose premises the other checks confirm.
Nothing in this round was hallucinated.

The audit is right that the architecture is sound - copy-on-write, two superblocks, barriers,
checksums, deferred reclaim - and that the faults live in the edges: mount failure, snapshot
recovery, and metadata that passes its checksum while being structurally impossible.

Ordered by what is at stake, which is not the order they were reported in.

## The one that can destroy a disk

- [x] **Any mount failure formats the volume.** `LiberFs::mount` returns `Option`, so an unreadable
  device, an unsupported version, a failed snapshot-table read and a genuinely blank disk are the
  same answer. `mount_or_format` treats every `None` as "no filesystem here" and lays down a fresh
  one.

  The tree already knows this hazard and has fought it twice: a corrupt snapshot table degrades to
  read-only rather than failing, and so does an incomplete generation walk - and the comment on the
  second says why, in as many words, that failing the mount "would present the volume as
  unformatted (and cost its data to the next format)". So the principle is established and the
  remaining paths simply do not follow it. `mount_at` still returns `None` when the device cannot
  read the last claimed block, and `load_snapshot_table` returning anything other than `Corrupt` -
  an I/O error - fails the mount outright.

  A transient virtio failure at boot is therefore enough to reformat a healthy system volume.

  Fixed. `MountError` has those five arms and `mount` returns them. The superblock parser was split
  so it can tell them apart at the source: no magic is `Unformatted`, our magic with a version,
  block size, feature set or algorithm this build cannot read is `Unsupported`, and anything past
  that which fails its checks is `Corrupt`. An I/O failure ANYWHERE outranks the rest - a device
  that did not answer has said nothing about what is on it, and nothing may be read as blank.

  `mount_or_format` now formats on `Unformatted` alone. Every other answer refuses the mount,
  changes nothing, and prints which it was and what to do - an unanswering disk, a volume from a
  newer build, a medium smaller than the volume it claims, damaged superblocks.

  The snapshot mounts keep their `Option`: nothing formats on the strength of those, and "there is
  no older generation" is an ordinary answer rather than a fault.

  Pinned by a test that mounts three devices and demands three different errors - a device that
  refuses every read, a blank one, and one whose superblock carries our magic and a version this
  build does not know. The test needed correcting once: it formatted a CLONE of the device and
  measured the untouched original, so the unsupported case reported `Unformatted` and would have
  passed for the wrong reason.

## Metadata that passes its checksum and is still impossible

- [x] **A raw extent whose `length` outruns its `store_len` gets blocks nobody marked.** The format
  says a raw run has `clen == 0` and `store_len == length`; the parser clamps the two fields
  separately and never compares them. The read path gates on `max(length, store_len)` - deliberately,
  so a forged extent cannot address past the pool - while every marking loop walks `0..store_len`.
  An extent with `length = 2, store_len = 1` therefore READS two blocks and marks one, and the
  second stays free for the allocator to hand to another file. Two owners, one block, silent
  overwrite.

  The existing test covers the variant that runs past the end of the pool, which the gate catches.
  It does not cover the dangerous one, where the whole forged span is inside it.

  Fixed. `check_extent` now checks the SHAPE before the addresses, because the addresses only mean
  something once the fields agree: `length > 0` and no longer than the pool; raw (`clen == 0`) means
  `store_len == length`; compressed means `store_len > 0` and `clen <= store_len * BLOCK_SIZE`. The
  address gate that was there is unchanged.

  The audit also asked for `store_len < length` on compressed runs, and that one is WRONG - it was
  written in and taken back out. It holds when a run is created and stops holding the moment the
  file is truncated: shrinking `length` leaves the stored stream whole, because decoding needs all
  of it to reach any of it. Demanding it made every truncated compressed file unreadable, which a
  later test caught. The test that covers this branch now asserts the case is LEGAL, so the mistake
  cannot be made twice.

  One validator, three callers, as asked. It already ran on the read path. It now also runs in
  `collect_inode_blocks`, which is what the free map is derived from - and `fsck` reaches it through
  `derive_free`, so that call site is covered by the same change. Refusing there arrives as walk
  damage and degrades the mount to READ-ONLY, which is the half that actually protects the disk: the
  disputed block is never handed out, because nothing is handed out at all. That matches what the
  tree already does with a node it cannot read, and for the same reason. `drop_inode_blocks`
  validates too, so a delete either returns every block of a run or refuses.

  Two tests, one per side of the format. The raw one forges `length = 2, store_len = 1` wholly
  INSIDE the pool - the variant the existing test does not reach - and demands the read be refused
  AND the mount be read-only. The compressed one drives the validator directly: a stream one byte
  past its stored blocks, a run storing as much as it serves, a run storing nothing, and an extent
  covering nothing.

  The raw test had to be moved once. Its first draft put the forged span at blocks 60-61 of a
  64-block pool, which is the metadata end: forging the inode overwrote the payload, the CRC no
  longer matched, and the mount refused for a reason unrelated to the extent's shape. It passed
  without the fix it was written to prove. It now picks blocks in the data half and asserts they are
  free first.

- [x] **Nothing detects two owners of one block.** Marking is idempotent by construction: setting a
  bit twice is setting a bit. So a validly checksummed image can have two files pointing at one
  data block, two extents sharing a checksum block, or two parents sharing a subtree, and the free
  map cannot tell. Delete one owner and the block joins `dead`; a commit later frees it while the
  other owner is still reading it.

  Fixed, and it turned out not to need a second map. Every mark in the free-map walks now goes
  through one helper that reports whether the bit was ALREADY set; the first repeat is remembered.
  A bitmap cannot express "twice", but the act of setting it can.

  The scoping is the whole design, and it is narrow on purpose. Strict marking is on for the walk of
  the LIVE generation alone - the one map in which every block has exactly one owner. The previous
  generation gets its own map, and all the snapshots deliberately SHARE one map, because sharing
  subtrees with each other is what makes them snapshots. The verdict is captured the moment the live
  walk ends, before anything cross-generational is marked, so a later change cannot widen it by
  accident.

  A duplicate reports `Corrupt` from `derive_free`, which the mount already degrades to read-only.
  That is the right severity: allocating from such a map is harmless, and the DELETE is what kills -
  it returns a block the other owner is still reading. Read-only forecloses both.

  Two tests, deliberately opposed. One forges an inode with two runs addressing one block and
  demands read-only. The other snapshots a volume twice and demands it still mounts WRITABLE - the
  guard against the opposite error, calling the design corruption. Unscoping strictness fails the
  second one, along with three existing snapshot tests, so the scoping is load-bearing and known to
  be.

  Worth recording: with strict marking on, all 105 tests that existed at the time passed unchanged.
  Nothing in the suite marks a live block twice, which is some evidence the invariant is real and
  not merely desirable.

- [x] **The free map is derived from metadata nobody verified.** `mark_inode_tree` and
  `mark_dir_tree` read through `dev.read_block` directly. The code says so - "Reads are raw (no
  checksum check)" - and the reasoning is sound as far as it goes: damage that IS detectable sets
  `walk_damage`, which degrades the mount to read-only, and aborting instead would present an
  intact-superblock volume as unformatted.

  What that leaves is the block that reads cleanly and is wrong. A node whose CRC the parent would
  have rejected is followed anyway, so it can move an extent pointer, hide a subtree, or omit a
  live block from the map - and the mount stays WRITABLE, because nothing failed. The next
  allocation then hands out blocks that were still recoverable.

  Fixed. Both mark walks now carry the expected CRC alongside every queued block - the root's from
  the superblock (or from the inode, for a directory tree), each child's from the link its parent
  holds - and a node whose contents do not match what vouched for it is walk damage, which reaches
  read-only before the first allocation.

  Scoped to the live generation, using the same flag as the two-owner check, because the reasoning
  inverts for the older ones: there the goal is to RESERVE whatever might still be referenced, and
  refusing to follow damage would under-reserve and free blocks a snapshot still holds. Tolerance is
  right for recovery and wrong for an allocator, so each gets what it needs.

  Pinned by a test that flips one byte of an mtime in the inode tree's root. The block still reads,
  still parses, still has its type and count - only the CRC the superblock recorded disagrees. That
  is exactly the case the old walk could not see: nothing failed, so the volume stayed writable.

## Snapshots and the generation behind the live one

- [x] **The previous generation's snapshot table is not protected.** The mount keeps
  `prev_inode_root` and `prev_inode_root_crc` and nothing else: `prev_snap_root` does not exist
  anywhere in the tree. `derive_free` therefore marks the live tree, the current snapshot chain and
  the previous INODE tree - but not the previous generation's snapshot table, nor the snapshots
  that existed only in it.

  Delete a snapshot, commit, and the older superblock still describes a generation in which that
  snapshot was live - while its table and blocks have already been declared free and may be
  overwritten before that superblock slot is. A crash before the next commit point leaves a
  superblock that `mount_snapshot` will offer as a complete image of a generation whose data is
  gone.

  Fixed. The mount and the commit now both carry `prev_snap_root` and its CRC beside the inode root
  they already kept, and `derive_free` walks that table into the previous generation's map: the
  chain's own blocks AND the inode trees of every snapshot it names.

  The lifetime works out exactly right without any new machinery. Those blocks land in `prev`, so
  they become `dead_prev` - the set the NEXT commit may free - and that commit is the one that
  overwrites the superblock slot describing them. Reserved until the slot naming them is gone, which
  is the invariant, reached through the mechanism that was already there.

  The chain loader had to be split to make this possible: it read only the live root into
  `self.snapshots` and there was no way to read any other. It now takes a root and returns a list,
  with a callback that hands out each chain block as it is visited - so the marking walk reserves
  the table's own blocks in the same pass. A previous table that cannot be read is walk damage
  rather than a hard failure: the reservation is incomplete, so the mount goes read-only.

  Pinned by a test that snapshots, commits once more so the live tree copies AWAY from the
  snapshot's root (otherwise the assertion would pass on a coincidence), deletes the snapshot, and
  then demands its root is still reserved - and that the older generation still mounts and still
  reads the file through the snapshot that the live generation no longer has.

- [x] **Snapshot records from disk are trusted more than the ones being written.** `create_snapshot`
  validates a name; `load_snapshot_table` checks none of it - not emptiness, not UTF-8, not
  duplicates, not that a root is in the pool or is a node of the right type, not the generation
  against the live one. A raw walk can skip an impossible root and leave the mount writable.

  Fixed. A record read off the medium now faces what one being written faces: a non-empty UTF-8
  name, unique within its table, a root that is neither the zero sentinel nor outside the pool, and
  a generation no higher than the live one - which is provable rather than a guess, since a snapshot
  carries the generation live when it was TAKEN while the superblock carries the one the commit
  produced. Any violation is `Corrupt`, which the mount degrades to read-only.

  The type check the audit also asked for went into the walk rather than the loader, since that is
  where the block is read anyway: a byte that is neither node type was being treated as an internal
  node, so the walk read separators and child links out of whatever the block happened to hold. That
  one applies to every generation, not just the live one.

  Pinned by three forgeries over one image - a nameless snapshot, a root past the pool, a generation
  from the future - each with every checksum above it repaired, so the mount refuses on the CONTENT
  and not on a checksum standing in for it. The unforged image is asserted to mount writable first,
  so the three cases cannot pass by accident.

## Arithmetic, streams and state that survives a failure

- [x] **A failed transaction keeps a compression change it did not commit.** `Txn` records the inode
  root, its CRC, the next inode, the snapshot table and the snapshot list - and not `compress`.
  `set_compression` mutates `self.compress` inside the transaction, so when the first barrier fails
  before the superblock is written, `abort` restores everything except that. The caller is told
  `Io`, the disk does not have the change, and the filesystem in memory reports it as made - and
  writes it into the superblock on the next unrelated commit.

  Fixed: `Txn` carries `compress`, and `abort` restores it with the rest. Pinned by a test over a
  device that fails exactly ONE barrier and then behaves - enough to roll the change back and still
  commit the write after it, which is what it takes to watch the surviving setting reach the disk on
  an unrelated commit. The test asserts both halves: the switch is unchanged in memory, and a
  remount finds it unchanged on the medium.

- [x] **I/O at the very top of the address space overflows.** `write_at` guards its own
  `offset.checked_add(len)` and then computes a block end without one; `read_range` adds
  `run_start + n * BLOCK_SIZE` the same way. A one-byte write at `u64::MAX - 1` passes the guard and
  overflows after it - a panic in debug, a wraparound in release. The existing test uses
  `u64::MAX - 2` with three bytes, so the first `checked_add` refuses it and this edge is never
  reached. Offsets inside a block should be computed with a modulus, not by adding to an absolute
  position.

  Fixed in both places, by computing DISTANCES from values already known to be in range rather than
  building an absolute position above the ceiling: the full-block test became `end - block_start >=
  BLOCK_SIZE`, and the two remaining sums saturate - which is exact here rather than merely safe,
  since `end` bounds the result either way.

  Pinned by a one-byte write at `u64::MAX - 1`, where the sum is exactly `u64::MAX` and the first
  guard therefore passes. It asserts the byte reads back, that the start of the file is a hole
  rather than somewhere the write wrapped to, and that one byte further out is still refused.

- [x] **An invalid compressed stream reads as short data plus zeros.** `lz_decompress` returns a
  `Vec`, never an error: whatever it managed to decode before the stream stopped making sense is
  the answer, and the read path pads the rest of the logical block with zeros. Every physical
  checksum can be valid, because this is not bit rot - it is a stream that is internally wrong. The
  decoder needs a `Result`, and must confirm it produced the whole logical range it was asked for.

  Fixed. `lz_decompress` returns an `Option`, every place it used to give up and hand back what it
  had now refuses, and it confirms two things a partial decode cannot satisfy: the stream's own
  length header equals the logical size the caller asked for, and the output is that long. The read
  path maps a refusal to `Corrupt`.

  One thing found while doing it, not in the audit: the caller's ceiling was `ext.length *
  BLOCK_SIZE`, and `length` for a COMPRESSED run was bounded only by `store_len < length` - so a
  forged extent could name a 16 TiB decompression buffer. `check_extent` now caps `length` at the
  pool size, which is sound because a run's blocks were once raw data in that pool.

  Pinned end to end: a compressed file whose stream is replaced by a well-formed one that simply
  ENDS - a header stating the true logical size, one literal run of three bytes, and a `clen` saying
  that is all there is - with every physical checksum in the image repaired to match. Nothing about
  it is bit rot, so nothing but the decoder can object.

  The test needed a second pass. Its first version left `clen` alone, so the decoder read on into
  the zeroed tail, met a zero match offset, and refused THERE - it passed without the completeness
  check it was written to prove. The stream has to end cleanly for the check to be the thing that
  catches it.

- [x] **A truncated compressed extent poisons the cache for the snapshot that still holds it.** The
  decompression cache is keyed on `ext.physical` alone, and `with_root` - which is how snapshots and
  `restore` are read - clears `icache` and `dcache` and leaves `decomp` alone. Truncating the live
  file leaves the physical blocks and the compressed stream untouched while shrinking `length`, so
  reading the live version caches a SHORT decode under a key the snapshot's longer extent shares.
  The snapshot then reads its first block correctly and gets zeros for the rest - and `restore_file`
  can write that back into the live tree as fact.

  Fixed on both counts, as the audit asked: the cache key is now `(physical, length, clen)`, and
  `with_root` clears the decompression cache with the other two.

  Worth being exact about what the test proves. Either fix alone is sufficient for this scenario -
  removing one leaves it passing, removing both fails it - because snapshot reads go through
  `with_root`, so the clear alone would cover them. The key is what makes the cache correct
  independently of who remembers to clear it, and inside a single generation two extents can no
  longer share an address anyway, since that is now the two-owner check's business.

  The test truncates a compressed file, confirms the stored blocks did not move and only the logical
  span shrank, reads the LIVE file first so the short decode is what lands in the cache, then reads
  the snapshot and demands the whole run - and finally restores from the snapshot and demands the
  live file be whole again, which is the path that could write the zeros back as fact.

  This test is also what caught the over-strict `store_len < length` rule recorded above.

## Structure that only a stricter checker would catch

- [x] **A CRC-consistent self-fanning tree makes `fsck` exponential.** The raw marking walk carries a
  visited bitmap and handles cycles; `check_inode_tree` and `check_dir_tree` carry only a depth
  limit. A hostile node with hundreds of children pointing at one node, with CRCs that agree, is
  walked once per pointer per level - `fanout ^ depth`. The depth limit protects the stack and not
  the clock. The existing self-fanning test exercises the raw walk, which is the one that already
  copes.

  Fixed: one visited bitmap, allocated per `fsck` and shared by both walks and every generation.
  Verifying a block twice reports nothing the first pass did not, so the second visit is simply not
  made. A block outside the pool is refused before the map is touched.

  Sharing it across the snapshot loop is a real saving rather than a compromise: snapshots share
  most of their subtrees with each other, so most of the repeat work on a HEALTHY volume is the same
  work.

  Pinned by a shape that needs no cycle and no checksum failure - nine levels, each one node whose
  twelve children all point at the single node of the next, built bottom-up so every CRC agrees -
  under a device that panics past a read budget, because a walk that is merely slow is
  indistinguishable from one that is stuck. Twelve to the eighth is about four hundred million
  reads; the budget is twenty thousand.

  The test was wrong once and passed for it: it forged the LIVE inode root, and `fsck` reaches
  `check_inode_tree` only for pinned generations - it walks the live volume by its namespace. The
  fan now hangs off a snapshot.

- [x] **A directory hash-collision group can be split across two leaves.** Leaves are ordered by
  `(hash, name)` while internal nodes route on the hash alone, so one hash must never span two
  leaves. `dir_split_point` looks for a boundary and, when every record in an overfull leaf shares
  one hash, falls back to index 1 - splitting the group it was supposed to keep together. Routing
  then reaches one leaf and the entries in the other become unfindable. Routing on the full
  `(hash, name)` key is the clean answer; anything else needs a collision leaf or an overflow chain.

  Fixed conservatively, and deliberately not by the clean answer: full-key routing means widening
  the separators in every internal node, which is an on-disk format change, and a collision chain is
  a new structure. `dir_split_point` returns an `Option` instead, `None` when every record shares
  one hash, and the insert that cannot be represented is refused as `NoSpace`.

  Nothing is lost and nothing becomes invisible, which is the whole difference: before, the entries
  went in and could not be found again while still occupying the tree. Reaching this at all takes
  enough names colliding in a 64-bit hash to overflow an entire leaf, which is a construction rather
  than an accident - so the refusal is the right cost until the format grows one of the two real
  answers. Both belong to a format revision, not here.

  The existing collision test now also asserts that a leaf of one hash group has no split at all.

- [x] **Deleting a damaged "empty" directory strands its children.** Emptiness is `inode.size == 0`.
  A damaged image can have a directory whose size says zero and whose `dir_root` still holds
  entries; the delete then frees the directory's B+tree and leaves the child inodes in the global
  inode tree - live to the free-map walk, unreachable from the namespace, invisible to a
  namespace-based `fsck`. The existing test proves the tree node is freed and asks nothing about the
  children. The delete should read the directory's real contents and refuse the mismatch.

  Fixed: emptiness now asks the TREE, on both paths that free a directory - the delete and the
  rename that replaces one. `size` is a cached count; the tree is the fact. A tree that cannot be
  read is not evidence of emptiness either, so the error propagates rather than being taken for "no
  entries".

  This REVERSED an existing test, which is worth being explicit about. It built exactly this damaged
  shape and asserted the replace succeeded and reclaimed the tree - the right answer to the leak it
  was written about, and the wrong answer overall, since freeing the tree is what strands the
  children. The test now demands the refusal, and the repair route with it: listing a directory
  walks its tree rather than trusting `size`, so the operator still sees the children, removes them,
  and then the same call succeeds - at which point the tree is reclaimed and not leaked, which is
  the original assertion, kept.

  The "repair verb" reasoning in `remove_inner` is untouched by this: it is about a DANGLING entry,
  whose inode does not exist, and that path still clears the name.

- [x] **`fsck` is a checksum scrubber, not a structural verifier.** It does not re-read the snapshot
  table from disk, does not walk the whole inode tree by a verified path, accepts a truncated
  directory leaf as however many records parsed cleanly, accepts a spill chain that ends before its
  declared extent count, and checks neither key ordering, separator ranges, record counts, extent
  overlap, duplicate physical blocks, the root inode's type, nor that every inode record is
  reachable. Worth splitting in two: `scrub_data` for checksums, and a structural pass that refuses
  to return what it managed to read.

  Split as suggested, though the report carries both rather than the calls being separate: the scrub
  fills `checksum_failures`, and a new structural pass fills `structural_failures` and a `faults`
  list of operator-facing sentences. They are kept apart because they mean different things - one
  says the medium is failing, the other says the metadata is wrong, and an operator needs to know
  which.

  Four of the listed gaps were already closed by earlier items in this milestone and are noted here
  only so the list is not read as still open: the root inode's type and duplicate physical blocks
  are settled at mount, the previous generation's snapshot table is now reserved and read, and every
  extent is validated individually wherever it is used.

  The structural pass adds: the live snapshot table re-read FROM DISK and compared against the
  mounted one; inode-leaf keys strictly ascending; internal separators ascending; record and child
  counts within what a block can hold; no block appearing twice in the inode tree; per file, an
  extent map as long as its declared count, ordered and non-overlapping, every run individually
  possible; and reachability - every inode record findable from the root by name, so an orphan that
  is live to the free-map walk and invisible to a namespace check gets counted and named.

  It records and CONTINUES rather than stopping at the first fault, so one broken inode cannot hide
  the rest, and an empty list is the only clean answer.

  Two tests. One asserts a healthy volume is silent - the half that matters most, since a
  false-positive structural checker is worse than none - and then drops a directory entry without
  freeing its inode and demands the orphan be counted and named. The other forges a file whose two
  runs cover the same logical block, each individually possible and impossible together, and demands
  the overlap be named.

- [x] **The superblock is checked for form, not for sense.** Magic, version, flags, algorithms, CRC
  and the pool size are validated; the relations between fields are not. `next_inode` may name an
  inode that already exists, and `alloc_inode` trusts it - so a new file can take over an existing
  inode and every name pointing at it. `root_inode` is never checked to be a directory. `generation`
  is incremented with `self.generation + 1` and nothing refuses `u64::MAX`.

  Fixed in three places, chosen by what each check costs.

  Settled in the parser, with no I/O: the inode root is non-zero and inside the pool (every formatted
  volume has a root leaf), the snapshot root is inside the pool or absent, `next_inode` is above
  `root_inode`, and the generation is not already `u64::MAX`. A slot failing any of these is not one
  this build accepts - which means the OTHER slot is tried, and a volume whose every slot is
  impossible is `Corrupt` and never blank.

  Settled at mount, which costs two reads: `next_inode` must name nothing that exists, and
  `root_inode` must be a directory. Both degrade to read-only rather than failing, because the data
  is intact and read-only is precisely what forecloses the harm - no allocation means no inode
  takeover.

  Settled at commit: a generation at `u64::MAX` refuses rather than wrapping into a superblock that
  looks older than the one it supersedes.

  One existing test changed its expectation and it is worth saying why. A superblock naming an inode
  root outside its own pool used to mount and then refuse the read; now the slot is rejected and the
  mount falls back to the other one, which is what keeping two is for. The foreign bytes are
  unreachable because nothing points at them at all, rather than because a later gate declined to
  follow.

- [x] **A named snapshot mount answered from the live generation's caches.** Not in the audit -
  found because the mount checks above are the first thing that ever reads an inode during a mount.

  `mount_named_snapshot` swaps `inode_root` to the snapshot's and switches the generation with it,
  and left `icache`, `dcache` and `decomp` holding entries decoded from the live tree - unlike
  `with_root`, which clears them for exactly this reason. It was latent, not harmless: nothing
  happened to populate those caches between the mount and the swap. The instant the mount read one
  inode of its own, the cached root DIRECTORY was the live one and the snapshot resolved every path
  through it - so a snapshot taken before a delete reported the file missing.

  Fixed by clearing all three at the swap, and pinned by a test that warms the caches on the live
  generation first and then demands the snapshot answer from its own tree and its own directory.

## Interfaces that lose the reason

- [x] **`lookup` collapses six answers into `None`.** `self.resolve(path).ok()` makes `NotFound`,
  `Corrupt`, `Io`, `NotDir`, `BadName` and `TooLong` indistinguishable - the same ambiguity as the
  mount, one layer up. The primary API should be `Result<Option<u32>, FsError>`.

  Fixed to exactly that: `Ok(None)` means the path names nothing, and every other answer says which
  it was. Nothing outside the tests used it, so the change cost only their call sites.

- [x] **A listing hides an I/O error as a missing file.** `read_dir_inode` skips an entry whose
  inode read returns `Invalid | Corrupt | Io`. A disk that hiccups therefore reports a directory
  that no longer contains the file - and a backup or sync tool downstream reads that as a deletion
  to propagate. `Io` has to propagate.

  Fixed. `Invalid` and `Corrupt` still skip, and that stays deliberate - a listing must not be
  stopped by one bad record on a volume someone is rescuing, and `fsck` is what names those. `Io` is
  a different claim entirely: the disk did not answer, so nothing is known about the entry.

  Pinned by a test that warms the caches for everything above the entry, then fails reads of exactly
  the block holding the child's inode, and demands `Io` rather than a listing one entry short.

- [x] **A whole-file overwrite drops `owner_tag`.** The replacement path builds
  `Inode::empty(TYPE_FILE)` and carries `ctime` across but not the owner, while partial writes and
  truncate keep the existing inode and so keep it. The documentation says the tag is preserved by
  every operation. Nothing depends on it yet, which is exactly why it will be wrong quietly.

  Fixed: the owner travels with `ctime`, and for the same reason - overwriting a file's contents
  does not make it a different file. The test asserts all three paths agree, so the odd one out
  cannot drift back.

## Long-lived limits

- [x] **Inode numbers are `u32`, monotonic, and never reused.** `alloc_inode` refuses at `u32::MAX`
  however empty the disk is. Not urgent; a fixed lifetime bound on a system that churns temporary
  files, and it belongs either in a 64-bit field or in the format's documented limits.

  Taken as the second option, which is the honest one: this is a documented limit of the format
  version rather than a defect. Reuse needs a free-inode map or a generation number beside each
  record, and widening the field is a format revision - both belong to that revision and not here.
  `alloc_inode` now says so, and says what the refusal at the ceiling is for.

- [x] **The free bitmap is sized through an unchecked `u64 -> usize` cast** - `(num_blocks as
  usize).div_ceil(8)`, twice - which truncates on a 32-bit target and asks for an enormous
  infallible allocation on a 64-bit one. `usize::try_from` and a fallible allocation, with a
  documented maximum volume size.

  Fixed: one `free_map_len` against a documented `MAX_BLOCKS` of 2^40 - 4 PiB at a 4 KiB block,
  whose bitmap is already 128 GiB, so memory is the limit that bites long before the field width.
  All four sizing sites go through it, and the mount reports an oversized claim as `Unsupported`.

  The test demonstrates the harm rather bluntly: without the bound, it does not fail, it ABORTS the
  process - "memory allocation of 137438953473 bytes failed".

- [x] **The label is not the UTF-8 it claims to be.** Truncation avoids splitting a UTF-8 sequence,
  but nothing validates the input as UTF-8 or refuses an embedded NUL - and `label()` reads only up
  to the first NUL, so what is written and what is read back can differ. Same treatment as snapshot
  names: validate, refuse NUL, then truncate.

  Fixed in that order. The clamp that avoided splitting a character was operating on a value that
  might not have been text at all. Pinned by a test that refuses a NUL and a non-UTF-8 byte pair,
  and round-trips an accented label through a remount.

## What this audit does not say

Nothing here was reproduced at runtime; the audit was static and so was this verification. Every
finding above was confirmed by reading the code it names, and several are contradicted by no test
because no test goes there - which is the point. The recommended first move is the audit's own: turn
the top findings into small regression tests over the existing `MemDevice`, where nearly all of them
can be built by hand.

## Closing

All twenty-one are done, and that first move is what was taken: every fix is pinned by a test built
by hand over `MemDevice`, and every one of those tests was WATCHED TO FAIL with its fix reverted
before being kept. The host suite went from 103 tests to 123.

Four of them did not fail on the first try, and each was a lesson rather than a nuisance:

- the mount test formatted a CLONE and measured the untouched original
- the raw-extent test put its forgery on the inode table, so the CRC objected instead of the shape
- the truncated-stream test let the decoder read into the zeroed tail, where a different guard
  caught it
- the exponential-fsck test forged the LIVE inode root, and `fsck` only reaches that walk for pinned
  generations

A test that passes before its fix exists is worse than no test, and only reverting finds them.

Two things surfaced that the audit did not name. `mount_named_snapshot` left the live generation's
inode and directory caches in place when it switched roots, so a snapshot taken before a delete
reported the file missing - latent only because nothing had ever read an inode during a mount
before. And the compressed-extent rule the audit proposed, `store_len < length`, is false after a
truncation; asserting it made every truncated compressed file unreadable.

One item was fixed conservatively rather than fully: a directory hash-collision group that fills a
whole leaf is now REFUSED instead of being split into unfindable halves. Full-key routing in the
separators, or a collision chain, is the real answer and belongs to a format revision.

Verified across x86_64, aarch64 and riscv64, plus `./check.sh --gate all`.
