# M0143 - LiberFS: what a mount may not do, and what a checksum does not prove

A fourth-party audit of LiberFS, verified claim by claim against the code on 2026-08-06 at
`0e2a353`. Twenty of its twenty-one findings were checked directly against the source and every one
of them held; the twenty-first is a list of gaps in `fsck` whose premises the other checks confirm.
Nothing in this round was hallucinated.

The audit is right that the architecture is sound - copy-on-write, two superblocks, barriers,
checksums, deferred reclaim - and that the faults live in the edges: mount failure, snapshot
recovery, and metadata that passes its checksum while being structurally impossible.

Ordered by what is at stake, which is not the order they were reported in.

## The one that can destroy a disk

- [ ] **Any mount failure formats the volume.** `LiberFs::mount` returns `Option`, so an unreadable
  device, an unsupported version, a failed snapshot-table read and a genuinely blank disk are the
  same answer. `mount_or_format` treats every `None` as "no filesystem here" and lays down a fresh
  one.

  The tree already knows this hazard and has fought it twice: a corrupt snapshot table degrades to
  read-only rather than failing, and so does an incomplete generation walk - and the comment on the
  second says why, in as many words, that failing the mount "would present the volume as
  unformatted (and cost its data to the next format)". So the principle is established and the
  remaining paths simply do not follow it. `mount_at` still returns `None` when the device cannot
  read the last claimed block, and `load_snapshot_table` returning anything other than `Corrupt` -
  an I/O error - fails the mount outright.

  A transient virtio failure at boot is therefore enough to reformat a healthy system volume.

  The fix is a typed `MountError` - `Unformatted`, `Unsupported`, `Corrupt`, `Io`, `DeviceTooSmall`
  - and formatting only on `Unformatted`. Everything else refuses, says which it was, and leaves
  every byte where it is.

## Metadata that passes its checksum and is still impossible

- [ ] **A raw extent whose `length` outruns its `store_len` gets blocks nobody marked.** The format
  says a raw run has `clen == 0` and `store_len == length`; the parser clamps the two fields
  separately and never compares them. The read path gates on `max(length, store_len)` - deliberately,
  so a forged extent cannot address past the pool - while every marking loop walks `0..store_len`.
  An extent with `length = 2, store_len = 1` therefore READS two blocks and marks one, and the
  second stays free for the allocator to hand to another file. Two owners, one block, silent
  overwrite.

  The existing test covers the variant that runs past the end of the pool, which the gate catches.
  It does not cover the dangerous one, where the whole forged span is inside it.

  Wanted: one validator for every extent, called at mount, in `fsck`, and before use - raw means
  `store_len == length`, `clen == 0`, `length > 0`; compressed means `store_len < length` and
  `clen <= store_len * BLOCK_SIZE`; plus in-pool, ordered, non-overlapping.

- [ ] **Nothing detects two owners of one block.** Marking is idempotent by construction: setting a
  bit twice is setting a bit. So a validly checksummed image can have two files pointing at one
  data block, two extents sharing a checksum block, or two parents sharing a subtree, and the free
  map cannot tell. Delete one owner and the block joins `dead`; a commit later frees it while the
  other owner is still reading it.

  A full derivation should build an ownership map beside the bitmap - block to first owner - and
  call a second, different owner in the same generation `Corrupt`. Sharing ACROSS copy-on-write
  generations is the whole design and stays legal; sharing between two live objects is not, until
  the format grows reflinks and refcounts.

- [ ] **The free map is derived from metadata nobody verified.** `mark_inode_tree` and
  `mark_dir_tree` read through `dev.read_block` directly. The code says so - "Reads are raw (no
  checksum check)" - and the reasoning is sound as far as it goes: damage that IS detectable sets
  `walk_damage`, which degrades the mount to read-only, and aborting instead would present an
  intact-superblock volume as unformatted.

  What that leaves is the block that reads cleanly and is wrong. A node whose CRC the parent would
  have rejected is followed anyway, so it can move an extent pointer, hide a subtree, or omit a
  live block from the map - and the mount stays WRITABLE, because nothing failed. The next
  allocation then hands out blocks that were still recoverable.

  The live generation's walk should verify each child against the CRC in its parent link, and any
  mismatch should reach read-only before the first allocation. A checksum-blind walk is a recovery
  tool, not a source of truth for a writable allocator.

## Snapshots and the generation behind the live one

- [ ] **The previous generation's snapshot table is not protected.** The mount keeps
  `prev_inode_root` and `prev_inode_root_crc` and nothing else: `prev_snap_root` does not exist
  anywhere in the tree. `derive_free` therefore marks the live tree, the current snapshot chain and
  the previous INODE tree - but not the previous generation's snapshot table, nor the snapshots
  that existed only in it.

  Delete a snapshot, commit, and the older superblock still describes a generation in which that
  snapshot was live - while its table and blocks have already been declared free and may be
  overwritten before that superblock slot is. A crash before the next commit point leaves a
  superblock that `mount_snapshot` will offer as a complete image of a generation whose data is
  gone.

  The whole previous superblock state has to be retained, and its snapshot roots marked, until the
  slot describing it has itself been overwritten.

- [ ] **Snapshot records from disk are trusted more than the ones being written.** `create_snapshot`
  validates a name; `load_snapshot_table` checks none of it - not emptiness, not UTF-8, not
  duplicates, not that a root is in the pool or is a node of the right type, not the generation
  against the live one. A raw walk can skip an impossible root and leave the mount writable.

## Arithmetic, streams and state that survives a failure

- [ ] **A failed transaction keeps a compression change it did not commit.** `Txn` records the inode
  root, its CRC, the next inode, the snapshot table and the snapshot list - and not `compress`.
  `set_compression` mutates `self.compress` inside the transaction, so when the first barrier fails
  before the superblock is written, `abort` restores everything except that. The caller is told
  `Io`, the disk does not have the change, and the filesystem in memory reports it as made - and
  writes it into the superblock on the next unrelated commit.

- [ ] **I/O at the very top of the address space overflows.** `write_at` guards its own
  `offset.checked_add(len)` and then computes a block end without one; `read_range` adds
  `run_start + n * BLOCK_SIZE` the same way. A one-byte write at `u64::MAX - 1` passes the guard and
  overflows after it - a panic in debug, a wraparound in release. The existing test uses
  `u64::MAX - 2` with three bytes, so the first `checked_add` refuses it and this edge is never
  reached. Offsets inside a block should be computed with a modulus, not by adding to an absolute
  position.

- [ ] **An invalid compressed stream reads as short data plus zeros.** `lz_decompress` returns a
  `Vec`, never an error: whatever it managed to decode before the stream stopped making sense is
  the answer, and the read path pads the rest of the logical block with zeros. Every physical
  checksum can be valid, because this is not bit rot - it is a stream that is internally wrong. The
  decoder needs a `Result`, and must confirm it produced the whole logical range it was asked for.

- [ ] **A truncated compressed extent poisons the cache for the snapshot that still holds it.** The
  decompression cache is keyed on `ext.physical` alone, and `with_root` - which is how snapshots and
  `restore` are read - clears `icache` and `dcache` and leaves `decomp` alone. Truncating the live
  file leaves the physical blocks and the compressed stream untouched while shrinking `length`, so
  reading the live version caches a SHORT decode under a key the snapshot's longer extent shares.
  The snapshot then reads its first block correctly and gets zeros for the rest - and `restore_file`
  can write that back into the live tree as fact.

  The key has to carry the extent's identity, not just its address; `with_root` has to clear every
  cache whose contents depend on the generation.

## Structure that only a stricter checker would catch

- [ ] **A CRC-consistent self-fanning tree makes `fsck` exponential.** The raw marking walk carries a
  visited bitmap and handles cycles; `check_inode_tree` and `check_dir_tree` carry only a depth
  limit. A hostile node with hundreds of children pointing at one node, with CRCs that agree, is
  walked once per pointer per level - `fanout ^ depth`. The depth limit protects the stack and not
  the clock. The existing self-fanning test exercises the raw walk, which is the one that already
  copes.

- [ ] **A directory hash-collision group can be split across two leaves.** Leaves are ordered by
  `(hash, name)` while internal nodes route on the hash alone, so one hash must never span two
  leaves. `dir_split_point` looks for a boundary and, when every record in an overfull leaf shares
  one hash, falls back to index 1 - splitting the group it was supposed to keep together. Routing
  then reaches one leaf and the entries in the other become unfindable. Routing on the full
  `(hash, name)` key is the clean answer; anything else needs a collision leaf or an overflow chain.

- [ ] **Deleting a damaged "empty" directory strands its children.** Emptiness is `inode.size == 0`.
  A damaged image can have a directory whose size says zero and whose `dir_root` still holds
  entries; the delete then frees the directory's B+tree and leaves the child inodes in the global
  inode tree - live to the free-map walk, unreachable from the namespace, invisible to a
  namespace-based `fsck`. The existing test proves the tree node is freed and asks nothing about the
  children. The delete should read the directory's real contents and refuse the mismatch.

- [ ] **`fsck` is a checksum scrubber, not a structural verifier.** It does not re-read the snapshot
  table from disk, does not walk the whole inode tree by a verified path, accepts a truncated
  directory leaf as however many records parsed cleanly, accepts a spill chain that ends before its
  declared extent count, and checks neither key ordering, separator ranges, record counts, extent
  overlap, duplicate physical blocks, the root inode's type, nor that every inode record is
  reachable. Worth splitting in two: `scrub_data` for checksums, and a structural pass that refuses
  to return what it managed to read.

- [ ] **The superblock is checked for form, not for sense.** Magic, version, flags, algorithms, CRC
  and the pool size are validated; the relations between fields are not. `next_inode` may name an
  inode that already exists, and `alloc_inode` trusts it - so a new file can take over an existing
  inode and every name pointing at it. `root_inode` is never checked to be a directory. `generation`
  is incremented with `self.generation + 1` and nothing refuses `u64::MAX`.

## Interfaces that lose the reason

- [ ] **`lookup` collapses six answers into `None`.** `self.resolve(path).ok()` makes `NotFound`,
  `Corrupt`, `Io`, `NotDir`, `BadName` and `TooLong` indistinguishable - the same ambiguity as the
  mount, one layer up. The primary API should be `Result<Option<u32>, FsError>`.

- [ ] **A listing hides an I/O error as a missing file.** `read_dir_inode` skips an entry whose
  inode read returns `Invalid | Corrupt | Io`. A disk that hiccups therefore reports a directory
  that no longer contains the file - and a backup or sync tool downstream reads that as a deletion
  to propagate. `Io` has to propagate.

- [ ] **A whole-file overwrite drops `owner_tag`.** The replacement path builds
  `Inode::empty(TYPE_FILE)` and carries `ctime` across but not the owner, while partial writes and
  truncate keep the existing inode and so keep it. The documentation says the tag is preserved by
  every operation. Nothing depends on it yet, which is exactly why it will be wrong quietly.

## Long-lived limits

- [ ] **Inode numbers are `u32`, monotonic, and never reused.** `alloc_inode` refuses at `u32::MAX`
  however empty the disk is. Not urgent; a fixed lifetime bound on a system that churns temporary
  files, and it belongs either in a 64-bit field or in the format's documented limits.

- [ ] **The free bitmap is sized through an unchecked `u64 -> usize` cast** - `(num_blocks as
  usize).div_ceil(8)`, twice - which truncates on a 32-bit target and asks for an enormous
  infallible allocation on a 64-bit one. `usize::try_from` and a fallible allocation, with a
  documented maximum volume size.

- [ ] **The label is not the UTF-8 it claims to be.** Truncation avoids splitting a UTF-8 sequence,
  but nothing validates the input as UTF-8 or refuses an embedded NUL - and `label()` reads only up
  to the first NUL, so what is written and what is read back can differ. Same treatment as snapshot
  names: validate, refuse NUL, then truncate.

## What this audit does not say

Nothing here was reproduced at runtime; the audit was static and so was this verification. Every
finding above was confirmed by reading the code it names, and several are contradicted by no test
because no test goes there - which is the point. The recommended first move is the audit's own: turn
the top findings into small regression tests over the existing `MemDevice`, where nearly all of them
can be built by hand.
