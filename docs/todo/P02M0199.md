# P02M0199 - Display brightness: a backlight contract, its providers, its keys and a tool

Status: OPEN. Created 2026-09-25 under the owner's approval of P02M0196 - "yes, do all of it; where a
milestone is missing, create it". NOTHING HERE IS STARTED: the owner asked for plans only until he says
otherwise, and no part starts without its own written plan.

WHY. A laptop panel's brightness is set through the firmware (ACPI's video extension: `_BCL`, `_BCM` and
`_BQC` on the panel's output device) or through the graphics driver's own registers; an external monitor's,
over the display cable (DDC/CI) or over USB (the HID monitor-control pages). None of them has anywhere to go:
DisplayService's vocabulary has no brightness, and `drivers/core/src/keys.rs` reserves KEY_BRIGHTNESSDOWN and
KEY_BRIGHTNESSUP "until backlight control exists".

WHAT THE DESIGN STARTS FROM, as the tree has it today:
  - DisplayService drives ONE scanout: the first `display` provider it connects to, or the boot framebuffer
    when nothing is published. Every surface configuration says `output: 0`, `set-scale` names no output, and
    the `display-device` wire carries one backing with no connector, EDID or name. Its state is ephemeral and
    it holds no configuration role.
  - Only a committed driver binding publishes into the provider catalogue, and a provider is named by its
    publisher's address. The kinds are a closed set, spelled in `device.lsidl`, `driver_protocol::provider`,
    the manifest's `ProviderKindName` and DeviceManager's two kind mappings.
  - The keyboard drivers put only keyboard-page (0x07) usages on the raw key sink, as three bytes (usage,
    state), and InputService streams them only to the display owner against a focus proof. Consumer-page
    usages - the brightness pair 0x6F/0x70 among them - end in `keys::feed_key`, which drops them as reserved;
    virtio-input forwards a code only when `keys::keycode_hid` has a keyboard-page usage for it, and EV_KEY
    224/225 have none. The one key InputService acts on before delivery is the secure-attention chord.
  - The HID field table (`drivers::hid::fields`) the UPS class maps over, and an EDID parser proved on the
    host (`user/libs/display/edid`) that nothing can feed yet.

WHAT IT RESTS ON. P02M0196 supplies the mechanism and this milestone the backlight CLASS on it: platform
devices and their claim (P02M0196a); the interpreter and namespace enumeration (P02M0196b); the COMPANION JOIN,
which resolves an `_ADR` node to its PCI function and makes a video OUTPUT node below an adapter - whose `_ADR`
is a display id and which names no registers - a METHOD-ONLY platform device claimable on its own; the
NODE-SCOPED CHANNEL to the ACPI service a driver receives with its claim, to evaluate methods on its node and
receive that node's `Notify` values; and P02M0196d's fixture - the region the harness controls and the path by
which it makes the firmware raise a notification. The USB half rests on nothing from P02M0196 (ORDER, below).

## P02M0199a - The output model and the contract

- [ ] OUTPUTS, AS DISPLAYSERVICE HAS THEM. There is exactly one output today, id 0 - the id every
  `surface-configuration.output` already carries - whatever the scanout is. DisplayService records its SOURCE
  and re-evaluates it whenever the scanout changes (a provider adopted, a rebind, the fall-through to the boot
  framebuffer): `provider(pci-address)`, the publisher address of the `display` provider it drives, or
  `boot-framebuffer(option<pci-address>)`, the PCI function that decodes the boot framebuffer. The second needs
  one kernel addition: the kernel holds both the framebuffer's physical base and the BARs its own PCI scan
  recorded, finds the function whose memory BAR contains that base, and returns it in the descriptor
  `framebuffer_map` fills - a decoder address and a present flag appended to `abi::Framebuffer` (ConsoleService,
  its other reader, is rebuilt with it); ramfb and a device-tree simple framebuffer have none. The output
  record also carries an EDID identity, which is NONE on every output today: the `display-device` wire has no
  field for it and the DDC/AUX transport P02M0099 lists is unowned, so adding one is that display driver's work.
  An output id is not persistent and a stored level is not keyed by it. Several outputs are not this
  milestone's; the vocabulary is a list, so they are additive.
- [ ] A BACKLIGHT IS WHAT HAS A LEVEL, NOT THE OUTPUT. A backlight provider describes itself:
  - its kind - firmware (ACPI video), USB monitor, or native (a graphics driver's registers);
  - its STABLE KEY, which survives a reboot and is what a stored level is keyed by: `acpi:` and the output
    node's namespace path; `usb:` and vendor:product:serial string, or vendor:product and the port path when
    the device has no serial; a native driver's function vendor:device and connector;
  - its levels - a discrete list, or a range with its logical minimum and maximum - and the firmware's AC and
    battery defaults where it has them;
  - its TARGET: the PCI function it belongs to (ACPI and native), the EDID identity - manufacturer id, product
    code, serial number - the monitor reports (USB, where the descriptor has the EDID usage), or none. A driver
    never derives its target: the ACPI one copies the adapter's PCI function from its claim's identity, the USB
    one reads the EDID from the device.
- [ ] JOIN RULES, run by DisplayService whenever a backlight appears or leaves or the output's source changes;
  each join records its reason:
  - `native`: a backlight published by the same binding as the output's `display` provider joins it;
  - `firmware-adapter`: an ACPI video backlight joins when its target equals the output source's PCI function -
    the display provider's publisher, or the boot framebuffer's decoder. On the laptops this exists for,
    nothing binds the graphics function and the panel is the boot framebuffer, which is why the decoder is
    needed;
  - `edid`: a USB backlight joins when the output has an EDID identity and it equals the monitor's (base-block
    manufacturer id, product code and serial number, read with the in-tree `edid` parser). Dormant until some
    output has an EDID, and host-tested until then;
  - `single-output`: otherwise, when output 0 has no backlight joined by the rules above and exactly one USB
    backlight is unjoined, that one joins it.
  No operator association is built: an unjoined backlight is still settable through the tool by its key.
- [ ] ONE ACTIVE BACKLIGHT PER OUTPUT, because two writers on one panel is the conflict this rule prevents:
  native before ACPI video before USB by EDID before single-output; between two ACPI outputs under one adapter,
  the one whose display id (`_ADR` bits 11:8) says internal flat panel, then namespace order. The others joined
  to that output are SHADOWED: listed with the winner's key, refused a set (`busy`), and never stepped, dimmed,
  defaulted or restored. An UNJOINED backlight is listed with no output: the tool can set it and the policy
  restores its stored level, but no key, firmware hotkey, idle dimming, default or automatic brightness acts on
  it.
- [ ] THE CLIENT VOCABULARY in `liber:display@1`, served by DisplayService. Not on `display-admin`, because
  brightness is not display administration and must not require it:
  - `display-brightness`, the READ: `outputs()` (id, source, EDID identity), `backlights()` (key, kind, output
    and join reason or none, active/shadowed/unjoined, levels, current level, floor, firmware defaults), and
    `subscribe()` - a snapshot, then one event per change of any backlight whoever made it, with its cause
    (key, firmware hotkey, device - a monitor's own buttons -, client) and a serial. A subscriber that stops
    reading has its stream closed rather than silently losing one backlight's last event, and resubscribes for
    a fresh snapshot;
  - `display-brightness-control`, the SET: `set(key, target, allow-zero)`, the target an absolute level, a
    percent of the range mapped to the nearest level, or a signed number of steps; it answers the level set and
    the serial of the event it produced. The manifest hands this root to the brightness policy alone (0199c);
    no capability name resolves to it.
  - THE FLOOR IS DISPLAYSERVICE'S, because a panel at level zero can be black and a black screen cannot be
    read to undo it: no key, firmware hotkey, step or ordinary set goes below it; only a set with `allow-zero`
    does. Default: the lowest level at or above 5 % of the range; the owner confirms the number when the part
    starts.
  - STEPS: a discrete backlight steps to the next listed level; a range steps by one sixteenth of its span,
    at least one unit.
  - A backlight call never blocks DisplayService's loop: it is issued and its answer awaited in the loop's wait
    set, with a deadline; a provider that misses it is marked failed and left out of the join until it answers
    again. Backlights arrive on the standing subscription loop, never waited for at bootstrap.
- [ ] THE DEVICE SIDE in `liber:display-device@1`, beside the display wire, because display brightness is its
  only consumer: `backlight` - `describe`, `get`, `set` and `events` (the level changed by the firmware or the
  device; a firmware hotkey: up, down, cycle, zero); and `ambient-light` - `describe` (the firmware's response
  curve where it has one) and `events` (illuminance in milli-lux).
- [ ] TWO PROVIDER KINDS, appended as the next two numbers when the part lands (21 and 22 today): `backlight`,
  whose one consumer is DisplayService, and `ambient-light`, whose one consumer is the brightness policy. Every
  spelling of the closed set moves together: `provider-kind` in `device.lsidl`;
  `driver_protocol::provider::{BACKLIGHT, AMBIENT_LIGHT}`; `ProviderKindName` and `wire()` in `system-manifest`;
  `provider_kind_from_wire` and `provider_kind_wire` in DeviceManager. Catalogue roles: DisplayService's
  `CATALOGUE` becomes `kinds = ["display", "backlight"]`; the policy's own is `["ambient-light"]`. Publishers,
  every one a driver binding: `acpi_backlight` and `xhci` publish `backlight`; `acpi_als` and `xhci` publish
  `ambient-light` (0199b); `xhci`'s `provides` gains one of each.
- [ ] TWO CAPABILITIES appended to `security.lsidl`'s `capability` enum after the last one present when the part
  lands, split the way `power-state` and `power-control` are:
  - `brightness`, the READ: outputs, backlights, levels and the change stream - a connection from
    DisplayService's new `BRIGHTNESS` serve-root, on which nothing sets anything;
  - `brightness-control`, the SET: set a level and change the policy's two settings - a connection from the
    brightness policy's `CONTROL` serve-root.
  Broker names `CAP_BRIGHTNESS` and `CAP_BRIGHTNESS_CONTROL` in `capability_names.rs`; ServiceManager resolves
  them to `display_service`/`BRIGHTNESS` and `brightness_policy`/`CONTROL` and lists both in
  `permission_manager`'s resolvable set; PermissionManager mints a fresh connection per grant, as it does for
  `power-state`. ROWS: `brightness`, the shipping tool, holds both, as `btctl` holds both Bluetooth authorities;
  the development probes `brightcheck` holds both and `brightread` holds `brightness` alone - its half of the
  gate is that it can read and cannot set. Nothing else is granted either. THE KEYS NEED NO GRANT: they reach
  DisplayService, which owns the brightness, on a stream InputService hands to it alone (0199c).

## P02M0199b - Providers and sensors

- [ ] ACPI VIDEO BACKLIGHT, the driver `acpi_backlight`:
  - IDENTITY AND MATCH. The panel's output node is a method-only platform device (P02M0196's companion item).
    Its match form is a class this milestone defines and P02M0196b's enumeration assigns: `video-output`, for a
    method-only device whose parent is a PCI companion that has `_DOD` or `_DOS`, and which itself has `_BCL`
    and `_BCM`. Its identity carries the parent's resolved PCI function, which becomes the backlight's target,
    resolved whether or not any driver binds that function; an adapter that resolved to no function leaves the
    backlight unjoined.
  - METHODS, over the node-scoped channel that comes with the claim: `_BCL` read once and normalised - the first
    two entries are the AC and battery defaults, the rest sorted and deduplicated, values above 100 dropped;
    fewer than two levels is a firmware defect, reported, and nothing is published. `_BCM` sets. `_BQC` reads;
    a value not in the list is reported as the nearest listed level and logged once; without `_BQC` the level
    is the last one set, unknown until then.
  - `_DOS` IS THE ADAPTER'S, NOT THE OUTPUT'S. This match row declares one method on the PARENT node, `_DOS`,
    which the node-scoped channel admits beside the output node's own. Evaluated at bind with 0x04: bit 2 set,
    so the firmware changes no brightness itself on a hotkey and only notifies; bits 1:0 clear, so an output
    switch is notified rather than performed behind the system. The adapter's switch notifications
    (0x80-0x84) go to the adapter's node, which this driver does not receive. A native graphics driver bound to
    the adapter's function would own `_DOS` through its companion; until one exists this driver evaluates it.
    In its RESUME step of P02M0197's driver contract it evaluates `_DOS` again and re-applies the level with
    `_BCM`, because firmware may reset both across a sleep.
  - NOTIFICATIONS on the output node, the whole map: 0x85 cycle brightness, 0x86 increase, 0x87 decrease, 0x88
    zero, 0x89 display off. The first four are forwarded as hotkeys and DisplayService applies them like keys:
    up and down one step; cycle one step up, from the top level to the floor; ZERO TO THE FLOOR AND NOT BELOW,
    because a firmware key press is not the explicit request zero needs. 0x89 changes no level and is logged -
    display power is not this milestone's. Any other value is logged and ignored. FIRMWARE THAT STEPS ANYWAY:
    before forwarding up, down or cycle the driver reads `_BQC`, and a level that already moved in that
    direction since the last set is reported as a firmware change instead of a hotkey - one press, one step.
- [ ] USB MONITOR CONTROL in driver.xhci, a class module (`class_display_hid.rs`) that is a map over
  `drivers::hid::fields` as `hid_power` is, never a second parser: an interface whose report descriptor has a
  Monitor Control application collection (Monitor page 0x80, usage 0x01) with the VESA Virtual Controls page's
  Brightness (0x82:0x10) as a feature report publishes `backlight`. Its range is the field's logical minimum and
  maximum; GET_REPORT reads, SET_REPORT sets; an input report carrying brightness, where a device sends one, is
  a device change; EDID Information (0x80:0x02), where the descriptor has it, is read once for the target.
  Placed after the input path in the class dispatch, as the power device is, so a keyboard or pointer interface
  is never taken for it. It is the second provider, which keeps the contract from being the shape of ACPI's.
- [ ] AMBIENT-LIGHT SENSORS, published as `ambient-light` and consumed by the brightness policy alone:
  - ACPI's `ACPI0008`, the driver `acpi_als`, matched by `_HID`: `_ALI` the illuminance, `_ALR` the response
    curve (pairs of adjustment and illuminance), `_ALP` the polling interval where the firmware sends no
    notification; `Notify` 0x80 (illuminance changed) and 0x82 (response changed) over its node-scoped
    channel. The colour methods `_ALC` and `_ALT` are not read;
  - the HID sensor page's, in the same xhci module: an Ambient Light collection (0x20:0x41) whose Illuminance
    data field (0x20:0x4D1) arrives in input reports, its unit exponent applied, and its reporting-state and
    power-state properties set by SET_REPORT so that it reports. A descriptor holding both a Monitor Control and
    an Ambient Light collection - a monitor with a light sensor - publishes both providers from one interface.
- [ ] DDC/CI (MCCS luminance over the display cable) waits for the DDC/AUX transport P02M0099 lists as
  blocked on "a display controller that can reach a bus", and a native graphics driver's own backlight
  registers come with that driver. Both are named here so the contract is written for them: the native kind,
  its join and its precedence are already in 0199a.

## P02M0199c - Keys, policy and the tool

- [ ] THE KEY PATH, and the raw key contract that changes for it:
  - THE DRIVERS. `usb_hid` puts the consumer-page usages of the SYSTEM-KEY set - brightness increment 0x6F and
    decrement 0x70 - on the raw key sink as a FIVE-byte frame (page, usage, state); keyboard-page usages keep
    their three-byte frame. virtio-input translates EV_KEY 225 and 224 into the same frame through
    `keys::keycode_consumer`, the inverse of `consumer_keycode`, so one table stays the single mapping source.
    Neither goes to the trusted sink. The console path keeps consuming both as reserved keys; the comment above
    them names where they go instead.
  - INPUTSERVICE decodes the five-byte frame apart from `record_raw` and reserves the set BEFORE ORDINARY
    DELIVERY, as it reserves the secure-attention chord. A consumer-page usage never enters `key-event`, which
    stays keyboard-page, so no client of it changes. A press is sent, non-blocking, on `system-keys` - a new
    serve-root `SYSKEYS` (`liber:input@1/system-keys`: a stream of `brightness-up` and `brightness-down`
    presses) handed as an exclusive client role to DisplayService, which already depends on InputService, so no
    ordering changes. Releases are not sent; raw input never repeats, so a held key is one step.
  - DISPLAYSERVICE applies a press to output 0's ACTIVE backlight: one step, never below the floor; with no
    active backlight it does nothing and says so once. A keyboard key and a firmware hotkey for one physical
    press - many laptops send both - are one step: a second step in the same direction from the other source
    within 100 ms is dropped.
  - DURING THE PROTECTED SESSION the brightness keys still act: they reach no application, they show and accept
    nothing, and the person at the protected screen has to be able to read it. The routing sits before
    InputService's `protected` check; the trusted keyboard's sink carries no consumer page and does not change.
- [ ] THE ACTIVITY SIGNAL. InputService, which sees every key, pointer and contact from every source, serves a
  new root `ACTIVITY` (`liber:input@1/input-activity`): `watch(idle-after)` answers a stream of edges - `idle`
  once there has been no input for that long, `active` at the first input after it - and nothing about what
  the input was. Input during the protected session counts. Its holder here is the brightness policy.
- [ ] THE BRIGHTNESS POLICY, a service of its own, `brightness_policy`, BECAUSE THE SCREEN MUST NOT WAIT FOR A
  VOLUME: restoring a level needs ConfigService, which starts after StorageService, while DisplayService starts
  without either and stays ephemeral with no configuration role. Dependencies: log_service, device_manager,
  input_service, display_service, power_service and config_service. Roles: clients of DisplayService's
  `BRIGHTNESS` and `BRIGHTNESSCTL` (the second exclusive), `CONFIG`, PowerService's `liber:power@1/power` read,
  InputService's `ACTIVITY`, and a `CATALOGUE` for `["ambient-light"]`; it serves `CONTROL`
  (`liber:display@1/brightness-policy`: set a level - forwarded to DisplayService with the caller's explicit
  zero, so the floor holds the same - and the two settings below). Restart transparent, state
  reconstructible. Without it keys, firmware hotkeys and the floor still work, and nothing is restored or
  dimmed. Its behaviour, with defaults the owner confirms when the part starts:
  - STORED LEVELS in ConfigService under `display.brightness.level.<stable key>`, in the provider's units,
    written once a level has been still for two seconds - ConfigService writes through on every set, and a held
    key would otherwise write each step; a change the policy made itself for idle dimming or automatic
    brightness is never stored, which it knows from the serial its own set answered;
  - RESTORED when a backlight appears whose level nothing has set since it appeared - at boot, after a replug,
    after a driver restart - snapped to the nearest current level and raised to the floor;
  - FIRMWARE DEFAULTS where nothing is stored: `_BCL`'s battery default when PowerService reports the machine
    running on battery, its AC default otherwise; without firmware defaults, the level the backlight came up
    with;
  - IDLE DIMMING of the active joined backlight after the idle timeout, to a fraction of its level (proposed:
    30 %) and never below the floor, restored on `active` unless someone changed the level meanwhile;
  - AUTOMATIC BRIGHTNESS off unless the owner chooses otherwise when the part starts: the active joined
    backlight follows the illuminance through `_ALR`'s curve, or, for a HID sensor, a default curve the policy
    carries, with hysteresis; a key or a set pauses it until the next idle, or as the owner decides;
  - its two settings - automatic brightness and the idle timeout - stored under `display.brightness.auto` and
    `display.brightness.idle`.
- [ ] `brightness`, a shipping tool: without arguments, the outputs and every backlight with its key, output
  and join reason or state, levels, current level and floor; `set` absolute, percent, `up`, `down`, with
  `--backlight KEY` for a backlight other than output 0's active one and `--zero` for the explicit zero;
  `auto on|off`; `idle SECONDS|off`.

## P02M0199d - Verification

- [ ] HOST SUITES: `_BCL` normalisation (defaults, ordering, duplicates, out-of-range values, too few levels)
  and `_BQC` values outside the list; THE WHOLE NOTIFICATION MAP, 0x85 to 0x89 and a value outside it, each to
  its effect; percent, step and floor mapping for lists and ranges, zero refused without `allow-zero`; the join
  and precedence table - native, ACPI by function, the boot framebuffer's decoder, USB by EDID, single output,
  shadowed, unjoined, ties; the kernel's BAR-containment decision; the VESA brightness and HID illuminance
  fields decoded from descriptors, unit exponents included; `_ALR` interpolation; the EDID identity compare;
  EV_KEY 224/225 to consumer 0x70/0x6F and back; InputService routing five-byte frames to `system-keys` -
  never into `key-event`, and during the protected session too - with the secure-attention reservation
  unchanged; the activity edges; the policy's settling write, restore rule, idle restore after a manual
  change, and defaults by AC state. The virtio pair is host-only: QEMU's key-code list has no brightness key
  to inject.
- [ ] USB, THROUGH THE GADGET, as P02M0099's UPS is proved (`usb_f_hid` with its own report descriptor and a
  far-end process like `ups-sim.py`), started by `test-kernel.sh` the way the UPS far end is.
  `usbredir_device.py` is not used: it plays neither a HID device nor an interrupt IN endpoint. Two new kinds
  in `usb-gadget.sh`:
  - `monitor`: one HID interface holding a Monitor Control collection (a Brightness feature report, 0..100, and
    an EDID Information feature report) and an Ambient Light collection, answered by `monitor-sim.py`, which
    records every brightness it is sent by SET_REPORT, answers GET_REPORT with the current one, and steps the
    illuminance dark, bright, dark in input reports. Checks: the backlight listed and joined to output 0 as
    `single-output` (no ACPI backlight, no output EDID); `brightcheck` sets an absolute level, a percent, up and
    down, and the far end saw each value; zero refused without `--zero` and accepted with it; `brightread` reads
    and is refused a set; with automatic brightness turned on by `brightcheck`, the level follows the light.
  - `consumer-keys`: a Consumer Control collection whose far end, `keys-sim.py`, presses brightness up twice and
    down once after configuration; checked against the ACPI fixture's backlight below, because a gadget is one
    device and xhci binds one class module per device.
- [ ] ACPI, THROUGH P02M0196d'S FIXTURE on x86_64: an SSDT, emitted by the in-tree AML generator the fixture
  uses, with a video adapter that the companion join resolves to the function decoding the boot framebuffer -
  on the test profile q35's default VGA function, confirmed from the kernel's own scan when the part starts, and
  extending QEMU's own node for that function by `Scope` where its DSDT has one rather than declaring a second
  node with the same `_ADR`; under it an output with `_BCL`, a `_BCM` that writes and a `_BQC` that reads the
  region, and an adapter `_DOS` that records its argument there; and an `ACPI0008` whose `_ALI` reads the
  region. Checks: the backlight joined as `firmware-adapter`; `_DOS` saw 0x04; the region holds every level the
  system sets; each of 0x85 to 0x89, raised through the fixture's notification path, has its effect - 0x88 lands
  on the floor, 0x89 changes nothing; the `consumer-keys` presses move it one step each; with automatic
  brightness on, the level follows an illuminance the harness writes and announces with 0x80 through `_ALR`'s
  curve; and after a second boot on the same volume, the region starting at the firmware default, the level
  stored in the first is restored.
- [ ] ORDER: the USB half - the contract, the xhci module, the gadget kinds, the key path, the activity signal,
  the policy and the tool - needs nothing from P02M0196 and lands first. The ACPI half - `acpi_backlight`,
  `acpi_als` and their checks, the key gate among them - waits for P02M0196a's platform devices, P02M0196b's
  enumeration with the `video-output` class, the companion join and the node-scoped channel with its parent
  `_DOS` allowance, and P02M0196d's fixture.

EXCLUDES: an on-screen level indicator, which belongs to whatever draws the session; keyboard backlights,
which are a vendor-specific control on most machines; display output switching (the adapter's 0x80-0x84
notifications, `_DOD`, `_DCS`, `_DGS`, `_DSS`) and display power, including acting on 0x89; an operator-made
association of a backlight with an output; more than one output in DisplayService.
