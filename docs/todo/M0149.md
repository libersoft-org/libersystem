# M0149 - A fault in a user copy must be an error, not a dead kernel

Status: DONE (2026-08-10). Reopened the same day by an audit that found the mechanism built and the
contracts around it missing - the two process-load syscalls bypassed it entirely, and every caller of
the new copies threw away the count that said how far they got. Both are closed: `copy_to_user_exact`
and `copy_from_user_exact` are the forms the call sites use, `write_user` returns a `Result` and has
no infallible form, the receive paths put a message back on the queue rather than half-deliver it,
and the ELF loader reads a kernel buffer. The last section is that round. Carried out of M0145, which verified the defect and could not fix it inside its own
scope: the fix is an exception table and three architectures' worth of trap entry, which is a
milestone rather than a task.

Every syscall that reads or writes userspace memory checks the buffer first - `user_buf_ok` and
`user_buf_writable` validate the range and its permissions, and they do it correctly. Then the copy
happens. Between those two moments another thread in the same process can unmap the page, and the
kernel takes a page fault in ring 0 on an address it just proved was fine. The comment on
`write_user` says so itself.

The check is not the bug. The check cannot be the fix: the window is inherent to checking a thing
and then using it, and closing it by holding the address-space lock across every copy would put a
userspace-controlled length inside a lock the fault handler needs. What is missing is the other
half - an access that faults inside a marked region resumes at a fixup address and returns an error,
the way every kernel that survives this does it.

## What is wanted

- [x] **An exception table.** A section of (faulting address, fixup address) pairs emitted by the
  copy routines and collected by the linker script, sorted at boot or at link time so the fault
  handler can binary-search it. One table, three linker scripts, and a shared lookup.

- [x] **Faultable copy primitives.** `copy_from_user` and `copy_to_user` written so that every
  instruction that touches a user address is inside a marked region with a fixup that returns
  `ERR_INVALID` (or the count copied so far, where a partial copy is meaningful). They replace the
  raw `copy_nonoverlapping` calls, not sit beside them.

- [x] **Per-architecture entry.** The page-fault path on x86_64, aarch64 and riscv64 consults the
  table before it decides a kernel fault is fatal, and resumes at the fixup with the error in the
  return register. Each has its own trap frame and its own idea of which register that is; this is
  the part that cannot be shared and the reason this is not a single afternoon.

- [x] **Every bulk path goes through them.** IPC receive currently does a raw `copy_nonoverlapping`
  after a general validation, which is the same window with none of the protection. Find the rest by
  grepping for the primitives rather than by memory: an unconverted path is invisible until it
  faults.

- [x] **A test that unmaps the page during the copy.** The defect is a race, so the test has to make
  the race happen: one thread in a long copy, another unmapping underneath it, and the syscall
  returning an error while the system stays up. Without this the milestone would be asserting that
  code was written, not that it works. Watch it fail first - with the fixup disabled the kernel
  should die, and if it does not, the test is not reaching the window.

- [x] **Then reconsider what the up-front checks are for.** With a faultable copy, `user_buf_ok`
  stops being the safety mechanism and becomes an early, cheap rejection of obvious nonsense. That is
  still worth having; what is not worth having is two mechanisms where the comments disagree about
  which one is load-bearing.


## What was built

`kernel/extable.rs` holds the table and the lookup; `arch/<arch>/usercopy.rs` holds the copies that
may fault. Every instruction that touches a user address emits its own `(faulting, fixup)` pair into
`.extable`, the linker gathers them between `__extable_start` and `__extable_end`, and each
architecture's fault path consults the table before deciding a kernel fault is fatal.

The match is on the faulting address EXACTLY, never a range. A fixup can only ever rescue an
instruction a copy routine put in the table itself; everything else still halts, which is what keeps
a real kernel bug loud.

**The lookup is linear, and that is a decision rather than a shortcut.** The milestone asked for a
sorted table and a binary search, which is right for the tens of thousands of entries a
general-purpose kernel accumulates because `get_user` is a macro inlined at every call site. Here
the faulting instructions ARE the copy routines and there are six. Sorting them costs a boot step
and a buffer to hold the sorted copy; a binary search over six entries is slower than reading them.
`the_exception_table_exists_and_is_small_enough_to_scan` asserts both ends of that - that the table
is not empty, and that it has not grown past the size where the reasoning holds.

x86_64 uses `rep movsb`: one instruction, so one entry per routine, and RCX holds exactly the count
still to go when it faults - the partial-copy answer, free. aarch64 and riscv64 use a byte loop with
two entries each, the load and the store, because either can be the one that faults depending on
direction. A word loop would be eight times fewer iterations and needs an alignment prologue, an
epilogue and four entries; worth doing if a measurement says the copy is the cost, and not worth
guessing at first.

### Three ways to write the resume, two of them wrong

The fixup is "make the fault return somewhere else", and each architecture hides a different trap in
that sentence.

**x86_64 - the compiler deleted it.** `frame.instruction_pointer = fixup` on the by-value
`InterruptStackFrame` drew *"value assigned to `frame` is never read"*, which is true of the local
and false of the machine: rustc's `x86-interrupt` ABI materialises that parameter in place, so the
store is what `iretq` resumes at - and nothing in the function reads it again, so every rule the
optimiser knows says the store is dead. It would have been deleted and the fault would have fallen
through to the halt. A `write_volatile` is the statement that the store IS the point. **The warning
was the only thing standing between this and a fix that silently did nothing.**

**aarch64 - the stub overwrote it.** `msr elr_el1, fixup` is the obvious translation and it is
undone on the way out: the vector stub saves ELR_EL1 into the trap frame on entry and
`__trap_return` loads it back before `eret`. The fault resumed at the faulting instruction, which
faulted again, forever. A livelock inside a fault handler prints nothing, so the aarch64 suite
simply stopped on the fixup test with no diagnostic at all. The fixup goes into the SAVED ELR at
frame offset 248.

**riscv64 - correct the first time**, and for a reason worth naming: the handler already receives
the trap frame as a pointer, so writing the saved SEPC was the only thing to write. The register did
not offer itself as a tempting wrong answer.

### The tests

`a_copy_to_a_page_that_is_not_there_reports_rather_than_kills_the_kernel` copies both directions to
an unmapped user address and asserts zero bytes moved and the fault counter advanced. Watched to
fail, and the failure is not a red test: with the lookup disabled it prints
`EXCEPTION: page fault ... CR2 = 0x7f0000000000` and the machine stops. An unfixed kernel and a
broken fixup look identical from there, which is the point - there is no way to write this test such
that it merely goes red.

`a_copy_that_loses_its_page_partway_reports_exactly_how_far_it_got` is the milestone's "unmap during
the copy", arranged so it happens every time. Two adjacent user pages with only the first mapped put
the copy in precisely the state a mid-copy unmap leaves - faulting partway, with bytes already
delivered behind it - at precisely the boundary. It asserts the ACCOUNTING, which the wholly-absent
case cannot: that the count coming back is the bytes that landed, and that they really landed. A
caller believing a wrong count truncates a message or reads uninitialised memory.

The genuine interleaving is not reproducible on a cooperative single-core harness and this suite has
retired tests that pretended otherwise. What is asserted is the state the race produces.

### What the up-front checks are for now

`user_buf_ok` and `user_buf_writable` stay, and their comments say what changed: they are no longer
the safety mechanism but an early, cheap refusal of obvious nonsense - a null pointer, a range that
wraps, an address past the user half, a read-only page where a write is coming. Refusing there
answers a caller with a clean error instead of a short copy nobody asked how to interpret. What is
gone is two mechanisms whose comments disagreed about which one was load-bearing.

## Reopened: the primitives are right and the contracts around them are not

An outside audit of the code, 2026-08-10. Everything it said held against the tree, and the summary
is worth stating plainly: **this milestone was closed on the mechanism and the mechanism is only half
the job.** The copies report how far they got; almost nothing reads the answer, and the two biggest
callers of userspace memory do not use them at all.

The status above goes back to IN PROGRESS. What follows is in the order it should be fixed.

- [x] **`SYS_PROCESS_LOAD` and `SYS_PROCESS_LOAD_MODULE` still hand a raw userspace slice to the ELF
  loader.** `core::slice::from_raw_parts(elf_ptr, elf_len)` and then the whole loader runs inside
  `user_access`, reading it. Every one of those reads is an ordinary instruction in the loader, not
  a declared entry in `.extable`, so a page that goes away mid-load faults in ring 0 at a PC nothing
  can rescue and the machine halts.

  **This is the exact class this milestone exists to close, and it is still reachable from ring 3
  with no privilege at all**: a process creates a child in its own Domain, holds MANAGE on it, calls
  load on a large image, and unmaps the buffer from a second thread. The comment above the slice
  explains why the ELF is not buffered on the kernel heap - a multi-megabyte copy per spawn - and
  that reasoning is sound, which is why the answer is not "copy it".

  The answer is to stop passing a pointer. The image should arrive as a MemoryObject handle plus an
  offset and length, so the kernel holds a reference to the backing for the whole load and there is
  nothing for the caller to unmap. That is an ABI change to two syscalls and their callers, which is
  why it is a task rather than a fix.

  DONE 2026-08-10, by BUFFERING rather than by the ABI change, and the reasoning is worth keeping.
  The image is copied into a kernel `Vec` through `copy_from_user_exact` - bounded by
  `MAX_ELF_BYTES`, fallible - and the loader then reads memory userspace cannot take away. It costs
  one copy of the file per spawn, about a megabyte for the programs this system has, against a spawn
  that already allocates and fills a frame per loaded page.

  The MemoryObject ABI is the better answer at scale and was not taken, because `MemoryObject`
  exposes a LIST of frames and the ELF parser wants a contiguous slice, so it would need a
  gather-copy anyway unless the frames happen to be contiguous. If images ever approach the 64 MB
  the ceiling allows, that is the change to make and this note is why.

  The test is `a_process_load_whose_image_goes_away_is_an_error_rather_than_a_dead_kernel`, driven
  from a kernel thread through the real syscalls because the load must get past a process handle
  before it reaches the image. It asserts on the FIXUP COUNTER, which is what separates the two
  kernels: with the buffer, the absent page is reached at a declared instruction and counted; with
  the raw slice it is reached by the ELF parser, which is not in the table. Watched failing by
  restoring the in-place read - and note what that run showed, because it is the honest limit of the
  test: the old kernel did not halt, it rejected the header before it ever read the second page. A
  test that made it halt would hang the suite rather than fail it, which is the property this whole
  file lives with.

- [x] **Six of six `copy_to_user` call sites discard the count.** `write_user`, `console_readlog`,
  `boot_profile`, `random_get`, `sys_channel_recv` and `sys_channel_recv_caps` all call the faultable
  copy and ignore what it returns, then report the length they were ASKED for. A short write is
  therefore indistinguishable from a complete one, to the caller and to the kernel.

  On the receive path that breaks the invariant M0151 is named for. The message is taken off the
  queue, the copy delivers 800 bytes of 4096, the capabilities are installed, and the syscall returns
  4096. The message is gone and the caller has most of it and does not know. M0151 closed the
  handle-resource transaction and M0149 opened a second boundary behind it - the queue against
  userspace memory - and that one is still open.

  DONE 2026-08-10. Every one goes through `copy_to_user_exact` and answers `ERR_NOT_MAPPED` on a
  short copy. The two receive paths do more than report: the payload is copied BEFORE anything is
  installed, and if it will not land the message goes back to the head of the queue
  (`Channel::return_to_head`) and nothing is consumed - a short copy means the caller unmapped its
  own buffer, which is not a reason to destroy what somebody else sent.

  One residual, stated rather than hidden: in `sys_channel_recv_caps` the capability ARRAY is
  written after the handles are installed, and the handles have by then left the message, so a
  failure there cannot put the message back. What is recoverable is recovered - every installed
  handle is closed, so nothing leaks - and the caller gets an error instead of a length. Writing the
  array first is impossible, because the numbers do not exist until the handles do.

- [x] **`read_bytes` ignores its count too, and a short read becomes a short message.** The payload
  buffer is zeroed first, so a send whose source page vanishes halfway delivers the prefix followed
  by zeros and returns success. Zero-filling was the right call for `read_user<T>` - a partially read
  scalar must not carry stack residue into a decision - but for a payload it turns a failed copy into
  a plausible message.

- [x] **`SYS_CHANNEL_CREATE` can report success without delivering either handle.** Both endpoints
  are inserted into the caller's table, then `write_user` puts the two raw handles out and its result
  is dropped, then `0`. If the output page went away after `user_buf_ok`, the caller owns two handles
  whose numbers it never received: a leak the caller cannot close and a success it cannot act on.
  Every syscall with an out-parameter has this shape.

- [x] **Give the milestone the two APIs the call sites actually need.** `copy_to_user_exact` and
  `copy_from_user_exact` returning `Result`, for the majority of callers where a partial copy is a
  failed syscall; and the counting form kept, named as such, for the few where a partial transfer is
  the answer. `write_user<T>` should return `Result` and have no infallible form at all - a
  fire-and-forget write to userspace is how three of the defects above are spelled.

- [x] **A fault is recovered on the PC alone; the faulting ADDRESS is never checked.** All three
  handlers ask `extable::fixup_for(pc)` and resume. But the entries cover instructions with a kernel
  operand as well as a user one - aarch64 and riscv64 declare both the load and the store, and
  x86_64's `rep movsb` has source and destination in one instruction - so a kernel bug that passes a
  bad KERNEL pointer to `copy_to_user` is recovered as though it were an ordinary user-copy fault,
  silently, and the caller is told it copied fewer bytes.

  The file claims the opposite: that an exact PC match keeps a genuine kernel bug loud. It does not,
  and the fix is one condition - recover only when the PC is in the table AND the fault address is in
  the user half. CR2 on x86_64, FAR_EL1 on aarch64, `stval` on riscv64; all three are already read at
  the top of their handlers.

  DONE 2026-08-10: `fixup_for(pc, fault_address)` refuses anything at or above `USER_VA_END` before
  it looks at the table at all, and all three handlers pass the address they already had. The test
  is `a_fault_on_a_kernel_address_is_never_rescued_however_the_pc_matches`, asserted on the lookup
  rather than by faulting - there is no way to arrange the real fault without also arranging the
  kernel bug. Watched failing with the condition disabled.

- [x] **`write_user`'s comment contradicts itself.** Lines above the function still say the window is
  not closed and that "closing that needs the fault-recovery table this milestone still owes"; lines
  inside it say the copy is faultable and that is what makes it safe. The second is true. The first
  is what an outside reader will believe, because it is the doc comment.
