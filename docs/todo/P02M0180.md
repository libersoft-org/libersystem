# P02M0180 - A sandboxed Bluetooth service above HCI

Status: OPEN. It closes when every implementation and verification item below is done.

The service owns Bluetooth host protocols and policy enforcement above a bounded HCI transport.
The USB transport in P02M0099 is still unimplemented. Its class module will live inside the USB
controller process under the existing `usb_class.rs` execution model; this service runs in a
separate process and resource Domain. It receives no device claim, MMIO, DMA or USB endpoint
capability. Platform radio policy remains outside this service.

## P02M0180 - Scope and implementation order

- [x] Deliver the transport wire, service, protected bond backend, real input consumer integration
  and an in-guest controller/peer fixture first. This is the prerequisite P02M0099 needs; service
  completion uses the fixture and does not claim USB transport coverage. The later USB item owns
  endpoint binding, transport recovery and its hardware/emulator gate against the same wire.
- [x] The first profile is the HID-over-GATT boot mouse subset, consumed by the existing
  InputService/ConsoleService pointer path. Support one LE central connection per controller,
  static/public peer addresses and an encrypted bonded boot mouse. Support bounded ATT/GATT
  discovery, Protocol Mode selection and Boot Mouse Input Report notifications. Convert relative
  movement/buttons to the existing normalized pointer stream and prove an actual cursor/button
  change. Do not add RFCOMM, BR/EDR profiles, keyboards, arbitrary report maps, audio, ISO streams,
  privacy-address resolution or additional profiles in this slice; return typed unsupported
  results for unsupported modes rather than claiming full HOGP conformance.
- [x] Require LE Secure Connections with a 128-bit key and a controller supporting the HCI P-256
  public-key/DHKey commands. Implement the host SMP state machine and AES-CMAC derivations in the
  host-testable leaf, using official vectors and independent expected values. Use healthy system
  randomness; refuse pairing if unavailable, and never use `random_insecure`. This mouse slice
  supports the Just Works association model, explicitly reported as encrypted but unauthenticated
  against active radio impersonation; no downgrade to legacy pairing. Operator authorization is
  required before pairing or enabling an input peer. Peer identity is not proven by its name.

**THE HOST-TESTABLE LEAF IS IN (2026-09-22), AND THE CRYPTOGRAPHY IS CHECKED AGAINST THE DOCUMENTS
RATHER THAN AGAINST ITSELF.** Six pure modules in `service-logic`, 39 host tests, no `rt` and no
`ipc-client` in any of them:

    aes      AES-128, encryption only - CMAC needs no other direction. FIPS-197 Appendix B and
               C.1, and the Core specification's own `e` sample.
    cmac     AES-CMAC. All four RFC 4493 examples and both published subkeys, checked separately
               so a failure says which half of the construction is wrong.
    smp      f4, f5, f6 and g2, every one against Core Appendix D.
    hci      packet kind, direction, the smaller of two ceilings, and the three credit counters.
    l2cap    ACL fragments back into PDUs, with the four ways that is not a PDU.
    hogp     the boot mouse report and the protocol-mode characteristic.

THE CURVE HALF IS THE CONTROLLER'S AND THERE IS NO P-256 HERE. This milestone requires a controller
with the HCI public-key and DHKey commands, so a host implementation would be a second version of
the one operation whose mistakes are silent, for no capability gained.

**THE f5 SALT IS CONFIRMED BY THE SPECIFICATION AND NOT BY A COMMENT.** Appendix D.3 prints the
intermediate `T` for a known secret; the test computes it from the constant in the module. A wrong
salt gives a wrong `T`, a wrong MacKey and a wrong LTK, and the pairing fails at the check value
with nothing saying why - so the one constant that cannot be inferred from a final value is checked
against an intermediate the document happens to publish.

AND THE COUNTER THAT SEPARATES THE TWO f5 KEYS IS THE ONLY THING THAT DOES. Counter zero is the
MacKey and counter one is the LTK. Swapped, a pairing between two implementations that made the
same mistake still completes and the link is encrypted with the key meant to authenticate it;
nothing observable distinguishes that from a correct pairing until a peer that got it right refuses
to talk. Both are asserted, and the document ties them together for free - `f6`'s sample is keyed
with the number `f5`'s counter-zero sample produced.

ONE VECTOR WAS WRITTEN FROM MEMORY AND WAS WRONG, which is why none of the others were. A second
`e` sample typed without the document failed, and the value was removed rather than adjusted: an
expected value a test cannot source proves only that the implementation agrees with whoever typed
it.

The protocol references are the [Bluetooth HID-over-GATT profile](https://www.bluetooth.com/specifications/specs/hid-over-gatt-profile-1-0/)
and the [Bluetooth Security Manager specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v6.3/out/en/host/security-manager-specification.html).
Use specifications and independently authored implementations; do not import differently licensed
stack source. The restricted mouse subset and security label are deliberate product scope.

## P02M0180 - Provider and client contracts

- [x] Add a typed internal HCI provider contract and a `bluetooth-hci` provider kind in
  `src/idl/device.lsidl`, corresponding registry/wire handling and generated bindings. Allocate
  unused enum values from the current combined vocabulary, never assume this is the only new kind.
  DeviceManager owns publication slot/generation and binding generation. A controller's USB child
  publication uses the controller binding lifetime plus its manager-assigned publication identity;
  no new independently claimed USB-interface identity is introduced.
- [x] Own the shared catalogue infrastructure stage before Bluetooth protocol implementation:
  add private `provider-catalogue-admin.open-consumer(kinds)` to DeviceManager and hand its
  root only to ServiceManager over trusted bootstrap. `kinds` is a bounded subset of the closed
  ProviderKind vocabulary. Minted clients enforce that subset on both `subscribe` and `open`,
  checking the manager's actual publication kind and generation rather than a caller's claimed
  kind. They expose no minting operation. ServiceManager mints each service's manifest-authorized
  client and updates all production/test bootstrap callers. Migrate existing consumer factories
  too: no legacy unrestricted `open` path may remain reachable by ordinary inventory clients.
  Preserve their read-only inventory operations without granting new private transport kinds.
  This stage is reusable by P02M0181
  through P02M0187 without waiting for Bluetooth completion. Raise the finite catalogue client
  and subscription caps from eight to 32, check the combined manifest needs against that budget
  and test cross-kind denial, stale-generation denial and refusal at the cap.

  **LANDED 2026-09-22, AND IT IS THE STAGE THE OTHER EIGHT SERVICES BUILD ON.** The catalogue's root
  answers the reserved CONNECT opcode, which takes no arguments - so every connection it minted
  reached every kind the machine publishes, and there was no smaller thing to hand out. A service
  needing one kind held the same authority as one driving eight, and the two consumers that only
  read the binding snapshot held it as well.

  WHAT IS THERE NOW: `provider-catalogue-admin.open-consumer(kinds)` in `device.lsidl`, served by
  DeviceManager on a second serve root delivered to ServiceManager alone. A minted connection
  carries its subset in the manager's own table, beside the channel it was minted with, and the
  subset moves with the channel when a slot is reused. `subscribe` is refused before the snapshot is
  taken; `open` is refused after the lookup, against the PUBLICATION'S kind rather than the one the
  caller named - a caller that could be believed about its own kind could name a different one.
  The root's own CONNECT now answers an INVENTORY connection, which reaches no provider at all.

  THE SUBSET IS DECLARED WHERE A SERVICE'S NEEDS ALREADY ARE. A factory role in the manifest takes
  `kinds`, validated against the closed provider vocabulary the manifest already carries, refused on
  any other role kind, bounded at the interface's own sixteen and refused for a kind named twice.
  Six rows carry one today: audio, display, input (three kinds), network, PermissionManager and the
  USB storage half. Empty is a real answer for the two inventory readers.

  THE CAPS ARE 32, AND EIGHT WAS ALREADY THE WHOLE BUDGET: nine rows mint a connection on an
  ordinary boot, so a boot that started all of them was at the ceiling with nothing left for a
  restart, and the refusal line had been observed during bring-up.

  **AND THE ENFORCEMENT FOUND A HAND-WRITTEN BOOTSTRAP A MANIFEST CHANGE COULD NOT.** PermissionManager
  is one of the branches the plan executor is still replacing, and it minted its catalogue
  connection through the root rather than from its row - so the row said `usb-bus` and the
  connection it actually held reached nothing. One line in a boot log named the kind and the subset,
  which is why the diagnostic carries both.

  Proved by: five host tests on the scope decision in `service_logic::catalogue_scope`; three on the
  manifest rules; one in-guest test that a connection minted for one kind is refused every other,
  that the allowed kind reaches the binding lookup instead, and that a stale generation is refused
  on an allowed kind too; and a 91-test x86_64 run over every rescoped consumer with zero refusals
  in the log.

  **CORRECTED 2026-09-23: TWO PARTS OF THIS ITEM WERE NOT THERE WHEN IT WAS TICKED.** The combined
  manifest demand was never checked against the table, and nothing tested the refusal at the cap.
  Both exist now: `system-manifest` adds up every role minting from the catalogue's roots - two slots
  each, since a restart mints the replacement before the old channel is seen to close - with
  DeviceManager's own, against the same 32, with a test at the bound and one past it; and a
  development-build self-test fills the real table and sees the next client refused and a returned
  slot admitted. The same pass found `provider_kind_from_wire` with no arm for `bluetooth-hci`, so
  that kind's subscription frames would have said `block`; it has one now.
- [x] BluetoothService subscribes to that kind-scoped catalogue endpoint and connects by exact
  publication identity. Snapshot plus live withdrawal follows the existing catalogue convention.
  The bootstrap/manager authorizes this service as the HCI consumer; a registry consumer count is
  only a capacity check. Ordinary clients receive neither catalogue-connect authority nor the
  provider endpoint. Account for all new services when sizing the bounded catalogue client and
  subscriber tables, which currently admit only eight.
- [x] The provider carries commands service-to-controller, events controller-to-service and ACL
  data both ways. Reserve a negotiated ISO packet kind for the separately owned transport, disabled
  in this service. Advertise supported kinds and packet/queue maxima before traffic. Hard packet
  ceilings including HCI headers are 258 bytes for commands, 257 for events, 1028 for ACL and
  4100 for ISO; honor smaller advertised/controller limits. Validate kind, direction and declared
  length before enqueueing. At most one HCI command is outstanding; obey returned command/ACL
  credits, bound incomplete ACL/L2CAP state, and never treat transport send as command completion.
  **CORRECTED 2026-09-24:** a command is checked against the controller's advertised maximum before it is
  queued, not only refused later by the transport.
- [x] Provider control supports initialization/reset and reports reset, fault and removal. A reset
  advances the service's controller-session epoch and invalidates links, scans and profile handles;
  withdrawal invalidates the publication itself. Close outstanding requests with typed outcomes,
  discard late packets from old epochs, clear partial reassembly and release held buttons on loss.
  Reconnect to a replacement only through a fresh catalogue publication and reinitialization.
  **CORRECTED 2026-09-24:** a session's scan now ends with the session - after a reset, a fault or a
  power-off its handle answers `not-found` - where a reset had left the old results readable.
- [x] Define `liber:bluetooth@1` read, operator and profile connection scopes. Read clients can
  enumerate controller identity/features/address/power and perform a scan with a caller deadline
  capped at ten seconds, at most 64 deduplicated results and explicit cancellation/completion.
  Read authority cannot power the controller, pair, forget a bond or activate an input profile.
  Operator requests are typed power-on/off, pair/cancel, forget and enable/disable a named peer;
  expose pairing progress and its security level, never raw HCI or keys. Pairing is capped at
  60 seconds and only one attempt is live per controller.
  **THE THREE SCOPES ARE DEFINED (2026-09-22) AND THE ENFORCEMENT IS NOT YET WRITTEN**, which is why
  this row stays open. `src/idl/bluetooth.lsidl` is a package of its own - nineteen now - carrying
  `bluetooth` (read), `bluetooth-operator` and `bluetooth-profile`, plus the private
  `bluetooth-bond-store`. THREE INTERFACES AND NOT THREE METHODS ON ONE, because what separates them
  is who may hold them: a component that may list the radios must not be able to power one, a
  component that may pair must not be able to read a key, and the input service must be able to do
  neither.

  THE HCI TRANSPORT IS IN `device` AND NOT HERE. A controller publishes a `bluetooth-hci` provider -
  kind 11, allocated in the closed vocabulary and agreeing with the driver wire - and that is a
  DRIVER contract. Putting it beside the client contracts would make every application that wants a
  pointer depend on the device wire, which is the division `display` and `display-device` already
  have for the same reason.

  WHAT THE PROFILE CHANNEL CARRIES IS A DECODED POINTER AND NOT A HID REPORT: movement, wheel and
  three button bits. The consumer needs no report parser and no knowledge of boot protocol, which is
  what keeps InputService from becoming a second HID implementation.
  **ENFORCED, AND RUN (2026-09-24).** Each interface is served on its own connections, the scan deadline
  is capped at ten seconds and its results at 64, and a pairing at sixty seconds with one per controller;
  `btread`, granted the read authority alone, lists and scans and was handed no operator connection.

- [ ] ServiceManager grants the operator endpoint only to the explicit trusted operator component
  through PermissionManager's manifest grant path, following the existing device-policy pattern;
  no default operator grant. This is an administrative authorization, not a claim that Just Works
  authenticates the physical mouse. The operator selects a current scan identity. Power requests
  enforce the configured platform allow/deny setting and report refusal without inventing radio
  policy. The InputService receives only `open-mouse(peer)` authority over enabled peers and a
  typed bounded report channel. Closing it or disabling the peer removes that input source.
  **CORRECTED 2026-09-24, STILL OPEN:** `pair` accepts only an address the controller's current scan
  reported (`not-found` otherwise); power-off sends `HCI_Reset` on its own after forgetting the session,
  where a disconnect and a scan-disable queued behind an in-flight command were dropped with the session and
  left the radio connected and scanning; and a controller that refused an initialisation command is left
  ready and off, so a power-on runs initialisation again rather than answering for nothing. What keeps the
  item open is unchanged: no shipping component holds the operator grant, and the allow/deny departure
  stated below is the owner's to accept.
- [ ] Add the InputService bootstrap client and a bounded additional source slot through which it
  opens the enabled mouse channel, reconnects after service restart and forwards normalized input
  through its existing pointer/console path. Do not publish a pretend driver provider from the
  Bluetooth userspace service. Update every bootstrap caller, including kernel harness callers.

## P02M0180 - Bonds and containment

- [x] Own a small `bluetooth_bond_store` service in this milestone. Its private capability supports
  lookup, atomic store/replace and delete by local controller identity plus peer address/type and
  key/security version. Store the LTK and only the metadata this restricted profile requires;
  reject mismatched controller/peer identities and unsupported record versions. Lookup may return
  key material only to BluetoothService so it can issue encryption commands. "Asked rather than
  read" means a typed confined operation, not a claim that HCI encryption works without a key.
- [x] ServiceManager/StorageService mint a writable directory-scoped storage connection for the
  backend's manifest-owned `vol://system/state/bluetooth-bonds` directory and grant the private
  bond endpoint solely to BluetoothService. Ordinary clients receive neither capability. Use the
  existing `volume.open-writer` replacement session and acknowledged `writer.commit` on
  disk-backed LiberFS; `writer.flush` confirms staged bytes only, and remove-then-rename is not
  an atomic replacement. Cap records at 64 and the complete store at 64 kB. The backend survives
  service restart/reboot through this directory; a corrupt record is
  unavailable, never an implicit new peer. Do not claim protection from a trusted storage
  administrator or add a general-purpose key manager/encrypted-volume project.
- [x] Pairing is reported as bonded only after durable commit. If storage is absent/full or a
  write fails, terminate the bonding attempt and erase temporary keys; do not silently downgrade
  to a transient bond. Reconnect retrieves the matching record and proves encryption before
  enabling input. Forget durably deletes it before reporting success and terminates the live link.
  Clear transient key buffers on completion/failure and exclude key bytes from logs and events.
  **CORRECTED 2026-09-24:** the keys are now cleared, not only let go - setting an `Option` to `None` had left
  the bytes in place. The SMP initiator overwrites its Diffie-Hellman key, MacKey and LTK where they lie, on
  completion, on failure and when it is dropped; BluetoothService zeroes (volatile writes) the bond record's
  key after a store or a lookup, the LTK in the step list, and every copy of the `LE Enable Encryption`
  parameters, queued, sent or dropped; and `open-mouse` and encryption read `enabled` from the store's keyless
  listing instead of pulling the key.
  **CORRECTED 2026-09-25:** the copies the IPC path made are cleared too. HCI commands go out from a frame
  BluetoothService encodes and zeroes, not through the generated client's own vector; every packet from the
  controller - the Diffie-Hellman key arrives in an event - is zeroed in the receive buffer and in its decoded
  copy once handled; and the bond store's `store` request and `lookup` reply are encoded and read in buffers the
  service owns and zeroes.
- [x] Extend the existing ProcessService bounded-launch mechanism with a finite resource-limits
  record and a prepared/release form usable by ServiceManager. Set every limit before releasing
  the process; reject invalid limits and fail startup if Domain creation or any limit assignment
  fails. No fallback to ordinary `launch(..., domain=0)`. ServiceManager selects the documented
  limits for these two manifest services; existing unrelated launches retain their behavior.
  Keep the Domain in ProcessService's existing accounting/cleanup record, and tear it down on
  failed launch or service stop before a replacement starts.
- [x] Initial BluetoothService limits: 64 MB memory, 256 handles, 4 threads, 2 MB IPC queues,
  2 MB stacks and zero DMA. Bond backend: 16 MB memory, 64 handles, 2 threads, 256 kB IPC queues,
  1 MB stacks and zero DMA. Measure image/runtime baseline under these exact limits and tune
  finite values with recorded headroom if necessary, never replace them with unlimited values.
  No launcher or device privilege is granted to either service. Use existing resource counters;
  this does not add a CPU scheduling policy.
- [x] Bound service tables to two controllers, one link each, 16 client connections, four
  L2CAP channels per link, 16 queued packets per link and 256 kB aggregate packet storage.
  L2CAP SDUs are at most 512 bytes with one incomplete SDU per channel and a one-second assembly
  deadline. Default ATT MTU 23 is sufficient for the mouse subset. Event-loop work is bounded
  per turn and waits use deadlines; refuse overload explicitly, with no allocation retry spin.
  On process death all ephemeral clients close. Restart rebuilds controllers from the catalogue,
  restores bonds through the backend and requires fresh profile channels; it never revives old
  client handles or button state.
- [x] Add the service binaries, source/dependency paths, staging destinations, state declarations
  and roles to `src/user/services/manifest.toml`; add generated protocol/client exports, operator
  and read grant vocabulary in `src/idl/security.lsidl`, PermissionManager delivery and service
  resolution/restart handling. Update IDL generation inputs, manifest-derived bootstrap code and
  relevant source-hygiene allowances in the same implementation. No new root authority is ambient.

**WHERE IT STOOD ON 2026-09-23, BEFORE THE GATE RAN: IMPLEMENTED AND NOT YET RUN.** Every item above has code in the
tree - the host stack, the bond store, the bounded launch, the input slot, the in-guest fixture with
its own independently written cryptography, the two probes and the two-boot gate
`check-bluetooth-service.sh` - and none of it beyond the catalogue stage is ticked, because the gate
has not been run: it needs a development image and two boots of one disk, and that run belongs to the
end of the job. Two places where the implementation departs from this plan's wording, each for a
measured reason, are stated here rather than hidden:

- INPUTSERVICE REACHES THE PROFILE BY NAME THROUGH THE BROKER, not through a bootstrap role. A role
  from a service is a dependency on it in this manifest, and a stop takes the whole reverse-dependency
  closure - so `stop bluetooth_service`, which this plan's own gate does, would have stopped
  InputService and the display above it. The broker is also what "reconnects after service restart"
  needs. The resolve is asynchronous, so a broker that answers late - or a kernel harness with no
  broker - leaves the slot empty rather than the pointer path parked.
- THE "CONFIGURED PLATFORM ALLOW/DENY SETTING" FOR THE RADIO DOES NOT EXIST in this tree, and inventing
  one would be the invented radio policy this plan forbids. The platform's existing allow/deny for a
  device is DeviceManager's persistent device policy: a disabled controller has no provider and is not
  in the list, so `power` naming it is `not-found`.

Done when the supported mouse path scans, pairs, durably bonds and supplies useful input through
capability-scoped channels; the separate Domains and aggregate bounds are enforced at boot; denial,
loss and restart behavior pass; and production host tests plus the registered guest gate land with
the implementation. The USB Bluetooth HCI transport is then unblocked, not already implemented.
