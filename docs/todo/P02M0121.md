# P02M0121 - A receive that takes a message must be able to deliver it

`sys_channel_recv_caps` was rewritten in P02M0115 around one rule: **decide under one lock, and take the
message only if it fits**. The rule is right and the rewrite is right. What the rewrite did not do is
apply it to the other receive, and what it did not notice is that the reservation it introduced
reserves the wrong thing.

The ordinary `sys_channel_recv` is not a legacy path. All four of the runtime's receive wrappers
issue it - `recv_blocking`, `recv_into`, `recv_vec_deadline` and `try_recv` - so every service loop
in the system reaches the kernel through it; `SYS_CHANNEL_RECV_CAPS` is the exception, used where a
receiver expects more than one capability. The receive that got the transactional treatment is the
rare one, and the one everything else uses still does this:

```rust
let message = channel.recv()?;              // dequeued. gone from the queue.
...
Some(cap) => thread.handles().lock().insert(cap).raw()
```

## What is wanted

- [x] **`sys_channel_recv` must be transactional and quota-aware, like its sibling.**

  `HandleTable::insert` charges through `Domain::charge_handle`, which increments and returns - it
  is the unconditional path, and its comment says so plainly: *"used by paths that must not fail,
  such as installing a transferred capability"*. That comment describes the constraint honestly and
  then draws the wrong conclusion from it. The install cannot fail **because the message is already
  destroyed if it does**, so the quota was dropped rather than the ordering fixed.

  The result is a direct hole in resource-domain isolation. A Domain with a handle limit of 64 that
  is at 64 receives a transferred capability and holds 65; receive again and it holds 66. Nothing
  refuses, and the limit that bounds every other way of acquiring a handle - `try_insert`,
  `try_insert_or_return`, `duplicate` (fixed in P02M0115 for exactly this reason) - is bypassed by
  asking a peer to send one.

  `try_insert` alone is not the fix: a refusal at that point destroys a message that has already
  left the queue and cannot be retried. It needs the same three steps `recv_caps` takes -
  **reserve, then dequeue what fits, then install against the reservation** - which for a single
  capability means `reserve(1)`, `recv_if_fits(bytes_cap, 1)`, `insert_reserved`, and
  `release_reservation(1)` when the message carried none.

  Note while doing it that `recv_if_fits` also bounds the BYTE length, which plain `recv` does not:
  today an over-long message is truncated to `bytes_cap` and the excess silently lost, with the
  return value reporting the truncated length. That is a second, quieter difference between the two
  receives and it should be resolved deliberately - either both truncate or both refuse - rather
  than fall out of whichever one was touched last.

- [x] **`HandleTable::reserve` must reserve the memory as well as the quota.**

  It charges `Domain::try_charge_handle` `count` times and nothing else. `insert_reserved` then calls
  `place`, which is:

  ```rust
  self.slots.push(Slot { cap: Some(cap), generation: 1 });
  ```

  an infallible `Vec::push`. So the guarantee the comment states - *"a later `insert` cannot be
  refused for space"* - is true only of the Domain's accounting. It says nothing about the kernel
  heap, and the caller's whole reason for taking the reservation is that it is about to destroy a
  message it cannot get back. Quota granted, message dequeued, `slots` needs to grow, the heap has
  nothing: that is an allocation abort in the kernel, on a path reachable from ring 3 by filling
  memory and receiving.

  `reserve(n)` must compute `n.saturating_sub(self.free.len())` and `try_reserve` that many slots
  before charging, releasing the quota if the reservation fails. After that, `insert_reserved` is
  infallible for the reason the comment already claims.

- [x] **Reserve what the message needs, not `MAX_MESSAGE_CAPS`.**

  `sys_channel_recv_caps` reserves 4 up front and releases the surplus after. The comment argues
  this *"costs nothing to a table with room and refuses early on a table without"*, and the first
  half is true. The second half is a false refusal: a Domain with one free handle slot receiving a
  message carrying one capability gets `ERR_RESOURCE_EXHAUSTED` for a message that fits.

  It fails in the safe direction, which is why this is last of the three. But the reason the
  over-reservation is there is the race the rewrite was fixing - the shape wanted is one where the
  head can be inspected and then taken **by identity**: a `peek` that returns
  `(message_id, caps, bytes)`, a reservation for the actual count, and a `recv_if_id(message_id)`
  that takes that message or nothing. A monotonic per-channel message counter is enough for the id,
  and it removes the last place where a receiver decides against one message and acts on another.

- [x] **Tests for all three, each watched to fail.**

  The quota bypass is deterministic: a Domain with a handle limit of four, a peer that sends a
  capability, and the receive that must refuse rather than reach five. The reservation is
  deterministic through the same shape used for the other allocation-failure tests. The false
  refusal is deterministic: limit N, N-1 handles held, a one-capability message, and it must arrive.

## Where this came from

The sixth outside audit round on this tree, 2026-08-09, verified claim by claim against the code.
The round's own summary of the P02M0115 receive work is that the main race is genuinely fixed and the
capability SEND path is now correct end to end; these three are the layer underneath it.

Worth carrying: the finding that produced the two most serious items here is the same finding twice
- **a fix applied to one of two paths that share an assumption**. P02M0116 recorded exactly that lesson
about the disk probe ("a change that improves one path has to be followed into every path that
shares its assumptions"), and the very next round found it again in the syscall layer. The two
receives are one hundred lines apart in the same file.


## What was built

**Both receives go through one function.** `receive_transactionally` in `syscall/mod.rs` does the
three steps in order - look at the head, reserve exactly what THAT message needs, take it by
identity - and `sys_channel_recv` and `sys_channel_recv_caps` are now the two callers of it. The
plain receive's unbounded `insert` is gone; it installs against a reservation like its sibling.

**A message has an identity.** `Message` carries a `u64` from a global monotonic counter assigned at
construction, and `Channel::recv_identified(id, ..)` takes the head only if it is still that
message, answering `RecvRefusal::Superseded` otherwise. This is what makes an EXACT reservation
possible: without it a reservation taken after a peek could be spent on a different message, which
is why the first version booked `MAX_MESSAGE_CAPS` up front.

That over-reservation turned out to matter more than it looked. For the multi-cap receive it was a
false refusal - a Domain with one free slot refused a message carrying one capability. For the
PLAIN receive it would have been worse: reserving one handle for every message would have stopped a
Domain at its limit from receiving plain bytes, so "reserve the maximum" was not a shortcut this
path could have taken at all.

`recv_if_fits` is gone rather than kept beside the new one. It closed the race that mattered and
left one open: it refused a message that did not fit and took whatever was at the head otherwise, so
a caller could still be handed a message it had not inspected as long as that one also fitted.
Harmless for the byte length and not for the capability count.

**The reservation books memory.** `reserve(n)` computes `n - free.len()` and `try_reserve`s that
many slots BEFORE charging the quota, so a refusal costs nothing to unwind and `insert_reserved` is
infallible for the reason its comment always claimed.

### The byte-length asymmetry, decided

P02M0121 asked for this to be resolved either way. It is resolved as: **the plain receive keeps
truncating, the multi-cap receive keeps refusing**, and the reason is the callers rather than
tidiness.

Every caller of the plain receive peeks the length first and sizes its buffer from the peek -
StorageService's stream loop asks the filesystem for a buffer of exactly the peeked size and treats
a short read as a short read, advancing by what arrived. Turning a shortfall into a refusal converts
a handled case into an aborted stream. The multi-cap receive's callers know the shape they expect
and can come back for a message left in the queue. The identity check removes the case that made
the difference dangerous: a receiver can no longer truncate a message it never looked at.

### Watched to fail

Reverted in one pass and re-run in the guest: the plain receive back to `recv()` plus `insert`, the
reservation back to quota-only, and the exact reservation back to `MAX_MESSAGE_CAPS`. All three
tests failed, each on its own assertion.
