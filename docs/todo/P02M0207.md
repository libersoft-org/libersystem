## THE ITEMS

- [x] 1. THE SAME SOURCE COMPILES TO THE SAME BYTES WHEREVER THE TREE IS (implemented 2026-11-05).
  - WHY `dynamic-report` failed sealed: every row of `docs/DYNAMIC_EXECUTABLES.tsv` differed between the tree it was
    written in and the sealed snapshot at `/data/yellow/.r<hash>`. Every crate of this tree is its own Cargo
    workspace and reaches its neighbours by `../` paths, and cargo hashes the ABSOLUTE path of such a dependency into
    `-C metadata` (`SourceId::stable_hash` strips only the workspace root). rustc derives the crate's identity from
    that value: the hash in every mangled symbol (every project crate's differed; `core` and `alloc`, hashed by
    sysroot-relative path, did not), and which upstream crate's copy of a shared generic a dependent links
    (`RawVec<i16>::grow_one` from `adpcm` in one tree, from `pcm` in the other), and with them the sizes. Panic
    locations carried the tree's absolute path into the shipped libraries as well. So the release, built from a
    sealed copy, could never match a report written in place - nor, for that matter, a checkout anywhere else.
  - THE FIX: `src/tools/rustc-wrapper.sh`, which `.cargo/config.toml` names as `build.rustc-wrapper`, so every cargo
    run under the repository goes through it. For a crate of this tree (cargo runs rustc in the package's
    directory) it replaces `-C metadata` with a hash of the command line with the tree's path taken out and of the
    identities of the crates it links, which it records beside each library (`.liber-crate-id/`). A crate from
    outside the tree keeps cargo's value, which does not depend on where the tree is. A dependency compiled before
    the wrapper has no record, and its dependents then keep cargo's value - the old behaviour, not a wrong one - so
    the build's cache keys name the wrapper: `build-shared.sh` empties the image graph's and the providers' cargo
    directories when its digest changes. Every compile also maps the tree's path to `.` in what it embeds.
  - WHAT THE HASH COVERS IS WHAT CARGO'S DOES, less the path: the arguments cargo writes itself, up to its
    dependencies (`-L dependency=`, `--extern`). What cargo appends after them - RUSTFLAGS, `cargo rustc -- ...`,
    a build script's `-L native=` and `--cfg` - is left out, as cargo leaves it out of `-C metadata` (cargo 0.94,
    `compute_metadata`). The first version hashed every argument, and the audit link found it the same night: the
    quarantine consumers are compiled with `-C force-unwind-tables=no` and call the image's runtime by its
    identity, so `vkprobe` named `rt` symbols no staged library exports. The audit link's own cargo directory
    (`.build/cargo/quarantine/<triple>`) is emptied on a new wrapper digest too, as `build-shared.sh`'s are, for the
    reason those are: an unchanged crate compiled there before kept its old identity.
  - ORACLE: the `reproducible-build` gate (`src/tools/check-reproducible-build.sh`, ten cases, a few seconds): a
    fixture tree built at two paths of different lengths gives identical binaries in release and in debug (where
    generics are shared between crates), names its sources relative to the tree, and records a path-independent
    identity for each library; built without the wrapper the two binaries differ, which proves the fixture reaches
    the defect; an unchanged tree compiles nothing again, a changed dependency recompiles it and its dependents, a
    dependency from before the wrapper keeps cargo's identity and the build runs, a library's identity is the same
    built with and without extra RUSTFLAGS (with a build script appending its own search path and `--cfg`), and
    `rustc -vV` passes through. Watched failing: with a wrapper that only runs the compiler, five of the first nine
    fail; with the first version, which hashed every argument, the RUSTFLAGS case fails.
  - ON THE REAL TREE: `src` copied to two paths of different lengths, the `tools` crate's whole image graph built
    for x86_64 with the image's flags and `build-std`: the object code of all 172 rlibs identical (171 by name, the
    two `qoi` rlibs as a pair). What still differs is cargo's `-C extra-filename` in the archive member names and in
    `lib.rmeta`, neither of which the image links.
  - REGISTERED in `check.sh`, the verify model's catalog (`harness.tools`) and resources (`host`), and
    `release-required.toml` by hand until the end-of-job port builds regenerate it.
  - LEFT TO ITEM 6: the tracked dynamic reports regenerated from in-place builds of all three targets
    (`./check.sh --refresh dynamic-report`), and `dynamic-report` passing in the sealed run.

- [x] 2. A BOOT BOUND TO REFUSE ITS DMA MODE DOES NOT READ A KERNEL FIRST (implemented 2026-11-05).
  - WHY: the no-device-tree profiles' absent-record row requires the loader to halt before `loader: kernel loaded`.
    The loader judged the DMA mode once, at the end of `efi_main`, after the kernel was read, verified and announced -
    so the row has failed since the commit that added it, on both ports. x86_64 has no such row (its absent-carrier
    rows forbid only the kernel starting).
  - THE FIX: a refusal is final the moment it is found unless it is `NothingSelected`: a contradiction is kept,
    `present` never changes once set, and the carrier is a fixed input. `bootproto::dma_mode::Latch::settled_refusal`
    answers that. The loader now reads this entry path's DMA-mode inputs right after the boot medium's pairing
    record is verified, and `dma_mode::refuse_if_settled` halts there - same sentence as before - for an independent
    input or a settled refusal; the final `resolve` judges the whole set from the same reading. A set that may still
    resolve stores nothing and prints nothing new. `guest-verdict.py`'s comments say which refusals now come before
    the kernel; its predicates are unchanged (the mixed-set rows refuse after it, as before).
  - ORACLE: `a_refusal_settled_on_part_of_the_set_is_never_lifted_by_the_rest` (bootproto): every set of up to four
    manifests, cut after every prefix, under all four kinds of carrier - a prefix that settles a refusal belongs to a
    set that refuses. The loader compiles on all three targets. The call order is proved only by the two gates (the
    loader is a UEFI binary with no tests), which fail today and are item 6's.

- [x] 3. THE PORTS' SLEEP CLOCK, CHECKED ON THE PAIR THAT SPANS THE SLEEP (implemented 2026-11-05).
  - WHY: the check took the last counter line before `sleep: entered` and the first after `sleep: resumed`. The
    counter's lines reach the serial line through ConsoleService and the console driver, which the sleep transaction
    suspends, while the kernel's lines go straight to the port; under emulation the counter ran seconds behind, so
    counts sampled before the freeze arrived after `sleep: resumed`, and the check compared two samples from before
    the sleep and read a 0 ms step. The kernel's clocks were right throughout: in the kept logs the pair that spans
    the sleep shows boot-time minus monotonic within 1 ms of the reported sleep. (P02M0197's 2026-10-21 note read the
    same evidence as the counter sampling between the freeze and the park; the samples were taken before the freeze
    and delivered late.) A second defect showed on riscv64: a kernel line written into the middle of a counter line
    ("boot-ms 55575" + "DeviceManager: resumed console-uart ..." + "4") was read as a clock eight minutes behind.
  - THE FIX, in `check-tickless-idle.py` and used by `check-system-suspend.py`: the counts in their own order, and the
    one place where boot-time minus monotonic moved - exactly one, every other step within a clock read's 100 ms;
    no sample that counts the sleep on the wire before `sleep: resumed`; and the pair at least as far apart on the
    monotonic clock as the transaction's flush-to-thaw window, so it spans the freeze. A counter line is read only
    whole: one another writer cut is rejoined with the rest of its own text, and a cut whose end never arrives fails
    the gate. The size check (within 100 ms of the reported sleep), the monotonic and entry/resume tick checks and the
    silence check are unchanged.
  - ORACLE: both gates' self-tests - six positive cases (one the ports' late delivery, which the old check refused),
    ten refused false outcomes (three new: a step of the wrong size, the clocks parting twice, a sample counting the
    sleep before the resume; and a pair that does not span the freeze), the riscv64 cut line rejoined and two cuts
    that cannot be rejoined refused. All six kept port logs (tickless aarch64 and riscv64 of 2026-11-02 and 2026-11-04, the
    `unsupported` boots of `system-suspend-riscv64` of the same days) replayed through the old and the new check: the
    old one refuses all six with "0 ms", the new one accepts all six at 5032 to 5107 ms against reports 1 ms lower,
    each pair spanning its freeze. The guest runs are item 6's.

- [x] 4. A TEARDOWN'S DEADLINE BOUNDS THE CONTROLLER, NOT THE LOG (implemented 2026-11-05).
  - WHY: `kernel.iommu.a_translated_address_stops_translating_when_its_claim_is_forced_to_end`, in the port IOMMU
    profiles' `--tags dma` suite, ends with the replacement binding's detach, and it was quarantined there on every
    run. `detach_for` armed its 200 ms deadline before the pre-revoke fault drain; this is the one detach in the suite
    whose endpoint has a fault queued, so the drain printed two lines, and on the ports' test machines - emulated,
    with the kernel console drawn into a `ramfb` framebuffer since 2026-09-20 - two lines outlasted the whole 200 ms.
    The DETACH then went out with its deadline behind it, the device answered, and the queue checked the clock before
    the used ring and returned `None`; and that request's failure latch closed the controller's request queue for the
    rest of the boot. x86_64 runs the same test under KVM, where two lines take milliseconds.
  - THE FIX: the deadline is armed again just before each conversation with the controller - the revoke and the
    domain's destruction - so the drains, bounded by their own buffer, no longer spend it; `VirtQueue::request`
    returns without sending anything when the deadline has already passed (the same refusal, with the queue still
    usable), and reads the used ring before the clock, so an answer that is there is taken.
  - ORACLE: the three port gates, which fail on every run, are item 6's. The kernel and its test kernel compile on
    all three targets. A kernel test of the latch on x86_64 would have to quarantine one of the suite's two `edu`
    fixtures for the rest of the boot under every later test, so it is not added.
