# P02M0160 - One artifact has two required shapes and one name, so the last build wins

Status: PLANNED (2026-08-26). BUILD CORRECTNESS. NOT A NEW FEATURE.

## Goal

Make the system volume's two shapes two artifacts, so that no order of commands can leave a consumer
reading the wrong one - and so that a verification run stops depending on what was built last.

The claim this milestone may make is small and worth stating exactly: after it, `./build.sh`,
`./image.sh` and `./test.sh` may be run in any order, any number of times, and every consumer reads
the shape it asked for. It does not change what either shape contains, and it is not a rework of the
build system.

## What is there now

The system volume is built in two shapes by the same step:

| | |
| --- | --- |
| `./build.sh` | `step_volume "$arch" 0` - a volume with NO kernel on it. What the test medium needs |
| `./image.sh` | `./build.sh --arch x86_64 --kernel-on-volume` - a volume WITH one. What a shipping medium needs |

Both write the same three paths, because `mkpackages` names its output from the destination stem and
the architecture and nothing else:

```
.build/boot/system-volume-<arch>.img
.build/boot/system-volume-<arch>.uuid
.build/boot/volume-<arch>.pkg
```

So the shape on disk is whichever command ran last, and every consumer takes it on trust. That is not
a race or a partial write: both builds are correct and complete, and each produces the artifact the
OTHER consumer must not read.

- **THE TEST MEDIUM READS THE SHIPPING SHAPE AND BOOTS THE WRONG KERNEL.** The loader prefers the
  system volume's kernel wherever the volume carries one, so a suite run after an `./image.sh` boots
  the SHIPPING kernel under the test harness: userspace comes up, the guest sits at a shell, no test
  ever runs, nothing writes the debug-exit port, and QEMU is killed - which is indistinguishable from
  a triple fault to everything downstream.
- **THE SHIPPING MEDIUM READS A PAIRING FOR A VOLUME THAT IS NOT THERE.** The uuid is derived from the
  volume's contents, so the two shapes have different ones. `./image.sh` bakes the uuid it saw into
  the ISO; a `./build.sh --part volume` afterwards replaces the volume and its uuid and leaves the ISO
  naming the old one. The loader then refuses the volume it can see, as unpaired - correctly, and for
  a reason nothing on the medium can explain.

**THE COST, MEASURED.** Five separate investigations in one round of work started at a symptom and
ended at the order of two commands: a `GUEST RESET` that was not a crash, twice; an IOMMU gate failure
that was not an IOMMU defect; a `signed-boot` line reading "a damaged signed manifest on the selected
volume did NOT stop the boot", which is a sentence about a trust chain and was a sentence about a
build; and one boot report read closely for a defect that was not in it. Each cost a diagnosis cycle
of its own because nothing about the symptom points at the cause.

**AND THE SAME DEFECT HAS ALREADY BEEN FIXED ONCE, IN THIS FILE, BY NAMING THE FILE.** The comment
directly above `step_volume` in `build.sh` says so:

> It used to read `.build/boot/kernel`, a slot every image builder writes and nobody owns, so the
> volume took whatever the previous recipe had left there - and a disk image built after a test run
> carried the TEST kernel and booted into the suite. Naming the file removes the slot from the path.

The kernel got its own name. The volume, whose own build that comment is attached to, did not.

## Work

- [x] **M1 - each shape gets its own name.** The volume with a kernel and the volume without one are
  two artifacts, named so, along with the uuid sidecar and the package that carry the same split. An
  `.img` that could be either is the thing this milestone removes.

- [x] **M2 - every consumer names the shape it needs.** `mkimage.sh iso` reads the shipping one;
  `mkimage.sh testiso` reads the test one; `check-signed-boot.sh` reads the shipping one. None of them
  reads "the system volume" any more, because there is no such file.

- [x] **M3 - a missing shape is a refusal that names the command that builds it.** Today a consumer
  finds a file and cannot tell which shape it is; afterwards it may find no file at all, and that must
  say `./image.sh` or `./build.sh --part volume` rather than "no such file". The failure moves from
  "silently wrong" to "loudly absent", which is the whole of the improvement.

- [x] **M4 - the pairing assertion runs where the pairing is USED, not only where it is written.**
  `mkimage.sh` already refuses to stage a pairing that does not match the volume beside it, and that
  check passed on every medium this round while the tree was still broken - because the mismatch was
  created AFTER the ISO was assembled. A medium carries its pairing; whatever reads that medium can
  check it against the volume it is about to attach, and `check-signed-boot.sh` now does. Make that
  the shared check rather than one gate's.

- [x] **M5 - the diagnosis added for this becomes unreachable, and a test says so.** `test-kernel.sh`
  now recognises "the loader took its kernel off the system volume, not the medium this suite staged"
  and prints how to undo it. That diagnosis is a good thing to keep - a tree can be in a bad state for
  other reasons - but after M1 it must not be reachable by building in an ordinary order. A test that
  builds in every order and requires the suite to run proves that.

- [x] **M6 - the verification sequences stop encoding an order.** Two scripts written during this
  round's verification carry comments explaining which of `./image.sh` and `./build.sh --part volume`
  has to run last for which gate. Both comments are descriptions of this defect and both go.

## Dependency order

M1 first; M2 and M3 are the same change seen from the consumers' side. M4 is independent. M5 and M6
are how the milestone is closed rather than steps toward it.

## Definition of done

- The volume with a kernel and the volume without one have different names, and no command produces a
  file that could be either.
- `./build.sh`, `./image.sh` and `./test.sh` can be run in any order and any number of times, and the
  suite runs, the ISO boots, and every gate makes its own claim. A test builds in several orders and
  requires exactly that.
- A consumer that cannot find the shape it needs names the command that builds it.
- A medium's pairing is checked against the volume being attached wherever one is, by shared code
  rather than by one gate.
- The wrong-kernel diagnosis in `test-kernel.sh` is still there, and is no longer reachable by
  building in an ordinary order.
- No comment anywhere explains which of two commands has to run last.

## What this milestone refuses, and why

- **A lock, or making the two commands mutually exclusive.** They do not conflict in time - each one
  finishes cleanly - so serialising them changes nothing. Two things that must not be confused need
  two names, not a queue.
- **Rebuilding everything before every check.** The caches exist because a change to one tool must not
  cost a whole userspace, and the answer to "the wrong artifact was read" is never "read all of them
  again".
- **Changing what either shape contains.** A shipping volume carries a kernel and a test volume does
  not; both are right, and this milestone is about telling them apart rather than about either.
- **A build-system rework.** The defect is one artifact with two shapes and one name, the fix is the
  one this file already applied to the kernel slot, and anything larger is a different milestone that
  should be argued for on its own.

## Results (2026-08-26)

The two shapes are `system-volume-<arch>.img` and `system-volume-bootable-<arch>.img`, with their
uuid sidecars beside them. `mkimage.sh` and `check-signed-boot.sh` name the bootable one; the test
harness and `run.sh` name the other; a consumer that finds neither says which command builds it.

`check-build-order.sh` builds both shapes in both orders and requires each to survive the other, and
refuses a tree where the two shapes have equal contents - which would make the gate pass on a tree
where the defect was still there. The pairing question moved into `src/tools/volume-pairing.sh`, so
the check that runs where a pairing is WRITTEN and the check that runs where a medium is READ are the
same code; that is what M4 asked for, and it is why `check-signed-boot.sh` no longer carries its own
copy of the superblock offset.

Neither remaining reference to a command order is a rule any more. `check-signed-boot.sh` asks
whether a medium and a volume were built from the same tree, which is a consistency question a
half-rebuilt tree can still fail; `check-qemu-virtio-iommu-x86_64.sh` asks whether its ISO predates
the kernel it is supposed to carry. Both name a rebuild rather than a sequence.

The wrong-kernel diagnosis in `test-kernel.sh` is still there and can no longer be reached by
building in an ordinary order.

A gate that is not in `verify-model`'s catalog is a gate nothing would ever select, so `build-order`
is in it - and adding it is what made `verify-model` say so, which is the catalog earning its place
rather than a formality.
