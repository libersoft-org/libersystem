# P02M0160 - One artifact has two required shapes and one name, so the last build wins

Status: COMPLETE (2026-08-26). BUILD CORRECTNESS. NOT A NEW FEATURE. M1-M6 named the artifacts apart;
M7 did the same for the receipts, which is where the defect had moved.

## Goal

Make the system volume's two shapes two artifacts, so that no order of commands can leave a consumer
reading the wrong one - and so that a verification run stops depending on what was built last.

The claim this milestone may make is small and worth stating exactly: after it, `./build.sh`,
`./image.sh` and `./test.sh` may be run in any order, any number of times, and every consumer reads
the shape it asked for. It does not change what either shape contains, and it is not a rework of the
build system.

## What is there now

**THIS SECTION IS THE TREE AS M1-M6 FOUND IT, AND M1-M6 ARE DONE.** It is kept because it is what the
work was argued from and because M7 is the same defect in the one file the split did not reach; what
the tree looks like now is under Results. Read the two together or the first will be mistaken for the
second.

The system volume was built in two shapes by the same step:

| | |
| --- | --- |
| `./build.sh` | `step_volume "$arch" 0` - a volume with NO kernel on it. What the test medium needs |
| `./image.sh` | `./build.sh --arch x86_64 --kernel-on-volume` - a volume WITH one. What a shipping medium needs |

Both write the same three paths, because `mkpackages` names its output from the destination stem and
the architecture and nothing else:

```
.build/boot/system-volume-<arch>.img
.build/boot/system-volume-<arch>.uuid
.build/boot/volume-<arch>.pkg
```

So the shape on disk is whichever command ran last, and every consumer takes it on trust. That is not
a race or a partial write: both builds are correct and complete, and each produces the artifact the
OTHER consumer must not read.

- **THE TEST MEDIUM READS THE SHIPPING SHAPE AND BOOTS THE WRONG KERNEL.** The loader prefers the
  system volume's kernel wherever the volume carries one, so a suite run after an `./image.sh` boots
  the SHIPPING kernel under the test harness: userspace comes up, the guest sits at a shell, no test
  ever runs, nothing writes the debug-exit port, and QEMU is killed - which is indistinguishable from
  a triple fault to everything downstream.
- **THE SHIPPING MEDIUM READS A PAIRING FOR A VOLUME THAT IS NOT THERE.** The uuid is derived from the
  volume's contents, so the two shapes have different ones. `./image.sh` bakes the uuid it saw into
  the ISO; a `./build.sh --part volume` afterwards replaces the volume and its uuid and leaves the ISO
  naming the old one. The loader then refuses the volume it can see, as unpaired - correctly, and for
  a reason nothing on the medium can explain.

**THE COST, MEASURED.** Five separate investigations in one round of work started at a symptom and
ended at the order of two commands: a `GUEST RESET` that was not a crash, twice; an IOMMU gate failure
that was not an IOMMU defect; a `signed-boot` line reading "a damaged signed manifest on the selected
volume did NOT stop the boot", which is a sentence about a trust chain and was a sentence about a
build; and one boot report read closely for a defect that was not in it. Each cost a diagnosis cycle
of its own because nothing about the symptom points at the cause.

**AND THE SAME DEFECT HAS ALREADY BEEN FIXED ONCE, IN THIS FILE, BY NAMING THE FILE.** The comment
directly above `step_volume` in `build.sh` says so:

> It used to read `.build/boot/kernel`, a slot every image builder writes and nobody owns, so the
> volume took whatever the previous recipe had left there - and a disk image built after a test run
> carried the TEST kernel and booted into the suite. Naming the file removes the slot from the path.

The kernel got its own name. The volume, whose own build that comment is attached to, did not.

## Work

- [x] **M1 - each shape gets its own name.** The volume with a kernel and the volume without one are
  two artifacts, named so, along with the uuid sidecar. NOT the package: `mkpackages`' system-volume
  mode produces the `.img` and the `.uuid` and nothing else, and `volume-<arch>.pkg` is assembled by
  the ordinary path and never carries a kernel - so two names for it would be two copies of one file.
  An `.img` that could be either is the thing this milestone removes.

- [x] **M2 - every consumer names the shape it needs.** `mkimage.sh iso` and `check-signed-boot.sh`
  read the bootable one; `test.sh`, `run.sh` and all three architectures in `qemu-run.sh` read the
  test one. `mkimage.sh testiso` reads neither - its payload is `volume-x86_64.pkg`, the factory
  archive, which is why the package is not split. None of them reads "the system volume" any more,
  because there is no such file.

- [x] **M3 - a missing shape is a refusal that names the command that builds it.** Today a consumer
  finds a file and cannot tell which shape it is; afterwards it may find no file at all, and that must
  say `./image.sh` or `./build.sh --part volume` rather than "no such file". The failure moves from
  "silently wrong" to "loudly absent", which is the whole of the improvement.

- [x] **M4 - the pairing assertion runs where the pairing is USED, not only where it is written.**
  `mkimage.sh` already refuses to stage a pairing that does not match the volume beside it, and that
  check passed on every medium this round while the tree was still broken - because the mismatch was
  created AFTER the ISO was assembled. A medium carries its pairing; whatever reads that medium can
  check it against the volume it is about to attach, and `check-signed-boot.sh` now does. Make that
  the shared check rather than one gate's.

- [x] **M5 - the diagnosis added for this becomes unreachable, and a test says so.** `test-kernel.sh`
  now recognises "the loader took its kernel off the system volume, not the medium this suite staged"
  and prints how to undo it. That diagnosis is a good thing to keep - a tree can be in a bad state for
  other reasons - but after M1 it must not be reachable by building in an ordinary order. The gate
  proves that the way it proves everything else: it builds in both orders and requires each shape's
  image, uuid and stamp to survive the other, which is what makes the diagnosis unreachable. It does
  not boot anything - the gates that boot already assert what they booted, and re-proving them here
  through a permutation matrix would only be slower.

- [x] **M6 - the verification sequences stop encoding an order.** Two scripts written during this
  round's verification carry comments explaining which of `./image.sh` and `./build.sh --part volume`
  has to run last for which gate. Both comments are descriptions of this defect and both go.

## Dependency order

M1 first; M2 and M3 are the same change seen from the consumers' side. M4 is independent. M5 and M6
are how the milestone is closed rather than steps toward it.

## Definition of done

- The volume with a kernel and the volume without one have different names, and no command produces a
  file that could be either.
- `./build.sh`, `./image.sh` and `./test.sh` can be run in any order and any number of times, and
  each shape - its image, its uuid AND its build stamp - is untouched by the command that builds the
  other. `check-build-order.sh` builds in both orders and requires exactly that; it does not boot
  anything, because the gates that boot already assert what they boot and a permutation matrix here
  would only re-prove them slowly.
- A consumer that cannot find the shape it needs names the command that builds it.
- A medium's pairing is checked against the volume being attached wherever one is, by shared code
  rather than by one gate.
- The wrong-kernel diagnosis in `test-kernel.sh` is still there, and is no longer reachable by
  building in an ordinary order.
- No comment anywhere explains which of two commands has to run last.

## What this milestone refuses, and why

- **A lock, or making the two commands mutually exclusive.** They do not conflict in time - each one
  finishes cleanly - so serialising them changes nothing. Two things that must not be confused need
  two names, not a queue.
- **Rebuilding everything before every check.** The caches exist because a change to one tool must not
  cost a whole userspace, and the answer to "the wrong artifact was read" is never "read all of them
  again".
- **Changing what either shape contains.** A shipping volume carries a kernel and a test volume does
  not; both are right, and this milestone is about telling them apart rather than about either.
- **A build-system rework.** The defect is one artifact with two shapes and one name, the fix is the
  one this file already applied to the kernel slot, and anything larger is a different milestone that
  should be argued for on its own.

## An audit of the implementation (2026-08-26): the stamp did not follow the split

- [x] **M7 - THE BUILD STAMP FOLLOWS THE SPLIT.** The two artifacts have two names now, and `built-$arch-volume` is still one file
  holding a digest of the SOURCES. `./build.sh --kernel-on-volume --part volume` writes it, and
  `test.sh` reads it and concludes the userspace is current - while the shape the suite actually
  boots, the one WITHOUT a kernel, may not have been built since the sources changed. Edit userspace,
  run `./image.sh`, run `./test.sh`: the staleness check passes and the suite boots an old volume.
  That is the same sentence as the original defect with a different subject, and it is the fix's own
  blind spot: naming the artifacts was not enough while the record of what was built is still shared.
  The smallest fix is one more file, so that each shape's stamp is written by the build that produces
  that shape and by nothing else:

  | | |
  | --- | --- |
  | `built-$arch-volume-test` | written ONLY by a build without a kernel; read by `test.sh` |
  | `built-$arch-volume` | written ONLY by a build with one; read by whatever checks a bootable tree |

  There is a third writer, and it is the one a reader would not look for:
  `check-implementation-mutations.sh` writes `built-x86_64-volume` itself, by hand, to tell the suite
  that its mutated tree is current. A fixture that forges a stamp has to forge the stamp the suite
  actually reads, so it moves with `test.sh` - and if it does not, the mutation gate stops testing
  mutations and starts refusing to run, which is a failure that looks like a defect in the mutation.

  The gate covers the `.uuid` beside each `.img`, because a pairing that belongs to the other shape is
  the same defect in the file the loader actually reads: six files, three per shape, and no command
  may touch a file belonging to the shape it is not building.

  AND EACH PAIRING IS CHECKED AGAINST ITS OWN IMAGE, not merely against the other pairing. The first
  version of the gate asserted the two uuids DIFFER, which catches two names over one artifact and
  nothing else: swap the two sidecars and both are still different, both still exist, and every check
  passes while each medium names the volume it is not paired with. `volume-pairing.sh` already has
  `pairing_matches_volume`, which is what M4 made shared for exactly this, so the check is two calls
  rather than a new mechanism.

Two further points from the same audit need no work, and are written down so the next reader does not
re-derive them.

`volume-<arch>.pkg` is NOT split, and must not be. The system-volume mode of `mkpackages` produces
the `.img` and the `.uuid` and nothing else; the package is assembled by the ordinary path and never
carries a kernel, so both commands produce identical bytes for it. Two names would be two copies of
one file.

The image cache key already hashes the bootable shape alone rather than both, so a key describes the
inputs of the image it belongs to. And the consumers were checked one at a time rather than assumed:
`test.sh`, `run.sh` and all three architectures in `qemu-run.sh` name the test shape, which is the
one they want; `mkimage.sh` and `check-signed-boot.sh` name the bootable one. No consumer reads a
name that could be either, because there is no longer such a name.

## Results (2026-08-26)

The two shapes are `system-volume-<arch>.img` and `system-volume-bootable-<arch>.img`, with their
uuid sidecars beside them. `mkimage.sh` and `check-signed-boot.sh` name the bootable one; the test
harness and `run.sh` name the other; a consumer that finds neither says which command builds it.

`check-build-order.sh` builds both shapes in both orders and requires each to survive the other, and
refuses a tree where the two shapes have equal contents - which would make the gate pass on a tree
where the defect was still there. The pairing question moved into `src/tools/volume-pairing.sh`, so
the check that runs where a pairing is WRITTEN and the check that runs where a medium is READ are the
same code; that is what M4 asked for, and it is why `check-signed-boot.sh` no longer carries its own
copy of the superblock offset.

Neither remaining reference to a command order is a rule any more. `check-signed-boot.sh` asks
whether a medium and a volume were built from the same tree, which is a consistency question a
half-rebuilt tree can still fail; `check-qemu-virtio-iommu-x86_64.sh` asks whether its ISO predates
the kernel it is supposed to carry. Both name a rebuild rather than a sequence.

The wrong-kernel diagnosis in `test-kernel.sh` is still there and can no longer be reached by
building in an ordinary order.

A gate that is not in `verify-model`'s catalog is a gate nothing would ever select, so `build-order`
is in it - and adding it is what made `verify-model` say so, which is the catalog earning its place
rather than a formality.

## Results: M7 (2026-08-26)

`./build.sh` writes `built-$arch-volume-test` when it builds a volume WITHOUT a kernel and
`built-$arch-volume` when it builds one with. `test.sh` reads the first, which is the shape it boots.
`check-implementation-mutations.sh` forges the first too, for the same reason: a fixture that writes
the receipt nobody reads does not produce a wrong answer, it produces "no build stamp" - a mutation
gate that stops testing mutations and starts refusing to run.

**AND THE GATE HAD TO COMPARE THE STAMP BY WHEN IT WAS WRITTEN, NOT BY WHAT IS IN IT.** Both shapes
are built from the same sources, so both receipts hold the same digest, and a command that rewrites
the other shape's receipt writes bytes identical to the ones already there. A content comparison sees
nothing and passes - while the harm is exactly that a receipt was issued for a build that did not
happen. The image and the pairing are compared by content, where a wrong value differs; the stamp is
compared by modification time, where it does not.

That distinction is not theoretical. Reintroducing the defect - one shared stamp for both shapes -
and running the gate produces:

```
build-order: building the test shape disturbed the bootable one - they are not two artifacts
    before: img=deb8267f... uuid=fd53f9e1... stamp=2026-08-26 18:29:20.710159390 +0200
    after:  img=deb8267f... uuid=fd53f9e1... stamp=2026-08-26 18:29:49.406382286 +0200
```

Identical image, identical pairing, and the stamp written by a command that was building the other
shape. A gate comparing only content would have passed on that tree.

A shape is three files now - image, pairing, receipt - and the gate requires all six to exist, the
two pairings to differ, and each shape's three to survive the command that builds the other.

## What the 2026-08-30 audit found

One finding, accepted and fixed: **the signed-boot list-absence mutation restored one third of the
bootable shape.** The shape is image, uuid sidecar and build stamp - one identity, read as one by
every consumer - and the nested volume rebuild rewrites all three while only the image was saved. A
normal run left the restored image paired with the listless build's uuid and carrying that build's
stamp; an interruption left even the image gone, because the trap only removed the work directory.

All three are now saved before the rebuild, the trap is armed at the same moment so every path out
restores the whole shape, and the restored shape is ASSERTED coherent - the sidecar beside the image
must name the image that is actually there. A restore that silently half-worked is what the finding
is about, so it is checked rather than assumed.
