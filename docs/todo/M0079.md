# M0079 - LiberFS: third-review fixes (GPT robustness, snap_open cost)

Status: COMPLETE. The third full source pass (2026-07-03). None data-endangering.

*Condensed 2026-08-08.*

**A degenerate GPT partition could kill StorageService.** An entry carrying the LiberFS type GUID but
spanning fewer sectors than the minimum pool made the format fail, the mount return nothing, and the
service exit - so **the disk's content could deny the whole storage service**. The probe skips
entries below a minimum and **keeps scanning**, so a later valid entry still wins.

**The GPT probe accepted a non-power-of-two entry size**, after which entries straddle the read pages
and the fixed-stride slot arithmetic parses garbage. The spec requires a power of two; enforced.

**`snap_open` mounted a whole second filesystem per request** - a full free-map derivation, O(volume),
to read one file out of a snapshot. The crate already had the right mechanism, so a re-rooted read
replaced it: O(file) per request, and the duplicated per-request mount machinery is gone.

`set_compression` returned Ok for a no-change value **before** the read-only gate, so a no-op request
on a degraded volume reported success instead of denial. The gate comes first now.

The volume label grew from 32 to 256 bytes in place, behind a feature-flag bump - the superblock was
reserved zeros from that offset on.

Recorded as a theoretical non-fix: a full directory leaf sharing one 64-bit name hash would strand a
record at the split, which needs a ~290-way FNV-64 collision. Acknowledged at the code rather than
guarded.
