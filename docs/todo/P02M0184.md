# P02M0184 - A camera vocabulary and service

Status: COMPLETE (2026-09-24). Every item below is done.

This owns the camera vocabulary and service prerequisite for P02M0099's UVC item, as requested
by the owner on 2026-09-21. CameraService carries capture frames and policy independently of
DisplayService. Consumers use existing codec leaves; neither service nor driver adds a decoder.
A service-level emulated camera proves the contract before live USB transport is implemented.

Current memory objects stay charged to their creating Domain when their handles move. Mapping
rights are enforced, but closing a producer's handle does not revoke another process's existing
mapping. Buffer ownership below relies on caller ownership and explicit leases, not imagined
mapping revocation. Current USB fixtures and class dispatch provide no UVC device.

## P02M0184a - Public contract and capture grants

- [x] Add `src/idl/camera.lsidl` (`liber:camera@1`) and a separate versioned
  `camera-device.lsidl` provider contract, generated protocols/clients and a `camera_service`
  program in the existing services crate. Wire manifest sources/program/service/dependencies,
  build inputs and ServiceManager's `SERVE`, private `ADMIN` and `CATALOGUE` roles. Append
  positional bootstrap roles and update all affected launchers and kernel harnesses.
- [x] Inventory access exposes bounded non-capture metadata and format queries, never frame
  buffers or a start operation. PermissionManager alone holds the private camera-admin factory
  and mints a `camera-capture` endpoint for an explicit policy grant scoped to a selected
  provider publication and service incarnation. Add the security vocabulary and policy path.
  A capture endpoint must explicitly negotiate and call `start`; minting or connecting alone
  never starts hardware. A future portal can consume this factory without being required here.
- [x] Bind stream handles to provider publication/binding generations and a new stream
  generation. Close, admin revocation, endpoint loss, client death, provider withdrawal and
  service restart terminate capture and invalidate all operations on that stream. A replacement
  camera is a new authority decision; stale handles do not silently rebind to it.
- [x] Bind each capture grant at minting to a `WAIT | TRANSFER` observer of the exact
  prepared client task through PermissionManager's existing `grant_for_task` path. CameraService
  watches owner termination as well as endpoint closure: a duplicated/transferred endpoint cannot
  keep capture authorized after its launching owner dies. The observer grants no task-management
  authority. Failed prepared launches revoke their capture grants and run the same stop cleanup.
- [x] Allow one capture stream per physical camera, maximum four cameras/four streams and
  32 client connections in the service. Incompatible concurrent opens return busy, including
  attempts from another grant. Renegotiation requires stopping and retiring the previous stream
  first. Return explicit unsupported/too-large/busy/stale outcomes, not silent format changes.

- [x] Reuse P02M0180's shared catalogue infrastructure stage: private
  `provider-catalogue-admin.open-consumer(kinds)`, held only by ServiceManager, mints this
  service's kind-scoped catalogue connection. DeviceManager checks the actual publication
  kind/generation on both subscribe and open. This depends on that infrastructure stage, not
  completion of Bluetooth functionality. Use its bounded 32-client/subscriber admission and
  combined manifest-budget check; do not duplicate its factory or rely on an unchecked filter.

## P02M0184b - Enumeration and producer boundary

- [x] Enumerate at most eight formats, 32 frame-size records/format and 32 intervals/size;
  represent continuous intervals as checked minimum/maximum/step, not expanded lists. Use bounded
  paged replies with snapshot generation. Reject zero/overflow dimensions, impossible strides,
  invalid intervals, duplicate/conflicting identifiers and over-budget descriptor graphs.
  **LANDED 2026-09-23.** The normalizer and the service's own `camera_streams::validate` hold eight formats,
  32 sizes and 32 intervals, keep continuous ranges as checked minimum/maximum/step, and refuse every shape
  listed; pages carry the snapshot generation and a page under another one is `stale`.
- [x] Initial frame types are packed YUY2 and MJPEG. Identify compressed versus uncompressed,
  width/height, selected rational frame interval, maximum bytes, valid byte length, and for YUY2
  checked stride/plane offset and color-range/matrix metadata with unknown allowed. MJPEG is
  opaque encoded data for the existing JPEG consumer leaf; unsupported codecs are refused.
  Exact negotiated values must be in the advertised set and fit the declared buffer budget.
- [x] The private producer wire owns enumerate, negotiate, register/queue caller buffers,
  explicit start/stop, completed-frame metadata and discontinuity/status events. Only
  CameraService opens a camera provider; public clients receive no catalogue or hardware
  endpoint. Add `camera` consistently to device IDL, driver protocol, manifest kind mapping,
  DeviceManager conversions and generated registries, allocating an unused append-only value
  alongside P02M0180-P02M0188. Keep subscription and withdrawals live. Connection-count limits
  are not authorization; bootstrap and restricted grants enforce that boundary.
- [x] Stage pure UVC format/frame descriptor normalization and negotiation validation in the
  existing host-testable driver library. The fixture uses this production helper over synthetic
  descriptors; the later UVC module reuses it. Runtime-free service-logic owns public selection,
  lease accounting and metadata state. P02M0099 owns actual USB descriptor fetching, probe/commit
  transfers, payload assembly, isochronous/bulk scheduling and FID/EOF recovery. No parsing is
  duplicated in CameraService, and this milestone does not claim an exercised USB transport.
  **LANDED 2026-09-23.** `drivers::uvc` (8 module-local tests) normalizes the VS format, frame and colour
  descriptors under every bound named above and selects exactly what is asked; the fixture's synthetic
  descriptors go through it. Selection checks, leases and metadata are `service_logic::camera_streams`.
- [x] The service verifies the producer's selected parameters against the requested format,
  advertised set and limits before accepting a stream. A producer refusing or changing them
  unwinds all registered buffers and leaves capture stopped. Size shared catalogue client and
  subscription bounds for the manifest's combined new and existing consumers; retain finite
  admission/refusal and reclaim connections on every failed open or teardown.

## P02M0184c - Buffer ownership, bounds and teardown

- [x] Clients allocate their own MemoryObjects and retain ownership/accounting, following the
  existing font service's caller-owned memory principle. Register at most four buffers/stream,
  each at most 8 MB, with at most 32 MB registered/stream and 128 MB globally. Validate actual
  object size/type/rights and checked layout before forwarding restricted writable mapping
  capabilities to the trusted producer. The service keeps only bounded handles/metadata;
  repeated requests never allocate frame storage charged to the service for the client to retain.
- [x] A buffer is in exactly one state: client-owned, queued, producer-writing, or completed
  and leased to the client. Only an explicit queue/requeue transfers write permission under the
  protocol. Completion carries buffer ID, stream/lease generation and valid byte length; after
  completion the producer cannot overwrite it until the client returns that exact lease.
  Duplicate registration of one backing within a stream and stale/double returns are refused.
  Queueing while a client reads violates its own lease, not another client's authority.
- [x] Keep memory mapping rights explicit: the producer gets only the mapping/read/write and
  transfer rights needed for this contract, no unrelated authority; client ownership may include
  write access, so returned pixel bytes are never trusted service input. Do not claim immutable
  pixels against their own owner. Publish metadata in typed IPC separate from client-writable
  bytes. No executable mappings or DMA authority are granted to clients.
- [x] The provider writes assembled data into queued caller-owned buffers, then publishes
  completion without a full-frame IPC copy. Hardware DMA stays in the controller's own bounded
  transfer buffers; this contract does not require DMA directly into arbitrary client memory.
  Initial assembly may copy payloads into the caller buffer. No service-to-client pixel copy or
  per-frame allocation is required, and no zero-copy hardware claim is made.
- [x] When no buffer is queued, discard new frames and count known drops; never overwrite a
  completed lease, allocate a replacement, or block unrelated cameras behind a slow reader.
  Bound completion metadata to the four registered buffers and retain one coalesced status
  snapshot outside that queue so terminal/loss state remains observable at saturation.
- [x] Stop cancels future writes and waits for the producer to return every queued/writing
  buffer before acknowledging completion. On endpoint loss/revocation do the same internally.
  Use a two-second local stop deadline: an unresponsive producer makes that camera unavailable,
  with its bounded slots quarantined until confirmed stopped or dead, rather than reusing memory
  while a writer may remain. Ordinary caller-retained mappings need not be revoked to stop writes.
- [x] Never transfer or reuse a previous grant's backing for a new grant. Clients may retain old
  pixels at their own Domain cost, but receive no future captures. A stopped stream is retired;
  a fresh stream registers its own explicit buffers. Release service/producer mappings and
  handles after confirmed stop; on process death kernel mapping cleanup is the confirmation.
  Old completions cannot enter the new generation. Client-delegated memory is the client's
  explicit sharing, not a service-created cross-grant buffer pool.

## P02M0184d - Honest timing and loss

- [x] Always carry host arrival time in `clock_ns()` nanoseconds since this boot, sampled by the
  producer when the complete frame is assembled and ready for handoff, not when a client reads.
  Carry device timing as optional raw ticks, counter width, known/unknown frequency, clock domain
  and reset generation. Do not substitute wall-clock seconds or infer capture age by subtracting
  uncorrelated clocks. No clock synchronization estimator is required here.
- [x] Preserve available device timing; missing values remain absent. Define modulo counter
  wrap from width, and increment the clock generation on reset or an ambiguous discontinuity;
  do not fabricate a monotonic device timeline across it. UVC PTS is conditional and uses device
  units; FID is a boundary toggle, not an absolute frame counter. These constraints follow the
  [USB-IF UVC 1.5 specification, section 2.4.3.3](https://forums.developer.nvidia.com/uploads/short-url/ig1j25sqsBdPWvS8gAD62hF6ysB.pdf#page=43).
- [x] Give each stream a monotonically increasing observation sequence. Advance for completed
  frames and definitely observed discarded frames, including no-buffer drops, before delivery;
  those known losses remain gaps with counts/reasons. Also carry a separate unknown-discontinuity
  flag/counter for losses whose frame count the backend cannot establish. Never estimate exact
  missing frames from FID alone. Reset the sequence only with a new stream generation.
