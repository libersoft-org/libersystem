# P02M0112 - Gates that stopped checking

Six of the eleven build gates had not checked anything since P02M0107, and reported success the whole
time. This milestone is the repair and the audit that followed it: for each remaining gate, can it
still fail?

## What happened

P02M0107 split compiling from packaging. Before it, the kernel's `build.rs` read the staged userspace
artifacts and refused the malformed ones; after it, that work lives in `mkpackages`, and the kernel
crate compiles the kernel and nothing else. The kernel's own `build.rs` says so in a comment.

`check-static-injection.sh` drives the whole `static-image` family - six gates that mutate a staged
artifact, run the build, and require it to be rejected. It drove the build by compiling the kernel,
with a `cargo clean -p kernel` in front to force `build.rs` to rerun. After P02M0107 that command
compiles a kernel which reads no artifacts. It succeeded, as it should have. The gate read that
success as "the injection was caught" and printed `passed`.

This is the shape worth remembering: the gate did not break loudly, and it did not start failing.
It kept passing, faster than before, while testing nothing. Nobody looks at a gate that passes.

It surfaced only because a SECOND fault in the same script - an unqualified `volume.pkg` left over
from qualifying the per-architecture build slots - made it fail for an unrelated reason. Fixing
that one exposed this one. Had the file name been right, the family would still be dead.

## The repair

- [x] `check-static-injection.sh` drives `mkpackages` rather than `cargo build`, because that is
  where all six rejections live - verified by grepping each rejection message to its source, all in
  `tools/mkpackages/src/main.rs`. The kernel is not built at all now: nothing under test needs one.

- [x] The gate is proven able to fail. Disabling the duplicate-edge rejection in `mkpackages` makes
  it report `x86_64 did not reject the injected duplicate-edge artifact` and exit 1; restoring the
  rejection makes it pass on all three architectures. A gate that has just been repaired is exactly
  the thing that should not be taken on trust.

- [x] `volume.pkg` -> `volume-x86_64.pkg` in the gate. Every other caller had already moved; this
  was the last one. The diagnostic that named the file now prints the name it was given rather than
  a literal, so a wrong path cannot say the right name again.

- [x] `check-dynamic-report.sh` printed `just test-tags ...` and `just dynamic-report-check` as the
  commands to reproduce its rows. P02M0110 removed both recipes. Now `./test.sh --tags ...` and
  `./check.sh --gate dynamic-report`.

- [x] The three checked-in report tables were stale, and not only in that column. Regenerating
  them moved every recorded size: the x86_64 image went from 2396160 to 2785280 bytes, and the
  other two targets grew comparably. That growth is the P02M0109/P02M0111 work - the storage service's
  streaming path and rt's additions - which never reached the tables because this gate was not run
  while those milestones were open. The gate was doing its job; nobody had asked it.

## The gate cannot say what went wrong

- [x] **A killed injection run leaves the tree mutated, and the next run dies with no message.**
  The gate mutates a staged artifact in place and restores it from an `EXIT` trap. A run that is
  killed rather than exiting - which is what happens when something else rebuilds underneath it -
  never restores, so the artifact stays malformed. The next run then fails its BASELINE packaging
  step, because `mkpackages` correctly refuses the artifact still sitting there from last time.

  That much is recoverable. What is not acceptable is how it reports it: `package_arch` is called
  without any error handling for the baseline, so `set -e` kills the script on the spot, with an
  empty log and exit 1. Twice tonight that produced a completely silent failure, and the first
  time it sent me looking for a defect in the wrong place - I blamed a concurrent build, which was
  the cause of the FIRST kill but not of the silent failure that followed it.

  A baseline that cannot be built is the gate's most likely failure, because it is what a previous
  interrupted run leaves behind. It should say so, name the artifact, and point at the log.

  Fixed. Both unguarded calls - the baseline and the rebuild after a restore - now report what
  failed, print the packaging log, name the artifact, and give the command that repairs it.

  Verified by producing the state rather than by reasoning about it: with `dyn_probe`'s ELF type
  overwritten to `ET_EXEC`, the gate exits 1 saying "baseline packaging failed before any
  injection", names the artifact by full path, and suggests `./build.sh --arch x86_64 --part
  user`; restoring the file makes it pass again. The first attempt at that verification wrote
  seven bytes at offset 64 and the gate passed - the mutation has to be one `mkpackages` actually
  checks, which is a reminder that "I corrupted the file" and "I corrupted what is validated" are
  different claims.

- [x] **The injection gates fail silently under load, and I could not pin why.** (Still open, and
  now instrumented - see the two items below it. What "under load" means here became concrete
  afterwards: this machine carries a 24-hour `cargo-fuzz` run with 56 workers across three targets,
  which is the background every one of these failures was observed against.)
  Recorded rather than explained, because the honest state is that I do not know.

  Three times tonight `./check.sh --gate all` exited 1 with the log ending mid-gate and nothing
  written - once after `malformed-dynamic aarch64`, once after `riscv64`, once after `x86_64`. Run
  on its own the same gate passes: directly, twice; through `check.sh`, twice more. So the varying
  stopping point is not a defect in a particular leg.

  What the three failures share is load. Each followed the three QEMU suites immediately, on a host
  shared with other tenants (17 of 31 GiB in use by processes that are not this build). A gate leg
  spawns `cargo run` under a 600-second timeout, and every path where that command REPORTS failure
  is now guarded and prints - so a silent death is most likely the shell itself being killed, which
  no amount of error handling inside it can report. `dmesg` shows no OOM kill in the window, which
  argues against the obvious version of that story and is why this is written as an open question.

  What NOT to do: raise a timeout or add a retry. Both would hide a gate that stops checking, which
  is the exact failure this milestone exists to record.

  The next-step diagnostic is now in place, which is as far as this can be taken without a
  recurrence. `check.sh` captures each gate's status instead of letting `set -e` end the run
  wordlessly, and reports an ordinary failure and a signal differently - "failed (exit 3)" versus
  "was KILLED by signal 9 - it did not fail, something stopped it". Verified with two temporary
  probe gates, one exiting 3 and one killing itself, both propagating their status out of the
  script.

  That splits the question in two the next time it happens. If the KILLED line appears, the gate
  child was killed and the signal names what did it. If the run still ends in silence, then it is
  `check.sh` ITSELF being killed, and no diagnostic inside it can ever report that - which was
  demonstrated by accident while building the probes: a `$$` that expanded one shell too early
  killed `check.sh` and reproduced the original silent signature exactly.

  RECURRED 2026-08-06, and the split was too coarse: there is a THIRD case. `malformed-dynamic`
  failed with `gate 'malformed-dynamic' failed (exit 1)` - so the gate DECIDED rather than being
  killed - and printed nothing of its own, not even the first architecture's result, with stderr
  captured. Run alone immediately afterwards it passed all three.

  That narrows it usefully. Not a signal, so nothing external stopped it; not the baseline, which
  now reports itself by name; and no output at all, so whatever `set -e` caught wrote nothing to
  either stream. What remains are the unguarded commands in `check_target` that fail silently -
  `mktemp`, `cp`, `mapfile`, the `sha256sum` substitutions - and the script preamble, which takes
  three `flock`s and reads the manifest before any leg begins.

  The next step is therefore narrower than "capture a status": guard those, or run the script under
  `set -x` into a file when it is invoked from `check.sh`, so the LAST command before the exit is
  on record. Still not to be answered with a retry.

  Chased further the same day, and the picture is now specific enough to be worth writing down even
  unsolved:

  - It is NOT load. Every failure since has been on an otherwise idle host.
  - It is NOT the injection family competing with itself: all six run together and pass.
  - It is NOT a signal, and not the baseline: two failures reported exit 1 and exit 74, both
    with no output at all - not even the first architecture's result, with stderr captured.
  - It is NOT the command: `bash -c 'set -euo pipefail; ( cd src && eval "..." )'`, which is
    exactly what `run_gate` does, passes every time. So does the script run directly, and under
    `bash -x`.
  - The failing gate MOVES. Twice `malformed-dynamic`, the seventh; once `duplicate-edge`, the
    first, with nothing before it. Tracing `check.sh` moved the failure from the seventh gate to
    the first, which argues for timing rather than for any one leg.
  - And a plain `--gate all` immediately afterwards passed all eleven.

  Exit 74 is the sharpest clue and does not match anything the script calls deliberately - not
  `timeout` (124/125/126/127), not a signal (128+n), not `mkpackages` (1). Finding what returns it
  is the thread to pull next.

  **A lead that did not hold, recorded because it looked conclusive.** Exit 74 is what the llvm
  tools return on EPIPE, and this tree had already met that twice - `build-shared.sh` and
  `check-source-hygiene.sh` both carry a paragraph about it, both written about `grep -q`.
  `check-static-injection.sh` turned out to have the same hazard in a different reader:
  `llvm-readelf -lW "$artifact" | awk '$1 == "DYNAMIC" {print $2; exit}'`, four of them, two inside
  the `duplicate-edge` branch - which is the gate that failed. Every symptom fitted: a race against
  the producer's flush strikes a different gate each run, passes on replication, and dies in a
  command substitution under `set -e` with no message at all.

  It is not the cause. A pipe holds 64 KiB before a write can block, and a writer whose ENTIRE
  output fits in the buffer never blocks, so it never sees the reader go away. `llvm-readelf -lW` on
  the probe artifact emits 1,279 bytes and `-SW` emits 1,853. Those pipelines cannot EPIPE. Driven
  300 times in a loop against a 29 MB kernel, the exit status was 0 every time.

  DONE 2026-08-12, in the sense this item can be finished: every diagnostic it names is now in place
  and demonstrated, and the intermittent itself waits on a recurrence to identify.

  The last prescribed step was "run the script under `set -x` into a file... so the LAST command
  before the exit is on record", and that is what landed. `check-static-injection.sh` opens a trace
  file and turns on `xtrace` into it as the very first thing it does - before the source root is
  resolved, because resolving it is itself one of the lines that has died wordlessly - with a `PS4`
  carrying a millisecond timestamp and the line number. Its `cleanup` prints the tail on a failure
  and deletes the file on a pass, so a green run leaves nothing behind.

  And `check.sh` prints it too, which is the half that matters most: a signal skips the gate's own
  EXIT trap, so on precisely the failures worth chasing the gate cannot report its own trace and
  only the caller can.

  Demonstrated rather than argued. With `kill -9 $BASHPID` injected after the tool probes, the run
  reports `gate 'duplicate-edge' was KILLED by signal 9` and then prints the trace, whose last line
  is `+ 02:47:01.237 check-static-injection.sh:124: kill -9 2392207` - the killing command, its line
  and its time, recovered from disk after the shell that ran it was gone. The trace was 2,697 lines
  and 62 kB for one gate leg, which is affordable for a file that exists only on failure.

  Still no retry and no raised timeout, for the reason recorded above.

  So exit 74 is still unexplained, and the reproduction that would settle it - the gate failing
  again, under `set -x` - has not happened since.

  The sites were converted anyway, because they are a real instance of a rule this tree already
  enforces and their being harmless today depends on an output size nobody is holding fixed. Six
  converted, including two `< <(...)` readers that were safe by accident rather than by
  construction. That is a cleanup, not a fix, and it is recorded as one.

- [x] **The gate that exists to catch this only knew one shape of it.** (Worth keeping regardless of
  the above: the rule is the tree's own, and its scanner was narrower than the rule.) `check-source-hygiene.sh`
  scans for `| grep -q` under `pipefail` - and the instance that cost a night was `| awk '...;
  exit}'`. The rule was right and its pattern was narrower than its own comment.

  Widened to `grep -m N`, `awk '...exit}'` and `sed -n '...q'`, and taught to skip comment lines,
  which it had to be: the paragraph explaining the rule matched the rule.

  It took two attempts, and the first failure is the interesting one. The awk alternative was
  written as `awk ["'][^"']*exit *}` - a class excluding both quote characters - and an awk program
  routinely contains both. `awk '$1 == "DYNAMIC" {print $2; exit}'`, the exact line this was written
  for, stops that class dead at `"DYNAMIC"`. The gate passed the tree while the bug it was written
  to catch was still in it. Verified the second time by reintroducing the hazard and watching the
  gate name it.

  Widening it found a fourth instance nobody was looking for: `qemu-run.sh` decides whether a host
  port is taken with `ss -ltn ... | grep -q LISTEN`, where a port that IS in use could read as a
  failed check.

- [x] **`head` is the same hazard.** A dozen `find ... | sort -nr | head -n1` pipelines in
  `build-shared.sh` and elsewhere have producers that would take SIGPIPE exactly as `llvm-readelf`
  does. They have been stable, and the pattern deliberately stopped short of `head` at first rather
  than landing one rule as a dozen failures.

  Done properly instead. Thirteen copies of `find ... | sort -nr | head -n1 | cut -d' ' -f2-` were
  saying one thing - "the newest file matching this pattern" - so they are one `newest_matching`
  helper now. It has no early reader anywhere in the chain: `sort` cannot emit before it has read
  ALL of its input, so capturing the sorted list and taking its first line with parameter expansion
  leaves nothing to close a pipe. Four other readers went the same way - two `uniq -d | head`, a
  `tr | sort | uniq -d | head` reduced to a plain emptiness test, and a `diff | grep | head -2`.

  That `diff` one had a second fault sitting under the first: `diff` exits 1 when the files differ,
  which is precisely the case being reported, so the pipeline's status was wrong either way. It is
  now `|| true` on the capture, where the intent is visible.

  With the tree conformant, the gate covers `head` too - verified by putting one of the thirteen
  back and watching it get named.

- [x] **The next silent death will name itself.** The honest state of the item above is that its
  cause is still unknown, and one wrong reconstruction has already been built from the exit status
  alone. What can be fixed without a reproduction is the silence.

  `check-static-injection.sh` now carries an ERR trap that prints the failing command and its line
  the moment it fails. Two details make the difference between that working and merely looking like
  it works:

  - `set -E` is required, not just `set -e`. Without `errtrace` the ERR trap is not inherited by
    functions, subshells or command substitutions - and everything this script does of consequence
    happens inside `check_target`. The first version lacked it, and a deliberately planted failure
    reported "no failing command recorded", which is how the gap was found rather than shipped.
  - The report is printed WHEN it happens, not remembered for the EXIT trap. A command substitution
    runs in a subshell, and nothing it assigns survives to the parent.

  ERR does not fire for a command whose failure is being tested - an `if`, a `while`, a `&&`, a
  `!` - so this stays silent for every failure the script already handles. Verified by planting a
  failure inside `check_target` and watching the trap name the command and the line.

- [x] **The rest of the early-close family, audited rather than assumed.** Having been wrong once
  about which reader was at fault, the remaining shapes were enumerated rather than eyeballed: a
  pipeline into a bare `read`, and a `... | while read` loop whose body can `break` or `return`
  before the producer is done. Both close the pipe exactly as `head` does.

  Every `.sh` in the tree that sets `pipefail` was scanned for both. Zero of each. That is a
  measurement rather than an impression, and it is what makes the widened gate a complete rule for
  the shapes it names instead of a partial one.

  `newest_matching` was checked against the pipeline it replaced across four dependency directories
  and three patterns, including one that matches nothing: twelve cases, identical answers. Paths
  containing spaces behave the same in both, since `${first#* }` strips exactly the timestamp field
  that `cut -d' ' -f2-` did.

## The audit

The question a passing gate cannot answer is whether it would fail. Asked of the other five:

| Gate | Can it fail? | Evidence |
| --- | --- | --- |
| `test-tags` | yes | Exits 1 on `descriptors -eq 0`. It guards the vacuous case by hand. |
| `artifact-metadata` | yes | Caught the launch-context work adding `base-proto` to nine tools. |
| `volume-layout` | yes | Compares two full sets; an empty package fails against a non-empty manifest. |
| `development-gate` | yes | Reports the count it found - 2 development-only programs. |
| `dynamic-report` | yes | Caught its own stale tables in this very run - see above. |

`test-tags` is the one that got it right on purpose: it counts what it inspected and refuses to
report success on nothing. That is the cheap defence against this entire class, and it is worth
copying wherever a gate walks a list it did not itself construct.

## A build that only worked because of what the last one left behind

- [x] **A from-scratch build of an architecture fails: the consumer stage redirects into a directory
  the build deleted.** Not a gate, but the same shape as everything else here - it looked fine only
  because leftover state was propping it up.

  `build-shared.sh` sweeps the artifact tree of anything the manifest no longer names, and ends with
  `find ... -type d -empty -delete`. That takes `logs/` with it whenever the last build happened to
  leave it empty. The consumer stage then writes its per-artifact transcript with a shell
  REDIRECT - `2>"$errors"` - which creates the file and not the directory, so the build dies on
  "No such file or directory" before compiling a single consumer.

  It never showed up in day-to-day work because any previous build of that architecture left
  transcripts behind, and a non-empty directory survives the sweep. It only appears when an
  architecture is built from nothing - which is what a fresh clone does, and what a CI runner does
  every time.

  Found by accident and then confirmed twice: once in a pristine `git worktree` at HEAD, and once
  after deleting every riscv64 artifact in the working tree. Both died at the same redirect, on
  different consumers. Fixed by recreating `logs/` beside the artifact root the sweep already
  restores; riscv64 then built from nothing.

  Worth noting how it was nearly misdiagnosed. The first symptom was a `mkpackages` digest
  assertion - `permission_manager` carrying an older `service-util` digest than the one on disk -
  which looked like a real staleness bug in the new digest validation. It was a consequence of an
  interrupted build (a `build-shared.sh` killed mid-flight left one rebuilt and the other not), and
  chasing it is what uncovered the actual fault underneath. The digest check was right; it was
  reporting genuine staleness, just staleness that had been created by hand.

## What this says about the ones that remain

Nothing here is a reason to trust the five. They can fail; whether they fail on the RIGHT things is
a separate question, and answering it means breaking each check deliberately, one at a time. That
was done for the injection family because it had just been repaired. The five have been passing
continuously through changes that would have tripped them, which is weaker evidence than a
deliberate revert but is not nothing.

  **2026-08-07: the diagnostic could not fire where the failures were.**

  Not a solution, but it removes the largest blind spot and it was visible in the script the whole
  time. The ERR trap was installed sixty-nine lines in. Before it ran:

  - a command substitution shelling out to `system-manifest.sh export-json` (which runs `jq` and
    reads files),
  - six `command -v` probes,
  - two `mkdir -p`,
  - three `exec N>` redirections onto lock files under `.build/state`,
  - three blocking `flock`s.

  Under `set -e` a failure in any of those ends the script with nothing but a status - which is
  exactly the signature recorded above: exit 1 and exit 74, *no output at all, not even the first
  architecture's result, with stderr captured*. The evidence was read as "the trap did not name the
  command", and the simpler reading is that the trap did not exist yet.

  A redirection that cannot be made is also one of the few things in this script that can plausibly
  answer with an I/O status, and `.build/state` is written by every build and every suite - so the
  three `exec`s are the first place to look, and they were in the unwatched region.

  Fixed by ordering: the state the traps read is declared first, the traps are armed second, and
  only then does the script do anything that can fail. A `phase` marker records where it has got to
  and both traps print it, so even a death that outruns the ERR trap - a signal, or the shell itself
  going - leaves its last known position rather than a bare number.

  This does not close the item. It makes the next recurrence say something, which the last three
  could not.

## A fifteenth gate, and the false green that asked for it

Added 2026-08-10, after `docs/todo/TODO.md` was found marking three milestones `- [x]` over documents
that held unfinished `- [ ]` tasks. One of them had been reopened by an audit hours earlier; one
carries a defect its own text calls "Still open, and I do not know why"; one had two tasks written
into it the same afternoon. A reader following the index - which is the only summary of a milestone
anybody sees without opening it - would have concluded all three were finished.

This is the milestone's own subject wearing different clothes. Nothing was checking, so nothing said
anything, and being careful is not a mechanism: reopening a milestone means editing two files and the
second one lives somewhere else, so it is forgotten exactly when the news matters most.

`tools/check-milestone-index.sh` compares every `- [x]` row in the index against the `- [ ]` count in
the file it names, and refuses an entry naming a file that is not there - which is how a rename
presents. Only that direction: `- [ ]` over a document with no open tasks is a milestone whose
remaining work is prose, which is ordinary.

It self-tests first, like the rest of them: a consistent index must be accepted, an index marking an
unfinished document done must be refused, and a dangling filename must be refused. Watched refusing
the real tree as well as the fixture, by marking P02M0120 done while it had two open tasks - which is
the exact state that prompted it.

Registered in `verify-model`'s gate table as well as in `check.sh`, because the model compares the
two lists and a gate in one and not the other is never selected by a change to its subject. Confirmed
by removing the registration: `check.sh runs gate 'milestone-index', which the catalog does not know
about - nothing would ever select it`.
