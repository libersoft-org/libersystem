# P02M0137 - The build spends its time re-checking what did not change

Status: TOOLING. NOT A PHASE-2 COMPLETION GATE.

## Why

A build in which NOTHING changed takes 3 minutes 51 seconds, and 208 of those seconds are one
stage. The build's own summary reports it:

```
stages=source:0, graph:0, providers:0, consumers:0, reports:208
providers=64/0  objects=0/0  executables=95/0
```

Those zeros are what `build-shared.sh` prints for stages it did not have to do - through the warm
snapshot, through per-item caches, or both; the summary does not distinguish them and this milestone
does not need it to. Nothing was rebuilt, the whole rest of the build is about 25 seconds, and the
reporting stage ran anyway.

**The expensive thing is not the check the build asks for.** `check-dynamic-report.sh` calls
`self_test` BEFORE it parses its mode, and `self_test` recursively invokes `"$0" --check`, the full
report-set generation and comparison over all three targets' artifacts. The `--check-inventory`
branch the build actually wants compares tool NAMES and exits, and never reaches `llvm-readelf` at
all. Measured with the self-test suppressed:

```
$ time DYNAMIC_REPORT_SELF_TEST=1 src/tools/check-dynamic-report.sh --check-inventory
dynamic-report: 74 checked tools match the manifest
real 0m0.156s
```

So the build pays roughly 208 seconds for 0.16 seconds of work it asked for. `--write` pays it too,
and so does an invalid argument - the usage error is printed after the full gate has run. `--arch
all` pays it once per target.

And what those 208 seconds buy is a WARNING: `check_dynamic_report_inventory` prints "checked dynamic
reports need refresh" to stderr and leaves the build status at 0.

The self-test itself is sound in intent - it hands the comparator a mutated report and requires it to
object, which is the right instinct and the reason this tree can trust the gate at all. Three things
about it are wrong. It runs for every mode rather than for the one it protects. It treats ANY
non-zero exit of the child as proof that the comparison worked, so a missing artifact or a parse
error is indistinguishable from "the comparator caught the mutation" - a green answer that is not
evidence, which is the failure mode this tree names most often. And `--check` performs the whole ELF
sweep twice, once in the self-test child and once for the real comparison, which is why
`docs/DEBUG.md` records the full check at about 500 seconds.

**The gate reads artifacts; it does not build them.** `generate_report` resolves each tool to
`$build_root/image/$target/$destination` and fails when it is absent, and `provider_metrics` does the
same for provider libraries. Everything below therefore says "report-set generation" or "ELF sweep",
never "generates the targets" - and the benchmark protocol has to prepare all three targets'
artifacts before it can time the gate at all. `docs/DYNAMIC_LINKING.md` currently says the gate
"rebuilds", which is part of what this milestone corrects.

**The test half is a different problem, and it is not serialisation.** An x86_64 run of
`process,memory,paging,scheduler,service,smp,kernel` is 226 tests in 283 seconds. Of the 24 tests
with a recorded duration, 16 are under `kernel.applications` and account for at least 212 s - the
per-test figures are printed as whole seconds, so every total here is a lower bound. But they are not
sixteen fixtures: twelve call `run_permission_scenario`, and ELEVEN of those twelve - one `Probes`
and ten `GovernedTools` - do exactly the same work and return at the same early exit, before the
branch that only `ScopedGrants` continues past. The helper builds the same storage/process/permission
topology, pipelines, command tools and real shell every time. Those twelve tests are at least 169 s
of the 283 s run.

Narrow selections are already cheap by comparison: `handle,object,channel,ipc` is 67 tests in 10
seconds, `scheduler,channel,ipc,smp,kernel` is 111 tests in 13 seconds.

**A faster benchmark is not the goal; a faster workflow is.** `commands.rs` decides whether to hand
the runner an exact ID list by COUNT - `selected.len() * 5 < total * 4` - against a PER-TARGET total
it computes from each test's architecture list. Asked for a real plan, the model reports 265 runnable
x86_64 tests (255 on aarch64 and riscv64), so the break-even is 211: a selection of 212 or more runs
the whole suite. The 226-ID selection measured above is one of them. A hand-driven `TEST_SELECTION`
benchmark could therefore improve by 35% while everyday `verify.sh` still boots everything, and this
milestone would look finished without having helped anyone. Closing that gap is a task below, not a
footnote.

**And today the workflow does not select those tests at all.** Planning a real change to
`src/user/services/core/src/permission_manager.rs` selects 9 build keys and ZERO kernel tests, then
emits `./test.sh --arch x86_64` - the whole suite, with no history key to account it against. The
reason is in the declarations: eleven of the twelve permission tests carry
`covers = ["kernel", "services"]`, generic strings, and the twelfth carries a tool-specific list of
its own - while their neighbours in the same file carry `bin.imgview`, `bin.lico` and `bin.imgconv`.
What all twelve have in common is that `bin.permission_manager` appears nowhere in the file, so
nothing connects the source file to the tests that exercise it. `commands.rs` then reports
the target as `unenumerated` when what actually happened is "enumerated, nothing selected", which
hides the gap rather than escalating it.

That is upstream of everything else here. A cheaper fixture and a smarter handoff would not help this
workflow by one second, because it never chooses those tests to begin with. Closing it is a Phase 0
task below.

Three different test counts appear in this tree and they are not interchangeable: source tagged
descriptors, unique kernel checks across architectures, and the runnable per-target set
`commands.rs` actually divides by. Only the last one decides a handoff. Any figure quoted below is
the per-target one, and the protocol re-reads it rather than trusting this paragraph.

The timings in this section are diagnostic observations from the investigation, not BPv1 acceptance
evidence. They were not collected under the provenance, sampling and state-restoration rules below
and therefore cannot close any task or inequality. Phase 0 must reproduce or supersede them from the
frozen revisions. Their purpose here is to explain why the work exists, not to serve as a denominator.

### Corrections carried from earlier drafts

Written down because the first draft would have built a cache and a target-passing API around a bug
that a mode check removes:

- The three-target ELF sweep in `preload_metrics` and `generate_report` is real, but the inventory
  branch never reaches it; the sweep runs because the SELF-TEST invokes a full `--check`. Caching the
  inventory result and scoping it to one target were answers to a misdiagnosis, and are gone.
- Target scoping does not apply anyway: the inventory is an architecture-invariant name check, not a
  check of per-target artifacts.
- `applications` is a module prefix in the test IDs, not a tag; the tag list is `define_test_tags!`
  in `src/kernel/tests.rs` and contains no such tag.
- 16 timed `applications` tests, not 15, and not all are shell pipelines - the slowest at 26 s is
  `imgconv_governed_working_set_is_measured`, and there are audio scenarios among them.
- `executables=95/0` is a build cache-hit count for dynamic volume programs, not the number of
  executables the report inspects; the report works with 64 providers and 74 tools per target.
- "Sharding is the only way past 212 s" was wrong, and the eleven identical fixtures are why.

Line numbers are deliberately absent below: this document will outlive them. Work from function,
recipe and test names.

determines what the baseline has to measure. A matrix written after the numbers are in is a matrix
written to fit them, and a baseline taken before the frozen sets exist cannot be compared to
anything.

#### Normative benchmark protocol BPv1

The sealed campaign, schemas and decision manifests are the executable source of truth once Phase 0
closes. The prose below defines what they must encode. Each BPv1 rule has one stable ID. Later tasks,
DoD clauses and closure rows are human-readable summaries; their normative references live in the
sealed core/resolved-rule-set crosswalk join. The validator rejects a join whose owner, pointer,
field, metric, applicability, inequality, revision class, runner assignment or evidence requirements
differ from the sealed rules.

  `src/tools/measure-dev-baseline.sh` invokes `just shared-libs`, and `src/Justfile` has no such
  recipe - only `shared-libs-verify`. It also never runs `build.sh` or the dynamic-report gate, folds
  a shared build and a kernel test into one sample, takes a single measurement, and records neither
  hardware nor load. Extend this helper into the versioned COLLECTOR with `--run <frozen-point>`.
  Its `--validate-phase0 campaign|build|guest|pair` and
  `--validate-evidence <evidence-root>` frontends must exec the separately pinned read-only validator;
  they may not source or import collector functions. Collector and validator share only the sealed
  schemas and declarative oracles. The exact commands remain frozen in the applicable manifest. The
  protocol specifies:

  - **BP.1 - `--for PATH` selects; it does not edit.** `verify.sh --for` only hands the planner a path name -
    the file is untouched - so on a clean tree the build steps of the "real workflow" sample can all
    be warm no-op hits, while a developer's actual edit to `permission_manager.rs` forces user,
    packages and volume to rebuild. Measuring the first and calling it the second is a no-op
    benchmark. Freeze a specific semantically neutral byte patch to that file and its digest in the
    GUEST Phase-0 manifest. “PRE-EDIT” means before the simulated `permission_manager.rs` edit at the
    revision being measured, not before this milestone's implementation. Baseline and post-change
    therefore each have their own canonical, unpatched, warm snapshot; the frozen patch and the
    edit-induced build-key miss/rebuild expectation are identical across them. First prepare an
    isolated worktree at the relevant revision and make it a warm, successful build; only then
    snapshot the PRE-EDIT source bytes, modes and mtimes together with the build cache and artifacts.
    Before the warm-up and before EVERY attempt, restore BOTH that revision's source snapshot and
    complete pre-edit warm cache, verify the pre-edit digests, apply the
    patch OUTSIDE the timer, verify the patched-file digest, and assert inside the timer that the
    frozen build-key misses and rebuilds actually happened. Reapplying a patch without first
    restoring the source is an invalid sample. `--for PATH` alone is a selection fixture, never
    evidence of a real edit.
  - **BP.2 - A canonical step-entry contract, restored after warm-up.** `TEST_SELECTION` is a compile-time
    test-kernel input and Cargo runs inside `executor_total_ns`. A selection-specific warm-up would
    otherwise compile outside the timer and make a cold developer selection look cheap. For every
    timed guest point, create and hash the STEP-ENTRY contract named by the GUEST manifest: host/tool
    caches may be warm, but the test-kernel, preflight, loader/image-builder and runtime-media
    hit/miss vector is explicit. Each contract has two identities. `raw_snapshot_digest` covers exact
    content, mode, size and timestamps restored within one revision/command and must match before
    every attempt of that point. `semantic_step_entry_digest_v1` is the cross-command comparator: it
    covers content/mode/size, build keys, selection-artifact presence and every mtime predicate on
    which production code branches, while normalising irrelevant absolute timestamp values. The
    schema enumerates each predicate, such as `volume_image newer_than system_disk`; an omitted
    timestamp-dependent branch is a validation failure. Completeness is checked by a pinned static
    extractor over the frozen benchmark call graph plus a boundary mutation for every discovered
    metadata comparison. The extractor output and schema must be equal as sets; a schema declaration
    alone is not proof that production has no omitted predicate.

    Run the untimed warm-up, DISCARD every mutation it made, then restore that point's raw snapshot
    before every timed attempt. The standalone twelve-ID point and the guest step inside the real
    workflow have equal semantic step-entry digests and expected hit/miss vectors; their raw snapshot
    digests are revision/command-specific and are not falsely required to contain identical absolute
    mtimes. Specifically, neither contains a selection-specific test-kernel artifact that the real
    first handoff would have to compile. To create the standalone comparator snapshot, apply the
    frozen patch and replay the composite's exact pre-guest build steps OUTSIDE the standalone timer,
    then remove/verify absence of that selection artifact. The composite reaches the same semantic
    digest by
    executing those build steps inside `verify_total_ns` and validates it at guest entry; it does not
    restore over its own freshly rebuilt outputs. Warm-up establishes host stability; it never
    changes the measured starting state.
  - **BP.3 - Artifact and helper preparation.** Run an untimed `./build.sh --arch all` before every gate
    benchmark family and before the PRE-change build/composite baseline, because the hidden
    pre-change self-test reads all three targets. The before and after gate samples use an identical
    artifact set, proven by digest. Also warm and snapshot the `system-manifest` binary, its Cargo
    target directory and `.build/state/manifest-tool.key`: `system-manifest.sh` may otherwise run
    `cargo build` inside the measured gate or build.
    Benchmark execution is exclusive with respect to `manifest-tool.lock`, and the trace proves the
    timed command waited for no competing manifest builder.
  - **BP.4 - Four explicit provenance manifests.** A source digest is required for all four families,
    produced only by the frozen subject-independent `verify-model-source-digest-v1` binary in M0.1.
    In canonical order,
    the family manifests contain a frozen UNION of external host/benchmark tools across both compared
    revisions: canonical path, SHA-256 and version for every executable/interpreter either side may
    reach, not version text alone. A pinned source/call-site extractor plus frozen success/error
    branch fixtures defines that universe; an exec trace alone covers only the path it observed. The
    union includes the runtime closure of every dynamically linked host executable. The campaign
    separately pins the
    OS/kernel, CPU model and microcode, filesystem/mount, container/VM, CPU-affinity,
    governor/turbo/power and I/O-policy identities that must remain equal across a comparison.
    Repository-built system-under-test outputs and milestone-owned fixture code instead carry their
    revision-specific source/content hashes in the family manifest; requiring those bytes to be
    equal would forbid the change being measured. Resolve and hash the full external universe
    before every sample even when that sample correctly does not execute one member. A timed
    performance attempt is never run under `strace`, ptrace, a preload tracer or the readelf
    observer. Owned scripts emit the frozen structural events they are responsible for. Separate
    untimed `exec-trace-companion` and transparent-readelf-observer attempts, from the same restored
    state and command template, record the complete exec path/argv
    multiset with the exact tracer and tracer hash frozen in the manifest. It confirms exercised
    call-path coverage and rejects an undeclared executable but cannot prove that an unexercised
    branch has no dependency; it is not timing evidence. Critical timed events and the companion
    multiset may differ across revisions only as the structural oracle says, for example when
    inventory loses all readelf calls.
    Every manifest field ending in `_roots` is an explicit canonical array, never an instruction to
    discover "relevant" paths later. A separate untimed file-access companion, using the exact
    tracer/hash and branch corpus frozen in the manifest, proves every cache/state access that can
    affect a frozen hit/miss predicate is contained in one declared root. The validator rejects
    duplicates, ancestor/child aliases, escape paths and an omission fixture for each required root
    class.
    At minimum the universe covers
    bash, `llvm-readelf`, jq, awk, sed, sort, stat, sha tools, cmp, diff, Cargo, rustc, linker and the
    QEMU/image tools whenever either side can reach them. Baseline and after performance samples require
    byte-identical external-tool UNION inventories. There is one deliberately narrow exception to the generic shim
    rule: `transparent-readelf-observer-v1` is untimed structural instrumentation, not a test proxy.
    M0.2B
    freezes its source/blob hash, resolved path and the underlying real `llvm-readelf` path/hash before
    M0.9B. It records only mode and canonical input path, delegates every call to that pinned binary,
    and preserves stdin, stdout, stderr and exit/signal status byte-for-byte. A differential regression
    proves those properties. Its companion traces are collected on both revisions from the same
    restored state, but every timed GATE arm invokes the unwrapped real tool directly. The observer
    remains in the frozen UNION for companion provenance and is always timing-ineligible. A
    perturbing/failing proxy, any other shim, or any changed observer is typed as a nested
    `fixture_class=perturbing-regression` execution. It may run only against the frozen bounded
    temporary graph inside `dynamic-report-regressions`, never against production artifacts and
    never as the tool for a production-gate sample. Its own path/hash/call trace is recorded. The
    standalone regression-gate and actual-combined top-level attempts are respectively typed
    `measurement_class=regression-gate-budget` and `measurement_class=combined-default-budget`; their
    `command_total_ns` values remain performance evidence because they intentionally measure the cost
    a default developer run pays, including that bounded subphase. Neither class reclassifies its
    nested proxy as production evidence or permits that proxy in a
    `measurement_class=production-gate` attempt, which contains no wrapper at all.
    Family-specific fields are:

    - GATE: every current-object reference and its `.build-key`/`.sha256` sidecars; content hashes of
      every referenced ET_REL object, provider library and all 74 tool executables for all targets;
      manifest JSON; `TOOL_WAVES` and `WAVE_TAGS`; all tracked TSVs; `system-manifest` binary/key/cache;
      exact command and environment.
    - BUILD: the complete fingerprinted pre-run output and artifact-cache trees, including content,
      mode, size and mtime; every Cargo cache root in the manifest's explicit
      `build_cargo_cache_roots` list; `.build/state/warm-$target.state` and
      `.inputs`; exe-start state; `system-manifest` binary/key/cache; exact command; and, for every
      PRE-change build that invokes hidden inventory, the entire GATE set above. The benchmark's
      content digest is independent of the production path/size/mtime fingerprint.
    - TEST: test kernel, boot image, volume, registry, exact ID selection, every restored writable
      runtime image with content/mode/size/mtime, Cargo/preflight/loader/image-builder caches, exact
      QEMU argv, firmware, timing-event log and proof of the prescribed cache hits or misses.
    - COMPOSITE: every BUILD, GATE and TEST field actually reached by the frozen `verify.sh` command,
      plus `verify-history.json`, `verify-trust.json`, `verify-shadow.json`, their age/clock policy,
      the model hash and the exact planner output. “Union of all of them” is not a substitute for
      enumerating these fields in the evidence schema.

  - **BP.5 - Six timing fields, with one owner for every criterion.** All intervals use the one host
    monotonic nanosecond clock implementation and resolved binary/library closure frozen by the
    campaign; `date +%s%N` is wall clock and does not satisfy this contract.
    `command_total_ns` measures the complete top-level build or gate command.
    `report_stage_ns` is owned by `build-shared.sh` and runs from immediately before invoking
    `check-dynamic-report.sh --check-inventory` until that child's status and diagnostics have been
    captured on every match, refresh-required and fatal path, excluding final summary rendering.
    In the post-change summary schema the field is always present: it is exactly unsigned integer
    zero iff `inventory_status=not-run`, and is a positive unsigned integer iff inventory was invoked
    and status is `match`, `refresh-required` or `fatal`. A branch with no build-shared summary carries
    outer `inventory_outcome=not-applicable` and no invented report-stage value.
    `executor_total_ns` measures the complete `./test.sh` guest executor including preflight, test
    kernel compilation, loader build and image assembly. `qemu_to_suite_ns` is host-monotonic time
    from immediately before QEMU process spawn to host receipt of the versioned machine
    `suite_completed` event. `scenario_to_suite_ns` runs from host receipt of machine
    `suite_started` to host receipt of `suite_completed`. Human prose markers and guest TSC values
    are never timer boundaries. Both fields are nullable after an incomplete/failed suite and
    mandatory after completed success. `verify_total_ns` measures the complete
    `verify.sh` command. The existing 226-ID, twelve-ID, full-suite and singleton performance
    criteria, and the CostModel/handoff, use `executor_total_ns`. The composite 65% criterion uses
    `verify_total_ns`. Workflow-versus-standalone guest equivalence compares `executor_total_ns`;
    the QEMU and scenario fields are mandatory attribution evidence, not alternative pass criteria.
    A guest-only target, if later desired, needs its own pre-frozen inequality.
  - **BP.6 - Raw-ancestor outer controls prevent instrumentation from becoming the speed-up.** M0.8I is
    present on both sides of the detailed StepResult comparison, but that alone does not prove it is
    cheap: a large constant overhead could inflate the instrumented baseline and make a no-better
    developer result pass a ratio. For every DT.4 acceptance selection (226, twelve, full and every
    representative singleton), the harness also collects a first-five
    `legacy-uninstrumented-control` directly on the exact common unoptimised ancestor. It measures
    host-monotonic process spawn-to-reap as `legacy_executor_outer_ns`, using the same command,
    revision-specific STEP-ENTRY algorithm and expected hit/miss vector but no M0.8I bytes. The raw
    ancestor composite likewise records `legacy_verify_outer_ns` around the complete real patched
    `verify.sh` command. Its frozen empty/age-invariant verification state contains no timestamp near
    a freshness boundary, every attempt proves the same exact plan/level, and actual wall epoch is
    archived; it does not pretend the raw ancestor understands `VERIFY_NOW_EPOCH`.

    These controls are valid legacy performance evidence with exact command/selection/catalog,
    successful exit, complete serial log and cache provenance, but never StepResult, history or
    fitter input. Every comparison uses the same timer boundary on both sides. DT.4 compares raw
    `legacy_executor_outer_ns` only with post-change `executor_outer_control_ns`, and compares M0.8I
    baseline `executor_total_ns` only with post-change `executor_total_ns`. DT.5 compares raw
    `legacy_verify_outer_ns` and instrumented `verify_total_ns` with the corresponding post-change
    harness-owned `verify_total_ns`. Each ratio and D0.4 practical-separation test must pass
    independently;
    neither denominator may be selected post hoc. Every instrumented test attempt also
    has an independent harness-owned spawn-to-reap `executor_outer_control_ns`. Its difference from
    `executor_total_ns` must satisfy the absolute/relative tolerance frozen in Phase 0, before and
    after, proving that preflight, compilation or shutdown was not moved outside the acceptance
    timer. `verify_total_ns` is itself the harness-owned outer boundary.
  - **BP.7 - Warm-up and repetition.** Use one untimed warm-up per distinct command and
    `TEST_SELECTION`, arm and subject revision; archive it as `sampling_role=warmup`, discard its
    mutations, restore the canonical command/selection entry snapshot, then take the first exactly
    five valid timed slots from at most eight timed slots PER POINT AND ARM. A changed selection or
    arm gets its own warm-up, but no artifact produced by it leaks into a timed slot. M0.9B and M0.9G
    record the preregistered initial baselines. Every performance collection, including initial
    baseline, FIT and held-out, follows its protected-CI-attested `sampling-schedule` before its first
    timing. Later ratios reconstruct the sealed BEFORE revision and replay all arms contemporaneously;
    raw/instrumented/post guest comparisons and old-full/new-full/new-combined gate comparisons use
    explicit three-arm orders. An environmentally invalid slot is retried in place and does not
    reshuffle later slots. The initial baseline is a drift canary: its replay median must satisfy
    campaign field `baseline_drift_bound_v1` before the comparison is eligible. It is never silently
    replaced by a more convenient historical or replayed denominator.
  - **BP.8 - Environment PRESCRIBED, not merely recorded.** Recording a behaviour-changing variable does not
    make the sample valid, it documents an invalid one. In every performance-eligible template,
    `DYNAMIC_REPORT_SELF_TEST` and `DYNAMIC_REPORT_OVERRIDE` are unconditionally unset - the first
    removes the very second sweep being measured, the second changes what is compared. The explicit
    M1.1 hostile-environment regressions are typed `fixture_class=hostile-env-regression`, may set the
    named legacy/reserved variables only for their frozen functional cases, and are never timing or
    ordinary-production evidence. `LIBER_IMAGE_REBUILD` is explicitly off; a
    rebuild is a different scenario, not a slower warm build. `SMP`, `TEST_TIMEOUT`, the accelerator
    and the exact `RUSTFLAGS` byte value, including explicit absence, are pinned, and `LC_ALL=C` is
    set. Construct the command
    environment from scratch with `env -i` and the Phase-0 ALLOWLIST rather than deleting a list of
    known offenders - `LIBER_DEVELOPMENT`, `LIBER_VERBOSE`, `MEM`, `QEMU_EXTRA` and `UEFI`
    are already outside the current list, and the next variable added to the tree would be too.
    An inherited `VERIFY_NOW_EPOCH` is NEVER an input: ordinary `verify.sh` rejects it before
    planning. Instrumented GUEST/COMPOSITE templates instead pass the explicit
    `--bpv1-context <ATTEMPT_DIR>/bpv1-context.json` capability. This is an anti-accident and
    benchmark-replay boundary, not a security boundary against a caller who can modify the repository
    and state root. The harness creates the canonical record mode 0600 with a cryptographically random
    256-bit nonce and a harness-minted `top_level_invocation_id`. It binds both to the locked GUEST
    manifest hash, collector-owned `collection_attempt_id`, subject revision, isolated
    `state_lineage_id`, state root and unsigned epoch. Before spawning top-level `verify.sh`, the
    harness records the digest in an evidence-local `BenchmarkContextLease`; this is not the
    production per-step `StepPending` journal. Under the lease lock, `verify.sh` validates all bindings and
    atomically marks the nonce consumed before planning and supplying the epoch internally to the
    model. Every later `StepPending` names its parent `top_level_invocation_id`. The
    flag/context is absent from raw-ancestor controls and BUILD/GATE. Missing, foreign, copied,
    concurrently replayed, already-consumed or malformed context is RED, so merely allowlisting or
    hand-setting a variable cannot change an ordinary plan.
    `LIBER_TIMING_LOG` is not inherited: the harness sets it to a fresh, unique evidence path for
    each attempt. Archive the raw effective `env -0` for audit. For cross-attempt comparison,
    validate every dynamic evidence/result path is under its assigned attempt directory, replace
    only that prefix with a typed placeholder, and hash the normalised
    `env -0 | LC_ALL=C sort -z` stream; retain both raw and normalised forms. Digest
    the firmware in use (OVMF, AAVMF, U-Boot) alongside it. Resolve every member of the frozen UNION
    tool universe through the frozen PATH before timing and compare its path/hash inventory
    byte-for-byte across the pair; do not confuse resolution with the untimed exec-trace companion.
    Host, accelerator, CPU affinity/governor/turbo/power policy, kernel, microcode and filesystem are
    held equal across compared samples rather than noted afterwards. "Equal load" needs a rule rather
    than a hope: record load average, runnable queue, steal, iowait and the frozen thermal/frequency
    observations before and at the campaign-owned frozen cadence throughout each sample. Discard and
    retry a slot only when the matching closed
    `environmental_invalidation_policy_v1` reason/threshold fires; archive the complete time series
    and reason enum. Any other anomaly is a functional failure. The paired block schedule in BP.7 is
    mandatory for every post-change ratio comparison.
  - **BP.9 - Structural confirmation, with the counts named.** Pre-change: the inventory check inside a
    build performs ONE completed all-target sweep, and a standalone `--check` performs TWO.
    Post-change: inventory performs ZERO and `--check` performs ONE. Confirm each by count, not by
    assumption - and beware the trap: if any foreign target's artifacts are missing, the self-test
    child fails EARLY and the build stays green, so a baseline taken then measures a cheap failure
    rather than the 208 seconds being claimed. That is why the pre-change build and composite
    provenance must include the whole gate set - all three targets, the manifest and wave map, and
    the tracked TSVs - and not only the build cache and outputs.
  - **BP.10 - A frozen sampling protocol, so a run cannot be quietly dropped.** Fix the numbers in
    advance: the first exactly five valid timed slots after the warm-up, at most eight timed slots per
    point and arm.
    Compute the median from those five and no other subset. Archive every
    attempt including warm-up and rejected slots with the exact role/reason. A functional failure
    stops and seals the collection with a typed failed summary; a rerun under the same schedule is
    allowed only for a reason in the campaign-owned
    `environmental_invalidation_policy_v1`. A variable-sized median is an invitation to keep going
    until the numbers look right. D0.4 is deliberately an engineering practical-separation guard,
    not a claim of a population p-value, confidence level or statistical power.
  - **BP.11 - Sample validity.** A sample counts only if the command reached its DEFINED successful outcome;
    for test runs, only if a fresh validated `StepResult v1` proves a completed successful suite and
    the executed IDs match the frozen list exactly. The only exception is a typed raw-ancestor
    `legacy-uninstrumented-control`, whose ancestor cannot emit StepResult: its exact frozen command,
    catalog/selection descriptor, successful process exit, complete serial log and cache trace are
    all required, and it is accepted only as a BEFORE outer-time denominator. Human output is never
    an accounting input. A timeout, a
    stall or an early exit is not a slow sample, it is not
    a sample. "Exited zero" is the WRONG test for `verify.sh`: the permission-manager case is
    `STALE 16` today and `verify.sh` deliberately exits 5 for a stale-but-successful run.
  - **BP.12 - The stale-handling option, and there is only one that works.** Always pass `--allow-shadow`,
    expect exit 0 - the flag SUPPRESSES the exit 5, it does not make 5 a success - and confirm the
    one exact baseline level and one exact after level frozen separately in the GUEST manifest, not
    an “STALE or SHADOW” disjunction. The prepared-TRUSTED-state alternative is not
    available: `model_hash` is computed over every check's `covers` list, and a trust certificate is
    valid only for one exact hash, so the `covers` change this milestone makes invalidates any
    snapshot that spanned it. Recording that here saves the next person from discovering it halfway
    through a measurement.
  - **BP.13 - The writable runtime images, restored per sample too.** `qemu_prepare_system_disk` recreates
    the virtio disk only when it is missing, the wrong size, or older than the factory volume - so
    with an unchanged volume image two samples in a row REUSE the disk the first one wrote to, and
    the second starts from a different filesystem. The same applies to the FAT, ISO, UDF and USB
    media. The frozen strategy is byte-for-byte restoration of every writable image from a canonical
    snapshot before the warm-up and again before each timed sample, OUTSIDE the timed interval;
    copy-on-write is not an alternative within this baseline. Digest the actual pre-run images rather
    than the factory volume they came from.
    Restore size, mode AND mtime with the contents: the decision to re-copy the system disk is
    `volume_image -nt disk`, so a restored image with a fresh timestamp silently changes what the
    next run does.
  - **BP.14 - A frozen verification state, restored per sample.** `verify.sh` reads and WRITES
    `verify-history.json`, and its answer also depends on `verify-trust.json`, `verify-shadow.json`,
    and, after M3, the vNext pending-attempt journal/sequence, record ages and the model hash - so
    every sample changes the input of the next one. Archive one canonical
    `state_snapshot_template_v1` containing the three legacy files and, when present, the initial
    vNext store, age policy and no live attempt. Restore that byte-identical template before the
    warm-up and each timed sample. Then, under the benchmark harness's evidence-local template-fork
    lock, not the production StateStore lock, and before the command starts,
    atomically fork a per-run state root with a new random `state_lineage_id`, `attempt_seq=0` and a
    binding to `state_template_digest`. The template digest is the cross-run comparator; the
    per-lineage raw state digest intentionally includes the unique ID and must not equal another
    run's digest. The ID is state data, not a command-template placeholder. Run the planner through
    the validated `BenchmarkContextLease` supplied by the isolated harness. Timestamp rebasing is not
    an alternative within this baseline. Carry template, lineage, frozen-clock and model digests in the
    provenance. Without this, five runs measure five different experiments without saying so.
    `attempt_seq` is monotonic and unique within one lineage, while collection, top-level-invocation and
    step-attempt IDs prevent two restored lineages or identity levels from being conflated.

    The instrumented baseline and after revisions actually implement the narrow benchmark seam:
    ordinary no-context execution uses the existing `SystemTime` path unchanged; inherited
    `VERIFY_NOW_EPOCH` fails before a plan exists; only a valid campaign/decision/collection-attempt/
    top-level-invocation/state-bound `BenchmarkContextLease`
    supplies the canonical unsigned epoch through an explicit typed clock API. The no-context path's
    observable plan, output, state bytes and exit status equal the ancestor contract; the document
    does not claim untestable universal "byte-for-behaviour" equivalence. The model never reads
    that inherited environment variable directly. Malformed, signed, overflowed, replayed or
    trailing input fails closed. A near-cutoff regression proves the validated context changes the
    plan exactly as predicted and the same environment without capability cannot.

    An isolated git worktree is the frozen state-isolation strategy for both wiring and performance
    runs, not an optional state-root alternative. The three legacy files and vNext journal/sequence
    resolve under `repo_root.join(".build/state/...")`, so the worktree gets its own canonical
    `.build/state`; the pre-change snapshot records the journal as absent/not-applicable, the
    post-change snapshot restores its canonical initial bytes, and the validator proves the developer
    worktree's corresponding live files remain byte-identical.
  - **BP.15 - Timer resolution.** `build-shared.sh` computes `report_seconds` from bash's integer `SECONDS`,
    where a printed `2` can be nearly three. BOTH places carrying a 2-second criterion - the
    standalone inventory benchmark and the reporting stage inside the build summary - need a
    monotonic sub-second timer. Adding one only to the harness leaves the stage claim unprovable.
    Bump the summary schema and emit the acceptance wire field as strict unsigned integer
    `report_stage_ns=<nanoseconds>` plus `build_shared_invocation_id`; do not parse a rounded human
    seconds
    field for acceptance. If a `reports_s` display is retained, derive it from the integer and verify
    exact formatting consistency, but it has no policy role. Require exactly one summary per expected
    `(collection_attempt_id, target, build_shared_invocation_id)` in the collector-bound summary
    envelope and exactly one of every required field within it; `--arch all`
    and a composite command legitimately have several distinct summaries. Reject missing, duplicate,
    signed, decimal, overflowed, trailing-garbage or malformed nanosecond fields. The writer/reader
    boundary regression proves `1999000000` and `2000000000` pass the 2-second bound,
    `2001000000` fails, and `2900000000` remains exact rather than becoming two seconds.
    Historical pre-change summaries do not contain the new schema/invocation ID. The harness assigns
    each only to an expected invocation proven by the frozen command trace and stores a separately
    typed `legacy-normalised` record; it may not pretend the old line carried a post-change field.
  - **BP.16 - What "raw samples" means.** Archive each run's individual duration, exit status, log,
    event stream and attempt manifest under the exact external raw root defined by M0.1. A hash proves
    nothing anyone can read later, and a path under `.build/logs` is overwritten by the next run. A
    mixture of whole logs and medians is not evidence.

- **DT.10 - Failure/effective-freshness semantics.** Failure regressions start from a genuinely
  current/fresh record and distinguish four cases. Failure before
  `suite_started` is a valid empty event prefix, refreshes nothing and blocks the whole requested set.
  A mid-suite assertion failure refreshes exactly prior passed IDs, reports only the attributed
  assertion ID as assertion-failed, emits no later guest event, terminates the process unsuccessfully
  and leaves later IDs not-started. An assertion followed by exit zero or another event is a protocol
  failure and refreshes nothing.
  A timeout/signal/QEMU loss refreshes exactly prior passed IDs, marks the active ID interrupted
  rather than assertion-failed, records both supervisor cause and wait status, and leaves later IDs
  not-started. If every test passed but `suite_completed` is missing, successful provenance may be
  retained but a `completion-missing` step blocker covers the entire requested set. A failed atomic
  step updates no key
  and reports the step, not an invented ID. None changes cost, cost epoch, bundle, surcharge or fixed
  overshoot. Every non-passing requested ID becomes effectively non-fresh because the new unresolved
  failure/incomplete evidence is newer than its last pass; a later validated pass resolves it. A
  passing whole-suite promotion has requested = started = passed = complete per-target catalog.

  backwards wall-clock timestamps. A missing/invalid result leaves the host-written pending blocker;
