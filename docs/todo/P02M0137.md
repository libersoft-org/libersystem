# P02M0137 - The build spends its time re-checking what did not change

Status: TOOLING. NOT A PHASE-2 COMPLETION GATE.

## Why

A build in which NOTHING changed takes 3 minutes 51 seconds, and 208 of those seconds are one
stage. The build's own summary reports it:

```
stages=source:0, graph:0, providers:0, consumers:0, reports:208
providers=64/0  objects=0/0  executables=95/0
```

Those zeros are what `build-shared.sh` prints for stages it did not have to do - through the warm
snapshot, through per-item caches, or both; the summary does not distinguish them and this milestone
does not need it to. Nothing was rebuilt, the whole rest of the build is about 25 seconds, and the
reporting stage ran anyway.

**The expensive thing is not the check the build asks for.** `check-dynamic-report.sh` calls
`self_test` BEFORE it parses its mode, and `self_test` recursively invokes `"$0" --check`, the full
report-set generation and comparison over all three targets' artifacts. The `--check-inventory`
branch the build actually wants compares tool NAMES and exits, and never reaches `llvm-readelf` at
all. Measured with the self-test suppressed:

```
$ time DYNAMIC_REPORT_SELF_TEST=1 src/tools/check-dynamic-report.sh --check-inventory
dynamic-report: 74 checked tools match the manifest
real 0m0.156s
```

So the build pays roughly 208 seconds for 0.16 seconds of work it asked for. `--write` pays it too,
and so does an invalid argument - the usage error is printed after the full gate has run. `--arch
all` pays it once per target.

And what those 208 seconds buy is a WARNING: `check_dynamic_report_inventory` prints "checked dynamic
reports need refresh" to stderr and leaves the build status at 0.

The self-test itself is sound in intent - it hands the comparator a mutated report and requires it to
object, which is the right instinct and the reason this tree can trust the gate at all. Three things
about it are wrong. It runs for every mode rather than for the one it protects. It treats ANY
non-zero exit of the child as proof that the comparison worked, so a missing artifact or a parse
error is indistinguishable from "the comparator caught the mutation" - a green answer that is not
evidence, which is the failure mode this tree names most often. And `--check` performs the whole ELF
sweep twice, once in the self-test child and once for the real comparison, which is why
`docs/DEBUG.md` records the full check at about 500 seconds.

**The gate reads artifacts; it does not build them.** `generate_report` resolves each tool to
`$build_root/image/$target/$destination` and fails when it is absent, and `provider_metrics` does the
same for provider libraries. Everything below therefore says "report-set generation" or "ELF sweep",
never "generates the targets" - and the benchmark protocol has to prepare all three targets'
artifacts before it can time the gate at all. `docs/DYNAMIC_LINKING.md` currently says the gate
"rebuilds", which is part of what this milestone corrects.

**The test half is a different problem, and it is not serialisation.** An x86_64 run of
`process,memory,paging,scheduler,service,smp,kernel` is 226 tests in 283 seconds. Of the 24 tests
with a recorded duration, 16 are under `kernel.applications` and account for at least 212 s - the
per-test figures are printed as whole seconds, so every total here is a lower bound. But they are not
sixteen fixtures: twelve call `run_permission_scenario`, and ELEVEN of those twelve - one `Probes`
and ten `GovernedTools` - do exactly the same work and return at the same early exit, before the
branch that only `ScopedGrants` continues past. The helper builds the same storage/process/permission
topology, pipelines, command tools and real shell every time. Those twelve tests are at least 169 s
of the 283 s run.

Narrow selections are already cheap by comparison: `handle,object,channel,ipc` is 67 tests in 10
seconds, `scheduler,channel,ipc,smp,kernel` is 111 tests in 13 seconds.

**A faster benchmark is not the goal; a faster workflow is.** `commands.rs` decides whether to hand
the runner an exact ID list by COUNT - `selected.len() * 5 < total * 4` - against a PER-TARGET total
it computes from each test's architecture list. Asked for a real plan, the model reports 265 runnable
x86_64 tests (255 on aarch64 and riscv64), so the break-even is 211: a selection of 212 or more runs
the whole suite. The 226-ID selection measured above is one of them. A hand-driven `TEST_SELECTION`
benchmark could therefore improve by 35% while everyday `verify.sh` still boots everything, and this
milestone would look finished without having helped anyone. Closing that gap is a task below, not a
footnote.

**And today the workflow does not select those tests at all.** Planning a real change to
`src/user/services/core/src/permission_manager.rs` selects 9 build keys and ZERO kernel tests, then
emits `./test.sh --arch x86_64` - the whole suite, with no history key to account it against. The
reason is in the declarations: eleven of the twelve permission tests carry
`covers = ["kernel", "services"]`, generic strings, and the twelfth carries a tool-specific list of
its own - while their neighbours in the same file carry `bin.imgview`, `bin.lico` and `bin.imgconv`.
What all twelve have in common is that `bin.permission_manager` appears nowhere in the file, so
nothing connects the source file to the tests that exercise it. `commands.rs` then reports
the target as `unenumerated` when what actually happened is "enumerated, nothing selected", which
hides the gap rather than escalating it.

That is upstream of everything else here. A cheaper fixture and a smarter handoff would not help this
workflow by one second, because it never chooses those tests to begin with. Closing it is a Phase 0
task below.

Three different test counts appear in this tree and they are not interchangeable: source tagged
descriptors, unique kernel checks across architectures, and the runnable per-target set
`commands.rs` actually divides by. Only the last one decides a handoff. Any figure quoted below is
the per-target one, and the protocol re-reads it rather than trusting this paragraph.

### Corrections carried from earlier drafts

Written down because the first draft would have built a cache and a target-passing API around a bug
that a mode check removes:

- The three-target ELF sweep in `preload_metrics` and `generate_report` is real, but the inventory
  branch never reaches it; the sweep runs because the SELF-TEST invokes a full `--check`. Caching the
  inventory result and scoping it to one target were answers to a misdiagnosis, and are gone.
- Target scoping does not apply anyway: the inventory is an architecture-invariant name check, not a
  check of per-target artifacts.
- `applications` is a module prefix in the test IDs, not a tag; the tag list is `define_test_tags!`
  in `src/kernel/tests.rs` and contains no such tag.
- 16 timed `applications` tests, not 15, and not all are shell pipelines - the slowest at 26 s is
  `imgconv_governed_working_set_is_measured`, and there are audio scenarios among them.
- `executables=95/0` is a build cache-hit count for dynamic volume programs, not the number of
  executables the report inspects; the report works with 64 providers and 74 tools per target.
- "Sharding is the only way past 212 s" was wrong, and the eleven identical fixtures are why.

Line numbers are deliberately absent below: this document will outlive them. Work from function,
recipe and test names.

    make the sample valid, it documents an invalid one. `DYNAMIC_REPORT_SELF_TEST` and
    `DYNAMIC_REPORT_OVERRIDE` are unconditionally unset - the first removes the very second sweep
    being measured, the second changes what is compared. `LIBER_IMAGE_REBUILD` is explicitly off; a
    rebuild is a different scenario, not a slower warm build. `SMP`, `TEST_TIMEOUT`, the accelerator
    and any relevant `RUSTFLAGS` are pinned, and `LC_ALL=C` is set. Use an ALLOWLIST rather than a
    list of known offenders - `LIBER_DEVELOPMENT`, `LIBER_TIMING_LOG` and `LIBER_VERBOSE` are already
    outside the current list, and the next variable added to the tree would be too. Host, accelerator and CPU
    governor are held equal across compared samples rather than noted afterwards, and "equal load"
    needs a rule rather than a hope: record the one-minute load average before each sample and
    DISCARD any sample taken above a stated ceiling, re-running it instead of averaging it in.
  - **Structural confirmation, so the 60% target has an honest denominator.** The pre-change gate
    baseline must be confirmed to perform two sweeps and the post-change one exactly one.
  - **Sample validity.** A sample counts only if the command reached its DEFINED successful outcome;
    for test runs, only if the runner printed `test suite complete: N passed` and the executed IDs
    match the frozen list exactly. A timeout, a stall or an early exit is not a slow sample, it is not
    a sample. "Exited zero" is the WRONG test for `verify.sh`: the permission-manager case is
    `STALE 16` today and `verify.sh` deliberately exits 5 for a stale-but-successful run.
  - **The stale-handling option, and there is only one that works.** Always pass `--allow-shadow`,
    expect exit 0 - the flag SUPPRESSES the exit 5, it does not make 5 a success - and confirm the
    expected STALE or SHADOW level by reading the log. The prepared-TRUSTED-state alternative is not
    available: `model_hash` is computed over every check's `covers` list, and a trust certificate is
    valid only for one exact hash, so the `covers` change this milestone makes invalidates any
    snapshot that spanned it. Recording that here saves the next person from discovering it halfway
    through a measurement.
  - **The writable runtime images, restored per sample too.** `qemu_prepare_system_disk` recreates
    the virtio disk only when it is missing, the wrong size, or older than the factory volume - so
    with an unchanged volume image two samples in a row REUSE the disk the first one wrote to, and
    the second starts from a different filesystem. The same applies to the FAT, ISO, UDF and USB
    media. Before the warm-up and before each timed sample, either create a fresh copy-on-write
    overlay or restore every writable image from a canonical snapshot, do it OUTSIDE the timed
    interval, and digest the actual pre-run images rather than the factory volume they came from.
  - **A frozen verification state, restored per sample.** `verify.sh` reads and WRITES
    `verify-history.json`, and its answer also depends on `verify-trust.json`, `verify-shadow.json`,
    record ages and the model hash - so every sample changes the input of the next one. Archive one
    initial snapshot of all three files plus the age and time policy, restore it before the warm-up
    and before each timed sample, and carry a state and model digest in the provenance. Without this,
    three runs of a benchmark measure three different experiments.

    An ISOLATED state root is mandatory for the performance runs, not only for the wiring test. All
    three files resolve to `repo_root.join(".build/state/...")`, so a benchmark that does not
    relocate them is writing the developer's live history - and a crash or a concurrent `verify.sh`
    then corrupts it. Use a separate repo root or a git worktree, or add a state-root option and use
    it.
  - **Timer resolution.** `build-shared.sh` computes `report_seconds` from bash's integer `SECONDS`,
    where a printed `2` can be nearly three. BOTH places carrying a 2-second criterion - the
    standalone inventory benchmark and the reporting stage inside the build summary - need a
    monotonic sub-second timer. Adding one to the benchmark while the stage still prints an integer
    leaves the criterion unprovable exactly where it is claimed.
  - **What "raw samples" means.** Each run's individual duration and exit status, plus its log
    ARCHIVED somewhere durable - a hash proves nothing anyone can read later, and a path under
    `.build/logs` is overwritten by the next run. Not a mixture of whole logs and medians.

### The build and the gate

- [ ] **Parse the mode first, and make the self-test depend on it.** Move mode parsing and validation
  ahead of `self_test`, and run the self-test only for `--check`. Complete the mode contract while
  the code is open: no argument means `--check`; an unknown or surplus argument fails with a usage
  status before anything is generated; `--write` performs exactly one report-set generation and no
  comparator self-test; `--check-inventory` performs zero `llvm-readelf` invocations and works with
  the binary absent from `PATH`. No new PUBLIC flag or environment variable - the build keeps asking
  for the cheap inventory warning exactly as it does today - but the self-test may keep a private
  injection mechanism, which is how it stays safe.

- [ ] **Sweep once in the full gate, and keep the self-test end-to-end.** After the change, one
  `--check` performs: ONE ELF sweep; exactly ONE authoritative comparison against the tracked TSVs;
  and three negative comparison probes over copies of those same candidates, with no second sweep.
  The risk in the refactor is losing what the recursive call currently proves - that the PUBLIC
  `--check` path actually reaches the comparison. Splitting into `generate_reports` and
  `compare_reports` can leave a well-tested comparator that the public entry point has quietly
  stopped calling. So either drive the negative fixture through the same public path a real `--check`
  takes, or add a separate regression test on the public wiring, and say in the script which.

  The mutation contract, spelled out because "hand it a corrupted report" is not specific enough to
  implement twice the same way. Each of the three reports gets its own probe. Each mutation starts
  from the candidate just generated, in a unique temporary directory; changes exactly one
  syntactically valid field; proves with `cmp` that the mutation landed and that the other two
  reports are byte-identical; requires the comparison to fail with a specific `report mismatch`
  status AND diagnostic, not merely a non-zero exit; and never touches a tracked TSV, a `.build`
  artifact, or a candidate the real check will later use.

- [ ] **Make a failing `llvm-readelf` fail the function, and test each call path.**
  `writable_load_bytes` and `immutable_load_bytes` feed a `while read` loop from
  `< <(llvm-readelf ...)`, and `provider_metrics` consumes those. `set -euo pipefail` does not apply
  to process substitution: the producer dies, the loop reads nothing, and the function returns a
  confident zero. Check the status of every relevant invocation explicitly.

  Testing by ARTIFACT CATEGORY does not prove the fix. A corrupt executable may fail first in a
  `--dyn-syms` pipeline whose status already propagates, and never reach `writable_load_bytes`; a
  corrupt provider may die at the first `-lW` and never exercise `immutable_load_bytes` or the
  provider's own `--dyn-syms`. Cover each repaired invocation path, and the reliable way to do that
  is a controlled `llvm-readelf` shim that fails only for a chosen mode - or a single shared wrapper
  that every call site goes through, tested once. A wrapper is not automatically safe: called as
  `< <(wrapper ...)` it loses its status exactly the way the current invocations do. It has to
  capture both output and status itself, and every caller has to consume it in a context that
  propagates - otherwise each consumer path needs its own test after all.

  Real corrupt fixtures still belong in the set, and each must be shown to have REACHED
  `llvm-readelf`: a truncated file or a bad magic that the existing size or hash sidecar checks
  reject first never gets to the parser, so the test proves nothing about the status it claims to
  exercise. Build consistent temporary sidecars or exercise the helper directly, and assert the
  parser was invoked. No test may damage a live `.build` file and restore it afterwards.

- [ ] **Test `--write` against a temporary output root, never the tracked TSVs.** The mode matrix has
  to run in a gate that is actually invoked, and a `--write` case pointed at the real paths would
  regenerate stale reports before the following `--check` - masking exactly the missing commit the
  gate exists to catch. Use a temporary output root or a temporary copy of the repository.

- [ ] **Say what the inventory check is responsible for - both halves of it.** Before the
  `--check-inventory` branch, the script already compares the manifest against `TOOL_WAVES`; the
  branch then compares the manifest against the x86_64 tool-name column of `DYNAMIC_EXECUTABLES.tsv`
  and requires that file to exist. So a corrupt header, a wrong metric, an aarch64 or riscv64 row, or
  damage to either aggregate report all pass. Document both invariants plus the missing-file case,
  **The decision, made here rather than deferred: the inventory check stays NAME-ONLY.** Its promise
  is exactly - the manifest agrees with `TOOL_WAVES`, the manifest's tool set agrees with the x86_64
  tool column of `DYNAMIC_EXECUTABLES.tsv`, and that file exists. Nothing about headers, metrics,
  other targets' rows, the aggregate reports, or schema. That limitation goes in the script beside
  the check, because an inventory check believed to do more than it does is worse than one known to
  do less.

  Schema is the full gate's business. `--check` compares byte-for-byte against the tracked TSVs,
  which catches any drift between the generator's output and what is committed - not the same thing
  as validating a schema in the abstract, and worth stating precisely, but it is the check that would
  fire on a malformed tracked report. A second, weaker validation in the build would duplicate it and
  give the two a chance to disagree.

  This settles the class boundary the status matrix needs, and it has to be stated in terms of what a
  name-only checker can OBSERVE. It sees a tool-set mismatch; it cannot tell whether a missing name
  came from a legitimate rename or from a corrupted row, so it must not classify by cause. Any
  detected mismatch is the green class. Schema is simply not a state this check has an opinion about.

- [ ] **Decide the status matrix, and make the build honour it.**
  `check_dynamic_report_inventory` turns every non-zero status into "checked dynamic reports need
  refresh", which swallows a syntax error, a manifest failure and an internal fault. The classes and
  their answers, to be implemented as written:

  | condition | build |
  |---|---|
  | any detected x86_64 tool-set mismatch | warning, green |
  | `DYNAMIC_EXECUTABLES.tsv` missing | warning, green |
  | manifest / `TOOL_WAVES` disagreement | RED - `dynamic-report-update` cannot fix it |
  | tool, parser or internal failure | RED |

  Schema appears in no row: it is not a state this check observes. That is the limitation stated
  above, not an omission - the full gate is what catches a malformed tracked report.

  The specific mismatch status the self-test needs carries this distinction. There is a trap to get
  right: `report_build_summary` captures `local status=$?` on entry and only THEN calls
  `check_dynamic_report_inventory`, printing that captured value as `status=`. So a build can exit
  non-zero while its own summary line reports `status=0`. Either the summary status must equal the
  final exit status, or the summary must carry a separate `inventory_status` field - decide which,
  and make the summary print in every case regardless.

- [ ] **State the policy once, precisely.** The inventory check runs in a successful untargeted
  shared-graph build; a targeted `--artifact` build and a build without shared libs do not reach it.
  What must hold universally is that NO variant of `build.sh` performs a full report-set generation.
  Write that in the script where the next person will read it.

- [ ] **Derive the wave count from one source.** The success line reads "... 15 waves and three whole

### The tests

- [ ] **Implement the frozen `covers` contract, and the zero-selected outcome with it.** This is the
  post-baseline half of the Phase 0 paper decision, and it is what makes every later measurement
  about a selection a real change produces. Add `bin.permission_manager` to all twelve permission

- [ ] **Stop rebuilding the identical permission fixture eleven times over, without weakening a
  single test.** All twelve stable IDs and every assertion stay. Two implementations are acceptable
  and the choice is this milestone's to make and record:

  - **Shared result**: the common base runs exactly once PER GUEST RUN that contains permission IDs -
    not once across twelve separate QEMU runs - and the tests share only an immutable finished
    result. Sharing a live mutable topology across `Testable::run` calls is NOT acceptable: it buys
    speed with order dependence and state leakage, which is a worse defect than the one being fixed.
    Decide and record whether the `ScopedGrants` extension runs only when its own ID is selected.
  - **Split**: the scenario is decomposed so each test performs only the work its assertions need.
    The criterion is that unrelated pipelines, shells and command tools are not run, NOT that no
    common operation ever repeats - isolated tests may each legitimately stand up a minimal
    PermissionManager topology.

  Either way, selecting one permission ID alone must still build whatever fixture that test needs,
  and the reduction must be OBSERVABLE: an exposed counter, trace or asserted maximum call count for
  the expensive setup. A 35% wall-clock improvement does not prove the scenario was not weakened by
  some other shortcut.

- [ ] **Make the handoff decision use the cost model, so the saving reaches `verify.sh`.**
  `commands.rs` decides whether to pass an exact ID list with `selected.len() * 5 < total * 4` - a
  second, count-based rule that ignores the model entirely. Against 265 runnable x86_64 tests the
  break-even is 211, so the frozen 226-ID selection is emitted as a WHOLE-SUITE run. Testing "the
  command actually emitted" would only freeze that behaviour in place.

  "Come from the same cost model" is not yet an algorithm, and there are three thresholds in the tree
  today: `plan.rs` compares estimated COSTS at 90%, `commands.rs` compares COUNTS at 80%, and
  `main.rs` prints advice at 80% of a full run. Write down, before implementing: the ratio that
  decides; what happens on a tie; what happens when history is missing or invalid; and which single
  layer OWNS the decision, with the others reading it rather than repeating it. Predetermined
  outcomes for three frozen cases can be satisfied by hardcoding, so they are a check on the policy,
  not the policy.

  The end-to-end test drives a representative `verify.sh --for ...` and asserts the command emitted
  and run - against a TEMPORARY state root with a fixed history and an isolated executor, or it will
  read and overwrite the developer's own `.build/state/verify-history.json`. Under the shared
  implementation the group cost has to reach this layer too.

  Inspecting the emitted command is not enough to prove the workflow got faster: if the predetermined
  outcome is "whole suite", the assertion passes and nothing improved. So there are TWO end-to-end
  checks and they must not be confused. The WIRING test may use a spy or stub executor and a fixed
  history - it asserts which command would run. The PERFORMANCE measurement uses a real or delegating
  executor on the frozen workflow case, is timed, records the IDs actually executed, and its emitted
  command must be one of the separately measured frozen variants. Timing a stub proves nothing about
  a workflow.

  One more thing to align while here: the share printed to the user divides by the estimate over the
  GLOBAL universe of every architecture and environment, while the planner decides per
  (architecture, environment) pair. The number a reader is asked to trust must use the same
  denominator as the decision it explains.

- [ ] **If shared is chosen, change the whole cost cycle, not just the estimator.** `record_step`
  subtracts the global fixed term once and splits the remainder EVENLY across the keys the step
  discharged - its own comment says so, and that decomposition is what makes the additive model add
  up. Add a bundle cost to the estimator alone and the fixture is counted twice: once smeared into
  every permission test's `last_seconds` by the recorder, and again as the group term. So the change
  runs the length of `record -> decomposition -> save/load -> estimate -> plan -> command`, with a
  regression test over that whole round trip rather than over the estimator in isolation. It must
  also reach `CostModel::full_suite_seconds`, which the timeout self-check uses and which would
  otherwise price a full suite with neither the bundle nor the scoped surcharge in it.

  And fixture-group membership needs ONE canonical source. A hardcoded list of twelve IDs in the test
  runner plus a second copy in the cost model will drift apart, and the day they disagree the model
  prices a group the runner no longer builds. Make membership metadata that the runner and the model
  both read, with a self-check that fails when they diverge.

  And if `ScopedGrants` runs only when its ID is selected, the shape is not one bundle but three
  terms - a base bundle for any permission ID, a scoped surcharge only for that ID, and per-test
  assertion costs - which the recorder, estimator, planner and calibration matrix must all agree on.
  This is the strongest argument for the split implementation: it keeps the model additive and none
  of this is needed.

- [ ] **Only a completed, passing step may price a test.** `verify.sh` records against every
  `PlanItemKey` the step discharged, seconds included, whether the step passed or failed - and
  `estimate` takes any record with `last_seconds > 0.0` without consulting `last_status`, while the
  staleness bound ignores it too. A timeout partway through a suite therefore marks tests that never
  ran as FRESH, prices them from a partial wall clock, and feeds that into the next exact-versus-full
  decision. The policy is the one the later task and the Definition of Done state, and it is exact rather than
  permissive: on a failed step, freshness is refreshed for precisely the IDs that finished and
  passed, and cost is not touched at all. Test
  both shapes of failure: a step that dies before its first test, and one that dies mid-suite.

- [ ] **Account for what ran, not for what was asked for.** When the count rule sends a strict subset
  to the whole suite, the emitted command drops `TEST_SELECTION` but `Step.keys` stays the ORIGINAL
  SUBSET - so the whole suite's wall clock is divided among only the selected keys, inflating their
  per-test cost and leaving every unselected test unrecorded. Five sets have to be kept apart, because a bare
  `executed IDs == accounted IDs` contradicts the success-only rule above the moment a suite dies
  partway: some IDs DID run.

  | set | meaning |
  |---|---|
  | attempted | what the command was asked to run |
  | successfully completed | what actually finished and passed |
  | freshness accounted | what may refresh the age bound |
  | cost accounted | what may update `last_seconds` |
  | failure evidence | what is reported as broken |

  For a step that PASSED, attempted, completed and accounted are one set - which is where this bug
  lives, since a promoted whole-suite run attempts and completes 265 tests while accounting only the
  selected subset. For a step that FAILED the two accounted sets come apart, and the policy is
  exact rather than permissive: freshness is refreshed for EXACTLY the IDs that finished and passed -
  not "at most", which would let an implementation refresh nothing and still comply - while COST
  stays untouched, because the step's wall clock includes a timeout and cannot price them without
  per-test timing. The
  regression starts from an existing GOOD record and drives `pass -> early failure` and
  `pass -> mid-suite failure`, asserting the failure does not overwrite the last valid cost. The
  shared-fixture round trip below does not cover any of this.

- [ ] **Verify across selections, orders and architectures - with the scope named, because TCG is
  expensive.**

  - x86_64: all twelve IDs individually, all twelve together, mixed selections, and the performance
    matrix.
  - aarch64 and riscv64: one combined twelve-ID functional run, plus at most one designated mixed
    run. No TCG singleton benchmarks unless the calibration matrix above explicitly calls for them.

  `TEST_SELECTION` only filters - the runner always uses registry order - so a single mixed run does
  not exercise ordering: place a non-permission test both BEFORE and AFTER the permission block. And
  presence alone does not detect leakage: assert a cleanup-sensitive invariant. Name the reversible
  quantities explicitly, because not all of them are: `ResourceCounter`'s `peak` is monotonic by
  design and never returns, and child Domains are held by strong references, so "domain totals return
  to baseline" is not a property that can hold. Use the `used` values that genuinely fall back, and
  state the exact moment the snapshot is taken - after the scheduler has drained and reaped, not at
  the instant the last assertion returns.
