# M0061 - Thin shell: job-control / session service + commands as binaries

Status: COMPLETE. Most commands had been shell built-ins, the shell created processes itself through
the raw `SYS_PROCESS_CREATE` / `SYS_PROCESS_LOAD` syscalls carrying `init.pkg` ELF blobs, and job
control lived inside the shell process.

*Condensed 2026-08-08.*

## What changed

- **A session / job-control service** owns the job table, the foreground job and the session
  environment, so none of it dies with the shell.
- **All process creation goes through ProcessService**, splitting mechanism from policy. It holds a
  single StorageService client - the loading mechanism, not a grantable capability - and loads each
  program from `vol://system/bin/<name>`: open, map the shared buffer, spawn from the image, unmap.
- **One system-wide permission store**, extending PermissionManager's typed manifest, rather than a
  second notion of what a program may do.
- **Every utility became its own ELF.** The shell is a thin launcher: everything except `cd` runs as
  a governed ELF through PermissionManager, with **no in-shell fallback path**. Removing the
  fallback is the part that matters - a fallback means the governed path can be broken and nobody
  notices.
- The Volume API gained directory operations (`list`, `mkdir`, `rmdir`).

## The numbers that made the split visible

Binaries are stripped (`strip -s`, roughly 30x smaller) and staged: 31 tools under `bin/` and five
non-bootstrap drivers under `drivers/`, giving a `volume.pkg` of 39 entries and about 4.2 MB.

**`init.pkg` shrank from 63 entries to 9** - the bootstrap set is only what is needed to mount the
system volume: `system_manager`, `service_manager`, `log_service`, `device_manager`,
`process_service`, `storage_service`, `virtio_blk` and two probes. `log_service` had to join that
set even though the original plan omitted it, because DeviceManager needs somewhere to report.

*(M0138 later took those nine out of the archive entirely and put them on the volume at real paths.)*
