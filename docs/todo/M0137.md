# M0137 - Build layering: compile, then package

The build works, and that is the problem: it works only when driven through `just`. Nothing in
the tree states that the kernel crate must not be built alone, or that an application cannot be
built without the shared-library step, so both are possible and neither says anything is wrong.
Twice on 2026-08-01 a new kernel was tested against a stale userspace and the result was read as
evidence about the code - once through artifacts copied into a git worktree, once by invoking
`boot/test-kernel.sh` directly and bypassing the preflight that builds userspace. Both produced
a confident, wrong diagnosis: a defect blamed on inherited code that was in fact a fresh
regression, and a fix declared broken that had simply never reached the binary.

The cause is not carelessness at the keyboard. It is that compilation and packaging are braided
together, so a partial build still yields something that looks like a system.

This milestone separates them. Compilation comes first and each piece stands alone; packaging is
a separate, final action that compiles nothing, checks that everything it needs is already
built, and refuses to produce an image when it is not. `src/user/services/manifest.toml` already
describes the userspace half of that assembly and calls itself "the only hand-edited source of
truth"; it becomes the description of the WHOLE system, and the image builder reads it rather
than carrying its own list.

- Done when: every artifact builds standalone, the manifest names the whole final assembly
  including the boot chain, packaging is a distinct step that only verifies and assembles, a
  missing library at compile time is a warning while a missing artifact at packaging time is an
  error, and a program that starts without a provider says which one is missing.

## What was true before this milestone

Measured on 2026-08-01 rather than assumed, by running each build:

| piece | builds alone? | note |
| --- | --- | --- |
| loader | yes | genuinely independent |
| kernel | yes, but silently incomplete | missing userspace ELFs are a `cargo:warning`, not an error |
| library | yes | e.g. `user/libs/image/png` |
| application with dependencies | NO | `unresolved import network_client` |

The kernel's own binary does NOT contain the userspace - an earlier note in this session said it
did, and that was wrong. `init.pkg` is written beside the kernel and handed to it by the loader
as a boot module, which the kernel finds through `boot_info`. What is coupled is the BUILD
SCRIPT: `kernel/build.rs` assembles the init package from userspace ELFs and reaches into
`.build/image/`. That is image-assembly work living in the kernel crate, and it is why building
the kernel alone appears to succeed while producing an image that cannot boot.

The application case is different in kind. `network-client` is an optional dependency behind a
`shared-image` feature, so without the shared-library step the feature is off and the import
disappears. Rust needs a library's METADATA to compile against it even when the code itself is
linked at runtime from a `.lslib`; the failure is a compile-time one wearing a packaging
problem's clothes.

## M0137a - The manifest describes the whole system

- [x] Extend `system-manifest` with a `[[boot_artifacts]]` section naming the boot chain, so the
  manifest is the final assembly of the system rather than of its userspace half only.
  Done 2026-08-01. Three kinds - `kernel`, `loader`, `init-package` - each with an owner and a
  destination in the image. Validation requires that every kind is present and that each appears
  exactly ONCE: two kernels in one image is not a configuration, it is a mistake the image
  builder would resolve by silently taking whichever it saw last. Verified by removing the
  kernel entry and watching `system-manifest check` fail with
  `boot_artifacts: no artifact provides Kernel`.
  `init.pkg` is an artifact in its own right rather than a property of the kernel, because the
  kernel binary genuinely does not contain it - only packaging joins the two.

- [x] Teach `mkimage.sh` to read the manifest instead of its own hard-coded artifact list, so
  what lands in an ISO or IMG is decided in one place.
  Done 2026-08-01. `system-manifest boot-artifacts` prints `<kind> <name> <destination>` and
  `verify_boot_artifacts` in `mkimage.sh` checks each against what is on disk, failing with the
  kind and path when one is absent. A kind the image builder cannot stage is itself an error,
  so adding an artifact to the manifest cannot be silently ignored by the builder.
  The manifest gained `volume-package` and its kernel destination was corrected from
  `boot/kernel` to `kernel`: the first version stated where the kernel OUGHT to live rather
  than where the image actually puts it, which would have made the manifest a second, wrong
  description instead of the single true one.
  Worth recording, because it is the same shape as the trap this milestone exists for: the
  presence check lived in `mkimage.sh` THREE times - once in each image builder and once at the
  top before the cache key. The first attempt replaced two of them and the failure test still
  "passed", because the surviving third check fired first and printed the old message. Verified
  properly by removing `init.pkg` and watching the manifest-driven check report
  `missing init-package` and exit 1, then rebuilding both ISO and IMG green.

## M0137b - Compilation and packaging are separate steps

- [x] Make the kernel independent of userspace on EVERY architecture, not just x86_64.
  Found while starting the extraction below, and it changed the size of this milestone: on
  aarch64 and riscv64 the kernel genuinely DID contain the userspace. Both boot files carried
  `include_bytes!(concat!(env!("OUT_DIR"), "/init.pkg"))`, because - as the comment there said -
  those machines have no bootloader to hand files over. So the kernel binary embedded the
  programs, and building the kernel required a built userspace. That is now gone.
  The packages are handed over at RUN time instead. The intended route was an initrd whose range
  the device tree carries, and it is closed by the emulator rather than by design: `dumpdtb`
  together with `-kernel` and `-initrd` SEGFAULTS this QEMU, and `-initrd` without `-kernel` is
  refused - both checked directly. The runner loads the device tree itself at a fixed address,
  so a tree it dumps could never describe an initrd it was not allowed to see.
  What replaced it follows the pattern this kernel already uses for the device tree (hint, then
  fixed address, then scan): the runner places the archive 32 MiB below the top of RAM and the
  kernel finds it by its `PKGARCH1` magic. No address has to be kept equal in two places.
  The trap worth recording is the frame allocator. The kernel holds a `&'static` slice into that
  archive for the whole boot, while the pool claims RAM up to the top - so without care it would
  hand out those frames and overwrite the userspace image WHILE it was still being loaded from
  it. The pool now stops below the archive. Verified on aarch64: found at `0x5e000000`, pool
  478 MB instead of 512, and SystemManager, LogService and DeviceManager all came up.
  Naming, corrected after review: these are not "modules". The system has a bootloader, a kernel
  and userspace programs; `bootproto::Module` is only the hand-off protocol's record for a blob,
  and the two blobs are the packages. The wrapper is `boot-packages-<arch>.pkg` and exists ONLY
  because those machines can be handed a single blob - programs are packed into two packages,
  and those two into one archive. Only the WRAPPER is redundant, and only on these machines:
  correcting a note first written here that suggested collapsing the two packages together.
  They are not two halves of one thing. `init.pkg` is an archive of EXECUTABLES the kernel
  spawns from - it loads SystemManager out of it and hands it over to spawn the rest.
  `volume.pkg` is a FILESYSTEM IMAGE: the kernel turns it into a MemoryObject, sends it as
  `RAMDISK`, and StorageService maps and serves it as the system volume. Different data, different
  consumers, and the split is what makes boot possible at all - nothing can be read from the
  volume until StorageService and the disk driver are running, and those cannot come from the
  volume they are needed to read.
  `init.pkg` holds the nine pinned programs that must run before the system volume is readable:
  `system_manager` and `service_manager` (launchers), `storage_service` and `virtio_blk` (the
  volume and the disk under it), `log_service`, `device_manager`, `process_service`, and the
  `resource_probe` / `watchdog_probe` probes. Everything else lives in `volume.pkg`.

- [ ] Move init-package assembly out of `kernel/build.rs` into a standalone step. The kernel
  crate should compile the kernel and nothing else; assembling an archive of userspace ELFs and
  reading `.build/image/` is packaging work. This is the change that removes the trap rather
  than papering over it - after it, building the kernel alone produces exactly a kernel, and
  no partial state can masquerade as a system.

- [ ] Make packaging a phase that compiles nothing. It verifies that every artifact the manifest
  names is present and current, then assembles. A missing artifact is an ERROR here, because
  this phase is the one that decides whether a bootable system exists at all - the opposite of
  the compile phase, where a missing optional library should stay a warning and let the build
  continue.

## M0137c - A program says what it is missing

- [ ] A dynamically linked program that starts without one of its providers must name the
  missing library rather than failing obscurely. Today the manifest declares each program's
  `providers` and the image installs them, but the failure mode when one is absent is not a
  message that says which.

## Explicit non-goals

Not a rewrite of the build system, a package manager, or a change to how `.lslib` providers are
resolved at runtime. Not a switch away from `just` as the driver. The point is narrow: make the
layering explicit, so that a build which cannot produce a working system says so instead of
producing something that merely looks like one.
