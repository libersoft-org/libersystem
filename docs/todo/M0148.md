# M0148 - Testing that scales with the change, not with the tree

Status: PLANNED. Nothing here changes what the tests assert; it changes which of them run, and it is
worth doing before the tool count multiplies rather than after.

The suite is honest and it is thorough. What it is not is SELECTIVE: changing one small tool runs
more than half of it, and the half it runs is mostly unrelated. That is affordable today and stops
being affordable at three times the tools, because the cost of a one-line change grows with the size
of the system rather than with the size of the change.

## What was measured, 2026-08-08

Everything below is a count from the tree as it stands, not an impression.

| | |
|---|---|
| Tagged kernel tests | 212 declared, 205 selected on x86_64 |
| Selected by wave 5 (`image,audio,service,process,storage`) for a one-tool change | **115 of 212 - 54%** |
| Kernel tests that exercise `audioconv` at all | **1** |
| Kernel tests naming ANY program | 30 of 205 - 14% |
| Kernel tests naming no program (kernel and library behaviour) | 175 |
| Always-on `smoke` set | 7 |
| Crates with host tests | 58 |
| Crates whose host tests any gate runs | **9** |

Wall clock, on a host at load 115 with 64 fuzzing processes:

| | x86_64 (KVM) | aarch64 (TCG) | riscv64 (TCG) |
|---|---|---|---|
| Whole suite | 130-151 s | 2877 s | 6104 s |
| `--tags image` (10 tests) | 63 s | 1518 s | - |

## What is wrong, precisely

**1. The tag vocabulary mixes two different questions.** Some tags say what a test EXERCISES -
`audio` is on 5 tests, `image` on 3, `display` on 3, `network` on 1. Others say what a test NEEDS in
order to run at all - `process` is on 35% of the suite, `service` on 30%, `storage` on 19%, because
nearly every test starts a service and launches something. Putting one of the second kind into a
selection collapses it to half the suite, which is exactly what wave 5 does. The waves were built
for the dynamic-linking migration, where "everything that could plausibly be affected" was the right
question; reused as a change-scoping mechanism they answer a question nobody asked.

**2. The scoping tables are guesses, and the real graph already exists.** `lib.sh`'s `COMPONENT_TAGS`
says `src/user/libs/audio/**` is tested with `audio,service,process,storage` - a hand-written
approximation. `manifest.toml` already records, per program and per library, exactly which providers
it links against; `check-dynamic-report.sh` already computes the transitive closure of that graph
and prints it. Asked properly, the manifest answers "who uses `flac`" with `play` and `audioconv`,
and "who uses `pcm`" with seven libraries and the two programs above them. A hand table cannot stay
right as the tool count multiplies; a derived answer cannot go stale.

**3. The cheap precise tests do not run and the expensive coarse ones do.** 49 of 58 crates with
host suites are in no gate: FAT, ISO9660, UDF, LiberMemFS, every image codec, MP3, Vorbis, Ogg, both
compression leaves, `abi`, `proto`, `term`. Those suites are milliseconds each and pin behaviour far
more finely than a boot can. Meanwhile a one-tool change boots QEMU 115 times over. This is the same
suite-in-name-only that `check-host-tests.sh` was written for, and it is nine crates into a job of
fifty-eight.

**4. Nothing connects a changed library to the tools that use it.** Which is the case the whole
exercise exists for: a change to `flac` must test `play` and `audioconv`, and today it either tests
half the system or - if somebody scopes by hand - neither of them.

**5. The architecture choice is manual and unguided.** Emulated runs cost twenty-four times what
x86_64 costs. Nothing says when a change can differ per architecture and when it provably cannot, so
the choice is made by feel, which means either wasted hours or an untested target.

## Tasks

- [ ] **Say what each test exercises, and gate the saying.** Extend `tagged_test!` with a `uses:`
  list naming the programs and libraries a test actually drives, alongside the tags it already
  carries. Tags stay what a human selects by; `uses` is what a tool selects by. Add a gate to
  `check.sh` that reads each test body for `program_elf(.., b"X")` and `lookup(b"X.lsexe")` and fails
  when the declaration and the code disagree in either direction - an undeclared launch or a declared
  program the test never touches. Without the gate the declarations rot, and a rotted `uses` list is
  worse than none: it silently stops selecting a test that would have caught the bug.

- [ ] **Derive the affected set from the manifest instead of a table.** Given a set of changed paths:
  map each to its crate, walk `manifest.toml`'s `providers` edges upward to every library and program
  that links it, and select the tests whose `uses` names any of them. Delete `COMPONENT_TAGS` when
  this lands - a derived answer and a hand-written one will disagree, and the hand-written one will
  be the one that is consulted. Keep a fallback only for paths the manifest does not describe, and
  keep that fallback wide: unknown reach is still tested with everything.

- [ ] **Put every crate's host suite in a gate.** All 58, not 9. Then scope THAT too: `cargo test -p
  CRATE` for what changed plus the crates that depend on it, which cargo already knows without any
  table at all. This is the highest-value item on the list and the cheapest: the suites exist, they
  are fast, and they are the only place most of this tree's behaviour is pinned down at all.

- [ ] **Make the default selection a floor plus the affected set.** `smoke` (7 tests) is the floor -
  it exists so that a scoped run still notices the system failing to boot. On top of it goes only
  what the graph selected. For `audioconv` that is 8 tests instead of 115; for a change to `pcm` it
  is 7 plus whatever exercises the seven codecs above it. The number to watch is that the scoped cost
  stays flat as tools are added, where today it grows with the tree.

- [ ] **Choose architectures from what the change can actually differ on.** Anything touching
  `src/kernel/arch/**`, the linker scripts, the loader, the ABI or the wire formats is booted on all
  three; ordinary userspace is CROSS-BUILT for all three and booted on one. The tool applies the rule
  and says which it chose, with a flag to override. The 24x emulation penalty is why this is worth
  encoding rather than leaving to judgement. *(This task originally claimed such code "cannot behave
  differently" per architecture. It was right to be challenged and is corrected under the review
  below - a `cfg(target_arch)`, a `repr(C)` layout, an atomic or a `build.rs` does not respect that
  claim. Cross-building everywhere is what makes booting one defensible.)*

- [ ] **Name the full sweep as a scheduled thing rather than a reflex.** The whole suite on all three
  architectures is right before a release, after a kernel change, and on a timer - not after every
  tool edit. Write down which of those it is, so that running it is a decision and not a habit, and
  so that NOT running it after a tool edit is also a decision.

- [ ] **Report what the scoped runs have not covered.** The risk of selecting is selecting too
  little, and the failure is silent. Keep a record of when each test last actually ran, and report
  the tests no scoped run has executed in some window. That turns "we might be under-testing" into a
  list, which is the same move the dynamic report makes for linking.

- [ ] **Measure the result and write the numbers into this file.** Selection size and wall clock,
  before and after, for a tool change, a library change, a service change and a kernel change. M0147
  is the precedent: the measurement is what turned a plausible optimisation into a backed-out one,
  and this milestone should be as willing to record that its own idea did not pay.

## An outside review, assessed

A second model was asked to review this milestone at commit `bfa3225`. Most of what it says is worth
having and is folded into the tasks below. Four of its claims do not survive contact with the tree,
and they are recorded here with the evidence, because a rejected suggestion that is not written down
gets suggested again.

The verdict point by point, so that adopting most of it does not read as adopting all of it:

| # | The review's point | Verdict | What happens |
|---|---|---|---|
| 1 | Kernel change should not expand to everything; give kernel and drivers a component graph | Right instinct, wrong example - drivers are userspace here | Split `src/kernel/arch/<target>` from shared kernel; give the driver crate per-device granularity |
| 2 | `uses` misses IPC, syscall, ABI, device and format edges | **Right, and the sharpest point** | `covers` names components, not only libraries |
| 3 | Split `covers` from `requires` | `covers` right; `requires` has no consumer yet | Adopt `covers`; `requires` recorded as later |
| 4 | "Cannot behave differently per arch" is too absolute | **Right** | Cross-build all three, boot one; wording corrected |
| 5 | Declaration checker must not rely only on grepping for launches | Right | Add a typed helper API and runtime observation during full sweeps |
| 6 | Fail-open as a formal invariant with a list | Right | Written as an invariant, enumerated |
| 7 | Property tests for the selector | Right, cheap, strong | Adopted in full |
| 8 | merge-base and rename/delete aware diff | Framing does not apply - no CI, no PRs - but it found a real bug | `--for-change` drops the old path of a rename; fix that, add `--for-range` |
| 9 | Shadow mode: scoped and full in parallel, compared | **Right, best item in the review** | Adopted; the full sweep only steps back once the record is clean |
| 10 | Replay historical regressions against the selector | Right | Adopted; this tree already has the corpus |
| 11 | One central component registry | Right instinct, wrong implementation | Extend the manifest; a registry only for what it cannot describe |
| 12 | Docs-only changes need no QEMU | Already true | `docs/**`, `*.md` and `*.sh` already resolve to no kernel test |
| 13 | Escalate to full on estimated cost, not on count | Right | Adopted, threshold derived from measurements |
| 14 | Test age as a bound, not a report | Right | Adopted as an upgrade of the reporting task |
| 15 | Cancel superseded CI runs | Does not apply - there is no CI | Not adopted |
| 16 | Amortise the per-test QEMU boot with snapshot/restore | **Wrong premise** - one boot serves the whole suite | Rejected, with the evidence recorded |

**What it got wrong about this tree.**

- **"Full is 115 tests."** 115 is the wave-5 SELECTION measured above; the suite is 205 of 212
  declared. Several of the review's thresholds are calibrated on the smaller number and should be
  re-derived from the real one.
- **"`test.sh` boots QEMU once per test, so amortise it with snapshot/restore."** It boots once for
  the whole suite: the guest log for the 205-test run contains exactly one `LiberSystem kernel is
  starting` and 205 results. There is no per-test boot cost to amortise, and building snapshot
  plumbing would be a large change for nothing. Rejected.
- **"Change one driver and the kernel suite expands to everything."** Drivers are USERSPACE here -
  `src/user/drivers/core/src/virtio_blk.rs` and its neighbours - so they already sit in the manifest
  graph the second task derives from. The kernel tree has no drivers subtree at all. The underlying
  point survives in a different place; see below.
- **"Cancel superseded CI runs; use GitHub Actions concurrency."** There is no CI. Everything is run
  by hand on one machine, and `test.sh` already refuses to start while another run holds the images.

**What it got right, and what changes because of it.** The review's strongest single contribution is
shadow mode: run the scoped selection AND the full suite for a period, and compare. That is the only
honest way to earn the right to stop running the full suite, and it is the same discipline M0147
used - measure the change rather than believe it.

Its second strongest is that `uses` is too narrow. The manifest describes ONE kind of edge, the
link-time one. A program reaches a service over IPC, a service reaches a kernel subsystem over a
syscall, a filesystem reaches a block driver over a device protocol, and none of those appear in a
provider list. A declaration that can only name libraries will silently under-select exactly the
integration paths that break.

Its third is that this milestone's claim about architecture neutrality was too absolute. "Cannot
behave differently" is not something a `cfg(target_arch)`, a `repr(C)` layout, an atomic or a
`build.rs` respects. The replacement is cheap and stronger: cross-COMPILE affected code for all
three targets on every change - which `./build.sh --arch all` already does - and BOOT one, with the
full multi-architecture sweep as the periodic check on that judgement.

## Tasks added by the review

- [ ] **Split `src/kernel` instead of treating it as one bucket.** The review's example was wrong and
  its instinct was not. `src/kernel/arch/x86_64/**` cannot affect a riscv64 boot, so it should select
  the whole suite on ONE architecture rather than all three; `src/kernel/arch/common/**` and the
  shared subsystems still select everything everywhere. Do the same for the driver crate, which is
  one crate holding virtio-blk, virtio-gpu, USB HID and USB storage - at crate granularity a
  keyboard change tests the disk. Per-device components inside it, or split the crate.

- [ ] **Let a test declare what it covers beyond the link graph.** `covers` names components, not
  only libraries: a service, a kernel subsystem, an on-disk format, a device protocol. The manifest
  supplies the link edges automatically; the other edges have to be written down because nothing
  else knows them.

- [ ] **One place decides what a path belongs to, and it is the manifest wherever the manifest can
  say.** The review asks for a central component registry, which is right, and proposes a new file,
  which would duplicate `manifest.toml` and cause the drift it warns about. Extend the manifest for
  everything it already describes; add a registry ONLY for what it cannot - kernel subsystems, arch
  trees, linker scripts, fixtures. Then gate it: every source file is owned by exactly one component
  or is explicitly marked non-code, and anything else selects the whole suite.

- [ ] **Shadow mode before trust.** For an agreed period, every scoped run is followed by the full
  suite, and the two results are compared. A scoped PASS with a full FAIL caused by the same change
  is proof the model missed an edge, and it goes into the corpus below. Only after that record is
  clean does the full sweep drop back to scheduled.

- [ ] **A corpus of real regressions the selector must catch.** For each bug this project has found,
  record the component that changed and the test that would have caught it, and assert that today's
  selector would have selected that test. This tree has the material already: the RECV_CAPS overrun,
  the clone-then-close capability duplication, the ungated device acquire, the frame use-after-free,
  the MS ADPCM block length. Each is a row.

- [ ] **Property tests for the selector itself.** Monotonicity (a larger change selects a superset),
  determinism, idempotence of the closure, full-absorption (any full-selecting path makes the whole
  answer full), total ownership, and correct handling of renames and deletions. Cheap to write and
  they make the selector as checkable as the thing it selects.

- [ ] **Fail open, as a written invariant with a list.** Unknown path, unmapped component, malformed
  manifest, parser failure, selector crash, ambiguous architecture, a change to the selector itself,
  a change to the test framework, a change to component metadata, a change to the build or image
  tooling - every one of them selects everything. A selector that fails and selects nothing must be
  impossible, not unlikely.

- [ ] **Fix the change set: renames and deletions.** `--for-change` currently reads
  `git status --porcelain` and keeps only the new name of a rename, so the OLD path's component is
  never consulted - a file moved out of a subsystem does not test that subsystem. Evaluate both
  sides, keep deletions, and add `--for-range REV..REV` for "what changed since that commit", which
  is this project's analogue of the review's merge-base point.

- [ ] **Escalate on cost, not on count.** When the scoped selection is within some fraction of the
  full suite's measured runtime, run the full suite instead - the bookkeeping is not worth the
  remainder. Derive the fraction from real timings rather than picking one.

- [ ] **Turn test age into a bound rather than a report.** A test that no run has executed within its
  window is scheduled automatically. The report says what has gone stale; the bound stops it.

- [ ] **Cross-compile all three, boot one.** Affected code is built for every target on every change;
  the QEMU run goes to one architecture unless the change is arch-sensitive. Replace this file's
  earlier "cannot behave differently" with the honest form: classified as low-risk and
  architecture-neutral, cross-built everywhere, and periodically validated by the full sweep.

- [ ] **`requires`, later.** The review's split of `covers` from `requires` is right in principle -
  what a test is selected BY and what it needs to RUN are different questions. It is not P0 here
  because the runner gives every guest the same devices and the same fixtures, so nothing would read
  `requires` today. Revisit when a test needs a machine shape the default guest does not have.

## What this deliberately does not do

Nothing here weakens an assertion, deletes a test, or makes a gate optional. The failure mode being
designed against is not a slow suite - it is a fast suite that stopped looking, which is what every
one of the gates in `check.sh` exists to prevent. Every default in the tasks above errs toward
running more: an unrecognised path gets the whole suite, a missing declaration fails the build, and
the smoke floor runs whatever else was selected.
