# M0148 - Testing that scales with the change, not with the tree

Status: PLANNED. Nothing here changes what the tests assert; it changes which of them run, and it is
worth doing before the tool count multiplies rather than after.

The suite is honest and it is thorough. What it is not is SELECTIVE: changing one small tool runs
more than half of it, and the half it runs is mostly unrelated. That is affordable today and stops
being affordable at three times the tools, because the cost of a one-line change grows with the size
of the system rather than with the size of the change.

### What selection can and cannot save

Those pairs are enough to separate the fixed cost of a run from the variable cost of a test, and the
answer changes what this milestone should optimise first. Solving `F + n*p` for each architecture:

| | fixed per run | per test | halving the suite saves |
|---|---|---|---|
| x86_64 | ~100 s | ~0.2 s | **~15%** |
| aarch64 | ~1450 s | ~7 s | ~25% |

**Selecting fewer kernel tests is the smallest lever this milestone has.** Cutting the x86_64 suite in
half saves about twenty seconds of a hundred and forty, because the build, the image and the boot are
paid once and dominate everything. The levers that actually pay are, in order: not booting an emulated
target that cannot be affected (100% of 2877 s or 6104 s), not booting at all when host suites answer
the question (100% of 140 s), and only then running fewer tests inside a boot that is happening anyway.

Two consequences for the task list. The architecture policy and the 58 host suites outrank test
selection and should land first. And a scoped selection is only worth its bookkeeping when it removes
a *boot*, which is what the cost-escalation rule below has to be calibrated against - not against a
test count. (These constants were measured on a host at load 115; recalibrate on an idle one. The
ratio is the durable part.)

## What is wrong, precisely

**1. The tag vocabulary mixes two different questions.** Some tags say what a test EXERCISES -
`audio` is on 5 tests, `image` on 3, `display` on 3, `network` on 1. Others say what a test NEEDS in
order to run at all - `process` is on 35% of the suite, `service` on 30%, `storage` on 19%, because
nearly every test starts a service and launches something. Putting one of the second kind into a
selection collapses it to half the suite, which is exactly what wave 5 does. The waves were built
for the dynamic-linking migration, where "everything that could plausibly be affected" was the right
question; reused as a change-scoping mechanism they answer a question nobody asked.

**2. The scoping tables are guesses, and the real graph already exists.** `lib.sh`'s `COMPONENT_TAGS`
says `src/user/libs/audio/**` is tested with `audio,service,process,storage` - a hand-written
approximation. `manifest.toml` already records, per program and per library, exactly which providers
it links against; `check-dynamic-report.sh` already computes the transitive closure of that graph
and prints it. Asked properly, the manifest answers "who uses `flac`" with `play` and `audioconv`,
and "who uses `pcm`" with seven libraries and the two programs above them. A hand table cannot stay
right as the tool count multiplies; a derived answer cannot go stale.

**3. The cheap precise tests do not run and the expensive coarse ones do.** 49 of 58 crates with
host suites are in no gate: FAT, ISO9660, UDF, LiberMemFS, every image codec, MP3, Vorbis, Ogg, both
compression leaves, `abi`, `proto`, `term`. Those suites are milliseconds each and pin behaviour far
more finely than a boot can. Meanwhile a one-tool change boots a guest and runs 115 mostly unrelated
kernel tests inside it. This is the same suite-in-name-only that `check-host-tests.sh` was written
for, and it is nine crates into a job of fifty-eight.

**4. Nothing connects a changed library to the tools that use it.** Which is the case the whole
exercise exists for: a change to `flac` must test `play` and `audioconv`, and today it either tests
half the system or - if somebody scopes by hand - neither of them.

**5. The architecture choice is manual and unguided.** Emulated runs cost twenty-four times what
x86_64 costs. Nothing says when a change can differ per architecture and when it provably cannot, so
the choice is made by feel, which means either wasted hours or an untested target.

## The design

One pipeline, and each stage has exactly one mechanism. The three vocabularies below are kept
strictly apart, because the measurement above is what happens when one of them is asked to do
another's job.

```
changed paths
      -> component ownership          (one table, manifest-derived where the manifest can say)
      -> reverse dependency closure   (typed edges: link, ipc, syscall, device, format, generation)
      -> affected components
      -> tests whose `covers` intersects them
      -> exact stable test IDs        + the smoke floor
      -> architecture policy          (which targets to build, which to boot)
      -> cost escalation              (scoped, or full when scoped is not worth the bookkeeping)
```

**Tags are the human interface. The component graph is the machine's dependency interface. Test IDs
are the machine's execution interface.** A `uses` list, if it exists at all, is observational - a
record of what a test was seen to touch, useful for auditing the declared graph. It is **not** a
selection primitive; `covers` is.

### Where the edges come from: three sources, unioned

`manifest.toml` is the **dynamic** graph - which `.lslib` a program loads at run time. It is not the
dependency graph, and building the selector on it alone would be a false-negative machine. Measured:
**27 of the 108 crates in this tree are named nowhere in the manifest**, and they are not marginal
ones.

| edge the manifest cannot see | measured |
|---|---|
| `src/fs` - `liberfs`, `libermemfs`, `fat`, `iso9660`, `udf`, `partition`, `fscore` | all seven absent from the manifest; all six non-`fscore` ones are static `path` dependencies of StorageService |
| the kernel's own storage fixtures | `src/kernel/Cargo.toml` links `liberfs`, `partition` and `fscore` **as regular dependencies** |
| the loader | links `liberfs`, `fat`, `fscore`, `abi`, `bootproto` |
| the kernel's `[dev-dependencies]` | **11 userspace library crates** - `aiff flac pcm wav wavpack bmp gif pix png tga webp` - because the `audioconv` and `imgconv` scenarios build their fixtures with the same codecs they test |
| `abi` | 8 static dependents, including the kernel and the loader |

The last row inverts an assumption a selector would otherwise make. "A userspace audio library cannot
affect the kernel" is false in this tree: change `flac` and the kernel's *test* binary is rebuilt, and
the fixture the `audioconv` scenario asserts against changes with it. No dynamic-linking view can show
that edge, because at run time there is no link at all.

Note also that the hand table this milestone deletes is **already wrong here**, not merely coarse:
`COMPONENT_TAGS["src/fs"]` is `filesystem,storage,volume`, which does not reach the kernel or the
loader. So this is not a regression the new design would introduce - it is a live defect the new
design must not inherit.

The graph is therefore the **union** of three sources, each typed:

| source | edges | derived or declared |
|---|---|---|
| `manifest.toml` providers | `link.dynamic` | derived |
| `cargo metadata` over every discovered manifest | `link.static`, `link.static.dev`, `generation.build` | derived |
| an explicit registry | `ipc`, `syscall`, `device`, `format`, `generation` | declared once between components |

`cargo metadata` is already needed for the host-suite reverse graph, so this costs one consumer, not
one mechanism. Cargo has **three** dependency kinds and each maps to a different edge, because each
means something different about what a change does:

| Cargo kind | edge | what a change to the dependency does |
|---|---|---|
| normal | `link.static` | changes the shipped binary |
| dev | `link.static.dev` | rebuilds the test binary; does not ship |
| build | `generation.build` | **changes generated source in something that does ship** |

Keeping them apart matters in both directions. `link.static.dev` must not be `link.static`, or the
kernel joins the closure of every codec for the wrong reason. And `generation.build` must not be
silently filtered out - which is the easy mistake, since build dependencies are neither linked nor
tested. There are four such edges here, and they are not marginal: `system-manifest` is a
build-dependency of both the kernel and CoreServices, and it *generates their source* -
`manifest.rs`, `library_paths.rs`, `program_paths.rs` in CoreServices, the test volume paths in the
kernel. Change it and shipped code changes without a single source file being touched.

That has a consequence for path ownership too: **`manifest.toml` is a build input, not only the
graph's data source.** Editing it regenerates code in the kernel and in CoreServices, so it needs its
own `generation.build` edges to both, independently of whatever it says about providers. Merging build
dependencies into `link.static` would be conservative and merely imprecise; dropping them is a false
green.

### The static graph must be configuration-complete, or it is worse than no graph

"Run `cargo metadata`" does not say **in which configuration**, and in this tree the default
configuration is the wrong one - not marginally, but for the edges that matter most.

| measured | |
|---|---|
| `src/user/apps/tools/Cargo.toml` | `default = []`, and **20 optional `path` dependencies** - every `*-client` and `*-client-provider` pair - reachable only through the `shared-image` feature |
| all 15 protocol crates plus `src/proto` | `default = []`, `ipc-client` optional behind `channel-client-impl`, which `shared-image` enables |
| how the image is actually built | `src/tools/build-shared.sh`: `cargo rustc --release --no-default-features --features shared-image` |

So `cargo metadata` in its default configuration reports that **`tools` depends on none of the client
libraries** and that **no protocol crate depends on `ipc-client`** - while the only configuration that
ever ships enables all of them. A selector built on that graph would answer "nothing uses
`ipc-client`" about the IPC plumbing every service and every tool links. That is a false-green
machine, built by the very fix that was meant to prevent false greens.

The rule, therefore: **an edge that exists under any buildable configuration exists in the graph.**
Union `cargo metadata` over the configurations the tree actually builds - at minimum default and
`--no-default-features --features shared-image`, per target - or, simpler and strictly safer, read the
manifests directly and treat every `path` dependency as an edge regardless of `optional`. Over-selection
from an edge that happens to be inactive costs a test run; under-selection from an edge that was active
in the shipped build costs a shipped regression. Where the distinction is worth keeping, keep it as a
condition on the edge (`when: feature channel-client-impl`) rather than by dropping the edge.

The same question applies one layer down, and is already live: `check-host-tests.sh` runs
`cargo test --manifest-path …` with default features, so for `tools` and every protocol crate **the
configuration that ships is the one never host-tested.** Extending that gate to all 58 crates has to
answer "in which configuration" too, and for at least these sixteen the answer is more than one.

### `covers`, defined so it cannot rot

`covers: X` means **the test contains an assertion able to detect a regression in X's contract.** It
does NOT mean the test's execution path goes through X.

Every integration test runs the scheduler, the allocator, IPC and the loader. If touching counted,
every test would cover everything and the selection would be the full suite wearing new metadata.

The relation is therefore **asymmetric, and the gate must be too**:

| | enforceable | why |
|---|---|---|
| `covers: X` implies X is reachable in the test's execution | yes, gate it | covering something the test cannot reach is a declaration error |
| the test launches X, therefore it covers X | **no** | a scenario that starts StorageService to test `component_host` asserts nothing about StorageService |

Mechanically inferring the second direction rebuilds `touches = covers` under a new name, and `covers`
inflates back to the full suite one honest-looking gate at a time. What the launch scan is good for is
an **audit report** - "these tests reach X and none of them claims to cover it" - read by a person,
never a build failure.

That leaves under-declaration - a test that really does pin `flac` and forgets to say so - with no
static check at all. That is accepted deliberately: it is exactly the failure shadow mode detects (a
test outside S fails while all of S passes), and it is the main reason trust is granted per component
on evidence rather than assumed.

### Stable IDs, and the one key everything is stored under

An ID is an **explicit literal** in the declaration - never derived from the Rust function name.
Globally unique, mandatory, and gated. Renaming a function must not change the ID, because the ID is
what every history below is keyed on; deriving it from the function name means a refactor silently
zeroes all of them. Changing an ID is a deliberate metadata migration.

But a bare test ID is not the unit of work. The planner emits `(check, architecture, environment,
reason)`, so the unit is:

```
PlanItemKey = (check_id, architecture | host, environment, configuration)
```

| example | key |
|---|---|
| a kernel test in the test guest | `(kernel.audio.flac_roundtrip, riscv64, test-guest, test)` |
| a crate's host suite, default features | `(host.proto, host, host, default)` |
| the same crate as it actually ships | `(host.proto, host, host, shared-image)` |
| the development self-test | `(dev.selftest, x86_64, dev-guest, development)` |

**Age, runtime, failure, shadow and cost history are all keyed on `PlanItemKey`, and so are the
regression fixtures.** Every field earns its place by being a way the same check can differ:

- the test ID alone loses the **architecture**, and a riscv64 result is not an x86_64 result;
- `(test, arch)` still loses the **environment**, so a regression fixture for the `dev_agent` can
  confirm the right test on the right target while never checking that the planner chose the dev
  guest - the only part of that plan that could have been wrong;
- `(test, arch, environment)` loses the **configuration**, and the section above is what makes that
  concrete: `proto` must be host-tested under default features *and* under `shared-image`, because
  those two builds do not even contain the same dependencies. Both runs would collide on
  `(host.proto, host, host)`, the shipped configuration would inherit the default one's freshness, and
  the age bound would report as covered a configuration that has never run.

`configuration` canonically names the feature set, the Cargo profile and the build mode; it does not
repeat the target, which `architecture` already carries. Encoding it into `check_id` instead
(`host.proto.shared-image`) works and is worse - it makes "all configurations of this check" a string
prefix match rather than a projection.

### Not every key exists: the applicability matrix

Tests are compiled per target and the counts differ: **205 on x86_64, 196 on aarch64** (riscv64 not yet
measured). A bound keyed on `(test, arch)` without knowing which pairs are real reports the missing
ones as permanently stale, and the age scheduler then chases combinations that cannot exist.

Applicability cannot be inferred from the path, either. `cfg(target_arch)` gating on tagged tests is
**not** confined to the arch trees - `test_suites/kernel.rs` has eight, `test_suites/hardware.rs` six,
`sched/tests.rs` two - so a test living in a shared file may exist on one target only. It has to be
**derived from what actually compiles**, per target, and recorded:

```
test_catalog: id -> { covers, applicable_architectures, environment }
```

Two consumers, both load-bearing. The age universe is the set of real `PlanItemKey`s and nothing else.
And the planner must never hand a guest an ID that does not exist there: an exact `TEST_SELECTION` that
names a test the aarch64 binary never compiled either errors or, worse, silently matches nothing.

### Architecture policy

Per target, not per category. "Arch-sensitive" is not an answer on its own - each class must name the
exact set of targets to boot, and every per-target file in this tree has a row:

| changed | built | booted |
|---|---|---|
| `src/kernel/arch/x86_64/**`, `src/kernel/linker/x86_64.ld`, `src/loader/src/arch/x86_64/**`, `src/user/user.ld` | all three | x86_64 |
| the same three trees for aarch64 (`src/user/user-aarch64.ld`) or riscv64 (`user-riscv64.ld`) | all three | that target |
| `src/kernel/arch/common/**`, `src/kernel/arch/mod.rs`, the ABI, the boot protocol, the wire formats | all three | all three |
| shared loader source - `src/loader/src/{main,uefi,elf,heap,blockio}.rs`, `arch/mod.rs` | all three | all three |
| `src/user/build.rs` - it *selects* one of the three user linker scripts by target | all three | all three |
| `src/boot/qemu-run.sh` and the rest of the harness - thirteen architecture-specific branches | all three | all three |
| ordinary userspace, no arch marker found | all three | one (x86_64) |

The distinction that matters and is easy to get wrong: **a file that is per-target selects its target;
a file that chooses between targets selects all of them.** `user-riscv64.ld` is the first kind.
`src/user/build.rs`, which maps `target_arch` to one of the three, is the second - a bug in its
mapping is invisible on the target it maps correctly. The loader has both kinds in one crate, which is
why it gets two rows rather than one.

**Cross-building all three proves a branch compiles, not that it is right**, so the mechanical scan
below is a *conservative risk classifier* and never a proof of neutrality. A crate containing
`cfg(target_arch)`, `cfg(target_pointer_width)`, `asm!`, `global_asm!`, a target-specific dependency
or a target-aware `build.rs` is **definitely** architecture-sensitive. A crate containing none of them
is a **candidate** for neutral - `usize`, `repr(C)` layout, alignment, atomics and a dependency's
internals can all differ without any of those appearing. Confidence comes from cross-building plus
shadow evidence plus the periodic full sweep, not from the scan.

Given the cost table above, this section is where most of the milestone's value is. Getting one row
wrong in the cheap direction costs an untested target; getting it wrong in the expensive direction
costs 6104 seconds. Both are worth a negative fixture.

### Execution environments are part of the plan, not a later refinement

The planner covers every kind of check, and this tree already has checks that cannot run in the same
guest. `qemu-run.sh` refuses `DEV_PROFILE=1` together with `TEST=1` outright, and two harnesses -
`src/boot/dev-selftest.py` and `src/boot/proto-test.py` - fail with "is `just dev-up` running?"
against anything else. So a plan item carries an environment from the start:

| environment | runs |
|---|---|
| `host` | the 58 crate suites, the manifest and inventory gates, the mechanical scans |
| `test-guest` | `qemu-run.sh TEST=1` - the tagged kernel suite, per architecture |
| `dev-guest` | `qemu-run.sh DEV_PROFILE=1` - `dev-selftest.py`, `proto-test.py`, `perf-gate.py`, the scenarios |

A change to `src/user/services/core/src/dev_agent.rs` must plan a **dev-guest** run; today it plans a
test-guest sweep that cannot reach the agent at all. This is separate from the deferred per-test
`requires` - that one still has no consumer, because within a single environment every guest is
identical. The environment dimension has three consumers today.

## Tasks

Ordered by measured value, not by pipeline order: the host suites and the architecture policy each
save more than every other item combined, and both are independent of the selector.

- [ ] **Put every crate's host suite in a gate, then scope that too.** All 58, not 9. There is no
  top-level workspace, so the reverse graph comes from `cargo metadata` over discovered manifests
  rather than from one query. Gate the inventory: a crate with host tests and no entry fails the
  build. **This is the highest-value item on the list and the cheapest** - the suites exist, they are
  milliseconds, and they are the only place most of this tree's behaviour is pinned at all. It also
  produces the `cargo metadata` graph the next two items need. Answer "in which configuration" while
  doing it: the gate runs `cargo test` with default features, and for `tools` and the fifteen protocol
  crates that is the one configuration the image never ships.

- [ ] **Automate the architecture policy, one row at a time, with a negative fixture per row.**
  Implement the table above. This is the single biggest saving in the milestone (100% of 2877 s or
  6104 s when a target cannot be affected) and the single biggest risk (an untested target). Every row
  gets a fixture: a change under `src/loader/src/arch/riscv64/` must plan riscv64 and must NOT plan the
  other two; a change to `src/user/build.rs` must plan all three; the default row must plan x86_64
  only. Until the fixtures exist the policy stays advisory - it prints what it would have chosen next
  to what was actually run.

- [ ] **One planner over every kind of check, not one per tool.** `./test.sh --for-change` answers only
  the kernel-suite question, and when nothing there applies it prints a note and **exits 0** - which
  for a human reads as "nothing to do" and for automation reads as "everything passed". Build
  `./verify.sh --for-change` (also `--for PATH`, `--for-range A..B`) which emits ONE plan covering
  builds, host suites, conformance runs, manifest gates and per-architecture, per-environment guest
  runs, with `--plan`, `--explain` and `--json`, and executes it. Every plan item carries `(check,
  architecture, environment, reason)` - the `host` / `test-guest` / `dev-guest` split is structural,
  because `qemu-run.sh` refuses two of them in the same guest. Shadow mode, the regression corpus, the
  cost estimator, the age scheduler and the person at the terminal then all use the same selector
  implementation rather than four that drift.

- [ ] **A component graph with typed edges, from three sources unioned.** `link.dynamic` from
  `manifest.toml`'s providers; `link.static`, `link.static.dev` and `generation.build` from
  `cargo metadata`'s three dependency kinds - do not collapse them, and in particular do not drop
  build dependencies, which is how `system-manifest` regenerating the kernel's and CoreServices'
  source would become invisible; and `ipc`, `syscall`, `device`, `format`, `generation` declared
  **once between components**, never
  repeated in every test's `covers`. **Manifest-only would be a false-negative machine** - 27 of 108
  crates are not in it, including all of `src/fs`, and the kernel statically links `liberfs` and
  dev-links eleven userspace codecs. Gate that the union is total: a crate reachable by any `path`
  dependency and absent from the graph fails the build. A change to `kernel::channel` reaches most of
  the system; if that has to be written into each test, the hand-maintained graph this milestone
  deletes is simply rebuilt inside the test files.

- [ ] **Make the static half configuration-complete, and gate that it is.** The default `cargo`
  configuration hides the edges that matter most: `tools` has 20 optional client dependencies behind
  `shared-image`, all 15 protocol crates reach `ipc-client` only through `channel-client-impl`, and the
  image is built `--no-default-features --features shared-image`. **An edge that exists under any
  buildable configuration is an edge.** Either union `cargo metadata` across the configurations the
  tree builds, per target, or read the manifests and take every `path` dependency regardless of
  `optional`. Fixture: `ipc-client` must select the protocol crates and the tools above them; if the
  graph says nothing uses it, the graph is being read in the wrong configuration.

- [ ] **Say what each test covers, with a stable ID, and gate the enforceable direction only.** Extend
  `tagged_test!` with an explicit `id` literal and a `covers` list. Gate: IDs globally unique and
  present, and a `covers` entry naming a component the test cannot reach fails. **Do not gate the
  converse.** "The test calls `program_elf(.., b"X")`, therefore it covers X" is `touches = covers`
  wearing a new name, and it is the mechanism by which `covers` would inflate back to the full suite -
  a scenario that starts StorageService to test `component_host` asserts nothing about StorageService.
  Emit the launch scan as an **audit report** a person reads instead: "these tests reach X and none
  claims to cover it."

- [ ] **One place decides what a path belongs to.** Extend the manifest for everything it already
  describes; add a registry only for what it cannot - kernel subsystems, arch trees, linker scripts,
  fixtures. Gate it: every source file is owned by exactly one component or explicitly marked
  non-code, and anything else selects the whole suite. Delete `lib.sh`'s `COMPONENT_TAGS` when this
  lands - a derived answer and a hand-written one will disagree, and the hand-written one is the one
  that gets consulted.

- [ ] **Negative fixtures for every gate whose false-negative would be a green build.** "A gate that
  breaks fails loudly on its own" is not true: `exit 0` at the top of a checker breaks it
  catastrophically and silently, and an inventory scan that quietly stops discovering half the crates
  still returns success. **A validator may not be tested only by running its current version over a
  currently-valid tree.** Each needs inputs it must REJECT: the tag checker against an undeclared tag,
  a duplicate ID and a missing `covers`; the host-test inventory against an omitted crate; the
  selector against an unknown path, a malformed graph and its own crash.

- [ ] **Property tests for the selector.** Monotonicity - a larger change selects a superset;
  determinism; idempotence of the closure; full-absorption, so any full-selecting path makes the whole
  answer full; total ownership; and correct handling of renames and deletions.

- [ ] **Fail open, as a written invariant with a list.** Unknown path, unmapped component, malformed
  manifest, parser failure, selector crash, ambiguous architecture, a change to the selector itself,
  to the test framework, to component metadata, or to the build or image tooling - **every one selects
  everything.** A selector that fails and selects nothing must be impossible, not unlikely.

- [ ] **Put the fail-open decision outside the thing that can fail.** "The selector crashes, therefore
  select everything" cannot be implemented inside the selector: a planner that segfaults is in no
  position to choose a fallback. `verify.sh` must be a thin outer shell that runs the planner as a
  **separate process**, and on any non-zero exit, empty plan or unparseable output falls through to a
  canonical FULL path - build all, check all, boot all three - written so plainly it cannot itself
  break. The absolute rule is narrower than "fall back": **a planner failure must never produce a green
  exit status.** If the fallback is judged too expensive to trigger automatically, the shell exits
  non-zero with `FULL VERIFICATION REQUIRED` instead. Both are acceptable; exiting 0 is not.

- [ ] **Shadow validation, cheaply: DRY by default.** The expensive version runs the scoped selection
  and then the full suite. It is not needed for most cases, because **one QEMU boot already serves the
  whole suite**: compute the scoped set S without running it, run the full suite once, and compare.
  Every test in S passing while a test outside S fails is proof the selector missed an edge - at
  **half** the QEMU cost, which against a 6104-second riscv64 sweep is not cosmetic.
  SHADOW-EXEC - really running S, then the full suite - is still needed to validate the execution
  mechanism itself: `TEST_SELECTION`, test ordering, state leaking between selected tests, and the
  smoke-plus-selected composition. Sample it, and require it before any component's trust level is
  raised.

- [ ] **Confirm a shadow miss before believing it.** "A test outside S failed" is a candidate, not
  evidence: it may be a flake. This tree has one on record - riscv64
  `process_service_lists_every_started_program` failed three times and then passed twice with no
  change, cause still unidentified. Charging that to the selector would hold a component in SHADOW
  forever for a reason that has nothing to do with it. So on a candidate miss: re-run the failing test
  on head; if it fails again, run it on base; **only a reproducible head-only failure counts as a
  missed edge.** Base is only ever run for a candidate, so the common case stays at one sweep.

- [ ] **Pin every shadow comparison to an immutable snapshot.** There is no CI: this runs on one
  development machine where an emulated sweep takes tens of minutes to hours, and the tree changes
  while it does. A comparison across a changed tree compares two different systems. Record base and
  head, the dirty-diff hash, the source-tree and manifest digests, the selector version and the build
  artifact digests, and **refuse the comparison if any moved** - or run the whole sweep in a temporary
  git worktree, which is cleaner.

- [ ] **End shadow mode on evidence, per component.** A month that only saw audio changes says nothing
  about the driver, kernel or arch edges. Exit criteria: every edge type exercised, every change class
  exercised, the regression corpus fully caught, no false-negative observed, selector property tests
  green. Grade components separately - `audio` TRUSTED while shared kernel is still UNTRUSTED - so the
  saving starts where the proof is instead of waiting for the whole system.

- [ ] **Make trust a certificate against one model hash, not a permanent property of a name.** Evidence
  proves that *a particular selector, over a particular model,* did not miss anything. Change the model
  and the evidence no longer describes what is running, but the word TRUSTED survives - which is how a
  selector gets silently more dangerous over time while its record still looks clean. Store
  `TRUSTED(component, model_hash)` and **demote that component's closure to SHADOW the moment the hash
  moves**, where

  ```
  model_hash = hash(ownership registry + dependency graph + test catalog + the actual `covers`
                    declarations + applicability matrix + architecture policy + environment policy
                    + selector version)
  ```

  One hash, not a list of five. A list invites a sixth input to be added later and not hashed, and
  hashing a *schema* is the specific version of that mistake worth naming: turning `covers: [flac]`
  into `covers: []` leaves every schema identical and must still destroy the trust. Hash the
  declarations, not their shape. The fail-open rule ("a change to component metadata selects
  everything") is not a substitute: one full run passing proves the tree is healthy, not that the new
  model would have caught anything.

- [ ] **A corpus of real regressions, stored as commit ranges.** `base..head` plus the expected set of
  **`PlanItemKey`s** - check, architecture, environment and configuration together - replayed through
  the planner.
  Stored that way it exercises diff parsing, rename and delete handling, path ownership, the closure,
  test selection, architecture choice and environment choice, rather than only the last steps. This
  tree already has the material: the `RECV_CAPS` overrun, the clone-then-close capability duplication,
  the ungated device acquire, the frame use-after-free, the MS ADPCM block length.

- [ ] **Split `src/kernel` instead of treating it as one bucket.** Per-target arch trees and per-target
  linker scripts select their own target, per the table above; shared subsystems stay full-everywhere
  in phase one. `src/kernel/mem`, `sched`, `object`, `syscall` and `elf` are separate subsystems and a
  timer change should not permanently cost 205 tests on three architectures - but narrowing them is
  where a selector is most likely to be wrong, so write the risk classes now and apply them only
  after shadow evidence for that class of change. The driver crate needs the same treatment: at crate
  granularity a keyboard change tests the disk.

- [ ] **Escalate on measured cost, and model the cost as fixed plus variable, per environment.**
  `cost(architecture, environment, selection) = fixed_startup(architecture, environment) +
  sum(measured duration of each selected item)`. A plain sum of test times is badly wrong here: the
  measured fixed term is ~100 s on x86_64 and ~1450 s on aarch64, so a "90% smaller" selection is a
  15% cheaper run. The environment belongs in the key because a dev guest and a test guest do not
  start alike. When the estimate lands within some fraction of the full suite, run the full suite -
  derive that fraction from real timings, per architecture, because the honest answer on x86_64 may be
  "almost never scope, just boot once and run everything." A wrong cost estimate is the one error here
  that cannot produce a false green, so calibrate it last.

- [ ] **Turn age into a bound over real `PlanItemKey`s.** A test is not fresh; a *key* is. The
  architecture policy deliberately boots one target for ordinary userspace changes, so the steady state
  it produces is x86_64 fresh and the other two ageing - a bound keyed on the test alone reports the
  whole suite fresh while two targets rot. Key runtime, failure and shadow history the same way; an
  aarch64 timing says nothing about riscv64, and a test-guest timing says nothing about a dev guest.

- [ ] **Build the applicability matrix, and derive it from what compiles.** 205 tests exist on x86_64
  and 196 on aarch64, and `cfg(target_arch)` gating is spread through shared files - eight in
  `test_suites/kernel.rs`, six in `hardware.rs`, two in `sched/tests.rs` - so the path cannot answer
  which target a test exists on. Record `id -> { covers, applicable_architectures, environment }` from
  the compiled test lists, per target. Without it the age universe contains keys that can never be
  fresh because they do not exist, and an exact `TEST_SELECTION` can name a test the target's binary
  never compiled.

- [ ] **Name what actually runs the scheduled sweep.** There is no CI, so "on a timer" schedules
  nothing. Either a systemd timer on the development machine at a quiet hour, or - simpler and more
  honest for one machine - stale tests join the next manual run and the runner says it did so.

- [ ] **Keep a full snapshot sweep as well; the age bound is not a substitute.** Stale tests joining
  the next manual run spreads coverage across many different trees: some tests on Monday's commit,
  others on Wednesday's. That satisfies an age bound while never once establishing that **one** revision
  passes everything. Both are needed - the age bound catches individual rot, the snapshot sweep catches
  the combination. Run the whole suite on all three architectures at one fixed revision, and do it in a
  worktree so the sweep is not racing the tree it is judging.

- [ ] **Restore the release gate, unconditionally.** This was in the first draft ("the whole suite on
  all three architectures is right before a release") and was lost in the consolidation. It is not
  covered by anything else here: TRUSTED, the cost estimator, the age bound and the selector are all
  mechanisms for spending less on an ordinary change, and every one of them should be **ignored** when
  cutting a release image. Build all, check all, boot all three, full suite, at one immutable revision.
  Releases are rare and the insurance is nearly free; a wrong selector decision shipped in an image is
  not.

- [ ] **Measure the result and write the numbers here.** Selection size and wall clock, before and
  after, for a tool change, a library change, a service change and a kernel change. M0147 is the
  precedent: the measurement is what turned a plausible optimisation into a backed-out one, and this
  milestone should be as willing to record that its own idea did not pay.

- [ ] **Per-test `requires`, later - but not the environment, which is needed now.** Separating what a
  *test* is selected BY from what it needs to RUN still has no consumer: within one guest every test
  gets the same devices and fixtures. Revisit when a test needs a machine shape the default guest does
  not have. This is not the same question as the `host` / `test-guest` / `dev-guest` split, which has
  three consumers today and belongs in the planner from the first version.

## What this deliberately does not do

Nothing here weakens an assertion, deletes a test or makes a gate optional. The failure being designed
against is not a slow suite - it is **a fast suite that stopped looking**, which is what every gate in
`check.sh` exists to prevent. Every default errs toward running more: an unrecognised path gets the
whole suite, a missing declaration fails the build, and the smoke floor runs whatever else was
selected.

## Appendix: three rounds of outside review

A second model reviewed this milestone three times. The design above is the result; this records what
each round contributed and what was rejected, so a rejected idea is not proposed again.

**Round one** (read the file, not the tree) got four things factually wrong and they are worth keeping
straight: 115 is the wave-5 SELECTION, not the 205-test suite; `test.sh` boots QEMU **once** for the
whole suite, so there is no per-test boot cost to amortise with snapshots; drivers here are
**userspace** (`src/user/drivers/`), so the "change one driver, test the kernel" example describes a
monolithic kernel this is not; and there is no CI, so cancelling superseded runs does not apply. Its
real contributions were that `uses` is too narrow for IPC, syscall and device edges, that the
architecture claim was too absolute, and shadow mode.

**Round two** read the tree properly and found a live defect: `component_tags` excluded `*.sh` and
`src/tools/*` from kernel testing entirely, which excused `src/boot/mkimage.sh` (builds the image),
`src/boot/qemu-run.sh` and `test-kernel.sh` (boot and judge the guest) and `src/tools/mkpackages`
(listed in `VOLUME_SOURCES`, so its output IS the system volume). Fixed in `lib.sh` at `78e18ee`.

**Round three** found that fix over-claimed, and it was right. **Only the path dimension of that
false green is closed.** `test.sh` still defaults to x86_64 (`archs=(x86_64)`), so a change to
`qemu-run.sh` - which carries thirteen architecture-specific branches - resolves to FULL and then runs
FULL on one target. A bug in its riscv64 branch still passes `--for-change` green. The automatic
architecture policy above is what closes it.

Round three also produced the design's two best ideas - dry shadow, and one planner instead of one
selector per tool - and corrected three overstatements of mine: that a broken gate fails loudly on its
own, that a mechanical scan proves architecture neutrality, and that `test.sh --for-change` exiting 0
means what a caller will read it as.

Its most useful structural point was not technical: the document had grown two generations of design
in one file, with the superseded version first. The section above is now the single authoritative
specification, and this appendix is history.

**Round four** reviewed the consolidated version and was right on every point; nothing was rejected.
Its central finding is that the graph was to be derived from `manifest.toml`, which describes the
**dynamic** link graph only - so all of `src/fs` would have been invisible. Verified and worse than
reported: 27 of 108 crates are absent from the manifest, the kernel statically links `liberfs`,
`partition` and `fscore`, and its `[dev-dependencies]` pull in eleven userspace codecs, so a `flac`
change rebuilds the kernel's test binary. The current hand-written table has the same hole
(`COMPONENT_TAGS["src/fs"]` reaches neither the kernel nor the loader), so this is a live defect being
inherited, not one being introduced. It also caught the document contradicting its own definition of
`covers` - one task demanded `program_elf(X) ⇒ covers(X)`, which is the `touches = covers` collapse the
definition exists to prevent - and it caught test age being keyed per test when the architecture policy
guarantees the three targets age at different rates. Its other adopted points: trust must be a
certificate against a versioned model rather than a permanent property of a name, fail-open cannot be
implemented inside the process that fails, the arch classifier needs a boot-target set per class and
not just a sensitive/neutral verdict, the planner needs execution environments today because
`DEV_PROFILE` and `TEST` are mutually exclusive, the release sweep was lost in the consolidation, an
age bound is not a snapshot sweep, cost is fixed plus variable, and a shadow miss must be
distinguished from a flake.

Checking round four's claims turned up two things it did not raise. The measured selection was
recorded as "115 of 212"; the guest's own line says `running 109 tests (96 skipped, 205 total)`, and
the denominator differs per target (196 on aarch64) because arch-gated tests are not compiled
elsewhere. And solving the two measured points for a fixed and a variable term shows the fixed cost
dominates so heavily - ~100 s of a 140 s x86_64 run - that **test selection is the least valuable idea
in this milestone**; the architecture policy and the host suites are worth several times more. The task
list is now ordered by that measurement rather than by the pipeline.

**Round five** raised four points; all four were adopted and one of them found a defect in round
four's own fix. Round four established that the graph must include static Cargo edges. Round five
asked *in which configuration* those edges are read, and the answer in this tree is damning:
`default = []` everywhere that matters, `tools` reaching its 20 client libraries only through
`shared-image`, all 15 protocol crates reaching `ipc-client` only through `channel-client-impl`, and
`build-shared.sh` building the image with `--no-default-features --features shared-image`. A selector
reading the default configuration would report that **nothing depends on `ipc-client`** - a false-green
machine built by the fix for false greens. The rule is now that an edge existing under any buildable
configuration is an edge, and the same question turned out to apply to `check-host-tests.sh`, which
tests those sixteen crates only in the configuration that never ships.

Its second point was that `(test ID, architecture)` is not enough without knowing which pairs exist:
205 tests compile on x86_64 and 196 on aarch64, so a bound over all pairs chases combinations that
cannot be fresh. Verified, and worse than stated - `cfg(target_arch)` gating is not confined to the
arch trees but scattered through `test_suites/kernel.rs`, `hardware.rs` and `sched/tests.rs`, so
applicability cannot be inferred from a path and must be derived from what compiles. Its third and
fourth points were structural and both correct: the five-part trust certificate should be one
`model_hash` over the actual declarations (hashing a *schema* leaves `covers: [flac]` -> `covers: []`
undetected), and every history and fixture should be keyed on the planner's own unit,
`PlanItemKey = (check, architecture, environment)`, so a regression fixture can check that the right
environment was chosen and not only the right test.

Round five's closing advice is also taken: further theoretical review has passed the point of
diminishing returns. What finds the next class of defect is implementing phase one and reading the
plans the selector actually produces.

**Round six** judged the design implementable and raised two data-model corrections, both consequences
of round five's own fix and both adopted. First, `PlanItemKey` had no configuration field, so the two
runs that round five had just declared necessary - `proto` under default features and under
`shared-image` - collide on one key, and the shipped configuration silently inherits the default one's
freshness. Second, `cargo metadata` has three dependency kinds, not two: build dependencies are
neither linked nor tested, which makes them the easy ones to filter out, and there are four here -
`system-manifest` generates `manifest.rs`, `library_paths.rs` and `program_paths.rs` for CoreServices
and the test volume paths for the kernel. Dropping that edge would let a change regenerate shipped
source with nothing selecting it. Writing it down also settled a question neither round asked:
`manifest.toml` is itself a build input with `generation.build` edges into the kernel and CoreServices,
not only the file the provider graph is read from.

That closes the review. The next audit is worth doing against `./verify.sh --for-change --plan` over
twenty or thirty real commit ranges from this repository's history, not against this document.
