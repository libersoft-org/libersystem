# M0088 - FAT: allocation bounds and spec conformance

Status: COMPLETE. Two allocation bounds that bite on large or nearly-full volumes, plus the
conformance debts that make our volumes look wrong to other systems.

*Condensed 2026-08-08.*

- **`read_chain`'s loop guard assumed 4-byte FAT entries**, so a legitimate FAT16 file past ~50% of
  the volume, or a FAT12 file past ~38%, failed with a false `Invalid`. The guard is the volume's
  cluster count now - no legitimate chain can be longer, for any family.
- **`max_cluster` came from the FAT's byte size alone**, which has slack past the real cluster count.
  On a nearly full volume the allocator handed out clusters **past the data region**: the write
  landed outside the volume and the FAT entries already written leaked as an orphan chain. The real
  cluster count - the BPB arithmetic, or exFAT's `ClusterCount` field, which was never read - caps it.
- **`gen_short` violated the 8.3 rules**: no `~N` uniquification, so two long names with a common
  prefix produced *identical* short entries; no sanitisation of the illegal set; and a leading-dot
  name yielded an empty base, i.e. a short name starting with a space, which the spec forbids.
- FAT32 reserved top-nibble bits were zeroed rather than preserved through a read-modify-write.
- **FSInfo was never updated**, so other systems saw a stale free-cluster count on media we wrote.
- **`..` was broken on FAT32**: a dot-dot entry pointing at the root carries first cluster 0, which
  was mapped to the FAT12/16 fixed root region - nonexistent on FAT32.
