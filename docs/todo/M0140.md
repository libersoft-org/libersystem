# M0140 - The build interface: scripts with flags, and a Justfile that stops being one

`just --list` prints 123 recipes. That is the whole discovery surface for building, running,
testing and imaging this system, and at 123 entries nobody reads it - they learn four commands and
never find out the other 119 exist.

The count is not the defect. It is the symptom of four different causes, and each needs a
different answer:

| family | count | why it is that many | answer |
| --- | --- | --- | --- |
| `*-aarch64`, `*-riscv64` | 26 | an orthogonal dimension spelled into names | a flag |
| `test*` | 30 | three independent switches (arch x build-only x fast) - `test-tags` alone is 12 names | flags |
| `*-conformance` | 12 | a LIST OF DATA written as code | one command over a list |
| `*-check` | 16 | gates; a caller wants "all" or "one" | one command over a list |
| `dev-*` | 23 | not a build system at all - a control surface for a running guest | its own script |

- Done when: the build interface is a set of scripts, each with `--help`, each taking flags rather
  than encoding its arguments in its name; everything they fully replace is deleted from the
  Justfile; what remains in the Justfile is listed here with a reason for remaining; and the three
  suites are green through the new entry points on all three architectures.

## Why scripts rather than a smaller Justfile

Both would work, and the honest framing matters because it decides how much of this is worth
doing.

**The tool is not the cause.** `./test.sh --arch aarch64 --tags fs --build-only --fast` is the
same matrix as `test-tags-build-fast-aarch64`, only better spelled. The reduction from 123 to
roughly a dozen comes from collapsing dimensions, and that is possible in either tool. A migration
that does not collapse them ends with 123 things wearing flags.

**The logic is already in scripts.** `mkimage.sh`, `qemu-run.sh`, `test-kernel.sh`,
`test-preflight.sh`, `lab.py` do the work; many recipes are already `#!/usr/bin/env bash` blocks.
The Justfile is mostly a dispatcher, so this is not "rewrite in shell" - it is "replace the
dispatcher".

**What scripts add:** real flags, `--help` per command, one language, no dependency on `just`.

**What they cost, and it is the part to be careful about:** the Justfile's dependency graph, which
runs a prerequisite once and in order. `test-riscv64: test-preflight-riscv64 loader-riscv64` is a
statement that both are built first and exactly once. In shell that becomes explicit, and getting
it wrong is not theoretical - this session shipped a disk image carrying the TEST kernel because a
volume was assembled before the slot it read from was written, and the same shared-slot mistake
put x86_64 programs on a riscv64 ESP. The replacement must be deliberate:

    ensure() { local key="$*"; [[ -n "${_done[$key]:-}" ]] && return 0; _done[$key]=1; "build_$1" "${@:2}"; }

## The scripts

Seven, sharing one library and one flag vocabulary. Every one answers `--help`.

    tools/lib.sh          # arch validation, ensure_*, logging, die, the shared flag parser
    tools/build.sh        --arch all --part kernel,user
    tools/run.sh          --arch x86_64 --display vnc,spice
    tools/test.sh         --arch all --tags fs,net --fast --build-only
    tools/image.sh        --format iso,img --size 1G
    tools/clean.sh        --part boot,kernel
    tools/check.sh        --all | --only volume-layout
    tools/dev.sh          up | log | key ...

`--part` rather than `--component`: "component" already means the SDK component in this tree,
`--stage` collides with the manifest's stage column, and `--target` with cargo's target triple.

`--part` names a closed set - `kernel`, `user`, `libs`, `loader`, `packages`, `volume`, `sdk`,
`all` - and NOT individual libraries or executables. Naming those here would be a second source of
truth beside the manifest, and it would drift exactly as `INSTALL.md` drifted; cargo already
selects them, so finer choices pass through: `./build.sh --part user -- -p imgconv`.

## What this milestone will NOT do

- **Collapse recipes whose bodies genuinely differ.** `loader-riscv64` assembles its EFI image by
  hand from a linker script and `llvm-objcopy`; `loader-aarch64` does not. Hiding that behind a
  flag moves the branch inside the body - the same complexity, harder to see.
- **Bury the architectures behind a default.** This tree has already recorded, twice, that a path
  nothing exercises rots. If `./test.sh` means x86_64, then `--arch all` must be equally at hand.
- **Lose the comments.** Most of the Justfile's 1065 lines are prose recording WHY a recipe exists,
  including traps that have already come back once. They move with the recipes or the traps do.

## M0140a - The cheap collapses

- [x] `dev-*` (23) becomes `./dev.sh <verb>`. These are wrappers over `lab.py` and are not
  build steps at all.
- [x] `*-conformance` (12) becomes `./check.sh --conformance [format]`, iterating a list. The
  formats are data.
- [x] `*-check` (16) becomes `./check.sh [--gate name]`, same shape. CI wants all of them; a human
  wants one.

## M0140b - The matrices

- [x] `test*` (30) becomes `./test.sh --arch <a> [--tags ...] [--fast] [--build-only]`.
- [x] The remaining `*-aarch64` / `*-riscv64` pairs become `--arch`.

## M0140c - Build and images

- [x] `./build.sh --part ...` over the closed set, with the prerequisite guards written explicitly.
- [x] `./image.sh --format iso|img|qcow2 --size <n>`.

## Done, and what it cost

**123 recipes -> 30; 1065 lines -> 368.** Eight scripts at the repository root, each with `--help`:
`build.sh`, `run.sh`, `test.sh`, `image.sh`, `check.sh`, `clean.sh`, `dev.sh`, and `format.sh`
which absorbed the formatting recipes.

Things this turned up that were not the point of it:

- **The shared-library list was a topological sort nobody had written down.** It lived in the
  Justfile three times, once per architecture, in a 900-character line - and this milestone briefly
  gave it a fourth copy in a script. It is derivable from `manifest.toml`, which calls itself the
  only hand-edited source of truth, so the tool grew a `library-crates` projection. Taking it
  alphabetically failed at once (`adpcm has no compile identity for provider lsrt`): the ORDER
  carried dependency knowledge, which the manifest's `providers` field can now supply properly.
- **`fmt` and `fmt-check` listed 67 crate directories by hand, twice.** The tree has 106 crates, so
  39 were never formatted and never checked. `format.sh` finds them instead.
- **`build-steps.sh` stopped existing.** It was split out because `test.sh` and `run.sh` also built
  things; once neither did, it had one caller and was just a second file to open.
- **Environment variables became flags.** `SMP=`, `MEM=`, `SERIAL=`, `TEST_TIMEOUT=`, `VNC_ADDR=`,
  `SPICE_PORT=` are `--smp`, `--mem`, `--serial`, `--timeout`, `--vnc-addr`, `--spice-port`. They
  reach the lower layer as variables still - the flag is the interface, the variable is plumbing -
  but `--smp abc` is now refused where `SMP=abc` went silently through to QEMU.

Two defects this milestone CAUSED, both found by running the suites rather than by reading:

- `require_built` checked the loader under the KERNEL's target triple. The loader is a UEFI
  application on x86_64 and aarch64 (`*-unknown-uefi`) and a hand-rolled ELF on riscv64, so a build
  that had just produced it was reported missing.
- `build.sh --part all` put the kernel on the system volume, because it built both. A shipping
  medium wants that; a test run does not, because the suite boots its own kernel from the ESP and
  the loader prefers the volume's. The x86_64 suite booted the SHIPPING kernel into an interactive
  shell and timed out after fifteen minutes. The kernel now goes on the volume only for
  `./image.sh`, which is the step that assembles a medium.

The second is the third time in this tree that a shared build slot has served the wrong artifact to
something. The others were `.build/boot/kernel` and `.build/boot/init.pkg`. A fourth followed
before the suites went green: `.build/boot/volume.pkg` is written by every architecture's build, so
after `--arch all` it held riscv64's, and the x86_64 suite failed at `dynamic test main is ELF`
parsing binaries for the wrong machine. The morning's fix had exported qualified copies for the
two device-tree architectures ONLY, leaving x86_64 with nothing but the shared name to fall back
to - a symptom fixed in two places instead of a cause fixed in one. M0140e removes the shared names
outright.

- **`shfmt` rewrote associative-array subscripts as arithmetic.** `[volume-layout]=` became
  `[volume - layout]=`, breaking the name of every gate in `check.sh`. Introduced by running
  `./format.sh` over the new scripts and not re-testing them afterwards - and `--gate
  artifact-metadata` had been demonstrated working before the formatting, so the evidence existed
  and was not re-checked. Quoted subscripts survive formatting; verified by formatting again.

## M0140f - Refuse a stale build instead of testing one

`./test.sh` deliberately builds nothing, so that a suite cannot quietly test something other than
what was meant. The other half of that bargain is missing: it does not notice when what IS there is
older than the sources, and `./build.sh` defaults to x86_64 - so `./build.sh --part user` followed
by `./test.sh --arch aarch64` runs the previous binary and says nothing.

That cost two twenty-minute runs in one afternoon, both of them mine, and both times the failure
looked like a defect in the code under test.

- [x] `require_built` already refuses a missing loader; make it refuse a system volume or service
  binary older than the sources it was built from, naming the command that would fix it.

  Done. The volume is compared against the sources it is built FROM - `user`, `fs`, `wire`, `abi`,
  `proto`, `idl`, `mkpackages` - and the loader against `loader`. Not against the kernel's sources:
  `cargo test` compiles that itself as part of running the suite, so comparing them would refuse
  every run after an ordinary test edit.

  The message names the file that is newer and the command that fixes it, because the failure it
  replaces did neither: the suite ran the previous binary and reported a defect in the code under
  test. Verified in both directions - touching a service source refuses the run, rebuilding clears
  it, and the same for the loader.

## M0140e - Run the three architectures at once

The suites take about an hour in sequence, and roughly 55 minutes of that is two emulated guests
booting one after the other. They could boot together: nearly everything they touch is already
per-architecture - the ESP, the system disk, the FAT/ISO/UDF/USB media, and a fresh OVMF variable
store per run.

- [x] Stop writing the unqualified `init.pkg`, `volume.pkg` and `kernel` in `.build/boot`. Every
  architecture writes them, so they hold whichever ran last - which has now served the wrong
  artifact to something three times, most recently a riscv64 volume archive to the x86_64 suite.
  Qualified copies exist for all three; the unqualified names have to stop being written, not just
  stop being read.
- [x] `aavmf-vars.fd` is shared, which only matters between two aarch64 runs, but it is the same
  shape of defect and costs one `mktemp` to fix.
- [x] Then make `--arch all` run them concurrently. Cargo serialises the compile through its
  target-directory lock, which is fine - the compile is cached and short, and the boots are what
  takes the hour.

Not attempted while the sequential run was still red: with parallelism on, a failure has two
possible causes and no way to tell them apart.

Done 2026-08-04. The archives are written under their qualified names AT SOURCE rather than copied
to them afterwards - the after-the-fact copy left the shared name in place for anything that still
read it, which is why the same defect kept coming back. Four consumers moved with it (`mkimage.sh`,
`check-development-gate.sh`, `lab.py`, the `volume-layout` gate), and a fifth turned up only when
the image build failed: `verify_boot_artifacts` checked a third path, and its advice named `just
build`, a command this milestone had already deleted.

`--arch all` waits on each architecture separately, so one failure does not hide another's result.
The stray-QEMU check had to be scoped to the architecture being started, or a legitimate concurrent
run would have refused itself.

Left behind and harmless: `boot-packages-*.pkg` and `modules-*.pkg` in `.build/boot` are dead
artifacts of the retired wrapper. Nothing reads them; `./clean.sh --part boot` removes them.

MEASURED, 2026-08-04, all three green either way:

| | sequential | concurrent |
| --- | --- | --- |
| x86_64 | 84 s | 84 s |
| aarch64 | 1704 s | 1704 s |
| riscv64 | 2016 s | 2177 s |
| wall clock | 63 min | **36 min** |

A 43% saving, and the contention is smaller than expected: aarch64 was unchanged and riscv64 lost
8%. Two TCG guests do not saturate this host, so the estimate that they would compete hard was
wrong in the useful direction.
