# P02M0104 - Incremental development and persistent QEMU test loop

Status: REOPENED (2026-08-16) by a fourth-party audit round, recorded in AI/audit/boot.md. The findings are appended as open tasks in the section at the end of this file; each was checked against the tree before being written down, and where a check contradicted the audit that is recorded with the task rather than dropped. Previously: COMPLETE, in six phases (P02M0104a-f).

Ordinary work on one leaf tool used to pay the cost of the whole system: a focused run reassembled
the volume package, restaged the boot image, booted a fresh guest and printed the entire build and
boot transcript. This milestone removed that coupling, in increasing order of implementation cost.

*This file was condensed on 2026-08-08. What was cut is the specification of work now visible in the
code, and the per-run validation enumerations that were evidence at the time. What is kept is why
things are the way they are, what was measured, what was rejected, and what was learned the hard
way.*

## Constraints that still bind

Two structural facts shaped the design and are worth not rediscovering:

1. **The staged artifact set reaches the guest differently per architecture.** On x86_64 the init
   and volume packages are separate boot modules; aarch64 and riscv64 embed them into the kernel
   binary with `include_bytes!`. Any claim that an artifact change avoids a kernel rebuild is
   therefore architecture-specific and must be verified per target.
2. **Application scenarios were compiled into the kernel test binary**, so adding one was a kernel
   change by construction. P02M0104d undid that; before it, no build-cache work could make application
   iteration cheap.

**Rejected transports, with reasons.** No virtio-fs, 9P, SMB, NFS, FTP or ambient host-directory
mount. A host-writable disk shared with a live guest filesystem was rejected outright: concurrent
host and guest writes to one mounted image corrupt it. Executable replacement goes through the
validated artifact publication protocol instead.

## The baseline everything is measured against

`just dev-baseline <cold|warm|leaf|provider>` records per-stage host-nanosecond events. Measured on
the documented x86_64 KVM host before any of the later phases:

| | |
|---|---|
| Cold build | 414.63 s |
| Warm, no change | 10.21 s |
| One leaf tool edited | 101.67 s |
| One shared provider edited | 94.73 s |
| The seven-test guest scenario itself | 24-40 ms |
| Output volume | 136 lines cold, 3 warm |

The scenario costing 40 ms inside a 101-second iteration is the whole argument for this milestone.

## What was built

**P02M0104a - cost reduction without architecture change.** Transcripts moved to files under `.build`
with a bounded tail on failure; x86_64 test mode capped at four CPUs (interactive boots keep the
host count); per-artifact build chatter reduced to one summary line; dynamic-report drift detected
during the build instead of surfacing later as a separate failing check.

**P02M0104b - builds proportional to the change.** `just dev-build <artifact> [target]` resolves the
manifest artifact and builds only its dependency closure, with every `.lslib` and intermediate
object an independently cached unit shared by all consumers. Concurrent requests for the same unit
coalesce behind one build. The cache is per target.

The cost of *proving* nothing changed turned out to dominate: on the cache-hit path the builder was
resolving one manifest row per artifact in a separate process, digesting each crate tree, rehashing
each archive and re-reading each output ELF - so it scaled with all 131 artifacts rather than with
the change. Fixed by recording per-artifact state and accepting a no-op through one batched `stat`
over size, inode, mtime and ctime, escalating to content hashing only for entries that moved.
Budget: a no-op single-artifact build inside one second, independent of artifact count.

**P02M0104c - persistent guest and hot artifact publication.**

- The development profile is named over QEMU `fw_cfg`, not through the boot protocol or the boot
  image, so selecting it changes no byte the guest is built from and needs no rebuild.
- Ownership is an `flock` held by the broker across the fork, so the kernel releases it when the
  broker dies and there is no stale lock to break by hand.
- **The broker is the only reader of the guest UART**, which is what makes the console detachable:
  it drains QEMU whether or not anyone is watching, so no absent or slow terminal can back the
  socket up. Sends to clients are non-blocking - a terminal that stopped reading loses bytes rather
  than stalling the guest. 256 kB of replay is delivered on attach.
- Staleness is decided from **identity, not symptoms**: six named input classes (protocol, kernel,
  loader, packages, image, topology), compared by content rather than timestamp, each naming the
  scope of its rebuild. A reattach deliberately keeps the recorded fingerprint - the broker changed,
  the guest did not - so a stale instance cannot be laundered by putting a new broker on it. Costs
  173 ms.
- The development channel is a **second single-port virtio-serial device**, not MULTIPORT
  negotiation. One measured finding shaped it: a generic `virtserialport` is never opened without
  MULTIPORT, so the guest's writes vanished entirely. A console port is required, and its cost is
  that UEFI writes its console output to every console-class device it enumerates, leaving a
  firmware preamble on the x86_64 channel. Framing simply begins at the guest's first byte rather
  than paying for MULTIPORT to remove a preamble. `DeviceInfo` gained the PCI address so two devices
  of one type stopped being indistinguishable to userspace.
- The control protocol is a 16-byte header plus payload behind a `Sink` that knows nothing about how
  bytes reach it. Every bound is a constant reported in the handshake: 64 kB per frame, 16
  outstanding, 32 MB per artifact, 64 MB of registry, three generations per artifact, 4 kB of
  terminal input. Three deadlines - fragment, open publication, session - each dated from when the
  thing it bounds began.
- **Provider compatibility is a written rule, not a judgement**: `bootproto::compat`, next to the
  ELF reader both halves already share. A candidate is compatible when its exported dynamic symbol
  set is a superset, no retained symbol changes kind/binding/size/visibility, the provider list and
  resolved closure are unchanged, and the identity matches in every field except the content digest.
  Publication *records* a verdict; it never gates. The loader decides again at launch, because the
  registry holds incompatible generations too.
- The registry is volatile, lives in the agent's memory and never touches the canonical system
  volume, so a reboot returns the guest to its built state. It is gated on the development boot
  profile - but the *protocol* is not, because the same channel exists in the cold test
  configuration of all three targets, where a runner must still handshake, type and reset.
- ProcessService resolves from the registry at the single point where it turns a manifest-resolved
  name into bytes. **There is no second launch path.** A refused generation fails the launch rather
  than falling back to the installed provider - falling back would run something other than what was
  published while looking like success.
- The boundary is compile-time first: `dev_agent` and `dev_channel` carry
  `required-features = ["development"]` and a shipping build produces neither binary, rather than
  shipping code that refuses at runtime.

**P02M0104d - application scenarios outside the kernel image.** The interpreter is not in the guest at
all: `src/boot/scenario.py` runs on the host and drives a running instance over the control protocol
and the broker's serial stream, so neither a scenario nor the runner costs a package reassembly, a
kernel relink or a QEMU restart. Scenarios are versioned TOML validated in full before the first
step runs; no step hands a string to a shell, host or guest, and the key and pointer vocabularies
are closed and checked against the runner's own tables - an unchecked name would be a way to run
monitor commands out of scenario data.

Key and pointer input go through the emulated devices rather than around them. That is the point of
them: terminal input over the control protocol reaches the console directly and proves nothing about
the input stack, while an injected key event takes the path a person's hand takes.

**P02M0104e/f - gates, and the defects this milestone made.** The invalidation matrix lives in
`docs/DEBUG.md` (twelve rows). `just staged-image-check` verifies 133 artifacts per target in 0.2 s
and runs in every test preflight. `fast-path-check` proves `dev-build` and the authoritative rebuild
produce byte-identical artifacts, and runs as the penultimate phase of `just release`.

## Budgets in force

| | Budget | Measured |
|---|---|---|
| Warm no-change build | 1 s | 0.37-0.40 s |
| Warm leaf iteration (build, audit, publish, scenario) | 6 s | 5.6-6.0 s |
| - build phase | 3.6 s | 3.2-3.4 s |
| - publish phase | 0.6 s | 0.4 s |
| - scenario phase | 2.6 s | 2.1-2.3 s |
| `dev-reboot` to a prompt | - | 5.9 s (against 25 s for down+up) |

Two things about measuring this loop, both learned by getting them wrong:

- **The first leaf iteration after `dev-up` costs 8.4 s**, with the build phase at 5.9 s against the
  3.2 s every later sample shows. Warm the loop once before sampling, or say plainly that the first
  iteration is excluded.
- The six-second budget was five until 2026-07-30. It was restated against measurement, not to make
  a red gate green: the one implemented optimization recovered a tenth of a second where most of the
  gap was expected, and the proposals that would close the rest buy time with correctness.

Of a 3.2-3.4 s warm leaf build, only about 1 s compiles, links and audits; the rest proves that
nothing more needed to. Roughly two thirds of a leaf build is now proof rather than work - which is
not waste, but it is the dominant term, and it was not when the same iteration cost 101.67 seconds.

## Optimization proposals, recorded and not implemented

1. **Bound the retained content-addressed object generations per artifact.** Nothing prunes them:
   `uname` held 12 cached objects after repeated one-line edits against 3 for an untouched tool, 167
   across the tree, and the state path set is built by a `find` per program over a 1,407-entry
   directory (71 ms per call). Both terms grow with edit history rather than with the closure. Risk:
   an object a valid executable state still references must never be pruned, or the next build
   reports `no valid current ET_REL object`. *(Implemented later; recovered at most 0.1 s.)*
2. **Prove a reused provider without re-deriving its closure** - 384 ms goes into concluding that
   the single provider in a leaf closure did not change.
3. Reduce the 502 ms tail after the last stage (state, summary, cleanup).
4. Trade correctness for time in the per-artifact state check - recorded and not recommended.

## Lessons worth keeping

**A capability added to a service's bootstrap is a change to every caller that starts it - and one
of those callers is a test harness that no ordinary run exercises.** ProcessService gained a registry
handle and the kernel test harness was never updated, so it blocked on a receive that never
completed. What the suite reported was three layers downstream: "PermissionManager did not request a
fresh NetworkService client", a message that sends the reader to the network stack, where nothing is
wrong. It took three rounds of tracing to walk back. The recorded baseline had this written down as
a pre-existing unrelated failure, which is how it survived.

**A closed channel is permanently ready, so waiting on it spins.** This was the answer three separate
times, in three different programs: the protocol serve loop, the launched-program output wait, and
the driver detecting its dead agent (a restart that should take three seconds took nine). Poll for
the closure where it happens.

**A query whose deadline expired left its reply to arrive later**, so the next query read the
previous answer and the channel ran permanently one behind: every launch loaded what the registry
held at the launch before. Worse than not resolving at all, because it looks like it worked. Queries
now drop anything queued before asking.

**`cfg!(feature = ...)` does not work inside a build script** - a build script is a separate
compilation and the macro reports false. Reading `CARGO_FEATURE_*` fixed the value but not the
caching, because `rerun-if-env-changed` does not apply to variables cargo sets itself. Both failures
are silent and both leave every assertion inside the build agreeing with itself while producing the
wrong image.

**The userspace heap never merged adjacent free blocks.** `rt`'s allocator pushed each freed block
onto the head of a list and left it there, so a program that repeatedly allocated and freed a large
block ended with free space split into pieces no later request fitted; `grow` then mapped another
megabyte region, and every one stayed mapped for the life of the process. Nothing was unreachable -
each region had an owner - which is exactly why no handle count and no component's memory ever moved.
Measured after the fix: `imgconv` from 479 frames a launch to zero across twenty launches, `uname`
from 103 to zero.

The search is worth recording because almost none of it was the problem. Eliminated by measurement:
not time, not the terminal, not the console duplicate handed to a child, not reading files, not the
Domain, not process teardown. Found by two kernel counters - live `Process` objects and live
`MemoryObject`s with their pages - printed on every process creation: processes returned to baseline
every time while memory objects climbed by one megabyte-sized object per launch. Two readings were
self-inflicted: twenty "launches" that cost nothing had never run (the command did not exist and its
error was swallowed by `capture_output=True`), and a kernel test that appeared to reproduce the leak
was measuring its own probe.

**`grep -q` inside a pipeline under `pipefail` is a race.** `grep -q` stops at its first match and
closes the pipe; the producer's next write fails with EPIPE, llvm tools report exit 74, and
`pipefail` makes that the status of the whole pipeline - so a successful match read as a failure.
Measured on a staged object: 1 failure in 2000 idle, **377 in 2000 with every core busy**. One of the
28 sites had the opposite symptom and silently PASSED what it exists to catch, because an EPIPE made
a present INTERP read as absent. A `source-hygiene` rule now rejects the construct, checked against
a reintroduced violation rather than only against a clean tree.

**A gate whose own measurement can become a cache hit is the failure it exists to catch.** The
performance gate edited a fixed comment to force a rebuild, and the second run was served from the
content-addressed cache - so it timed a cache hit while reporting a rebuild. The comment now carries
the clock.

**It was never a stall.** A cold aarch64 development boot appeared to hang inside module loading,
and four layers of tracing produced a different stall location on every run. The diagnostic prints
were the slowness: each goes out of an emulated PL011 a byte at a time, one per segment of every
module of every service. A boot built without them reaches the prompt perfectly well. Everything
about a "varying stall location" was an artefact of watching a slow boot and stopping at different
points.

**The frame check is strict from the second run of a scenario onward, not always.** A program
launched for the first time grows its heap to a working size and keeps it - memory in use, not
memory lost. Three scenarios failed a zero-tolerance check for exactly that reason, and lowering the
check to accommodate them would have made it blind to a real leak of the same size. What no
legitimate cost explains is a scenario paying again what it already paid.

**A test that has not been seen to fail is not known to be testing anything.** Both halves of the
input-events scenario were checked against their own negative control: with the pointer step removed
the viewer never redraws, and with the quit removed the restoration assertion fails naming all four
pieces of terminal state.

**When a staged image is corrupt, copy it aside before rebuilding.** An aarch64 image would not boot
past DeviceManager - no error, no fault - and deleting the staged directory fixed it outright, taking
the evidence with it. The mechanism was never identified and now cannot be. A red test caused by
build state is indistinguishable from one caused by code, which is what `staged-image-check` exists
to prevent.

**P02M0104f, the defects this milestone made:** one symptom that did not reproduce and was recorded
wrongly in the first place; 216 MB of `.o` and `.rmeta` link inputs staged across three targets,
answered by taking them out rather than by auditing them; a preflight stamp published through a
temporary name two concurrent runs shared; and one timeout serving three architectures of very
different speed, which made `just test-all` unable to pass at all. `dev-up` now takes a
`--build-timeout` (1800 s) separate from its boot `--timeout` (240 s), and each deadline names which
wait it bounded.

## Fourth audit (2026-08-16): `AI/audit/boot.md`

Thirty findings against `boot/` - the QEMU harness, the scenario runner and the development loop.
Two are Critical and both are operational safety rather than correctness: they destroy things
outside the run.

- [x] **`boot`, `test` and `quit` kill every matching x86 QEMU process owned by the user
  (BOOT-001, Critical).** A developer with an unrelated QEMU open loses it to a test run.
- [~] **An x86 cold scenario reuses and deletes the persistent instance's live control namespace and
  writable disk names (BOOT-002, Critical).** Control namespace separated; the writable images are
  still shared. A cold run and the persistent instance this milestone
  exists to provide destroy each other.
- [~] **Direct AArch64 and RISC-V boots do not pass the init package required to start userspace
  (BOOT-003, High).** Runner and kernel both carry the hand-off now; the kernel halves are written
  and not yet compiled, because that needs the two slow cross builds.
- [x] **False greens in the test oracles (BOOT-008, -009, -019, -028, all High/Medium).** `absent`
  observes at most two seconds whatever deadline it declares; a `RUN` timeout is returned as
  ordinary output, and prompt-shaped program output can end a request early; the performance tracer
  can produce a trace without observing boot; input-producer failures can be converted into stable
  digests and stamped current. Each of these is a test that reports success without measuring its
  subject - the class this tree has already been burned by, and the reason `AI/CLAUDE.md` says a
  green test is not evidence until it has been watched to fail.
- [~] **Artifact freshness (BOOT-005, -006, -010, -030, High).** BOOT-005, -006 and -010 are closed;
  BOOT-030 - target-qualified, content-addressed scenario fixtures - is not started. Media caches keyed on existence and
  mtime, non-atomic and able to retain partial fixtures permanently; an image cache that omits
  direct inputs, trusts unverified cached output and can ignore manifest-generator failure;
  persistent-instance fingerprints that omit relevant source and environment inputs; scenario
  fixtures that are stale-prone, non-atomic and fixed to x86 despite a cross-target cold runner.
- [x] **Cleanup and identity integrity (BOOT-004, -024, -027, High).** A failed `dev-down` removes
  live coordination state and stale identity can target a REUSED process group; `dev-up` can report
  ready without recording a boot generation, disabling restart detection; common protocol failures
  escape as `SystemExit` and bypass scenario teardown entirely.
- [x] **Opt-in VNC and SPICE consoles are unauthenticated and listen on every interface by default
  (BOOT-011, High).** Bind to loopback, and require an explicit opt-out to do anything else.
- [x] **Timeouts do not bound several blocking operations (BOOT-007, High).**
- [x] **The boot harness had no tests of its own (found while fixing the above).** `boot/harness-test.py`
  and the `boot-harness` gate: 25 host tests against fakes, no guest and no QEMU, each written
  against the broken version first and watched to fail on it.
- [~] **The medium findings (BOOT-012 through -023, -025, -026, -029).** Closed: -012, -013, -014,
  -015, -016, -017, -018, -019, -022, -023, -025, -026, -029. Open: -020 (weak test claims) and

  IDs so an asynchronous event can be read as a reply; the console broker silently losing
  nonblocking partial writes; serial-log cursors advancing past unread bytes; `UnboundLocalError`
  hiding the real failure; no per-instance lock; a `pipefail`/`head` failure inside the watchdog; the
  performance gate editing a tracked source without `finally` recovery; unreproducible image
  assembly; shared screenshot scratch paths; UEFI runs racing through shared ESP paths and deleting
  other runs' firmware stores; decoders indexing untrusted-length input; leaked scratch files; and a
  documented-executable tracer tracked 0644.


### BOOT-001 and BOOT-011 closed; the rest of the harness priced (2026-08-18)

**BOOT-001** ran `pkill -9 -f qemu-system-x86` before `lab boot`, before `lab test`, and again in
`lab down` - a PATTERN match across every process the user owns. A developer with an unrelated QEMU
open lost it to a test run, and the pattern cannot tell whose guest it is. The lab starts its guest
with `start_new_session=True`, so it has a process group of its own: that group is recorded at launch
and killed by id, and only after `pgrep -g` confirms the group still holds a QEMU - a recorded group
whose number has been reused is the same mistake one step along. No QEMU flag needed, and nothing the
lab did not start can be reached.

**BOOT-011**: `-vnc 0.0.0.0:0` and `-spice addr=0.0.0.0,disable-ticketing=on`. Ticketing off means no
password, so the address was the only thing between the guest's console and the network - and it was
every interface. Both bind to loopback now; reaching further is an explicit act through `VNC_ADDR` or
`SPICE_ADDR`.

**The remaining seven items are the bulk of this milestone and are not started.** They are: the
BOOT-002 cold/persistent namespace collision (Critical), BOOT-003 (aarch64 and riscv64 direct boots
pass no init package), the four false-green oracles (BOOT-008, -009, -019, -028), artifact freshness
(BOOT-005, -006, -010, -030), cleanup and identity integrity (BOOT-004, -024, -027), unbounded
blocking operations (BOOT-007), and the fifteen medium findings. Each needs the harness exercised
rather than merely compiled, and several - the oracles especially - need a way to make the harness
fail on purpose to prove the fix, which is its own piece of work.

Measured: x86_64 `boot,smoke` 11/11, and `lab.py` parses.


### BOOT-002: the control namespace is separated; the disks are not (2026-08-18)

`scenario-cold` on x86 selected the persistent instance's UNSUFFIXED `dev-channel.sock`, unlinked it
without checking whether that instance was up or taking its lock, and bound it - and left the monitor
and QMP overrides unset, so it used the persistent monitor paths too. Every other target already had
its own suffix; x86 was the one that did not, which is exactly the one the persistent instance uses.

A cold run now sets `COLD=1`, and `dev_channel_socket` and the monitor/QMP paths answer with
`-cold-<arch>` names on every target. The lab computes the same names for its own end, for all
targets rather than only the emulated ones.

MARKED PARTIAL, because the audit names a second half this does not touch: both profiles still use
the same unsuffixed system, media and USB images, and the one persistent-instance disk conflict check
deliberately excludes `DEV_PROFILE=1` - which is the mode `scenario-cold` runs in. Separating the
writable images means deciding whether a cold run gets copies or overlays and what it costs to make
them, which is a design choice rather than a rename.

Measured (x86_64): `boot,smoke` 11/11, host suites green, and both scripts parse. The cold scenario
itself was NOT executed - it needs a persistent instance up to be worth running against, which is the
state this fix exists to protect.


### The oracles, and the entry points that had rotted out from under them (2026-08-18)

**BOOT-003, partial.** The runner's comment said the boot modules arrived as an initrd whose range
the device tree carried. No invocation had ever passed `-initrd`, and no kernel read
`fdt::BootInfo::modules_start` - the field is parsed, tested, and was read by nothing. So every
direct aarch64 and riscv64 boot reached `run_system_manager` with an empty archive and printed that
it was starting no userspace, under a comment describing the mechanism that would have prevented it.

The two machines cannot use the same mechanism, and finding out why is most of the work here:

- **riscv64 can.** OpenSBI hands the kernel the tree QEMU generated for that same invocation, so
  `-initrd` annotates the tree the kernel reads. Measured on qemu-system-riscv64 10.0.11: the dumped
  tree gains `linux,initrd-start` and `-end`, eight bytes each, whose difference is the package size
  to the byte.
- **aarch64 cannot.** QEMU enters an ELF kernel with x0 = 0 and places no tree for it - measured,
  the kernel prints `DTB 0x0` - which is why the runner dumps a tree from a SEPARATE invocation and
  loads it at `DTB_ADDR`. That dump cannot be taken with the real arguments: `dumpdtb` together with
  `-kernel` SEGFAULTS qemu-system-aarch64 10.0.11, with and without `-initrd`. No tree that kernel
  can read will ever carry an initrd range.

So aarch64 gets the archive at a fixed address through `-device loader`, the same mechanism the DTB
on that line already uses, and only the START is agreed on: a PKGARCH1 archive states its own
extent, so `bootmem::archive_len` reads the length out of the entry table rather than out of a
second constant two components would have to keep equal. `boot_archive_range` prefers a device-tree
range when there is one and falls back to the probe address, so riscv64 exercises the firmware
mechanism and aarch64 exercises the runner's. Both carve the archive out of the frame pool - nothing
else does: `loader_reservations` reads a hand-off a direct boot does not have, and `/chosen` is not
`/reserved-memory`.

ONE BLOB IS ALL EITHER MACHINE TAKES, so this is the init package without the system volume package
beside it - SystemManager starts, the shell and the development agent do not. A driven guest needs
both, so `DEV_PROFILE=1` without `UEFI=1` is now REFUSED on these targets instead of hanging on a
handshake that cannot arrive, and `scenario-cold` asks for UEFI on them. `run.sh` already took that
position for the same reason.

Marked partial: the two kernel halves are written and have NOT been compiled. That needs the
aarch64 and riscv64 builds, which are the slow ones and are deliberately last.

**The lab's entry points had been dead for some time, and no finding covers it.** `lab.py` started
guests with `just run` and built with `just user kernel-build` / `just user-aarch64`. None of those
three recipes exists: building moved to `./build.sh` and booting to `./run.sh`, and the recipes went
with the move. Every caller reported the failure as something else - `dev-up` waited for a QEMU that
was never started and blamed its build timeout, `scenario-cold` said "the userspace did not build"
whatever had happened - and all three were in fact `error: justfile does not contain recipe`. They
are paths now, checked for existence, so a missing entry point is a missing file. `run.sh` also says
of itself that it builds nothing, so `dev-up` and `lab boot` build as a step of their own; the
build and boot deadlines stay separate, which was the reason the old split existed. Thirty-odd
operator-facing messages naming `just dev-up` and friends were rewritten to `just lab dev-up`: the
recipes they named are reached through `just lab` now, so every one of them was advice that errors
out.

**BOOT-014, which BOOT-008 sits on top of.** Cursors advanced to a SEPARATELY taken file size after
the read, and the broker appends the whole time - so bytes landing in between were stepped over
without any oracle seeing them. `serial_read` returns the bytes and the offset they end at from one
descriptor, and every cursor move goes through it. The test writes from a second thread while
reading and requires consecutive reads to reassemble the file exactly; against the old code it loses
roughly a third of the lines.

**BOOT-008.** `absent` slept `min(limit, 2)` and looked once. Its only caller declares ten seconds,
so eight of them were unobserved - and the cursor was then advanced past whatever had appeared, so
the next step could not see it either. It watches continuously now, for the whole declared interval,
and takes a boundary: `until = "prompt"` holds until the shell prompt returns, which is the honest
bound for "this command printed no such thing" and is what `registry-provider` uses. A negative
assertion consumes nothing.

**BOOT-009.** The broker sent the collected bytes and nothing else on both the prompt path and the
timeout path, so a hung command that had printed something was WIRE IDENTICAL to a successful one
and `lab sh` exited 0 on it. Replies are framed - `LIBERLAB1 <outcome> <length>` - with named
outcomes, `lab sh` exits non-zero on anything but `prompt`, and an unframed answer is refused rather
than read as bytes. The prompt-spoofing half cannot be closed from the host: `has_prompt` is a regex
over terminal bytes and `program output\nvol://attacker> ` matches. What the host can do is refuse a
prompt that is still being written past, so a match must survive `PROMPT_SETTLE` with no further
bytes. A program that prints a prompt shape and keeps running no longer ends the request; one that
prints it and then blocks in silence still does, and closing that needs an unforgeable per-request
sentinel from the guest shell.

**BOOT-028.** Every producer ran inside a command substitution used as a `printf` ARGUMENT or behind
`< <(...)`, and bash propagates neither status - `set -euo pipefail` does not reach into either. A
failed `git ls-files` became the SHA-256 of an empty stream, and because the check side computed its
record the same way under the same breakage, the two matched and the gate reported the inputs
current. Producers are captured to files with checked status, every command substitution carries its
own `|| fail`, required inputs are required rather than omitted, counts are recorded beside digests,
and an inventory below fifty files is refused as not being this tree. `exit` inside a `$(...)` ends
the subshell only, which is the same trap one level down and is why the substitutions are checked
individually.

**BOOT-019.** The tracer set `booted` and never read it, so a guest still booting produced a trace
made of boot markers; one captured marker of any label was the whole acceptance condition; a missing
phase endpoint printed `n/a` and the tool exited 0; and a failed self-calibration became a scale of
zero, printing every duration as 0.000 ms. Each is now a named error, and the trace must contain the
command's own start/end markers.

**BOOT-017 and BOOT-026, taken while passing through.** The watchdog's victim selection ended a
`pipefail` pipeline in `head -n 1`: with more than one candidate the upstream loop died of SIGPIPE
and `set -e` ended the WATCHER - after it had written its `.hit` file and before it killed anything,
so the per-test stall bound collapsed back to the suite timeout and the run was classified by a mark
left by a watchdog that never acted. Candidates are collected whole; exactly one is killed and any
other count is stated rather than guessed at. Progress was counted as any `[ok]` anywhere, which
ordinary display text satisfies; it is the runner's own completion lines now. And `perf-trace.py`,
documented as `boot/perf-trace.py`, was mode 0644 - `check-source-hygiene.sh` now requires a file
that declares an interpreter to be executable, `scenario.py` lost the shebang it never needed, and
the tree's own outstanding violation of the `head`-in-a-pipeline rule was the watchdog above.

**The harness had no tests, which is why a reading was all any of this ever got.** `boot/harness-test.py`
runs 25 host tests against fakes - a real serial log on disk, a socket pair playing the guest, a
`PATH` of deliberately broken producers - with no QEMU and no privileged operation, behind
`./check.sh --gate boot-harness`. Every test was written against the broken version and watched to
fail on it: the `absent` sample (3 failures), the cursor race (the partition test loses a third of
its lines), the settled prompt, and the preflight producers.

Measured: `boot-harness` 25/25; x86_64 `boot,smoke` 11/11 and `memory` 74/74 (the new
`bootmem::archive_len` tests among them, watched to fail under a mutation returning the table end
instead of the archive end); `source-hygiene --current` clean; `test-preflight write`/`check` on the
real tree; and both runner scripts parse. NOT measured: the cold scenario, the aarch64 and riscv64
kernels, and `dev-up` - the last needs an x86 persistent instance, which this machine's other work
is using.


### Identity, cleanup, deadlines and the caches that never checked their inputs (2026-08-18)

**BOOT-024.** The boot generation is the only thing that distinguishes one boot of a guest from the
next, and it was written by REOPENING THE LIVE LOCK FILE and truncating it - so a crash or a
concurrent read during the rewrite left an empty JSON document, which `dev_identity_read` returns as
`{}`: status then misread a live locked instance as merely starting, and the generation was simply
gone. `dev-up` also computed `dev_record_boot()`'s result and threw it away, and that function
returns False when the agent does not answer within thirty seconds - which is exactly what happens,
because the shell is ready before the agent is. So `dev-up` could print "ready" having recorded
nothing, and every later session skipped the restart comparison, because the comparison was
conditional on there being a value: `if recorded and recorded != ...`.

The record is a sidecar published by rename and KEYED TO THE LOCK'S INODE, so a record left by an
instance that is gone cannot bind a session to that guest's boot. Recording it is part of readiness -
failing to means `dev-up` fails and cleans up - and an absent record is now a refusal rather than a
comparison to skip.

**BOOT-004.** A process group id is reused, and `dev_group_alive` answers "some group with this
number exists". That was the whole basis on which `dev-down` escalated SIGKILL to it and on which
`dev_state` called an instance `detached`. The recorded identity carries the leader's `/proc` start
time now - fixed at creation, not reusable with the number - and a group that cannot be verified is
reported rather than signalled.

The other half is worse and is about what cleanup DESTROYS. `dev-down` computed `stopped` and then
unlinked the lock and every socket regardless. If the broker survived, unlinking `DEV_LOCK` removed
the pathname while the broker still held its flock on the old inode: the next `dev-up` created a new
file at the same path, locked it successfully, and two instances both believed they owned the
singleton profile - the exclusivity that protects one system volume and one set of ports, destroyed
by the command whose job is to release it. Nothing is unlinked unless the guest actually stopped.

**BOOT-027 and BOOT-015.** `scenario.run` caught `ScenarioError` and nothing else, so teardown ran on
exactly two paths out of the loop. The step adapters call the protocol helpers directly and those
report connection, handshake, timeout and refusal failures with `die`, which raises `SystemExit` -
the protocol layer's NORMAL error path. A control socket that disappeared, a request that timed out,
a malformed reply reaching an unpack, or a Ctrl-C during a step all left through neither handler:
teardown never ran, and the next scenario inherited a launched program, a raw terminal, a registry
still shadowing installed files, and the fixtures. Execution is primary-result-then-unconditional-
teardown now, transport exceptions become step-scoped failures naming the step, and an interruption
is re-raised after the guest has been given back. `teardown`'s own `free` is initialised before the
`try` it is read after - it was not, so any failure in an earlier stage was caught as intended and
then replaced by `UnboundLocalError`, which took the remaining scenarios with it.

**BOOT-007.** The deadline was a value passed to some GUEST requests, not a boundary on the host
processes those requests were made from. `dev-publish` applied `--timeout` independently to the
handshake, the begin, EVERY CHUNK and the commit, so a maximum-size artifact multiplied the
advertised bound by the number of frames it happened to need; `dev-launch` and the scenario `output`
and `finished` steps handed every poll the original full limit, so one late call could overrun the
deadline the loop had just computed by another whole interval; a key batch was up to 64 separate
five-second monitor operations that had never been told about the step's budget; and `dev-loop`, the
scenario publish/reset/restart wrappers, the cold build, the performance gate and the self-test ran
children with no host timeout at all. Every one of those now spends one absolute deadline, and
`run_child` gives each child a session of its own and stops the whole GROUP with TERM then KILL - a
cold QEMU that ignores TERM used to outlive the command that started it, holding the sockets and
disks the next run needs.

**BOOT-012.** QMP is asynchronous, and the helper read exactly the next line as the answer. A device,
reset or stop event arriving between request and response became the reply - and an event carries no
`error` key, so a command QEMU never executed was reported as a success returning `None`, with every
later read one object out of step. Requests carry an `id`, events and foreign replies are skipped,
the greeting is checked, and the receive buffer is bounded.

**BOOT-013.** A nonblocking `send` may accept only a PREFIX without raising, and the return value was
discarded - so the tail vanished on a console connection that stayed attached and therefore never
requested the replay that would have covered the gap. Backpressure disconnects now; a bounded replay
from a known point is something a reader can reason about, and silent truncation is not.

**BOOT-023.** The registry decoder indexed and sliced its way through names, generation records and
detail strings with no bounds check, and Python hides that: a slice past the end is silently SHORT,
so a truncated reply decoded into a plausible registry with bytes quietly missing. It goes through a
cursor that checks every read and requires exact exhaustion, and every prefix of a valid reply is
now a named malformed-input failure. The PCAP dumper trusted record lengths and used the IPv4 header
length as an offset without checking it landed inside the frame.

**BOOT-010.** Freshness hashed four suffixes - `.rs`, `.toml`, `.lock`, `.ld` - under three roots, so
an assembly file, a linker script with another extension, a JSON target specification, a build script
or a factory payload was invisible. It hashes every file under the roots now (excluding build output
directories, which is a set that can be named; a set of source KINDS cannot), and three classes were
added: `payload` (the factory volume and the product configuration), `build` (the root build scripts
and `src/tools`) and `manifest`. Measured at 174 ms for the whole walk, against a quarter of a
second before it covered less.

**BOOT-005.** The four fixture media were generated only when the output path did not exist. Nothing
else was consulted - not the files copied into them, not the recipe, not the tool - so the images in
this tree were dated three weeks before the script that claims to produce them, and every run reused
them because they were there. `xorriso`, mount, copy and unmount failures were suppressed with
`|| true` AFTER the output had been created, so a formatted-but-empty or half-written image was left
at the canonical path where the existence check protected it forever. They are keyed on source
content, recipe and tool identity, built into a candidate, VERIFIED, and renamed into place; the
unmount is checked, because a live host loop mount on an image QEMU is about to attach writable is
the corruption this file is otherwise careful to avoid.

That verification immediately found something: **the UDF fixture has never contained the volume
files.** Measured on this host, the kernel mounts a `mkfs.udf --media-type=hd` image READ-ONLY, so
the copy has always failed with `cp: Read-only file system` and the old code kept the empty
filesystem it had just created. Every UDF fixture in this tree is an empty UDF volume. Nothing is
published now and the runner says so. The FAT, ISO and USB fixtures rebuilt from current sources for
the first time since July, and the storage suite passes 42/42 against them - which is the first time
that result has been about the current tree.

**BOOT-006.** `verify_boot_artifacts` read the authoritative artifact list through `< <(...)`, and
bash does not propagate a process substitution's status: a failed `cargo run -- boot-artifacts`
left the loop with no iterations and `missing=0`, so the function declared every required artifact
present by not reading the list. The cache key hashed a subset that omitted the manifest, the
fallback bootstrap set copied onto the ESP and the volume pairing sidecar, so a destination could
move or the fallback set change with the key unmoved - a HIT returning an image that does not
implement the current manifest. And a matching key returned the file without looking at it. All
three are closed: checked export, complete key, recorded output digest verified on every hit, and
the key recomputed after assembly so an input replaced mid-build is refused rather than recorded.
Measured: a corrupted cached ISO is detected and rebuilt; changing only the pairing sidecar
invalidates.

**BOOT-016.** Scenarios share the terminal, the control channel, the registry, the single launch
slot, the fixtures and the teardown, and two host processes could both see `ready` and begin. An
flock held across the whole validate/run/teardown sequence serializes them, and being an flock it is
released by the kernel when the holder dies. Cold runs get a run-local first-touch record per
target; they all shared the persistent instance's one file, so a cold aarch64 run deleted the x86
instance's record.

**BOOT-025.** The ESP, the stripped kernel and the firmware variable store were fixed per-target
paths, and every run deleted ALL `ovmf-vars.*.fd` before creating its own - so a run that had just
made its copy and had not yet opened it found it gone. Each carries this shell's pid now, and this
shell is the process that becomes QEMU, so the pid is alive exactly as long as the file is in use
and the sweep can tell a leftover from a live run's file with certainty.

**BOOT-017, -018, -019, -022, -026, -029.** The watchdog's `head -n 1` inside a `pipefail` pipeline
killed the WATCHER instead of the guest whenever there was more than one candidate; progress was any
`[ok]` anywhere, which ordinary output satisfies. The performance gate trusted an unchecked `git
status`, restored the source only on the normal path, and ignored the restoration build's status -
so an interruption left its probe in the user's tracked source and a failed rebuild left the staged
executable derived from it. The tracer set `booted` and never read it. The screenshot tool shared
three singleton paths and killed log followers by PATTERN. `perf-trace.py` was mode 0644 under a
shebang. `mkimage.sh`'s cleanup named two candidates and the test-ISO builder chose a third. And the
self-test and the performance gate both proved "one boot throughout" by comparing QEMU's process
group - which `system_reset` leaves alone while creating a new boot; both compare the boot
generation now.

Measured: `boot-harness` 52/52 (every test written against the broken version and watched to fail on
it); x86_64 `boot,smoke` 11/11 and `storage` 42/42 against regenerated fixtures; `host-tests`,
`milestone-index`, `test-tags` and `source-hygiene --current` clean; `mkimage` cache hit, corrupted-
output rebuild and pairing invalidation exercised directly. NOT measured: `dev-up`, `dev-down`,
`dev-loop`, the performance gate and the self-test all need a live persistent instance, which this
machine's other work is using.
