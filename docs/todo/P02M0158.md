# P02M0158 - The boot report names the same device twice and the same component two ways

Status: COMPLETE (2026-08-28). Reading the report again found SEVEN lines that break this milestone's own rules, five of them written after it closed; they are the last section of this file, with the boot they were fixed on. The 2026-08-26 audit's 2 defects are the section before it. Was COMPLETE (2026-08-26), REOPENED (2026-08-28). BOOT REPORT QUALITY. NOT A PHASE-2 COMPLETION GATE.

## Goal

Finish what P02M0155 started on the console. That milestone took the boot report from lines that were
false or duplicated to lines that carry their own fact - the DMA summary that used to print before
any device had bound, the topology fact printed twice, and seven services announcing themselves with
one indistinguishable line.

The same reading, done again on 2026-08-26 against a full interactive boot, finds six places where
the report still costs the reader more than it gives: two names for one device, two prefixes for one
component, four identical driver lines, a harness marker rendered to a person, a subsystem that
reports success without its result, and two memory lines that read as one fact stated twice.

None of this changes behaviour. What it changes is whether somebody reading a console can tell what
happened, which is the only thing a boot report is for.

## What is there now

The boot this is measured from, x86_64 under OVMF from `.build/boot/libersystem.iso`, 2026-08-26.

- **ONE DEVICE, TWO NAMES, BOTH ON SCREEN.** The driver announces itself as
  `driver.virtio-pointer: online` ([virtio_input.rs:132](../../src/user/drivers/core/src/virtio_input.rs)),
  and the kernel's DMA audit calls the same PCI function `virtio-input at 00:09.0`. Nothing in the
  output connects them, and the machine has two `virtio-input` functions - 00:08.0 and 00:09.0 - so a
  reader cannot even work it out by elimination.

- **ONE COMPONENT, TWO PREFIXES, TWO LINES APART.**
  [device_manager.rs](../../src/user/services/core/src/device_manager.rs) prints `devmgr:` at lines
  442 and 519 and `DeviceManager:` at eight other sites, which lands as:

  ```
  devmgr: xhci did not bind; its resources are released and the next candidate follows
  DeviceManager: 10 of 11 device(s) online
  ```

- **FOUR IDENTICAL DRIVER LINES.**

  ```
  driver.virtio-blk: online
  driver.virtio-blk: online
  driver.virtio-blk: online
  driver.virtio-blk: online
  ```

  This is the defect P02M0155 fixed for `StorageService`, which now correctly says `(vol://ram)`,
  `(vol://tmp)` and so on. The drivers did not get the same treatment, and the information exists -
  the DMA audit six lines further down distinguishes the same four devices as 00:01.0, 00:05.0,
  00:06.0 and 00:07.0.

- **A HARNESS MARKER RENDERED TO A PERSON.** `PERF tsc_hz 2595394200` is
  [main.rs:305](../../src/kernel/main.rs), written with a leading `\x1e` so the harness can find it
  in a log. Nothing strips the record separator on an interactive console, so it renders as the one
  unformatted capitalised line in the whole boot - a line addressed to a program, shown to a reader
  who has no use for it.

- **A SUBSYSTEM THAT REPORTS SUCCESS WITHOUT ITS RESULT.** `network: configured via DHCP` says the
  transaction completed and not what it produced. Every other line in the report carries its own
  fact: the frame count, the core count, the volume name, the release. This one asks the reader to
  go and look.

- **TWO MEMORY LINES THAT READ AS ONE FACT STATED TWICE.**

  ```
  memory: buddy allocator up - 1036141 free frames, 383 KiB of metadata
  ...
  memory: 1035077 physical frames free
  ```

  They are two different moments, 1064 frames apart, and the second one does not say that it is a
  later moment or what happened in between. Two numbers that nearly agree, with nothing saying why
  they differ, read as a rounding error rather than as a measurement.

## Work

- [x] **M1 - one name per device, chosen once.** The driver and the kernel's device table must use
  the same string for the same PCI function. Whichever name wins, it is the same one in
  `driver.<name>: online`, in the DMA audit and in the device summary - and a second function of the
  same type is distinguished by its address rather than by a second name for its type.

- [x] **M2 - one prefix per component.** `devmgr:` becomes `DeviceManager:`. While there, check the
  rest of the report for the same shape: a component that prints under two prefixes is a component a
  reader cannot grep for.

- [x] **M3 - a driver line carries which device it is about.** `driver.virtio-blk: online` becomes
  distinguishable the way the storage service's line already is, using the address the DMA audit
  already prints. Four block devices produce four lines that differ.

- [x] **M4 - the harness markers do not reach an interactive console.** Either the console strips the
  record separator and what follows it, or the measurement is printed in the report's own format and
  the marker is emitted only where the harness reads. The harness must keep finding it - the perf
  gates parse that line - so this is a presentation change with a test that the marker is still
  there on the path the harness uses.

- [x] **M5 - `network:` says what it got.** The address, the prefix length and the gateway, on the
  line that says the configuration succeeded. A DHCP failure already has its own line and keeps it.

- [x] **M6 - the two memory lines say which moment each is.** One line reports the allocator coming
  up; the later one says what is free after early boot AND what was consumed since, so the difference
  between the two numbers is stated rather than left for the reader to subtract.

- [x] **M7 - the boot report is read end to end once more, from a full interactive boot, and what
  this milestone did not find is recorded.** The first pass found the DMA summary printed before any
  device had bound; the second found these six. A report is judged by reading it, and the reading is
  the deliverable rather than a step towards it.

## Dependency order

All six are independent. M1 touches two crates and should go first because M3 uses the name it
settles. M7 comes last, by definition.

## Definition of done

- No two lines in a boot name the same device differently, and no component prints under two
  prefixes.
- No two lines in a boot are identical; where several instances of one thing come up, each line says
  which instance it is.
- Nothing addressed to the harness is rendered on an interactive console, and the harness still finds
  every marker it parses.
- Every line that reports a subsystem succeeding carries the result of that success.
- The boot report has been read end to end from a full interactive boot after the changes, and what
  that reading found is written down here.

## What this milestone refuses, and why

- **Moving the DMA/IOMMU summary earlier.** It looks late - it prints after every userspace service -
  and it is deliberate: drivers bind while the service set comes up, so that is the first point at
  which the answer exists at all. The reasoning is at
  [main.rs:806-809](../../src/kernel/main.rs) and it stands.
- **A log level, a filter or a quiet mode.** The report is short enough to read, and a boot that
  hides lines by default is a boot whose report nobody trusts. The fix for a noisy line is the line.
- **A structured log format.** Machine-readable output has its own marker convention already, and
  replacing the human-readable report with records that need a tool to read would trade the problem
  this milestone is about for a worse one.
- **Renaming services or drivers for tidiness.** M1 and M2 settle a name only where the SAME thing is
  currently called two things. A name that is merely inelegant stays.

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED for one line and one test.

- [x] **One virtio-blk branch still prints the unaddressed line this milestone removed.** When
  `channel()` fails the driver reports a bare `driver.virtio-blk: online`
  ([virtio_blk.rs](../../src/user/drivers/core/src/virtio_blk.rs)) while every other exit from the
  same function goes through `common::describe`, which puts the device's address into the line -
  including the no-request-queue branch eight lines above it. Two instances failing the same way
  print the same string, and it says "online" for a driver that has no service channel. Use
  `describe` with the reason, as its neighbour does.

- [x] **The PERF marker's condition has no test that boots it.** Publishing the TSC anchor only under
  the development profile ([main.rs](../../src/kernel/main.rs)) is the right rule and nothing asserts
  it: no run boots that profile and requires the line, so the day the condition stops matching, the
  trace tool loses its anchor silently and the traces it produces are wrong rather than absent. The
  trace tool already boots the guest with exactly that profile - assert it there.

## Results (2026-08-26)

The virtio-blk channel-failure branch goes through `describe` like every other exit from that
function, so it carries the device's address and says why. It reported a bare
`driver.virtio-blk: online` - the same string for every instance failing the same way, and the word
"online" for a driver with no service channel.

The PERF anchor's condition has a witness. `perf-trace.py` is the thing that boots the development
profile, and it warned and self-calibrated when the anchor was absent - so the day the condition
stopped matching, every trace would quietly have become a few-percent estimate from host wall-clock
and the report would have looked identical. A missing anchor is now an error naming the condition,
with `--self-calibrate` for someone who wants to measure anyway.

## The report read again (2026-08-28)

Status: REOPENED again, and closed again below. The definition of done says no component prints
under two prefixes and no two lines in a boot are identical. Both were false, and five of the seven
findings below were written after this milestone closed - which is the argument for reading the
report rather than trusting that a rule stays kept once it is written down.

Read from a full boot of `.build/boot/libersystem.iso` under OVMF, x86_64, and read a second time on
a 100-core guest because the first reading was done at 8 cores and one of the worst lines in the
report is invisible below 64.

- [x] **The kernel printed under the loader's prefix.** Eighteen lines into the boot, after seventeen
  lines the UEFI loader wrote, came `loader: this boot's system volume is a paired block volume` -
  and the kernel wrote it ([main.rs](../../src/kernel/main.rs)). It is M2's defect from the other
  side: `devmgr:`/`DeviceManager:` was one component under two prefixes, this was two components
  under one. A reader who greps `loader:` got two programs' accounts interleaved, and the line
  reporting what arrived over the boot protocol was indistinguishable from the loader's own account
  of choosing it.

- [x] **`loader: signed manifest verified` was printed twice with the same digest.** The medium's
  manifest is verified once to learn which volume it is paired with and again as cover for the
  kernel read off it - two questions, one string, matching digests because it is the same record.
  `announce_release` ([main.rs](../../src/boot/loader/src/main.rs)) has three callers and none said
  what it had verified.

- [x] **`loader: bootstrap set verified against a SIGNED etc/boot.manifest2` was printed twice.** The
  system volume answers first and the boot medium answers after it declines, and the receipt was the
  same string for both ([blockio.rs](../../src/boot/loader/src/blockio.rs)). A comment in
  [main.rs](../../src/boot/loader/src/main.rs) records an earlier fix for this same line printing
  twice - that one stopped the SAME source being asked twice and left two sources sharing one
  receipt. The distinguisher was already in hand: `assemble_bootstrap` takes the `Expected` that
  says which source it is reading.

- [x] **`DeviceManager: providers published` was printed twice.** `report_catalogue`
  ([device_manager.rs](../../src/user/services/core/src/device_manager.rs)) runs once after the boot
  drivers and once after the rest, and neither line said which - so on a machine whose second phase
  publishes nothing new the two lines are byte-identical.

- [x] **One line was printed 3236 times, and it is half of every line the console wrote.** On a
  100-core host `tlb: 100 cores are online and this tracks 64 - a shootdown cannot reach them all`
  ([tlb.rs](../../src/kernel/mem/tlb.rs)) was printed on every shootdown: 3236 copies in one boot,
  3236 of 6509 lines. The comment above it already argued the fix - "a machine does not grow cores
  while it runs, the first line is the whole story" - and the code said it per shootdown anyway. Said
  once per boot. The count is not lost: `memory: N page(s) retired for good` totals the consequence.

- [x] **`DeviceManager: boot window and this boot's deadline` named two numbers and printed
  neither.** The function's own comment says "say which budget this launch is working to", and the
  branch where both values exist stated that they exist. It is M5's defect exactly - a subsystem
  reporting success without its result - reintroduced by later work.

- [x] **A driver's line was cut in half by the kernel's.** The report carried
  `driver.virtio-blk: online (00:02.0)iommu: 00:08.0 attached to domain 4` followed by a bare
  newline: two lines a reader cannot read, and neither of them the line either component wrote.
  `online` ([common.rs](../../src/user/drivers/core/src/common.rs)) wrote the report and its
  terminator as two separate calls, and the kernel writes to the same port from its own cores. The
  terminator belongs to the line, so it is one write. The evidence is the mechanism rather than the
  absence of a race in one run - a boot after the change shows no split line, which is what a fixed
  race and a lucky one both look like.

## What this reading refuses, and why

**A machine with more cores than `mem::tlb::MAX_CPUS` does not finish booting, and that is not this
milestone's to fix.** At 100 cores the boot reaches `providers published after the boot devices` and
then does nothing but retire pages - 3058 of them in 100 seconds, userspace never started. The
kernel is behaving as `KERN-ARCH-012` says it should at the point of the shootdown: it refuses
rather than truncating, because answering "flushed" for cores it cannot reach would be a physical
use-after-free. What is missing is upstream of that - the machine was brought up with 100 cores the
TLB layer cannot track, and the refusal is discovered one page at a time instead of once at
bring-up. That is an SMP defect with a real fix (bound what comes online, or track what comes
online) and it is [P02M0168](P02M0168.md); changing `MAX_CPUS` or the online cap under a boot-report
milestone would be deciding a kernel limit as a side effect of tidying a log. Writing that milestone
found more than the reading did: five constants named `MAX_CPUS` holding four different values, a
`u64` online mask that is a sixth bound and not a constant at all, and two comments asserting a
bound that does not exist.

**The per-page `frame: WARNING ... the page is RETIRED` lines stay.** They are 3058 of the 3096 lines
left in that boot and the temptation to cap them is obvious. Each one names a distinct page that has
left circulation for good, which on a supported machine is rare and is the whole record of memory
permanently lost. A cap would hide a leak to make a log shorter, and the log is long here because
the machine is unsupported, not because the line is wrong.
