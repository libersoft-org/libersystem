## The two that can free memory somebody is still using

- [x] **The TLB shootdown has no request identity, so a late acknowledgement counts for the wrong
  request.** `mem/tlb.rs` has `PENDING: [AtomicBool; MAX_CPUS]`, a bare `ACKED: AtomicUsize` and
  `IN_FLIGHT` to serialise. A core services a request with
  `if PENDING[me].swap(false) { flush_local_tlb(); ACKED.fetch_add(1); }` - and nothing in that
  acknowledgement says WHICH request it belongs to.

  The window opens on timeout. The requester spins to 200,000,000, prints
  `tlb: shootdown timed out with n/targets`, sets `complete = false` and releases `IN_FLIGHT` - while
  a slow core may be between its flush and its `fetch_add`. The next requester zeroes `ACKED` and
  starts counting, and the stale increment lands in the new count. With three or more cores the
  remaining acknowledgements can reach `targets` while one core never flushed the mapping this
  request is about.

  **The window is not hypothetical in this tree.** `.build/logs/test` holds **487** occurrences of
  `tlb: shootdown timed out`, across **x86_64 (51 logs), riscv64 (24) and aarch64 (22)**. The
  timeout path is ordinary here, not exotic.

  And the result gates physical reuse: `frame::retire` releases the quarantine only
  `if crate::mem::tlb::shootdown()`, so a false success is a frame handed back to the allocator
  while a core can still reach it through a stale TLB entry - a physical use-after-free.

  Give the protocol generations: a global request counter, `pending_generation[cpu]` written by the
  requester, `ack_generation[cpu]` written by the core after its flush, and a wait for
  `ack_generation[cpu] >= generation`. An acknowledgement then cannot be mistaken for a newer one.


  DONE 2026-08-10. Requests carry a generation now: `REQUEST` hands out numbers, the requester
  writes `PENDING_GENERATION[cpu]` and waits for `ACK_GENERATION[cpu] >= generation`, and a core
  flushes and then `fetch_max`es its own generation. A late acknowledgement carries an older number
  and cannot satisfy a newer wait, so nothing needs resetting between requests - which was the other
  half of the defect. `fetch_max` rather than a store because `service_pending` is re-entered from
  both the idle loop and the wake-IPI handler.

  The timeout now names the cores that did not answer and the generation they are behind on, rather
  than printing `2/7`. Confirmed in the wild while this was being written: the riscv64 sweep of
  `5b427f4` ended with `a_fat_volume_accepts_a_write_as_its_first_operation... tlb: shootdown timed
  out with 2/7 acknowledgements`, which is this window being entered on an ordinary run.

- [x] **`SharedPage::drop` returns a frame straight to the allocator, bypassing the retirement the
  private frames use.** It is `unsafe { frame::deallocate(self.frame) }`, and its SAFETY comment
  argues ownership - which is true and is not the question. Every frame that was ever in a page
  table goes back through `frame::retire` precisely because another core may still have it cached.

  DONE 2026-08-11, on the fourth attempt, once the thing that was actually in the way was fixed.
  `Drop` calls `frame::retire`, so the one path that handed a frame straight back to the allocator
  while another core could still hold a translation for it is gone.

  The three failed attempts were all blocked by the same thing and none of them named it. The first
  blamed the heap-allocated quarantine - correctly, and fixing it did not help. The second blamed the
  quarantine again. The third produced a measurement - 14 passes against 82 - that did not survive a
  control run. What was in the way was `shootdown` itself: neither of its spin loops serviced this
  core's own pending request, so two cores shooting down at once each kept the other waiting out a
  two-hundred-million-spin timeout, and the retirement multiplies shootdowns. That is fixed
  (see the finding below), and with it in:

  - x86_64: 227 of 227, and the suite is FASTER than with `deallocate` - 123 s against 159 s.
  - aarch64: 219 of 219 in 2138 s, on the target that stopped at 14 twice.

  So the milestone had the order backwards: it said the allocation-free quarantine had to land
  first, and it did have to, but it was not sufficient. The shootdown had to land first.

  ATTEMPTED AND REVERTED AGAIN 2026-08-11 - the third attempt, and the first one to produce a
  measurement instead of a suspicion. It is still the right change and it still cannot land alone.

  With the allocation-free quarantine in (which is what the second attempt said was missing), the
  aarch64 and riscv64 suites stopped finishing: both wedged inside
  `kernel.extable.a_process_load_whose_image_goes_away_is_an_error_rather_than_a_dead_kernel`, which
  is a `SYS_PROCESS_LOAD` whose image goes away halfway - exactly the loader-rollback path this
  finding is about. x86_64 finished all 227.

  THE ISOLATION FAILED, and saying so is the point of this paragraph. The first comparison looked
  decisive - 14 passes with the retire against 82 without it, same machine, one line apart - and a
  third run with the retire REVERTED wedged at 14 in the same test again. So the retire is not
  proven to cause it; what the three runs actually show is a non-deterministic wedge that the change
  may make more likely and may have nothing to do with. That wedge is now its own finding below.

  The revert stands anyway, for a reason that does not depend on the isolation: this landed twice
  before and was pulled back twice, the frame-lifetime race it fixes has never been observed, and
  the reclaim path it uses stops every core to do its work. Landing it while the suite it has to
  pass cannot be run is not landing it.

  Run ALONE the same test passes in 11 seconds, so this needs several cores doing other work: the
  drop retires, the quarantine reaches its drain threshold, and the drain shoots down - an IPI to
  every core and a spin until they all answer. x86_64 gets an answer (and even there a related test
  reported `shootdown 62 timed out with 2/3 acknowledgements` and cost 77 seconds). The two
  emulated targets do not.

  So the blocker is not the quarantine any more, it is the SHOOTDOWN: a reclaim path that has to
  stop every core cannot run inside a rollback that itself runs on a busy machine. The next attempt
  needs one of - a shootdown that cannot stall (a per-core acknowledgement the idle path completes
  rather than a spin), or a per-core deferred free that needs no IPI at all, or a retirement that
  defers to a point where the machine is known to be quiet. Until then the frame goes back
  immediately, and the race stays open and named.

  Two tests keep the changes made with it, because they are right either way:
  `a_fuzzed_elf_header_is_refused_without_leaking` and its relocation twin drain the quarantine
  before counting (other code fills it) and compare with `>=` rather than `==` - the drain releases
  whatever else was queued, so the count can legitimately come back HIGHER than the loop started.
  That is the same rule `a_load_that_runs_out_of_frames_anywhere_gives_back_everything` had already
  settled on: what a load owes is that it kept nothing.

  The rollback path is where it bites. `load_parsed` on a late failure does `unmap_segments` and
  `shared.truncate(shared_start)`, dropping the `Arc`s; `load_module_into` maps into an address
  space that belongs to an already-running process, whose other threads are on other cores; and
  x86's `unmap_page_in` does a local `invlpg` only. So a relocation failure in a module loaded into
  a live process can free a frame that a running thread still reaches, with no shootdown between.

  `SharedPage` must retire rather than deallocate, or the loader must own the last unmap and retire
  explicitly. The private path already does this - `frame::retire` followed by
  `frame::drain_quarantine` - so the fix is to stop the shared path being the exception.


  ATTEMPTED AND REVERTED 2026-08-10, and the attempt found the reason this cannot land alone.

  `Drop` calling `frame::retire` is correct for the race and leaks a frame on the one path that
  matters: `retire` queues into a HEAP-allocated quarantine, the heap grows by taking frames, and
  the failure this drop runs on is precisely "there are no frames". The queue cannot take it, the
  fallback needs a shootdown, and when that does not complete the page is counted lost. The
  out-of-frames rollback test said so exactly - `a load refused at allocation 85 kept 1 frame(s) it
  took (0 still quarantined)` - which is the quarantine finding below, made reachable by this one.

  So the two land TOGETHER: the allocation-free quarantine first, then this. Retiring into a queue
  that cannot allocate is not safer than freeing; it is the same defect with an extra step. The
  reasoning is in the code at the `Drop`, so the next person to notice `deallocate` there finds out
  why before changing it.

## Capability transfer is not a transaction

- [x] **`sys_thread_create` never commits the bootstrap capability it took.** It calls
  `take_for_transfer`, whose doc states the contract in as many words: "Exactly one of
  `commit_taken` or `restore_taken` must follow". Both failure paths call `restore_taken`. The
  success path ends at `install_object(&thread, new_thread, Rights::ALL, 0)` and there is no
  `commit_taken` anywhere in the function.

  The cost is exact, because `commit_taken` does two things: `retire_or_recycle(slot, &mut self.free,
  index)` - returning the slot to the free list under the generation rules - and
  `domain.uncharge_handles(1)`. Neither happens. So **every successful spawn that passes a bootstrap
  capability permanently leaks one handle slot and one unit of the parent's handle quota**, on the
  ordinary success path of the ordinary spawn syscall. A supervisor that spawns in a loop walks its
  own quota down until it cannot spawn.

  The second-order failure is worse and rarer: `install_object` is the last statement and has no
  rollback, so if the CALLER's handle table refuses the new thread handle, the bootstrap is already
  in the child and is not returned. Neither party can name it.

  Make the transfer a real transaction with unwinding, rather than three call sites each remembering
  the discipline.


  DONE 2026-08-10. `install_object` runs first and its result is held; a failure there takes the
  capability back out of the child and restores it to the handle it came from; only then does
  `commit_taken` run. So the contract `take_for_transfer` states - exactly one of commit or restore -
  now holds on every path through the function, and the slot and the quota unit stop leaking on the
  ordinary success path.

- [x] **`close_all` does not know the reserved-transfer state exists.** `take_for_transfer` leaves a
  slot deliberately in-between: `cap = None`, generation untouched, index NOT on the free list, so
  nothing can occupy it while the message is in flight. `close_all` does `self.free.clear()` and then
  pushes EVERY index, whatever its state.

  So a termination racing an in-flight transfer puts the reserved slot on the free list; the
  subsequent `restore_taken` writes the capability back into a slot that is simultaneously free, and
  the next insert can hand out the same index. On the other branch `commit_taken` pushes an index
  that is already free, and the free list holds it twice.

  `close_all` also writes `slot.generation.wrapping_add(1)` directly instead of going through
  `retire_or_recycle`, so it bypasses the generation-exhaustion protection that `close` has, and it
  frees slots that were retired for exactly that reason.

  The slot needs a state - Free, Live, TransferReserved, Retired - and `close_all` needs to respect
  it.


  DONE 2026-08-10. The slot carries an explicit `reserved` flag, set by `take_for_transfer` and
  cleared by both endings, and `close_all` leaves those slots entirely alone. It also stopped
  hand-rolling `wrapping_add` on the generation: the rule that a slot whose generation cannot
  advance is retired rather than reused is now spelled the same way in both places, so a retired
  slot is no longer pushed back onto the free list either.

  Pinned by two tests, and the second was watched to fail: replacing the `reserved` guard with
  `false` produces `assertion left != right failed: close_all must not hand out a slot with a
  transfer in flight`. Both pass with the guard, along with the shootdown, frame-ownership,
  rollback and spawn tests - six selected, 11 s.

## Charges and states that rollback does not restore

- [x] **`return_to_head` puts a message back uncharged and over the limit, and its own comment says
  so.** `recv_identified` refunds the sender's queue charge on the way out; if the copy to userspace
  then fails, the syscall calls `return_to_head`, which is `inbox.lock().push_front(message)`. The
  comment defends both properties: the message "goes back UNCHARGED" because the paying domain is no
  longer reachable from there, and it goes back "even when the queue is at its limit" because "one
  over for that instant costs a bounded amount of memory".

  The bound is the part that does not hold. Nothing serialises these returns against each other, so
  N receivers failing their copies concurrently push N messages past the limit, none of them
  charged - which exceeds `CHANNEL_QUEUE_MAX` and understates the domain's `ipc_queue` usage by the
  same N. The refund is in the wrong place: the queue charge should be released when delivery
  COMMITS, with the message holding its reservation through the receive attempt, so a rollback
  restores the charge with the message.


  DONE 2026-08-10. The queued-bytes charge no longer leaves with the dequeue: both receive paths
  carry it on the message and release it at the point of no return - after the payload has reached
  the caller's buffer, where `return_to_head` is no longer reachable. A returned message is
  therefore a message that was never uncounted, and N concurrent failed copies put back N messages
  that all still count against the limit.

  Watched to fail: restoring the refund on dequeue gives `assertion left == right failed: taking a
  message off the queue does not refund it - delivery has not committed`.

- [x] **`terminating` is a flag where a barrier is needed.** `Process::terminate` sets it, then
  unmaps, then closes handles, and the syscalls check `is_terminating()` and proceed without holding
  anything. So a `sys_thread_create` that passes the check before the flag is set can call
  `register_thread` after `close_all` has run, and the process acquires a thread after its cleanup.
  `sys_thread_start` does not check the process at all - `sched::thread_start` consults only
  `thread.try_start()` - so a thread created through that race can be enqueued into a killed process.
  The same shape covers the mapping paths: check, then map, then record, with termination free to
  snapshot in the middle.

  A `Live -> Terminating -> Dead` state with guards, where termination takes the exclusive
  transition and waits for outstanding guards, is what the flag is standing in for.


  PARTLY DONE 2026-08-10 - the two paths the finding names are closed, the general barrier is not.

  `register_thread` is `#[must_use]` and decides under the `threads` lock; `begin_teardown`
  publishes the flag under that same lock, so a registration either sees it and refuses or
  completes before teardown returns. `Thread::build` returns `None` when the registration is
  refused, so a thread is not even constructed into a process that is going away. And
  `sys_thread_start` now tests the PROCESS, which it did not test at all - `try_start` only ever
  answered "was this thread started before".

  What remains is the general shape: a `Live | Terminating | Dead` state with a guard that every
  resource-extending syscall holds, which is what makes the mapping paths safe too. That is a
  design change rather than a patch and it is still worth having; this closes the one path that
  demonstrably ended with a live thread inside a cleaned-up process.

## Allocation that can panic where the ABI promises an error

- [x] **Userspace-reachable paths still allocate infallibly, the scheduler worst of all.**
  `src/kernel/sched/mod.rs` has eight `.push(` calls against one `try_reserve`. `block_on_flagged`
  and `block_on_any` push into the wait buckets and `TIMED_WAITERS` with interrupts off;
  `wake_object` builds a `Vec` of woken threads under the bucket lock; `check_deadlines` does the
  same. Elsewhere: the ELF loader's `frames.push` / `shared.push`, the export registry's `String`,
  `Process::register_thread`, the mapping records, `live_threads`, and `notify_crash` allocating a
  `Vec::with_capacity(16)` on the fault path.

  The rule this kernel should be able to state is that any allocation an untrusted syscall can
  provoke is fallible. The scheduler wants more than that: its waiters should be intrusive fields on
  the `Thread`, not heap nodes allocated at the moment of blocking.

- [x] **A failed page-table walk keeps the intermediate tables it created.** `try_map_page_in` calls
  `next_table_create` per level with `?`, so a failure at the third level leaves the first two newly
  created tables attached to the address space - while the comment says "Nothing is left mapped on
  failure", which is true of the leaf and not of the metadata. RISC-V's `map_page_root` has the same
  shape. Repeated partial failures pin page-table frames that the domain's memory quota does not
  count. Either unwind the levels this call created, or charge page-table pages to the process and
  call them a cache.


  DONE for x86_64 2026-08-10; the RISC-V counterpart is still open. `try_map_page_in` records the
  levels it CREATES (an existing level belongs to somebody else's mapping and must survive), and on
  a failure further down clears each parent entry and retires the frame, in reverse. Clearing the
  entry first matters: retiring the frame while the parent still points at it would leave a live
  page-table pointer into memory the allocator has given away, which is worse than the leak.

  The quarantine is drained on that path rather than left for the next batch - this is the
  out-of-memory path, and holding the frames that would satisfy the caller's next attempt is the
  opposite of what it needs.

  `map_page_root` in `arch/riscv64/paging.rs` has the same shape and the same defect. It is not done
  here because this session can only verify x86_64 cheaply, and an unverified change to another
  architecture's mapper is not worth the green it would print.

- [x] **The quarantine can lose pages permanently when the heap is short - and `SharedPage` waits on it.** Not releasing a frame
  after a failed shootdown is the right call. But the quarantine is a heap `Vec`, and when its
  `try_reserve` fails the code falls back to a small stack buffer of eight frames and, past that,
  calls `note_lost_pages(1)` - after which nothing tracks the frame at all. So a heap shortage
  combined with an unresponsive core permanently shrinks physical memory, and the mechanism that
  exists to reclaim memory needs to allocate memory to work. The quarantine has to be
  allocation-free: a bit in per-frame metadata, an intrusive list, or a fixed per-CPU ring.

  DONE 2026-08-10. The quarantine is a fixed 512-entry array behind the same lock, not a `Vec`:
  `push` refuses when it is FULL - a capacity decision - and the caller then pays for its own
  shootdown, which is the path that already existed. There is no `try_reserve` left in the reclaim
  path, so a heap shortage can no longer turn deferred memory into lost memory. Draining takes
  bounded batches, so it never needs a buffer proportional to the queue and never holds the lock
  across a free. 227 of 227 on x86_64 with it in.

  It did NOT unblock `SharedPage` retiring, which is what it was expected to do - see that finding.


  DONE for the scheduler 2026-08-10. The park path reserves its bucket and timed-list room BEFORE it
  commits - before interrupts are masked and before `begin_park` - and returns without parking when
  the heap will not give it, which turns a kernel abort into a caller re-check. The wake paths and
  `check_deadlines` no longer build a vector under the lock at all: they claim in fixed batches of
  sixteen, drop the lock, enqueue, and come back, which also bounds how long the bucket is held.
  227 of 227 on x86_64 with it in.

  The wider sweep - the ELF loader's pushes, the export registry's `String`, the mapping records,
  `notify_crash` - is not done. The rule this milestone wants ("any allocation an untrusted syscall
  can provoke is fallible") is a sweep with a gate behind it, not a patch.

## Device-facing lifetimes

- [x] **An MSI vector is returned to the pool with its mapping and its device still live.**
  `unbind` for an MSI vector is `REGISTRY.free((vector - MSI_BASE) as usize); return;`, with a
  comment that "there is no source to mask". The MSI-X table page mapped at
  `MSIX_VIRT_BASE + slot * 0x1000` is never unmapped, so re-acquiring the slot calls `map_page` over
  a live leaf - which the paging layer deliberately refuses and the infallible entry point turns
  into a panic. And nothing masks the table entry or disables MSI-X on the departing device, so it
  can keep raising a vector that now belongs to somebody else's driver.

  The slot has to own the whole state: the owning BDF, the capability, the table mapping and the
  vector. Teardown masks the entry, disables MSI-X, fences, unmaps, and only then frees the vector.


  DONE 2026-08-10. `unbind` masks the device's MSI-X entry (vector control bit 0) while the page is
  still mapped, then unmaps it, and only then frees the vector. The entry's offset within its page
  is recorded when it is programmed, so the mask writes the same words the kernel wrote - the table
  is page-mapped but the entry need not sit at offset 0, and a mask at a guessed offset would
  corrupt whatever the device keeps there.

  That also fixes the re-acquire panic: the slot's fixed kernel address is free again, so
  `program_msix_entry` no longer maps over a live leaf.

- [x] **A DMA buffer's frame can be reclaimed while a device still has a descriptor for it.** The
  buffer hands a device a real physical address and its lifetime is the kernel object's; there is no
  IOMMU enforcing anything, and a CPU shootdown says nothing about a device's in-flight transfer. So
  a dropped buffer can be re-allocated to another owner while the device completes an old write into
  it. Long-term this is an IOMMU domain per device; short of that it needs an explicit submission
  ownership rule - the frames are not reclaimable until the device has acknowledged completion.
  Under a threat model where every driver is trusted this is not privilege escalation, and it is
  still a lifetime bug that a correct driver can hit.

  DESIGNED 2026-08-11, NOT APPLIED - and the reason is the shape of the fix rather than the hour.

  The CPU half is already right: `DmaBuffer::drop` retires rather than deallocates, so no core keeps
  a stale translation. What no shootdown can say anything about is a DEVICE that still holds a
  descriptor pointing at the frame, and nothing in this system currently knows when that stops being
  true - the buffer's lifetime is the kernel object's, and the object goes away when its last
  handle does.

  The rule that fixes it is a submission-ownership one: a buffer that has been handed to a device is
  not reclaimable until the driver says the device is done with it. That is an addition to the
  DRIVER CONTRACT, not to the kernel object - `submit(buffer)` marking it in flight, `complete()`
  clearing it, and a drop with the flag set going to a per-device pending list rather than to
  `retire`. Every driver has to be taught it, and a driver that forgets is a leak rather than a use
  after free, which is the correct direction for the failure to lean.

  Doing half of it - the flag with no driver calling it - would be decoration, and doing all of it
  is a milestone. Under the current threat model (every driver trusted) this is a lifetime bug a
  correct driver can hit, not privilege escalation. The long-term answer stays an IOMMU domain per
  device, which subsumes it.

  SHARPENED 2026-08-11, because the design above answers the wrong half of the problem. A
  `submit`/`complete` pair is a rule a driver keeps, and the case that actually loses memory is the
  one where there is no driver left to keep it: a driver that FAULTS with a descriptor live never
  calls `complete`, and that is exactly when the kernel tears its process down and retires its
  frames. Nine in-tree drivers would each have to be taught a rule that does not cover the case it
  was written for.

  The rule that does cover it is keyed on the DEVICE rather than on the driver: a DmaBuffer records
  which device it was created for, and its frames are not recycled until that device has been
  re-acquired - because acquiring a virtio device begins by resetting it (status register to 0),
  which is what actually stops an in-flight transfer. A dead driver then costs pinned memory until
  its device is picked up again, which is a leak in the direction a leak should lean, and it needs
  nothing from the driver that died.

  What it costs is an ABI change: `SYS_DMA_BUFFER_CREATE` takes the device handle the caller already
  holds, `rt::dma_buffer_create` passes it, and the nine drivers pass what they have in hand.

  DONE 2026-08-11, that way. Four pieces:

  - A buffer NAMES ITS DEVICE. `SYS_DMA_BUFFER_CREATE` takes a DeviceMemory capability in its second
    argument (0 = no device, which is what every caller passed before it existed and what memory
    that never goes to hardware still passes). A capability rather than an index, because the two
    ends of the rule have to be the same authority: whoever names a device here is whoever will
    later claim to have stopped it. `DeviceMemory` therefore carries which device-table entry it is
    for, which it did not.
  - TEARDOWN MARKS, A CLOSE DOES NOT. `Process::orphan_dma_buffers` walks the dying process's handle
    table and marks every DmaBuffer before `close_all`, on both the kill and the exit path. A buffer
    the process closed itself is never marked and is retired exactly as before. That difference is
    the whole rule - "you said you were done" against "you never got to say anything" - and it is
    what the `submit`/`complete` version could not express.
  - A MARKED BUFFER'S FRAMES ARE HELD, not retired: a fixed 64-entry table keyed by device, with
    `try_reserve` on the way in because this runs on a teardown path. Past the bound the frames are
    retired as they were before the rule existed, and the line is printed rather than swallowed.
  - `SYS_DEVICE_QUIESCED(device_capability)` RELEASES THEM, and it is called where the reset is:
    `virtio::negotiate_for`, straight after the handshake that writes status 0 and waits for the
    device to read back 0, and the xHCI driver after `HCRST` clears. Two call sites cover every
    driver in the tree, because every virtio driver shares that negotiation.

  The kernel cannot check the claim and never will on a machine with no IOMMU - it has no per-class
  knowledge of what "reset" means for hardware it does not drive. What it does enforce is that the
  claim comes from the holder of that device's capability and has to be made explicitly. A driver
  that never resets its device never releases anything: a leak rather than a use after free.

  `kernel.object.dma_buffer.a_dead_drivers_dma_frames_wait_for_its_device_to_be_reset` covers all
  three cases - the deliberate close that must NOT hold (holding there would leak on the ordinary
  path), the terminated owner that must, and the release that only the right device triggers.

  The long-term answer stays an IOMMU domain per device, which subsumes all of this.

- [x] **`SYS_FRAMEBUFFER_MAP` leaves its mapping behind when the reply cannot be written.** After
  `alloc_vrange` and `map_pages` succeed, the geometry is written to userspace and a `write_user`
  failure returns the error with the mapping and the VA reservation still in place - so the caller is

  DONE 2026-08-10. A failed `write_user` now unmaps every page and releases the virtual range before

- [x] **Two threads faulting on the same stack page kill the process.** `grow_user_stack` allocates

- [x] **RISC-V leaves `SSTATUS.SUM` set for the whole life of the kernel.** Both the usercopy and

  where x86's SMAP keeps the window explicit and narrow. Clear SUM by default and open it around the
  usercopy primitives with an interrupt-safe guard.
  ANALYSED 2026-08-11, not applied - the change is written out below because the analysis is the
  expensive part and it is done.

  DONE 2026-08-11, exactly as analysed, plus the one piece the analysis had not noticed:
  `clac_on_entry` is called by the x86 entry points and NOTHING called it on riscv64, so the second
  edit needed a fifth - `riscv64_trap` calls it first thing. Without that, a trap taken inside a
  window would run the whole handler with user access, and one that context-switched would leak the
  window into the next thread.

  So: `user_access` opens SUM with `csrrs` and closes it only if it was closed before (nesting-safe),
  `clac_on_entry` clears it on trap entry, `boot.rs` and `smp.rs` set only the FPU bit, and
  `copy_to_user_page` is wrapped like x86's. Verified by a riscv64 boot, which is the only thing
  that can verify it - a wrong guard does not fail loudly, it faults inside a copy that used to
  work.

  The architecture already has the shape: every kernel access to user memory goes through
  `arch::paging::user_access`, which x86 implements as `stac`/`clac` and riscv64 implements as
  `f()`. So the fix is four edits and no new plumbing:

  1. `riscv64::paging::user_access` - `csrrs` SUM on, run `f`, and `csrc` it off again ONLY if it
     was off before, so a nested window does not close the outer one.
  2. `riscv64::paging::clac_on_entry` - currently `{}`; `csrc` SUM. The trap frame saves SSTATUS at
     word 33 and the return path does `csrw sstatus, t1`, so clearing it in the handler is invisible
     to the interrupted code. Without this a trap taken inside a window runs the whole handler with
     user access, and one that context-switches leaks it into the next thread.
  3. `boot.rs` and `smp.rs` - stop setting bit 18 alongside the FPU's bit 13. Both currently do.
  4. `copy_to_user_page` in `riscv64::paging` - wrap the `copy_nonoverlapping` in `user_access`, as

  Why it is not applied tonight: it is only provable by a riscv64 boot, and a wrong guard does not
  fail loudly - it faults inside a copy that used to work, which is the kind of failure worth having
  the whole test budget in front of rather than the end of it.

  ring-3 page fault in the log is NOT the defect: `watchdog_probe` dereferences null because the
  supervisor commands it to - `CRASH` is one of the two failure modes the watchdog drill exercises.

  **THE DEFECT: the Map Table Length is at offset 264, and `scan_sequence` read it at 272.** In a
  Logical Volume Descriptor (ECMA-167 3/10.6) the Logical Volume Contents Use occupies 248..264, the
  Map Table Length 264..268, the Number of Partition Maps 268..272, and the Implementation
  Identifier 272..304. So the length was being read out of the identifier - on a volume `mkfs.udf`
  writes, the string `\0*Linux UDFFS`, which is 1766599168 as a little-endian u32. The bound check
  refused it, no sequence yielded a partition, and a perfectly good volume mounted as `Corrupt`.

  **Every fixture in the crate was built to the same misreading**, which is why all twenty-six tests
  agreed with it. That is the third time in two days a validator and its fixtures have agreed with
  each other and with no real medium, and the second time the fix was found by pointing a real
  formatter at it - so `an_image_from_an_independent_formatter_mounts` now builds a volume with
  `mkfs.udf --media-type=hd --blocksize=2048`, the same command `harness/qemu-run.sh` gives the guest,
  and requires it to mount. It fails against the old offset in 0.07 seconds, where the guest took a
  full build and a boot to say the same thing less clearly.

- [x] **Two cores shooting down at once deadlock each other until the timeout, and the aarch64 and
  riscv64 suites cannot finish because of it.** Found 2026-08-11 while trying to isolate the `SharedPage` retirement
  above, which is how it got mistaken for that change's fault.

  What is measured: on aarch64 the suite reaches this test and produces no further output for the
  whole watchdog window (900 s, and 2400 s on a second attempt), with QEMU still burning CPU - so it
  is spinning, not idle. riscv64 stops in the same test. x86_64 runs it and the whole suite. The
  test PASSES when selected alone (11 s) and inside `--tags kernel` (48 tests, 11 s), `--tags
  syscall` (52 tests, 12 s) and `--tags dynamic,frame,memory,syscall` (54 tests before the run hit
  its own limit on a genuinely slow `imgconv`), so it needs the state of the ~80 tests before it.

  It is NOT the machine being busy: it reproduced at load 3.9 as well as at load 10. It is not the
  `SharedPage` retirement: it reproduces with that reverted. It is not new to the suite's content -
  the same suite passed 216 of 216 on 2026-08-10 at 22:14, which is the last known-good run.

  The test deliberately faults in ring 0 with a user page that has gone away, on a machine with
  eight cores and other threads live, so a spin with no output is consistent with a shootdown
  waiting for an acknowledgement that never comes, or a lock held across one.

  IT IS A SHOOTDOWN, and the guest said so itself once the watchdog window was raised enough to let
  it keep going. The wedged test eventually printed:

      tlb: shootdown 3 timed out with ... acknowledgements
      tlb:   cpu 2 is at generation 2 and was asked for 3

  So a core does not answer, the initiator waits out its timeout, and the test is full of
  shootdowns - it unmaps a user page, deallocates its frame, and tears down a child process. Nothing
  is deadlocked; every shootdown pays a full timeout and the suite runs out of wall clock. That also
  explains the shape of every other observation: x86_64 finishes (its wake-IPI reliably reaches a
  parked core, and even there `shootdown 62 timed out with 2/3 acknowledgements` cost 77 s in one
  test), the two emulated targets do not, and the `SharedPage` retirement made it worse because it
  ADDS shootdowns rather than because it is wrong.

  Confirmed from the host as well, with `gdb -p` against the wedged QEMU: of its ten threads three
  were executing translated guest code and the rest were blocked in a syscall - three guest cores
  spinning, five parked. The parked ones are the ones not acknowledging.

  FOUND AND FIXED 2026-08-11, and it was not the parked cores at all - it was `shootdown` itself.
  Both of its spin loops waited without servicing THIS core's own pending request:

  - the `IN_FLIGHT` acquisition loop, where a second requester queues, and
  - the acknowledgement loop, where the holder waits.

  So two cores shooting down at once were each the reason the other could not finish: the holder
  waited for an acknowledgement from a core spinning in the first loop, which would not look at its
  flag until the holder gave up - two hundred million spins later. The interrupt path cannot cover
  that, and this is why it looked like a delivery problem: the wake IPI is serviced by the handler
  only when the core takes it, and a core already inside `shootdown` does not.

  The fix is `service_pending()` in both loops - answering needs no interrupt at all. Measured on
  aarch64 with everything else identical: `a_process_load_whose_image_goes_away_is_an_error_rather_
  than_a_dead_kernel` goes from "the suite stops here, twice, at 14 passes" to `[ok]`, with no
  shootdown timeout anywhere in the log, and the suite runs on past 87.

  What this does NOT settle: whether a genuinely parked core answers promptly. Every timeout seen
  today is explained by the collision above, and `a_shootdown_makes_another_core_stop_using_the_old_
  translation` passes on all three targets - but the 77-second x86_64 case from earlier in this
  milestone was a real timeout too, and it is worth re-measuring now that collisions cannot cause
  one.

- [x] **`a_load_that_runs_out_of_frames_anywhere_gives_back_everything` cannot be run alone.**
  Found 2026-08-10 while bisecting a frame loss that turned out not to exist: the test passes in the
  full suite and fails deterministically - three runs out of three - when selected on its own, with
  `a load refused at allocation 85 kept 1 frame(s) it took (0 still quarantined)`. On a clean HEAD,
  with nothing modified.

  SOLVED 2026-08-11, and it was two things - one of them a real leak.

  THE REAL LEAK, in `KernelStack::allocate`: `frame::allocate().filter(|frame| try_map_page(..).is_ok())`
  made two failures into one. A frame that was allocated and then could not be MAPPED - because the
  mapper itself ran out of frames for an intermediate table - was dropped by the combinator, and
  `rollback` frees what is mapped, so nothing knew about it. Every failed spawn whose budget landed
  on the mapper's own allocation lost exactly one frame. Now the two steps are separate and the
  frame goes straight back. Fixing it moved the failure from budget 85 to budget 87, which is what
  said the rest was something else.

  THE REST IS NOT A LEAK AT ALL: the kernel HEAP grows by taking frames - `register_thread` pushes
  onto a `Vec`, the handle table grows, headers are boxed - and the sweep compares the machine's
  free-frame count around each attempt. A frame the heap took is not a frame the load kept, and it
  never comes back inside the window. After two hundred other tests the heap is at its working size
  and takes nothing; alone it grows mid-sweep and the count comes back short. That is the whole
  mystery, and the giveaway was in the message from the beginning - "0 still quarantined".

  So the test now performs one complete spawn and tears it down before it starts measuring, with
  that reasoning written beside it. It passes selected alone, which is what an exact selection
  needs.

  Worth keeping: this was blamed on the frame allocator, the quarantine, the page-table rollback and
  the shared-page cache in turn, and each was suspected on plausibility rather than on evidence. The
  evidence was one number in the failure message.

- [x] **The two frame-lifetime findings need tests that can fail.** A shootdown whose acknowledgement
  arrives after the timeout, asserting the next request does not count it - injectable, because the
  timeout is already reachable. A module load into a live multi-threaded process failing after its
  shared pages are mapped, asserting the frames go through the quarantine rather than the allocator.
  A spawn-with-bootstrap loop asserting the parent's handle quota is unchanged afterwards. A
  `close_all` racing a transfer, asserting no index appears twice in the free list. N concurrent
  receivers failing their copies, asserting the queue does not exceed its limit. And a
  process-termination race asserting no thread is registered after cleanup.

  DONE 2026-08-11 - all six, and every one of them was watched to fail with its defect put back.
  That mattered: the first drafts of three of them passed against the defect they were written for.
  The shootdown test exercised a helper of its own at generation 0; the quarantine test accepted
  `queued || free_count() >= before`, which the defect satisfies; and the receive test called a
  `send_to_self_for_test` written beside it rather than the path the syscall takes. A test that has
  not been watched to fail is a claim about code that nobody has checked, and these three are why
  that rule is worth the extra build.

  The receive test found a live defect rather than confirming a closed one. `return_to_head` puts a
  message back with no bound check, and the bound it does not check is measured on the deque alone -
  so between a receive's take and its put-back the endpoint advertises room it does not have. A
  sender takes that room, the returned message lands on top of it, and the queue is one deeper than
  its limit. Measured: depth 8 against a limit of 4, with four receives in flight, and it grows by
  the number of in-flight receives every round. The copy that fails is `copy_to_user_exact`, so what
  decides how often this happens is whether ring 3 passes a good buffer.

  Fixed the way the milestone's other transaction was: the slot travels with the message.
  `Message::slot_reserved` is taken by `recv_identified` together with the message and given back by
  exactly one of `Channel::commit_delivery` (delivery happened, the slot is really free, and a
  sender waiting for room is woken HERE rather than at the take) or `return_to_head` (the message is
  back in the slot it never gave up). A send measures `inbox.len() + in_flight`, and so does
  `is_writable`, so nothing is ever told about room that a receive is holding. The counter is
  touched only under the inbox lock, which is what makes "look at the depth, then take a slot" one
  step.

  The teardown test asserts what teardown actually promises - that the set of registered threads
  cannot GROW under the cleanup - rather than that it is empty. A thread registered before
  termination stays registered until it exits, and one that was never started never reaches a kill
  point to exit at. The first draft asserted the empty set and failed against a correct tree, which
  is the same error as a test that passes against a broken one.

  The two races that need a second core held between two instructions - the shootdown's late
  acknowledgement and the registration that lands after `close_all` - are performed at the point in
  time the race delivers them to, rather than raced for. That is stated at each test: there is no
  way to stop another core between a check and its store from inside a test, and the reachable half
  of both races is the late half.

## Order

The audit's order is the right one and it is kept here. `K01` and `K02` first: they are the two that
end with a frame in use by one core and owned by another, and the first of them has a window this
tree's own logs show being entered 487 times.

Then the capability transfer as one transaction, with `close_all` taught the slot states - they are
the same bug seen from two sides.

Then the receive transaction and the process lifecycle barrier, then the fallible-allocation sweep,
then the MSI teardown.

The platform assumptions last, except that they should be written down first: a hard-coded QEMU
timebase and a bus-0-only PCI scan are not defects while the target is QEMU, and they are defects
the moment anything claims otherwise.

`K13` is not below. The page a full quarantine stops tracking belongs to

### The scheduler: one reservation for four pushes

`reserve_wait_slots` asks `bucket_of(koid).lock().try_reserve(1)` (`src/kernel/sched/mod.rs:416`).
`try_reserve` is measured against the vector's own length, not against the calls before it: it means
"have room for one more than you hold", so asking four times asks for the same one place four times.
`block_on_any` calls it once per koid and then pushes once per koid, and `bucket_of` is
`koid % WAIT_BUCKET_COUNT` with 64 buckets (`src/kernel/sched/mod.rs:141`). Two koids in one bucket
and the second push allocates.

Where it allocates is the point. It is `src/kernel/sched/mod.rs:507`, after `arch::disable_interrupts()`
and after `thread.begin_park()` - interrupts masked, the thread half-parked, on the heap the
reservation exists to stop touching. `block_on_flagged` registers in exactly one bucket and is
correct; `block_on_any` is the one that registers in several.

It is not contrived to reach. `SYS_WAIT_ANY` takes up to `MAX_WAIT_HANDLES`, koids are handed out in
sequence, and 64 buckets means a caller that creates sixty-five objects and waits on the first and
the last has chosen a collision on purpose - while a set of eight ordinary handles collides by
accident about a third of the time.

- [x] **Reserve per bucket, not per koid.** Count how many registrations each distinct bucket will
  receive and `try_reserve(count)` once for it. The deadline slot is already separate and stays.
  A test that builds a wait set whose koids share a bucket and asserts the reservation covers every
  push is the one that would have caught this, and it wants the bucket function exposed to tests
  rather than re-derived in them.

  DONE 2026-08-12. `block_on_any` counts the registrations each distinct bucket will receive and
  reserves that many once, rather than calling `try_reserve(1)` per koid - which asked for the same
  one place N times, because `try_reserve` is measured against the vector's own length. The bucket
  function is exposed to tests rather than re-derived in them, and the test builds a wait set whose
  koids collide on purpose and asserts every push was covered.

### The allocations that are still infallible on paths userspace reaches

The milestone claims allocation-free wait paths. What is true is that the hot WAKE paths are
allocation-free - `drain_bucket_into_run_queue` batches into a fixed array, `wake_object` collects
sets into one - and that `block_on_flagged` reserves before it commits. The rule the milestone
states is broader than that, and these are the places it does not hold. Each is an infallible
allocation that ABORTS the kernel on a short heap, on a path a ring-3 caller decides to take.

- [x] **`sys_wait` on a process group** builds `group_koids` with an infallible `collect()` sized by
  the group's live membership (`src/kernel/syscall/mod.rs:2245`).

  DONE 2026-08-12. `try_reserve` then push, refusing with `ERR_NO_MEMORY`.

- [x] **`sys_wait_any`** does `objects.resize_with(n, || None)` (`src/kernel/syscall/mod.rs:2312`)
  where every other buffer in that function went through `try_zeroed_u64`. It is the odd one out in
  its own function.

  DONE 2026-08-12. Through the same `try_zeroed`-shaped fallible path as every other buffer in the
  function, so it is no longer the odd one out in it.

- [x] **`Process::register_thread`** pushes into `threads` infallibly
  (`src/kernel/object/process/mod.rs:363`) - under the lock that makes it a barrier, which is
  precisely where a failure is least welcome and most necessary.

  DONE 2026-08-12. `try_reserve(1)` under the `threads` lock, refusing the registration - which the
  caller already handles, because a registration can also be refused for termination.

- [x] **`notify_crash`** allocates on the FAULT path (`src/kernel/fault.rs:138`), which is the path
  taken when a process has just died - a plausible moment for the heap to be short, and the one
  place the kernel has already promised it "must neither block nor fail".

  DONE 2026-08-12. Fallible, and it says what it dropped rather than aborting: a crash notification
  that cannot be allocated is a lost message, not a dead kernel.

- [x] **`Channel::drop`** drains its inbox through `drain(..).collect::<Vec<Message>>()`
  (`src/kernel/object/channel/mod.rs:448`) on every channel close, sized by what the peer queued.
  It needs no vector at all: pop and refund one at a time, releasing the lock between.

  DONE 2026-08-12. It needs no vector at all now: pop one message, release the lock, refund it,
  repeat. The `drain(..).collect()` that sized itself on whatever the peer had queued is gone.

### The lifecycle barrier exists for threads and for nothing else

The thread race is genuinely closed. `begin_teardown` publishes `terminating` under the `threads`
lock and `register_thread` takes the same lock, so a registration either sees the flag or completes
before teardown returns. That is a barrier.

Nothing else has one. `sys_memory_map` reads `is_terminating()` at its top
(`src/kernel/syscall/mod.rs:1619`) and calls `record_memory_mapping` at its bottom
(`src/kernel/syscall/mod.rs:1657`), with a VA reservation and a page-table walk in between;
`terminate()` publishes the flag and takes its snapshot with `core::mem::take` in between those two
(`src/kernel/object/process/mod.rs:504`). The check and the record are not one step and the teardown
runs between them.

For `mapped_memory` this is self-healing and the audit did not say so: `Drop for Process` runs
`unmap_objects()` a second time, so a mapping recorded after the snapshot is collected when the last
reference to the process goes. Said plainly because a task that overstates its own consequence gets
deferred for the wrong reason.

What is NOT self-healing is the one that matters. `orphan_dma_buffers` runs exactly once, from
`terminate()`, and walks the handle table (`src/kernel/object/process/mod.rs:495`). A `DmaBuffer`
that is not in the table at that instant is never marked, and an unmarked buffer's frames go
straight back into circulation on drop - which is the `K09` rule losing its own precondition. Two
ways to be absent: recorded after the pass, or held by `take_for_transfer`, which empties the slot
and leaves it reserved (`src/kernel/object/handle/mod.rs:454`) so `for_each_object` sees nothing
there. `close_all` correctly declines to reclaim a reserved slot, and `restore_taken`
(`src/kernel/object/handle/mod.rs:483`) then puts the capability back into a table whose close has
already happened. The capability itself is released when the table drops, so that half is not a
leak; the DMA pass having already run is the half that is.

- [x] **One guard every resource-extending operation holds, across the check AND the record.**
  Something a caller acquires before it consults `is_terminating` and releases after it has
  recorded, which `begin_teardown` waits out - so "the process is live" is true for the whole
  operation rather than at its first instruction. Then delete the scattered `is_terminating` checks
  that only cover their own first line, and make `record_memory_mapping`, `record_dma_mapping` and
  `register_thread` reachable only through it.

  DONE 2026-08-12. `Process::begin_extend` returns an `ExtendGuard`, refused once `terminating` is
  up; `begin_teardown` publishes the flag under BOTH the `threads` and `extending` locks and then
  waits for the in-flight count to reach zero before its caller takes the `core::mem::take`
  snapshot. So "the process is live" holds for the whole operation rather than at its first
  instruction.

  The three records live ON the guard - `record_memory_mapping`, `record_dma_mapping`,
  `record_dma_buffer`, `register_thread` - rather than on `Process`, which is what makes "held
  across the check and the record" enforceable instead of conventional: without a guard there is
  nothing to call. Each is fallible for the reason the section above gives, and `sys_memory_map` /
  `sys_dma_buffer_map` roll their mapping back when the record cannot be made, because a mapping the
  cleanup list does not know about is one nothing will ever collect.

  The scattered `is_terminating()` reads at the tops of those two syscalls are gone, replaced by the
  guard they were an approximation of.

- [x] **Mark a DMA buffer as orphaned wherever it can be, not only where it usually is.** A buffer in
  flight through a transfer, or created after the teardown pass, must reach the same rule. The guard
  above is one way; a per-process registry the buffer joins at creation rather than at map is
  another, and it is the one that does not depend on the handle table being the only place a
  capability lives.

  DONE 2026-08-12, with the per-process registry rather than the guard alone - the option this task
  named as the one that does not depend on the handle table being the only place a capability lives.
  `Process::dma_buffers` holds a weak reference to every buffer the process CREATED, joined under
  the guard in `sys_dma_buffer_create`, and `orphan_dma_buffers` walks it as well as the handle
  table. A buffer in flight through `take_for_transfer` - in no table at all - is reached, and so is
  one whose creation raced the teardown, because that creation either finished inside a guard the
  teardown waited out or was refused one.

  Dead entries are reaped on each join, so a driver cycling buffers does not grow the list.

### The DMA hold table hands the frames back when it fills

`MAX_HELD` is 64 (`src/kernel/object/dma_buffer/mod.rs:67`), and past it `hold` returns the frames
to the caller, which retires them and prints
`"hold table full - N frame(s) of a terminated driver retired while device D may still write"`
(`src/kernel/object/dma_buffer/mod.rs:260`).

The kernel is stating the defect out loud, which is better than hiding it, and the reasoning written
beside it - "a bounded lifetime bug is better than an unbounded list" - was the right trade against
the alternative it considered. It is the wrong trade against the one it did not: a fixed-size table
that never allocates, and a leak when even that is full. A pinned frame is a bounded loss the
machine survives. A frame handed to the next allocator while a device writes into it is a physical
use-after-free with a driver's data landing in someone else's page, and no bound on what it damages.

- [x] **Make the hold table fixed and allocation-free, like `QUARANTINE`.** It is metadata for dead
  drivers; it should not be able to fail for the same reason the quarantine no longer can, and
  `try_reserve` on a heap that is short is exactly when a driver is most likely to have died.

  DONE 2026-08-12. `[Option<Held>; MAX_HELD]` behind the same lock, and `release_for` takes entries
  out one at a time rather than building a vector - so neither the hold nor the release can fail for
  want of a heap, which was the point: a driver dying is exactly when the heap is likely to be
  short.

- [x] **When it is full, leak - never retire.** Drop the frames from the allocator's account
  permanently and count them where the other lost pages are counted, with a message that says a
  device was never confirmed stopped. The rule this milestone wrote is that a frame a device may be
  writing to does not go back; the overflow path is the one case where the rule is suspended, and
  there is no reason for it to be.

  DONE 2026-08-12. The overflow drops the frames out of circulation permanently, counts them in the
  frame allocator's own LOST total (`note_lost_pages`, made `pub(crate)` for it) as well as a DMA
  counter, and prints that a device was never confirmed stopped. `hold` no longer has a way to give
  frames back, so the retire that used to follow it cannot be reached.

  `a_full_hold_table_leaks_a_dead_drivers_frames_rather_than_recycling_them` fills the table and
  asserts the overflow is leaked and counted rather than returned.

### The ACPI checksum does not cover the pointer that is followed

`madt_local_apics` sums the RSDP's first 20 bytes (`src/kernel/smp/mod.rs:293`), then for revision 2
or later reads the XSDT pointer at offset 24 (`src/kernel/smp/mod.rs:306`). The comment beside it
says the first 20 "cover the pointers this code reads". For revision 0 and 1 that is true - the RSDT
pointer is at 16. For revision 2 it is not: offset 24 is outside the range that was summed, and the
extended checksum that does cover it, over the first 36 bytes, is never asked for. The code's own
justification is the thing that is wrong, which is why it reads as finished.

Beside it, every firmware physical address is dereferenced before anything has asked whether it is
inside the direct map. `find_table` evaluates `table_signature(hhdm, phys)` before `table_ok(hhdm, phys)`
- `&&` is left to right (`src/kernel/smp/mod.rs:375`) - and `table_ok` itself reads the length
through the same offset. A pointer past the end of the HHDM is a wild read in early boot, before
there is a fault handler worth the name.

This is firmware, at boot, on a machine whose configuration is ours, and that is a fair reason to
rank it below the others. It is not a reason to leave it: `table_ok` exists because this code
already decided not to take the firmware's word, so the gap is an inconsistency rather than a
policy, and closing it is one comparison.

- [x] **Verify the v2 extended checksum before reading the XSDT pointer**, and fall back to the RSDT
  when it fails rather than following a pointer nothing has vouched for.

  DONE 2026-08-12. Revision 2 sums the first 36 bytes before the XSDT pointer at offset 24 is read,
  and falls back to the RSDT - which the checked first 20 bytes do cover - when it fails, saying so.
  A pointer nothing has vouched for is not followed; refusing to follow it does not have to mean
  refusing to boot SMP.

- [x] **One bounds check every firmware physical address passes before it is dereferenced** - inside
  the direct map, and with the table's own length inside it too - applied in `table_signature`,
  `table_length` and to the RSDP itself, not only to the tables reached through `table_ok`.

  DONE 2026-08-12. `mem::within_direct_map(phys, len)` against a `DIRECT_MAP_LIMIT` published from
  the retained boot memory map - the same map the loader computed its HHDM extent from, so this is
  the extent rather than an estimate of it. Applied to the RSDP itself, and inside `table_signature`
  and `table_length`, which now answer `Option` - so `find_table`'s left-to-right `&&` can no longer
  dereference before `table_ok` gets a chance to refuse. `table_ok` additionally requires the
  table's own declared length to be inside the map, because the megabyte ceiling bounds how far a
  bad length walks and not whether the walk stays readable.

  `a_firmware_pointer_outside_the_direct_map_is_refused_before_it_is_dereferenced` asserts the bound
  and the three readers. It tests the refusal rather than reproducing the wild read, deliberately:
  the failure being closed is a triple fault, and a test that reproduces it reports nothing.

### New: x86 PCI config is a two-step transaction with no lock

Mechanism #1 is a pair of global ports: `CONFIG_ADDRESS` at 0xCF8 selects the register,
`CONFIG_DATA` at 0xCFC transfers it. `Access::read32` and `Access::write32`
(`src/kernel/arch/x86_64/pci/mod.rs:41`) issue the pair with nothing between them, so two cores
interleave and one reads or writes the other's device:

```
CPU0: outl CF8 = device A
CPU1: outl CF8 = device B
CPU0: inl  CFC        -> device B's register
```

Boot does not show it - the scan is serial on one core. Runtime does: `msix_enable` is reached from
the MSI syscall (`src/kernel/syscall/mod.rs:1121`), so ring 3 on any core issues this pair, and
`set_intx_disabled` runs from device acquisition (`src/kernel/device.rs:64`). A write landing on the
wrong function is a command register written into somebody else's device.

It is x86-only, and the reason belongs in the fix: ECAM puts the register in the ADDRESS, so
`read32` on aarch64 and riscv64 is a single `read_volatile` (`src/kernel/arch/riscv64/pci.rs:55`)
with nothing to interleave. Mechanism #1 puts it in a side register, and that is what makes it a
transaction rather than an access.

- [x] **One lock around the CF8 -> CFC pair**, held across both instructions, in the x86 `Access`
  implementation where the pair lives - so the common walker and every runtime caller get it without
  knowing it exists.

  DONE 2026-08-12: `static CONFIG_PORTS: SpinLock<()>`, taken by `read32` and `write32` in
  `arch/x86_64/pci`. Nothing above them changed - the common walker, `msix_enable` and
  `set_intx_disabled` are serialised without knowing it - and the two device-tree backends are
  untouched, because ECAM puts the register in the address and has no pair to serialise.

### MSI-X masking stops the next message, not the one in flight

`mask_and_unmap_msix_entry` says it itself: "the device may still have a message in flight; masking
stops the next one, which is all this can promise without the driver's cooperation"
(`src/kernel/arch/x86_64/interrupts/mod.rs:192`). The teardown is a real improvement - the right
entry is masked, its page is unmapped while it is still reachable, and the slot is released last -
and the re-acquire panic is gone. What remains is that a vector can be reused while a message the
old device already sent is on its way.

The honest answer is the one the DMA rule reached: masking is a request, and only the device says it
stopped. That makes this the same shape as `K09` rather than an interrupt-controller detail.

- [x] **Read back what the mask did, and say what is still unproven.** At minimum, do not reuse a
  vector until the device behind it has been quiesced through the path `SYS_DEVICE_QUIESCED`
  already provides; where that is not available, record the vector as pending rather than free.

  DONE 2026-08-12, as the second half of the task - the vector is recorded as PENDING rather than
  free - which is the half that is actually enforceable. `MsiRegistry::retire` drops the binding and
  leaves the slot reserved with its owner retained; `acquire` therefore cannot hand it to the next
  driver, and `release_for_device` frees it when `SYS_DEVICE_QUIESCED` arrives - the same claim,
  from the same capability, that releases the dead driver's DMA frames. All three backends, because
  the rule is not arch-specific: x86 masks the MSI-X entry, aarch64 has written the GICv2m frame
  address into it, and riscv clears an IMSIC enable bit that stops nothing already sent.

  Reading the mask back is deliberately NOT done. A read of the vector-control word returns what was
  just written to it and says nothing about a message already on the wire, so it would be evidence
  of nothing while looking like evidence. What the device did is a question only the device answers,
  which is what the pending state now waits for.

### The two architecture headers say something this tree disproves

`src/kernel/arch/aarch64/mod.rs:3` opens with `STATUS: STUB` and ends "a boot on this arch is not
possible until then". This milestone measured 226 of 226 tests on that target.

The interesting fact is not that the comment is stale. It is why it can be stale and still describe
something real: aarch64 boots through `aarch64_main` (`src/kernel/arch/aarch64/boot.rs:175`), which
brings up its own console, exception vectors, GIC and timer, and never calls `arch::init`,
`arch::init_interrupts` or `arch::init_syscalls` - which are still `todo!()`, seventeen of them in
that file and twelve in riscv64's. So the HAL contract listed at the top of `src/kernel/arch/mod.rs`
is not satisfied by either port that boots; those ports go around it.

That matters more than a wrong comment, because the contract is the document that says how a fourth
architecture would be added, and it currently describes a path that two of the three existing
targets do not take.

- [x] **Correct both headers to what is true**: which contract entry points each backend implements,
  which it bypasses through its own boot path, and which are genuinely unreached.

  DONE 2026-08-12. riscv64's header was already accurate. aarch64's said `STATUS: STUB` and "a boot
  on this arch is not possible" while the target was passing 226 of 226, and now says which
  submodule implements each mechanism, that the six portable `init_*` hooks remain `todo!()`, and
  that none of them is on a path this target takes because it enters at `boot::aarch64_main`.

- [x] **Say in `arch/mod.rs` that the contract is the x86_64 path**, and either bring the other two
  through it or record that boot is deliberately per-architecture and the contract begins after it.
  A list of required symbols that two backends satisfy with `todo!()` is not a contract yet.

  DONE 2026-08-12. The contract paragraph now says the six `init_*` entries are the hooks the

  device tree and firmware already in supervisor mode) and the cost (nothing type-checks the three
  bring-up sequences against each other, so a step added to one is silently absent from the others).
  The two candidate fixes are named there rather than scheduled, so the next person reads a decision
  instead of a gap.

### Order

The SMP race first: the CF8/CFC pair is reachable from ring 3 today, and it is one lock.

Then the two that end with memory in the wrong hands - the DMA overflow path, and the orphan pass
that a buffer can be absent from - because they are the same rule losing its precondition twice, and
because the second is what makes the first reachable more often than the table's size suggests.

Then the scheduler's bucket reservation, which is a real abort with interrupts off, and the
fallible-allocation sweep behind it. `Channel::drop` is worth doing first of those: it needs no
vector at all.

Then the lifecycle guard, which is the largest and the one that should be designed rather than
patched - it is what closes the DMA orphan hole properly, so the narrow fix above should be written
so it does not have to be undone.

The ACPI checks and the MSI-X quiesce last. The two architecture headers are documentation and can
go at any point; they should not wait for the code they describe, because a false statement about
what boots is doing damage while it waits.

## Reopened again: the second pass moved three of its own invariants

A third audit of the same surface, against this tree at `8df720c` - 2026-08-12. Every finding below
was read in the code before it was written here, and where the audit named a consequence the code
does not have, that is said rather than repeated.

The shape is different from last time and worth naming, because it is not "the fix stopped at its
hot path" again. Three of these exist BECAUSE of the second pass. `ExtendGuard` is a real barrier
and two syscalls that extend a process more than any other do not take it. `take_for_transfer` is a
real two-outcome protocol and the spawn that uses it holds no guard over the window between the two
outcomes, so a third party can decide the outcome for it. The queue charge was correctly moved from
the dequeue to the commit, and one receive path has no commit - so a model that used to refund
early now does not refund at all.

That is the cost of fixing an invariant by fixing its callers: the invariant gets stronger and the
call sites that were not in the list get weaker, because they used to be no worse than the rest and
now they are the only ones left. The two findings carried over from the second pass - the infallible
allocations and the RMW config accesses - are the same story a round late.

One finding is NOT here. The frame allocator's double-allocation detector reports and then hands the
frame out anyway; that belongs to [P02M0120](P02M0120.md), whose whole subject is the one
unreproduced sighting the detector exists for, and it is recorded there.

### The spawn holds no guard over the window its own transfer opens

`sys_thread_create` (`src/kernel/syscall/mod.rs:1370`) reads `process.is_terminating()` at
`:1383` and then runs a four-step transaction on the TARGET: `take_for_transfer` from the caller,
`try_insert_or_return` into the child, `create_user_thread`, `install_object`, `commit_taken`. The
flag read is a read. The guard that would make it a barrier is taken three calls later, inside
`Thread::build` (`src/kernel/object/thread/mod.rs:219`), which is far too late: by then the
capability is already in the child.

The window is exact. The child's bootstrap capability is inserted ORDINARILY - it is not reserved -
so a `terminate()` that runs now reaches `close_all` (`src/kernel/object/handle/mod.rs:533`), which
skips reserved slots and takes this one, destroying the capability. `create_user_thread` then fails,
because `begin_extend` refuses. The rollback tries to take the capability back out of the child
(`src/kernel/syscall/mod.rs:1435`) and gets `Err`, so `restore_taken` is never reached.

What is left afterwards is worse than the loss of the capability, and it is permanent: the caller's
slot stays `reserved: true` with `cap: None`, which no other operation in the handle table ever
clears. The slot is not on the free list, `commit_taken` will not run, `close_all` will skip it
forever, and the one unit of handle quota `take_for_transfer` deliberately did not refund is never
refunded. A supervisor that races a spawn against a kill loses one slot and one quota unit per
attempt until it cannot spawn at all - which is the exact failure `K03` was closed to prevent, one
layer up.

- [x] **Take the target's `ExtendGuard` before the capability moves, and hold it to the commit.**
  The transaction is "this child gains a capability and a thread"; that is one resource-extending
  operation on the target and it needs one guard over all of it, from before `try_insert_or_return`
  to after `commit_taken`. `Thread::build` may keep its own guard - guards nest by counting - or the
  outer one can be passed down; what must not remain is a window where the child is extended by a
  caller holding nothing.

  DONE 2026-08-13. `sys_thread_create` takes `process.begin_extend()` before anything moves and drops
  it after `commit_taken`. `Thread::build` keeps its own - guards nest by counting - so nothing had to
  be threaded down.

- [x] **Replace the `is_terminating()` read at `:1383` with that guard**, so the target's liveness
  is decided once, at the point that also prevents it from changing. A flag read before a
  transaction answers a question about a moment that has passed by the time the answer is used.

  DONE 2026-08-13. The read is gone; the guard's refusal is the same `ERR_INVALID`.

- [x] **Make an abandoned reservation impossible to leave behind.** Whatever the outcome, exactly
  one of `commit_taken`/`restore_taken` must run - the contract says so in as many words at
  `src/kernel/object/handle/mod.rs:454` and this call site can currently reach neither. A
  reservation whose owner is gone should be recoverable rather than eternal: either the take is
  scoped to a guard that restores on drop, or `close_all` learns to reclaim a slot whose transfer
  can no longer complete.

  DONE 2026-08-13. `HandleTable::abandon_taken` is the third outcome: the handle value dies, the slot
  goes back under the generation rules and the quota is refunded - `commit_taken`'s costs exactly,
  differing only in where the capability went. Both rollbacks in `sys_thread_create` now end in one
  of the three, whatever the child did with the capability.

- [x] **A test that kills the child between the insert and the thread build** and asserts the
  caller's handle is either intact or properly retired - never a reserved slot with no capability
  and no way to reach one. The counter to assert on is the Domain's handle charge before and after.

  DONE 2026-08-13 as `a_transfer_that_can_no_longer_be_resolved_gives_the_slot_back`
  (`src/kernel/object/tests.rs`), which asserts the property directly - the quota comes back, the
  handle value is dead, and the slot is reusable - rather than through a kill whose timing the
  harness cannot control. The guard makes the racing kill unreachable; the test pins what the table
  does when a transfer cannot be resolved either way, which is what the damage was made of.

### The lifecycle guard is not taken by the two syscalls that extend a process the most

`SYS_PROCESS_LOAD` (`src/kernel/syscall/mod.rs:1300`) calls `loader::load_image_into`
(`:1334`) and `SYS_PROCESS_LOAD_MODULE` (`:1341`) calls `loader::load_module_into` (`:1357`).
Neither takes `begin_extend` on the target. `sys_process_load` does not even read
`is_terminating()` - it looks the process up with MANAGE and loads into it.

These are the largest resource-extending operations the kernel has. `load_image_into`
(`src/kernel/loader.rs:125`) maps every PT_LOAD segment, allocates a frame per page, maps a ring-3
stack, then `adopt_frames`, `adopt_shared_pages` and `charge_stack`. `load_module_into`
(`:170`) additionally claims a module slot and registers dynamic symbols. Every one of those is a
record the teardown snapshot has to see.

So a `PROCESS_LOAD` that begins before a `terminate()` and adopts after it hands a dead process a
page table full of live mappings and a frame list nothing will collect from `terminate`'s snapshot.
Say plainly what this is and is not: `Drop for Process` runs `unmap_objects` and frees adopted
frames when the last reference goes, so this is not the physical use-after-free the first audit
found - it is a resource set that grows after the barrier that exists to close it, held until the
last handle to a dead process is dropped. The invariant "after `begin_teardown` a process's resource
set cannot grow" is simply not true, and `PROCESS_LOAD_MODULE` is by definition an operation on a
process that already exists and may already be dying.

- [x] **Hold `begin_extend` across the whole of both loads**, from before the first allocation to
  after `adopt_frames`/`adopt_shared_pages`/`charge_stack` and after any rollback. Refuse with
  `ERR_INVALID`, the same refusal `sys_thread_create` gives for the same reason.

  DONE 2026-08-13. Both `load_image_into` and `load_module_into` take it at the top and hold it
  through the adopts and every rollback.

- [x] **Decide where the guard belongs** - the syscall or `loader::load_*_into` - and state it. The
  loader is called from boot as well as from the syscall, so a guard inside it must be one a boot
  path can also take; the argument for putting it there anyway is that the rule then travels with
  the operation instead of with one of its callers, which is the whole lesson of this section.

  DONE 2026-08-13: IN THE LOADER, and the comment there says why. The boot path takes it without
  noticing - a process it has just created is not terminating - and the rule then travels with the
  operation rather than with one of its callers, which is this section's own lesson. The refusal is a
  new `LoadError::Terminating` rather than `BadImage`, because the image is fine and the caller's
  mistake is a race; both map to `ERR_INVALID` at the syscall boundary.

- [x] **A test that terminates the target while a load is in flight** and asserts the load is
  refused rather than completing into a process whose cleanup has already run. The observable is the
  process's frame and mapping counts after both have finished.

  DONE 2026-08-13 as `a_load_into_a_terminating_process_is_refused`
  (`src/kernel/test_suites/dynamic.rs`): a module load and a main-image load into a terminated
  process, each refused, with the address space asserted to hold neither the segment nor a stack.

### `Channel::recv` takes the message and never releases its charge

The second pass moved the queued-bytes refund from the dequeue to the delivery commit, and it was
right to: a receive that failed its copy used to put an uncharged message back past the limit. The
commit point is `Channel::commit_delivery` (`src/kernel/object/channel/mod.rs:357`), reached from
the syscall path after `recv_identified`.

`Channel::recv` (`:261`) is the other receive path and it has no commit. It pops the message and
returns it with `queue_charge` still set - the comment at `:264` explains why the refund is no
longer there and does not say what takes its place for THIS caller - and `Message` has no `Drop`, so
when the returned message goes out of scope the charge is simply forgotten. `take_queue_charge` is
private; the caller could not release it if it knew to.

It is not a dead path. `src/kernel/main.rs:525` drains `kernel_ep.recv()` for the boot-chain reports
SystemManager sends from ring 3 through `send_charged_or_return`; `src/kernel/main.rs:445` drains
the crash channel the same way; `src/kernel/arch/aarch64/boot.rs:573` and
`src/kernel/arch/riscv64/boot.rs:495` do it on their targets. Every message the kernel reads this
way leaves its sender's Domain permanently charged for bytes that are no longer queued anywhere. A
service whose kernel-side peer reads it in a loop walks its own IPC quota down until its sends start
failing with `Full` against an empty queue, and nothing reports why.

- [x] **`recv` is a committed receive, so make it commit.** Release the queue charge and the slot
  reservation before returning the message: this path has no rollback and no put-back, so the
  dequeue IS the point of no return. That is one call, and it restores the accounting the
  transactional path already keeps.

  DONE 2026-08-13. `Channel::recv` releases the queue charge as it dequeues, which is the point of no
  return for a path with no rollback.

- [x] **Name the two receives apart** - `recv_committed` and `recv_transactional`, or keep `recv`
  and document the split at both definitions. Two functions that differ in who owes the refund, and
  are told apart only by which one the caller happened to reach for, is how this was introduced.

  DONE 2026-08-13 by documenting the split at both definitions - `recv` says it commits and why,
  `recv_identified` says its charge travels to `commit_delivery`. Renaming was considered and not
  done: `recv` has callers in the boot paths of all three targets and the rename would have touched
  them for no gain the comments do not already give.

- [x] **Give `Message` a `Drop` that refunds what it still holds**, so a charge cannot be lost by
  any future path at all, and the explicit release becomes an optimisation rather than the only
  thing standing between the kernel and a slow leak. A drop that refunds is also what makes the
  charge safe to carry across an early return.

  DONE 2026-08-13, on the CHARGE rather than on the message. A `Drop` on `Message` makes it
  un-destructurable and forty call sites move `bytes` and `caps` out of one; a `QueueCharge` with its
  own `Drop` gives the same guarantee with no such cost. The explicit release at the commit point
  stays as an optimisation - it frees the sender's quota when delivery is certain rather than
  whenever the message happens to die.

- [x] **A test that measures the Domain's `ipc_queue` before and after a kernel-side drain** and
  asserts it returns to where it started. It wants the counter readable in the test kernel, which
  `SYS_DOMAIN_STATS_GET` already provides.

  DONE 2026-08-13 as `the_committed_receive_refunds_what_it_takes`, which drains sixteen messages the
  way the kernel does and asserts the counter returns to where it started - and separately that a
  message taken transactionally and never committed refunds itself when it dies.

### Repeated MSI-X acquisition for one device aliases table entry 0

`MsiRegistry::acquire` (`src/kernel/arch/common/msi.rs:66`) answers "is this SLOT free" and records
the owner; it never asks whether that owner already holds a slot. Every backend programs the
device's MSI-X table ENTRY 0 for whatever slot it was given - `program_msix_entry` writes the first
entry on x86 (`src/kernel/arch/x86_64/interrupts/mod.rs:129`), on riscv
(`src/kernel/arch/riscv64/interrupts/mod.rs:87`) and on aarch64.

So two `SYS_DEVICE_MSIX_ACQUIRE` calls for one device index produce two vectors, two registry slots
and two `Interrupt` objects, all pointing at one hardware entry - which now carries the second
vector. The first `Interrupt` is bound to a vector the device will never raise, and when it drops,
`unbind` (`src/kernel/arch/x86_64/interrupts/mod.rs:98`) masks and unmaps entry 0, which is the
entry the SECOND interrupt is live on. An old handle silently disables a new one.

Its authority is DeviceManager's, so this is not a ring-3 escalation; it is a functional trap for the
one caller that exists, and the restart path walks straight at it - a crashed driver's vector is
retired but its device is unchanged, and rebinding acquires again for the same device.

- [x] **Refuse a second live acquisition for a device, or allocate real table entries.** One entry
  per device is a legitimate limit for a kernel that programs one; what is not legitimate is
  discovering the limit by aliasing. The registry knows the owner, so the check is a search of
  `owner` for a slot that is `used` and not `pending`.

  DONE 2026-08-13, and it took two corrections that are worth recording because each was a real
  answer. `MsiRegistry::has_live(owner)` is the question - `used` and not `pending` - and
  `sys_device_msix_acquire` is where it is asked.

  The first attempt refused on a PENDING slot too. That broke driver restart: a pending slot's
  `Interrupt` is already gone, and what the pending state protects is that no new owner is given that
  VECTOR while a message for it may be in flight - a fact about the slot, not about the device.

  The second attempt put the refusal inside `MsiRegistry::acquire`, and the xHCI bring-up test failed
  on it - correctly. That test spawns the userspace xhci driver over a controller the BOOTED SYSTEM
  has already claimed, standing in for DeviceManager by calling `acquire_msi` directly; it has been
  passing because of the aliasing this item is about. So the rule belongs at the syscall, which is
  the path whose one caller is DeviceManager, and the mechanism stays able to serve a caller that
  knows what it is doing.

- [x] **Program the entry index the slot owns, not entry 0**, if more than one vector per device is
  wanted - the table's size is in the MSI-X capability and the backends already map the table page.
  Whichever is chosen, say it at `acquire_msi`, which currently documents "entry 0" as though it
  were the only entry that exists.

  DONE 2026-08-13 as the other half of the choice: ENTRY 0 IS THE ONLY ENTRY, and `acquire_msi` on
  all three backends now says so and says what wanting more would take. Programming the slot's own
  index is the change that lifts the limit; the refusal is what makes it a change rather than a bug
  fix.

- [x] **A test that acquires twice for one device** and asserts the second is refused - or, under
  the other choice, that it programs a different entry and dropping the first leaves the second
  delivering.

  DONE 2026-08-13 as `one_device_holds_one_msi_slot` (`src/kernel/object/tests.rs`): the second
  acquisition is refused, another device is unaffected, and a restarting driver may take a FRESH slot

### The MSI-X syscall programs hardware before it has anywhere to put the result

`sys_device_msix_acquire` (`src/kernel/syscall/mod.rs:1112`) acquires the vector, programs the
device's table, binds the `Interrupt`, calls `msix_enable`, and only then `install_object`
(`:1148`) - which fails if the caller's handle table is full or its Domain is at quota.

On that failure the `Interrupt` drops, `unbind` masks the entry and `MsiRegistry::retire` marks the
slot PENDING - correctly, by the rule the second pass established, because a message may be in
flight. But the slot now waits for a `SYS_DEVICE_QUIESCED` that will never come for a driver that
was never created. The vector is out of circulation until someone quiesces a device that never
started, and the failure is repeatable: MSI slots are a fixed table, and each failed acquire costs
one.

- [x] **Reserve the caller's handle slot first, then touch the hardware.** `HandleTable::reserve`
  and `insert_reserved` exist for exactly this and are already used by the receive path: reserve,
  acquire the vector, program, bind, enable, insert against the reservation, release the reservation
  on any earlier failure. Then no failure path leaves hardware programmed.

  DONE 2026-08-13. `sys_device_msix_acquire` reserves, acquires, programs, binds, enables and then
  installs against the reservation - which cannot fail - releasing the reservation on every earlier
  refusal.

- [x] **Distinguish "never delivered" from "may have delivered" in the retire.** A slot whose
  `Interrupt` never reached its owner cannot have a message in flight for that owner and can be
  freed outright - `MsiRegistry::free` already exists for the acquired-and-never-programmed case and
  this is the same case one step later, provided the entry is masked first.

  DONE 2026-08-13. `release_unused_msi` (all three backends) masks and FREES: a vector whose
  `Interrupt` never reached an owner cannot have a message in flight for it, and MSI-X was not even
  enabled on the device yet. Retiring those left a fixed-table slot waiting for a quiesce from a
  driver that was never created.

### `restore_taken` writes into a table that has already been closed

`close_all` (`src/kernel/object/handle/mod.rs:533`) skips reserved slots, which is right - their
capability is elsewhere and one of two calls is still to come. `restore_taken` (`:483`) then puts
the capability back unconditionally, into a table whose process has finished its teardown.

The audit called this a lifecycle hole and it is one; it is smaller than the two above. Accounting
stays consistent - `take_for_transfer` never refunded, `Drop for HandleTable` (`:584`) refunds every
live capability - so what actually happens is that an object is held alive by a dead process's table
until the last reference to the `Process` goes. That is a delayed release, not a leak and not
corruption. It is still true that `close_all` is not the terminal barrier its name and its use imply.

- [x] **Give the table a closed state and make `restore_taken` respect it.** Live: restore. Closing
  or closed: drop the capability instead, refunding as `close_all` would have. Three states named
  once are clearer than the current arrangement, where "has this table been closed" is answerable
  only by inference.

  DONE 2026-08-13. `close_all` sets `closed`; `restore_taken` into a closed table drops the
  capability, clears the reservation and refunds the quota - what `close_all` would have done had the
  capability been present. The existing teardown test asserted the opposite and now asserts this,
  with the reason recorded in it.

### PCI config read-modify-write is locked per access, not per operation

The CF8/CFC lock the second pass added is correct and closes the interleaving it was written for.
What it does not cover is the operations built ON it: `set_intx_disabled`
(`src/kernel/arch/common/pci.rs:521`) reads the command register, modifies a bit and writes it back
as two separately-locked accesses, and `msix_enable` (`:532`) does the same for two registers.

No concurrent writer to those registers exists today - the INTx disable happens during the serial
boot scan, and MSI-X enable is DeviceManager's, one device at a time - so this is hardening and not
a defect. It is recorded because the lock is there and it looks like it covers this.

- [x] **A transactional config update.** `update16`/`update32` taking a closure and holding the
  config lock across the read and the write, with the existing read-modify-write helpers moved onto
  it, so a future concurrent writer cannot reintroduce the race the lock was added to remove.

  DONE 2026-08-13. `ConfigAccess::update32` holds the backend's lock across the read and the write
  through `with_config`, with `read32_raw`/`write32_raw` for use inside it (the lock is not
  reentrant). Every config read-modify-write in the tree goes through it - `set_intx_disabled`,
  `msix_enable`, `assign_bars_ecam` and `enable_mem_and_master` - and `write_command`, which was the
  second half of each of them, is gone.

## Reopened a third time: the new rollback walks into the door that was built to stop it

A fourth audit, against this tree at `4350074` - 2026-08-14. Four findings and all four hold. The
first is the most serious thing any of these audits has produced, and it is worth saying why before
saying what it is: `frame::retire` exists because of a defect this milestone found, its doc comment
names the exact scenario, and the rollback added in the LAST round to fix K06 on the stack-growth path
bypasses it.

The audit's account of the round is otherwise right and closes four findings properly: `thread_create`
holds `begin_extend` across the whole bootstrap transaction, `HandleTable` has a terminal `closed`
state so a late restore cannot resurrect a capability into a dead process, the raw `Channel::recv`
releases the sender's queue charge and `QueueCharge` makes forgetting it recoverable, and both loader
entry points take the lifecycle guard inside the operation rather than at the syscall. The CF8/CFC

### A frame that was in a page table is returned to the allocator without a shootdown

`src/kernel/fault.rs:98-103`:

```rust
if !process.try_adopt_frame(new_frame) {
    let _ = process.address_space().unmap(page);
    unsafe { frame::deallocate(new_frame) };
    return false;
}
```

`AddressSpace::unmap` is `arch::paging::unmap_page_in` and nothing else
(`src/kernel/object/address_space/mod.rs:102-104`) - the PTE is cleared and the local core invalidates
its own TLB. Another core running in the same address space keeps its translation until something
tells it to drop one.

`frame::retire` is what tells it. Its own comment states the rule and the failure
(`src/kernel/mem/frame/mod.rs:1167-1172`):

> The one door back to the allocator for anything a page table ever pointed at. [...] A frame handed
> out again while another core still has a stale translation is a physical use-after-free, and it does
> not need a hostile process to arrive - it needs two cores and a mapping that outlived its unmap by a
> few microseconds.

So:

```
CPU A                                   CPU B (same address space)
-----                                   --------------------------
stack fault, frame X allocated
map VA -> X
                                        touches VA, TLB caches VA -> X
try_adopt_frame(X) fails (heap short)
unmap VA, local invlpg only
frame::deallocate(X)                    TLB still says VA -> X
X is free; allocator hands it to
a page table, a kernel object, or
another process
                                        writes through VA into whoever owns X now
```

Ring 3 reaches this by touching a guard page while the kernel heap is short, which is the same
condition the fallible adoption was added for. The repair made the failure REACHABLE and returned the
frame through the wrong door.

- [x] **`frame::retire(&[new_frame])` after the unmap,** never `deallocate`. That is the rule the
  module states; this path is the one caller that does not follow it.

- [x] **Make the rule mechanical.** Every other site that frees something a page table pointed at was
  converted to `retire` in the round that created it, and the next new rollback will be written the
  same way this one was. `deallocate` should not be reachable from code that can have mapped the
  frame - a separate type for a mapped frame, or `deallocate` made private to the retirement path with
  the boot-time callers named explicitly.

- [x] **A test that catches the class,** not the instance: a counter of frames returned through
  `deallocate` after having been mapped, asserted zero, or an SMP test that faults a stack page under
  an injected adoption failure while another core reads the same address.

### `has_live` and `acquire` are two operations, and two CPUs can pass both

`sys_device_msix_acquire` asks `device_has_live_msi(owner)` and then calls `acquire_msi`, which calls
`MsiRegistry::acquire`. That function CASes `used[slot]` and stores the owner
(`src/kernel/arch/common/msi.rs:65-74`); it does not look at whether the owner already holds a slot.
`has_live` is a separate read over the array (`:92-97`).

The comment above `has_live` states the design deliberately (`:78-81`): the question is answered here
and enforced at the syscall, so that the kernel's own bring-up test can call the mechanism directly.
That is a reasonable split for a sequential caller and it does not survive two of them:

```
CPU 0                          CPU 1
-----                          -----
has_live(A) -> false
                               has_live(A) -> false
acquire(A) -> slot 4
                               acquire(A) -> slot 5
program A's MSI-X entry 0 = 52
                               program A's MSI-X entry 0 = 53
```

Both syscalls succeed, the device's entry 0 holds 53, and dropping the first `Interrupt` masks entry 0
- the entry the second one is live on. That is precisely the aliasing the comment at `:83-86`
describes and forbids: "An old handle silently disabling a new one."

And the arch backends say the mechanism prevents it. `src/kernel/arch/riscv64/interrupts/mod.rs:89-90`
and its aarch64 twin both say "`MsiRegistry::acquire` refuses a device that already holds a slot".
It does not.

- [x] **One operation: `acquire_unique_live(owner, limit)`,** which finds a free slot and claims it for
  an owner that has no live slot, atomically. The syscall keeps the policy decision - what to do when
  it fails - and stops holding a decision made from a value that can change under it.

- [x] **Correct the two arch comments,** which describe an enforcement the shared mechanism does not
  do. They are the reason a reader would not look for this.

## A fifth round: the markers were load-bearing, and four of them were false

Against `7b71ece`. The audit's account of the fourth round is accurate and is not in dispute: the
stack-growth rollback retires its frame, `check-frame-retirement.sh` turned that into an invariant
and found the heap rollback carrying the same defect, and the MSI-X race is closed by an atomic
composite under one claim lock rather than by another pre-check. Each was verified against the code.
Its finding is about K06, and it is the right one: the gate got much wider and the code it grades
learned to talk to it.

An `ALLOC-OK:` marker is a claim, and the gate stops asking when it sees one. Four of them claimed
things that were not true, and the gate's own surface had a hole big enough for a whole class.

### Markers that asserted a booking nobody had made

- [x] **`elf::load_parsed` reserved nothing.** The marker read "the vector is reserved from the
  segment count above" and there is no reservation in the function - the two `try_reserve`s nearby
  book `frames` and `shared`, which are different vectors. The count comes from the image, so it is
  not a compile-time bound, and a short heap part-way through mapping a program's segments aborted
  the kernel. Now booked, fallibly, from `segment_count()`.

- [x] **`Process::adopt_frames` / `adopt_shared_pages` said "moved in whole at spawn".** That
  describes one of three callers. `load_module_into` - `SYS_PROCESS_LOAD_MODULE` - adopts into a
  process that already owns every frame of its main image, so `extend` grows a vector with contents
  in it, on a ring-3 path, with no way to report a failure. `reserve_adopt` books both vectors and
  the three loader paths call it BEFORE their point of no return, so the failure lands inside the
  transaction that already knows how to unwind: the module path books before registering symbols,
  the image path unmaps its segments and stack, and the spawn path just returns the frames.

- [x] **`reserve_dynamic_module_at` said "bounded by the loader's module-graph limit".** A bound says
  there will never be a sixty-fifth entry; it says nothing about whether the heap can hold the first.
  `try_reserve(1)`, into the refusal the function already had.

- [x] **The scheduler's run queues said "one entry per RUNNABLE thread, bounded by the Domain thread
  quota".** Same sentence, worst place: seven `push_back` sites, reached by `SYS_THREAD_START` and by
  every wake, and enqueue has nowhere to put a refusal - a runnable thread that cannot be queued is a
  thread that never runs again. So the room is booked at CREATION, on every core, where `None` is an
  answer every caller already handles. A woken thread joins the waker's queue and any core can be the
  waker, which is why the booking is not per-core; the count is global and the invariant each core
  holds is `capacity >= live threads`.

- [x] **And a test that the booking balances.** The first attempt reserved in a wrapper around the
  constructor and released both in the wrapper's failure branch and in `Drop for Thread`, so a thread
  that was built and then refused registration released twice - the counter wrapped through zero and
  the next reservation panicked on the overflow. The booking is now taken immediately before the
  object that owns it and released by hand only where no object came into being. Verified by
  reintroducing the double release and watching the test fail on it.

### The gate could not see `collect`, which is how a syscall path stayed hidden

`Process::live_threads` ends in `.collect()`, and `SYS_PROCESS_SIGNAL` walked it to wake every thread
while `SYS_PROCESS_STATS_GET` used it to ask whether any thread was left. Two ring-3 syscalls
allocating infallibly, in a file the gate scans, because `collect` was not in what it looked for.

- [x] **`.collect()` is in the gate's surface.** It allocates outright, so it is graded like
  `Vec::with_capacity`: fixed or marked.

- [x] **`SYS_PROCESS_SIGNAL` walks in fixed batches.** `live_threads_from` fills storage the caller
  already has and releases the lock before the caller touches it - waking takes the scheduler's lock
  and dropping the last reference runs `Thread::drop`, neither of which may happen underneath it.

- [x] **`SYS_PROCESS_STATS_GET` reads the counter it already has.** `live_thread_count` answers the
  question `live_threads().is_empty()` was building a vector to ask.

- [x] **And the four more the widened gate then found,** none of them in the audit: `ProcessGroup::create`
  collected a bounded membership infallibly; `ProcessGroup::live` did the same and has five ring-3
  callers, which now fill a `MAX_GROUP_MEMBERS` array in one pass; `Domain::kill` built two vectors
  by `collect` - and killing a Domain is what a supervisor does when memory has already run out, so
  an allocation on the path that reclaims memory is the one that must not be there; the remaining
  `collect`s are the System Graph dump and boot enumeration, marked as such.

### The other two

- [x] **`ObjectHeader::name` borrows instead of cloning.** It returned `Option<String>` - a fresh
  allocation per reader - and the reader that matters is the ring-3 fault handler naming the process
  it is about to terminate. A faulting process on a short heap took the kernel through an allocation
  while handling the fault, which is the worst moment this kernel has to ask for memory: the request
  that caused the pressure is the one being cleaned up. `with_name` holds the lock across a closure.

- [x] **`HandleTable::insert` refunds the Domain when the table cannot grow.** It charged the quota,
  called `place`, and `place`'s failure branch dropped the capability and returned handle 0 - so a
  short heap left the Domain paying for a handle that does not exist, unreclaimable because there is
  no handle to close, once per attempt. The invalid handle stays: this is the form documented as
  unable to fail, and a token that names nothing is a refusal the holder discovers on first use.

### The gate itself

- [x] **The `try_reserve` exemption is per-receiver and in order.** It was "this function mentions
  `try_reserve` somewhere", which exempted a push ABOVE the reservation and a push on an entirely
  different collection. It now matches the receiver - `self.free` in `self.free.insert(..)` - and only
  from a reservation already seen. One booking still exempts any number of growths of that
  collection, because `try_reserve(n)` followed by a loop of pushes is the CORRECT pattern and no
  textual rule can count them; the header says so rather than implying otherwise.

- [x] **Every reservation on a line, not the first.** A transaction that books two collections in one
  condition - `a.try_reserve(n).is_err() || b.try_reserve(n).is_err()` - books both, and reading only
  the first left the second looking unbooked.

- [x] **A marker anywhere in the comment block above the line.** It had to be on the line touching the
  code, which produced markers written for the gate rather than for a reader. With a self-test.

The gate remains a review gate and not a proof: it cannot say which collection was reserved for how
many pushes, and the audit is right that a text scan never will. What it can do is refuse an
unmarked growth and make every exemption name itself, and the four false markers above are the
argument for keeping the second half honest.

## Reopened: aarch64 does not finish its suite, and the run-queue booking is withdrawn

Found by running the full sweep this round was supposed to close with. Two things, and they are not
the same thing - which took four aarch64 runs to establish, because the first three looked like one.

### The booking that was added last round is withdrawn

`reserve_run_slot` booked a run-queue slot on EVERY core when a thread was created, to make the
scheduler's `push_back` infallible. Reserving takes each core's scheduler lock and called
`try_reserve` under it - which asks the kernel heap for memory while a core is locked out of its own
scheduler. `heap::grow` maps pages, mapping issues a TLB shootdown, and a shootdown WAITS for every
other core to acknowledge; a core spinning for the lock this one holds never will.

Building the larger queue outside the lock and swapping it in under it removes that particular
hazard, and the suite still stopped. The mechanism takes N spinlocks on a path reachable from a
syscall, which is a scheduling hazard whatever the allocation does.

- [x] **The booking is removed** and the reasoning is written where the next person will look for it -
  at the run queues in `sched/mod.rs`, including what was tried and what it cost.

- [x] **The enqueue sites grow the queue OUTSIDE the lock.** That hazard is real independently of
  anything above: `cpu_sched(cpu).inner.lock().run_queue.push_back(..)` holds the lock across a push
  that may reallocate, which is the same allocation-under-a-lock-a-shootdown-waits-on. `enqueue_on`
  grows first where blocking is allowed and holds the lock only for a move. It does NOT make the push
  unconditionally allocation-free - a racing enqueue can take the room back, and the final push stays
  unconditional because a runnable thread has to go somewhere. Rare where it used to be routine.

- [x] **An intrusive run queue, which is the answer the audit named.** The link lives in the `Thread`
  and enqueue moves pointers, so there is nothing to allocate and nothing to book. That closes K06
  for the scheduler properly, and it is a rewrite of this file's data structure rather than a patch.
  `RunQueue { head, tail, len }` over `Thread::run_link`, with `reserve_run_slot`, `release_run_slot`
  and `LIVE_THREADS` deleted along with the test that proved the booking balanced - there is no
  booking left to balance. It is also what fixed the aarch64 suite below: `--tags object` went from a
  300 s timeout to 38 tests in 15 s, and the full suite now reaches its fortieth test in the time the
  old one reached its third.

### And aarch64 does not finish its suite - which is NOT caused by any of the above

Measured, because the first three attempts each moved the failure and looked like progress:

    HEAD, no local changes:            hangs at `event_syscall_latches_and_polls` (900 s timeout)

The first line is the one that matters: **the committed tree fails on its own.** The full aarch64

## Found: the guard page's fault cannot be reported, so a kernel stack overflow becomes a machine-wide runaway

2026-08-15. Four days of narrowing by component never converged, and the reason is that every
component really was innocent. The defect is in the aarch64 EXCEPTION ENTRY, which is upstream of all
of them - so eliminating the scheduler, the registers, the extable, the allocation, the loader and
process creation moved the investigation no closer, one careful measurement at a time.

What finally answered it was asking the GUEST rather than the source. `QEMU_EXTRA="-s"` opens the
gdbstub in the ordinary test run, the run is left alone until the guest goes quiet, and gdb attaches
to a machine that is still wedged. Three numbers ended it:

    all 8 cores      PC = __exception_vectors + 0x200   (Current EL, SPx, Synchronous)
    ESR_EL1          0x96000044   EC 0x25, a WRITE, translation fault at level 0
    FAR_EL1          equal to SP, to the byte
    ELR_EL1          __exception_vectors + 0x204        the `stp x0, x1, [sp, #0]`

So the faulting instruction is the exception entry's OWN first store, and the address it faults on is
its own stack pointer.

**The mechanism, and it is measured rather than argued.** `VEC` opens with `sub sp, sp, #816` and
`stp x0, x1, [sp, #0]` - the frame is 816 bytes because every trap saves all 32 SIMD registers as
well as the GPRs. Once SP does not point at mapped memory, that store faults, the CPU re-enters the
same vector, subtracts another 816, stores again and faults again. Nothing bounds it, and SP walks
down through the address space at 816 bytes a turn.

**What made SP bad in the first place is NOT yet known, and the first answer here was wrong.** The
obvious candidate was a kernel stack overflow past the guard page - the stack was 16 KiB and had
never been measured against anything. It has been measured now, and it refutes that:
`the_deepest_kernel_path_leaves_headroom_on_its_stack` reports the real `SYS_PROCESS_LOAD` path
using **9680 bytes**, which fits inside the ORIGINAL 16 KiB with room to spare. So plain call depth
never overflowed anything, and the stack being raised to 64 KiB is not the fix it was written up as.
It stays, because a measured 9680-byte path with an 816-byte frame per nested trap has no business
living in 16 KiB, and because the test now pins the number instead of leaving it a guess - but the
trigger is still open, and it is the item at the end of this section.

**That is every remaining symptom in this milestone, and they stop being four mysteries:**

- *The silence.* The loop never reaches a print. A hang that produces no diagnostic is not a
  diagnostic failing - it is a fault taken before any code that could report it runs.
- *The memory corruption.* SP walks DOWN through the kernel window at 816 bytes a turn, and wherever
  it lands on a mapped page the store SUCCEEDS - a register pair written into whatever is there.
  Measured falling billions of bytes between two attaches. `qemu-system-aarch64: wrong value for
  queue_enable ffff0000` is one of those stores landing in virtio MMIO, and `ffff0000` is the top
  half of a kernel address, which is exactly what `stp x0, x1` writes. The frame-pool and HHDM-extent
  theories recorded above were reasonable and are not needed.
- *The wedge point moving.* MARK-3 in one run, MARK-6 in another, MARK-7 and past it in a third. The
  overflow depends on where an interrupt lands in the deep call chain, so the last marker printed is
  timing, not location. Every attempt to narrow by "where did it stop" was reading noise.
- *The SMP dependence.* Eight cores mean IPIs and timer interrupts landing inside the deepest part of
  the call chain, each costing another 816 bytes, and one core's runaway then destroys the other
  seven - which is why all eight were found in the same loop rather than one.

And it explains why adding a `serial_println!` moved the failure: another call frame, in the path
that was already out of stack.

- [x] **Measure what the deepest path actually costs, and stop guessing at `KERNEL_STACK_SIZE`.**
  It was 16 KiB and had never been checked against anything.
  `kernel.object.thread.the_deepest_kernel_path_leaves_headroom_on_its_stack` measures it: the stack
  is zeroed at allocation, so the lowest byte anything ever wrote is the high-water mark, read from
  outside the thread by the spawner that still holds its `Arc`. It drives the real
  `SYS_PROCESS_LOAD` path, prints the figure, and fails if less than a quarter is spare - an
  interrupt at the deepest point costs another 816 bytes before the handler runs. Asserted in one
  direction only: a ceiling that is too generous costs memory per thread, differs by architecture,
  and an assertion that fires when the kernel gets CHEAPER is one that gets deleted.

  **The answer is 9680 of 65536 bytes, 14%** - and it is the measurement that killed the hypothesis
  it was written to confirm. 9680 fits inside the old 16 KiB, so the deepest call chain was never
  overflowing. The ceiling stays at 64 KiB because 6 KiB of headroom over an 816-byte-per-trap frame
  is too thin to reason about, not because it fixed anything.

  Worth recording for the shape of it: this test passes on eight cores, run alone, doing very nearly
  what the two wedging tests do. What it does not have is the ~10 tests before it, which is the same
  thing this milestone noticed a week ago - the failure needs the suite's accumulated state.

- [x] **Serialize the console, because two cores printing at once is the OTHER cause of the "corrupted
  output".** `core::write!` calls `write_str` once per formatting fragment, so a single
  `serial_println!` reaches the port as several writes with nothing between them. x86_64 locks its TX
  ring per slice; aarch64's PL011 and riscv64's NS16550 are polled and take NO LOCK AT ALL, so they
  mix at byte granularity. That is `caught_before=1837` where the counter was in single digits, and
  `child=<mixed>100000001` - two cores' digits in one line, with nothing wrong with either value.
  Four measured cycles of this milestone treated those as evidence of memory corruption.

  The lock is in `_print`, where the fragments are visible, and `serial_println!` now makes ONE call
  rather than one for the line and one for the newline. Bounded acquisition rather than `lock()`: a
  core that halts, panics or faults while holding it would silence every other core forever, which is
  the exact failure this milestone has spent the most on. Past the bound the line goes out
  unserialized, which is the behaviour that existed before.

- [x] **Make an unusable stack pointer SURVIVABLE, which is the durable half.** DONE 2026-08-15, and
  it works: the machine no longer eats itself.

  The aarch64 exception entry now decides whether `SP` can hold a frame BEFORE it writes one. Getting
  a register to ask the question with is the whole difficulty, since anything spilled to the stack
  depends on the stack: `TPIDRRO_EL0` frees `x0` with no memory access at all, `x0` then reaches the
  per-CPU block through `TPIDR_EL1`, and that frees two more into per-CPU memory that is statically
  allocated and mapped for the life of the kernel. The test itself is a range check -
  `sp - floor <= span`, unsigned - so one subtract and one compare catch a pointer that has run off
  the bottom AND one that has been corrupted upward. Seventeen instructions, inside the 128-byte
  slot, and every way the check itself can fail falls back to exactly the old behaviour: a zero
  `TPIDR_EL1` and a zero span both branch straight to the reserve.

  The offsets are `const` operands fed to the assembler from `offset_of!`, not numbers written out
  twice, with a static assertion that the floor and the span stay adjacent for the `ldp`. That is the
  sixth audit's own recommendation about trap-frame offsets, applied to the thing it was made about.

  WHAT IT BOUNDS MATTERS AS MUCH AS THE CHECK. The scheduler publishes the incoming thread's stack on
  every switch, and both idle paths restore what the core recorded for its own idle stack rather than
  clearing it - a first version cleared to zero, which left the stacks with NO guard page (the
  secondaries' `SEC_STACKS` is a plain static array, and the BSP's boot stack runs into `.bss`) also
  being the only stacks nothing checked. The linker script already records what that costs: the boot
  stack went from 64 KiB to 256 KiB after the in-kernel LiberFS format walked off it into `.bss`, and
  the symptom was "memory corruption rather than a fault".

  Measured: seven of eight cores reach the detector and HALT in it, where the same build without it
  had all eight looping in the vector writing register pairs down through the kernel window. The
  corruption is contained.

- [x] **Make the bad-stack report reach the wire.** DONE 2026-08-15, and it took two more corrections
  of the reporter, both worth recording because both are the same mistake as the bug it reports on.

  It printed nothing while seven cores sat in its halt loop, and `core::fmt` was why: unoptimised it
  is many nested frames deep for one formatted line, so the formatting ran off the 4 KiB reporting
  stack into the neighbouring core's slice - silently, because these are plain arrays - and the
  re-entry counted itself as another report. Raising the stack to 16 KiB changed nothing; removing
  `core::fmt` did. The reporter is fixed strings and a hand-written hex digit now, with no call depth
  and no allocation, and the reporting stacks stay at 16 KiB because the first size had never been
  measured either.

- [x] **AND THE FIRST REAL REPORT REFUTED THE HYPOTHESIS THE REPORTER WAS WRITTEN AROUND.** Three
  cores, each with its own bounds, all of them a secondary core's idle stack:

      sp=0xffff0000403e95b9  bounds 0xffff0000404539d9..=0xffff0000404636a9
      sp=0xffff000040437f49  bounds 0xffff0000404839d9..=0xffff0000404936a9
      sp=0xffff000040417869  bounds 0xffff0000404639d9..=0xffff0000404736a9
      esr=0x8a000000 (EC 0x22, a PC ALIGNMENT FAULT)  far=elr=0xff0000403a2115ff

  Four things in that, and none of them is a stack overflow:

  - **The three cores share one ELR to the bit.** Three independent overflows do not land on one
    address; three cores taking the same corrupted control-flow target do.
  - **It is a PC alignment fault.** The core jumped to an address that is not 4-byte aligned, so this
    is a bad branch target rather than a bad stack.
  - **`0xff0000403a2115ff` is a 64-bit value shifted one BYTE left** with `0xff` shifted in - and
    `0xffff0000403a2115` lands in `.rodata`. Something is being read, or written, one byte off.
  - **The stack pointers are 178 KB, 311 KB and 500 KB below their floors, and none of them is
    16-byte aligned.** A stack pointer that got where it is by making calls moves in 16-byte steps
    and stays inside its own allocation. These were WRITTEN.

  So the reporter's own line - "sp is BELOW it, so this is a stack overflow" - was an over-claim of
  exactly the kind this milestone keeps catching, made by the diagnostic built to stop them. It
  prints the distance and the alignment now and lets the reader conclude, because the alignment is
  the evidence and the direction is not.

- [x] **Bind the secondary stack size to ONE number, which was one edit from its own silent
  corruption.** `SEC_STACK_SIZE` is a Rust constant and `aarch64_secondary_start` computed the
  per-core stack top from `mov x6, #16384` written out in the assembly beside it. Raising the
  constant alone would have given all seven secondaries stack pointers inside core 0's slice,
  overlapping - and the first symptom would have been another round of memory corruption with no
  obvious cause. It is a `const` operand now, verified in the disassembly as `mov x6, #0x10000`.
  This is the sixth audit's recommendation about hand-shared assembly offsets, found in a second
  place while acting on it in the first.

- [x] **Raise and MEASURE the secondary idle stacks.** 16 KiB, no guard page, and running the
  scheduler plus the reaping of exited threads and processes - `Arc::drop_slow` through the object
  graph and an address-space unmap, in a debug build. They are 64 KiB now, and
  `the_deepest_kernel_path_leaves_headroom_on_its_stack` reports each core's high-water from the
  zeroed `.bss` the same way the thread stacks are measured, failing if any core is within a quarter
  of its ceiling. Reported per core rather than thresholded per test, because how deep the idle path
  goes depends on how much reaping has happened by the time the suite reaches it, and a threshold
  there would be a threshold on test order.

- [x] **FOUND, 2026-08-15. `SEC_STACKS` had an alignment of ONE, so every secondary core ran its
  whole life with `SP` congruent to 9 modulo 16.**

  The declaration was `static mut SEC_STACKS: [[u8; SEC_STACK_SIZE]; MAX_CPUS]`. The element type is
  `u8`, so the array's alignment is one byte, and the linker placed it at `0xffff0000404436a9`. The
  bring-up stub computes each core's stack top as `SEC_STACKS + cpu_id * SEC_STACK_SIZE +
  SEC_STACK_SIZE`, so every secondary started life on a stack pointer ending in 9 and never
  recovered. `#[repr(C, align(16))]` on a wrapper struct moved it to `0xffff0000404436b0` and the
  aarch64 suite went past the test that has been wedging it for four days:
  `a_process_load_whose_image_goes_away_is_an_error_rather_than_a_dead_kernel` is `[ok]`.

  AAPCS64 requires `SP` to be 16-byte aligned at all times, and almost nothing notices when it is
  not - which is why this survived every test this kernel has. Frame-relative accesses are
  self-consistent, so the arithmetic works and the values are right. What does not survive is an
  instruction that requires natural alignment whatever `SCTLR_EL1.A` says, and `ldxr`/`stxr` - the
  exclusive pair under every atomic - is one. An atomic on a stack slot faults, and the fault arrives
  with a stack pointer no handler can save a frame on. Everything else followed from there: the
  runaway, the silence, the corruption of `.data` and `.rodata` below the stacks, the moving wedge
  point, the SMP dependence, and x86_64 being untouched.

  **THE EVIDENCE WAS IN THE FIRST MEASUREMENT AND WENT UNREAD FOR FOUR DAYS.** The very first gdb
  capture of a wedged guest recorded eight stack pointers and the note "low nibble always 9" - and
  then chased what the misalignment had scribbled instead of the misalignment. Every later report
  said it again: `...95b9`, `...9ac9`, `...5349`, `...0109`, `...f9`, `...c9`. Six hypotheses were
  built and refuted, each one a theory about the debris. The one number that was constant across all
  of them was the one nobody looked at twice.

  Worth stating plainly, because this milestone is the record: the byte-shifted pointers were real
  after all. They are register pairs saved on a stack misaligned by one, read back as words. The
  retraction of that observation was itself wrong; what was wrong the first time was reading them as
  the CAUSE rather than as the mechanism's fingerprint.

- [x] **And the size raises were not the fix either.** `SEC_STACK_SIZE` went to 64 KiB on the theory
  that the idle path had outgrown 16 KiB. With the alignment fixed, the measurement says the deepest
  any core's idle context reaches is 4203 bytes and the other seven sit at 2568 - 26% and 16% of the
  original 16 KiB. It is back at 16 KiB, held by
  `the_deepest_kernel_path_leaves_headroom_on_its_stack`, which now reports every core.
  `KERNEL_STACK_SIZE` stays at 64 KiB: 9680 bytes of measured depth in 16 KiB leaves under a quarter
  spare against an 816-byte frame per nested trap, which is the one size raise the numbers support.

- [x] **Give the idle and bring-up stacks guard pages.** `SEC_STACKS` is a static array and the boot
  stack runs into `.bss`, so an overflow of either is silent by construction - which is why the size
  had to be raised twice by symptom rather than once by fault. The exception vectors now REPORT an
  overflow at the next trap, which is a catch and not a stop. Mapping these with an unmapped page
  below turns the overflow itself into a fault at the instruction that causes it, which is what the
  per-thread stacks already have.

  DONE for the secondaries, which are the ones that mattered. A core now stands on its `SEC_STACKS`
  slice only from the boot stub to `KernelStack::allocate`, then `run_on_stack` moves it onto a
  guarded kernel range - the same allocation threads have had since they existed, with the base page
  left unmapped - and it never goes back. An overflow there is a fault at the instruction that causes
  it rather than a silent write into the previous core's memory.

  MEASURED, because that is what this milestone does now: the bring-up slices carry 1979-2587 bytes
  of 16384 (12-15%), which is the prologue and nothing more, so cores really do leave them early. The
  test that reported idle depth reports bring-up depth instead and says why it is kept - the slices
  are still an unguarded static array, and a number that climbs there is a core doing real work on
  memory with no guard below it.

  A core that cannot get a guarded stack keeps its slice and says so rather than being refused: the
  vector check still bounds it, and refusing a core over one allocation is worse than running it with
  the protection that already existed.

  The BSP keeps its linker-placed boot stack, and the reason is worth stating: the boot map uses 1 GB
  blocks, so an unmapped page below `__boot_stack_bottom` would force a block split during early
  boot. It is 256 KiB, it is bounded by the vector check, and its deepest measured use is a fraction
  of that.

- [x] **`kernel.elf.a_segment_overlapping_one_already_loaded_is_refused` was a symptom, exactly as

- [x] **`reserve_adopt` books capacity against a `len` another transaction can move, so two
  concurrent loads can both be told yes.** `try_reserve(additional)` guarantees room relative to the
  CURRENT length and records nothing; there is no outstanding-reservation state. So core A reserves
  50 against len 100 (capacity 150), core B reserves 50, sees capacity 150 is already enough and
  reserves nothing, A adopts to len 150, and B's `extend` reallocates INFALLIBLY - which is the
  original defect, reached through concurrency instead of through a missing call.

  DONE, and NOT with the lock the audit suggested. A `SpinLock` held across a load is a lock held
  across allocation and mapping with interrupts masked - which is precisely the hazard that got the
  scheduler's pre-booking withdrawn earlier in this milestone: heap growth waits on a TLB shootdown,
  and a core spinning for the lock cannot acknowledge it. Applying that shape here would have traded
  a rare infallible extend for a reproducible deadlock.

  Instead `Process::image_load` is a one-owner gate: `begin_image_load` claims it with one
  compare-exchange, the guard releases on drop including on every rollback, and a second concurrent
  load into the same process is REFUSED. That is an answer `SYS_PROCESS_LOAD` already returns and its
  callers already handle, and two simultaneous loads into one process is not something a correct
  spawner does. Both `load_image_into` and `load_module_into` take it - the module path is the one
  the audit named, since it runs against a process that already owns its main image.

  Verified: x86_64 `kernel,memory,process` 185 of 185, aarch64 `kernel,syscall` 99 of 99.

  `begin_extend` does not close it: it counts operations in flight so teardown can wait for them, and
  explicitly does not serialize them, so two `SYS_PROCESS_LOAD_MODULE` calls are inside the guard at
  once by design. The cheapest correct answer is a process-local lock held across `load_image_into`
  and `load_module_into`; the more honest one is a reservation token that owns the booked capacity
  until it is committed or dropped. Either way the comment claiming "booked before the point of no
  return" is currently a sequential statement wearing a concurrent word.

- [x] **`Domain::new_child` and `Domain::register_process` still push on the strength of "bounded",
  which this milestone has already rejected twice.** `domain/mod.rs:255` and `:289` both carry

  not reach 65 entries; it says nothing about whether the heap can add the first one under pressure -
  the exact argument that got `reserve_dynamic_module_at` fixed and the scheduler rewritten. Both are
  ring-3 reachable (`SYS_DOMAIN_CREATE`, and every process spawn registers), and both functions
  already return `Option`/`bool`, so `try_reserve(1)` before the push needs no signature change. On
  `new_child` the refusal must also not leave the child looking attached.

  DONE. Both `try_reserve(1)` before the push and return their existing refusal - `None` and `false` -
  so neither needed a signature change, and `Thread::build` already declines to construct a thread
  into a process whose registration was refused.

- [x] **Boot reserves at most 16 holes for a hand-off that may declare 64 modules, and drops the rest
  in silence.** `bootmem::loader_reservations` writes into the caller's slice and its `push` closure
  is `if length > 0 && *written < out.len()` - past the end it simply stops, with no error and no
  count returned to say so. Both device-tree boot paths pass `[Hole; 16]`
  (`aarch64/boot.rs:290`, `riscv64/boot.rs:250`), and two of those go to `BootInfo` and the module
  descriptor array, leaving 14 module buffers - while the same function accepts `modules_len` up to
  64. A module past the fourteenth is not carved out of free RAM, so the frame allocator may hand out
  the page an ELF archive is sitting in, which is the flaky `BadImage` this milestone already fixed
  once, reachable again by staging more modules. Size the array from the same 64 the parser bounds
  against, and make an overflow refuse or shrink the pool rather than return a short list that reads
  as complete.

  DONE. `MAX_HOLES` is `2 + MAX_MODULES` and both ports size their arrays from it instead of writing
  `16` out by hand, which is what let the constant and the callers disagree. `push` also no longer
  stops in silence: a reservation it cannot record prints the range it could not protect, because a
  short list that reads as complete is the failure mode here.

- [x] **`DIRECT_MAP_LIMIT` is derived from the firmware memory map, and on the device-tree targets
  the direct map is a FIXED size that has nothing to do with it.** `publish_direct_map_limit`
  (`mem/mod.rs`) takes the top of the retained regions, and its comment describes the loader-built
  HHDM - which is the x86_64 story. aarch64's boot stub maps 1 GB blocks over 0..4 GiB
  (`aarch64/boot.rs:47`) and riscv64's maps 0..8 GiB (`riscv64/boot.rs:55-63`), both fixed in
  assembly before any map is read. On a machine whose device tree reports more RAM than that,
  `within_direct_map` answers true for physical addresses `phys_to_virt` does not translate - and the
  frame allocator can be seeded with banks the kernel cannot reach through the HHDM at all. QEMU's
  512 MB configuration is far below both, so nothing shows today. Either build the direct map from
  the memory map, or clamp both the limit and the allocator's seed to what the boot stub actually
  mapped, and derive the limit from the page tables rather than from firmware.

  DONE, the short way the audit named: the limit is clamped to what the boot stub actually mapped.
  `set_direct_map_extent` records that span - 4 GiB on aarch64, 8 GiB on riscv64, both fixed in the
  boot assembly - and `publish_direct_map_limit` takes the MINIMUM of it and the map's top. The map
  says what memory EXISTS; the stub says what is reachable through `phys_to_virt`, and only the
  second of those bounds a firmware pointer.

  Recorded because the first attempt was wrong in an instructive way: it stored straight into
  `DIRECT_MAP_LIMIT` from the boot path, which runs BEFORE the memory map is retained - so the map's
  later `fetch_max` raised the limit right back to the map's top, and
  `a_firmware_pointer_outside_the_direct_map_is_refused_before_it_is_dereferenced` caught it
  immediately. Keeping the ceiling in its own static and applying it at publication makes the two
  independent of each other's order. That test passing is the check that this works at all.

  Long term the direct map is BUILT from the banks and this goes away; the allocator-side half of the
  same problem - banks seeded past what is mapped - is recorded in P02M0129, and the two should be
  fixed together.
