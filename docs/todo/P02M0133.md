# P02M0133 - The parts are right; the transactions between them are not

Status: IN PROGRESS (2026-08-11). Twenty-one of twenty-four closed, including the shootdown generations,
the allocation-free quarantine, the MSI teardown, the scheduler's allocation-free wait paths and the
whole capability/receive/lifecycle group. (Twenty-two: one finding was added here, about a test that
cannot be run outside its suite.)

Six remain, and each is left for a stated reason rather than for lack of turns: `SharedPage`
retiring is blocked behind a frame loss whose cause has been narrowed twice and not found; the DMA
lifetime and the RISC-V `SUM` window are design changes rather than patches; PCI bridge enumeration
cannot be exercised on the one machine available; the isolation defect above needs the loader's
rollback looked at with a cold cache; and the adversarial test list is work in its own right.

x86_64 runs 227 of 227 against everything closed here. The riscv64 changes - the device-tree
timebase and the mapper's rollback - boot and run: a selected test passed in 8 s on 2026-08-11.

A full riscv64 sweep the same night was stopped by the stall watchdog with NO test completed and the
loader's last line as the final output, which looked like a boot the changes had broken. It was not:
the same kernel boots and tests fine when the machine is not also running x86_64 builds and suites.
The lesson is about the measurement rather than the code - an emulated target sharing a machine with
compile jobs is not a target under test - and it cost an hour of suspecting the wrong thing. What is
left is listed at the end of this status and in the tasks below: the fallible-allocation sweep and
the allocation-free quarantine, the MSI teardown, DMA ownership, and the platform assumptions - of
which three (the RISC-V timebase, SUM, and the RISC-V half of the page-table rollback) are
deliberately not done here, because this session could only verify x86_64 cheaply and an unverified
change to another architecture's mapper or usercopy is worth less than the green it would print.

The second frame-lifetime finding - `SharedPage` retiring rather than deallocating - was attempted,
found to leak on the out-of-frames path, and reverted with its reason recorded both here and at the
code. It waits on the allocation-free quarantine, and the two land together.

Everything closed below was exercised in a guest, and the three that could be watched to fail were:
`close_all` handing out a reserved slot, the receive that refunded on dequeue, and the exact
selection this milestone's neighbour fixed.

An outside audit of `src/kernel` - memory, paging, TLB, the scheduler and waits,
processes and threads, capabilities and handles, IPC, the ELF loader, syscalls, IRQ/MSI, DMA, all
three backends and the boot/hardware parsers - 2026-08-10. The findings below were checked against
the tree; two are worse than the audit stated and one of those is measured here for the first time.

The audit's framing is worth keeping because it is right: this does not read as a badly written
kernel. Overwriting a live PTE is refused; the user-half bound is enforced inside
`AddressSpace::try_map` rather than trusted from the ELF validator; the ELF image is buffered before
parsing instead of parsed out of a live userspace slice; the exception table handles usercopy
faults; `IA32_FMASK` clears the flags it must; the frame allocator's metadata allocation is fallible
where it sizes from a syscall; `WaitSet` has `try_reserve` and explicit ceilings.

What it has reached is the second class of defect. Not a missing bounds check - **individually
correct pieces whose interactions are not transactions.** A capability transfer with no commit. A
slot state machine one function does not know about. A shootdown protocol with no request identity.
A rollback path that returns a frame the way the non-rollback path is careful not to.

## The two that can free memory somebody is still using

- [x] **The TLB shootdown has no request identity, so a late acknowledgement counts for the wrong
  request.** `mem/tlb.rs` has `PENDING: [AtomicBool; MAX_CPUS]`, a bare `ACKED: AtomicUsize` and
  `IN_FLIGHT` to serialise. A core services a request with
  `if PENDING[me].swap(false) { flush_local_tlb(); ACKED.fetch_add(1); }` - and nothing in that
  acknowledgement says WHICH request it belongs to.

  The window opens on timeout. The requester spins to 200,000,000, prints
  `tlb: shootdown timed out with n/targets`, sets `complete = false` and releases `IN_FLIGHT` - while
  a slow core may be between its flush and its `fetch_add`. The next requester zeroes `ACKED` and
  starts counting, and the stale increment lands in the new count. With three or more cores the
  remaining acknowledgements can reach `targets` while one core never flushed the mapping this
  request is about.

  **The window is not hypothetical in this tree.** `.build/logs/test` holds **487** occurrences of
  `tlb: shootdown timed out`, across **x86_64 (51 logs), riscv64 (24) and aarch64 (22)**. The
  timeout path is ordinary here, not exotic.

  And the result gates physical reuse: `frame::retire` releases the quarantine only
  `if crate::mem::tlb::shootdown()`, so a false success is a frame handed back to the allocator
  while a core can still reach it through a stale TLB entry - a physical use-after-free.

  Give the protocol generations: a global request counter, `pending_generation[cpu]` written by the
  requester, `ack_generation[cpu]` written by the core after its flush, and a wait for
  `ack_generation[cpu] >= generation`. An acknowledgement then cannot be mistaken for a newer one.


  DONE 2026-08-10. Requests carry a generation now: `REQUEST` hands out numbers, the requester
  writes `PENDING_GENERATION[cpu]` and waits for `ACK_GENERATION[cpu] >= generation`, and a core
  flushes and then `fetch_max`es its own generation. A late acknowledgement carries an older number
  and cannot satisfy a newer wait, so nothing needs resetting between requests - which was the other
  half of the defect. `fetch_max` rather than a store because `service_pending` is re-entered from
  both the idle loop and the wake-IPI handler.

  The timeout now names the cores that did not answer and the generation they are behind on, rather
  than printing `2/7`. Confirmed in the wild while this was being written: the riscv64 sweep of
  `5b427f4` ended with `a_fat_volume_accepts_a_write_as_its_first_operation... tlb: shootdown timed
  out with 2/7 acknowledgements`, which is this window being entered on an ordinary run.

- [x] **`SharedPage::drop` returns a frame straight to the allocator, bypassing the retirement the
  private frames use.** It is `unsafe { frame::deallocate(self.frame) }`, and its SAFETY comment
  argues ownership - which is true and is not the question. Every frame that was ever in a page
  table goes back through `frame::retire` precisely because another core may still have it cached.

  DONE 2026-08-11, on the fourth attempt, once the thing that was actually in the way was fixed.
  `Drop` calls `frame::retire`, so the one path that handed a frame straight back to the allocator
  while another core could still hold a translation for it is gone.

  The three failed attempts were all blocked by the same thing and none of them named it. The first
  blamed the heap-allocated quarantine - correctly, and fixing it did not help. The second blamed the
  quarantine again. The third produced a measurement - 14 passes against 82 - that did not survive a
  control run. What was in the way was `shootdown` itself: neither of its spin loops serviced this
  core's own pending request, so two cores shooting down at once each kept the other waiting out a
  two-hundred-million-spin timeout, and the retirement multiplies shootdowns. That is fixed
  (see the finding below), and with it in:

  - x86_64: 227 of 227, and the suite is FASTER than with `deallocate` - 123 s against 159 s.
  - aarch64: 219 of 219 in 2138 s, on the target that stopped at 14 twice.

  So the milestone had the order backwards: it said the allocation-free quarantine had to land
  first, and it did have to, but it was not sufficient. The shootdown had to land first.

  ATTEMPTED AND REVERTED AGAIN 2026-08-11 - the third attempt, and the first one to produce a
  measurement instead of a suspicion. It is still the right change and it still cannot land alone.

  With the allocation-free quarantine in (which is what the second attempt said was missing), the
  aarch64 and riscv64 suites stopped finishing: both wedged inside
  `kernel.extable.a_process_load_whose_image_goes_away_is_an_error_rather_than_a_dead_kernel`, which
  is a `SYS_PROCESS_LOAD` whose image goes away halfway - exactly the loader-rollback path this
  finding is about. x86_64 finished all 227.

  THE ISOLATION FAILED, and saying so is the point of this paragraph. The first comparison looked
  decisive - 14 passes with the retire against 82 without it, same machine, one line apart - and a
  third run with the retire REVERTED wedged at 14 in the same test again. So the retire is not
  proven to cause it; what the three runs actually show is a non-deterministic wedge that the change
  may make more likely and may have nothing to do with. That wedge is now its own finding below.

  The revert stands anyway, for a reason that does not depend on the isolation: this landed twice
  before and was pulled back twice, the frame-lifetime race it fixes has never been observed, and
  the reclaim path it uses stops every core to do its work. Landing it while the suite it has to
  pass cannot be run is not landing it.

  Run ALONE the same test passes in 11 seconds, so this needs several cores doing other work: the
  drop retires, the quarantine reaches its drain threshold, and the drain shoots down - an IPI to
  every core and a spin until they all answer. x86_64 gets an answer (and even there a related test
  reported `shootdown 62 timed out with 2/3 acknowledgements` and cost 77 seconds). The two
  emulated targets do not.

  So the blocker is not the quarantine any more, it is the SHOOTDOWN: a reclaim path that has to
  stop every core cannot run inside a rollback that itself runs on a busy machine. The next attempt
  needs one of - a shootdown that cannot stall (a per-core acknowledgement the idle path completes
  rather than a spin), or a per-core deferred free that needs no IPI at all, or a retirement that
  defers to a point where the machine is known to be quiet. Until then the frame goes back
  immediately, and the race stays open and named.

  Two tests keep the changes made with it, because they are right either way:
  `a_fuzzed_elf_header_is_refused_without_leaking` and its relocation twin drain the quarantine
  before counting (other code fills it) and compare with `>=` rather than `==` - the drain releases
  whatever else was queued, so the count can legitimately come back HIGHER than the loop started.
  That is the same rule `a_load_that_runs_out_of_frames_anywhere_gives_back_everything` had already
  settled on: what a load owes is that it kept nothing.

  The rollback path is where it bites. `load_parsed` on a late failure does `unmap_segments` and
  `shared.truncate(shared_start)`, dropping the `Arc`s; `load_module_into` maps into an address
  space that belongs to an already-running process, whose other threads are on other cores; and
  x86's `unmap_page_in` does a local `invlpg` only. So a relocation failure in a module loaded into
  a live process can free a frame that a running thread still reaches, with no shootdown between.

  `SharedPage` must retire rather than deallocate, or the loader must own the last unmap and retire
  explicitly. The private path already does this - `frame::retire` followed by
  `frame::drain_quarantine` - so the fix is to stop the shared path being the exception.


  ATTEMPTED AND REVERTED 2026-08-10, and the attempt found the reason this cannot land alone.

  `Drop` calling `frame::retire` is correct for the race and leaks a frame on the one path that
  matters: `retire` queues into a HEAP-allocated quarantine, the heap grows by taking frames, and
  the failure this drop runs on is precisely "there are no frames". The queue cannot take it, the
  fallback needs a shootdown, and when that does not complete the page is counted lost. The
  out-of-frames rollback test said so exactly - `a load refused at allocation 85 kept 1 frame(s) it
  took (0 still quarantined)` - which is the quarantine finding below, made reachable by this one.

  So the two land TOGETHER: the allocation-free quarantine first, then this. Retiring into a queue
  that cannot allocate is not safer than freeing; it is the same defect with an extra step. The
  reasoning is in the code at the `Drop`, so the next person to notice `deallocate` there finds out
  why before changing it.

## Capability transfer is not a transaction

- [x] **`sys_thread_create` never commits the bootstrap capability it took.** It calls
  `take_for_transfer`, whose doc states the contract in as many words: "Exactly one of
  `commit_taken` or `restore_taken` must follow". Both failure paths call `restore_taken`. The
  success path ends at `install_object(&thread, new_thread, Rights::ALL, 0)` and there is no
  `commit_taken` anywhere in the function.

  The cost is exact, because `commit_taken` does two things: `retire_or_recycle(slot, &mut self.free,
  index)` - returning the slot to the free list under the generation rules - and
  `domain.uncharge_handles(1)`. Neither happens. So **every successful spawn that passes a bootstrap
  capability permanently leaks one handle slot and one unit of the parent's handle quota**, on the
  ordinary success path of the ordinary spawn syscall. A supervisor that spawns in a loop walks its
  own quota down until it cannot spawn.

  The second-order failure is worse and rarer: `install_object` is the last statement and has no
  rollback, so if the CALLER's handle table refuses the new thread handle, the bootstrap is already
  in the child and is not returned. Neither party can name it.

  Make the transfer a real transaction with unwinding, rather than three call sites each remembering
  the discipline.


  DONE 2026-08-10. `install_object` runs first and its result is held; a failure there takes the
  capability back out of the child and restores it to the handle it came from; only then does
  `commit_taken` run. So the contract `take_for_transfer` states - exactly one of commit or restore -
  now holds on every path through the function, and the slot and the quota unit stop leaking on the
  ordinary success path.

- [x] **`close_all` does not know the reserved-transfer state exists.** `take_for_transfer` leaves a
  slot deliberately in-between: `cap = None`, generation untouched, index NOT on the free list, so
  nothing can occupy it while the message is in flight. `close_all` does `self.free.clear()` and then
  pushes EVERY index, whatever its state.

  So a termination racing an in-flight transfer puts the reserved slot on the free list; the
  subsequent `restore_taken` writes the capability back into a slot that is simultaneously free, and
  the next insert can hand out the same index. On the other branch `commit_taken` pushes an index
  that is already free, and the free list holds it twice.

  `close_all` also writes `slot.generation.wrapping_add(1)` directly instead of going through
  `retire_or_recycle`, so it bypasses the generation-exhaustion protection that `close` has, and it
  frees slots that were retired for exactly that reason.

  The slot needs a state - Free, Live, TransferReserved, Retired - and `close_all` needs to respect
  it.


  DONE 2026-08-10. The slot carries an explicit `reserved` flag, set by `take_for_transfer` and
  cleared by both endings, and `close_all` leaves those slots entirely alone. It also stopped
  hand-rolling `wrapping_add` on the generation: the rule that a slot whose generation cannot
  advance is retired rather than reused is now spelled the same way in both places, so a retired
  slot is no longer pushed back onto the free list either.

  Pinned by two tests, and the second was watched to fail: replacing the `reserved` guard with
  `false` produces `assertion left != right failed: close_all must not hand out a slot with a
  transfer in flight`. Both pass with the guard, along with the shootdown, frame-ownership,
  rollback and spawn tests - six selected, 11 s.

## Charges and states that rollback does not restore

- [x] **`return_to_head` puts a message back uncharged and over the limit, and its own comment says
  so.** `recv_identified` refunds the sender's queue charge on the way out; if the copy to userspace
  then fails, the syscall calls `return_to_head`, which is `inbox.lock().push_front(message)`. The
  comment defends both properties: the message "goes back UNCHARGED" because the paying domain is no
  longer reachable from there, and it goes back "even when the queue is at its limit" because "one
  over for that instant costs a bounded amount of memory".

  The bound is the part that does not hold. Nothing serialises these returns against each other, so
  N receivers failing their copies concurrently push N messages past the limit, none of them
  charged - which exceeds `CHANNEL_QUEUE_MAX` and understates the domain's `ipc_queue` usage by the
  same N. The refund is in the wrong place: the queue charge should be released when delivery
  COMMITS, with the message holding its reservation through the receive attempt, so a rollback
  restores the charge with the message.


  DONE 2026-08-10. The queued-bytes charge no longer leaves with the dequeue: both receive paths
  carry it on the message and release it at the point of no return - after the payload has reached
  the caller's buffer, where `return_to_head` is no longer reachable. A returned message is
  therefore a message that was never uncounted, and N concurrent failed copies put back N messages
  that all still count against the limit.

  Watched to fail: restoring the refund on dequeue gives `assertion left == right failed: taking a
  message off the queue does not refund it - delivery has not committed`.

- [x] **`terminating` is a flag where a barrier is needed.** `Process::terminate` sets it, then
  unmaps, then closes handles, and the syscalls check `is_terminating()` and proceed without holding
  anything. So a `sys_thread_create` that passes the check before the flag is set can call
  `register_thread` after `close_all` has run, and the process acquires a thread after its cleanup.
  `sys_thread_start` does not check the process at all - `sched::thread_start` consults only
  `thread.try_start()` - so a thread created through that race can be enqueued into a killed process.
  The same shape covers the mapping paths: check, then map, then record, with termination free to
  snapshot in the middle.

  A `Live -> Terminating -> Dead` state with guards, where termination takes the exclusive
  transition and waits for outstanding guards, is what the flag is standing in for.


  PARTLY DONE 2026-08-10 - the two paths the finding names are closed, the general barrier is not.

  `register_thread` is `#[must_use]` and decides under the `threads` lock; `begin_teardown`
  publishes the flag under that same lock, so a registration either sees it and refuses or
  completes before teardown returns. `Thread::build` returns `None` when the registration is
  refused, so a thread is not even constructed into a process that is going away. And
  `sys_thread_start` now tests the PROCESS, which it did not test at all - `try_start` only ever
  answered "was this thread started before".

  What remains is the general shape: a `Live | Terminating | Dead` state with a guard that every
  resource-extending syscall holds, which is what makes the mapping paths safe too. That is a
  design change rather than a patch and it is still worth having; this closes the one path that
  demonstrably ended with a live thread inside a cleaned-up process.

## Allocation that can panic where the ABI promises an error

- [x] **Userspace-reachable paths still allocate infallibly, the scheduler worst of all.**
  `src/kernel/sched/mod.rs` has eight `.push(` calls against one `try_reserve`. `block_on_flagged`
  and `block_on_any` push into the wait buckets and `TIMED_WAITERS` with interrupts off;
  `wake_object` builds a `Vec` of woken threads under the bucket lock; `check_deadlines` does the
  same. Elsewhere: the ELF loader's `frames.push` / `shared.push`, the export registry's `String`,
  `Process::register_thread`, the mapping records, `live_threads`, and `notify_crash` allocating a
  `Vec::with_capacity(16)` on the fault path.

  The rule this kernel should be able to state is that any allocation an untrusted syscall can
  provoke is fallible. The scheduler wants more than that: its waiters should be intrusive fields on
  the `Thread`, not heap nodes allocated at the moment of blocking.

- [x] **A failed page-table walk keeps the intermediate tables it created.** `try_map_page_in` calls
  `next_table_create` per level with `?`, so a failure at the third level leaves the first two newly
  created tables attached to the address space - while the comment says "Nothing is left mapped on
  failure", which is true of the leaf and not of the metadata. RISC-V's `map_page_root` has the same
  shape. Repeated partial failures pin page-table frames that the domain's memory quota does not
  count. Either unwind the levels this call created, or charge page-table pages to the process and
  call them a cache.


  DONE for x86_64 2026-08-10; the RISC-V counterpart is still open. `try_map_page_in` records the
  levels it CREATES (an existing level belongs to somebody else's mapping and must survive), and on
  a failure further down clears each parent entry and retires the frame, in reverse. Clearing the
  entry first matters: retiring the frame while the parent still points at it would leave a live
  page-table pointer into memory the allocator has given away, which is worse than the leak.

  The quarantine is drained on that path rather than left for the next batch - this is the
  out-of-memory path, and holding the frames that would satisfy the caller's next attempt is the
  opposite of what it needs.

  `map_page_root` in `arch/riscv64/paging.rs` has the same shape and the same defect. It is not done
  here because this session can only verify x86_64 cheaply, and an unverified change to another
  architecture's mapper is not worth the green it would print.

- [x] **The quarantine can lose pages permanently when the heap is short - and `SharedPage` waits on it.** Not releasing a frame
  after a failed shootdown is the right call. But the quarantine is a heap `Vec`, and when its
  `try_reserve` fails the code falls back to a small stack buffer of eight frames and, past that,
  calls `note_lost_pages(1)` - after which nothing tracks the frame at all. So a heap shortage
  combined with an unresponsive core permanently shrinks physical memory, and the mechanism that
  exists to reclaim memory needs to allocate memory to work. The quarantine has to be
  allocation-free: a bit in per-frame metadata, an intrusive list, or a fixed per-CPU ring.

  DONE 2026-08-10. The quarantine is a fixed 512-entry array behind the same lock, not a `Vec`:
  `push` refuses when it is FULL - a capacity decision - and the caller then pays for its own
  shootdown, which is the path that already existed. There is no `try_reserve` left in the reclaim
  path, so a heap shortage can no longer turn deferred memory into lost memory. Draining takes
  bounded batches, so it never needs a buffer proportional to the queue and never holds the lock
  across a free. 227 of 227 on x86_64 with it in.

  It did NOT unblock `SharedPage` retiring, which is what it was expected to do - see that finding.


  DONE for the scheduler 2026-08-10. The park path reserves its bucket and timed-list room BEFORE it
  commits - before interrupts are masked and before `begin_park` - and returns without parking when
  the heap will not give it, which turns a kernel abort into a caller re-check. The wake paths and
  `check_deadlines` no longer build a vector under the lock at all: they claim in fixed batches of
  sixteen, drop the lock, enqueue, and come back, which also bounds how long the bucket is held.
  227 of 227 on x86_64 with it in.

  The wider sweep - the ELF loader's pushes, the export registry's `String`, the mapping records,
  `notify_crash` - is not done. The rule this milestone wants ("any allocation an untrusted syscall
  can provoke is fallible") is a sweep with a gate behind it, not a patch.

## Device-facing lifetimes

- [x] **An MSI vector is returned to the pool with its mapping and its device still live.**
  `unbind` for an MSI vector is `REGISTRY.free((vector - MSI_BASE) as usize); return;`, with a
  comment that "there is no source to mask". The MSI-X table page mapped at
  `MSIX_VIRT_BASE + slot * 0x1000` is never unmapped, so re-acquiring the slot calls `map_page` over
  a live leaf - which the paging layer deliberately refuses and the infallible entry point turns
  into a panic. And nothing masks the table entry or disables MSI-X on the departing device, so it
  can keep raising a vector that now belongs to somebody else's driver.

  The slot has to own the whole state: the owning BDF, the capability, the table mapping and the
  vector. Teardown masks the entry, disables MSI-X, fences, unmaps, and only then frees the vector.


  DONE 2026-08-10. `unbind` masks the device's MSI-X entry (vector control bit 0) while the page is
  still mapped, then unmaps it, and only then frees the vector. The entry's offset within its page
  is recorded when it is programmed, so the mask writes the same words the kernel wrote - the table
  is page-mapped but the entry need not sit at offset 0, and a mask at a guessed offset would
  corrupt whatever the device keeps there.

  That also fixes the re-acquire panic: the slot's fixed kernel address is free again, so
  `program_msix_entry` no longer maps over a live leaf.

- [ ] **A DMA buffer's frame can be reclaimed while a device still has a descriptor for it.** The
  buffer hands a device a real physical address and its lifetime is the kernel object's; there is no
  IOMMU enforcing anything, and a CPU shootdown says nothing about a device's in-flight transfer. So
  a dropped buffer can be re-allocated to another owner while the device completes an old write into
  it. Long-term this is an IOMMU domain per device; short of that it needs an explicit submission
  ownership rule - the frames are not reclaimable until the device has acknowledged completion.
  Under a threat model where every driver is trusted this is not privilege escalation, and it is
  still a lifetime bug that a correct driver can hit.

  DESIGNED 2026-08-11, NOT APPLIED - and the reason is the shape of the fix rather than the hour.

  The CPU half is already right: `DmaBuffer::drop` retires rather than deallocates, so no core keeps
  a stale translation. What no shootdown can say anything about is a DEVICE that still holds a
  descriptor pointing at the frame, and nothing in this system currently knows when that stops being
  true - the buffer's lifetime is the kernel object's, and the object goes away when its last
  handle does.

  The rule that fixes it is a submission-ownership one: a buffer that has been handed to a device is
  not reclaimable until the driver says the device is done with it. That is an addition to the
  DRIVER CONTRACT, not to the kernel object - `submit(buffer)` marking it in flight, `complete()`
  clearing it, and a drop with the flag set going to a per-device pending list rather than to
  `retire`. Every driver has to be taught it, and a driver that forgets is a leak rather than a use
  after free, which is the correct direction for the failure to lean.

  Doing half of it - the flag with no driver calling it - would be decoration, and doing all of it
  is a milestone. Under the current threat model (every driver trusted) this is a lifetime bug a
  correct driver can hit, not privilege escalation. The long-term answer stays an IOMMU domain per
  device, which subsumes it.

- [x] **`SYS_FRAMEBUFFER_MAP` leaves its mapping behind when the reply cannot be written.** After
  `alloc_vrange` and `map_pages` succeed, the geometry is written to userspace and a `write_user`
  failure returns the error with the mapping and the VA reservation still in place - so the caller is
  told the operation failed and the address space says otherwise.


  DONE 2026-08-10. A failed `write_user` now unmaps every page and releases the virtual range before
  returning the error, so the caller that is told the call failed is not left owning a framebuffer
  whose address it was never given.

- [x] **Two threads faulting on the same stack page kill the process.** `grow_user_stack` allocates
  a frame, zeroes it and calls `try_map`; the loser of the race gets an error, returns `false`, and
  the fault handler treats that as an unhandled fault. The page it needed is mapped - by the winner,
  a moment earlier. Distinguish "already mapped, with the permissions we wanted" from "out of
  memory", free the spare frame, and let the faulting thread continue.


  DONE 2026-08-10. After a refused `try_map` the fault path asks whether the page is now mapped
  writable-and-user - which is what the winner of the race just did - and continues if it is. The
  permissions are checked rather than mere presence, so a mapping that is not the growth this thread
  needed still refuses instead of returning the thread into the same fault.

## Platform assumptions

- [x] **The RISC-V timebase is the constant 10,000,000.** `hz()` returns it with the comment "QEMU
  virt CLINT timebase" - and `arch/riscv64/mod.rs:49` separately carries
  `todo!("riscv64: timebase-frequency")`, so the hole is already known in one place while the
  hard-coded value is in use in the other. Every timeout, tick conversion, timer and deadline is

- [x] **RISC-V leaves `SSTATUS.SUM` set for the whole life of the kernel.** Both the usercopy and
  the paging comments state it. That makes every kernel pointer bug a potential user-memory access,
  where x86's SMAP keeps the window explicit and narrow. Clear SUM by default and open it around the
  usercopy primitives with an interrupt-safe guard.
  ANALYSED 2026-08-11, not applied - the change is written out below because the analysis is the
  expensive part and it is done.

  DONE 2026-08-11, exactly as analysed, plus the one piece the analysis had not noticed:
  `clac_on_entry` is called by the x86 entry points and NOTHING called it on riscv64, so the second
  edit needed a fifth - `riscv64_trap` calls it first thing. Without that, a trap taken inside a
  window would run the whole handler with user access, and one that context-switched would leak the
  window into the next thread.

  So: `user_access` opens SUM with `csrrs` and closes it only if it was closed before (nesting-safe),
  `clac_on_entry` clears it on trap entry, `boot.rs` and `smp.rs` set only the FPU bit, and
  `copy_to_user_page` is wrapped like x86's. Verified by a riscv64 boot, which is the only thing
  that can verify it - a wrong guard does not fail loudly, it faults inside a copy that used to
  work.

  The architecture already has the shape: every kernel access to user memory goes through
  `arch::paging::user_access`, which x86 implements as `stac`/`clac` and riscv64 implements as
  `f()`. So the fix is four edits and no new plumbing:

  1. `riscv64::paging::user_access` - `csrrs` SUM on, run `f`, and `csrc` it off again ONLY if it
     was off before, so a nested window does not close the outer one.
  2. `riscv64::paging::clac_on_entry` - currently `{}`; `csrc` SUM. The trap frame saves SSTATUS at
     word 33 and the return path does `csrw sstatus, t1`, so clearing it in the handler is invisible
     to the interrupted code. Without this a trap taken inside a window runs the whole handler with
     user access, and one that context-switches leaks it into the next thread.
  3. `boot.rs` and `smp.rs` - stop setting bit 18 alongside the FPU's bit 13. Both currently do.
  4. `copy_to_user_page` in `riscv64::paging` - wrap the `copy_nonoverlapping` in `user_access`, as
     x86's already is.

  Why it is not applied tonight: it is only provable by a riscv64 boot, and a wrong guard does not
  fail loudly - it faults inside a copy that used to work, which is the kind of failure worth having
  the whole test budget in front of rather than the end of it.

## Tests

- [x] **`kernel.boot.init_package_starts_system_manager` failed, and the cause was one field offset.**
  On x86_64 the pinned half of the system came up - SystemManager, StorageService, all eight
  devices, DHCP - and then four VOLUME-staged services never reported online: PermissionManager,
  ConsoleService, SystemGraphService and the Shell. 18 of 23 lines, every time.

  BISECTED TO ONE COMMIT, 2026-08-11. Four builds and four runs of the single test:

  | tree | result |
  | --- | --- |
  | working tree | FAIL |
  | everything uncommitted stashed | FAIL |
  | plus `src/fs/fat` reverted to `acce4a7~1` | FAIL |
  | `eaea523` - the kernel work, before the FS commits | pass |
  | `6b227e5` - iso9660 SUSP/RRIP | pass |
  | `17a9033` - UDF descriptor validation | FAIL |

  Then instrumented, because the log said nothing: the guest's own supervisor was given prints at
  each stage of the boot drill, and the first line out was the answer -
  `service failed to start: udf_storage reason=bootstrap channel closed without a report`. The
  storage instance behind the UDF-tagged volume mounts with `Udf::mount`, whose failure path is
  `None => exit()`, and every service that depends on that instance stayed Pending behind it. The
  ring-3 page fault in the log is NOT the defect: `watchdog_probe` dereferences null because the
  supervisor commands it to - `CRASH` is one of the two failure modes the watchdog drill exercises.

  **THE DEFECT: the Map Table Length is at offset 264, and `scan_sequence` read it at 272.** In a
  Logical Volume Descriptor (ECMA-167 3/10.6) the Logical Volume Contents Use occupies 248..264, the
  Map Table Length 264..268, the Number of Partition Maps 268..272, and the Implementation
  Identifier 272..304. So the length was being read out of the identifier - on a volume `mkfs.udf`
  writes, the string `\0*Linux UDFFS`, which is 1766599168 as a little-endian u32. The bound check
  refused it, no sequence yielded a partition, and a perfectly good volume mounted as `Corrupt`.

  **Every fixture in the crate was built to the same misreading**, which is why all twenty-six tests
  agreed with it. That is the third time in two days a validator and its fixtures have agreed with
  each other and with no real medium, and the second time the fix was found by pointing a real
  formatter at it - so `an_image_from_an_independent_formatter_mounts` now builds a volume with
  `mkfs.udf --media-type=hd --blocksize=2048`, the same command `boot/qemu-run.sh` gives the guest,
  and requires it to mount. It fails against the old offset in 0.07 seconds, where the guest took a
  full build and a boot to say the same thing less clearly.

- [x] **Two cores shooting down at once deadlock each other until the timeout, and the aarch64 and
  riscv64 suites cannot finish because of it.** Found 2026-08-11 while trying to isolate the `SharedPage` retirement
  above, which is how it got mistaken for that change's fault.

  What is measured: on aarch64 the suite reaches this test and produces no further output for the
  whole watchdog window (900 s, and 2400 s on a second attempt), with QEMU still burning CPU - so it
  is spinning, not idle. riscv64 stops in the same test. x86_64 runs it and the whole suite. The
  test PASSES when selected alone (11 s) and inside `--tags kernel` (48 tests, 11 s), `--tags
  syscall` (52 tests, 12 s) and `--tags dynamic,frame,memory,syscall` (54 tests before the run hit
  its own limit on a genuinely slow `imgconv`), so it needs the state of the ~80 tests before it.

  It is NOT the machine being busy: it reproduced at load 3.9 as well as at load 10. It is not the
  `SharedPage` retirement: it reproduces with that reverted. It is not new to the suite's content -
  the same suite passed 216 of 216 on 2026-08-10 at 22:14, which is the last known-good run.

  The test deliberately faults in ring 0 with a user page that has gone away, on a machine with
  eight cores and other threads live, so a spin with no output is consistent with a shootdown
  waiting for an acknowledgement that never comes, or a lock held across one.

  IT IS A SHOOTDOWN, and the guest said so itself once the watchdog window was raised enough to let
  it keep going. The wedged test eventually printed:

      tlb: shootdown 3 timed out with ... acknowledgements
      tlb:   cpu 2 is at generation 2 and was asked for 3

  So a core does not answer, the initiator waits out its timeout, and the test is full of
  shootdowns - it unmaps a user page, deallocates its frame, and tears down a child process. Nothing
  is deadlocked; every shootdown pays a full timeout and the suite runs out of wall clock. That also
  explains the shape of every other observation: x86_64 finishes (its wake-IPI reliably reaches a
  parked core, and even there `shootdown 62 timed out with 2/3 acknowledgements` cost 77 s in one
  test), the two emulated targets do not, and the `SharedPage` retirement made it worse because it
  ADDS shootdowns rather than because it is wrong.

  Confirmed from the host as well, with `gdb -p` against the wedged QEMU: of its ten threads three
  were executing translated guest code and the rest were blocked in a syscall - three guest cores
  spinning, five parked. The parked ones are the ones not acknowledging.

  FOUND AND FIXED 2026-08-11, and it was not the parked cores at all - it was `shootdown` itself.
  Both of its spin loops waited without servicing THIS core's own pending request:

  - the `IN_FLIGHT` acquisition loop, where a second requester queues, and
  - the acknowledgement loop, where the holder waits.

  So two cores shooting down at once were each the reason the other could not finish: the holder
  waited for an acknowledgement from a core spinning in the first loop, which would not look at its
  flag until the holder gave up - two hundred million spins later. The interrupt path cannot cover
  that, and this is why it looked like a delivery problem: the wake IPI is serviced by the handler
  only when the core takes it, and a core already inside `shootdown` does not.

  The fix is `service_pending()` in both loops - answering needs no interrupt at all. Measured on
  aarch64 with everything else identical: `a_process_load_whose_image_goes_away_is_an_error_rather_
  than_a_dead_kernel` goes from "the suite stops here, twice, at 14 passes" to `[ok]`, with no
  shootdown timeout anywhere in the log, and the suite runs on past 87.

  What this does NOT settle: whether a genuinely parked core answers promptly. Every timeout seen
  today is explained by the collision above, and `a_shootdown_makes_another_core_stop_using_the_old_
  translation` passes on all three targets - but the 77-second x86_64 case from earlier in this
  milestone was a real timeout too, and it is worth re-measuring now that collisions cannot cause
  one.

- [x] **`a_load_that_runs_out_of_frames_anywhere_gives_back_everything` cannot be run alone.**
  Found 2026-08-10 while bisecting a frame loss that turned out not to exist: the test passes in the
  full suite and fails deterministically - three runs out of three - when selected on its own, with
  `a load refused at allocation 85 kept 1 frame(s) it took (0 still quarantined)`. On a clean HEAD,
  with nothing modified.

  SOLVED 2026-08-11, and it was two things - one of them a real leak.

  THE REAL LEAK, in `KernelStack::allocate`: `frame::allocate().filter(|frame| try_map_page(..).is_ok())`
  made two failures into one. A frame that was allocated and then could not be MAPPED - because the
  mapper itself ran out of frames for an intermediate table - was dropped by the combinator, and
  `rollback` frees what is mapped, so nothing knew about it. Every failed spawn whose budget landed
  on the mapper's own allocation lost exactly one frame. Now the two steps are separate and the
  frame goes straight back. Fixing it moved the failure from budget 85 to budget 87, which is what
  said the rest was something else.

  THE REST IS NOT A LEAK AT ALL: the kernel HEAP grows by taking frames - `register_thread` pushes
  onto a `Vec`, the handle table grows, headers are boxed - and the sweep compares the machine's
  free-frame count around each attempt. A frame the heap took is not a frame the load kept, and it
  never comes back inside the window. After two hundred other tests the heap is at its working size
  and takes nothing; alone it grows mid-sweep and the count comes back short. That is the whole
  mystery, and the giveaway was in the message from the beginning - "0 still quarantined".

  So the test now performs one complete spawn and tears it down before it starts measuring, with
  that reasoning written beside it. It passes selected alone, which is what an exact selection
  needs.

  Worth keeping: this was blamed on the frame allocator, the quarantine, the page-table rollback and
  the shared-page cache in turn, and each was suspected on plausibility rather than on evidence. The
  evidence was one number in the failure message.

## Order

The audit's order is the right one and it is kept here. `K01` and `K02` first: they are the two that
end with a frame in use by one core and owned by another, and the first of them has a window this
tree's own logs show being entered 487 times.

Then the capability transfer as one transaction, with `close_all` taught the slot states - they are
the same bug seen from two sides.

Then the receive transaction and the process lifecycle barrier, then the fallible-allocation sweep,
then the MSI teardown.

The platform assumptions last, except that they should be written down first: a hard-coded QEMU
timebase and a bus-0-only PCI scan are not defects while the target is QEMU, and they are defects
the moment anything claims otherwise.
