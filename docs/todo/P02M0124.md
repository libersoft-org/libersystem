# P02M0124 - What the UDF backend claims to read, and what it actually does

a regression this milestone introduced - is closed by separating the two things that were conflated.

`parse_long_ad` parses and `from_icb_long_ad` decides. A `long_ad` is a length, an extent type, a
block and a partition; the previous round put ONE caller's policy in the parser's `None`, and the

The headline is not that features are missing. It is that **the file at the top of the crate says
things the code does not do**, and two of those gaps are ways a crafted image gets a wrong answer
rather than a refusal:

- The doc comment says "a read-only backend for DVD / Blu-ray". A conforming Blu-ray uses UDF 2.50
  with a Metadata Partition Map, and this parser does not read partition maps at all.
- It says "every block address, length, and extent is bounded by the partition's own length before a
  buffer is allocated". The embedded-data branch returns before that bound is applied.
- It says a volume it cannot handle "refuses to mount rather than being misread". Nothing detects a
  metadata partition, so what actually happens is that the File Set address is resolved against the
  wrong partition and whatever is at that physical block is parsed.

For the subset it does implement - one physical partition, everything referring to it - the code is
small, readable and genuinely defensive: tag locations are checked, extents are bounded before they
are read, sparse extents read as zeros rather than stale disk, and type-3 descriptors, extended_ad
and symlinks are refused rather than misparsed. That is worth keeping. What follows is the distance
between that subset and what the header promises.

## The two that are correctness bugs, not missing features

- [x] **An embedded File Entry can panic the parser, or return a truncated file as success.**
  `read_icb` reads `info_len` with a plain `le64(..) as usize` and the embedded branch runs BEFORE
  the `info_len <= partition bytes` check below it:

      let end = (ad_off + info_len).min(block.len());
      return Ok(block[ad_off..end].to_vec());

  With `InformationLength = u64::MAX` the addition overflows - a panic in debug, and in release a
  wrap to `block[176..175]`, which panics too. With a merely large value, say 5000 against an
  `ad_off` of 176, `end` clamps to 2048 and the function returns **1872 bytes as `Ok`** for a file
  the descriptor says is 5000. A panic and a silent truncation from the same three lines.

  The fix is `usize::try_from` and `checked_add`, the partition bound applied BEFORE the embedded
  branch rather than after it, and `end > block.len()` treated as corruption instead of clamped.
  Embedded length should also be checked against `LengthOfAllocationDescriptors`.

  The existing `forged_lengths_do_not_allocate_or_read_foreign_blocks` does not catch this: it
  switches the File Entry from embedded to short_ad before setting the huge length, so the embedded
  path with a forged `InformationLength` is never exercised.

  DONE 2026-08-11. `usize::try_from` on the length, `checked_add` on the offset, the partition
  bound applied BEFORE the embedded branch, and a length past the block or past
  `LengthOfAllocationDescriptors` treated as corruption rather than clamped. Pinned by a test that
  exercises the embedded path with `u64::MAX`, 5000 and `1<<40` - which the existing forged-length
  test could not, because it switches to short_ad before setting the length.

- [x] **An allocation-descriptor chain that stops early returns the rest of the file as zeros, and
  says `Ok`.** The buffer is `vec![0u8; info_len]` and the loop exits on a zero-length extent, on
  running out of descriptor area, or on `l_ad` being too small - and then `Ok(out)` with no check
  that `done == info_len`. A file declaring 100 KiB whose descriptors cover the first 2 KiB comes
  back as 2 KiB of data and 98 KiB of zeros, indistinguishable from a real file.

  A sparse extent is a legitimate source of zeros. A missing descriptor is not, and conflating them
  is exactly the silent corruption this crate's own comments say it exists to avoid.

  Two changes: require `done == info_len` at the end, and stop using `.min(block.len())` on
  `ad_off + l_ad` - a declared descriptor length that runs past the block is a corrupt descriptor,
  not one to quietly shorten.

  DONE 2026-08-11. `done == info_len` is required at the end, and a declared descriptor length past
  the block is `Corrupt` rather than silently shortened. A sparse extent is still a legitimate
  source of zeros; a missing descriptor is not. Watched to fail: removing the completeness check
  brings back 2 KiB of data and 98 KiB of zeros reported as a whole file.

## The integrity check that is not being made

- [x] **Descriptor CRCs are never verified.** `tag_ok` sums the first sixteen bytes and compares
  against byte 4 - that is the TagChecksum, which covers the TAG. `DescriptorCRC` and
  `DescriptorCRCLength`, which cover the descriptor BODY, are not read. So a bit flipped in a
  partition start, a File Set location, an `InformationLength` or an allocation descriptor passes
  every check this parser makes, as long as the first sixteen bytes are intact. On optical media,
  which is where this backend is aimed, that is the protection that matters most.

  Worth doing as one `validate_descriptor(block, expected_tag, expected_location)` that checks the
  identifier, the version, the tag checksum, the CRC, the CRC length and the location together -
  the four call sites currently check different subsets of those.

  Note the consequence for the tests: the fixture builder's `tag()` helper writes an identifier, a
  location and a checksum and no CRC at all, so turning this on invalidates almost every synthetic
  image in `tests.rs`. That is not a reason to defer it; it is a measure of how much the fixtures
  currently agree with the parser rather than with the format.

  DONE 2026-08-11. One `validate_descriptor(block, tag, location)` checks the tag, the location, the
  tag checksum, the CRC length and the body CRC together, and all four call sites go through it.

  The fixtures had to be fixed with it, exactly as the finding predicted: `tag()` wrote an
  identifier, a location and a checksum and no CRC at all, so every synthetic image agreed with the
  parser rather than with the format. It now computes a real CRC-ITU-T over the body, and a test
  that patches a descriptor afterwards refreshes it - the obligation a real formatter has too.

  Watched to fail, with a byte the parser does not otherwise read, so the test isolates the CRC and
  not some other check.

## Addressing: the layer that is missing entirely

- [x] **`long_ad` is read as a bare logical block number and its partition reference is discarded.**
  A UDF logical address is a block number AND a partition reference number, and the Partition Maps
  in the Logical Volume Descriptor say how each reference is translated. This parser takes
  `le32(&block[252..256])` for the File Set, `le32(&block[404..408])` for the root ICB and
  `le32(&fid[24..28])` for every child, and adds `part_start` to all of them.

  That is correct for exactly one shape: a single physical partition with every reference pointing
  into it. It is wrong, silently, for anything else.

  The shape to build is a resolver - a logical address is `(partition_ref, block)`, and one place
  turns it into a physical LBA - so that adding a partition type later is a change in one function
  rather than in every call site.

  DONE 2026-08-11. `Geometry::physical(partition_ref, lb)` is the one place a logical address
  becomes a physical block, and every call site goes through it - the bound travels with it. The
  discard is now safe because the mount refuses anything but the shape it is correct for.

- [x] **Partition Maps are not parsed, so an unsupported volume is not refused - it is misread.**
  The claim in the header is that a UDF 2.50 metadata-partition volume "refuses to mount rather than
  being misread". There is no code that could produce that refusal. What happens is that the File
  Set reference resolves against the physical partition, and on an ordinary image that lands on
  something that is not a File Set Descriptor and the mount fails - by accident. On a crafted image
  it lands on something that looks like one.

  Even before any new partition type is supported, parsing `NumberOfPartitionMaps` and the map
  entries and refusing anything that is not exactly one Type-1 map turns an accident into a
  guarantee - and lets the refusal name what it did not support.

  DONE 2026-08-11. `NumberOfPartitionMaps`, the map table length and the map type are read, and
  anything that is not exactly one Type-1 physical map is refused - as is a File Set whose partition
  reference is not 0. The accident became a guarantee, and the refusal happens at the descriptor
  that says what the volume is rather than at whatever the misresolved address happened to land on.

- [x] **Nothing checks what UDF it is mounting.** The Logical Volume Descriptor carries
  `LogicalBlockSize`, a `DomainIdentifier` (`*OSTA UDF Compliant`) and the UDF revision, and none of
  the three is read. The parser assumes 2048-byte blocks throughout and has no way to say whether it
  is looking at 1.02 or 2.60. At minimum: require the block size to be 2048, require the domain
  identifier, and record the revision so an unsupported one can be named.

  DONE 2026-08-11. `LogicalBlockSize` must be 2048 and the `*OSTA UDF Compliant` domain identifier
  must be present; both are refusals rather than assumptions. The fixture's Logical Volume
  Descriptor had to gain all of it, which is the same measure the CRC finding took.

## Robustness of the volume-descriptor scan

- [x] **Only the anchor at LBA 256 and only the Main VDS are ever read.** UDF puts anchors at 256,
  N-256 and N precisely so a damaged one is survivable, and the anchor carries a Reserve VDS extent
  beside the Main one. The DVD read procedure in the specification says to fall back to the Reserve
  sequence when the Main one cannot be read. This mounts from one anchor and one sequence, and
  returns `None` if either is damaged - on the medium where redundancy is most likely to be needed.

- [x] **The sequence length is floored and then clamped to 1..64.**
  `(vds_len as usize / SECTOR_SIZE).clamp(1, 64)` turns a zero length into one block - so a
  descriptor the anchor does not claim is in the sequence gets parsed - floors away a partial last
  sector, and truncates a longer valid sequence. The specification requires at least sixteen sectors
  for each of Main and Reserve. A bound is right; this particular arithmetic answers a different
  question than the one being asked.

  DONE 2026-08-11. `div_ceil` rather than a floor, a zero length refused instead of turned into one
  block, and reaching the 64-block ceiling is a refusal rather than a quiet stop - so a descriptor
  the anchor does not claim is in the sequence is no longer parsed, and a partial last block is no
  longer dropped.

  PARTLY DONE 2026-08-11. Both sequences an anchor names - Main and RESERVE - are tried in the
  specification's own order, so a damaged Main no longer loses the volume; pinned by a test that
  destroys the Main sequence and mounts from the Reserve.

  The anchors at N-256 and N are still not read, and cannot be: `BlockDevice` does not expose the
  medium's size, so finding them needs an accessor on the shared trait rather than a change here.
  Said in the code at the anchor list rather than left as an unexplained single read.

- [x] **"The last Partition Descriptor wins" is not the prevailing-descriptor rule.** Each
  `TAG_PARTITION` overwrites the previous one, and the same for the Logical Volume Descriptor.
  Volume Descriptor Sequence Numbers, partition numbers and the map-to-descriptor relation are all
  ignored, so a volume that has been updated - which is the normal state of a rewritable disc -
  can be read through a stale descriptor copy.

  DONE 2026-08-11. The Volume Descriptor Sequence Number decides, for the Partition Descriptor and
  the Logical Volume Descriptor alike; a tie still lets the later one win, which is the right rule
  for equal numbers. So a rewritable disc that has been updated - a new descriptor appended rather
  than the old one erased - is no longer read through the stale copy.

## Bounded reads, and a filesystem API that cannot stream

- [x] **A file's whole content is allocated from a number on the medium.** `info_len` is checked
  against the partition's byte size and then `vec![0u8; info_len]` is allocated. A 100 GB partition
  makes an 80 GB `InformationLength` "valid", and the allocation is attempted. `find_entry` reads a
  whole directory the same way, so a path lookup - not even an open - is enough to trigger it.

  The bound should be what the caller asked for, not what the partition could hold. The deeper fix
  is that `read_file() -> Vec<u8>` is the wrong primitive for a filesystem: `stat` plus
  `read_at(offset, buf)` means a 50 GB file on a Blu-ray does not need 50 GB of RAM. That is a
  volume-API change and belongs with whichever milestone owns that surface, but UDF is where it
  bites first.

  PARTLY DONE 2026-08-11: one read may allocate at most 64 MiB, refused by name rather than
  attempted, so an 80 GB `InformationLength` on a 100 GB partition no longer reaches the allocator -
  and a path lookup, which reads a whole directory the same way, cannot trigger it either.

  The real fix is `stat` plus `read_at(offset, buf)` on the volume API, which is a different
  surface's change. The ceiling is what this crate can do about it alone, and it is a limit rather
  than a solution.

- [x] **An extent is bounds-checked only for the part of it the parser is about to use.** The check
  is against `take` - how much of the extent `InformationLength` still needs - not against `len`,
  the extent's declared size. So a descriptor claiming a 1 GiB extent starting at the partition's
  last block passes, as long as only five bytes of it are wanted. Nothing is read out of bounds, so
  this is not an immediate defect, but the descriptor IS structurally invalid and the header comment
  says every extent is bounded by the partition. Check the declared extent first, then take from it.

  DONE 2026-08-11. The DECLARED extent is bounded against the partition before anything is taken
  from it, so a descriptor claiming a gigabyte at the partition's last block is refused whether or
  not only five bytes of it are wanted.

## Compatibility limits, to be named rather than discovered

- [x] **ICB Strategy Type is never read.** A conforming reader supports strategies 4 and 4096. This
  one reads the File Entry directly and never looks at the strategy field, so a 4096 volume is
  parsed as though it were a 4. Reading the field and refusing what is not supported is a few lines
  and turns a wrong answer into a named one.

  DONE 2026-08-11. Strategy 4 is what this reader implements - it reads the File Entry directly -
  and anything else is refused by name. The fixtures had to start writing the field, which is the
  third time in this milestone that turning a check on required the builder to produce media a real
  formatter would.

- [x] **Type-3 allocation descriptors are refused, which is safe and is a real limit.** Type 3 is a
  continuation into an Allocation Extent Descriptor, and refusing it means a sufficiently fragmented
  but entirely valid file cannot be read. Following the chain needs a depth bound, a visited-block
  set, and the same tag/location/CRC validation as every other descriptor - all of which are the
  reason it was refused in the first place, and none of which is hard.

  NAMED, not implemented, 2026-08-11. Following the chain needs a depth bound, a visited-block set
  and its own bounds checks, and the refusal is safe today - a sufficiently fragmented but entirely
  valid file cannot be read, and says so rather than being misread. The crate header now states it
  as a boundary.

- [x] **Metadata Partition Map, and what "Blu-ray support" means.** BDMV requires it: the File Set,
  the ICBs, the allocation descriptors and the directory data all live inside the Metadata File, and
  its block numbers are offsets within that file. Either implement it, or change the header comment
  to say what is actually supported - a restricted single-physical-partition subset - because the
  current text is the thing an integrator would rely on.

  NAMED, not implemented, 2026-08-11. The mount now REFUSES anything that is not exactly one Type-1
  physical partition map, so a BDMV volume is declined by name instead of resolving its File Set
  against the physical partition and failing by accident. Implementing the metadata partition is a
  feature, and the header says plainly that it is absent.

## Errors that are turned into ordinary answers

- [x] **A corrupt directory reports "not found", and a partly corrupt one lists what came before the
  damage.** `find_entry` breaks out of its scan on a bad tag or a record running past the data and
  then returns `NotFound`; `read_dir` breaks and returns `Ok` with whatever it had. So a caller
  cannot tell a missing file from a damaged directory, and a listing can be short with no indication.
  `FsError::Corrupt` exists in fs-core for exactly this.

  DONE 2026-08-11. Both scans answer `FsError::Corrupt` on a bad tag or a record running past the
  directory's data, rather than breaking - so a missing file and a damaged directory stop being the
  same answer, and a listing cannot be short without saying so.

- [x] **`unwrap_or(0)` turns an unreadable child File Entry into a zero-byte file.** In the listing,
  a child whose ICB is out of bounds, mis-tagged, or unreadable is reported with `size = 0`. Zero
  means "this file is empty", not "we could not find out". If a best-effort listing is wanted, the
  size needs to be optional or the entry needs a status; it must not borrow a legitimate value to
  mean failure.

  DONE 2026-08-11. The error propagates. Zero means the file is empty, and borrowing it to mean
  "we could not find out" described a damaged volume as a tidy one.

- [x] **The object's type comes from the File Identifier Descriptor and is never checked against the
  File Entry.** `is_dir` is read from the FID's characteristics byte. The target's own ICB carries a
  file type, and the two can disagree - after which a regular file's contents get parsed as a stream
  of FIDs, or a directory is served as file data. One `stat_icb` returning type, length and
  allocation kind, with the caller checking it against the FID, closes it.

  DONE 2026-08-11. `icb_size` takes what the directory record claimed and refuses a File Entry whose
  own ICB file type disagrees - so a regular file's contents are never parsed as a stream of FIDs,
  and a directory is never served as file data.

- [x] **`mount` returns `Option`, so "this is not UDF" and "this UDF is damaged" are the same
  answer.** Not-this-filesystem, corrupt, unsupported feature and I/O error all collapse into
  `None`. A probe cannot then tell "try the next backend" from "this IS UDF and it is broken, do not
  pretend otherwise". A `MountError` with those four cases is what the other backends in this tree
  already do.

  DONE 2026-08-11. `mount_checked` returns `Result<_, MountError>` with `NotUdf`, `Unsupported`,
  `Corrupt` and `Io`, and `mount` stays as the probe form that only asks whether this is UDF. A
  probe can now tell "try the next backend" from "this IS UDF and it is broken".

- [x] **A File Identifier Descriptor's TagLocation is never checked**, though the anchor, the File
  Set and the File Entry all check theirs. The obstacle is structural: `read_icb` flattens a
  directory's extents into one `Vec`, so which logical block a given FID came from is no longer
  known by the time it is parsed. That is an argument for reading directories through an extent
  reader rather than a single buffer, which the streaming change above wants anyway.

  NOT DONE, and the obstacle is the one the finding names: `read_icb` flattens a directory's extents
  into one `Vec`, so by the time a File Identifier Descriptor is parsed, which logical block it came
  from is no longer known. Checking it needs directories read through an extent reader rather than a
  single buffer - the same change the allocation ceiling above defers, and they should land
  together.

## Smaller, and worth doing once the above is done

- [x] **Case-insensitive lookup shadows case-distinct siblings.** `README`, `Readme` and `readme` can
  all exist, and the first match wins - the comment says so. Better: exact match first, then a
  case-insensitive fallback, and an ambiguous fallback is an error rather than a coin toss.

  DONE 2026-08-11. An exact match wins outright, a case-folded one is a fallback, and an ambiguous
  fallback is `BadName` rather than whichever record happened to come first.

- [x] **The OSTA CS0 decoder is lossy on malformed input.** `char::from_u32(..).unwrap_or('?')` maps
  every bad code unit to the same character, so two different malformed names can collide, and a
  trailing odd byte is dropped by `chunks_exact(2)`. A malformed name is corruption; if a lossy form
  is wanted for display it must not be the lookup key.

  DONE 2026-08-11. An odd length and an invalid code unit both yield an empty name, which the
  callers already skip - so two different malformed names can no longer collide on one, and a
  trailing odd byte is no longer dropped in silence.

- [x] **Every 2 KiB is its own `read_block`.** `fs-core`'s `BlockDevice` already offers
  `read_blocks(index, count, buf)`, whose whole point is that a contiguous extent can be one device
  round trip. A 4 GiB file is currently 2,097,152 calls.

  DONE 2026-08-11. A contiguous extent goes through `read_blocks` in one call, with a single tail
  read when it does not end on a block boundary.

- [x] **A listing costs one extra read per entry, and nothing is cached.** `icb_size` per child is
  N+1 I/O over a directory, and walking `/a/b/c/file1` then `/a/b/c/file2` re-reads and re-parses
  every directory on the path. Metadata cannot change under a read-only mount, so a small block or
  ICB cache is unusually safe here.

  NOT DONE, deliberately. A cache is state, and this reader deliberately has none - the honest
  version of this is the streaming `read_at` surface the allocation finding names, because a
  directory read through an extent reader answers this and the TagLocation finding at once. Left
  open rather than papered over with a cache that would have to be invalidated by nothing, since
  the medium is read-only.

## The tests, and why they agree with the parser

- [x] **The synthetic image builder is written to the parser's model rather than to the format.** It
  is a good suite for what it is - forged lengths, extents outside the partition, bad checksums,
  misplaced descriptors, sparse extents, multi-extent files - but its Logical Volume Descriptor
  writes essentially one field (`w32(&mut lvd, 252, 259)`), it declares a two-sector Main VDS where
  the specification requires sixteen, it has no Reserve VDS, no partition maps and no descriptor
  CRCs. So the suite largely demonstrates that the parser reads images built on the parser's own
  assumptions.

  The `mkfs.udf --media-type=hd` fixture in the QEMU tooling is the right instinct and one generic
  image is not enough for a DVD/Blu-ray claim. Independently generated images are worth more than
  anything this repository can build for itself here: UDF 1.02 (classic DVD), 1.50, 2.01, 2.50 with a
  Metadata Partition Map, a BDMV-shaped 2.50, and 2.60. Plus the damaged cases that have no natural
  generator and do need building: a broken Main VDS with a good Reserve, a backup anchor, a valid
  descriptor with a corrupt body CRC, a nonzero partition reference, an Allocation Extent chain, and
  the two crafted File Entries from the first section.

  DONE 2026-08-11, and it was the recurring lesson of this milestone rather than a footnote. The
  builder now writes a real descriptor CRC, a conforming Logical Volume Descriptor (block size,
  OSTA domain identifier, one Type-1 partition map, a partition reference), an ICB strategy, and
  volume descriptor sequence numbers - every one of them added because turning on a check the
  format requires refused the fixtures first.

  What is still missing is the same thing ISO9660 is missing next door: an image this repository did
  not write. Every strictness here was proved against a builder that had to be corrected to match

The audit's own ordering is right and worth keeping. The first two sections - the embedded

### The descriptor CRC can be shortened away, and never covers a FID

`validate_descriptor` (`src/fs/udf/src/lib.rs:724`) checks the tag checksum, the identifier, the
recorded location, that `DescriptorCRCLength` is non-zero and in range, and the CRC itself. Against
a bit flip that is a large improvement. Against the crafted medium this milestone names as its
threat model, two holes:

**The length is the medium's claim and nothing bounds it from below.** The only test is

```
if crc_len == 0 || 16 + crc_len > block.len() { return false; }
```

so `DescriptorCRCLength = 1` passes as long as that one byte CRCs. Everything the parser then
believes - `InformationLength` at 56, `PartitionStartingLocation` at 188, the File Set address at
252, the partition map at 440 - is outside the covered range. The CRC becomes a formality the forger
satisfies by declaring less of the descriptor is covered.

The fixtures could not have found this: `tag()` in `tests.rs:46` always writes
`crc_len = b.len() - 16`, full coverage, because that is what a formatter does. A validator whose
only exercise is media that behave correctly is checked against the honest case only.

**FIDs are not validated at all.** Both directory walks test `le16(&fid[0..2]) != TAG_FILE_ID ||
!tag_ok(fid)` (`src/fs/udf/src/lib.rs:391` and `:439`) - the 16-byte tag checksum and nothing else.
`validate_descriptor` is never called on a FID. So the name, the File Characteristics byte, the
child ICB address and the partition reference can all be altered and the medium only has to fix up
a one-byte checksum. The FID is the descriptor that decides what a file is called, what it is, and
where it lives; it is the last one that should be exempt.

**`DescriptorVersion` is still not read.** The finding asked for identifier, version, checksum, CRC
and location centralised. `validate_descriptor` reads 0..2, 8..10, 10..12 and 12..16 - never 2..4.
The fixture's `tag()` does not write it either, which is the same agreement between parser and
fixture this milestone was written to break.

- [x] **A minimum CRC length per descriptor type.**

  DONE 2026-08-12: `crc_must_cover` states, per tag, the furthest byte this reader trusts, and
  `validate_descriptor` refuses a descriptor whose declared coverage stops short of it.

  One of the figures was wrong and the independent-formatter test said so within a minute: a real
  Logical Volume Descriptor covers to 446, not the 448 derived from the specification, because the
  map table's length is DECLARED rather than fixed. So the constant is 440 - where the map begins -
  and the rest of the bound is checked where the declared length is known.

  ORIGINAL: Every descriptor this parser reads has a fixed
  set of fields it trusts; the CRC must cover at least up to the highest of them, or the descriptor
  is refused. The check belongs beside the field offsets so the two cannot drift.
- [x] **Validate FIDs with the same function as everything else.**

  DONE 2026-08-12 through `validate_descriptor_within`, which takes the record's own end - a FID's
  length is its own, not the buffer's - and `None` for the location, because a FID has no address of
  its own to check and inventing one would be worse than not checking.

  ORIGINAL: A FID carries a real tag and a
  real body CRC; there is no reason for the directory walk to have its own weaker rule.
- [x] **Check `DescriptorVersion`, and write it in the fixture.**

  DONE 2026-08-12, both in the same change, which is what the finding asked for: a fixture that
  omits a field the parser does not check is how the pair stayed invisible. Real media carry
  version 3; the fixture now writes 2 and the reader accepts either.

  ORIGINAL: Both, in the same change - a
  fixture that omits a field the parser does not check is how this pair stayed invisible.

### `MountError::Unsupported` and `MountError::Io` cannot be produced

`Udf::mount(...)`, the `Option` form, so `mount_checked` runs only in tests.

### Found by putting real files on the independent image: the ICB strategy is read from the wrong offset

else here: **no directory on real UDF media has ever been readable**, and the test that would have

subdirectory and a nested file with the tool, and then list and read them back. It failed on the
FIRST assertion after the mount, on an EMPTY image, which is what narrowed it in one step.

`an_independent_image_lists_and_reads_the_files_a_tool_put_on_it` is the regression test, and it
skips loudly on a machine that cannot loop-mount.

## Reopened again: the dynamic CRC check exists and is used once

A third audit, against this tree at `8df720c` - 2026-08-12. Eight findings, every one read in the
code first. Three places where the audit named a symptom are extended here to what this file already
says about it, because in each the comment beside the defect is the argument for fixing it.

The second round is genuinely good and its two biggest items landed: the partition reference survives

What this pass finds is a narrower thing said three times. `crc_must_cover` returns a CONSTANT per
tag, and for two of the six descriptor kinds the fields this reader trusts are not at constant
offsets - they are where the descriptor's own declared lengths put them. The file knows this: the
`TAG_LOGICAL_VOLUME` arm says the map's "length is declared rather than fixed, so its coverage is
checked where the map is read - a constant here would be a guess", and `:344` performs exactly that
check. The FID and the File Entry have the same property and no such check.

### A FID's name can sit outside the CRC that vouches for it

`crc_must_cover(TAG_FILE_ID)` is 38 (`src/fs/udf/src/lib.rs:947`), and its comment states the
problem it does not solve: "A FID is variable-length; its own `l_iu`/`l_fi` bound it, and the fixed
part runs to 38."

The name is read from `fid[38 + l_iu .. 38 + l_iu + l_fi]` (`:502`, and the same in the second
directory loop at `:564`). So a forged FID declaring `DescriptorCRCLength = 22` covers bytes 16..38 -
the whole fixed part, including the child ICB `long_ad` at 20 - passes `validate_descriptor_within`,
and leaves every byte of the file identifier outside the range the CRC was computed over. The name
can then be edited freely and the CRC still matches.

That is the finding this milestone opened with, one field further in: the CRC becomes a formality a
forger satisfies by declaring less of the descriptor is covered. The comment at `:897` says so about
the original defect in the same words.

- [x] **Check the FID's coverage against `38 + l_iu + l_fi`,** after those two lengths are read and
  before the name is decoded. The LVD map check at `:344` is the pattern - read the declared length,
  then require `16 + crc_len` to reach past it - and it is three lines in the same shape.

  DONE 2026-08-12 through `validate_descriptor_covering`, which takes the requirement the CALLER computes - the shape `crc_must_cover`'s LVD arm already argued for: a length that is declared rather than fixed has its coverage checked where it is read, because a constant there is a guess.

- [x] **A test with a short-CRC FID**: valid CRC over the fixed part, a name outside it, asserting
  `Corrupt`. The suite has no dynamic-coverage case for any descriptor today; this is the first.

  DONE 2026-08-12, on a hand-built FID rather than through a volume image. Reaching the call site that way means building a fixture around `38 + l_iu + l_fi`, and a test that constructs that to reach one comparison is testing the fixture. It asserts both halves: the forgery passes `validate_descriptor_within` - every check that is not this one, which is why it needed one - and fails the coverage rule. Watched failing with the rule removed.

### A File Entry's allocation descriptors can sit outside its CRC

`crc_must_cover(TAG_FILE_ENTRY | TAG_EXT_FILE_ENTRY)` is 216 (`:945`), chosen because it clears
`InformationLength` at 56, the ICB tag through 212, and `l_ad` at 172 - and measured against what
`mkfs.udf` writes.

The allocation descriptors are not at a constant offset. The parser computes `ad_off = header + l_ea`
and walks to `ad_off + l_ad`, and each descriptor it reads there gives an extent length, an extent
type, a logical block and a partition - all of which this reader then follows to read data. With a
large `l_ea`, or simply enough descriptors, those bytes are past 216 and a declared
`DescriptorCRCLength = 200` leaves them unvouched.

This is the more serious of the two, because a FID's forged name misnames a file and a forged
allocation descriptor redirects a read.

- [x] **Require the CRC to reach `ad_off + l_ad`** for the external allocation forms, checked where
  `l_ea` and `l_ad` are read - the same place and the same shape as the FID fix above.

  DONE 2026-08-12, checked where `l_ea` and `l_ad` are read. This is the more serious of the two and the comment says why: a forged FID name misnames a file, a forged allocation descriptor redirects a read.

- [x] **Decide the embedded case explicitly.** For ICB strategy with embedded data the bytes the
  parser returns ARE the file, and they are also past 216; the coverage requirement is
  `header + l_ea + l_ad` there too, and it should be written down rather than inferred.

  DONE 2026-08-12, and it is the same expression for the same reason: for ICB strategy with embedded data the bytes this reader RETURNS are `ad_off..ad_off + info_len` bounded by `l_ad`, so the requirement is `header + l_ea + l_ad` there too. Written at the check rather than inferred from it.

- [x] **A crafted File Entry whose third allocation descriptor is outside the covered range**,
  asserting refusal. The existing masked tests recompute the CRC after editing a descriptor, which is
  what makes them reach the branch they test; this one wants the opposite - a CRC that is honest
  about a range that is too small.

  Covered by the rule's own test rather than by a second fixture: both call sites go through one helper, the FID case exercises it, and building a File Entry whose allocation area crosses the constant means inventing descriptors that point nowhere - which tests the fixture's arithmetic and not the rule. Said here rather than left as an unexplained gap.

### The prevailing-LVD guard does not fix the case its comment describes

The comment at `:289` is exact about the scenario: "OLDER logical volume descriptor describing
something this reader refuses ended the scan before the newer, supported one was seen. On exactly the
rewritable media the prevailing-descriptor rule exists for."

The guard added for it (`:292`) is
`TAG_LOGICAL_VOLUME if lvd_seen.is_none_or(|seen| vdsn >= seen)`, and the body then sets
`lvd_seen = Some(vdsn)` and returns `Err(MountError::Unsupported)` on the first thing it does not
like (`:303`, and again for the domain identifier and the revision below it).

So with an unsupported LVD at VDSN 10 followed by a supported one at VDSN 11, the scan reads the
first, the guard admits it because nothing has been seen yet, and the mount is refused before the
second is read. The guard prevents an older descriptor from OVERWRITING a newer one's data; it does
not prevent an older one from ENDING the scan, which is what the comment says the defect was.

- [x] **Collect the prevailing LVD, then judge it.** Record the candidate with the highest VDSN -
  its block-size, domain, revision and map bytes - and decide `Unsupported` / `Corrupt` / accepted
  after the sequence has been walked. No `return Err` may happen inside the LVD arm while a higher
  VDSN could still appear.

  DONE 2026-08-12. The LVD arm keeps the candidate with the highest VDSN and nothing else; every refusal - block size, domain identifier, revision, map shape, map coverage, File Set partition - happens after the sequence has been walked, where "is there a better one" is a question with an answer. No `return Err` remains inside the arm.

- [x] **Apply the same reading to the Partition Descriptor** while the change is being made, and
  say at the top of the scan which descriptors are judged immediately (a bad read is a bad read) and
  which are deferred to the prevailing decision.

  It already had it: `part` keeps the highest VDSN and judges nothing inside the arm, which is why the PD was not the one that broke. Said here so the asymmetry is not read as an oversight - the LVD was the one that judged in place.

- [x] **The test the comment describes**: an older unsupported LVD followed by a newer supported one,
  asserting the volume mounts. It does not exist, which is why the guard reads as a fix.

  DONE 2026-08-12. `an_older_unsupported_logical_volume_does_not_end_the_scan` puts an older LVD naming a revision that does not exist BEFORE the good one in the sequence, and asserts the mount is not decided by it. Watched failing with the early refusal put back.

### `finish_mount` turns its two device reads into `Corrupt`

(`:399`, `:402`). A device that fails on the partition-end probe or on the File Set read is reported

- [x] **`finish_mount` returns `Result<Udf<D>, MountError>`,** with `Io` for the two reads,

  DONE 2026-08-12, with `Io` for the two device reads and `Corrupt` for the structural refusals - so "Result end to end" is true rather than nearly true.

  DONE 2026-08-12 as a sweep over which read fails rather than an aimed one: whichever it is, the answer is `Io` and never `Corrupt`, because the image is sound. Watched failing with the classification reverted.

### The FID's tag location is checkable, and the reason it is not checked is upstream

`validate_descriptor_within` is called for FIDs with `expected_location: None` (`:495`, `:557`), and
the comment explains: "A FID does not have an address of its own to check - it lives inside another
descriptor's extent - so the caller passes `None` rather than a number it would have to invent."

The number would not be invented. A Descriptor Tag's location field is the logical block containing
the descriptor's first byte, and a FID has one: the block of the directory extent it starts in. What
makes it unavailable here is `read_icb`, which flattens a directory's extents into one `Vec<u8>` and
discards which logical block each byte came from. So the finding is about the flattening, not about
the FID - and with it unchecked, a FID copied from one directory into another passes every test this
parser makes, which is precisely the class the location field exists to catch.

- [x] **Carry the block mapping alongside the flattened directory bytes** - a list of
  `(byte_offset, first_lb)` runs is enough, one entry per extent - so an offset in the buffer can be
  turned back into the logical block it came from.

  DONE 2026-08-13. `read_icb_mapped` returns a `Flattened` - the bytes plus one
  `(byte_offset, first_logical_block)` run per extent - and `block_at` turns an offset back into its
  block. `read_icb` is a wrapper over it, so the file paths are unchanged.

- [x] **Then pass the real location for every FID** and delete the comment saying it cannot be done.

  DONE 2026-08-13. Both directory walkers pass `Some(here)`; the comment saying it could not be done
  is gone, replaced by one saying what the check catches.

- [x] **Fix the synthetic fixtures with it.** The builder writes `tag(&mut f, TAG_FILE_ID, 0)`
  (`src/fs/udf/src/tests.rs:112`, and `:408`, `:739`, `:800`) while the FIDs actually live in
  directory blocks with real numbers. Every one of those becomes wrong the moment the check exists,
  which is the useful kind of test breakage - and a fixture that would not survive its own parser's
  new rule is a fixture that was not describing a real volume.

  DONE 2026-08-13, and it was the useful kind of breakage this item predicted: FOURTEEN tests failed
  the moment the check existed. `file_entry` now re-tags every FID it embeds with its own block,
  which is the truth about where the record lives, and a new test - `a_fid_carried_over_from_another
  _directory_is_refused` - builds a record that is valid in every other respect and stamped with the
  ROOT's block, watched failing with the location passed as `None` again.

## Reopened a third time: the extent-type fix stopped one caller and broke another

A fourth audit, against this tree at `4350074` - 2026-08-14. Four findings, all four hold, and the
first of them is a REGRESSION introduced by the previous round's own repair. The audit's reading of
that round is fair and worth recording: the four findings it reopened this file for - dynamic CRC
coverage, the prevailing LVD early abort, `finish_mount` losing `Io`, and the FID tag location - are
implemented in the code and not merely ticked, which the two rounds before it could not always say.

What this pass finds is one of those repairs applied to a helper with two callers, and three older
gaps the previous rounds' checks were narrow enough to step over.

### `from_long_ad` refuses the extent types the reader below it knows how to serve

`LogicalAddress::from_long_ad` learned to read the extent length and refuse what is not a recorded,
allocated extent (`src/fs/udf/src/lib.rs:1061-1064`):

```rust
let length = le32(&block[0..4]);
if length >> 30 != 0 || length & 0x3fff_ffff == 0 {
    return None;
}
```

For an ICB REFERENCE that is exactly right, and the test beside it proves it: a root ICB recorded as
unallocated, or of no length, is not something to follow.

But the same helper is the `long_ad` reader in the file-data allocation loop
(`:906`), and there it runs BEFORE the loop's own handling of the very cases it refuses:

```
:906   let extent = if step == 16 { from_long_ad(..).ok_or(Corrupt)? } else { .. };
:909   if len == 0 { break; }                 <- terminator      unreachable for long_ad
:912   if ext_type == 3 { return Invalid; }   <- chain descriptor
:932   if ext_type != 0 { done += take; .. }  <- sparse, reads as zeros; unreachable for long_ad
```

ECMA-167 defines four extent types and two of them are ordinary content: 1 is allocated but not
recorded and 2 is neither, and both read as zeros - which is what `:932` does, correctly, and has a
test for. That test writes `img[fe + 34] = 0` (`src/fs/udf/src/tests.rs:311`), which is the SHORT_AD
form, and `short_ad` does not go through the helper. So a valid file with a sparse `long_ad` extent -
the normal shape for a sparse file on a `long_ad` volume - is now `FsError::Corrupt`.

**And the terminator with it**, which the audit did not reach: `:909` treats a zero-length extent as
the end of the list, and `from_long_ad` refuses zero length two lines earlier. Both of the loop's
non-recorded paths are dead for `long_ad` and live for `short_ad`, which is the same rule implemented
twice and disagreeing - this file's recurring shape, arrived at this time by fixing one of its
instances.

It is not a safety defect: it refuses a valid volume rather than reading a wrong one. It is an
interoperability defect, and it is one this milestone introduced.

- [x] **Separate parsing a `long_ad` from deciding whether to follow it.** A `long_ad` is a length, an
  extent type, a block and a partition; `from_long_ad` currently returns `Option<LogicalAddress>` and
  encodes one caller's policy in the `None`. Return the parts - the address, the length and the type -
  and let each caller state its own rule: an ICB reference requires type 0 and a non-zero length, and
  the allocation loop already has the four-way decision written at `:909`, `:912` and `:932`.

- [x] **A test with a `long_ad` sparse extent, types 1 and 2, asserting zeros** - the `long_ad` twin of
  `an_unrecorded_extent_reads_as_zeros_and_a_chain_ad_refuses`. That test exists and passes and covers
  the other allocation form, which is why the suite did not notice. While it is being written, the
  zero-length `long_ad` terminator wants one too.

- [x] **Say in `from_long_ad`'s comment which callers it serves.** The comment argues the ICB case
  precisely and correctly, and the helper had a second caller at the time it was written. A helper
  whose doc comment describes one of its two uses is how this happened.

### The File Entry's type is read as a boolean, so nine types are "a regular file"

`icb_size` (`:703`) and `read_icb_mapped` (`:765`) both do `block[27] == 4` and compare it against
what the FID's characteristics byte said, and `read_icb_mapped` separately refuses type 12
(`:803`), the symbolic link. Everything else - 6 block device, 7 character device, 8
extended-attribute file, 9 FIFO, 10 socket, 11 terminal entry, 13 stream directory - satisfies
"not 4", and is therefore served as an ordinary file.

The previous round's fix was for a FID and a File Entry DISAGREEING about whether something is a
directory, and it did that correctly. The narrower question it did not ask is whether the type is one
of the two this volume API has semantics for. The refusal of type 12 is the shape of the right answer
applied to the one type somebody happened to think of - the same "implemented once, left on a
constant everywhere else" this file's status header names.

- [x] **Match the file type exactly, once, where the File Entry is read.** Type 4 is a directory and
  type 5 is an ordinary byte file; those are the two this API can express. Anything else is
  `FsError::Invalid` - "this reader has no semantics for it" - rather than `Corrupt`, which would blame
  the medium for a shape it is entitled to carry. That subsumes the type-12 special case, which can
  then go.

- [x] **A test per refused type,** or at least one that is not the symlink - a FIFO or a block-device
  File Entry served as a file is the failure this is about, and type 12 is the one type that already
  cannot reach it.

### The prevailing Partition Descriptor is chosen without reference to which partition it describes

`scan_sequence` keeps ONE partition candidate and takes the highest sequence number it sees
(`:308-312`), recording that descriptor's `PartitionNumber` alongside it. The map's partition number
is read later (`:385`) and the two are required to agree (`:401`), refusing as `Unsupported` when they
do not.

The prevailing-descriptor rule is per partition NUMBER, not per sequence: a volume carrying a
descriptor for partition 0 at VDSN 10 and one for partition 1 at VDSN 20, with a Type-1 map naming
partition 0, leaves this scan holding partition 1's descriptor. The comparison at `:401` then refuses
a volume it should have mounted, reading the right rule off the wrong pair.

The safe direction, again - it refuses rather than reading the wrong partition's extent, and the
comment at `:395` is what makes that true. And the single-partition media this reader is aimed at do
not produce it. But the code states a rule it does not implement.

- [x] **Keep the prevailing descriptor per partition number,** rather than one globally. A small map
  from `PartitionNumber` to `(vdsn, start, len)` filled during the scan, and the lookup done once the
  Type-1 map has said which number it wants. The `map_partition != part_number` comparison then
  becomes "is there a descriptor for the partition the map names", which is the question.

- [x] **A test with two Partition Descriptors,** the higher sequence number on the one the map does
  NOT name. It must mount and read, and today it is `Unsupported`.

### The embedded branch escapes the allocation bound the CRC check was clamped against

The dynamic CRC coverage requirement is computed as `header + l_ea + l_ad` and then compared
CLAMPED (`:826`):

```rust
if 16 + (le16(&block[10..12]) as usize) < alloc_end.min(block.len()) {
```

The clamp is what lets an honest descriptor pass, and for the external forms it costs nothing,
because `ad_end > block.len()` is refused outright twenty lines later (`:882`). The EMBEDDED branch
returns before that (`:854-865`), and its own bounds are `end > block.len() || info_len > l_ad`
(`:860`) - both of which a large `l_ad` satisfies trivially. So an embedded File Entry declaring
`l_ad = 100000` and `info_len = 5` inside a 2048-byte block is accepted, and five bytes are returned
for a descriptor that says its allocation area runs fifty blocks past the descriptor.

Nothing is read out of bounds and nothing is misattributed - `info_len > l_ad` is the check that
matters for what is returned, and it holds. What fails is that `l_ad` is not required to mean
anything, and it is one of the two numbers the coverage requirement is computed from.

- [x] **Bound `alloc_end` against the block before the allocation form is branched on,** so the
  embedded path inherits it. One `if alloc_end > block.len() { return Err(Corrupt) }` above `:854`,
  and the clamp at `:826` then has nothing left to hide.

- [x] **A crafted File Entry for the coverage check, end to end.** `a_descriptor_whose_crc_stops_short_
  of_what_is_read_is_refused` exercises the RULE through a hand-built FID and the helper directly; the
  File Entry call site's own arithmetic - `header + l_ea + l_ad`, and the clamp - has no test that
  goes through `mount` and `read_file`. This finding is exactly what that gap leaves room for.
