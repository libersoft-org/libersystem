# P02M0145 - The development profile does not boot, and nothing was going to tell us

Status: COMPLETE (2026-08-23). REPAIR, plus the gate that stops it happening again. NOT A PHASE-2
COMPLETION GATE.

## Goal

Make the development profile reach a shell, and make its rotting again a build failure rather than
something the next person discovers by hand.

This is not a feature. The development profile is how every scenario in `harness/scenarios/` is run -
`lab.py scenario-cold` builds with `LIBER_DEVELOPMENT=1`, boots that guest, and drives it over the
control channel - so while it does not boot, EVERY SCENARIO IS UNRUNNABLE. P02M0101 hit exactly that
last week: `harness/scenarios/audio-capture.toml` was written, its every step was verified by hand
through the serial console, and the runner could not replay one of them.

## What is there now

Measured on 2026-08-23, by building the profile and booting it.

- **IT DID NOT COMPILE.** `LIBER_DEVELOPMENT=1 ./build.sh` failed on two errors in
  `dev_protocol.rs`: a call to `permission.run` missing the `environment` argument that method
  gained when `security.lsidl` grew it, and an `unsafe` block that had become unnecessary. Neither
  is subtle. Both had been there since the interface changed, because nothing builds this profile.
- **AND THEN IT DID NOT BOOT.** With those fixed, the boot stops after seven services with
  `recovery: no interactive shell after 300 rounds`, four times, and reboots. No service reports a
  failure, because none has failed: the chain is BLOCKED.
- The block is exact, and this is where it is. ServiceManager starts `storage_service`, then drives
  DeviceManager's phase 2 (`drive_runtime_drivers`), which sends `DRIVERS` and then waits for eight
  handoffs. DeviceManager receives `DRIVERS`, and in this profile `launch_volume_drivers` also
  starts the development agent - `start_dev_agent`, which ends by waiting for the agent to report
  in. The agent never does. So DeviceManager never answers, ServiceManager never continues, and the
  machine never reaches a shell.
- **THE AGENT IS WAITING FOR A MESSAGE NOBODY SENDS.** `dev_agent.rs` reads three things from its
  bootstrap: `BYTES` with the wire, `STORAGE` with a volume client, and `CONSOLE` with a
  ConsoleInputSource. `start_dev_agent` in `device_manager.rs` sends the first two. The third read
  is `recv_tagged`, which BLOCKS.
- The `CONSOLE` read arrived in 9fede7bc, with the Privilege objects that made typing into the
  console need a capability. The agent's side was written; the sender's side was not. DeviceManager
  holds a perfectly good `console_input` - it hands one to every keyboard driver eleven lines away -
  and never offers it to the agent.
- This is the ORDERED-BOOTSTRAP HAZARD this tree has written down three times, most recently in
  `permission_manager.rs`: "a tag read where nothing was sent consumes the message that was actually
  next and then waits forever for one nobody will send". It is recorded as a hazard and it is not
  checked by anything.
- Nothing builds this profile: `check.sh` has twenty-eight gates and none of them passes
  `LIBER_DEVELOPMENT=1`. `check-development-gate.sh` reads that variable, but it checks which
  ARTIFACTS a configuration stages - it does not compile the other one.

## Work

- [x] **M1 - The agent is given its console.**
  - `start_dev_agent` sends `CONSOLE` after `STORAGE`, carrying a duplicate of the
    `console_input` DeviceManager already holds - narrowed the same way the keyboard drivers' copy
    is, because it is the same capability for the same purpose.
  - A HANDLE OF ZERO IS A LEGAL ANSWER and the agent already treats it as one: `unwrap_or(0)` and
    the comment beside it say the agent works without a console and simply cannot type. So the
    message is sent whether or not there is a console to put in it - what must not vary is the
    NUMBER of messages, which is the whole of what an ordered bootstrap is.

- [x] **M2 - A bootstrap that never completes costs the agent, not the machine.**
  - `start_dev_agent`'s last act is `recv_blocking` on the agent's report. That is a wait with no
    end, on the boot's critical path, for a program that might be broken - and M1 is exactly the
    case where it was. One process failing to start took the whole machine down and said nothing.
  - The wait gets a deadline. On expiry DeviceManager prints what happened, abandons the agent, and
    answers phase 2 - which is what it already does when the agent cannot be LOADED
    ("the control channel is transport-only"), so the failure path exists and only the timeout does
    not reach it.
  - NOT A WATCHDOG, and not a retry. This is one bounded wait becoming a bounded wait with a number
    on it. `DevAgent::restart` is the mechanism for an agent that dies later and is unchanged.

- [x] **M3 - The development profile is built by a gate.**
  - It broke twice in one release for one reason: nothing compiles it. A gate that builds it is the
    smallest thing that would have caught both - the compile errors directly, and M1 the moment
    anybody booted it.
  - `check.sh` gains `development-build`: build the userspace with `LIBER_DEVELOPMENT=1` for one
    target and fail if it does not compile. One target, because the profile's difference is a Rust
    feature and not a per-architecture path; x86_64, because it is the target every other cheap gate
    already uses.
  - IT DOES NOT BOOT THE GUEST. A gate that boots is a gate that takes minutes, and this one exists
    to catch the class of fault that a compiler catches. Booting is M4's job and it is not a gate.

- [x] **M4 - A scenario runs, and it is the one that could not.**
  - The proof this milestone is finished is `lab.py scenario-cold x86_64` completing a scenario
    against a cold development guest. `harness/scenarios/audio-capture.toml` is the one to use: it is
    the scenario P02M0101 wrote and could not run, and every step in it is already known to be true
    from a hand-driven boot, so a failure is the runner's or the profile's rather than the
    scenario's.
  - `shell-basics.toml` runs beside it, because it is the shortest scenario in the tree and a
    failure in both says "the guest" where a failure in one says "that scenario".

## Dependency order

```text
M1 -> M4
M2        independent of M1, and the reason M1 was invisible
M3        independent of both
```

M1 is the repair, M2 is why the repair took a day to find, M3 is why it was needed at all, and M4 is
the evidence. M2 and M3 are worth having even if M1 were the only bug this profile will ever grow -
which it will not be, because the profile is a second configuration of a system with one test suite.

## Definition of done

- `LIBER_DEVELOPMENT=1 ./build.sh` compiles, and a gate fails if it stops compiling.
- A development guest reaches the shell prompt with every service online, and the agent reports in.
- An agent that never reports in leaves a message and a working machine, proven by watching it - a
  deliberately broken agent must not stall the boot.
- `lab.py scenario-cold x86_64 harness/scenarios/audio-capture.toml harness/scenarios/shell-basics.toml`
  passes both.

## Results

Measured on 2026-08-23 on this host (Linux 6.12.100+deb13-amd64, QEMU 10.0.11, KVM available), each
item by running the thing it describes.

- **M1.** `start_dev_agent` sends `CONSOLE` after `STORAGE`, carrying `duplicate(console_input,
  RIGHT_TRANSFER)` - the same narrowing the keyboard drivers' copy gets - and sends it as a zero
  handle when there is no console. `DevAgent` retains the console so a replacement agent gets one
  too; deriving it again in `restart` is not possible, because the value comes from phase 2 and
  `restart` runs long after it.
  `LIBER_DEVELOPMENT=1 ./build.sh --arch x86_64` then `DEV_PROFILE=1 ./run.sh --arch x86_64 --smp 4`
  reaches `vol://system>` with `agent.dev: online (registry)` and all twenty-six services online. The
  same command before this change stopped after seven services and rebooted four times.

- **M2.** The report wait is `try_recv` + `wait_periodic` against a deadline, and on expiry
  DeviceManager prints, CLOSES the agent's bootstrap - so the agent stops rather than holding the
  wire - and answers phase 2.
  Watched to fail: with a fourth `recv_tagged(b"NOSUCH")` inserted into `dev_agent.rs` before its
  report, the guest printed `the development agent did not report in; it is abandoned`, then `the
  control channel is transport-only`, and REACHED THE SHELL PROMPT. The same broken agent without
  the deadline reproduced the M1 failure exactly: seven services, four recovery attempts, reboot.

- **THE DEADLINE HAS TO BEAT THE RECOVERY LADDER, which is not obvious and cost a boot to find.**
  Ten seconds was tried first and NEVER FIRED: the kernel's recovery ladder gives the chain a bounded
  number of settle rounds and reboots the machine when they run out, which on this host is about ten
  seconds from the wait starting. A deadline that expires after the reboot is not a deadline. Two
  hundred ticks (two seconds) fires with the settle window still open, and is still two orders of
  magnitude more time than a working agent takes - it reports in before the first service does.

- **M3.** `check.sh` gains `development-build` (28 gates -> 29, mirrored in
  `verify-model/src/catalog.rs`, which `verify-model check` compares against `check.sh`). It builds
  the services and drivers crates with `--features development` into their own target directory, the
  way `check-development-gate.sh` builds the shipping configuration into its own, and then checks
  that the development-only programs the manifest names were actually produced - a compile that
  built none of them would be a gate reporting on nothing.
  19.7 s on this host. Watched to fail: a deliberate type error in `dev_agent.rs` gave
  `development-build: services does not compile with --features development` and exit 1.

- **M4.** `lab.py scenario-cold x86_64 harness/scenarios/audio-capture.toml
  harness/scenarios/shell-basics.toml` passes both: audio capture in 63.6 s, shell basics in 13.2 s.

- **AND M4 FOUND A SECOND FAULT, in the runner rather than the guest.** With M1 fixed, both scenarios
  ran, both passed, and both were then FAILED by their own teardown: "the scenario passed but its
  scope was not restored". `publish`, `reset` and `restart` are the three scenario steps that
  re-invoke `lab.py` as a child process, and `CHANNEL_OVERRIDE` - which is how a cold run says which
  guest to drive - is a module global that does not cross a fork+exec. Those three drove the
  persistent instance's sockets while every other step drove the cold guest, so on a machine with no
  persistent instance they could not reach anything at all.
  The four endpoint overrides (channel, serial, monitor, QMP) are now read from the environment at
  import and put into the child's environment by `scenario_child`. Three tests in
  `harness/harness-test.py` cover both halves, each watched to fail against the broken version
  (`boot-harness`: 70 tests -> 73).

## What this milestone refuses, and why

- **A CONSOLE for the agent that is not the one DeviceManager holds.** The agent wants to type into
  the console; DeviceManager already has that capability and already narrows it for drivers. Minting
  a second path to the same authority would be two things to keep in step for one purpose.
- **Making every bootstrap handoff optional.** The ordered bootstrap is what lets a receiver read
  its capabilities by position without a negotiation, and a tag that may or may not arrive is a
  negotiation with no protocol. The rule stays: every message in the sequence is sent, and a zero
  handle is how "there is none" is said.
- **A gate that boots the development guest.** Minutes per run for a fault a compiler catches in
  seconds. M4 boots it once, by hand, as evidence - and when scenarios are cheap enough to run in a
  gate, that is a different milestone with a different argument.
- **Reviving the persistent development instance (`dev.sh up`).** It is a second way to run the same
  guest and it is not what blocked P02M0101. Whether it works is a question for whoever needs it.
