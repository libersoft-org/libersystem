The last section is the one to read if you only read one: the buddy went green on x86_64 and failed
on aarch64, and the cause was not the buddy. The frame pool had contained the boot packages for as
long as the loader has been reading them into RAM, and the old allocator's address order was the
only thing hiding it.

The frame allocator keeps freed spans in a run table. The table is bounded - it was bounded on
purpose, to fix a deadlock - and `insert` says outright that a span which does not fit is not being
tracked. So under enough fragmentation, freeing memory silently loses it. That is safer than the
deadlock it replaced and it is not a resting place for a kernel meant to run for months: the machine
gets slowly smaller, nothing reports it, and the symptom arrives weeks later as an allocation
failure with no cause attached.

The same shape showed up once already and was caught by accident. During P02M0117 the frame quarantine
dropped pages when its queue could not grow, which is exactly when frames are short; it cost nine
pages per failed load and was only noticed because a test printed how many were still quarantined.
A counter would have found it in a second. That is the cheap half of this milestone.

## What is wanted

- [x] **Count what is lost, before changing anything.** A refusal counter on every path that declines
  to track a freed span, and a boot-time report of it. This is a day's work, it makes the defect
  visible instead of theoretical, and it is what says whether the buddy allocator below actually
  fixed anything. P02M0117's rule: measure first, and be willing to record that the change did not pay.

- [x] **A buddy allocator for the frame layer.** It answers three things the run table answers badly:
  metadata bounded at boot rather than growing with fragmentation, coalescing that does not depend on
  a table having room, and contiguous multi-page allocation for DMA without a linear scan. The
  bitmap is sized from the memory map once and never allocates again, which is the property that
  makes "a free cannot fail" true rather than usually true.

- [x] **A free that cannot fail, and a signature that says so.** Today's `deallocate` and `retire`
  can decline. With bounded metadata they cannot, and the types should stop pretending otherwise -
  a `Result` nobody can act on is worse than none, because every caller invents its own wrong
  handling for it.

- [x] **Keep the quarantine on top.** The TLB quarantine from P02M0117 is orthogonal and stays: a frame
  that was mapped is not safe to hand out until every core has flushed it, whatever structure holds
  the free list. What changes is that `drain_quarantine` can no longer fail to return frames.

- [x] **Fragmentation tests that actually fragment.** Allocate and free in a pattern that shreds the
  address space, then assert that the total free count returns to what it started at - and assert it
  through a counter the test owns, not the global one. P02M0117 retired four tests that asserted numbers
  belonging to the whole machine; this one has to be written to survive an eight-core kernel doing
  other things.

- [x] **A contiguous-allocation test with a real caller.** DMA buffers are the reason contiguous
  allocation exists. The test should ask for one after fragmenting, and get it.


## The counters, built

`lost_pages()` and `refused_frees()` are compiled in rather than `#[cfg(test)]`, and the difference
between them is the point.

`refused_frees` already existed and counts a free this allocator DECLINES - an address it never
handed out, a span overlapping the free pool. That is a caller's bug and costs nothing: the frames
were never the allocator's to lose. It was test-only because a test needed it, which is the whole
reason it existed.

`lost_pages` counts the other thing, which is the one this milestone is about: a perfectly good free
that could not be RECORDED. Three paths reach it and **none of them was counted**:

- the run table at capacity (`insert_at` refuses rather than allocating from the heap it feeds);
- a quarantined page whose shootdown could not complete, one at a time;
- the same, for a whole batch.

Each now adds to the count and prints the running total beside its warning, and the boot log carries
a baseline line whether or not anything has been lost - a later non-zero reading is only worth
something if a zero one was printed too.

`a_fragmenting_workload_loses_no_pages_and_says_so` asserts the DELTA across its own churn, never
the absolute value: the counter belongs to the whole machine and seven other cores are running while
the test does. It is the guard rather than the demonstration - driving the run table to its ceiling
would mean deliberately losing real pages out of a live kernel, which is a poor trade for a test.
What it catches is a change that starts dropping frees on an ordinary workload, which is exactly how
the quarantine defect arrived: nine pages per failed load, noticed only because something happened
to print a count.

The number is not yet in `MemoryStats`, so `lsmem` cannot show it. That needs an ABI field and is a
deliberate decision rather than an oversight.


## The two tests, built

`a_fragmenting_workload_loses_no_pages_and_says_so` shreds the address space - a wide span handed
back in two interleaved passes, three times over - and asserts the DELTA of `lost_pages` across its
own work, never the absolute value. The counter belongs to the whole machine and seven other cores
are running while the test does; P02M0117 retired four tests that asserted numbers belonging to the
machine rather than to themselves.

`a_dma_buffer_still_gets_a_contiguous_span_after_the_pool_is_shredded` asks through the REAL caller.
`DmaBuffer::create_in` is what needs contiguous spans in production and it does more than call the
allocator - it charges a Domain, maps the pages, and refuses cleanly when it cannot - so a test that
called `allocate_contiguous` directly would pass over a caller that had stopped being able to use
the answer. It asks twice: a small buffer while every other page of a wide span is free (a caller
needing four contiguous pages must not be refused because the pool is untidy), and one spanning the
whole width once the rest is returned, which only a table that re-coalesced can serve.

## What is NOT done, and why it was not attempted here

The buddy allocator and the infallible-free signature that depends on it are untouched.

This is the kernel's physical memory allocator. A defect in it corrupts memory rather than failing,
and verifying it means three architectures at up to 75 minutes each. It is a milestone's worth of
work by this file's own description - the counters above are called "the cheap half" in the opening
paragraph - and it was reached at the end of a very long unattended session, which is the exact
condition P02M0117 records as "how a subtle one gets committed".

What it now has that it did not: **the measurement it asked for first**. `lost_pages` is compiled
in, printed at boot, and asserted by two tests, so the question the buddy allocator exists to answer
- how much does this actually lose - can be answered with a number before anything is rewritten, and
again afterwards to say whether it paid.


## A free that cannot fail, without replacing the allocator

The loss had one cause and it was a number: `MAX_RUNS = 8192`, described as *"sized well past what a
healthy pool fragments into"* - which is a claim about healthy pools rather than about what is
possible. Past it `insert_at` refused, the freed span was lost, and the machine got quietly smaller.

The most disjoint free runs a pool of N pages can hold is **N/2**, because two free runs must have an
allocated page between them. There is no arrangement with more. So the table is now reserved for
`worst_case_runs(total)` at boot, and a free cannot find it full.

It costs 16 bytes per two pages - about 0.2% of the pool, a megabyte on a 512 MB machine - reserved
once, never grown, and it makes `deallocate` unable to lose a frame. The signature says so, and it
draws the line the old comment blurred: a free can still be REFUSED - a double free, an address this
allocator never handed out - and those frames were never the allocator's to lose. `lost_pages()` and
`refused_frees()` count the two separately for exactly that reason.

`the_run_table_is_reserved_for_the_worst_the_pool_can_reach` pins the arithmetic, because the day it
drifts nothing else notices: the table simply starts refusing again, on a fragmented machine, weeks
later. It also asserts the table is the heap-backed one - the pre-heap seed table is fixed at 128
runs and can still lose a span, so everything above would be true of a table nobody was using if the
upgrade had silently declined.

The refusal branch in `insert_at` stays, unreachable, and says so. An argument is not a guarantee: if
the sizing is ever wrong, the alternative to that branch is writing past the end of a `Vec`.

## The buddy, built

`mem/frame/buddy.rs`. A bitmap per order over the physical extent - lowest usable frame to highest,
holes included, because a hole is simply never freed in and so reads as allocated forever. That is
what lets one buddy cover a memory map with gaps in it, and it is why the extent is the map's rather
than a power of two.

Measured on the x86_64 test guest: **1,035,451 free frames and 383 KiB of metadata** - a bit per
block per order, summed to two bits per page, about 0.009% of the pool. Reserved once at
`upgrade_to_heap` and never grown. The boot log prints both numbers.

A block of 2^k pages at index `i` has exactly one buddy, `i ^ 1`, found by xor. Merging is clearing
a bit. **There is no table to fill, so a free cannot fail** - which is the property this milestone
exists for, and it is now true by construction rather than by a reservation being big enough.

### Bitmaps rather than free lists, and why

The textbook buddy keeps a list per order so allocation is O(1) instead of a scan. Both ways to
build one here cost more than they return: intrusive lists threading `next` through the free pages
need every free page reachable through the direct map, on three architectures, forever - a
correctness dependency this allocator otherwise does not have; side arrays cost about 16 bytes per
page, twice what the run table cost, to remove a scan that is small.

Small because allocation at order k reads `pages >> k` bits: a 64-page DMA buffer scans 32 words
against a run list that could hold 65,536 entries. **That is the "without a linear scan" this
milestone asked for** - what remains is a handful of `u64` loads, not a walk of the pool.

### The scan that was not small, and the measurement that caught it

The first version had the hint and no counts, and the x86_64 suite went from **117 s to 483 s**.

The shape of a buddy is what makes that bite. A freshly seeded pool is a few huge blocks, so orders
0 through 17 are EMPTY - and an empty order can only be proved empty by reading its whole bitmap.
Every second single-page allocation did exactly that: split a big block, which lowers the low
orders' hints; consume the piece; then scan sixteen thousand words to rediscover that order 0 is
empty again.

A count per order answers "is this order empty" without reading a word. **483 s -> 112 s**, level
with the run table it replaced.

That number is also the answer to the question this milestone was left open on. The previous entry
here said the contiguous-allocation scan should be measured before a rewrite was justified, and it
was right to ask - but the measurement that mattered turned out not to be the one anticipated. What
a buddy costs is not the DMA path; it is the emptiness probe on the ordinary single-page path, and
it does not show up in a design argument at all.

### What kept the old allocator's job

The run table survives in two places and both are deliberate. The **pre-heap seed table** still
serves boot, because the frame allocator is what brings the heap up and there is nowhere to put a
bitmap before then; it is a handful of runs and a loss there is a boot-time impossibility. And the
**worst-case-sized heap table** stays as the fallback if the buddy's metadata cannot be reserved -
the weaker version of the same guarantee rather than none - and the boot log says so out loud,
because quietly running the old allocator is the kind of fallback nobody notices for a year.

Ownership checking is unchanged and still one level up: the buddy answers "is this block free",
`check_owned_free` answers "was this the caller's to give back", and they are different questions.
The double-free that the run table caught with an overlap test is now asked of the bitmap directly.

### Tests

Four in `buddy.rs`, over a made-up extent so the arithmetic is exercised without the machine's own
pool: that a span freed page-by-page in an awkward order merges back into ONE block (only observable
by then allocating it whole - a pool holding 64 separate one-page blocks refuses that); that the
rounding of a 3-page request is handed back rather than held; that a pool whose page count is not a
power of two never hands out the gap past its end; and that a free it cannot frame is refused rather
than corrupting the tree.

`the_run_table_is_reserved_for_the_worst_the_pool_can_reach` now asserts the buddy is the one
serving first, because everything else in it is about the fallback - and if the buddy failed to
build, the fallback is what the machine is running.

## What the buddy exposed: the pool contained the boot packages

The buddy went green on x86_64 at both 4 GB and 512 MB and then failed on aarch64, in one test, at
around 900 seconds: `spawn StorageService harness: BadImage`. This section is the diagnosis, because
almost none of it was the allocator and the sequence is the part worth keeping.

**What the fault actually was.** aarch64 and riscv64 boot with no memory map. Their loaders pass
`memmap: 0` - the comment in both says the memmap is "x86-only" - so their kernels fabricated one:
a single usable region from `__kernel_end` to the top of RAM. But this machine has no bootloader
module hand-off either, so the loader reads the boot packages off the volume INTO RAM above the
kernel and passes their addresses. Measured on the aarch64 test guest, they land at
`0x5bc3f000..0x5c175000` (5.3 MB) and `0x5c8d8000..0x5cc59000` (3.6 MB) - high in a 512 MB machine.
Those bytes are read for the whole life of the boot; they are where every program's ELF image comes
from. **The frame pool declared them free.**

**Why it never surfaced before.** The run table hands out the lowest free address first and never
comes back down, so within one test run it simply never climbed to `0x5bc3f000`. The buddy seeds by
framing the pool into blocks of falling order - one big block at the bottom, progressively smaller
ones toward the top - which puts the TAIL of RAM into the small orders, exactly where a single-page
allocation looks first. A few hundred allocations in, `paging::alloc_frame` handed out a page of the
boot archive and zeroed it.

So this was never a buddy bug. It was a boot bug the buddy's allocation ORDER uncovered, and it had
been shipping for as long as the loader has been reading packages into RAM.

**How it was found, in order, because three of the four steps were wrong.**

1. *"A small pool"* - x86_64 at `MEM=512M` passed all 220. Wrong.
2. *"The metadata reservation takes frames between reading the run list and seeding from it"* - a
   real hazard, restructured, and then instrumented to print how many frames it actually consumed.
   **Zero.** Wrong, and it would have been recorded as the fix if it had not been measured.
3. *"A double allocation"* - the ownership record already knows which frames are on loan, so
   `check_not_owned` was added to `take_one`/`take_contiguous` to ask at the moment of handing one
   out. A full aarch64 run to the failure: **zero double allocations.** Wrong - and the counter is
   worth keeping, because the run table could not hand the same frame out twice and a bitmap can.
4. *"The bytes are corrupt"* - which is where a canary should have gone first. Printing the header
   on failure: `1245536 bytes, header [00, 00, ...]`. The length is perfect and the content is
   zeroed, and zeroing is what `alloc_frame` does. That named the mechanism in one line.

The pattern in the three wrong answers is the same: each was a plausible defect in the code that had
just changed. The evidence that ended it came from asking what the FAILURE looked like, not from
re-reading the diff. An isolated reproduction was also tried and was misleading - the test hangs
alone on aarch64 with the buddy disabled too, so "it fails in isolation" proved nothing about the
change.

**The fix.** `arch/common/bootmem.rs`: `loader_reservations` reads the hand-off - the `BootInfo`
structure, its module descriptor array, and every module's bytes, all three of which are read after
the allocator is up - and `carve` subtracts them from the range, page-aligning outward, merging
overlaps, and truncating rather than covering a hole if it runs out of room. aarch64 and riscv64 both
use it, and both now print each reserved range at boot. The aarch64 pool went from 507 MB to 498 MB,
which is the 9 MB that was never free.

### Two real defects in the buddy, found on the way

Neither caused the failure above; both were live.

**Allocation under the allocator lock.** `allocator.runs().to_vec()` while holding it - the global
allocator's `grow` calls `frame::allocate`, which takes the lock this thread holds. On a SpinLock
that is a core spinning forever, and it presented as an aarch64 test hanging with no output. The
file states this rule twice, about the run table and about the ownership record, and the new code
broke it anyway. Fixed by seeding from a fresh read under the installing lock, with every allocation
done outside it.

**`free_span` dropped pages silently and `free_count` counted them anyway.** A block the buddy
refuses - outside the extent, or running past its end - was skipped, but the caller credited the
whole span. A pool that reports free frames no allocation can find is worse than a smaller pool.
`free_span` now returns what it took, `#[must_use]`, and the shortfall goes to `LOST_PAGES` with a
line saying so.

## Reopened: the bootstrap does not hold the invariant the milestone is named for

The same audit, 2026-08-10, on the buddy commit. Three findings against the integration rather than
the allocator; the allocator itself it read and had no objection to. One of the three was already
fixed hours earlier and is recorded above.

- [x] **Allocation under the frame lock.** `allocator.runs().to_vec()` while holding it, which is the
  deadlock the file warns about twice. Found independently the same day, from an aarch64 test that
  hung with no output, and fixed by seeding the buddy from a fresh read under the installing lock
  with every allocation done outside it. See "Two real defects in the buddy" above.

- [x] **The buddy is only attempted if the much LARGER fallback allocation succeeds.** The order is:
  compute `worst_case_runs`, reserve the run table, and on failure print "staying on the seed table,
  where a free CAN be lost" and RETURN - before the buddy's metadata is ever sized. On a 4 GiB
  machine that reservation is about 8 MiB and the buddy's bitmap is 383 KiB, so the one case where
  the buddy matters most is the case where it is never tried, and the kernel comes up on the 128-run
  seed table with the original defect live.

  The order should be: extent, then `Buddy::new`, and if it succeeds seed it from the seed runs and
  never reserve a run table at all. Only if the buddy cannot be built is the run table worth trying.

  DONE 2026-08-10: extent, then `Buddy::new`, and the worst-case table reserved only when that
  returns None. Both boot lines say which happened. This closes the next task too - the fallback is
  not emptied after the fact, it is never taken - and the assertion is in
  `the_run_table_is_reserved_for_the_worst_the_pool_can_reach`: watched failing by restoring the old
  order, which reported **8,304,048 bytes** of fallback held on a 4 GiB machine behind a boot line
  claiming 383 KiB.

- [x] **A boot that cannot hold the invariant should not be a warning.** If neither the buddy nor a
  worst-case run table can be reserved, the kernel currently prints a line and runs anyway on a table
  where a free can be silently lost. The milestone's claim is that a valid free is never lost; a
  kernel that knows it cannot keep that should fail to boot rather than keep it as a footnote.
  Deliberately listed after the reordering above, because with the buddy tried first this becomes
  nearly unreachable - which is the point.

  DONE 2026-08-10: a panic naming both reservations that failed. Reachable only on a machine too
  short of memory to reserve a few hundred kilobytes at boot, which is a machine that was not going
  to run this system anyway - and stopping there says so in one place instead of somewhere unrelated
  an hour later.

- [x] **The run table's 8 MiB is still held after the buddy takes over.** `table.clear()` empties it
  and keeps its capacity, so a 4 GiB machine reports "383 KiB of metadata" while `worst_case_runs`
  bytes stay reserved underneath. The buddy has so far ADDED 383 KiB to the 8 MiB rather than
  replacing it, and the boot line says otherwise. Drop the `Vec` outright once the buddy is
  installed, and have the reported number be the memory actually held.

  DONE 2026-08-10 by the reordering above: on the path that works the `Vec` is never created, so
  there is nothing to drop and the boot line's number is the whole of it.

### An unresolved double allocation on riscv64, and the instrument built to catch it

Recorded because it is open, not because it is understood.

A riscv64 run on 2026-08-10 printed **80 `DOUBLE ALLOCATION` lines, all naming the same page**,
inside `a_shootdown_makes_another_core_stop_using_the_old_translation`, and ended in a kernel store
page fault. The address was `0x9c0a7000` - exactly one page below the first range the boot carve
reserves, so the last page of the first usable region. That build had no injection of any kind; the
duplicates were real.

It has not reproduced. The next run passed the same test, and the difference is test ORDER: adding a
test to the frame suite moved the shootdown test from fifth to seventy-somethingth, so it no longer
runs against a freshly seeded pool. That matters here, because the buddy seeds by framing the pool
into blocks of falling order and the small orders are therefore filled from the TAIL of each region -
so the pages immediately below a carve boundary are among the first ever handed out. The failing run
was hitting exactly those pages; the passing one was not.

- [x] **Reproduce it deliberately and find it. NOT REPRODUCED - and the search changed the answer
  anyway. Everything that did not work is below, and what finally did is [the last section of this
  file](#the-search-was-moved-somewhere-it-could-be-run-fourteen-million-times).**

  Four attempts, 2026-08-10, none of which reproduced it:

  1. The test alone on riscv64 (`TEST_SELECTION`) - passes. It also passes alone with the buddy
     DISABLED, so running it alone is not a valid reproduction of anything: this test needs the
     tests before it.
  2. The test alone on aarch64, which has the same carve and the same region boundaries - passes.
  3. The exact five-test prefix of the failing run, replayed by `TEST_SELECTION` on riscv64 -
     passes.
  4. The same five with the OLD bootstrap order restored (the 8 MiB run table reserved before the
     buddy), on the theory that the reservation's allocation history was what put the pool in the
     failing state - passes.

  And the full riscv64 suite has since run green twice, 215 tests, with `frame::audit()` comparing
  the bitmap against the ownership record after every one of them.

  So the state is: eighty double allocations of one page, observed once, on the last page of the
  first usable region, in a build whose only difference from a passing one is the boot's allocation
  history - and not reproducible by any of the four ways to arrange that history deliberately. It is
  recorded rather than closed because a defect seen once and not explained is not a defect that has
  been fixed, whatever the suite says afterwards.

  What would find it next: run the full suite on riscv64 with the detector printing the ORDER the
  page was allocated at, so the state can be reconstructed rather than guessed - the boundary page is
  among the first the buddy hands out, because seeding puts each region's tail into the small orders,
  which is why it is the page that shows up and not a random one.

  **THE INSTRUMENT IS BUILT, 2026-08-12, and the run is what remains.** The detector could say THAT
  a page came out twice and nothing about the state that produced it, which is the whole question.
  It now says both handouts: the order and the allocation number of the one happening, and the order
  and allocation number the record remembers for the previous one - "handed out at order 0 as
  allocation 412, already on loan from order 0 as allocation 9310" instead of "already on loan".

  `owned_order` (one byte per frame) and `owned_seq` (four) sit beside the ownership bitmap, debug
  builds only, reserved the same way and with the same failure behaviour: a record that cannot be
  reserved leaves the detector firing and saying less, rather than taking the bitmap down with it.
  `take_contiguous` also names WHICH page of its span was already owned, since the span is what it
  reports and the page is what is wrong. 0xFF means "never handed out".

  This is left open deliberately: an instrument is not a reproduction. What closes it is a full
  riscv64 run in which the detector fires - which is the thing that has not happened again in the
  fourteen runs since, and which nothing about this change makes more likely. It makes the next
  sighting explicable instead of another paragraph like this one.

  **AND ONE DEFECT CAME OUT OF READING `insert` FOR IT, 2026-08-12.** Not the double allocation -
  saying so would be exactly the overclaim this milestone has avoided twice - but a defect in the
  same file that makes the instrument unreliable, which is worth more here than anywhere else.

  `insert` cleared the ownership record BEFORE it had established that the free was legal, and both
  refusal paths returned without putting the bits back: the buddy path's "these pages are already
  free" test and the run table's overlap test. A refused free therefore left the record saying "not
  on loan" about pages that were still out on loan to their real owner. Three consequences, and
  every one of them is worse than the free that was refused:

  - the real owner's eventual free is REFUSED by `check_owned_free`, because the record no longer
    says those pages were ever handed out - so a bad free by one caller makes a good free by another
    leak;
  - `frame::audit()` compares the record against the bitmap after every test and fires, naming
    whichever test happened to be running rather than the free that did it;
  - `check_not_owned` - the double-ALLOCATION detector, the instrument above - reads those pages as
    nobody's. The one thing that would explain a double allocation is blinded for exactly the pages
    a bad free just touched.

  Both paths now check everything first and mutate nothing until the operation is known to be legal.

  HOW REACHABLE IT IS, stated rather than implied: the refusal only runs when the record and the
  bitmap already disagree, which cannot happen while the allocator is consistent. So this is a
  latency amplifier rather than a first cause - it cannot start a divergence, it can only widen one
  and hide it. `a_refused_free_leaves_the_ownership_record_it_found` therefore INJECTS the

## The search was moved somewhere it could be run fourteen million times

2026-08-14. The sighting was never reproduced. What changed is that the search stopped costing a
guest boot, and it found a different defect on the same path - one that makes the sighting's exact
signature unreachable from any caller, which is a stronger statement than an explanation of one
event would have been.

**`src/buddy` is the allocator, moved out of the kernel.** It is pure bitmap arithmetic with no
kernel dependency at all, and inside `kernel::mem::frame` the only way to exercise it was to boot: a
few thousand allocations in whatever order that boot produced, at up to ninety minutes a run on the
target the sighting happened on. Four deliberate attempts to arrange the failing boot's allocation
history are recorded above; each of them bought one ordering.

On a host it takes **6.4 million operations in the sighting's own pool shape** - a 512 MB extent
carved into regions around the loader's reservations, so a region's tail sits immediately below a
hole exactly as `0x9c0a7000` did - plus two million more on a pool shredded and fully returned, plus
six million across two thousand randomly shaped pools with awkward extents and holes of every size.
**14.4 million operations in 51 seconds** (`BUDDY_SOAK=100`, release), against a model that knows who
holds every page; and 3.6 million more in 23 seconds in a DEBUG build, where the allocator's own
`debug_assert`s about writing past the end of an order's bitmap are live and where the kernel's test
suite runs. Every one of them clean.

The gate does not run the campaign. `check.sh` runs the same tests at their default size, which is a
few seconds and enough that a defect in this arithmetic is unlikely to survive a day of ordinary
development; `BUDDY_SOAK` is what multiplies it, and the number above is the answer it gave once
rather than a cost paid on every sweep.

### The property no in-kernel check can make

A double allocation is one page in TWO free blocks, and nothing in the kernel can see that before it
happens. `free_pages()` is a total. `is_free_page` is one page. `frame::audit()` compares the
ownership record's count against the buddy's - and a page counted twice by both stays consistent with
itself. The state is invisible right up to the moment two allocations return the same address, which
is where the sighting was found and is why it had nothing attached to it.

`for_each_free_block` walks the whole free set, so the host test asserts the property directly:
after every operation, no page is covered by more than one free block, the walk's total equals the
maintained count, and both agree with the model page for page.

### What that found, and a belief this milestone had been carrying

**`Buddy::free` did not refuse a free of something already free.** Deliberately - the frame allocator
above it asks first, because it has an ownership record to keep consistent and must decide before it
mutates anything. But "the caller checks" is not the same as "it cannot happen", and the seeding path
calls `free_span` with no such caller above it.

The two shapes of that mistake are different defects, and the first version of the test asserting
them FAILED - which is how the correction was found:

- freeing a page a LARGER free block already covers puts the small bit under the big block. The page
  is in the free set twice and the next two allocations that reach it both get it. **That is the
  sighting's signature.**
- freeing the same block at the SAME order sets a bit that is already set, which folds into nothing,
  while `free_pages` counts it anyway. That is a pool reporting a page no allocation can find - the
  run table's old failure mode arriving from the other direction, and NOT a duplication.

This file had been saying "a double free" as though it were one thing. It is two, and only one of
them is this milestone's defect.

Both are refused now, inside `free`, at the cost of one masked bitmap scan - and the check asks the
right question rather than an easier one: not "is this block's own bit set", nor "is its first page
free", but does the block overlap ANY free block at any order, including a smaller one sitting inside
it. That third case is the one a per-page test on the first page misses entirely.

- [x] **Put the already-free refusal in the allocator, not only above it.** DONE 2026-08-14.
  `a_double_free_is_refused_and_this_is_what_it_prevents` shows the state it prevents through a
  test-only door (`free_ignoring_double`), which is the only way to show it now that the rule exists:
  two allocations, the same address.

- [x] **And keep the caller's guard, which answers a different question.** `insert` still asks
  `any_free` over the whole span before it touches the ownership record, because a refusal must leave
  the state it found - the defect this milestone already recorded from the other side. The two are
  not redundant: one keeps the record consistent, the other keeps the bitmap consistent when a caller
  forgets.

### What this does and does not close

eighty times, and this file's own standard - a defect seen once and not explained is not one that has

## Fourth audit (2026-08-16): `AI/audit/buddy.md`

Four findings. The second is this milestone's own sentence - a free that loses the memory it frees -
arriving through a path the milestone did not cover.

- [x] **`free_span` discards a whole block when any part of it is already free (BUD-002).**
  VERIFIED: the loop calls `self.free(at, order)` and then advances `at += taken * PAGE_SIZE; left
  -= taken` WHETHER OR NOT the free was accepted. `free` refuses a block that overlaps any existing
  free block, so one already-free page inside a chosen order-3 block discards the other seven -
  seven valid pages that overlapped nothing, gone, with only an aggregate shortfall to show for it.
  Seed page 4 of an otherwise allocated 8-page extent and call `free_span(base, 8)`: it returns 0.
  This contradicts the overlapping-seed contract the crate's own tests describe, whose fixture
  happens to put the overlap on a boundary where the greedy framing separates old from new. Either
  subdivide a candidate block until the free and allocated parts are separate, or refuse the whole
  call before mutating anything - but not the present middle.
- [x] **`Buddy::new` accepts unaligned, zero-length and wrapping extents (BUD-001).** VERIFIED: it
  sizes the bitmap and returns a live allocator with no check on alignment, zero length, or
  `base + pages * PAGE_SIZE`. `free` then tests alignment RELATIVE to `self.base`, so an unaligned
  base makes equally unaligned physical addresses pass. The kernel's current caller supplies
  page-granular runs, so this is a public-API contract gap rather than a live defect - but `new`
  returns `Option` precisely to be the validation boundary.
- [x] **Span queries and frees are not bounded by the allocator's extent (BUD-003).** VERIFIED:
  `free_span` runs `while left > 0` with an unchecked `at +=`, so a caller error becomes unbounded
  work with the frame-allocator lock held rather than a bounded refusal.
- [x] **The documented metadata cost is wrong by a factor of two (BUD-004).** VERIFIED by
  arithmetic: the module comment says "2 bits per page, `pages / 4` bytes. 128 KiB on a 4 GiB
  machine", and with `PAGE_SIZE = 4096` a 4 GiB extent is 1,048,576 pages, so `pages / 4` is 262,144
  bytes - 256 KiB. The implementation reports the real figure; only the prose is wrong, and boot

### Resolution of all four buddy findings (2026-08-16)

**A refused block is subdivided rather than skipped.** `free_span` framed a span into the largest
aligned blocks and advanced by the whole block whether `free` accepted it or not, so one already-free
page inside an order-3 block discarded the other seven - seven pages that overlapped nothing and
that no allocation could find again. `free_block_or_split` now splits a refused block down to order
0, where a refusal really does mean "already free". That is partial insertion, which is what the
overlapping-seed contract promises and what a seeder needs.

WATCHED TO FAIL AT EVERY POSITION. `a_partly_overlapping_span_keeps_every_page_that_was_not_already_free`
seeds each of the eight pages in turn and requires seven newly taken, the whole extent free, every
page represented exactly ONCE across the free set, and all eight allocatable afterwards. Restoring
the skip turns it red at page 0. The original fixture passed because its overlap fell on a boundary
where the greedy framing separates the old page from the new ones.

**Construction validates the extent.** `new` returns `Option` in order to be that boundary and
checked nothing: zero pages, an unaligned base and a byte length that overflows are all refused now,
and the per-order word count is accumulated with `checked_add`. The unaligned case is the sharpest,
because `free` checks alignment RELATIVE to `self.base` - so an unaligned base let equally unaligned
addresses through every later check and `Buddy::new(1, 1)` could hand out physical address 1.

**Span queries are bounded by the extent, not by the caller's count.** `any_free` ran one iteration
per page of whatever it was given with unchecked address arithmetic, and `free_span` looped until
the caller's count ran out however far past the end it had gone - a caller error became unbounded
work with the frame allocator's lock held. Both intersect with the extent first. The test asks both
with `u64::MAX` and would hang the runner rather than fail if the bound were missing.

**The metadata example is derived.** It said 128 KiB for a 4 GiB machine; `pages / 4` over 1,048,576
pages is 256 KiB. `the_metadata_cost_is_what_the_module_says_it_is` computes it from
`metadata_bytes()` so the prose cannot drift from the implementation again.
