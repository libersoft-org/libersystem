# P02M0170 - Verification evidence belongs to one revision and one immutable test artifact

Status: PLANNED. VERIFICATION INTEGRITY FOLLOW-UP. NOT A COVERAGE REDUCTION.

## Goal

Close the remaining evidence-integrity gap after P02M0167 and make a release run produce one
machine-readable dossier proving which immutable revision, toolchain, profiles, checks and artifacts
were actually exercised.

This milestone does not rebuild the selector. Ordinary scoped verification already consults the
shadow/trust store, candidate activation is already bound to the model hash, and `--release` already
ignores selection. Those are prerequisites to preserve.

## What is there now

The selection-specific executable race is CLOSED, and the plan must not re-specify it. Under the
same-architecture build lock the harness already compiles with `--message-format=json`, reads the
exact executable Cargo produced, copies it to a run-unique path while the lock is still held, and
invokes the QEMU runner directly on that copy rather than letting `cargo test` re-resolve the shared
target directory. What remains of that item is narrower than a mechanism: the copy is an ordinary
writable file, its digest is never computed, and nothing downstream is bound to it.

The rest of the release path is where the evidence gap actually is:

- `run_full` is `build.sh --arch all`, the three guest suites, then `check.sh`. Nothing on that path
  runs `image.sh`, while the Secure Boot gate needs `.build/boot/libersystem.iso` and the
  virtio-IOMMU gate needs both that ISO and a build receipt matching the current tree. A genuinely
  clean snapshot therefore cannot run its own mandatory gates, and a reused workspace can pass one
  of them against media built from another tree, because that gate only checks the file exists.
- A catalog `Check` has `id`, `kind`, `covers`, `variants` and `command` and nothing else. It cannot
  say that a row is release-required, what produces its inputs, what it must emit, or which rows are
  concrete profiles rather than umbrella or fallback work. Umbrella gates are deliberately excluded
  from the catalog, and the two `GuestFallback` rows carry no `covers` and are skipped by `select` -
  so "every release obligation is derived from the catalog" is not currently expressible.
- No producer publishes evidence. `check.sh` records umbrella output and status, the multi-boot
  gates keep their phase logs in a `mktemp -d` removed by an EXIT trap - including on failure -
  `verify.sh` records per-key outcome and duration only, and the harness prints result-log paths
  with no envelope naming the source, the staged ELF, the medium or the plan-item key.
- The three development rows invoke scripts that require a guest left running by `./dev.sh up`,
  their `requires` list is empty, and no release path starts one. `check-development-build.sh`
  deliberately compiles and does not boot.
- Two different source identities exist and disagree: the shell helper hashes selected directories
  and extensions, while the model verifier hashes HEAD plus the working tree's changed paths and
  bytes. Neither covers firmware, the QEMU binary, feature flags or the environment overrides that
  select them.
- The detached sweep publishes nothing. Its worktree is removed by an exit trap whether it passed or
  failed, so evidence does not outlive the snapshot that produced it.

## Work

- [ ] **M1 - the staged executable is immutable and bound, not merely private.** Keep the existing
  locked build, JSON artifact discovery, under-lock copy and direct runner invocation exactly as
  they are. Add the three things that make the copy evidence rather than a convenience: publish it
  atomically, make it read-only (or otherwise immutable for the life of the run), and compute its
  digest under the same lock. Every downstream step - the medium build, the guest launch, the result
  log and the dossier row - names that digest.

  **AND CONTENT ADDRESSING IS DETECTION, NOT STABILISATION** (corrected 2026-08-31, and this time in
  M1 rather than only in M2). An earlier version rejected any protection of media construction on the
  grounds that the medium is content-addressed. That is the wrong conclusion from a true premise:
  `mkimage.sh` holds a lock over its own assembly, and its own comment says its PRODUCERS are not
  covered by it - so an input can be replaced while the image is being written, and what the builder
  implements is to recompute the key afterwards and DIE. That makes a corrupt medium impossible and
  makes a concurrent run FAIL, which is exactly what M2 forbids. P02M0167's history records this
  overlap making one run fail.

  So the medium gets a stable boundary rather than a check after the fact. ONE of:

    SNAPSHOT   every medium INPUT - the staged ELF, the volume, the packages, the loader, the
                 manifest and the fallback bootstrap set - is copied to a run-private immutable path
                 before assembly, and assembly reads only those paths. This is the technique M1
                 already applies to the ELF, extended to the rest, and it is the preferred answer
                 because it serialises nothing.
    SERIALISE  or every run passes through one defined snapshot point before assembly, held for the
                 duration of the copy rather than the duration of the build.

  **AND ACQUISITION IS THE OTHER RACE; NEITHER OPTION CLOSES IT BY ITSELF** (corrected 2026-08-31).
  Both options above stabilise what happens AFTER the inputs are in hand, and the previous version
  stopped there. SNAPSHOT copies live paths, and a producer can replace or rewrite one of those paths
  WHILE the copy is running; SERIALISE holds off other runs and holds off no producer at all. So the
  race is not removed, it is moved into acquisition - and it comes back in two forms the after-the-
  fact key check cannot see: a TORN read, where a producer rewrites an input with byte-identical
  content and the copy catches it half-written, so the before and after keys agree while describing
  bytes the medium was not built from; and a MIXED-GENERATION set, where one input is copied before a
  producer's publication and the next after it, and every individual input is intact.

  Acquisition is therefore made atomic with respect to PRODUCERS, not only with respect to other
  consumers. Both halves are required and both are cheap:

    ATOMIC PUBLICATION   every producer of a medium input publishes by writing a temporary file and
                           RENAMING it into place, so a reader observes the whole previous version or
                           the whole new one and never a partial file. This is what removes the torn
                           read, and it removes it for readers this milestone does not own.
    A SNAPSHOT POINT     acquisition and producer publication exclude each other, over the one lock
      PRODUCERS TAKE       that already serialises the tree's build steps. Held for the duration of
                           the COPY only - never across assembly and never across a compile, which is
                           the exclusion this milestone continues to refuse. This is what removes the
                           mixed-generation set, which atomic rename alone cannot: intact inputs from
                           two different generations are each individually whole.

  The recorded per-input digests stay, and stop being the argument: they are what proves after the
  fact that the boundary held, not what makes it hold.

  AND THE HANDOFF TO THE GUEST BINDS THE OBJECT, NOT THE NAME - the same rule M8 states for tools and
  firmware, and the medium was left on the weaker one (corrected 2026-09-01). A previous version
  recorded the assembled medium's digest and rechecked the writable ISO PATHNAME "at the moment of
  invocation". M8 explains at length why that is not enough: rehashing a name and then using the name
  is a check-then-use race, and the medium's case is worse than the tools' because QEMU is handed
  `-cdrom "$iso"` as a pathname and opens it AFTER the exec - so the window is not a few syscalls, it
  spans process startup.

  So the medium takes one of M8's two forms, for the same reasons: a RUN-PRIVATE IMMUTABLE COPY that
  QEMU is pointed at, or a HELD DESCRIPTOR opened once, hashed through that descriptor and inherited
  by QEMU. The descriptor form is preferred where the invocation accepts one; the copy is the
  fallback. The digest recheck stays as a second signal and stops being the argument, which is what
  M8 already says for every other input class. One rule for every input the dossier names is also the
  point: a reader should not have to work out why the medium is bound more weakly than the firmware
  that boots it.

  What stays refused is holding the CARGO build lock across assembly: it serialises compilation for a
  property that belongs to the medium's inputs, not to the compiler.

- [ ] **M2 - concurrency proves identity, not merely absence of a compiler crash.** Run two suites
  for the same architecture concurrently with disjoint selections/tags. Each result must name and
  execute exactly its own catalog keys and staged-executable digest, while both guests overlap in
  time - and BOTH SUCCEED, which is the assertion that distinguishes a stable boundary from a
  collision the builder merely detects. Mutations that must fail the gate: removing the staging step,
  making the staged copy writable and replacing it mid-run, dropping the digest binding so a result
  cannot be tied to the binary that produced it, replacing a medium INPUT during a concurrent
  assembly, replacing a medium input during ACQUISITION rather than during assembly - which is the
  window M1's snapshot point exists for and which the assembly-time mutation does not reach -
  publishing an input non-atomically so that a copy can observe it half-written, and replacing the
  assembled medium at its pathname between assembly and guest launch.
  AND THAT LAST ONE IS PLACED IN THE WINDOW THAT MATTERS (added 2026-09-01): after the medium has been
  hashed and BEFORE QEMU opens it - which, because QEMU opens its `-cdrom` after the exec, means
  during process startup rather than before it. A mutation placed anywhere earlier tests the recheck
  and not the binding, and the recheck was never the part in doubt.
  Keep the already content-addressed read-only fixtures and run-unique writable paths; this item
  closes only the accepted selection-specific executable remainder from P02M0167.

- [ ] **M3 - preserve the existing strict scoped-verification contract with direct regressions.**
  Pin that an ordinary scoped run is `TRUSTED` only when current-model shadow evidence covers its
  change class and targets; otherwise it exits distinctly as `SHADOW` unless the caller explicitly
  chooses `--allow-shadow`. Pin that a frozen candidate cannot activate against different canonical
  inputs or evidence from another model. If the current implementation satisfies these tests, no
  selector rewrite is performed.

- [ ] **M4 - the catalog can express a release obligation.** Extend the catalog entry so the release
  set is derivable from it and independently checkable:

  - a stable fully qualified key of plan item and variant, which is what every result names;
  - a closed CLASS, so a concrete required profile, an umbrella name and a fallback row are
    distinguishable by data rather than by convention;
  - a RELEASE-REQUIRED bit, set from a declared class rather than per row, so deleting one row
    cannot quietly shrink the obligation;
  - PREREQUISITES and PRODUCERS, so an artifact-consuming gate names the step that must build its
    input; and
  - the ARTIFACT INPUTS each row consumes and the EVIDENCE it must publish.

  Validate the derived catalog against invariants that do not come from the catalog itself:
  every supported architecture appears in every class that claims to be per target, every
  release-required class has at least its declared cardinality, and no release-required row is an
  umbrella or a fallback.

  **AND AGAINST A FROZEN KEY SET, BECAUSE CARDINALITY INVARIANTS DO NOT DETECT A SUBSTITUTION**
  (added 2026-08-31). Architecture presence and a minimum count are both preserved by deleting one
  mandatory row and inserting or relabelling a different row of the same class - so the catalog-derived
  expectation blesses a set that is not the one the release requires. A stable fully qualified key
  identifies a row; it does not say which rows are OBLIGATORY.

  So the release set is a CLOSED, CHECKED-IN LIST of required keys and variants, reviewed as its own
  artifact, and the derived catalog is compared against it exactly: a required key absent from the
  catalog fails, and a catalog row claiming to be release-required that is not on the list fails.
  Adding a genuinely new required profile is an edit to that list, which is the point - it makes the
  addition a reviewed act rather than a side effect of a catalog change.

  Mutations that must fail before any work executes: deleting a mandatory row, reclassifying one out
  of the release set, and REPLACING one with a different row of the same class and cardinality.

- [ ] **M5 - the shipping images are built work, not found work.** Put every shipping-image
  construction the mandatory gates consume into the catalog as producer rows with their own keys,
  and express the prerequisite edges from the gates that read them. The release run builds them and
  passes the resulting run-private immutable paths and digests to the dependent gates; a gate binds
  its result to the exact image digest recorded in the dossier and does not discover a shared
  `.build/boot` artifact by convention. A gate whose named input was not produced by this run is a
  failure, not a skip.

- [ ] **M6 - the development rows have a runnable lifecycle.** Give the development guest explicit
  setup, build, immutable-image, boot, readiness, test and teardown steps - or one self-contained
  gate that owns all of them - with run-private sockets, disks, variable state and logs, and
  guaranteed teardown. Declare those steps as the prerequisites of the three development checks so
  they can no longer depend on a guest a person happened to leave running. Record the exact boot
  artifact digest in every development result. Keep `check-development-build.sh` as the compile-only
  gate it is; it is not evidence that the development configuration boots.

- [ ] **M7 - evidence is published by producers into one envelope.** Define a run-private,
  atomically published, machine-readable envelope: run ID, the exact plan-item/variant key, the
  revision and configuration identity from M8, every input artifact path and digest, outcome,
  duration, and the paths and digests of every result log. Update each gate and guest producer to
  publish it BEFORE its cleanup runs.

  **AND PUBLISHING A PATH IS NOT PRESERVING A LOG** (corrected 2026-08-30). The multi-boot gates keep
  their phase logs under a `mktemp -d` removed by an EXIT trap, so an envelope recording the path and
  digest of such a log describes a file that no longer exists by the time the dossier is read - and
  on a FAILING gate, which is when the log matters, the trap still fires. The producer therefore
  COPIES THE LOG BYTES into the durable run-owned output before cleanup, and the envelope references
  that stored object rather than the temporary path. The regression is explicit: after a gate fails
  and its process has exited, every log its envelope names is still readable and still matches its
  recorded digest. The collector rejects duplicate,
  unknown, missing, cross-run and stale envelopes. A required key with no envelope is a failure and
  is reported as one, distinctly from a key whose envelope records a failure.

- [ ] **M8 - identity is a contract, not a label.** Define ONE source identity and use it in both
  places that currently answer differently: NUL-safe over tracked path, mode and bytes, plus
  submodules, lockfiles and declared generated inputs - or, for a clean detached snapshot,
  explicitly the Git tree identity, labelled as such. Define a closed influencing-input manifest:
  resolved tool paths with hashes and versions, the Rust/Cargo lock identity, firmware image hashes
  rather than package names, target/feature/profile flags, and the exact list of environment
  variables permitted to influence the run. An undeclared override is refused.

  **AND BEFORE/AFTER IS NOT IMMUTABILITY** (corrected 2026-08-30). A previous version verified the
  source identity before and after the run and called that sufficient. It is not: a detached worktree
  stays writable, so a file can be changed, consumed by a producer, and restored before the post-check
  - and a Git TREE identity does not change for an ordinary worktree edit at all, so the check can be
  blind to the very edit it is looking for. The snapshot is therefore made GENUINELY NON-WRITABLE for
  the run, or each producer is bound to verified immutable input bytes it reads through a path nothing
  else can replace. The before/after check stays as a cheap second signal and stops being the
  argument. M10 gains the matching regression: MUTATE-USE-RESTORE, in which a source file is modified,
  consumed by a producer, and restored before the run ends - which the generic in-progress mutation
  fixture does not cover.

  **AND THE MANIFEST BINDS THE BYTES USED, NOT ONLY THE BYTES SEEN ONCE** (corrected 2026-08-31). The
  influencing-input manifest above records resolved tool paths, hashes and firmware image hashes at
  ONE moment, and the immutability rule and the mutate-use-restore regression that follow it cover
  only the SOURCE snapshot. Nothing binds a recorded tool or firmware hash to the bytes that later
  execute: the harness resolves and executes QEMU through `PATH` after identity collection, and QEMU
  opens the environment-selected OVMF image later still. A compiler, a QEMU executable or a firmware
  image that is replaced after collection and restored before the post-check therefore makes the
  dossier name bytes the run did not use - and it does so through the same mutate-use-restore shape
  the source half already refuses, on inputs the source half does not cover.

  So every recorded tool and firmware image is BOUND TO THE BYTES THAT WERE VERIFIED, and re-hashing a
  PATHNAME is not that (corrected 2026-08-31). An earlier version made re-hashing at the moment of
  invocation the requirement and an immutable copy merely an acceptable stronger answer. That is a
  check-then-use race and it is the same shape as the defect it was written to close: the harness
  execs QEMU by pathname after its arguments are built, and hands QEMU the OVMF PATHNAME for the
  firmware to open later still. Either can be replaced between the hash and the `execve` - or between
  the hash and QEMU's own `open`, which is later again - and restored afterwards, so the dossier
  names bytes the run did not use and the post-check agrees. A window narrowed from "the whole run"
  to "a few syscalls" is still the window.

  So the binding is to the OBJECT rather than to the name, and one of these two is mandatory:

    A VERIFIED COPY     the tool or firmware image is copied to a run-private immutable path, hashed
                          THERE, and used only from there - the technique M1 already applies to the
                          staged executable and the medium inputs
    A HELD DESCRIPTOR   or the file is opened ONCE, hashed through that descriptor, and used through
                          that same descriptor - `fexecve` or `/proc/self/fd/N` for the executable,
                          and an inherited descriptor for a firmware image QEMU opens - so the bytes
                          verified and the bytes used are the same object whatever happens to the
                          name

  The descriptor form is the cheaper one and is preferred where the consumer accepts a descriptor;
  the copy is the fallback where it does not. Re-hashing the path stays as a second signal and stops
  being the argument, exactly as the before/after source check did.

  AND MUTATE-USE-RESTORE EXTENDS BEYOND SOURCE FILES, WITH ITS MUTATION IN THE WINDOW THAT MATTERS:
  the regression covers a replaced-and-restored TOOL and a replaced-and-restored FIRMWARE IMAGE as
  well as a source file - the three input classes the identity block claims, and one fixture cannot
  stand for all of them - and each mutation happens AFTER the hash and BEFORE the use, which is the
  only placement that distinguishes a bound object from a checked name. A fixture that mutates before
  the hash tests nothing this correction is about.

- [ ] **M9 - one immutable release run emits one durable dossier.** Run from a clean detached
  worktree or an equivalent source snapshot. The dossier contains, for every release-required key at
  that revision, the key, outcome, duration, result-log and artifact digests, and the M8 identity
  block. A required key that is absent, skipped, unparsable, or represented only by a stale or
  cross-run envelope makes the release run fail. Existing `check.sh` gates may supply the evidence,
  but their presence in a large umbrella command is not inferred from a zero exit code.

  Publish into a durable output root OUTSIDE the disposable worktree, in a directory named by a
  collision-free run ID, finalized atomically and immutably. A failed or incomplete run keeps its
  evidence with an explicit state rather than losing it with the snapshot. The dossier records both
  the audited snapshot identity and the publisher version.

- [ ] **M10 - the report is fail-closed and reproducible.** Host fixtures delete one required
  profile result, substitute a log from another commit/artifact/run, delete a required catalog row,
  change the tree while a run is in progress, and corrupt the report. Each is refused, and each with
  its own distinguishable reason. Re-rendering a completed dossier from the same recorded result set
  is byte-for-byte deterministic apart from a clearly separated invocation timestamp.

## Definition of done

- Concurrent same-architecture selections cannot compile, package or boot one another's kernel, and
  each result is bound to the digest of the binary it ran.
- The ordinary scoped path retains its current trust/shadow behavior.
- A release run builds every artifact its mandatory gates consume, and no gate reads an artifact
  this run did not produce.
- A release has one durable report tied to one immutable revision, one identity block and one
  artifact set, and the report proves every release-required key ran successfully rather than
  recording an umbrella exit code. A required key with no evidence fails the run.

## What this milestone refuses

- Git-host branch protection, required-status configuration, release publishing or key custody.
- Running the full release matrix for every ordinary source edit.
- New selector heuristics, lower trust thresholds, or a second shadow/candidate model.
- A general CI system. The envelope, the class model and the identity manifest exist to make ONE
  release run's claim checkable; they are not a scheduler, a dashboard or an artifact store.
