## Why this is a milestone and not a task list

The engine has a decode stage and an execution stage and nothing between them. `Instance::new` takes
a `Module` that has been parsed and structurally decoded, and runs it. WebAssembly's own design puts
a VALIDATION pass there, and every one of the findings below is either a check that pass would make
or a resource bound that only makes sense once it exists.

Adding the checks one at a time to the decoder and the interpreter is how a validator gets written
badly: each check ends up in whichever pass happened to be convenient, the invariants are stated
nowhere, and the next instruction added is validated by whoever remembers. The shape that works is
the specification's:

```
bytes -> Parser -> Module -> VALIDATOR -> ValidatedModule -> Instance::new -> Interpreter
```

with `Instance::new` unable to accept anything but a `ValidatedModule`, so the type system carries
the guarantee rather than a convention.

This is also why the audit's own summary is worth repeating: the new checks in `component_host` are
good and they are a door. The wall beside them is this.

## What the boundary above already does, and what it cannot do

`world::resolve` requires an import to match by name AND declared signature, and `component_host`
refuses a module at instantiation when any import does not resolve. That is a real improvement and
it is correctly credited in [P02M0130](P02M0130.md).

It constrains what a module DECLARES. It does not constrain what reaches the host at call time,
because `Value::as_i32` converts every variant:

```rust
pub fn as_i32(self) -> i32 {
    match self {
        Value::I32(v) => v,
        Value::I64(v) => v as i32,
        Value::F32(v) => v as i32,
        Value::F64(v) => v as i32,
    }
}
```

`src/wasm/src/interp.rs:25`. A module may declare `(param i32 i32)` correctly, push two `F64`s in a
body no validator ever type-checked, and `window` will convert them. A conforming validator refuses
that module; this engine runs it.

The cheap half of the answer belongs in the host and is recorded in [P02M0130](P02M0130.md) - match
on `[Value::I32(ptr), Value::I32(len)]` and trap otherwise. The real answer is here.

## The validator

- [x] **A validation pass, and a type that proves it ran.** `validate(Module) -> Result<ValidatedModule, ValidationError>`,
  with `Instance::new` taking only a `ValidatedModule`. Everything below is either a rule this pass
  enforces or a bound it makes meaningful, and each should be added with a module that violates it
  and is watched to be refused.

  DONE 2026-08-12. `src/wasm/src/validate.rs`: `validate(Module) -> Result<ValidatedModule,
  ValidationError>`, and `Instance::new(&ValidatedModule) -> Result<Instance, Trap>`. There is no
  other constructor, so the type system carries the guarantee: nothing can reach the interpreter
  without having been checked. `ValidatedModule` also holds the decoded bodies, because validation
  walks the instruction stream anyway and decoding twice would let the two walks disagree.

- [x] **Type-check every function body** against its declared signature: operand stack types through
  every instruction, block and loop parameter and result types, `br`/`br_if`/`br_table` label arity,
  the value types `select` produces, and the stack shape at every `end`. This is the rule that makes
  the host's declared-signature check mean something at call time.

  DONE 2026-08-12. An operand-stack simulation with the specification's polymorphic `Unknown` after
  `unreachable` and unconditional branches: block/loop/if parameter and result types, `br`/`br_if`/
  `br_table` label arity (and that every `br_table` arm carries the same thing), `select`'s two arms
  agreeing, the stack shape at every `end`, and one signature table for the whole numeric opcode
  block - so an opcode the interpreter can execute and the validator cannot type is a refusal rather
  than an unchecked instruction.

  One honest limit, stated in the code: the decoder records block ARITIES rather than types, so a
  single anonymous block result is checked for its count and left to unify. Recovering the exact
  type means the decoder keeping it, which is a change to the `Instr` encoding.

- [x] **Type-check constant expressions** - global initialisers, data and element offsets - rather
  than evaluating whatever the bytes contain.

  DONE 2026-08-12. `const_expr` returns the type it produced; a global whose initialiser is not of
  its declared type is refused, and every offset goes through `const_offset`, which requires an
  `i32`.

- [x] **Validate every index at validation time**: function, type, table, memory, global, local and
  label. Today an out-of-range index is a trap when execution reaches it, which means a module can
  be instantiated and partially run before it is known to be malformed.

  DONE 2026-08-12. Function, type, table, memory, global, local and label - all at validation. An
  out-of-range index used to be a trap when execution reached it, which meant a module could be
  instantiated and partially run before it was known to be malformed.

## The rules the parser does not enforce

- [x] **Bound a function body's reader to the body.** `parse_code` computes `body_end` and checks it
  against the buffer (`src/wasm/src/parser.rs:350`), then reads the local declarations through the
  MAIN reader (`:355`) before taking `r.bytes(body_end - r.pos)` (`:364`). A declaration list that
  runs past `body_end` therefore reaches that subtraction with `r.pos > body_end` - a `usize`
  underflow, which is a panic with overflow checks on and an enormous length without them. A
  sub-reader limited to the body makes the whole question go away.

  DONE 2026-08-12. `parse_code` builds a sub-reader over `buf[..body_end]`, so nothing inside the
  body can read past it and the `body_end - r.pos` subtraction that could underflow is gone. The
  local-group count is also bounded against `MAX_LOCALS` rather than pushed in an unbounded loop.

- [x] **Section order, uniqueness and the known set.** A module may today repeat a section, present
  them out of order, or carry a standard section this parser does not know and have it skipped by
  its declared size - which is correct for CUSTOM sections and wrong for every other kind.

  DONE 2026-08-12. Non-custom sections must be strictly increasing by id, which enforces order and
  uniqueness in one comparison, and an id above 12 is refused rather than skipped - skipping a
  standard section means running a module whose declared contents were never read. Custom sections
  (id 0) stay unrestricted, which is what the format says.

- [x] **The function and code section counts must agree**, and a code entry must correspond to a
  declared function.

  DONE 2026-08-12. `parse_code` refuses a count that differs from the function section's, and
  `parse` refuses a declared function left with no body.

- [x] **Reject trailing bytes inside a function body** rather than ignoring whatever follows the
  final `end`.

  DONE 2026-08-12. The decoder refuses anything after the body's final `end`.

- [x] **Canonical LEB128.** Widths are not checked, so a value may be encoded with redundant
  continuation bytes - two spellings of the same module, which matters the moment anything hashes or
  signs one.

  DONE 2026-08-12, both signed and unsigned. The unsigned reader refuses a redundant trailing zero
  byte and a value that does not fit in 32 bits; the signed one refuses a redundant sign byte.

- [x] **The memory index immediate** is decoded wrongly, and alignment immediates are not validated
  against the access width.

  DONE 2026-08-12. The memory index is read as the LEB128 `u32` it is - it was read as one BYTE, so
  a multi-byte encoding left the reader short of the next opcode - and any value but 0 is refused.
  Alignment immediates are checked against the access width: `2^align` may not exceed it.

- [x] **Refuse a second `else`** for one `if`.

  DONE 2026-08-12, in the decoder and again in the validator. The second `else` overwrote the
  first's recorded jump, so the then-branch fell into the second arm and the first became
  unreachable code nothing had said was unreachable.

- [x] **The start section is skipped by its declared size** (`src/wasm/src/parser.rs:4` says so) and
  `Instance::new` never runs one. Either implement it or refuse a module that carries one - what it
  must not be is silently ignored, because a module whose initialisation never happened is a module
  running in a state its author never wrote.

  DONE 2026-08-12, by REFUSING it - the honest half of "implement it or refuse it". This engine's
  components are called through their exports and none declares a start function, so implementing it
  would be untested code; skipping it was the one answer that is certainly wrong, because a module
  whose initialisation never happened then ran in a state its author never wrote.

## The rules the interpreter does not enforce

- [x] **`global.set` ignores mutability.** `src/wasm/src/interp.rs:324` writes the global without
  consulting `Global.mutable`, which the parser records and nothing reads. An immutable global is a
  constant a module may rely on; here any module can change any of them.

  DONE 2026-08-12, at validation. An immutable global is a constant a module may rely on; the parser
  recorded `mutable` and nothing read it, so any module could change any global.

- [x] **`memory.grow` is a guest-driven infallible allocation.** `src/wasm/src/interp.rs:394` does
  `memory.resize(memory.len() + delta * PAGE, 0)`: the declared maximum is not consulted, `-1` is
  never returned, the resize cannot fail gracefully, and `delta` comes off the guest's stack. A
  module asking to grow by a large number of pages does not get a failure code - it takes the host
  process down. That is a denial of service reachable from any component, and it is the single most
  practical defect in this list.

  DONE 2026-08-12, and it needed the parser as well as the interpreter: the memory section read the
  declared maximum and threw it away (`let _max`), so there was nothing for `memory.grow` to honour.
  `Module::memory_max_pages` keeps it, and a maximum below the minimum is now a parse error.

  All four reasons to refuse answer -1 and leave the memory alone, which is what the specification
  says and what a guest allocator is written to handle: arithmetic that would wrap, the module's own
  maximum, `MAX_MEMORY_PAGES` (1024 pages = 64 MB, the HOST's limit whatever the module declares),
  and a `try_reserve` the host cannot satisfy.

  `memory_grow_is_bounded_and_answers_minus_one` covers an ordinary grow, the host ceiling, a
  `0xffff_ffff` delta and a module-declared maximum. Watched to fail without the bound: the ceiling
  case answered `I32(1)` - the grow attempted - instead of `I32(-1)`.
- [x] **Element segments may create or extend a table** rather than being bounded by the table's
  declared limits.

  DONE 2026-08-12. Validation refuses a segment writing past the table's declared minimum, and
  `Instance::new` now sizes the table to exactly that minimum rather than to "the larger of the
  declared minimum and the highest write" - a declared limit a segment can raise is not a limit.

- [x] **Per-instance resource limits**: maximum memory pages independent of what the module
  declares, maximum table size, maximum locals per frame, maximum operand stack depth. A limit the
  module declares is not a limit the host imposed.

  DONE 2026-08-12. `MAX_LOCALS` (4096), `MAX_TABLE_ENTRIES` (65536), `MAX_FUNCTIONS` (65536) and
  `MAX_GLOBALS` (4096) in `validate.rs`, beside `MAX_MEMORY_PAGES` in the interpreter - all of them
  the HOST's, enforced whatever the module declares.

## Execution bounds, which the engine has none of

- [x] **Fuel, or an equivalent budget.** `loop br 0 end` is an unbounded loop inside the interpreter
  today, with nothing that ends it. A component host in a capability system may not have "the guest
  can decide to never return" as a possible outcome.

  DONE 2026-08-12. One unit per instruction, charged before the instruction runs, from a
  `DEFAULT_FUEL` of ten million per INVOCATION - a wall rather than a schedule: an ordinary
  component call is thousands of instructions and anything reaching ten million is spinning.
  `loop br 0 end` now traps instead of never returning.

- [x] **An explicit call stack with a depth limit.** Guest recursion is currently Rust recursion, so
  a deeply recursive module overflows the host's stack rather than trapping.

  DONE 2026-08-12. `MAX_CALL_DEPTH`, MEASURED rather than chosen: 256 still overflowed a 2 MB host
  thread, because `exec`'s frame holds one activation's control and operand stacks, so it was
  lowered until the deliberately-infinite recursion trapped instead of aborting. It sits at 32, and
  the test is what re-establishes that number if `exec` ever grows.

- [x] **`Instance::new` must return `Result`.** It cannot report a module it could not instantiate,
  which is the other half of the validator: something has to be able to say no.

  DONE 2026-08-12. The remaining failures after validation are the ones validation cannot see - a
  host that cannot allocate the declared memory or table - and both are refusals now rather than an
  abort or a `Trap` held in a field until the first `invoke`.

## Numerics

- [x] **Float operations do not follow the specification.** `trunc`, `floor`, `ceil`, `nearest` and
  a Newton-Raphson `sqrt` are hand-written in `interp.rs`, so signed zero, subnormals, rounding mode
  and the `sqrt` edge cases are approximations of what WebAssembly requires. A component that
  computes differently here than everywhere else is a portability defect rather than a safety one -
  which is why this is last - but it is a defect in an ABI that is supposed to be a contract.

  DONE 2026-08-12, further than the milestone asked.

  The signed zeros first: `trunc(-0.5)`, `ceil(-0.5)` and `nearest(-0.3)` are `-0.0` and every one
  of them answered `+0.0`, because the arithmetic went through `as i64` and came back unsigned. Same
  for every subnormal. A one-bit difference that `copysign`, `1.0/x` and any component comparing bit
  patterns can see.

  Then `sqrt`, which is now CORRECTLY ROUNDED with no libm and no intrinsics. Newton still produces
  the estimate; what is new is the finish - Dekker's splitting gives an exact product as a pair of
  doubles, so the estimate is corrected to the true floor and the choice between it and its
  successor is decided by comparing the exact midpoint's square against the input. That is the
  definition of correct rounding, evaluated rather than approached. Subnormals are scaled by 2^106
  first, since the exponent-halving seed cannot read one.

  `sqrt_is_correctly_rounded_against_the_host` checks every answer against the platform's own
  `f64::sqrt` over 950+ values including subnormals, powers of two and the values Newton is worst
  at. Watched to fail: `sqrt(2)` was off by one ULP.

## Diagnostics and honesty

- [x] **`ParseError` and `Trap` carry a string and nothing else.** A refusal that cannot say which
  function, which offset and which rule is a refusal nobody can act on - and this milestone is about
  to add a great many refusals.

  DONE for the refusals this milestone added, which is where the great many of them are.
  `ValidationError` carries the function index, the instruction index and the rule, and its
  `Display` reads "function 3, instruction 12: global.set on immutable global 0".

  `ParseError` and `Trap` keep their `&'static str`. Not deferral by omission: a parse failure has
  no function to name and the reader's own position is the only useful coordinate, which would mean
  threading an offset through every primitive for a message nobody has been unable to act on. If
  that changes, the shape to copy is `ValidationError`.

- [x] **The crate's own description claims a validation that does not exist.** `src/wasm/src/lib.rs:4`
  says the runtime "decodes each function body into a validated instruction stream". It decodes into
  a STRUCTURALLY DECODED instruction stream; the word validated has a specific meaning in this
  specification and this engine does not do it. Correct the sentence now rather than when the
  validator lands, because until then it is the sentence that makes every finding above look
  already handled.

  DONE 2026-08-12, and now it exists, so the sentence describes it: parse into a `Module`, VALIDATE
  into a `ValidatedModule`, run that with an `Instance` which accepts nothing else.

## Order

The validator first, as a stage that exists and refuses nothing, then rule by rule with its refusal
corpus - so `ValidatedModule` becomes real before it becomes strict, and `Instance::new` can be
narrowed to it early.

`memory.grow` before the rest of the interpreter rules, because it is the one that is reachable
today and takes the host with it.

The parser's body-boundary sub-reader with it: it is small and it is the only parser item that
misbehaves on input rather than merely accepting too much.

Then the remaining parser rules, then the interpreter's globals and element bounds, then fuel and
the explicit call stack.

The floats and the diagnostics last. The two documentation corrections - the crate description and
the start-section decision - at any point, and the crate description early: it is one sentence and
it is currently the reason this whole surface reads as finished.

## Reopened again: the validator exists and is not yet sound

A third audit, against this tree at `8df720c` - 2026-08-12. Twelve findings, every one read in the
code first. Where the audit's reasoning needed narrowing or its severity needed correcting, that is
said here rather than repeated.

The shape is the one that follows a real fix. The last round's finding was structural - there was no
validation layer at all - and the layer that was built is the right one: `parse -> validate ->
ValidatedModule -> Instance`, enforced by the type of `Instance::new` rather than by discipline. That
holds and nothing below asks for it to change.

What is left is that the validator is not yet SOUND for the subset the decoder claims to accept. In
three places it decides a type from information the decoder threw away, and in each of those it is
wrong in both directions at once: it refuses modules the specification calls valid, and it accepts
modules the specification calls invalid. That is a worse position than having no validator, in one
narrow sense worth stating plainly - a missing check is a known gap, and a check that answers
confidently from a guess is a gap nobody looks for.

Two claims above are also larger than the code. The per-instance limits item names a maximum operand
stack depth that does not exist, and its note says `MAX_MEMORY_PAGES` is "enforced whatever the
module declares" when it is enforced only on `grow`.

Said in fairness, because it bounds how urgent this is: every one of these is about ARBITRARY
modules. The component this repository ships parses, validates and runs - its section list is
`type import func table memory global export elem code data`, with no data-count section and no
block type this pass mistypes - so nothing here is breaking the system today. It is what happens
when the engine is handed a module it did not build.

### The decoder throws the block type away and the validator invents `i32`

`Instr::Block { result_arity: u8 }`, `Loop { param_arity: u8 }` and `If { result_arity: u8 }`
(`src/wasm/src/decode.rs:21`, `:24`, `:27`) keep an arity and nothing else. The value type, the
parameter types and the type index the block named are gone by the time validation runs.

`block_signature` (`src/wasm/src/validate.rs:449`) then reconstructs a signature it does not have.
For the one-result shape it writes `r.push(ValType::I32)` (`:469`). Its own comment three lines above
says the opposite - "a one-result block is checked for its COUNT and its type is left to unify, which
`expect_at` does through `Type::Unknown`" - and no `Unknown` appears in the function. The comment
describes a design; the code implements a guess.

So `(block (result i64) i64.const 7 end)` is refused, and `(block (result i64) i32.const 7 end)` is
accepted. Both are wrong, and the second is the direction a validator exists to prevent.

There is a second half the audit did not reach. For an arity above one the function searches
`module.types` for the FIRST candidate whose parameter and result counts match (`:456`) and returns
it. A block that names type 3 gets type 0 if type 0 has the same shape. That is the same defect in a
different disguise: the index is present in the binary, discarded by the decoder, and re-derived
here by a rule that cannot be right.

- [x] **Carry the real block type through the decoder.** `BlockType::Empty | Value(ValType) |
  TypeIndex(u32)` on `Block`, `Loop` and `If`, read from the `blocktype` byte the decoder already
  consumes - a negative value type or a positive type index. It is the encoding change the comment
  at `:447` already identifies as the fix; this task is to make it.

  DONE 2026-08-12. `BlockType::Empty | Value(ValType) | TypeIndex(u32)` on `Block`, `Loop` and `If`, read from the `blocktype` the decoder was already consuming and then reducing to two counts. The interpreter needs only how many values a frame keeps, so `block_results`/`block_params` derive the arities from the type - it is unchanged in what it needs, and the validator gains what it could not reconstruct.

- [x] **Delete `block_signature`'s reconstruction.** With a real block type, params and results come
  from the type or from the single value type, and the arity fields become derived rather than
  primary. The interpreter reads the same field for how many values to keep, so the two stop having
  separate notions of what a block is.

  DONE 2026-08-12. Params and results come from the type or from the single value type; the `i32` guess and the search for the first declared type with matching counts are both gone.

- [x] **Tests in both directions, per shape.** A `(result i64)` block that is correct and must pass;
  the same block with an `i32` body that must fail; a `(type n)` block where another type has the
  same arity, asserting the named one is used. The last is the one no arity-based check can pass.

  DONE 2026-08-12. `a_block_is_checked_against_the_type_it_declares`: a `(result i64)` block correct and incorrect, and a block naming type 1 where type 0 has the same arity - correct and incorrect - which is the case no arity-based check can pass. Watched failing with the `i32` guess put back.

### The narrow `i64` stores are typed by their storage width

The decoder folds all seven integer stores into `Store { width, offset }`
(`src/wasm/src/decode.rs:53`), so `i32.store` (0x36, width 4) and `i64.store32` (0x3e, width 4) are
indistinguishable afterwards, as are `i32.store8` (0x3a) and `i64.store8` (0x3c) at width 1.

The validator decides the value type from the width: `if *width == 8 { I64 } else { I32 }`
(`src/wasm/src/validate.rs:391`). Its comment says outright that "the decoder folds `i64.store32` and
`i32.store` into one `Store`" and then types them the same anyway.

`i64.store8`, `i64.store16` and `i64.store32` all take an `i64` operand and narrow it on the way to
memory. All three are refused here when written correctly, and all three are accepted when given an
`i32`. `FStore` next to it already carries `wide: bool` for exactly this reason, so the shape of the
fix is in the same file.

Narrow this: it is a validator soundness defect and NOT a memory-safety one. The interpreter
(`src/wasm/src/interp.rs:445`) takes the low `w` bytes of whatever value is on the stack and
bounds-checks the slice, so the mistyped case stores a defensible byte pattern rather than reaching
out of memory.

- [x] **Give `Store` the value type, not only the storage width.** A `wide: bool` beside `width`
  matches `FStore` and is enough for the seven opcodes that exist; the decoder knows which opcode it
  read.

  DONE 2026-08-12. `wide: bool` beside `width`, matching `FStore` next door, set from the opcode the decoder read.

- [x] **A test per narrow store**, correct and incorrect: `i64.store8` with an `i64` must pass and
  with an `i32` must fail, and the same for 16 and 32. Three of the six cases fail today.

  DONE 2026-08-12. `the_narrow_i64_stores_take_an_i64` covers all six cases - each narrow store correct and incorrect - of which three failed before. Watched failing with the rule reverted.

### The host memory ceiling does not apply to the memory the module starts with

`MAX_MEMORY_PAGES` is 1024 (`src/wasm/src/interp.rs:89`) and appears exactly once more, inside
`memory.grow` (`:506`). `Instance::new` computes `module.memory_min_pages as usize * PAGE`
(`:196`) and reserves it, with no comparison to that constant and none in the validator either -
`validate.rs` bounds functions, globals, locals and the table, and reads `memory_min_pages` only to
bound data segments (`:183`).

So `(memory 100000)` is a six-byte declaration that asks the host for six gigabytes before a single
instruction runs. `try_reserve_exact` turns a failure into a refusal rather than an abort, which is
why this is a resource-policy hole and not a crash - but the policy the milestone states is "a limit
the module declares is not a limit the host imposed", and here the module's declaration IS the limit.
On a host that overcommits, the reserve succeeds and `resize` faults the pages in one by one.

- [x] **Enforce `MAX_MEMORY_PAGES` on the declared minimum, in the validator**, so the refusal
  arrives with the module rather than at instantiation and carries a `ValidationError` naming the
  rule. The maximum, where the module declares one, wants the same treatment.

  DONE 2026-08-12, minimum and maximum, so the refusal arrives with the module and carries a `ValidationError` naming the rule rather than surfacing at instantiation.

- [x] **Correct the DONE note above.** It says the host constants are "enforced whatever the module
  declares"; for memory that is true of `grow` and false of the initial size, which is the half an
  attacker controls for free.

  DONE 2026-08-12 - it is true now, which is the other way to correct it: the constant is enforced on the declared minimum, on the declared maximum and on `grow`.

### A few bytes of hostile input still reach `Vec::with_capacity` with a `u32`

Three places allocate from a count read out of the input before anything has checked that the input
contains that many items:

- `br_table` in the body decoder: `let n = read_u32(...)?; Vec::with_capacity(n as usize)`
  (`src/wasm/src/decode.rs:171`). A body of a handful of bytes can declare `0xffffffff` labels and
  ask for sixteen gigabytes.
- The element section, twice: `let n = r.u32()? as usize; Vec::with_capacity(n)`
  (`src/wasm/src/parser.rs:293` and `:309`).

All three are infallible `with_capacity`, so the failure is an allocation abort in the host process
rather than a refusal - and all three happen during parse or decode, which is BEFORE fuel, before the
host limits, and before anything else this milestone added. The engine's whole resource story starts
one step too late.

- [x] **Bound every count against the input before allocating.** A vector of `n` items cannot be
  present in fewer than `n` bytes of remaining input, and that check needs nothing but the reader's
  own position - it is the cheapest possible bound and it makes the count self-limiting.

  DONE 2026-08-12 for the three sites: `br_table`'s label vector and the element section's two index vectors. A label or an index is at least one byte, so `n` of them cannot be present in fewer than `n` bytes of what is left - the check needs nothing but the reader's own position.

- [x] **Then allocate fallibly.** `try_reserve` and a refusal, so a count that passes the bound and
  still cannot be held is a `ParseError` rather than an abort. The handle table in the kernel learned
  the same lesson this week; this is the same rule at a different boundary.

  DONE 2026-08-12. `try_reserve` and a refusal at all three, so a count that passes the bound and still cannot be held is a parse error rather than an abort. The two changes are separable and the test says which it proves: with the input bound removed the `try_reserve` still refuses, so what the test pins is that a hostile count is ANSWERED; the bound is the cheaper path to the same answer.

- [x] **Sweep for the pattern rather than fixing three sites.** `grep with_capacity src/wasm` is the
  whole audit and it currently returns six lines; three are sized by already-parsed structures and
  three are sized by the attacker. A comment at the reader saying which is which would keep the next
  one from being written.

  DONE 2026-08-12. `grep with_capacity src/wasm` now returns only the three sized by already-parsed structures; the three sized by the medium are gone.

- [x] **A test that is a few bytes long and would need gigabytes**, asserting a refusal. It is the
  only test in this milestone that would fail by exhausting the machine rather than by returning the
  wrong answer, so it is worth writing carefully - a declared count with no bytes behind it.

  DONE 2026-08-12. `a_declared_count_is_bounded_by_the_input_before_it_is_allocated` - a body declaring `0xffffffff` labels in a dozen bytes, refused.

### `memory 0` is still spelled as "no memory"

`Module::memory_min_pages` is documented as "0 if module declares none"
(`src/wasm/src/module.rs:97`), and both the validator's memory checks derive existence from it:
`module.memory_min_pages > 0 || module.memory_max_pages.is_some()` (`src/wasm/src/validate.rs:142`
and `:221`).

`(memory 0)` is a valid memory with an initial size of zero pages - a module that declares it and
calls `memory.size` is well-formed, and this validator answers "a memory instruction in a module with
no memory". `(memory 0 10)` happens to work, because the maximum makes the second half of the
disjunction true, which is worse than failing consistently.

- [x] **Make the memory an `Option`, as the table already is.** `module.table` is
  `Option<...>` and answers "is there one" without a sentinel; memory should be spelled the same way,
  and then the two checks above become one field access.

  DONE 2026-08-12. `Option<MemoryType>` with `min_pages` and `max_pages`; the two `min > 0 || max.is_some()` existence checks became one field access.

- [x] **A test with `(memory 0)` and `memory.size`**, asserting it validates and returns zero.

  DONE 2026-08-12, and it had to be built by hand: the test builder's `mem_pages: 0` means "emit no memory section" - the same sentinel one layer up, in the fixture.

### The LEB128 rule the parser enforces is not the specification's

`Reader::u32` (`src/wasm/src/parser.rs:51`) refuses an encoding with a redundant trailing byte, and
its comment says "The specification requires the shortest encoding" (`:49`). `Reader::i64` does the
same for sign bytes (`:86`), and `a_non_canonical_leb128_is_refused` (`src/wasm/src/tests.rs:863`)
pins the behaviour with `0x81 0x00`.

The specification says the opposite. Its integer grammar restricts the encoding's WIDTH and nothing
else, and its note on that grammar gives the example directly: `0x03` and `0x83 0x00` are both
well-formed encodings of 3, and `0x7e` and `0xFE 0x7F` are both well-formed encodings of -2. Trailing
zeros within the width bound are legal WebAssembly. This parser refuses conforming modules and a test
now holds it there.

The motivation in the comment is legitimate and should survive the fix: two byte-level spellings of
one module is a real problem for anything that hashes or signs. But that is a LiberSystem packaging
policy about which encodings this system will SHIP, not a fact about which modules are well-formed,
and putting it in the core parser as a spec claim is how a conformance bug gets a test written for
it.

The opposite gap is still open in the other reader. `read_u32` in the body decoder
(`src/wasm/src/decode.rs:370`) has no width check at all: it reads a fifth byte at shift 28 and
silently drops the bits above 32, where the parser's reader refuses them (`parser.rs:56`). So the
two readers disagree, and the one used for instruction immediates is the permissive one.

- [x] **Accept trailing zeros within the width, in both readers**, and correct the comment to say
  what the rule actually is. The test goes with it - inverted, asserting `0x81 0x00` is accepted as
  the value 1.

  DONE 2026-08-12. The specification's integer grammar bounds the encoding's LENGTH and nothing else, and its own note gives the example this parser was refusing. The test is inverted rather than deleted: it now asserts `0x81 0x00` decodes to 1, and that six bytes or bits above the 32nd are refused - the bound that IS the specification's.

- [x] **Add the width checks the specification does require**, to `decode.rs` where they are absent:
  a `u32` whose fifth byte carries bits above the 32nd is malformed, and the signed readers want the
  s32/s33/s64 forms distinguished rather than everything going through one `read_i64`.

  DONE 2026-08-12 in `decode.rs`, which had none while the parser's reader did - so the two readers in one crate disagreed about what a `u32` is, and the permissive one was the one used for instruction immediates.

- [x] **If a canonical-encoding rule is wanted, put it where policy lives** - a check over an image
  about to be signed or shipped, stated as this system's rule - and say at both readers that the core
  parser deliberately accepts what the specification accepts.

  Recorded rather than built: the motivation - two byte-level spellings of one module - is real for anything that hashes or signs, and it belongs to a check over an image about to be shipped. The core parser now accepts what the specification accepts, and says so at both readers.

### The section-order check assumes IDs ascend, and one of them does not

The parser refuses a section whose id is not greater than the last (`src/wasm/src/parser.rs:148`).
That is right for eleven of the twelve. The data-count section has id 12 and its place in the module
is BETWEEN element (9) and code (10) - the ids do not correspond to the order.

So a conforming module carrying a data count is refused as "out of order", and the ordering

is the one thing it exists to state.

Its practical reach today is small and worth recording as such: the component this repository builds
has no data-count section at all (`type import func table memory global export elem code data`), so
nothing in this tree hits it. A module from a toolchain with bulk-memory enabled generally does.

- [x] **Replace the ascending-id test with the specification's order.** A table of the twelve ids in
  their real sequence and an index into it is the same few lines and is correct for data count.

  DONE 2026-08-12. A table of the twelve ids in their real sequence and an index into it: `[1,2,3,4,5,6,7,8,9,12,10,11]`, so the data-count section's place between element and code is right and `code data datacount` is refused.

- [x] **Read the data count rather than skipping it,** and refuse a module whose count disagrees with
  the number of data segments - or refuse the section outright while this engine has no `memory.init`
  or `data.drop`, which is the choice the start section already made and is defensible for the same

  DONE 2026-08-12 by the second answer the task offers, which is the one the start section already chose: the data-count section is refused rather than skipped while this engine has no `memory.init` or `data.drop`. Skipping a section whose only content is a claim about the module was the thing not to do; refusing says the module uses a feature this engine does not implement, which is true.

### The embedder boundary checks counts and not types

### Fuel counts instructions, and some instructions are not one instruction's work

`Budget::charge` subtracts one per instruction (`src/wasm/src/interp.rs:144`). `memory.fill` and

## Reopened: the validator learned block parameters and the interpreter did not

A fourth audit, against this tree at `4350074` - 2026-08-14. Seven findings and all seven hold. One of
them is a different KIND of defect from anything this milestone has carried before, and it is worth
separating from the rest.

Everything found here so far has been a module that should be refused and is not, or one that should
be accepted and is not. This is the first case where **a module that validates correctly executes with
the wrong answer**. That is the failure mode an interpreter exists to make impossible, and it arrived
through a repair: `BlockType` was fixed to carry the real type, the VALIDATOR was taught what block
parameters mean, and the interpreter's frame setup was left as it was.

The audit's account of the round is otherwise right and closes ten of its twelve: narrow `i64.store*`
is typed by `wide` rather than by width, `Option<MemoryType>` distinguishes `(memory 0)` from no
memory, the initial memory is bounded by the host policy, `br_table` and element vectors are bounded
by the input before they reserve, typed `select` keeps its annotation, `call_indirect` refuses a
non-zero table index, both sides of the embedder boundary are type-checked, bulk operations cost fuel
by size, and the operand stack has a depth limit.

### A parameterised block leaves its parameters on the stack

The three control instructions set their runtime frame differently
(`src/wasm/src/interp.rs:378-391`):

```rust
Instr::Block { .. } => ctrl.push(Frame { base: stack.len(),                            .. });
Instr::Loop  { .. } => ctrl.push(Frame { base: stack.len().saturating_sub(params), ..   });
Instr::If    { .. } => ctrl.push(Frame { base: stack.len(),                            .. });
```

`Loop` is right and the other two are not. Entering a block of type `[t1*] -> [t2*]` pops the `t1*`
and pushes a label whose stack height is what is left; the parameters then become the block's own
operands. A branch to that label truncates to the label's height. With `base` recorded before the
parameters are accounted for, the truncation leaves them behind.

The validator already computes the right number, one file over (`src/wasm/src/validate.rs:280-286`):
it pops the parameters, takes `height = stack.len()` AFTER the pop, and pushes them back inside the
frame. So the two halves of the engine disagree about the same block, and the half that decides the
answer is the one that is wrong.

```wat
(type $t (func (param i32) (result i32)))
(func (result i32)
  i32.const 10
  i32.const 20
  block (type $t)
    i32.const 30
    br 0
  end
  i32.add)
```

Correct: the block consumes 20, `br 0` carries 30 out, the stack is `[10, 30]`, the answer is 40.
Here: `base` is 2 rather than 1, `br 0` truncates to 2 and leaves `[10, 20, 30]`, and `i32.add`
answers 50.

- [x] **Subtract the parameters in `Block` and `If`,** the way `Loop` already does. Three characters
  of arithmetic, and the number is already computed by `block_params`.

- [x] **Then stop computing it three times.** The arity of a block is known at validation, where the
  signature has already been resolved and checked; carrying resolved control metadata out of the
  validator would make `block_params`/`block_results` unnecessary and would make this class of
  disagreement structural rather than a matter of two functions agreeing.

- [x] **A differential test with a parameterised block and a branch out of it,** which is the test that
  distinguishes the two answers. The current corpus test cannot: it asserts `parse(..).is_ok()` on the
  valid modules (`src/wasm/src/tests.rs:1429`) and never validates, instantiates or runs one.

### `Frame::arity` is a `u8`

`interp.rs:109` declares `arity: u8`, and `block_results`/`block_params` cast with
`t.results.len() as u8` (`:1442`, `:1450`). A block type with 256 results wraps to zero. The validator
caps the operand stack at 8192, so the engine's own limits already assume more than 255 values can be
live.

- [x] **`usize`,** and the two helpers with it. Nothing in the current toolchain's output reaches 256
  results; the cast is a silent wrap where a refusal or a correct number belongs.

### `else` does not restore the block's parameters, and a typed `if` without one is refused

The validator's `Frame` carries `end_types` and no `start_types` (`validate.rs:122-128`). At `Else` it
truncates to `frame.height` and clears `unreachable` (`:299-305`) without pushing the parameters back,
so the `then` arm sees them and the `else` arm does not - and a valid parameterised `if` is refused.

Beside it, `:316` refuses any `if` that has no `else` and non-empty results. For a type like
`[i32] -> [i32]` the empty branch is legal: the parameter is the result. The binary format permits
omitting `else` when that branch is empty, which is not the same as requiring no results.

- [x] **Give the frame its `start_types`,** which is what the specification's own validation algorithm
  carries, and re-push them at `else`. The block entry already has the values - `block_signature`
  returns both halves and only `results` is kept.

- [x] **Refuse a missing `else` only when the empty branch does not typecheck,** which is
  `start_types != end_types` rather than `!end_types.is_empty()`.

### One LEB reader for three different widths

`read_i64` decodes `i32.const` (`decode.rs:290`), `i64.const` (`:291`) and the block type (`:409`).
The binary format specifies three different signed forms - `s32`, `s33` and `s64` - and each bounds
its own length: at most `ceil(N/7)` bytes, with defined rules for the unused bits of the last one. So
an `i32.const 0` written in six bytes is malformed and this reader accepts it, truncating with
`as i32`.

The test suite already records this. The malformed-corpus check carries
`const ACCEPTED_CEILING: usize = 20` (`tests.rs:1393`) - twenty modules the specification calls
malformed still parse, and integer-width forms are among the named reasons. As a ratchet that is the
right mechanism; as evidence of binary conformance it is a statement that the gap is measured, not
that it is closed.

- [x] **`read_s32`, `read_s33` and `read_s64`,** each bounded by its own width, with the block type and
  the two constants reading the one that belongs to them.

- [x] **Lower the ceiling by what that closes,** so the number keeps meaning "this is the gap" rather
  than "this is the allowance".

### The export section is validated for two kinds out of four

`parser.rs:490-491` maps `0x00` to `Func`, `0x02` to `Memory` and everything else - including an
undefined byte like `0xff` - to `Other`. The validator then checks the index for `Func` and `Memory`
and matches `_ => {}` for the rest (`validate.rs:175-184`). There is no duplicate-name check.

The specification requires every exported index to be valid and every export name in a module to be
distinct. This milestone's claim is that every static index is validated before an instance exists;
`Other` is the hole in that sentence.

- [x] **Refuse an undefined export kind byte at parse,** rather than folding it into a catch-all.

- [x] **Refuse `Table` and `Global` exports explicitly as unsupported,** or validate their indices.
  What may not stand is accepting them unvalidated under a name that means "ignored".

- [x] **Refuse duplicate export names,** which is a module-level rule and belongs beside the index
  checks.

### Table limits are read where memory limits are validated

The memory parser refuses a flags byte above 1, with a comment saying exactly why: anything else is a
limits encoding from a feature this engine does not implement, and reading past it as though bit 0
were the only meaningful one is how a module for a different engine parses here (`parser.rs:295-299`).

The table parser reads the byte and tests only `flags & 0x01` (`:332`). The defined encodings are
`0x00`, `0x01`, `0x04` and `0x05`, with the upper pair naming a 64-bit address type this engine does
not support - so a table64 module parses here as an ordinary 32-bit table.

- [x] **Apply the memory parser's rule to tables,** and point the comment at the memory one rather than
  restating it, so the two cannot drift apart again.

### The valid corpus proves the parser and nothing behind it

`tests.rs:1429` counts `parse(&c.bytes).is_ok()` over the specification's valid modules. That is the
right first rung and it is the only one: a module that parses, validates, instantiates and then
computes the wrong answer passes it. The first finding in this section is exactly such a module.

- [x] **Run the valid corpus through `parse -> validate -> Instance::new`,** at least for the modules
  inside the supported subset, so acceptance is proved at the layer that decides behaviour rather than
  at the one that reads bytes.

- [x] **And execute what the corpus asserts about,** where the case carries an expected result. That is
  the differential conformance step this engine is now close enough to be worth building; every finding
  above except the export and table ones would have been caught by it.

## A fifth round: the engine is narrow now, and the harness that guards it is not

Against `7b71ece`. The audit's account of the fourth round is accurate and is not in dispute: the
parameterised-block stack base is fixed at its cause rather than at its symptom, `start_types` gives
both arms of an `if` their parameters and decides the no-else rule by whether the empty branch
typechecks, `Frame::arity` is `usize`, the signed LEB readers are width-specific, and the table limits
flags are refused like the memory ones. Each was checked against the code. Five findings remain, and
the most important is not in the engine at all.

### `assert_return` that traps was counted as "skipped"

`spec_run`'s result arm read every `Err` as a module outside this engine's subset:

    match outcome {
        Err(_) => skipped += 1,
        Ok(got) => { ran += 1; if !same(&got, &want) { wrong.push(..) } }
    }

Its comment justifies that with "an unsupported instruction in its body" - which describes a MODULE,
and the module is three stages past it. `validate` decodes every body and refuses `unsupported
opcode`, so a module that reached this line has no unreachable instruction left in it. What the arm
actually swallowed is the interpreter returning a trap where the specification states a number, which
is the exact defect the execution corpus was built to catch, filed as a skip and leaving the suite
green.

Turning it into a disagreement immediately produced two, and they were a third thing again -
`imports.wast` and `names.wast` import the suite's `spectest` host, which this runner does not
provide, so every call trapped with "no imports available". That is a property of the module and
knowable before a single assertion runs, which is the audit's own point: subset decisions belong at
module admission.

- [x] **`assert_return` + `Err` is WRONG,** not skipped.

- [x] **Except for the two traps this ENGINE imposes** - out of fuel and call depth - which the
  specification does not model at all, counted apart rather than folded in.

- [x] **Refuse the module, not the result, when the harness cannot serve its imports.** Decided once
  per module, where the reason is a property of the module.

- [x] **Move the executed floor to what that leaves,** with the reason recorded beside it: 2133
  executed and 567 skipped, four fewer than before because four assertions belonged to modules this
  runner was never able to run - two of which had been trapping.

### Two identical module declarations shared one instance

`extract-wasm-spec-runs.py` indexed modules with `modules.setdefault(current, len(modules))`, keyed
on the module's BYTES. Two separate `(module ...)` declarations that assemble identically therefore
collapsed to one index - and the runner groups by that index and instantiates once per group, so the
second declaration inherited the first one's mutated globals and memory. The suite writes its
assertions against a fresh instance.

Demonstrated against the old script with a two-module fixture whose bytes match: it emitted one `M`
row and pointed both assertions at it. The new one emits two.

- [x] **Instance identity is the module's OCCURRENCE, not its content.** Assigned on first use, so a
  module no assertion reaches is still not written out.

- [x] **Say so in the format note at the top,** which said a shared module "is written once".

The fixture itself is regenerated from a checkout of the specification repository with `wasm-tools`,
neither of which is in this tree, so the corpus on disk still carries whatever merges the old script
made. The extractor is what was wrong and is what is fixed; the numbers move at the next regeneration.

### The engine findings

- [x] **A memory export's index is checked.** `ExportKind::Memory if !has_memory` asked only whether
  the module declares A memory, so `(memory 1) (export "mem" (memory 1))` validated - and there is no
  memory 1, because this engine supports exactly one. Every other kind of export had its index
  checked; this one had the easier half of its question written down.

- [x] **Arguments are checked before the callee is chosen.** The count-and-type check sat in the
  defined-function branch, past the `return` that dispatches an import - so a module that imports a
  function and re-exports it handed the embedder's arguments to `Host::call_import` unchecked. The
  boundary is where the values enter, not where the body is. The two hosts in this tree destructure
  their arguments exactly and were not at risk; the generic `Host` API is what a third implementation
  reaches for.

- [x] **`MAX_CONTROL_DEPTH`.** `MAX_STACK_DEPTH` bounds the operand stack and does not bound the
  control stack: entering a block pops its parameters and pushes them straight back, so a body
  nesting blocks of a type with 8192 parameters and 8192 results holds the stack at exactly 8192
  forever while every frame clones three type vectors - about 24 KiB of validator allocation for the
  two bytes that encode the block. That is the `br_table` amplification in the structure that walks
  the body. A bound rather than a restructure: making the frame borrow its signatures divides the
  constant by three and leaves the growth linear in a number the module chooses.

- [x] **`memory.grow` is charged for the pages it zeroes.** `resize` zeroes every byte it adds, so
  the instruction's cost is bounded by an operand - the rule that put `memory.copy` and `memory.fill`
  in the bulk class. It cost one unit for up to 64 MiB of zeroing while a `memory.fill` over the same
  bytes cost 65,000, so the budget priced the same work two ways depending on which instruction asked
  for it. Charged only on the path that grows, so a refused request cannot drain the budget.

- [x] **`Instance::invoke_with_fuel`,** found while writing the test for the item above.
  `DEFAULT_FUEL`'s comment says "a caller that wants a different wall calls `invoke_with_fuel`" and
  there was no such function - `Budget::with_fuel` existed and was reachable from nothing. An
  embedder metering a component it does not trust is why the budget exists.

- [x] **A regression test for each,** every one of them run against the unmodified engine first: the
  two that could be (the API for the other two did not exist) by reverting the file, and all four by
  neutering the single line each fix turns on.

## Reopened by the sixth audit: the limits are real and they start after the expensive part

An outside audit of `src/wasm`, 2026-08-15. It confirms the round's fixes: the memory export index,
the re-exported import handled at the right layer, a separate `MAX_CONTROL_DEPTH`, the `memory.grow`
fuel price, the `assert_return` trap false-green, and module instance identity. Its through-line is
that this engine's resource policy is enforced by the VALIDATOR and the expensive work happens before
the validator runs. Each finding below was checked against the source.

- [ ] **The parser and decoder allocate before any host limit applies.** `MAX_CONTROL_DEPTH` is a
  validator limit, and by the time it can refuse anything `decode()` has already walked the whole
  function body, built an `Instr` per opcode, allocated a `Vec` for every `br_table`, and held the
  raw body and the decoded stream at the same time. The section parsers have the same shape: a
  declared count is read and the corresponding vector is filled before anything asks whether the
  count is plausible against the remaining bytes. So a structurally inflated module exhausts the host
  before it is refused - the module is rejected in the end and the host paid for it first. The policy
  has to begin at the input boundary: bound each declared count against the bytes that could possibly
  encode it, and cap the decoded body size as it is produced rather than after.

- [ ] **`MAX_STACK_DEPTH` is checked once per instruction, and one instruction can push an unbounded
  number of operands.** `validate.rs:329` tests `stack.len() > MAX_STACK_DEPTH` before `match instr`,
  so it bounds what the PREVIOUS instruction left. A `call` pushes one operand per callee result and
  a typed block pushes its whole parameter and result tuple, so a single instruction can take the
  stack far past the ceiling, clone a large `FuncType` and reallocate the validator's stack before
  the next iteration refuses it.

  The module is still rejected, so this is not a soundness bypass - it is the ceiling failing to be
  an ALLOCATION ceiling, which is what it exists to be. Add `MAX_TYPE_PARAMS` and `MAX_TYPE_RESULTS`,
  and an `ensure_stack_room(n)` before each bulk push. The current one-check-per-instruction comment
  argues that an instruction adds a bounded number of operands, and that is exactly the assumption
  a large result tuple breaks.

- [ ] **`memory.grow` reserves the memory before it charges for it.** `interp.rs:633` is
  `memory.try_reserve(new_bytes.saturating_sub(memory.len()))` and the fuel charge is at `:647` -
  `budget.charge_bulk(new_bytes - memory.len())?` - so a guest with too little fuel still gets the
  host to make the reservation, and only then traps. The reservation stays. Charge first and reserve
  after: the ordering the comment above the charge already argues for ("a refused grow does no
  work") is not the ordering the code has.

- [ ] **The official-spec runner's bare effect invoke ignores a trap.** An invoke executed for its
  effect discards the result, so a module that traps mid-way is replayed as though its state change
  succeeded - and the state it left behind is then asserted against. That is the same class as the
  `assert_return` false-green this round fixed, in the other direction: propagate the trap and fail
  the case.

- [ ] **`assert_trap` accepts any `Err`, including a host-limit trap.** The spec case names the trap
  it expects; accepting any failure means a module that hits `MAX_STACK_DEPTH`, runs out of fuel or
  is refused by a host limit satisfies a test about integer division by zero. Match the expected
  cause, and treat a host-limit trap as a failure of the case rather than as its pass condition.

- [ ] **`ReadOutcome::Read(n)` and `WriteOutcome::Wrote(n)` are not checked against the buffer or the
  `i32` ABI.** The host validates the requested length and then trusts the count the service adapter
  returns, so a wrong adapter can report more than the buffer holds, or a value that wraps negative
  when cast - which the guest reads as a status. Bound it: `n > requested || n > i32::MAX` is an
  internal error, not a count. (Recorded in P02M0130 as well, because the same boundary is crossed
  from the SDK side.)

- [ ] **`load_component()` has no size limit and copies the whole object with an infallible
  `.to_vec()`.** A component file large enough kills the host before the parser sees a byte of it.
  Bound the length against the same ceiling the rest of this engine uses, and make the copy fallible.

- [ ] **Several header comments describe the previous architecture or a different supported subset.**
  This engine has been reopened by a stale comment before, and a comment that describes a subset the
  code no longer implements is the one a new contributor builds on.
