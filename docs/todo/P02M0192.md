# P02M0192 - Gamepads: an input vocabulary, the USB mapping and a gamepad test tool

Status: OPEN. It closes when every item below is done.

THE OWNER'S DECISION (2026-09-25): a new milestone that brings a TOOL into LiberSystem for testing gamepads,
in the text interface, showing which button is pressed on which gamepad. The tool is the consumer the
vocabulary lacked, so the rule that held the vocabulary back - no shape without a real consumer - is met by
this milestone rather than stepped around.

WHAT EXISTS. P02M0099's HID expansion item left the gamepad half open for want of a shape, and the device
side is less finished than that item's note says. The shared report-descriptor parser lets the Generic
Desktop, Simulation, Game and Button pages through its page filter with their logical bounds, but NO FIXTURE
HOLDS A GAME CONTROL: its six parser tests cover digitizers, contacts, collection depth and units. The input
path's `Segment` records neither the Null State bit nor the collection a field belongs to; only the separate
`fields` table, which the HID power class reads, records both. `usb-gadget.sh setup hid-gamepad` builds a
real USB gamepad with four eight-bit axes (X, Y, Z, Rz) and sixteen buttons, and NO HAT. And today a gamepad
is FLATTENED: the xHCI HID module binds only the first HID interface of a device, folds any Generic Desktop X
axis into the system pointer - so a gamepad's stick moves the console cursor and its first eight buttons
click - and lists the device as a pointer. `liber:input@1` carries `pointer-event`, `key-event` and
`contact-event`, none of which is a set of axes with a button bitmap. InputService takes the first provider
of each kind it finds at bootstrap and closes its catalogue subscription, so nothing published later - a
second controller, a replacement - ever reaches it.

## P02M0192 - The vocabulary

- [ ] `liber:input@1` gains the gamepad records, additive, the version staying 1:
  `gamepad-axis { usage: u32, minimum: i32, maximum: i32 }` (the usage page-extended, the page in the high
  sixteen bits); `gamepad { id: u32, label: string (at most 32 bytes), axes: list<gamepad-axis> (at most 8),
  buttons: u8 (at most 32), hats: u8 (at most 2) }`; `gamepad-state { id: u32, buttons: u32, hats: list<u8>,
  axes: list<i32> }`, where bit n-1 is Button-page button n, a hat is 0..7 for north and then clockwise in
  eighths or 8 for CENTRED, and the axis values are the device's own logical values in the order of `axes`,
  never rescaled; and the variant `gamepad-event { present(gamepad), arrived(gamepad), state(gamepad-state),
  departed(u32) }`. THE ID IS INPUTSERVICE'S: a number given at each arrival and never reused while the
  service runs, so a gamepad unplugged and plugged back is a new gamepad.
- [ ] THE STREAM'S ORDER: a gamepad stream opens with a `present` and then a `state` for every gamepad there at
  that moment; afterwards it carries a `state` for every change of a gamepad's buttons, hats or axes, an
  `arrived` and its first `state` for each new one, and a `departed` for each one that leaves. A consumer
  therefore always knows WHICH gamepad pressed WHAT, and a gamepad's events never carry another's id.
- [ ] FOCUS IS DECIDED IN INPUTSERVICE, NOT IN THE DRIVER, and there are exactly two ways in:
  - A GRAPHICAL APPLICATION calls `input.subscribe-gamepads` (op 4) with the one-shot focus proof
    `subscribe-keys` and `subscribe-contacts` take, on any connection that may call those. One such stream is
    live: a new valid subscription replaces it, and on focus loss every held button and every hat off centre
    is released to it (a `state` with no buttons and centred hats, axes as they were) before it closes.
  - A CONSOLE PROGRAM is granted the new capability `input-gamepad`. PermissionManager mints it per launch
    through `input-admin.open-gamepads` (op 2, appended after `open-keys`), which returns a connection of a new
    GAMEPAD scope on which only `input.observe-gamepads` (op 5) works and every other operation is refused;
    `observe-gamepads` is refused on every other scope. Its stream is delivered ONLY WHILE NO GRAPHICAL SURFACE
    HOLDS DISPLAY FOCUS, so a background program cannot watch a game's input: a surface taking focus releases
    held buttons to the console stream and closes it, and `observe-gamepads` is refused while a surface holds
    focus. ONE console stream at a time: a second is refused while the first is open rather than displacing it.
  - ARMING THE PROTECTED SESSION releases and closes both kinds of gamepad stream, exactly as it revokes key and
    contact focus; while it is up no gamepad event is delivered anywhere and both operations are refused.
    Gamepad state is still tracked, so nothing is stuck when the session ends.
  - A refusal is the correlation id with no stream, as `subscribe-keys` refuses. Gamepad input is never
    forwarded to ConsoleService.
- [ ] `input-gamepad` is APPENDED LAST to the `capability` enum in `security.lsidl` (a capability's number is
  its position, as `midi-output`'s note says), with its place in PermissionManager's `VOCABULARY` (whose
  compile-time exhaustiveness check then passes), its grant tag, `for_capability` answering 0 because it is
  minted per launch, and the mint in `grant_for_task` through `open-gamepads`. The `gamepad` tool's policy row
  grants it and nothing else.

## P02M0192 - The provider kind, the driver wire and discovery

- [ ] A NEW PROVIDER KIND, `gamepad`, appended after the last kind with the next free wire number when it
  lands (21 as of this plan, after `admin-executor`; other planned milestones append kinds too, and whichever
  lands first takes the number), because a consumer of `pointer` is handed one cursor and a consumer of
  `input` keystrokes. It is declared in every closed table, each of which refuses a kind it does not name: the
  `provider-kind` enum in `device.lsidl`, `driver_protocol::provider::GAMEPAD`, the system-manifest's
  `ProviderKindName` and its wire number, DeviceManager's two kind mappings, the xHCI driver's `provides` row
  (`{ kind = "gamepad", most = 1 }`, one consumer), InputService's `CATALOGUE` role (`kinds = ["input",
  "pointer", "touch", "gamepad"]`), and every other exhaustive match over the kind that the build then names.
- [ ] THE DRIVER WIRE, one frame per message, little-endian, defined ONCE in a new `driver_protocol::gamepad`
  module whose encoder and bounded decoder are host-tested there, and used by the xHCI driver, the fixture
  below and InputService alike - one layout rather than hand-written copies:
  - ARRIVAL `[1][handle u32][buttons u8][hats u8][axes u8][label length u8][label][per axis: usage u32,
    minimum i32, maximum i32]` - the handle is the publisher's own number for this attachment, never reused
    while it runs; at most 32 buttons, 2 hats, 8 axes and 32 label bytes of printable ASCII;
  - STATE `[2][handle u32][buttons u32][hat 0 u8][hat 1 u8][one i32 per axis]` - hats as the vocabulary states
    them, an unused hat slot 8;
  - DEPARTURE `[3][handle u32]`.
  A frame whose length or counts disagree, a STATE for an unknown handle or of the wrong shape, a hat above 8
  or a button bit past the gamepad's count is refused by the decoder and changes nothing.
- [ ] THE PUBLISHER'S RULES. A STATE is sent only when the mapped state CHANGED and never blocks: one that
  cannot be sent is dropped, because the next change carries the whole state. ARRIVAL and DEPARTURE never block
  either, but one that cannot be sent CLOSES that consumer's connection rather than being lost. With no
  consumer connected nothing is sent; at every connection - the first and any later one - the publisher sends
  an ARRIVAL and a STATE for each gamepad it holds, which is what makes a gamepad bound at boot, before
  InputService connected, visible to it.
- [ ] THE DISCOVERY RULE. The xHCI driver publishes its `gamepad` provider UNCONDITIONALLY at its handshake, as
  it publishes the pointer, so one controller's gamepads arriving and leaving later are frames on one standing
  connection. InputService KEEPS ITS `gamepad` CATALOGUE SUBSCRIPTION OPEN, as MidiService keeps its own, and
  adopts every live gamepad provider - a second controller, the fixture, a restarted driver's replacement - up
  to four, dropping a withdrawn one. A provider withdrawn, or whose connection closes, is every one of its
  gamepads departing; a connection that closed while its provider is still published is opened again once,
  and the publisher's resend makes its gamepads arrive afresh. InputService tracks at most eight gamepads,
  keyed by (source, handle), and refuses an arrival past that with one line. The input, pointer and touch kinds
  keep their bootstrap-only discovery.

## P02M0192 - The mapping (P02M0099's HID expansion, its gamepad half)

The gamepad half of P02M0099's HID expansion item closes when this part lands with its evidence below.

- [ ] `hid::parse` RECORDS WHAT A GAMEPAD NEEDS on every segment: the usage and ordinal of the application
  collection it is in (the rule `fields` already applies) and the Input item's Null State bit. A GAMEPAD is a
  Generic Desktop application collection whose usage is Game Pad (0x05) or Joystick (0x04) and which carries
  at least one mapped control; each such collection is one gamepad, so a two-player adapter declaring two
  under two report ids is two gamepads. `Layout::has_gamepad` joins `is_useful`. `fields` is not used for the
  input path: `Layout` is what the pointer and key decoders walk, so it is where the exclusion below must be.
- [ ] A GAMEPAD IS NOT A POINTER, A KEYBOARD OR A TOUCH SURFACE: segments inside a gamepad collection are
  excluded from `has_pointer`, `has_keyboard`, `has_consumer`, `has_digitizer`, `keys_diff`, `pointer_fold`
  and `contacts`, so its stick no longer moves the console cursor and its buttons no longer click. The
  inventory lists the device as `gamepad` (a new kind after `dfu`, ranked below keyboard and touch and above
  pointer), and the driver's online line says `(gamepad)` when one is bound.
- [ ] `Layout::gamepads` MAPS a report onto the record. AXES are the variable fields on the Generic Desktop page
  with usages X through Wheel (0x30..0x38) and on the Simulation page, in bit order, at most eight, carrying
  their logical minimum and maximum and read in the signedness the descriptor declared. BUTTONS are the
  variable one-bit Button-page fields for buttons 1..32; array-form buttons and buttons past 32 are not mapped.
  HATS are Hat Switch (0x39) fields, at most two, whose logical range has 8 positions (the value less the
  minimum is the direction) or 4 (twice that); a hat of any other range is not mapped. Anything else in the
  collection is not mapped and costs nothing, and the collection's other controls still are.
- [ ] VALUES OUTSIDE A FIELD'S DECLARED RANGE ARE NOT CLAMPED INTO PLAUSIBLE ONES, and centred is not an error:
  - A HAT outside its range is CENTRED, whether or not the descriptor set Null State: HID 1.11 section 6.2.2.5
    makes a released hat exactly such a value, and devices that omit the flag send it too.
  - An AXIS in a Null State field outside its range is "no value": the axis keeps its previous value.
  - An AXIS WITHOUT Null State outside its range is refused: THAT FIELD keeps its previous value, the rest of
    the report applies, and the driver says so once per gamepad.
- [ ] THE xHCI HID MODULE BINDS EVERY HID INTERFACE OF A DEVICE, as the serial module brings up every port, up
  to four: each with its own interrupt endpoint and ring, its OWN REPORT PAGE (the device's data page carries
  its control transfers and cannot be shared by several standing reports), its own layout, previous reports
  and gamepad states, and the boot-keyboard fallback applied per interface. All of a device's endpoints are
  added in one Configure Endpoint command, and reports are routed by slot and endpoint. `Hids` holds a device
  once, with its interfaces. A device is bound when at least one interface is useful; the others give their
  ring and page back.
- [ ] EACH GAMEPAD IS PUBLISHED on the `gamepad` provider, whose token is appended LAST in the offer list
  because a token is a position: an ARRIVAL at bind labelled `usb VVVV:PPPP port P if I` (with `pad N` for a
  second collection in one interface), a STATE per changed report, and a DEPARTURE from the detach path -
  which today releases the device and tells nobody - for every gamepad of every interface the unplugged port
  carried, before its rings and pages are released. The handle is a per-driver counter, so a replug is a new
  handle.

## P02M0192 - The tool

- [ ] `gamepad`, a shipped text tool beside `lsusb`, declared in the manifest like it and granted
  `input-gamepad` and nothing else. FULL-SCREEN BY DEFAULT, like `watch` and `less`: the alternate screen, raw
  input, and one line per connected gamepad - its number, its label, its pressed buttons by number, each axis
  by name (X, Y, Z, Rx, Ry, Rz, Slider, Dial, Wheel, the Simulation names, or the usage in hex) with its value
  and range, each hat as N, NE, ... NW or centred - redrawn in place as states arrive, with arrivals and
  departures shown in a status line and an empty screen saying that no gamepad is connected. `q` or Ctrl+C
  leaves, and every exit path restores the terminal. A refused or closed stream (a graphical application holds
  the display, a protected session is up, another program already watches) is reported with those causes and
  the tool exits non-zero.
- [ ] `gamepad --lines`, THE SAME STREAM AS LINES, for a log, a pipe and a gate: `gamepad: watching` once the
  stream is open, then one line per event - `gamepad: present N label=... axes=X:0..255,Y:0..255,...
  buttons=16 hats=1`, `gamepad: arrived N ...`, `gamepad: state N buttons=1,16 axes=0,128,128,255 hats=E`
  (with `buttons=none` and `hats=centred`), `gamepad: departed N` - and `gamepad: closed` when the stream ends.
  It exits when the stream closes or when a line cannot be written because its reader has gone.

## P02M0192 - Fixtures and gates

- [ ] THE USB DEVICE. `usb-gadget.sh`'s `hid-gamepad` descriptor gains a hat - a four-bit Hat Switch over 0..7
  (physical 0..315 degrees) with the NULL STATE flag, then four bits of padding - so its report is seven bytes;
  and a new kind, `hid-gamepad-pair`, puts TWO such functions in one configuration (`hid.usb0`, `hid.usb1`) as
  `acm-pair` puts two serial ports. ONE COMPOSITE DEVICE, UNPLUGGED WHOLE: the harness has one gadget
  controller and one free root port (the hub is on 1, the stick on 2, the UAS device on 4), a device behind
  the hub leaves without the driver hearing it, and a function cannot be unlinked from a bound gadget. So the
  USB proof unplugs the device and sees both gamepads leave, and "one leaves while the other keeps working" is
  proved at the service level and in the tool's gate.
- [ ] THE FAR END, `gamepad-source.py`, started by `test-kernel.sh` for `hid-gamepad-pair` and stopped by its
  teardown like the other gadget daemons. It finds each function's device node by the `dev` attribute of its
  configfs directory rather than assuming `/dev/hidgN` numbering, waits for the GUEST's configuration
  (`gadget_state`), and plays LEVELS rather than edges, each held for two hundred reports - a write to a HID
  function waits until the guest has taken the report before it, so the holds are paced by the guest and not by
  the host's clock: (1) interface 0 holds button 1 with X at 0, interface 1 holds button 16, the hat east and Rz
  at 255, every other axis 128; (2) both released, the hat at its null value 15; (3) it unbinds the gadget,
  which to the guest is the device unplugged, as `printer-sink.py` does. `test-kernel.sh` adds the kind to the
  root-port-3 list and builds, tears down and verifies the gadget under its existing exit trap, as for every
  gadget kind.
- [ ] THE USB PROOF, in the kernel's hardware suite where the other USB classes are proved:
  `kernel.hardware.usb_gamepads_report_which_pad_pressed_what`, tagged `Drivers, Usb, Slow`, run with
  `USB_GADGET=hid-gamepad-pair`. The test binds the controller, plays InputService's side of the `gamepad`
  provider, and connects to the `pointer` provider as well. It asserts two arrivals with distinct handles and
  labels naming interfaces 0 and 1, each with four axes over 0..255, sixteen buttons and one hat; the held
  levels on the right gamepad and NEVER on the other; the released level with the hat CENTRED - the null state a
  range check would have refused; NO pointer frame at any point; and both departures after the unplug. Without
  the gadget it prints the suite's `NOT RUN` line as every gadget test does, and THE ITEM IS NOT CLOSED ON A
  `NOT RUN`: its evidence is an x86_64 run in which it ran. The ports are a separate measurement, as for the
  other USB classes.
- [ ] THE SERVICE-LEVEL PROOF, in the kernel's services suite:
  `kernel.services.gamepads_reach_the_focus_owner_and_the_console_watcher_by_identity`, standing in for the
  drivers as every InputService test does, with a catalogue helper that keeps the gamepad subscription open.
  Two gamepads from one provider and a third from a provider published later on that subscription arrive
  under three distinct ids; a state on one reaches the consumer under that id alone; one departs and the others
  keep reporting; a provider's closed connection departs its gamepads; the console stream is refused a second
  time while open, is released and closed when a surface takes focus, and is refused while a surface holds it;
  the graphical stream refuses a forged proof, snapshots on the valid one and releases on focus loss; arming
  the protected session closes both and refuses new ones; a malformed or foreign frame changes nothing. Every
  existing InputService test answers the new fourth catalogue subscription.
- [ ] THE IN-GUEST FIXTURE, for the tool's gate. `gamepad_fixture` is a development-only driver bound to QEMU's
  `edu` test function at the pinned address 00:17.0 (the other fixtures hold 0x18..0x1e), publishing a
  `gamepad` provider over the production wire and a `fixture-control` endpoint serving the development-only
  `gamepad-fixture` interface in `input.lsidl`: `attach(label)` makes a gamepad of the harness's shape - X, Y, Z
  and Rz over 0..255, sixteen buttons, one hat - and returns its handle; `report(handle, buttons, hat, axes)`;
  `detach(handle)`. `gamepadcheck` is a development-only probe whose policy row grants `fixture-control`. The
  fixture is not a claim about USB: it delivers the frames a driver would, which is the half the USB proof does
  not reach.
- [ ] A COLD DEVELOPMENT SCENARIO GATE, `qemu-gamepad-tool` (`src/tools/check-gamepad-tool.sh`, x86_64, on
  `guest-gate.sh` with the fixture's `edu` device and no NIC, registered in `check.sh`), which types ONE line:
  `gamepad --lines | gamepadcheck`. THE PIPE IS THE SYNCHRONISATION: the probe reads the tool's own lines,
  waits for `gamepad: watching` before it touches the fixture, and after each step waits, bounded, for the line
  that step must produce before taking the next - so nothing is scripted ahead of a tool that is not
  listening, and a line for the wrong gamepad during a step fails it. The steps: two gamepads attach and arrive
  under two ids; button 3 pressed on the SECOND shows on the second and not the first; releasing it clears it;
  X on the first moved to 0 and then to 255 shows the range's ends; the second's hat moved east and back shows
  `E` and `centred`; the first detaches, its departure shows, and a button on the second still shows; the first
  attaches again and arrives under a NEW id. The probe then prints `gamepadcheck: PASS which gamepad pressed
  what`, closes its input and detaches what is left - whose departure lines the tool cannot write to a closed
  pipe, which ends it. The gate asserts the fixture's online line and the PASS line and fails on any `FAIL`.

## P02M0192 - Verification

- [ ] Host tests: `driver_protocol::gamepad` frames round-trip and every malformed one is refused; the parser
  and the mapping over the gadget's exact descriptor with its hat, a joystick with Simulation-page throttle and
  rudder, a two-player descriptor with two Game Pad collections under two report ids, and hostile variants -
  more than eight axes, more than 32 buttons, a five-position hat, a Game Pad collection with no mapped control,
  an out-of-range axis with and without Null State, an out-of-range hat without it. And the regression bar,
  asserted rather than assumed: the boot keyboard, a relative mouse and QEMU's tablet decode exactly as
  before, and the gamepad descriptor folds into no pointer and no key. The services-suite and hardware-suite
  tests above; the gates `declared-interfaces`, `provider-routing`, `no-fixed-provider-slots` and
  `source-hygiene`; the aarch64 and riscv64 cross-builds; the dynamic report refreshed for the tool.

EXCLUDES: force feedback and rumble (an output report, and a separate authority); gamepads over Bluetooth -
P02M0194 brings them into InputService over the `bluetooth-profile` contract InputService already reads the
mouse from, mapped onto this vocabulary and joining the same gamepad set as another source, and never as a
`gamepad` catalogue provider, because only a driver binding publishes; the Game page's own controls; button
remapping and calibration profiles; changing how the input, pointer and touch kinds are discovered.
