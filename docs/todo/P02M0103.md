# P02M0103 - Future-ready 3D graphics foundation + software-rendered scene

Status: FUTURE TRACK, PLANNED AFTER P02M0096a AND P02M0097; INDEPENDENT OF P02M0102 AND NOT A
PHASE-2 COMPLETION GATE. **REVISED 2026-08-14 by an outside review of the design**, checked claim by
claim against the tree - twenty-six tasks at the end of this file, and three claims that did not
survive the check, recorded there as not surviving it. The four that change the shape of the work:
the OS/WSI conventions and the renderer's coordinate conventions are two layers and this file had
them as one; the graphics device vocabulary is designed against zero consumers, which this file's own
two-consumer rule forbids elsewhere; textures and blending were optional future work and a renderer
without them is not general; and the C/C++ substrate wants TLS, which `docs/DYNAMIC_LINKING.md`
refuses by name. That last one is a hard blocker rather than a refinement. Build the OS-facing foundations that a later OpenGL, OpenGL ES
or Vulkan implementation will need, then prove
the complete application path with a bounded software 3D renderer and the polished
**3D Test SW** scene. This milestone does NOT implement or port OpenGL, OpenGL ES, Vulkan, Mesa,
Gallium, virglrenderer, Venus, a GLSL compiler or a SPIR-V compiler, and does not enable
virtio-gpu 3D acceleration. Those are separate future milestones that must reuse the
contracts and measurements established here rather than placing API policy in the kernel.

The architectural split is deliberate: OpenGL/OpenGL ES/Vulkan are userspace API
libraries; WSI, presentable images, synchronization, governed memory and access to a
capability-scoped graphics device are OS contracts; virgl/Venus/native-device protocols
belong to a backend/driver. The software renderer exercises the same window-system,
resource-lifetime, resize and frame-pacing contracts but remains an ordinary CPU client of
DisplayService. It is not a fake OpenGL implementation and no provisional `gl*`/`vk*` API
is introduced merely to draw one demo.

## P02M0103a - API-neutral graphics and porting prerequisites

- [ ] Write `docs/GRAPHICS.md` before adding interfaces. Freeze the ownership diagram and
  future integration routes: OpenGL/OpenGL ES through EGL plus a Mesa state tracker and an
  appropriate software or Gallium backend; Vulkan through a loader + ICD, with Venus as
  the likely virtualized transport; DisplayService as the EGL/Vulkan WSI and presentation
  owner; and the virtio-gpu driver as the device transport owner. Record which boundary
  validates every untrusted length/opcode/resource reference. Do not invent a common
  GL/Vulkan command language or expose virtqueue descriptors to applications.
- [ ] Extend the P02M0091 display contract with a versioned, bounded present-queue model while
  preserving the current single-surface API as a compatibility path. A presentable surface
  has an immutable pixel format, explicit extent, resize generation and two or three
  images; `acquire-next` returns one available image, `present` consumes it with a damage
  region and completion point, and release/process death returns every image. Define
  FIFO frame ordering, maximum in-flight frames, backpressure, occluded/background
  behavior, stale-generation/OUT_OF_DATE handling and console restoration. The initial
  implementation uses CPU-mappable MemoryObjects and the existing synchronous 2D scanout,
  but the contract must also permit a future non-mappable GPU image imported by
  DisplayService without changing application WSI semantics.
- [ ] Add a first-class synchronization capability suitable for graphics without making
  it graphics-specific: a monotonic timeline/fence value, signal by its owning backend,
  wait/poll integration with the scheduler, bounded waiter accounting, timeout and peer-
  death/error completion. Values never decrease or wrap silently; forged future signals,
  use-after-close, duplicate completion and wait storms fail closed. CPU rendering uses
  the same completion path so the contract is tested before a GPU backend exists.
- [ ] Define API-neutral graphics resource descriptors and checked layout helpers:
  buffers and 1D/2D/3D images, extent/mip/layer/sample counts, row/slice pitch, format,
  tiling, usage and host visibility. Every byte size/offset/subresource calculation is
  checked before allocation or mapping. Import/export transfers explicit capabilities and
  rights; it never accepts ambient integer names or raw host pointers. CPU-visible images
  use MemoryObjects initially; future device-local resources may be opaque while retaining
  the same lifetime, accounting and ownership rules.
- [ ] Add a capability-scoped graphics adapter/device/context/queue vocabulary without
  claiming an accelerated implementation. Adapter discovery reports stable identity,
  backend/capset identifiers, limits, formats, queue kinds and supported synchronization
  primitives. Contexts own all backend resources; queues accept only bounded command
  envelopes for one advertised backend/capset and return a completion fence; reset or peer
  death invalidates the context and wakes every waiter. Until a future backend installs a
  protocol-specific validator and executor, accelerated context creation/submit returns a
  typed `unsupported`, never a permissive opaque pass-through. Provide a null/reference
  backend test that validates lifetime, limits, cancellation and fence behavior without
  interpreting GPU commands.
- [ ] Integrate graphics resources with ResourceManager and SystemGraph. Charge host-
  visible bytes, device-local bytes, image count, buffer count, contexts, queued command
  bytes and in-flight submissions to the creating Domain before allocation. Publish
  bounded counters and reset/fault state without exposing command or image contents.
  Exhaustion returns typed errors and releases partial transactions; killing a Domain
  reclaims contexts, queues, mappings, imported images and waiters even if the backend is
  wedged.
- [ ] Specify pixel/color conventions once: coordinate origin, viewport orientation,
  clip-space depth range, front-face winding, normalized channel order, alpha mode,
  linear-light versus sRGB transfer, and conversion into P02M0091's B8G8R8X8 scanout. The
  software renderer follows these rules exactly; future GL/Vulkan WSI adapters perform
  explicit conversions rather than relying on host-specific defaults.
- [ ] Prepare the foreign-library/toolchain substrate needed before importing a large
  upstream graphics stack, but import no stack in this milestone. Pin cross C/C++ compiler
  and archive/link steps for the three targets; provide tested C ABI calls into allocator,
  memory/string/math, monotonic time, atomics, TLS, threads, mutex/condition/event waits,
  mapped MemoryObjects and dynamic-provider lookup. Maintain an exact required-symbol
  inventory derived from a chosen Mesa/Vulkan-loader configuration; do not grow a general
  POSIX layer or expose ambient files, processes or devices. Host build tooling must accept
  reproducible Meson/CMake-generated object lists without bypassing P02M0096a identity,
  relocation, W^X, provider and license audits.
- [ ] Record the future dependency and licensing policy before selecting upstream code.
  LiberSystem-owned implementation remains Unlicense; imported Mesa, Vulkan loader,
  compiler/runtime or conformance sources retain their own compatible notices and exact
  source/version/patch provenance. The image identity records bind generated objects to
  that inventory, and the build rejects an unreviewed license, downloaded-at-build source
  or copied implementation with lost attribution. This milestone imports none of those
  projects, but its synthetic build proves the inventory/audit path.
- [ ] Reserve future loader/ICD discovery under P02M0097's system layout. Implement a bounded,
  versioned provider manifest schema for API name/version, architecture, entry provider,
  backend/capset and required extensions. Paths are package-owned and signature/identity
  checked; no environment-variable search path, current-directory plugin load or arbitrary
  `dlopen` exists. In this milestone only a synthetic provider is discovered and rejected
  or selected in tests; no GL/Vulkan ABI is exported.
- [ ] Add hostile-input and lifecycle tests before any accelerated backend: malformed
  format/extent/pitch/mip descriptors, overflowed image sizes, invalid generations,
  duplicate acquire/present, fence races, context reset, backend death, command-envelope
  truncation, unsupported capsets, forged imports, cross-Domain handles, budget exhaustion
  and cleanup during in-flight presentation. Fuzz all parsers and checked layout helpers;
  prove that a malicious graphics client cannot map another surface, submit to another
  context, retain foreground input or leave the console scanout blank.

## P02M0103b - Bounded software 3D renderer

- [ ] Add small atomized no_std libraries rather than a monolithic app framework:
  `render-math` for `Vec2/Vec3/Vec4`, matrices, quaternions, transforms and camera
  projection; `soft3d` for scene traversal, clipping and rasterization; and existing
  `pix`/`surface` for pixel storage and presentation. Keep public scene data independent
  of DisplayService and keep the CPU backend behind one renderer boundary so a later GPU
  renderer can consume the same mesh/material/camera model without emulating OpenGL.
  Build reusable implementation as P02M0096a `.lslib` providers when at least two consumers
  or a measured ownership boundary justifies it; the demo PIE must not duplicate shared
  math/raster code.
- [ ] Implement a complete triangle pipeline: model/view/projection transforms,
  homogeneous frustum clipping (including the near plane), viewport/scissor conversion,
  indexed triangles, deterministic back-face culling, top-left fill convention,
  perspective-correct interpolation, 24- or 32-bit depth buffer, depth test/write and
  checked raster bounds. Degenerate, non-finite, off-screen and sub-pixel triangles are
  skipped deterministically and can never create an unbounded loop or out-of-range write.
- [ ] Implement materials and lighting sufficient for a real scene rather than flat debug
  triangles: per-face/base color, vertex normals, ambient term, normalized Lambert diffuse,
  Blinn-Phong specular with bounded shininess, one directional key light and one animated
  point/fill light with attenuation. Perform lighting in linear color and convert to the
  declared display transfer function on output. Textures, normal maps, shadows, skeletal
  animation and a programmable shader language remain optional future work, not hidden
  completion requirements.
- [ ] Add bounded scene resources: immutable vertex/index buffers, meshes, instances,
  transforms, camera, materials and a fixed configured maximum number of lights/draws/
  triangles per frame. Validate indices and finite transforms at ingestion, use checked
  allocation for color/depth buffers, account peak memory to the process Domain and reuse
  frame allocations. Scene traversal and clipping allocate no unbounded per-triangle
  vectors from hostile geometry.
- [ ] Add frame scheduling over the P02M0103a present queue: render into the acquired image,
  wait for completion before reuse, maintain at most the negotiated frames in flight and
  pace against monotonic time instead of busy-spinning. Resize/out-of-date recreates color
  and depth targets transactionally; allocation failure keeps or cleanly releases the old
  scene and returns control to the console. A hidden/background scene blocks or throttles
  and consumes no raw input.

## P02M0103c - 3D Test SW, the end-to-end scene

- [ ] Add one governed PIE application named **3D Test SW**, with canonical artifact
  `test3d-sw.lsexe` and only `display + input-keys` grants. It acquires a
  native/preferred present queue and renders a continuously rotating
  indexed cube above a simple ground plane. The six cube faces have visibly distinct
  material colors, correct shared-edge depth/occlusion, smooth or deliberately hard face
  normals, ambient + directional + animated point lighting and specular highlights. A
  perspective camera, dark non-flat background and ground reference make rotation and
  depth unmistakable; no face-order painter shortcut is accepted.
- [ ] Make the scene interactive and recoverable: Esc/q exits, Space pauses, R resets,
  arrow keys orbit the camera and +/- changes distance or field of view. Key-down/up state
  comes through the P02M0091 focus capability; focus loss clears held state. Resize recreates
  targets and preserves camera/animation state. Clean exit, crash, allocation failure,
  emergency kill and DisplayService restart always release images and restore the text
  console.
- [ ] Provide deterministic demo/test controls without exposing them in normal UI: fixed
  simulation time/frame, fixed camera and fixed light seed. A host renderer test produces
  a small golden/reference frame with tolerance-based color/depth comparisons rather than
  requiring bit-identical cross-architecture floating point. The live app remains clock-
  driven and visibly animated.
- [ ] Host tests cover vector/matrix/quaternion identities, camera/frustum transforms,
  clipping every plane, winding/culling, perspective interpolation, depth ordering,
  shared-edge fill, non-finite/degenerate input, lighting/color transfer and guarded
  canaries around color/depth targets. Property/fuzz tests feed hostile meshes, indices,
  transforms, extents and viewport/scissor rectangles under strict allocation limits.
- [ ] Governed kernel tests launch the staged PIE against stand-in Display/Input services
  and assert acquire -> multiple distinct presents -> resize/recreate -> key interaction ->
  release/exit, plus crash restoration and denied-capability behavior. Package audits prove
  ET_DYN/provider identity/order, exact grants and no static duplicate renderer/runtime.
- [ ] Live QEMU validation on x86_64 captures at least three timed frames and uses pixel
  checks to prove the scene is nonblank, the projected cube occupies a bounded central
  region, all six material colors appear across the captured rotation, depth occlusion and
  lighting gradients exist, and successive frames differ while the background/console do
  not leak through. Capture after resize on desktop and mobile-like aspect ratios; q must
  restore the console. AArch64 and RISC-V must cross-build and run deterministic renderer
  tests; live screenshot parity uses tolerances where emulation cost is practical.
- [ ] Measure release performance and memory at 320x240, 640x480 and 800x600. The required
  floor is a stable 30 FPS at 640x480 on the documented x86_64 QEMU/KVM host with no frame
  allocation after warm-up, bounded present latency and a reported color/depth/scene peak.
  Record transform, clipping, raster, lighting and present times separately in
  `docs/PERF.md`; optimize tile/bin traversal or fixed-point edge evaluation only from
  measurements, without architecture-specific output corruption or unsafe unchecked
  indexing.
- [ ] Publish `docs/SOFTWARE_3D.md`: coordinate/color conventions, pipeline stages,
  clipping/raster rules, scene/material format, memory formulas, controls, performance
  table and the exact boundary a future Mesa/Gallium/Vulkan backend replaces. Include a
  screenshot of the actual 3D Test SW scene and a tri-architecture validation matrix.
- Done when: the API-neutral WSI/synchronization/resource/lifecycle contracts are bounded,
  capability-scoped, documented and hostile-input tested; the foreign-driver/provider
  integration substrate has a reproducible synthetic proof but no accelerated API
  implementation; `soft3d` renders clipped, depth-tested and lit indexed geometry; and a
  governed dynamically linked `test3d-sw.lsexe` continuously shows the interactive
  **3D Test SW** scene with its rotating six-color lit cube, survives
  resize/focus loss/failure, restores the console on
  every exit path, meets the measured 640x480 frame budget and passes host, package,
  focused QEMU and tri-architecture gates.
- Explicitly deferred: actual EGL/OpenGL/OpenGL ES/Vulkan entry points and conformance;
  Mesa/Gallium, LLVM shader compilation, GLSL/SPIR-V compilation, virglrenderer/Venus,
  virtio-gpu context/blob/3D command execution, native hardware drivers, compute, ray
  tracing, compositor/windowed multi-app presentation and desktop effects. Each requires a
  separately approved milestone and must consume P02M0103 contracts rather than weakening
  capability, validation, accounting or identity gates.
- Concept: P02M0014/P02M0038 (virtio-gpu 2D scanout and resize), P02M0091 (surface/input app platform),
  P02M0093/P02M0096a (shared providers and PIE ownership), P02M0097 (final userspace/system layout),
  P02M0008/P02M0010 (observability and governed resources), and the future desktop/GPU phases.


## An outside review of this design, checked against the tree

2026-08-14, before any of this is implemented - which is the right time for it, because everything
below is a change to a contract rather than to code.

Every claim was checked against this tree before being written down, and three did not survive that
check. They are recorded here rather than dropped, because a review is a set of claims and this file
should say which of them held.

### What the review got wrong

- **"There is no `graphics` library category and P02M0097's list has to be extended."** There is no
  list. `system-manifest`'s `library_category` DERIVES the category from the path -
  `user/libs/<category>/<leaf>` - and falls back to a named table only for the handful of libraries
  that live outside `user/libs/`. So `src/user/libs/graphics/soft3d/` stages to
  `vol://system/lib/graphics/soft3d.lslib` today, with no gate change at all. The recommendation is
  right and costs nothing; the reason given for it was wrong.
- **"Do not assume LLVMpipe; softpipe is the more portable first experiment."** This file never
  names LLVMpipe. The underlying fact is worth keeping - llvmpipe is an LLVM JIT rasterizer with
  x86/x86-64/ppc64le paths, and two of this system's three targets are neither - so it belongs in
  `GRAPHICS.md` as a constraint on the eventual choice, not as a correction to something this file
  said.
- **"Say Venus is a candidate rather than the Vulkan path."** It already says "with Venus as **the
  likely** virtualized transport". No change.

### The tasks the review does justify

- [ ] **Split the conventions item in two: what the OS owns and what the renderer owns.** The
  present item asks for "coordinate origin, viewport orientation, clip-space depth range, front-face
  winding, channel order, alpha and sRGB" in one place, and those are two different layers. Pixel
  format, colour space and transfer function, alpha mode, row direction, image origin, pitch and
  extent are a description of MEMORY and belong to DisplayService. Clip-space depth range,
  handedness, winding and the viewport transform are a renderer contract and belong to `soft3d`.
  The test of whether the split is right: a future Vulkan ICD must be able to use this system's WSI
  without adopting one single 3D convention from the software renderer. Today it could not.

- [ ] **Negotiate the image count instead of writing "two or three" into the contract.** The server
  publishes `min_images` and `max_images`, the client asks for a count inside that range, and the
  first implementation reports 2..=3. The number is an implementation property; putting it in the
  contract means the contract changes when the implementation does.

- [ ] **Say what FIFO does and does not require, and make the mode an enum.** `present_mode` with
  one value supported today (`Fifo`) and the rest refused by name. FIFO must mean the PRESENTED
  order is the queue order; it must not require that images are presented in the order they were
  acquired, because a producer that renders two frames concurrently finishes them in whatever order
  it finishes them.

- [ ] **Specify the present lifecycle precisely enough to implement twice.** When does an acquired
  image become writable; what exactly does `present` wait for on the producer's side; when does the
  image return to the available pool; what happens to in-flight images on process death and on a
  DisplayService restart. `acquire-next` needs wait / timeout / cancel semantics rather than one
  blocking shape. This is the item where a vague contract costs the most later: the difference
  between "rendering into this image is finished" and "the compositor is finished with this image"
  is invisible on a synchronous CPU scanout and load-bearing on anything else.

- [ ] **Damage is a bounded array of rectangles, not one rectangle.** `surface::present` takes a
  single `Rect` today, which is the simple case rather than the general one. A bounded array with a
  documented maximum, and a defined meaning for "empty" (nothing changed) and for the full-extent
  case.

- [ ] **Defer the parts of the graphics device vocabulary that no consumer exercises.** This
  milestone's own renderer item says to build a shared library "when at least two consumers or a
  measured ownership boundary justifies it" - and then designs an adapter/device/context/queue
  vocabulary, a capset model, device-local image abstractions and backend command envelopes against
  ZERO consumers. The present queue is used by the software renderer and stays. The rest is a
  transport abstraction for a backend that does not exist, and the risk is exactly the one this file
  is otherwise careful about: freezing a boundary against an imagined implementation. Keep what the
  software renderer uses; design the device vocabulary against a real Mesa/Vulkan prototype.

- [ ] **Name the TLS problem, and gate it.** `docs/DYNAMIC_LINKING.md` refuses every relocation form
  outside a named set, "including TLS", and the porting-prerequisites item asks for a tested C ABI
  including TLS. Those two cannot both be true. A `tls_get()` function is not the answer either: if
  an upstream C/C++ build emits `__thread` / `thread_local`, it emits TLS RELOCATIONS, and the
  loader refuses them. So the prerequisite is one of two things and the milestone has to say which:
  ELF `PT_TLS` plus the per-architecture TLS relocations in the loader, or a demonstrated upstream
  configuration that generates none. Gate it: a foreign binary containing an unsupported TLS
  relocation is refused, and the prerequisite is not done until the selected configuration produces
  zero of them or the loader supports them.

- [ ] **Audit ABI requirements, not just a function list.** Exceptions and unwind tables, RTTI,
  atomics and their alignment requirements, stack alignment at foreign call boundaries,
  compiler-rt/libgcc helper symbols, `dlopen`-style dynamic loading, pthread-like primitives,
  once-init, rwlocks, and generated config headers. A list of libc functions answers "will it link";
  these answer "will it run".

- [ ] **Give `render-math` a contract, not a type list.** Row-major or column-major storage; `M*v`
  or `v*M`; handedness; angle units; what a projection constructor produces (name them
  `perspective_rh_zo` and so on rather than one implicit `perspective`); quaternion normalisation
  rules; and the answer for a singular matrix and for NaN/Inf inputs. Every one of these is a silent
  wrong-picture bug rather than a failure. `libm` is already a dependency in this tree's audio
  libraries, so no new maths dependency is needed for `sin`/`cos`/`sqrt`.

- [ ] **Put a scene layer between the maths and the rasterizer.** `render-math` = pure maths;
  `render-scene` = mesh, material, texture, camera, light, render state and draw list, with no
  DisplayService dependency; `soft3d` = the CPU implementation behind the renderer boundary. As
  written, `soft3d` owns both the public scene model and the rasterizer, so a future GPU renderer
  would have to depend on the software rasterizer crate to reuse the model.

- [ ] **Textures are not optional for a general renderer.** Without them this is a good demo
  rasterizer of coloured polygons. A first version needs `Texture2D`, UV coordinates,
  perspective-correct UV interpolation, one explicitly named small set of formats, nearest and
  bilinear sampling, and clamp and repeat addressing. Mipmapping, anisotropic filtering, compressed
  formats and normal maps stay optional. This is a scope INCREASE and is written as one deliberately.

- [ ] **And minimal blending.** Opaque and source-over alpha, plus `depth_write = false`. Sorting
  transparent geometry can stay the caller's job; refusing to blend at all cannot.

- [ ] **Pick one depth format.** "24- or 32-bit" is two contracts. For a CPU rasterizer: 32-bit
  `u32` normalised depth, with the mapping `[0,1] -> [0, 0xffff_ffff]` written down, an explicit
  clear value and an explicit compare op. No packed 24-bit handling, and the same coverage and depth
  results on all three architectures.

- [ ] **Stop skipping sub-pixel triangles.** A triangle smaller than a pixel is not degenerate: it
  can still contain a sample centre and must still produce a fragment. Refuse the degenerate and the
  non-finite; put everything else through the ordinary coverage test, where a triangle covering no
  sample simply produces nothing. As written, thin geometry disappears.

- [ ] **Specify the sample point and the edge arithmetic.** The top-left rule alone does not
  determine coverage. Sample at `(x + 0.5, y + 0.5)`, say how viewport coordinates are quantised,
  and use fixed-point edge equations in `i64` so coverage and shared-edge decisions are identical on
  x86_64, aarch64 and riscv64. Float stays for interpolation and shading. The golden-frame test
  spans three architectures, so this is what decides whether that test can exist at all.

- [ ] **Specify the clipper.** Six clip planes by name, the behaviour at `w == 0`, at NaN/Inf, and
  for a zero intersection denominator. Sutherland-Hodgman over two fixed-size arrays and a fan
  triangulation afterwards - which is also what makes the memory bound a proof rather than a claim.

- [ ] **Transform normals with the inverse transpose.** `model * normal` is wrong under non-uniform
  scale, and the item that asks for vertex normals does not say how they transform. Say
  inverse-transpose of the upper 3x3, then normalise, and say what happens when the matrix is
  singular or non-finite.

- [ ] **Decide per-vertex or per-fragment lighting.** For a Blinn-Phong specular highlight to look
  like one, normals and positions interpolate and the lighting is per fragment. Add an `Unlit`
  material as well: debug geometry, a textured UI element and a plain mesh should not be forced
  through Lambert plus Blinn-Phong. The point-light attenuation needs a written formula and a clamp
  near zero distance.

- [ ] **Limits belong to the caller, not to the crate.** `RendererLimits` - `max_draws`,
  `max_input_triangles`, `max_clipped_vertices`, `max_lights`, `max_texture_bytes`,
  `max_scratch_bytes` - passed at construction. Bounded either way; a small application does not pay
  a large one's reservation, and a large one is not stopped by a constant somebody chose.

- [ ] **Allow transient geometry.** Immutable vertex and index buffers are right for a static mesh
  and wrong as the only route: a general renderer changes some geometry every frame. A borrowed
  `MeshView` valid for one render call, beside the long-lived immutable resources.

- [ ] **Give `surface` a safe borrowed target before the demo exists.** `imgview` builds a
  `&mut [u8]` out of `Mapping::addr()` with `from_raw_parts_mut`
  (`src/user/apps/tools/src/imgview.rs:540`). A `Mapping::with_target(|target| ...)` or a
  lifetime-bound `pixels_mut()` puts that unsafety in one library instead of in every application
  that draws. This is worth doing whether or not the 3D work happens.

- [ ] **The renderer borrows its colour target rather than owning it.** Rendering into the acquired
  present image is the whole point of the present queue; a renderer that allocates its own colour
  buffer copies every frame for nothing. Depth and scratch are the renderer's own and are recreated
  transactionally on resize.

- [ ] **Keep the 30 FPS demo gate and add a real benchmark beside it.** A rotating cube over a
  ground plane at 640x480 is light enough that a slow rasterizer passes. A deterministic benchmark
  scene with a fixed triangle count, deliberate overdraw, clipping and textures, reporting
  triangles/s, shaded fragments/s and nanoseconds per stage. And pin the environment the numbers
  mean anything in: vCPU count, QEMU version and configuration, CPU model, profile flags, and
  whether the clock is guest or host.

- [ ] **Rewrite the "all six material colors appear" check.** Which faces are visible depends on the
  rotation axis, the camera and the lighting - the bottom face may never be visible from an ordinary
  camera, and shading changes the RGB that a classifier is looking for. Deterministic test poses
  where the visible face is known in advance, and let the live animation test assert only that the
  image changes.

- [ ] **A golden frame is a regression test, not a correctness oracle.** It proves the output has
  not changed, not that it was ever right. Add small independent checks: a tiny reference rasterizer
  over 16x16 or 32x32 tiles, or differential tests per pipeline stage. The cheapest one worth having
  immediately is two triangles forming a quad - across the shared edge there must be neither a gap
  nor a doubly-covered pixel.

- [ ] **A typed `RendererError` and a no-panic contract.** `InvalidMesh`, `InvalidTransform`,
  `TooLarge`, `OutOfMemory`, `UnsupportedFormat`, `TargetMismatch`, `NonFinite`. The fuzz test then
  asserts something stronger than "no out-of-bounds write": every public input ends in a valid frame
  or a typed error, never a panic.
