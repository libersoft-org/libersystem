true of the INTEGER half of a rasteriser and is not achievable for the floating-point half - operand

clear, storage and comparison. 2D COVERAGE IS NOT IN THAT LIST and the word appeared unqualified
here for two passes while the paragraph above it said the opposite (corrected 2026-08-30).
TOLERANCE-BASED: interpolated floating attributes, filtering, shading and the final RGB conversion.

## Who consumes this API, and who instantiates the backend

Added 2026-08-30, architecture premise corrected 2026-09-08. This file promises public `render2d`
and `render3d` APIs "for ordinary applications written by other people" and must name their access
boundary. `docs/CONCEPT_EN.md` defines native typed capability IPC/ABI as the default application
contract; WebAssembly/WASI components are the first recommended host on top of it, not the
application ABI itself. `docs/DYNAMIC_LINKING.md` separately limits the `.lslib` Rust ABI to an
internal system-image build optimisation, not a cross-release third-party ABI. The native IPC
contract therefore exists, but it does not by itself expose these in-process rendering APIs to
external applications. That graphics-specific boundary must be specified separately; an
in-process `DrawList` does not create it.

The answer this file takes, stated so it stops being ambiguous: **these are INTERNAL SAME-IMAGE RUST
APIs in v1.** Their consumers are in-tree applications and toolkits built from the same tree, and
that is what "public" means here - public within the image, versioned with it, not an ABI anyone
outside the release links against. A native SDK boundary or a Wasm-host graphics adapter, each with
its own version, resource, copy, lifetime and capability semantics, is a SEPARATELY APPROVED
milestone and is the only thing that makes the third-party claim true. Until one exists this file
does not make that claim.

AND SOMETHING HAS TO INSTANTIATE THE BACKEND. This file says applications never name `soft2d` or
`soft3d` and that only a backend depends on them, while deferring the OS graphics device and factory
vocabulary and naming no crate or service that selects and creates the software backend - so an
in-tree application must either name the backend directly, breaking the layering, or invent a
factory. v1 permits COMPILE-TIME SELECTION: one small composition crate owns the choice, every
consumer takes the trait, and the crate is the single place `soft2d` is named. A runtime
device/factory vocabulary with manifest and provider edges arrives with the first second backend and
not before, because that is the milestone that can test it.

AND THE 3D PROFILE IS NOT DECLARED STABLE AGAINST ONE BACKEND. The command, resource and submission model
is validated against a concrete SECOND backend - a GPU backend, or a deliberately different-shaped
second implementation - before "Profile 1 is stable" is said of it, by this file's own rule that a
shape with fewer than two real consumers is a guess.

A sixth pass changed what this milestone is FOR. Every pass before it improved the inside of a
document whose purpose was "enough graphics to prove a present queue and then draw a software cube".
The real purpose is a platform for a desktop environment, a mobile shell and ordinary applications
written by other people. That pass introduced `render2d` above `soft2d`, because `soft2d` was both
the public API and the CPU implementation of it, and it un-deferred paths, antialiasing, transforms,
clipping, layers, compositing and text - which are not advanced features a desktop wants eventually
but what an icon, a button, a scroll viewport and a line of text are MADE OF.

**A seventh pass finished that correction, because the sixth applied it to one dimension and not the
other, and because "complete" was still an adjective rather than a gate.** Two changes:

  - **`render3d` was missing, and its absence was the same mistake the sixth pass had just fixed.**
    The layering read `render-scene -> soft3d` and was described as the equivalent of
    `render2d -> soft2d`. It is not. `render2d` is a DRAWING AND COMMAND API; `render-scene` is a
    retained DATA MODEL. The 3D counterpart of `render2d` is a resource, pipeline, pass and command
    API - and with it missing, an application wanting a CAD viewport, a custom engine, a
    postprocessing chain, render-to-texture or a non-standard material had nowhere to go except the
    scene graph or the CPU rasteriser. The stack is now `scene3d -> render3d -> soft3d`, and a future
    GPU backend implements `render3d` rather than a whole scene graph.
  - **"Complete" is now two finite PROFILES rather than a word.** `Render2D Core Profile 1` and
    `Render3D Core Profile 1` each enumerate a closed list of features that the public API expresses,
    the software backend implements ENTIRELY, and a conformance suite covers. Inside a profile a
    backend may NOT answer `Unsupported`; that variant exists only for post-profile extensions. This
    is what converts "a complete software library" from an intention into something a gate can refuse.

That pass also removed three phrases that quietly capped the design: `conic gradient in the type
space even if the first backend refuses it`, `non-separable blend modes are deferred by name`, and -
the largest - `soft3d implements a subset and returns a typed Unsupported for the rest`, together
with the scene-model item that required hierarchy, passes, offscreen targets, instancing and skinning
only to be ADMISSIBLE rather than implemented. A library whose backend may decline its own API is a
specification for a demo.

**An eighth pass closed the contracts INSIDE those layers, and corrected a guarantee the seventh pass
had quietly broken.** The architecture did not move; four direct contradictions and one whole class of
under-specification did. The contradictions: the compositing line said "12 Porter-Duff operators" over
a list of thirteen (`Plus` is additive and is not one of them); the 3D profile named five primitive
topologies and the backend then promised "all six"; `sRGB8A8` sat in the format list while
`ColorSpace` already carried the transfer function, so two places could disagree about whether bytes
are encoded; and the 2D part required loading a real scalable font while the milestone that parses
font files, `P02M0136`, depends on this one - a dependency cycle in which each milestone waits for the
other or writes a throwaway parser twice.

The broken guarantee is the one worth naming on its own. The fifth pass promised BIT-EXACT geometry
classification and clipping topology, and that was achievable when the vertex pipeline was
fixed-function. The seventh pass added a PROGRAMMABLE vertex stage, whose output position is computed
by floating-point shader code that the same split puts on the tolerance side - so the input to a
bit-exact stage stopped being bit-exact, and two architectures could classify a vertex at
`z = +/-1e-8` differently and BOTH conform. A guarantee that its own inputs cannot support is worse
than no guarantee. The fix is to make the seam explicit: the clip-space POSITION output has strict
floating-point semantics of its own - fixed operand order, no FMA contraction, canonical NaN, stated
rounding - and is then QUANTISED into a canonical clip representation before any classification runs.
Everything downstream of that quantisation is bit-exact; every other varying stays tolerance-based.

The under-specified class is everything a profile entry names without defining: what a tone-mapping
operator or a dither actually is, what a blend factor set contains, where MSAA samples sit, what a

- [x] Say which alpha combinations are VALID and which are merely unimplemented, and fix the
  byte-level rules two implementations otherwise answer differently. `AlphaMode` is `Opaque`,
  `Straight`, `Premultiplied`; an `X8` format is `Opaque` only, so `Straight` and `Premultiplied` on
  one are a type error and not an unsupported case; an `A8` format carries alpha and nothing else.
  Under `Opaque` an alpha channel reads and writes 1.0 in its storage representation (the maximum
  channel integer for UNORM, 1.0 for float), rather than being carried through unexamined.
  Under `Premultiplied`, normalized bounded color storage may treat a channel above alpha as clamped
  to alpha. Floating linear HDR/wide-gamut intermediates retain valid negative or above-alpha values
  until explicit output conversion; the alpha rule must not erase the color model's allowed range.
  Freeze zero-alpha canonicalization and non-finite handling in the storage/semantics matrix.
  Channel order is defined by the format
  NAME and never by host endianness; float values convert to integer by round-half-away-from-zero

  THE NUMBERS. `graphics-profile::thresholds` freezes render2d antialiasing coverage at `<= 2/255`
  absolute per pixel against the analytic area, with `<= 1/255` mean over the covered region.
  `soft2d`'s rasteriser is EXACT IN X AND SAMPLED IN Y: each pixel row is cut into sixteen
  sub-scanlines and the crossings on each are computed exactly, so a vertical edge is analytic and a
  near-horizontal one is quantised to a sixteenth of a level. Half a step is a thirty-second, which
  is `8/255` - four times the frozen bound. The measurement: an axis-aligned rectangle whose top edge
  falls at `y = 26.4` is drawn with coverage `10/16 = 0.625` where the area is `0.6`, a difference of
  `6/255`, and the pixels a VERTICAL edge cuts agree to the last bit.
  THE RASTERISER'S OWN COMMENT SAYS THE SAMPLING "buys accuracy the tolerance does not ask for",
  which is the claim this measurement contradicts. One of the two is wrong and the specification is
  the one that was frozen, so the implementation is what moves.
  THE FIX IS NOT MORE SAMPLES. Reaching `2/255` by sampling needs 128 sub-scanlines, which is eight
  times the work on a path that already has a performance floor it does not meet. The answer is an
  ANALYTIC AREA rasteriser - the signed-area cell accumulation every serious 2D rasteriser uses -
  which is exact in both directions AND cheaper than sixteen sweeps, so this item and the performance
  floor above it are the same change rather than competing ones.
  DONE 2026-09-14. THE RASTERISER ACCUMULATES AREA. Each edge is clipped to the pixel row it crosses
  and then to each pixel column it passes through, and two numbers are accumulated per pixel: the
  signed vertical extent the edge spans there, and the area of that pixel lying to the RIGHT of it. A
  left-to-right sweep of the row turns the pair into the winding-weighted coverage of every pixel,
  exactly, at any sub-pixel position, in both directions. The fill rule is applied to that accumulated
  value - saturated for non-zero, folded for even-odd - rather than to a per-sub-scanline winding.
  THE ALIASED PATH IS STILL A SAMPLE AT THE PIXEL'S CENTRE, and has to be: "a pixel is in or it is

  different answer for a sliver narrower than half a pixel.

## P02M0103g - soft3d, the complete CPU implementation of Profile 1

The software 3D backend. It implements the WHOLE of `Render3D Core Profile 1`; a profile feature it
cannot execute is a defect, not an `Unsupported`.

- [x] Split `soft3d` into PREPARE and EXECUTE the way `soft2d` is split, and for the same reason:
  resource upload, shader validation and lowering, pipeline creation, command-list validation and
  tile/bin scratch reservation all happen BEFORE submission, and `submit(prepared)` then allocates
  nothing in steady state. Its internal execute phase fulfills the `Submission` contract from `e`. Without that boundary, programmable shaders, pipeline creation, mipmap
  generation and the pass graph each become a place a frame can start allocating, and the
  no-steady-state-allocation requirement in this milestone becomes untestable on the 3D side while
  being enforced on the 2D one.
  DONE 2026-09-14. `soft3d::frame` is the boundary: `prepare` validates both shader modules against
  the device's limits, checks that the two stages agree about every varying LOCATION AND TYPE, checks
  that the pipeline's shading rate is the one its fragment stage's inputs force, refuses a draw
  naming a pipeline the plan does not hold or asking for zero instances, and sizes the tile and bin

  A FIXTURE ASSERTS THE STEADY STATE RATHER THAN ASSUMING IT: three identical frames, with the
  scratch capacity read between them, and the assertion that it did not grow after the first - which
  is what makes "allocates nothing in steady state" a property of the boundary rather than of the

  the already-completed-ticket shape the submission model was written to admit beside a GPU

- [x] Implement the rasteriser with these conventions fixed: sample points at pixel centres
  `(x + 0.5, y + 0.5)` at 1x, and the frozen profile positions at 2x/4x; fixed-point edge
  equations rather than floating-point comparisons, so
  coverage is exact and shared edges cannot double-fill or leave a seam; the top-left fill rule;
  deterministic back-face culling by winding; perspective-correct interpolation. Degenerate and
  off-screen primitives are skipped deterministically; non-finite positions are typed refusals

  skipped: it either covers a sample point or it does not, and dropping it by size makes small
  geometry flicker as the camera moves.

  The numbers, because "fixed-point" without them is half a contract and identical coverage on three
  architectures is what the other half decides: `SUBPIXEL_BITS = 8`, `MAX_RASTER_EXTENT = 16_384`,
  float viewport coordinates quantised by round-half-away-from-zero, edge equations in checked `i64`.
  Those constants make the arithmetic checkable: clipped viewport coordinates lie in `0..=2^22`
  subpixel units, so coordinate differences are at most `2^22` in magnitude, each edge product is
  at most `2^44`, and subtracting two products is bounded by `2^45`, within `i64`. Validate that
  coordinate bound before edge evaluation and record the proof beside the constants; a coordinate
  equal to `2^22` does not fit a signed 22-bit representation. All of this is on the BIT-EXACT side of the
  split at the top of this file.
  DONE 2026-09-14. `src/user/libs/graphics/soft3d` is the crate; `fixed` holds the grid and `raster`

  THE PROOF IS WRITTEN OUT BESIDE THE CONSTANTS AND A FIXTURE IS THE ARITHMETIC IT IS ABOUT: two
  coordinates at the extremes of the legal range produce an edge value the fixture holds against
  `2^45`, and against `2^43` from below - because a bound the worst case never reaches is a bound
  about nothing. A coordinate EQUAL to `2^22` is admitted and one past it refused, which is the
  off-by-one a check written as "fits in twenty-two bits" gets wrong.
  A BACK-FACING TRIANGLE IS REWOUND RATHER THAN GIVEN ITS OWN PATH, so the edge tests, the fill rule

  two comparisons that must be exact mirror images is how a front face and a back face that share an
  edge get a seam. The original facing is carried for the fragment stage, and a fixture holds it
  against `render-math`'s `facing` on the NDC positions BEFORE the viewport inverts Y, which is the
  one place the convention could be backwards.
  THE TOP-LEFT RULE HAS THE FIXTURE IT EXISTS FOR: a quad split along its diagonal, every sample
  counted, and the assertion that no sample is filled twice and none is missed - which is what a
  floating-point edge test cannot guarantee and this fixed-point one can. A sub-pixel triangle is
  kept and answers by coverage; a degenerate one produces nothing on every architecture; a coordinate

  varyings use that parameter. A `noperspective` varying uses the projected parameter
  `u = t*w1 / ((1-t)*w0 + t*w1)` and value `(1-u)*a0 + u*a1`, so it remains linear after perspective

  existing `w == 0` refusal covers a non-projectable intersection rather than substituting `t`.
  These varying calculations remain on the tolerance-based side of the geometry/shading split.

  copy it unchanged to every resulting primitive. Never interpolate it or choose a new provoking
  value when clipping removes the original vertex or when the clipped polygon is fan-triangulated.

  clipping preserves the same field and original flat value through every plane; normal, UV and

      left    x + w >= 0        bottom  y + w >= 0        near    z     >= 0
