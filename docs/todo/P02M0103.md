# P02M0103 - Future-ready 3D graphics foundation + software-rendered scene

Status: FUTURE TRACK, PLANNED AFTER P02M0096a AND P02M0097; INDEPENDENT OF P02M0102 AND NOT A
PHASE-2 COMPLETION GATE.

**REWRITTEN 2026-08-15 to be a single statement of the work.** It carried its outside reviews inline
for two rounds, and the third review's sharpest finding was about the document rather than the
design: the main text still said "24- or 32-bit depth" and "textures remain optional future work"
while a review section two hundred lines below said "pick one depth format" and "textures are not
optional" - both as open checkboxes, with nothing to say which was newer. The reviews are gone;
their conclusions are the items below and their reasoning is stated where it changes a decision.
Everything in this file is what to build.

A fourth pass closed what that rewrite left open. Three contradictions survived it - the live QEMU
gate still demanded the "all six material colours" check the text above it had just refuted, the
renderer both allocated and borrowed its colour target, and `a2` both required TLS and permitted a
configuration without it - and a fourth class of defect ran through the whole file: items that
required a value to be CHOSEN without choosing it. "State the handedness", "a small cap", "pick a
depth format" are not normative. Where such an item appears below it now carries the number:
`MAX_DAMAGE_RECTS = 16`, 8 subpixel bits, depth `[0, 0xffff_ffff]` cleared to `0xffff_ffff` and
compared with `Less`, column-major `M * v` right-handed with `[0, 1]` clip depth and CCW front faces.
Two implementations reading this file must produce the same pixels.

Three things were DEFERRED rather than refined, all by the same rule this tree applies elsewhere - a
shape with fewer than two real consumers is a guess written down:

  - the graphics adapter/device/context/queue vocabulary, which had one consumer and it was the null
    backend written to exercise it. The first real virgl/Venus/native backend is what says what a
    device model needs;
  - the generic timeline/fence capability, for the same reason. What presentation needs is a
    completion mechanism for presentation, which is specified below; a system-wide timeline
    primitive is worth extracting when GPU, video decode or DMA also want one;
  - the resource accounting for device-local bytes, contexts, queues, command bytes and in-flight
    submissions, none of which exist once the above are deferred.

And the C/C++/TLS/Mesa substrate is split into its own part, because a `no_std` Rust renderer has no
business waiting for ELF TLS - which `docs/DYNAMIC_LINKING.md` refuses by name.

The architectural split is deliberate: OpenGL/OpenGL ES/Vulkan are userspace API
libraries; WSI, presentable images, synchronization, governed memory and access to a
capability-scoped graphics device are OS contracts; virgl/Venus/native-device protocols
belong to a backend/driver. The software renderer exercises the same window-system,
resource-lifetime, resize and frame-pacing contracts but remains an ordinary CPU client of
DisplayService. It is not a fake OpenGL implementation and no provisional `gl*`/`vk*` API
is introduced merely to draw one demo.

## P02M0103a1 - Graphics foundation

Everything the software renderer stands on, and nothing that waits for a GPU. `P02M0103b` depends on
this part and NOT on `a2`.

- [ ] Write `docs/GRAPHICS.md` first, and name the layers in it, because "framebuffer" currently
  means five things: the UEFI boot surface in `bootproto`, the virtio-gpu resource's DMA backing,
  the DisplayService scanout, an application's surface, and `pix::Target`. FRAMEBUFFER is the legacy
  linear boot surface only; SCANOUT is what the display controller is showing; IMAGE is any 2D
  region of pixels; SURFACE is a presentable application object; RENDER TARGET is an image a
  renderer draws into. Freeze the ownership diagram and the future integration routes - OpenGL/ES
  through EGL and a Mesa state tracker, Vulkan through a loader and ICD with Venus as the likely
  transport, DisplayService as the WSI and presentation owner, the display driver as device
  transport - and record which boundary validates every untrusted length, opcode and resource
  reference. Do not invent a common GL/Vulkan command language or expose virtqueue descriptors to
  applications.

- [ ] Define the canonical image model, and keep it separate from the future GPU one. The base type
  describes a plane of pixels and nothing else: extent, pitch, pixel format, transfer function,
  alpha mode and row origin, with every offset and size computed through checked arithmetic. It does
  NOT store a byte length - it computes one, `required_bytes() -> Result<usize, LayoutError>`,
  because a stored length beside a view that carries a real slice is two answers to one question and
  they drift. `ImageView` validates `data.len() >= layout.required_bytes()?`. A larger allocation
  with trailing padding may be described by a separate `allocation_len` beside the layout, never by
  overwriting the mathematically required size. A terminal raster and a decoded PNG need none of mip
  levels, array layers, sample counts, tiling, usage or memory domain - those belong to a
  `GpuImageDesc` that a later backend milestone adds ON TOP of this layout, sharing its format and
  extent. Building the ordinary image model out of the GPU one replaces four over-specific
  representations with one over-general one.

- [ ] Name what the bytes mean: `PixelFormat` (`B8G8R8X8_UNORM`, `R8G8B8A8_UNORM`), transfer function
  (`Linear`, `Srgb`) and `AlphaMode` (`Opaque`, `Straight`, `Premultiplied`). This is not speculative
  - `pix`'s `RgbaImage::to_bgrx` already multiplies each channel by alpha, which composites onto
  black and produces premultiplied bytes in a format whose alpha is ignored, and nothing in the type
  system says so. The v1 scanout may keep accepting only opaque `B8G8R8X8_UNORM`; the image model
  must not be narrowed to it.

  Say which combinations are VALID and which are merely unimplemented, because "not every
  combination needs an implementation" is a licence to leave the matrix undefined:
  `B8G8R8X8_UNORM` is `Opaque` only - it has no alpha channel, so `Straight` and `Premultiplied` are
  a type error and not an unsupported case; `R8G8B8A8_UNORM` takes any of the three. And fix the
  byte-level rules that two implementations otherwise answer differently: channel order is defined
  by the format NAME and never by host endianness; all v1 RGB formats use sRGB PRIMARIES and differ
  only in transfer function, so `Linear` means linear-light sRGB primaries rather than "linear with
  respect to something unstated"; float or linear values convert to `u8` by round-half-away-from-zero
  after clamping to `[0, 1]`; NaN converts to zero and infinities clamp rather than wrapping or
  panicking; and the `X` byte in `B8G8R8X8_UNORM` is IGNORED on read and written as `0xff`, so a
  producer cannot leak stale bytes into it and a consumer cannot start depending on one.

- [ ] Provide `ImageView<'a>` and `ImageViewMut<'a>` - a borrowed slice plus a layout - whose
  constructors refuse a pitch below the minimum row bytes, a length below `required_bytes()`, a
  zero extent or an unknown format. `surface::Mapping` hands out one of these (or runs a closure
  over one) and `Mapping::addr()` is DELETED rather than left beside it: today
  `imgview.rs` turns that `u64` into a target with
  `core::slice::from_raw_parts_mut(surface.addr() as *mut u8, target_len)`, an application computing
  a length and building an aliasing mutable slice from a raw pointer. One consumer now, which is why
  it is cheap now and expensive after soft3d, a compositor and a video path have each written their
  own.

- [ ] Converge the pixel-plane types that already exist rather than adding a fifth. `pix::Target`
  carries `data/width/height/pitch/bytes_per_pixel` plus six channel shift/size fields; `pix::Image`
  carries `data/width/height/pitch`; `term::Raster` and `term::Geometry` are a third; and
  `surface::Mapping` rebuilds a `Framebuffer` with the shifts hard-coded to 16/8/0. Each becomes the
  new layout and view, or is deleted. `bootproto::Framebuffer` stays a boot-protocol type with a
  one-way adapter into the image model - a boot hand-off and a general image are different layers.

  Fix the dependency graph now rather than leaving it as an alternative, because "`pix` either
  becomes this or sits on top of it" is the kind of open choice this document exists to close.
  `graphics-core` owns `Extent2D`, `Offset2D`, `Rect`, `PixelFormat`, transfer function, `AlphaMode`,
  `ImageLayout`, `ImageView`/`ImageViewMut`, checked pixel conversion, source-over compositing and
  nearest/bilinear sampling. `pix` DEPENDS on it and stays what it already is - an image utility
  library with owned `RgbaImage`, animation `Frame`/`Animation`/`Compositor`, crop, scale and blit -
  while its own `Image`, `Target` and `Rect` become aliases of the shared types or are deleted.
  `soft2d` depends on `graphics-core` and not on `pix`. `soft3d` depends on `graphics-core` and not
  on `pix` or `soft2d`. Nothing depends on `pix` in the other direction.

- [ ] Replace the current display contract with the present queue, with NO compatibility path for
  the single-surface API. Nothing is versioned before the first release and no external software
  depends on it, so carrying a second legacy path from the moment the right one exists buys nothing.
  A presentable surface has an immutable pixel format, an explicit extent, a resize generation and a
  NEGOTIATED image count - the service advertises minimum and maximum, the client requests, the
  service answers with the actual, and no number is written into the interface. `present_mode` is an
  ENUM with `Fifo` defined now - every present is displayed, in order, and the queue applies
  backpressure - so that `Mailbox` and `Immediate` have a place to be added rather than a meaning to
  be argued about. Specify the image
  state machine as states rather than prose: `Available -> acquire -> Acquired -> present ->
  PendingPresent -> released -> Available`, with `Stale` after a generation change and a rule that a
  stale image is never presented into a new generation. Define FIFO ordering, maximum frames in
  flight, backpressure, occluded/background behaviour, `OUT_OF_DATE` handling, what process death
  returns, and console restoration.

- [ ] Damage is a BOUNDED LIST of rectangles with an explicit whole-surface fallback, not one
  rectangle. Both sides of the driver protocol carry a single `(u32, u32, u32, u32)` today and the
  driver unions everything it receives (`union_rect` in `virtio_gpu.rs`), so a client updating two
  corners of a screen sends their bounding box - which is most of the screen. A cap costs nothing now
  and is the difference between a compositor that can be efficient and one that cannot.

  "A small cap" is not an ABI. Fix `MAX_DAMAGE_RECTS = 16` and state the semantics: an EMPTY list
  means nothing changed and the present is still ordered and still completes; an explicit `Full`
  variant means the whole extent, and is not spelled as one rectangle covering it; a rectangle
  outside the extent is a TYPED INVALID rather than a silent clamp, because silently clamping hides
  the caller's arithmetic bug; exceeding the cap is the caller's problem to solve by merging or
  sending `Full`, not the service's to solve by dropping rectangles; overlapping rectangles are legal
  and may be normalised; and coordinates are always in the image space of the generation the present
  belongs to. The backend MAY merge rectangles when merging is cheaper than transferring them
  separately, but the unconditional union of everything is exactly what this item removes - carrying
  a list to a driver that always collapses it to one bounding box buys nothing.

- [ ] Give presentation a completion mechanism of its own rather than a system-wide timeline, and
  name its TWO events separately, because "finished with the image" means two different things to
  the two ends and collapsing them is what makes a presentation path race. PRODUCER-READY: the
  contents are complete and the image may be read and presented. CONSUMER-RELEASE: the presentation
  pipeline is done with the image and the producer may overwrite it. For a CPU renderer
  producer-ready is immediate at the `present` call; for a future imported GPU image it is
  asynchronous, which is the whole reason it is a named event now rather than an assumption. The
  rule that falls out is exact: `acquire_next` returns only images that have been consumer-released,
  and never an image still in `PendingPresent`. Beside that the contract needs timeout, cancellation
  and peer-death completion, bounded waiter accounting, no silent wrap, no forged future signal and
  no duplicate completion. A presentation-specific one-shot completion or the existing `Event`
  mechanism is enough; if GPU submission, video decode or DMA later want the same primitive, THAT is
  when it is worth extracting into a general timeline.

- [ ] Replace the DisplayService <-> display-driver byte protocol with a typed LSIDL interface, and
  specify its lifecycle rather than only its calls. `display_service.rs` writes `b"PRESENT"` and four
  little-endian `u32`s into a 23-byte buffer; `virtio_gpu.rs` decodes it with `rd32_le(m, 7)` and a
  length check, with `FB`, `FBNEW`, `RESIZE`, `FLUSH`, `OK` and `ERR` beside it. Every other service
  boundary in this tree is LSIDL with typed capabilities. `liber:display-device@1` states: who owns
  the backing and for how long the capability is valid; how a backing binds to a generation; whether
  a resize changes the visible extent or delivers a new backing, and what happens to the old one;
  what present completion means; what driver death does to in-flight presents; how DisplayService
  finds a new backing after a driver restart; that the event stream is bounded; and that a backing
  from an old generation can never be presented into a new one. The virtio-gpu path already does the
  transactional backing replacement - the interface must capture it as a contract rather than lose
  it as a driver detail.

- [ ] Add `soft2d`: a small `no_std` CPU drawing library over `ImageViewMut`, with no DisplayService
  dependency. `pix` is an image and pixel utility library - `RgbaImage`, animation frames, blit,
  crop, scale - and it has real consumers, but its public drawing surface is three blits. Something
  has to draw the 2D test below, and without a library it draws them locally, which is the private
  rasteriser this milestone exists to prevent. First version: clear, fill rect, stroke rect, line,
  blit, scaled blit with nearest and bilinear, source-replace and source-over, a scissor rectangle,
  and a linear gradient. No allocation during a draw, checked bounds, clipping instead of refusing,
  and no panic for hostile coordinates. Explicitly NOT in the first version: Bezier paths,
  anti-aliased vector stroking, arbitrary affine transforms, filters, blur, fonts or text layout -
  that is a later GUI and vector stack.

  Four things this needs stated, or two implementations will disagree:

  - ONE implementation of pixel conversion, source-over compositing and nearest/bilinear sampling,
    living in `graphics-core` and shared by `pix`, `soft2d` and `soft3d`; none of the three carries a
    private second copy. This is already real: `pix::blend_over` is an integer straight-alpha
    source-over evaluated on sRGB-encoded bytes, and `soft3d` needs blending in linear light, so the
    shared primitive takes its WORKING SPACE as part of the contract and each caller states which it
    uses. Merging them without saying that would silently change what `pix` composites today.
    Bilinear must also fix its sampling centre, its clamp and repeat behaviour, and that it
    premultiplies BEFORE interpolating - interpolating straight alpha pulls the colour of fully
    transparent texels into the result and rings dark halos around transparent edges.
  - Line rasterisation is DEFINED, not left to the implementation, since anti-aliasing is deferred:
    one-pixel aliased lines, integer endpoints, deterministic Bresenham-style coverage after
    clipping, and an explicit rule on whether the final endpoint is included. Without it "line" draws
    differently on two architectures or in two call sites and no test can say which is right.
  - Damage returned from a draw is CONSERVATIVE, not exact. Exact damage would mean comparing old and
    new pixels - a source-over with alpha zero changes nothing while covering a rectangle - and that
    cost defeats the purpose. Every draw returns the smallest inexpensive conservative raster bound:
    it contains every pixel that may have changed, is clipped to the target and scissor, and is empty
    when no sample was reached.
  - A typed `DrawError` - `InvalidLayout`, `UnsupportedFormat`, `NonFinite`, `TooLarge`,
    `TargetMismatch` - because out-of-range coordinates are CLIPPED and are not errors, while an
    unusable target, an unsupported format or arithmetic that cannot be represented are.

  Host tests cover rectangle clipping against each edge, zero-size and overflowing coordinates, line
  endpoints in every octant, nearest and bilinear sampling, clamp and repeat, straight and
  premultiplied source-over, sRGB/linear conversion, the scissor, gradient endpoints, returned damage
  bounds, and guarded canaries around the target. Property and fuzz tests feed hostile coordinates,
  extents and pitches and prove no panic and no out-of-bounds write.

- [ ] Integrate what actually exists with ResourceManager and SystemGraph: surface and image bytes,
  surface count, present image count, queued presents, damage metadata and waiters, charged to the
  creating Domain before allocation. Publish bounded counters and reset/fault state without exposing
  image contents. Exhaustion returns typed errors and releases partial transactions; killing a
  Domain reclaims surfaces, images, mappings and waiters even if the driver is wedged. Device-local
  bytes, contexts, queues, command bytes and in-flight submissions are the GPU milestone's to add
  when they exist.

- [ ] Specify the OS-facing pixel conventions here and the RENDERER's conventions in `P02M0103b` -
  they are two layers and this file had them as one. This part owns: row origin, channel order,
  alpha mode, transfer function and the conversion into the scanout format. Clip-space depth range,
  front-face winding and viewport orientation belong to the renderer.

- [ ] Prove the whole foundation with a 2D animation before a single triangle exists, and make it
  the gate between this part and `P02M0103b`. The image viewer draws one frame, so it exercises none
  of what a present queue is for. Specify it as an APPLICATION and not as a sketch, to the same
  standard `P02M0103c` holds the 3D one to: one governed PIE named **2D Test SW**, canonical artifact
  `test2d-sw.lsexe`, only `display + input-keys` grants, Esc/q exits, Space pauses, R resets.

  It renders THROUGH `soft2d` - an application-local rasteriser or a duplicate drawing loop is not
  accepted - and shows an animated gradient background, two opaque moving rectangles, one
  semi-transparent moving rectangle, a scaled RGBA checkerboard image, and two non-contiguous
  changing regions. It acquires, draws, presents, acquires the next image, survives a resize and
  keeps going. That one demo exercises `soft2d`, `ImageViewMut`, the pixel formats, alpha, blit,
  scaling, clipping, multi-rectangle damage, acquire/present, double or triple buffering, resize and
  frame pacing - and it is a far better place to find out one of them is wrong than inside the first
  rasteriser.

  It passes this part only when: clean exit AND crash both restore the text console; a resize
  continues without ever presenting a stale image; nearest and bilinear scaling are both actually
  used; source-replace and source-over are both actually used; two separate damage rectangles travel
  the whole path from application to driver as two; a live QEMU capture proves both animation and
  blending; the package audit proves ET_DYN, provider identity and order, the exact grants and no
  statically duplicated drawing code; and there is no steady-state allocation once the queue and
  resources exist.

- [ ] Add hostile-input and lifecycle tests before anything is built on this: malformed format,
  extent and pitch descriptors, overflowed image sizes, invalid generations, duplicate acquire and
  present, completion races, driver death, truncated messages, forged imports, cross-Domain handles,
  budget exhaustion and cleanup during in-flight presentation. Fuzz every parser and every checked
  layout helper; prove that a malicious client cannot map another surface, retain foreground input
  or leave the console scanout blank.

## P02M0103a2 - Foreign graphics-stack prerequisites

Needed before importing Mesa, a Vulkan loader or any upstream C/C++ graphics stack. `P02M0103b` does
NOT depend on this part, and nothing in it gates the software renderer.

- [ ] Prepare the foreign-library and toolchain substrate, but import no stack. Pin cross C/C++
  compiler and archive/link steps for the three targets; provide EXACTLY the foreign ABI facilities
  the pinned upstream configuration requires - allocator, memory/string/math, monotonic time,
  atomics, threads, mutex/condition/event waits, mapped MemoryObjects and dynamic-provider lookup,
  plus thread-local storage only under the condition the next item sets. Maintain an exact
  required-symbol inventory derived
  from a chosen Mesa or Vulkan-loader configuration; do not grow a general POSIX layer or expose
  ambient files, processes or devices. Host build tooling must accept reproducible Meson/CMake object
  lists without bypassing P02M0096a identity, relocation, W^X, provider and license audits. Audit
  the ABI and not only the symbol list: exception and unwind tables, RTTI, static initialisers and
  their ordering, `atexit` registration and the `errno` model are what a C++ stack needs from a
  platform, and a required-symbol inventory does not mention any of them.

- [ ] Resolve the TLS blocker before promising the substrate, and resolve it as ONE of two variants
  rather than as both at once. `docs/DYNAMIC_LINKING.md:197` refuses TLS relocations by name. TLS is
  MANDATORY if and only if the selected binaries emit `PT_TLS`, TLS symbols or TLS relocations, and
  which of the two variants applies is a decision this part makes rather than discovers:

  - VARIANT A - support it: `docs/DYNAMIC_LINKING.md` changes with a stated design covering `PT_TLS`
    segments, the architecture-specific TLS relocations for all three targets, the per-thread block
    allocation and its accounting, and thread teardown.
  - VARIANT B - avoid it: the inventory is built against a configuration that emits ZERO TLS
    requirements, and the audit PROVES their complete absence rather than assuming it - no `PT_TLS`
    segment, no TLS relocation, no TLS symbol in any pinned object.

  Whichever is chosen, the required-symbol inventory and the substrate item above are built to match
  it; a substrate that promises TLS while the audit is meant to prove there is none is neither.

- [ ] Record the dependency and licensing policy before selecting upstream code. LiberSystem-owned
  implementation stays Unlicense; imported Mesa, Vulkan loader, compiler runtime or conformance
  sources keep their own compatible notices with exact source, version and patch provenance. The
  image identity records bind generated objects to that inventory, and the build rejects an
  unreviewed license, a downloaded-at-build source or a copied implementation with lost attribution.
  This part imports none of those projects; its synthetic build proves the audit path.

- [ ] Reserve loader/ICD discovery under P02M0097's system layout: a bounded, versioned provider
  manifest for API name and version, architecture, entry provider, backend identifier and required
  extensions. Paths are package-owned and identity-checked; no environment-variable search path, no
  current-directory plugin load, no arbitrary `dlopen`. Only a synthetic provider is discovered and
  selected or rejected in tests; no GL or Vulkan ABI is exported.

## P02M0103b - Bounded software 3D renderer

Depends on `P02M0103a1` and on nothing in `a2`. Every value below is normative: where an earlier
draft offered two options, one is chosen here.

- [ ] Three small `no_std` libraries rather than one renderer that owns everything: `render-math`
  for `Vec2/Vec3/Vec4`, matrices, quaternions, transforms and camera projection; `render-scene` for
  the scene model, independent of any renderer; and `soft3d` for clipping and rasterisation.
  Splitting the scene model out is what lets a later GPU renderer consume the same scene without
  emulating the CPU one - with the model inside `soft3d`, "a different renderer" means "a different
  scene model" too. Build them as P02M0096a `.lslib` providers once two consumers or a measured
  ownership boundary justify it; the demo PIE duplicates no shared code.

  `render-math` is a CONTRACT and not a type list, and this file picks the values rather than
  requiring that someone pick them - "state the handedness" is not normative, a handedness is:
  angles in RADIANS everywhere, COLUMN-MAJOR storage, `M * v` as the transform, RIGHT-HANDED world
  and view space, clip-space depth in `[0, 1]`, counter-clockwise front faces. Constructors are named
  for what they encode - `perspective_rh_zo`, `orthographic_rh_zo` - so a caller cannot pick the
  wrong convention silently. Quaternions state their normalisation policy: constructors normalise,
  operations preserve unit length, and a zero-length quaternion is an error rather than a NaN
  generator. Inversion of a singular matrix returns a typed error and never a matrix of infinities,
  and every entry point states what it does with NaN and infinite inputs.

  `render-scene` owns the mesh, material, light, instance and camera model - and, because textures
  and blending are required below, also `Texture2D`, `Sampler`, `RenderState` with its `BlendState`
  and `DepthState`, and the `DrawList`. A scene model that cannot express "this draw is transparent
  and does not write depth" forces that state back into the renderer, which is exactly what
  splitting the two apart was for.

- [ ] Implement the triangle pipeline, with these conventions fixed: sample points at pixel centres
  `(x + 0.5, y + 0.5)`; fixed-point edge equations rather than floating-point comparisons, so
  coverage is exact and shared edges cannot double-fill or leave a seam; the top-left fill rule;
  deterministic back-face culling by winding; clipping against all six homogeneous clip planes named
  explicitly, with fixed-size buffers and stated behaviour at `w == 0` and for NaN and infinite
  coordinates - a clipper is where hostile geometry goes first, and "clip against the frustum" is
  not implementable twice the same way; perspective-correct interpolation; and a `u32` depth buffer - one format, not
  "24- or 32-bit", because a CPU rasteriser gains nothing from packing and loses the checked
  arithmetic. Degenerate, non-finite and off-screen triangles are skipped deterministically. A
  SUB-PIXEL triangle is NOT skipped: it either covers a sample point or it does not, and dropping it
  by size is a rule that makes small geometry flicker as the camera moves.

  "Fixed-point" and "`u32` depth" are only half a contract without the numbers, and identical
  coverage on three architectures is exactly what the missing half decides: 8 SUBPIXEL BITS for
  viewport quantisation, edge equations evaluated in checked `i64` so no product can overflow within
  the stated maximum raster coordinates, and a maximum raster coordinate small enough that the
  product is provably representable. Depth maps `[0, 1]` onto `[0, 0xffff_ffff]` by
  round-half-away-from-zero, clears to `0xffff_ffff`, and compares with `Less`. These are values, not
  guidance; a second implementation reading this file must produce the same pixels.

  The clipper interpolates ALL varyings, not just position. Every vertex a clip plane creates is
  built with a single intersection parameter that is then applied identically to position, normal,
  UV, vertex colour and any other varying - clip position alone and the geometry is right while the
  texture and lighting jump at the near plane, which is a bug that looks like a texturing bug. State
  the behaviour when the intersection denominator is zero. The maximum vertex count after clipping a
  triangle against six planes is a PROVEN algorithmic constant with fan triangulation of the result,
  not a number the caller configures - so it lives in the clipper and NOT in `RendererLimits`.

- [ ] Implement materials and lighting: per-face and base colour, vertex normals transformed by the
  inverse transpose, an ambient term, normalised Lambert diffuse, Blinn-Phong specular with bounded
  shininess, one directional key light and one animated point light with attenuation, computed
  PER FRAGMENT. Lighting is in linear light and converts to the display transfer function on
  output. An `Unlit` material is required as well - it is what a debug view, a UI overlay and a
  texture test need, and adding it later means adding a second path through the fragment stage.

- [ ] Textures are REQUIRED, not optional future work. A renderer without them is a demo of one
  scene rather than a general renderer, and every later consumer wants them: UV coordinates on the
  vertex, perspective-correct UV interpolation, nearest and bilinear sampling, clamp and repeat
  addressing, and a bounded texture size checked at ingestion. Alpha blending is required with it:
  opaque and source-over, with `depth_write = false` for the transparent pass and the draw order
  stated - sorting is the caller's job and the renderer says so rather than pretending it is not
  there.

  Sampling and blending are where two implementations diverge invisibly, so name the semantics: the
  supported texture formats are `graphics-core`'s, with the accepted `AlphaMode` on ingestion stated
  and straight alpha converted once at ingestion rather than per sample; sRGB texels are DECODED to
  linear before filtering, because filtering encoded values blends the wrong quantity; texels are
  premultiplied before interpolation for the same reason `soft2d` requires it; source-over is
  evaluated in LINEAR LIGHT and converted to the display transfer function on output; texel centres
  are at `(i + 0.5) / extent`; and `repeat` addressing is defined for NEGATIVE and large UVs by
  Euclidean remainder, so `-0.25` and `0.75` sample the same texel rather than differing by the sign
  convention of the language's `%`. The transparent pass turns off depth WRITES only - the depth TEST
  stays on, or transparent geometry draws over the objects in front of it.

- [ ] Bound the renderer with a `RendererLimits` value rather than fixed configured constants:
  `max_lights`, `max_draws`, `max_input_triangles`, `max_generated_triangles`, `max_texture_extent`,
  `max_texture_bytes`, `max_scratch_bytes`. A caller states its limits, the renderer allocates
  against them once, and hostile geometry meets a number the caller chose instead of one compiled in.
  Caller-chosen does NOT mean unbounded: a requested limit is clamped by the implementation's hard
  maximum, by what the raster arithmetic can represent, and by the Domain's budget, in that order -
  otherwise `usize::MAX` formally satisfies a bounded design while defeating it. The clip buffer size
  is not on this list; it is the proven constant established above.

  Validate indices and finite transforms at ingestion, account peak memory to the process Domain and
  reuse frame allocations. Scene traversal and clipping allocate nothing per triangle. The renderer
  VALIDATES its borrowed colour target - format, extent and layout against the frame it is about to
  draw - and uses checked allocation only for what it owns: the depth buffer, scratch storage and any
  tile or bin buffers. It does not allocate the colour target, because it does not own it.

- [ ] Pass geometry as a transient `MeshView` borrowed for the duration of a draw rather than an
  owned buffer the renderer keeps, and return a typed `RendererError` rather than an option: a
  caller that gets `None` cannot tell "limits exceeded" from "not finite" from "out of memory", and
  those need different answers. The variants are `InvalidMesh`, `InvalidTransform`,
  `UnsupportedFormat`, `TargetMismatch`, `NonFinite`, `LimitExceeded` and `OutOfMemory`. The renderer
  BORROWS its colour target - an `ImageViewMut` from `P02M0103a1` - and owns only its depth buffer
  and scratch storage.

- [ ] Add frame scheduling over the present queue: render into the acquired image, wait for
  CONSUMER-RELEASE before reusing it, keep at most the negotiated frames in flight and pace against
  monotonic time instead of busy-spinning. Resize and `OUT_OF_DATE` are handled at the ownership
  boundary the previous items set: the application reacquires the surface images OUTSIDE the
  renderer, and the renderer transactionally recreates the depth buffer and scratch storage it owns.
  Allocation failure keeps or cleanly releases the old scene and returns control to the console. A
  hidden or background scene blocks or throttles and consumes no raw input.

- [ ] Host tests cover vector, matrix and quaternion identities, camera and frustum transforms,
  clipping against every plane, winding and culling, perspective interpolation, depth ordering,
  shared-edge fill, sub-pixel coverage, texture addressing and filtering, alpha blending,
  non-finite and degenerate input, lighting and colour transfer, and guarded canaries around the
  colour and depth targets. Property and fuzz tests feed hostile meshes, indices, transforms,
  extents, UVs and viewport rectangles under strict allocation limits.

## P02M0103c - 3D Test SW, the end-to-end scene

- [ ] Add one governed PIE application named **3D Test SW**, with canonical artifact
  `test3d-sw.lsexe` and only `display + input-keys` grants. It acquires a present queue and renders
  a continuously rotating indexed cube above a simple ground plane. The six cube faces have visibly
  distinct material colours, correct shared-edge depth and occlusion, smooth or deliberately hard
  face normals, ambient plus directional plus animated point lighting, and specular highlights. A
  perspective camera, a dark non-flat background and the ground reference make rotation and depth
  unmistakable; no face-order painter shortcut is accepted.

- [ ] The scene MUST exercise textures and blending, because `P02M0103b` makes both required and a
  required feature that the end-to-end test never runs is a feature nothing proves. One cube face
  carries a checkerboard texture, the ground carries a repeated one, and a small semi-transparent
  panel stands in front of the scene - which together put UV interpolation, sampling, both
  addressing modes, alpha blending and the depth test under transparency through the whole path from
  scene to scanout. The textures are generated procedurally, so the application still needs only
  `display + input-keys` and no storage grant.
- [ ] Make the scene interactive and recoverable: Esc/q exits, Space pauses, R resets,
  arrow keys orbit the camera and +/- changes distance or field of view. Key-down/up state
  comes through the P02M0091 focus capability; focus loss clears held state. Resize recreates
  targets and preserves camera/animation state. Clean exit, crash, allocation failure,
  emergency kill and DisplayService restart always release images and restore the text
  console.
- [ ] Provide deterministic demo and test controls without exposing them in normal UI: fixed
  simulation time per frame, a fixed camera and a fixed light seed. A host renderer test produces a
  small golden frame with tolerance-based comparison rather than requiring bit-identical
  cross-architecture floating point. The live application stays clock-driven and visibly animated.

- [ ] A golden frame is a REGRESSION test and not a correctness oracle - it proves the output has
  not changed, not that it was ever right. Add small independent checks beside it: per-stage
  differential tests, or a tiny reference rasteriser over 16x16 tiles. The cheapest one worth having
  first is two triangles forming a quad: across the shared edge there must be neither a gap nor a
  doubly-covered pixel, which is a property that can be checked without a reference image at all.

- [ ] Keep the 30 FPS demo floor and add a real benchmark beside it: a rotating cube over a ground
