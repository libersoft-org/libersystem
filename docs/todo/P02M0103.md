# P02M0103 - The graphics platform desktop and mobile applications are built on

Status: FUTURE TRACK, PLANNED AFTER P02M0096a AND P02M0097; INDEPENDENT OF P02M0102 AND NOT A
PHASE-2 COMPLETION GATE.

**REWRITTEN 2026-08-15 to be a single statement of the work.** It carried its outside reviews inline
for two rounds, and the third review's sharpest finding was about the document rather than the
design: the main text still said "24- or 32-bit depth" and "textures remain optional future work"
while a review section two hundred lines below said "pick one depth format" and "textures are not
optional" - both as open checkboxes, with nothing to say which was newer. The reviews are gone;
their conclusions are the items below and their reasoning is stated where it changes a decision.
Everything in this file is what to build.

A fourth pass closed what that rewrite left open. Three contradictions survived it - the live QEMU
gate still demanded the "all six material colours" check the text above it had just refuted, the
renderer both allocated and borrowed its colour target, and the foreign part both required TLS and
permitted a configuration without it - and a fourth class of defect ran through the whole file: items
that required a value to be CHOSEN without choosing it. "State the handedness", "a small cap", "pick
a depth format" are not normative. Where such an item appears below it now carries the number:
`MAX_DAMAGE_RECTS = 16`, 8 subpixel bits, depth `[0, 0xffff_ffff]` cleared to `0xffff_ffff` and
compared with `Less`, column-major `M * v` right-handed with `[0, 1]` clip depth and CCW front faces.

A fifth pass drew the line that claim needs. "Two implementations must produce the same pixels" is
true of the INTEGER half of the pipeline and is not achievable for the floating-point half - operand
order, FMA contraction, the libm in use and the optimiser all move the last bit, which is why the
golden frame below is tolerance-based. So the contract is split, and each item says which side it is
on. BIT-EXACT: geometry classification, clipping topology, viewport quantisation, coverage,
shared-edge ownership, and depth clear, storage and comparison. TOLERANCE-BASED: interpolated
floating attributes, texture filtering, lighting and the final RGB conversion. An item that wants
bit-exactness on the tolerance side has to say the operand order and forbid contraction, and none
below does.

**A sixth pass changed what this milestone is FOR, and it is the only one of the six that changed the
scope rather than the wording.** Every pass before it improved the inside of a document whose stated
purpose was "enough graphics to prove a present queue and then draw a software cube". Measured
against that purpose the file was nearly finished. Measured against the real one - LiberSystem must
be ready for a desktop environment, a mobile shell and ordinary 2D and 3D applications written by
people who are not us - it had two structural faults that no amount of internal consistency fixes:

  - **`soft2d` was both the public 2D API and the CPU implementation of it.** The 3D half already got
    this right: `render-scene` is the model, `soft3d` is one renderer of it, and the reason written
    down for that split - "with the model inside `soft3d`, a different renderer means a different
    scene model too" - is exactly as true one dimension down. With applications written directly
    against `soft2d`, the first GPU 2D backend either rewrites every application or grows a second
    public API beside the first. There is now a `render2d` layer, and `soft2d` is its CPU backend.
  - **The 2D feature set was scoped to what the test program needed.** Bezier paths, antialiasing,
    affine transforms, path clipping, layers, general compositing and text were all deferred as "a
    later GUI and vector stack". Those are not advanced features that a desktop wants eventually;
    they are what an icon, a rounded button, a scroll viewport, a group opacity and a line of text
    are MADE OF. A platform without them is a platform on which the first real application writes its
    own rasteriser - which is the single failure this milestone exists to prevent.

What survives that unchanged is the platform layer: the image and colour model, the present queue,
damage, completion, the typed driver boundary and the resource accounting. Those were designed for
the general case and they hold. What changed is everything above them.

The C/C++/TLS/Mesa substrate has MOVED OUT to `P02M0135`. It never gated anything here, a `no_std`
Rust renderer has no business waiting for ELF TLS, and porting an upstream C++ stack is not a step in
building a 2D/3D library - it was diluting a milestone that is now large enough on its own.

Three things stay DEFERRED rather than refined, all by the same rule this tree applies elsewhere - a
shape with fewer than two real consumers is a guess written down:

  - the graphics adapter/device/context/queue vocabulary, which had one consumer and it was the null
    backend written to exercise it. The first real virgl/Venus/native backend is what says what a
    device model needs;
  - the generic timeline/fence capability, for the same reason. What presentation needs is a
    completion mechanism for presentation, which is specified below; a system-wide timeline
    primitive is worth extracting when GPU, video decode or DMA also want one;
  - the resource accounting for device-local bytes, contexts, queues, command bytes and in-flight
    submissions, none of which exist once the above are deferred.

The architectural split is deliberate: OpenGL/OpenGL ES/Vulkan are userspace API libraries; WSI,
presentable images, synchronisation, governed memory and access to a capability-scoped graphics
device are OS contracts; virgl/Venus/native-device protocols belong to a backend/driver. The software
renderers exercise the same window-system, resource-lifetime, resize and frame-pacing contracts but
remain ordinary CPU clients of DisplayService. They are not a fake OpenGL implementation and no
provisional `gl*`/`vk*` API is introduced merely to draw a demo.

The layering, once, so no item below has to restate it:

## P02M0103a - Common graphics platform

Everything both dimensions stand on, and nothing that waits for a GPU. Every later part depends on
this one; it depends on nothing in the others.

- [ ] Write `docs/GRAPHICS.md` first, and name the layers in it, because "framebuffer" currently
  means five things: the UEFI boot surface in `bootproto`, the virtio-gpu resource's DMA backing,
  the DisplayService scanout, an application's surface, and `pix::Target`. FRAMEBUFFER is the legacy
  linear boot surface only; SCANOUT is what the display controller is showing; IMAGE is any 2D
  region of pixels; SURFACE is a presentable application object; RENDER TARGET is an image a
  renderer draws into. Freeze the ownership diagram above and the future integration routes -
  OpenGL/ES through EGL and a Mesa state tracker, Vulkan through a loader and ICD with Venus as the
  likely transport, DisplayService as the WSI and presentation owner, the display driver as device
  transport - and record which boundary validates every untrusted length, opcode and resource
  reference. Do not invent a common GL/Vulkan command language or expose virtqueue descriptors to
  applications.

- [ ] Define the canonical image model, and keep it separate from the future GPU one. The base type
  describes a plane of pixels and nothing else: extent, pitch, pixel format, transfer function,
  alpha mode and row origin, with every offset and size computed through checked arithmetic. It does
  NOT store a byte length - it computes one, `required_bytes() -> Result<usize, LayoutError>`,
  because a stored length beside a view that carries a real slice is two answers to one question and
  they drift. The formula is exact rather than "the size the extent needs", because the last row does
  not include its padding and an implementation that charges a full pitch for it refuses a legal
  framebuffer: `(height - 1) * pitch + minimum_row_bytes`, all in checked arithmetic.
  `ImageView` validates `data.len() >= layout.required_bytes()?`. A larger allocation
  with trailing padding may be described by a separate `allocation_len` beside the layout, never by
  overwriting the mathematically required size.

  A terminal raster and a decoded PNG need none of mip levels, array layers, sample counts, tiling,
  usage or memory domain - those belong to a `GpuImageDesc` that a later backend milestone adds ON
  TOP of this layout, sharing its format and extent. Building the ordinary image model out of the GPU
  one replaces four over-specific representations with one over-general one.

- [ ] Use TWO coordinate spaces and say which is which, because a platform that only has integer
  pixel coordinates cannot do HiDPI, fractional scaling, zoom, rotation or smooth animation - and
  those are not desktop luxuries, they are what a phone does on every orientation change. The PUBLIC
  drawing coordinate is `f32` and SIGNED: geometry has to be positionable between pixels and has to
  clip off the left and top edges as naturally as off the right and bottom, and an unsigned integer
  parameter makes "half a pixel to the left of the origin" unrepresentable. Integer coordinates stay
  INSIDE the rasterising backend, where quantisation is defined. `Rect` is HALF-OPEN,
  `[x, x + width) x [y, y + height)`, so adjacent rectangles tile without overlapping and an empty
  rectangle is width or height zero. Presentable surfaces have a fixed `TopLeft` row origin in v1,
  with `RowOrigin` on the layout for images that are not presentable.

- [ ] Name what the bytes mean: `PixelFormat` (`B8G8R8X8_UNORM`, `R8G8B8A8_UNORM`), transfer function
  (`Linear`, `Srgb`) and `AlphaMode` (`Opaque`, `Straight`, `Premultiplied`). This is not speculative
  - `pix`'s `RgbaImage::to_bgrx` already multiplies each channel by alpha, which composites onto
  black and produces premultiplied bytes in a format whose alpha is ignored, and nothing in the type
  system says so. The v1 scanout may keep accepting only opaque `B8G8R8X8_UNORM`; the image model
  must not be narrowed to it.

  TWO formats is too few, and this is the one place the model was narrower than the tree it is
  meant to unify. `src/uefi/src/gop.rs` accepts `PIXEL_RGB` - which is R, G, B, unused in memory,
  so `R8G8B8X8_UNORM` and not either of the two above - as well as `PIXEL_BGR` and `PIXEL_BIT_MASK`
  with validated contiguous disjoint channel masks whose ELEMENT SIZE comes from the masks, so 16-
  and 24-bit modes are live. `bootproto::Framebuffer` carries that description as `bpp` plus six
  shift/size fields, and `term::Geometry`/`term::Raster` carry it again with
  `bytes_per_pixel: usize`. Requiring `term::Raster` to become the canonical layout while the
  canonical layout cannot express what `Raster` expresses is not a convergence, and narrowing it to
  32 bpp would reintroduce a defect this tree already fixed: the comment at `gop.rs:72` records that
  a literal `32` there gave a firmware-reported 24- or 16-bit layout "a diagonal smear rather than a
  picture". So the model has two arms:

      enum PixelStorage {
          Known(PixelFormat),                 // B8G8R8X8_UNORM, R8G8B8X8_UNORM, R8G8B8A8_UNORM
          PackedRgbUnorm(PackedRgbLayout),    // bytes_per_pixel + per-channel shift/bits + reserved
      }

  `PackedRgbUnorm` exists for BOOT AND SCANOUT ADAPTERS - the GOP hand-off and the terminal - and is
  not a texture format, not a presentable application surface format and not something a renderer
  samples. Application surfaces in v1 accept the `Known` arm only. That keeps one image model
  without pretending the firmware only ever hands over one layout.

  Say which combinations are VALID and which are merely unimplemented, because "not every
  combination needs an implementation" is a licence to leave the matrix undefined:
  `B8G8R8X8_UNORM` and `R8G8B8X8_UNORM` are `Opaque` only - they have no alpha channel, so
  `Straight` and `Premultiplied` are a type error and not an unsupported case; `R8G8B8A8_UNORM`
  takes any of the three, and under `Opaque` its alpha byte READS as 1.0 and is WRITTEN as `0xff`
  rather than being carried through unexamined. Under `Premultiplied`, a pixel whose channel exceeds
  its alpha is NON-CANONICAL: it is accepted, it is not an error, and every operation may treat it
  as clamped to alpha - stating that is cheaper than a validation pass over every uploaded image.
  And fix the byte-level rules that two implementations otherwise answer differently: channel order
  is defined by the format NAME and never by host endianness; all v1 RGB formats use sRGB PRIMARIES
  and differ only in transfer function, so `Linear` means linear-light sRGB primaries rather than
  "linear with respect to something unstated"; float or linear values convert to `u8` by
  round-half-away-from-zero after clamping to `[0, 1]`; NaN converts to zero and infinities clamp
  rather than wrapping or panicking; and the `X` byte in any `X8` format, and the reserved channel of
  a packed layout, is IGNORED on read and written as `0xff`, so a producer cannot leak stale bytes
  into it and a consumer cannot start depending on one.

- [ ] Provide `ImageView<'a>` and `ImageViewMut<'a>` - a borrowed slice plus a layout - whose
  constructors refuse a pitch below the minimum row bytes, a length below `required_bytes()`, a
  zero extent or an unknown format. `surface::Mapping` hands out one of these (or runs a closure
  over one) and `Mapping::addr()` is DELETED rather than left beside it: today
  `imgview.rs` turns that `u64` into a target with
  `core::slice::from_raw_parts_mut(surface.addr() as *mut u8, target_len)`, an application computing
  a length and building an aliasing mutable slice from a raw pointer. One consumer now, which is why
  it is cheap now and expensive after `soft2d`, `soft3d`, a compositor and a video path have each
  written their own.

- [ ] Provide OWNED images and offscreen render targets, not only borrowed views. An application has
  to be able to create an image and draw into it without a Surface and without DisplayService, or
  every one of these needs a special case: component caches, thumbnails, chart and map tiles, an
  image editor, shadow generation, a 3D frame that a 2D pass composites, a 2D texture that a 3D pass
  samples, screenshots and every host test of every drawing routine. `OwnedImage` carries a layout
  and its bytes, is charged to the creating Domain, and hands out `ImageView`/`ImageViewMut`. This is
  the single type that makes 2D and 3D interoperate rather than each rendering only to a scanout.

- [ ] Converge the pixel-plane types that already exist rather than adding a fifth. `pix::Target`
  carries `data/width/height/pitch/bytes_per_pixel` plus six channel shift/size fields; `pix::Image`
  carries `data/width/height/pitch`; `term::Raster` and `term::Geometry` are a third; and
  `surface::Mapping` rebuilds a `Framebuffer` with the shifts hard-coded to 16/8/0. Each becomes the
  new layout and view, or is deleted. `bootproto::Framebuffer` stays a boot-protocol type with a
  one-way adapter into the image model - a boot hand-off and a general image are different layers.

  Fix the dependency graph now rather than leaving it as an alternative, because "`pix` either
  becomes this or sits on top of it" is the kind of open choice this document exists to close.
  `graphics-core` owns `Extent2D`, `Point2D`/`Vector2D`, `Rect`, `RoundedRect`, `Transform2D`,
  `Color`, `PixelFormat`, transfer function, `AlphaMode`, `ImageLayout`, `ImageView`/`ImageViewMut`,
  `OwnedImage`, `Sampler`, `DamageRegion`, checked pixel conversion, compositing and sampling. `pix`
  DEPENDS on it and stays what it already is - an image utility library with owned `RgbaImage`,
  animation `Frame`/`Animation`/`Compositor`, crop, scale and blit - while its own `Image`, `Target`
  and `Rect` become aliases of the shared types or are deleted. `render2d` depends on
  `graphics-core`; `soft2d` depends on `render2d` and `graphics-core`; `render-scene` and `soft3d`
  depend on `graphics-core`. Nothing depends on `pix` in the other direction, and nothing but a
  backend depends on `soft2d`.

  That graph settles the RUST side and leaves the WIRE side to grow a duplicate. These same values
  cross three interfaces - the application display interface, the new display-device interface below,
  and their generated protocol crates - and `liber:display@1` already declares its own
  `enum pixel-format { b8g8r8x8 }`. Hand-defining the vocabulary once in `graphics-core` and again in
  each IDL rebuilds exactly the divergence this part exists to remove. So there is a value-only IDL
  package, `liber:graphics@1`, owning the wire-safe types - `extent-2d`, `offset-2d`, `rect`,
  `pixel-format`, `transfer-function`, `alpha-mode`, `row-origin`, `damage-region`, `image-layout` -
  which every graphics interface imports instead of redeclaring. `graphics-proto` is the generated
  wire identity; `graphics-core` re-exports those types and adds what cannot cross a wire: checked
  constructors, `required_bytes()`, `ImageView`/`ImageViewMut` over real slices, and the conversion,
  sampling and compositing routines. `liber:display@1`'s own `pixel-format` is deleted in the same
  change that introduces the package, not left beside it.

- [ ] Break the ONE-SURFACE-PER-CONNECTION assumption, which is the WSI half of the scope error at
  the top of this file. `liber:display@1` says it in its own words - "One display connection owns at
  most one surface" - with `acquire`/`present`/`release`/`input-focus` all at connection level and a
  synchronous `present`. Every desktop and mobile application is more than one surface: a main
  window, a dialog, a popup, a menu, a tooltip, a video surface, offscreen content. Replacing the
  synchronous present with a queue and leaving the object model at one surface would rebuild the same
  wall one layer up. The model is:

      DisplayConnection
          create_surface(...) -> Surface capability
      Surface
          its own present queue, its own event stream,
          its own extent, scale, transform and colour metadata

  A compositor is still a later milestone; what this item forbids is an object model that a
  compositor would have to break. Foreground input focus stays a property of a surface rather than of
  a connection, so P02M0091's focus capability binds to the surface that actually has it.

- [ ] Separate LOGICAL size, PHYSICAL extent and SCALE FACTOR, and put all three in the surface
  contract. `liber:display@1` today has one extent and calls it "preferred logical size", which is
  the physical one wearing the other's name - there is no scale anywhere in the interface. A phone
  surface is 400 x 800 logical at scale 3.0 and 1200 x 2400 physical, and an application that cannot
  see those as three numbers either renders at the wrong size or renders blurred. Applications lay
  out in logical units, `render2d` transforms by the scale, and the backend rasterises physical
  pixels. Surface events carry a CHANGE of any of: extent, scale factor, orientation/transform,
  output, colour space, visibility, focus, and a close request - each as its own event rather than
  one "something changed" that every client re-queries.

- [ ] Replace the current display contract with the present queue, with NO compatibility path for
  the single-surface API. Nothing is versioned before the first release and no external software
  depends on it, so carrying a second legacy path from the moment the right one exists buys nothing.
  A presentable surface has an immutable pixel format, an explicit extent, a resize generation and a
  NEGOTIATED image count - the service advertises minimum and maximum, the client requests, the
  service answers with the actual, and no number is written into the interface. `present_mode` is an
  ENUM with `Fifo` defined now - every present is displayed, in order, and the queue applies
  backpressure - so that `Mailbox` and `Immediate` have a place to be added rather than a meaning to
  be argued about. Advertise `min_images = 2` and `max_images = 3` in v1 - negotiated stays
  negotiated, but a service free to answer "one" turns the double-or-triple-buffering gate below
  into a test of nothing. Specify the image
  state machine as states rather than prose: `Available -> acquire -> Acquired -> present ->
  PendingPresent -> released -> Available`, with `Stale` after a generation change and a rule that a
  stale image is never presented into a new generation. Define FIFO ordering, maximum frames in
  flight, backpressure, `OUT_OF_DATE` handling, what process death returns, and console restoration.

  Three things that state machine is missing. An `Acquired -> abandon -> Available` edge, because a
  client that acquires an image and then decides not to draw must have a way back that is not a
  present. The resize transitions in full: `Available` in an old generation becomes `Stale`;
  `Acquired` in an old generation becomes `Stale` and the client discards it rather than presenting
  it; `PendingPresent` in an old generation completes or is discarded and then becomes `Stale`. And
  the Rust shape that makes the machine unrepresentable-when-wrong rather than merely documented:
  `acquire_next` returns an owned `AcquiredImage`, drawing borrows it, and `present` CONSUMES it, so
  after presenting there is no safe path to the pixels until the queue hands them back.

  `Fifo` as written promises something the occlusion rule takes away - "every present is displayed"
  cannot hold for a background client that must also not be blocked forever. Split the promise: FIFO
  is the ordering of ACCEPTED presents, by present-call order and not acquire order; while visible,
  every accepted frame reaches logical presentation; while occluded or in the background, new
  acquires block or answer `NotVisible`, and frames already accepted still complete IN ORDER but may
  complete as discarded. That needs a per-present outcome rather than a bare completion -
  `Displayed`, `DiscardedOccluded`, `ReplacedByResize`, `DriverLost` - which is also what a client
  needs to tell "my frame was shown" from "my frame was dropped and I should stop rendering".

- [ ] Give the frame loop a TIMING contract rather than leaving every application to sleep on the
  monotonic clock. Smooth animation on a desktop or a phone needs to know when the next frame is due,
  not to guess: a preferred frame deadline, the output's refresh interval, the presentation timestamp
  of a completed present, and the `PresentOutcome` above. A compositor will later supply frame
  callbacks synchronised to scanout, and the contract has to have a place for them now - retrofitting
  a callback into a design whose only pacing primitive is `sleep` means every application that
  animates is rewritten. What this milestone implements can be the simple version; what it must not
  do is make the simple version the interface.

- [ ] Damage is a BOUNDED LIST of rectangles with an explicit whole-surface fallback, not one
  rectangle. Both sides of the driver protocol carry a single `(u32, u32, u32, u32)` today and the
  driver unions everything it receives (`union_rect` in `virtio_gpu.rs`), so a client updating two
  corners of a screen sends their bounding box - which is most of the screen. A cap costs nothing now
  and is the difference between a compositor that can be efficient and one that cannot.

  "A small cap" is not an ABI. Fix `MAX_DAMAGE_RECTS = 16` and state the semantics: an EMPTY list
  means nothing changed and the present is still ordered and still completes; an explicit `Full`
  variant means the whole extent, and is not spelled as one rectangle covering it; a rectangle
  outside the extent is a TYPED INVALID rather than a silent clamp, because silently clamping hides
  the caller's arithmetic bug; exceeding the cap is the caller's problem to solve by merging or
  sending `Full`, not the service's to solve by dropping rectangles; overlapping rectangles are legal
  and may be normalised; and coordinates are always in the image space of the generation the present
  belongs to. The backend MAY merge rectangles when merging is cheaper than transferring them
  separately, but the unconditional union of everything is exactly what this item removes - carrying
  a list to a driver that always collapses it to one bounding box buys nothing.

  And answer the question all of that skips: damage relative to WHAT, when consecutive frames are
  drawn into different images? With images A, B, A, a client that draws two rectangles into B has
  said nothing about the rest of B - it may hold A's content, B's content from two frames ago, or
  whatever the allocator left there. Partial redraw and multiple images are incompatible until this
  is written down, and the v1 rule is the simple one: **every presented image contains a COMPLETE
  valid frame.** Damage is a HINT describing which pixels changed against the previously presented
  frame; it is not permission to leave the rest of the image undefined. From that: the first present
  of a generation is `Full`; an empty damage list asserts the submitted frame is pixel-identical to
  the previous one, which lets DisplayService release the image without copying; and a client that
  wants to redraw only part of an image has to know what that image already holds, which is a
  `buffer_age` extension a later milestone can add without changing this rule.

  Give the bounded merging one implementation too - `DamageRegion::{None, Rects { rects: [Rect; 16],
  len: u8 }, Full}` in `graphics-core` with a `push_or_full()` helper that degrades to `Full` on the
  seventeenth rectangle. Otherwise every 2D application writes its own bounded merge, and the cap
  above becomes sixteen different behaviours at the cap.

- [ ] Give presentation a completion mechanism of its own rather than a system-wide timeline, and
  name its TWO events separately, because "finished with the image" means two different things to
  the two ends and collapsing them is what makes a presentation path race. PRODUCER-READY: the
  contents are complete and the image may be read and presented. CONSUMER-RELEASE: the presentation
  pipeline is done with the image and the producer may overwrite it. For a CPU renderer
  producer-ready is immediate at the `present` call; for a future imported GPU image it is
  asynchronous, which is the whole reason it is a named event now rather than an assumption. The
  rule that falls out is exact: `acquire_next` returns only images that have been consumer-released,
  and never an image still in `PendingPresent`. Beside that the contract needs timeout, cancellation
  and peer-death completion, bounded waiter accounting, no forged future signal and no duplicate
  completion.

  Pick the mechanism rather than offering two, since "a one-shot completion or the existing `Event`"
  is the same open choice this document keeps closing elsewhere: it is a ONE-SHOT `Event`, and the
  rights are what make the guarantees structural instead of aspirational. Producer-ready is an
  OPTIONAL event the producer hands to `present`; DisplayService receives WAIT only and the producing
  side holds SIGNAL only, so "no forged future signal" is a capability the forger does not have
  rather than a rule someone must remember. A CPU renderer passes `None`, which means ready at the
  moment of the call. Consumer-release is the image returning to the queue, with an optional waitable
  release event for a client that wants to block on it. The event cannot be reset or signalled twice,
  and peer death drives it to a terminal failed state that WAKES its waiters rather than leaving
  them. Drop "no silent wrap" from the requirements: a one-shot has no counter to wrap, and a
  requirement that cannot be violated is one nobody will check. If GPU submission, video decode or
  DMA later want the same primitive, THAT is when it is worth extracting into a general timeline.

- [ ] Replace the DisplayService <-> display-driver byte protocol with a typed LSIDL interface, and
  specify its lifecycle rather than only its calls. `display_service.rs` writes `b"PRESENT"` and four
  little-endian `u32`s into a 23-byte buffer; `virtio_gpu.rs` decodes it with `rd32_le(m, 7)` and a
  length check, with `FB`, `FBNEW`, `RESIZE`, `FLUSH`, `OK` and `ERR` beside it. Every other service
  boundary in this tree is LSIDL with typed capabilities. `liber:display-device@1` states: who owns
  the backing and for how long the capability is valid; how a backing binds to a generation; whether
  a resize changes the visible extent or delivers a new backing, and what happens to the old one;
  what present completion means; what driver death does to in-flight presents; how DisplayService
  finds a new backing after a driver restart; that the event stream is bounded; and that a backing
  from an old generation can never be presented into a new one. The virtio-gpu path already does the
  transactional backing replacement - the interface must capture it as a contract rather than lose
  it as a driver detail.

- [ ] Integrate what actually exists with ResourceManager and SystemGraph: surface and image bytes,
  surface count, present image count, queued presents, damage metadata and waiters, charged to the
  creating Domain before allocation - but charged ONCE. The kernel already accounts MemoryObject and
  IPC bytes against the Domain, and ResourceManager is policy above those counters, so "charge image
  bytes" must not be read as a second independent byte budget the same MemoryObject also pays into:
  the kernel's existing accounting charges the storage, and the graphics counters CLASSIFY that usage
  and enforce optional graphics-specific limits on top of it. Where a graphics sub-budget is
  deliberately additional, it says so. Publish bounded counters and reset/fault state without exposing
  image contents. Exhaustion returns typed errors and releases partial transactions; killing a
  Domain reclaims surfaces, images, mappings and waiters even if the driver is wedged. Device-local
  bytes, contexts, queues, command bytes and in-flight submissions are the GPU milestone's to add
  when they exist.

- [ ] Specify the OS-facing pixel conventions here and the RENDERER's conventions in their own parts -
  they are separate layers and this file once had them as one. This part owns: row origin, channel
  order, alpha mode, transfer function, logical/physical/scale, and the conversion into the scanout
  format. Clip-space depth range, front-face winding and viewport orientation belong to `P02M0103e`.

- [ ] Add hostile-input and lifecycle tests before anything is built on this: malformed format,
  extent and pitch descriptors, overflowed image sizes, invalid generations, duplicate acquire and
  present, completion races, driver death, truncated messages, forged imports, cross-Domain handles,
  budget exhaustion and cleanup during in-flight presentation. Fuzz every parser and every checked
  layout helper; prove that a malicious client cannot map another surface, retain foreground input
  or leave the console scanout blank.

## P02M0103b - render2d, the public 2D API

The backend-neutral 2D library applications are written against. This part defines the MODEL and the
command stream; `P02M0103c` implements it on the CPU. It depends on `P02M0103a` and on no backend.

- [ ] Introduce `render2d` as a separate library from any rasteriser, and make that the boundary a
  future GPU backend replaces. An application, a UI toolkit and a game talk to `render2d`; they never
  name `soft2d`. This mirrors `render-scene`/`soft3d` exactly, and for the same stated reason.

- [ ] Give it a `Canvas` with saved state and a recorded `DrawList`. The immediate-mode surface is
  `save`, `restore`, `set_transform`, `concat_transform`, `set_clip`, `set_opacity`, `set_blend_mode`,
  `begin_layer`, `end_layer` plus the drawing calls - but what it PRODUCES is a bounded, validated
  display list rather than pixels. That indirection is what makes the same drawing replayable by a
  CPU backend now and a GPU backend later, cacheable per component, analysable for damage,
  transportable to a compositor, and testable without any backend at all. A canvas that writes
  straight into a slice is a CPU-only API however carefully it is written.

- [ ] Paths are REQUIRED and are not a later vector-graphics feature. `MoveTo`, `LineTo`,
  `QuadraticTo`, `CubicTo`, `Close`, with `FillRule::NonZero` and `FillRule::EvenOdd`. Every icon,
  every font outline, every rounded control, every chart, every SVG asset and every animated shape is
  a path; deferring Bezier curves defers all of them, and the first application to want one writes
  its own rasteriser - which is the failure this milestone exists to prevent.

- [ ] Antialiasing is REQUIRED, with a stated contract rather than a stated algorithm: coverage in
  `[0, 255]`, composited premultiplied, deterministic clipping, bounded scratch memory, and coverage
  applied to path fills, strokes, ellipses, rounded rectangles, transformed edges and glyphs. The
  backend picks scanline coverage or another method; what the public layer fixes is that a shape's
  edge has a coverage value and that two backends agree on the geometry that produces it. Aliased
  one-pixel drawing stays available as an explicit fast path, not as the only thing there is.

- [ ] Strokes are a full model, not a one-pixel line: stroke width, `Butt`/`Round`/`Square` caps,
  `Miter`/`Bevel`/`Round` joins, a miter limit, dash pattern and dash offset. The integer Bresenham
  line stays as an internal fast path for the axis-aligned one-pixel case; it is not the public
  drawing model.

- [ ] Provide the shapes applications actually draw, implemented over the path engine rather than
  each with its own rasteriser: filled and stroked rectangle, rounded rectangle, circle, ellipse,
  line, polyline, polygon, arc and arbitrary path.

- [ ] `Transform2D` is a general affine transform - translate, scale, rotate, skew, concatenate,
  invert - stored as a 3x3 homogeneous matrix. Without it there is no rotated element, no zoom, no
  animated transform, no orientation transition, no transformed image and no scene composition, and
  HiDPI itself is a scale transform. Deferring "arbitrary affine transforms" defers the scale factor
  the platform layer above just introduced.

- [ ] `Paint` covers what a UI is actually painted with: solid colour, linear gradient, radial
  gradient and image pattern, with conic gradient in the type space even if the first backend
  refuses it. A gradient takes MULTIPLE colour stops, a spread mode of `Clamp`/`Repeat`/`Mirror`, its
  own transform, and interpolates in linear light. One two-colour linear gradient is a demo feature,
  not a UI painting model.

- [ ] Clipping is rectangle, rounded rectangle AND path, and clips NEST. A scroll viewport, a rounded
  avatar, a card with clipped content and a nested component are the ordinary cases, and a single
  scissor rectangle serves none of them. An alpha mask is part of this item; an inverse clip is
  either specified or explicitly named as deferred, not left unmentioned.

- [ ] Layers and group opacity: `begin_layer(bounds, opacity, blend_mode)` / `end_layer`. This is
  basic UI semantics rather than an effect - two overlapping children inside a parent at 50 % opacity
  must be composited together and then blended once, not blended individually against the background,
  and there is no way to get that right without an offscreen group. A design without layers cannot
  add them later without changing every drawing call that has an opacity.

- [ ] Compositing is the Porter-Duff set - `Clear`, `Source`, `Destination`, `SourceOver`,
  `DestinationOver`, `SourceIn`, `DestinationIn`, `SourceOut`, `DestinationOut`, `SourceAtop`,
  `DestinationAtop`, `Xor`, `Plus` - plus the separable blend modes a modern UI uses: `Multiply`,
  `Screen`, `Overlay`, `Darken`, `Lighten`. The exotic non-separable Photoshop modes are deferred by
  name and the enum has room for them.

- [ ] Image drawing is a full operation: source rectangle, destination rectangle, arbitrary affine
  transform, `Nearest` and `Bilinear` filtering, `Clamp`/`Repeat`/`Mirror` addressing, opacity, and
  colour-space conversion. Bicubic and anisotropic sampling are deferred by name.

- [ ] Basic effects belong in the command model from the start even if the first implementation is
  slow: Gaussian blur, drop shadow and a colour matrix, applied to a layer. The point is not the
  filters themselves - it is that a filter chain over a layer changes the shape of a display list,
  and retrofitting one into a command model that never had it is a rewrite of the model.

- [ ] Text enters through `draw_glyph_run(glyph_run, paint, transform)`, where a `GlyphRun` is
  already-shaped, already-positioned glyphs. That is the correct seam: `render2d` renders glyph
  outlines and glyph masks and knows nothing of scripts, and the shaping stack above it is
  `P02M0136` - **Text foundation** - covering OpenType parsing, font fallback, Unicode segmentation,
  script shaping, bidirectional text, line breaking and layout. But the seam alone does not prove a
  platform can put text on a screen, so this milestone also carries the MINIMUM end-to-end path: load
  one scalable font, rasterise its outlines THROUGH the path engine, render a positioned glyph run
  with grayscale antialiasing, and cache rasterised glyphs. Full shaping is a named next milestone
  and not an indefinite deferral - a graphics platform that cannot draw a word is not one applications
  can be written on.

- [ ] The public error type is typed and distinguishes what the caller can act on: an out-of-range
  coordinate is CLIPPED and is not an error, while an unusable target, an unsupported paint or
  format, a non-finite transform, an unrepresentable size and an exhausted budget are each their own
  variant. Recording into a `DrawList` validates eagerly, so an application learns at the call that
  produced the mistake rather than at replay.

- [ ] Host tests for this part run WITHOUT a backend: recording, validation, transform algebra, path
  construction and flattening tolerance, clip stack nesting, layer nesting, state save/restore
  balance, display-list bounds and damage computation, and the typed refusals. Property and fuzz
  tests feed hostile transforms, unbounded paths, degenerate curves and deep nesting under strict
  allocation limits.

## P02M0103c - soft2d, the CPU backend

The software implementation of `P02M0103b`, and the only part of the 2D stack that knows what a pixel
is. `no_std`, no DisplayService dependency, draws into an `ImageViewMut` or an `OwnedImage`.

- [ ] Implement the `render2d` backend interface: consume a validated `DrawList` and produce pixels.
  It is one backend among future others and its public surface is the backend trait, not an
  application-facing drawing API. Nothing outside this part names `soft2d`.

- [ ] Implement a coverage antialiasing rasteriser for filled paths under both fill rules, with
  bounded scratch storage, no allocation during a draw, and deterministic output for a given input.
  This is the core of the whole 2D stack: shapes, strokes, rounded rectangles, ellipses and glyph
  masks are all paths through it.

- [ ] Implement stroking by converting a stroke to a fill - caps, joins, miter limit and dashing -
  rather than by a second rasterisation path with its own rules. Keep the aliased integer line as an
  explicit fast path, with the rule it already had: integer Bresenham with BOTH endpoints included,
  ties at `error == 0` broken toward the smaller minor coordinate, and clipping applied before
  rasterising so a clipped line covers the same pixels as the visible part of the unclipped one. A
  caller drawing a connected polyline omits the first point of each segment after the first.

- [ ] Implement clipping as a coverage mask rather than as a rectangle test, so rounded and path
  clips cost the same machinery as rectangular ones, and nested clips intersect masks. The
  axis-aligned rectangle case keeps a fast path.

- [ ] Implement layers, group opacity, the Porter-Duff set and the named blend modes, and the basic
  filters - blur, drop shadow, colour matrix - over offscreen layer targets from `P02M0103a`.

- [ ] ONE implementation of pixel conversion, compositing and nearest/bilinear sampling, living in
  `graphics-core` and shared by `pix`, `soft2d`, `soft3d` and DisplayService's own copy and scale
  path; none of them carries a private second copy. This is already real: `pix::blend_over` is an
  integer straight-alpha source-over evaluated on sRGB-encoded bytes, and `soft3d` needs blending in
  linear light, so the shared primitive takes its WORKING SPACE as part of the contract and each
  caller states which it uses. Merging them without saying that would silently change what `pix`
  composites today. Fix the stage ORDER once, since every such disagreement is really a disagreement
  about it: decode transfer function -> convert straight to premultiplied -> sample and filter ->
  blend in the stated working space -> convert back to the target's alpha mode -> encode transfer
  function -> quantise. Bilinear fixes its sampling centre, its clamp/repeat/mirror behaviour, and
  that it premultiplies BEFORE interpolating - interpolating straight alpha pulls the colour of fully
  transparent texels into the result and rings dark halos around transparent edges. And "shared"
  means CALLED: four implementations agreeing on a specification is what the tree has now.

- [ ] Rectangles and gradients are exact rather than approximately agreed. `Rect` is half-open, a
  fill covers every sample point inside it, a one-pixel aliased `stroke_rect` lies INSIDE the
  rectangle rather than straddling its boundary, and a zero-width or zero-height rectangle draws
  nothing and is not an error. A gradient evaluates its stops in linear light along the projection
  onto its axis, applies its own transform first, and honours `Clamp`/`Repeat`/`Mirror` outside
  `[0, 1]`.

- [ ] Damage returned from a draw is CONSERVATIVE, not exact. Exact damage would mean comparing old
  and new pixels - a source-over with alpha zero changes nothing while covering a rectangle - and
  that cost defeats the purpose. Every draw returns the smallest inexpensive conservative raster
  bound: it contains every pixel that may have changed, is clipped to the target and clip stack, and
  is empty when no sample was reached.

- [ ] Host tests cover path filling under both rules, coverage values along known edges, stroke caps
  and joins, dashing, clip nesting and rounded clips, layer opacity against manually composited
  reference values, every Porter-Duff operator against its algebraic definition, transformed image
  drawing, nearest and bilinear sampling, clamp/repeat/mirror, straight and premultiplied
  compositing, sRGB/linear conversion, gradient stops and spread modes, glyph mask rasterisation,
  returned damage bounds, and guarded canaries around the target. Property and fuzz tests feed
  hostile coordinates, extents, pitches, transforms and degenerate curves and prove no panic and no
  out-of-bounds write.

## P02M0103d - 2D Test SW, the end-to-end 2D proof

The gate between the 2D stack and the 3D one. Nothing in `P02M0103e` starts until this passes.

- [ ] Add one governed PIE named **2D Test SW**, canonical artifact `test2d-sw.lsexe`, only
  `display + input-keys` grants, Esc/q exits, Space pauses, R resets. It renders THROUGH `render2d` -
  an application-local rasteriser or a duplicate drawing loop is not accepted, and that includes
  generating any test image, which is drawn with `render2d` or shipped as fixed data rather than by a
  private loop that is a rasteriser under another name.

- [ ] The scene exercises the whole public API rather than the subset a framebuffer demo needs,
  because a required feature the end-to-end test never runs is a feature nothing proves: filled and
  stroked Bezier paths under both fill rules, antialiased edges at a shallow angle, a rotated and
  scaled image, a multi-stop gradient with a non-default spread mode, a rounded-rectangle clip with
  content scrolling under it, a nested clip, a group-opacity layer containing two overlapping
  children, at least two non-`SourceOver` blend modes, a drop shadow, and a line of text as a
  positioned glyph run.

- [ ] It runs in PHASES, because "an animated background" and "two non-contiguous damage rectangles
  that reach the driver as two" contradict each other - a background that changes every frame changes
  every pixel, and its only honest damage is `Full`. The phases separate the claims instead of
  averaging them:

      1. full        everything drawn, damage = Full
      2. partial     background held still, objects move, damage = old bounds + new bounds
      3. multi-rect  exactly two distant regions change; the driver stand-in sees TWO rectangles
                     before any backend merging
      4. full-again  background parameters change, damage = Full
      5. resize      new generation, and its first frame is Full by the rule above
      6. scale       the scale factor changes with the logical size held constant; layout is
                     unchanged and every edge is resolved at the new physical resolution

- [ ] Prove the multi-surface model too, since `P02M0103a` introduced it and an untested object model
  is a claim: the application opens a SECOND surface - a popup or dialog - presents to both, and both
  survive independently when one is resized, hidden or closed.

- [ ] It passes this part only when: clean exit AND crash both restore the text console; a resize
  continues without ever presenting a stale image; nearest and bilinear filtering are both actually
  used; phase 3's two rectangles travel the whole path from application to driver as two; a live QEMU
  capture proves animation, antialiasing, blending and text; the package audit proves ET_DYN,
  provider identity and order, the exact grants and no statically duplicated drawing code; and there
  is no steady-state allocation once the queue and resources exist. Hold it to the same bar as the 3D
  one: host tests and a cross-built run on all three architectures, and a measured steady-state frame
  budget at 640x480 recorded in `docs/PERF.md`. A foundation whose only proof runs on one
  architecture is a foundation for one architecture.

## P02M0103e - render-math and render-scene, the public 3D API

Depends on `P02M0103a`. Every value below is normative: where an earlier draft offered two options,
one is chosen here.

- [ ] Two `no_std` libraries, separate from any renderer: `render-math` for `Vec2/Vec3/Vec4`,
  matrices, quaternions, transforms and camera projection; `render-scene` for the scene model.
  Splitting the scene model out is what lets a later GPU renderer consume the same scene without
  emulating the CPU one - with the model inside `soft3d`, "a different renderer" means "a different
  scene model" too. Build them as P02M0096a `.lslib` providers once two consumers or a measured
  ownership boundary justify it; the demo PIE duplicates no shared code.

  `render-math` is a CONTRACT and not a type list, and this file picks the values rather than
  requiring that someone pick them - "state the handedness" is not normative, a handedness is:
  angles in RADIANS everywhere, COLUMN-MAJOR storage, `M * v` as the transform, RIGHT-HANDED world
  and view space, clip-space depth in `[0, 1]`, counter-clockwise front faces. Constructors are named
  for what they encode - `perspective_rh_zo`, `orthographic_rh_zo` - so a caller cannot pick the
  wrong convention silently. Quaternions state their normalisation policy: constructors normalise,
  operations preserve unit length, and a zero-length quaternion is an error rather than a NaN
  generator. Inversion of a singular matrix returns a typed error and never a matrix of infinities,
  and every entry point states what it does with NaN and infinite inputs.

  Four of those choices only become unambiguous together, and leaving the last one out inverts what
  gets culled: `+Y` is up in world and view space, the camera looks along `-Z`, NDC `+1` is the TOP
  of the image, the surface row origin is `TopLeft`, and the viewport maps
  `y_window = (1 - (y_ndc * 0.5 + 0.5)) * height`. Front-face culling is evaluated BEFORE that Y
  inversion. A Y flip reverses apparent winding, so an implementation that culls after it culls the
  opposite faces while satisfying every other sentence in this file.

- [ ] `render-scene` owns the mesh, material, light, instance and camera model - and, because
  textures and blending are required below, also `Texture2D`, `Sampler`, `RenderState` with its
  `BlendState` and `DepthState`, and the `DrawList`. A scene model that cannot express "this draw is
  transparent and does not write depth" forces that state back into the renderer, which is exactly
  what splitting the two apart was for.

- [ ] Design `render-scene` so the SOFTWARE renderer does not become its ceiling. `soft3d` implements
  a subset and returns a typed `Unsupported` for the rest; it does not get to decide what the public
  3D model may express. Concretely, the model has to admit - without a redesign - additional material
  models, multiple render passes, offscreen render targets, instancing, a scene hierarchy and
  skeletal animation. None of those are implemented here. What is forbidden is a scene model shaped
  so that adding them means a new scene model, which is the same mistake one dimension up that this
  milestone's sixth pass was written to correct.

- [ ] 2D and 3D interoperate through the shared types rather than through a bridge: both use
  `graphics-core`'s `ImageLayout`, colour space, alpha mode, `Sampler` and `OwnedImage`. A 3D pass
  renders into an `OwnedImage` that `render2d` then draws as an image - a HUD over a game, a viewport
  in an editor, a 3D preview in a document - and a 2D pass renders into an `OwnedImage` that
  `render-scene` uses as a texture. Neither direction needs a conversion step, and that is the point
  of having one image model.

## P02M0103f - soft3d, the CPU 3D backend

Depends on `P02M0103a` and `P02M0103e`.

- [ ] Implement the triangle pipeline, with these conventions fixed: sample points at pixel centres
  `(x + 0.5, y + 0.5)`; fixed-point edge equations rather than floating-point comparisons, so
  coverage is exact and shared edges cannot double-fill or leave a seam; the top-left fill rule;
  deterministic back-face culling by winding; clipping against all six homogeneous clip planes named
  explicitly; perspective-correct interpolation; and a `u32` depth buffer - one format, not
  "24- or 32-bit", because a CPU rasteriser gains nothing from packing and loses the checked
  arithmetic. Degenerate, non-finite and off-screen triangles are skipped deterministically. A
  SUB-PIXEL triangle is NOT skipped: it either covers a sample point or it does not, and dropping it
  by size is a rule that makes small geometry flicker as the camera moves.

  "Fixed-point" and "`u32` depth" are only half a contract without the numbers, and identical
  coverage on three architectures is exactly what the missing half decides: `SUBPIXEL_BITS = 8`,
  `MAX_RASTER_EXTENT = 16_384`, float viewport coordinates quantised by round-half-away-from-zero,
  and edge equations evaluated in checked `i64`. Those two constants are what make the third
  checkable rather than aspirational: quantised coordinates fit in 22 bits signed, an edge product is
  two of them multiplied, and the difference of two such products is provably inside `i64` - write
  that proof down beside the constants, because "small enough that the product is representable" is a
  requirement nobody can verify. Depth maps `[0, 1]` onto `[0, 0xffff_ffff]` by
  round-half-away-from-zero, clears to `0xffff_ffff`, and compares with `Less`. All of this is on the
  BIT-EXACT side of the split at the top of this file.

- [ ] The clipper interpolates ALL varyings, not just position. Every vertex a clip plane creates is
  built with a single intersection parameter that is then applied identically to position, normal,
  UV, vertex colour and any other varying - clip position alone and the geometry is right while the
  texture and lighting jump at the near plane, which is a bug that looks like a texturing bug.

  "Named explicitly" means named, so here they are for the chosen right-handed `[0, 1]` clip space,
  each as the inequality a vertex satisfies to be inside:

      left    x + w >= 0        bottom  y + w >= 0        near    z     >= 0
      right   w - x >= 0        top     w - y >= 0        far     w - z >= 0

  With the three degenerate cases decided rather than deferred: a vertex with `w == 0` is not
  projectable and its whole primitive is REFUSED; a zero intersection denominator produces no new
  vertex and the result follows from the inside/outside classification alone; and any non-finite
  coordinate fails the primitive with `NonFinite` rather than being clipped to something plausible.
  The bound is likewise a number and not a promise of one: Sutherland-Hodgman against a convex volume
  adds at most one vertex per half-space, so `MAX_CLIPPED_VERTICES = 3 + 6 = 9` and
  `MAX_TRIANGLES_AFTER_CLIP = 9 - 2 = 7` under fan triangulation. Those live in the clipper and NOT
  in `RendererLimits` - they are proven, not configured.

- [ ] Implement materials and lighting: per-face and base colour, vertex normals transformed by the
  inverse transpose, an ambient term, normalised Lambert diffuse, Blinn-Phong specular with bounded
  shininess, one directional key light and one animated point light with attenuation, computed
  PER FRAGMENT. Lighting is in linear light and converts to the display transfer function on
  output. An `Unlit` material is required as well - it is what a debug view, a UI overlay and a
  texture test need, and adding it later means adding a second path through the fragment stage.

  Names of algorithms are not a specification - "Lambert plus Blinn-Phong plus attenuation" has
  several implementations that disagree by more than a tolerance, and a test needs one expected
  answer. Write the equation:

      base    = material.base * vertex_colour * texture_rgb
      N = normalize(normal),  L = normalize(light_pos - frag_pos)
      V = normalize(eye_pos - frag_pos),  H = normalize(L + V)
      diffuse  = max(dot(N, L), 0)
      specular = if diffuse > 0 { pow(max(dot(N, H), 0), shininess) } else { 0 }
      atten    = 1 / max(kc + kl*d + kq*d*d, EPS)
      out      = clamp(ambient*base + atten*(diffuse*base + specular*spec_colour), 0, 1)

  and settle what it still leaves open: the value of `EPS`, the valid range of `shininess`, that
  specular has its OWN colour rather than multiplying the base, that lighting never changes alpha,
  and that the clamp happens before the transfer-function conversion and not after.

- [ ] Textures are REQUIRED, not optional future work. A renderer without them is a demo of one
  scene rather than a general renderer, and every later consumer wants them: UV coordinates on the
  vertex, perspective-correct UV interpolation, nearest and bilinear sampling, clamp and repeat
  addressing, and a bounded texture size checked at ingestion. Alpha blending is required with it:
  opaque and source-over, with `depth_write = false` for the transparent pass and the draw order
  stated - sorting is the caller's job and the renderer says so rather than pretending it is not
  there.

  Sampling and blending are where two implementations diverge invisibly, so name the semantics: the
  supported texture formats are `graphics-core`'s, with the accepted `AlphaMode` on ingestion stated
  and straight alpha converted once at ingestion rather than per sample; sRGB texels are DECODED to
  linear before filtering, because filtering encoded values blends the wrong quantity; texels are
  premultiplied before interpolation for the same reason `soft2d` requires it; source-over is
  evaluated in LINEAR LIGHT and converted to the display transfer function on output; texel centres
  are at `(i + 0.5) / extent`; and `repeat` addressing is defined for NEGATIVE and large UVs by
  Euclidean remainder, so `-0.25` and `0.75` sample the same texel rather than differing by the sign
  convention of the language's `%`. The transparent pass turns off depth WRITES only - the depth TEST
  stays on, or transparent geometry draws over the objects in front of it.

  "Converted once at ingestion" raises a question it does not answer - converted into WHAT, owned by
  whom - so split it: `render-scene::Texture2D` owns the ORIGINAL canonical layout and bytes and is
  what a scene describes; `soft3d::TextureResource` is created by uploading one, validates it,
  converts it to the renderer's internal premultiplied linear representation, and counts against
  `max_texture_bytes`. Textures are therefore long-lived renderer resources even though `MeshView` is
  transient, and a later GPU renderer builds its own resource from the same scene texture instead of
  inheriting a CPU layout. `RendererError` gains `InvalidTexture` and `InvalidRenderState` with it.

- [ ] Bound the renderer with a `RendererLimits` value rather than fixed configured constants:
  `max_lights`, `max_draws`, `max_input_triangles`, `max_generated_triangles`, `max_texture_extent`,
  `max_texture_bytes`, `max_scratch_bytes`. A caller states its limits, the renderer allocates
  against them once, and hostile geometry meets a number the caller chose instead of one compiled in.
  Caller-chosen does NOT mean unbounded: every request is checked against the implementation's hard
  maximum, what the raster arithmetic can represent, and the Domain's budget - otherwise `usize::MAX`
  formally satisfies a bounded design while defeating it. But a failed check REFUSES or NEGOTIATES
  and never silently clamps: a caller that asks for 100_000 draws and is quietly given 10_000 finds
  out three frames later, in a failure that names neither number. Over the hard maximum is
  `LimitExceeded`; over the Domain budget is `OutOfMemory`; and if the renderer wants to grant less
  than was asked, construction returns the ACTUAL limits alongside the renderer so the caller can
  see what it got. The clip buffer size is not on this list; it is the proven constant established
  above.

  Validate indices and finite transforms at ingestion, account peak memory to the process Domain and
  reuse frame allocations. Scene traversal and clipping allocate nothing per triangle. The renderer
  VALIDATES its borrowed colour target - format, extent and layout against the frame it is about to
  draw - and uses checked allocation only for what it owns: the depth buffer, scratch storage and any
  tile or bin buffers. It does not allocate the colour target, because it does not own it.

- [ ] Pass geometry as a transient `MeshView` borrowed for the duration of a draw rather than an
  owned buffer the renderer keeps, and return a typed `RendererError` rather than an option: a
  caller that gets `None` cannot tell "limits exceeded" from "not finite" from "out of memory", and
  those need different answers. The variants are `InvalidMesh`, `InvalidTransform`,
  `UnsupportedFormat`, `TargetMismatch`, `NonFinite`, `LimitExceeded`, `OutOfMemory`,
  `InvalidTexture`, `InvalidRenderState` and `Unsupported`. The renderer BORROWS its colour target -
  an `ImageViewMut` or an `OwnedImage` from `P02M0103a` - and owns only its depth buffer and scratch
  storage.

- [ ] Frame scheduling lives ABOVE the renderer and not inside it. `soft3d` knows nothing of
  DisplayService: it borrows a colour target, draws, and returns. Acquire, present, pacing,
  completion, resize, `OUT_OF_DATE` and focus behaviour belong to the application or to a shared
  graphics-app helper shared with the 2D side - putting the present queue inside `soft3d` is what
  would make the later GPU renderer reimplement a window system to render a triangle. This item is
  the INTEGRATION gate for that helper: render into the acquired image, wait for CONSUMER-RELEASE
  before reusing it, keep at most the negotiated frames in flight, pace against the timing contract
  rather than busy-spinning, reacquire surface images OUTSIDE the renderer on resize while the
  renderer transactionally recreates the depth buffer and scratch storage it owns, keep or cleanly
  release the old scene on allocation failure, and block or throttle in the background while
  consuming no raw input.

- [ ] Host tests cover vector, matrix and quaternion identities, camera and frustum transforms,
  clipping against every plane, winding and culling, perspective interpolation, depth ordering,
  shared-edge fill, sub-pixel coverage, texture addressing and filtering, alpha blending,
  non-finite and degenerate input, lighting and colour transfer, and guarded canaries around the
  colour and depth targets. Property and fuzz tests feed hostile meshes, indices, transforms,
  extents, UVs and viewport rectangles under strict allocation limits.

## P02M0103g - 3D Test SW, the end-to-end 3D and interop proof

- [ ] Add one governed PIE application named **3D Test SW**, with canonical artifact
  `test3d-sw.lsexe` and only `display + input-keys` grants. It acquires a present queue and renders
  a continuously rotating indexed cube above a simple ground plane. The six cube faces have visibly
  distinct material colours, correct shared-edge depth and occlusion, smooth or deliberately hard
  face normals, ambient plus directional plus animated point lighting, and specular highlights. A
  perspective camera, a dark non-flat background and the ground reference make rotation and depth
  unmistakable; no face-order painter shortcut is accepted.

- [ ] The scene MUST exercise textures and blending, because `P02M0103f` makes both required and a
  required feature that the end-to-end test never runs is a feature nothing proves. One cube face
  carries a checkerboard texture, the ground carries a repeated one, and a small semi-transparent
  panel stands in front of the scene - which together put UV interpolation, sampling, both
  addressing modes, alpha blending and the depth test under transparency through the whole path from
  scene to scanout. The textures are generated procedurally, so the application still needs only
  `display + input-keys` and no storage grant.

- [ ] The scene MUST prove 2D/3D interop, because that is what an actual application looks like and
  the shared image model above is otherwise an untested claim: `soft3d` renders the scene into an
  `OwnedImage`, and `render2d` composites a HUD over it - antialiased shapes, a translucent panel and
  a line of text as a glyph run - before the result is presented. One frame therefore travels
  `render-scene -> soft3d -> OwnedImage -> render2d -> soft2d -> Surface`, which is the path a game,
  an editor and a map application all take.

- [ ] Make the scene interactive and recoverable: Esc/q exits, Space pauses, R resets,
  arrow keys orbit the camera and +/- changes distance or field of view. Key-down/up state
  comes through the P02M0091 focus capability; focus loss clears held state. Resize recreates
  targets and preserves camera/animation state. Clean exit, crash, allocation failure,
  emergency kill and DisplayService restart always release images and restore the text
  console.

- [ ] Provide deterministic demo and test controls without exposing them in normal UI: fixed
  simulation time per frame, a fixed camera and a fixed light seed. A host renderer test produces a
  small golden frame with tolerance-based comparison rather than requiring bit-identical
  cross-architecture floating point. The live application stays clock-driven and visibly animated.

- [ ] A golden frame is a REGRESSION test and not a correctness oracle - it proves the output has
  not changed, not that it was ever right. Add small independent checks beside it: per-stage
  differential tests, or a tiny reference rasteriser over 16x16 tiles. The cheapest one worth having
  first is two triangles forming a quad: across the shared edge there must be neither a gap nor a
  doubly-covered pixel, which is a property that can be checked without a reference image at all.

- [ ] Keep the 30 FPS demo floor and add a real benchmark beside it: a rotating cube over a ground
  plane at 640x480 is light enough that a slow rasteriser passes it. A deterministic benchmark scene
  with a fixed triangle count, deliberate overdraw, clipping and textures, reporting triangles per
  second, shaded fragments per second and nanoseconds per stage - and pin the environment those
  numbers mean anything in: vCPU count, QEMU version and configuration, CPU model, profile flags,
  and whether the clock is the guest's or the host's.

- [ ] Governed kernel tests launch the staged PIE against stand-in Display/Input services
  and assert acquire -> multiple distinct presents -> resize/recreate -> key interaction ->
  release/exit, plus crash restoration and denied-capability behavior. Package audits prove
  ET_DYN/provider identity/order, exact grants and no static duplicate renderer/runtime.

- [ ] Live QEMU validation on x86_64 captures at least three timed frames and uses pixel
  checks to prove the scene is nonblank, the projected cube occupies a bounded central
  region, depth occlusion and lighting gradients exist, and successive frames differ while
  the background/console do not leak through. There is deliberately NO "all six material colours
  appear across the captured rotation" check here: that assertion cannot mean what it says, because
  which faces are visible depends on the rotation axis, the camera and the lighting - the bottom face
  may never be visible from an ordinary camera - and shading changes the RGB any classifier looks
  for. What replaces it is four checks that can each fail for one reason: DETERMINISTIC TEST POSES in
  which the visible face is known in advance and is verified per pose; the checkerboard face sampled
  for its alternating pattern; the repeated ground texture sampled for its periodicity; and the
  semi-transparent panel sampled for a blend of panel and background rather than either alone. The
  LIVE animation check asserts only that the image changes between frames. Capture after resize on
  desktop and mobile-like aspect ratios; q must restore the console. AArch64 and RISC-V must
  cross-build and run deterministic renderer tests; live screenshot parity uses tolerances where
  emulation cost is practical.

- [ ] Measure release performance and memory at 320x240, 640x480 and 800x600. The required
  floor is a stable 30 FPS at 640x480 on the documented x86_64 QEMU/KVM host with NO STEADY-STATE
  ALLOCATION while extent, scene and resources are unchanged - which is what "no frame allocation
  after warm-up" was reaching for and does not say, since a resize and a texture upload legitimately
  allocate and are measured separately - plus bounded present latency and a reported
  colour/depth/scene peak. Record transform, clipping, raster, lighting, texture sampling, fragment
  shading, blending and present times separately in `docs/PERF.md`. Optimise tile and bin traversal
  only from measurements, without architecture-specific output corruption or unsafe unchecked
  indexing. Fixed-point edge evaluation is NOT on that list: it is a correctness mechanism this
  milestone requires for exact shared-edge coverage, so it is not something a measurement may decide
  to drop - only its implementation may be tuned.

- [ ] Publish `docs/GRAPHICS_2D.md` and `docs/SOFTWARE_3D.md`. The 2D document covers the public
  drawing model, coordinate spaces and scale, paths and fill rules, the antialiasing contract, paints
  and gradients, clipping and layers, compositing operators, the glyph-run seam, the backend
  interface a GPU implementation replaces, and a performance table. The 3D document covers
  coordinate/colour conventions, pipeline stages, clipping/raster rules, scene/material format,
  memory formulas, controls, its performance table and the exact boundary a future
  Mesa/Gallium/Vulkan backend replaces. Both include a screenshot of the actual test application and
  a tri-architecture validation matrix.

- Done when, PER PART:
  - `a` is done when the API-neutral WSI/synchronisation/resource/lifecycle contracts are bounded,
    capability-scoped, documented and hostile-input tested, multiple surfaces per connection work,
    and logical size, physical extent and scale factor are three separate numbers in the interface.
  - `b` is done when `render2d` records and validates a display list covering paths, antialiasing,
    strokes, transforms, paints, nested clipping, layers, compositing, image drawing, basic filters
    and glyph runs, and passes its backend-free host tests.
  - `c` is done when `soft2d` implements that display list, shares `graphics-core`'s conversion,
    compositing and sampling rather than duplicating them, and passes its host and fuzz tests.
  - `d` is done when `test2d-sw.lsexe` passes its host, package, tri-architecture and live QEMU
    gates, including the scale-change and second-surface phases.
  - `e` is done when `render-math` and `render-scene` fix every convention above and the scene model
    admits further material models, passes, offscreen targets, instancing and hierarchy without a
    redesign.
  - `f` is done when `soft3d` renders clipped, depth-tested, textured, blended and lit indexed
    geometry into a borrowed target and passes its host tests and its benchmark.
  - `g` is done when a governed dynamically linked `test3d-sw.lsexe` continuously shows the
    interactive **3D Test SW** scene with a `render2d` HUD composited over it, survives resize, focus
    loss and failure, restores the console on every exit path, meets the measured 640x480 frame
    budget and passes host, package, focused QEMU and tri-architecture gates.

- Explicitly deferred, each to a named milestone rather than to "later": full text shaping,
  OpenType, font fallback, BiDi and line layout (`P02M0136`); the foreign C/C++/TLS/Mesa substrate
  (`P02M0135`); a widget toolkit, layout engine, themes, accessibility and gesture recognition; the
  compositor, window decorations, desktop shell and multi-application presentation; SVG and PDF
  parsing; non-separable blend modes; bicubic and anisotropic sampling; actual
  EGL/OpenGL/OpenGL ES/Vulkan entry points and conformance; Mesa/Gallium, LLVM shader compilation,
  GLSL/SPIR-V compilation, virglrenderer/Venus, virtio-gpu context/blob/3D command execution, native
  hardware drivers, compute and ray tracing. Each requires a separately approved milestone and must
  consume P02M0103 contracts rather than weakening capability, validation, accounting or identity
  gates.
- Concept: P02M0014/P02M0038 (virtio-gpu 2D scanout and resize), P02M0091 (surface/input app platform),
  P02M0093/P02M0096a (shared providers and PIE ownership), P02M0097 (final userspace/system layout),
  P02M0008/P02M0010 (observability and governed resources), and the future desktop/GPU phases.
