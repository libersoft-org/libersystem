# P02M0103 - The graphics platform desktop and mobile applications are built on

Status: FUTURE TRACK, PLANNED AFTER P02M0096a AND P02M0097; INDEPENDENT OF P02M0102 AND NOT A
PHASE-2 COMPLETION GATE.

**REWRITTEN 2026-08-15 to be a single statement of the work.** It carried its outside reviews inline
for two rounds, and the third review's sharpest finding was about the document rather than the
design: the main text still said "24- or 32-bit depth" and "textures remain optional future work"
while a review section two hundred lines below said "pick one depth format" and "textures are not
optional" - both as open checkboxes, with nothing to say which was newer. The reviews are gone;
their conclusions are the items below and their reasoning is stated where it changes a decision.
Everything in this file is what to build.

A fourth pass closed items that required a value to be CHOSEN without choosing it. "State the
handedness", "a small cap", "pick a depth format" are not normative. Where such an item appears below
it now carries the number: `MAX_DAMAGE_RECTS = 16`, 8 subpixel bits, the clip-plane inequalities,
`MAX_CLIPPED_VERTICES = 9`, column-major `M * v` right-handed with `[0, 1]` clip depth and CCW front
faces.

A fifth pass drew the line those numbers need. "Two implementations must produce the same pixels" is
true of the INTEGER half of a rasteriser and is not achievable for the floating-point half - operand
order, FMA contraction, the libm in use and the optimiser all move the last bit. So the contract is
split and each item says which side it is on - and the split is PER DIMENSION, because 2D and 3D
coverage are not the same problem. In 3D, coverage is discrete sample-point classification against
quantised edges and IS bit-exact. In 2D, coverage is an antialiased area estimate, and this file
deliberately lets a backend choose its coverage algorithm - so 2D coverage is TOLERANCE-BASED while
2D path topology, clip classification and quantised geometry stay deterministic. Requiring a
particular coverage number from an unspecified algorithm was a contradiction between the split and
the antialiasing item. BIT-EXACT: geometry classification, clipping topology,
viewport quantisation, coverage, shared-edge ownership, and depth clear, storage and comparison.
TOLERANCE-BASED: interpolated floating attributes, filtering, shading and the final RGB conversion.

A sixth pass changed what this milestone is FOR. Every pass before it improved the inside of a
document whose purpose was "enough graphics to prove a present queue and then draw a software cube".
The real purpose is a platform for a desktop environment, a mobile shell and ordinary applications
written by other people. That pass introduced `render2d` above `soft2d`, because `soft2d` was both
the public API and the CPU implementation of it, and it un-deferred paths, antialiasing, transforms,
clipping, layers, compositing and text - which are not advanced features a desktop wants eventually
but what an icon, a button, a scroll viewport and a line of text are MADE OF.

**A seventh pass finished that correction, because the sixth applied it to one dimension and not the
other, and because "complete" was still an adjective rather than a gate.** Two changes:

  - **`render3d` was missing, and its absence was the same mistake the sixth pass had just fixed.**
    The layering read `render-scene -> soft3d` and was described as the equivalent of
    `render2d -> soft2d`. It is not. `render2d` is a DRAWING AND COMMAND API; `render-scene` is a
    retained DATA MODEL. The 3D counterpart of `render2d` is a resource, pipeline, pass and command
    API - and with it missing, an application wanting a CAD viewport, a custom engine, a
    postprocessing chain, render-to-texture or a non-standard material had nowhere to go except the
    scene graph or the CPU rasteriser. The stack is now `scene3d -> render3d -> soft3d`, and a future
    GPU backend implements `render3d` rather than a whole scene graph.
  - **"Complete" is now two finite PROFILES rather than a word.** `Render2D Core Profile 1` and
    `Render3D Core Profile 1` each enumerate a closed list of features that the public API expresses,
    the software backend implements ENTIRELY, and a conformance suite covers. Inside a profile a
    backend may NOT answer `Unsupported`; that variant exists only for post-profile extensions. This
    is what converts "a complete software library" from an intention into something a gate can refuse.

That pass also removed three phrases that quietly capped the design: `conic gradient in the type
space even if the first backend refuses it`, `non-separable blend modes are deferred by name`, and -
the largest - `soft3d implements a subset and returns a typed Unsupported for the rest`, together
with the scene-model item that required hierarchy, passes, offscreen targets, instancing and skinning
only to be ADMISSIBLE rather than implemented. A library whose backend may decline its own API is a
specification for a demo.

**An eighth pass closed the contracts INSIDE those layers, and corrected a guarantee the seventh pass
had quietly broken.** The architecture did not move; four direct contradictions and one whole class of
under-specification did. The contradictions: the compositing line said "12 Porter-Duff operators" over
a list of thirteen (`Plus` is additive and is not one of them); the 3D profile named five primitive
topologies and the backend then promised "all six"; `sRGB8A8` sat in the format list while
`ColorSpace` already carried the transfer function, so two places could disagree about whether bytes
are encoded; and the 2D part required loading a real scalable font while the milestone that parses
font files, `P02M0136`, depends on this one - a dependency cycle in which each milestone waits for the
other or writes a throwaway parser twice.

The broken guarantee is the one worth naming on its own. The fifth pass promised BIT-EXACT geometry
classification and clipping topology, and that was achievable when the vertex pipeline was
fixed-function. The seventh pass added a PROGRAMMABLE vertex stage, whose output position is computed
by floating-point shader code that the same split puts on the tolerance side - so the input to a
bit-exact stage stopped being bit-exact, and two architectures could classify a vertex at
`z = +/-1e-8` differently and BOTH conform. A guarantee that its own inputs cannot support is worse
than no guarantee. The fix is to make the seam explicit: the clip-space POSITION output has strict
floating-point semantics of its own - fixed operand order, no FMA contraction, canonical NaN, stated
rounding - and is then QUANTISED into a canonical clip representation before any classification runs.
Everything downstream of that quantisation is bit-exact; every other varying stays tolerance-based.

The under-specified class is everything a profile entry names without defining: what a tone-mapping
operator or a dither actually is, what a blend factor set contains, where MSAA samples sit, what a
shader IR may express, what a resource descriptor holds. Those are listed below with values, because
a profile whose entries cannot be implemented twice the same way is a list of intentions.

**On scale, stated plainly rather than discovered later:** the profiles below are the work of a
compact 2D vector engine and a compact software 3D pipeline with programmable shading. That is a
subsystem, not an ordinary milestone, and the nine parts exist so it can be built and gated in
order rather than attempted at once. The build order is `s -> a -> b -> c -> d` for the 2D track and
`s -> a -> e -> f -> g -> h -> i` for the 3D one, with `d` gating nothing in 3D and `e` able to start
as soon as `a` is done. `s` comes first in both because it is the normative specifications, and a
backend written before its specification is the specification. What is NOT negotiable in either track is that no part is called done while its
backend can decline a command its profile requires.

Three things stay DEFERRED, all by the same rule this tree applies elsewhere - a shape with fewer
than two real consumers is a guess written down:

  - the graphics adapter/device/context/queue vocabulary, which had one consumer and it was the null
    backend written to exercise it. That is the OS-level device model, and it is distinct from
    `render3d`, which is a userspace rendering model with two planned implementations;
  - the generic timeline/fence capability. What presentation needs is a completion mechanism for
    presentation, which is specified in `a`; a system-wide timeline is worth extracting when GPU,
    video decode or DMA also want one;
  - the resource accounting for device-local bytes, contexts, queues, command bytes and in-flight
    submissions, none of which exist once the above are deferred.

The C/C++/TLS/Mesa substrate lives in `P02M0135` and the text shaping stack in `P02M0136`. Neither
gates anything here: `render2d` consumes an already-shaped `GlyphRun`, and the Rust renderers never
needed a C++ substrate.

The architectural split is deliberate: OpenGL/OpenGL ES/Vulkan are userspace API libraries; WSI,
presentable images, synchronisation, governed memory and access to a capability-scoped graphics
device are OS contracts; virgl/Venus/native-device protocols belong to a backend/driver. The software
renderers exercise the same window-system, resource-lifetime, resize and frame-pacing contracts but
remain ordinary CPU clients of DisplayService. They are not a fake OpenGL implementation and no
provisional `gl*`/`vk*` API is introduced merely to draw a demo.

## P02M0103s - The normative specifications, frozen before any backend exists

A ninth pass found a defect that is about this document rather than about the design, and it is the
same shape as the one the third pass found: the file had grown a large number of sentences of the
form "ONE named tone-mapping operator", "the exact 2x and 4x sample positions", "a stated number of
anisotropic taps", "either strict semantics or quantise through one rule - choose one and say which",
"sampling while rendering is refused or defined". Every one of those correctly identifies something a
specification must decide. **None of them decides it.** A milestone that enumerates the open
questions reads like a specification and gates like a wish, and two implementations reading it still
produce different pixels - which is the exact failure the fourth pass was written to end.

The answer is NOT to inflate this file with matrices, kernels and sample coordinates. It is to admit
what this file is - a ROADMAP and a definition of done - and to put the actual values in normative
documents that are written and FROZEN BEFORE the backends they govern. `docs/GRAPHICS_2D.md` and
`docs/GRAPHICS_3D.md` currently appear as the last item of the last part, which is backwards: a
specification published after the thing it specifies is a description.

- [ ] Write `docs/graphics/IMAGE_COLOR_PROFILE_1.md` and freeze it before `P02M0103a` builds anything
  on it. It carries what the colour item only promises: the Bradford adaptation matrices, the
  reference white luminance, the named tone-mapping operator WITH its equation and parameters, the
  gamut-mapping equation, the exact PQ and HLG transfer functions and inverses, the ordered-dither
  matrix and its phase, and the half-float rounding, subnormal, NaN and infinity policy.

- [ ] Write `docs/graphics/WSI_PROFILE_1.md`: the scale-factor representation and the exact
  logical-to-physical rounding rules, the surface event set, the present state machine, damage
  semantics, and the completion contract.

- [ ] Write `docs/graphics/RENDER2D_PROFILE_1.md`: the equation for every Porter-Duff operator and
  every blend mode including the non-separable four with their luminance and saturation models and
  gamut clipping; the flattening tolerance as a NUMBER, the maximum subdivision depth as a number,
  and the projective `w` epsilon as a number with the horizon rule chosen; the boolean-operation
  answers rather than the boolean-operation questions; the per-node filter contract; the LCD gamma;
  and `Render2DLimits` with its guaranteed minima.

- [ ] Write `docs/graphics/RENDER3D_PROFILE_1.md`: the format capability table (sampled, filterable,
  renderable, blendable, MSAA, vertex, readback, attachment - per format, with full names rather than
  `R8`/`RGBA8` shorthand); the vertex format table; the rasteriser state table; the exact 2x and 4x
  MSAA sample positions with the shading frequency, centroid rule, mask order, alpha-to-coverage
  mapping and integer/depth resolve rules; the per-format depth and stencil semantics with the
  `Depth32F` question ANSWERED; the sampler contract with tap counts, footprint, LOD formula,
  cube-face orientation and seam rule, mip-generation kernel, depth-compare return and border-colour
  representation; and the resource hazard policy stated as rules rather than as "refused or defined".

- [ ] Write `docs/graphics/SHADER_IR_1.md` with its own version and profile hash: integer overflow,
  division and modulo by zero, NaN, infinity, signed zero and subnormal behaviour, float-to-integer
  conversion, transcendental accuracy bounds, uninitialised values, out-of-bounds array access,
  uniform-buffer layout and alignment, matrix memory layout, helper-lane and post-`discard` derivative
  behaviour, implicit versus explicit LOD per stage, and the versioned serialised encoding with
  instruction IDs and canonical constant forms.

- [ ] Write `docs/graphics/SCENE3D_PROFILE_1.md`: the PBR equations and constants - GGX/Trowbridge-
  Reitz, Smith visibility, Schlick Fresnel, the roughness remapping and minimum, environment
  prefiltering, the BRDF LUT - plus shadow-map format, constant and slope bias, PCF kernel, the
  cascade decision, the bloom threshold and kernel, the fog equation, and the root-motion policy
  chosen rather than required.

- [ ] Then move `docs/GRAPHICS_2D.md` and `docs/GRAPHICS_3D.md` to what they should be: the
  human-facing overview and the place performance tables, conformance results and the screenshot
  land at the END. The normative content lives in the profile documents above and is frozen first.

- [ ] State the GUARANTEED MINIMUM limits in each profile document, because implementation-defined
  limits without a floor let a backend pass conformance while being useless: a `max_texture_extent`
  of 16, a `max_draws` of 1 or a `max_shader_instructions` of 8 would satisfy every other sentence
  here. `RENDER2D_PROFILE_1_MIN_LIMITS`, `RENDER3D_PROFILE_1_MIN_LIMITS` and
  `SCENE3D_PROFILE_1_MIN_LIMITS` are part of the profile, and the conformance suites run against
  those minima rather than against whatever the backend happens to offer.

- [ ] Make a change to any frozen profile document a VISIBLE event, not an edit: each carries a
  version and a hash, the machine-readable registry carries the same hash, and a gate refuses a tree
  where a backend or a conformance suite claims a profile version the document does not match. This
  is what stops the four artefacts - document, registry, backend, suite - from drifting apart, which
  is the failure every "complete" claim in this file depends on not happening.

## P02M0103a - Common graphics platform

Everything both dimensions stand on, and nothing that waits for a GPU. Every later part depends on
this one; it depends on nothing in the others.

- [ ] Write `docs/GRAPHICS.md` first, and name the layers in it, because "framebuffer" currently
  means five things: the UEFI boot surface in `bootproto`, the virtio-gpu resource's DMA backing,
  the DisplayService scanout, an application's surface, and `pix::Target`. FRAMEBUFFER is the legacy
  linear boot surface only; SCANOUT is what the display controller is showing; IMAGE is any 2D
  region of pixels; SURFACE is a presentable application object; RENDER TARGET is an image a
  renderer draws into. Freeze the ownership diagram above and the future integration routes -
  OpenGL/ES through EGL and a Mesa state tracker, Vulkan through a loader and ICD with Venus as the
  likely transport, DisplayService as the WSI and presentation owner, the display driver as device
  transport - and record which boundary validates every untrusted length, opcode and resource
  reference. Do not invent a common GL/Vulkan command language or expose virtqueue descriptors to
  applications.

- [ ] Define the canonical image model, and keep it separate from the future GPU one. The base type
  describes a plane of pixels and nothing else: extent, pitch, pixel storage, alpha mode, row origin
  and MEANING - and the meaning is the only place a colour space lives, because a `color_space`
  field beside an `ImageMeaning::Color(ColorSpace)` is two answers to one question and they drift
  exactly the way the byte-length field did. A non-colour image therefore has no colour space at
  all rather than an ignored one:

      struct ImageLayout {
          extent: Extent2D, pitch: u32, storage: PixelStorage,
          alpha: AlphaMode, origin: RowOrigin, meaning: ImageMeaning,
      }
      enum ImageMeaning { Color(ColorSpace), Data, NormalMap(NormalMapConvention), Depth, Mask }

  Every offset and size is computed through checked arithmetic. It does
  NOT store a byte length - it computes one, `required_bytes() -> Result<usize, LayoutError>`,
  because a stored length beside a view that carries a real slice is two answers to one question and
  they drift. The formula is exact rather than "the size the extent needs", because the last row does
  not include its padding and an implementation that charges a full pitch for it refuses a legal
  framebuffer: `(height - 1) * pitch + minimum_row_bytes`, all in checked arithmetic.
  `ImageView` validates `data.len() >= layout.required_bytes()?`. A larger allocation
  with trailing padding may be described by a separate `allocation_len` beside the layout, never by
  overwriting the mathematically required size.

  A terminal raster and a decoded PNG need none of mip levels, array layers, sample counts, tiling,
  usage or memory domain - those belong to a `GpuImageDesc` that a later backend milestone adds ON
  TOP of this layout, sharing its format and extent. Building the ordinary image model out of the GPU
  one replaces four over-specific representations with one over-general one.

- [ ] Use TWO coordinate spaces and say which is which, because a platform that only has integer
  pixel coordinates cannot do HiDPI, fractional scaling, zoom, rotation or smooth animation - and
  those are not desktop luxuries, they are what a phone does on every orientation change. The PUBLIC
  drawing coordinate is `f32` and SIGNED: geometry has to be positionable between pixels and has to
  clip off the left and top edges as naturally as off the right and bottom, and an unsigned integer
  parameter makes "half a pixel to the left of the origin" unrepresentable. Integer coordinates stay
  INSIDE the rasterising backend, where quantisation is defined. Both kinds are HALF-OPEN,
  `[x, x + width) x [y, y + height)`, so adjacent rectangles tile without overlapping and an empty
  rectangle is width or height zero. Presentable surfaces have a fixed `TopLeft` row origin in v1,
  with `RowOrigin` on the layout for images that are not presentable.

  Give the two spaces two TYPES, because one `Rect` cannot serve both and the version that tried was
  wrong at one end or the other: a damage rectangle crossing an IDL boundary must be whole physical
  pixels, and a drawing rectangle must be fractional and signed. So `PointF`/`RectF` (`f32`) for
  geometry, transforms, paths and drawing bounds; `PixelOffset` (`i32`) and `PixelRect` (`u32`) for
  damage, post-rasterisation scissor, surface extents and everything on the wire. `liber:graphics@1`
  carries `pixel-rect` and never the float one - a wire format with an `f32` rectangle whose meaning
  depends on a transform stack the receiver cannot see is not a wire format.

- [ ] Carry the FORMAT SET both profiles need, not only the ones a scanout accepts. Eight-bit RGB is
  what a display takes; it is not what a mask, a glyph cache, a filter intermediate, a wide-gamut
  composite or an HDR target is made of, and adding those formats after the compositing code exists
  means rewriting the compositing code. The mandatory set:

      A8_UNORM            coverage masks, glyph masks, alpha-only layers
      R8_UNORM            single-channel data images
      R8G8_UNORM
      B8G8R8X8_UNORM      scanout
      R8G8B8X8_UNORM      scanout (GOP PIXEL_RGB)
      B8G8R8A8_UNORM
      R8G8B8A8_UNORM      encoding is never a second storage format - see below
      R10G10B10A2_UNORM   wide-gamut scanout
      R16G16B16A16_UNORM
      R16G16B16A16_FLOAT  the canonical intermediate

  And name the canonical INTERMEDIATE explicitly, because the choice is invisible until the artefacts
  appear: layers, filter intermediates and offscreen composition are premultiplied LINEAR
  `R16G16B16A16_FLOAT`. Repeated compositing through 8-bit sRGB intermediates bands and loses
  precision, and a blur over an 8-bit intermediate is where it shows first.

  A second arm handles what firmware hands over. `src/uefi/src/gop.rs` accepts `PIXEL_RGB`,
  `PIXEL_BGR` and `PIXEL_BIT_MASK` with validated contiguous disjoint channel masks whose ELEMENT
  SIZE comes from the masks, so 16- and 24-bit modes are live; `bootproto::Framebuffer` carries that
  as `bpp` plus six shift/size fields and `term::Geometry`/`term::Raster` carry it again. Narrowing
  the model to fixed formats would reintroduce a defect this tree already fixed - the comment at
  `gop.rs:72` records that a literal `32` there gave a firmware-reported 24- or 16-bit layout "a
  diagonal smear rather than a picture". So:

      enum PixelStorage {
          Known(PixelFormat),                 // the list above
          PackedRgbUnorm(PackedRgbLayout),    // bytes_per_pixel + per-channel shift/bits + reserved
      }

  `PackedRgbUnorm` exists for BOOT AND SCANOUT ADAPTERS - the GOP hand-off and the terminal - and is
  not a texture format, not a presentable application surface format and not something a renderer
  samples.

- [ ] Say which alpha combinations are VALID and which are merely unimplemented, and fix the
  byte-level rules two implementations otherwise answer differently. `AlphaMode` is `Opaque`,
  `Straight`, `Premultiplied`; an `X8` format is `Opaque` only, so `Straight` and `Premultiplied` on
  one are a type error and not an unsupported case; an `A8` format carries alpha and nothing else.
  Under `Opaque` an alpha channel READS as 1.0 and is WRITTEN as `0xff` rather than carried through
  unexamined. Under `Premultiplied`, a pixel whose channel exceeds its alpha is NON-CANONICAL: it is
  accepted, it is not an error, and every operation may treat it as clamped to alpha - stating that
  is cheaper than a validation pass over every uploaded image. Channel order is defined by the format
  NAME and never by host endianness; float values convert to integer by round-half-away-from-zero
  after clamping; NaN converts to zero and infinities clamp rather than wrapping or panicking; and
  the `X` byte of an `X8` format, and the reserved channel of a packed layout, is IGNORED on read and
  written as `0xff`, so a producer cannot leak stale bytes into it and a consumer cannot start
  depending on one.

- [ ] Colour management is a MODEL, not two transfer functions. `Linear`/`Srgb` over implied sRGB
  primaries is right for a first scanout and wrong for a phone, and retrofitting a colour space into
  a compositor that assumed one is a rewrite of every blend. `ColorSpace` carries primaries, white
  point and transfer function, and computes conversion matrices; the mandatory set is sRGB, Display
  P3, Rec. 2020 and their linear variants, plus the PQ and HLG transfer functions. ICC profile
  parsing is a separate later module; what this item forbids is a public model that makes one
  impossible.

  Naming the spaces is the easy half. "Supports tone mapping and dithering" is not a contract - two
  implementations can satisfy that sentence and produce visibly different images - so Profile 1 picks
  the algorithms: BRADFORD chromatic adaptation between white points, with the matrices written down;
  a stated reference white luminance and whether HDR values are absolute cd/m² or a named relative
  model; linear values permitted to go negative and above one INSIDE the pipeline, clamped only at
  output; ONE named tone-mapping operator with its parameters; the exact PQ and HLG transfer
  formulae and their inverse; and a stated gamut-mapping rule for out-of-gamut colours.

  Dithering picks ONE and it is ORDERED, with a fixed matrix and a fixed phase relative to the target
  origin. "Ordered or error-diffusion" was another unchosen alternative, and here the alternative is
  not merely vague - error diffusion carries state ACROSS pixels, which makes a tile-parallel
  renderer's output depend on tile decomposition. A backend built to render tiles independently and
  deterministically cannot use it without giving up both properties. Half-float behaviour is stated
  with the rest: NaN, infinity, subnormals and the rounding mode used when converting into
  `R16G16B16A16_FLOAT`.

- [ ] Say what an image MEANS, not only how it is stored, because a colour-managed pipeline that
  cannot tell a colour from a measurement will transform the measurement. A normal map, a roughness
  map, a coverage mask and a depth buffer are all just bytes, and running any of them through an sRGB
  decode corrupts them silently - the artefact looks like a lighting bug, which is where the days go.
  So an image carries `ImageMeaning::{Color(ColorSpace), Data, NormalMap, Depth, Mask}`, and every
  conversion path refuses to apply a transfer function to anything but `Color`.

- [ ] Provide `ImageView<'a>` and `ImageViewMut<'a>` - a borrowed slice plus a layout - whose
  constructors refuse a pitch below the minimum row bytes, a length below `required_bytes()`, a
  zero extent or an unknown format. `surface::Mapping` hands out one of these (or runs a closure
  over one) and `Mapping::addr()` is DELETED rather than left beside it: today
  `imgview.rs` turns that `u64` into a target with
  `core::slice::from_raw_parts_mut(surface.addr() as *mut u8, target_len)`, an application computing
  a length and building an aliasing mutable slice from a raw pointer.

- [ ] Provide OWNED images and offscreen render targets, not only borrowed views. An application has
  to be able to create an image and draw into it without a Surface and without DisplayService, or
  every one of these needs a special case: component caches, thumbnails, chart and map tiles, an
  image editor, shadow maps, render-to-texture, a 3D frame a 2D pass composites, a 2D texture a 3D
  pass samples, screenshots and every host test of every drawing routine. `OwnedImage` carries a
  layout and its bytes, is charged to the creating Domain, and hands out `ImageView`/`ImageViewMut`.

  And it stays exactly that: a 2D, SINGLE-SAMPLE, single-plane colour image. It is the INTEROP
  currency between the two dimensions and it is deliberately not the universal attachment type -
  multisample storage, depth and stencil aspects, cube/array/3D dimensionality and mip chains all
  belong to `render3d`'s resources in `P02M0103e`, and `ImageLayout` has no sample count to validate
  against. The interop path is therefore explicit rather than implied:

      3D MSAA / HDR attachments  --resolve + colour conversion-->  OwnedImage  -->  render2d

  Saying "a 3D attachment is an `OwnedImage`" would have made `soft3d`'s own requirement to validate
  a target's SAMPLE COUNT unsatisfiable against a type that cannot express one.

- [ ] Converge the pixel-plane types that already exist rather than adding a fifth. `pix::Target`
  carries `data/width/height/pitch/bytes_per_pixel` plus six channel shift/size fields; `pix::Image`
  carries `data/width/height/pitch`; `term::Raster` and `term::Geometry` are a third; and
  `surface::Mapping` rebuilds a `Framebuffer` with the shifts hard-coded to 16/8/0. Each becomes the
  new layout and view, or is deleted. `bootproto::Framebuffer` stays a boot-protocol type with a
  one-way adapter into the image model - a boot hand-off and a general image are different layers.

  The dependency graph, decided rather than offered as an alternative. `graphics-core` owns
  `Extent2D`, `Point2D`/`Vector2D`, `Rect`, `RoundedRect`, `Transform2D`, `Color`, `ColorSpace`,
  `PixelFormat`, `AlphaMode`, `ImageLayout`, `ImageView`/`ImageViewMut`, `OwnedImage`, `Sampler`,
  `DamageRegion`, checked pixel conversion, compositing and sampling. `pix` DEPENDS on it and stays
  an image utility library - owned `RgbaImage`, animation `Frame`/`Animation`/`Compositor`, crop,
  scale, blit - while its own `Image`, `Target` and `Rect` become aliases or are deleted. `render2d`
  and `render3d` depend on `graphics-core`; `soft2d` depends on `render2d`, `soft3d` on `render3d`;
  `scene3d` depends on `render3d` and never on `soft3d`. Nothing depends on `pix` in the other
  direction, and nothing but a backend depends on `soft2d` or `soft3d`.

  That graph settles the RUST side and leaves the WIRE side to grow a duplicate. These values cross
  the application display interface, the display-device interface and their generated crates, and
  `liber:display@1` already declares its own `enum pixel-format { b8g8r8x8 }`. So there is a
  value-only IDL package, `liber:graphics@1`, owning the wire-safe types - `extent-2d`, `offset-2d`,
  `rect`, `pixel-format`, `color-space`, `alpha-mode`, `row-origin`, `damage-region`, `image-layout`
  - which every graphics interface imports instead of redeclaring. `graphics-proto` is the generated
  wire identity; `graphics-core` re-exports those and adds what cannot cross a wire: checked
  constructors, `required_bytes()`, views over real slices, and the conversion, sampling and
  compositing routines. `liber:display@1`'s own `pixel-format` is deleted in the same change that
  introduces the package, not left beside it.

- [ ] Carry OUTPUT COLOUR metadata on the surface, because a colour-space NAME is not enough to tone
  map with - a conversion that does not know the destination's luminance is guessing at the one
  number that decides how the image looks. The surface reports its colour space plus SDR white
  luminance, minimum and maximum luminance and maximum frame-average luminance, and the HDR-to-SDR
  and HDR-to-HDR paths in the colour item above consume those rather than assuming a display.

- [ ] Add the MULTI-PLANE image model, which is the largest functional hole left in the 2D half: every
  mandatory format above is RGB or RGBA, so a video player, a camera preview and a hardware decoder
  must convert every frame to RGBA before `render2d` will draw it - a full-frame conversion per frame
  on the CPU, for the one workload where that cost is least affordable. It is a SEPARATE type rather
  than a widening of `ImageLayout`, so a single-plane image never grows fields it cannot use:
  `MultiPlaneImage` with its planes, a planar format, a YUV colour model, range and chroma siting.
  Profile 1 carries `NV12`, `I420` and `P010`, BT.601/BT.709/BT.2020 conversion, full and limited
  range and explicit chroma siting, and `render2d` draws one through the SAME shared sampling and
  conversion pipeline as everything else rather than through a private video path.

- [ ] Migrate `pix` rather than leaving it beside the model. `pix::RgbaImage` as it stands is
  `width`/`height`/`pitch`/`pixels` with no format, alpha mode, colour space or meaning, so keeping it
  unchanged leaves a back door through which an image with no colour metadata enters the new system -
  and the item above converges the pixel-plane types precisely to close doors like that. Either
  `RgbaImage` becomes `OwnedImage`, or it wraps one and is always RGBA8 with an explicit alpha mode
  and meaning. The animation `Frame` and `Compositor` go the same way.

- [ ] Break the ONE-SURFACE-PER-CONNECTION assumption. `liber:display@1` says it in its own words -
  "One display connection owns at most one surface" - with `acquire`/`present`/`release`/
  `input-focus` all at connection level and a synchronous `present`. Every desktop and mobile
  application is more than one surface: a main window, a dialog, a popup, a menu, a tooltip, a video
  surface, offscreen content. Replacing the synchronous present with a queue and leaving the object
  model at one surface would rebuild the same wall one layer up. The model is:

      DisplayConnection
          create_surface(...) -> Surface capability
      Surface
          its own present queue, its own event stream,
          its own extent, scale, transform and colour metadata

  A compositor is still a later milestone; what this item forbids is an object model a compositor
  would have to break. Foreground input focus is a property of a surface rather than of a connection,
  so P02M0091's focus capability binds to the surface that actually has it.

- [ ] Separate LOGICAL size, PHYSICAL extent and SCALE FACTOR, and put all three in the surface
  contract. `liber:display@1` today has one extent and calls it "preferred logical size", which is
  the physical one wearing the other's name - there is no scale anywhere in the interface. A phone
  surface is 400 x 800 logical at scale 3.0 and 1200 x 2400 physical, and an application that cannot
  see those as three numbers either renders at the wrong size or renders blurred. Applications lay
  out in logical units, `render2d` transforms by the scale, and the backend rasterises physical
  pixels. Surface events carry a CHANGE of any of: extent, scale factor, orientation/transform,
  output, colour space, visibility, focus, and a close request - each as its own event rather than
  one "something changed" that every client re-queries.

  The scale factor is a RATIO on the wire, `{ numerator: u32, denominator: u32 }`, not a bare `f32`:
  a fractional scale that two sides round differently produces an off-by-one extent, and that is the
  bug that shows as a one-pixel seam nobody can reproduce. With it, state which of logical and
  physical is authoritative, how logical coordinates round to pixels, that left and top round down
  while right and bottom round up so adjacent rectangles still tile, how input coordinates map back
  into logical space, what an orientation transform does to all of it, and that any scale change
  bumps the surface generation exactly as a resize does.

- [ ] Replace the current display contract with the present queue, with NO compatibility path for
  the single-surface API. Nothing is versioned before the first release and no external software
  depends on it. A presentable surface has an immutable pixel format, an explicit extent, a resize
  generation and a NEGOTIATED image count - the service advertises minimum and maximum, the client
  requests, the service answers with the actual, and no number is written into the interface.
  `present_mode` is an ENUM with `Fifo` defined now, so `Mailbox` and `Immediate` have a place to be
  added rather than a meaning to be argued about. Advertise `min_images = 2` and `max_images = 3` in
  v1 - negotiated stays negotiated, but a service free to answer "one" turns the
  double-or-triple-buffering gate into a test of nothing. Specify the image state machine as states:
  `Available -> acquire -> Acquired -> present -> PendingPresent -> released -> Available`, with
  `Stale` after a generation change and a rule that a stale image is never presented into a new
  generation. Define FIFO ordering, maximum frames in flight, backpressure, `OUT_OF_DATE` handling,
  what process death returns, and console restoration.

  Three things that state machine is missing. An `Acquired -> abandon -> Available` edge, because a
  client that acquires an image and then decides not to draw must have a way back that is not a
  present. The resize transitions in full: `Available` in an old generation becomes `Stale`;
  `Acquired` in an old generation becomes `Stale` and the client discards it rather than presenting
  it; `PendingPresent` in an old generation completes or is discarded and then becomes `Stale`. And
  the Rust shape that makes the machine unrepresentable-when-wrong rather than merely documented:
  `acquire_next` returns an owned `AcquiredImage`, drawing borrows it, and `present` CONSUMES it, so
  after presenting there is no safe path to the pixels until the queue hands them back.

  `Fifo` as written promises something the occlusion rule takes away - "every present is displayed"
  cannot hold for a background client that must also not be blocked forever. Split the promise: FIFO
  is the ordering of ACCEPTED presents, by present-call order and not acquire order; while visible,
  every accepted frame reaches logical presentation; while occluded or in the background, new
  acquires block or answer `NotVisible`, and frames already accepted still complete IN ORDER but may
  complete as discarded. That needs a per-present outcome rather than a bare completion -
  `Displayed`, `DiscardedOccluded`, `ReplacedByResize`, `DriverLost`.

- [ ] Give the frame loop a TIMING contract rather than leaving every application to sleep on the
  monotonic clock: a preferred frame deadline, the output's refresh interval, the presentation
  timestamp of a completed present, and the `PresentOutcome` above. A compositor will later supply
  frame callbacks synchronised to scanout, and the contract has to have a place for them now -
  retrofitting a callback into a design whose only pacing primitive is `sleep` means every
  application that animates is rewritten.

- [ ] Damage is a BOUNDED LIST of rectangles with an explicit whole-surface fallback, not one
  rectangle. Both sides of the driver protocol carry a single `(u32, u32, u32, u32)` today and the
  driver unions everything it receives (`union_rect` in `virtio_gpu.rs`), so a client updating two
  corners of a screen sends their bounding box - which is most of the screen.

  "A small cap" is not an ABI. Fix `MAX_DAMAGE_RECTS = 16` and state the semantics: an EMPTY list
  means nothing changed and the present is still ordered and still completes; an explicit `Full`
  variant means the whole extent, and is not spelled as one rectangle covering it; a rectangle
  outside the extent is a TYPED INVALID rather than a silent clamp; exceeding the cap is the caller's
  problem to solve by merging or sending `Full`, not the service's to solve by dropping rectangles;
  overlapping rectangles are legal and may be normalised; and coordinates are always in the image
  space of the generation the present belongs to. The backend MAY merge rectangles when merging is
  cheaper than transferring them separately, but the unconditional union of everything is exactly
  what this item removes.

  And answer the question all of that skips: damage relative to WHAT, when consecutive frames are
  drawn into different images? With images A, B, A, a client that draws two rectangles into B has
  said nothing about the rest of B. The v1 rule is the simple one: **every presented image contains a
  COMPLETE valid frame.** Damage is a HINT describing which pixels changed against the previously
  presented frame; it is not permission to leave the rest of the image undefined. From that: the
  first present of a generation is `Full`; an empty damage list asserts the submitted frame is
  pixel-identical to the previous one, which lets DisplayService release the image without copying;
  and a client wanting to redraw only part of an image needs to know what that image already holds,
  which is a `buffer_age` extension a later milestone can add without changing this rule.

  Give the bounded merging one implementation - `DamageRegion::{None, Rects { rects: [Rect; 16],
  len: u8 }, Full}` in `graphics-core` with a `push_or_full()` helper that degrades to `Full` on the
  seventeenth rectangle. Otherwise every application writes its own bounded merge and the cap becomes
  sixteen different behaviours at the cap.

- [ ] Give presentation a completion mechanism of its own rather than a system-wide timeline, and
  name its TWO events separately, because "finished with the image" means two different things to
  the two ends and collapsing them is what makes a presentation path race. PRODUCER-READY: the
  contents are complete and the image may be read and presented. CONSUMER-RELEASE: the presentation
  pipeline is done with the image and the producer may overwrite it. For a CPU renderer
  producer-ready is immediate at the `present` call; for a future imported GPU image it is
  asynchronous, which is the whole reason it is a named event now. The rule that falls out is exact:
  `acquire_next` returns only images that have been consumer-released, and never an image still in
  `PendingPresent`.

  The mechanism is a ONE-SHOT `Event`, and the rights are what make the guarantees structural instead
  of aspirational. Producer-ready is an OPTIONAL event the producer hands to `present`;
  DisplayService receives WAIT only and the producing side holds SIGNAL only, so "no forged future
  signal" is a capability the forger does not have rather than a rule someone must remember. A CPU
  renderer passes `None`, which means ready at the moment of the call. Consumer-release is the image
  returning to the queue, with an optional waitable release event. The event cannot be reset or
  signalled twice, and peer death drives it to a terminal failed state that WAKES its waiters. Beside
  that: timeout, cancellation and peer-death completion, bounded waiter accounting and no duplicate
  completion. If GPU submission, video decode or DMA later want the same primitive, THAT is when it
  is worth extracting into a general timeline.

- [ ] Replace the DisplayService <-> display-driver byte protocol with a typed LSIDL interface, and
  specify its lifecycle rather than only its calls. `display_service.rs` writes `b"PRESENT"` and four
  little-endian `u32`s into a 23-byte buffer; `virtio_gpu.rs` decodes it with `rd32_le(m, 7)` and a
  length check, with `FB`, `FBNEW`, `RESIZE`, `FLUSH`, `OK` and `ERR` beside it. Every other service
  boundary in this tree is LSIDL with typed capabilities. `liber:display-device@1` states: who owns
  the backing and for how long the capability is valid; how a backing binds to a generation; whether
  a resize changes the visible extent or delivers a new backing, and what happens to the old one;
  what present completion means; what driver death does to in-flight presents; how DisplayService
  finds a new backing after a driver restart; that the event stream is bounded; and that a backing
  from an old generation can never be presented into a new one.

- [ ] Integrate with ResourceManager and SystemGraph: surface and image bytes, surface count, present
  image count, queued presents, damage metadata and waiters, charged to the creating Domain before
  allocation - but charged ONCE. The kernel already accounts MemoryObject and IPC bytes against the
  Domain, and ResourceManager is policy above those counters, so "charge image bytes" must not be
  read as a second independent byte budget the same MemoryObject also pays into: the kernel's
  accounting charges the storage, and the graphics counters CLASSIFY that usage and enforce optional
  graphics-specific limits on top of it. Publish bounded counters and reset/fault state without
  exposing image contents. Exhaustion returns typed errors and releases partial transactions; killing
  a Domain reclaims surfaces, images, mappings and waiters even if the driver is wedged.

- [ ] Add hostile-input and lifecycle tests before anything is built on this: malformed format,
  extent and pitch descriptors, overflowed image sizes, invalid generations, duplicate acquire and
  present, completion races, driver death, truncated messages, forged imports, cross-Domain handles,
  budget exhaustion and cleanup during in-flight presentation. Fuzz every parser and every checked
  layout helper; prove that a malicious client cannot map another surface, retain foreground input
  or leave the console scanout blank.

## P02M0103b - Render2D Core Profile 1

The public, backend-neutral 2D API. This part defines the PROFILE; `P02M0103c` implements all of it.
Depends on `P02M0103a` and on no backend.

- [ ] Define `Render2D Core Profile 1` as a closed, enumerated list, and make "complete" mean this
  list. A conforming backend implements every entry; `Unsupported` is reserved for extensions added
  after Profile 1 and may never be returned for anything in it. The profile:

      geometry     paths (move/line/quad/cubic/close), non-zero and even-odd fill,
                   rect, rounded rect, circle, ellipse, arc, line, polyline, polygon
      strokes      width, butt/round/square caps, miter/bevel/round joins, miter limit,
                   dash pattern and offset
      antialiasing analytic coverage for fills, strokes and glyphs
      transforms   affine AND projective (3x3 with perspective terms)
      paints       solid, linear/radial/conic gradient, image pattern;
                   multi-stop, clamp/repeat/mirror spread, own transform, linear-light stops
      clipping     rect, rounded rect, path, nested, alpha mask, inverse
      layers       group opacity, blend mode, bounded nesting
      compositing  the 12 Porter-Duff operators plus additive Plus, and every separable
                   and non-separable blend mode below
      images       source/dest rect, arbitrary projective transform, nearest/bilinear/
                   bicubic, mipmapped minification, clamp/repeat/mirror, opacity,
                   colour-space conversion
      filters      a bounded FilterGraph, not three special cases
      text         glyph runs: outlines, grayscale masks, bitmap strikes, colour-layer
                   glyphs, embedded colour bitmaps, glyph transforms, subpixel positioning
      queries      path boolean ops, hit testing, tight and stroke bounds, length,
                   point and tangent at distance

- [ ] Make BOTH profiles machine-readable, because a profile that exists only as a list in a Markdown
  file drifts away from the backend and the conformance suite the first time someone adds a feature
  in one place. The canonical form is code - `enum Render2DFeature`, `enum Render3DFeature`, and a
  `RENDER2D_CORE_PROFILE_1` / `RENDER3D_CORE_PROFILE_1` constant listing exactly what each contains -
  and the documentation table, the capability report, the backend checklist and the conformance
  matrix are all GENERATED from it, with a profile hash so a change is visible. A gate then checks
  three things no reviewer reliably catches: every mandatory feature has at least one conformance
  test, every profile feature has a backend handler, and no test claims a feature outside the
  profile. This is what keeps "complete" true a year after it is first true, and it is cheap only if
  it exists before the two backends do.

  Each feature names its OWNER - `GraphicsCore`, `Render2D`, `Render3D`, `Scene3D` or `Backend` -
  because the "every feature has a backend handler" check is wrong for features no backend
  implements. Path boolean operations, hit testing, bounds, length and point-at-distance are
  geometry-core functions that `soft2d` never sees; demanding a backend handler for them would force
  a stub whose only purpose is to satisfy a gate. The handler check applies to `Backend`-owned
  features; the conformance-coverage check applies to all of them.

- [ ] Bound `render2d` with a `Render2DLimits` value, which the 3D side has and this side does not:
  maximum commands, resources, path verbs, path points, subpaths, clip depth, layer depth, filter
  nodes, filter radius, glyphs per run, image extent, layer pixels, prepared scratch bytes, cache
  bytes and display-list bytes. A recording API without limits is an unbounded allocation driven by
  application data, which is the shape this tree bounds everywhere else. The guaranteed minima are in
  the profile document so that "supports Profile 1" cannot mean "accepts ten path points".

- [ ] Decide what `DrawList` transport actually has to do in v1, rather than promising the largest
  version of it. "Transportable to a compositor" is currently required, and it drags in a whole
  contract - capability transfer for every referenced resource, font, image and path lifetime across
  processes, schema compatibility, a validating parser as a security surface, cache invalidation -
  for a consumer that does not exist, while a real compositor mostly wants finished surfaces rather
  than every application's vector command stream. Profile 1 requires an IMMUTABLE, VERSIONED,
  CACHEABLE list replayable in-process, which is what the caching, damage analysis and backend
  independence above actually need. Cross-process transport becomes a named `render2d-wire` extension
  designed against a real consumer - and if it is kept mandatory instead, then canonical byte order
  and alignment, resource ID plus generation, capability ownership and rights, immutable snapshot
  semantics, unknown-command and version handling, resource hashing and prepared-list invalidation
  are all part of Profile 1 and none of them is written yet.

- [ ] State what a stroke width MEANS under a transform, which decides what a scaled or projectively
  transformed stroke looks like and is currently unsaid: whether width, dash lengths and the miter
  limit are measured in user space before the transform or in device space after it, with an explicit
  `StrokeScaling::{WithTransform, NonScaling}` if both are wanted. Under a projective transform the
  two differ enough that a UI drawn with one and tested against the other is visibly wrong.

- [ ] Introduce `render2d` as a separate library from any rasteriser, and make that the boundary a
  future GPU backend replaces. An application, a UI toolkit and a game talk to `render2d`; they never
  name `soft2d`.

- [ ] Give it a `Canvas` with saved state and a recorded `DrawList`. The immediate-mode surface is
  `save`, `restore`, `set_transform`, `concat_transform`, `set_clip`, `set_opacity`, `set_blend_mode`,
  `begin_layer`, `end_layer` plus the drawing calls - but what it PRODUCES is a bounded, validated
  display list rather than pixels. That indirection is what makes the same drawing replayable by a
  CPU backend now and a GPU backend later, cacheable per component, analysable for damage,
  transportable to a compositor, and testable without any backend at all. A canvas that writes
  straight into a slice is a CPU-only API however carefully it is written.

- [ ] Specify the `DrawList` as a TRANSPORTABLE format, since the previous item promises it can be
  cached and handed to a compositor and that promise constrains its representation. It carries a
  versioned command schema, a resource table with typed handles for paths, images, fonts and filters,
  stated resource lifetime and immutability, deduplication, bounded command bytes and bounded
  nesting, a defined validation boundary, thread-safe replay and cancellation. It contains NO raw
  Rust references, because a list that can only be replayed inside the process that built it is not a
  list a compositor will ever receive.

- [ ] Paths carry OPERATIONS and QUERIES, not only construction. Union, intersection, difference,
  xor and simplify; fill and stroke hit testing; tight bounds and stroke bounds; length; point and
  tangent at a distance. A vector editor, a map, a chart, a diagram and every custom control that
  responds to a click needs these, and an application that cannot ask a path whether it contains a
  point implements its own geometry - which is the private-rasteriser failure one level up.

  Boolean operations need their edge cases decided or two backends produce different unions: how
  self-intersections are resolved, what an OPEN subpath means as an operand, how two operands with
  different fill rules combine, whether the result preserves curves or is polygonised, the tolerance
  used, the canonical ordering and winding of the output contours, what happens to degenerate and
  zero-length edges, and that the whole operation is deterministic for a given input.

- [ ] Flattening tolerance is ONE number shared by everything that consults geometry, and projective
  transforms give it a singularity to answer for. Curves are flattened ADAPTIVELY IN DEVICE SPACE
  with the tolerance stated in PHYSICAL PIXELS and a bounded maximum subdivision depth, and reaching
  that depth has a stated outcome rather than an implementation's guess. Under a projective
  transform, a control point at or near `w == 0` is on the projective horizon: define the epsilon,
  and define whether such a segment is clipped or the primitive refused - a curve whose control point
  projects to infinity has no useful flattening. The same tolerance governs fills, strokes, boolean
  operations, path length and hit testing; if a bounds query flattens differently from the
  rasteriser, an application asks where something is and draws it somewhere else.

- [ ] Antialiasing is REQUIRED with a stated contract rather than a stated algorithm: coverage in
  `[0, 255]`, composited premultiplied, deterministic clipping, bounded scratch memory, applied to
  path fills, strokes, ellipses, rounded rectangles, transformed edges and glyphs. The backend picks
  scanline coverage or another method; the public layer fixes that an edge HAS a coverage value and
  that two backends agree on the geometry producing it. Aliased one-pixel drawing stays available as
  an explicit fast path, not as the only thing there is.

- [ ] Compositing is the full set. Porter-Duff: `Clear`, `Source`, `Destination`, `SourceOver`,
  `DestinationOver`, `SourceIn`, `DestinationIn`, `SourceOut`, `DestinationOut`, `SourceAtop`,
  `DestinationAtop`, `Xor`, `Plus`. Separable blend modes: `Multiply`, `Screen`, `Overlay`, `Darken`,
  `Lighten`, `ColorDodge`, `ColorBurn`, `HardLight`, `SoftLight`, `Difference`, `Exclusion`.
  Non-separable: `Hue`, `Saturation`, `Color`, `Luminosity`. That is twelve Porter-Duff operators
  plus additive `Plus`, which is not one of them - the count and the list have to agree. The
  non-separable four are NOT deferred: they are what a theme tint, a highlight and a duotone are,
  they need the whole pixel rather than a per-channel function, and adding them later changes the
  shape of the compositing loop.

  Every mode carries its EQUATION and not only its name, because `SoftLight`, `ColorDodge` and
  `ColorBurn` have several implementations in the wild that disagree at the ends of the range, and
  the non-separable four need their luminance and saturation model and their gamut-clipping rule
  written down or they are four different pictures. State also the working space each is evaluated
  in and what happens to an out-of-range result.

- [ ] Layers and group opacity: `begin_layer(bounds, opacity, blend_mode, filter)` / `end_layer`.
  This is basic UI semantics rather than an effect - two overlapping children inside a parent at
  50 % opacity must be composited together and blended once, not blended individually against the
  background. A design without layers cannot add them later without changing every drawing call that
  has an opacity.

- [ ] Filters are a bounded `FilterGraph` rather than three named effects, because a filter chain over
  a layer changes the shape of a display list and retrofitting one is a rewrite of the model. Nodes:
  `GaussianBlur`, `DropShadow`, `ColorMatrix`, `Composite`, `Blend`, `Convolution`,
  `MorphologyDilate`, `MorphologyErode`, `DisplacementMap`, `Crop`, `Tile`. A BACKDROP filter has a
  place in the command model - background blur is what every current shell does behind a panel - and
  the graph is depth- and cost-bounded so a hostile document cannot ask for an unbounded chain.

  Every node declares its BOUNDS ALGEBRA, and a backdrop filter is why this is not bookkeeping: an
  input-bounds transform, an output-bounds expansion, a dependency-bounds function and a maximum
  kernel radius and cost. A blurred panel does not change only when its own content changes - it
  changes when the content UNDER it changes, because that is what it samples. Without dependency
  bounds an application redraws the panel, reports its rectangle as damage, and leaves a stale blur
  of yesterday's background behind it; with them, damage under the panel expands through the kernel
  and out to the panel's own bounds. Damage computation over a `DrawList` consults this algebra
  rather than assuming a node touches only what it covers.

- [ ] Text enters through `draw_glyph_run(glyph_run, paint, transform)`, where a `GlyphRun` is
  already-shaped, already-positioned glyphs. Shaping, OpenType parsing, fallback, BiDi, line breaking
  and layout are `P02M0136`. But `render2d` must render EVERYTHING that stack can produce, not only
  the easy case: outline glyphs, grayscale masks, LCD subpixel masks where a surface supports them,
  bitmap strikes, colour-layer glyphs, embedded colour bitmaps (emoji), transformed glyphs, and
  fractional subpixel positioning. A grayscale-outline-only glyph run is not a text rendering layer,
  it is the first quarter of one.

  Colour glyphs mean the specific formats and not a category: `COLR` v0 layer lists, and `COLR` v1's
  paint graph with solids, gradients, transforms, clips and composites - which is why it is specified
  HERE, since a v1 paint graph is drawn with the very paints, clips and composites this profile
  already has. Bitmap strikes and embedded colour bitmaps come with it. SVG glyphs stay out, because
  SVG parsing is deferred by name.

  LCD subpixel masks need something from the surface or they cannot be implemented at all, so the
  surface carries `SubpixelLayout::{None, RgbHorizontal, BgrHorizontal, RgbVertical, BgrVertical}`
  and the rules that follow: an unknown layout means grayscale; a rotated or non-axis-aligned
  transform means grayscale; rendering into a transparent offscreen layer means grayscale, because
  three coverage values against an unknown backdrop cannot be composited correctly later; and the
  gamma the masks are blended in is stated. Every one of those falls back rather than refusing - a
  mandatory profile entry that a surface cannot satisfy must degrade, not fail.

  This milestone proves the RASTERISATION half end to end and stops there: the fixtures are
  pre-decoded glyph outlines, a bitmap strike and a colour glyph, and what is demonstrated is that a
  positioned `GlyphRun` of each kind renders and caches. It does NOT load a font file. Requiring that
  here would create a cycle - `P02M0136` parses fonts and depends on this part for drawing, so this
  part depending on font parsing means each waits for the other, or a throwaway parser gets written
  twice and the second one inherits the first one's bugs. Real font file to shaped run to pixels is
  proven once, in `P02M0136`, against the renderer this part delivers.

- [ ] The public error type is typed and distinguishes what the caller can act on: an out-of-range
  coordinate is CLIPPED and is not an error, while an unusable target, an unsupported paint or format
  OUTSIDE the profile, a non-finite transform, an unrepresentable size and an exhausted budget are
  each their own variant. Recording into a `DrawList` validates eagerly, so an application learns at
  the call that produced the mistake rather than at replay.

- [ ] Host tests for this part run WITHOUT a backend: recording, validation, transform algebra
  including projective composition and inversion, path construction, flattening tolerance, boolean
  operations against known results, hit testing, bounds, clip stack nesting, layer nesting, state
  save/restore balance, filter-graph bounds, display-list serialisation round-trip and damage
  computation. Property and fuzz tests feed hostile transforms, unbounded paths, degenerate curves
  and deep nesting under strict allocation limits.

## P02M0103c - soft2d, the complete CPU implementation of Profile 1

The software backend. `no_std` core, no DisplayService dependency, draws into an `ImageViewMut` or an
`OwnedImage`. It implements the WHOLE profile; a command in Profile 1 that it cannot execute is a
defect, not an `Unsupported`.

- [ ] Implement the `render2d` backend interface in TWO phases, `prepare` then `render`, because
  "no steady-state allocation" and a profile containing layers, clip masks, blur, backdrop filters,
  path flattening, glyph caches and image pyramids cannot both be true without saying WHEN the
  scratch is worked out:

      let prepared = backend.prepare(&draw_list, target_desc, limits)?;
      backend.render(&prepared, target)?;          // allocates nothing

  `prepare` validates the resource table, flattens and caches paths, computes tile bins, resolves
  filter and dependency bounds, builds image pyramids, reserves layer and filter scratch, and returns
  either the exact memory requirement or a typed refusal. `render` replays. A frame that repeats with
  the same list and the same target then genuinely allocates nothing, and a frame that cannot fit
  says so before it starts drawing instead of failing halfway through a filter chain. It is one
  backend among future others and its public surface is the backend trait, not an application-facing
  drawing API. Nothing outside this part names `soft2d`.

- [ ] Implement a coverage antialiasing rasteriser for filled paths under both fill rules, with
  bounded scratch storage, no allocation during a draw, and deterministic output for a given input.
  This is the core of the whole 2D stack: shapes, strokes, rounded rectangles, ellipses and glyph
  masks are all paths through it.

- [ ] Implement stroking by converting a stroke to a fill - caps, joins, miter limit and dashing -
  rather than by a second rasterisation path with its own rules. Keep the aliased integer line as an
  explicit fast path with the rule it already had: integer Bresenham with BOTH endpoints included,
  ties at `error == 0` broken toward the smaller minor coordinate, and clipping applied before
  rasterising so a clipped line covers the same pixels as the visible part of the unclipped one.

- [ ] Implement clipping as a coverage mask rather than a rectangle test, so rounded, path, nested
  and inverse clips cost the same machinery as rectangular ones and masks intersect. The
  axis-aligned rectangle case keeps a fast path.

- [ ] Implement every paint: solid, linear, radial and CONIC gradients with multi-stop interpolation
  in linear light, `Clamp`/`Repeat`/`Mirror` spread, per-paint transform, and image patterns. Conic
  is in the profile, so it is implemented here rather than typed and refused.

- [ ] Implement image drawing at quality, not only at correctness: nearest, bilinear and bicubic
  sampling; mipmapped or pyramid-based minification so a large downscale does not alias; and
  anisotropic sampling or a bounded multi-tap approximation for projective transforms. A general
  image renderer that only has bilinear produces shimmering thumbnails, which is the most visible
  defect a 2D library can ship with.

- [ ] Implement layers, group opacity, every Porter-Duff operator, every separable and non-separable
  blend mode, and the whole `FilterGraph` over offscreen layer targets from `P02M0103a`. Layer and
  filter intermediates use the canonical premultiplied linear `R16G16B16A16_FLOAT` format, and the
  final conversion to the surface format applies tone mapping and dithering where the target is
  narrower.

- [ ] Implement glyph rendering for every glyph kind the profile lists, with a bounded glyph cache
  keyed by face, size, transform and subpixel phase, and a mask cache for repeated shapes.

- [ ] ONE implementation of pixel conversion, compositing and sampling, living in `graphics-core` and
  shared by `pix`, `soft2d`, `soft3d` and DisplayService's own copy and scale path; none carries a
  private second copy. This is already real: `pix::blend_over` is an integer straight-alpha
  source-over on sRGB-encoded bytes while a correct compositor needs linear light, so the shared
  primitive takes its WORKING SPACE as part of the contract and each caller states which it uses.
  Fix the stage ORDER once: decode transfer function -> convert straight to premultiplied -> sample
  and filter -> blend in the stated working space -> convert back to the target's alpha mode ->
  encode transfer function -> quantise with dithering. Filtering premultiplies BEFORE interpolating -
  interpolating straight alpha pulls the colour of fully transparent texels into the result and rings
  dark halos around transparent edges. And "shared" means CALLED.

- [ ] Rectangles and gradients are exact rather than approximately agreed. `Rect` is half-open, a
  fill covers every sample point inside it, a one-pixel aliased `stroke_rect` lies INSIDE the
  rectangle rather than straddling its boundary, and a zero-width or zero-height rectangle draws
  nothing and is not an error.

- [ ] Damage returned from a draw is CONSERVATIVE, not exact. Exact damage would mean comparing old
  and new pixels - a source-over with alpha zero changes nothing while covering a rectangle - and
  that cost defeats the purpose. Every draw returns the smallest inexpensive conservative raster
  bound: it contains every pixel that may have changed, is clipped to the target and clip stack, and
  is empty when no sample was reached.

- [ ] Make it a REAL software backend, not a single-threaded reference: tile-based rendering with
  per-tile command binning, a bounded worker pool, SIMD fast paths, cancellation when a surface is
  closed or resized mid-frame, and caches for paths, masks, glyphs and filter intermediates. A
  desktop fallback that renders a 4K frame on one core is a fallback nobody can use.

  With one rule that keeps it honest: there is a DETERMINISTIC SCALAR REFERENCE path, and every
  parallel or SIMD path is differential-tested against it. The bit-exact/tolerance split at the top
  of this file says which parts must match exactly - coverage and geometry classification - and which
  match within tolerance.

- [ ] Host tests cover path filling under both rules, coverage values along known edges, stroke caps
  and joins, dashing, clip nesting, rounded and inverse clips, layer opacity against manually
  composited reference values, every Porter-Duff operator and every blend mode against its algebraic
  definition, projectively transformed image drawing, all three filters and minification, every
  spread mode, colour-space conversion and tone mapping, dithering, each filter node, glyph masks of
  every kind, returned damage bounds, guarded canaries around the target, and scalar-versus-parallel
  agreement. Property and fuzz tests feed hostile coordinates, extents, pitches, transforms,
  degenerate curves and deep filter graphs and prove no panic and no out-of-bounds write.

against `render2d` until it passes.

- [ ] Build a 2D CONFORMANCE suite as a governed PIE named **2D Conformance SW**, canonical artifact
  `test2d-conformance-sw.lsexe`, so it is named and auditable on the same terms as the 3D one rather

  matrix. It walks the profile entry by entry - driven by the machine-readable registry, so a feature

  pass condition per scene rather than one screenshot. It runs on all three

  curves, every cap/join/dash, projective transforms, all four paint kinds with every spread mode,
  rect/rounded/path/nested/inverse clipping, layer nesting and group opacity, every Porter-Duff
  operator, every separable and non-separable blend mode, nearest/bilinear/bicubic and minification,

- [ ] Add one governed PIE named **2D Test SW**, canonical artifact `test2d-sw.lsexe`, only

  and neither substitutes for the other.

- [ ] The scene demonstrates the platform an application would actually use: filled and stroked
  Bezier paths under both fill rules, antialiased edges at a shallow angle, a projectively
  transformed image, a multi-stop conic gradient, a rounded-rectangle clip with content scrolling
  under it, a nested and an inverse clip, a group-opacity layer containing two overlapping children,
  several non-`SourceOver` blend modes including a non-separable one, a backdrop-blurred panel, and a
  line of text including a colour glyph.

- [ ] It runs in PHASES, because "an animated background" and "two non-contiguous damage rectangles
  that reach the driver as two" contradict each other - a background that changes every frame changes
  every pixel, and its only honest damage is `Full`:

      1. full        everything drawn, damage = Full
      2. partial     background held still, objects move, damage = old bounds + new bounds
      3. multi-rect  exactly two distant regions change; the driver stand-in sees TWO rectangles
                     before any backend merging
      4. full-again  background parameters change, damage = Full
      5. resize      new generation, and its first frame is Full by the rule above
      6. scale       the scale factor changes with the logical size held constant; layout is
                     unchanged and every edge is resolved at the new physical resolution

- [ ] Prove the multi-surface model, since `P02M0103a` introduced it and an untested object model is

- [ ] It passes only when: the conformance suite passes on all three architectures with no profile
  entry unsupported; clean exit AND crash both restore the text console; a resize never presents a
  stale image; phase 3's two rectangles travel the whole path from application to driver as two; a

  proves ET_DYN, provider identity and order, the exact grants and no statically duplicated drawing
  code; there is no steady-state allocation once the queue and resources exist; and a measured
  steady-state frame budget at 640x480 and at a HiDPI scale is recorded in `docs/PERF.md`.

## P02M0103e - render-math and Render3D Core Profile 1

The public, backend-neutral 3D API - resources, pipelines, passes, shaders and command lists. This is
the layer whose absence the seventh pass was written to correct. Depends on `P02M0103a`.

- [ ] `render-math` is a CONTRACT and not a type list, and this file picks the values rather than
  requiring that someone pick them - "state the handedness" is not normative, a handedness is:
  angles in RADIANS everywhere, COLUMN-MAJOR storage, `M * v` as the transform, RIGHT-HANDED world
  and view space, clip-space depth in `[0, 1]`, counter-clockwise front faces. Constructors are named
  for what they encode - `perspective_rh_zo`, `orthographic_rh_zo` - so a caller cannot pick the
  wrong convention silently. Quaternions state their normalisation policy: constructors normalise,
  operations preserve unit length, and a zero-length quaternion is an error rather than a NaN
  generator. Inversion of a singular matrix returns a typed error and never a matrix of infinities,
  and every entry point states what it does with NaN and infinite inputs.

  Four of those choices only become unambiguous together, and leaving the last one out inverts what
  gets culled: `+Y` is up in world and view space, the camera looks along `-Z`, NDC `+1` is the TOP
  of the image, the surface row origin is `TopLeft`, and the viewport maps
  `y_window = (1 - (y_ndc * 0.5 + 0.5)) * height`. Front-face culling is evaluated BEFORE that Y
  inversion. A Y flip reverses apparent winding, so an implementation that culls after it culls the
  opposite faces while satisfying every other sentence in this file.

- [ ] Define `Render3D Core Profile 1` as a closed, enumerated list on the same terms as the 2D one:
  a conforming backend implements every entry, and `Unsupported` is reserved for post-profile
  extensions. The profile:

      resources    buffers, 2D textures, cube maps, 2D arrays, 3D textures, samplers,
                   mipmaps, render targets
      geometry     u16/u32 indices, multiple vertex streams, configurable attributes,
                   triangle list/strip/fan, line list/strip, point list, primitive
                   restart, indexed and non-indexed, instancing, base vertex,
                   base instance
      pipeline     programmable vertex and fragment stages, vertex layout, primitive
                   topology, rasteriser state, depth/stencil state, blend state per
                   attachment, colour write masks, viewport and scissor
      passes       render passes with load (clear/load/discard) and store (store/discard)
                   per attachment, multiple colour attachments, depth/stencil attachment,
                   MSAA resolve, offscreen render targets, render-to-texture
      depth        Depth16, Depth24, Depth32F, Depth24Stencil8, Depth32FStencil8;
                   all compare ops, depth write, depth bias; stencil compare, read/write
                   masks, fail/depth-fail/pass ops, separate front and back state
      msaa         1x, 2x, 4x; sample masks; alpha-to-coverage; resolve
      sampling     nearest/linear min and mag, nearest/linear mip, trilinear,
                   clamp/repeat/mirror/border, LOD bias and min/max LOD, depth-compare
                   sampling, anisotropic filtering to max_anisotropy 8
      formats      R8, RG8, RGBA8, RGB10A2, RGBA16F, RGBA32F, R32_UINT, the depth formats
                   (encoding is ColorSpace's, never a second sRGB storage format)
      readback     colour, depth and object-ID attachment readback

- [ ] Introduce a PROGRAMMABLE shader model, `render-shader`, and treat it as the largest single item
  in this part - fixed-function Lambert and Blinn-Phong cannot be a complete renderer, because a
  procedural material, a picking pass, a scientific visualisation, a postprocess and every effect an
  application invents are all "a different fragment function". The model is a VALIDATED PORTABLE IR:
  vertex and fragment stages, typed uniforms, textures and samplers, varyings with `smooth`,
  `noperspective` and `flat` interpolation, bounded loops, no recursion, and checked memory access.
  `soft3d` interprets it first; a JIT or a translation to a GPU shader representation comes later
  without changing the API.

  Explicitly NOT Rust closures. A closure is the obvious shortcut and it is a dead end: a future GPU
  backend cannot take one, so the day the GPU backend arrives every shader in every application is
  rewritten. Ship a programmatic IR BUILDER so this milestone does not also have to write a GLSL or
  WGSL front end - a text shading language is a later, separate, optional piece.

  "A validated portable IR" is a description, and Profile 1 needs the enumeration. TYPES: `bool`,
  `i32`, `u32`, `f32`, their 2/3/4-component vectors, `mat2`/`mat3`/`mat4`, and arrays with a
  compile-time length. OPERATIONS: arithmetic, comparison, logical and bitwise, conversions, vector
  and matrix products, `dot`, `cross`, `normalize`, `min`, `max`, `clamp`, `mix`, `exp`, `log`,
  `pow` and the trigonometric set. CONTROL FLOW: `if`, `switch`, bounded `for` and `while`, `break`,
  `continue`, `return`, `discard`. VERTEX BUILT-INS: vertex and instance index, base vertex and base
  instance, the position output, point size. FRAGMENT BUILT-INS: fragment coordinate, front-facing,
  sample index, sample mask, and depth output. OUTPUTS: several colour attachments, an INTEGER
  attachment for object IDs, depth, and the sample mask.

  Two additions the profile's own requirements force. Interpolation needs `centroid` and `sample`
  beside `smooth`, `noperspective` and `flat` - without them MSAA shades at sample points that can
  lie outside the primitive and edges go wrong in a way that looks like a rasteriser bug. And
  DERIVATIVES - `dFdx`, `dFdy`, `fwidth` - are not optional here: the profile mandates implicit mip
  level selection and anisotropic footprints, and both are computed from derivatives. State how they
  are evaluated for a partially covered quad.

  Resource binding gets a real model rather than one `bind_resources` call: a `BindingLayout`
  declaring binding index, resource type, array length and stage visibility; `BindGroup`s built
  against a layout; and dynamic offsets. Shader IR and pipeline state otherwise have no shared
  contract about what binding 3 means.

- [ ] Resolve the bit-exact seam a programmable vertex stage creates, because the fifth pass's
  guarantee and the seventh pass's shaders are in direct conflict and the conflict is invisible until
  two architectures disagree. Clipping topology and geometry classification are BIT-EXACT; a shader
  computing the clip-space position in floating point is TOLERANCE-BASED; so a vertex landing at
  `z = +/-1e-8` may be classified differently on two machines while both conform. The seam is
  explicit: the position output has STRICT floating-point semantics of its own - a fixed operand
  order for the projection, no FMA contraction, canonical NaN, stated rounding - and is then
  QUANTISED into a canonical clip representation. Classification, clipping and rasterisation consume
  the quantised value and are bit-exact from there down. Every other varying stays tolerance-based,
  and the conformance suite compares them accordingly.

- [ ] Provide the command model: `CommandList`, `RenderPass`, `RenderTargetSet`, `GraphicsPipeline`,
  `ShaderProgram`, `VertexLayout`, `Buffer`, `Texture`, `Sampler`, `PipelineState`, with
  `begin_render_pass`, `end_render_pass`, `bind_pipeline`, `bind_vertex_buffer`, `bind_index_buffer`,
  `bind_resources`, `set_viewport`, `set_scissor`, `draw`, `draw_indexed`, `draw_instanced`. This is
  a USERSPACE rendering model and is not the OS-level adapter/device/queue vocabulary that stays
  deferred - the difference is that this one has two planned implementations and that one has none.

- [ ] Complete the RESOURCE model, because naming resource kinds in a profile and naming `Buffer` and
  `Texture` in a command list does not yet say how one is created or what part of it a pass writes.
  Descriptors: `BufferDesc` with size, usage and host visibility; `TextureDesc` with dimension,
  extent, mip levels, array layers, sample count, format and usage; `TextureViewDesc` with aspect,
  base mip and count, base layer and count, and view dimension; and `RenderTargetView` /
  `DepthStencilView` built from views rather than from whole textures - a shadow pass renders to one
  cube face and one mip, and a model without subresource views cannot say that. Operations: create
  and destroy, map and unmap, write buffer, write texture, buffer-to-buffer, texture-to-texture and
  buffer-to-texture copies, blit, resolve, generate mipmaps, clear and readback.

  With the HAZARDS stated rather than left to the backend to discover: sampling a subresource while
  rendering to it is refused or defined; attachment aliasing within a pass is refused or defined;
  what is visible from one pass to the next; what `discard` leaves behind and that reading it
  afterwards is a typed error rather than whatever the tile buffer held; and the lifetime of a view
  against the resource it names. A CPU backend gets these right by accident and a GPU backend does
  not, which is exactly why they belong in the API and not in `soft3d`.

- [ ] Enumerate the BLEND STATE, since "blend state per attachment" cannot be conformance-tested
  without knowing what a state may contain. Factors: `Zero`, `One`, `SrcColor`, `OneMinusSrcColor`,
  `DstColor`, `OneMinusDstColor`, `SrcAlpha`, `OneMinusSrcAlpha`, `DstAlpha`, `OneMinusDstAlpha`,
  `ConstantColor`, `OneMinusConstantColor`, `ConstantAlpha`, `OneMinusConstantAlpha`,
  `SrcAlphaSaturate`. Operations: `Add`, `Subtract`, `ReverseSubtract`, `Min`, `Max`. Separate colour
  and alpha state, a blend constant, per-attachment enable and a colour write mask.

- [ ] Fix the MSAA geometry rather than the sample count alone: the exact 2x and 4x sample positions,
  whether shading runs once per covered pixel or once per sample, the centroid location rule, the
  order in which the sample mask and alpha-to-coverage are applied, the alpha-to-coverage mapping for
  each count, and that resolve is an arithmetic average in linear premultiplied space. "4x MSAA"
  without sample positions is two different coverage results that both satisfy the words.

- [ ] Give each depth and stencil format its own semantics, because the earlier bit-exact rule was
  written when there was one `u32` depth buffer and there are now five formats. For each: the mapping
  from clip depth, the rounding, the packing, the clear representation, and the behaviour of every
  compare operation. `Depth16` and `Depth24` stay on the BIT-EXACT side. `Depth32F` cannot simply
  join them - its interpolated values come from floating-point arithmetic whose last bit moves with
  operand order - so it either gets strict semantics of its own (fixed order, no FMA contraction,
  stated rounding, canonical NaN and infinity handling) or its stored value is quantised through one
  named rule before comparison. Choose one and say which. Stencil states its bit width, packing and
  the full operation set; depth bias states its units for each format.

- [ ] Bound the device rather than the frame: `Render3DLimits` states maximum attachments, texture
  extents and bytes, samples, vertex streams, attributes, uniform bytes, bound resources, draws and
  command bytes per list, shader instruction and loop bounds. Every request is checked against the
  implementation's hard maximum, what the raster arithmetic can represent, and the Domain's budget -
  but a failed check REFUSES or NEGOTIATES and never silently clamps: a caller given a quiet
  reduction finds out three frames later in a failure that names neither number. Over the hard
  maximum is `LimitExceeded`; over the Domain budget is `OutOfMemory`; and where less is granted than
  asked, construction returns the ACTUAL limits alongside the device.

- [ ] Typed errors throughout: `InvalidMesh`, `InvalidTransform`, `UnsupportedFormat`,
  `TargetMismatch`, `NonFinite`, `LimitExceeded`, `OutOfMemory`, `InvalidTexture`,
  `InvalidRenderState`, `InvalidShader`, `IncompatiblePipeline` - and `Unsupported`, which within
  Profile 1 is unreachable by construction and exists for extensions beyond it.

- [ ] 2D and 3D interoperate through the shared types rather than through a bridge: both use
  `graphics-core`'s `ImageLayout`, `ColorSpace`, `AlphaMode`, `Sampler` and `OwnedImage`. A 3D pass
  renders into an `OwnedImage` that `render2d` draws as an image - a HUD over a game, a viewport in
  an editor, a 3D preview in a document - and a 2D pass renders into an `OwnedImage` that `render3d`
  uses as a texture. Neither direction needs a conversion step, and that is the point of one image
  model.

- [ ] Host tests for this part run WITHOUT a backend: vector, matrix and quaternion identities,
  camera and frustum transforms, pipeline and vertex-layout validation, render-pass attachment
  compatibility, shader IR validation including rejection of unbounded loops, recursion and
  out-of-range access, command-list bounds, and every typed refusal. Property and fuzz tests feed
  hostile shader IR, malformed vertex layouts and incompatible attachment sets.

## P02M0103f - scene3d, the retained scene layer

The convenience layer applications use when they do not want to build command lists themselves. It
generates `render3d` command lists and contains NO backend-specific path. Depends on `P02M0103e`.

- [ ] `scene3d` IMPLEMENTS - not "admits" - hierarchy with parent/child local and world transforms,
  cameras, lights, mesh instances, materials, render queues, bounding spheres and axis-aligned boxes,
  frustum culling, LOD selection, instancing, visibility masks, skinning, morph targets, an animation
  pose input, offscreen targets and a render-pass graph. The previous draft required these only to be
  possible to add later, which is the same deferral the seventh pass removed from `soft3d`: a scene
  layer that cannot express a hierarchy is one every application replaces.

- [ ] Give `scene3d` its own closed profile, `Scene3D Core Profile 1`, in the same machine-readable
  registry as the other two. `Render3D Core Profile 1` is a low-level pass and pipeline API and does
  not contain hierarchy, animation clips, PBR materials, lights, shadows, LOD, sorted transparency,
  picking or postprocessing - yet those are exactly what "a complete 3D library" means to an
  application, and with them outside every registry they are the one part free to drift away from
  its conformance suite and its documentation. A third `enum Scene3DFeature` and its constant closes
  that gap on the same terms: no `Unsupported` inside the profile, a test per feature, and the
  guaranteed minima in `SCENE3D_PROFILE_1.md`.

- [ ] Ship a STANDARD MATERIAL library over the programmable pipeline, so an ordinary application
  does not write shader IR to draw an ordinary object: `Unlit`, `VertexColor`, `Lambert`,
  `BlinnPhong` and `PbrMetallicRoughness`. The PBR material carries base-colour, metallic-roughness,
  normal, occlusion and emissive maps, `Opaque`/`Mask`/`Blend` alpha modes and a double-sided flag -
  which is the glTF data model, chosen deliberately as the reality check, because a material model
  that cannot consume the assets the world already has is a material model for one demo.

  "PBR metallic-roughness" is a family of implementations that disagree, so Profile 1 picks: GGX /
  Trowbridge-Reitz normal distribution, Smith visibility, Schlick Fresnel, the roughness remapping
  and its minimum, the metallic workflow's base-colour interpretation, how occlusion is applied,
  the units of emissive, tangent-space handedness and the normal-map convention, how a double-sided
  surface flips its normal, the alpha-mask threshold, the environment prefiltering and BRDF LUT, and
  the colour space of EVERY map - base colour and emissive are `Color`, metallic-roughness, normal
  and occlusion are `Data` and are never transfer-decoded. Without those, a conformance scene has no
  single expected answer and the material is only a name.

  Shadows likewise: the shadow-map format, the constant and slope-scaled bias, the PCF kernel, the
  cube-face orientation for point lights, and whether directional cascades are inside Profile 1 or
  outside it. Postprocessing likewise: the tone-map operator (the same one `P02M0103a` fixes), the
  bloom threshold and kernel, and the fog equation.

  `BlinnPhong` keeps the exact equation earlier passes fixed, now as a LIBRARY material rather than
  as the renderer's only path, so its tests keep their single expected answer:

      base    = material.base * vertex_colour * texture_rgb
      N = normalize(normal),  L = normalize(light_pos - frag_pos)
      V = normalize(eye_pos - frag_pos),  H = normalize(L + V)
      diffuse  = max(dot(N, L), 0)
      specular = if diffuse > 0 { pow(max(dot(N, H), 0), shininess) } else { 0 }
      atten    = 1 / max(kc + kl*d + kq*d*d, EPS)
      out      = clamp(ambient*base + atten*(diffuse*base + specular*spec_colour), 0, 1)

  with `EPS` and the `shininess` range named, specular carrying its OWN colour rather than
  multiplying the base, lighting never changing alpha, and the clamp applied before the
  transfer-function conversion.

- [ ] Lighting has no fixed count. Multiple directional, point and spot lights, an ambient term, an
  environment map and image-based lighting, with shadow maps: directional, spot, and cube shadows for
  point lights. "One directional and one point light" was a demo's requirement written as a design.

  No fixed count is NOT no limit, and this layer needs its own `Scene3DLimits` for the same reason
  `render3d` does - a scene is built from application data, and unbounded application data reaching a
  renderer is the shape every other part of this tree bounds: maximum nodes, hierarchy depth, mesh
  instances, lights per type, visible draws, skeleton joints, morph targets, animation tracks,
  passes, shadow maps and transparent items, each with a stated refusal on overflow. With the
  structural checks beside them: CYCLE DETECTION in the hierarchy and in the pass graph, dirty-flag
  propagation and update ordering, dynamic bounds recomputed for skinned and morphed geometry rather
  than trusting the rest pose, and a shadow-resource budget.

- [ ] Animation is a SYSTEM, not an input. `scene3d` currently takes a pose and leaves producing it
  to the caller, which means every game and every editor writes the same clip player - so the clip
  data model and its playback belong here: `AnimationClip` with channels, translation/rotation/scale
  tracks and morph-weight tracks; step, linear and cubic interpolation; loop, clamp and ping-pong;
  cross-fade and blending between several clips; skeleton pose evaluation; and a stated root-motion
  policy. Asset importers stay deferred - reading a glTF file is not this milestone - but the runtime
  that plays a clip is what makes the scene layer usable without one.

- [ ] Transparency is the library's job, not the caller's. An opaque queue, an alpha-mask queue and a
  transparent queue; stable back-to-front sorting within the transparent queue; per-draw blend state
  and colour write masks. Weighted-blended OIT is an extension beyond Profile 1. What is not
  acceptable is telling the application to sort its own geometry and calling that a design decision.

- [ ] HDR and postprocessing are part of the scene layer: a linear HDR render target, tone mapping,
  the output transfer conversion, full-screen postprocess passes and fog, with bloom as a built-in
  effect. The general pass and shader model means further effects need no architectural change.

- [ ] Picking and readback, because a desktop 3D application, an editor and a CAD viewport all need
  them: an object-ID attachment, a selection pass, and depth and pixel readback. The software backend
  may answer synchronously; a later GPU backend makes the same API asynchronous without changing its
  shape.

- [ ] Host tests: hierarchy transform composition, culling against known frusta, LOD thresholds,
  queue ordering and transparent sorting stability, skinning and morph evaluation against hand-computed
  poses, shadow-map matrix derivation, and that every scene feature emits only `render3d` commands.

## P02M0103g - soft3d, the complete CPU implementation of Profile 1

The software 3D backend. It implements the WHOLE of `Render3D Core Profile 1`; a profile feature it
cannot execute is a defect, not an `Unsupported`.

- [ ] Split `soft3d` into PREPARE and EXECUTE the way `soft2d` is split, and for the same reason:
  resource upload, shader validation and lowering, pipeline creation, command-list validation and
  tile/bin scratch reservation all happen BEFORE execution, and `execute(command_list)` then allocates
  nothing in steady state. Without that boundary, programmable shaders, pipeline creation, mipmap
  generation and the pass graph each become a place a frame can start allocating, and the
  no-steady-state-allocation requirement in this milestone becomes untestable on the 3D side while
  being enforced on the 2D one.

- [ ] Implement the rasteriser with these conventions fixed: sample points at pixel centres
  `(x + 0.5, y + 0.5)`; fixed-point edge equations rather than floating-point comparisons, so
  coverage is exact and shared edges cannot double-fill or leave a seam; the top-left fill rule;
  deterministic back-face culling by winding; perspective-correct interpolation. Degenerate,
  non-finite and off-screen primitives are skipped deterministically. A SUB-PIXEL triangle is NOT
  skipped: it either covers a sample point or it does not, and dropping it by size makes small
  geometry flicker as the camera moves.

  The numbers, because "fixed-point" without them is half a contract and identical coverage on three
  architectures is what the other half decides: `SUBPIXEL_BITS = 8`, `MAX_RASTER_EXTENT = 16_384`,
  float viewport coordinates quantised by round-half-away-from-zero, edge equations in checked `i64`.
  Those two constants make the third checkable: quantised coordinates fit in 22 bits signed, an edge
  product is two of them multiplied, and the difference of two such products is provably inside
  `i64` - write that proof down beside the constants. All of this is on the BIT-EXACT side of the
  split at the top of this file.

- [ ] Implement the clipper, interpolating ALL varyings and not just position. Every vertex a clip
  plane creates is built with a single intersection parameter applied identically to position,
  normal, UV, colour and every other varying - clip position alone and the geometry is right while
  texture and shading jump at the near plane, a bug that looks like a texturing bug.

  The six planes for the chosen right-handed `[0, 1]` clip space, each as the inequality a vertex
  satisfies to be inside:

      left    x + w >= 0        bottom  y + w >= 0        near    z     >= 0
      right   w - x >= 0        top     w - y >= 0        far     w - z >= 0

  With the degenerate cases decided: a vertex with `w == 0` is not projectable and its primitive is
  REFUSED; a zero intersection denominator produces no new vertex and the result follows from the
  inside/outside classification; a non-finite coordinate fails the primitive with `NonFinite`. The
  bound is a number, not a promise of one: Sutherland-Hodgman against a convex volume adds at most
  one vertex per half-space, so `MAX_CLIPPED_VERTICES = 3 + 6 = 9` and
  `MAX_TRIANGLES_AFTER_CLIP = 9 - 2 = 7` under fan triangulation. Those live in the clipper and are
  proven, not configured.

- [ ] Implement the shader interpreter for `render-shader` IR - both stages, all interpolation
  qualifiers, typed uniform and resource binding, bounded loops and checked access - with a
  deterministic scalar path. Every shading result is on the TOLERANCE side of the split.

- [ ] Implement every pass and attachment feature in the profile: multiple colour attachments,
  load/clear/discard and store/discard per attachment, offscreen targets and render-to-texture, all
  five depth/stencil formats with the full compare, write, mask and stencil-operation set, depth
  bias, and MSAA at 1x/2x/4x with sample masks, alpha-to-coverage and resolve.

- [ ] Implement the full sampler and texture set: 2D, cube, array and 3D textures; mipmap generation
  and selection; nearest and linear min/mag and mip filtering; trilinear; clamp, repeat, mirror and
  border addressing; LOD bias and min/max LOD; depth-compare sampling for shadow maps; and
  anisotropic filtering to `max_anisotropy` 8 by a stated number of taps along the major axis, with
  the LOD and footprint derived from the shader derivatives. Cube-map face selection and orientation,
  seam handling across faces, border colours, the depth-compare return value, 3D filtering, and the
  filter used when generating mipmaps - including that generation happens in LINEAR light and that a
  `Data` or `NormalMap` image is never transfer-decoded on the way - are all stated. Texel centres are at
  `(i + 0.5) / extent`, and `repeat` is defined for NEGATIVE and large coordinates by Euclidean
  remainder so `-0.25` and `0.75` sample the same texel rather than differing by the sign convention
  of the language's `%`. sRGB texels are DECODED to linear before filtering and premultiplied before
  interpolation; blending is evaluated in LINEAR LIGHT.

- [ ] Implement the geometry set: all six topologies - triangle list, strip and fan, line list and
  strip, point list - with primitive restart, u16 and u32 indices, multiple vertex streams,
  configurable attributes, instancing with base vertex and base instance, and the vertex-side work
  that skinning and morph targets require.

  The clipping and raster rules above are written for TRIANGLES, and the other two kinds need their
  own or they are undefined: the provoking vertex for `flat` interpolation, line rasterisation rules
  and width, point size and its rasterisation, how lines and points clip against the same six planes,
  and that back-face culling applies to triangles ONLY. A profile that mandates six topologies and
  specifies one is a profile with five gaps.

- [ ] Make it a REAL software renderer, not a reference implementation: tile and bin rasterisation,
  a bounded worker pool, SIMD interpolation and shading, a texture cache, mipmap selection and
  hierarchical depth. With the same honesty rule as `soft2d`: a DETERMINISTIC SCALAR REFERENCE path
  exists, every parallel and SIMD path is differential-tested against it, and the bit-exact half of
  the split must match exactly while the shading half matches within tolerance.

- [ ] Validate indices, attachment compatibility and finite transforms at ingestion; account peak
  memory to the process Domain; reuse frame allocations; allocate nothing per primitive during
  traversal and clipping. The renderer VALIDATES its borrowed colour target - format, extent, sample
  count and layout - and uses checked allocation only for what it owns: depth/stencil, scratch, tile
  and bin storage. It does not allocate a target it does not own.

- [ ] Frame scheduling lives ABOVE the renderer and not inside it. `soft3d` knows nothing of
  DisplayService: it renders into targets and returns. Acquire, present, pacing, completion, resize,
  `OUT_OF_DATE` and focus behaviour belong to the application or to a graphics-app helper shared with
  the 2D side - putting the present queue inside `soft3d` is what would make the later GPU renderer
  reimplement a window system to draw a triangle. This item is the INTEGRATION gate for that helper:
  render into the acquired image, wait for CONSUMER-RELEASE before reusing it, keep at most the
  negotiated frames in flight, pace against the timing contract rather than busy-spinning, reacquire
  surface images OUTSIDE the renderer on resize while the renderer transactionally recreates what it
  owns, keep or cleanly release the old scene on allocation failure, and block or throttle in the
  background while consuming no raw input.

- [ ] Host tests cover clipping against every plane, winding and culling, perspective interpolation,
  depth ordering and every compare op, stencil operations, shared-edge fill, sub-pixel coverage,
  every topology, instancing, every addressing and filtering mode, mip selection, MSAA coverage and
  resolve, alpha-to-coverage, shader IR execution including every interpolation qualifier, blending
  for every state, readback, non-finite and degenerate input, and guarded canaries around every
  attachment. Property and fuzz tests feed hostile meshes, indices, transforms, extents, UVs,
  viewport rectangles and shader IR under strict allocation limits.

  `test3d-conformance-sw.lsexe`, that walks the profile entry by entry with a scene per feature and a

  rasterisation and depth; stencil operations; MSAA at each supported count; every primitive
  topology; a programmable vertex and fragment shader; mipmaps, trilinear and anisotropic filtering;

  postprocessing; HDR and tone mapping; sorted transparency; object-ID picking; and 2D/3D interop.

- [ ] Each scene is checked by a property that can fail for one reason rather than by a single golden

  forming a quad: across the shared edge there must be neither a gap nor a doubly-covered pixel,
