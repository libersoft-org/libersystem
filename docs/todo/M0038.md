# M0038 - Security hardening: app sandbox, permission manifests, PermissionManager

Status: COMPLETE (2026-06-27).

Phase 0 already forbade ambient authority - a component gets only the capabilities it is handed.
This added the **policy** layer above that mechanism: typed manifests, a service that grants and
audits against them, a strict sandbox, and a written threat model.

*Condensed 2026-08-08.*

The manifest is **a typed object in the IDL, not a text or JSON file**: an enum of capabilities, a
`manifest` record of component plus grants, and an `audit-entry` of component, capability and
whether it was granted. A parsed configuration file would put the authority decision behind a parser;
a generated type puts it in the interface.

PermissionManager grants a launching component exactly its manifest's capabilities and records every
grant and refusal. A launched component starts with those and nothing else, and that is verified
rather than asserted. The threat model - malicious application, compromised driver - is written down
in `docs/THREAT_MODEL.md` with the bounds that are actually enforced.

Testing is syscall fuzzing plus property tests of the capability rules: a handle grants no operation
its rights do not name.

## One ungated syscall, found later

**`SYS_SYSTEM_POWER` was ungated - any ring-3 process could halt the machine.** It now takes a handle
and requires MANAGE on the **root** Domain. That key is chosen rather than arbitrary: whoever holds
it can already `sys_domain_kill` the whole system, so stopping the machine is no new authority, while
requiring any other Domain would have been an escalation.
