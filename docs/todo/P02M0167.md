## Goal

Make the verification a caller can run after a change cost what that change is worth, without
checking less than the change needs.

The claim this milestone may make: after it, a change to one driver does not run the whole x86_64
kernel suite while reporting that it runs 1% of one, a machine with a hundred cores can be told to
use them and is safe to be told, and a selector that narrows can say what evidence entitles it to.
`--jobs` defaults to ONE - see M3 - so the parallelism is available and opted into rather than
assumed: the claim is that asking for it stops being dangerous, not that the default changes. It does NOT make the full
sweep cheaper - the sweep is supposed to be expensive - and it does not remove a single test.

## What is there now

Measured 2026-08-27 against the tree, by running the planner, not by reading it. The counts were
re-measured on 2026-08-28 and the ones below are that day's. They have MOVED SINCE, and the readings
stay as they were taken rather than being quietly rewritten: P02M0168 added the `smp-core-cap` gate

A dated measurement that edits itself is not a measurement.

- **THE PLAN AND THE RUN DISAGREE, AND THE PLAN IS THE OPTIMISTIC ONE.** This is the finding the
  first draft missed and the one that decides the milestone. For a change to one driver:

      $ ./verify.sh --for src/user/drivers/core/src/virtio_input.rs --plan
      9 of 1205 runnable keys selected.
      estimated 87 s against 8217 s for everything - 1% of a full run.

      $ ... verify-model commands --stdin
      STEP  3  0  kernel suite x86_64 (unenumerated)  ./test.sh --arch x86_64

  The plan contains no guest test at all, and the command list ends with the WHOLE x86_64 suite.
  The step carries zero keys, so it costs zero in the estimate and records nothing in the history:
  a run whose largest item is invisible to the model that ordered it.

  The fallback is not a bug in itself - it was added so that a target the model cannot enumerate is
  booted rather than assumed clean, which is right. It fires on the wrong condition. `kernel_by_arch`
  is built from the SELECTED kernel tests, so "no tests selected on a booted target" and "this
  target's tests could not be read" are the same state to it, and the note it prints - *"the model
  could not enumerate this target's tests"* - is false in the first case. Enumeration worked. The
  selection was empty, which is a different fact with a different answer.

  On x86_64 the cost is about 190 s against the 87 s the plan claims. On an emulated target the same shape
  would be about 3100 s (aarch64) or 3700 s (riscv64) against a claimed zero.

- **THE SELECTOR WORKS WHEN IT HAS ANYTHING TO SELECT.** Verified rather than assumed, because the
  first draft asserted the opposite:
  - `virtio_input.rs` -> 9 of 1205 keys: three builds on three targets, no guest test.
  - `imgconv.rs` -> 11 of 1205 keys: the same builds plus EXACTLY the two imgconv tests.
  - `audio-client-provider/src/lib.rs` -> 48 of 1205 keys: twelve tests on each of three targets,
    handed to each by id.

  So the component model is not the thing answering "everything". The kernel is - deliberately, see
  below - and the zero-key fallback is.

- **THE KERNEL IS ONE COMPONENT, ON PURPOSE.** The planner says so itself: *"phase one keeps shared
  kernel subsystems whole - narrowing mem/sched/object/syscall is where a selector is most likely to
  be wrong, and it is deferred until there is shadow evidence per change class."* `verify-model
  check` lists seven subsystems as declared-narrowable and not narrowed. The deferral is right. What
  is missing is anyone producing the evidence it waits for, and a way to produce it that is not
  circular - see M5.

- **GATES RUN BROAD SUITES TO ASSERT NARROW THINGS.** `qemu-arch-profiles` ran
  `--tags boot,smp,interrupt,paging,scheduler,drivers,memory` on eight interrupt-controller profiles
  to assert five named tests. `memory` carries
  `kernel.applications.imgconv_governed_working_set_is_measured`, which costs **1149 seconds** on an
  emulated aarch64 - 83% of a 23-minute profile, eight times, two and a half hours per gate.
  `qemu-numa` had the same shape with `--tags memory,smp` for seven named tests, with the narrow tag
  it needed used three lines below in the same file. BOTH ARE FIXED; they are described here because
  they are the pattern, not the exception, and the next gate will do it again unless the shape is
  named.

  THE TAG WAS NOT THE DEFECT. `imgconv_governed_working_set_is_measured` asserts on the measured peak
  of three conversions, on the 4K peak fitting the production quota, and on a conversion under an
  80 MB Domain failing with a typed diagnostic while leaving its destination byte-for-byte intact.
  That is memory governance. It belongs in `memory`. What was wrong was a gate about interrupt
  controllers asking for a whole subject tag when it wanted five named tests.

- **ONE GUEST AT A TIME ON A HUNDRED-CORE MACHINE.** Measured during a profile run: load average
  1.39, one `qemu-system-aarch64` at 108% CPU. `verify.sh` runs its steps in a serial
  `while IFS=$'\t' read -r -u 3` loop - no `&`, no `wait`, no `-P` anywhere in the file - and the
  profile gates run their profiles one after another. So the serialisation is in the RUNNER, and the
  shared writable images are what would make fixing the runner unsafe:

      per run already:  esp-<arch>.$$.img, the firmware variables
      shared, fixed:    virtio-blk-<arch>.img, fat-media<suffix>.img, usb-media<suffix>.img,
                        iso-media<suffix>.iso, system-volume-<arch>.img
      shared, fixed:    virtio-console<suffix>.out - the guest's own console capture
      shared, fixed:    dev-channel-<arch>-test.sock, qemu-monitor.sock, qemu-qmp.sock
                        - and every one of them is `rm -f`-ed at startup, so a second guest does not
                          collide with the first, it DELETES it
      discovered:       the gates find their log by globbing `.build/logs/test/<arch>-*-guest.log`
                        and taking the newest

  The last line is the dangerous one and the first draft did not name it. Two guests of one
  architecture in flight, and a gate can read the other one's log and pass.

  AND "THE GUEST LOG" IS NOT ONE FILE ON ALL THREE TARGETS. `test.sh` says so itself: *"on riscv64
  it lands in the RUN log while the guest log holds only U-Boot and the loader. Read the guest log
  alone on riscv64 and a healthy run looks hung before its first line."* So a runner that returns
  "the log it wrote" returns the wrong file on one target of three, and the fix is a per-run
  RESULT log - the one carrying the oracle - not a per-run guest log.

  AND THE CANONICAL DISKS ARE NOT CLEAN. A guest writes to them, so copying the shared image per
  run copies whatever the last guest left in it. Per-run isolation has to start from an immutable
  template or it propagates contaminated state instead of sharing it.

- **THE ESTIMATE IS USED FOR ONE THING AND NOT THE OTHERS.** The first draft said it is never used,
  which is wrong. `plan.rs` uses it to WIDEN: per (architecture, environment) pair, where there is a
  boot to amortise, a selection costing more than 0.9 of the whole pair takes the whole pair. That
  rule is sound and the comment above it is worth reading. What the estimate is not used for is
  ORDER - a plan that will fail runs its cheapest evidence last - and there is no way to ask for a
  bounded run at all.

- **AND THE GATES ARE ONE STEP, SO THEIR COSTS ARE FICTION RATHER THAN ABSENT.** Every selected gate
  is collapsed into a single `./check.sh --gate a,b,c,...` step carrying all their keys, and
  `record_step` distributes a step's wall clock EVENLY over the keys it discharged. So the history
  does not lack per-gate costs - it holds one invented number per gate, each equal to the merged
  step's duration divided by however many ran together. A cheapest-first order taken from those
  would be sorting on an artefact of how the gates happened to be batched.

- **AND A STEP WITH NO KEYS RECORDS NOTHING AT ALL.** `record_step` returns on an empty key list.
  The unenumerated full-suite step above carries none, so the largest item in a driver plan is
  invisible to the estimator that ordered it, permanently and by construction.

- **AND A STEP NEEDING ANOTHER STEP'S OUTPUT IS SCHEDULED BEFORE IT, SO THE FULL SWEEP CANNOT PASS
  IN ONE PASS.** Measured 2026-08-28 on a 100% selection: the run orders its 86 steps by KIND -
  builds 1-3, host suites 4-78, the merged gates 79, conformance 80, the kernel suites 81 onward -
  and `capability-trace` is a gate that reads an artifact only a kernel suite produces. Step 3
  rebuilds `.build/cargo/kernel/x86_64-unknown-none/debug/kernel`; the gate at step 79 compares the
  newest x86_64 trace against that binary's timestamp, correctly finds it older, and refuses:
  *"the newest x86_64 trace is older than the kernel beside it - it is evidence about a kernel that
  has been rebuilt since. Run ./test.sh"*. The x86_64 suite that would produce a fresh one runs
  afterwards.

  The gate is right and the ORDER is wrong, which is the shape M4's prerequisite clause is about,
  arrived at from the other side: this is not a step that would be cheaper elsewhere, it is a step
  that CANNOT SUCCEED where it is.

  AND IT CANNOT BE PREPARED AROUND, which is worth recording because it was tried. Running the
  x86_64 suite BEFORE the sweep, so the trace is fresh when the gates run, does not help: the sweep's
  own step 3 rebuilds the kernel and makes the trace older than the binary again. The second sweep of
  2026-08-28 was launched with a trace confirmed fresh minutes earlier - `capability-trace` passing
  standalone, "the live trace matches the reference and replays against the model" - and the gate
  failed inside the sweep anyway. A step whose prerequisite is invalidated by a step that runs before
  it is not a scheduling preference; it is the graph missing. And because the 45 gates are one merged step, the refusal marks
  all 45 keys failed - so a full sweep of a clean tree reports 45 failures for one ordering defect,
  which is also M4's fabricated-cost problem wearing its other face.

- **THE BUILD FAN-OUT IS THREE TARGETS WHATEVER IS BOOTED.** The driver change above builds
  `packages,user,volume` on aarch64 and riscv64 and boots neither. This is DEFENSIBLE - an
  arch-specific compile error is a real defect and a cheap one to find - and it is recorded here as
  an unmeasured cost rather than as work, because nothing has measured whether it is cheap.

## Work

- [x] **M0 - the zero-key fallback stops running a suite it does not account for.** This is the item
  the rest is worth nothing without, and it is small.

  Three states, three answers, and the first draft left the third open where it had no business
  being open - the architecture policy has ALREADY decided which targets a change boots, and
  lowering a plan to commands is not the place to overrule it:

  | the model | the answer |
  | --- | --- |
  | could not enumerate this target's tests | today's behaviour: boot whole, today's note. Booting blind is the safe answer to a model that cannot see. |
  | enumerated them and selected none, but the target is booted | a named boot/smoke check FROM THE CATALOG, with its own key and its own cost |
  | the target need not be booted at all | the PLANNER drops it, before the plan is final. Never the lowering. |

  AND ALL OF IT HAPPENS IN THE PLANNER, NOT IN THE LOWERING. The boot check and the unenumerated
  step are catalog checks with keys, selected into the plan like anything else. Decided at lowering
  they would leave `--plan` showing no guest step while the run performs one, which is the defect
  restated rather than fixed - and a key the plan never contained is one the recorder discards.

  THE SAME MISMATCH EXISTS A SECOND TIME AND IS PART OF THIS ITEM. When a selection is within a
  fifth of the whole suite, the lowering runs `./test.sh --arch X` - all of it - while attaching
  only the SELECTED keys. So the plan says 195 keys and the run does 205, and ten tests run
  unrecorded. Widening is a decision, and the planner already makes one on cost; there is no reason
  for a second widening rule to live in the step builder.

  Two more things this needs, and they are not the same KIND of thing - which is why leaving them
  together left both open. The boot check needs a catalog id: that is not measured at all - it is a
  naming decision, and it is taken in the catalog change that ADDS the check, like every other
  check's id, rather than fixed in this document. The unenumerated step needs a
  conservative cold-start cost, which IS measured - and the obvious source for it is the wrong one.
  `full_suite_seconds(architecture, "test-guest", tests)` counts the tests the model DISCOVERED for
  that target, and a target the model could not enumerate has none: `tests` is zero and the estimate
  collapses to the fixed boot term. So deriving the seed from the per-arch full-suite estimate prices
  the one case it exists for at the cost of booting and running nothing. The count that IS available
  for an unenumerable target is the number of test ids DECLARED IN SOURCE - `scan_source` reads them
  whether or not any binary was found - and it is an upper bound, which is the safe direction for a
  seed. What this item owes is that neither the id nor the seed is settled by whoever gets there
  first.

  AND THE KEY RULE IS ABOUT EVIDENCE, NOT ABOUT EVERY STEP. M3 adds a staged build that no test
  discharges, so "every step carries a key" as written forbids something this same milestone asks
  for. Two things, separately named: a step has a `StepId` - what schedules it, what its dependencies
  are stated in, and what its cost is keyed on - and it has the keys it DISCHARGES. A prerequisite
  discharges none, and that is legitimate. What is forbidden is a step that RUNS TESTS and discharges
  nothing, which is exactly the fallback this item is about: it is evidence-producing, so it carries
  a real aggregate catalog key, and a prerequisite is never the reason a target counts as covered.

  THE GATE FOR THIS is a test that lowers a plan to commands and asserts that every evidence-producing
  step carries at least one key, that the keys a step carries are the keys its command will run, and
  that every step - prerequisite or not - has a `StepId` the history can be keyed on.

- [x] **M1 - `tags` and `covers` are different instruments and the tree says which is which.** The
  first draft treated tags as the selector's handle. They are not: `verify-model`'s `select` reads
  `covers` and never looks at a tag. Tags serve `./test.sh --tags` and the gates.

  So this item is not a retag. It is a written rule and the two consequences of it:

  - `covers` answers *what would this test catch*, for the change selector. It is already on all 370
    kernel tests and `verify-model check` enforces that.
  - `tags` answer *what group does this test belong to*, for a person or a gate asking for one. Most
    are subjects; some are honestly not - `Smoke`, `Slow`, `Stress` and the `arch-*` tags describe
    how a test RUNS or where, which is a legitimate second kind of group and not a violation of the
    rule. The rule is that a tag says something true about the test, not that every tag is a
    subject. A test may carry several.
  - **A GATE ASSERTING N NAMED THINGS ASKS FOR THOSE N THINGS.** `TEST_SELECTION` exists, takes ids,
    and hard-fails on an id it does not have. A gate that wants five tests and asks for a subject tag
    is buying every test that subject will ever acquire.

  THE GATE FOR THIS IS NOT A COUNT. Counting tests per tag before and after proves movement, not
  correctness. What each gate must prove is that ITS OWN oracles are still selected: the gate names
  the ids it asserts on, and a check reads the result log back and fails if one of them did not run.

  THIS APPLIES TO GATES BUILT ON CATALOG KERNEL TESTS, and only to those. A host-only gate and one
  that asserts directly on an artifact have no test ids to name, and demanding some of them would be
  a rule satisfied by inventing them.

- [x] **M2 - the guest step is derived from what a change can break, and a `covers` line is a claim
  rather than the evidence for it.** `build.volume` covers some two hundred components because the
  volume contains every binary. The first draft read that as "therefore every guest test runs", and
  the plans above show it does not - the wide `covers` drives BUILD FRESHNESS, which is correct and
  must stay: drop it and a guest boots the previous userspace, which makes every result taken on it
  meaningless.

  What is missing is the positive half. A driver change selects no guest test at all, and M0 stops
  that from silently becoming the whole suite - but "runs nothing" is not the right answer either.

  SO THE WORK IS AN ORACLE, NOT AN ANNOTATION. Writing `covers = ["bin.virtio_input"]` on a test
  that never asserts anything which fails when that driver breaks moves the plan and changes nothing
  about what is caught - it is the tag mistake of M1 wearing the other instrument's clothes. Each
  driver and service needs a runtime oracle that actually fails.

  THE CONTRACT IS A READINESS STATE PLUS AN OBSERVABLE EFFECT, and the state is not the same word
  for both halves of the census this item asks for. A DRIVER reaches `Online`; a SERVICE reaches
  `Ready`, which ServiceManager tracks and defines as "started, reported in, and serving" - the
  service itself says when it can answer, because nothing outside it knows. An earlier draft said
  `Online` for both and would have had the service half of the census asserting on a state
  ServiceManager does not have.

  AND THE STATE IS NOT THE CONTRACT ON ITS OWN: "its provider answers" is not it either.
  `virtio_console` reports online having published no provider at all, and demanding one would make
  a passing driver look like a failing test.

  AND THE DRIVER'S OWN REPORT IS THE LAST RESORT, NOT THE FIRST. A line the driver prints about
  itself is the weakest oracle there is - it says the code reached that line. `virtio_console` writes
  a banner THROUGH its transmit queue, which is a real round trip to the device and shows up outside
  the driver entirely; that is the effect worth asserting. The order is: an external effect where one
  exists, a provider answering where one is published, and the driver's own report only where neither
  does.

  AND THE ORACLE IS READ FROM THIS RUN'S RESULT LOG - the path M3.3 makes the runner return - never
  found by globbing for the newest log of an architecture. An external effect asserted against
  another guest's output is M3's failure wearing M2's clothes, and a banner is exactly the kind of
  line that would still be sitting in the previous run's capture.

  DEFINITION OF DONE FOR THIS ITEM IS A CENSUS, NOT AN EXAMPLE. Every staged driver and service has
  at least one runnable oracle naming it, or a declared exception saying why it has none. One driver
  demonstrated proves the mechanism and not the coverage - and the exceptions are a machine-checked
  list of `component` and `reason`, because an exception nobody can enumerate is a gap that reads
  like a decision.

- [x] **M3 - one run identity, then parallelism, and the guard learns to tell runs apart.** MET AGAIN (2026-08-29) - see the audit sections at the end of this file. In this
  order, because the second is unsafe without the first.

  0. THE TEST KERNEL ITSELF, WHICH IS THE ONE THIS LIST MISSED AND THE WORST OF THEM.
     `TEST_SELECTION` is compile-time - `option_env!`, which is what makes the runner refuse an
     unknown id rather than skip it - and every kernel build shares one `target-dir`
     (`src/kernel/.cargo/config.toml`). So two guests of one architecture with DIFFERENT selections
     compile to the SAME executable path with different contents, and the second build can overwrite
     the kernel before the first runner has put it in its medium. That is a run reporting green over
     somebody else's selection, which is the exact failure this item exists to prevent, reached
     without any shared disk at all.

     AND IT IS NOT ONLY THE EXECUTABLE. On x86_64 the suite builds its medium from that kernel into
     `$BUILD/$SLUG-test.iso` - a FIXED path, `mkimage.sh`'s `make_iso` under `test_medium=1` - and
     `qemu-run.sh` hands it to QEMU with `-cdrom` further down. The write is a rename, so it is
     atomic; atomic is not private. The second selection can replace the medium before the first
     guest opens it, and what boots is the other run's suite under this run's name.

     THE IDENTITY COVERS BOTH COMPILE-TIME FILTERS. `TEST_SELECTION` and `TEST_TAGS` are both
     `option_env!`, so two runs differing only in tags compile to the same path with different
     contents exactly as two differing in ids do. A run identity built on one of them is a race with
     a smaller window.

     So: compile under a build lock and stage the selection-specific kernel AND the medium built from
     it as one immutable per-run artifact, hand the guest that exact path, and only then start guests
     in parallel. That staged build is a PREREQUISITE in M4's budget closure, not a free step, and it
     discharges no key - which is the case M0 has to leave room for.
  1. A `RUN_ID` per guest covering everything a run writes, listens on, or reads back: the data
     disks, the FAT, UDF and USB media, the system volume copy, the guest's console capture,
     the dev-channel socket, and the monitor and QMP sockets. Today the ESP alone is per-run and
     every socket is `rm -f`-ed at startup.

     THE READ-ONLY FIXTURE MEDIA ARE NOT ON THAT LIST, AND "READ-ONLY" IS ABOUT THE GUEST ONLY. No
     guest writes `iso-media*.iso`, so they stay SHARED with `readonly=on` and a copy per run would
     be cost with no isolation bought. THE RUNNER DOES WRITE THEM: `qemu-run.sh` keys each fixture by
     content and regenerates it into the shared path when the key does not match. NOT HALF-WRITTEN,
     which an earlier draft said and the code refutes - it builds into a candidate and publishes with
     an atomic rename. The risk is a GENERATION SWAP: two runs starting on a stale fixture both
     rebuild it, and a guest can open a whole, valid fixture that is not the one its own run keyed
     and staged against. So the
     fixtures are prepared by ONE LOCKED PREREQUISITE STEP that completes before any guest starts,
     and no guest path may regenerate one. THAT IS NOT SUFFICIENT ON ITS OWN, and the third statement
     of this item is the one that closes it: `media_publish` renames a candidate onto a FIXED final
     path, so any later invocation - another sweep, a person running `./test.sh` beside it - can
     replace the file between the preparation step and a guest opening it, atomically and
     invisibly. The path has to carry the generation: a CONTENT-ADDRESSED final name, so two
     generations are two files and replacing one is not something that can happen to the other. The
     lock then only stops two runs building the same name twice, which is cost rather than
     correctness. Immutable during the run is the property; `readonly=on` is only how the guest is
     held to it, and the test is two runs on two different fixture generations, each getting its
     own. THE SUITE'S OWN `-test.iso` IS A DIFFERENT FILE and belongs to item 0: it is
     rebuilt per selection, so it is not a fixture at all. An earlier draft had "the ISO" in both
     places, and the reason was that one word was naming two artifacts.
  2. FROM AN IMMUTABLE TEMPLATE, not from the canonical disk. A guest writes to its images, so
     copying the shared one per run copies whatever the last guest left in it - which turns one
     contaminated disk into N contaminated disks and calls it isolation.
  3. The runner RETURNS the path of its RESULT log - the one carrying the oracle - and gates take it
     as an argument. Not "the guest log": on riscv64 the suite's output lands in the RUN log while
     the guest log holds only U-Boot and the loader, so a runner returning the guest log returns the
     wrong file on one target of three. Globbing for the newest log of an architecture is a
     correct-looking read of another guest's result.
  4. AND IT IS NOT THE ONLY THING THAT STARTS GUESTS TODAY. `test.sh --arch all` runs the three
     architectures CONCURRENTLY and says so in its own comment, and `--release` calls it from outside
     the planner - so "exactly one answer to how many guests may run" is already false before this
     item adds anything. The three-way arch run is safe today because its media are per-architecture,
     which is a different property from being scheduled. AND THE CHOICE IS MADE HERE RATHER THAN
     LEFT AS A PAIR: **the flat paths run one architecture at a time**, and `verify.sh --jobs` is the
     only scheduler. Not a limiter both paths consult, because the flat path's whole value is that it
     consults nothing - "it is what runs when the thing that makes choices is broken", and a shared
     limiter is one more thing that can be broken while it runs. The cost lands on `--release` and
     `--sweep`, which are the paths that are deliberately slow and thorough, and that is the right
     place for it. `test.sh --arch all` keeps its own concurrency for somebody running it by hand;
     that is not a second scheduler, because nothing else is scheduling then, and the stray-guest
     guard is what stops it colliding with a run that is.
  5. `verify.sh --jobs N`, which owns the parallelism: builds and other prerequisites complete before
     any guest starts, guests run up to N at a time, every step is waited for, and the failures are
     aggregated rather than the first one winning.
  6. AND THE PROFILE GATES ARE THE EXPENSIVE CASE, so `--jobs` alone does not touch them.
     `qemu-arch-profiles` runs eight profiles serially INSIDE one step, and parallelising the steps
     around it changes nothing. `qemu-numa` has the same shape with three, and so will the next gate
     written this way - the rule is about MULTI-PROFILE GATES and not about one gate's name.
     EACH PROFILE BECOMES ITS OWN CATALOG STEP - not a `--jobs` of its
     own, which would be a second scheduler: an outer N times an inner N is N-squared guests, and
     "how many QEMUs may run" must have exactly one answer on this machine. It also gives each
     profile its own key and therefore its own measured cost, which M4 needs.
  7. `verify-history.json` is written by ONE writer. Parallel steps recording into it concurrently
     is a lost-update race in the file the estimator reads: the parent collects results and writes
     them serially, or there is a lock, and which one is a choice - having neither is not.
  8. `test.sh`'s stray-guest guard - which today refuses when ANY `qemu-system-<arch>` holds a file
     under `$BUILD_DIR` - refuses only for a guest holding THIS run's files.
  9. `--jobs` DEFAULTS TO ONE. Parallelism is opted into, because the failure mode of getting it
     wrong is a green that means nothing and the failure mode of not using it is a slow run. And the
     artifacts of a `RUN_ID` whose guest died get cleaned up.

  THE FAILURE MODE HERE IS THE WORST ONE THIS TREE HAS: two guests writing one image is a result that
  is green and means nothing. So the guard's new rule gets a test that watches it refuse a real
  collision, not only accept a real parallel pair.

- [x] **M4 - the plan is ordered by cost and can be given a budget, with a contract.**

  Ordering: cheapest-first among the steps whose prerequisites are met, so a real defect surfaces in
  minutes rather than at the end of a sweep.

  BEFORE ANY ORDERING IS TRUSTWORTHY, THE FABRICATED COSTS GO. `record_step` splits a step's
  duration evenly over its keys, so every cost on disk for anything that ran MERGED is that step's
  duration divided by however many things were batched with it. That is the gates, and it is also
  the merged builds and the conformance suites. Ordering on those is sorting on the batching.
  Anything that can be scheduled separately is timed separately, and the existing merged entries are
  DISCARDED rather than inherited by the first cheapest-first run. ONLY THE COSTS WHERE THE STEP
  PASSED: a record also carries when a key last ran and whether it passed, and throwing that away for
  a step that really did run every member would turn a cost migration into a freshness reset - every
  key suddenly overdue, for a reason that has nothing to do with whether it ran.

  BUT A FAILED MERGED STEP'S FRESHNESS IS A LIE AND GOES WITH THE COSTS. `check.sh` runs its gates in
  order and stops at the first failure; `record_step` then stamps EVERY key of the step with the
  time and the failure. Measured 2026-08-28 on a full sweep: `capability-trace` refused, it was the
  fifth gate of forty-five, and all forty-five were recorded as having run and failed - forty of them
  never started. So the rule is by outcome. A step that PASSED ran all of its members, and its
  per-key `last_run` and status are true. A step that FAILED ran an unknown prefix of them, so its
  per-key freshness and status are discarded along with its costs unless a per-member result exists
  to keep. Keeping them means forty gates that never ran count as recently checked.

  AND TWO QUANTITIES, NOT ONE - which the paragraph above reads as denying and must not. The per-key
  ESTIMATE and the scheduled step's COST answer different questions and both have to survive. The
  planner needs a per-key estimate before there is a step at all: the 0.9 widening rule prices a
  selection of kernel tests, including tests that have never run. And kernel tests inside one boot
  are not separately schedulable, so their per-key figures are estimates and stay estimates. What is
  discarded is the other quantity - a merged step's duration divided over its keys and presented as a
  measurement of something schedulable. Freshness and pass/fail stay keyed on `PlanItemKey`;
  scheduling and the budget are keyed on `StepId`.

  AND A `StepId` HAS TO SAY WHEN TWO STEPS ARE THE SAME WORK, or it cannot key a cost. It is the
  kind, the architecture, the configuration or profile, and the sorted list of what the step was
  asked to do - selection ids, tags, or build parts. It does NOT contain the `RUN_ID`: an identity
  that changes every run has no history and every step is priced as unseen. A step with no history is
  priced by the fixed-plus-per-key estimate; a keyless prerequisite with no history gets a
  conservative seed or is refused under a budget as `INCOMPLETE`, because an unpriced prerequisite is
  the cheapest thing in every plan.

  AND THE DEPENDENCY GRAPH IS VALIDATED BEFORE IT IS WALKED: `StepId`s are unique, every dependency
  names a step that exists, and the graph is acyclic. A scheduler that waits on a step nobody emitted
  hangs, and two steps sharing an id merge two costs into one figure that describes neither.

  `--budget SECONDS` is in ESTIMATED seconds and is not a timeout - it decides what to start, never
  what to kill. Its contract:

  - THE BUDGET COVERS THE PREREQUISITES. Putting builds outside it, which the first draft did, makes
    `--budget 10` a run that spends forty minutes building and then declines to test. What is
    costed is a whole prerequisite-closed branch: the step and everything it needs.
  - A STEP HAS TO KNOW WHAT IT NEEDS, and today's `Step` carries no dependencies at all - so
    "prerequisite-closed" is a phrase with nothing behind it until each step names the steps it
    requires. That is the smallest addition that makes the rest of this arithmetic meaningful. AND
    IT IS NOT ONLY ABOUT BUDGETS: the measurement above shows a gate scheduled before the suite
    whose output it reads, which no cost model can fix and dependencies do.
  - the budget is a sum of ESTIMATED work and does not move with `--jobs`: running two things at
    once makes a run finish sooner, not cost less;
  - a prerequisite shared by two branches is counted ONCE - the second branch pays only its own
    incremental closure;
  - if the cheapest complete branch does not fit, run NOTHING and say what the minimum would have
    been - a budget that half-builds has spent the time and bought no evidence. "Starts nothing it
    cannot finish" means nothing whose ESTIMATED closure does not fit; a budget is not a timeout and
    never kills a step that overran its estimate;
  - among affordable branches, take the cheapest;
  - a step with no measured cost is not started under a budget without a conservative SEED - an
    unknown priced at zero is the cheapest thing in every plan and would always be picked first;
  - a step's cost is the WHOLE step's, keyed on the thing that is actually scheduled, and a fast
    FAILURE is not a measurement of what succeeding costs;
  - a failed prerequisite blocks its dependents and nothing else: independent branches carry on, and
    the run reports both what failed and what it did not reach;
  - FAIL OUTRANKS INCOMPLETE. A run that skipped work AND found a defect is a failure, and reporting
    the skipping is the smaller half of what happened.
  - a merged step is never split to fit;
  - every skipped step and key is PRINTED;
  - the run exits with a distinct non-zero `INCOMPLETE` status, never a green;
  - `--sweep`, `--release` and `--shadow` refuse a budget outright.

  A selector that quietly trims its own scope is the defect P02M0156 is named after, and a budget is
  that defect with a flag on it unless every one of those holds.

- [x] **M5 - the narrowing is EARNED, by a candidate model, under BOTH bars that already exist.** MET AGAIN (2026-08-29) - see the audit sections at the end of this file.

  The ordering argument in the first draft stands and is the point of the item: gather the evidence,
  then split. What it did not say is how, and taken literally it cannot be done - while `kernel`
  selects everything, `--shadow` compares FULL against FULL and proves nothing about a narrower
  model. Worse, splitting changes the registry and the catalog and therefore `model_hash`, and
  evidence bound to the old hash is correctly discarded. Evidence first, split second, and the split
  destroys the evidence.

  A CANDIDATE MODEL BREAKS THE CIRCLE:

  1. The candidate is a FROZEN, VERSIONED input - not a flag - and it computes the narrower
     selection. "A model file" is not enough, and this is the part that decides whether step 4 can
     ever be satisfied. `model_hash` is taken over the registry text, the configuration catalog, the
     graph's edges, every feature definition, the arch-risk table AND the catalog itself - check by
     check, each with its `covers` and its variants. Narrowing changes TWO inputs: ownership in
     `registry.toml`, and the `covers` written in the kernel tests' own sources, which reach the hash
     through the catalog. So the candidate is a complete overlay of BOTH.

     AND THE TWO PLANNERS DO NOT READ THE SAME FILE, which the previous draft of this line said and
     which makes step 4 prove nothing: if the active planner is still reading the candidate overlay,
     an identical hash says the overlay equals itself. The contract is four steps and they are all
     small. The candidate planner reads the canonical model plus the FROZEN overlay. Activation
     MATERIALISES that overlay into the canonical files. The active model is then re-read from the
     canonical files alone, with no overlay in the path. Only that hash is compared with the
     candidate's. The registry is hashed as raw text, so what is frozen is the exact resulting bytes
     - which makes materialising it a copy rather than a regeneration that has to agree.

     AND THE HASH IS CHECKED AT THE WRONG END ON ITS OWN. Comparing only the RESULT says nothing
     about what was there before: an activation that overwrites a `registry.toml` somebody edited in
     the meantime produces exactly the hash the candidate predicts, because the overlay decides it -
     so the check passes while destroying an unrelated change, and the evidence certifies a model
     nobody reviewed. The candidate therefore also carries the digests of the canonical inputs it was
     FROZEN AGAINST, and activation verifies those BEFORE its first write. A base that has moved is a
     refusal with nothing written, not a merge and not an overwrite.
  2. The authoritative run is still FULL: nothing is skipped while evidence is being gathered.
  3. The comparison is recorded against the CANDIDATE's `model_hash`.
  4. Activation CHECKS THE HASH. The model that becomes active must hash identically to the
     candidate the evidence was gathered under, and activation is refused otherwise. Without that
     check "the same candidate, activated" is a claim about a human's intention.

  AND THE THRESHOLD AS WRITTEN IS UNREACHABLE FOR THIS SHAPE OF CANDIDATE, which is the one thing
  in this milestone that would have stopped the work dead. `trust.rs` wants five DISTINCT decisions
  per scope pair, and a decision's digest is the selected keys covering the component plus that
  component's edges plus its targets. For a frozen `kernel.mem` candidate every change inside
  `src/kernel/mem` selects the same tests, walks the same edges and implies the same targets - so
  five different edits produce ONE digest and the counter never passes one. The tree already
  suspected this: the comment above the digest says an isolated component's decision "is often
  byte-identical run after run, so the counter was hard to advance HONESTLY".

  AND THIS CHANGES WHAT DISTINCTNESS MEANS. Saying otherwise was the first draft's mistake, twice
  over: it claimed the record already stores changed paths and that the existing fallback uses them.
  Neither is true. `Record` stores `source_digest`, `changed_components`, `change_kinds` and
  `edge_kinds` - no paths - and the fallback to `changed_components` exists only for records written
  before per-component decisions did, where the comment calls collapsing them "the safe direction".

  WORSE, THE TREE REJECTED CONTENT-BASED DISTINCTNESS ON PURPOSE and wrote down why: *"five edits to
  audio that each produce the SAME decision are five different digests and counted five times -
  which is one decision validated five times, the shape this criterion exists to refuse."* A
  milestone that reinstates it while claiming to reuse an existing mechanism is changing a rule
  behind the reader's back.

  So: state the change. That rule is right about what it was defending against - re-running ONE
  comparison against one tree - and it over-reaches when it concludes that identical decisions carry
  no independent information.

  AND IT CHANGES THE RULE WHEREVER DISTINCTNESS IS COUNTED, not only for candidates. A criterion that
  means one thing while evidence is being gathered and another once a model is active is two rules
  sharing a name, and the second would re-grade certificates written under the first without anyone
  asking for it. A shadow comparison does not test the decision; it tests whether the
  SELECTION was adequate for THAT CHANGE, and adequacy is a property of the change. Five different
  edits are five different full runs and five genuine opportunities to find a miss, however alike
  the selection looked each time.

  WHAT THAT COSTS IS ONE FIELD, and it has to be per-component: the changed paths under this
  component AND their content, digested. Paths alone are not enough - `src/kernel/elf.rs` is a single
  file, so five edits to it share one path set - and the global `source_digest` is not enough either,
  because an unrelated change elsewhere in the tree would buy false distinctness for a component
  nobody touched. The planner test therefore runs over a single-file subsystem as well as a
  multi-file one, because that is the case the cheap answer gets wrong.

  AND THE FIELD HAS TO SAY WHAT A CHANGE IS, because "the paths and their content" does not answer a
  delete, a rename, a copy or an untracked file. One shape covers all of them: the digest is over the
  sorted tuples `(change kind, path, content before or ABSENT, content after or ABSENT)`, and a
  rename contributes both its origin and its destination. A deletion is then a real change with a
  real digest rather than a path with nothing behind it, and two edits that swap a file between two
  names are two different changes rather than one.

  AND IT IS PROVED BY A PLANNER TEST, not by a unit test holding hand-made digests. The existing
  distinctness tests construct `decision-0`, `decision-1` and so on, which is why nobody noticed the
  real planner cannot produce them. The test that matters runs five real changes through the real
  planner against a candidate and asserts the counter reaches five.

  AND TWO BARS HAVE TO BE MET, NOT ONE. `trust.rs` also asks for at least one `shadow-exec` and for
  `required_architectures`, which for `TestGuest` is TWO. The registry carries a per-subsystem bar:
  `src/kernel/mem` says *"shadow-clean on all three targets"*, and `src/kernel/syscall` adds *"plus
  the ABI unchanged"*. The general bar is the weaker of the two for exactly the subsystems that
  matter most, so meeting it is necessary and not sufficient.

  `risk_class.evidence` IS PROSE AND HAS TO BECOME FOUR FIELDS to be checked at all: which targets
  must be clean, how many distinct changes, whether the ABI must be unchanged, and WHICH KINDS of
  change must be among them. The fourth is not optional and three was a miscount: `mem` says
  "allocator and page-table changes", `object` says "capability, channel, handle and domain", and
  `sched` says "SMP and preemption" - conditions three fields cannot express, so a check built on
  three would pass on five edits to one corner. A list of required change groups, not an expression
  language.

  AND A REQUIRED GROUP NEEDS A PRODUCER, which nothing is today. `Record` carries `change_kinds`, but
  those say how a component was REACHED - what it ships, what its tests are built from - not what the
  edit was about, so no record can answer "was this an allocator change". So each group is DECLARED:
  a name and the paths that constitute it. The groups a change set matched are written into its
  evidence record beside the rest, and a declared group that matches no tracked path is REFUSED
  rather than left standing as a bar nobody can meet. That is the whole mechanism - a group whose
  paths cannot express it is a sign the group is wrong, not a reason for an expression language.

  AND `the ABI unchanged` HAS TO MEAN ONE THING. Taken conservatively it is checkable today: the
  change set contains no `abi` component. That is stricter than the sentence strictly needs and it is
  unambiguous, which is what a bar has to be. A digest over a named ABI manifest is the stronger
  answer and it is not needed to close this item.

  AND ONE ACTIVATION, NOT SEVEN. "One subsystem at a time" cannot work: `model_hash` is global, so
  the second activation changes it and prunes the first subsystem's certificate. One frozen
  cumulative candidate, evidence still graded per subsystem, and the activation happens once when
  every subsystem in it qualifies. Fewer moving parts than the per-subsystem version, and it is the
  only one the existing trust store can express.

  A PRECONDITION NOBODY HAS DONE: most kernel tests declare `covers = ["kernel"]`. A narrower kernel
  model that they all still cover selects everything anyway. Subsystem-level `covers` on the kernel
  tests is part of this item, not a follow-up to it.

  AND ONE ROW OF THE REGISTRY PROMISES SOMETHING THE DISCOVERY CANNOT DO. `src/kernel/test_suites`
  says *"a test file reaches the tests in it; once `covers` is on every test this is derivable rather
  than declarable, and this row disappears"*. `covers` IS on every test now - 370 of 370, and
  `verify-model check` says so every run - and the row has not disappeared, because discovery throws
  the source path away: a `Declaration` carries `id` and `covers` and nothing else, so "the tests in
  this file" is not a question the model can be asked. The declaration gains its source paths -
  PLURAL, because the scanner already merges several arch-gated declarations of one id, a
  `#[cfg(target_arch = "..")]` variant per target implementing the same test three ways under one
  identity, and a single path would silently keep whichever file was read last. A planner test then
  asserts that changing one test file selects the tests declared IN it - not the whole kernel, and
  not nothing. Then the row goes, which is the row saying so.

## Dependency order

Not the order the items are written in, and the difference matters enough to state: M1's gate reads a
result log back, and M2's oracle asserts on an external effect in one - both of which are M3.3's
per-run RESULT log, without which they would be written against the newest log of an architecture,
which is the read this milestone exists to stop.

    M0  ->  M3.0 - M3.3  ->  M1, M2  ->  the rest of M3  ->  M4  ->  M5

M0 first because everything downstream is priced and ordered by keys that do not exist until a step
carries them. M3.0-M3.3 next: run identity, the immutable template and the returned result log are
what make an oracle addressable. M1 and M2 then have something to assert against. The rest of M3 -
`--jobs`, the per-profile steps, the single history writer, the guard - is parallelism, which is safe
only after identity. M4 needs the per-step costs the split above produces, and M5 needs all of it.

## Definition of done

- Every evidence-producing step in a lowered plan carries at least one key, and the keys a step
  carries are the keys its command will run - neither the zero-key fallback nor the near-full
  widening is decided anywhere but the planner.
- A change to one driver selects a runtime oracle that FAILS when that driver breaks - the binding
  reaching `Online` plus whatever that driver's success looks like - does not contain the image,
  audio or LiCo suites, and does not fall back to a whole suite.
- Every staged driver and service has at least one runnable oracle naming it, or a declared
  exception saying why it has none - and the negative case is shown for BOTH: one driver and one
  service, each broken deliberately, each failing the oracle that names it. A census proved on
  drivers alone says nothing about the half of it that reaches `Ready` rather than `Online`.
- A change to one application selects that application's suites and the integration tests that
  exercise it, and not the kernel's object or scheduler suites.
- Every gate built on catalog kernel tests names the ids it asserts on, and a check reads the result
  log back and fails if one of them did not run.
- No gate sets a timeout tighter than the stall detector that decides whether a run is wedged.
- Guests of one architecture run in parallel with no shared writable file and no shared socket, each
  built from an immutable template, each consumer reading the result log its own run produced, one
  writer to the history, and a test that watches the guard refuse a genuine collision.
- Each profile of a profile gate is its own step with its own key, scheduled by the one `--jobs`,
  and nothing on the machine has a second answer to how many guests may run at once.
- `--budget` costs whole prerequisite-closed branches, starts nothing it cannot finish, exits
  INCOMPLETE naming what it skipped and what the minimum would have been, and is refused by
  `--sweep`, `--release` and `--shadow`.
- Every separately schedulable unit is separately timed, and no cost derived from a merged step -
  gate, build or conformance suite - survives into the first cheapest-first run.
- A candidate model can actually REACH the trust threshold, shown by five real changes through the
  real planner rather than by hand-made digests.
- A narrowing activates only when the active model hashes identically to the candidate its evidence
  was gathered under, AND both `trust.rs`'s threshold and that subsystem's `risk_class.evidence` are
  satisfied.
- Every step has a `StepId` that schedules it and carries its cost; every evidence-producing step
  also carries the keys its command discharges, and a prerequisite that discharges none is never why
  a target counts as covered.
- The suite's own selection-specific medium is per-run and immutable, and its identity covers both
  compile-time filters - `TEST_SELECTION` and `TEST_TAGS`.
- The candidate is a complete overlay of BOTH narrowing inputs - registry ownership and the kernel
  tests' `covers`. The candidate planner reads canonical plus that overlay; the active planner reads
  the materialised canonical files with NO overlay in its path, and only those two hashes are
  compared. An activation whose hash is refused leaves every canonical input byte-for-byte as it
  was.
- The distinctness test runs over a single-file subsystem as well as a multi-file one.
- Every required change group is declared as a name and the paths that constitute it, the groups a
  change matched are recorded in its evidence record, and a declared group matching no tracked path
  is refused.
- Changing one kernel test file selects the tests declared in it, and the `src/kernel/test_suites`
  risk-class row is gone.
- A table-driven test covers all three of M0's states and the near-full widening, in the planner.
- Two suites of ONE architecture run at the same time with different `TEST_SELECTION` and different
  `TEST_TAGS`, each with its own medium and its own result log, and each reports its own selection.
- A scheduler test covers the dependency graph, a prerequisite shared by two branches, a step with no
  measured cost, `FAIL` outranking `INCOMPLETE`, and a failed prerequisite blocking its descendants
  and nothing else.
- Activation verifies the digests of the canonical inputs the candidate was frozen against BEFORE its
  first write, and a base that has moved is a refusal with nothing written.
- Fixture generations are content-addressed, so two runs staged against two generations each open
  their own - shown by a test that runs exactly that, not by a lock nobody can observe holding.
- `verify.sh --jobs` is the only scheduler: every verification path that starts guests goes through
  it, and the flat `--release` and `--sweep` paths run one architecture at a time rather than calling
  a three-way concurrent runner from outside it.
- The full sweep runs everything it runs today - the same COVERAGE, which is what "unchanged" means
  here and does not extend to the ORDER. It cannot: `--sweep` runs `build`, then `check`, then
  `test`, and `capability-trace` is a check that reads a log only a test produces, so a sweep of a
  clean tree fails on it every time. A definition of done that froze the order would forbid the fix
  for the defect this milestone measured.
- `--release` and `--sweep` are ordered correctly TOO, and not by the planner. Both are flat by
  design - `--release` says so in its own comment, "it consults no model, reads no plan and makes no
  choice, because it is what runs when the thing that makes choices is broken" - so the dependency
  graph cannot reach them and must not be made to. Their sequence is corrected where it is written,
  and a check that reads a test's output runs after the tests on every one of the three paths.

## What the first draft of this milestone got wrong

Kept deliberately: a milestone that silently corrects its own premises teaches nothing, and two of
these were argued confidently from a reading of the code rather than from running it.

- **"A tag is the selector's only handle on a test."** It is not a handle at all. `verify-model`
  selects on `covers`. Retagging cannot change a `verify.sh` plan, only what `--tags` and the gates
  pull. M1 is rewritten.
- **"`imgconv_governed_working_set_is_measured` is tagged `Memory` because it allocates."** It
  asserts on peaks, on a Domain quota, and on an out-of-memory failure preserving its destination.
  The tag was true; the gate asking for the whole subject was the defect. The tag was removed on
  2026-08-27 and put back the same day.
- **"The volume's wide `covers` implies every guest test."** It implies every BUILD, which is what it
  is for and must stay. Measured: a driver change selects 9 of 1205 keys and an imgconv change
  selects 11, including exactly the two imgconv tests.
- **"The estimate is printed and never used."** It is used to widen a selection to a whole
  (architecture, environment) pair above a 0.9 cost ratio. It is not used to order, and there is no
  budget.
- **"The disks simply were not copied."** The disks, the media, the volume copy, the dev-channel
  socket, the monitor socket and the QMP socket - and the log the gates read is found by globbing,
  which is the part that could produce a green from another guest's run.
- **Missed entirely:** the zero-key full-suite fallback, which is now M0 and is the largest single
  gap between what a plan says and what a run does.

### And what the SECOND draft got wrong

Reviewed again on 2026-08-27, and these are the ones that survived the first correction.

- **M0 left the contract open where the tree had already closed it.** "Drop the target or run a boot

  narrowing this milestone exists to stop. Dropping a target is the planner's, before the plan is
  final.
- **M0 did not notice that a keyless step is unmeasurable BY CONSTRUCTION.** `record_step` returns

- **M2 asked for `covers` and called it evidence.** A `covers` line is a claim about what a test

- **M3's per-run list was short and its log rule was wrong on one target of three.** Missing: the

- **M4's per-gate costs are not missing, they are invented.** `record_step` divides a merged step's

- **M4 put prerequisites outside the budget,** which makes `--budget 10` a run that spends forty
  minutes building and then declines to test.
- **M5 cited one bar when there are two.** `trust.rs` asks `TestGuest` for two targets; the registry
  asks `src/kernel/mem` for three and `src/kernel/syscall` for an unchanged ABI on top. The general

- **M5 said "activate that candidate" without saying how it is checked.** Activation compares hashes
  or it is a claim about intent.

  configuration catalog, the graph, the feature definitions, the arch-risk table and the catalog
  itself with every check's `covers`. Narrowing changes registry ownership AND the `covers` in the
  kernel tests' sources, so a candidate that is not an overlay of both can never hash identically at
  activation - which turns the strictest step of M5 into an unsatisfiable one.
- **The fourth `risk_class` field had no producer.** Nothing observes that a change was "an
  allocator change": `change_kinds` says how a component was reached, not what the edit was about.
  The groups are declared as names and paths, the matched ones are recorded, and a group matching no
  tracked path is refused. `the ABI unchanged` is given one meaning.
- **A registry row promises what the discovery cannot do.** `src/kernel/test_suites` says the row
  disappears once `covers` is on every test. It is - 370 of 370 - and the row is still there, because
  a `Declaration` carries no source path.

What was rejected: a `group -> paths/specimen/gate` mapping, where the last two are machinery for a
problem the paths already solve; and picking the boot check's catalog id here, which is a naming
decision for the catalog and not a value this document should fix. What was accepted from the same
finding is that an id is not a measurement, and saying so beside a cold-start seed was lumping two
different kinds of open question together.

### And the sixth round

Reviewed again on 2026-08-28, against the fifth round's own text. Four of the six findings are about
sentences the fifth round wrote, which is what a review is for.

- **The cold-start seed was derived from the estimate that is zero for exactly this case.**
  `full_suite_seconds` prices the tests the model DISCOVERED, and a target it could not enumerate has
  none - so the seed for the unenumerated step would have been the fixed boot term alone. The count
  that exists for such a target is the test ids declared in source, which is an upper bound.
- **"Discard the costs, keep the freshness" is true only for a step that passed.** `check.sh` stops
  at its first failing gate and `record_step` stamps every key of the step. The sweep on this same
  day recorded forty-five gates as run and failed when five had run - so keeping the freshness of a
  failed merged step means forty gates that never started count as recently checked.
- **`StepId` was introduced without saying when two of them are the same work.** An identity that
  contains the `RUN_ID` has no history; one that omits the selection merges two different jobs into
  one cost. And a dependency graph nobody validates lets a scheduler wait on a step that was never
  emitted.
- **The activation hash compared a model with itself.** "The candidate planner and the active planner
  read the same overlay" makes step 4 a tautology. The candidate reads canonical plus the frozen
  overlay; activation materialises it; the active model is re-read from canonical files alone; that
  hash is the one compared.
- **`source_path` had to be `source_paths`.** The scanner already merges several arch-gated
  declarations of one test id, and a single path keeps whichever file was read last.
- **"The changed paths and their content" does not answer a delete or a rename.** The digest is over
  sorted `(change kind, path, before or ABSENT, after or ABSENT)` tuples, and a rename contributes
  both ends.

Plus one editorial slip: a sentence still compared the measured cost against "a claimed 75 s" after
the plan output above it had been re-measured to 87 s.

Nothing was rejected this round. Every finding was a correction to a contract this document states
rather than a proposal to add one, which is the difference between this round and the last two.

### And the seventh round

Reviewed with P02M0099 on 2026-08-28. Three findings, all structural, and none of them about a
measurement.

- **The items had no dependency order and their written order is wrong.** M1's gate reads a result
  log back and M2's oracle asserts on an external effect in one - both of which are M3.3's per-run
  RESULT log. Written in the order they appear, M1 and M2 would be built against the newest log of an
  architecture, which is the read this milestone exists to stop. The order is now stated.
- **"The full sweep is unchanged" forbade the fix.** `--sweep` runs `build`, then `check`, then
  `test`, and `capability-trace` is a check reading a log only a test produces - the ordering defect
  this milestone measured. A definition of done freezing the order would have made the fix a
  violation of it. Unchanged means the same COVERAGE.
- **The Definition of done contradicted M5's own contract, and activation was not atomic.** One
  bullet still said the candidate and active planners "read the same one" after M5 had been corrected
  to say the opposite. And an activation that materialises the overlay before the hash is compared can
  fail with the canonical files already overwritten, so a refusal now has to leave every input
  byte-for-byte as it was.

Held from the previous round rather than conceded: the boot check's catalog id is still not chosen
here. An id is a naming decision taken in the catalog change that adds the check, and a milestone
that picks one is choosing a name for code nobody has written. The COLD-START SEED, which the same
finding bundled with it, is a measurement and does now have its formula.

### And the eighth round

Reviewed on 2026-08-28 with P02M0099. Three findings, all contracts rather than measurements, and one
of them is about a word.

- **M2 used the driver's readiness state for services.** A driver reaches `Online`; a service reaches
  `Ready`, which is ServiceManager's own state and its own definition - "started, reported in, and
  serving". The census in this item covers both, so half of it would have asserted on a state that
  does not exist there. The definition of done now asks for the negative case on one of each rather
  than on a driver alone.
- **"Read-only" was doing work it cannot do.** The shared fixture media are read-only TO THE GUEST,
  and `qemu-run.sh` regenerates them into the shared path whenever their content key does not match -
  so two runs starting on a stale fixture both rebuild it and one guest can open it half-written.
  Immutable during the run is the property; it needs one locked preparation step that finishes before
  any guest starts, and no guest path regenerating a fixture of its own.
- **`--release` and `--sweep` are flat by design and the planner cannot reach them.** `--release`
  says why in its own comment: it consults no model and reads no plan, because it is what runs when
  the thing that makes choices is broken. So fixing the dependency graph fixes ONE of three full
  paths, and the other two are corrected where their sequence is written. FOUR PLACES, NOT THREE:
  `planner_failed` prints the same order as advice - "run the whole thing yourself: ./build.sh --arch
  all && ./check.sh && ./test.sh --arch all" - which is the sequence a person reaches for exactly
  when the planner cannot be trusted to have got it right.

Also corrected: the header said six rounds with a seventh already in the file.

### And the ninth round

Reviewed on 2026-08-28. No implementation blockers left; three corrections, two of them to the eighth
round.

- **"One guest can open it half-written" was wrong about the code.** `qemu-run.sh` builds each
  fixture into a candidate and publishes it with an atomic rename, so it is never torn. The real risk
  is a GENERATION SWAP - a guest opening a whole, valid fixture that is not the one its own run staged
  against. The locked preparation step is the right fix for both readings, which is why a wrong reason
  had not produced a wrong requirement; it would have produced a wrong test.
- **M0 read as forbidding the catalog change from choosing the id.** It is a naming decision and that
  change is exactly where it belongs. The seed is the half that must not be invented.
- **The wrong order is written in FOUR places, not three.** `planner_failed` prints
  `build && check && test` as its recovery advice - the sequence a person reaches for precisely when
  the planner cannot be trusted, which makes it the worst of the four to leave stale.

### And the tenth round

Reviewed on 2026-08-28. Three findings, and all three are about a guard that protects the wrong thing
rather than about a missing one.

- **The activation hash is checked at one end only.** Comparing the RESULT says nothing about the
  base: an activation that overwrites a `registry.toml` edited in the meantime still produces the
  hash the candidate predicts, because the overlay decides it. The check passes while destroying an
  unrelated change and certifying a model nobody reviewed. The candidate carries the digests of what
  it was frozen against, and activation verifies them before its first write.
- **A preparation lock does not make a fixture immutable.** `media_publish` renames onto a FIXED
  path, so any later invocation can replace the file between preparation and a guest opening it -
  atomically, and therefore invisibly. The path has to carry the generation. With a content-addressed
  name, two generations are two files and the lock is left doing what a lock is good at: stopping the
  same name being built twice, which is cost rather than correctness.
- **A second scheduler already exists and predates the first.** `test.sh --arch all` runs three
  architectures concurrently, says so in its own comment, and `--release` calls it from outside the
  planner - so "exactly one answer to how many guests may run" was false before M3 added anything.
  Safe today because the media are per-architecture, which is a different property from being
  scheduled.

### And the eleventh round

Reviewed on 2026-08-28. One finding, and it is this document doing the thing it keeps catching other
people doing.

- **The second-scheduler item named two answers and picked neither**, in the item and again in the
  definition of done - "one limiter both paths take, OR that flat path serialised". An open `or` in a
  contract is a decision handed to whoever implements it, which is exactly what the previous ten
  rounds have been closing elsewhere. Chosen: the flat paths run one architecture at a time and
  `verify.sh --jobs` is the only scheduler. A shared limiter was the wrong half - the flat path's
  value is that it consults nothing, so giving it something to consult removes the reason it exists.

## What this milestone refuses, and why

- **Deleting a test, or skipping one QUIETLY.** Nothing here removes a test, and every change is
  about WHICH of them a given question needs - a question that needs all of them still gets all of
  them. The word that matters is quietly: `--budget` skips work by design, which is why its contract
  requires it to print what it did not run and to exit `INCOMPLETE`. What is refused is a run that
  trims its own scope without saying so, or an `INCOMPLETE` presented as a passing verification.
- **Narrowing the kernel model on judgement.** That is M5's whole point, and phase one already
  declined to do it without evidence.
- **A second, weaker trust criterion.** `trust.rs` already decides what evidence earns a narrowing.
  A milestone that wants a narrowing meets that bar or moves it in the open.
- **A distributed or remote runner.** The machine has a hundred cores and uses one; there is nothing
  to distribute until that is false.
- **Per-test process isolation inside the guest.** The guest boots once and runs a suite; making each
  test its own boot would cost more than everything above saves.

## Results (2026-08-28)

The defect this milestone is named after, before and after, on the change that produced it:

```
$ ./verify.sh --for src/user/drivers/core/src/virtio_input.rs --plan
before:  9 of 1201 keys, estimated 75 s - and the run did ./test.sh --arch x86_64, the WHOLE suite,
         about 190 s, under a step carrying ZERO keys
after:  10 of 1223 keys, estimated 72 s - and the run does ./test.sh --arch x86_64 --tags smoke,
        one key, the boot check the plan names
```

**M0.** Three states, three answers, all in the planner. `guest.boot-smoke` and `guest.whole-suite`
are catalog checks with ids, variants and somewhere for a measured cost to live; `select` never picks
them, because their reason is a fact about the plan rather than about coverage. The keyless step is
gone - `record_step` returns on an empty key list, so the largest item in a driver plan could never
acquire a cost however many times it ran. The near-full widening moved out of the step builder,
where it ran the whole suite while attaching only the selected keys: the plan said 195 and the run
did 205. Every step now carries a `StepId` - kind, architecture, configuration and what it was asked
to do, digested when that is two hundred ids, and never a run identity. The cold-start seed comes
from the test ids the SOURCE declares, because `full_suite_seconds` counts what was DISCOVERED and a
target that could not be enumerated has none - so the obvious source priced the one case it exists
for at the cost of booting and running nothing.

**M1.** The rule is written where tags are declared, next to `tagged_test!`. `check-gate-oracles.sh`
refuses a gate naming a test id the tree no longer declares - watched to fail on a renamed id, where
the grep matches nothing and an assertion that is an ABSENCE reports the profile as proven.

**M2.** A census, not an example. `check-component-oracles.sh` enumerates every staged driver and
service from the manifest and demands a test that names it or a written reason. The first run said
25 of 26 had neither. Eleven were closed with annotations of tests that already assert the effect -
and the model REFUSED sixteen more, correctly: `covers X` implies the test can reach X, reach is the
forward closure of what a body LAUNCHES, and a test asserting a driver's effect never launches the
driver - DeviceManager binds it at boot. Those fifteen are recorded with the test that does guard
them, which is a different thing from an excuse. Closing them needs the reach relation to include the
boot chain. Two more are honest gaps: nothing in the suite fails when `session_service` or
`time_service` breaks.

**M3.** The suite's own medium carries its content key, so two selections are two files - it was one
fixed path, rebuilt per selection, published by a rename that is atomic and not private. Every
writable image a guest touches is this run's own copy from an immutable template; the fixtures it
reads are attached `readonly=on`, which they were not, and the storage suite's 50 tests pass that
way. `test-kernel.sh` prints `RESULT-LOGS`, both files, because the oracle is in the run log on
riscv64 and the guest log on the other two - and `check-gate-result-logs.sh` refuses the glob coming
back. Each of the eight interrupt profiles is its own step with its own key. `verify.sh --jobs`
bounds guests and defaults to one; the flat `--release` and `--sweep` paths run one architecture at a
time, because `test.sh --arch all` was a second scheduler older than the first.

**M4.** Steps carry their prerequisites by id, and the gates split in two: `capability-trace` reads a
log only a guest produces and compares it against a binary the build just refreshed, so ordered
before the guests it could not pass however clean the tree was - measured twice, the second time with
a trace confirmed green minutes earlier. The plan is ordered cheapest-first WITHIN dependency layers.
`--budget` prices whole prerequisite-closed branches, prints every skipped step, exits INCOMPLETE,
and is refused by the three modes that mean "all of it". Every cost invented by dividing a merged
step's duration is discarded once - all 1661 of them, because the marker that tells a measured cost
from a divided one did not exist when they were written and a migration that has to guess would
throw away the good ones too.

**M5.** A candidate is a complete overlay of BOTH narrowing inputs, because `model_hash` covers the
registry text AND the catalog with every check's `covers`. Activation verifies the digests of the
canonical inputs it was frozen against BEFORE its first write, re-reads the active model from those
files with no overlay in its path, compares only that hash, and rolls back byte for byte. Both
refusals were watched: a moved base leaves the tree untouched, and a hash mismatch restores it.
Distinctness is keyed on WHAT CHANGED - sorted `(kind, path, before, after)` tuples - and the test
that proves it fails with `left: 1, right: 5` without that key, which is the deadlock exactly: a
frozen subsystem candidate produces one decision for every change inside it. The rule it replaces is
still honoured: five runs of one change are still one piece of evidence. `risk_class` has the four
fields its prose describes, change groups are declared as a name and its paths, and the model refuses
a group that matches nothing - which caught three wrong paths the moment it was written.

### What this milestone leaves for somebody else, named

- **The reach relation does not include the boot chain**, so fifteen drivers and services have an

- **`session_service` and `time_service` have no oracle at all.** Enumerated rather than decided.
