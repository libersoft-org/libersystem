# P02M0167 - The selector answers "everything" to every question, so nobody asks it

Status: PLANNED. VERIFICATION ECONOMICS. NOT A NEW CHECK, AND NOT A REDUCTION IN WHAT IS CHECKED.

Revised 2026-08-27 after an external review. Three of the five items had a premise that did not
survive being run against the tree; what replaced them is below, and the paragraph
"What the first draft of this milestone got wrong" says which and why, because a milestone that
quietly corrects itself teaches nothing.

## Goal

Make the verification a caller can run after a change cost what that change is worth, without
checking less than the change needs.

The claim this milestone may make: after it, a change to one driver does not run the whole x86_64
kernel suite while reporting that it runs 1% of one, a machine with a hundred cores does not verify
on one, and a selector that narrows can say what evidence entitles it to. It does NOT make the full
sweep cheaper - the sweep is supposed to be expensive - and it does not remove a single test.

## What is there now

Measured 2026-08-27 against the tree, by running the planner, not by reading it.

- **THE PLAN AND THE RUN DISAGREE, AND THE PLAN IS THE OPTIMISTIC ONE.** This is the finding the
  first draft missed and the one that decides the milestone. For a change to one driver:

      $ ./verify.sh --for src/user/drivers/core/src/virtio_input.rs --plan
      9 of 1201 runnable keys selected.
      estimated 75 s against 8742 s for everything - 1% of a full run.

      $ ... verify-model commands --stdin
      STEP  3  0  kernel suite x86_64 (unenumerated)  ./test.sh --arch x86_64

  The plan contains no guest test at all, and the command list ends with the WHOLE x86_64 suite.
  The step carries zero keys, so it costs zero in the estimate and records nothing in the history:
  a run whose largest item is invisible to the model that ordered it.

  The fallback is not a bug in itself - it was added so that a target the model cannot enumerate is
  booted rather than assumed clean, which is right. It fires on the wrong condition. `kernel_by_arch`
  is built from the SELECTED kernel tests, so "no tests selected on a booted target" and "this
  target's tests could not be read" are the same state to it, and the note it prints - *"the model
  could not enumerate this target's tests"* - is false in the first case. Enumeration worked. The
  selection was empty, which is a different fact with a different answer.

  On x86_64 the cost is about 190 s against a claimed 75 s. On an emulated target the same shape
  would be about 3100 s (aarch64) or 3700 s (riscv64) against a claimed zero.

- **THE SELECTOR WORKS WHEN IT HAS ANYTHING TO SELECT.** Verified rather than assumed, because the
  first draft asserted the opposite:
  - `virtio_input.rs` -> 9 of 1201 keys: three builds on three targets, no guest test.
  - `imgconv.rs` -> 11 of 1201 keys: the same builds plus EXACTLY the two imgconv tests.
  - `audio-client-provider/src/lib.rs` -> 12 of 344/347/356 tests, handed to each target by id.

  So the component model is not the thing answering "everything". The kernel is - deliberately, see
  below - and the zero-key fallback is.

- **THE KERNEL IS ONE COMPONENT, ON PURPOSE.** The planner says so itself: *"phase one keeps shared
  kernel subsystems whole - narrowing mem/sched/object/syscall is where a selector is most likely to
  be wrong, and it is deferred until there is shadow evidence per change class."* `verify-model
  check` lists seven subsystems as declared-narrowable and not narrowed. The deferral is right. What
  is missing is anyone producing the evidence it waits for, and a way to produce it that is not
  circular - see M5.

- **GATES RUN BROAD SUITES TO ASSERT NARROW THINGS.** `qemu-arch-profiles` ran
  `--tags boot,smp,interrupt,paging,scheduler,drivers,memory` on eight interrupt-controller profiles
  to assert five named tests. `memory` carries
  `kernel.applications.imgconv_governed_working_set_is_measured`, which costs **1149 seconds** on an
  emulated aarch64 - 83% of a 23-minute profile, eight times, two and a half hours per gate.
  `qemu-numa` had the same shape with `--tags memory,smp` for seven named tests, with the narrow tag
  it needed used three lines below in the same file. BOTH ARE FIXED; they are described here because
  they are the pattern, not the exception, and the next gate will do it again unless the shape is
  named.

  THE TAG WAS NOT THE DEFECT. `imgconv_governed_working_set_is_measured` asserts on the measured peak
  of three conversions, on the 4K peak fitting the production quota, and on a conversion under an
  80 MB Domain failing with a typed diagnostic while leaving its destination byte-for-byte intact.
  That is memory governance. It belongs in `memory`. What was wrong was a gate about interrupt
  controllers asking for a whole subject tag when it wanted five named tests.

- **ONE GUEST AT A TIME ON A HUNDRED-CORE MACHINE.** Measured during a profile run: load average
  1.39, one `qemu-system-aarch64` at 108% CPU. `verify.sh` runs its steps in a serial
  `while IFS=$'\t' read -r -u 3` loop - no `&`, no `wait`, no `-P` anywhere in the file - and the
  profile gates run their profiles one after another. So the serialisation is in the RUNNER, and the
  shared writable images are what would make fixing the runner unsafe:

      per run already:  esp-<arch>.$$.img, the firmware variables
      shared, fixed:    virtio-blk-<arch>.img, fat-media<suffix>.img, usb-media<suffix>.img,
                        iso-media<suffix>.iso, system-volume-<arch>.img
      shared, fixed:    virtio-console<suffix>.out - the guest's own console capture
      shared, fixed:    dev-channel-<arch>-test.sock, qemu-monitor.sock, qemu-qmp.sock
                        - and every one of them is `rm -f`-ed at startup, so a second guest does not
                          collide with the first, it DELETES it
      discovered:       the gates find their log by globbing `.build/logs/test/<arch>-*-guest.log`
                        and taking the newest

  The last line is the dangerous one and the first draft did not name it. Two guests of one
  architecture in flight, and a gate can read the other one's log and pass.

  AND "THE GUEST LOG" IS NOT ONE FILE ON ALL THREE TARGETS. `test.sh` says so itself: *"on riscv64
  it lands in the RUN log while the guest log holds only U-Boot and the loader. Read the guest log
  alone on riscv64 and a healthy run looks hung before its first line."* So a runner that returns
  "the log it wrote" returns the wrong file on one target of three, and the fix is a per-run
  RESULT log - the one carrying the oracle - not a per-run guest log.

  AND THE CANONICAL DISKS ARE NOT CLEAN. A guest writes to them, so copying the shared image per
  run copies whatever the last guest left in it. Per-run isolation has to start from an immutable
  template or it propagates contaminated state instead of sharing it.

- **THE ESTIMATE IS USED FOR ONE THING AND NOT THE OTHERS.** The first draft said it is never used,
  which is wrong. `plan.rs` uses it to WIDEN: per (architecture, environment) pair, where there is a
  boot to amortise, a selection costing more than 0.9 of the whole pair takes the whole pair. That
  rule is sound and the comment above it is worth reading. What the estimate is not used for is
  ORDER - a plan that will fail runs its cheapest evidence last - and there is no way to ask for a
  bounded run at all.

- **AND THE GATES ARE ONE STEP, SO THEIR COSTS ARE FICTION RATHER THAN ABSENT.** Every selected gate
  is collapsed into a single `./check.sh --gate a,b,c,...` step carrying all their keys, and
  `record_step` distributes a step's wall clock EVENLY over the keys it discharged. So the history
  does not lack per-gate costs - it holds one invented number per gate, each equal to the merged
  step's duration divided by however many ran together. A cheapest-first order taken from those
  would be sorting on an artefact of how the gates happened to be batched.

- **AND A STEP WITH NO KEYS RECORDS NOTHING AT ALL.** `record_step` returns on an empty key list.
  The unenumerated full-suite step above carries none, so the largest item in a driver plan is
  invisible to the estimator that ordered it, permanently and by construction.

- **THE BUILD FAN-OUT IS THREE TARGETS WHATEVER IS BOOTED.** The driver change above builds
  `packages,user,volume` on aarch64 and riscv64 and boots neither. This is DEFENSIBLE - an
  arch-specific compile error is a real defect and a cheap one to find - and it is recorded here as
  an unmeasured cost rather than as work, because nothing has measured whether it is cheap.

## Work

- [ ] **M0 - the zero-key fallback stops running a suite it does not account for.** This is the item
  the rest is worth nothing without, and it is small.

  Three states, three answers, and the first draft left the third open where it had no business
  being open - the architecture policy has ALREADY decided which targets a change boots, and
  lowering a plan to commands is not the place to overrule it:

  | the model | the answer |
  | --- | --- |
  | could not enumerate this target's tests | today's behaviour: boot whole, today's note. Booting blind is the safe answer to a model that cannot see. |
  | enumerated them and selected none, but the target is booted | a named boot/smoke check FROM THE CATALOG, with its own key and its own cost |
  | the target need not be booted at all | the PLANNER drops it, before the plan is final. Never the lowering. |

  AND THE UNENUMERATED STEP GETS AN ACCOUNTABLE KEY OF ITS OWN. `record_step` returns early on an
  empty key list, so a step carrying none is invisible to the history for ever - which is how the
  most expensive item in a driver plan came to cost zero in the estimate that ordered it. A step
  that runs is a step that is measured.

  THE GATE FOR THIS is a test that lowers a plan to commands and asserts that every step carries at
  least one key, and that the plan's estimate covers what the commands will run.

- [ ] **M1 - `tags` and `covers` are different instruments and the tree says which is which.** The
  first draft treated tags as the selector's handle. They are not: `verify-model`'s `select` reads
  `covers` and never looks at a tag. Tags serve `./test.sh --tags` and the gates.

  So this item is not a retag. It is a written rule and the two consequences of it:

  - `covers` answers *what would this test catch*, for the change selector. It is already on all 369
    kernel tests and `verify-model check` enforces that.
  - `tags` answer *what subject is this test about*, for a person or a gate asking for a group. A
    test may carry several honestly.
  - **A GATE ASSERTING N NAMED THINGS ASKS FOR THOSE N THINGS.** `TEST_SELECTION` exists, takes ids,
    and hard-fails on an id it does not have. A gate that wants five tests and asks for a subject tag
    is buying every test that subject will ever acquire.

  THE GATE FOR THIS IS NOT A COUNT. Counting tests per tag before and after proves movement, not
  correctness. What each gate must prove is that ITS OWN oracles are still selected: the gate names
  the ids it asserts on, and a check reads the result log back and fails if one of them did not run.

  THIS APPLIES TO GATES BUILT ON CATALOG KERNEL TESTS, and only to those. A host-only gate and one
  that asserts directly on an artifact have no test ids to name, and demanding some of them would be
  a rule satisfied by inventing them.

- [ ] **M2 - the guest step is derived from what a change can break, and a `covers` line is a claim
  rather than the evidence for it.** `build.volume` covers some two hundred components because the
  volume contains every binary. The first draft read that as "therefore every guest test runs", and
  the plans above show it does not - the wide `covers` drives BUILD FRESHNESS, which is correct and
  must stay: drop it and a guest boots the previous userspace, which makes every result taken on it
  meaningless.

  What is missing is the positive half. A driver change selects no guest test at all, and M0 stops
  that from silently becoming the whole suite - but "runs nothing" is not the right answer either.

  SO THE WORK IS AN ORACLE, NOT AN ANNOTATION. Writing `covers = ["bin.virtio_input"]` on a test
  that never asserts anything which fails when that driver breaks moves the plan and changes nothing
  about what is caught - it is the tag mistake of M1 wearing the other instrument's clothes. Each
  driver and service needs a runtime oracle that actually fails: the binding for that device reaches
  `Online` and its provider answers. THEN the `covers` line naming it is true.

  DEFINITION OF DONE FOR THIS ITEM IS A CENSUS, NOT AN EXAMPLE. Every staged driver and service has
  at least one runnable oracle naming it, or a declared exception saying why it has none. One driver
  demonstrated proves the mechanism and not the coverage.

- [ ] **M3 - one run identity, then parallelism, and the guard learns to tell runs apart.** In this
  order, because the second is unsafe without the first.

  1. A `RUN_ID` per guest covering everything a run writes, listens on, or reads back: the data
     disks, the FAT, ISO, UDF and USB media, the system volume copy, the guest's console capture,
     the dev-channel socket, and the monitor and QMP sockets. Today the ESP alone is per-run and
     every socket is `rm -f`-ed at startup.
  2. FROM AN IMMUTABLE TEMPLATE, not from the canonical disk. A guest writes to its images, so
     copying the shared one per run copies whatever the last guest left in it - which turns one
     contaminated disk into N contaminated disks and calls it isolation.
  3. The runner RETURNS the path of its RESULT log - the one carrying the oracle - and gates take it
     as an argument. Not "the guest log": on riscv64 the suite's output lands in the RUN log while
     the guest log holds only U-Boot and the loader, so a runner returning the guest log returns the
     wrong file on one target of three. Globbing for the newest log of an architecture is a
     correct-looking read of another guest's result.
  4. `verify.sh --jobs N`, which owns the parallelism: builds and other prerequisites complete before
     any guest starts, guests run up to N at a time, every step is waited for, and the failures are
     aggregated rather than the first one winning.
  5. AND THE PROFILE GATES ARE THE EXPENSIVE CASE, so `--jobs` alone does not touch them.
     `qemu-arch-profiles` runs eight profiles serially INSIDE one step; parallelising the steps
     around it changes nothing. Either each profile becomes its own step, or the gate takes a
     bounded `--jobs` of its own.
  6. `verify-history.json` is written by ONE writer. Parallel steps recording into it concurrently
     is a lost-update race in the file the estimator reads: the parent collects results and writes
     them serially, or there is a lock, and which one is a choice - having neither is not.
  7. `test.sh`'s stray-guest guard - which today refuses when ANY `qemu-system-<arch>` holds a file
     under `$BUILD_DIR` - refuses only for a guest holding THIS run's files.

  THE FAILURE MODE HERE IS THE WORST ONE THIS TREE HAS: two guests writing one image is a result that
  is green and means nothing. So the guard's new rule gets a test that watches it refuse a real
  collision, not only accept a real parallel pair.

- [ ] **M4 - the plan is ordered by cost and can be given a budget, with a contract.**

  Ordering: cheapest-first among the steps whose prerequisites are met, so a real defect surfaces in
  minutes rather than at the end of a sweep.

  BEFORE ANY ORDERING IS TRUSTWORTHY, THE FABRICATED COSTS GO. The gates are one merged step and
  `record_step` splits a step's duration evenly over its keys, so every per-gate cost on disk is
  that step's duration divided by however many gates happened to be batched with it. Ordering on
  those is sorting on the batching. Emit and time each gate separately, and DISCARD the existing
  per-gate entries rather than letting the first cheapest-first run inherit them.

  `--budget SECONDS` is in ESTIMATED seconds and is not a timeout - it decides what to start, never
  what to kill. Its contract:

  - THE BUDGET COVERS THE PREREQUISITES. Putting builds outside it, which the first draft did, makes
    `--budget 10` a run that spends forty minutes building and then declines to test. What is
    costed is a whole prerequisite-closed branch: the step and everything it needs.
  - if the cheapest complete branch does not fit, run NOTHING and say what the minimum would have
    been - a budget that half-builds has spent the time and bought no evidence;
  - among affordable branches, take the cheapest;
  - a merged step is never split to fit;
  - every skipped step and key is PRINTED;
  - the run exits with a distinct non-zero `INCOMPLETE` status, never a green;
  - `--sweep`, `--release` and `--shadow` refuse a budget outright.

  A selector that quietly trims its own scope is the defect P02M0156 is named after, and a budget is
  that defect with a flag on it unless every one of those holds.

- [ ] **M5 - the narrowing is EARNED, by a candidate model, under BOTH bars that already exist.**

  The ordering argument in the first draft stands and is the point of the item: gather the evidence,
  then split. What it did not say is how, and taken literally it cannot be done - while `kernel`
  selects everything, `--shadow` compares FULL against FULL and proves nothing about a narrower
  model. Worse, splitting changes the registry and the catalog and therefore `model_hash`, and
  evidence bound to the old hash is correctly discarded. Evidence first, split second, and the split
  destroys the evidence.

  A CANDIDATE MODEL BREAKS THE CIRCLE:

  1. The candidate is a FROZEN, VERSIONED input - a model file, not a flag - and it computes the
     narrower selection.
  2. The authoritative run is still FULL: nothing is skipped while evidence is being gathered.
  3. The comparison is recorded against the CANDIDATE's `model_hash`.
  4. Activation CHECKS THE HASH. The model that becomes active must hash identically to the
     candidate the evidence was gathered under, and activation is refused otherwise. Without that
     check "the same candidate, activated" is a claim about a human's intention.

  AND TWO BARS HAVE TO BE MET, NOT ONE. `trust.rs` carries the general threshold - five distinct
  clean comparisons per scope pair, at least one `shadow-exec`, and `required_architectures`, which
  for `TestGuest` is TWO. The registry carries a per-subsystem one: `src/kernel/mem` says
  *"shadow-clean on all three targets"*, and `src/kernel/syscall` adds *"plus the ABI unchanged"*.
  The general bar is the weaker of the two for exactly the subsystems that matter most, so meeting
  it is necessary and not sufficient. Activation checks the `risk_class.evidence` condition as well,
  and the condition has to be machine-checkable to be checked - which is itself part of this item.

  A PRECONDITION NOBODY HAS DONE: most kernel tests declare `covers = ["kernel"]`. A narrower kernel
  model that they all still cover selects everything anyway. Subsystem-level `covers` on the kernel
  tests is part of this item, not a follow-up to it.

## Definition of done

- Every step in a lowered plan carries at least one key, and the plan's estimate covers what the
  commands actually run.
- A change to one driver selects a runtime oracle that FAILS when that driver breaks, does not
  contain the image, audio or LiCo suites, and does not fall back to a whole suite.
- Every staged driver and service has at least one runnable oracle naming it, or a declared
  exception saying why it has none.
- A change to one application selects that application's suites and the integration tests that
  exercise it, and not the kernel's object or scheduler suites.
- Every gate built on catalog kernel tests names the ids it asserts on, and a check reads the result
  log back and fails if one of them did not run.
- No gate sets a timeout tighter than the stall detector that decides whether a run is wedged.
- Guests of one architecture run in parallel with no shared writable file and no shared socket, each
  built from an immutable template, each consumer reading the result log its own run produced, one
  writer to the history, and a test that watches the guard refuse a genuine collision.
- The profile gates run their profiles concurrently, by whichever of the two routes is chosen.
- `--budget` costs whole prerequisite-closed branches, starts nothing it cannot finish, exits
  INCOMPLETE naming what it skipped and what the minimum would have been, and is refused by
  `--sweep`, `--release` and `--shadow`.
- No per-gate cost derived from a merged step survives into the first cheapest-first run.
- A narrowing activates only when the active model hashes identically to the candidate its evidence
  was gathered under, AND both `trust.rs`'s threshold and that subsystem's `risk_class.evidence` are
  satisfied.
- The full sweep is unchanged and still runs everything.

## What the first draft of this milestone got wrong

Kept deliberately: a milestone that silently corrects its own premises teaches nothing, and two of
these were argued confidently from a reading of the code rather than from running it.

- **"A tag is the selector's only handle on a test."** It is not a handle at all. `verify-model`
  selects on `covers`. Retagging cannot change a `verify.sh` plan, only what `--tags` and the gates
  pull. M1 is rewritten.
- **"`imgconv_governed_working_set_is_measured` is tagged `Memory` because it allocates."** It
  asserts on peaks, on a Domain quota, and on an out-of-memory failure preserving its destination.
  The tag was true; the gate asking for the whole subject was the defect. The tag was removed on
  2026-08-27 and put back the same day.
- **"The volume's wide `covers` implies every guest test."** It implies every BUILD, which is what it
  is for and must stay. Measured: a driver change selects 9 of 1200 keys and an imgconv change
  selects 11, including exactly the two imgconv tests.
- **"The estimate is printed and never used."** It is used to widen a selection to a whole
  (architecture, environment) pair above a 0.9 cost ratio. It is not used to order, and there is no
  budget.
- **"The disks simply were not copied."** The disks, the media, the volume copy, the dev-channel
  socket, the monitor socket and the QMP socket - and the log the gates read is found by globbing,
  which is the part that could produce a green from another guest's run.
- **Missed entirely:** the zero-key full-suite fallback, which is now M0 and is the largest single
  gap between what a plan says and what a run does.

### And what the SECOND draft got wrong

Reviewed again on 2026-08-27, and these are the ones that survived the first correction.

- **M0 left the contract open where the tree had already closed it.** "Drop the target or run a boot
  check" is not a choice the lowering may make: the architecture policy decided which targets a
  change boots, and a step that quietly declines to boot one is the same class of unilateral
  narrowing this milestone exists to stop. Dropping a target is the planner's, before the plan is
  final.
- **M0 did not notice that a keyless step is unmeasurable BY CONSTRUCTION.** `record_step` returns
  on an empty key list, so the fallback could never have acquired a cost however many times it ran.
- **M2 asked for `covers` and called it evidence.** A `covers` line is a claim about what a test
  would catch. A test that never asserts anything which fails when the driver breaks satisfies the
  annotation and catches nothing - the M1 mistake, in the other instrument.
- **M3's per-run list was short and its log rule was wrong on one target of three.** Missing: the
  ISO medium and the guest's own console capture. Wrong: "the log the runner wrote" is the guest
  log, and on riscv64 the suite's output is in the RUN log - `test.sh` says so in its own header.
  Missing entirely: that a per-run copy of a contaminated canonical disk is a contaminated per-run
  disk, that `qemu-arch-profiles` serialises INSIDE one step so `--jobs` around it buys nothing, and
  that parallel steps writing one history file is a lost-update race.
- **M4's per-gate costs are not missing, they are invented.** `record_step` divides a merged step's
  duration evenly, so every per-gate figure on disk is an artefact of batching. Ordering on them
  without discarding them first is worse than not ordering at all.
- **M4 put prerequisites outside the budget,** which makes `--budget 10` a run that spends forty
  minutes building and then declines to test.
- **M5 cited one bar when there are two.** `trust.rs` asks `TestGuest` for two targets; the registry
  asks `src/kernel/mem` for three and `src/kernel/syscall` for an unchanged ABI on top. The general
  threshold is the weaker one exactly where it matters most.
- **M5 said "activate that candidate" without saying how it is checked.** Activation compares hashes
  or it is a claim about intent.

## What this milestone refuses, and why

- **Deleting a test, or skipping one QUIETLY.** Nothing here removes a test, and every change is
  about WHICH of them a given question needs - a question that needs all of them still gets all of
  them. The word that matters is quietly: `--budget` skips work by design, which is why its contract
  requires it to print what it did not run and to exit `INCOMPLETE`. What is refused is a run that
  trims its own scope without saying so, or an `INCOMPLETE` presented as a passing verification.
- **Narrowing the kernel model on judgement.** That is M5's whole point, and phase one already
  declined to do it without evidence.
- **A second, weaker trust criterion.** `trust.rs` already decides what evidence earns a narrowing.
  A milestone that wants a narrowing meets that bar or moves it in the open.
- **A distributed or remote runner.** The machine has a hundred cores and uses one; there is nothing
  to distribute until that is false.
- **Per-test process isolation inside the guest.** The guest boots once and runs a suite; making each
  test its own boot would cost more than everything above saves.
