# P02M0108 - The loader reads the filesystem: retire the bootstrap archive

Status: COMPLETE (2026-08-03), green on all three architectures.

Nine programs ran on every boot that existed nowhere a user could look: `system_manager`,
`service_manager`, `device_manager`, `virtio_blk`, `storage_service`, `process_service`,
`log_service` and two probes were staged `pinned`, meaning their only copy was an entry inside
`init.pkg` - an archive, not a file at `libexec/system_manager.lsexe`. This milestone made the
loader read the filesystem and retired the archive from the boot path.

*Condensed 2026-08-08 to the design, the two prerequisites nobody had accounted for, and the risks
that are still real.*

## What it does now

The loader has a `fs_core::BlockDevice` over the firmware disk protocol with LiberFS linked in, and
FAT linked read-only so the boot volume is optional. It **discovers** the system volume by examining
every block device the firmware reports rather than hard-coding one. The bootstrap set is a
manifest-named list read file by file from that volume, and the nine programs are staged at real
paths under `libexec/`.

`init.pkg` and `volume.pkg` are gone from the boot path and from the shipping media. Both still
exist as build artifacts, so the milestone's own comparison remains runnable.

All three architectures boot through the loader - on riscv64 U-Boot starts it - and the
`boot-packages-<arch>.pkg` wrapper and the magic scan that found it are retired.

**Two images, two purposes** (decided 2026-08-03): IMG and QCOW2 on every architecture, ISO on
x86_64 only.

## Two prerequisites this milestone had not accounted for

**The loader had no allocator.** LiberFS and FAT are `no_std` but not allocation-free - between them
they use `Vec`, `Box` and `String` in nearly two hundred places, because a directory walk and a file
read are sized at runtime. `src/loader/src/heap.rs` is a bump allocator over firmware pages that
never reuses memory, and that is the right shape rather than a shortcut: the loader runs once and
ceases to exist at `ExitBootServices`, so a free list would cost code and bugs to reclaim memory
nothing lives long enough to need. It is retired at `ExitBootServices` on all three architectures,
so an allocation after that point fails loudly instead of handing out memory the loader no longer
owns.

**There was no LiberFS volume on the disk at boot.** The disk carried `volume.pkg`, a factory
archive at LBA 0, and the storage service formatted a volume and seeded it from that archive *after*
boot - so at the moment the loader ran there was no filesystem to read. The first boot with this
work reported `no LiberFS volume on any block device` and fell back to the ESP. `src/tools/mkvolume`
now builds a LiberFS image on the host **from the same `liberfs` crate the loader and the storage
service use**, so a built image and a runtime-formatted volume are the same format because they are
the same code. It mounts the image and reads back every file it wrote before writing it out: a
volume that formats but does not mount is worth catching on the build host rather than on a machine
that will not boot.

## Risks worth naming, still true

- **The loader is now privileged code that parses on-disk structures.** In a system whose whole
  argument is that drivers are isolated userspace processes, this is a genuine concession. It is
  bounded - read-only, no writes, and it ceases to exist at `ExitBootServices` - but a malformed
  filesystem is parsed by the most privileged code in the boot.
- **Boot cost:** reading nine files from LiberFS is more work than reading one archive, which
  existed partly because it is one contiguous read. Measure it rather than assume.
- **A volume the loader cannot read is now an unbootable system**, where the archive would still
  have brought the machine up far enough to say so. The failure message matters more than usual.
