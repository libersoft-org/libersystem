# P02M0062 - FAT: fifth-pass findings (write-side interop and the last mount nits)

Status: COMPLETE. The fifth full source pass (2026-07-04). Nothing left that corrupts or leaks - two
ways a file we write comes out wrong for its consumers.

*Condensed 2026-08-08.*

**The exFAT NameHash was computed over the name as written, and the specification defines it over the
UP-CASED name.** Windows uses the stored hash as a lookup shortcut and skips any entry set whose hash
does not match its own up-cased computation - so a file written here with any lowercase letter listed
fine in Explorer and **failed to open by name**. That is the crate's core interchange job broken for
most real names. The hash now up-cases each UTF-16 unit before the rotate-and-add.

**A non-UTF-8 name was stored as U+FFFD**, so a lookup by the very bytes the file was created with
matched neither the long name nor the 8.3 form: the write succeeded and the file was unreachable by
its own name, silently. Refused at write; the read side stays lossy for foreign media.

Two smaller ones: the FAT12 slot read-modify-write touched two sectors even when the entry did not
straddle, so it rewrote a sector past the FAT - identical content, but a torn-write window on a
region the operation never meant to touch. And a classic BPB with zero root entries mounted with a
zero-sector root region; refused now, like every other degenerate layout.
