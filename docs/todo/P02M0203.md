# P02M0203 - Boot-capable storage drivers: the system volume's criticality belongs to its binding

Status: PLANNED (2026-10-14; revised 2026-10-15 after the plan audit) - the owner's decision is recorded below;
nothing is implemented yet, by his instruction ("zatim neimplementuj").

THE OWNER'S DECISION (2026-10-14), on the question P02M0099 left when NVMe and AHCI became able to host the
system volume: "souhlasim s doporucenim" - accept the bootstrap-set cost, and move the criticality from the driver
class to the one binding that holds the system volume.

WHY. `lifecycle = "boot-critical"` in `src/user/services/manifest.toml` says two different things at once:
  - WHERE THE DRIVER LIVES AND WHEN IT BINDS - in `init.pkg`, bound in phase one before any volume is mounted. That
    is a fact about the DRIVER: a driver that might have to make the system volume reachable cannot be loaded from
    it. `stage = "pinned"` already says the same thing, and `system-manifest` requires the two to agree.
  - WHAT AN OPERATOR MAY DO - a boot-critical binding refuses `disable`, `enable`, `select` and `retry`
    (`device_manager::decide_policy`, `driver_binding::decide_retry`), because its policy would live on the volume it
    may be needed to mount. That is a fact about ONE DEVICE - the one whose disk is `vol://system`.
Since NVMe and AHCI joined `virtio_blk` in the bootstrap set (2026-10-04), every controller of those three kinds
pays the second price, a data disk included: `lsdev --disable` on a second NVMe answers `refused`. DeviceManager
could not do better as the tree stands. It does not know which binding holds the system volume: StorageService
chooses the disk by the medium's pairing uuid and reports only a per-disk format table. In that table the disk it
serves and every other LiberFS disk read the same, `FORMAT_LIBERFS`.

WHAT STAYS. NVMe, AHCI and virtio-blk remain in the bootstrap set on every architecture. The staged pair of NVMe and
AHCI is about 325 KB on x86_64, 525 KB on aarch64 and 230 KB on riscv64. One image must boot from any standard
controller. The alternatives are more complex and more fragile: an image per machine, or a loader choosing drivers.
A general-purpose initramfs carries its storage drivers the same way.

WHAT DOES NOT CHANGE: WHEN A STORED POLICY TAKES EFFECT.
  - DeviceManager reads stored policy when its owner ConfigService connection arrives (`POLICYCFG`).
  - ServiceManager sends that connection at the end of bring-up, so every driver bound in phase one or phase two is
    already bound by then.
  - A stored disable on a device that is already bound leaves it up and stops it from being bound again
    (`load_stored_policy`, and the check in `begin_bind` before every later bind). The live verb tears a device down at
    once.
That is the rule for every driver today, and it is the rule for the data disks here too. After a reboot a disabled
data disk is bound in phase one, because the record that disables it is on the volume, and it stays up. It is not
bound again after a crash or a retry.

NOT IN THIS MILESTONE. Making a stored disable hold at boot changes the rule for every driver: when the policy is
read, and what happens to a consumer that already holds the device. A disk handed to the media, ISO or UDF storage
instance is a mounted volume of a service that is not restarted. The owner decided on 2026-10-15 that it should hold,
and it is P02M0205, which lands after this milestone and changes item 7's last step.

- [ ] 1. THE BOOTSTRAP PROPERTY IS THE STAGING, NOT A LIFECYCLE.
  - `boot-critical` leaves `system-manifest`'s `DriverLifecycle`. The enum describes what a driver binds to
    (controller, function, interface), and boot-critical is a staging and policy fact.
  - `ahci`, `nvme` and `virtio_blk` declare `lifecycle = "function"` and keep `stage = "pinned"`.
  - The validator's two lifecycle rules become one staging rule: a pinned driver must provide `block`, the only reason
    to bind before there is a volume. A driver that provides none is refused `stage = "pinned"`. A volume-staged
    `block` provider (virtio-scsi, SDHCI, the xHCI driver's USB storage) stays allowed.
  - The generated registry's `boot_critical` flag becomes `bootstrap`, derived from the stage. Phase-one selection
    and the phase-two summary read it; nothing about operator policy does.
  - In the same change:
    - the `system-manifest` tests;
    - the registry stub in `check-device-claim-result.py`;
    - the manifest comments of the three entries, which state the class-wide cost;
    - the comments in ServiceManager and SystemGraphService;
    - the wording in `docs/DYNAMIC_LINKING.md`, `mkpackages` and `check-driver-protocol-note.sh`.
- [ ] 2. STORAGESERVICE SAYS WHICH DISK IT SERVES.
  - Its classification table gains a sixth code, `FORMAT_SERVED`, for the disk `vol://system` is served from, in
    place of `FORMAT_LIBERFS` for that one probe. Every other LiberFS disk, a decoy or another system's disk, stays
    `FORMAT_LIBERFS`.
  - `parse_classification_report` accepts the code.
  - The role routing treats it as a LiberFS disk, so it gets no role.
- [ ] 3. SERVICEMANAGER TELLS DEVICEMANAGER.
  - When the system StorageService reports, ServiceManager sends DeviceManager `SYSVOL` with the probe's index on its
    control channel. DeviceManager reads it in its loop as it reads `POLICYCFG` and `ACPI`: by tag, not by position.
  - When DeviceManager mints the probes, it records which node each one is for, in the order it mints them
    (`sort_probe_slots`). That is the order the hand-off and the table use, so it maps the index to the node with it.
- [ ] 4. THE MARK IS THE NODE'S.
  - The node `SYSVOL` names holds `vol://system` for the rest of the boot, across every rebind of its driver. A
    `BindingId` carries a generation; the mark does not.
  - Until `SYSVOL` arrives, and if it never does, every `bootstrap` node holds it. That is today's behaviour and the
    safe default. A boot with no probes, the kernel fixtures, sends no index and keeps it.
  - The node that holds it refuses `disable`, `enable`, `select` and `retry`, and stored policy never applies to it.
    Every other `bootstrap` node takes all four verbs and stored policy like any device, under the rule above.
  - `driver_binding::decide_retry` takes "holds the system volume" in place of "boot-critical", and `decide_policy`
    asks the node.
- [ ] 5. THE REFUSAL SAYS WHY.
  - `policy-outcome.refused` is redefined in `device.lsidl` as "this device holds the system volume; its policy would
    live on the volume it serves".
  - `lsdev` prints that sentence, and the generated protocol docs follow.
- [ ] 6. HOST TESTS. Each is watched failing before it passes:
  - `decide_retry` and `decide_policy` refuse the volume's node and accept a sibling node of the same driver;
  - the default before `SYSVOL`;
  - the index-to-node mapping in probe order;
  - `parse_classification_report` accepts the new code and refuses the next one;
  - the validator refuses a pinned driver that provides no `block`.
- [ ] 7. THE ORACLE, `boot-volume-controllers`: x86_64 first, the ports at the end of the job.
  - Its decoy case already boots two disks of one controller kind on a persistent disk set: the paired system
    volume and an unpaired LiberFS decoy. It gains, for NVMe, AHCI and virtio-blk:
    - `lsdev --disable` on the system disk's row is refused, with the sentence of item 5;
    - `lsdev --disable` on the decoy's row is accepted, the decoy's binding reads `disabled`, and its provider is gone;
    - on a cold boot of the same disks, the decoy is bound in phase one and DeviceManager says it is disabled in
      stored policy and stays up; `lsdev` shows the stored disable; `lsdev --enable` on it is accepted and removes the
      record.
  - The decoy is LiberFS like the system disk, so a refusal that falls on the right row proves the mark comes from
    StorageService's choice and not from the format.
  - The gate reads the rows' indexes from `lsdev` in the boot before the one that types the verbs.
