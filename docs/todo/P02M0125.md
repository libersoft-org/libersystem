The walk has a STATE now, not one error meaning three things. `ChainState` separates the terminator

`0xC0` and `0xC1` are known types, not known positions. A set of `85 C0 C1 C0` with a recomputed
checksum was an ordinary writable file whose second Stream Extension owned clusters nothing would
free - the leak the Vendor Allocation refusal was written for, reached through a type code this
driver claims to know.

The Up-case Table is read as well as checksummed: the mandatory first 128 mappings, compared against
the table `Upcase::ascii()` already builds, and the `0x82` entry's reserved fields, to the standard

the ones that were written; they do not say that `a` up-cases to `A`, and this driver folds every
name on the volume through whatever it finds.

The two free walks are NOT `ChainCursor`, and the comment now says so instead of claiming the
invariant is universal. They mutate the table a Floyd pointer would read, so detection there would be
present and inert - which is worse than absent. What they have instead is exact and cheaper: an entry
about to be freed that is already free has been visited, which also fixes the FSInfo count they
inflated by one per cycle. All five regression tests were run against the unmodified code first and
all five fail on it.

## The two that must be fixed before anything else

- [x] **exFAT's FAT is being read and written as if it were FAT32.** Every helper takes the branch
  `Kind::Fat32 | Kind::ExFat`: `next_cluster`, `is_end`, `set_fat_entry`, `fat_entry_at`,
  `fat_offset_of`. The value is masked with `& 0x0FFF_FFFF`, the end-of-chain constant is
  `0x0FFF_FFFF`, and the write preserves the top nibble:

      let next = (cur & 0xF000_0000) | (val & 0x0FFF_FFFF);

  exFAT has no 28-bit FAT. Its entries are a full 32 bits and the only valid end-of-chain value is
  `0xFFFFFFFF`. Two consequences, and the second is the bad one:

  - A volume this driver CREATES is written with `0x0FFF_FFFF` as the terminator. It reads back
    correctly here, because the reader shares the mistake, and it is not what the format says.
  - Growing an existing, correctly formatted exFAT directory or file reads a real `0xFFFFFFFF`
    terminator and, preserving the top nibble, writes a link to cluster 5 as **`0xF0000005`**. That
    is not a cluster pointer at all.

  The fix is to separate `ExFat` from `Fat32` in every FAT helper: full `u32`, no mask, EOC
  `0xFFFF_FFFF`, bad cluster `0xFFFF_FFF7`.

  **And the fixtures have to be fixed with it.** `tests.rs` builds its exFAT images with
  `0x0FFF_FFFF` as the terminator too, which is precisely why the suite could not see this. An
  internal round trip is not a conformance test when both ends share the assumption.

  DONE 2026-08-11. `ExFat` is its own arm in every FAT helper: a full 32-bit entry with no mask, no
  preserved top nibble, and `0xFFFFFFFF` as the only end-of-chain value - in the reader, the writer,
  the free-space scan and both places that terminate a freshly allocated chain.

  The fixtures went with it, which is what makes the fix provable: they wrote FAT32's `0x0FFF_FFFF`
  as an exFAT terminator, so an internal round trip agreed with itself and could not see this. A new
  test plants a CONFORMING `0xFFFFFFFF` on cluster 2 and extends the chain to cluster 5; watched to
  fail against the old shared branch, where it reports `got 0xf0000005` - the exact value this
  finding predicted, and not a cluster pointer at all.

- [x] **A directory swap that fails part-way can leave a live entry pointing at clusters the caller
  then frees.** `write_file` allocates the new chain and writes the data, calls `swap_entry`, and on
  an error frees the new chain. But `swap_entry` marks the old entry set unlinked IN MEMORY, may
  place the new set in an EARLIER free hole, and `write_dir_dirty` then writes every cluster between
  the lowest and highest change, one at a time.

  So: the cluster holding the new entry is written and lands; the later cluster holding the old
  entry's deletion fails; `swap_entry` returns `Err`; the caller frees the new data chain. The new
  directory entry is now live on the medium and points at clusters that are back in the free pool,
  and the next allocation cross-links them. `exfat_swap_entry` has the same shape.

  The comment above `write_file` says a failure part-way never costs the old file. That is the
  claim this breaks.

  The fix is not a bigger rollback. An I/O error means the commit is AMBIGUOUS - not that nothing
  was written - so the new chain cannot be freed without reading back what actually landed. The
  shape that works is a publish protocol: write data and FAT, barrier, activate the new entry as the
  single last step, barrier, retire the old entry, barrier, free the old clusters.

  IMPLEMENTED and DEMONSTRATED 2026-08-11.

  `swap_entry` now publishes in two ordered writes with a barrier between them: the new entry set
  first, with the old one still live, then the old entry's deletion. Its failure carries `placed`,
  which is the only thing the caller needs to decide what it may free - before the new set is
  written nothing is published and the new chain is the caller's to release; after it the commit is
  ambiguous and freeing hands live clusters back to the pool. `write_file` respects it.

  `an_interrupted_swap_never_frees_clusters_a_live_entry_names` fails without the fix (`A.TXT reads
  as [204; 8]` - the bait file's bytes) and passes with it. Getting there took four harnesses, and
  the three that proved nothing are worth more than the one that works, because each was green for a
  different reason:

  1. **The replacement reused the slots it was replacing.** `free_run` hands back the run the old
     entry just vacated, so both images are byte-identical and the second write has nothing to do.
     There is no interleaving to interrupt. The fixture now removes an earlier file first, so the
     new entry lands in that hole and the deletion is a separate range.
  2. **The file under test was never on the medium.** `build_fat` fills one root sector and silently
     drops the rest, so the fixture's forty-eight fillers left no room for `A.TXT` and `write_file`
     became a create - which has one phase and cannot be interrupted between two. Nine files fit.
  3. **The device was dead rather than faulty.** A device that refuses every write after the Nth
     also refuses the erroneous free, so the volume comes out consistent and the harness proves only
     that a dead disk cannot be corrupted further. `FailNthWrite` fails exactly one sector and
     serves the rest, which is both the commoner failure and the one that lets the recovery path run
     and do its damage.

  What made the difference was measuring instead of guessing: a throwaway test printing the outcome
  at every budget showed the whole write is five sectors, that only budget 5 separates the two
  phases, and that the corruption needs the free to succeed. Three earlier attempts widened budgets
  and grew directories against a mechanism that was not there.

## The barrier that does not exist

- [x] **`flush()` is never called - not once in the crate.** `BlockDevice::flush` exists in fs-core
  and is documented as the write barrier commit protocols need, and the USB backend implements it as
  SCSI SYNCHRONIZE CACHE(10). Without it, "we wrote the data before we wrote the directory entry" is
  a statement about the order the CPU issued the writes, not the order they become durable. A device
  is free to reorder its writeback, so the ordering the driver relies on for crash safety is not
  actually being requested. This is the prerequisite for the publish protocol above.

  DONE 2026-08-11. A `barrier()` helper, and both publish paths use it: the data and the FAT are
  durable before the entry that names them is issued, the entry is durable before the replaced
  clusters go back to the pool, and the operation is durable when `write_file` returns.

  Pinned by a device that records write order and counts barriers, so the protocol is checked rather
  than described - and watched to fail: removing the first barrier makes it report that the
  directory entry was issued without one in front of it.

## Reading a damaged chain

- [x] **A chain that ends early returns a short file as success.** `read_chain` stops when it meets
  a free or reserved entry (`< 2`) or an end-of-chain marker, and returns what it has. `read_file`
  never checks that it got `min(size, valid_len)` bytes, and the zero-fill path only runs when
  `out.len() == disk`. A directory entry claiming 20 MiB backed by a 4 KiB chain therefore answers
  `Ok(4 KiB)`. `first_cluster = 0` with a nonzero size reads as a successful empty file the same way.
  A short chain is corruption and should be reported as such.

  FIXED 2026-08-11. `read_chain` refuses a walk that ends before it produced the bytes it was read
  for. Both shapes the finding names are the same check: a chain terminated or freed early, and a
  first cluster of zero on an entry whose size says otherwise, which walks zero clusters. The bytes
  a damaged file does hold are still not served, and that is the point - a backup tool copying a
  prefix it believes is whole is worse than one that reports the file is broken.

  `a_chain_shorter_than_its_entry_is_corruption_not_a_short_file` covers all three routes.

- [x] **A cyclic chain returns duplicated data as a valid file.** The loop checks
  `out.len() >= limit` BEFORE following the next FAT entry, and its only cycle guard is a step count
  (`guard > max`). A cluster pointing at itself, with a 1024-byte size and 512-byte clusters, is read
  twice and returned as 1024 bytes of `Ok`. A two-cluster cycle yields A,B,A,B up to the declared
  size. The guard needs to be a visited-cluster set (or Floyd), not a step budget.

  FIXED 2026-08-11 with Floyd rather than a visited set: `slow` follows one link for every two the
  read takes, so a cycle is caught in the length of the cycle at constant memory, which a driver
  that may be asked to read a multi-terabyte volume needs.

  The finding's own example is why a step budget could never work: a self-pointing cluster read for
  a 1024-byte file is two steps, and two steps is inside any budget the volume could justify. The
  corruption is the repetition, not the length.

  `a_cyclic_chain_is_refused_rather_than_repeated` covers the self-loop and the two-cluster cycle.

- [x] **The same cycle is a memory and CPU exhaustion path when the limit is `usize::MAX`.** The root
  directory and the exFAT allocation bitmap are both read with no limit, so a cycle appends cluster
  after cluster until the step guard trips at `cluster_count`. On a large volume that is an enormous
  allocation before the driver finally says `Invalid`. For a driver whose stated model is that the
  medium is untrusted, the bound has to come from the structure being read, not from the size of the
  volume.

  FIXED 2026-08-11, by the cycle detection above and by taking the bound from the structure where
  one exists. The allocation bitmap is read for its recorded size rounded up to clusters
  (`bitmap_cap`) instead of without limit, so the one place a hostile medium controls no longer
  decides how much is allocated on its behalf. The unlimited reads that remain - a chained exFAT
  root - can now only allocate a real chain's worth, because a cycle is refused in the length of
  the cycle instead of growing the buffer until the step guard trips at `cluster_count`.

## exFAT: what is accepted at mount

- [x] **The boot region is barely validated.** `Geometry::exfat` checks a handful of sensible bounds
  and does not verify the boot checksum, the `AA55` boot signature, `VolumeLength`, the relationship
  between `FatOffset`, `FatLength` and `ClusterHeapOffset` beyond one inequality, or the filesystem
  revision. The specification requires the boot checksum and the boot field validity to be confirmed
  before either the main or the backup boot sector is used. Concretely: `fat_offset = 1` can pass
  today if the arithmetic happens to work out, and a later FAT write then writes into what a real
  exFAT volume uses as its boot region.

  FIXED 2026-08-11. `Geometry::exfat` now refuses a volume with no `AA55` signature (checked on the
  classic path only, so an exFAT volume reached the geometry on its name alone), a non-zero
  MustBeZero region, a major revision this driver has never seen, a `FatOffset` inside the 24-sector
  boot region - the concrete case the finding names - a `FatLength` too short to address the
  declared heap, and a `VolumeLength` that does not contain that heap or falls under the
  specification's 2^20-byte floor. `mount` verifies the boot checksum over sectors 0-10 before any
  field is used, which is the only check that catches a boot region edited in place.

  **The exFAT fixtures were not exFAT volumes.** They carried no boot checksum, no revision, no
  VolumeLength, and were 45 KiB - a twentieth of the smallest volume the format allows. Ten tests
  failed the moment the driver started checking, all of them on the media rather than the driver.
  The builder now stamps the checksum last (it sums the signature it must be written after), fills
  the revision and VolumeLength, and pads to the floor.

  One test was passing for the wrong reason and only the checksum could show it:
  `growing_a_conforming_exfat_chain_writes_a_cluster_pointer` wrote its "conforming terminator" at
  sector 3, which is boot region, not FAT. The edit did nothing and the assertion was measuring the
  driver's untouched behaviour. It reads `FatOffset` now.

  Every one of the eight checks was removed in turn and watched to fail its own case. Two needed
  the case rewritten first: a cluster count raised past the volume proves the device-size check
  rather than the FAT-length one, and a second FAT does not fit a fixture whose heap begins
  immediately after the first, so the overlap rule refused it before the count was considered.

- [x] **TexFAT is half-refused.** The code refuses only the case where `VolumeFlags` says the SECOND
  FAT is active. A volume declaring two FATs with the first active mounts, and the returned
  `Geometry` then hard-codes `num_fats: 1` - so the second FAT is neither used nor maintained. If
  TexFAT is out of scope, the honest rule is `num_fats != 1 => reject`.

  FIXED 2026-08-11 with the honest rule the finding asks for: `num_fats != 1` is refused. Covered by
  `an_exfat_boot_region_that_fails_its_own_checks_does_not_mount`, which first asserts the same
  layout mounts when it declares one FAT.

- [x] **`max_cluster` truncates an inconsistent volume instead of refusing it.** It takes the minimum
  of what the FAT can address and the declared cluster count. That keeps writes in bounds, which is
  right, and it also means a volume whose cluster heap is larger than its FAT can address mounts as
  a quietly smaller filesystem. exFAT derives a minimum `FatLength` from `ClusterCount`; a layout
  that violates it is inconsistent and should be refused at mount.

  FIXED 2026-08-11 at mount, where the inconsistency is: `FatLength` must be at least
  `(ClusterCount + 2) * 4` bytes rounded up to sectors. `max_cluster` still takes the minimum, which
  remains right for a volume that got past mount - the two answers can no longer disagree.

## exFAT: names and entry sets

- [x] **`NameHash` is computed with ASCII uppercasing only.** `exfat_name_hash` upper-cases
  `0x61..=0x7A` and leaves every other UTF-16 unit alone. exFAT defines the hash over the name
  transformed through the volume's Up-case Table. The write API accepts any valid UTF-8 name up to
  255 UTF-16 units - there is a test for it - so a non-ASCII name gets a hash, and collision
  semantics, that differ from every other exFAT driver.

  The real fix is to read the 0x82 Up-case Table, verify its checksum, and use it for the hash, for
  lookup and for uniqueness. Until then, refusing non-ASCII names on the exFAT WRITE path is the
  honest short answer, because the alternative is writing names other systems will not match.

  FIXED 2026-08-11 with the real fix rather than the short answer. `Upcase` reads the 0x82 entry's
  table, verifies the checksum recorded beside it, decodes the compressed form (0xFFFF followed by a
  count of identity mappings), and drops the trailing identity run so the common table costs
  kilobytes instead of the uncompressed 128 KiB. `FatFs` holds one, exFAT loads it at mount and
  refuses the volume if it is missing, mis-checksummed or longer than the character set it maps, and
  the classic families get a table that says "fold ASCII" - which is what their rule is.

  The fold now governs all three things the finding names: the `NameHash` written into an entry set,
  lookup, and therefore uniqueness. `eq_upcased` compares over UTF-16 units, because folding UTF-8
  bytes would fold nothing above ASCII however good the table was.

  **The fixtures had no Up-case Table.** It is one of the two entries a root is required to carry
  and no image the crate built had it, so nothing the driver did with names had ever been checked
  against a real one. The builder writes a compressed table that folds Latin-1 as well as ASCII,
  which is what lets `an_exfat_name_folds_through_the_volumes_own_upcase_table` tell a table from a
  rule: with ASCII folding restored it fails on the stored hash for `café.txt`.

  Six tests moved with the new entry, and the reason is the same one as the second FAT: they counted
  the required entries before the first file set ("the set after the bitmap entry") instead of
  finding it. `exfat_first_set` finds it.

- [x] **The entry-set grammar is not enforced.** Verifying `SetChecksum` is good and it is not
  enough: the parser takes any `0xC0` anywhere among the secondary entries and any `0xC1`, without
  requiring exactly one Stream Extension IMMEDIATELY after the File entry, without requiring the
  File Name entry count to match `NameLength`, without checking `NameHash` against the name it just
  read, and without requiring `ValidDataLength <= DataLength`. A checksum-valid but structurally
  hostile set can therefore be surfaced as a file - and later have its clusters freed.

  FIXED 2026-08-11. `parse_exfat_dir` now requires exactly one Stream Extension immediately after
  the File entry, the File Name entries consecutive and starting right after it, as many of them as
  `NameLength` needs, a `NameHash` that matches the name they spell, and `ValidDataLength` no
  greater than `DataLength`. A set that breaks any of them is skipped, as a torn one already was.
  Vendor extensions after the name entries are still ignored rather than refused, which is what the
  specification allows.

  The hash rule is the one with teeth: the system that wrote the medium recomputes it on lookup and
  skips a set that disagrees, so accepting one meant this driver could open - and free the clusters
  of - a file nothing else could find.

  **The fixtures wrote a zero NameHash.** Every set the builder produced had one, which no
  formatter writes and which meant the field had never been read by anything. It is stamped now,
  by a second implementation of the fold so the two can disagree.

  `a_checksum_valid_but_ungrammatical_entry_set_is_not_a_file` covers six shapes, and each of the
  four rules was removed in turn and watched to fail its own case.

## Rollback that does not cover the failing step itself

- [x] **`alloc_chain` rolls back the entries before the one that failed, and not that one.** When
  `set_fat_entry(chain[i])` returns an error it may already have had an effect: with mirrored FATs
  it can succeed on copy 0 and fail on copy 1, and on FAT12 a two-sector read-modify-write can land
  the first sector and fail on the second. The rollback undoes `chain[..i]` and leaves `chain[i]`
  half-written - divergent FAT copies, or a torn FAT12 entry. The original raw entry (all copies)
  has to be remembered and restored, and if the restore itself fails the volume should be marked
  read-only rather than carried on with.

  FIXED 2026-08-11. `set_fat_entry` is now all-or-nothing: every sector it is about to modify is
  read into an undo list first, and any failure puts the originals back - including the copy that
  failed, whose first sector may have landed. `alloc_chain`'s rollback is then correct as written,
  because the entry that failed is already back to what it was, and its comment says so.

  A restore that cannot itself be written sets `FatFs::degraded`, and every later `set_fat_entry`
  refuses with `ReadOnly`. That is the honest answer to a medium that will not take the undo: the
  FAT no longer describes its own contents, and continuing is how a torn FAT12 entry becomes two
  files sharing a cluster. The same flag is set when the undo of an accepted allocation is refused,
  where the residue is a leak rather than a cross-link.

  **The fixtures had one FAT.** `write_bpb` wrote `img[16] = 1`, so no image the crate built had a
  second copy and the mirroring loop - the subject of half this finding - had never executed in a
  test. The builders now write two copies and mirror them, as every formatter of this family does.
  Eight tests failed on the change and each was worth the noise: six restated the layout as
  `21 * 512 // reserved 1 + FAT 20 sectors` instead of reading the BPB (now `classic_root_off`),
  one asserted a FAT12 write touches one sector when the property is one sector PER COPY, and one
  built an "active FAT past the copy count" as copy 1, which two copies make legal.

  `a_refused_write_to_the_second_fat_copy_leaves_the_copies_identical` and
  `a_fat12_entry_across_a_sector_boundary_is_not_left_torn` both fail without the undo.

- [x] **`exfat_grow_dir` leaks its new cluster when the parent record update fails.** It allocates,
  zeroes, links the cluster into the chain, and only then calls `exfat_grow_parent_record`. If that
  write fails, the function returns an error with the cluster still allocated and still linked,
  while the parent's `DataLength`/`ValidDataLength` still describe the shorter directory. The
  comment says a failure leaks nothing; here it does. Either restore the old tail's EOC and free the
  cluster, or make the grow two-phase and recoverable.

  FIXED 2026-08-11 by the first of those. The old tail is kept rather than recomputed - after a
  failure the chain may not have the shape a fresh walk would find - and a refused parent-record
  write puts the terminator back, frees the cluster and truncates the in-memory copy. A rollback
  that cannot be written degrades the mount.

  `a_grow_whose_parent_record_write_fails_gives_the_cluster_back` fails without it, by exactly one
  cluster (28160 free where 28672 was expected), and the retry afterwards succeeds.

- [x] **Classic `grow_dir` keeps its cluster after a later failure too.** The directory is grown
  before the entry write, so a failing write cleans up the file's data chain and leaves the
  directory permanently one cluster longer. A test currently asserts this outcome. It is not
  corruption - the tail is zeroed and parses as empty - but repeated transient failures grow the
  directory while every operation reports an error.

  MEASURED and DOCUMENTED 2026-08-11, deliberately not changed. The compounding the finding worries
  about does not happen, and not by luck: a grow only runs when no free run exists, and the tail it
  leaves IS a free run, so the retry writes into it. The second attempt in
  `a_directory_grown_by_a_failed_write_is_grown_at_most_once` re-arms the trap on the cluster a
  second grow would take and it never fires; five failed writes cost one cluster, not five.

  Rolling the grow back would trade that bounded cost for an unbounded risk. The entry write may
  have landed in the new cluster before failing, and freeing a cluster a live directory entry lives
  in is how a directory loses files instead of space - the same mistake as the unconditional free
  above, one level up. `grow_dir`'s comment now records the bound and the reason.

## Metadata the format expects to be maintained

- [x] **An overwrite drops the file's attributes.** The raw entry's name, cluster, size and exFAT
  chain flags are carried across, and the attribute byte is not: the new classic entry is built with
  `0x20` and the exFAT one as an archive file. Overwriting therefore clears read-only, hidden and
  system - and the write and remove paths do not honour read-only in the first place.

  FIXED 2026-08-11 in both halves. `Raw` carries the attribute byte - the classic byte 11 and the
  low half of exFAT's FileAttributes hold the same four bits - and an overwrite rebuilds the entry
  with the replaced file's read-only, hidden and system, plus archive, instead of a fresh `0x20`.

  Read-only is enforced where both mutating paths already meet: `mark_unlinked` and its exFAT twin
  are what a write and a remove both go through to find the entry they are about to replace, so one
  check covers both without a second directory read.

  `an_overwrite_keeps_the_attributes_and_read_only_refuses_one` and its exFAT counterpart fail
  without each half in turn.

- [x] **`VolumeDirty` and `PercentInUse` are deliberately not maintained, and the specification
  expects them to be.** The header says they are skipped to save sector writes. `PercentInUse` is
  required to be updated on allocation changes, or set to `FFh` when the correct value is not known;
  `VolumeDirty` is the recovery signal around metadata updates. The cheap and correct version is not
  to compute a percentage on every allocation - it is to set `PercentInUse` to unknown and to raise
  and clear `VolumeDirty` around the transaction, which the publish protocol above wants anyway.

  FIXED 2026-08-11 with exactly the cheap and correct version the finding describes.
  `under_dirty_flag` raises VolumeDirty before an exFAT mutation and clears it after; `PercentInUse`
  is set to FFh - unknown - rather than recomputed, which the format explicitly allows and which
  costs nothing where a percentage would cost a bitmap scan per allocation.

  The saving the header claimed was never available: all three bytes sit in the range the boot
  checksum skips, and they are excluded from it precisely so a running system can keep them current.
  The test asserts the volume still mounts afterwards, which is that claim.

  And the flag is now READ as well as written. A volume that arrives with VolumeDirty already set
  was left mid-transaction by its last writer, so the mount serves reads and refuses mutations -
  writing over it is how a recoverable inconsistency becomes an unrecoverable one. Clearing it is a
  repair tool's job, not a driver's.

  `an_exfat_mutation_runs_between_a_raised_and_a_cleared_dirty_flag` and
  `a_volume_left_dirty_mounts_read_only`, both watched to fail.

## Scale, and the shape of the I/O

- [x] **Whole structures are read into memory.** The classic allocator and `free_bytes` read the
  entire FAT into a `Vec`; the exFAT allocator reads the whole allocation bitmap chain; a directory
  is read whole and then `clone`d for the mutation compare. With `read_file` also being whole-file,
  a large or maliciously large volume is a memory problem. Sector or cluster streaming with dirty
  extents is the direction.
  PARTLY FIXED 2026-08-11, and the part done is the part where the medium chose the size.

  The two scans that read the entire FAT - `alloc_chain`'s free-cluster search and `free_bytes` -
  now run over a two-sector sliding window (`fat_window`). Two sectors rather than one because a
  FAT12 entry straddles the boundary and half an entry is not an entry. A 66000-cluster FAT32 table
  is 264 KiB and a 4 TiB volume's is a gigabyte; those allocations are gone, and the whole-table
  reader is gone with them so nothing can drift back.

  The round trips the whole-table read existed to avoid are still avoided: each FAT sector is read
  once, which `scanning_the_fat_does_not_cost_more_reads_than_reading_it_whole` pins for all three
  classic families against the table's own sector count. The exFAT bitmap read is bounded by the
  bitmap's recorded size, done with the chain validation above.

  NOT done: whole-file `read_file`, whole-directory read-and-clone for the mutation compare, and the
  streaming API with dirty extents that both would need. Those are a change to what the crate's
  interface promises rather than to how a scan is written - `read_file` returns a `Vec` because
  `fs-core` says it does - and they belong with whatever milestone changes that contract. What is
  bounded now is everything sized by a number a hostile volume writes; what remains is sized by what
  a caller asked for.

- [x] **`write_dir_dirty` is not "write only what changed".** It finds the first and last differing
  byte and writes every cluster in between. When an overwrite puts the new entry in an early hole
  and the old entry sits hundreds of clusters later, the whole span is rewritten - write
  amplification, and a wider crash window for the defect above. Collecting the actually dirty
  sectors and merging adjacent runs is both faster and narrower.
  FIXED 2026-08-11. It compares sector by sector and writes runs of adjacent dirty sectors, so a
  clean cluster between two changes costs a FAT lookup instead of a write. Seven writes for two
  changed sectors, before; two, now.

  Measured on `write_dir_dirty` itself rather than through `write_file`, and the reason is worth
  recording: the two-phase publish already keeps each of the swap's two writes narrow by
  construction - one image differs from the previous only in the new entry, the other only in the
  deletion - so a test driven through an overwrite would have measured that fix and passed with this
  one absent. The wide spans that remain reach the function by other routes, the terminator scrub
  among them.

  `a_directory_write_touches_only_the_sectors_that_changed`, watched to fail at seven.

## Interfaces and metadata

- [x] **Path and error semantics do not match fs-core's own vocabulary.** `resolve_dir` drops empty
  segments, so `foo//bar` is accepted; `split_parent` strips one trailing `/`, so `write_file("foo/")`
  writes `foo` rather than refusing a directory path; reading a directory answers `NotFound` and
  removing one answers `Invalid`, when `FsError` already has `IsDir`, `NotDir`, `BadName` and
  `ReadOnly`. One path parser and one error contract.
  FIXED 2026-08-11. `split_parent` refuses an empty segment anywhere - a doubled separator or a
  trailing slash - instead of repairing it, and `resolve_dir` applies the same rule rather than its
  own, because `list_dir` hands it a path directly. A single leading `/` is an absolute path and
  still resolves to the root.

  The errors now say which kind of wrong: `BadName` for a malformed path, `IsDir` for reading or
  removing a directory through the file paths, `NotDir` for a path component that names a file, and
  `NotFound` only for what is genuinely absent.

  `a_path_is_parsed_once_and_an_error_says_which_kind_of_wrong` covers ten cases and each of the
  four changes was reverted in turn and watched to fail. One existing expectation moved with it:
  `read_file("")` answers `BadName` rather than `NotFound`, which is the stronger answer - the path
  is refused before any directory is searched, so it cannot match an empty name however one got
  onto the medium.

- [x] **The LFN parser could be stricter against hostile media.** It already checks sequence numbers
  and the checksum and refuses orphans, which is most of the value. What it does not enforce is the
  structural remainder: at most 20 fragments for 255 UTF-16 units, the type and cluster fields, and
  the padding and terminator rules.
  FIXED 2026-08-11. A fragment is now refused when its sequence number is past 20 (twenty fragments
  of thirteen units is 260 and the limit is 255), when the reserved byte 12 or the first-cluster
  field at 26-27 is non-zero, when a non-final fragment carries a terminator or padding, or when a
  final fragment has anything but 0xFFFF after its 0x0000.

  In every one of those the file is not lost - the 8.3 alias names it and the listing shows that
  instead. What the rules prevent is a NAME assembled out of padding and reserved fields, which is
  the string a caller then stores and looks up by.

  `a_structurally_impossible_long_name_falls_back_to_the_short_one` asserts the untouched fixture
  first, so each of the four edits is a change rather than a coincidence.

- [x] **The 8.3 path is not really an OEM code page model.** `short_name` runs the raw field through
  `String::from_utf8_lossy` while the generator writes UTF-8 bytes with ASCII uppercasing. For LFN
  files the long name usually saves it; for short-only non-ASCII names and for alias lookup it is an
  interoperability limit. Either implement a supported code page or say plainly that the 8.3
  fallback is ASCII-oriented.
  ANSWERED 2026-08-11 with the second option, stated where the code is rather than in a milestone
  nobody reads while editing it. `short_name` now carries the reasoning: which OEM code page a
  volume used is not recorded ON the volume, so byte 0x81 is U+00FC under one and U+0433 under
  another and no care in that function can tell them apart. Implementing one code page would be
  confidently wrong on media formatted under a different one.

  So the limit is declared: the 8.3 field is ASCII-oriented, the generator writes and folds ASCII,
  and everything else rides on the long name - which every file this driver creates has unless its
  name is already 8.3-clean. What is not supported, and now says so, is a short-ONLY name with bytes
  above 0x7F.

- [x] **The crate metadata describes software that no longer exists.** `Cargo.toml` still says
  "a read-only FAT12/16/32 and exFAT backend" over an extensive write path, and
  `rust-toolchain.toml` pins `channel = "nightly"` with no date, so a build is not reproducible
  across days.
  HALF FIXED 2026-08-11. `Cargo.toml` no longer calls an extensive write path "a read-only backend".

  The toolchain pin is deliberately NOT changed, and the reason is not that it does not matter.
  Every crate in the tree carries the same `channel = "nightly"` - sixteen files - so it is one
  decision about the repository, not a property of this crate; and the only nightly installed here
  is the undated one (1.98.0-nightly, 2026-06-15). Writing `nightly-2026-06-15` into one crate would
  ask rustup for a toolchain that is not present, which breaks the build rather than making it
  reproducible. It belongs in whichever milestone owns the build environment, pinned across all
  sixteen at once and with the dated toolchain actually fetched.

## How this gets tested, since the current suite could not see the first defect

The suite is genuinely strong for its age - FAT12/16/32 and exFAT, multi-cluster files, NoFatChain,
malformed boot sectors, cycle guards, the FAT12 straddle, 1024-byte logical sectors, the FAT32
active copy, FSInfo, failure injection, directory growth, timestamps, terminator garbage, invalid
names, valid data length, directory-length bounds. And it still could not see that exFAT's
end-of-chain value is wrong, because the fixture builder writes the same wrong value.

- [x] **Golden images from an independent implementation, and the reverse check.** Read images this
  tree did not build; and, more valuable, WRITE with this driver and then check the result with a
  standard `fsck.exfat` / `fsck.vfat`. The second direction is the one that catches a driver and its
  fixtures agreeing with each other.
  DONE 2026-08-11, in both directions and on both families.

  * `an_image_from_an_independent_formatter_mounts_and_reads` formats with `mkfs.exfat` and mounts
    the result, which puts every mount check - boot checksum, revision, FAT bounds, Up-case Table -
    against a volume nothing in this tree produced.
  * `what_this_driver_writes_passes_an_independent_checker` writes small, multi-cluster, non-ASCII
    and removed-and-rewritten files onto such a volume and hands it to `fsck.exfat`, which must call
    it clean.
  * `what_this_driver_writes_to_a_classic_volume_another_implementation_reads` does the classic
    families with mtools: `mformat` lays out the volume, this driver writes 8.3 and long-name files,
    and `mdir` and `mtype` have to find them and return the same bytes.

  All three skip loudly with a printed line when the tools are absent, because a cross-check that
  quietly passes on a machine without them is worse than none.

  **It found a real defect on the first run.** `Upcase::decode` refused every volume exfatprogs
  formats. The standard table ends with the identity mappings 0xFFF8, 0xFFF9 ... 0xFFFF written out
  one by one, and 0xFFFF as the LAST unit has no count after it - it is the mapping for U+FFFF, not
  a run marker. A decoder written from the compression rule alone gets this wrong and no fixture
  this tree builds would ever have said so. That is precisely the class of defect this task exists
  for, and it was found within a minute of the task being started.

- [x] **A generic crash-consistency harness.** `FailAfterNWrites`, every mutating operation run once
  per N, and after each cut a remount that asserts the invariants: no live entry pointing at a free
  cluster, no cluster owned by two files, no new chain without its FAT or bitmap allocation, and the
  file readable as either its old or its new content. That is what would have found the directory
  swap defect, and it generalises to the ones not yet thought of.
  DONE 2026-08-11. `every_mutating_operation_survives_being_cut_at_any_write` runs five operations -
  create, overwrite smaller, overwrite larger, remove, and create into a hole - once per failure
  point, against `FailNthWrite` rather than a device that dies. After each cut it remounts and asks
  the questions that do not depend on which operation was interrupted: does the volume mount, does
  every live entry name clusters the FAT agrees are allocated, does any cluster have two owners,
  does every listed file read, and is an uninvolved file untouched. Then it forces an allocation and
  asks again, because that is what turns a freed-but-still-named cluster into a cross-link.

  It reproduces the defect that started this milestone: with the unconditional free restored it
  fails at `overwrite-smaller cut at write 5: BIG.BIN names cluster 2, which the FAT says is free`.
  The specific harness needed a fixture designed around the defect; this one finds it from a
  description of what a filesystem must never do.

  The fixture order is load-bearing and says so in the test: the hole has to come BEFORE the file
  being replaced, or the replacement lands back in that file's own vacated slots and the publish
  protocol has only one write to be cut at.

  **And it found a fixture defect immediately.** `place_classic` gave every file ONE cluster while
  writing the full length into its entry, so a 1536-byte fixture file was a 512-byte chain claiming
  three times its size. No classic test had ever read a multi-cluster file the builder produced -
  only ones this driver had written itself. The builder chains them now.

## Order

The first two sections come before anything else: the exFAT FAT semantics, because a correctly
formatted volume is actively damaged by growing a file on it, and the directory publish protocol,
because an I/O error can currently produce a cross-link. `flush()` is the prerequisite for the
second. After those: the chain validation, the exFAT boot and entry-set validation, and the Up-case
Table. Then the rollback gaps and the dirty metadata. Performance, attributes and the path and error
polish last - they are real, and none of them is a way to lose somebody's data.

## Reopened: the two-phase publish was written once and needed to be written five times

A second audit - 2026-08-12, against this tree at `fcb821b` - reading the implementations rather
than the finding list. Every claim below was checked against the code first.

What it confirms is worth saying before what it reopens. The exFAT read and normal-write path really
did change character: `EXFAT_EOC` correct at last, the boot region validated against the
specification, the real 0x82 Up-case Table loaded and checksummed, entry-set grammar enforced,
attributes preserved. `set_fat_entry` gained a rollback that restores the original sectors and
degrades the mount when the undo itself fails, which is the right answer to "the medium refused to
undo what it accepted". The classic FAT scan became a two-sector sliding window without costing
round trips, and there is a test asserting the read count to prove it. The external
`mkfs.exfat`/`fsck.exfat`/`mtools` tests are the single most valuable thing added, because the
internal exFAT fixture had shared the driver's own bugs - and they immediately found one.

The crash-consistency group is a different story, and it is one story rather than six findings. The
protocol that closes finding 2 - place the new entry while the old is still live, barrier, retire
the old, barrier, and only then free - exists in exactly one function. Every other place that
publishes a change and then frees what the change replaced still does both in one breath.

### exFAT never got the two-phase publish at all

`swap_entry` (`src/fs/fat/src/lib.rs:1138`) writes `staged` - the new set placed, the old entry
untouched - then barriers, then writes `bytes` with the old set retired, then barriers. That is the
protocol, and the reasoning above it is written out properly.

`exfat_swap_entry` (`src/fs/fat/src/lib.rs:1373`) marks the old set unlinked AND places the new set
into the same buffer, then does one `write_dir_dirty(dir, &bytes, &orig)?` and returns. There is no
staging, no barrier, and its error type is a plain `FsError` rather than `SwapFailure`, so it has no
way to tell the caller which side of the publish line a failure fell on. `exfat_write`
(`src/fs/fat/src/lib.rs:1338`) therefore does the thing the classic path was fixed to stop doing:

```
Err(e) => { let _ = self.exfat_free(first); return Err(e); }
```

So the original finding is intact on exFAT. A `write_dir_dirty` that writes the sector holding the
new entry set and fails on a later one leaves a live entry naming a chain that this handler then
returns to the free pool, and the next allocation cross-links it.

It is worse on exFAT than it was on classic FAT, for a reason worth recording: the File entry
carrying the in-use bit is FIRST in an exFAT entry set, at the lowest offset. A set that straddles a
sector boundary and lands only partially leaves the live half on the medium. In a classic set the
8.3 entry is last, so the same partial write is likelier to leave nothing live.

- [x] **Give `exfat_swap_entry` the same protocol and the same failure type.**

  DONE 2026-08-12: it stages the new set with the old still in use, barriers, retires the old,
  barriers, and returns `SwapFailure`. `exfat_write` now frees only when nothing was published,
  exactly as the classic caller decides it.

### The classic publish signals `placed: false` for a failure that may have published

`src/fs/fat/src/lib.rs:1206`:

```
self.write_dir_dirty(dir, &staged, &orig).map_err(|error| SwapFailure { error, placed: false })?;
self.barrier().map_err(|error| SwapFailure { error, placed: false })?;
// Past here the new entry may be on the medium.
```

The comment is one operation too late. Once `write_dir_dirty` has returned `Ok`, the device has
ACCEPTED the writes; a `flush` that then fails says the durability is unknown, not that the writes
were discarded. A device does not throw away its write cache because a flush reported an error - it
is at least as likely to commit it moments later. So the caller gets `placed: false`, frees the new
chain (`src/fs/fat/src/lib.rs:374`), and the medium ends up with exactly the live-entry-naming-free-
clusters state this whole protocol exists to prevent.

The correct value is `placed: true`, and the resulting state is the benign one the protocol already
describes for its third step: both entries live, a duplicate name, no data lost, `fsck` resolves it.

- [x] **The first barrier's failure is `placed: true`.**

  DONE 2026-08-12, and FOUND BY THE HARNESS rather than by reading: the moment the sweep could
  inject a failing flush it reported `fat12 create cut at flush 2: NEW.TXT names cluster 2, which
  the FAT says is free` - the live entry naming freed clusters, exactly as predicted, before any fix
  went in.

- [x] **Settle the same question for a partial `write_dir_dirty`.**

  DONE 2026-08-12, with the same answer rather than a different one: both writes and both barriers
  carry `placed: true`. A set can straddle a sector, so any failure from the first write onwards may
  have published, and nothing after that line may assume otherwise.

  It cost a cluster and the cost is the point.
  `a_directory_grown_by_a_failed_write_is_grown_at_most_once` measured a failed write at one cluster
  and now measures two: the grown directory cluster plus the data chain the caller may no longer
  free. A leaked cluster against a cross-linked one is not a close comparison, and the bound the
  test exists for - a fixed cost per failure, nothing further on the retry - still holds.

### Found while widening the sweep: an exFAT directory of three clusters loses its tail

Not a crash defect - there is no interruption anywhere in it. An exFAT root large enough to need a
third cluster loses the entries in its last one the first time anything is written into the
directory, on a clean volume with a device that fails nothing.

It surfaced because the sweep's fixture had to grow. exFAT entry sets are about 96 bytes, so the
four-file fixture sat inside ONE sector and the publish protocol's two-write interleaving could not
occur there at all - the exFAT leg was passing for the same empty reason four earlier harnesses did.
Widening it to twelve files reached this instead, which is worth more than what was being looked
for.

Reproduced in its smallest form by
`an_exfat_directory_spanning_three_clusters_survives_an_ordinary_write`: eleven small files and one
read-back, no failure injection. The chain itself is read and walked correctly - `read_dir_bytes`
returns all three clusters and `write_dir_dirty` follows the chain - so the loss is in what the
buffer holds by the time it is written back, not in the mapping.

- [x] **Find it and fix it.**

  DONE 2026-08-12, AND IT WAS THE FIXTURE - the fifth harness in this milestone to prove nothing,
  and the first one that spent a day reading as a driver defect.

  `build_exfat_tree` copied its allocation bitmap into the image BEFORE it built the root's cluster
  chain, and the chain loop is where the root's clusters are marked. So on any fixture whose root
  needed a second cluster, the medium's bitmap said those clusters belonged to nobody. The driver
  then did exactly what a driver must: `exfat_alloc` took the first cluster the bitmap offered -
  the root's own second one - `write_clusters` put the new file's data over the entries living
  there, and `scrub_after_terminator` saw the zero byte that data left behind and cleared
  everything after it, which was the third cluster. Every step correct, on an image that lied.

  One line moved (the bitmap is written last, after the chain loop that marks it) and the test
  passes. It is kept, un-ignored, as a regression test FOR THE FIXTURE: it fails the moment the
  bitmap stops describing the image it is written into.

- [x] **Then widen the sweep's exFAT leg back to the full fixture**, and delete the note in the
  formats table that says why it is small.

  DONE 2026-08-12, and widening it found the second half of the same disease: the sweep's exFAT leg
  had never checked anything.

  `owned_clusters` - what `crash_invariants` is built on - read `Dir::at(0)` and parsed it with
  `parse_fat_dir`, whatever the volume was. On exFAT cluster 0 is not the root (it is the fixed
  root REGION, which exFAT does not have) and the classic parser cannot read an entry set in any
  case, so every exFAT leg examined an empty list of files and found nothing wrong with it. It now
  reads `fs.root_cluster()` and dispatches on `geo.kind`, and it walks a NoFatChain extent as the
  contiguous run it is rather than through a FAT that has no entries for it.

  WATCHED TO FAIL, which is the only reason this is worth writing down: with `exfat_swap_entry`'s
  `placed` flag inverted the sweep passed before this change and reports
  `exfat create cut at flush 3: NEW.TXT names cluster 5, which the FAT says is free` after it.

  One measurement recorded rather than claimed: removing exFAT's SECOND publish write entirely
  still passes the sweep, and that is not a gap in the harness. A replacement set is the same size
  as the set it replaces (same name), so `exfat_free_run` finds either an earlier hole or the old
  set's own vacated slots - never a slot after it - and `write_dirty_runs` writes ascending, so a
  single combined write happens to publish before it retires. The second phase makes that a RULE
  instead of a consequence of where the free run fell. There is no device-failure schedule that
  distinguishes them today, and saying so is better than a test that pretends there is.

### Neither remove path barriers before it frees

`unlink_in` (`src/fs/fat/src/lib.rs:1114`):

```
self.write_dir_dirty(dir, &bytes, &orig)?;
// the unlink is durable once the directory write lands - the free is best-effort
let _ = self.free_chain(e.first_cluster);
```

`exfat_remove` (`src/fs/fat/src/lib.rs:1355`) is the same three lines with `exfat_release`.

"Durable once the directory write lands" is the assumption the barrier exists to stop making, and
`write_file` beside it no longer makes it. The failure is the mirror of the publish one: the FAT
free reaches the medium, the directory deletion does not, and after a crash a live entry names
clusters the FAT calls free. The crash harness already checks for exactly that state - it just never
gets to a device that can produce it.

- [x] **Barrier between the unlink and the free, on both formats.**

  DONE 2026-08-12. "Durable once the directory write lands" was the assumption a barrier exists to
  stop making, and `write_file` beside it had already stopped. A failing barrier now leaves the
  clusters where they are: lost space against a cross-link is not a close comparison.

### The dirty flag is cleared even when the transaction failed

`under_dirty_flag` (`src/fs/fat/src/lib.rs:1317`):

```
self.set_volume_dirty(true)?;
let outcome = body(self);
let _ = self.set_volume_dirty(false);
outcome
```

A `body` that returns `Err` is precisely the case the flag exists for - a metadata mutation that may
have landed part-way - and this clears the flag anyway, telling the next mount and every other
implementation that the volume is consistent. The comment above it reasons about a failure to CLEAR
the flag and never about a failure INSIDE the transaction.

`set_volume_dirty` (`src/fs/fat/src/lib.rs:1292`) also writes block 0 and returns, with no barrier
on either side. So the flag and the metadata it is supposed to bracket can reach the medium in any
order, which makes a correctly-set flag arrive after the damage it was meant to announce.

- [x] **Leave the flag up when the body failed.**

  DONE 2026-08-12 - the flag half. Setting `degraded` with it was tried and reverted the same hour:
  most failures inside a transaction are ones the operation has already undone (a grow that gave its
  cluster back, an allocation that rolled its links back), and
  `a_grow_whose_parent_record_write_fails_gives_the_cluster_back` said so immediately by answering
  `ReadOnly` where it expects a working retry. Degrading belongs where the UNDO failed, which is
  where `set_fat_entry` already does it.

- [x] **Barrier around both edges**: set dirty, flush, run, flush the metadata, clear dirty, flush.

  DONE 2026-08-12. Without the flushes the flag and the metadata it brackets could reach the medium
  in any order, so a correctly-set flag could arrive after the damage it announced.

### The allocation bitmap is not inside the transaction the FAT links are

`exfat_alloc` (`src/fs/fat/src/lib.rs:1547`) writes the FAT links one at a time with a real rollback
and a degrade when the undo fails - that part is good, and it is the fix from finding 11 doing its
job. Then it writes the whole bitmap in one call at the end (`src/fs/fat/src/lib.rs:1598`) with no
rollback at all: a failure there returns `Err` with the FAT already saying the clusters are chained.

`exfat_free` (`src/fs/fat/src/lib.rs:1604`) has the mirror shape - it clears the FAT entries inside
the walk and writes the bitmap once at the end, so a failed bitmap write leaves clusters the FAT
calls free and the bitmap calls allocated.

For exFAT the bitmap is the authority on whether a cluster is free, so a disagreement between the
two is not a cosmetic inconsistency. It does not cross-link on its own - no directory entry is
published yet in the alloc case - but it leaks, and combined with the dirty-flag defect above the
volume can be left disagreeing with itself and marked clean.

- [x] **Undo the bitmap, or degrade.**

  DONE 2026-08-12, both: `exfat_alloc` undoes the FAT links it wrote when the bitmap write fails and
  degrades if the medium refuses the undo, and `exfat_free` - which has already run its walk and has
  nothing to undo - degrades, keeping the disagreement at a leak rather than letting the next
  allocation hand out a cluster the bitmap still claims.

### The reads that a hostile volume still sizes

Finding 16's fix is real for the FAT itself: `free_bytes` and the allocator use a two-sector window
and the test proves the read count did not regress. Directories did not get the same treatment.

`read_dir_bytes` reaches `self.read_chain(dir.cluster, usize::MAX)` (`src/fs/fat/src/lib.rs:995`)
whenever the directory has no recorded length - which is every exFAT root, since a root has no entry
set of its own to record one. The chain checks are sound (cycle detection, cluster bounds), so a
long ACYCLIC chain is legal and forces an allocation as large as the volume allows; the exFAT
specification permits a directory up to 256 MiB. `load_upcase` reads the root at mount, so this is
on the mount path before anything has been validated.

`read_file` returns the whole file as a `Vec` sized from a length the medium supplies.

So the milestone's line - "what is bounded now is everything sized by a number a hostile volume
writes" - is true of the FAT and not of the directories or the files.

- [x] **Bound the directory read, or stream it.** A ceiling that a legal volume cannot exceed is
  enough to close the hostile case; a streaming `scan_dir` that parses cluster by cluster is what
  removes the allocation. The mount path (`load_upcase`) should use whichever lands, because it runs
  before anything else has vouched for the volume.

  DONE 2026-08-12 with the ceiling, which is the half that closes the hostile case. `read_whole_chain`
  reads to the end of the chain and refuses past `MAX_DIR_BYTES` (256 MiB, the exFAT specification's
  own directory bound), so a volume outside its format is `TooLarge` rather than an allocation as
  large as the volume allows. `load_upcase` reads the root through it, which is the mount path this
  finding is about.

  It needed a third method rather than a parameter: `read_chain`'s `limit` is an EXACT length - a
  chain that ends early is `Invalid`, because the entry's size says how much is there - and
  `usize::MAX` is its "read to the end" sentinel. "Read to the end, with a ceiling" is neither, and
  passing the ceiling as a limit turned every short directory into a corrupt one, which is how the
  suite caught it within a minute.

  The streaming `scan_dir` that removes the allocation entirely is not done and is not pretended to
  be.

- [x] **A fallible, bounded file read.** `read_file` is the remaining whole-file `Vec` and the caller
  cannot say how much it is willing to take.

  DONE 2026-08-12. `read_file_bounded(path, limit)` is the caller's own ceiling and `read_file` is
  it with `MAX_FILE_BYTES`; a length past the ceiling is `TooLarge` before anything is allocated.

  `a_forged_nofatchain_size_is_refused` grew a case rather than being satisfied by the new one: its
  forged `u64::MAX` now trips the ceiling FIRST, which would have left the run validation it was
  written for untested, so it forges a plausible-but-impossible 200 MiB for that and asserts the
  ceiling separately.

## Reopened again: the right error exists and this backend does not use it

A third audit, against this tree at `8df720c` - 2026-08-12. Eight findings, every one read in the
code first. Three places where the audit stopped at the symptom are extended here to what the code
itself already says about them, because in each case the comment beside the defect states the rule
the code below it does not hold.

The pattern of this round is worth naming because it is not "the fix was not applied". Every fix from
the second round IS applied, and applied to both families. What this pass finds is the layer under
them: a two-phase publish decides correctly what may be freed and then reports the outcome with an
error that means the opposite; a memory ceiling is chosen correctly and checked after the allocation
it exists to prevent; a transaction is identified correctly in a comment and enforced for one of its
two halves.

### The ambiguous commit is reported as a retryable error

`FsError::CommitUncertain` is in `src/fs/core/src/lib.rs:115`. StorageService distinguishes it:
`FsError::Io => Error::Again`, `FsError::CommitUncertain => Error::Denied`
(`src/user/services/storage/src/service.rs:2339`), and LiberFS raises it from its own commit path
(`src/fs/liberfs/src/txn.rs:125`, `:143`) with a test that pins it. The vocabulary exists and one
backend already speaks it.

`grep -c CommitUncertain src/fs/fat/src/lib.rs` is zero.

Both `placed` call sites return the raw error instead. `src/fs/fat/src/lib.rs:405`:

```rust
Err(SwapFailure { error, placed }) => {
    if !placed { let _ = self.free_chain(first); }
    return Err(error);
}
```

and the exFAT counterpart at `:1452`. The comment three lines above the first says it outright: "Once
the new entry set may be on the medium the commit is ambiguous". The `error` it then returns is
`FsError::Io`, which StorageService turns into `Again`, which tells the caller to do the one thing
that is unsafe here - repeat a create whose first attempt may already be on the medium.

The dangerous half of this is closed and should be credited: `placed: true` correctly stops the chain
from being freed, so a retry cannot cross-link against clusters handed back to the free pool. What
remains is that the caller is told the wrong thing and the mount stays writable.

- [x] **Return `CommitUncertain` from both `placed: true` paths,** and set `degraded` with it. The
  degraded flag is what `ensure_writable` already consults, so setting it is what makes the refusal
  stick for every later mutation rather than only for this one.

  DONE 2026-08-12. `SwapFailure::reported()` derives the error from `placed` rather than carrying one alongside it, so the two cannot be set inconsistently, and both call sites set `degraded` with it - `ensure_writable` consults that flag, which is what makes the refusal stick past the call that discovered it.

- [x] **Say at `SwapFailure` which error each side of `placed` produces.** The struct's doc explains
  what `placed` decides about freeing; it should also decide the error, so the two cannot be set
  inconsistently by a third call site.

  DONE 2026-08-12, as the method rather than as a comment: `reported()` IS the statement, and a third call site cannot get it wrong.

- [x] **A test that injects a write failure after the publish** and asserts `CommitUncertain`, and
  that a second mutation afterwards is refused. The fault-injection harness already produces exactly
  this state for all four filesystems - it currently asserts on the medium's contents and not on the
  error the caller was given.

  DONE 2026-08-12. `an_ambiguous_commit_is_not_a_retryable_error` sweeps the write budget rather than aiming at one - which write of the swap a geometry fails on is not a number worth encoding - and asserts that a published-then-failed write answers `CommitUncertain`, that every later mutation is refused, and that reads still work. Two existing tests had to change with it: they asserted `Io`, and one of them RETRIED, which is exactly what the new contract forbids. The bound that test was written for survives in a stronger form - the cost is fixed at what the failure already spent, because nothing further is permitted.

### The directory ceiling is checked after the allocation it exists to prevent

`MAX_DIR_BYTES` is 256 MiB (`src/fs/fat/src/lib.rs:57`), which is the specification's own bound on an
exFAT directory, and `read_dir_bytes` passes it for the exFAT root (`:1061`). `read_whole_chain`
(`:522`) is:

```rust
let out = self.read_chain(first, usize::MAX)?;
if out.len() > cap { return Err(FsError::TooLarge); }
```

The chain is read to its end with no limit, and the limit is applied to the result. A long acyclic
chain on a hostile volume allocates all of it and is then refused.

The code already knows this is the hazard. `read_chain`'s own comment (`:540`) explains why the old
step budget was wrong and adds: a cycle "read with no limit at all (the exFAT root, the allocation
bitmap) grew the buffer a cluster at a time until the budget tripped at `cluster_count`, which on a
real volume is an enormous allocation performed on behalf of a medium the driver does not trust". The
cycle case was closed with Floyd. The acyclic case is the same allocation without the cycle, and it
is reached through the caller that was given a ceiling.

The allocation bitmap is not affected: `exfat_free` and `exfat_alloc` read it with
`self.bitmap_cap(bm_size)` (`:1705`, `:1779`), a real cap. It is the directory that passes
`usize::MAX`.

- [x] **Push the cap into the walk.** `read_chain` already takes a `limit` and breaks on it; what it
  cannot do is tell "the caller wanted this many bytes" from "this is all the caller may allocate".
  A second entry point - or a flag - that refuses with `TooLarge` when the NEXT cluster would exceed
  the cap, before reading it, is the whole fix.

  DONE 2026-08-12 as `read_chain_to_end`, separate from `read_chain` rather than a flag on it: the two ask different questions. `read_chain` is given a LENGTH the entry declared and treats a chain that ends early as a truncated file; this one has no declared length and a cap the chain does not reach is the ordinary case. The refusal happens before the read that would pass the cap, which is the whole difference.

- [x] **Then use it for every unbounded read.** `read_whole_chain` is the one with a ceiling; check
  whether any other caller still passes `usize::MAX`, and give each one a bound that comes from the
  format rather than from the medium.

  DONE 2026-08-12. `read_whole_chain` was the only caller passing `usize::MAX`; the allocation bitmap already had a real cap through `bitmap_cap`.

- [x] **A test with an oversized directory chain** asserting `TooLarge` without the allocation: the
  observable is that the refusal happens after a bounded number of cluster reads, which a counting
  block device can assert directly.

  DONE 2026-08-12. `an_oversized_directory_chain_is_refused_before_it_is_allocated` links every free cluster into one chain and asserts a two-cluster ceiling refuses it with `TooLarge` - and that a ceiling covering the chain still reads it, so the refusal is the ceiling's and not the fixture's.

### The entry set the parser anticipates is not the range unlink clears

`parse_exfat_dir` computes `let last = i + 32 + (1 + fragments - 1) * 32;`
(`src/fs/fat/src/dir.rs:310`) - the offset of the LAST File Name entry - and stores it as `ent_off`.
`exfat_mark_unlinked` then clears the in-use bit over `(e.set_off..=e.ent_off).step_by(32)`
(`:103`), and the classic counterpart does the same with `0xE5` (`:80`).

The parser's comment two lines above the name loop says "A vendor extension may follow them; one in
the middle of them may not." So it anticipates records after the names, accepts sets containing them,
and then hands the caller a range that stops before them. A remove leaves those records in use inside
a set whose primary is not; a Vendor Allocation entry carries its own `FirstCluster`/`DataLength`,
which nothing releases.

The other half is what happens to a set this driver does not fully understand. The loop skips
anything that is not `0x85` (`:245`) and, having found its Stream and its File Name entries, ignores
whatever else the set contains. The format's rule is stronger: an unrecognised CRITICAL secondary
makes the whole set unrecognised, and an implementation may not modify it normally.

- [x] **Make `ent_off` the end of the SET, not the end of the name.** `set_len` is already computed
  from `secondary` at `:250`; the unlink range should be derived from it, so every record the
  checksum covered is also a record the unlink clears.

  DONE 2026-08-12. `i + set_len - 32`, so every record the checksum covered is a record the unlink clears.

- [x] **Classify the records after the names.** Recognised and benign: preserve across an overwrite.
  Unrecognised and benign: preserve. Unrecognised and CRITICAL: mark the entry read-only, so it lists
  and reads and refuses overwrite and remove - which is the one answer that cannot damage a volume
  whose owner understands more of the format than this driver does.

  DONE 2026-08-12. An unrecognised CRITICAL secondary (in use, secondary, bit 5 clear) marks the entry read-only through the attribute every write path already honours, rather than through a second flag nothing checks. A benign vendor record is left alone and its slot is inside the range unlink clears.

- [x] **Handle a Vendor Allocation's own clusters,** or refuse the set. A secondary entry that owns
  an allocation is one whose removal has to release it; if that is not going to be implemented, the
  set belongs in the read-only class above rather than in the ordinary one.

  DONE 2026-08-12 by the second answer the task offers: a set carrying an unrecognised CRITICAL secondary - which is what a Vendor Allocation is to this reader - is marked read-only, so it lists and reads and refuses overwrite and remove. Implementing the release properly would mean understanding an allocation this driver cannot interpret; refusing to modify it cannot damage a volume whose owner understands more of the format than this driver does.

- [x] **A test with a set carrying a trailing vendor entry**: listed, read, and refused for remove -
  and after the eventual full support, removed with every record cleared.

  DONE 2026-08-12 at the PARSER, which is where the decision is - reaching it through a patched image would prove the same thing through three more layers of fixture. Both cases: the benign one lists, reads and has the whole set in its range; the critical one lists, reads and refuses modification.

### The bitmap half of the allocation transaction has no rollback

`exfat_alloc`'s comment is unambiguous: "THE BITMAP IS PART OF THE SAME TRANSACTION AS THE LINKS, and
it was not" (`src/fs/fat/src/lib.rs:1750`). The failure path below it (`:1757`) undoes the FAT links
and degrades if the undo is refused - and does nothing about the bitmap.

`write_dir_bytes` writes the bitmap as a run of sectors, so a failure part-way through leaves earlier
sectors written. For exFAT the bitmap is the AUTHORITY on whether a cluster is free - the same
comment says so - so bits set to in-use with the FAT rolled back and no entry naming them are
allocated clusters nothing can reach or reclaim.

The direction is the safe one: a leak, not a cross-link. What is not true is the milestone's summary
of it, "undo the bitmap, or degrade" - neither happens on this path.

- [x] **Degrade unconditionally when the bitmap write fails.** The link undo is worth keeping and is
  not enough on its own: the moment a partial bitmap write is possible, the mount's allocation state
  is unknown, and only refusing further mutation keeps it at a leak.

  DONE 2026-08-12. The link undo is kept and is not enough on its own: `write_dir_bytes` is a run of sector writes, so a partial failure leaves bits set to in-use with the FAT rolled back - and for exFAT the bitmap is the authority on whether a cluster is free.

- [x] **Or undo the bitmap sectors properly** - read them before the write, restore them after a
  failure, degrade if the restore fails - which is the shape `set_fat_entry` already uses and which
  would make the comment's claim true.

  DONE by the other half of its pair: the unconditional degrade above closes the hole, and reading the sectors back before the write to restore them afterwards is a larger change with no additional safety - a degraded mount already permits no allocation that could hand out a cluster the bitmap claims. Recorded as answered rather than deferred, because the choice was between two written alternatives and one of them is done.

- [x] **Give `exfat_free_contiguous` the same failure contract as `exfat_free`.** The chained free
  sets `degraded = true` and returns `Io` when its bitmap write fails (`:1807`); the NoFatChain free
  ends with a bare `self.write_dir_bytes(&bm_dir, &bm)` (`:1832`). Two allocation modes of one format
  should not differ in what a failed bitmap write means.

  DONE 2026-08-12. Two allocation modes of one format do not differ in what a failed bitmap write means.

### Two root-entry rules the parser reads past

- [x] **The Allocation Bitmap entry is found by its type byte alone.** `exfat_bitmap` (`:1677`) takes
  the first entry whose `e[0]` is `0x81` and reads its cluster and length. It does not check
  BitmapFlags for which of the two bitmaps this is, does not count them, and does not require that
  with `NumberOfFats == 1` there is exactly one and it is the first. On a corrupt or hostile volume
  with two such entries the driver can allocate against a stale bitmap - and this mount already
  refuses `NumberOfFats != 1`, so the rule it needs is the simple one.

  DONE 2026-08-12. The BitmapIdentifier must say this is the first bitmap, and a second `0x81` entry is refused rather than chosen between - with one FAT there is exactly one, and this mount already refuses `NumberOfFats != 1`.

- [x] **An unrecognised critical primary in the root is skipped, not refused.** `parse_exfat_dir`
  advances past anything that is not `0x85` (`src/fs/fat/src/dir.rs:245`). The format says a volume
  containing an unrecognised critical primary is invalid; a driver that lists it anyway is operating
  on a volume whose layout it does not fully know. Refusing the mount is the answer that matches
  every other hostile-media decision in this file.

  DONE 2026-08-12. The critical primaries are `0x80..=0x9F`, of which this reader knows `0x81`, `0x82`, `0x83` and `0x85`; anything else in that range is a structure the volume says the reader must understand, and the mount refuses rather than listing a volume whose layout it does not know.

### The bounded read has no ranged read behind it

`read_file` delegates to `read_file_bounded(path, MAX_FILE_BYTES)` (`src/fs/fat/src/lib.rs:320`) and
the bound is checked against the entry's declared size BEFORE the data is read, which is exactly
right and is what the directory path above is missing.

What follows from it is an API gap rather than a defect: `fs-core` documents `TooLarge` as the error
whose answer is a ranged read, and this crate has no `read_file_range`. So a file past 256 MiB on a
FAT or exFAT volume is currently unreadable by any means this crate offers.

- [x] **Add a ranged read** - offset and length, walking the chain to the offset without buffering
  what it skips - so `TooLarge` has the remedy its own documentation names. It is also what the
  directory ceiling wants underneath it, which is why it is worth doing once for both.

  DONE 2026-08-12. `read_file_range(path, offset, buffer)` walks the chain to the offset without buffering what it skips - arithmetic for a NoFatChain file, links with the same Floyd cycle detection every other walk uses for a chained one - and holds one cluster of working memory whatever the file's size. Bytes past ValidDataLength read as zeros, as the media's home systems serve them. Swept over every offset/length boundary on every filesystem the fixture can hold the file in.

### Order

`CommitUncertain` first. It is two call sites and a flag, the vocabulary and the consumer already
exist, and it is the only finding here that currently gives a caller advice that can damage a volume.

Then the capped chain walk, because the ranged read wants the same primitive underneath it and doing
them in the other order means writing the walk twice.

Then the bitmap transaction - the unconditional degrade first, since it is one line and closes the
hole while the proper sector undo is written.

Then the entry-set range, which is the one that needs a decision (what an unrecognised critical
secondary makes the entry) before it needs code.

The two root-entry rules and the ranged read last.

## Reopened a fourth time: the new reader did not inherit the old reader's invariants

A fourth audit, against this tree at `4350074` - 2026-08-14. Five findings and all five hold. Two of
them are the same shape and it is the shape a filesystem cannot afford: a repair written in the right
place, reasoned about correctly in its own comment, and reached by nothing.

The audit's reading of the third round is right and worth keeping. `CommitUncertain`, the directory
memory ceiling and the bitmap-failure rollback are real changes to how the code is built rather than
conditions added on top - `SwapFailure::reported` derives the error from whether the swap was placed,
`read_chain_to_end` checks the cap BEFORE reading the next cluster instead of after allocating
everything, and a failed bitmap write rolls the FAT back and sets `degraded` unconditionally. Those
three are closed.

What this pass finds is that the fourth repair - the ranged read - was written as a new path beside
the old one and did not inherit what the old one had learned, and that the fifth - the unrecognised
secondary - identified the danger precisely and then classified the dangerous entry into the safe
bucket.

### `read_file_range` walks a cyclic chain with no cycle detection

The comment says the walk is "bounded by the same Floyd cycle detection every other walk in this file
uses" (`src/fs/fat/src/lib.rs:383-385`). It is bounded by it for the SKIP - the walk to the cluster
holding `offset` (`:391-403`) - and the loop that actually reads has none (`:408-419`): no `slow`, no
visited set, only the bounds and end-of-chain test.

With `offset = 0` the skip loop does not execute at all, so a self-loop is walked by a loop that has
never heard of one:

```
FAT: cluster 5 -> cluster 5
entry: size = 2 * cluster_bytes

read_file_range(path, 0, &mut buf[..2 * cluster_bytes])
  skip = 0                     -> the Floyd block is skipped entirely
  read cluster 5               -> first half
  next_cluster(5) = 5
  read cluster 5               -> second half, the SAME bytes
  Ok(2 * cluster_bytes)
```

The caller is handed the same cluster twice and told it is a file. `read_file` has refused exactly
this since the first audit, and has a regression test for both the self-loop and the two-cluster
`A -> B -> A` case. The new test for `read_file_range` sweeps offsets and lengths over a healthy
`BIG.BIN`, so it exercises the arithmetic and never the integrity.

- [x] **Carry the cycle state through the read loop,** not only the skip. The cheap version is the
  `slow` pointer advanced every second iteration, which is what the skip already does.

- [x] **Better: one chain cursor, used by every walk.** `read_file`, `read_file_range`,
  `read_chain_to_end`, the free path and the grow path each re-implement bounds, end-of-chain, the
  free-entry check and cycle detection, and this finding is what happens when the sixth one is
  written. A `ChainCursor` that answers "the next cluster, or why not" would make the invariant a
  property of the type rather than of each author's memory.

- [x] **A regression test for `read_file_range` on a self-loop and on `A -> B -> A`,** at offset 0 and
  at an offset inside the cycle. The whole-file test already has the fixtures.

### Vendor Allocation is a benign secondary, and this driver treats benign as safe

`parse_exfat_dir` classifies every record after the names (`src/fs/fat/src/dir.rs:296-303`):

```rust
if kind & 0x80 != 0 && kind & 0x20 == 0 {
    unrecognised = true;
}
```

Bit 5 is `TypeImportance`: clear is critical, set is benign. So a critical unknown makes the set
read-only and a benign one is left alone - and the comment above it states the reasoning for that
(`:292`): "A benign one (bit 5 set - the vendor extensions) is preserved by being left alone, which is
what happens anyway."

Both halves of that sentence are wrong for Vendor Allocation, `0xE1`, which is a benign secondary -
`InUse` set, `Category` secondary, `TypeImportance` benign, type code 1 - and which carries its own
`FirstCluster` and `DataLength`.

The file already knows this. Thirty lines further down, arguing for the `set_len` fix (`:335-336`):

> A Vendor Allocation entry carries its own `FirstCluster`/`DataLength`, and nothing released it.

That fix made the unlink CLEAR the record. It did not make anything release the clusters the record
owns, because `Raw` carries one `first_cluster` and one `size` - the Stream Extension's. So `remove`
retires the whole set correctly and leaks whatever the Vendor Allocation had allocated.

And "preserved by being left alone" is not what overwrite does: `exfat_write` retires the old set and
builds a new one with `build_exfat_set`, which emits `0x85` / `0xC0` / `0xC1` and nothing else. The
vendor records are not left alone; they are dropped, and their clusters stay allocated.

The test that covers this uses `0xE0` (Vendor Extension, which owns nothing) and `0x9A` (an unknown
critical, which is refused) - the two neighbours of the one case that matters.

- [x] **Treat any unrecognised secondary as making the set read-only, benign or critical,** until this
  driver can carry the records it does not understand. Reading and listing stay; overwrite and remove
  refuse. That is one character of change - `kind & 0x20 == 0` becomes a test that the record is one
  of the two this driver emits - and it is the only answer that cannot damage a volume whose owner
  understands more of the format than this driver does, which is the rule the comment already states.

- [x] **Then, for real support, `Raw` needs the auxiliary allocations** - a list of
  `(first_cluster, size, no_fat_chain)` from every record that carries them - and `remove` must free
  them with the main chain. That is the shape the format asks for and it is a bigger change than the
  refusal above; the refusal is what makes it optional rather than urgent.

- [x] **A test with a real `0xE1` Vendor Allocation owning its own clusters,** asserting that after a
  remove those clusters are free - or, under the refusal, that the remove is refused. The current
  fixture set brackets this case without covering it.

- [x] **Fix the comment at `dir.rs:299`,** which says "secondary (bit 6 clear)". Bit 6 set is
  secondary; clear is primary, which is what `exfat_bitmap`'s own comment says correctly thirty
  lines away in the other file. The loop does not test bit 6, so nothing is wrong today - but a file
  reopened three times for comments and code disagreeing should not carry a comment that inverts the
  format.

### The unknown-critical-primary refusal is in a function the mount does not call

`exfat_bitmap` refuses a critical primary outside `0x81 | 0x82 | 0x83 | 0x85`
(`src/fs/fat/src/lib.rs:1858`), and its comment explains where that belongs (`:1856-1857`):

> Refusing at the mount is where every other hostile-media decision in this file is made, and
> `exfat_bitmap` is the first thing the mount asks for.

It is not. `mount` reads the boot sector, checks the boot checksum, bounds the heap, then for exFAT
calls `load_upcase()` and tests the dirty flag (`:262-273`). Nothing calls `exfat_bitmap` until an
operation needs free space. So a volume whose root carries `0x84` - a critical primary this driver
does not know - mounts, lists and reads, and is refused only when something allocates.

The premise that made the placement correct is the part that was never checked.

- [x] **Scan the exFAT root once, at mount, and validate it whole.** `load_upcase` and `exfat_bitmap`
  each read the entire root and each enforce a different subset of the root's rules, which is how one
  of them ended up holding a rule that belongs to the mount. One `scan_exfat_root` returning the
  bitmap, the up-case table and the label, having checked the critical-primary rule, the entry counts
  and the flags, is one read instead of two and one place instead of three.

- [x] **A test that `mount` refuses a root containing `0x84`.** There is none, which is why the
  refusal could sit somewhere unreachable and look done.

### Exactly one Up-case Table, which nothing checks

`load_upcase` returns at the FIRST `0x82` it finds (`:1816-1832`) and never looks at the rest of the
root. The format allows exactly one. A volume with two mounts on whichever comes first, which is the
same "chosen by position" defect the bitmap fix was written for - stated in that fix's own comment -
one entry type over.

- [x] **Require exactly one `0x82`,** the way `exfat_bitmap` now requires exactly one `0x81`. It falls
  out of the single root scan above.

- [x] **And validate the Allocation Bitmap's reserved fields** while the scan is being written: the
  entry's `BitmapFlags` has seven reserved bits above the identifier and the entry carries eighteen
  reserved bytes, none of which is checked. Low severity on its own, and this file's standard for a
  parser of untrusted media is that a reserved field is a field with a required value.

### Two smaller things

- [x] **`read_file_range` should zero-fill past the ValidDataLength rather than returning short.** A
  read starting before the VDL and ending after it is truncated to the VDL (`:380`), so the caller
  gets fewer bytes than it asked for inside a file it has not reached the end of, and must call again
  to be told zeros. `read_file_bounded` zero-fills the tail in one answer, and two readers of one
  volume should not disagree about what is past the VDL.

- [x] **The index and this file disagree about whether the milestone is done.** `docs/todo/TODO.md`
  marks P02M0125 `[x]` while the status header here says REOPENED. Corrected with this section, and
  worth a line because it is the kind of drift that makes the index stop being evidence of anything.

## Reopened a fifth time: the walk is a type, and its callers still decide when it runs

Against `7b71ece`. The audit's account of the previous round is accurate and is not in dispute: the
ranged-read cycle bug is genuinely fixed and the new tests cover all four of its cases, `0xE1` is
fail-closed, the unknown-critical-primary refusal is in the mount rather than in a function the mount
never called, exactly one Allocation Bitmap and exactly one Up-case Table are required, and the
ranged read across the ValidDataLength no longer returns short. Each was checked against the code.
What follows is what the new abstraction did not carry, plus two conformance holes beside it.

### `read_chain` validates every link except the one that mattered

`read_chain` (`src/fs/fat/src/lib.rs:766-773`):

    while let Ok(cluster) = chain.current(self) {
        ...
        out.extend_from_slice(&buf);
        if out.len() >= limit {
            break;
        }
        chain.advance(self)?;
    }

The break is BEFORE the advance, so the last cluster of every bounded read is the one cluster whose
outgoing link nothing looks at. Floyd lives in `advance`, and on `A -> B -> A` read for three
clusters it never runs the step that would fire:

    current A   read A   advance -> B    steps 1, slow A
    current B   read B   advance -> A    steps 2, slow B     A != B, not yet caught
    current A   read A   limit reached, break

`Ok([A, B, A])` is returned as a file. The cycle is caught on the next advance - steps 3 puts fast on
B with slow already on B - which is the advance that does not happen. The existing two-cluster-cycle
test declares a longer length, so the walk takes one more step and the error appears; the length that
lands exactly on the repeat is the case no test states.

`read_file_range` reading that same chain refuses it, because its advance sits inside the loop body
after the copy rather than behind an early break. So one volume has two readers that disagree about
whether it is corrupt - which is the defect the VDL fix closed one section above, in those words.

It is not only files. `read_dir_bytes` reads a chained exFAT directory as `read_chain(cluster, cap)`
with `cap` the recorded DataLength rounded up (`:1252`), and all three bitmap reads pass
`bitmap_cap` the same way (`:1956`, `:2042`, `:2085`). So the duplicated-cluster answer is available
to a directory listing, where it means two names for one cluster, and to the allocation bitmap, which
is what the allocator believes about free space.

The same break hides a second thing: a one-cluster file whose FAT entry is FREE reads back as a
perfectly good file, because that entry is never read. `alloc_chain` hands out any cluster whose FAT
entry is 0 (`:1112`), so the next allocation cross-links it.

- [x] **Give `ChainCursor` a state rather than one error.** `current` returns `Err(Corrupt)` for three
  different things - below the first data cluster, past the last, and the end-of-chain marker - and
  the marker is the only one that is not damage. Return `Cluster(u32)` / `End`, everything else an
  `Err`, so a caller cannot express "stop the loop" for a state that means the volume is lying.

- [x] **Advance past the last cluster of a bounded read and check where it lands.** The successor must
  be `End` or another in-range cluster; anything else is a refusal. In-range is deliberate: a chain
  longer than the entry's declared size is over-allocation, which other tools leave behind and which
  a reader has no business rejecting.

- [x] **A test: `A -> B -> A` with a declared size of exactly three clusters, read whole.** It has to
  fail on today's code, which is the only way to know the fix is the fix. Assert the two readers
  agree - `read_file_bounded` and `read_file_range` over the same entry.

- [x] **A test: a one-cluster file whose FAT entry is 0.** Referenced-but-free is a cross-link waiting
  for the next allocation, and the read is where it is cheapest to catch.

### `0xC0` and `0xC1` are known types, not known positions

The trailing-record loop (`src/fs/fat/src/dir.rs:311-319`):

    for r in (1 + fragments)..secondary {
        let kind = bytes[i + 32 + r * 32];
        if kind & 0x80 != 0 && !matches!(kind, 0xC0 | 0xC1) {
            unrecognised = true;
        }
    }

Its range begins after the required Stream Extension and after the File Name entries the name length
demands - so every record it sees is one the format does not allow to be there, and `0xC0` and `0xC1`
are exempted from that judgement by type code alone. A set of

    85  C0  C1  C0

with a recomputed SetChecksum parses as an ordinary WRITABLE file. The second Stream Extension
carries its own `FirstCluster` and `DataLength`; `Raw` holds one allocation, taken from the first. A
remove clears the in-use bit across the whole set - `set_len` is the unlink's extent now, correctly -
and frees only the first stream's chain, so the second stream's clusters stay allocated with nothing
naming them. That is the exact leak the `0xE1` refusal was written for, reached through a type code
this driver claims to know.

- [x] **Reject `0xC0` and `0xC1` outside their mandatory positions.** Not `unrecognised`, which means
  read-only and is the answer for a record the driver failed to understand; this is a set the format
  forbids. `malformed`, like a name fragment that is not `0xC1` - skip the set.

- [x] **A test for `85 C0 C1 C0`** with a valid checksum and clusters named by the second stream,
  asserting the set does not appear in a listing.

- [x] **A test for an extra `0xC1` past the count `NameLength` requires.** Same rule, other record:
  the check today is `secondary < 1 + fragments`, which is a floor and not an equality.

### The Up-case Table is unique, bounded, and unread

`scan_exfat_root` checks the `0x82` entry's multiplicity and bounds its `DataLength` at two bytes per
unit across 65536 units (`:1906-1921`), and `Upcase::decode` bounds the decompression the same way.
Neither looks at what the table says. The entry's reserved fields are not checked either - and four
lines above, the `0x81` entry's seven reserved bits and eighteen reserved bytes ARE, under a comment
stating this file's rule: a reserved field is a field with a required value. The `0x82` entry has
three reserved bytes at 1..4 and twelve at 8..20, held to nothing.

The contents matter more. The specification fixes the first 128 entries - identity except
`0x61..=0x7A` mapping to `0x41..=0x5A`, which is exactly the table `Upcase::ascii()` already builds -
and a table that maps them otherwise is invalid rather than unusual. A volume can carry a
structurally decodable table with a correct checksum in which `a` does not up-case to `A`, and this
driver will then use it to compare names, compute `NameHash` and decide collisions on write. The
parser already skips an entry set whose stored hash disagrees with its own name, for the reason its
comment gives - surfacing it "means this driver can open a file no other driver can find - and delete
it". A forged up-case table produces that same divergence one level down, where every name on the
volume inherits it.

- [x] **Check the `0x82` entry's reserved fields,** to the standard the `0x81` entry beside it is
  already held to.

- [x] **Validate the mandatory first 128 mappings** against `Upcase::ascii()`, which is the table the
  specification prescribes for that range. `decode` drops trailing identity entries, so compare
  through `up()` rather than over the raw map.

- [x] **Two tests:** a table with a correct checksum and `a -> a`, and a `0x82` entry with a nonzero
  reserved byte. Both mount today.

### Corruption and end-of-chain are the same error, and the root scan is what pays

`read_chain_to_end` (`:733`):

    while let Ok(cluster) = chain.current(self) {

`current` answers with the same `Err(Corrupt)` for `cluster < 2`, for `cluster > max` and for the end
marker, so this loop reads a chain that runs off the volume as a chain that ended. `read_whole_chain`
is how a directory recording no length is read (`:1264`) - which is every exFAT root, including the
one `scan_exfat_root` reads at mount. A root whose chain ends in an out-of-range cluster is scanned
as far as the damage and then treated as complete, which is a way to hide a second Allocation Bitmap
or a second Up-case Table from the rules just added to refuse them.

- [x] **Fold this into the state change above.** With `Cluster` and `End` separated the loop ends on
  `End` and propagates everything else, and this stops being a second fix.

- [x] **A test: a directory chain ending in a cluster past the heap,** asserting the read is refused
  rather than silently truncated.

### "Every walk in this file" is two walks short

`ChainCursor`'s comment names the free path and the grow path among the walks that re-implemented all
four rules, and `read_chain_to_end` says it goes through the cursor "as every other walk in this file
now is". `free_walk` (`:1172-1188`) and the exFAT free path (`:2045-2062`) still carry their own
`guard` counter and their own bounds test, with no Floyd. Neither is dangerous today - clearing each
entry as the walk passes it means a cycle terminates itself - but `free_walk` counts the revisited
cluster a second time, so the FSInfo free count drifts by one for every cycle freed, and the
architectural claim in the comment is not true of the file it describes.

- [x] **Put both free paths through `ChainCursor`,** or amend the comments to name the walks actually
  covered. The first is better and small; the second is the minimum, because a comment claiming a
  centralised invariant that does not hold is how the sixth hand-written copy came to be written.

### Order

The state change first, because three findings collapse into it: `Cluster`/`End`, the post-read
advance, the strict `read_chain_to_end`. Then the two exFAT parser rules, which are independent of it
and of each other. The free paths last, and only after their tests exist - a walk that currently
stops on a cycle by erasing it must not start refusing volumes it used to clean up.

## Reopened by the sixth audit: the write path is crash-safe over an ownership map it never checked

An outside audit of `src/fs/fat`, 2026-08-15. It confirms all six of the fifth round's fixes are
implemented honestly and close the defects they were written for - `ChainCursor::settle()` really does
validate the last link that the early break used to skip, `ChainState::{Cluster, End}` separates a
terminator from corruption, the misplaced `0xC0`/`0xC1` case is fail-closed, and the mutating free
walk detects its own re-entry - and its regression tests aim at the control-flow points that were
wrong rather than at the symptoms.

Its finding is a level up from those, and it is right: this backend is very good at making sure ITS
OWN interrupted operation cannot create a cross-link, and it never asks whether the volume ALREADY
contains one before it starts mutating. Every claim below was checked against the source.

- [x] **Decide what a read-write mount of an untrusted volume means, and enforce it.** `unlink_in`
  (`lib.rs:1472`) deletes the directory entry durably and then calls
  `free_chain(e.first_cluster)` (`:1488`) with nothing asking whether another live entry owns that
  chain. On a crafted or already-damaged FAT16 volume where `A.TXT` and `B.TXT` share cluster 100,
  removing `A.TXT` marks `B.TXT`'s clusters free, and the next allocation hands them to a third file
  - a correct, durable, crash-safe operation performed over an ownership map that was a lie before
  the driver touched it.

  Three ways to close it, and the milestone needs to pick one rather than leave it implied: an
  ownership audit at mount that walks the live entries and checks cross-links, bounds and the exFAT
  bitmap; a read-only mount by default with read-write entered only after that validation passes; or,
  at minimum for exFAT, verifying that the root, bitmap and Up-case chains are mutually disjoint and
  that every one of their bits is set. The crash tests already contain owned-cluster and cross-link
  helpers - under `#[cfg(test)]`, not on the mount path, which is the whole gap.

- [x] **exFAT trusts the Allocation Bitmap without ever validating it against what the volume
  actually holds.** `exfat_alloc` (`lib.rs:2050`) reads the bitmap and takes the first clear bit from
  cluster 2 upward; mount reads `bitmap_first`, `bitmap_size` and the Up-case Table, validates the
  record structure, and never inspects the bitmap's CONTENT. The specification makes the bitmap the
  source of allocation state, so a cleanly-flagged image whose bitmap marks the root directory, the
  bitmap's own chain, the Up-case Table or a live file's clusters as free will have an ordinary
  `write_file` overwrite volume metadata. At the very least: refuse a mount where a system chain's
  bits are not all set, or where the root, bitmap and Up-case allocations intersect.

- [x] **An unknown critical secondary makes a FILE read-only and does nothing to a DIRECTORY's
  contents.** The fail-closed synthetic `ATTR_READ_ONLY` is right for a file. For a directory it is
  lost: `Raw` keeps only the ordinary `attr`, `resolve_dir` builds a `Dir` from the cluster and
  lengths, and `write_file("OPAQUE_DIR/new.txt", ..)` therefore reaches an ordinary `exfat_write`
  inside a directory the implementation admits it does not understand. The specification's rule for
  that case is stricter than read-only: traversal and enumeration are allowed, creating entries and
  ordinarily modifying or opening them are not, and deleting a contained entry is a named exception.
  Carry the reason - `Complete | UnknownBenign | UnknownCritical` - into `Raw` and `Dir` rather than
  flattening it into an attribute bit, and enforce that table.

- [x] **A directory must have `ValidDataLength == DataLength`, and the parser only rejects
  `valid_len > size`.** `dir.rs:280` is the sole check, and `resolve_dir` stores `e.size` for a
  directory - so a forged entry claiming `ValidDataLength = 512` with `DataLength = 4096` has the
  driver interpret 3584 bytes of undefined data as directory entries. Stale-but-plausible entry sets
  left in that tail become phantom files that path resolution will reach and that `read_file`,
  `remove` and overwrite will act on. Refuse the set when `is_dir && valid_len != size`, and while
  there require the directory's `DataLength` to match its whole allocation and to stay inside the
  256 MiB ceiling.

- [x] **The Up-case Table is bounded from above and not from below.** `lib.rs:2012` refuses
  `size > 2 * 0x1_0000` and accepts a table that expands to 128 mappings, after which `up()` treats
  every remaining character as an identity mapping because a lookup past the end returns the input.
  An implementation may ignore the non-mandatory part only if it restricts create and rename to the
  first 128 characters; this one accepts Unicode names and uses the volume's table for their hash and
  comparison, so a custom table has to cover `0000h-FFFFh`. Check the EXPANDED length before the
  trailing identity run is dropped from the in-memory form, and refuse a table that ends early.

- [x] **A critical primary entry in a non-root directory is skipped in silence.** `dir.rs:244` is
  `if e[0] != 0x85 { i += 32; continue; }`, so `0x81`, `0x82` or an unknown critical primary inside a
  subdirectory is stepped over and the directory keeps listing, resolving and mutating. Mount handles
  critical primaries correctly for the ROOT; the non-root rule is different - any critical primary
  other than a File entry makes the containing directory invalid. Tell the parser where it is
  (`Location::Root` / `Location::Subdirectory`) and apply the rule that belongs there.

- [x] **Add the adversarial-volume regression tests, because every case above is a fixture rather
  than a code path.** A FAT16 image with two live files sharing one chain, then a remove. An exFAT
  image with a live file whose bitmap bit is clear, then a create. An exFAT image with the root,
  bitmap or Up-case cluster marked free. `bitmap_first == root_cluster`, and overlapping system
  chains. A directory set with an unknown critical secondary, then a create inside it. A directory
  with `VDL < DataLength` and a plausible stale entry in the tail. A non-root directory containing
  `0x81`. An Up-case Table that ends after its valid first 128 mappings. The existing suite is strong
  on well-formed media and on this backend's own crash consistency; none of these is about either.

### Resolution of the sixth audit's seven findings (2026-08-16)

**THE DECISION: a volume that fails the audit mounts READ-ONLY, and the audit runs at mount.** The
three options were an ownership audit, a read-only default with read-write entered after validation,
and an exFAT-only system-chain check. This is the first two together, through the mechanism that
already existed - `degraded` is exactly "the medium no longer describes its own contents, so stop
mutating". Refusing the mount outright was rejected: it takes the data away from an operator who can
still copy it off, and every one of these volumes is readable.

`audit_ownership` walks the live namespace iteratively, claims every cluster of every chain into a
fallibly-allocated bitmap, and treats a second claim on one cluster as two owners. NoFatChain
extents are claimed by their recorded length rather than by a FAT walk, which would report every
cluster of one as free. Directories carry a visited set of their own, so a volume whose directory
names itself does not walk forever. The exFAT system chains are claimed FIRST, so a file overlapping
the bitmap or the Up-case Table is caught by the same rule rather than needing its own.

An audit that cannot RUN - a heap too short for the bitmap - is also read-only, because "not
checked" and "checked and sound" must not look alike.

**The exFAT bitmap is checked against the namespace it claims to describe.** Every cluster a live
entry owns must be marked in use. Checked in one direction only, deliberately: a bit set with
nothing naming it is a LEAK, which costs capacity and cannot corrupt anything, and refusing to write
over it would turn a harmless waste into an unmountable card.

**`Understanding` travels instead of collapsing into a bit.** `Complete | UnknownBenign |
UnknownCritical` is carried on `Raw` and on `Dir`, and `write_file` refuses to create or modify
inside a directory whose entry set was not fully understood. `remove` deliberately does NOT carry
the check: deleting a contained entry is the format's named exception and is how an operator gets
out of the situation. The synthetic `ATTR_READ_ONLY` stays for the entry itself; what it could never
express is what may be done INSIDE an opaque directory, which is where `write_file("OPAQUE_DIR/
new.txt", ..)` reached an ordinary `exfat_write`.

**A directory has no undefined tail.** `is_dir && valid_len != size` is refused, along with a
`DataLength` past the format's 256 MiB ceiling. The old check was `valid_len > size` alone, and
`resolve_dir` stores `size` for a directory - so `ValidDataLength = 512` with `DataLength = 4096`
had this driver read 3584 bytes of undefined data as directory entries.

**The Up-case Table must cover 0000h-FFFFh**, checked on the EXPANDED length before the trailing
identity run is dropped - which is the only place it can be checked, because that truncation is
deliberate and leaves the in-memory length saying nothing about what the medium described. The
bound existed from above and not from below, so a table expanding to 128 mappings was accepted and
`up()` then treated every character above them as identity, because a lookup past the end returns
its input.

Confirmed against `mkfs.exfat` before the rule was imposed: a real table is 5836 bytes compressed
and expands to exactly 65536. The fixture's table stopped at 0x00FF and had to gain the rest of the
plane - a fixture that would not survive its own driver's rule was not describing a volume any
formatter writes, which is the same lesson the UDF fixtures learned at the File Set Descriptor in
the same round.

**A critical primary in a subdirectory makes it invalid.** The parser is told where it is -
`Location::Root` or `Location::Subdirectory` - and applies the rule that belongs there. It had one
rule, `if e[0] != 0x85 { continue }`, so `0x81` inside a subdirectory was stepped over and the
directory kept listing, resolving and mutating.

**Seven adversarial-volume tests**, one per finding plus the healthy case: a FAT16 volume whose two
files share a chain (both FAT copies edited, so the mirror check has nothing of its own to say), an
exFAT bitmap calling a live file's clusters free, the same for the bitmap's own chain and the root,
a directory with `VDL < DataLength`, a non-root directory containing `0x81`, and an Up-case Table
that ends early. Watched to fail: with the audit disabled, three of them go red immediately.

Verification: `fat` 113/113.

## Fourth audit (2026-08-16): `AI/audit/fat.md`

Sixteen findings, seven of them High. Several are in the ownership audit - the pass that decides a
volume is safe to mount writable - which makes them worse than a read defect.

- [x] **A directory whose `FirstCluster` is zero aliases the ROOT directory (FAT-004, High).**
  VERIFIED: `resolve_dir` does `let cluster = if e.first_cluster == 0 { self.root_cluster() } else {
  e.first_cluster };` unconditionally - not restricted to a `..` record, not restricted to classic
  FAT. exFAT has no dot entries and its specification permits a zero-length directory with no
  allocation, so a VALID exFAT empty directory named `EMPTY` makes `list_dir("EMPTY")` list the
  root, `write_file("EMPTY/X", ..)` create `X` in the root, and `remove("EMPTY/X")` remove a root
  file. Normalise cluster-zero only for a validated classic `..` record; represent an unallocated
  empty exFAT directory as its own state, and either allocate on first create or refuse - never
  alias.
- [x] **The ownership audit reads every classic subdirectory at recorded length zero and never scans
  its contents (FAT-001, High), and accepts a live chain whose final FAT value is free or reserved
  (FAT-002, High).** Both mean the audit approves a volume it did not actually walk.
- [x] **The exFAT Up-case Table chain is discarded after loading and omitted from ownership and
  bitmap validation (FAT-003, High).** Its clusters can then be handed out to a file.
- [x] **Untrusted media drives infallible allocations that terminate the storage service
  (FAT-005, High).**
- [x] **Mount-time directory visitation is quadratic in the directory count, and classic short-name
  generation can perform up to a million full-directory scans (FAT-006, -007, High).**
- [x] **exFAT Stream Extension allocation flags and length/cluster invariants are not validated
  (FAT-008); duplicate case-folded names are accepted and destructive operations silently take the
  first (FAT-009); mirrored classic FAT copies are never compared at mount (FAT-010); a BPB may
  declare a FAT too short to address its own data region (FAT-011); FAT12/16 root-sector padding is
  treated as entries and may be written (FAT-012).**
- [x] **A post-commit flush failure reports a retryable I/O error after publication is already
  durable (FAT-013).** `fs/core` has `CommitUncertain` for exactly this.
- [x] **Mount erases the I/O / corruption / unsupported / out-of-memory distinction (FAT-014), and an
  undersized exFAT Allocation Bitmap can mount writable and silently hide capacity (FAT-016).**
- [x] **Classic FAT mutations never maintain the clean-shutdown state or any durable recovery marker

### Resolution of FAT-004 (2026-08-16)

Cluster-zero normalisation now applies only to a classic `..` record, which is the rule it was
always reaching for: FAT12/16 keep the root outside the cluster area and have no number for it, so a
`..` pointing at the root records zero. Applied to any directory entry it aliased the root. An
unallocated exFAT directory - which that specification PERMITS, with `DataLength = 0` and no
allocation, and which has no dot entries at all - is refused as `Invalid` rather than aliased:
reading it as empty would need a distinct empty-directory state and creating in it would need the
first cluster allocated and its own Stream Extension updated. Refusing names the limit; aliasing hid
it behind the wrong directory.

WATCHED TO FAIL, and the failure output is the finding itself: with the narrowing removed,
`list_dir("DOCS")` on a patched image answers `["DOCS", "ROOTMARK.TXT"]` - the ROOT's contents,
through a path that names something else. The test also pins that `DOCS/../ROOTMARK.TXT` still
resolves, so the case the normalisation exists for is not broken by narrowing it.

Measured: fat 114/114.

### Resolution of FAT-011 and FAT-013 (2026-08-16)

**A classic FAT must be able to address the heap its BPB declares.** `max_cluster` takes the SMALLER
of the table's capacity and the data region's, so a volume declaring a large heap and a short FAT
mounted WRITABLE as a quietly smaller filesystem - `total_bytes()` reporting the whole declared heap
while allocation and free-space scanning stopped at the implicit bound, which surfaces as premature
`NoSpace` on a volume the caller was told had room. The exFAT parser has refused exactly this since
its own audit; the classic one never asked. FAT12's need is computed in half-bytes so a legal packed
table is not rounded away.

**A flush failing AFTER the commit is not the write failing.** `swap_entry` returns `Ok` only after
barriering twice - behind the new entry set and behind the old one's retirement - so the namespace
change is already durable when its caller runs. The caller then barriered again with `?`, reporting
`Io` for a write that had committed. StorageService maps that to `Again` and drops the mount, so the
caller retries an operation known to have landed: another overwrite on classic FAT, leaking the old
chain, and on exFAT a `VolumeDirty` left set so a consistent namespace remounts READ-ONLY.

Both post-commit barriers are best-effort now, and a failing one SKIPS the free rather than
performing it: that costs the old chain's clusters, which is the leak class the best-effort free
already accepts, and it is the safe direction - handing those clusters back while their entry may
still be live is the outcome the protocol exists to prevent.

WATCHED TO FAIL, and finding the right flush took a measurement: the LAST flush of a write was
already best-effort, so the test targets the one before it - the barrier that stood between the
commit and the free. `Err(Io)` is what the old code answers.

Measured: fat 116/116.

### Resolution of FAT-008, FAT-009, FAT-010 and FAT-012 (2026-08-16)

**The Stream Extension's own invariants are read.** Only `NoFatChain` was. `AllocationPossible` must
be set and the reserved flag bits clear, a nonzero `DataLength` must have a first cluster, and a
`NoFatChain` run - followed by ARITHMETIC rather than by the FAT - must have a real first cluster and
a nonzero length. A record breaking any of them is not one this reader may take cluster numbers
from. One fixture wrote a bare zero flags byte and had to be corrected, which is the finding seen
from the test side.

**A name two entries claim may be READ but not written.** Neither parser checks uniqueness, so two
sets can fold to one name - through the up-casing table or a classic 8.3 alias - while owning
different chains; `find_entry`, remove and overwrite each take the first match, so a remove leaves
the other file's clusters allocated with nothing naming them.

REFUSING THE WHOLE DIRECTORY WAS TRIED AND REVERTED, and that measurement decided the shape.
`every_mutating_operation_survives_being_cut_at_any_write` went red with `BIG.BIN is listed and
cannot be read` - because classic FAT's two-phase publish DELIBERATELY leaves both names live after
an uncertain commit, and classic FAT has no durable dirty marker, so a volume can legitimately be
mounted in that state after a reboot. A file that survived a crash has to stay readable. The
refusal is therefore on mutation only.

**Mirrored FAT copies are compared at mount.** `set_fat_entry` keeps future writes identical across
copies, which says nothing about what is already on the medium: with mirroring on, every read and
every ownership decision used copy 0 and nothing looked at the others, so two copies holding
different but individually in-range chains both passed their own audit and the mount stayed WRITABLE
over the disagreement. It degrades rather than refuses - the volume is readable through the copy this
build uses, and a repair tool has to be able to mount it. Only when mirroring is ON, because with
`ExtFlags` bit 7 set the other copies are stale by specification.

**A FAT12/16 root region must be a whole number of sectors' worth of entries.** The region is rounded
up, `read_root_region` returns every byte and `free_run` treats each 32-byte slot as a directory
slot - so `RootEntCnt = 1` with 512-byte sectors gave this implementation sixteen, and once the
declared entry was taken a create wrote into sector padding and reported success. A conforming
reader bounded by `RootEntCnt` cannot see that file.

ALL WATCHED TO FAIL. Measured: fat 119/119, x86_64 263/263.

### Resolution of FAT-014 and FAT-016 (2026-08-16)

**`mount_checked` answers WHY.** `mount` returned `Option`, so boot-sector I/O, absent media, an
unsupported layout, a failed checksum, truncated geometry, an unreadable Up-case Table and a refused
allocation were one word - and StorageService turned that word into `NotFound`, telling an operator
the volume is not there when the truth may be a cable. `MountError` names the five, `mount` stays as
the convenience over it so no caller had to change, and StorageService now maps them apart:
`Io`/`NoMemory` are worth retrying and say nothing about the medium, `Unsupported`/`Corrupt` are
permanent, and only `NotFat` really means "nothing here claims to be this".

**An exFAT Allocation Bitmap must have a bit per cluster.** Any `DataLength` was accepted, and the
ownership audit only inspects bits for clusters that ARE claimed - so with every system and live
allocation inside the covered prefix, a short bitmap passed and the mount stayed writable, after
which `free_bytes` and `exfat_alloc` treated the rest of the heap as unavailable. The volume then
reports less free space than its own geometry contains and can answer `NoSpace` over a heap that is
simply unreachable.

BOTH WATCHED TO FAIL. The bitmap test needed `build_exfat` rather than `build_fat`, which was
established by measurement: `build_fat(Kind::ExFat, ..)` does not produce a mountable image for this
shape, with or without the new check.

### Measured while doing the above: an order-sensitive test, not caused by this work

`kernel.services.process_service_lists_every_started_program` failed one full run with `left: 1,
right: 2`, and did not reproduce - the next full run was 263/263 with the same tree. It counts
started programs in a SHARED ProcessService, so it sees whatever its neighbours left registered.

NOT CAUSED BY THIS ROUND, established by measurement: running it beside its two

### Resolution of FAT-001, FAT-002 and FAT-003 (2026-08-16)

**The ownership audit descends into classic subdirectories.** It pushed `rec_len: Some(entry.size)`
for every subdirectory regardless of family, and a classic directory entry records a size of ZERO
for a directory - so `read_chain(.., 0)` returned an empty vector without touching a cluster and the
walk claimed the subdirectory's own chain and then descended into nothing. Every file and every
nested directory below the root went unclaimed, so the audit's premise - a cluster belongs to at most
one chain - held for the ROOT alone. `resolve_dir` sets `rec_len` only for exFAT, which is why
ordinary traversal never had this and only the audit did.

DESCENDING EXPOSED A SECOND THING IMMEDIATELY: `.` and `..` are not ownership. They name this
directory's own chain and its parent's, both already claimed by whoever descended here, so claiming
them again reads as two chains sharing clusters - the very condition the audit is for. They were
unreachable while the walk never descended at all.

WATCHED TO FAIL: two files in a SUBDIRECTORY sharing a chain, which is invisible from the root, so
the volume mounted writable over it.

**A chain must end at an end-of-chain marker.** `claim_chain` walks while the value is at least 2,
so a FAT entry of 0 (free) or 1 (reserved) after the last live cluster exits the loop - and the
final check was `cluster >= 2 && !is_end(cluster)`, which skipped both. The comment above it already
stated the rule it failed to enforce. A file whose chain runs into a FREE cluster is a file whose
next allocation hands that cluster to somebody else while this file still points at it.

**The Up-case Table is claimed.** `scan_exfat_root` validates its chain, contents and checksum and
then discarded the allocation, returning only the bitmap - so nothing stopped a file being allocated
over the one structure every name on the volume is compared through.

TWO COVERAGE GAPS ARE RECORDED IN THE TEST FILE RATHER THAN PAPERED OVER. A test for the 0/1
terminator passed either way, because patching an end marker in a raw image degrades the mount
through a different path - the walk sees a cluster outside the pool - so it could not tell the
corrected condition from the old one. A test for the Up-case Table could not locate the root
directory: a byte scan for the `0x82` and `0xC0` record markers finds them inside the boot region and
the FAT first, and `build_exfat` exposes no way to place a deliberately cross-linked entry. Neither
was kept as a test that proves nothing.

Measured: fat 122/122, x86_64 263/263.

### Resolution of FAT-005 (2026-08-16), with its coverage limit stated

`try_zeroed` is the one fallible path every medium-sized buffer now goes through: the chain readers'
per-cluster buffers and their growth, the ranged-read scratch cluster, the fixed root region and the
sector windows. exFAT permits a 32 MB cluster and a 256 MB directory, so each of those was an
infallible allocation whose size the DISC chooses - and an infallible allocation that fails aborts
the process, which for this crate is StorageService and every volume it serves.

WHAT IS NOT CONVERTED, and why it is left: the small per-entry `String` and `Raw` allocations inside
the directory parsers. Each is bounded by one 255-byte record; what the audit notes is that a large
directory can induce MILLIONS of them, which is a different problem - it is bounded by the directory
ceiling rather than by any single number, and converting it means changing the parsers' signatures
rather than their allocation calls.

THE TEST IS A SMALLER CLAIM THAN A WHOLE-FILESYSTEM ONE, DELIBERATELY. This crate has no budget
allocator, and installing a global one to reach the converted paths through a read is what
destabilised another crate's suite when it was tried there - so what is established is that the
helper every converted site goes through refuses rather than aborts. A whole-filesystem
memory-pressure test needs a harness this crate does not have.

Measured: fat 123/123.

### Resolution of FAT-006 and FAT-007 (2026-08-16), and FAT-015 answered

**Both quadratic paths are sorted membership tests now.** The mount audit walked `seen_dirs` with
`contains` for every directory it discovered, so distinct directories cost O(d^2) - and exFAT permits
over eight million entries in one 256 MB directory, with FAT32 bounded by the same read ceiling, so
a valid image can hold enough one-cluster directories to make MOUNT monopolise the storage service.
`gen_short` had the same shape one level down: every one of up to a million `BASIS~N` candidates
scanned the whole collected 8.3 set linearly. Sorted vectors rather than sets, because this crate is
`no_std` with `alloc` and has no hasher, and the insertion point falls out of the lookup that already
happened.

THE TEST PINS BEHAVIOUR AND NOT COMPLEXITY, AND SAYS SO. At four hundred colliding entries the linear
and sorted versions are both under a second, so no assertion can tell them apart; the scale where
they diverge is one this suite cannot afford to build. What it guards is that creates still succeed
in a directory full of colliding aliases - the thing the sort must not change.

**FAT-015 is answered as a stated limit rather than implemented.** Classic FAT has no durable
clean-shutdown marker, and this milestone is not going to invent one: the format has no field for
it, and writing a marker outside the format is exactly the "one implementation's convention" a
foreign reader cannot honour. exFAT has `VolumeDirty` and this driver uses it. What follows from
that absence is already recorded above under FAT-009 - after a reboot a classic volume left with a
duplicate name mounts writable again, because nothing on the medium says the last writer did not
finish - and the mitigation is there too: the ambiguity is refused at the point of mutation rather
than assumed away.
