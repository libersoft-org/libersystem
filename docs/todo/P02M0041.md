# P02M0041 - Streaming replies (retire the 4096 B wire ceiling)

Status: COMPLETE.

Every typed reply had to fit one 4096-byte message. An earlier milestone made overflow a visible
error; this made it impossible.

*Condensed 2026-08-08.*

**The pattern is chosen per operation, not applied uniformly**: `stream<T>` sub-channels for
unbounded lists (the permission audit trail, a big directory listing), explicit offset-and-limit
paging where the client wants random access.

A detail worth keeping: `stream_list` replies with the correlation id and **no consumer handle** for
a bad path, so **an error stays distinguishable from an empty directory** - the shell's `cd`
validates paths through exactly that difference.

Consumers migrated on a shared drain helper or a hand loop, depending on whether they render as
frames arrive: an unsorted `ls` prints each row as its frame lands, so a huge listing starts printing
immediately, while sorted output collects first because column alignment needs the whole set.

**Sockets lost their chunk constants.** A recv-stream chunk is now as large as the connection's own
64 kB ring held - a runtime fact rather than a wire constant.

**`volume.write` grew a streaming form**, so a file's size is bounded by the filesystem rather than by
any single transfer.

**And the last wire constant went with `SYS_CHANNEL_PEEK`**: the kernel reports a pending message's
actual length without dequeuing it, so a transport sizes its buffer exactly instead of guessing a
ceiling.
