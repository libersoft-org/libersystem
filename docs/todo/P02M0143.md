# P02M0143 - Five holes an outside audit found that are worth closing, and the ones that are not

Status: OPEN. HARDENING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Close the findings of an external architecture audit that have a bounded fix, and record why the
rest are refused.

The audit's facts hold up - every claim below was checked against the tree - but its remedies are
sized for a system with users, hardware and a second protocol version, and this one has none of
those. Its largest proposals would cost more than the whole of phase 2 and are refused by name in
"What this milestone refuses" below. What remains has a fix measured in days, and that is this
milestone.

The audit's boot-tail finding is already P02M0142 and is not repeated here.

NO SCORE IS QUOTED, deliberately. An earlier draft opened with the audit's grade and got it wrong -
the number it cited is the weight of one category, not the whole - and a milestone that hangs on
somebody's mark is arguing about the mark instead of the code. What matters is which findings are
true, and each one below says which line of the tree makes it true.

## What is there now

Measured on 2026-08-22 by reading the tree.

- `CMD_BUS_MASTER` is set in `arch/common/pci/mod.rs` at BAR assignment - `assign_bars_ecam`, which
  runs during enumeration, before any driver exists - and by two runtime helpers, `msix_enable` and
  `enable_mem_and_master`. It is cleared NOWHERE. A device whose driver has died keeps the ability
  to write to memory for the life of the boot.
- `sys_dma_buffer_create` accepts a device handle of ZERO, which produces a buffer bound to no
  device. `sys_dma_buffer_phys` then hands back a physical address for it under `Rights::READ`,
  as a plain integer that outlives the buffer and the process.
- `ResourceAccount` charges memory, DMA, queued IPC bytes, handles, wait-set registrations, threads
  and stack. Page tables are not among them: `arch/*/paging.rs` calls `frame::allocate()` directly,
  so a process that maps pages makes the kernel allocate frames nobody charges it for.
- The loader verifies nothing about the kernel it jumps to. `check-staged-image.sh` computes
  digests, but for LIBRARIES AND DYNAMIC VOLUME PROGRAMS - not for the kernel or the boot payload.
  The digests this needs do not exist yet.
- `@rights(...)` in LSIDL already generates a check: `handle_carries` runs between a decoded request
  and the service seeing it, and refuses a handle that does not carry what the schema declares. It
  is used in the entire IDL exactly ONCE, on `display.bind`.

WHAT IS ALREADY BETTER THAN THE AUDIT ASSUMED, so nothing here is fixed twice:

- The capability check the audit wants built for LSIDL is half built. `handle_carries` already takes
  a required object type as well as required rights; the generator passes `NO_REQUIRED_TYPE`. What
  is missing is a schema that says which type, and use.
- The in-kernel ELF parser is covered by two gates, `malformed-dynamic` and
  `malformed-symbol-relocation`, which inject fixed malformations and require the loader to refuse
  them. NEGATIVE TESTS, NOT FUZZING - an earlier draft called them fuzzing and that overstated them,
  though they do address the risk that moving the parser to userspace was proposed to solve.
- The ordered bootstrap the audit wants replaced by a `BootstrapBundle` is already typed and
  fail-closed through `receive_roles`, and P02M0141 has since put twenty-one of twenty-three services
  on the generated plan that feeds it. What remains is the RECEIVING half: four services check what
  they are handed and the rest still read by hand. That is a continuation, not a new design.

AND ONE THING THE AUDIT SAID THAT AN EARLIER DRAFT ANSWERED TOO CONFIDENTLY. Against the audit's
call for selective revocation, that draft claimed PermissionManager already revokes a delegated
grant by closing its connection. It does not: there is no `revoke` in `permission_manager.rs` at
all. The per-grant connection is the SHAPE that would make revocation possible; nothing performs
one today. The refusal below stands on its own grounds, not on a capability the tree does not have.

## Work

- [x] **M1 - Bus mastering follows ownership.**
  - A device may write to memory exactly while a driver owns it. Today it may from enumeration until
    the machine stops.
  - THE THREE PLACES, AND NONE OF THEM IS IN A DRIVER:
    - enumeration does NOT enable it, and clears whatever the firmware left set;
    - `sys_device_acquire` enables it - that call IS a driver taking the device;
    - the disappearance of the last `DeviceMemory` for that device disables it. A handle dies with
      its process, so a driver that crashes disables its own device without knowing the rule exists.
  - NOT IN `SYS_DEVICE_QUIESCED`, AND AN EARLIER DRAFT PUT IT THERE. That syscall is not a shutdown
    notice: `virtio::negotiate_for` calls it during a NEW driver's startup, immediately after
    resetting the device, and it means "the previous driver's frames are safe to recycle now".
    Clearing bus mastering there would disable DMA for the driver that just came up. That is not a
    breakage to be fixed by rewriting drivers - it is the wrong moment, and it would still be the
    wrong moment after any rewrite. `sys_device_quiesced` keeps exactly the meaning it has.
  - THE ONE PIECE OF REAL WORK IS MAKING "NOBODY OWNS IT" DEFINABLE. `sys_device_acquire` mints a
    FRESH `DeviceMemory` per call, so two acquisitions of one device are two independent objects and
    there is no single refcount to reach zero. A per-device-index count, incremented on acquire and
    decremented in `DeviceMemory::Drop`, is enough - and the kernel already keys per-device
    bookkeeping this way, in `dma_buffer::release_for`.
  - THE RULES, SO NOBODY HAS TO INFER THEM:
    - only the transitions 0 -> 1 and 1 -> 0 touch the PCI bit; every acquisition in between changes
      the count and nothing else;
    - the count and the config-space write happen under one lock, so two acquisitions racing cannot
      leave the bit disagreeing with the count;
    - an acquisition that FAILS changes neither;
    - `msix_enable` and `enable_mem_and_master` stop setting the bit on the side. They may keep
      enabling memory space; bus mastering has one owner now and they are not it;
    - the scope is devices the kernel has in `device::DEVICES`, not any PCI function a caller can
      name.
  - NOT A SINGLE-OWNER RULE. The audit's reviewer proposed allowing only one live acquisition per
    device, which would also make the question definable. It is a change to who may own a device,
    not to when a bit is set, and it can meet places where DeviceManager and a driver both hold one.
    The counter answers the same question without deciding that.
  - THIS IS NOT AN IOMMU AND DOES NOT PRETEND TO BE. A device with bus mastering off cannot write
    anywhere; a device with it on can still write wherever it was programmed to. What this closes is
    the window before an owner exists and after one has gone.

- [x] **M2 - A physical address is obtainable only from a device-bound DMA buffer.**
  - `sys_dma_buffer_create` takes a device handle, and zero is accepted: the buffer is then bound to
    nothing. `sys_dma_buffer_phys` does not look, so an address can be had for a buffer no device
    was ever named for.
  - Refuse `phys` for an unbound buffer. That is the whole change.
  - NOT "ONLY WHILE MAPPED", WHICH AN EARLIER DRAFT ASKED FOR AND WHICH WOULD BREAK THE DISPLAY.
    virtio-gpu deliberately does not map its framebuffer backing - ConsoleService renders into it and
    a `DmaBuffer` maps only once - while the GPU still needs the physical addresses. Mapping is not
    what makes an address legitimate; being for a device is.
  - THE TITLE SAYS WHAT IS ACHIEVABLE. An earlier one promised that an address would not outlive
    what it describes, which no change here can deliver: an address is an integer, and without an
    IOMMU nothing takes one back. The threat model gets that sentence, in those words.
  - THE TEST IS BOTH DIRECTIONS. An unbound buffer is refused, AND a device-bound one still answers
    - including one that is not mapped, because virtio-gpu's framebuffer is exactly that and it is
    the case a careless narrowing would break.
  - INDEPENDENT OF M1. Both are the DMA boundary and neither needs the other.

- [x] **M3 - Page tables are charged to the Domain that caused them.**
  - A process that maps pages makes the kernel allocate frames for its own page tables, and nothing
    charges them. A mapping loop is a way to consume kernel memory without meeting a limit.
  - The work, and it stops here: connect a userspace `AddressSpace` to its `Domain`; charge the root
    and intermediate page-table frames against the memory limit that already exists; refuse a
    mapping that would exceed the quota WITHOUT leaving a partial result; give the frames back on
    rollback and when the address space dies; prove it on all three architectures.
  - AND IT STOPS THERE. "Find every allocation behind channels, events, timers and IRQ bindings" is
    an audit with no end, and an earlier draft made it a deliverable. Page tables are the path that
    is known to be unbounded and reachable from an ordinary syscall; anything else gets an account
    when something shows it needs one, not because a sweep was promised.
  - `ALLOC-OK` IS NOT AN ACCOUNTING EXEMPTION and an earlier draft used it as one. It marks a
    justified infallible heap allocation. Who pays for a kernel object is a different question and
    needs its own answer at the site.

- [x] **M4 - The loader verifies what it loads.**
  - THE DIGESTS DO NOT EXIST YET, which an earlier draft got wrong. `check-staged-image.sh` covers
    declared libraries and dynamic volume programs. Nothing computes a digest for the kernel or the
    boot payload - exactly the bytes the loader reads - so this item produces them as well as
    checking them.
  - THE CONTRACT, CHOSEN HERE RATHER THAN LEFT TO THE IMPLEMENTER. An earlier draft listed eight
    decisions and made none of them, which is not a milestone that is ready:
    - one small versioned SHA-256 manifest at `etc/boot.manifest`, beside the `etc/bootstrap.list`
      the loader already reads;
    - EACH SOURCE CARRIES ITS OWN. On the system volume it covers the kernel, `bootstrap.list` and
      every program that list names; on a boot medium it covers the kernel and whatever bootstrap
      files sit there directly;
    - it names the digest of the FINAL bytes the loader reads, after any staging;
    - once the loader has CHOSEN a source, a manifest that is missing, malformed or disagreeing is
      fatal. A source that cannot be opened at all is skipped as it is today - choosing is one thing,
      failing a check is another, and there is no falling through from the second to the first;
    - a direct development `-kernel` boot is outside this check, and says so where it is skipped;
    - four tests: a good boot, an altered kernel, an altered bootstrap file, and a manifest that is
      corrupt or absent.
  - NO SIGNING, NO KEYS, NO A/B SLOTS, NO ANTI-ROLLBACK, NO TPM. Those need a key holder, an update
    channel and a recovery story, and this project has none of the three. This is also not a release
    freeze and closes no version.
  - WHAT IT PROVES, IN THE MILESTONE'S OWN WORDS: the content matches the manifest beside it. That
    catches corruption, a half-written image and artifacts from two different builds mixed together.
    It does NOT catch an old image - an old one carries its own old manifest and agrees with itself -
    and it does not prove the image came from a trusted build, because an attacker who can rewrite
    one can rewrite both. An earlier draft claimed staleness; that was wrong.

- [x] **M5 - Finish the capability check LSIDL already generates.**
  - `@rights(...)` already produces a `handle_carries` guard between a decoded request and the
    service, and `handle_carries` already accepts a required kernel object type - the generator
    passes `NO_REQUIRED_TYPE` today. The annotation appears once in the whole IDL.
  - THE SCOPE, NARROWED TO WHAT IS DECIDABLE NOW:
    - REQUESTS ONLY. Replies are deferred by name, not by silence;
    - each LSIDL `resource` declares the kernel object type it stands for - `task` is a Process,
      `task-group` a ProcessGroup - and the generator knows the built-in `channel` and `buffer`. A
      resource that declares nothing keeps `NO_REQUIRED_TYPE`, so this can be adopted one resource
      at a time rather than in one edit;
    - `@rights` keeps meaning exactly what it means now: the minimum the handle must carry;
    - on refusal, every capability taken from that message is closed and the service is not called;
    - name the requests that get the annotation. "Use it in more than one interface" was an earlier
      wording and it is not a scope, it is a wish.
  - NO CEILING. An earlier draft asked for a maximum beside the minimum, the way `receive_roles` has
    one at bootstrap. Nothing in the IDL has a caller that needs one, and a field with no consumer is
    what M1 of P02M0141 exists to prevent. It can be added when a method wants it.
  - `ROLEKIND` IS THE WRONG VOCABULARY HERE and an earlier draft reached for it. It describes
    bootstrap roles - serve root, factory, payload - not what a method's parameter is.
  - Tests: wrong object type, missing right, and that nothing is left open after a refusal.
  - THE REQUESTS THAT GET IT, named: `display_admin.bind` (which had it), and `permission.run`,
    `permission.run-pipeline` and `permission.run-with-file`, whose `stdout` is a channel the
    launcher WRITES the child's output to - so `@rights(send)` is the authority the method actually
    needs, and a caller handing over a receive-only end is refused instead of producing a child
    whose output goes nowhere. Adding a fifth is a decision about that method's callers, which is
    why the set is named rather than promised.
  - `resource task` declares `@kernel(process)` and `resource task-group` declares
    `@kernel(process-group)`; `channel` and `buffer` are built in, so `handle<channel>` checks the
    Channel type without any package saying so. A resource that declares nothing still emits
    `NO_REQUIRED_TYPE`, which is what lets this be adopted one resource at a time.
  - THE ABI MANIFEST MOVED, deliberately: adding `@rights` to a parameter changes the method's
    recorded signature, so `./gen.sh` refused until it was accepted with `--accept-breaking`. That
    is the pre-release answer and it is the right one here - nothing is versioned before the first
    release, and the alternative is an annotation nobody may ever add.

## Dependency order

```text
M1   M2   M3   M4   M5      independent of one another
```

Nothing here blocks anything else. M1 and M3 are the two with a security argument, M5 is the
cheapest because the mechanism exists, and M4 is the largest because it produces something that does
not exist yet.

A SIXTH ITEM WAS DROPPED: an allocation-free IPC fast path. Its case was that a channel message
costs a `Vec<u8>`, a `Vec<Capability>` and a `VecDeque` slot, which is true. But P00M0011 already
recorded a raw channel round trip at about 0.76 microseconds, nothing since has shown IPC to be a
problem, and the item as written said to measure first and then make the change regardless - which
is not what measuring is for. If IPC ever looks slow, there is a number to compare against.

## Definition of done

- A device has bus mastering enabled exactly while at least one `DeviceMemory` for it exists, and
  the enumeration path leaves it off - including when the firmware left it on.
- `sys_device_quiesced` still means what it meant, and a driver's normal startup is unaffected.
- `sys_dma_buffer_phys` refuses a buffer bound to no device, and the threat model states in one
  sentence that an address already read cannot be taken back.
- Page tables - root and intermediate - are charged to the Domain that caused them on all three
  architectures, a quota refusal leaves no partial mapping, and a rollback or a dying address space
  gives the charge back.
- The loader refuses to boot a kernel or bootstrap file whose digest does not match the manifest of
  the source it chose, and refuses a missing or malformed manifest on that source. The milestone says
  plainly that this is integrity, not authenticity, and not freshness.
- A capability arriving in an LSIDL REQUEST is refused when its object type or its rights do not
  match the declaration, generated from that declaration; the refusal closes what it took; and the
  named requests carry the annotation.

## Result, 2026-08-23

All five items are implemented. Three of them turned out to have a hole the item had not
anticipated, and those are what this section is mostly about.

**M1 - THE BIT FOLLOWS OWNERSHIP, AND THE SWEEP IS NOT WHERE THE ITEM PUT IT.** `device::OWNERS` is
one count per device-table index, taken under the same lock as the config-space write;
`sys_device_acquire` raises it and `DeviceMemory::drop` lowers it, and only the 0 -> 1 and 1 -> 0
transitions touch the PCI bit. An acquisition that fails changes neither, and the syscall gives the
count back by hand when the handle table refuses the handle - `Drop` will not run for a capability
the caller never received.

The item said enumeration clears the bit. Enumeration is `assign_bars_ecam`, and X86_64 DOES NOT
CALL IT: the firmware places the BARs there, so the whole function is compiled for the other two
targets only. On the port where the firmware also ENABLES bus mastering - the one port where a device
arrives already able to write to memory - the clearing code never ran. The sweep is now in
`device::init`, over every function the scan found, which is the one place all three ports pass
through. Bridges are left alone (header type 1): their bus-master bit forwards transactions from
everything behind them rather than granting the bridge anything of its own.

Two owners had to be made explicit. The kernel's own aarch64 `virtio_blk` driver - the boot-time
sector-0 probe - is a bus master with no `DeviceMemory` to die with, so it takes the device in
`init` and its `Drop` resets the device and gives it back. And the xHCI test harness, which stands in
for DeviceManager, was minting `DeviceMemory::new(bar_phys, len)` for a bare physical range; it now
mints `for_device(index, ..)` and acquires, as the syscall does. Without that the controller brought
its rings up and waited forever for a completion the bus would not let it write - which is exactly
what this milestone is for, seen from the other side.

**M2** is one branch: `sys_dma_buffer_phys` refuses when `dma.device().is_none()`. Both directions
are tested, including the unmapped-but-device-bound case that virtio-gpu's framebuffer actually is.

**M3** connects a userspace `AddressSpace` to its `Domain` and charges the root and every
intermediate page-table frame to it. `try_map` reserves `MAX_NEW_TABLES` pages up front - 3 on
x86_64, 3 on aarch64, 2 on riscv64, each backend stating its own depth - maps, and refunds what it
did not use, so a quota refusal leaves no partial mapping and a dying address space gives the whole
charge back.

**M4 - THE VERIFIER WAS THE EASY HALF.** `bootproto::boot_manifest` is a version line and
`<sha256>  <path>` rows, with the four host tests the item asked for: a good boot, an altered kernel,
an altered bootstrap file (told apart from an unrecorded one), and a manifest that is corrupt or
absent. `mkpackages` writes one into the volume and into the fallback set.

Both real defects were in the staging and the wiring, where no host test could see them:

- THE x86_64 BOOT MEDIUM CARRIED NO MANIFEST. `qemu-run.sh` stages the ESP for aarch64 and riscv64;
  x86_64's is built by `mkimage.sh`, which copied `etc/bootstrap.list` and `libexec/*` and nothing
  else. Every x86_64 boot died at the loader with "this source has no etc/boot.manifest".
- THE KERNEL FROM A BOOT MEDIUM WAS CHECKED AGAINST NOTHING. Only the system-volume branch verified
  its kernel. The two fallback branches read it and loaded it - and that is the branch every machine
  without a system volume takes, and the branch all three test media take.

A boot medium therefore gets a manifest of its own, written where it is staged, because the kernel
there is the STRIPPED build: a different sequence of bytes from the volume's, so the volume's digest
for it would refuse every boot. `read_boot_file` learned to translate `/` into `\` for the firmware
file protocol on the way - it had taken the caller's string verbatim for both readers, which worked
for exactly as long as every name was a single component and then `etc/boot.manifest` reached the
firmware reader as a name no volume has. Each check that passes now says so in the boot log, because
a silent check cannot be told apart from one that was never wired up.

AND THERE IS A GATE, `boot-manifest`, which is what closes this properly. It asks the loader's own
question of the staging sets and the media on disk - every file the loader would read has a row, and
the row is the digest of the bytes that are there - and it self-tests against a set it builds. Both
defects above would have been caught by it on the day they were written.

**M5** - `@kernel(...)` on an LSIDL `resource` names the kernel object type it stands for; `task` is
a Process and `task-group` a ProcessGroup, `channel` and `buffer` are built in, and a resource that
declares nothing still emits `NO_REQUIRED_TYPE`, so this is adopted one resource at a time. The
guard `@rights` already generated now carries the real type code. `permission.run`,
`run-pipeline` and `run-with-file` declare `@rights(send)` on `stdout`, beside `display_admin.bind`
which had it. A refusal closes every capability the message carried, which is asserted rather than
assumed.

## How this was verified

- x86_64: full suite 313 passed; the real image boots to the shell prompt with the loader reporting
  both checks. The three added tests were watched to fail: breaking `release_bus_master` fails
  `kernel.hardware.a_device_masters_the_bus_only_while_a_driver_holds_it` on the exact assertion,
  and pointing the manifest's kernel row at another file stops the boot at
  "loader: the kernel does not match etc/boot.manifest on the boot medium".
- aarch64: full suite 301 passed, including both bus-mastering tests and the real-device capture the
  same rule made possible.
- riscv64: full suite 301 passed, and the image boots with the loader reporting both checks.
- Every gate green, all twenty-eight of them.

AND THE GATE, `boot-manifest`, which is what closes M4 rather than the tests do. It asks the
loader's own question of the staging sets and the media on disk - every file the loader would read
has a row, and the row is the digest of the bytes that are there - and it self-tests against a set
it builds. Both of M4's real defects were in staging that no host test could see, and this gate
would have caught them on the day they were written.

## What this milestone refuses, and why

Recorded because the audit asked for each, and a later reader should find a decision rather than an
omission.

- **An IOMMU.** Three architectures of device-side page tables, and under emulation it would prove
  almost nothing. M1 and M2 narrow the window it would close; the rest stays in the threat model,
  including that a misprogrammed device with bus mastering on can write into memory that has been
  freed or belongs to somebody else. That is not only a leak, and an earlier draft implied it was.
- **A general pager: `VmObject`, copy-on-write, page cache, swap.** The system has no `fork`, no
  file mapping and an immutable image loaded from a package. A subsystem built for requirements that
  do not exist.
- **A capability derivation tree with selective revocation in the kernel.** It puts an indirection on
  the hottest path in the kernel. The service layer's per-grant connection is the shape that would
  make targeted revocation possible without it - and today nothing revokes anything, which is the
  honest reason this is deferred rather than solved.
- **Priority classes, priority donation, NUMA placement, tickless scheduling, admission control.**
  The scheduler has no priorities, so priority inversion cannot occur. Adding priorities in order to
  need donation invents the disease and the cure together.
- **Moving the ELF loader, the dependency resolver and PCI enumeration into userspace.** It trades
  about a thousand lines of kernel for a wider kernel API - map into a foreign address space, seal an
  image, a load transaction - and the parsing risk is already met by two negative-test gates.
- **LSIDL wire evolution: field IDs, flexible records, protocol negotiation, side-by-side major
  versions.** Nothing in this tree is versioned yet by an explicit project rule. Wire evolution
  before a version two is machinery for a migration nobody has to do.
- **Formal specification of kernel invariants.** Twenty-eight gates, a verification model and
  property tests are proportionate at this stage. A formal model of nine subsystems is a research project that
  would not change a line of the kernel.
