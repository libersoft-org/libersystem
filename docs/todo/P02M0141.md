# P02M0141 - One system model: components, identities, and dependencies

Status: PLANNED. SYSTEM-ARCHITECTURE FOUNDATION. NOT A PRODUCT, RELEASE OR UPDATE GATE.

## Goal

Describe the system that exists today in one logical model instead of maintaining separate partial
lists for artifacts, services, dependencies and runtime identity.

The existing `src/user/services/manifest.toml` remains the source owner. This milestone extends it;
it does not create a second manifest, a new configuration language or a framework for hypothetical
server and desktop products.

## Version ownership rule

`v1` remains open until the project owner explicitly says otherwise. Completing this milestone
means that its current acceptance criteria and standing gates pass. It does not freeze an API, ABI,
schema, file format, machine description, product profile or release line. Breaking `v1` changes
remain allowed when all in-tree producers, consumers, generated files and tests migrate together.
Only the project owner may declare `v1` closed or start a successor version.

## Scope

This milestone owns the common names and relationships needed to describe the current development
system. Existing milestones keep ownership of their implementations:

- P02M0079 owns the manifest, artifact/service rows and current generators;
- P02M0098 owns driver discovery, binding and provider lifecycle;
- LSIDL owns service protocol schemas;
- the kernel owns capability, Domain and process mechanisms; and
- P02M0104/P02M0118 own execution and verification selection.

This track does not add release signing, update/rollback, remote management, multi-tenancy,
alternative providers, rolling compatibility, a package ecosystem, desktop policy or transparent
recovery of every open resource.

## Work

- [ ] **M1.1 - Record the Current Development Contract.**
  - Describe the current reference VMs, boot paths, host/guest boundary and the components that are
    actually part of the development system.
  - Maintain an open `DevelopmentMachineProfile` for the QEMU configurations used on x86_64,
    aarch64 and riscv64. It is reproducible test input, not a frozen support tier.
  - Give each current profile a deterministic ID and digest over its exact QEMU/firmware/device
    inputs so later test evidence can name what it exercised. The profile remains editable in `v1`.
  - State the current application boundary honestly: native Liber ABI, LSIDL and the implemented
    Liber Wasm import world. Do not claim full WASI, POSIX or third-party compatibility prematurely.
  - Keep architectural decisions and their reasons in ADRs that may be superseded during `v1`
    development through an explicit migration; an ADR is not a freeze declaration.

- [ ] **M1.2 - Give artifacts, deployments and live instances unambiguous identities.**
  - Distinguish an artifact, a reusable program/component, a desired service deployment and a live
    process instance.
  - Define stable `ArtifactId`, `ComponentId` and `DeploymentId`/`ServiceId` values for the current
    tree, plus changing `BootId` and `InstanceEpoch` values at runtime.
  - State which identities persist across a process restart and which are created again at boot.
  - Map existing manifest names to these identities without renaming every subsystem merely for
    architectural uniformity.
  - Do not add generic `ResourceId`, tenant, placement or dynamic-provider identities before a real
    current consumer needs them.

- [ ] **M1.3 - Extend the existing manifest into the open `SystemSpec v1` model.**
  - Add only facts used by the current system: artifact/component/deployment identity, exact
    provided and required interfaces, current provider binding, start dependency, bootstrap role
    reference, supervision/Domain parent, restart class, state class, resource-profile reference
    and config-schema reference.
  - Add lean canonical declarations for resource limits already enforced by ResourceManager and for
    ConfigService keys already exposed: owner, type, default, validation and live-or-restart
    behavior. Do not invent unused policy dimensions.
  - Keep the current exact binding between a requirement and its provider. Alternatives, version
    ranges, placement and runtime provider selection are outside this milestone.
  - Represent only fixed volume roles that actually exist in the current composition without
    inventing a separate data volume, general Volume Registry or global namespace.
  - Give the schema an open version tag, deterministic canonical form and digest for drift detection
    and correlation. The digest is not a release identity or compatibility promise.
  - Reject duplicate identities, missing references, dependency cycles and invalid parents while
    allowing the schema to continue evolving inside `v1`.

- [ ] **M1.4 - Derive the common static composition view from `SystemSpec`.**
  - Preserve the build/staging and service dependency generation that already works.
  - Add a canonical inventory of current components, deployments, exact interface bindings and
    desired System Graph identities.
  - Expose the same identities to the later bootstrap, lifecycle, authority, Domain, resource and
    observability projections without making `SystemSpec` own those mechanisms.
  - Remove a hand-maintained table only after generated-versus-current comparison proves it
    represents the same fact or records a reviewed correction.
  - Never keep both a generated and manually edited source for the same composition fact.

- [ ] **M1.5 - Migrate the current tree and make model drift a standing error.**
  - Give every staged artifact and every long-lived deployment in the current development image one
    canonical declaration and identity.
  - Update documentation so machine and application claims match the current implementation rather
    than future roadmap intentions.
  - Add repository checks for duplicate/missing identities, invalid references, cycles, stale
    generated output and an undeclared staged deployment.
  - Make a schema change select the manifest/generator and architecture-conformance tests through
    the existing verification model.
  - Record migration evidence, but do not label the result frozen, production-ready or released.

## Dependency order

```text
M1.1 --> M1.2 --> M1.3 --> M1.4 --> M1.5
```

Normative design and fixtures may be developed in parallel, but each task closes against the
implemented current model produced by the preceding task.

## Definition of done

- Every current staged artifact and long-lived deployment has one canonical identity and manifest
  declaration.
- Desired deployments, live instances, boot epochs and service epochs are distinct concepts with
  machine-checkable relationships.
- Exact current interface requirements and provider bindings are visible in the model.
- The existing manifest remains the source owner; no parallel `SystemSpec` database or fragment
  framework requires manual synchronization.
- The development machine and application documentation states what exists without turning it into
  a frozen product claim.
- Current development profiles have deterministic identities/digests, while remaining open to
  coordinated change inside `v1`.
- Repository gates reject structural errors and generated drift.
- Completing the milestone leaves `v1` open for continued coordinated change.

The implementation records the exact commands and results used to close each M1.x item in dated
evidence sections here. That evidence proves consistency of the current development tree only; it
does not certify a release or end `v1` development.
