# P02M0141 - Close the architecture of the production reference appliance

Status: PLANNED. SYSTEM-ARCHITECTURE GATE. The reference VM appliance must not be called
production-ready until this milestone is complete. P02M0142 and P02M0143 consume the identities,
contracts and projections frozen here; they do not reopen them by inventing parallel models.

## Goal

Turn the existing collection of capable subsystems into one recoverable, updatable and operable
product architecture.

The kernel object model, capability security, LSIDL protocols, process-isolated services and
per-volume storage workers are foundations to preserve. The missing layer is the system-wide
contract above them: one logical description of what is shipped, how instances are created, where
authority comes from, who owns state and resources, how failure is contained, how a client finds a
replacement, and which exact machine and release are supported.

This milestone combines two inseparable steps. It first freezes the reference architecture in
machine-readable contracts, then migrates the appliance onto those contracts and proves recovery,
update and remote operation end to end. A document-only design is not completion, and a runtime
change without the corresponding generated model is not completion either.

Task prefixes are global within this three-milestone architecture track: `M1.x` is the appliance,
`M2.x` the general/server platform and `M3.x` the desktop/application platform.

## Terms

- **RTO** (`recovery time objective`) is how long recovery may take.
- **RPO** (`recovery point objective`) is how much committed state may be lost.
- **SLO** (`service-level objective`) is a measurable availability or latency target.
- **SBOM** (`software bill of materials`) is the release inventory of shipped software inputs.
- **TCB** (`trusted computing base`) is the transitive set that must behave correctly for one named
  security property; different properties have different TCBs.

## Decisions fixed by this milestone

- The first production product is a precisely versioned QEMU/KVM + UEFI + virtio reference
  appliance. ISA support and development boot paths do not imply support for an arbitrary physical
  machine.
- "One source of truth" means one composed and validated logical `SystemSpec`, assembled from
  owned component fragments, shared profiles and product/machine overlays. It does not mean one
  giant hand-edited file.
- `SystemSpec` describes artifacts, desired deployments, boot grants and the permitted roots and
  rules of later delegation. It does not replace runtime capabilities and is not an ACL containing
  every object that may ever exist.
- A stable component or service identity is distinct from a runtime process instance. Every
  instance and exported long-lived resource carries an epoch.
- For the reference appliance, loss of the control-plane epoch is fail-closed: the complete
  `system@epoch` Domain is destroyed and reconstructed. Workloads are not silently orphaned or
  adopted. A later server profile may preserve them only through an explicit rebind protocol.
- The compatibility unit is the signed whole image unless a boundary is explicitly classified as
  a runtime service, application, package or persistent-state compatibility boundary.
- Kernel handles and Channels remain node-local. Remote administration terminates in a trusted
  userspace gateway which derives a narrow, leased local proxy capability.
- The System Graph is a read-only, freshness-bearing projection. Authority topology is
  capability-scoped and redacted; observing it is itself confidentiality-sensitive authority.
- Trust is assessed per property. Boot integrity, isolation, policy, confidentiality and DMA safety
  have different transitive trusted computing bases; there is no single generated "the TCB" list.

## Relationship to existing milestones

P02M0079, P02M0098, P02M0104, P02M0106, P02M0118 and the existing loader, driver, identity and
verification tracks remain the owners of their subsystem implementations. This milestone owns the
cross-system composition contract and the production-appliance gate. Existing work may satisfy a
slice only when it is projected through the common identities and passes the system-level failure
and release tests below. It is not reopened merely to rename it.

This milestone does not build a distributed orchestrator, a cluster control plane, a desktop, an app
store, a POSIX kernel personality or support for arbitrary hardware.

It also does not absorb local kernel, driver, filesystem, ISO/UDF/FAT, parser or codec defects from
the implementation audit. When an architecture conformance scenario exposes one, record it as a
separate defect owned by the relevant subsystem and keep this milestone's closure criterion at the
system invariant that the scenario exercises.

## Work

### Contract and source of truth

- [ ] **M1.1 - Publish the Current Product Contract and the architectural decision record set.**
  - Freeze a baseline inventory of shipped artifacts, deployments, manual wiring, boot authority,
    Domains, resource policies, state owners and configuration namespaces. Copy each of the 27
    architecture-audit findings into a self-contained closure matrix mapped to one work package or
    to an explicit later-profile deferral with a preserved seam.
  - State exactly what the reference appliance is, what it supports, what is development-only and
    what is outside the product. Keep long-term Vision in a separate document.
  - Publish a product-profile catalog with distinct identifiers and gates for reference VM,
    physical edge, server, desktop and future AI products. Only the reference VM contract is made
    normative here; the other rows name their later owner and must not borrow this profile's claims.
  - Freeze ADRs for the capability/kernel boundary, whole-image compatibility unit, explicit volume
    namespaces, replaceable app-host seam and node-local Channel boundary.
  - Describe the Current App Contract honestly: native Liber ABI, LSIDL service ABI and the current
    Liber core-Wasm import world are present; a full Component Model/WASI Preview 2 environment,
    POSIX compatibility and third-party ecosystem are future adapters.
  - Every ADR names the invariant, alternatives, trade-off, compatibility impact and the evidence
    required before it may be superseded.

- [ ] **M1.2 - Define the composed `SystemSpec v1` schema and canonical identities.**
  - Separate `ArtifactSpec`, `ComponentTypeSpec` and `DeploymentSpec`; do not confuse a reusable
    program type, desired deployment and live instance.
  - Define `ArtifactId`, `ComponentTypeId`, `DeploymentId`/`ServiceId`, `ScopeKey`,
    `ComponentInstanceId`, `ResourceId`, `BootId` and `InstanceEpoch`, including uniqueness and
    persistence rules.
  - Cover static, per-device, per-volume, per-session and on-demand instantiation with an owner,
    trigger, scope key, cardinality, admission rule and placement constraint.
  - Compose locally owned fragments with resource/policy profiles and product/MachineProfile
    overlays into one deterministic canonical representation with a version and digest.
  - Provide schema evolution rules and reject unknown required fields instead of silently applying
    defaults from a different version.

- [ ] **M1.3 - Compile every duplicated system graph from `SystemSpec` and remove split ownership.**
  - Generate artifact build/staging inventory, service start graph, concrete bindings, typed
    bootstrap plan, boot grant and delegation plan, Domain/resource tree, lifecycle table, desired
    System Graph, verification selection and release inventory.
  - Generate authority/trust inventories as inputs to property-specific analysis; never claim the
    inventory alone is a complete TCB proof.
  - Migrate one projection at a time in shadow mode: compare generated and legacy output on the real
    image, switch the consumer only after equality or an explicit reviewed difference, then delete
    the manual table.
  - A repository gate rejects duplicate identity, missing artifact/provider, dependency cycle,
    invalid scope, unknown grant, impossible delegation, invalid Domain parent, incompatible
    interface version and generated drift.
  - Adding an ordinary service after this task requires a fragment and implementation, not a new
    branch in a central Rust bootstrap router.

- [ ] **M1.4 - Replace positional bootstrap conventions with one typed, versioned control contract.**
  - Define `BootstrapEnvelope v1` / `ComponentStart v1` with component and instance identity,
    expected handles by typed role, config version, scope, parent/failure group and protocol version.
  - Generate both sender and receiver bindings. Field order is not semantic; refuse missing or
    duplicate required fields, unknown required fields, wrong typed roles and unexpected
    authority-bearing values deterministically.
  - Put readiness, health, quiesce, stop and disconnect messages in versioned LSIDL or an equally
    explicit generated bootstrap schema; raw numeric tag folklore is not a second control API.
  - Preserve bootstrap minimality: no service receives a resolver, root or manager capability merely
    because it is convenient to pass one universal envelope.

- [ ] **M1.5 - Close the executable-load trust boundary as an explicit architecture.**
  - Choose and record one model: a narrow versioned kernel load contract whose parser and relocation
    semantics are part of the relevant TCB, or a userspace-produced immutable validated load plan
    whose safety-critical spans and rights are rechecked by the kernel.
  - Specify who authenticates the executable bytes, what identity is bound to the loaded image, how
    shared code is accounted and which ABI/relocation changes break compatibility.
  - Implement the chosen boundary and add hostile-plan/image and version-mismatch tests. Do not move
    semantic service types into the kernel to make the boundary look typed.

### Recovery, lifecycle, authority and resources

- [ ] **M1.6 - Make SystemManager a persistent recovery root, including recovery of itself.**
  - Run SystemManager in a small recovery Domain outside the replaceable system epoch. It holds only
    the sealed bootstrap roots and `MANAGE` authority required to create and destroy exactly one
    `system@BootId/Epoch` Domain.
  - SystemManager starts ServiceManager, observes its epoch, commits or rejects boot health, and does
    not absorb per-application policy, per-service wiring or ordinary data-plane work.
  - Add a kernel first-userspace recovery hook or platform watchdog contract which can replace a
    dead SystemManager and gives the replacement enough authority to remove the prior system epoch.
  - If safe reconstruction cannot be proved, the specified result is reboot and optional slot
    rollback, never continued operation with an ownerless userspace tree.

- [ ] **M1.7 - Turn ServiceManager into a desired-state executor and align the Domain tree.**
  - ServiceManager consumes the compiled plan, starts deployments through ProcessService, supplies
    only generated grants, reconciles desired versus observed instances and emits lifecycle events.
  - Build the declared `system@epoch` hierarchy for control plane, core data services, devices and
    workloads. Supervision parent, failure group and resource parent are identical by default; every
    exception is explicit and mechanically checked.
  - On ServiceManager loss, SystemManager destroys the complete epoch before constructing the next
    one. No registry, client, worker or workload from the old appliance epoch remains reachable.
  - Startup ordering is derived from typed start barriers. Runtime failure propagation is governed
    by explicit edge semantics rather than inferred from startup graph centrality.

- [ ] **M1.8 - Add stable service resolution and recovery contracts for exported resources.**
  - Resolve `ServiceId + interface@version + scope` to an authorized provider `InstanceEpoch` and a
    fresh client Channel. A name is a lookup key, never proof of authority.
  - The resolver may return only scopes allowed by the caller's resolver/grant capability and must
    preserve provider provenance from the trusted composition.
  - Define client behavior for provider replacement: fail, re-resolve, retry or continue through a
    persistent coordinator. Defaults must not turn an unknown operation into an unsafe retry.
  - Give file, socket, watch, session and stream objects `ResourceId/Epoch` semantics: reopen token,
    resume cursor, replay/duplicate rule, gap signal and a clear permanently-lost result.
  - Prove that replacing an instance never lets an old endpoint impersonate the new epoch or lets a
    client reuse stale authority silently.

- [ ] **M1.9 - Define one lifecycle and state-ownership model for every long-lived deployment.**
  - Use a closed lifecycle vocabulary including absent, starting, ready, healthy, degraded,
    stopping, failed, backoff and replaced, with desired and observed state kept distinct.
  - Every transition carries stable identity, epoch, reason, health/readiness, parent/failure group,
    timestamp/sequence and recovery or migration outcome.
  - Classify service state as ephemeral, reconstructible, durable, external or session-owned; name
    the owner, persistence location, schema version, migration policy and behavior on epoch change.
  - Replace the current restart label with readiness, health, stop, retry budget/backoff and state
    recovery contracts. "Process started" is not `Ready`, and "Channel answered once" is not
    `Healthy`.

- [ ] **M1.10 - Publish the appliance fault matrix with explicit recovery objectives.**
  - Cover process crash, hung service, ServiceManager/control-plane loss, SystemManager loss, kernel
    failure, device reset/hot-unplug, power loss, corrupted durable state and failed update.
  - For each class name the detector, escalation owner, affected failure Domain, response, preserved
    state, RTO and RPO. State unsupported guarantees explicitly rather than assigning fictional
    zero-loss objectives.
  - Exercise late and concurrent failures, including a fault during cleanup, migration, health
    commit and rollback. Recovery logic must have a bounded retry budget and a terminal safe state.
  - Use the matrix to derive failure-injection verification; a restart-policy string without a
    watched recovery outcome does not close a row.

- [ ] **M1.11 - Make authority derivation, lifetime and power authority explicit.**
  - `boot_grants` name the source grantor, object/interface class, rights, scope and whether further
    delegation is allowed. Dynamic grants are derived from authority the specialized grantor really
    holds, not minted because a manifest row or principal name says so.
  - `delegation_rules` state source capability class, derived class, maximum rights, scope rule,
    attenuation path, lifetime/lease and revocation owner for PermissionManager, DeviceManager,
    SessionService, powerbox and other grantors.
  - Generate an auditable initial authority graph and verify at runtime that actual boot holdings
    are no broader. Dynamic object instances need not be enumerated in advance, but their derivation
    must be attributable to an allowed root and rule.
  - Split `SystemPower` into a narrow capability for reboot/poweroff/update transitions. A client
    that may react to a power button must not receive root-Domain management authority.

- [ ] **M1.12 - Define the complete resource, overload and request-semantics plane.**
  - Resource profiles cover memory, handles, Channels/queued bytes, threads, CPU share/reservation,
    priority, DMA, interrupt/work budget, client admission and a protected recovery reserve.
  - Reserve enough CPU and memory for SystemManager and recovery control plane to make progress
    while data-plane tenants are exhausting their budgets.
  - Specify priority inversion/donation behavior across synchronous IPC and bound work triggered by
    one request or interrupt; memory quotas alone are not temporal isolation.
  - Standardize deadline, cancellation, backpressure, retry and idempotency metadata and errors.
    `0` must not ambiguously mean both "forever" and "use a default".
  - ResourceManager enforces or delegates admission, publishes pressure/denial events and follows a
    declared degraded/refusal policy. Every unbounded inheritance is an explicit reviewed profile,
    not omission.

- [ ] **M1.13 - Give configuration a typed schema and lifecycle contract.**
  - Every key has type, owner, default, validation, secret classification, mutability, persistence
    and compatibility version.
  - State whether a change is live, transactional, deferred to restart or requires a new system
    epoch. Failed validation or persistence never appears as a successful applied configuration.
  - Generate service-facing config bindings and release/state compatibility checks from the schema;
    reject unknown mandatory keys and incompatible downgrade.
  - Define atomic update, audit and rollback behavior for a set of related keys rather than relying
    on per-key best effort.

- [ ] **M1.14 - Define reference-volume identity and lifecycle without inventing a global root.**
  - Define stable `VolumeId` and changing `VolumeInstanceEpoch`, with roles for active/inactive
    system slot, persistent state, recovery and removable/external media. Bind fixed roles to the
    release and MachineProfile instead of discovery order.
  - Give the appliance one bounded Volume Registry/resolver owner and define duplicate UUID,
    hotplug, removal/reinsertion, device reset, stale endpoint and worker-replacement behavior.
  - A friendly label or UUID is a lookup key, not authority. Resolution requires a capability for
    the requested volume role/scope and returns an epoch-bound endpoint to the existing per-volume
    worker.
  - Reconstruct registry live state after a whole-system epoch rebuild without making persistent
    data process-owned. A reinserted or replaced medium cannot alias an earlier instance silently.
  - Per-user namespace composition, powerbox policy and general cross-volume coordination remain in
    P02M0142/P02M0143; this task closes only the volumes required to boot, update and recover the
    reference appliance.

### Product contract, operations and release

- [ ] **M1.15 - Make observability a secured projection of the same lifecycle model.**
  - Desired nodes and static edges come from `SystemSpec`; live identity, epoch and transitions come
    from the lifecycle event plane; counters name their source and freshness.
  - Distinguish unknown, stale, down and degraded. A one-time snapshot is not the complete System
    Graph promised to operators.
  - Provide capability-scoped and redacted views with opaque identifiers for sensitive authority,
    Channel, principal and workload relationships. The observer is included in the confidentiality
    TCB and has no implicit control authority.
  - Produce separate trust inventories for boot/code integrity, process isolation, policy decisions,
    confidentiality and DMA memory safety, including transitive parsers, stores and grantors.

- [ ] **M1.16 - Freeze a versioned Tier-1 `MachineProfile` and support matrix.**
  - Specify firmware/boot method, architecture variants, QEMU/KVM version policy, CPU/SMP topology,
    memory limits, interrupt/timer model, virtio device set and features, DMA/IOMMU assumptions,
    display/console, storage layout and power semantics.
  - Classify each architecture and boot path as Tier 1, development or unsupported and name the
    exact automated qualification for each. "UEFI-capable" or "boots in QEMU" is not a machine
    contract.
  - Bind the profile identity and digest into `SystemSpec`, verification evidence and release
    manifest. A release cannot inherit whichever emulator flags a developer happened to use.
  - Select the appliance credential/trust root: vTPM, authenticated UEFI variable, host-provisioned
    secret or an explicitly weaker threat model. Define the monotonic source used for expiry and
    anti-rollback rather than assuming a trustworthy clock or counter exists.
  - Publish known ceilings and the policy for changing them; a profile change is a reviewed release
    event rather than a silent script default change.

- [ ] **M1.17 - Build the signed release, A/B update, recovery and state-migration architecture.**
  - Define a signed `ReleaseManifest` binding loader, kernel, init package, system volume,
    `SystemSpec`, policy, `MachineProfile`, state-compatibility range, provenance and SBOM.
  - Define the trust chain and keep three roles distinct: offline release-signing private keys,
    appliance verification trust anchors and device/operator credentials. Specify storage,
    rotation, revocation and anti-rollback policy and whether UEFI Secure Boot is inside Tier 1.
  - Use two immutable system slots, atomic boot selection, a bounded health-commit window, automatic
    rollback and an independently bootable recovery path. Persistent state lives outside the slots.
  - Each durable owner supplies schema compatibility and a transactional migration/rollback plan.
    A rollback is refused or repaired when the old release cannot safely read state changed by the
    candidate.
  - Prove reproducible artifact identity and bind verification evidence to the exact release bytes,
    toolchain/profile and signing identity rather than only to source digests.

- [ ] **M1.18 - Add the minimal device and operator identity required by an unattended appliance.**
  - Define device identity, appliance operator identity and their distinction from the full
    multi-user principal model deferred to P02M0142/P02M0106.
  - Provide first-boot provisioning, authenticated ownership claim, secure credential/secret
    storage using M1.16's selected platform root, rotation, revocation, expiry and recovery without
    a universal factory password.
  - Bind identity and audit events to the release and boot epoch while preserving a stable device
    identity across ordinary updates.
  - Threat-model lost credentials, cloned images, reset/reprovision, clock uncertainty and recovery
    media before enabling remote administration.

- [ ] **M1.19 - Add a narrow authenticated `RemoteGateway` without exporting capabilities.**
  - Terminate an encrypted authenticated session in userspace, map the remote principal through
    policy and derive a scoped, leased, revocable and audited local proxy capability.
  - Initial remote operations are limited to health, logs, update and recovery. Shell, arbitrary
    service resolution and raw kernel/object access are not implied.
  - Never serialize a kernel handle or Channel. Define request identity, replay protection,
    cancellation, rate/admission limits, disconnect cleanup and audit correlation.
  - The normal gateway lives inside `system@epoch` and is intentionally unavailable while that
    epoch is being destroyed. It must return within the declared recovery RTO after reconstruction.
    A recovery image may expose a separate minimal gateway only when its network, credential root,
    authority and resource reserve are explicitly part of the recovery profile and its TCB; no live
    endpoint or session crosses between those epochs.

### Integration and production gate

- [ ] **M1.20 - Migrate the shipped appliance and close the production gate with system scenarios.**
  - Every shipped artifact, deployment, authority root, Domain, resource profile, config schema and
    durable state owner is represented in the canonical model; temporary compatibility bridges are
    enumerated and removed before closure.
  - Run a watched scenario for every row in M1.10's fault matrix, including hung
    ServiceManager/SystemManager, kernel failure, corrupted durable state and a fault during cleanup.
    Also cover clean boot, service replacement, overload, device loss, power interruption, candidate
    update, migration failure, failed health commit, every permitted rollback/forward-repair path,
    recovery boot and remote credential revocation.
  - For every scenario capture stable IDs/epochs, lifecycle events, affected Domains, authority
    derivation, resource accounting, RTO/RPO result and exact release identity.
  - Audit generated versus observed startup authority and fail the gate on an unexplained broader
    capability, orphaned old-epoch object, unclassified state owner or stale observability result.
  - Publish the final support matrix, operator recovery procedure and known limitations. Marketing
    and roadmap text may use "production reference appliance" only after this record is complete.

## Definition of done

- One composed, versioned `SystemSpec` accounts for every shipped artifact and live deployment and
  generates the build, boot, authority, Domain/resource, lifecycle, observability, verification and
  release projections without parallel hand-maintained tables.
- SystemManager and its lower recovery owner can replace a complete system epoch without leaving an
  orphaned process, endpoint, resource account or authority root.
- Every long-lived service and resource has stable identity, epoch, state owner, lifecycle,
  timeout/cancellation behavior and a defined recovery outcome.
- System, persistent, recovery and removable volumes have stable identities and changing instance
  epochs; duplicate/reinsert/stale-endpoint scenarios cannot alias authority across media instances.
- Initial and dynamically derived authority is attributable to a real grantor capability and an
  allowed attenuation rule; `SystemPower` is independent of root-Domain management.
- Recovery control plane remains schedulable under declared overload and all fault-matrix rows meet
  their recorded RTO/RPO or explicitly documented refusal behavior.
- A signed candidate release can be installed into the inactive slot and health-committed. Every
  injected update/migration failure reaches its declared consistent terminal state: safe rollback
  where state compatibility permits it, otherwise forward repair or the recovery image. No result
  assumes unproven backward compatibility of persistent state.
- The exact Tier-1 MachineProfile, device/operator provisioning and narrow RemoteGateway are tested
  as part of the same release identity.
- At minimum, the milestone adds and passes repository gates equivalent to:

```sh
./check.sh --gate system-spec
./check.sh --gate authority-plan
./check.sh --gate machine-profile
./check.sh --gate release-identity
./verify.sh --release
git diff --check
```

The concrete gate names may be settled while implementing M1.3, but their coverage and the exact
commands/results used to close every M1.x item must be recorded in dated evidence sections in this
file. A green unit-test collection without the watched recovery/update scenarios above is not the
completion evidence.

- P02M0079: the current data-driven service/artifact manifest and lifecycle seed.
- P02M0098: the normative device pilot for declarative binding, generation fencing, hotplug and
  provider lifecycle; M1.3 adapts/projects it into the common model rather than creating a second
  driver registry.

  operator identity.
- Existing loader, ABI, filesystem, security and hardening milestones remain implementation gates

milestone consumes their proven contracts.
