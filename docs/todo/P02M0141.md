# P02M0141 - Wiring the system can re-run, and authority it can prove

Status: PLANNED. SYSTEM-ARCHITECTURE FOUNDATION. NOT A PRODUCT, RELEASE OR UPDATE GATE. Nothing
here freezes a schema, an ABI or a version; the project's standing rule that nothing is versioned
before the first release applies to this milestone like every other.

## The two measurements this milestone exists for

Everything below is justified by two facts about the tree as it stands, both read out of the code
rather than assumed. Both were re-measured on 2026-08-22 after a review found the first draft of
this section overstated one of them; the numbers here are the ones the code gives.

**TWENTY OF TWENTY-THREE SERVICES CANNOT BE RESTARTED.** `service_manager.rs` has a function called
`restartable()` and it returns true for three names - `config_service`, `device_service` and
`system_graph_service`. `relaunch_service` says why in its own words: `_ => return false, // A
service whose bootstrap this ladder cannot re-run.` The bootstrap is a hand-written ladder of
twenty-three `if name == b"..."` branches inside the parent, each calling a bespoke function with
the capabilities that service happens to need - `bootstrap_permission_manager` takes twenty-six
parameters. A ladder is not a plan, and a plan is the thing you can run a second time. So twenty
services are marked `escalate` in the manifest, which means a crash leaves them Failed until the
guest reboots. The restart machinery from P02M0011 is present and correct and has almost nothing it
is allowed to act on.

**A CAPABILITY THAT CAN KILL THE WHOLE SYSTEM IS HELD BY THE SERVICE SUPERVISOR, THE DEVICE MANAGER
AND TWO KEYBOARD DRIVERS.** `send_power` duplicates the root-Domain handle with `MANAGE | TRANSFER |
DUPLICATE`. SystemManager receives it from the kernel and PASSES IT ON rather than keeping it, so
after boot the holders are ServiceManager, DeviceManager and one instance each of `virtio_input` and
`xhci` - the two guarded by `if driver_name == b"virtio_input" || driver_name == b"xhci"`, because
those two own the Power key. Block, network, GPU, sound and USB storage do NOT receive it.

What the handle is for is Ctrl+Alt+Del. What it also is, in the kernel's own comment beside
`sys_system_power`, is this: *"whoever holds MANAGE on it can already `sys_domain_kill` the whole
system"*. It also sets the root Domain's resource limits. So a keyboard driver can kill the machine,
and so can the service supervisor, in a system whose thesis is least authority - because there is
nobody resident to hold the broad handle and lend a narrow answer.

Neither of these is an aesthetic complaint about layering. One is the reason the system has no
recovery; the other is the reason its authority story is not true. The work below is scoped to those
two, plus the machinery needed to keep them from coming back.

## What this replaces

This milestone is the surviving half of four planned ones - P02M0141 through P02M0144 - reviewed and
merged on 2026-08-21, then corrected on 2026-08-22 after a second review checked its factual claims
against the code and found three of them wrong. Both the dropped items and the corrections are
recorded at the end, because a plan that quietly loses items or quietly fixes its own facts teaches
nothing about the judgement that did either.

## Scope

The existing owners keep their subjects. `src/user/services/manifest.toml` remains the one
hand-edited source and `tools/system-manifest` remains its parser, validator and projector.
P02M0011 keeps the watchdog, restart budget, backoff and teardown. P02M0098 keeps driver discovery,
binding and provider lifecycle. LSIDL keeps protocol schemas. The kernel keeps capabilities,
Domains and processes. ResourceManager keeps limits, ConfigService keeps values, PermissionManager
keeps dynamic application grants, SystemGraphService keeps the read-only projection. P02M0104 and
P02M0118 keep scenarios and test selection.

NOT IN SCOPE, and named so nobody adds them by drift: a second manifest or configuration language,
a general service registry, provider selection or version ranges, alternative providers, release
signing, update or rollback, remote management, multi-tenancy, a package ecosystem, workload
adoption across failure, transparent recovery of arbitrary open resources, and a graceful
system-wide shutdown sequence.

## Work

### Part 1 - the model, extended only as far as something consumes it

The manifest already carries artifacts, programs, libraries, sources and services with their
dependencies, and already generates the runtime service table and the staging lists. What it does
not carry is the one thing the bootstrap ladder encodes in code instead, and two runtime identities
that do not exist anywhere in the tree.

- [x] **M1 - Declare each service's capability roles as ONE relation, not three spellings of one.**
  - A service requires an interface, that interface has a provider, and the provider is delivered
    as a named role. Those are not three facts. Record ONE: role name, the LSIDL interface it
    speaks, and the provider that supplies it. Three separate fields is two chances for them to
    disagree, and the disagreement would be silent.
  - THE START DEPENDENCY IS DERIVED FROM THE ROLE WHERE A ROLE EXISTS, AND NOT OTHERWISE. Not every
    dependency carries a capability: `device_manager` declares `dependencies = ["log_service"]` and
    receives no log handle at all - its bootstrap reads `POWER`, `CONSOLE` and `DEVPRIV` and nothing
    else. That is an ordering-only dependency and it is real, so the `dependencies` column keeps the
    entries no role accounts for, and the generator derives the rest. A derivation that assumed
    every dependency has a role would silently drop that edge and reorder the boot.
  - NOT EVERY ROLE IS AN LSIDL SERVICE, so the role says WHAT KIND of thing it is from a short
    closed list of what the bootstrap actually delivers today: a client channel to a service (then
    the interface field applies), a memory object (the init package), a Domain handle, a privilege
    handle (`CONSOLE`, `DEVPRIV`), one end of a channel pair the supervisor made, a handle produced
    by a driver, or a tag that carries no handle. Enumerate the kinds that exist; do not invent a
    delivery framework for kinds that do not.
  - For a client-channel role the interface field REFERENCES an LSIDL package and interface. It does
    not restate anything LSIDL already says, and for the other kinds there is no interface to name.
  - DO NOT ADD A SEPARATE "can this be obtained again at restart" FLAG. A role can be delivered
    again when the EXECUTOR STILL HAS SOMETHING TO DELIVER - it kept a handle it may duplicate, or
    it can mint a fresh one - and that is a property of how the role is delivered, which this record
    already says. `DUPLICATE` on its own proves nothing: a right to copy a handle you no longer hold
    copies nothing.
  - THE TREE ALREADY KNOWS THIS AND SAYS SO. `send_privilege` reads "A duplicate, not the handle
    itself: this supervisor keeps what it was handed so a restarted service can be given one again",
    and `send_power` does the same. Those two comments are the restart contract, written one call
    site at a time; this item's job is to make it a property of the declaration instead.
  - Each role declares its presence class - a required capability, an optional capability, or a
    required TAG that may legitimately arrive carrying a zero handle. The third is not a
    hypothetical: the volume bundle sends bare tags for volumes a boot did not grant, and a receiver
    that treats a present tag with no handle as an error would refuse to start on a smaller boot.
  - Each role declares the kernel object type and the rights it must arrive with, because that is
    what a receiver can actually check (see M4).
  - Record the restart class already in the `restart` column, and the fixed volume roles the
    current composition has, BY DECLARED IDENTITY rather than by discovery order. Volumes routed by
    an incomplete hand-maintained table is not hypothetical: two of the seven were unreachable from
    every program in the tree until 2026-08-21 for exactly that reason.
  - SUPERVISION AND DOMAIN PARENT ARE RECORDED AS EXCEPTIONS, NOT AS COLUMNS. Today ServiceManager
    supervises every managed service and M12 puts them all in one control-plane Domain, so a
    per-service parent field would carry the same value twenty-three times - a field with no
    discriminating power, which is the thing the rule below forbids. State the default in one place
    and give a service a parent field only when it differs.
  - ADD NOTHING ELSE YET. A field with no consumer is a field that will be wrong when the first
    consumer arrives, because nothing was checking it. Every later part of this milestone that needs
    a new fact adds it here at that moment.
  - Reject duplicate names, missing references, dependency cycles and invalid parents.
  - THE TWO MANAGERS ARE NOT `[[services]]` ROWS AND MUST BECOME DECLARED SOMEWHERE. SystemManager
    and ServiceManager are started by the kernel and by each other, so the manifest describes
    neither - and M5 and M12 want to check exactly their authority and their Domain. Give them two
    explicit control-plane entries. They are not ordinary managed services and should not pretend to
    be; two rows in a small separate control-plane section is enough, and a general "everything is a
    deployment" abstraction is not.
  - Physical device selection stays with P02M0098. This declares roles, not hardware.

- [x] **M2 - Add the two runtime identities that do not exist: `BootId` and `InstanceEpoch`.**
  - `InstanceEpoch` appears nowhere in the tree today, which is why a restarted service is
    indistinguishable from the one it replaced to anybody holding an endpoint from before.
  - USE WHAT ALREADY EXISTS RATHER THAN ALLOCATING A NEW NUMBER. A process KOID is already unique
    for the life of the system, so the epoch of an instance can simply BE its KOID. That removes
    the allocator, the persistence question and the wraparound question in one move; introduce a
    separate counter only if something needs an epoch before a process exists.
  - `BootId` belongs to the KERNEL's boot, not to SystemManager. A userspace owner would lose it
    the moment SystemManager is replaced, which is precisely the event the id has to survive.
  - Transition reasons and sequence numbers are lifecycle vocabulary and belong to M8, not here.
    This item adds identity and nothing else.
  - DO NOT introduce `ArtifactId`, `ComponentId`, `DeploymentId` and `ServiceId` as four new
    identity types. The manifest's existing names already separate an artifact from a program from a
    service, and in this system a deployment and a service are the same thing.

### Part 2 - generated wiring, so the bootstrap is a plan and not a ladder

- [x] **M3 - Generate the roles plan on top of the dependency graph that already exists.**
  - Start order is ALREADY manifest-driven and already derived from declared dependencies. Do not
    generate a second ordering or a second plan format beside it. What is missing is the per-service
    role list, so add that to the existing projection.
  - The sender and the receiver read the SAME generated role constants. A hand-written vocabulary on
    one side and a hand-written read on the other is a defect this tree has already paid for: three
    programs read bootstrap tags out of the order the grant loop sent them, which made a blocking
    read consume the message that was actually next and then wait forever for one nobody sends.
    `kill` had been launching into a hang since it was written. It took a bisect over 170 tests to
    find, because the failure surfaced in an unrelated service.
  - Bootstrap cycles that genuinely exist stay visible and mechanically checked, under the component
    that owns them, instead of hiding inside a service-name branch.

- [x] **M4 - Make the managed bootstrap path typed, complete and fail-closed.**
  - Reuse the current launch context, `CapSet`, typed grant sender and Ready/failure report. Do not
    invent a second envelope.
  - Check what a receiver CAN check: that every required role arrived, that no role arrived twice,
    that each handle is the KERNEL OBJECT TYPE and carries the RIGHTS the declaration names, and
    that no unexpected authority-bearing role is present. All of it before Ready, not at first use.
  - WHAT CANNOT BE CHECKED HERE IS THE PROTOCOL. From a Channel handle the kernel can say it is a
    channel and what rights it carries; it cannot say which LSIDL interface answers on the other
    end. A wrong interface declaration surfaces where it always has - at the first call, as a decode
    failure - and the place to catch it early is a contract test between the generated client and
    the generated server. Do not build introspection the kernel does not have, and do not promise
    that some later conformance check will find it, because a composition check cannot see a
    protocol.
  - Close every handle the receiver did not adopt, on the success path and on every refusal path.
  - Driver-specific control messages stay with P02M0098.

- [x] **M5 - Generate the initial authority plan and check the boot against it.**
  - Describe every boot grant by grantor, target, and the SAME TWO PROPERTIES M1 and M4 already
    use - the kernel object type and the rights. Not a third vocabulary: "capability class" and
    "scope" were words the first draft introduced here and defined nowhere, and a check whose fields
    have no agreed meaning is a check nobody can implement twice the same way.
  - Generate the maximum initial holdings expected for each deployment and compare them with what
    was actually delivered during boot.
  - BE HONEST ABOUT WHAT THIS PROVES. It proves the code sent no more than the declaration allows.
    It does NOT prove the declaration is least authority: a manifest that declares a root-Domain
    handle for a keyboard driver would pass. M11 is what narrows the authority; M5 is what stops it
    widening again afterwards. Written the other way round, this item would read as a security proof
    it cannot deliver.
  - THE DRIVER BOUNDARY IS DECIDED HERE, NARROWLY. This milestone enforces exactly one rule about
    drivers: NO DRIVER EVER RECEIVES ROOT-DOMAIN `MANAGE`. That is the leak it exists to close and
    it is checkable from the generated plan. Every other driver grant - which device, which memory
    window, which interrupt - stays with P02M0098 and is not audited here. "Either inside this check
    or explicitly checked by P02M0098" was the earlier wording, and an obligation that names two
    possible owners names none.
  - A service name is a lookup identity only; the capability remains the authority.
  - Dynamic grants stay with PermissionManager. No universal runtime derivation graph, and no live
    global handle graph.

- [x] **M6 - The end state: central bootstrap is a plan executor.**

- [x] **M7 - Migrate projection by projection, comparing the old wiring against the generated one.**
  - THIS IS THE ONLY ITEM THAT DELETES ANYTHING, and it closes last of the wiring items, because its
    projections come from M3 (roles), M5 (grants) and M12 (placement) and it cannot switch a
    consumer over to a projection that does not exist yet.
  - For each projection - roles, grants, placement, and the `dependencies` entries a role now
    accounts for - generate it, compare it against what the ladder does today, and only then switch
    the consumer over.
  - Then DELETE the hand-maintained table or column the accepted projection replaced. This
    comparison is temporary by construction: keeping the old table alive to compare against forever
    would be two editable sources for one fact, which is the thing this milestone exists to remove.
  - The permanent checks are different checks and they stay: the receiver-side checks in M4, and
    M5's comparison of what a deployment was actually handed at boot against what it was allowed.
    What ends here is only the old-versus-generated comparison.

### Part 3 - runtime ownership, so failure has an owner and an outcome

- [x] **M8 - One small lifecycle, with desired state kept apart from observed state.**
  - DESIRED STATE HAS TWO VALUES: `running` and `stopped`. Nothing else, and it is a different field
    from the observed one. Without it a service the operator deliberately stopped is indistinguishable
    from one that is missing, and every check downstream would report the deliberate act as drift.
  - The OBSERVED states are `absent`, `starting`, `ready`, `stopping`, `stopped` and `failed`, and
    nothing else. `degraded` is a HEALTH value, not a lifecycle state - a service can be Ready and
    unhealthy - and `replaced` is a REASON an instance stopped. Folding both into the state enum
    makes a value that answers two questions and can therefore answer neither precisely.
  - Every transition carries the deployment, the `BootId`, the `InstanceEpoch` from M2, a reason and
    a monotonic sequence, so a late event from a dead instance cannot overwrite a newer one.
  - Started is not Ready, and one successful bootstrap reply is not lasting health. For each managed
    service declare the readiness condition and the health detector.
  - RESTART POLICY IS A SMALL SET OF SHARED PROFILES, not six numbers repeated on twenty-three rows.
    Budget, backoff and escalation belong to two or three named profiles a service references; a
    service that needs its own is the exception that justifies writing one out.
  - Reuse the P02M0011 watchdog and restart ladder. Do not add a second supervisor.

- [x] **M9 - Say who owns each service's state, and what a restart loses.**
  - TWO SEPARATE QUESTIONS, TWO SEPARATE ANSWERS. What survives - `ephemeral`, `reconstructible`,
    `durable` - is a recovery class. Who it belongs to - the service, a session, something outside
    the system - is an ownership scope. One enum mixing them cannot describe a service with durable
    files and ephemeral sessions, which is most of the interesting ones.
  - For each, name the owner, the storage where there is any, and the result of both a process
    restart and a whole-guest reboot.
  - DO NOT PROMISE that a replacement process inherits an open file, socket, watch, session or
    stream. The default result is an explicit loss or error, and saying so is the point: a system
    that implies continuity it does not have teaches its clients to omit the handling that would
    have saved them.
  - Per-service reopen or replay behaviour is added only by a service that actually implements it.

- [x] **M10 - Make the outcome of a call across a restart honest.**
  - THE DISTINCTION ALREADY EXISTS ONE LAYER DOWN AND IS THROWN AWAY ONE LAYER UP. `SvcTransport`
    returns `SendRefused` when the request never left, and `PeerClosed` or `TimedOut` when it was
    sent and no reply came - which is exactly "nothing happened" versus "may already have been
    acted on". A receive on a dead channel does not hang either: `rt::recv_blocking` returns
    `Received::Closed`, and the transport reconnects through the broker so the NEXT call reaches the
    replacement. Two earlier drafts of this item proposed building all of that; none of it needs
    building.
  - IT IS NOT THE GENERATOR THAT LOSES IT, IT IS THE WRAPPER. The generated `Client` keeps the
    error - `pub fn last_error(&self) -> Option<TransportError>` is right there - and its methods
    additionally return `None` through `.map_err(...).ok()?`. What throws the error away is the
    hand-written client on top: `VolumeClient::write` reaches the generated code through a provider
    shim that builds a `Client`, calls, and drops it, so `last_error` dies with it and the caller
    sees a bare `None` for a request that was never sent and for one that may have written to the
    medium.
  - So the fix is at that layer and it is small: carry the transport error out to the caller instead
    of discarding it - by holding the `Client` rather than making a throwaway one, or by returning
    the error alongside. Do not change the transport, which is already right, and do not rewrite the
    generator for a fault the wrapper introduced.
  - SCOPE IT TO THE CLIENTS THE FAULT MATRIX ACTUALLY DRIVES - the ones talking to services that get
    restarts switched on. There are a dozen client crates and sweeping all of them is a mechanical
    day's work inside a milestone about restarts, which is how a milestone stops being about
    restarts. The shape is identical everywhere, so the rest follow when something needs them; this
    is a scoping decision, not a claim that some clients deserve worse errors.
  - NEVER AUTO-RETRY A REQUEST THAT WAS ALREADY SENT. Reconnecting for the next call is right;
    replaying the last one is how a transfer happens twice.
  - DO NOT ADD A PER-BINDING RECOVERY STRATEGY TABLE - re-resolve here, explicit loss there, restart
    the dependent somewhere else. Nothing in the tree needs to choose between those yet, and a
    manifest column for a policy with no consumer is the field M1 forbids. A truthful outcome and no
    silent replay is the contract; callers decide, and if a pattern repeats often enough to deserve
    a name, name it then.
  - Reporting the new instance's epoch to the caller is optional and only worth doing if the broker
    actually resolves one. The obligation is a truthful terminal outcome, not a number.
  - Cover it in the fault matrix: a client mid-call when its service is replaced must get an answer,
    and the answer must distinguish the two cases above.

- [x] **M11 - Keep SystemManager resident, give the power path a narrow door, and supervise the
  resident manager.**
  - SystemManager is 153 lines today and exits once ServiceManager reports in, so nobody owns the
    control-plane branch after boot. It stays resident, owns exactly that branch, watches
    ServiceManager's health and owns the escalation decision when the branch fails.
  - Root-Domain `MANAGE` is held by SYSTEMMANAGER ALONE. Not DeviceManager, not the two keyboard
    drivers, and not ServiceManager, which holds it today. What the power path receives instead is a
    narrow local SystemPower request service: reboot and power off, nothing else.
  - THE MILESTONE CREATES A NEW HOLE HERE AND MUST CLOSE IT. The kernel's recovery ladder supervises
    SystemManager only until the system is up - `supervise()` returns true on the first round that
    completes without a fault and stops watching. Once SystemManager is resident, its LATER death is
    unsupervised, and it is the one process whose death leaves the control plane ownerless.
  - THE CRASH CHANNEL ALONE IS NOT ENOUGH, for two reasons. It reports FAULTS, and a SystemManager
    that returns or calls `exit()` cleanly is just as gone. And the pre-online ladder RESTARTS
    SystemManager, which was harmless while it owned nothing - once M12 gives it a control-plane
    Domain, a retry would start a second SystemManager beside an orphaned branch that still contains
    a running ServiceManager.
  - ONE RULE COVERS BOTH: once the control-plane Domain exists, ANY loss of SystemManager - fault or
    clean exit - reboots the guest, and the pre-online retry ladder applies only before that point.
    The kernel watches the process itself, not only the fault channel.
  - NAME THE DELIVERY PATH, because it crosses a fence this milestone otherwise respects. The two
    drivers that own the Power key are launched by DeviceManager, so what has to reach them is a
    CLIENT CHANNEL to SystemPower, travelling SystemManager to ServiceManager to DeviceManager to
    the driver - the same route the root-Domain handle takes today, carrying something harmless
    instead. DeviceManager forwarding a narrow client endpoint is not driver policy and does not
    become P02M0098's problem; what stays P02M0098's is when and to which driver it is delivered.
    Left unnamed, this is the seam where the narrowing stalls on "not my area".
  - A bounded graceful shutdown before the power syscall is NOT part of this. It is a feature, this
    item is an authority narrowing, and mixing them is how the narrowing gets delayed behind the
    feature.
  - SystemManager does not absorb per-service wiring, application policy, driver policy or
    data-plane work. ServiceManager stays the one service supervisor.

- [x] **M12 - One real control-plane Domain, owned by SystemManager.**
  - Create ONE child Domain for ServiceManager and the whole control-plane branch beneath it, owned
    by SystemManager.
  - SERVICEMANAGER HOLDS NO DOMAIN HANDLE AT ALL - not the root's, and not its own branch's.
    `sys_process_create` puts a new process in the CALLER'S OWN Domain when it is given handle 0, so
    a ServiceManager that lives inside the control-plane Domain spawns every service into that same
    Domain without holding a Domain capability. It therefore cannot `sys_domain_kill` its own
    branch, and tearing the branch down stays with SystemManager, which is the only holder. Giving
    ServiceManager `MANAGE` on its own subtree would have been the obvious design and it is strictly
    weaker for no gain.
  - DO NOT CREATE A DOMAIN PER SERVICE. A Domain earns its existence by being a real teardown unit
    or a real accounting unit; twenty-three of them, created because the diagram is symmetrical, is
    twenty-three kernel objects and one more thing to keep consistent. Add a further sub-Domain only
    where something actually tears down or accounts separately.
  - The Domain is the accounting parent as well as the failure parent. Do not invent three parallel
    parent graphs that have to be kept in agreement.
  - Bulk termination removes the owned branch through the Domain, which is what Domains are for,
    rather than through hand-written per-process cleanup.
  - On unrecoverable control-plane loss, stop advertising the branch as healthy and reach a declared
    reboot or terminal failure. Do not adopt workloads across it.

- [x] **M13 - Exercise a finite fault matrix, reusing the scenarios that exist.**
  - The rows this milestone owns, because nothing else does: SystemManager lost after boot,
    ServiceManager lost, a non-restartable service failing, a client mid-call across a restart, and
    an ownerless branch still reported healthy.
  - Device or provider loss and resource denial belong to P02M0098 and P02M0010. P02M0098 IS STILL
    OPEN, so those rows are not this milestone's to write and not its to wait for: when those
    scenarios exist, their owners add the system-level assertion to them. Do not write second copies
    here, and do not block on work that has not happened.
  - No invalid-configuration row: config schema declarations were deliberately left out of this
    milestone, so there is nothing here to declare invalid.
  - Each row names its detector, its owner and its bounded outcome: restart with a new epoch,
    explicit failure, branch teardown or guest reboot.
  - DO NOT BUILD A FAULT-INJECTION FRAMEWORK, and do not add ten separate cold boots. Kill a process
    and observe; that is what the existing harness already does.
  - Run through P02M0104 and register selection through P02M0118.
  - THIS IS NOT OPTIONAL POLISH. The evidence is this project's own record: the transactional writer
    was broken for every program in the system from the day it was written, through an
    argument-register mismatch that compiled without a warning, and it survived because no test had
    ever run the path. An untested recovery path is a broken recovery path.

## The fault matrix, as it stands

Each row names its detector, its owner, its bounded outcome, and the test that measures it. Rows
belonging to other milestones are listed so the gaps are visible rather than absent.

| what fails | detector | owner | outcome | measured by |
| --- | --- | --- | --- | --- |
| SystemManager ends after boot | kernel, from the idle hook, on the process | kernel | reboot - no replacement beside an orphaned branch | `kernel.boot.a_control_plane_that_lost_its_owner_is_not_reported_healthy` |
| ServiceManager ends | SystemManager, its branch channel closes | SystemManager | it kills the branch Domain it owns and exits, and the row above then applies | NOT MEASURED - see the gap below |
| a service that cannot be restarted fails | supervisor, its channel closes | ServiceManager | recorded failed, dropped from the wait set, not reported up | `kernel.services.a_service_that_cannot_be_restarted_is_left_failed_rather_than_reported_up`, which measures the DETECTOR (an ended service is observable as ended) on a harness instance and not the supervisor's own recording |
| a client is mid-call when a service ends | the transport | the caller | `again` if the request never left, `commit-uncertain` if it may have been acted on; never a silent retry | `kernel.services.a_call_that_never_left_is_told_apart_from_one_that_may_have_landed` and `kernel.services.a_call_that_may_have_landed_is_answered_commit_uncertain` |
| a service is handed a role it cannot use | the receiver, before it reports ready | the service | refused by name, every handle taken so far closed | `kernel.services.a_bootstrap_role_is_refused_by_name_and_leaves_nothing_behind` |
| a restarted service is confused with the one it replaced | the supervisor, by epoch | ServiceManager | the epoch differs, and the boot chain says so only when it does | `kernel.boot.init_package_starts_system_manager` |
| a device or provider is lost | P02M0098 | P02M0098 | not this milestone's row, and not waited on | P02M0098, still open |
| a resource is denied | P02M0010 | ResourceManager | not this milestone's row | P02M0010 |

NO FAULT-INJECTION FRAMEWORK WAS BUILT, and none is wanted. Every row above is reached by ending a
process and looking, which is what the existing harness already does. A row that needed machinery to
provoke would be a row about the machinery.

THE REBOOT IS NOT EXECUTED IN A TEST. The decision is: `control_plane_lost` takes the two facts it
depends on as arguments so a test can hand it a process that has really ended, and the three cases -
alive, ended before the system is up, ended after - are asserted on the same process. That pairing
is deliberate. An earlier version asserted the pre-online case while the process was still alive,
and a rule that ignored the flag entirely passed it.

## Dependency order

```text
M1 --> M2 --> M3 --> M4 --> M5
                      |
                      +--> M8 --> M9 --> M10        lifecycle, state, clients
                             |
                             +--> M11 --> M12       ownership and authority

M3 + M5 + M12 --> M7 --> M6                         migrate each projection, then the router is gone

M6 + M10 + M12 --> restarts may be enabled --> M13  fault matrix
```

The arrows are closure dependencies, not work order. Generators, negative tests and fixtures may be
written in parallel; each item closes against the implementation the one before it produced.

FOUR EDGES MATTER MORE THAN THE REST. M7 closes AFTER M12, not before: it migrates the placement
projection and cannot switch a consumer to one that does not exist. M6 is not a task that runs, it
is the state M7 leaves behind. M11 needs M8, because "watches ServiceManager's health" is meaningless
until health is defined. And M13 comes after restarts are switched on, because two of its rows - a
client mid-call across a restart, and a service that could not be restarted before - do not exist as
situations until then.

M1 IS DELIBERATELY LAZY. Do not finish the model and then look for consumers - add each fact when
the projection that needs it is being written. A model completed ahead of its consumers is a model
whose fields nothing has ever checked, and that is the way this kind of work usually dies.

## Definition of done

- PARTLY. `restartable()` is no longer a hand-written list of three names: whether a service can be
  restarted follows from its declaration, AND from a state class that tolerates a restart and a
  client contract that survives one. The fault matrix demonstrates it on a service that could not be
  restarted before. -- The list is gone and the policy reads the manifest, with a gate comparing it
  against the mechanism. The state class is not consulted, and no service that could not be restarted
  before can be restarted now. THE MIGRATION IS NO LONGER WHAT BLOCKS IT: `relaunch_service` could
  re-run the plan for any of the twenty-one now that the plan is the default. What still blocks it is
  M6's own warning - turning it on would convert services that stay visibly dead into services that
  come back and break their clients in a new way, and the client contract that would survive one is
  M9's and M10's, not this item's.
- MET, with one half of the comparison narrower than it sounds. ROOT-DOMAIN `MANAGE` IS HELD BY
  SYSTEMMANAGER AND NOTHING ELSE - not ServiceManager, not DeviceManager, not the two keyboard
  drivers. The power path goes through the narrow SystemPower service, and the boot-authority
  comparison shows no deployment received more than it declared. -- The grant is now `MANAGE` alone.
  The comparison runs where a receiver can make it: `receive_roles` checks type and rights against
  the generated plan, and it runs for the four migrated services that read positionally, not for the
  eighteen that still read by hand.
- MET. SystemManager stays resident and owns a real control-plane Domain. ServiceManager holds NO
  Domain handle - it lives inside that Domain and spawns into it - so it cannot tear down its own
  branch; it remains the one service supervisor and executes a generated plan. -- Twenty-one
  services of twenty-three, and the two exceptions carry policy the plan does not model.
- MET. A post-online SystemManager death is detected by the kernel and reaches a declared reboot,
  rather than leaving an ownerless control plane reported as healthy. -- And a PRE-online one no
  longer slips through either: an ended manager is a failed attempt, and the ladder stops rather
  than starting a second manager beside a branch the last attempt built.
- MET. Adding an ordinary service needs a manifest row and an implementation, and no central branch.
  -- The plan is the default: a name absent from the two-service exception list is executed from it.
- Every manifest-managed service, plus SystemManager and ServiceManager, has a recovery class, an
  ownership scope, a readiness rule and a restart or escalation outcome, with a stated result for
  process restart and guest reboot. DRIVERS ARE NOT IN THIS SET - they are long-lived too, and their
  lifecycle is P02M0098's; "every long-lived deployment" was the earlier wording and it quietly
  annexed them.
- MET, and measured on both sides. A client whose call was interrupted by a restart can tell "the
  request was never sent" from "the request may have been acted on", and no already-sent request is
  retried automatically.
- MET FOR TWENTY-ONE OF TWENTY-THREE. No fact has both a generated and a hand-edited source. The
  old-versus-generated comparison ends with the migration that used it; M4's receiver checks and
  M5's boot-authority comparison stay. -- Two services are still described twice and compared on
  every check run, and both keep their branch for a reason written beside it rather than because the
  migration ran out. The pair that was NOT temporary - `restartable()` beside the manifest's
  `restart` column - is gone.

Evidence sections below record the exact commands and results for each item as it closes. They
describe the current development tree. They are not a release, and they do not freeze anything.

## Result, 2026-08-22

All thirteen items are implemented. TWENTY-ONE SERVICES OF TWENTY-THREE are wired entirely from the
plan, and the two that are not are named in the supervisor's own source with the reason. A second
pass over the finished work - this milestone's own code, read the way an outside reviewer would -
found nine defects, two of them regressions the migration itself introduced. They are recorded below
with the rest, along with what finishing the migration turned up.

What follows is what the work found, because the findings are worth more than the list.

**THE TWO MEASUREMENTS THIS MILESTONE OPENED WITH ARE BOTH ANSWERED.**

Root-Domain `MANAGE` is held by SystemManager alone. It used to reach ServiceManager, DeviceManager
and one instance each of `virtio_input` and `xhci` - four holders, two of them keyboard drivers, of
a capability the kernel's own comment describes as able to `sys_domain_kill` the whole system. What
travels down the chain now is a `system-power` connection with two ops and no arguments. The
manifest's list of who may hold the root Domain is empty, and the gate refuses a service that
declares one.

The bootstrap is a plan, and the plan is now the DEFAULT. `start_service` executes it for any
service that is not on a two-name exception list, so an ordinary service of an existing shape needs
a manifest row and an implementation and no edit to the supervisor at all. `bootstrap.rs` lost a
third of itself - 1440 lines to 1106 - and every bespoke bootstrap function with it.

TWO SERVICES KEEP THEIR BRANCH, each for a reason the source states beside the list.
PermissionManager holds authority to hand ON, so several of its clients need `DUPLICATE`, which the
plan's client role does not grant; saying so would mean per-role rights in the manifest, which is
model growth for one service. SystemGraphService is handed one message per running component,
carrying that component's name, its edges and a read-only duplicate of its Process - the plan has
one `NODE` role and no way to say "as many as there are".

**WHAT THE WORK FOUND THAT WAS NOT PLANNED.**

- THIRTEEN SERVICES RECEIVED A CAPABILITY FROM A SERVICE THEY DID NOT DEPEND ON. Their start order
  worked by accident of the resolver. The manifest already carried a comment about the last time
  that happened - a machine that booted to no shell - and this was thirteen more of it. Declaring a
  provider is now a declared dependency, checked.
- EVERY SERVICE HELD `MANAGE`, `DUPLICATE` AND `REVOKE` OVER ITS OWN SERVICE CHANNEL. A fresh
  channel end carries every right and the supervisor transferred serve roots exactly as the kernel
  minted them. Narrowed to send, receive, wait and transfer - and eighty-six tests passed unchanged,
  which is the best evidence that nothing needed the rest.
- `DEVICE_MANAGER` DEPENDS ON `LOG_SERVICE` AND RECEIVES NO LOG HANDLE. An ordering-only dependency,
  which is why the `dependencies` column had to stay beside the roles rather than being derived away.
- `CONFIG_SERVICE` DOES NOT GET A PLAIN CLIENT. It gets one scoped to a directory, minted from
  StorageService's admin endpoint. That is policy, not wiring, and its branch legitimately remains -
  but the ROW said `client of SERVE` for a week, which is the wrong endpoint and the wrong kind. It
  says `factory of ADMIN` now; the confinement is still the part the plan cannot carry.
- `READY` IS A MESSAGE IN THE SEQUENCE, not decoration. The shell hung the moment it was migrated
  without one: a receiver that never sees the terminator waits forever for a send nobody will make.
  It is a declared role now.
- A SUPERVISOR THAT LOSES ITS OWN LAST BOOT REPORT. Making SystemManager resident deadlocked the
  boot twice, and both were mine: it served SystemPower only after the chain was up, while
  ServiceManager asks for its connection DURING bring-up; and it left a closed connection in its
  wait set, where a closed peer is permanently readable - sixteen million spins, measured, which
  starved the very reader that would have drained what it was trying to send.

**WHAT FINISHING THE MIGRATION FOUND**, because the last eighteen services were not just wiring.

- A PRIVILEGE THAT DID NOT EXIST SENT NO MESSAGE AT ALL. `send_privilege` returned success and sent
  nothing for a zero handle, while DisplayService reads that position with a BLOCKING tagged
  receive. A machine without the display privilege would have waited there for a message nobody was
  going to send. The plan's rule that the tag always travels is what removes it, and the rule was
  written for a different reason entirely.
- TWO ROLES SAID `CLIENT` WHERE THE BRANCH MINTED A CONNECTION. ProcessService's storage and
  ConsoleService's display were declared as duplicates of a shared root and wired as private
  connections - the same defect the second pass found in TimeService, twice more, found this time
  by reading the branch beside the row rather than by a test. Both are `factory` now.
- DISPLAYSERVICE'S FOCUS AND KILL WERE TRANSFERRED, NOT COPIED, and nothing said so. They are
  `exclusive` now, like the shell's console channels: InputService made those pairs for
  DisplayService alone, and a copy kept in the supervisor would mean the input side never learns
  that the display it forwards focus to has gone.

**WHAT THE MODEL STILL CANNOT SAY**, and therefore what the eighteen remaining branches carry: a
client scoped to a directory, a handle produced by a driver, the contents of a payload, and a
connection cached deliberately for the life of the system. Each is a fact the manifest would have to
grow a way to express, and each is named at the call site that supplies it rather than hidden. That
list is the honest boundary of M1's laziness rule: the model grew exactly as far as a consumer
needed it and no further.

## The control plane's own rows

The Definition of done asks for these two beside every manifest-managed service. They are written
here rather than in `manifest.toml` because neither is a managed service: ServiceManager is what
starts managed services, and SystemManager is what starts ServiceManager. A row in the file the
supervisor reads would be a service the supervisor tries to start.

| | SystemManager | ServiceManager |
| --- | --- | --- |
| recovery class | ephemeral | ephemeral |
| ownership scope | the system | the system |
| readiness rule | it relayed `ServiceManager: online` and reported `SystemManager: online` behind it | every manifest service it started reported online |
| what a process restart loses | everything: the SystemPower connections it minted, and the branch Domain it owns | every serve root it holds, so every managed service with it |
| restart or escalation | RESTART before the branch exists, REBOOT after - the branch is what separates the two | none: SystemManager kills the branch and ends, and the kernel reboots |
| what a guest reboot loses | nothing that was not already lost | nothing that was not already lost |

## What is still open, named rather than absent

- THE MIGRATION, which is M6 and M7 and is five of twenty-three. The two facts the first five found
  are in the model now, so the next batch is wiring rather than discovery.
- `RESTARTABLE()` READS THE DECLARATION and no longer repeats it, but the mechanism behind it -
  `relaunch_service` - still knows one bootstrap per name. The two are compared by
  `check-bootstrap-plan`, so the policy cannot come to promise a restart the mechanism cannot
  perform; what makes the list grow is the migration, not this item.
- HEALTH, AS DISTINCT FROM LIVENESS. M11 asks SystemManager to watch ServiceManager's health; what
  it watches is the branch channel, so a ServiceManager that hung with its channel open would not be
  noticed. The heartbeat exists and the watchdog ladder exists - they are exercised on the canary -
  and pointing them at the branch means ServiceManager answering probes on the channel it reports
  on. That is a real piece of work, and building a SECOND supervisor to avoid it is what M8 forbids.
- THE SERVICEMANAGER-ENDS ROW IS NOT MEASURED. The kernel half is: `control_plane_lost` decides,
  and the test asserts all three of its cases on a process that really ended. The userspace half -
  a closed branch channel leading to `domain_kill` and `exit` - is control flow inside SystemManager,
  and reaching it in a test means standing up a SystemManager, a ServiceManager and a branch, which
  is the fault-injection machinery M13 refuses. Named here rather than claimed.
- M5'S DRIVER CLAUSE HOLDS BY CONSTRUCTION AND NOT BY CHECK. "No driver ever receives root-Domain
  `MANAGE`" is true, and it is true because the capability is minted at exactly one line in the
  kernel and handed to exactly one process, which keeps it. What the manifest gate counts is
  `kind = power` on SERVICE rows, and drivers are `[[programs]]` with no roles at all - so if a
  driver were ever handed one, the gate would say nothing. The property is stronger than the check
  that guards it, and this is the record of that gap rather than a claim it does not exist.
- `RECEIVE_ROLES` COVERS THE FOUR MIGRATED SERVICES THAT READ POSITIONALLY. The shell reads its
  twenty-one roles BY NAME through `recv_caps`, deliberately: ConsoleService spawns it too, per
  virtual terminal, with a different subset. A positional contract there would be a contract with
  two senders who do not agree, so it keeps the set it has.

## What was dropped, and what was corrected

Reviewed 2026-08-21 against the tree, and re-reviewed 2026-08-22 against the code by a second pass
that checked the factual claims one at a time. Four planned milestones became this one. The rest is

### The second pass, 2026-08-22

The finished work was read again, item by item, against the code rather than against the record.
Nine defects. They are listed with what they cost, because the two that cost most were introduced by
this milestone's own migration and neither was caught by any test.

**THE SHELL'S CONSOLE CHANNELS WERE COPIED WHERE THEY USED TO BE HANDED OVER.** An ordinary client
role is a duplicate and the supervisor keeps the end it copied from - which is right for a service
channel several components share, and wrong for exactly two. ConsoleService reloads the shell on a
virtual terminal when that terminal's channel closes, which is what makes `exit` return a login
prompt; with the supervisor still holding a copy, the peer never closes and the console waits for a
shell that has gone. The old branch transferred those two and said so in a comment. The model now
carries `exclusive`, the manifest says it on both roles, and the manifest gate refuses a second
client of a root that is handed over.

**TIMESERVICE LOST ITS PRIVATE NETWORK CONNECTION.** Its branch called `network.open()`, which mints
a connection per caller; declared as a plain client it became a duplicate of the shared root, and
NetworkService carries a comment beside `open` saying why two callers on one channel take each
other's replies. Declared a factory now - and NetworkService answers the reserved connect request
like every other multi-client service, so `factory` means one thing everywhere rather than one thing
per service.

**THE RECOVERY LADDER COULD START A SECOND SYSTEMMANAGER BESIDE AN ORPHANED BRANCH.** M11 describes
this hole in three paragraphs and the implementation did not close it: SystemManager creates the
control-plane Domain early, so a fault after that point left a branch full of running processes and
the ladder retried anyway. The ladder now counts the root Domain's children and stops once an
attempt has built one, which is M11's rule word for word. Read-only: the kernel escalates, and the
branch's owner is what tears it down.

**A SYSTEMMANAGER THAT ENDED CLEANLY WAS REPORTED AS A SYSTEM THAT CAME UP.** `supervise` looked
only at the crash channel, which reports faults; a manager that returned sent nothing to it. The
test that covered this asserted the wrong thing outright - its stand-in body returned immediately
and the assertion was that supervision called that a success. Both cases are now asserted against
the same rule, and the stand-in that must survive blocks instead of returning.

**SYSTEMMANAGER COULD NOT TEAR DOWN THE BRANCH IT OWNS.** M12 asks for bulk termination through the
Domain; the handle was created, used for one `spawn_in`, and never passed to the loop that outlives
it. It is a guard on that loop now, so the branch goes down whichever of the five ways the loop
ends.

**THE POWER PATH'S FALLBACK COULD NOT SERVE ANYONE.** Without a wait set it fell back to serving
requests alone - except minting a per-holder channel calls `waitset_add`, which fails on a zero
handle, so every connect was refused, and the loop polled only the root channel, so a minted
connection would never have been read. Deleted. A comment promising a working power path over code
that has none is worse than the honest failure.

**FOUR DECLARED INTERFACES DID NOT EXIST.** Three roles named `liber:resources@1/resource` where the
interface is `resources`, and one named `liber:process@1/supervisor` for an interface defined in
`liber:observability@1`. Wrong from the day they were written, harmlessly, because no generator
reads the field - which is precisely how a declaration rots: it is read by people, who believe it.
`check-declared-interfaces` resolves every one of them against the IDL now.

**THE LIFECYCLE RECORD CARRIED AN EPOCH OF ZERO AND A STATE NOBODY ENTERED.** A first start read the
epoch from the slot holding the PREVIOUS instance, so the identity M2 added to tell instances apart
was absent from the first two entries of every service's history. And the restart path recorded a
transition to `Stopping` and then set `Failed`, so the history named a state the system had no
producer for - in a record whose whole purpose is to say what happened.

**A SERVICE THE OPERATOR STOPPED STILL READ `DESIRED: RUNNING`.** M8's first bullet is that the
deliberate act must be distinguishable from the accident, and only the shell's own logout path was
setting it: every `stop <service>` left the two fields disagreeing, which is what any drift check
would have reported as a fault.

**AND THE CHECK EARNED ITS PLACE TWICE ON THE FIRST RUN.** Wiring `receive_roles` into the four
migrated services that read positionally broke two things immediately, and both were real.

The test harness hands a serve root with `Rights::ALL` where the supervisor narrows it to send,
receive, wait and transfer, so LogService refused its bootstrap and the WASI component behind it
read nothing. A stand-in supervisor that grants more than the real one is a test agreeing with
nothing, so the harness was narrowed to what the supervisor sends.

Then the boot itself: a FACTORY role was delivered exactly as the provider minted it, which is with
every right the pair was made with, because the provider made the pair. Serve roots were narrowed
and duplicated clients were narrowed; the one kind that came from outside this process was not. The
provider decides that a connection exists and the supervisor decides what the holder may do with
it - different questions, and only one of them was being answered.

Both had been true for as long as the code existed. Nineteen services still read their bootstrap by
hand and would have accepted either.

Also from the same pass, and smaller: the root-Domain grant carried `TRANSFER` and `DUPLICATE` for a
delegation that M11 removed; `restartable()` was a hand-written list of three names beside a manifest
column naming the same three; `config_service`'s storage role said `client of SERVE` when what it is
handed is minted from the `ADMIN` root; TimeService refused to start without a network its own
manifest row calls optional; and the shell's `ADMIN` role is a pair on which the SUPERVISOR answers,
which the role kind's doc did not allow for.

### Corrected on 2026-08-22

**THE POWER CAPABILITY IS NOT AS WIDELY HELD AS THE FIRST DRAFT SAID.** It claimed every boot driver
holds root-Domain `MANAGE`. `device_manager.rs` guards that grant with `if driver_name ==
b"virtio_input" || driver_name == b"xhci"`, so block, network, GPU, sound and USB storage never
receive it. The real holders after boot are ServiceManager, DeviceManager and one instance each of
`virtio_input` and `xhci`; SystemManager is handed the capability and passes it on rather than
keeping it, so it is not among them either. The problem is real and the fix is unchanged; the scale was overstated, and an argument
that overstates its evidence is one nobody should act on.

**A CLIENT WHOSE SERVICE DIES DOES NOT HANG.** The first draft's M10 was built on the belief that
`rt`'s blocking receives block forever on a dead peer. They return `Received::Closed`, and
`SvcTransport::call` already reconnects through the broker and returns `TransportError::PeerClosed`,
so the next call reaches the replacement. M10 shrank from "make the client survive a restart" to the
one distinction that is genuinely missing - whether an interrupted request may already have been
acted on.

**THE KERNEL'S RECOVERY LADDER DOES NOT COVER A RESIDENT SYSTEMMANAGER.** The first draft said a
later SystemManager loss falls back to "the existing first-userspace recovery ladder". `supervise()`
returns true on the first round that completes without a fault and stops watching, so there is no
such fallback after boot. M11 now owns closing the hole it creates.

**NOT EVERY DEPENDENCY CARRIES A CAPABILITY, SO THE START ORDER CANNOT BE DERIVED FROM ROLES ALONE.**
The first draft of M1 said the start dependency follows from the role relation and the
`dependencies` column could go. `device_manager` declares a dependency on `log_service` and its
bootstrap line sends it the package, `POWER`, `CONSOLE` and `DEVPRIV` - no log handle anywhere. A
generator built on that claim would have dropped the edge and reordered the boot, and the failure
would have appeared as a service starting before its logger rather than as a wrong manifest.

Also corrected: the bootstrap ladder has twenty-three branches, not twenty-one, and
`bootstrap_permission_manager` takes twenty-six parameters, not twenty-five. And M6 was written
owning a deletion that M7 also owned, with the closure order between them backwards - one act
described in two items, which is the defect M1 exists to remove, appearing in the plan itself.

### Dropped

**THE DEVELOPMENT MACHINE PROFILE, ITS DIGEST AND THE ADR DIRECTORY.** The proposal was a
`DevelopmentMachineProfile` for the QEMU configurations on the three architectures, each with a
deterministic identity and a digest over its exact QEMU, firmware and device inputs, plus
architecture decisions kept in ADRs. A commit does not pin the host's QEMU version or the contents
of external firmware - that much is true - but the existing P02M0104 fingerprint and run logs
already record what a run used, which is what evidence needs. The ADR directory is worse than what
exists: this project keeps its reasoning in the milestone files and in unusually long comments
beside the code, which is nearer the thing being explained, and adding ADRs makes a third place
where reasons live - the exact duplication the rest of this milestone forbids. The one real finding
in that item is small and worth doing on its own: the QEMU invocation is written out in both
`qemu-run.sh` and `screenshot.sh`, and should be in one place.

**FOUR NEW IDENTITY TYPES.** `ArtifactId`, `ComponentId`, `DeploymentId` and `ServiceId` were to be
defined for a system with twenty-three services, where a deployment and a service are the same thing
and the manifest's existing names already separate an artifact from a program from a service. The
proposal itself warned against renaming subsystems for uniformity, which is most of what it would
have caused. `BootId` and `InstanceEpoch` survive because nothing in the tree can express what they
express - and even they reuse existing numbers rather than introducing allocators.

**THE SCHEMA DIGEST AND CANONICAL FORM.** `tools/system-manifest` already canonicalizes and
cross-validates. A digest on top of that detects drift the existing gates already detect.

**PROJECTING RESOURCE PROFILES AND CONFIG SCHEMAS.** ResourceManager owns limits and ConfigService
owns values, and both work. Adding manifest references to them, generating a projection of those
references, then checking the projection matches, is bookkeeping around two services that are not
the problem. The first draft dropped these from the model and then kept asking for them in the graph
and the conformance gate; that contradiction is fixed above.

**THE SYSTEM GRAPH AND THE RUNTIME CONFORMANCE GATE, DEFERRED RATHER THAN DROPPED.** Two items
stood here: give SystemGraphService the declared system beside the observed one, and fail a standing
gate on unexplained drift between them. They were written as optional in their own introduction -
"if this milestone has to be cut short, cut here" - and as mandatory in the definition of done,
which is a contradiction the reader would have had to resolve by guessing.

Resolved by cutting. THE SECURITY RESULT DOES NOT DEPEND ON THEM: M5 already compares what each
deployment was handed at boot against what it was allowed, which is the check that stops the
authority leak from coming back, and M13 already demonstrates the recovery paths. What the graph
items add is composition drift - a live deployment nobody declared, a declared one that is missing -
which is worth having and is not worth holding the two real fixes behind. They come back as their
own milestone once M1-M13 have landed and the identities they would render actually exist.

**A GRACEFUL SHUTDOWN SEQUENCE BEFORE THE POWER SYSCALL.** Suggested for the SystemPower proxy: ask
ServiceManager to stop the branch cleanly with a bound, then power off if that fails. It is a
reasonable feature and it is not this milestone, which is about who may hold the authority. Attaching
it here delays the narrowing behind work that has nothing to do with it.

**THE `v1` OWNERSHIP RULE, REPEATED IN EVERY FILE.** Four copies of a paragraph saying that
completing a milestone does not freeze an API, an ABI, a schema, a file format, a machine
description, a product profile or a release line. The project's standing rule already says nothing
is versioned before the first release. One sentence at the top of this file is the whole content.
