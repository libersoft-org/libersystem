# P02M0141 - Wiring the system can re-run, and authority it can prove

Status: PLANNED. SYSTEM-ARCHITECTURE FOUNDATION. NOT A PRODUCT, RELEASE OR UPDATE GATE. Nothing
here freezes a schema, an ABI or a version; the project's standing rule that nothing is versioned
before the first release applies to this milestone like every other.

## The two measurements this milestone exists for

Everything below is justified by two facts about the tree as it stands, both read out of the code
rather than assumed.

**TWENTY OF TWENTY-THREE SERVICES CANNOT BE RESTARTED.** `service_manager.rs` has a function called
`restartable()` and it returns true for three names - `config_service`, `device_service` and
`system_graph_service`. `relaunch_service` says why in its own words: `_ => return false, // A
service whose bootstrap this ladder cannot re-run.` The bootstrap is a hand-written ladder of
twenty-one `if name == b"..."` branches inside the parent, each one calling a bespoke function with
the capabilities that service happens to need - `bootstrap_permission_manager` takes twenty-five
parameters. A ladder is not a plan, and a plan is the thing you can run a second time. So twenty
services are marked `escalate` in the manifest, which means a crash leaves them Failed until the
guest reboots. The restart machinery from P02M0011 is present and correct and has almost nothing it
is allowed to act on.

**EVERY BOOT DRIVER HOLDS A CAPABILITY THAT CAN KILL THE WHOLE SYSTEM.** `send_power` duplicates the
root-Domain handle with `MANAGE | TRANSFER | DUPLICATE` and hands it to DeviceManager, which passes
it on to `launch_boot_drivers` and `launch_volume_drivers` - so the keyboard, block, network, GPU,
sound and USB drivers each hold it. What it is for is Ctrl+Alt+Del. What it also is, in the kernel's
own comment beside `sys_system_power`, is this: *"whoever holds MANAGE on it can already
`sys_domain_kill` the whole system"*. It also sets the root Domain's resource limits. This is a
capability system whose thesis is least authority, handing its broadest handle to a keyboard driver
because there is nobody resident to hold it and lend a narrow answer.

Neither of these is an aesthetic complaint about layering. One is the reason the system has no
recovery; the other is the reason its authority story is not true. The work below is scoped to those
two, plus the machinery needed to keep them from coming back.

## What this replaces

This milestone is the surviving half of four planned ones - P02M0141 through P02M0144 - reviewed
and merged on 2026-08-21. The three that were deleted are recorded at the end under WHAT WAS
DROPPED AND WHY, because a plan that quietly loses items teaches nothing about the judgement that
lost them.

## Scope

The existing owners keep their subjects. `src/user/services/manifest.toml` remains the one
hand-edited source and `tools/system-manifest` remains its parser, validator and projector.
P02M0011 keeps the watchdog, restart budget, backoff and teardown. P02M0098 keeps driver discovery,
binding and provider lifecycle. LSIDL keeps protocol schemas. The kernel keeps capabilities,
Domains and processes. ResourceManager keeps limits, ConfigService keeps values, PermissionManager
keeps dynamic application grants, SystemGraphService keeps the read-only projection. P02M0104 and
P02M0118 keep scenarios and test selection.

NOT IN SCOPE, and named so nobody adds them by drift: a second manifest or configuration language,
a general service registry, provider selection or version ranges, alternative providers, release
signing, update or rollback, remote management, multi-tenancy, a package ecosystem, workload
adoption across failure, or transparent recovery of arbitrary open resources.

## Work

### Part 1 - the model, extended only as far as something consumes it

The manifest already carries artifacts, programs, libraries, sources and services with their
dependencies, and already generates the runtime service table and the staging lists. What it does
not carry is the two things the bootstrap ladder encodes in code instead, and one runtime identity
that does not exist anywhere in the tree.

- [ ] **M1 - Declare each service's exact interfaces and bootstrap roles in the manifest.**
  - For every managed deployment, record the interfaces it provides and the interfaces it requires,
    with the current exact provider binding. Alternatives, ranges and runtime selection are out.
  - For every managed deployment, record the named capability roles it must be given before it can
    become Ready - the facts that live today inside twenty-one hand-written bootstrap functions.
  - Record the supervision and Domain parent, the restart class already in the `restart` column, and
    the fixed volume roles the current composition actually has, BY DECLARED IDENTITY rather than by
    discovery order. Volumes routed by an incomplete hand-maintained table is not hypothetical: two
    of the seven were unreachable from every program in the tree until 2026-08-21 for exactly that
    reason.
  - ADD NOTHING ELSE YET. A field with no consumer is a field that will be wrong when the first
    consumer arrives, because nothing was checking it. Every later part of this milestone that needs
    a new fact adds it here at that moment.
  - Reject duplicate names, missing references, dependency cycles and invalid parents.

- [ ] **M2 - Add the runtime identities that do not exist: `BootId` and `InstanceEpoch`.**
  - `InstanceEpoch` appears nowhere in the tree today, which is why a restarted service is
    indistinguishable from the one it replaced to anybody holding an endpoint from before.
  - Every start and every lifecycle transition carries the deployment's identity, the `BootId` and
    its `InstanceEpoch`, with a reason and a monotonic sequence, so a late event from a dead
    instance cannot overwrite a newer one.
  - DO NOT introduce `ArtifactId`, `ComponentId`, `DeploymentId` and `ServiceId` as four new
    identity types. The manifest's existing names already distinguish an artifact, a program and a
    service, and in this system a deployment and a service are the same thing. Introduce a name when
    a second consumer needs to say something the existing name cannot.

### Part 2 - generated wiring, so the bootstrap is a plan and not a ladder

- [ ] **M3 - Generate one start-and-roles plan and share its constants with both ends.**
  - Compile the start order and, for each deployment, the named roles it must receive, from the
    manifest.
  - The sender and the receiver read the SAME generated role constants. A hand-written vocabulary on
    one side and a hand-written read on the other is a defect this tree has already paid for: three
    programs read bootstrap tags out of the order the grant loop sent them, which made a blocking
    read consume the message that was actually next and then wait forever for one nobody sends.
    `kill` had been launching into a hang since it was written. It took a bisect over 170 tests to
    find, because the failure surfaced in an unrelated service.
  - Bootstrap cycles that genuinely exist stay visible and mechanically checked, under the component
    that owns them, instead of hiding inside a service-name branch.

- [ ] **M4 - Make the managed bootstrap path typed, complete and fail-closed.**
  - Reuse the current launch context, `CapSet`, typed grant sender and Ready/failure report. Do not
    invent a second envelope.
  - Refuse a missing role, a duplicate role, a role of the wrong type and an unexpected
    authority-bearing role, all BEFORE Ready rather than at first use.
  - Close every handle the receiver did not adopt, on the success path and on every refusal path.
  - Driver-specific control messages stay with P02M0098.

- [ ] **M5 - Generate the initial authority plan and check the boot against it.**
  - Describe every boot grant by grantor, target, capability class, rights and scope.
  - Generate the maximum initial holdings expected for each deployment and COMPARE THEM WITH WHAT
    WAS ACTUALLY DELIVERED during boot. This is the item that turns least authority from an
    intention into a checked property, and it is the one that would have caught the root-Domain
    handle sitting in the keyboard driver.
  - A service name is a lookup identity only; the capability remains the authority.
  - Dynamic grants stay with PermissionManager. No universal runtime derivation graph.

- [ ] **M6 - Reduce central bootstrap to a plan executor.**
  - ServiceManager becomes the sole executor of the ordinary managed-service plan. SystemManager
    consumes only the generated root and control-plane entry.
  - Delete every service-specific branch whose only work is to look up an artifact, send declared
    handles or register a graph node. Keep the ones that carry real policy or a real bootstrap
    cycle, under their owner, explicitly.
  - THE TEST OF THIS ITEM IS `restartable()`. When the plan can be re-run, that function stops being
    a list of three names and becomes a property of the declaration; a service is restartable
    because its roles can be delivered again, not because somebody wrote a branch for it.
  - Adding an ordinary service of an existing shape must need a manifest row and an implementation,
    and no edit to a central router.

- [ ] **M7 - Migrate projection by projection, comparing before switching, and keep comparing.**
  - For each projection - start order, roles, grants, placement - generate it, compare it against
    what the tree does today, and only then switch the consumer over.
  - Delete only the hand-maintained table the accepted projection replaces. Never leave a generated
    and an editable source for one fact.
  - KEEP THE COMPARISON AFTER THE MIGRATION ENDS. A generator with no second opinion is a single
    point of truth that cannot be wrong out loud, and the failure this tree found on 2026-08-21 was
    exactly of that shape in miniature: the protocol declared a write of up to 65535 bytes, the
    service read requests into 1024, and nothing compared the two, so every transactional write in
    the system failed silently for as long as the code had existed.

### Part 3 - runtime ownership, so failure has an owner and an outcome

- [ ] **M8 - One small lifecycle, with desired state kept apart from observed state.**
  - States: absent, starting, ready, degraded where a service means something by it, stopping,
    failed, stopped or replaced.
  - Started is not Ready, and one successful bootstrap reply is not lasting health. For each managed
    service declare the readiness condition, the health detector, the restart or escalation class,
    the retry budget, the backoff and the terminal result.
  - Reuse the P02M0011 watchdog and restart ladder. Do not add a second supervisor.
  - A restarted service gets a new `InstanceEpoch`; stale endpoints and late events stay attached to
    the old one.

- [ ] **M9 - Classify who owns each service's state, and say plainly what a restart loses.**
  - Classify every long-lived deployment as ephemeral, reconstructible, durable, external or
    session-owned, and name the owner, the storage where there is any, and the result of both a
    process restart and a whole-guest reboot.
  - DO NOT PROMISE that a replacement process inherits an open file, socket, watch, session or
    stream. The default result is an explicit loss or error, and saying so is the point: a system
    that implies continuity it does not have teaches its clients to omit the handling that would
    have saved them.
  - Per-service reopen or replay behaviour is added only by a service that actually implements it.

- [ ] **M10 - Give the client side of a restart an owner.**
  - THIS IS THE ITEM THE ORIGINAL PLAN DID NOT HAVE. M9 decides that a restart hands clients an
    explicit error; nothing in the four milestones owned the code that has to produce it. A restart
    nobody's clients survive is a restart that turns one dead service into several.
  - Define what a client holding an endpoint from a previous epoch observes, and make `rt`'s
    blocking receives and the broker's re-resolve produce it rather than block.
  - Cover it in the fault matrix below: a client that was mid-call when its service was replaced
    must get an answer, and the answer must name the epoch change rather than looking like a
    protocol error.

- [ ] **M11 - Keep SystemManager resident, and give the power path a narrow door.**
  - SystemManager is 153 lines today and exits once ServiceManager reports in, so nobody owns the
    control-plane branch after boot. It stays resident, owns exactly that branch, watches
    ServiceManager's health and owns the escalation decision when the branch fails.
  - Root-Domain `MANAGE` stays inside SystemManager. What DeviceManager and the keyboard path
    receive instead is a narrow local SystemPower request service - reboot and power off, nothing
    else. NO DRIVER RECEIVES ROOT-DOMAIN MANAGEMENT AUTHORITY. This is the milestone's security
    result and M5 is what keeps it true afterwards.
  - SystemManager does not absorb per-service wiring, application policy, driver policy or
    data-plane work. ServiceManager stays the one service supervisor.
  - If SystemManager itself is lost, use the existing first-userspace recovery ladder. No in-place
    resurrection framework.

- [ ] **M12 - Make supervision, failure and Domain ownership the same thing by default.**
  - Build the declared Domain hierarchy from the generated plan; supervision owner, failure parent
    and resource parent agree unless an exception is recorded and checked.
  - Bulk termination removes a whole owned branch through the Domain, which is what Domains are
    for, rather than through hand-written per-process cleanup.
  - On unrecoverable control-plane loss, stop advertising the branch as healthy and reach a declared
    reboot or terminal failure. Do not adopt workloads across it.

- [ ] **M13 - Exercise a finite fault matrix.**
  - Clean boot; a selected service crashing; a service hanging; a non-restartable service failing;
    ServiceManager lost; SystemManager lost; a device or provider lost; a resource denial; invalid
    configuration or state; and a client mid-call across a restart.
  - Each row names its detector, its owner and its bounded outcome: restart with a new epoch,
    explicit failure, branch teardown or guest reboot.
  - No ownerless userspace branch may remain reported as healthy.
  - Run through P02M0104 and register selection through P02M0118.
  - THIS IS NOT OPTIONAL POLISH. The evidence for that is this project's own record: the
    transactional writer was broken for every program in the system from the day it was written,
    through an argument-register mismatch that compiled without a warning, and it survived because
    no test had ever run the path. An untested recovery path is a broken recovery path.

### Part 4 - the graph tells the truth, and drift is an error

- [ ] **M14 - Give the System Graph the declared system beside the observed one.**
  - Generate desired deployment nodes and static binding edges from the manifest, using the same
    identities the build and bootstrap projections use, and keep them VISIBLY SEPARATE from what is
    observed.
  - Attach `BootId`, `InstanceEpoch`, lifecycle state, reason, sequence and freshness to live nodes;
    distinguish current, unknown, stale, down and degraded. On restart the old epoch is marked
    non-current before the replacement is presented as Ready.
  - SystemGraphService does not become a source of desired state or a control authority. It reads.
  - Report each deployment's actual Domain and resource parent, its state class and config schema
    identity, and whether its boot holdings stayed inside the generated maximum. DO NOT expose a raw
    global handle graph: a complete capability topology is an attack map, and the question worth
    answering is "did this deployment exceed its declaration", not "who can reach what".
  - CLI, JSON and CBOR stay renderings of one model.

- [ ] **M15 - Compare declared against observed, and fail a standing gate on unexplained drift.**
  - Detect an undeclared live deployment, a missing required one, a wrong Domain or resource parent,
    boot authority broader than declared, a stale current epoch and an unknown required profile or
    schema.
  - Classify the differences that are ordinary during starting and stopping, so a transition does
    not read as permanent drift.
  - The comparison is read-only. Remediation belongs to SystemManager, ServiceManager or the
    subsystem owner.
  - Add the architecture assertions to the M13 scenarios rather than writing parallel copies of
    them, plus the two cases that matrix does not have: a late event from a dead epoch, and an
    invalid bootstrap role.
  - Make a change to the manifest, the generators, the bootstrap, the managers, the Domain
    projection or the graph select the relevant scenarios through the existing verification model,
    and keep the everyday gates cheap enough to run every time.

The arrows are closure dependencies, not work order. Generators, negative tests and fixtures may be
written in parallel; each item closes against the implementation the one before it produced.

M1 IS DELIBERATELY LAZY. Do not finish the model and then look for consumers - add each fact when
the projection that needs it is being written. A model completed ahead of its consumers is a model
whose fields nothing has ever checked, and that is the way this kind of work usually dies.

## Definition of done

- `restartable()` is gone as a hand-written list: whether a service can be restarted follows from
  whether its declared roles can be delivered again, and the fault matrix demonstrates it on a
  service that could not be restarted before.
- No driver holds root-Domain `MANAGE`. The power path goes through a narrow SystemPower service and
  the boot-authority comparison proves no deployment received more than it declared.
- SystemManager stays resident and owns the control-plane branch; ServiceManager remains the one
  service supervisor and executes a generated plan.
- Adding an ordinary service needs a manifest row and an implementation, and no central branch.
- Every long-lived deployment has a state owner, a readiness rule, a restart or escalation outcome
  and a stated result for process restart and guest reboot; a client mid-call across a restart gets
  an answer that names the epoch change.
- Desired and observed graph state share identities, old epochs are visibly not current, and
  unexplained drift fails a standing gate.
- No fact has both a generated and a hand-edited source, and the generated-versus-observed
  comparison stays in place after the migration that introduced it.

## What was dropped and why

Reviewed 2026-08-21 against the tree. Four planned milestones became this one; the rest is recorded
rather than deleted silently, because the reasons are the useful part.

**THE DEVELOPMENT MACHINE PROFILE, ITS DIGEST AND THE ADR DIRECTORY.** The proposal was a
`DevelopmentMachineProfile` for the QEMU configurations on the three architectures, each with a
deterministic identity and a digest over its exact QEMU, firmware and device inputs, so later
evidence could name what it exercised - plus architecture decisions kept in ADRs. The digest answers
a question a commit hash already answers, for a tree with one developer and no release line. The ADR
directory is worse than what exists: this project keeps its reasoning in the milestone files and in
unusually long comments beside the code, which is nearer the thing being explained, and adding ADRs
makes a third place where reasons live - the exact duplication the rest of this milestone forbids.
The one real finding in that item is small and is worth doing on its own: the QEMU invocation is
written out in both `qemu-run.sh` and `screenshot.sh`, and should be in one place.

**FOUR NEW IDENTITY TYPES.** `ArtifactId`, `ComponentId`, `DeploymentId` and `ServiceId` were to be
defined for a system with twenty-three services, where a deployment and a service are the same thing
and the manifest's existing names already separate an artifact from a program from a service. The
proposal itself warned against renaming subsystems for uniformity, which is most of what it would
have caused. `BootId` and `InstanceEpoch` survive because nothing in the tree can express what they
express.

**THE SCHEMA DIGEST AND CANONICAL FORM.** `tools/system-manifest` already canonicalizes and
cross-validates. A digest on top of that detects drift the existing gates already detect.

**PROJECTING RESOURCE PROFILES AND CONFIG SCHEMAS.** ResourceManager owns limits and ConfigService
owns values, and both work. Adding manifest references to them, then generating a projection of
those references, then checking that the projection matches, is bookkeeping around two services that
are not the problem. If a missing profile reference ever silently applies an unrelated default, that
is a defect for ResourceManager to fix where it lives.

**THE `v1` OWNERSHIP RULE, REPEATED IN EVERY FILE.** Four copies of a paragraph saying that
completing a milestone does not freeze an API, an ABI, a schema, a file format, a machine
description, a product profile or a release line. The project's standing rule already says nothing
is versioned before the first release. One sentence at the top of this file is the whole content.

**AND ONE THING WAS ADDED**: M10, the client side of a restart. The original plan decided that a
replacement process does not inherit open resources and that clients get an explicit error, and then
never said whose code produces that error. It is in `rt`'s blocking receives and the broker's
re-resolve, and without it a restart converts one failed service into every client that was talking
to it.
