# M0109 - Service lifecycle: a data-driven manifest, a typed grant sender, and honest failure reports

Status: COMPLETE.

Three review findings shared one root: **service bring-up was half code, half convention.**

*Condensed 2026-08-08.*

**The service table was a hardcoded array, and the kernel build kept parallel name lists.** A single
manifest is the source of truth now: the user build generates ServiceManager's table from it, and the
kernel build derives every staging list it used to keep as five parallel arrays. The runtime service
set and the staged binaries can no longer drift, and adding a service is one row plus its code.

**The granting side of the bootstrap handshake still sent ad-hoc string tags** - an earlier milestone
had typed only the receiver. Both ends name every capability through one shared constant now, so a
renamed or mistyped tag is a compile error rather than a capability the receiver silently misses.
That matters because the receiver's `take` returns nothing for a name it does not find, which looks
exactly like a capability that was never granted.

**A service that failed during bootstrap exited silently** - the supervisor saw a peer-close with no
reason, roughly 40 `unwrap_or_else(exit)` sites deep. One rt helper sends a tagged report naming the
failing step and the reason before exiting; ServiceManager reads it in place of the "online" message,
journals it and surfaces it as the service's last failure. A close with no report at all is recorded
as exactly that, rather than as an unexplained failure.
