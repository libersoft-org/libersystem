# P02M0169 - Three bounded correctness debts: prepared launches, LSIDL rights and scheduler truth

Status: PLANNED. CORRECTNESS/HARDENING FOLLOW-UP. NOT A NEW SUBSYSTEM.

## Goal

Close three small findings which are real in the current tree but do not justify three independent
architecture projects:

1. every capability the schema declares and a manifest can request must be grantable, and every
   failed launch must be cancelled or recovered rather than merely losing the caller's task handle;
2. an LSIDL `@rights` annotation must either generate an enforceable dispatch guard or be rejected
   by the schema validator; and
3. the scheduler's contract-bearing comments must describe the preemptive, wake-migrating scheduler
   that is implemented now.

The three items are independent. They share this milestone only because each is a bounded correction
to an already implemented mechanism.

## What is there now

- The capability schema declares 23 capabilities. `VOCABULARY` carries 21, and the two it omits are
  `Session` and `DevicePolicy` - both of them already held, mapped to a tag and returned by
  `Clients::for_capability`. So the claim that there is one canonical ordered vocabulary is false
  in two places, not one. `kill` requests `Session` and waits for `SESSION`; `lsdev` requests
  `DevicePolicy` and reads `DEVPOLICY`. Neither can be granted.
- `recv_tagged` reads ONE message and matches its tag, so a capability that is never sent is not a
  capability the reader skips - it is a message the reader consumes on behalf of the next tag. A
  missing grant therefore desynchronises every later read in that handshake rather than degrading
  the one it belongs to. `lsdev`'s `CONFIG` read is downstream of its `DEVPOLICY` read for exactly
  this reason.
- ProcessService already implements `cancel` for a prepared launch. The pipeline path uses it on
  several failures, but `launch_under_manifest`, the single-tool path, the selected-file path, and
  some group-refusal paths still close `started.task` without cancelling the prepared process held
  by ProcessService. Closing the broker's handle is not cancellation.
- `ProcessService::release` REMOVES the prepared token before calling `Spawned::release`, and the
  runtime's `process_release` closes the thread token even when `SYS_THREAD_START` failed. So a
  single release that fails after that point cannot be cancelled: the token the cancel path looks
  up is already gone. PermissionManager reduces every non-`Ok(true)` single release to one bare
  `None`, which cannot distinguish a pre-start refusal from a start whose outcome is unknown.
- The pipeline seals its group AFTER the commit. `run_pipeline_under_manifest` returns live tasks,
  and only then does the caller call the fallible `process_group_create` and close every task
  handle; on failure it returns `Error::Invalid`. `sys_process_group_create` can fail on member
  count, a user-buffer copy, allocation, a handle lookup without MANAGE, and `ProcessGroup::create`.
  A complete pipeline can therefore be running after the broker has discarded every handle needed
  to signal, wait for, or reap it.
- Generated dispatch calls `handle_carries` for a direct `handle<T>` parameter and checks both
  minimum rights and a declared kernel object type. Three shapes escape it: a parameter whose
  written type is not literally `handle<...>`, an annotated method whose result cannot express
  `denied` (the generator emits the unguarded call), and a stream-return method - the ordinary
  dispatch loop skips those, and the separate `<method>_open` path calls the service with no guard
  at all. The validator checks right NAMES only, so all three compile.
- Resolver export metadata attaches `kernel_type` to resources and not to aliases, so an alias
  chain cannot carry the object identity the guard needs even where it resolves to a handle.
- `sched/mod.rs` still opens by calling the scheduler cooperative and non-migrating. Timer
  preemption is implemented, and a wake deliberately enqueues on the waker's core, so both
  statements are false. The migration comment further down is accurate about migration and then
  states that an address space live on two cores has no shootdown and calls that an open Phase-2
  item - while `mem/tlb.rs` implements a synchronous all-core flush that WAITS for every other
  online core to acknowledge before the frames are returned. Some local references to cooperative
  test-driving remain accurate and are not to be mechanically replaced.

## Work

- [ ] **M1 - the grant vocabulary is exhaustive against the schema.** Add `Capability::Session` AND
  `Capability::DevicePolicy` to the one ordered grant vocabulary, keep the existing SessionService
  and device-policy client wiring, and remove comments which still claim PermissionManager has no
  such client. Both are granted by this manager, from this `Clients` struct, through this
  `for_capability` - there is no second owner to assign either to. A missing held client is a typed
  failed grant; it must not start a component without the authority it requested.

  Add a compile-time or host-test exhaustiveness assertion over the generated capability enum so a
  capability added to the schema and not deliberately classified fails the build rather than
  producing an ungrantable manifest entry. The assertion is what makes "one canonical ordered
  vocabulary" checkable; without it this item closes two instances of a defect whose class stays
  open.

- [ ] **M2 - every launch has one rollback owner until commit, and one recovery owner after it.**
  Audit all four PermissionManager launch shapes (`launch_under_manifest`, one tool, a pipeline,
  and one selected file). After `launch_prepared` succeeds and before `release`/`release_group`
  commits, every error path cancels the koid through ProcessService and closes the local/bootstrap
  handles.

  **AND THE WINDOW OPENS BEFORE `launch_prepared` RETURNS, WHICH IS WHERE THIS ITEM USED TO START**
  (2026-08-30). The bootstrap handle is transferred with the request, so ProcessService can retain a
  prepared record and the reply can still be lost: `ChannelTransport::call` distinguishes
  `SendRefused`, `PeerClosed`, `ReceiveFailed` and `TimedOut` - and says in its own comment that a
  deadline means "the request may already have been acted on" - while the caller collapses all four
  into one `_ => { close(manager_side); return None; }`. At that point PermissionManager holds
  neither the koid nor a task handle, so there is nothing to cancel with, and dropping the temporary
  client does not close the shared service channel whose teardown would otherwise drive cleanup.

  **THE RECOVERY OWNER IS A PER-TRANSACTION OWNER CONNECTION, AND THE CALLER-ID DESIGN IS REJECTED**
  (decided 2026-08-31). An earlier version made a caller-chosen transaction ID the primary design and
  the owner connection an acceptable alternative. That is the wrong way round, because the caller-ID
  path cannot recover on the channel it would run on: `ChannelTransport::call` reads exactly ONE
  queued message and a generated call treats a correlation mismatch as failure without draining. So
  when the timed-out launch's reply arrives late, the next `status(id)` call consumes THAT reply,
  fails its correlation check, and leaves the real status reply queued to poison the call after it.
  A recovery mechanism whose first use corrupts the connection it recovers on is not one.

  Instead: THE TRANSACTION RUNS ON ITS OWN CONNECTION - not one connection per prepare (corrected
  2026-08-31). The caller opens a channel, performs the WHOLE transaction over it, and holds it until
  the transaction ends. For a single launch that is one prepare plus its release; for a pipeline it is
  every stage's prepare, the group seal and the group release TOGETHER, because `release_group`
  requires every named koid to belong to the CURRENT caller and prepared state is keyed by owner
  channel plus koid. One connection per stage would therefore leave no owner able to release the
  group, and each stage would be refused - so a per-prepare reading of this rule breaks the one
  operation the pipeline exists for. The connection is the transaction; the transaction is the whole
  pipeline. (The cross-owner fixture below proves the negative half - that one caller cannot reach
  another's prepare - and does not establish this positive rule, which is why it is written here.)

  Everything the caller-ID design needed follows from the connection rather than from a namespace:

    identity        the connection IS the transaction. There is no ID to mint, no collision to
                      resolve, no replay to define, and no reused-ID case to test
    ownership       structural. ProcessService already keys prepared state by owner channel plus
                      koid, precisely because a koid alone let one client start or cancel another
                      client's launch; this keeps that property instead of reintroducing the bug a
                      global ID would. It is also what forces the whole pipeline onto ONE connection,
                      above
    a lost reply    the caller drops the connection. ProcessService's disconnect cleanup is already
                      owner-scoped and already tears down what that owner prepared, so dropping IS
                      the cancel - and a late reply is delivered to a dead endpoint and discarded
                      rather than into the next call
    recovery        DROPPING IS THE ONLY RECOVERY, AND THERE IS NO STATUS CALL (corrected
                      2026-08-31). A previous version said status could be asked on the same
                      connection "because nothing else has ever used it". The timed-out call itself
                      used it: if that reply arrives late, the status call consumes it, rejects its
                      correlation and leaves the real status reply queued - which is the exact
                      poisoning defect this correction rejected the caller-ID design for, committed
                      by the replacement. Nor can a FRESH connection ask instead, because ownership
                      is the channel: a new connection sees none of the old one's records.
                      Dropping is not a weaker answer, it is the complete one for the case that
                      needs it. An uncertain PREPARE means at most a prepared-but-unreleased record
                      exists, and that is exactly what owner-scoped disconnect cleanup abandons -
                      handles closed, nothing running, the service's own record forgotten. So an
                      uncertain prepare reply drops the connection unconditionally
    retention       bounded by the connection's lifetime rather than by a policy about terminal
                      records: when the caller lets go, the record goes

  What is not acceptable is the current shape, in which the transport's four distinct endings are
  discarded at the one call site that can act on them.

  The four outcomes are handled distinctly by the caller: `SendRefused` means nothing was prepared;
  `PeerClosed` means the service is gone and its records with it; `ReceiveFailed` and `TimedOut` are
  UNCERTAIN and DROP THE TRANSACTION CONNECTION - which is the recovery rule above, and it applies
  whatever stage the transaction had reached. Where the transaction had already released, dropping
  frees the prepared remainder but NOT what is running, so the started-process recovery below still
  applies on top of it: dropping is the complete answer for prepared state and the necessary first
  step for the rest.

  M4 fault-tests a lost reply, a malformed reply, and a reply that arrives LATE - after the caller
  has given up - each proving no prepared record and no live process survives, and that the late
  reply reaches no other call. It adds the case the rejected same-connection status would have
  failed: a LATE prepare reply followed by a second call on that connection, proving the caller made
  no such call because it dropped instead. A cross-owner case proves one caller's connection cannot
  observe or cancel another's prepare, and a PIPELINE case proves every stage of one pipeline is
  prepared and group-released over ONE connection - a fixture that prepares two stages on two
  connections and then attempts the group release must be refused, which is what makes the
  one-connection-per-transaction rule testable rather than advisory.

  Give the SINGLE-launch release the same three typed outcomes the group release has, because the
  current collapse to one `None` is what makes the ordinary paths unrecoverable:

  - a PRE-START REFUSAL (the koid was not prepared, or not this client's): nothing ran, cancel is
    unnecessary and the record was never made;
  - a POST-REMOVAL START FAILURE: ProcessService has already removed the token, so cancellation
    cannot find it. The release path itself owns synchronous `forget`/Domain cleanup for the record
    it just orphaned;
  - an UNCERTAIN TRANSPORT/REPLY: the process may be running. Retain enough ownership to `SIG_KILL`,
    wait for confirmed termination, and remove/reap the record and Domain.

  `Ok(false)` from a group release is a pre-commit refusal: cancel every still-prepared member and
  preserve the promise that no stage ran. `Err` is different: ProcessService has removed the
  prepared tokens and may have started a prefix of the group. Recover it as above and report a
  commit fault; do not relabel that partial-commit recovery as an atomic refusal.

  `run_tool_under_manifest` currently calls the already-live `launch_bounded` for `imgconv`, so a
  later grant failure cannot be restored to "the tool never ran" with `cancel` or `SIG_KILL`. Extend
  the existing prepared request with that per-launch Domain bound, or add the one owner-scoped
  prepared-bounded operation, and commit it only after the same complete grant transaction as every
  other tool. Cancellation must synchronously remove its ProcessService record and Domain. Prefer
  one small guard/helper over hand-copied early-return sequences; do not otherwise redesign launch
  semantics.

- [ ] **M3 - a pipeline is sealed while cancellation is still possible.** Create the process group
  over the PREPARED members, before `release_group` commits, so the group handle exists as the
  cleanup owner for the whole transaction rather than being minted from tasks that are already
  running. A group-creation failure is then an ordinary pre-commit refusal: cancel every prepared
  member, start no stage, and return.

  If sealing over prepared members is not expressible against the current syscall - membership is
  taken over `Process` handles with MANAGE and is sealed at creation - then the group is created
  after commit and the caller MUST keep every task handle until creation has succeeded, recovering
  a failure by signalling, waiting for and reaping every member. Choose one; do not leave the
  current shape, in which the handles are closed before the failure is known.

- [ ] **M4 - the launch regression observes effects, not comments.** A positive fixture launches
  the real governed `kill`, proves that it receives the Session client, signals a controlled job and
  completes. A second positive fixture launches the real governed `lsdev` and proves it receives the
  device-policy client AND that its later `CONFIG` read is still aligned, because a desynchronised
  handshake is how this defect actually presents.

  Fault injection at each pre-commit handoff/grant, on the bounded prepared path, at group refusal,
  at group creation and during a group release proves that no prepared or live process, Domain
  charge, bootstrap handle, frame, or ProcessService record remains above its baseline. The refusal
  oracle additionally proves no stage ran; the injected partial-commit fault instead proves every
  possibly started stage was terminated and reaped and the fault was reported honestly. Cover all
  three single-release outcomes from M2 separately - a pre-start refusal, a post-removal start
  failure and an uncertain reply are different code paths and a fixture that only drives the first
  proves nothing about the other two. Cover a pipeline group and the selected-file path as well as
  the ordinary and bounded single-tool paths, because those are separate implementations today.

- [ ] **M5 - LSIDL refuses an unenforceable `@rights` promise.** Put one classification of an
  enforceable rights-bearing parameter behind both validation and generation. For this version the
  accepted shape is a parameter WRITTEN as `handle<resource>` - the exact shape for which dispatch
  emits `handle_carries`. Options, lists, results, records and NAMED ALIASES are rejected rather
  than recursively authorized, and an alias is rejected even where it resolves to a handle: the
  resolver attaches `kernel_type` to resources and not to aliases, so an accepted alias would
  silently fall back to `NO_REQUIRED_TYPE` and weaken the object-type half of the guard while
  reading in the schema exactly like a directly written handle.

  Reject two method-level shapes as well:

  - an annotated method whose result cannot return the schema's `denied` case, because the
    generator emits the unguarded service call for it today; and
  - an annotated method whose return is a STREAM, because the ordinary dispatch loop skips those
    and the `<method>_open` path calls the service with no guard. Rejecting is the smaller
    correction than teaching a second dispatch branch to enforce, and no schema in the tree
    currently annotates a stream method, so it costs nothing to close now and would cost a silent
    hole to close later.

  **AND THE ANNOTATION'S PRESENCE SURVIVES ITS ARGUMENTS** (2026-08-30). `@rights()` and `@rights(1)`
  are both accepted by the parser today - the argument list may be empty, and a numeric argument
  parses as `Arg::Num` - while `collect_rights` keeps only `Arg::Name`, so both produce an EMPTY
  rights vector. Validation iterates that vector and finds nothing to reject, and generation skips
  the guard when it is empty. So a malformed annotation is indistinguishable from no annotation and
  generates an UNGUARDED method, which is the exact outcome this item's Definition of done forbids.
  The parser must preserve that a `@rights` annotation was WRITTEN, separately from what it resolved
  to, and the validator must reject an empty list, a non-name argument and a repeated right.

  **AND A DENIAL CLOSES WHAT IT DECODED** (2026-08-30). Generated dispatch decodes the handle, calls
  `request_handles.clear()`, and then returns `Denied` without closing the decoded capability. That
  leaks it: `Handles` is `Copy` and documents itself as NON-OWNING transport metadata, `clear` only
  zeroes the numbers, and the serve loop's cleanup closes only handles still present in that list -
  so after `clear` there is nothing left for it to find. A refusal that keeps the capability it
  refused is worse than one that never checked, because the caller believes the handle was rejected.
  Generation closes every decoded request capability not handed to the service on the denial path.

  Compile-fail fixtures cover every rejected shape - nested, aliased (local AND imported),
  missing-denied, stream-return, `@rights()`, `@rights(1)` and a repeated right. A positive
  generated-dispatch test and a mutation prove that a bare handle still checks rights and object type
  before calling the service, and a RESOURCE-BASELINE fixture proves repeated denied calls return the
  process's handle count to its starting value - not merely that the metadata list is empty, which it
  already is. Update `docs/LSIDL.md`
  and its conformance checklist in the same change: the current annotation table explicitly says
  runtime enforcement is not generated, and the language contract may not remain weaker or
  contradictory after this behavior changes.

- [ ] **M6 - scheduler prose states the implemented contract.** Correct the module header and the
  other contract-bearing comments in `sched/mod.rs` which still globally describe cooperative or
  non-migrating operation. State the actual boundary: timer-preemptive per-CPU run queues, explicit
  remote placement/wake IPIs, and wake-side migration onto the waker's core.

  Correct the migration paragraph's TLB claim in the same pass. It states that an address space live
  on two cores has no shootdown and calls that an open Phase-2 item; `mem/tlb.rs` implements a
  synchronous all-core flush which waits for every other online core to acknowledge before frames
  are returned to the allocator. Describe what is actually there - a deliberately blunt whole-buffer
  flush on every other online core, with the waiting as the correctness argument - and say that the
  open refinements are a per-address-space active-CPU mask and per-page invalidation. A maintainer
  reading the current text can conclude that cross-core address spaces are unsafe and design around
  a hazard that was closed.

  Preserve accurate local descriptions of cooperative test harnesses. This item changes no
  scheduling policy, balancing, affinity, or TLB behavior.

## Definition of done

- Every capability the schema declares is either in the grant vocabulary or deliberately classified
  out of it, and a new schema capability that is neither fails the build. `kill` receives `SESSION`
  and `lsdev` receives `DEVPOLICY` through the governed production launch path, with every later
  tagged read in those handshakes still aligned.
- No failed prepared or bounded launch leaves a live process, ProcessService record or resource
  charge - INCLUDING a prepare whose reply was lost or malformed, which is recovered by DROPPING the
  transaction connection rather than being unobservable, and a pipeline whose every stage was
  prepared and released over that one connection.
  A pre-commit group refusal starts no stage; a partial-commit fault and an uncertain single
  start are recovered and reported without making that stronger claim; and a pipeline's group
  handle is never discarded while its creation outcome is unknown.
- Every accepted `@rights` annotation is guarded in generated dispatch; every unsupported parameter
  shape, alias, missing-denied result, stream return, empty argument list and non-name argument is
  rejected before code generation; a denial closes every capability it decoded, proved against a
  handle-count baseline; and the LSIDL specification states the same accepted shapes and enforcement
  behavior.
- The scheduler's contract-bearing documentation no longer contradicts preemption, wake-side
  migration, or the implemented cross-core shootdown.

## What this milestone refuses

- A new SessionService, device-policy service, permission model or general launch redesign. One
  owner-scoped prepared-bounded operation is allowed only to remove the current live-before-grants
  exception; group-fault cleanup may add only the narrow synchronous reap needed to close records
  it already owns.
- Recursive authorization semantics for containers of handles, and alias-chain propagation of
  resource/kernel-type identity. Rejecting an unsupported promise is the smaller and safer
  correction, and it is the same decision for both.
- Teaching the stream-return dispatch branch to enforce rights in this language version.
- Scheduler load balancing, affinity, topology work, a change to the 64-CPU admission policy, or any
  change to TLB shootdown policy. M6 corrects prose about the shootdown; it does not touch it.
