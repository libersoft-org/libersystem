# P02M0176 - Audit unsafe boundaries in the kernel and userspace before changing them

Status: PLANNED. AUDIT ONLY. NO SOURCE CONVERSION AND NOT A PHASE-2 COMPLETION GATE.

## Goal

Perform a dedicated audit of production `unsafe` boundaries in both the kernel and userspace and
decide, case by case, where safe Rust can narrow or remove the boundary and where `unsafe` is the
correct representation of hardware, ABI, raw-memory or concurrency invariants.

The existence of `unsafe` is not itself a defect. Kernel page tables, context switches, interrupt
entry, MMIO and DMA necessarily cross contracts the type system cannot prove. Conversely, many
userspace functions are declared unsafe only because a typed syscall wrapper or exported ABI is
unsafe, and that propagation may expose a much larger boundary than callers actually have to uphold.
This milestone first establishes which case each site is. It does not pre-decide that all unsafe code
must become safe.

## The configuration matrix is derived, not named

An audit's completeness claim is only as good as its enumeration of what ships, and the labels that
read naturally here do not match this tree:

- The SHIPPING KERNEL is not a Cargo release build. `build.sh` runs `cargo build` with no
  `--release`, and the volume is staged from the `debug` output. So `#[cfg(debug_assertions)]` code -
  the frame allocator's poisoning and accounting among it - IS in the shipping kernel, and an audit
  that reads "release kernel" as Cargo release would omit code that ships.
- STATIC USERSPACE is likewise Cargo's dev profile, with `development` enabled selectively for the
  services and drivers crates.
- SHARED-IMAGE USERSPACE is a materially different configuration: release mode,
  `--no-default-features --features shared-image`, a custom target with `-Z build-std`, its own
  RUSTFLAGS and a separate linking pipeline. It selects different runtime linkage, allocation,
  raw-memory and assembly boundaries in the same source.
- There is a THIRD shipped executable shape the current wording misses entirely: the SDK-built
  `wasm32-unknown-unknown` component. `build.sh` builds it `--release` with default features, the
  canonical manifest stages it at `components/liber_component/app.wasm`, and its in-tree closure
  carries unsafe host imports and linkage attributes. The separate `dev-diagnostics` build of the
  same example is development evidence and is a different row.

M1 therefore derives the matrix from the build scripts, Cargo metadata and the canonical manifest
rather than naming it, and each row records shipped artifact roots, target triple or spec, Cargo
profile, exact default and explicit features, build-std and Rust flags, relevant environment, and
the pinned compiler. Shipping, development-only and test-only closures stay separate.

## Work

- [ ] **M1 - freeze the artifact/configuration matrix and define the inventory mechanism.** Produce
  the derived matrix above, naming the current kernel accurately as the shipping non-test dev-profile
  configuration. Cover production `unsafe fn`, unsafe blocks, `unsafe impl`, raw pointers, mutable
  statics, inline/global assembly, FFI and unsafe linkage attributes across every row: the kernel on
  x86_64, AArch64 and RISC-V; static userspace; shared-image userspace; the shipping WASM component
  and its in-tree SDK closure; and the development-only closure as its own configuration.

  Define the INVENTORY MECHANISM rather than calling it syntax-aware, because a source parser counts
  disabled branches and macro definitions and cannot decide artifact reachability, while expanded
  output loses source provenance. Specify a toolchain-pinned pipeline that starts from the artifact
  matrix, captures build-script output and macro- and cfg-expanded code, reconciles it back to
  source-level sites, and records the commands, tool versions and digests it used. This tree needs
  that reconciliation to work: services and DeviceManager include generated code through
  `include!(concat!(env!("OUT_DIR"), ...))`, and architecture-selected macros emit `global_asm!`.

  Group generated wrappers and repeated architecture stubs by the shared invariant, record test-only
  and generated sites separately, include in-tree dependency code, and explicitly exclude the
  internals of third-party dependencies. Classify each boundary as: required caller-enforced
  unsafety; implementation unsafety correctly contained behind a safe API; unnecessarily broad and
  suitable for safe encapsulation/removal; ABI/linkage-only; or unclear/material defect requiring a
  follow-up.

- [ ] **M2 - audit the kernel by trust boundary.** Review the portable core and each x86_64,
  AArch64 and RISC-V backend, including pointer provenance/alignment/lifetime, page-table/direct-map
  ownership, per-CPU and interrupt concurrency, context/assembly ABI, usercopy fixups, MMIO volatile
  access, DMA/external mutation and every `unsafe impl Send/Sync`. Record what invariant makes the
  operation sound, who establishes it, which configurations/callers reach it, and what evidence can
  falsify it. Follow each proof through the safe admission/validation code it relies on: for example,
  raw per-CPU pointers and leaked scheduler/TLB tables depend on CPU-count truncation, allocation and
  publication ordering. The intentional 64-CPU portable cap (and lower backend caps) is a precondition
  to verify, not unsafe debt to remove in this audit.

- [ ] **M3 - audit userspace by cohort.** Separately review the runtime/syscall layer, drivers,
  core/storage/system services, libraries, applications, and the SDK/component closure. Distinguish
  real raw-memory or device invariants from a safe operation hidden behind an overly broad unsafe
  wrapper and from generated `#[unsafe(no_mangle/export_name)]` repetition. The component boundary is
  audited on both sides: the guest's host imports and linkage attributes, and the interpreter's side
  of the same contract.

- [ ] **M4 - publish decisions and route follow-ups to BOUNDED owners.** Produce an indexed audit
  report at `AI/audit/unsafe-boundaries.md`, pinned to the source revision and configuration matrix,
  which says where conversion/encapsulation is appropriate and where unsafe should remain, with the
  reason and missing proof for every material finding.

  Keep the revision's deterministic inventory beside the report as a machine-readable file with a
  fixed path, schema and regeneration command: stable site and group IDs, source or generator
  provenance, artifact and configuration reachability, boundary category, owner and disposition.
  Without those fields "every discovered site is represented" is circular rather than checkable. Add
  completeness fixtures for a cfg-only site, a macro-produced site, a generated site, an in-tree
  dependency site and a test-only site, so a missing class of site is mechanically detectable.

  Route findings by SEVERITY, not by subject area. A safe-encapsulation opportunity or a boundary
  that genuinely belongs to planned family work may be attached to its family item in P02M0099. A
  CONFIRMED UNSOUNDNESS OR MATERIAL DEFECT IN CURRENTLY SHIPPED CODE MAY NOT BE: P02M0099 states
  that its existing driver debt is not in its Definition of done and is deferred until the affected
  family's next item, so attaching a live defect there is an unbounded disposition wearing the word
  "owned". Every such finding gets its own narrowly scoped corrective item with a severity, an owner
  and a disposition identifier. This audit itself still edits no production code.

## Dependencies and ordering

- Independent of the IPv6 future track in P02M0174/P02M0175; the numeric order does not serialize
  the audit behind it.
- The snapshot covers whatever P02M0172/P02M0173 code is present at the revision selected when the
  audit starts; it is not a permanent obligation for later milestones to rewrite this report.
- P02M0099 receives only the dispositions M4 permits it to receive.
- This report is required before a later blanket unsafe-conversion campaign or next-phase assurance
  claim, not before ordinary Phase-2 completion.

## Definition of done

- Kernel and production userspace unsafe boundaries are inventoried and classified with explicit
  invariants and ownership across the DERIVED configuration matrix - including the shipping
  dev-profile kernel, shared-image userspace and the shipped WASM component - and generated/test
  repetition does not hide or inflate the production view.
- The report clearly distinguishes sites suitable for safe conversion from necessary unsafe sites.
- Every discovered site/group is represented in the revision-pinned machine-readable inventory, and
  the completeness fixtures prove that a cfg-only, macro-produced, generated, in-tree dependency or
  test-only site cannot be silently absent.
- Every confirmed unsoundness or material defect in shipped code has its own bounded corrective
  item; nothing material is parked on an umbrella that defers it indefinitely. This audit itself
  makes no blanket code change or ongoing policy.

## What this milestone refuses

- `forbid(unsafe_code)` for the kernel/runtime/drivers, mass wrapper churn, or a target unsafe count.
- Treating an adjacent `SAFETY:` comment as proof without checking its callers and lifetime model.
- Claiming Miri or host tests execute privileged assembly, MMIO or real DMA behavior they cannot see.
- Auditing the internals of third-party dependencies, or changing any build profile to make the
  matrix tidier. The matrix records what ships; it does not propose what should.
