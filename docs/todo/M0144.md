# M0144 - LiberFS: what a mount may still lose, and what a parser may not quietly repair

A second audit of LiberFS by the same fourth party, delivered after M0143 closed and verified claim
by claim against the code at `7352135` on 2026-08-06. **All ten of its new findings hold.** Two are
capable of destroying a disk, and neither is in LiberFS proper - both live where the filesystem
meets the medium and the partition table.

The audit also re-ran itself against a later commit and reported that nothing in LiberFS had
changed. That is correct and expected: the only commits since were shell tooling and documentation,
so the second pass restates the first. It is one round of findings, not two.

Its scoring of the 21 fixes from M0143 was checked too and is fair. Where it says a fix is complete,
it is; where it says one is partial, the remainder is in this milestone.

Ordered by what is at stake, which is not the order they were reported in.

## The two that can destroy a disk

- [x] **One unreadable or unsupported superblock slot is ignored when the other one parses.**
  `mount_at` records `saw_io` and `saw_unsupported` while reading the slots, and then consults them
  ONLY through `no_slot()` - which runs only when neither slot yielded a superblock. One valid slot
  is enough to proceed to a writable mount, whatever happened to the other.

  Two ways that costs a volume.

  A transient read failure: slot 0 holds generation 100 and reads cleanly, slot 1 holds generation
  101 and its read fails once. The mount takes 100 as the newest, and `prev_valid` is false because
  only one slot parsed - so `derive_free` reserves nothing for 101. Its blocks are free, the next
  transaction allocates them, and the commit after that writes over slot 1. A single failed 4 KiB
  read has destroyed the newer consistent generation.

  A format upgrade: a newer build writes a superblock this build reports `Unsupported`, and the
  other slot still holds the older format it understands. The old build mounts the old slot
  writable and begins overwriting the newer generation's data - which is exactly what the
  `Unsupported` arm was added to prevent, defeated by the aggregation rather than by the check.

  Wanted: for a normal writable mount, any unreadable slot alongside a valid one is `Io`, and any
  unsupported slot alongside an OLDER valid one is `Unsupported`. Opening the readable slot anyway
  is a legitimate thing to want, and it belongs behind an explicit recovery entry point that is
  always read-only.

  The M0143 mount test covers a dead device, a blank disk, and both slots unsupported. It does not
  cover one good slot beside one bad one, which is the case that matters here.

  Fixed as asked. `mount_at` takes a `MountMode` now, and `Newest` - the only writable one - refuses
  outright when either flag is set: an unreadable slot is `Io`, an unsupported one is `Unsupported`.
  The flags were being consulted only in the one case where they change nothing that matters (when
  nothing parsed, there is no volume to protect); they are consulted where there IS one.

  `mount_recovery` is the door that refusal closes: the newest slot that parses, whatever happened
  to the other, and read-only by construction rather than by policy - so nothing it cannot account
  for can be overwritten. A separate call on purpose, because the point of the refusal is that this
  is not a thing to do by accident.

  Pinned by a test that builds a two-generation volume, then presents it three ways: the NEWER slot
  unreadable (`Io`), the newer slot carrying a version this build does not know (`Unsupported`), and
  the same unreadable image through `mount_recovery` - which mounts, reads the file, and refuses a
  write.

- [x] **An ambiguous GPT probe still ends in formatting the whole disk.**
  `gpt_liberfs_partition` returns `Option<(u64, u64)>`, and `None` is the answer to six different
  questions: the disk has no GPT; the LBA 1 read failed; the header is malformed; an entry-array
  read failed; there is a GPT but no LiberFS partition; the partition found has an impossible span.

  `mount_or_format` treats every `None` the same - fall back to the whole device - and
  `FS_START_SECTOR` is **0**. So the fallback is not "past the partition table", it starts at sector
  zero. A GPT disk has no LiberFS superblock there, the mount returns `Unformatted`, and the service
  lays a fresh filesystem from LBA 0 over the protective MBR, the GPT header, the partition entry
  array and every partition on the disk.

  M0143 fixed the analogous rule one layer up - format only on `Unformatted` - and this is the same
  rule not yet applied to the probe: an answer that means "I could not tell" is being read as "there
  is nothing here".

  Fixed with exactly that shape: `PartitionProbe` with `RawDisk`, `LiberFs { first, last }`,
  `GptWithoutLiberFs`, `CorruptGpt` and `Io`. `RawDisk` is returned only when LBA 1 was READ and
  does not begin a GPT, which is the one answer that means "this disk carries no partition table".

  `mount_or_format` now takes the whole-device fallback for `RawDisk` alone. The other three refuse
  the mount, change nothing, and print which it was - a disk that did not answer, a GPT this build
  cannot read, a GPT that belongs to something else. Refusing costs a boot; the alternative cost the
  disk.

  This REVERSED a kernel test, and that is the clearest evidence the finding was real. A test built
  a GPT naming a LiberFS partition too small to use and demanded the service skip the entry and
  "fall back to the factory layout" - under the rule that the disk's content must never deny
  storage. The factory layout starts at sector ZERO, so falling back meant laying a filesystem over
  the protective MBR, the GPT header and the entry array. The rule is wrong when the content IS a
  partition table.

  The test now demands the refusal and, more to the point, checks what the disk looks like
  afterwards: the GPT header byte-identical, the entry array byte-identical, and no superblock at
  sector zero.

## Metadata a writable mount should not have accepted

- [x] **`next_inode` is checked against one number instead of against the highest one in use.**
  The mount added by M0143 reads `read_inode(next_inode)` and is satisfied when that exact inode
  does not exist. The invariant is stronger: `next_inode` must be above EVERY live inode key.

  A tree holding inodes 1 and 3 - inode 2 having been deleted - with a checksum-consistent
  superblock saying `next_inode = 2` passes that check. The first new file takes 2, the second takes
  3, and `tree_insert` overwrites the existing inode 3: every directory entry pointing at it now
  names the new file instead.

  Fixed on both paths. The live mark walk in `derive_free` already reads every leaf record, so it
  keeps the highest key it sees; the mount compares `next_inode` against it and degrades to
  read-only when the counter is not above it. The single-number read stays as a cheap second opinion
  for the case the walk could not finish. The structural pass makes the same comparison against the
  keys it collects and names it as a fault.

- [x] **The parser clamps impossible extent fields into possible ones before anything can object.**
  `Extent::parse` reduces `length` and `store_len` with `.min(CRCS_PER_BLOCK)`, which is 1024. A
  forged extent of `length = 5000, store_len = 5000` therefore reaches `check_extent` as `1024 /
  1024` - a perfectly well-formed raw run - and passes.

  The consequences are quiet ones: the file is silently reinterpreted as a shorter run plus a hole,
  the blocks past the first 1024 are reserved by nobody, `fsck` never sees the value that was
  actually on the medium, and the mount stays writable. The clamp is doing the job of a validator
  and reporting nothing.

  `read_snapshot_table` does the same with its record count, clamping to `SNAPS_PER_BLOCK` rather
  than calling an impossible count corrupt.

  Fixed as asked. `Extent::parse` reads both fields faithfully and `check_extent` refuses anything
  above `CRCS_PER_BLOCK` - the ceiling is a real one (one checksum block holds one CRC32C per stored
  block), and it belongs where exceeding it is an ANSWER rather than a silent repair.
  `read_snapshot_table` does the same with its record count instead of trimming it to the nearest
  possible value and carrying on.

  The record-layout test asserted the clamp as specified behaviour and now asserts the faithful
  round trip, including values no legitimate writer emits.

- [x] **The superblock's label is validated when written and not when read.** M0143 made
  `format_opts` refuse a label that is not UTF-8 or that contains a NUL. `parse_checked` copies the
  label straight out of the block with neither check, so a volume authored elsewhere still produces
  a `label()` that is not what the record holds. The same treatment the snapshot names got should
  apply here.

  Fixed: the slot is not this build's if the label is not text. What is checked is `name_in(&label)`,
  which is precisely what `label()` returns - the NUL padding after the name is part of the record,
  not part of the name.

- [x] **An unknown inode type keeps the volume writable while its blocks go unmarked.** This one is
  a disagreement with a documented decision rather than an oversight, and is worth deciding on
  again rather than assuming either way.

  `Inode::parse` says, in as many words, that a type byte which is neither `TYPE_FILE` nor
  `TYPE_DIR` parses file-shaped BY DECISION and lands harmless end to end: reads and writes refuse
  it, a listing shows it inert, the mark walks reserve nothing for it, and `remove` can clear it.
  That story is coherent and the code keeps it.

  What it does not cover is how such a type usually arises - one flipped byte in the type field of a
  real file. Then the file's data, checksum and spill blocks are reserved by nobody, the mount stays
  writable because nothing failed, and the allocator hands out blocks that were still recoverable.
  The structural pass does not report the unknown type either.

  The audit's position is that an unknown type should set `walk_damage`, be a structural fault, and
  keep the volume read-only. That trades the repair verb's freedom for the data's safety, which is
  the trade M0143 made everywhere else.

  Fixed, but NOT that way, and the difference is worth stating because the audit's version was tried
  first and a test caught what it cost. Degrading to read-only protects the blocks and takes the
  repair verb with it: the operator can no longer remove the record that caused the degradation, so
  the volume cannot be repaired in place at all. The existing test asserting `remove` clears such an
  inode failed, which is how it surfaced.

  The mark walk MARKS it instead, as the file `Inode::parse` already builds it as. That reserves the
  same blocks the read-only version protected, keeps the volume writable, and leaves `remove`
  working. Reserving is the conservative direction: at worst it holds blocks nothing needs until the
  record is removed, and at best it is exactly right, because the record usually IS a file whose
  type byte was flipped. The structural pass names the type, so it is not silent either.

  The existing test gained the two assertions that were missing: the blocks behind the record are
  reserved, and `fsck` names the type.

## Work a hostile image can make unbounded

- [x] **`collect_dir_entries` still has no visited set, so the live namespace is exponential.**
  M0143 gave the visited bitmap to `check_inode_tree` and `check_dir_tree`. `collect_dir_entries` -
  which is what every ordinary directory operation goes through - kept only its depth budget and
  recurses into every child pointer.

  A checksum-consistent internal node whose two hundred child links all point at the next level's
  single node is walked `fanout ^ depth` times. The mount does degrade to read-only, because the
  duplicate-owner check added by M0143 sees the repeat - but read-only does not help here: `list`,
  `read_dir`, `dir_has_entries`, `rmdir`, the replacing `rename`, `subtree_contains` and the live
  namespace walk of `fsck` itself all still go through this function. `fsck` reaches its guarded
  walker only later; it starts with `dir_entries_of`.

  Fixed as asked: iterative, with a visited bitmap, and a block reached twice inside ONE directory
  tree is `Corrupt` - a tree in a single generation is a tree, and the copy-on-write sharing that is
  legal elsewhere is between generations, never inside one. `dir_has_entries` stops at the first
  record it finds, since one entry is the whole answer.

  Pinned by the same shape as the fsck test - nine levels of twelve-way fan into one node each,
  built bottom-up so every CRC agrees - aimed at `list` and `read_dir`, under a device that panics
  past a read budget. Twelve to the eighth is about four hundred million; the budget is twenty
  thousand. Read-only is no defence against this one, which is why it needed its own fix: these are
  all reads.

- [x] **The free maps are still infallible allocations.** M0143 added `MAX_BLOCKS` and a checked
  cast, which stopped the truncation and the absurd sizes. What it did not change is that every map
  is still `vec![0u8; map_len]`, which aborts the process rather than returning an error.

  `MAX_BLOCKS` is 2^40 blocks, whose bitmap is 128 GiB, and a mount allocates `free` and `pinned`
  before `derive_free` adds `live`, a second `pinned`, `prev`, and the structural pass's `visited`.
  A checksum-consistent superblock naming a legal size can therefore ask for hundreds of gigabytes
  and take StorageService down through the allocator instead of returning `MountError`.

  Fixed as asked. One `try_zeroed` over `try_reserve_exact` for every map sized from a number read
  off the medium - both of the mount's, all three of `derive_free`'s, both of the structural pass's,
  and the two walk maps - and a `MountError::NoMemory` for refusing one. The mount's own maps are
  built BEFORE the filesystem value, so the refusal is a mount error rather than a half-built state.

  `NoMemory` is deliberately not a claim about the medium: it says this machine cannot hold the maps
  for this volume, and the same volume may mount elsewhere. That is why it is a separate arm rather
  than folded into `Unsupported`.

  Pinned by a volume at half the format ceiling - legal, and a 64 GiB bitmap - which now reports
  instead of aborting. The test also asserts an ordinary size still succeeds, so the guard cannot
  pass by refusing everything.

## Arithmetic that a checksum cannot make impossible

- [x] **The structural pass can overflow on a logical offset near the ceiling.**
  `check_file_shape` computes `ext.logical + ext.length as u64` plainly. `check_extent` bounds the
  PHYSICAL span and the length, and says nothing about `logical`, so an extent at `logical =
  u64::MAX - 2` with `length = 8` and a physical run inside the pool passes it - and then panics the
  checker in a debug build, or wraps in release and gets the overlap comparison wrong.

  Introduced by M0143's own structural pass, in a milestone that fixed the same class of arithmetic
  in `write_at` and `read_range`. Fixed with `checked_add`, and a logical range that leaves the
  address space is now a structural fault in its own right - which also stops the wrapped value from
  making the overlap comparison wrong for every extent after it.

- [x] **`dir.size += 1` can overflow on a damaged volume.** A directory inode whose checksummed
  `size` is `u64::MAX` panics in debug and wraps to zero in release on the next insert - and nothing
  refuses such an inode at mount, because neither the mount nor the structural pass compares a
  directory's `size` against the number of records its tree actually holds.

  Both done: the insert uses `checked_add` and reports `Corrupt` rather than committing a count that
  says the directory is empty, and the structural pass counts the entries a directory's tree
  actually holds and names the disagreement.

## The directory tree is still checked far more loosely than the inode tree

- [x] **`fsck` verifies file metadata thoroughly and directory structure barely.** The structural
  pass added by M0143 is genuinely strict about the inode tree and extent maps. Directory trees are
  reached mostly through `dir_leaf_parse`, which is deliberately tolerant: a record that runs past
  the end of the block ends the parse and it returns what it managed to read.

  So a truncated leaf yields a directory that lists part of itself, a `lookup` that cannot find an
  entry which is on the medium, and an insert that then edits a list already out of order - with
  `fsck` reporting no structural cause for any of it.

  Fixed with a `check_dir_structure` that walks every directory's tree iteratively, with its own
  visited map, and checks the whole list the audit gave: record counts against the header's and
  against what a block can hold, `(hash, name)` strictly ascending, duplicate names, `stored_hash ==
  name_hash(name)`, names that are the text the format says they are, separator ordering, child key
  ranges against those separators, a node type that is not a node, a block reached twice inside one
  tree, and `size` against the number of entries actually there.

  Child key ranges against their separators are done too, and they turned out to be the check worth
  having most - because they are the only one that is not local to a node. A leaf can be perfectly
  ordered, every stored hash can match its name, and every separator above it can be strictly
  ascending, and the leaf can still hold records that routing sends down the OTHER child. Those
  entries are on the medium, they count against the directory's size, and no lookup will ever reach
  them. Nothing local can see that; only the interval can.

  `route_child` advances while `sep(i) <= key`, so child `i` is routed `[sep(i-1), sep(i))` - lower
  inclusive, upper exclusive, open at the ends. That interval is carried down both walks, and the
  inode tree got it as well as the directory tree, since it routes the same way and the code is the
  same shape.

  Pinned by a two-leaf tree built by hand from two real names, with the separator set to the higher
  of their two hashes and each record placed in the leaf that cannot be reached for it. The test
  also asserts that the ordering and hash checks stay QUIET, so the fault it sees is the range check
  speaking and not one of the others catching the forgery first.

  Pinned by two forgeries and one control. The control matters most - a healthy volume with a
  directory of three files reports zero structural faults, because a false-positive checker is worse
  than none. Then a leaf claiming four hundred records, which walks off the end of the block and
  comes back short, and a directory whose cached size disagrees with its own tree.

  The first forgery had to be made bigger. Claiming a few extra records just makes the parser read
  on into the zero padding and hand back that many empty ones - caught, but by the hash and ordering
  checks rather than by the count the test was written to exercise.

## Closing

All eleven are done, with nothing held back. The LiberFS host suite went from 123 tests to 128, and
every new test was watched to FAIL with its fix reverted before being kept.

Two of the fixes did not end up where the audit pointed, and both are worth reading before the code:

- The unknown inode type is MARKED rather than degraded to read-only. The audit's version was
  written first and an existing test caught that it removes the operator's only repair verb.
- `check_extent` still does not demand `store_len < length` for a compressed run. That was settled
  in M0143 and remains true here: truncating a compressed file leaves the stored stream whole.

Two of the fixes are outside LiberFS entirely - the slot aggregation is in `mount_at`, and the
partition probe is in StorageService. That is where both disk-destroying findings lived.

## What this audit does not say

Nothing here was reproduced at runtime; the audit was static and so was this verification. Every
finding was confirmed by reading the code it names. Two details were checked further than the audit
took them and both make the picture worse rather than better: `FS_START_SECTOR` is 0, so the
whole-disk format in the second critical finding begins at sector zero and takes the GPT header with
it; and the unknown-inode-type behaviour is not an accident but a decision with a paragraph
explaining it, so changing it means overriding that reasoning deliberately.

The audit's own recommendation is the right first move again: the two critical findings are worth
more than the other eight together, and neither of them is in LiberFS - they are in `mount_at`'s
aggregation and in StorageService's partition probe.
