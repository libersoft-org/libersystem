# P02M0171 - A signed release can still be old: enforce a monotonic boot floor

Status: FUTURE TRACK. X86_64 OVMF BOOT SECURITY. NOT A PHASE-2 COMPLETION GATE.

## Goal

Extend P02M0150's authenticated QEMU boot so an attacker who can replace boot disks cannot boot a
correctly signed release older than the highest security generation this machine has accepted.

The claim is deliberately narrower than general update security: firmware authenticates a current,
anti-rollback-aware loader; the firmware-backed monotonic state and kernel/hypervisor are trusted;
and the attacker controls persistent boot media, not firmware/NVRAM administration. The QEMU proof
must prevent substitution of a pre-policy loader, because an older firmware-authorized loader which
ignores the floor would bypass the property before the new code ran.

The manifest format, signer and shared loader validation remain common to all three loader targets.
The enforcing completion profile is x86_64 OVMF, however, because P02M0150 qualifies firmware Secure
Boot only there. This milestone does not imply an anti-rollback chain on AArch64 or RISC-V firmware.

## What is there now, and what it forces

- Loader trust is COMPILE-TIME. The profile comes from `LIBER_TRUST_PROFILE`, defaulting to
  `test-trust`, and the accepted roots are compiled in - a release build without a key does not
  compile. So enforcement is already a property of the binary rather than of anything on the disk,
  and this milestone must keep it that way rather than inventing a second selector.
- Ordinary x86_64 QEMU runs COPY a fresh OVMF variables image on every boot and sweep stale copies,
  and the Secure Boot checker clones its base image and removes the clone. Under that lifecycle a
  monotonic floor is reset every boot, so monotonicity is vacuous unless a profile owns a persistent
  store. This is the reason the enforcing behavior cannot simply be switched on globally.
- The UEFI layer types exactly one Runtime Services entry - `GetVariable` - for exactly two
  hard-coded global variable names, and collapses every status and size failure to `None`.
  `SetVariable` is deliberately left as an untyped pointer, with the reason written in the file: a
  loader that could set variables could enrol its own key. Adding a write path is therefore a
  deliberate widening of that boundary and must be argued, scoped and tested as one.
- A manifest key has no purpose or role. `root_for` selects a root by key id, and verification
  checks product, architecture, source kind, volume identity and release. Manifest v2 carries no
  generation and no recovery discriminator.
- The product identity the loader compares against is a compiled-in constant, and its own comment
  records that it is one of four copies of the product name and names the milestone that will
  remove it. This milestone uses that constant; it does not add a fifth copy and it does not take
  over the deduplication.

## Work

- [ ] **M1 - freshness is a signed number, not a display version.** Introduce a new versioned signed
  manifest format carrying a canonical unsigned 64-bit `security-generation`. It is covered by the
  manifest signature and is independent of the human release string. External-release signing
  requires an explicit generation; malformed, missing, wrapped, or non-canonical values are
  refused. The shared parser, signer and loader agree on exactly the same bytes. Every medium and
  volume manifest composed into one boot must carry the same generation; latch and compare it
  independently of the human release string. An enforcing trust profile does not silently interpret
  a v2 manifest as generation zero or choose one value from a mixed-generation artifact set.

- [ ] **M2 - the enforcing profile is a build identity with a stated provisioning ceremony.** The
  anti-rollback profile is selected the way trust already is: a compile-time profile identifier and
  compiled-in roots, never a value read from replaceable media. Define, in this order:

  - which profile identifiers enforce the floor and which do not, and that `test-trust` and the
    development builds do NOT, so the ordinary fresh-variables boot paths keep working unchanged;
  - the UNPROVISIONED state and how it is distinguished from a failed read - an enforcing build
    that finds no state has either never been provisioned or is being attacked, and those are not
    the same answer;
  - the one-time PROVISIONING ceremony, who performs it, and the initial floor it writes; and
  - that after provisioning, missing state is a refusal rather than a reset to zero.

  Name the persistent variables-image owner and its lifecycle for the gate and for any public
  enforcing runner, explicitly against the ordinary per-run fresh copy. A negative fixture proves
  that replacement media cannot select a non-enforcing path or downgrade the profile.

- [ ] **M3 - the state record has canonical bytes and detectable torn writes.** Freeze the record
  schema before anything writes one: magic, format/version, explicit endianness and reserved-byte
  rules, product identity taken from the loader's existing compiled-in product constant, the
  accepted floor, and an integrity/commit discriminator that a partially written record fails.
  Selecting the highest "valid" slot is only a rollback defence if a torn write cannot parse as a
  plausible lower value, so the discriminator is the load-bearing field and not a checksum added
  for tidiness.

  Store it in two independently validated nonvolatile vendor slots. Fix the vendor GUID, the two
  variable names, the UEFI attributes required on read and written on write, and the maximum
  length. Extend the UEFI variables layer with a bounded typed `GetVariable`/`SetVariable`/readback
  path that returns DISTINCT outcomes for absent, short, oversized, wrong-attribute, access-denied,
  device-error, write-failed and readback-mismatch - the current collapse to `None` would make a
  firmware error indistinguishable from a provisionable absence. The write path is the only new
  Runtime Services entry this milestone adds, and the file's existing argument for why writes were
  excluded is answered in the same change rather than deleted.

  On read, select the highest valid floor; one damaged slot never authorizes the lower value in it,
  and two invalid slots refuse boot. Wrong product identity is a refusal.

- [ ] **M4 - compare and advance in a fail-closed order.** Verify the current loader, signed
  manifests, cross-manifest generation equality, product/architecture/source and every selected
  artifact first. The one generation of that complete selected set is the only input to the floor:
  refuse it below the stored value. For a higher generation, write and read back the older/inactive
  slot before treating it as current; never overwrite the only valid highest slot first. Selecting
  the maximum independently valid slot makes a torn/failed update leave either the previous valid
  floor or the new one, never an accepted lower value. Transfer control only after that readback.
  Equal generation remains bootable so a reinstall of the same release is not mistaken for a
  rollback.

- [ ] **M5 - recovery is a signed purpose, not a second copy of the same authority.** A manifest key
  currently has no role, so "separately authorized" has to be built rather than assumed. Choose ONE
  design and specify it:

  - a signed PURPOSE field in the manifest, enforced against purpose-scoped trust roots, so a root
    accepted for recovery is not accepted for ordinary boot and the reverse; or
  - a genuinely separate authenticated recovery-loader profile with its own firmware-enrolled
    signer.

  Either way, state its relationship to the firmware signer and to the generation floor: a recovery
  image must itself carry a generation at least as high as the floor, and recovery can never clear
  or lower the state. Cross-use negatives prove that recovery credentials cannot sign an ordinary
  boot set and ordinary credentials cannot claim recovery. Adding a recovery key to the ordinary
  accepted-root set is not an implementation of this item.

  Because this milestone does not build an A/B updater or health-commit protocol, a validly signed
  but broken higher-generation release may require recovery; document that availability tradeoff
  instead of weakening rollback checks.

- [ ] **M6 - the old-loader bypass is closed in the QEMU claim.** Rotate the QEMU policy-loader
  signer at this boundary: enroll the current signer and place the previously trusted loader signer
  in the firmware revocation database. The negative fixture is a real pre-policy loader which was
  accepted under the previous variables image and remains correctly signed by that formerly trusted
  signer; the updated persistent image must refuse it while accepting the current anti-rollback-
  aware loader. Record the signer transition and revocation as part of the trusted initial state.
  Production firmware enrollment/revocation operations and physical recovery remain outside this
  QEMU milestone, so documentation must not generalize the gate to arbitrary machines.

- [ ] **M7 - persistent multi-boot evidence.** A named x86_64 OVMF gate, using ONE persistent
  variables image across the whole sequence, boots generation N, refuses N-1 from both the original
  and a cloned disk, accepts N+1 and advances the floor, accepts N+1 again, and refuses a damaged or
  substituted state record. Power-loss injection around the state write must not produce an accepted
  lower floor. The recovery fixture succeeds at N+1 and is refused below it, and the cross-use
  negatives from M5 run here. A mixed-generation medium/volume set is refused without advancing the
  floor. The previously authorized pre-policy loader is shown accepted with the old variables image
  and refused after the M6 signer transition.

  Host fixtures over a mocked firmware cover what QEMU cannot be made to produce on demand: torn,
  short, oversized, wrong-product, wrong-attribute, absent, access-denied, write-failed and
  readback-mismatch reads and writes, and both-slots-invalid. Shared parser/loader fixtures keep all
  three target builds agreeing on the new manifest. Mutating the loader to skip comparison or
  readback makes the gate fail. Prove separately that a non-enforcing profile still boots with a
  fresh variables image, because that is every other run on this machine.

## Dependencies

- P02M0150 remains complete and owns origin/authenticity through signed manifest v2. This milestone
  adds freshness without changing what P02M0150 claimed.
- P02M0129 and P02M0151 own the loader/platform boundary and typed architecture contract.
- P02M0172 also proposes an authenticated loader-to-kernel value. If both are implemented, the
  manifest evolves once and the compatibility matrix covers both fields together rather than
  churning the format twice.

## Definition of done

- Under the named persistent x86_64 OVMF trust profile, a disk attacker cannot boot a signed
  manifest below the stored security generation or reset that generation by replacing media.
- Enforcement is selected by the loader build, never by the medium, and the non-enforcing profiles
  keep their current fresh-variables behavior.
- A higher generation advances atomically only after the complete authenticated artifact set is
  verified, and recovery is a separately authorized purpose which never lowers the floor.
- A pre-policy loader is not authorized in the profile used to make the claim.

## What this milestone refuses

- A/B installation, online update transport, health commit, package-level rollback or automatic
  rollback after a failed application start.
- TPM measured boot, remote attestation, production HSM/key ceremonies or physical-hardware
  qualification.
- A general UEFI variable API. One typed write path for these two slots, with the existing argument
  against a broader one answered rather than removed.
- Deduplicating the product-name constant; that belongs to the milestone the loader's own comment
  already names.
- AArch64/RISC-V firmware anti-rollback enforcement before those profiles acquire their own
  qualified firmware-authenticated loader and protected persistent-state gates.
- A claim against an administrator who resets/replaces firmware NVRAM or deliberately changes the
  firmware trust database.
