# M0086 - FAT: data-loss and correctness bugs

Status: COMPLETE. Both majors sit in the write half; the read-only paths were unaffected.

*Condensed 2026-08-08.*

**`unlink_in` never matched a long file name.** It compared only the 8.3 form and skipped the LFN
fragments, while remove and overwrite both routed through it - so removing a long-named file returned
`NotFound` on a file that exists, and **an overwrite added a duplicate directory entry and leaked the
old cluster chain forever**.

The tests missed it for a specific reason worth remembering: the one long-name write test **wrote
once and never overwrote or removed**. A test that exercises creation only cannot see a defect in
deletion.

**The exFAT NoFatChain flag was ignored.** Windows writes contiguous files with no FAT chain at all,
which on real media is most files - so a multi-cluster file read back **silently truncated** to its
first cluster, and removing it freed only that cluster. Both reads and frees now go by length for
such files, including for NoFatChain subdirectories.

**`write_file` freed the old file before the new one was safe.** The order was unlink, allocate,
write, add entry - so a failure at the last step lost the old data *and* leaked the new chain. Both
families now allocate and write first, swap the directory entry in one read-modify-write, then free
the old chain, with the new chain freed on any failure path.
