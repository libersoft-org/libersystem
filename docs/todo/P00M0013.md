# P00M0013 - Fault isolation and crashed-process cleanup

Status: COMPLETE.

A userspace page fault or GPF terminates only the faulting `Process`, never the kernel, and the other
cores and the scheduler keep running across the kill.

*Condensed 2026-08-08.*

The page-fault and #GP handlers check the saved code selector's privilege level: a ring-3 fault
records a `FaultInfo` on the running `Process` and longjmps back into the kernel thread that entered
ring 3, reusing the same mechanism a normal return uses. Teardown then closes every handle, frees the
frames and the address space, and refunds the Domain accounting. `fault_info_get` exposes what
happened to whoever asks.

## Two later corrections worth keeping

**A booted system killed a process on every boot, and nobody knew which.** It is `watchdog_probe`,
ServiceManager's managed canary, and the fault is deliberate: its `CRASH` handler writes to the
unmapped null page, which is exactly the `code 0x6` in the report. A deliberate crash that looks
identical to an accident in the log is a permanent source of doubt.

**The fault message now names the process.** It reads
`fault: ring-3 <kind> (code 0x6) at 0x20173f, addr 0x0 - terminating process koid=4935
(watchdog_probe)`, emitted from `fault::terminate_user` - the one path all three architectures reach,
so no target can drift into reporting less.
