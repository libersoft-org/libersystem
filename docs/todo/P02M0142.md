# P02M0142 - General platform and server architecture

Status: PLANNED AFTER P02M0141. FUTURE SERVER PRODUCT-PROFILE GATE. NOT A PHASE-2 COMPLETION GATE.
This milestone does not block the production reference appliance; it begins only from P02M0141's
canonical identities, SystemSpec, lifecycle, authority, release and recovery contracts.

## Goal

Generalize the deliberately simple, whole-image reference appliance into a server platform that can
host multiple tenants, dynamic provider instances, third-party packages and mixed-version service
boundaries without weakening capability authority or turning ServiceManager into a distributed
orchestrator.

The server is not "the appliance with more drivers". It introduces architectural promises the
appliance intentionally does not make: contract-based provider selection, optional and degraded
dependencies, explicit availability tiers, principal and delegation policy, revocable grants,
multi-tenant temporal/resource isolation, dynamic volume namespaces, network transport security and
compatibility windows. Each promise needs a product profile and a failure model of its own.

Task prefixes are global within this three-milestone architecture track: `M1.x` is the appliance,
`M2.x` the general/server platform and `M3.x` the desktop/application platform.

## Decisions fixed by this milestone

- Components depend on `interface@version + scope + constraints`, not on a concrete process name.
  A deployment plan may bind that requirement to an instance, but the requirement itself remains a
  contract.
- Startup order and runtime failure dependence are distinct. A start barrier does not imply that a
  consumer must die when its provider later disappears.
- Protocol version negotiation answers compatibility only. Provider authenticity/provenance comes
  from an authority-preserving trusted resolver and signed composition, not from a handshake or
  self-reported service name.
- P02M0141's resolver binds a closed, signed, lockstep appliance composition to one exact provider
  version and scope. This milestone generalizes that seam to alternatives, tenant scopes, dynamic
  providers, placement and mixed versions; it does not replace the stable identities or capability
  authorization already defined there.
- A principal is identity and policy context, never ambient authority. An operation still requires
  a capability derived by an authorized grantor.
- The per-volume StorageService process model is retained. The missing layer is a Volume Registry,
  dynamic instance lifecycle and namespace composition, not one larger storage process.
- The appliance's whole-epoch fail-closed recovery remains the default. A server availability tier
  may preserve a workload only through an explicit adoption/rebind protocol and a stable recovery
  root outside the replaced control-plane epoch.
- This is a node/server architecture, not a cluster scheduler. Replication, consensus, distributed
  placement and cross-node live migration are separate future product work.

## Relationship to existing milestones

- P02M0098 remains the owner and normative device pilot for discovery, binding, generation fencing,
  hotplug and per-device provider lifecycle. This milestone projects/adapts that pilot into the
  general Service Registry; it does not invent a second device binder or incompatible event model.
- P02M0106 first freezes the local account, AuthService, login and account-bound session model.
  M2.7 extends those exact principal and credential identifiers to tenants, services and remote
  operators; it does not proceed with a parallel account schema.
- P02M0012 and P02M0130 own the current Liber component ABI/SDK; P02M0093 and P02M0095 own the
  image-internal native artifact model. This milestone defines compatibility and trust boundaries
  around third-party packages rather than reimplementing those formats.
- P02M0103, P02M0105, P02M0135 and P02M0136 are not server prerequisites unless a concrete server
  profile selects graphics, locale or foreign application stacks.

This milestone does not own physical-hardware breadth, individual network protocols, a desktop,
Mesa/OpenGL/Vulkan, a POSIX layer, an app store or cluster orchestration.

## Work

- [ ] **M2.1 - Publish the Server Product Contract and availability profiles.**
  - Define supported deployment shapes, tenant assumptions, operations model, compatibility window,
    availability goals, durability promises and exact MachineProfile overlays.
  - Name at least a baseline tier that follows appliance whole-epoch recovery and any higher tier
    that promises independent provider restart or workload survival. Give each tier its own RTO,
    RPO, state and dependency requirements.
  - State whether a profile is single-node, which services may have multiple instances and which
    singleton assumptions remain. Do not imply cluster availability from process restart.
  - Classify every server-facing interface as local-only, authenticated remote, image-internal,
    mixed-version or third-party. Record explicit non-goals instead of inheriting Vision prose.

- [ ] **M2.2 - Extend appliance contract bindings to alternatives and typed runtime dependencies.**
  - Start from P02M0141's exact `provides/requires` and add server version ranges, tenant scope,
    alternative/multiple-provider constraints, necessity and availability/SLO expectation; do not
    redefine the base interface or identity schema.
  - Give every edge one runtime meaning: `startup`, `runtime-hard`, `runtime-soft`, `optional` or
    `observe`; define provider loss, retry, degraded behavior and restart propagation separately.
  - Support declared alternatives and selection policy without letting a consumer gain authority to
    every candidate provider.
  - Reject ambiguous providers, unsatisfied required contracts, impossible scope bindings,
    incompatible versions and dependency cycles at composition time where they are decidable.
  - Migrate central process-name dependencies; names may remain deployment labels but are no longer
    the semantic interface.

- [ ] **M2.3 - Extend appliance templates to tenant cardinality and provider placement.**
  - Reuse P02M0141's static, per-device, per-volume, per-session and on-demand templates and add
    tenant scope, alternative-provider selection and server placement constraints without a second
    runtime-instance model.
  - Define trigger, creator/grantor, supervision owner, cardinality, admission, placement,
    co-location/anti-affinity and teardown condition for every dynamic class.
  - Remove singleton routing assumptions from service publication, DeviceManager, volume binding and
    session/workload launch paths selected by the server profile.
  - A creation event produces one attributable `ComponentInstanceId/InstanceEpoch`; disappearance,
    duplicate discovery and reappearance cannot alias an earlier instance.
  - Dynamic instances inherit declared authority/resource maxima and may only narrow them for their
    concrete scope.

- [ ] **M2.4 - Extend the appliance resolver into a multi-provider server registry.**
  - Preserve P02M0141's `ServiceId`, `InstanceEpoch`, scope and fresh-endpoint semantics; add
    multiple providers, supported version ranges, health, availability tier, provenance and
    placement metadata.
  - Resolve only through a capability authorizing the requested interface and scope. Listing and
    discovery rights are separate from connection rights, and registry metadata is redacted for an
    unauthorized observer.
  - Return a fresh client endpoint or an explicit brokered proxy; never duplicate one shared reply
    endpoint across mutually untrusted clients.
  - Make registration, replacement and removal atomic against resolution, with generation checks
    that reject a stale provider or late event.
  - The registry cannot mint broader authority than it received and cannot authenticate a provider
    from a self-asserted name.

- [ ] **M2.5 - Separate mixed-version compatibility from provider provenance.**
  - Define LSIDL interface identity, compatible version ranges, feature negotiation, unknown-field
    behavior and deprecation windows for boundaries where releases may mix.
  - The trusted resolver binds a returned endpoint to the signed deployment/provider provenance;
    protocol negotiation then selects a mutually supported semantic version and nothing more.
  - Define rolling replacement for stateless and stateful services, including in-flight request,
    stream/resource epoch and state-schema rules. Refuse rolling upgrade where whole-image lockstep
    remains the honest contract.
  - Add compatibility matrices and bidirectional conformance tests across every supported adjacent
    version; latest-to-latest alone is not a compatibility policy.
  - Do not add service semantic types to generic kernel Channels or treat a sealed token as proof
    that the provider implementation is correct.

- [ ] **M2.6 - Define explicit control-plane replacement, adoption and rebind for higher tiers.**
  - For each availability tier decide which workloads and providers are inside the replaceable
    control-plane epoch and which, if any, live in independently owned Domains.
  - A preserved workload must have a stable recovery owner outside the replaced epoch, a bounded
    adoption token, a declared resource-account parent and a protocol for reconnecting policy,
    registry, config and observability state.
  - Put only the minimal `RecoveryCoordinator`/`ResolverRoot` needed for that promise in the recovery
    Domain. It may redirect an authorized resolution but may not become an ambient service root.
  - Define split-brain exclusion, epoch fencing, abandoned-operation handling and fallback when
    adoption cannot complete. The safe fallback is the tier's declared kill/restart behavior.
  - Prove that no process can survive merely because it was accidentally outside the manager's
    Domain tree.

- [ ] **M2.7 - Complete the principal, credential and delegation model.**
  - Define stable identities and lifecycle for human accounts, services/workloads, devices and
    remote operators. State which identities persist across release, reboot, session and tenant
    recreation.
  - Keep authentication, attribution and authorization separate: credentials prove a principal,
    policy selects an allowed derivation, and an actual capability authorizes the operation.
  - Integrate P02M0106's local account/AuthService/session model and P02M0141's appliance operator
    identity without creating parallel credential stores or principal identifiers.
  - Define service/workload credentials, provisioning, rotation, expiry, revocation, recovery and
    audit correlation, including a secure time-uncertain bootstrap path.
  - Model delegation between principals only as attributable attenuation of held authority; a role
    or group may inform policy but never becomes a kernel-wide ambient check.

- [ ] **M2.8 - Generalize leases and revocation across capability derivation.**
  - Reuse the scoped leased proxy required for P02M0141's RemoteGateway as the first concrete
    mechanism, then define which other grant classes use a brokered lease, generation/epoch fencing,
    Domain termination or a true object-wide revoke.
  - For each grant class implement the declared mechanism: object-wide revoke where appropriate,
    otherwise a generation-fenced proxy/lease, epoch fencing or failure-Domain termination.
  - Track derivation provenance, parent grant, rights/scope attenuation, lease clock/expiry,
    revocation owner and cleanup acknowledgment.
  - Cover logout, the foreground display/input grants removed by session lock, powerbox grants,
    device removal, tenant teardown, operator revoke and service-epoch replacement. Background work
    explicitly allowed to survive lock keeps only its declared authority. Closing one duplicated
    handle is not revocation.
  - Define behavior for in-flight operations, offline providers and recovery after the revocation
    owner restarts; stale leases fail closed and cannot revive after clock rollback or epoch reuse.
  - Publish revocation events without exposing the underlying sensitive authority graph.

- [ ] **M2.9 - Build multi-tenant failure, resource and temporal isolation.**
  - Define tenant, service and workload Domain hierarchy, ownership, bulk termination, state
    boundaries and cross-tenant shared-service policy.
  - Resource profiles include memory, objects, queued IPC, threads, CPU shares/reservations,
    priority, interrupt/DMA work and recovery reserve. Define overcommit and admission explicitly.
  - Bound per-principal connections, requests, streams and outstanding work at shared services; one
    tenant's backpressure may not block unrelated tenants or the control plane.
  - Define priority inversion/donation across tenant-to-service IPC and protect availability-tier
    budgets from interrupt or background work storms.
  - Provide per-tenant accounting and pressure events without exposing another tenant's topology or
    usage beyond the authorized aggregate.

- [ ] **M2.10 - Extend the Volume Registry and compose namespaces for path-oriented hosts.**
  - Retain one isolated storage worker per mounted backend. Register volume UUID, instance epoch,
    media/device provenance, filesystem type, health, mutability, state class and mount policy.
  - Define duplicate UUID, removal/reinsertion, hotplug, stale handle and device-reset behavior. A
    reinserted medium never silently inherits the old worker epoch.
  - Native capability clients receive concrete object/directory capabilities. Only a path-oriented
    app host or session receives a namespace composed from explicitly granted roots; a friendly name
    is not authority and global ambient `/` or drive-letter discovery is not introduced.
  - Provide the common scoped grantor/lease mechanism used by tenant policy and later powerbox
    choices. P02M0143 owns the trusted user-choice UI and desktop portal policy.
  - Define the narrow coordinator contract for operations intentionally spanning volumes, including
    partial-failure and recovery semantics, rather than pretending independent filesystems provide
    an atomic cross-volume transaction.

- [ ] **M2.11 - Define the multi-interface network and transport-security architecture.**
  - Model interfaces, addresses, routes, DNS, policy domains and network namespaces as scoped
    resources rather than one global NetworkService state.
  - Separate link/transport mechanisms, routing/policy ownership and application-facing socket
    authority; multi-homing and interface replacement use stable identities and epochs.
  - Define TLS or equivalent authenticated transport termination, credential ownership, trust roots,
    rotation, revocation and connection identity for remote services.
  - Integrate RemoteGateway without making it an ambient bypass around PermissionManager, tenant
    network policy or the service resolver.
  - Specify admission, fair scheduling, connection limits, audit and degraded operation when DNS,
    time, one interface or a certificate authority is unavailable.

- [ ] **M2.12 - Freeze the third-party package and application compatibility boundary.**
  - Define signed package identity, publisher/provenance, dependencies, requested interfaces,
    resource profile, state schema, supported app contract and install/upgrade/remove lifecycle.
  - Treat package metadata as a request for authority, never a grant. Composition/policy must resolve
    it to explicit scoped capabilities or refuse installation/launch.
  - State which native ABI, LSIDL, Liber Wasm and future adapter versions a server profile supports;
    do not label the current core-Wasm world as general WASI compatibility.
  - Isolate untrusted parsing/instantiation and bind the resulting deployment to the exact verified
    package bytes and publisher policy.
  - An app store, POSIX compatibility and arbitrary Linux binaries remain outside this milestone;
    the seam and refusal behavior are the deliverable.

- [ ] **M2.13 - Extend operations, audit, SLO and property-specific trust views.**
  - Use the common lifecycle event plane for tenant, provider, binding, lease, config, state,
    security and update events with sequence, freshness and gap semantics.
  - Define availability/latency SLOs and health aggregation per tier. A green process heartbeat is
    not proof that a service or dependency chain meets its SLO.
  - Provide capability-scoped local and remote operational views, bounded cursors/retention and
    nonblocking subscriber delivery. Slow observers cannot stall policy or service execution.
  - Maintain separate transitive TCB/trust analyses for boot integrity, tenant isolation,
    authorization, confidentiality, update provenance, transport security and DMA under each
    MachineProfile.
  - Audit grants, delegation, resolution, revocation and administrative actions using stable
    principals and epochs without logging secret payloads.

- [ ] **M2.14 - Migrate one complete server profile and prove the architecture under churn.**
  - Select a finite reference server composition and migrate every deployment to contract-based
    requirements, dynamic identities, scoped resolution, principal context, tenant Domains and
    operations events.
  - Exercise simultaneous provider replacement, optional-provider loss, incompatible version,
    stale registration, lease expiry, tenant overload, volume reinsert, interface failover,
    credential rotation and control-plane replacement.
  - Run two tenants concurrently and prove cross-tenant resolution/state/volume/observability
    refusal plus memory, handle, IPC and CPU starvation isolation. Keep a leased endpoint open past
    revocation and prove that the selected broker/fence makes further use fail within its contract.
  - Install, update and remove one signed third-party service package with no undeclared authority;
    exercise two network interfaces with distinct tenant policies; verify operations stream
    freshness, gap detection and tenant redaction under a deliberately slow observer.
  - For any tier promising adoption, kill the control plane during in-flight client and resource
    operations and prove fencing, rebind, accounting and the declared RTO/RPO. Tiers without that
    promise must prove complete fail-closed teardown instead.
  - Compare actual authority, placement, resource and lifecycle graphs with the compiled profile and
    reject unexplained runtime edges or singleton escape paths.
  - Publish the supported compatibility matrix, server threat model, operational recovery procedure
    and measured SLO evidence for the exact release and MachineProfile.

## Definition of done

- Every deployment requirement names a versioned interface, scope and typed runtime semantics; no
  server-critical dependency relies only on a concrete process name or startup order.
- Static and dynamic providers use the same identities, scoped resolver, generation fencing,
  lifecycle events and resource/failure model.
- Compatibility negotiation and provider provenance are independently specified and tested across
  the complete supported version window.
- Human, workload, device and remote principals share one attribution/delegation model while actual
  operations remain capability-authorized. Every grant has a classified lifetime; only grants
  declared leased/revocable promise revocation, and each proves its broker, epoch fence, object
  revoke or Domain-termination mechanism.
- Tenant resource/temporal isolation, dynamic volume namespaces and multi-interface network policy
  meet the declared availability and confidentiality properties under concurrent churn.
- Any workload-survival claim has a tested recovery owner, adoption/rebind protocol and split-brain
  fence; otherwise whole-epoch teardown is the explicit behavior.
- One finite server product profile passes system conformance with no hand-wired singleton escape
  and publishes exact SLO, compatibility, threat-model and support evidence.
- At minimum, the milestone adds and passes repository gates equivalent to:

```sh
./check.sh --gate service-contracts
./check.sh --gate principal-delegation
./check.sh --gate server-profile
./verify.sh --profile server-reference
git diff --check
```

The final implementation records the concrete gate names, exact commands, release identity and
watched-failure evidence in dated sections in this file. Passing the appliance profile alone cannot
close this milestone.
