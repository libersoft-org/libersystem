# P02M0142 - Generated wiring: typed bootstrap, grants, and Domains

Status: PLANNED AFTER P02M0141. SYSTEM-ARCHITECTURE FOUNDATION. NOT A PRODUCT, RELEASE OR UPDATE
GATE.

## Goal

Generate the static wiring needed to boot the current system from `SystemSpec` and remove the
remaining service-specific tables and positional bootstrap conventions.

This milestone connects existing mechanisms. It does not replace `CapSet`, LSIDL,
PermissionManager, ResourceManager, the driver registry or the verification model.

## Version ownership rule

`v1` remains open until the project owner explicitly says otherwise. Completing this milestone
means that its current acceptance criteria and standing gates pass. It does not freeze an API, ABI,
schema, file format, machine description, product profile or release line. Breaking `v1` changes
remain allowed when all in-tree producers, consumers, generated files and tests migrate together.
Only the project owner may declare `v1` closed or start a successor version.

## Scope

The milestone owns generated projections and the invariant that the sender and receiver agree. The
underlying policies and mechanisms keep their present owners:

- P02M0079 owns the manifest generator and typed grant transport;
- P02M0098 owns driver-specific bootstrap and lifecycle;
- PermissionManager owns dynamic application grants;
- ResourceManager and kernel Domains own accounting and enforcement; and
- SystemGraphService owns the read-only graph exposed to observers.

There is no general service registry, provider selection, reconnect framework, remote authority,
multi-user policy or release/update work here.

## Work

- [ ] **M1.1 - Generate one concrete start and bootstrap-role plan.**
  - Compile the current exact service bindings and start dependencies from `SystemSpec`.
  - For each managed deployment list the named capability roles it must receive before it can
    become Ready.
  - Reuse common generated role constants on both the sender and receiver side.
  - Keep explicit bootstrap-cycle exceptions visible and mechanically checked instead of hiding
    them in service-name branches.

- [ ] **M1.2 - Finish the typed managed-service bootstrap path.**
  - Reuse the current launch context, `CapSet`, typed grant sender and Ready/failure reporting.
  - Remove remaining positional reads and private numeric tags from the standard managed-service
    path; do not invent a second universal envelope.
  - Refuse missing, duplicate, wrong-type and unexpected authority-bearing roles before Ready.
  - Close every handle not adopted by the receiver on both success and refusal paths.
  - Leave driver-specific control messages with P02M0098.

- [ ] **M1.3 - Generate the initial authority plan.**
  - Describe each boot grant by source grantor, target deployment, capability/interface class,
    rights and current scope.
  - Treat a service name as a lookup identity only; the actual capability remains the authority.
  - Generate the maximum initial holdings expected for each deployment and compare them with the
    handles actually delivered during boot.
  - Keep dynamic grants with their current specialized owners rather than building a universal
    runtime derivation graph.
  - Record the current root-Domain power grant honestly; P02M0143 replaces its over-broad consumer
    path with the narrow SystemPower proxy owned by SystemManager.

- [ ] **M1.4 - Generate Domain, resource, config and fixed-volume placement.**
  - Project supervision, failure, Domain and resource parents for every managed deployment.
  - Project references to existing resource profiles and ConfigService schemas; do not create a
    second ResourceManager or config database.
  - Project only the fixed volume roles present in the current composition by declared identity
    instead of discovery order, and refuse a missing or swapped writable role.
  - Feed desired nodes and static edges to the existing System Graph model using the identities from
    P02M0141.
  - Keep hotplug, removable namespaces and general cross-volume coordination outside this track.

- [ ] **M1.5 - Reduce central bootstrap code to a generic plan executor.**
  - Make SystemManager consume only the generated root/control-plane entry and make ServiceManager
    the sole executor of the ordinary managed-service plan.
  - Remove service-specific branches whose only job is to look up an artifact, send declared
    handles or register a desired graph node.
  - Keep true policy and exceptional bootstrap cycles explicit under their owning component rather
    than pretending every service is identical.
  - Adding a normal static service of an existing shape must require a manifest row and
    implementation, not a new central router branch.

- [ ] **M1.6 - Migrate projection by projection and enforce drift checks.**
  - Compare generated and current start, bootstrap, grant and placement data before switching each
    consumer.
  - Delete only the manual table that the accepted projection replaces.
  - Reject missing providers, unknown required roles, broader-than-declared boot grants, invalid
    Domain/resource parents and stale generated output.
  - Feed architecture relationships to P02M0118 without replacing its test-selection and evidence
    model.
  - Record the current migration result without freezing the schema or its future evolution.

## Definition of done

- The standard managed bootstrap path has no implicit capability ordering or private copy of role
  names.
- Every initial boot grant is attributable to a real source, target and `SystemSpec` declaration;
  observed boot holdings are no broader than the generated maximum.
- Every managed deployment has generated supervision, Domain/resource, config and fixed-volume
  placement consumed by the existing owners.
- A normal service of an existing shape no longer requires a service-specific branch in central
  bootstrap code.
- Existing subsystem registries and policy services remain authoritative for their own domains.
- Generated-versus-current migration leaves no second editable table for the same fact.
- Completing the milestone leaves `v1` open for continued coordinated change.

The implementation records the exact commands and results used for each M1.x item. Evidence proves
that the current development system follows its declared wiring; it is not a release certificate.
