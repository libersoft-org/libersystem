# P02M0148 - `shutdown` tears the system down and then does not stop the machine

Status: COMPLETE (2026-08-23). REPAIR. NOT A PHASE-2 COMPLETION GATE.

## Goal

Make `shutdown` stop the machine, and make it work from the shell a logout leaves behind.

Two defects on one path, reported from a live guest. Neither is subtle once the path is followed,
and both are the same shape: a capability that changed form, and a caller that was not changed with
it.

## What is there now

Measured on 2026-08-23 by reading the path end to end, from the two symptoms a user reported.

- **`shutdown` STOPS EVERY SERVICE AND THEN LEAVES THE MACHINE RUNNING.** The shell sends
  `!poweroff` on its supervisor channel; ServiceManager tears the service tree down in
  reverse-dependency order, writes `service_manager: power verb - shutting down`, and calls
  `system_power(power, action)` - which is `syscall(SYS_SYSTEM_POWER, power, ...)`. **THE KERNEL
  WANTS A DOMAIN THERE.** `sys_system_power` looks its argument up as `ObjectType::Domain` with
  `Rights::MANAGE`, and what ServiceManager holds under the name `power` is a CHANNEL - a client of
  the `system_power` service SystemManager serves, which is what that handle became when the
  root-Domain handle stopped being passed down the boot chain. The lookup fails, the syscall returns
  an error, and ServiceManager's own comment describes what then happens: "if it somehow does
  return (an unsupported machine), the loop stays alive". So the guest sits with every service
  stopped and QEMU still running, which is exactly what was reported.
- The keyboard driver's Power key does it correctly - `system_power::Client::new(...).power_off()`
  over the same kind of channel - so of the two holders of this authority, the one written second is
  the one that works. ServiceManager's call site was left on the syscall when the authority became
  a service.
- **A SHELL THAT A LOGOUT RELOADED CANNOT STOP THE MACHINE AT ALL.** `exit` on VT 1 closes the
  shell's channels; ConsoleService's `reload_vt` spawns a fresh shell on the same VT, which is
  right. But `spawn_shell` sends `STORAGE`, `LOG`, `DEVICE`, `PROCESS`, `CONFIG`, `NET`, `TIME`,
  `AUDIO`, `PERM`, `SESSION`, `CONSOLE` and `CONTROL` - and no `ADMIN`, because ConsoleService has
  no supervisor channel to send. The reloaded shell takes `CAP_ADMIN` as zero and answers
  `power: no supervisor connection; cannot stop the machine from here`.
- The first shell has one because the manifest declares its `ADMIN` role and ServiceManager makes
  that pair when it starts the shell. Nothing re-makes it, and the process that reloads the shell is
  not the process that owns the pair.
- **SECONDARY VTs ARE A DELIBERATE POLICY AND THE RELOADED PRIMARY IS NOT.** The shell's own comment
  says the no-admin answer is for "a secondary VT / a minimal boot". A VT 1 that a person logged out
  of and back into is neither: it is the primary console, with the same user in front of it, and it
  loses an authority by having been used.

## Work

- [x] **M1 - The supervisor asks the service that holds the authority.**
  - ServiceManager's `!poweroff` / `!reboot` handler calls `system_power::Client` over the channel
    it was given, the way `keys.rs` already does, instead of the syscall that needs a Domain.
  - AND IT SAYS SO WHEN THE ANSWER IS NO. The current code cannot tell "powered off" from "refused"
    because the syscall it calls never returns on success; a client call that returns IS the failure
    case, and the supervisor is the last thing running at that point - if it does not print, nothing
    else will.

- [x] **M2 - A reloaded primary shell keeps what the VT had.**
  - ConsoleService gains a supervisor channel of its own and hands the shell it spawns ON THE
    PRIMARY VT a duplicate of it, under `CAP_ADMIN`. Secondary VTs keep getting none, which is the
    existing policy and stays written down.
  - WHY CONSOLESERVICE AND NOT THE SUPERVISOR: the supervisor makes the pair when it starts a
    service, and nothing tells it a VT has been reloaded. The process that spawns the replacement is
    the one that has to carry the capability, and that is ConsoleService.
  - The supervisor already stands on two admin channels - the shell's and the one PermissionManager
    grants the sandboxed `stop` tool - so this is a third of a kind it already has, not a new
    mechanism.

- [x] **M3 - Both are shown on a booted machine.**
  - `shutdown` from the boot shell: QEMU EXITS. Not "the log says shutting down" - the process ends.
  - `exit`, then `shutdown` on the reloaded shell: the same.
  - Watched to fail first, on the tree as it stands, so the evidence is about the fix rather than
    about the two commands being typed.

## Results

Measured on 2026-08-23 against a booted x86_64 development guest, driven over the control channel.

- **WATCHED TO FAIL FIRST.** On the tree as it stood, `shutdown` printed
  `supervisor: device_manager stopped`, `supervisor: log_service stopped`,
  `service_manager: power verb - shutting down` and then the KERNEL's `halting` - and QEMU was still
  running afterwards. That last line is the tell: `boot_userspace` had returned, meaning
  SystemManager's branch had ended, and nothing had asked the kernel to stop the machine.

- **M1.** ServiceManager calls `system_power::Client::power_off()` / `reboot()` over the channel it
  holds, and reports what came back - the call returns only when the machine did not stop, and this
  process is the last one running at that point. `shutdown` now ends the guest: QEMU exits. `reboot`
  restarts it: QEMU stays and the loader banner appears a second time (one boot before, two after).

- **M2.** ConsoleService takes an `ADMIN` role of its own and hands the shell it spawns on the
  PRIMARY VT a duplicate of it; secondary VTs and PTY shells get nothing, as before. Proven the way
  it was reported: `exit`, then `shutdown` at the fresh prompt - the teardown runs and QEMU exits.

- **THE RIGHT TO HAND A SERVE ROOT ON HAD TO BE SAID OUT LOUD.** `handed_on` was refused on anything
  but a client role, on the stated grounds that "a serve root is a fresh endpoint" and so is not a
  narrowed duplicate. It is one: `serve_root` makes the pair and hands the service a duplicate
  narrowed to send, receive, wait and transfer - the same ceiling the client arm applies, and
  without `duplicate` in it ConsoleService could not pass the channel to anything. The rule now
  allows `handed_on` on a serve root, `serve_root` widens the ceiling when the role says so, and the
  comment says which two deliveries are narrowed duplicates rather than asserting that only one is.

- The supervisor stands on a third admin channel beside the shell's and the one PermissionManager
  grants the sandboxed `stop` tool. Same handler, same one-request-at-a-time shape: a shell asking
  to stop a service or the machine is the same request whichever channel it arrives on.

## Definition of done

- `shutdown` and `reboot` from the shell stop or restart the machine, and say so if refused.
- A shell reloaded onto VT 1 after `exit` can do both; a secondary VT still cannot, deliberately.
- The Power key path is unchanged - it already worked, and it is the one that must keep working when
  the supervisor does not.

## What this milestone refuses, and why

- **Giving the shell the power capability directly.** It was taken away on purpose: of the things
  that could stop the machine the shell is the least trusted, and a backstop that bypasses the
  supervisor is a second, unsupervised way to halt a running system. The shell asks; it does not
  hold.
- **Giving every VT's shell a supervisor channel.** Whether a secondary VT may stop the machine is a
  policy question this milestone does not answer; it only restores what a logout took away from the
  primary.
- **A `shutdown` that skips the teardown when the supervisor does not answer.** A machine that stops
  without flushing the journal loses the record of why it was stopped, and the Power key already
  exists for the case where the supervisor is the problem.
