# M0027 - Core services: Process, Device, Config

- [x] ProcessService: process lifecycle (create / start / exit / info) as a typed service over the kernel syscalls
- [x] DeviceService: typed device enumeration / info on top of DeviceManager
- [x] ConfigService: a typed `ConfigNode` tree with an IDL schema (no textual `/etc` parsing; text is only an editable representation)
- [x] **`ps` reports every process the system ever started, forever.** ProcessService records each
  launch in `started` and nothing ever removes an entry, so a guest that has run twenty commands
  lists twenty terminated processes and a long-lived one lists thousands. Found 2026-07-30 while
  hunting a memory leak, by running `ps` in a development instance: the output is a wall of
  finished `uname.lsexe` and `echo.lsexe`. It is also a slow leak of its own, since the list only
  grows, though a `process-info { koid, name }` is small enough that the growth is not what makes
  this worth fixing - reporting dead processes as live is. A terminated process should leave the
  list, which means noticing that it terminated: the service holds no handle to a launched process
  (`launch` transfers it to the caller), so this needs either a handle kept for the purpose or a
  koid liveness query. Note for whoever takes it: this is not the ~308 kB per command leak
  recorded against M0134d, which was what the search was actually for. The record holds no
  capability, so it cannot be keeping an image resident; the two findings are independent.
  Result (2026-07-31): the service keeps a handle, which is the first of the two routes this
  item named, and it needed no new kernel work - `SYS_PROCESS_STATS_GET` already answers
  RUNNING / STOPPED / FAILED for a Process handle, and SystemGraphService already reads a
  component's state that way. A koid liveness query would have been a second mechanism for a
  question one already answers.
  `started` holds a `Launched { info, handle }` now. `start` keeps the handle it used to close;
  `launch` and `launch_bounded` must transfer theirs to the caller for job control, so they
  record a duplicate carrying `RIGHT_READ` and nothing else - enough for `process_stats`, not
  enough to signal or otherwise act on somebody else's job. An observer should be able to see
  and not to act.
  `reap` drops every entry that is no longer RUNNING and closes its handle, and it runs on
  every launch as well as on every `list`. Reaping only on `list` would have left a guest that
  nobody runs `ps` on accumulating an entry per command exactly as before - it would merely
  have stopped lying about them at the moment somebody finally asked. Running it on both bounds
  the record by the number of live processes rather than by how long the system has been up.
  One case is deliberately kept rather than guessed at: a launch whose handle could not be
  duplicated records 0 and is never reaped. Reporting a live process as gone is this same
  defect from the other side, and a handle this service failed to duplicate says nothing about
  whether the process is running.
  The cost of the handle is one small kernel object per live-then-dead process, and no memory:
  a process's mappings go with its threads, so a zombie Process holds an object header and
  nothing else. It lasts until the next launch or the next `ps`, not until reboot.
  Validation is `process_service_drops_a_terminated_process_from_the_list`, which asserts both
  directions because either alone proves nothing: it launches (not starts - only `launch` hands
  back the live handle, so only `launch` lets the test be the thing that ends the process),
  asserts the running process IS listed, terminates it, and asserts the list is empty. Checked
  against its own negative control: with reaping disabled the test fails on the second
  assertion with 1 against 0, while the first still passes, so it fails for the reason it
  exists and not for another. 12 process-service tests green, 151 tagged tests in the suite.
- Done when: the Process / Device / Config services answer typed queries over IPC, renderable as CLI / JSON / CBOR. Together with LogService (M0022) and StorageService (M0026) this completes the phase-1 "Process, Storage, Log, Device, Config" set.
- Concept: Examples of services, System API model (Configuration row), core services list.
- Result: three more core services now speak generated `liber:system` bindings over IPC, each a standing userspace process ServiceManager brings up in the boot chain and hands the shell a client for. **DeviceService** (`interface device`) enumerates the kernel device table over the `device_count`/`device_info` syscalls and answers `list` / `get(index)` with typed `device-entry { index, type, mmio-len }` records (`type` a `device-type` enum mirroring the virtio type codes); the shell's `dev` / `dev json` render them. **ProcessService** (`interface process`) launches a named program from the init package - `start(name)` wraps `rt::spawn` (the kernel process-create/load/thread syscalls), reads the new process's koid back through `object_info` (`SYS_OBJECT_INFO_GET`, with `ObjectInfo` moved into `abi` as the SSOT next to `DeviceInfo`), and records it; `list` reports the started processes as `process-info { koid, name }`; the shell's `run <name>` / `ps` drive it. **ConfigService** (`interface config`) is an in-memory typed configuration tree, keyed by dotted paths (the tree lives in the key, so no recursive node type is needed) and seeded with a few system defaults; it answers `get(key)` / `list` / `set(entry)` with `config-entry { key, value }` records (configuration is structured data, never parsed from text); the shell's `config` / `config <key>` / `set <key> <value>` read and write it. The same generated call renders binary on the wire and CLI / JSON on the client (the `to_text` / `to_json` emitters, now also handling a handle-in-record). Each service has a kernel test driving it over the generated wire (`device_service_lists_devices`, `process_service_starts_a_program`, `config_service_serves_the_tree` - the last verifying a `set` reads back via `get`), and the boot-chain order test grew to ten reports; 60 tests green, and live boot shows `dev`, `ps`/`run`, and `config`/`set` working. With LogService (M0022) and StorageService (M0026) the phase-1 "Process, Storage, Log, Device, Config" service set is complete. Deferred: a CBOR renderer (the M0025-optional binding), ProcessService `exit`/kill (no clean per-process terminate helper yet), and persistence / a recursive `ConfigNode` variant for the config tree.
