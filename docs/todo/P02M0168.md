# P02M0168 - The kernel brings up every core the firmware lists and then two tables assume sixty-four

Status: PLANNED. KERNEL CORRECTNESS. QEMU-CLOSABLE.

Found on 2026-08-28 by reading a boot report end to end on the machine this tree is developed on,
which has 100 cores. Recorded first in P02M0158, which is where the reading was done, and refused
there: a boot-report milestone is not the place to decide a kernel's core limit.

## Goal

Make "how many cores can this kernel run on" a question with one answer, asked once, at the moment a
machine is brought up - so that a machine over the limit is refused by name instead of being
discovered one lost page at a time.

## What is there now

**A 100-core boot does not finish.** Measured twice, `./run.sh` with the host's own core count, 150 s
and 100 s. Both reach `DeviceManager: providers published after the boot devices - 4 block` and
produce nothing further except retirement warnings: 3058 pages permanently out of circulation in the
100-second run. Userspace never starts. The kernel is not wedged - it is working, and every page it
frees after a page-table teardown is one it can never use again.

**The refusal that produces this is correct where it happens.** `mem::tlb::shootdown`
([tlb.rs](../../src/kernel/mem/tlb.rs)) answers `false` when the machine has more cores than its
generation arrays track, because answering `true` would mean telling the caller that cores 64 and up
had flushed when they were never asked - and the caller's next move is to hand the frames back. That
is `KERN-ARCH-012`, and it is the last honest place in the chain. `frame::retire` then quarantines
the span, the quarantine ring fills, and the page is retired for good.

**What is missing is upstream of it.** Nothing bounds the bring-up. On x86_64 `madt_local_apics`
([smp/mod.rs](../../src/kernel/smp/mod.rs)) returns however many local APICs the firmware lists, and
`init` sizes the per-CPU and scheduler tables from that count - both are heap allocations, so they
scale to any machine. Two structures do not, and they are the ones nobody sized:

- `mem::tlb::MAX_CPUS = 64`, the width of `PENDING_GENERATION` and `ACK_GENERATION`. Over it, every
  shootdown refuses.
- `smp::ONLINE_MASK`, a `u64`. `mark_in_mask` writes nothing for a core with id 64 or above, so a
  core that reported in is not recorded as having done so.

**There are five constants named `MAX_CPUS` in this tree, holding four different values.**

| where | value | what it bounds | what happens above it |
| --- | --- | --- | --- |
| [tlb.rs](../../src/kernel/mem/tlb.rs) | 64 | TLB shootdown generation arrays | every shootdown refuses; pages retire |
| [smp/mod.rs](../../src/kernel/smp/mod.rs) `ONLINE_MASK` | 64 (a `u64`, not a constant at all) | which cores reported in | the bit is not set, and `is_online` falls back |
| [arch/aarch64/percpu.rs](../../src/kernel/arch/aarch64/percpu.rs) | 8 | the static per-CPU pool | `assert!` - a panic naming the pool |
| [arch/aarch64/psci.rs](../../src/kernel/arch/aarch64/psci.rs) | 8 | secondary stacks and slots | - |
| [fdt](../../src/fdt/src/lib.rs) | 8 | harts parsed from a device tree | - |
| [topology](../../src/topology/src/lib.rs) | 256 | the portable CPU table | - |

Three ports, three different answers, and on x86_64 no answer at all until a page is already lost.

**Two comments state bounds that do not exist.**

- `// ALLOC-OK: CPU bring-up at boot; bounded by MAX_CPUS` in `smp::init` - the vector it annotates
  is bounded by what the MADT lists and by nothing else.
- `is_online` above id 64 says "this tree's `MAX_CPUS` is larger than 64, so a mask this narrow would
  quietly report the cores above it as offline". The `MAX_CPUS` it must mean is exactly 64. The
  fallback it justifies answers `cpu < online_count()`, which is a different question: it says an id
  is in range, not that the core behind it reported in - and the mask exists precisely because
  "how many" and "which ones" are not the same fact.

## Work

- [ ] **M1 - One supported core count, and the bring-up refuses above it.** One constant answers
  "how many cores can this kernel run on", and every structure that sizes itself per core is sized
  from it or checked against it. A machine with more is refused where the count is established -
  before any per-CPU table is filled and before the first shootdown - by a line that names the
  machine's count, the supported count and what was done about it. Which of "refuse to boot" and
  "run on the first N and say so" is right is M1's to settle, and it is settled once for all three
  ports rather than per structure.

- [ ] **M2 - `is_online` answers the question it is named for.** Either the mask is as wide as the
  supported count, or the fallback stops standing in for it. `cpu < online_count()` is true for
  every id below the tally whether or not that core ever answered, which is the stand-in the mask
  was introduced to remove - and its one reader is the NUMA binding pass, which skipped a boot hart
  for exactly this class of reason.

- [ ] **M3 - No supported boot reaches the shootdown refusal.** The refusal stays; it is the safe
  answer and the reason this defect lost memory instead of corrupting it. What changes is that
  M1 makes it unreachable on a machine this kernel accepted, so a boot that retires a page for
  this reason is a bug in M1 rather than a machine being large.

- [ ] **M4 - The two comments say something true.** Both quoted above. A comment asserting a bound
  that does not exist is worse than no comment: it is the reason nobody looked.

- [ ] **M5 - A machine over the bound is run, not reasoned about.** `./run.sh --smp N` above the
  supported count reproduces this in one command on x86_64. A check boots it and asserts the named
  refusal from M1 and that no page was retired - the two halves of "the kernel knew, and it knew
  before it cost anything".

## Dependency order

M1 first: M2, M3 and M5 all describe consequences of the count existing. M4 is independent and
costs nothing. M5 last, because it asserts what M1 decided.

## Definition of done

- One constant answers how many cores this kernel supports, and every per-core structure is sized
  from it or checked against it.
- A machine that exceeds it is refused at bring-up, by a line naming both counts, before any
  per-CPU table is filled.
- No boot retires a page because a shootdown could not reach a core.
- `is_online` answers whether a core reported in, at every id below the supported count.
- A run above the bound exists, asserts the refusal, and asserts that nothing was retired.

## What this milestone refuses, and why

- **Raising the number as the fix.** 64 to 256 moves the cliff and leaves everything else true: the
  bring-up still has no bound, the mask is still a different width from the arrays, and the machine
  that exceeds the new number still finds out one page at a time. The defect is that the question is
  never asked, not that the answer is small.

- **Making the shootdown arrays a heap allocation to avoid having a constant.** They are read on the
  shootdown path from every core, and the ALLOC-OK rules in this tree exist because boot-time and
  hot-path allocation is what turns a recoverable condition into an unrecoverable one - which is the
  shape this milestone is already about.

- **Truncating the shootdown to the cores it can reach.** That is the change `KERN-ARCH-012` was
  written against: it answers "flushed" for cores that were never asked, and the caller frees the
  frames. Losing memory is the safe failure and it stays the failure until M1 stops it happening.

- **Fixing the log.** The 3236 identical lines this was found under are P02M0158's, and they are
  already fixed there. A shorter log for a machine giving its memory away would have hidden this
  rather than surfaced it.
