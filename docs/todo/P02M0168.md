# P02M0168 - The kernel brings up every core the firmware lists and then two tables assume sixty-four

Status: COMPLETE (2026-08-28). KERNEL CORRECTNESS. QEMU-CLOSABLE.

Found on 2026-08-28 by reading a boot report end to end on the machine this tree is developed on,
which has 100 cores. Recorded first in P02M0158, which is where the reading was done, and refused
there: a boot-report milestone is not the place to decide a kernel's core limit.

## Goal

Make "how many cores can this kernel run on" a question with one answer, asked once, at the moment a
machine is brought up - so that a machine over the limit is refused by name instead of being
discovered one lost page at a time.

## What is there now

**A 100-core boot does not finish.** Measured twice, `./run.sh` with the host's own core count, 150 s
and 100 s. Both reach `DeviceManager: providers published after the boot devices - 4 block` and
produce nothing further except retirement warnings: 3058 pages permanently out of circulation in the
100-second run. Userspace never starts. The kernel is not wedged - it is working, and every page it
frees after a page-table teardown is one it can never use again.

**The refusal that produces this is correct where it happens.** `mem::tlb::shootdown`
([tlb.rs](../../src/kernel/mem/tlb.rs)) answers `false` when the machine has more cores than its
generation arrays track, because answering `true` would mean telling the caller that cores 64 and up
had flushed when they were never asked - and the caller's next move is to hand the frames back. That
is `KERN-ARCH-012`, and it is the last honest place in the chain. `frame::retire` then quarantines
the span, the quarantine ring fills, and the page is retired for good.

**What is missing is upstream of it.** Nothing bounds the bring-up. On x86_64 `madt_local_apics`
([smp/mod.rs](../../src/kernel/smp/mod.rs)) returns however many local APICs the firmware lists, and
`init` sizes the per-CPU and scheduler tables from that count - both are heap allocations, so they
scale to any machine. Two structures do not, and they are the ones nobody sized:

- `mem::tlb::MAX_CPUS = 64`, the width of `PENDING_GENERATION` and `ACK_GENERATION`. Over it, every
  shootdown refuses.
- `smp::ONLINE_MASK`, a `u64`. `mark_in_mask` writes nothing for a core with id 64 or above, so a
  core that reported in is not recorded as having done so.

**AND THE POLICY IS ALREADY DECIDED - IT IS WRITTEN DOWN, AND TWO PORTS OF THREE IMPLEMENT IT.** This
is the finding that makes the milestone small, and it was missed when this file was written. The
answer to "refuse the machine or run on the first N" is in [fdt](../../src/fdt/src/lib.rs), beside
the constant it justifies: *"Eight, because that is the aarch64 per-CPU pool - the smallest backend
limit in the tree, and the one a larger table would only postpone hitting. A machine with more cores
than this boots on the first eight and SAYS so; refusing the tree the way an over-long `/memory` does
would turn a sixteen-core machine into no machine at all, which is the worse of the two answers
here."* And the ports do it: aarch64 and riscv64 both park the excess and print
`SMP - N declared core(s) past the M this kernel holds stay parked`, sized from `topology.slots()`.

x86_64 does none of it. `madt_local_apics` returns however many the firmware lists, `total` is that
length, nothing is parked and nothing is said - so the one port with no static per-CPU pool is the
one port that consults no limit at all.

So M1 is not a design question. It is: apply the rule this tree already wrote, on the third port, and
name the number in one place.

**AND ONE MORE THING FALLS OUT OF THE SAME GAP.** The AP wake loop skips the entry equal to
`bsp_lapic_id` and counts `online` up from 1. If the boot processor is NOT in the MADT list, nothing
is skipped, every entry is woken, and `online` reaches `total + 1` - one more than
`percpu::allocate(total)` reserved. x86_64's `this_cpu` indexes that allocation through a raw
pointer with no bound, so the extra core writes past it. Nothing observed this; it is the same
missing check, reached from the other side, and it belongs to the same item.

**The five constants named `MAX_CPUS` are not four answers to one question**, and reading them that
way is what makes the gap look larger than it is. Three are BACKEND CAPACITIES, one is a TABLE
BOUND, and the sixth bound is not a constant at all.

| where | value | what it bounds | what happens above it |
| --- | --- | --- | --- |
| [tlb.rs](../../src/kernel/mem/tlb.rs) | 64 | TLB shootdown generation arrays | every shootdown refuses; pages retire |
| [smp/mod.rs](../../src/kernel/smp/mod.rs) `ONLINE_MASK` | 64 (a `u64`, not a constant at all) | which cores reported in | the bit is not set, and `is_online` falls back |
| [arch/aarch64/percpu.rs](../../src/kernel/arch/aarch64/percpu.rs) | 8 | the static per-CPU pool | `assert!` - a panic naming the pool |
| [arch/aarch64/psci.rs](../../src/kernel/arch/aarch64/psci.rs) | 8 | secondary stacks and slots | - |
| [fdt](../../src/fdt/src/lib.rs) | 8 | harts parsed from a device tree | - |
| [topology](../../src/topology/src/lib.rs) | 256 | the portable CPU table | - |

Three ports, three different answers, and on x86_64 no answer at all until a page is already lost.

**Two comments state bounds that do not exist.**

- `// ALLOC-OK: CPU bring-up at boot; bounded by MAX_CPUS` in `smp::init` - the vector it annotates
  is bounded by what the MADT lists and by nothing else.
- `is_online` above id 64 says "this tree's `MAX_CPUS` is larger than 64, so a mask this narrow would
  quietly report the cores above it as offline". The `MAX_CPUS` it must mean is exactly 64. The
  fallback it justifies answers `cpu < online_count()`, which is a different question: it says an id
  is in range, not that the core behind it reported in - and the mask exists precisely because
  "how many" and "which ones" are not the same fact.

## Work

- [x] **M1 - x86_64 caps its bring-up the way the other two ports already do.** The rule and the
  wording exist; what is missing is the third port applying them. `smp::init` takes the machine's
  count from the MADT, caps it at the supported count, parks the rest and says so in the same shape
  the other two use. The boot processor keeps its place whatever the table's order was - it is the
  core running the code - and `online` never exceeds the slots `percpu::allocate` reserved, which is
  the second half of the same check.

  AND THE SUPPORTED COUNT IS NAMED ONCE, in `smp`, because that is the module that brings cores up.
  `mem::tlb` sizes its generation arrays from it instead of declaring its own, and the online mask's
  width is asserted against it at compile time rather than agreeing with it by coincidence. The
  per-port backend capacities stay what they are - aarch64's static pool is 8 for a reason the
  linker can see - and the supported count on a port is the smallest limit that applies to it, which
  is the rule `fdt` already states.

- [x] **M2 - `is_online` answers the question it is named for, by not needing a fallback.** Once M1
  holds, no core id can reach the mask's width, so the `cpu >= 64` branch is unreachable and goes -
  and the comment justifying it goes with it, which is the one that says `MAX_CPUS` is larger than
  64 when it is exactly 64. `cpu < online_count()` is true for every id below the tally whether or
  not that core ever answered, which is the stand-in the mask was introduced to remove; its one
  reader is the NUMA binding pass, which skipped a boot hart for exactly this class of reason.

- [x] **M3 - No supported boot reaches the shootdown refusal.** The refusal stays; it is the safe
  answer and the reason this defect lost memory instead of corrupting it. What changes is that
  M1 makes it unreachable on a machine this kernel accepted, so a boot that retires a page for
  this reason is a bug in M1 rather than a machine being large.

- [x] **M4 - The two comments say something true.** Both quoted above. A comment asserting a bound
  that does not exist is worse than no comment: it is the reason nobody looked.

- [x] **M5 - A machine over the bound is run, not reasoned about.** `./run.sh --smp N` above the
  supported count reproduces this in one command on x86_64. A check boots it and asserts the named
  refusal from M1 and that no page was retired - the two halves of "the kernel knew, and it knew
  before it cost anything".

## Dependency order

M1 first: M2, M3 and M5 all describe consequences of the count existing. M4 is independent and
costs nothing. M5 last, because it asserts what M1 decided.

## Definition of done

- One constant answers how many cores this kernel supports, and every per-core structure is sized
  from it or checked against it.
- A machine that exceeds it is refused at bring-up, by a line naming both counts, before any
  per-CPU table is filled.
- No boot retires a page because a shootdown could not reach a core.
- `is_online` answers whether a core reported in, at every id below the supported count.
- A run above the bound exists, asserts the refusal, and asserts that nothing was retired.

## What this milestone refuses, and why

- **Raising the number as the fix.** 64 to 256 moves the cliff and leaves everything else true: the
  bring-up still has no bound, the mask is still a different width from the arrays, and the machine
  that exceeds the new number still finds out one page at a time. The defect is that the question is
  never asked, not that the answer is small.

- **Making the shootdown arrays a heap allocation to avoid having a constant.** They are read on the
  shootdown path from every core, and the ALLOC-OK rules in this tree exist because boot-time and
  hot-path allocation is what turns a recoverable condition into an unrecoverable one - which is the
  shape this milestone is already about.

- **Truncating the shootdown to the cores it can reach.** That is the change `KERN-ARCH-012` was
  written against: it answers "flushed" for cores that were never asked, and the caller frees the
  frames. Losing memory is the safe failure and it stays the failure until M1 stops it happening.

- **Fixing the log.** The 3236 identical lines this was found under are P02M0158's, and they are
  already fixed there. A shorter log for a machine giving its memory away would have hidden this
  rather than surfaced it.

## Results

The same 100-core host the defect was found on, booted from `.build/boot/libersystem.iso`. Before,
the boot stopped after `providers published after the boot devices` and did nothing but retire pages
- 3058 of them in 100 seconds, userspace never started. After:

```
memory: buddy allocator up - 1035435 free frames, 383 KiB of metadata
smp: 36 declared core(s) past the 64 this kernel holds stay parked
smp: 64 of 64 cores online
memory: 1033847 frames free after early boot (1588 taken since the allocator came up)
memory: 0 page(s) retired for good, 0 page(s) lost in all, 0 free(s) refused
...
network: configured via DHCP - 10.0.2.15/24 via 10.0.2.2
vol://system>
```

Sixty-six lines to a prompt, where the same machine produced 6509 and no prompt. No `tlb:` line and
no `frame: WARNING` anywhere in it: the shootdown never refused, because there is no longer a core it
cannot reach.

**M1 was smaller than this milestone thought, and that is the finding worth keeping.** The policy was
already decided and written down - `fdt::MAX_CPUS` argues it beside the constant it justifies, and
aarch64 and riscv64 have parked their excess cores and said so all along. Only x86_64, the one port
whose per-CPU tables are heap allocations and therefore have no limit of their own, consulted no
limit at all. So the work was to apply an existing rule on the third port, not to invent one.

**M2 needed no fallback once M1 held.** `is_online` answered `cpu < online_count()` above id 64 -
which says an id is inside the tally, not that the core behind it reported in - under a comment
claiming this tree's `MAX_CPUS` was larger than sixty-four when it was exactly sixty-four. With the
cap, no id can reach the mask's width, so the branch is a bound check that answers `false` and the
comment is gone. A compile-time assertion now ties the supported count to the mask's width, because
the two agreeing by coincidence is how the fallback came to exist.

**And one defect was found while fixing this one.** The AP wake loop skips the entry equal to
`bsp_lapic_id` and counts `online` from 1, so a MADT that does not list the boot processor leaves
nothing skipped and the last core takes id `total` - one past what `percpu::allocate` reserved, which
`this_cpu` reaches through a raw pointer with no bound. Nothing had observed it; it is the same
missing check from the other side and it is closed with the same item.

The number is now named once, in `smp`, where cores are brought up. `mem::tlb` and the frame
allocator's injector read it from there instead of the shootdown arrays declaring it for everyone -
which was the arrangement that let the module deciding how many cores to start never look at it.
