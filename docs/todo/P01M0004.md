# P01M0004 - ServiceManager and the boot chain

Status: COMPLETE.

SystemManager starts ServiceManager, which brings up the core services in dependency order, and the
CLI becomes an ordinary userspace component at the end of the chain rather than kernel-embedded code.

*Condensed 2026-08-08.*

ServiceManager tracks each service's state and holds its report channel as a control channel, so the
stop path is the same channel the start report came on. It announces itself online only once every
service has reached a healthy end state - a real consumer of the state table rather than a table
nobody reads.

**The stop is demonstrated on a leaf during boot, deliberately.** Every standing service at this
point is load-bearing, so stopping storage, logging or the shell would disrupt the running system;
`device_manager` is the one thing nothing depends on. A client-driven `stop <service>` and
reverse-dependency teardown belong with the later restart policy.

## The recovery ladder, and the one sanctioned exception

`supervise` spawns SystemManager, runs to a quiescent point, and drains a crash-notify channel
matching the record the fault path emits on a ring-3 fault. A round that completes without
SystemManager faulting means the system is up. If the original attempt and three restarts all fault,
the kernel escalates to a reset.

**This is the kernel's one deliberate rescue mechanism - the single sanctioned exception to "the
kernel is pure mechanism".** Naming it as an exception is what stops it becoming a precedent.

Both directions are tested: a stand-in that page-faults on every attempt exhausts the ladder and
reports escalation, and one that returns cleanly survives the first attempt with no recovery spawn.
