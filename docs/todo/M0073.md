# M0073 - LiberFS: correctness bugs and data-loss holes

Status: COMPLETE. The findings that can lose or corrupt data. Each fix is small; together they make
the copy-on-write guarantees actually hold end to end.

*Condensed 2026-08-08.*

**There was no flush or write barrier anywhere** - the most serious finding, because the whole CoW
crash-consistency argument rests on ordering that nothing enforced. `BlockDevice::flush` exists now
(a no-op default for cache-less backings), `commit` brackets the superblock write with two barriers,
and `format` flushes.

- **A corrupt snapshot table silently destroyed every named snapshot.** A CRC mismatch is `Corrupt`
  now and the mount degrades to read-only, so no commit can overwrite what is still readable.
- **`compress_extent` baked in silent corruption**: it read source blocks without verifying them, so
  damage was compressed into the new extent and the evidence lost. Every source block is verified
  against its CRC first; a mismatch leaves the run raw, where the read path and `fsck` still surface
  the damage.
- **Snapshot mounts were not enforced read-only.** A `read_only` flag is set by both snapshot mounts
  and by the degraded path, and every public mutation runs through one gate.
- **mtime and ctime were always zero in production** - only the tests called `set_clock`.
  StorageService stamps the RTC's Unix seconds now; the NTP-disciplined policy clock stays in
  TimeService, which is the right split.
