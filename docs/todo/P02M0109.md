# P02M0109 - LiberMemFS: a writable filesystem that lives in memory

Status: COMPLETE, after six rounds of outside review of the filesystem and the storage-service paths
around it.

Every volume this system could mount was backed by a medium. There was nowhere to write that does not
survive a reboot and does not cost a disk write - no `/tmp`, and no place for state a service needs
only while it is running. `LiberMemFS` is that place: files held directly on the heap, no block
layer, no on-disk format, rebuilt empty on every boot.

*Condensed 2026-08-08. The six review rounds are merged by theme rather than replayed in order, and
each finding is stated once instead of once as a complaint and again as a resolution.*

## Why not LiberFS on a RAM block device

The cheap answer was to implement `BlockDevice` over a memory buffer and format LiberFS onto it -
about fifty lines, everything already working. That was the recommendation until the code was
measured on 2026-08-02, and the measurement changed the answer:

| LiberFS module | lines | needed in RAM? |
| --- | --- | --- |
| `blkalloc` | 970 | no - the heap allocates |
| `txn` | 810 | no - there is no crash to recover from |
| `lib` | 796 | mostly no - superblock, on-disk structures, checksums |
| `dir` | 543 | the idea, but a map rather than a B+tree |
| `fsops` | 511 | the idea, simpler |
| `snapshot` | 329 | no |
| `fsck` | 220 | no - it is rebuilt every boot |
| `inode` | 167 | the idea, simpler |

Reusing LiberFS in RAM means carrying a block allocator, a transaction log and a checker that protect
against a medium that is not there, to reach data the CPU can already address. The "free, already
tested" argument is thinner than it looks: much of that test suite covers durability, which is not a
property RAM has.

The other difference is what a fixed size means. **A RAM disk reserves its whole size whether or not
anything is in it; a memory filesystem holds only what is stored, and a limit is a CAP rather than a
reservation.** That distinction is what the rest of the milestone is built on.

## One filesystem, two allocation policies

`vol://ram` and `vol://tmp` are not two implementations. Files, directories, path resolution and
every trait method are identical; only the moment their memory is charged differs, and the system
already had the mechanism in per-Domain accounting.

| | `vol://ram` - reserved | `vol://tmp` - capped |
| --- | --- | --- |
| charged | at mount | at write |
| guarantees | the space is there | the space may be there |
| when memory is short | the MOUNT fails | the WRITE fails |
| unused space | held | not taken in the first place |
| suits | state that must not fail because something else took the memory | scratch, where waste is worse than an occasional refusal |

Two implementations would duplicate directories, paths, reads and writes to express one condition.
The policy belongs at mount time and the accounting belongs to the Domain that owns the volume.

## What six rounds of review found, by theme

Every round was verified claim by claim against the code, and essentially all of it held. The
findings cluster into six kinds, and the kinds are more useful than the list.

### Allocations that abort instead of refusing

The whole point of a memory filesystem is to behave under memory pressure, and most allocation sites
did not. `try_reserve_exact` guarded some paths while the ones around them called infallible `Vec`
operations that abort the process: the outer `Vec` of chunks, `read_buffer` copying the whole input
before the filesystem is ever called, `MemFs::list_entries` undoing the backend's care,
`write_stream` accumulating without bound, `recv_vec_blocking` doing `vec![0u8; pending]` with no
cap, and `rt`'s own allocator exiting rather than returning null.

A guarded allocation next to an unguarded one guarantees nothing - the process dies at the second.

### The reservation, five times

More rounds were spent on what `Reserved` promises than on anything else, which is itself the
finding: an accounting rule that is nearly right reads as right.

- Charge `Vec::capacity()`, not `Vec::len()` - the difference is memory that is held and unreported.
- A shrink has to decide what happens to the freed capacity; reporting it as free while the file
  still holds it is a lie the next writer pays for.
- Rewriting a file needs room for **both copies at once**, and the capacity check subtracted the old
  one first.
- A failed regrow released the old reservation and then failed to take the new one, leaving the
  volume **worse than before it ran**.
- A late refusal resynced while the new file was still allocated.
- `stream_push` reserved the wrong amount, so growth could allocate infallibly - the guard and the
  thing it guards computed different numbers.

### Errors collapsed into other errors

- `copy_tree` discarded every error and reported success.
- `Volume::list` turned an error into an empty listing - indistinguishable from an empty directory.
- Destination validation collapsed every failure into `NotFound`.
- An out-of-memory during a streamed write was reported as end-of-file, with the partial file left
  behind.
- `lookup` could not tell "not found" from "a file used as a directory".
- An unexpected `channel_peek` error was treated as "try again later", forever.
- An abandoned listing looked like a completed one.

The shape is always the same: a failure that cannot be expressed in the return type becomes the
nearest value that can, and the caller acts on it.

### One client could stop the service

`send_blocking` on a reply path means a client that stops reading stops everyone. Four reply paths
still had it after the first fix, the admin reply was unbounded, the client table had no ceiling and
allocated infallibly, a stream handle without WAIT could spin the serve loop, and `try_send` could
not distinguish a full queue from a closed peer. A pending write outlived the client that asked for
it.

`MAX_CLIENTS` is 64, and the number was measured rather than chosen.

### Two implementations of one protocol

The serve loop used the pending model while another path did not, so the same request took different
routes depending on how it arrived. That is the defect that produces the others: every rule then has
to be enforced twice, and one copy always drifts.

### Documents that stopped being true

The generated ABI no longer matched the IDL; the crate documentation still described the reservation
as "one contiguous allocation"; three claims in `docs/LIBERMEMFS.md` were false; the listing's
terminal frame was a runtime convention the schema did not mention; and a written statement that "no
unbounded send to a client remains in the service" was untrue at the moment it was written.

A document that describes an invariant the code stopped holding is worse than no document, because
it is read as evidence.

## Two things worth keeping about the process

**A test that shares its accounting with the implementation tests nothing.** The property test
asserted the implementation's own arithmetic back at it.

**A regression test that passes after its own fix is reverted must be rewritten, not kept.** That
habit is what caught several of the items above, and one outside reviewer singled it out.
