# P02M0130 - What the component SDK is, and what its milestone says it is

Status: PLANNED. An outside audit of `src/sdk` and everything its correctness depends on - the
build, the packaging, `component_host`, the Wasm runtime and the end-to-end test - 2026-08-10. Every
claim checked against the tree held.

The SDK itself is about a hundred lines and they are good ones. The capability model is the right
shape: the guest never names a path, a channel or a service, it sees three imports, and the host
holds the authority. Bounds checking is the host's job and the host does it. The artifact is built
by an ordinary Rust toolchain and runs on this project's own interpreter, which is worth far more
than a hand-assembled test blob. Packaging declares it in the manifest rather than dropping a file
into the volume.

Two findings are larger than the code they are about.

**The end-to-end test cannot fail the way it claims to test.** The host copies the guest's bytes
BEFORE writing them, reports the copy, and the test compares against the copy - so a `write_file`
that does nothing still passes.

**The milestone above it claims something that is not in the tree.** P02M0012 is `Full Component Model
+ WASI preview 2 + an SDK`, COMPLETE, and says "An SDK builds a component against the WIT worlds for
Rust, C and Go." There is no `.wit` file anywhere in this repository, no wit-bindgen, no canonical
ABI and no component encoding; the parser checks the core-Wasm magic and version 1, the SDK declares
`#[link(wasm_import_module = "liber")]` core imports, and the one language is Rust.

(The third finding of that size - the SDK being outside the system volume's freshness model, so an
edit to it cannot invalidate a built volume - belongs to the verification model and is written up in
P02M0118.)

## The test that cannot fail

- [x] **The E2E test proves the read, the transform and the log, and not the write.** In
  `component_host`, `WorldFn::Write` does `self.output = memory[ptr..end].to_vec()` and only then
  calls `write_file`. The report sent back to the test is `host.output` - the copy taken before the
  write - and `run_component_scenario` unpacks it as `bytes[5..]`. The test asserts
  `content == expected` and its comment says this proves the filesystem write.

  FIXED 2026-08-11: the host reads the output file BACK through StorageService after the run and
  reports those bytes, and the test asserts them against the expected content as well as against the
  copy taken on the way into the write. The host does the reading rather than the test because the
  host is the one holding the storage grant - the bytes still travel through the service, which is
  the point.

  While changing the report, a second defect fell out of it: `content` was parsed as `bytes[5..]`
  after `score_negative` had been appended to the report earlier the same day, so the content the
  assertion compared began with four bytes of score. The report is now a struct
  (`ComponentRun`) rather than a positional tuple, which is what let that happen.

  It does not. `write_file` could return zero, StorageService could refuse, the output grant could
  be read-only, the IPC could fail - and the assertion still passes, because the bytes it compares
  never went near the filesystem. The test must open `components/liber_component/out.txt` through
  StorageService after the run and compare what is actually there.

- [x] **`run`'s return value is read and discarded.** `let _count: i32 = match instance.invoke("run",
  ..)` - the count is never sent, so nothing checks the export's return ABI. The guest is no better:
  it calls `world::write_output(&buf[..n])` and throws the result away, so a failed write is
  invisible on both sides of the boundary. Report the count, assert it equals the expected length,
  and make the guest react to a short write.

  FIXED 2026-08-11: the host reports the count and the test requires it to equal the expected
  length, so the export's return ABI is checked. The guest reacts too - it reads every world call's
  answer and returns a negative status for a failed read, a failed log, or a short write, where it
  used to throw all three away.

- [ ] **Add the negative cases, which is where the interesting behaviour is.** A read-only output
  grant; a write that fails; a LogService that is not answering; a host returning a count larger
  than the buffer; an unknown import; an import with the wrong signature; an out-of-range `(ptr,
  len)`; a pointer with the high bit set; an empty input; an input of exactly 256 bytes; an input
  larger than 256; a guest panic reaching the host as a trap.

  PARTLY 2026-08-11, and the rest is blocked on a harness rather than on the cases.

  Three are now closed by construction and asserted somewhere: an unknown import and an import with
  the wrong signature refuse the component at instantiation (`resolve` returns `Option`), and the
  staged artifact is checked against exactly that world at BUILD time by `validate_component`. An
  out-of-range `(ptr, len)` - including a pointer with the high bit set, which the unsigned
  conversion now reaches - answers `Fault` instead of a silently clamped window.

  The rest need a host that can be driven with hostile inputs, and `component_host` is a userspace
  binary: nothing in it can be exercised from a host test, and the kernel suite can only run the one
  real component end to end. The shape that unblocks it is the crate split below - the world's host
  side as a library the guest-independent cases can be run against - so this waits on that rather
  than on somebody writing twelve more assertions.

## The claim in P02M0012

- [x] **Decide which of the two things this is, and name it that.** There are two honest positions
  and the milestone currently states neither.

  DECIDED 2026-08-11: it is a Liber component ABI and a Liber Rust SDK. `docs/todo/P02M0012.md` is
  renamed and rewritten to say so, the entry in `TODO.md` follows, and WASI Preview 2 is named there
  as its own future milestone with its outstanding work listed rather than implied to exist. The
  history is kept in the file, because the failure mode - a condensation that dropped "usable
  subset, Rust done, C and Go remaining" - is the part worth remembering.

  If the current design is the intent - a small capability-oriented Wasm ABI over this project's own
  interpreter - then it is a good design and it should be called what it is: a Liber component ABI
  and a Liber Rust SDK. Nothing is wrong with the architecture; the word "Full Component Model" is
  what is wrong.

  If WASI Preview 2 is genuinely wanted, then WIT definitions, versioned worlds, the canonical ABI,
  component encoding, generated bindings, resources and handles, the standard WASI interfaces and
  the other two languages are all outstanding, and P02M0012 is not COMPLETE.

  The audit notes that the commit which created P02M0012 was more careful - it said a usable subset,
  Rust done, C and Go remaining - and that the later condensation of the milestone turned the subset
  into the full thing. That is the failure mode P02M0118's last task is about, in a different file.

## The world ABI

- [x] **The world is unversioned.** Its whole identity is the strings `liber.read`, `liber.write`
  and `liber.log`. The day the read signature changes, old and new modules both import
  `liber.read` and nothing can tell them apart. Namespace and version it - `liber:vfs@1`,
  `liber:log@1`, or whatever this project's own convention becomes - before anything outside this
  repository builds against it. (Versioning the ABI is not the same question as releasing the
  system: this is a compatibility boundary, and it needs an identity from its first external user,
  not from the first release.)

  FIXED 2026-08-11: `liber:vfs@1` (read, write) and `liber:log@1` (log), on both sides. The world's
  whole identity was three unversioned strings, so the day a signature changed an old module and a
  new one would both import `liber.read` with nothing to tell them apart. Done together with the
  error model below, because they are one ABI break and doing them apart would have been two.

  Not moved: `wasi_host.rs`, an older standalone demo host carrying a hand-encoded module that
  imports the unversioned `liber.read`. It is a second implementation of the same idea and it should
  either move with the world or be retired; both are more than a rename of a byte array with LEB
  lengths in it.

- [x] **Imports are matched by name and never by signature.** `resolve` is a match on
  `(module, field)`; the parser knows each import's `type_index` and the module can produce its
  `FuncType`, and none of that is consulted. It matters more than it would elsewhere because
  `Value::as_i32` converts `I64`, `F32` and `F64` as well as `I32` - so a module declaring
  `liber.read` with the wrong type does not get "incompatible import", it gets silent conversion at
  call time. Check the exact signature at instantiation.

  FIXED 2026-08-11. `resolve` takes the import's `FuncType` from the module's type section and
  requires an exact match on parameters and results. It matters more here than it would elsewhere
  because `Value::as_i32` converts `I64`, `F32` and `F64` as well as `I32` - so a module declaring
  `liber.read` with the wrong type used to get a silent conversion at call time, on the boundary
  whose whole job is to be where the guest's word is not taken for anything.

- [x] **An unknown import is accepted and only traps if it is called.** `_ => WorldFn::Unknown`, and
  the trap happens at the call site. For a capability system the import list IS the manifest of
  requested authority: a module asking for `liber.camera` should be refused when it is instantiated,
  not tolerated on the grounds that the call site might be unreachable.

  FIXED 2026-08-11. `resolve` returns `Option`, and an import the world does not offer - by name or
  by type - refuses the component at instantiation. `WorldFn::Unknown` is gone. The import list is
  the manifest of requested authority, and "the call site might be unreachable" is not an answer to
  a module asking for a camera.

- [x] **Pointers and lengths are signed.** The guest passes `ptr as i32` and the host reads
  `v.as_i32() as usize`. A wasm32 address is a 32-bit pattern, and `0x9000_0000` is a valid one that
  becomes negative as an `i32` and then an enormous `usize`, which the host refuses. The current
  module's memory is small so it cannot happen today; the ABI is nonetheless capped at the low
  2 GiB. Read them as `as_i32() as u32 as usize`, and state `u32` in the ABI.

  FIXED 2026-08-11: `as_i32() as u32 as usize`. A wasm32 address is a 32-bit pattern, and reading it
  as signed sign-extended anything at or above 0x8000_0000 into an enormous `usize` that the bound
  then refused - so the ABI was silently capped at the low 2 GiB. Today's module has a small memory
  and cannot reach it; the conversion was still the wrong one.

- [x] **The error model cannot express the difference between "empty" and "refused".**
  `read_input` turns any negative into `0`, so an error and a legitimate end of input are the same
  answer; `write_output` returns a count where `0` means failed, read-only, and a genuine zero-byte
  write; `log` returns nothing at all. In a capability system "I am not allowed to write" is
  precisely the thing a component most needs to distinguish from "the write was empty". A status
  plus a count, with defined codes.

  FIXED 2026-08-11: an `i32` where a negative value is a status and a non-negative one is a count.
  `STATUS_DENIED` (-1), `STATUS_FAULT` (-2), `STATUS_IO` (-3), `STATUS_UNSUPPORTED` (-4), defined on
  both sides, with the guest wrappers returning `Result<usize, Error>` and an `Error::Unknown(i32)`
  so a newer host's code is reported rather than invented.

  `log` returns a status too - it returned nothing at all, so a component could not tell whether its
  one diagnostic channel had worked. A read-only output is `Denied` rather than `Ok(0)`, which is the
  distinction the whole finding is about, and `write_file` in the host returns `Option<usize>` to
  carry it. A `(ptr, len)` outside the guest's memory is `Fault` rather than a silently clamped
  window - it used to `.min(mem_len)`, so a component near the top of its memory wrote fewer bytes
  than it asked to and got a count it could not distinguish from a short file.

- [x] **`write_output` trusts whatever the host returns.** `read_input` defends itself with
  `(n as usize).min(buf.len())`; `write_output` is `if n < 0 { 0 } else { n as usize }`. A host
  regression returning a million for a hundred-byte write hands a million straight to the
  application through a wrapper whose job is to be the safe side of that boundary. Clamp, or trap.

  FIXED 2026-08-11: clamped to `buf.len()`, like `read_input` beside it. The host cannot have
  written more than it was given, and a wrapper whose job is to be the safe side of that boundary
  should not need the host to be right about it.

- [x] **`log_message` says bytes and the host means text.** The signature is `&[u8]`; the host does
  `String::from_utf8_lossy`. Either the API takes `&str`, or the host stops transforming what it was
  handed. Silently substituting replacement characters is the wrong answer to either contract.

  FIXED 2026-08-11 by making both sides say text. `log_message` takes `&str`; the host refuses a
  `log` whose bytes are not UTF-8 rather than substituting replacement characters where nobody can
  see them. The demo component decides for itself - it upper-cases ASCII, so what came in as text is
  still text, and it checks rather than assuming.

## The build contract

- [x] **`rust-toolchain.toml` says `channel = "stable"` and its comment says this keeps the build
  reproducible.** It does not: `stable` is whatever `rustup` last fetched. For most crates that is a
  reproducibility annoyance. Here the guest runs on this project's own interpreter, so a new stable
  can legitimately emit instruction selections, memory layouts, data segments or float conversions
  that the interpreter does not implement - and the component that worked yesterday stops working
  with no change of ours. Pin the exact tested release.

  FIXED 2026-08-11: pinned to `1.93.1`, the release everything here was built and verified with, with
  the reason in the file - the guest runs on this project's own interpreter, so a new stable can
  legitimately emit something the interpreter does not implement and the component that worked
  yesterday stops working with no change of ours. The wasm32 target was installed for that toolchain
  as part of the change, so the pin does not cost a download at the next build.

- [x] **Validate the built artifact against our own parser, in the build.** The pin above reduces
  the risk; a check removes it. After `just sdk`, run the produced `.wasm` through `wasm::parse` and
  fail the build on anything it cannot represent. That also catches the next item automatically.

  FIXED 2026-08-11, in `mkpackages` - the step that stages the component, so the check runs where the
  artifact is consumed and needs no new tool. `validate_component` parses it with `wasm::parse` (the
  same code that will have to run it), requires its declared initial memory to fit what the host can
  give it, and requires its imports to be exactly the world by name AND signature.

  That also closes the link-flag finding below: the memory assertion is the EFFECT of
  `-zstack-size=65536`, so a build that misses `src/sdk/.cargo/config.toml` fails here instead of
  producing a component the host cannot instantiate.

- [x] **A correctness-critical link flag lives only in `src/sdk/.cargo/config.toml`.**
  `-zstack-size=65536` is there because the default 1 MB wasm stack forces an initial linear memory
  the host's heap cannot hold - by the file's own comment, without it the component is not
  hostable. Cargo only reads that file when invoked from inside the directory, which `build.sh`
  does; a build driven with `--manifest-path` from elsewhere may not, and would also miss the
  `target-dir` the packager's hard-coded artifact path depends on. Assert the declared initial
  memory pages after the build rather than relying on the working directory.

  FIXED 2026-08-11 by asserting its effect rather than its presence: `validate_component` requires
  the staged component to declare at most four initial memory pages. Without the flag the default
  1 MB wasm stack forces sixteen or more, so a build driven from elsewhere - which would also miss
  the `target-dir` the artifact path depends on - fails at the staging step with the number in the
  message.

## The SDK as an SDK

- [ ] **This is one demo crate, not a reusable SDK.** A single `cdylib` holds the world bindings,
  the demo's buffer, the transform and both exports. Split it: a `liber-sdk` crate carrying the
  bindings and abstractions, and an `examples/` component that uses them. Until then "SDK" describes
  an intention rather than an artifact somebody else can depend on.

  NOT DONE 2026-08-11. It is the right change and it is a restructure, not an edit: a `liber-sdk`
  library crate carrying the world bindings, an `examples/` component that uses them, and a build
  that still produces `liber_component.wasm` at the path `mkpackages` stages from - with the
  `target-dir` and the `-zstack-size` flag in `src/sdk/.cargo/config.toml` following it. Everything
  else in this milestone was landed and verified tonight; this one wants a build cycle of its own
  rather than the tail of one, because a broken artifact path fails at packaging and takes the
  evidence for the rest of the work with it.

- [x] **`static mut BUF` is the wrong pattern to publish.** A 256-byte static plus a hand-made
  `&mut` through `addr_of_mut!`, where the instance is single-threaded and the host never re-enters
  `run` - so it is sound today and it is an example, which means it will be copied into code where
  those two facts do not hold. The stack is 64 kB and the buffer is 256 bytes: `let mut buf = [0u8;
  256]` costs nothing and cannot be misused.
  FIXED 2026-08-11: `let mut buf = [0u8; 256]` in `run`. It was sound where it stood - single
  instance, no re-entry - and this is an example, which is exactly the reason not to publish it: the
  pattern gets copied into code where neither of those holds.

- [x] **A fixed 256-byte read is not how a file should be read.** The demo says so in a comment and
  for the demo it is fine. As the example a developer copies, it teaches a file API that has no
  handle, no offset, no streaming and no way to tell a short read from the end - because the ABI
  has none of those. Either grow the world to express them or make the example's boundedness
  explicit rather than incidental.
  ANSWERED 2026-08-11 with the second option: the boundedness is explicit rather than incidental.
  The demo's buffer is a local `[u8; 256]` in `run` with the reason written beside it, and
  `read_input`'s clamp is what makes a short read safe rather than lucky.

  Growing the world to express a handle, an offset and a distinguishable end of input is the other
  option and it is a change to the ABI, not to the example - it wants the versioned world and the
  status/count error model recorded above, and should land with them rather than piecemeal.

- [x] **`score` does not do what its comment says.** The comment is
  `score(x) = floor(x * 1.5 + 2.0)`; the code is `((x as f64) * 1.5 + 2.0) as i32`, and a
  float-to-int cast truncates toward zero. For `x = -3` the comment says `-3` and the code says
  `-2`. The only test is `score(10) == 17`, where the two agree. Change the code or change the
  comment - and add the negative case either way.
  FIXED 2026-08-11 by correcting the comment - truncation is what the cast does and what the
  interpreter's float-to-int conversion is being exercised for - and by adding the negative case the
  finding asks for. The host now calls `score(-3)` as well and reports both, and the kernel test
  requires -2: the value where truncating and flooring disagree, which `score(10) == 17` could never
  have distinguished.

- [ ] **A panic tells the developer nothing.** The guest's panic handler is
  `core::arch::wasm32::unreachable()` and the host answers `Err(_) => exit()`. For a shipping
  sandbox that minimalism is right; for development it means every guest bug looks identical. A
  development mode that carries the panic location, the trap reason and the function it happened in
  is the difference between an SDK somebody can use and one they can only guess at.

  NOT DONE 2026-08-11. The design is small and it belongs with the crate split above: a
  `dev-diagnostics` feature on the SDK crate whose panic handler writes the location through
  `liber:log@1` before `unreachable()`, off by default so a shipping sandbox keeps its minimalism.
  It needs a place to live that is not the example, which is what the split provides.

## Tests

- [ ] **`src/sdk` has no tests of its own, and no gate is specific to it.** Its whole coverage is
  one kernel end-to-end happy path - the one that cannot fail on the write. The list under "the test
  that cannot fail" is most of what is needed; add to it the pure-guest cases that need no host at
  all (`score` on negatives and at the boundaries, `read_input` clamping, `write_output` clamping
  once it clamps), and the build-artifact assertions (parses under `wasm::parse`, initial memory
  within the host's limit, exactly the three expected imports with the expected signatures).

  PARTLY 2026-08-11. It now has a gate that is specific to it: `validate_component` runs at every
  build and asserts the three artifact properties this asked for - it parses under `wasm::parse`,
  its initial memory is within what the host can hold, and its imports are exactly the world by name
  and signature. The end-to-end test also stopped being one that cannot fail (it reads the output
  file back off the volume, and checks `run`'s return value).

  Still missing: the pure-guest cases (`score` on negatives and at the boundaries, `read_input` and
  `write_output` clamping), which need the guest logic in a crate that can be compiled for the host
  - the split above - since the current crate is a `cdylib` with a `#[panic_handler]` and cannot be
  a test target.

  And the one that belongs to the model rather than to the SDK, tracked in P02M0118: editing
  `src/sdk/src/world.rs` must move the system volume's source digest.

## Order

The test first. It is small, it is the reason the rest of this list was not found sooner, and until
it reads the file back, every other fix here is being validated by an assertion that cannot fail.

Then the naming in P02M0012, because it costs nothing and it is currently telling everyone - including
future audits - that a thing exists which does not.

Then the ABI: version it, check import signatures at instantiation, refuse unknown imports, make
pointers unsigned, and give the three calls a real error model. These are the things that get harder
to change with every component built against them, and there is exactly one today.

The build pin and the artifact validation next, then the split into a real SDK crate and an example,
then the polish.
