## The test that cannot fail

- [x] **The E2E test proves the read, the transform and the log, and not the write.** In
  `component_host`, `WorldFn::Write` does `self.output = memory[ptr..end].to_vec()` and only then
  calls `write_file`. The report sent back to the test is `host.output` - the copy taken before the
  write - and `run_component_scenario` unpacks it as `bytes[5..]`. The test asserts
  `content == expected` and its comment says this proves the filesystem write.

  FIXED 2026-08-11: the host reads the output file BACK through StorageService after the run and
  reports those bytes, and the test asserts them rather than the copy taken on the way into the
  write. The host does the reading rather than the test because the host is the one holding the
  storage grant - the bytes still travel through the service, which is the point.

  AND IT FOUND WHAT THE AUDIT SAID IT WOULD, immediately. The write in this scenario has NEVER
  happened: `run_component_scenario` hands StorageService a `RAMDISK`, which mounts as `ArchiveFs`
  over a mapped PKGARCH1 image, and an archive is read-only. The old assertion could not fail, and
  what it asserted was false in every run since it was written.

  So the test now asserts what actually happens there, which is worth having: the volume refuses,
  `write_file` answers `None`, the host maps it to `STATUS_DENIED`, the guest reports it, and the
  count comes back through the export's return value - the whole error model end to end, and the
  "read-only output grant" negative case the list below asks for. The POSITIVE case belongs to
  `kernel.volume_layout.fresh_seeded_system_volume_...`, which runs the same component against a
  real seeded LiberFS volume and reads `out.txt` back off it; that one passes, so the write path is
  proven where a write can actually land.

  While changing the report, a second defect fell out of it: `content` was parsed as `bytes[5..]`
  after `score_negative` had been appended to the report earlier the same day, so the content the
  assertion compared began with four bytes of score. The report is now a struct
  (`ComponentRun`) rather than a positional tuple, which is what let that happen.

  It does not. `write_file` could return zero, StorageService could refuse, the output grant could
  be read-only, the IPC could fail - and the assertion still passes, because the bytes it compares
  never went near the filesystem. The test must open `components/liber_component/out.txt` through
  StorageService after the run and compare what is actually there.

- [x] **`run`'s return value is read and discarded.** `let _count: i32 = match instance.invoke("run",
  ..)` - the count is never sent, so nothing checks the export's return ABI. The guest is no better:
  it calls `world::write_output(&buf[..n])` and throws the result away, so a failed write is
  invisible on both sides of the boundary. Report the count, assert it equals the expected length,
  and make the guest react to a short write.

  FIXED 2026-08-11: the host reports the count and the test requires it to equal the expected
  length, so the export's return ABI is checked. The guest reacts too - it reads every world call's

## The world ABI

- [x] **The world is unversioned.** Its whole identity is the strings `liber.read`, `liber.write`
  and `liber.log`. The day the read signature changes, old and new modules both import
  `liber.read` and nothing can tell them apart. Namespace and version it - `liber:vfs@1`,
  `liber:log@1`, or whatever this project's own convention becomes - before anything outside this
  repository builds against it. (Versioning the ABI is not the same question as releasing the
  system: this is a compatibility boundary, and it needs an identity from its first external user,
  not from the first release.)

  FIXED 2026-08-11: `liber:vfs@1` (read, write) and `liber:log@1` (log), on both sides. The world's
  whole identity was three unversioned strings, so the day a signature changed an old module and a
  new one would both import `liber.read` with nothing to tell them apart. Done together with the
  error model below, because they are one ABI break and doing them apart would have been two.

  Not moved: `wasi_host.rs`, an older standalone demo host carrying a hand-encoded module that
  imports the unversioned `liber.read`. It is a second implementation of the same idea and it should
  either move with the world or be retired; both are more than a rename of a byte array with LEB
  lengths in it.

- [x] **Imports are matched by name and never by signature.** `resolve` is a match on
  `(module, field)`; the parser knows each import's `type_index` and the module can produce its
  `FuncType`, and none of that is consulted. It matters more than it would elsewhere because
  `Value::as_i32` converts `I64`, `F32` and `F64` as well as `I32` - so a module declaring
  `liber.read` with the wrong type does not get "incompatible import", it gets silent conversion at
  call time. Check the exact signature at instantiation.

  FIXED 2026-08-11. `resolve` takes the import's `FuncType` from the module's type section and
  requires an exact match on parameters and results. It matters more here than it would elsewhere
  because `Value::as_i32` converts `I64`, `F32` and `F64` as well as `I32` - so a module declaring
  `liber.read` with the wrong type used to get a silent conversion at call time, on the boundary
  whose whole job is to be where the guest's word is not taken for anything.

- [x] **An unknown import is accepted and only traps if it is called.** `_ => WorldFn::Unknown`, and
  the trap happens at the call site. For a capability system the import list IS the manifest of
  requested authority: a module asking for `liber.camera` should be refused when it is instantiated,
  not tolerated on the grounds that the call site might be unreachable.

  FIXED 2026-08-11. `resolve` returns `Option`, and an import the world does not offer - by name or
  by type - refuses the component at instantiation. `WorldFn::Unknown` is gone. The import list is
  the manifest of requested authority, and "the call site might be unreachable" is not an answer to
  a module asking for a camera.

- [x] **Pointers and lengths are signed.** The guest passes `ptr as i32` and the host reads
  `v.as_i32() as usize`. A wasm32 address is a 32-bit pattern, and `0x9000_0000` is a valid one that
  becomes negative as an `i32` and then an enormous `usize`, which the host refuses. The current
  module's memory is small so it cannot happen today; the ABI is nonetheless capped at the low
  2 GiB. Read them as `as_i32() as u32 as usize`, and state `u32` in the ABI.

  FIXED 2026-08-11: `as_i32() as u32 as usize`. A wasm32 address is a 32-bit pattern, and reading it
  as signed sign-extended anything at or above 0x8000_0000 into an enormous `usize` that the bound
  then refused - so the ABI was silently capped at the low 2 GiB. Today's module has a small memory
  and cannot reach it; the conversion was still the wrong one.

- [x] **The error model cannot express the difference between "empty" and "refused".**
  `read_input` turns any negative into `0`, so an error and a legitimate end of input are the same
  answer; `write_output` returns a count where `0` means failed, read-only, and a genuine zero-byte
  write; `log` returns nothing at all. In a capability system "I am not allowed to write" is
  precisely the thing a component most needs to distinguish from "the write was empty". A status
  plus a count, with defined codes.

  FIXED 2026-08-11: an `i32` where a negative value is a status and a non-negative one is a count.
  `STATUS_DENIED` (-1), `STATUS_FAULT` (-2), `STATUS_IO` (-3), `STATUS_UNSUPPORTED` (-4), defined on
  both sides, with the guest wrappers returning `Result<usize, Error>` and an `Error::Unknown(i32)`
  so a newer host's code is reported rather than invented.

  `log` returns a status too - it returned nothing at all, so a component could not tell whether its
  one diagnostic channel had worked. A read-only output is `Denied` rather than `Ok(0)`, which is the
  distinction the whole finding is about, and `write_file` in the host returns `Option<usize>` to
  carry it. A `(ptr, len)` outside the guest's memory is `Fault` rather than a silently clamped
  window - it used to `.min(mem_len)`, so a component near the top of its memory wrote fewer bytes
  than it asked to and got a count it could not distinguish from a short file.

- [x] **`write_output` trusts whatever the host returns.** `read_input` defends itself with
  `(n as usize).min(buf.len())`; `write_output` is `if n < 0 { 0 } else { n as usize }`. A host
  regression returning a million for a hundred-byte write hands a million straight to the
  application through a wrapper whose job is to be the safe side of that boundary. Clamp, or trap.

  FIXED 2026-08-11: clamped to `buf.len()`, like `read_input` beside it. The host cannot have
  written more than it was given, and a wrapper whose job is to be the safe side of that boundary
  should not need the host to be right about it.

- [x] **`log_message` says bytes and the host means text.** The signature is `&[u8]`; the host does
  `String::from_utf8_lossy`. Either the API takes `&str`, or the host stops transforming what it was
  handed. Silently substituting replacement characters is the wrong answer to either contract.

  FIXED 2026-08-11 by making both sides say text. `log_message` takes `&str`; the host refuses a
  `log` whose bytes are not UTF-8 rather than substituting replacement characters where nobody can
  see them. The demo component decides for itself - it upper-cases ASCII, so what came in as text is
  still text, and it checks rather than assuming.

## The build contract

- [x] **`rust-toolchain.toml` says `channel = "stable"` and its comment says this keeps the build
  reproducible.** It does not: `stable` is whatever `rustup` last fetched. For most crates that is a
  reproducibility annoyance. Here the guest runs on this project's own interpreter, so a new stable
  can legitimately emit instruction selections, memory layouts, data segments or float conversions
  that the interpreter does not implement - and the component that worked yesterday stops working
  with no change of ours. Pin the exact tested release.

  FIXED 2026-08-11: pinned to `1.93.1`, the release everything here was built and verified with, with
  the reason in the file - the guest runs on this project's own interpreter, so a new stable can
  legitimately emit something the interpreter does not implement and the component that worked
  yesterday stops working with no change of ours. The wasm32 target was installed for that toolchain
  as part of the change, so the pin does not cost a download at the next build.

- [x] **Validate the built artifact against our own parser, in the build.** The pin above reduces
  the risk; a check removes it. After `just sdk`, run the produced `.wasm` through `wasm::parse` and
  fail the build on anything it cannot represent. That also catches the next item automatically.

  FIXED 2026-08-11, in `mkpackages` - the step that stages the component, so the check runs where the
  artifact is consumed and needs no new tool. `validate_component` parses it with `wasm::parse` (the
  same code that will have to run it), requires its declared initial memory to fit what the host can
  give it, and requires its imports to be exactly the world by name AND signature.

  That also closes the link-flag finding below: the memory assertion is the EFFECT of
  `-zstack-size=65536`, so a build that misses `src/sdk/.cargo/config.toml` fails here instead of
  producing a component the host cannot instantiate.

- [x] **A correctness-critical link flag lives only in `src/sdk/.cargo/config.toml`.**
  `-zstack-size=65536` is there because the default 1 MB wasm stack forces an initial linear memory
  the host's heap cannot hold - by the file's own comment, without it the component is not
  hostable. Cargo only reads that file when invoked from inside the directory, which `build.sh`
  does; a build driven with `--manifest-path` from elsewhere may not, and would also miss the
  `target-dir` the packager's hard-coded artifact path depends on. Assert the declared initial
  memory pages after the build rather than relying on the working directory.

  FIXED 2026-08-11 by asserting its effect rather than its presence: `validate_component` requires
  the staged component to declare at most four initial memory pages. Without the flag the default
  1 MB wasm stack forces sixteen or more, so a build driven from elsewhere - which would also miss
  the `target-dir` the artifact path depends on - fails at the staging step with the number in the
  message.

## The SDK as an SDK

- [x] **This is one demo crate, not a reusable SDK.** A single `cdylib` holds the world bindings,
  the demo's buffer, the transform and both exports. Split it: a `liber-sdk` crate carrying the
  bindings and abstractions, and an `examples/` component that uses them. Until then "SDK" describes
  an intention rather than an artifact somebody else can depend on.

  DONE 2026-08-11. `src/sdk` IS the library now - the package is `liber-sdk`, carrying the world
  bindings (`world.rs`), the status model (`status.rs`) and the panic handler (`panic.rs`) - and
  `src/sdk/examples/liber_component` is the example that uses it, as a workspace member. The crate
  keeps its name, so the manifest's `owner = "liber_component"`, the staged destination and the
  volume's source model are unchanged; `step_sdk` gained `--workspace`.

  One thing decided the layout rather than taste: `verify-model` walks every `Cargo.toml` under
  `src/` and requires a `[package] name`, so a virtual workspace root at `src/sdk` would have taken
  the planner down with "no [package] name" - the SDK being the root package is also the truer
  shape. Prepared and built in a copy outside the repository first, because a full verification was
  running in the working tree and a restructure mid-run would have invalidated it.

  The artifact is unchanged where it matters: the same three imports with the same signatures, two
  initial memory pages, `run` and `score` exported - checked by reading the module's own sections,
  and by `validate_component` at every build from now on.

- [x] **`static mut BUF` is the wrong pattern to publish.** A 256-byte static plus a hand-made
  `&mut` through `addr_of_mut!`, where the instance is single-threaded and the host never re-enters
  `run` - so it is sound today and it is an example, which means it will be copied into code where
  those two facts do not hold. The stack is 64 kB and the buffer is 256 bytes: `let mut buf = [0u8;
  256]` costs nothing and cannot be misused.
  FIXED 2026-08-11: `let mut buf = [0u8; 256]` in `run`. It was sound where it stood - single
  instance, no re-entry - and this is an example, which is exactly the reason not to publish it: the
  pattern gets copied into code where neither of those holds.

- [x] **A fixed 256-byte read is not how a file should be read.** The demo says so in a comment and
  for the demo it is fine. As the example a developer copies, it teaches a file API that has no
  handle, no offset, no streaming and no way to tell a short read from the end - because the ABI
  has none of those. Either grow the world to express them or make the example's boundedness
  explicit rather than incidental.
  ANSWERED 2026-08-11 with the second option: the boundedness is explicit rather than incidental.
  The demo's buffer is a local `[u8; 256]` in `run` with the reason written beside it, and
  `read_input`'s clamp is what makes a short read safe rather than lucky.

  Growing the world to express a handle, an offset and a distinguishable end of input is the other
  option and it is a change to the ABI, not to the example - it wants the versioned world and the
  status/count error model recorded above, and should land with them rather than piecemeal.

- [x] **`score` does not do what its comment says.** The comment is
  `score(x) = floor(x * 1.5 + 2.0)`; the code is `((x as f64) * 1.5 + 2.0) as i32`, and a
  float-to-int cast truncates toward zero. For `x = -3` the comment says `-3` and the code says
  `-2`. The only test is `score(10) == 17`, where the two agree. Change the code or change the
  comment - and add the negative case either way.
  FIXED 2026-08-11 by correcting the comment - truncation is what the cast does and what the
  interpreter's float-to-int conversion is being exercised for - and by adding the negative case the
  finding asks for. The host now calls `score(-3)` as well and reports both, and the kernel test
  requires -2: the value where truncating and flooring disagree, which `score(10) == 17` could never
  have distinguished.

- [x] **A panic tells the developer nothing.** The guest's panic handler is
  `core::arch::wasm32::unreachable()` and the host answers `Err(_) => exit()`. For a shipping
  sandbox that minimalism is right; for development it means every guest bug looks identical. A
  development mode that carries the panic location, the trap reason and the function it happened in
  is the difference between an SDK somebody can use and one they can only guess at.

  DONE 2026-08-11: a `dev-diagnostics` feature on `liber-sdk`. Off, the handler is `unreachable()`
  as before - a shipping sandbox should say nothing, and the host surfaces the trap either way. On,
  it writes `panic at <file>:<line>:<column>: <message>` through the log the component was ALREADY
  granted, so the diagnostic needs no new capability and nothing has to be stripped from a release
  build. The formatter is a 256-byte fixed sink that truncates on a character boundary: a panic
  handler is the last place to want an allocator, and a multi-byte character cut in half would make
  the entry unreadable rather than short.

### Every write failure is reported as a refusal

`WorldFn::Write` maps the host helper's `None` to `STATUS_DENIED`
(`src/user/services/core/src/component_host.rs:103`), with a comment explaining that a volume saying
no is `Denied` and the component can act on it. The helper produces `None` for three different
things (`src/user/services/core/src/component_host.rs:169`):

- `make_buffer(bytes)?` failing - a buffer this host could not create or map, which is the host's
  problem and not the volume's;
- `client.write(...)` answering `None` - no answer at all, a dead or unreachable service;
- `Some(Err(..))` - the service answered and refused, which may or may not be a permission.

The `_ => None` arm at the bottom erases the difference before the caller can see it, and the caller
turns all of it into "the volume said no". So the guest is told to stop asking when the truth may be
that the host ran out of memory or that StorageService is gone - and this milestone's own error
model has `STATUS_IO` for exactly that.

  DONE 2026-08-12: `write_file` answers a `WriteOutcome` - `Wrote`, `Refused`, `Failed`. Only
  `Error::Denied` is the volume saying no; a buffer this host could not create, a service that never
  answered, and every other error answer are `STATUS_IO`, because none of them is "you may not".

### `liber:vfs@1` has two implementations that disagree about what a failure is

`wasi_host` was repaired for all three things the last round named - the import is `liber:vfs@1`, the
window goes through `wasm::world::window`, the signature is resolved, and the module is validated.
The comment recording the third says why (`src/user/services/core/src/wasi_host.rs:147`):

> `wasm::world::window` refuses rather than clamps and reads a wasm32 address as the 32-bit pattern
> it is. **One set of rules, in one place, for both hosts.**

The rule for a FAILED read is not one set of rules. `wasi_host` ends its read with

```rust
.ok_or(Trap("granted read failed"))?
```

(`:156`), so a StorageService that does not answer kills the instance. `WorldHost` answers the same
import on the same ABI with `None => STATUS_IO` (`src/wasm/src/world.rs:191`), so the guest learns the
read failed and may report it to its own caller.

Both ship. The image contains two hosts of one versioned ABI, and which semantics a component gets
depends on which host launched it - which is exactly what a version on an interface is supposed to
make impossible.

- [x] **Build `wasi_host` on `WorldHost<S>`.** Its grants differ - a fixed file or a picked one -
  and that is what `WorldServices` is for: an implementation of the trait per grant, with the
  dispatch, the window rules, the UTF-8 contract and the status mapping shared. The seam already
  exists and this is the second caller it was built for.

  DONE 2026-08-12. Its grants differ - a fixed file or a picked one - and that is exactly what `WorldServices` is for: `WasiServices` implements the trait per grant, and the dispatch, the window rules, the UTF-8 contract and the status mapping all come from `WorldHost`. The comment beside the window fix already stated the rule - "One set of rules, in one place, for both hosts" - and this is the rest of it.

- [x] **Or delete `wasi_host`,** if the picker demonstration no longer earns its place. The choice
  is a product one; what may not stand is a second implementation of a versioned interface with
  different failure semantics.

  Not taken: it was rebuilt on `WorldHost` instead, which keeps the powerbox demonstration - a read whose grant comes from the user's pick rather than from a fixed path - and removes the second implementation. The choice was between the two and one of them is done.

- [x] **A test that both hosts answer a dead service the same way.** Whichever route is taken, the
  assertion is the invariant: one ABI, one answer.

  DONE 2026-08-12. `both_hosts_answer_a_dead_service_the_same_way` asserts at the SEAM, which is what both hosts are now built on: a service that did not answer is `STATUS_IO` and a window outside memory is `STATUS_FAULT` - the trap reserved for a guest that broke the contract, not for a service that failed.

### The SDK library owns the final program's panic handler

`liber-sdk` presents itself as a reusable library - "everything here is what somebody else's
component depends on" - and unconditionally compiles a `#[panic_handler]` into every `wasm32`
consumer: `#[cfg(target_arch = "wasm32")] mod panic;` (`src/sdk/src/lib.rs:41`), with the handler at
`src/sdk/src/panic.rs:13`.

A panic handler is a policy of the final binary. A component may want its own diagnostics, a
different trap, or to be linked in an environment that supplies one - and a `#[panic_handler]` may
appear once per program, so a consumer that wants its own cannot have it while depending on this
crate. The handler itself is good work: `dev-diagnostics` off by default, the message through the
log the component already holds, no new capability. It is in the wrong crate.

- [x] **Export the reporting and leave the handler to the component.** `liber_sdk::report_panic(info)`
  in the library, `#[panic_handler]` in `examples/liber_component`, so the SDK provides the behaviour
  and the program declares the policy.

  DONE 2026-08-12. `liber_sdk::report_panic(info)` is the behaviour; the `#[panic_handler]` is one line in `examples/liber_component`, which a component author copies with the rest of the example. A library may not take a policy of the final binary away from every consumer that depends on it, and a `#[panic_handler]` may appear once per program.

- [x] **Or make it an opt-in feature** - `panic-handler`, default off - if a one-line component
  should keep working without writing one. Either way the choice belongs to the consumer, and the
  reason belongs beside whichever is chosen.

  Not taken: the handler is one line in the example a component author already copies, so a feature flag would add a knob to avoid writing a line that is being copied anyway. Recorded because it was a written alternative and choosing the other one is the answer.

### The packaging gate parses what the host validates

- [x] **A test with a module that parses and does not validate**, asserting the packaging step

  DONE 2026-08-12 in `mkpackages`: a body leaving a value on the stack of a function declared to return nothing - it parses, which is what makes it the right fixture, and the validator refuses it.

The audit's own summary of the three previous rounds is worth keeping because it is the standard this

What it finds is that the claim in this file's own status header is still stronger than the code:

> `wasi_host` is built on `WorldHost` rather than patched, so **one versioned ABI has one set of error

The first half is true. The second is true of `WorldHost` and not yet true of what is plugged into it.
`WorldHost` maps `Refused -> STATUS_DENIED` and `Failed -> STATUS_IO` identically for all three
operations - that part is finished and tested. But `WorldServices` is implemented twice, and the two
implementations answer the same StorageService error with different variants. The seam made the
disagreement possible to see; it did not by itself remove it.

```
                          WorldHost<S>            one mapping, tested

                 |                           |
         ComponentServices             WasiServices
                 |                           |
    Err(_)   -> Refused -> DENIED    Err(_) -> None -> Failed -> IO
```

### The same `liber:vfs@1 read` failure reaches the guest as two different statuses

`component_host::read_file` maps a volume that answered with an error to `ReadOutcome::Refused`
(`src/user/services/core/src/component_host.rs:120`), which the world turns into `STATUS_DENIED`.
`wasi_host`'s two read helpers throw the error away before their caller can see it - `read_fixed`
ends its open with `_ => return None` (`src/user/services/core/src/wasi_host.rs:178`) and
`read_picked` does the same with its pick (`:196`) - and `WasiServices::read` then turns every `None`
into `ReadOutcome::Failed` (`:151-154`), which the world turns into `STATUS_IO`.

So `Error::Denied` from the same service, on the same versioned import, is `STATUS_DENIED` under one
host and `STATUS_IO` under the other. That is the finding the third audit opened and it is not closed;
it moved from the dispatch, where a test could reach it, to the adapter, where no test does.

The comment at `wasi_host.rs:146-150` states the deferral honestly, and its reasoning is the part to
revisit rather than the omission:

> Separating them properly means the helpers reporting which, which is work for the day this host's
> grants grow past two.

The work is one `match` arm per helper. What is being deferred is not the cost; it is the decision
about what each service error means to a guest - and that decision is the ABI, which is why it cannot
sit in an adapter as a wildcard.

- [x] **Make `read_fixed` and `read_picked` return `ReadOutcome`,** not `Option<usize>`. The helpers
  are the only place that sees the service's answer, so they are the only place that can classify it.
  `WasiServices::read` then has nothing left to guess at and becomes a pass-through, which is the
  shape `ComponentServices::read` already has.

- [x] **A test that both hosts answer a REFUSED service the same way,** beside
  `both_hosts_answer_a_dead_service_the_same_way`. That test asserts at the seam, which is why it
  passes today while the two adapters disagree below it - a dead service is `Failed` on both sides and
  a refused one is not. The invariant is the same one and the second half of it has no test.

### `Some(Err(_)) -> Refused` calls four things access denied

`read_file` maps every service error to `Refused` (`component_host.rs:120`) and `emit_log` does the
same (`:170`) - the audit found the first and not the second. The error enum has five variants
(`src/user/libs/protocol/base-proto/src/generated/liber/base/v1.rs:187`): `Denied`, `NotFound`,
`Invalid`, `Again`, `Closed`. Only the first is "you may not". `Again` is "try later" and a guest told
`STATUS_DENIED` will not; `Closed` is the peer going away, which is the machine and not the grant;
`Invalid` is this host having asked wrongly, which is nobody's business but this host's.

`write_file` already gets this right, and its comment is the argument for fixing the other two
(`:144-146`):

> `Denied` is the volume refusing; every other answer is a fault on the way there. `NotFound` and
> `Invalid` are the host having asked wrongly, `Again` and `Closed` are the service - none of them is
> "you may not", which is the only thing `Denied` means.

That comment was written about `write` and it is a statement about the error enum.

- [x] **Match `Error::Denied` explicitly in `read_file` and `emit_log`,** the way `write_file` does,
  and let every other variant be `Failed`. One vocabulary for all three operations, decided in one
  place, rather than three wildcards that happen to differ.

- [x] **Decide what `NotFound` means to a guest and write the decision down.** The world has four
  statuses and none of them is "not there", so this is a choice and not a lookup: `STATUS_DENIED` says
  the grant does not cover it, `STATUS_IO` says the machine failed, `STATUS_UNSUPPORTED` says the host
  does not do this. Today a wildcard picks, which is the same as not having decided. For a capability
  world the honest answer is probably that a granted path which is not there is the HOST's
  misconfiguration and not the guest's - but the requirement is that the file says which and why.

- [x] **`WasiServices::write` and `log` answer `Refused` for operations this host does not offer**
  (`wasi_host.rs:161-167`), which reads as "you may not" for something nobody may. `STATUS_UNSUPPORTED`
  exists for exactly that. Unreachable today - the import resolution refuses both before the instance
  exists - so this is tidiness, but it is tidiness in the vocabulary the two findings above are about.

### The packaging gate carries a second copy of the world

`wasm::world::resolve` is the canonical answer to "is this import in the world, with the right
signature" (`src/wasm/src/world.rs:59`), and the host, `wasi_host` and the toolchain panic test all go
through it. The packaging gate does not: `validate_component` builds its own table of three
`(module, field, params, results)` tuples (`src/tools/mkpackages/src/main.rs:540-544`) and does its own
`find` plus signature comparison (`:547-548`).

The gate was added so a build-time answer would not be deferred to run time, and its own comment says
the point is applying "the validator the host runs, which this gate did not" (`:520`). The import check
beside it is still a re-implementation of the host's rule rather than the rule. Two copies of a
compatibility boundary drift the day the boundary moves - a `@2` world, or one signature changed - and
the failure mode is a package that the gate passes and the host refuses, which is precisely what this
gate exists to prevent.

- [x] **Call `wasm::world::resolve(&import.module, &import.field, signature)` in `validate_component`**
  and fail when it answers `None`. The crate is already a dependency of `mkpackages` for `parse` and
  `validate`, so this deletes the table rather than moving it.

- [x] **Then decide what the gate can still SAY.** `resolve` answers `None` for both "not in the world"
  and "in the world with the wrong signature", and passing `None` as the signature does not separate
  them - it returns `None` too, by construction (`world.rs:69`). The gate's two messages today name
  which of the two happened, and that is worth keeping: either give `resolve` an error type with the
  two cases, or accept one message that names both. What may not stand is a second copy of the table
  kept for the sake of the wording.

### The `dev-diagnostics` half of the panic handler is never exercised automatically

`the_sdks_own_panic_handler_reaches_the_host_as_a_trap_with_its_line_logged`
(`src/wasm/src/world/tests.rs:392`) reads the real toolchain artifact, invokes `panic_now`, and asserts
the trap unconditionally. It then branches on whether the binary contains the string `panic at`
(`:424`) and asserts `host.logged()` when it does and `!host.logged()` when it does not (`:442-446`).

Both branches are real assertions rather than a skip, and the negative branch is the more valuable of
the two, because it catches a handler that started logging in a shipping build - the audit reads the
branch correctly and asks for it to be made unconditional, which would lose that. But `build.sh:56`
builds the SDK workspace with no `--features`, and nothing else in
the tree passes `dev-diagnostics`. So the branch that runs is always the negative one, and everything
under `#[cfg(feature = "dev-diagnostics")]` in `src/sdk/src/panic.rs` - the formatting of file, line,
column and message, and the call through the granted log - has no automatic coverage against a real
guest. The hand-assembled test covers the HOST's half of that path against an assumed shape, which is
the gap the toolchain test was written to close.

- [x] **Build the example a second time with `--features dev-diagnostics`,** into its own target
  directory so the shipping artifact is untouched, and assert the positive branch against it with no
  condition: a real panic logs its line through the granted log AND traps. The two artifacts then cover
  the two halves of the feature, each unconditionally, instead of one artifact covering whichever half
  it happens to be.

- [x] **Say in `build.sh` which of the two the image stages,** since after this there are two
  `liber_component.wasm` files on disk and the staged one is the shipping build. The package builder
  reads a path; the comment beside it should say why it is that path.

### The official example throws away the distinction the last three rounds built

`run` maps a failed read to `STATUS_IO` unconditionally
(`src/sdk/examples/liber_component/src/lib.rs:53-56`) and a failed log the same way (`:65-69`), while
`write_output` right below them matches `Err(Error::Denied) => STATUS_DENIED` and everything else to
`STATUS_IO` (`:75-76`). The SDK's API is correct - `clamp_count` turns the status back into an `Error`
with all four cases - and the example discards two thirds of it.

This is not a defect in the SDK and it is not reachable today, since the component's grants are wired
before it starts. It matters because of what this file is: the example is the thing a component author
copies, three rounds of this milestone went into making these states distinguishable, and the code
published as the way to use them shows two of the three being collapsed.

- [x] **Match `Err(Error::Denied) => STATUS_DENIED` for the read and the log too,** the way the write
  already does. Three world calls, one pattern, in the file whose job is to be copied.

## Fifth audit (2026-08-15)

An outside review of the component ABI, the SDK and the two hosts after the fourth audit's fixes. It
confirms the centralised error classification, the exhaustive `is_refusal`, the shared world in the
packager and the real dev-diagnostics artifact as properly closed, and raises seven points. All
seven hold.

The first is the one worth leading with, because of where it is.

- [x] **`wasi_host` undid the distinction in its last four lines.**

  DONE 2026-08-15. Four rounds of this milestone went into separating "you may not" from "there was
  nothing there" - `Error::Denied` becomes `ReadOutcome::Refused` becomes `STATUS_DENIED`, and a
  read of an empty file is `Read(0)` and a success. Then the host reported the result to the
  supervisor as `count.max(0)` bytes of the component's memory: a refusal became zero bytes, an
  empty file became zero bytes, and the supervisor received the same empty message for both.

  The report now carries the STATUS FIRST - four little-endian bytes - and the payload after it, so
  a negative status arrives as a negative status. Both kernel scenarios read the new shape and the
  component test asserts the status is the count, not a sign the payload has to be guessed from.

  It is a good reminder of what these audits keep finding: the defect was not in the layer the work
  went into, it was in the four lines after it.

- [x] **The shipping panic test graded itself against whatever it was handed.**

  DONE 2026-08-15. It looked for "panic at" in the artifact and asserted `logged` or `!logged`
  accordingly - so a build that accidentally gained `dev-diagnostics`, through a changed default or
  a stray `--features`, would have switched the test's expectation and stayed green. A test that
  adapts to the change it exists to catch is not a test of anything. The shipping policy is that a
  shipping component says nothing on its way down, and that is now what is asserted.

- [x] **A missing artifact was a PASS.**

  DONE 2026-08-15. The helper printed "SKIPPED" and returned `None`, the tests returned, and the
  harness recorded a pass. The comment said the skip was loud; Rust captures stdout and stderr of
  passing tests, so on the gate it was silent - a tree where the SDK never built produced a green
  suite with nobody told.

  The two halves needed different answers. "This machine has no wasm32 toolchain" is a reason not to
  RUN, and the harness has a word for that: `#[ignore]` is reported in the summary, which is visible
  where a captured message is not. "The artifact should be there and is not" is a reason to FAIL,
  because it is the difference between a check that did not run and a check that ran against
  nothing. So the tests are `#[ignore]`d, a missing artifact panics with what to build, and
  `check-host-tests.sh` runs with `--include-ignored` - the gate is the place those artifacts exist.

- [x] **The dev-diagnostics test checked that something was logged, not what.**

  DONE 2026-08-15. `report_panic` promises `panic at <file>:<line>:<col>: <message>`, and the test
  asserted a bool. A panic handler rewritten to log "oops" and trap would have kept it green while
  the diagnostic it exists to produce disappeared. The stub already recorded the text; the helper
  now hands it back and the test asserts the shape the SDK documents.

- [x] **The SDK example collapsed `Unsupported` into `Io`.**

  DONE 2026-08-15. The previous round taught it to keep `Denied`, and it went on discarding the one
  the ABI names outright: `Unsupported` is an operation the host does not implement, which is not a
  machine that failed. This file is what a component author copies, so it now maps every variant
  once through a `status_of` function - written once rather than three times inline, because three
  copies of a mapping is how the two halves of this file came to disagree in the first place.
  `Unknown(x)` passes the host's own number back rather than inventing a name for it.

- [x] **`Unsupported` in `wasi_host` is a branch that cannot run, and now says so.**

  DONE 2026-08-15. The audit is right that the milestone overstated it: a component importing
  `write` or `log` is refused at INSTANTIATION by the import resolution, so those answers never
  execute. The right response is not to change the behaviour - refusing the whole component is
  correct, because the import list is the manifest of requested authority and a host that cannot
  serve an import should not build the instance - but to stop describing a runtime answer that no
  runtime reaches. The comment now says which host reaches them.

- [ ] **State the ABI's count limit, or widen it deliberately.** `read` and `write` take a `u32`
  length and return an `i32`, so a count above `i32::MAX` cannot be expressed as a positive result.
  Nothing can reach it today - component memory is capped at four Wasm pages - and that is a reason
  it is a task rather than a defect. What it should not be is undiscovered: either the contract says
  a single call moves at most 2 GiB, or a later ABI revision returns something wider. A limit nobody
  wrote down is a limit somebody finds.
