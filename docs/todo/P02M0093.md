*Condensed 2026-08-08.*

**The compatibility model was decided first and written down**, in `docs/DYNAMIC_LINKING.md`, before
anything was built. That ordering is the point: a dynamic linking scheme whose compatibility rule is
discovered afterwards has already shipped incompatible artifacts.

The constraint that shaped everything: **the bare targets support neither Rust `dylib` nor
`cdylib`**. So the pinned builder emits full-graph PIC rlibs and links deterministic ELF shared
objects from them, rather than relying on a Rust-level dynamic library that does not exist for these
targets.

The library set is atomized - one library, one concern, with real dependency edges between them
rather than a single bag of shared code.

## Fourth audit (2026-08-16): `AI/audit/bootproto.md`

Three findings, two High, both in the compatibility decision that authorises hot replacement.

- [ ] **Compatibility compares provider NAMES and throws their identity digests away (BTP-001,
  High).** VERIFIED: `Identity::providers` splits each `provider=<name>:<digest>` record at the
  colon and yields only the name - its comment says so - and `decide` compares exactly that. Two
  images whose providers differ ONLY by digest are therefore reported `Compatible`, which is the one
  thing the digest exists to prevent. The process loader has a stricter, canonical parser that
  requires field order, hexadecimal widths, sorted unique providers and provider digests, and
  compares them - so the two components implement DIFFERENT IDENTITY LANGUAGES, and a publication
  reported compatible can then fail to launch. Use one parser and one typed `Identity` for both, and
  compare ordered `(name, digest)` pairs.
- [ ] **Export comparison rescans the whole symbol table for every symbol whose order diverged
  (BTP-002, High).** VERIFIED, with a caveat worth keeping: the audit calls it "billions of
  comparisons", and the code's own comment records the measured cost of rescanning per symbol as
  ~810 ms at 672 exports against ~8 ms for the walk. So the real number is known and is large rather
  than astronomical - and a candidate whose exports are in reverse order reaches the rescan path for
  every symbol. Build a bounded sorted index of candidate exports once instead.
- [ ] **`e_ident[EI_VERSION]` and `e_version` are never validated (BTP-003).** An image that does not
  declare the ELF version whose layout is then used to read it is accepted.
