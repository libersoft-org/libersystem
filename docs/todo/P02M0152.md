## Goal

Discover CPU and memory affinity on a two-node QEMU machine, preserve that affinity in physical
memory allocation, and provide an explicit local/strict/fallback placement contract which is tested
on x86_64, aarch64 and riscv64.

"NUMA works" in this milestone means observable placement correctness:

- a strict allocation comes from the requested node or fails;
- a preferred allocation chooses the local/nearest node and has a deterministic fallback;
- freeing, retirement, quarantine and accounting return to the physical node which owns the frame;
- a thread requested on a node executes on an online CPU of that node.

It does not mean QEMU demonstrated a latency benefit. Emulated topology is enough to prove routing
and accounting, not real cache, interconnect or memory-controller performance.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b` and QEMU 10.0.11.

- `bootproto::MemRegion` carries physical base, length and kind, with no proximity domain. `BootInfo`
  has fields for an ACPI RSDP and FDT pointer, but that is not the same as both being populated: x86
  UEFI supplies the RSDP, while the current aarch64 and riscv64 UEFI paths hand the kernel no DT and
  store no usable RSDP. Their QEMU NUMA evidence must therefore use direct-boot generated-DT profiles;
  this milestone keeps their existing UEFI boots as single-node regressions with no topology claim.
- The x86 SMP parser walks MADT for processors and no SRAT, SLIT or HMAT. The shared FDT parser used
  by aarch64/riscv64 does not retain `numa-node-id` or a distance map.
- `mem::frame` upgrades to one global buddy allocator protected by one lock. It has strong ownership,
  fragmentation, double-free, retirement and lost-page checks, but no physical-range-to-node map and
  no preferred-node argument.
- The scheduler has per-core run queues and no priority/load-balancing policy. NUMA placement was
  deliberately excluded by P02M0143; no half-implemented policy needs preserving.
- A two-node QEMU command with two `memory-backend-ram` objects is accepted on x86_64 `q35`, aarch64
  `virt` and riscv64 `virt`. QEMU emits ACPI proximity data on x86 and FDT `numa-node-id` on ARM/RISC-V;
  both device-tree targets also emit `distance-map` when distances are supplied.
- On the device-tree targets the early direct map is still bounded to 4 GiB on aarch64 and 8 GiB on
  riscv64. NUMA fixtures must place their RAM inside the mapped extent; silently ignoring a node
  above it is not NUMA support.
- RISC-V multi-node QEMU can expose more than one IMSIC region. P02M0151 owns the controller-topology
  correction and is therefore a real prerequisite rather than an ordering preference.
- On x86, SRAT has to be read before physical memory is divided into node pools, while the current
  `mem::init` publishes the direct-map bound, seeds frames and starts the heap as one operation. NUMA
  therefore requires an explicit early boot-order split; a parser cannot safely use
  `within_direct_map` before that bound exists and partition the already-live allocator afterwards as
  though no early frame had been taken.

## Work

- [x] **M1 - Normalize firmware topology without inventing missing affinity.**
  - Split x86 early memory bring-up into: publish HHDM/memory-map bounds; parse and validate firmware
    topology; seed the frame allocator; then start the heap. No SRAT pointer is dereferenced before
    the first phase has established the same direct-map ceiling the existing ACPI reader relies on.
  - Add bounded ACPI SRAT parsing for processor/x2APIC and memory affinity on x86_64. Parse SLIT when
    present; an absent SLIT produces the documented local/remote default, not fabricated firmware
    values. Enabled affinity ranges are validated as firmware ranges and then INTERSECTED with
    `seeds_the_pool()` memory. Reserved, firmware-owned or hotplug portions are reported/ignored for
    allocation rather than making an otherwise valid SRAT fatal.
  - On the aarch64 and riscv64 DIRECT-BOOT profiles retain `numa-node-id` on CPU and memory nodes and
    parse the versioned `distance-map`/distance matrix emitted by QEMU. Their existing UEFI/no-DT
    profiles remain single-node regression boots and make no NUMA-discovery claim.
  - Normalize firmware node ids, hardware CPU ids (APIC id, MPIDR or hart id), physical memory ranges
    and directed distances. Do not assign logical CPU ids while parsing firmware: after secondary
    bring-up, bind each CONFIRMED online logical CPU to the node of its reported hardware id. A timed
    out, late or absent CPU creates no logical affinity entry. `Unknown` is a first-class answer; it
    is not silently node zero.
  - Bound node/range/matrix counts before allocation, use checked cell/address arithmetic, and reject
    duplicate ids, overlaps with contradictory ownership, references to absent nodes, malformed
    matrices and ranges outside the actual direct-map limit. A valid affinity range extending through
    non-seedable memory is intersected as above, not rejected for describing more than the free pool.
  - Keep firmware parsing host-testable. Fixtures cover valid ACPI/FDT tables, checksums/truncation,
    32/64-bit cells, sparse node ids, asymmetric distances, CPU-only/memory-only nodes and topology
    records arriving in any order.

- [x] **M2 - Physical frames retain their node ownership through every allocator state.**
  - Firmware topology is known before `frame::init`, but the allocation which bootstraps the heap
    remains deliberately TOPOLOGY-NEUTRAL: the fixed pre-heap seed table is one boot pool and promises
    no locality. Record ownership by physical range, then partition its remaining free runs into one
    buddy pool per memory-bearing node after the heap exists. Frames consumed during the neutral phase
    still return to their physical node if they are later freed. Unaffiliated usable memory remains in
    an explicit unknown pool; it is not relabelled local.
  - Provide `allocate_strict(node)` and `allocate_preferred(node)`. Strict never reaches another
    pool; preferred tries the requested node, then increasing firmware distance, then unknown memory
    according to one deterministic tie rule.
  - Ordinary `allocate()` becomes local/preferred only after node pools are installed and the calling
    CPU has a confirmed logical-to-node binding. Before that readiness point it uses the neutral boot
    pool; it must not call `this_cpu()` before per-CPU state exists. A missing topology retains the
    present single-pool behavior.
  - Contiguous allocation follows the same strict/preferred contract and cannot assemble one span
    from two nodes.
  - THE EXPLICIT-NODE ENTRY POINTS ARE SPECIFIED AND EXERCISED AND NOT YET REACHED FROM PRODUCTION.
    This line used to say page-table and kernel-stack callers "can express a preference", which in a
    production build they cannot: `allocate_strict`, `allocate_preferred`, `allocate_contiguous_preferred`
    and `place_on` are `#[cfg(test)]`, because the callers that would use them are M3's and a public
    surface nothing calls is a surface nothing exercises. What production DOES get is the ordinary
    path made node-aware: `allocate` and `allocate_contiguous` both ask `local_node()` once bindings
    exist, so every allocation - including the contiguous spans DMA buffers ride - is local by
    default. Giving the explicit contract a production caller is a placement policy, and it belongs
    to the milestone that adds one rather than to this one.
  - `deallocate(phys)`, retire, quarantine and delayed TLB-safe reclamation find the owner from a
    checked sorted physical-range map, never from the CPU performing the free. A frame cannot migrate
    between node pools through an error path.
  - Preserve the allocator's existing invariants: double free is refused, a free cannot be silently
    lost, debug ownership remains exact, and global totals equal the sum of node plus unknown pools.
  - One outer lock for all node pools is acceptable here. Lock sharding is a performance claim and
    follows measurements, not the existence of nodes.

- [x] **M3 - CPU placement has a small explicit NUMA contract.**
  - Bind P02M0151's confirmed logical CPU ids to the firmware hardware-id affinity map, then publish
    `cpu_node(cpu)`, online CPU masks per node and the normalized distance query inside the kernel.
    An unconfirmed firmware CPU and a logical id which never came online appear in no mask. No

  - Add an internal thread-placement hint which selects an online CPU on the requested node or

  - A kernel stack or other CPU-owned allocation created for a selected CPU prefers that CPU's node.

  - Do not add automatic page migration, periodic balancing or a new priority policy. The scheduler

## Dependency order

```text
P02M0151 -> M1 -> M2 -> M4 -> M5 -> M6
                    \-> M3 --^
```

Topology and the pre-frame boot ordering must be trustworthy before allocator ownership changes.
Hardware-id affinity is bound to logical ids only after online CPU discovery; CPU placement can then
be built beside the allocator model, but the integration gate needs both.

## Definition of done

- The default no-topology/single-node boot preserves current allocation and scheduler behavior.
- The x86 UEFI/ACPI and two non-x86 direct-boot/FDT QEMU profiles discover the expected CPUs,
  physical ranges and distances; existing non-x86 UEFI/no-DT boots remain single-node regressions
  and are not presented as NUMA proof.
- Strict, preferred and ordinary local allocation have separate positive, exhaustion and rollback
  tests; returned physical addresses, not stored labels or elapsed time, prove placement.
- Free, retirement and quarantine return frames to their physical owner, and per-node totals sum
  exactly to the global total before and after the host and QEMU stress matrices.
- An internal node placement request runs on an online CPU from that node without claiming automatic
  migration or balancing.
- Documentation says no physical NUMA system and no performance property was validated.

## What this milestone refuses, and why

- **Production memory validation.** Firmware quirks, cache/interconnect behavior, controller routing
  and errata require real hardware. The user currently has none, so no milestone converts QEMU into
  that claim.
- **A speedup requirement.** QEMU topology is useful for correctness and often meaningless for
  locality latency. Performance is measured later on a named physical system.
- **Memory/CPU hotplug, automatic page migration, load balancing and cache-aware scheduling.** They
  are separate policies with failure and lifetime rules; none is needed to prove local allocation.
- **HMAT bandwidth classes, CXL tiers or persistent memory.** SRAT/SLIT/FDT proximity is the bounded
  first contract.
- **Device locality or DMA placement.** IOMMU/DMA isolation has P02M0153; combining security domains
  with locality before either works would make both harder to verify.
- **A userspace NUMA policy API.** The milestone is kernel topology and allocation correctness only.
- **RAM beyond an architecture's direct map.** Such memory remains explicitly unavailable until the
  mapping limit is removed; assigning it a NUMA node must not make an unreachable frame allocatable.
- **NUMA discovery in the current aarch64/riscv64 UEFI paths.** They carry no DT today. This milestone
  proves those architectures through direct-boot QEMU trees and preserves UEFI as a single-node
  regression. ACPI parsing or a new DT hand-off is a separately named boot-contract prerequisite for
  any later UEFI NUMA claim, not part of this milestone.


## Results

### M1 - the tables, read and refused

- **A CRATE, FED MALFORMED TABLES.** `src/topology` holds the normalized model - nodes, physical
  ranges, hardware CPU ids, a distance matrix - and 24 host tests feed it the ways a table is wrong:
  a signature that is not the one asked for, a length longer than the buffer, one byte changed so
  the checksum notices, an entry claiming zero length that a trusting reader would loop on for ever,
  a matrix whose diagonal is not the local distance, a SLIT declaring 65536 localities before
  anything is allocated from it, two nodes claiming one page, one processor in two places, a range
  that wraps past the top of the address space.

- **`Unknown` IS A FIRST-CLASS ANSWER AND NOT NODE ZERO.** Memory no table describes and a processor
  no table mentions both answer `Affinity::Unknown`. Calling either of them node zero would invent an
  affinity, and an allocation steered by an invented affinity is worse than one that was never
  steered - it is wrong in a way nothing reports.

- **A REPAIRED TOPOLOGY IS A FABRICATED ONE.** Overlapping claims that AGREE are merged, because
  firmware describing one page twice for one node is redundant; overlapping claims that DISAGREE are
  refused whole, because one of the two is wrong and there is no way to tell which. The system then
  runs with no topology, which is a state the report names and the allocator has a pool for.

- **THE PROXIMITY DOMAIN IS FOUR BYTES IN THREE PLACES.** ACPI's classic processor affinity structure
  splits it: one byte at offset 2 and three more at offset 9. Reading only the low byte is correct
  for every machine with fewer than 256 nodes and silently wrong for the rest, and the test that
  covers it names a node at 0x100.

- **AND THE DEVICE-TREE HALF FOUND A REAL DEFECT.** `fdt` now retains `numa-node-id` on banks and
  harts and reads `/distance-map` as directed triples - and doing so exposed two bugs in code that
  had been correct for a single-node machine. The bank list is insertion-sorted, and the parallel
  node array was not sorted with it, so every bank's affinity would have attached to whichever bank
  landed in its slot. Worse, adjacent banks are COALESCED: on a two-node QEMU machine the banks are
  exactly adjacent - 0x4000_0000 and 0x5000_0000, one node each - and merging them produced a single
  range whose affinity was whichever half was written first. Both are fixed and both have tests; 76
  fdt tests pass.

- **AN ASYMMETRIC MATRIX STAYS ASYMMETRIC.** The distance from node 0 to node 1 need not equal the
  distance back, in ACPI or in a device tree, and a reader that stored one number per pair would
  quietly halve a real machine's table. A cell the tree left out is REMOTE rather than zero: a zero
  would read as nearer than local, which is how a missing cell becomes a preference.

### M2/M3 - the pools, and the cores that belong to them

- **ONE POOL UNLESS FIRMWARE DESCRIBED MORE THAN ONE NODE.** The allocator's single `Option<Buddy>`
  became a `Vec<Pool>`, and on every machine this tree has booted so far that vector holds exactly
  one entry and every path behaves as it did. A machine with two memory-bearing nodes gets one pool
  each plus one for memory no node owns, and the difference is which pool an address routes to.

- **THE ROUTING IS BY ADDRESS, NEVER BY THE CPU DOING THE FREEING.** That is the whole rule, and the
  host model exists to prove the alternative is catchable: a frame from node 0 freed on a core of
  node 1 and routed by the core keeps every total plausible and leaves the frame in a pool that does
  not own it. `a_free_routed_by_the_freeing_cpu_corrupts_the_pools` drives exactly that and requires
  the model to refuse it.

- **AND EXTENTS THAT INTERLEAVE ARE REFUSED RATHER THAN APPROXIMATED.** A buddy owns one contiguous
  extent, so a machine whose nodes interleave cannot be partitioned this way. It gets one pool and a
  line saying why - which is the same state a machine with no topology has, and not a partition that
  puts half a node's memory somewhere else.

- **TWO DEADLOCKS, BOTH THE SAME MISTAKE, BOTH FOUND BY A HUNG TEST.** The preferred order was built
  in a `Vec` and the node pools in another, and both ran with the allocator's lock held - and the
  global allocator's `grow` calls `frame::allocate`, straight back into that lock, on a SpinLock,
  for ever. The file warns about this twice for other paths; these were the third and fourth. The
  order is now computed in a stack array bounded by the node bound, and the pools are built before
  the lock is taken.

- **CORES ARE BOUND AFTER BRING-UP, AND ONLY THE ONES THAT ANSWERED.** Firmware describes processors
  it believes exist. A core that timed out or was never started has no binding, is in no node's
  count, and `place_on` refuses it by a typed reason rather than finding some other core.

### M5/M6 - the two-node machine, and what it proves

- **THE ORDERING HAZARD M1 NAMED WAS REAL, AND IT COST A SILENT WRONG ANSWER.** `within_direct_map`
  is the check every firmware pointer is validated against, and on x86_64 it answers from a bound
  published at the END of `mem::init` - after the topology reader ran. So the reader found no SRAT
  on a machine that has one, said so, and the machine ran with no topology. The bound is now
  published first, from the map rather than the retained copy, because retaining needs the heap.

- **AND THE PARSER READ THE PROXIMITY DOMAIN FROM THE WRONG OFFSET.** ACPI puts it in three
  different places in three affinity structures: offset 2 for memory, offset 4 for x2APIC, and a
  byte at 2 plus three at 9 for the classic APIC. Reading the memory structure's at 4 lands on two
  reserved bytes and the low half of the base address - and the boot report then said "node 0: 4095
  MiB, node 1: 0 MiB" while the processors were distributed perfectly correctly. The host fixture
  had been written from the same wrong reading and agreed with the bug, which is why the test that
  now catches it asks the three structures apart by name.

- **PLACEMENT IS PROVED BY ADDRESSES.** On the two-node profile: a strict allocation returns a frame
  whose physical address is inside the firmware range of the node that was asked for; a strict
  allocation on a node with no pool is refused while a preferred one falls back; a sixteen-page
  contiguous span never crosses a node boundary at any of its pages; every frame goes back to the
  pool that owns it and the pools' free counts sum to the allocator's before, during and after. A
  thread placed on node 1 RAN on a core whose normalized node is 1 - the test reports the weaker
  "it was queued there" if the other core never picks it up, and the gate refuses that report.

- **THREE PROFILES, EACH READING TWO NODES.** x86_64 `q35` through its UEFI/ACPI path: 2047 and 2048
  MiB, two processors each, distances from the SLIT. aarch64 `virt` and riscv64 `virt` through their
  DIRECT-BOOT generated-DT paths: 256 MiB and two processors each, distances from `/distance-map`.
  All three partition the allocator into a pool per node plus one for unaffiliated memory, and all
  fourteen `numa`-tagged tests pass on each.

- **THE DT PORTS NEEDED A HARNESS FIX, AND IT IS A REAL ONE.** The direct-boot path DUMPS a device
  tree from a separate QEMU invocation and loads it at a fixed address - and that invocation did not
  carry `QEMU_EXTRA`. So a machine given `-numa` booted with a tree dumped from a machine that was
  not: the guest read one memory node where its hardware had two, with nothing able to say the tree
  and the machine disagreed. The dump now carries the same arguments the run does.

- **AND THE UEFI PROFILE CANNOT BE THE ONE THAT PROVES THIS, WHICH IS WHY THE MILESTONE SAYS DIRECT.**
  On these ports the loader hands the kernel a firmware memory map and the device tree's `/memory` is
  then not used at all. A UEFI boot therefore reads its topology from the tree and its banks from
  somewhere else - and on the two-node machine that firmware map arrived truncated, sixteen usable
  regions of thirty-six, all inside the first node: 221 MiB of a 512 MiB machine, with the second
  node's pool never created because its memory was never seeded. The direct profile is where both
  halves come from the same tree, and it seeds all 502 MiB.

- **AND ONE BOOT LINE HAD BEEN QUIETLY LYING FOR AS LONG AS BANKS COULD BE SPLIT.** aarch64 printed
  `RAM {ram_base}..{ram_base + ram_size}`, which is the FIRST CONTIGUOUS RUN and not the machine's
  memory. On a one-node machine the two are the same; on a two-node machine where the banks are
  adjacent but differently owned they are not, and the line said a 512 MiB machine had 256 MiB. It
  now prints every bank with its node, and the regions actually handed to the allocator beside them -
  which is what made the truncation above readable at all.

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED. One ordering bug, one path that did not get the contract the rest of the allocator
got, and one entry point that exists only in test builds.

- [x] **A preferred allocation can try a remote node before the one it asked for.** `fallback_order`
  sorts every node by `(distance(from, node), node.0)` ([lib.rs](../../src/topology/src/lib.rs)) and
  `distance` answers `LOCAL_DISTANCE` for `from == from`. Firmware may declare an off-diagonal
  distance of `10`, and a test pins that this is accepted rather than refused - "a machine may report
  two nodes that are equally near" ([tests.rs](../../src/topology/src/tests.rs)). On such a machine
  node 0 sorts ahead of a requested node 1 on the tie rule alone, and M2 says preferred "tries the
  requested node, then increasing firmware distance". Put the requested node first by construction
  instead of relying on its distance being the smallest number in the row.

- [x] **`allocate_contiguous` never became node-aware, and it is the one DMA buffers ride.**
  `allocate` asks `local_node()` and passes the answer down; `allocate_contiguous` calls
  `take_contiguous(pages)`, which passes `None` ([frame/mod.rs](../../src/kernel/mem/frame/mod.rs)).
  M2 says contiguous allocation follows the same strict/preferred contract as the single-frame path.
  `take_contiguous_from` already takes a `want`, so this is the readiness check the other path
  already has, applied to the caller that most wants locality.

- [x] **The node-explicit entry points are `#[cfg(test)]`, under a checked line that reads as
  delivered.** `allocate_strict`, `allocate_preferred`, `allocate_contiguous_preferred` and
  `place_on` are all test-only ([frame/mod.rs](../../src/kernel/mem/frame/mod.rs),
  [numa/mod.rs](../../src/kernel/smp/numa/mod.rs)), and the comment beside them says why: the callers
  that would use them are M3's and do not exist. M2 says page-table and kernel-stack callers "can
  express a preference" - in a production build they cannot, because the functions are not compiled.
  Either give the thread's kernel stack the placement M3 describes, so the contract has a caller, or
  amend M2 to say the explicit contract is specified and exercised and not yet reached from
  production. Ordinary `allocate()` IS node-local once bindings exist, so this is the narrow claim
  that is wrong, not the whole of M2.

## Results (2026-08-26)

`fallback_order` sorted by `(distance, node id)` and `distance(n, n)` is `LOCAL_DISTANCE` - which
firmware is allowed to declare off the diagonal, and a test pins that this is accepted rather than
refused, because two nodes may really be equally near. On such a machine node 0 won the tie against a
REQUESTED node 1, so every preferred allocation for node 1 reached into node 0 first. The requested
node is first by construction now; the tie rule orders the fallbacks and may not displace the node
the caller named.

`allocate_contiguous` passed `None` where `allocate` passes `local_node()`, so the one allocation
whose whole purpose is a device reaching memory was the one that ignored which node the memory is on.
`take_contiguous_from` already took the node; it was simply never given one, and the node-blind
wrapper that hid that is gone.

M2's wording said page-table and kernel-stack callers "can express a preference", which in a
production build they cannot - the explicit entry points are `#[cfg(test)]` because their callers are
M3's. The line now says what is true: the ordinary path is node-local, and giving the explicit
contract a production caller is a placement policy belonging to the milestone that adds one.

## What the 2026-08-28 audit found

Seven findings. Six fixed, one open. The three that were WRONG ANSWERS rather than missing evidence
are first, because that is the order a reader needs them in.

1. **A frame taken during the topology-neutral phase was retired instead of returned.** FIXED.
   `upgrade_to_heap` sized the buddy from the first and last REMAINING free runs, and `heap::init`
   has already taken frames off the head of the run table by then - so every one of them sat below
   the buddy's base. Freeing one found no covering pool, `free_span` refused an address below its
   base, and the allocator recorded the frame as lost and RETIRED IT FOR EVER. The extent is now
   `seeded_base`/`seeded_pages`, fixed while the free runs still were the whole pool; the buddy is
   still seeded from the runs that are actually free, so the early frames are covered without being
   handed out twice. `kernel.mem.frame.a_frame_taken_before_the_buddy_existed_is_inside_the_pool_that_would_take_it_back`
   asserts it, and WAS WATCHED TO FAIL on the old extent - on this machine, which is what turns this
   from a reading of the code into a measurement.

2. **A preferred allocation did not try the requested node first.** FIXED. `Pools::preference` keyed
   on `(distance, node id)`, and firmware may declare an off-diagonal distance equal to
   `LOCAL_DISTANCE` - two nodes equally near, which this kernel accepts. Node 0 then sorted ahead of
   a requested node 1 on the tie rule alone. `Topology::fallback_order` had already been corrected for
   exactly this and carries the comment explaining it; the allocator's own copy of that order had not.
   The key is now `(node != want, distance, node id)`.

3. **A malformed device-tree distance map was read as a shorter valid one.** FIXED. The triple loop
   stopped at the first incomplete triple, stopped at `MAX_NUMA_CELLS`, and `continue`d past a
   distance above 255 - all silently, under a comment claiming the last of those was "refused rather
   than truncated". `distance-map` mode was also entered on the node NAME with no
   `compatible = "numa-distance-map-v1"` check. `BootInfo::numa_distance_malformed` now records all
   four, and the kernel refuses the distances and KEEPS THE AFFINITY - the same split the ACPI reader
   makes for a bad SLIT. Covered by `a_distance_map_that_is_not_one_is_refused_rather_than_truncated`.

4. **Firmware affinity ranges were not intersected with seedable memory.** FIXED. M1 asks for the
   intersection in as many words and both readers passed raw ranges to `Builder`, so the normalized
   topology and the boot report stated per-node totals covering memory this kernel never hands out.
   `Builder::restrict_to_seedable` takes the spans and `build` intersects every range with them - a
   range may survive as several pieces, and one with no overlap drops out. `numa::discover` now takes
   the boot memory map and both readers supply the same list. The allocator was never endangered:
   `partition` ranges only over the runs it seeded. What was wrong was the number everyone reads.

5. **M3's placement contract did not reach the allocation that depends on it.** FIXED. The API named
   a core only AFTER the thread existed - `prepare_with_object` built it, `start_thread_on` chose the
   core - so the kernel stack was already in the CREATING core's node and stayed there for the life of
   the thread. `Thread::new_for_cpu` takes the cpu, resolves its node and allocates the stack through
   `frame::allocate_preferred` (no longer `cfg(test)`, because it now has a production caller).
   PREFERRED, never strict: a thread that cannot be created is worse than one whose stack is remote.
   `kernel.smp.numa.a_thread_placed_on_a_node_runs_on_a_core_of_that_node` now asserts the stack's
   node through `Thread::stack_node`.

6. **The weaker-placement rejection read the wrong file.** FIXED. `weak_placement` took `$2` and
   greped that one file while both call sites hand it the whole `result_logs` array - run log first,
   guest log second - and the `numa-fixture:` oracle is in the GUEST log on x86_64 and aarch64. So the
   one check that rejects a weaker placement was reading the file that cannot contain it. It now
   `shift`s and greps `"$@"`, like every other check in that gate.

7. **The reference model is never compared with the implementation.** OPEN, and M4 is unticked for it.
   The model checks itself; nothing drives the same trace through the kernel allocator, and it has no
   contiguous operation and no quarantine state. The auditor's other M5 observations - that
   `strict_fails_where_preferred_falls_back` never exhausts node 0, that the contiguous test does not
   assert WHICH node, that the free test does not arrange a remote-CPU free - are accurate and are
   evidence gaps in the same direction. They belong with M4's harness rather than as separate edits.
