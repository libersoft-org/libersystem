# P02M0153 - Virtio-IOMMU confines the first x86_64 QEMU endpoints

Status: OPEN. X86_64 QEMU SECURITY SLICE. NOT A NATIVE-IOMMU, ALL-DRIVER OR PHYSICAL-HARDWARE
CLAIM.

THE DMA/IOVA CONTRACT MOVED HERE FROM P02M0098, and this milestone is no longer blocked behind it.
It was written there because a driver's DMA is a driver-lifecycle concern, which is true - and it
made the only milestone that was going to implement it wait for a slice nobody was writing. So the
contract, its kernel-owned backend interface, its host fake and the IOMMU-absent policy are M0 and
M0a below, and the first concrete backend that proves them is the same milestone's M1 onward.
P02M0098 keeps what the LIFECYCLE owns: releasing a bound driver's DMA memory in its reset and
containment order, accounting it to a Domain and a binding, and draining it before pages are
refunded.

## Goal

Under a named x86_64 QEMU `virtio-iommu` enforcing profile, each endpoint selected for this first
protected slice - the hostile `edu` fixture and one ordinary `virtio-net` device - can read or write
only the live DMA mappings attached to that endpoint's current binding generation, even when its
driver is buggy or malicious.

Discovery, attach, map, invalidation or teardown failure must end in a refused binding, disabled bus
mastering, or a quarantined device and frames. It must never silently become untranslated DMA.

The security claim is profile-specific:

> In the enforcing QEMU profile, an endpoint which addresses an unmapped page, another endpoint's
> page, a direction-forbidden mapping, or an address revoked from its old binding is stopped by the
> IOMMU and cannot modify the sentinel physical memory behind that attempted access.

This removes each of the two protected endpoints' drivers from the DMA memory-safety TCB for this
profile. Drivers left on P02M0098's explicit untranslated path receive no such claim. The kernel
IOMMU backend, the emulated IOMMU and the hypervisor remain trusted by this claim.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b` and QEMU 10.0.11.

- `DmaBuffer` pins and charges physically contiguous pages and can retain the device-table index for
  which it was created. On driver termination, pages can be held until that device is declared
  quiesced; overflow leaks them deliberately instead of recycling memory a device may still reach.
- PCI bus mastering is disabled after discovery, enabled on the first `DeviceMemory` owner and
  disabled after the last owner. This narrows the active window and is a useful ordering primitive.
- `SYS_DMA_BUFFER_PHYS` still gives a driver a raw physical integer. Binding the buffer to a device
  limits who may ask, but the integer cannot be revoked and the device is not constrained to it.
- `SYS_DEVICE_QUIESCED` trusts the holder's statement that reset completed. The kernel cannot observe
  device-side translations because there is no IOMMU domain, invalidation or fault path.
- There is no generic IOMMU interface, IOVA allocator, endpoint attach/detach, requester-id alias
  model or backend in the tree - and until this milestone was rewritten, no milestone that was
  actually going to write one: P02M0098 owned the contract and was not being worked on, so the only
  implementation waited on a slice with no author. The contract is M0/M0a here now. P02M0098 keeps
  binding identity, generation and the reset/containment order; P02M0099 lists `virtio-iommu`, whose
  one concrete backend and QEMU proof live here.
- QEMU exposes `virtio-iommu-pci` on x86_64, aarch64 and riscv64. It also exposes the PCI `edu` test
  device on all three. Availability in `-device help` is not kernel discovery: today's `DeviceEntry`
  admits only resolved virtio and xHCI functions, so retaining an arbitrary PCI function and making
  EDU's bounded BAR claimable is work THIS milestone does for its own fixture rather than waits for.
  It closes only the x86_64 fixture.
- On the current q35 UEFI boot path, starting with both `default-bus-bypass-iommu=off` and
  `boot-bypass=off` blocks OVMF's SATA access to the boot ISO before the loader runs. The enforcing
  profile must therefore make one measured firmware-to-kernel transition instead of claiming that
  translation can be strict before its driver exists.

## Dependencies and ownership

```text
P02M0098                      P02M0153 (this milestone)
  binding identity              M0  portable directional DMA/IOVA contract
  + generation                  M0a generic backend interface + host fake
  reset/containment                 iommu-required / trusted-untranslated policy
  ordering                            |
     |                                v
     +------------------------->  M1..M6 virtio-iommu backend + QEMU gate
```

WHAT IS STILL P02M0098'S, AND WHAT THIS MILESTONE DOES WITHOUT. Binding identity with a generation
token, and the reset/containment order a crashed driver is torn down in, remain there: they are
about drivers rather than about translation, and this milestone does not recreate them. Where M3
needs a binding generation to attach an endpoint to, it uses the one the device registry already
carries and says so - a mapping bound to a generation that cannot change is a weaker claim than one
bound to a generation that can, and the weaker claim is stated rather than dressed up.

P02M0099 is coordination, not another hard dependency: its `virtio-iommu` inventory row points here,
while this backend reuses the virtio PCI transport already present at today's HEAD. Completion of the
rest of P02M0099's hardware families is unrelated to this gate.

WHY THE SLICE MOVED RATHER THAN THE DEPENDENCY BEING WAIVED. Attaching an endpoint to "the current
driver" is meaningless without binding identity, crash ownership, DMA-address semantics,
fake-backend rollback and reset completion. Three of those five are DMA-address semantics,
fake-backend rollback and the interface they belong to - they are this milestone's subject, they
were written elsewhere, and nothing was implementing them there. The other two stay in P02M0098 and
are used as they are. The point of the move is that a contract lives with the code that proves it,
not that the dependency was inconvenient.

The generic isolation mechanism and `virtio-iommu` security backend are kernel-owned. An ordinary
driver never receives the IOMMU control queue or permission to map arbitrary frames: a userspace
service which could do so would simply become the same memory-safety TCB under another name.

## Work

- [ ] **M0 - One portable DMA contract, before any backend translates anything.**
  - `DmaAddress`/IOVA, the generation-bound `DmaMapping` lifecycle and ONE kernel-owned backend
    interface: domain create/destroy, endpoint attach/detach, map/unmap, invalidation completion and
    bounded fault delivery. A host fake backend exercises every completion, failure and rollback
    order - which is what lets M1's real backend be a second implementation of a tested interface
    rather than the first implementation of an untested one.
  - Each mapping declares device-read (`to-device`), device-write (`from-device`) or bidirectional
    direction, address width, alignment, segment/count and coherency needs. The kernel enforces
    ranges and permissions, builds scatter/gather or bounded bounce buffers for address-limited
    devices, and provides explicit `sync-for-device` / `sync-for-cpu` with the cache maintenance and
    barriers non-coherent aarch64/riscv64 need and coherent x86 does not.
  - COMPLETION PRECEDES CPU REUSE. Revoke drains or cancels DMA, synchronizes caches, invalidates
    IOMMU/device translation state, and only then refunds pages. Host and fake-device tests model
    stale caches, the wrong direction, out-of-range descriptors and 32-bit DMA limits.
  - The exposure this replaces is `SYS_DMA_BUFFER_PHYS`: an integer a driver is handed and the
    device is not constrained to. It stays only under the explicit `trusted-untranslated` policy
    below, and every other path takes an address the kernel can revoke.

- [ ] **M0a - The IOMMU-absent threat model, stated rather than implied.**
  - Capability isolation cannot contain a malicious bus-mastering device or driver without
    translated DMA. Bounce buffers solve reachability and coherency; they do not solve an attacker
    programming an arbitrary address. Saying so is the point of this item - a system that quietly
    behaves as though capabilities cover DMA has a hole exactly where its strongest claim is.
  - Registry policy marks a driver `iommu-required` or trusted-for-untranslated-DMA. An untrusted
    DMA driver REFUSES TO BIND without an enforcing IOMMU; the minimal boot-critical trusted set may
    bind under a loud, audited, degraded-isolation state that says which drivers are in it.
  - Translated and untranslated devices stay in separate Domains and accounting pools. Native VT-d,
    AMD-Vi and ARM SMMU are later backends to the same interface; this milestone owns the first
    `virtio-iommu` provider and the QEMU gate that proves it, and defines the clean no-IOMMU
    behaviour now rather than after one exists.

- [ ] **M1 - Checked virtio-IOMMU messages implement the completed backend interface.**
  - Implement the contract's bounded `probe`, `domain_create/destroy`, `attach/detach`, `map/unmap`,
    `invalidate` and fault-drain operations using checked virtio request/response codecs. A response
    which only accepted a request is not confused with the completion the generic contract requires.
  - The enforcing backend MUST support device-read, device-write and bidirectional page permissions.
    Unsupported permission negotiation refuses the enforcing profile; it may not weaken the Goal's
    direction claim or map every request read/write.
  - `SYS_DMA_BUFFER_PHYS` remains confined to P02M0098's explicit `trusted-untranslated` policy.
    Protected drivers receive only the live `DmaAddress`/IOVA that the prerequisite contract defines.
  - Host work here tests the virtio-IOMMU wire codec, feature negotiation, request status and malformed
    event handling. Generic interval, accounting and failure-order tests remain owned by P02M0098's
    fake backend.

- [ ] **M2 - `virtio-iommu` is initialized before either x86_64 protected endpoint can master the bus.**
  - Discover the controller through the kernel's retained PCI identity, negotiate only implemented
    features and validate input/IOVA ranges, reserved regions, queue sizes, request ids and response
    status before trusting them.
  - Keep the IOMMU control virtqueues in one documented, pinned kernel bootstrap mapping which is
    never exposed to another driver. Resolve the bootstrapping exception explicitly; do not enable
    global bypass to make the controller configure itself.
  - Derive endpoint identity from kernel PCI segment/bus/device/function and the backend's requester
    rules, not a userspace-supplied device index. This first topology contains direct-root-port EDU
    and virtio-net functions only; a bridge alias or other endpoint form is refused rather than
    generalized inside the fixture.
  - The named QEMU profile sets q35 `default-bus-bypass-iommu=off` but starts the controller with
    `boot-bypass=on` so OVMF can read the SATA boot ISO. It uses modern-only virtio functions
    (`disable-legacy=on`) and gives protected virtio endpoints `iommu_platform=on`.
  - After loader hand-off, the kernel negotiates `VIRTIO_IOMMU_F_BYPASS_CONFIG`, quiesces and disables
    bus mastering on the firmware SATA function and every non-controller endpoint, then changes the
    controller bypass configuration to off and reads it back. Only after that confirmation may it
    attach, map and enable bus mastering for EDU or virtio-net. A missing feature or failed transition
    is a typed bind refusal for `iommu-required` devices, never a degraded continuation.
  - Keep this a dedicated fixture: apart from the firmware-only SATA boot function, the IOMMU, EDU and
    virtio-net, do not inherit optional DMA devices from the ordinary harness merely to make them part
    of the transition.
  - Bound and validate the fault event queue. A malformed or flooding emulated device cannot grow an
    unbounded kernel log or allocation.

- [ ] **M3 - Backend completions plug into P02M0098's binding lifecycle.**
  - Create one isolation domain per exclusive device binding/endpoint. A reused BDF receives a new
    binding generation; stale mappings and completion events cannot attach to the replacement.
  - Attach the endpoint before enabling bus mastering or publishing `DeviceMemory`. Creating a DMA
    buffer reserves quota and IOVA, installs translations and confirms map completion before returning
    a handle or address to the driver.
  - Feed attach/map/unmap/detach completions and failures into P02M0098's existing rollback ledger. Its
    failed reservation, handle install or driver launch paths must leave no translation, attachment,
    bus-master bit, quota charge or hidden capability; this milestone proves the concrete backend does
    not violate that ordering.
  - On clean mapping close, P02M0098 marks the mapping closing and blocks new cooperative submissions,
    then waits for this backend's confirmed unmap/invalidation. The IOVA remains in the hardware-
    reachable set until that completion arrives, and its frames are retired only afterwards. Neither
    layer relies on a driver's queue-completion statement for memory safety.
  - On crash/forced unbind, P02M0098 owns disable/reset/quarantine policy. This backend must confirm
    detach/invalidation or fail it explicitly; an unconfirmed operation can never release the endpoint
    or affected pages from the prerequisite lifecycle's quarantine.

- [ ] **M4 - EDU and one ordinary virtio-net endpoint consume IOVA in the first enforcing slice.**
  - Add the bounded test binding for EDU and migrate virtio-net's queue and packet buffers to the
    P02M0098 DMA-address contract. No descriptor for either protected endpoint receives a value
    obtained from raw physical disclosure.
  - The domain contains exactly the binding's live ring/data mappings, with no blanket RAM/direct-map
    identity range. Identity-valued IOVAs are acceptable during migration only if they are still
    installed and revoked as ordinary mappings; equality with a physical address grants no bypass.
  - EDU and the selected virtio-net binding declare `iommu-required` and do not start without
    enforcement. Other existing drivers remain outside this milestone and may retain current behavior
    only in P02M0098's explicitly listed degraded profile; they are not covered by this Goal.
  - Expose this backend's mapping, IOVA, endpoint and fault counters to the binding/Domain accounting
    P02M0098 already owns, so repeated crash/restart can return to an asserted baseline.

- [ ] **M5 - Faults are bounded security events with containment policy.**
  - Record endpoint, domain and binding generation, IOVA, access direction and reason without logging
    payload memory. Keep counters and only a bounded recent-event ring.
  - Translate an unknown endpoint, stale generation, permission fault or out-of-range DMA into the
    generic fault event P02M0098's lifecycle consumes. That prerequisite owns the mask/disable,
    quarantine and supervisor policy; this backend must neither bypass it nor invent a parallel one.
  - A fault storm does bounded work and cannot exhaust the heap or starve unrelated endpoint/domain
    fault processing.

- [ ] **M6 - A hostile EDU fixture and ordinary virtio-net prove the x86_64 boundary.**
  - Add named `virtio-iommu-protocol` and `qemu-virtio-iommu-x86_64` gates. The first checks this
    backend's codec, negotiation and event parser; P02M0098's existing generic DMA/fake-backend gate
    remains the owner of interval and rollback semantics. The second cold-boots M2's staged x86_64
    profile, observes the loader while boot bypass is on, and requires the guest's confirmed
    bypass-off transition before EDU or virtio-net receives bus-master ownership.
  - Ordinary virtio-net traffic must continue through the enforcing profile. A gate which proves only
    that the IOMMU device enumerated is not isolation evidence.
  - Required hostile cases are:
    1. DMA before endpoint attach faults and leaves a sentinel unchanged.
    2. Failed attach returns no device handle and leaves bus mastering disabled.
    3. The last byte of a mapping is reachable; the first byte after it faults.
    4. Zero-length, unaligned, overflowing, reserved and overlapping IOVA mappings fail atomically;
       numeric IOVA zero is accepted or refused only according to the negotiated input/reserved range.
    5. IOVAs are domain-local: map the same numeric IOVA independently in domains A and B, then unmap
       it only from A. Endpoint A's access faults while B's mapping remains valid and B's sentinel
       cannot be reached or changed by A.
    6. Device write to a to-device/read-only mapping faults while the permitted direction works.
    7. DMA to an old IOVA after unmap/invalidate faults after its frame is allocated to a sentinel.
    8. A driver crash with an in-flight descriptor cannot modify the frame's next owner.
    9. Injected unmap/invalidation failure quarantines rather than recycles the frame.
    10. A stale binding generation cannot map or attach in the replacement domain for the same BDF.
    11. `iommu-required` without a controller refuses bind instead of using untranslated DMA.
    12. A fault flood remains within fixed event-memory and work bounds.
    13. A request to map frames outside the caller's `DmaBuffer` is refused before reaching backend.
    14. A malformed, unknown or mismatched virtio response cannot complete another request; the
        affected attach/map/unmap remains failed and P02M0098's lifecycle keeps the resource safe.

## Dependency order

```text
P02M0098 -> M1 -> M2 -> M3 -> M4 -> M6
                            \-> M5 --^
```

The completed P02M0098 address/lifecycle contract comes first, the controller establishes
enforcement, and only then can binding publication and the two endpoint migrations rely on it. Fault
translation is developed beside backend wiring and must participate in the hostile gate.

## Definition of done

- The x86_64 enforcing profile boots OVMF only through the declared temporary boot bypass, then proves
  the kernel disabled bypass before EDU or the selected virtio-net endpoint receives bus-master
  ownership.
- Each protected bus-mastering endpoint is attached to exactly one live domain. Equal numeric IOVAs
  in different domains resolve independently, and each domain maps exactly the live DMA mappings of
  its current binding generation.
- All fourteen hostile cases fault/refuse at the expected boundary and sentinel memory remains
  unchanged; P02M0098's prerequisite fake-backend gate still covers every generic rollback point and
  unsafe teardown order.
- Clean close, crash, injected failure and restart leave exact expected endpoint, mapping, DMA quota,
  IOVA and quarantine counts, without cross-generation reuse.
- Ordinary virtio-net traffic passes while enforcement is active; no claim is made here for storage,
  display, input, audio or another untranslated endpoint.
- P02M0098's no-IOMMU profile still permits only explicitly declared degraded bindings and never
  labels them isolated.
- `docs/THREAT_MODEL.md` says that a DMA driver leaves the memory-safety TCB only under an enforcing
  profile; `virtio-iommu`, kernel backend and hypervisor remain assumptions. Nothing claims native or
  physical-hardware IOMMU validation.

## What this milestone refuses, and why

- **VT-d, AMD-Vi, ARM SMMU and native RISC-V IOMMU backends.** QEMU exposes models for some, but one
  common paravirtual backend is the bounded first proof. Native discovery, firmware tables, aliases
  and errata each need a separately qualified backend.
- **Physical hardware and non-coherent-DMA qualification.** QEMU can prove map/unmap/fault/lifetime
  logic, not cache maintenance or silicon invalidation behavior.
- **The aarch64 and riscv64 virtio-IOMMU runtime gates, and migration of every existing DMA driver.**
  QEMU advertises both devices there, but device availability is not a tested kernel topology. They
  follow only after this x86_64 EDU/virtio-net slice closes with measured evidence.
- **Interrupt remapping, ATS, PRI, PASID, SVA, SR-IOV or nested translation.** None is necessary to
  confine the current single-function QEMU endpoints and each expands the requester/state model.
- **Protection from a malicious hypervisor or malicious IOMMU implementation.** They enforce the
  boundary being tested and are therefore trusted in this profile.
- **A userspace process with arbitrary map authority.** Moving the mapping oracle out of ring 0 does
  not reduce the property-specific TCB and makes bus-master ordering harder to enforce atomically.
- **Performance optimization.** Huge IOMMU pages, batched invalidation and per-CPU IOVA caches follow
  correctness measurements; they are not allowed to weaken the hostile matrix.
