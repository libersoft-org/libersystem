THE DMA/IOVA CONTRACT MOVED HERE FROM P02M0098, and this milestone is no longer blocked behind it.
It was written there because a driver's DMA is a driver-lifecycle concern, which is true - and it
made the only milestone that was going to implement it wait for a slice nobody was writing. So the
contract, its kernel-owned backend interface, its host fake and the IOMMU-absent policy are M0 and
M0a below, and the first concrete backend that proves them is the same milestone's M1 onward.
P02M0098 keeps what the LIFECYCLE owns: releasing a bound driver's DMA memory in its reset and
containment order, accounting it to a Domain and a binding, and draining it before pages are
refunded.

## Goal

Under a named x86_64 QEMU `virtio-iommu` enforcing profile, each endpoint selected for this first
protected slice - the hostile `edu` fixture and one ordinary `virtio-net` device - can read or write
only the live DMA mappings attached to that endpoint's current binding generation, even when its
driver is buggy or malicious.

Discovery, attach, map, invalidation or teardown failure must end in a refused binding, disabled bus
mastering, or a quarantined device and frames. It must never silently become untranslated DMA.

The security claim is profile-specific:

> In the enforcing QEMU profile, an endpoint which addresses an unmapped page, another endpoint's
> page, a direction-forbidden mapping, or an address revoked from its old binding is stopped by the
> IOMMU and cannot modify the sentinel physical memory behind that attempted access.

This removes each of the two protected endpoints' drivers from the DMA memory-safety TCB for this
profile. Drivers left on P02M0098's explicit untranslated path receive no such claim. The kernel
IOMMU backend, the emulated IOMMU and the hypervisor remain trusted by this claim.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b` and QEMU 10.0.11.

- `DmaBuffer` pins and charges physically contiguous pages and can retain the device-table index for
  which it was created. On driver termination, pages can be held until that device is declared
  quiesced; overflow leaks them deliberately instead of recycling memory a device may still reach.
- PCI bus mastering is disabled after discovery, enabled on the first `DeviceMemory` owner and
  disabled after the last owner. This narrows the active window and is a useful ordering primitive.
- `SYS_DMA_BUFFER_PHYS` still gives a driver a raw physical integer. Binding the buffer to a device
  limits who may ask, but the integer cannot be revoked and the device is not constrained to it.
- `SYS_DEVICE_QUIESCED` trusts the holder's statement that reset completed. The kernel cannot observe
  device-side translations because there is no IOMMU domain, invalidation or fault path.
- There is no generic IOMMU interface, IOVA allocator, endpoint attach/detach, requester-id alias
  model or backend in the tree - and until this milestone was rewritten, no milestone that was
  actually going to write one: P02M0098 owned the contract and was not being worked on, so the only
  implementation waited on a slice with no author. The contract is M0/M0a here now. P02M0098 keeps
  binding identity, generation and the reset/containment order; P02M0099 lists `virtio-iommu`, whose
  one concrete backend and QEMU proof live here.
- QEMU exposes `virtio-iommu-pci` on x86_64, aarch64 and riscv64. It also exposes the PCI `edu` test
  device on all three. Availability in `-device help` is not kernel discovery: today's `DeviceEntry`
  admits only resolved virtio and xHCI functions, so retaining an arbitrary PCI function and making
  EDU's bounded BAR claimable is work THIS milestone does for its own fixture rather than waits for.
  It closes only the x86_64 fixture.
- On the current q35 UEFI boot path, starting with both `default-bus-bypass-iommu=off` and
  `boot-bypass=off` blocks OVMF's SATA access to the boot ISO before the loader runs. The enforcing
  profile must therefore make one measured firmware-to-kernel transition instead of claiming that
  translation can be strict before its driver exists.

## Dependencies and ownership

```text
P02M0098                      P02M0153 (this milestone)
  binding identity              M0  portable directional DMA/IOVA contract
  + generation                  M0a generic backend interface + host fake
  reset/containment                 iommu-required / trusted-untranslated policy
  ordering                            |
     |                                v
     +------------------------->  M1..M6 virtio-iommu backend + QEMU gate
```

WHAT IS STILL P02M0098'S, AND WHAT THIS MILESTONE DOES WITHOUT. Binding identity with a generation
token, and the reset/containment order a crashed driver is torn down in, remain there: they are
about drivers rather than about translation, and this milestone does not recreate them. Where M3
needs a binding generation to attach an endpoint to, it uses the one the device registry already
carries and says so - a mapping bound to a generation that cannot change is a weaker claim than one
bound to a generation that can, and the weaker claim is stated rather than dressed up.

P02M0099 is coordination, not another hard dependency: its `virtio-iommu` inventory row points here,
while this backend reuses the virtio PCI transport already present at today's HEAD. Completion of the
rest of P02M0099's hardware families is unrelated to this gate.

WHY THE SLICE MOVED RATHER THAN THE DEPENDENCY BEING WAIVED. Attaching an endpoint to "the current
driver" is meaningless without binding identity, crash ownership, DMA-address semantics,
fake-backend rollback and reset completion. Three of those five are DMA-address semantics,
fake-backend rollback and the interface they belong to - they are this milestone's subject, they
were written elsewhere, and nothing was implementing them there. The other two stay in P02M0098 and
are used as they are. The point of the move is that a contract lives with the code that proves it,
not that the dependency was inconvenient.

The generic isolation mechanism and `virtio-iommu` security backend are kernel-owned. An ordinary
driver never receives the IOMMU control queue or permission to map arbitrary frames: a userspace
service which could do so would simply become the same memory-safety TCB under another name.

## Definition of done

- The x86_64 enforcing profile boots OVMF only through the declared temporary boot bypass, then proves
  the kernel disabled bypass before EDU or the selected virtio-net endpoint receives bus-master
  ownership.
- Each protected bus-mastering endpoint is attached to exactly one live domain. Equal numeric IOVAs
  in different domains resolve independently, and each domain maps exactly the live DMA mappings of
  its current binding generation.
- Every hostile case faults or refuses at the expected boundary, and it is stated where each one is
  proved rather than counted: cases 1, 3, 5, 6 and 7 run in QEMU against a real emulated device with
  real sentinel memory and are required by name; cases 2, 4, 8 and 9 are host-tested against the fake
  backend, because an injected unmap failure and a driver crash with a descriptor in flight are
  states an emulated device does not offer on demand. P02M0098's prerequisite fake-backend gate still
  covers every generic rollback point and unsafe teardown order.
- Clean close, crash, injected failure and restart leave exact expected endpoint, mapping, DMA quota,
  IOVA and quarantine counts, without cross-generation reuse.
- Ordinary virtio-net traffic passes while enforcement is active; no claim is made here for storage,
  display, input, audio or another untranslated endpoint.
- P02M0098's no-IOMMU profile still permits only explicitly declared degraded bindings and never
  labels them isolated.
- `docs/THREAT_MODEL.md` says that a DMA driver leaves the memory-safety TCB only under an enforcing
  profile; `virtio-iommu`, kernel backend and hypervisor remain assumptions. Nothing claims native or
  physical-hardware IOMMU validation.

## What this milestone refuses, and why

- **VT-d, AMD-Vi, ARM SMMU and native RISC-V IOMMU backends.** QEMU exposes models for some, but one
  common paravirtual backend is the bounded first proof. Native discovery, firmware tables, aliases
  and errata each need a separately qualified backend.
- **Physical hardware and non-coherent-DMA qualification.** QEMU can prove map/unmap/fault/lifetime
  logic, not cache maintenance or silicon invalidation behavior.
- **The aarch64 and riscv64 virtio-IOMMU runtime gates, and migration of every existing DMA driver.**
  QEMU advertises both devices there, but device availability is not a tested kernel topology. They
  follow only after this x86_64 EDU/virtio-net slice closes with measured evidence.
- **Interrupt remapping, ATS, PRI, PASID, SVA, SR-IOV or nested translation.** None is necessary to
  confine the current single-function QEMU endpoints and each expands the requester/state model.
- **Protection from a malicious hypervisor or malicious IOMMU implementation.** They enforce the
  boundary being tested and are therefore trusted in this profile.
- **A userspace process with arbitrary map authority.** Moving the mapping oracle out of ring 0 does
  not reduce the property-specific TCB and makes bus-master ordering harder to enforce atomically.
- **Performance optimization.** Huge IOMMU pages, batched invalidation and per-CPU IOVA caches follow
  correctness measurements; they are not allowed to weaken the hostile matrix.


## Results

### M0/M0a - the contract, and the threat model it exists inside

- **A CRATE, BECAUSE EVERY RULE IN IT IS ABOUT AN OPERATION THAT DID NOT COMPLETE.** `src/dma` holds
  the IOVA space, the direction rules, the mapping lifecycle and the backend interface, and 24 host
  tests drive the orders a booted kernel with an emulated IOMMU cannot produce on demand: an unmap
  that confirms while its invalidation does not, a map refused after its address was reserved, a
  detach that never answers. `fake` is the first implementation of the interface, which is what let
  the real one be a second implementation of something already tested.

- **A FREED ADDRESS IS NOT IMMEDIATELY REUSABLE, AND A QUARANTINED ONE NEVER IS.** The address goes
  back only when the unmap and the invalidation have both completed; either failing takes both the
  address and the frames out of circulation for good. One address is a negligible loss - a device
  reaching a stranger's memory is not.

- **CAPABILITY ISOLATION DOES NOT COVER DMA, said in code rather than in a comment.** `Policy` and
  `decide_bind` have exactly three answers and no fourth, and `dma_policy` records by name every
  device running untranslated. Every device in this tree is `trusted-untranslated` today, which is a
  statement about the tree rather than about the devices - and the boot log now says so on every
  boot.

### M1/M2 - the device, and the transition that turns enforcement on

- **THE WIRE FORMAT IS HOST-TESTED AGAINST ANSWERS THAT ARE WRONG.** 15 further tests: a status code
  from a later specification is never success, a truncated tail is not a status, a fault record with
  no address flag tells the kernel nothing and is dropped while the good record behind it is still
  read. `negotiate` acknowledges only what this code implements, and refuses a device that does not
  offer what an enforcing profile needs.

- **AND THE FIRST REAL BOOT FOUND TWO DEFECTS THE HOST TESTS COULD NOT.** `attach` and `detach` carry
  reserved fields that make them twenty bytes rather than sixteen, and a request four bytes short is
  answered `VIRTIO_IOMMU_S_INVAL` by a device behaving perfectly. Then, with attach working, every
  `map` was refused - because the available ring's index was being advanced by two for a
  two-descriptor chain, so the device also processed the empty slot behind it, ran descriptor zero a
  second time against a scratch page that now held different bytes, and the status the driver read
  was that phantom request's. Both were invisible to a host test and obvious from one QEMU boot.

- **THE TRANSITION IS MEASURED, NOT CONFIGURED.** The profile starts in boot bypass because OVMF
  cannot reach the SATA boot medium without untranslated DMA. The kernel negotiates
  `VIRTIO_IOMMU_F_BYPASS_CONFIG`, disables bus mastering on every PCI function but the controller -
  the firmware's SATA function included - writes bypass off and READS IT BACK. Anything short of all
  of that is a refusal for every `iommu-required` driver, never a degraded continuation.

### M3/M4/M6 - the boundary, proved by a device told to cross it

- **FIVE HOSTILE CASES, AND WHAT IS CHECKED IS THE MEMORY.** QEMU's `edu` device copies between an
  arbitrary physical address and its own buffer on command, which is as close to a malicious driver
  as this tree can get. Each case writes a sentinel pattern into a frame, tells the device to reach
  it, and reads the pattern back: DMA before attach, the byte after a mapping's end, a write to a
  read-only mapping, an address after its mapping was revoked and its frame given to somebody else,
  and the same numeric address mapped in two domains where only one is unmapped. All five are
  refused by the hardware.

- **AND THE SAME FIXTURE WITHOUT AN IOMMU OVERWRITES THE SENTINEL.** That is not a failure - it is
  the hole this milestone exists to close, demonstrated on purpose, and the case asserts it. A
  fixture that could not show the unprotected behaviour would not be evidence of the protected one.

- **THE GATE REFUSES TO PASS ON ENUMERATION.** `qemu-virtio-iommu-x86_64` requires the confirmed
  bypass-off line and each of the five cases BY NAME, and fails if any case reports itself skipped or
  absent - which is exactly what the same boot without a controller produces.

- **AND ORDINARY VIRTIO-NET RUNS THROUGH IT.** The migration needed one bit: a device configured
  with `iommu_platform=on` requires `VIRTIO_F_ACCESS_PLATFORM`, and a driver that does not
  acknowledge it is refused `FEATURES_OK` - which is what "DeviceManager: restarting virtio_net"
  three times over turned out to mean. Acknowledging it is the driver saying the addresses it
  programs are the platform's rather than raw physical ones, and they are: `SYS_DMA_BUFFER_PHYS`
  answers a translated device with the revocable IOVA. Nothing else in the driver changed - its
  rings and packet buffers now carry IOVAs because the syscall that hands them out does.

- **AND A THIRD DEFECT SURFACED WHEN THE GATE STOPPED USING UEFI.** The controller's registers were
  reached at `hhdm + physical`, which is true for RAM and NOT for MMIO - the direct map does not
  cover a BAR. It worked under the UEFI loader, whose page tables are wider, and page-faulted on the
  direct `-kernel` boot the harness actually uses. Working in exactly the profile the gate boots is
  the worst kind of working; the window is now mapped, uncached, at its direct-map address.

- **WHAT REMAINS, AND WHY.** `IOMMU_REQUIRED_TYPES` is empty. The mechanism is there and a kernel
  test drives the refusing arm directly, but putting `virtio-net` in that list removes networking
  from every profile without a `virtio-iommu` - the ordinary harness included. Which profiles a
  system supports is a shipping decision rather than a fact about the driver, and it belongs to
  whoever declares a profile. M3's binding generation is the owner-count transition rather than
  P02M0098's binding token, which that milestone owns and this one does not recreate. M5's fault
  delivery is polled at binding transitions and at boot rather than interrupt-driven. Cases 2, 4, 8
  and 9 of M6's list are host-tested against the fake backend - an injected unmap failure and a
  driver crash with an in-flight descriptor are states an emulated device does not offer on demand.

## Reopened by two outside audits (2026-08-26): a revoke that releases without unmapping, and a case that cannot fail

Two independent audits, read against this milestone's own Definition of done. Every claim was checked
against the source; the ones that did not survive are recorded at the end rather than dropped.

The backend, the bypass-off transition, the IOVA allocator, the domain lifecycle types and the
translated/degraded split are real and stand. Two findings are not cosmetic: the teardown path
releases addresses and frames WITHOUT unmapping them, and the hostile case that exists to prove a
revoked address cannot reach the frame's next owner is written so that it passes whatever the
hardware does.

- [x] **Case 7 is a test that cannot fail.**
  [tests.rs:147-155](../../src/kernel/iommu/tests.rs) allocates `first`, maps it, unmaps it, then
  allocates `next` - and `first` is still alive and still owns its frame, so `next` is a DIFFERENT
  physical frame. The stale translation under test points at `first`'s frame; the assertion reads
  `next.intact()`. The case passes with an IOMMU, without one, and with a backend that ignores every
  unmap. It is the case whose name is "an unmapped address is unreachable once its frame belongs to
  somebody else", and it never puts a second owner on that frame.

  Fix it so the frame really changes hands: drop `first`, allocate `next`, and REQUIRE that `next`
  landed on the same physical address before the transfer is attempted - refusing to claim a result
  if the allocator handed back a different frame, rather than passing quietly as it does now.

- [x] **`revoke_endpoint` releases every IOVA and reports the frames reusable without calling
  `unmap` on any mapping.** [dma/src/lib.rs:648-664](../../src/dma/src/lib.rs) detaches, invalidates,
  and then walks the live and closing mappings marking them `Released` and returning their addresses
  to the space. `finish_close`, twenty lines above it, does the correct thing for a single mapping -
  unmap, then invalidate, then release, and quarantine both on either failure. The teardown path
  skips the first step for all of them.

  That is only safe if the domain is destroyed and never reachable again, and this API does not
  enforce that: the domain stays in `domains`, `set_generation` exists, and an endpoint can be
  attached to it again. Rewrite the order as unmap every mapping, invalidate, await confirmation,
  detach, retire the domain, and only then release the addresses and tell the caller the frames may
  be refunded - with any unconfirmed step leaving addresses AND frames quarantined.

- [x] **The unmap this lifecycle depends on has never completed outside a kernel test, and a boot
  under the enforcing profile shows it failing every time.** Measured 2026-08-26, `./run.sh --iommu`
  on the shipping ISO with eight cores:

  ```
  iommu: 00:0b.0 attached to domain 9
  dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
  dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
  dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
  DeviceManager: restarting virtio_gpu
  ```

  Four times, once per bring-up attempt. The line is
  [dma_buffer/mod.rs:368](../../src/kernel/object/dma_buffer/mod.rs): `DmaBuffer::drop` calls
  `iommu::unmap_for_device`, which does `begin_close` then `finish_close`
  ([iommu/mod.rs:487-494](../../src/kernel/iommu/mod.rs)), and `finish_close` quarantines because
  either `backend.unmap` or `backend.invalidate` did not confirm. `invalidate` is
  `Ok(Confirmed::by_backend())` by construction for this backend, so it is the UNMAP request that
  fails. The encoding is not the cause: `encode_map` and `encode_unmap`
  ([virtio_iommu.rs:184-218](../../src/dma/src/virtio_iommu.rs)) both compute
  `virt_end = virt_start + len - 1`, inclusive and symmetric.

  **Why nothing noticed.** A `DmaBuffer` is dropped only when the driver holding it exits, and every
  driver in an ordinary boot runs for the life of the system. The single exception is a driver that
  is failing - so this path is walked once per boot, by the one process already on its way out, and
  its failure reads as part of that process's collapse. The kernel test that covers unmap passes
  against the EDU fixture, which is what made this look proved.

  Whatever is wrong here is upstream of the two items below it: a teardown order cannot be corrected
  while the step it is ordering does not complete. Find out what the device answers to that request -
  a non-zero status, or no completion at all - before rewriting the order around it.

  Note what this boot also establishes: there is not one `iommu: FAULT` in it, and nine of eleven
  endpoints attach, run and report `dma: every bus-mastering device is translated`. The failure is
  in releasing a translation, not in making or enforcing one.

- [x] **`domain_destroy` in the virtio backend detaches endpoints and leaves the translation entries
  in place.** [virtio_iommu.rs:342-351](../../src/dma/src/virtio_iommu.rs). On its own that is
  defensible if the generic layer unmaps first; combined with the item above, neither layer does it
  and neither holds an authoritative list of what remains. Whichever layer takes the responsibility
  must be the one with the list.

- [x] **Every fault is attributed to `self.attached.first()` rather than to the endpoint the device
  named.** [virtio_iommu.rs:405](../../src/dma/src/virtio_iommu.rs). The endpoint comes out of the
  device's own record; the domain is guessed from whichever pair happens to be first in the vector,
  and the generation is a single backend-wide value. On this milestone's own multi-endpoint profile -
  two `edu` devices and a virtio-net, each in its own domain - every fault line after the first
  device names the wrong domain. Keep an endpoint-to-(domain, generation) map in the backend and
  resolve the decoded endpoint through it.

- [x] **`poll_faults` loops without a bound while its own comment says it does not.**
  [iommu/mod.rs:458-470](../../src/kernel/iommu/mod.rs) says "Bounded, and said plainly: … the drain
  is bounded by the buffer" - the BUFFER is bounded at eight events, and the `loop` around it is not.
  A device that keeps producing events keeps this function running and printing. Give it a total
  ceiling per call, and when it hits the ceiling say how many were left rather than dropping the fact.

- [x] **`IOMMU_REQUIRED_TYPES` is empty, and that has to become a decision rather than a comment.**
  [dma_policy/mod.rs:73](../../src/kernel/dma_policy/mod.rs). The list's own comment argues the case
  honestly - putting `virtio-net` in it removes networking from every profile without a
  `virtio-iommu`, which is a shipping decision - and the mechanism is real and is exercised by a
  kernel test. What is not tenable is closing a milestone titled "confines the first x86_64 QEMU
  endpoints" with no production device type actually declaring that it requires confinement.

  Two ways out, and one has to be chosen: make the policy profile-conditional, so the enforcing
  profile's declared endpoints are `IommuRequired` and every other profile is unchanged; or state in
  the section below that no production type declares it yet, and move the requirement to the
  milestone that turns the enforcing profile on by default. Either is honest. The current state
  reads as the first while implementing neither.

- [x] **The "ordinary virtio-net traffic passes while enforcement is active" evidence is the string
  `NetworkService: online`.** That proves the service started, not that a packet crossed a translated
  DMA path. Send and receive something, and assert on the bytes.

- [x] **Three small API holes that let a caller construct states the types claim are impossible.**
  All three are cheap and all three weaken sentences this milestone wrote:
  - `Requirements` has public fields and no constructor, so `permits`
    ([dma/src/lib.rs:140](../../src/dma/src/lib.rs)) divides by `alignment` and can be handed a zero;
    `len == 0` with `address == 0` underflows `end - 1`.
  - `FaultLog::new(0)` makes `record` call `remove(0)` on an empty vector.
  - `Confirmed::by_backend()` is `pub` while its comment says "Only a backend can construct one of
    these". Every backend is inside the `dma` crate, so `pub(crate)` makes the comment true.

- [x] **The degraded-DMA audit keeps a device that gave the bus back.** Found in an interactive
  boot on 2026-08-26, in two lines one screen apart:

  ```
  devmgr: xhci did not bind; its resources are released and the next candidate follows
  DeviceManager: 10 of 11 device(s) online
  ...
  dma: DEGRADED ISOLATION - 11 device(s) master the bus untranslated (enforcing=false)
  dma:   xhci at 00:04.0
  ```

  `record_degraded` is called from `admit` ([device.rs:157](../../src/kernel/device.rs)) at the
  moment a driver ASKS to master the bus, which is the right moment to take the decision and the
  wrong one to make the record permanent: `release_bus_master` clears the PCI bit and the IOMMU
  attach on the 1 -> 0 transition and there is no path anywhere that removes the row. A driver that
  asked, failed to bind and released is audited forever as reaching memory untranslated.

  This is the list this milestone calls "an audited record of exactly which drivers are running in
  the degraded state", so a wrong count is a wrong claim even though it errs on the safe side. Give
  the record the same lifetime as the bus-master ownership it describes: the row goes when the last
  owner does, and the count then agrees with the device summary printed above it.

### Claims from the audits that did not survive checking, and ones that are answered

- **"The binding generation is a constant."** True and not a defect. `attach_for`
  ([iommu/mod.rs:418](../../src/kernel/iommu/mod.rs)) passes `1`, so a restart that reuses a BDF
  cannot be refused on a stale generation - and the comment beside it says exactly that, and that
  the value is weaker than a real binding token. The real token belongs to the driver lifecycle;
  this is recorded so the milestone that implements it knows this is its call site. The backend now
  stamps each binding with the generation current at ITS attach, so when a real token arrives the
  fault attribution already carries it per endpoint rather than per controller.

- **"Case 3 and case 5 are weaker than claimed."** Partly. Case 3 does not prove its outside sentinel
  is the first physical byte past the mapping, and case 5 does not re-check endpoint B after A's
  unmap. Both are worth strengthening and neither is a false green in the way case 7 is - the
  sentinels are real and are read by a real device. They ride along with the case 7 rewrite.

- **"Only five of the fourteen hostile cases run in QEMU."** True and already stated by this
  milestone: the section above records that cases 2, 4, 8 and 9 are host-tested against the fake
  backend because an injected unmap failure and a driver crash with an in-flight descriptor are
  states an emulated device does not offer on demand. What the Definition of done says - "All
  fourteen hostile cases fault/refuse at the expected boundary AND sentinel memory remains unchanged"
  - reads as fourteen cases in a machine with real sentinels. Reword that line to say which cases are
  proved where, or move the remaining ones into QEMU. Not a defect in the implementation; a defect in
  the sentence.

- **"A malicious device can complete a request the driver never issued, because the virtqueue
  completion checks only the used index."** Confirmed in the code
  ([virtqueue.rs:146-155](../../src/kernel/iommu/virtqueue.rs)) and it belongs here: check the used
  ring's descriptor id and length against what was submitted before treating a request as complete.

## Results of the reopen (2026-08-26)

### What the audits were right about, and what the fix turned out to be

The teardown finding and the live boot were the SAME defect seen from two sides, and the second
side is what named it. `DeviceManager: drop` releases bus mastering before the process's DMA buffers
are dropped, so `revoke_endpoint` ran first, marked every mapping `Released` and handed their
addresses back - and each buffer's own close then found a mapping that was not `Live`, was told
`NotMapped`, and quarantined frames the revoke had already declared reusable. Three frames per
bring-up attempt, four attempts per boot, on the one code path an ordinary boot walks.

The fix is the order the audit asked for and one thing it did not: `revoke_endpoint` now unmaps
every mapping through the backend BEFORE detaching the endpoint - a `virtio-iommu` destroys a domain
when its last endpoint leaves, so an unmap sent afterwards names a domain the device no longer has -
and `Iommu::close` answers a terminal state with the verdict the first owner reached instead of an
error. Order between the two owners no longer matters, which is what a process teardown needs.

### And what neither audit found, because only a boot could

Strengthening the "ordinary traffic" oracle from `NetworkService: online` to a real DHCP lease
turned the gate red immediately: behind the enforcing controller, `virtio-net` transmitted, QEMU's
DHCP server answered, and the guest never saw a packet. Four measurements narrowed it:

| | |
| --- | --- |
| `-object filter-dump` on the netdev | 6 packets - DISCOVER out, OFFER back, ARP both ways. TX works |
| RX slot addresses printed by the driver | `0x4000`, `0x45f6`, `0x4bec` - the IOVAs are correct |
| A counter on the RX interrupt | never fires |
| QEMU's `virtio_iommu_translate` trace | the device never touched the receive ring at all |

The receive ring was at **IOVA 0**. A `virtio` device treats a queue whose descriptor table sits at
address zero as a queue that was never programmed: QEMU's `virtio_init_region_cache` returns early
on a zero address and builds no mapping for the ring, so the device never reads it, never fills a
buffer, never raises an interrupt - and reports nothing, because from its side there is no queue
there. Without a controller the same driver works, because a physical frame is never at address
zero; the IOVA allocator's first fit starts at the negotiated input range's base, which QEMU
publishes as zero.

`IovaSpace::allocate` now never hands out the null address. One line, and it is the whole difference
between the two boots below:

```
network: DHCP unanswered, using static config          <- before
network: configured via DHCP                           <- after
```

**It closes `virtio-gpu` too**, which is the display driver this tree has been unable to run behind
a controller since the profile existed, and which was recorded as a separate unexplained failure:

```
iommu: every domain carries the MSI doorbell at 0xfee00000+0x100000, mapped one to one - a device's interrupt is a memory write and goes through its own domain
iommu: 00:0b.0 attached to domain 9
driver.virtio-gpu: online (00:0b.0)
DeviceManager: 10 of 11 device(s) online, 1 unbound
dma: every bus-mastering device is translated
```

### The doorbell, and the request nobody was sending

Found on the way: `negotiate` had acknowledged `F_PROBE` since this backend was written and nothing
ever sent a probe, so the reserved regions were an empty list by omission. A device's interrupt is a
memory write and goes through its own domain, so the doorbell has to be in it. The backend now sends
the probe, decodes `RESV_MEM` properties, and the kernel maps an MSI region one to one - WRITABLE,
which the first attempt was not: QEMU's trace named it as `flags=1` against an MSI arriving as
`flag=2`. QEMU bypasses the region either way, so this is not what fixed the interrupt; it is what
the specification requires and what a controller that does not bypass will need.

The probe also exposed a transport that read a status out of a buffer whose layout it did not know:
the first successful probe printed `the device refused request type 5 with status 1`, the 1 being
the low byte of a property type. `Transport::request` now takes the status offset.

### What the gate says now

```
qemu-virtio-iommu:   case 1 PASSED
qemu-virtio-iommu:   case 3 PASSED
qemu-virtio-iommu:   case 5 PASSED
qemu-virtio-iommu:   case 6 PASSED
qemu-virtio-iommu:   case 7 PASSED
qemu-virtio-iommu:   a DHCP lease was obtained through the enforcing controller - real packets both ways
```

Cases 3, 5 and 7 are the rewritten ones. Case 7 was the audit's headline finding and it was right:
the old body allocated `first`, unmapped it, then allocated `next` while `first` still owned its
frame - so `next` was a different frame and the assertion was true with an IOMMU, without one, and
against a backend that ignored every unmap. It now releases the frame, requires the allocator to
hand back the SAME one, and reports itself inconclusive rather than passing if it does not. Watched
to fail: with the unmap mutated away, `a device reached an address after its mapping was revoked,
and changed the frame's next owner`.

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED. One of these is a fail-open in the exact place this milestone exists to close.

- [x] **A device that writes nothing at all is read as a device that confirmed the request.**
  `Wire::request` zeroes the device-writable half of the scratch frame before submitting
  ([iommu/mod.rs](../../src/kernel/iommu/mod.rs)); `wait_used` accepts any written length that is not
  GREATER than the buffer, zero included ([virtqueue.rs](../../src/kernel/iommu/virtqueue.rs)); and
  `S_OK` is 0 ([virtio_iommu.rs](../../src/dma/src/virtio_iommu.rs)). A device that completes the
  descriptor and touches no memory therefore returns `Ok(())` for ATTACH, MAP and UNMAP alike, and
  the kernel records an isolation that was never established. The `written > tail_len` check was
  added to stop a device claiming more than it was given; the other end of the range was left open.
  Require the device to have written at least through the status byte, which means `wait_used` has to
  hand back the length rather than a bool.

- [x] **A probe answer that was cut short is used as though it were complete.** `decode_probe` walks
  the property list and `break`s on a truncated header or a length running past the buffer
  ([virtio_iommu.rs](../../src/dma/src/virtio_iommu.rs)), returning whatever it had collected. The
  caller cannot tell a complete list from a truncated one, and what is missing may be a reserved
  region or the MSI doorbell. Report the truncation and refuse the attach - the same rule as the
  status byte, applied to the answer that says which addresses the domain must not use.

- [x] **Reserved regions are printed and not reserved.** `install_probed_regions` maps the MSI
  doorbell one to one and, for `RegionKind::Reserved`, prints a line
  ([iommu/mod.rs](../../src/kernel/iommu/mod.rs)) under a comment reading "the space is told rather
  than trusted to avoid it by accident". The space is not told. `IovaSpace::take_exact`
  ([dma/lib.rs](../../src/dma/src/lib.rs)) is the call that would tell it and it is never made, so
  the allocator can hand out an address inside a hole the device declared unusable.

- [x] **A domain whose row cannot be recorded stays attached in the hardware.** `attach_for` calls
  `attach_endpoint` and, when `DOMAINS.try_reserve(1)` fails, returns `false` and returns
  ([iommu/mod.rs](../../src/kernel/iommu/mod.rs)). The endpoint is attached, a domain exists, and
  nothing knows about either - so `domain_of` answers `None` and the next attempt attaches the same
  endpoint to a SECOND domain. Detach before reporting the failure.

- [x] **The Definition of done still says fourteen hostile cases run where five do.** The audit
  section above recorded this and said what to do - "reword that line to say which cases are proved
  where" - and the line was not reworded. Five run in QEMU and are required by name; 2, 4, 8 and 9
  are host-tested against the fake backend because an emulated device does not offer those states on
  demand. Say that in the DoD instead of a count.

### Second independent audit (2026-08-26): three the first one missed

- [x] **A controller that is on the bus and did not come up is recorded as a machine with no
  controller.** `dma_policy::init` reads `iommu::present()` under a comment saying the question is
  "asked of the bus rather than of the bring-up"
  ([dma_policy/mod.rs](../../src/kernel/dma_policy/mod.rs)) - and `PRESENT.store(true)` happens only
  in the `Ok` arm of `iommu::init`, after `bring_up` succeeded
  ([iommu/mod.rs](../../src/kernel/iommu/mod.rs)). `find_controller` already answered before that.
  So a machine whose controller fails feature negotiation, queue setup or the bypass read-back gets
  `isolation_expected = false`, `policy_for(VIRTIO_TYPE_NET)` answers `TrustedUntranslated`, and the
  protected driver binds DEGRADED instead of being refused. The failure branch prints "every driver
  that requires translation will be refused" one statement before the code makes that false. This is
  the fail-open the whole milestone exists to remove, and the fix is to store `PRESENT` where the
  controller is found rather than where it succeeds. A failed bring-up must also leave nothing half
  configured: reset the device and drop bus mastering before returning.

- [x] **The event queue reads a fixed 24 bytes and ignores what the device wrote.** `poll_used`
  returns a ring slot and discards the used element's `id` and `len`
  ([virtqueue.rs](../../src/kernel/iommu/virtqueue.rs)); `take_event` copies `FAULT_LEN` bytes out of
  the event buffer whatever the device put there, then re-offers the SAME buffer without zeroing it
  ([iommu/mod.rs](../../src/kernel/iommu/mod.rs)). A short report is therefore completed with the
  tail of the previous one, a wrong descriptor id is not noticed, and a device that advances the used
  index without writing has the driver parse stale bytes as a fault. Read the used element's `id` and
  `len`, parse only the bytes the device wrote, and clear the buffer before handing it back. This is
  the same defect as the status byte above, on the queue that was not fixed with it.

- [x] **A fault the device is entitled to report is dropped without a word.** `decode_fault` refuses
  a report with `FAULT_F_ADDRESS` clear and refuses any reason it does not recognise
  ([virtio_iommu.rs](../../src/dma/src/virtio_iommu.rs)), and `drain_faults` turns both into
  `continue` with no log and no count ([virtio_iommu.rs](../../src/dma/src/virtio_iommu.rs)). The
  address flag exists precisely so a device can report a fault whose address it does not know, so
  refusing that report discards the news the fault queue exists to carry. And `decode_status` in the
  same file already gets this right - every code it does not know becomes `Unconfirmed`, "including
  ones added after this was written". Apply the same rule to reasons, accept an address-less report
  as the less detailed thing it is, and if a record really is malformed, say so rather than dropping
  it into silence.

- [x] **The endpoint is probed after it is attached, which is why its reserved holes cannot be
  carved out.** `attach_endpoint` creates the domain with an empty reservation list, attaches, and
  only then probes ([iommu/mod.rs](../../src/kernel/iommu/mod.rs)), under a comment saying the device
  "cannot be asked before the endpoint exists". It can: PROBE names a requester id, which a function
  on the bus has whether or not it belongs to a domain. Probing first is what lets the domain be
  built with its holes already in it, and it is the natural fix for the reserved-region item above
  rather than a second patch beside it. Two smaller things on the same path: an endpoint that reports
  no MSI region at all gets no doorbell mapping and silently loses its interrupts - the same failure
  the identity mapping was added to fix, in the case the property is absent - and `last - start + 1`
  overflows for a region ending at `u64::MAX`.

The audit also reads the specification as forbidding an ordinary MAP of an MSI `RESV_MEM` region,
which is what `install_probed_regions` does today. That contradicts a measurement recorded above in
this file - without that mapping QEMU dropped every interrupt, with its own trace naming
`addr=0xfee00000` as the unmatched translation. Read the specification text before changing it: a
mapping that was added because interrupts stopped arriving is not something to remove on a citation.

Not accepted: masking the reserved bits of a PROBE property type rather than ignoring a property
that has them set - masking is the more permissive reading and the walk is still bounded by the
declared length; and the infallible `push` in the property loop, which is bounded by the probe
buffer the device was given.

## Results (2026-08-26): the two fail-opens, and what they had in common

Every finding of both audits is closed. Two of them were the same mistake in two places, and it is
worth naming because it is the mistake this milestone exists to remove.

**A RANGE CLOSED AT ONE END IS NOT A CHECK.** `wait_used` refused a device that claimed to have
written MORE than the buffer holds and accepted one that claimed to have written nothing - and the
scratch tail is zeroed before every request, and `VIRTIO_IOMMU_S_OK` is zero. So a device that
completed the descriptor and touched no memory returned `Ok(())` for ATTACH, MAP, UNMAP and DETACH
alike, and the kernel recorded an isolation nothing had established and released IOVAs and frames on
the strength of it. `VirtQueue::request` now returns the length rather than a bool, and `Wire`
refuses any completion that did not write through the status byte - compared against the OFFSET the
caller gave, because a probe's status sits after its properties and "some bytes arrived" is not the
same question as "the status arrived".

The event queue had the same shape: `poll_used` answered with a slot index this side computed and
threw away the id and length the DEVICE wrote, and `take_event` copied a whole record out of a buffer
that was never cleared. A short report was completed with the tail of the previous one. Both fields
are now read, only the written bytes are parsed, the buffer is cleared before it goes back, and a
completion naming a descriptor other than the outstanding one is reported and not read.

**AND `present` WAS A FACT ABOUT THE BRING-UP UNDER A NAME THAT SAYS BUS.** `PRESENT.store(true)` sat
in the success arm of `iommu::init`, so a controller that failed feature negotiation, queue creation
or the bypass read-back left `present()` false - and `dma_policy::init` reads exactly that to decide
whether this machine was SUPPOSED to be isolated. The one case a protected driver must refuse became
indistinguishable from a machine that never had a controller, and `virtio-net` bound degraded. The
failure branch printed "every driver that requires translation will be refused" one statement before
the code made that untrue. It is stored where `find_controller` answers now, and a failed bring-up
resets the device and drops its bus-master bit rather than leaving a half-configured master behind.

**AND MOVING IT SPLIT ONE QUESTION INTO THE TWO IT ALWAYS WAS.** Three callers read `present` to
decide whether to USE a controller - attach an endpoint before bus mastering, detach it after, map a
DMA buffer through it - and with the value now true on a machine whose controller failed, all three
would have reached for one that is not there. They want a different question: `translating` answers
whether the controller CAME UP, and `present` answers whether the machine has one. The policy that
decides what a failure MEANS wants the second; everything that wants to talk to hardware wants the
first. They were one value for as long as a failed bring-up was indistinguishable from no hardware.

**THE PROBE MOVED IN FRONT OF THE ATTACH,** which is what let the reserved holes be carved out at
all. The old order created the domain whole, attached, then probed - so the answers arrived after the
address space existed and the reserved regions were printed instead of reserved, under a comment
saying the space "is told rather than trusted to avoid it by accident". It was not told. A PROBE
names a requester id, which a function on the bus has whether or not it belongs to a domain, so the
domain is now built from the answer. A truncated property list is refused rather than trimmed, a
region ending at the top of the address space no longer wraps to a zero length, and an endpoint that
reports no MSI region at all gets this port's own doorbell rather than silently losing its
interrupts.

**AND AN ATTACH THAT COULD NOT BE RECORDED IS UNDONE.** `try_reserve` failing after a successful
attach used to return `false` and walk away, leaving the endpoint translating under a domain nothing
tracked - so the next attempt built a second one for the same endpoint.

A fault report the controller is entitled to send is no longer discarded: an address-less report is a
real fault reported in less detail, and a reason this code cannot name is `Unconfirmed`, which is the
rule `decode_status` in the same file has always used for status codes.

The Definition of done says where each hostile case is proved rather than counting to fourteen.

## What the 2026-08-28 audit found

Six findings. Three fixed - including the one that mattered - three open.

FIXED:
1. **An unconfirmed MAP released its IOVA and its physical frames.** `Fault::Unconfirmed`'s own
   definition says "the kernel does not know the state of the hardware, so nothing may be released",
   and both map paths released for EVERY error under a comment asserting nothing was installed. A
   controller could install a translation, lose its reply, and the kernel would hand the frame to the
   next owner. `Iommu::map_failed` now quarantines the IOVA on `Unconfirmed` (recording a
   `MappingState::Quarantined` mapping so the accounting sees it) and releases only on a refusal;
   `DmaBuffer::create_for` LEAKS the frames deliberately, counted through `note_lost_pages`, and does
   not refund the charge - the same answer this kernel already gives a dead driver's frames whose
   device was never confirmed stopped.
2. **Domains were never destroyed.** `Backend::domain_destroy` had no caller, so failed binds
   accumulated domains and consumed ids. `Iommu::destroy_domain` retires a domain and its terminal
   mappings, and REFUSES one still holding a quarantined mapping - forgetting that would hand back an
   address space on exactly the evidence that says not to. `attach_endpoint` now destroys the domain
   when the attach fails.
3. **A failed MSI-doorbell mapping continued into a bus-mastering binding.** `install_doorbell`
   logged and returned, `attach_endpoint` reported success, and `device::claim` enabled bus
   mastering for a binding known not to receive interrupts. It is now fallible and the caller rolls
   the domain back, so the claim fails - the refusal the rule asks for.

OPEN:
- M0's portable bounce/coherency contract is described and not implemented: `Plan::Bounce` has no
  consumer, `Requirements::coherent` is never read, there are no `sync_for_*` operations.
- IOMMU faults are printed and never reach the binding lifecycle, and `detach_for` revokes before
  draining so attribution is lost (`DomainId(0)`, `Generation(0)`) on the path that most needs it.
- The mapping/IOVA/fault counters are read only by the DMA crate's own tests; `DomainStats` exposes
  none of them, so M4's restart baseline cannot be asserted through the integration.
