# P02M0149 - A provider was rebuilt, its consumer was not, and only the packager noticed

Status: OPEN. BUILD CORRECTNESS. NOT A PHASE-2 COMPLETION GATE.

## Goal

Find out how a staged library can keep a provider digest that no longer matches the provider beside
it, close that hole, and make the failure say what it is.

## What is there now

Measured on 2026-08-24, from a riscv64 build that stopped in packaging.

- **THE PACKAGER REFUSED A TREE THE BUILDER HAD JUST CALLED FINISHED.** `./build.sh --arch riscv64`
  reported `libs`, `user` and `kernel` as built and then `mkpackages` panicked:

  ```
  assertion `left == right` failed: audio-proto identity provider chain
    left:  ["provider=base-proto:b0ca983c...", "provider=ipc-client:646a2a13...", ...]
    right: ["provider=base-proto:1e1e89a8...", "provider=ipc-client:a47592e4...", ...]
  ```

  `left` is what the staged `audio-proto.lslib` RECORDS about the providers it was built against;
  `right` is the digest of those provider artifacts as they are staged now. They disagree.

- **THE FILE DATES SAY WHAT HAPPENED.** In the same staged tree:

  | file | staged |
  | --- | --- |
  | `lib/protocol/audio-proto.lslib` | 2026-08-23 10:33 |
  | `lib/protocol/base-proto.lslib`  | 2026-08-24 00:46 |

  A provider was replaced and a library that records its digest was not. Twenty-three of the
  sixty-five staged `.lslib` files predated that day's builds; forty-two were fresh.

- It is not a one-off: two consecutive incremental builds produced the identical failure. Deleting
  `.build/image/riscv64gc-unknown-none-elf` and rebuilding fixed it, and the rebuilt
  `audio-proto.lslib` is the same size as the one it replaced - so the library's own compilation had
  not changed. What was stale was the provider digest inside it.

- **THREE OBVIOUS EXPLANATIONS DO NOT FIT, and each was checked rather than assumed:**
  - *A cache shared between architectures.* It is not:
    `artifact_cache_dir="$build_root/cache/$target"`.
  - *A cache key that ignores providers.* It does not: a library's key is a digest over its EXPECTED
    IDENTITY RECORD - which contains `provider=<name>:<digest>` for each provider - plus the
    compiled rlib's own sha. A provider whose identity changed should move its consumer's key.
  - *Consumers built before providers.* They are not: the builder takes its library list in the
    order `system-manifest.sh library-crates` prints it, and `base-proto` is 19th while
    `audio-proto` is 43rd. The provider was built first, so the consumer's expected identity should
    have been computed against the new one.

- **WHAT IS NOT KNOWN IS THE MECHANISM, and the evidence was destroyed by the fix.** Deleting the
  staged tree was the right operational move and it removed the only instance of the broken state
  anyone has seen. Nothing in this milestone should be written as though the cause were known.

- **WHAT CAUGHT IT WAS AN ASSERTION IN THE PACKAGER**, three steps after the inconsistency was
  created, and it is the reason nothing shipped. It is also all that stands there: the library
  builder reported success on the very rows that were wrong.

- **AND IT REFUSES WITHOUT SAYING WHAT TO DO.** What a person sees is a Rust panic and two lists of
  sixty-four-character digests. It does not say which artifact is stale, that the staged tree is
  inconsistent, or that deleting it is the way out - all three of which had to be worked out from
  file dates.

## Work

- [ ] **M1 - Reproduce it deliberately.**
  - Nothing here can be fixed against a state that no longer exists. Build a tree, make a provider's
    bytes change without changing any source file in a consumer's dependency closure, and see
    whether the consumer survives as a cache hit.
  - The provider identity is computed from the artifact ON DISK, so the interesting inputs are the
    ones that change a provider's bytes without changing its sources: a different toolchain, a
    different feature set from an earlier configuration, a partially built tree, an interrupted run.
    THE LAST TWO ARE THE LIKELY ONES here - the tree that failed had been built by `scenario-cold
    riscv64` under `LIBER_DEVELOPMENT=1` hours earlier.
  - If it cannot be reproduced, that is the finding, and this milestone becomes M3 alone.

- [ ] **M2 - The builder refuses what it has just made inconsistent.**
  - Whatever M1 finds, the library phase can ask the packager's question at the point the answer is
    cheap: every staged provider's identity matches what each consumer recorded. It reads staged
    files and digests, which the phase has already computed.
  - CHECKED, NOT ASSUMED AWAY. The cache is what makes an incremental build worth having; this does
    not remove it, it makes the build prove the invariant the cache is supposed to preserve.

- [ ] **M3 - The refusal names the artifact and the way out.**
  - `mkpackages` says which library is stale, which provider it was built against, which provider is
    staged, and that the staged tree for that target is inconsistent - not two digest lists.
  - The message ends with the command that fixes it, because the fix is not obvious: remove
    `.build/image/<target>` and rebuild.

## Definition of done

- Either the mechanism is named and closed, or the attempt to reproduce it is written down with what
  was tried.
- A build that would stage a library against a provider it was not built against fails in the phase
  that stages it.
- The failure names the artifact, both digests' owners and the command that clears it.

## What this milestone refuses, and why

- **Weakening the packager's assertion.** It is the only thing that noticed. It stays exactly as
  strict; what changes is where the same question is asked first and how the answer reads.
- **Rebuilding everything every time.** The incremental library build is what keeps a change to one
  tool from costing a whole userspace, and this is a missed invalidation rather than a reason to
  stop caching.
- **Deleting the staged tree automatically on a mismatch.** A builder that silently discards the
  evidence of its own inconsistency is how a mechanism stays unknown - which is exactly the position
  this milestone starts from.
