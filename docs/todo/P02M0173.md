# P02M0173 - Virtio-IOMMU enforces the AArch64 and RISC-V QEMU profiles

Status: PLANNED AFTER P02M0172. AARCH64/RISCV64 QEMU SECURITY SLICE. NOT A NATIVE-IOMMU OR PHYSICAL-HARDWARE CLAIM.

## Goal

Extend the already implemented generic DMA/IOVA and virtio-IOMMU contract from the x86_64 QEMU
profile to the current AArch64 and RISC-V QEMU machines. On each named enforcing profile, every
driver-owned bus-mastering endpoint in that profile must use only live IOVA mappings in its own
binding domain; a failed controller, attach, mapping or bypass transition must never fall back to
untranslated DMA.

P02M0153 already owns the portable contract, backend, fault model and first hostile x86_64 proof.
P02M0159 already makes the ordinary x86_64 QEMU run translated. This milestone reuses both and owns
only the missing emulated topology, endpoint rollout and gates on the other two architectures.

## Current profile boundary

At the current tree the relevant QEMU PCI bus masters are the virtio block, network, GPU,
keyboard/tablet, serial/console and sound functions plus qemu-xHCI. The RISC-V UEFI fixture also has
a firmware-only NVMe ESP. The implementation must derive the exact closed endpoint set from the
harness/registry and fail when a new bus master is added without a policy and enforcement decision;
the prose list is not an allow-list, and the census is per profile rather than the union of every
conditional test/interactive/development device. Ramfb and other non-mastering devices do not acquire
a fake DMA requirement merely because they appear in the same machine.

The executable profile matrix is fixed here so "AArch64 and RISC-V" is not inferred from one lucky
boot:

| profile | required evidence |
| --- | --- |
| AArch64 direct, GICv2+v2m, 4 CPUs | complete hostile EDU gate plus ordinary shipping endpoint effects |
| AArch64 direct, GICv3+ITS, 4 CPUs | enforcing transition, translated endpoint MSI-X delivery through the ITS, and ordinary DMA effects |
| AArch64 AAVMF/UEFI, GICv2+v2m, 4 CPUs | firmware boot-bypass transition, then enforcing storage/network boot |
| RISC-V direct, AIA/IMSIC, 4 CPUs | complete hostile EDU gate plus ordinary shipping endpoint effects |
| RISC-V U-Boot/UEFI, AIA/IMSIC, 4 CPUs | firmware/NVMe quiesce and boot-bypass transition, then enforcing boot |

The existing AArch64 GICv3-without-ITS interrupt profile has no supported PCI MSI backend. It remains
an architecture-profile boot, but it may not be labelled DMA-isolated: an `iommu-required` endpoint
there remains unbound rather than silently untranslated. Test, interactive and development variants
carry separate generated endpoint censuses wherever their devices differ.

## Work

- [ ] **M1 - the named profiles have explicit enforcing QEMU topologies.** Add
  `virtio-iommu-pci` before the endpoints it translates, mark every protected virtio endpoint with
  `iommu_platform=on`/`VIRTIO_F_ACCESS_PLATFORM`, and keep requester identities stable and visible.
  Convert every protected RISC-V virtio PCI function to modern-only (`disable-legacy=on`) in the same
  harness transaction: QEMU cannot offer `VIRTIO_F_ACCESS_PLATFORM` through its current transitional
  or legacy mode, so adding only `iommu_platform=on` is a configuration that cannot negotiate.
  Give AArch64 and RISC-V the same explicit `--no-iommu` escape as x86_64. Controller presence,
  endpoint options and boot-bypass state are produced in one harness path so an endpoint cannot be
  added behind the controller without the matching access-platform decision. Every enforcing
  AArch64 machine explicitly sets `default-bus-bypass-iommu=off`; relying on QEMU's root-bus default
  is not an enforcement contract, and the opposite-setting mutation must fail the gate.

- [ ] **M2 - the portable backend is made genuinely portable, not copied.** Exercise PCI ECAM
  discovery, requester-ID derivation, reserved ranges and the backend's current polled request/event
  queue completion and fault draining on each supported ECAM port. Separately prove that translated
  endpoint MSI-X doorbells map and arrive through GICv2m, GICv3+ITS and IMSIC on the matrix rows that
  claim those interrupt paths; a polled controller queue is not evidence for endpoint interrupt
  delivery. Remove any q35 address, LAPIC, MSI-routing or root-complex assumption found in the shared
  virtio-IOMMU backend. Direct-root functions are the supported topology; unmodelled bridge aliases
  are refused rather than guessed. Keep the IOMMU's own pinned bootstrap queues kernel-owned as
  P02M0153 requires. If interrupt-driven control/event delivery is introduced, it is a shared-backend
  change and the x86_64 gate must cover it too; non-x86 rollout does not require that expansion.

- [ ] **M3 - bypass ends before a driver can master the bus.** Start with boot bypass only where
  firmware/direct boot needs it. At kernel handoff, quiesce every endpoint the firmware used and
  disable bus mastering for every non-controller function, initialize the controller, turn bypass
  off and read it back, then attach, map and finally re-enable each admitted endpoint. A firmware-
  touched virtio device reaches status zero and confirms reset before BME is cleared; the RISC-V UEFI
  NVMe path clears `CC.EN` and observes `CSTS.RDY=0`, or completes a supported function/controller
  reset, before BME readback. Clearing BME alone does not drain work already issued by firmware. If
  the kernel has no safe reset path, that UEFI enforcing profile refuses rather than assumes
  quiescence.

  Remove the current AArch64 early virtio-blk exception from enforcing profiles: it probes before
  normal device/IOMMU initialization, enables BME and places physical queue addresses in the device.
  Either relocate/convert that bootstrap access behind confirmed IOMMU initialization and
  `DmaAddress`, or do not execute it on the enforcing path. The transition gate rejects any kernel
  BME or DMA before bypass-off except the IOMMU's documented pinned bootstrap queues. A machine which
  cannot complete the whole sequence refuses all DMA-capable bindings in the enforcing-required
  profile rather than falling into P02M0172's explicit trusted degraded profile.

- [ ] **M4 - every current DMA driver consumes `DmaAddress` on these profiles.** Reverify the
  current block, network, display, input, console, sound and xHCI paths with the policy produced by
  P02M0172. No descriptor or controller register for an enforcing binding receives raw physical
  disclosure. Mapping, unmapping, invalidation, crash/reset and generation rollover use the existing
  P02M0153/P02M0098 lifecycle; architecture work may not invent a second teardown order. The profile
  reports zero driver-owned untranslated endpoints after all bindings settle. Re-run the shared host
  fake for failed attach/map/invalidation, crash/in-flight teardown and stale binding generation;
  these are software lifecycle states which QEMU cannot be required to manufacture on demand. The
  host/protocol gate also proves the fault-drain per-call limit, malformed-event handling and explicit
  dropped/remaining accounting; one posted QEMU event buffer cannot deterministically prove that
  software work bound.

- [ ] **M5 - every matrix row is independent evidence.** Give all five profile rows separate catalog
  keys, commands, result logs and measured costs, and mark all five as release-required in the same
  canonical catalog P02M0170's dossier consumes; optional architecture umbrella names are never the
  planner's indivisible step. The canonical AArch64-direct-GICv2+v2m and RISC-V-direct-AIA rows boot EDU
  and prove the architecture-sensitive hardware cases: DMA before attach; another domain's IOVA; the
  byte after a mapping; a direction-forbidden write; an old IOVA after confirmed unmap; and a bounded
  sequence of repeated denied DMA. That sequence proves unchanged sentinel memory, continuing
  enforcement and containment of the offending endpoint; M4, not QEMU queue timing, proves the
  per-call fault-work bound. The other rows prove their distinct controller-delivery or firmware
  transition without pretending to inject the host-fake-only states from M4. A mutation which leaves
  bypass on or uses a physical address must fail for the intended assertion.

- [ ] **M6 - ordinary endpoints work while translation is active.** On each architecture, prove
  real block I/O and network traffic and exercise each profile's display/input/audio/USB service
  effects where its endpoint census says those devices are present. Require the controller's bypass-
  off readback, one live domain per bound endpoint, no IOMMU fault, no degraded admission and no
  missing current bus master. Enumeration or an `Online` status alone is not the oracle.

- [ ] **M7 - enforcing becomes ordinary only after every affected profile gate passes.** Match the
  x86_64 policy: the supported ordinary direct and UEFI AArch64/RISC-V `run.sh` rows above contain
  the controller and require translation; `--no-iommu` selects P02M0172's explicit loud degraded
  boot-profile value and matching no-controller topology in the same trusted harness path. Keep a
  dedicated untranslated regression rather than silently removing the only test of no-controller
  behavior. Profiles without the interrupt support needed by the controller are named as unsupported
  for enforcement rather than inheriting the claim from another row.

## Dependencies

- P02M0098 and P02M0161-P02M0166 own binding identity, rollback, teardown and reporting.
- P02M0153 owns the generic contract and virtio-IOMMU backend.
- P02M0159 owns the default/degraded QEMU policy pattern.
- P02M0170 owns the revision-bound release dossier; its catalog-derived required set consumes this
  milestone's five profile keys whether P02M0170 lands before or after them.
- P02M0172 must first remove the hard-coded DMA-policy list.

## Definition of done

- The named AArch64 and RISC-V QEMU profiles confirm bypass off and have no driver-owned
  untranslated bus master.
- Hostile EDU access is stopped by the emulated IOMMU on both architectures, while real current
  devices continue to produce their observable effects.
- Missing/broken enforcement refuses required bindings, and `--no-iommu` remains explicit and loud.

## What this milestone refuses

- VT-d, AMD-Vi, ARM SMMU, a native RISC-V IOMMU, firmware-table qualification or real hardware.
- ATS, PRI, PASID, SVA, SR-IOV, interrupt remapping, nested translation or performance tuning.
- Protection from a malicious hypervisor/IOMMU implementation; QEMU is part of this profile's TCB.
