# P02M0173 - Virtio-IOMMU enforces the AArch64 and RISC-V QEMU profiles

Status: PLANNED AFTER P02M0172. AARCH64/RISCV64 QEMU SECURITY SLICE. NOT A NATIVE-IOMMU OR PHYSICAL-HARDWARE CLAIM.

## Goal

Extend the already implemented generic DMA/IOVA and virtio-IOMMU contract from the x86_64 QEMU
profile to the current AArch64 and RISC-V QEMU machines. On each named enforcing profile, every
driver-owned bus-mastering endpoint in that profile must use only live IOVA mappings in its own
binding domain; a failed controller, attach, mapping or bypass transition must never fall back to
untranslated DMA.

P02M0153 already owns the portable contract, backend, fault model and first hostile x86_64 proof.
P02M0159 already makes the ordinary x86_64 QEMU run translated. This milestone reuses both and owns
only the missing emulated topology, endpoint rollout and gates on the other two architectures.

## Current profile boundary

At the current tree the relevant QEMU PCI bus masters are the virtio block, network, GPU,
keyboard/tablet, serial/console and sound functions plus qemu-xHCI. The RISC-V UEFI fixture also has
a firmware-only NVMe ESP. The implementation must derive the exact closed endpoint set from the
harness/registry and fail when a new bus master is added without a policy and enforcement decision;
the prose list is not an allow-list, and the census is per profile rather than the union of every
conditional test/interactive/development device. Ramfb and other non-mastering devices do not acquire
a fake DMA requirement merely because they appear in the same machine.

The executable profile matrix is fixed here so "AArch64 and RISC-V" is not inferred from one lucky
boot. Each ROW IS A COMPOSITE of named boot phases, because the hostile and the ordinary evidence
cannot come from the same artifact: `edu` is `#[cfg(test)]` and exists only in the test kernel, and a
test boot runs `test_main()` and exits before production userspace ever starts, so a test kernel
cannot exercise a shipping driver and a shipping kernel cannot host `edu`. The x86_64 gate is already
built this way - one hostile test-kernel boot and a second shipping-image boot - and this milestone
copies that shape rather than inventing a single-boot version of it.

| profile row | phase | artifact | required evidence |
| --- | --- | --- | --- |
| AArch64 direct, GICv2+v2m, 4 CPUs | hostile | test kernel | complete hostile EDU gate |
| | ordinary | shipping image | shipping endpoint effects, zero untranslated bus masters |
| AArch64 direct, GICv3+ITS, 4 CPUs | transition | test kernel | enforcing transition, translated endpoint MSI-X through the ITS |
| | ordinary | shipping image | ordinary DMA effects |
| AArch64 AAVMF/UEFI, GICv2+v2m, 4 CPUs | transition | shipping image | firmware boot-bypass transition after quiesce |
| | ordinary | shipping image | enforcing storage/network boot |
| RISC-V direct, AIA/IMSIC, 4 CPUs | hostile | test kernel | complete hostile EDU gate |
| | ordinary | shipping image | shipping endpoint effects, zero untranslated bus masters |
| RISC-V U-Boot/UEFI, AIA/IMSIC, 4 CPUs | transition | shipping image | firmware/NVMe quiesce and boot-bypass transition |
| | ordinary | shipping image | enforcing boot |

Every phase names its own artifact digest, topology, endpoint census, effect oracle and result log.
A row is green only when every one of its phases is; a row with a missing phase is a failure and not
a partial pass. The test, interactive and development variants change the emulated endpoint set, so
each variant that a phase actually boots carries its own generated census - the base census is not
allowed to stand in for a development-only bus master.

The existing AArch64 GICv3-without-ITS interrupt profile has no supported PCI MSI backend. It remains
an architecture-profile boot, but it may not be labelled DMA-isolated: an `iommu-required` endpoint
there remains unbound rather than silently untranslated.

## Work

- [ ] **M1 - the named profiles have explicit enforcing QEMU topologies.** Add
  `virtio-iommu-pci` before the endpoints it translates, mark every protected virtio endpoint with
  `iommu_platform=on`/`VIRTIO_F_ACCESS_PLATFORM`, and keep requester identities stable and visible.
  Convert every protected RISC-V virtio PCI function to modern-only (`disable-legacy=on`) in the same
  harness transaction: QEMU cannot offer `VIRTIO_F_ACCESS_PLATFORM` through its current transitional
  or legacy mode, so adding only `iommu_platform=on` is a configuration that cannot negotiate.
  Give AArch64 and RISC-V the same explicit `--no-iommu` escape as x86_64. Controller presence,
  endpoint options and boot-bypass state are produced in one harness path so an endpoint cannot be
  added behind the controller without the matching access-platform decision.

  PIN THE UPSTREAM HOST BRIDGE ON BOTH ARCHITECTURES, with the property each machine actually has.
  Every enforcing AArch64 machine explicitly sets the `virt` machine's `default-bus-bypass-iommu=off`.
  RISC-V `virt` does not have that machine property: the equivalent is the GPEX host bridge's own
  `bypass-iommu`, so the enforcing RISC-V topology explicitly forces `gpex-pcihost.bypass-iommu=off`.
  Reading the virtio-IOMMU controller's own bypass byte as off does not prove that the upstream PCI
  host routes endpoint DMA through the controller, so relying on either machine's default is not an
  enforcement contract - the qualified QEMU currently defaults GPEX bypass to off, which is exactly
  the kind of fact that can change under the gate without anything failing. Assert the effective
  topology, add the opposite-setting mutation on both architectures, and record the QEMU capability
  and version through P02M0170 so a version without the property REFUSES rather than silently
  omitting it.

- [ ] **M2 - the portable backend is made genuinely portable, not copied.** Exercise PCI ECAM
  discovery, requester-ID derivation, reserved ranges and the backend's current polled request/event
  queue completion and fault draining on each supported ECAM port. Separately prove that translated
  endpoint MSI-X doorbells map and arrive through GICv2m, GICv3+ITS and IMSIC on the matrix rows that
  claim those interrupt paths; a polled controller queue is not evidence for endpoint interrupt
  delivery. Remove any q35 address, LAPIC, MSI-routing or root-complex assumption found in the shared
  virtio-IOMMU backend. Direct-root functions are the supported topology; unmodelled bridge aliases
  are refused rather than guessed. Keep the IOMMU's own pinned bootstrap queues kernel-owned as
  P02M0153 requires. If interrupt-driven control/event delivery is introduced, it is a shared-backend
  change and the x86_64 gate must cover it too; non-x86 rollout does not require that expansion.

- [ ] **M3 - bypass ends before a driver can master the bus.** Start with boot bypass only where
  firmware/direct boot needs it. At kernel handoff, quiesce every endpoint the firmware used and
  disable bus mastering for every non-controller function, initialize the controller, turn bypass
  off and read it back, then attach, map and finally re-enable each admitted endpoint. A firmware-
  touched virtio device reaches status zero and confirms reset before BME is cleared; the RISC-V UEFI
  NVMe path clears `CC.EN` and observes `CSTS.RDY=0`, or completes a supported function/controller
  reset, before BME readback. Clearing BME alone does not drain work already issued by firmware.

  xHCI IS NOT COVERED BY EITHER PROCEDURE AND IS PRESENT IN BOTH UEFI TOPOLOGIES: qemu-xHCI is
  attached with USB keyboard, tablet and storage, and firmware may have initialized it and issued
  transfers. The only xHCI reset sequence in this tree lives in the userspace driver, which starts
  long after the transition it would have to protect. So the enforcing UEFI profiles require an
  EARLY pre-transition xHCI halt and reset - run stop, wait for HCHalted, reset, wait for the
  controller-not-ready bit to clear - with register readback and a bounded timeout, before BME is
  cleared for that function. A gate fails when the sequence is absent or times out. If that early
  sequence cannot be implemented safely, remove qemu-xHCI and its USB devices from the enforcing
  UEFI topology, or refuse that profile; quiescence is never inferred from BME alone.

  If the kernel has no safe reset path for any firmware-touched endpoint, that UEFI enforcing profile
  refuses rather than assumes quiescence.

  Remove the current AArch64 early virtio-blk exception from enforcing profiles: it probes before
  normal device/IOMMU initialization, enables BME and places physical queue addresses in the device.
  Either relocate/convert that bootstrap access behind confirmed IOMMU initialization and
  `DmaAddress`, or do not execute it on the enforcing path. The transition gate rejects any kernel
  BME or DMA before bypass-off except the IOMMU's documented pinned bootstrap queues. A machine which
  cannot complete the whole sequence refuses all DMA-capable bindings in the enforcing-required
  profile rather than falling into P02M0172's explicit trusted degraded profile.

- [ ] **M4 - every current DMA driver consumes `DmaAddress` on these profiles.** Reverify the
  current block, network, display, input, console, sound and xHCI paths with the policy produced by
  P02M0172. No descriptor or controller register for an enforcing binding receives raw physical
  disclosure. Mapping, unmapping, invalidation, crash/reset and generation rollover use the existing
  P02M0153/P02M0098 lifecycle; architecture work may not invent a second teardown order. The profile
  reports zero driver-owned untranslated endpoints after all bindings settle. Re-run the shared host
  fake for failed attach/map/invalidation, crash/in-flight teardown and stale binding generation;
  these are software lifecycle states which QEMU cannot be required to manufacture on demand. The
  host/protocol gate also proves the fault-drain per-call limit, malformed-event handling and explicit
  dropped/remaining accounting; one posted QEMU event buffer cannot deterministically prove that
  software work bound.

- [ ] **M5 - every matrix row is independent evidence, and every phase within it is too.** Give all
  five profile rows separate catalog keys, commands, result logs and measured costs, and mark all
  five as release-required in the same canonical catalog P02M0170's dossier consumes; optional
  architecture umbrella names are never the planner's indivisible step.

  Because a row spans two artifacts, each PHASE gets its own subkey, artifact digest, endpoint
  census and result log, and the row is the declared composite of them. P02M0170's dossier binds
  every constituent artifact and result, and REJECTS a row with any missing phase rather than
  reading the row's exit code. One green row key may never bind hostile evidence from a test kernel
  to shipping-driver claims, or shipping effects to a kernel that cannot run `edu`.

  The HOSTILE PHASES of the AArch64-direct-GICv2+v2m and RISC-V-direct-AIA rows boot the test kernel
  with EDU and prove the architecture-sensitive hardware cases: DMA before attach; another domain's
  IOVA; the byte after a mapping; a direction-forbidden write; an old IOVA after confirmed unmap;
  and a bounded sequence of repeated denied DMA. That sequence proves unchanged sentinel memory, continuing
  enforcement and containment of the offending endpoint; M4, not QEMU queue timing, proves the
  per-call fault-work bound. The other rows' phases prove their distinct controller-delivery or
  firmware transition without pretending to inject the host-fake-only states from M4. A mutation
  which leaves bypass on or uses a physical address must fail for the intended assertion.

- [ ] **M6 - ordinary endpoints work while translation is active.** On each architecture, prove
  real block I/O and network traffic and exercise each profile's display/input/audio/USB service
  effects where its endpoint census says those devices are present. Require the controller's bypass-
  off readback, one live domain per bound endpoint, no IOMMU fault, no degraded admission and no
  missing current bus master. Enumeration or an `Online` status alone is not the oracle.

- [ ] **M7 - enforcing becomes ordinary only after every affected profile gate passes.** Match the
  x86_64 policy: the supported ordinary direct and UEFI AArch64/RISC-V `run.sh` rows above contain
  the controller and require translation;
  AND THE DEVELOPMENT ROW FLIPS WITH THEM, WHICH THIS ITEM DID NOT SAY (added 2026-09-02). P02M0172
  ships THREE non-x86 rows at the produced `no-iommu` value - the two public ones and the DEVELOPMENT
  one - and records that this milestone is not done until it has flipped all three alongside the
  topology. This item named only the ordinary `run.sh` rows, so both sides could have been satisfied
  while the development carrier still said `no-iommu` on a machine that now has a controller - which
  is precisely the controller/mode mismatch P02M0172's M6 refuses, on the boot a developer uses most.
  So the development row is flipped here too, and it has the same oracle as the others: after the
  flip, a development boot on AArch64 or RISC-V carries `enforcing-required`, prints that every
  bus-mastering device is translated, and ADMITS an `iommu-required` driver. Its pre-transition half
  belongs to P02M0172 and is already written there; `--no-iommu` selects P02M0172's explicit loud degraded
  boot-profile value and matching no-controller topology in the same trusted harness path. Keep a
  dedicated untranslated regression rather than silently removing the only test of no-controller
  behavior. Profiles without the interrupt support needed by the controller are named as unsupported
  for enforcement rather than inheriting the claim from another row.

## Dependencies

- P02M0098 and P02M0161-P02M0166 own binding identity, rollback, teardown and reporting.
- P02M0153 owns the generic contract and virtio-IOMMU backend.
- P02M0159 owns the default/degraded QEMU policy pattern.
- P02M0170 owns the revision-bound release dossier; its catalog-derived required set consumes this
  milestone's five profile rows and their per-phase subkeys, and its class model must accept a
  composite row, whether P02M0170 lands before or after them.
- P02M0172 must first remove the hard-coded DMA-policy list.

## Definition of done

- The named AArch64 and RISC-V QEMU profiles confirm bypass off - at the controller AND at the
  upstream PCI host bridge, explicitly set rather than defaulted - and have no driver-owned
  untranslated bus master.
- Hostile EDU access is stopped by the emulated IOMMU on both architectures, while real current
  devices continue to produce their observable effects, each proven by its own named phase against
  its own named artifact.
- Every firmware-touched endpoint in an enforcing UEFI profile is quiesced by a procedure written
  for its device class before bus mastering is cleared, or that profile refuses.
- Missing/broken enforcement refuses required bindings, and `--no-iommu` remains explicit and loud.
- All THREE of P02M0172's non-x86 rows carry `enforcing-required` when this milestone is done - the
  two public ones and the development one - each with the post-transition admission fixture above.
  Added 2026-09-02: the obligation was written on P02M0172's side alone, so this milestone could have
  met its own definition of done and left the development carrier mismatched against its new
  topology.

## What this milestone refuses

- VT-d, AMD-Vi, ARM SMMU, a native RISC-V IOMMU, firmware-table qualification or real hardware.
- ATS, PRI, PASID, SVA, SR-IOV, interrupt remapping, nested translation or performance tuning.
- Protection from a malicious hypervisor/IOMMU implementation; QEMU is part of this profile's TCB.
- A single-boot profile row. A row that claims both hostile and shipping evidence is two phases, and
  collapsing them to make one command shorter is the defect this matrix exists to prevent.
