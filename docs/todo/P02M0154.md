Status: COMPLETE again (2026-08-26). Every finding of the two outside audits is closed. The batch
configuration now reaches a batch of two and a cover proves it; the invariants are stated over every
location and per object rather than over the first of each and over the whole machine; the published

HOST/QEMU-CLOSABLE.

## Goal

Give the security-critical handle and channel state machines a small executable specification,
explore all states inside published finite bounds, and check that the implementation follows the same
transaction boundaries under ordinary use, allocation refusal, user-copy failure and process
teardown.

The claim this milestone may make is deliberately finite:

> For each published TLC configuration, every reachable model state satisfies the listed authority,
> linear-transfer, stale-handle, queue and accounting invariants; corresponding kernel traces and
> mutation tests show that the Rust implementation uses the modeled commit and rollback order.

This is stronger than an informal design argument and weaker than a proof of the complete kernel.
TLC explores a bounded abstraction, the conformance layer observes selected implementation events,
and QEMU exercises the actual syscall boundary. None of those facts proves unmodeled code, unsafe
Rust, assembly, the compiler, hardware or executions outside the stated bounds.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b`.

- `HandleTable` uses generation-tagged opaque handles, checks object type and rights on lookup,
  attenuates duplicated capabilities, retires a slot before its generation can wrap, and charges
  installed handles to a Domain.
- A transfer has an explicit reserved source slot: `take_for_transfer` must be followed by exactly
  one of `commit_taken` or `restore_taken`. Concrete receiver slots and quota are booked before a
  message is removed from a channel.
- Multi-capability send returns all taken capabilities on failure. Receive names the message it
  peeked, reserves the required slots, takes that exact message and copies its payload. A payload-copy
  failure before commit returns the message to the queue head. On success the actual order is
  `commit_delivery`, install capabilities into the pre-booked slots, then copy their raw handle numbers
  to userspace. A handle-number copyout failure is therefore POST-COMMIT: the payload stays delivered,
  the message cannot return, and every installed handle is closed so no unpublished capability leaks.
- `close_all`, a transfer racing process termination, reservation rollback, queue accounting and
  message identity all have focused regression tests. The unusually detailed comments record bugs
  already found at these boundaries.
- `ObjectHeader::revoke` is test-only. The production authority model therefore has stale handles
  after slot reuse and object destruction, but no production syscall which globally invalidates all
  derived capabilities. Documentation must not turn the test helper into a global-revocation claim.
- There is no executable security specification, exhaustive finite state search, implementation-to-
  model trace, or mutation gate proving that these tests are capable of detecting a widened right,
  duplicated transfer, resurrected handle or skipped rollback.

No physical device is involved in this property. The model closes on the host, the full syscall
conformance scenario closes in x86_64 QEMU, and aarch64/riscv64 run only their architecture-specific
pre- and post-commit usercopy fault seams.

## Property boundary

The modeled state includes only the authority-bearing and transactional pieces needed for this
claim:

```text
Process / Domain
  -> handle table: Free | Live | TransferReserved | Booked | Retired, plus Closed
  -> handle quota charge

Capability
  -> object identity + object type + rights + captured object generation

Channel endpoint
  -> bounded ordered queue + identified message held for delivery
  -> queued-byte charge + reserved queue slot

Message
  -> identity + bounded payload size + ordered capability batch
  -> queued | held-before-commit | committed-with-local-caps
     | committed-with-unpublished-handles | finished
```

The model represents allocation and user-copy outcomes nondeterministically. Payload-copy failure
before commit and handle-number copyout failure after commit are different transitions with different
ownership outcomes. It models arbitrary interleaving between enabled actors, including
close/termination between every transfer phase. It does not model the allocator, scheduler, page
tables or byte-copy implementation internally.

Rights are a finite set containing at least `USE`, `DUPLICATE` and `TRANSFER`. `USE` abstracts a
type-correct object operation; it is not a claim that every concrete syscall's rights table is
complete. Object types are distinct atoms so type sealing is checked rather than assumed.

Production behavior and the test-only object-generation revocation helper use separate model
configurations. The production result must not cite the revocation configuration until a production
revocation API, authority policy and implementation exist.

  - `StaleHandlesStayDead`: close/recycle changes the slot generation, exhaustion retires the slot,

  - `QuotaConserved` and `QueueBounded`: charges equal the resources they represent, and queued plus

## Required negative matrix

1. Duplicate asks for one right absent from its source and is refused without a new handle.
2. Use through a capability of the wrong object type is refused even when its rights bits match.
3. A closed and recycled raw handle never reaches the replacement object.
4. A generation at its maximum retires its slot and never wraps to an old handle.
5. A second thread cannot take a `TransferReserved` source handle.
6. A successful non-duplicating send leaves authority in the queued message and not the sender.
7. Full queue, closed peer, quota refusal and allocation refusal restore the complete ordered batch.
8. Closing the sender during rollback cannot resurrect a live source-table handle.
9. Destination reservation failure leaves the identified message queued and charges unchanged.
10. Two receivers cannot peek one message and commit another, even when sizes and cap counts match.
11. Partial payload copy returns the same message to the head and installs no capability.
12. Handle-number copyout failure after commit consumes the message and leaves the payload delivered,
    but closes every installed handle and leaves neither an unpublished prefix nor leaked booking.
13. Closing the destination during delivery cannot install into its closed table.
14. Queue depth counts a message held by an uncommitted receive, so concurrent send cannot overfill.
15. A delivered or dropped message refunds its queued-byte charge exactly once.
16. Closing an endpoint releases every queued capability and charge without allocating during drop.
17. A capability cannot acquire ambient authority merely by sharing an object or Domain identity.
18. Test-only object revocation rejects an old snapshot, while the production report makes no global-
    revoke claim.

## Results

Measured on 2026-08-24.

- **M1 - THE MAP IS FROZEN, AND IT IS `docs/spec/capability/MODEL_MAP.md`.** Six handle-slot states
  (`Free | Live | TransferReserved | Booked | Retired`, plus the table-wide `Closed`) named against
  the fields that represent each; seven ownership phases for a capability with the Rust value that
  physically holds it in each, including the one that only exists after the point of no return -
  COMMITTED BUT UNPUBLISHED, where the handle is installed and its number has not reached userspace;
  three ledgers with the exact call that moves each entry; and fourteen model actions with the lock
  that makes each atomic.

- **AND THE POINT OF THE EXERCISE IS THE GAPS BETWEEN THEM.** Two locks are two actions however
  transactional the helper's name: `sys_channel_send` takes the handle table, releases it, then
  takes the peer's inbox, so a send is at least three actions with interleaving points between them.
  Each of those points is written down with what may arrive there - an allocation failure, a user
  copy that faults, a process termination - because a specification whose actions are too coarse
  proves something about a kernel this is not.

- **THE LEDGER RULES WERE READ OUT OF THE CODE RATHER THAN ASSUMED.** A take does not refund and a
  restore does not charge; the refund is at `commit_taken`, at `abandon_taken`, or at
  `restore_taken` INTO A CLOSED TABLE, which is the case where there is nobody to give the
  capability back to. `insert_reserved` charges nothing because `reserve` already paid. A model that
  charged at install would disagree with the implementation for the whole window a termination can
  land in.

- **M2 - THE SPIKE RUNS, IT IS MEASURED, AND THE FIRST THING IT DID WAS FAIL ON A REAL DEFECT.**
  `docs/spec/capability/` holds `Capability.tla` (what a slot, a capability, a message and a charge
  ARE - no variables, no actions), `Transfer.tla` (the transitions and the invariants) and
  `spike.cfg`. TLC 2.19 is pinned by SHA-256 in `toolchain.lock`; `./bootstrap.sh` is the one command
  that fetches and verifies it, watched to refuse both ways - an absent artifact and a corrupted one.
  The spike explores 7621 distinct states to depth 24 in 1.8 s and every invariant holds, without
  fairness. `MEASUREMENTS.md` records the counts, the digests and the TLC and Java versions, because
  a later run that explores fewer states is a different result.

- **WHAT IT FOUND: `close_all` RETURNS BOOKED SLOTS TO THE FREE LIST.** `QuotaConserved` violated in
  three states - `Init`, `Book`, `Terminate`. `HandleTable::close_all` rebuilds the free list from
  every slot that is not `reserved`, and a BOOKED slot - one `reserve` took out of circulation and
  `insert_reserved` has not used yet - is not `reserved`. The index lands on the free list while
  `booked` still names it, so an install and the next insert can be handed the same slot; and the
  handle quota `reserve` charged is refunded by nobody, because `close_all` refunds the slots that
  HAD a capability and `Drop` refunds the LIVE ones. Two actions, found exhaustively, on a path no
  test in this tree walks. The fix follows the rule already in that function - a booking is no more
  `close_all`'s to reclaim than a transfer is - and is P02M0154's first implementation change rather
  than something the model merely describes.

- **AND THREE THINGS ABOUT THE MODEL, WHICH IS THE OTHER HALF OF WHAT A SPECIFICATION IS FOR.**
  Modeling the fix made TLC reject the model until it was faithful: a post-commit copyout failure
  refunding a handle somebody else had already closed (the kernel's `close` checks the slot's
  GENERATION and refuses, which is why its `let _ = close(..)` is right); `release_reservation`
  enabled in the middle of a delivery, which neither of its two call sites is; and a receive whose
  capabilities were all dropped under a closing table being unable to end, when the payload was
  delivered and the count still has to be written.

- **M3 - THE SECOND CONFIGURATION, AND WHAT ITS FIRST SHAPE COST.** `handles.cfg` is the spike with
  ONE lever moved: the minted capability carries `DUPLICATE`, so `HandleTable::duplicate` is
  reachable and the rights algebra is exercised rather than merely defined; a second object type
  comes with it because type sealing is vacuous where there is one type to ask for. 1039839 distinct
  states, depth 31, 79 s. `TransferIsLinear` is deliberately NOT checked there - it counts one
  authority in one place, which is exact only while nothing duplicates - and splitting the
  configuration is M3's rule rather than weakening the invariant under its own name.

- **AND THE RULE EARNED ITSELF IMMEDIATELY.** The first `handles.cfg` widened four dimensions at once
  - three slots, three generations, two types, and a duplicate quantified over EVERY subset of the
  minted rights - and produced 37 million states in six minutes with three million still queued,
  killed rather than finished. The committed shape moves duplication alone, keeps the spike's slot
  and generation bounds, and offers a duplicate two right sets instead of eight: keep everything, and
  narrow to one.

- **AND THE THIRD CONFIGURATION SEPARATES THE TEST HELPER FROM THE PRODUCTION CLAIM.**
  `revoke-test-only.cfg` is the only one where `ObjectHeader::revoke` exists at all - the others set
  `RevocationModeled` false, which REMOVES the action rather than leaving it disabled behind a
  guard, and the spike's state count being identical either way is how that is visible. 30484
  distinct states, depth 26, 3.7 s. `RevokedSnapshotCannotOperate` is stated over the GUARD rather
  than over an outcome, so a mutation that drops the generation check fails it: removing
  `cap.objgen = objgen` from `Usable` makes TLC report the violation in two states, `Init` and
  `Revoke`, and restoring it passes. An invariant nobody has seen fail is a sentence, not a check.

- **M3 (COMPLETE) - SIX CONFIGURATIONS, EACH ONE MEASURED LEVER FROM ANOTHER.** `spike` (the
  transfer racing a close), `handles` (duplication reachable, a second object type),
  `revoke-test-only` (the helper that exists only in tests), `transactions-single` (a queue with room,
  so "off the queue and still holding its slot" and "the queue is full" stop being the same state),
  `transactions-batch` (`BatchMax = 2`, the smallest configuration in which "returns ALL of them" is
  a different sentence from "returns it") and `propagation` (three processes, so a capability is
  passed ALONG rather than just across). Every count, depth, runtime, peak and digest is in
  `MEASUREMENTS.md`, with the gate budget: about two and a half minutes at four workers, of which
  `propagation` is half.

- **AND THE MOST EXPENSIVE ONE IS THE THIRD PROCESS.** Every action is quantified over the process
  set, so a third actor multiplies the interleavings rather than adding to them - three million
  states against the spike's twelve thousand. It is kept because a two-process model cannot express
  a chain at all, and its rights algebra is ONE derivation rather than every subset, which is where
  the cost would have stopped being affordable. That is M3's rule applied rather than quoted.

- **M4 - ALL FOURTEEN NAMED INVARIANTS ARE WRITTEN AND CHECKED.** `TransferIsLinear`,
  `AuthorityNeverWidens`, `NoForgery`, `TypeSealing`, `StaleHandlesStayDead`, `QuotaConserved`,
  `QueueBounded`, `SlotOwnershipUnique`, `PostCommitCopyoutIsTerminal`, `ClosedProcessCannotResurrect`,
  `ReceiveIsTransactional` and `MessageIdentityStable`, plus the step property
  `GenerationsOnlyAdvance`, `RevokedSnapshotCannotOperate` in the configuration that models the
  test-only helper, and `FailedSendRestores` - stated as the contract `take_for_transfer` promises:
  a slot is `Reserved` only while its process holds the capability that came out of it, so no
  outstanding batch means no reservation left behind. That is "exactly one of commit, restore or
  abandon follows" seen as a state rather than as a sequence.

- **AND MODELLING THE BATCH FOUND TWO RULES THE CODE HAS AND THE MODEL DID NOT.** Turning one
  transfer-local capability into a SEQUENCE made TLC index past the end of one - the model being
  wrong rather than the kernel - twice: a take may not start a second batch after the message is
  queued (the capabilities have left, their slots are still reserved, and appending there produces a
  capability in hand whose slot nobody is holding), and a take is bounded by the RESERVATIONS
  outstanding rather than by what is in hand. The syscall takes everything it will send and then
  sends; it never takes another after the send.

- **AND THE GATE IS A GATE.** `check.sh --gate capability-model` (31 gates now, mirrored in
  `verify-model`, selected by a kernel change because the specification is a model OF the kernel)
  runs every published configuration with NO NETWORK: it re-checks the JAR against the pin before
  running it - the bootstrap verified what it FETCHED, this verifies what it is about to RUN, and a
  cache is writable in between - and when the artifact is absent it prints `./bootstrap.sh
  tla2tools` rather than reaching for a mirror. Watched to refuse: with the JAR moved aside the gate
  fails by name.

- **AND IT KEEPS THE MODEL CHECKER'S SCRATCH OUT OF THE TREE, which cost something to learn.** TLC
  writes its state queue to a `states/` directory beside the specification unless it is told
  otherwise - 1.5 GB for the configuration that exploded, one file per queue segment, in a directory
  git reports as untracked. An editor's file watcher tried to diff them and crashed on every one.
  The gate passes `-metadir .build/tlc/<config>`, `.gitignore` catches a bare `tlc2.TLC` run that
  does not, and neither is a thing anybody would have thought to write down before it happened.

- **M6 (MODEL HALF) - SIX DEFECTS, EACH CAUGHT BY THE INVARIANT THAT NAMES IT.**
  `check.sh --gate model-mutations` (35 gates) breaks the specification on purpose, one rule at a
  time, on a copy: a generation that WRAPS instead of retiring (`GenerationsOnlyAdvance`), a
  duplicate that may widen (`AuthorityNeverWidens`), a transfer that CLONES rather than moves
  (`TransferIsLinear`), a rollback into a closed table that installs anyway
  (`ClosedProcessCannotResurrect`), a receive that takes whatever is at the head rather than the
  message it inspected (`MessageIdentityStable`), and an install that does not consume its booking -
  which leaves an index Live and booked at once, and is `SlotOwnershipUnique`. Each mutation must
  match EXACTLY ONCE: one that matches nothing is a gate that has quietly stopped testing, which is
  the failure the mutations exist to catch, in the tool that catches it.

- **AND ONE MUTATION NEEDED ITS CONFIGURATION CHANGED TO BE REACHABLE AT ALL.** "A duplicate may
  widen" is unbreakable where no widening derivation is on offer - the action is simply disabled -
  so that mutation narrows the minted rights too. A mutation that cannot be reached proves nothing
  about the invariant that would have caught it, and noticing the difference is the whole point.

- **NINE COVER PROPERTIES, EACH REQUIRED TO BE REFUTED.** Written as their own negations - "this
  never happens" - so TLC has to produce the behaviour that does it: a published receive, a
  post-commit copyout failure, a PRE-commit payload failure, a restore, an abandon, a drop into a
  closed table, generation retirement, a close racing a transfer, and a capability delivered to
  another process. An invariant that passes because its dangerous action is never enabled is a
  failed gate, and nothing in a passing run says which of the two happened.

- **AND THE FIRST COVER RUN FOUND THE MODEL WAS NOT EXPLORING ITS OWN PRE-COMMIT FAILURE.**
  `PayloadCopyFails` was defined, commented, and absent from the transition relation. Every
  invariant had been passing over a model in which a receive could not fail before its commit -
  which is one of the two outcomes this milestone exists to distinguish. `NoPayloadFailure` could not
  be refuted, which is exactly what a cover is for; with the action in `Next` the spike grows from
  38316 states to 45092 and everything still holds.

- **AND THE GHOST THE COVERS READ IS A CONFIGURATION'S CHOICE.** `outcome` triples a state space
  wherever it is on, and reaching a transition is proved as cheaply in the smallest configuration as
  in the largest: with it on, `propagation` costs 10.7 million states and five minutes; off, it is
  back to three million and constant. `CoversModeled` is off there and on where the covers run.

- **WHAT REMAINS IN M6:** mirroring rights widening, stale generation, transfer clone, closed-table
  restore and wrong-message identity against the QEMU conformance fixture.

### M5 - the kernel's own trace, replayed against the model

- **THE SINK RECORDS SIXTEEN ACTIONS AND NOTHING ELSE.** `src/kernel/object/trace.rs` is a fixed
  4096-entry ring of all-integer records - action, outcome, party, slot, generation, rights, message
  identity. No pointers, no payload bytes, no object addresses: a trace carrying them is a trace
  nobody could publish. It is allocation-free because it runs INSIDE the paths it observes, under
  the locks they already hold, and a full ring stops recording and says so - a truncated trace that
  claimed to be complete would be a clean bill of health over the part that fitted.

- **THE EMIT POINTS ARE THE MODEL'S ACTIONS, ONE FOR ONE.** `take_for_transfer`, `commit_taken`,
  `restore_taken`, `abandon_taken`, `reserve`, `release_reservation`, `insert_reserved` (both arms),
  `close`, `close_all`, and the five channel ones. Writing them exposed a real defect: `abandon_taken`
  called `commit_taken`, so every abandon emitted BOTH - a trace saying one transfer resolved twice.
  The shared half is now `resolve_taken` and each action emits its own.

- **NINE RUNS PER SUITE: ONE HAND-WRITTEN, EIGHT SEEDED.** The hand-written fixture drives each
  fault class deliberately, because a seeded walk finds interleavings but does not promise to reach
  the rollback that happens once in a thousand schedules. The eight seeded schedules then drive the
  same operations in an order a splitmix64 stream decides, which is where the interleavings nobody
  thought of come from. Both are deterministic: the trace is byte-identical across runs, which is
  what makes a committed reference worth anything.

- **THE CHECKER REFUSES TWELVE DELIBERATE DEFECTS.** `src/tools/trace-check` replays each run against
  a hand-written mirror of the model's guards. A checker that accepts everything passes every run it
  will ever see, so before it is trusted with a real trace it must refuse: a take without TRANSFER, a
  take presenting a stale generation, a take of an empty slot, a transfer resolved that was never
  taken, an install against no booking, a refused restore in a table that never closed, an
  install-into-closed in a table that is open, a dequeue of a message nobody inspected, a message
  returned after its delivery committed, a capability placed into a slot a transfer is holding, a
  capability placed into a closed table, and a trace that never reaches a rollback at all.

- **AND THE FIRST RULE IT ENFORCED WAS WRONG.** A capability appearing outside the transfer protocol
  was refused if the table had already stepped - which reads as forgery until a seeded schedule
  creates a second object, which every real process does. `Transfer.tla` follows ONE capability, so
  its `Init` is per-capability rather than per-table; the rule is now what `NoForgery` actually says,
  that a placed capability may not displace a live one, may not land in a slot a transfer is holding,
  and may not appear in a table that has closed. `MODEL_MAP.md` records the boundary.

- **THE GATE RUNS WITHOUT QEMU AND STILL CANNOT GO STALE.** `check-capability-trace.sh` runs the
  mutation suite against a normalized reference committed under `docs/spec/capability/trace/`, and
  where a guest log exists it holds the live trace against that reference and fails on a difference.
  Message and channel identities are renumbered by first appearance, since the raw ones come from
  counters that have been running since boot.

- **WHAT THIS IS NOT.** Sampled trace refinement over a selected boundary: 382 steps across nine runs,
  every one an enabled model step, every fault class covered at least once. It does not show that
  every model trace is a Rust execution, and no number of runs would.

### M6 - the same five defects, in the kernel

- **FIVE DELIBERATE KERNEL DEFECTS, EACH CAUGHT BY THE ASSERTION WRITTEN AGAINST IT.** A duplicate
  that may widen, a slot that answers to a handle from a previous generation, a take for transfer
  that clones rather than moves, a restore into a closed table that produces a live handle, and a
  receive that takes the head rather than the message it named. `check-implementation-mutations.sh`
  applies each one, builds and boots the kernel, and requires the conformance fixture to fail by the
  named assertion.

- **NOTHING WRITES A SOURCE FILE IN THE WORKING TREE.** The suite compiles the kernel from source, so
  a mutation has to live in a file somewhere - and somebody may be editing this tree while the gate
  runs. It works on a copy at a fixed path under `.build`, fixed rather than temporary so cargo's
  fingerprints stay valid and the second mutation onwards is an incremental kernel build. Userspace,
  the packages and the volume are seeded from what this tree already built, since only `src/kernel`
  changes.

- **AND THE FIXTURE NEEDED THREE MORE SCENARIOS TO EARN THE CLAIM.** Written first, the fixture
  caught only two of the five: nothing in it asked whether a duplicate may widen, whether a recycled
  slot answers to the old handle, or whether a receive naming a superseded message takes what
  replaced it. A test that still passes its mutation does not support the claim, so the fixture now
  counts capabilities across BOTH tables after a transfer (a clone leaves two), asserts a closed
  table acquires nothing from a restore, and drives a receive against a queue that moved under it.

- **THE ONE THAT CAUGHT ITSELF ON THE SECOND ASSERTION, NOT THE FIRST.** Removing the generation
  check does not make a closed handle resolve: the slot holds no capability, so the lookup fails
  either way. It is the slot's REUSE that brings the old handle back to life, and only an assertion
  made after the reuse can see it. The gate names that assertion, because naming the other one would
  have been a mutation the fixture appeared to catch for the wrong reason.

- **AND EACH MUTATION RUNS THE FIXTURE ALONE.** Three of the five are also caught by tests that run
  earlier in the suite - good news about the suite, and no evidence at all about the fixture this
  milestone built. `TEST_SELECTION` names the one test, so what fails is what was being tested.

- **AND REGISTERING THE GATE FOUND THREE THAT WERE ALREADY WRONG.** `trust-profile`, `signed-boot`
  and `secure-boot` were catalogued as covering `boot.loader`, which is not a component - the
  component is `bin.libersystem-loader`. `verify-model` had been failing on all three since they were
  added, in the silent direction: a check nothing selects.

### M7 - the syscalls, driven the way userspace drives them

- **SIX TESTS UNDER A TAG OF THEIR OWN.** `capability-tcb` on x86_64: two threads over one handle
  table and one endpoint; a user buffer that stops existing partway through a receive, at each side
  of the commit point; every refusal a transfer has; a destination at its handle quota; two receivers
  racing for one message; and termination at each of the four transfer phases. `object::tests` drives
  the Rust API and is what the trace records - these drive the SYSCALLS, and check the state they
  leave from outside the operation that was supposed to preserve it.

- **THE FAULT IS REAL, NOT INJECTED.** Two adjacent user pages with only the first mapped put a copy
  in exactly the state a mid-copy unmap leaves behind. Before the commit the message goes back to the
  queue whole and the caller is told; after it the message cannot go back, so the handles that were
  installed are closed instead - and the Domain's handle count is what proves they were, because a
  handle whose number the caller was never given is one it can never close.

- **AND TWO ASSERTIONS EXIST ONLY TO SAY THE RACE HAPPENED.** A sender that runs to completion before
  its receiver starts passes every other assertion in the two-thread test. The endpoint is one message
  deep and both threads count their waits, so a run in which they took turns instead of contending
  fails on the counters rather than passing quietly. The same for the two receivers: each counts what
  it took, and a run where one did all the work and the other watched is a failure.

- **ONE PREMISE WAS WRONG, AND THE TEST SAID SO.** The two-receiver test first required a receive to
  be REFUSED as superseded - which cannot happen at that interface: `SYS_CHANNEL_RECV_CAPS` takes no
  message id, because `receive_transactionally` peeks and takes the head by identity inside one
  decision. What a caller can observe is that nothing is delivered twice and nothing is lost, and that
  is what it now asserts; the identity refusal itself is exercised directly against `recv_identified`,
  where a caller CAN name a message that is no longer at the head.

- **AND SO WAS AN ASSERTION ABOUT QUOTA.** "A send while the destination is at its quota is refused
  too" - it is not, and it must not be: a transfer MOVES a capability, so the take refunds the unit
  the message will cost and a table with no room to create anything can still hand over what it holds.
  That is `QuotaConserved` seen from outside, and the test now says so.

- **AND THE OTHER TWO PORTS NEEDED NO PORT-SPECIFIC CASE.** The user-buffer test is written against
  `memlayout::USER_VA_END` and `arch::paging::map_page` rather than against x86 addresses, so the
  same fixture runs through each port's own exception-table seam unchanged: all thirteen
  `capability-tcb` tests pass on aarch64 and on riscv64, the partial-copy case among them. A case
  written per port would have been three fixtures asserting the same thing, and the one that differs
  between them - which instruction faults and how far it got - is `extable`'s subject and has its own
  per-port tests.

- **AND THE STALE REFERENCE WAS CAUGHT BY ITS OWN GATE.** Strengthening the conformance fixture in M6
  changed the trace it emits, and `capability-trace` refused the tree until the committed reference was
  refreshed - which is the failure mode that gate was written for.

## Dependency order

```text
M1 -> M2 -> M3 -> M4 -> M5 -> M6 -> M7
```

The executable state relation and measured spike precede the published bounds and any meaningful
invariant result. The focused QEMU fixture then precedes its implementation mutations, and the full
QEMU gate closes only after those mutations show that both the model and implementation checks detect
the faults they name.

This milestone has no dependency on P02M0153. IOMMU/DMA isolation changes which drivers belong to the
memory-safety TCB; it does not change the handle/channel transfer invariants modeled here.

## Definition of done

- The checked-in model and measured configurations reproduce their recorded digests, state counts and
  invariant results with the pinned Java/TLC artifact. A fresh checkout has one documented,
  checksum-verifying bootstrap step; after it (and in CI from the same cache key), verification runs
  with networking disabled.
- Every listed invariant holds in all applicable published configurations, and every deliberate
  mutation fails with the expected invariant and a retained minimal counterexample.
- The traceability table names the Rust lock/commit/failure boundary behind every model action; every
  implementation trace is accepted by that relation and every modeled rollback class is exercised.
- Every model-applicable negative case is represented in the host model/cover matrix. Concrete-only
  properties such as exact copyout, error values and allocation-free endpoint drop are asserted by the
  full tagged x86_64 syscall/regression scenario. Aarch64 and riscv64 run only the focused pre-commit
  payload-fault and post-commit handle-copyout-fault cases at their usercopy seam. No text claims that
  host tests execute the target-specific kernel binary.
- Closing, failure and termination return handle, booking, queue and Domain counters to their exact
  expected ownership state. A pre-commit failure restores the message; a post-commit copyout failure
  keeps the payload delivered while closing every unpublished handle. No capability is duplicated,
  leaked or installed in a closed process.
- `docs/THREAT_MODEL.md` and capability/IPC documentation state the finite model bounds, fairness
  assumptions, tool version, abstraction gaps and test-only revocation status beside the result.
- No document calls the kernel, IPC subsystem or TCB "formally verified". The accepted wording is a
  machine-checked bounded model plus implementation trace and QEMU conformance evidence.

## What this milestone refuses, and why

- **A proof of the complete kernel or complete TCB.** Scheduler interleavings are abstracted, and
  allocators, page tables, unsafe code, assembly, compiler and hardware are outside this model.
- **An unbounded theorem.** Exhaustive finite state search is valuable because its exact bounds are
  published; it is not induction over arbitrary processes, slots, messages or executions.
- **Production global or selective revocation.** The current generation bump is test-only and no
  derivation tree exists. A real revocation policy and syscall would need their own authority and
  lifecycle design before this model could make that claim.
- **The PermissionManager policy graph.** It decides which named capabilities bootstrap code grants;
  this milestone checks what the kernel does once a capability exists. Policy-to-runtime wiring keeps
  its existing audit gates.
- **DMA containment.** A capability to a device is not a hardware DMA firewall. P02M0153 owns the
  QEMU `virtio-iommu` security boundary.
- **Timing, covert-channel or denial-of-service freedom.** Queue and quota bounds are safety/resource
  invariants, not a proof of fair scheduling, constant time or absence of resource contention.
- **A home-grown proof engine.** The repository owns the specification, configurations, trace adapter
  and gates, not a new model checker whose correctness would become another unreviewed assumption.

- [x] **`transactions-batch.cfg` cannot reach a batch of two, so the all-or-nothing rule it exists for
  is only ever checked over a batch of one.** The configuration
  ([transactions-batch.cfg](../spec/capability/transactions-batch.cfg)) sets `Objects = {o1}`,
  `MintedRights = {"USE", "TRANSFER"}` and `DerivedRights = {}`, and `Init`
  ([Transfer.tla:63-90](../spec/capability/Transfer.tla)) mints exactly one capability into one slot.
  With no `DUPLICATE` and no derivation, a second authority-bearing capability never exists.
  `BatchMax = 2` is a ceiling, not a reachable state. `Book(p)` is additionally guarded on
  `Len(booked[p]) = 0`, so the receive side cannot reserve two slots either.

  Its own header comment says "Two objects, because a batch of one object twice is a batch a
  duplicate-source check refuses" - the configuration below the comment does not do that. The
  duplicate-source refusal the comment names is unreachable too.

- [x] **`TransferIsLinear` is stated over the whole system, so it cannot survive the fix above.**
  [Transfer.tla:476](../spec/capability/Transfer.tla) is
  `CopiesInSlots + CopiesInXfer + CopiesInQueue + CopiesInHeld =< 1` - at most one authority-bearing
  capability ANYWHERE. Two independent capabilities for two objects is a legal state that this
  invariant reports as a violation. Linearity has to be per capability instance: give a capability an
  instance identity independent of the object id, and require that at most one authority-bearing copy
  of each instance exists. Without that, the configuration cannot be widened and the invariant cannot
  be kept at the same time.

- [x] **Three invariants quantify over the first queued message and the first capability in it, and
  this is NOT vacuous.** [Transfer.tla:465](../spec/capability/Transfer.tla) counts
  `Len(queue[1].caps)` and nothing else; `AuthorityNeverWidens`
  ([:483](../spec/capability/Transfer.tla)) reaches `queue[1].caps[1]`; `NoForgery`
  ([:488](../spec/capability/Transfer.tla)) covers slots and `xfer` and omits the queue and the held
  message entirely. `transactions-single.cfg` runs with `QueueLimit = 2`, so a second queued message
  genuinely exists in that search and none of the three looks at it. Quantify all of them over every
  queued message, every capability in each, the held message, both transfer buffers and the slots.

- [x] **`TypeSealing` does not record the type the operation asked for.**
  [Transfer.tla:554](../spec/capability/Transfer.tla) requires `lastUse.type \in Types` and
  `"USE" \in lastUse.rights`. The first conjunct holds by construction for any capability, and `Types`
  is a singleton in five of the six configurations, so it holds trivially there twice over. The
  property this is named for - that whatever ran had the type it was ASKED for - needs the requested
  type stored in `lastUse` and an equality against it, so that removing the type check from `Usable`
  fails this invariant. Add a mutation that does exactly that; if the current invariant survives it,
  that is the measurement of how vacuous it was.

- [x] **`capability-trace` exits successfully on a tree with no guest log.**
  [check-capability-trace.sh:40-56](../../src/tools/check-capability-trace.sh) prints "the reference
  was not held against a live run" and returns zero. As a fast host gate that is a reasonable default
  and the script says so honestly. As COMPLETION evidence for "every implementation trace is accepted
  by that relation" it is not: the milestone can be closed by a gate that replayed a checked-in file
  and never saw the kernel. Add a mode that requires a live trace, and use it in the profile that
  closes this milestone.

- [x] **The capability README lists three of the six configurations.**
  [README.md:17-19](../spec/capability/README.md) names `spike`, `handles` and `revoke-test-only`;
  `propagation`, `transactions-batch` and `transactions-single` are missing from the table. Whoever
  reads the directory learns half of what it holds.

### Reachability has to be proved, not assumed, once the above lands

The cover properties are the right mechanism and they did not catch the unreachable batch, because
no cover asserts a two-capability state. Add covers that TLC must refute for: a batch of length two,
a queue holding two messages, a second capability inside one message, and a rollback of a
two-element batch. A cover that stops being refuted is the signal that a configuration has quietly
shrunk - which is what happened here.

- **"The concrete suite does not cover allocation refusal or a generation at `u32::MAX`."** Not
  re-verified in this round. Written down so the next pass over the concrete matrix checks it rather
  than assuming it was considered.

## Results of the reopen (2026-08-26)

### The batch configuration did not model a batch, and now it does

`BatchMax = 2` said the model would CARRY two capabilities; `Objects = {o1}` and an `Init` that
minted exactly one meant a second could never be put anywhere. So the rule the configuration is named
for - a refused send returns ALL of them, and a duplicate source is refused - was checked over a batch
of length one, which is the length at which "all of them" and "it" are the same sentence. Every
invariant held, the run finished, and a passing result was published for a model that could not reach
its own subject.

`Init` now mints one capability per object, and `transactions-batch.cfg` has two. That could not be
done while `TransferIsLinear` said what it said:

```tla
TransferIsLinear == CopiesInSlots + CopiesInXfer + CopiesInQueue + CopiesInHeld =< 1   \* before
TransferIsLinear == \A o \in Objects : CopiesOf(o) =< 1                                \* after
```

The old form is not linearity. It says the whole machine holds at most one capability, so two
capabilities for two objects - an ordinary state - was reported as a violation, and the configuration
was left with one object rather than the invariant being stated correctly. The two configurations
that model `HandleTable::duplicate` still do not check it, for the reason they always gave.

**And a cover proves the batch is reached**, which is the part that would have caught this:

```
model-mutations: cover NoBatchOfTwo is reached
model-mutations: cover NoMessageOfTwo is reached
model-mutations: cover NoBatchOfTwoRestored is reached
model-mutations: cover NoTwoQueuedMessages is reached
```

The last one failed first, and that failure was worth more than the three that passed: with one
object, `transactions-single.cfg` could not put two messages in a queue whose limit was two, so its
second queue slot was a number. It has two objects now, which is what makes quantifying an invariant
over every queued message mean anything.

### The invariants now quantify over what the model holds

`CopiesInQueue` counted `queue[1]` and nothing behind it; `AuthorityNeverWidens` reached
`queue[1].caps[1]`; `NoForgery` covered slots and `xfer` and omitted the queue and the held message
entirely. All three are stated over `AllCaps` - every capability in every location, named once, so an
invariant cannot quantify over less than the model holds by accident.

`TypeSealing` required `lastUse.type \in Types`, which is true by construction for any capability -
and `Types` is a singleton in five of the six configurations, so it held trivially there twice over.
The model now records the type the operation ASKED for, and the invariant is an equality against it.

The audits said every recorded digest and every state count was stale. Half of that is right, and the
half that is wrong is worth recording: three of the six counts (`handles`, `revoke-test-only`,
`propagation`) still matched the tree exactly. All eight digests did not.

### And the gate holds the run to them

```
capability-model: spike - 45092 distinct states, depth 27, as recorded
```

It parses `MEASUREMENTS.md` rather than keeping a machine-readable copy beside it, because the
document is the thing that has to be true and a second copy is one more place to drift. Watched to
fail, with one recorded count changed by one:

```
capability-model: spike explored 45092 distinct states, and docs/spec/capability/MEASUREMENTS.md records 45091
capability-model:   a different result is a DIFFERENT RESULT: re-run, check what changed, and update docs/spec/capability/MEASUREMENTS.md deliberately
```

### The counterexamples are kept, and they are the same bytes every run

Six mutation counterexamples are written to `docs/spec/capability/counterexamples/`. They ran with
four workers, which race to the first violation - so each run found a different behaviour of the same
length and the retained files churned on every gate run. One worker makes the search order
deterministic; two consecutive runs now produce byte-identical files, which is what makes them worth
checking in.

### The trace gate can no longer close this milestone without seeing the kernel

`--require-live` is what `check.sh` runs. Without it the gate printed "the reference was not held
against a live run" and exited zero, so the claim that a running kernel emitted a trace and it was
replayed could be closed by a run that replayed a checked-in file. The lenient default stays for the
fast host gate; the profile that closes the milestone does not have it.
