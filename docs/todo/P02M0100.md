# P02M0100 - LiberCommander (`lico`, `licoedit`, `licoview`)

Status: IN PROGRESS AFTER P02M0097. The initial shared `lico` terminal core is a manifest-owned
`lib/terminal/lico.lslib` with host-tested terminal-mode ownership/restoration, ConsoleService
resize decoding, bounded key and SGR-pointer decoding, bounded UTF-8 decoding, focus/menu/dialog
state, key binding dispatch, progress state and conservative file-type detection. It also contains
a version-1 syntax-description parser, deterministic filename-before-first-line selection and a
bounded stateful highlighter; installing the initial descriptor assets and exposing their narrow
app-directory view remain open. The panel/TUI, viewer and editor slices may start then, but
P02M0100 cannot complete until P02M0101's public storage/transactional-writer foundation exists;
P02M0102 later extends the command bar with pipelines/redirection but is not required for
P02M0100's single-command completion gate. Build one keyboard-first, mouse-capable orthodox
file-management suite for the Phase-2 console: `lico.lsexe` is the two-panel manager,
`licoedit.lsexe` is the standalone text editor and `licoview.lsexe` is the standalone
text/raw/hex viewer. All three are ordinary governed executables, share bounded no_std
TUI, text-buffer and syntax-description libraries, and operate only on the terminal,
session state and volume capabilities PermissionManager explicitly grants. This slice
does not include file/directory comparison or synchronization, multi-rename, browsing
archives/packages as directories, image/audio/media viewing, remote filesystems, a
plugin ABI, or plugin execution. The bottom command bar is included, but it is a UI over
the ordinary governed launch path, not a second long-lived or hidden shell.

- [x] Define a versioned, declarative syntax-description format and one bounded parser/
  matcher shared by `licoedit` and `licoview`. Keep one independently addable descriptor
  per language beside the suite under `bin/lico/syntax/` (initially Rust, LSIDL, TOML,
  JSON, Markdown and shell/config text); each descriptor names file globs and optional
  first-line recognition, lexical contexts, delimiters, escapes, keywords and style
  classes. A new language is added by installing another descriptor, not by recompiling
  either app.
  Descriptors contain no executable commands, paths or capability requests; reject
  unknown versions, duplicate/conflicting rules, invalid UTF-8, excessive rules/nesting/
  token lengths and non-progressing matches before highlighting begins. A missing or bad
  descriptor falls back to plain text and cannot prevent opening the file.
  Result. The format and its parser were built with the `lico` core; what this round added is the
  half that makes "a new language is added by installing another descriptor" true rather than
  possible - THE DESCRIPTORS THEMSELVES, six of them, installed under `bin/lico/syntax/` as
  manifest-declared factory files: Rust, LSIDL, TOML, JSON, Markdown and shell/config text.

  A DESCRIPTOR IS DATA AND THE FILES PROVE IT: literals, contexts and style names, with no commands,
  no paths and no capability requests anywhere in the format. The rules are LITERAL matches rather
  than patterns on purpose - a regular expression engine is where a highlighter turns into an
  interpreter running input somebody else wrote, and a viewer that can be made to loop by opening a
  file has a denial of service in it. Literals always make progress.
  Where a language's own rule is subtle the descriptor says so rather than approximating: Rust's
  block comments nest, which is what `max-nesting` is for; a TOML or shell literal string takes no
  escapes at all, so its context has no escape rule and that absence IS the behaviour.

  The host tests read the INSTALLED BYTES through `include_bytes!` rather than a transcription - a
  test written against a copy proves the copy parses, which is not the question. Each descriptor
  must parse, name itself as the file it is installed as, and produce spans over its own text: a
  descriptor that parses and highlights nothing is the failure a person writing one actually
  reaches, and it looks exactly like a file with nothing to highlight. And selection is asserted
  across the WHOLE installed set, because a glob that is too greedy does not fail to parse - it
  steals files from another language, and the reader sees Rust keywords in a JSON file rather than
  an error.

  FOUND WHILE WRITING THEM, and fixed: a comment line of a bare `#` was not a comment. The rule
  required `"# "` with the space, so the line every multi-paragraph comment uses to separate its
  paragraphs fell through to the header check and the file was refused as `InvalidHeader` - naming
  a header line that was right there and correct. A format whose comment syntax has a trap in it is
  a format people write invalid files in.
  The manifest's factory-file rule now admits `bin/lico/syntax/*.syntax` by SHAPE, with no deeper
  nesting, so "install another descriptor" cannot become "install anything anywhere under bin".

  read-only asset bundle (or an equivalent app-directory view capability) and compile
  only the selected language's rules into a bounded matcher. Do not call the current
  whole-system-volume client an app-directory capability: the standalone viewer/editor
  must not gain unrelated files merely to highlight text. Define deterministic precedence
  for filename versus first-line matches, a reload operation, stable style names mapped
  through the current theme, and incremental line-state caching so edits and scrolling
  re-highlight only the affected viewport/range. Host tests share golden source samples
  between editor and viewer and prove identical token spans, chunk-boundary behavior and
  hostile-descriptor rejection.
  Result. The capability is `app-assets`, and this item's sharpest sentence is the reason it exists:
  "do not call the current whole-system-volume client an app-directory capability". Reading the
  descriptors through the volume bundle would have meant the viewer held every file on every mounted
  volume in order to colour some keywords - the shape of over-granting a capability system exists to
  make unnecessary, since the authority to read one directory is expressible and so should be
  expressed.

  It is minted PER LAUNCH by PermissionManager from the private `volume-admin` endpoint, which
  already existed for ConfigService's persistence and the journal. The supervisor hands the manager
  a duplicate of that endpoint and the manager grants it to NOBODY: the thing that hands out a
  narrowed authority must not itself be one of the things handed out. The minted client carries the
  directory as its SCOPE rather than as a convention the holder is trusted to respect - a path
  outside it is refused by StorageService, and it cannot mint a broader one.

  THE SCOPE IS A FUNCTION OF WHO IS BEING LAUNCHED, not a field beside the grant. A path in the
  manifest would be a place to write the wrong one, and "which files may this program read" should
  be answerable from the program's identity alone. `asset_bundle` maps a component to its directory
  and the default is its own name; the exception is a FAMILY sharing one bundle - LiberCommander is
  three programs over one set of descriptors, and installing three copies would be three things to
  keep in step for no gain.

  `licoview` loads them at startup and every failure is a `continue`: no assets granted, a directory
  that will not list, a file that will not read, a descriptor that does not parse. That is this
  milestone's own rule - a missing or bad descriptor falls back to plain text and cannot prevent
  opening the file - and writing it as the control flow rather than as a check is what makes it hold
  for reasons nobody anticipated.

  NOT DONE in this item: the reload operation, incremental line-state caching for scrolling and
  edits, and the shared golden-sample tests between editor and viewer. The editor does not exist
  yet, so "identical token spans between editor and viewer" has one side; the caching is a change to
  the highlighting call path rather than to the asset path, and belongs with the editor that will
  exercise it.

  Result (2026-08-16). Two panels with their own URI, selection, scroll, ordering, filter, history,

  AN UNGRANTED VOLUME IS NOT REACHABLE AND NOT PROBEABLE, and that is a property of the bundle
  rather than a check here: the manager holds exactly the volume clients PermissionManager sent it,
  a path is routed to the client its URI names, and a URI naming a volume that was not granted
  reaches no client at all. There is nothing to probe with.

  A DIRECTORY THAT WILL NOT OPEN LEAVES THE PANEL WHERE IT WAS. The volume's own reason goes to the
  status line - denied, absent, busy, refused - and the other panel is untouched, because the
  failure is a return value on one panel's refresh rather than a state the manager enters.
- [ ] Panel modes: ordinary file list, directory tree, selected-entry information and
  passive-panel quick text view. List mode offers stable name/extension/size/mtime/type
  sorting, directories-first toggle, concise/long columns, hidden-file toggle, explicit
  refresh and free-space/status display. Tree construction is iterative and lazy; quick
  view embeds the same bounded read-only text renderer as `licoview` without duplicating
  its parser or gaining edit authority.
  Result (2026-08-16), the LIST-MODE half. Ordering is name / extension / size / mtime / type with a
  reverse toggle, a directories-first toggle and a hidden-file toggle, and every one of them is
  STABLE in the sense a reader cares about: name is always the tie-break, so two files of the same
  size do not swap places between refreshes and the entry under the cursor is still under it after
  one.

  THE CURSOR FOLLOWS THE ENTRY AND NOT THE POSITION. Re-sorting a listing and leaving the cursor on
  row four selects whatever moved there, which is how a reader deletes the wrong file after changing
  the sort order - so the rebuild finds the previously selected NAME in the new order.

  A leading dot is not an extension separator (`.config` is a hidden file named `config`, not a file
  with a `config` extension), and `..` is never hidden by the hidden-file rule - a panel that could
  hide the way out of a directory would be a trap. Reversing reverses the FILES and the DIRECTORIES
  rather than moving the directories to the bottom: reversing by size asks for the biggest first,
  not for the folders to move.

  The listing is kept WHOLE and the presentation is applied to a view of indexes into it, so turning
  a filter off costs nothing and never re-reads the directory - and re-reading is not merely slower,
  it is a chance for the answer to have changed underneath a reader who only changed how they were
  looking at it.

  THE THREE OTHER MODES landed 2026-08-16, on `M-v`, and the mode is PER PANEL because a reader
  looking at a tree on one side and a listing on the other is the ordinary case. `Tree` marks
  directories where the name begins, which is what makes a walked subtree readable as one; `Info`
  shows every field the listing knows about the selected entry, one per row; `Quick` shows the first
  screenful of the entry selected in the OTHER panel - through the same bounded window read every
  volume tool uses, because a preview is a look rather than an open, and holding a whole file to
  show twenty lines of it is what the window read exists to avoid. Its rendering escapes control
  bytes for the same reason `hexdump` does.

  STILL OPEN in this item: the tree does not EXPAND a node in place (it marks directories in the
  current listing rather than splicing a child listing under one, so "iterative and lazy" is true of
  the search walk and not yet of this view), and concise/long columns with a free-space display.

  And tags are CLEARED BY A REFRESH: a tag is something the reader made on the screen in front of

  `F8` ASKS FOR A TYPED CONFIRMATION rather than a keystroke, because a destructive operation whose

  PREFIX and not substring - a reader typing `co` means the file that begins with it, and matching

  Per-panel back/forward history has a browser's shape, and the half that matters is what a NEW

  THERE IS NO HIDDEN SHELL AND NO PROCESS AUTHORITY. `lico` holds `Capability::Permission` - the
  narrow launch broker - and nothing else that could start anything: it names a program and its
  arguments, and PermissionManager runs that program under the PROGRAM'S OWN manifest. Launching
  from a panel lends the child nothing, because the manager has nothing to lend.
  `Capability::Process` would be raw process creation and is deliberately absent.

  Cursor and word editing, quoted arguments (a name with a space in it holds together), bounded
  history that does not record the same line twice, `^N` to insert the selected name and `^T` to
  complete. COMPLETION CONVERGES on the longest common prefix rather than cycling, so a second press
  adds nothing rather than picking one of the possibilities for the reader. The line being typed
  survives a walk through the history and comes back when the walk returns to the present, which is
  the thing a history is most able to get wrong.

  `cd` IS PANEL NAVIGATION AND IS NOT LAUNCHED, and the other state-mutating builtins are refused by
  name - the same rule the shell applies to `cd x | grep y`, and for the same reason: they would run
  somewhere their effect is discarded, and reporting success for that is a lie. A shape-recognised

  A FOREGROUND COMMAND OWNS THE SCREEN AND GIVES IT BACK: the panels are left through the alternate

  Result (2026-08-16). Copy, same-volume rename, cross-volume move, mkdir and delete over the tagged
  set - or over the entry under the cursor when nothing is tagged, which is the orthodox contract.

  THE PLAN IS MADE BEFORE A VOLUME IS TOUCHED and it is where the traps are caught. A destination
  inside one of the sources is refused by name: `cp -r a a/b` is a request that cannot be satisfied,
  and a program that starts it discovers that by filling the volume. The check compares AT A
  SEPARATOR, because `vol://system/binary` is not inside `vol://system/bin` and a plain prefix test
  would refuse a copy that is perfectly legal. A source landing on itself is a separate refusal with
  its own sentence. A total that includes a directory is marked as a LOWER BOUND rather than being
  quietly wrong by whatever the subtree holds, because a progress figure over a total nobody
  computed is one that lies.

  EVERY COPY GOES THROUGH THE TRANSACTIONAL WRITER, so nothing is visible under the destination's
  name until the commit: a copy interrupted, refused or out of space leaves whatever was there
  before exactly as it was, and that is the control flow rather than an error path. A cross-volume
  move copies, publishes, and only then removes the source - so an interruption leaves two files
  rather than none. Within a volume it is `rename`, which moves the entry and never the bytes.

  CANCELLATION IS CHECKED BETWEEN ENTRIES, so an interrupt stops at an entry boundary: what has been
  done is complete and what has not been started is untouched.

  Pinned by `kernel.applications.lico_switches_panels_and_restores_the_terminal`, which drives `F7`
  and a typed name and requires the created directory to appear in the panel - watched failing with
  the mkdir call removed, so it measures the volume path and not the prompt.

- [x] `licoview` search supports forward/backward text with case/whole-word options and
  a separate hexadecimal-byte query mode (for example `48 65 6c 6c 6f`) usable from
  both raw and hex views. Validate the complete byte pattern before scanning, define
  spacing/case and optional wildcard syntax explicitly, bound reverse-search indexes and

  Result (2026-08-16). Two kinds of query, kept apart in `lico::search` because they are asked about
  different things: TEXT, which a reader types and which may fold case or require whole words, and
  BYTES, which somebody diagnosing a format types as hexadecimal and which must never be
  reinterpreted as text. Both are LITERAL - a pattern language with repetition is an interpreter
  running input somebody else wrote, and a viewer that can be made to loop by opening a file has a
  denial of service in it.

  THE WHOLE BYTE PATTERN IS VALIDATED BEFORE ANY WINDOW IS COMPARED, and each refusal is its own
  named case because each needs a different sentence to fix. `48 6` is an ODD NIBBLE and is refused
  rather than guessed at; so is `4 8`, because a separator inside a byte is a mistyped byte and not
  two of them. `??` is any byte and is two characters wide, so a wildcard occupies exactly the width
  of the byte it stands for. Spacing and case are PRESENTATION and are the one place this is
  lenient: `48 65 6C`, `4865 6c` and `48656C` are the same three bytes because that is how the same
  three bytes are written by a hex dump, a specification and a person. The pattern length is bounded,
  so a pasted megabyte cannot become a query dragged over every window of the file.

  Forward is "at or after" and backward is "strictly before", through ONE scan function both queries
  use - which is what makes repeating a search advance rather than find the same place forever, and
  a search that finds nothing leaves the view where it was and says so. Whole-word is a FILTER and
  not a stop: rejecting the `alpha` inside `alphabet` continues to the next candidate, where ending
  the search there would report "not found" about a file that contains the word.

  The viewer has three views over the same bytes rather than three programs - text, raw and hex -
  and switching keeps the reader's place, rounded down to a row boundary in hex because a dump whose
  rows do not start on a multiple of sixteen cannot be compared against another. A file detected as
  binary OPENS in hex, since a decoded rendering of an executable shows a reader something that is
  not there. Non-printable bytes render as `.` in both the hex ASCII column and the raw view: a byte
  written as itself puts control characters on the terminal, which is how a dump changes the
  terminal's mode. `g`, `o` and `%` go to a line, a byte offset and a percentage; `i` and `W` toggle
  the case and whole-word rules and both are shown in the header, so a search that finds nothing has
  its rule visible rather than remembered.

  Syntax highlighting is wired here for the first time: the installed descriptors were being loaded
  and handed to nothing. A descriptor is chosen once per render from the name and the first line,
  `h` toggles it, and a file that matches nothing is plain text - this milestone's own rule.

  NOT DONE: streaming. The viewer still reads a bounded 512 kB into memory, so "stream files larger

  and are not claimed by this one. `less` already pages a file it does not hold, through a table of
  line offsets, and that is the shape this will take.

- [ ] Editor operations: character/word/line and shift-movement selection, copy/cut/
  paste, block indent/unindent, duplicate/delete/move line, bounded undo/redo with clean
  save points, goto line, forward/backward search and deterministic replace-one/replace-

  Domain budgets; an oversized edit fails without corrupting the buffer or saved file.
  Result (2026-08-16), everything but the regex mode, which is named at the end rather than implied.

  THE ONE PLACE TEXT CHANGES is `TextBuffer::splice`, and every mutator routes through it - insert,
  paste, delete, the line operations, indent, replace. That is what makes the undo record, the
  revision, the selection and the cursor impossible to update by one path and forget by another,
  which is how an editor comes to have an operation that is not undoable and nobody finds out until
  a reader loses work to it.

  EVERYTHING THAT CAN FAIL IS BOOKED BEFORE A BYTE MOVES, so this item's own sentence - "an
  oversized edit fails without corrupting the buffer" - is a property rather than a hope. There is a
  test that fills a four-byte buffer, is refused the fifth byte AND a three-byte run, and asserts
  both the text and the CURSOR are where the accepted edit left them: a buffer whose caret moved for
  an edit that did not happen is corrupt in the way a reader notices next.

  UNDO TAKES BACK AN OPERATION, NOT A KEYSTROKE. A run of ordinary typing coalesces into one entry
  and anything that is not a continuation of it - a move, a deletion, a paste - starts another; a
  paste is one edit and so is a replace-all, because each was one action. The history is bounded by
  a BYTE BUDGET rather than a count, since what costs memory is what an edit remembers and one
  replace-all over a large file remembers more than a thousand keystrokes; when it is reached the
  OLDEST entries go, because undo is used to take back what was just done. The cursor is restored
  with the text, which is what stops undo feeling broken when the bytes are right.

  UNINDENTING DOES NOT EAT TEXT: a line that does not begin with the indent unit is left alone,
  which is the ordinary case for a block where one line is already at the margin. A selection that
  ends at the first column of a line does not include that line, because selecting downward to the
  start of the next line is how a reader selects the lines above it. Both are tests.

  Deleting the LAST line takes the newline BEFORE it, since that line has none of its own -
  otherwise deleting it leaves a blank line and a trailing newline the file never had.

  Word movement skips what separates words rather than stepping over it, and `_` is part of a word -
  the same rule the search's whole-word option uses, written in one function so the two cannot come
  to disagree about where a word ends.

  Replace-one acts on the SELECTION rather than on "the next match", because after a find the
  selection is exactly the match the reader can see; a selection that is not the pattern is refused
  rather than replaced anyway.

  Four deliberate breaks were watched to fail: removing the typing coalescence, unindenting
  regardless of the unit, starting a backward search AT the cursor rather than before it, and each
  turned a green suite red on the test that names it.

  STILL OPEN: the shared-regex mode. There is no regex engine in this tree - P02M0101 states the

  asks for that does not need one is here.
