# M0132 - Capability-native pipes and redirection

Status: PLANNED AFTER THE M0131 FOUNDATION SLICE, BEFORE M0131 COMPLETION. It consumes the
public transactional writer, launch context and a small available set of path-based
stream tools, but does not wait for every M0131 executable; M0131's final stdin-native
integration runs after this milestone. Add pipelines and input/output redirection as
native composition of bounded stream capabilities, not as a POSIX file-descriptor table
or ambient filesystem escape. This milestone completes M0035j's deliberately deferred
multi-process process groups and gives M0131 stream utilities one consistent stdin/stdout/
stderr contract. Each stage remains an independently governed executable with its own
PermissionManager manifest; connecting byte streams never transfers the producer's or
consumer's other capabilities.

- [x] Specify one versioned byte-stream contract used by runtime stdio, pipelines and
  StorageService adapters: bounded chunks, blocking/backpressured write, readable/
  writable readiness, writer-close -> EOF, reader-close -> broken-pipe/cancellation and
  an idempotent explicit error close where ordinary EOF is insufficient. Define the
  maximum queued bytes/chunks and fair wake ordering; a slow or stopped stage cannot
  make another Domain allocate unbounded memory.
  Result (2026-07-31): `rt::stream`, and it deliberately adds almost no mechanism - the
  interesting finding is that a Channel already provides every property a pipe needs, each
  built for a different reason before pipelines existed. An endpoint's inbox is bounded at 64
  messages and a send past that reports Full, which is backpressure by depth. Every queued
  message is charged to the SENDER's Domain IPC quota until it is taken, which is backpressure
  by bytes and is precisely the requirement this item states - a slow stage cannot make another
  Domain allocate without bound, because the kernel already refuses to let it. And peer close
  is observable at both ends, which is EOF one way and broken pipe the other.
  So the contract is the convention on top: `MAX_CHUNK` of 4096 with the chunk AS the frame
  (re-framing a byte stream over an ordered message queue would buy nothing), and
  `MAX_IN_FLIGHT` stated as depth times chunk so a stalled pipeline's worst-case memory is a
  number rather than a property of whichever path ran. Building a second queue beside the
  kernel's would have meant two answers to "how much can a stalled pipeline hold", and only one
  of them is enforced by Domains.
  Three distinctions in the read result carry the weight. A zero-length message is neither data
  nor an end, and is skipped: treating it as the end lets an empty write truncate a stream.
  `End` (the writer closed) is separate from `Failed` (the writer reporting it could not
  finish), because a consumer that cannot tell them apart publishes a truncated result as a
  complete one - the exact failure the transactional writer exists to prevent, so the stream
  must not hide it. And `fail` sends non-blocking on purpose: a writer that is failing must not
  block behind a consumer that stopped reading, or a broken stage hangs instead of reporting.
  `Writer` closes on drop, so a stage that returns early cannot leave its consumer waiting for
  an EOF that never arrives - a hang rather than a finish. `Reader::close` is how an
  early-exiting consumer (`head` on a huge file) tells the stage upstream to stop.
  Not claimed: fair wake ordering, which is the scheduler's existing behaviour rather than
  something this contract sets, and versioning of the contract itself, which has no second
  version to be compatible with yet.
- [ ] Generalize the runtime launch context from the existing stdin/stdout channels to
  three explicit endpoints in M0131's versioned context: stdin (read), stdout (write) and
  stderr (write), each absent, terminal-backed, pipeline-backed or storage-backed by
  transferred capability. Preserve the current terminal behavior for ordinary launches,
  keep stdout and stderr separate by default, close inherited duplicates promptly and
  expose no numeric descriptor API, arbitrary endpoint lookup or ambient inheritance.
- [x] Add a typed process-completion result before defining pipeline status: clean exit
  carries a bounded integer code, signal/fault/forced teardown carries a distinct reason,
  and waiting on a Process or ProcessGroup returns that immutable result after readiness.
  Today's Process handle exposes only terminated/killed readiness and `rt::exit()` has no
  status, so `pipefail`, per-stage diagnostics and success-gated publication must not infer
  success from mere closure. Preserve the first terminal cause and define group status
  over the ordered stage results without exposing ambient PIDs.
  Result (2026-07-31, partial - the per-process half): `SYS_USER_EXIT` took NO argument and
  discarded a0, so a process could finish and never say how. A waiter saw closure and nothing
  else, which makes a program that ran and refused indistinguishable from one that worked.
  The status is now latched on the Process and reported through `process_stats` as
  `completion` plus `completion_valid`.
  Two decisions worth recording. `exit()` keeps its signature and means status 0: there are 311
  call sites in the tree and success is nearly all of them, so making each write `exit(0)` would
  add no information to any of them; `exit_with(status)` is the explicit form. And the report
  carries a separate validity flag rather than letting 0 stand for both outcomes, because 0 is
  at once the commonest success and the natural "nothing here" - a process that faulted never
  got to report anything, and reading that as a successful zero is how a broken stage would
  report success.
  First writer wins, the same rule the recorded fault follows, so a multi-threaded process whose
  threads exit differently has one answer and it does not change under a reader.
  Validation is `a_clean_exit_reports_its_status`, four assertions each ruling out a different
  wrong implementation: nothing reported reads as `None` and not 0, a reported 42 reads back as
  42 (not merely "non-zero" - the value is asserted, so a stub returning 1 fails), a second exit
  does not overwrite the first, and a reported 0 reads as `Some(0)` rather than absent.
  The syscall's own line is deliberately NOT covered by that test, and the reason is a real
  constraint: `SYS_USER_EXIT` does not return - it longjmps to the kernel thread that entered
  ring 3 - so a kernel test thread calling it jumps to a stack that was never parked and
  double-faults, which is what the first version of the test did. It is covered instead by
  every process in every boot, since all 311 `exit()` calls now pass a status through it.
  Still open here: the group half - a group status defined over the ordered stage results -
  which waits on the pipeline itself rather than on this primitive.
- [x] Add a kernel `ProcessGroup` object (or an equally explicit capability object) that
  owns a bounded set of live process references and supports group wait plus capability-
  gated INT/TERM/KILL/STOP/CONT. Membership is fixed by the trusted launcher at spawn,
  cannot be joined by an untrusted process and is removed on exit. ConsoleService holds
  one MANAGE-scoped group capability for the foreground job, so Ctrl+C/Ctrl+Z/Ctrl+\
  affect every live pipeline stage and no unrelated process.
  Result (2026-07-31, the object and its syscalls; ConsoleService adoption follows with the
  shell work): `ProcessGroup` is object type 11, created over a set of Process handles by
  `SYS_PROCESS_GROUP_CREATE` and signalled by `SYS_PROCESS_GROUP_SIGNAL`, capped at 64 members.
  Three of its properties are refusals of Unix behaviour rather than omissions, and each is
  worth stating because the Unix shape is what a reader will expect.
  Membership is SEALED at creation. A Unix process group can be joined with `setpgid`, which is
  how a process escapes the group its parent placed it in; there is no reason a pipeline stage
  should be able to leave the job it belongs to, and sealing it makes "which processes does this
  signal reach" answerable from the handle alone.
  Members are held WEAKLY, so a group never keeps a dead process alive. Owning them strongly
  would pin every stage for as long as the job table holds the group, and the point of the
  object is to reach processes that are still running.
  Authority comes from the HANDLE, not from membership: signalling needs the group capability
  with MANAGE, and being in the group grants nothing, so one stage cannot signal its siblings.
  That is precisely the confused-deputy shape Unix has, where any member may `kill(0, sig)` the
  rest. Creation requires MANAGE on each member for the same reason - a group cannot be
  assembled out of processes the caller could not already signal one at a time.
  Two smaller decisions. The per-process and per-group paths share one `deliver_signal`, so a
  group cannot drift from what signalling a member directly does. And a group signal continues
  through every live member even after one fails, because a partially interrupted pipeline is
  worse than either outcome - the stages that received it exit while the rest run on with their
  peers gone.
  Validation is `a_process_group_reaches_every_member`. The assertion that carries it is that
  ONE dead stage does not finish the job: without it an implementation reporting finished as
  soon as any member ended would pass. It also asserts that dropped members leave the live set
  (proving the references are weak), and that an empty group and one past the cap are REFUSED
  rather than truncated - a group missing a stage would signal an incomplete job with nothing
  to say so.
- [ ] Extend SessionService jobs from one Process handle to one job handle representing
  either a single process or ProcessGroup, plus the ordered display command and aggregate
  running/stopped/completed state. `&`, `jobs`, `fg`, `bg`, shell restart and completion
  reaping work identically for single commands and pipelines; a partially exited group
  remains a job until every stage is reaped, and all handles close on session teardown.
- [x] Replace line-prefix dispatch with a bounded lexer/parser that produces an explicit
  command/pipeline/redirection AST while preserving existing variable expansion and
  canonical option normalization. Recognize operators only outside quoted/escaped text,
  lex operators before variable expansion and never reinterpret expanded data as syntax,
  reject empty stages, duplicate/conflicting redirects, unsupported descriptor numbers,
  dangling operators, excessive stages/arguments/expanded bytes and recursive expansion
  before any file is opened or process spawned. Keep assignment/session-state builtins
  explicit rather than accidentally applying them in a child pipeline context.
  Result (2026-07-31, the parser; wiring the shell to it comes with the pipeline transaction):
  `shell_language::parse_pipeline` turns a raw line into stages, each with its own ordered
  redirections. The ORDER OF OPERATIONS is the security property here and it is why this is a
  lexer rather than a few splits.
  Today's shell calls `parse_and_expand` FIRST and routes the result, which is safe only
  because no operator exists yet. The moment `|` means something, expanding first turns a
  variable's contents into structure: `FOO='| rm x'; echo $FOO` would build a pipeline out of
  data. Operators are therefore found on the RAW line and an expanded value is never lexed
  again - the fix is not to escape the data but never to look at it as syntax, which is the
  bug every shell that got this wrong shares.
  Quoting is part of lexing for the same reason: an operator inside quotes is a literal, so
  `echo "a | b"` is one argument. If quoting were applied after operators were found, the split
  would already have happened.
  The test that carries this asserts the property directly, with operator characters arriving
  from variables in each position that matters - a pipe that must not create a stage, a
  redirect that must not name a file, an ampersand that must not background the job. A parser
  that expanded first would pass every other test in the file and fail these three.
  Bounds refuse rather than trim (8 stages, 64 words per stage, 4096 bytes), because a
  truncated pipeline is a different command from the one that was typed, and every refusal
  happens before a caller could open a file or launch a stage - which is the point of parsing
  separately from running. `3>&1` is refused as an unsupported descriptor rather than guessed
  at, and a leading digit is a descriptor ONLY when it introduces a redirect, so `file2` and
  `2x` stay ordinary words.
  Validation is five host tests beside the existing expansion ones, 23 passing in
  `just services-host-test` - host-side, so the fuzzing this item's sibling asks for has
  somewhere fast to run.
- [ ] Initial shell grammar: `A | B`, `< path`, `> path`, `>> path`, `2> path`,
  `2>> path` and `2>&1`, with left-to-right redirection ordering documented and tested.
  Compound shell language, command substitution, here-documents, arbitrary `N>&M`, shell
  scripts and POSIX descriptor emulation remain out of scope. A state-mutating builtin
  such as `cd`, assignment, `unset`, `fg` or `bg` is rejected as a pipeline stage; simple
  parent-shell use retains today's persistent SessionService semantics.
- [ ] Build a pipeline transaction in the trusted shell/launch broker: parse and resolve
  every executable/path, authorize every stage independently, allocate all stream pairs
  and redirection adapters, create the process group, then create every stage behind an
  explicit start gate (a suspended-launch or equivalent ProcessService primitive), install
  all endpoints, register the complete graph and release the stages together. The current
  launch starts immediately, so this gate is a required mechanism, not an assumed ordering.
  Note on that last sentence (2026-07-31): it is true of the ProcessService API and NOT of the
  kernel, which changes the size of this item. `SYS_THREAD_CREATE` and `SYS_THREAD_START` have
  always been separate capability-gated steps; every launch path simply called them back to
  back, so the gate existed and nothing exposed it. It is exposed now as `rt::process_prepare`
  / `rt::process_release`, with `prepare_with_object` / `start_thread` as the kernel-side twin,
  each split OUT of the combined call rather than added beside it so the two cannot drift in
  how a thread is built.
  The prepared handle is the authority to start exactly one stage. Dropping it leaves a process
  that never runs, which is what a failed transaction wants: no stage observes a half-built
  graph because no stage has run at all.
  Verified by `a_prepared_thread_does_not_run_until_released`, which gives the scheduler a full
  `run_until_idle` to run the prepared thread BEFORE asserting that it did not - without that
  the test would pass over an implementation that merely deferred the start by a tick.
  ProcessService exposes it as `launch-prepared` and `release` (ops 6 and 7). A prepared launch
  is an ordinary launch that has not begun: the caller gets the same `start-result`, so job
  control is identical, and `release` names the koid it already has.
  The start token stays inside the service. A reply carries one handle and a prepared launch
  would need two, but keeping it here is the better answer regardless - a caller cannot hold a
  half-started process open indefinitely, and there is no second capability to lose track of.
  `release` returns false rather than an error when a koid has nothing pending, because
  releasing twice is a caller's bug and not a condition the system should hide.
  The spawn path was restructured rather than extended, and the first attempt at this was
  wrong in a way worth recording. It handed the token out through a one-slot static beside the
  return value, justified by a blast radius that turned out to be eight call sites rather than
  a change to the boot chain. The process and its start token are two results of ONE operation,
  and splitting them across a return value and a global lets them disagree about which launch
  they describe. They are now one `Spawned { process, thread }` with `release` and `abandon`,
  and the whole path returns `Option<Spawned>` - so failure is one value instead of negative
  integers mixed with `Option`.
  That restructuring exposed something the static would have hidden: the STATIC program path
  started immediately and could not be prepared at all. `rt::spawn_prepared_in` fixes it and
  `spawn_in` is now prepare-then-release, so the static and dynamic paths cannot diverge in how
  a process is built - the same reason `prepare_with_object` was split out of
  `spawn_with_object` rather than added beside it.
  Every existing launch releases immediately and behaves exactly as before, which is what makes
  this safe to put on the path every launch in the system takes. Verified by booting: the boot
  chain comes up green.
  Any failure closes endpoints, terminates/reaps already created stages, removes temporary
  outputs and leaves no job entry; no stage observes a half-built graph or inherits a
  handle intended for another edge.
- [ ] For each `A | B` edge, transfer only A's write endpoint as stdout and B's read
  endpoint as stdin. Pipelines of more than two stages compose the same primitive and
  obey a configured stage/endpoint budget. Stderr remains on the terminal unless
  redirected; `2>&1` duplicates the current stdout stream capability at that exact point
  in left-to-right evaluation without granting authority over its eventual destination.
- [ ] Input redirection resolves a path against the shell's current URI and granted
  volume, opens it read-only and pumps it through the M0131 bounded streaming-read adapter.
  A directory, missing/read-denied file, unsupported backend or oversized path fails
  before launch. The child receives only the stream endpoint, not the source volume or
  reusable file capability, unless its own manifest separately grants one.
- [ ] Replace output redirection (`>`/`2>`) writes to a bounded temporary sibling through
  M0131's transactional writer and publishes only when the owning command or complete
  pipeline closes the redirected stream normally. A clean non-zero exit still publishes
  by default (`grep` with no match and diff-like tools may produce intentional output);
  launch failure, signal, fault, adapter/storage failure or inability to finalize aborts
  the writer and preserves the previous destination. An optional strict-success policy
  may additionally require code zero, but is never implicit. Append (`>>`/`2>>`) uses the
  writer's explicit append mode with per-write ordering; never emulate append by reading
  and rewriting the whole file or silently degrade it on an incapable/read-only backend.
- [ ] Define lifecycle propagation precisely: natural producer close delivers EOF;
  consumer early exit closes its read end and wakes the producer with broken pipe;
  terminal interrupt/quit targets the whole ProcessGroup; stop preserves queued bounded
  data without accepting more than the cap; resume restarts all live stages; killing one
  stage closes its outputs so downstream cannot hang forever. Adapter or storage failure
  signals the owning job and is surfaced separately from an executable exit.
- [ ] Add observable per-stage completion records and a stable pipeline status policy.
  Default interactive status is the last stage's result while launch/adapter failures are
  always failures; provide an explicit `pipefail` session setting that returns the
  rightmost failed stage. Background completion reports one job with a concise failing
  stage, and SystemGraph/counters expose stage count, queued bytes, blocked writers,
  transferred bytes and cancellation without logging stream contents.
- [ ] Prove the contract with current `cat`/`readln` plus whichever M0131 path tools are
  available in the foundation slice, and publish one migration checklist/API for the
  remaining `grep`, `head`, `tail`, `sort`, `cut`, `tee`, `wc`, `less` and `hexdump`.
  M0131 then makes each consume stdin when no path is supplied and write only stdout/stderr
  endpoints. At least one early-closing consumer exercises broken-pipe propagation and
  one fan-out probe exercises backpressure; tools do not detect pipelines through
  environment variables or receive broader volume grants merely because the shell
  redirected a path.
- [ ] Capability and hostile-input tests prove no pipeline edge leaks service/file/
  process handles, a stage cannot signal its group without MANAGE authority, redirects
  cannot escape granted volumes, and `2>&1` aliases only the intended stream. Fuzz the
  lexer/parser and launch rollback; stress full queues, zero-byte chunks, close races,
  stopped groups, stage crash, shell crash/restart, consumer early exit, disk full,
  append concurrency and destination replacement under strict Domain budgets.
- [ ] Governed end-to-end gates cover foreground/background two- and multi-stage
  pipelines, every redirect form and ordering combination, Ctrl+C/Ctrl+Z/fg/bg, EOF,
  broken pipe, `pipefail`, transactional replacement and append on supported/read-only
  volumes. Record throughput, context switches, queued-memory peaks and cancellation
  latency for large streams, then keep x86_64/aarch64/riscv64 builds and focused QEMU
  tests green with no regression for ordinary non-pipeline launches.
- Done when: arbitrary bounded chains within the configured stage limit compose through
  explicit stdin/stdout/stderr capabilities; redirection is volume-scoped and failure-
  safe; one ProcessGroup is one session/terminal job; signals, stop/resume, EOF, broken
  pipe, rollback and status semantics are deterministic; no fd/PID/global-filesystem
  ambient authority was introduced; current tools plus the available M0131 foundation
  tools interoperate through the public contract without private adapters; and the
  remaining M0131 tool migration is an API-conformance task, not a missing pipe primitive.
- Concept: M0030/M0071 (typed event and bounded streaming IPC), M0035i/M0035j (PTY, signals and
  the deferred process-group step), M0038/M0061/M0119 (PermissionManager, governed launch and
  persistent jobs), M0043-M0111/M0131 (streaming and transactional storage operations), and
  the existing `rt` stdin/stdout capability channels.
