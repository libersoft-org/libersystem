# P02M0122 - What authorises a write to somebody's disk

P02M0116 moved `Disk::Blank` from "I recognised nothing" to "every byte this build looked at is zero",
which was the right move and closed the case that started it: a raw ext4 whose superblock begins at
byte 1024, one sector past where the old probe stopped. This milestone is about the four sentences
in that answer that are still doing more work than they can carry.

Two of them are about the same word. **"Every byte this build looked at"** and **"the disk is
empty"** are not the same claim, and only one of them licenses a whole-device format.

## The blank disk that is not blank

`scanned_blank` reads LBA 0 through 128, then LBA 512 and LBA 1024 - 131 sectors, chosen because
that is where the filesystems this build knows about announce themselves. A disk that is zero across
all 131 and carries data from LBA 2000 onwards answers `Disk::Blank`, and `mount_or_format` then
takes the whole-device path: `LiberFs::mount` at `FS_START_SECTOR`, `MountError::Unformatted`,
`format_opts`. The data is gone.

That is not a contrived disk. Raw data volumes, container images, custom formats, anything whose
metadata sits at the end of the device, anything a filesystem this build has never heard of: none of
them announce themselves in the first 64 KiB, and there is no list of offsets that fixes this,
because the reason there is no complete list of signatures is the same reason there is no complete
list of places.

The `Disk` doc comment is honest about the limit - *"every byte of it this build looked at is
ZERO"* - so nothing here is misdescribed. What is wrong is that a sampled observation is wired to a
destructive default.

## What is wanted

- [x] **A whole-device format must be a permission, not a deduction.** Answered by DELETION, which
  is better than what this item proposed. See "The format was a leftover" below.

  The GPT case is a different situation and should stay as it is: an entry carrying the LiberFS type
  GUID is somebody deliberately saying *this range is ours*, and acting on it needs no further
  licence. The whole-device case has no such statement anywhere - the disk is silent, and silence is
  being read as consent.

  So `Disk::Blank` should stop being sufficient. A whole-device format needs an explicit
  provisioning right the boot policy grants deliberately: either a new right beside `BLOCK` on the
  device capability, or a separate `ProvisionDisk` capability the storage service is handed only
  when the system is being installed rather than booted. Then:

  ```
  Blank + the provisioning right -> format
  Blank without it               -> refuse, and say what it would have done and what to grant
  ```

  A first boot onto a fresh disk is exactly when someone is standing there deciding, and every boot
  afterwards is exactly when nobody is. The permission separates those two, which no amount of
  reading sectors can.

  **P02M0116 reached the same conclusion and recorded it rather than building it**: *"Recorded as
  direction rather than built: auto-formatting a whole device should need an opt-in. A GPT entry
  carrying the LiberFS GUID is an explicit statement by whoever partitioned the disk; a raw whole
  device is not, and the service currently infers permission from the absence of evidence."* Two
  independent audit rounds since have arrived at it as their P0. It is the item to build.

  Decide at the same time what the scan is still FOR once the permission exists. The honest answer is
  that it stops being a safety mechanism and becomes a diagnostic - "this disk does not look empty,
  are you sure" - and the doc comment on `Disk::Blank` should be rewritten to say so, because
  "the ONLY answer that licenses laying a filesystem over a whole device" will no longer be true.

  If content-derived emptiness is ever wanted as a real proof rather than a hint, the only version
  of it that works is reading the whole device and finding it zero. Worth costing before ruling out:
  on a small system volume it is a one-off pass at boot, and the current scan already spends 131
  reads to prove much less.

- [x] **`entries_overlap` must not allocate.**

  It builds `let spans: Vec<(u64, u64)> = ...collect()` from a hostile partition table. The GPT
  parser around it was rewritten to be fallible throughout for precisely this reason, and this
  function - added by that same rewrite - put an infallible allocation back into the path. The crate
  is a dependency of both the kernel and the storage service, so the failure is either an allocation
  abort in the kernel or the userspace `__rust_alloc_error_handler`, where the correct answer is
  `Disk::NoMemory` and is already a variant.

  It is bounded at 512 entries so it cannot be driven arbitrarily large, which is why this is not a
  P0. The fix costs nothing: the algorithm is already quadratic, so two nested `chunks_exact`
  iterators over `gpt.entries` do the same work with no allocation at all and no `Vec` to size.

- [x] **Validate every used entry, not only the LiberFS candidate.**

  `find_liberfs` says *"The whole table has to be consistent before any one entry of it is acted
  on"*, and that is the right rule. `entries_overlap` implements a third of it: it compares used
  entries against each other and against nothing else. `usable_span` - which checks `first <= last`,
  containment in the declared usable range, and non-overlap with the header, the backup header and
  the entry array - runs only for entries carrying the LiberFS type GUID.

  So a checksum-valid table with a Linux entry at `first = 1, last = 1`, sitting on top of the GPT
  header itself and overlapping no other partition, passes. It is a table no correct tool produced,
  and the answer that comes back is `Disk::LiberFs`, which authorises a write.

  Every used entry should go through the same span validation, and a table containing one that fails
  it should answer `Disk::CorruptGpt` - the same answer overlap already produces, for the same
  reason. Note also that `entries_overlap` currently `continue`s past a backwards span (`last <
  first`) on the grounds that `usable_span` refuses it separately; once every entry is validated,
  that reasoning holds properly instead of holding only for LiberFS entries.

- [x] **Compare the primary and backup GPT as tables, not as byte arrays.**

  The agreement check is `Ok(backup) if backup.entries == gpt.entries`. Two copies can carry
  identical entry bytes and still disagree about `first_usable`, `last_usable`, `entry_size`, the
  entry count, or the disk GUID, each header with a correct CRC over its own contradictory contents.
  `entry_size` is the sharpest of these: the same bytes parsed at a different stride are a different
  table, and `find_liberfs` walks `chunks_exact(gpt.entry_size)`.

  The comment says *"a verified backup that disagrees stops the write"*, which is stronger than what
  runs. Compare the canonical identity - disk GUID, first/last usable, entry count, entry size, and
  the entry array - excluding only the three fields that differ between the copies by construction
  (`current_lba`, `backup_lba`, `entries_lba`). `Gpt` already carries all but the disk GUID.

- [x] **A negative fixture for each, in `src/fs/partition/src/tests.rs`.**

  The crate's test file is already the right shape for this - it builds images byte by byte and
  asserts the probe's answer - and each of these is one image: data at LBA 2000 and zeros
  everywhere the scan looks; a foreign entry over the GPT header; two headers agreeing on entries
  and disagreeing on `entry_size`. The provisioning permission needs its test at the service level
  instead, where the refusal is.

  The first of those fixtures is worth writing even before the permission exists, because of what
  the suite currently proves. `a_disk_of_arbitrary_bytes_is_not_a_blank_disk` iterates
  `[2, 7, 64, 128, BLANK_FAR_PROBES[0], BLANK_FAR_PROBES[1]]` - **every one of them a sector the
  scanner reads**, two of them named by the scanner's own constant. It is a test of the scan's
  coverage written in the scan's own terms, so it passes by construction and would go on passing if
  the scan shrank to those six sectors. A test asserting the CURRENT answer at LBA 2048 -
  `Disk::Blank`, which is the wrong answer - documents the hole where the suite can see it, and
  becomes the test that flips when the permission lands.

## Where this came from

The sixth outside audit round on this tree, 2026-08-09, verified claim by claim against the code.
The round rated whole-device format safety unchanged at 7/10 across the two rounds - the one score
that did not move - and argued that P02M0116 should not be `[x]` while it stands.

P02M0116 stays complete, and this is not a technicality. Its scope was what P02M0114 left in the probe,
and it delivered that: eleven findings, all fixed, with the `Blank` answer honestly documented as
bounded by what the scan looks at. What this milestone changes is not a defect in that work but the
decision it inherited without examining - **that a probe should be able to authorise a destructive
write at all**. That is a different question, and it is the reason this is its own file rather than
a reopened section, following the same convention P02M0117 states for P02M0109.

The three GPT items are hardening in the crate P02M0116 built, and each of them is the same shape as
something that round already found: a fallible parser with one infallible call left in it, a
whole-table rule implemented for part of the table, and a comment describing a stronger check than
the code performs.


## What was built (everything except the permission)

The provisioning permission is the one item left, because it is a decision about what the boot
policy grants rather than a defect to fix. The three GPT items are done.

**`entries_overlap` became `table_is_inconsistent`**, allocates nothing, and checks every used entry
rather than only the LiberFS candidate. Two nested `chunks_exact` iterators do the quadratic
comparison the `Vec` was collected for, and each used entry now goes through the span rules
`usable_span` applied to LiberFS entries alone: non-zero, first before last, inside the declared
usable range, clear of both header copies and the entry array.

`MIN_PARTITION_SECTORS` is deliberately NOT among them. A small foreign partition is an ordinary
thing for another system to have made; only a LiberFS volume needs room for a volume. That
distinction is what separates "degenerate, skip it" from "impossible, condemn the table", and it is
where the line now sits.

**Two existing tests changed their expected answer**, which is worth naming rather than burying. A
table holding a LiberFS entry on top of the GPT header used to answer `GptWithoutLiberFs`; it now
answers `CorruptGpt`. Both refuse to write, so nothing was unsafe - what was wrong is the second
half of what the old answer claimed. `GptWithoutLiberFs` says *this disk belongs to something else
and its table is fine*, and nothing had checked the second clause.

**`copies_agree` replaced `backup.entries == gpt.entries`**, comparing the disk GUID, both usable
bounds, the entry count and the entry size as well as the array - everything the two copies must
share, excluding only the three fields that differ by construction.

### Watched to fail

All four rules reverted at once; four tests failed, including both of the pre-existing ones whose
answer changed.

### The hole, now visible in the suite

`a_disk_whose_data_begins_past_the_scan_is_still_called_blank` asserts the CURRENT answer, which is
the wrong one: data at LBA 2048 answers `Blank` and licenses a whole-device format. It is written
that way on purpose - the suite could not see this before, because the test that was supposed to
cover it iterates only over sectors the scanner reads, two of them named by the scanner's own
constant. That test passes by construction and would pass if the scan shrank to those six sectors.
The new one flips when the permission lands.


## The format was a leftover, and the answer was to delete it

This milestone spent four paragraphs designing a permission for a capability the system should not
have had. The right question was not *who may authorise a whole-device format* but **why does a
service format disks at boot at all** - and once asked, the history answers it:

- The format existed to SEED. There was a factory archive at LBA 0, and a fresh disk was formatted
  and populated from it, which is how a bootable volume came into being.
- **P02M0108 retired the seeding.** The system volume became a filesystem built by `mkpackages` on the
  build host, verified to mount before it ships, and written to the medium as an image.
- The format stayed. With nothing left to seed, it formatted an EMPTY volume and printed that it
  had done so - which helps nobody: a machine whose system volume never arrived is not helped by
  being handed a blank one, and a disk holding somebody else's data is destroyed by it.

Nothing needed it. `qemu_prepare_system_disk` truncates a 128 MB file and `dd`s the prebuilt volume
image over the front, so every boot in this tree - shipping and test alike - starts on a disk that
already carries a formatted volume. The format path was reachable only by attaching a disk that is
not the shipped one, which is precisely the case where it must not fire.

So `mount_or_format` is `mount_system_volume`, and it does not create:

- `Disk::Blank` refuses and says to write a volume image deliberately.
- `MountError::Unformatted` refuses too. It means the probe called the container a LiberFS volume
  and the mount disagreed - a contradiction about a REAL volume, so damage rather than emptiness -
  and the old code answered it by formatting exactly the volume the contradiction was about.
- `format_opts` and `stir_uuid` are gone from the service.

`Disk::Blank` is now a diagnosis rather than a licence, and the sampling limit stops being a hazard:
a hint that can be wrong about a disk nobody is about to write to costs nothing. The doc comment
says so, and `a_disk_whose_data_begins_past_the_scan_is_still_called_blank` keeps pinning the scan's
reach without claiming it is safe to rely on.

**Provisioning a disk is `mkpackages` writing a verified image to it, on a machine where a person is
standing.** That step already existed; it is the only one there should be. No new right, no new
capability, no boot policy - the mechanism this milestone was going to build had exactly one caller,
and the caller was the bug.

## Sixth audit round: each GPT copy only defends its own metadata

2026-08-10, from an audit that had nothing left to say about the destructive path - the format-on-boot
removal it had asked for as a capability was answered by deleting the capability, and it agreed that
was the better answer. What it found instead is one gap in the parser, and it is a real one.

- [x] **A partition is checked against ONE entry array: the one belonging to the copy being read.**
  `Gpt` carries `entries_lba` and `entries_last_lba` for the copy it was parsed from, and both
  `table_is_inconsistent` and `usable_span` test a partition against `gpt.entries_lba ..=
  gpt.entries_last_lba` and the two header LBAs. Validating the primary therefore never asks whether
  a partition overlaps the BACKUP's entry array, and validating the backup never asks about the
  primary's.

  A conforming table puts `last_usable` below the backup metadata so the question never arises. A
  checksum-valid hostile one is the case this parser exists for, and there the two spans are
  independent facts. A LiberFS partition selected over the backup entry array is a writable
  filesystem sitting on the recovery copy of the table describing it - not destroyed at mount, which
  is what the removal of format-on-boot bought, but overwritten in the ordinary course of use.

  Both copies are already read on the path that matters (`copies_agree`), so both spans are in hand;
  the fix is to carry both into the span test rather than one. The one path where only a single copy
  exists is `Err(_) => find_liberfs(&gpt)` - a primary standing alone because the backup is
  unreadable - and that policy is right and documented: only a backup that VERIFIES and disagrees is
  a reason to refuse. But standing alone should mean the metadata span the backup would have occupied
  is derived from the header (`backup_lba` and the entry count are in the primary) and defended
  anyway, because that is the region a recovery would need.
