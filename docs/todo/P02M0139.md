# P02M0139 - Reuse the PermissionManager test fixture without sharing test state

Status: TOOLING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Stop rebuilding the same PermissionManager integration topology for every assertion while preserving
twelve separately selectable tests and their failure attribution.

Twelve tests call `run_permission_scenario`. Eleven take the same non-`ScopedGrants` branch after the
same package parsing, service creation, channel topology, governed launches, pipelines and shell
session have already run. The twelfth continues into scoped graphics/audio grants. The repeated work
is a fixture-boundary problem, not a reason to merge the tests or redesign the planner.

This milestone starts after P02M0138 freezes the twelve-consumer inventory and its selection
regression. That correctness oracle is its only dependency. It is independent of P02M0137 and owns no
planner, cost-model, history, calibration, attestation or QEMU-instrumentation work.

Two sets have different jobs in this milestone:

- the **fixture cohort** is all twelve frozen consumers and proves that setup reuse is complete;
- the **workflow cohort** is the exact evidence-backed included set produced by P02M0138 and is the
  only set used to judge the ordinary workflow or a possible future planner problem.

## Required fixture shape

- The eleven non-scoped consumers share one lazily initialized, fully completed, immutable base
  result per guest run.
- The `ScopedGrants` consumer uses a separate lazily initialized result at most once per guest run.
- Initialization follows a short `Empty -> Building -> Ready|Failed` state machine. The expensive
  scenario runs outside the kernel `SpinLock`. Consumers use `try_lock()` and fail deterministically
  on contention or `Building`. The sole builder must complete `Building -> Ready|Failed`: it retries
  `try_lock()` only after each failed attempt has restored interrupts, yields between attempts and
  never spins with interrupts disabled.
- A cached result contains only immutable observations such as bytes, booleans and timestamps. It
  contains no live channel, process, memory object, capability, scheduler domain or mutable service
  topology.
- Before publication, the fixture closes its external endpoints, kills a standalone `Domain::new`
  owned only by that fixture and containing every process started directly or indirectly by the
  scenario, including the real shell. It pumps the scheduler until `live_processes().is_empty()`,
  checks the domain's resource-account counters against their captured pre-run values and drops the
  last domain reference. It must not use `new_child`, whose parent retains the child. This adds no
  general telemetry protocol or Domain-detach work.
- Every selected singleton initializes what it needs itself. No test depends on another test having
  run first.
- The twelve stable IDs, tags, evidence-backed `covers` declarations and assertion bodies remain
  separate.

## Scope

This milestone owns `run_permission_scenario`, the two result accessors, their direct callers, a
small initialization counter/marker used by regression tests, and direct timing of the selected
permission workflow. It does not change production PermissionManager behavior, test-selection rules,
planner thresholds, history schemas, guest event protocols or general benchmark infrastructure.

### Two requirements that could not be met as written

Both are in the reap, and both were measured rather than argued:

- **`live_processes()` never empties.** It stalls at four and stays there through 256 pump rounds.
  All four report `killed=true live_threads=0` - nothing of them is running. That list holds `Weak`s
  and returns whatever still upgrades, so it answers "is the `Process` object still allocated", not
  "is anything still running", and a terminated process's `Arc` is still referenced from outside this
  domain. The implemented condition is every process terminated with no live thread, which is what
  "pumps until nothing is left running" was asking for.
- **The resource counters do not return to their pre-run values,** for the same reason: charges are
  refunded in `Process::drop`. Measured after a base build: memory 0 -> 237568, threads 0 -> 4,
  handles 0 -> 0. Handles are therefore checked exactly - every endpoint, memory object and
  capability this fixture opened is closed before its result is published, which is the part that
  could let a cached result carry live state. Memory and thread slots are bounded per lingering
  terminated process rather than required to be zero, so a fixture that leaked a megabyte or left a
  fifth process behind still fails the check.

### What the reuse does not change

Failure attribution was rerun rather than assumed. The P02M0138 `dynamic_policy` mutation, applied to
the reused fixture, fails the same test at the same line with the same message and the same observed
bytes as it did before the change: `applications.rs:420`, `request_probe's undeclared storage request
was refused by the headless policy default`, with `storage granted` in hand. The tests selected ahead
of it in the same run still report `[ok]`, and the base setup count is 1 - so the failure came from
the observation, not from a rebuild. Restored, the twelve pass again.

## Correction (2026-08-19): the shell was outside the fixture domain, and the leak bound scaled itself

Two findings from an outside review, both correct, both about the teardown:

- **The real shell was spawned into `sched::root_domain()`**, which the Required fixture shape names
  explicitly as something the fixture's domain must contain - and which the comment beside the
  service spawns claimed was already true. It was true of the governed tools, because ProcessService
  creates them and `sys_process_create` uses the caller's domain; it was not true of the shell, which
  the scenario starts itself. So the one process the milestone names by hand was the one the teardown
  never reached: not killed with the group and not counted in the leak check. It now runs in the
  fixture's domain like everything else.
- **The leak bound was `lingering * RESIDUE`, computed from the count measured after the run**, so a
  sixth terminated process raised its own allowance and the check could not fail on one - while the
  comment beside it claimed it could. The bound is a constant now: at most five lingering processes,
  and memory and thread slots bounded against that constant rather than against what was observed.
  Measured after moving the shell: five for the base scenario, four for the scoped one.

The review also asked for the measurement to be pinned to the exact candidate rather than to a commit
plus a file count. `identity.txt` now carries the sha256 of `src/kernel/tests.rs` and
`src/kernel/test_suites/applications.rs` as measured.

Re-verified after both corrections: twelve tests pass, one base and one scoped setup, 48.6s
whole-command against the 191.473s baseline.
