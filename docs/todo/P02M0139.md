# P02M0139 - Reuse the PermissionManager test fixture without sharing test state

Status: TOOLING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Stop rebuilding the same PermissionManager integration topology for every assertion while preserving
twelve separately selectable tests and their failure attribution.

Twelve tests call `run_permission_scenario`. Eleven take the same non-`ScopedGrants` branch after the
same package parsing, service creation, channel topology, governed launches, pipelines and shell
session have already run. The twelfth continues into scoped graphics/audio grants. The repeated work
is a fixture-boundary problem, not a reason to merge the tests or redesign the planner.

This milestone starts after P02M0138 freezes the twelve-consumer inventory and its selection
regression. That correctness oracle is its only dependency. It is independent of P02M0137 and owns no
planner, cost-model, history, calibration, attestation or QEMU-instrumentation work.

Two sets have different jobs in this milestone:

- the **fixture cohort** is all twelve frozen consumers and proves that setup reuse is complete;
- the **workflow cohort** is the exact evidence-backed included set produced by P02M0138 and is the
  only set used to judge the ordinary workflow or a possible future planner problem.

## Required fixture shape

- The eleven non-scoped consumers share one lazily initialized, fully completed, immutable base
  result per guest run.
- The `ScopedGrants` consumer uses a separate lazily initialized result at most once per guest run.
- Initialization follows a short `Empty -> Building -> Ready|Failed` state machine. The expensive
  scenario runs outside the kernel `SpinLock`. Consumers use `try_lock()` and fail deterministically
  on contention or `Building`. The sole builder must complete `Building -> Ready|Failed`: it retries
  `try_lock()` only after each failed attempt has restored interrupts, yields between attempts and
  never spins with interrupts disabled.
- A cached result contains only immutable observations such as bytes, booleans and timestamps. It
  contains no live channel, process, memory object, capability, scheduler domain or mutable service
  topology.
- Before publication, the fixture closes its external endpoints, kills a standalone `Domain::new`
  owned only by that fixture and containing every process started directly or indirectly by the
  scenario, including the real shell. It pumps the scheduler until `live_processes().is_empty()`,
  checks the domain's resource-account counters against their captured pre-run values and drops the
  last domain reference. It must not use `new_child`, whose parent retains the child. This adds no
  general telemetry protocol or Domain-detach work.
- Every selected singleton initializes what it needs itself. No test depends on another test having
  run first.
- The twelve stable IDs, tags, evidence-backed `covers` declarations and assertion bodies remain
  separate.

## Scope

This milestone owns `run_permission_scenario`, the two result accessors, their direct callers, a
small initialization counter/marker used by regression tests, and direct timing of the selected
permission workflow. It does not change production PermissionManager behavior, test-selection rules,
planner thresholds, history schemas, guest event protocols or general benchmark infrastructure.

  - Pin the revision, host/kernel, CPU/memory, KVM availability, compiler, QEMU and exact commands.
  - Freeze the public plan, its exact workflow cohort and every emitted `TEST_SELECTION` guest
    command before timing. Prepare the required x86_64 artifacts; for each distinct command, run one
    immediate warm-up followed by five consecutive timed executions in the same pre/post command
    order for:
    - one `Probes` singleton;
    - one `GovernedTools` singleton;
    - the `ScopedGrants` singleton;
    - the complete twelve-ID fixture cohort; and
    - the workflow cohort, if it differs from the fixture cohort.
  - If the public plan expands the workflow cohort, also retain five warm samples of that exact
    production-lowered guest command. Otherwise record `not-expanded` and add no extra run.
  - Run the public PermissionManager verification command once as an integration check:
    `./verify.sh --for src/user/services/core/src/permission_manager.rs --allow-shadow`. Do not use
    five history-mutating public runs as the timing series.
  - Retain stdout, stderr, status, whole-command monotonic duration and the plan-emitted
    `TEST_SELECTION` command temporarily under ignored `.build/benchmarks/permission-fixture/`;
    transcribe all five exact duration/status pairs and the measurement identity into the tracked
    Results section. Do not depend on the guest's thresholded per-test timing text.
  - Record the current runtime setup count. The expected diagnostic is eleven completed base setups
    plus one completed scoped setup for the twelve-ID run.

- [ ] **M1.2 - Publish immutable results, not a shared live topology.**
  - Split scenario execution from assertion access without changing the observations produced.
  - Initialize the base result on the first non-scoped request, complete the whole scenario, then
    publish the immutable result. Later non-scoped consumers only read it.
  - Initialize and publish the scoped result independently on its first request.
  - Never expose a partly initialized result. A setup failure returns the original diagnostic, marks
    that class unusable for the remainder of the guest run and cannot become empty/default
    observations or trigger retry-shopping.
  - Complete the teardown and leak checks in the Required fixture shape before changing the state to
    `Ready`; do not retain live kernel objects or mutable service state between assertions.

- [ ] **M1.3 - Preserve standalone execution and failure attribution.**
  - Keep all twelve `tagged_test!` declarations and assertion bodies separate.
  - Preserve the P02M0138 canonical stable-ID map and declaration markers byte-for-byte: eleven base
    consumers and one scoped consumer. New accessors do not become the membership oracle, and
    test-only failure-injection callers are not members of the production cohort.
  - A singleton from each class passes in a fresh boot and initializes only its required result.
  - Grouped subsets pass when their earliest declared selected consumer is the probe, a
    governed-tool assertion or the scoped-grant assertion; `TEST_SELECTION` is not treated as an
    ordering interface.
  - Repeated reads return byte-identical observations and do not rerun setup.
  - A test-only counter or log marker proves base initialization `<= 1` and scoped initialization
    `<= 1` per guest run without adding a production telemetry protocol.

- [ ] **M1.4 - Cover the fixture boundary with focused regressions.**
  - Run the three representative singletons, the eleven non-scoped IDs together, all twelve IDs
    together, and the ordinary PermissionManager verification workflow.
  - Inject a base initializer failure and a scoped initializer failure; each must fail the requesting
    test and leave no readable partial cache.
  - Force a consumer/read collision with terminal publication and prove that the builder still
    publishes exactly one `Ready|Failed` state rather than stranding `Building`.
  - Run unrelated tests immediately before and after the fixture cohort and require the post-reap
    resource baseline and those tests to remain unchanged.
  - Preserve every original assertion body byte-for-byte. Rerun one named P02M0138 watched-fail
    mutation and require the same named assertion and test attribution before and after fixture
    reuse.
  - Use `./verify.sh` for repository verification. Do not add a hand-maintained cross-architecture
    QEMU matrix or new guest instrumentation.

- [ ] **M1.5 - Remeasure and make an explicit keep/no-go decision.**
  - Repeat the same warm-up and five raw samples from M1.1 on the same host and prepared inputs.
  - For `KEEP`, require the fixture-cohort median guest run to be at most 65% of its baseline median
    and require one base plus one scoped initialization with every original assertion executed.
  - Record the workflow cohort's direct before/after samples and one externally timed public
    before/after plan and integration run. Do not infer a planner issue from the fixture cohort alone.
  - Record exactly one decision: `KEEP` if the target and all isolation checks pass; otherwise revert
    or decline the fixture change and close this milestone as a measured no-go.
  - Record `PLANNER_FOLLOW_UP_WARRANTED=yes|no` using the boundary below. Do not create or reserve a
    planner milestone here.

## Planner decision boundary

This milestone neither specifies nor authorizes planner work. Record
`PLANNER_FOLLOW_UP_WARRANTED=yes` only when every condition below is true after the fixture decision:

1. the production plan expands the workflow cohort to a strict superset;
2. across the five warm samples, the direct workflow-cohort median is at most 65% of the
   production-lowered guest median;
3. the median difference is at least 30 seconds; and
4. the production-lowered guest median is at least 50% of the externally measured wall time of the
   one public integration run.

Otherwise record `PLANNER_FOLLOW_UP_WARRANTED=no`. A `yes` is advisory and still requires explicit
approval before another milestone is created. Any approved proposal must compare the expected cost
of the exact selection with the full suite rather than use raw test count alone; this milestone does
not design that cost model. QEMU instrumentation, StateStore, history redesign, model fitting and
attestation remain out of scope.
