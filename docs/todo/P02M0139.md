# P02M0139 - Reuse the PermissionManager test fixture without sharing test state

Status: TOOLING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Stop rebuilding the same PermissionManager integration topology for every assertion while preserving
twelve separately selectable tests and their failure attribution.

Twelve tests call `run_permission_scenario`. Eleven take the same non-`ScopedGrants` branch after the
same package parsing, service creation, channel topology, governed launches, pipelines and shell
session have already run. The twelfth continues into scoped graphics/audio grants. The repeated work
is a fixture-boundary problem, not a reason to merge the tests or redesign the planner.

This milestone starts after P02M0138 freezes the twelve-call-site inventory and its selection
regression. That correctness oracle is its only dependency. It is independent of P02M0137 and owns no
planner, cost-model, history, calibration, attestation or QEMU-instrumentation work.

## Required fixture shape

- The eleven non-scoped consumers share one lazily initialized, fully completed, immutable base
  result per guest run.
- The `ScopedGrants` consumer uses a separate lazily initialized result at most once per guest run.
- A cached result contains only immutable observations such as bytes, booleans and timestamps. It
  contains no live channel, process, memory object, capability, scheduler domain or mutable service
  topology.
- Every selected singleton initializes what it needs itself. No test depends on another test having
  run first.
- The twelve stable IDs, tags, evidence-backed `covers` declarations and assertion bodies remain
  separate.

## Scope

This milestone owns `run_permission_scenario`, the two result accessors, their direct callers, a
small initialization counter/marker used by regression tests, and direct timing of the selected
permission workflow. It does not change production PermissionManager behavior, test-selection rules,
planner thresholds, history schemas, guest event protocols or general benchmark infrastructure.

## Work

- [ ] **M1.1 - Measure the post-P02M0138 behavior before changing the fixture.**
  - Pin the revision, host/kernel, CPU/memory, KVM availability, compiler, QEMU and exact commands.
  - Prepare the required x86_64 artifacts, run one warm-up, then retain five raw timed samples for:
    - one `Probes` singleton;
    - one `GovernedTools` singleton;
    - the `ScopedGrants` singleton;
    - the complete twelve-ID selection;
    - `./verify.sh --for src/user/services/core/src/permission_manager.rs --allow-shadow`.
  - Retain stdout, stderr, status, per-test timings and the plan-emitted `TEST_SELECTION` command
    under ignored `.build/benchmarks/permission-fixture/`.
  - Record the current runtime setup count. The expected diagnostic is eleven completed base setups
    plus one completed scoped setup for the twelve-ID run.

- [ ] **M1.2 - Publish immutable results, not a shared live topology.**
  - Split scenario execution from assertion access without changing the observations produced.
  - Initialize the base result on the first non-scoped request, complete the whole scenario, then
    publish the immutable result. Later non-scoped consumers only read it.
  - Initialize and publish the scoped result independently on its first request.
  - Never expose a partly initialized result. A setup failure remains a test failure and cannot be
    cached or translated into empty/default observations.
  - Do not retain live kernel objects or rely on service state left mutable between assertions.

- [ ] **M1.3 - Preserve standalone execution and failure attribution.**
  - Keep all twelve `tagged_test!` declarations and assertion bodies separate.
  - A singleton from each class passes in a fresh boot and initializes only its required result.
  - Grouped subsets pass when their first selected consumer is the probe, a governed-tool assertion,
    or the scoped-grant assertion.
  - Repeated reads return byte-identical observations and do not rerun setup.
  - A test-only counter or log marker proves base initialization `<= 1` and scoped initialization
    `<= 1` per guest run without adding a production telemetry protocol.

- [ ] **M1.4 - Cover the fixture boundary with focused regressions.**
  - Run the three representative singletons, the eleven non-scoped IDs together, all twelve IDs
    together, and the ordinary PermissionManager verification workflow.
  - Inject a base initializer failure and a scoped initializer failure; each must fail the requesting
    test and leave no readable partial cache.
  - Preserve all original assertion failures with one focused temporary production mutation from
    P02M0138.
  - Use `./verify.sh` for repository verification. Do not add a hand-maintained cross-architecture
    QEMU matrix or new guest instrumentation.

- [ ] **M1.5 - Remeasure and make an explicit keep/no-go decision.**
  - Repeat the same warm-up and five raw samples from M1.1 on the same host and prepared inputs.
  - Require the twelve-ID median guest run to be at most 65% of its baseline median.
  - Require one base initialization and one scoped initialization for the twelve-ID run, with every
    original assertion still executed.
  - Record the ordinary workflow's before/after plan, selected IDs, step timings and total wall time.
  - Record exactly one decision: `KEEP` if the target and all isolation checks pass; otherwise revert
    or decline the fixture change and close this milestone as a measured no-go.
  - Do not create or reserve a planner milestone here.

## Conditional planner follow-up

Create a later planner milestone only if the completed measurements prove all three facts:

1. direct exact-ID execution is materially faster;
2. the production plan nevertheless expands that selection to the full suite; and
3. the expansion, rather than build, boot or fixture time, is the measured bottleneck.

If the plan already hands over the exact small ID set, or another stage dominates, do not change the
planner. Any later proposal must start from that concrete profile. QEMU instrumentation, StateStore,
history redesign, model fitting and attestation remain out of scope.

## Definition of done

- The base result initializes at most once and the scoped result at most once per guest run.
- No cached result contains live or mutable test state.
- Every stable test remains independently selectable and retains its assertions and attribution.
- Singleton, grouped, failure-injection and ordinary-workflow regressions pass.
- The predeclared performance target is met, or the optimization is explicitly declined and reverted.
- Raw before/after samples and the `KEEP` or no-go decision are recorded below.
