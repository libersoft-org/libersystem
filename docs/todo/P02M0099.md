### What ticking a driver item costs, which is why two finished ones are not ticked

STATED HERE BECAUSE IT IS A PROPERTY OF THIS FILE RATHER THAN OF ANY ITEM IN IT (2026-09-16). The
precedent is explicit and is the one this file set for itself: `virtio-blk maintenance` carried
"IMPLEMENTED 2026-09-09, awaiting its three-target suite run before it is ticked" and was ticked only
after that run. So a driver item is not closed by working; it is closed by working ON THREE TARGETS.

THAT MAKES THE SLOW-TARGET RUNS PART OF EVERY DRIVER ITEM'S COMPLETION AND NOT A FINAL SWEEP, and
the two written this week are where it shows. NVMe, AHCI, SDHCI and HDA each have a host-tested decision core, a
manifest entry and DMA declaration, a QEMU model wired into the harness, an oracle that writes a
sector and reads it back, and a measured bind window. On x86_64 they are finished. None is ticked,
and the only thing missing from any of them is the run on aarch64 and riscv64.

THE CONSEQUENCE IS WORTH SEEING PLAINLY: if those runs are deferred until this file is complete, this
file cannot become complete, because completing it means ticking items that the runs are what closes.
The two orderings that resolve it are a decision rather than a discovery - run the slow targets at
each driver item's boundary, which is what the precedent above describes, or accept a target-by-target
close and tick an item on x86_64 with the other two recorded as outstanding. This file does not choose
between them; it records that one of them has to be chosen, and that the choice is not the
implementer's to make quietly.

UNTIL IT IS MADE, THE RATIONAL ORDER IS TO BATCH. Every driver finished before the next slow-target
run closes in that run rather than needing one of its own, so the cost of the decision falls with
every item written in the meantime.

                              execution model, the AML interpreter, the identity discriminant)

A shared library closes on host tests and hostile fixtures and never on a bind. An in-controller
class module closes on the contract in the USB section - controller-driven lifecycle, a bounded
per-class resource budget and an observable effect - and never on an independent bind. A prerequisite
closes on the decision being recorded and the mechanism existing, not on a device appearing.

## What the binder does not reach yet, and who extends it

Measured 2026-08-28, because three of the four things groups 2 and 3 assume were explicitly REFUSED
by [P02M0163](P02M0163.md) and are not arriving from anywhere else.

- **A claimable device exists for every PCI function; a RESOURCED one does not.** Corrected
  2026-08-30: this said NVMe, AHCI and HDA "have no entry", and P02M0163 closed that - `device.rs`
  now pushes a `DeviceEntry` for every remaining function of the scan, carrying the class triple and
  the address under `TRANSPORT_PLAIN_PCI`. What those entries carry is `bar_phys: 0, bar_len: 0,
  msix_cap: 0`: the function is claimable and has NO resource profile, so there is still nothing to
  hand any of them a BAR or an MSI-X vector through. That, and not the entry, is what the first
  plain-PCI item owns.
- **There is no firmware inventory.** P02M0163 refuses ACPI and FDT in as many words: the FDT parser
  produces a `BootInfo` - RAM banks, CPU ids, controller addresses - not an inventory with
  `compatible` strings a rule could match, and there is no AML namespace on x86_64 at all.
- **The binding unit is a PCI function.** `BindingId` is bus, device, function and generation. A USB
  interface, an NVMe namespace and a hotplug slot are not expressible in it.
- **There is no arrival or removal event.** The PCI scan runs once at boot. P02M0163 refuses hotplug
  because a milestone promising it would have had to build the mechanism as well.

- **A PROVIDER CAN BE WITHDRAWN AND THE CATALOGUE NOW SAYS SO; NO DRIVER DOES IT.** Corrected
  2026-08-30 - P02M0164 closed most of this and the rest of the paragraph would otherwise send the
  first implementer to build what is already there. `Withdraw` is opcode 6 of the driver protocol and
  DeviceManager handles `BindingEvent::Withdrawn`; the catalogue's `subscribe` is a SERVED stream
  carrying the snapshot and the live additions, `provider-info` now carries a `live` flag so a
  withdrawal travels on that same stream identified by slot and provider generation, and a
  `requires` edge both WAKES a `DependencyPending` node when its provider appears and STOPS an online
  one when its provider is withdrawn. A per-consumer `open` mints a connection per consumer with a
  declared consumer limit, so a second or late consumer is no longer stranded IN SHAPE.

  **AND ITS CONNECTION ACCOUNTING HAS LANDED; THE FIRST-HANDOFF RULE IS WRITTEN HERE SO THE NEXT
  MIGRATION READS IT RATHER THAN REDERIVING IT** (corrected 2026-08-31). The previous version of this
  paragraph declared the accounting a BROKEN PREREQUISITE in three places and assigned the repair to
  the first destination migration. That migration happened - AudioService - and the repair went with
  it. All three are closed, and the paragraph is kept rather than deleted because what replaced them
  is a RULE later items must follow:

  - THE INITIAL CONNECTION IS COUNTED, and the rule is that EXISTING PLUS PROMISED is the number
    every minting path checks. Publication initialises `consumers` to zero and the offered channel
    the driver made itself is counted separately while it still sits in the entry; the two together
    are `outstanding`. So a provider declaring one consumer cannot have its initial holder and one
    `open` alive at once, which is what the old zero-plus-uncounted-offer arrangement allowed.
  - THE OFFERED CHANNEL IS THE FIRST PUBLIC CONNECTION, and served `open` is where it is handed out.
    This is the first-public-handoff rule, and it is one rule rather than two paths: `open` MOVES the
    offered endpoint to the asking consumer and counts it, and only mints a new pair once that one is
    gone. It is never DUPLICATED, because a duplicate shares the driver's reply queue with whoever
    holds the original - the exact failure the per-consumer factory exists to prevent. Without this,
    the public factory could not deliver the first connection for a default single-consumer provider
    at all: the one connection it may serve was reachable only through the private `Catalogue::take`.
  - EVERY MINTING PATH IS ACCOUNTED, THE BOOT'S OWN INCLUDED. `Catalogue::take`, `mint_connection`
    and served `open` all check the driver's declared bound before handing anything out and all
    increment on success; `Catalogue::disconnected` gives the place back when a driver reports a
    consumer's endpoint closing, which is what makes reconnect expressible. The boot probe was the
    one path that minted without consulting or incrementing anything, so a declared bound was
    understated before the first public ask; it is checked now, and a driver asked for more
    connections than its entry declares is a manifest that is wrong about the driver.
  - THE MANIFEST BOUND IS RECONCILED AT BUILD TIME. `system-manifest` carries the same
    `MAX_PROVIDER_CLIENTS = 8` the drivers' served set is sized to and refuses an entry declaring
    more, so a count that is accepted at build time is one the driver can actually serve.

  So P02M0164 is MET as a mechanism, and what remains is per DESTINATION. A destination migration no
  longer owns a repair - it owns its own subscribe, attach, detach and reconnect, and it can rely on
  the accounting above being there.
  WHAT IS ACTUALLY MISSING IS THE PRODUCING SIDE AND THE MIGRATION. No driver sends the message: xHCI
  creates its block channel unconditionally, "Always created" by its own comment, answers with an
  error status when no stick is attached, and on a detach drops its storage state and leaves the
  publication standing. Destination discovery has since moved: NetworkService and InputService open
  their initial providers through catalogue snapshots; AudioService watches audio publications; and
  DisplayService subscribes and reacquires a display connection after a driver restart. These are
  partial lifecycle migrations, not the complete multi-provider contract. The destination table
  below owns the remaining identity, live selection, detach/failover and reconnect work.

- **THE ONE RULE THIS MILESTONE STATES IS BROKEN BY THE MECHANISM EVERY NEW DRIVER MUST USE.** The
  head says no driver may add a "source `match` arm", and resources are handed out by exactly that:
  a literal name list - `driver_name == b"virtio_input" || driver_name == b"virtio_net" || ...` -
  decides which drivers get an MSI-X vector. A new driver that needs an interrupt has no way to say
  so except by being added to it, so the rule describes an intention rather than a constraint.

AND ONE OF THESE IS NOT A NARROW EXTENSION, WHICH THE RULE BELOW MUST NOT SWALLOW (added
2026-08-30). The binding unit being a PCI function is not a gap a driver widens on its way past. The
identity is BDF plus generation in `BindingId`; provider origin is bus/device/function in
`provider-info`; the manifest's match vocabulary has exactly two transports, `virtio-pci` and
`plain-pci`, and every predicate beside them is a PCI field; and the kernel's claim and release
address a PCI function. A PL011, a firmware-described 16550, an ACPI namespace device, an I2C child,
a USB interface and an NVMe namespace are not one row added to that - they are a DISCRIMINATED
identity, and changing the identity type reaches matching, claim and release, binding ids, provider
origins, policy keys, diagnostics, revocation and generation handling at once.

Owning that inside whichever UART or storage driver arrives first is how a system-wide name acquires
one driver's shape: every later item then inherits whatever that driver happened to need, and the
non-PCI items that follow have no sound public identity at all. So it is an ARCHITECTURAL
PREREQUISITE with its own approval, not a driver's bullet - stated here, owned elsewhere, and named
by every item that needs it:

    a discriminated, stable device-node identity carried through matching, claim/release,
    binding ids, provider origins, policy, diagnostics and generation, with transport-specific
    resource and teardown hooks, and a manifest match vocabulary that can express a
    firmware-described node without pretending it is a PCI function.

Until it exists, the items that need it are BLOCKED and say so; the plain-PCI resource profile below
does NOT need it, because a plain-PCI function is already expressible.

THE RULE FOR EVERYTHING ELSE, AND IT IS THE WHOLE ANSWER: the FIRST driver of a family that needs one
of these owns the NARROW extension it needs and says so in its own bullet.

**AND "FIRST" MEANS FIRST IMPLEMENTED, NEVER A NAMED DRIVER** (corrected 2026-08-30). A previous
round wrote the rule and then fixed three of its instances to particular drivers - the plain-PCI
resource profile to NVMe, the SCSI core to virtio-SCSI, the I2C contract to HID-over-I2C - while the

The rule is therefore applied uniformly and in every occurrence, including the tables below:

    the plain-PCI RESOURCE PROFILE - the BAR and MSI-X vector a plain-PCI entry does not carry - is
      owned by the first implemented plain-PCI item, whichever it is. NVMe is the LIKELIEST because
      it stands first in the list, and it is not the owner by name. This is a NARROW EXTENSION and
      not a new identity: a plain-PCI function is already expressible, which is exactly the

    the I2C controller contract is owned by the first implemented I2C consumer - HID-over-I2C,
      SSIF or another

AND ONE PATH NEEDS NO FIRMWARE NODE AT ALL - BUT IT IS NOT CHEAP, AND THIS SAID IT WAS (corrected

    THE INGESTION CONTRACT IS `SYS_ENTROPY_ADD`, AND THE SUBMITTER DOES NOT SAY WHAT ITS BYTES ARE

    division is the whole security of the call - a driver that could name its own credit could seed a

    there is nothing to connect to, which is the point.

    SHORT AND FAILING REQUESTS. A short answer is an answer and is submitted as it came; a request
    that times out leaves the descriptor with the device rather than reposting over it, because a
    reused descriptor corrupts a virtqueue for the life of the guest; an empty submission is credited
    zero AND STILL MOVES THE POOL, so a failing device cannot make the output repeatable.

    NEVER PROOF OF HEALTH. `SYS_ENTROPY_HEALTH` answers credit and provenance - how many bits, how
    many submissions, from which kinds of source, and whether this machine has a hardware instruction
    at all. The one boolean says the threshold was reached. Whether a machine seeded only by a
    paravirtual device is good enough for a given purpose is the caller's question, and a kernel that
    answered it would be answering for every future caller too.

    AND IT CLOSED A REAL HOLE. `SYS_RANDOM_GET` refused outright on a machine with no hardware random
    instruction, which is two of this system's three architectures - so anything wanting key material
    had nowhere to go and the only call that always answered was the one named `insecure`. A seeded
    pool answers instead.

    THE EVIDENCE. Eight host tests in `entropy` cover the refusal below threshold, the crediting rate
    and its ceiling, the per-submission bound, DETERMINISTIC INJECTION (the expected draw was
    computed by an independent SHA-256 written against Python's `hashlib`, so it asserts the
    construction rather than self-agreement), two draws never repeating, a RESTARTED DRIVER handing
    the same device bytes over again not repeating the output, and an empty submission still moving
    the pool. Two kernel tagged tests cover what only a running kernel can: a capability that names
    no binding is refused, the submission bounds are refused before the capability is even looked at,
    and a machine with no hardware instruction refuses the secure draw until the pool is seeded and
    answers afterwards. The harness attaches `virtio-rng-pci` on all three targets in test mode, so
    the guest suite boots with the device present; the profiles that do not attach one are what keep
    the unseeded refusal reachable.

  suite is green with `virtio-rng-pci` attached in test mode: x86_64 394, aarch64 382, riscv64 385.

  to be implemented and the rule three sections down says the first one answers it for all three:
  "whether a virtio port, a UART and a USB adapter are one contract, or whether the byte stream is
  the base and the line-coding and control lines are a serial layer on top".

      THE BYTE STREAM IS THE BASE. `liber:device@1`'s `console-stream` is it, and it is deliberately
      not a serial port: `attach` settles a version, `write` answers with what it took, `receive`
      hands back a stream endpoint, and there is no baud rate, no parity, no stop bits, no DTR, no
      RTS, no break and no line-status event anywhere in it. `ProviderKind::ConsoleBytes` is what a
      publisher of one publishes, and a publication carries a NAME so several of them on one device
      can be told apart.

      WHY THE BASE IS NOT THE SERIAL PORT, and this is the half that had to be decided rather than
      drifted into. A virtio-serial port has NO line coding at all - the specification does not
      define one - so a common contract carrying baud and parity would make every virtio port answer
      a question it has no answer to, and the honest answer would have to be a refusal on every
      operation the base defines. A UART and a USB CDC-ACM adapter do have those controls, and both
      have them as a DIFFERENT set: CDC-ACM carries line coding in a class request and a UART in
      device registers. So the line-coding and control lines are a SERIAL LAYER, a second interface
      a driver that has them serves IN ADDITION to the byte stream - not fields on the byte stream
      that two of the three publishers would leave empty.

      WHAT A LATER CLAIMANT THEREFORE OWES, so this is a decision rather than an opinion. A 16550, a
      PL011 or a CDC-ACM adapter publishes `ConsoleBytes` and serves `console-stream` over
      `drivers::serial_port` - the module this item extracted for exactly that reuse, which is
      transport-free: it takes a receive queue, a transmit queue and a DMA buffer, and knows nothing
      about virtio beyond them. The serial layer is a SEPARATE interface with its own provider kind,
      owned by the first of those three that needs it, and a consumer that only wants bytes never
      has to hold it.

## 2. Generic and universal controllers

Standardized silicon interfaces: one driver per specification, every vendor's part behind it. Ordered
by what a real machine cannot be used without - storage and console first, because a machine that
cannot read its disk or print a line cannot be debugged - with server and legacy compatibility paths
at the end.

- [ ] **NVMe** generic PCIe storage controller: controller reset/enable, admin plus I/O
  queues, identify controller/namespaces, PRP transfers, flush, read/write, status and
  timeout recovery behind the existing block contract used by `virtio-blk` and USB
  storage. Bound queue depth and transfer size, validate every completion ID/phase,
  support multiple namespaces/controllers and cleanly fail unsupported metadata,
  protection, zoned or vendor commands rather than partially interpreting them.

        driver.nvme: sqe slot 0 dw0 00010006 entries 8
        driver.nvme: command 01 got id 0 waiting for 5, sq 0 head 0, dw3 00010000

    The submission entry was read back out of queue memory before the doorbell and carried the id
    that was sent, so the write landed where the controller reads. The completion did not: `sq 0
    head 0` says the controller had consumed NOTHING from that queue while five commands were
    outstanding, so it was not answering anything. Every field of the entry was zero except the
    phase bit.
    A SIXTEEN-BYTE WRITE FROM A DEVICE IS NOT ATOMIC TO ITS READER. The phase bit became visible
    before the id, the status and the queue head did, and a driver that reads the whole entry and
    then decides believes a completion that has not finished arriving. A barrier BEFORE the read
    orders nothing about a write still in flight while it runs.

    pass's is a barrier taken and the entry read again. And command id ZERO IS NEVER ISSUED - a rule

    is by construction nobody's, which makes it a completion that has not arrived rather than one
    belonging to somebody else. Those want opposite responses: wait, or give up.

     division is exact. A descriptor in one unit removes the question; until then the division
     refuses rather than truncating, which for a boot surface means serial-only - the same
     degradation as a machine with no framebuffer at all.

     an overlapping one, and a reserved channel that is either; whoever takes this item should not
     redo it.

     ways to get a scanout - a `DisplayController` privilege and a syscall for the boot surface, a
     catalogue subscription for a GPU - and only the second can be replaced when its publisher goes
     away. Publishing the boot surface as an ordinary `ProviderKind::Display` would make the handoff
     a withdrawal and an adoption, which is the service's own path for "the GPU driver rebound".
     AND IT IS NOT A REFACTOR OF WHAT EXISTS, which this plan said it was and which was wrong
     (corrected 2026-09-15, after looking). It needs TWO mechanisms this tree does not have, both
     checked rather than assumed:
     - SOMETHING TO HAND OVER. `SYS_FRAMEBUFFER_MAP` maps into the CALLER's address space and answers
       with a virtual address; `MemoryObject::create_in` and `DmaBuffer::create_in` both ALLOCATE
       fresh physical pages. Nothing in this kernel wraps an EXISTING physical range in a
       transferable object, and `MemoryObject`'s `Drop` retires its frames to the allocator - which
       for a firmware aperture would hand MMIO out as ordinary RAM. That object is a capability
       decision: a handle that maps arbitrary physical memory is what a capability system must not
       hand out, so it would be minted by the kernel for one range it already owns and nothing else.
     - SOMETHING TO PUBLISH IT. Every publication in the catalogue is keyed to a `BindingId` -
       `publish_all(binding, entry, offers)` - which is a device CLAIM: a bus, a device, a function
       and a generation. A boot framebuffer is not a device and has no claim, so there is no path by
       which a program with no device publishes a provider at all. Either that path exists, or the
       boot surface becomes a synthetic device node; both are new mechanisms.
     Whoever takes this owns both first. The syscall would then be what the PUBLISHER uses rather
     than what the consumer uses, which is the shape - but the shape is the end of the work and not
     the start of it.
  3. THE CACHE POLICY IS NOT STATED ANYWHERE AND IS THEREFORE NOT CHECKABLE. `sys_framebuffer_map`
     maps `PRESENT | WRITABLE | NO_EXECUTE` with no memory type, which is write-back on x86_64 and

     the surface is ordinary RAM, and WRONG for a discrete card's linear aperture, which wants
     write-combining. The descriptor carries the policy the surface was mapped with; the machines in
     the harness assert `write-back`; and the day a target needs write-combining, the field is where
     that is said rather than a third mapping path.

  ITS MEASURABLE LIMITS: a maximum extent and pitch refused rather than clamped (the same ceiling
  the image model already states), a pitch at least the minimum row for the element size, a surface

  one of them is a firmware-supplied number, which is the reason they are limits at all.

  - THE WIRE STATES ONE UNIT AND IT IS BYTES. `bootproto::Framebuffer::bpp` is `bytes_per_pixel`, so

    masks it is derived from are read; the kernel copies rather than divides. The two ramfb paths
    state 4 where they stated 32.
  - AND THE KERNEL VALIDATES WHAT IT READS, which is the half that was missing entirely. `describable`
    asks what a geometry has to satisfy for a row to mean anything: a non-zero extent, an element size
    a pixel can be, and A PITCH THAT HOLDS A WHOLE ROW OF IT. That last one was never checked at all -

    is not a smaller picture, it is every row after the first read at the wrong offset. Refused rather
    than repaired, which for a boot surface means serial-only: the same answer a machine with no video

  - THE FIXTURE IS ABOUT THE GEOMETRY AND NOT THE ARITHMETIC: a pitch one byte short, a zero element,

    see from userspace.

  responses, isolate codec/controller failure, and leave vendor DSP firmware, jack
  policy and machine-specific routing quirks to Phase 5.

  **ITEM PLAN (2026-09-16), written before any code because the rule below says so.**

  CLASSIFICATION: `driver`, the fourth consumer of the plain-PCI resource profile and the first of
  them that is not storage. That matters for what it tests about the profile: the three before it all
  published `block`, so "a resourced plain-PCI function can serve a provider" had only ever been
  shown for one kind of provider.

  WHAT IT REQUIRES THAT ALREADY EXISTS: the same prerequisite set as the storage drivers, and the
  PCM contract `virtio-snd` already serves, published under `provider::AUDIO`. This item consumes
  that contract and defines none: the roadmap says in as many words that playback and capture go
  through the SAME contract as `virtio-snd` and USB Audio, so a second audio wire would be the block
  wire's mistake repeated in a different family.

  WHAT IT OWNS THAT DOES NOT YET EXIST: THE HDA COMMAND AND CODEC LAYER, and it is almost entirely
  decisions rather than register access, which is why most of it belongs in a host-tested module:
    - The CORB and RIRB rings: a command is a 32-bit verb and a response is a 64-bit pair, both in
      rings whose read and write pointers the controller and the driver each own half of. The
      arithmetic is the same shape as every other ring in this tree and is where this driver would be
      wrong in the same way the NVMe one was.
    - The VERB ENCODING: a codec address, a node id, a command and a payload packed into one word,
      with two payload widths depending on which command it is. A verb built with the wrong width
      addresses a different node with a different command and is answered, not refused.
    - THE WIDGET GRAPH WALK, which is the work the group-2 table warns about when it calls this item
      large. A codec reports function groups, each reports widgets, each widget reports a type and a
      connection list, and a route from a pin to a converter is a path through that. It is bounded
      here: the FIRST pin complex that reports an output-capable connection to an audio-output
      converter, with the walk bounded by the node counts the codec itself reports.
    - The stream format word and the buffer descriptor list.

  WHAT IT EXCLUDES: capture in the first slice, because a route to a converter is the same problem
  twice and playback is the one with an oracle; unsolicited responses beyond bounding them;
  multiple codecs beyond taking the first that answers; vendor DSP firmware, jack policy and
  machine-specific routing, which the item text puts in Phase 5; and MSI, because this driver polls
  like every other one here.

  TARGET DEVICE MODEL: QEMU `-device intel-hda` with an `hda-output` codec behind it.

  OBSERVABLE-EFFECT ORACLE: the convention rejects "the driver reached Online", and for audio it
  would be especially empty. The effect is that the CONTROLLER CONSUMED THE BUFFER: a stream is
  started over a known buffer descriptor list and the controller's own link position counter is read
  advancing past the bytes it was given, which is the hardware saying it played them. A codec that
  answered its identity verb with a real vendor id is the second half, because a route built on a
  codec that answered nothing would still start a stream that plays silence.

  MEASURABLE LIMITS: a bounded CORB/RIRB depth with the response wait typed rather than spun; the
  widget walk bounded by the codec's reported node counts and refused if they exceed what one page of
  descriptors can hold; one stream, one buffer descriptor list, one fragment.

  DEFINITION OF DONE FOR ITS CLASS: host tests over the verb encoding, the ring arithmetic, the
  format word and the graph walk with malformed codec answers; the QEMU model proving the governed
  process, the DeviceManager binding and the destination contract; the bind window recorded per
  target; registered in the verification model in the same change. Acceptance on aarch64 and riscv64
  is a separate measurement on each and this plan does not claim it.

  **WHERE IT STANDS (2026-09-16): UP ON x86_64 WITH ITS ORACLE PASSING.**
  `driver.hda: online (00:0d.0, codec 0, converter 2)` - the controller out of reset, the command and
  response rings running, the codec found by its identity verb, its widget graph walked, an output
  converter and a pin complex that can drive one selected, and the PCM service published under the
  SAME provider kind `driver.virtio-snd` uses. 405 tests pass.

  THE ORACLE IS THE HARDWARE SAYING IT TOOK THE BYTES, which for audio is the only thing that means
  anything: a driver that brings a controller up, routes through a codec that answered nothing and
  starts a stream over an empty buffer reports exactly what a working one reports, and plays silence.
  So the harness hands it one period over the PCM contract and then reads the controller's OWN LINK
  POSITION COUNTER, requiring it to have advanced. Reaching READY is the other half and is a claim in
  itself: this driver refuses to report in without a codec that answered with a real vendor and a pin
  that reaches a converter.

  **WHAT IT TOOK WAS FOUR ROUNDS OF MEASUREMENT AND NO REASONING THAT SURVIVED.** Every wrong guess
  is listed because each one was plausible and each one cost a build:
    - The command ring's pointer reset. The specification requires the bit written as one, READ BACK
      AS ONE - that read is the confirmation - then written as zero and read as zero. Writing one and
      waiting for it to clear waits for something the controller never does: the register sat at
      0x8000 for ever. REAL, and fixed.
    - The ring size. Sixteen entries is OPTIONAL; only 256 is required of every controller, and one
      that declines sixteen leaves the driver wrapping at sixteen while it wraps at 256. Wrong, fixed,
      and NOT the cause.
    - A diagnostic that borrowed another failure's sentence and printed the wrong register beside it,
      which sent the reader to GCTL for a problem in CORBRP.
  WHAT IT ACTUALLY WAS, and only the pointers could say it: `CORBWP 2 CORBRP 1` - the controller had
  fetched exactly one command and stopped. `RINTCNT` is how many responses it writes before raising
  the response interrupt AND HALTING THE COMMAND RING until `RIRBSTS` is cleared. At one, which is
  what an interrupt-driven driver wants, a POLLING driver gets its first answer and then silence,
  with every other register looking correct. It is 255 now and the status is acknowledged after every
  response.

  **AND ONE DEFECT IT FOUND WAS NOT ABOUT AUDIO AT ALL**, which is the part worth carrying to every
  driver here. The waits were bounded in SPIN COUNTS, and a spin is not a time: one iteration is an
  MMIO read, tens of nanoseconds on silicon and a trap into the hypervisor under emulation, three
  orders of magnitude apart. Ten million of them outlasted the two-second bind window, so
  DeviceManager killed this driver for silence before it could say what it was waiting for - and
  outlasted the BOOT window too, bringing up nine of twenty-four services, which looked like adding
  one audio driver had broken the system. The machine already has the unit: 100 Hz everywhere, READY
  due 200 ticks after BIND, every driver here binding inside 44. Bring-up takes one deadline in ticks
  and every wait shares it, so a bring-up where everything times out still finishes in time to say so.

  WHAT IS STILL OPEN: capture, which this slice excludes; unsolicited responses beyond bounding them;
  a second codec beyond taking the first that answers; the bind window recorded per target; and
  acceptance on aarch64 and riscv64.

  P02M0163 refused the second as "splitting a driver into several and giving each its own authority"

  **AND IF THE FIRST ANSWER IS CHOSEN, THE CLASS MODULE NEEDS ITS OWN CLASSIFICATION AND ITS OWN
  DEFINITION OF DONE** (added 2026-08-30). The head classifies an item as a `driver` when it
  independently claims and binds a device, and a `shared library` when it has no device and no
  binding. An in-controller class module is NEITHER: it touches a real device and it does not claim
  one, so under the current classification it either inherits P02M0098/P02M0161/P02M0162 gates it
  cannot satisfy or falls through to a parser's gates that prove nothing about a device. Both
  readings were available, which is how a USB item could have closed against whichever it preferred.

  So the head's classification gains a fifth kind, `in-controller class module`, and it closes on a
  contract of its own:

    authority     the module holds NO claim and NO Domain of its own; it operates strictly through
                    the controller's claim and the controller's resources, and the item states which
                    controller operations it may invoke and which it may not
    isolation     a bound per-class resource budget inside the controller's Domain - endpoints,
                    buffers, in-flight transfers - so one class module cannot starve another or the
                    controller, with a typed refusal at the bound
    interface     ONE named owner for the controller-to-class-module interface, which is the
                    controller item, not each class module; a class module that needs a new
                    controller operation extends that interface rather than reaching around it
    lifecycle     attach, detach and per-class teardown driven BY THE CONTROLLER, replacing the
                    independent bind/rollback a driver would have. Detach releases the class
                    module's resources and leaves the controller serving; controller teardown tears
                    down every module with it

  **DECIDED 2026-09-13: THE FIRST ANSWER. A USB class driver in this system is a MODULE INSIDE THE
  CONTROLLER'S PROCESS AND DOMAIN.** It holds no claim, binds no device and has no Domain of its own,
  and it reaches the bus only through the controller that claimed it. The per-driver registry entry,
  claim and transactional bind that a DRIVER owes therefore do not apply to a class module, and this
  document says so here rather than leaving each USB item to decide.
  WHY THIS ANSWER AND NOT THE OTHER. The second makes a USB interface a binding unit with its own
  endpoint capabilities, its own generation and composite devices - which is a SUB-FUNCTION IDENTITY,
  the same cross-cutting case as the firmware node, owned by no class driver. P02M0163 refused it once
  already as "splitting a driver into several and giving each its own authority", and choosing it here
  would put every USB class item behind an unowned prerequisite. The cost of the second answer is
  exactly why the first exists, and nothing in the class items needs what the second buys.

  AND THE MECHANISM EXISTS, which is the other half of what an architectural prerequisite closes on.

    REQUIRES   the xHCI controller and its two class modules, which is what there is to isolate
    OWNS       `drivers::usb_class` - the execution model written down, the per-class budget and its
                 typed refusal - and its wiring in `xhci.rs` and `usb_storage.rs`
    GATE       `host.drivers`, 8 new tests at each ceiling and one past it, plus the guest `usb` and

  WHAT A MODULE MAY INVOKE IS NOW A LIST AND NOT AN UNDERSTANDING: address and configure a device,
  bring an endpoint up and take it down, queue a transfer on a ring it was given, wait for a
  completion, read a descriptor. It may NOT touch the controller's registers, allocate from the Domain
  directly, enable or disable a slot, or reach any device other than the one it was attached to. A
  module that needs an operation the list does not have extends the interface in the CONTROLLER, which
  is one place and one owner.
  THE ISOLATION IS A NUMBER PER CLASS, CHARGED ON ATTACH AND GIVEN BACK ON DETACH. It was not
  hypothetical: the HID module's device list was an unbounded `Vec` that a tier of hubs full of
  keyboards fills, each one taking an endpoint and a DMA page of the controller's, and the
  mass-storage module's data buffer grew to the largest request anybody ever made and never shrank -
  inside the controller's Domain, for the life of the process. Eight HID devices with eight endpoints,
  eight rings and eight reports in flight; one mass-storage device with two endpoints, two rings and a
  data buffer bounded at one megabyte, which is the number `fit_data` now refuses past.
  THE REFUSAL IS TYPED AND SAYS WHICH CEILING IT REACHED, because "the keyboard budget is full" and
  "this controller serves one disk" are different things to tell somebody with a cable in their hand.
  A refused device is left ADDRESSED and in the inventory rather than released, so a later detach still
  gives its pages back - and a refused admission charges nothing, which the tests check by refusing
  sixteen times and requiring the usage to be where it was.
  THE LIFECYCLE IS THE CONTROLLER'S. It admits before a module takes a device and releases when the
  port goes away, in the same two places that already allocate and free the pages - so the budget
  cannot drift from the memory, and a hundred plug/unplug cycles end where they started.
    gate          the observable effect through the destination service, plus a detach-under-load
                    case and a per-class budget-exhaustion refusal - the two things an independent
                    bind would otherwise have proved

  THE BUS CONTRACT IS THREE OPERATIONS AND NO CONTROLLER VOCABULARY: a write, a read, and the
  WRITE-THEN-READ that every register access is. The third is not the first two in sequence, and the
  difference is the whole reason it is named: a repeated start with no stop in between is what stops
  another master, or the device's own register pointer, from acting in the gap. There is no clock
  rate, no bus number, no pin and no arbitration in it, so a controller item will IMPLEMENT this
  rather than having to be described by it - and the IPMI SSIF transport that consumes the same bus
  class takes it as it stands.
  AN ADDRESS IS A NEWTYPE BECAUSE THE RESERVED RANGES ARE NOT ADDRESSES. `0x00` to `0x07` and `0x78`
  to `0x7f` belong to the bus standard's general call and ten-bit addressing; a driver that addresses
  one is broadcasting rather than talking to a device, and an eighth bit shifted in by a caller that
  confused the address with the read/write byte is refused where an address enters rather than at
  each transaction.
  EVERY NUMBER THE DEVICE PUBLISHES IS CHECKED BEFORE IT IS A BUFFER LENGTH. The descriptor is refused
  when its own length field is not thirty, when its version is not `0x0100`, when its reserved bytes
  are not zero, when its report descriptor is empty or beyond this module's ceiling, when its maximum
  input length cannot hold the two-byte prefix that is counted INSIDE it, and when that maximum is
  larger than the bus will carry. The first two matter most and for the same reason: a device still in
  reset answers a register read with zeroes, which would otherwise decode as a descriptor promising
  nothing and be believed.
  AND A REPORT IS BELIEVED ONLY AS FAR AS IT ARRIVED. The declared length is checked in BOTH
  directions - longer than what the bus returned is the device asking for a read past the buffer;
  shorter than its own prefix, or longer than the device's own published maximum, is the device
  contradicting itself - and a zero length is the RESET INDICATION rather than an empty report, which
  is the only handshake this protocol has and the one a driver waits for.
  THE REPORT ID ESCAPE IS THE ONE PLACE THE ENCODING IS NOT A BIT FIELD: an id of fifteen or more
  travels after the opcode with `0x0f` in the nibble, so a driver that wrote `id & 0x0f` would address
  report 31 as report 15 and never notice. The tests assert the bytes that go out, not only the answer
  that comes back.
  IT DOES NOT PARSE A REPORT DESCRIPTOR: those bytes go unchanged to the generic HID parser
  `drivers::hid` already has, which is what keeps one report-descriptor implementation in this tree.
  WHAT REMAINS IS THE BINDING HALF, and it is the item below: it needs an I2C controller with a real
  fixture and the firmware-node device identity, neither of which has an owner yet.

### What this table changes about the plan

- **`virtio-rng` is the cheapest true start**, and it is the only one: free specification, a
  permissive reference, a QEMU model, no AML, and the one contract it creates - typed entropy
  ingestion - has exactly one consumer, which is `SYS_RANDOM_GET`.
- **Everything else drags a shared contract, and the second version of this list denied it as
  confidently as the first.** `NVMe` and `AHCI` came off because the first block driver written owns
  the canonical block wire. But `16550`, `PL011` and `virtio-serial` stayed on under the words "no
  shared contract to create on the way", while this same file says four hundred lines earlier that
  the serial contract has THREE CLAIMANTS AND NO DEFINITION. Whoever writes the first of them makes
  it - and multiport did, on 2026-09-15: the byte stream is the base, the line coding is a layer, and
  the shared cost the three of them were said not to have is `drivers::serial_port`, which exists.
- **AND `16550` IS NOT A CHEAP DRIVER BEHIND ONE SHARED DECISION EITHER** (corrected 2026-09-03).
  This paragraph called the three of them "cheap drivers behind one decision the three of them
  share", which carries the shared-contract cost and drops the other one - and the item and the
  architecture section both say what it is. The LEGACY x86 slice needs three mechanisms nothing in
  this tree has: a range-scoped REVOCABLE PORT-I/O authority, where the public driver resource
  vocabulary has no port-I/O object or syscall at all; legacy FIXED-IRQ routing and its revocation,
  which the MSI-X path does not provide; and an ATOMIC HANDOFF, because the x86 kernel programs COM1
  directly, owns IRQ4 and polls receive from the idle hook after userspace starts, with no transfer

  blockers, and the table's Note column says so rather than `trivial`. `PL011` is blocked on the same
  identity prerequisite and its Note is already honest.
- **Cheap as a driver is not cheap as a first step**, which is the thing this list keeps getting
  wrong. The question is not how big the driver is; it is how many later items consume what writing
  it forces you to define.
- **The four AML items are not driver work and must not be picked up as if they were.** Whoever wants

- **UVC, UAC2, HDA, UAS, virtio-fs and MBIM are month-scale**, and saying so here is cheaper than

One of the review's own claims was wrong and is corrected in place rather than repeated: object type

## Sixth audit (2026-08-28)

## Thirteenth audit (2026-08-28)
