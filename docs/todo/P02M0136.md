THIS MILESTONE'S PRECONDITION IS THEREFORE: `P02M0103b` carries ONE `DrawList` contract, and its

`P02M0103b` carried two mandatory `DrawList` contracts - an immutable
in-process replayable list in one item and a transportable cross-process format in another - and the
font resource is carried by whichever wins, since its lifetime, its transport and whether a raw
reference may appear in a list all differ between them. Implementing the shared seam against the
loser would have meant replacing it. `P02M0103` DECIDED IT on 2026-08-30: Profile 1's `DrawList` is
immutable, versioned, cacheable and replayable IN-PROCESS, carrying a typed resource TABLE - not
inline references - with cross-process transport becoming the named `render2d-wire` extension.
So the font resource is a TYPED HANDLE INTO A PROCESS-LOCAL RESOURCE TABLE, and the contract frozen
by the seam item below is written against that and nothing else.

Created 2026-08-15 alongside `P02M0103`'s seventh pass. `render2d` draws a `GlyphRun` - glyphs that
are already chosen, already shaped and already positioned - and that seam is deliberate: a rasteriser
has no business knowing what a script is, and a shaping engine has no business knowing what a
coverage mask is. But the seam only divides the work; it does not do half of it. Without this
milestone LiberSystem can draw text it is handed and cannot produce text from a string, which is not
a platform ordinary applications can be written on.

The division of labour, stated once so neither milestone drifts into the other:

real font file this system reads is read here**, and the end-to-end proof - font file to shaped run
to pixels - is this milestone's, against the renderer `P02M0103c` delivered. Neither side writes a
throwaway parser.

## The seam is not yet a contract, and it is this milestone's first CONTRACT item

The audit's sharpest finding: neither milestone says how a glyph ID becomes geometry. This side
produces glyph indices; that side must rasterise outlines, masks, bitmap strikes and `COLR` paint
graphs - and nothing owns the validated font bytes, the decoded glyph data, the lookup, the lifetime
or the identity between them. A glyph index and a kind flag cannot be drawn.

Two further consequences fall out of the same hole. `P02M0103`'s glyph cache WAS keyed by face, size,
transform and subpixel phase - omitting the glyph index itself, the variation coordinates this
milestone promises, and the palette and strike selection colour and bitmap glyphs need, so two
different instances of one face collided in that cache and rendered stale pixels. That key is now
corrected in both files and is stated below. And fallback produces runs over SEVERAL faces while
this milestone's `GlyphRun` carries a singular `face`, so the output of the fallback item cannot be
expressed in the type the seam item defines.

                          HOW THE HANDLE IS ATTENUATED, BECAUSE THE FIRST ANSWER NAMED RIGHTS THE
                          TRANSPORT CANNOT DELIVER (corrected 2026-09-02). This said the handle
                          arrives with map and write and neither `RIGHT_DUPLICATE` nor
                          `RIGHT_TRANSFER`. A generated typed call passes its request handles through
                          `ChannelTransport::call` to `send_caps_blocking`, and that path is
                          `SYS_CHANNEL_SEND_CAPS`, which takes each handle with `Rights::TRANSFER`
                          REQUIRED, CONSUMES it from the sender's table, and delivers it with its
                          rights unchanged. So a handle without `TRANSFER` cannot be sent at all, and
                          the only attenuating primitive - the single-handle
                          `SYS_CHANNEL_SEND_ATTENUATED` - is not what the typed transport uses.

                          that already exists: `SYS_HANDLE_DUPLICATE` takes a rights mask and refuses
                          anything the original does not already hold, so it narrows and never
                          widens. The caller creates the object (holding every right, and charged for
                          it), duplicates a handle down to exactly `MAP | WRITE | TRANSFER`, and
                          passes the COPY. It keeps the original, so the send consuming the copy
                          costs it nothing.

                              object on, and that is a code obligation with a gate rather than a
                              right it lacks. Said plainly, because a plan that claims a rights bit
                              it cannot obtain is a plan whose security argument is decoration;
                            map and write and no read, so a service that is filling a buffer cannot
                              read what the caller had in it.

  **AND THE CANONICAL-EQUIVALENCE POLICY IS PRESERVATION, DECIDED HERE** (2026-09-01). The stage
  above named "canonical-equivalence policy" and chose none, which is a slot rather than a rule: the
  composed and decomposed spellings of one string could take different fallback, shaping and cache
  paths, and two implementations following this file could disagree about every cluster boundary in a
  decomposed run while both claiming to follow it. The rule, in three parts:

    the buffer is       The pipeline NEVER rewrites the caller's bytes. No NFC, no NFD, no NFKC.
      NEVER REWRITTEN     Every offset in a `GlyphRun` - cluster starts, caret positions, selection
                          boundaries - is a byte offset into the ORIGINAL UTF-8 the caller passed.
                          This is the load-bearing half: normalising the buffer and then reporting
                          offsets into the normalised copy is how a text engine returns caret
                          positions that do not exist in the caller's string, and no mapping back
                          survives a decomposition that changes length.
    equivalence is      A canonical composition and its decomposition are ONE grapheme cluster under
      RESOLVED BEFORE     UAX #29, so itemisation and fallback see one indivisible unit either way.
      FALLBACK, NOT       THAT IS NOT ENOUGH ON ITS OWN, AND THE PREVIOUS VERSION STOPPED THERE
      INSIDE SHAPING      (corrected 2026-09-01). Atomicity keeps a sequence together; it does not
                          make two spellings COVER the same. A face may have a glyph for precomposed
                          U+00E9 and no combining acute, or the reverse - so fallback, which runs
                          before shaping, would already have chosen different faces for the two
                          spellings, and the stage allowed to resolve equivalence ran afterwards. The
                          policy and its own regression could not both be implemented.
                          So coverage is asked in a CANONICAL VIEW: a face covers a cluster when it
                          covers the cluster's canonical composition OR its full decomposition, and
                          fallback asks that question rather than asking about the raw bytes. The
                          view is a lookup over the cluster, not a rewrite of the buffer - the
                          original UTF-8 is still what every offset in a `GlyphRun` refers to, which
                          is the rule above and is unchanged. Shaping then applies whichever form the
                          chosen face actually needs. Within a run the shaper applies
                          the canonical composition and decomposition its tables require - which is
                          what OpenType shaping does in any case - and may not change cluster
                          boundaries or the byte spans reported for them while doing it.
    and it is TESTED    A regression pins it: the composed and decomposed spellings of one string
                          produce the SAME glyph sequence and the same total advance, take the same
                          fallback decision, and report cluster byte spans differing only as the two

    shaping and fallback attempts       16 fallback faces per cluster, 4 shaping retries per run
    layout passes                       8 per line, 2 per paragraph
    INPUT per shaping run               4096 code points
    INPUT per paragraph                 65536 code points
    OUTPUT per shaping run              16384 glyphs
    OUTPUT per paragraph                262144 glyphs

  THE LAST FOUR ARE ABSOLUTE, AND WITHOUT THEM THE REST BOUND NOTHING (added 2026-08-31). The item's
  own opening names per-run glyph count as one of the three limits it exists to fix, and the table
  did not contain one: every row above was either font-INTERNAL - a property of the face, which a
  larger document does not change - or PROPORTIONAL. `64x the input run` is the clearest case: it
  caps the multiplier and not the product, so an arbitrarily large source still demands arbitrarily
  large work and allocation, which is exactly the exhaustion the checked offsets do not prevent.
  A proportional rule with no absolute ceiling under it is a ratio, not a bound.

  Both directions are capped because either alone leaves a hole: an input cap without an output cap
  still admits a 4096-point run that a pathological face expands to 262144 glyphs, and an output cap
  without an input cap still admits an unbounded source whose refusal is only discovered after it has
  been read. The two are independent and BOTH refuse - whichever binds first - and the proportional
  `64x` rule continues to apply inside them rather than being replaced by them.

  A face or a document that exceeds any of them is REFUSED with the typed refusal below, not
  truncated. These are ceilings for a bounded appliance rather than derived from a corpus
  measurement; a value may be raised before the profile is frozen and not after, and raising one
  afterwards is a profile change with its conformance consequences.
  ALLOCATION IS FALLIBLE ON THIS PATH. Userspace infallible allocation exits the process when it
  fails, so "charged to the calling Domain" does not by itself produce the typed refusal this
  milestone promises: parser, cache and layout allocations use the fallible forms, cache insertion is
  transactional, and a refusal rolls back partial insertion and releases its charges. Deterministic
  work accounting makes the same input meet the same limit on every architecture.
