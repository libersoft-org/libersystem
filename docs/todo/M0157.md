# M0157 - The ABI's own guarantee, which is the one thing it cannot get wrong

Status: IN PROGRESS. An outside audit of `src/abi` against the kernel's dispatch, the userspace
runtime, LogService, the LSIDL schema and the ABI's own history. Every finding was checked against
the tree and every one held.

The crate is the right idea and most of it is done well: small, `no_std`, dependency-free, one place
for the syscall numbers and the limits, `repr(C)` throughout, checked arithmetic in the package
parser, and explicit `_pad` fields where they were needed. What it does not yet do is protect the
one thing it exists for.

**`ABI_VERSION` is a promise to an older binary, and there are no older binaries yet.** Nothing here
is versioned until the first final release, so the audit's leading finding - that two breaking
changes rode on one version - is true and does not apply. What the number still does inside one
build is catch a stale artifact, and that turned out to matter. The findings below are the ones that
stand on their own.

## Done in this round

- [x] **`ABI_VERSION` is 1 and stays 1 - the audit's first finding does not apply yet.** It argued,
  correctly on its own terms, that `SYS_WAITSET_WAIT` changing from an index to a koid and
  `SYS_WAITSET_REMOVE` changing from a handle to a koid are breaking changes that should have moved
  the number. Both are real, and both change what a number MEANS rather than where an argument sits,
  which is the shape the policy comment reads past most easily.

  **But nothing in this system is versioned yet, because there has been no release.** A version is a
  promise to something already out there; moving it records compatibility with binaries nobody has,
  and costs a rebuild of every userspace artifact to say so. Versioning starts after the first final
  release.

  This was bumped to 3 before asking, and reverted on instruction. The two changes worth naming when
  that day comes are recorded at the constant so the next person does not have to find them again.

  The handshake itself is not idle in the meantime: kernel and userspace carry the same constant, so
  a STALE artifact in the image is refused at startup rather than left to misbehave - which is
  exactly what it caught while the number was briefly moved, and how the cache defect below was
  found.

- [x] **`DeviceInfo`'s implicit padding is now an explicit `_pad0: u32`.** `repr(C)` inserts four
  bytes to align `bar_len`; Rust does not promise that padding in an otherwise initialised value is
  initialised; and the kernel's `write_user` copies `size_of::<T>()` raw bytes to userspace. Four
  bytes of kernel stack were being handed over on every `SYS_DEVICE_INFO`. Naming the field and
  assigning it zero makes them a value. **The binary layout does not change** - the padding occupied
  exactly those four bytes - so this is not itself an ABI break. Every other struct in the file that
  needed one already had it.

## What the version experiment exposed: the shared-image cache misses its dependencies

Moving `ABI_VERSION` and moving it back was, by accident, a very good test of the build's caching -
because the constant is compiled into every userspace artifact and the handshake refuses a stale one
at startup. Two holes came out of it, one layer apart, and they are the same hole:

- [x] **A `tools` binary was never rebuilt when anything below it changed.**
  `executable_source_digest` has two branches. The general one begins
  `printf 'dependency-closure=%s\n' ...`; the `tools` one hashed only the tool's own manifest, lock,
  `lib.rs`, its own `.rs`, the linker scripts and the product config. `rt` and `abi` are below every
  tool and appeared in neither. Fixed by giving that branch the same closure line - after which the
  tools rebuilt and no artifact was older than the change.

- [ ] **A shared LIBRARY has the same hole, and fixing the tools only moved the symptom.**
  `provider_source_sha` is `source_digest "$crate_dir"` - the library crate's own directory. `abi`
  lives in a different directory, so changing it leaves `lsrt.lslib` a cache hit. The tools then
  relinked correctly against a runtime that was still compiled at the old revision, and the guest
  said so: `abi: refusing a caller built against revision 3; this kernel is 1`.

  The current tree is green because the image was force-rebuilt (`LIBER_IMAGE_REBUILD=1`), which is
  a workaround and not the fix. The provider key needs the closure the consumer key has - carefully,
  because over-invalidating here costs a full image rebuild on every touch, and that is the reason
  these keys are narrow in the first place.

  What makes this worth a task rather than a footnote: a stale shared library is not a stale
  timestamp. Every executable in the image links against it, so ONE missed invalidation silently
  reverts a change for the whole userspace - and the only thing that noticed was a constant whose
  entire job is to notice.

- [x] **The refusal now says both numbers.** `sys_abi_check` printed nothing and `rt` printed "built
  against a different kernel ABI revision" - which binary, and which two revisions, were left to the
  reader. It cost hours here. It now logs
  `abi: refusing a caller built against revision N; this kernel is M`, and that single line is what
  turned "something is stale" into "an artifact from the window when the constant was 3".

- [x] **A correction, because the wrong conclusion was nearly recorded as a finding.** The seventy-two
  `could not compile` messages under `.build/image/<target>/logs/` are DELIBERATE: `build-shared`
  runs cargo until the final link fails on two known duplicate symbols, keeps the ET_REL seed object
  cargo emitted, and links the image itself. It requires `graph_status == 101` AND both messages,
  precisely so a different compile error cannot pass as the expected boundary. `build.sh` exiting 0
  over those logs is correct.

  It read as seventy-two silent failures. Removing the "colliding" aliases from `rt` to fix it broke
  the build a new way - `Cargo image graph did not stop after emitting its ET_REL seed object` -
  which is what said the collision was the mechanism rather than the bug. The log looked like the
  answer; the code that reads the log was the answer.

## The version discipline, which the bump alone does not fix

- [ ] **When versioning starts, nothing will mechanically connect a change to the version.** Not a
  defect today - see above - and the machinery is worth having ready for the day it becomes one: a
  check that fails a change touching an existing syscall handler, an existing `rt` wrapper, or any
  `repr(C)` struct in `abi` unless the version moved or the change declares itself ABI-compatible.
  The two changes that would have tripped it are already recorded at the constant.

- [ ] **The layout and the numbers have no test.** `repr(C)` fixes the layout for one compiler run;
  it does not stop somebody inserting a syscall number in the middle, widening a field, or reordering
  a struct - and with kernel and userspace built from the same crate, all of that is green. What is
  missing is a set of assertions that fail when a value changes rather than when two halves disagree:
  `size_of` and `align_of` and field offsets for every `repr(C)` struct, a snapshot of every `SYS_*`
  number, uniqueness of the syscall ids and of the rights bits, a snapshot of the error codes, and
  `RIGHTS_ALL == OR(every right)`.

- [ ] **The crate has two tests.** For the file the whole system's compatibility rests on, that is
  the reason the drifts above went unseen. Beyond the invariants: strict package corruption cases,
  truncated log fields, invalid UTF-8, duplicate keys, and CBOR output actually run through a decoder
  rather than compared to what this encoder produced.

## The log record, which claims more than it checks

- [ ] **`LogRecord::parse` does not parse the record.** It validates the fixed prefix and then takes
  the entire remaining slice as `fields`; the iterator stops early on a truncated field and reports
  nothing. A record declaring `field_count = 1` with an empty field region parses successfully. After
  `Some(LogRecord)` a caller is entitled to assume the wire grammar holds, and it does not.

  One pass that walks exactly `field_count` key/value pairs and ends exactly at the end of the
  record. If a lazy form is wanted for speed it should be a separate, differently named function for
  already-validated bytes.

- [ ] **`render_cbor` can return `Some` over invalid CBOR.** It writes a map head announcing
  `rec.field_count()` pairs and then iterates `rec.fields()`, which may stop early for the reason
  above - and returns the length anyway. A CBOR map of length N must be followed by 2N data items.
  Strict parsing removes the cause; the renderer should also refuse if it emitted fewer pairs than it
  announced.

- [ ] **The wire format takes arbitrary bytes and the renderers emit them as text.** `encode` accepts
  `&[u8]` for source, keys and values with no UTF-8 validation. `json_str` copies anything above the
  ASCII control range straight through, so `0xff` lands inside a JSON string; `cbor_tstr` uses major
  type 3, which is defined as UTF-8 text. So `source = b"\xff"` is valid input and produces invalid
  JSON and invalid CBOR.

  Two coherent answers, and the LSIDL schema has already chosen: these are strings, so validate UTF-8
  at `encode` and at `parse`. (The other would be to keep them bytes and have JSON base64 them and
  CBOR use major type 2.)

- [ ] **Fields are a list on the wire and a map in JSON.** LSIDL says `list<field>` and `abi::log`
  permits repeated keys, but the JSON renderer emits an object - so two `error` fields become
  whatever the consumer does with a duplicate key. Either render an array of `{key, value}` objects,
  or make uniqueness an invariant the encoder enforces.

- [ ] **The text renderer lets a log entry forge log entries.** `render_text` copies source, key and
  value through unescaped, so a value containing a newline and a plausible prefix appears as a second
  record, and an ESC sequence reaches the terminal. The JSON renderer escapes controls; the human one
  does not, and the human one is the one being read.

- [ ] **"Canonical" is claimed and not enforced.** `parse` accepts arbitrary trailing bytes after the
  declared fields, so a record, that record plus `00`, and that record plus four junk bytes are all
  the same logical record. A format that uses the word canonical should require the buffer to be
  consumed exactly.

- [ ] **The encoder is not transactional.** `Buf::bytes` writes byte by byte and returns `None` when
  it runs out, leaving the output partly overwritten. Not a safety problem, and "None on overflow"
  invites a caller to assume nothing was written. Either say so, or compute the length first. A
  range copy would also be faster than per-byte bounds checks.

## Two definitions of the same thing

- [ ] **`abi::log` and the LSIDL Log protocol are independent implementations of one wire format.**
  `abi::log` calls itself the canonical structured-log type shared across the system; `log.lsidl`
  defines source, key and value as `string` and states that its encoding reproduces `abi::log`
  byte for byte; and the generated codec has its own `Entry`, its own `Severity` and its own
  encode/decode. LogService and the log client both use the GENERATED type, not `LogRecord`.

  So the two already disagree about what input is valid - one takes bytes, one takes strings - and
  the only thing keeping the bytes identical is that somebody remembers to. In a crate whose whole
  argument is single-source-of-truth, that is the shape being argued against. Either retire
  `abi::log` and let the protocol live in LSIDL, or have the generated codec call the shared
  implementation instead of reproducing it.

- [ ] **`ObjectInfo::object_type` is documented as a stable ABI code and its values live in the
  kernel.** The mapping - Domain 0, Process 1, ... WaitSet 13 - is `ObjectType::code()` in
  `src/kernel/object/mod.rs`. Change it there and nothing in `abi` moves, so userspace has no way to
  find out at compile time. The constants belong in `abi`, with `code()` returning them.

## Documentation that no longer describes the call

- [ ] **Several syscall comments are wrong about the current ABI.** `SYS_SYSTEM_POWER`'s comment says
  the argument is `POWER_REBOOT` or `POWER_OFF` and that restricting the call "is a future
  PermissionManager concern"; the handler is `sys_system_power(handle, action)` and the first
  argument is a MANAGE-capable handle to the root Domain. `SYS_CONSOLE_FEED` documents a byte and a
  serial flag and the handler takes a third argument for the console-input privilege; the framebuffer
  call likewise takes a display-controller privilege.

  The irony is that `ABI_VERSION` was correctly bumped 1 -> 2 when those privileges landed. The
  implementation was right and the document beside it was not updated - in the file whose reason for
  existing is to be the definition.

  Worth more than a correction pass: each syscall constant should carry `a0`..`a3`, the rights or
  capability it requires, the success value and the errors it can return, in a form regular enough
  that the numbers and the documentation can be generated from one definition.

## The package parser

- [ ] **`Package::parse` validates the header and calls the archive valid.** The checked arithmetic
  is right and the structural checks stop there: the reserved header field is not examined, an
  entry's blob offset may point into the header or the entry table, blob ranges may overlap, two
  entries may share a name, a name may carry garbage after its first NUL, an empty name is accepted,
  and a bad offset on an entry nobody looks up is not found until somebody does.

  As a trusted build artifact that is survivable. As an on-disk parser it should walk every entry at
  parse time: canonical name, offset at or past the table end, end within the buffer, and no
  duplicates or overlaps.

- [ ] **Lookup is linear and there is no entry ceiling.** Every `lookup` scans from zero and the only
  bound on the entry count is that the table fits in the input. Fine for the init package; if the
  format ever grows, enumerate-plus-lookup becomes quadratic. An iterator yielding `(name, blob)`
  without a second scan is most of the fix.

## Smaller

- [ ] **`RIGHTS_ALL = 0xfff` is a hand-written literal** beside twelve individually defined bits. The
  thirteenth right will not update it. `RIGHT_READ | RIGHT_WRITE | ...` lets the compiler keep them
  in step - and the assertion in the invariants task above would catch it either way.

- [ ] **The toolchain is `channel = "nightly"` with no date.** The same commit is not guaranteed to
  build with the same compiler next month. For fixed-width `repr(C)` types the layout is not at risk
  today; reproducibility is.

## Order

The two items already done were the ones that could not wait: an unbumped version is a promise
already broken, and the padding was kernel memory crossing a boundary. Next is the discipline that
stops the first from recurring - the invariants tests and the change check - because everything else
in this file is a defect that a test would have named. Then the log record, which claims a grammar it
does not enforce and renders bytes as text. Then the two-definitions problem, which is the one that
will get worse on its own.
