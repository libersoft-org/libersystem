## WHAT WAS PROPOSED AND IS CHANGED OR DROPPED

Each idea of the chat's plan was weighed again before this was written. These are the ones that were wrong as stated:

  - "END A GATE AFTER ITS LAST COMMAND, AND TYPE `poweroff` IN EVERY GATE." Dropped as a blanket rule. Several gates
    assert that something does NOT appear - no `FAIL` line, no refusal, no stray access - and a run cut short would pass
    them when the failing line comes late. Kept: ending when the console is closed (the guest is gone, so nothing more
    can arrive), and stopping the guest when the console driver stops recording (B7) - nothing the console log holds can
    change after that; the gates that also read a simulator's log on the host keep their window. An earlier end only per
    gate, through a completion line the gate names, and only with a watch-fail showing that a failure line arriving late
    still fails it.
  - "REMOVE THE BARRIER THAT DRAINS EVERY GUEST BEFORE A HOST STEP." Not without a resource model. Run blindly side by
    side, host gates broke each other's diagnostics on 2026-10-21 and the test guard refused six profile rows. Overlap
    comes only with every step declaring what it reads and writes - an architecture's staging and its profile, the boot
    media, the USB gadget, `.build/state` marks, a host port, the lab's and cold runs' names (private per run, C7), `/tmp`
    traces - and the scheduler overlapping steps whose declarations do not conflict.
  - "EIGHT TO TWELVE GUEST SLOTS ON 100 CORES." Too optimistic. Load already made three timing assertions fail. The
    width starts at four and grows only while the measured flake rate stays at zero, and timing-sensitive gates are
    marked to run alone.
  - "SEPARATE STAGING DIRECTORIES FOR THE TWO PROFILES" as the first step. Deferred, though not for the disk: the staging
    is 53 MB and `.build/boot` 2.5 GB against 28 GB free. It changes every build and boot path, while switching the
    profile only when a step needs the other one (B4), with the steps that need one profile run together (C2), removes
    most switches without touching any of them. Separate directories only if the switches that remain still cost
    measurably.
  - "PUT THE PROFILE BACK ON EVERY PATH THAT SWITCHES IT." Changed. Putting it back after each use pays the switch twice
    for every development step, and makes each of them a writer of the staging that no scheduler can overlap. The
    profile is switched when a step needs the other one, and put back once, at the end of a run (B4); a step that finds
    the wrong one refuses at once (B3).
  - "A LINT AGAINST 'PUMP ONCE, THEN RECEIVE'." Dropped. Most of the ~209 sites are correct - the answer is produced on
    the same core inside the pump - so a lint would force a rewrite of correct tests or be suppressed. Instead: one
    bounded-wait helper, a test fixed when it flakes, and a ledger of flakes with their causes.
  - "SPLIT THE PORTS' SUITES" as a replacement for the whole suite. Changed: a split reorders tests and gives each part a
    fresh boot, so it hides one test's leftovers breaking another (the transport flake was exactly that). The split runs
    at the milestone's end; the whole suite still runs on each port in every L2 and L3.
  - "OPTIMISED TEST BUILDS." A measurement first, not a change: optimisation alters timing and code generation, makes a
    failing test harder to debug, and lengthens the compile the per-change level waits for.
  - "CONTINUE A RELEASE RUN." Only when the tree's identity AND the tools' (QEMU, firmware, toolchain, image key) are the
    same; a release's final dossier still comes from one sealed run.
  - "LEVELS" as a new mechanism. Changed: the levels are presets of `verify.sh`'s existing tiers and its one planner,
    not a second way of choosing tests; and L2 and L3 are one plan, the release's, apart from who declares it a release.
  - "NIGHTLY RUNS." Dropped as a mechanism: nothing in the tree starts a run at night, and the long levels run on the
    owner's request. What depended on "every night" counts L2 runs instead (C5, D2).

## THE ITEMS

### A. Levels with a budget

- [ ] A1. FOUR PRESETS OF `verify.sh`, each an existing tier on a stated tree, with a budget:
  - L0, after each change: the inner tier, `./verify.sh --budget 600`, on the working tree - ten minutes. What the
    budget does not start is handed on, not lost: a key the budget skipped moves into the handoff's deferred set, owed by
    L1, where today the run ends INCOMPLETE and writes no handoff (`verify.sh:1277-1283`, `tier.rs:349`). A failed key
    still fails the run and leaves no handoff.
  - L1, at a milestone's end: the merge tier, `./verify.sh --merge HANDOFF`, at the committed HEAD, widened by the whole
    x86_64 suite (`suite.kernel` on x86_64) and by the ports' whole suites split across guests (D1) - ninety minutes, for
    a plan that does not select everything. A plan that does (WHAT IS MEASURED) has an L1 the size of L2, and L2's
    budget.
  - L2, a full verification: `./verify.sh --release` - every release-required key, over a sealed snapshot of HEAD,
    through the scheduler - started on a clean tree, so that the tree can be edited while it runs (`--release` refuses a
    dirty tree, `verify.sh:356`; `--sweep` is serial, `verify.sh:444`, and is not a level). `--release --in-place` only
    when nobody will edit the tree during the run. Four hours.
  - L3, a release: an L2 run that continued nothing from another run (E1), on the revision the owner names and declares
    the release; its dossier is the release's.
  The working rule that goes with it: during work L0, at a milestone's end L1, L2 and L3 on the owner's request. A change
  to the harness - every item of this milestone is one - is verified during the work by its item's oracle and by the
  gates it changes, run alone; the L2 that VERIFICATION names runs once, after the last item. Oracle for the handoff: the
  tier's tests - a budgeted inner run that skips one key writes a handoff with that key deferred, and `--merge` runs it;
  an inner run with a failed key writes none.
- [ ] A2. EACH PRESET PRINTS ITS ESTIMATE BEFORE IT STARTS and its measured time after, from the history - a price
  measured under an older model is used and marked as such (C6) - so a budget that is not met is seen.
- [ ] A3. THE ARITHMETIC BEFORE THE FIGURES. Before A1's figures are adopted, from the measured prices: for each level,
  the time of the steps that still conflict with one another (the serial remainder), the longest single step, and the
  sum of the steps divided by the width. A figure this cannot meet is changed in THE TARGET and A1. Recorded here.

### B. A guest gate ends when its guest has

- [ ] B1. `guest-console.py` ENDS WHEN THE CONSOLE CLOSES. A closed socket is an end, not an empty read to spin on.
  Oracle: a host test of the driver against a socket that closes, which today spins to its deadline.
- [ ] B2. A GATE'S OWN COMPLETION LINE, gate by gate. A gate whose oracle is positive - it needs named lines - may name
  the line after which nothing it judges can still arrive, and `guest_gate_run` then stops the guest. A gate with
  negative checks keeps a settle window after that line, and the window is stated in the gate. Each converted gate is
  watched failing with a failure line injected late. First the long one that types no `poweroff`: `firmware-tree` on
  both ports; then the gates whose measured times still show the most idle after B1 and B7. (`camera-usb`,
  `virtio-gpu-edid` and `boot-volume-controllers` type `poweroff` already, so B1 alone ends them.)
- [ ] B3. THE STAGING SAYS ITS PROFILE. `build.sh` and `image.sh` stamp the staging of each architecture with the profile
  it was built in; `test.sh`, `guest-gate.sh` and every gate that boots the staging refuse a mismatch at once, naming
  it. The refusal exits with a status of its own and names the profile the step needs, so a runner can act on it (B4).
  Oracle: a test kernel run against a development staging stops in seconds with the reason, instead of failing a boot
  test an hour later.
- [ ] B4. THE PROFILE IS SWITCHED WHEN A STEP NEEDS THE OTHER ONE, not put back after every step that used it:
  - under `verify.sh`, which says so in the environment, `guest-gate.sh` does not put the shipping staging back. The
    runner builds the staging in the profile the next step needs - known from the step's declaration (C1), and until C1
    lands from B3's refusal, after which the step runs again, once - and builds the shipping staging once when the run
    ends;
  - run by hand, `guest-gate.sh` puts the staging back as it does today, and every other path that switches it
    (`dev.sh up`, `lab.sh boot`, `lab.sh scenario-cold`, `check-tickless-idle.py`, `check-hibernate.sh`,
    `check-bluetooth-independent.py`, the bootable volume) leaves it as it is: the next step that needs the other profile
    refuses at once with B3's reason and the command that fixes it.
  Oracle: a run of two x86_64 development-image gates followed by the x86_64 suite changes the profile stamp twice (into
  the development profile, back to shipping at the end), where today the staging is rebuilt four times; and the x86_64
  suite run by hand straight after `lab.sh scenario-cold` refuses at once, naming the profile, instead of failing on an
  undeclared entry.
- [ ] B5. ONE DEVELOPMENT ISO FOR ALL GATES, content-addressed: a gate asks `mkimage` for the image its key names and
  reuses it while the key matches; a private copy only for a gate that writes to its medium. With B4, consecutive
  development gates find the staging unchanged, so the key matches and the image is built once. Oracle: two gates in a
  row build one image; a source change between them builds a second.
- [ ] B6. THE GATES THAT CANNOT PASS ARE MADE ABLE TO:
  - `concurrent-selection` takes its ids from what the x86_64 test kernel compiles, not from the source;
  - `signed-boot`'s re-signing passes the medium's own DMA mode to the signer, so each case is refused for its own
    reason and not for the mode;
  - `verify-evidence` clears `LIBER_RELEASE_REQUIRED` for its nested runs, as it clears `LIBER_VERIFY_RUN`;
  - `perf-anchor` declares the enforcing-required volume it boots as a prerequisite;
  - `tickless-idle` counts the wakes of the line the console's holder has after a handoff. The kernel prints the
    identity it armed only at boot (`main.rs:1459`); at a handoff it prints the wired source it gives away
    (`console_uart/mod.rs:601`, COM1's at `x86_64/serial.rs:577`). The item first establishes which identity the wake
    counters use for the driver's claim; if no line names it, the handoff line gains it;
  - `verify.sh --release --plan` plans without building a snapshot first, and the unbound variable is gone.
  Each is watched failing for its old reason before it passes.
- [ ] B7. THE GUEST STOPS WHEN ITS CONSOLE DRIVER DOES. `guest_gate_run` stops the guest when the driver exits, instead
  of letting `run.sh` run on to `GUEST_GATE_TIMEOUT` with nothing recording the console. The four gates that touch QEMU's
  own output (`camera-usb`, `firmware-tree`, `usb-legacy`, `virtio-gpu-edid`) only copy it for diagnosis. The gates
  whose verdict also reads a simulator's log on the host, which keeps growing until QEMU stops - `power-ups`
  (`ups-sim.log`) and `brightness-usb` (`monitor-sim.log`) - keep their window until they name a completion line (B2);
  `camera-usb` types `poweroff` already. Oracle: a host test of `guest_gate_run` with a stand-in `run.sh` that never
  exits - today it waits for `GUEST_GATE_TIMEOUT`, after the change it ends within seconds of the driver; and
  `usb-release` and `bluetooth-le` give the same verdict before and after on one tree.

### C. Overlap that is safe

- [ ] C1. STEPS DECLARE THEIR RESOURCES in the verify model's catalog: the staging of an architecture - read or written,
  and in which profile -, the boot media, the USB gadget, a host port, the lab's and cold runs' names (private per run
  once C7 lands), `.build/state` marks and `/tmp` traces. `verify-model check` refuses a gate with no declaration, and a
  declaration that disagrees with what the gate's script calls: a host test follows each gate's command in `check.sh` to
  the scripts it runs and requires a guest wherever they call `guest_gate_run`, `run.sh`, `qemu-run.sh`, `lab.sh`,
  `lab.py` or `dev.sh`, and a staging write wherever they call `build.sh` or `image.sh` - in both directions. Its first
  watch-fail is the five gates that boot a guest and are catalogued as host gates today: `icd-selection`, `lifecycle`,
  `foreign-loader-guest`, `foreign-facilities-guest` and `ipv6-peer` (`catalog.rs:323-535`, absent from
  `GATES_THAT_BOOT_A_GUEST`, `catalog.rs:971`). Oracle: the catalog's host test refuses a gate added without a
  declaration, and one declared as a host gate whose script calls `guest_gate_run`.
- [ ] C2. THE SCHEDULER OVERLAPS ONLY WHAT DOES NOT CONFLICT, drains nothing else, and runs the steps that need one
  staging profile together, so the staging is switched once per group (B4). Oracle: `verify-scheduler`'s fixtures - two
  writers of one staging never overlap, a reader waits for a writer, two readers overlap, and the steps that need the
  development profile run as one group between two switches.
- [ ] C3. A GATE'S TEMPORARY FILES AND MARKS ARE ITS OWN, where a conflict has been reproduced:
  - `check.sh` prints and removes only the injection trace of the gate it ran;
  - `check-run-verdict.sh` judges only the step marks of the builds it started, and `build.sh` removes marks whose pid
    is gone;
  - the x86_64 guest's monitor and QMP sockets and its host port are private to the run;
  - `staged-consistency`'s failure beside the host lane is reproduced first, by running it beside each gate of that lane;
    the writer found is declared (C1) or made private, and a failure that does not reproduce goes into F2's ledger.
  Oracle: each conflict reproduced before its fix and gone after - `run-verdict` beside a concurrent `build.sh`, whose
  live mark fails it today; two failing injection gates side by side, each printing only its own trace; two x86_64
  guests at once, where today the second cannot forward host port 5555.
- [ ] C4. `test.sh`'s GUARD KNOWS EVERY PRIVATE FILE `qemu-run.sh` CREATES. Oracle: the guard's fixture in
  `check-guest-verdict.py` admits each private scratch name with its owner's pid and still refuses another run's file.
- [ ] C5. THE WIDTH GROWS BY MEASUREMENT. Four slots first; timing-sensitive gates marked to run alone; the width raised
  only after five L2 runs with no flake attributed to load in F2's ledger.
- [ ] C6. PRICES SURVIVE A MODEL CHANGE, AND THE ORDER SERVES THE WALL CLOCK:
  - a release records its history into the tree's `.build/state`, not into the snapshot it deletes;
  - a step's price is its last measured duration under its step id and command, whatever model hash it was measured
    under - the model hash binds evidence, not cost; A2 marks a price measured under an older model;
  - a step never measured: a guest step keeps today's seed; a host step stays unpriced for a budget, as the cost model
    decides on purpose (`history.rs:500-513`), and is ordered by its kind, host suites first;
  - the guest slots start the longest priced steps first, so a long step is never the last to start; the cheap host
    work runs first on its own lane beside them, so its failures still come in the first minutes.
  Oracle: verify-model's tests - a price survives a catalog edit; a budget never admits a host step that was never
  measured; with two slots and guest steps of 100, 10, 10 and 10 s, the 100-s step starts first.
- [ ] C7. THE LAB'S AND THE COLD RUNS' NAMES ARE PRIVATE TO A RUN. The persistent instance's serial socket, control
  socket and logs (`lab.py:237-240`), and a cold run's channel, serial broker, monitor, QMP, log and scenario record
  (`lab.py:3156-3268`), move under the run's private state directory, so two lab gates or cold scenarios of one target
  can run at once. Oracle: two cold scenarios of one target started together each drive and read their own guest; today
  they share one set of sockets and logs.
- [ ] C8. `hibernate-ports` IS ONE GATE PER PORT. It runs aarch64 and then riscv64 in one step
  (`check-hibernate-ports.py:56`, `:395`) - 6,842 s, the longest step of the run. Each port's half becomes its own gate,
  key and price, as `boot-volume-controllers-aarch64` and `-riscv64` are, and `release-required.toml` carries the two
  keys in place of the one. Oracle: `verify-model check` with the two keys, and each half run alone.

### D. The kernel suites

- [ ] D1. A SUITE SPLIT ACROSS GUESTS. Per architecture, the compiled test ids (from the test binary, as the planner
  reads them) are dealt into parts by their measured durations, the six heaviest each in a part of its own, and each
  part runs as an exact selection in its own guest. The parts discharge the kernel-test keys of the tests they ran, never
  `suite.kernel`, which only a whole run discharges (D2), so the release list does not change. `TEST_SELECTION` is
  compile-time and the compile takes the architecture's build lock (`test-kernel.sh:340-362`), so each part is one more
  compile, done one after another; their time is part of D1's measured cost, and the number of parts is chosen with it.
  Oracle: a split of the aarch64 suite runs every id exactly once and its verdict equals the whole suite's on the same
  tree.
- [ ] D2. THE WHOLE SUITE STILL RUNS, on every target in every L2 and L3, because a split hides one test's leftovers
  breaking another; it alone discharges `suite.kernel`.
- [ ] D3. A FAILURE DOES NOT HIDE THE REST. After a test fails, the runner boots again with the tests after it, as a
  selection, and reports every failure of the suite; the verdict stays failed. Each restart is one more compile, as in
  D1. Oracle: a suite with one planted failure reports it and runs every later test.
- [ ] D4. A MEASUREMENT OF OPTIMISED TEST BUILDS: the aarch64 suite and its compile time at `opt-level` 1 with debug
  assertions and overflow checks kept, against the debug build, on one tree. Adopted only if every outcome is the same
  and the per-change level does not get slower; otherwise recorded and left.

### E. The release run

- [ ] E1. A RUN CONTINUES WHAT AN IDENTICAL ONE LEFT. When the tree's identity and the tools' digests (QEMU, firmware,
  toolchain, image key) are equal, an L2 reuses the passed envelopes of an earlier L2 and runs only what failed or never
  ran; a release (L3) is an L2 that reused nothing from another run. Oracle: `verify-evidence` gains a continued run
  whose dossier names the run each envelope came from, and refuses one whose QEMU digest moved.
- [ ] E2. THE SMALLER DEFECTS: a release at `--jobs 1` writes its dossier even when the two-guest step was skipped, and
  `--catalog`, `--age`, `--trust` and `--model-hash` with `--release` do not build a snapshot first.

### F. Flakes

- [ ] F1. ONE BOUNDED WAIT for the kernel suites - wait until a condition holds, at most a stated number of rounds -
  alongside `peer_closed` and the gamepad test's helpers, which it replaces.
- [ ] F2. A FLAKE LEDGER in `docs/verification/`: each test or gate that failed and then passed without a change, with
  the date, the target, the load and the cause once known. A test listed twice is fixed before anything else in it.
- [ ] F3. THE KNOWN ONE: `typec-tcpci-riscv64`'s timing steps, each given a bound that holds on an emulated target or
  marked to run alone. (The spool test on riscv64 is not a flake; it is under OPEN.)

## THE ORDER

B1, B7, B3, B6 and C4 first - small, and each removes hours or false failures on its own; then B4 (switching on B3's
refusal), B5, and B2 beginning with `firmware-tree`; then C1, C3, C7 and C8, then C2, C6 and C5; then D1 to D3; E1 and
E2; D4 and F alongside. A3's arithmetic comes before A1's figures are adopted; A1 and A2 are written last, once the costs
they budget are measured.

## VERIFICATION

- Every item's oracle above, watched failing first.
- During the work, each item is verified by its oracle and by the gates it changes, run alone. Its changes are harness
  changes, which select everything, so no level runs over the whole tree until the last item.
- THE MEASUREMENT THIS MILESTONE IS JUDGED BY. The baseline is what the 2026-10-20/21 rehearsal measured: 22.3 hours for
  183 steps and about two more for the other 190, run one after another - no run is repeated to get it. After the last
  item: A3's arithmetic; L0 on three changes - a leaf driver or service, a kernel change, a harness change - and L1 on
  the first, each against its budget; one L2, with its wall time, the sum of its steps, and every step that failed for
  the harness and not the code. Recorded here.

## OPEN, FOR THE OWNER

  - Whether the levels and their budgets (A1, THE TARGET) are the ones to work to. L2 and L3 now run one plan and have
    one figure, four hours, where the first version had three to four hours for a night's run and four to six for a
    release.
  - Whether D4's measurement may be made.
  - The defects found by the 2026-10-20/21 runs that are code, not harness, and belong to their own milestones: the
    loader loading the kernel before it refuses an absent DMA-mode record (`arch-profile-*-no-dt-absent-1`), the IOMMU
    hostile and transition phases on the ports, the ports' idle-sleep clock check, a live holder of a shared line that
    never acknowledges, `qemu-pcie-hotplug`'s removal order, `development-lifecycle`'s protocol fuzz, and the spool test
    on riscv64 (`spool_service_sends_submitted_jobs_exactly_once`), which fails alone on the product's two-second answer
    bound - P02M0186's.

EXCLUDES: new tests or gates for product features; faster emulation itself (QEMU's own options); hardware runs, which are
not part of phase 2; a runner that starts levels on its own (CI, a timer) - the long levels run on the owner's request;
narrowing what a change to the kernel or the harness selects (the registry's list of components that select
everything); product bounds and timeouts, which belong to their own milestones; and any oracle made weaker - an oracle
changes only where it checks the wrong thing (B6), and is watched failing for its old reason first.
