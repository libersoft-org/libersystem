# P02M0206 - Verification that fits a working day: levels, guests that end when they are done, safe overlap, split suites

Status: PLANNED (2026-10-22) - the owner's decision is recorded below; nothing is implemented yet, by his instruction
("zatim neimplementuj").

THE OWNER'S DECISION (2026-10-22). After the release rehearsal of 2026-10-20/21 ran 22 hours and reached half its steps,
the owner said a verification of that length makes work impossible and asked for a plan to test properly and
efficiently. The plan was written in the chat as six groups, A to F; the owner answered: "OK, vsechny tyto navrhy, A, B,
C, D, E, F sepis do navrhu noveho milestone (docs/todo), zatim neimplementuj... a jeste nez to udelas, zamysli se nad
tim, jestli nejaky z tvych navrhu neni fakt spatny napad." The second half of that sentence is answered in "What was
proposed and is changed or dropped", below; the items are written as they stand after it.

WHAT IS MEASURED TODAY (2026-10-20/21, read from the run's evidence and logs):
  - THE RUN. `./verify.sh --release --in-place --jobs 2` ran 183 of its 373 steps in 22 hours and was stopped there. The
    steps' own durations add up to 22.3 hours - the run was serial in practice, on a host of 100 cores and 251 GB that
    stayed at a load of 1 to 3. Gates took 19.8 hours of it (12.9 on x86_64 and the host, 6.9 on the ports), the three
    kernel suites 2.5, the builds 0.1. The 190 steps it never reached - 148 host suites, 35 host gates, 3 image
    producers, the development lifecycle and 3 guest gates - took about two hours more, run afterwards.
  - A GUEST GATE COSTS ITS WHOLE BUDGET. `src/harness/guest-console.py` keeps recording until `--seconds` runs out,
    including after the guest is gone: a closed console reads as an empty chunk, which it does not tell from a timeout,
    so it spins to the deadline. Most `guest_gate_run` scripts never type `poweroff`, so `run.sh` runs until
    `GUEST_GATE_TIMEOUT` kills it. `camera-usb`, `firmware-tree` and `virtio-gpu-edid` on the ports took 1200 or 1201 s
    every time and `boot-volume-controllers` on the ports 3901 s (five boots of 600 s and one of 900 s); the same work
    measured 425 to 600 s when it was timed by hand.
  - THE PROFILE IS SWITCHED BACK AND FORTH. Each x86_64 gate on `guest-gate.sh` builds a private development ISO, which
    never hits `mkimage`'s cache (the key files are looked for beside a fresh temporary output), and rebuilds the shipping
    staging on its way out: 205 to 275 s a gate, for 33 gates. Gates that come up through `dev.sh up`, `lab.sh boot`,
    `lab.sh scenario-cold`, `check-tickless-idle.py`, `check-hibernate.sh` or `bluetooth-independent`'s own image build
    leave the shared staging in the development profile, and later steps read it: `provider-media-order`, the x86_64
    suite and `development-gate` failed on "system volume contains an undeclared entry drivers/acpi_fixture.lsexe" and
    "not the shipping configuration" for no fault of the code.
  - NOTHING OVERLAPS. `verify.sh` drains every running guest before any step that boots none (`verify.sh:1176`), 65
    gates are exclusive, and the default is one guest slot. Where it did overlap, it broke things:
    - `test.sh`'s guard against a stray QEMU (`require_no_stray_qemu`) allows a run's private files by name, and the
      private scratch images `qemu-run.sh` attaches (`uas-scratch.<pid>.img`, `nvme-scratch.<pid>.img`, the SCSI, SD,
      AHCI and NVDIMM scratch files) are not on its list - six profile rows failed in one second on "a qemu-system-ARCH
      already holds this tree's disk images" for a collision that was not one;
    - three host gates run beside each other on 2026-10-21 failed for each other: `check.sh` prints the shared
      `/tmp/liber-injection-trace.*.log` on any failure, `staged-consistency` mutated staging another gate was reading,
      and `run-verdict` read another build's `.build/state/build-step.<pid>` mark. Alone, each passed.
  - THE PORTS' SUITES ARE SLOW BECAUSE OF A FEW TESTS. aarch64 took 4270 s and riscv64 about 4300 to 4400 s; a boot costs
    only 25 to 40 s. Six tests are half of aarch64's time - `audioconv` 608 s, `imgconv` 402 s, the dynamic loader 388
    s, the permission manager 242 s, `init_package` 231 s, the shell's command word 216 s - and none of them is tagged
    `Slow`. Each guest's work runs on one host core under TCG, and the test kernel and the userspace are debug builds.
  - A SUITE STOPS AT ITS FIRST FAILURE, and a flaky test hides every test after it: the riscv64 suite stopped twice, at
    a gamepad check that passes alone five times of five and at a spool test, and 28 then 11 tests had to be run again by
    selection.
  - A RELEASE RUN CANNOT BE CONTINUED. A new run id each time, envelopes from another run refused, the run directory
    sealed at the end: a run that fails in its fifteenth hour starts again. A sealed release records its step history
    into the snapshot's `.build`, which is deleted, so the next one starts unpriced, and every step without a price sorts
    last - the 148 cheap host suites ran at the end.
  - SOME GATES CANNOT PASS AT ALL, whatever the code does: `concurrent-selection` selects a port-only test on x86_64
    (since 2026-09-29), `signed-boot`'s re-signing cases call the signer without the `--dma-mode` it has required since
    2026-09-10, `verify-evidence` inherits `LIBER_RELEASE_REQUIRED` inside a release, `perf-anchor` has no declared
    prerequisite for the enforcing-required volume it boots, `tickless-idle` on riscv64 counts the console interrupt the
    kernel announced before the UART was handed to its driver, and `verify.sh --release --plan` stops on "changed:
    unbound variable".
  - FLAKES BY TIMING. A test that pumps the scheduler once and expects the answer is the most common shape (about 209
    sites); three such tests were fixed on 2026-10-20/21 (the gamepads, the display brightness tests, the kernel
    transport). Under load three more appeared: the transport test's three-tick patience, the Bluetooth fixture's OPP
    model timing out, and `typec-tcpci-riscv64` failing a different timing step each run.

THE TARGET. A milestone's end verified within an hour, a night's full verification within three to four hours, and a
release within four to six - each figure to be measured, not assumed, and each recorded here when an item lands.

## WHAT WAS PROPOSED AND IS CHANGED OR DROPPED

Each idea of the chat's plan was weighed again before this was written. These are the ones that were wrong as stated:

  - "END A GATE AFTER ITS LAST COMMAND, AND TYPE `poweroff` IN EVERY GATE." Dropped as a blanket rule. Several gates
    assert that something does NOT appear - no `FAIL` line, no refusal, no stray access - and a run cut short would pass
    them when the failing line comes late. Kept: ending when the console is closed (the guest is gone, so nothing more
    can arrive). An earlier end only per gate, through a completion line the gate names, and only with a watch-fail
    showing that a failure line arriving late still fails it.
  - "REMOVE THE BARRIER THAT DRAINS EVERY GUEST BEFORE A HOST STEP." Not without a resource model. Run blindly side by
    side, host gates corrupted each other on 2026-10-21. Overlap comes only with every step declaring what it reads and
    writes - an architecture's staging, the boot media, `.build/state` marks, a host port, the lab instance, `/tmp`
    traces - and the scheduler overlapping steps whose declarations do not conflict.
  - "EIGHT TO TWELVE GUEST SLOTS ON 100 CORES." Too optimistic. Load already made three timing assertions fail. The
    width starts at four and grows only while the measured flake rate stays at zero, and timing-sensitive gates are
    marked to run alone.
  - "SEPARATE STAGING DIRECTORIES FOR THE TWO PROFILES" as the first step. Deferred. It changes every build and boot path
    and doubles staging on a disk that is 97 % full. First the cheap and certain half: a profile stamp on the staging, a
    check that refuses a mismatch at once, and the shipping staging restored on every path that switches it. Separate
    directories only if the switching then still costs measurably.
  - "A LINT AGAINST 'PUMP ONCE, THEN RECEIVE'." Dropped. Most of the ~209 sites are correct - the answer is produced on
    the same core inside the pump - so a lint would force a rewrite of correct tests or be suppressed. Instead: one
    bounded-wait helper, a test fixed when it flakes, and a ledger of flakes with their causes.
  - "SPLIT THE PORTS' SUITES" as a replacement for the whole suite. Changed: a split reorders tests and gives each part a
    fresh boot, so it hides one test's leftovers breaking another (the transport flake was exactly that). The split runs
    at the milestone's end; the whole suite still runs once per port each night.
  - "OPTIMISED TEST BUILDS." A measurement first, not a change: optimisation alters timing and code generation, makes a
    failing test harder to debug, and lengthens the compile the per-change level waits for.
  - "CONTINUE A RELEASE RUN." Only when the tree's identity AND the tools' (QEMU, firmware, toolchain, image key) are the
    same; a release's final dossier still comes from one sealed run.
  - "LEVELS" as a new mechanism. Changed: the levels are presets of `verify.sh`'s existing tiers and its one planner,
    not a second way of choosing tests.

## THE ITEMS

### A. Levels with a budget

- [ ] A1. FOUR PRESETS OF `verify.sh`, each with a stated budget and what it may defer:
  - L0, after each change: host suites and gates the change selects, and the x86_64 kernel tests it selects - under ten
    minutes (today's inner tier, kept);
  - L1, at a milestone's end: the whole x86_64 suite, the guest gates the change selects on every target it boots, and
    the ports' suites split across guests (D1) - under ninety minutes;
  - L2, nightly or before a large commit: every gate, whole suites on all three targets - three to four hours;
  - L3, a release on the owner's word: L2 over a sealed snapshot, with its dossier.
  The working rule that goes with it: during work L0, at a milestone's end L1, L2 and L3 only on the owner's request.
- [ ] A2. EACH PRESET PRINTS ITS ESTIMATE BEFORE IT STARTS and its measured time after, from the history, so a budget
  that is not met is seen.

### B. A guest gate ends when its guest has

- [ ] B1. `guest-console.py` ENDS WHEN THE CONSOLE CLOSES. A closed socket is an end, not an empty read to spin on.
  Oracle: a host test of the driver against a socket that closes, which today spins to its deadline.
- [ ] B2. A GATE'S OWN COMPLETION LINE, gate by gate. A gate whose oracle is positive - it needs named lines - may name
  the line after which nothing it judges can still arrive, and `guest_gate_run` then stops the guest. A gate with
  negative checks keeps a settle window after that line, and the window is stated in the gate. Each converted gate is
  watched failing with a failure line injected late. First the long ones: `camera-usb`, `firmware-tree`,
  `virtio-gpu-edid` and `boot-volume-controllers` on the ports.
- [ ] B3. THE STAGING SAYS ITS PROFILE. `build.sh` and `image.sh` stamp the staging of each architecture with the profile
  it was built in; `test.sh`, `guest-gate.sh` and every gate that boots the staging refuse a mismatch at once, naming
  it. Oracle: a test kernel run against a development staging stops in seconds with the reason, instead of failing a
  boot test an hour later.
- [ ] B4. EVERY PATH THAT SWITCHES THE PROFILE PUTS IT BACK: `dev.sh up`/`down`, `lab.sh boot`, `lab.sh scenario-cold`,
  `check-tickless-idle.py`, `check-hibernate.sh`, `check-bluetooth-independent.py`, and the bootable volume
  (`--kernel-on-volume`) beside the plain one. Oracle: `provider-media-order` and the x86_64 suite run straight after
  each of those gates, and pass.
- [ ] B5. ONE DEVELOPMENT ISO FOR ALL GATES, content-addressed: a gate asks `mkimage` for the image its key names and
  reuses it while the key matches; a private copy only for a gate that writes to its medium. Oracle: two gates in a row
  build one image; a source change between them builds a second.
- [ ] B6. THE GATES THAT CANNOT PASS ARE MADE ABLE TO:
  - `concurrent-selection` takes its ids from what the x86_64 test kernel compiles, not from the source;
  - `signed-boot`'s re-signing passes the medium's own DMA mode to the signer, so each case is refused for its own
    reason and not for the mode;
  - `verify-evidence` clears `LIBER_RELEASE_REQUIRED` for its nested runs, as it clears `LIBER_VERIFY_RUN`;
  - `perf-anchor` declares the enforcing-required volume it boots as a prerequisite;
  - `tickless-idle` counts the wakes of the line the console's holder has after a handoff;
  - `verify.sh --release --plan` plans without building a snapshot first, and the unbound variable is gone.
  Each is watched failing for its old reason before it passes.

### C. Overlap that is safe

- [ ] C1. STEPS DECLARE THEIR RESOURCES - the staging of an architecture (read or written), the boot media, the lab
  instance, a host port, `.build/state` marks, `/tmp` traces - in the verify model's catalog, and `verify-model check`
  refuses a gate with none. Oracle: the catalog's host test refuses a gate added without a declaration.
- [ ] C2. THE SCHEDULER OVERLAPS ONLY WHAT DOES NOT CONFLICT, and drains nothing else. Oracle: `verify-scheduler`'s
  fixtures - two writers of one staging never overlap, a reader waits for a writer, two readers overlap.
- [ ] C3. A GATE'S TEMPORARY FILES AND MARKS ARE ITS OWN: the injection trace under the gate's work directory, the build
  step mark named by its build, the x86_64 guest's monitor and QMP sockets and host port private to the run. Oracle:
  the three host gates that broke each other on 2026-10-21 (`staged-consistency`, `virtio-iommu-protocol`,
  `run-verdict`) pass run side by side.
- [ ] C4. `test.sh`'s GUARD KNOWS EVERY PRIVATE FILE `qemu-run.sh` CREATES. Oracle: the guard's fixture in
  `check-guest-verdict.py` admits each private scratch name with its owner's pid and still refuses another run's file.
- [ ] C5. THE WIDTH GROWS BY MEASUREMENT. Four slots first; timing-sensitive gates marked to run alone; the width raised
  only after a week of nightly runs with no flake attributed to load.
- [ ] C6. PRICES ARE KEPT AND CHEAP WORK GOES FIRST. A release records its history into the tree's `.build/state`, and a
  step with no price is seeded by its kind - a host suite cheap, a guest step dear - so the cheap failures come in the
  first minutes, not the last.

### D. The kernel suites

- [ ] D1. A SUITE SPLIT ACROSS GUESTS. Per architecture, the compiled test ids (from the test binary, as the planner
  reads them) are dealt into parts by their measured durations, the six heaviest each in a part of its own, and each
  part runs as an exact selection in its own guest. The parts discharge the suite's key only together. Oracle: a split
  of the aarch64 suite runs every id exactly once and its verdict equals the whole suite's on the same tree.
- [ ] D2. THE WHOLE SUITE STILL RUNS, once a night on each port and in every release, because a split hides one test's
  leftovers breaking another.
- [ ] D3. A FAILURE DOES NOT HIDE THE REST. After a test fails, the runner boots again with the tests after it, as a
  selection, and reports every failure of the suite; the verdict stays failed. Oracle: a suite with one planted failure
  reports it and runs every later test.
- [ ] D4. A MEASUREMENT OF OPTIMISED TEST BUILDS: the aarch64 suite and its compile time at `opt-level` 1 with debug
  assertions and overflow checks kept, against the debug build, on one tree. Adopted only if every outcome is the same
  and the per-change level does not get slower; otherwise recorded and left.

### E. The release run

- [ ] E1. A RUN CONTINUES WHAT AN IDENTICAL ONE LEFT. When the tree's identity and the tools' digests (QEMU, firmware,
  toolchain, image key) are equal, a rehearsal reuses the passed envelopes and runs only what failed or never ran; a
  sealed release does the same only within its own snapshot. Oracle: `verify-evidence` gains a continued run whose
  dossier names the run each envelope came from, and refuses one whose QEMU digest moved.
- [ ] E2. THE SMALLER DEFECTS: a release at `--jobs 1` writes its dossier even when the two-guest step was skipped, and
  `--catalog`, `--age`, `--trust` and `--model-hash` with `--release` do not build a snapshot first.

### F. Flakes

- [ ] F1. ONE BOUNDED WAIT for the kernel suites - wait until a condition holds, at most a stated number of rounds -
  alongside `peer_closed` and the gamepad test's helpers, which it replaces.
- [ ] F2. A FLAKE LEDGER in `docs/verification/`: each test or gate that failed and then passed without a change, with
  the date, the target, the load and the cause once known. A test listed twice is fixed before anything else in it.
- [ ] F3. THE KNOWN ONES: the spool test on riscv64 (a printer's answer past its 200-tick bound) and `typec-tcpci-riscv64`'s
  timing steps, each given a bound that holds on an emulated target or marked to run alone.

## THE ORDER

B1, B3, B4, B6 and C4 first - small, and each removes hours or false failures on its own; then B2 and B5; then C1 to C3,
C5 and C6; then D1 to D3; E1 and E2; D4 and F alongside. A's presets are written last, once the costs they budget are
measured.
