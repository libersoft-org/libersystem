# P02M0094 - Audio player (streaming decoders over AudioService)

Status: COMPLETE (2026-08-23). APPLICATION PLATFORM. NOT A PHASE-2 COMPLETION GATE.

The second real application-platform consumer, runnable from the console:
`play vol://media/music.flac` incrementally reads and decodes an audio file,
pushes bounded signed-i16 chunks through the P02M0091 `audio-stream` capability,
and never needs device access or enough memory to hold the whole track. The
decoder graph follows the same rule as image support: one library per codec or
container, shared `pcm` vocabulary, real dependencies between leaves, and no
growing "libaudio" monolith.

- [x] Uncompressed and ADPCM containers: `wav` parses RIFF/WAVE and delegates
  PCM 8/16/24/32-bit mono/stereo conversion to `pcm`; a separate `adpcm`
  leaf decodes both IMA ADPCM and Microsoft ADPCM blocks used by WAV. `aiff`
  parses AIFF and AIFC PCM, including big-endian samples and bounded extended
  sample-rate metadata. Container and codec boundaries remain explicit rather
  than accumulating unrelated decoders in `wav`.
- [x] Lossless compressed leaves: `flac` implements native FLAC metadata and
  frame/subframe decode, fixed/LPC prediction, Rice residuals and CRC;
  `wavpack` implements bounded WavPack lossless stream and block decoding.
  Both are no_std parsers over a bounded reader and emit `pcm` source frames;
  neither allocates the whole file or input-controlled unbounded tables.
  - Result (2026-07-15): the prefix-free `wavpack` leaf validates versioned
    `wvpk` headers, checked word-sized metadata (including large/odd items),
    exact APEv2 trailers and contiguous multi-block sample indexes. Its integer
    entropy reader, adaptive decorrelation terms/weights/history, joint-stereo
    reconstruction and per-block CRC stream mono, true-stereo and false-stereo
    PCM in bounded chunks; hybrid, float, extended-integer and multichannel
    profiles fail typed as unsupported. Seven host tests pin mono/stereo
    bit-exact output, a 10-second two-block sample-count + hash golden,
    second-block corruption, truncation and 256 deterministic mutations. The
    governed `play` path sniffs `wvpk`, transfers non-silent PCM through its
    scoped AudioService stream and closes it for both mono and true-stereo
    fixtures. The complete app-library suite and focused x86
    audio/process/service/storage selection (54/54) are green; aarch64 and
    riscv64 build the full userspace/package graph, and the final x86
    `wavpack.lslib` is 18,400 bytes with only `pcm.lslib` + `lsrt.lslib` edges.
- [x] Common lossy leaves: `mp3` implements MPEG-1/2 Layer III, including
  bounded ID3 skip/metadata handling; `ogg` handles only Ogg page/packet
  framing and `vorbis` depends on it for Vorbis codebook, floor, residue and
  MDCT decode. Each unsupported profile or version fails with a typed error,
  never a partial misdecode. Opus, AAC and other codecs are outside P02M0094.
  - Result (2026-07-15): the prefix-free `vorbis` leaf is a narrowly audited
    no_std packet-decoder fork of Lewton's MIT/Apache-licensed core, with Ogg,
    async, C API and examples excluded. LiberSystem's bounded `ogg` leaf owns
    page/packet CRC, sequence, continuation and granule framing; `vorbis` owns
    identification/comment/setup headers, Huffman/codebook, floor 0/1, residue,
    coupling, IMDCT, overlap and final-granule trimming, and emits the shared
    `pcm` format. Thirty-three host tests include retained core vectors, malformed
    headers/CRC/truncation, compact oversized codebook/comment declarations,
    chunked reads and a full 256-frame FFmpeg PCM golden with at most one i16
    quantization step of float-decoder variance. Governed `play` streams the staged
    Ogg fixture through AudioService and closes it; the complete app-library suite
    and focused x86 selection (54/54) are green, both cross-userspace builds pass,
    and x86 `vorbis.lslib` is 259,280 bytes
    with only `ogg.lslib` + `pcm.lslib` + `lsrt.lslib` runtime edges.
- [x] Hostile-input discipline and conformance: every chunk length, sample rate,
  channel count, frame size, seek offset, codebook/table count and output-frame
  multiplication is checked before allocation or indexing; host suites use
  public conformance/golden vectors plus truncated, corrupt, oversized and
  randomized fixtures. Decoder output is compared by sample count + hash (and
  exact samples where the format guarantees bit-exact decode); a malformed file

- [x] The governed `play` tool: `play <vol://...>` receives exactly

- [x] Integration and performance: stand-in StorageService + AudioService kernel

- [x] Add one bounded streaming encoder contract beside the shared `pcm` vocabulary,
  without creating a monolithic audio library. A decoder yields canonical signed-i16
  interleaved frames plus rate/channel metadata; optional shared transforms perform
  checked mono/stereo remixing and deterministic sample-rate conversion; each output
  codec remains owned by its existing leaf and writes incrementally through a fallible
  byte sink. Final frame counts, checksums, seek tables and container sizes must be
  correct without retaining an unbounded track in memory. If a format requires fields
  known only at EOF, finalize into bounded block metadata or a private staged output
  and publish atomically; interruption, encode failure and out-of-space must not expose
  a successful partial destination or replace an existing file.
  - Result (2026-08-08): `pcm::encode` is the contract and it is three pieces that stay apart on
    purpose. A `Sink` is somewhere bytes go and is allowed to fail - `write` appends, `patch` goes
    back over what was already written, and the default `patch` REFUSES. That default is the
    interesting half: a container whose size is only known at the end says so by being built over a
    sink that can seek, and an encoder handed a forward-only destination is refused when it is
    BUILT rather than after an hour of decoding has been spent on a file that cannot be completed.
    `VecSink` carries a ceiling so a hostile frame count hits a bound instead of the machine, and
    `ForwardOnly` exists to be refused, which is what the tests use to prove the refusal happens.
  - `Remix` is mono/stereo both ways, averaging in i32 so two full-scale samples do not wrap on the
    way to being halved. `Resample` is linear interpolation in integer arithmetic - deliberately not
    the nearest-neighbour hold `Format::advance` does for playback, because playback is feeding a
    mixer and conversion is writing a file somebody keeps, and deliberately not floating point,
    because a conversion whose result depends on the FPU is one whose test cannot state what it
    expects. It carries its interpolation state across pushes, so a track converted in ten-thousand
    frame chunks is bit-identical to the same track converted in one; the test asserts exactly that
    over five chunk sizes, and it fails when the carry is removed.
  - Nowhere in any of it is there a place to put a whole track. The PCM profiles convert frame by
    frame into the sink; the block codecs hold exactly one block; FLAC holds one block of 4096.
- [x] Complete encoders for every format/profile that `play` currently accepts, with
  no host FFmpeg dependency in the target implementation:

    `fmt`, `fact` and padded `data` chunks;

    rate, frame count and SSND layout;

    deterministic compression-effort search;
  - WavPack: bounded mono/stereo lossless blocks, decorrelation, entropy metadata,
    sample indexes and CRC; hybrid/float/multichannel output remains typed Unsupported;
  - Ogg Vorbis: Vorbis identification/comment/setup and audio packets plus Ogg page
    lacing, granule positions, sequence numbers and CRC, with deterministic stream ID;
  - MP3: MPEG-1/2 Layer III mono/stereo with legal frame headers, bit reservoir,
    psychoacoustic/quantization decisions and Xing/Info plus gapless delay/padding
    metadata. Unsupported MPEG versions or channel modes fail explicitly rather than
    emitting a mislabeled approximation.
  Encoder source and test-vector provenance must satisfy the project license policy;
  externally produced fixtures may be used for interoperability tests but are not
  copied implementations. Each lossless output round-trips sample-exactly through an
  independent decoder; lossy outputs meet documented quality/error thresholds.
  - Result (2026-08-08), FOUR of the six: **WAV** (PCM 8/16/24/32 with canonical `fmt`, padded
    `data` and even-aligned chunks; IMA ADPCM and Microsoft ADPCM with `fact` carrying the true
    frame count), **AIFF/AIFC** (big-endian AIFF, AIFC `NONE` and `sowt`, with `FVER` and the
    eighty-bit extended sample rate built from the integer without a floating-point unit), and
    **FLAC** (STREAMINFO, fixed-order prediction zero through four, constant and verbatim subframes,
    Rice residuals with a partition search, stereo decorrelation across all four layouts, CRC-8
    frame headers and CRC-16 frame footers, and the variable-length frame numbering).
  - What makes the ADPCM tests worth having is that they are EXACT against a lossy codec. The
    encoder runs the decoder's own state update sample by sample, so it knows precisely which
    samples will come back, and the assertion is equality against that prediction rather than "close
    enough". It earned its keep immediately: the Microsoft profile was writing a block one byte too
    long, because the dangling half-nibble was inferred from `samples_per_block`'s parity and the
    two codecs carry a different number of samples in their headers - one against two - so the same
    parity means opposite things. Held as an explicit pending half-byte, it cannot.
  - FLAC's compression is chosen by MEASURING: every candidate subframe and every stereo layout is
    costed in bits and the cheapest is written, so `Effort` bounds how many candidates are tried
    rather than guessing which one wins. The test asserts that more effort never produces a larger
    file, which is only true because of that. Forty thousand frames of silence come out under a
    kilobyte; a resonant signal comes out at about half of its PCM.
  - Eleven deliberate breaks were watched to fail before any of this was believed: FLAC's mid/side
    rounding, a wrong subframe order, a corrupted CRC-8, a longer-than-minimal frame number, a
    bit writer that emits its bytes reversed, and each of the three ways a stereo layout can be
    mis-wired (the side channel into the wrong slot, and either subframe width missing its
    seventeenth bit); the AIFF extended-float exponent; the loss of resampler state between pushes;
    and truncation instead of rounding in eight-bit WAV. All eleven turned a green suite red.
  - Two of those tests exist because the first round of breaks found the coverage rather than the
    code. The frame number never exceeds two bytes in a nine-thousand-frame track, so the four-byte
    encoding was written and never executed - it is tested directly now, at every length boundary.
    And which stereo layout the encoder picks depends on the material, so one signal exercises one
    layout: four shapes are converted now, chosen so that a different layout is the cheapest for
    each.
  - `general LPC` is deliberately absent from FLAC. The container and the frame layout are identical
    either way, so it is a ratio improvement that fits behind this interface later rather than a
    different format. The MD5 in STREAMINFO is left zero, which the format defines as "not computed"
    - claiming a digest nothing was checked against would be worse than admitting there is none.
  - **WavPack**, added the same day and the most intricate of the four. Two decorrelation passes -
    a second-difference predictor and a first-difference one - over WavPack's adaptive-median
    entropy coder, with joint stereo, the per-block CRC and the sample index. Every step is the
    decoder's arithmetic run forwards, because both sides adapt: an encoder that computes a median
    or a weight even slightly differently produces a stream that decodes into noise from that point
    on, and nothing before that point would look wrong.
  - Three parts of it are worth naming because they are where the format hides its teeth. The
    ones-count is packed two samples at a time - the PARITY of each count says whether the next
    sample codes its own or is forced to zero - so the encoder has to know the next sample's bucket
    before it can write this one's, and the next bucket depends on the medians this one is about to
    move; it is resolved by advancing a copy one step. The decoder goes looking for a zero-run
    whenever both first medians have fallen to nothing, which digital silence guarantees, so the
    encoder answers that field with an empty run rather than using runs at all - a wrong guess about
    when the decoder will read it desynchronises everything after. And `parse_terms` REVERSES the
    decorrelation bytes, so the byte order is the pass order backwards.
  - WavPack is also the only encoder here that never patches: its block header carries no size that
    is only known at the end, so it writes to a forward-only sink. There is a test that says so,
    because it is a property a caller can rely on and a refactor could quietly remove it.
  - Six more deliberate breaks, six failures: the decorrelation byte order, the missing zero-run
    field, a parity that ignores the lookahead, the joint-stereo inverse, a shifted CRC and the
    bounded code's long branch. The zero-run one is the reason the silence test exists.
  - **Still open: Ogg Vorbis and MP3.** Vorbis is large but tractable in the same shape. MP3 is a
    different order of work - psychoacoustics, the bit reservoir and quantisation decisions - and is
    the one place in this milestone where "no host FFmpeg dependency" is a substantial project
    rather than a constraint on one.
  - The FIRST PIECE OF VORBIS LANDED 2026-08-13: `ogg::PageWriter`, the counterpart of the
    `PacketReader` this tree already had. It laces packets into pages, spans a packet across pages
    when its segment table fills, carries the serial, the rising sequence number and the
    beginning/continued/end flags, and computes the page CRC through the same `ogg_crc` the reader
    checks with - over the header with the checksum field zeroed, so the two cannot disagree about
    what is covered.
  - It is tested THROUGH THE READER rather than against bytes somebody typed: what makes a page
    writer correct is that the packets come back. Six tests - ordinary packets with their granule
    positions and stream flags, a packet whose length is a multiple of 255 (the case the format's
    zero-length terminator exists for, three lengths of it), a 200,000-byte packet that spans pages,
    empty packets, the per-page serial and sequence, and a packet past the ceiling refused without
    disturbing the writer.
  - Watched failing: removing the zero-length terminator turns two of those tests red - the
    multiple-of-255 one, where the following packet is absorbed into the first, and the empty-packet
    one, where an empty packet disappears and every granule after it shifts.
  - The SECOND PIECE, the same day: the Vorbis bit writer, the codebook builder and all three
    headers, in `vorbis/src/encode.rs`. The headers are written and then READ BACK BY THIS TREE'S
    OWN DECODER - `header::read_header_ident`, `read_header_comment`, `read_header_setup` - and the
    values compared, because a specification can be misread twice in the same direction and a parser
    somebody else wrote from it cannot be.
  - The configuration is the simple end of every fork the format offers, and each choice is a RATIO
    decision rather than a decodability one: one block size (no window switching), floor 1 with a
    single class, residue 2 with one classification, and no channel coupling. Each fits behind the
    same interface later.
  - Three things this cost, all of them found by the decoder rather than by reading:
    `float32_unpack` takes a TEN-bit exponent and a nine-bit mask wrote a one that came back as
    10^-70; a mapping submap is THREE bytes and the first is the reserved one nobody reads, so
    writing two made the modes parse out of the mapping's bytes; and a floor class carries at most
    EIGHT posts, because the dimension field is three bits - fourteen posts in one class wrote a
    thirteen that read back as five, which is legal, so the only symptom was `HeaderBadFormat`
    eleven fields later. The posts are split across two partitions of the same class now.
  - That last one is why there is a test that walks the setup header field by field beside the one
    that parses it: the parsing test says a header is wrong, and the walking test says where.
  - What Vorbis still needs on top of it: the audio packets - a forward MDCT, the floor-1 fit, the
    residue quantisation and the packet assembly. That is the half where the output has to SOUND
    like the input rather than merely parse, and it is the next piece.
  - The audio leaves' host suites were being run by NOTHING. They existed, they were thorough, and
    no gate invoked them - the same suite-in-name-only that `check-host-tests.sh` was written for.
    All five are in that gate now, which is what makes the 41 tests above part of `./check.sh`.
    Running them needed one thing said out loud: `src/user/.cargo/config.toml` names a bare-metal
    target and builds `core` from source, so a host test has to be run from outside that subtree or
    the second `core` collides with the one `std` carries.
  - **Ogg Vorbis**, added 2026-08-14 and complete: a stream this encoder writes plays back through
    `Vorbis::parse` and the same `read_i16_le` the player calls.
    `forward_mdct` is direct from the definition and O(n squared) on purpose - a decoder's inverse
    runs on every packet of every file somebody plays, and an encoder runs once over a file somebody
    is converting, so the transform whose loop IS its own definition is the one that can be read
    against the formula. It round-trips against this tree's inverse, including the overlap-add of
    two consecutive blocks, which is what proves the window halves line up.
    THE FLOOR IS WHERE THE TEETH ARE. Floor 1 does not carry a curve - it carries CORRECTIONS to a
    prediction the decoder computes from posts it has already fixed, under a rule with two branches
    (a zig-zag around the prediction for small corrections, a measurement from whichever side has
    more room for large ones). `code_floor` inverts that branch for branch and uses the decoder's own
    `low_neighbor`, `high_neighbor` and `render_point` rather than a copy: an encoder that predicts
    even slightly differently writes a number that decodes to a different curve, and the residues -
    the spectrum divided by that curve - then decode into noise with nothing before that point
    looking wrong. Those four and the inverse-dB table are `pub(crate)` now, so there is one
    implementation rather than two that agree today.
    `fit_floor` fits the envelope OVER the spectrum rather than through it, because the residue book
    covers -1 .. +0.97 and a bin above its own floor cannot be represented at all. A first pass takes
    the loudest bin in the half-segments either side of each post; that is not enough, because the
    curve between two posts is a straight line in the dB domain and a peak in the middle of the
    widest segment still stands above it - so the fit renders its own answer, raises the posts either
    side of any bin still uncovered, and repeats under a bounded number of passes. The test puts a
    peak at bin 900, in the middle of the 768..1024 segment, which is exactly what a single-pass fit
    gets wrong.
    A spectrum the floor cannot reach is REFUSED. At multiplier 2 the highest coded Y lands one table
    entry short of 1.0, and both alternatives are silent lies: fitting as high as possible clips that
    bin, and scaling changes the output level with no field in the format to record it. `encode`
    therefore scales explicitly, ONE FACTOR FOR THE WHOLE STREAM - a scale that changed between
    packets would be a gain nothing records, which is audible as pumping - and it MEASURES the peak
    in a first pass over the transform rather than bounding it from the samples, because a bound
    from the samples costs about twelve decibels of headroom on every file to cover a case most
    files do not hit. The spectra are not kept between the passes, so the encoder's memory stays a
    function of the block and not of the file.
    The residue is quantized against a 64-entry book after division by the floor, interleaved the
    way format 2 requires (`c0[0], c1[0], c0[1], ...`, which is what makes a stereo partition cover
    the same band in both channels so one classification decides for both), and packed one class
    codeword plus thirty-two values per partition.
    Ogg framing uses the existing `PageWriter`, which gained a public `flush`: Vorbis requires its
    identification header to be ALONE on the first page, and a writer that packs as much as fits
    puts the comment beside it.
    TWO OFF-BY-ONES WORTH RECORDING, both found by the end-to-end test and neither audible as an
    error. The packet count is `frames/n + 2`, not `+1`: the first packet decodes to nothing (no
    predecessor to overlap with) AND the last block of signal needs a packet after it to complete
    its own overlap - one short ends the stream a full block early, which nobody notices until they
    compare lengths. And the mode number is written in `ilog(modes-1)` bits, which for one mode is
    ZERO bits: writing a zero there instead shifts every later field by one and produces a packet
    that decodes into noise with nothing in it wrong.
    Deliberately absent: multiple block sizes (one size, so no window flags and no mode selection),
    channel coupling, and any psychoacoustic model beyond "the floor follows the spectrum". Each is
    a ratio improvement behind the same container rather than a different format.
    STILL OPEN in this item: MP3. Five of the six formats are done.

    **MP3 LANDED 2026-08-23, and all six formats are done.** The blocker recorded here earlier was
    real and it was DATA: Layer III codes its spectrum with the thirty-odd tables ISO 11172-3 prints
    - about fourteen hundred (length, codeword) pairs - and a second table nobody thinks of until
    they need it, the 512-tap analysis window of the polyphase filterbank. Neither can be derived
    from a formula, and neither can be written from memory: one wrong codeword produces a stream
    that decodes into noise from that point with nothing before it looking wrong.

    BOTH WERE RECOVERED MECHANICALLY, and both check themselves.

    - THE CODE TABLES came out of `nanomp3`, the MIT-or-Apache-2.0 decoder this tree already depends
      on, by WALKING ITS LOOKUP: its tables are a packed two-level structure, so following every
      path and reading off the codeword that reaches each leaf gives the standard's own
      `(length, codeword)` form back. What arrived is the standard's data, not anybody's code. It
      verifies itself: a Huffman table is valid exactly when it is prefix-free and its lengths
      satisfy Kraft's equality, and all eighteen - sixteen code tables, two quadruple tables - do,
      exactly, at the dimensions the standard names.
    - THE ANALYSIS WINDOW WAS SOLVED FOR, because the decoder carries the SYNTHESIS window folded
      into its own butterflies and not in a form that can be read off. The path from a signal
      through the analysis to the decoder's output is linear in that window, so feeding the real
      decoder streams built from known coefficients and fitting the 512 values that reproduce what
      it returns determines them. The residual is 6e-6 of the signal and the values run to
      +/-0.03578 - the extreme the published window has.

    THE ENCODER ITSELF is this tree's: the analysis filterbank, the 18-point MDCT, the forward alias
    butterflies, the quantiser and its rate loop, the region split, the table selection, the frame
    and side-info layout, and the Xing/Info gapless metadata. Long blocks, constant bitrate, no bit
    reservoir, two channels coded independently, scalefactors zero and the rate loop moving
    `global_gain` alone - each stated at the top of `encode.rs` with what it costs.

    WHAT IT MEASURES. A 320 kbit/s round trip through this tree's own decoder returns the signal at
    correlation 1.00000 with an error 80 dB down, aligned at sample zero and exactly as long as it
    went in - which is the gapless tag doing its job. 128 kbit/s stereo hits 128 kbit/s exactly,
    which is what constant bitrate means, and encodes at 27x real time.

    THREE THINGS THAT COST AN AFTERNOON, all found by measuring rather than by reading:

    - THE RATE LOOP DROVE ITSELF INTO CLIPPING. It prefers a finer step, and a step fine enough
      pushes a line past what the escape tables can carry - so a high bitrate reconstructed WORSE
      than a low one. The quantiser reports whether it clipped and the loop treats that as not
      fitting.
    - THE GAPLESS TAG CANNOT EXPRESS A SMALL DELAY. A decoder reading it computes the skip as
      `one frame + declared delay + 529`, so the smallest total it can name is 1681 samples; this
      encoder's own delay is 481. Declaring the difference is impossible, so the track is PRIMED
      with 576 samples of silence - which is what every encoder writing this tag does - and the
      delay is declared against that.
    - `push` WAS QUADRATIC. It buffered the whole call and then drained thirty-two samples at a time
      off the FRONT, so a caller handing over a minute of audio moved two hundred billion samples.
      The pending buffer now never holds more than one block: 1.7x real time became 27x, with the
      output bytes identical.

- [x] Add governed `audioconv [options] <input> <output>`. Input is selected by the
  same structural content sniffer as `play`; output is selected by the destination
  suffix or matching `--format`. The first complete matrix accepts every playable
  input and emits WAV/WAV-IMA/WAV-MS, AIFF/AIFC, FLAC, WavPack, Ogg Vorbis and MP3.
  `--force` controls replacement; `--rate`, `--channels` and applicable `--bits`
  select PCM transformation; normalized `--quality 0..100` controls lossy MP3/Vorbis
  fidelity and `--compression 0..100` controls lossless FLAC/WavPack effort without
  changing decoded samples. Inapplicable or contradictory options are rejected from
  one capability/default table shared by parser, help and tests. Version one strips
  tags, pictures and arbitrary metadata deliberately and reports that fact together
  with source/destination format, rate, channels, frames, duration and byte count.
  The tool receives only the volume bundle, never AudioService or device authority,
  and supports cross-volume conversion through StorageService.
  - Result (2026-08-08), the LIBRARY half: `audioconv` is a crate beside the codec leaves, split
    the way `imgconv` is - the library decides and does, the binary holds the capabilities and the
    paths - so "does `--bits 24` mean anything for Ogg Vorbis" is answered by a host test instead of
    by booting. Ten tests, all of them pure over their input.
  - One `PROFILES` table answers every capability question, and the parser, the help text and the
    tests all read it. That is what stops a format growing a capability in the help that the parser
    does not honour, and the tests assert the invariant directly: nothing is both lossless and
    quality-controlled, nothing lossy takes a compression effort, and the table's order matches the
    enum its lookup indexes by. `--quality` on FLAC, `--compression` on WAV, `--bits` on FLAC and
    `--bits 12` on WAV are each refused as `UnsupportedOption` rather than ignored.
  - The input is sniffed structurally, the same way `play` does it, so a FLAC named `.wav` converts
    and a `.flac` that is not one is refused before a destination is opened. The destination comes
    from the suffix or from `--format`; the two ADPCM profiles have no suffix of their own - they
    are WAV files - which is why the table lets a profile have none.
  - The pipeline is decode -> remix -> resample -> encode, in bounded chunks, remixing BEFORE
    resampling so the rate conversion happens on the channel layout that is actually being written.
    The encoded input is held, because every decoder in this tree parses from a slice; the decoded
    audio never is. A hundred-thousand-frame track converts with the same buffers as a hundred.

    which is audible as pumping - and the peak of a spectrum is not a function of the peak of the

  - **OGG VORBIS WAS AT 0.14x REAL TIME**, which is a conversion nobody would wait for: seven
    seconds of work per second of audio, and the encoder runs its transform TWICE per packet because
    it measures its peak in a first pass. `forward_mdct` was the definition written out - `2n` terms
    for each of `n` outputs with a `cosf` call in the inner loop - which is the right shape for a
    first version and can be read against the formula, which is why it was written that way.
    It is now the same transform computed differently: the `2n` inputs are FOLDED onto `n` by the
    cosine's own symmetries into a plain DCT-IV, and that is one complex FFT with a twiddle either
    side. 0.14x became 18.8x - a hundred and thirty-six times - and the output bytes are IDENTICAL,
    which is what says the transform did not change, only its cost. The round-trip against this
    tree's own inverse MDCT, including the overlap-add of two consecutive blocks, is what verifies
    the fold and the FFT rather than a reading of the derivation.
  - THE LOSSY CONVERSION IS A TEST OF ITS OWN, and the reason is a number worth recording: the
    lossless conversion scenario already cost 681 SECONDS on riscv64 under emulation, three quarters
    of the window in which the suite requires a test to finish, and a fifth conversion inside it
    pushed it past - the guest was stopped twice before the cause was clear. Two tests that each
    finish say more than one that is stopped, and the split falls along the line this milestone
    draws anyway: lossless round-trips sample-exactly, lossy is judged by decoding back to the shape
    that was asked for. The 681 seconds is not a defect and is not fixed by the split; it is what
    four encoders over a quarter-second of audio cost when every instruction is emulated, and it is
    written down here so the next conversion added to that test is added knowingly.
  - PEAK HEAP IS MEASURED, not estimated: a counting global allocator behind the bench reports the
    high-water mark each encoder adds while it runs, which is the number that tests the bounded
    memory each of them claims. It found one immediately - **the MP3 encoder was holding the whole
    track**. Its `push` turned samples into subband blocks and only emitted frames when the call
    returned, so a caller handing over a minute of audio held ten megabytes of subband samples per
    channel: 35 MB of peak heap for a 961 kB output. Emitting a frame as soon as there are blocks
    for one took it to 1.8 MB - which is the output buffer itself - and made it 1.8 times faster as
    well.
  - THE HOSTILE CASE EVERY ENCODER SHARES is a destination that runs out part way through, and it is
    tested for all six at once through `audioconv`: each must refuse rather than report a partial
    file as a whole one. That found the second thing - **Ogg Vorbis ignored the caller's ceiling**.
    It is the one profile that builds its bytes at the end rather than streaming into the sink, so
    the bound every other profile met simply did not reach it. It carries the ceiling now and checks
    what it built.
