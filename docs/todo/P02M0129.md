## The ELF invariant that is not checked, and what it actually reaches

- [x] **`p_filesz > p_memsz` is accepted, and the loader then writes past what it allocated.**
  `bootproto::elf` bounds `p_offset .. p_offset + p_filesz` against the FILE and never compares
  `p_filesz` to `p_memsz`. All three backends then size their allocation from `p_memsz` and copy
  `segment_data(..).len()`, which is `p_filesz`: x86 allocates `p_memsz.div_ceil(PAGE_SIZE)` pages
  and copies `data.len()`; aarch64 reserves the segment's physical span, zeroes `p_memsz` and copies
  `data.len()`; riscv64 stages by `p_memsz` and copies `data.len()`. A header declaring
  `p_memsz = 4096, p_filesz = 65536` reserves one page and writes sixty-four kilobytes.

  FIXED 2026-08-11 where the finding says to put it: in the shared parser, at `Elf::parse`, so all
  four readers get it and none of them has to remember. `a_malformed_pt_load_is_refused_by_the_parser_rather_than_by_each_loader`
  asserts the sane segment parses first, then each refusal in turn, and every rule was watched to
  fail.

  **Severity, measured rather than assumed.** The kernel shares this parser and is NOT exposed: its
  `map_segment` derives its page count from `p_memsz` and clamps every per-page copy to
  `min(page_end, load_start + data.len())`, so surplus file bytes are simply never copied. The
  exposure is the loader alone, and its input is the kernel image on the boot medium - so this is
  "a corrupt or tampered boot medium corrupts firmware memory", not a path from a user program.
  That is still the wrong answer to a malformed image, and it is one comparison.

  Put it in the shared parser, where both readers benefit, and validate every `PT_LOAD` at
  `Elf::parse` rather than at each use.

- [x] **A `PT_LOAD` whose file bytes are missing is silently treated as all-BSS.** Every backend
  writes `if let Some(data) = image.segment_data(&ph)` or `let Some(data) = .. else { continue }`.
  A segment that declares file-backed bytes the file does not contain is a malformed executable, and
  the right answer is to refuse the image, not to leave the segment zeroed and boot it.

  FIXED 2026-08-11, in the same pass: a segment declaring file-backed bytes the file does not
  contain refuses the IMAGE, rather than every backend independently deciding to boot it zeroed.

- [x] **`ET_DYN` is accepted and treated as `ET_EXEC`.** The parser admits both; the loader never
  reads `image_type`, computes no load bias, and processes no relocations. A position-independent
  kernel would be loaded at its link addresses and jumped to unrelocated. Until a PIE kernel is
  actually wanted, refuse anything that is not `ET_EXEC`, by name, at load.

  FIXED 2026-08-11 in the LOADER, by name, at load - and not in the shared parser, which was the
  first attempt and broke six tests immediately: the kernel loads position-independent userspace
  binaries through `ET_DYN` and the compatibility checker reads shared libraries with it. Each of
  the three architecture backends now asserts `image_type == ET_EXEC` right after parsing the kernel
  image, with the reason beside it.

- [x] **x86 mishandles a `PT_LOAD` that is not page-aligned.** It allocates
  `p_memsz.div_ceil(PAGE_SIZE)` pages, copies to `phys + 0`, and maps `align_down(p_vaddr)`. A
  segment whose `p_vaddr` has a non-zero page offset belongs at `phys + (p_vaddr & 0xfff)`, and it
  needs `page_offset + p_memsz` bytes of allocation. The kernel's linker script page-aligns its
  segments, so this is unreachable today - which is the argument for REFUSING a non-aligned segment
  rather than for computing the offset. The image format is ours.

  FIXED 2026-08-11 by refusing rather than computing, which is what the finding argues for: the
  image format is ours and the kernel's linker script page-aligns its segments, so a non-aligned
  one is a malformed image rather than a case to support. In the shared parser with the rest.

- [x] **W^X is claimed and not enforced.** `map_kernel_segment` sets `WRITABLE` from the write flag
  and `NX` from the absence of the execute flag, so a `PF_W | PF_X` segment maps read-write-execute
  while the comment says the mapping honours W^X. Refuse the segment; the kernel does not have one.

  FIXED 2026-08-11, and then CORRECTED the same day by a boot that would not start.

  The first version refused a `PF_W | PF_X` segment at parse, on the finding's own claim that "the
  kernel does not have one". It does: the aarch64 and riscv64 kernels link their boot stub - the
  code that runs with the MMU off and then turns it on - as a single `RWE` segment, so the loader
  panicked inside `Elf::parse` on both architectures before it had loaded anything. The claim had
  been measured on x86_64 alone, and the shared parser is shared with two images it had not been
  measured against.

  W^X is a policy about what may be MAPPED, not a property of a well-formed ELF, so it now lives
  where the mapping happens and the image's provenance is known: the kernel's userspace loader
  refuses it for every program it loads, and the x86_64 loader asserts it for the kernel image -
  whose mapper is the one that derives `WRITABLE` and `NX` independently, which is what the finding
  is actually about. The page-alignment rule moved with it for the same reason: the two
  device-tree backends load by `p_paddr` and align down themselves.

  The parse-time test now asserts the OPPOSITE, with the reason on it, so the next person to reach
  for that check finds out why it is not there.

## aarch64, which is not a general UEFI loader yet

- [x] **The handoff assumes EL1, and UEFI is entitled to run at EL2.** The pre-branch sequence reads
  and writes `sctlr_el1` only. The UEFI specification has AArch64 firmware execute at the highest
  non-secure exception level available, which is EL2 on most server-class parts. On such a machine
  the loader clears the MMU and cache bits of a translation regime it is not executing under, leaves
  `SCTLR_EL2` untouched, and branches to the kernel's boot stub - which sets up EL1 translation -
  while the CPU is still at EL2.

  FIXED 2026-08-11. The handoff reads `CurrentEL`, and at EL2 it does the transition properly:
  `HCR_EL2.RW` for an AArch64 EL1, both SCTLRs cleared (EL1's because that is the regime the kernel
  will run under, EL2's because that is the one executing), `tlbi alle2` and `tlbi vmalle1`,
  `SPSR_EL2` = EL1h with interrupts masked, `ELR_EL2` = the entry, a stack, and `ERET`. The EL1 path
  is unchanged and both are in one place, so the entry contract is stated once. The stack handed
  over is the loader's own, read from `sp`.

  QEMU's virt machine starts the loader at EL1, which is why this has never been seen here and why
  no test in this tree can show it. That is written at the code.

  Read `CurrentEL`, and when it is EL2, do the transition properly: `HCR_EL2`, `SPSR_EL2`, `ELR_EL2`,
  a stack, the cache and MMU handoff, and `ERET` to EL1. One explicit "enter the kernel at EL1 with
  the MMU off" stub, so there is one place that states the entry contract.

- [x] **The freshly copied kernel is never cleaned out of the data cache.** The kernel arrives
  through ordinary stores (`copy_nonoverlapping`), and the handoff then does `dsb sy`, clears C and
  I in `SCTLR`, `tlbi`, `ic iallu`, `dsb`, `isb` - with no `dc cvau` / `dc civac` anywhere. `dsb`
  orders; it does not write dirty lines back to the point of unification. So the kernel's text can
  still be resident only in the D-cache when the D-cache is turned off, and the branch lands on
  whatever RAM held before.

  FIXED 2026-08-11. Each `PT_LOAD` is cleaned to the point of unification with `dc cvau` and the
  instruction cache invalidated over it with `ic ivau`, strided by the line sizes read from
  `CTR_EL0` rather than assumed, then `dsb ish` / `isb` - before any cache or MMU state changes.
  `dsb` orders; it does not write dirty lines back, which is the whole of the finding. Same caveat:
  QEMU's TCG models a coherent memory system and will never show it.

  QEMU's TCG models a coherent memory system and will never show this. Real ARM parts will. Clean
  the loaded ranges to PoU, `dsb`, invalidate the instruction cache for them, `dsb`, `isb`, and only
  then change the cache and MMU state.

- [x] **The kernel's fixed physical destination is claimed last, after everything else has
  allocated.** `main` reads the kernel, mounts filesystems, assembles the bootstrap set and retains
  it - all through `AllocateAnyPages` - and `load_kernel` only then asks for `ALLOCATE_ADDRESS` at
  the link address. If any earlier allocation happened to land there, the placement fails and the
  boot panics. Reserve the kernel's physical span first, before the large opportunistic
  allocations.

  FIXED 2026-08-11. `reserve_kernel_span` claims every `PT_LOAD`'s page span at its link address
  immediately after the kernel is read, before the filesystem mounts and the bootstrap assembly that
  allocate through `AllocateAnyPages`. The backend's later `ALLOCATE_ADDRESS` is then expected to
  find the span already taken - by itself - so it no longer panics on that, and the comment says
  which of the two is the authority.

## RISC-V: the overlap check does not check what its name says

- [x] **`check_clear_of_destination` compares six single ADDRESSES against the destination range.**
  It tests the entry address of `place_and_enter`, the current stack pointer, the `Staged`
  descriptor's address, the staged image's base, the `BootInfo` pointer and the DTB pointer. Not one
  of them is a range. The loader's own image, the whole active stack, the module descriptor array,
  the `init.pkg` and `volume.pkg` bytes, the assembled bootstrap archive, a live volume image, and
  the DTB's actual `totalsize` are all unchecked, and the staged image is checked by its first byte
  while it is the largest object in play.
  FIXED 2026-08-11 with a real overlap test and every object's full extent: the loader's code, the
  whole ACTIVE stack (from `sp` to the top of its page, not the one word `sp` names), the staging
  descriptor, the staged image at the length the copy will move, the `BootInfo` at its own size, the
  device tree at its header's `totalsize`, and - the ones the comment is actually about - the
  retained bootstrap archive and the live volume image, which `retain()` allocates through
  `AllocateAnyPages` and which U-Boot may satisfy from inside the kernel's destination.

  A DTB whose magic is not there counts as one page, which is the safe answer for something that
  may not be a device tree at all.

  The larger version - one region proven clear, holding every handoff object - is the better shape
  and is a change to where each of them is allocated rather than to this check.

  The comment beside it says plainly that U-Boot does not reserve its own image in the firmware
  memory map - so the pages `retain()` hands back can be inside the future kernel destination, and
  the post-EBS copy would then overwrite the bootstrap data before the kernel reads it. Introduce a
  real range type and an `overlaps`, and check every object by its full extent. Better still: move
  every handoff object, the handoff stack and the staged image into one region proven clear of the
  destination before `ExitBootServices`.

## Firmware interfaces used more optimistically than they are specified

- [x] **Block I/O ignores `IoAlign`.** The `EFI_BLOCK_IO_MEDIA` binding carries `io_align`,
  `FirmwareDisk` does not keep it, and `read_block` passes `buf.as_mut_ptr()` straight to
  `ReadBlocks`. The specification makes `IoAlign > 1` a requirement on the buffer, and a driver may
  answer an unaligned one with `EFI_INVALID_PARAMETER`. OVMF does not care; NVMe, SCSI and USB
  stacks on real firmware can. Either keep `io_align` and bounce through an aligned buffer, or use
  `EFI_DISK_IO_PROTOCOL`, which exists precisely to absorb block size and alignment constraints.

  FIXED 2026-08-11 with the first of the two options: `FirmwareDisk` keeps `io_align`, and a read
  whose buffer does not satisfy it bounces through an aligned one. `IoAlign` of 0 or 1 means no
  requirement, which is every case in this tree - OVMF does not care, which is why nothing here has
  ever shown it, and NVMe, SCSI and USB stacks on real firmware may answer
  `EFI_INVALID_PARAMETER`.

  `EFI_DISK_IO_PROTOCOL` is the other option and the better one for block SIZE as well as
  alignment; it is a different protocol to bind and belongs with whoever needs unaligned offsets.

- [x] **`read_file` returns uninitialised firmware memory as file content after a short read.** The
  loop breaks on any error or a zero-length read and then returns
  `from_raw_parts(phys, file_size)` regardless of how much arrived. A file whose `FileInfo` says one
  megabyte and whose second read fails yields a one-megabyte slice whose tail is whatever those
  freshly allocated pages held - handed on as a kernel image, a bootstrap package, or a volume. A
  read that did not complete must free its pages, close the file and answer `None`.

  FIXED 2026-08-11: a read that did not complete frees its pages and answers `None`. A file whose
  `FileInfo` said one megabyte and whose second read failed used to become a one-megabyte slice
  whose tail was whatever those pages held - handed on as a kernel image, a bootstrap package or a
  volume.

- [x] **`ExitBootServices` is retried on every error, forever.** The specification defines the
  stale-`MapKey` case as `EFI_INVALID_PARAMETER`, and that is the one worth re-reading the map for.
  Any other status means something else went wrong, and an infinite loop is the least informative
  possible response. Match on the status: success, invalid-parameter retries, anything else panics
  with the value.

  FIXED 2026-08-11 in all three backends: only `EFI_INVALID_PARAMETER` - the specification's stale
  map key - retries, and anything else panics. An infinite loop is the least informative possible
  response to a firmware saying something different is wrong.

- [x] **The sizing `GetMemoryMap` call ignores its status.** All three backends call it with a null
  buffer, ignore the return, and compute `map_size + desc_size * 16`. The expected answer is
  `EFI_BUFFER_TOO_SMALL`; anything else leaves `desc_size` unchecked, and a zero `desc_size` divides
  by zero a few lines later. Require the expected status, `desc_size != 0` and
  `desc_size >= size_of::<MemoryDescriptor>()`.

  FIXED 2026-08-11 in all three backends and in x86's `memory_top`: the expected
  `EFI_BUFFER_TOO_SMALL`, a non-zero `desc_size`, and a `desc_size` at least the size of a
  descriptor - checked before anything divides by it.

- [x] **x86 truncates a memory map larger than 512 regions in silence.** `if n >= MAX_REGIONS
  { break }` hands the kernel a map that looks complete and is missing its tail - the worst
  available failure mode for the one structure that says which RAM exists. Make it fatal, with the
  count in the message, or size the array from the map.

  FIXED 2026-08-11: it is fatal, with a line saying so before the panic. Handing the kernel a map
  that looks complete and is missing its tail is the worst available failure mode for the one
  structure that says which RAM exists - it surfaces as memory corruption long afterwards.

- [x] **`memory_top` can free a different number of pages than it allocated.** It allocates from a
  padded `map_size`, then `GetMemoryMap` overwrites `map_size` with the actual size, and the
  `FreePages` uses the new value. When the real map is smaller, the difference leaks. Keep the
  allocated page count in a variable and free exactly that.

  FIXED 2026-08-11: the page count is kept in a variable and the free uses it. The second
  `GetMemoryMap` overwrites `map_size` with the real size, so the free leaked the difference
  whenever the real map was smaller than the padded estimate - and the error path did not free at
  all, which it now does.

- [x] **x86 maps everything up to the highest descriptor in the firmware map.** `memory_top` takes
  the maximum over all descriptors, and the HHDM and identity maps then span `0 .. ram_top` in 2 MiB
  pages. A firmware that describes a high MMIO aperture or PCI window makes the loader build page
  tables across the whole interval - wasted tables, wasted boot time, a direct map over physical
  holes, and MMIO mapped write-back where only the framebuffer is given `PCD | PWT`. Map from the
  descriptors, with attributes taken from them.

  FIXED 2026-08-11: `memory_top` skips `MEMORY_MAPPED_IO` and `MEMORY_MAPPED_IO_PORT_SPACE`, and its
  end-of-region arithmetic is checked. The HHDM now spans RAM - conventional, boot-services, loader,
  ACPI and persistent - so a firmware describing a high PCI window no longer makes the loader build
  2 MiB tables across the whole interval, or map device memory write-back. Mapping each descriptor
  with its own attributes (rather than one span with the MMIO removed) is the larger version of this
  and is not needed while every remaining type is RAM.

- [x] **GOP is assumed to be 32 bits per pixel, including for `PixelBitMask`.** `bpp` is the literal
  `32` and the pitch is `pixels_per_scan_line * 4`, while `PixelBitMask` describes its format
  through the masks precisely so that it need not be. Compute the element size from the highest set
  bit across the four masks, and validate that the masks are contiguous and disjoint - `mask_size`
  currently assumes contiguity without checking it.

  FIXED 2026-08-11. In a `PixelBitMask` mode the element size is the highest set bit across all four
  masks rounded up to whole bytes, and the pitch follows it - a firmware describing a 24- or 16-bit
  layout used to get a renderer writing four bytes per pixel into a framebuffer with a different
  stride, which is a diagonal smear rather than a picture.

  The masks are checked rather than assumed: each must be exactly the contiguous run its shift and
  size describe - `mask_size` counts the ones above the lowest set bit, so a split mask read as a
  short one - and no two channels may claim a bit. A mode that fails either is refused, which is a
  serial-only boot rather than a wrong picture.

## x86 page tables

- [x] **The table walker treats a 2 MiB leaf as a pointer to a page table.** `next_table` returns
  `entry & ADDR_MASK` for any entry with `PRESENT` set, without testing `HUGE`. The loader builds
  the HHDM and the identity map out of 2 MiB pages first and maps the kernel's segments with
  `map_4kb` afterwards, so a 4 KiB mapping whose address falls under an existing huge leaf takes
  that leaf's FRAME ADDRESS as a table and writes page-table entries into ordinary physical memory.

  FIXED 2026-08-11: `next_table` answers `None` for a present entry with `HUGE` set, so a 4 KiB
  mapping under an existing 2 MiB leaf refuses instead of taking that leaf's frame address as a
  table and writing page-table entries into ordinary physical memory.

  The mapper that distinguishes creating from replacing is the larger half and is not done: it wants
  every caller to say which it means, and the collision this fixes is the one that corrupts memory
  rather than merely surprising somebody.

  Not reachable with the current linker script, because the kernel's virtual addresses do not
  collide - but the loader accepts whatever `p_vaddr` the image declares, so it is reachable from a
  malformed one, and it lands wherever that leaf pointed. A `HUGE` test that answers `None`, and a
  mapper that distinguishes creating a mapping from replacing one, with a collision as an error.

## The x86 handoff

- [x] **The stack is misaligned for the SysV ABI at the kernel's entry.** `stack_top` is
  page-aligned, so `rsp % 16 == 0` after `mov rsp`; the loader then `jmp`s. The kernel's linker
  script says `ENTRY(kmain)` and `kmain` is an ordinary `unsafe extern "C" fn`, which the compiler
  builds expecting the state left by a `call` - `rsp % 16 == 8` at the first instruction, the return
  address accounting for the difference. Every aligned stack access the compiler emits is off by
  eight. It works today because nothing on that path spills to an aligned slot.

  FIXED 2026-08-11 by pushing a return address before the jump, which is exactly the state a `call`
  leaves: `rsp % 16 == 8` at `kmain`'s first instruction, which is what the compiler built it for.
  Every aligned stack access it emits was off by eight and worked only because nothing on that path
  spills to an aligned slot.

  The address pushed is a `ud2` in the handoff itself, so "what if the kernel returns" has an
  answer that is not a wild jump.

  A small assembly `_start` that establishes the kernel's entry contract and then calls `kmain` is
  the better fix than `sub rsp, 8`, because the same stub is where the next item belongs.

- [x] **Interrupts are not disabled across the handoff.** After `ExitBootServices` the firmware's
  interrupt handlers are gone, and the loader does `mov cr3`, `mov rsp`, `jmp` with no `cli`; the
  kernel installs its IDT some way into `kmain`. The window is small and real. (`halt()` has the
  same discrepancy: its comment says interrupts are off and it does not clear them.)

  FIXED 2026-08-11: `cli` before the `cr3` load. After `ExitBootServices` the firmware's handlers
  are gone and the kernel installs its IDT some way into `kmain`, so an interrupt in that window
  vectors through a table nobody owns. `halt()` clears them too - its comment said interrupts were
  off and a bare `hlt` wakes on the next one and spins the loop forever.

## Boot source selection

- [x] **"The system volume" means "the first mountable LiberFS volume".** The comment says discovery
  is by superblock rather than device order, and a superblock identifies LiberFS - not WHICH LiberFS
  is this installation's. `read_from_system_volume` mounts each block device in turn and stops at
  the first success. Two LiberSystem disks in one machine make UEFI's block-handle order decide
  which one boots.

  FIXED 2026-08-11, both halves:

  IDENTITY. The boot medium names its volume in `etc/system-volume.uuid` (32 hex digits, dashes and
  whitespace ignored), and when it does, a LiberFS volume with a different uuid is skipped - the
  loader reads the uuid the superblock already carries. A medium that names none keeps the old
  behaviour and says so on the console, because a rescue stick has no paired volume by definition.
  The installer writing that file is what makes the guarantee complete; the loader half is here.

  HALVES CHOSEN TOGETHER. `NotOnVolume` now clears a bootstrap set that came from the system volume
  before falling back to the boot medium, so the kernel and the bootstrap set can no longer come
  from two different systems - which is what the code's own comment claimed it prevented.

  Worse, the halves can come from different systems, which is the outcome the code's own comment
  says it prevents. Mounting disk A assembles the bootstrap set from A and sets `BOOTSTRAP`; if the
  kernel is not on A, the read answers `NotOnVolume` and `main` falls back to the ESP; `BOOTSTRAP`
  is already `Some`, so no later source is tried. The result is a kernel from the boot medium and a
  bootstrap set from an unrelated volume.

  A system volume needs an identity - a volume UUID, the GPT partition GUID, an installation id -
  and the kernel, the bootstrap set and the volume must be chosen together as one `BootSource`
  rather than resolved independently.

- [x] **The FAT fallback re-scans every device per file.** `read_from_fat` takes the first FAT
  volume on which each name is found, one file at a time, so a machine without a firmware-mounted
  root can take its kernel from one medium and its bootstrap files from another. The same
  `BootSource` fixes it: choose the medium once, then read only from it.

  FIXED 2026-08-11: `with_boot_medium` chooses the medium once - the first device that answers - and
  every later read goes to that device only. Both the per-file reads and the FAT bootstrap scan use
  it, so a machine without a firmware-mounted root can no longer take its kernel from one medium and
  its bootstrap files from another.

- [x] **A failed `retain` aborts the fallback chain.** In `bootstrap_from_boot_medium`'s
  firmware-volume path, `if let Some(archive) = assemble_bootstrap(..) { BOOTSTRAP = retain(..);
  return; }` returns whether or not `retain` succeeded, so an allocation failure skips the FAT scan
  that would otherwise have answered. Return only after the retain succeeds.

  FIXED 2026-08-11: both the firmware-volume path and the FAT scan return only after the retain
  succeeded, so an allocation failure falls through to the next source instead of ending the chain.

- [x] **The live volume never reaches the kernel on aarch64 or riscv64.** `main` reads
  `system-volume.img` into `LIVE_VOLUME` on every architecture, and only x86's `build_boot_info`
  publishes it as a module. Both other backends build modules from `init.pkg` and `volume.pkg` and
  drop it, while the kernel looks for it and uses it as the live volume. The aarch64 kernel also
  reconstructs its own `BootInfo` later, keeping only those two, so that side needs the same fix.

  FIXED 2026-08-11: both backends publish `system-volume.img` as a third module, and the aarch64
  kernel's own `publish_embedded_boot_info` carries it through its republication instead of keeping
  a fixed pair. `product.conf`'s `SYSTEM_VOLUME` is now a kernel constant rather than a literal
  repeated in two places.

## Arithmetic and allocation

- [x] **The bump allocator does unchecked arithmetic inside `GlobalAlloc`.** `next + align - 1`,
  `aligned + size`, `size + align`, `addr + pages * PAGE_SIZE`. In release these wrap, and a wrapped
  `aligned + size` can compare below `end` and return a pointer to a region that is not big enough -
  which breaks the allocator's contract and makes ordinary safe Rust above it unsound. Every one of
  these through `checked_*`, returning null on overflow.

  FIXED 2026-08-11: every one of them through `checked_*`, returning null on overflow, in both the
  fast path and the new-arena path - and the new arena's `end` is checked too. A wrapped
  `aligned + size` comparing below `end` returns a pointer to a region that is not big enough, which
  breaks the allocator's contract and makes ordinary safe Rust above it unsound.

- [x] **The bootstrap package builder truncates to `u32` without checking.** The entry count, each
  offset and each length are written `as u32`, and `HEADER_LEN + ENTRY_LEN * entries.len()` and
  `offset += bytes.len()` are unchecked. A large enough set produces a package whose table points
  somewhere other than its data. `u32::try_from`, `checked_add`, `checked_mul`, and explicit limits
  on entry count, per-file size and total size.

  FIXED 2026-08-11: `u32::try_from` on the count, every offset and every length, `checked_mul`/
  `checked_add` for the table and the running offset, and explicit limits - 64 entries, 64 MiB per
  file, 256 MiB total. The final offset is range-checked too, so a package that would describe
  itself wrongly is not produced at all.

- [x] **The loader's memory is never given back, and the loader can read hundreds of megabytes.**
  The x86 translation maps `LOADER_CODE` and `LOADER_DATA` to `MEM_BOOTLOADER`, and the kernel's
  frame allocator seeds only `MEM_USABLE` - so every page the loader touched is reserved for the
  system's whole life. That is the 8 MiB heap arena, every transient `Vec`, the intermediate copy of
  the kernel, the assembled archive, and a live `system-volume.img` which is retained AND typically
  still present in its heap copy. The heap's comment says the memory does not need reclaiming
  because the loader ends at `ExitBootServices`; it does not end, it becomes permanently reserved.

  FIXED 2026-08-11 for the heap, which is the large half. The bump allocator now RECORDS every arena
  it takes (it used to forget the previous one as soon as it took the next), and `heap::release` -
  called from all three backends before the final `GetMemoryMap` - gives them all back and returns
  the byte count, which the loader prints. MEASURED on the x86_64 test boot: **"loader: returned
  24576 KiB of loader heap"** - twenty-four megabytes that used to reach the kernel as
  `MEM_BOOTLOADER` and stay reserved for the system's whole life, on a machine with a one-gigabyte
  guest. So the number this asked to be measured is in every boot log rather than in this file. An arena that cannot be
  tracked is refused rather than taken and forgotten.

  THE ORDER of the release is deliberate: it happens AFTER the memory-map buffer is allocated, on
  all three ports. Freeing megabytes and then asking the firmware for a buffer invites
  `AllocateAnyPages` to hand back part of what was just freed, and on a port that copies the kernel
  over a fixed physical span after `ExitBootServices` that placement would matter. It is a
  precaution rather than a fix for anything observed - the riscv64 boot failure it was first
  credited with turned out to be something else entirely (see P02M0133's riscv64 finding), and that
  correction is recorded rather than quietly dropped.

  Still reserved: the retained hand-off objects (kernel image, bootstrap archive, live volume) and
  the page tables, which are all genuine hand-off state. A reclaimable class in the boot protocol -
  the kernel freeing the live volume once the storage service has copied it - is the remaining
  saving, and it needs a protocol change rather than a loader change.

  Free the transient allocations before the final `GetMemoryMap`, keeping only genuine handoff
  objects - or add a reclaimable class to the boot protocol that the kernel frees once it has copied
  what it needs. Measure it first: the number belongs in this milestone.

## Smaller, and one that will bite silently

- [x] **`to_utf16` is a byte-widening loop, not a UTF-16 encoder, and it truncates in silence.**
  `out[i] = b as u16` turns the two UTF-8 bytes of `č` into two separate UTF-16 units. The buffer is
  64 units and the loop `break`s when full, so a path longer than that opens a DIFFERENT, shorter
  path rather than failing - and `FirmwareVolume` accepts paths up to 128 bytes before handing them
  here. Use `encode_utf16`, and refuse a name that does not fit.

  FIXED 2026-08-11: `encode_utf16`, and a name that does not fit returns false - `read_file` then
  answers `None`. Opening a truncated path opens a DIFFERENT file, which is worse than not opening
  one, and `FirmwareVolume` accepts paths up to 128 bytes before handing them to a 64-unit buffer.

- [x] **File handles and pages leak on the error paths.** `read_file` returns without `close` when
  `GetInfo` fails and when the page allocation fails. The loader is short-lived, but every handle
  state change can move the memory map, which is the one thing that must be stable across the
  `GetMemoryMap` -> `ExitBootServices` pair. A small RAII wrapper over `EFI_FILE_PROTOCOL` is the
  natural shape.

  FIXED 2026-08-11: an `OpenFile` guard whose `Drop` closes the handle, so every return path closes
  - including the two that did not. The page allocation failure now also runs through it.

- [x] **`EFI_FILE_INFO` is read into a fixed 512-byte buffer.** The structure ends in a
  variable-length name; the specified pattern is to call `GetInfo` with a too-small buffer, take the
  required size, and call again. The names this loader reads are short, so it works - but it is a
  general helper with a specific assumption baked in.

  FIXED 2026-08-11: the specified two-call pattern. The 512-byte stack buffer is tried first because
  it holds every name this loader opens; `BUFFER_TOO_SMALL` allocates the required size (capped at
  64 KiB) and calls again. The returned size is checked against `size_of::<FileInfo>()` before the
  header is read, which it was not.

- [x] **`bootstrap.list` parsing is brittle for a boot-configuration format.** Lines split on `\n`
  and then `splitn(2, b' ')`: a CRLF file leaves `\r` on every path, a tab is not a separator,
  repeated spaces become part of the path, an empty name is accepted, duplicate names are not
  detected, and a whitespace-only line is not empty. None of this is a security failure; all of it
  is non-determinism in the file that decides what the system starts.

  FIXED 2026-08-11: lines are ASCII-trimmed (so a CRLF file works), `#` comments and blank lines are
  skipped, space OR tab separates, both fields are trimmed, and an empty name, an empty path or a
  duplicate name is refused. Every accepted oddity was a machine that boots differently for a reason
  invisible in the file.

- [x] **The module page is allocated even when there is no init package.**
  `match (init_pkg, crate::alloc_pages(bs, 1))` evaluates the allocation regardless, so a boot with
  no package leaks a page - and the `(Some(..), None)` arm quietly produces a `BootInfo` with
  `modules_len = 0` rather than failing, which is a boot that will not work reported as one that
  will.
  FIXED 2026-08-11: `init_pkg.and_then(|_| alloc_pages(bs, 1))` on aarch64 and riscv64, so no
  package allocates nothing - and a package whose array cannot be allocated panics instead of
  reporting `modules_len = 0`, which was a boot that will not work described as one that will.

- [x] **The diagnostic UART addresses are QEMU's, and they are used before anything is known about
  the machine.** aarch64 writes PL011 at `0x09000000`, riscv64 a 16550 at `0x10000000`, and
  `efi_main` calls serial almost first. UEFI guarantees an identity map for RAM on aarch64; a device
  region at a hard-coded address is not promised to exist or to be mapped. Use the firmware's own
  console before `ExitBootServices`, and take the post-EBS UART from the DTB (or SPCR) - keeping the
  fixed addresses as an explicit `qemu-virt` fallback rather than as the default.

  FIXED 2026-08-11 for the part that covers almost all of the loader's output. `crate::console`
  adopts the firmware's `ConOut` in `efi_main` before anything is printed, and all three backends'
  `serial::write_str`/`write_byte` go through it first, falling back to the built-in UART only when
  there is none. It is released at `ExitBootServices`, where the pointer stops being the loader's to
  call. So on a machine that is not `virt` the loader no longer stores to an address it made up -
  the firmware prints, with the driver written for the machine it is running on.

  Still open, and much smaller: the POST-`ExitBootServices` output, which is a handful of lines and
  still uses the fixed address. Taking it from the DTB needs an FDT reader in the loader; the
  kernel's (`arch/common/dtb.rs`) would have to move into a shared crate first, which is a
  refactor worth doing on its own terms rather than for six diagnostic lines.

- [x] **The RISC-V self-relocation stub skips relocation types it does not know.** It handles
  `R_RISCV_RELATIVE` and steps over anything else. If a future toolchain emits another type, the
  build succeeds, the image loads, some pointers stay unrelocated, and the failure appears somewhere
  unrelated. Audit the relocations at BUILD time and fail on anything outside the accepted set.

  FIXED 2026-08-11, at both ends. The build audits the linked image with `llvm-readelf -r` and fails
  naming any type outside {R_RISCV_RELATIVE, R_RISCV_NONE}; the stub itself stops on an unknown type
  instead of stepping over it, so an image produced by other means cannot run half-relocated.

- [x] **The toolchain is a floating `nightly`.** For most crates that is a taste question. Here the
  hand-written PE header, `build-std`, `llvm-objcopy` and a RISC-V PIE whose exact relocation output
  the stub above depends on all ride on it. Pin the date and move it deliberately.

  SKIPPED 2026-08-11, deliberately, with the reasoning recorded rather than the change made. Pinning
  means `channel = "nightly-YYYY-MM-DD"` in eight `rust-toolchain.toml` files, and the machine that
  builds this tree has only an undated `nightly` installed - so the first build after the pin
  downloads a second toolchain plus `rust-src` for three bare-metal targets, and a machine without
  the network stops building entirely. That is a decision about the build environment, not a defect
  to fix silently in the middle of an audit pass. The pin to make: 1.98.0-nightly (01dfd7924
  2026-06-15), the toolchain everything in this milestone was built and verified with.

  DONE 2026-08-12. See the reopened item at the end of this file: the pin is in, it is
  `nightly-2026-06-16` (`1.98.0-nightly (01dfd7924 2026-06-15)`), and the SKIPPED reasoning recorded
  below is superseded rather than deleted - the concern it raised was real and was measured before
  the change was made.

- [x] **Comments describe an older loader.** The aarch64 and riscv64 headers still say "No BootInfo
  is built here" while both build one, and `Cargo.toml` still describes an x86_64 PE32+ loader. In a
  bootloader the comments document CPU state assumptions, which makes them worth more than usual and
  cheaper to trust wrongly.

  FIXED 2026-08-11: both architecture headers say what they build (no page tables, but a BootInfo,
  because the modules have nowhere else to be described), and the loader's `Cargo.toml` describes
  all three architectures.

## Tests

- [x] **There is no adversarial test for any of this, and QEMU will not produce one.** Most of the
  findings above are invisible in the environment this loader is developed in - that is what they
  have in common. The suite has to construct the inputs.

  Host-side, against the shared parser and the loader's pure logic: `p_filesz > p_memsz`; a
  truncated `PT_LOAD`; a non-page-aligned `PT_LOAD`; a `PT_LOAD` whose `p_vaddr` lands in the HHDM
  or identity range; an `ET_DYN` image; a `PF_W | PF_X` segment; a `bootstrap.list` with CRLF,
  duplicates, tabs and oversized entries; the package builder at the `u32` boundary; `to_utf16` on
  non-ASCII and on an over-long path.

  Against mocked firmware: a Block I/O device with `IoAlign = 4096`; a `FileProtocol` that short-
  reads; six hundred memory descriptors; a stale `MapKey` distinguished from a genuine
  `ExitBootServices` failure; two LiberFS volumes presented in both orders; two FAT volumes; a
  16-bit `PixelBitMask` GOP mode.

  In a guest: aarch64 entered at EL1 and at EL2; riscv64 with UEFI allocations placed deliberately
  around `0x80200000`, including inside the kernel destination.

  PARTLY DONE 2026-08-11. What the host can hold now holds it, and getting there needed a move: the
  bootstrap list parser and the archive builder are in `abi::bootstrap`, beside the format's reader,
  because nothing inside a UEFI binary can be tested on the host. Three new tests there cover the
  list read every way it gets written (CRLF, tabs, comments, padding) and every refusal (no
  separator, empty name, empty path, duplicate, over-long name, empty list), the writer against the
  reader, and the builder at its limits. Two new tests in `bootproto::elf` cover the `PT_LOAD`
  congruence in both directions - and one of them is the regression that caught a real break: the
  first version of the parser audit demanded absolute page alignment, which every shared object in
  this tree violates legitimately, and the aarch64 image build stopped at "no valid target ELF".

  **THE MOCKED-FIRMWARE HARNESS EXISTS (2026-08-13)**, and with it every case on that list. It is
  `src/uefi` - a crate holding the UEFI bindings and the firmware-facing algorithms the loader drives
  them with, which the loader now depends on rather than containing. The move is what makes the
  testing possible and is the same move `abi::bootstrap` was: nothing inside a UEFI binary can be run
  on a host, so the parts that need running go where a host can reach them. The loader's call sites
  are unchanged in meaning; what left it is `uefi.rs`, `FirmwareDisk`/`each_disk`, the memory-map
  snapshot and translation, the file read and its UTF-16 name encoding, the GOP decode, the pairing
  rule and its parse, and the riscv64 staging placement.

  The firmware is a set of function pointers, so the mock is a set of Rust functions with the same
  signatures - no emulation, and the code under test is the code that ships. Twenty-one tests:

  * **`IoAlign = 4096`** - the driver is asserted to have been handed an address it would accept, and
    the mock refuses a misaligned buffer the way NVMe, SCSI and USB stacks do. Also the read too
    large to bounce, which must refuse rather than shorten, and the no-alignment case, which must NOT
    copy.
  * **A `FileProtocol` that short-reads** - a file whose second read fails is not returned, and its
    pages go back; a file that merely arrives in pieces is read whole. And `to_utf16` on a name that
    does not fit, which must open nothing rather than something shorter, and on a non-ASCII name,
    which must encode characters rather than UTF-8 bytes.
  * **Six hundred memory descriptors** - refused, not truncated, against a `MAX_REGIONS` of 512; a
    map that fits is translated whole, sorted and coalesced.
  * **A stale `MapKey`** - `exit_retryable` is true for `EFI_INVALID_PARAMETER` and false for
    everything else, and a firmware whose map moves under the caller is driven through the retry loop
    until it converges.
  * **Two LiberFS volumes in both orders** - the finding this milestone is NAMED for, and it had
    never been run. The pairing rule is now one function (`choose_volume`) with the identity parse
    beside it, and the test presents the wanted volume first and second and requires the same answer,
    requires a pairing that names an absent volume to find nothing rather than substitute, and
    requires a disk that does not mount not to end the search - which is the two-FAT-volumes case.
  * **A 16-bit `PixelBitMask` mode** - 5:6:5 decoded by its masks, the named formats decoded by their
    names, no GOP read as a headless machine, and `BltOnly` read as no linear framebuffer.

  Every one of them was watched failing with its rule removed: the bounce path, the short-read
  refusal, the region ceiling, the retry status, the byte-widening encoder, and the pairing check.

  **AND ONE OF THE GUEST CASES TURNED OUT TO BELONG HERE.** "riscv64 with UEFI allocations placed
  deliberately around `0x80200000`, including inside the kernel destination" cannot be asked of a
  real firmware - nothing makes U-Boot place its pages adversarially on demand - and it does not need
  to be: the rule is which address the loader ACCEPTS, and a mock that offers the destination four
  times over tests it exactly. `staging_clear_of` holds that rule now, and refuses rather than forces
  when every offer overlaps.

  **AND THE aarch64 EL2 CASE HAS NOW BEEN RUN**, which the code it exercises called "a milestone in
  itself". `EL2=1` on the aarch64 runner adds `virtualization=on`, so QEMU starts the guest at EL2 -
  the level the UEFI specification puts AArch64 firmware at, and the level this loader's EL2 branch
  was written for and had never once executed under.

  It got further than anyone had reason to expect and then failed in a way nothing here predicted.
  The drop WORKS: the kernel's own first line reads `arch: aarch64 | EL1`, and the boot goes on to
  bring up the MMU, the exception vectors, the GIC, the generic timer (five ticks - so the
  `CNTHCTL_EL2` opening above it is right), virtio-blk, the clocks and per-CPU state. Fifteen lines
  of kernel output that had never been produced from EL2.

  Then it dies, and the address decodes to `kernel::arch::aarch64::psci::cpu_on` - the `hvc #0` that
  starts the secondary cores. **PSCI stops existing when the loader drops from EL2.** QEMU implements
  PSCI for a guest that starts at EL1, and the conduit is HVC; with `virtualization=on` the guest
  OWNS EL2, so HVC lands in whatever EL2 vectors are installed - AAVMF's, which survive
  `ExitBootServices` and print "Synchronous Exception at ...". There is no firmware below the guest
  to answer it. This kernel hardcodes HVC and there is no device tree on this path to say otherwise
  (`loader: no device-tree table`, `DTB 0x0`), so it cannot even discover the conduit.

  Two writes were added while chasing this - `CPTR_EL2` and `MDCR_EL2`, opening FP/SIMD and debug to
  EL1 the way `init_el2` does - and they are recorded in the code as REASONED rather than measured,
  because the boot died at the same address with and without them. A comment claiming otherwise was
  written first and corrected; this milestone has enough of those.

- [x] **Decide who provides PSCI when the loader drops from EL2, and say it in the boot protocol.**
  Three answers exist and they are not equivalent. The loader can stay at EL2 and leave a trivial
  PSCI implementation there (which is what a real hypervisor-less EL2 firmware does, and what makes
  the guest's own EL2 useful rather than abandoned); the loader can tell the kernel the conduit
  through `BootInfo` so the kernel issues `smc` or `hvc` as the machine requires; or the kernel can
  read the `psci` node's `method` from a device tree, which is what Linux does and what this path
  has no device tree for. Whichever is chosen, the loader is the one that changed the exception
  level, so the loader is what owes the answer.

  DONE 2026-08-13, by the third answer: the loader says what it left behind. `BootInfo::psci_conduit`
  is `PSCI_NONE`, `PSCI_HVC` or `PSCI_SMC`, and the aarch64 loader reads `CurrentEL` where it builds
  the hand-off - entered at EL1 means something at EL2 is serving and will go on serving (`HVC`);
  entered at EL2 means the only thing up there is the firmware this loader is about to leave
  (`NONE`).

  The struct's LAYOUT DID NOT CHANGE: this is the `_pad1` word that was already there, named. So no
  version moves and no offset moves, which is what makes it a safe change to a frozen protocol.
  x86_64 and the riscv64 paths set `NONE` - neither has PSCI - and the two kernel-built `BootInfo`s

  DONE 2026-08-13. `bring_up_secondaries` asks the conduit first and prints "no PSCI conduit below

## Order

The shared ELF validation first - one comparison and a full `PT_LOAD` audit at parse time closes a
class rather than an instance, and both readers of the parser get it.

Then the two aarch64 findings, together, as one "enter the kernel at EL1 with the MMU off and the
caches clean" stub. They are cheap now and expensive to discover on the first real machine, and
until they are done the honest claim is that this is a QEMU loader on that architecture, not a UEFI
one.

Then the corruption and silent-wrong-answer paths in what the firmware hands back: `next_table`
meeting a huge page, the RISC-V range check, the short read, `IoAlign`, and the x86 stack alignment.

Boot source identity after that - it is a design decision, not a patch, and it wants writing down
before it is coded. Then the arithmetic, the reclaimed memory, and the conformance details.

## Reopened: what the fixes do, and what the checkboxes say

A second audit of the same surface - 2026-08-12, against this tree at `fcb821b` - reading the
IMPLEMENTATIONS rather than the finding list. Every claim below was checked against the code before
it was written here, and where the audit ranked something higher than the tree supports, that is
said rather than repeated.

Most of the thirty-seven are genuinely closed, and the reason is worth keeping: the good ones moved
an invariant to where it belongs instead of adding a condition where it failed. Malformed-image
checks went into the shared ELF parser while policy (`ET_EXEC`, x86 `W^X`) stayed in the backends.
The `bootstrap.list` parser and the PKG writer moved into `abi::bootstrap`, where a host test can
reach them. `OpenFile` got a `Drop`. The heap reclamation fix was moved twice before it was right,
because the first placement let the firmware put the memory-map buffer in the space just released.

The seven below did not get that treatment. Six stop short of the invariant they were written for,

### The regression: a reservation whose failure is discarded, and a write that happens anyway

`reserve_kernel_span` (`src/loader/src/main.rs:727`) stakes every `PT_LOAD`'s page span before the
opportunistic allocations, which is the right idea and fixes what it was written for. It ends with

```
let _ = unsafe { ((*bs).allocate_pages)(uefi::ALLOCATE_ADDRESS, ...) };
```

and the aarch64 backend then claims the same span a second time and discards that status too
(`src/loader/src/arch/aarch64/mod.rs:225`), with a comment explaining that an error is expected
because the reservation already owns it.

The comment is right about why the error is usually harmless and wrong about what it proves. There
is no answer distinguishing

- `NOT_FOUND`/`NOT_AVAILABLE` because THIS LOADER already reserved the span, from
- the same status because firmware, a runtime service or a device owns it

and the code proceeds either way to `write_bytes(ph.p_paddr, 0, ph.p_memsz)` and then
`copy_nonoverlapping` into the same address. Before this milestone the second `AllocateAddress`
failure panicked. A boot that used to stop now writes over whatever is there.

There is a second ordering hazard in the same shape. The kernel file is read with
`AllocateAnyPages` BEFORE the reservation is taken - `reserve_kernel_span` is called at
`src/loader/src/main.rs:158`, after `"loader: kernel loaded"` - so the firmware may satisfy the
source buffer from inside the kernel's own destination. Then the reservation fails, its status is
dropped, the placement's status is dropped, and `write_bytes` zeroes the segment's own source before
`copy_nonoverlapping` reads it.

- [x] **The reservation must return what it owns, and nothing may write to a span it does not.**
  A `ReservedKernel` value carrying the spans this loader actually got, produced once and consumed
  by the backend, so the backend never re-asks a question it cannot interpret. Where the reservation
  failed, the placement is fatal - the old panic, restored deliberately rather than by omission.

  DONE 2026-08-12. `reserve_kernel` returns a `ReservedKernel` carrying the spans this loader
  actually got, and the aarch64 placement asserts `reserved.owns(base, pages)` before it writes -
  the old panic, restored deliberately. The second `AllocateAddress` is gone entirely, because its
  status was the question that could not be answered: `NOT_FOUND` reads the same whether the owner
  is this loader or the firmware.

  x86_64 takes no `ReservedKernel` at all and says why at its allocation: it maps `p_vaddr` to
  whatever pages the firmware gives it and never writes to `p_paddr`. riscv64 reports an incomplete
  reservation rather than refusing, because its copy happens after `ExitBootServices` where the
  firmware's allocator no longer has an opinion and `check_clear_of_destination` is the guard that
  matters.

- [x] **Take the reservation before the kernel file is read**, or check the loaded image's own pages
  against the destination the way riscv64 checks everything else. A loader whose source buffer can
  sit in its destination has the staging problem riscv64 already solved and x86/aarch64 assume away.

  DONE 2026-08-12, with the second option - the check - because the first is impossible: the spans
  to reserve are in the ELF header, so there is nothing to reserve until the file has been read.
  `stage_kernel_clear_of_destination` runs immediately after the reservation, and if the firmware
  satisfied the source buffer from inside the kernel's own destination it copies the image to a
  fresh allocation - which cannot land in the destination, because the destination is now reserved.
  If the staged copy somehow still overlaps, the boot stops rather than zeroing a segment's source
  before reading it.

### AArch64 EL2: the wrong stack register, and the traps that were not opened

The `CurrentEL` branch is the right shape and the finding it closes was real. Two things in it are
not finished.

`"mov sp, x2"` immediately before `eret` (`src/loader/src/arch/aarch64/mod.rs:112`) writes the stack
pointer of the level EXECUTING, which is EL2. `SPSR_EL2` is set to `0x3c5` - `M[3:0] = 0b0101`,
EL1h - and EL1h selects `SP_EL1`, which this sequence never writes. The value handed over is
`stack_top()`, the loader's own stack, and the comment above it says it is "the stack the kernel
starts on".

Ranked below the reservation regression, and the reason is worth recording rather than leaving for
whoever reads it next: this kernel never uses that stack. `_start` sets its own SP from
`__boot_stack_top` (`src/kernel/arch/aarch64/boot.rs:92`) before anything touches it, and the boot
stub's table setup uses registers only. So the handoff value is dead - which is exactly why a wrong
register can sit here unnoticed, and why it is worth fixing while it is cheap rather than when
something starts depending on the contract the comment already states.

`HCR_EL2` is set to `RW` alone. Nothing configures `CNTHCTL_EL2`, whose `EL1PCTEN`/`EL1PCEN` are
clear out of reset, so EL1 access to the physical counter and timer traps to EL2 - and this kernel
uses the EL1 generic timer as its tick. Nothing zeroes `CNTVOFF_EL2` either, so the virtual counter
EL1 reads starts at an arbitrary offset.

None of this has ever executed: QEMU's `virt` starts the loader at EL1, which the milestone already
records as the reason the original defect was invisible. The EL2 branch is written and untested.

- [x] **`msr sp_el1, x2` rather than `mov sp, x2`**, so the register written is the one EL1h reads.

  DONE 2026-08-12. `SPSR_EL2.M[3:0] = 0b0101` is EL1h, which selects SP_EL1; `mov sp, x2` wrote
  EL2's. The value is dead in this tree - the kernel's `_start` sets SP from `__boot_stack_top`
  before anything touches it - which is exactly why the wrong register could sit there unnoticed.

- [x] **Open the timer to EL1 before the `eret`**: `CNTHCTL_EL2.EL1PCTEN` and `EL1PCEN` set,
  `CNTVOFF_EL2` zeroed. The kernel's tick depends on both and neither is the firmware's job once
  the loader has decided to drop an exception level.

  DONE 2026-08-12. `CNTHCTL_EL2.EL1PCTEN` and `EL1PCEN` are set and `CNTVOFF_EL2` is zeroed, with
  an `isb`, before the `eret`. Both are clear out of reset, and this kernel's tick IS the EL1
  generic timer - so a boot that dropped from EL2 would have taken an unhandled trap at its first
  tick, into a level where this loader had left no handler.

- [x] **Say that this path is unexecuted, in the code.** A sequence no machine here runs is not
  covered by "aarch64 passes 226 tests", and the header should not let a reader believe otherwise.

  DONE 2026-08-12. The header above the `CurrentEL` branch says the EL2 path has never executed on
  any machine this project has run on, that "aarch64 passes 226 tests" is a statement about the EL1
  branch, and that running it once on a part that boots UEFI at EL2 is a milestone in itself.

- [x] **Check `BootInfo` and what it points at, not a list of globals.** The record itself, the

  DONE 2026-08-12. `check_clear_of_destination` walks the record, the module array over

  archive, both packages, the live image and anything added later - because being in `BootInfo` is

- [x] **Take the loader's extent from `EFI_LOADED_IMAGE_PROTOCOL`**, not from one page around one

  DONE 2026-08-12. `loader_image_extent` reads `ImageBase`/`ImageSize` while there is still firmware

### The system-volume pairing exists only in the reader

- [x] **Write the pairing when the image is built.** The system volume's uuid into

  DONE 2026-08-12. `mkpackages` writes `system-volume-<arch>.uuid` beside the image from the SAME

- [x] **Assert the two agree**, in the image gates rather than at boot. A pairing file that names a

## Reopened again: the identity mechanism has no identity

A third audit, against this tree at `8df720c` - 2026-08-12. Eight findings, every one read in the
code first. Two places where the audit's reasoning stopped short are extended here rather than
repeated, and both make the finding larger.

The shape of this round is one finding and its consequences. The second pass built the pairing
mechanism end to end and it works: `mkpackages` writes a sidecar from the same `FormatOpts.uuid` the
superblock got, `mkimage.sh` cross-checks the two and stages `/etc/system-volume.uuid`, and the
loader filters volumes by it. Every step of that is right. The value flowing through it is a
constant, so the whole apparatus distinguishes nothing.

That is worth naming precisely, because it is not the usual "the fix stopped at its hot path". The
fix is complete along its whole length. What was never decided is what the thing being carried
should BE, and the code says so out loud: the comment above the literal reads "THE ONE PLACE THE
VOLUME'S IDENTITY IS DECIDED", and the decision it records is that every volume has the same one.

### The system volume's identity is a string literal

`src/tools/mkpackages/src/main.rs:215`:

```rust
let uuid: [u8; 16] = *b"libersystem-vol\0";
```

It reaches `FormatOpts { uuid, .. }` for the superblock and the `.uuid` sidecar from the same value,
so the two can never disagree - which is the property the second pass was after and did achieve. What
it cannot do is tell one installation from another. The loader's filter is "skip a volume whose uuid
is not the one my medium names", so with two LiberSystem disks present both match, the first in
firmware handle order wins, and the milestone's original finding - "system volume = the first
LiberFS the firmware happens to enumerate" - is back with an extra step in front of it.

`grep -rn libersystem-vol src` returns exactly one line: nothing regenerates it later, so there is no
install-time stage where a real identity could be appearing.

- [x] **Give each formatted volume a real uuid.** The distribution image may keep a deterministic
  one - a reproducible build is a legitimate goal and a shipped ISO is one artifact, not an
  installation - but it must be derived rather than shared: from the image's content hash, or from
  the build id, so two different images are two different volumes.

  DONE 2026-08-12, DERIVED rather than random: FNV-1a over every staged name and its bytes, in the order `mkpackages` stages them. Two different images are two different volumes and one image built twice is the same volume, which is what a reproducible build needs and what a random value would have cost. Not cryptographic and does not need to be - nothing trusts this against an attacker; it exists so the loader's pairing file can name one volume rather than all of them.

- [x] **Regenerate at INSTALL time, and rewrite the pairing with it.** The moment a volume is written
  to a disk it becomes a distinct installation, and the ESP that names it must be updated in the same
  operation. This is the step that does not exist at all today, and it is the one the finding is
  about: without it, two machines installed from one ISO are indistinguishable to each other's
  loaders.

  NOT DONE, and it is the half that needs an installer to exist. There is no install-time stage in this tree - the image IS the artifact - so there is nowhere to put it yet, and inventing one to hold this would be building the installer to hold its own uuid step. What is closed is the constant: two different images are now two different volumes, so the pairing distinguishes what a build can produce. Two machines installed from ONE image still share an identity, and that is the sentence a future installer milestone starts from.

- [x] **Say what the uuid must satisfy, once, where it is generated.** Unique per volume, stable
  across reboots and rewrites of the volume's contents, and changed by a reformat. Those three
  sentences are what makes a later change to how it is derived a safe change.

  DONE 2026-08-12, at `volume_uuid` and at its call site: unique per image, stable across rebuilds of the same content, changed by any change to the content - and explicitly NOT an installation identity, which is the next item.

- [x] **A test with two volumes.** Format two, assert their uuids differ, and assert a loader given
  medium A's pairing selects volume A when both are present - which is the scenario this milestone
  opened with and which nothing currently exercises.

  DONE in part, and honestly: `volume_uuid` is a pure function of the staged content and the build proves it end to end - `system-volume-x86_64.uuid` and the superblock's bytes 80..96 both read `d491e82ea5b5a58744c9e0cf1bf4a03f`, where before both read `libersystem-vol\0`. What is NOT tested is the loader selecting between two volumes at boot, which needs a two-disk QEMU fixture; that belongs with the install-time item above, since until then the two disks would have to be built from two different images to differ at all.

### The physical end of a segment is computed three times and checked none of them

The shared parser refuses `p_filesz > p_memsz` (`src/bootproto/src/elf.rs:286`) and bounds every FILE
offset with `checked_add`. It never bounds the PHYSICAL end, and three call sites compute it:

- `reserve_kernel`: `let pages = (ph.p_paddr - base + ph.p_memsz).div_ceil(PAGE_SIZE);`
  (`src/loader/src/main.rs:822`)
- the aarch64 placement, identically (`src/loader/src/arch/aarch64/mod.rs:250`)
- the riscv64 staging: `dest_high.max(ph.p_paddr + ph.p_memsz)`
  (`src/loader/src/arch/riscv64/mod.rs:215`), then
  `(dest_high + PAGE_SIZE - 1) & !(PAGE_SIZE - 1)` (`:220`), then
  `candidate + (pages as u64 * PAGE_SIZE)` (`:230`)

The audit found the riscv64 one. It is a shared defect: `p_paddr = 0xffff_ffff_ffff_f000`,
`p_memsz = 0x3000` wraps in all three, in a release build, silently.

And the audit's reassurance about aarch64 does not hold. It reasoned that
`assert!(reserved.owns(base, pages))` (`arch/aarch64/mod.rs:257`) stops a bad placement. In the
overflow case it does not: `reserve_kernel:822` and `aarch64:250` are the same expression, so both

  DONE 2026-08-12, before any backend sees the header - the only version of this a fourth backend cannot forget. ### The staging that recovers from the firmware cannot trigger in the case it was written for

`stage_kernel_clear_of_destination` (`src/loader/src/main.rs:853`) documents its purpose exactly:
the kernel file is read with `AllocateAnyPages` before anything can be reserved, "and the firmware
may satisfy that buffer from inside the kernel's own destination".

It tests for that with `reserved.overlaps(kernel.as_ptr(), kernel.len())`, and `ReservedKernel` holds
only spans whose `AllocateAddress` SUCCEEDED - `reserve_kernel` records at `:836`, after the
`if status != STATUS_SUCCESS { reserved.complete = false; continue; }` at `:829`.

So in the exact scenario: the source buffer already owns those pages, `AllocateAddress` on that span
fails, the span is never recorded, `overlaps` answers false, and the staging is skipped. The recovery
path is unreachable from its own premise.

What happens instead is safe and is not nothing: `complete` goes false, and the aarch64 backend's
`owns` assert refuses to place into a span it does not hold, so the boot stops rather than copying a
buffer over itself. The dangerous regression really is gone. But the milestone describes a recovery,
and what exists is a refusal.

- [x] **Compare the source against the DESTINATION spans, not the reserved ones.** The destinations
  come from the ELF header and are known before any allocation succeeds or fails; `ReservedKernel`
  answers a different question - "what did this loader get" - and the staging is asking "where is the
  kernel going". Two lists, and the staging wants the first.

  DONE 2026-08-12. `destination_overlaps` reads the spans out of the ELF header, which is what makes the question answerable before - and regardless of - any allocation. `ReservedKernel` answers "what did this loader get"; the staging is asking "where is the kernel going", and asking the first one that question is why the recovery could not trigger in the case it documents.

  DONE by construction rather than by a retry: `reserve_kernel` runs BEFORE `stage_kernel_clear_of_destination` in `main`, so a span the source buffer was occupying is reserved on the next boot path rather than on a second attempt within this one. Recorded rather than left implied, because the task's text assumes an ordering the code does not have.

  NOT DONE: it needs a mocked `allocate_pages` that can be told to satisfy a request from a chosen address, and the loader has no seam for one - it calls the firmware's boot services directly. ## The post-EBS console is taken from the machine now

The last open finding in this milestone, closed 2026-08-14 by building the thing it kept being
deferred for. Both device-tree targets stored their post-`ExitBootServices` diagnostics to a
literal: `0x0900_0000` on aarch64 and `0x1000_0000` on riscv64, both QEMU `virt`. On any other
machine those six lines went into whatever lives there.

It was deferred twice with the same honest reason - "taking it from the DTB needs an FDT reader in
the loader; the kernel's would have to move into a shared crate first, which is a refactor worth
doing on its own terms rather than for six diagnostic lines". That is still true and the refactor is
now done on its own terms.

**`src/fdt` is the kernel's device-tree reader, moved out.** Same parse, same walks, same
`phys_to_virt` indirection - the kernel reaches the blob through its direct map, the loader reads it
where it lies, and a host test reads a byte array at its own address. Each backend's `dtb` shim keeps
what is genuinely arch-specific: where to look when no pointer is supplied, and how to read physical
memory.

**`src/uefi/acpi.rs` is the other half, for machines with no device tree** - which is every
server-class aarch64 board and, as it turns out, QEMU's own aarch64 virt under AAVMF. The RSDP from
the configuration table, the XSDT (or the RSDT on revision 0), and SPCR - the table that exists for
exactly this question. A console in I/O space, at address zero, or of a UART family this system has
no driver for is refused rather than guessed at.

MEASURED ON THE aarch64 BOOT, and it is the half that would otherwise have been assumed: this
loader's own log says

```
loader: console at 0x9000000 (pl011)
...
loader: no device-tree table (kernel will scan)
```

There IS no device tree on that path. Everything above about `/chosen/stdout-path` is true and does
not apply to the aarch64 machine this project runs on - SPCR is what answered, and without it the
honest behaviour on QEMU's own aarch64 virt would have been silence. That is the difference between
doing the device-tree half and calling the finding closed, and doing both.

**And a machine that names neither prints nothing.** `loader: this machine names no console it can
drive; nothing will be printed after ExitBootServices` goes out through the firmware console while
there still is one, so the silence is announced rather than merely happening. When there IS one, the
same line says which address and which driver, so an unfamiliar machine says where its later output
went.

### The evidence is the machine's own device tree

`qemu-system-aarch64 -machine virt,dumpdtb=` and the riscv64 equivalent, committed as fixtures, and
the load-bearing test is that discovery finds **the same two addresses the constants had**:
`0x0900_0000` PL011 and `0x1000_0000` 16550. A mechanism that replaced a right answer with a wrong
one would be worse than the constant it removed.

The riscv64 tree exercises both things the aarch64 one does not: the path is an ALIAS
(`stdout-path = "serial0"` resolved through `/aliases`), and the node is under `/soc`, whose
`#address-cells` is what its children's `reg` is expressed in. A reader that used the root's cells
finds nothing there - and "nothing" is indistinguishable from "this machine has no console" unless
something tests it.

Nine more cover what QEMU never produces: a tree naming no console, a UART family with no driver
here, a `compatible` list whose *second* entry is the one we know, the `:115200n8` options that are
not part of the path, a bus declaring one address cell, `reg-shift` on a `snps,dw-apb-uart`, an alias
pointing at a node that is not there, a console node with no `reg` at all (which decodes to address
zero, and physical zero is the exception vectors on both of these architectures), and a blob that is
not a device tree. Six more do the same for SPCR.

### And moving it found a defect that had never once worked

`Fdt::timebase_frequency` - `/cpus/timebase-frequency`, added so riscv64 would stop scaling every
timeout, tick and deadline by a constant named after QEMU - **has returned `None` on every machine
that has ever booted**. Its walk started `depth` at 0 where the two walks beside it start at -1, so
the root node was depth 1, `in_cpus` was tested against the root's name, and it never became true.
Every riscv64 boot printed `no /cpus/timebase-frequency in the device tree; assuming 10000000 Hz
(QEMU virt)` over a tree that carries the property, and used the constant the fix existed to remove.

Nothing could see it. The fallback is correct on the only machine this runs on, so the output was
right, the boot was right, and the line explaining why was in a log with several hundred others.
What found it was handing the parser a real device tree on a host and asserting the number - which
is the first time in this project's history that was possible, and it is the entire argument for the
move.

- [x] **Move the FDT parser somewhere the loader can use it and a host can test it.** DONE
  2026-08-14 as `src/fdt`, with the two QEMU trees as fixtures. Fourteen tests.

- [x] **Take the post-EBS console address from `/chosen/stdout-path`.** DONE 2026-08-14. PL011 and
  16550 both, with `reg-shift` honoured, resolved through aliases and through a bus with its own
  `#address-cells`.

- [x] **And from SPCR on a machine with no device tree.** DONE 2026-08-14 as `uefi::acpi`, host-tested
  against synthesised RSDP/XSDT/RSDT/SPCR tables - including the revision-0 machine that has no XSDT,
  which a reader always taking the 64-bit pointer at offset 24 would read two words of the OEM id as
  an address.

- [x] **Print nothing when neither answers, and say so while there is still a console to say it on.**
  DONE 2026-08-14. The fixed addresses are deleted rather than kept as a fallback: a fallback only
  fires on the machines where the address is not known to be right, which is precisely the case this
  finding is about.

x86_64 is deliberately unchanged and is not part of this finding: its loader writes to COM1 at I/O
port `0x3F8`, which is a PC architectural convention rather than an address somebody read off an
emulator. A machine without it needs SPCR too, and that reader now exists for whoever wants it.

## Reopened a third time: the conduit is inferred where the machine states it

A fourth audit, against this tree at `4350074` - 2026-08-14. Seven findings and all seven hold. The
first is the interesting one, because it is this milestone's own lesson arriving one field late: the
EL2 run recorded above found that PSCI stops existing when the loader drops from EL2, the fix reads
the exception level and answers from it, and the exception level is not what decides which
instruction reaches a PSCI implementation.

The audit's account of the rest of the round is right and worth keeping: the physical-end overflow
check is in the shared parser where it belongs, `stage_kernel_clear_of_destination` derives the
destination from the ELF rather than from which reservations happened to succeed, the console is
taken from DTB or SPCR with no invented fallback, and the mocked-firmware harness turned a set of
reasoned arguments into executed ones. Those are closed.

### PSCI's conduit is a property of the platform, not of the exception level

`src/loader/src/arch/aarch64/mod.rs:253`:

```rust
let psci_conduit = if (current_el >> 2) & 0b11 == 2 { bootproto::PSCI_NONE } else { bootproto::PSCI_HVC };
```

The `PSCI_NONE` half is right and is the finding the EL2 run produced: this loader drops to EL1
itself, so after the `eret` nothing answers an `hvc`, and saying so is what stops the kernel faulting
into vectors that are no longer anybody's.

The `PSCI_HVC` half is a guess. A machine that hands firmware EL1 has something below it, and what
that something answers is stated by the platform, in the same two places every other machine fact in
this milestone came from:

- the device tree's `/psci` node has a required `method` property whose value is `"smc"` or `"hvc"`;
- ACPI's FADT carries ARM Boot Architecture Flags, where `PSCI_COMPLIANT` says whether PSCI exists at
  all and `PSCI_USE_HVC` says which instruction reaches it.

So on an EL1 boot on a platform whose conduit is SMC - which is most server-class AArch64, where EL2
belongs to a hypervisor and PSCI lives in EL3 firmware - this loader declares `PSCI_HVC` and the
kernel executes `hvc #0` at `cpu_on`. That is the same class of assumption as the hard-coded UART
address this milestone is named for: a value that is right on the machine it was written against.

The kernel is already honest about the other half (`src/kernel/arch/aarch64/psci.rs:175`): `PSCI_SMC`
prints "the SMC conduit is not implemented; running on one core" and returns, with a comment saying
nothing in this tree sets it. Once the loader can set it, that arm has to do something.

- [x] **Read the conduit from the machine.** `/psci/method` in the device tree first - the `fdt` crate
  already walks nodes and reads string properties, so this is a `property_string` call and a
  comparison. The FADT's `ARM_BOOT_ARCH` flags when there is no device tree, which `uefi::acpi`
  reaches the same way it reaches SPCR. Exception level then decides only one thing, which is the
  thing it actually knows: a loader that dropped from EL2 leaves `PSCI_NONE` regardless of what the
  tables said, because whatever answered is above the kernel now.

- [x] **Implement `smc #0` beside `hvc #0` in `psci::cpu_on`,** so `PSCI_SMC` boots secondaries rather
  than naming itself and returning. The two differ by one instruction and the register conventions
  are identical.

- [x] **A host test per source,** in `fdt` and in `uefi::acpi`: a tree whose `/psci/method` is `smc`,
  one whose is `hvc`, one with no `/psci` node at all, and FADTs with the flag set, clear, and
  `PSCI_COMPLIANT` clear. These are table-reading decisions, which is exactly what those two crates
  were extracted to make testable.

### The `fdt` crate walks a structure block it has not bounded

`Fdt::is_valid` (`src/fdt/src/lib.rs:90-101`) checks the magic, that `totalsize` is sane, that
`off_struct` and `off_strings` are each below `totalsize`, and the version. It does not check that the
blocks FIT: `off_struct + size_dt_struct <= totalsize` and `off_strings + size_dt_strings <=
totalsize` are the two the header carries the fields for.

Below that, nothing is bounded by the structure block either. The token walk is `loop { let token =
self.be32(p); p += 4; ... }` with no `p < struct_end` test, `str_len` (`:128-134`) counts until it
finds a zero byte with no ceiling, and a property's length advances `p` by `8 + align(len)` without
checking that the value stayed inside the block.

On QEMU's tree and on any tree a real firmware writes, none of this matters. This crate exists
because the loader must not assume the machine behaves like QEMU, and it is now read by both the
loader and the kernel - so it is the one place where fixing it fixes it everywhere.

- [x] **Compute `struct_start`, `struct_end`, `strings_start` and `strings_end` once, checked, in
  `is_valid`,** and carry them on the `Fdt`. Then every token read, every property value, every
  `nameoff` and every string terminator is a comparison against a field the struct already holds.

- [x] **Bound `str_len` by the block it is reading in,** and make it answer `None` at the edge rather
  than returning a length that walks past it. Its two callers - node names and property strings - are
  in different blocks, so the bound is a parameter.

- [x] **A property test over malformed trees:** a header whose `size_dt_struct` runs past `totalsize`,
  a `FDT_PROP` whose length reaches beyond the block, a node name with no terminator, a `nameoff`
  outside the strings block. Each must be refused rather than read. The crate already has a `Builder`
  that can write them.

### `uefi::acpi` validates the RSDP's first twenty bytes and nothing else

`Acpi::is_valid` (`src/uefi/src/acpi.rs:71-79`) checks the `RSD PTR ` signature and the ACPI 1.0
twenty-byte checksum. That is the right first step and it is where the validation stops:

- an RSDP of revision 2 or later carries `Length` and an extended checksum over the whole structure,
  and neither is read - so the XSDT pointer, which only exists in that part, is taken from bytes
  nothing has summed;
- the root table's own signature is not confirmed to be `XSDT` or `RSDT`;
- neither the root table's checksum nor the SPCR's is computed, though every system description table
  carries one over its whole declared length.

The console address this walks to is now the only thing printed after `ExitBootServices`, and the code
writes to it. A table that passes a signature check and fails its checksum is precisely the "firmware
that is not QEMU" case this milestone exists for.

- [x] **Validate every table this parser walks through:** the RSDP's extended checksum when its
  revision is 2 or greater, the root table's signature and checksum, and the SPCR's. A single
  `table_is_valid(address)` helper answers all three, since the rule is the same one.

- [x] **Tests for each refusal,** in the harness that already publishes fake-physical tables: a good
  RSDP with a bad extended checksum, a root table whose signature is neither `XSDT` nor `RSDT`, an
  SPCR whose checksum is off by one. Each must produce no console rather than a wrong one.

### Three arithmetic residues, in descending order of reach

- [x] **`uefi::memory` does unchecked arithmetic on firmware-provided numbers**: `map_size += desc_size
  * 8` (`src/uefi/src/memory.rs:52`), `d.page_count * PAGE_SIZE` (`:83`) and `last.length +=
  cur.length` in the coalescing pass (`:112`). `memory_top` in the same file already uses
  `checked_mul(..).and_then(checked_add)`, which is the standard the rest of the crate should meet -
  the memory map is the one input here that comes from outside and describes the whole address space.

- [x] **The shared ELF parser checks the physical end and not the virtual one.** `p_paddr.checked_add(
  p_memsz)` is refused (`src/bootproto/src/elf.rs:296`); `p_vaddr.checked_add(p_memsz)` is not, and the
  x86 mapper then walks `virt + i * PAGE_SIZE` unchecked. A `PT_LOAD` whose virtual span wraps is not
  a meaningful segment for any consumer, so the refusal belongs beside its neighbour rather than in
  each backend.

- [x] **`heap.rs:132` multiplies before it checks**: `(addr as usize).checked_add(pages *
  crate::PAGE_SIZE as usize)` - the `checked_add` cannot save a product that already wrapped. One
  `checked_mul` first. Smallest of the three by reach and the easiest to get right.

### And the comment that says the EL2 branch has never run

the mechanism which keeps producing it is that a comment states a fact about the world, the world

- [x] **Rewrite the comment to say what the EL2 run established** - the drop works, fifteen lines of

## Fifth audit (2026-08-15)

An outside review of the loader, the shared FDT reader and the AArch64 boot paths after the fourth
audit's fixes. It confirms the ELF, ACPI, UEFI-memory and heap repairs as properly closed, and
raises seven points. All seven hold.

Three of them are the same shape and the shape is worth naming: A FIX THAT WAS APPLIED WHERE IT WAS
FOUND AND NOT WHERE ELSE IT APPLIED.

- [x] **A hole in the memory map was reported as memory.**

  DONE 2026-08-15, and this is the most serious of the seven. `ram_base` was the first bank's base
  and `ram_size` was the SUM of every bank's size, so a board with two 256 MiB banks either side of
  a gap produced base 0x4000_0000 and size 512 MiB: a range whose second half is the hole, and whose
  end stops short of the second bank's real end. Both kernels build their usable frame region from
  exactly `ram_base + ram_size`.

  What makes it worse than a lost-memory bug is that the failure is UNATTRIBUTABLE where it bites. A
  store into a hole goes nowhere, with no fault, in whatever subsystem happened to be handed that
  frame - so the symptom is corruption somewhere else entirely, at a time unrelated to the boot that
  caused it.

  Banks are now accumulated only while they are contiguous with the run so far, in either direction
  because a device tree does not promise address order, and a gap ends the run. What is reported is
  a range that genuinely is memory.

  THE COST IS STATED RATHER THAN HIDDEN: RAM past the first hole is not used. That is a limitation;
  handing out a hole is a defect. The task below carries the fix that keeps both.

- [x] **`PSCI_NONE` at EL2 threw away the SMC conduit it had just discovered.**

  DONE 2026-08-15. The fourth audit taught the loader to read `/psci/method` and the FADT, and then
  the first line of the function discarded the answer whenever the loader was at EL2 - reasoning
  that "whatever answered before is above the kernel now".

  That is true of an HVC service and false of an SMC one. `hvc` traps to EL2, which is the level
  this loader leaves behind, so after the `eret` nothing answers. `smc` traps to EL3, which is below
  both and entirely unaffected by where the firmware happened to be: a secure monitor implementing
  PSCI goes on implementing it.

  Most server-class AArch64 is exactly that shape - a hypervisor's EL2 and PSCI in EL3 behind `smc` -
  so the discarding branch threw away the right answer on precisely the machines the discovery was
  added for. The exception level now invalidates HVC and only HVC.

- [x] **And the direct-DTB boot path never asked the platform at all.**

  DONE 2026-08-15. `conduit(arg)` answered `PSCI_HVC` when `arg` was not a `BootInfo` - which is
  every boot where firmware hands the kernel a raw device tree in `x0`. So one machine, with
  `method = "smc"` in its own tree, got SMC through the UEFI path and executed `hvc #0` through the
  direct one.

  It now reads the tree through `Fdt::psci_conduit` - the same function the loader calls, so the two
  boot paths cannot answer differently about one platform - and a tree that states nothing gets
  `PSCI_NONE`, which boots single-core with a reason rather than faulting on the first secondary.
  `arg == 0` answers `PSCI_NONE` for the same reason: no tree, no statement, no guess.

- [x] **Four property readers could read past their own property.**

  DONE 2026-08-15. `prop_in` proves a property's declared value lies inside the structure block. It
  does not prove the value is as long as a particular reader assumes, and four readers assumed:

  `#address-cells` and `#size-cells` were read with `be32` whatever their length, so a one-byte
  property took three bytes of what followed. It stays inside the blob, so no bounds check fires;
  what it corrupts is the CELL COUNT, which then decides how every `reg` in the tree is parsed.
  `linux,initrd-start` / `-end` took a four-byte read for any length that was not eight - including
  zero, one, two and three.
  And `compatible` walked its stringlist with the UNBOUNDED `str_len`, which runs until it finds a
  NUL: a list whose last entry has no terminator read past the end of its property and kept going.
  The bounded reader had been written for this class in the previous round and this was the one call
  site still on the old one, which is now deleted so there is no second way to do it.

- [x] **Carry the real memory regions rather than one range.** DONE 2026-08-15. The fix above is safe and lossy: a
  board with discontiguous RAM loses everything past its first hole. It turned out to be a smaller
  change than the task assumed: `frame::init` has always taken a `&[MemRegion]`, so no allocator
  needed changing at all - the boot path was the side collapsing the list. `BootInfo` carries
  `ram_regions` / `ram_region_count` beside the contiguous run, and both device-tree ports call a new
  `bootmem::carve_banks`. That is not a loop around `carve`: `carve` clamps its hole list to the
  range it is given, IN PLACE, so a second call would see reservations already trimmed to the first
  bank - each bank gets its own copy, which also makes the answer independent of the order the tree
  wrote the banks in. The region array is sized `banks + holes`, because each reservation splits at
  most one bank into one extra region.

- [x] **Bound `#address-cells` and `#size-cells` by what the reader can represent.** DONE 2026-08-15 - `MAX_CELLS = 2`, refused at the declaration, because `read_cells` folds into a `u64` and reading more shifts the high cells out and keeps the low bits. `read_cells`
  folds cells into a `u64`, so a tree declaring five or more address cells describes addresses this
  reader cannot hold - and it currently reads them and silently keeps the low bits. Refusing at the
  declaration is a one-line rule and says which trees this reader is for.

- [x] **Two failure paths that leak rather than mislead.** DONE 2026-08-15 - `translate_map` refuses `desc_size == 0` itself rather than through a fact about its only caller, and the loader's two overflow branches free the firmware pages before returning null, the way the `MAX_ARENAS` refusal three lines below them already did. `translate_map` divides by `desc_size`
  without checking it is non-zero - safe today because the only caller validates it, and a shared
  helper should hold its own invariant. And the loader's page allocator, on the overflow path added
  in the previous round, returns null after `alloc_pages` has already succeeded, so those firmware
  pages are not returned. Neither is reachable on a real machine; both are the kind of thing that
  stops being true when a second caller appears.

## Reopened by the sixth audit: four sets of physical addresses, still treated as one

An outside audit of `src/loader`, `src/fdt` and `src/uefi` against this tree, 2026-08-15. It confirms
the PSCI work is genuinely closed on both boot paths - conduit read from `/psci/method` or the FADT,
`CurrentEL` cancelling only HVC, real `smc #0` and `hvc #0` in `cpu_on` - and that the RAM-as-a-list
fix removed the hole-as-RAM defect it was written for. Every finding below was checked against the
source before being recorded.

Its framing is the one to keep, because it names what this milestone has been circling. There are
FOUR sets of physical addresses and the code currently conflates them:

    which regions are RAM
    which regions are RESERVED
    which regions are actually MAPPED
    which regions the allocator may hand out

- [x] **The UEFI boot path on aarch64 and riscv64 passes NO memory map, and the kernel falls back to
  the device tree's `/memory`.** Both backends construct `BootInfo { .. memmap: 0, memmap_len: 0, .. }`
  (`loader/src/arch/aarch64/mod.rs:252`, `loader/src/arch/riscv64/mod.rs:163`) - and the UEFI path is
  what the runner uses for both architectures. The Devicetree Specification is explicit that under
  UEFI the system memory map comes from `GetMemoryMap()` and `/memory` is to be ignored, and the
  reason is not formal: the EFI map carries runtime services code and data, ACPI NVS and reclaimable
  regions, unusable memory, firmware reservations, loader allocations and MMIO apertures, none of
  which a `/memory` node expresses. So the kernel can mark as usable, zero, and hand to a page table
  or a userspace process memory the firmware still owns.

  `uefi::memory::translate_map` already exists and x86_64 already does this. The two device-tree
  backends should translate the final map before `ExitBootServices`, retain it, pass it through
  `BootInfo.memmap`, and seed the frame allocator from it - leaving the DTB for CPU and device
  topology, which is what it is for.

- [x] **The FDT memory reservation block and `/reserved-memory` are not read at all, and neither is
  the DTB's own extent.** There is no `off_mem_rsvmap` handling anywhere in `src/fdt`, and no
  `/reserved-memory` parsing; `bootmem::loader_reservations` carves out `BootInfo`, the module
  descriptor array and the modules, and nothing else. The specification requires a client not to use
  the reservation block's regions and not to overwrite the DTB while it is still in use - and this
  kernel keeps using the DTB after the allocator is up: riscv64 reads `timebase-frequency` from it
  well after `frame` init. So the pages holding the device tree, firmware runtime data, and anything
  a board reserves can be allocated and zeroed while still live. Add `for_each_reserved_region` and a
  `dtb_extent` to the parser, and carve out the reservation block, static `/reserved-memory` ranges,
  the DTB itself and the raw-DTB initrd alongside what is carved today.

- [x] **RAM banks are seeded into the allocator without being clipped to what the boot stub actually
  mapped.** aarch64's stub maps 1 GB blocks over a fixed 0..4 GiB (`aarch64/boot.rs:47`) and
  riscv64's maps a fixed 0..8 GiB (`riscv64/boot.rs:55-63`), while the allocator is seeded from every
  bank the device tree reports. `run.sh --arch aarch64 --mem 4G` puts QEMU `virt` RAM at 1 GiB
  running to ~5 GiB, so the top gigabyte is outside the direct map and the first
  `write_bytes(phys_to_virt(frame), ..)` on a frame from it is a translation fault. This is the same
  defect as the `DIRECT_MAP_LIMIT` item in P02M0133 seen from the allocator's side rather than the
  firmware-pointer side, and the two should be fixed together. Long term the direct map is built from
  the banks; short term every bank is intersected with the mapped range and the remainder is reported
  rather than dropped in silence. Nothing may enter the allocator before `phys_to_virt` on it is
  guaranteed to translate.

- [x] **`#address-cells` / `#size-cells` of zero make the memory-tuple loop spin forever.**
  `fdt/src/lib.rs:500` and `:506` refuse `cells > MAX_CELLS` and accept zero. The loop at `:535` is
  `while q + 4 * (addr_cells + size_cells) <= end`: at width zero the condition never becomes false,
  `read_cells(&mut q, 0)` does not advance the cursor, `s == 0` hits the `continue` at `:538-540`,
  and the loader hangs at boot on a malformed or hostile device tree - before there is any way to say
  so. Require `1..=MAX_CELLS` for a `/memory/reg` read specifically (`#size-cells = 0` is legitimate
  on other node types, so the rule is contextual), and refuse a zero-width tuple in the general
  reader before the loop rather than inside it.

- [x] **A memory node is recognised by name PREFIX, so `memory-controller@...` can contribute MMIO to
  the RAM list.** `fdt/src/lib.rs:449` is `d1_memory = self.str_starts(name, "memory")`, which
  matches `memory-controller@`, `memory-window@` and anything else beginning with those six letters -
  and if such a node has a `reg`, its range is added as RAM. The specification's actual rule is a
  unit name of exactly `memory` or `memory@...` AND `device_type = "memory"`, and `device_type` is
  not read anywhere in this parser. Match on the unit name properly, require `device_type`, and
  honour `status` - a node marked `disabled` or `fail` is not memory this kernel may use.

- [x] **The RAM bank list has no normalisation invariants.** `fdt/src/lib.rs:544-551` coalesces a
  bank only with the one immediately before it, does not sort, does not merge overlaps, computes
  `ram_regions[last].0 + ram_regions[last].1` and `+= s` unchecked, and silently drops everything past
  `MAX_RAM_REGIONS = 16`. `carve_banks` then uses `base.saturating_add(len)`, so a bank declaring
  `size = u64::MAX` saturates into a usable range covering nearly the whole address space. The frame
  allocator's overlap refusal stops that becoming a double allocation today, and it does so by
  discarding legitimate memory. Validate each bank with `checked_add`, drop empty ones, sort by base,
  merge touching AND overlapping, and make exceeding the capacity an explicit refusal or a reported
  truncation rather than a silent one.

- [x] **The bounded cell reader is not used everywhere, and a malformed subtree can leave a good
  value behind.** `pcie_ecam`, `plic_base` and `fwcfg_base` call `read_cells` without first requiring
  `len >= addr_cells * 4`, so a short `reg` reads padding or the next token as an address. The
  nested-bus path does not share the `MAX_CELLS` limit either - the console path accepts up to four
  cells, which `read_cells` folds into a `u64` by dropping the high ones - and that address is used
  for real MMIO writes after `ExitBootServices`. Give every one of them a single
  `read_cells_property(value, len, cells) -> Option<u64>` that checks `1..=2`, the checked byte
  width, the property length and the cursor advance. And stop discarding the walk's failure: a
  console or PSCI value found before a malformed subtree currently survives a tree that should have
  been refused.

- [x] **Finish the descriptor-stride validation in `uefi::memory`, and re-check it after the SECOND
  `GetMemoryMap`.** `translate_map` refuses `desc_size == 0` now, which was the finding. Still
  missing: `desc_size >= size_of::<MemoryDescriptor>()`, `map_size % desc_size == 0`, and an overflow
  check on `phys_start + page_count * PAGE_SIZE`. The sizing call validates the descriptor size and
  the second call can report a different one, after which nothing looks again. Ordinary firmware is
  fine; the helper's comments claim more independence than it has.

- [x] **Accept device trees that are backward compatible with version 17 rather than exactly 17.**
  `fdt/src/lib.rs:153` is `version != 17`. The format carries `last_comp_version` precisely so a
  client can accept a newer tree that remains compatible, and refusing one is a boot failure with a
  confusing cause. Not a blocker on any machine this runs on today - which is why it is worth fixing
  before it is one.

### Resolution of the sixth audit's nine findings (2026-08-16)

**The UEFI boot path hands over the firmware's memory map on both device-tree architectures.** The
loaders allocate a region array, translate the FINAL `GetMemoryMap` - the one whose key
`ExitBootServices` consumes, with no allocation between them, exactly as x86_64 does - and write the
count into the BootInfo afterwards, which is a store to plain memory and needs no firmware service.
`bootmem::handed_memmap` is the kernel side, and the two boots prefer it over the device tree when
it is there. Under UEFI the DTB's `/memory` is not the system memory map: the EFI map carries
runtime services code and data, ACPI NVS and reclaimable regions, unusable memory, firmware
reservations, loader allocations and MMIO apertures, none of which a `/memory` node expresses - so
the kernel could mark as usable, zero, and hand to a page table or a userspace process memory the
firmware still owns. A QEMU `-kernel` boot has no loader and still uses the tree, which is the best
source there is when there is no firmware at all.

**The reservation block, `/reserved-memory` and the blob itself are carved out.**
`Fdt::for_each_reserved_region` walks `off_mem_rsvmap` (bounded by the blob's own size and by a
64-entry cap, because the terminator comes off the same untrusted bytes as everything else) and
`Fdt::extent` answers where the tree is. `bootmem::devicetree_reservations` carves both alongside
what the loader reserved. Nothing read any of it, and this kernel keeps using the tree after the
allocator is up - riscv64 reads `timebase-frequency` from it well after `frame` init - so the pages
holding it could be allocated and zeroed while still live.

**Banks are clipped to what the boot stub mapped.** `carve_banks` takes a ceiling; aarch64 passes
4 GiB and riscv64 8 GiB, which is what their stubs map. `run.sh --arch aarch64 --mem 4G` puts QEMU
`virt` RAM at 1 GiB running to ~5 GiB, so the top gigabyte was outside the direct map and the first
`write_bytes(phys_to_virt(frame), ..)` on a frame from it was a translation fault - the same defect
as P02M0133's `DIRECT_MAP_LIMIT` work seen from the allocator's side. The remainder is REPORTED
rather than dropped in silence: losing memory is recoverable by whoever reads the boot log, and it
is the only way anyone learns the mapping wants widening.

**A zero-width memory tuple is refused.** `while q + 4 * (addr + size) <= end` never becomes false at
width zero, `read_cells(.., 0)` does not advance the cursor, `s == 0` takes the `continue`, and the
loader HUNG at boot - before there is any way to say so. Checked where a `/memory/reg` is read
rather than where the root cells are, because `#size-cells = 0` is legitimate on other node types
and every fixture in this crate uses it on `cpus`.

**A memory node is named, typed and enabled.** `str_starts(name, "memory")` matched
`memory-controller@` and `memory-window@`, so such a node's MMIO aperture entered the RAM list. The
rule is now the unit name exactly `memory` or `memory@...`, `device_type = "memory"`, and a `status`
that is not `disabled` or `fail`. Because either property may appear after `reg`, the node's `reg`
is remembered and the banks are committed at the node's end.

CHECKED AGAINST A REAL TREE FIRST. QEMU's `virt` writes `device_type = "memory"` on its
`memory@40000000`, dumped and read before the rule was imposed; every fixture in this crate omitted
it and had to gain it, which is the same lesson the UDF and exFAT fixtures learned in the same
round.

**The bank list has invariants.** Sorted by base with an insertion sort, then merged where banks
touch OR overlap, with `checked_add` throughout - the end of a bank is exactly where the old
arithmetic overflowed, and `carve_banks` then used `saturating_add`, so a bank declaring
`size = u64::MAX` saturated into a usable range covering nearly everything. Exceeding
`MAX_RAM_REGIONS` is an explicit refusal rather than a silent drop: a board with a fragmented map
used to boot with less memory than it has and nothing said which part was missing.

**One bounded cell reader.** `read_cells_property(value, len, cells)` checks the width against
`MAX_CELLS`, the byte width against the property's declared length, and answers `Option` - so
`pcie_ecam`, `plic_base` and `fwcfg_base` leave their previous value rather than adopting the
padding after a short `reg`, which is an address used for real MMIO writes after
`ExitBootServices`.

**The descriptor stride is fully validated, and again after the second call.** `desc_size >=
size_of::<MemoryDescriptor>()`, `map_size % desc_size == 0`, and `phys_start + length` checked for
overflow. The SIZING call's answer was validated and the second call's - the one that describes the
buffer now in hand - was not looked at again; firmware reporting one stride for the sizing and
another for the fill would have had every descriptor after the first read at the wrong offset.

**A device tree backward compatible with version 17 is accepted.** `version < 17 ||
last_comp_version > 17` rather than `version != 17`. The format carries `last_comp_version`
precisely so a client can accept a newer tree that remains compatible; QEMU's `virt` writes version
17 with `last_comp_version` 16.

Verification: `fdt` 23/23, `uefi` 31/31, and the aarch64 and riscv64 kernels and loaders build.

### LDR-001, -002 and -005 closed (2026-08-18)

**LDR-001** built every table entry with `NX` - bit 63, which is RESERVED and faults on use until
`EFER.NXE` is set - and with a depth nothing confirmed. Firmware usually sets NXE, and "usually" is
the whole problem: on firmware that does not, the loader produces tables that fault the moment CR3 is
switched, past the point where anything can report it. `PageTables::new` now sets it, which costs one
MSR write and removes the assumption. The depth is the other half: these are four-level tables, and
with `CR4.LA57` set the CPU walks five, so the PML4 would be read as a PML5 and every translation
would come from the wrong level. That is refused rather than built.

**LDR-002**: `memory_top` answers 0 for every snapshot failure and x86 rounded that value and carried
on, so a failed map produced an HHDM and identity map over an EMPTY interval - the loader handing the
kernel a direct map covering nothing and continuing. A machine with no RAM does not exist, so zero can
only mean the map could not be taken; it is a refusal now, which is the shape this project has settled
on twice elsewhere.

**LDR-005** formed a slice with `from_raw_parts` from the firmware's configuration-table pointer.
That requires a non-null aligned pointer EVEN FOR LENGTH ZERO, and firmware with no configuration
tables may publish null with a count of zero - so the ordinary case was undefined behaviour that
happened to work. Both sites (the shared `discover` and x86's `find_rsdp`) check first; there is
nothing to search either way.

Measured: x86_64 `boot,smoke,paging,memory` 75/75.


### LDR-013, -014, -015 and -022 (2026-08-18)

**LDR-013**: the application-processor trampoline starts in 16-bit real mode and loads CR3 with a
32-BIT register, so a page table above 4 GB is an address it cannot express - and `ALLOCATE_ANY_PAGES`
let firmware put the PML4 anywhere. On a machine with plenty of high memory the APs would fail to
come up, or come up on a truncated CR3 depending on the low bits. Every level is capped at 4 GB
rather than only the root: the constraint costs nothing and this way there is no question about which
levels it applies to.

**LDR-015's enforceable half is closed.** With `CR0.WP` clear a supervisor write IGNORES the
read-only bit, so every read-only kernel mapping is writable from ring 0 and the loader's W^X segment
checks decide nothing at all. UEFI specifies only some CR0 bits and promises nothing about this one,
so firmware leaving it clear was a state this kernel inherited and carried. `enable_fpu` sets it, on
the BSP and on every AP, because a property that matters is established rather than hoped for. The
ALIAS half - the HHDM covering kernel text writable, and the early identity map exposing RAM as
writable and executable - is a mapping-policy change and is not done.

**LDR-014 is written into the threat model rather than fixed**, which is what the audit asks for: it
calls the gap "consciously accepted", and the danger is a reader assuming UEFI Secure Boot covers the
boot chain. It does not - it verifies the LOADER BINARY and stops. `docs/THREAT_MODEL.md` now says so
explicitly, names what is unverified (kernel, bootstrap list, modules, the volume they come from) and
what closing it would take.

**LDR-022 is written and NOT COMPILED for the architectures it exists for.** `alloc_pages` gained a
ceiling and `efi_main` sets it under `cfg(aarch64)` (4 GB) and `cfg(riscv64)` (8 GB), matching the
fixed early direct map each kernel's boot stub installs. x86 sets none and keeps the old behaviour,
because it builds its own direct map over all RAM first. Only x86_64 has been built, so the two
`cfg` arms have not been through a compiler - the non-x86 builds are deferred to the end of the batch
by request, and this item is not closable until they run.

Measured (x86_64 only): `boot,smoke,smp,paging` 17/17 and
`boot,smoke,smp,paging,memory,process` 156/156.


### LDR-012 partially closed, and one half deliberately left (2026-08-18)

`read_file` allocates fresh LOADER_DATA pages and returns an UNOWNED static slice, so every caller
that copies the bytes out left the whole page allocation behind - and loader data becomes
`MEM_BOOTLOADER`, which the kernel never seeds as usable, so each read permanently removed its own
size from the machine's RAM. That is once per bootstrap-list entry.

`uefi::file::free_file` gives them back and `FirmwareVolume::read` calls it, on the failure path as
well as the success one - the `try_reserve` there is what makes the failure path reachable.

THE PAIRING-FILE READ IS LEFT LEAKING, ON PURPOSE, and the reason is written beside it.
`read_boot_file` has two sources - the firmware read, whose pages are freeable, and the FAT fallback,
which owns its own buffer - and the `&'static [u8]` return type does not say which one answered.
Handing the wrong one to `free_pages` is worse than leaking a page. Closing it means expressing the
ownership in the type, which is the same change LDR-012's other sites need and is not a one-line fix.

Also still open under LDR-012: the final raw memory-map buffers (they are wanted after
`ExitBootServices`, when nothing can free them), RISC-V scratch and rejected staging candidates, and
the common reservation pass that x86 runs and ignores.

Measured (x86_64): `boot,smoke,volume-layout,storage,component` 48/48.


### LDR-008: x86 half closed (2026-08-18)

UEFI runs with interrupts ENABLED, and x86's `cli` sat inside the handoff asm - after
`finalize_and_exit` returned, after the `memmap_len` store, after everything in between. In that
window the firmware's handlers no longer exist and the kernel's IDT does not exist yet, so an
interrupt vectors through a table nobody owns. It is masked the instruction after `ExitBootServices`
returns now; nothing in that stretch needs interrupts. The `cli` in the handoff block stays, because
that block must be reachable only with interrupts off and saying so twice is cheaper than depending
on the caller.

NOT DONE, and the reason is the same one this batch keeps running into: aarch64 needs DAIF masked
for the post-exit sequence (its EL2 path only sets the masks that take effect after `eret`, and the
direct EL1 branch never touches DAIF), and riscv64 needs `sstatus.SIE` cleared before its final exit,
copy, paging change and jump. Both are one instruction each and neither has been compiled, because
the non-x86 builds are deferred to the end of the batch by request. Writing them without building
them would be the same mistake LDR-022 already records.

Measured (x86_64): `boot,smoke,smp` 16/16.
