# P02M0144 - The build says nothing it cannot back up

Status: OPEN. HYGIENE. NOT A PHASE-2 COMPLETION GATE.

## Goal

Every one of the three builds compiles without a warning, and it does so BECAUSE THE CODE IS TRUE -
not because a lint was switched off. Both halves are the point. Silencing is what got the tree here,
and a milestone that ends with a quiet build and a hundred `allow` attributes has made the problem
harder to see rather than smaller.

## What is there now

Measured 2026-08-22 on the pinned `nightly-2026-06-16`, by building each target and reading what
cargo printed. The hidden half was measured with `cargo rustc -- --force-warn dead_code --force-warn
unused`, which overrides an `allow` attribute rather than obeying it - the same command reproduces
every number below.

**THE BUILD PRINTS WARNINGS ON EVERY TARGET.**

|  | x86_64 | aarch64 | riscv64 |
| --- | --- | --- | --- |
| kernel | 20 | 66 | 29 |
| loader | 11 | 3 | 6 |
| services | 14 | 14 | 14 |
| storage | 7 | 7 | 7 |
| fat, mkpackages | 2 | 2 | 2 |
| **printed** | **54** | **92** | **58** |

**AND THAT IS THE SMALL NUMBER.** Ninety-one attributes in `src/` switch `dead_code` or `unused` off
before anything reaches the terminal - fifty-five of them `#![allow(dead_code)]` at the top of a
whole file. Override them and the KERNEL ALONE reports:

|  | x86_64 | aarch64 | riscv64 |
| --- | --- | --- | --- |
| kernel prints | 20 | 66 | 29 |
| kernel actually has | 140 | 127 | 138 |

**THE THREE TARGETS DO NOT DIFFER IN DEAD CODE. THEY DIFFER IN WHERE THE SILENCERS SIT.** That is
the finding this milestone exists for, and the two tables above are the proof: printed, aarch64
looks three times worse than x86_64; measured, the three are within ten percent of each other.
Eleven files under `arch/x86_64` carry a file-wide `#![allow(dead_code)]` - `usermode.rs`,
`paging.rs`, `apic/mod.rs`, `ioapic.rs`, `percpu.rs`, `syscall.rs`, `tsc.rs`, `random.rs`,
`context.rs`, `interrupts/mod.rs`, `pci/mod.rs`. `arch/riscv64/usermode.rs` carries one.
aarch64's `usermode` is written inline inside `arch/aarch64/mod.rs` and therefore carries none - so
the SAME ring-3 probe programs, doing the same job for the same tests, are reported on one target
and silent on the other two.

Nobody decided that. It is where the files happened to be split.

**THE CENSUS**, so the size is not a surprise halfway through:

| where | attributes | of which file-wide |
| --- | ---: | ---: |
| `src/kernel` | 58 | 45 |
| `src/user` | 24 | 7 |
| `src/uefi`, `src/loader`, `src/fs` | 6 | 1 |
| `src/tools`, `src/bootproto`, `src/abi` | 3 | 2 |
| **total** | **91** | **55** |

**WHAT THE WARNINGS ARE NOT: CODE IN THE SHIPPED IMAGE.** An earlier reading of this claimed the
test probe programs and the A64 instruction encoder are compiled into the image that boots. They are
not. `nm` on the linked aarch64 kernel finds zero symbols for `PROGRAM_BASIC`, `program_*_bytes` and
the encoders, while live code in the same modules - `usermode::enter`, `bootmem::carve` - is present,
out of 22 233 symbols. The linker drops them.

So the cost is not bytes. The cost is that fifty-four to ninety-two lines of noise per build is
exactly where the next warning that MEANS something goes to hide - and the tree has already paid
that once, in a `check.sh` gate whose own comment says a wrong `extern` signature "compiled without
a warning".

**AND NOTHING WOULD NOTICE.** None of the twenty-six gates in `check.sh` reads compiler output, and
nothing anywhere refuses a new `allow`.

**TWO SILENCERS ARE ON THE WRONG FUNCTION.** In `extable/mod.rs` a `#[cfg_attr(not(test),
allow(dead_code))]` sits above a doc comment that belongs to the NEXT item, so it lands on
`refused()` while the function it was written for, `caught()`, is one of the two that warn. The same
slip repeats eight lines down: the attribute meant for `declared()` lands on `first_entry()`, which
is `#[cfg(test)]` already and needed nothing. Two attributes, both misapplied, both invisible -
which is the whole argument against the mechanism in six lines of one file.

## Scope

IN: every warning the three builds print; every `allow(dead_code)` and `allow(unused*)` attribute
under `src/`; the lints that are not about dead code (`function_casts_as_integer`, unnecessary
`unsafe`, unnecessary parentheses, unused `mut`, unused imports); the cargo profile note the kernel
prints; and a gate that keeps the result.

OUT, deliberately:

- **Clippy.** Not run today. Turning it on is a separate decision with its own argument, and
  bundling it here would make a hygiene milestone into a style one.
- **Other lint families** - `unsafe_op_in_unsafe_fn`, `missing_docs`, the pedantic groups. This
  milestone closes what the compiler already says by default and adds no new opinions.
- **The `todo!()` HAL bodies.** P02M0142 M2 owns those and says why they cannot simply be deleted.
  See the coordination note at the end.
- **Behaviour.** An item deleted here is one nothing calls. If reading a dead method suggests a
  behaviour that is MISSING, that is a note for a milestone, not work in this one.

## Work

- [x] **M1 - The silencers come out first, and the build gets loud for one commit.**
  - Remove all ninety-one `allow(dead_code)` / `allow(unused*)` attributes under `src/`, including
    the `cfg_attr` spellings. `#[cfg_attr(not(feature = "development"), allow(unused_variables))]`
    is a silencer wearing a cfg's clothes; the parameter gets an underscore or the item gets a real
    cfg.
  - IT LANDS FIRST AND ON ITS OWN, warnings and all. Doing it at the end would mean M2 to M6 spent
    their time on the fifty-four visible items while a hundred and twenty more sat under the floor,
    and the milestone would close with the tree still lying about itself. A commit that prints four
    hundred warnings is fine as long as the next one can see them.
  - The two misplaced attributes in `extable/mod.rs` go with the rest. There is nothing to fix about
    a misplacement once the attribute is gone.
  - DONE. Ninety-one attributes removed from seventy-six files, including the two misplaced ones in
    `extable/mod.rs` and the `cfg_attr` spellings. On x86_64 the build went from 54 printed warnings
    to 238 - the kernel alone from 20 to 140, matching the `--force-warn` measurement exactly, which
    is what says the measurement method was sound. aarch64 and riscv64 are not re-measured yet;
    their kernels held 127 and 138.

- [~] **M2 - Code that only tests reach says so, on every target.**
  - The rule, and it admits no exception: an item whose only callers are under `#[cfg(test)]` is
    itself `#[cfg(test)]`.
  - The known members: the ring-3 probe programs and their instruction encoders in
    `arch/x86_64/usermode.rs`, `arch/riscv64/usermode.rs` and the inline `usermode` module in
    `arch/aarch64/mod.rs`; `arch/common/msi.rs::is_pending`; `arch/x86_64/idt::has_error_code`;
    `extable::{caught, declared}`; `paging::writable_executable_block` on the two targets that have
    one. M1 will add the rest, and most of what it adds will be object-API methods.
  - SYMMETRY IS THE DELIVERABLE, not tidiness. The same probe programs must be gated the same way on
    all three targets, so that the next person reading `usermode` on any of them learns the same
    thing about it.
  - An item that tests reach on one target and production code reaches on another gets
    `#[cfg(any(test, target_arch = "..."))]` - one attribute stating both facts, not two files
    disagreeing.

- [~] **M3 - Code that one architecture reaches carries its cfg.**
  - `arch/common/bootmem` in full: its only callers are `arch/aarch64/boot.rs` and
    `arch/riscv64/boot.rs`, and on x86_64 the whole module is eleven warnings.
  - `arch/common/time.rs::TickClock`: aarch64 `gic.rs`, riscv64 `mod.rs`, and `smp/tests.rs` on
    every target - so `any(test, target_arch = "aarch64", target_arch = "riscv64")`.
  - `#![feature(abi_x86_interrupt)]` in `main.rs`, which aarch64 and riscv64 both report as declared
    and unused. `main.rs` already uses `cfg_attr` for the test-framework features, so the shape is
    in the file.
  - In the loader: `ReservedKernel` and `reserve_kernel`, whose only caller is the aarch64 backend
    (x86_64 takes `ReservedKernel::EMPTY`), and the post-EBS console path - `PostEbs`'s
    `reg_shift`/`access_width`, `firmware_tables`, `identity_map`, `write_byte_post_ebs`, `read_reg`,
    `write_reg` - reached only from `arch/aarch64/serial.rs`, `arch/riscv64/serial.rs` and
    `arch/aarch64/mod.rs`.
  - THIS IS NOT A LICENCE TO FORK. Gating a shared module to the targets that use it is not the same
    as copying it, and if resolving an item would need it copied, the item belongs in M4 or stays
    where it is with the reason written down.

- [~] **M4 - Code that nothing reaches is deleted, one item at a time.**
  - Already identified: `console::is_disabled` (superseded by `try_claim`, which the comment above
    it explains); the loader's `ReservedKernel::{overlaps, is_complete}` and its `complete` field
    (`overlaps` was replaced by `destination_overlaps` and the call site documents why; the field is
    written three times and read never - the enforcement is `assert!(reserved.owns(..))`);
    `mkpackages::timing_event`, the build-side half of the `LIBER_TIMING_LOG` protocol that the test
    driver, `qemu-run.sh` and `lab.py` all write to and no build step ever called.
  - `heap::{try_extend, try_vec}` GO, AND THE GATE'S COMMENT IS CORRECTED WITH THEM.
    `tools/check-kernel-allocations.sh` advertises a family of six fallible helpers; `try_arc` has
    twenty-one callers, `try_box` and `try_string` two each, `try_push` one, and these two have none
    in the life of the kernel. A helper nobody has ever needed is not an API - it is two functions
    the next author will write in the shape they actually need. The gate's list drops to four.
  - WHAT M1 UNCOVERS IS READ, NOT SWEPT. The hundred and twenty extra items in the kernel are mostly
    methods on `object/*`. Each is one of three things and the reading says which: only tests call
    it (M2), nothing calls it and nothing should (delete), or nothing calls it and something should
    (a note, not a change). There is no bulk answer and a bulk answer is how a real hole gets swept
    up with the rest.
  - THE BOUND ON THIS ITEM: it adds nothing. If reading a dead method suggests missing behaviour,
    the item records it and moves on.
  - WHAT THE READING FOUND, beyond the list above. `isr_ack` and `read_isr` in the driver transport
    were the same read of the same register under two names, and only one was ever called - the
    duplicate had sat under a file-wide `allow` since it was written. `Queue.handle` carried the
    comment "keeps the ring DMA buffer alive" and kept nothing: no `Drop` closed it, so the buffer
    outlives the queue either way. `uefi::memory` assigned a field to itself. `unmap_pages` was in
    the HAL contract on all three backends and called by none of them. `msix_count` was resolved
    for every PCI device and read by nothing. `RecvRefusal::TooLarge` and `TooManyCaps` measured
    the size the caller would need and handed it to `sys_channel_recv`, which matches both with
    `_` and answers `ERR_INVALID`.

- [x] **M5 - Vocabulary with no producer, which is three different problems wearing one warning.**
  - `RoleKind::Power` IN THE EXECUTOR IS UNREACHABLE, and P02M0141 is why: it converted the last
    `kind = "power"` row (DeviceManager's `POWER`) to a `client` named `SYSPOWER`, and
    `system-manifest` now refuses any power role at all - `MAY_HOLD_ROOT_DOMAIN` is `[&str; 0]`. So
    `build.rs` can never emit that arm. The variant goes from `service_manager.rs`, and `build.rs`'s
    mapping arm becomes a build failure that names the reason. The variant in `system-manifest`
    STAYS: there it is the tripwire that does the refusing.
  - `Lifecycle::{Function, Interface}` and `Priority::{Exact, Quirk}` in DeviceManager are schema
    values no driver row uses today. Same treatment ONLY IF the executor has no behaviour for them -
    which is the thing to establish first. A variant the code handles and the manifest has not yet
    needed is different from one the code cannot handle.
  - `Reason::{BootstrapRefused, Unresponsive, BudgetSpent}` ARE NOT DEAD VOCABULARY, AND THIS IS THE
    ONE ITEM HERE THAT IS A DEFECT. ServiceManager has a watchdog and a restart budget and reaches
    both states. It just does not say so: when the budget runs out at `service_manager.rs:1168` the
    last recorded reason stays `Replaced`. `last_reason` goes out over the supervisor stat contract,
    and today it can never say "restart budget spent" or "unresponsive" - the two things an operator
    looking at a service that keeps dying would look for first. The fix is the missing write.
  - `Transition.{from, to, epoch}` and `LifecycleLog.boot` are written and never read. Decide by
    reading what `SupervisorStat` already carries: either the record reports them or it stops
    keeping them. Keeping a field for a reader that does not exist is the same defect as the
    variant above, seen from the other end.

- [ ] **M5b - A BADGE IS STAMPED, STORED AND NEVER READ BACK.** Found by M1, and it is not a warning
  to resolve - it is a mechanism with no delivery.
  - `sys_channel_send` takes one look at the handle table for the authority AND the badge (a fix
    with its own comment about a sibling thread closing the handle in between), stamps the badge
    onto the `Message`, and the message carries it to the receiver. Nothing reads `Message.badge`
    except `object/channel/tests.rs`. `HandleInfo.badge` is the same story on the other side: the
    field is filled from the capability and `sys_handle_info` does not return it.
  - So a server cannot tell one client's endpoint from another's by the badge, which is what badges
    are for, and the kernel does all the work to carry one.
  - BOTH RESOLUTIONS ARE OUT OF THIS MILESTONE'S BOUND. Deleting the chain removes a deliberate
    capability mechanism; delivering the badge to the receiver is a feature with an ABI change. The
    warning stays until that is decided, and this item is where the decision is recorded.

- [ ] **M6 - The warnings that are not about dead code.**
  - `function_casts_as_integer`, three sites, all riscv64: `arch/riscv64/boot.rs:182`,
    `arch/riscv64/traps/mod.rs:261` and the loader's `arch/riscv64/mod.rs:360`. None is wrong today -
    one of the values is written into `stvec`, so if it were wrong riscv64 would not boot - and the
    fix is the `as *const ()` the lint asks for.
  - The small ones the other two targets report: an unnecessary `unsafe` block, unnecessary
    parentheses around a `let` scrutinee, an unused `mut`, unused imports.
  - THE CARGO PROFILE NOTE IS RESOLVED BY TESTING ITS OWN CLAIM. `src/kernel/Cargo.toml` overrides
    `[profile.dev.package.compiler_builtins]` and its comment says the override is load-bearing -
    that without it the `compiler-builtins-mem` intrinsics abort the kernel on an unaligned u128 -
    while cargo answers that the spec matched no package. One of those is wrong. Remove the stanza,
    run the x86_64 suite, and see whether the invalid-opcode abort comes back. If it does, find the
    spelling cargo accepts and the note goes away with it; if it does not, the stanza goes and the
    comment with it. What is not acceptable is a line printed on every build that nobody can act on.

- [ ] **M7 - A gate, so it stays quiet.**
  - Two rules, because one without the other is how this milestone becomes necessary again:
    warnings fail the build on all three targets, and a new `allow(dead_code)` / `allow(unused*)`
    under `src/` fails the gate.
  - It lands LAST, and only once the three builds are clean - a gate introduced earlier is a gate
    that fails on the day it is written, which is how gates get disabled.
  - It is demonstrated by breaking it: introduce one warning, watch it fail, remove it. A green gate
    nobody has seen fail is not evidence.

## Work already in the working tree

A mechanical pass ran before this file existed - which is the wrong order, and is why the pass is
recorded here rather than left to be rediscovered. It is uncommitted, it touches twelve files, and
`./build.sh --arch x86_64` passes with it. It took x86_64 from 54 printed warnings to 32.

What it did, by the item it belongs to:

- **M6**: ten redundant `mut` bindings on `ReceivedCaps::Message { len, handles: mut caps }` across
  DisplayService, AudioService, InputService, NetworkService and StorageService - `Handles` is
  `Copy` and each site copies it again on the next line; five `unsafe { exit() }` wrappers and one
  nested `unsafe` in StorageService, where `rt::exit` has been a safe function for some time; one
  nested `unsafe` in the loader's heap; two unused imports.
- **M4**: `console::is_disabled`, the loader's `ReservedKernel::overlaps`, and
  `mkpackages::timing_event`.

And two things it did that this milestone forbids. It put `#[allow(dead_code)]` on
`heap::{try_extend, try_vec}` rather than deciding about them - that attribute has been removed
again, the two functions now warn, and M4 says what happens to them. AND IT DELETED
`ReservedKernel::is_complete` AND THE `complete` FIELD AS UNREAD, on the evidence of an x86_64 build.
`arch/riscv64/mod.rs:65` calls `is_complete()` before it stages the kernel. Both are restored.

THAT IS THE WHOLE ARGUMENT FOR MEASURING ON THREE TARGETS, in one mistake: on x86_64 the loader's
whole reservation is dead, so the warning named every field at once and reading it as "nothing uses
these" was wrong for one of them. Every deletion in M4 is checked against all three builds before it
counts as done.

## Definition of done

- `./build.sh --arch x86_64`, `--arch aarch64` and `--arch riscv64` each print ZERO compiler
  warnings, on a clean build and not only on a cached one.
- `grep -rn "allow(dead_code)\|allow(unused" src/ --include=*.rs` returns nothing.
- The three guest suites still pass at their present counts - 305 / 292 / 291 - and
  `./check.sh --gate all` is green.
- The gate from M7 has been SEEN to fail: once on an introduced warning, once on an introduced
  `allow`.
- Every item was closed by a cfg, a deletion, or a write that was missing. None by a marker, and
  none by moving a file so the lint stops looking.

## What this shares a border with

**P02M0142 M2 - the HAL contract.** The two meet at exactly one place and it is worth naming so
neither reopens the other. M2's subject is the twenty-seven `todo!()` bodies, which have static
callers from portable code and therefore do not warn; its deliverable is the contract comment at the
top of `arch/mod.rs`. What THIS milestone sees is the other half of the same story: `enable_nx`,
`enable_smap_smep`, `smap_enabled`, `smep_enabled` and `clac_on_entry` exist as real no-op bodies on
aarch64 and riscv64 and have no caller there at all, because only `arch/x86_64/mod.rs` calls them.
They are listed in that same contract comment as entries every backend owes.

So M2 fixes the promise and this milestone gates or deletes what the promise never needed. Whichever
lands first, the other reads it - and if it is convenient to correct the contract comment while
doing M3, that is M2's text arriving early rather than a second opinion about it.
