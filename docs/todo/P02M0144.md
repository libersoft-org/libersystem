# P02M0144 - Truthful System Graph and architecture conformance

Status: PLANNED AFTER P02M0143. SYSTEM-ARCHITECTURE FOUNDATION. NOT A PRODUCT, RELEASE OR UPDATE
GATE.

## Goal

Make the existing System Graph a truthful read-only projection of both the declared system and the
system that is actually running. Continuously detect when runtime composition, authority, Domains,
resources or lifecycle drift away from the architecture described in P02M0141-P02M0143.

This milestone extends SystemGraphService and the existing verification infrastructure. It does not
create another registry, event service, management API or certification system.

## Version ownership rule

`v1` remains open until the project owner explicitly says otherwise. Completing this milestone
means that its current acceptance criteria and standing gates pass. It does not freeze an API, ABI,
schema, file format, machine description, product profile or release line. Breaking `v1` changes
remain allowed when all in-tree producers, consumers, generated files and tests migrate together.
Only the project owner may declare `v1` closed or start a successor version.

## Scope

P02M0008 remains the owner of SystemGraphService, tracing, counters and CLI/JSON/CBOR projections.
P02M0104 remains the scenario runner and P02M0118 remains the test-selection and evidence model.
This milestone only gives those systems the common identities, lifecycle and comparison rules
needed to observe architectural truth.

There is no remote observer, tenant redaction, capability-topology browser, new telemetry platform,
release certificate or product support matrix in this milestone.

## Work

- [ ] **M1.1 - Populate desired graph identity from `SystemSpec`.**
  - Generate desired component/deployment nodes and static dependency/binding edges from the
    P02M0141 model.
  - Use the same `ComponentId`, `DeploymentId`/`ServiceId` and development profile identity as the
    build and bootstrap projections.
  - Keep desired state visibly separate from runtime observations.
  - Do not turn SystemGraphService into a source of desired state or control authority.

- [ ] **M1.2 - Feed live lifecycle state into the existing graph.**
  - Attach `BootId`, `InstanceEpoch`, lifecycle state, transition reason, sequence and freshness to
    live deployment nodes.
  - Distinguish current, unknown, stale, down and degraded where the service declares a degraded
    state.
  - On restart, mark the old epoch non-current before presenting the replacement as Ready.
  - Bound retained transition history and subscriber work using the existing observability owners.

- [ ] **M1.3 - Show the runtime relationships needed to verify architecture.**
  - Report the actual supervision/Domain/resource parent and referenced resource profile for each
    managed deployment.
  - Report the current state class/owner reference and config schema identity without exposing
    configuration secrets or payloads.
  - Report whether initial boot holdings stayed within the generated authority maximum; do not
    expose a raw global handle graph.
  - Keep CLI, JSON and CBOR as renderings of the same underlying System Graph model.

- [ ] **M1.4 - Compare generated and observed system state.**
  - Detect an undeclared live deployment, a missing required deployment, wrong Domain/resource
    parent, broader boot authority, stale current epoch or unknown required config/resource profile.
  - Classify expected temporary differences during starting/stopping so ordinary transitions do not
    look like permanent drift.
  - Make unexplained drift visible in the graph and fail the architecture-conformance gate.
  - Keep the comparison read-only; remediation remains with SystemManager, ServiceManager or the
    subsystem owner.

- [ ] **M1.5 - Add focused architecture-conformance scenarios.**
  - Reuse the P02M0143 M1.7 scenario IDs and harness for clean boot, service restart, manager
    failure, resource denial and invalid configuration/state; add graph/conformance assertions to
    those same scenarios rather than creating parallel copies.
  - Add only the architecture-specific cases absent from that matrix: stale/late epoch events and
    an invalid bootstrap role.
  - Check desired-versus-live identity, Domain/resource placement, boot authority maximum and graph
    freshness in the reused and added cases.
  - Execute scenarios through P02M0104 and register coverage and selection through P02M0118.
  - Use the current `SystemSpec` and development-profile digest only to correlate evidence with the
    tested tree, never as a signed release identity.

- [ ] **M1.6 - Make architecture checks part of ordinary development.**
  - Extend the P02M0141/P02M0142 standing gates with lifecycle identity and
    generated-versus-observed conformance; do not duplicate their model-drift or bootstrap-plan
    checks.
  - Ensure changes to the manifest/schema, generators, bootstrap, managers, Domain/resource
    projection or System Graph select the relevant scenarios.
  - Keep the gates bounded enough for normal development and route expensive guest scenarios
    through the existing verification planner.
  - Record failures with the owning component and invariant rather than creating a second audit
    database.
  - Continue updating the checks as `v1` evolves; passing them never freezes the architecture.

## Definition of done

- Desired and live System Graph state use the same component, deployment, boot and instance
  identities.
- Old or stale epochs are visibly different from the current instance.
- The graph reports architecture-relevant Domain/resource, state/config and boot-authority results
  without becoming a control plane or exposing a raw global authority graph.
- Generated-versus-observed drift is detected with transition-aware rules and fails a standing gate
  when unexplained.
- CLI, JSON and CBOR remain projections of one SystemGraphService model.
- Architecture scenarios run through the existing QEMU and verification infrastructure and are
  selected by relevant changes.
- Completing the milestone proves conformance of the current development tree only and leaves `v1`
  open for continued coordinated change.

The implementation records exact commands and results in dated evidence sections. Those records
are development evidence, not a release certificate or declaration that the architecture is
finished.
