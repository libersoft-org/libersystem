# P02M0144 - The build says nothing it cannot back up

Status: COMPLETE (2026-08-25). HYGIENE. NOT A PHASE-2 COMPLETION GATE.

## Goal

Every one of the three builds compiles without a warning, and it does so BECAUSE THE CODE IS TRUE -
not because a lint was switched off. Both halves are the point. Silencing is what got the tree here,
and a milestone that ends with a quiet build and a hundred `allow` attributes has made the problem
harder to see rather than smaller.

## What is there now

Measured 2026-08-22 on the pinned `nightly-2026-06-16`, by building each target and reading what
cargo printed. The hidden half was measured with `cargo rustc -- --force-warn dead_code --force-warn
unused`, which overrides an `allow` attribute rather than obeying it - the same command reproduces
every number below.

**THE BUILD PRINTS WARNINGS ON EVERY TARGET.**

|  | x86_64 | aarch64 | riscv64 |
| --- | --- | --- | --- |
| kernel | 20 | 66 | 29 |
| loader | 11 | 3 | 6 |
| services | 14 | 14 | 14 |
| storage | 7 | 7 | 7 |
| fat, mkpackages | 2 | 2 | 2 |
| **printed** | **54** | **92** | **58** |

**AND THAT IS THE SMALL NUMBER.** Ninety-one attributes in `src/` switch `dead_code` or `unused` off
before anything reaches the terminal - fifty-five of them `#![allow(dead_code)]` at the top of a
whole file. Override them and the KERNEL ALONE reports:

|  | x86_64 | aarch64 | riscv64 |
| --- | --- | --- | --- |
| kernel prints | 20 | 66 | 29 |
| kernel actually has | 140 | 127 | 138 |

**THE THREE TARGETS DO NOT DIFFER IN DEAD CODE. THEY DIFFER IN WHERE THE SILENCERS SIT.** That is
the finding this milestone exists for, and the two tables above are the proof: printed, aarch64
looks three times worse than x86_64; measured, the three are within ten percent of each other.
Eleven files under `arch/x86_64` carry a file-wide `#![allow(dead_code)]` - `usermode.rs`,
`paging.rs`, `apic/mod.rs`, `ioapic.rs`, `percpu.rs`, `syscall.rs`, `tsc.rs`, `random.rs`,
`context.rs`, `interrupts/mod.rs`, `pci/mod.rs`. `arch/riscv64/usermode.rs` carries one.
aarch64's `usermode` is written inline inside `arch/aarch64/mod.rs` and therefore carries none - so
the SAME ring-3 probe programs, doing the same job for the same tests, are reported on one target
and silent on the other two.

Nobody decided that. It is where the files happened to be split.

**THE CENSUS**, so the size is not a surprise halfway through:

| where | attributes | of which file-wide |
| --- | ---: | ---: |
| `src/kernel` | 58 | 45 |
| `src/user` | 24 | 7 |
| `src/uefi`, `src/loader`, `src/fs` | 6 | 1 |
| `src/tools`, `src/bootproto`, `src/abi` | 3 | 2 |
| **total** | **91** | **55** |

**WHAT THE WARNINGS ARE NOT: CODE IN THE SHIPPED IMAGE.** An earlier reading of this claimed the
test probe programs and the A64 instruction encoder are compiled into the image that boots. They are
not. `nm` on the linked aarch64 kernel finds zero symbols for `PROGRAM_BASIC`, `program_*_bytes` and
the encoders, while live code in the same modules - `usermode::enter`, `bootmem::carve` - is present,
out of 22 233 symbols. The linker drops them.

So the cost is not bytes. The cost is that fifty-four to ninety-two lines of noise per build is
exactly where the next warning that MEANS something goes to hide - and the tree has already paid
that once, in a `check.sh` gate whose own comment says a wrong `extern` signature "compiled without
a warning".

**AND NOTHING WOULD NOTICE.** None of the twenty-six gates in `check.sh` reads compiler output, and
nothing anywhere refuses a new `allow`.

**TWO SILENCERS ARE ON THE WRONG FUNCTION.** In `extable/mod.rs` a `#[cfg_attr(not(test),
allow(dead_code))]` sits above a doc comment that belongs to the NEXT item, so it lands on
`refused()` while the function it was written for, `caught()`, is one of the two that warn. The same
slip repeats eight lines down: the attribute meant for `declared()` lands on `first_entry()`, which
is `#[cfg(test)]` already and needed nothing. Two attributes, both misapplied, both invisible -
which is the whole argument against the mechanism in six lines of one file.

## Scope

IN: every warning the three builds print; every `allow(dead_code)` and `allow(unused*)` attribute
under `src/`; the lints that are not about dead code (`function_casts_as_integer`, unnecessary
`unsafe`, unnecessary parentheses, unused `mut`, unused imports); the cargo profile note the kernel
prints; and a gate that keeps the result.

OUT, deliberately:

- **Clippy.** Not run today. Turning it on is a separate decision with its own argument, and
  bundling it here would make a hygiene milestone into a style one.
- **Other lint families** - `unsafe_op_in_unsafe_fn`, `missing_docs`, the pedantic groups. This
  milestone closes what the compiler already says by default and adds no new opinions.
- **The `todo!()` HAL bodies.** P02M0142 M2 owns those and says why they cannot simply be deleted.
  See the coordination note at the end.
- **Behaviour.** An item deleted here is one nothing calls. If reading a dead method suggests a
  behaviour that is MISSING, that is a note for a milestone, not work in this one.

- [x] **M5 - Vocabulary with no producer, which is three different problems wearing one warning.**
  - `RoleKind::Power` IN THE EXECUTOR IS UNREACHABLE, and P02M0141 is why: it converted the last
    `kind = "power"` row (DeviceManager's `POWER`) to a `client` named `SYSPOWER`, and
    `system-manifest` now refuses any power role at all - `MAY_HOLD_ROOT_DOMAIN` is `[&str; 0]`. So
    `build.rs` can never emit that arm. The variant goes from `service_manager.rs`, and `build.rs`'s
    mapping arm becomes a build failure that names the reason. The variant in `system-manifest`
    STAYS: there it is the tripwire that does the refusing.
  - `Lifecycle::{Function, Interface}` and `Priority::{Exact, Quirk}` in DeviceManager are schema
    values no driver row uses today. Same treatment ONLY IF the executor has no behaviour for them -
    which is the thing to establish first. A variant the code handles and the manifest has not yet
    needed is different from one the code cannot handle.
  - `Reason::{BootstrapRefused, Unresponsive, BudgetSpent}` ARE NOT DEAD VOCABULARY, AND THIS IS THE
    ONE ITEM HERE THAT IS A DEFECT. ServiceManager has a watchdog and a restart budget and reaches
    both states. It just does not say so: when the budget runs out at `service_manager.rs:1168` the
    last recorded reason stays `Replaced`. `last_reason` goes out over the supervisor stat contract,
    and today it can never say "restart budget spent" or "unresponsive" - the two things an operator
    looking at a service that keeps dying would look for first. The fix is the missing write.
  - `Transition.{from, to, epoch}` and `LifecycleLog.boot` are written and never read. Decide by
    reading what `SupervisorStat` already carries: either the record reports them or it stops
    keeping them. Keeping a field for a reader that does not exist is the same defect as the
    variant above, seen from the other end.

- [x] **M5b - A BADGE WAS STAMPED, STORED AND NEVER READ BACK.** Found by M1, and it was not a
  warning to resolve - it was a mechanism with no delivery.
  - `sys_channel_send` takes one look at the handle table for the authority AND the badge (a fix
    with its own comment about a sibling thread closing the handle in between), stamps the badge
    onto the `Message`, and the message carries it to the receiver. Nothing reads `Message.badge`
    except `object/channel/tests.rs`. `HandleInfo.badge` is the same story on the other side: the
    field is filled from the capability and `sys_handle_info` does not return it.
  - So a server cannot tell one client's endpoint from another's by the badge, which is what badges
    are for, and the kernel does all the work to carry one.
  - AND IT COULD NOT HAVE WORKED. Every `install_object` in the kernel passes zero, and the ABI has
    no field, no argument and no syscall that could set one - so a badge was zero for every
    capability in every table, and a receiver that could read one would have learned nothing.
  - THE SYSTEM ALREADY ANSWERS THE QUESTION ANOTHER WAY. A server here mints a separate connection
    per client and knows who is speaking from which channel the message arrived on - DisplayService
    and StorageService both keep a `Client` with its own `chan`. Badges are the other design, where
    one endpoint is shared and the kernel labels the sender. This tree does not use it.
  - RESOLVED BY DELETING IT, on that reading: `Message.badge`, `HandleInfo.badge`, `Capability.badge`
    and the `badge` parameter of `Capability::new`, `insert_object`, `try_insert_object`,
    `install_object`, `Process::install`, `spawn_elf_process`, `spawn_with_object` and
    `prepare_with_object`, plus `lookup_typed_with_badge` and the two assertions that were the only
    readers. Four hundred and thirty-three call sites lost a `, 0`. If the shared-endpoint design is
    ever wanted it arrives with the two syscalls that were always missing, which is the half nobody
    had written.

## What this shares a border with

**P02M0142 M2 - the HAL contract.** The two meet at exactly one place and it is worth naming so
neither reopens the other. M2's subject is the twenty-seven `todo!()` bodies, which have static
callers from portable code and therefore do not warn; its deliverable is the contract comment at the
top of `arch/mod.rs`. What THIS milestone sees is the other half of the same story: `enable_nx`,
`enable_smap_smep`, `smap_enabled`, `smep_enabled` and `clac_on_entry` exist as real no-op bodies on
aarch64 and riscv64 and have no caller there at all, because only `arch/x86_64/mod.rs` calls them.
They are listed in that same contract comment as entries every backend owes.

So M2 fixes the promise and this milestone gates or deletes what the promise never needed. Whichever
lands first, the other reads it - and if it is convenient to correct the contract comment while
doing M3, that is M2's text arriving early rather than a second opinion about it.
