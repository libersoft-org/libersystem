# P02M0193 - soft2d on several cores: parallel tile rendering over the system's worker pool

Status: OPEN. It closes when every item below is done.

THE OWNER'S DECISION (2026-09-25): yes to parallel 2D rendering, as a milestone of its own. P02M0103 built
the same thing for 3D - `soft3d` shades a draw's tiles through `soft3d::frame::Workers`, `rt::pool` supplies
the threads, and the frame is bit-identical to the serial walk at every worker count - and recorded the 2D
half as "a plan of its own" because the 2D backend shares mutable state across tiles that the 3D one does
not. This milestone is that plan.

WHAT MAKES 2D DIFFERENT, measured in the code rather than assumed:
  - ONE TILE SURFACE and one set of scratch - the rasteriser, the surface pool for layers and filters, the
    mask pool, the span buffers - serve every tile in turn. A second worker needs its own, and all of it is
    charged against the profile's PREPARED SCRATCH CEILING (64 MiB in `Render2D Core Profile 1`), so the
    number of lanes a frame can afford is a function of the frame, not a constant.
  - THE CEILING HAS A SECOND CLAIMANT, AND IT CAN CHANGE PIXELS. Prepare builds an optional decoded copy - a
    level zero - of every image drawn `Bilinear` or `Bicubic`, and gives copies back, newest first, until
    the frame fits. The code calls sampling a copy "the same picture" and giving one back a cost of "time
    and nothing else", and neither is true to the bit: the copy holds each texel as `R16G16B16A16Float`,
    while the direct path decodes every tap through a single-precision table, so keeping or giving back a
    copy can move an output pixel. If a lane could take a copy's room, the picture would depend on the
    worker count.
  - THE REPLAY ALLOCATES, although the backend's own header says it does not. Every tile builds a clip
    stack and a layer stack in fresh vectors; every tile a glyph run reaches flattens each outline and
    colour-layer glyph of the run and builds its edges again; a filtered layer builds its node table and a
    blur its kernel in every tile; and every frame collects its shader table and resolves each gradient's
    ramp. In the guest each of those takes the process's one test-and-set heap lock, so with several lanes
    they become contention that the host benchmark's allocator does not show.
  - THE GLYPH CACHE IS WRITTEN DURING THE REPLAY. It holds DECODED forms - an outline, a mask, a bitmap
    strike or colour layers - fetched from the provider the first time a tile meets a glyph, and outlines
    are rasterised in every tile, not cached as masks. It is bounded and evicts in insertion order, and a
    prepared list is bound only to the generation that `clear` bumps. Two workers meeting the same glyph
    is a race, and an entry decoded before the frame can be evicted before the frame uses it.
  - THE INPUTS A TILE READS ARE NOT `Sync`. `rt::pool::for_each` takes a `Sync` work closure; the image
    source is consulted inside a tile and the cancellation before every tile, neither trait requires
    `Sync`, and the cancellation fixture counts through a `Cell`.
  - THE TARGET IS ROW-MAJOR and belongs to the caller. A 64-pixel band of rows is one contiguous slice, so
    BANDS can be handed to workers safely - but 480 rows are only eight bands, which caps the speedup at
    eight. Tiles as the unit need either a tile-major intermediate or a disjoint-rectangle writer, and which
    one is decided by measuring both, not by preference. AND A FRAME IS ONLY AS PARALLEL AS ITS UNITS: 64x48
    is one tile and one band, and `rt::pool::for_each` wakes at most one helper fewer than there are units,
    so a one-unit frame runs wholly on the caller's thread and a parallel comparison at that size compares
    the serial walk with itself.
  - CANCELLATION is asked between tiles today, by one thread; with several it must stop every worker at its
    next tile and still leave whole tiles behind.

## P02M0193 - The interface and the scheduling

- [ ] A `Workers` interface for `soft2d` in the shape `soft3d`'s has - the caller's pool, lanes of private
  scratch, units of work handed out once each, and `Serial` as the default and the SCALAR REFERENCE - so an
  application holds ONE pool for both backends. Inside a unit the order is the serial one (bin order, then
  rows); a pool that returns before running every unit is refused, a unit handed out twice is drawn once,
  and a failure reports the lowest failing unit's error, which is the one the serial walk meets first. The
  backend holds its `Workers` from construction, as it holds its image source: the `Backend` trait's
  `prepare` and `render` carry no pool, and `prepare` is where the lanes are reserved.
- [ ] `Sync` WHERE A LANE READS. `ImageSource` and `Cancellation` gain `Sync` as supertraits. Every image
  source in the tree is plain data already - `soft2d-bench`'s, the conformance suite's, the host fixtures',
  `test2d-sw`'s and `test3d-sw`'s - and the cancellation fixture counts through an atomic instead of a
  `Cell`. `GlyphProvider` does NOT gain it: after the glyph item below it is called only at prepare, never
  by a lane. What the lanes share besides - the prepared list, the shader table, the transfer tables - is
  plain data and is only read.
- [ ] A LANE OWNS EVERYTHING A UNIT WRITES, within the ceiling: the tile surface, the rasteriser, the surface
  pool, the mask pool, the span buffers, the clip stack, the layer stack and a filtered layer's node table,
  each reserved at prepare for this list - the clip stack to its clip depth, the layer stack to its layer
  depth, the node table to its largest filter graph, the rasteriser's crossings and active list to its
  widest edge list with the glyph edges counted - so no lane grows whichever units it is handed.
  THE CEILING IS SPENT IN AN ORDER THAT CANNOT CHANGE A PIXEL. The FIRST lane is settled the way today's one
  set of scratch is: the optional copies are given back, newest first, against the list's own scratch and
  ONE lane's, and a frame that does not fit that is refused before it starts, exactly as today (the lane's
  stacks and node table are its only new part, and at the profile's depths they are kilobytes). LANES
  BEYOND THE FIRST are fitted only into what is left, up to the lanes the pool offers, so a lane never
  displaces a copy and every worker count keeps the copies the one-lane frame keeps. A COST THAT EXISTS
  ONLY WITH SEVERAL LANES - the tile-major intermediate, if the unit of work below needs one - is charged
  together with those lanes, and a frame whose second lane does not fit beside it runs on one lane without
  it, so that cost never refuses a frame. The frame reports the lanes it runs with and the units it is cut
  into. The copies are not made single precision instead: that would double their memory and move the
  pixels of draws that sample one today. The comments that call a copy "the same picture" and its loss
  "time and nothing else" are corrected to say it can move a pixel. A HOST CASE HOLDS THE ORDER: an image
  whose copy fits beside one lane but not beside the pool's lanes, on a frame cut into AT LEAST AS MANY
  UNITS AS THE POOL HAS LANES, the target bit-identical at every worker count, with the kept copy, a lane
  count below the pool's and the unit count all asserted - so the case is known to sit on the boundary it
  tests, and a lane count held down only because an implementation caps its lanes at the frame's units
  cannot pass it.
- [ ] NOTHING IN THE REPLAY ALLOCATES, which makes the header's claim true. Per frame: each gradient's ramp
  is resolved at prepare into the prepared list, and the shader table keeps its storage from one frame to
  the next the way `soft3d::frame` recycles its tiles and views. Per unit: the stacks and the node table
  are the lane's, a blur's kernel weights are computed at prepare with its graph, and glyph edges are built
  at prepare (next item). Anything else the counting allocator finds moves into the same reservation.
- [ ] GLYPHS DECODED AND PLACED AT PREPARE, so the replay reads only the prepared list and never the cache
  or the provider. Prepare computes every placed glyph's cache key and device origin - the arithmetic the
  replay does today, moved and not changed - and resolves each distinct key through the cache, decoding a
  miss through the provider. An outline or colour-layer form is flattened at its placed origin and
  edge-built there, once per placed glyph, exactly as a tile does it today, so the edges and the pixels are
  the same; like a fill's edges they are the prepared form and not scratch. A mask or bitmap form is held
  by reference. NOTHING IS PRE-RASTERISED: an outline turned into a mask would composite through the
  coverage gamma that masks go through and outlines do not, and every text pixel would move.
  THE MISS RULE, DECIDED: THERE IS NO MISS AT RENDER. Cache entries become shared (`Arc`); the prepared list
  holds every form it draws, and an eviction drops only the cache's own reference, so a form stays alive
  while a list holds it - the profile's "a live prepared snapshot retains its own resources". The cache's
  byte bound counts what the cache holds, and what a list holds is released with the list. `clear` still
  bumps the generation and the prepared key still carries it, so a list prepared against a replaced face is
  refused by name as today. `GlyphRaster::get` keeps its signature.
- [ ] The unit of work - row bands, or tiles through a tile-major intermediate or a disjoint-rectangle
  writer - chosen by measurement on the benchmark scenes, and the choice recorded with its numbers.
- [ ] Cancellation that every lane asks before each unit and that stops every lane at its next unit, and a
  test that cancels mid-frame with several lanes, on a frame cut into more units than it has lanes, and
  finds every unit either whole or untouched.

## P02M0193 - Verification

- [ ] THE SCALAR REFERENCE HOLDS IT: every existing scene and a crowded one - clips rectangular, masked and
  inverse, nested layers, a filter reading the backdrop, images, gradients and text of every glyph kind -
  through `Serial`, through real threads, backwards and handing units out twice, the target BIT-IDENTICAL
  to the serial walk's at every worker count. No tolerance: the units run one algorithm over disjoint
  pixels, so any difference is a defect, and the profile's tolerances measure an implementation against
  the analytic answer, not two schedules of one implementation against each other. THE CROWDED SCENE HAS
  A FLOOR ON ITS UNITS: it is cut into at least as many units as the lanes of the pools that run it,
  whichever unit is chosen - four lanes need at least 256 rows - and the case asserts its unit count,
  because a one-unit frame runs on the caller's thread alone and running it backwards or twice reorders
  nothing. Most existing scenes are one tile, which is the case of lanes left idle.
- [ ] A WARMED FRAME ASKS THE ALLOCATOR FOR NOTHING, measured and not claimed: `soft2d`'s test build gets
  the counting allocator `soft3d`'s has (thread-local, `realloc` counted), and the crowded scene is
  prepared once and rendered three times with the third counted - ZERO through `Serial`, and ZERO through
  a pool that runs four lanes on the test thread, since a pool that spawned threads would count its own
  allocations and not the frame's - with the third frame bit-identical to the first.
- [ ] `soft2d-bench --workers N` and `--scaling`, with the five frozen scenes at one to sixty-four workers
  in `docs/PERF.md`, each row naming the lanes the frame ran with and its units, because the ceiling can
  hold the lanes below the worker count (`UI-effects`, by the code's own arithmetic, fits about twenty
  beside its photo's copy); the picture bit-identical to one worker's at every count.
- [ ] `test2d-sw` renders through `rt::pool`: `--workers=N` pins the lane count, the default is one lane
  per core capped as `test3d-sw`'s is, `--workers=1` is the serial walk and the SERIAL REFERENCE, and the
  demo prints the lanes its frames ran with and the units they were cut into - the frame's own report, not
  the pool's threads plus one, which is what `test3d-sw` prints. `--compare` renders every frame again on
  the demo's own thread into a spare image and requires the two BIT-IDENTICAL, and a guest test runs it
  with four workers on all three architectures, the way `test3d-sw --workers 4 --compare` is run, but not
  at that test's 64x48, which is one soft2d unit. THE GUEST SURFACE IS CUT INTO AT LEAST AS MANY UNITS AS
  THE WORKERS IT ASKS FOR, whichever unit is chosen - four 64-row bands are 256 rows - and the test
  asserts the lane count, the unit count and the number of frames compared, each read from the demo's
  output and not only found.
- [ ] THE MEASURED DEMO ROWS STATE THEIR WORKER COUNT. The 2D demo rows in `docs/PERF.md` are re-measured
  at `--workers=1` and at the default, each row naming its worker count AND the guest's vCPU count (the
  harness's default is the host's core count; a gate pins its own, as P02M0189's pins four): the workers
  share those vCPUs with DisplayService, and that is part of the pooled row. P02M0189's account is the
  SERIAL walk, and the pooled draw is an additional recorded row beside it, not a term of it. The two
  milestones close in either order, and WHO EDITS P02M0189'S GATE FOLLOWS FROM WHETHER THE GATE EXISTS, as
  P02M0189's serial-walk and gate items state too: the change here that makes the pool `test2d-sw`'s
  default pins every `qemu-2d-account` run that exists at that point to `--workers=1` and adds the pooled
  row, in that same change, whether or not P02M0189 has closed; a gate first written after that change
  pins from its first version.

EXCLUDES: changing any scene, budget or ceiling of P02M0103's 2D floor, which stays that milestone's; SIMD,
which is a separate route; a GPU.
