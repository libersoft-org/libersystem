# P02M0193 - soft2d on several cores: parallel tile rendering over the system's worker pool

Status: OPEN. It closes when every item below is done.

THE OWNER'S DECISION (2026-09-25): yes to parallel 2D rendering, as a milestone of its own. P02M0103 built
the same thing for 3D - `soft3d` shades a draw's tiles through `soft3d::frame::Workers`, `rt::pool` supplies
the threads, and the frame is bit-identical to the serial walk at every worker count - and recorded the 2D
half as "a plan of its own" because the 2D backend shares mutable state across tiles that the 3D one does
not. This milestone is that plan.

WHAT MAKES 2D DIFFERENT, measured in the code rather than assumed:
  - ONE TILE SURFACE and one set of scratch - the rasteriser, the surface pool for layers and filters, the
    mask pool, the span buffers - serve every tile in turn. A second worker needs its own, and all of it is
    charged against the profile's PREPARED SCRATCH CEILING (64 MiB in `Render2D Core Profile 1`), so the
    number of lanes a frame can afford is a function of the frame, not a constant.
  - THE GLYPH CACHE IS WRITTEN DURING THE REPLAY: a glyph is rasterised the first time a tile meets it. Two
    workers meeting the same glyph is a race; the cache must be filled before the tiles run (at prepare,
    where the glyph runs are already known) or be per lane.
  - THE TARGET IS ROW-MAJOR and belongs to the caller. A 64-pixel band of rows is one contiguous slice, so
    BANDS can be handed to workers safely - but 480 rows are only eight bands, which caps the speedup at
    eight. Tiles as the unit need either a tile-major intermediate or a disjoint-rectangle writer, and which
    one is decided by measuring both, not by preference.
  - CANCELLATION is asked between tiles today, by one thread; with several it must stop every worker at its
    next tile and still leave whole tiles behind.

## P02M0193 - The interface and the scheduling

- [ ] A `Workers` interface for `soft2d` in the shape `soft3d`'s has - the caller's pool, lanes of private
  scratch, units of work handed out once each - so an application holds ONE pool for both backends.
- [ ] Per-lane scratch within the ceiling: the frame computes what one lane costs and runs with as many as
  fit, down to one, and reports how many it used; a frame that does not fit even one lane is refused
  before it starts, exactly as today.
- [ ] Glyphs rasterised at prepare for the glyph runs the list names, so the replay only READS the cache.
- [ ] The unit of work - row bands or tiles with a tile-major intermediate - chosen by measurement on the
  benchmark scenes, and the choice recorded with its numbers.
- [ ] Cancellation that stops every lane at its next unit, and a test that cancels mid-frame with several
  lanes and finds only whole units drawn.

## P02M0193 - Verification

- [ ] THE SCALAR REFERENCE HOLDS IT: every existing scene and a crowded one through the serial walk, through
  real threads, backwards and handing units out twice - the pixels identical to the serial walk's, bit for
  bit on the parts the profile says are bit-exact and within its tolerance where it says tolerance - plus
  the warmed-frame allocation count through a pool.
- [ ] `soft2d-bench --workers N` and `--scaling`, with the five frozen scenes at one to sixty-four workers
  in `docs/PERF.md`; the picture checked at every count.
- [ ] `test2d-sw` renders through `rt::pool`, and a guest test compares its frames with the serial walk the
  way `test3d-sw --compare` does, on all three architectures.

EXCLUDES: changing any scene, budget or ceiling of P02M0103's 2D floor, which stays that milestone's; SIMD,
which is a separate route; a GPU.
