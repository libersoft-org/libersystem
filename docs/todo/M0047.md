# M0047 - Layered console: stream -> grid model -> renderer -> swappable display

The console is today one monolithic `Term` (in ConsoleService) that BOTH keeps the cell
grid AND draws pixels, duplicated again by the kernel's own framebuffer console
(`console.rs`). This milestone splits it into three graphics-independent layers, mirroring
the ABI "one model, many codecs" pattern (LSIDL -> CLI/JSON/CBOR):

  L1 stream  - the raw byte stream programs emit (text + ANSI control codes); no grid,
               width-agnostic (transport, not stored state).
  L2 grid    - a graphics-free terminal model: cell grid + ANSI/CSI/OSC parser + cursor +
               SGR attributes + scrollback + a per-row soft/hard wrap flag; knows a width,
               has no pixels.
  L3 render  - the only layer that knows pixels/font/geometry; turns the L2 grid into
               glyphs on a surface.
  display    - a swappable surface backend under L3 (boot framebuffer <-> virtio-gpu); a
               backend handoff copies the existing content (may change resolution) and never
               clears, so the picture survives like a Windows display-driver install.

Consumers attach at the layer that fits: ssh/telnet and a raw log tap L1 (forward the
stream; the remote end has its own grid, so they never fight over width); the screen
renderer and a "screen as text" snapshot tap L2; pixels are L3 only. This also lands the
long-standing "don't clear the boot log" goal (the boot log is just L2 content that
survives the L3/display handoff) and removes the kernel/ConsoleService renderer duplication.
Note: full-screen TUI apps (vim/htop) paint cells by coordinate, so the model is a grid,
not reflowing text; "unbounded lines" are an export-time reconstruction from the grid + the
wrap flag. Each sub-step must build and keep the test harness green (66 [ok]).

- [x] M0047a - Extract the raw pixel `Surface` out of ConsoleService's `Term`: addr +
      geometry (width/height/pitch/bpp/shifts/sizes) and the pure pixel ops (`channel`,
      `pack`, `put_pixel`, `fill`, the bulk pixel-scroll copies) move into a `Surface` struct;
      `Term` holds a `surface` and delegates every pixel write. The only code that touches
      pixels and the framebuffer address now lives in one place (the L3-below display target).
      Done when: build + tests green, the console behaves identically.
- [x] M0047b - Make the grid model graphics-free: `Cell` stores logical colour (a `Color` fg/bg
      + bold/underline/reverse) instead of packed framebuffer pixels; colour resolution
      (`palette`/`pack`/`resolve`/`indexed`) moves to draw time in the renderer. Removes the
      last pixel dependency from the cell grid. Done when: green, behaviour identical.
- [x] M0047c - Extract the graphics-free L2 `Screen` (cell grid primary/alt/dirty, the
      ANSI/CSI/OSC parser, cursor, SGR attributes, scrollback) now that the grid is pixel-free;
      `Term` becomes `Screen` + the renderer. Done when: green, behaviour identical, no pixel
      field on `Screen`.
- [x] M0047d - Carve the L3 renderer out as a separate consumer: all glyph/geometry draw code
      (`draw_cell`, `draw_caret`, `flush`, the dirty walk) moves into a `FramebufferRenderer`
      that reads the `Screen`'s dirty cells through a clean diff/snapshot interface. Done when:
      green, behaviour identical.
- [x] M0047e - Add the per-row soft/hard wrap flag to `Screen` and a first non-graphical
      consumer: a `TextSink` that serializes scrollback + screen to logical lines, joining
      soft-wrapped rows into unbounded lines and emitting `\n` only on hard breaks. Done when: a
      test dumps a known screen to the expected text; green. (Proves L2 is graphics-independent.)
- [x] M0047f - Swappable display backend under the surface: the `Surface` becomes a trait
      (pixels + geometry + `present`) with boot-framebuffer and virtio-gpu backends; the
      renderer targets "the current surface". A backend handoff copies the existing pixels into
      the new backing and may change resolution, but never clears. Done when: the virtio-gpu
      takeover preserves the on-screen content (no blank/banner wipe); green.
- [x] M0047g - One console, no duplication: the kernel boot console and the ConsoleService
      renderer share the L2 model + L3 renderer (the kernel hands its content across at
      takeover). The kernel boot log stays on screen after ConsoleService and the gpu take
      over. Removes the duplicate renderer (the "find dead/duplicate code" NOTES item). Done
      when: the boot log is visible in the running shell on both the boot-fb and gpu/spice
      paths; green.
- [x] M0047h - Wire an L1 stream tap (optional, foundation for ssh/telnet/script): route the raw
      byte stream to additional sinks (a raw capture / log) alongside the L2 model. Done when:
      a raw-capture sink records the exact emitted stream; green.
- Done when: the console is three clean layers (stream / grid model / renderer) over a

  every sub-step.
- [x] **`display_service_restores_the_console_surface` takes the whole suite down.** Found
  2026-07-31 while running the `service` tag: the run reports
  `INCOMPLETE: QEMU exited successfully without the test-suite completion marker` at that test,
  so the guest leaves without the completion line and every test ordered after it is never
  reached - `resource_manager_contains_a_domain` among them, which is how this was noticed at
  all. That is worse than a failing test: a red one names itself and the suite carries on,
  while this one silently truncates the coverage behind it, and a truncated run reports as a
  failed recipe rather than as tests that never ran.
  Bisected rather than assumed. It fails identically at `6eeb394`, before the process-naming
  and fault-reporting work that was in flight when it surfaced, so it is inherited and not
  fallout from that. Whether it predates the suite decomposition (`e02cf1f`, which is where
  this test's file moved) is not established.
  Both opening questions are answered, and neither answer is the one the wording suggested.
  Why it looks successful: in test mode the only legitimate exit is the debug-exit device -
  the runner writes 0x10 for pass, QEMU exits 33 and `qemu-run.sh` maps that to 0; 0x11 for
  fail gives 35. A plain 0 means QEMU ended without that port being written at all, and with
  `-no-reboot` on the command line that is precisely what a guest RESET produces. So the guest
  did not exit cleanly - it reset, and the most likely cause is a triple fault: there is a
  double-fault handler and it prints, so a double fault would have said so, while a fault
  inside that handler resets the CPU with nothing on the wire. That is why the log simply
  stops mid-test. The runner message said "QEMU exited successfully", which reads as benign
  and cost this investigation a wrong first hypothesis; it now names a guest reset and says
  that everything after the last logged test never ran.
  Whether the test wedges or is a casualty: a casualty, and not of any single predecessor. It
  passes alone (`display`, 10 tests) and in every pair tried against the blocks that run
  before it in the `service` order - `config,display` (13), `audio,display` (14),
  `dynamic,display` (25). So the state that kills it accumulates across more of the suite than
  any pair reproduces, which is the hardest shape to catch: invisible in a focused run, and in
  a full run it hides inside the larger failure it causes.
  Three hypotheses are eliminated by evidence. A fourth was recorded here as eliminated and is
  NOT - the correction matters more than the claim did. `-d cpu_reset` shows eight resets in a
  failing run, all of them the boot-time SMP bring-up, and that was read as ruling out a triple
  fault. It rules out nothing: `-no-reboot` makes QEMU EXIT instead of resetting, so a
  guest-requested reset produces no cpu_reset entry by construction. Every observation here is
  equally consistent with a triple fault, and the reasoning that dismissed it was checking for
  a record that cannot exist. It is NOT a power-off from userspace: all three callers of `system_power`
  - the Power key in `driver.keys`, ServiceManager's `!poweroff` verb, and the shell's power
  request - now announce themselves before calling, and none of them speaks in a failing run.
  And it is NOT the suite finishing with its output lost: `qemu-run.sh` maps QEMU's exit 33
  (the debug-exit device reporting a pass) to 0, so a 0 at the caller had two possible
  meanings; the raw code is now printed, and it is 0, not 33. The guest never wrote the debug
  port at all.
  **It is a triple fault, and the faulting instruction is `write_cr3`.** Under TCG the last two
  exceptions before the guest disappears are:
    v=0e e=0018 cpl=0 IP=ffffffff80120c68 CR2=ffffffff80120c68
    v=08 e=0000 cpl=0 IP=ffffffff80120c68  EAX=000000007e4d4000
  A ring-0 page fault whose faulting address IS the instruction pointer, error code 0x18 - an
  instruction fetch from a non-present page - followed by a double fault at the same address
  and then nothing. `ffffffff80120c68` is 8 bytes into
  `kernel::arch::x86_64::context::write_cr3` (which begins at `ffffffff80120c60`), and the EAX
  on the double-fault line is the CR3 being loaded: `0x7e4d4000`.
  So the sequence is: a context switch installs a page table that does not map the kernel it is
  executing in, the next instruction fetch faults at the current IP, the fault handler needs
  that same mapping to run and faults again, and the CPU resets. This is a kernel address-space
  lifetime defect, not a console one - the test that dies is the one that kills a process
  (`emergency revoke SIG_KILLs the process bound by PermissionManager`), and switching to a
  Process whose AddressSpace has been torn down is exactly this shape. The console milestone
  holds the entry because that is where the investigation started; the defect belongs to the
  kernel.
  **The cause is a frame handed out twice: a surface is painted into a live page table.** A
  guard added before every CR3 load - refusing to switch into an address space whose kernel
  half has drifted from the kernel's own - turns the silent triple fault into a named panic,
  and it names this:
    address space 0xa3b9000 diverges from the kernel mapping at PML4[256]: 0x33669900336699 vs 0x7d217023
  The kernel's entry is an ordinary page-table entry. The other is `0x00336699` repeated - not
  an entry at all but PIXELS, and specifically the colour this suite's own display test fills a
  320x200 benchmark surface with (`fill(&benchmark_surface, 0x0033_6699, 320 * 200)`,
  `test_suites/services.rs`). So the physical frame backing that address space's PML4 is also
  backing a drawing surface, and painting the surface overwrites the page table. The kernel
  half is destroyed, the next switch into that space cannot fetch the next instruction, and the
  machine resets.
  **And the writer is the test harness, not the kernel.** Its `fill` helper took `frames()[0]`
  and wrote the whole run contiguously from there, which is correct only while the run fits in
  one frame. A `MemoryObject`'s frames come from the frame allocator and are not physically
  contiguous, so the 320x200 surface - 256 kB, 62.5 pages - ran off its first frame and over 61
  unrelated ones. Nothing was allocated twice and no kernel invariant was broken: a page table
  was simply painted on by something writing past the end of its buffer. `fill` now walks the
  frame list a page at a time and asserts the object has enough frames for what it was asked to
  paint.
  This is why it resisted every ordinary technique. Every other surface in the suite is 4x4 -
  64 bytes, one frame - so only the single large fill could do damage; WHAT it damaged depended
  on which frames happened to follow the first one, which is a function of the whole allocation
  history of the run; and the consequence surfaced later still, when something switched into
  the address space whose tables had been overwritten. No single test causes it, which is why
  no pair reproduced it, and the effect is separated from the cause by both time and subsystem.
  Fixed and verified: the `service` tag completes, 54 tests passed, where it had been dying at
  the eleventh all day.
  Getting there needed one more correction of method, and it is the reusable part. The tests
  run under KVM (`-enable-kvm`, unless `NOKVM=1`), where the host kernel executes the guest and
  QEMU sees almost nothing: `-d int` produces an EMPTY file and `-d cpu_reset` logs only the
  resets QEMU performs itself. Both were read as evidence about the guest and neither is. Under
  `NOKVM=1` the same failure reproduces and `-d int` writes 417 MB in which the last two records
  are the answer. A blind instrument that returns nothing looks exactly like an instrument
  reporting nothing to find.
  Three diagnostics landed while eliminating the above, and they are the durable part of this
  entry. `QEMU_EXTRA` now reaches test mode - it was documented as extra QEMU arguments and
  applied to every configuration except the one where a guest actually needs diagnosing.
  `qemu-run.sh` prints the raw QEMU exit code in test mode, so a passing suite and a
  self-terminating QEMU are no longer the same number. And the runner says GUEST RESET with
  the consequence spelled out, instead of "exited successfully", which reads as benign and is
  what sent this investigation after a clean shutdown that never happened.
