# P02M0101 - Additional system utilities

Status: COMPLETE (2026-08-23). APPLICATION PLATFORM. NOT A PHASE-2 COMPLETION GATE.

The ordinary small programs the appliance/edge console lacked. Every command is one canonical
`<name>.lsexe` staged under `bin/`, launched by PermissionManager with the minimum typed
capabilities it needs; no implementation is folded back into the shell. `uptime.lsexe` already
exists and is retained as the conformance baseline. `clear` moves from its current shell-builtin
implementation to `clear.lsexe`, because it changes no session state. The requested `shich` spelling
is treated as a typo for the conventional `which.lsexe`; no nonstandard alias is staged. `env` is
deliberately not duplicated here: SessionService already owns typed cwd, `PATH` and environment
variables and the shell already implements `NAME=VALUE`, `$NAME`, `env` and `unset` over that
persistent per-session state.

- [x] Storage and stream primitives required by the tools, added once to
  `liber:storage` rather than re-created in each binary: file `stat`; bounded/streaming
  reads; atomic same-volume `rename`; `truncate`; timestamp update/create (`touch`);
  and a `watch(path) -> stream<file-event>` contract for change/remove/replace. Add one
  transactional writer resource for sequential and bounded positioned writes, explicit
  append mode, truncate, flush, commit/publish and abort; this is the shared primitive for
  editor safe-save, audio-header finalization, `tee` and P02M0102 redirects, rather than each
  client inventing temporary names or rewriting a whole file to append. Extend every
  writable backend honestly and return typed unsupported/denied for read-only or
  incapable backends. Cross-volume move is never mislabeled atomic: copy -> verify ->
  publish -> delete source, leaving the source intact on any pre-delete failure.

  DONE 2026-08-13. `liber:storage` grew seven ops: `stat` (17), `rename` (18), `truncate` (19),
  `touch` (20), `read` (21), `watch` (22) and `open-writer` (23), plus the `writer` interface the
  last of those returns a channel to.

  `read` IS A WINDOW, and its contract is what makes the tools bounded: at most `length` bytes from
  `offset`, clamped to what one reply may carry rather than refused, and a SHORT ANSWER IS THE END
  OF THE FILE rather than a failure. Every streaming tool in this milestone is a loop over it. The
  clamp is the part worth keeping: a caller cannot break its own stream by picking too large a
  chunk, so there is no chunk size a tool has to know.

  `watch` reports what passes THROUGH the service - writes, removals, renames, truncations,
  timestamps - and nothing else. A disk edited behind the service's back produces no event, and the
  contract says so rather than implying a promise about the medium. A watcher that cannot keep up is
  DROPPED rather than buffered: its end of the stream closes, and the contract tells it what to do
  about that (re-read, rather than reconstruct state from the events it received). The events are
  produced by the mutations themselves, through an outbox on the volume that the serve loop drains -
  because a mutation happens behind the generated `Service` trait, which is handed the volume and
  has no way to reach the watcher table.

  The WRITER is transactional in the one sense that matters: nothing it writes is visible until
  `commit`, so a session that dies half way leaves the file exactly as it was. It stages in the
  service, bounded by the same accumulation policy a streamed write is - which is stated in the
  contract, because a client that needs more than that must use `write-stream` and give up the
  transaction. One session per path, refused with `again`, since two publishing in an order neither
  chose means the loser's work disappears at the moment it reported success.

  Two things this cost that were not in the plan. The writer's channel speaks a SECOND interface,
  and both interfaces number their ops from one - so `writer.write-at` (2) and `volume.list` (2)
  collided, and a session's positioned write was answered by the directory streamer. Dispatching by
  the CLIENT rather than by the op is the only arrangement that cannot collide, and it is what the
  contract says anyway. And `open-writer` is the one volume op whose answer is a new CLIENT, which
  the generated dispatch cannot reach - so the loop dispatches through a `VolumeCall` wrapper that
  holds the client table, the same shape `volume-admin.open-directory` already needed.

  BACKENDS, honestly: LiberFS answers all seven (`stat`, `rename` and `truncate` were already there,
  `touch` is truncate-to-own-size, `read` seeks rather than reading the whole file). The memory
  filesystem gained `rename`, `truncate` and `touch`. FAT, ISO9660, UDF and the boot archive answer
  `invalid` for the mutating four, which is a statement about the medium rather than about the
  caller - and it is a REAL GAP for `vol://media` and `vol://usb`, where `mv` and `truncate` cannot
  work until the FAT backend implements them. That is left open rather than papered over.

  `touch` takes the timestamp from its caller (`at`, Unix seconds; zero means the service's clock),
  which is what lets `touch.lsexe` pass a TimeService reading instead of letting the filesystem
  guess.

  Verified by breaking it: with `volume.read` returning an empty window, the guest test fails at its
  first assertion (`the first window`, left `Some([])`, right `Some([97, 98, 99, 100])`). Two guest
  tests cover the seven ops end to end, over a memory volume that implements all of them.

  DONE 2026-08-13. The pure half is `user/libs/command/cli`, a leaf crate that touches no capability

  inputs it needs. It holds the glob matcher, the argument classifier, the size and range parsers,

  The matcher is ITERATIVE with one backtrack point. The recursive form is the textbook one and it
  is a way to crash a tool by naming a file: forty asterisks against a four-kilobyte name is the
  input, and it is a test.

  The IPC half - the iterative `volume.list` walker, the bounded window reader and the `VolumeSource`
  that turns a file into a `ChunkSource` - lives in the `tools` library beside the client it needs.
  The walker's frontier is explicit and bounded in three directions (depth, pending directories,
  entries per listing), so a tree deep or wide enough to exhaust a recursive walker is refused by
  name rather than by the stack.

  Sizes use BINARY units and refuse the decimal spellings rather than reading `1KB` as 1024 - a
  seven-per-cent difference at gigabytes is data lost by a tool that guessed. Ranges are inclusive
  at both ends and a reversed one is refused rather than reordered.

  No regex engine: `grep` searches for a fixed string and says so, because a shared bounded engine is
  its own piece of work and a half-understood pattern is a wrong answer that looks right.
- [x] Replace PermissionManager's ad-hoc `(args, cwd, stdout)` bootstrap sequence with a
  versioned bounded launch context carrying arguments, canonical cwd and an immutable
  snapshot of the SessionService string-variable table (there is no separate export flag
  today). The launcher validates variable names/count/total bytes; a child can read but
  not mutate its parent/session snapshot, and handles/capabilities never enter it. Values
  intended as secrets do not belong in this ordinary environment table. Preserve today's
  `$NAME` shell expansion, but make `PATH` available to `which` and the P02M0100 command bar
  without granting either a mutable SessionService capability. P02M0102 extends this same
  context with stdin/stdout/stderr endpoints instead of creating a second bootstrap format.
  This item BLOCKS all nine open items of P02M0102, which was found on 2026-08-05 by starting P02M0102's
  first item and reading it properly. Its cost is 65 files - 52 tools and 13 services read their
  bootstrap messages directly, and `args` and `cwd` are two of those messages - so it is a
  launch-ABI change rather than a service-local one, and it should be planned as such.

  DONE 2026-08-05, in the shape above minus the environment snapshot, which is the next step and
  is described at the end.

  `base:launch-context` is one versioned record - arguments, cwd, environment - sent as ONE message
  right after the stdout handoff and BEFORE any capability grant. It replaced two bare messages
  with the grants between them, where the cwd had to be sent LAST because a tool reads its grants
  with a tagged receive and a bare message arriving early is consumed as whatever that tool reads
  next. That rule lived in a comment in the launcher and had to be obeyed by fifty-two programs.

  It lives in `base`, not in `session` where `env-var` was first written, and finding out why took
  two attempts. The record needs `env-var`; `session` already imports `process`, so `process` could
  not import `session` back. Putting the context in `session` instead would have made every program
  that reads its own arguments link the whole session interface. Moving `env-var` down into `base`
  - which everything imports already - resolves both. That move is a breaking ABI change by the
  checker's reckoning (`session.env-list` returns a type with a new owner) and was accepted
  deliberately; the wire bytes are unchanged, since `env-var` encodes as the same two
  length-prefixed strings wherever it is declared.

  Where the DECODE happens was the second thing the design got wrong. The obvious home is `rt`, so
  every program gets its context in one call - but the manifest refused it by name:
  `lsrt -> base-proto -> lsrt`. Every shared library depends on the runtime, so the runtime sits at
  the bottom of that graph and may depend on none of them. `rt` therefore bounds and delivers the
  MESSAGE (`recv_launch_bytes`, capped at 64 KiB) and the program decodes it with the schema's own
  type. Restating the record's shape inside `rt` would have put a second definition of the format
  in the one place that must never disagree with it.

  A launcher may attach ONE capability to that message - the shell does, for `script`'s PTY master
  and for a net tool's client - so the program receives context and capability atomically.
  `recv_launch_with` returns it; `recv_launch_bytes` CLOSES it rather than dropping it, because a
  discarded handle stays open for the life of the process. That is the same leak the governed tools
  had been carrying two of per launch.

  Scope, counted: 41 tools decode the context, 10 only consume it (they read no field, so they need
  no schema dependency at all), both launchers send it - PermissionManager for governed tools and
  the shell for its direct spawns - and 16 hand-written stagings across four kernel test suites had
  to learn the format. The shell path gained something it never had: a shell-spawned tool now
  inherits a working directory, where before only PermissionManager passed one.

  Verified by breaking it, not by the suite passing: replacing a context with an empty message
  makes the tool refuse it and produce nothing, and the test catches that. (The first run of that
  check used a tag the test does not carry, and passed for that reason - a green result proves
  nothing until you have seen the test fail.)

  The environment snapshot followed, and the shape it took was decided by where the table lives.
  SessionService holds it and PermissionManager has no client for it; the shell does. So the shell
  PROPOSES the table through the `run` / `run-pipeline` ops and the launcher DECIDES it - the same
  split as for capabilities, and the reason the check lives in the launcher rather than where the
  table was read.

  Passing the whole `launch-context` record through `run` was considered and rejected: a pipeline
  carries its arguments per stage (`pipeline-stage { name, args }`), so the record's `arguments`
  field would have been dead weight in that call. The ops take `environment` beside the `cwd` they
  already had.

  Bounds, refused rather than trimmed: at most 64 variables, 64 bytes of name, 4096 of value,
  32 KiB in total - well inside the 64 KiB the whole encoded context may occupy, since the
  arguments and the working directory share it. A name must be non-empty and free of `=` and NUL,
  because a pair rendered as `NAME=value` anywhere would otherwise not parse back. Silently
  dropping the sixty-fifth variable would give a program an environment its caller never described,
  and the difference would surface as a tool behaving differently with nothing to point at.

  Verified by sending one variable named `BAD=NAME`: the launch is refused, and the test says so.

  A child holds the values and no capability to the session, so it reads what it inherited and
  cannot change what its parent or its session will see - which is what makes `PATH` reachable by
  `which` without handing anyone a mutable session client.
- [x] **`less.lsexe`**: an interactive pager for a path (and later a pipeline input)
  using the existing PTY/alternate-screen/raw-input contract. Stream large files,
  support line/page/home/end movement, forward/backward fixed-text search, repeat search,
  line numbers, wrap/no-wrap, horizontal scroll and follow mode; resize reflows without
  losing the logical position and every exit path restores the terminal. It is a text
  pager, while P02M0100's `licoview` is the richer standalone file viewer.
  Result (2026-08-14). IT DOES NOT LOAD THE FILE, which is the decision the rest follows from: what
  it holds is a table of line-start OFFSETS built in one pass, plus one screen's bytes at a time
  read back through the same bounded window every other volume tool uses. A pager that read the
  whole file into memory would fail on exactly the file somebody reaches for a pager to read, and
  the index costs eight bytes a line against the line itself. It is also what makes backward
  movement cheap - a forward-only pager is `head` with extra steps, and going back needs either the
  whole file or a way to find a line again.

  A PIPELINE'S OUTPUT IS A DIFFERENT SHAPE AND IS TREATED AS ONE. A stream cannot be re-read, so
  with no path `less` drains its input into memory, bounded, and pages that - and says `(stream)` in
  the status line, with a message before the terminal is taken over when the bound was reached. A
  pager that silently showed the first megabyte of a longer stream would be lying about what the
  command produced.

  Movement (line, page, home, end), forward and backward search with repeat, line numbers, wrap /
  no-wrap with horizontal scroll. A search starts from the line AFTER the current top so repeating
  advances rather than finding the same line forever, and a search that finds nothing leaves the
  view where it was and says so - moving to the end on a failed search loses the reader's place.
  Horizontal movement is accepted only with wrapping off, because with it on every byte of the line
  is already on the screen.

  The terminal is entered through the shared `TerminalGuard`, so every exit path - quit, Ctrl+C, a
  console that went away - restores raw mode, the cursor, mouse reporting and the alternate screen
  through one implementation rather than this program's own idea of what needs undoing.

  `rt::tty_winsize` is new and is how the pager learns its size: over the CONTROL CHANNEL, the same
  capability `tty_set_mode` uses. The conventional way - print a cursor-position query and parse
  what comes back on stdin - makes a program's request indistinguishable from its data and needs the
  answer interleaved with whatever the user is typing; a control channel is a capability the shell
  hands to an interactive foreground job, and a program without one cannot ask. A tool that gets no
  answer chooses 24x80 rather than refusing, because a pager on a silent terminal is still a pager.

  NOT BUILT: follow mode, and resize reflow beyond taking the size once at startup. Both need the
  console to PUSH an event - a file change, a winsize change - and the pager's input loop currently
  waits on the keyboard alone; wiring a second waitable source is the same work for both and is
  where they belong together.

  SCOPED 2026-08-14, and left open with the shape written down so the next round does not
  rediscover it. This is a VERTICAL SLICE through four layers, and the item's own first sentence
  names the reason: the capture contract does not exist.

  The driver is playback-only by construction, not by omission. `driver.virtio-snd` sets up the
  control, event and transmit queues and says so in a comment - "the receive (capture) queue is not
  used" - and `find_output_stream` scans the PCM info array for `direction == D_OUTPUT` and returns
  the first. Capture needs the RX queue set up, an input-stream search beside the output one, and a
  session that submits EMPTY buffers for the device to fill rather than full ones for it to play.
  That last difference is the whole of it: playback hands the device data and waits for it to be
  consumed; capture hands it space and waits for it to be filled, so the used-ring handling and the
  period lifetime are inverted.

  Above the driver: `audio.open-stream` returns a `pcm-stream` whose only ops are `write` and
  `close`, so capture needs its own interface (a `read` that answers a bounded period) and its own
  op - and, per this item, its own LAUNCH-SCOPED GRANT rather than reusing playback's
  `audio-stream`, because "may record" is not "may make a sound" and a manifest that cannot say so
  is a manifest that grants a microphone to anything that beeps.

  Above that, the tool: the WAV ENCODER ALREADY EXISTS - P02M0094 built PCM 8/16/24/32 with
  canonical `fmt` and padded `data` chunks - so `audiorec` is the streaming and the finalisation
  rather than the format. The RIFF/data lengths are patched before commit through the transactional
  writer, which is what makes "abort rather than leave an apparently valid truncated file" the
  default rather than an error path: a session that dies never commits, and what is on the volume is
  what was there before.

  AND IT CANNOT BE VERIFIED HERE, which is why it is not worth building blind. The suite's QEMU
  guest has no audio input to capture, so every layer would be exercised against a device that
  never fills a buffer - and a capture path whose only test is "it did not crash" is a path that
  will be wrong in a way nobody notices until there is real hardware. The honest order is: a
  loopback or synthetic input source in the scenario first, then the slice.

  DONE 2026-08-23, and the sentence above is what decided the shape. THE SYNTHETIC SOURCE CAME
  FIRST: the test guest now carries `virtio-sound-pci` with QEMU's `none` audio backend, which is
  not a disabled device but a source that fills a capture period with silence on the device's own

  THE SLICE, THROUGH FOUR LAYERS:

  - `driver.virtio-snd` gained the receive queue, an input-stream search beside the output one, and
    the capture lifecycle. The direction is the whole difference: playback hands the device a period
    it may READ and waits for it to be consumed; capture hands it SPACE it may WRITE and waits for
    it to be filled, which is one flag per descriptor and an inverted wait. Its service protocol has
    three message shapes now - a period to play, an empty message that ends playback, and a one-byte
    command - documented in full beside the constants, because a third shape a reader has to infer
    is a protocol nobody can maintain.
  - `audio.open-capture` returns a `pcm-capture` whose `read` answers one converted period, so a
    recorder that stops asking stops the flow. The engine stays event-driven: a `read` with no period
    ready is DEFERRED exactly as a `write` with no capacity is - the raw request is kept, a period is
    asked for, and the request is re-dispatched when the answer lands - so capture never blocks an
    unrelated client's RPC. Conversion is the existing `Remix` and `Resample`, in that order, because
    the resampler is built for the output channel count.
  - `audio-capture` IS ITS OWN GRANT, minted through `audio-admin.open-captures`. A connection from
    it may record and may not `beep` or `open-stream`; a playback connection may not record. That is
    the item's own sentence made true: a manifest that could only say `audio-stream` would hand a
    microphone to anything that beeps.
  - `audiorec.lsexe` holds the volume bundle and the capture grant and nothing else. It writes
    through a storage TRANSACTION - `open-writer` / `write` / `write-at` / `commit` - which is what
    makes "abort rather than leave an apparently valid truncated file" the default rather than an
    error path: the RIFF and `data` lengths are patched by `write-at` before the commit, and a run
    that is interrupted, refused or loses the device never commits at all. It stops at `--seconds`
    or at RIFF's 32-bit ceiling, whichever comes first, and refuses a `--seconds` past that ceiling
    before it records rather than after.

  WHAT IS MEASURED, AND WHERE. The device path is asserted against the real device
  (`kernel.hardware.virtio_snd_driver_captures_a_period_from_the_device`): a period comes back, it
  is 2048 bytes, it IS silence, and a second period follows - so a driver returning stale playback
  bytes or a short buffer fails, and so does a machine that starts producing real audio, which is
  the right way to find that out. The sample values are asserted where they can be
  (`kernel.applications.audiorec_records_a_capture_stream_and_never_publishes_a_failed_one`): known
  periods with DIFFERENT VALUES PER CHANNEL go through the whole conversion into a file, so a mono
  recording distinguishes the average from either channel - a downmix that quietly kept the left one
  would pass against a signal that is the same on both. Breaking that downmix was watched to turn
  the test red. `harness/scenarios/audio-capture.toml` joins the two on a booted system, through
  PermissionManager and the shell.

  AND IT FOUND SOMETHING ON THE WAY, which is the part of this item worth reading twice. On a booted
  machine `audiorec` printed nothing at all - and so did `play`, `watch` and `less`. NO INTERACTIVE
  TOOL COULD BE LAUNCHED FROM THE SHELL, and none of them said so, because a launch that never
  happened has nothing to report. The cause: a foreground job is handed the terminal, which the
  shell does by DUPLICATING its console, and the plan-based bootstrap narrows a client role to send,
  receive, wait and transfer - a ceiling with no `duplicate` in it. `duplicate` was refused,
  `run_tool_interactive` returned false, and the shell went straight back to the prompt.
  It is fixed where it belongs: a role may declare `handed_on`, which means the holder passes this
  channel on and therefore may duplicate it, and the shell's `CONSOLE` role declares it. Not a right
  handed to every client in the system - a decision about one channel, written at that channel. The
  ceiling stays what it was for everything else.

  NOT DONE, and named rather than left as a gap: AIFF output. The item says it waits for a real AIFF
  encoder and is not claimed as reuse of the decode-only leaf - P02M0094 has written one since, so

  and propagate downstream closure/cancellation instead of buffering indefinitely.
  Result (2026-08-14), built as P02M0102's fan-out probe and finished here. One input, several
  outputs, which is where a bounded stream stops being theoretical: it blocks on whichever consumer
  is slowest, and the block IS the backpressure - a `tee` that buffered instead would turn a slow

  writer exactly as `redirect_out`'s do, so a destination is published only when the input ends

  THE DEFAULT FAILURE POLICY IS THE OPPOSITE OF THIS ITEM'S TEXT, deliberately, and both are built.
  `--fail-fast` is there; the default is continue. The reason is what the line MEANS: `cmd | tee log
  | grep error` is a line somebody typed to see the output, with the log as a side effect, and
  ending the pipeline because the log could not be written silently turns it into a different
  command. Failing fast is right when the FILE is the point - a recording somebody will read later -
  which is what the flag is for. Under `--fail-fast` a destination that cannot be OPENED ends the

  Pinned by `kernel.applications.a_fan_out_stage_with_an_unwritable_destination_still_carries_the_stream`,

- [x] **`watch.lsexe`**: repeatedly launch a governed command through PermissionManager,

  Result (2026-08-14). The last clause is the design rather than a constraint on it: `watch` is

  ONE CHILD AT A TIME, and the interval is when the next run STARTS rather than how long to wait
  after the last one ended - so a run that overruns simply delays the next and is never overlapped.

  start of the run, so the display ticks at the interval rather than at the interval plus however

  THE OUTPUT GOES TO A CHANNEL, not to the terminal, which is what lets the screen be redrawn whole

  says now, and a buffer that filled up and then ignored the rest would freeze the display on the

  running" and the loop goes on. `watch` was given authority to START the command and nothing more;

  can interrupt it themselves.

  The interrupt is CAUGHT rather than left to kill the process, and armed before the alternate
  screen is entered so there is no window in which Ctrl+C leaves the terminal switched. Every exit

  Result (2026-08-14). `network.probe(addr, ttl)` is the operation, and "the tool never receives raw
  NIC access" is what it exists for: a traceroute is conventionally a program holding a raw socket -
  ambient authority over every packet the machine sends and receives - handed out to discover a
  route. The service owns the interface and the caller owns one question, "who discards a datagram
  that lives this long", and cannot ask a different one.

  THE STACK LEARNED TO READ TWO ICMP ERRORS. Type 11 (time exceeded) and type 3 (unreachable) are
  new `Event`s, and each carries the SEQUENCE NUMBER RECOVERED FROM INSIDE THE ERROR. An ICMP error
  quotes the datagram that caused it - its IP header and the first eight bytes after, which for an
  echo are the identifier and sequence we sent - and that quote is the only thing tying an answer to
  a probe: several probes are in flight and every router answers from its own address, so without it
  a reply cannot be attributed to a hop. A traceroute that accepted the first error to arrive would
  draw a plausible route that is not the route. Every length in the quote is checked against the
  buffer, because it is data from the network describing the shape of data from the network.
  `build_icmp_echo_ttl` takes the TTL as a parameter and the old builder delegates to it with 64 -
  two builders differing in one byte are two things that can drift.

  FOUR OUTCOMES, KEPT APART, because they say different things about the path: a hop answered, the
  destination answered (which ends the trace), somebody refused (`!`, an answer saying the path is
  blocked), or nothing came back (`*`, silence - a router configured not to report itself, which is
  a choice and not a fault). A refusal is a ROW and not an ending: the next hop may well answer, and
  stopping at the first `!` would report a path shorter than the one that exists.

  burst - several probes over thirty hops sent as fast as possible is aimed at a path somebody else

## How this was verified, 2026-08-23

The three items that were open close on evidence at three levels, because no one level can carry
this: the device path can only be shown against a device, the sample values can only be shown
against known input, and the two are only joined on a booted system.

- **The device.** `kernel.hardware.virtio_snd_driver_captures_a_period_from_the_device` runs the
  REAL driver against the REAL virtio-sound device the test guest now carries, on all three targets.
  A period comes back, it is 2048 bytes, it IS silence - which is what QEMU's `none` backend
  produces - and a second period follows, so the used ring is shown to advance rather than to answer
  once. A driver returning stale playback bytes, a short buffer or uninitialised DMA memory fails
  that, and so would a machine that started producing real audio, which is the right way to find out.
- **The samples.** `kernel.applications.audiorec_records_a_capture_stream_and_never_publishes_a_failed_one`
  feeds known periods - DIFFERENT PER CHANNEL, so a mono recording distinguishes their average from
  either of them - through AudioService's conversion, `audiorec`'s encoder and a storage transaction
  into a file, and reads that file back with this tree's own WAV decoder. Both shapes are covered:
  8 kHz mono, where the audio is remixed and resampled, and 48 kHz stereo, where it is neither and
  the interleaving is what is under test. Breaking the downmix was watched to turn it red.
- **Every architecture.** x86_64 313, aarch64 301, riscv64 301, all green, and all twenty-eight
  gates with them. The two tests above run on all three, so the capture path is exercised against
  the aarch64 and riscv64 PCI backends - which assign their own BARs and deliver their interrupts
  differently - and not only against the one where the firmware does that work.
- **The machine.** A booted x86_64 system, driven through its serial console:
  `audiorec -r 8000 -c 1 -s 1 -f take.wav` answers
  `8000Hz/1ch/16-bit 8000fr duration=1000ms bytes=16044 dropped=22 peak=172` - the same numbers the
  suite asserts - `wc` finds the file at that length, `audioconv` converts it to FLAC and to Ogg
  Vorbis, and `play take.flac` reads it back as `FLAC 8000 Hz, 1 channel, 8000 frames`. That run is
  what `harness/scenarios/audio-capture.toml` performs as a scenario.

  THE SCENARIO HAS NOT BEEN EXECUTED AS A SCENARIO, and that is worth saying plainly rather than
  leaving for somebody to discover. `lab.py scenario-cold` boots the DEVELOPMENT profile, and that
  profile does not currently reach a shell: it had not compiled since `permission.run` gained its
  environment parameter, so nothing had built it, and with the two compile errors fixed the boot
  still stops after DeviceManager with "no interactive shell after 300 rounds". That is a
  pre-existing breakage in the development agent's own bootstrap and it is not this milestone's -
  the ordinary profile boots and was driven. Every step in the scenario file is a command that was
  typed into a booted system and an answer that came back, so the file records a run that happened;
  what has not happened is the runner replaying it.

  ONE THING THE SCENARIO HAD TO LEARN FROM THAT RUN: every path in it is RELATIVE. The console's
  line discipline has a finite input buffer, and a command line past it is truncated where it
  stands - the shell then runs whatever the first part happened to spell, which is how
  `audioconv vol://system/scenario-take.wav vol://system/scenario-take.flac` became
  `audioconv: invalid options`.

TWO THINGS THAT ONLY THE BOOTED MACHINE COULD HAVE FOUND, both of them pre-existing and both now
fixed: no interactive tool could be launched from the shell at all (the console role carried no
right to duplicate - see the `audiorec` item), and `audioconv` had no PermissionManager policy row,
so the tool existed on the volume, was exercised by the suite, and could not be launched on a real
system by any means. Both are the same shape of gap: a path the suite reaches by another door.
