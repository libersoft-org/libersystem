# P02M0162 - A bind that fails part-way leaves the parts that succeeded

Status: COMPLETE (2026-09-09) — scoped repairs and regression verification complete; the unchanged dynamic-report baseline failure is recorded below.

This is the transactional binding slice of P02M0098's seven-milestone programme. The latest
reviewed audit is `AI/audit/audit-M0162.md`, 2026-09-08T19:54:23Z, finding 1. M1, M3 and M7
were reopened for that finding and are now verified. The other requirements retain their existing
implementation. The final validation section below records this repair; earlier reports remain historical.

## Goal and scope

Make binding one operation that either completes or relinquishes everything it acquired. If
containment or teardown cannot be confirmed, the kernel keeps the device quarantined and its
resources charged and unavailable for the boot; the manager must report that same terminal fact,
including when the claim syscall failed before returning any handles.

Each stable device node orders its own generation-stamped events. A crash racing a rebind must
not double-spawn, double-close, release another generation's claim, or strand a claim. Kernel
claim authority belongs to P02M0098/P02M0153, driver framing to P02M0161, discovery to P02M0163,
providers/dependencies to P02M0164, watchdog/planned stop to P02M0165, and policy/rendering to
P02M0166. This plan retains those boundaries and the current architecture.

## Current architecture and repaired gap

- `src/user/services/core/src/device_manager.rs` owns stable `Node` records, each with an optional
  live `Binding`, unpublished offers, candidate cursor, incident deadlines, queue and optional
  `Teardown`. Bring-up and standing supervision multiplex these through the central wait/reducer.
- `src/user/libs/driver/binding/src/lib.rs` owns the shared state/cause vocabulary, transition
  predicate, generation-filtered queue, attempt/window decisions and `Holdings`/`Pending` ledger.
  These production decisions are host-testable without starting the `no_std` service binary.
- `begin_bind` checks the artifact's protocol note, enters `Binding`, observes kernel claim state,
  admits the attempt, then calls `device_claim`. A successful grant immediately puts both the
  Claim and MMIO handles in `Holdings::claimed`, before any other fallible acquisition.
- `src/kernel/device.rs::claim` can change `Free` to `Quarantined` while ATTACH is unanswered,
  retaining the attempted generation without publishing a claim handle. `claim_errno` maps this
  and generation retirement to `ERR_UNSUPPORTED`; the errno alone cannot identify quarantine.
- `begin_bind` now refunds an unclaimed attempt and takes a fresh error-result snapshot before
  choosing the failure cause. Both pre-claim and post-error observation use `observe_claim_snapshot`
  to adopt quarantine, generation and charged counts. `resolve_teardown` preserves that terminal
  state after empty local cleanup. Non-quarantine and missing snapshots retain errno classification.
- Kernel snapshots already expose state, generation and charged resource counts. The existing
  `Binding -> Quarantined` transition and `TeardownUnconfirmed` cause are sufficient. No new
  syscall, state, errno, worker or kernel attachment algorithm is needed.

## Work and preserved requirements

- [x] **M1 — staged bind and idempotent rollback; verified 2026-09-09.** Acquire claim,
  resources, bootstrap endpoints, child Domain and process through one transaction. Hand the
  remaining ownership to the installed Binding for handshake supervision; count the bind as
  successful and publish its held offers only after the correct-generation READY. Until ownership
  transfers, the transaction owns both channel ends and every unsent grant; a successful transfer
  removes only the transferred handle from its ledger. It holds the MMIO grant alongside the Claim immediately after a successful syscall.
  Release the ELF mapping after `spawn`, since the kernel loader copies the image during that
  syscall. A failure unwinds exactly the resources acquired, in reverse-safe order. Confirmed
  rollback lands in `Backoff` or `Failed` with its cause; unconfirmed kernel ownership lands in
  `Quarantined`, even if no handle reached userspace. R1 below closes that last case.

- [x] **M2 — one ordered queue per stable device node.** The queue outlives individual bindings;
  every binding event names its generation. Reject stale frames and close transferred handles
  carried by rejected frames. A duplicate terminal event has no lifecycle or retry effect.
  Refuse the newest event when the eight-event queue is full, preserving earlier ordering.
  `drain_channel` consumes at most 64 raw receive attempts per pass, including malformed and
  stale traffic, then returns to other nodes and deadlines. Preserve this bound while P02M0165
  corrects heartbeat admission. Backoff is a deadline in the central loop, never a per-node sleep.

- [x] **M3 — one record containing both state and cause; verified 2026-09-09.** Retain
  `BindingRecord { state, failure, generation, attempts, .. }` in `driver-binding`, with the
  existing `BindingState` variants `Unbound, DependencyPending, Disabled, Binding, Online,
  Stopping, Backoff, Failed, Quarantined`. There is no `Removed`, because discovery does not rescan.
  Use the transition table below, check rejected transitions at production call sites and log
  them. State is separate from cause; kernel quarantine is not an ordinary failed candidate.
  R1 retains the shared state machine and existing operator retry authority.

  | From | To | Condition |
  | --- | --- | --- |
  | `Unbound`, `DependencyPending` | `Binding` | selected candidate is eligible and the transaction opens |
  | `Unbound`, `DependencyPending`, `Backoff` | `Failed` | permanent pre-attempt failure, such as missing artifact or incompatible protocol note |
  | `Binding` | `Online` | current-generation READY received before its own deadline |
  | `Binding` | `Backoff` | no claim taken, retryable failure or bounded wait for an earlier release |
  | `Binding` | `Failed` | no claim taken, permanent refusal or exhausted budget |
  | `Binding` | `Stopping` | acquired resources require teardown |
  | `Binding` | `Quarantined` | snapshot reports kernel quarantine before or after the attempted claim; adopt state, cause and generation |
  | `Online` | `Stopping` | exit, channel closure, watchdog expiry or planned stop |
  | `Stopping` | `Backoff` | confirmed fault teardown with automatic allowance and time left |
  | `Stopping` | `Failed` | confirmed fault teardown with permanent cause or no budget |
  | `Stopping` | `Quarantined` | teardown not confirmed |
  | `Backoff` | `Binding` | due retry, with requirements and both budgets rechecked |
  | `Backoff` | `Failed` | absolute incident window expired |
  | `Failed` | `Binding` | one permitted operator retry, with requirements satisfied |
  | `Unbound`, `Binding`, `Backoff`, `Stopping`, `Failed` | `DependencyPending` | P02M0164's dependency gate or confirmed dependency-loss stop; held resources first pass through teardown |
  | `Unbound`, `DependencyPending`, `Binding`, `Backoff`, `Stopping`, `Failed` | `Disabled` | P02M0166's disable; held resources first pass through teardown |
  | `Disabled` | `Unbound` | operator enable, preserving spent automatic attempts |
  | `Quarantined` | — | terminal for the boot, including operator requests |

  The dependency and disable rows summarize the existing shared enum extensions owned by
  P02M0164/P02M0166. An Online binding reaches them through `Stopping`, never by relabelling
  live holdings. Anything outside the shared transition predicate is refused. A duplicate event
  does not create a self-transition. `record_failure` may refresh the cause of an already Failed
  pre-attempt record, and covers `Unbound`, `DependencyPending`, `Backoff` and `Failed`; it must
  not overwrite Online, Disabled or Quarantined. A mixed candidate list records the last concrete
  failure, not an earlier missing-artifact flag.

  | Cause | Automatic retry classification |
  | --- | --- |
  | `driver-missing`, `protocol-mismatch`, `claim-refused`, `iommu-required`, `resource-exhausted` | permanent |
  | `spawn-failed`, `handshake-timeout`, `driver-exited`, `hung` (P02M0165) | retryable within both budgets |
  | `DriverReported(DriverFailureCode)` | retain the actual code and its shared retryability decision |
  | `teardown-unconfirmed` | quarantine takes precedence; retry is never considered |
  | `stopped` (P02M0165) | planned outcome governed by `StopIntent`, not automatic fault retry |

  For a non-quarantined claim refusal, preserve `ERR_ACCESS_DENIED -> IommuRequired` and the
  existing ordinary refusal classification for other errors. `artifact-mismatch` remains outside
  this vocabulary until a milestone builds its digest check; this repair introduces no new cause.

- [x] **M4 — short userspace transitions and one central `wait_any`.** A binding retains its
  Process handle after spawn. The rollback sequence remains:

  1. Kill the process without depending on driver cooperation, retaining the Process handle
     until exit is confirmed or the teardown deadline expires.
  2. Close the manager's bootstrap endpoints and all untransferred resource handles exactly once.
  3. Release the actual owned claim by its full ClaimKey. Kernel containment removes bus mastering,
     revokes derived authority, masks interrupts and confirms IOMMU teardown. This call is
     intentionally synchronous; `iommu::detach_for` has a spin budget and a 20-tick deadline.
     Do not replace it with an asynchronous kernel worker in this milestone.
  4. Settle the Process exit and claim terminal result through `Pending`. The claim may already
     have answered in the syscall; otherwise retain its waitable handle. After both confirmations
     or expiry, close retained handles and kill/close the child Domain. Only confirmed release
     permits resource reuse; unconfirmed teardown quarantines it.

  An empty local ledger needs no process exit or claim release. Its successful cleanup proves
  only that this manager owns nothing, not that a separately observed kernel quarantine is Free.
  R1 preserves that distinction at settlement.

  Both bring-up phases and standing supervision must advance queued events and completed
  zero-handle teardowns before waiting or reporting no work. Earlier-phase teardowns remain
  supervised in later phases. Include pending handshakes, Process/Claim confirmations, due
  backoffs and the earliest relevant deadline. Omit already-confirmed, persistently ready handles;
  keep deadlines for unconfirmed zero-handle teardowns. Respect `MAX_WAIT_HANDLES`, retaining
  rotating admission and the one-tick fallback for omitted handles. A timer wake checks each
  owner's deadline and cannot expire an unrelated handshake.

- [x] **M5 — bounded automatic attempts, incident windows and teardown reserve.** Keep READY's
  two-second maximum from BIND, three automatic admitted claims per node per boot, and the two
  backoffs of 100 ms and 200 ms. Registry policy may lower supported limits, never raise them.
  Admission reserves an automatic attempt before `device_claim` and refunds that reservation
  only when no grant was returned; previously spent attempts survive candidate changes, READY,
  later faults and operator enable. A refused claim that leaves kernel quarantine still ends the
  node regardless of that refund. `record.attempts` counts successful claim admissions, not phantom
  claims created to represent quarantine.

  One operator retry out of an eligible Failed node grants one further claim, with its own fresh
  incident window and no automatic backoff chain. Missing artifacts or unclaimed refusals may
  move to a fallback under that unspent grant; a successful admission consumes it. No operator
  action clears quarantine or refills the automatic allowance.

  Use one absolute incident deadline across candidates and backoffs. The kernel publishes its
  own outer deadline and duration in monotonic ticks, and enforces that deadline both while
  draining runnable threads and while waiting. ServiceManager retains the duration and passes
  the original deadline only to the first DeviceManager. Current target inputs are 3,000 ticks
  for x86_64, 4,000 for aarch64 and 40,000 for riscv64; these are the current `boot_userspace`
  arguments, not the obsolete 300/400/4000 settle-round counts. This repair changes none of them
  and makes no new hardware timing claim.

  An incident receives one third of the outer duration; one third of its actual allotted slice
  is reserved for teardown. Clamp only to an original boot deadline still ahead of now. With no
  published duration, retain the per-attempt limit and the 200-tick teardown fallback. An opened
  bit prevents a failed candidate or expired window from opening another window. READY ends the
  incident; an actual later Online fault opens the next incident without refunding boot attempts.
  Do not enter a backoff that consumes the remaining bind slice. Reset the previous stop intent
  to Fault before the next Binding transition so dependency recovery cannot bypass these limits.

  Latch READY's deadline at BIND. Accept a READY only when its per-frame receipt tick is strictly
  earlier; reading it at or after expiry cannot commit, even if draining began before expiry.
  A timely queued frame retains its order when processed later. Preserve the existing before/at/
  after/cross-tick, stale-frame and saturation regression coverage.

- [x] **M6 — a small, explicit bootstrap exception.** Pin into `init.pkg` if and only if a driver
  is boot-critical for mounting the system volume. Discover first and launch no driver for absent
  hardware. Retain registry-build refusals both for a boot-critical artifact staged on the volume
  it must mount and for an unnecessary noncritical artifact pinned into the package.

- [x] **M7 — production fault and invariant coverage; verified 2026-09-09.** Keep
  existing ledger tests for every acquisition failure, crash during bind, crash after Online,
  stale exit racing replacement, silent handshake, unconfirmed release, and repeated rollback.
  Assert one claim owner at most, no leaked local process/handle/accounting, and quarantine charges
  retained when reuse is unconfirmed. Keep queue ordering/generation negative controls, standing
  recovery/operator-budget scenarios, completed rollback/earlier-phase progress tests and the
  continuously replenished channel test. The syscall-result composition cases in R1 are registered and pass; passing
  pure ledger tests alone cannot establish that the manager classifies the kernel result correctly.

## R1 — adopt quarantine created inside a failed claim (implemented and verified 2026-09-09)

1. **Record kernel state after a failed claim, before classifying errno.** In `begin_bind`, take
   one fresh `device_claim_snapshot` on the error path, before choosing the ordinary failure cause.
   Apply this to claim errors generally: `ERR_UNSUPPORTED` also means generation retirement, and
   a later kernel grant-construction rollback can return another errno after containment failed.
   Use the existing snapshot ABI; no polling or new wait is needed for this observation.
2. **Share quarantine adoption with the pre-claim observer.** Factor or reuse the existing
   quarantine handling in `observe_claim`, without treating its missing-snapshot/Bindable result
   as a new successful claim. When an actual snapshot says Quarantined, check the legal
   `Binding -> Quarantined` move with `TeardownUnconfirmed`, adopt its generation in both
   `node.record.generation` and `node.id`, and retain the existing snapshot-derived resource
   accounting. Log the observed terminal state. Do not call `claim_admitted`, fabricate a
   ClaimGrant, populate the transaction with an unowned handle, or release by a guessed key.
   With an unavailable or non-quarantined snapshot, retain the existing errno-based refusal
   behavior; absence of a snapshot neither grants a claim nor proves quarantine. The pre-claim
   Free/Releasing/Claimed paths retain their existing semantics.
3. **Keep caller progression and settlement consistent.** Retain the existing unclaimed-attempt
   refund and the existing zero-holding `give_up_retryable`/`Pending` route for an adopted
   quarantine, carrying `TeardownUnconfirmed`. This lets both initial boot launch and
   `start_candidate` return while the pending cleanup is settled by the central loop. In
   `resolve_teardown`, finish actual local ledger cleanup, then explicitly preserve an already
   Quarantined record and return Quarantined; do not attempt `Quarantined -> Failed` merely
   because an empty ledger returned `Settled::Free`. `advance` must return `Step::Done` so no
   fallback candidate is tried. Repeated advancement is inert. No retry deadline, claim wait,
   replacement spawn or new incident is scheduled. Existing `decide_retry`/policy handling must
   return the quarantine refusal without changes to operator policy.
4. **Add a production composition regression to the registered driver-event-dispatch coverage.**
   Extend an existing production extraction or a focused fixture registered through that gate;
   execute the real claim-error branch, quarantine observer/adoption, syscall adapter,
   `Attempt`/`Holdings`/`Pending`, settlement, candidate progression and retry decision, with
   controlled snapshots and syscall outcomes. Do not replace the manager's classification with
   a fixture-only model. Cover:

   - Free before claim; claim returns `ERR_UNSUPPORTED`; the following snapshot is Quarantined
     at the attempted generation. After cleanup, state/cause/id/accounting match that snapshot,
     there are no locally owned handles, and no kill, release or spawn is issued.
   - One candidate and multiple fallback candidates, both initial and standing paths; an existing
     spent automatic budget is preserved, the current unclaimed reservation is refunded exactly
     once, and a manual grant cannot cause another acquisition on the quarantined node. Exercise
     the actual operator retry handler and assert its quarantine outcome.
   - Already-quarantined pre-claim snapshot; repeated settlement/advance; both retain the same
     terminal record and never attempt an illegal transition or double-close anything.
   - Non-quarantined `ERR_UNSUPPORTED` (retirement), ordinary claim refusal, access denial,
     unavailable post-error snapshot, and a successful claim. They retain their established
     classification/ownership rules; a resource-error rollback whose snapshot is Quarantined
     still adopts quarantine. Keep the existing bounded pre-claim Releasing wait case.

   The critical negative control restores the old claim-error classification and must fail on
   `Failed / claim-refused` and its granted operator retry. A settlement negative control must
   detect attempting to demote adopted quarantine or resuming fallback acquisition.
5. **Validate and close only after implementation.** Run driver-binding and driver-protocol host
   suites and the registered driver-event-dispatch/progress and IOMMU protocol gates. Build the
   affected manager for x86_64, aarch64 and riscv64. Use the existing x86_64 enforcing-IOMMU boot
   and development driver recovery checks for integration; keep the controlled syscall case as
   the proof of this specific boundary rather than claiming a new hardware failure injection.
   Review all changed paths against M1–M7, then run documentation/index and whitespace checks.
   Record actual results and any failures before marking M1/M3/M7 and this milestone complete.

Implementation checkpoint: `begin_bind` now reads a fresh snapshot on each claim error and shares
`observe_claim_snapshot` with pre-claim observation. `resolve_teardown` preserves adopted quarantine
after local cleanup. The new registered `check-device-claim-result.py` executes the production claim
stage, observer, ownership/settlement and caller/policy decisions: four scenario groups and three
negative controls pass. Its effects are controlled syscall boundaries; this is not guest or hardware
validation. Final build and integration results are recorded below.

## Definition of done

- Every failed acquisition closes exactly what reached this transaction. A kernel-quarantined
  device is reported as Quarantined with its observed generation and `teardown-unconfirmed`,
  even when the manager never received a claim handle; kernel-held resources remain unavailable.
- Duplicate/stale events cannot affect a replacement, and one driver's delay or continuously
  refilled control channel cannot prevent other nodes' lifecycle work.
- State transitions, causes, attempt accounting, fallback selection and operator policy agree:
  quarantine is terminal for the boot, while confirmed retryable faults use the existing budgets.
- Both bring-up phases and standing supervision finish cleanup without waiting on a driver;
  actual unconfirmed resources follow the shared quarantine path.
- Existing M2/M4/M5/M6 coverage remains valid and the new M7 composition regression fails against
  the old behavior. Plan completion is separate from implementation/test completion.

## Explicit exclusions and validation limits

No actor framework, general scheduler, asynchronous kernel release worker, new claim ABI, new
failure vocabulary, discovery rescan/removal test, digest-verification mechanism, or physical
hardware qualification is introduced. Watchdog receipt and development-control backpressure
repairs remain in P02M0165; provider identity/routing repairs remain in P02M0164. Suspend/resume
and a new DeviceManager restart mechanism are outside this repair. ServiceManager currently
escalates a lost DeviceManager; P02M0165 documents the volume-driver reconstruction cycle, so the
retained boot-window duration is verified at its existing handoff/arithmetic boundaries without
claiming an unavailable live restart drill.
