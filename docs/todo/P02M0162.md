# P02M0162 - A bind that fails part-way leaves the parts that succeeded

Status: PLANNED AFTER P02M0161. TRANSACTIONAL BIND AND THE BINDING STATE MACHINE. THIRD OF SEVEN - see P02M0098.

## Goal

Make binding one operation that either completes or leaves nothing, and give each binding one place
where its events are ordered - so that a crash racing an unplug cannot double-spawn, double-free or
leave a device claimed by a process that is gone.

## What is there now

- **BIND IS A SEQUENCE OF STEPS THAT EACH SUCCEED SEPARATELY.** `launch_one` maps the ELF, spawns the
  process, hands over the device capability and waits for a report. A failure part-way leaves
  whatever the earlier steps did: the claim taken, the process running, the capability handed over.
  `check-qemu-virtio-iommu`'s own boot showed the shape of it - a driver that failed after attaching
  left three frames quarantined, and only because P02M0153 made the teardown say so.
- **THERE IS NO STATE MACHINE.** `state[idx]` is a small integer set at a few points. There is no
  event queue, so a driver exit arriving while a rebind is in progress is handled by whatever code
  happens to be running.
- **AND THE LOOP BLOCKS ON ONE DRIVER.** `launch_one` calls `recv_blocking`, so a driver that never
  answers stops DeviceManager itself and every other device waits behind it.
- **THE PROCESS HANDLE IS DROPPED AFTER `spawn`.** Nothing holds it, so nothing can end the process a
  failed bind started - which is what makes "leaves nothing behind" untrue in the one case it is
  written for.
- **SUPERVISION ENDS AT THE ONLINE REPORT.** After a driver says it is up, nothing watches it. A
  crashed driver's device stays claimed by a process that no longer exists.

## Work

- [ ] **M1 - bind is staged and rolls back.** Claim, resources, spawn, handshake - and a failure at
  any step undoes the ones before it in reverse: the process stopped, the handles closed, the
  accounting returned, the claim released, the node left `unbound` or `failed` with the reason. The
  rollback is idempotent, because an interrupted rollback is the case that leaves the mess.

- [ ] **M2 - one ordered queue per device node, not per binding.** Discovery happens before a binding
  exists and removal after it is gone, so a queue owned by the binding has nowhere to put the two
  events that matter most. The queue belongs to a stable device node holding `Option<Binding>`, and
  every binding event carries the generation it is about. Two nodes are independent; one node never
  handles two events at once.

- [ ] **M3 - the record is a state AND a cause, and the transition table is written down.**
  `BindingRecord { state: BindingState, failure: Option<FailureCause>, .. }` where `BindingState` is
  `Unbound, Binding, Online, Stopping, Backoff, Quarantined, Removed`. A state and a reason are not
  alternatives - "quarantined" and "hung" are two halves of one answer - and a graph with a hole in
  it is one that gets closed by whoever hits the hole first, so the allowed transitions are a table.
  Defined HERE rather than where it is finally rendered, because five milestones would otherwise each
  invent their own numbers and strings. A duplicate event is idempotent.

- [ ] **M4 - one `wait_any` loop, and the binding owns the process handle.** Short non-blocking
  transition steps driven from one central wait, so no driver can block the manager - an actor
  framework is not needed and is not wanted. The `Binding` owns the process handle from `spawn`, and
  rollback is: end the process and confirm the exit, close local handles, confirm P02M0098's
  teardown, and release the claim LAST, because the claim is what keeps the device quiet.

- [ ] **M5 - the deadline and the backoff are numbers, so they are written down.** A `READY` deadline,
  a retry limit and backoff constants, with the retry and quarantine counter owned here. P02M0165
  reuses this path for a hang rather than adding a second one.

- [ ] **M6 - the bootstrap exception stays small and explicit.** Only the drivers needed to mount the
  system volume live in `init.pkg`; DeviceManager still discovers hardware before launching them and
  starts none for absent hardware. A staged driver needed to reach the volume that contains it is a
  cycle, and is refused at registry-build time rather than at boot. The checker exists; this item is
  a regression test for it, not a second implementation.

- [ ] **M7 - the fault cases are the tests.** Crash during bind, crash after online, exit racing a
  restart, removal racing a bind, a driver that never answers. After each: one claim owner at most,
  no leaked process, handle or accounting, and a state the event log explains.

## Definition of done

- A bind that fails at any step leaves no claim, no process, no handle and no accounting behind, with
  a test per step.
- Each device node handles one event at a time, duplicate events change nothing, and a slow driver
  cannot stop the manager from serving another.
- A binding's record carries both where it is and, when it failed, why - and the transitions it took
  to get there are the ones the table allows.
- A driver that crashes after reporting online loses every resource it was granted and is rebound or
  quarantined by a declared policy.
- The states and their legal transitions are written down and enforced, not implied by the code.
- A dependency cycle through the system volume is refused when the registry is built.

## What this milestone refuses, and why

- **An actor framework or a general scheduler for DeviceManager.** One queue per binding is a queue,
  and the thing being fixed is that events are handled wherever they arrive.
- **Detecting hung drivers.** A driver that exits is a different problem from one that stops making
  progress, needs a heartbeat the protocol does not have yet, and is P02M0165's.
- **Suspend and resume.** Planned stop is the same milestone as the watchdog, for the same reason.
