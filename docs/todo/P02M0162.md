## Goal

Make binding one operation that either completes or leaves nothing, and give each binding one place
where its events are ordered - so that a crash racing a rebind cannot double-spawn, double-free or
leave a device claimed by a process that is gone. "Either completes or leaves nothing" has one stated
exception and it is deliberate: a teardown that could not be CONFIRMED leaves the device's resources
charged and quarantined, because the alternative is handing back frames a device may still be writing
to.

## What is there now

- **BIND IS A SEQUENCE OF STEPS THAT EACH SUCCEED SEPARATELY.** `launch_one` maps the ELF, spawns the
  process, hands over the device capability and waits for a report. A failure part-way leaves
  whatever the earlier steps did: the claim taken, the process running, the capability handed over.
  `check-qemu-virtio-iommu`'s own boot showed the shape of it - a driver that failed after attaching
  left three frames quarantined, and only because P02M0153 made the teardown say so.
- **THERE IS NO STATE MACHINE.** `state[idx]` is a small integer set at a few points. There is no
  event queue, so a driver exit arriving while a rebind is in progress is handled by whatever code
  happens to be running.
- **AND THE LOOP BLOCKS ON ONE DRIVER.** `launch_one` calls `recv_blocking`, so a driver that never
  answers stops DeviceManager itself and every other device waits behind it.
- **THE PROCESS HANDLE IS DROPPED AFTER `spawn`.** Nothing holds it, so nothing can end the process a
  failed bind started - which is what makes "leaves nothing behind" untrue in the one case it is
  written for.
- **SUPERVISION ENDS AT THE ONLINE REPORT.** After a driver says it is up, nothing watches it. A
  crashed driver's device stays claimed by a process that no longer exists.

## Work

- [x] **M1 - bind is staged and rolls back.** MET AGAIN (2026-08-29) - see the audit sections at the end of this file. Claim, resources, spawn, handshake - and a failure at
  any step undoes the ones before it in reverse: the process stopped, the handles closed, the
  accounting returned, the claim released, and the node left in one of the three states M3's table
  allows a failed bind to reach - `Backoff`, `Failed` or `Quarantined` - each with the reason. THE
  RETURNS ARE CONDITIONAL ON A CONFIRMED TEARDOWN and this item first said them without exception:
  reaching `Quarantined` means the teardown was NOT confirmed, and the whole point of that state is
  that its frames, vectors and grants stay charged and out of circulation. "Undoes the ones before
  it" is true of the two paths that end in `Backoff` or `Failed`; the third undoes what it safely
  can and says what it could not. NOT
  `Unbound`, which this item said first: `Unbound` is where a node starts and what invites a bind, so
  a failed bind landing there is a bind that immediately happens again with nothing recorded about
  why the last one did not work. The rollback is idempotent, because an interrupted rollback is the
  case that leaves the mess.

- [x] **M2 - one ordered queue per device node, not per binding.** **MET AGAIN (2026-08-29)** - see the implementer's addendum in the audit file. A binding is not the thing that
  outlives its own events: the exit of a driver arrives while its binding is being torn down, and the
  next binding's `READY` arrives on the same device afterwards - so a queue owned by a binding has
  nowhere to put the events on either side of it, and the two bindings would each have a queue with
  the interesting moment falling between them. The queue belongs to a stable device node holding
  `Option<Binding>`, which exists from the boot scan onward, and every binding event carries the
  generation it is about. Two nodes are independent; one node never handles two events at once.

- [x] **M3 - the record is a state AND a cause, and both are written down here.**
  `BindingRecord { state: BindingState, failure: Option<FailureCause>, .. }`. A state and a reason are
  not alternatives - "quarantined" and "hung" are two halves of one answer - and a graph with a hole
  in it is one that gets closed by whoever hits the hole first, so the transitions are a table.
  Defined HERE rather than where it is finally rendered, because five milestones would otherwise each
  invent their own numbers and strings. A duplicate event is idempotent.

  `BindingState` is `Unbound, Binding, Online, Stopping, Backoff, Failed, Quarantined`. There is no
  `Removed`: nothing rescans, so no removal event exists to enter it, and a state nothing can produce
  is a state every reader has to reason about for nothing. Two more variants are named by later
  milestones and are added by the milestone that first produces one, so that no variant is
  unreachable on the day it appears: `DependencyPending` in P02M0164, where a declared requirement
  first has something to wait for, and `Disabled` in P02M0166, where an operator first has a way to
  set it. They belong to this enum wherever they are added - one enum, in one file.

  | from | to | on |
  | --- | --- | --- |
  | `Unbound` | `Binding` | a driver is selected and the transaction opens |
  | `Binding` | `Online` | `READY` arrives with the current generation |
  | `Binding` | `Backoff` | the transaction failed BEFORE the claim was taken, attempts left |
  | `Binding` | `Failed` | the same, for a reason retrying cannot change OR the attempt budget is spent |
  | `Binding` | `Stopping` | the transaction failed AFTER the claim was taken - there is a device to quieten now, and the only way back is through the teardown |
  | `Online` | `Stopping` | the driver exited |
  | `Stopping` | `Backoff` | teardown confirmed, attempts left |
  | `Stopping` | `Failed` | teardown confirmed, and the failure was one retrying cannot change OR the attempt budget is spent |
  | `Stopping` | `Quarantined` | teardown NOT confirmed - the device may still be live |
  | `Backoff` | `Binding` | the delay expired |
  | `Backoff` | `Failed` | the absolute TIME budget expired - a different budget from the attempt count, which is spent in `Binding` or `Stopping` |
  | `Failed` | `Binding` | an operator retry (P02M0166's), when every declared requirement is published |
  | `Failed` | `DependencyPending` | the same retry, when one is not - retrying straight into a bind gated on a condition nobody re-checked is how an operator gets the same failure twice and learns nothing from it |
  | `Quarantined` | - | terminal for the boot; its resources are never reused |

  Anything not in the table is refused and logged as a transition that was attempted, because a state
  machine that silently ignores an illegal event is one nobody can debug.

  `FailureCause` is `driver-missing`, `protocol-mismatch`, `claim-refused`,
  `iommu-required`, `resource-exhausted`, `spawn-failed`, `handshake-timeout`, `driver-exited`,
  `DriverReported(DriverFailureCode)`, `teardown-unconfirmed` - the driver-reported one CARRYING
  P02M0161's code rather than flattening it away, because "the driver said it failed" without saying
  what it said is a cause that explains nothing. Each variant declares whether it is RETRYABLE, in
  one place, and EVERY variant answers - a flag some variants leave unset is a flag each call site
  guesses at:

  | retryable | not |
  | --- | --- |
  | `handshake-timeout`, `driver-exited`, `spawn-failed`, `hung` when P02M0165 adds it, a `DriverFailureCode` that declares itself retryable | `driver-missing`, `protocol-mismatch`, `claim-refused`, `iommu-required`, `resource-exhausted`, a `DriverFailureCode` that does not |

  `claim-refused` is not retryable because the device is held by somebody else and waiting changes
  nothing this milestone controls; `spawn-failed` is, because it is usually a transient shortage.
  `teardown-unconfirmed` is not in either column: it never reaches the question, because it ends at
  `Quarantined`. The table's `Binding -> Backoff` versus `Binding -> Failed` reads this flag instead
  of each call site deciding again.

  ONE OF THESE HAS NO PRODUCER YET AND THAT IS AN ITEM, NOT A DECORATION. `iommu-required` is
  distinguishable in `dma::BindDecision::Refused` and collapses into a general `ERR_INVALID` by the
  time anything could record it; `artifact-mismatch` names a check nothing performs. Either the path
  that can tell reports a distinguishable error, or the variant goes - a vocabulary with words
  nothing can say is a vocabulary that lies about its coverage. THIS MILESTONE CHOOSES, one each way.
  `iommu-required` stays and gets its producer: `dma::BindDecision::Refused` already knows a driver
  whose policy demands translation was refused on a machine that is not enforcing it, and loses that
  on the way out through a general `ERR_INVALID` - so the work is a distinguishable errno on one path,
  not a new mechanism. `artifact-mismatch` goes: the digest check that would produce it is the
  build-order cycle P02M0161 refuses to close here, so it is a word for something nothing in this
  scope can say, and it comes back with the milestone that builds its producer.
  P02M0165 adds `hung` when it can detect one, and P02M0166 renders the list; none of them extends it
  with a state, because where a binding IS and why it got there are different questions.

- [x] **M4 - one `wait_any` loop, and the binding owns the process handle.** **MET AGAIN (2026-08-29)** - see the implementer's addendum in the audit file. Short non-blocking
  transition steps driven from one central wait, so no driver can block the manager - an actor
  framework is not needed and is not wanted. The `Binding` owns the process handle from `spawn`, and
  rollback is, in this order:

  1. `SIG_KILL` the process - not a request it can decline, because a driver that failed its
     handshake is not a driver whose cooperation is available - keep the Process handle until the
     exit event arrives rather than dropping it, and give the wait a deadline of its own: a child
     that does not exit, and a claim that does not reach `Free`, both end at `Quarantined` rather
     than holding the node open. That deadline is the teardown slice M5 reserves inside the bind
     budget - not "whatever is left", which is nothing when the bind failed by running out of time;
  2. close the manager's own handles to it;
  3. release the claim by its `ClaimKey`, which is what performs P02M0098's teardown: bus mastering
     off, interrupts masked, the IOMMU unmap confirmed. The teardown cannot be confirmed BEFORE this
     step, which is what this item said first - the release is what starts it;
  4. the exit and the claim reaching `Free` arrive as EVENTS on this node's queue while it is
     `Stopping`, and the node leaves that state when both have. A release that does not reach `Free`
     leaves the node `Quarantined` and its resources out of circulation, which is P02M0098 M8's rule
     and not a second one.

  Steps 1 and 4 say "record" and "arrive as events" rather than "wait", and that is the difference
  between this item and the loop it replaces. A rollback that BLOCKS on an exit is `recv_blocking`
  again under another name: one dying driver stops the manager, and every other device waits behind
  the teardown of a device nobody is using.

  BUILT 2026-08-27, and M2 with it - they are one change, because a queue nothing pushes to is dead
  code and this tree refuses a suppression to hide that. `Node { index, record, binding:
  Option<Binding>, offers, incident, candidates, queue }` is created from the boot scan and lives for
  the life of the program; the record used to be a local that died with the loop iteration that made
  it. `pump` builds a wait set of two handles per node in flight - its channel and its process - and
  waits on the SOONEST deadline anywhere, so the first node to run out is the one that wakes it.
  `drain_channel` takes every frame waiting rather than one per wake, and drops any whose generation
  is not the current binding's, closing what came with it. `advance` runs one node's queue and
  answers `Waiting`, `Online`, `Again`, `NextCandidate` or `Done`; routing the providers is the
  caller's, because which provider goes where is a policy this machinery has no business knowing.

  AND THE ELF MAPPING SHRANK FROM A HANDSHAKE TO A SYSCALL. It used to be held for the whole
  attempt, which with a dozen devices in flight would have meant a dozen mappings. `sys_process_load`
  copies the image into a kernel buffer before the loader touches it - so the mapping is released the
  moment `spawn` returns, and concurrency costs one mapping at a time.

  MEASURED: 9 of 9 devices online, four virtio-blk disks bound together in phase 1 where they used to

- [x] **M5 - the deadline and the backoff are numbers, so here they are.** MET AGAIN (2026-08-29) - see the audit sections at the end of this file. A `READY` deadline of 2
  seconds from `BIND`; at most 3 AUTOMATIC bind attempts per node per boot, which is 2 backoffs
  between them, of 100 ms and then 200 ms. An operator `retry` out of `Failed` is not one of the
  three and does not reset them: it grants exactly ONE further attempt, with a fresh incident
  deadline and no new automatic backoff chain behind it. Without that rule the two mechanisms meet in
  the table with nothing said - the limit is three, and there is an edge back into `Binding` - and
  whoever implements it decides for themselves whether an operator can spend the budget again. They are defaults a registry entry may LOWER for a device known to be
  quick - never raise, which is the rule the absolute budget below states and for the same reason: a
  per-entry number that can grow past the global one turns the global one into a suggestion. Not
  constants scattered through the code, and the retry and quarantine counters are owned
  here. P02M0165 reuses this path for a hang rather than adding a second one.

  THESE NUMBERS ARE BOUNDED FROM OUTSIDE, and this item's first draft - 5 seconds, and three backoffs
  to 400 ms - was not bounded by anything. The tree already carries the measurement. DeviceManager's
  existing agent deadline is two seconds, and the comment above it says why in the only terms that
  matter here: ServiceManager is blocked on DeviceManager's phase-2 answer, the kernel's recovery
  ladder gives that chain a bounded number of settle rounds and REBOOTS the machine when they run
  out, and *"ten seconds was tried and the reboot beat it every time"*. A deadline longer than that
  window never fires, because the guest is already restarting.

  AND THE PER-DEVICE WORST CASE IS THE WRONG THING TO BOUND. 2 s x 3 attempts plus 300 ms of backoff
  is 6.3 seconds for ONE device, which is already past the window the kernel's settle ladder gives
  the whole chain - and a machine with several unbindable devices multiplies it. So the budget is
  ONE ABSOLUTE deadline across every attempt on a node, not a per-attempt deadline times a count:
  2 seconds for the first `READY`, and the node's attempts end when either the budget of 3 is spent
  or the node's share of the boot window has passed since the first `BIND`, whichever comes first.

  AND THE WINDOW HAS TO BE SOMETHING DEVICEMANAGER CAN SEE. This item has now had three units and
  the first two were both wrong. Seconds: the boot window is target-specific and a settle round is
  not a fixed duration - `idle_halt()` wakes on any interrupt - so a one-off "300 rounds is about N
  seconds" stops being true on a busier machine. Settle rounds: worse, because
  `for _ in 0..settle_rounds { sched::run_until_idle(); .. }` is a local loop counter inside the
  kernel's `supervise`, and userspace cannot read it, convert it or wait on it. A budget in a unit
  the enforcer cannot observe is not a budget.

  The unit userspace HAS is monotonic ticks: `wait_any(handles, deadline)` takes an absolute deadline
  in ticks and DeviceManager's whole loop is already built on it. So `boot_userspace` takes an
  `outer_window_ticks` for the target instead of a round count - the input contract changes, because
  a duration cannot be recovered from a loop counter afterwards - and the kernel publishes that
  window as one absolute tick deadline alongside the rest of the boot hand-off, and
  DeviceManager derives both slices from that single value rather than from a constant of its own.
  One number, computed where the window is actually known, in the unit the code that must respect it
  already speaks.

  AND IT IS THE KERNEL'S OWN DEADLINE, NOT A SECOND ONE. `supervise` drives each attempt with its own
  `settle_rounds` loop, so publishing a tick deadline beside that loop would leave two authorities
  over one window, disagreeing the first time a round takes longer than the last. Each outer attempt
  computes ONE absolute deadline, the kernel's loop ends on it, and that same value is what crosses
  the hand-off - so "the boot window" names one thing on both sides of the boundary.

  AND THE SCHEDULER HAS TO RESPECT IT IN BOTH OF ITS HALVES. Checking the deadline around
  `run_until_idle()` is not enough, and neither is capping the wait: that function is
  `while !run_queue.is_empty() { reschedule(Requeue); }` and only THEN a bounded wait, so a thread
  that yields and requeues itself keeps the queue non-empty and the drain never reaches the part
  where a deadline is consulted. So both: the wait becomes `min(nearest progress deadline, outer
  deadline)`, and the drain checks the deadline between reschedules. Two tests, because they are two
  mechanisms - a thread that WAITS past the window, and a thread that stays runnable by yielding.
  Neither needs preemption or a new scheduler.

  A third test for the duration: the second incident is run AFTER a DeviceManager restart, which is
  the only version of it that proves ServiceManager kept the value rather than the manager holding
  it in a variable that died with it.

  BUILT 2026-08-27, and finishing it found the defect the item's own rule was written against.

  `Incident::open` CLAMPED UNCONDITIONALLY to the boot's deadline. An hour after boot, an incident's
  own slice is far past a boot deadline that expired long ago - so every recovery was handed a
  deadline ALREADY IN THE PAST and every bind failed instantly, for arithmetic about a boot that had
  finished. That is word for word what this item says a per-node window must not do, live in the
  code that implements it. The clamp now applies only while the boot deadline is still AHEAD of now.

  AND THE ARITHMETIC MOVED TO WHERE IT CAN BE DRIVEN. `driver_binding::IncidentWindow::deadline`
  takes the window, the share, the boot deadline and the instant, and three host tests walk it: the
  first incident clamped by the boot, a recovery an hour later getting its full slice, and a boot
  that published no window bounding nothing. Two clamps with an off-by-one between them decide
  whether a machine recovers, and that is not something to reason about inside a `no_std` binary
  nobody can run on a host - which is exactly how the unconditional clamp survived being written.

  THE OBSERVABLE EXISTS AND ONE HALF OF IT IS ASSERTED EVERY BOOT: `BOOT_DEADLINE.swap(0)` in
  ServiceManager hands the deadline to the first DeviceManager and the length alone to every one
  after it, and DeviceManager says which of the two it got on its own first line. The SECOND half
  cannot be observed in this tree: nothing relaunches DeviceManager, because its restart policy is
  `escalate` and P02M0165 M6 records why a cold reconstruction is circular - it would load volume
  drivers from the system volume the dead manager's own drivers were serving. What that milestone
  did build is the half that makes such a reconstruction safe when it exists, and the arithmetic
  above is now driven directly rather than through a drill that has nothing to restart.

  WHAT THE VALUE IS remains open and is named as open rather than guessed here. The tree has three
  target constants - 300, 400 and 4000 - and they are ROUND counts, so they cannot simply be
  relabelled as ticks: the same number in a different unit is a different budget. Whoever changes the
  contract measures each target's window once and states the three tick values, which is a
  measurement and not a decision this document can make for them.

  WHO KEEPS THE LENGTH, since an absolute deadline expires. A recovery an hour later, or a
  DeviceManager that has been restarted, needs the BUDGET and not the boot's instant of it.
  ServiceManager derives the duration once from the first hand-off and keeps it across DeviceManager
  restarts; the first incident is additionally clamped by the original boot deadline, because that
  one really does compete with the boot, and every later incident gets `now + duration`. That is two
  values with stated owners rather than a constant compiled into a service.

  ONE THIRD OF THE WINDOW FOR A BIND, of which a third is reserved for the teardown. Both are choices
  and are stated as such rather than dressed up as measurements - what makes them defensible is the
  shape, not the value: two thirds of the boot are left for everything that is not one device's bind,
  and a bind that exhausts its own budget still has a positive slice left to release the claim with.
  Giving the rollback "whatever remains", which this item said first, hands it zero in exactly the
  case it exists for - a bind that failed BY running out of time.

  AND THE WINDOW RESTARTS PER INCIDENT, NOT PER NODE. Measuring from the node's first `BIND` ever
  would mean a driver that ran happily for an hour and then crashed has no budget left to be rebound
  with: its recovery would be `Failed` on arithmetic about a boot that finished long ago. The
  deadline covers ONE bind or recovery attempt-chain and starts again with the next incident. The
  boot window is what bounds the first one, which is the only one that competes with the boot. A registry entry may lower this deadline for a device
  known to be quick; it may not raise it above the global maximum, which is the whole point of having
  one.

  THE ABSOLUTE DEADLINE CAN EXPIRE IN `Backoff`, and the table needs the edge or the node sits there:
  `Backoff -> Failed` when the budget of TIME is spent, distinct from the budget of attempts, which is
  spent in `Binding` or `Stopping`. Simpler still where it applies - a backoff that would end after
  the deadline is not entered at all, and the node goes straight to `Failed` with the reason.

  A device that cannot be bound inside the window is `Failed` with a cause and the boot continues
  without it, which is the behaviour the machine needs and the one a per-attempt bound cannot
  promise.

## Definition of done

- A bind that fails at any step leaves no claim, no process, no handle and no accounting behind, with
  a test per step - EXCEPT where the teardown could not be confirmed, which leaves the node
  `Quarantined` and its resources deliberately charged and out of circulation, and there is a test
  for that too.
- Each device node handles one event at a time, duplicate events change nothing, and a slow driver
  cannot stop the manager from serving another.
- A binding's record carries both where it is and, when it failed, why - and the transitions it took
  to get there are the ones the table allows.
- A driver that crashes after reporting online loses every resource it was granted and ends in one of
  the three states the table allows: rebound through `Backoff`, `Failed` with its cause when the
  budget is spent, or `Quarantined` when the teardown did not confirm.
- The states and their legal transitions are the table in M3, enforced rather than implied, and an
  illegal transition is refused and logged rather than ignored.
- A dependency cycle through the system volume is refused when the registry is built.

## What this milestone refuses, and why

- **An actor framework or a general scheduler for DeviceManager.** One queue per device node is a
  queue, and the thing being fixed is that events are handled wherever they arrive.
- **Detecting hung drivers.** A driver that exits is a different problem from one that stops making
  progress, needs a heartbeat the protocol does not have yet, and is P02M0165's.
- **Suspend and resume.** Planned stop is the same milestone as the watchdog, for the same reason.

## What the 2026-08-28 audit found

Seven findings. Two and a half fixed, the rest open.

FIXED:
- **The automatic retry budget was off by one.** M5 says three attempts and two backoffs of 100 ms
  and 200 ms; `may_try_again` was `attempt < MAX_DRIVER_RESTARTS` with `node.attempt` ZERO on the
  first attempt, so it ran FOUR attempts and three backoffs, the third re-using 200 ms because
  `BACKOFF_TICKS` has two entries and the index is clamped. The constant is now
  `MAX_AUTOMATIC_ATTEMPTS` - named for what it bounds, which is how the error survived - and the test
  is `attempt + 1 < MAX_AUTOMATIC_ATTEMPTS`.
- **`iommu-required` had no producer.** The kernel keeps the DMA-policy refusal distinct
  (`ERR_ACCESS_DENIED`) and `begin_bind` mapped every claim error to `ClaimRefused`. The two are now
  told apart, which was M3's stated condition for keeping the variant.
- **The `Ready` call site ignored the state table's refusal** - fixed, see M0161.

OPEN:
- The bind transaction does not own `driver_side` or any assembled resource handle, so several
  ordinary partial-failure paths leak handles and their accounting. `Attempt` has to become the owner
  of everything the transaction takes.
- Teardown is synchronous and blocking: `roll_back` calls `device_release` inline (which walks every
  live mapping, and each virtio-IOMMU request can spin 10,000,000 iterations) and `back_off` parks the
  single DeviceManager thread. One node's teardown delays every other node. M4's event-driven
  teardown, with the claim-settled event the kernel's waitable Claim object was built for, does not
  exist.
- Retryable failures BEFORE the binding is installed never reach the retry decision:
  `give_up_with` hardcodes `confirmed_lands_at(false)`.
- A crash after `Online` cannot recover - the standing loop discards `Step` - and neither `attempt`
  nor `incident` is reset at `READY`, so an hour-old incident judges the recovery. `PolicyVerb::Retry`
  starts zero attempts.
- `observe_claim` seeing a kernel-quarantined device attempts `Binding -> Quarantined`, which is not
  in the table; the silent refusal then lets `give_up` report `Failed`/`teardown-unconfirmed` for a
  device that is already terminally quarantined.
- M7's resource-invariant fault tests do not exist, which is exactly why the leak above is invisible
  to a passing suite. THEY ARE WHERE THIS SHOULD START: written first, they fail against today's code.
