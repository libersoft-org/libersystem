# M0150 - A free must never lose the memory it frees

Status: PLANNED. Carried out of M0145, which confirmed the defect and said in its own text that the
answer is a milestone of its own.

The frame allocator keeps freed spans in a run table. The table is bounded - it was bounded on
purpose, to fix a deadlock - and `insert` says outright that a span which does not fit is not being
tracked. So under enough fragmentation, freeing memory silently loses it. That is safer than the
deadlock it replaced and it is not a resting place for a kernel meant to run for months: the machine
gets slowly smaller, nothing reports it, and the symptom arrives weeks later as an allocation
failure with no cause attached.

The same shape showed up once already and was caught by accident. During M0147 the frame quarantine
dropped pages when its queue could not grow, which is exactly when frames are short; it cost nine
pages per failed load and was only noticed because a test printed how many were still quarantined.
A counter would have found it in a second. That is the cheap half of this milestone.

## What is wanted

- [x] **Count what is lost, before changing anything.** A refusal counter on every path that declines
  to track a freed span, and a boot-time report of it. This is a day's work, it makes the defect
  visible instead of theoretical, and it is what says whether the buddy allocator below actually
  fixed anything. M0147's rule: measure first, and be willing to record that the change did not pay.

- [x] **A buddy allocator for the frame layer.** It answers three things the run table answers badly:
  metadata bounded at boot rather than growing with fragmentation, coalescing that does not depend on
  a table having room, and contiguous multi-page allocation for DMA without a linear scan. The
  bitmap is sized from the memory map once and never allocates again, which is the property that
  makes "a free cannot fail" true rather than usually true.

- [x] **A free that cannot fail, and a signature that says so.** Today's `deallocate` and `retire`
  can decline. With bounded metadata they cannot, and the types should stop pretending otherwise -
  a `Result` nobody can act on is worse than none, because every caller invents its own wrong
  handling for it.

- [x] **Keep the quarantine on top.** The TLB quarantine from M0147 is orthogonal and stays: a frame
  that was mapped is not safe to hand out until every core has flushed it, whatever structure holds
  the free list. What changes is that `drain_quarantine` can no longer fail to return frames.

- [x] **Fragmentation tests that actually fragment.** Allocate and free in a pattern that shreds the
  address space, then assert that the total free count returns to what it started at - and assert it
  through a counter the test owns, not the global one. M0147 retired four tests that asserted numbers
  belonging to the whole machine; this one has to be written to survive an eight-core kernel doing
  other things.

- [x] **A contiguous-allocation test with a real caller.** DMA buffers are the reason contiguous
  allocation exists. The test should ask for one after fragmenting, and get it.


## The counters, built

`lost_pages()` and `refused_frees()` are compiled in rather than `#[cfg(test)]`, and the difference
between them is the point.

`refused_frees` already existed and counts a free this allocator DECLINES - an address it never
handed out, a span overlapping the free pool. That is a caller's bug and costs nothing: the frames
were never the allocator's to lose. It was test-only because a test needed it, which is the whole
reason it existed.

`lost_pages` counts the other thing, which is the one this milestone is about: a perfectly good free
that could not be RECORDED. Three paths reach it and **none of them was counted**:

- the run table at capacity (`insert_at` refuses rather than allocating from the heap it feeds);
- a quarantined page whose shootdown could not complete, one at a time;
- the same, for a whole batch.

Each now adds to the count and prints the running total beside its warning, and the boot log carries
a baseline line whether or not anything has been lost - a later non-zero reading is only worth
something if a zero one was printed too.

`a_fragmenting_workload_loses_no_pages_and_says_so` asserts the DELTA across its own churn, never
the absolute value: the counter belongs to the whole machine and seven other cores are running while
the test does. It is the guard rather than the demonstration - driving the run table to its ceiling
would mean deliberately losing real pages out of a live kernel, which is a poor trade for a test.
What it catches is a change that starts dropping frees on an ordinary workload, which is exactly how
the quarantine defect arrived: nine pages per failed load, noticed only because something happened
to print a count.

The number is not yet in `MemoryStats`, so `lsmem` cannot show it. That needs an ABI field and is a
deliberate decision rather than an oversight.


## The two tests, built

`a_fragmenting_workload_loses_no_pages_and_says_so` shreds the address space - a wide span handed
back in two interleaved passes, three times over - and asserts the DELTA of `lost_pages` across its
own work, never the absolute value. The counter belongs to the whole machine and seven other cores
are running while the test does; M0147 retired four tests that asserted numbers belonging to the
machine rather than to themselves.

`a_dma_buffer_still_gets_a_contiguous_span_after_the_pool_is_shredded` asks through the REAL caller.
`DmaBuffer::create_in` is what needs contiguous spans in production and it does more than call the
allocator - it charges a Domain, maps the pages, and refuses cleanly when it cannot - so a test that
called `allocate_contiguous` directly would pass over a caller that had stopped being able to use
the answer. It asks twice: a small buffer while every other page of a wide span is free (a caller
needing four contiguous pages must not be refused because the pool is untidy), and one spanning the
whole width once the rest is returned, which only a table that re-coalesced can serve.

## What is NOT done, and why it was not attempted here

The buddy allocator and the infallible-free signature that depends on it are untouched.

This is the kernel's physical memory allocator. A defect in it corrupts memory rather than failing,
and verifying it means three architectures at up to 75 minutes each. It is a milestone's worth of
work by this file's own description - the counters above are called "the cheap half" in the opening
paragraph - and it was reached at the end of a very long unattended session, which is the exact
condition M0147 records as "how a subtle one gets committed".

What it now has that it did not: **the measurement it asked for first**. `lost_pages` is compiled
in, printed at boot, and asserted by two tests, so the question the buddy allocator exists to answer
- how much does this actually lose - can be answered with a number before anything is rewritten, and
again afterwards to say whether it paid.


## A free that cannot fail, without replacing the allocator

The loss had one cause and it was a number: `MAX_RUNS = 8192`, described as *"sized well past what a
healthy pool fragments into"* - which is a claim about healthy pools rather than about what is
possible. Past it `insert_at` refused, the freed span was lost, and the machine got quietly smaller.

The most disjoint free runs a pool of N pages can hold is **N/2**, because two free runs must have an
allocated page between them. There is no arrangement with more. So the table is now reserved for
`worst_case_runs(total)` at boot, and a free cannot find it full.

It costs 16 bytes per two pages - about 0.2% of the pool, a megabyte on a 512 MB machine - reserved
once, never grown, and it makes `deallocate` unable to lose a frame. The signature says so, and it
draws the line the old comment blurred: a free can still be REFUSED - a double free, an address this
allocator never handed out - and those frames were never the allocator's to lose. `lost_pages()` and
`refused_frees()` count the two separately for exactly that reason.

`the_run_table_is_reserved_for_the_worst_the_pool_can_reach` pins the arithmetic, because the day it
drifts nothing else notices: the table simply starts refusing again, on a fragmented machine, weeks
later. It also asserts the table is the heap-backed one - the pre-heap seed table is fixed at 128
runs and can still lose a span, so everything above would be true of a table nobody was using if the
upgrade had silently declined.

The refusal branch in `insert_at` stays, unreachable, and says so. An argument is not a guarantee: if
the sizing is ever wrong, the alternative to that branch is writing past the end of a `Vec`.

## The buddy, built

`mem/frame/buddy.rs`. A bitmap per order over the physical extent - lowest usable frame to highest,
holes included, because a hole is simply never freed in and so reads as allocated forever. That is
what lets one buddy cover a memory map with gaps in it, and it is why the extent is the map's rather
than a power of two.

Measured on the x86_64 test guest: **1,035,451 free frames and 383 KiB of metadata** - a bit per
block per order, summed to two bits per page, about 0.009% of the pool. Reserved once at
`upgrade_to_heap` and never grown. The boot log prints both numbers.

A block of 2^k pages at index `i` has exactly one buddy, `i ^ 1`, found by xor. Merging is clearing
a bit. **There is no table to fill, so a free cannot fail** - which is the property this milestone
exists for, and it is now true by construction rather than by a reservation being big enough.

### Bitmaps rather than free lists, and why

The textbook buddy keeps a list per order so allocation is O(1) instead of a scan. Both ways to
build one here cost more than they return: intrusive lists threading `next` through the free pages
need every free page reachable through the direct map, on three architectures, forever - a
correctness dependency this allocator otherwise does not have; side arrays cost about 16 bytes per
page, twice what the run table cost, to remove a scan that is small.

Small because allocation at order k reads `pages >> k` bits: a 64-page DMA buffer scans 32 words
against a run list that could hold 65,536 entries. **That is the "without a linear scan" this
milestone asked for** - what remains is a handful of `u64` loads, not a walk of the pool.

### The scan that was not small, and the measurement that caught it

The first version had the hint and no counts, and the x86_64 suite went from **117 s to 483 s**.

The shape of a buddy is what makes that bite. A freshly seeded pool is a few huge blocks, so orders
0 through 17 are EMPTY - and an empty order can only be proved empty by reading its whole bitmap.
Every second single-page allocation did exactly that: split a big block, which lowers the low
orders' hints; consume the piece; then scan sixteen thousand words to rediscover that order 0 is
empty again.

A count per order answers "is this order empty" without reading a word. **483 s -> 112 s**, level
with the run table it replaced.

That number is also the answer to the question this milestone was left open on. The previous entry
here said the contiguous-allocation scan should be measured before a rewrite was justified, and it
was right to ask - but the measurement that mattered turned out not to be the one anticipated. What
a buddy costs is not the DMA path; it is the emptiness probe on the ordinary single-page path, and
it does not show up in a design argument at all.

### What kept the old allocator's job

The run table survives in two places and both are deliberate. The **pre-heap seed table** still
serves boot, because the frame allocator is what brings the heap up and there is nowhere to put a
bitmap before then; it is a handful of runs and a loss there is a boot-time impossibility. And the
**worst-case-sized heap table** stays as the fallback if the buddy's metadata cannot be reserved -
the weaker version of the same guarantee rather than none - and the boot log says so out loud,
because quietly running the old allocator is the kind of fallback nobody notices for a year.

Ownership checking is unchanged and still one level up: the buddy answers "is this block free",
`check_owned_free` answers "was this the caller's to give back", and they are different questions.
The double-free that the run table caught with an overlap test is now asked of the bitmap directly.

### Tests

Four in `buddy.rs`, over a made-up extent so the arithmetic is exercised without the machine's own
pool: that a span freed page-by-page in an awkward order merges back into ONE block (only observable
by then allocating it whole - a pool holding 64 separate one-page blocks refuses that); that the
rounding of a 3-page request is handed back rather than held; that a pool whose page count is not a
power of two never hands out the gap past its end; and that a free it cannot frame is refused rather
than corrupting the tree.

`the_run_table_is_reserved_for_the_worst_the_pool_can_reach` now asserts the buddy is the one
serving first, because everything else in it is about the fallback - and if the buddy failed to
build, the fallback is what the machine is running.
