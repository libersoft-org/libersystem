# P02M0084 - Own UEFI-only bootloader (x86_64 / aarch64 / riscv64)

Status: REOPENED (2026-08-16) by a fourth-party audit round, recorded in AI/audit/uefi.md. The findings are appended as open tasks in the section at the end of this file; each was checked against the tree before being written down, and where a check contradicted the audit that is recorded with the task rather than dropped. Previously: COMPLETE.

A revision of the concept's original "we do not write our own bootloader" decision. The target is one
small EFI application per architecture over a shared core, **strictly UEFI-only** - the BIOS path is
not carried.

*Condensed 2026-08-08.*

The loader is hand-rolled and dependency-free (`src/loader`), with its own minimal UEFI FFI, over a
shared zero-dependency `bootproto` crate that carries the hand-off. Development moved to UEFI first,
so QEMU boots through OVMF with a read-only shared CODE image and a private writable VARS copy per
run.

The three variants share the loader's architecture-neutral core - boot-volume file I/O and the ELF
reader - and differ only in `arch/<arch>/`: page-table setup and the hand-off mechanism. Each loads
the kernel's `PT_LOAD` segments and enters it the same way.

Proven end to end on x86_64 QEMU/OVMF: 52 of 52 cores online, every driver and userspace service up,
the interactive shell live, and the suite green.

*(P02M0108 later gave this loader a filesystem, so it reads the bootstrap set from the system volume
rather than from an archive.)*

## Fourth audit (2026-08-16): `AI/audit/uefi.md`

Seven findings against the firmware-facing half of the loader.

- [x] **GOP geometry is not checked against the framebuffer aperture (UEFI-001, High).** Width,
  height, stride and pixel size come from firmware and are used to compute writes into a mapped
  aperture without proving the product fits it.
- [x] **Overlapping memory descriptors are passed through as independent regions (UEFI-002, High).**
  The same physical page can then be handed to two owners.
- [ ] **`memory_top` still creates write-back mappings across reserved memory and holes
  (UEFI-003, High).** Mapping MMIO or absent physical space write-back is an architecture violation
  on aarch64, not merely wasteful.
- [ ] **Safe public APIs dereference unvalidated raw firmware pointers and hand out unbounded
  lifetimes (UEFI-005, High, soundness).** The same class as `Fdt::new` in `AI/audit/fdt.md`.
- [x] **The second memory-map result can claim more bytes than were allocated (UEFI-004), SPCR
  access width is converted to spacing and then discarded (UEFI-006), and the mock leaks every
  handle buffer it returns (UEFI-007).**


### UEFI-001, -002, -004, -006 and -007 closed; -003 and -005 priced (2026-08-18)

**UEFI-001**: width, height, stride and pixel size were taken from firmware and multiplied into
writes against an aperture whose size came from the same source and was never compared. Every step is
checked now - `pitch_px * bpp` and `height * pitch` are exactly where a large-but-plausible pair
becomes a small number - and a mode that does not fit its own aperture is reported absent. Watched to
fail against the unchecked construction.

**UEFI-002**: only exactly-adjacent same-kind runs were merged, so overlapping descriptors came
through as independent regions and one physical page could be described twice - once usable, once
reserved - and handed to two owners. The audit offered strict rejection or canonicalization;
canonicalization was chosen because refusing to boot on firmware with benign overlaps is worse than
resolving them. The precedence is restrictive and that is the point: where two descriptors disagree
about a byte, the one that is NOT usable owns it, because an ambiguity resolving to usable puts MMIO
or firmware memory into the frame allocator. The test covers partial overlap, full containment,
identical bases and same-kind overlap, and asserts the output is disjoint with no restricted byte
reported usable.

**UEFI-004**: `map_size` is an input capacity and a firmware output through one variable, and only
stride and divisibility were checked afterwards. It is now also checked against the buffer that was
allocated.

**UEFI-006** was worse than "converted and discarded": access size 4 is QWORD and fell into the
default zero-shift branch, so a table declaring eight-byte spacing got registers one byte apart -
silently mistranslated rather than merely unused. The access width is kept as well as the spacing,
and the post-boot-services console reads and writes at the declared width; a UART described as
dword-access was getting byte accesses at correctly-spaced addresses, which many such parts do not
answer at all.

**UEFI-007**: the mock forgot one handle buffer per `locate_handle_buffer` call and `free_pool` is a
no-op, so a looping test grew the heap for as long as it ran. The buffers are recorded and freed with
the rest of the state.

**UEFI-003 is deferred with its cost.** The recommendation is to replace the scalar `memory_top`
contract with a per-descriptor sparse HHDM carrying cache attributes, leave holes unmapped, bound the
identity map to the transition code, and update the kernel's direct-map limit model in the same
change so it stops assuming contiguity. That is a loader AND kernel change across three
architectures, and a partial version is worse than none: a direct map that no longer covers what the
kernel assumes it covers does not fail visibly.

**UEFI-005 is deferred with its cost, measured rather than estimated.** Marking `alloc_pages`,
`memory_map_snapshot`, `memory_top`, `staging_clear_of`, `translate_map`, `read_file`, `each_disk`,
`locate_framebuffer` and `Acpi::new` as `unsafe fn` with stated contracts was attempted and reverted:
it produces 51 production call sites and 69 test errors to wrap. The change is mechanical and has no
behavioural effect, so it belongs in a round that can carry it end to end rather than half of one.

Measured: uefi 33/33 host tests with two new tests watched to fail first, all 67 host suites, and
x86_64 `boot,console,display` 18/18.

### The aarch64 boot failure is NOT from this work - baseline established (2026-08-18)

`./test.sh --arch aarch64 --tags boot,smoke` FAILS on the current tree: services do not come online.
The symptom VARIES between runs on the same binary - one run showed `device_service` crashing
repeatedly plus a ring-3 page fault at addr 0x0 in `watchdog_probe`, later runs showed
`resource_manager`, `audio_service` and `input_service` reporting "FAILED to start" - which reads
like instability rather than one deterministic regression.

**The baseline was established and it fails the same way.** Every file this session changed under
`src/kernel`, `src/uefi`, `src/loader`, `src/idl`, `src/proto` and `src/user` - 26 of them - was
restored to its `67fe4b7` content in place, aarch64 was rebuilt, and the same test was run: it FAILS,
with the same signature (`resource_manager`, `audio_service`, `input_service` and `network_service`
reporting "FAILED to start", `device_service` crashing). The tree was then restored from saved copies
and rebuilt green. So the failure pre-dates all of it.

Two things about HOW that was measured, because the obvious route does not work here. A `git
worktree` at `67fe4b7` cannot be used as a baseline: the shared-image build matches providers by
mangled symbol name, and those names embed a hash that depends on the build path, so an out-of-tree
build fails with "N declared providers (expected 1)" for reasons that have nothing to do with the
commit. The in-place file restore is what gives a comparable measurement. And removing the
KERN-CORE-021 MSI lock changed nothing, which was the first hypothesis and the wrong one.

x86_64 is green throughout and the serial console works on aarch64 - the failure is visible in its
own log - so the UEFI-006 console change is not implicated either.

**The bisect was run and it ended early, because the tree already names this.** Measured:
`boot,smoke` fails on aarch64 at HEAD, at `67fe4b7`, and at `916c4dc` - the last of those predating
the whole audit round. Going further back, the history names it directly: `1cb6589` (2026-08-16) is
*"Identify aarch64 heap corruption"*, and `P02M0132.md` carries a section headed "It is not a
filesystem defect: the aarch64 heap is corrupt", which hands the problem on as **"the aarch64 kernel
heap hands out memory that is not its own, and the remaining source is still to be found"**. Around
it sit `14517cb`, `39c6b6e`, `d6d2a9b` and `13013a0`, all aarch64 corruption work from 15-16 August.

So there is no regression commit to find. "Services FAILED to start" is the same phenomenon as the
`imgconv` assertion failure recorded there: the heap hands out memory that belongs to something else,
and WHICH thing breaks depends on who asks for it next. The varying symptom between identical runs is
that, not flakiness in the harness.

The next step is already written down in P02M0132 and the instrumentation for it is already in place
(the unhandled-exception report carries `LR` and `x29`): a guest that allocates a known pattern, frees
nothing, and re-reads it after the same workload.

WHAT THIS DOES NOT SAY: that aarch64 is fine. It is a real, open failure and it belongs to whatever
introduced it, which is earlier than this session. The symptom varies between runs on identical
binaries - one run showed a ring-3 page fault at addr 0x0 in `watchdog_probe` alongside the crashes -
so it reads like instability rather than one deterministic fault. It needs its own investigation with
its own bisect, and this milestone is not it.
