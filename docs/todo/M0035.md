# M0035 - Interactive console: line editor, history, and the console subsystem

Status: COMPLETE. Started as readline-style editing in the shell and grew into the whole console
subsystem (M0035a-k): a userspace ConsoleService owning the framebuffer, a cell-buffer terminal,
multiple virtual terminals, scrollback, Unicode, colour, mouse and selection.

Per the microkernel split, the editing lives in the userspace shell; the kernel console stays a dumb
byte sink.

*Condensed 2026-08-08 to the architecture it settled on and the numbers that still bind.*

## The split

The kernel prints only its own boot log to the framebuffer and serial, then **hands the display to
userspace**: `SYS_FRAMEBUFFER_MAP` maps the framebuffer's physical frames into ConsoleService, which
owns everything visible from then on.

`driver.virtio-input` converts keycodes to bytes before anything else sees them: it tracks modifier
state across press *and* release (a release matters for a modifier, so it is handled before the
press-only gate; Caps Lock toggles on press), applies a US layout with a shifted table, and maps the
navigation keys above the 64-entry ASCII keymap to standard xterm escape sequences - `ESC [ D/C/A/B`,
`ESC [ H`, `ESC [ F`, `ESC [ 3 ~`. The shell therefore reads the same bytes a serial terminal would
send, and needs no keycode knowledge.

## The terminal model

ConsoleService models the screen as a **grid of cells** (`Cell { glyph, fg, bg, underline }`) with a
primary and an alternate buffer, rather than drawing straight to pixels. Escape sequences and
scrolling are pure grid edits, and `flush` repaints only the cells that changed. That is what makes
scrolling, damage tracking and double buffering possible at all.

On top of it: an alternate screen buffer (`ESC [ ? 1049 h/l`) so a full-screen program does not
clobber the shell's scrollback; a UTF-8 output decoder folding a lead byte plus continuations into a
codepoint, with U+FFFD for a malformed sequence; a 256-glyph `font8x8_latin.bin` (extended from 128);
the 16-colour palette plus 256-colour and 24-bit truecolour SGR; SGR mouse mode (`ESC [ ? 1006 h`);
and a blinking caret driven off the 100 Hz tick.

**Per-VT scrollback is deterministic memory, sized once.** A fixed ring per VT, allocated at
creation. (Corrected 2026-08-10: the depth is `SCROLLBACK_ROWS = 1000`, the operator can raise it
through `console.scrollback` with no ceiling, and VTs are created on demand with no cap. At 1024x768
that is 2.15 MB per VT, and 4.17 MB at 1920x1080 - not the 196 kB and four-VT cap this paragraph
described, and not bounded by a 1 MB heap, which now grows. See M0158.) Lines scrolling off the full primary screen are captured; the alternate
screen is not.

**Terminal size is typed, not guessed.** `winsize` travels on the per-VT control channel and
`Term::resize(cols, rows)` clamps to what the physical framebuffer can show and reflows the cell
buffer. The local resolution-change *source* came later, from M0044.

## Multi-client services, and the sessions above them

The per-service channels became multi-client through a **generic transport-level connect** rather
than a typed `open()` per interface: `rt` gained `serve_multi` (a `wait_any` loop over a growing
channel set) and a reserved `CONNECT_OP`. StorageService, DeviceService, ProcessService,
ConfigService and TimeService all use it.

ConsoleService is the session spawner: N virtual terminals, each with its own cell buffer,
scrollback and shell, with keystrokes routed to the foreground VT only and a reserved chord to
switch. Two shells run concurrently on different VTs.

Selection is the Linux convention: click-drag selects, the selection is the clipboard, and the
wheel scrolls back when no program is tracking the mouse.
