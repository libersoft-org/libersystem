# P02M0172 - DMA isolation policy is registry data, not a kernel device-type list

Status: PLANNED. DMA POLICY PREREQUISITE. QEMU SECURITY FOLLOW-UP.

## Goal

Make every staged driver declare whether it performs no DMA, requires translated DMA, or is an
explicitly trusted untranslated exception, and make kernel admission enforce that declaration from
the trusted generated registry.

P02M0153 defined the policy vocabulary, but the current production decision is still a hard-coded
kernel `IOMMU_REQUIRED_TYPES` list containing only virtio-net. Every other device type silently
defaults to `TrustedUntranslated`. That contradicts the registry-policy claim and blocks an honest
cross-architecture enforcing rollout: adding a driver should not require another kernel name/type
arm before it can be protected.

This milestone extracts and closes the open "declared DMA policy per driver" prerequisite in
P02M0099. It implements no IOMMU backend.

## Two boundaries this plan fixes before implementation

**The DMA mode is NOT the development profile.** `boot_profile()` reads one fw_cfg scalar and
recognizes exactly `development` and `development-trace`, an unrecognized name reads as no profile,
and the file states the value is ADVISORY. Those exact strings also gate security-sensitive
userspace behavior, the harness injects the file only on that branch, and test mode deliberately
carries no profile metadata at all. Reusing or replacing that scalar would either break development
semantics or make every current test, direct and non-x86 boot fail closed. So the DMA mode is a
SEPARATE typed field with its own producers, and the advisory scalar stays advisory.

**The canonical registry identity is the validated program NAME, and it already exists.** Generated
entries are identified by `name`, operator policy persists `select=<name>`, and P02M0166 already
calls that the registry entry ID. Introducing a second stable ID would orphan every stored operator
preference and give reporting, userspace selection and kernel admission three ways to name one
entry. This milestone therefore carries the existing name; it defines the encoding, width and ABI
representation that name needs in order to cross the claim boundary, which is what is genuinely
missing.

## Work

- [ ] **M1 - the manifest has a required closed DMA-policy field.** Every `role = "driver"` row
  declares exactly one of `none`, `iommu-required`, or `trusted-untranslated`; non-driver rows cannot
  declare it, unknown values are rejected, and absence is rejected rather than defaulted. Migrate
  every current driver row deliberately. `none` is an enforceable non-bus-mastering claim mode: the
  driver may receive its validated MMIO and interrupt resources, but PCI bus mastering remains off
  and the binding cannot mint a DMA buffer/address or activate another DMA path. It is not merely a
  statement that the current driver happens not to ask.

- [ ] **M2 - the DMA mode is its own typed boot-contract field.** Define a closed DMA-mode value -
  `enforcing-required` or the explicit `no-iommu` degraded profile - carried in its own field,
  fixed before driver admission, and never inferred from the development profile scalar.

- [ ] **M3 - the authenticated handoff is defined, not assumed.** `BootInfo` v2 has no authenticated
  policy field, and P02M0150 deliberately did not extend it because its trust decision stayed inside
  the loader. This decision is kernel-owned, so the handoff must exist:

  - THE SIGNED MANIFEST FIELD: one `u32` beside P02M0171's generation, `1` = `enforcing-required`,
    `2` = `no-iommu`, every other value refused. Covered by the same signature and validated in the
    same place as product, architecture, source kind and volume identity;
  - A BOOT-WIDE EQUALITY LATCH, on the same terms P02M0171 uses for its generation (added
    2026-08-30). A boot composes several signed manifests - the medium's and each volume's - and
    without a rule two individually valid same-release manifests can disagree about whether
    enforcement is required. So: EVERY selected signed manifest carries the SAME DMA mode, the first
    verified manifest latches it, and a later one that differs REFUSES the boot rather than letting
    either value win. There is no "authoritative manifest" and no precedence order, because a
    precedence order is a rule an attacker composes media against. M8 adds a mixed-mode signed-set
    refusal fixture;
  - A VERSIONED `BootInfo` EXTENSION carrying the value AND its PROVENANCE - one enum, `signed`
    (validated from a manifest by this loader) or `harness` (asserted by a trusted direct-boot path)
    - because the kernel's admission decision differs between them and a single scalar cannot say
    which it is. `BootInfo` is at `VERSION = 2`; this is an appended field and a version bump, which
    is what that guard exists for;
  - PER-PATH VALIDATION: a loader writes `signed` only for a value it verified against a signature it
    checked, and a direct-boot path writes `harness` only from the named harness contract. Copying an
    untrusted assertion into either is the defect the provenance enum makes visible, and M8 mutates
    exactly that; and
  - THE TRUSTED DIRECT-BOOT CARRIER, which is NOT `BootInfo` and could not have been (corrected
    2026-08-31). On a direct AArch64 or RISC-V boot the kernel receives a raw DTB and CONSTRUCTS its
    own `BootInfo` later; worse, `device::init` and `dma_policy::init` both run BEFORE that
    construction. So "the harness writes a `BootInfo` field" asked a host to write into an object
    that does not exist yet, and admission would have decided before any authenticated mode was
    parsed. The carrier has to be something the kernel reads EARLY, from the data it is actually
    handed:

        x86_64 direct      an `fw_cfg` file of this product's own, beside the profile scalar and
                             separate from it - a fixed-length record carrying the mode and the
                             `harness` provenance, read once during early init
        AArch64/RISC-V     a property under this product's own node in the device tree the harness
          direct             passes, read by the existing FDT parser in the same pass that reads the
                             memory map and the interrupt controller

    Both are parsed BEFORE `dma_policy::init`, and the parsed value is what `dma_policy` reads -
    that ordering is the requirement, not an implementation note, because a mode parsed after
    admission is a mode admission did not use. `BootInfo` still carries the value onward for
    reporting and for userspace, but it is not where admission gets it.

    The provenance rule is unchanged and is what makes this safe on a direct boot: the value reads
    `harness` and never `signed`, so the kernel knows it is trusting the named harness as part of the
    TCB rather than a signature it checked. On a boot where an `fw_cfg` file or DT property is
    present but this product's own node is absent, or the record is malformed, the mode is ABSENT and
    M2's named-producer rule applies - the direct rows name a producer, so that refuses.

  A boot-media-controlled value may never present itself as authenticated policy. If P02M0171 lands
  in the same period, the manifest evolves ONCE and one compatibility matrix covers both fields;
  ordering is stated in Dependencies rather than left to whichever is implemented first.

- [ ] **M4 - one identity carries selection and policy across the claim boundary.** Keep the program
  name as the entry identity and attach the policy to it.

  **THE GRAMMAR ALREADY EXISTS AND IS ADOPTED VERBATIM** (corrected 2026-08-30). A previous version
  said to define normalization, encoding and maximum width later; `system-manifest`'s `validate_name`
  already constrains a program name to 1-64 bytes of ASCII alphanumerics plus `_` and `-`, and the
  parser rejects a duplicate program name outright. Defining a second normalization would create two
  answers for one identity, which is the defect this item exists to prevent. So the identity IS that
  name, in those bytes, with NO normalization step at all - a name is already canonical or it is
  rejected at manifest validation - and the maximum width is 64.

  What genuinely remains is the ABI representation, chosen here rather than deferred: a FIXED
  64-BYTE FIELD, NUL-padded, carried in the claim request and stamped on the grant and the report.
  Fixed rather than length-prefixed because the claim boundary is a `repr(C)` ABI struct and a
  variable-length field there is a second parser; 64 because that is the manifest's own bound, so the
  two cannot drift. It is a DECLARED field: `ClaimKey`'s reserved padding is not repurposed.
  `device_claim` currently carries device index and privilege, and `ClaimKey` carries
  device index, padding and generation; the identity must be added as a declared field with its own
  ABI decision, not written into reserved padding.

  DeviceManager passes the identity of the exact priority/fallback candidate it is attempting, not a
  free policy scalar. A fallback candidate therefore carries its own decision rather than inheriting
  the first matching row's. The kernel stamps entry identity, policy and the newly minted binding
  generation on the claim.

- [ ] **M5 - the authority boundary is frozen: DeviceManager selects, the kernel validates.**
  Privileged DeviceManager's selected matching entry is AUTHORITATIVE. The kernel does not recompute
  priority - operator policy can deliberately select a lower-priority candidate, and a kernel that
  recomputed would silently overrule the operator. The kernel validates:

  - that the named entry EXISTS in the table generated from the same manifest;
  - that the entry's match rules admit the concrete device being claimed;
  - the entry's declared DMA policy against the boot DMA mode; and
  - the binding generation.

  Membership-plus-device-plus-policy-plus-generation is the complete check. Write that down as the
  trust model it is: privileged DeviceManager is the selection authority, and the kernel's job is to
  make sure the selection names something the image actually declared for this device.

- [ ] **M6 - admission has no permissive fallback.** Remove `IOMMU_REQUIRED_TYPES` and the implicit
  default to `TrustedUntranslated`. On an `enforcing-required` mode, both DMA-capable policies are
  translated and either refuses if enforcement is absent or failed. On the explicit trusted
  `no-iommu` mode, `iommu-required` refuses and only `trusted-untranslated` may enter the existing
  loud degraded inventory; an unexpected controller/mode mismatch is refused rather than silently
  reclassified. A `none` claim uses M1's non-mastering path in either mode and refuses every DMA
  activation. An unknown, stale-generation, entry/device mismatch or mode mismatch refuses, and so
  does a MISSING mode on a path whose M2 row names a producer - but NOT on the test and development
  rows, where absence is the stated answer and selects the loud degraded contract (see M2's
  missing-value rule, which this sentence used to contradict by refusing every absence). Every one of
  them refuses rather than choosing the least restrictive answer.

- [ ] **M7 - policy changes select and rebuild every consumer.** Ensure the shared manifest is an
  input to the generated userspace registry, kernel admission data, image metadata and verification
  model, and bind the DMA-mode value into the direct or loader/kernel boot contract as appropriate.
  A one-line policy or mode change cannot leave a kernel from the old decision beside DeviceManager
  or an image from the new one.

- [ ] **M8 - hostile policy fixtures prove the boundary.** Host tests reject missing/unknown fields,
  fields on services, existing same-priority ambiguous overlaps, and stale/mismatched or
  non-normalizing entry identities. A positive different-priority overlap with different policies
  proves that an intentional fallback is valid and that each attempted entry reaches the kernel with
  its own policy and generation. Include the case the authority boundary exists for: an operator has
  persistently selected a LOWER-priority candidate, and the kernel admits it because the entry is
  declared for that device - and refuses when it is not.

  Kernel/guest tests prove the full M6 mode/policy matrix, including MMIO and IRQ but no BME or DMA
  for `none`. A MIXED-MODE SIGNED SET is refused without admitting anything: two individually valid
  same-release manifests carrying different DMA modes make the boot refuse at M3's latch. And the
  identity bytes are proved IDENTICAL end to end - the persisted operator selection, the generated
  table, the claim request, the kernel's stamp and the report all carry the same 64 bytes for one
  entry.

  Mutations that must fail: restoring the permissive default, inferring degraded authority from
  controller absence, recomputing priority in the kernel, accepting a DMA mode whose provenance says
  it came from replaceable media, a loader writing `signed` provenance for a value it did not verify,
  and removing the equality latch so a mixed-mode set boots. Assert that the current image has no
  staged driver without an explicit classification, and that no producer named in M2's matrix is
  missing a value.

## Dependencies

- P02M0153 owns `DmaAddress`, IOMMU backend admission and the three policy outcomes.
- P02M0161-P02M0166 own registry selection, binding generations, rollback, stop and reporting, and
  P02M0166 owns the entry name that M4 carries.
- P02M0150 owns signed manifest v2 and the loader trust decision that M3 extends into the kernel.
- P02M0171 also evolves the signed manifest. If both are in flight, one coordinated manifest
  evolution carries both fields and one compatibility matrix covers them; neither may land a second
  incompatible format change.
- P02M0099 remains the driver roadmap; future DMA-capable items consume this mechanism rather than
  adding another policy arm.

## Definition of done

- Every staged driver has one validated DMA policy from the manifest.
- The DMA mode is a distinct field with a stated producer for every row of M2's matrix, carries its
  provenance, is equal across every signed manifest a boot composes, and the development profile
  scalar is unchanged.
- Kernel admission enforces the exact attempted entry's policy and mode, including a usable but
  non-bus-mastering `none` claim, with no device-type list or silent trusted-untranslated default,
  and without overruling an operator's selection.
- Policy, entry identity, binding generation, operator reporting and rebuild selection cannot drift.

## What this milestone refuses

- A new IOMMU backend, endpoint migration, native hardware or a physical-machine claim.
- A second entry identity beside the program name, and any use of reserved ABI padding to carry one.
- Kernel-side priority recomputation.
- Treating every driver as malicious on a profile with no translating hardware; explicit degraded
  exceptions remain possible and visible.
- A free-form policy language. Three closed outcomes are the complete current admission contract.
