# P02M0182 - A capability-scoped smart-card service

Status: OPEN. Completion is the explicitly supported service slice below, including its fixture
proof. It does not claim implementation of the separately owned USB CCID transport or support for
readers without a trusted PIN-entry facility.

P02M0099's CCID class owns transport, card power/parameter negotiation, bounded exchange and
transport abort. Authentication policy, reader grants and transaction ownership belong here.
The CCID class remains a module in the USB controller's process, following `usb_class.rs`; the
smart-card service is a separate process and receives a typed transport capability, not USB claims.

## P02M0182 - Supported card and PIN boundary

- [ ] Support contact PIV cards through short-APDU-level CCID-compatible providers. Start with
  reader pinpads that support the standard secure PIN-verification operation. Non-pinpad readers
  can enumerate/read supported public card data; `verify` returns typed `trusted-input-unavailable`
  without accepting a PIN from the application. This pinpad-only authentication slice is sufficient
  for this milestone. P02M0188 owns action/target confirmation, not secret entry, and is not an
  assumed PIN broker or a prerequisite for this slice.
- [ ] Future non-pinpad verification requires a separately owned trusted secret-entry contract:
  a trusted renderer/input owner excludes the requester, delivers the secret only directly to this
  service on a bound private channel, and cancels/erases on timeout, focus/path loss or disconnect.
  That extension is outside this milestone's supported slice and must not be substituted with an
  application's prompt, stdin, InputService raw-key grant or P02M0188's confirmation response.
- [ ] Define typed `liber:smartcard@1` reader metadata/slots/presence/ATR, transaction acquisition,
  constrained APDU exchange, `verify-piv-pin`, PIV authentication, cancel and release. PIN verification
  takes only the transaction and deadline, never PIN bytes. The service chooses PIV application PIN
  reference `0x80`, constructs the secure-verification template and asks the reader to collect and
  verify the PIN locally. The transport validates secure-operation framing; it makes no decision
  about who may authenticate, which reference is allowed or whether a client is authorized.
- [ ] The ordinary `exchange` endpoint is an allowlist for the selected PIV application, not an
  arbitrary byte tunnel. Accept only canonical SELECT of the fixed PIV AID and canonical GET DATA
  for the Discovery Object and public PIV Authentication certificate. Validate the complete
  CLA/INS/P1/P2/Lc/data/Le grammar and transaction state. Client chaining, alternate logical
  channels, proprietary commands, secure messaging and every other application are unsupported.
  Reject VERIFY (including status-only variants), CHANGE REFERENCE DATA, RESET RETRY COUNTER,
  PUT DATA and key-management commands before the provider sees them. A universal opcode blacklist
  cannot make arbitrary applications safe, so this slice offers no privileged raw-APDU escape hatch.
- [ ] Provide a typed `authenticate-piv` operation for the PIV Authentication key with the supported
  P-256 algorithm and a fixed-size digest/challenge. The service constructs and validates the
  GENERAL AUTHENTICATE command/response grammar and requires successful service-owned PIN
  verification in the same transaction. Unsupported key algorithms return unsupported. It does
  not claim to verify a remote party's identity, trust a certificate or implement login policy.
  Bound any service-owned GET RESPONSE sequence and its total bytes/deadline; callers cannot use
  continuation APDUs to bypass the allowlist.
- [ ] Each PIN request performs at most one reader verification attempt. Return typed success,
  incorrect-PIN with available retry count, blocked, cancelled, timed-out, card-removed or provider
  error; never automatically retry a failed PIN. No client response, log, trace or service/provider
  wire carries entered PIN bytes. Reject readers whose advertised secure-operation format cannot
  support the fixed PIV template. The guarantee concerns the supported PIV semantics, not arbitrary
  cards that reinterpret unrelated bytes as a PIN.

The command policy follows [NIST SP 800-73 Part 2, PIV card commands](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-73pt2-5.pdf).
The reader exchange levels and abort ordering follow [USB CCID 1.1](https://www.usb.org/sites/default/files/DWG_Smart-Card_CCID_Rev110.pdf).
These are protocol references, not permission to copy differently licensed implementation source.

## P02M0182 - Provider ownership and reader grants

- [ ] Freeze an internal typed provider contract with reader/slot capabilities, exchange level,
  supported T=0/T=1 selection, pinpad capabilities, card-present/card-generation and bounded ATR;
  operations are power-on/off/reset, select supported protocol, APDU exchange, secure PIN verify
  and abort-to-quiescent. Requests carry service request ID, slot and expected card generation;
  responses echo them. Presence changes and provider faults are typed bounded events.
- [ ] The provider owns CCID descriptor/slot parsing, ATR parsing, card negotiation, CCID sequence
  IDs, command framing, physical removal and abort/drain. Put reusable ATR parsing/validation in
  a pure leaf shared by provider code and fixture, not duplicated in the service. The service
  validates provider message bounds and owns PIV parsing, authentication and transaction states.
  Initially accept short-APDU exchange-level readers for either negotiated T=0 or T=1; the reader
  performs card-level protocol machinery. Character/TPDU and extended-APDU-only readers return
  unsupported. Host T=0/T=1 byte-protocol engines, if later needed, belong to the P02M0099 transport
  item and require their own host tests before that mode is enabled; do not build duplicate engines
  here or present an APDU fixture as proof of unimplemented modes.
- [ ] Add a `smartcard-reader` provider kind, registry/wire handling and generated bindings using
  currently unused append-only values. DeviceManager assigns publication/binding generations and
  authorizes a private catalogue connection for SmartcardService using the shared
  `provider-catalogue-admin.open-consumer(kinds)` factory owned by P02M0180's infrastructure
  stage; full Bluetooth completion is not a prerequisite. Each USB reader publication
  lives under the controller binding; no USB sub-function claim model is introduced. Subscribe
  to the current set plus withdrawals and connect by exact publication identity. Registry consumer
  counts are capacity, not authorization; ordinary applications cannot connect to transport endpoints.
  Contribute this service's subscription to that stage's combined-manifest check against the
  shared finite 32-client/subscription bound.
- [ ] Expose a private `smartcard-admin` mint operation to PermissionManager through ServiceManager
  bootstrap. It creates a connection bound to one current reader publication and an operation mask
  (public-read/exchange, transaction, verify/authenticate). The public connection has no reader
  selector that can change that binding. Slot selectors remain within the granted reader, and
  transaction handles inherit both reader and operation scope; public readers cannot invoke verify.
- [ ] Add a `smartcard` application capability and bounded component-to-reader/operation policy to
  the existing manifest/PermissionManager grant path. Policy selects an explicit configured reader
  alias; the private admin endpoint resolves it to exactly one manager-published current identity
  at launch and fails on absence/ambiguity. Never choose the first available reader or trust an
  application's arbitrary reader ID as authorization. Bootstrap policy binds approved aliases to
  provider metadata; minting returns the exact selected identity for the permission audit. The
  default is no reader grant. A fresh launch may resolve an authorized replacement, but an existing
  grant never changes publication generation or silently reconnects to it.
- [ ] Bind reader/transaction grants to the launched client's task observer as well as channel
  lifetime so transferred/duplicated endpoints cannot keep an expired/dead owner's transaction
  alive. Withdrawal closes the reader grant and all transactions; service restart closes all
  ephemeral grants and requires fresh minting. No application receives the admin minting endpoint,
  catalogue endpoint or the driver capability.

## P02M0182 - Transactions, removal and bounded recovery

- [ ] Serialize by reader slot. States are absent, idle, acquired, command-in-flight, cancelling,
  resetting and unavailable. A transaction captures reader publication, slot, provider card
  generation, service reset epoch, owner task/connection and a monotonically unique transaction
  ID. A reinsertion, reset or service restart invalidates old handles even if the ATR is identical.
  Allow at most one in-flight APDU or pinpad operation per slot.
- [ ] Acquisition queues at most eight waiters per slot in FIFO order, each with a deadline;
  a transaction lease is at most 60 seconds and cannot be renewed indefinitely. Ordinary APDU
  requests are capped at ten seconds, pinpad entry at 30 seconds and both at the remaining lease.
  Expired queued acquisitions return timeout without touching the card. Every operation checks
  current identity and ownership before dispatch. Completion versus timeout/removal has one
  serialized winner; no request can produce two terminal replies.
- [ ] Release, client death/disconnect, lease expiry or explicit cancellation stops admission and
  moves an active command to cancelling. The provider owns CCID's control-plus-bulk abort and
  discards late slot responses until matching abort completion. The service does not regrant
  merely because its local timer expired. It waits for an explicit quiescent result, then powers
  the card off/on and reselects the supported PIV application before another client acquires it.
  Clear all service authentication state at every handoff; reset is required even after a clean
  release because card authentication state may otherwise survive across clients.
- [ ] Abort and reset each have a five-second recovery cap. If quiescence/reset cannot be proven,
  mark the slot unavailable, fail its waiters and require an independently completed provider
  recovery/new publication before admitting a new client. Do not reuse a possibly active sequence
  or hand the next client a partially completed operation. The provider may use bounded whole-reader
  recovery if its hardware cannot recover one slot; notify/fail all affected slot transactions.
- [ ] Card removal is a distinct terminal result, immediately invalidates the card generation and
  clears verification state. Keep the transport drain state separate from card absence, so rapid
  reinsertion cannot admit a command before an old abort is safely finished. Reject late replies
  by publication/card/reset/request identity. Disconnect also makes the provider unavailable;
  normal stream silence is not proof of removal. On service/provider-client disconnect, the
  provider aborts/drains its outstanding operations and powers off the slot before accepting a
  replacement service session; new service startup requires an explicit quiescent/reset handshake.
- [ ] Bound the service at eight readers, four slots per reader, 32 reader grants and 32 outstanding
  transactions. ATR is at most 33 bytes; short command APDUs at most 261 bytes and each response at
  most 258 bytes, with service-owned response continuation capped at 16 kB total. Explicitly
  reject a larger advertised reader/slot set or unsupported APDU mode; do not allocate by untrusted
  descriptor length. Queued acquisitions and continuation buffers count against these global caps.
- [ ] Card events use an atomic current snapshot plus monotonically ordered presence/generation
  changes, with at most 16 pending events per client. Never coalesce removal and reinsertion into
  unchanged presence. Close a slow/overflowed stream and require a new snapshot; transaction
  removal/cancellation still runs independently and cannot wait for an event consumer to drain.

## P02M0182 - Delivery and verification

- [ ] Add the service, pure leaf/protocol exports, manifest source/dependency/staging entries,
  reconstructible state declaration, bootstrap roles, PermissionManager grant/mint handling and
  resolver/restart paths. Update all bootstrap/test harness callers. The service is given scoped
  provider access and logging/time only; no device claim, ordinary input capability or storage
  authority is necessary for this pinpad-only slice.
- [ ] Land a test-only in-guest reader/card provider before the USB CCID item. It implements the
  production contract with two reader identities, deterministic ATR/PIV public data and a supported
  P-256 fixture key, local pinpad outcome injection and scripted abort/removal/delayed completion.
  Inject outcomes through a harness-only capability; the application's API has no secret injection
  operation. The provider fixture is absent from shipping configuration. P02M0099 later adapts
  actual CCID readers to this wire and owns its physical USB/sequence/slot-change gate.
- [ ] Host-test production ATR parsing, PIV grammar and transaction/lease/recovery decisions in
  `service-logic` or an equivalent pure leaf without `rt`/`ipc-client`, using separate test modules.
  Include deterministic malformed lengths/TLVs/ATR chains, duplicate/mismatched IDs, stale card
  generations and all relevant T=0/T=1 negotiation/unsupported-mode decisions. Actual CCID framing,
  sequence handling and any future character/TPDU state machines are transport-owned tests,
  required in the change that implements them, not invented service responsibilities.
- [ ] Add the standalone `smartcard-service` x86_64 guest gate against the real service and fixture.
  A granted client waits for insertion, reads the exact ATR, acquires a transaction and exchanges
  allowed PIV APDUs. The pinpad operation succeeds without a PIN in client/provider messages;
  typed PIV authentication produces a signature checked against the fixture's public key by an
  independent host OpenSSL verifier declared as a gate prerequisite. A PIN-bearing VERIFY,
  alternate AID, chained/proprietary command and
  unsupported non-pinpad verification must fail before any disallowed provider operation.
- [ ] Prove reader-A grants cannot reach reader B, read-only grants cannot authenticate and old
  grants fail after withdrawal/republication. Exercise a second queued client, expiry during an
  APDU, owner death with a duplicated endpoint, late completion, cancel timeout and removal with
  rapid reinsertion. Assert the second client receives no command slot until drain/reset completes
  and cannot inherit verification state. A declared timeout without this observed ordering fails.
  Also kill/restart the service during an APDU and verify the replacement session waits for
  provider quiescence/reset. Exercise event overflow/resnapshot and count all handles/buffers
  returning to baseline.
- [ ] Register the gate in `check.sh`, verify-model catalogue, guest-evidence profiles and the
  release-required exact set, with an explicit complete test-image producer. Cover the service,
  pure leaf/protocol, manifest and provider/grant/bootstrap components so changes select the proof.
  Run model validation, generation/source-hygiene checks, focused host tests, this x86_64 gate and
  AArch64/RISC-V cross-builds. State clearly that fixture success establishes the service/pinpad
  policy contract, not unimplemented USB transport or character/TPDU mode compatibility.

Done when a reader-scoped client observes cards and performs allowed bounded PIV operations under
exclusive, expiring transactions; pinpad verification is service-controlled with no PIN-bearing
client path; all loss/recovery/authority tests and registered gates pass; and the typed provider
contract is ready for P02M0099's USB CCID implementation. Non-pinpad PIN entry remains unsupported
until its separately specified trusted secret-entry extension exists.
