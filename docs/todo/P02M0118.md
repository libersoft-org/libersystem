## The annotation, and the two false-green paths it exposed

`covers` is on **every** kernel test, and the reachability gate checks every one - so this says
"every" rather than a number, which is what went stale here twice. (Three counters disagreed on
2026-08-10: 231 `tagged_test!` invocations in the tree, 228 known to the model, 220 seen by the tag

The effect, measured:

|---|---|---|---|
| a codec (`flac`) | 19 of 708 | 5 of 205 | - |
| one tool (`audioconv.rs`) | 10 of 708 | **1** of 205 | **20 s** against 108 s |
| a memory filesystem | 31 of 708 | - | - |

Annotating was mostly mechanical - a default per suite, then narrowed to what each test can actually
reach, which dropped 69 components across 48 declarations that had been over-claimed. What was not
mechanical is what it revealed. **While every kernel test was selected regardless, two gaps were
invisible**, and both are false-green paths:

- **A build covered its crates and not the programs they build.** A tool's own source file resolves
  to its `bin.` component - a longer prefix than the crate directory - so a change to
  `audioconv.rs` selected the audioconv scenario and NO build at all. The guest would have booted
  the previous tool and passed. A change to `bin.xhci` selected nothing whatever, and only the
  empty-selection escalation caught it.
- **Packaging had the same hole.** With the build fixed, the tool compiled and was never staged, so
  the volume still carried the old one and the staleness check was content.

Both are closed and both were only findable once the selection stopped covering for them. The
milestone's own argument applies to itself: a suite that selects everything hides the fact that it
cannot tell what to select.

A fifth defect was mine and in the opposite direction - dangerous rather than quiet. The
`dynamic-report` self-test corrupted the tracked TSV in place and restored it afterwards, which is
fine until a kill, a crash or a concurrent run intervenes; one did, and it left
`docs/DYNAMIC_EXECUTABLES.tsv` mutated in the working tree with the gate failing for what looked
like a real reason. It compares against a temporary COPY now, through an override the check honours
and nothing else sets. **A self-test that can damage the repository is a worse hazard than the
defect it guards against.**

Four defects in the annotation machinery surfaced the same way and are worth recording because each

- **The shipping configuration of sixteen crates cannot be host-tested at all.** Not "is not" -

- **A per-target change planned a boot with no build.** A change under `src/kernel/arch/riscv64`

Two more were defects in this milestone's own new code, caught before they could be trusted, and both
are worth naming because they are the shape of failure the whole design is about - a green result over
work that never happened:

- **A target could enumerate zero tests and report nothing wrong.** Test applicability is read from
  the compiled binaries, and `build.sh --part kernel` writes the ORDINARY kernel into the same
  `deps/` directory under the same `kernel-<hash>` shape. Taking the newest file there picked it,
  found no test descriptors, and gave the target no catalog variants - so a plan could name a target
  in its header and emit not one item for it. Now the newest candidate that actually carries
  descriptors is used, and a target enumerating less than half of its peers' count is a gated error.
- **The runner would have eaten its own plan.** The step loop read the plan on stdin, and the first
  step that reads anything - `./test.sh` boots QEMU, which does - would have consumed the rest of it,
  ending the run early and reporting success over the steps it never took. Read on fd 3 now, and the
  runner refuses to report a result unless it took exactly as many steps as the plan listed.

**Corrected 2026-08-08, and the earlier version of this section was wrong.** It reported a fixed cost
of ~100 s per x86_64 run and concluded that selecting fewer tests was the smallest lever this
milestone had. That arithmetic mixed a run made under load 115 with 64 fuzzing processes against one

| tests | seconds |
|---|---|
| 2 | 9 |
| 20 | 12 |

Which gives **~8 s fixed and ~0.5 s per test**, not 100 s fixed. So:

| | fixed per run | per test | halving the suite saves | 20 of 205 saves |
|---|---|---|---|---|
| x86_64 | ~8 s | ~0.5 s | ~46% | **~89%** |

**Selecting fewer tests is worth a great deal**, which is the opposite of what this document said
before it was measured properly. It needed exact selection to be worth anything at all - the runner
could only be handed tags, so a scoped answer still ran the whole suite - and that now exists:
`TEST_SELECTION` takes stable IDs and refuses one it does not have.

The ordering of the levers is otherwise unchanged, and the biggest is still not this one. Not booting
an emulated target that cannot be affected avoids 2877 s or 6104 s outright; not booting at all when
a host suite answers the question avoids the whole run. Test selection is now a strong third rather
than a rounding error.

Two things this changes. The task list was reordered once on the strength of the wrong number, which
happened to put the architecture policy and the host suites first - still the right order, reached
for a reason that did not hold. And the escalation threshold has to be recalibrated: a rule that gave
up on scoping because it "only" removed half the tests was reasonable at 100 s fixed and is not at 8 s.

## What is wrong, precisely

**1. The tag vocabulary mixes two different questions.** Some tags say what a test EXERCISES -
`audio` is on 5 tests, `image` on 3, `display` on 3, `network` on 1. Others say what a test NEEDS in
order to run at all - `process` is on 35% of the suite, `service` on 30%, `storage` on 19%, because
nearly every test starts a service and launches something. Putting one of the second kind into a
selection collapses it to half the suite, which is exactly what wave 5 does. The waves were built
for the dynamic-linking migration, where "everything that could plausibly be affected" was the right
question; reused as a change-scoping mechanism they answer a question nobody asked.

**2. The scoping tables are guesses, and the real graph already exists.** `lib.sh`'s `COMPONENT_TAGS`
says `src/user/libs/audio/**` is tested with `audio,service,process,storage` - a hand-written
approximation. `manifest.toml` already records, per program and per library, exactly which providers
it links against; `check-dynamic-report.sh` already computes the transitive closure of that graph
and prints it. Asked properly, the manifest answers "who uses `flac`" with `play` and `audioconv`,
and "who uses `pcm`" with seven libraries and the two programs above them. A hand table cannot stay
right as the tool count multiplies; a derived answer cannot go stale.

**3. The cheap precise tests do not run and the expensive coarse ones do.** 49 of 58 crates with
host suites are in no gate: FAT, ISO9660, UDF, LiberMemFS, every image codec, MP3, Vorbis, Ogg, both
compression leaves, `abi`, `proto`, `term`. Those suites are milliseconds each and pin behaviour far
more finely than a boot can. Meanwhile a one-tool change boots a guest and runs 115 mostly unrelated
kernel tests inside it. This is the same suite-in-name-only that `check-host-tests.sh` was written
for, and it is nine crates into a job of fifty-eight.

**4. Nothing connects a changed library to the tools that use it.** Which is the case the whole
exercise exists for: a change to `flac` must test `play` and `audioconv`, and today it either tests
half the system or - if somebody scopes by hand - neither of them.

**5. The architecture choice is manual and unguided.** Emulated runs cost twenty-four times what
x86_64 costs. Nothing says when a change can differ per architecture and when it provably cannot, so
the choice is made by feel, which means either wasted hours or an untested target.

## The design

One pipeline, and each stage has exactly one mechanism. The three vocabularies below are kept
strictly apart, because the measurement above is what happens when one of them is asked to do
another's job.

```
changed paths
      -> component ownership          (one table, manifest-derived where the manifest can say)
      -> reverse dependency closure   (typed edges: link, ipc, syscall, device, format, generation)
      -> affected components
      -> tests whose `covers` intersects them
      -> exact stable test IDs        + the smoke floor
      -> architecture policy          (which targets to build, which to boot)
      -> cost escalation              (scoped, or full when scoped is not worth the bookkeeping)
```

**Tags are the human interface. The component graph is the machine's dependency interface. Test IDs
are the machine's execution interface.** A `uses` list, if it exists at all, is observational - a
record of what a test was seen to touch, useful for auditing the declared graph. It is **not** a
selection primitive; `covers` is.

### Where the edges come from: three sources, unioned

`manifest.toml` is the **dynamic** graph - which `.lslib` a program loads at run time. It is not the
dependency graph, and building the selector on it alone would be a false-negative machine. Measured:
**27 of the 108 crates in this tree are named nowhere in the manifest**, and they are not marginal
ones.

| edge the manifest cannot see | measured |
|---|---|
| `src/fs` - `liberfs`, `libermemfs`, `fat`, `iso9660`, `udf`, `partition`, `fscore` | all seven absent from the manifest; all six non-`fscore` ones are static `path` dependencies of StorageService |
| the kernel's own storage fixtures | `src/kernel/Cargo.toml` links `liberfs`, `partition` and `fscore` **as regular dependencies** |
| the loader | links `liberfs`, `fat`, `fscore`, `abi`, `bootproto` |
| the kernel's `[dev-dependencies]` | **11 userspace library crates** - `aiff flac pcm wav wavpack bmp gif pix png tga webp` - because the `audioconv` and `imgconv` scenarios build their fixtures with the same codecs they test |
| `abi` | 8 static dependents, including the kernel and the loader |

The last row inverts an assumption a selector would otherwise make. "A userspace audio library cannot
affect the kernel" is false in this tree: change `flac` and the kernel's *test* binary is rebuilt, and
the fixture the `audioconv` scenario asserts against changes with it. No dynamic-linking view can show
that edge, because at run time there is no link at all.

Note also that the hand table this milestone deletes is **already wrong here**, not merely coarse:
`COMPONENT_TAGS["src/fs"]` is `filesystem,storage,volume`, which does not reach the kernel or the
loader. So this is not a regression the new design would introduce - it is a live defect the new
design must not inherit.

The graph is therefore the **union** of three sources, each typed:

| source | edges | derived or declared |
|---|---|---|
| `manifest.toml` providers | `link.dynamic` | derived |
| `cargo metadata` over every discovered manifest | `link.static`, `link.static.dev`, `generation.build` | derived |
| an explicit registry | `ipc`, `syscall`, `device`, `format`, `generation` | declared once between components |

`cargo metadata` is already needed for the host-suite reverse graph, so this costs one consumer, not
one mechanism. Cargo has **three** dependency kinds and each maps to a different edge, because each
means something different about what a change does:

| Cargo kind | edge | what a change to the dependency does |
|---|---|---|
| normal | `link.static` | changes the shipped binary |
| dev | `link.static.dev` | rebuilds the test binary; does not ship |
| build | `generation.build` | **may change the dependent's build output through its build script** |

The build row is deliberately the broadest of the three, because a build script's reach is wider than
code generation: the scripts in this tree emit `cargo:rustc-link-arg` (both `src/kernel/build.rs` and
`src/user/build.rs` pass the linker script that way) and `cargo:rustc-env` as well as writing source
into `OUT_DIR`. Defining the edge as "generates source" would be narrower than Cargo's semantics and
would invite an implementation that only looks for generated files.

Keeping them apart matters in both directions. `link.static.dev` must not be `link.static`, or the
kernel joins the closure of every codec for the wrong reason. And `generation.build` must not be
silently filtered out - which is the easy mistake, since build dependencies are neither linked nor
tested. There are four such edges here, and they are not marginal: `system-manifest` is a
build-dependency of both the kernel and CoreServices, and it *generates their source* -
`manifest.rs`, `library_paths.rs`, `program_paths.rs` in CoreServices, the test volume paths in the
kernel. Change it and shipped code changes without a single source file being touched.

That has a consequence for path ownership too: **`manifest.toml` is a build input, not only the
graph's data source.** Editing it regenerates code in the kernel and in CoreServices, so it needs its
own `generation.build` edges to both, independently of whatever it says about providers. Merging build
dependencies into `link.static` would be conservative and merely imprecise; dropping them is a false
green.

### The static graph must be configuration-complete, or it is worse than no graph

"Run `cargo metadata`" does not say **in which configuration**, and in this tree the default
configuration is the wrong one - not marginally, but for the edges that matter most.

| measured | |
|---|---|
| `src/user/apps/tools/Cargo.toml` | `default = []`, and **20 optional `path` dependencies** - every `*-client` and `*-client-provider` pair - reachable only through the `shared-image` feature |
| all 15 protocol crates plus `src/proto` | `default = []`, `ipc-client` optional behind `channel-client-impl`, which `shared-image` enables |
| how the image is actually built | `src/tools/build-shared.sh`: `cargo rustc --release --no-default-features --features shared-image` |

So `cargo metadata` in its default configuration reports that **`tools` depends on none of the client
libraries** and that **no protocol crate depends on `ipc-client`** - while the only configuration that
ever ships enables all of them. A selector built on that graph would answer "nothing uses
`ipc-client`" about the IPC plumbing every service and every tool links. That is a false-green
machine, built by the very fix that was meant to prevent false greens.

The rule, therefore: **an edge that exists under any buildable configuration exists in the graph.**
Union `cargo metadata` over the configurations the tree actually builds - at minimum default and
`--no-default-features --features shared-image`, per target - or, simpler and strictly safer, read the
manifests directly and treat every `path` dependency as an edge regardless of `optional`. Over-selection
from an edge that happens to be inactive costs a test run; under-selection from an edge that was active
in the shipped build costs a shipped regression. Where the distinction is worth keeping, keep it as a
condition on the edge (`when: feature channel-client-impl`) rather than by dropping the edge.

The same question applies one layer down, and is already live: `check-host-tests.sh` runs
`cargo test --manifest-path …` with default features, so for `tools` and every protocol crate **the
configuration that ships is the one never host-tested.** Extending that gate to all 58 crates has to
answer "in which configuration" too, and for at least these sixteen the answer is more than one.

### `covers`, defined so it cannot rot

`covers: X` means **the test contains an assertion able to detect a regression in X's contract.** It
does NOT mean the test's execution path goes through X.

Every integration test runs the scheduler, the allocator, IPC and the loader. If touching counted,
every test would cover everything and the selection would be the full suite wearing new metadata.

The relation is therefore **asymmetric, and the gate must be too**:

| | enforceable | why |
|---|---|---|
| `covers: X` implies X is reachable in the test's execution | yes, gate it | covering something the test cannot reach is a declaration error |
| the test launches X, therefore it covers X | **no** | a scenario that starts StorageService to test `component_host` asserts nothing about StorageService |

Mechanically inferring the second direction rebuilds `touches = covers` under a new name, and `covers`
inflates back to the full suite one honest-looking gate at a time. What the launch scan is good for is
an **audit report** - "these tests reach X and none of them claims to cover it" - read by a person,
never a build failure.

That leaves under-declaration - a test that really does pin `flac` and forgets to say so - with no
static check at all. That is accepted deliberately: it is exactly the failure shadow mode detects (a
test outside S fails while all of S passes), and it is the main reason trust is granted per component
on evidence rather than assumed.

### Stable IDs, and the one key everything is stored under

An ID is an **explicit literal** in the declaration - never derived from the Rust function name.
Globally unique, mandatory, and gated. Renaming a function must not change the ID, because the ID is
what every history below is keyed on; deriving it from the function name means a refactor silently
zeroes all of them. Changing an ID is a deliberate metadata migration.

But a bare test ID is not the unit of work. The planner emits `(check, architecture, environment,
configuration, reason)`, so the unit is:

```
PlanItemKey = (check_id, architecture | host, environment, configuration)
```

| example | key |
|---|---|
| a kernel test in the test guest | `(kernel.audio.flac_roundtrip, riscv64, test-guest, test)` |
| a crate's host suite, default features | `(host.proto, host, host, default)` |
| the same crate as it actually ships | `(host.proto, host, host, shared-image)` |
| the development self-test | `(dev.selftest, x86_64, dev-guest, development)` |

**Age, runtime, failure, shadow and cost history are all keyed on `PlanItemKey`, and so are the
regression fixtures.** Every field earns its place by being a way the same check can differ:

- the test ID alone loses the **architecture**, and a riscv64 result is not an x86_64 result;
- `(test, arch)` still loses the **environment**, so a regression fixture for the `dev_agent` can
  confirm the right test on the right target while never checking that the planner chose the dev
  guest - the only part of that plan that could have been wrong;
- `(test, arch, environment)` loses the **configuration**, and the section above is what makes that
  concrete: `proto` must be host-tested under default features *and* under `shared-image`, because
  those two builds do not even contain the same dependencies. Both runs would collide on
  `(host.proto, host, host)`, the shipped configuration would inherit the default one's freshness, and
  the age bound would report as covered a configuration that has never run.

`configuration` canonically names the feature set, the Cargo profile and the build mode; it does not
repeat the target, which `architecture` already carries. Encoding it into `check_id` instead
(`host.proto.shared-image`) works and is worse - it makes "all configurations of this check" a string
prefix match rather than a projection.

### Not every key exists: the check catalog

Tests are compiled per target and the counts differ: **205 on x86_64, 196 on aarch64** (riscv64 not yet
measured). A bound keyed on `(test, arch)` without knowing which pairs are real reports the missing
ones as permanently stale, and the age scheduler then chases combinations that cannot exist.

Applicability cannot be inferred from the path, either. `cfg(target_arch)` gating on tagged tests is
**not** confined to the arch trees - `test_suites/kernel.rs` has eight, `test_suites/hardware.rs` six,
`sched/tests.rs` two - so a test living in a shared file may exist on one target only. It has to be
**derived from what actually compiles**, per target.

And it is not only tests. **The catalog covers every executable planner item without exception** -
builds, host suites, manifest and inventory gates, conformance runs, kernel tests, the development
checks, and any check kind added later - each with its own valid combinations. Builds are in it for
the same reason as everything else: `build.kernel / riscv64 / host / test` is something the planner
emits, and the invariant below says the planner emits nothing outside the catalog. What a build
detects is a compile failure, so its `covers` is the set of components it compiles.

So the catalog is over **checks**, and it enumerates whole variants rather than one axis:

```
check_catalog: check_id -> { kind, covers, applicable_variants: [{ architecture, environment, configuration }] }
```

```
host.proto                    -> host    / host       / default
                                 host    / host       / shared-image
kernel.audio.flac_roundtrip   -> x86_64  / test-guest / test
                                 aarch64 / test-guest / test
                                 riscv64 / test-guest / test
dev.selftest                  -> x86_64  / dev-guest  / development
```

This gives the model one invariant instead of three separate tables:

> **The universe of runnable work is exactly the set of `PlanItemKey`s derivable from the check
> catalog.** Age, runtime, failure, shadow, cost history and the regression corpus all range over that
> same universe, and the planner may emit nothing outside it.

Both halves matter. Without the catalog the age bound invents keys that can never be fresh; and the
planner must never hand a guest a check that does not exist there - an exact `TEST_SELECTION` naming a
test the aarch64 binary never compiled either errors or, worse, silently matches nothing.

### Architecture policy

Per target, not per category. "Arch-sensitive" is not an answer on its own - each class must name the
exact set of targets to boot, and every per-target file in this tree has a row:

| changed | built | booted |
|---|---|---|
| `src/kernel/arch/x86_64/**`, `src/kernel/linker/x86_64.ld`, `src/loader/src/arch/x86_64/**`, `src/user/user.ld` | all three | x86_64 |
| the same three trees for aarch64 (`src/user/user-aarch64.ld`) or riscv64 (`user-riscv64.ld`) | all three | that target |
| `src/kernel/arch/common/**`, `src/kernel/arch/mod.rs`, the ABI, the boot protocol, the wire formats | all three | all three |
| shared loader source - `src/loader/src/{main,uefi,elf,heap,blockio}.rs`, `arch/mod.rs` | all three | all three |
| `src/user/build.rs` - it *selects* one of the three user linker scripts by target | all three | all three |
| `src/boot/qemu-run.sh` and the rest of the harness - thirteen architecture-specific branches | all three | all three |
| ordinary userspace, no arch marker found | all three | one (x86_64) |

The distinction that matters and is easy to get wrong: **a file that is per-target selects its target;
a file that chooses between targets selects all of them.** `user-riscv64.ld` is the first kind.
`src/user/build.rs`, which maps `target_arch` to one of the three, is the second - a bug in its
mapping is invisible on the target it maps correctly. The loader has both kinds in one crate, which is
why it gets two rows rather than one.

**Cross-building all three proves a branch compiles, not that it is right**, so the mechanical scan
below is a *conservative risk classifier* and never a proof of neutrality. A crate containing
`cfg(target_arch)`, `cfg(target_pointer_width)`, `asm!`, `global_asm!`, a target-specific dependency
or a target-aware `build.rs` is **definitely** architecture-sensitive. A crate containing none of them
is a **candidate** for neutral - `usize`, `repr(C)` layout, alignment, atomics and a dependency's
internals can all differ without any of those appearing. Confidence comes from cross-building plus
shadow evidence plus the periodic full sweep, not from the scan.

Given the cost table above, this section is where most of the milestone's value is. Getting one row
wrong in the cheap direction costs an untested target; getting it wrong in the expensive direction
costs 6104 seconds. Both are worth a negative fixture.

### Execution environments are part of the plan, not a later refinement

The planner covers every kind of check, and this tree already has checks that cannot run in the same
guest. `qemu-run.sh` refuses `DEV_PROFILE=1` together with `TEST=1` outright, and two harnesses -
`src/boot/dev-selftest.py` and `src/boot/proto-test.py` - fail with "is `just dev-up` running?"
against anything else. So a plan item carries an environment from the start:

| environment | runs |
|---|---|
| `host` | the 58 crate suites, the manifest and inventory gates, the mechanical scans |
| `test-guest` | `qemu-run.sh TEST=1` - the tagged kernel suite, per architecture |
| `dev-guest` | `qemu-run.sh DEV_PROFILE=1` - `dev-selftest.py`, `proto-test.py`, `perf-gate.py`, the scenarios |

A change to `src/user/services/core/src/dev_agent.rs` must plan a **dev-guest** run; today it plans a
test-guest sweep that cannot reach the agent at all. This is separate from the deferred per-test
`requires` - that one still has no consumer, because within a single environment every guest is
identical. The environment dimension has three consumers today.

The **kernel subsystems** are written down and deliberately NOT applied - seven `[[risk_class]]` rows with a class and the evidence that would discharge each, validated (a class naming a path that no longer exists fails the gate) and printed by `verify-model check` every run. Narrowing them is one line each once the evidence exists; guessing now is where a selector is most likely to be wrong.

- [x] **Escalate on measured cost, and model the cost as fixed plus variable, per environment.**
  `cost(architecture, environment, selection) = fixed_startup(architecture, environment) +
  sum(measured duration of each selected item)`. A plain sum of test times is badly wrong here: the
  measured fixed term is ~100 s on x86_64 and ~1450 s on aarch64, so a "90% smaller" selection is a
  15% cheaper run. The environment belongs in the key because a dev guest and a test guest do not
  start alike. When the estimate lands within some fraction of the full suite, run the full suite -
  derive that fraction from real timings, per architecture, because the honest answer on x86_64 may be
  "almost never scope, just boot once and run everything." A wrong cost estimate is the one error here
  that cannot produce a false green, so calibrate it last.

  PARTIAL 2026-08-08: `cost(architecture, environment, selection) = fixed + sum(variable)`, with the fixed term charged ONCE per (architecture, environment) pair that appears - two hundred selected tests are one boot. Every plan prints its estimate as a share of a full run and says so when scoping stops paying. A step's wall clock is decomposed across the keys it discharged rather than charged to each of them; recording it per key was tried first and turned one 110-second boot into an estimate of six hours. The escalation is advisory - it reports rather than widens, because escalating on an ESTIMATE lets a bad estimate quietly cost hours.

- [x] **Turn age into a bound over real `PlanItemKey`s.** A test is not fresh; a *key* is. The
  architecture policy deliberately boots one target for ordinary userspace changes, so the steady state
  it produces is x86_64 fresh and the other two ageing - a bound keyed on the test alone reports the
  whole suite fresh while two targets rot. Key runtime, failure and shadow history the same way; an
  aarch64 timing says nothing about riscv64, and a test-guest timing says nothing about a dev guest.

  DONE 2026-08-08: `.build/state/verify-history.json`, keyed on the four-field key and written by `verify.sh` after every step. `./verify.sh --age` reports what has gone stale over the CATALOG's universe, so a key that cannot exist is never reported as eternally stale, and orphaned entries are listed rather than deleted because a vanished key is usually a rename.

- [x] **Build the check catalog, and derive its variants from what compiles.** 205 tests exist on
  x86_64 and 196 on aarch64, and `cfg(target_arch)` gating is spread through shared files - eight in
  `test_suites/kernel.rs`, six in `hardware.rs`, two in `sched/tests.rs` - so the path cannot answer
  which target a test exists on. Record `check_id -> { kind, covers, applicable_variants }` where a
  variant is `{architecture, environment, configuration}`, derived per target from the compiled lists
  and covering **builds**, host suites, gates, conformance runs and the dev checks as well as kernel
  tests - every kind of item the planner can emit. **This catalog defines the universe** every history
  and the regression corpus range over, and the planner may emit nothing outside it. Without it the age bound invents keys that can never be fresh, and an exact
  `TEST_SELECTION` can name a test the target's binary never compiled.

  DONE 2026-08-08: 301 checks and 707 variants, kernel-test applicability read per target from the compiled binaries' `CASE` symbols - one `nm`, no boot. Guarded against reading the wrong binary, which is a real failure here rather than a theoretical one.

- [x] **Name what actually runs the scheduled sweep.** There is no CI, so "on a timer" schedules
  nothing. Either a systemd timer on the development machine at a quiet hour, or - simpler and more
  honest for one machine - stale tests join the next manual run and the runner says it did so.

  DONE 2026-08-08: every completed run ends by reporting what it left stale and naming `--age` and `--sweep`. Deliberately a report rather than an automatic join: silently adding an emulated boot would turn a two-minute scoped run into a two-hour one, and the same measurement that justifies the architecture policy prices that at 2877 s. It is a decision with a price tag, so it belongs to whoever is at the terminal.

- [x] **Keep a full snapshot sweep as well; the age bound is not a substitute.** Stale tests joining
  the next manual run spreads coverage across many different trees: some tests on Monday's commit,
  others on Wednesday's. That satisfies an age bound while never once establishing that **one** revision
  passes everything. Both are needed - the age bound catches individual rot, the snapshot sweep catches
  the combination. Run the whole suite on all three architectures at one fixed revision, and do it in a
  worktree so the sweep is not racing the tree it is judging.

  DONE 2026-08-08: `./verify.sh --sweep` refuses a dirty tree, creates a `git worktree` at HEAD, and runs build-all, check-all, test-all-three inside it. That is the part the age bound cannot do - stale keys joining the next manual run spreads coverage over many different trees, which satisfies a bound while never once establishing that ONE revision passes everything.

- [x] **Restore the release gate, unconditionally.** This was in the first draft ("the whole suite on
  all three architectures is right before a release") and was lost in the consolidation. It is not
  covered by anything else here: TRUSTED, the cost estimator, the age bound and the selector are all
  mechanisms for spending less on an ordinary change, and every one of them should be **ignored** when
  cutting a release image. Build all, check all, boot all three, full suite, at one immutable revision.
  Releases are rare and the insurance is nearly free; a wrong selector decision shipped in an image is
  not.

  DONE 2026-08-08: `./verify.sh --release` refuses a dirty tree, prints the revision, and runs `./build.sh --arch all && ./check.sh && ./test.sh --arch all` without consulting the planner at all - it is the same flat path the fail-open fallback uses, for the same reason.

- [x] **Measure the result and write the numbers here.** Selection size and wall clock, before and

## Follow-ups: closing the gap between the implementation and the design

An outside audit of the implementation at `44a9d5c1`. Each item below was verified against the tree
before being written down; the two that were one-line defects rather than missing work are already
fixed and are recorded here as evidence that the rest are worth taking seriously.

### Fixed on the spot

- [x] **Shadow returned green for two of its four verdicts.** Only `CandidateMiss` exited non-zero,
  so `Void` - the comparison judged nothing - and `SelectionFailed` both returned 0, and `verify.sh`
  then printed "no evidence against the selection" over a run that had produced no evidence either
  way. Only `Consistent` is green now.
- [x] **Trust counted a failed comparison as evidence of a target.** `architectures_seen` filtered on
  the component and the model hash but NOT on the verdict, so five clean x86_64 comparisons plus one
  riscv64 `CandidateMiss` satisfied "evidence from two targets" - a certificate earned partly on the
  strength of a run that found a fault. Renamed to `clean_architectures_seen`, filtered, and pinned
  by a test.
- [x] **A comment in `verify.sh` claimed rename handling that does not exist** (see P0 below). The
  behaviour is unchanged and the comment now describes it truthfully, because a comment that lies
  about a safety property is worse than none.

### P0 - each of these could produce a green result over something unverified. All six are closed.

- [x] **Consult the trust store on an ordinary run.** `trust.rs` defines SHADOW as "every scoped
  decision is validated against a full sweep before it is believed", and nothing enforces it:
  `./verify.sh` computes a scoped plan and executes it whatever the component's level. `--trust` is
  a report. Until a component is TRUSTED under the current model hash, a scoped run must not be the
  only thing standing behind a green - either by running the shadow comparison itself or by refusing
  to call the result equivalent to a full verification.

  DONE 2026-08-08: `verify-model level` answers what a scoped green is WORTH - FULL, TRUSTED, or SHADOW naming the components with no evidence - and `verify.sh` prints it as the last thing every run says. It reports rather than refuses, because nothing is TRUSTED yet and nothing can be until comparisons accumulate; refusing would make the tool unusable on the day it started being honest. `VERIFY_REQUIRE_TRUST=1` turns it into a failure for anyone who wants the strict contract, and was watched doing so.

- [x] **Derive architecture sensitivity instead of only declaring it.** The design called for a
  mechanical classifier - `cfg(target_arch)`, `cfg(target_pointer_width)`, `asm!`, `global_asm!`,
  target-specific dependencies, a target-aware `build.rs` - as a conservative risk signal. Only the
  hand-written path table exists. Measured: **13 files under `src/user` contain `global_asm!`**, and
  `volume-client-provider` has a per-target branch for each of the three (`jmp` / `b` / `tail`) while
  planning `boot: x86_64` only. Cross-building catches a branch that stops compiling; it does not
  catch one that compiles and jumps wrong.

  DONE 2026-08-08: `archrisk.rs` scans every source and manifest for `target_arch`, `asm!`, `global_asm!`, `naked_asm!`, `target_pointer_width`/`endian`/`feature`, target-specific dependency tables and target-reading build scripts, and attributes each finding to the owning component. **25 of 218 components** come back sensitive - targeted rather than blanket. A change to `volume-client-provider` now boots all three and says why; `flac`, `liberfs`, `xhci` and `audioconv` still cost 2-3%.

  Two properties keep it a risk classifier rather than an oracle. It can only WIDEN - a component with no marker keeps whatever the policy table said, because absence proves nothing. And an explicit rule OUTRANKS it: every line of `src/kernel/arch/aarch64` is target-specific, from which a scan can only conclude "all targets", while the table knows the answer is aarch64 alone - letting the scan win would spend 6104 s of riscv64 on an aarch64-only change. Both directions are tested and both were watched to fail.

- [x] **Parse renames and deletions in the model, not in the shell.** `git status --porcelain` reports
  `old -> new` and `verify.sh` keeps only the new path, so moving a file out of a component does not
  select that component, and a rename into `docs/` can look like nothing changed. The regression
  corpus uses `git diff --name-only` instead, so it exercises a different diff parser from the one
  production uses - which is why it never caught this. One parser, in `verify-model`, over
  `--porcelain=v2 -z`, feeding both sides of a rename to the planner, used by the corpus too.

  DONE 2026-08-08: `changes.rs`, over `--porcelain=v2 -z` and `--name-status -z`, returning BOTH sides of a rename. `verify.sh` and the regression corpus now call the same function - they previously used three different spellings of the question, which is why the corpus could not catch the shell's defect. Seven tests, including the end-to-end case: a file renamed from `src/kernel/` into `docs/` selects the kernel rather than reading as a documentation change. Writing them found two more defects in the new parser itself - the unmerged record has nine metadata fields and not ten, and `split` returns an empty field rather than `None`, so a truncated rename record was being accepted with an empty origin.

- [x] **Guarantee one guest step per booted architecture.** `commands.rs` derives guest steps from the
  kernel-test items in the plan, and a target with no enumerated tests contributes none - so a plan
  can report `booted: x86_64, aarch64, riscv64` and emit no aarch64 boot at all. That is exactly the
  case the missing-enumeration escalation is supposed to cover, and the escalation makes the plan
  FULL without making the step appear. The invariant to add and gate: for every architecture in
  `architectures_booted`, exactly one guest execution step exists.

  DONE 2026-08-08: guest steps were derived purely from kernel-test plan items, so a target with no enumerated tests contributed none and a plan could report `booted: x86_64, aarch64, riscv64` while running two of them. Any booted architecture without a step now gets one, carrying no keys because nothing was enumerated to record against. Gated by a test asserting the step set EQUALS the booted set, and by both directions of the unenumerated case - in scope escalates and boots, out of scope changes nothing.

- [x] **Pin shadow to an immutable source snapshot, not to the model hash.** `--shadow` compares the
  model hash before and after the sweep, and an ordinary source edit does not move it - so a tree
  edited during a multi-hour emulated sweep passes the check. `source_digest()` exists and is only
  written into the record afterwards. Compare it before and after, or better, run the sweep in a
  worktree the way `--sweep` already does and delete the race instead of detecting it.

  DONE 2026-08-08: `verify-model source-digest` (HEAD plus the bytes of every dirty file) is taken before and after the sweep and the comparison is void if it moved. Demonstrated rather than assumed: appending a comment to `flac/src/lib.rs` moves the source digest and leaves the model hash **unchanged**, which is exactly why comparing model hashes did not close the race. The model hash is still checked as well - they answer different questions.

- [x] **Model the artifact chain: source -> build -> packages -> volume -> guest.** `build.packages`
  and `build.volume` declare `covers = ["manifest", "harness.tools"]`, which is not the set of their
  real inputs, and `build.sh` deliberately does not chain them. Concretely: CoreServices depends on
  `src/term`; a change there selects `build.user`, need not select `build.packages` or
  `build.volume`, and `test.sh`'s staleness check consults a hand-written `VOLUME_SOURCES=(user fs
  wire abi proto idl tools/mkpackages)` that contains **neither `term` nor `volume`**. So the guest
  can boot a system volume that predates the change and pass. Build receipts - artifact digest over
  input digests, configuration and architecture - are the durable fix; another hand-written list is
  not.

  DONE 2026-08-08, both halves, and the false-green path is demonstrated closed. **The plan side**: `build.packages` and `build.volume` declared `covers = [manifest, harness.tools]`, which is not their input set - they compile nothing, they ASSEMBLE, and their inputs are every artifact the manifest stages. Covers is now the closure of every staged program and library over `link.static`, `link.dynamic` and `generation.build`, so a `src/term` change selects `build.user`, `build.packages` AND `build.volume`. Deliberately wide: packaging is cheap and a stale volume is not. A codec change went from 2% to 3%.

  **The staleness side**: `lib.sh`'s `VOLUME_SOURCES` was `(user fs wire abi proto idl tools/mkpackages)` and the derived answer is `(abi bootproto fs idl proto term tools user volume wasm wire)` - four missing, two of them serious. CoreServices statically links `src/term`, so editing the terminal stack could compile a new CoreServices, skip packaging, and leave the check content that the volume was current; `src/volume` IS the factory files the volume ships. Both fixed, and `verify-model check` now compares the literal list against the derived one in both directions - watched failing when `term` is removed. Verified end to end: editing `src/term/src/lib.rs` moves the volume digest, which it did not before.

## What this deliberately does not do

Nothing here weakens an assertion, deletes a test or makes a gate optional. The failure being designed
against is not a slow suite - it is **a fast suite that stopped looking**, which is what every gate in
`check.sh` exists to prevent. Every default errs toward running more: an unrecognised path gets the
whole suite, a missing declaration fails the build, and the smoke floor runs whatever else was
selected.

## Appendix: three rounds of outside review

This milestone went through three rounds of outside review. The design above is the result; this records what
each round contributed and what was rejected, so a rejected idea is not proposed again.

**Round one** (read the file, not the tree) got four things factually wrong and they are worth keeping
straight: 115 is the wave-5 SELECTION, not the 205-test suite; `test.sh` boots QEMU **once** for the
whole suite, so there is no per-test boot cost to amortise with snapshots; drivers here are
**userspace** (`src/user/drivers/`), so the "change one driver, test the kernel" example describes a
monolithic kernel this is not; and there is no CI, so cancelling superseded runs does not apply. Its
real contributions were that `uses` is too narrow for IPC, syscall and device edges, that the
architecture claim was too absolute, and shadow mode.

**Round two** read the tree properly and found a live defect: `component_tags` excluded `*.sh` and
`src/tools/*` from kernel testing entirely, which excused `src/boot/mkimage.sh` (builds the image),
`src/boot/qemu-run.sh` and `test-kernel.sh` (boot and judge the guest) and `src/tools/mkpackages`
(listed in `VOLUME_SOURCES`, so its output IS the system volume). Fixed in `lib.sh` at `78e18ee`.

**Round three** found that fix over-claimed, and it was right. **Only the path dimension of that
false green is closed.** `test.sh` still defaults to x86_64 (`archs=(x86_64)`), so a change to
`qemu-run.sh` - which carries thirteen architecture-specific branches - resolves to FULL and then runs
FULL on one target. A bug in its riscv64 branch still passes `--for-change` green. The automatic
architecture policy above is what closes it.

Round three also produced the design's two best ideas - dry shadow, and one planner instead of one
selector per tool - and corrected three overstatements of mine: that a broken gate fails loudly on its
own, that a mechanical scan proves architecture neutrality, and that `test.sh --for-change` exiting 0
means what a caller will read it as.

Its most useful structural point was not technical: the document had grown two generations of design
in one file, with the superseded version first. The section above is now the single authoritative
specification, and this appendix is history.

**Round four** reviewed the consolidated version and was right on every point; nothing was rejected.
Its central finding is that the graph was to be derived from `manifest.toml`, which describes the
**dynamic** link graph only - so all of `src/fs` would have been invisible. Verified and worse than
reported: 27 of 108 crates are absent from the manifest, the kernel statically links `liberfs`,
`partition` and `fscore`, and its `[dev-dependencies]` pull in eleven userspace codecs, so a `flac`
change rebuilds the kernel's test binary. The current hand-written table has the same hole
(`COMPONENT_TAGS["src/fs"]` reaches neither the kernel nor the loader), so this is a live defect being
inherited, not one being introduced. It also caught the document contradicting its own definition of
`covers` - one task demanded `program_elf(X) ⇒ covers(X)`, which is the `touches = covers` collapse the
definition exists to prevent - and it caught test age being keyed per test when the architecture policy
guarantees the three targets age at different rates. Its other adopted points: trust must be a
certificate against a versioned model rather than a permanent property of a name, fail-open cannot be
implemented inside the process that fails, the arch classifier needs a boot-target set per class and
not just a sensitive/neutral verdict, the planner needs execution environments today because
`DEV_PROFILE` and `TEST` are mutually exclusive, the release sweep was lost in the consolidation, an
age bound is not a snapshot sweep, cost is fixed plus variable, and a shadow miss must be
distinguished from a flake.

Checking round four's claims turned up two things it did not raise. The measured selection was
recorded as "115 of 212"; the guest's own line says `running 109 tests (96 skipped, 205 total)`, and
the denominator differs per target (196 on aarch64) because arch-gated tests are not compiled
elsewhere. And solving the two measured points for a fixed and a variable term shows the fixed cost
dominates so heavily - ~100 s of a 140 s x86_64 run - that **test selection is the least valuable idea
in this milestone**; the architecture policy and the host suites are worth several times more. The task
list is now ordered by that measurement rather than by the pipeline.

**Round five** raised four points; all four were adopted and one of them found a defect in round
four's own fix. Round four established that the graph must include static Cargo edges. Round five
asked *in which configuration* those edges are read, and the answer in this tree is damning:
`default = []` everywhere that matters, `tools` reaching its 20 client libraries only through
`shared-image`, all 15 protocol crates reaching `ipc-client` only through `channel-client-impl`, and
`build-shared.sh` building the image with `--no-default-features --features shared-image`. A selector
reading the default configuration would report that **nothing depends on `ipc-client`** - a false-green
machine built by the fix for false greens. The rule is now that an edge existing under any buildable
configuration is an edge, and the same question turned out to apply to `check-host-tests.sh`, which
tests those sixteen crates only in the configuration that never ships.

Its second point was that `(test ID, architecture)` is not enough without knowing which pairs exist:
205 tests compile on x86_64 and 196 on aarch64, so a bound over all pairs chases combinations that
cannot be fresh. Verified, and worse than stated - `cfg(target_arch)` gating is not confined to the
arch trees but scattered through `test_suites/kernel.rs`, `hardware.rs` and `sched/tests.rs`, so
applicability cannot be inferred from a path and must be derived from what compiles. Its third and
fourth points were structural and both correct: the five-part trust certificate should be one
`model_hash` over the actual declarations (hashing a *schema* leaves `covers: [flac]` -> `covers: []`
undetected), and every history and fixture should be keyed on the planner's own unit,
`PlanItemKey = (check, architecture, environment)`, so a regression fixture can check that the right
environment was chosen and not only the right test.

Round five's closing advice is also taken: further theoretical review has passed the point of
diminishing returns. What finds the next class of defect is implementing phase one and reading the
plans the selector actually produces.

**Round six** judged the design implementable and raised two data-model corrections, both consequences
of round five's own fix and both adopted. First, `PlanItemKey` had no configuration field, so the two
runs that round five had just declared necessary - `proto` under default features and under
`shared-image` - collide on one key, and the shipped configuration silently inherits the default one's
freshness. Second, `cargo metadata` has three dependency kinds, not two: build dependencies are
neither linked nor tested, which makes them the easy ones to filter out, and there are four here -
`system-manifest` generates `manifest.rs`, `library_paths.rs` and `program_paths.rs` for CoreServices
and the test volume paths for the kernel. Dropping that edge would let a change regenerate shipped
source with nothing selecting it. Writing it down also settled a question neither round asked:
`manifest.toml` is itself a build input with `generation.build` edges into the kernel and CoreServices,
not only the file the provider graph is read from.

**Round seven** found the `configuration` field added by round six had not been propagated through the
rest of the model, and it was right in all four places. `model_hash` did not include the configuration
catalog, which is the one that could have outlived its evidence: `shared-image` is a *label*, so adding
a feature to it changes what is tested while leaving the label - and, if the graph unions every
optional edge anyway, the graph hash - unmoved. The planner task still described plan items as
`(check, architecture, environment, reason)`, which would have let an implementation get the key right
and emit JSON that cannot distinguish the two `host.proto` runs. The applicability matrix was still
one axis over tests when the planner schedules host suites, gates and the dev self-test too; it is now
a **check catalog** of whole `{architecture, environment, configuration}` variants, which replaces
three separate tables with one invariant - the universe of runnable work is exactly the keys derivable
from the catalog. Its wording point was also grounded rather than pedantic: `generation.build` was
defined as "generates source", but the build scripts here also emit `cargo:rustc-link-arg` (the linker
script, in both `src/kernel/build.rs` and `src/user/build.rs`) and `cargo:rustc-env`, so a narrow
definition would invite an implementation that only looks for generated files.

**Round eight** found two consistency defects and no design ones. A sentence in the stable-IDs section
still described the plan item as `(check, architecture, environment, reason)` two lines above the
four-field `PlanItemKey` - a leftover from round seven's edit, and exactly the kind of contradiction an
implementer resolves by picking the wrong one. And the check catalog enumerated host suites, gates and
the dev self-test but not **builds**, while the invariant says the planner emits nothing outside the
catalog and the planner plainly emits builds; that left a choice between breaking the invariant and
excluding builds from the unified model. Both fixed; the catalog now says "every executable planner
item without exception", and a build's `covers` is the set of components it compiles, because what a
build detects is a compile failure.

**The design is frozen here.** Eight rounds produced, in order: real architectural defects, then
overstatements, then one genuine false-green hole (the configuration-blind dependency graph), then
propagation gaps, and finally stale sentences. That progression is the signal to stop. The next audit
is worth doing against `./verify.sh --for-change --plan` over twenty or thirty real commit ranges from
this repository's history, checking the `PlanItemKey`s it actually emits - not against this document.
One thing deliberately left to implementation: the concrete schema of the configuration catalog, which
belongs in the data model rather than in prose.

## Three older gates, now with negative fixtures

Recorded as remaining when P02M0118 closed: `development-gate`, `artifact-metadata` and `volume-layout`
were the three gates with no proof that they refuse. Each now runs a self-test first, on the same
argument the rest of them use - a validator exercised only against a valid input is not exercised,
and the tree is valid, so it passes, and it would pass just as well if it had stopped looking.

**`volume-layout`** got a wrapper, `tools/check-volume-layout.sh`, which compares against a **copy**
of the package and never the tracked artifact. Three injections: a faithful copy must be accepted, a
copy with one entry renamed in place must be refused, and 512 random bytes must not be read as an
empty archive. The copy-not-in-place rule is not fastidiousness - a self-test that edited a tracked
file in place left `docs/DYNAMIC_EXECUTABLES.tsv` corrupted in this working tree once, when a
concurrent run landed between the damage and the repair.

**`artifact-metadata`** takes its manifest from `ARTIFACT_METADATA_MANIFEST` when injected, and
`--contracts-only` stops before the ELF checks an injected manifest does not describe. Three
injections: a program that lost a provider, a program that changed owner, and - the one that matters
most for a table-versus-table check - a manifest describing NO dynamic executables at all. A
selector that matches nothing compares nothing, and that is the shape this kind of gate fails in.

**`development-gate`** takes `DEVELOPMENT_GATE_MANIFEST` and `--manifest-only`, since checks 3 and 4
build crates and read the built package. Injections: no program marked development-only (the gate
would pass vacuously), and an ordinary shipped program marked development-only, which the crate's
`required-features` check must refuse.

### The self-test that proved nothing, briefly

Worth recording because it is the exact defect these gates exist to catch, arriving inside the thing
meant to catch it. The third injection first named a program that does not exist in the manifest, so
`jq` changed nothing, the gate was handed the real manifest, it passed - and the self-test read that
pass as "the injection was correctly refused". It was caught by deliberately breaking the rule it
guards and finding the self-test silent.

It now asserts that the injection LANDED - the development-only count must go up by exactly one -
before reading its result. Every injection that transforms an input should do the same; an injection
that quietly did nothing is indistinguishable from a gate that quietly checks nothing.

## Fourth round of outside review: the evidence layer, not the selector

An audit against `476e93ef`, the first to say it found nothing wrong with the SELECTION. Its six
previous P0s stayed closed; every claim it made this round was checked against the tree and five of
six held. The one that did not is worth stating: it reported `development-gate`, `artifact-metadata`
and `volume-layout` as still lacking negative fixtures. All three had gained one hours earlier
(`src/tools/check-*.sh`, and each runs its injections before it is allowed to approve anything). The
audit read a document that said they were missing rather than the scripts that said otherwise - which
is the last task below, and the reason it is not cosmetic.

What remains is one theme with several faces: **the trust machinery is designed per-universe and fed
from one universe.** Nothing here is a false green today. Every one of them is a way for a
certificate to mean less than it says.

- [x] **Only one universe produces evidence.** `main.rs` writes every shadow record as
  `Universe::TestGuest`. Nothing produces a `Host` or `DevGuest` record, and `trusted_everywhere`
  requires `Host` AND `TestGuest`, so it cannot return true for any component, ever. A store that can
  only answer "not trusted" is not a trust model; it is a constant. Either `--shadow` learns to
  compare a host-suite selection and a dev-guest selection against their full runs, or
  `trusted_everywhere` stops asking for evidence the pipeline cannot produce - and the first is the
  honest one, because the host suite is where a scoped selection is cheapest to be wrong about.

  DONE 2026-08-10, the first way. `--shadow` now produces a HOST record as well: the runner walks
  `verify-model host-checks` (the catalog's own list, so the shell decides nothing), runs each one,
  and writes `id PASS|FAIL` plus a `total` line - written directly rather than scraped, because the
  host runner knows each check's id and its exit status. `shadow::compare_host` reads it through the
  same comparator the guest uses; the `kernel.` prefix turned out to be the only guest-specific part
  of it.

  Builds are excluded from the host walk: re-running three architectures' builds to answer "did
  anything outside the selection fail" would cost more than the sweep it is comparing against, over
  artifacts the sweep already produced.

  And `trusted_everywhere` no longer names a fixed pair. `catalog::judging_universes(component)`
  derives them from the environments the component's own checks run in, so a development-only binary
  is judged by `DevGuest` and a host tool is not asked for guest evidence. A component nothing covers
  has no judges and answers FALSE rather than vacuously true - an empty `all()` is true, and that is
  exactly the shape this defect had.

  `DevGuest` still has no producer. It is one environment with one target and one check
  (`dev.selftest`), and nothing that changes only dev-guest code is common enough yet to have
  motivated a comparison; the machinery now accepts one the moment there is something to feed it.

- [x] **`REQUIRED_ARCHITECTURES = 2` applied to universes that cannot have two.** The rule is right
  for `TestGuest` and impossible for the others: `Host` runs on the host and has exactly one target,
  `DevGuest` is built for x86_64 alone. A universal constant makes those two permanently
  unqualifiable for reasons that have nothing to do with their evidence. The requirement belongs
  per-universe - a target SET each universe can actually reach, taken from the catalog rather than a
  number - and `trusted_everywhere` belongs over the universes that can judge THAT component, so a
  development-only binary needs `DevGuest` and a host tool does not need `TestGuest`.

  DONE 2026-08-10 for the requirement: `required_architectures(universe)` answers 2 for `TestGuest`
  and 1 for `Host` and `DevGuest`, and the number lives beside the universe because it is a property
  of what that universe can reach. `trusted_everywhere` still asks for a fixed pair; that is part of
  the evidence-producer task above and moves with it.

- [x] **The selector's own source is not in the model hash.** `SELECTOR_VERSION` is `1` and is bumped
  by remembering to. It has not moved across `archrisk`, `Reach::TestBuild`, cost escalation and
  exact selection - four changes to what the selector decides. The inputs it hashes did move, so
  there is no live exploit, and that is luck rather than design: a purely algorithmic change with
  identical inputs would leave every certificate standing over a selector that now answers
  differently. Hash the contents of `src/tools/verify-model/src/*.rs` and delete the constant. A
  certificate should lapse because the code changed, not because someone typed a bigger number.

  DONE 2026-08-10: `selector_source_digest` hashes every `.rs` under `src/tools/verify-model/src`, by
  name and content, and the constant is deleted. Read at RUN TIME from the checkout rather than
  `include_str!`, because a binary built before an edit would otherwise carry the old hash - and a
  stale binary agreeing with itself is the thing being guarded against. Demonstrated: appending a
  comment to `archrisk.rs` moves the model hash and removing it moves it back.

- [x] **`source_digest` still parses `git status --porcelain` by hand.** It splits on `" -> "` and
  keeps the destination, which is the exact defect `changes.rs` was written to fix, and it is not
  NUL-safe so a path with a newline in it is read as two files. The shadow pin it produces is the
  thing that decides whether a comparison is still about the tree that was compared. It should be
  built from `changes.rs`: HEAD, plus each change's kind, origin, destination and current bytes.
  One parser for git in this tool, not two.

  DONE 2026-08-10: `source_digest` calls `changes::working_tree` and hashes HEAD plus, per change,
  the kind, both sides of a rename, and the current bytes (or `<absent>` for a deletion). The
  hand-rolled `rsplit(" -> ")` is gone.

- [x] **Escalation counts keys, not cost.** `selected / whole > 0.9` treats twenty host keys and
  twenty riscv64 guest keys as the same quantity, and they differ by two orders of magnitude in
  wall-clock. The measurement to build it on already exists - `history.rs` has the durations. Ratio
  of estimated scoped cost to estimated relevant-full cost, per environment. This is optimisation,
  not safety: the current rule escalates too eagerly on cheap universes and not eagerly enough on
  expensive ones, and both are wasted time rather than a wrong answer.

  DONE 2026-08-10, and PER PAIR rather than globally, which turned out to be the substantive part.
  The fixed term dominates - a boot is paid once however many tests run in it - so the real question
  is never "should the whole plan become FULL" but "having decided to boot riscv64, is running its
  four selected tests meaningfully cheaper than running all 205". Usually it is not. A global rule
  cannot express that: it answers the riscv64 question by also booting the two targets nobody asked
  about.

  Restricted to pairs with a non-zero fixed cost, because a host pair has no boot to amortise and
  widening it is pure extra work. The first version omitted that and pulled a shipping kernel build
  into a codec change - caught by `a_test_build_reach_does_not_order_a_shipping_build`, the test that
  exists for the opposite defect and turned out to cover this one too. Pinned by
  `the_cost_escalation_measures_seconds_and_not_keys`.

- [x] **Stable IDs are optional and nothing uses them.** The macro has an `id = ".."` arm and all 209
  tests take the default, `stringify!(name)`. Renaming a test therefore retires its history and
  starts a new key with no evidence - not a false green, because the loss is of trust rather than of
  coverage, but not the stable identity the design specified either. Give all 209 an explicit
  namespaced literal and delete the two arms that default it, so the identity cannot be lost by
  editing a function name.

  DONE 2026-08-10: 231 tests carry `id = "kernel.<module>.<name>"`, and the two defaulting arms are
  deleted, so a missing `id` is a compile error naming the test. The namespace is the module rather
  than the file path, so moving a test between files inside a module does not move its identity
  either.

- [x] **`SHADOW` exits 0 by default.** The level is now computed and printed, which was the whole of
  the previous finding, and `VERIFY_REQUIRE_TRUST=1` makes anything short of proven fail. But the
  default is still `if ./verify.sh; then publish; fi` treating SHADOW as done. Safe should be the
  default and permissive the opt-out: FULL and TRUSTED exit 0, SHADOW and STALE exit non-zero with
  their own status, and `--allow-shadow` (or `--dev`) is how a person says they know. Deliberately
  DONE 2026-08-10, flipped. FULL and TRUSTED exit 0; SHADOW exits 4 and STALE exits 5 - their own
  statuses, distinct from 1, so a caller can tell an unproven run from a failed one. `--allow-shadow`
  (or `--dev`) is how somebody says they know; `VERIFY_REQUIRE_TRUST=1` is still accepted and now
  redundant. This DOES fail runs that used to pass, and that is the point rather than a side effect.

  **The flag did not work when this was first ticked**, and how that happened is the part worth
  keeping. Its `case` arm set the variable and had no `shift`, so the argument loop never advanced
  and `./verify.sh --allow-shadow` spun forever in bash - no output, no child process,
  indistinguishable from a long build until somebody read `/proc`. It was ticked after checking that
  the flag parsed and that `--plan` still worked, and `--plan` is the one path that never reaches
  what the flag controls: the level check runs at the END of a run with real steps.

  Fixed and then exercised, which is the order it should have gone in: the same scoped change run
  twice, `exit=5` without the flag and `exit=0` with it, both after `all 6 step(s) passed`.

- [x] **This document states its own history as its current state.** Four places still say `covers` is
  on 11 of 209 tests with 198 undeclared; it is on 209 of 209. The header says three gates have no
  negative fixtures; all three have them. An outside reader took the stale sentence over the tree and
  filed a finding against it, which is the cost made concrete. Split the file: current state at the
  top, and an implementation diary below it that is explicitly dated and explicitly past.

  DONE 2026-08-10 by DATING rather than splitting. Every stale number now carries the date it was
  true, in italics, in place. Splitting the file would have moved a thousand lines and broken every
  reference into it, and the defect was never the diary - it was a diary entry written in the present
  tense. The gate that keeps the header honest from now on is a different thing and exists:
  `check.sh --gate milestone-index`, see P02M0112.

## A fifth round, and what it says about reading an audit

An outside audit arrived 2026-08-10 pinned to `476e93e` - **nine commits behind HEAD**. It found the
selector sound (its own words: no remaining false-green path, ~9.2/10 against ~7.5 before) and listed
ten things to finish before DONE. Checked one by one against the tree:

- **per-universe trust requirements** - already there. `required_architectures(universe)` answers 2
  for `TestGuest`, 1 for `Host`, 1 for `DevGuest`, for the reason the audit gives.
- **`trusted_everywhere` derived from the catalog** - already there. It takes the universes that can
  judge a component rather than a hard-coded pair.
- **strict exit semantics by default** - already there. SHADOW exits 4, STALE exits 5,
  `--allow-shadow` / `--dev` is the opt-out, `VERIFY_REQUIRE_TRUST=1` still accepted and now
  redundant. The audit asked for exactly this arrangement.
- **mandatory explicit stable IDs** - already there. The macro has no arm without `id`; a missing one
  is a compile error naming the test, and every kernel test carries an explicit namespaced literal.
  Both examples the audit names as unannotated (`imgview_interactions`, the audioconv test) carry one.
- **the selector's own source in the model hash** - already there. `SELECTOR_VERSION` is gone;
  `selector_source_digest` hashes every `.rs` under `verify-model/src`, sorted, name and bytes.
- **`source_digest` through the new change parser** - already there. It goes through
  `changes::working_tree`, hashing HEAD, each change's kind, both sides of a rename, and the bytes.
- **cost escalation over a measured model** - already there. `CostModel::estimate` on measured
  per-key durations, per (architecture, environment), and only where the fixed boot cost is non-zero.
  The `> 0.9` is a ratio of estimated SECONDS, not of key counts.
- **three missing negative fixtures** - not true, and instructive. All three gates inject a corrupted
  manifest and prove the refusal. The audit read it from a stale line in the header of THIS file -
  which is the second time that has happened, and the reason the previous round's last task exists.
- **this document's stale numbers** - closed 2026-08-10 by dating every one in place.

One held, and it is the one that matters:

- [x] **`DevGuest` has no evidence producer, so four components can never be trusted.** The universe
  exists, `Universe::of` routes `dev.*` checks to it, `required_architectures` answers 1 for it, and
  the trust command enumerates all three. Nothing ever writes a `DevGuest` record. `shadow` takes
  `--guest-log` (writes `TestGuest`) and `--host-log` (writes `Host`, added in the fourth round) and
  there is no third.

  `trusted_everywhere` asks the catalog which universes judge a component, so this is not abstract:
  `dev.selftest`, `dev.perf-gate` and `dev.proto-test` cover **`bin.dev_agent`, `bin.dev_channel`,
  `harness.boot` and `proto`**, and each of those four now requires a certificate that no code path
  can grant. Two of them are ordinary components, not development curiosities.

  The fourth round found the trust machinery designed per-universe and fed from one universe. The fix
  fed two. This is the third: a `--dev-log` parser for `dev-selftest.py`'s output, a `DevGuest`
  record from it, and `verify.sh` calling it after the dev-guest steps the way it already calls the
  other two. Until then the honest statement is that `DevGuest` is declared and unfed, and this
  milestone should not say TRUSTED is reachable for everything while it is.

- [x] **Exact kernel selection is BROKEN at HEAD: the model emits function names and the runner
  matches explicit ids.** Found 2026-08-10 while reconciling three test counters that disagreed.

  `kerneltests.rs::parse_declarations` never reads the `id = ".."` clause. It takes the first
  snake_case argument - the FUNCTION NAME - as the test's identity, so a check is
  `kernel.<fn_name>`. `commands.rs` then strips `kernel.` and hands the bare name over as
  `TEST_SELECTION`. The guest runner compares against `test.id()`, which since 2026-08-10 is the
  mandatory namespaced literal (`kernel.applications.imgview_interactions`). They cannot match, and
  an unmatched id is deliberately a hard failure: `test selection error: no test with id '..'` then
  `exit_qemu(false)`.

  Measured, not reasoned: a change to `src/user/libs/image/qoi/src/lib.rs` emits
  `TEST_SELECTION=audioconv_converts_across_volumes_and_never_writes_a_failed_conversion,imgconv_cross_volume_and_failed_overwrite_preserve_destination,imgconv_governed_working_set_is_measured,imgview_interactions,lico_switches_panels_and_restores_the_terminal`
  - five bare function names against five namespaced ids.

  **This is a regression the stable-id task introduced.** Before it, `id` defaulted to
  `stringify!($name)`, so the model's function name and the runner's id were the same string and the
  selection matched. Making ids mandatory AND namespacing them changed one side of an equality whose
  other side nobody owned. It is not a false green - it fails loudly - but every scoped run that
  selects under 80% of the kernel suite fails its guest step, which is the dimension this milestone
  measured at 9 s against 108 s.

  It went unnoticed because nothing scoped has run since: the ABI change selected 766 of 766 keys,
  and above the 80% threshold `commands.rs` deliberately omits the list.

  The fix is both halves at once, and a test that pins the equality: `parse_declarations` reads the
  `id` literal and uses it as the identity (its absence is now a malformed declaration, not a
  default), and `commands.rs` stops stripping the prefix, because the runner matches the whole
  literal. Then a check that every id the model emits exists in the built suite - the one invariant
  that would have caught this the moment it landed.


  DONE 2026-08-10, both halves plus the invariant. `parse_declarations` now returns the `id`
  literal, `KernelTest` carries it, the catalog's check id IS that id, and `commands.rs` hands it
  over verbatim. A binary test with no declaration is now an error rather than a guessed identity,
  and the self-check refuses any kernel check id that is not a declared id, any empty id, and any
  two tests sharing one - the check that would have caught this the day it landed.

  Two things fell out of it that the task did not anticipate. `breakpoint_exception_returns` existed
  in both the x86_64 IDT and riscv64 trap modules under different ids, and the model joins the built
  binary to the source by function name - so those two were ONE test to it, sharing architectures
  and covers. The riscv64 function is renamed and its id is untouched, which is the id doing exactly
  what it exists for. And the guest printed `self.name` while the plan key carried the id, so the

## Reopened: the evidence layer proves less than the universe it certifies

A sixth audit - 2026-08-12, against this tree at `fcb821b` - reading the implementation rather than
the task list. Every claim below was checked against the code first, and one of its findings is
refused with the reason recorded.

It found nothing wrong with the selector, which is worth stating plainly: rename handling,
architecture risk, stale volumes, the SDK payload, exact IDs, the missing guest step and the
build-script edges are all genuinely closed in the code. The status here has been IN VALIDATION
throughout, and that was the right call - what is unfinished is the evidence, not the selection.

What the audit adds is that the evidence is not merely thin. It is **narrower than the universe it
grants a certificate for**, in two specific ways, and both are in the producer rather than in the
comparison.

### `Universe::Host` includes builds, and the Host evidence never runs one

`judging_universes` maps any variant with `Environment::Host` to `Universe::Host`
(`src/tools/verify-model/src/catalog.rs:139`), and every `build.*` check is declared with
`environment: Environment::Host` (`src/tools/verify-model/src/catalog.rs:166`). So a component
covered by a build check requires a Host certificate.

The Host producer excludes builds:

```
if check.kind == verify_model::catalog::CheckKind::Build { continue; }
```

`src/tools/verify-model/src/main.rs:211`, with a comment explaining the cost: re-running three
architectures' builds to answer "did anything outside the selection fail" would cost more than the
sweep it compares against.

That reasoning is sound about cost and wrong about what the certificate then means. The evidence
covers gates, host suites and conformance; the certificate is issued for a universe that also
contains builds. A selector defect that drops `build.user` from a selection cannot be observed by
this producer, and five clean runs later the component is TRUSTED for `Host` anyway - at which point
a scoped green is allowed to stand on a claim nothing checked.

- [x] **Either split the universe or feed the evidence.**

  DONE 2026-08-12, by SPLITTING - the smaller change and the one that makes the rule structural
  rather than remembered. `Universe::HostBuild` is separate from `Universe::Host`, `Universe::of`
  routes `build.*` to it, `judging_universes` maps a Host-environment variant of a `Build` check to
  it, and `level` consults all four. A build's certificate can now only be earned by evidence about
  builds - which is to say, not yet - instead of being inherited from a comparison that never
  looked at one.

  `required_architectures` gives it 2, by the same argument the guest suite has: builds run for
  three targets and evidence about one says nothing about the others. That number is what the
  universe will need rather than what it currently gets, because it currently gets nothing.

  The serialized name of the other one stays `Host`, so the records already on disk keep meaning
  exactly what they said: they were produced by that producer, over gates, suites and conformance.

### The Host result identity is a check id, and the key is four fields

The frozen model is `PlanItemKey = (check, architecture, environment, configuration)`. The Host
producer prints `check.id` and a command (`src/tools/verify-model/src/main.rs:216`), once per Host
variant, and `parse_host_log` stores them in a `BTreeMap` keyed on the id alone
(`src/tools/verify-model/src/shadow.rs:175`).

Two consequences follow directly:

- A check with more than one Host variant emits several lines carrying the SAME id. The map keeps
  the last, while `verify.sh` counts every line into `total` - so the declared total and the number
  of outcomes disagree, and the disagreement is silent.
- The command is `check.command` with `{arch}` substituted and nothing else. The real lowering adds
  the configuration's features - `format!("{} --no-default-features --features {other}", item.command)`
  at `src/tools/verify-model/src/commands.rs:45` - so a non-default variant is run as if it were the
  default one, and its result is filed under an id that does not say which variant it was.

Most `shared-image` host variants are unavailable today for the `rt`/`panic_impl` reason the registry
records, so the practical blast radius is small right now. The data model has configuration as a
dimension, and evidence that discards a dimension of the key cannot be evidence about it.

- [x] **Emit the whole key.** `check<TAB>architecture<TAB>environment<TAB>configuration<TAB>verdict`,
  parsed back into a `PlanItemKey` rather than a string.

  DONE 2026-08-12. `host-checks` and `dev-checks` both emit the five fields, `verify.sh` writes them
  back with the verdict, and `parse_host_log` returns `KeyedResults` - a `BTreeMap<PlanItemKey, _>`.
  `compare_host` and `compare_dev` now compare key against key through one `compare_keyed`, so
  nothing is reconstructed: the old code rebuilt `"host" / "host" / "shared-image"` for everything,
  which was the wrong configuration for every gate, every conformance suite and every default host
  suite - so the history lookup missed as well. A repeated key is now `Void` rather than absorbed.

  Watched to fail: `two_configurations_of_one_check_are_two_results` reports `left: 1, right: 2`
  against the old collapse.

- [x] **One lowering, not two.** The producer should build its commands through `commands.rs`, so a
  configuration's features cannot be present in the run and absent from the shadow.

  DONE 2026-08-12: `commands::host_command` is the one place a configuration becomes
  `--no-default-features --features X`, called by the runner's plan steps and by both shadow
  producers.

### The cost model cannot select scoped on the emulated targets, and cannot learn otherwise

`CostModel::default` sets `fixed_seconds` to 100 s for x86_64 test-guest, 2300 s for aarch64 and
3200 s for riscv64, with `default_variable` at 0.5 s
(`src/tools/verify-model/src/history.rs:157`). The estimate is `fixed + sum(per-key variable)`
(`src/tools/verify-model/src/history.rs:179`) and the planner widens a selection to the whole set
when `scoped / whole > 0.9` (`src/tools/verify-model/src/plan.rs:284`).

Put those together with this tree's own measurements and the numbers decide the outcome before the
selection does. On aarch64, 226 keys: the whole set estimates 2300 + 113 = 2413 s, and a selection
of ONE key estimates 2300.5 s. The ratio is 0.953 - above the threshold - so every scoped aarch64
selection widens to the full suite, no matter how small it is. riscv64 is 0.966 and behaves the
same. Only x86_64, where the fixed term is 100 against a whole-set estimate of about 218, can ever
stay scoped.

The model also cannot correct itself, and that is the part worth fixing first. `record_step`
distributes `(step_seconds - fixed).max(0.0)` across the keys
(`src/tools/verify-model/src/history.rs:85`). The aarch64 suite measured 2069 s in
[P02M0133](P02M0133.md) against a fixed term of 2300, so the residual is negative, clamped to zero,
and every key records zero seconds. `estimate` then ignores the record because it requires
`last_seconds > 0.0` and falls back to the 0.5 s default. The history can never learn a per-test
cost on the two targets whose costs matter most.

The direction is safe - it over-tests rather than under-tests - and the comment beside the constants
explains honestly where each came from. What it does not say is that they are whole-suite figures
sitting in a field that means startup cost, which is why they swamp the ratio.

- [x] **Make the residual honest.**

  DONE 2026-08-12, and it is the half that had to come first: the measurement cannot correct the
  constant while the measurement is the thing being discarded.

  `record_step` no longer clamps. A run that comes in under its fixed term records the overshoot in
  `History::fixed_overshoot`, keyed by `architecture/environment` and keeping the LARGEST seen - the
  fixed term is a floor on what a run costs, so the run that came furthest under it is the strongest
  statement about how wrong the constant is. The per-key share stays zero, because there is
  genuinely nothing left to distribute.

  And it is a statement rather than a number in a file: `self_check_failures` reads the history and
  FAILS when an overshoot exceeds a tenth of its fixed term, saying that the term is a whole-suite
  figure sitting in a field that means startup cost and that every scoped selection on that target
  therefore widens to the full suite. The aarch64 measurement in [P02M0133](P02M0133.md) - 2069 s
  against a 2300 s term - is exactly the shape that now reports itself.

  `#[serde(default)]` on the new field, so the histories already on disk load and read as "never
  overshot" rather than being dropped.

- [x] **Measure fixed and per-test separately, per target.**

  DONE 2026-08-12. Nine runs, exactly as the item specified - 2 tests, 20 tests and the whole suite
  on each target, the selections a deterministic stride sample over that target's ids, timed as
  whole `./test.sh` invocations because that is what `record_step` charges:

  |---------|---------|----------|-------------|----------------|-------------------|-----------------|
  | x86_64  |    23 s |     26 s | 131 s (240) |       19.5 s   |          0.46 s   | 100 s / 0.5 s   |

  Both halves of the model were wrong and in opposite directions. The fixed term was a whole-suite

  one global 0.5 s, which priced an emulated test as if it cost what a native one costs when it
  costs fifteen to twenty times more. `CostModel` now carries `variable_seconds` per target beside

  THE NUMBER THE ITEM WAS RAISED FOR: the planner widens a selection to the whole set above

  It is now 0.284 and 0.181.

  - `the_cost_escalation_measures_seconds_and_not_keys` asserted `few / many > 0.9` for riscv64 -

## A seventh round: the evidence layer is now fail-closed against itself

An outside audit against this tree at `8df720c` - 2026-08-12. Five findings held and one did not; the
one that did not is recorded below with what actually misled it, because a stale comment that costs
an auditor a wrong conclusion is a defect with a measurable price.

Its central observation is right and is the reason this section exists. The selector has no new
false-green path, and the sixth round genuinely closed the false-TRUST one: `Universe::HostBuild`
means a Host certificate can no longer stand for builds nothing compared. What that split created is
the opposite failure, and it is worse than it looks from the code alone.

**Measured, not argued.** The catalog names 192 components that any universe judges. **189 of them -

## An eighth round, from trying to use it: five comparisons that were one comparison

2026-08-14. This milestone has said for six rounds that its remaining work is not a task - that it is
accumulating shadow comparisons until components become TRUSTED, which is usage rather than code.
That was very nearly true. What was left in the code was one criterion, and it was found the way the
last three rounds' worst defects were found: by trying to actually use the thing.

**Nothing has ever been TRUSTED, so the grant path had never once run end to end.** `verify-model`'s
own suite grants certificates over hand-built logs, and every one of those logs was five records
with an empty `source_digest` - five copies of one comparison. So the cheapest way to earn the first
real certificate this tool would ever issue was to run one `./verify.sh --shadow` five times over,
and working out that this was the cheapest way is what made it obvious that it must not be.

**And it would have worked.** `evaluate` counted RUNS. The selector is deterministic - there is a
property test in this very crate asserting exactly that - so the same change against the same tree
produces the same selection and the same sweep verdict every time. Five of them is one piece of
evidence wearing the number five, and a certificate earned that way says "a scoped answer about this
component can be believed" on the strength of a single answer.

That is this milestone's own subject arriving inside its own trust criteria: a green worth less than
it looks.

- [x] **Count distinct evidence, not runs.** DONE 2026-08-14. `distinct_evidence_for` counts
  distinct (tree content digest, change set) pairs among the clean records, and `evaluate` requires
  `REQUIRED_CLEAN_RUNS` of those as well as of runs. The unit is the SELECTION INPUT rather than the
  tree, because that is what determines the answer being validated - two different changes compared
  against one tree are two pieces of evidence, and one change compared twice is one.

- [x] **Make the fixtures honest about it.** DONE the same day. Six of this crate's own tests built
  their evidence with an empty digest and would have gone on passing over the new rule if the helper
  had kept doing that; they now vary the tree, and `five_comparisons_of_one_change_are_one_piece_of_evidence`
  pins the rule from both sides - six repetitions of one comparison are refused, and five different
  changes against ONE tree are accepted.

### What this costs, said plainly

It makes trust strictly harder to earn, and it makes it impossible to earn in an afternoon. That is
the right direction and it is also the honest answer to why this file has said "usage rather than
code" for six rounds: the criterion that made it *look* like a lap of the machine could be arranged
was the criterion that was wrong.

So the state is unchanged in substance and now true rather than nearly true. Nothing is TRUSTED.
Getting there needs five genuinely different comparisons per component per universe, on the targets
each universe can reach, under one model hash - which accumulates from ordinary development and
cannot be manufactured. The machinery that grants, prunes on a moved hash, grades per universe and
refuses a dry-only record is built, tested and now correct about what it counts.

One stale comment went with it: `required_architectures` still said `HostBuild` has no producer,
which stopped being true when `build-checks` became the third producer in the seventh round. That is
the fourth round in which a comment describing a previous state as a current one has been recorded
here.

## A ninth round: the build producer runs on the wrong architecture set

A fourth external audit, against this tree at `4350074` - 2026-08-14. Five findings and all five hold.
Two of them are the same defect from the two directions this milestone keeps rediscovering: the
`HostBuild` evidence producer answers a question about builds using the set of architectures that are
BOOTED, and the one universe whose execution mechanism differs from its evidence mechanism is the one
exempted from proving that it executes.

The audit's account of the eighth round is right and needs no defending: the DevGuest command is
fixed by a typed lowering rather than a special case, Host and DevGuest SHADOW-EXEC are really
implemented, `universes_with_producers` closes the wall structurally, and the cost model now carries

### `architectures_booted` is not `architectures_built`, and the build evidence uses the wrong one

`verify.sh` computes one set of targets, from `booted` (`verify.sh:275`):

```sh
targets="$(printf '%s\n' "$changed" | ... -- booted --stdin)"
```

and the `HostBuild` producer loops over it (`:415`):

```sh
for build_arch in $targets; do
```

The plan carries both sets and this milestone separated them on purpose - `plan.rs:71-72` - because a
change that boots one target still has to COMPILE on the other two. The regression corpus states the
case in the model's own words (`model/regressions.toml:75-81`): `riscv64-trap-handling` boots riscv64
alone and must select `build.kernel / x86_64 / host / shared-image`, with the reason recorded as "a
branch that stops compiling elsewhere is a regression as well".

So on that very change the planner selects an x86_64 build check and the shadow producer never runs
one, because x86_64 is not in the boot set. `HostBuild` requires evidence from at least two
architectures. The ordinary shape of userspace work - cross-build everything, boot x86_64 - therefore
records build evidence for one architecture and never reaches the bar.

The eighth round removed the wall in the DATA MODEL, which is what `universes_with_producers` and
`a_build_covered_component_can_reach_trusted` check. That test builds its two-architecture records by
hand, so it cannot see that the shell never produces them.

- [ ] **A `built` command beside `booted`,** printing `plan.architectures_built`, and the `HostBuild`
  loop reading it. Two lines of Rust and one of shell. The guest shadow keeps `booted`; the two sets
  must not merge back, which is the whole reason they are separate fields.

- [ ] **A test at the production semantics, not at the record shape.** Given an ordinary per-target
  change, assert `architectures_built != architectures_booted` AND that the set the build producer
  would iterate is the built one. The current test proves a component with the right records can be
  trusted; what is missing is that a real run produces those records.

### `HostBuild` is exempted from SHADOW-EXEC, and it is the universe with two execution paths

`exec_universes` covers `TestGuest | Host | DevGuest` (`trust.rs:101-103`). The reasoning for leaving
`HostBuild` out is that a full sweep builds everything anyway, so a scoped build proves nothing new.

That is true of the BUILD and false of the MECHANISM. The production runner groups parts
(`commands.rs`): `./build.sh --arch X --part a,b,c`. The evidence producer runs the catalog's commands
one at a time: `./build.sh --arch X --part libs`, then `--part user`, and so on. Those are different
code paths through the same script, and only the second one is ever compared.

A grouped `--part a,b,c` whose parser silently used only `a` and exited zero would leave every
individual build check passing, every `HostBuild` record clean, a certificate granted - and the scoped
runner building less than the selection said. That is the precise shape of the defect that produced
SHADOW-EXEC in the first place: the planner naming Rust function names while the runner used stable
IDs, every dry comparison clean, found by hand.

- [ ] **Sample the collapsed build path once before a `HostBuild` grant,** through `commands::steps`
  rather than through the catalog commands, and compare the `PlanItemKey`s the scoped build discharges
  against the ones the selection named. Same three invariants the guest comparison uses - executable,
  not wider, agreeing - against the mechanism that actually ships.

- [ ] **Then remove the exemption** so `exec_universes` covers every universe with a producer, and let
  the comment beside it record why the exemption existed rather than that it does.

### The distinctness key counts unrelated neighbours as independent evidence

The eighth round added `distinct_evidence_for` because five reruns of one comparison were satisfying
a criterion meant to require five different changes. The key it uses (`shadow.rs:613`) is
`(source_digest, changed_components.join(","))`.

On one unchanged tree, five comparisons of `audio + neighbour-0` .. `audio + neighbour-4` are five
distinct pairs, and the selector's decision ABOUT AUDIO may be byte-identical in all five. The
criterion is stated in this file as five genuinely different changes; what the key enforces is five
different change SETS, which is weaker in exactly the direction that matters, since the neighbour is
free and the audio half is what the certificate is about.

This is a real narrowing of the eighth round's own claim rather than a new class of defect, and the
honest reading is that "impossible to manufacture" was too strong.

- [ ] **Key distinctness on what the selector actually decided for THIS component,** not on the global
  change set: the selected `PlanItemKey`s for the component, the edge kinds that reached it and the
  architecture policy result. Then `audio + anything` is one piece of evidence unless the audio
  decision differed, which is the property the criterion was written for.

- [ ] **Keep a test for both directions.** The existing one asserts six identical comparisons are one
  piece; the new one has to assert that five audio-plus-different-neighbour comparisons are also one
  piece, which is what today's key gets wrong.

### The trust criteria still do not consult what the records carry

Older, and now more visible because the milestone was marked COMPLETE. Records hold `change_kinds`,
`edge_kinds`, `model_self_check` and `shadow_exec`; `evaluate` requires clean runs, distinct evidence,
architecture coverage and a SHADOW-EXEC sample. It does not require that the relevant change classes
or edge kinds were exercised, or that the regression corpus passed.

The frozen design named those, and the reason is the one distinctness only partly addresses: five
perfect verifications of one KIND of change are not evidence about a different kind.

- [ ] **Grade the criteria the records can already answer** - relevant change classes exercised,
  relevant edge kinds exercised, regression corpus green in the run that produced the record. The data
  is there; `evaluate` is the only thing that does not read it.
