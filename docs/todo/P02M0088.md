# P02M0088 - Multi-arch track follow-ups (the P02M0085-P02M0087 loose ends)

Status: REOPENED (2026-08-16) by a fourth-party audit round, recorded in AI/audit/kernel.md (architecture findings) and AI/audit/fdt.md. The findings are appended as open tasks in the section at the end of this file; each was checked against the tree before being written down, and where a check contradicted the audit that is recorded with the task rather than dropped. Previously: COMPLETE (2026-07-11). Three loose ends from the P02M0085-P02M0087 port track that had been
recorded only as inline notes inside finished boxes, which is how they nearly stayed.

*Condensed 2026-08-08.*

**The unlocked page-table race, closed on x86_64 and aarch64.** riscv64 had already gained a
`PT_LOCK`; the other two had the same latent race and no lock. Both backends now take the same
`SpinLock<()>` - a **leaf** lock over the frame allocator, with page-table-then-frame ordering and
never the reverse, so it cannot deadlock. x86_64 takes it in `map_page_in` and `unmap_page_in`, the
funnel every mapping goes through.

*(P02M0089 then wrote the concurrency test for it, which immediately found a real aarch64 leak the lock
did not cover: `free_address_space` descending one level short on a four-level tree.)*

**aarch64 boots the clean production path.** Its non-test tail ran `aarch64_run_demos()`; it now runs
the same production sequence as the others - system manager, the service chain, the shell on an
interrupt-driven idle halt.

**The device tree reaches the kernel through `BootInfo`, not through injection.** Two avenues were
open; the loader building a `BootInfo` with a `dtb` field was chosen over injecting a DTB, so the
device-tree architectures enter their boot stub with the pointer where QEMU `-kernel` would have put
it. One path, whether the firmware or the loader started the kernel.

## Fourth audit (2026-08-16): `AI/audit/kernel.md` architecture findings, and `AI/audit/fdt.md`

The same external audit reported twenty-five architecture and platform findings, five of them
Critical. Two were checked line by line before being written down; those checks are recorded here.

- [x] **RISC-V trusts a user-controlled `tp` as the kernel per-CPU pointer (KERN-ARCH-001, reported
  Critical, security).** FIXED 2026-08-20 - the trap path establishes a trusted `tp` before any Rust
  runs; see the section at the end. VERIFIED AGAINST THE TREE, AND IT IS AS DESCRIBED. `percpu::this_cpu` and
  `this_cpu_mut` both read `tp` directly (`mv {}, tp`) and dereference it. `__trap_entry` swaps `sp`
  with `sscratch` to reach the kernel stack, saves `x4` - which IS `tp` - into the frame, and NEVER
  establishes a trusted kernel `tp` before calling Rust. U-mode may put any value in `tp`, so a
  syscall or a timer trap makes the kernel read and write per-CPU state through an address the user
  chose. `percpu::set_from_user` writes through it on the syscall path. That is an arbitrary S-mode
  write from ring 3, and it is the most serious thing in the whole audit set. The fix is the one the
  `sp` path already uses: swap a trusted per-hart pointer from an architecturally reserved location
  on every trap and restore the user `tp` only immediately before `sret`.
- [x] **Privilege entry leaks registers on AArch64 and RISC-V, and AArch64 violates the kernel FP ABI
  (KERN-ARCH-002, Critical).** Registers not restored on the way out carry kernel values back to
  ring 3. The AArch64 x4 leak was the cause of the PermissionManager crash below; RISC-V's
  general-purpose path was read and is complete; the AArch64 entry scrub and FP ABI are closed.
- [x] **A RISC-V user `ebreak` causes a nested supervisor fault; ordinary x86 user exceptions halt
  the machine; x86 accepts entry and stack values that can fault during ring-0 `iretq`
  (KERN-ARCH-003, -004, -005, all Critical).** Each turns a user-triggered fault into a dead machine
  rather than a dead process - the property P02M0119 established for user copies, not yet held for
  user faults.
- [x] **AArch64 and RISC-V boot direct maps leave writable-executable aliases (KERN-ARCH-006).**
  W^X is advertised and not held on two of three targets.
- [x] **The global tick rate multiplies by CPU count on AArch64 and RISC-V (KERN-ARCH-007).** Every
  deadline in the system is then wrong by the core count, which is worth measuring before fixing so
  the milestone records what it actually was.
- [~] **Non-x86 CPU discovery assumes dense IDs and publishes CPUs that never came online; a missing
  x86 AP trampoline leaves a phantom multi-CPU count; the AP trampoline truncates CR3 to 32 bits;
  CPUs above index 63 are omitted from TLB shootdowns (KERN-ARCH-008, -009, -010, -012).** The last
  is a correctness bound hiding in a `u64` bitmask. All four are CLOSED.
- [~] **Device and interrupt plumbing (KERN-ARCH-014 through -017, -022, -023).** Virtio PCI
  capabilities from different BARs coerced into one mapping; ECAM BAR allocation overlapping
  retained firmware BARs; an MSI-X table entry that can straddle the one mapped page; GICv2m SPI
  identifiers truncated to eight bits; ramfb failure freeing only the first page; RTC access racing
  between CPUs with unbounded polling. KERN-ARCH-016, -017, -022 and -023 are CLOSED; -014 and -015
  are open.
- [x] **AArch64's fallible mapper leaks intermediate page tables on OOM, and every 4 kB mapper
  assumes an existing intermediate entry is a table (KERN-ARCH-019, -021).**
- [x] **Inherited `CR4.FSGSBASE` can let ring 3 redirect trusted GS state (KERN-ARCH-024).**
  Conditional on the firmware leaving it set, which is why it needs to be established rather than
  inherited.
- [x] **The device tree's `/reserved-memory` subtree is never read (FDT-001, reported High).**
  VERIFIED: `grep -rn "reserved-memory" --include=*.rs src/` matches NOTHING. Only the header
  reservation block at `off_mem_rsvmap` is walked, so firmware, secure-world, DMA-pool and
  framebuffer ranges declared the standard way sit inside a `/memory` bank the allocator is then
  told it owns. UEFI boots take the EFI memory map and are not exposed; direct DT boots are.
- [x] **`Fdt::new` is a safe function that dereferences an arbitrary physical address (FDT-007,
  High, soundness).** VERIFIED: `pub fn new(base: u64, phys_to_virt: fn(u64) -> u64) -> Self` stores
  the integer, and `u8_at` does `read_volatile((self.p2v)(pa))`. `Fdt::new(1, identity).is_valid()`
  is safe Rust that reads address 1. Make raw construction `unsafe`, or take a bounded reader.
- [~] **The rest of the device tree's platform description is thinner than its callers assume
  (FDT-002 through -006, -008).** FDT-004 and FDT-008 closed; FDT-002, -003, -005 and -006 open. CPU nodes reduced to a count so consumers invent hardware IDs;
  device addresses ignoring bus translation, `ranges` and `status`; ISA-extension detection by
  substring, succeeding if ANY cpu matches; malformed reservation data failing OPEN into the

### KERN-ARCH-001: bounded, and the real fix specified (2026-08-16)

**WHAT CHANGED.** `this_cpu` and `this_cpu_mut` go through `trusted_tp`, which requires the register
to name the BASE of one of the slots in the block this kernel allocated - correctly aligned, an
exact multiple of the stride from the base, and inside the count. Anything else panics.

**WHAT THAT BUYS, STATED EXACTLY.** It does not restore correctness. What it removes is the
arbitrary S-mode write: `set_from_user` wrote through `tp` on the syscall path, so ring 3 could pick
any address in the address space. The worst a user can now select is a DIFFERENT HART'S per-CPU
block, which is a wrong answer rather than memory-unsafety. Requiring the exact base rather than
merely a pointer inside the region matters: an offset into the middle of a block would let a user
choose which FIELD a write lands on, which is most of the original problem back again.

**WHY THE REAL FIX IS NOT IN THIS ROUND, and what it is.** The correct answer is to establish a
trusted per-hart pointer on every trap before any Rust runs, the way `sp` already is - and
`sscratch` cannot simply be shared, because it holds the kernel trap stack for the U-mode path and
ZERO while an S-mode handler runs, which is exactly what `__trap_entry` uses to tell a nested trap
from a user one. The conventional shape on this architecture is to put the per-CPU pointer in
`sscratch` and derive the trap stack from the block it names, which changes `__trap_entry`,
`riscv64_enter_umode` and the nested-trap discriminator together. That is trap-entry surgery on the
one target whose full suite costs about 6,100 s, and it wants its own round rather than the tail of
this one.

Measured: riscv64 kernel tags 69/69 with the bound in place. The scheduler tag fails on
`a_remote_spawn_wakes_a_halted_core_without_waiting_for_the_tick` at 6.7 ms against its 4 ms bound -
the host-load-sensitive timing test already recorded above, not this change: nothing here touches
the wake path.


### FDT-001, -004, -007 and -008 closed (2026-08-19)

**FDT-007: raw construction is `unsafe`, and the contract travels with it.** `Fdt::new(1, identity)
.is_valid()` was safe Rust that read address 1. It is `unsafe fn` now, with the contract stated at
the constructor rather than at the reader - every method on the type is a `read_volatile` through the
address and the translation function it was handed, so a check INSIDE the object cannot make
constructing it safe: the first four bytes are dereferenced deciding whether the blob is a blob.

The propagation is the part worth recording. Both kernel backends have a private `fn at(base)`
helper, and both had a public surface - `parse`, `located`, `timebase_frequency`,
`has_isa_extension` - taking a `hint: u64` straight from the boot register. Making only `Fdt::new`
unsafe would have moved the hole up one level, so `at`, `locate` and every public function in those
two modules are `unsafe fn` with the same contract, discharged in `boot.rs` where the register's
provenance is actually known. The scan windows stay this module's own business and say so: they are
compile-time constants inside the direct map.

`fdt`'s own tests do the opposite, for the same reason `uefi`'s do: one safe `at(blob)` forwarder
with the argument made once - the blob is a `&'static [u8]` this process owns and `identity` is the
right translation for an address that is already virtual - instead of forty-eight `unsafe` blocks
stating nothing.

**FDT-001: `/reserved-memory` is read.** A device tree says "do not use this" in two places and only
the older one was being read. The header's reservation block was walked; the `/reserved-memory`
subtree - firmware runtime, a secure world's carve-out, DMA pools, a framebuffer an earlier stage
handed over - was not, and those ranges lie INSIDE a `/memory` bank by construction, which is what
makes them worth declaring and is exactly why reading `/memory` and stopping hands them out.

`for_each_reserved_memory_node` walks it with the same bounds as everything else here: cell counts
from the subtree when it declares them and from the root otherwise, both refused past `MAX_CELLS`, a
capped child count, and pairs read whole or not at all. `reusable` regions are reserved like any
other, because the specification's licence to use one until its owner claims it back assumes a
protocol for giving it back that this kernel does not have. A child with `size` and no `reg` asks the
client to PLACE the region; this reader places nothing, so nothing is carved - stated as a gap rather
than left as an omission. `bootmem::devicetree_reservations` calls it beside the header block, with
its own completeness report.

UEFI boots are not exposed - they take the firmware's own map and never reach this. Direct
device-tree boots are, and that is the path this covers.

**FDT-004: whole names, and every hart.** `has_isa_extension` was a byte scan over the property, so
`c` matched inside `zicsr` and `sv` matched inside `svpbmt`; and it answered `true` on the FIRST hart
that carried the name, after which the kernel used the extension on all of them - an illegal
instruction on a heterogeneous machine. `riscv,isa-extensions` is now compared element by element
against its NUL-separated entries, `riscv,isa` is split the way the specification defines it (a base
whose letters after the width are single-letter extensions, then `_`-separated names), and the
verdict is taken per hart at the node's end and combined with AND. A tree with no CPU nodes answers
`false` rather than vacuously `true`.

**FDT-008: a stream with a node still open is refused.** `parse` broke out of its loop at `FDT_END`
whatever the depth, so a token stream with more `FDT_BEGIN_NODE`s than `FDT_END_NODE`s was read to
the end and every depth-dependent decision in it - which node a `reg` belonged to, above all - was
taken over a structure the writer never closed.

**Found by the new tests, in the new code.** Moving the ISA verdict to the terminator made the walk's
own `if depth < 0 { return false }` fire when the ROOT closed, one token before the answer - so every
positive case became negative. Four tests failed on the first run; the guard is `depth < -1` now,
with the reason at the line. Worth recording because the previous shape hid it: while the function
returned `true` the moment it found a match, nothing ever reached the root's `FDT_END_NODE`.

Watched to fail, each against the code that would have passed before:

| mutation | result |
| --- | --- |
| `/reserved-memory` matched by prefix instead of by name | the `reserved-memory-pool` test fails |
| the walker records the range but does not report it | four of the six subtree tests fail |
| `FDT_END` breaks at any depth | the unbalanced-stream test fails |

Measured: fdt 36/36 host tests, and all three kernels and loaders build.

### KERN-ARCH-002 on AArch64, and the crash it was causing (2026-08-19)

**One instruction, in the wrong place.** The vector macro read:

```
	cmp     x0, x2
	mov     x4, #\id                   // which slot this is, for the report; harmless otherwise
	b.hi    __trap_bad_stack           // SP is not on the stack this thread was given
	b       9f
```

`__trap_bad_stack` wants the vector index, and this handed it over before deciding whether to go
there - so the `mov` ran on EVERY exception, the ordinary path fell through to `__trap_common`,
and `__trap_common` saves x4 into the frame it later restores from. Every trap on this
architecture - every timer interrupt, every preemption, every syscall - returned to EL0 with x4
replaced by the number of the vector it came through.

That is the finding's own words, exactly: a kernel value handed to ring 3 for free. It is also worse
than an information leak. x4 is an ordinary register; code that keeps a value in it across an
asynchronous interrupt is entitled to find it there afterwards, and does not.

The branch is inverted now, so the `mov` only runs on the way to a report that is about to stop the
machine.

**It was the PermissionManager crash.** That failure had been recorded as pre-existing and
unexplained through four sessions, and the number in it was the evidence all along:

- `fault: ring-3 page fault (code 0x92000006) at 0x10019630, addr 0x18` - ESR EC 0x24, DFSC 0x06: a
  READ with no level-2 translation. FAR 0x18.
- `0x10019630` is `permission_manager::launch_under_manifest` + the main image's `DYNAMIC_MAIN_BASE`
  of `0x1000_0000`. The instruction there is `ldr x20, [x27, #0x10]`, so x27 was 8.
- x27 comes from `mov x27, x4` in the prologue, and x4 is the fourth argument:
  `audit: &mut Vec<AuditEntry>`.
- **8 is `VEC 8` - "Lower EL, AArch64, Synchronous", which is what a syscall from userspace comes
  through.** The caller had loaded x4 with `&mut audit`, made a syscall before the call, and got the
  vector index back in its place.

So `audit.push(..)` read a length through a pointer of 8. Nothing about it was PermissionManager's,
and nothing about it was a null dereference: it was the kernel writing 8 into a userspace register.

**Measured.** `./test.sh --arch aarch64 --tags shell` fails on the tree before the change and passes
11/11 after it, with only the kernel rebuilt.

**RISC-V's general-purpose half was read and is clean**: `__trap_entry` saves x1 and x3 through x31
plus `sepc`, `sstatus` and the whole FP file, and it already saves x5 before using it as scratch -
with a comment recording that exact class of corruption being fixed once before. The AArch64 FP ABI
half of KERN-ARCH-002 is untouched and stays open.


### KERN-ARCH-012 closed: the bound refuses instead of truncating (2026-08-19)

The mechanism is arrays now rather than the `u64` bitmask the audit describes, and the bound moved
with it: `MAX_CPUS` is 64, every loop in `shootdown` said `cpus.min(MAX_CPUS)`, and `service_pending`
returns early for a core id past the arrays.

On a machine with more than sixty-four cores that is not a smaller job. `shootdown` counted only the
cores it could hold, waited only for those, and returned **true** - and the caller's next move is to
hand the frames back to the allocator. Cores 64 and up were never asked to flush and could not have
been, so they keep translations to memory that now belongs to somebody else. That is the physical
use-after-free the whole module exists to prevent, reached by clamping a loop.

It refuses now: a core count past the bound is reported once and answered `false`. The callers
already know what to do with that - `frame::retire` quarantines the span and tries again later - and
the module's own comment two screens up says why nothing else is acceptable: "carry on regardless is
the one answer that cannot be right here."

Tested at the boundary rather than by producing the machine, which cannot be done here (QEMU is given
eight cores): a new guest test pins that 1 and `MAX_CPUS` are covered, `MAX_CPUS + 1` is not, and
that this machine is inside the bound - so the ordinary path is still the one being exercised by
everything else.


### KERN-ARCH-007 closed, and what it actually was (2026-08-19)

**Eight times fast, on the machine this suite runs on.** The scheduler tick is a PER-CORE timer on
all three architectures - the LAPIC on x86, CNTP on aarch64, the CLINT on riscv64 - and each core
takes its own interrupt. aarch64's `handle_irq` and riscv64's `on_timer_tick` both answered that with
`TICKS.fetch_add(1)`, so the global monotonic counter advanced once per core per period. The boot log
says what the multiplier is: `SMP - 7/7 secondary cores online`, so eight cores, so `TICK_HZ` of 100
became 800. Every deadline in the system - a sleep, a timeout, a wait, the caret blink - fired at an
eighth of its stated interval.

**x86_64 had already solved it, and its comment records what does not work.** Counting only the boot
core's tick was the original design there and was removed because a stalled boot core froze the clock
and hung every tick-based wait. So the rate is gated on the machine's own cycle counter instead: any
core may drive it, a tick is only claimed once a full period has passed since the last, and the core
that wins the compare-exchange advances by the WHOLE backlog in one step - because catching up one
tick per interrupt would replay a stall at the interrupt rate times the core count.

That mechanism is now `arch::common::time::TickClock`, in the portable file, because three backends
needed the same one. aarch64 reads `CNTVCT_EL0`/`CNTFRQ_EL0` and riscv64 the `time` CSR with the
device tree's `timebase-frequency`; both counters are always available, so neither needs x86's
calibration window. Every core still re-arms its own timer - that is what drives preemption on that
core - and only the shared clock is gated.

**Tested on the mechanism, not on a stopwatch.** A rate measured against a wall clock on an emulated
guest under load is a flaky test, and this is a fact about arithmetic: the same instant, seen by any
number of cores, is one tick. `kernel.smp.the_global_clock_advances_once_per_period_however_many_cores_tick`
drives eight simultaneous arrivals through four cases - the instant that starts the clock, one full
period, a ten-period backlog, and part of a period - plus an uncalibrated counter, which counts
nothing rather than guessing a rate.

Watched to fail with the gate removed, which is the shape the two backends had: **`left: 8, right: 1`**
on the first assertion. That number is the finding.


### KERN-ARCH-024 closed: the bit is established, and the design says why it matters (2026-08-19)

**What the entry path assumes.** `usermode.rs` states it plainly: "GS is deliberately not swapped
across the ring boundary: the user thread keeps the kernel's GS base, which is safe because the
per-CPU block lives in supervisor-only pages... That lets the syscall entry stub reach the kernel
stack pointer through GS without swapgs."

That is one fact where two are needed. The second - **ring 3 cannot change the GS base** - was not
stated and was not established. `WRGSBASE` is a ring-3 instruction whenever CR4.FSGSBASE is set, and
this kernel never touched the bit: whether user code could redirect GS was whatever the firmware had
left behind. On a machine that left it on, user code could point GS at memory of its own choosing
and the next syscall would take its kernel stack pointer from there - a ring-0 stack pivot, on a path
with no other check.

**Cleared on every core, before any USER-flagged mapping exists.** `paging::establish_cr4_policy` runs
in both `init` and `init_ap`, beside `enable_nx` and `enable_smap_smep`, and is separate from the
latter deliberately: that function returns early on a CPU with neither SMEP nor SMAP, and this must
happen on every machine. Clearing costs nothing here - the kernel uses none of `RDFSBASE`,
`WRFSBASE`, `RDGSBASE` or `WRGSBASE`, because per-CPU state is written through the `IA32_GS_BASE`
MSR, which is ring 0 only.

`kernel.arch.ring_three_cannot_write_the_gs_base` reads the control register back. Asserted there
rather than by executing `wrgsbase` from ring 3, because what is being prevented is the kernel
following a user-chosen pointer: a test that reproduced it would not report anything. The other two
backends reach per-CPU state through `TPIDR_EL1` and the `sscratch`/`tp` pair, neither of which ring
3 can write, so there is no equivalent bit and the test says so.


### Open, found on the way: a thread blocked in `wait` is not woken by its peer closing, on aarch64 (2026-08-19)

`process_service_lists_every_started_program` launches two `holdopen` processes, each blocked in
`rt::wait` on the bootstrap channel the test holds. Dropping both ends should make each wait ready -
`Channel::is_readable` is "inbox non-empty OR peer closed" and `sys_wait` re-checks it on every wake
- so both children should return, exit, and leave ProcessService's list.

On x86_64 they do, on the first `run_until_idle`. On aarch64 they do not, within **sixty-four**
passes with a list request between each: the list still reports 2. The children are alive and
blocked, not crashed - the rest of the suite (254 tests) passes around them.

What that points at is the wake, not the readiness: either nothing signals the channel's koid when
the last peer handle is dropped, or the signal does not reach a thread parked on another core on
this architecture. It is worth having, because a thread that waits forever on a channel whose peer is
gone is a hang with no error - the shape this tree has closed several times elsewhere.

Not fixed here, and the assertion that found it was removed rather than left red: the other direction
is already covered by `process_service_drops_a_terminated_process_from_the_list`, which terminates a
process explicitly instead of waiting for one to notice.

What it took was three of the findings in this file: the x4 leak in the vector prologue

### The riscv64 wake IPI works, and the test that suggested otherwise cannot measure it (2026-08-20)

`a_remote_spawn_wakes_a_halted_core_without_waiting_for_the_tick` failed twice on riscv64 after the
tick-rate fix, at 6.05 ms and 5.67 ms against a 4 ms bound. Two explanations fit that: the host, or a
wake IPI that never arrives. The kernel was instrumented to settle it - a counter on every
`sbi_send_ipi`, its returned error, and the hart id it was aimed at, and a second counter in the
`code == 1` handler that receives it - and the answer is unambiguous:

```
IPI-PROBE best=3596100 sent=203 err=0 received=203 last_dest=7 cpu_count=8 lapic1=0
```

Every IPI is sent, none errors, and **every one is received**. `lapic1=0` is correct rather than
suspicious: this machine's boot hart is hart 4, so CPU 1 really is hart 0 - the log says `cpu 1 up
(hart 0)`. The wake path is sound.

**What the numbers actually say.** Five runs of the tag on an idle host:

| run | best of twenty trips |
| --- | --- |
| 1 | 5.76 ms - over the bound |
| 2 | 3.60 ms |
| 3 | 3.61 ms |
| 4 | 3.38 ms |
| 5 | 3.31 ms |

So a woken cross-core spawn costs about 3.4 ms on riscv64 under TCG, against a bound of 4. The test's
own comment models the machine as "with the IPI the trip is microseconds", and that is true on x86_64
and aarch64 and is not true here: the twenty-five-times instruction cost this architecture's runs pay
puts the trip within fifteen per cent of the bound, and any excursion crosses it.

**Which means the test cannot discriminate on riscv64.** Its comment states the gap it relies on:
without the IPI a trip waits for the next tick, "so each spawn-to-run trip averages about 5 ms". With
the IPI it costs 3.4 ms here. Those two overlap, so no bound separates them - a pass says nothing and
a failure says nothing either. Raising the bound would not repair that; it would only make the test
quiet.

**A correction, recorded rather than quietly replaced.** The first version of this section said the
IPI was not reaching the halted hart and that the eight-times-fast clock had been hiding it - on the
strength of one run of the tag with the old clock restored, which passed. One run of a measurement
that varies between 3.3 and 5.8 ms is not evidence of anything, and the instrumentation above says
plainly that the IPI arrives. The tick-rate fix did not break this test; it removed the last of the
headroom a marginal bound had.

**Fixed by measuring the property instead of the clock.** The test counts TICK BOUNDARIES now: it
reads `arch::apic::ticks()` either side of each trip and requires the best of twenty to have crossed
none. A trip that crossed no boundary did not wait for one, which is exactly what the test is named
for - and it does not care how many nanoseconds the emulator spent getting there.

The discrimination is exact rather than a margin. Without the IPI, EVERY trip waits for the next tick
and therefore crosses a boundary, so passing wrongly would need all twenty to straddle one by luck.
Watched to fail: with `send_wake_ipi` disabled the test reports `left: 1, right: 0`; with it back, it
passes. The old bound had stopped being able to tell those apart on riscv64, and a coin toss decided
whether the 165 tests after it ran at all.

### KERN-ARCH-003, -004 and -005 closed: a user fault kills the process (2026-08-20)

Three ways for an unprivileged instruction to stop every CPU, all of them the same shape: a fault
raised in ring 3 reaching a path written for a fault raised in the kernel.

**KERN-ARCH-004 - every x86 vector now asks where the fault came from.** Page faults and #GP
compared the saved code selector's low two bits; nothing else did, so `ud2`, a divide by zero, a
bound-range check, an alignment or SIMD fault called the fatal halt path whatever raised it. The
comparison is one function in front of every vector now, and the vectors without a dedicated handler
get one each - generated by a macro, three lines apiece - so a crash record can say WHICH exception
it was. `FaultInfo::address`, otherwise CR2, carries the vector number for those.

**KERN-ARCH-003 - the RISC-V breakpoint handler no longer reads the user's PC.** It decided the
instruction's length by `read_volatile`ing it at `sepc`, and did so BEFORE asking which privilege
level raised the trap. Trap entry clears `sstatus.SUM`, so for a U-mapped page that supervisor read
faults - nested, with no usercopy fixup, onto the fatal path. The origin check moved above it: a
U-mode `ebreak` ends the process like any other user fault and nothing dereferences its PC, while an
S-mode one still advances past the instruction, which is what a kernel breakpoint is for.

**KERN-ARCH-005 - a thread cannot be created at an address the ring transition would fault on.**
`entry` and `stack_top` were stored as given and reached `iretq` unexamined; a noncanonical RIP or
RSP raises #GP or #SS before the privilege change completes, which the handler sees as
kernel-origin. `USER_VA_END` is the exclusive top of the low canonical half on all three
architectures, so one comparison refuses both the noncanonical and the kernel-half cases, and a
sixteen-byte stack alignment makes a bad start fail predictably rather than inside the child.
Everything else an address can be wrong about - unmapped, no-execute, supervisor-only, read-only -
stays a recoverable ring-3 page fault that kills the child alone, which was already right.

**Watched to fail, and two of them by killing the machine:**

| mutation | result |
| --- | --- |
| `invalid_opcode` halts regardless of CPL | `EXCEPTION: invalid opcode at 0x40000000`, then TIMEOUT with "last test: unknown" |
| the RISC-V breakpoint branch runs before the origin check | the illegal-instruction probe passes, the `ebreak` probe kills the machine, TIMEOUT |
| the entry and stack bounds removed | `thread_create` returns a handle where it should return `ERR_INVALID` |

A suite that stops with nothing to report is what this finding looks like from the outside, which is
why the first two tests say so in their own comments: the test RETURNING is half the assertion.

The tests: `an_ordinary_ring_three_exception_kills_the_process_and_not_the_machine` runs a ring-3
`ud2` and a ring-3 divide by zero, checks the recorded fault kind for each, checks the Domain's
thread slot came back, and then runs an ordinary kernel thread to prove the scheduler survived.
`a_user_breakpoint_kills_the_process_and_not_the_machine` does the same on riscv64 for an illegal
instruction, a 32-bit `ebreak` and a 16-bit `c.ebreak` - both encodings, because the length
calculation was the reason for the read that faulted.
`a_thread_cannot_be_started_at_an_address_the_ring_transition_would_fault_on` asks for five refusals
and one acceptance, so "refuses everything" cannot pass as "refuses these".

`every_vector_is_filed_by_whether_it_pushes_a_code` guards the new tables against the architecture's
own `has_error_code`, and requires every vector below 32 to be populated exactly once: a vector on
the wrong side reads the interrupt frame at the wrong offset, and `iretq` returns to whatever that
produced.

Measured: x86_64 168 tests over `kernel,process,idt`, riscv64 77 over `kernel`.


### KERN-ARCH-001 closed: the trap path establishes `tp` (2026-08-20)

`tp` is an ordinary register in U-mode. `__trap_entry` saved the user's `x4` into the frame and then
called Rust with the user's value still in the register, and every per-CPU access in the kernel reads
`tp` and dereferences it - `percpu::set_from_user` WRITES through it on the syscall path. That is an
arbitrary S-mode write chosen by an unprivileged process.

The mitigation that stood until now bounded the damage - the pointer had to be a slot base in the
block this kernel allocated - so the worst a user could select was a different hart's block. That is
a wrong answer instead of memory unsafety, and it is not the same as correct.

**The fix is the one `sp` already uses: a trusted value parked where the trap path can find it.**
`sscratch` could not simply carry the per-CPU pointer, because it carries the kernel trap sp for the
U-mode path and zero for an S-mode handler, which is what tells the two apart. So the pointer goes
eight bytes BELOW the trap sp instead - inside the sixteen bytes at the top of the 544-byte frame
that hold no register - and `__trap_entry` loads it immediately after saving the user's `x4`, before
anything else runs.

**Written by whoever is about to return.** `riscv64_enter_umode` parks it for the first excursion,
and `__trap_return` parks it again on every return to U-mode, in the branch that already
re-establishes `sscratch`. That is what makes it correct across migration: a user thread preempted on
one hart and resumed on another finds the pointer of the hart it is actually running on, because the
hart that resumed it wrote the word.

Only for traps from U-mode, decided on `SSTATUS.SPP` rather than on whether `sscratch` is non-zero -
an S-mode trap already has the kernel's `tp`, and the word at that offset then belongs to the frame
it interrupted.

The slot-base check in `percpu::trusted_tp` stays, with a different job: it no longer bounds what
ring 3 can select, it states that the establishment happened. A `tp` that is not a slot base now
means the trap path did not run or parked the wrong word, which is a kernel defect and is caught
rather than dereferenced.

Measured: riscv64 78 tests over the `kernel` tag, which is every ring-3 excursion the suite has -
each one takes this path on entry and on return.

### KERN-ARCH-006 closed: the direct map is split, and the split is read out of the hardware (2026-08-20)

Both boot stubs map DRAM with 1 GiB leaves that carry read, write AND execute. The kernel runs out
of that map, so on aarch64 and riscv64 every page of RAM was executable through it and the kernel's
own text was writable through it - W^X advertised, and held on one target of three.

The fix is the same shape on both: after the secondaries are up, `harden_direct_map` replaces those
leaves with 2 MiB ones and gives each the permissions its contents want - read-execute where the
block lies wholly inside `[__kernel_rx_start, __kernel_rx_end)`, read-write-execute-never everywhere
else. Both linker scripts now round the text and rodata run to 2 MiB at both ends so that span is
expressible in those leaves; the alignment sits BETWEEN output sections, not inside one, or it pads
the image by the gap.

Ordering is the whole reason this is not in the stub. A secondary enables its MMU and then keeps
executing at its LOW physical PC through the same tables, so taking execute off the identity window
before the last one is up faults it on the instruction after the `satp`/`sctlr_el1` write.

`writable_executable_block()` walks the LIVE tables and returns the first leaf that is both. It is
what the guest test asserts on, so the property is read out of the hardware's descriptors rather
than out of the code that wrote them - which is what caught the first version of this:

- The aarch64 walk started at TTBR1 and treated it as the L1. With `T1SZ=16` TTBR1 holds the **L0**,
  and the stub's blocks are one level below it at `L0[0] -> L1[1..3]`. So `harden_direct_map` found
  three zero descriptors, split nothing, and printed its success line anyway; the guest booted, the
  suite passed, and the map was untouched. `boot_l1()` now resolves the level, and both the splitter
  and the walker go through it.
- With the split disabled the test reports `the direct map is still writable and executable at
  0x40000000` on aarch64 and `at 0x0` on riscv64; with it enabled both are clean. That is the
  measurement, not the log line.

Sv39's root already IS the 1 GiB level, so the riscv64 walk needed no such correction: it splits
`root[256..264]` (the high direct map, execute permitted inside the text span) and `root[2]` (the
low identity window, execute permitted nowhere - nothing runs there once the harts are up).

### KERN-ARCH-019 and -021 closed: a mapper that refuses what it cannot walk (2026-08-20)

Two defects in the same three walks.

**-021, all three ports.** Each 4 kB mapper read "valid" as "table" and followed the address field
down. At the 1 GiB and 2 MiB levels a valid entry can just as well BE the mapping, and then that
field names ordinary memory - so the walk wrote a page-table entry into whatever lived there and
mapped the caller's page into a table that was never a table. The direct map is where every target
keeps such leaves: 2 MiB pages from the loader on x86_64, and 2 MiB blocks from `harden_direct_map`
on the other two, which is what made this reachable rather than theoretical. All three now refuse -
`HUGE` on x86_64, a block descriptor (`TABLE` clear) on aarch64, `PTE_RWX` set on riscv64. Refusing
rather than splitting is deliberate: re-cutting somebody else's large mapping, and reproducing its
attributes across 512 leaves, is not a decision a request for one page gets to make.

**-019, aarch64.** The fallible mapper's own comment promised nothing was left behind on failure -
true of the leaf, and not of the metadata. A walk that got one or two levels in and then could not
allocate the next returned `Err` with fresh page-table frames attached to the address space, and
nothing counted them; repeated partial failures pinned memory the domain's quota never saw. It now
carries the same `created`/`unwind_created` rollback the x86_64 and riscv64 mappers already had,
clearing each entry BEFORE retiring its frame and draining the quarantine, because the caller of an
out-of-memory path is the one who needs those frames back.

`kernel.arch.mapping_a_4_kb_page_over_a_large_leaf_is_refused` asks for a 4 kB page at the direct-map
address of physical 0 - covered by a large leaf on all three targets - and requires `Err`. Watched to
fail on each: with the check disabled it reports `a 4 kB map at 0xffff800000000000 walked into a
large leaf instead of refusing` rather than the corruption it would have caused unobserved.

### KERN-ARCH-009 and -010 closed: the published core count is the confirmed one (2026-08-20)

`smp::init` published the firmware's discovered total before starting anything, and narrowed it to
the confirmed count only INSIDE the branch that starts application processors. Both ways of skipping
that branch left the total standing: the loader reserving no trampoline page (-009), and - once
checked - a page-table root the trampoline's 32-bit CR3 load cannot express (-010). The scheduler
bounds-checks against that number, the shootdown waits on it and the IPI paths dispatch to it, so
what was left behind was cores that exist for every one of them and were never woken.

`online` is now declared before the branch, starts at the boot processor, and is stored once after
it, on every path. The three conditions moved into `ap_boot_refusal(total, trampoline, cr3)`, which
names each one - so the reason a machine runs single-core is a line an operator can read rather than
a branch that was not taken.

For -010 the loader already allocates its tables under `TABLE_CEILING` with `ALLOCATE_MAX_ADDRESS`.
That is the loader's promise; `apboot::cr3_is_reachable` checks it where the value is USED, because
the root the kernel is running on is not required to have come from that allocation. `install`
returns false rather than copying a trampoline that would enable paging on a truncated root.

`kernel.smp.the_published_core_count_is_the_one_that_came_online` asks the refusal directly for each
condition and asserts `cpu_count() == online_count()` on the machine running it. Watched to fail:
with the trampoline clause removed it reports `no trampoline page means no AP can be started`.

### KERN-ARCH-008 closed: the tree's own CPU ids, and only the cores that answered (2026-08-20)

Two separate assumptions, both in the same sentence of the audit.

**Which cores exist.** The FDT walk counted `cpu@` nodes and discarded the `reg` that says WHICH
core each one is; `status` was not read at all, though `/memory` has honoured it since FDT-004. Both
non-x86 backends then started ids `0..cpu_count` - dense, zero-based, in tree order, none of which a
device tree promises. A board whose harts are 0, 1, 4, 5, or whose middle core is `disabled`, had
targets that are not cores and cores that never started.

`BootInfo` now carries `cpu_ids: [u64; MAX_CPUS]` - the hardware ids of the nodes that are enabled
AND carry a readable `reg`, read in the cells `/cpus` declares rather than the root's - with
`cpu_count` as the number of entries and `cpu_nodes` as every node seen. A node without a `reg`
names no core and is counted, not recorded: inventing an id from the enumeration order is the
assumption this finding is about. More cores than the table holds are CAPPED and reported, not
refused; refusing the tree the way an over-long `/memory` does would turn a sixteen-core machine
into no machine at all.

**Which cores are real.** Both backends started every target and then waited for all of them at
once, so a logical id was consumed whether or not a core came back. The id is the index into the
per-CPU pool, the scheduler's run queues and the stack block, so a failure left a hole: a phantom id
below the count, and a live core above it. Bring-up is now one core at a time - `CPU_ON`/`hart_start`,
then wait for THAT core to report in - and the id is handed out only on arrival. The count published
afterwards is what the function returns: cores online, boot core included.

The per-core wait is a bound and says so; it is not a measurement of anything.

Five host tests in the `fdt` crate cover the shapes: sparse ids `0, 1, 4, 5`; a disabled middle CPU
with `status` written AFTER `reg`, which is the order that catches a reader deciding too early; a
two-cell `/cpus` address; sixteen nodes against an eight-entry table; and a node with no `reg`. Each
watched to fail - dropping the `status` clause reports 4 usable cores where 2 are, pinning
`cpus_addr_cells` to one reads MPIDR `0x100` as `0`, and defaulting a missing `reg` to the
enumeration index records a core that does not exist.

Not touched, and worth naming: `smp::set_cpu_count` still fills the aarch64 id table with `ids[i] =
i`. That is the GICv2 CPU-INTERFACE number an SGI targets, not an MPIDR, and it is a different
mapping from the one this finding is about - correct for QEMU virt, and an assumption of its own on
a machine where the interface order and the tree order differ.

### KERN-ARCH-002 closed on AArch64: nothing crosses either way (2026-08-20)

Two halves of one excursion, and the same trampoline pair owns both.

**Out.** The first `eret` into EL0 handed ring 3 every register exactly as the kernel left it. x1 was
the user stack pointer, x3 the SPSR, x4 the ADDRESS OF THE THREAD'S RESUME SLOT and x5 the parked
kernel stack pointer - two kernel pointers, handed over by a program that only asked to run - with
x6..x30 and the whole SIMD file carrying whatever the kernel had last computed there, which on this
port includes bulk memory moves. Later entries were never the problem: the trap frame restores what
the user itself last had. This is the one path that decides what a fresh context STARTS with, and it
decided nothing. `aarch64_enter_el0` now zeroes x1..x30, all thirty-two V registers and FPSR/FPCR
before the `eret`; x0 is the argument the caller asked for.

**Back.** AAPCS64 makes the low halves of v8..v15 callee-saved, and this pair is a callee like any
other - `enter` is an ordinary call, and `SYS_USER_EXIT` returns by unwinding to its caller through
`exit`. Only the GPRs were saved, so a user program writing to d8..d15, which it is entitled to do,
handed those values back as the kernel's own callee-saved state. The frame is 160 bytes now and
carries them.

The test measures both across one excursion. `aarch64_el0_fp_probe` puts a distinct canary in each
of d8..d15 and makes the same call `enter` makes - in assembly, because an `asm!` block declaring
those registers clobbered would make the compiler spill its own values around the measurement, which
is the behaviour under test. The EL0 program folds x1..x30 and BOTH halves of v0..v31 into one word,
stores it, then deliberately clobbers d8..d15 and exits. The kernel requires the word to be zero and
the canaries to have come back.

Watched to fail both ways. With the scrub removed: `ring 3 could see 0xffffff80ffffffff in registers
the kernel handed it`. With the FP restores removed: `the excursion did not give back d8..d15 (bit 0
= d8): 0b11111111` - all eight. A leak in any register fails this whether or not anyone thought to
name that register.

### KERN-ARCH-016 closed: an MSI-X entry is mapped whole (2026-08-20)

The x86 backend mapped ONE page of a device's MSI-X table and wrote four dwords at the entry's
offset into it. An MSI-X table's offset within its BAR is 8-byte aligned - the low three bits of the
capability field hold the BIR - so a spec-valid device can put its entry at 0xff8, and the last two
dwords, message data and vector control, then go to an unmapped address: a kernel page fault while
programming an interrupt, and the same assumption again at teardown when masking.

`msix_pages_for_entry` answers how many pages the entry needs, `program_msix_entry` maps that many,
and the teardown unmaps them in reverse - the mask is written through the second page when the entry
straddles, so it has to go last. The per-slot stride went from one page to two, which is what keeps
a straddling entry off its neighbour's fixed address; the whole 192-slot window is 1.5 MiB and still
inside the single page table `init` materialises for it.

The test walks every 8-byte-aligned offset in a page and requires the entry's last byte to be inside
what would be mapped, checks the 0xff0/0xff8 boundary by name, and asserts both the slot stride and
the window's total size. Asserted as arithmetic because the failure is a kernel page fault and QEMU
will not place a table where it would happen. Watched to fail: pinned to one page it reports the
entry at 0xff8 ending past it.

The other two ports reach MSI-X tables through the physical direct map, which is contiguous, so
neither has this to fix.

### KERN-ARCH-022 closed: the framebuffer comes back whole (2026-08-20)

ramfb's failure path called `frame::deallocate(fb_phys)` once, with a comment saying "the run stays
contiguous" - true of the memory, and nothing to do with how much of it comes back. That API
releases exactly ONE frame, so a 1920x1080 framebuffer left 2024 of its 2025 pages gone for the life
of the boot, on a path that only runs when something has already failed and nobody is watching the
free count. `release_span` gives back the whole run and now serves the scratch span in the same file
too, which had the loop written out by hand.

The test allocates an eight-page contiguous span, releases it through `release_span`, and requires
the free count to return exactly - measured on the allocator, because forcing the final fw-cfg DMA
to fail needs a device that is not there. Watched to fail: cut back to one page it comes up seven
short.

### KERN-ARCH-023 closed: the CMOS clock is serialised and every wait is bounded (2026-08-20)

Three defects in one small file.

A CMOS read is two port accesses - select at 0x70, read at 0x71 - and nothing held them together.
Another core selecting its own register in between meant the first core read whatever the second had
selected: a minute where the hour should be, silently and with the right shape. The whole snapshot,
including the status byte the decode is done against, now runs under one lock.

Both waits were unbounded: the update-in-progress spin, and the loop that wanted two agreeing
passes. An RTC that is absent, wedged with `UIP` set, or ticking faster than the reads never leaves
either - and `SYS_CLOCK_RTC` reaches this from a syscall entry with interrupts masked, so ring 3
could take a core out of the machine with a clock read and no timer left to bring it back. Both are
budgets now, and a clock behaving as specified is nowhere near either.

And bit 7 of the index port is the NMI MASK. Every register index here is below 0x80, so the old
code left NMI enabled by arithmetic rather than by decision; it is masked explicitly now, because a
future index with the high bit set would turn NMI off for the life of the machine.

`snapshot` takes its reader as a parameter, which is what makes any of this testable: an RTC stuck
mid-update is not something QEMU can be asked for. Three tests drive it with mocks - one always
updating, one never settling, one that ticks once and then holds still - and a fourth covers the
decoding, which nothing had ever covered: BCD against binary, the 12-hour PM flag, midnight as hour
12 with the flag clear, an implausible century, and dates the clock cannot be reporting. Watched to
fail: forcing `binary` breaks the BCD case, and doubling the UIP budget breaks the read count.

### KERN-ARCH-017 closed: an interrupt identifier is as wide as the architecture makes it (2026-08-20)

The portable interrupt identifier was a `u8` - the width of an x86 IDT vector, standing in for every
architecture. A GICv2m SPI is ten bits and an IMSIC EID eleven, so on two ports of three the
identifier a backend handed back was a truncation. The aarch64 path made that concrete: it
programmed the full `u32` SPI into the device's message data and then returned `spi as u8`, so on a
frame based at SPI 256 or above the hardware stayed armed under the real SPI while the registry, the
bind, the teardown and `lsirq` all named `spi & 0xff` - a different interrupt, possibly another
device's, and on QEMU's numbering possibly an SGI.

`Interrupt`, the three backends' whole public surface (`is_bindable`, `bind`, `unbind`, `bind_msi`,
`is_bound`, `eoi`, `register`, `acquire_msi`, `acquire_msi_unique`, `release_unused_msi`),
`HandlerFn` and `sys_interrupt_bind` now carry `u32`. The x86 IDT vector stays a byte where it is
one - a gate index IS a byte - and widens on the way out.

QEMU virt's GICv2m frame starts at SPI 80, so the test stands up a frame based at 256 (saving and
restoring the real range, and taking every result before restoring it, so a failed assertion cannot
leave the following tests looking at a machine that does not exist), acquires a slot through the
real `acquire_msi`, and requires SPI 256 back. Watched to fail: with the truncation reintroduced it
reports `the frame's first slot is SPI 256, not SPI 256 truncated to a byte` - it answers 0, which
on this port is SGI 0, the cross-core wake IPI.

RISC-V's EIDs run 1..=62 today, so nothing was reachable there; the width is now correct rather than
accidentally sufficient.
