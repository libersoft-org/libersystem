# P02M0088 - Multi-arch track follow-ups (the P02M0085-P02M0087 loose ends)

Status: REOPENED (2026-08-16) by a fourth-party audit round, recorded in AI/audit/kernel.md (architecture findings) and AI/audit/fdt.md. The findings are appended as open tasks in the section at the end of this file; each was checked against the tree before being written down, and where a check contradicted the audit that is recorded with the task rather than dropped. Previously: COMPLETE (2026-07-11). Three loose ends from the P02M0085-P02M0087 port track that had been
recorded only as inline notes inside finished boxes, which is how they nearly stayed.

*Condensed 2026-08-08.*

**The unlocked page-table race, closed on x86_64 and aarch64.** riscv64 had already gained a
`PT_LOCK`; the other two had the same latent race and no lock. Both backends now take the same
`SpinLock<()>` - a **leaf** lock over the frame allocator, with page-table-then-frame ordering and
never the reverse, so it cannot deadlock. x86_64 takes it in `map_page_in` and `unmap_page_in`, the
funnel every mapping goes through.

*(P02M0089 then wrote the concurrency test for it, which immediately found a real aarch64 leak the lock
did not cover: `free_address_space` descending one level short on a four-level tree.)*

**aarch64 boots the clean production path.** Its non-test tail ran `aarch64_run_demos()`; it now runs
the same production sequence as the others - system manager, the service chain, the shell on an
interrupt-driven idle halt.

**The device tree reaches the kernel through `BootInfo`, not through injection.** Two avenues were
open; the loader building a `BootInfo` with a `dtb` field was chosen over injecting a DTB, so the
device-tree architectures enter their boot stub with the pointer where QEMU `-kernel` would have put
it. One path, whether the firmware or the loader started the kernel.

## Fourth audit (2026-08-16): `AI/audit/kernel.md` architecture findings, and `AI/audit/fdt.md`

The same external audit reported twenty-five architecture and platform findings, five of them
Critical. Two were checked line by line before being written down; those checks are recorded here.

- [ ] **RISC-V trusts a user-controlled `tp` as the kernel per-CPU pointer (KERN-ARCH-001, reported
  Critical, security).** VERIFIED AGAINST THE TREE, AND IT IS AS DESCRIBED. `percpu::this_cpu` and
  `this_cpu_mut` both read `tp` directly (`mv {}, tp`) and dereference it. `__trap_entry` swaps `sp`
  with `sscratch` to reach the kernel stack, saves `x4` - which IS `tp` - into the frame, and NEVER
  establishes a trusted kernel `tp` before calling Rust. U-mode may put any value in `tp`, so a
  syscall or a timer trap makes the kernel read and write per-CPU state through an address the user
  chose. `percpu::set_from_user` writes through it on the syscall path. That is an arbitrary S-mode
  write from ring 3, and it is the most serious thing in the whole audit set. The fix is the one the
  `sp` path already uses: swap a trusted per-hart pointer from an architecturally reserved location
  on every trap and restore the user `tp` only immediately before `sret`.
- [ ] **Privilege entry leaks registers on AArch64 and RISC-V, and AArch64 violates the kernel FP ABI
  (KERN-ARCH-002, Critical).** Registers not restored on the way out carry kernel values back to
  ring 3.
- [ ] **A RISC-V user `ebreak` causes a nested supervisor fault; ordinary x86 user exceptions halt
  the machine; x86 accepts entry and stack values that can fault during ring-0 `iretq`
  (KERN-ARCH-003, -004, -005, all Critical).** Each turns a user-triggered fault into a dead machine
  rather than a dead process - the property P02M0119 established for user copies, not yet held for
  user faults.
- [ ] **AArch64 and RISC-V boot direct maps leave writable-executable aliases (KERN-ARCH-006).**
  W^X is advertised and not held on two of three targets.
- [ ] **The global tick rate multiplies by CPU count on AArch64 and RISC-V (KERN-ARCH-007).** Every
  deadline in the system is then wrong by the core count, which is worth measuring before fixing so
  the milestone records what it actually was.
- [ ] **Non-x86 CPU discovery assumes dense IDs and publishes CPUs that never came online; a missing
  x86 AP trampoline leaves a phantom multi-CPU count; the AP trampoline truncates CR3 to 32 bits;
  CPUs above index 63 are omitted from TLB shootdowns (KERN-ARCH-008, -009, -010, -012).** The last
  is a correctness bound hiding in a `u64` bitmask.
- [ ] **Device and interrupt plumbing (KERN-ARCH-014 through -017, -022, -023).** Virtio PCI
  capabilities from different BARs coerced into one mapping; ECAM BAR allocation overlapping
  retained firmware BARs; an MSI-X table entry that can straddle the one mapped page; GICv2m SPI
  identifiers truncated to eight bits; ramfb failure freeing only the first page; RTC access racing
  between CPUs with unbounded polling.
- [ ] **AArch64's fallible mapper leaks intermediate page tables on OOM, and every 4 kB mapper
  assumes an existing intermediate entry is a table (KERN-ARCH-019, -021).**
- [ ] **Inherited `CR4.FSGSBASE` can let ring 3 redirect trusted GS state (KERN-ARCH-024).**
  Conditional on the firmware leaving it set, which is why it needs to be established rather than
  inherited.
- [ ] **The device tree's `/reserved-memory` subtree is never read (FDT-001, reported High).**
  VERIFIED: `grep -rn "reserved-memory" --include=*.rs src/` matches NOTHING. Only the header
  reservation block at `off_mem_rsvmap` is walked, so firmware, secure-world, DMA-pool and
  framebuffer ranges declared the standard way sit inside a `/memory` bank the allocator is then
  told it owns. UEFI boots take the EFI memory map and are not exposed; direct DT boots are.
- [ ] **`Fdt::new` is a safe function that dereferences an arbitrary physical address (FDT-007,
  High, soundness).** VERIFIED: `pub fn new(base: u64, phys_to_virt: fn(u64) -> u64) -> Self` stores
  the integer, and `u8_at` does `read_volatile((self.p2v)(pa))`. `Fdt::new(1, identity).is_valid()`
  is safe Rust that reads address 1. Make raw construction `unsafe`, or take a bounded reader.
- [ ] **The rest of the device tree's platform description is thinner than its callers assume
  (FDT-002 through -006, -008).** CPU nodes reduced to a count so consumers invent hardware IDs;
  device addresses ignoring bus translation, `ranges` and `status`; ISA-extension detection by
  substring, succeeding if ANY cpu matches; malformed reservation data failing OPEN into the
  allocator; console metadata permitting truncated addresses; unbalanced token streams accepted.
