# M0141 - Streams as pending operations, and a harness that can move the clock

Three times now a review has found that one client can stop StorageService, and three times the
answer has been a deadline. A deadline bounds the harm; it does not remove it. The service is still
unavailable while it waits, because the receive runs synchronously inside the serve loop.

The structural answer was named in M0139x and never written down as work:

    OP_WRITE_STREAM  -> create a pending write
    stream readable  -> take one chunk
    stream closed    -> commit
    stream timeout   -> abort

With that, no waiting stream blocks anyone: the loop returns to serving after every chunk, and a
sender that stalls costs the service nothing but a table entry.

- Done when: a stream neither blocks the serve loop nor needs a deadline to stop being harmful; a
  second client is served while a stream is pending, and there is a test that proves it; and the
  two tests recorded as unwritable in M0139ae exist.

## Why this is filed now

It was recorded inside M0139's prose - as "a larger change and is recorded as such" - and prose
inside another milestone is not a task anyone picks up. The same is true of the harness's inability
to advance the guest clock: two tests in M0139ae are blocked on it and the blocker existed only as a
sentence explaining why they were not written.

## M0141a - The harness can move the guest clock

Two tests in M0139ae cannot be written without it, and the reason is measurable: a hundred thousand
scheduler passes advance the guest clock by a few hundred ticks, so a bound of thirty seconds is
about a million pumps away. Neither test is hard; both are unreachable.

- [x] A way for a kernel test to advance the guest's notion of time, so a deadline can be reached
  deliberately rather than waited out. The suites run under QEMU with the LAPIC/generic timer, and
  `clock()` reads it, so this is a harness capability rather than a kernel feature - but it has to
  be one the scheduler's timed waiters honour, or nothing wakes.
- [x] Then write the two: an idle stream hitting its deadline, and a list consumer that never
  reads. Both were built and removed during M0139; the notes there record exactly what each needs.

  Done 2026-08-04. `clock_skew()` is added inside each architecture's `ticks()`, not beside it, so
  the SCHEDULER sees the jump too - its timed waiters are compared against the same reading. A skew
  visible only to the test would let a deadline "pass" with nobody woken.

  Both tests were verified by reverting the fix each covers: with the idle deadline removed the
  silent-sender test fails, and with the outbound send unbounded the unread-listing test fails. The
  listing uses eighty entries because the channel queue holds 64 - with two it never blocks, and an
  earlier version of that test passed with the bound REMOVED, which is a decoration rather than a
  test.

Not a workaround: bounding those operations by attempt COUNT instead of time was tried and is
worse. Counting attempts around a wait is meaningless - the wait sleeps to the deadline, so the
counter reaches two - and yielding to make the count meaningful keeps the run queue non-empty, so
`run_until_idle` never settles and the peer that would unblock the service never runs at all.

## M0141b - Streams become pending operations

- [x] `OP_WRITE_STREAM` creates a pending write and RETURNS. The serve loop goes back to its other
  clients; chunks arrive as readability events on the stream's channel.
- [ ] The same for the outbound direction. `stream_list` blocks the service on a consumer that does
  not read, and its bound is a deadline for the same reason - it produces entries synchronously.
- [x] A test that a second client is served while a stream is pending. It is listed in M0139ae as
  impossible today, and it is the one that proves this milestone did what it says.

  Done: a stream is opened and left open, a read from the same client is answered while it is
  pending, and the stream then completes with the bytes it carried. Verified by routing
  `OP_WRITE_STREAM` back through the synchronous dispatch: the suite fails, because the read is
  never answered.
- [ ] Once streams cannot block the loop, revisit what the deadlines are still for. They stop being
  the defence and become a bound on how long a table entry may live, which is a different question
  with different numbers.

### How the inbound half was done

The serve loop intercepts `OP_WRITE_STREAM` like it already intercepted `OP_LIST`: `begin_stream`
validates the destination, registers a `PendingWrite` and returns without answering. The stream's
channel joins the wait set, so a chunk arriving and a client asking for something are the same kind
of event; `take_chunk` takes ONE chunk and returns to the loop. The reply is written by hand at the
end, because the call that asked for it returned long before.

One at a time, deliberately. The memory filesystem accumulates a stream inside the volume so the
accounting can see it, and has room for one such write; a second would have to fall back to
accumulating in the service's heap, which is the hole that path exists to close. A second stream is
refused with `Again` - true and retryable - rather than silently charged somewhere else.

**What this cost, and it is the same trap as three times before.** The loop's wait was
`wait_any(&waits, deadline)`, and `wait_any` passes no flags: a plain timed wait counts as pending
PROGRESS, so `run_until_idle` halts until the deadline whenever the run queue empties. With a
stream deadline in the set, the peer that would send the next chunk could not run - the service
slept thirty seconds and gave up on a sender that had never been given the chance to speak. The
clean-stream test failed with the timeout firing BEFORE the harness sent its first chunk.

Finding it took seven instrumented runs, and every guess before the evidence was wrong: the handle
was correct, the channel was alive and empty, the scheduler registered the wait properly. What
settled it was printing the clock beside the deadline - `now == idle` said three thousand ticks had
passed during sixty-four pumps, which only happens if the harness was asleep. `wait_any_periodic`
exists for exactly this and was not used.

## What this does not change

The bounds that are NOT about blocking stay: the accumulation ceiling, the minimum average chunk
size that refuses a drip-feeder, and the per-path write plan. Those bound what a sender may cost in
memory and work, which a pending-operation model does not address by itself.
