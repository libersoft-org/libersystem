# P02M0159 - Every boot exercises the degraded DMA path and none exercises the isolated one

Status: PLANNED (2026-08-26). DEFAULT PROFILE. NOT A PHYSICAL-HARDWARE OR NATIVE-IOMMU CLAIM.

## Goal

Make an ordinary `./run.sh` boot the machine this system claims to support: one with an IOMMU in it,
every bus-mastering device translated, and the degraded path reached only by asking for it.

One driver stands between here and there, and finding out which one and why is most of this
milestone. The flag flip at the end is three lines.

The claim this milestone may make stays inside what QEMU proves: the DEFAULT emulated x86_64 machine
runs with `virtio-iommu` enforcing and every endpoint attached. It is not a claim about native IOMMU
backends, about aarch64 or riscv64, or about physical hardware - those stay where they are.

## What is there now

`--iommu` is opt-in ([run.sh:137](../../run.sh)), and the reason recorded in the harness
([qemu-run.sh:868-875](../../src/harness/qemu-run.sh)) is that `virtio-gpu` does not come up behind a
translating controller. Everything else does.

Re-measured on 2026-08-26 with `./run.sh --iommu --smp 8` against the shipping ISO, and the picture
is narrower and more useful than the original note:

```
iommu: virtio-iommu is translating - bypass is off and read back as off
iommu: 00:02.0 attached to domain 1
driver.virtio-blk: online
                                     ... nine endpoints, all of them fine ...
iommu: 00:0b.0 attached to domain 9
dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
DeviceManager: restarting virtio_gpu
                                     ... three more attempts, identical ...
devmgr: virtio_gpu did not bind; its resources are released and the next candidate follows
DeviceManager: 9 of 11 device(s) online, 1 unbound
iommu: virtio-iommu present, enforcing=true, healthy=true
dma: every bus-mastering device is translated
```

Three facts come out of that, and two of them close off directions that looked obvious:

- **THERE IS NOT ONE `iommu: FAULT` IN THE WHOLE BOOT.** No device reached an address it was not
  given. Address translation is not what is failing, so "teach the driver to use IOMMU addresses" is
  work with nothing to do: the negotiation is shared code
  ([virtio.rs:207-218](../../src/user/drivers/core/src/virtio.rs)) that takes `ACCESS_PLATFORM`
  whenever the device offers it, and the address answer is one syscall that returns an IOVA for a
  translated device. `virtio-gpu` uses the same two as the four drivers that work.

- **THE DRIVER DIES BEFORE IT SAYS ANYTHING.** There is no `driver.virtio-gpu: online` and no error
  from it - it attaches and then is gone. The three unmap failures are its buffers being torn down as
  the process exits, so they are the shape of its death rather than its cause.

- **THE UNMAP FAILURE IS A SECOND, INDEPENDENT DEFECT, AND IT IS NOT THIS MILESTONE'S.** It is
  recorded against the milestone that owns the IOMMU lifecycle, with the reasoning for why nothing
  had noticed it. It matters here only as a warning: while it stands, a failing driver's frames are
  quarantined rather than returned, so any bring-up attempt is destructive.

## Work

- [ ] **M1 - find out why the driver dies, before changing it.** It exits without printing, so the
  first task is to make it say something: which call returned what, on the path from attach to the
  first control-queue request. The known symptom from the earlier round is that `GET_DISPLAY_INFO`
  never completes, so the question is narrow - does the device receive the request and answer
  nothing, or is the queue itself not where the device thinks it is? Both are answerable by reading
  the used ring and the device status after the timeout rather than by guessing.

- [ ] **M2 - the same measurement with the endpoint's own faults drained at the failure.** Faults are
  polled at binding transitions and at boot, so a fault raised between two of those is reported late
  and could be reported after the driver is already gone. Drain and print at the moment the request
  times out, so "no fault" is established at the moment it matters rather than at the end of the
  boot.

- [ ] **M3 - fix what M1 and M2 name.** Held open deliberately: the fix belongs to whichever layer
  turns out to be wrong, and this milestone does not get to assume it is the driver. It may be the
  driver, the kernel's DMA mapping for this device, or the device model - the earlier round already
  showed `virtio-gpu-pci` fails the same way as `virtio-vga`, which rules out the VGA-compatible
  device model on its own.

- [ ] **M4 - `virtio-gpu` binds, presents and survives a restart under the enforcing profile.** Not
  "it printed online": a frame reaches the display and the driver is still there afterwards. The
  restart matters because the device is the one that has been restarted four times per boot, and a
  bring-up that only works from cold is not a fix.

- [ ] **M5 - the default flips, and `--no-iommu` is what turns it off.** `./run.sh` boots with the
  controller; `--no-iommu` boots without. The help text says WHEN to reach for it - reproducing a
  machine that has no IOMMU, and bisecting a driver that misbehaves under translation - rather than
  only what it does. The `IOMMU` variable stays plumbing, and becomes tri-state so an unset value
  means the default rather than off.

- [ ] **M6 - the test suite does not follow, and the help says so.** The reasoning is already in the
  harness and it stands: putting a controller under every test changes what sixty tests are testing
  without adding a claim the enforcing gate does not already make. What must change is that this
  split stops being a surprise - `run.sh --help` and the testing documentation say that an ordinary
  run is translated and the suite is not, and why.

- [ ] **M7 - the degraded report is checked from the other side.** With the controller present and
  every endpoint attached, the boot prints `dma: every bus-mastering device is translated` and no
  degraded rows. Assert exactly that, so a later change that quietly drops an endpoint back to
  untranslated fails rather than printing one more line nobody reads.

## Dependency order

M1 and M2 are one sitting and produce the answer M3 needs. M4 closes M3. M5, M6 and M7 come after M4
and only after: flipping the default while the display driver still dies would make every developer
boot start without a screen, which is the exact trade this milestone exists to remove.

The unmap defect recorded against the IOMMU milestone should be fixed before M1, because until it is,
every failed bring-up attempt quarantines frames and a long diagnosis session leaks memory it cannot
get back.

## Definition of done

- `./run.sh` on x86_64 boots with `virtio-iommu` enforcing, and every bus-mastering device is
  attached to a domain.
- `virtio-gpu` binds, presents a frame and survives a restart under that profile; the boot carries no
  `DeviceManager: restarting virtio_gpu`.
- The boot prints no degraded rows and no `iommu: FAULT`, and a check asserts both rather than a
  reader noticing.
- `--no-iommu` boots the untranslated machine, and its help text says when that is the right thing to
  ask for.
- The test suite still runs untranslated, and both `run.sh --help` and the testing documentation say
  that it does and why.
- Why the driver was failing is written down here, whatever the answer turned out to be - including
  if it turns out not to have been the driver.

## What this milestone refuses, and why

- **Rewriting the driver before the measurement names it.** The obvious reading - "the display driver
  does not support IOMMU" - is already contradicted by the boot: there are no faults, and the
  IOMMU-facing code is shared with four drivers that work. Rewriting on that reading would be a
  change made against evidence rather than from it.
- **Making the enforcing profile the default on aarch64 and riscv64.** QEMU advertises the device
  there, and device availability is not a tested kernel topology. Those follow their own gates.
- **Putting a controller under the test suite.** Unchanged from the harness's own note, and M6 makes
  the split explicit rather than removing it.
- **Removing the degraded path.** A machine whose firmware offers no IOMMU is a machine this system
  must still boot, and `--no-iommu` is how that machine stays reachable from here.
- **A physical-hardware claim.** This is the default EMULATED profile. Native backends, firmware
  tables and real silicon are not in it.
