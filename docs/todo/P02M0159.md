# P02M0159 - Every boot exercises the degraded DMA path and none exercises the isolated one

Status: COMPLETE (2026-08-29). Every audit finding in this file is closed and the gate this milestone
names as its own evidence passes end to end, the DEFAULT-MACHINE phase included - the one phase that
had never passed, because the kernel's supervised boot never reached its own readiness check and so
never printed the isolation summary. See the definition of done for what that turned out to be. Run
against the tree on 2026-08-29:

    qemu-virtio-iommu: the controller transitioned out of bypass, five hostile cases were refused by the hardware, an ordinary endpoint passes real traffic, and the DEFAULT machine is the isolated one

Previously REOPENED (2026-08-26). An independent audit of the closed milestones found 3 verified defects; they are the last section of this file. Was COMPLETE (2026-08-26). DEFAULT PROFILE. NOT A PHYSICAL-HARDWARE OR NATIVE-IOMMU CLAIM.

`./run.sh` boots a machine with a `virtio-iommu` in it and every endpoint translated; `--no-iommu`
boots the other one. The driver that blocked it was not at fault: the IOVA allocator was handing out
the null address, which a virtio device reads as "this queue was never programmed".

## Goal

Make an ordinary `./run.sh` boot the machine this system claims to support: one with an IOMMU in it,
every bus-mastering device translated, and the degraded path reached only by asking for it.

One driver stands between here and there, and finding out which one and why is most of this
milestone. The flag flip at the end is three lines.

The claim this milestone may make stays inside what QEMU proves: the DEFAULT emulated x86_64 machine
runs with `virtio-iommu` enforcing and every endpoint attached. It is not a claim about native IOMMU
backends, about aarch64 or riscv64, or about physical hardware - those stay where they are.

## What is there now

`--iommu` is opt-in ([run.sh:137](../../run.sh)), and the reason recorded in the harness
([qemu-run.sh:868-875](../../src/harness/qemu-run.sh)) is that `virtio-gpu` does not come up behind a
translating controller. Everything else does.

Re-measured on 2026-08-26 with `./run.sh --iommu --smp 8` against the shipping ISO, and the picture
is narrower and more useful than the original note:

```
iommu: virtio-iommu is translating - bypass is off and read back as off
iommu: 00:02.0 attached to domain 1
driver.virtio-blk: online
                                     ... nine endpoints, all of them fine ...
iommu: 00:0b.0 attached to domain 9
dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
dma: an unmap did not complete - 1 frame(s) are QUARANTINED rather than returned
DeviceManager: restarting virtio_gpu
                                     ... three more attempts, identical ...
devmgr: virtio_gpu did not bind; its resources are released and the next candidate follows
DeviceManager: 9 of 11 device(s) online, 1 unbound
iommu: virtio-iommu present, enforcing=true, healthy=true
dma: every bus-mastering device is translated
```

Three facts come out of that, and two of them close off directions that looked obvious:

- **THERE IS NOT ONE `iommu: FAULT` IN THE WHOLE BOOT.** No device reached an address it was not
  given. Address translation is not what is failing, so "teach the driver to use IOMMU addresses" is
  work with nothing to do: the negotiation is shared code
  ([virtio.rs:207-218](../../src/user/drivers/core/src/virtio.rs)) that takes `ACCESS_PLATFORM`
  whenever the device offers it, and the address answer is one syscall that returns an IOVA for a
  translated device. `virtio-gpu` uses the same two as the four drivers that work.

- **THE DRIVER DIES BEFORE IT SAYS ANYTHING.** There is no `driver.virtio-gpu: online` and no error
  from it - it attaches and then is gone. The three unmap failures are its buffers being torn down as
  the process exits, so they are the shape of its death rather than its cause.

- **THE UNMAP FAILURE IS A SECOND, INDEPENDENT DEFECT, AND IT IS NOT THIS MILESTONE'S.** It is
  recorded against the milestone that owns the IOMMU lifecycle, with the reasoning for why nothing
  had noticed it. It matters here only as a warning: while it stands, a failing driver's frames are
  quarantined rather than returned, so any bring-up attempt is destructive.

## Work

- [x] **M1 - find out why the driver dies, before changing it.** It exits without printing, so the
  first task is to make it say something: which call returned what, on the path from attach to the
  first control-queue request. The known symptom from the earlier round is that `GET_DISPLAY_INFO`
  never completes, so the question is narrow - does the device receive the request and answer
  nothing, or is the queue itself not where the device thinks it is? Both are answerable by reading
  the used ring and the device status after the timeout rather than by guessing.

- [x] **M2 - the same measurement with the endpoint's own faults drained at the failure.** Faults are
  polled at binding transitions and at boot, so a fault raised between two of those is reported late
  and could be reported after the driver is already gone. Drain and print at the moment the request
  times out, so "no fault" is established at the moment it matters rather than at the end of the
  boot.

- [x] **M3 - fix what M1 and M2 name.** Held open deliberately: the fix belongs to whichever layer
  turns out to be wrong, and this milestone does not get to assume it is the driver. It may be the
  driver, the kernel's DMA mapping for this device, or the device model - the earlier round already
  showed `virtio-gpu-pci` fails the same way as `virtio-vga`, which rules out the VGA-compatible
  device model on its own.

- [x] **M4 - `virtio-gpu` binds, presents and survives a restart under the enforcing profile.** Not
  "it printed online": a frame reaches the display and the driver is still there afterwards. The
  restart matters because the device is the one that has been restarted four times per boot, and a
  bring-up that only works from cold is not a fix.

- [x] **M5 - the default flips, and `--no-iommu` is what turns it off.** `./run.sh` boots with the
  controller; `--no-iommu` boots without. The help text says WHEN to reach for it - reproducing a
  machine that has no IOMMU, and bisecting a driver that misbehaves under translation - rather than
  only what it does. The `IOMMU` variable stays plumbing, and becomes tri-state so an unset value
  means the default rather than off.

- [x] **M6 - the test suite does not follow, and the help says so.** The reasoning is already in the
  harness and it stands: putting a controller under every test changes what sixty tests are testing
  without adding a claim the enforcing gate does not already make. What must change is that this
  split stops being a surprise - `run.sh --help` and the testing documentation say that an ordinary
  run is translated and the suite is not, and why.

- [x] **M7 - the degraded report is checked from the other side.** With the controller present and
  every endpoint attached, the boot prints `dma: every bus-mastering device is translated` and no
  degraded rows. Assert exactly that, so a later change that quietly drops an endpoint back to
  untranslated fails rather than printing one more line nobody reads.

## Dependency order

M1 and M2 are one sitting and produce the answer M3 needs. M4 closes M3. M5, M6 and M7 come after M4
and only after: flipping the default while the display driver still dies would make every developer
boot start without a screen, which is the exact trade this milestone exists to remove.

The unmap defect recorded against the IOMMU milestone should be fixed before M1, because until it is,
every failed bring-up attempt quarantines frames and a long diagnosis session leaks memory it cannot
get back.

## Definition of done

- `./run.sh` on x86_64 boots with `virtio-iommu` enforcing, and every bus-mastering device is
  attached to a domain.
- `virtio-gpu` binds, presents a frame and survives a restart under that profile; the boot carries no
  `DeviceManager: restarting virtio_gpu`.
- The boot prints no degraded rows and no `iommu: FAULT`, and a check asserts both rather than a
  reader noticing.
- `--no-iommu` boots the untranslated machine, and its help text says when that is the right thing to
  ask for.
- The test suite still runs untranslated, and both `run.sh --help` and the testing documentation say
  that it does and why.
- Why the driver was failing is written down here, whatever the answer turned out to be - including
  if it turns out not to have been the driver.

MET (2026-08-29) - `./check.sh --gate qemu-virtio-iommu-x86_64` passes end to end, the default-machine
phase included. That phase had never passed, and the reason was not in this milestone's subject at
all: `supervise` drove its first drain with the UNBOUNDED `run_until_idle`, which returns only when
nothing is runnable and nothing is waiting on a deadline - a state the service set never reaches,
because virtio-gpu polls its display size on a repeating timer. The drain never returned on any
default boot. The whole system ran inside it - drivers bound, DHCP completed, the shell printed its
prompt - while the loop that asks whether a shell is listening, and everything after it, was never
reached: no readiness, no `SYSTEM_IS_UP`, and no `dma_policy::report`, which is the isolation summary
this gate requires of an ordinary boot.

Four things were behind it. The drain is bounded; it is bounded by a SLICE rather than by the window,
because `run_until_idle_until` returns only once its bound has passed and handing it the window's own
deadline makes the readiness question a formality asked after the window is over; the window itself
was 300 ticks against a MEASURED settle of 1085 on the default x86_64 machine, so it is 3000 now with
the measurement recorded at the call site; and a window that closes over a LIVE SystemManager is no
longer treated as a failed boot that ends in `arch::reset()` - the system is up and the console has
not attached yet, which is what a CD-ROM-backed or emulated machine looks like. `console_shell_loop`
was corrected with it: it read "no shell yet" as "the shell exited" and halted a machine that was
still coming up.

AND THE SUMMARY RETRACTS ITSELF. Reaching the end of that window says the machine is up, not that
DeviceManager has finished binding - the traffic profile publishes `dma: every bus-mastering device
is translated` with no endpoint attached and attaches one four lines later - so the summary can be
taken while a driver is still on its way to the bus. Nothing else in the log would contradict a stale
one: untranslated admissions are RECORDED rather than printed, on purpose, so the summary is the only
statement a reader gets. `dma_policy` now remembers that it published, and every admission after that
point says, at the moment it happens, that the device just admitted falsifies the summary above it -
deduplicated like the record it guards, so a driver that reopens its device does not turn one fact
into a flood. That is stronger than moving WHEN the snapshot is taken: a USB stick plugged in an hour
after boot is admitted through the same path, and no boot-time signal can cover it.

The gate's freshness preflight was rewritten with it. It compared the kernel ELF's mtime with the
image's, while the phases exercise DeviceManager, the userspace drivers and the services on the
system volume - all of which `build.sh` rebuilds without rewriting the kernel. It now asks
`mkimage.sh` for this tree's content-derived image key and compares it with the receipt recorded
beside the published medium, and does so BEFORE any phase runs, because the phases themselves rewrite
staged artifacts the key covers. Making that possible needed one fix in the builder: the key hashed
`sha256sum` output including FILE NAMES, so the same tree keyed differently depending on how the
script was invoked - which also meant the image cache missed on nothing.

## What this milestone refuses, and why

- **Rewriting the driver before the measurement names it.** The obvious reading - "the display driver
  does not support IOMMU" - is already contradicted by the boot: there are no faults, and the
  IOMMU-facing code is shared with four drivers that work. Rewriting on that reading would be a
  change made against evidence rather than from it.
- **Making the enforcing profile the default on aarch64 and riscv64.** QEMU advertises the device
  there, and device availability is not a tested kernel topology. Those follow their own gates.
- **Putting a controller under the test suite.** Unchanged from the harness's own note, and M6 makes
  the split explicit rather than removing it.
- **Removing the degraded path.** A machine whose firmware offers no IOMMU is a machine this system
  must still boot, and `--no-iommu` is how that machine stays reachable from here.
- **A physical-hardware claim.** This is the default EMULATED profile. Native backends, firmware
  tables and real silicon are not in it.

## Results

### M1/M2/M3 - the driver was not at fault

The milestone refused to assume the display driver was wrong, and it was right to: it was not. The
measurement went the other way each time an obvious answer was tried.

| Measured | What it ruled out |
| --- | --- |
| Not one `iommu: FAULT` in a whole translated boot | The device never reached an address it was not given - address translation is not what fails |
| `virtio-gpu` uses the same shared negotiation and the same address syscall as four drivers that work | There is no "IOMMU support" missing from this driver to write |
| `dma_buffer_phys_at` returns `base + offset` off the IOVA, printed from the guest as `0x4000`, `0x45f6`, `0x4bec` | The per-page address path, which is the only call `virtio-gpu` makes that the working drivers do not |
| QEMU's `virtio_iommu_translate` trace: 46 translations, 45 completions | Exactly one address the device could not resolve, and the trace named it |

The unmatched one was `0xfee00000`, the x86 MSI doorbell - which turned out to be a second finding
rather than the cause, because QEMU bypasses its own reserved MSI region either way. The cause was
found by asking a different question: which addresses did the device touch AT ALL. It never touched
the receive ring. The ring was at **IOVA 0**, and a virtio device treats a queue whose descriptor
table sits at address zero as a queue that was never programmed - QEMU's `virtio_init_region_cache`
returns early on a zero address and builds no mapping for it. Nothing errors, because from the
device's side there is no queue there.

Without a controller the same drivers work, because a physical frame is never at address zero. The
IOVA allocator's first fit started at the negotiated input range's base, which QEMU publishes as
zero, so the FIRST ring allocated in each domain landed on it.

The fix and its evidence are recorded against the milestone that owns the IOVA space. One line.

### M4 - the display driver, under the controller

```
iommu: every domain carries the MSI doorbell at 0xfee00000+0x100000, mapped one to one - a device's interrupt is a memory write and goes through its own domain
iommu: 00:0b.0 attached to domain 9
driver.virtio-gpu: online (00:0b.0)
DeviceManager: 10 of 11 device(s) online, 1 unbound
network: configured via DHCP - 10.0.2.15/24 via 10.0.2.2
dma: every bus-mastering device is translated
```

No `DeviceManager: restarting virtio_gpu` anywhere in the boot. The one device still unbound is
`xhci`, which does not bind with a controller or without one and is unchanged by any of this. (The
two lines that carry more than they did are the boot report milestone's, landed in the same round.)

### M5/M6 - the default, and the split that goes with it

`./run.sh` boots translated. `./run.sh --no-iommu` boots the other machine and says so:

```
iommu: no virtio-iommu on this machine
dma: DEGRADED ISOLATION - 11 device(s) master the bus untranslated (enforcing=false)
```

The default is conditional on which run this is, not global: `TEST=1` still defaults to no
controller, so `./test.sh` is unchanged and the suite still exercises what it always did. That split
is now stated in `run.sh --help` and in a section of `docs/TESTING.md` rather than left as a
surprise, and it says where a failure that appears only under translation belongs.

### M7 - and a check that the default really is this

The last two phases of the enforcing gate boot the way a developer does, with no flags, and ask the
boot what machine it is: translated, no degraded rows, no faults, and the display driver running.
Then `--no-iommu`, to prove the untranslated machine is still reachable - a system that can only
boot one of them has not made isolation optional, it has made every machine without an IOMMU
unreachable.

```
qemu-virtio-iommu: booting the DEFAULT machine, the way an ordinary run does
qemu-virtio-iommu:   the default machine is translated, nothing is degraded, nothing faulted, and the display driver runs
qemu-virtio-iommu: booting --no-iommu, the machine without one
qemu-virtio-iommu:   --no-iommu boots the untranslated machine and says so
```

Every earlier phase of that gate builds its own QEMU command line, so all of them would keep passing
on a day when `run.sh` quietly stopped putting a controller in the machine it boots. That is exactly
the state this milestone found the tree in, where the isolated path was proved by one gate and
walked by nobody.

### What this milestone found on the way, and did not fix

- **`--iommu` was an environment variable in a script where everything else is a flag.** Fixed while
  here, then replaced by `--no-iommu` when the default flipped. `EL2=1` in `test.sh` is the same
  shape and is still an environment variable; it is left for whoever next touches that script.
- **`xhci` does not bind, translated or not.** Pre-existing, unchanged, and out of scope here.

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED. The default profile is real; two of the ways the gate proves it are not
fail-closed.

- [x] **The default-machine phase cannot fail on a crash.** It runs `timeout 120 ./run.sh ... || true`
  ([check-qemu-virtio-iommu-x86_64.sh](../../src/tools/check-qemu-virtio-iommu-x86_64.sh)), which it
  has to - an ordinary run does not exit - and then greps for the lines it wants. A guest that prints
  all of them and panics ten seconds later passes. The greps that follow already assert the absence
  of degraded rows and of faults; add the absence of a panic and of a guest reset to them.

- [x] **The ISO is checked for existing, not for being this build's.** `[[ -f "$ISO" ]]`
  ([check-qemu-virtio-iommu-x86_64.sh](../../src/tools/check-qemu-virtio-iommu-x86_64.sh)) is the
  whole test, so an image built before the change under test satisfies both the ordinary-traffic
  phase and the default-machine phase. Compare it against the kernel it is supposed to contain.

- [x] **The display proof is one line, and it does not exclude a restart loop.** `driver.virtio-gpu:
  online (` is asserted, and the driver sends it after `display_size()`, which is a real
  command-and-response round trip through the controller - so it is not nothing, and the audit's
  reading of it as a bare liveness check understates it. What it does not exclude is a driver that
  comes up, dies and comes up again. Require the line exactly once. A presented-frame oracle is not
  worth building for this: the round trip the online report already depends on is the part that
  needed the IOMMU to work.

## Results (2026-08-26)

The default-machine phase must use `timeout ... || true` - an ordinary run does not exit - and that
swallowed every way the guest could fail after printing the lines the gate wanted. A boot that
printed all of them and panicked ten seconds later passed. The absence of a panic, a guest reset and
a loader FATAL is asserted beside the absences already there.

The ISO was checked for existing, not for being this build's, so an image from before the change
under test satisfied both QEMU phases - the gate would then have proved the isolation default of a
kernel nobody had just changed.

And the display proof requires the online line EXACTLY once. A driver that binds, dies and restarts
prints it on each attempt, and presence alone cannot tell that from a clean bring-up. A
presented-frame oracle was considered and not built: the driver sends its report after
`display_size()`, which is a real command-and-response round trip through the controller, so the line
already depends on the queue working in both directions behind translation - which is the part that
needed the IOMMU.
