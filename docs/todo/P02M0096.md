# P02M0096 - Image conversion tool (`imgconv`)

Status: COMPLETE (2026-07-18, including the P02M0096a dynamic-linking half).

`imgconv <input> <output>` converts every image format LiberSystem supports without gaining display,
input or device authority. Input is identified by bounded content sniffing; the output codec comes
from the destination suffix or an explicit `--format`. The tool receives only `volumes`, so source
and destination may live on different mounted volumes.

*This file was condensed on 2026-08-08: the specification of behaviour now visible in the code was
removed, and what was measured, decided or learned was kept.*

## The rules the codec set is built on

- **One codec or container per leaf**, sharing a pixel/frame vocabulary. No monolithic image crate,
  no "libimage" that grows. Twelve atomized `no_std` leaves.
- **Decoders retain straight alpha.** Premultiplication happens only when `imgview` renders. The
  behaviour this replaced blended PNG transparency against black into B8G8R8X8, which cannot be
  recovered - a conversion tool cannot be built on a display-shaped model.
- **Sniffing is structural, not magic-byte matching.** APNG detection walks real PNG chunk
  boundaries rather than finding `acTL` in arbitrary compressed bytes; PCX validates its header
  fields rather than claiming every file. Unknown and corrupt-but-recognised inputs stay distinct.
- Every dimension, pitch, frame count, cumulative animation pixel total and duration is checked
  before allocation.

## What was built

Twelve leaves with decoders and, where the format has a writable representation, encoders: BMP, PNG,
PPM, QOI, TGA, PCX, ICO, APNG, ICNS, GIF, baseline JPEG and WebP, plus a separate bounded `deflate`
compressor leaf (the existing `inflate` stays a decoder rather than becoming a mixed module).

**WebP is a native `no_std` VP8 keyframe encoder** built from the RFC 6386 bitstream model: boolean
entropy coding, B_PRED luma, DC/V/H/TM chroma search, 4x4 DCT/IDCT, quantization, coefficient bands,
neighbour contexts, zero runs and category tokens. Opaque output uses canonical simple `VP8 `;
transparent output uses `VP8X + ALPH + VP8 ` and preserves alpha exactly. Lossy animated output is
explicitly unsupported rather than silently dropping frames.

**Quality and compression are independent and never overloaded.** Lossy WebP: quality 0..100 drives
the quantizer, effort 0/25/50/75 progressively admits chroma predictor candidates with deterministic
tie-breaking. Lossless WebP: effort 0 picks the plain VP8L profile, intermediate levels analyse a
proportionally growing row sample and choose predictor-off/on from measured residual variation,
effort 100 encodes both valid profiles and publishes the smaller. Fixed-compression formats reject
the controls rather than ignoring them.

Gates: `just image-conformance` validates every emitted profile against 11 external-tool recipes
covering all 12 formats, plus an independent input corpus. `just image-mutate` passes 11,392
prefixes, 34,296 targeted mutations and 2,304 seeded mutations through the leaves and the sniffer.

Measured: quality-100 RGB MSE 0.566 against a bound of 25; quality 100 versus quality 0 measures MSE
250 against 923. `webp.lslib` is 349,912 / 442,936 / 384,000 bytes on x86_64 / AArch64 / RISC-V.
Benchmark ceilings are 8 MiB per static profile and 4 MiB encode / 2 MiB decode for WebP; measured
VP8L effort-100 peaks 3,670,706 / 1,049,888 bytes and VP8 quality-100 peaks 2,542,735 / 1,835,124.

## The memory budget, and why the first measurement was wrong

The governed tool ran under a 96 MiB Domain quota that refused to convert the one image the system
actually ships. The arithmetic was never wrong - the measurement was.

All three cases the original budget was sized from **upscale from a tiny source** (a 2x2 BMP, a 23x15
WebP), so the decoded input costs nothing and the peak is essentially one output buffer. The shipped
`wallpapers/logo.webp` is a 3840x2160 lossy WebP: converting it holds a decoded 4K input *and* a 4K
output at once, about 33 MB each - a term no synthetic upscale can show.

Measured, all four now pinned by `imgconv_governed_working_set_is_measured`:

| case | peak bytes |
|---|---|
| 1920x1080 upscale | 22,368,256 |
| 3840x2160 upscale | 85,135,360 |
| 23x15 animation | 2,105,344 |
| the shipped 4K wallpaper | 109,830,144 |

The real conversion costs 29% more than the 4K upscale the old limit was sized from. The budget is
128 MiB, which keeps roughly the original relative headroom (22% against 19%) - the author's intent
preserved, only the measurement replaced.

**The test measures in a deliberately generous 512 MB Domain and compares against the production
quota**, rather than running inside the production Domain. That is the difference between a failure
saying `out of memory` and one saying `measured 109,830,144 bytes against a 100,663,296 byte limit`.
The first is the least useful possible answer to the question "what should the quota be", and it is
exactly what the original setup produced. The production constant and the test's copy now name each
other, because a kernel test cannot read a userspace service's constant and a copy that drifts
asserts against a quota nobody enforces.

Two things about the measuring cost two runs and are worth passing on. A 4K PNG of that wallpaper is
2.2 MB, so media capacity was never the constraint - `cannot write output` was read as a small
medium and the capacity was raised on that guess instead of on a measurement. Worse, the raise asked
for 65,536 FAT16 clusters, past the 65,524 the format allows, producing an image the driver refuses
and the identical message. **That message does not distinguish a full medium, a malformed medium and
a failed write**, which is a defect of its own and the reason both wrong turns looked like progress.

## P02M0096a - the dynamic-linking half

The milestone also converted the image to one coherent PIC provider/consumer graph.

- **A tiny generated `_start` object per architecture**, not a static runtime: `tools/exe-start.rs`
  emits it from checked Rust source and the build audits its exact symbol and relocation boundary.
  688 / 736 / 776 bytes on x86_64 / AArch64 / RISC-V; RISC-V is explicitly RV64GC `lp64d` to match
  consumer ELF flags. `lsrt` owns the shared ABI-check entry `liber_rt_start`.
- **A strict executable graph enforced at image construction.** The final packager re-parses the
  stripped bytes of every declared dynamic executable with the same bounded ELF reader the runtime
  uses, and rejects a wrong machine, non-`ET_DYN`, missing or duplicate `PT_DYNAMIC`, W+X,
  `PT_INTERP`, RPATH/RUNPATH/TEXTREL, malformed `DT_NEEDED`, a missing direct `lsrt.lslib`,
  unstaged provider names, and any difference between `DT_NEEDED` and the manifest edge set. Static
  `/bin` injection fails before `volume.pkg` is written.
- **Provider load order is canonical, not encounter order.** ProcessService maps and validates the
  whole bounded dependency graph before loading anything, then repeatedly selects the
  lexicographically smallest provider whose dependencies are already loaded. The image linker
  derives the same order independently and emits a bounded sidecar per executable; ProcessService
  refuses a missing, malformed or different order before creating a process. Slot biases therefore
  follow one provider-before-consumer order on every boot.
- **A standing gate stops the rule decaying.** Cargo metadata for the `tools` package must match its
  sorted manifest rows exactly, so a future tool fails image construction until it enters the
  dynamic graph, and package staging rejects every non-`ET_DYN` artifact under `vol://system/bin`
  including a loose injected file.

## What was left deliberately incomplete

The listed future format profiles remain typed, non-blocking subsets rather than silent
approximations - an unsupported profile fails by name.
