# M0146 - What M0144 left in the disk probe, and three gaps it opened itself

A third audit of LiberFS by the same fourth party, delivered after M0144 closed and verified claim
by claim against the code at `de562de` on 2026-08-06. **All ten of its findings hold.**

Its verdict on M0144 is fair and worth recording before the complaints: six of the eleven fixes are
complete against the problem they were written for, four are much better with residue, and one - the
partition probe - is still not safe. That matches what this verification found.

The uncomfortable part is that **three of these ten are regressions M0144 introduced**, not residue
it failed to clear:

- Reserving an unknown-type inode's blocks without teaching the DELETE path to release them.
- Rewriting the directory walk iteratively and reversing the order it documents.
- Refusing an allocation in the structural pass by returning silently.

Each was a consequence of a fix that was itself correct. The lesson is the same one M0144 recorded
about the read-only-versus-repair-verb trade: a change that improves one path has to be followed
into every path that shares its assumptions, and none of the three had a test that would notice.

Ordered by what is at stake.

## The disk probe is still not safe

- [x] **`RawDisk` means "LBA 1 does not begin with EFI PART", which is not the same as "blank".**
  The probe answers `RawDisk` for anything whose LBA 1 lacks the GPT signature, and
  `mount_or_format` treats that as licence to format the whole device from `FS_START_SECTOR`, which
  is 0.

  So the disks that get formatted from sector zero now include: an ordinary MBR-partitioned disk; a
  hybrid MBR; a GPT disk whose first eight bytes are damaged while its protective MBR and backup GPT
  are intact; a "superfloppy" carrying FAT or ext4 directly at LBA 0; and any disk holding foreign
  data with no GPT signature. LiberFS finds no magic on such a disk, reports `Unformatted`, and the
  service lays a filesystem over it.

  M0144 fixed the answer for a GPT that IS recognised and left the negative case exactly as
  dangerous as it was. The rule established there - an answer meaning "I could not tell" may not be
  read as "there is nothing here" - applies to the absence of a GPT signature as much as to a failed
  read.

  Wanted, as the audit puts it: `BlankRawDisk`, `LiberFs`, `MbrWithoutLiberFs`, `GptWithoutLiberFs`,
  `CorruptGpt`, `ForeignFilesystem`, `Io`. `BlankRawDisk` requires LBA 0 AND LBA 1 read, no active
  MBR entries and no protective MBR at LBA 0, no GPT at LBA 1, and no recognisable foreign
  filesystem. Formatting a whole device follows that answer alone.

- [x] **The GPT that IS parsed is believed without being verified.** The probe checks the signature,
  that `entry_size` is a power of two in range, that `num_entries` is non-zero, the type GUID,
  `first != 0`, `last > first`, and a minimum span. It checks none of: the header CRC32, the
  partition-entry-array CRC32, `header_size`, `current_lba`, `backup_lba`, `first_usable_lba`,
  `last_usable_lba`, the partition against the device's real capacity, overlap with the GPT header
  or the entry array, or overflow in the entry-array LBA arithmetic.

  The scenario is small: an entry with the LiberFS type GUID, `first = 1`, `last = 100000`. Every
  check above passes - `first` is non-zero and `last` exceeds it. The mount then targets LBA 1,
  which is the primary GPT header itself, finds no superblock, reports `Unformatted`, and the
  service formats starting on top of the partition table that named the partition.

  So the typed probe closed the `None` → whole-disk path and still trusts unverified numbers to
  decide WHERE it may write, which is the same class of mistake one level in.

  Wanted: verify both CRCs, check every header LBA relation, obtain the device's actual capacity,
  use checked arithmetic throughout, require the partition to lie wholly inside the usable range,
  refuse any overlap with GPT metadata - and when the primary GPT is damaged, consult the backup
  rather than formatting anything.

## The three M0144 opened

- [x] **An unknown-type inode's blocks are reserved and never released.** M0144 made the mark walk
  treat a type byte that is neither `TYPE_FILE` nor `TYPE_DIR` as file-shaped, so its data, checksum
  and spill blocks are reserved instead of left free for the allocator. That part is right and the
  test covers it.

  What was not followed through is the other end. `drop_deleted_inode` branches
  `if r#type == TYPE_FILE { drop_inode_blocks } else if dir_root != 0 { drop the tree }`, and an
  unknown type is neither: it is not `TYPE_FILE`, and `Inode::parse` only fills `dir_root` for
  `TYPE_DIR`, so it is zero. Removing such an inode clears the name and the record and drops
  nothing.

  Before M0144 that was consistent - nothing was reserved, so nothing needed releasing. Now the
  blocks stay marked used for the life of the mount, until a remount, an `fsck`, or a snapshot
  change forces a full rederive. The repair verb still works and the space does not come back with
  it.

  The fix is one character of intent: `if r#type != TYPE_DIR { drop_inode_blocks }`, which is the
  same "file-shaped unless it is a directory" rule the parser and the mark walk already use. The
  test asserts the record disappears and says nothing about the blocks; it should assert both.

- [x] **The iterative directory walk reversed the order it promises.** `collect_dir_entries` is
  documented as returning entries "in key order", and M0144 replaced its recursion with a LIFO stack
  that pushes children `0..=count` and pops the last one first. Records inside a leaf stay sorted;
  the leaf GROUPS come out right-to-left, so any directory large enough to have an internal node
  lists in the wrong order through `list` and `read_dir`.

  The security fix was the point and it holds. This is a behavioural regression beside it, and the
  correction is to push in reverse so child 0 is popped first.

  Worth noting why no test caught it: the directory tests use few enough entries that the tree is a
  single leaf, where LIFO and FIFO are the same thing. A test with enough names to force a split
  would have failed immediately.

- [x] **A refused allocation in the structural pass is silent.** `check_dir_structure` begins
  `let Ok(mut visited) = try_zeroed(...) else { return };`, so when memory is short it checks nothing
  and reports nothing - and `fsck` returns a clean structural report for directories it never looked
  at. A report that cannot distinguish "checked and sound" from "not checked" is worse than one that
  admits the difference.

  Related, and from the same M0144 change: a `try_zeroed` failure inside `derive_free` surfaces as
  `FsError::NoSpace`, and the mount maps everything except `Corrupt` at that point to
  `MountError::Io`. StorageService then tells the operator the disk did not answer when the problem
  was memory. The process no longer aborts, which was the point; the diagnosis is now wrong instead
  of fatal.

  Wanted: a fault recorded when a check cannot run, and `NoSpace` carried through to
  `MountError::NoMemory` rather than folded into `Io`.

## Residue M0144 did not reach

- [x] **The overflow chain still clamps an impossible record count.** `Extent::parse` was fixed to
  keep what is on the medium, and `load_spill` was not: it still computes
  `count = raw.min(EXTENTS_PER_BLOCK).min(want)`. A checksum-consistent chain block can claim more
  records than fit in a block, or more than the inode is still missing, and the number is quietly
  normalised into a possible one. The structural pass then has nothing to disagree with.

  Same treatment as the extent fields: `raw_count > EXTENTS_PER_BLOCK` or `raw_count > remaining` is
  `Corrupt`, not something to trim.

- [x] **The directory checker knows one rule about names and the path API knows eight.** Creating a
  path refuses invalid UTF-8, empty segments, `.` and `..`, control characters, the reserved
  punctuation set, NUL, and over-long names. `check_dir_structure` checks UTF-8 and non-empty, so a
  record read off the medium named `..`, or `a/b`, or one carrying a control character, passes an
  `fsck` that a path API could never have produced and cannot address afterwards.

  Wanted: one `validate_name_segment` used by both `split_segments` and the structural checker, so
  the two cannot drift again.

- [x] **A null child pointer inside an internal node is accepted as ordinary.** Both walks treat
  `ptr == 0` as "nothing here" and move on. That is right for an empty directory root and for a
  sentinel outside the tree, and wrong for a child slot of an internal node: a B+tree node missing a
  child is an impossible structure, and every key routed into that slot resolves to nothing while
  `fsck` reports the tree clean because the counts add up.

- [x] **The shared visited map can hide a bad CRC in a second snapshot's link.** `fsck` walks every
  snapshot with one visited bitmap, which is what makes it affordable. But the skip happens BEFORE
  the block is verified against the CRC recorded in the link that reached it - so if snapshot A
  verified a shared block and snapshot B points at the same block with a wrong expected CRC, B's bad
  link is never checked. Snapshot B cannot actually be opened, and `fsck` says nothing about it.

  The optimisation needs to distinguish "this block's contents have been scrubbed" from "this
  particular (block, expected CRC) link has been verified".

- [x] **The label check stops at the first NUL and the rest of the field is unexamined.** M0144
  validates `name_in(&label)`, which is what `label()` returns - deliberately, and recorded as such.
  The audit's narrower point stands anyway: a field like `system\0\xff\xffgarbage` is not something
  any writer produces, so the bytes after the terminator being non-zero is itself evidence the
  record was not written by this format. Requiring the tail to be zero padding costs nothing and
  refuses an image that is provably not ours.

## Test coverage this round asks for

- [x] **The GPT regression test covers one case and the dangerous ones are the others.** The kernel
  test added by M0144 builds a GPT naming a LiberFS partition too small to use and proves the disk
  is left untouched. Nothing covers an MBR-partitioned disk, a foreign superfloppy at LBA 0, a
  corrupted GPT signature, a bad header CRC, a bad entry-array CRC, or a partition entry that
  overlaps the GPT metadata - and every one of those formats the disk today.

- [x] **A directory large enough to split, listed in order.** The regression above survived because
  every directory test fits in one leaf. A test with enough entries to force an internal node,
  asserting the listing is sorted, would have caught it and would catch the next one.

- [x] **Removing an unknown-type inode returns its blocks.** The existing test asserts the record
  goes away. It should assert the allocator gets the blocks back, which is what actually distinguishes
  the fix from the regression.

## What this audit does not say

Nothing here was reproduced at runtime; the audit was static and so was this verification. All ten
findings were checked against the code they name and every one held - as with the two rounds before
it, nothing was hallucinated.

The audit is also explicit that it could not run the tests - its environment could not reach GitHub -
and that it therefore treats M0144's test results as a claim by the repository rather than as its
own measurement. That is the correct posture and worth mirroring: the 128-test figure and the
watched-to-fail discipline behind it are recorded here as this repository's claim, and the three
regressions above are a fair reminder that a green suite bounds what was tested, not what is true.

## What was done

All thirteen. The eight LiberFS items are in `src/fs/liberfs`, the two probe items are a new crate,
and the three test items are the tests that make the difference between the fix and the regression
visible - each of them written to FAIL against the code as it stood.

### The probe is now a crate that answers a question about a disk

`gpt_liberfs_partition` is gone from StorageService; `src/fs/partition` is where the question lives
now. It reads through a `Sectors` trait, so the same code answers for a virtio-blk disk behind a
block service and for a map of sectors on the host - which is what makes twenty tests affordable
where six integration cases would have been the ceiling.

The vocabulary is the audit's, plus one the audit could not have known was needed:

| answer | what was found | what the service does |
|---|---|---|
| `Blank` | LBA 0 and LBA 1 both read, no table, no filesystem | format the whole device |
| `LiberFsWholeDevice` | our own superblock at LBA 0, no table | mount the whole device |
| `LiberFs { first, last }` | a verified GPT naming a usable LiberFS partition | mount inside the partition |
| `GptWithoutLiberFs` | a verified GPT that names no LiberFS partition | refuse, say so |
| `MbrWithoutLiberFs` | an MBR partition table, or a hybrid MBR | refuse, say so |
| `CorruptGpt` | a GPT signature or protective MBR, neither copy verifying | refuse, say so |
| `ForeignFilesystem { name }` | FAT / FAT32 / exFAT / NTFS laid at LBA 0 | refuse, name it |
| `Io` | the device did not answer | refuse, say so |

`LiberFsWholeDevice` is the one the audit's list would have got wrong, and it would have broken
every second boot: the fixed whole-device layout puts a LiberFS superblock at LBA 0 with no
partition table, which is *precisely the shape of a superfloppy*. Folding it into
`ForeignFilesystem` makes the service refuse to mount its own volume - which is not a guess, it is
what the suite did when that fold was tried deliberately. It stays a separate answer rather than
being merged back into `Blank` because only one of the two describes a disk with nothing on it, and
collapsing those is the mistake this whole milestone is about.

The GPT is verified rather than believed: the header CRC32 over its declared `header_size`, the
partition-entry-array CRC32 over exactly `num_entries * entry_size` bytes, `header_size` in range,
the primary and backup at different LBAs, a usable range that runs forwards, both copies of the
metadata and the entry array outside that range, checked arithmetic for the array's span, and every
LBA bounded by the device's real capacity - a device that will not report one bounds nothing, so the
table may not be acted on at all. A partition must then lie wholly inside the declared usable range
and overlap neither copy of the metadata. When the primary does not verify, the backup at the last
sector is consulted before anything is called damaged, which is what a backup is for.

The audit's own scenario - an entry with the LiberFS type GUID, `first = 1`, `last = 100000` - now
fails on the usable range, which is the check that does not depend on this build happening to know
where the tables are.

### Watched to fail, and four that were not

Every fix here was reverted and its test observed failing: eleven in LiberFS, thirteen separate
checks in the probe, three end-to-end in the kernel suite. Four of them did not fail on the first
attempt, and all four were the test's fault rather than the fix's:

- The unknown-type deletion test used `set_compression(false)` as a filler commit. That call returns
  early when the setting is already off, so no commit happened and the reclaim never advanced -
  the test measured a deletion that had not been reclaimed yet, in both arms.
- The shared-visited-map test broke the *first* snapshot's link, which is checked first whatever the
  map does. Two snapshots taken back to back - so they share a root block - with the SECOND record's
  CRC broken is the shape that needs the fix.
- Three of the probe's checks (the capacity bound, the entry-array dimensions, the usable range)
  passed because another check refused the same image first. Each needed an image where the check
  under test is the only thing that can object.

That is the whole value of the discipline: four tests that were green, that named a real property,
and that proved nothing.

### The two paths a host test could not reach

`derive_free`'s refused allocation and `check_dir_structure`'s were unreachable by construction: if
the machine can allocate the first free map it can allocate the second, so no choice of `num_blocks`
gets there. That is *why* one of them came to answer a refusal by returning silently and the other
by blaming the disk - nothing could run them.

`try_zeroed` now has a thread-local injection switch under `cfg(test)`, the same shape as the
kernel's per-CPU frame injector and for the same reason: `cargo test` runs tests in parallel, and a
global switch would inject into whichever test happened to be allocating. Both paths are now
ordinary tests.

### The host suites now run

`fs/liberfs` had 128 host tests and nothing ran them - not `test.sh`, not `check.sh`. A suite
nothing runs is a suite in name only, and it would have made the twenty new probe tests decorative
too. `./check.sh --gate host-tests` runs both crates' suites; the in-kernel suite answers what the
system does with these crates, and this answers what the crates do.

### Counts

- LiberFS host tests: 128 -> 137
- partition host tests: 0 -> 20
- kernel suite: 192 -> 195 (an MBR disk, a foreign superfloppy, and a whole-device volume remounted)
