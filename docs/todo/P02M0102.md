- [x] Specify one versioned byte-stream contract used by runtime stdio, pipelines and
  StorageService adapters: bounded chunks, blocking/backpressured write, readable/
  writable readiness, writer-close -> EOF, reader-close -> broken-pipe/cancellation and
  an idempotent explicit error close where ordinary EOF is insufficient. Define the
  maximum queued bytes/chunks and fair wake ordering; a slow or stopped stage cannot
  make another Domain allocate unbounded memory.
  Result (2026-07-31): `rt::stream`, and it deliberately adds almost no mechanism - the
  interesting finding is that a Channel already provides every property a pipe needs, each
  built for a different reason before pipelines existed. An endpoint's inbox is bounded at 64
  messages and a send past that reports Full, which is backpressure by depth. Every queued
  message is charged to the SENDER's Domain IPC quota until it is taken, which is backpressure
  by bytes and is precisely the requirement this item states - a slow stage cannot make another
  Domain allocate without bound, because the kernel already refuses to let it. And peer close
  is observable at both ends, which is EOF one way and broken pipe the other.
  So the contract is the convention on top: `MAX_CHUNK` of 4096 with the chunk AS the frame
  (re-framing a byte stream over an ordered message queue would buy nothing), and
  `MAX_IN_FLIGHT` stated as depth times chunk so a stalled pipeline's worst-case memory is a
  number rather than a property of whichever path ran. Building a second queue beside the
  kernel's would have meant two answers to "how much can a stalled pipeline hold", and only one
  of them is enforced by Domains.
  Three distinctions in the read result carry the weight. A zero-length message is neither data
  nor an end, and is skipped: treating it as the end lets an empty write truncate a stream.
  `End` (the writer closed) is separate from `Failed` (the writer reporting it could not
  finish), because a consumer that cannot tell them apart publishes a truncated result as a
  complete one - the exact failure the transactional writer exists to prevent, so the stream
  must not hide it. And `fail` sends non-blocking on purpose: a writer that is failing must not
  block behind a consumer that stopped reading, or a broken stage hangs instead of reporting.
  `Writer` closes on drop, so a stage that returns early cannot leave its consumer waiting for
  an EOF that never arrives - a hang rather than a finish. `Reader::close` is how an
  early-exiting consumer (`head` on a huge file) tells the stage upstream to stop.
  Not claimed: fair wake ordering, which is the scheduler's existing behaviour rather than
  something this contract sets, and versioning of the contract itself, which has no second
  version to be compatible with yet.
- [x] UNBLOCKED 2026-08-05: P02M0101's versioned launch context is built, so the endpoint work below
  extends it rather than inventing a second bootstrap format. What was blocking, and the blocker is written into this item's own
  text: it says this extends that context "instead of creating a second bootstrap format". That
  context does not exist yet - P02M0101's item for it is open - so building the endpoints first would
  create exactly the second format the sentence forbids. Checked 2026-08-05, before starting.

  Every other open item in this milestone is downstream of this one, so the whole of P02M0102 waits on
  one item in P02M0101. Worth knowing before picking this up expecting a self-contained piece of work.

  The size of that dependency, measured before starting and confirmed by doing it: `args` and `cwd`
  were bare bootstrap messages in 51 tools and both launchers. 41 tools now decode the context, 10
  only consume it, and 16 hand-written stagings in the kernel test suites had to learn the format.

  FOUND WHILE DOING IT, and older than the change that surfaced it: every net command typed at a
  shell prompt started a process that never answered.

  `ip`, `arp`, `ss`, `ping`, `nslookup`, `tcp`, `nc` and `httpd` have TWO launchers with two
  different shapes. The shell reaches them through `dispatch_net`, which opens a NetworkService
  client and hands it to `exec` as the one capability attached to the launch message.
  PermissionManager reaches the same programs through its grant loop, which sends the client under
  the `NETWORK` tag. Every one of the eight waited only for the tag, and nothing on the shell path
  ever sends one - confirmed by grepping every sender of that tag in the tree: there is exactly
  one, and it is the manager's grant loop.

  It predates the launch-context work. Before it, the tools discarded the attached handle with a
  `Received::Message { .. }` pattern and blocked on the same tagged receive; the context work only
  changed a silent leak into a closed handle. Neither hangs less.

  Why nobody noticed, which is the interesting part: `dispatch_net` is matched BEFORE the governed
  router, so the broken path is the only one a user can reach - while the working path is the one
  every test covers, because PermissionManager's startup demonstration runs `ip` that way and its
  output appears in the boot log. A tool that visibly works at boot and hangs when you type it.

  Fixed in `rt::granted_capability`: take the attached capability when there is one, wait for the
  tag when there is not. Written once rather than eight times, because the two-launcher shape is a
  property of the system rather than of any one tool.

  Pinned by a test that stages a net tool the way the SHELL stages one and asserts it queries the
  client it was handed. Written before the fix and watched to fail on the real symptom - the tool
  never asks - so the test is known to be measuring the thing it names.

  What the endpoint work inherits: a message whose shape is a schema record rather than a position
  in a run, a 64 KiB bound on it, and the rule that a capability rides the context MESSAGE while
  the context RECORD carries none. stdin, stdout and stderr are capabilities, so they belong on the
  message or under their own tags - never as fields.

- [x] Generalize the runtime launch context from the existing stdin/stdout channels to
  three explicit endpoints in P02M0101's versioned context: stdin (read), stdout (write) and
  stderr (write), each absent, terminal-backed, pipeline-backed or storage-backed by
  transferred capability. Preserve the current terminal behavior for ordinary launches,
  keep stdout and stderr separate by default, close inherited duplicates promptly and
  expose no numeric descriptor API, arbitrary endpoint lookup or ambient inheritance.
  Design constraint learned the hard way on 2026-08-01, before this item is built: an
  additional endpoint must ride in the SAME bootstrap message as stdout, as an ordered extra
  capability - NEVER as a following message. `inherit_stdout` was written to peek for an
  optional trailing `STDIN` message and take it when one was pending. A receiver cannot tell a
  message that was never sent from the NEXT handoff in the bootstrap sequence, so it swallowed
  the args of every launch that sends anything after STDOUT, shifting the whole sequence by one
  and leaving the program blocked forever. It broke `imgconv` at the plain `--help` call, which
  printed nothing and never exited, and no sender had even been written yet - the trailing
  message was speculative. Fixed by taking capability 0 as stdout and an optional capability 1
  as stdin from the one message, which is what the P02M0090 multi-capability work is for.

  DONE 2026-08-05, and the constraint above was reversed on purpose. It was right when written: a
  receiver could not tell an endpoint that was never sent from the next handoff in the sequence.
  The terminator removed that, and position brought a hole of its own the moment a third endpoint
  existed - `cmd 2> file &` is an output and an error stream with NO input between them, which an
  ordered list cannot express without a placeholder someone has to remember to send. The endpoints
  are now a named run ending at READY: `CAP_STDOUT`, `CAP_STDIN`, `CAP_STDERR`, each independently
  absent.

  `inherit_stdout` keeps its name and signature, so none of the fifty-four programs that call it
  changed - only what arrives on the channel did. Both launchers send the named run; nineteen
  hand-written stagings in the kernel suites learned to end it.

  Behaviour is preserved exactly where it should be. A terminal launch still sends one endpoint and
  the child reads and writes that same full-duplex console. A pipeline stage still gets a separate
  input. `eprint` falls back to stdout when no error stream arrives, which is every launch today.

  That fallback is why 143 diagnostics across 44 tools could move to `eprint` without changing one
  observable byte - and why doing so proves nothing on its own. The endpoint is pinned by a test
  that hands `cat` two distinct channels and asserts the diagnostic arrives on the error one while
  stdout stays empty; with `eprint` forced back to stdout that test fails on the missing message,
  so it measures the endpoint rather than the fallback.

  Only the tools' OWN `name: message` lines moved - the Unix diagnostic convention. Ordinary output
  never carries the program's name, so the rule picks out exactly the lines that belong on stderr.
- [x] Give the bootstrap handoff a length or a terminator, so changing its shape cannot silently
  shift it. Today it is an ordered run of tagged messages with nothing in front of it, and both
  ends carry the count implicitly - a list of `recv_tagged` calls in one file and a list of sends
  in another. Get them out of step and every later message is read as the wrong thing.
  This bit three times on 2026-08-01/02, in three places, and never where the mistake was:
  `inherit_stdout` peeked for a message nobody sent and swallowed a program's ARGUMENTS; two
  receives added to PermissionManager without matching sends made it report that NetworkService
  had not asked for a client; and growing the `volumes` bundle from five entries to seven left
  two behind in every governed tool, which then read them as its working directory - surfacing
  as "imgview did not acquire a surface", four steps from the change.
  A count sent first, or a sentinel ending the run, turns all three into an immediate local
  error. Worth doing before the pipeline work adds more handoffs: stdin, stderr and the
  redirection endpoints are all more messages in this same sequence.

  FINDING, 2026-08-05: the sentinel this item asks for is already built, proven, and in use -
  it just has almost no users. `rt::recv_caps` reads named capability messages up to a `READY`
  terminator (`rt::send_ready`) into a `CapSet`, and `CapSet::take(name)` pulls each one out BY
  NAME. That defeats all three historical bugs by construction rather than by detection: there
  is no ordering contract to get out of step with, a capability the parent withholds is simply
  not sent instead of being a placeholder someone must remember to send, `READY` bounds the run
  so reading past the end cannot swallow the next handoff, and `Drop` closes whatever the child
  never claimed, so a rename leaks nothing. Its tags are shared constants (`rt::CAP_*`), so a
  mistyped tag is a compile error rather than a capability that silently arrives as zero.

  So this is not a design task. It is a migration, and the count of what is left is the real
  content of this item: `recv_caps` is used by three files (`shell.rs`, `console_service.rs`,
  and rt itself), while the ordered `recv_tagged` run is used by fifty-seven.

  Where it hurts most, and where to start: `permission_manager.rs` takes twenty capabilities
  with `unwrap_or(0)`. That is deliberate - the manager cannot grant what it does not hold - but
  it makes a withheld capability and a drifted sequence the same event at the call site, which
  is exactly why bug two above surfaced as a claim about the wrong service. Migrating that one
  handoff removes the ambiguity outright, and its twenty-three messages make it the largest
  single instance of the pattern in the tree.

  Deliberately NOT doing the cheap alternative first. Teaching `recv_tagged` to tell a wrong tag
  from a withheld capability would make the ordered run diagnosable while leaving it fragile,
  and it would add a second mechanism to a path that should be shrinking. This tree has twice
  had to delete machinery that existed for no user; the fix here is to use what already works.

  MIGRATED, 2026-08-05: PermissionManager. All twenty-three capabilities are taken by name out of
  one `CapSet`, the supervisor ends its run with `send_ready`, and both ends name every tag
  through a shared `rt::CAP_*` constant, so a mistyped tag is now a compile error. The wire bytes
  are unchanged - only the mechanism moved, from position to name.

  It found a third sender immediately. `kernel/tests.rs` hand-writes this same handshake for the
  governed-tool scenario, and it ended at `SERVE` with no terminator; the migrated manager waited
  for a `READY` that never came and did nothing, which the harness reported as "PermissionManager
  did not request a fresh NetworkService client" - the identical misleading message this item
  records from 2026-08-01. That a hand-written third participant existed at all, unnoticed, is the
  argument for the change rather than against it.

  Verified by removing a send rather than by the suite passing. With `STORAGE_ISO` deliberately
  not sent from the middle of the run, 57 service-tagged tests still pass, including the governed
  pipeline: the capability reads as absent and nothing after it shifts. Under the ordered protocol
  that same omission is what shifted every later message and surfaced four steps away.

  Green on all three: x86_64 156, aarch64 148, riscv64 149.

  MIGRATED, 2026-08-05: the `volumes` bundle, which is where the third failure in this item
  happened. Twelve governed tools (`cat`, `du`, `ls`, `lsblk`, `lsvol`, `mkdir`, `rm`, `rmdir`,
  `write`, `imgconv`, `imgview`, `play`) each read seven volume clients in order, and each carried
  a hand-written drain of the two it had no use for, with a comment explaining that a message left
  behind would be consumed as whatever it read next - which for these tools is the working
  directory. They now take what they want by name and leave the rest to be closed by the set.

  Two things this turned up that the item did not know.

  The `let _ = recv_tagged(...)` drain discarded the handle WITHOUT closing it, so every governed
  tool leaked up to two capabilities per launch. `CapSet` closes what nobody claims, so the
  migration fixed a leak nobody was looking for.

  And the bundle has FOURTEEN senders: `grant_volumes`, plus thirteen hand-written stagings across
  `kernel/tests.rs` and `test_suites/dynamic.rs`, each spelling the sequence out again. Twelve
  receivers and fourteen senders, every one of them depending on the others positionally, is the
  whole argument for this change stated as a number. Adding the terminator to the real sender and
  not to the thirteen hand-written ones is what made `imgconv` hang: an unconsumed `READY` shifted
  its working directory, exactly the failure this item was opened about, reproduced by the fix for
  it. The one useful thing about that is where it surfaced - a timeout in the imgconv test rather
  than a wrong answer somewhere else - and how the fix converged: once every sender ends its run,
  no receiver can be shifted by one that does not.

  Verified the same way as the first migration - by breaking the sender, not by the suite passing.
  With `USB`, `RAM` and `TMP` all dropped from `cat`'s bundle, 22 dynamic-tagged tests still pass:
  `cat` gets its working directory and reads its file. Under the ordered protocol a bundle three
  short shifts every message after it.

  What is left, measured rather than estimated. Before these two migrations the ordered run had
  handshakes of twenty-three and of seven; now the longest is THREE (`process_service`,
  `graphics_probe`), thirteen files read two, and thirty-two read exactly one. A one-message
  handshake cannot drift, and a two- or three-message one ends in `SERVE`, which every service
  turns into a loud `fail_bootstrap` rather than a zero. The hazard scales with the length of the
  run, and the long runs are the ones that are gone.

  So this item is done, without every file having been converted. The remaining ones are worth
  migrating when they are next touched for other reasons - `rt::CAP_*` and `recv_caps` are there
  and proven - but converting a single-message handshake buys nothing, and the pipeline work this
  item was blocking can proceed: stdin, stderr and the redirection endpoints go into a bundle that
  now has a terminator. This one was migrated first because it is the
  largest and because it is where the ambiguity between "withheld" and "drifted" actually cost
  something.
- [x] Add a typed process-completion result before defining pipeline status: clean exit
  carries a bounded integer code, signal/fault/forced teardown carries a distinct reason,
  and waiting on a Process or ProcessGroup returns that immutable result after readiness.
  Today's Process handle exposes only terminated/killed readiness and `rt::exit()` has no
  status, so `pipefail`, per-stage diagnostics and success-gated publication must not infer
  success from mere closure. Preserve the first terminal cause and define group status
  over the ordered stage results without exposing ambient PIDs.
  Result (2026-07-31, partial - the per-process half): `SYS_USER_EXIT` took NO argument and
  discarded a0, so a process could finish and never say how. A waiter saw closure and nothing
  else, which makes a program that ran and refused indistinguishable from one that worked.
  The status is now latched on the Process and reported through `process_stats` as
  `completion` plus `completion_valid`.
  Two decisions worth recording. `exit()` keeps its signature and means status 0: there are 311
  call sites in the tree and success is nearly all of them, so making each write `exit(0)` would
  add no information to any of them; `exit_with(status)` is the explicit form. And the report
  carries a separate validity flag rather than letting 0 stand for both outcomes, because 0 is
  at once the commonest success and the natural "nothing here" - a process that faulted never
  got to report anything, and reading that as a successful zero is how a broken stage would
  report success.
  First writer wins, the same rule the recorded fault follows, so a multi-threaded process whose
  threads exit differently has one answer and it does not change under a reader.
  Validation is `a_clean_exit_reports_its_status`, four assertions each ruling out a different
  wrong implementation: nothing reported reads as `None` and not 0, a reported 42 reads back as
  42 (not merely "non-zero" - the value is asserted, so a stub returning 1 fails), a second exit
  does not overwrite the first, and a reported 0 reads as `Some(0)` rather than absent.
  The syscall's own line is deliberately NOT covered by that test, and the reason is a real
  constraint: `SYS_USER_EXIT` does not return - it longjmps to the kernel thread that entered
  ring 3 - so a kernel test thread calling it jumps to a stack that was never parked and
  double-faults, which is what the first version of the test did. It is covered instead by
  every process in every boot, since all 311 `exit()` calls now pass a status through it.
  Still open here: the group half - a group status defined over the ordered stage results -
  which waits on the pipeline itself rather than on this primitive.
- [x] Add a kernel `ProcessGroup` object (or an equally explicit capability object) that
  owns a bounded set of live process references and supports group wait plus capability-
  gated INT/TERM/KILL/STOP/CONT. Membership is fixed by the trusted launcher at spawn,
  cannot be joined by an untrusted process and is removed on exit. ConsoleService holds
  one MANAGE-scoped group capability for the foreground job, so Ctrl+C/Ctrl+Z/Ctrl+\
  affect every live pipeline stage and no unrelated process.
  Result (2026-07-31, the object and its syscalls; ConsoleService adoption follows with the
  shell work): `ProcessGroup` is object type 11, created over a set of Process handles by
  `SYS_PROCESS_GROUP_CREATE` and signalled by `SYS_PROCESS_GROUP_SIGNAL`, capped at 64 members.
  Three of its properties are refusals of Unix behaviour rather than omissions, and each is
  worth stating because the Unix shape is what a reader will expect.
  Membership is SEALED at creation. A Unix process group can be joined with `setpgid`, which is
  how a process escapes the group its parent placed it in; there is no reason a pipeline stage
  should be able to leave the job it belongs to, and sealing it makes "which processes does this
  signal reach" answerable from the handle alone.
  Members are held WEAKLY, so a group never keeps a dead process alive. Owning them strongly
  would pin every stage for as long as the job table holds the group, and the point of the
  object is to reach processes that are still running.
  Authority comes from the HANDLE, not from membership: signalling needs the group capability
  with MANAGE, and being in the group grants nothing, so one stage cannot signal its siblings.
  That is precisely the confused-deputy shape Unix has, where any member may `kill(0, sig)` the
  rest. Creation requires MANAGE on each member for the same reason - a group cannot be
  assembled out of processes the caller could not already signal one at a time.
  Two smaller decisions. The per-process and per-group paths share one `deliver_signal`, so a
  group cannot drift from what signalling a member directly does. And a group signal continues
  through every live member even after one fails, because a partially interrupted pipeline is
  worse than either outcome - the stages that received it exit while the rest run on with their
  peers gone.
  Validation is `a_process_group_reaches_every_member`. The assertion that carries it is that
  ONE dead stage does not finish the job: without it an implementation reporting finished as
  soon as any member ended would pass. It also asserts that dropped members leave the live set
  (proving the references are weak), and that an empty group and one past the cap are REFUSED
  rather than truncated - a group missing a stage would signal an incomplete job with nothing
  to say so.
- [x] Extend SessionService jobs from one Process handle to one job handle representing
  either a single process or ProcessGroup, plus the ordered display command and aggregate
  running/stopped/completed state. `&`, `jobs`, `fg`, `bg`, shell restart and completion
  reaping work identically for single commands and pipelines; a partially exited group
  remains a job until every stage is reaped, and all handles close on session teardown.
  Done 2026-08-01. `job-info` carries a `group` flag and `job-register` takes it, because a
  ProcessGroup and a Process are driven by DIFFERENT syscalls: sending the process signal to a
  group handle is refused, which would leave a pipeline stopped forever while the session
  believed it had resumed it. The shell registers through `register` or `register_group`,
  split rather than defaulted, because passing the wrong kind produces a job that can never be
  resumed or reaped and no error at the point of the mistake.
  A background pipeline is ONE job labelled `echo | readln`, so `jobs`, `fg` and completion
  reaping treat it exactly like a background command.
  This exposed a real kernel gap, not just plumbing: `wait` recognised Channel, Event, Timer,
  Interrupt and Process but NOT ProcessGroup, so a group handle was never ready. A session
  polls a job's handle to notice completion, so a pipeline job would have stayed in the table
  for the life of the session - a leak that shows up as a stuck `jobs` entry rather than a
  crash, which is why it needed a test rather than a reading.
  `a_group_handle_becomes_waitable_only_once_every_stage_ends` pins three states, and the
  middle one carries the weight: a group with SOME stages ended is still not ready. An
  implementation reporting ready on the first exit passes an all-dead check while announcing a
  pipeline finished with a stage still producing. The probe waits with a finite deadline, so a
  regression times out instead of parking a thread forever and taking the suite with it.
  Verified: full x86_64 suite 152 passed.
- [x] Replace line-prefix dispatch with a bounded lexer/parser that produces an explicit
  command/pipeline/redirection AST while preserving existing variable expansion and
  canonical option normalization. Recognize operators only outside quoted/escaped text,
  lex operators before variable expansion and never reinterpret expanded data as syntax,
  reject empty stages, duplicate/conflicting redirects, unsupported descriptor numbers,
  dangling operators, excessive stages/arguments/expanded bytes and recursive expansion
  before any file is opened or process spawned. Keep assignment/session-state builtins
  explicit rather than accidentally applying them in a child pipeline context.
  Result (2026-07-31, the parser; wiring the shell to it comes with the pipeline transaction):
  `shell_language::parse_pipeline` turns a raw line into stages, each with its own ordered
  redirections. The ORDER OF OPERATIONS is the security property here and it is why this is a
  lexer rather than a few splits.
  Today's shell calls `parse_and_expand` FIRST and routes the result, which is safe only
  because no operator exists yet. The moment `|` means something, expanding first turns a
  variable's contents into structure: `FOO='| rm x'; echo $FOO` would build a pipeline out of
  data. Operators are therefore found on the RAW line and an expanded value is never lexed
  again - the fix is not to escape the data but never to look at it as syntax, which is the
  bug every shell that got this wrong shares.
  Quoting is part of lexing for the same reason: an operator inside quotes is a literal, so
  `echo "a | b"` is one argument. If quoting were applied after operators were found, the split
  would already have happened.
  The test that carries this asserts the property directly, with operator characters arriving
  from variables in each position that matters - a pipe that must not create a stage, a
  redirect that must not name a file, an ampersand that must not background the job. A parser
  that expanded first would pass every other test in the file and fail these three.
  Bounds refuse rather than trim (8 stages, 64 words per stage, 4096 bytes), because a
  truncated pipeline is a different command from the one that was typed, and every refusal
  happens before a caller could open a file or launch a stage - which is the point of parsing
  separately from running. `3>&1` is refused as an unsupported descriptor rather than guessed
  at, and a leading digit is a descriptor ONLY when it introduces a redirect, so `file2` and
  `2x` stay ordinary words.
  Validation is five host tests beside the existing expansion ones, 23 passing in
  `just services-host-test` - host-side, so the fuzzing this item's sibling asks for has
  somewhere fast to run.
- [x] Initial shell grammar: `A | B`, `< path`, `> path`, `>> path`, `2> path`,
  `2>> path` and `2>&1`, with left-to-right redirection ordering documented and tested.
  Compound shell language, command substitution, here-documents, arbitrary `N>&M`, shell
  scripts and POSIX descriptor emulation remain out of scope. A state-mutating builtin
  such as `cd`, assignment, `unset`, `fg` or `bg` is rejected as a pipeline stage; simple
  parent-shell use retains today's persistent SessionService semantics.
  Done 2026-08-01. `shell_language::parse_pipeline` covers every form above with 24 host tests,
  and redirections keep their written order because `> a > b` and `2>&1 > f` differ by it.
  Operators are lexed on the RAW line and expanded text is never re-lexed, so a variable
  holding `|` or `>` cannot inject structure. `3>&1` is refused as `UnsupportedDescriptor`
  rather than quietly treated as something else.
  The builtin rule landed here too, slightly wider than written and deliberately so: `cd`,
  `unset`, `export`, `fg`, `bg` and shape-recognised assignments are refused not only as a
  pipeline stage but also when backgrounded or redirected. All three run the builtin somewhere
  whose state is discarded, so `cd /tmp | grep x` would leave the directory unchanged while
  reporting success - refusing is the only honest answer, and one condition covers all three.
  Boundary cases are pinned: `cmd --opt=v` is not an assignment, `=leading` is not one either,
  and `cdrom` is not `cd`.
  NOT wired: the shell still parses with `parse_and_expand`, so none of this is reachable from
  a prompt yet - that is the pipeline-transaction and edge-wiring items below. User-facing
  documentation of the grammar is deliberately deferred until it IS reachable, because
  documenting syntax a user cannot type yet would be a promise the shell does not keep.
- [x] Build a pipeline transaction in the trusted shell/launch broker: parse and resolve
  every executable/path, authorize every stage independently, allocate all stream pairs
  and redirection adapters, create the process group, then create every stage behind an
  explicit start gate (a suspended-launch or equivalent ProcessService primitive), install
  all endpoints, register the complete graph and release the stages together. The current
  launch starts immediately, so this gate is a required mechanism, not an assumed ordering.
  Note on that last sentence (2026-07-31): it is true of the ProcessService API and NOT of the
  kernel, which changes the size of this item. `SYS_THREAD_CREATE` and `SYS_THREAD_START` have
  always been separate capability-gated steps; every launch path simply called them back to
  back, so the gate existed and nothing exposed it. It is exposed now as `rt::process_prepare`
  / `rt::process_release`, with `prepare_with_object` / `start_thread` as the kernel-side twin,
  each split OUT of the combined call rather than added beside it so the two cannot drift in

  AND A SECOND, FOUND WHILE WIRING THE REFUSALS: a line the grammar refused was RUN AS AN ORDINARY
  COMMAND. Every parse failure fell through to `dispatch`, which knows nothing about operators, so

  an unterminated quote is most often an apostrophe in ordinary text (`echo it's fine`), where

  THE CAPABILITY CLAIMS, and which layer each is checked at.
  `a stage cannot signal its group without MANAGE` is pinned in the kernel, against the handle
  rather than against the absence of one: a group handle holding READ|WAIT is refused by

  MANAGE stops all three. Asserted in that order on purpose - the refusal is checked while nothing

  of the assertions. This also guards the fallback that taught the process-signal syscall to take a
  group: the thing a widening bug would do is exactly what this refuses.

## Reopened: a group's member list is its ABI identity, and two paths compact it

An outside audit of the ABI surface, 2026-08-15, against this tree. Five findings, all checked
against the code before being written here, and all five are true as stated. The audit's framing is
the right one: the position of a member in a `ProcessGroup` is not an implementation detail, it is
what `SYS_PROCESS_GROUP_STATS` promises - "per-member `ProcessStats` in the order the processes were
created into the group" - so any function that renumbers the list breaks the contract.

- [x] **`live()` and `live_into()` compact `members` in place, and `records` is indexed by the
  position they change.** `object/process_group/mod.rs:153` and `:167` both open with
  `guard.retain(|member| member.strong_count() > 0)` - a MUTATION of the member list, from two
  functions whose names suggest a read. `records` is sized once at `create` (`original_size`) and is
  never compacted. `record_member` (`:125`) then finds the process's position in the CURRENT member
  list and writes `records[position]`.

  So the two collections agree only until the first member is dropped. After that:

      members: [A, B, C]  records: [-, -, -]      A exits, records[0] = A
      A dropped, anything calls live_into()
      members: [B, C]     records: [A, -, -]
      B exits: position(B) == 0, records[0] is already Some -> B's record is NEVER WRITTEN
      stats:  index 1 -> live[1] = C reported as stage B; index 2 -> "running" for a stage that is gone

  `sys_process_group_stats` (`syscall/mod.rs:1706-1709`) reads `group.records()` and then
  `group.live_into(&mut members)` and joins them BY INDEX, which is exactly the pairing that has come
  apart.

  **It is not confined to the diagnostic syscall, and that is what makes it a defect rather than a
  wrong answer in a report.** `finished()` (`:185`) - the condition a group wait completes on - calls
  `live_into`, so an ordinary pipeline that waits on its job compacts its own member list mid-run.
  The lost record is permanent: nothing re-runs `record_member` for a stage that already returned.

  The fix is to stop having two collections indexed by one number. One slot per stage, holding the
  koid, the `Weak<Process>` and the `Option<StageRecord>` together, never moved and never removed -
  `MAX_GROUP_MEMBERS` is 64, so tombstones cost less than the renumbering does. `live_into` then
  skips dead slots without renumbering the living ones, and a `snapshot_into(&mut [ProcessStats])`
  fills the caller's buffer in creation order from ONE pass under ONE lock, rather than joining two
  independent snapshots taken a moment apart.

- [x] **Write the mixed-state test, because the existing one cannot fail.** The persistent-records
  test ends all three stages BEFORE dropping any strong reference, so every record is written while
  the member list is still full - the one ordering in which the defect above is invisible. The test
  that catches it is the interleaved one: end stage A, drop it, call `finished()` (or anything else
  that reaches `live_into`), end stage B, and require `records[1]` to be B's. Watch it fail against
  the current code first; the point of this milestone's own harness work is that a test written after
  a fix proves nothing until it has been seen red.

- [x] **One group can hold the same Process twice.** `ProcessGroup::create` takes `&[Arc<Process>]`
  and downgrades each one without comparing them, and `sys_process_group_create` resolves handles
  without checking that two of them do not name the same object - which two capabilities to one
  process routinely do. The duplicate is not harmless: `record_member` matches by koid and always
  finds the FIRST slot, so the second never gets a record and reads as permanently running; the
  process also takes the same group back-link twice and is signalled twice by one group signal.
  Refuse a repeated koid at creation with `ERR_INVALID` - a group whose stages are not distinct
  cannot mean what a pipeline needs it to mean.

- [x] **Two infallible `Vec::clone()`s on ring-3-reachable paths, in files the allocation gate
  scans.** `ProcessGroup::records()` is `self.records.lock().clone()` (`:146`), on the
  `SYS_PROCESS_GROUP_STATS` path; `Process::record_in_groups()` is
  `self.groups.lock().clone()` (`process/mod.rs:468`), on every process teardown - which is a path
  that runs when memory has already run out. Neither can refuse.

  The gate is the more important half of this. `src/tools/check-kernel-allocations.sh` matches
  `Vec::with_capacity`, `vec![..]`, `Box::new`, `Arc::new`, `String::from`, `format!`, `to_string`
  and the collection-growth forms - and `.clone()` on a heap-backed type is in none of them, which is
  why both of these sit in scanned files and were never flagged. Add `.clone()` / `.to_vec()` for
  heap-backed receivers to the gate, and expect it to find more than these two: that is what happened
  the last three times the gate's vocabulary was widened, and it is recorded in P02M0133 each time.

  The call sites then answer it the way the rest of the kernel does - `records_into(&mut [..])`
  filling storage the syscall already has, and `record_in_groups` iterating under the lock or into a
  fixed buffer, since `MAX_GROUP_MEMBERS` bounds both.

- [x] **Group back-links are never removed, and `create` is not transactional.** `join_group`
  (`process/mod.rs:451`) pushes a `Weak<ProcessGroup>` and nothing ever removes it, so a process that
  outlives several groups walks a list of dead links on every terminal path. Worse, `create`
  (`process_group/mod.rs:105-116`) returns `None` on the first `join_group` that fails and leaves the
  back-links it already installed on the earlier members - a group that does not exist, still
  referenced by half its intended stages. Drop dead links before pushing a new one, and unwind the
  installed back-links on a failed creation, so a refused group leaves nothing behind.

### Closed 2026-08-16: one slot per stage, and the gate that could not see the clone

All five findings were real as written, and the first one was reproduced before it was fixed.

**THE TEST WAS WRITTEN FIRST AND WATCHED TO FAIL.**
`kernel.object.a_stages_slot_survives_an_earlier_stage_being_dropped` ends stage A, drops it, calls
`finished()` - the condition an ordinary group wait completes on, so an ordinary pipeline reaches it
- and then ends stage B. Against the old code it failed at `stage B finished and was recorded`,
which is the exact mechanism the audit predicted: `position(B)` was 0 after the compaction, slot 0
already held A's record, and B's record was therefore never written at all. Not a wrong number in a
report - a record silently discarded.

**ONE COLLECTION, NOT TWO INDEXED BY THE SAME NUMBER.** `members` and `records` are now
`slots: Vec<MemberSlot>`, each holding the koid, the `Weak<Process>` and the `Option<StageRecord>`
together. Slots are never moved and never removed, so a position means the same stage for the life
of the group; `live_into` skips dead slots without renumbering the living ones and no longer mutates
anything, which is what its name always claimed. At `MAX_GROUP_MEMBERS` = 64 a tombstone is cheaper
than the renumbering was.

`record_member` finds its slot by the koid held IN the slot rather than by upgrading each weak
reference and asking - so a stage is still findable after its last strong reference is gone, which
is precisely the state the record exists for.

**`SYS_PROCESS_GROUP_STATS` IS ONE PASS UNDER ONE LOCK.** It read the records and the live members
as two independent snapshots and joined them by index. Even with the compaction gone that is two
reads of a group that can change between them, so `snapshot_into` fills the caller's array from the
slots directly, in creation order, and the syscall writes it out. The `[ProcessStats; 64]` it fills
is the caller's own storage, as every other bounded kernel path here does it.

**A REPEATED MEMBER IS REFUSED.** `create` compares koids pairwise - quadratic over a list bounded
at 64 - and returns `None`, which the syscall reports as `ERR_INVALID`. The audit's reasoning is
what makes refusal right rather than deduplication: a group whose stages are not distinct cannot
mean what a pipeline needs it to mean, and silently collapsing two stages into one would make the
group's size disagree with the line somebody typed.

**THE BACK-LINKS ARE PRUNED AND `create` UNWINDS.** `join_group` drops dead links before pushing, so
a long-lived process joined to a succession of short-lived groups no longer walks all of them on
every terminal path; `leave_group` is new, and `create` calls it on every member it already linked
when a later `join_group` fails - so a refused creation leaves nothing behind pointing at a group
that never existed.

**THE ALLOCATION GATE NOW SEES THE FORMS THAT HID THESE.** `check-kernel-allocations.sh` gained
`.to_vec()` / `.to_owned()` unconditionally, `.clone()` taken out of a lock guard, and `.clone()`
bound to a `let` whose type is spelled as a collection. The gate's self-test refuses each of those
five forms and accepts a plain `Arc` clone, so the rule is proven to say no before it is allowed to
say yes.

Widening it found a third defect immediately, which is what the audit predicted: `boot_log_text`
answered `SYS_CONSOLE_READLOG` with `sink.as_bytes().to_vec()` - a second infallible copy of the
whole boot scrollback, on a syscall path, of bytes the sink already owned. `TextSink::into_bytes`
hands them over instead. What the gate still cannot catch is stated in its own header rather than
left for the next audit: a bare `x.clone()` on a collection FIELD, because `thread.clone()` and
`self.free.clone()` are the same text and differ only in a type that is not on the line.

It also found a PRE-EXISTING RED GATE, unrelated to this milestone and true at HEAD:
`enqueue_on`'s `run_queue.push_back` was flagged while the identical push at the bottom of
`sched/mod.rs` was not. The marker explaining it sat in the comment block ABOVE `fn`, and the gate
reads only the block that begins inside the function. Same marker, moved inside.

**Verified**: x86_64 `kernel,memory,component,service` green, the five group tests
(`a_stages_slot_survives_an_earlier_stage_being_dropped`,
`a_group_remembers_what_each_stage_finished_as_after_the_stage_is_gone`,
`a_process_group_reaches_every_member`, `a_group_handle_becomes_waitable_only_once_every_stage_ends`,
`signalling_a_job_reaches_a_group_the_same_way_it_reaches_a_process`) green, and
`./check.sh --gate kernel-allocations` clean with the widened rules.

ONE THING THE NEW TEST COST, recorded because it is a property of this suite rather than of this
change: written without cleanup, it left its third stage RUNNING - a process that never exits, in a
boot that runs 268 tests - and 170 tests later
`kernel.services.process_service_lists_every_started_program` reported one started program where two
had started. The two tests pass together in isolation and the production fix passes the full run
without the new test, which is how the test rather than the change was identified as the cause. It
terminates its last stage now. A kernel test that leaves a live process behind is a cost every later
test in the same boot pays.

## Fourth audit (2026-08-16): `AI/audit/idl.md`

Six findings, two High. Both High ones are about this milestone's own transaction: what a prepared
launch is, and what "starts none of them" means.

- [~] **A prepared launch is keyed by a public KOID and protected by nothing (IDL-001, High).**
  VERIFIED ON BOTH SIDES. The schema is `@op(7) release: func(koid: koid) -> result<bool, error>`,
  and ProcessService keeps ONE service-wide `prepared: Vec<(u64, Spawned)>` that `release` searches
  by koid. A KOID is not a secret - `process.list` returns them - so any client of the shared
  service can release another client's prepared launch. There is no cancel, no lease, and no
  disconnect cleanup, and PermissionManager has several early returns that close `started.task`
  without telling ProcessService, leaving the process loaded and stopped forever. The schema's
  stated reason for keeping the token inside the service - "a reply carries one handle and a
  prepared launch would need two" - IS NO LONGER TRUE: `abi::MAX_MESSAGE_CAPS` is 4. Return a
  move-only token that `release` and a new `cancel` consume, and make peer closure the abandonment
  signal.
- [x] **`run-pipeline` promises all-or-none and commits one stage at a time (IDL-002, High).**
  VERIFIED, AND THE IMPLEMENTATION ALREADY SAYS SO IN ITS OWN COMMENT: "Past the first release the
  transaction can no longer be unwound cleanly: stages already running are told to stop rather than
  left orphaned." A stage that has run may have written, sent or printed before `SIG_KILL` reaches
  it, so "a failure at any stage starts none of them" is false exactly when it matters. This cannot
  be repaired inside PermissionManager: the schema has no primitive that validates every token and
  then makes the group runnable in one transition. Add one, or stop making the guarantee.

  RESOLVED by adding the primitive. `process.release-group` (op 8) takes the whole list of prepared
  koids and validates every one of them - prepared, owned by this client, and named once - before
  queueing any thread; a list it cannot use is refused with nothing started. `run-pipeline` commits
  through it in one call instead of releasing koid by koid, so the loop that answered a mid-commit
  refusal by sending `SIG_KILL` to the stages already running is gone, and with it the case where
  "starts none of them" was false. The schema comment now names the primitive the guarantee rests on
  rather than asserting the guarantee. `just gen-check` is clean and the twelve permission and
  pipeline tests pass against the one-transition commit.

  OUTSTANDING - a regression at the wire boundary. The end-to-end path is covered by those twelve,
  but the property this change is about - a refused group leaves every token still prepared, so a
  second release can still start them all - needs a test driving `launch-prepared` and
  `release-group` directly, and the kernel suite has no harness for a prepared launch today. One was
  written; the service returned no reply for op 6 with that encoding. Rather than leave a failing
  test in the tree it was removed, and building that harness is its own piece of work.
- [x] **`handle<task>` names both a Process and a ProcessGroup (IDL-003).** `pipeline-result.group`
  and the session store both carry either object under one resource type with a separate boolean to
  say which, so the wire type cannot prevent a mismatched pair.

  RESOLVED by removing the pair. `process.task-group` is a resource of its own and
  `pipeline-result.group` now has it, but the type alone would have changed nothing: `Type::Handle(_)`
  discards the resource name in codegen, so every handle in every package is a bare `u64` and `task`
  and `file` are already indistinguishable in Rust. What the finding actually names is a handle
  travelling beside a boolean that says what it is, and the fix for that is a tag inside the value.
  `job-target` is a variant of `process(handle<task>)` and `group(handle<task-group>)`; `job-entry`
  carries one instead of a handle, and `job-register` takes one instead of `group: bool` plus
  `proc`. A mismatched pair is now unrepresentable rather than merely discouraged - on the wire and
  in SessionService's own table, which held the same pair and now holds the same variant.

  `job-info.group` stays. That record travels without a handle: it is the session's own answer to
  "what am I holding", read by `jobs` for display, and it is now computed from the tag rather than
  stored beside it, so it cannot drift. Removing it would have been a different change.

  The ABI check refused the retyping as breaking and asked for `--accept-breaking`, which is what
  `just gen-accept-breaking` is for and what a pre-release schema change is. `just gen-check` is
  clean afterwards, the twelve permission and pipeline tests pass, and the only caller of
  `job_register` - the shell - hands over a tagged target.

  NOT COVERED: the job table has no guest test, before this change or after. Registering,
  foregrounding and reaping a job are exercised only by using the shell.
- [ ] **No schema uses `@rights`, and `buffer` proves nothing about the object behind it
  (IDL-004).** The same gap `AI/audit/wire.md` reports as WIRE-002 and `AI/audit/drivers.md` as
  DRV-003, seen from the schema: authority is documented in prose and enforced by whoever remembers.
- [~] **Lists and strings have no declarable length, item count or byte budget (IDL-005), and the

### IDL-006 closed, IDL-001 halved, and the rest priced (2026-08-18)

**IDL-006 is done.** The shared `error` enum carried five variants and could express none of the
distinctions the rest of the tree had already grown: `timed-out` (the request MAY have been acted on,
which is exactly what `again` cannot say), `unsupported`, `exhausted`, `no-space`, `io`, `corrupt`,
`cancelled` and `commit-uncertain`. `fs/core` had grown `NoMemory`, `TooLarge` and `CommitUncertain`
for these and the protocol could not carry them across. All eight added and the sixteen protocol
crates regenerated. Adding enum cases is a breaking ABI delta, taken with `--accept-breaking`, which
is the intended pre-release path while nothing is versioned.

The one exhaustive match over the enum stopped the build exactly where its comment promised it would
- "at the one place that decides" - and the decision is recorded there: none of the eight is a
refusal, because each is a statement about the host, the medium or the operation and not about
whether the guest was ALLOWED. `Unsupported` is the closest call and still falls that way.

**IDL-001's security half is closed without touching the schema.** A prepared launch was keyed by
koid alone, and a koid is not a secret - `process.list` returns them - so any client of the shared
service could release, and therefore START, another client's prepared launch. `serve_multi` already
passes the channel a request arrived on and `process_service` was discarding it with `|_chan, ...|`.
Prepared entries are now keyed by (owner channel, koid) and `release` matches both; a client naming a
koid it does not own gets the same answer as one naming a koid that does not exist, which is the
truth from where it stands and gives away nothing about whether the koid is real.

MARKED PARTIAL, not done, because two halves remain and both need the schema: a move-only token that
`release` and a new `cancel` consume, and peer closure as the abandonment signal. The audit's own
note that the schema's stated reason for keeping the token inside the service is no longer true
(`abi::MAX_MESSAGE_CAPS` is 4) still stands and is the right fix.

**The remaining four are language or schema work, priced rather than started.** IDL-002 the audit
itself says cannot be repaired inside PermissionManager - the schema has no primitive that validates
every token and commits them together, so all-or-none needs one. IDL-003 needs `handle<task>` split
into distinct resource types, rippling through `pipeline-result`, the session store and both
services. IDL-004 (`@rights`) and IDL-005 (declarable list and string bounds) are LSIDL language
features: `reject_anns_except` accepts only `op`, `since` and `deprecated` today, so both mean parser,
AST, validator and codegen changes plus applying the annotations across sixteen schemas. IDL-005 is
marked partial because IDL-006, the half of it this milestone could close, is closed.

Measured: x86_64 `process,service,shell,lico,component` 136/136 and all 67 host suites.
