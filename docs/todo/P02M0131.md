# P02M0131 - What LiberMemFS's capacity actually bounds

Status: PLANNED. An outside audit of `src/fs/libermemfs` against the shared `fs/core` contract, the
generated `Storage` ABI and the StorageService paths around it, 2026-08-10. Every claim checked
against the tree held; the first one is larger than the audit stated and is written up at its
measured size.

Six rounds of review have already been through this crate and it shows. Reads and listings allocate
fallibly; a failed write leaves the previous contents intact; a rewrite reuses the existing buffer;
`allocated()` counts high-water capacity rather than `len`, which is what closed the grow-and-shrink
hole; the stream is charged to the volume while it is still arriving and can be received straight
into the destination buffer; path parsing is bounded before the UTF-8 pass and allocates nothing;
lookup is a binary search; and there is an OOM allocator and a ten-thousand-operation invariant test.

What has not settled is the memory model, and the reason is one sentence the implementation is
trying to hold in two halves: **the capacity is a bound on memory actually held, AND the allocator's
own structures are outside it.** Every finding below is somewhere those two halves meet.

## The accounting hole, measured

- [ ] **A directory's `Children` vector is never charged, and its capacity survives the entries.**
  `allocated()` sums `data.capacity()` for files and recurses into directories; `names()` sums
  `name.len()`. Neither counts `children.capacity()`. `insert` grows the vector through
  `try_reserve(1)` and `remove` calls `Vec::remove`, which never shrinks it - so a directory that
  held four thousand entries and now holds none still owns the backing store for four thousand
  `(String, Node)` slots, and `footprint()`, `free()` and `reservation_intact()` all report it as
  absent.

  MAX_ENTRIES bounds LIVE nodes, not the historical capacity of the vectors that held them. Empty
  the directory, leave it, create another, repeat. Measured on this tree's types:
  `(String, Node)` is **56 bytes**; one directory grown to 4096 and emptied retains **224 kB**; the
  full sequence the audit describes retains 8,382,465 slots - **447 MB** - none of it visible to any
  accounting the volume has, and reachable through the ordinary public `remove`.

  `docs/LIBERMEMFS.md` states that uncharged per-entry overhead "is a fixed implementation-defined
  cost already bounded by `MAX_ENTRIES`, so the worst case is a few hundred kilobytes whatever the
  capacity". That is exactly right for entries that EXIST and wrong for capacity that was kept, and
  the difference is three orders of magnitude.

  Charge `children.capacity() * size_of::<(String, Node)>()` to a metadata budget, and give the
  empty case back: a directory that reaches zero entries can drop its backing store by assignment to
  `Vec::new()`, which allocates nothing and cannot fail. The general answer is the arena the
  documentation already names as the endpoint.

## What `Reserved` can actually promise

- [ ] **The reservation guarantees a byte total, not the allocation the write needs.** Files are
  monolithic `Vec<u8>`, so growing one calls `try_reserve_exact` and the allocator may need the old
  block and the new block live at the same time - which this crate's own test
  `growing_past_a_files_high_water_mark_needs_both_blocks` exists to pin. A 64 MiB reserved volume
  holding a 32 MiB file that grows to 48 MiB ends within capacity and can still fail at the peak,
  and releasing the reservation first does not help: the old block is still there.

  `reservation_intact` compares a SUM - `reserved == capacity - footprint` - so a reservation held
  as several chunks satisfies it while no single contiguous run large enough for the next file
  exists. "Intact" currently means the arithmetic is right, not that the promise can be kept.

  The honest interim fix is to say so: the reservation bounds the volume's total and does not
  guarantee any particular allocation will succeed. The real fix is the arena, or chunked file
  storage where growth never needs a new monolithic block - and that is a design task, not a patch.

- [ ] **`Reserved` reserves the data and not the metadata that must accompany it.** A volume of
  exactly C reserves C, and storing C bytes of files also needs their names, their nodes and their
  directory slots. On a heap with no slack the mount succeeds and the first write fails on a
  directory slot the reservation never covered. If `Reserved` is meant to be a hard promise it has
  to reserve everything the volume will allocate; if it is not, the documentation should stop using
  the word guarantee.

## Preflights that disagree with the operations they precede

- [ ] **`Ok(0)` is returned where the path cannot be written at all.** For a new file
  `writable_len` answers `free.saturating_sub(name)`, so a volume with 1 free byte and a 5-byte name
  answers `Ok(0)`; StorageService turns that into `WritePlan::Allowed { max_len: Some(0) }`, whose
  documented meaning is that the path MAY be written, and the write then fails with `NoSpace`
  because the name alone does not fit. `Ok(0)` must mean "an empty file can be created here";
  anything less is `Err(NoSpace)`.

- [ ] **The two preflights disagree with each other at `MAX_ENTRIES`.** `writable_len` returns
  `Err(NoSpace)` when the entry count is full; `stream_len` returns `Ok(0)`; `stream_begin` then
  returns `Err(NoSpace)`. Three answers to one question, in one file. Make them one answer.

- [ ] **`stream_len` forgets the pending path when the file already exists.** The new-file arm
  subtracts the WHOLE path and carries a comment explaining precisely why - `stream_begin` charges
  `path.len()` and keeps the whole path in the pending state, "the two numbers have to be the same
  number". The existing-file arm is `Ok(free.min(MAX_FILE_BYTES))`, and `stream_begin` allocates the
  pending path for a replace exactly as it does for a create. On a volume with 1000 bytes where
  `abc` and its name occupy 903, the preflight promises 97 and the stream can take 94. This is
  deterministic, not an allocator edge, and the test that pins the property covers the nested-create
  case and not the replace.

- [ ] **A new stream can take everything it was promised and fail in `stream_commit`.** The preflight
  allows roughly `capacity - path.len()`, and the pending state then holds the path plus that data -
  the whole capacity. `stream_commit` moves the pending out of `self`, so it stops counting, but the
  bytes are still there in local variables while `write_file_owned_unsynced` allocates a fresh
  `String` for the final name and possibly grows the parent's `Children`. On a tight heap the
  transfer accepts one hundred per cent of what it was promised and the commit fails on metadata.
  Prepare the destination's metadata in `stream_begin` and MOVE it at commit.

- [ ] **`write_file` has no post-allocation check, and the streaming path has one.**
  `stream_spare` re-checks `footprint() > capacity` after `try_reserve_exact` and aborts on an
  overshoot, with a comment saying the allocator "promises at least what was asked for and may give
  more... Undo an overshoot rather than leave the volume over its own capacity". `write_file`
  computes its bound before `store()` and never looks again, so a generous allocator can leave a
  successful write with `footprint() > capacity`. For a new file the result's capacity can be
  checked before insertion; for in-place growth the rollback is harder, which is another place the
  monolithic `Vec` is doing the arguing.

## Semantics that differ from the rest of the filesystem stack

- [ ] **Two writable backends enforce two different name policies.** `fs::core::FsError::BadName`
  documents a malformed name as "an empty segment, `.` or `..`, not UTF-8, or a byte outside the
  portable-name policy". LiberFS's `validate_name_segment` enforces all four. LiberMemFS's
  `segments()` enforces two: it rejects `.` and `..` and non-UTF-8, has no portable-byte check at
  all, and DELIBERATELY tolerates empty segments so `/a/b/`, `a//b` and `a/b` name one thing.

  It matters because StorageService mounts LiberMemFS as the live `vol://system` (as well as
  `vol://ram` reserved and `vol://tmp` capped), so the same application creates `foo:bar` on a live
  system and cannot create it on an installed LiberFS one. One validator in `fs/core`, used by every
  writable backend; and separator normalisation decided at one layer rather than per filesystem.

- [ ] **Directories report their subtree's size where the ABI says zero.** `list_entries` fills
  `Entry.size` from `node.bytes()`, which for a directory sums everything under it, and the
  generated `Storage` documentation says plainly that "a directory reports a length of zero". The
  adapter passes the value through to the client. The backend should report zero; a recursive
  occupied-bytes figure is a different quantity and wants its own call if it is ever wanted.

## The streaming API's state machine

- [ ] **`stream_spare` and `stream_advance` have no enforced protocol.** `stream_spare` resizes the
  pending data to its new total - filling with zeros - before handing back the slice, and
  `stream_advance(offered, written)` truncates using numbers the CALLER supplies. StorageService
  uses it correctly, but the API is public: `stream_spare(4096)` followed by `stream_commit()`
  stores four kilobytes of zeros that were never written, and an `offered` that does not match the
  last offer truncates data that was already valid. Track the outstanding offer in `Pending`, refuse
  a second `stream_spare` while one is open, and make `stream_commit` return `Invalid` if an offer
  is outstanding.

## Deliberate, and worth revisiting anyway

- [ ] **A capped volume never gives an allocation back.** A file grown to 60 MiB and rewritten to
  nothing still holds 60 MiB of quota, because `allocated()` counts capacity - which is the fix that
  closed the grow-and-shrink hole, is documented, and is pinned by tests. Keeping it is defensible.
  But `vol://tmp` is where a caller most expects a truncate to return the space, and the zero-length
  case costs nothing to give back: replacing the data with `Vec::new()` frees the block and cannot
  fail. Larger shrinks can have a fallible compaction. The heap not returning pages to the domain
  does not mean the volume cannot return them to its own other files.

- [ ] **The toolchain is a floating `nightly`.** Same as elsewhere in the tree: pin the exact tested
  release. (This is a build-input pin, not a product version - nothing here is versioned before the
  first release.)

## Tests

- [ ] **Three of these want deterministic regressions, and they are the three that are cheapest to
  get wrong again.** A directory filled and emptied repeatedly, asserting that `footprint()` tracks
  the retained slots once they are charged; `writable_len` and `stream_len` refusing rather than
  answering zero when the name alone does not fit, and agreeing with each other at `MAX_ENTRIES`;
  `stream_len` on an EXISTING file being takeable in full (the current test covers the nested-create
  case only); a commit at exactly the promised maximum on a volume with no slack; a directory's
  listed size being zero; a name carrying a non-portable byte being refused by both writable
  backends identically; and `stream_commit` after a `stream_spare` whose slice was dropped.

## Order

The `Children` accounting first. It is the only finding with a number in the hundreds of megabytes,
it is reachable through the ordinary public API, and charging it is a contained change - the empty
case gives its memory straight back.

Then the preflight group, which is four small edits to three functions and removes every place a
caller can be told a number the next call will not honour.

Then the shared name policy and the directory size, because they are about two backends agreeing
with one contract, and both are small.

`Reserved`'s real guarantee last, because the honest options are to weaken the claim now and build
the arena later - and the claim should be weakened as soon as it is known to be too strong, which is
today.
