Six rounds of review have already been through this crate and it shows. Reads and listings allocate
fallibly; a failed write leaves the previous contents intact; a rewrite reuses the existing buffer;
`allocated()` counts high-water capacity rather than `len`, which is what closed the grow-and-shrink
hole; the stream is charged to the volume while it is still arriving and can be received straight
into the destination buffer; path parsing is bounded before the UTF-8 pass and allocates nothing;
lookup is a binary search; and there is an OOM allocator and a ten-thousand-operation invariant test.

What has not settled is the memory model, and the reason is one sentence the implementation is
trying to hold in two halves: **the capacity is a bound on memory actually held, AND the allocator's
own structures are outside it.** Every finding below is somewhere those two halves meet.

## The accounting hole, measured

- [x] **A directory's `Children` vector is never charged, and its capacity survives the entries.**
  `allocated()` sums `data.capacity()` for files and recurses into directories; `names()` sums
  `name.len()`. Neither counts `children.capacity()`. `insert` grows the vector through
  `try_reserve(1)` and `remove` calls `Vec::remove`, which never shrinks it - so a directory that
  held four thousand entries and now holds none still owns the backing store for four thousand
  `(String, Node)` slots, and `footprint()`, `free()` and `reservation_intact()` all report it as
  absent.

  MAX_ENTRIES bounds LIVE nodes, not the historical capacity of the vectors that held them. Empty
  the directory, leave it, create another, repeat. Measured on this tree's types:
  `(String, Node)` is **56 bytes**; one directory grown to 4096 and emptied retains **224 kB**; the
  full sequence the audit describes retains 8,382,465 slots - **447 MB** - none of it visible to any
  accounting the volume has, and reachable through the ordinary public `remove`.

  `docs/LIBERMEMFS.md` states that uncharged per-entry overhead "is a fixed implementation-defined
  cost already bounded by `MAX_ENTRIES`, so the worst case is a few hundred kilobytes whatever the
  capacity". That is exactly right for entries that EXIST and wrong for capacity that was kept, and
  the difference is three orders of magnitude.

  Charge `children.capacity() * size_of::<(String, Node)>()` to a metadata budget, and give the
  empty case back: a directory that reaches zero entries can drop its backing store by assignment to
  `Vec::new()`, which allocates nothing and cannot fail. The general answer is the arena the
  documentation already names as the endpoint.

  FIXED 2026-08-11, and the fix is a shrink policy plus an accounting rather than only an
  accounting - because charging the table to the volume's CAPACITY makes every small volume
  unusable: a four-slot table is 224 bytes and the tests mount volumes of twelve.

  So the two halves the milestone asks for, kept apart on purpose:

  * `metadata_bytes()` reports what the tables hold, retained capacity included. This is the number
    that did not exist; its absence was the whole finding.
  * `MAX_METADATA_BYTES` bounds it, separately from the capacity. The capacity bounds what a caller
    stored; this bounds what a caller kept, which is the thing they could drive without limit.
    `room_for_an_entry` gates on both, everywhere the entry count was gated.

  And the retention itself is prevented rather than merely measured. `shrink_children` runs on every
  remove: an emptied directory gets a fresh `Vec`, which allocates nothing and cannot fail, and a
  table more than four times its contents is moved into a right-sized one with `try_reserve_exact` -
  fallible, and a failure keeps the oversized table, because refusing a `remove` for want of memory
  to shrink would be absurd. `shrink_to_fit` does neither: it aborts on allocation failure, which is
  the one thing this crate is written not to do.

  Both tests fail without it, at exactly the audit's numbers: an emptied directory kept 14560 of
  14560 bytes, and one down from 1000 entries to 10 kept 57568 of 57568.

## What `Reserved` can actually promise

- [x] **The reservation guarantees a byte total, not the allocation the write needs.** Files are
  monolithic `Vec<u8>`, so growing one calls `try_reserve_exact` and the allocator may need the old
  block and the new block live at the same time - which this crate's own test
  `growing_past_a_files_high_water_mark_needs_both_blocks` exists to pin. A 64 MiB reserved volume
  holding a 32 MiB file that grows to 48 MiB ends within capacity and can still fail at the peak,
  and releasing the reservation first does not help: the old block is still there.

  ANSWERED 2026-08-11 with the honest interim fix the finding names: the claim is weakened where it
  is made. `docs/LIBERMEMFS.md`'s promise section now says that the reservation bounds a byte TOTAL
  and does not guarantee any particular allocation, works the audit's own 64/32/48 MiB example, and
  states that `reservation_intact()` compares a sum - "intact" means the arithmetic is right, not
  that the next write can be served. The comment above `reservation_intact` says the same thing at
  the call site. The comparison table's "the space is there" is now "the total is taken at mount".

  The real fix - an arena, or chunked file storage where growth never needs a new monolithic block -
  is recorded there as the design task it is, not implied by a word.

  `reservation_intact` compares a SUM - `reserved == capacity - footprint` - so a reservation held
  as several chunks satisfies it while no single contiguous run large enough for the next file
  exists. "Intact" currently means the arithmetic is right, not that the promise can be kept.

  The honest interim fix is to say so: the reservation bounds the volume's total and does not
  guarantee any particular allocation will succeed. The real fix is the arena, or chunked file
  storage where growth never needs a new monolithic block - and that is a design task, not a patch.

- [x] **`Reserved` reserves the data and not the metadata that must accompany it.** A volume of
  exactly C reserves C, and storing C bytes of files also needs their names, their nodes and their
  directory slots. On a heap with no slack the mount succeeds and the first write fails on a
  directory slot the reservation never covered. If `Reserved` is meant to be a hard promise it has
  to reserve everything the volume will allocate; if it is not, the documentation should stop using
  the word guarantee.

  ANSWERED 2026-08-11 in the same place and by the same rule. The documentation now states which
  memory the reservation covers and which it does not: names are charged against the capacity and so
  compete with the data rather than being reserved beside it, and directory tables are on the
  separate `MAX_METADATA_BYTES` budget and are not reserved at all. A volume of exactly C can
  therefore mount and still fail a write on a slot the reservation never covered.

  Reserving everything requires the arena; until then the word guarantee is applied to exactly one
  claim - the total is taken at mount and nothing else in the process can take it - and to nothing
  else.

## Preflights that disagree with the operations they precede

- [x] **`Ok(0)` is returned where the path cannot be written at all.** For a new file
  `writable_len` answers `free.saturating_sub(name)`, so a volume with 1 free byte and a 5-byte name
  answers `Ok(0)`; StorageService turns that into `WritePlan::Allowed { max_len: Some(0) }`, whose
  documented meaning is that the path MAY be written, and the write then fails with `NoSpace`
  because the name alone does not fit. `Ok(0)` must mean "an empty file can be created here";
  anything less is `Err(NoSpace)`.

  FIXED 2026-08-11. `Ok(0)` now means what StorageService reports it to mean - an empty file can be
  created here - and a free space that cannot hold the name is `Err(NoSpace)`.

- [x] **The two preflights disagree with each other at `MAX_ENTRIES`.** `writable_len` returns
  `Err(NoSpace)` when the entry count is full; `stream_len` returns `Ok(0)`; `stream_begin` then
  returns `Err(NoSpace)`. Three answers to one question, in one file. Make them one answer.

  FIXED 2026-08-11. `stream_len` answers `Err(NoSpace)`, which is what `writable_len` and
  `stream_begin` already answered. One question, one answer.

- [x] **`stream_len` forgets the pending path when the file already exists.** The new-file arm
  subtracts the WHOLE path and carries a comment explaining precisely why - `stream_begin` charges
  `path.len()` and keeps the whole path in the pending state, "the two numbers have to be the same
  number". The existing-file arm is `Ok(free.min(MAX_FILE_BYTES))`, and `stream_begin` allocates the
  pending path for a replace exactly as it does for a create. On a volume with 1000 bytes where
  `abc` and its name occupy 903, the preflight promises 97 and the stream can take 94. This is
  deterministic, not an allocator edge, and the test that pins the property covers the nested-create
  case and not the replace.

  FIXED 2026-08-11. Both arms subtract the whole path, because `stream_begin` allocates the pending
  path for a replace exactly as for a create. The audit's arithmetic is now a test: on a volume of
  1000 bytes where `abc` and its name occupy 903, the promise and what the stream can take are the
  same number, and `a_stream_over_an_existing_file_can_take_everything_it_was_promised` takes it.

- [x] **A new stream can take everything it was promised and fail in `stream_commit`.** The preflight
  allows roughly `capacity - path.len()`, and the pending state then holds the path plus that data -
  the whole capacity. `stream_commit` moves the pending out of `self`, so it stops counting, but the
  bytes are still there in local variables while `write_file_owned_unsynced` allocates a fresh
  `String` for the final name and possibly grows the parent's `Children`. On a tight heap the
  transfer accepts one hundred per cent of what it was promised and the commit fails on metadata.
  Prepare the destination's metadata in `stream_begin` and MOVE it at commit.

  FIXED 2026-08-11 by preparing the expensive half at `stream_begin`. `Pending` carries the
  destination's name, allocated up front and MOVED into the tree at commit, and `footprint` counts
  it - so the refusal, if there is one, happens before the sender transmits anything.

  The parent's SLOT is deliberately not pre-reserved with it, and finding out why was the useful
  part: a directory table is on the metadata budget, not the volume's capacity, so reserving one at
  begin made `reservation_intact` account for memory that budget does not - the two budgets meeting
  in the one place they must not. `room_for_an_entry` has already established at begin that a slot
  is available, and a slot is a few dozen bytes against the name's 255.

- [x] **`write_file` has no post-allocation check, and the streaming path has one.**
  `stream_spare` re-checks `footprint() > capacity` after `try_reserve_exact` and aborts on an
  overshoot, with a comment saying the allocator "promises at least what was asked for and may give
  more... Undo an overshoot rather than leave the volume over its own capacity". `write_file`
  computes its bound before `store()` and never looks again, so a generous allocator can leave a
  successful write with `footprint() > capacity`. For a new file the result's capacity can be
  checked before insertion; for in-place growth the rollback is harder, which is another place the
  monolithic `Vec` is doing the arguing.

  FIXED 2026-08-11 for the case that can be undone. A new entry whose allocation overshot the
  capacity is removed again and the write refused, exactly as `stream_spare` does. In-place growth
  is not undone: the old contents are gone by then and there is nothing to put back, so the
  overshoot is accepted and recorded rather than a successful write being discarded. That asymmetry
  is the monolithic `Vec` arguing for the chunked storage the reservation finding wants, and the
  comment says so.

## Semantics that differ from the rest of the filesystem stack

- [x] **Two writable backends enforce two different name policies.** `fs::core::FsError::BadName`
  documents a malformed name as "an empty segment, `.` or `..`, not UTF-8, or a byte outside the
  portable-name policy". LiberFS's `validate_name_segment` enforces all four. LiberMemFS's
  `segments()` enforces two: it rejects `.` and `..` and non-UTF-8, has no portable-byte check at
  all, and DELIBERATELY tolerates empty segments so `/a/b/`, `a//b` and `a/b` name one thing.

  FIXED 2026-08-11. `fscore::validate_name_segment` and `is_portable_name_byte` are the policy now,
  and both writable backends call them: LiberFS's own validator is a two-line wrapper that supplies
  its `NAME_MAX`, which is the one part of the rule that legitimately differs between filesystems.
  LiberMemFS gained the portable-byte check it never had.

  `both_writable_backends_refuse_the_same_names` walks the reserved set. Separator normalisation is
  left where it is - LiberMemFS still treats `/a/b/`, `a//b` and `a/b` as one name, which every
  caller in this tree expects - but that is now the only difference, and it is about paths rather
  than names.

  It matters because StorageService mounts LiberMemFS as the live `vol://system` (as well as
  `vol://ram` reserved and `vol://tmp` capped), so the same application creates `foo:bar` on a live
  system and cannot create it on an installed LiberFS one. One validator in `fs/core`, used by every
  writable backend; and separator normalisation decided at one layer rather than per filesystem.

- [x] **Directories report their subtree's size where the ABI says zero.** `list_entries` fills
  `Entry.size` from `node.bytes()`, which for a directory sums everything under it, and the
  generated `Storage` documentation says plainly that "a directory reports a length of zero". The
  adapter passes the value through to the client. The backend should report zero; a recursive
  occupied-bytes figure is a different quantity and wants its own call if it is ever wanted.

  FIXED 2026-08-11. `list_entries` reports zero for a directory, which is what the generated
  `Storage` documentation states and what the adapter hands the client. The recursive occupied-bytes
  figure is still computable - `Node::bytes` - and wants its own call if it is ever wanted.

## The streaming API's state machine

- [x] **`stream_spare` and `stream_advance` have no enforced protocol.** `stream_spare` resizes the
  pending data to its new total - filling with zeros - before handing back the slice, and
  `stream_advance(offered, written)` truncates using numbers the CALLER supplies. StorageService
  uses it correctly, but the API is public: `stream_spare(4096)` followed by `stream_commit()`
  stores four kilobytes of zeros that were never written, and an `offered` that does not match the
  last offer truncates data that was already valid. Track the outstanding offer in `Pending`, refuse
  a second `stream_spare` while one is open, and make `stream_commit` return `Invalid` if an offer
  is outstanding.

  FIXED 2026-08-11. `Pending` tracks the outstanding offer: a second `stream_spare` over an open one
  is `Invalid`, `stream_advance` checks the numbers it is given against the offer that was actually
  handed out rather than believing them, and `stream_commit` refuses while an offer is open - which
  is what stopped `stream_spare(4096)` followed by `stream_commit()` from storing four kilobytes of
  zeros nobody wrote.

  `stream_advance` returns `Result` now, and StorageService propagates it rather than dropping it:
  a protocol violation there would be a bug in that file, not a condition the medium can produce,
  and the one thing it must not become is a file full of zeros that reports itself complete.

  `the_streaming_pair_is_a_protocol_rather_than_a_convention` covers all three, each watched to
  fail.

  **One correction, because the wrong conclusion was nearly recorded here.** Turning the adapter
  trait's default `stream_advance` into `Err(Invalid)` was a real defect and it is fixed: the
  service calls `stream_advance` after every chunk, including when `stream_spare` returned `None`
  because the backend does not implement it, so "no offer" and "a broken offer" were being answered
  with the same error. The default is `Ok` now, the service tracks whether an offer was actually
  opened, and the distinction is written down at both ends. Nothing in the crate's own 48 tests
  could have seen it: the backend that returns `None` is the one in StorageService.

  What it did NOT do is take PermissionManager, ConsoleService, SystemGraphService and the Shell
  offline, which is what the failing `kernel.boot.init_package_starts_system_manager` in that run
  looked like it was saying. That failure is older than tonight - see P02M0133 - and the two
  arriving together is exactly how a real defect gets credited with somebody else's symptom.

## Deliberate, and worth revisiting anyway

- [x] **A capped volume never gives an allocation back.** A file grown to 60 MiB and rewritten to
  nothing still holds 60 MiB of quota, because `allocated()` counts capacity - which is the fix that
  closed the grow-and-shrink hole, is documented, and is pinned by tests. Keeping it is defensible.
  But `vol://tmp` is where a caller most expects a truncate to return the space, and the zero-length
  case costs nothing to give back: replacing the data with `Vec::new()` frees the block and cannot
  fail. Larger shrinks can have a fallible compaction. The heap not returning pages to the domain
  does not mean the volume cannot return them to its own other files.

  CHANGED 2026-08-11, for the case the audit says costs nothing. A write of zero bytes assigns a
  fresh `Vec`, which frees the block and cannot fail; a partial shrink still holds its allocation,
  because compacting one is fallible and losing a write to it would be the worse trade.

  Two existing tests moved with it, and both were pinning the old rule rather than the property.
  The property - that the accounting and the heap agree, so the volume never reports space it does
  not have - is unchanged and is what the rewritten
  `a_shrunk_file_keeps_its_allocation_and_the_volume_says_so` states: it now shows a PARTIAL shrink
  keeping its buffer and being refused a second large file, then a truncate to nothing releasing it
  and the same write succeeding into memory that is really there. The ten-thousand-operation model
  gained the same one-line rule, on the same terms: derived from the sizes the test asked for, never
  read back from the implementation it checks.

- [x] **The toolchain is a floating `nightly`.** Same as elsewhere in the tree: pin the exact tested
  release. (This is a build-input pin, not a product version - nothing here is versioned before the
  first release.)

  DEFERRED 2026-08-11, with the reason rather than silently. Every crate in the tree carries the
  same `channel = "nightly"` - sixteen files - so it is one decision about the repository, and the
  only nightly installed here is the undated one (1.98.0-nightly, 2026-06-15). Pinning a date in one
  crate asks rustup for a toolchain that is not present, which breaks the build instead of making it
  reproducible. It belongs to whichever milestone owns the build environment, pinned across all
  sixteen at once with the dated toolchain actually fetched. Recorded identically in P02M0125.

## Tests

- [x] **Three of these want deterministic regressions, and they are the three that are cheapest to
  get wrong again.** A directory filled and emptied repeatedly, asserting that `footprint()` tracks
  the retained slots once they are charged; `writable_len` and `stream_len` refusing rather than
  answering zero when the name alone does not fit, and agreeing with each other at `MAX_ENTRIES`;
  `stream_len` on an EXISTING file being takeable in full (the current test covers the nested-create
  case only); a commit at exactly the promised maximum on a volume with no slack; a directory's
  listed size being zero; a name carrying a non-portable byte being refused by both writable
  backends identically; and `stream_commit` after a `stream_spare` whose slice was dropped.
  DONE 2026-08-11. Every one of the seven, and each watched to fail against the code it guards:

  * `a_directory_filled_and_emptied_gives_its_table_back` and
    `a_directory_that_shrinks_a_long_way_gives_most_of_its_table_back` - `metadata_bytes()` tracking
    retained slots, over eight fill-and-empty cycles and one long shrink.
  * `a_preflight_never_promises_what_the_next_call_refuses` - refusing rather than answering zero
    when the name alone does not fit, and the two preflights and the operation agreeing at
    MAX_ENTRIES.
  * `a_stream_over_an_existing_file_can_take_everything_it_was_promised` - the replace case the old
    test did not cover.
  * `a_stream_that_takes_its_whole_promise_commits` - a commit at exactly the promised maximum. Not
    under a heap budget: an allocation failure inside one is a panic inside the harness, and the
    property is an accounting one, which a capped volume states exactly.
  * `files_and_directories_round_trip` - a directory's listed size being zero.
  * `both_writable_backends_refuse_the_same_names`, against the same list LiberFS's
    `rejects_unportable_name_characters` uses. The policy is one function in `fs/core`, so what each
    backend's test pins is that it reaches it.
  * `the_streaming_pair_is_a_protocol_rather_than_a_convention` - commit over an open offer, a
    second offer, and numbers that describe some other offer.

## Order

The `Children` accounting first. It is the only finding with a number in the hundreds of megabytes,
it is reachable through the ordinary public API, and charging it is a contained change - the empty
case gives its memory straight back.

Then the preflight group, which is four small edits to three functions and removes every place a
caller can be told a number the next call will not honour.

Then the shared name policy and the directory size, because they are about two backends agreeing
with one contract, and both are small.

`Reserved`'s real guarantee last, because the honest options are to weaken the claim now and build
the arena later - and the claim should be weakened as soon as it is known to be too strong, which is
today.

## Reopened: two admissions in the code, a guard with a second door, and a namespace nobody holds

A second audit - 2026-08-12, against this tree at `fcb821b` - reading the repairs rather than the
finding list. Every claim below was checked against the code first.

What was fixed was fixed well. `shrink_children` on every remove, with a fresh empty `Vec` for an
emptied directory and a fallible right-sized table for a shrunken one - and a `remove` that still
succeeds when that allocation fails. `metadata_bytes` and `MAX_METADATA_BYTES` as a budget of their
own. `writable_len` and `stream_len` refusing when the NAME does not fit, so `Ok(0)` finally means
what it says, and both subtracting the path cost on replace as well as create. A directory's length
reported as zero, which is what the ABI says. `write(path, b"")` dropping the old buffer so a
truncate returns the quota. Each with a test that reaches it.

The four below did not get there.

### `stream_push` does not know about an open offer, and the result commits zeros

`stream_commit` refuses while an offer is outstanding (`src/fs/libermemfs/src/lib.rs:1036`) with an
exact statement of why: "Committing would store the rest as the zeros `stream_spare` filled it with
- bytes that were never written, in a file that reports itself complete."

`stream_push` (`src/fs/libermemfs/src/lib.rs:907`) never looks at `pending.offered`. So:

```
stream_begin("f")
stream_spare(100)     // data.len() = 100 zeros, offered = Some(100)
stream_push(b"abc")   // permitted; data.len() = 103
stream_advance(100, 0)
stream_commit()
```

`stream_advance` computes `keep = pending.data.len() - (outstanding - written)`
(`src/fs/libermemfs/src/lib.rs:1023`), which is `103 - 100 = 3`, and truncates to it. The first
three bytes are the zeros the offer filled; `abc` was at 100..103 and is discarded. The volume
commits a three-byte file of zeros and reports it complete - which is precisely the sentence at
`:1036`, arrived at through the one entry point that does not check.

- [x] **Refuse `stream_push` while an offer is outstanding.**

  DONE 2026-08-12. `stream_push` now asks `pending.offered.is_some()` before anything else, which is
  the guard `stream_commit` already had at the other door.

- [x] **A test that mixes the two mechanisms and asserts the refusal**, watched to fail against the
  current tree, where it commits zeros instead.

  DONE 2026-08-12, inside `the_streaming_pair_is_a_protocol_rather_than_a_convention` where the rest
  of the protocol is asserted: spare(100), push("abc") refused, advance(100, 3), push("def"), and
  the file is six bytes. Watched to fail with the guard removed - `left: Ok(()), right:
  Err(Invalid)` - which is the push being accepted and its bytes then truncated away.

### The stream prepays the name and not the slot

`Pending` carries `name: Option<String>` (`src/fs/libermemfs/src/lib.rs:295`) and the name is
allocated at `stream_begin`, which was the fix. Commit then goes to `insert`, which does
`children.try_reserve(1)` (`src/fs/libermemfs/src/lib.rs:132`) - a fallible heap allocation, after
the whole file has been accepted.

So "the stream promised to take this file and the commit cannot fail" is still not true: it can
fail, on one slot, at the end. The comment explains that directory tables have a budget of their own
and that is a fair reason for the accounting to be separate - it is not a reason for the allocation
to be late.

- [x] **Reserve the parent's slot at `stream_begin`**, or place a reserved node there and fill it at
  commit.

  DONE 2026-08-12 by the second, which closes this and the namespace item together: `stream_begin`
  inserts an empty file at the path, so the slot is taken from the metadata budget at begin and
  `insert`'s `try_reserve(1)` no longer runs at commit.

  This is not the budget confusion the earlier comment refused. RESERVING a slot inside the capacity
  arithmetic would make a reserved volume count memory the metadata budget does not; inserting an
  ordinary entry charges the metadata budget, which is where a directory entry has always been
  charged. `Pending::name` went with it - the name is in the tree now, and counting it in
  `footprint` as well would be the same accounting error in the other direction.

### In-place growth may exceed capacity, and the code says so

`write_file` undoes an over-allocation only for a new entry
(`src/fs/libermemfs/src/lib.rs:805`), and the comment above it states the rest plainly: the old
contents are gone, putting the file back is not possible from here, "so the overshoot is accepted
and the volume records it rather than discarding a write that succeeded."

That is a defensible decision about what to do at that point in the code, and it leaves an invariant
broken: `write_file` can return `Ok(())` on a volume whose `footprint()` now exceeds its
`capacity()`, on any allocator whose `try_reserve_exact` gives more than was asked for.

The comment also identifies the real fix, and it is the same one the reservation finding wants:
"That asymmetry is the monolithic `Vec` arguing for the chunked storage the reservation finding
wants."

- [x] **Grow into a new buffer and swap, or chunk the storage.**

  DONE 2026-08-12 by the first: growth past the file's held capacity builds the new buffer first,
  checks what the volume would then hold, and swaps only if it fits. A generous allocator is
  refused instead of accepted, so `write_file` can no longer answer `Ok(())` on a volume over its
  own capacity.

  `data.len() > file.len()` was the wrong condition to hang it on and the property test said so
  within a run: a ten-byte file in a forty-four byte buffer taking twenty new bytes needs no
  allocation, and replacing the buffer there quietly compacted the file - the high-water rule this
  filesystem states, broken by the fix for something else. The test is `capacity`.

  `growing_a_file_never_takes_the_volume_over_its_capacity` grows a file until the volume refuses
  and checks the bound after every answer, because the defect was a SUCCESSFUL write leaving it
  crossed.

### The stream validates a destination and nothing holds it

`stream_begin` resolves the path and rejects a directory or a missing parent
(`src/fs/libermemfs/src/lib.rs:834`); `stream_commit` resolves it again against the tree as it is
then (`src/fs/libermemfs/src/lib.rs:1054`). Between the two, StorageService returns to its serve
loop after every chunk - deliberately, so one large upload does not stall every other client - and
that loop still serves `write`, `remove`, `mkdir` and `rmdir`.

So a client can transfer an entire file into a destination that was removed after it was checked, or
that has since become a directory, and learn about it at commit. Nothing is corrupted; the work is
simply wasted, and `stream_plan`'s answer meant less than it appeared to.

This is not the same as a missing lock. The question is what `stream_begin` PROMISES, and there are
two honest answers.

- [x] **Decide, and make the code say it.**

  DONE 2026-08-12: the begin HOLDS the path. `an_open_stream_holds_its_destination` asserts that
  `mkdir` over a streaming destination is refused and that the claim is visible in the directory;
  `an_abandoned_stream_leaves_no_destination_behind` asserts the placeholder goes when the stream
  does, and that a stream REPLACING an existing file leaves it alone when abandoned - there was no
  placeholder to take away and the file was never the stream's to remove.

### Two recorded rather than tasked

- **`Reserved` had its specification corrected rather than its implementation.**
  `reservation_intact()` now says honestly that it means the reserved byte count adds up, not that
  the next allocation of that size will succeed. That is the right thing to have written down. The
  underlying model - monolithic `Vec<u8>` files out of the global heap, a reservation in bytes
  rather than in a usable arena, directory metadata outside the reservation - is unchanged, and it
  is the same monolithic `Vec` the over-allocation comment points at. A real guarantee is an arena
  or page-backed chunked files, which is a milestone rather than a task.
- **The floating nightly** is the same repo-wide item recorded in [P02M0129](P02M0129.md),
  [P02M0125](P02M0125.md) and [P02M0127](P02M0127.md). Decided once, in one place.

### One divergence worth closing while the file is open

- [x] **Empty path segments mean different things in the two writable filesystems.**

  DONE 2026-08-12 for the half that was genuinely ambiguous: `a//b` is now `BadName` in LiberMemFS,
  so one path no longer has two spellings on a volume whose sibling backend refuses one of them.

  Leading and trailing separators are still tolerated, and that is recorded as a decision rather
  than left as an oversight. LiberFS is stricter still - `split_segments` passes EVERY segment to
  the validator, so `/a/b` is `BadName` there - and matching it would change what `vol://` paths
  mean for every caller in the tree. Adopting it was tried and reverted the same hour: `b""` is how
  LiberMemFS names its root and nine tests failed on the first run.

- [x] **Which of the two separator rules the Storage ABI states.**

  DONE 2026-08-12, and the ABI states the tolerant one. `src/idl/storage.lsidl` now carries the rule
  on the `volume` interface, so it is generated into `docs/gen/liber/storage/v1.md` and reaches
  every caller as documentation rather than living in two filesystems' heads: a MIDDLE segment may
  not be empty, so `a//b` is `bad-name` on every volume; a leading or trailing separator is
  TOLERATED and means the same path without it.

  Why that way round rather than the stricter one, said in the contract itself: `a//b` had two
  readings on a volume whose sibling backend refused one of them, which is a path that resolves or
  does not depending on what is mounted - exactly what a shared ABI exists to prevent. `/a/b` versus
  `a/b` is one reading of one path either way, so adopting LiberFS's stricter rule would have
  changed every `vol://` caller in the tree for no gain in agreement.

  And LiberFS was the one that had to move, so it did: `split_segments` normalises a leading or
  trailing separator away rather than passing every segment to the validator.
  `the_storage_abis_separator_rule_is_this_backends_rule_too` asserts the four answers there, and
  `a_path_that_tries_to_leave_the_volume_is_refused` asserts the same four in LiberMemFS - two tests
  rather than a shared helper, because the point is that two implementations AGREE and a helper
  would only prove that one of them calls itself twice.

### Order

`stream_push` first - it is two lines, and it is the only item here that commits wrong data while
reporting success.

Then the placeholder at `stream_begin`, which closes the late slot allocation and the namespace
question together and is the reason to do them as one change rather than three.

Then the empty-segment rule, which is small and is a divergence between two filesystems under one
API.

The in-place overshoot last of the tasks, and honestly: it is a symptom of the monolithic `Vec`, and
fixing it properly is the chunked-storage work the reservation model needs anyway. What can be done
now is stating the broken invariant where a caller will read it.

## Reopened again: the placeholder is a claim nothing enforces

A third audit, against this tree at `8df720c` - 2026-08-12. Four findings, every one read in the code
first. Two are extended past what the audit said, because in both the comment beside the defect is
either the argument for the fix or a statement this file disproves forty lines further down.

What the round got right stays right. The growth path builds a separate `Vec`, checks the
allocator's ACTUAL capacity against the volume before adopting it, and swaps only then - which is
the shape asked for and it is done exactly. `stream_push` refuses while an offer is open. `a//b` is
decided by the Storage ABI rather than per backend. The toolchain is `nightly-2026-06-16`.

The placeholder is also the right idea, and the reasoning recorded at `src/fs/libermemfs/src/lib.rs:906`
is sound: a stream that validated a destination and then held nothing could have its parent removed
mid-transfer, and `insert`'s `try_reserve(1)` was a fallible allocation at COMMIT, after a whole file
had been accepted. Both are real problems and an entry in the tree answers both.

What it does not do is hold anything against the operations it was written to defend against.

### A completed write can be deleted by another client's abort

`stream_begin` inserts `Node::File(Vec::new())` (`lib.rs:924`) and records `placeholder: true` in
`Pending`. The NODE carries no mark. And `self.pending` is consulted in exactly nine places
(`grep -n 'self.pending' src/fs/libermemfs/src/lib.rs`), every one of them inside the stream API
itself or in `footprint`. `write_file`, `write_file_owned`, `remove`, `mkdir` and `rmdir` do not
consult it at all.

`stream_abort` then does, unconditionally for a placeholder stream (`:1118`):

```rust
if let Some(pending) = self.pending.take() && pending.placeholder {
    let path = pending.path;
    let _ = self.remove(&path);
}
```

So this sequence loses data, deterministically, with no timing subtlety:

```
A: stream_begin("x")          -> placeholder file at "x"
B: write_file("x", IMPORTANT) -> Ok(())          B is told the write succeeded
A: stream_abort()             -> remove("x")     B's file is gone
```

and this one loses a file the placeholder never even owned:

```
A: stream_begin("x")
B: remove("x")                -> Ok, placeholder gone
B: write_file("x", NEW)       -> Ok, a file B owns
A: stream_abort()             -> remove("x")     NEW is gone
```

`remove` has no way to know the node at that path is not the one the stream put there, because
nothing distinguishes them.

This is a different class from everything else in this milestone. The findings so far have been about
accounting, refusals and work thrown away; this one silently destroys a write the caller was told had
succeeded.

- [x] **Make the placeholder a node kind, not a file.** `Node::Reserved` (or
  `Node::File { data, claimed_by_stream: bool }`), so the tree itself carries the claim and every
  operation can see it.

  DONE 2026-08-12. `Node::Claimed(Vec<u8>)`, holding what the destination held when the stream opened - empty for a new file, the previous contents for a replacement. Adding the variant made the compiler enumerate every site that had to decide, which is why the accounting walks, the parent walks, the preflights and the listing all answer for it explicitly rather than by a catch-all.

- [x] **Refuse the ordinary mutators against a claimed path.** `write_file`, `write_file_owned`,
  `remove`, `mkdir` and `rmdir` answer `FsError::Busy` - or `Exists`, if a new error is not wanted -
  for a path a stream is holding. That is the "holds its destination" this milestone announced.

  DONE 2026-08-12. `write_file`, `write_file_owned`, `remove` and `mkdir` answer `Exists`; `rmdir` answers `NotDir`, as it does for a file. `Exists` rather than a new variant: it is the answer `mkdir` already gave for this condition, it needs no `FsError` addition rippling into the Storage ABI, and it says the true thing - the name is taken. The refusal lives in the PUBLIC entry points, because `stream_commit` reaches `write_file_owned_unsynced` to replace the claim it made itself.

- [x] **Abort removes only what it still owns.** Even with the refusals above, `stream_abort` must
  check that the node at the path is still the placeholder before removing it, because the parent
  directory can be removed and recreated underneath it.

  DONE 2026-08-12. `stream_abort` looks at the node before touching it: a claim it created is removed, a claim over an existing file is turned back into that file with the bytes it was holding, and anything else is left alone. Watched failing by forcing the unconditional remove back.

- [x] **Decide what happens to a claimed path when its PARENT is removed.** `rmdir` on the parent of
  a claimed entry is the same question one level up, and today it is answered by whatever the
  placeholder file happens to make `rmdir` do.

  DONE 2026-08-12. It falls out of the claim being a real entry: `rmdir` on the parent finds it non-empty and answers `NotEmpty`, so a transfer cannot have its directory removed from under it. Asserted in `an_open_stream_holds_its_destination` rather than left to inference.

- [x] **The four regression tests the current one is missing** - see the last finding below.

  DONE 2026-08-12, in the last finding's items: `an_open_stream_holds_its_destination` now asserts
  all four mutators plus the parent, and two new tests carry the data-loss sequences and the
  replacement case. Every one of them was watched failing with its rule removed.

### A replacing stream holds nothing at all

`let placeholder = is_new;` (`:915`), and the insert below it runs only `if is_new`. So a stream that
REPLACES an existing file creates no claim, and the sequence the placeholder exists to prevent works
exactly as it did before:

```
A: stream_begin("file")       -> "file" exists, no placeholder
B: remove("file")
A: ... whole transfer ...
A: stream_commit()            -> write_file_owned_unsynced re-resolves the path
                                 finds nothing, takes the CREATE path
```

- the name and the slot are allocated at commit after all, which is the finding the placeholder was
added to close, and the milestone's claim that `stream_begin` holds the path is true for one of its
two cases.

- [x] **Claim the destination for a replacing stream too.** The existing file's data stays where it
  is - a stream that is abandoned must leave the file exactly as it was, which is this milestone's
  own rule - so the claim is a flag on the existing node rather than a new entry, and `stream_abort`
  clears it without touching the data.

  DONE 2026-08-12. `stream_begin` moves the existing buffer into `Node::Claimed` - no allocation, so a replacement cannot be refused for memory after its destination has been checked - and the abort moves it back. `let placeholder = is_new` remains, but now it decides only whether the abort REMOVES the entry or restores it.

- [x] **A test for the replace case**: begin a stream over an existing file, remove it, transfer,
  commit - and assert the removal was refused rather than the commit silently becoming a create.

  DONE 2026-08-12. `a_replacing_stream_holds_its_destination_too`: the remove and the write are refused, a reader sees the previous contents until the commit, and the commit both replaces them and releases the claim. That last assertion is its own finding - the adopt path rewrites the buffer in place and leaves the node as it found it, so without `release_claim` a commit that fitted the existing allocation left a claim nobody could release and a permanently unwritable file.

### The slot is charged to a budget its own comment says it does not belong to

`stream_begin` computes (`:873`):

```rust
let entry_cost = path.len() + if is_new { name.len() + SLOT_BYTES } else { 0 };
if (self.footprint() as usize).saturating_add(entry_cost) > self.capacity { return Err(FsError::NoSpace); }
```

and the comment above it justifies the `SLOT_BYTES` term as "because `footprint` counts the directory
table it goes into".

`footprint` does not. It is `root.allocated() + root.names() + pending` (`:344`-`:352`). Directory
tables are `metadata_bytes()` (`:361`), a separate budget bounded by `MAX_METADATA_BYTES` - which is
the whole point of the retained-table finding this milestone opened with.

Forty lines below the arithmetic, the same function says so (`:909`):

> This is not the budget confusion that was refused before. RESERVING a slot inside the capacity
> arithmetic would make a reserved volume count memory the metadata budget does not; inserting an
> ordinary entry charges the metadata budget, which is where a directory entry has always been
> charged.

Two comments in one function, contradicting each other, and the code follows the false one.

It has a visible consequence beyond tidiness: `stream_len` costs a new destination at `path + name`
(`:947`ff) while `stream_begin` costs it at `path + name + SLOT_BYTES`, so on a volume where
`free >= path + name` and `free < path + name + SLOT_BYTES` the preflight answers `Ok(0)` and the
begin answers `NoSpace`. That is the preflight/execute mismatch this milestone already fixed once for
`writable_len`.

- [x] **Drop `SLOT_BYTES` from the capacity check** and let `room_for_an_entry` plus the fallible
  `insert` bound the slot, which is where a directory entry is bounded everywhere else. Prepaying the
  slot by INSERTING it is still right and is unaffected.

  DONE 2026-08-12. The slot is bounded where a directory entry has always been bounded: `room_for_an_entry` and the fallible `insert`.

- [x] **Delete the false comment** and keep the one at `:909`, which states the rule correctly.

  DONE 2026-08-12. Replaced with what is true - `footprint` is `allocated + names + pending` and the tables are `metadata_bytes` - and with the consequence, so the next reader meets the reason rather than the rule.

- [x] **A test that `stream_len` and `stream_begin` agree** on the boundary volume - the same shape
  as the `writable_len` test this milestone already has.

  DONE 2026-08-12. `stream_len_and_stream_begin_agree_about_a_new_destination` sweeps every capacity from 32 to 320 rather than aiming at one, because the boundary depends on the allocator's answers. Watched failing with the term put back: `capacity 32: stream_len said Ok(30) and stream_begin said Err(NoSpace)`.

### The test asserts one of the four operations its own comment names

`an_open_stream_holds_its_destination` (`src/fs/libermemfs/src/tests.rs:991`) opens with exactly the
right description: the serve loop "still serves `write`, `remove`, `mkdir` and `rmdir`", so a client
could transfer a whole file into a path that had since been removed or turned into a directory.

It then asserts `mkdir` (`:1006`) and the listing. `write` and `remove` - the two that are actually
permitted, and the two the first finding above is made of - are not tested, and they are the reason

- [x] **Assert all four.** `write_file`, `remove`, `mkdir`, `rmdir` against a claimed path, each
  refused. A test whose comment enumerates four operations and checks one reads as covering four.

  DONE 2026-08-12. `write_file`, `write_file_owned`, `remove`, `mkdir` and `rmdir`, plus the read that must still work and the parent that must not be removable.

- [x] **And the two data-loss sequences** as tests in their own right: write-then-abort, and
  remove-recreate-then-abort, each asserting the other client's bytes survive.

  DONE 2026-08-12. `an_abort_cannot_delete_a_write_another_caller_completed` runs both directions - the write refused while a claim is open, and a claim taken over an existing file left exactly as it was found. Watched failing with the refusal removed.

### Unchanged and still accepted

`Reserved` still means "the sum of the chunks is intact" rather than "any allocation of this size
will succeed", because a file is one monolithic `Vec`. That is a stated design limit, this milestone
says so plainly, and the honest fix is chunked backing rather than another check - it is not

### Order

The placeholder's ownership first, and all four of its tasks together: a node kind, refusals in the

## Reopened: two new mutators arrived without the invariants the old ones were given

A fourth audit, against this tree at `4350074` - 2026-08-14. Six findings and all six hold. The audit
is explicit that it is NOT reopening the third round's four - `Node::Claimed`, the replacement claim,
`release_claim`, the mutator refusals and the `SLOT_BYTES` removal are real and have the regression
tests that match them - and it is right. What it found instead is that `rename` and `truncate`, which
arrived after that round, do not hold the invariants that round established.

That is worth stating as the finding rather than as six of them. This milestone is named for what
capacity bounds, and its history is a sequence of write paths learning the same four rules: charge
`capacity()` and not `len()`, refuse before mutating, allocate-check-swap rather than allocate-and-
hope, and put the reservation back on every exit. The ordinary write path knows all four. The two
newest public mutators know none of them, and the 10,000-operation property model - the thing that
would have said so - draws from six operations that do not include either.

### `truncate` breaks four rules the write path already keeps

`LiberMemFs::truncate` (`src/fs/libermemfs/src/lib.rs:1560-1598`):

- **It charges `len()` where the volume accounts `capacity()`.** `have` is `bytes.len()` (`:1566`) and
  the check is `footprint() + (want - have) > capacity` (`:1574`). A file holding 20 bytes in an
  80-byte buffer is already charged for 80; growing it to 40 allocates nothing, and this refuses it
  with `NoSpace`. That is the `len`-versus-`capacity` confusion this milestone was opened for, in a
  function written after it was closed.

- **It never checks `MAX_FILE_BYTES`.** `write_file` and the streaming path both refuse past 64 MiB.
  `truncate` bounds `want` only by the volume's capacity, so on a volume larger than that a caller can
  create a file no other write path in this crate would accept.

- **It trusts what `try_reserve_exact` gave it.** `:1586` reserves and `:1588` resizes, with no check of
  the resulting `bytes.capacity()`. The allocator may return more than was asked for, and the volume
  charges what it holds - so `footprint()` can end above `capacity()`. The ordinary growth path
  already knows this and builds into a temporary buffer it can measure before swapping in.

- **A refused grow leaves the reservation dropped.** `:1577-1579` releases the whole reservation before
  the allocation, `:1586` can return with `?`, and `resync_reservation()` is at `:1596` - after the
  return. So a `Reserved` volume that refuses a truncate comes back with its reservation gone. This is
  the defect the previous round found and fixed in `write_file`, in the function beside it.

- **And `shrink_to_fit()` at `:1590` is infallible,** which the crate elsewhere refuses to accept:
  `shrink_children` (`:196-210`) is hand-written specifically so that a shrink cannot abort the storage
  service on an allocation failure, and says so. One shrink policy, two implementations, in one file.

- [x] **Rewrite the grow path as allocate-check-swap,** the way `write_file` does: build the new
  buffer, measure its real capacity against what the volume can hold, then swap. That closes the
  `len`/`capacity` charge, the post-reserve capacity check and the reservation-on-exit problem
  together, because they are all consequences of mutating in place.

- [x] **Refuse past `MAX_FILE_BYTES`,** with the same error the other paths use, so the file-size bound
  is a property of the volume rather than of which call reached it.

- [x] **Shrink through the fallible path,** or state in a comment why a file's buffer may use
  `shrink_to_fit` when a directory's table may not. One of those is the answer; having both without
  saying so is not.

### `rename` can push the volume past its capacity, and can lose the file it moved

`LiberMemFs::rename` (`:1513-1554`):

- **The name-length delta is never charged.** Names are part of `footprint()`; `rename` allocates the
  new name (`:1537`) and checks nothing. On a volume that is exactly full, renaming `a` to
  `very-long-name` succeeds as long as the host heap has room, and `footprint()` ends above
  `capacity()` - the invariant this milestone exists to hold.

- **The pre-reservation can be destroyed before it is used.** `:1544` reserves one slot in the
  destination's table specifically so the insert cannot fail after the source is gone. Then `:1548`
  removes the source through `remove`, which calls `shrink_children` unconditionally (`:168-173`), and
  `shrink_children` replaces the table with one sized exactly to its contents (`:206-210`). For a
  rename WITHIN one directory those are the same table, so the reserved slot is given back, `insert`
  at `:1551` has to allocate again, and if that fails the node has already been taken out of the tree
  and is dropped on the way out. The ABI promises rename is atomic within a volume.

  The window is narrow - `shrink_children` only acts on a table at or below a quarter occupancy - and
  it is exactly the case the reservation was written to make impossible.

- **`rename("missing", "missing")` answers `Ok(())`.** The same-path early return (`:1520-1522`) is
  before the existence check, so renaming something that is not there succeeds.

- [x] **Charge the delta before anything moves:** `footprint() - source_name.len() +
  destination_name.len() > capacity` refuses with `NoSpace`. It belongs beside the other refusals, in
  the block whose comment already says "EVERYTHING THAT CAN REFUSE, FIRST".

- [x] **Do not shrink the table between the reserve and the insert.** Either a `remove` that does not
  shrink, with the shrink done after the insert succeeds, or - cleaner for the same-parent case -
  rename the key in place and skip the remove/insert pair entirely.

- [x] **Check the source exists before the same-path shortcut,** so a no-op rename of a missing file
  is `NotFound`.

- [x] **A test for each:** a volume exactly full renaming to a longer name must refuse and leave the
  file; a rename must never end with `footprint() > capacity()`; a same-directory rename under
  allocation failure must leave the source where it was.

### `writable_len` and `stream_len` say yes where the write says no

Both accept a claimed destination - `Some(Node::File(existing)) | Some(Node::Claimed(existing))` at
`:470` and `:1291` - and report the space a write would have. `write_file` and `stream_begin` refuse a
claimed path with `Exists`.

So a caller can ask "may I write here, and how much" during another caller's open stream, be told a
number, prepare that payload, and be refused. Not a data-loss path, and it is the same class this
milestone has closed twice: a preflight that answers a question the operation behind it will answer
differently.

- [x] **Answer `Err(FsError::Exists)` for `Claimed` in both,** which is what the operation does. The
  two arms are currently merged precisely because the shape is the same; the answer is not.

### The property model does not draw the new operations

`a_random_workload_never_breaks_the_invariants` runs ten thousand steps and picks `rng.next() % 6`
(`src/fs/libermemfs/src/tests.rs:459-466`): write, write-empty, mkdir, remove, rmdir, read. `rename`,
`truncate` and `touch` are not in it, and a search of that file finds no direct call to either new
mutator at all.

That is the mechanism behind everything above. The model is what enforces "footprint never exceeds
capacity" and "a refused operation changes nothing" across the paths it draws from; the two paths it
does not draw from are the two that broke both rules.

- [x] **Add `rename`, `truncate` and `touch` to the model,** which means the operation count and a
  second path for rename. The invariants it already asserts after every step are the ones these two
  violate, so this is the test that would have found all six findings above.

- [x] **And deterministic unit tests for each,** since the model proves invariants and not semantics:
  truncate up, truncate down, truncate past `MAX_FILE_BYTES`, truncate on a `Reserved` volume that
  refuses, rename within a directory, rename across directories, rename onto an existing name, rename
  of a missing file.

## Fifth audit (2026-08-15)

An outside review of LiberMemFS after the fourth audit's fixes. It confirms nine of them as properly
implemented and raises four points: one residual defect in `truncate`, one inconsistency beside it,
one inaccuracy in the random model, and three regression tests that do not exercise what their own
comments claim. All four hold. All four are fixed.

The fifth thing is what happened while fixing the third.

- [x] **`truncate` allocated for a grow the caller had just proved allocates nothing.**

  DONE 2026-08-15, and it was an internal contradiction rather than a subtle race. The outer
  `truncate` charges `bytes.capacity()`, so for 20 bytes in an 80-byte buffer a grow to 40 changes
  the footprint by nothing - and its own comment says exactly that, in the sentence explaining why
  it reads `capacity` and not `len`. `truncate_swap` then branched on `len` alone, took the growing
  path, and built a fresh 40-byte Vec.

  So the two halves disagreed about whether an allocation was about to happen; on a tight heap that
  disagreement was a `NoSpace` for memory the volume was already holding, and on a Reserved volume
  the caller kept its reservation for an allocation that then occurred. The 20-in-80 shape is not
  exotic - it is what `write_file` deliberately produces, because a partial overwrite keeps the
  high-water buffer.

  Longer than the contents and inside the buffer now extends in place. Only a grow past the buffer
  builds a new one.

- [x] **The shrink adopted whatever the allocator returned without measuring it.**

  DONE 2026-08-15. `try_reserve_exact` promises AT LEAST what was asked for - the sentence the grow
  path immediately below is built around, which is why it measures `grown.capacity()` before
  swapping. The shrink path took `smaller` on faith. A generous allocator answering a shrink with a
  block larger than the buffer already had would have made a SHRINK raise the volume's footprint.
  The same discipline, applied to the same uncertainty, in the same function.

- [x] **The random model said a truncate costs its length, and that stopped being true.**

  DONE 2026-08-15, and the model FOUND THE FIX rather than needing to be told about it: with the
  in-place grow in place, step 1511 of the ten-thousand-operation run disagreed with the volume by
  four bytes.

  The model held one number per file - what the volume is charged - which was enough while every
  write path rebuilt the buffer at the size asked for. A truncate has three cases and only two of
  them do that: shorter than the contents rebuilds at the new size, longer than the buffer builds a
  new one, and longer than the contents but inside the buffer allocates nothing. Telling those apart
  needs the length AND the charge, so the model now carries both.

- [x] **Three regression tests did not exercise what their comments describe.**

  DONE 2026-08-15, and the review is right about all three.

  The `len`-versus-`capacity` fixture made its gap with `truncate(20)` - which closes it, because a
  shrink rebuilds the buffer at the new size. By the time the test grew back to 40 the file was 20
  bytes in a 20-byte buffer and the grow genuinely had to allocate. It passed, and not for the
  reason it gave. The gap is now made with a partial `write_file`, which is the path that keeps the
  high-water allocation, and the footprint before and after the grow is asserted to be equal - so
  "this allocates nothing" is checked rather than described.

  The reservation case asked for more than the volume holds, which the capacity precheck refuses
  before the reservation is touched at all. The case the fix was about is a grow the check ALLOWS
  and the heap then refuses.

  The same-directory rename test ran on an ordinary heap, where the second allocation simply
  succeeds - so the broken code would have renamed the file correctly and every assertion would have
  held.

  Both are now BUDGET SWEEPS rather than single points, for the reason this tree has learned twice
  before: a budget tuned to today's allocation sequence stops testing the moment the sequence moves,
  and the test goes quiet rather than red. Each asserts a property that holds at every budget - the
  rename is atomic, and a Reserved volume's footprint plus its reservation is its capacity - rather
  than a particular outcome at a particular number.

- [x] **AND THE PART THAT MATTERS MOST: I could not make either sweep fail on the old code.**

  This is the result of trying to prove the point above, and it is worth more than the tests.

  With the pre-fix `rename` restored - `remove` with its shrink, instead of `take` - the sweep passes
  at every budget from 0 to 512. Three fixtures were tried. The reason is arithmetic that nobody had
  written down: `shrink_children` fires only at or below a quarter occupancy and sizes the new table
  EXACTLY to the contents, and every `remove` in the fixture shrinks as it goes - so by the time the
  rename runs, the table is already tight, the reserve grows it by one, and after the take the
  occupancy is too high for the shrink to fire at all. The insert then needs no allocation and the
  defect cannot happen.

  The same is true of the reservation case: with the resync moved back behind a `?`, the sweep still
  passes at every budget to 2048.

  So the honest statement about both fixes is this: they are STRUCTURALLY right - `take` removes the
  possibility by construction rather than relying on the shrink policy's arithmetic never lining up,
  and a resync that always runs cannot be skipped by a return path - but neither repaired a defect
  anybody has shown to be reachable through the public API. The tests are better than what was there
  and assert real invariants; what they are not is proof that the old code was broken.

  A fix for an unreachable defect is still worth having when it is this cheap, because the thing
  that made it unreachable is an accident of two policies' arithmetic and neither was written to
  guarantee it. What is not worth having is a completion note claiming a test pins a bug it cannot
  reproduce - which is what this document would have said if nobody had tried.

- [x] **Decide whether the shrink policy's arithmetic is a guarantee or an accident, and say which.** DECIDED 2026-08-15: **a guarantee**, and made one.
  The finding above rests on `shrink_children` never leaving a table too small for the insert that
  follows it, which is true today because of how `MIN_SLOTS`, the quarter-occupancy window and the
  exact-fit resize interact. Nothing states it, nothing tests it, and a change to any of the three
  could make the old `rename` shape reachable again - except that shape is gone. What is left is a
  property several other call sites lean on without knowing it.

  Checking it showed the exact-fit resize does not actually provide it: a table of a hundred entries
  shrunk to a capacity of a hundred has no room at all, and the next insert allocates. What made it
  look true is that the callers reaching that path had small tables. So `shrink_children` asks for
  the headroom instead of hoping for it - `len + 1`, floored at `MIN_SLOTS` - and the guarantee is
  stated at the function, asserted in debug, and pinned by a test that fills a directory past
  `MIN_SLOTS`, empties it into the shrink window, and inserts. One slot is what the property needs
  and all it needs: it is about the insert that FOLLOWS a shrink, not about a run of them.

## Reopened by the sixth audit: two invariant gaps and a set of comments that outlived their code

An outside audit of `src/fs/libermemfs`, 2026-08-15. It confirms the fifth round's fixes are real -
growth through `truncate()` inside an existing buffer, the shrink that no longer trusts
`try_reserve_exact` blindly, the randomised model that now covers truncate, the late-OOM tests, and
`shrink_children`'s real headroom guarantee - and its two new findings are both places where the rule
this milestone states is not quite what the code enforces. Each was checked against the source.

- [x] **A refused `stream_begin()` can leave a Reserved volume short of its reservation.** Two failure
  branches call `self.resync_reservation()` while an allocation they made is still alive and not yet
  counted: after `owned.extend_from_slice(path)` succeeds, the `owned_name.try_reserve_exact(..)`
  failure and the `placed.is_err()` failure (`lib.rs`, the `is_new` block) each resync and return.
  At that moment `owned` - and in the second case `owned_name` - is a live local, not in
  `self.pending` and not in the tree, so `footprint()` does not see it. The resync therefore tries to
  take back the whole declared free capacity while part of the heap is still held by memory nothing
  is accounting for, and on a tight heap the regrow comes up short. The locals drop at the `return`
  and no second resync ever runs, so the volume ends with the tree unchanged, the call answering
  `NoSpace`, and `reservation_intact() == false`.

  `write_file`, `truncate` and `stream_commit` already get this right by letting temporaries die
  before resynchronising, and the documentation states that every refusal restores the invariant. The
  clean fix is the same shape: `stream_begin` releases, calls a `stream_begin_unsynced` helper whose
  locals are gone by the time it returns, then resyncs unconditionally. A regression test has to
  sweep the heap budget and check `reservation_intact()` after every refused `stream_begin`.

- [x] **`MAX_METADATA_BYTES` is checked before the growth, not against the result.**
  `room_for_an_entry` (`lib.rs:694`) is
  `self.root.count() < MAX_ENTRIES && (self.metadata_bytes() as usize) < MAX_METADATA_BYTES`, and the
  `insert` that follows does `children.try_reserve(1)` - which may double the table rather than add
  one slot. So an insert can be accepted below the ceiling and finish above it, with no post-check
  and no rollback: the "hard ceiling on live and retained directory tables" is a ceiling on the state
  before the allocation.

  The same check errs the other way too. At exactly the boundary it refuses an insert into a table
  that already has a free slot and needs no new metadata allocation at all. And `rename` does not use
  it - it does not change the node count - while still reserving the destination table and possibly
  growing its capacity. Decide the rule against the RESULTING capacity, and let an insert that needs
  no allocation through.

- [x] **Four comments and one document now describe behaviour the code does not have.**
  `docs/LIBERMEMFS.md:210` still says `/a/b/`, `a//b` and `a/b` name the same thing, while the
  implementation correctly refuses an empty MIDDLE segment as `BadName` - the Storage ABI and this
  milestone carry the new rule and the filesystem's own document does not. The document also still
  says a Capped buffer is held until the file is removed, where an explicit `truncate()` now compacts
  fallibly and can return quota without a remove. The `Pending` comment block describes a `name`
  field "allocated at begin and moved into the tree at commit" and a `None for a replace` state, and
  the struct's fields are `path`, `data`, `placeholder`, `offered` - there is no `name`. And a rename
  test's comment claims a budget exists at which a broken implementation leaves the file in neither
  the source nor the destination, which is the opposite of what this milestone measured.

  Grouped as one item because they are one habit rather than four mistakes: after a series of fixes
  the comments were not re-read, and this milestone has already been reopened once by a comment that
  outlived its code.

- [x] **A huge `truncate` would answer `NoSpace` rather than `TooLong` on a 32-bit target.** The
  length is narrowed before it is compared, so the size check cannot see a value that does not fit a
  `usize`. No 32-bit target exists here today, which is exactly why it costs nothing to fix now:
  compare against the declared maximum in a width that can hold it, then narrow.

### Resolution of the sixth audit's four findings (2026-08-16)

**`stream_begin` resynchronises once, after its temporaries are gone.** The body moved to
`stream_begin_unsynced` and the public entry point calls it and then resyncs unconditionally - the
shape `write_file`, `truncate` and `stream_commit` already had. The release stays INSIDE the body,
at the point where allocation begins, so a refusal that allocates nothing (a bad path, a directory,
no room for an entry) never drops the reservation and never acquires the window in which a tight
heap could decline to give it back.

THE REGRESSION TEST WAS CAUGHT PASSING AGAINST THE DEFECT, which is the part worth recording. The
first version swept 640 budgets around a 4 KiB volume and produced not one refused `stream_begin`:
a stream releases the whole reservation before it allocates, so on a volume much larger than its
path there is always room and no failure branch is ever taken. It was green, it proved nothing, and
only restoring the old code and watching it stay green showed that. The rebuilt test uses a 520-byte
volume against a 255-byte path and the same 255-byte name, so the second `try_reserve_exact` is the
one that runs out - and it asserts `refusals > 0` for exactly this reason. Against the original
shape it now reports `a refused stream_begin left the reservation short at 86 of 86 refusal(s);
first: slack 128, footprint 0, reserved 0 of a 520-byte capacity`.

**The metadata ceiling is decided against the resulting table.** `room_for_an_entry` now takes the
destination path, finds the table the entry would go into, and asks `metadata_admits_a_slot` - which
admits an insert into a table with a spare slot outright (it allocates nothing, so no ceiling has
anything to say about it) and otherwise charges what `Vec` will grow to. `grown_capacity` predicts
that growth - double, then the small-table floor by element size - and
`a_full_table_grows_the_way_the_metadata_ceiling_predicts` checks the prediction against a real
`Vec`, so a change in the standard library's growth policy is a failing test rather than a ceiling
that quietly stopped holding. `rename` now asks too, through `room_for_an_entry_by_bytes`: it does
not change the node count, which was read as "no entry check applies", while it still grows the
destination's table - the one mutator that could drive the retained tables past the ceiling one move
at a time.

The rule is tested as a pure function of four numbers, and that is not a convenience.
`MAX_METADATA_BYTES` is four times the whole node budget and `shrink_children` keeps every table
within a factor of four of its contents, so a volume driven through the public API cannot be brought
to its own ceiling - the count limit stops it first, by design. A test that filled a volume and
watched it refuse would be measuring `MAX_ENTRIES` and reporting it as evidence about
`MAX_METADATA_BYTES`. Both halves are covered: the unit test at the ceiling, and an end-to-end test
that checks the tables after EVERY accepted entry.

**A length no volume could hold is `TooLong`.** `truncate` compared the bound in `u64` before
narrowing, and both refusal paths now answer `TooLong` - which is what actually makes the fix hold,
because no ordering of two `TooLong`s can produce `NoSpace`. The test says so and says what it
cannot reach: on a 64-bit host `u64::MAX` fits a `usize`, so this run cannot distinguish the two
orderings, and claiming it pins the order would be the test asserting more than it checks.

**The four comments and the document.** `docs/LIBERMEMFS.md` no longer says `a//b` names the same
file as `a/b` - a middle separator is `BadName`, and the document now records that leading and
trailing ones are tolerated by DECISION rather than by oversight. It also no longer says a Capped
buffer is held until the file is removed: `truncate()` compacts, fallibly, and returns quota without
a remove. The `Pending` block described a `name` field the struct has not had for two revisions; it
now says where the name actually lives (in the tree, as the `Claimed` entry) and why `footprint()`
must not count it twice. And the rename sweep's comment claimed "the broken code has a budget at
which it is at NEITHER" - measured, and false: with the old shape restored the sweep passes at every
budget from 0 to 512. The comment now says that, says why (`shrink_children` cannot fire at the
occupancy the fixture leaves), and says the fix is still worth having for being structural rather
than for repairing a reachable defect.

Verification: `libermemfs` 65/65, with each of the three code fixes watched to fail first.

## Fourth audit (2026-08-16): `AI/audit/libermemfs.md`

Five findings, three Medium. The first is confirmed by counting.

- [x] **Heap pressure is reported as configured volume exhaustion (MEMFS-001).** VERIFIED BY
  COUNTING: `NoSpace` appears 52 times in the crate and `NoMemory` appears ZERO times - while
  `fs/core` documents `NoMemory` with the reason it was added, that the two "drive opposite
  policies: `NoSpace` says delete something or use another volume, `NoMemory` says the storage
  service is under pressure and the same request may well succeed in a moment". `read_file` and
  `list_entries` are the clearest cases: they add nothing to the volume and still answer that it is
  full. The existing fail-budget tests assert the conflation, so they change with the fix.
- [ ] **`rename` under `Policy::Reserved` allocates beside its own reservation instead of drawing on
  it (MEMFS-002).** Every other mutator releases the reservation first; rename can therefore fail an
  operation that fits, by competing with memory the filesystem itself is holding.
- [ ] **Accounting charges requested bytes rather than actual container capacity for names and
  reservation chunks (MEMFS-003).** `capacity` then stops being a truthful heap bound, and the model
  test cannot see it because it reproduces the same `len` accounting.
- [x] **The per-file byte ceiling returns `TooLong`, which is documented for names and paths, rather
  than `TooLarge` (MEMFS-005).** VERIFIED at `write_file`: `if data.len() > MAX_FILE_BYTES { return
  Err(FsError::TooLong) }`. A caller told `TooLong` may reasonably shorten the path, which cannot
  help.
- [ ] **One leading and one trailing empty path component are deliberately accepted (MEMFS-004).**
  Same cross-backend question as ISO-002 and UDF-005: decide it once at the Storage API boundary
  rather than per backend.

### Resolution of MEMFS-001 and MEMFS-005 (2026-08-16)

**A refused allocation is `NoMemory`; a capacity check is still `NoSpace`.** The split is
mechanical: eighteen sites moved - thirteen `try_reserve*(..).map_err(..)` and five
`try_reserve*(..).is_err()` guards - and the twenty-eight explicit capacity refusals stayed exactly
as they were. `fs-core` grew `NoMemory` because the two drive opposite policies, and this crate used
`NoSpace` 52 times against zero uses of `NoMemory`.

THE FAIL-BUDGET TESTS ASSERTED THE CONFLATION, as the audit said they did, and they are the evidence
the fix reaches the paths that matter: six of them - a read, a listing, two reserved mounts, a
growth and a stream push - now require `NoMemory`, and the rest still require `NoSpace` because
their refusal is genuinely the volume being full. The listing case aborted the whole suite before it
was updated, because `assert_eq!` formats its failure inside a 512-byte budget.

`map_fs_err` in StorageService needed no change: it already distinguished them and its comment
already said what this fix makes true - "the filesystems no longer conflate them, so the distinction
exists to be surfaced when the protocol grows one". Growing that word is IDL-006.

**A file-size ceiling answers `TooLarge`.** Six byte-count refusals moved - whole write, owned
write, two stream paths and truncate's two - and the two PATH limits kept `TooLong`, which is what
`fs-core` documents it for. A caller told its path was too long for a refusal about the file's
length is being sent to shorten something that cannot help.
