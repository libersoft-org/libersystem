# P02M0138 - PermissionManager changes must select the tests that exercise them

Status: TOOLING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Make a change to `src/user/services/core/src/permission_manager.rs` select the kernel tests whose
assertions can detect a regression in PermissionManager's contract.

The current public plan identifies the changed component as `bin.permission_manager` and emits nine
build keys, but it selects zero kernel tests. The command layer consequently adds an unenumerated
x86_64 full-suite boot whose result cannot be attributed to individual test keys. That is a coverage
correctness failure, not merely a performance problem.

This milestone uses the coverage and selection machinery completed in P02M0118; it does not reopen
or redesign that machinery. It follows P02M0137 in roadmap order but has no technical dependency on
the dynamic-report fix.

## Coverage rule

`covers = ["bin.permission_manager"]` is justified only when the test contains an assertion that can
detect a regression in PermissionManager's contract. Calling `run_permission_scenario` or launching
the binary is not sufficient.

Every new declaration therefore needs a watched-fail probe: make one narrow temporary production
mutation, prove that the intended assertion fails for the intended reason, then restore the mutation.
A boot failure, missing artifact, unrelated panic, timeout or parser failure is not evidence that the
assertion covers PermissionManager.

Every mutation was applied to `src/user/services/core/src/permission_manager.rs` alone, rebuilt with
`./build.sh --arch x86_64 --part user,packages,volume`, and the candidate run by itself through
`TEST_SELECTION`. The mutated source, the staged `permission_manager` executable, the init package
and the boot volume were hashed for each round, and a round whose staged executable matched the clean
one was discarded rather than believed - otherwise the guest would have been running the unmutated
artifact and its "failure" would have proved nothing. After every round the source was restored and
the staged executable rehashed back to the clean value. Raw logs and hashes are in
`.build/benchmarks/permission-coverage/`.

Two classes of result were rejected as evidence rather than recorded as inclusions:

- Widening `sandbox_probe`'s static grant to `Network` made `run_permission_scenario` itself return
  `Err("governed ip did not query its fresh NetworkService client")`. C02, C03, C09 and C12 then
  "failed" at their `.expect(...)` on the helper. That shows the mutation reached the guest and
  nothing at all about what those tests assert, so all four went back to undecided and were probed
  again with mutations that leave the fixture intact.
- Dropping `Display` from `graphics_probe`'s manifest removed an admin request and shifted every
  later correlation id, so `imgview` failed the scenario before C03 was reached. The mutation that
  decided C03 leaves the `open_streams()` call - and therefore the reply sequence - exactly where it
  was and only discards the handle.

C03 needed two repairs to its oracle before any mutation could reach it, which M1.3 requires for a
mandatory direct-policy test. `run_permission_scenario` turned both an empty read from
`graphics_probe` and a refused `graphics_probe` launch into scenario errors, so the one test whose
purpose is to assert what those scoped grants are could never see a narrowed grant: the helper
judged first and reported a broken fixture. Both are now carried out as observations. A malformed
reply is still a fixture error, because that is the transport rather than a decision.

C09's inclusion rests on argument forwarding rather than on a grant, because every grant mutation
that stops `which` running aborts the scenario at the command-tools stage, which runs before the
shell session that produces what C09 reads. The evidence is a genuine PermissionManager decision; the
narrowness is a property of this fixture's staging, and P02M0139 is what makes the stages
independent.


## Correction (2026-08-19): the regression did not lock the real declarations

An outside review pointed out that the planner regression is hermetic on purpose - it writes its own
suite and puts `bin.permission_manager` on it, which is what stops it agreeing with the declarations
by construction - and that nothing therefore failed if the declaration was deleted from the tracked
`applications.rs`. That was true: the zero-selected-tests defect this milestone exists to fix could
have come back without a single test going red.

The lock is in the cohort audit, where it reads the declaration in the place the planner reads it.
Each `declare_permission_cohort` marker is now resolved to the `tagged_test!` carrying that stable
id, and that declaration is required to cover `bin.permission_manager`. Watched on the real tree:
removing the entry from one member makes `verify-model check` exit 1 naming that member. Two unit
tests cover the same two failures over the hermetic fixture.
