# P02M0179 - A run that ends says so, and a run that stalls says so while it is still stalling

Status: COMPLETE (2026-09-13). TOOLING CORRECTNESS. NOT A PHASE-2 COMPLETION GATE, and not a feature of the system
being built: it is a defect in the build and test INTERFACE, and it costs whoever is watching.

## Goal

Make "has this run finished, and how did it end" a question that is answered by looking in ONE place,
in ONE shape, for every entry point - and make a run that has stopped making progress say so while it
is still happening rather than at whatever moment somebody next looks.

## What is there now, and what it costs

THE GUEST TEST PATH IS ALREADY RIGHT, and it is the model for the rest. `src/harness/test-kernel.sh`
carries a per-target stall watchdog with its window beside the wall-clock budget, counts COMPLETED
tests from the runner's own `<id>...[ok]` lines rather than from the string `[ok]` appearing anywhere,
kills only its own guest and only by pid, and ends with `PASS: ...` or `FAIL (exit N, Ns)`. Nothing
about a guest run is ambiguous.

Everything above it is ambiguous, and in three separate ways.

- **A FAILURE HAS NO VERDICT.** `build.sh` announces success (`built: <parts> for <archs>`) and
  announces failure with whatever the tool underneath it happened to print. Measured on 2026-09-13:
  a build failed in nine seconds with `build-shared: Cargo image graph did not stop after emitting
  its ET_REL seed object` and `status=1`, and was waited on for THIRTY MINUTES, because the thing
  watching the log was watching for words and those were not the words. A failed run and a running
  run produced the same observable: a log that had stopped growing.

- **EVERY ENTRY POINT ENDS DIFFERENTLY.** `build.sh: built: ...`, `check.sh: all selected checks
  passed`, `[test-x86_64] PASS: ...`, `gen.sh: no drift: ...`. Failures more so: `error[E0603]`,
  `build-shared: ... status=1`, `... did not stop after emitting its ET_REL seed object`,
  `test.sh: the x86_64 build does not match the sources`, `warning: build failed`. Anything that
  watches a run has to know every one of those shapes, and the one it does not know is silence.

- **A RUN THAT DIES LEAVES NO MARK.** `verify.sh` was started three times on 2026-09-13 and stopped
  each time at step 2 of 180 with no error line, because the shell that launched it was killed and
  took the process group with it. The log simply ended mid-step. The same absence of a mark means a
  run killed by a signal, by the OOM killer or by a parent exiting is indistinguishable from one
  still working.

- **AND THE BUILD HAS NO STALL WINDOW AT ALL.** `test.sh` takes `--timeout` and the guest runner has
  `TEST_STALL`; `build.sh` has neither. A build that wedges - a lock nobody releases, a compiler that
  does not return - is discovered by a person eventually.

## What this milestone is NOT

It does not change what any check checks, what any suite runs, or which architectures anything is run
on. It changes only how a run REPORTS, and it adds nothing to the critical path: a verdict is one
line and one small file.

## Definition of done (phase 2)

- [x] **M1 - one verdict, one shape, from a trap.** Every entry point - `build.sh`, `test.sh`,
  `check.sh`, `gen.sh`, `verify.sh` - ends with exactly one line in one format:

      <script>: RESULT ok|failed exit=<code> seconds=<elapsed>

  It is emitted from a `trap ... EXIT` and NOT from the bottom of the script, because the runs
  hardest to notice are the ones that never reach the bottom: `set -e` aborting mid-script, a signal,
  a parent exiting and taking the process group. The trap CHAINS onto whatever is already installed -
  `test.sh` and `check.sh` install a guest cleanup on EXIT, and a verdict that replaced it would
  leave a guest holding a disk image.
  DONE 2026-09-13. `run_verdict` and `arm_run_verdict` are in `lib.sh`; all five entry points arm it
  immediately after sourcing, and after `install_guest_cleanup` where that exists.
  TWO WAYS IT LIED BEFORE IT WAS RIGHT, both found by testing the cases rather than the happy path:
    - A SIGNALLED RUN REPORTED SUCCESS. Bash runs the EXIT trap with `$?` still zero after a signal,
      so a shot-down run said `RESULT ok exit=0` - worse than no verdict, because a reader is told it
      succeeded. INT, TERM, HUP and QUIT now exit with the shell's own 128+n convention, and that is
      what the EXIT trap reports: `RESULT failed exit=143`.
    - A CHAINED TRAP REPORTED THE CLEANUP'S STATUS. `trap "cleanup; run_verdict" EXIT` makes `$?` the
      status of CLEANUP, so `test.sh` exited 1 and said `ok` as soon as its guest cleanup succeeded.
      The script's status is captured FIRST and handed to `run_verdict` as an argument.
  VERIFIED, four cases: success (`gen.sh: RESULT ok exit=0`), failure (`build.sh --part nosuchpart`
  -> `RESULT failed exit=1`), signal (`RESULT failed exit=143`), and a chained trap (`test.sh
  --build-only` over a stale image -> `RESULT failed exit=1`).

- [x] **M2 - a status file beside the log, because prose is not a protocol.** When `RUN_STATUS_FILE`
  names a path, the same fields are written there as `key=value` lines. The file's EXISTENCE is the
  signal: it is written when the run ends and is absent while it runs, so "has it finished" is a file
  test rather than a search for words in a log. Interactive runs pass nothing and get the line alone.
  DONE 2026-09-13, verified: `RUN_STATUS_FILE=... ./build.sh --part nosuchpart` writes
  `script=build.sh / outcome=failed / exit=1 / seconds=0`. The write is best-effort and never fails
  the run - a verdict that could itself break a build would be a worse defect than the one it fixes -
  and the directory is created first, because a run can fail before it has built anything to put a
  log beside.

- [x] **M3 - the build gets the stall window the guest runner already has.** `build.sh` takes
  `--stall SEC` (with a default and a `BUILD_STALL` override, matching `TEST_STALL`) and reports a
  build whose log has not grown within the window, naming the step it was on. Progress is counted
  from the build's OWN step lines, not from any pattern that ordinary output can contain - the guest
  runner's `<id>...[ok]` rule exists because counting `[ok]` anywhere let display text hold a hang
  off indefinitely, and the same mistake is available here.
  DONE 2026-09-13. `--stall SEC` and `BUILD_STALL` (default 900, `0` disables), and the progress
  signal is a MARK rather than a log: `build.sh` has no log of its own - its output goes wherever the
  caller sent it - so each step stamps `.build/state/build-step.<pid>` with its own name and the
  watchdog compares that file's age. The `step` helper announces and stamps together, because a step
  that printed without stamping would be a step the watchdog thinks never started.
  IT REPORTS AND DOES NOT KILL, which is the one place this differs from the guest watchdog it copies.
  A guest can be shot down and restarted; a build killed mid-link leaves artifacts nobody can reason
  about. The defect being fixed is not KNOWING, so saying it is the whole fix.
  VERIFIED: a mark aged past the window produces
  `build.sh: STALLED - no step has started for 121s; the last one was 'libs (x86_64)'`, and an
  ordinary build leaves no mark behind - the cleanup is a trap, and the verdict chains onto it.

- [x] **M4 - the failure shapes that exist are named in one place.** `build-shared.sh`'s own refusals
  (`... did not stop after emitting its ET_REL seed object`, a non-zero `summary ... status=`) and
  `test.sh`'s pre-flight refusals (`the <arch> build does not match the sources`) exit through a
  path that produces M1's verdict, so no refusal reaches a reader as prose alone. A gate proves it:
  a deliberately broken build and a deliberately stale image each produce a `RESULT failed` line and
  a status file, and the gate fails if either produces only prose.
  DONE 2026-09-13. M1's trap already covers every exit, including those refusals - what was missing
  was the PROOF, and `src/tools/check-run-verdict.sh` is it, registered in `check.sh` as
  `run-verdict`.
  IT PROVES IT BY MAKING THEM FAIL, which is the only way a gate for this can be worth anything: a
  gate that ran the scripts successfully would prove nothing about the defect, because the whole
  defect lives on the failure paths and that is where the shapes differ. Five cases, each failing
  differently: a script's own `die` in argument parsing, a refused architecture, a successful listing
  (so the gate is not merely proving that everything fails), a SIGNAL - where no code of ours runs at
  all and the EXIT trap is everything - and the status file's existence and contents.
  VERIFIED through `./check.sh --gate run-verdict`, all five green.

- [x] **M5 - the rule is written where the next reader will look.** `docs/TESTING.md` states that the
  state of a run is read from the status file or the verdict line and never by grepping a log, and
  that a detached run must be started with `setsid` so it survives the shell that launched it - the
  three silent deaths above were all the same missing `setsid`.
  DONE 2026-09-13: `docs/TESTING.md` gains "Has it finished, and how did it end", beside the existing
  "Slow, or stopped?" section that answers the neighbouring question for guest runs. It states the
  verdict line and its shape, the status file and what its existence means, the `setsid` rule with the
  three deaths that produced it, and the build's stall window - and it says plainly not to decide a
  run's state by searching a log for words, with the thirty-minute wait that rule comes from.

## Done when

Every entry point ends with one verdict line in one shape, on success, on failure, on `set -e` and on
a signal; a status file exists exactly when a run has ended; the build reports a stall inside its
window rather than after it; a broken build and a stale image are each proven to produce a verdict
rather than prose; and `docs/TESTING.md` says how a run's state is read.

## Explicitly out of scope

Changing what any suite covers, changing any timeout that decides whether a test PASSES, and any
change to the guest runner's watchdog - it is the design being copied, not the thing being fixed.
