# P02M0179 - A run that ends says so, and a run that stalls says so while it is still stalling

Status: REOPENED (2026-09-13). Corrected implementation plan; implementation and acceptance remain
pending. The previous COMPLETE claim and the checked M1-M5 items are superseded by the requirements
below. Existing helpers, watchdog, gate and documentation are a starting point, not completion proof.

This is TOOLING CORRECTNESS, not a product feature or a separate phase-2 completion gate. Registering
its regression check still requires the normal verification catalog and release-set integration.

## Goal and scope

Give `build.sh`, `test.sh`, `check.sh`, `gen.sh` and `verify.sh` one terminal reporting contract for
normal and handled exits, and report a build that stops starting steps while that condition persists.
A failed build previously left only a subordinate diagnostic and was mistaken for a running build;
verification logs also stopped without a terminal result after launcher/process-group termination.
These are reporting defects. Log growth and arbitrary success/error words cannot establish a result.

Preserve the existing build/check selections, refusal rules, exit statuses, verification evidence,
release lifecycle and guest cleanup. Keep the guest watchdog unchanged; its explicit observer
shutdown and the existing interruptible child waits are integration references. Add only small
reporting/cleanup work, with no wait for a stall interval on the completion path.

An in-process trap cannot report the shell's SIGKILL/OOM death, machine loss, or an exit before the
helper is armed. A broken stderr or unwritable status destination can also prevent delivery. Missing
terminal information therefore means pending or unknown, not proof that work is still running.
An independent supervisor for abrupt-death detection is outside this milestone.

## Verified starting point

- `lib.sh` has `arm_run_verdict`/`run_verdict`, but it composes only the EXIT trap present when armed,
  writes the inherited `RUN_STATUS_FILE` directly, and accepts an inherited start time.
- `check.sh` installs guest cleanup after arming and replaces that EXIT trap. `verify.sh` replaces it
  in release, sweep, display, shadow and executor setup; its four direct model-query actions use
  `exec`. `build.sh` replaces/rearms it for mark removal. These paths need one owner for finalization.
- `build.sh` uses its own step mark, which is the right progress source, but does not own/reap the
  observer or its sleeper, polls every 30 seconds, and does not validate its stall setting.
- `src/tools/check-run-verdict.sh` checks argument refusals, a listing, a self-signal and one partial
  status assertion. It does not prove a subordinate build failure, real stale-image refusal, all
  entry points, trap composition, nested ownership, or watchdog timing/lifecycle.
- `run-verdict` is registered in `check.sh` but missing from the verification catalog and frozen
  release-required set. `docs/TESTING.md` and the former completion criteria overstate the guarantees.

## Implementation plan

### M1 - one terminal verdict per invocation, with owned cleanup

- [ ] Replace trap-text extraction/rearming with one small EXIT dispatcher in `lib.sh` and explicit
  registration of the existing named cleanup functions. Arm once near the start of each of the five
  entry points, after `SCRIPT_NAME` and sourcing the helper, before argument handling or other setup.
  Sourcing `lib.sh` alone must not arm traps or claim a status destination. Repeated arming in the
  same owner is idempotent; later cleanup registration must not reset timing or add another verdict.
- [ ] Capture the owner's `BASHPID`, script name and start time privately at arming. Do not inherit
  elapsed-time state. A subshell, command substitution or watchdog inheriting shell variables must
  not finalize the parent. A separately executed entry point arms its own independent invocation.
- [ ] On EXIT, save the original status before any cleanup, prevent recursive/double finalization,
  run all registered cleanup once, then attempt status publication and emit the final line on stderr:

      <script>: RESULT ok|failed exit=<code> seconds=<elapsed>

  `outcome=ok` iff the saved code is zero; elapsed is a nonnegative integer in seconds for this
  invocation. Cleanup/reporting failures must be diagnosed without suppressing later cleanup or
  replacing the original exit code. End with that code even if a cleanup command fails. No callback
  may call `exit` or install another EXIT trap. Keep machine-readable stdout unchanged.
- [ ] Integrate every existing cleanup site through the dispatcher, including failure between
  resource acquisition and the rest of mode setup. Register a callback immediately after acquiring
  its resource, and tolerate partially initialized state. Preserve resource-specific ordering:

  | Entry point/path | Cleanup or process-replacement integration |
  |---|---|
  | `check.sh` | `install_guest_cleanup`, sourced evidence helpers, and existing gate/conformance waits; guest cleanup must coexist with the verdict even for help/argument exits. |
  | `test.sh` | Existing guest cleanup and per-target background/wait paths; preserve ownership of guests started by this run. |
  | `build.sh` | Early argument exits plus later observer, sleeper and progress-mark cleanup from M3, with no second verdict arm. |
  | `gen.sh` | Early listing/help/refusal paths and generator workloads. |
  | `verify.sh` release | `release_prepare`/`release_cleanup`, including failure after snapshot creation and after changing into it; preserve evidence/dossier behavior. |
  | `verify.sh` sweep | Owned worktree removal on success, failure and handled interruption. |
  | `verify.sh` display | `--plan`/`--json` temporary rendered output, including planner failure after its cleanup is registered. |
  | `verify.sh` shadow | Pending-record cleanup and existing shadow completion/failure paths. |
  | `verify.sh` executor | Steps-file cleanup plus release cleanup where applicable, including prepared plans and normal/tier execution. |
  | `verify.sh` model queries | Replace `exec` in `--catalog`, `--model-hash`, `--age` and `--trust` with child execution whose actual status reaches the owner's EXIT dispatcher. |

  Inspect sourced helpers and all `trap`/`exec` sites as part of implementation; the table is the
  current inventory, not permission to leave a later replacement unexamined. Keep guest cleanup
  usable by `run.sh` and other callers that are outside the five verdict entry points.
- [ ] Handle INT, TERM, HUP and QUIT, when delivered with a usable handler, by exiting with `128+n`
  through the same dispatcher. Preserve cleanup rather than overwriting signal behavior. Bash can
  defer traps behind a foreground child: use the existing background-and-interruptible-`wait`
  approach for long external workloads in the five entry points, including model-query commands.
  Keep orchestration/state changes in the owner; wrap leaf commands or pipelines, preserving their
  real status and `pipefail`. On interruption stop and reap the workloads this invocation started,
  using recorded ownership and existing descendant cleanup where needed, before publishing its
  terminal result. Never signal unrelated processes by executable name. This is signal cleanup,
  not a new build timeout. Explicitly test interruption while a child is running, not only a shell
  sending a signal to itself. Signals inherited as ignored are not a trap guarantee.

### M2 - an invocation-owned terminal file with atomic publication

- [ ] Keep `RUN_STATUS_FILE` optional. The caller must provide a fresh, unused destination for every
  invocation, with one writer and no concurrent reuse. Recommend a file inside a new `mktemp -d`
  directory; do not use `mktemp` to pre-create the terminal file. Serial reuse is also unsupported:
  choose a new path. This avoids locks, a run registry, and stale success records.
- [ ] At initial arming capture the request in a private, non-exported owner variable, resolve a
  relative destination against the invocation's original working directory, and unset the exported
  request before starting descendants. Do not derive the path later from `PWD`, `BUILD_DIR` or a
  release snapshot. Descendants keep their own verdict lines but have no status destination unless
  their caller explicitly supplies a different fresh path. Guard inherited subshell state by owner
  identity as in M1; fixture children must never publish into the gate/check wrapper's file.
- [ ] Prepare the parent directory if needed and verify the terminal destination is unused,
  including rejecting a pre-existing regular file, directory or symlink. Do not delete, truncate or
  repurpose an existing destination. Diagnose an unusable or pre-existing destination and disable
  file publication for that invocation; continue the requested work and retain its real exit code.
  Such a destination carries no result for the current invocation, even if old bytes are present.
- [ ] After work and owned cleanup finish, calculate the fields once, write a private temporary file
  in the destination directory, close it and rename it atomically to the terminal destination:

      script=build.sh
      outcome=failed
      exit=1
      seconds=9

  The line and file use the same four values. Do not expose a partial file at the terminal name.
  Publication is best-effort; diagnose failures, remove owned temporary files on handled paths, and
  still attempt the verdict line without altering the work's status. No durability/fsync guarantee
  or multi-writer protocol is required.
- [ ] Define the reader contract precisely: for a correctly allocated fresh destination, a complete
  record means work and cleanup reached terminal finalization. No child may publish it while outer
  work is pending. The shell may still be returning from its EXIT trap when publication becomes
  visible; this is not proof its PID has already disappeared. Absence is inconclusive, including
  during work, SIGKILL/OOM death, or failed publication. Use the launcher's wait/exit information to
  distinguish a live run from an ended run with no result. Never accept an old/reused path as the
  current run's record or treat a missing file as success.

### M3 - report build stalls promptly and stop the observer promptly

- [ ] Preserve `--stall SEC`, `BUILD_STALL`, default 900 seconds, and `0` disabling observation. An
  explicit flag overrides the environment. Validate the effective value before creating a mark or
  observer: nonnegative decimal integer in `0..2147483647`, normalized as decimal (including leading
  zeroes). Reject missing flag values, negatives, fractions, nonnumbers and out-of-range values
  through the normal failed-verdict path; an invalid unused environment value does not defeat a
  valid explicit override.
- [ ] Count only `build.sh`'s own calls to `step`, not child output or general log growth. Use an owned
  progress mark under `.build/state`, initialized with a setup label, and publish a complete record
  on each step announcement. Record a new step generation, timestamp and label together so repeated
  names and multiple changes within one clock tick still reset the observer. Read consistent mark
  snapshots; ordinary compiler output must never postpone the report.
- [ ] Poll at intervals of at most one second when enabled. For a continuously stalled step, emit
  `build.sh: STALLED - no step has started for <age>s; the last one was '<label>'` when the measured
  age reaches the configured window, by window plus two seconds under ordinary host scheduling and
  a stable clock. The allowance covers timestamp granularity and polling; this is not a hard
  realtime guarantee under host suspension or clock changes. State this bound instead of promising
  detection strictly inside the window. Emit once per no-progress episode; every new step generation
  resets/rearms it even if progress happened between polls. A later stall must report again.
- [ ] Report only: do not kill a compiler/build, change its result, or alter guest/test timeouts when
  the window expires. A long legitimate step may need a larger window. Observer startup/runtime
  failure should be diagnosed without replacing the build's real result or silently claiming
  observation is active.
- [ ] Retain the observer PID in the build owner. The observer must retain any sleeper PID, wait
  interruptibly, and terminate/reap its sleeper when stopped. Its local cleanup must not publish a
  build verdict. Register build cleanup before launching the observer; on all handled exits stop
  and reap it and its sleeper, then remove the mark before M1/M2 finalization. Use only owned PIDs.
  A short completed build must not leave output pipes open until the next polling interval. With
  `0`, start no observer/sleeper and require no progress mark for observation.

### M4 - prove the actual failure paths and integrate the gate

- [ ] Expand `src/tools/check-run-verdict.sh` into a bounded host-only regression gate using private
  temporary roots/logs/artifacts. Copy actual entry scripts and shared helpers without altering their
  reporting/control-flow logic; stub only subordinate work/tools where necessary. Do not symlink an
  entry script back into the live tree or corrupt its sources, images, stamps, Cargo outputs or
  verification history. Assert that each intended injection was reached. Reuse `LIBER_VERIFY_STEPS`
  and its existing prepared-plan format without KEY rows for executor fixtures.
- [ ] For every supported terminal case, capture the process's actual exit status and stderr, and
  require exactly one matching RESULT line from the requested invocation. Check its script name,
  expected status, matching outcome, and nonnegative integer elapsed time; compare all four fields
  against its fresh status file. Do not use the last arbitrary RESULT line as proof. Child verdicts
  may exist; capture fixture invocations separately and verify outer identity/count explicitly.
  Exercise the assertion helper with missing/duplicate/wrong-script lines and mismatched fields or
  exit codes so these defects themselves fail the gate.
- [ ] Cover the following cases, using synchronization markers or pipes to observe live work and
  bounded external timeouts to clean up a failing test:

  | Case | Required evidence |

  | All five entry points | Lightweight successful help/list/query paths and failures, with line/file agreement; `check.sh` itself is included. |

  | Cleanup composition | Exercise early and later registrations, successful and failing cleanup, and failure after each resource is acquired. Each cleanup runs once, remaining cleanup/verdict still runs, original status survives, and no owned child/resource remains. |
  | Verification branch inventory | Exercise plan/json with planner success/failure, all four former `exec` actions with success/distinct failure statuses, the prepared-plan executor, and isolated release/sweep/shadow paths after their cleanup registrations. Stub subordinate tools in private roots so no real release or guest suite is needed. |
  | Catchable signals | Drive real long-child paths in all five wrappers, signal the owning shell while it is waiting, and check prompt failed result plus owned-child cleanup.   | Nested status ownership | A prepared `verify.sh` plan runs successful `gen.sh --list`, then waits on a synchronized step before failing.   | Status lifecycle | Relative destination across a directory change; missing parent directory; pre-existing destination left unchanged with a diagnostic; forced publication failure preserving process status; repeated readers never observe partial terminal fields; inherited start time cannot change this invocation's elapsed time. |
  | Abrupt death boundary | Kill only an isolated fixture process/group with SIGKILL and reap it externally. Confirm no terminal record is required and classify the missing result as unknown. This documents the limit, not a passing test of guaranteed crash publication. |
  | Observer lifecycle | Capture short successful, failed and interrupted actual build fixtures with default and short windows. Require output EOF promptly after terminal publication (within two seconds on an ordinarily scheduled host), removed marks and no surviving observer/sleeper. Compare with disabled observation; never wait the configured window for cleanup. |
  | Observer timing | Use a live step with a 1-2 second window; require STALLED while the build is still waiting and by the documented bound. - [ ] Avoid recursive gate invocation: exercise `check.sh` inside the gate using a lightweight path
  and an isolated subordinate gate. An external acceptance driver must also run the registered
  `RUN_STATUS_FILE=<fresh path> ./check.sh --gate run-verdict` and assert that the wrapper exits 0
  with exactly one `check.sh` verdict and its own complete success file, never a fixture's result.
- [ ] Keep the `check.sh` registration and add `("run-verdict", "harness.tools")` to `GATES` in
  `src/tools/verify-model/src/catalog.rs`, updating its array length. Use the existing concrete

  `gate.run-verdict / host / host / default` to
  `src/tools/verify-model/model/release-required.toml` in its established format/order. Existing
  ownership and select-everything rules already cover harness tools/scripts; no new subject,
  planner exemption or release-class exception is needed.
- [ ] After implementation run the expanded gate through its actual wrapper and run
  `./check.sh --gate verify-model`, `./check.sh --gate verify-model-tests`, and
  `./check.sh --gate verify-scheduler`. Verify catalog visibility and the exact release-required key;
  run Bash syntax checks for changed shell files. Existing model validation must pass both gate-set
  and release-set equality. Record actual results here; an argument-only gate or old passing run

### M5 - document the usable contract

- [ ] Correct `docs/TESTING.md` beside the existing completion/stall guidance: the five entry points,
  exact stderr RESULT format and four status fields, supported exits, one fresh destination per run,
  parent/child ownership, best-effort atomic publication, and pending/unknown meaning of absence.
  Explain terminal finalization versus OS process reaping, and use launcher wait/exit information
  when the record is missing. Show a fresh directory example with separate log and terminal paths;
  keep stderr redirected so the verdict is retained. Do not decide completion from arbitrary log
  words or a log that stopped growing.
- [ ] Replace the universal `setsid` survival rule with accurate launch guidance: `setsid` creates a
  separate session/process group and may isolate a run from signals aimed at the launching group.
  Redirect standard streams explicitly for detached work. Shell exit alone does not universally
  kill descendants; launcher cleanup, cgroups, OOM and explicit SIGKILL can still end the run.
  Reliable supervision/reaping belongs to the launcher; `setsid` is not terminal-result insurance.
- [ ] Document the build's default/override/disabled/invalid-input behavior, own-step progress source,
  once-per-episode reporting, window-plus-two-second scheduling allowance, prompt observer cleanup,
  and report-only behavior. Update comments/help that make the same unsupported guarantees while
  implementing their owning M1-M3 change.
- [ ] Keep this checklist and `docs/todo/TODO.md` synchronized. The index is reopened with this plan;
  restore COMPLETE and its checked row only after the corrected implementation and acceptance pass.

## Implementation order and completion criteria

Implement M1/M2 together first, then integrate M3 into that same finalizer. Expand the M4 fixtures
alongside these changes; complete catalog/release registration and validation before marking the
gate integrated. Update M5 to match the implemented contract and record the measured acceptance.

Done means every supported exit of each of the five entry points emits one owner verdict with the
actual exit code after owned cleanup, and a usable fresh requested destination receives the same
complete terminal record atomically. Nested invocations cannot announce their parent's completion.
Missing records remain pending/unknown for unsupported death or delivery failures. Enabled build
observation reports a live no-step interval by its configured window plus the documented allowance,
rearms on real step progress, and leaves no observer, sleeper or capture delay after a handled exit.
The broken-build and stale-image paths, lifecycle/ownership cases and model integration above are
proven, and the reader documentation describes these exact guarantees.

## Explicitly out of scope

Changing suite coverage or architecture policy; changing pass/fail timeouts or the guest watchdog;
killing builds on a stall report; creating a supervisor, status database, heartbeat service or
concurrent-writer lock protocol; guaranteeing delivery after SIGKILL/OOM/machine loss; and validating
all internal `build-shared.sh` refusal detectors. This revision changes planning documents only;
the implementation and its acceptance evidence are still outstanding.
