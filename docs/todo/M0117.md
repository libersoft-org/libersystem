# M0117 - riscv64 (RISC-V) kernel + loader port

Status: COMPLETE. The kernel and its own UEFI loader run on `qemu-system-riscv64 -machine virt` over
OpenSBI, filling in the M0115 architecture contract with the RISC-V mechanisms.

*Condensed 2026-08-08 to the mechanisms a reader needs to orient in the port, and the two defects
that were genuinely hard to find.*

## The mechanisms

| area | how it is done here |
|---|---|
| MMU | Sv39 tables via `SATP`, higher half at `KERNEL_VA_OFFSET = 0xFFFF_FFC0_0000_0000`, 8 GiB direct map; every address space copies the shared high-half kernel megapages |
| Traps | `STVEC` direct mode, `scause`/`stval` decode; a resumable stack-growth fault, a U-mode fault that kills only the process (via the `SSCRATCH` U/S kernel-stack switch), an S-mode fault that halts |
| Timer | S-mode timer through SBI TIME `set_timer` drives the scheduler tick; `rdtime` is the monotonic and fine clock |
| SMP | secondary harts via the SBI HSM `hart_start` call - **the boot hart is not necessarily hart 0** |
| Platform | SBI legacy console, ECAM PCI over the shared `arch::common::pci` |
| Loader | `src/loader/src/arch/riscv64/` mirrors the aarch64 backend over the shared core |

Parity items all closed: the interactive machine gained the graphical display, virtio-input, audio
and second console devices; the suite went from a partial set to running deterministically; the core
count scales to the machine's harts with no compile-time cap; and the boot reaches the full pinned
service set through the interactive shell on the clean production path, with the port-demo tail
retired.

## The disk corruption that was not a disk problem

Fresh-seed virtio-blk writes were corrupting the volume, and it read as a LiberFS or driver fault
for a long time. **The root cause was the riscv trap frame.** `__trap_entry` used `t0` - which *is*
`x5` - as scratch to compute the pre-trap `sp` (`csrr t0, sscratch`, `addi t0, sp, N`) **before**
saving `x5` to the frame, and then stored the already-clobbered `t0` as `x5`.

So every single trap silently corrupted the interrupted thread's `x5`. Any code holding a value in
that caller-saved register across an interrupt got a different value back, which is why the symptom
landed on whatever happened to be running - and why it looked like a storage bug.

The lesson generalises past RISC-V: a trap entry that uses a register as scratch before saving it
corrupts the interrupted context in a way no single subsystem's tests can localise, because the
victim is whoever was unlucky.
