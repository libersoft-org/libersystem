# P02M0147 - A full-screen program is launched without the terminal it is about to take over

Status: OPEN. REPAIR. NOT A PHASE-2 COMPLETION GATE.

## Goal

Give a governed interactive launch the terminal control channel, so a full-screen program can ask
for raw input instead of running cooked with its keys going to the shell.

## What is there now

Measured on 2026-08-23 against a booted development guest, by starting `licoview` and pressing keys.

- **THE PROGRAM RENDERS AND THEN CANNOT BE TYPED AT.** `licoview vol://system/hello.txt` enters the
  alternate screen, hides the cursor, turns on mouse reporting and draws the file. Then `q` - typed
  over the console AND, separately, injected through the emulated keyboard - is ECHOED on the
  terminal and buffered by the shell's line editor. The program never sees it. Nothing quits it but
  Ctrl+C, which reaches it as a signal rather than as input.
- The cause is one missing capability. `rt::tty_set_mode(raw, echo)` asks the terminal over a
  CONTROL channel, and returns false when the program was given none: `licoview` then runs in cooked
  mode, where the line editor owns every keystroke. It was given none because **`permission.run` has
  no way to carry one**: its signature is `run(name, args, cwd, environment, @rights(send) stdout:
  handle<channel>)`, PermissionManager forwards `CAP_STDOUT` and the manifest grants, and there is
  no `CAP_CONTROL` anywhere on that path. Every full-screen tool in the tree - `licoview`,
  `licoedit`, `lico`, `imgview`, `less`, `watch`, `ps -i`, `play`, `audiorec` - is launched through
  it.
- **THE TREE ALREADY DISAGREES WITH ITSELF ABOUT THIS.** `shell.rs`'s `send_stdout` duplicates the
  control channel and sends it as `CAP_CONTROL` for an interactive job - that path is written, is
  commented, and is not the path a governed launch takes. `run_tool_interactive` passes only stdout.
  Two ways to start a foreground job, one of which hands over the terminal.
- The shell's `CONTROL` role gained `handed_on = true` in P02M0146, which is what lets it duplicate
  the channel at all. Necessary and not sufficient: the duplicate has nowhere to go.
- What this cost: `harness/scenarios/terminal-lifecycle.toml` and
  `harness/scenarios/input-events.toml` both fail on every architecture, at the first step that
  needs a program to answer a key. They are the only two scenarios that drive an interactive
  program, and they have been failing for as long as this has been true.

## Work

- [x] **M1 - The launch interface carries the terminal.**
  - `permission.run` takes the caller's tty control channel alongside its stdout. Send-only, like
    the shell's own duplicate: the child ASKS the terminal for a mode, it does not listen in on what
    the shell and the console say to each other.
  - HOW "THERE IS NO TERMINAL" IS SAID is the design question and it has to be answered explicitly,
    because most launches have no terminal to give: a pipeline stage, a background job, a program
    started by the development agent. Whatever the answer is, it is uniform - the number of messages
    in a bootstrap sequence may not vary with whether a capability exists, which is the
    ordered-bootstrap rule this tree has written down four times.
  - The interface change is breaking and goes through `./gen.sh --accept-breaking`.

- [x] **M2 - PermissionManager forwards it, and only where it should.**
  - `CAP_CONTROL` goes to the child in the launch endpoint set, beside `CAP_STDOUT`.
  - NOT TO A PIPELINE STAGE AND NOT TO A BACKGROUND JOB. The terminal belongs to whoever is in the
    foreground; that is the shell's bookkeeping (it is what sets `SET_FG`), and a stage that is not
    in the foreground must not be able to put the terminal in raw mode behind the user's back.

- [x] **M3 - The shell hands over what it holds.**
  - `run_tool_interactive` passes a send-only duplicate of its control channel, for
    `Shape::InteractiveArgs` launches only. This is the same duplicate `send_stdout` already makes,
    so the two paths stop disagreeing.

- [~] **M4 - The two scenarios that could never pass, pass.**
  - x86_64 and aarch64 done; riscv64 runs with the rest of the slow-architecture work at the end of
    the batch it belongs to, which is where every emulated run in this tree is paid for.
  - `lab.py scenario-cold x86_64 harness/scenarios/terminal-lifecycle.toml
    harness/scenarios/input-events.toml` completes both, and the same on aarch64 and riscv64 - the
    runner reaches all three since P02M0146.
  - The evidence is the program answering a key: `q` quits it and the terminal is restored in order.
    A green run that reached the same place by a longer timeout is not evidence.

## Results

Measured on 2026-08-24 against cold development guests.

- **M1.** `permission.run-interactive` is `run` plus `@rights(send, receive) control:
  handle<channel>`. A SEPARATE OP RATHER THAN AN OPTIONAL HANDLE, and the second reason is the one
  that decided it: the generator emits its `@rights` guard only for a bare `handle<...>` parameter -
  `if p.rights.is_empty() || !matches!(p.ty, Type::Handle(_)) { continue; }` - so an
  `option<handle<channel>>` would have carried `@rights(send, receive)` in the schema and NO CHECK
  in the generated dispatcher. A capability boundary that silently stops checking is worse than a
  second op. (That gap is real for any future optional handle and is worth closing on its own.)

- **M2.** PermissionManager forwards it as `CAP_CONTROL` beside `CAP_STDOUT`, and only when it is
  non-zero - `run` passes zero, so a pipeline stage and a background job get nothing, exactly as
  before. The terminal is owned the way `stdout` is: both are released only on the refusal that
  happens before either is forwarded, because past that point they belong to the child.

- **M3.** `run_tool_interactive` passes a duplicate of the shell's own control channel.

- **AND THE RIGHTS SET IS NOT WHAT THE INTENT SAYS.** The duplicate was first narrowed to send,
  receive and wait - the child asks for a mode and reads back a size, and passing the terminal on is
  not its business. The launch then failed with `again`, which the client returns for
  `TransportError::SendRefused`: **a handle is only SENDABLE if it carries `transfer`**, and this
  one crosses two channels to reach the child. Without it the request never left the shell. The set
  is now the same one the stdout duplicate carries.

- **M4.** Both scenarios pass cold: x86_64 - terminal lifecycle 8.4 s, input events 6.2 s; aarch64 -
  59.5 s and 39.7 s. The evidence is the program answering a key: `licoview` renders, `q` from the
  EMULATED KEYBOARD quits it, and the restore sequence follows in order, with no echo of the `q` -
  which is raw mode being in force.

- **AND M4 FOUND TWO MORE THINGS, both in the harness rather than the guest.**
  - **A second rotted expectation.** `terminal-lifecycle` waited for `Tab/pointer panel` from
    `lico`. That string is nowhere in the tree; `lico` draws `lico  two-panel file manager`. Same
    class as `arrows/page scroll` in P02M0146: a scenario asserting text no program has printed for
    as long as anyone can tell.
  - **A PROMPT STEP THAT ACCEPTED A PROMPT FROM BEFORE IT.** On aarch64 the typed command reached
    the shell as `l` and then `icoview vol://system/hello.txt` - two commands, neither of them the
    one the scenario typed. The Ctrl+C a scenario sends over the CONTROL CHANNEL and the keys it
    sends through the EMULATED KEYBOARD are two paths into one console with different latencies: the
    `^C` landed between the first and second letter, discarded the line, and left the rest to run on
    its own. The `prompt` step returned immediately because the prompt from BEFORE the Ctrl+C was
    still the last thing in the log. It now waits for the prompt to SETTLE - the same rule the
    broker path has carried for a long time - so a prompt still being written past is not one to
    type at.

## Definition of done

- A full-screen program launched from the shell owns its terminal: keys reach it, are not echoed,
  and the mode it took is given back when it exits.
- A pipeline stage and a background job get no control channel, and asking is refused.
- `terminal-lifecycle` and `input-events` pass cold on all three architectures.

## What this milestone refuses, and why

- **Bringing back `ESC[?9001h`.** A program's data and its requests were the same bytes, so `cat` on
  a file containing them reconfigured the terminal. The capability replaced it deliberately; the
  fault here is that the capability is not delivered, not that it exists.
- **Giving every launch a control channel.** The terminal is a foreground property. Handing one to
  everything would let a background job take raw mode from under the shell.
- **Letting a program without a terminal fail.** `tty_set_mode` answering false is correct and the
  tools already handle it - a pager on a terminal that will not answer is still a pager. What is
  wrong is that the answer is false for a job that IS in the foreground.
