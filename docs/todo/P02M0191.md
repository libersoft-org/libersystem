# P02M0191 - Port I/O as a capability: a range-scoped authority for userspace drivers

Status: OPEN. It closes when every item below is done.

THE OWNER'S DECISION (2026-09-25): a new milestone that adds the permissions for I/O ports, so the 16550
UART driver P02M0099 lists - and any later driver of an x86 legacy device - can run in userspace like every
other driver here.

WHAT THE MACHINE HAS AND THIS SYSTEM DOES NOT. On x86 a device may be reached through the separate 64 KiB
I/O port space with the `in` and `out` instructions, and ring 3 may execute them only when the task-state
segment's I/O permission bitmap allows that port (or IOPL is raised, which allows EVERY port and is refused
here outright). The kernel today builds no bitmap at all: its own early console writes COM1 from ring 0 and
nothing in userspace can touch a port. ARM and RISC-V have no port space - their "ports" are MMIO - so this
is an x86_64 mechanism with a portable interface shape.

WHY A CAPABILITY AND NOT A FLAG. "May this process do port I/O" is the IOPL answer and it hands out the PIC,
the PIT, the keyboard controller, the CMOS and the PCI configuration mechanism at once. What a driver needs
is ONE range - `0x3F8..0x3FF` for COM1 - so the authority is an object naming a range, minted by the kernel
only for ranges firmware or the platform describes, delegated through DeviceManager with the device claim,
and revoked with it.

## P02M0191 - The mechanism

- [ ] A `PortRange` kernel object: a base and a length inside the 64 KiB space, rights to read and write,
  minted only by the kernel for described ranges (ACPI `_CRS` I/O descriptors once the firmware-node
  identity reads them, and the fixed legacy ranges of devices the platform guarantees - COM1..COM4 - until
  then). No range overlapping one the kernel keeps for itself (the PIC, the PIT, the PCI configuration
  ports) can be minted at all.
- [ ] Enforcement by the hardware, not by a syscall per access: each process that holds a mapped
  `PortRange` has an I/O permission bitmap, installed in the TSS on every switch to one of its threads and
  cleared on every switch away, with the cost of that switch measured and stated beside the design. A
  syscall-per-access fallback is the alternative if the measured switch cost is unacceptable, and the item
  records which was chosen and why.
- [ ] A port outside the process's ranges faults as a general protection fault in ring 3 - a recoverable
  fault that ends the process and nothing else - and a test asserts exactly that, alongside the positive
  case.
- [ ] DeviceManager hands the range over with the claim and takes it back at release; a driver that is
  killed loses its bitmap before any other process runs on that core.

## P02M0191 - The early console handoff

- [ ] The kernel's early COM1 console stays until the userspace driver claims the port, then stops writing
  it; a kernel panic afterwards still reaches the port through a polled path that ignores the driver,
  because panic output that depends on a userspace process is panic output that is lost.
- [ ] P02M0099's 16550 item then binds through this mechanism and is closed there, not here.

## P02M0191 - Verification

- [ ] Kernel tests: a range minted and mapped, reads and writes that reach a QEMU `isa-serial` port, a
  neighbouring port refused with a fault, the bitmap gone after release and after a kill, and two
  processes holding different ranges never seeing each other's.
- [ ] The three cross-builds, with the portable interface compiled on ARM and RISC-V and answering
  `unsupported` there.

EXCLUDES: IOPL; port ranges for devices nobody described; the PCI configuration mechanism, which stays the
kernel's.
