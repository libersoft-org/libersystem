# P02M0191 - Port I/O as a capability: a range-scoped authority for userspace drivers

Status: OPEN. It closes when every item below is done.

THE OWNER'S DECISION (2026-09-25): a new milestone that adds the permissions for I/O ports, so the 16550
UART driver P02M0099 lists - and any later driver of an x86 legacy device - can run in userspace like every
other driver here.

WHAT THE MACHINE HAS AND THIS SYSTEM DOES NOT. On x86 a device may be reached through the separate 64 KiB
I/O port space with the `in` and `out` instructions, and ring 3 may execute them only when the task-state
segment's I/O permission bitmap allows that port (or IOPL is raised, which allows EVERY port and is refused
here outright). The kernel today builds no bitmap at all (every core's TSS points its bitmap offset past the
segment's limit), its own early console writes COM1 from ring 0, and nothing in userspace can touch a port.
ARM and RISC-V have no port space - their "ports" are MMIO - so this is an x86_64 mechanism with a portable
interface shape.

WHY A CAPABILITY AND NOT A FLAG. "May this process do port I/O" is the IOPL answer and it hands out the PIC,
the PIT, the keyboard controller, the CMOS and the PCI configuration mechanism at once. What a driver needs
is ONE range - `0x3F8..0x3FF` for COM1 - so the authority is an object naming a range, minted by the kernel
only for a range a device's row records, handed to the driver by DeviceManager with that device's claim,
and revoked with it.

WHAT IT DEPENDS ON, AND IN WHICH ORDER (2026-09-26):
  - P02M0191a and P02M0191b - the object, its sources, the reserved set and the enforcement - land first.
    Two of the three sources are PCI's (an I/O BAR, a chipset sub-range) and the tests run on synthetic
    device rows, so nothing else is needed for them; source (a) is wired to P02M0196a's platform rows as soon
    as those exist, and the milestone does not close before it is.
  - A DEVICE THAT IS NOT A PCI FUNCTION HAS NO ROW AND NO CLAIM in this kernel: the device table is filled
    from the PCI scan and a claim key is an index into it. The platform device - its row, its claim, the
    kernel's own declaration of COM1 and the `_CRS` rows the ACPI service reports - is P02M0196a's, and so
    are CLAIM-SCOPED WIRED INTERRUPTS: today's only wired path, `SYS_INTERRUPT_BIND`, is gated by the
    DeviceManager privilege and derives nothing from a claim, so a release cannot revoke it. P02M0191c, the
    COM1 handoff, therefore cannot start before P02M0196a's platform-device claim and wired interrupts exist,
    and the 16550's legacy slice waits on both milestones.
  - The 16550 driver itself is P02M0099's 16550 item. P02M0191c and that item land together (the last item
    of P02M0191c says how).
  - AML SystemIO operation regions are governed by P02M0196b's policy for the ACPI service; this milestone
    provides the object and the mint path they use.
  - PCI configuration-register writes for a claim holder are P02M0200's, not this milestone's.

## P02M0191a - The object, where a range comes from, and what is never minted

- [ ] A `PortRange` kernel object: a base and a length inside `0..=0xFFFF`, and NO DIRECTIONAL RIGHTS - the
  bitmap has one bit per port that governs `in` and `out` alike, so a range is all or nothing. Its handle
  carries the ordinary rights (transfer, and the right to map it). It is mapped into AT MOST ONE PROCESS at a
  time, as a `DeviceMemory` window is, and holding the handle grants nothing until the holder maps it - so a
  DeviceManager that mints a range and passes it on never gains port access itself. On aarch64 and riscv64
  every call answers `ERR_UNSUPPORTED` and no row ever carries a port resource.
- [ ] THE MINT SOURCES. A range exists only because a row records it, the caller names it by its index on
  that row and never by address, and the kernel checks it against the reserved set and against every live
  grant both when the row is recorded and again at mint (rows the kernel declares itself are the reserved
  set's one exception, stated there):
  (a) PLATFORM-DEVICE PORT RESOURCES, on P02M0196a's rows: the static tables the kernel parses itself (SPCR,
      DBG2, the FADT-derived devices, WDAT), the kernel's own declaration of COM1 (`kernel:com1`, KERNEL-HELD
      until P02M0191c hands it over), and `_CRS` I/O descriptors the ACPI service reports. The kernel does not
      evaluate AML, so for a reported `_CRS` it cannot know the range really belongs to that device. What it
      ENFORCES is the reserved set, exclusivity, and no overlap with an I/O BAR or a bridge's I/O window the
      PCI scan recorded; the ATTRIBUTION of the range to the device is trusted to the ACPI service, a
      privileged system component, and that trust is stated here rather than implied.
  (b) A PCI FUNCTION'S I/O BARS, which `bar_address` and `bar_size` skip today. The boot scan records every
      I/O BAR of every function on the function's row: its base, and a length sized with the function's I/O
      decode off for the duration of the probe; a BAR whose base or end lies above `0xFFFF` is refused. They
      are minted with the ordinary PCI claim; the claim sets the function's I/O-space enable and the release
      clears it, exactly as bus mastering is handled.
  (c) CHIPSET SUB-RANGES DERIVED BY THE KERNEL. A DERIVATION ROW, keyed by the vendor:device of the function
      whose configuration register holds a block's base, names that register (offset and mask), the block's
      length, the sub-ranges (offset, length) that go with the function's claim, and the conditions under
      which the row applies (a decode-enable bit, the base agreeing with a FADT block, a table whose presence
      suppresses the row). The kernel reads the base once during the boot scan, refuses the row with a line
      when a condition fails, computes the sub-ranges, refuses - with a line - any sub-range that touches the
      reserved set (so PM1, the PM timer and GPE stay the kernel's even inside the same block), and records
      the rest on the function's row. A (c) sub-range NEVER toggles the function's
      decode: the block is the chipset's and the kernel's own registers live in it. This milestone ships the
      table with NO ROWS; each consumer writes its own row (P02M0200 the ICH9 LPC bridge's TCO sub-range).
  AML SYSTEMIO OPERATION REGIONS are not a claim's. P02M0196b's policy decides which regions the ACPI
  service may hold (and the embedded controller's two ports it names); what it holds is a `PortRange` minted
  through a call gated by that service's `FirmwareInterpreter` privilege, with the same reserved-set and
  exclusivity checks. A region over a reserved port is never a `PortRange` - it is served, if at all, by
  P02M0196b's kernel-mediated path.
  WHO MAY ASK, AND NOBODY ELSE: DeviceManager, through a claim handle, for the ranges the claimed row
  records; and the ACPI service, for its regions. The `FirmwareInterpreter` call is the ONLY one that takes a
  base and a length from a caller.
  EXCLUSIVE: a port is in at most one live grant - one claim's range or one of the ACPI service's regions.
  There is NO INTERIM LEGACY RULE: no fixed COM1..COM4 table - nothing guarantees COM2..COM4, and a
  legacy-free machine has no COM1. COM1 exists here because the kernel declares the port it already drives.
- [ ] THE RESERVED SET - every port the kernel drives, and every port that would let its holder start a
  transfer nothing translates, refused at every mint. It has three parts, and the third makes it a set that
  grows while the machine runs:
  fixed: the PIC (`0x20..0x21`, `0xA0..0xA1`), the PIT (`0x40..0x43`) and `0x61`, the CMOS index and data
  pair (`0x70..0x71` - the index port also holds the NMI mask), the PCI configuration mechanism (`0xCF8` and
  `0xCFA..0xCFF`: every byte of it but `0xCF9`, below), fw_cfg `0x510..0x51B` - the WHOLE interface, because
  its DMA address registers would let a holder make the device write any physical memory - the ISA DMA
  controllers' channel and control registers, `0x00..0x1F` (the chipset's alias of the first controller at
  `0x10` included) and `0xC0..0xDF`, for the same reason although the kernel drives neither controller: they
  master the bus untranslated, into the first 16 MiB, for any device on a DMA channel, which is why
  P02M0196a keeps the controller kernel-held; their page registers from `0x81` cannot start a transfer and
  stay mintable, as port `0x80` does, and firmware loses nothing, since ACPICA already denies AML these
  channel and control registers once firmware has seen a Windows `_OSI` - and, in the test build only, the
  exit port `0xF4..0xF7`;
  from the FADT, COMPUTED BEFORE THE BOOT SCAN (`device::init`) AND IN THE TEST BUILD AS WELL, where each
  lies in system I/O at its declared length: the PM1a and PM1b event and control blocks, PM2 control, the
  PM timer, the GPE0 and GPE1 blocks, and the SMI command port - read through `smp::acpi_table`, which both
  builds compile, because source (c) checks its rows against this part during the scan, while the kernel's
  one FADT reader today, `sci::init`, runs in the boot tail after the scan and only in the production build;
  TAKEN AT RUN TIME: when the kernel installs a register for its own use after boot - the system-I/O
  registers P02M0198's processor tables name (`_PCT`, the `_CST`/`_LPI` entry registers, `_PTC`) - the
  install is REFUSED if any of its ports is already reserved or in a live grant, and otherwise the ports JOIN
  the set under the same lock the mint checks, so no later mint can take them; they leave it only when the
  last install holding them is uninstalled. The one exception to the refusal is a register the SAME kernel
  item already holds, which is admitted again and counted - firmware names one `_CST` register in every
  core's table, and a replaced table installs its own again. A later kernel item that starts driving a port
  uses this path rather than a new list.
  COM1 `0x3F8..0x3FF` FOLLOWS THE RUN-TIME RULE. Its ports are in the set from the kernel's first line,
  because the kernel drives COM1 from then on. They leave it when the COM1 claim's `PortRange` is minted at
  the handoff and rejoin it when that grant ends at the release (P02M0191c) - each time in ONE STEP with the
  grant, under the lock every mint checks - so no other mint, the ACPI service's SystemIO regions included,
  can take them while the kernel drives them or in between. The one mint the set does not refuse is
  therefore that claim's `PortRange`, and only after the handoff has flipped COM1's owner.
  ROWS THE KERNEL DECLARES ARE NOT REFUSED BY IT: P02M0196a's kernel-held devices mint nothing - of the
  ports they describe, those the kernel drives and those that could start an untranslated transfer are in
  the set, and the rest (the DMA controllers' page registers) grant nothing through a row that mints
  nothing - and the `kernel:com1` row records COM1's - the one such row that can be
  claimed, its `PortRange` being the one mint above. A description P02M0196a merges into any of them (the
  PIC's or the clock's node, SPCR, DBG2, the `PNP0501` node) adds no range, so the reservation refuses none
  of them.
  FIRMWARE RESERVATIONS NEVER JOIN THE SET. A `PNP0C01`/`PNP0C02` range is a reservation row of P02M0196b's,
  with that step's own rule for the rows published around it, but a mint inside it is governed by this set,
  the claims and the ACPI service's policy like any other: such ranges routinely cover ports nothing here
  drives (port `0x80`, a GPIO block) and whole blocks the kernel keeps only part of - the ICH9 PM block,
  whose TCO sub-range P02M0200 mints through source (c).
- [ ] THE TERMINAL-PATH CATEGORY - ports the kernel writes only on panic, reset or power-off, which MAY be
  minted to a described device and which the kernel then writes in those paths without asking or waiting
  for the holder, because the path ends the machine (the sleep entry, which does not, is P02M0191c's own
  item): `0x64` (the 8042's reset pulse - a PS/2 driver needs
  the port), `0xCF9` (the reset control byte; the processor checks every byte an access covers, so a holder of
  `0xCF9` alone still cannot make the doubleword `CONFIG_ADDRESS` access at `0xCF8`), the FADT's reset
  register where it is a port, the power-off path's fixed fallback ports (word writes at `0x600`, `0x604` and
  `0xB004`, where the FADT does not already reserve them, until P02M0197 replaces them with the FADT's own
  control blocks), and COM1 `0x3F8..0x3FF` WHILE A CLAIM HOLDS IT - while the kernel owns COM1 its ports are
  in the reserved set instead - which the terminal-path writer of P02M0191c uses.

## P02M0191b - Enforcement by the hardware, and revocation that is confirmed

- [ ] DECIDED: THE TSS I/O PERMISSION BITMAP, not a syscall per access. Every core's TSS grows by the 8 KiB
  bitmap and the byte of ones the processor requires after it, and its limit covers both. Each process with a
  mapped range has one bitmap - allocated fallibly on its first map (a map that cannot allocate is refused),
  the union of its mapped ranges, a generation bumped on every change, and its highest set byte - shared by
  all its threads. On every switch to a thread the core compares the incoming process and generation with
  its record (next item): a process with no mapped range gets the bitmap offset past the TSS limit, which
  refuses every port and copies nothing; otherwise the bytes up to the process's highest one are copied (128
  bytes for COM1) and every byte past them is kept all ones. IOPL stays zero by construction: ring 3 is
  entered only with the kernel's fixed initial flags or the flags the processor saved on entry, and `popf` at
  CPL 3 cannot change IOPL. THE COST IS MEASURED, not assumed - a thread ping-pong with and without a
  range-holding process, before and after the change - and stated in `docs/PERF.md`.
- [ ] THE CORE'S RECORD, AND COPIES THAT TAKE NO LOCK. Every switch leaves in the core's per-CPU state what
  the core loaded - the process's object id, which is never reused, and the generation it copied at - and a
  reference to the running process, valid while one of that process's threads is current on the core and
  cleared by every switch to the idle context. The process's lock serializes CHANGES only: a change makes
  the generation odd before it touches the bytes and even again after, and takes no other lock and
  allocates nothing in between (the bitmap is allocated before, on the first map). Every copy - the
  switch's, the service step's and the `#GP` path's below - reads the generation before and after copying
  and retries while it was odd or moved, then records it. A change runs with interrupts masked under the
  process's lock and takes nothing else, so no copy on its own core can run inside it and a copy on another
  core waits at most one change. Every copy still retries only a bounded number of times, since changes can
  follow each other: past the bound the switch and the service step load the refuse-everything state (the
  offset past the limit) and record nothing loaded, and the `#GP` path returns without copying, so the
  instruction faults again - always safe, because a grant not yet loaded costs one more `#GP`, whose path
  copies again. The service step and the `#GP` path find the running process ONLY through the core's
  record - never through `current_thread`, which takes the core's scheduler lock - so `service_pending`,
  which the contended wait of every spin lock calls with interrupts masked, stays lock-free.
- [ ] A port outside the process's ranges faults as a general protection fault in ring 3 - a recoverable
  fault that ends the process and nothing else - and a test asserts exactly that, alongside the positive
  case.
- [ ] REVOCATION IS PUSHED, AND A RELEASE DOES NOT SETTLE UNTIL IT IS CONFIRMED. The TSS is per core, so a
  thread of the process running on another core keeps the old bitmap until its next switch - long enough for
  the next claimant to be driving the device. An unmap or a revocation therefore clears the range's bits as
  one change under the process's lock, RELEASES THAT LOCK, copies again on the local core if it is running
  the process, and only then runs ONE ROUND of the TLB shootdown's own request and acknowledgement (per-core
  generations, the wake IPI, the bounded wait that answers false), whose per-core service step now also
  compares the generation in its core's record with the running process's and, when it moved, copies again
  as above. Because the service step takes no lock, no acknowledging core can be waiting on anything the
  requester holds - the shootdown's own rule - and releasing the process's lock first also keeps the
  process's other changes from waiting out the round. The loaded generation is recorded together with the
  copy, so a switch racing the round is caught by the round's own comparison.
  The revocation answers whether the round confirmed; the whole-TLB flush it costs is paid only on an unmap.
  A range whose round did not confirm keeps its ports out of every later grant this boot, whether a claim
  carried it or the ACPI service held it.
- [ ] GRANTS ARE PULLED, not pushed. A map needs no round - a grant cannot leak authority - but a sibling
  thread already running on another core has not loaded it. So a ring-3 `#GP` in a process with a mapped
  range first compares the generation in its core's record with the process's: if the core is behind it
  copies again and returns, and the instruction retries; only a `#GP` against a current bitmap ends the
  process.
- [ ] A DERIVED OBJECT OF THE CLAIM. A `PortRange` minted from a claim is registered with `register_derived`;
  the release's `revoke_effects_of` tears its mapping out through the round above and answers whether it
  confirmed, and a range whose last reference is being dropped while the release sweeps is counted on the
  claim as an MMIO window is (`settled_mmio`), so it is waited for rather than counted quiet. An unconfirmed
  round ends the claim `Quarantined`, exactly as an unconfirmed MMIO flush does. A killed driver loses its
  bitmap on each core at that core's next switch, and the release that follows the kill confirms it.
- [ ] THE INTERFACE, additive and at version 1: a `PortRange` minted from the claim handle BY KIND AND INDEX
  (the `MANAGE` right, as `SYS_DEVICE_MSIX_ACQUIRE` takes it) - the same call P02M0196a uses for every
  resource of a platform claim, introduced by whichever of the two lands first and given its other kinds by
  the second - map and unmap of a `PortRange` in the caller, and the row's port resources in the
  device-information record. DeviceManager mints EVERY port range the claimed row carries and passes each to
  the driver as a new `PortRange` resource frame, exactly as the MMIO window is passed - no per-driver name
  list decides it. The runtime gains x86_64 `in`/`out` helpers for drivers.

## P02M0191c - The COM1 handoff

What COM1 carries today is more than early boot, and all of it stays on the one wire: every kernel line
(the asynchronous ring the timer and idle loops drain), ConsoleService's mirror of the foreground terminal
(`SYS_DEBUG_WRITE` into that ring), and the shell's serial input (read on IRQ 4, from the idle hook and from
the shell loop, and fed to the console channel). `lab` owns this console, `lab sh` runs over it, and scenario
oracles read the serial log. None of that changes; what changes is who drives the UART.

- [ ] ONE OWNER AT A TIME, AND THE HANDOFF IS THE CLAIM. The kernel's COM1 code gets an ownership state -
  KERNEL, DRIVER with the claim's generation, SLEEP with the claim's generation (the sleep-entry item
  below), or TERMINAL (the terminal-path item below) - held under the
  lock that already serializes the transmit ring. Every kernel access to COM1's registers takes that lock and
  returns without touching the port unless the kernel owns it: the timer and idle drains, the IRQ 4 receive
  handler, the idle-hook and shell-loop polls, and the lossless path's full-ring drain, which then drops the
  byte and counts it. Claiming the kernel-declared COM1 row (P02M0196a's `kernel:com1`, which this item alone
  makes claimable) flips the state under that lock FIRST, then unregisters the kernel's IRQ 4 handler, and
  only then lets DeviceManager mint the claim's resources - the `PortRange`, the claim-scoped IRQ 4
  (P02M0196a) and the console tap - and prints one line naming the claim COM1 went to. COM1's ports stay in
  the reserved set until that `PortRange` is minted, and the mint moves them into the claim's grant in one
  step under the lock every mint checks (P02M0191a), so nothing else can be granted them in between. A byte
  received in between waits in the UART's FIFO and kernel output waits in the ring; from the moment the
  claim returns no kernel path but the terminal-path writer and the sleep entry below touches the port.
- [ ] KERNEL OUTPUT AFTER THE HANDOFF: THE RING STAYS, AND THE DRIVER DRAINS IT. The ring remains the kernel's
  output queue at its 16 KiB bound - kernel lines and every `SYS_DEBUG_WRITE` caller. A CONSOLE TAP, a derived
  object of the COM1 claim passed as a new `ConsoleTap` resource frame, moves bytes out of it in order and
  answers how many the bound dropped since the last read, and the driver writes a one-line marker for a
  non-zero count; DeviceManager mints it from the claim handle as it mints a port range. The tap is
  signalled when the ring goes from empty to non-empty, the way an `Interrupt` is signalled, which is
  already safe from interrupt context. Before serving each console-stream write the driver empties the tap,
  so a kernel line queued before a mirror chunk reaches the wire before it.
- [ ] RECEIVE, THE MIRROR AND THE SERIAL SHELL MOVE TO THE DRIVER'S `ConsoleBytes` PUBLICATION. The driver
  serves IRQ 4 and publishes the port's `ConsoleBytes` under a provider name reserved for the kernel's
  console UART (a `driver_protocol::provider` constant), holding received bytes - bounded at the kernel's own
  512-byte input bound - until a consumer attaches, so a shell that was listening before the handoff loses
  no keystroke to it. ConsoleService subscribes to `console-bytes` through the broker's catalogue and attaches
  to that provider as the development agent attaches to its channel; while attached, its mirror goes out as
  console-stream writes (an `again` answer keeps the backlog, as a partial `SYS_DEBUG_WRITE` does now) and
  received chunks enter `handle_keys` as serial input. When the provider goes away it returns to
  `SYS_DEBUG_WRITE` and to the kernel's console channel, which it never stopped reading, writing its gap
  marker first. While a driver holds the port the kernel feeds no COM1 byte to the console channel; the
  keyboard path and the development channel's serial-marked feed are untouched.
- [ ] REACQUISITION WHILE NO DRIVER HOLDS THE PORT. When the COM1 claim is released - the driver died, was
  stopped, or DeviceManager gave up on it - the release revokes the `PortRange`, IRQ 4 and the tap, and the
  end of the claim's grant returns COM1's ports to the reserved set in the same step, under the lock every
  mint checks. Then the kernel takes the ring's lock, flips the state to KERNEL, and READS OUT WHAT THE
  RECEIVER HOLDS BEFORE ANYTHING ELSE - it clears DLAB, which the driver may have left set, and reads the
  receive register while the line status says data is ready, bounded at 64 bytes, the deepest FIFO a
  16550-family part has - because the boot sequence that follows resets the receive FIFO (its FCR `0xC7`, and
  QEMU also empties the FIFO whenever the FIFO-enable bit changes, as it does after a driver that turned the
  FIFO off). It then re-initialises the UART with its boot sequence (the driver may have left any line
  setting), re-registers and re-routes its IRQ 4 handler, enables the receive interrupt, feeds the bytes it
  read out to the console channel, and prints one line saying COM1 is the kernel's again - in the development
  build with the count of kernel accesses to COM1's registers made while the driver held it, which the handoff
  gate requires to be zero (P02M0191d). The timer and idle drains resume with whatever queued meanwhile; lines
  past the ring's bound are counted and the count is printed. Input typed between the driver's death and the
  release is what the UART's FIFO holds, and the read-out keeps it. A release that ends `Quarantined` still
  returns the port to the KERNEL and its ports to the reserved set - the kernel is not a claimant, and a
  stranded holder can at worst interleave bytes with it - but the row is not claimed again this boot.
- [ ] PANIC, AND EVERY OTHER TERMINAL PATH, IGNORE THE OWNER - AND TAKE THE WIRE BEFORE THEY PRINT.
  `flush_sync` becomes the terminal-path writer, and it is entered BEFORE anything is printed: the panic
  handler in both builds and the kernel-fatal halts - the double fault and a ring-0 exception, which today
  print into the ring and halt without draining it - enter it before their first line, and reset, power-off
  and the test exit before they act. It takes the ring's lock with a bounded wait and past the bound
  proceeds without it; re-runs the UART's whole boot initialisation - interrupt enables off, divisor and line
  settings, the FIFOs enabled and cleared, modem control with loopback off - because a driver may have left
  any register in any state: DLAB set, another divisor, the FIFO off, or loopback on, in which every byte
  sent returns to the receiver and none reaches the wire; polls the transmit-holding register and writes out
  the ring's backlog, then a line with the count the bound dropped when it is not zero; and sets the owner
  to TERMINAL, which is never left. From then on every kernel line goes to the wire synchronously, as in
  early boot, and nothing enters the ring - so the panic text follows the backlog on the wire and can no
  longer be dropped at a full ring, the state a hung driver, or one slower than the kernel's output, leaves
  behind. A driver still running on another core can interleave bytes with it; it cannot withhold the text,
  because nothing in this path waits for it or passes through the ring it drains.
- [ ] THE SLEEP ENTRY IS NOT A TERMINAL PATH, because the machine comes back. P02M0197b's kernel sleep entry,
  which writes its `sleep: entered` line to the wire before the machine sleeps, never enters the
  terminal-path writer and never leaves the owner at TERMINAL. It takes the ring's lock and follows the owner
  it finds:
  - KERNEL: it drains the ring and writes its line synchronously, and the owner stays KERNEL - today's
    `flush_sync` without the terminal state;
  - DRIVER: every binding has answered `SUSPENDED` before the entry (P02M0197a's step 4), so the driver has
    stopped driving the UART, and the entry LENDS COM1 TO THE KERNEL FOR THE SLEEP: it sets the owner to
    SLEEP, re-runs the UART's boot initialisation with the receive interrupt left off - IRQ 4 stays the
    claim's and nothing is read while the machine sleeps - and drains the ring and writes its line
    synchronously. Its last act before it returns is to set the owner back to DRIVER with the claim's
    generation, so later lines queue for the tap. The claim, its `PortRange`, IRQ 4 and the tap are
    untouched throughout, and the development build's count of kernel accesses made while a driver holds
    the port does not include these, since the owner is not DRIVER while they are made. The UART's
    settings are the kernel's after such a sleep, so the COM1 driver's `RESUME` reprograms the UART
    whatever the sleep state - P02M0099's 16550 item carries that step.
  In both cases every kernel line until the entry returns goes to the wire synchronously, `sleep: resumed`
  among them, so the first line is on the wire before the machine sleeps and the second before any driver
  resumes - which is what P02M0197d's suspend-to-idle oracle reads. A panic inside the window enters the
  terminal-path writer as every panic does. Whichever of this part and P02M0197b lands second wires the
  entry to this rule; until this part lands the kernel always owns COM1 and the entry's flush is today's
  `flush_sync`.
- [ ] OTHER PORTS' CONSOLES. This part wires x86_64's COM1 only. P02M0099's handoffs of aarch64's PL011 and of
  riscv64's MMIO 16550 reuse the tap object and the ownership rules defined here, and add the transmit ring
  those ports do not have yet.
- [ ] P02M0099's 16550 item builds the driver on this mechanism and is closed there. This part and that item
  land together, and neither closes until the handoff gate below passes over that driver.

## P02M0191d - Verification

- [ ] THE x86_64 TEST MACHINE GETS A SECOND `isa-serial` (`0x2F8`, IRQ 3, a null chardev), and every test that
  drives a UART drives that one - in loopback (modem-control bit 4), or observed through the test build's
  record of the kernel's accesses to its registers - so the oracle is read inside the guest and nothing is
  written into the log the suite is judged by.
- [ ] Kernel tests of the mechanism, on a synthetic row carrying `0x2F8..0x2FF`: the range minted and mapped,
