# M0145 - The kernel's lowest layers do not yet keep the promises the upper ones make

A fourth-party audit of the kernel, verified against the code at `7352135` on 2026-08-06. It
reports 37 findings across three severities. **Every finding checked against the source held.**
Nothing was hallucinated, and one claim was found to be UNDERSTATED rather than overstated.

The audit's own summary is the fair one: this is not a badly built kernel. Capability handles with
rights and generations, per-process address spaces, resource domains, explicit W^X, quotas,
rollbacks - the design is a real capability microkernel rather than a hobby monolith. What it does
not yet have is the transactional and synchronisation machinery that design REQUIRES once it runs
untrusted ring-3 code on more than one CPU. Several subsystems already assume both.

One correction to the audit, in its favour and against it in one place each:

- **Understated.** The `ET_EXEC` chain is worse than described. Verified end to end: `validate_segment`
  is passed `window = None` for `ET_EXEC`, `AddressSpace::try_map` passes straight to the mapper with
  no half check, the x86_64 syscall entry decides its origin from the SIGN of the return RIP
  (`test rcx, rcx` / `js`), and `user_buf_ok` returns `true` UNCONDITIONALLY when
  `!in_user_syscall()`. All four links exist today. That is a complete privilege-escalation path,
  not a hazard.
- **Overstated, slightly.** The audit says `user_buf_ok` does not confine a buffer to userspace. It
  does - `if end > USER_VA_END { return false }`. Its other three claims about that function are
  exact: no `USER` permission bit, no write permission, and a time-of-check window before the copy.

Ordered by the audit's own phases, which are the right ones.

## Phase 1 - closing the userspace/kernel boundary

Until these are done, untrusted ring-3 code is not isolated. Everything else on this list is a
correctness problem; these are a security boundary that is currently open.

- [x] **An `ET_EXEC` image is not confined to userspace, and the syscall entry trusts an address
  sign.** `elf.rs` computes `window` as `(image_type == ET_DYN).then_some(...)`, so an `ET_EXEC`
  segment is checked for overlap and alignment and against nothing else. `try_map` does not bound
  the address either.

  The exploit chain is complete without any other bug: map an executable page in the higher half,
  jump to it, issue `SYSCALL`. The entry stub reads a negative return RIP, takes the kernel
  self-call path, leaves the user stack in place and sets `FROM_USER = 0` - after which every
  `user_buf_ok` in the kernel returns `true` for any address at all.

  Fixed, with the three independent defences the chain needs and one of them removing the question
  entirely.

  **The origin is no longer inferred.** `syscall_entry` had a ring-0 branch for exactly one caller:
  `invoke`, the kernel's own syscall, which executed a real `syscall` instruction. That caller now
  calls `syscall_dispatch` directly and sets `from_user = false` itself - which is what the AArch64
  and RISC-V ports have always done. With no ring-0 caller left, the stub treats every entry as
  untrusted and the `test rcx, rcx` / `js` heuristic is gone rather than corrected. A ring-0 caller
  reaching a ring-3 entry point is not a thing to detect; it is a thing to make impossible.

  x86_64 needed a `percpu::set_from_user` to do this, which the other two ports already had. It did
  not, precisely because it inferred the answer instead.

  **Every segment is bounded, whatever the image type.** `validate_segment` refuses a start at or
  past `USER_VA_END`, an end past it, and an empty range - before the `window` check, which stays as
  the tighter bound a dynamic image gets.

  **The mapper bounds it too.** `AddressSpace::try_map` refuses a mapping carrying `USER` outside the
  user half, and the infallible `map` asserts the same. That is the narrowest place every user
  mapping passes: the loader, the stack, the fault handler's demand-grown pages and the mmap paths
  all arrive at those two calls. It is deliberately redundant with the ELF check - the ELF validator
  protects against a bad image, and this protects against a bad caller.

  Pinned by a test that builds a minimal `ET_EXEC` and demands it load at an ordinary low address
  and be refused at `USER_VA_END`, one page past it, the canonical higher half, and the top of the
  address space - asserting no frames are left behind each time. It then asks the mapper directly
  for a `USER` mapping at `USER_VA_END` and one page below, which must fail and succeed
  respectively. Reverting both bounds fails it.

  `user_buf_ok`'s `!in_user_syscall() => true` is left as it is, and is now sound rather than
  merely conventional: the only way that flag reads false is a genuine in-kernel dispatch call.

- [x] **User pointer access is not fault-safe and checks the wrong things.** `user_buf_ok` proves a
  page is translatable and nothing more: not that it carries `USER`, not that it is writable for a
  copy-out, and not that it is still mapped when the copy happens - another thread of the same
  process can unmap between the two. The copy is then a raw `copy_nonoverlapping` in ring 0, and a
  ring-0 fault is treated as a kernel bug and stops the machine.

  Wanted: real `copy_from_user` / `copy_to_user` / `read_user_value` / `write_user_value` that check
  U/S and R/W, hold the address space against concurrent unmap (or pin the pages), copy in bounded
  chunks, and have an architectural fault-recovery table so a fault returns an error instead of
  panicking.

  Two of the four are done, and the two that remain are named precisely rather than implied.

  **Done: the permissions.** Every port gained a `translate_flags` returning the leaf's portable
  permission bits - on x86_64 the AND down the hierarchy, because a cleared USER or WRITABLE at any
  level denies the leaf. `user_buf_ok` now requires `USER` on every page, and a new
  `user_buf_writable` additionally requires `WRITABLE`. Present-ness is not permission, and asking
  only whether an address translated let a ring-3 caller hand the kernel a pointer into a page it
  cannot itself reach.

  **Done: the copy-out guard.** `write_user` checks writability before it stores, so a page that
  went read-only after its buffer was validated is not written through - that write faulted in ring
  0, which this kernel treats as its own bug and stops on.

  **Not done: the time-of-check window.** A page can still go away between the check and the copy.
  Closing it needs either the address space held against concurrent unmap or the pages pinned.

  **Not done: the fault-recovery table.** A ring-0 fault on a user address is still fatal rather
  than an error return. That is a per-port exception-table change, and it is why the window above
  cannot be closed by checking harder.

  Pinned by a test over `translate_flags` - a mapped page without USER, a USER page without
  WRITABLE, and an unmapped address - which is the PRIMITIVE the checks are built on. Worth being
  exact: removing the checks from `user_pages_ok` does not fail that test, because it asserts on the
  primitive rather than through a syscall. The syscall path has no test of its own here.

- [x] **The mapper overwrites a live leaf PTE without a word.** `try_map_page_in` writes the leaf
  with `entry.write_volatile(...)` unconditionally. Mapping over an existing mapping silently
  replaces it: the previous frame is leaked, a second load can overwrite the first, two concurrent
  stack faults can overwrite each other, and one loader's rollback can remove another's mapping.
  The hierarchy walk also does not everywhere distinguish a table pointer from a large-page leaf.

  Fixed the overwrite on all three ports: the leaf is read first and a live entry is refused. A
  caller that MEANS to replace a mapping unmaps first, which is the operation that hands the old
  frame back to whoever owns it.

  **Not done, and deliberately separated:** the typed `MapError` and the transactional intermediate
  tables. The refusal is what stops the silent frame loss, and it is worth having on its own and
  now. The error type is a signature change through three ports and every caller, and the
  transaction belongs with the loader rollback in Phase 3 - doing it here would mean writing the
  unwind twice. Both stay open above.

  Pinned by a test that maps a page, demands the second mapping at the same address be refused, and
  then checks the ORIGINAL frame is still the one mapped there - a refusal that damaged the existing
  entry would be no better than the overwrite. It then unmaps and maps again, so the refusal is
  shown to be about the mapping being live rather than about the address.

- [x] **A syscall can ask the kernel for an unbounded allocation.** `sys_channel_send_caps` does
  `alloc::vec![0u8; bytes_len as usize]` before the message is charged to any quota, and
  `MAX_MESSAGE_CAPS` exists while `MAX_MESSAGE_BYTES` does not. The same shape is in `read_bytes`,
  in the ELF load path, and in `wait_any`'s per-count vectors. These are infallible `vec!`
  allocations, so exhaustion is an allocation-error handler rather than an error return.

  Fixed, with one part deliberately left and named below.

  `abi` gained `MAX_MESSAGE_BYTES` (1 MiB - far above the 64 KiB launch context the services
  actually exchange, far below anything that threatens the kernel heap), `MAX_WAIT_HANDLES` (256)
  and `MAX_ELF_BYTES` (64 MiB). Every one of them is checked at the TOP of its syscall, before a
  handle is resolved or a lock is taken: a number that large is not a message whatever handle it
  names, and refusing it costs nothing.

  The wait-set ceiling is fixed rather than derived. It was bounded by how many handles the caller
  holds, and that limit is itself reachable past its own ceiling through `SYS_HANDLE_DUPLICATE` -
  so "as many as you hold" was not a bound at all.

  Every allocation sized from a userspace number now goes through `try_zeroed_bytes` or
  `try_zeroed_u64`, which use `try_reserve_exact` and return `ERR_NO_MEMORY` instead of aborting
  the process through the allocation-error handler.

  **Not done: charging the quota before building the payload.** The ceiling bounds what can be
  asked for and the fallible allocation bounds what happens when the machine cannot supply it, so
  the unbounded-allocation hazard is closed. The ordering the audit asks for - reserve the IPC
  quota, then allocate - is a separate change to `send_charged`'s interface and is left open.

  Pinned by a test that drives three syscalls one byte past each ceiling and demands `ERR_INVALID`.
  It does not assert that an ordinary length still works, and says why: that context has no current
  thread, so an ordinary send cannot reach far enough to tell the size check apart from the thread
  lookup. The rest of the suite sends real messages through these paths in every service test.

## Phase 2 - physical memory and SMP

- [x] **There is no TLB shootdown.** Every architecture invalidates locally only - `invlpg`,
  `tlbi vae1`, `sfence.vma` - and nothing tracks which CPUs an address space is live on, sends an
  IPI, or waits for acknowledgement. A process with threads on two CPUs can have CPU A unmap a page
  and return the frame to the allocator while CPU B still holds the translation and keeps writing
  through it, into whatever the frame becomes next - including a page table.

  Wanted: a per-address-space active-CPU mask, a TLB generation, an IPI shootdown with ACKs, and
  leaf frames released only after the shootdown completes. Teardown can use ASID/PCID generations or
  epoch-based reclamation instead.

  Fixed, deliberately blunt. `mem::tlb::shootdown()` sets a per-core flag on every other online
  core, sends the wake IPI each port already has, and WAITS for every one of them to answer. The
  answering core flushes its whole translation buffer and acknowledges - from the wake-IPI handler
  on x86_64 and AArch64, and from the idle loop on all three, which is the only path RISC-V has.

  Three deliberate choices, each cheaper to reason about than its refinement:

  - **Whole-buffer, not per-page.** The requester does not know which addresses another core
    cached, and a full flush needs no such knowledge. Per-page invalidation is an optimisation of
    this, not a correction of it.
  - **Every core, not an active-CPU mask.** The mask is the obvious refinement and needs
    address-space bookkeeping on every context switch to be trustworthy. Flushing everyone is
    correct without it.
  - **At the point frames are RELEASED, not where a PTE is cleared.** That is the ordering the
    audit asks for - "released only after the shootdown completes" - and it is also what keeps this
    out of deadlock: a core spinning for acknowledgement holds no lock an answering core could
    need. `free_frames` and `Process::drop` both wait before handing anything back.

  The wait is bounded and says so if it expires, because a wedged core must not take the caller
  with it - and the caller here is on the path that frees memory.

  Pinned by a test that drives ten shootdowns in a row and one from an idle machine, asserting they
  RETURN. A timed-out shootdown prints; a completed one is silent, and the suite runs clean on four
  cores with a real shootdown on every process teardown.

  **Not done:** the active-CPU mask, per-page invalidation, and ASID/PCID generations for teardown.
  All three are performance work on top of a correct mechanism.

- [x] **`kstack_ptr` is written both atomically and not.** It is an `AtomicU64` that the scheduler
  reads with `load(Acquire)`, while the context-switch assembly writes the same memory with a plain
  `mov [rdi], rsp` / `str x2, [x0]` / `sd`. That is a data race by the Rust memory model, and on
  AArch64 and RISC-V the plain store carries no release ordering - another CPU can observe a
  non-zero SP and start restoring a register frame that is not globally visible yet.

  Fixed by making the assembly store a RELEASE rather than by splitting the state, and the reason is
  that the slot is ALREADY the publication: `begin_park` writes zero, the context switch writes the
  real stack pointer, and a waker spins until it reads a non-zero one. A second flag would say
  exactly what the pointer already says. What was missing was the ordering, not the signal.

  So: `stlr` on AArch64, a `fence rw, w` before the store on RISC-V, and on x86-64 the plain `mov`
  is left as it is - total store ordering makes it a release already, and the comment now says so
  rather than leaving the next reader to wonder whether it was considered.

  The mixed atomic/non-atomic access stays, and is sound only because both halves are written down
  and kept together: `kstack_ptr_addr` carries the contract - the assembly store is the release, and
  every Rust reader uses `Acquire` - and says that a change to either side has to move the other.

  Not pinned by a test. The failure needs two cores observing a partially visible register frame,
  which the harness cannot force; what can be checked is that all three ports build and the suite
  still passes on x86_64 and AArch64, which is a regression guard and not evidence of the fix.

- [x] **Two last threads can both decide they are not the last.** `sched` counts other live threads
  from a `process.live_threads()` snapshot and calls `mark_exited()` when it sees none. Two threads
  exiting concurrently each see the other, neither marks the process exited, and the process stays
  formally alive forever: `wait` never returns, handles never close, peers never see `PeerClosed`,
  quotas stay held.

  Fixed with exactly that counter. `register_thread` raises it and `thread_exited` lowers it,
  returning true for the one caller that took it to zero - so exactly one thread is told it was the
  last, whatever order they arrive in. A snapshot cannot answer a question about the moment after it
  was taken; a counter can.

  Refusing creation once terminating is NOT done here - it belongs with the process lifecycle state
  machine in Phase 3, where the `Terminating` state it needs is introduced.

  Pinned by a test that registers four threads and reports four exits, demanding exactly one "you
  were the last", and then checks the two-thread case reports it on the second and not the first.
  Reverting to the snapshot count fails it.

- [x] **The frame allocator can deadlock on the heap it feeds.** `FrameAllocator` holds
  `heap: Option<Vec<Run>>` under a global `SpinLock`, and inserting a freed run can grow that `Vec`.
  The global allocator's `alloc` calls `grow()`, and `grow()` calls `frame::allocate()` - so the
  frame lock is held across a path that takes the frame lock again. On one CPU that is a self
  deadlock on a spin lock; across two it is the classic AB-BA.

  The invariant is written down in `frame/mod.rs` and is not true: "the kernel heap never allocates
  frames at runtime (its window is mapped once at boot), so growing the Vec under the frame lock
  cannot re-enter this allocator". `heap::grow` is reached from `alloc` whenever a request does not
  fit.

  Wanted: the frame allocator must not use the heap it supplies - a bitmap, a buddy allocator,
  pre-allocated run descriptors, or metadata in a reserved physical region.

  Fixed by removing the allocator's ability to ask, rather than by replacing it. The run table's
  capacity is reserved ONCE, in `upgrade_to_heap`, and never grows again - so `insert_at` under the
  frame lock cannot call the global allocator, and the cycle has no edge to close.

  A table at capacity refuses the insert and says so on the console, losing track of one freed span
  rather than deadlocking the machine. `MAX_RUNS` bounds fragmentation, not memory: a run is a
  contiguous free span, and a pool splintered into more than 8192 of them is one where something
  else has already gone wrong.

  The comment claiming "the kernel heap never allocates frames at runtime" is gone with the
  reasoning it supported. `heap::grow` is reached from `alloc` whenever a request does not fit, so
  it was never true; the table simply no longer depends on whether it is.

- [x] **Kernel thread stacks have no guard page.** Each thread's stack is a `Box<[u8]>` from the
  kernel heap. An overflow corrupts neighbouring heap objects or allocator metadata and surfaces far
  from its cause. Wanted: stacks mapped in their own VA range with an unmapped guard page below, and
  an emergency stack for double faults.

  Fixed: a `KernelStack` in its own kernel virtual range, frames mapped one page ABOVE the base so
  the base page is never mapped and is the guard. An overflow now faults at the moment it happens,
  on an address that names the thread it belongs to, instead of walking into whatever the allocator
  put underneath and surfacing somewhere else later.

  **Not done:** the emergency stack for double faults. That is an IST/exception-stack change per
  architecture and is its own piece of work.

  Not pinned by a test - deliberately overflowing a kernel stack ends the guest, which is the
  correct behaviour and not something a suite can assert against without a fault-injection harness.
  What is checked is that every thread in the system now runs on one of these, which the whole
  suite exercises.

- [x] **`SpinLockGuard` can be moved to another CPU.** It holds only `&SpinLock<T>` and a `bool`, so
  it is auto-`Send` whenever the lock is `Sync` - while its `Drop` restores the interrupt state of
  the CPU that runs the drop. Moving it re-enables interrupts on the wrong core and leaves the
  original one with interrupts off. Wanted: make the guard `!Send` with a `PhantomData`, and record
  the acquiring CPU in debug builds.

- [x] **A late AP can take another AP's identity and stack.** x86 bring-up uses single global
  statics - `AP_CPU_ID`, `AP_LAPIC_ID` and one trampoline stack - and moves on after a timeout. An
  AP that arrives after the mailbox has been rewritten reads the NEXT AP's identity and stack, which
  can initialise one per-CPU slot twice and run two CPUs on one stack.

  Fixed as a SEQLOCK plus a claim, which gets the same guarantee out of the slots that are already
  there rather than a mailbox per AP. `AP_SEQ` is odd while the BSP is rewriting the identity and
  even when it is stable, so an arriving core can tell a torn read from a whole one; `AP_INVITE`
  names the generation currently open, and a core joins only by winning a compare-exchange against
  it.

  That is what ties the two halves together: the identity a core read and the invitation it is
  answering are checked as one thing. A core whose invitation was superseded - because the BSP timed
  out and moved on, which is exactly the case - loses the exchange and halts instead of joining. The
  BSP also withdraws the invitation explicitly on timeout, so a core arriving in the gap finds
  nothing open.

  Halting is the right failure: it costs one core, and the alternative was two cores sharing one
  stack.

  Not pinned by a new test - forcing an AP to arrive late needs control over bring-up timing the
  harness does not have. What is checked is that the existing `smp_all_cores_online` still reports
  4 of 4, which is the regression this change could plausibly cause and would otherwise pass
  unnoticed with the suite green on fewer cores.

## Phase 3 - capability and lifecycle transactions

- [x] **A capability transfer is a clone followed by a close whose result is ignored.**
  `sys_channel_send_caps` builds every `Capability` under the handle-table lock, releases it, sends,
  then re-takes the lock and does `let _ = table.close(...)`. Two consequences, and the second needs
  no race at all:

  Two threads of one process transferring the same handle both find it valid, both clone, both send,
  and only one `close` succeeds - the other failure is discarded. And a single caller may simply
  list the same raw handle twice in one `SEND_CAPS` array: nothing rejects duplicates, so one handle
  becomes two capabilities. Either way a capability is duplicated without the `DUPLICATE` right,
  which is the capability model's central promise.

  Fixed with `take` / `put_back`, which is the second shape the audit offered and the simpler one.

  `take` REMOVES the capability and bumps the slot generation, so the raw handle the caller still
  holds is dead the moment it returns - there is no window in which it names anything. A transfer
  moves a capability; a move that leaves the source in place is a duplication however the
  bookkeeping is written afterwards.

  The batch takes every capability under ONE lock or takes none, putting back whatever it took
  before a refusal. Duplicate entries are refused outright by a `has_repeat` predicate - that case
  needed no race, just a repeated number in the array.

  A failed send returns them too, which needed a channel change: `send_charged` consumed the message
  and dropped it, and with it the capabilities the sender had already given up. Not duplicated, not
  leaked - GONE, with the sender told only "would block". `send_charged_or_return` hands them back.

  They come back under NEW handles, because their old slots died when they were taken. That is the
  honest outcome of a move that had to be undone, and better than either of the things it replaced.

  Pinned by a test that takes a handle and demands it names nothing afterwards - neither takeable
  nor inspectable - that a returned capability arrives under a different handle, and that the
  repeat predicate answers correctly. Making `take` a clone again fails it on the first assertion.

  **Not done here:** the bootstrap transfer in `SYS_THREAD_CREATE`, which has its own item below,
  and the receive side, which has another. Both need the same `take`/`put_back` pair and are listed
  separately because their failure modes are different.

- [x] **`SYS_HANDLE_DUPLICATE` walks past the handle limit.** `HandleTable::duplicate` finishes with
  `self.insert(...)`, the unbounded variant, while `try_insert` exists beside it. A process holding
  one handle with `DUPLICATE` can exceed `PROP_HANDLE_LIMIT` indefinitely. The plain `CHANNEL_RECV`
  path and some bootstrap paths use the unbounded insert too. "A transfer must always succeed" is
  not an invariant that can hold when the receiving table can be full.

  Fixed for `duplicate`, which is the user-reachable one: it goes through `try_insert` and returns a
  new `HandleError::LimitReached`, which the syscall reports as `ERR_RESOURCE_EXHAUSTED`. A full
  quota is not a bad handle, and the difference is what lets a caller back off instead of assuming
  it was handed something broken.

  The remaining unbounded installs - the plain `CHANNEL_RECV` and the bootstrap paths - are left for
  the transactional receive in this same phase, because that is where "the target has room" stops
  being an assumption and becomes something reserved before the message is dequeued. Fixing them
  piecemeal first would mean writing the reservation twice.

  Pinned by a test that gives a domain a handle limit of four and duplicates until it is refused,
  demanding exactly three duplicates and a `LimitReached` rather than a run that never ends.

- [x] **Receive removes the message before it knows it can deliver it.** `recv_caps` dequeues first
  and only then discovers that the payload does not fit, or that handle quota is short, or that some
  capabilities cannot be installed. A too-small buffer returns an error with the message already
  gone; short quota installs a prefix and drops the rest. Wanted: a peek that reports payload size
  AND capability count, target handles reserved before the dequeue, and an all-or-nothing receive.

  Fixed as asked. `peek_shape` reports the payload size AND the capability count without taking the
  message; the receive checks the buffer, RESERVES the handle quota for every capability, and only
  then dequeues. A message that cannot be delivered stays in the queue, so the caller can come back
  with a bigger buffer or after closing some handles.

  Installing against the reservation uses `insert_reserved`, which charges nothing - the quota was
  paid when the room was booked. The first version called `insert`, which charges, and would have
  billed twice for every capability received.

- [x] **A failed thread creation can lose the bootstrap capability.** `SYS_THREAD_CREATE` moves the
  capability into the child and closes it in the parent BEFORE creating the thread. If the thread
  quota or the stack allocation then fails, the capability sits in the child with no thread to
  receive its raw handle, and the caller no longer has it. Wanted: reserve the thread and the handle
  slot before committing the transfer, or make the whole sequence one rollback transaction.

  Fixed as the rollback transaction, because the capability is baked into the thread's entry context
  and cannot be attached afterwards. The bootstrap is TAKEN from the caller and inserted into the
  child, and if the thread then cannot be made, it is taken back out of the child and put back in
  the caller.

- [x] **The exit status is published before it is written.** Missing from this milestone when it was
  written - the audit reports it as P1-19 and it was dropped in the transcription, which is worth
  recording rather than quietly adding.

  `set_exit_status` did `exit_status_set.swap(true, AcqRel)` and only THEN stored the value, so a
  reader that saw the flag could still read the old status - zero, for every process that had not
  exited before - and report a clean exit for a value that had not been written.

  Fixed by separating the two jobs one flag was doing. `exit_status_claimed` decides who writes
  (first writer wins, unchanged), and `exit_status_set` is released after the value is stored, so a
  reader that sees it sees the status. Two flags are needed because one has to be claimed BEFORE the
  write and the other published AFTER it, which are opposite orders.

- [x] **A terminal state is published before the cleanup it promises.** `mark_exited` stores
  `exited = true` and only then calls `close_all()`; `terminate()` sets `killed` before unmapping
  objects and closing handles. A waiter can observe a finished process whose mappings and
  capabilities still exist, and a concurrent syscall can create a mapping or a thread that the
  cleanup snapshot has already passed. Wanted: `Running → Terminating → Terminated`, the terminal
  state published last, and every mutating syscall refused from `Terminating` on.

  Fixed with the state the audit asks for. `terminating` is set FIRST - before any cleanup - and
  `killed` / `exited` are published LAST, when they are true. A waiter that sees a terminal flag now
  sees a process whose handles are closed and whose mappings are gone.

  The refusals are wired to `is_terminating`: memory mapping, DMA mapping and thread creation all
  return `ERR_INVALID` once a process has begun going away. Those are the paths that add to what the
  cleanup has to collect, and a registration landing after the cleanup's snapshot is one nothing
  would ever collect.

  A mistake worth recording: the first version of this edit removed the `killed` store it had just
  added, so `terminate()` marked nothing terminal at all. The group-readiness test caught it
  immediately - a process that never reports terminated makes a pipeline that never finishes.

- [x] **Mapping an object is a check followed by an act.** `is_mapped_in` and `add_mapping` take the
  lock separately, so two threads can both find an object unmapped and both map it.
  `forget_memory_mapping` then uses `retain` to drop EVERY reference to that object while the object
  side removed only one - so the second mapping stays in the page tables, leaves the process cleanup
  list, outlives the object, and later points at frames belonging to something else. Wanted: an
  atomic `Absent → Reserved → Mapped` reservation, per-mapping identifiers so cleanup removes
  exactly one, and every create/map refused once terminating.

  Fixed with the reservation the audit asks for: `reserve_mapping` claims the right to map into a
  cr3 under ONE lock and refuses if anyone already holds it, `commit_mapping` records where the
  mapping landed, and `abandon_reservation` gives the claim back when the mapping fails. Both the
  memory-object and DMA paths use it.

  Refusing create/map once terminating is done too, through `is_terminating`.

  **Not done:** per-mapping identifiers, so `forget_memory_mapping` removes exactly one entry rather
  than every reference to an object. With the reservation in place a second mapping can no longer
  exist for the `retain` to over-remove, so the reachable half of that is closed.

- [x] **Dynamic modules reserve a count, not a slot.** A process carries `dynamic_modules:
  AtomicUsize` and no record of which biases are taken. Two loads at the same bias both pass the
  count check, both map the same addresses, the second overwrites the first's PTEs, and either
  one's rollback unmaps the other's. `resolve_dynamic_symbol_by_suffix` promises uniqueness in its
  comment and returns the first match. Wanted: a locked `slot → ModuleState` table with atomic
  reservation, and an ambiguity error from the suffix resolver.

  Fixed both halves. A process now records the BIASES its modules occupy, and
  `reserve_dynamic_module_at` refuses a bias already taken - before either load touches the address
  space, rather than as a mapping failure partway through with two rollbacks interleaved.

  `resolve_dynamic_symbol_by_suffix` returns None when more than one symbol matches, instead of
  whichever the map happened to yield first. Its contract asked for uniqueness and it did not check
  it, so the answer silently changed with the registry.

- [x] **A domain can outlive its parent.** A child holds its parent `Weak` while the parent holds
  children strongly, so a child can survive a parent it can no longer charge through - after which
  the enclosing limits stop applying. `kill()` also flags, snapshots, then kills the snapshot, so a
  process registered concurrently escapes; neither `new_child` nor `register_process` refuses an
  already-killed domain. Wanted: one direction strong and the other weak (or a central tree owner),
  and an atomic register-unless-killed.

  Fixed the register-unless-killed, which is the half that lets a process escape a kill:
  `register_process` takes the list lock, checks `killed` under it, and refuses - so a process
  registered between a kill's snapshot and its flag can no longer slip through. A refused
  registration terminates the process at once rather than leaving it running under an authority
  that no longer accounts for it.

  **Not done:** inverting the strong/weak direction between parent and child. That is a change to
  how the whole Domain tree is owned and wants a single tree owner to be the answer; the escape
  route it enables is narrower than the registration one and is left open above.

- [x] **The loader leaves live PTEs pointing at freed frames.** `load_image_into` maps the ELF
  segments into the process address space and then maps the stack; when `map_stack` fails it calls
  `free_frames(frames)` and unmaps nothing. The segments' page table entries still name frames that
  are back in the allocator - a use-after-free of physical memory as soon as they are handed out
  again. `map_stack` has no rollback of its own, and `SYS_PROCESS_LOAD` is not visibly restricted to
  one `Created → Loaded` transition.

  Fixed the use-after-free, which is the part that costs memory rather than tidiness.

  `elf::loaded_ranges` recomputes the virtual ranges a load maps, and the stack-failure path unmaps
  them before `free_frames` hands anything back. `load_parsed` already unmaps its own segments when
  IT fails; this is the failure that happens AFTER it has succeeded, which nothing covered.

  `map_stack` also rolls back its own pages now instead of returning partway with some mapped -
  it knows their addresses, they are fixed.

  A second defence landed with it by accident and is worth naming: the mapper refuses to overwrite a
  live leaf, so the "second load overwrites the first" half of this finding is closed from the other
  side even where the loader has not been made transactional.

  **Not done:** the full transaction the audit describes - every PTE, every page-table frame and
  every symbol registration recorded and unwound - and the atomic `Empty → Loading → Loaded` state.
  Those belong with the process lifecycle state machine, which is still open above, and writing the
  unwind before the state exists would mean writing it twice.

- [x] **`DeviceMemory` does not know which address space it is mapped in.** It stores only
  `mapped_at: AtomicU64`, and `Drop` calls `paging::unmap_page(base)`, which acts on whichever
  address space is ACTIVE when the last `Arc` goes away - a supervisor, another thread, another
  process entirely. The unrelated process loses that virtual address, the driver's real mapping
  survives, and the VA range returns to the pool while it is still mapped. Wanted: mappings that
  carry their address space and are torn down with `unmap_page_in`, owned by the process rather
  than by the globally shared MMIO object.

  carry their address space and are torn down with `unmap_page_in`, owned by the process rather
  than by the globally shared MMIO object.

  Fixed the half that damages an unrelated address space: the object records the `Arc<AddressSpace>`
  it was mapped in and the teardown unmaps THERE, not in whichever space is active when the last
  reference dies. A mapping with no recorded space leaves the tables alone rather than guessing.

  **Not done:** moving ownership of the mapping to the process, which wants a per-process mapping
  table that the memory-object reservation work in this same phase also needs.

## Phase 4 - the wait subsystem

- [x] **Arming a timer wakes nobody.** `Timer::set` stores the deadline and the armed flag and does
  not call `wake_object`. A thread already parked on an unarmed timer's KOID stays parked after
  another thread arms it. `WAIT_ANY` also does not fold timer deadlines into the scheduler deadline
  it computes, so without an external timeout it does not wake at expiry either. Wanted: `set` and
  `cancel` wake the KOID's waiters, and `WAIT_ANY` takes the minimum of its own timeout and every
  timer in the set.

  Fixed the wakes: `set` and `cancel` both wake the timer's koid. Readiness published without a wake
  is readiness nobody arrives to see.

  **Not done:** folding timer deadlines into `WAIT_ANY`'s computed deadline. A timer now wakes its
  waiters when it is ARMED or CANCELLED, which is the case the audit describes; what remains is the
  natural expiry of a timer already armed when the wait began.

- [x] **A process group is not told when its members die.** A waiter registers on the group's KOID
  while member termination wakes only the process KOID, and nothing registers the group as an
  observer. A group can report `finished()` while a waiter without a timeout waits forever. Also
  `size()` is documented as the original fixed membership while `live()` prunes dead weak references
  out of the same vector, so it changes. Wanted: member termination propagated to the group, or
  waits decomposed onto member KOIDs - and the original size stored separately.

  Fixed by DECOMPOSING the wait, which is the second option and needs no back-link from a process to
  the groups it belongs to: a wait on a group registers on the group's koid and on every live
  member's, so the wake a terminating process already sends is the one being listened for.

  `size()` is stored at creation. It was read off the same vector `live()` prunes, so it shrank as
  members died - the opposite of the sealed membership it documents.

## Hardening and portability

- [x] **Introspection ignores revocation.** `lookup` checks `Capability::is_valid()`; `info`,
  `rights_of`, `badge_of` and `entries` check only the slot and its generation, so a revoked handle
  still reads as live in the System Graph.

  Fixed with one `live_cap_of` - the slot check plus the object-generation check - used by
  `rights_of`, `badge_of` and `info`, and `entries` skips a revoked capability outright. One
  validation used by everything is the only way "is this handle alive" stays one answer.

- [x] **Generations are 32-bit and wrap.** Object and handle-slot generations both wrap, so after
  2^32 recycles an old token matches again - reachable by deliberate churn. Wanted: 64-bit
  generations, and a slot retired rather than wrapped.

  Fixed by RETIRING rather than widening. A handle packs a 32-bit generation and a 32-bit index into
  the u64 userspace holds, so widening it is an ABI change; retiring the slot is not, and closes the
  same hole. A slot whose generation cannot be incremented is not returned to the free list - one
  slot of one table is a negligible loss, and a handle coming back from the dead is not.

  The object generation in `ObjectHeader` still wraps. It is packed into nothing, so widening it is
  the cheap fix there; left open because it belongs with the revocation work.

- [x] **Raw frame deallocation is a safe function.** `pub fn deallocate(phys: u64)` takes a bare
  physical address and is safe, though correctness needs the caller to own the frame and free it
  exactly once. Wanted: an owning `Frame`/`FrameRun` type, `unsafe` on the raw form, and an
  ownership bitmap in debug builds.

  Two of the three are done. `deallocate` and `free_pages` are `unsafe fn` with the contract
  written out, and every one of the ~45 call sites now says why it is entitled to the frame -
  which is the point of the marker: not that the compiler checks anything, but that a reviewer
  sees the claim beside the call.

  The bitmap is real and it earns its keep. `insert` already refused a span overlapping the free
  pool, which catches a double free of a frame that is still free and nothing else. The record
  catches the two cases beside it: a frame that was **never handed out at all** - an MMIO address,
  a bootloader reservation, a number that was never a frame - which would have added non-RAM to
  the pool and handed it out as memory; and a frame freed twice with an allocation in between,
  where the second free lands while it is legitimately out on loan to someone else. One bit per
  frame, 128 KiB on a 4 GiB machine, `debug_assertions` only, built after the heap comes up and
  seeded from "everything not currently in a free run is out on loan", which is exactly true at
  that moment.

  Pinned by `the_allocator_refuses_a_frame_it_never_handed_out`. Removing the check from `insert`
  fails it on the first assertion: the bogus address became free memory and `free_count` went up
  by one.

  **Not done: the owning `Frame`/`FrameRun` type.** Not deferred for size - it does not fit. Half
  the frames in this kernel are not held in a Rust value at all: they live as address bits inside
  page-table entries, and `free_address_space` recovers them by walking the hierarchy and reading
  them back out. A type whose `Drop` frees the frame cannot exist where the frame's only record is
  a PTE. The bitmap is the check that works across both representations, which is why it is the
  part that got built.

- [x] **Resource accounting can wrap and hides underflow.** `charge` is `used.fetch_add(amount,
  AcqRel).saturating_add(amount)` - the saturation applies to the value computed from the result
  while the atomic itself can wrap - and `uncharge` uses `saturating_sub`, so a double refund
  silently reads as zero.

  Fixed the wrap: `charge` is a compare-exchange loop that saturates in the ATOMIC rather than only
  in the number derived from it. There is no saturating fetch, so it reads, saturates, swaps and
  retries. A counter driven past `u64::MAX` used to come back small, and every limit derived from it
  was suddenly satisfied.

  The `saturating_sub` in `uncharge` is left as it is, and the fail-stop the audit asks for is not
  done: making a double refund loud belongs with the frame-ownership work in this same list, where
  there is something to assert against. Saturating is the safe direction meanwhile - it
  under-reports usage, which refuses work rather than permitting it.

- [x] **The scheduler migrates threads while parts of the code assume it does not.** A wake enqueues
  the woken thread on the waker's CPU, so a thread can resume on a different core than it left.
  Some comments and synchronisation choices are written for the opposite. Wanted: either migration
  supported and every per-CPU state, TLB assumption, syscall stack and interrupt state audited for
  it, or a `home_cpu` and affinity that puts the thread back.

  Resolved by taking the FIRST option and writing the audit down. Migration is deliberate - it puts
  a woken thread where the data that woke it is warm and needs no balancer - and the note now sits
  at `enqueue`, where it happens, listing what has been checked to survive it: the saved stack
  pointer (release/acquire, fixed in this milestone), the kernel stack (the thread's own mapped
  range, not per-CPU), `KERNEL_RSP` (reloaded from the incoming thread on every switch), and the
  interrupt state (restored by a guard that is now pinned to one CPU).

  And what does not survive it: the TLB. An address space live on two cores has no shootdown, so a
  migrating thread leaves translations behind. That is the open item in Phase 2 - the reason
  migration is not yet safe for a multi-core process, rather than a reason to stop migrating.

- [x] **`USER_VMAP` is one global pool for every process.** Userspace mmap addresses come from a
  single `VaPool` spanning `USER_MMAP_BASE..USER_VA_END`, though two address spaces may safely use
  the same virtual address. It contends globally, lets one process exhaust the VA space for all of
  them, and complicates range lifetime for nothing. Wanted: a `VaPool` per address space.

  Done as asked. `VaPool` moved out of `syscall` into `mem::vapool` and each `AddressSpace` carries
  one. The kernel window stays global, because that one genuinely is shared: one kernel half, every
  address space, so a range handed out there has to be unique system-wide.

  The change that made it work is that a free now has to name the space it is freeing into.
  `free_vrange(base, len)` routed by address alone, which is all a global pool needs and not enough
  for a pool that lives somewhere; it takes an `Option<&AddressSpace>` now, and `remove_mapping`
  takes the space rather than a bare `cr3`. That reached four Drop paths and every map syscall.

  The old comment claimed the global pool "lets a shared object's single `mapped_at` stay
  unambiguous". It is not what disambiguates anything: `MemoryObject` and `DmaBuffer` key their
  mappings by `cr3` and always did, and `DeviceMemory` refuses a second mapping outright.

  Pinned by `each_address_space_has_its_own_user_window`, which asserts two spaces hand out the
  **same** address - the one thing a global pool cannot do. Reverted to a global static it fails
  with the two bases 16 KiB apart.

  One leak fixed in passing: `sys_dma_buffer_map` did not `abandon_reservation` when the mapping
  itself failed, so an out-of-frames map left a reservation that blocked every later attempt to map
  that buffer in that address space. The `MemoryObject` path beside it always did.

- [x] **MMIO mapping ignores a non-page-aligned physical base.** `DeviceMemory` keeps `phys_base` as
  given and maps by pages; nothing records `phys_base % PAGE_SIZE` or rounds the length up around
  it. A BAR or sub-region that does not start on a page boundary yields a virtual address that does
  not point at the register the caller asked for. Wanted: map from `align_down(phys_base)`, span
  `align_up(offset + len)`, and return `va + offset`.

  Fixed exactly so: `aligned_phys_base` is what gets mapped, `pages` counts from the offset so an
  unaligned region still covers its own tail, and the syscall returns `base + page_offset`. The low
  bits of a BAR are not representable in a PTE, so mapping from the raw base dropped them.

- [ ] **RISC-V ignores `NO_CACHE`.** `leaf_bits` builds `PTE_V | PTE_A | PTE_D | PTE_R` plus W, X and
  U and never consults `NO_CACHE`, relying on the platform's physical memory attributes. That holds
  on QEMU virt and is not a general answer: MMIO without correct attributes can be reordered or
  cached. Wanted: Svpbmt/PBMT where available, platform PMA otherwise, and a clear error when the
  requested semantics cannot be guaranteed.

  Partly done, and the "clear error" was tried and TAKEN BACK OUT. Refusing a mapping this port
  cannot express takes every device with it - virtio included - so a case that works today becomes a
  boot that does not. That is a worse answer than the silent one it replaces.

  What is done instead: `no_cache_supported()` reports false, so the gap is askable rather than
  implied, and the reasoning sits where the flag is discarded. Svpbmt, or a platform PMA check that
  can actually verify the region, is work this port still owes.

- [x] **ACPI parsing trusts firmware lengths and addresses.** The SMP path reads RSDP/RSDT/XSDT/MADT
  through raw HHDM pointers with some minimum-length checks and no checksum validation, no bounds
  against the memory map, and no overflow guards. A damaged table can send the kernel outside the
  direct map. Wanted: one validated reader with checked arithmetic, region bounds and checksums.

  Fixed the checksums and the lengths, which is what stops a bad table becoming a wild read. The
  RSDP is checked over its first 20 bytes before either pointer in it is followed; every SDT is
  checked with ACPI's own rule - the bytes sum to zero mod 256 - and a length outside 36 bytes to
  1 MiB is refused before the sum is even computed, so a nonsense length cannot drive the walk off
  the end of the direct map. A table whose signature says APIC but whose checksum disagrees is not
  believed.

  **Not done:** bounding the tables against the memory map. That needs the map available where this
  runs and is a larger change; the checksum and length bounds close the reachable failure.

  Verified by the SMP bring-up still reporting 4 of 4 cores - a change here could silently drop
  cores while every test still passed.

- [x] **AArch64 NX reporting does not match the mapper.** The paging code sets execute-never
  attributes while the helper used to report NX support does not derive its answer from them, so a
  test can skip the check or the system can report NX inactive while leaves use it. Wanted: derive
  the helper from the translation controls actually programmed.

  Fixed by making it true, which is what the mapper beside it has always done: `leaf_bits` sets
  execute-never for every non-executable page unconditionally, with no CPU feature to enable and
  nothing to turn off. Reporting `false` was a plain contradiction, and the kind that hides rather
  than breaks - a test asking whether NX is active would skip its own check.

- [ ] **The privileged console and display syscalls are not capability-gated.** The comments say so
  themselves - gating was deferred. `SYS_FRAMEBUFFER_MAP` checks a buffer and whether the console is
  disabled and nothing else, so any process can take the display before ConsoleService does;
  `SYS_CONSOLE_FEED` can inject keyboard and serial input into a privileged console; and
  `SYS_CONSOLE_ATTACH` can redirect the console sink and silence kernel output. Wanted: distinct
  `DisplayController`, `ConsoleInputSource` and `ConsoleSink` capabilities endowed only to the
  services that should hold them.

## The tests this needs, which are not the tests it has

The audit's closing observation is the one worth keeping: the gap is not the NUMBER of tests, it is
their kind. The kernel has many, and they exercise happy paths, fault handling, SMP bring-up and
ring-3 entry. Almost nothing here is reachable that way. These findings need a deterministic
interleaving, a fault injected at a chosen N-th allocation, two genuinely concurrent CPUs, an
invariant checked after a rollback, or churn under load.

- [ ] **Capability transfer**: two threads transferring one handle; the same handle listed twice in
  `SEND_CAPS`; a send that fails on a full queue leaving every handle with the caller; a receiver
  short of quota; a receiver whose buffer is smaller than the payload; a thread creation that fails
  after the bootstrap transfer is staged.

- [x] **Page tables**: mapping over a mapped VA must report `AlreadyMapped`; a user API must refuse
  the kernel half; a malicious `ET_EXEC` with a high `p_vaddr`; a segment overlapping the stack or
  the mmap window; OOM at each individual level of hierarchy creation, with the rollback leaving
  every prior mapping untouched.

  All five, and the last one is what needed the harness. `a_page_table_oom_rolls_back_and_leaves_
  earlier_mappings_alone` maps a low page, then maps a far one with the allocator told to refuse
  the k-th allocation for k = 0, 1, 2, ... - so the failure walks down the hierarchy one level at a
  time - and after every refusal checks that the low page is still mapped, still to its own frame.
  It walks the budget upward rather than naming a depth, because the depth is four levels on
  x86_64 and three on Sv39.

  Watched to fail: with the injection made a no-op it fails on `refusals > 0` - the far page maps
  at budget 0, so nothing was ever refused and the test proved nothing.

  `a_user_mapping_is_refused_outside_the_user_half` covers the mapper's bound, at the boundary in
  both directions; `an_et_exec_segment_may_not_name_the_kernel_half` and `a_bias_may_not_carry_a_
  segment_out_of_the_user_half` cover the loader's. Both were watched to fail with their check
  removed.

  **The stack/mmap overlap check did not exist and now does.** Writing the test for it found that
  `validate_segment` bounded a segment against the user half, the dynamic window and the segments
  already loaded - and not against the two ranges the kernel maps into every process whether the
  image mentions them or not. Nothing unsafe followed: `try_map` refuses to remap a live page, so
  the stack mapping failed and took the load with it. What it failed WITH was `OutOfMemory`, for an
  image that is malformed rather than large, after the image had chosen which of its own segments
  got mapped first.

- [ ] **TLB and SMP**: two threads of one process on two CPUs; CPU A unmaps and the frame is
  immediately reallocated; CPU B must not reach the old translation after the shootdown ACK; the
  same again through process teardown and stack growth.

- [x] **Loader OOM injection**: fail deterministically at the first ELF data frame, at each
  intermediate page-table frame, at the first stack frame, mid-stack, at symbol registration, and at
  dynamic module mapping - and after every one, the page tables, the frame count and the process
  metadata must equal their state before the call.

  Done by measurement rather than by enumeration. `a_load_that_runs_out_of_frames_anywhere_gives_
  back_everything` loads a real service image with the allocator told to refuse the k-th allocation,
  k = 0, 1, 2, ... until a load completes - which for `log_service.lsexe` on x86_64 is **88
  allocations**. Every one of those 88 points is a distinct place the load can fail, and after each
  the frame pool must be exactly what it was before the call. That single number is what the
  rollback is for: a frame allocated and not recorded, a segment unmapped without its frames
  returned, a stack half-mapped and abandoned, page tables built for a load that never finished -
  each of them shows up as a pool that shrank.

  Watched to fail: with `free_frames` replaced by `mem::forget`, it fails at allocation 74, one
  frame short.

  **It found a real bug on its first run, and the bug was a panic.** `KernelStack::allocate` did
  `frame::allocate().expect("out of frames: kernel thread stack")`, and thread creation is
  reachable from ring 3 - `SYS_THREAD_CREATE`, and every process spawn makes one - so a frame pool
  that had run low turned an ordinary userspace call into a dead machine. The Domain thread quota
  does not help: it bounds how many threads ONE process may have, not whether there is memory for
  the next one, and the pressure can come from anywhere in the system.

  `KernelStack::allocate` and `Thread::new` return `Option` now, the partial stack is given back on
  the way out, the Domain thread charge is refunded, and `spawn_elf_process` takes its own process
  down and reports `OutOfMemory`. The kernel-internal spawns (`sched::spawn`, `spawn_on`,
  `spawn_with_object`) still `expect`, deliberately: they are boot-time and test-time and have no
  caller that could act on a refusal.

  **Not covered:** symbol registration and dynamic module mapping. The image this drives is a
  static one, so those two paths are not on the 88.

- [ ] **Scheduler**: two last threads exiting together; a thread woken onto a different CPU; two
  CPUs waking one thread; starting an already-started thread; a kill during a map syscall; a kill
  during thread creation; an AP arriving after the boot timeout.

- [ ] **Wait subsystem**: a timer unarmed at the start of a wait and armed later; `WAIT_ANY` with
  only a timer and no external timeout; a process group finished by its last member; a channel
  closing exactly as a waiter registers; a stop/continue between the readiness check and the park.

- [ ] **Fuzzing**: ELF headers and program headers, dynamic relocation tables, syscall arguments and
  lengths, capability transfer arrays, the ACPI/MADT parser, map/unmap sequences, and handle
  generation churn through close and duplicate.

## What this audit does not say

Nothing here was reproduced at runtime; the audit was static and so was this verification. Of the 37
findings, 27 were checked line by line against the code they name and every one held. The remainder
- parts of the thread-start path, the receive ordering, the heap's alignment-prefix loss, and the
process-group and domain lifetime details - were read but not traced end to end, and are recorded on
the audit's reading rather than on an independent one. They are marked by nothing special because
the fix for each begins with confirming it, which is where the work starts anyway.

The severity ordering is the audit's and is worth keeping: the boundary comes first, because until
`ET_EXEC` validation, the mapper's address bound, the syscall origin and fault-safe user copies are
done, everything else is a correctness problem inside a system that is not isolated to begin with.
