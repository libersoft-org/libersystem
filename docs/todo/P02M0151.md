# P02M0151 - The architecture boundary contains no panic-shaped compatibility contract

Status: OPEN. ARCHITECTURE CORRECTNESS. HOST/QEMU-CLOSABLE. NOT A PHYSICAL-HARDWARE SUPPORT CLAIM.

## Goal

Remove the x86 boot-handoff symbols which aarch64 and riscv64 currently satisfy with unreachable
`todo!()`, make the named direct-boot interrupt/timer/SMP profiles consume the machine description,
confine today's no-DT UEFI compatibility to explicit QEMU descriptors, and close the concrete
secondary-CPU lifecycle defects which QEMU or a host firmware model can reproduce.

This milestone does not "finish ARM" or "finish RISC-V" in the unbounded sense. Its claim is:

> Every symbol in an architecture's compiled contract is a path that architecture can execute; the
> named direct-boot discovery profiles exercise their actual timer, interrupt and SMP topology
> without reaching an unimplemented body, while no-DT UEFI regressions make no discovery claim.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b`.

- P02M0142 made the boot tail portable and documented why the non-x86 `todo!()` bodies are not live:
  `main::kmain`, INIT/SIPI, IOAPIC and the real-mode AP trampoline belong to the x86 loader
  hand-off; aarch64 and riscv64 enter their own `boot.rs` prologues.
- The used paths are real. Aarch64 installs VBAR, starts GICv2 and the generic timer, observes timer
  interrupts, wakes secondaries through PSCI and drives preemption. RISC-V installs STVEC, uses SBI
  TIME and HSM, receives IMSIC interrupts and drives the same scheduler.
- The source nevertheless contains eleven executable `todo!()` bodies under `arch/aarch64` and nine
  under `arch/riscv64`. None is reached by the current entry point, but a static scan and README
  call them unfinished interrupt/timer glue. The contract is still shaped so that the false
  conclusion is easy to reach.
- Aarch64's GICv2 distributor, CPU interface and GICv2m frame addresses are QEMU constants. RISC-V's
  IMSIC S-file base and stride are QEMU constants even though the device tree describes the
  controller. Passing one fixed QEMU profile is therefore not evidence that discovery works.
- Secondary bring-up hands a logical id out only after a core reports online, but reuses that id and
  its stack after a timeout. A core which accepted `CPU_ON`/`hart_start` and arrives late can then
  collide with the next attempt. The same shape exists on aarch64 and riscv64.
- RISC-V carries firmware hart ids as `u64` until per-CPU initialization and then truncates them to
  `u32`. Its IMSIC enable/disable operations act on the current hart, while an `Interrupt` does not
  retain which hart its MSI targeted; teardown on another hart can disable the wrong interrupt file.
- The ordinary harness fixes aarch64 to QEMU `virt,gic-version=2` and riscv64 to
  `virt,aia=aplic-imsic`. QEMU also exposes a GICv3/ITS profile, and host DT fixtures can move or
  reshape controller nodes without requiring physical hardware.
- THE DEVICE TREE PROFILES ARE DIRECT-BOOT PROFILES. The current AAVMF/U-Boot UEFI paths do not hand
  the kernel a DTB on these two targets; they enter with a `BootInfo` whose DT source is absent and
  work today only because the controller addresses are compiled in. This milestone does not call
  that discovery. It keeps those UEFI paths as explicitly named single-node regression profiles,
  without a controller-topology claim, while generated-DT discovery is proved through QEMU's direct
  `-kernel` entry. Carrying a DT through those firmware paths, or discovering the same topology from
  ACPI, is separate boot-handoff work.

## Work

- [x] **M1 - Split the x86 boot hand-off from the portable post-boot HAL in the type-checked tree.**
  - `kmain`, x86 AP discovery/INIT-SIPI-SIPI, IOAPIC routing and the real-mode trampoline are
    compiled only for x86_64. Their symbols are no longer requirements imposed on another backend.
  - Aarch64 and riscv64 delete the corresponding `todo!()`/empty compatibility functions. Do not
    replace them with calls into their already-running initialization; that would make a dormant
    double-init path rather than remove it.
  - Keep one explicit portable post-boot surface for paging, context switch, per-CPU access, timer
    ticks, wake IPIs, device interrupt binding, user entry and reset/power. A new architecture must
    implement that surface and its own named boot prologue, not a list copied from x86.
  - Add a build/static gate which rejects `todo!`, `unimplemented!` and unconditional panic bodies
    in the compiled production architecture surface. Test-only fault probes remain identifiable as
    tests rather than exceptions to a text scan.

- [x] **M2 - The ARM GIC core topology comes from firmware data before the first controller
      access.**
  - This is the direct-boot FDT path. Decode and validate the generated tree before `gic::init`, and
    publish the boot stub's real direct-map ceiling before the validator asks whether an MMIO range
    is reachable. The existing UEFI-without-DT path is a separately named single-node QEMU
    regression fallback, makes no controller-topology claim and is not evidence for this discovery
    claim.
  - That fallback has one central, immutable `qemu-virt-gicv2` descriptor selected only by the named
    UEFI/no-DT harness profile. It is not a generic architecture default, is never selected when a
    DT exists, and keeps QEMU constants out of the live discovered backend. This is the bounded
    price of preserving today's loader regression without adding ACPI discovery to this milestone.
  - Parse and validate the GIC distributor, CPU/redistributor and MSI-controller regions from the
    FDT supplied by QEMU. Check address arithmetic, region sizes, overlaps and that each range lies
    in the mapped physical window before the first MMIO access.
  - Preserve the current GICv2 core as one discovered profile. Add the GICv3 system-register,
    redistributor, timer-PPI and SGI wake/shootdown path as a second core profile. Redistributor
    discovery and per-core setup are data-driven rather than indexed from a compiled address.
  - The architected generic timer remains read from architectural registers, while its selected PPI
    and interrupt-controller routing are checked against the machine description. A missing or
    contradictory MAIN GIC is a fatal, named boot refusal: without its timer interrupt this kernel
    cannot claim a working scheduler even on one core. A valid GIC with no supported MSI controller
    may continue without device IRQs and says exactly that.
  - Host parser tests mutate every address/count/cell-width and cover truncation, duplicate nodes,
    overflow and a controller outside the direct map before the two GIC core profiles run.

- [x] **M3 - ITS/MSI is a checkpoint after, not part of, GICv3 core bring-up.**
  - First close a GICv3 profile which proves timer progress, SGI wake, TLB shootdown and secondary
    scheduling with ITS disabled. Do not debug redistributor bring-up and an ITS command queue as
    one failure domain.
  - Then initialize the ITS command queue, device/collection/property/pending tables and LPI state
    behind the existing portable MSI contract. Every allocation, map, unmap and release has a
    bounded completion rule; an unconfirmed release is not reused.
  - The final `virt,gic-version=3,its=on` profile must deliver and tear down a real device MSI.
    Until this checkpoint passes, the GICv3 core profile is named as timer/IPI-only rather than as
    complete device-interrupt support.

- [x] **M4 - The RISC-V AIA/IMSIC topology comes from the DT, with ids that stay wide enough.**
  - This is likewise the direct-boot generated-DT profile. The existing UEFI path without a DT
    remains an explicitly named single-node QEMU regression fallback and does not satisfy the
    discovery gate.
  - Parse IMSIC bases, stride/group topology, hart association and interrupt-id range from the FDT.
    Delete the fixed `0x2800_0000` answer from the discovered backend; a missing or unsupported
    topology refuses MSI rather than claiming the QEMU default.
  - Preserve the UEFI/no-DT regression only through one central, immutable `qemu-virt-aia`
    descriptor selected by that named harness profile. It is never selected when a DT exists and is
    reported as a static QEMU fallback, not as firmware discovery.
  - Carry hart ids in a type wide enough for the SBI ABI through `percpu`, the portable CPU-id
    table, wake IPIs and MSI target construction. If a narrower hardware field genuinely exists,
    validate it at that field's boundary and name the refusal.
  - Record the target hart with every allocated IMSIC EID. Bind, unbind, unused-release and
    quiesced-release update the interrupt file which owns the EID, using a targeted operation or a
    bounded cross-hart request; they never assume teardown runs on the allocator's hart.
  - If that cross-hart request times out, the EID remains quarantined and unavailable for reuse
    until its owning hart acknowledges the disable. A timeout may leak a vector visibly; it may not
    hand a still-enabled identity to another device.
  - Host fixtures cover sparse/non-zero hart ids, reordered CPU nodes, relocated IMSIC ranges,
    unsupported group layouts and ids above `u32::MAX`; the current AIA QEMU profile remains the
    live integration proof.

- [x] **M5 - A secondary start attempt owns a unique descriptor until it is resolved.**
  - Allocate an attempt record containing firmware id, logical id, stack, state and generation
    before issuing PSCI `CPU_ON` or SBI `hart_start`. A successful firmware return transfers that
    record to the secondary; a timeout marks it abandoned but never reuses its id or stack while it
    may arrive.
  - A late secondary observes the generation/abandoned state and parks without initializing a reused
    per-CPU slot. Failed firmware calls, which guarantee that no core accepted the entry, may
    release their untouched record under an explicit rule.
  - Validate that the boot CPU/hart is represented exactly once in the usable firmware topology
    before sizing per-CPU arrays. A malformed tree cannot turn `N` declared CPUs into the boot CPU
    plus `N` secondaries writing an `N`-entry allocation.
  - Put the PSCI/SBI call and online-report protocol behind a host-testable fake. Exercise immediate
    failure, timeout then late arrival, out-of-order arrival, duplicate report and more declared
    CPUs than the supported bound on both architectures.

- [ ] **M6 - Named QEMU profiles execute exactly the paths this milestone claims.**
  - Add reproducible DIRECT-BOOT discovery profiles, not undocumented `QEMU_EXTRA` recipes: aarch64
    GICv2/GICv2m, aarch64 GICv3 with ITS off, aarch64 GICv3/ITS, and riscv64 AIA/IMSIC. Keep the
    existing aarch64/riscv64 UEFI boots as separate single-node regression profiles labelled
    `UEFI/no-DT`; they prove the loader path still works, not that controller discovery occurred.
  - At one CPU/hart, each applicable profile observes timer progress, user/kernel preemption, MSI
    delivery and correct MSI teardown. At four CPUs/harts it additionally observes a remote wake
    IPI, a real TLB shootdown acknowledgement and secondary-core scheduling. A one-core run is never
    asked to prove a remote event or the existence of a secondary.
  - Run the full architecture suite on each primary profile. Secondary controller profiles may use a
    declared `boot,smp,interrupt,paging,sched,drivers` integration set if their full-suite cost is
    recorded, but a profile which only reaches a boot banner is not evidence.
  - Mutation/fake-firmware cases from M2-M5 run as host gates. QEMU is not asked to produce
    malformed firmware states it has no switch for.

- [x] **M7 - Documentation names supported profiles, not counts of dormant panics.**
  - Replace README's twelve/seventeen-hook claim with a table of entry path, interrupt controller,
    timer, SMP firmware interface, QEMU profile and physical-hardware status per architecture.
  - The architecture module documents the smaller post-boot contract and the deliberately separate
    machine prologues. It does not say three boot prologues are one implementation.
  - Record the exact test/profile result and preserve the statement that none of it qualifies a
    physical machine.

## Results

Measured on 2026-08-24. This section grows as the items land; what is written here is what has been
run.

- **M1 - THE HAND-OFF COMPILES FOR x86_64 ALONE, AND THE TWENTY BODIES ARE GONE.** `kmain`, the ACPI
  MADT walk, the AP identity seqlock, INIT-SIPI-SIPI, the real-mode trampoline's stack and
  reachability checks, the x86 INTx registry and the loader's memory hand-off are `#[cfg(target_arch
  = "x86_64")]`. aarch64 and riscv64 define none of them: eleven `todo!()` bodies under
  `arch/aarch64` and nine under `arch/riscv64` were deleted along with the empty compatibility shims
  beside them (`enable_rx_irq`, `remove_bootstrap_identity`, `register`, `IRQ_BASE`, `HandlerFn`,
  `cr3_is_reachable`, `local_id`, `send_init`, `send_startup`, `install`, `set_stack`). `cargo
  check` is clean for `x86_64-unknown-none`, `aarch64-unknown-none` and
  `riscv64gc-unknown-none-elf`; x86_64 builds and boots to a shell.

- **THE COMPILER FOUND THREE PLACES WHERE A PORT WAS SKIPPING A PORTABLE STEP.** Removing the
  requirement made every symbol's real reach visible, and three portable calls turned out to be
  reached on some targets and not others:
  - aarch64 never called `heap::reserve_window` or `syscall::reserve_kernel_vmap`. Both are no-ops
    there - the kernel runs from the low half on the boot identity map - but the step belongs to the
    LAYOUT rather than to the architecture, and a port that skips it is a port whose missing call is
    doing the work of a comment. Both are now taken by all three.
  - riscv64 never printed the product banner and neither device-tree port reported how many cores
    came online. All three print both now, off the same constant and the same portable counter every
    port already increments. A port that wakes cores and never says how many answered is one whose
    secondary bring-up can regress in silence.

- **THE GATE.** `tools/check-arch-surface.sh` (`./check.sh --gate arch-surface`, 30 gates now,
  mirrored in `verify-model`) refuses `todo!` and `unimplemented!` anywhere in the compiled
  architecture surface, dropping `#[cfg(test)]` blocks and `tests.rs` files first so a deliberate
  test fault probe stays identifiable as a test. It carries a self-test that proves both halves - a
  production body is seen, a test-only body is not - and it was watched to fail on a planted
  `todo!()` under `arch/x86_64`.

- **M2 - THE GICv2 CORE IS DISCOVERED, AND THE GICv3 PROFILE IS NOT WRITTEN YET.** The shared FDT
  reader takes the distributor and CPU interface out of the controller's two-range `reg`, the
  version out of `compatible`, and the GICv2m frame out of the controller's child node. It refuses
  a `reg` too short for two ranges, a zero-sized or overflowing range, two ranges that share a byte,
  a controller whose `compatible` it does not know, a disabled one, a second one after a usable one,
  and a frame under a controller that maps nothing. Eleven host cases, including the real QEMU tree,
  which names exactly the addresses the constants used to carry. The prologue validates both ranges
  against the direct map before the first MMIO access and refuses a tree with no usable controller
  BY NAME - without its timer interrupt this kernel cannot claim a scheduler, so guessing an address
  would be claiming a machine rather than reading one. A valid GIC whose MSI frame is absent or
  unreachable boots and says device interrupts are unavailable. Measured: `aarch64: GICv2 from the
  device tree - distributor 0x8000000+0x10000, cpu interface 0x8010000+0x10000`, timer IRQs
  delivered, 8 of 8 cores online, shell up.

- **THE TWO CEILINGS WERE TWO STATICS, AND THE VALIDATOR READ THE WRONG ONE.** `within_direct_map`
  read only the map-derived limit, which is published when the frame allocator is seeded - long
  after a prologue asks about its interrupt controller. So the first discovered boot refused the
  machine that had just described itself: `the device tree describes no usable interrupt
  controller`. Both statics answer the same question - how far `phys_to_virt` translates - and the
  larger of the two is the honest answer at any moment. This is exactly the ordering the item names,
  found by the boot rather than by reading.

- **M4 - THE IMSIC ADDRESS COMES FROM THE TREE, AND THE SUPERVISOR ONE IS THE ONE TAKEN.** An AIA
  machine describes two IMSICs and QEMU lists the firmware's first, so a reader that took the first
  node would point every device MSI at interrupt files OpenSBI owns - which this kernel cannot read
  and would never see fire. They are told apart by `interrupts-extended`: IRQ 9 is the supervisor
  external interrupt, 11 the machine one. A machine with no IMSIC (plain `virt`, routing through a
  PLIC) leaves the address alone and says so. A new host fixture from `virt,aia=aplic-imsic` carries
  the case, beside the PLIC machine's tree. Measured: `riscv64: IMSIC S-mode files from the device
  tree at 0x28000000+0x8000`, 8 of 8 harts online, shell up.

- **M2 (COMPLETED) - THE GICv3 CORE IS A SECOND DISCOVERED PROFILE, AND THE SAME TWO RANGES MEAN
  DIFFERENT THINGS ON IT.** A GICv2's second `reg` range is a memory-mapped CPU interface; a GICv3
  has no such thing - its CPU interface is SYSTEM REGISTERS - and that range is the REDISTRIBUTOR
  region instead. The version comes from `compatible` and decides which, so nothing is inferred from
  the shape of `reg`. The per-core half is data-driven the way the item asks: a core finds ITS OWN
  redistributor by matching its MPIDR affinity against each frame's `GICR_TYPER`, walking to the
  frame whose Last bit is set, rather than indexing the region by logical CPU id - which is the same
  dense assumption the secondary bring-up carried, and just as untrue on a machine whose cores are
  not a flat 0..N.

- **AND THE GROUP IS WHY A GICv3 BRING-UP EITHER WORKS OR DELIVERS NOTHING.** Every enable register
  in a redistributor resets to GROUP 0, and a GICv3 delivers group 0 as FIQ and group 1 as IRQ - so
  an interrupt enabled without being moved to group 1 is delivered to a handler this port does not
  install. `GICR_IGROUPR0` for the SGIs and PPIs, `GICD_IGROUPR` for the SPIs, `ICC_IGRPEN1_EL1` for
  the interface, and the redistributor woken out of ProcessorSleep before any of it. SGIs are sent
  through `ICC_SGI1R_EL1` BY AFFINITY - which is what the caller has held all along - so the
  eight-interface limit named in M4 is a GICv2 property this controller does not have.

- **MEASURED, FIRST BOOT.** `GIC=3 ./run.sh --arch aarch64`: `GICv3 from the device tree -
  distributor 0x8000000+0x10000, redistributors 0x80a0000+0xf60000`, timer IRQs delivered, `8 of 8
  cores online` - which is the SGI wake and eight redistributors found by affinity, not one - and
  twelve userspace services up. It then stops where the milestone says it stops: with `its=off` and
  no v2m frame the machine has no MSI controller, the kernel says so by name, and userspace reaches
  the first driver that needs a device interrupt and no further. THAT IS THE TIMER/IPI-ONLY
  CHECKPOINT M3 IS DEFINED AGAINST, and it is why the ITS is a separate failure domain rather than
  part of this. The GICv2 profile boots to a shell unchanged.

- **AND THE PROFILE IS A NAMED KNOB RATHER THAN A `QEMU_EXTRA` RECIPE.** `GIC=2` (default, GICv2 +
  GICv2m), `GIC=3` (GICv3, `its=off`) and `GIC=3its`. `its=off` is written out rather than left to
  QEMU's default, which is ON: a core profile that quietly had an ITS would not be the profile it
  says it is.

- **M3 - THE ITS DELIVERS AND TAKES BACK A REAL DEVICE MSI, AND THE CHECKPOINT BEFORE IT IS WHY
  THAT WAS DEBUGGABLE.** A GICv2m frame is a register a device writes an SPI NUMBER into: the device
  names the interrupt. An ITS is not that. The device writes an EVENT ID to one translation
  register, and the controller decides from tables THIS KERNEL OWNS - a command queue, a device
  table, a collection table, an interrupt translation table per device and a global LPI
  configuration table - which LPI to raise and where. `its.rs` is that: the tables, the serial
  command ring, MAPD/MAPC/MAPTI/INV/INVALL/DISCARD/SYNC, and one collection aimed at the boot core,
  which is the routing the v2m path has always had. Measured on `GIC=3its`: `its: up - 16 event id
  bits, 512 device ids, 8192 LPIs from INTID 8192`, ten of eleven devices online, `network:
  configured via DHCP` - which is virtio-net RECEIVING - and a shell. Teardown is exercised in the
  same boot: xhci does not bind, and its vector is discarded from the ITS and freed rather than left
  mapped.

- **AND THE NEGOTIATION IS READ BACK RATHER THAN ASSUMED, THREE TIMES.** The tables' cacheability is
  writable-or-ignored, so a controller that does not snoop this kernel's caches is refused by name
  instead of being handed tables it cannot see. The device table's size is this port's choice, so a
  DeviceID past it is refused rather than folded into another device's entry. And `GITS_TYPER.PTA`
  decides whether a collection names a redistributor's ADDRESS or its PROCESSOR NUMBER - a third
  numbering, neither the logical cpu id nor the affinity - and QEMU reports the second, so the first
  is the form that could not be tested by running it.

- **FOUR DEFECTS, AND THE LAST TWO ARE THE ONES A CHECKPOINT BUYS YOU.** The bring-up needed memory
  and ran before the frame allocator existed - true for as long as a v2m frame, which is one
  register read, was the only MSI controller this port knew. `GITS_CTLR` is thirty-two bits wide
  among sixty-four-bit neighbours, and a 64-bit store to it was ignored, so the controller never
  enabled and every command sat unread. Then, with the ITS demonstrably up and translating - the
  pending bits appeared in the table this kernel allocated - nothing was delivered, because **an LPI
  configuration entry's bit 1 must be written as one**: left clear the controller reads the entry as
  GROUP 0, delivered as FIQ, which this port neither enables nor handles. And with that fixed the
  FIRST device MSI arrived and no second one ever did, because the completion was guarded by `intid
  < 1020` - true of every SPI a v2m frame can raise and false of every LPI an ITS can. The interface
  held that LPI's running priority forever. Each of those is invisible at the level of "MSI does not
  work"; the GICv3 core profile passing first is what made "the controller is up and the interrupt
  is not delivered" a statement anyone could make.

- **M4 - THE IDS ARE AS WIDE AS THE FIRMWARE THAT NAMES THEM, AND THE NARROW FIELDS SAY SO.** The
  portable CPU-id table and all three per-CPU blocks carried a `u32`. An SBI hart id is an
  `unsigned long` and an MPIDR affinity is forty bits - Aff3 sits at 39:32 - so both device-tree
  ports were truncating, and on aarch64 a machine with a non-zero Aff1 would have had two cores
  answering to one id in the one table the IPI paths read. The table, `percpu`, the wake IPI and
  `sys_cpu_info` are `u64` now. THE NARROW FIELDS ARE REAL AND STAYED NARROW, each checked at its
  own boundary: an APIC id is 32 bits (and x86's per-CPU block keeps it that way - the syscall entry
  assembly reads fixed offsets past it, which the tree's own `offset_of!` assertions caught the
  moment the field grew), the xAPIC ICR destination is 8 bits, an IOAPIC redirection entry's
  physical destination is 8, and GICv2's SGI target list addresses EIGHT CPU INTERFACES BY NUMBER -
  which is not an MPIDR at all. That last one was `cpu & 0xff` over an affinity value: on a machine
  with a non-zero Aff1 it picks interface 0, so the IPI goes to the BOOT CORE instead of the target
  and nothing says so. Each of the four now names its limit and does not send.

- **AND THE EID WAS BEING DISABLED IN THE WRONG HART'S INTERRUPT FILE.** An IMSIC enable bit lives
  in ONE hart's file and `siselect`/`sireg` address the running hart's, always - so an EID enabled
  by the hart that ran the acquire could only ever be disabled BY THAT HART, while teardown runs
  wherever the last reference happened to drop. `disable_eid` cleared a bit in a file where the EID
  was never enabled and reported success: the device kept delivering to the owner, and the
  "best-effort" disable the unbind path documented had in fact done nothing at all. The owner is now
  recorded with the EID; a teardown on another hart posts the request to that hart's mailbox, raises
  its wake IPI and waits under a bound, and the hart services it from the software-interrupt handler
  the IPI raises. IF IT DOES NOT ANSWER, THE VECTOR IS QUARANTINED - a state the registry did not
  have: not free, not waiting for its device, but out of circulation for the life of the boot,
  because a device quiesce says nothing about an enable bit this kernel could not clear. It leaks a
  vector visibly; reusing one hands a live identity to another driver. Quarantine is compiled for
  riscv64 alone, since it is the only backend whose disable can fail - an x86 MSI is torn down in
  the device's own register and a GICv2m SPI in the distributor, and any core can write either.

- **THE TREE DESCRIBES THE FILES' LAYOUT, AND THIS PORT ONLY ADDRESSES ONE OF THEM.** `base + hart *
  4096` is true of a flat, hart-indexed array whose file N belongs to hart N - and the AIA binding
  describes machines where none of that holds: guest-indexed files, group-indexed files, and an
  association given by `interrupts-extended` in FILE ORDER rather than by hart id. The parser now
  reads all of it, including resolving each file's entry through the cpu nodes' interrupt-controller
  phandles, which meant teaching it phandles at all. The kernel refuses what it cannot address and
  says which fact refused it, rather than computing an address inside a layout it does not
  understand; a hart with no interrupt file is not an MSI target either. Six host fixtures cover it:
  the real eight-hart AIA tree ties file N to hart N, a tree that lists its cpus backwards is still
  resolved by phandle, a dangling phandle is a file belonging to no hart, a 64-bit `cpu@reg` under
  `#address-cells = 2` survives whole, relocated files are followed, and a guest- or group-indexed
  layout is reported rather than flattened.

- **AND M4 FOUND THE TEST BUILD OF BOTH DT PORTS BROKEN BY M1.** Making the ACPI walk x86-only left
  `smp/tests.rs` calling `table_signature`, `table_length` and `table_ok` on every target, so
  `cargo check --profile test` failed for aarch64 and riscv64 - a break no ordinary build shows,
  because those two only compile their test build under `test.sh --arch`. The bound those readers
  are asserted against is portable and stays on all three; the readers themselves are the ACPI
  walk's and are now compiled where ACPI is.

- **M5 - AN ID IS SPOKEN FOR THE MOMENT IT IS OFFERED, AND A TIMEOUT DOES NOT TAKE IT BACK.** Both
  ports had the same loop: hand out the next logical id, call firmware, wait, and on a timeout
  `continue` WITHOUT advancing the id - so the next core was offered the id and the stack the last
  one may still be on its way to claim. The rule is now that a firmware call which RETURNS SUCCESS
  has released a core, so its id is abandoned rather than returned; only a call the firmware REFUSED
  can take its id back, because that is the one case nothing was ever released. The arriving core
  claims its id with a compare-exchange before it touches per-CPU state, a stack or a trap vector,
  and parks if the claim fails - a late core costs one core, joining costs the machine.

- **AND THE ONLINE TALLY WAS NOT THE COUNT ANYTHING SHOULD BE SIZED FROM.** With ids that can skip,
  a core that comes up after an abandoned attempt holds an id ABOVE the number of cores online - and
  the per-CPU table, the run queues, the controller-id map and riscv64's stack block are all indexed
  by that id. `set_cpu_count` and `sched::allocate` now take the ids handed out; the per-CPU table
  takes the ceiling of what can ever be handed out, because a secondary writes into it while the
  boot core is still inside the bring-up loop.

- **THE TREE CAN ALSO BE WRONG ABOUT WHICH CORES EXIST, AND THAT IS SIZING TOO.** `smpboot::Topology`
  reduces the declared list before anything is allocated from it: every occurrence of the running
  core is dropped (it is not a core to start), a repeat of an id already in the list is dropped and
  counted, and the remainder past the pool bound is parked and counted. `slots()` - secondaries plus
  one - is what the arrays are sized from. THE CASE THAT MATTERS IS A TREE THAT OMITS THE RUNNING
  CORE: N declared cores are then N secondaries and N+1 ids, and every array sized from the declared
  count was one entry short of what a successful boot writes. Each of the three now prints a line
  rather than narrowing in silence.

- **IT IS A CRATE BECAUSE THE CASES THAT MATTER ARE ONES QEMU HAS NO SWITCH FOR.** `src/smpboot` -
  no `std`, warnings denied, the same reason `buddy` is a crate - holds the id ownership rule and
  the topology reduction; PSCI and SBI are left with the call, the bounded wait and the wording of
  the line. Sixteen host tests drive a scripted firmware through immediate refusal, timeout, a core
  released two waits late, a core that reports twice, a tree that omits the boot core, names it
  twice, repeats an id, or declares more cores than the pool holds. The suite is DISCOVERED rather
  than registered - `check-host-tests.sh` now enumerates 69 crates. Watched to fail on both rules:
  returning an abandoned id instead of keeping it fails the three late-arrival cases, and sizing
  from the declared count fails the three topology cases.

- **THE TWO PORTS NOW SHARE THE LOOP.** aarch64's `Psci` and riscv64's `Hsm` are `smpboot::Firmware`
  implementations of three methods each. Measured on cold guests: aarch64 `SMP - 8 of 8 declared
  cores online`, shell up; riscv64 the same, from a boot QEMU happened to start on HART 7 - so the
  boot-core-is-not-id-zero case is the live one rather than a fixture.

- **M7 - THE README STATES MACHINES, NOT A COUNT OF DORMANT PANICS.** The claim it carried -
  "`riscv64` and `aarch64` ... still carry unimplemented hooks in their interrupt and timer glue -
  twelve and seventeen of them" - was true when it was written and false the moment M1 deleted the
  twenty bodies and gated the surface. It is now a table: entry path, interrupt controller, timer,
  secondary-core firmware interface, the named QEMU profiles, and physical-hardware status, per
  architecture. The sentence that no port has been run on physical hardware stays, with the addition
  that no emulated result here is a claim about one. The architecture module already documents the
  three-part contract and the deliberately separate machine prologues; M1 rewrote it when it removed
  the requirement.

The contract cleanup is first so new controller work cannot deepen the false surface. The GICv3

## Definition of done

- Aarch64 and riscv64 contain no x86 boot-handoff compatibility body and no production architecture
  contract member whose answer is `todo!`, `unimplemented!` or an unconditional placeholder panic.
- The direct-boot aarch64 GICv2 and riscv64 AIA profiles retain their behavior using discovered
  controller data; the staged GICv3 core profile delivers timer and IPI before the GICv3/ITS profile
  is required to deliver a device MSI. Existing UEFI/no-DT boots remain green as single-node
  regressions but are not labelled discovery evidence, and their static QEMU descriptors cannot be
  selected by a boot which has a DT.
- Hart ids are not silently truncated, an IMSIC vector is torn down on its recorded target, and a
  timed-out disable quarantines its EID; a timed-out secondary cannot share a stack or logical id
  with a later attempt.
- Every named QEMU profile passes its applicable one-core or four-core integration gate, with host
  mutation tests covering the firmware shapes QEMU cannot emit.
- README and architecture documentation describe actual supported emulated profiles and continue to
  state that no physical-hardware support has been established.

## What this milestone refuses, and why

- **Blind implementations of the deleted stubs.** The real work already occurs in each boot
  prologue; calling it through an x86-shaped dormant path risks double initialization and proves
  nothing.
- **One universal boot sequence.** Machine bring-up is architecture-specific. The portable tail and
  post-boot HAL are shared; forcing PSCI, SBI and INIT/SIPI into one abstraction would hide their
  materially different failure rules.
- **Every ARM or RISC-V interrupt controller.** PLIC-only RISC-V, vendor AIA layouts, GICv4, SoC
  interrupt fabrics and board power/reset glue require separately named profiles. Absence from this
  QEMU milestone is not papered over by a generic architecture label.
- **ACPI controller discovery or a new DT hand-off for the existing non-x86 UEFI paths.** Those
  paths currently have no DT. They remain single-node regression profiles here; making firmware
  topology discoverable through them is separate boot-protocol work, and a prerequisite for any
  later UEFI discovery claim, not work hidden inside this milestone or implied by a direct-boot FDT
  result.
- **Scheduler policy features.** Priorities, load balancing, affinity policy, tickless operation and
  NUMA placement are not missing interrupt hooks. NUMA has its own milestone.
- **A physical-hardware claim.** QEMU does not reproduce firmware quirks, interrupt coherency,
  errata or board wiring. This milestone makes emulated paths complete and honestly named, nothing
  more.
