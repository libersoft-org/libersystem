# P02M0165 - A driver that stops answering looks exactly like one that is busy

Status: PLANNED AFTER P02M0164. SUPERVISION, PLANNED STOP AND ACCOUNTING. SIXTH OF SEVEN - see P02M0098.

## Goal

Notice a driver that has stopped making progress, stop one on purpose without losing its in-flight
work, and keep the resource counters honest across every crash and restart.

## What is there now

- **AN EXIT IS NOTICED AND A HANG IS NOT.** P02M0162 supervises a driver that exits. A driver that is
  alive and wedged - a control queue that never completes, a request outstanding forever - is
  indistinguishable from an idle one, and an idle device is not a fault.
- **THERE IS NO PLANNED STOP.** Shutdown revokes; nothing asks a driver to drain first. Storage
  flushes because `StorageService` flushes, not because the driver was told to.
- **A HEARTBEAT EXISTS AND ACCEPTS ANYTHING AS A PONG.** `rt::heartbeat` sends the reserved opcode
  and returns true for `Polled::Message { .. }` whatever came back, so a driver answering with
  unrelated traffic reads as responsive.
- **THE MECHANISM FOR ACCOUNTING EXISTS AND IS NOT BEING USED.** This item said "a child `Domain` per
  binding already accounts for memory, handles, threads, IPC, DMA and stack", and that is wrong.
  `Domain` does account for all of those, and `spawn_in(elf, bootstrap, domain)` is how a manager puts
  a child under one - but `launch_one` calls `spawn(elf, driver_side)`, which is `spawn_in(.., 0)`,
  and domain 0 means the SPAWNER'S OWN Domain. Every driver in the system is therefore charged to
  DeviceManager, and a driver that exhausts memory exhausts the manager's budget rather than its own.
  So the sub-Domain is a change, not a description. What is genuinely outside `Domain` either way is
  device-specific: MMIO windows, IRQ vectors, IOMMU grants.
- **DEVICEMANAGER'S OWN CRASH IS UNHANDLED.** It holds every claim in the system.
- **AND THE SYSTEM VOLUME'S IDENTITY IS P02M0164'S, ONE MILESTONE EARLIER.** It was an item here
  until the audit of 2026-08-26 put it where its first consumer is: P02M0164 deletes the four block
  slots, and the moment they go, "which disk is the root" has to have an answer. This milestone needs
  the same answer for a different reason - a cold reconstruction must find the volume the boot found -
  and it consumes what P02M0164 built rather than building a second one.

## Work

- [ ] **M1 - `PING`/`PONG { sequence }`, answered by the control loop.** The payload carries the
  sequence and nothing else: P02M0161 put the generation in the frame HEADER, on every frame in both
  directions, so a second copy in the body is a second thing that can disagree with the first. The existing
  `rt::heartbeat` counts any message as a pong, which makes a busy driver and a wedged one look the
  same. On a driver channel the reply is the typed frame, handled by the same loop as every other
  event rather than by a second one. A deadline is declared by the registry entry and is about the
  driver's control path, not whether its device is busy: a driver may not pet its watchdog through an
  unrelated child.

  THE CADENCE COMES OUT OF THE DEADLINE rather than being a second number to keep in step with it:
  the manager pings at half the entry's declared deadline ROUNDED UP, because half of a deadline of
  1 is 0 and a period of zero is either a busy loop or, through the same `wait_any` rule, no timeout
  at all - the two failures this bound exists to prevent, reached by arithmetic. So an entry that asks for a longer
  deadline is pinged less often and never the other way round, and a driver always has one whole
  period to answer in before the deadline it declared.

  The registry requires `0 < deadline <= MAX_HEARTBEAT_DEADLINE`, and the lower bound is not
  pedantry: `wait_any` reads a deadline of 0 as NO TIMEOUT, so an entry declaring zero would not be
  supervised strictly - it would not be supervised at all, and would look like the most responsive
  driver in the machine. The upper bound is one shared policy constant, for the same reason
  P02M0162's bind budget has one: an entry that can name any deadline it likes is an entry that can
  opt out.

- [ ] **M2 - a wedged driver is torn down like a crashed one.** The teardown is P02M0162's
  transaction and the retry and quarantine counter is P02M0162's too; what this adds is the reason
  for starting it, and a bounded diagnostic capture taken BEFORE the process is gone - which is what
  P02M0166 later displays. Bounded means a fixed list, written here so it cannot grow into a
  diagnostic subsystem: the binding id and generation, the state it was in, the cause, the last
  opcode received and how long ago, the restart count, and the Domain's counters at that moment.
  No device payload, no memory dump, no log excerpt.

- [ ] **M3 - one `STOP`, and it means all of it - including that it is not a crash.** Take no new
  work, finish or explicitly abandon what was accepted, flush, call the existing `device_quiesced`,
  answer `STOPPED`. The node carries a stop INTENT into `Stopping`, because P02M0162's table sends a
  confirmed teardown on to `Backoff` and then back to `Binding` - which is right for a driver that
  died and exactly wrong for one that was asked to stop: the operator stops it and it starts again.
  The intent is what `Stopping` resolves against, and there are only four of them:

  | intent | teardown confirmed | teardown NOT confirmed |
  | --- | --- | --- |
  | crash or hang | `Backoff`, or `Failed` when the budget is spent | `Quarantined` |
  | dependency lost | `DependencyPending` | `Quarantined` |
  | operator disable | `Disabled` (P02M0166) | `Quarantined` |
  | shutdown | no further state is entered at all - the manager is going away, so there is no next binding to describe | `Quarantined`, and the report says so |

  An unconfirmed teardown ends in `Quarantined` whatever the intent was, because what is unknown is
  whether the device is still live, and no intent changes that. A separate `QUIESCE`
  followed by `STOP` is two round trips for one transition and the second has nothing left to do. On
  a planned stop the provider is withdrawn and new connections refused FIRST, so nothing arrives
  during the drain. A deadline that expires forces the revocation and says it was forced - never that
  a clean flush happened.

- [ ] **M4 - shutdown traverses dependents in reverse.** A controller being stopped stops its children
  first. NOT bus removal: P02M0163 establishes that the scan runs once and no removal event exists, so
  the only ways a controller goes away are a shutdown and a teardown, and both are asked for from
  inside. The panic path may force revoke and must not claim otherwise.

- [ ] **M5 - one child `Domain` per binding, plus a small device-specific ledger.** DeviceManager
  creates a sub-Domain per binding and launches the driver with `spawn_in` rather than `spawn`, which
  is the change: today every driver is charged to the manager's own Domain. The Domain then accounts
  for memory, handles, threads, IPC, DMA and stack and `DomainStats` already reports them - a second
  set of books for the same resources is work that can only disagree with the first.
  What it does not cover is MMIO windows, IRQ vectors and IOMMU grants, and that ledger is the only
  new accounting - and it cannot live only in DeviceManager, because M6 kills that process and
  expects the next one to know what is still quarantined. The kernel's claim record already tracks
  these resources in order to revoke them, so the ledger is RECONSTRUCTED from it rather than kept a
  second time: one source of truth, and the one that outlives the manager. A failed bind or a restart
  returns both to baseline ONLY where the teardown was
  confirmed. A `Quarantined` node keeps its resources charged and out of circulation, which is the
  whole point of quarantining them - P02M0098 M5 makes the confirmation the precondition for reuse,
  and an accounting that zeroes on the way past would say the frames and vectors are available while
  the device may still be writing to them. Exhaustion is a typed bind failure rather than a
  half-online driver.

- [ ] **M6 - DeviceManager can crash and be rebuilt.** ServiceManager owns its `Domain` and the driver
  subtree under it; if it dies, ServiceManager withdraws the provider roots, kills that Domain and
  only THEN starts a cold reconstruction - otherwise the old drivers still hold claims the new
  manager is about to hand out.

  AND KILLING A DOMAIN IS NOT INSTANT, so the reconstruction reads each claim's state before binding
  rather than assuming it is free. `Domain::kill()` marks the subtree and terminates its processes,
  and `Process::terminate()` closes each handle table SYNCHRONOUSLY - so the claim handle's last
  logical close, and with it the start of P02M0098's forced teardown, happens promptly rather than
  whenever a reference is finally dropped. What is asynchronous is the rest: the terminated threads
  observe the kill at their next scheduling point, and the teardown itself has to confirm the device
  is quiet. This item first blamed the delay on the last references, which is the wrong half. Either
  way a new manager can legitimately arrive at a device that is `Releasing`. Treating that as a refusal would be a permanent `Failed` for a state that was about
  to clear on its own, because P02M0162 classifies `claim-refused` as not retryable - a transient
  condition promoted to a terminal one by two correct rules meeting. So, and "waits and then binds"
  is not one of the branches - a bind is attempted only on an OBSERVED `Free`, never on a deadline
  having merely passed:

  | state read | what the reconstruction does |
  | --- | --- |
  | `Free` | bind normally |
  | `Releasing` | re-read until `Free`, bounded by the incident deadline this milestone already has |
  | `Releasing` still, at that deadline | do NOT acquire: `Quarantined` with `teardown-unconfirmed`, which is the conservative answer and the true one - nothing observed the device go quiet |
  | | AND THE KERNEL LATCHES IT TOO. A binding marked `Quarantined` in userspace while the kernel's claim stays `Releasing` is two authorities again: a late teardown reaching `Free` would put the frames and vectors back into circulation against a state that had already been declared terminal. The claim record carries the SAME hard deadline and latches `Releasing -> Quarantined` itself, atomically; a completion arriving after that is recorded as late and releases nothing |
  | `Quarantined` | adopt it; it is already terminal |
  | `Claimed` | an invariant violation, reported as one - a correct `domain_kill` cannot leave it here, and a manager that quietly rebound over it would be handing out a device somebody still holds |

  The new manager has no claim handle to be woken on, because the old one died with its Domain, so
  this is a bounded poll by device index from the wait loop it already runs - not a new mechanism and
  not an unbounded one. ONE READ ANSWERS BOTH QUESTIONS: the privileged snapshot returns the
  generation, the claim state and the resources still held for that device, so polling the state and
  rebuilding the ledger are the same call rather than two sources that can disagree. It never inherits a live claim it cannot account for, and it finds
  the same system volume again because P02M0164 made that a question with an answer.

- [ ] **M7 - a named table of the races that are reachable.** Reachable in THIS tree, which is what
  makes it a table and not a wish: a driver answering `READY` after its deadline, a crash between
  publish and subscribe, a crash with DMA in flight, a watchdog expiry racing a clean exit, a
  DeviceManager restart with drivers still live, and a `STOPPED` that arrives after the deadline it
  was supposed to beat - which must NOT turn a forced teardown back into a clean one. Once the forced path has been
  entered the outcome is decided; a late answer is recorded as late and changes nothing, because the
  alternative is a report that says a driver flushed when the manager had already stopped waiting. A device removed mid-bind is NOT on it - there is no
  removal event to race with. A cartesian product of every event against
  every other is a way of never finishing; a named list is a plan. After each: at most one claim
  owner, no stale provider, no leaked process, handle, vector, mapping or counter.

## Definition of done

- A driver that stops making progress is detected, torn down and rebound or quarantined, and an idle
  driver is not.
- A frame with the wrong opcode, a stale generation or an out-of-order sequence does NOT reset the
  watchdog, with a test per case. This is the whole of what `rt::heartbeat` gets wrong today - it
  returns true for any `Polled::Message` - so a `PING`/`PONG` that was only added, and never proved
  to refuse the three things the old one accepted, would leave a wedged driver looking healthy for
  the same reason it does now.
- A planned stop that completes leaves the binding at rest and does not restart the driver.
- One `STOP` drains or cancels in-flight work and reaches `STOPPED` before revocation, with the
  provider withdrawn first; a forced teardown says it was forced.
- Every driver runs in its own sub-Domain rather than the manager's, and every resource is charged to
  a binding through that Domain plus the device ledger. A failed bind or a restart whose teardown was
  CONFIRMED returns the counters to baseline, asserted rather than assumed; one that was not leaves
  them charged, which is what `Quarantined` means. Not every field: `DomainStats::memory_peak` is a
  high-water mark and is meant never to fall, so an assertion that "every counter returns to
  baseline" would be asserting against a diagnostic doing its job.
- DeviceManager can be killed and reconstructed without a claim being left owned by nothing, and the
  reconstruction finds the same system volume.
- The named race table is registered as a gate and has been watched to fail.

## What this milestone refuses, and why

- **Suspend and resume of the whole machine.** Planned stop is what a driver needs to be taken away
  safely. System power states are a separate subject with their own firmware surface, and nothing
  here needs them.
- **A general watchdog service.** The deadline belongs to the binding, beside the thing it is
  watching.
- **Predicting hardware failure.** Quarantine after a declared number of failed rebinds is a policy
  anyone can read. Anything cleverer is guessing.
