# P02M0135 - Foreign graphics-stack prerequisites

Status: FUTURE TRACK. INDEPENDENT OF P02M0103 AND NOT A PHASE-2 COMPLETION GATE.

Split out of `P02M0103` on 2026-08-15. It lived there as `P02M0103a2` and nothing in `P02M0103`
depended on it - the software 2D and 3D stacks are `no_std` Rust and never needed a C++ substrate.
Keeping it there meant a milestone about building a 2D/3D library also had to be about cross
compilers, ELF TLS and upstream license provenance, which is two milestones wearing one number. The
split changes no content and no decision; it changes what each milestone is answerable for.

Needed before importing Mesa, a Vulkan loader or any upstream C/C++ graphics stack. It gates none of
`P02M0103`, and `P02M0103` gates none of it: the two can be built in either order or at the same
time.

## What this milestone claims, and what it does not

Corrected 2026-08-30 after the 2026-08-30 plan audit. The first version promised an "exact
required-symbol inventory derived from a chosen Mesa or Vulkan-loader configuration" and, four
bullets later, that it imports none of those projects and that a synthetic build proves the audit
path. Both cannot be true. An inventory derived from nothing is a guess, and a guess is exactly what
the first real import discovers - which is the failure this milestone exists to prevent.

The claim is therefore narrowed and made derivable:

**This milestone prepares the substrate for ONE NAMED, PINNED upstream configuration, and says so.**
It does not prepare "Mesa, a Vulkan loader, or any upstream C/C++ graphics stack". Evidence gathered
against one configuration cannot carry a claim about the others: they differ in libc surface, C++
runtime use, TLS models and discovery layout, and those differences are the substance of the work.
A second consumer earns a second, separately approved profile that reuses this milestone's
mechanisms and re-derives its own inventory.

**The pinned upstream is an AUDIT-ONLY input, and the one term for it is AUDIT-LINKED AND
QUARANTINE-STAGED** (corrected 2026-08-30). "Discarded" was the previous term and it made this
milestone's own guest evidence impossible: the launch path resolves executables and libraries
from
manifest-generated tables and admits a dynamic image only with an expected identity and an exact
`DT_NEEDED`/provider closure, so an artifact that is never staged and never manifest-named cannot
traverse it - and the guest gate requires exactly that traversal. Both requirements cannot hold, so
the one that is really needed is stated: what this milestone refuses is PRODUCTION IMPORT, not the
existence of the file.

    QUARANTINE STAGING     a TEST-ONLY manifest role and a test-only image, built by the gate and
                             used by nothing else. The audit-linked ELF is named there so it can be
                             launched, checked and observed. It is deleted with the test image.
    PRODUCTION IMPORT      refused, and that refusal is what this milestone is about: the artifact
                             is absent from the shipping manifest, absent from every shipping image,
                             and named by no production role. A gate asserts that the shipping image
                             contains no artifact derived from the pinned upstream, watched to fail.

  The distinction is the one the audit link already rests on - measuring is not importing - now
  applied to staging as well. It is fetched once, offline, from a recorded archive digest, cross-compiled
to objects, LINKED against the substrate this milestone builds, inspected, and QUARANTINE-STAGED for
the guest gate alone. Nothing it produces is imported, installed, or named by any production
manifest, and its test image is deleted with the gate that built it.
"COMPILE-ONLY" was the previous wording and it contradicted pass 2 below, which links; "never linked
into anything" was the same error. The distinction that matters is IMPORT, not link: linking to
measure is how the inventory is settled, and importing is what this milestone refuses.

**The inventory is derived in TWO passes, and the second one LINKS** (corrected 2026-08-30). The
previous version rejected any link as circular, and that was wrong in a way worth stating: a final
link needs a substrate, so it cannot come FIRST - but it is not circular to build the substrate from
the object closure and then link against what was built. That is a second pass, and it is the only
thing that proves the first one right.

    pass 1, OBJECTS      compile the pinned configuration to its complete object closure and take
                         every undefined symbol. This is a CANDIDATE surface and is explicitly not
                         the external closure: per-object undefined symbols include references other
                         upstream objects satisfy, so it over-states what the substrate must supply.
    pass 2, AUDIT LINK   build the substrate from that candidate, then LINK the pinned configuration
                         against it for all three targets and inspect the link map and the final ELF.
                         Archive member selection, weak and COMDAT resolution, symbol versioning and
                         visibility, generated members and compiler-runtime selection all happen
                         here and nowhere else.

The audit link is NOT an import: its output is inspected, quarantine-staged for the guest gate and
then dropped, and no PRODUCTION manifest names it - the same rule the objects are under. And that ELF
is not exempt from
this tree's artifact checks; it is the artifact this milestone's whole surface claim is derived from,
so it runs through them (see the audit-link item's gates below). What it settles that pass 1 cannot: which
candidate symbols were never needed (the substrate stops supplying them), which requirements only
link-time selection reveals (the substrate gains them), and the FINAL `PT_TLS` question, which
Variant B's own gate demands of a linked ELF and which no object-only inspection can answer.

Without pass 2 the gate can demand internal symbols that need no substrate, miss link-selected
requirements, and pass while the pinned configuration still cannot link - which is a substrate that
is complete by its own measure and unusable by its consumer's.

## Items

- [ ] **Record the dependency and licensing policy FIRST, before any upstream source is fetched.**
  MOVED TO THE HEAD OF THIS LIST 2026-08-30: it said it precedes pinning and sat five items below it,
  and an ordering rule stated after the thing it orders is a rule nobody follows.
  LiberSystem-owned implementation stays Unlicense; imported Mesa, Vulkan loader, compiler runtime
  or conformance sources keep their own compatible notices with exact source, version and patch
  provenance. The image identity records bind generated objects to that inventory, and the build
  rejects an unreviewed licence, a downloaded-at-build source and a copied implementation with lost
  attribution. This item precedes the pinning item above in ORDER, because a policy written after
  the source has been chosen is a policy fitted to the choice.
  This milestone imports no upstream project into the image; the pinned configuration is an
  audit-only input under the same licence review as anything else that enters the tree.

- [ ] **THE PINNED CONFIGURATION IS THE VULKAN LOADER, AND THIS FILE PICKS IT** (decided 2026-08-30).
  The previous version told the implementer to "choose ONE of Mesa or a Vulkan loader" and record the
  details later, which is a choice deferred rather than a pin made - and every dependent branch in
  this file (threads, C++ policy, TLS, discovery) is scoped by that choice, so none of them could be
  decided either. Mesa and a Vulkan loader differ in build system, headers, runtime surface,
  threading and TLS behaviour, licensing closure and discovery model; picking one is what turns this
  file from a shape into a plan.

  **`Vulkan-Loader` (KhronosGroup), Apache-2.0.** The licence is corrected here (2026-08-30): a
  previous round wrote MIT, and the project's own `LICENSE.txt` is Apache-2.0 with more-permissive
  exceptions on some files. That is not a fatal difference - Apache-2.0 is permissive and this is an
  audit-only input - but a wrong licence in a plan whose licensing item is "a check rather than an
  analysis" turns the check into a rubber stamp. The per-file closure is determined and recorded by
  the licensing item, not asserted here.

  **AND IT IS TWO PINNED PROJECTS, NOT ONE.** `Vulkan-Headers` is a separately versioned KhronosGroup
  repository and a required build dependency of the loader; a pin that names only the loader does not
  identify a buildable configuration. Both are pinned, both are digested, and their compatibility
  (the loader builds against the header revision named) is part of what the lockfile records.

  Chosen over Mesa for four reasons that are properties of the projects rather than preferences:
  - It is the SMALLEST upstream that exercises the mechanisms this milestone is about - a foreign
    ABI substrate, a discovery model, and a provider ABI - where Mesa additionally drags in LLVM, a
    shader compiler and a driver stack, none of which this milestone claims. It is a C99 project in
    production; "a C/C++ substrate" was the previous wording and it overstated what this consumer
    demonstrates (see the C++ item).
  - Its DISCOVERY MODEL is the reason the discovery item exists at all: ICD manifests are what the
    loader is FOR, so pinning it makes that item concrete instead of hypothetical.
  - Its licence is permissive throughout the closure this milestone would build - Apache-2.0 with
    more-permissive per-file exceptions - which keeps the licensing item a bounded check rather than
    a copyleft analysis.
  - Mesa is the eventual consumer and is NOT excluded: it becomes a second profile, separately
    approved, re-deriving its own inventory against the substrate this one establishes. That is the
    rule this file already states - evidence from one configuration cannot carry a claim about
    another.

  **THE LOCKFILE IS TWO PINS WITH A STATED FREEZE ORDER, NOT ONE GATE ON EVERYTHING**
  (corrected 2026-08-30). Making one complete lockfile a gate on every other item was
  self-blocking, and the audit is right about the cycle: that lockfile had to digest the platform-port
  patch, which is a later deliverable; the three toolchain files; and the sysroot - while the sysroot
  is sized from "the facilities the inventory names" and pass 1 cannot produce that inventory without
  a sysroot to compile against. The implementer would have had to violate the first gate to create
  the inputs the gate demands.

  So the pin is split, and each half gates what it can actually precede:

    BOOTSTRAP PIN, frozen FIRST and gating pass 1. Everything that exists independently of this
      milestone's own work: both project revisions and archive digests; the three cross/toolchain
      files with their digests; the compiler, archiver and linker identities, versions and flags; the
      full CMake option set; and the generated-source policy. Pass 1 compiles against a MINIMAL
      BOOTSTRAP SYSROOT - the C99 headers and stubs the configuration needs to compile at all, which
      is a question the option set answers rather than the inventory - and that sysroot's digest is
      recorded here too. This half contains no output of this milestone and therefore has no cycle.

    DERIVED PIN, frozen at the END of pass 2 and gating COMPLETION. What this milestone produces and
      must not then drift: the ordered platform-port patch series with a digest per patch, the final
      profile sysroot digest, the generated-source digests as actually produced, and the
      compiler-runtime component selected by the converged link.

  The freeze order is therefore: bootstrap pin -> pass 1 -> substrate -> platform port -> pass 2
  converging link -> derived pin. Nothing may start before the bootstrap pin, and nothing may be
  declared done before the derived pin. A build that takes any pinned value from anywhere but the
  half of the lockfile that owns it fails.

  Both halves are checked in and the build READS them rather than duplicating their values.
  The BOOTSTRAP half carries:
  - both projects - `Vulkan-Loader` and `Vulkan-Headers` - each by exact revision and by the SHA-256
    of its source archive, with the statement that the loader revision builds against that header
    revision;
  - the CMake option set IN FULL, not the non-default subset. The options that change what the
    inventory contains are named explicitly so none is left implicit: `BUILD_TESTS` (OFF - it is the
    only reason C++17 would be required, see the C++ item), each `BUILD_WSI_*_SUPPORT` (all OFF -
    LiberSystem is none of those window systems, and they are what pull in X11/Wayland/XCB), the
    assembly/dispatch option, the loader-layer and debug options, and the install and shared/static
    choice;
  - the GENERATED-SOURCE policy: which sources the build generates from the registry, whether they
    are generated during the audit build or vendored, and their digests either way - generated code
    that is not pinned makes the inventory unreproducible;
  - the three cross/toolchain files, one per target, each with its digest;
  - the compiler, archiver and linker identities, versions and flags; and
  - the BOOTSTRAP sysroot digest.

  The DERIVED half carries the ordered platform-port patch series with a digest per patch (or the
  explicit statement that there is none), the generated-source digests as produced, the final profile
  sysroot digest, and the compiler-runtime component the converged link selected.
  Sources are fetched ONCE and vendored or content-addressed; a build that downloads is a build that
  is not reproducible, and it is refused by the licensing item below.
  This input is AUDIT-ONLY: compiled, audit-linked, inspected and quarantine-staged for the guest
  gate. Nothing it produces is imported into a shipping image or named by a production manifest.

- [ ] **Derive the candidate surface from the object closure (pass 1).** For each of the three
  targets, compile the pinned configuration to its complete object
  closure and record: every undefined symbol with its type and binding; every symbol the
  configuration expects from a compiler runtime; every TLS symbol, `PT_TLS` segment and TLS
  relocation form; every relocation form used; the C++ ABI facilities actually referenced -
  `__cxa_*`, unwind personality/RTTI symbols, `.init_array`/`.fini_array` entries, `atexit`
  registration, `errno` access; and the discovery-metadata layout the configuration reads at
  runtime. The three targets are recorded SEPARATELY and the differences between them are part of
  the evidence: an inventory that is the same on all three has not been derived from three builds.
  The inventory is a generated artifact with a digest, regenerated rather than edited, and a
  regeneration that differs from the recorded one fails the gate.

- [ ] **Settle the inventory by an AUDIT LINK against the built substrate (pass 2).** Link the pinned
  configuration against the substrate, for all three targets, with nothing staged and nothing kept
  but the evidence. Record and compare: the link map; every symbol the link resolved out of the
  substrate; every candidate symbol it did NOT need, which is removed from the substrate rather than
  left as surface nobody requires; every requirement that only link-time selection produced - archive
  members, weak and COMDAT resolution, symbol versions, compiler-runtime members - which is added;
  and the FINAL ELF's program headers, which is where `PT_TLS` is answered.
  THE LINK IS STRICT AND IS REPEATED UNTIL IT CONVERGES (2026-08-30): no host default library paths,
  no default libraries, and no unresolved symbols permitted - a link that silently pulls a host libc
  measures the host and not the substrate. And removing or adding substrate symbols after one audit
  link can itself change archive-member and weak selection, so the loop is: link, adjust the
  substrate to what the link resolved, relink. The gate is the FIXED POINT - two consecutive links
  producing the same resolved set on all three targets - not the first link's output.
  The substrate's declared surface is then EQUAL to what the audit link resolved, per target, and
  that equality is the gate. Object-closure equality is not the gate and never was: it over-states the
  surface, because a per-object undefined symbol may be satisfied by another upstream object.

- [ ] **OWN A MINIMAL CROSS SYSROOT, because pinning compilers and flags does not give C sources
  anything to include** (added 2026-08-30). The lock names compilers, cross files and flags; a C or
  C++ translation unit additionally needs HEADERS and a target ABI, and this tree has none. The
  architecture puts compiler targets, a sysroot, ABI bindings and linker support in future native-SDK
  work, so there is nothing to inherit either.
  Without one, the three-target compile gate is not merely unproven - it is impossible except by
  silently using the HOST's libc and sysroot, which derives the wrong ABI for a freestanding target
  and drags in exactly the general POSIX surface this milestone forbids. That failure is silent: the
  build succeeds and the inventory is wrong.
  This milestone owns a PROFILE-SPECIFIC sysroot, sized by the pinned configuration and by nothing
  else: the target triple and data model per architecture; the headers the pinned sources actually
  include, and no others; the type sizes, alignments and struct layouts they depend on; the constants
  and prototypes for the facilities the inventory names; and the compiler builtins the pinned
  compiler emits calls to. It is versioned, licensed and digested like any other input, and bound
  into the lockfile, the inventory, the cache key and the image identity - so a header change moves
  the inventory rather than silently changing what was compiled.
  IT IS NOT A LIBC. Headers for what the substrate provides, and nothing for what it does not: a
  header declaring a function the substrate has no symbol for is a compile that succeeds and a link
  that fails, which is the POSIX layer arriving through the include path instead of through the
  symbol list.

- [ ] **Provide EXACTLY the foreign ABI facilities that inventory names, and nothing beyond them.**
  Allocator, memory/string/math, monotonic time, atomics, mapped MemoryObjects; mutex, condition and
  once primitives under the single-threaded contract stated below; NO thread creation or join, which
  the item below makes a measured stop condition rather than a facility; thread-local storage ONLY
  under the TLS item below; provider lookup ONLY under the discovery item below. Do not grow a
  general POSIX layer and do not expose ambient files, processes or devices. A facility that the
  derived inventory does not name is not built: this milestone's scope is the closure of one
  configuration, and every symbol outside it is a POSIX layer arriving one function at a time.

- [ ] **THE PINNED CONFIGURATION CREATES NO THREADS, AND THAT IS WHAT THE INVENTORY MUST SHOW**
  (decided 2026-08-30). Two rounds recorded a self-thread runtime as an unowned prerequisite and then
  as a hard block, and neither gave it an owner - which left this milestone unschedulable on a
  mechanism it may not even need. The block is removed by separating two things the previous version
  ran together:

    SYNCHRONISATION      mutexes, condition variables and once-initialisation. `Vulkan-Loader` is
                           thread-SAFE by specification - it serialises its own dispatch so that a
                           multi-threaded caller is safe - and that establishes a synchronisation
                           surface. In a process that creates no threads, those primitives are
                           satisfiable without any new kernel mechanism: an uncontended lock is a
                           counter, and once-initialisation is a flag. The substrate supplies them
                           with a DOCUMENTED SINGLE-THREADED CONTRACT and says so in the ABI notes,
                           so nobody later mistakes them for a concurrency implementation.
    SELF-SPAWN AND JOIN  `pthread_create`, `pthread_join`, `pthread_detach`. Thread SAFETY does not
                           imply thread CREATION, and the previous version inferred one from the
                           other. This is the facility that needs a runtime that does not exist.

  So the configuration is pinned WITHOUT thread creation - `BUILD_TESTS=OFF` removes the test
  harness, which is where a loader's own threads would come from - and the exact-surface rule decides
  the rest by measurement: **if pass 1's inventory names any thread-creation symbol on any target,
  this milestone STOPS and the self-thread runtime becomes a numbered prerequisite before it
  resumes.** That is a gate on a derived fact, not an assumption, and it is the honest form of a
  question that cannot be answered until the configuration is built.

  What such a runtime would have to own, recorded so whoever numbers it has the contract rather than
  the sentiment: narrow self-spawn authority that is not process-management authority; independently
  placed guarded stacks with their own accounting; join and detach with a defined exit and
  failure-propagation contract; per-thread runtime state initialisation; and blocking synchronisation
  with a stated memory-ordering and wakeup contract, including a resettable or paired wakeup object.
  The tree has none of it today: a new process receives only its bootstrap channel;
  `SYS_THREAD_CREATE` requires `MANAGE` on an explicit Process handle, which an ordinary application
  does not hold over itself; `rt::process_prepare` is the process-LAUNCH path and always uses the one
  `USER_STACK_TOP`; demand stack growth is bound to that same span; Thread is not waitable, so there
  is no join; and Event's only reset is `#[cfg(test)]`.

  `P02M0103` needs the same mechanism for its renderer worker pools and has likewise removed it from
  everything mandatory. Neither file is now blocked on an unnumbered milestone, and whoever numbers
  it owns ONE contract for both consumers; two private thread runtimes for one system is the failure
  this paragraph exists to prevent.

- [ ] **Decide the C++ ABI, mechanism by mechanism - and under this pin the expected answer is
  FORBIDDEN.** Exception tables and unwinding, RTTI, static initialisers and their ordering, `atexit`
  registration, and the `errno` model each get ONE of two answers, written down: the supported ABI
  with its named owner, or the exact compiler flags plus the artifact check that forbids it. Neither
  answer may be "audit it".

  **THE PINNED CONFIGURATION IS C99 IN PRODUCTION, SO THIS ITEM IS SCOPED TO WHAT IT ACTUALLY NAMES**
  (corrected 2026-08-30). `Vulkan-Loader`'s documented production requirement is C99; C++17 is
  required for its TEST SUITE, and `BUILD_TESTS` defaults off and is pinned OFF here. So the previous
  version's extensive C++ ABI and lifecycle work was not derived from the selected consumer, which
  contradicts this file's own exact-surface rule - a facility the inventory does not name is not
  built. Enabling the upstream test suite to force C++ into the inventory would size the substrate to
  a test harness rather than to the runtime, and would pull in GoogleTest as well; it is refused.

  Therefore: each mechanism is decided by what pass 1 and pass 2 actually name. Where the inventory
  names nothing, the answer is FORBIDDEN, and the deliverable is the compiler flags plus a build-time
  artifact check with a watched-fail mutation on every target - which is cheap, is worth having, and
  is the whole of the C++ work under this pin. Where the inventory DOES name a mechanism, the
  supported-ABI answer below applies to that mechanism and to no other.

  If a later profile wants to prove C++ support, it pins a genuine production C++ consumer and
  re-derives its own inventory; that is the same rule this file already applies to Mesa.
  The tree's current state is the reason this cannot be deferred: `liber_rt_start` performs the ABI
  check and calls the program entry directly, so no constructor or destructor runner exists at all,
  and all three ordinary userspace linker scripts `/DISCARD/` every `.eh_frame*` section - so a C++
  object that compiles and links silently loses its unwind metadata. A symbol-complete synthetic C
  program passes every check this milestone would otherwise run while real C++ is broken.
  Where a mechanism IS supported, state: once-per-process init and fini ordering across the provider
  DAG, what happens when initialisation fails part way, normal exit versus crash semantics, and the
  unique owner and licence of the compiler-runtime, C++ ABI and unwind components. Where it is
  forbidden, the artifact check is a build-time refusal with a watched-fail mutation, on every
  target.

- [ ] **Resolve the TLS blocker as ONE of two variants, and make each variant's evidence
  executable.** `docs/DYNAMIC_LINKING.md` refuses TLS relocations by name, and the package audit and
  runtime loader share that one relocation policy. TLS is MANDATORY if and only if the derived
  inventory shows `PT_TLS`, TLS symbols or TLS relocations. Which variant applies is decided by that
  inventory, and the substrate and inventory items above are built to match it.

  - VARIANT A - SUPPORT IT. `docs/DYNAMIC_LINKING.md` changes, AND the mechanism is implemented and
    proved, because a design document is not TLS. It states: the supported code-generation models
    and the exact relocation forms admitted per target; the TCB, DTV and module-offset layout; the
    initialisation image and its alignment rules; how the initial thread and every later thread are
    set up; the thread-pointer set/save/restore contract on x86_64, aarch64 and riscv64; the policy
    for dynamic accessors; per-thread block allocation, its Domain accounting, and teardown
    including TLS destructors. The package audit and the runtime loader must both ADMIT the chosen
    forms - the two share one policy and changing one without the other is an image that stages and
    will not run, or runs and will not stage. Positive evidence is per-thread isolation observed in
    a guest, not a document.
    Variant A therefore depends on a thread-creating runtime, which the no-thread-creation pin above
    deliberately does not have: with one thread there is no isolation to observe, so Variant A is not
    provable under this pin. If the inventory forces TLS anyway, that is the second measured stop
    condition in this file and it is resolved the same way - by numbering the runtime, not by
    weakening the evidence.

  - VARIANT B - AVOID IT. The configuration is pinned such that it emits ZERO TLS requirements, and
    the audit PROVES the absence rather than assuming it. The scan covers every admitted `ET_REL`
    member INCLUDING compiler-runtime and generated objects, and the AUDIT-LINKED ELF - which is
    quarantine-staged rather than shipped - not a standalone inventory taken
    once - looking for `PT_TLS`, `STT_TLS` symbols and every TLS
    relocation form. The complete scan input list and its result are bound into the cache key and
    the image identity, so a flag, a compiler-runtime change or a new generated object that begins
    emitting TLS invalidates the evidence instead of silently outliving it. Both the build-time and
    the runtime refusal are mutation-tested and watched to fail.

  Whichever is chosen is named in the Done condition. A substrate that promises TLS while the audit
  is meant to prove there is none is neither.

- [ ] **Define how foreign artifacts enter the manifest, build, cache and identity graph - as a
  first-class kind, not as an exception.** "Host build tooling must accept reproducible Meson/CMake
  object lists without bypassing the identity, relocation, W^X, provider and licence audits" names
  the requirement and no mechanism, and no mechanism exists:
  every manifest source must contain a `Cargo.toml` and every library destination is derived from a
  Rust source-ownership category; `build-shared.sh` asks Cargo for the dependency closure and
  inventories only Rust/Cargo/linker inputs; and the identity record is a fixed-order, Rust-specific
  grammar - `rustc-commit` as 40 hex digits, `rustflags` that must start with
  `-C relocation-model=pic`, non-empty Cargo `features` - which both the packager and ProcessService
  enforce exactly. A foreign artifact can therefore only enter by forging meaningless Rust fields,
  by being appended after identity generation, or by a private fork of the staging graph. All three
  put source, patches, compiler output, providers or licence obligations outside cache invalidation
  and runtime verification.
  This milestone owns the representation:
  a foreign source and artifact kind in the system manifest with a deterministic, ordered object-list
  format; a language-neutral image identity - a new version, not a reinterpretation of the existing
  one - binding the exact compiler, archiver and linker artifacts and flags, the target and sysroot,
  the configure inputs and generated files, the complete source/patch/licence closure, the final
  objects, and the direct providers;

  **AND THE MIGRATION IS DECIDED HERE, NOT DISCOVERED DURING IT** (added 2026-08-30). "A new version"
  says nothing about what happens to the artifacts that already exist, and every current route
  rejects anything but v1: ProcessService parses v1 with Rust-specific fields, the packager asserts
  the same, the shared compatibility path requires those fields and refuses every other format, and
  device publication independently enforces it. A foreign v2 artifact is refused four times over,
  and a half-migration breaks mixed closures or hot publication instead.

    the shape          v2 REPLACES v1 image-wide. Not version-dispatched, not coexisting: two
                       formats in one provider closure means every reader carries two parsers and
                       every provider-digest comparison has to say which format it is comparing, and
                       this image is built as one artifact from one tree - there is no released v1
                       artifact anywhere that a v2 image must interoperate with.
    the fields         a COMMON section every artifact has - format, kind, artifact, package,
                       source digest, target, profile, and the direct-provider digests - and a
                       LANGUAGE section keyed by producer: `rust` carries `rustc-commit`,
                       `rustflags` and `features`; `foreign` carries compiler, archiver and linker
                       identity, flags, sysroot digest and the configure-input digest. A reader that
                       needs only the common section never parses the other.
    provider digests   over the COMPLETE canonical v2 record, common section AND language section
                       (corrected 2026-08-30). A previous round said "the COMMON section only, so a
                       cross-language edge is an ordinary edge", and that was unsound: a provider
                       could change its compiler, linker, flags, sysroot, configure-input digest,
                       rustflags or features - every one of them able to change ABI and code
                       generation - without changing the digest its consumers embed, so a stale
                       consumer or a stale cache entry would pass after an ABI-affecting rebuild.
                       It also WEAKENED the current contract, in which build, packaging and
                       ProcessService all hash and compare the complete record. The cross-language
                       concern it was solving does not require it: a consumer HASHES the language
                       section, it does not PARSE it, and hashing bytes needs no knowledge of their
                       producer. The common/language split therefore governs who must UNDERSTAND
                       which fields, and not what identity covers.
                       If a future need arises to compare only ABI-affecting inputs, that is a
                       separately defined ABI DIGEST covering every ABI-affecting producer field -
                       not a digest that omits fields because one reader finds them opaque.
    the transition     COLD. Every artifact in the image is rebuilt to v2 in one change; there is no
                       boot in which some providers are v1 and some are v2, and therefore no hot
                       publication across formats to design. The gates that must move with it are
                       named: `mkpackages`, ProcessService, the shared compatibility path, and
                       device publication - all four, in that change, because any one left behind
                       refuses the whole image.
 and the coordinated changes across `system-manifest`,
  `build-shared.sh`, `mkpackages`, ProcessService, the shared ELF/identity parser, the
  staged-consistency gate and the cache keys, each named. Negative identity tests are part of it:
  a foreign artifact with a malformed, absent or wrong-target record is refused at packaging AND at
  launch, watched to fail.
  Foreign artifacts pass the EXISTING relocation, W^X, export-owner, provider-closure and runtime
  revalidation paths. They do not get a parallel audit, because a parallel audit is the thing that
  drifts.
  Mutation tests for the identity change, watched to fail: a provider rebuilt with a different
  compiler, a different flag set, a different sysroot digest, a different configure-input digest,
  different rustflags and a different feature set must each change the provider digest, invalidate
  every consumer edge that names it, and invalidate the cache key. A digest that survives any of
  those is the defect this correction exists to prevent.

- [ ] **Choose ONE loader/ICD discovery model, and prove the selected provider actually loads.**
  The policy this milestone freezes is unchanged and stays right: paths are package-owned and
  identity-checked, metadata is bounded and versioned, and there is no environment-variable search
  path, no current-directory plugin load and no arbitrary `dlopen`. What was missing is the loading
  and authority model, without which selection proves nothing: the current model loads the exact
  manifest and `DT_NEEDED` provider closure, verifies each identity edge, and starts the first
  thread only after every eager relocation completes, with lazy binding, replacement, unload and
  search paths all forbidden. There is no `dlopen`/`dlsym` seam, no declared role for a metadata
  file, and no owner holding a narrow capability to enumerate candidates. A post-start loader cannot
  add an ICD without bypassing the identity closure; handing the application StorageService
  authority to scan candidates recreates the ambient-file policy this milestone forbids.
  **DECIDED 2026-08-30: (a) PRE-LAUNCH SELECTION, AND PROCESSSERVICE IS THE ACTOR.** ProcessService
  selects the ICD before the process starts and adds it to the verified closure - one actor, because
  the edge must exist before the closure is built and ProcessService is what builds it. A recommendation was
  not a decision, and the other two are now rejected on grounds this file already holds:
  (b) DECLARED CANDIDATE SET is incompatible with the loader as it stands. Eagerly loading every
  candidate means several providers exporting the same Vulkan entry points into one closure, and the
  current model rejects duplicate providers outright - so it needs a symbol-namespace or collision
  design that is a loader redesign, not a discovery choice.
  (c) OUT-OF-PROCESS PROVIDER needs a graphics-call channel protocol, and every GL and Vulkan ABI is
  deferred by name in this same file. It would have this milestone design the protocol whose API it
  refuses to export.
  (a) needs no new PROCESSSERVICE mechanism, because selection happens before the closure is built.

  **BUT IT DOES NEED A LOADER PORT, AND THAT IS A DELIVERABLE OF THIS MILESTONE** (2026-08-30). The
  previous version said "needs no new loader mechanism" and meant this system's loader; the sentence
  read as though the pinned upstream needed nothing either, which is false and would have let the
  synthetic selector gate pass while the audit target still could not load an ICD. Upstream's Unix
  platform layer discovers drivers through the filesystem and the environment and then opens the
  selected one with `dlopen`, resolves its entry points with `dlsym` and releases it with `dlclose`.
  There is no LiberSystem branch in it. Adding an ICD to ProcessService's eager closure gives the
  already-mapped loader neither a handle nor a symbol-query API, so pre-launch selection answers
  DISCOVERY and answers nothing about LOADING.

  **THE MODEL IS DECIDED HERE, NOT LEFT AS QUESTIONS FOR THE PORT TO ANSWER** (corrected
  2026-08-30). A previous version listed what the port "states" and named no mechanism, and the two
  facts that constrain it are both in the tree: ProcessService discovers only `DT_NEEDED` edges and
  requires the identity provider set to EQUAL them, and the kernel's export registry is a
  process-wide flat `Vec<(String, u64)>` with no module provenance and no ring-3 query at all. So
  neither "add the selected ICD" nor a provider-bounded `dlsym` is expressible today.

    THE ACTOR             ProcessService. Not "or a narrow registry" - one actor, because the edge
                            has to be added before the closure is built and ProcessService is what
                            builds it.
    THE IDENTITY EDGE     the selected ICD becomes an ORDINARY DECLARED DEPENDENCY of the consumer
                            for this launch: ProcessService reads the metadata record, resolves it to
                            a staged provider, and adds that provider to BOTH the dependency set and
                            the expected identity set before the equality check runs - so the
                            existing "identity set equals `DT_NEEDED` set" invariant holds with the
                            ICD inside it rather than being weakened to admit it. A record naming a
                            provider that is not staged, or whose identity does not verify, fails the
                            launch; nothing is loaded after the first thread starts.
    SYMBOL RESOLUTION     ONE WELL-KNOWN ENTRY SYMBOL PER ICD, and no `dlsym` equivalent at all.
                            The Vulkan ICD ABI is already shaped this way - a driver exposes a single
                            documented entry point and every further address comes from the function
                            pointer it returns - so the port resolves that ONE symbol as an ordinary
                            provider export at load time and goes through it thereafter. This is the
                            decision that keeps the milestone bounded: a provider-scoped export query
                            would need module provenance in the kernel's export table and a new ring-3
                            syscall, which is a kernel redesign this milestone has no business doing
                            for a substrate audit.
    `dlopen`/`dlclose`    become "take a reference to the already-verified provider" and "drop it".
                            They open nothing and can fail only by naming a provider that is not in
                            the closure.
    FAILURE AND ROLLBACK  every replaced call returns the upstream error the platform layer already
                            handles; a failed selection leaves no partially built closure, because
                            selection happens before the closure is built and a failed record refuses
                            the launch outright.

  The port is pinned in the DERIVED half of the lockfile, like every other modification this
  milestone produces.

  This is the largest single piece of work the pinned configuration implies, and naming it is what
  keeps this milestone's claim honest: a substrate that satisfies every undefined symbol and still
  cannot load an ICD has not prepared anything.
  Whichever is chosen states: the metadata owner and its P02M0097-compatible path and manifest role;
  the capability flow; deterministic duplicate, version and extension selection; the binding between
  the metadata and the code it names, and how that binding resists a change between check and use;
  export-collision behaviour; and accounting and rollback on a failed selection.
  The exact manifest FIELDS - API name and version, architecture, entry provider, backend
  identifier, required extensions - are still designed against the configuration this milestone
  pins, by the same rule that deferred `P02M0103`'s adapter/device/context/queue vocabulary. What is
  no longer deferred is the mechanism the fields are carried by. Selection and refusal are exercised
  through the real launch path with a synthetic provider; a synthetic in-process parser choosing a
  record is not evidence that the record's code can be loaded. AND THE GUEST GATE EXERCISES THE
  PORTED LOADER ITSELF, not only a separate synthetic selector: the audit-linked `Vulkan-Loader`
  runs in a guest against a synthetic ICD, reaches its entry points through the replaced
  `dlopen`/`dlsym` path, and a candidate that fails identity is refused - watched. A selector gate
  that never runs the thing being ported proves the wrong half. No GL or Vulkan ABI is exported.

## Done when

Named gates, in three tiers. Each is registered in the verification model and wired into
`verify.sh`'s freshness and selection so it runs when its subject changes.

**Host and build gates.**
- THE LOCKFILE IS COMPLETE AND IS THE BUILD'S ONLY SOURCE FOR THESE VALUES: both project revisions
  and archive digests, the patch series including the platform port, the full CMake option set, the
  generated-source policy and digests, the three toolchain files, the tool identities and the sysroot
  digest. A build that takes any of them from anywhere else, or a lockfile missing any field, fails -
  watched. Nothing else in this milestone starts before this gate passes.
- The pinned configuration compiles to objects for x86_64, aarch64 and riscv64 from the recorded
  digests, offline, and a repeat build produces an identical inventory digest.
- The regenerated inventory equals the recorded one, per target, symbol for symbol.
- The declared substrate surface EQUALS the CONVERGED AUDIT-LINK-RESOLVED SET, per target - no
  missing symbol and no symbol built that nothing requires. It is NOT the pass-1 undefined-symbol
  closure, which pass 2 says in as many words over-states the surface because a per-object undefined
  symbol may be satisfied by another upstream object; this gate said "the derived undefined-symbol
  closure" and contradicted the correction it was meant to complete (corrected 2026-08-30).
- The selected TLS variant's scan passes: Variant A's admitted forms, or Variant B's proof of
  absence over every admitted `ET_REL` member and the audit-linked ELF.
- The C++ ABI decision matrix is enforced: every mechanism marked forbidden fails the build when
  reintroduced, watched.
- An attempted build-time download is refused, watched.

**Package gates.**
- THE AUDIT-LINKED ELF ITSELF runs through the generic relocation, W^X, dynamic-metadata,
  identity/provider and export-collision checks, per target, WITHOUT being installed (added
  2026-08-30). It was previously exempt - only a synthetic artifact was checked - which would have
  let this milestone close with a substrate surface derived from an artifact the later importer
  immediately rejects. The checks are run on it as a file, before and independently of the
  quarantine staging the guest gate needs; no production manifest names it.
- A synthetic foreign artifact stages through the real manifest as its declared foreign kind, with a
  language-neutral identity record, and passes the same existing relocation, W^X, export-owner and
  provider-closure audits. The synthetic artifact proves the PACKAGING path; the audit-linked ELF
  proves the SURFACE this milestone claims. Neither substitutes for the other.
- Each of these is refused, watched to fail: a prohibited relocation, a W+X mapping, a wrong-target
  or wrong-architecture identity, a malformed or absent identity record, malformed discovery
  metadata, and an unreviewed licence.

**Guest gates.**
- The synthetic foreign consumer LAUNCHES on all three architectures through ProcessService, its
  provider closure verified, and performs a bounded lifecycle: allocate, map, use each admitted ABI
  facility, and exit cleanly.
- AND EVERY SUPPORTED C++ MECHANISM HAS A POSITIVE GATE OF ITS OWN, because "use each admitted
  facility" does not establish an ORDER or a FAILURE (added 2026-08-30). The forbidden mechanisms
  have watched-fail artifact mutations and the supported ones had nothing, so the milestone could
  close with its hardest lifecycle contracts documented and untested. Under the current pin the
  expected set is EMPTY - a C99 production closure with tests off names no C++ ABI facility - and an
  empty set means these gates are not written, not that they are waived. For each mechanism the
  pinned configuration actually admits:
  - static initialisation ORDER across the provider DAG, observed - a constructor in a provider runs
    before one in its consumer, and the guest records the sequence rather than asserting it ran;
  - a constructor that FAILS part way, and what the partial initialisation leaves behind;
  - `atexit` handlers on a normal exit, in reverse registration order;
  - the same process CRASHING, and which of those handlers did not run - the difference between the
    two paths being the whole of what a lifecycle contract says;
  - `errno` observed as PROCESS-WIDE, which is what the no-thread-creation pin makes correct; the
    per-thread model is what a thread-creating runtime would later have to change.
  A mechanism with no positive gate is not admitted.
- Discovery selects the synthetic provider through the chosen model's real path, and refuses a
  candidate that fails identity, watched.
- Under Variant B - which the no-thread-creation pin selects unless the inventory says otherwise -
  no per-thread TLS isolation test exists, and its absence is the point. Variant A's guest isolation
  test is written only if the pin is broken by a measured requirement.
- No thread-creation symbol appears in any target's inventory, watched: a fixture that injects one
  into the recorded inventory makes the gate refuse, because that is the measured stop condition the
  thread item defines.

The milestone is done when those gates pass for the ONE pinned configuration; the lockfile is
committed and is the build's only source for the pinned values; the loader platform port exists and
the audit-linked loader reaches a synthetic ICD's entry points in a guest; the audit link has
converged to a fixed point on all three targets and its ELF has passed the generic artifact checks;
the TLS variant is resolved and named; the licensing and provenance policy is recorded with the
per-file closure determined rather than asserted; and no accelerated API is implemented.

It is APPROVABLE as it stands, and its freeze order is the one M1 states: bootstrap pin -> pass 1 ->
substrate -> platform port -> converging pass 2 -> derived pin (2026-08-30). A previous round declared it not approvable until a
self-thread runtime was numbered; the configuration is pinned without thread creation, so that block
is removed and replaced by two measured STOP CONDITIONS - a thread-creation symbol or a TLS
requirement appearing in the derived inventory - each of which pauses the milestone at a known point
rather than preventing it from starting.
