# M0062 - USB stack (xHCI + HID + mass storage)

Status: COMPLETE. An xHCI host controller driver, enumeration over the bus, and the two classes an
appliance needs: HID keyboards and mass storage. A USB stick mounts through the same Volume API as
the virtio disks; a USB keyboard feeds the existing console input.

*Condensed 2026-08-08.*

## Shape

The kernel's PCI scan discovers any xHCI controller by its **class triple** (0x0C/0x03/0x30,
vendor-agnostic). `DeviceInfo.virtio_type` became `device_type`, with non-virtio codes above the
virtio id space (`DEVICE_TYPE_XHCI = 0x100`), and `pci.rs` gained standard write-all-ones BAR sizing.
Everything above that is a userspace driver.

**The keyboard logic is shared, not duplicated.** Modifier tracking, the US layout tables,
Ctrl+letter control codes, the navigation-key ANSI sequences, Shift+PageUp/PageDown scrollback and
the Ctrl+Alt+Delete chord moved out of `driver.virtio-input` into a `keys` module that both keyboard
drivers compile in - so a USB and a virtio keyboard cannot drift apart in behaviour.

**Mass storage** is SCSI Bulk-Only Transport: the driver finds a class 8 / subclass 6 / protocol 0x50
interface with its bulk IN/OUT pair, brings both endpoints up with one Configure Endpoint command,
spins the unit up and exposes a `BlockDevice`.

**Hubs and hot-plug** both work, which matters because on real machines devices usually sit behind a
hub: a device reporting class 9 is expanded - configuration selected, class descriptor read for the
port count, each port powered, checked, reset through the hub and its speed read - and Port Status
Change events at runtime reconcile the root ports so a newly attached device enumerates without a
reboot.

**Stall recovery is the full dance**, per endpoint: `reset_endpoint` clears the controller-side halt
and repositions the transfer ring past the abandoned TD, `recover_bulk` adds the device-side
CLEAR_FEATURE(ENDPOINT_HALT) to reset its data toggle, and `recover_ep0` handles the default endpoint.

## Testing it, and one defect worth remembering

QEMU attaches a `qemu-xhci` with a `usb-kbd` and a `usb-storage` stick (a 16 MB FAT image seeded from
`volume/` via mtools) on the test path as well, so the device set is deterministic and the kernel
suite drives the whole stack live.

`USB_HOST=vendorid:productid ./run` attaches a real host device for interactive testing; the emulated
stick is skipped for that run so the real device is the bus's one storage device. Interactive only -
the test path keeps the emulated set.

**The driver's online report was assembled into a fixed buffer with the size trusted at every
append.** It is a `Bounded<96>` writer now, whose `push` copies only what fits: the size is checked
once rather than at every call site, and an overlong report arrives cut short instead of taking the
driver down.
