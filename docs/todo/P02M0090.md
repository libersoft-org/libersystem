## P02M0090a - Phase 0: implementation truth and current wire safety

Status: DONE (2026-08-12). It said DONE on 2026-07-14 and was not: an audit of `src/wire` on
2026-08-10 found this phase's own completion criterion unmet - the bounded-handle invariant enforced
by `wire`, by the kernel and by the generated client, and NOT by the typed server receive, which
took one and destroyed the rest. P02M0090f is that repair and it is closed; the criterion holds
symmetrically now, in the receive path, in the thirteen converted call sites, in the validator that
stopped refusing `Many`, and in the gate that bans a new single-cap receive.

The last thing the phase owed was three of its own TESTS, which still asserted the retired refusal
and were red: they now assert what the migration established - `Many` is a shape, the bound is
`wire::MAX_HANDLES` enforced where the handles are, and an UNRESOLVED imported cardinality still
fails closed.

- [x] Make `docs/LSIDL.md` describe the implementation that actually exists, and require it to change in the SAME changeset as every parser/validator/wire/codegen change (generated `docs/gen/*.md` are outputs, not a substitute for the language specification). Correct the known mismatches: (1) no generated package-version handshake exists; (2) `@since` is accepted syntactically and silently discarded because the AST stores no annotation metadata; (3) `@rights` names are validated but codegen/runtime do not enforce the required rights; (4) the implemented `buffer` wire is one out-of-band transferred handle plus `len u64`, not the documented dma-id/offset/len descriptor; (5) `use` parses but packages/exports are not resolved; (6) generated `Transport::call` is synchronous with one in-flight call per Transport, despite the spec claiming correlation ids currently enable several concurrent calls. Add a spec-conformance checklist/test so aspirational behavior is explicitly labelled future work rather than stated as shipped.
- [x] Enforce the kernel channel's one-handle-per-message invariant in BOTH validation and the codec. Resolve named types and compute a `zero | one | many` out-of-band-handle cardinality for every request, reply and stream frame: record/tuple fields and method params use `sum`, result/option/variant alternatives use `max`, and `list<T>` is `many` whenever `T` can carry a handle because the schema permits more than one element. Reject non-indirected recursive value cycles that would generate an infinite Rust type, and make the cardinality fixed-point/cycle handling explicit so recursive list-shaped types cannot evade the check. Until Phase A supplies a resolved imported wire shape, today's `External` is unknown and must fail closed rather than being assumed handle-free; the package resolver then feeds the same analyzer concrete imported metadata. A `stream<T>` opening reply consumes its one handle with the implicit sub-channel; each `T` item is checked independently as its own frame. The current `idl/system.lsidl` already conforms (audited: every record/reply/param list carries at most one handle and no `list<T>` element can carry one), so enabling this validation is not a flag day; note that today's `type_codec_ok` would happily generate bindings for `list<handle<T>>`, which is exactly the hole being closed. Harden encoding AND decoding with an explicit occupied/consumed bit (not `handle != 0`): `Sink::set_handle` must return failure on a second call, `Reader::take_handle` must consume the slot and fail on a second read, and generated writers/readers must propagate those failures. No path may turn a failed encode into success: fix `encode_vec` (which currently discards `write` failure), generated clients, dispatch fallback/reset, and manual Sink users as needed. Define ownership on every failure path: a request handle remains with the caller until a successful send; the service host closes an unconsumed received handle after malformed/failed dispatch; a client closes an unexpected or undecodable reply handle; and an unsent reply handle is returned to the service host for close rather than erased by writer reset. Distinguish deliberate no-reply stream handling from codec failure in the dispatch result. Add zero/one/many, nested, recursion, unresolved-import, duplicate-write, duplicate-read, malformed-message cleanup, stream-open/frame and partial-encode golden tests; document the exact rule.
- [x] Reserve the runtime control opcodes in semantic validation now: a typed `@op` may not use `0xfffc..=0xffff`, which rt already owns as `GOODBYE_OP`, `RESOLVE_OP`, `HEARTBEAT_OP`, and `CONNECT_OP`. Move these constants plus `TYPED_OP_MAX = 0xfffb` into the dependency-free `abi` crate, which is already the shared host/no-std contract and is re-exported by rt; make `lsidl-gen` consume that same source rather than copying the numbers. Document typed interface opcodes as `1..=TYPED_OP_MAX` and add a test for each collision. Any future LSIDL protocol-info query must first extend this explicit control namespace and lower `TYPED_OP_MAX` rather than silently stealing an interface opcode.

## P02M0090b - Phase A: package resolver and monolith split

Status: DONE (2026-07-14).

- [x] Implement real cross-file LSIDL imports, then use them to split the 729-line `idl/system.lsidl` / generated 9300-line `proto/src/system.rs` monolith by contract domain. The syntax and AST scaffolding already exist (`use liber:system.{error, severity};`, `File.uses`), but today `lsidl-gen` processes each input independently and validation treats every imported name as an unverified `External`: it never loads the package, proves that the named export exists, distinguishes a resource from a value type, detects an import cycle, or emits a Rust reference to the imported definition. This task implements that missing package-graph layer; do not hand-edit or mechanically split generated `system.rs`.
- Import contract (decided before implementation): imports are explicit named imports only (no wildcard and no re-export), with an optional per-name alias for real cross-domain collisions (`use liber:storage@1.{error as storage-error};`). Extend the AST to retain the imported package version plus each source name, optional alias, and their individual spans; diagnostics must not collapse an entire `use` into one imprecise location. Imported names are otherwise referenced unqualified and collide with a local/imported/built-in name as an error. Pin the imported package version (`use liber:system@1.{error, severity};`) so a dependency cannot silently move to a wire-incompatible package revision. The compilation unit contains exactly one file and one exact version for each package path; loading a second version of the same path is a hard error until a concrete side-by-side migration requires multi-version linking. Duplicate identities, a missing package/version, a missing exported name, self-import, and package dependency cycles are hard errors with the importing file + precise name/alias span in the diagnostic. Resolved exports retain their concrete declaration kind (record, enum, variant, flags, resource, interface, or later alias) and semantic metadata; an interface is not a value type, and `handle<T>` still requires an imported `resource` rather than today's permissive `External` placeholder. Imports are direct only: package B importing A does not re-export A to package C.
- Front-end architecture: replace the per-path `process()` loop with one load/resolve/generate pipeline. (1) Read + lex + parse every CLI input into a source-aware package registry. (2) Build and DFS/topologically sort the import graph, reporting cycles as their package chain. (3) Resolve every `Use` against the exact-version target's export table and build each file's symbol table with concrete kinds and canonical identities. (4) Run semantic validation only after resolution. (5) Generate ALL Rust, Markdown, compatibility-test and manifest outputs in memory, derive every destination, and reject destination collisions before touching disk. A read/parse/resolve/validation/codegen failure writes NO outputs. A successful normal generation stages every file, uses atomic per-file replacement, updates the generated-output manifest, and removes stale files only after all replacements succeeded; document the unavoidable filesystem-failure semantics rather than claiming an impossible cross-directory atomic transaction. Sort packages/outputs canonically so CLI input order cannot affect bytes or write order.
- Code generation: each exact LSIDL package version emits its own Rust module/file and Markdown document; the canonical Rust path includes every package-path component and the pinned version (contract: `liber:storage@1` -> `proto::generated::liber::storage::v1`, with kebab-to-snake/Rust-keyword escaping and normalization-collision rejection). The resolved symbol carries that canonical path, exact declaration kind, wire shape and semantic metadata needed by codegen (not just a local name). Generated code emits qualified references to the one foreign Rust type rather than cloning its declaration; imported interfaces may not masquerade as value types. Preserve special behavior across imports too: an imported error enum containing `again` must still drive dispatch's oversized-reply fallback (today `again_enums` scans only local enums and would silently lose that behavior after a split). Generated compatibility/golden tests must compile and exercise records/interfaces containing imported value types, an imported `again` error, imported resources/handles and import aliases. Update `docs/LSIDL.md` grammar + examples and make generated docs link imported symbols to their exact owning package version.
- Source documentation before migration: introduce LSIDL doc comments (`///` declarations/members and optional `//!` package docs), retain their source spans in the AST, and emit them on generated Rust types/methods and in `docs/gen`. Ordinary `//` / `/* */` comments remain non-semantic and discarded. Land this before moving declarations so the useful prose currently surrounding items in `system.lsidl` moves with those declarations rather than being lost or reconstructed afterward.
- Migration after the resolver and source-doc preservation are green: split `system.lsidl` into cohesive packages (initial shape: shared types/error, storage/volume, process/device, network/socket/listener, console/input, observability/log/graph/supervisor, security/permission/resources/session). Keep a small hand-written Rust `proto::system` compatibility facade that explicitly re-exports every existing top-level type and interface module from `proto::generated`, preserving the current `proto::system::{Type, interface}` paths while consumers migrate package by package. The existing hand-written `addr`, `clock`, `path`, and `shell` extensions and their tests must continue compiling against those re-exported canonical types. This facade is an API compatibility layer, NOT an LSIDL import/re-export and does not violate direct-only import semantics; remove it only in a separate API-change task. `just gen` remains the single command, passes all `idl/*.lsidl` files as one compilation unit, owns only the generated namespace/docs plus its checked output manifest, never overwrites hand-written files, formats the proto crate, and is deterministic regardless of CLI input order.
- Tests: parser/AST tests for exact-version `use`, per-name aliases/spans and doc comments; resolver tests for valid imported record/enum/variant/flags/resource, imported-interface misuse, missing package, wrong version, rejection of two loaded versions for one package path, missing name, duplicate import/local/built-in collision, self-import, two- and multi-package cycles, wrong imported kind in `handle<T>`, direct-not-transitive visibility, canonical-module normalization collision, and input-order independence; no-write-on-front-end/codegen-failure and stale-manifest fixtures; codegen fixture where a generated client/server round-trips an imported record and transfers a `handle<imported-resource>`; Markdown escaping/multiline/docs-link fixtures; compatibility-facade/helper tests; end-to-end `just gen` followed by proto tests and builds of all current consumers. Preserve the existing wire golden bytes while declarations move between source packages.

## P02M0090d - Phase C: protocol features requiring separate design and migration

Status: DEFERRED by design; these protocol migrations do not hold Phase 0/A/B or source atomization open.

- [x] Runtime package identity/version negotiation is NOT a simple codegen toggle. First reserve a control-opcode band globally in the validator (today typed `@op` accepts all 1..=65535 while rt already intercepts `GOODBYE_OP=0xfffc`, `RESOLVE_OP=0xfffd`, `HEARTBEAT_OP=0xfffe`, `CONNECT_OP=0xffff`) and inventory every raw protocol sharing those values. Then design a stateless generated `PROTOCOL_INFO` query (likely the next reserved control opcode) that returns interface/package identity + exact version without changing existing method frames. Do not promise "once per connection" caching until there is persistent connection state: `Transport` is synchronous/stateless and 100+ call sites construct a fresh generated `Client<ChannelTransport>` inline, so a bool inside `Client` would only mean once per temporary client. Decide explicitly whether old servers without the query are refused or supported during migration. This is separate from the native ABI handshake and is not required to split source packages.
  Two of the four prerequisites above are already satisfied, checked 2026-08-01 rather than
  assumed. The control-opcode band IS reserved globally: `abi::TYPED_OP_MAX = 0xfffb` sits
  below `GOODBYE_OP`/`RESOLVE_OP`/`HEARTBEAT_OP`/`CONNECT_OP`, and `validate.rs:189` rejects any
  typed `@op` above it - so the text above claiming `@op` accepts all 1..=65535 is stale. The
  inventory is also clean: no hand-written protocol collides with the band. Every user of those
  four opcodes goes through the named `abi` constants, and the highest hand-written `OP_` value
  anywhere in the tree is 16. The only literal `0xfff*` matches are kernel virtual addresses and
  FAT16 cluster markers, neither of which is a protocol opcode.
  Built on 2026-08-01. `PROTOCOL_INFO_OP = 0xfffb` with `TYPED_OP_MAX` lowered to `0xfffa`;
  checked rather than assumed to be safe, because the highest `@op` across all 15 schemas is 16.
  The constant lives in `abi` and `wire` re-exports it, since generated code reaches `wire` as
  `crate::codec` but never `abi`, and a second copy of the value is exactly the drift a reserved
  band exists to prevent (`wire -> abi` is acyclic; `abi` has no dependencies).
  Answered by the GENERATED dispatch, not by rt: rt's serve loops serve every interface and
  cannot know which package a given service implements, while the generated code is the one
  layer that does. It is emitted ahead of the typed `match`, so no `@op` can shadow it, and the
  validator refuses a typed opcode that high - two guards that must agree, which is what
  `a_typed_opcode_cannot_reach_the_reserved_control_band` pins.
  Stateless as required: request is `[op][corr]`, reply is `[corr][package path][version]`, no
  service method runs, and no existing method frame changes. The client method deliberately
  does NOT cache - the warning above is right, and it is now recorded in the emitted comment so
  nobody "optimises" a per-connection flag into a per-temporary-client one.
  MIGRATION DECISION, and the reason it is smaller than it looks: this tree builds every
  service and every client into ONE image from one source tree, so a client that knows the
  query never meets a server predating it. There is no supported mixed-version configuration to
  tolerate or refuse today. What a caller must still handle is a peer that does not answer -
  `dispatch` returns None for an unknown opcode and the serve loop then sends no reply, so a
  query against such a peer BLOCKS rather than failing. That is acceptable while the image is
  built as a unit, and it is the thing to fix first if independently-versioned packages ever
  ship: `Transport::call` has no deadline, so the fix belongs there, not in the query.
  Verified on all three architectures: x86_64 150 passed, aarch64 142, riscv64 143, plus 43
  lsidl/proto tests and 37 lsidl-gen tests. Two of those generator tests were added here and a
  third had to be REWRITTEN rather than repaired - `stream_helpers_carry_one_handle_per_open_

- **DEFERRED BY DESIGN, and not a task** (restated 2026-08-12; a plain bullet rather than a checkbox
  because an unchecked box is a claim that somebody should be doing this, and nobody should):
  declarative `@rights` runtime
  enforcement. It cannot be built as a task because what it needs first is a DESIGN - the generated
  dispatch context, the transferred-handle ownership rule on denial, and an error return that can
  represent `denied` - and building it without them is how the sender's own rights metadata comes to
  be trusted. Until that design lands, `@rights` is validated contract metadata and the kernel's
  rights checks at the actual handle operations are what enforce anything. The original text: declarative `@rights` runtime enforcement also needs an execution boundary, not bytes sent by the untrusted caller. Today the parser validates right names and AST parameters store them, but proto codegen cannot call rt's `object_info` without creating a proto -> rt -> proto cycle. Before implementing, design a generated dispatch context/`HandleInspector` trait supplied by the service host (rt implements it through kernel `SYS_OBJECT_INFO_GET`), define transferred-handle ownership/close behavior on denial, and require an error return that can represent `denied` (or a transport-level protocol error). Never trust rights metadata encoded by the sender. Until that design lands, document `@rights` as validated contract metadata and rely on kernel rights checks at actual handle operations.
  Design sketch, 2026-08-01, with the blocking part now cheaper than when this was written.
  The stated obstacle - "proto codegen cannot call rt's `object_info` without creating a
  proto -> rt -> proto cycle" - is avoidable in the direction the item already suggests, and
  that direction now has a working precedent: `rt` gained a dependency on `wire` for `Handles`
  and it is green on all three architectures. So put the trait where generated code already
  reaches (`wire`, which it sees as `crate::codec`) and let the runtime implement it:
      pub trait HandleInspector { fn rights(&self, handle: u64) -> Option<u32>; }
  `rt` implements it over `object_info` (`rt/src/lib.rs`, which already returns `rights`), the
  service host passes it into the generated dispatch, and the dependency runs rt -> wire. No
  cycle, and `proto` stays free of `rt`.
  Non-negotiable property: the rights must be read from the KERNEL through the handle the
  caller actually transferred, never from bytes the caller encoded. Rights metadata on the wire
  is an attacker-supplied claim, so the check must ask `object_info` about the handle itself.
  The validator half already exists: `validate.rs` knows the twelve legal right names and
  mirrors the `RIGHT_*` bits.
  Two decisions still genuinely open, and both shape the trait, so they come BEFORE any code:
  (1) who owns a transferred handle when the check denies - the dispatch must neither leak it
  nor close what the serve loop will also close, and the loops now close every unclaimed
  capability in the request list, which is the interaction to design against; (2) how denial is
  reported - there is no return path that can say `denied` today, so either every `@rights`
  method's error enum must be able to carry it or the transport needs a protocol-level error.
  Answers to both, for whoever builds this. (1) On denial the dispatch should leave the
  capability UNCLAIMED in the request list and return the refusal; the serve loops close every
  unclaimed capability already, so that is neither a leak nor a double close and needs no new
  ownership rule. (2) Mirror the `again` precedent rather than inventing a mechanism: codegen
  already collects error enums carrying an `again` case (`again_enums`) to express the
  reply-overflow fallback, so collect the ones carrying `denied` the same way, and have
  validation require that a method annotated `@rights` returns a result whose error enum has
  that case - a precise diagnostic at schema-write time beats a runtime surprise.
  SCOPE FINDING, 2026-08-01, and it argues for waiting: NO schema uses `@rights` today. Zero
  occurrences across all 15 `.lsidl` files; the only appearances are one example in
  `docs/LSIDL.md` and a pair of lsidl-gen validation tests. Runtime enforcement means adding a
  `HandleInspector` to the generated `dispatch` signature, which is another sweep of the 22+
  call sites that the multi-capability work just rewrote - for no current consumer, and with no
  real schema to validate the design against. Adding the validation rule alone would be worse
  than waiting: it would demand a `denied` case that nothing can ever produce, while
  `docs/LSIDL.md` currently states the honest position ("runtime enforcement is not generated
  yet"). Recommended: build this WITH the first schema that needs it, using the design above.

## P02M0090f - The 1 -> 4 handle migration stopped halfway, and Phase 0's own criterion says so

Status: DONE (2026-08-12). All thirteen findings are closed. The three tests that still asserted the
one-handle refusal - `rejects_multiple_handles_in_records_and_requests`,
`rejects_lists_of_handle_bearing_values` and the imported-cardinality one - were the last of it, and
they are the finding in miniature: the migration moved the rule and left the assertions describing
the rule it replaced, red, in a suite nobody had run since. They now assert the current one, and the
unresolved-import case is asserted to still fail closed, which is the half that did not change.

### The half-migration

An outside audit of `src/wire` against the kernel, the runtime and the generator, 2026-08-10. Every
one of its thirteen findings held. The first is not a new discovery so much as this milestone's
completion criterion, unmet: *"the BOUNDED-handle invariant ... enforced symmetrically by schema
validation, writer/reader failure paths and failure-path capability cleanup"*.

`wire` says four. The kernel says four and has `SYS_CHANNEL_SEND_CAPS` / `SYS_CHANNEL_RECV_CAPS`.
The generated client says four. **The typed server receive says one, and the LSIDL validator still
refuses to let a schema ask for more than one** - which is the only reason the first is not already
losing capabilities in production.

- [x] **`serve()` and `serve_multi_ticked()` receive through the single-handle syscall.** Both call
  `recv_blocking`, which is `SYS_CHANNEL_RECV`, and then build
  `Handles::from_slice(&[handle])`. The kernel's own comment for that call says it "takes the first
  and drops the rest". So a client that legitimately sends stdin, stdout and stderr has two of them
  destroyed before the server's dispatch is reached - not refused, destroyed.

  The fix is one runtime primitive that every typed server uses - receive into a `Handles` through
  `SYS_CHANNEL_RECV_CAPS` - and no typed path left touching the single-cap receive. The legacy call
  can stay for bootstrap and stream messages, which expect at most one by construction.

  **This must land before the validator is allowed to accept `Many`.** Today's order is the safe one
  by accident: the schema cannot express what the server would drop.

  DONE 2026-08-12. `rt::recv_caps_blocking` is the primitive - `SYS_CHANNEL_RECV_CAPS` into a
  `Handles` - and `rt::try_recv_caps` is its polling sibling, for the loops that multiplex several
  channels themselves. `serve` and `serve_multi_ticked` go through the first; the single-handle
  receive stays for bootstrap and stream messages, which carry at most one by construction.

- [x] **Eleven of the thirteen single-cap receives are NOT in the runtime, and fixing `serve()` will
  not reach them.** The task above says "no typed path left touching the single-cap receive", which
  is the right goal and names only the two runtime helpers. `Handles::from_slice(&[handle])` occurs
  thirteen times in this tree: twice in `src/user/runtime/rt/src/lib.rs` - `serve` and
  `serve_multi_ticked` - and eleven times in dispatch loops that were written by hand and do their
  own receive:

      src/user/services/core/src/audio_engine.rs      (2)
      src/user/services/core/src/display_service.rs   (2)
      src/user/services/core/src/network_service.rs   (2)
      src/user/services/storage/src/service.rs        (2)
      src/user/services/core/src/console_service.rs   (1)
      src/user/services/core/src/input_service.rs     (1)
      src/user/drivers/core/src/xhci.rs               (1)

  it, and a client sending three capabilities to any of those services loses two of them whatever
  the runtime does. This is what makes the validator's refusal load-bearing across the whole
  userspace rather than across the two helpers.

  The enumeration is the cheap part and the gate is the point: once the sites are converted,

### The decoder is not as strict as the crate says it is

- [x] **`boolean()` accepts 2 through 255 as `true`.** `Some(self.u8()? != 0)`, against a stated
  contract that a malformed buffer answers `None`. One logical value with 255 encodings is
  malleability with no purpose, and it starts costing the moment a frame is hashed, compared or
  replayed. The generated `option<T>` tag has the same shape and the same answer: `0 => false`,
  `1 => true`, anything else `None`.

  DONE 2026-08-12. `0 => false`, `1 => true`, anything else `None`, and the test sweeps all 254
  refused values.

- [x] **Decoding accepts a valid prefix followed by anything.** The generated
  `decode(bytes) -> Option<T>` is `T::read(&mut Reader::new(bytes))` and never checks that the
  reader finished. `01 02 03` and `01 02 03 DE AD BE EF` decode to the same value. With extensible
  records explicitly deferred by this milestone, the current format should be strict: a `finish()`
  on `Reader` that requires the bytes AND the handles to be consumed, called at the framing
  boundary - not inside every nested `read`, which must not require the end of the buffer.

  DONE 2026-08-12. `Reader::finish()` requires every byte AND every capability consumed, and the
  generated `decode` calls it - at the framing boundary, not inside a nested `read`, which must not
  require the end of the buffer.

- [x] **`Transport::discard_handles` defaults to doing nothing.** The trait's own comment says its
  purpose is closing capabilities from a malformed or unexpected reply, and the runtime implements
  it correctly. A future transport whose author does not implement it compiles silently and leaks.
  Resource ownership should not be opt-in: remove the default body and let the test transports write
  the empty one explicitly.

  DONE 2026-08-12. The default body is gone; the two test loopbacks write the empty one and say why
  (they hand back handle numbers nothing opened). Resource ownership is not an opt-in.

### API shapes that make the mistake easy

- [x] **`encode_vec()` and `decode()` drop handles for any type that carries one.** The generator
  emits them for every serialisable type. `encode_vec` builds a `VecWriter`, calls `write` - which
  may call `set_handle` - and then returns `w.into_inner()`, which is `self.buf`. The handles are
  discarded. `decode` mirrors it with `Reader::new(bytes)` and no capabilities at all. So the pair
  the generator advertises as a round trip is not one for capability-bearing types.

  Either do not generate them for such types, or make the shape carry both -
  `EncodedMessage { bytes, handles }` - so that half a wire representation cannot be passed around
  by accident.

  DONE 2026-08-12, both halves. `encode_vec` REFUSES when the writer recorded a capability - the
  bytes alone are not the message - and `encode_message` is the shape that carries both, returning
  `(Vec<u8>, Handles)`. `decode_message` is its opposite, and `decode` requires the reader to have
  finished.

- [x] **`Handles` is `Copy` while representing owned kernel references.** Copying the numbers does
  not duplicate the capabilities, so two copies can each believe they own them, and with handle reuse
  that is the shape of an ABA bug. It is safe today because `Handles` has no `Drop` and ownership is
  explicit everywhere. Either name it as non-owning transport metadata and keep `Copy`, or make it a
  move-only envelope on the ownership paths - the second is what a capability system should prefer.

  DONE 2026-08-12 by taking the first option and WRITING IT DOWN, which is what the finding asked
  for. `Handles` is named as non-owning transport metadata at its definition, with the reason the
  move-only envelope was not chosen: this type is read by the syscall wrappers, by the generated
  dispatch and by the serve loops, and a `Drop` that closes would fire on every one of those
  by-value borrows. What owns a capability here is the code path, stated at each hand-off.

- [x] **`VecWriter`'s allocation failure does not come back through `Option`.** `Sink::put` returns
  `Option<()>` and for `SliceWriter` that means "buffer full"; `VecWriter` pushes onto a `Vec` and an
  allocation failure aborts instead. Elsewhere this runtime works hard to make attacker-sized
  allocations fallible - `Reader::string_lp` does exactly that. Either say plainly that `None` means
  capacity and allocation failure stays fatal, or give `VecWriter` fallible growth.

  DONE 2026-08-12 with fallible growth rather than a note. `put` and `raw` both `try_reserve`, so
  `None` means the same thing for both sinks: the sink could not take the byte.

- [x] **`Sink::raw` writes one byte at a time.** A default `for &b in s { self.put(b)? }` over a
  multi-kilobyte string is the codec's hot path. A bulk copy for `SliceWriter` and an append for
  `VecWriter` are the natural shapes - measured first, because this crate is checked against an exact
  list of runtime imports and `from_slice` right above it carries a comment about avoiding a `memcpy`
  that an aarch64 build once caught.

  DONE 2026-08-12. Both concrete sinks override it - `copy_from_slice` after one bounds check for
  `SliceWriter`, `try_reserve` plus `extend_from_slice` for `VecWriter` - and the byte-at-a-time
  default stays, because a new sink should work before it is fast and the overrides are where a
  `memcpy` may legitimately appear.

### Two comments that teach the wrong model

- [x] **`Sink::set_handle` still says "at most one per message, matching the kernel channel's
  single-handle limit".** It is the opposite of true: the kernel allows four, the syscalls exist, and
  `set_handle` itself accepts four. This is a trait comment, so it is the first thing a new reader
  builds their model from.

  DONE 2026-08-12. It says what is true: one handle per call, refused past `MAX_HANDLES`, and the
  kernel allows four.

- [x] **"Everything is heap-free except `string_lp`"** is in the module header, above `VecWriter`, a
  JSON renderer returning `String` and a CBOR renderer building `Vec<u8>`. The real and genuinely

## P02M0090h - The guarantee the documentation states is true of the bytes and not of the capability

A fourth audit, against this tree at `4350074` - 2026-08-14. Five findings and all five hold. The
audit's arithmetic on the previous round is fairer than this file's own header: of the eight it
reopened for, five are fully closed and three are substantially repaired with a residual edge left
in each. The header says "eight closed"; the accurate sentence is five closed and three narrowed,
and what is left is written out below.

The through-line is one this milestone has met before at a different field. `Handles` is not an
owner - the comment at `codegen.rs:728` says so plainly, "`Handles` is not an owner, so dropping it
closes nothing" - and every remaining finding is a place where a capability's ownership is decided by
a convention nobody can typecheck rather than by the type.

### `list<handle<T>>` can leak the fifth capability, and the specification says it cannot

`docs/LSIDL.md:314` states the guarantee:

> **Past the limit, nothing is dropped.** A schema whose shape carries five is refused at generation.
> A `list<handle<T>>` is accepted, because its count is a property of the value rather than of the
> schema - and there the writer answers: `set_handle` returns `Option`, every generated `write`
> propagates it with `?`, so the WHOLE message fails to encode rather than losing its fifth
> capability.

The message does fail. The capability is still lost, and for the reason the sentence steps over: the
fifth handle is never GIVEN to the writer. `set_handle` refuses at the boundary
(`src/wire/src/lib.rs:164-165` and `:222-223`), so `writer.handles()` holds four, and the generated
failure cleanup can only hand back what the writer holds -
`Handles::try_from_slice(writer.handles())` at `codegen.rs:517`, `:534`, `:542`. The fifth is in the
service's own value, which for a `list<handle<T>>` is a `Vec<u64>`: plain integers with no `Drop`.
Nothing closes it and nothing can reach it.

"Nothing is dropped" is true of the DATA - no byte is silently discarded - and the sentence is
written in a file about capabilities, where dropping means something else. In a capability system an
unreachable live handle is authority with no holder, which is worse than a leaked allocation.

`Cardinality::Unbounded` is what admits the shape (`validate.rs:396-398`), and
`report_cardinality` accepts it explicitly beside `Exact` (`:459`). The comment above the list arm
already states the problem it is solving - "a schema could ask for as many capabilities as the value
happened to hold and the writer would refuse past four - at run time, on the fifth element, with the
first four already written" - and then permits it.

- [x] **Refuse `Unbounded` when the element carries capabilities,** which is the only case it arises
  in: `Type::List` maps `Exact(0)` to `Exact(0)` already, so a list of capability-free values is
  unaffected. This is the same refusal `Many` used to carry, restored for the one shape whose count
  the schema genuinely cannot bound - and unlike that refusal it is not blocking a migration, because
  no schema in the tree uses it. `check_stream_frames` inherits it for `stream<list<handle<T>>>`.

- [x] **Or make the encoder transactional,** which is the real fix and much larger: an encode that
  fails must return every capability the VALUE holds, not every capability the WRITER accepted. That
  needs the generated `write` to give handles back on the failure path, which is a change to the
  writer trait and to every generated encoder. Worth naming as the alternative so the refusal above
  is understood as the cheap half of a decision rather than the whole answer.

- [x] **Correct `docs/LSIDL.md:314`.** Whichever route is taken, the paragraph currently promises
  something the code does not do. If the refusal lands, the sentence becomes simple: a shape whose
  capability count is not bounded by the schema is refused at generation, list or no list.

### The stream consumer's handle ownership is a convention, and the tree already holds both readings

`xxx_read(msg: &[u8], frame_handles: &Handles) -> Option<T>` takes the handle list by SHARED
reference, copies it into the `Reader`, and hands the caller a decoded value that now owns whatever
`take_handle` adopted - while `frame_handles` is unchanged and still lists all of them. Whether the
caller may close them depends on whether the decode succeeded and on whether the element type carries
capabilities at all, and nothing in the signature says so.

Two consumers in this tree read that convention opposite ways:

- `src/user/apps/tools/src/tail.rs:176-179` closes every frame handle and THEN decodes.
- `src/user/apps/tools/src/ls.rs:288-293` decodes and THEN closes every frame handle.

Both are correct today, and for the same reason: `FileEvent` and the directory entry carry no
capabilities, so the loop at `tail.rs:176` closes an empty list and the loop at `ls.rs:292` closes an
empty list. The day either element grows a `handle<T>` - which the generator now permits, and the
frame transport now carries correctly - `tail` hands the decoder handle numbers it has already
closed and `ls` closes the handles the decoded value adopted. Two different failures from one
unstated rule.

- [x] **Take the frame handles by `&mut Handles` and remove what the decode adopts.** After a
  successful read the list holds exactly what the schema did not account for, which the caller can
  then close unconditionally - and after a failed one it holds everything, which the caller closes
  the same way. One rule, no branch on success, and the borrow checker enforces that the caller is
  not reading a list the decoder is consuming.

- [x] **Then fix both consumers,** since with a `&mut` signature `tail.rs` will not compile as
  written - which is the point. `ls.rs` moves its close after the decode and needs nothing else.

### `protocol_info` and the stream-open reply are the message boundaries `finish()` missed

The ordinary reply path calls `r.finish()?` (`codegen.rs:790`) and its comment says why: "a reply
could carry anything after its value and decode as though it had not". Three generated paths beside
it do not:

- `protocol_info`'s client reads the correlation id, the package string and the version, and returns
  (`codegen.rs:694-701`) - no `finish()`.
- The `stream<T>` reply with no error type checks the correlation id and the handle count and returns
  `reply_handles.first()` (`:733-737`) - no `finish()`.
- The `result<stream<T>, E>` reply checks the tag, reads a `u32` placeholder and returns (`:748-751`)
  - no `finish()` on the `Ok` arm.

Each of those is a real message boundary, and the argument the ordinary path's comment makes is about
message boundaries rather than about that one path.

- [x] **Call `finish()` on every generated message boundary,** including the server's
  `PROTOCOL_INFO_OP` arm (`:469`), which answers after reading the opcode and the correlation id
  without looking at the rest of the request.

- [x] **A generator test that asserts it structurally,** the way the tree already tests that
  `r.u8()? != 0` cannot come back: every generated `pub fn` that decodes a reply contains a
  `finish()`. A rule stated once in a comment on one path is what produced these three.

### An imported multi-handle type is counted as four

`validate.rs` is quantitative now, and `resolve.rs` is not: `HandleCardinality` is still
`Zero | One | Many` (`src/tools/lsidl-gen/src/resolve.rs:15`), and the import mapping reads
`HandleCardinality::Many => Cardinality::Exact(MAX_HANDLES)` (`validate.rs:414`). So an imported
record carrying two capabilities is counted as four, and a local record combining it with another
two-capability field is refused at six when the truth is four.

This fails SAFE - it rejects a valid schema rather than admitting an over-limit one - and it is
invisible until somebody writes that schema. It is also the last place in this chain where the count
is a word rather than a number, which is what the whole `Exact`/`OverLimit` change was for.

- [x] **Carry the exact count through `ResolvedSymbol`.** `HandleCardinality::Many` becomes a number,
  `resolve.rs:259`'s `One | Many => Many` fold becomes the same `sum` the validator does, and the
  import arm stops rounding up.

- [x] **A test with an imported two-capability record used twice,** which must generate and does not.

### Two sentences in `docs/LSIDL.md` describe a world with no capabilities in it

Beside the `list<handle<T>>` paragraph above, `docs/LSIDL.md:344` says a `stream<T>` consumer "drains
them with ordinary channel receives". For a handle-bearing `T` it must use the capability-aware
receive - `recv_vec_caps_blocking` and its siblings - which is exactly what the frame transport was
rebuilt for last round, and both consumers in the tree already do.

- [x] **Say which receive a stream consumer uses, and when.** The sentence predates multi-capability
  frames and reads as guidance rather than as history.

## Fifth audit (2026-08-15)

An outside review of the generator, the validator and the generated code after the fourth audit's
fixes. It confirms four of the five as properly closed and raises four points. Every one was checked
against the generated code rather than against this document, every one holds, and all four are
fixed here.

The through-line is worth stating because it is the same one twice: BOTH REMAINING DEFECTS WERE
SHAPES THE SCHEMA PERMITTED AND THE PROTOCOL COULD NOT CARRY, and both were invisible to a test that
was checking the right idea with the wrong invariant.

- [x] **The Err arm of a guarded stream open never ended at a boundary.**

  DONE 2026-08-15. `result<stream<T>, E>` has one reader and two paths. The Ok arm read the
  correlation and called `finish`; the Err arm read the error and returned it. So a stream-open
  refusal with bytes after it - `[corr][0][Error::Denied][DE AD BE EF]` - decoded as an ordinary
  refusal, on the one reply shape in the generator that did not check.

  The generated Err arm now binds the error, calls `finish`, and returns. The order matters and is
  written down where it is easy to get wrong: the check is about what is LEFT after the value, and a
  `?` inside `Some(...)` would have run them the other way round.

- [x] **And the test that was supposed to prevent exactly this could not see it.**

  DONE 2026-08-15, and this is the more interesting half. The guard was
  `finishes >= readers` - a count of `Reader::new(` against a count of `.finish()` across the whole
  generated file. A reader with two paths, one of which checks, is one reader and one finish. The
  count passed for as long as the defect existed.

  That is a statement about TEXT where the rule is a statement about PATHS. The counting stays,
  because it catches a whole reader with no finish anywhere; beside it every arm that returns a
  decoded value is now named explicitly, so a new arm has to be added to the test. Watched failing:
  with the codegen fix reverted the new assertion turns the suite red, and it passes with it in
  place.

- [x] **`result<stream<T>, E>` accepted a capability-bearing error arm the transport cannot carry.**

  DONE 2026-08-15, and this was the most serious of the four. A `result` takes its cardinality as
  `max(ok, err)`, so a one-capability `E` against the Ok arm's one subchannel was legal. The
  generated transport cannot express it in either direction: `_reply_err` takes no handle
  out-parameter and refuses outright when the encoder recorded one, and the client's Err arm refuses
  a reply that arrives with any handle at all.

  Worse than a plain mismatch, and this is why it is a leak rather than a refusal: by the time
  `_reply_err` refuses, the SERVER HAS ALREADY MINTED the capability, and there is no out-parameter
  to hand it back through. It is stranded exactly the way an over-long capability list strands its
  fifth handle - which is the failure this milestone is named for, arriving by a second road.

  REFUSED STATICALLY RATHER THAN SUPPORTED. Supporting it means an out-parameter on `_reply_err` and
  a handle-aware decode on the client's Err arm: a wire and API change for a shape nothing in this
  tree asks for. The refusal is where that decision is recorded and the place to change it when
  something does ask. The check is on the CARDINALITY and not on the syntax, so a record error
  carrying a capability is refused identically to a bare `handle<file>`; a capability in the Ok
  arm's FRAME stays legal, because the frame carries it on its own message.

- [x] **A stale comment argued for the behaviour the code no longer has.**

  DONE 2026-08-15. Above `report_cardinality`, a long comment still said "`Unbounded` is a
  `list<handle<T>>`, and it is ACCEPTED", and went on to argue the case - that the count is a
  property of the value so the wire must bound it. The code had already stopped agreeing.

  The argument is true about the WRITER and false about the capabilities the writer never took:
  `set_handle` refuses at the boundary, the whole encode fails, and cleanup walks
  `writer.handles()` - which never held the fifth. The comment now says that.

  A stale comment arguing for the opposite behaviour is worse than no comment. The next reader has
  to work out which of the two is current, and the comment is the more persuasive of the pair.

- [x] **Found while fixing the above, in a different layer: `bin/` stopped being only programs.**

  DONE 2026-08-15. `kernel.boot.system_packages_use_canonical_executable_names` asserted that
  anything under `bin/`, `libexec/` or `drivers/` is named like an executable, which was true while
  `bin/` held only programs. P02M0100's app asset bundles put data there - `bin/<program>/...`, the
  scope an `app-assets` grant is narrowed to - and the gate caught it.

  The rule is now about DEPTH and is checked rather than assumed: a path directly under `bin/` is a
  program and must be named like one, and a deeper path is an asset whose owning program MUST be
  staged. An asset bundle for a program that is not there is a staging mistake wearing the name of
  something that does not exist.

## Sixth audit (2026-08-15): both correctness findings confirmed fixed; three follow-ups

The sixth audit re-read `src/wire`, `lsidl-gen`, the regenerated protocols and this milestone against
this tree, and its main result is a confirmation rather than a finding: the two correctness defects
left by the round before are fixed IN THE IMPLEMENTATION, not only in this document. The `Err` arm of
a guarded stream open decodes the error, calls `r.finish()?` and only then returns `Some(Err(..))` -
in the generator and in the regenerated Storage client - so a refusal with bytes after it is no
longer read as an ordinary refusal. And a capability-bearing `E` in `result<stream<T>, E>` is now a
generation error, decided on the computed cardinality rather than the syntactic shape, so a record or
variant that merely contains a handle is caught too.

It explicitly does not ask for this milestone to be reopened as critical, and neither do these three.
They are follow-ups: one latent API hazard and two places where the guarantee is narrower than it
reads.

- [x] **`decode_message` takes `&Handles` and clears nothing, so its ownership rule exists only in
  whoever remembers it.** `codegen.rs:197` generates
  `pub fn decode_message(bytes: &[u8], handles: &Handles) -> Option<T>`, which decodes and returns
  without touching the caller's list. `Handles` is deliberately non-owning and `Copy`, so after a
  successful decode the returned `T` and the caller's list name the SAME kernel handles, and the
  caller has to know that success means "do not close these" while failure means "close them" -
  which nothing in the signature says.

  This is the exact class the stream and request paths already fixed: they take `&mut Handles` and
  call `handles.clear()` once the frame is known good (`codegen.rs:476`, `:503`, `:587`, `:677`), so
  a successful read leaves the caller holding nothing and a failed one leaves it holding everything.
  Give the generic helper the same shape. No production caller uses it today, which is why this is a
  hazard in a public helper rather than a leak - and why it is cheap to change now.

- [x] **Replace the source-shape assertions with behavioural malformed-reply tests.** The counting
  rule `finishes >= readers` is a statement about TEXT, and the file's own comment
  (`lsidl-gen/src/tests.rs:698`) already says so after it let the `Err` arm through: two readers and
  two finishes passes even when one reader has both finishes and the other has none. The named
  arm-by-arm assertions added beside it close today's gap and are matched against generated Rust
  formatting, so they break on reindentation and say nothing about a NEW arm.

  What proves the property is driving the decoder: a valid `Err` reply accepted, the same reply plus
  one trailing byte refused, `Ok(stream)` accepted and the same plus a trailing byte refused,
  `protocol_info` plus a trailing byte refused, and a malformed reply's capabilities all closed. Keep
  the counting rule - it still catches a reader with no boundary check anywhere - and stop asking
  string matching to prove a protocol property.

- [x] **Write the capability-free error-arm rule into `docs/LSIDL.md`.** The validator enforces that
  `E` in `result<stream<T>, E>` must carry exactly zero capabilities, and the specification does not
  mention it - a schema author meets the rule as a compiler diagnostic instead of reading it. The
  document already covers the four-capability message limit, the `list<handle<T>>` refusal and
  capability-aware stream receive, so this belongs beside them, with the reason: the generated
  server's `_reply_err` has no handle out-parameter, so a capability the server minted for the error
  arm could not be returned to the host to be closed.

### Resolution of the sixth audit's three follow-ups (2026-08-16)

**`decode_message` now takes `&mut Handles` and clears on success.** The generator emits the same
shape the framing boundaries already had - the dispatch, the stream frame and the reply readers all
take `&mut Handles` and `clear()` once the frame is known good - so a successful decode leaves the
caller holding nothing and a refusal leaves it holding everything. Every protocol crate was
regenerated; no production caller existed, which is why this closed as a signature change rather
than as a leak.

**The source-shape assertions are gone and the property is driven instead.** `lsidl-gen`'s
`every_generated_message_boundary_ends_with_finish` keeps the counting rule and nothing else: the
count is the half that sees every reader the generator can emit, including ones no schema in this
tree instantiates, and catches a whole boundary added with no `finish` anywhere. The five
`rust.contains("...")` assertions naming individual arms were deleted - they matched generated Rust
FORMATTING to prove a protocol property, so they broke on reindentation and said nothing about a new
arm.

What replaced them lives in `src/proto/src/tests.rs`, where generated code compiles:
`every_arm_of_a_guarded_stream_open_ends_at_its_framing_boundary` and
`the_identity_query_ends_at_its_boundary_too` drive `volume::list` and `protocol_info` through a
`ScriptedReply` transport that answers with bytes and capabilities the test wrote - so the client's
framing is under test rather than a matching server's. Eight cases: a valid Err, the same plus one
trailing byte, a valid Ok stream open, the same plus one trailing byte, an Err arm carrying a
capability, an Ok arm carrying none, an unknown tag, and the identity reply in all three shapes.
Each refusal is also checked to have RELEASED what it was carrying, which is the half a decode-only
assertion cannot see.

BOTH WERE WATCHED TO FAIL. Deleting `r.finish()?` from the regenerated Err arm produced
`left: Some(Err(NotFound)), right: None` on the trailing-byte case - the exact defect the deleted
string match was written for, caught by behaviour. Deleting it from `protocol_info` produced
`left: Some(("liber:storage", 1)), right: None`. The generated file was restored from a copy taken
before the experiment and the suite re-run: proto 49/49, lsidl-gen 46/46, and the `host-tests` gate
green.

**`docs/LSIDL.md` states the capability-free error-arm rule**, beside the four-capability limit and
the `list<handle<T>>` refusal, with the reason rather than only the rule: a stream open's Ok arm has
already spent the reply's out-of-band list on the sub-channel, `_reply_err` has no `reply_handles`
out-parameter, and the cardinality rule cannot catch it because `max(ok, err)` of one and one is
one. It records what the shape costs - by the time `_reply_err` refuses, the server has MINTED the
capability and has nowhere to hand it back - that the refusal is deliberate rather than a gap, and
that an `E` whose count cannot be resolved is refused separately, because an unbounded answer is not
a zero.
