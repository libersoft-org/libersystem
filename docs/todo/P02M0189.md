# P02M0189 - Where the system's time goes, measured layer by layer

Status: OPEN. It closes when every implementation and verification item below is done.

THE FACT THIS MILESTONE OPENS ON IS ALREADY IN THE TREE, AND NOBODY HAS EXPLAINED IT. The live 2D
demo at 640x480 reports two numbers of its own: a frame's DRAW costs 79.6 ms mean and the loop's
PRESENT INTERVAL comes to 132.4 ms (`docs/PERF.md`, 2026-09-15). The difference is 52.8 ms - forty
percent of every frame - and no measurement in this tree says how it divides. `docs/PERF.md` reads
that pair as "the draw is most of the interval, so what the loop waits for is the renderer rather
than the display", which is true of the larger term and says nothing about the other forty percent.

WHAT THE CODE ALREADY SAYS ABOUT THE 52.8 MS, AND WHAT IT CANNOT. The demo's draw clock times only
`prepare` and `render`: the image is ACQUIRED and the scene RECORDED before the clock starts, so both
sit inside the 52.8 ms although the table calls the figure "record + replay". The present is
SYNCHRONOUS: DisplayService copies the surface into the scanout and calls the driver, the driver
answers only after the device acknowledged both the transfer and the flush, and only then does the
present return. And after it returns the frame loop WAITS ON PURPOSE: DisplayService reports no frame
timing, so `Pacing::on_present` falls back to `UNPACED_INTERVAL_NS` (16 ms), and `park` rounds that
deadline up to the 10 ms kernel tick - every interval contains an idle of 16 to 26 ms that is a
library's policy and a timer's granularity, not transport, service or driver work. DisplayService
times its blit and its device call per present, but only an admin connection can read those
counters and nothing on the live path does; the tree's cross-process tracer (`perf-trace.py`) is
wired to the console path and no marker sits on the frame path. So the code names the terms and
cannot say how long each takes on this machine, how much of each is computing and how much waiting,
or what is left once they are added up. That is this milestone.

THE BASELINE IS OLDER THAN THE RENDERER IT MEASURED, AND IT IS NOT ONE KIND OF FRAME. It predates the
2026-09-19 `Tile::store`, `Tile::load`, per-row shader and decoded-source changes, all of which the
demo's scene pays. It was taken at `--size=640x480` on the default 1280x800 virtio-gpu scanout, so
every present took the SCALED path onto a 1066x800 output. And under `--frames=600 --phase-frames=60`
the demo's phase counter stops at `full-again`, the fourth phase, and each phase change owes two whole
frames, so 484 of its 600 frames presented the whole surface, 58 the partial phase's rectangles and 58
the two rectangles: its mean is mostly whole-surface frames and still mixes three damage shapes whose
present paths differ. The account is taken on the current tree, per damage shape, with the scanout,
the path and the pixel counts stated.

AND THE RENDERER HAS BEEN MEASURED TO DEATH WHILE THAT NUMBER SAT THERE. soft2d has a probe suite
down to the nanosecond per pixel, soft3d has one per stage, and both have found and closed real
defects - `Tile::store`'s per-pixel encode was ninety-one percent of a full-screen fill. What has
never been measured is everything the renderer hands its result TO. So the graphics work has a floor
it can quote and the system around it has none, and a frame that misses its ceiling cannot be
attributed to either.

THIS MILESTONE PRODUCES AN ACCOUNT AND NOT AN OPTIMIZATION. Its product is a breakdown in which every
millisecond of a frame belongs to a named layer, a repeatable instrument that produces it again, and
- where the answer is that this system has no primitive for something and does it the long way
instead - a named follow-up item that says what is missing. Making any layer faster is explicitly
NOT in this milestone, with one exception stated in its own item below. A measurement milestone that
starts fixing things stops measuring, and the thing it was going to fix is usually not the one that
mattered.

## P02M0189 - What it measures, and the order

- [ ] x86_64 FIRST AND ALONE until the account is complete. The two emulated ports charge per
  instruction, so they magnify the terms that execute the most instructions and shrink the ones that
  wait - which is the opposite of the distortion this milestone is looking for. They are measured at
  the end, as a CHECK on the account rather than as a source of it, and a term whose share moves
  between the three is a term the account has to explain.
- [ ] THE BASELINE IS RE-MEASURED FIRST, on the current tree and before any instrument code lands: the
  2026-09-15 command, unchanged but for the worker pin below, at the lab guest's default core count -
  the condition the old row was taken under - and the gate's dormant run (its `development` boot below)
  in the gate's conditions, taken three times so its run-to-run spread is known. Both are written into
  `docs/PERF.md` as a dated re-measure with the conditions below, and every later number is compared
  with them, not with the 2026-09-15 row.
- [ ] EVERY COMPARISON STAYS ON ONE TREE. A change to code the path runs, for any reason but the
  instrument - soft2d or render2d, the demo and its frame loop, DisplayService and `pix`, the runtime
  and IPC libraries, the driver, the kernel's syscall, IPC, scheduling, timer and memory paths,
  P02M0193 included - moves the numbers it touches, and a comparison across it measures the change. If
  one lands before the instrument's dormant run is taken, the re-measure is taken again on the tree the
  instrument lands on, without the instrument, and replaces the first, so the dormant comparison sees
  the instrument and nothing else. If one lands after that and before the account is written into
  `docs/PERF.md`, the dormant comparison stands and every row already taken - the account's, the
  optimised run's, the emulated ports' - is taken again on the new tree, with that tree's dormant run
  as the reference its numbers are compared with.
- [ ] The measured path is one frame, end to end, in a booted guest: the application acquiring an
  image, recording its scene and drawing it, the surface it presents, the transport that carries the
  present, DisplayService, the display driver, and the device's acknowledgement of the transfer and
  the flush - then back to the application, including the wait its frame loop chooses before it
  draws again. Every boundary crossed is a named term in the breakdown. THE PATH IS THE ONE THE DEMOS
  ALREADY USE and no second path is built to measure it: the demo gains measurement modes, and every
  mode that presents goes through the same frame loop, service, driver and device.
- [ ] THE DRAW IS THE SERIAL WALK, WHICHEVER OF THIS MILESTONE AND P02M0193 LANDS FIRST. The account
  describes one chain of work per frame, so its draw is soft2d's serial walk on the demo's own thread,
  and the order of the two decides only who pins it. EVERY RUN THIS MILESTONE MAKES WHILE THE DEMO HAS
  `--workers` - the first-step re-measure included, if it is taken then - pins `--workers=1`, and one
  more run at the demo's default worker count is recorded as the POOLED ROW beside the account - its
  draw, its interval and the lanes it used - and is not a term of it; a run made before the demo has the
  flag needs neither, so a milestone that closes before P02M0193 lands closes on the serial walk alone.
  WHO EDITS THE GATE FOLLOWS FROM WHETHER THE GATE EXISTS, not from which milestone has landed or
  closed, and P02M0193 states the same rule: the change that makes the pool `test2d-sw`'s default pins
  every `qemu-2d-account` run that exists at that point to `--workers=1` and adds the pooled row, in
  that same change; a gate first written after that change pins from its first version. If P02M0193
  lands while this milestone is open, it is a change to code the path runs, handled as the one-tree item
  above says.
- [ ] THE CONDITIONS ARE PART OF EVERY NUMBER, and a number without them is not in the account: the
  build profile of each layer (next section); the scanout size the driver reported, the surface size,
  and whether DisplayService took the direct or the scaled path, with the source and output pixels;
  QEMU's display device (`virtio-vga`), its display back end (headless, no client connected), the
  vCPU count, KVM with `-cpu host`, the DMA mode the harness wrote for the boot, the host CPU model;
  the calibrated TSC rate; and the digest of the image booted.
- [ ] The primitives under that path are measured separately and in their own item. They are what the
  per-layer terms are BUILT of, and a layer costing four times its own primitives is a different
  finding from one costing exactly them.
- [ ] THE ACCOUNT MUST ADD UP, and this is the completion criterion that cannot be weakened. For each
  damage shape - the whole surface, the partial phase's rectangles, the two rectangles - the sum of
  the named terms is within five percent of that shape's measured present interval. Unattributed
  time is the defect this milestone exists to remove, so "the rest" is not a term; an interval that
  will not close is reported as an open question with the residue's size, not as a finished account.

## P02M0189 - The build profile of every layer

- [ ] THE LAYERS ARE NOT BUILT ALIKE, and the account says so beside every term. On the measured path
  two layers are `dev` builds at opt-level 0: the kernel, which `build.sh` builds with plain
  `cargo build` and `image.sh` puts on the image from cargo's `debug` output, and the virtio-gpu
  driver, a `linkage = "static"` program that `build.sh` builds the same way and `mkpackages` stages
  from that output. DisplayService is not one of them: it is declared `linkage = "dynamic"`, so
  `mkpackages` stages it from the `.build/image` tree that `build-shared` fills, compiling with
  `--release`, and `pix` and its other providers come from there too - a release PIE, like the demo and
  its libraries. Unoptimised code therefore inflates the kernel's share of every term - each syscall,
  IPC transfer, context switch and wake, whichever process it serves - and the driver's terms, which are
  exactly the terms this milestone could otherwise call architecture.
- [ ] EACH PROCESS'S PROFILE IS READ FROM WHAT THE IMAGE STAGED, NOT FROM `build.sh`, whose
  `cargo build` of the services also leaves a `debug` DisplayService that no image stages. The gate
  records, for the kernel, the driver, DisplayService and the demo, the artifact the image staged - the
  tree it came from, which follows from the program's `linkage` exactly as `mkpackages` chooses it -
  and its digest, beside the image's digest.
- [ ] ONE OPTIMISED COMPARISON RUN, and this is the route. Once the x86_64 account closes, the gate is
  run once more on the same tree with `CARGO_PROFILE_DEV_OPT_LEVEL=2` exported - cargo's own override
  of the `dev` profile, with no source edit. It reaches the kernel and every static program - on the
  measured path, the virtio-gpu driver - and nothing `build-shared` compiles with `--release`, so
  DisplayService and the demo are the same bytes in both runs, and what moves in their terms is the
  kernel and driver code they run or wait on. THE VARIABLE STAYS EXPORTED FOR THE WHOLE GATE RUN: each
  boot builds its image through `image.sh`, which re-runs `build.sh`, whose `cargo build` of the kernel
  and the static programs runs on every invocation under whatever profile the environment names -
  cargo's own fingerprint sees the change and rebuilds both ways - so a boot that lost the variable
  would quietly build the ordinary image again. `--rebuild` is no part of it: it clears only
  `build-shared`'s source-keyed cache of the release PIEs, which the variable does not reach, and the
  ordinary build comes back with the next build run without the variable. The primitives are measured
  in both builds. The whole `services` package optimised once lost its stand-in GPU in the TEST boot
  (`docs/PERF.md`); this run is the live boot, and if it does not reach the demo that is recorded as a
  finding and left alone.
- [ ] THE OPTIMISED ROW COMES FROM ANOTHER IMAGE. The image build is reproducible, so a run whose image
  digest is the ordinary run's booted the ordinary image. The gate, run with the variable set, compares
  its record with the ordinary run's and takes the row only if the image digest and the staged kernel
  and driver differ from the ordinary run's and the staged DisplayService and demo do not.
- [ ] A TERM IS CLASSIFIED ONLY WITH ITS OPTIMISED FIGURE BESIDE IT. What the optimised run removes is
  the unoptimised build's cost - a class of its own in the verdict - and not architecture or a missing
  primitive; only what remains is classified otherwise. That cost can come only from the kernel and the
  static programs: on the measured path, the driver's terms, the kernel's share of every term whose
  thread enters it, and a wait behind a static program's thread. DisplayService, the demo and their
  libraries are release builds in both runs, so their own code is never in that class. If the optimised
  run could not be taken, every term that could hold that cost is classified as the unoptimised build's
  cost, unresolved.

## P02M0189 - The instrument

- [ ] BUILT ON THE FACILITY THE TREE HAS: THE CLOCK AND THE ANCHOR. Every timestamp is `rt::perf_now` -
  the TSC read in ring 3 without a syscall, the same cycle clock the kernel times with - and the host
  converts cycles with the `\x1ePERF tsc_hz` anchor the kernel already publishes under the
  `development-trace` boot profile, which is also the profile `perf-trace.py` boots. The clock's
  resolution is measured (back-to-back reads) rather than assumed and is stated in the account: a
  term of 200 us measured on a clock that ticks every millisecond is not a term, it is a rounding. On
  the emulated ports the clock is the port's `perf_now` except riscv64's per-hart `rdcycle`, where
  the global `time` counter is used, and that run says which.
- [ ] ONE BOUNDED RECORD BUFFER IN THE KERNEL, because every process on the path must deliver its
  records after the run and two of them have no end: DisplayService and the driver are long-lived and
  learn nothing when the demo stops, so a buffer of their own would have no moment to leave. Under
  `development-trace` only, the kernel allocates one fixed buffer at boot (8 MiB of 32-byte records)
  and answers two new syscalls. `SYS_PERF_RECORD(site, cycles, value)` appends one record - the
  caller's site as an 8-byte ASCII tag, its own `perf_now` reading and one value - to which the
  kernel adds the thread and the core; a site with several values writes one record per value.
  `SYS_PERF_CONTROL` ARMS (empties the buffer and starts accepting), DISARMS, and DRAINS. Appending
  is one atomic index bump: it never blocks, never allocates and never formats, and a record past the
  bound is REFUSED AND COUNTED rather than wrapped over. Outside `development-trace` both syscalls
  answer `unsupported` and nothing is allocated. The syscalls are additive and the ABI version
  stays 1.
- [ ] SCHEDULER RECORDS ON THE SAME CLOCK, because a timestamp at a site cannot tell a thread that
  computed from one that was preempted - and the scheduler is round robin with a one-tick quantum
  that puts a woken thread on its WAKER's run queue, so the processes of one frame can queue behind
  each other on one core. While the buffer is armed the kernel appends a SWITCH record at every
  context switch (the core, the outgoing thread and why it left - blocked, preempted, yielded,
  exited - and the incoming thread) and a WAKE record whenever a thread becomes runnable (the thread,
  its waker, the core it was queued on, and whether a message, a deadline or something else woke
  it). Every term's work/wait pair follows from them: WORK is the on-CPU time of the thread or threads
  in the term; WAIT is the rest, split into BLOCKED (switched out blocked until woken) and RUNNABLE BUT
  NOT RUNNING (woken or preempted until switched in). Unarmed, each hook is one test of the armed
  flag.
- [ ] THE SITES, AND NO FRAME IDENTITY ON THE WIRE. The demo and the frame loop record: acquire begun
  and answered, recording begun and ended, drawing begun and ended, the producer-ready signal, the
  present call begun and returned (with the serial DisplayService answered and the damage shape), and
  every `park` - the deadline asked for in nanoseconds and in ticks, and whether `wait_any` ended on a
  message or on the deadline. DisplayService records each request received (with its operation),
  each present accepted (surface and serial), the blit begun and ended (source and output pixels,
  direct or scaled, the scanout size), the device call begun and returned, the completion sent, the
  reply sent, and each pass of its dispatch loop's `wait_any` (with the number of handles waited on).
  The virtio-gpu driver records the call received, each command's queue notified and its completion
  observed (with the polls and yields it took as the value), and the reply sent. DisplayService's
  blit and device records sit exactly where its `presentation-stats` counters are taken, so the two
  cannot disagree. The JOIN needs nothing new on the wire: the demo and DisplayService by the present
  serial DisplayService already allocates and returns in the reply; the driver's records by nesting
  inside DisplayService's device call, which is synchronous with one in flight per connection; the
  kernel's records by thread. `surface.present` and `display-device.present` are unchanged.
- [ ] THE RUNTIME REQUEST IS THE BOOT PROFILE, AND THERE IS NO BUILD FLAG. The sites are compiled into
  the ordinary build through one `rt` call beside `perf_now`; each process reads `rt::boot_profile`
  once, and unless it is `development-trace` a site is one test of that cached flag. Under it a site
  is one `SYS_PERF_RECORD`, which the kernel drops unless the buffer is armed. The measured
  application ARMS the buffer when its warm-up ends and DRAINS it when its measured frames end (the
  demo's `--account` mode), so the boot's own presents and everything outside that window are not
  recorded. The ordinary development image therefore serves and no second image is produced for the
  instrument; the account names the profile, the gate's command and the image digest, because a
  measurement nobody can reproduce from the source tree is an anecdote. `rt::PERF` and `perf_mark` -
  the per-marker serial path the console tracer uses - are left as they are: a serial write per site
  would cost more than the terms it brackets.
- [ ] THE RECORDS LEAVE THROUGH THE DEBUG SERIAL, AFTER THE RUN. The drain writes every record as a
  `\x1ePERF` line - the line form `perf-trace.py` parses, extended by the thread, core and kind fields -
  then a table naming each thread's process, then one line with the record and refusal counts. The
  collector is a frame-account mode of `perf-trace.py` that reads a serial log, sharing its marker
  parser and its `tsc_hz` conversion; the console tracer keeps accepting its three- and four-field
  markers.
- [ ] PROVE THE INSTRUMENT DOES NOT MEASURE ITSELF. The same run in a `development` boot, where every
  site is dormant, and in a `development-trace` boot with the buffer armed; both intervals are
  reported and the difference is the instrument's cost, stated in the account beside every number it
  produced. Both come from the demo's ordinary report, which covers every frame of a run whatever its
  mode; in `--account` mode the demo arms after its first eight presents and prints a SECOND report
  over the armed frames only, which is what the account is checked against. The DORMANT cost - one
  cached-flag test per site - is measured as a primitive and multiplied by the sites a frame passes,
  so the claim that the ordinary path does not pay for the instrument is a number; and the dormant
  run's interval must match the re-measure of the same command on the tree the instrument lands on
  within that measurement's run-to-run spread. An instrument costing more than the term it is placed
  around is measuring the instrument, and the way that is noticed is by having the number.

## P02M0189 - The present path, layer by layer

- [ ] Break each damage shape's interval into named terms:
  - THE FRAME LOOP'S PACING WAIT, as two sub-terms: the fallback interval the loop chose because the
    backend reported no timing, and the rounding beyond it that the 10 ms deadline unit adds. For
    every park: whether it ended on a message or on its deadline, the deadline asked for, and when the
    thread actually ran. The first park after a present ends at once on the release DisplayService
    sent before replying, and the second waits for the deadline; both are in the account;
  - acquiring an image, which is a call to DisplayService;
  - recording the scene;
  - drawing it (`prepare` and `render`);
  - the producer-ready signal and the present call's way to DisplayService;
  - DisplayService: its dispatch until the present is accepted, the blit (direct or scaled), the
    device call, the completion (the release and the events) and the reply;
  - the driver: receiving the call, building each command, THE DEVICE'S ACKNOWLEDGEMENT of each
    command - from notifying the queue to observing the completion, as the driver sees it - and the
    reply;
  - the way back and the application running again.
  Measuring the pacing wait is the whole of what this milestone does about it; changing the pacing,
  or DisplayService's missing frame timing, is not in it.
- [ ] COUNT THE COPIES OF THE FRAME, which is a number rather than a time and is the first thing a
  reader of this account will want - per damage shape and per path. How many times do a frame's pixels
  move between the application's draw target and what the device shows, how many pixels each copy
  moves, and is each of them necessary? On the scaled path a 640x480 surface becomes a 1066x800 output
  written pixel by pixel - 2.8 times the surface's pixels - and the device's transfer moves that
  rectangle; on the direct path rows are copied at the surface's own size. The same item lists every
  mapping the path makes and whether it is per frame or per generation, each with the code that makes
  it. A copy nobody can justify is the shape of a missing primitive, and this milestone names it as
  one rather than removing it.
- [ ] MEASURE THE WAIT SEPARATELY FROM THE WORK at every boundary. A layer that takes 20 ms because
  it computed for 20 ms and one that takes 20 ms because it was not scheduled for 19 of them are
  opposite findings with opposite fixes, and a breakdown that reports one number for both cannot tell
  them apart. Every term is reported as a pair from the scheduler records, its wait split into blocked
  and runnable-but-not-running. A SPIN IS NEITHER UNTIL IT IS NAMED: the driver waits for the device
  by polling the used ring and yielding every 4096 polls, so its thread is on-CPU while nothing in the
  guest computes. The device's acknowledgement is therefore reported as DEVICE TIME - wall time from
  notify to observed completion, which is QEMU's work on the host under the recorded conditions -
  with the guest CPU the spin burned and its yield count as a row of their own; it is not charged as
  guest work.
- [ ] Measure the same path with ONE VISIBLE SURFACE AND N HIDDEN ONES. DisplayService composes
  nothing - before a compositor at most one surface is visible, and a hidden surface's present
  completes as discarded without a copy - so what scales with the surface count today is its dispatch
  loop, which rebuilds its wait vector and waits on every surface channel on each pass. The demo's
  `--hidden-surfaces=N` opens N surfaces on its connection before its measured one (the newest
  surface becomes the visible one) and never draws into them; the account is taken at N = 0 and
  N = 15 (the per-connection bound of sixteen less the measured one), with ConsoleService's own hidden
  surface present in both, and the per-pass cost is reported against the handle count.
- [ ] Measure it at two sizes WITH THE SCANOUT AND THE SURFACE VARIED TOGETHER, so the direct path is
  what scales: the surface at the screen's own size (no `--size`) on a 640x480 scanout and on the
  default 1280x800 one, and the baseline's condition - a 640x480 surface scaled onto 1280x800 - as a
  third row that isolates what scaling adds. Confirm which terms scale with pixels and which do not.
  A term that does not move with the frame's area is not paying for the picture, and those are the
  terms this milestone is looking for. The harness grows one knob for it: `GPU_SIZE=WxH` in
  `qemu-run.sh` sets `virtio-vga`'s `xres` and `yres`; the size the driver actually reported is what
  the account records.

## P02M0189 - The primitives underneath

- [ ] ON THE PATH, FROM ITS OWN RECORDS. One IPC round trip on the transport this path actually uses,
  at the message sizes it actually sends, with the two ends in separate processes and separate
  Domains: the demo's `acquire-next` and `present` calls, less DisplayService's recorded handling of
  them - not a loopback in one process, which measures neither the scheduler nor the transfer. The
  CHANNEL WAKE - a message makes a waiting thread runnable, until it runs - from every such wake on
  the path. The DEADLINE WAKE - the tick that passes a wait's deadline, until the thread runs - from
  the frame loop's pacing park. The wake terms are what every "the service was not scheduled"
  explanation rests on, and the kernel wake path note in `docs/PERF.md` is from 2026-07-06 and
  predates every service on this path.
- [ ] OFF THE PATH, in the demo's `--primitives` mode, the same binary and profile as the frame: one
  syscall's floor (`SYS_DEBUG_NOOP` in a loop), so that a layer's cost can be stated in syscalls where
  that is what it is made of; what a page costs - a MemoryObject of one surface image's size created,
  mapped, touched, unmapped, and copied - because a 640x480 image is 300 pages and the default scanout
  1,000, so a microsecond a page is a millisecond a frame; the clock's resolution; and one dormant
  instrument site.
- [ ] EVERY ONE OF THESE IS MEASURED IN THE GUEST, under the scheduler and the address spaces the
  real path runs under, and in both builds of the profile item. A host-side number for any of them
  belongs in a different document.

## P02M0189 - The comparison that makes a number mean something

- [ ] Run the same drawing work two ways and put them side by side. IN ONE PROCESS: the demo's own
  scene, the same binary and profile at the same size, drawn in the guest into private memory of the
  surface's layout with no DisplayService connection, no present and no pacing
  (`test2d-sw --offscreen`), its frame being the recording and the draw. THROUGH THE REAL PATH with
  one application, which is the account. The difference is what this system charges for being a
  system, and it is the single number this milestone is for. The host benchmark suites (`bench.sh`:
  frozen scenes, host release builds) are cited as context and are not a leg of the comparison.
- [ ] STATE THE CHARGE AS A RATIO AND AS A COST PER FRAME, both, because they answer different
  questions. A path that adds 50 ms to a 5 ms frame and one that adds 50 ms to a 500 ms frame are the
  same absolute finding and opposite priorities. The charge is stated with and without the frame
  loop's policy wait, and with and without the unoptimised build's cost.
- [ ] Compare against nothing outside this tree. There is no second operating system on this machine
  to be measured against, and a number quoted from a specification or from memory is not a
  measurement. What this milestone compares is this system against itself with layers removed.

## P02M0189 - The verdict

- [ ] Name the dominant term, in one sentence, with its share of the frame. If the largest term is
  the renderer after all, that is the finding and it is written down as plainly as any other - the
  hypothesis that opened this milestone is a hypothesis.
- [ ] For every term above five percent of the frame, say which of six things it is: work that has to
  happen; work that happens more often than it has to; waiting that is a scheduling consequence; work
  this system does the long way because it has no primitive for the short way; A WAIT A PROGRAM CHOSE -
  the frame loop's fallback interval, reported and not charged to the system, while the tick rounding
  beyond it is classified like any other term; and THE UNOPTIMISED BUILD'S COST - what the optimised
  comparison run removes. THE FOURTH IS THE ONE THIS MILESTONE WAS ASKED FOR, and each instance of it
  becomes a named follow-up item stating what the missing primitive is and what it would remove. It
  does not implement one.
- [ ] Write the account into `docs/PERF.md` as one section with the date, the conditions, each
  process's build profile and staged artifact, the instrument's cost and its dormant cost, the table of
  terms per damage shape and size, the residue, the classification, and the pooled row when there is
  one. The same change corrects the 2026-09-15 row's label, which calls a prepare-and-render figure
  "record + replay", and says of that row and of its re-measure how many of their frames presented each
  damage shape. A finding that lives only in a milestone is a finding the next person measuring this
  path will not read.
- [ ] Record every disproof. A term that was expected to be large and was not is worth exactly as
  much as one that was, and this tree already keeps disproofs for the renderer - the transfer-encode
  memo, the filter-node span rewrite - for the reason that the next attempt starts knowing.

## P02M0189 - The one exception to "measure, do not fix"

- [ ] A change is in scope here ONLY where the measurement is impossible without it: a term that
  cannot be isolated because two layers share one timestamp, a boundary with no observable crossing,
  a clock too coarse to resolve it. Such a change is minimal, is named in the account as a change
  made for measurement, and carries the number that justified it. The instrument itself - the kernel
  buffer, its scheduler records and its two syscalls, the sites, the demo's measurement modes, the
  harness's scanout knob and the collector - is this milestone's product and not such a change;
  dormant, its cost is the number the instrument items measure.
- [ ] Anything else found on the way is written down and left alone. A milestone that finds a
  ten-line fix and takes it has spent its remaining measurements defending that fix.

## P02M0189 - Gates and completion

- [ ] HOST TESTS for the instrument's host-testable parts. The record buffer's layout, bound and
  refusal count live in a small `no_std` crate the kernel links (as it links `src/acpi`) and are
  tested on the host. The collector's join (present serial, call nesting, thread), its grouping by
  damage shape, its work/wait split from switch and wake records and its residue are tested against
  fixture logs - including a log whose buffer refused records, one missing a site and one with a
  second thread of the demo on a CPU inside a draw, all of which it must reject - run by the gate
  before it boots anything. A ring that silently drops the last frame of every run is an instrument
  that reports the frames nobody cared about, which is why the buffer refuses and counts rather than
  wraps.
- [ ] THE GATE: `qemu-2d-account`, `src/tools/check-qemu-2d-account.sh`, a live x86_64 QEMU gate on the
  real virtio-gpu driver - not the guest suite's demo test, whose stand-in GPU at 192x128 has no driver
  and no device. It builds the development ISO through the lab path as `qemu-2d-demo` does, so the
  ordinary image serves and no image-producer row is added, and all its boots boot that one image by
  digest; it records that digest and the staged artifacts the build-profile section names. It refuses to
  start while another guest is up, rather than reuse an instance booted under unknown conditions or take
  down one it did not start. It pins `SMP=4`, runs headless, and boots three times:
  - `DEV_PROFILE=1 LIBER_BOOT_PROFILE=development-trace` on the default 1280x800 scanout:
    `test2d-sw --account --no-input --no-second-surface --frames=160 --phase-frames=40` at
    `--size=640x480` (the baseline's scaled condition), at the screen's own size (direct), and at
    `--size=640x480 --hidden-surfaces=15`; then `test2d-sw --offscreen` at 640x480 and at 1280x800;
  - the same profile with `GPU_SIZE=640x480`: the `--account` run at the screen's own size (direct);
  - `DEV_PROFILE=1` alone (the `development` profile, every site dormant) on the default scanout: the
    `--size=640x480` run without `--account`, for the instrument's cost and the comparison with the
    reference re-measure; then `test2d-sw --primitives`, so the dormant site is measured dormant.
  The first eight presents of each run are warm-up and are not in the account; the phase counter stops
  at `full-again`, so each `--account` run arms 152 presents - 76 of the whole surface, 38 of the
  partial phase's rectangles and 38 of the two rectangles. WHENEVER THE DEMO HAS `--workers`, every
  `test2d-sw` run of the gate pins `--workers=1`, and the third boot adds its `--size=640x480` run once
  more at the demo's default worker count, whose draw, interval and lane count are the pooled row - from
  the gate's first version if the pool is already the demo's default when the gate is written, and
  otherwise added by the change that makes it the default, to every run of the gate that exists then,
  whether or not this milestone has closed (the serial-walk item's rule, which P02M0193 states too). The
  gate fails if any damage shape's residue exceeds five percent, if any term lacks its work/wait pair,
  if the drain reports a refused record, if the `tsc_hz` anchor is missing, if the account's draw and
  interval disagree with the demo's armed-frames report beyond the clock conversion, or if a thread of
  the demo other than the one that recorded the draw is on a CPU inside an `--account` run's draw -
  which is how a pooled default nobody pinned would show. It is registered in `check.sh`'s gate table
  and in the verification model: in its gate list with `bin.test2d-sw` as the subject and, as covered
  components, the drawing stack the `qemu-2d-demo` gate covers plus `bin.display_service`,
  `bin.virtio_gpu` and the kernel, and in its list of gates that boot a guest. The gate is the thing
  that keeps the account true after the next change to any layer in it.
- [ ] The emulated ports run LAST, once x86_64's account closes, and only to check it: the gate's
  scaled `--account` run under the `development-trace` profile, through the lab's cold scenario runner,
  which is how a guest runs on those ports. Their numbers go in the same section, marked as what they
  are.
- [ ] No milestone item here is closed by an argument. Every one of them closes on a number, and a
  number that was not measured in this tree by a command in this tree is not one.

EXCLUDES: the desktop leg - the real path "with the display doing what a desktop makes it do" - and
any measurement of composing several visible surfaces: DisplayService composes nothing, and P02M0103
leaves the compositor, simultaneous composition and z-order to a later milestone, which measures that
leg when it exists. Changing the frame loop's pacing, DisplayService's missing frame timing, or any
layer's speed, beyond the exception above.
