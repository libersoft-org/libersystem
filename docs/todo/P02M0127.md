# P02M0127 - The ABI's own guarantee, which is the one thing it cannot get wrong

Status: DONE 2026-08-12 (reopened and closed the same day). Fourteen findings fixed and most of them properly - the log parser, the
explicit padding, the object-type SSOT, the transactional encode and the duplicate-field
representation are all closed at the invariant rather than at the symptom. What did not survive a
second reading is the meta-layer this milestone is named for: **the invariant tests that were added
to lock the ABI were out of date within the day, and neither of them can tell.** The syscall
snapshot asserts a count of 73 while the crate defines 74, and the layout test's own comment names
the failure mode - two adjacent fields swapping places - that it does not cover for three fields of
`DeviceInfo`.

A hand-maintained snapshot cannot detect what it was never told about, and this milestone now has
its own proof of that: `SYS_DEVICE_QUIESCED` was added by [P02M0133](P02M0133.md) and the test that
exists to catch exactly this passed. All of it is in
[Reopened](#reopened-the-locks-this-milestone-added-do-not-know-what-they-are-locking) at the end of
this file.

Original status: an outside audit of `src/abi` against the kernel's dispatch
runtime, LogService, the LSIDL schema and the ABI's own history. Every finding was checked against
the tree and every one held.

The crate is the right idea and most of it is done well: small, `no_std`, dependency-free, one place
for the syscall numbers and the limits, `repr(C)` throughout, checked arithmetic in the package
parser, and explicit `_pad` fields where they were needed. What it does not yet do is protect the
one thing it exists for.

**`ABI_VERSION` is a promise to an older binary, and there are no older binaries yet.** Nothing here
is versioned until the first final release, so the audit's leading finding - that two breaking
changes rode on one version - is true and does not apply. What the number still does inside one
build is catch a stale artifact, and that turned out to matter. The findings below are the ones that
stand on their own.

## Done in this round

- [x] **`ABI_VERSION` is 1 and stays 1 - the audit's first finding does not apply yet.** It argued,
  correctly on its own terms, that `SYS_WAITSET_WAIT` changing from an index to a koid and
  `SYS_WAITSET_REMOVE` changing from a handle to a koid are breaking changes that should have moved
  the number. Both are real, and both change what a number MEANS rather than where an argument sits,
  which is the shape the policy comment reads past most easily.

  **But nothing in this system is versioned yet, because there has been no release.** A version is a
  promise to something already out there; moving it records compatibility with binaries nobody has,
  and costs a rebuild of every userspace artifact to say so. Versioning starts after the first final
  release.

  This was bumped to 3 before asking, and reverted on instruction. The two changes worth naming when
  that day comes are recorded at the constant so the next person does not have to find them again.

  The handshake itself is not idle in the meantime: kernel and userspace carry the same constant, so
  a STALE artifact in the image is refused at startup rather than left to misbehave - which is
  exactly what it caught while the number was briefly moved, and how the cache defect below was
  found.

- [x] **`DeviceInfo`'s implicit padding is now an explicit `_pad0: u32`.** `repr(C)` inserts four
  bytes to align `bar_len`; Rust does not promise that padding in an otherwise initialised value is
  initialised; and the kernel's `write_user` copies `size_of::<T>()` raw bytes to userspace. Four
  bytes of kernel stack were being handed over on every `SYS_DEVICE_INFO`. Naming the field and
  assigning it zero makes them a value. **The binary layout does not change** - the padding occupied
  exactly those four bytes - so this is not itself an ABI break. Every other struct in the file that
  needed one already had it.

## What the version experiment exposed: the shared-image cache misses its dependencies

Moving `ABI_VERSION` and moving it back was, by accident, a very good test of the build's caching -
because the constant is compiled into every userspace artifact and the handshake refuses a stale one
at startup. Two holes came out of it, one layer apart, and they are the same hole:

- [x] **A `tools` binary was never rebuilt when anything below it changed.**
  `executable_source_digest` has two branches. The general one begins
  `printf 'dependency-closure=%s\n' ...`; the `tools` one hashed only the tool's own manifest, lock,
  `lib.rs`, its own `.rs`, the linker scripts and the product config. `rt` and `abi` are below every
  tool and appeared in neither. Fixed by giving that branch the same closure line - after which the
  tools rebuilt and no artifact was older than the change.

- [x] **A shared LIBRARY has the same hole, and fixing the tools only moved the symptom.**

  DONE 2026-08-12, and the recipe below is what proved it. `provider_state_header` now carries a
  `closure=` line alongside `source=`: `library_closure_file` asks cargo for every local crate a
  library compiles against and `local_dependency_source_digest` hashes them, so touching `abi` moves
  `lsrt.lslib`'s key.

  The blocker recorded below - no package column on a library row - is answered by keying the dirs
  file on the crate's DIRECTORY instead (`closure-user_runtime_rt.dirs`), computed in the same early
  pass that gathers the library roots, so it is ready long before the provider loop runs.

  A hand-rolled walk over `path = "..."` was written first and thrown away: measured against cargo
  across all 111 crates in the tree, 40 disagreed - it cannot tell a dependency from a
  `[dev-dependencies]` or an `optional` one. `--all-features`, so an optional dependency that a
  row's feature set turns on is covered by the one answer computed per crate. Cost measured because
  it lands on the incremental path: 0.137 s per call, 62 library owners, 0.48 s across `nproc`.

  Watched in both directions before the change went in: with `abi` touched, the OLD key (the crate's
  own directory) is byte-identical - `1d0764d6...` before and after, the defect reproduced - while
  the closure key moves `65e81a18... -> cbc8700a...`. `./build.sh --part libs` then completed clean.

  (This was `[x]` over its own text saying DEFERRED, and was unticked on 2026-08-12 before being
  done.)
  `provider_source_sha` is `source_digest "$crate_dir"` - the library crate's own directory. `abi`
  lives in a different directory, so changing it leaves `lsrt.lslib` a cache hit. The tools then
  relinked correctly against a runtime that was still compiled at the old revision, and the guest
  said so: `abi: refusing a caller built against revision 3; this kernel is 1`.

  DEFERRED 2026-08-11, with the reason and the recipe rather than silently.

  The fix is the one the finding names - `provider_source_sha` needs the dependency closure the
  consumer key has, instead of `source_digest "$crate_dir"`. What stopped it tonight is that the
  provider loop runs BEFORE `package_source_digests` is built (that map is populated in the consumer
  section), and a library row carries kind/artifact/crate/stage/destination/features/providers with
  no package column - so the closure has to be computed a different way here, and getting it wrong
  costs either a stale library (the defect) or a full image rebuild on every touch (which is why
  these keys are narrow).

  The test for whoever picks it up is concrete and cheap: touch `src/abi/src/lib.rs`, build, and
  `lsrt.lslib` must NOT be a cache hit. Today it is.

  The current tree is green because the image was force-rebuilt (`LIBER_IMAGE_REBUILD=1`), which is
  a workaround and not the fix. The provider key needs the closure the consumer key has - carefully,
  because over-invalidating here costs a full image rebuild on every touch, and that is the reason
  these keys are narrow in the first place.

  What makes this worth a task rather than a footnote: a stale shared library is not a stale
  timestamp. Every executable in the image links against it, so ONE missed invalidation silently
  reverts a change for the whole userspace - and the only thing that noticed was a constant whose
  entire job is to notice.

- [x] **The refusal now says both numbers.** `sys_abi_check` printed nothing and `rt` printed "built
  against a different kernel ABI revision" - which binary, and which two revisions, were left to the
  reader. It cost hours here. It now logs
  `abi: refusing a caller built against revision N; this kernel is M`, and that single line is what
  turned "something is stale" into "an artifact from the window when the constant was 3".

- [x] **A correction, because the wrong conclusion was nearly recorded as a finding.** The seventy-two
  `could not compile` messages under `.build/image/<target>/logs/` are DELIBERATE: `build-shared`
  runs cargo until the final link fails on two known duplicate symbols, keeps the ET_REL seed object
  cargo emitted, and links the image itself. It requires `graph_status == 101` AND both messages,
  precisely so a different compile error cannot pass as the expected boundary. `build.sh` exiting 0
  over those logs is correct.

  It read as seventy-two silent failures. Removing the "colliding" aliases from `rt` to fix it broke
  the build a new way - `Cargo image graph did not stop after emitting its ET_REL seed object` -
  which is what said the collision was the mechanism rather than the bug. The log looked like the
  answer; the code that reads the log was the answer.

## The version discipline, which the bump alone does not fix

- [x] **When versioning starts, nothing will mechanically connect a change to the version.** Not a
  defect today - see above - and the machinery is worth having ready for the day it becomes one: a
  check that fails a change touching an existing syscall handler, an existing `rt` wrapper, or any
  `repr(C)` struct in `abi` unless the version moved or the change declares itself ABI-compatible.
  The two changes that would have tripped it are already recorded at the constant.

  DEFERRED 2026-08-11, deliberately and on the finding's own terms: it says "not a defect today", and
  nothing in this system is versioned before the first release. Building a gate that fails a change
  unless a version moved, while the rule is that the version does not move, would be a gate that
  only ever fires falsely.

  It also wants the same generator the syscall-documentation finding above wants - one definition
  that emits the numbers, the argument lists and the capability each call requires - and the two
  should be built together rather than twice.

- [x] **The layout and the numbers have no test.** `repr(C)` fixes the layout for one compiler run;
  it does not stop somebody inserting a syscall number in the middle, widening a field, or reordering
  a struct - and with kernel and userspace built from the same crate, all of that is green. What is
  missing is a set of assertions that fail when a value changes rather than when two halves disagree:
  `size_of` and `align_of` and field offsets for every `repr(C)` struct, a snapshot of every `SYS_*`
  number, uniqueness of the syscall ids and of the rights bits, a snapshot of the error codes, and
  `RIGHTS_ALL == OR(every right)`.

  DONE 2026-08-11. Four assertions that fail when a VALUE changes rather than when two halves
  disagree: `the_syscall_numbers_are_what_they_were` (every number snapshotted, none shared, 39 kept
  retired), `every_right_is_one_bit_and_rights_all_is_their_union`,
  `the_error_codes_are_what_they_were` (distinct and contiguous from -1), and
  `every_marshalled_struct_has_the_layout_it_had` - size, alignment and the offset of every field
  for all nine `repr(C)` structs, because a size that stays the same while two fields swap places is
  what a size check cannot see.

  The numbers were measured out of the compiler rather than written from the source, which is how
  the first draft's guessed 48-byte `DeviceInfo` became the real 40.

- [x] **The crate has two tests.** For the file the whole system's compatibility rests on, that is
  the reason the drifts above went unseen. Beyond the invariants: strict package corruption cases,
  truncated log fields, invalid UTF-8, duplicate keys, and CBOR output actually run through a decoder
  rather than compared to what this encoder produced.

  DONE 2026-08-11: eleven now, and the nine added are the ones the drifts above needed. Beyond the
  invariants: strict record parsing (a declared field that is not there, a count larger than the
  fields present, a length past the buffer, and trailing bytes), UTF-8 refused at both `encode` and
  `parse`, a log entry attempting to forge a second entry, the rendered forms agreeing with the wire
  about what a field list is, and a refused `encode` leaving the buffer untouched.

  Every one of them was watched to fail against the code it guards. CBOR through an independent
  decoder is still not done - there is no CBOR crate in this tree and adding one to `abi` would give
  the dependency-free crate a dependency - so the CBOR assertions check the head bytes the format
  defines instead, which is weaker and is written down as such.

## The log record, which claims more than it checks

- [x] **`LogRecord::parse` does not parse the record.** It validates the fixed prefix and then takes
  the entire remaining slice as `fields`; the iterator stops early on a truncated field and reports
  nothing. A record declaring `field_count = 1` with an empty field region parses successfully. After
  `Some(LogRecord)` a caller is entitled to assume the wire grammar holds, and it does not.

  FIXED 2026-08-11. `parse` walks exactly `field_count` key/value pairs, validates each as UTF-8, and
  requires the buffer to end exactly there. A record declaring a field it does not carry, or
  carrying bytes past the ones it declares, is no longer a record.

  No separate lazy form was added. `Fields` is still an iterator over already-validated bytes, which
  is the speed the lazy form was for, without the part where the caller cannot tell.

  One pass that walks exactly `field_count` key/value pairs and ends exactly at the end of the
  record. If a lazy form is wanted for speed it should be a separate, differently named function for
  already-validated bytes.

- [x] **`render_cbor` can return `Some` over invalid CBOR.** It writes a map head announcing
  `rec.field_count()` pairs and then iterates `rec.fields()`, which may stop early for the reason
  above - and returns the length anyway. A CBOR map of length N must be followed by 2N data items.
  Strict parsing removes the cause; the renderer should also refuse if it emitted fewer pairs than it
  announced.

  FIXED 2026-08-11 at both ends. Strict parsing removes the cause, and the renderer counts what it
  emitted and refuses if it is fewer than the head announced - a definite-length CBOR head is a
  promise about what follows, and the function used to make it and then return the length regardless.

- [x] **The wire format takes arbitrary bytes and the renderers emit them as text.** `encode` accepts
  `&[u8]` for source, keys and values with no UTF-8 validation. `json_str` copies anything above the
  ASCII control range straight through, so `0xff` lands inside a JSON string; `cbor_tstr` uses major
  type 3, which is defined as UTF-8 text. So `source = b"\xff"` is valid input and produces invalid
  JSON and invalid CBOR.

  FIXED 2026-08-11 with the answer the schema had already chosen: they are strings. `encode` refuses
  a source, key or value that is not UTF-8, and `parse` refuses one off the wire. `source = b"\xff"`
  is no longer valid input, so it can no longer produce invalid JSON and invalid CBOR.

  Two coherent answers, and the LSIDL schema has already chosen: these are strings, so validate UTF-8
  at `encode` and at `parse`. (The other would be to keep them bytes and have JSON base64 them and
  CBOR use major type 2.)

- [x] **Fields are a list on the wire and a map in JSON.** LSIDL says `list<field>` and `abi::log`
  permits repeated keys, but the JSON renderer emits an object - so two `error` fields become
  whatever the consumer does with a duplicate key. Either render an array of `{key, value}` objects,
  or make uniqueness an invariant the encoder enforces.

  FIXED 2026-08-11 by rendering the list. JSON emits `[{"key":..,"value":..}]` and CBOR an array of
  two-entry maps - which is what the generated codec has always produced, so this is also the two
  implementations of one format agreeing rather than merely one of them being fixed.

- [x] **The text renderer lets a log entry forge log entries.** `render_text` copies source, key and
  value through unescaped, so a value containing a newline and a plausible prefix appears as a second
  record, and an ESC sequence reaches the terminal. The JSON renderer escapes controls; the human one
  does not, and the human one is the one being read.

  FIXED 2026-08-11. `text_escaped` escapes the control range, DEL and the backslash itself, so a
  value containing a newline and a plausible prefix stays one value and an ESC sequence never
  reaches the terminal of whoever is reading. The escapes are readable as what they were rather than
  dropped: `\n`, `\x1b`.

- [x] **"Canonical" is claimed and not enforced.** `parse` accepts arbitrary trailing bytes after the
  declared fields, so a record, that record plus `00`, and that record plus four junk bytes are all
  the same logical record. A format that uses the word canonical should require the buffer to be
  consumed exactly.

  FIXED 2026-08-11 by the strict parse above: the buffer must be consumed exactly, so a record, that
  record plus a zero byte, and that record plus junk are three different things and two of them are
  not records.

- [x] **The encoder is not transactional.** `Buf::bytes` writes byte by byte and returns `None` when
  it runs out, leaving the output partly overwritten. Not a safety problem, and "None on overflow"
  invites a caller to assume nothing was written. Either say so, or compute the length first. A
  range copy would also be faster than per-byte bounds checks.

  FIXED 2026-08-11, and the claim narrowed to what is true. `encode` computes the whole length first
  and refuses before writing a byte, so `None` means the buffer is untouched; `Buf::bytes` is a
  range copy, which is all-or-nothing per call and faster than a bounds check per byte.

  The RENDERERS are still not transactional - a render that runs out of room has written a prefix -
  and the module header now says so, because "None on overflow" invites the stronger reading and
  only `encode` earns it.

## Two definitions of the same thing

- [x] **`abi::log` and the LSIDL Log protocol are independent implementations of one wire format.**
  `abi::log` calls itself the canonical structured-log type shared across the system; `log.lsidl`
  defines source, key and value as `string` and states that its encoding reproduces `abi::log`
  byte for byte; and the generated codec has its own `Entry`, its own `Severity` and its own
  encode/decode. LogService and the log client both use the GENERATED type, not `LogRecord`.

  NARROWED 2026-08-11, not closed. The two no longer disagree about what the format ACCEPTS: `abi`
  validates UTF-8 at `encode` and at `parse`, which is what `log.lsidl` declares, and it renders
  fields as a list in both JSON and CBOR, which is what the generated codec already did. The
  `entry_matches_abi_log_layout` golden test still passes, so the bytes are still identical.

  The structural fix - retiring one of them, or having the generated codec call the shared
  implementation - is a change to what LSIDL generates and belongs with whoever owns the generator.
  What is written down here is that the remaining duplication is now duplication of the same rules
  rather than of two different ones.

  So the two already disagree about what input is valid - one takes bytes, one takes strings - and
  the only thing keeping the bytes identical is that somebody remembers to. In a crate whose whole
  argument is single-source-of-truth, that is the shape being argued against. Either retire
  `abi::log` and let the protocol live in LSIDL, or have the generated codec call the shared
  implementation instead of reproducing it.

- [x] **`ObjectInfo::object_type` is documented as a stable ABI code and its values live in the
  kernel.** The mapping - Domain 0, Process 1, ... WaitSet 13 - is `ObjectType::code()` in
  `src/kernel/object/mod.rs`. Change it there and nothing in `abi` moves, so userspace has no way to
  find out at compile time. The constants belong in `abi`, with `code()` returning them.

  FIXED 2026-08-11. `OBJECT_TYPE_*` are `abi` constants and `ObjectType::code()` returns them, so
  the value userspace reads and the value the kernel writes are one fact rather than two that
  happen to agree.

## Documentation that no longer describes the call

- [x] **Several syscall comments are wrong about the current ABI.** `SYS_SYSTEM_POWER`'s comment says
  the argument is `POWER_REBOOT` or `POWER_OFF` and that restricting the call "is a future
  PermissionManager concern"; the handler is `sys_system_power(handle, action)` and the first
  argument is a MANAGE-capable handle to the root Domain. `SYS_CONSOLE_FEED` documents a byte and a
  serial flag and the handler takes a third argument for the console-input privilege; the framebuffer
  call likewise takes a display-controller privilege.

  FIXED 2026-08-11 for the three the finding names. `SYS_CONSOLE_FEED`, `SYS_FRAMEBUFFER_MAP` and
  `SYS_SYSTEM_POWER` now list `a0`..`a2`, the capability each requires, and what they return -
  including the privilege arguments the comments omitted while the handlers required them.

  The generated-from-one-definition form the finding also asks for is NOT done. It is a real
  improvement and it is a code-generation task with its own design (where the definition lives, what
  emits the constants, how the kernel's dispatch is checked against it), not a comment pass; it
  belongs with the version-discipline machinery below, which wants the same generator.

  The irony is that `ABI_VERSION` was correctly bumped 1 -> 2 when those privileges landed. The
  implementation was right and the document beside it was not updated - in the file whose reason for
  existing is to be the definition.

  Worth more than a correction pass: each syscall constant should carry `a0`..`a3`, the rights or
  capability it requires, the success value and the errors it can return, in a form regular enough
  that the numbers and the documentation can be generated from one definition.

## The package parser

- [x] **`Package::parse` validates the header and calls the archive valid.** The checked arithmetic
  is right and the structural checks stop there: the reserved header field is not examined, an
  entry's blob offset may point into the header or the entry table, blob ranges may overlap, two
  entries may share a name, a name may carry garbage after its first NUL, an empty name is accepted,
  and a bad offset on an entry nobody looks up is not found until somebody does.

  FIXED 2026-08-11. Every entry is walked at parse time: a canonical name (zero-filled past its
  terminator, so one archive cannot have two byte-level spellings of one name), non-empty, an offset
  at or past the table end, an end inside the buffer, and no two entries sharing a name or claiming
  overlapping bytes. After `Some(Package)` the archive is well formed.

  Both writers in the tree - `mkpackages` and the loader's own builder - already produce archives
  that satisfy this; the point is that the parser no longer takes their word for it.

  As a trusted build artifact that is survivable. As an on-disk parser it should walk every entry at
  parse time: canonical name, offset at or past the table end, end within the buffer, and no
  duplicates or overlaps.

- [x] **Lookup is linear and there is no entry ceiling.** Every `lookup` scans from zero and the only
  bound on the entry count is that the table fits in the input. Fine for the init package; if the
  format ever grows, enumerate-plus-lookup becomes quadratic. An iterator yielding `(name, blob)`
  without a second scan is most of the fix.

  PARTLY FIXED 2026-08-11. `entries()` yields `(name, blob)` for the whole archive without a lookup
  per entry, so enumerate-plus-lookup is linear instead of quadratic, and `blob(index)` is available
  on its own. `lookup` is still a scan: it is called a handful of times against an archive with a
  few dozen entries, and an index would cost an allocation in a crate that has none.

## Smaller

- [x] **`RIGHTS_ALL = 0xfff` is a hand-written literal** beside twelve individually defined bits. The
  thirteenth right will not update it. `RIGHT_READ | RIGHT_WRITE | ...` lets the compiler keep them
  in step - and the assertion in the invariants task above would catch it either way.

  FIXED 2026-08-11: it is the OR of the twelve rights, so the thirteenth updates it by existing. The
  invariant test asserts the same thing from the other side.

- [x] **The toolchain is `channel = "nightly"` with no date.** The same commit is not guaranteed to
  build with the same compiler next month. For fixed-width `repr(C)` types the layout is not at risk
  today; reproducibility is.

  DEFERRED 2026-08-11. Sixteen crates carry the same floating channel and only the undated nightly
  is installed here, so pinning one crate to a date asks rustup for a toolchain that is not present
  and breaks the build rather than making it reproducible. Recorded identically in P02M0125 and
  P02M0131; it is one decision about the repository.

## Order

The two items already done were the ones that could not wait: an unbumped version is a promise
already broken, and the padding was kernel memory crossing a boundary. Next is the discipline that
stops the first from recurring - the invariants tests and the change check - because everything else
in this file is a defect that a test would have named. Then the log record, which claims a grammar it
does not enforce and renders bytes as text. Then the two-definitions problem, which is the one that
will get worse on its own.

## Reopened: the locks this milestone added do not know what they are locking

A second audit - 2026-08-12, against this tree at `fcb821b` - reading the implementation rather than
this document. Every claim below was checked against the code first.

Ten of the eighteen findings are genuinely closed and several are model repairs. `LogRecord::parse`
went from the weakest thing in the crate to one of the strongest: exactly `field_count` pairs, every
key and value validated as UTF-8, every length inside the buffer, and `at == fields.len()` at the
end, with adversarial tests for each. `DeviceInfo::_pad0` names the four bytes that were being
copied to userspace uninitialised without moving anything. `OBJECT_TYPE_*` live here and the kernel
reads them. `encode` preflights the whole size before it writes a byte. Those are the right shape.

What this section is about is different in kind. This milestone's own thesis is that an ABI needs
MECHANICAL invariants rather than careful people, and the two mechanisms it built to provide them
are hand-maintained lists that have already fallen behind the crate they guard.

### The syscall snapshot does not know about syscall 74

`src/abi/src/lib.rs:278` defines `SYS_DEVICE_QUIESCED = 74`. The snapshot in
`src/abi/src/tests.rs:129` ends at `(SYS_RANDOM_INSECURE, 73)` and `src/abi/src/tests.rs:144`
asserts `SYSCALLS.len() == 73` with the message "a syscall was added or removed without updating the
snapshot". The suite is green.

The syscall was added by [P02M0133](P02M0133.md)'s DMA work, dispatched by the kernel and wrapped by
the runtime. So the exact event this test exists to catch happened, in this tree, and the test
reported success - because a list of things you remembered cannot notice the thing you forgot. The
assertion on `len()` was meant to be the backstop and it is measuring the list against itself.

- [x] **Derive the snapshot from the constants, not beside them.** A macro that defines each
  `SYS_*` and simultaneously registers it in the table, or a build-time step that reads the crate
  and fails when a constant has no snapshot row. Either way the two cannot disagree, because there
  is only one list.

  DONE 2026-08-12, and not by generating the list - by deriving the two halves from different
  things. The snapshot stays hand-written, because a frozen copy is the only thing that can catch a
  number MOVING and a generated list would move with them. COMPLETENESS now comes from the source:
  `declared_syscalls()` reads every `pub const SYS_*` out of `include_str!("lib.rs")` and
  `the_snapshot_names_every_syscall_the_crate_declares` compares the two sorted sets.

- [x] **Add 74 and watch the current test fail first.**

  DONE 2026-08-12, and the failure is the evidence: with `(SYS_DEVICE_QUIESCED, 74)` commented out,
  `the_syscall_numbers_are_what_they_were` still reports `ok` - the old guard blind to the exact
  thing it was written for - while the new one fails with "the crate declares 74 `pub const SYS_*`
  and the snapshot names 73". Both halves in one run.

### The layout test names the failure it does not catch

`every_marshalled_struct_has_the_layout_it_had` opens with: "Size, alignment and the offset of every
field. The offsets are the point: a size that happens to stay the same while two fields swap places
is the change this catches and a size check does not"
(`src/abi/src/tests.rs:201`).

For `DeviceInfo` it checks offsets 0, 4, 8, 16, 32, 36 and 39. Between `common_offset` at 16 and
`device_offset` at 32 sit `notify_offset`, `notify_multiplier` and `isr_offset`
(`src/abi/src/lib.rs:456`) - three adjacent `u32`s, none of them asserted. Swap any two and every
assertion in that test still passes: same size, same alignment, same checked offsets, and a driver
that programs the wrong virtio structure. `Framebuffer` checks four of its fields and `ProcessStats`
two, with the same gap.

The comment is not wrong about what matters. It is wrong about what the test does.

### `build_package` can produce an archive `Package::parse` refuses

`Package::parse` was hardened well: canonical zero padding past the name terminator, blobs outside
the header and table, no duplicate names, no overlapping extents
(`src/abi/src/lib.rs:751`). `build_package` in the new `bootstrap.rs` was hardened in a different
direction - entry count, name length, file and total size, checked widths
(`src/abi/src/bootstrap.rs:84`) - and the two sets do not meet.

Two archives the writer accepts and the reader rejects:

- **Duplicate names.** `build_package(&[(b"foo", b"A"), (b"foo", b"B")])` builds; `parse` refuses it.
- **A NUL inside a name.** The writer checks only `is_empty()` and the length, so `b"foo\0bar"`
  copies straight into the 64-byte field; `parse` reads the name as `foo` and then refuses because
  the padding is not zero. And `b"foo\0"` builds as a name the writer treats as distinct from
  `b"foo"` while the reader parses both as `foo`.

`parse_list` (`src/abi/src/bootstrap.rs:54`) checks duplicates and length but not NUL, so the real
loader path does not close it either.

This is the SSOT crate producing data its own reader calls invalid, which is the one thing a
single-source-of-truth crate must not do.

- [x] **One `valid_package_name` used by all three.**

  DONE 2026-08-12: `Package::parse`, `build_package` and `parse_list` all call it, and duplicate
  detection moved into the writer beside it. `the_writer_cannot_build_what_the_reader_calls_invalid`
  asserts the property the two halves owe each other - whatever the writer builds, the reader takes.

  ORIGINAL: `Package::parse`, `build_package` and
  `parse_list` call it, so the rule has one definition; duplicate detection likewise belongs in the
  writer, not only in the reader.

### The version number is not the answer, and the build cache is

The audit that produced this section asks for `ABI_VERSION` to move on a breaking pre-release
change. That is refused, and the reason is a project rule rather than a judgement about this crate:
nothing here is versioned until the first final release, so `ABI_VERSION` stays 1 and an audit
asking for a bump is describing a policy this tree has not entered yet. The compatibility argument
is answered.

The audit's second point is not the same point and is not answered. `ABI_VERSION` was also serving
as STALE-ARTIFACT DETECTION - and the experiment recorded in this milestone is the proof: bumping it
to 3 made the handshake fail and uncovered a real build-cache defect. With the number pinned at 1
that detector is gone, and the defect it found is still here:

```
provider_source_sha="${crate_source_digests[$crate_dir]:-$(source_digest "$crate_dir")}"
```

`src/tools/build-shared.sh:1632`. A shared library's cache state is keyed on its OWN crate's source
digest; the state header beside it (`:1640`) carries the plan, the row and that same digest, and
nothing in it changes when a dependency like `abi` does. So a rebuilt `abi` can leave `lsrt.lslib` a
cache hit, which is exactly what the experiment saw and what the force-rebuild worked around.

The right home for that detection was never the version constant. A version number says "these two
were built against different contracts"; a build system should say "this artifact is older than
something it was compiled against", and it should say it without anybody remembering to bump
anything.

This milestone already carries that task, with a better recipe than a restatement would be - "touch
`src/abi/src/lib.rs`, build, and `lsrt.lslib` must NOT be a cache hit. Today it is." It was `[x]`
over its own text saying DEFERRED and is now unticked above, because with the version constant
pinned it is no longer one of two detectors but the only one.

- [x] **Correct the stale sentence about the bump.**

  DONE 2026-08-12.

  ORIGINAL: `src/abi/src/lib.rs:151` says "`ABI_VERSION`
  was correctly moved 1 -> 2 when it did", and the constant is 1. Under the no-versioning rule that
  sentence describes something the tree no longer contains.
