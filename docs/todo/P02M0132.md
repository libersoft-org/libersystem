## What the mount accepts and fsck refuses

- [x] **The live inode tree is walked without local leaf validation.** `mark_inode_tree` checks the
  CRC, the node type and - since this session - the routing interval every key must fall in. It does
  not call `validate_fixed_leaf`, which is what proves a leaf's keys are ordered, and its own comment
  says why the interval was added: "`validate_fixed_leaf` and `validate_internal` are local". Local
  and absent are different things. `fsck` calls it; `tree_insert_node` calls it before mutating; the
  mount does not.
  FIXED 2026-08-11. `mark_inode_tree` runs `validate_fixed_leaf` and `validate_internal` under
  `mark_strict`, so a live node has to be a node - keys ordered in a leaf, separators ordered and
  children present in an internal one - before the walk follows it. It costs no I/O: the block is
  already read.

  `an_unordered_live_inode_leaf_takes_the_mount_read_only` swaps two records in the MIDDLE of the
  live inode leaf and forges the CRC the superblock records for it. The middle matters and the test
  says so: swapping the ends moves the leaf's lowest and highest keys, which the routing interval
  and the max-inode bookkeeping already notice - the first version of this test passed with the fix
  reverted, because it was measuring those. Two records in the middle change nothing but the order,
  and the mount stays writable without the fix.

  A CRC-valid leaf holding keys `0, 2, 1` is inside its routing interval and unordered, so it passes
  the mount. `tree_lookup` then binary-searches it and can answer `None` for a key that is present,
  which surfaces as `FsError::Invalid` - and `remove_inner` treats exactly that as a dangling
  directory entry, deliberately, as the operator's repair verb. So `remove("foo")` drops the only
  name of a live inode whose blocks are still allocated, and commits it.

  Run `validate_fixed_leaf` and `validate_internal` under `mark_strict`. It costs no I/O - the walk
  already reads every live tree block - and a structurally impossible live inode tree should take
  the volume read-only.

- [x] **`load_spill` accepts a chain that ends before the declared extent count.** It validates each
  chain block's count, the CRC, the bounds and the walk length, and refuses a count that cannot be
  true. What it never checks is the total: `extent_count = 7` with four inline extents and a null
  spill pointer returns `Ok(())`. `fsck` has the check and its message for it - "the spill chain
  ends before the declared extent count".
  FIXED 2026-08-11 with both checks the finding names: the cheap early one - a declared count above
  the inline capacity with a null spill pointer is corrupt before a block is read - and the total at
  the end, which every per-block check leaves open.

  `an_extent_map_that_ends_before_its_declared_count_is_corrupt` needed a raw slot writer
  (`write_inode_slot_for_test`), because `write_inode` calls `flush_extents`, which is exactly the
  repair the finding is about: it sets `extent_count = extents.len()`, so the only way to build the
  damaged shape is to go around it. With both guards removed the read returns `Ok` and the missing
  extents come back as zeros - the holes, permanently, in a generation that checksums perfectly.

  The rewrite is what makes it matter: `flush_extents` sets `inode.extent_count =
  inode.extents.len()`, so editing such an inode replaces an incomplete map with a self-consistent
  one and the missing extents become holes, permanently, in a valid generation. One comparison at
  the end of `load_spill`, and the cheaper early one - a declared count above the inline capacity
  with a null spill pointer is corrupt before any block is read.

- [x] **Nothing enforces one name per inode.** There is no hardlink API and no link count, so the
  format's implicit rule is one inode, one directory entry - and no code states it. `fsck`'s
  namespace walk does `if !reached.insert(child) { continue; }`, which is the cycle defence doing
  double duty: a second reference to an already-reached inode is skipped rather than reported.
  FIXED 2026-08-11, at both ends, and the rule is now stated where it can be enforced.

  `fsck` reports a second reference instead of skipping it: the `reached.insert` was the cycle
  defence doing double duty, and the walk still skips (descending twice is the loop it defends
  against) but now also names the inode and its second name.

  The MOUNT refuses to write to such a volume. `derive_free`'s live-generation walk already reads
  every leaf of every directory tree, so this costs one bit per issued inode number and no extra
  I/O - a fallible `try_zeroed(next_inode / 8)` beside the maps already there. Read-only rather
  than a damage flag, because the repair for an alias is to remove one of the two names, and that
  removal is exactly the operation that frees the shared inode's blocks while the other name still
  points at it.

  `one_inode_with_two_names_is_refused_by_the_mount_and_named_by_fsck` builds the image - two
  perfectly formed, correctly checksummed records naming one inode - and pins both halves. Watched
  to fail with each half disabled.

  So a checksum-valid image with `/a` and `/b` both naming inode 7 passes fsck, and `remove("a")`
  frees inode 7's blocks and deletes it from the inode tree while `/b` still points at it. The same
  holds for two names on one DIRECTORY inode, which additionally makes the namespace a graph.

  Decide the rule and enforce it: the root has no incoming reference and every other reachable inode
  has exactly one. `mark_dir_tree` already walks the directory trees at mount, so the parentage check
  can ride along rather than costing another pass.

- [x] **`fsck` never checks that a compressed extent decodes.** It verifies extent shape, the
  checksum block's CRC and each stored block's CRC, and `check_file_shape` covers the logical
  layout - but nothing runs the decompressor. The decoder correctly refuses an invalid match offset,
  a truncated sequence, a bad length extension and a stream that does not produce the whole logical
  range, so an extent whose blocks all checksum correctly and whose LZ stream is syntactically
  invalid gives `fsck: 0 failures` and `read_file: Corrupt`.

  FIXED 2026-08-11: `check_file_shape` runs the decoder over every compressed extent and drops the
  result. One extent is at most `CRCS_PER_BLOCK` blocks, so this is bounded whatever the file's
  size, and reusing the real decoder means `fsck` and a read cannot disagree about what decodes.

  The counters are separated as asked, and it took a new type to do it: `ExtentFault` (Io, Shape,
  Checksum, Stream) inside `decompress_extent_detailed`, collapsed back to one `FsError` for every
  caller that is not `fsck`. `FsckReport` grew `stream_failures` - a volume where the medium gave
  back exactly what was written, the shape is legal, and the file still cannot be read.
  `fsck_runs_the_decompressor_and_counts_a_bad_stream_apart` builds that volume, re-stamping both
  the stored block's CRC and the checksum block's own CRC so nothing else can object. Watched to
  fail.

  Validate the stream in `fsck`. It does not need to hold the decompressed extent - a decoder into a
  sink that checks the grammar and the final length is enough - and the counters should separate
  checksum failures from stream failures from structural ones.

- [x] **`fsck` does not check extents against EOF.** `check_file_shape` covers structure, ordering,
  overlap and logical overflow, and never compares an extent to `inode.size`. A file of 4096 bytes
  can carry an extent mapped at logical block 1000, which no legitimate writer produces: the blocks
  are allocated, invisible in the file's contents, and reserved forever. Require
  `logical + length <= size.div_ceil(BLOCK_SIZE)` per extent, and no extents at all when the size is
  zero. Sparse holes are unaffected - this is about allocated mappings past the end.

  FIXED 2026-08-11: `logical + length <= size.div_ceil(BLOCK_SIZE)` per extent, which also covers
  the zero-size case (nothing may be mapped). Sparse holes are untouched - this is about mapped
  blocks past the end. `fsck_reports_an_extent_mapped_past_the_end_of_its_file`, watched to fail.

- [x] **The two superblock slots are never checked against each other.** Each validates alone, and
  when both are valid the mount sorts by generation and takes the higher as current and the lower as
  previous. Nothing requires them to be the same volume: not the UUID, not `num_blocks`, not
  `root_inode`, and not that the generations are consecutive. Two checksum-valid slots from
  unrelated states mount as a pair - and `derive_free` then reads the previous root under the
  current slot's geometry, with the rolling snapshot being part of what keeps the allocator honest.
  Require the four, and treat a mismatch as recovery or read-only rather than an ordinary writable
  mount.

  FIXED 2026-08-11: the mount requires the four - same uuid, same `num_blocks`, same `root_inode`,
  and consecutive generations, because a commit writes the other slot with generation + 1 and
  nothing else. A mismatch means one of the slots is not this volume's and which one cannot be known
  from here, so the newer is used ALONE (no previous root, so `derive_free` cannot read one volume's
  older generation under another's geometry) and the mount is read-only - which keeps both slots on
  the medium for repair instead of letting the next commit overwrite the evidence. `mount_snapshot`
  refuses outright: the older slot is a snapshot of this volume or it is nothing.
  `two_superblock_slots_from_unrelated_volumes_do_not_mount_as_a_pair` breaks one field at a time,
  watched to fail.

- [x] **The superblock parser is looser than the writer.** The format says the root directory is
  inode 0 and the formatter writes `ROOT_INODE`; `parse_checked` only requires
  `next_inode > root_inode`, so an image can nominate any other directory inode as the root and
  mount over a subtree, with the rest of the inode tree becoming unreachable namespace data. The
  compression byte is written as 0 or 1 and read as `!= 0`, so 2 and 255 are also true. Neither is
  dangerous today; both are asymmetries in a filesystem that has made writer/parser symmetry a
  principle.
  FIXED 2026-08-11, and the two halves land in different places for a reason worth recording.

  The compression byte is refused at parse: a value the writer can never produce makes the SLOT
  unreadable, and the other slot is the right answer.

  The root inode is checked at MOUNT and degrades the volume to read-only. Refusing the superblock
  for it made the mount fall back to the previous generation and mount THAT writable - so a
  hand-written root would have silently discarded the newest generation instead of being reported.
  The first version of this fix did exactly that and an existing test caught it.

  `the_superblock_parser_is_as_strict_as_the_writer` nominates a real DIRECTORY as the root, because
  with a file there the "root must be a directory" check fires instead and the test would be
  measuring that one. Both rules watched to fail.

## Memory that scales with the volume

- [x] **A directory listing allocates a bitmap the size of the whole volume.**
  `collect_dir_entries_bounded` does `try_zeroed(self.free.len())` for cycle detection in ONE
  directory's B+tree. `MAX_BLOCKS` is `1 << 40`, so at 4 KiB blocks the format claims up to 4 PiB,
  and the temporary map for a `read_dir` is one bit per block of the volume: **32 MiB at 1 TiB,
  128 MiB at 4 TiB, 512 MiB at 16 TiB**. `derive_free` holds several volume-sized maps at once -
  `free`, `pinned`, the live map, the new pinned, the previous - and `fsck` allocates its own.

  FIXED 2026-08-11 for the listing walk: `collect_dir_entries_bounded` uses a `BTreeSet<u64>` sized
  by the blocks it actually visits, the same shape the transaction's `fresh` and `dead` sets already
  use. Every `read_dir`, `rmdir`, `list` and namespace walk stops allocating one bit per block of
  the volume - 32 MiB at 1 TiB, half a gigabyte at 16 TiB - to walk one directory.

  Not changed: `fsck`'s per-directory `visited` (same shape, but its "not enough memory to check
  this directory" fault is a reported outcome that a `BTreeSet` cannot produce), its whole-volume
  `seen_blocks` (a volume-sized walk wants a volume-sized map), and `drop_deleted_inode`'s marked
  map (documented O(pool), damaged-directory path only). The free-space model itself - one bit per
  block, in RAM, for the whole volume - stands, and the honest statement remains that the supported
  volume size is bounded by RAM rather than by `MAX_BLOCKS`.

  The visited set should be proportional to the tree being walked, not to the volume: a `BTreeSet`,
  a sparse map, or a generation-tagged reusable table. The free-space model itself - one bit per
  block, in RAM, for the whole volume - is the longer question, and the honest interim statement is
  that the supported volume size is bounded by RAM rather than by `MAX_BLOCKS`.

- [x] **`read_dir` materialises the whole directory.** The B+tree is built for millions of entries
  and the only way to enumerate it returns every entry in one `Vec`, with an inode lookup each and
  the volume-sized bitmap above. A cursor - `read_dir_page(dir, cookie, max)` - is what the tree is
  already shaped for.

  FIXED 2026-08-11: `read_dir_page(path, after, max)`, with `collect_dir_page` underneath. Internal
  nodes are entered at the child the cursor's hash routes to, so the subtrees entirely before the
  cursor are never read, and the walk stops as soon as the page is full. `read_dir` stays for the
  callers that want everything at once. `a_directory_can_be_read_a_page_at_a_time` checks the pages
  concatenate to exactly what one call returns AND counts block reads: a late page costs 16 blocks
  against the first page's 19, where without the pruning it costs 31. Watched to fail.

- [x] **The path parser has no total bound.** Each segment is limited to 255 bytes and nothing
  limits the path's length or its segment count, and the segments are collected with an infallible
  `Vec::push`. A caller handing the crate a large buffer of short segments gets an allocation
  proportional to it. StorageService bounds paths from outside; the filesystem crate should not
  depend on that. Resolving the path as an iterator removes the collection entirely.

  FIXED 2026-08-11. `PATH_MAX` (4096 bytes) is checked before the walk, `PATH_DEPTH_MAX` (64) during
  it, and the segment vector is reserved fallibly at a size the depth bounds - `Vec::push` aborts
  the process when memory is short, which turned a hostile path into a crash in a crate whose every
  other allocation is fallible.

  Not done: resolving as an iterator to remove the collection entirely. It is the better shape and
  it changes `split_segments`'s signature and both its call sites' borrow structure; the bound is
  what closes the hole.

## Write-path policy worth deciding rather than patching

- [x] **A write that fails compression for want of space fails the whole write.** The documentation
  says compression is an optimisation and the run stays raw when the compressed form cannot be
  stored - and `compress_extent`'s `alloc_data()?` / `alloc_meta()?` propagate `NoSpace` up through
  `compress_inode`, which `write_file_inner` calls with `?` after the raw file is already written.
  So a file that fits raw is refused, and the transaction rolls back, because the OPTIONAL step
  could not get temporary blocks. `NoSpace` from a compression attempt should discard the attempt
  and keep the raw extent; `Io` and `Corrupt` should still propagate.

  FIXED 2026-08-11: `compress_inode` treats `NoSpace` as "leave the run raw" - which is what the
  documentation always said happens - and `Io`/`Corrupt` still propagate. `compress_extent` also
  releases the blocks it had already claimed before failing, which it did not, so the discarded
  attempt no longer holds a reservation until the next rederivation.

  `a_compression_attempt_that_runs_out_of_space_keeps_the_raw_file` sweeps fill level x payload size
  and asserts the invariant that decides it: a file that fits with compression OFF must fit with it
  on. HONEST LIMIT, recorded in the test too - the sweep does not diverge under the old behaviour
  either. A write that succeeds leaves at least the slack its own commit needed for metadata, which
  is more than the two blocks a compression attempt wants, so the propagated `NoSpace` was
  unreachable on this allocator rather than merely rare. The fix is by construction.

- [x] **Decide what a pre-commit corruption discovery should do.** Compression re-reads the raw
  blocks it is about to re-encode and verifies them against their checksums; on a mismatch it leaves
  the run raw and returns `Ok(())`, and `compression_never_launders_a_corrupt_source_block` pins
  that. The reasoning is written down and is not silly: do not launder a device corruption into a
  freshly checksummed compressed extent, and let a later read or `fsck` surface it.

  DECIDED 2026-08-11, and written into `docs/LIBERFS.md` under "What a corruption found DURING a
  write does". The behaviour stands: leave the run raw, let the write proceed, let a read or `fsck`
  report it. Two reasons, both now on the page. The mismatch is evidence about the MEDIUM and not
  about the write in hand - failing the caller's write neither repairs the old block nor tells them
  anything they can act on. And the check only exists on the compression path, so making it fatal
  would mean a volume with compression enabled refuses writes the same volume with compression off
  accepts: a correctness property depending on an optimisation. The generalisation, when wanted, is
  verify-after-write independent of compression, named there as a different feature with a real
  cost and not in version 1.

  The audit's counter-argument is also right: at that moment the filesystem has proof that the bytes
  it is about to publish are wrong, and it still has a good previous generation and an unpublished
  superblock. Publishing a file it knows is unreadable is a strange contract. This is a decision
  between two defensible answers - not a bug - and it should be made explicitly, with the answer and
  its reasoning in `docs/LIBERFS.md`. A verify-after-write policy independent of compression is the
  third option and probably the one that generalises.

- [x] **A directory's cached count can be repaired into a wrong state.** `dir.size` is a cached
  entry count and `remove` does `dir.size = dir.size.saturating_sub(1)`. A directory whose stored
  count is 0 while its tree holds five entries loses a real entry and keeps the count at 0, and the
  inode is re-checksummed and committed. `rmdir` no longer trusts the count for emptiness, which was
  the important fix; this is the remaining half. `checked_sub(1).ok_or(FsError::Corrupt)` at minimum,
  and better, derive it or demote it to a hint that no mutation preserves.

  FIXED 2026-08-11, and NOT by refusing - which was the first attempt and an existing test caught
  it. `a_damaged_empty_directory_is_refused_not_emptied` pins the repair route: removing the
  children is how an operator fixes a directory whose count lies, and `checked_sub(..).ok_or(
  Corrupt)` closes it. So a count that cannot describe what was just removed is DERIVED from the
  tree that remains - the one operation that both survives the damage and ends it.
  `a_directory_count_that_disagrees_with_its_tree_is_repaired_not_ground_down`, watched to fail.

## Error vocabulary and API edges

- [x] **A memory shortage is reported as a full disk.** `MountError` distinguishes `NoMemory`, and
  inside the filesystem the fallible allocations map to `FsError::NoSpace` - `read_range`'s
  `try_reserve_exact` among them. To a caller, `NoSpace` means the medium is full, which drives a
  different policy from "the storage service is out of RAM". Add `NoMemory` to the shared `FsError`
  and keep the two apart; and finish the sweep, because some larger operations still allocate
  infallibly.

  FIXED 2026-08-11. `FsError` has `NoMemory`, and every fallible allocation inside the filesystem
  answers it: the extent vector, the snapshot hash lists, `try_zeroed`, `read_range`'s buffer.
  `NoSpace` now means only what a caller thinks it means. `MountError::NoMemory` is derived from it
  rather than from a `NoSpace` that had to be re-read as something else.

  StorageService maps both to `Again` for now, because the Storage protocol has no finer word - and
  the comment there says so, so the distinction is available the moment the protocol grows one.

  `a_memory_shortage_is_not_a_full_disk` asserts both halves, including that a genuinely full volume
  still says `NoSpace`. One existing test moved with it and its expectation was the conflation.

- [x] **A legitimate sparse file reads back as `Corrupt`.** `read_file` refuses a size larger than
  the pool's bytes, and the comment beside it acknowledges that such a file can be legitimate and
  points at `read_at`. The behaviour is right and the error is not: this is "too large to return in
  one buffer", not "the medium is inconsistent". A distinct error, so a caller can tell a damaged
  volume from a large file.

  FIXED 2026-08-11. `FsError::TooLarge` - too big to return in one buffer, ask for a range - instead
  of telling a caller the medium is inconsistent about a file the comment beside the check calls
  legitimate in the same breath. The existing test asserted the wrong word and now asserts the
  right one.

- [x] **`read_range` truncates on a 32-bit target, where its comment says it does not.** The comment
  claims u64 end to end "so a 32-bit build never silently truncates a large file", and the next line
  is `try_reserve_exact((end - offset) as usize)`. Convert with `usize::try_from` and answer the
  memory error. Whether this repository will ever have a 32-bit target is a separate question; the
  comment describes the code wrongly today.

  FIXED 2026-08-11: `usize::try_from`, answering `TooLarge` where the conversion cannot be made and
  `NoMemory` where the reservation fails. On a 64-bit target the conversion cannot fail and the
  comment was true by accident; on the 32-bit build it was written for, it was false.

- [x] **The snapshot mounts collapse every failure into `None`.** `mount_snapshot` returning
  `Option` is argued in a comment - "there is no older generation" is ordinary rather than a fault -
  and that argument holds for the absence. It does not cover the rest: `mount_at(..).ok()` and
  `mount_named_snapshot`'s `mount(dev).ok()?` turn a corrupt volume, an I/O failure, an unsupported
  format and a memory shortage into the same answer as "no snapshot here", which is the conflation
  the main mount was given `MountError` to end. `Result<Option<..>, MountError>`.

  FIXED 2026-08-11: both are `Result<Option<LiberFs<D>>, MountError>`. `Ok(None)` is the one
  ordinary absence - no older generation, or no snapshot by that name - and a corrupt volume, an I/O
  failure, an unsupported format and a memory shortage each arrive as themselves. No caller outside
  the crate existed yet, so this cost nothing but the tests that were reading the old shape.

- [x] **A commit's outcome is not expressible in its return type.** The transaction layer already
  understands the hard part: once the superblock write has been attempted, a reported I/O failure
  does not mean it did not land, so the new state is adopted and the filesystem goes read-only. The
  API is `Result<(), FsError>`, which cannot tell the caller "this definitely did not commit" from
  "this may have committed and the barrier or `derive_free` afterwards failed" - and in the
  `snapshots_dirty` case the superblock is provably published before the failure. StorageService
  needs to know not to retry blindly. A distinct `CommitUncertain` is the missing piece of an
  otherwise good crash-safety story.

  FIXED 2026-08-11: `FsError::CommitUncertain`, returned by the two paths that can only say "may
  have landed" - the write-or-barrier failure after the superblock has been offered to the device,
  and the `snapshots_dirty` walk failure, where the superblock is provably published. Both already
  adopted the new state and went read-only; what was missing was a way to say so. `Io` could not:
  a caller told `Io` retries, which is the one response that must not happen against a volume whose
  generation may already have moved past what the caller read. StorageService maps it to `Denied`
  rather than `Again` for exactly that reason. `a_failed_durability_flush_adopts_the_commit_read_

## Small

  FIXED 2026-08-11 by naming it. The convenience entry point is `format_scratch`, so a caller has to

  FIXED 2026-08-11. `commit` ends the transaction without writing when both roots and their
  checksums, the inode counter, the compression flag, the snapshot table and the fresh and dead

  FIXED 2026-08-11 with the second option: a separate validator, and the claim narrowed where it was

## Reopened: the alias check has a hole at inode 0, and fsck counts some faults twice

A second audit - 2026-08-12, against this tree at `fcb821b` - reading the repairs rather than the
finding list. Every claim below was checked against the code first.

Most of this milestone stands and the important part of it stands well. `mark_inode_tree` calls the
same leaf and internal validators the strict pass uses, so an unordered leaf no longer becomes the
basis of a writable filesystem. `load_spill` requires the chain to end where it said it would.
`CommitUncertain` exists and takes the volume read-only rather than inviting a blind retry. The
superblock pair is checked as a pair. `read_dir_page` is a real cursor. `TooLarge`, `NoMemory` and
`NoSpace` are three different answers. The portable-name split is a better rule than the one it
replaced.

The five below are what the checklist does not show.

### The alias bitmap starts with the root unclaimed

`derive_free` allocates the one-name-per-inode map as `try_zeroed((next_inode).div_ceil(8))`
(`src/fs/liberfs/src/txn.rs:239`) - every bit clear - and the record walk flags an alias only on the
SECOND sighting of an inode (`src/fs/liberfs/src/txn.rs:617`).

`ROOT_INODE` is 0 (`src/fs/liberfs/src/lib.rs:233`), and the root has no incoming reference by
construction. So a volume whose directory tree contains a record pointing back at inode 0 sets bit 0
and the walk carries on: the first sighting of the root looks exactly like the first sighting of any
other inode. The mount stays writable over a namespace loop through the root.

`fsck` gets this right for a reason worth copying rather than re-deriving: its `reached` set contains
the root BEFORE the walk starts, so a directory record naming the root is a duplicate reference the
moment it is seen. The mount's seed should say the same thing.

- [x] **Claim the root's bit before the walk**, so "already seen" is true of inode 0 from the start
  and the two checkers agree by construction.

  DONE 2026-08-12: one `set_bit(&mut names, ROOT_INODE)` before `mark_inode_tree`, seeded the way
  `fsck` seeds `reached`. `a_directory_record_naming_the_root_is_an_alias_too` builds a root leaf
  whose one record points at the root, and asserts the remount is read-only; watched to fail against
  the tree as it was.

  It also moved an existing test, which is the change being real rather than additive.
  `a_looped_namespace_cannot_hang_the_walks` builds exactly this shape on purpose and asserted
  `rename` answered `Invalid`; it now answers `ReadOnly`, because the volume is refused as a whole
  rather than that one move. The termination that test is named for is unaffected and is still
  asserted, over the loop, with the volume in the new state.

### `fsck` counts a compressed extent's checksum fault twice

`check_file_shape` handles four extent faults (`src/fs/liberfs/src/fsck.rs:487`). Only the `Stream`
arm increments `streams`; `Checksum`, `Io` and `Shape` push a message into `faults` and nothing
else. The report is then built as

```
structural_failures: faults.len() as u32 - stream_failures
```

`src/fs/liberfs/src/fsck.rs:111`. So a compressed extent whose stored blocks fail their checksums is
counted once by the scrub pass into `checksum_failures` and once again inside `structural_failures`,
and the three counters the report separates on purpose no longer mean what they say. `Io` has the
same shape with a worse label: an extent that could not be READ is reported as a structural fault of
the filesystem.

- [x] **Count each fault in the category it belongs to.**

  DONE 2026-08-12: `StructureTally` carries `structural`, `checksum`, `io` and `stream`, incremented
  at the match arm that raises the fault. The subtraction is gone, so a fifth kind cannot be
  silently miscounted into `structural_failures` the way `Checksum` and `Io` were.

- [x] **The test that is missing is the mirror of the one that was added.**

  DONE 2026-08-12: `a_compressed_extent_with_a_bad_checksum_is_counted_once` damages a stored block
  and leaves the checksum alone, then asserts `stream_failures == 0` and `structural_failures == 0`
  beside the scrub pass's count. Watched to fail with the old subtraction restored - `left: 1,
  right: 0`, the second count appearing exactly where it used to.

### Pinned snapshots get the checksum scrub and not the stream check

The live pass gained real decoding - `decompress_extent_detailed(ext)` at
`src/fs/liberfs/src/fsck.rs:485`, which is the finding this milestone closed. The named snapshot
generations go through `check_inode_tree`, which ends at
`self.load_spill(&mut inode).and_then(|()| self.count_corrupt(&inode))`
(`src/fs/liberfs/src/fsck.rs:563`) - physical checksums only.

So a compressed extent held by a pinned snapshot can have every CRC correct and a stream that does
not decode, and `fsck` reports the volume clean while its own comment says the pinned generations
are verified. The data is unreadable and nothing says so until somebody tries to read it, which for
a snapshot may be after the live copy is gone.

- [x] **One extent validator for both passes.**

  DONE 2026-08-12: `count_undecodable` runs `decompress_extent_detailed` over a snapshot inode's
  compressed extents, beside `count_corrupt`'s checksum scrub. The live pass reports each fault by
  name because it can; the snapshot pass counts them because it has nowhere to name them - and both
  ask the extent the same question. `a_pinned_snapshots_undecodable_stream_is_reported` covers it.

### The fsck extent walk clones the extent map

`for ext in inode.extents.clone().iter()` (`src/fs/liberfs/src/fsck.rs:455`). `Extent` is `Copy` and
the vector is sized by a fragmented file's extent count, which comes off the medium - so this is an
infallible allocation proportional to a number a hostile image chooses, on the check that exists to
survive hostile images. This milestone spent several findings removing exactly that shape.

- [x] **Index instead of cloning.**

  DONE 2026-08-12. The bounded `vec![0; ...]` buffers in the compression path are left as they are:
  capped by the extent size limit, which is the difference between them and a clone sized by a
  number the medium chooses.

### The directory count is repaired only when it underflows

`unlink` derives the count from the tree when `dir.size.checked_sub(1)` returns `None`
(`src/fs/liberfs/src/dir.rs:134`), with a good explanation: removing the children is how an operator
repairs such a directory, so refusing would close the only route out.

The same reasoning applies to a count that is wrong in the other direction and the code does not
apply it. A stored size of 100 over a tree of 5 decrements to 99, and the commit writes the
inconsistency back as though it were now correct. Underflow is the case that happens to be
detectable by arithmetic, not the case that matters most.

- [x] **Derive rather than decrement whenever the count and the tree disagree** - partly, and the
  part that is refused is refused on purpose.

  DONE 2026-08-12 for the shape that can be checked without paying for it: a decrement that leaves a
  non-zero count over an EMPTY tree now answers zero. An empty tree is the one shape a walk confirms
  in a single node read, whatever the directory's size.

  Deriving on every removal was considered and rejected with a number rather than a feeling:
  `collect_dir_entries` walks the whole tree, so `rm -rf` over a large directory would go quadratic.
  Paying O(n) per unlink to repair a count that is only ever wrong on a damaged volume is the wrong
  trade, and `fsck` already reports the general case by name - "size says N entries and the tree
  holds M" - which is where an operator can act on it.

- [x] **Stop recording the directory count at all.** Decided rather than done, and recorded here as
  the decision it is: NOT IN THIS MILESTONE.

  The reasoning stands and has not changed - a count that must agree with a tree is a second source
  of truth, and every defect in this thread is what that costs. What follows from it is that
  removing it is an on-disk FORMAT change: the field is in the inode, `fsck` reports on it, and a
  volume written by a build that keeps it must still be mountable by one that does not. That is a
  format-revision milestone with a migration path and a compatibility matrix, and doing it inside an
  audit repair is how a format acquires a third source of truth rather than losing its second.

  What this milestone owed was the asymmetry it is named for, and that is closed: a decrement that
  leaves a non-zero count over an EMPTY tree now answers zero (the one shape a walk confirms in a
  single node read), `fsck` reports the general case by name, and the mount no longer accepts what
  `fsck` rejects. The remaining half is carried as a note here and belongs to whichever LiberFS
  milestone takes the format next.

### Two scaling facts, recorded rather than tasked

- The alias bitmap is sized `next_inode / 8`, and its comment says it is "sized by the inode numbers
  this volume has issued, not by the pool". Inode numbers are never recycled, so on a long-lived
  volume the issued count is the LARGER of the two: ten live files on a volume that has created four
  billion temporaries wants half a gigabyte of bitmap to check ten names. It is fallible, so this is
  a mount that fails rather than a mount that corrupts - and a `BTreeSet` keyed on the inodes
  actually reached would be sized by what is there.
- The free-space model is still O(volume) and this milestone says so plainly. That is the honest
  position and it belongs in a filesystem milestone of its own - a persistent free-space tree or
  allocation groups - not here. What follows from it is that the format's 4 PiB ceiling is what the
  format can address, not what this implementation can mount, and the header should keep saying so.

- [x] **Size the alias check by what is reachable, not by what was ever issued.**

  DONE 2026-08-12: `mark_names` is a `BTreeSet<u32>` and the walk's whole interaction with it is
  `insert` returning false. The root is seeded into it the same way `fsck` seeds `reached`.

### Order

The root bit first: it is one line, it is the hole in the check this milestone is named for, and

## Reopened again: the injector and the allocator disagree about what running out means

A third audit, against this tree at `8df720c` - 2026-08-12. Four findings, every one read in the code
first. Two places where the audit named the symptom are extended here to what the code says about
itself, because in both the comment beside the defect is the argument for fixing it.

Two of the five residues are properly closed and should be credited plainly. The alias set is seeded
with `ROOT_INODE` before the walk (`src/fs/liberfs/src/txn.rs:263`), which makes the mount agree with
`fsck` by construction rather than by coincidence - the comment says exactly that, and it is the
right reason. And `fsck` indexes the extent list instead of cloning it
(`src/fs/liberfs/src/fsck.rs:509`), so a map sized by the medium no longer buys a second copy.

The other three have a shape this milestone has produced before: the fix is applied and something
about the fix is not carried through. The relevant vocabulary exists in each case - `StructureTally`
has a `stream` field, `MountError` has `NoMemory`, `try_zeroed` has a fallible form - and in each case
the new code reaches for the wrong one.

### The mount's out-of-memory arm matches the error only the test injector produces

`try_zeroed` (`src/fs/liberfs/src/lib.rs:343`) has two failure paths and they do not agree:

```rust
#[cfg(test)]
if inject::should_fail() { return Err(FsError::NoSpace); }
let mut v: Vec<u8> = Vec::new();
v.try_reserve_exact(len).map_err(|_| FsError::NoMemory)?;
```

The mount matches on the first of those. After `load_snapshot_table` (`fsops.rs:278`) and after
`derive_free` (`fsops.rs:298`):

```rust
Err(FsError::NoSpace) => return Err(MountError::NoMemory),
Err(_) => return Err(MountError::Io),
```

and the comment above the second explains the intent perfectly - "Folding that into `Io` told the
operator the disk did not answer when the disk was fine and the MACHINE was short - a wrong diagnosis
pointing at the wrong component" - while stating as fact that "`try_zeroed` reports a refused
allocation as `NoSpace`". That is true of the injector and false of the allocator.

So the production path produces the wrong diagnosis the comment was written to prevent. And it is not
only `try_zeroed`: `read_snapshot_table` returns `FsError::NoMemory` directly from three sites
(`src/fs/liberfs/src/snapshot.rs:196`, `:202`, `:226`), all of them under `load_snapshot_table`, all
of them landing in `Err(_) => MountError::Io`.

`a_mount_short_of_memory_does_not_blame_the_disk` (`src/fs/liberfs/src/tests.rs:3979`) arms
`fail_allocation_after(2)` and asserts `MountError::NoMemory`. It passes, and it passes over the
injector's error rather than the allocator's, so it cannot see this.

Note also which direction the arm is wrong in. Nothing at mount allocates disk space, so `NoSpace`
there can ONLY come from the injector - the arm exists for the test and for nothing else.

- [x] **Make the injector return what the allocator returns.** `FsError::NoMemory` under
  `#[cfg(test)]`, so the fault-injected path and the real path are the same path. That single line
  turns the existing test into a test of production.

  DONE 2026-08-12. `FsError::NoMemory` under `#[cfg(test)]`, so the fault-injected path and the real one are the same path. Two tests were asserting `NoSpace` for a refused ALLOCATION and had to be corrected with it - they were pinning the injector rather than the operation, which is the finding restated from the test side.

- [x] **Match `NoMemory` at both mount sites,** and delete the `NoSpace` arm rather than keeping both
  - a mount cannot legitimately run out of disk space, so an arm for it is a claim about a state that
  does not exist.

  DONE 2026-08-12. The `NoSpace` arms are gone rather than doubled: nothing at mount allocates disk space, so an arm for it was a claim about a state that cannot arise, and it existed only because the injector produced it.

- [x] **Sweep the rest of the mount for the same conflation.** `map_mount_error` (`fsops.rs:723`)
  answers `Io` for `FsError::Io` and `Corrupt` for everything else, so a `NoMemory` reaching it is
  reported as a corrupt volume - which is a worse diagnosis than `Io` and is the same defect one
  function over.

  DONE 2026-08-12. `map_mount_error` answered `Corrupt` for everything that was not `Io`, so a `NoMemory` reaching it was reported as a damaged volume - a worse diagnosis than `Io`, because a caller that believes it may decide the volume needs repairing.

### The alias set traded a wrong size for an infallible one

The change from a `next_inode`-sized bitmap to a `BTreeSet` is right, and its comment
(`src/fs/liberfs/src/txn.rs:238`) makes the case well: inode numbers are never recycled, so "ten live
files on a volume that has created four billion temporaries wanted half a gigabyte of bitmap to check
ten names".

The same comment records the property the replacement dropped: "It was fallible, so that is a mount
that fails rather than one that corrupts; it is still the wrong size." The bitmap came from
`try_zeroed` and could refuse. `BTreeSet::insert` (`txn.rs:263` for the root, `:643` per record) has
no fallible form, so a mount that runs short while walking a large namespace aborts the process
instead of returning `MountError::NoMemory` - and not aborting on memory pressure is what the whole
fallible-allocation series in this milestone was for.

This is not an argument for the bitmap. It is the third structure in this file that needs "grow, or
say no", and the first two got one.

- [x] **Give the alias set a fallible growth path.** A sorted `Vec<u32>` with `try_reserve` and a
  binary search answers the same question - "have I seen this inode" - with an allocation that can
  refuse, and it is smaller per element than a `BTreeSet` node. A chunked sparse set is the other
  shape; either is fine, and the requirement is that inserting can return `NoMemory`.

  DONE 2026-08-12. A sorted `Vec<u32>` with `binary_search` and `try_reserve`: the same question, an allocation that can refuse, and smaller per element than a tree node. The comment that recorded what the `BTreeSet` gave up - "It was fallible, so that is a mount that fails rather than one that corrupts" - is what this restores.

- [x] **Then propagate the refusal.** `mark_inode_tree` already returns `Result`, so the insert's
  failure travels the path the walk's other failures do, and the mount answers `NoMemory`.

  DONE 2026-08-12. `mark_inode_tree` already returns `Result`, so the insert's failure travels the path the walk's other failures do and the mount answers `NoMemory`.

- [x] **A test that refuses the allocation mid-walk** and asserts `MountError::NoMemory` rather than
  an abort - which is the same test shape `fail_allocation_after` already provides, once the finding
  above makes it exercise the real error.

  DONE 2026-08-12. `a_mount_that_runs_short_inside_the_namespace_walk_refuses_rather_than_aborts` sweeps every budget from 0 to 40 over a volume of 24 files and asserts a mount either completes or answers `NoMemory` and never anything else - including never aborting, which is what a sweep can assert and an aimed case cannot.

### A snapshot's undecodable stream is counted as a checksum failure

The detection half is done and done well. `count_undecodable` (`src/fs/liberfs/src/fsck.rs:484`)
calls `decompress_extent_detailed` and counts `ExtentFault::Stream`, and its comment states the
principle: "whatever the live walk asks of an extent the snapshot walk asks too - the difference
between the two is which tree is being walked, not which checks apply."

The classification half is not. `check_inode_tree` folds the two counts into one `u32`
(`fsck.rs:642`):

```rust
self.load_spill(&mut inode).and_then(|()| self.count_corrupt(&inode)).map(|bad| bad.saturating_add(self.count_undecodable(&inode)))
```

and the caller adds that to `checksum_failures` (`fsck.rs:116`). So a pinned snapshot whose blocks all
match their checksums and whose LZ stream does not decode is reported as a medium-integrity fault.

`StructureTally` (`fsck.rs:8`) already carries the four categories apart, with `stream` documented as
"Every block came back as written and the shape is legal, and the stream still does not decode" - and
the live pass uses it. The snapshot pass returns a bare count, so the distinction the live pass makes
is thrown away one call later. By the comment's own principle, the difference between the two walks
should be which tree is walked, not which category the answer lands in.

- [x] **Return a `StructureTally` from `check_inode_tree`,** so the snapshot pass reports into the
  same four counters the live pass does. The u32 it returns today is the only reason the categories
  cannot survive the call.

  DONE 2026-08-12, threaded as an out-parameter rather than as a return type, which is the shape `walk_inode_records` and `check_file_shape` already use. `bad` now counts ONE thing - checksum faults - because adding to both double-counted every fault: once into `checksum_failures` through the return, once into its category through the tally.

- [x] **Decide what a snapshot's `Corrupt`/`Io` root should count as** while doing it. `fsck.rs:118`
  turns both into `1` on `checksum_failures`; an unreadable node is `io` and a broken shape is
  `structural`, and the tally has both.

  DONE 2026-08-12, and the audit's suggestion was half wrong, which is worth recording. It proposed `Corrupt` as `structural`; in this codebase `FsError::Corrupt` is defined by `fs-core` as "a block read back whose checksum did not match the one stored beside its pointer" - the MEDIUM, which is what `checksum_failures` counts. So `Corrupt` goes on being counted as a checksum failure and `Io` - the medium not answering at all, which is a different fact - is what moved. `a_second_snapshots_bad_link_is_checked_too` is what caught the mistake.

### A test that asserts "somewhere" cannot see a miscategorisation

`a_pinned_snapshots_undecodable_stream_is_reported` (`src/fs/liberfs/src/tests.rs:1009`) ends:

```rust
assert!(report.checksum_failures > 0 || report.structural_failures > 0, "the snapshot's damage is reported somewhere: {report:?}");
```

The message says what the assertion is: damage reported SOMEWHERE. A disjunction over the categories
is exactly the assertion that cannot detect the finding above it - and `stream_failures`, the counter
the fault actually belongs in, is not in the disjunction at all.

It is worth naming this as its own item rather than folding it into the fix, because the live
equivalent got this right in the same round:
`a_compressed_extent_with_a_bad_checksum_is_counted_once` asserts `checksum >= 1`,
`stream == 0` and `structural == 0` - the three-way form. The snapshot test was written to the weaker
shape beside it.

- [x] **Assert the category, not the total**: `stream_failures == 1`, `checksum_failures == 0`,
  `structural_failures == 0`. Written this way it fails today, which is the point.

  DONE 2026-08-12, and writing the assertion first found a second defect the audit did not reach: the FIXTURE never damaged the snapshot's extent. `first_extent_of` reads the LIVE inode tree, the test rewrote the file so the live tree named a different extent, and the damage landed there - so the old disjunction was passing on a checksum failure in the live tree, not on the snapshot's stream. The file is now removed rather than rewritten, `first_extent_of_snapshot` and `forge_snapshot_inode_slot` walk the snapshot's own three CRC levels, and `read_file_from_snapshot` asserts the damage landed before fsck is asked about it.

- [x] **Use the three-way form for every fault-classification test.** A report whose value is that it
  separates three causes is not tested by an assertion that accepts any of them.

  DONE 2026-08-12 for this one; `stream_failures == 1` and `structural_failures == 0` are asserted exactly, and `checksum_failures` carries a written reason for not being asserted at zero rather than a weakened assertion - see the test.

Recorded so the next audit does not re-derive it.

## Reopened a third time: the fallible replacement is quadratic, and the tally stops one level up

A fourth audit, against this tree at `4350074` - 2026-08-14. Six findings and all six hold. None is a
data-loss path and none is new corruption; what they are is the cost of two repairs that changed the
right thing and left the shape around it.

The audit's account of the third round is right and closes it: `try_zeroed` answers `NoMemory` in test
and production alike so the injector no longer diagnoses a fault the real path cannot produce, `mount`
maps `NoMemory` to `MountError::NoMemory` on both the snapshot-table and free-derivation paths, the
alias set is fallible again, the root is seeded before the walk, and an undecodable snapshot stream
lands in `stream_failures` rather than in `checksum_failures`. Those hold.

### The alias set traded an abort for a quadratic mount

`mark_names` is a sorted `Vec<u32>` maintained by `binary_search` plus `insert`
(`src/fs/liberfs/src/txn.rs:643-655`). The fallibility is the point and it is right: `try_reserve`
before every `insert`, `NoMemory` propagated, no allocator abort. What came with it is that
`Vec::insert` shifts every element after the position.

Inode numbers arrive in the order the namespace walk reaches them, and the directory B+tree is ordered
by `(name_hash, name)` - so the arrival order is effectively unrelated to numeric order, and each
insert moves about half the vector. Over N reachable inodes that is O(N²) memmove during MOUNT, on a
filesystem whose own milestones aim at directories with millions of entries.

Nothing about the correctness needs the vector sorted DURING the walk. The question the walk asks is
"has this inode been seen", and the answer is only needed at the end.

- [x] **Append during the walk, sort once after it.** `try_reserve(1)` then `push` - same fallibility,
  same refusal - then `sort_unstable()` and one linear pass over adjacent pairs to find a repeat.
  O(n log n) in place, and seeding `ROOT_INODE` first still catches a record pointing at the root,
  because a duplicate root shows up as an adjacent pair like any other.

- [x] **Move `mark_alias` to that pass.** It stops being a flag set during the walk and becomes a
  property of the finished set, which is also what makes the sort valid - there is nothing to preserve
  about the order the inodes were reached in.

### The regression test for that fallibility cannot reach the allocation it is named for

`a_mount_that_runs_short_inside_the_namespace_walk_refuses_rather_than_aborts`
(`src/fs/liberfs/src/tests.rs:4066`) sweeps allocation budgets and requires every mount to complete or
answer `NoMemory`. The injector it drives is `inject::should_fail()`, which is checked inside
`try_zeroed` (`src/fs/liberfs/src/lib.rs:354-357`).

The alias set does not go through `try_zeroed`. It calls `names.try_reserve(1)` directly, at
`txn.rs:263` and `:652`. So the budgets this test sweeps land on the free map, the pinned map and the
other `try_zeroed` allocations before and around the walk - never on the allocation the test's own
comment says it is about ("THE ALIAS SET, which stopped being fallible when it stopped being a
bitmap").

The production code is correct: `try_reserve` really does return `Err` and the caller really does
propagate it. What is wrong is the evidence. A test that names a specific allocation and cannot fail
it is the shape this milestone keeps finding elsewhere - a check that passes for a reason other than
the one it states.

- [x] **One fallible-allocation helper, and the injector inside it.** `try_reserve_one(&mut vec)` -
  or `try_push` - used by the alias set and by every other growable structure on the mount path, with
  `inject::should_fail()` checked there as well as in `try_zeroed`. Then the budget sweep reaches every
  allocation rather than one family of them.

- [x] **Assert which allocation failed,** at least for the alias set: a budget that lands inside the
  walk must produce `NoMemory` from the walk, not from a map allocated before it. Otherwise the test
  passes at budget zero for the wrong reason and no one can tell.

### The typed tally stops at the recursion boundary

`StructureTally` splits `structural`, `checksum`, `io` and `stream`, and the leaf checks use it: an
I/O failure on a file inode does `tally.io += 1` and returns 0. But `check_inode_tree` and
`check_dir_tree` still return `Result<u32, FsError>`, and their recursive arms still collapse a child
subtree's failure into a count (`src/fs/liberfs/src/fsck.rs:698` and `:735`):

```rust
Err(FsError::Corrupt | FsError::Io) => 1,
```

That `1` is added to `bad`, and `bad` becomes `checksum_failures`. So an I/O failure deep in a subtree
is still reported as a checksum failure - the same miscategorisation the round just closed, one level
of recursion up.

And `snapshot_tally.io` is collected and never reported. `fsck.rs:125` increments it on a root-level
snapshot I/O failure; the report at `:144-145` reads `snapshot_tally.structural` and
`snapshot_tally.stream` and nothing else. A counter that is written and never read is worse than no
counter, because it looks like the case is handled.

- [x] **Thread the tally through the whole recursion** instead of returning `u32`. Every arm that today
  turns an error into a count becomes an increment on the field that names it, and
  `Err(FsError::Corrupt | FsError::Io) => 1` disappears rather than being repeated more carefully.

- [x] **Decide what an I/O failure is in `FsckReport`,** and then report it. Either an `io_failures`
  field beside the other three, or a stated rule for folding it into one of them - what may not stand
  is a `StructureTally::io` that both halves of the walk maintain and the report cannot express.

### The snapshot stream fixture still leaves one checksum failure unexplained

The test that proves the classification (`tests.rs:1035-1050`) asserts `stream_failures == 1` and
`structural_failures == 0`, and deliberately does not assert `checksum_failures == 0`. Its comment
says why, honestly: making a snapshot's medium look perfect takes four re-stamps, three are done, and
the volume still reports one checksum failure - "so something in the chain is read through a path the
raw edits do not reproduce - `read_block_csum_aware`, most likely".

The reasoning that the classification is provable without it is fair as far as it goes. But the test's
premise is "an undecodable stream over blocks that all match their checksums", and the fixture does
not establish the second half - so what the test actually pins is that the stream fault is counted in
`stream_failures`, not that it is the ONLY thing counted. And the named suspect was never confirmed.

- [x] **Find the fourth re-stamp,** or find out that `read_block_csum_aware` reaches the block by a
  path the edits do not cover - which would be a finding about the reader rather than about the
  fixture. Either way the comment currently records a guess, and this file's own standard is that a
  defect seen and unexplained is not one that has been closed.

- [x] **Then assert all three counters,** the way `a_compressed_extent_with_a_bad_checksum_is_counted_once`
  already does for the live path.

### Two smaller things

- [x] **`dead_prev` is a `BTreeSet` filled by infallible `insert`.** Every other structure on the mount

## Fifth audit (2026-08-15)

An outside review of LiberFS after the fourth audit's fixes. It confirms six of them as properly
implemented - the O(n^2) alias set, the injectable alias OOM, the deep snapshot I/O classification,
the published `io_failures`, the snapshot-LZ fixture and the fallible `dead_prev` derivation - and
raises four points. All four hold.

The first is a REGRESSION THE FOURTH AUDIT'S OWN FIX INTRODUCED, and it is the most serious thing
any of these rounds has found in this crate.

- [x] **`commit` could answer `NoMemory` for a transaction that was already on the medium.**

  DONE 2026-08-15. Making `dead_prev` a fallible `Vec` was right for the mount path and was applied
  to the commit path as well - where the copy happens AFTER the superblock write. A bare `?` there
  answered `NoMemory` for a generation that had already landed.

  That is not a diagnostic imprecision. StorageService maps `NoMemory` to `again`, which tells the
  caller to RETRY - and retrying a transaction whose generation has already moved is the exact thing
  `CommitUncertain` exists to prevent; it maps to `denied` for that reason. So the fix for an
  abort-on-OOM created a path where a durable write was reported as a retryable failure.

  THE CORRECT ANSWER WAS ALREADY IN THE SAME FUNCTION, ten lines above: the `snapshots_dirty` branch
  handles a failure after a successful publish by going read-only and returning `CommitUncertain`,
  with a comment saying the caller is told not to retry the write it thinks it lost. The file
  contained both the right answer and the wrong one.

  Fixed by not being on that road at all: the next generation's dead list is known before the
  barrier, so it is BUILT before the barrier - `try_reserve_exact` and a copy while failing is still
  free - and what happens after the superblock lands is a swap, which cannot fail. A refusal now
  happens where a rollback is still possible and means what it says.

  There was a second effect the review names and it is gone with the first: the old shape took
  `self.dead` and moved entries one at a time, so a failure partway left the remainder in neither
  set - blocks marked allocated that this mount would never reclaim. A leak rather than a
  use-after-free, and it needed a full re-derive to recover.

- [x] **And the OOM sweep could not have caught it.**

  DONE 2026-08-15. The sweep asserted that after a refused write the EARLIER data still reads, which
  is a statement about the volume being answerable, not about the refused write. The half that was
  missing is the half the contract is about: a `NoMemory` reaches the caller as `again`, so it is a
  truthful answer only if nothing landed.

  The sweep now reads back the range the refused write aimed at and asserts its bytes are not there.
  Watched failing: with the post-commit `?` restored, budget 1 reports `NoMemory` while the bytes
  ARE on the volume, and the assertion names exactly that. This is the one finding of the two audit
  rounds on this crate whose defect is demonstrably reachable through the public API.

- [x] **The live namespace walk folded I/O and structural faults into `checksum_failures`.**

  DONE 2026-08-15. The report grew an `io_failures` field for the snapshot recursion while the live
  walk kept counting a failed READ as a checksum mismatch - so the same disk not answering was an
  I/O fault when the snapshot path met it and a checksum failure when the live path did. An operator
  reading "checksum failure" reaches for the medium, and half the time the medium is fine.

  The three are now counted separately where they are raised: `Io` into `io_failures`, `Corrupt`
  into `checksum_failures`, and `Invalid` - a directory entry naming an inode that does not exist -
  into `structural_failures`, because that is the namespace being inconsistent rather than the bytes
  being wrong. Every one of them still puts the path in `damaged`; what changed is the diagnosis.

  A test asserted the old taxonomy - that a dangling entry is a checksum failure - and the assertion
  was the taxonomy being wrong rather than the code. It now asserts all three counters, which is
  what makes the distinction a rule instead of a rename.

- [x] **`FsError::Corrupt` was carrying two different meanings inside the tree walk.**

  DONE 2026-08-15. fs-core defines `Corrupt` as a checksum mismatch, and `check_inode_tree` returned
  it for two faults that are not: a tree deeper than the format permits, and a pointer outside the
  pool. The caller counted every `Corrupt` as a checksum failure, so an operator was told a block
  failed its checksum when nothing had - and the fault that actually occurred was not reported at
  all.

  Both are now counted where they are RAISED, into `tally.structural`, and the walk answers `Ok(0)`:
  no checksum failures below here. That is the shape `walk_inode_records` already used for the
  faults it names, so the two halves of the structure pass now classify the same way.

- [x] **Say what the injector actually injects.** DECIDED 2026-08-15: **the comments were wrong, not the injector.** The review's one remaining nit is fair: the shared
  `try_push` calls the failure injector on every call, including ones where the vector already has
  capacity and `try_reserve(1)` would allocate nothing. The property it proves is "every fallible
  growth point can refuse", which is the safety property worth having - but comments around the
  sweeps describe it as a count of ALLOCATIONS, which it is not. Either the injector should fire
  only when the reserve would really allocate, or the comments should say what it is.

  The comments now say what it is: a budget counts FALLIBLE GROWTH POINTS - calls that could be
  refused - and not mallocs. That is the right unit for the property the sweeps prove, which is
  "every growth point can refuse and the caller survives it": a refusal at a call that would not have
  allocated tests it exactly as well, because the caller cannot tell which kind it got and must not.
  Firing only on real allocations was the other option and is worse - it would make the budget a
  number about `Vec`'s growth strategy and skip whole call sites because an earlier push happened to
  reserve room, which is a weaker test wearing a truer name.
