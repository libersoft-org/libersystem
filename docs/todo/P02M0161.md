# P02M0161 - Every driver family invents its own bring-up wire

Status: COMPLETE (2026-08-28). Reaudited on 2026-08-28; see "What the 2026-08-28 audit found" at the end of this file.

Previously: Status: COMPLETE (2026-08-27). THE DRIVER PROTOCOL. SECOND OF SEVEN SLICES - see P02M0098
for the split.

One handshake, versioned, with the binding's generation on every frame. The wire is
`src/user/libs/driver/protocol`; all eight drivers and DeviceManager speak it, and so do the two
kernel suites that spawn a real driver and stand in for DeviceManager while it comes up - from the
same crate, because a harness with its own copy of the frame layout is a harness that drifts.

Proved by 15 host tests (two deliberate defects planted, both caught), a green 354-test x86_64 run
including `virtio_snd_driver_captures_a_period_from_the_device` - a real driver brought up over the
new wire - and `check.sh --gate driver-protocol-note`, which reads the ELF note out of the artifacts
that SHIPPED rather than out of the linker's output.

AND ON ALL THREE ARCHITECTURES: `driver-note: 21 driver artifacts across 3 architecture(s) carry the
protocol note their own source emits`. That was the last outstanding clause - a note that survived on
one port and not another would have made the version refusal an architecture-dependent accident, and
the three linker scripts having been asked nicely is not evidence about what shipped.

WHAT IS NOT PROVED YET: only x86_64 has BOOTED the new handshake. The aarch64 and riscv64 in-kernel
suites have not been run against it, and they are where a driver that comes up differently on an
emulated machine would show.

## Goal

One handshake between DeviceManager and a driver, versioned, with the binding's generation on
everything either side says. Small enough to read in one sitting.

The claim this milestone may make: after it, a driver's start and its report are the same exchanges
whatever the driver is, a message from a replaced process cannot be mistaken for the replacement's,
and a driver built against a different version of the protocol is refused before it is given a
device. NOT its stop - `STOP`/`STOPPED` is P02M0165's, whole, and a goal that promised it here would
be promising the half of the lifecycle this milestone does not build.

## What is there now

- **THERE IS NO HANDSHAKE TO SPEAK OF.** `launch_one` calls `recv_blocking` and treats
  `Received::Message` as success whatever it contains: it stores the handle, prints the bytes and
  returns true. So a driver that sends nothing recognisable is a driver that came up, and the text
  each family sends - `driver.virtio-blk: online (00:02.0)`, and a different string per driver - is
  read by nobody. What looks like a per-family dialect is really no protocol at all.
- **THE REPORT IS A HUMAN SENTENCE STANDING WHERE A MESSAGE SHOULD BE.** The boot-report milestone
  changed those strings for readability and had to chase every assertion that parses them.
- **THERE IS NO VERSION AND NO GENERATION.** A driver from an older image and one from this build are
  indistinguishable, and a message from a process the manager has already replaced is accepted as the
  replacement's.
- **AND NOTHING CARRIES A VERSION BEFORE THE CLAIM.** The generated registry has no protocol version
  in it, so there is nothing to refuse a driver on until after it has been handed a device.

## Work

- [x] **M1 - the wire format is exact, which means the widths are written down.** A header of fixed
  size, little-endian throughout because all three targets are, and a payload whose length the header
  states:

  | field | width | |
  | --- | --- | --- |
  | `magic` | `u32` | one constant; a frame without it is not a frame |
  | `version` | `u16` | the protocol version, matching the ELF note of M3 |
  | `opcode` | `u16` | one of the five in M2; anything else is refused |
  | `generation` | `u64` | P02M0098's claim generation, on every frame in both directions |
  | `payload_len` | `u32` | bytes after the header; bounded by a stated maximum |

  At most ONE capability handle per frame - a rule this protocol IMPOSES, not one the channel
  enforces for it. That was written the wrong way round here and the difference matters:
  `sys_channel_send_caps` moves a whole list, and the ordinary receive *"takes the first and drops
  the rest"*. A protocol that assumed one and used the plain receive would silently discard whatever
  a driver attached beyond it - capabilities gone, nobody told, on the path M5 calls hostile input.

  So the receive is the capability-aware one, the count is checked against what the opcode declares -
  exactly 0 or exactly 1 - and a frame carrying the wrong number is refused with EVERY handle it
  arrived with closed, not only the first. A refused message must not leave a capability behind,
  whichever way it was malformed, and "behind" includes the ones the reader never looked at.

  And each opcode's payload is a fixed shape, because "a stated size for every payload" is not a
  size until it is stated:

  | opcode | handle | payload |
  | --- | --- | --- |
  | `BIND` | no | the `DeviceInfo` the manager sends today, plus `resource_count: u16` (the manager's count of the list it is about to send - see M2) |
  | `RESOURCE` | yes | `kind: u16` from the closed set in M2 |
  | `OFFER` | yes | `provider_kind: u16`; at most `MAX_INITIAL_OFFERS` per handshake |
  | `READY` | no | empty |
  | `FAILED` | no | `code: u16` from `DriverFailureCode`, NOT P02M0162's `FailureCause` |

  `payload_len` is bounded by the largest of these, which is `BIND`'s; a frame declaring more is
  refused before anything is read.

  `FAILED` CARRIES A DRIVER'S VOCABULARY, NOT THE MANAGER'S. This item first reused P02M0162's
  `FailureCause`, which lets a driver - hostile input, by M5's own rule - declare `iommu-required` or
  `teardown-unconfirmed`: causes only the manager can determine and which would then be recorded as
  fact. `DriverFailureCode` is a CLOSED set of what a driver can honestly know about itself, and it
  is written out because P02M0162 reads retryability off each code - a set given as three examples in
  prose is a set every implementer closes differently:

  | code | retryable | |
  | --- | --- | --- |
  | `resource-unusable` | no | what it was handed does not work, and a second attempt hands it the same thing |
  | `device-not-responding` | yes | the part may yet come up; this is the case a rebind exists for |
  | `out-of-memory` | yes | a transient shortage, and the backoff is what it costs |
  | `unsupported-device` | no | it read the device and will not drive it; nothing changes that |
  | `internal-error` | no | the driver does not know what went wrong, so nothing says a second try differs |

  The manager records any of them as `DriverReported(code)`, keeping the code rather than flattening
  it away, and reads the retryable column rather than deciding again at the call site.

  ONE VERSION COVERS THE OPCODES AND THE PAYLOADS TOGETHER. Adding an opcode, or changing any payload
  above, bumps the single `version` that appears both in the frame header and in M3's ELF note. Two
  numbers that could disagree would make "the handshake confirms what the note claimed" a check of
  nothing.

- [x] **M2 - the message set is five opcodes, and each has one direction.** This item said four and
  wrote two of them as `RESOURCE`/`OFFER`, which cannot be one opcode: they travel in opposite
  directions, and with one handle per frame the manager needs to send more than one capability. What
  `launch_one` already does is the shape:

  | | |
  | --- | --- |
  | manager -> driver | `BIND` once, then `RESOURCE` as many times as the device needs |
  | driver -> manager | `OFFER` up to `MAX_INITIAL_OFFERS` times, then exactly one `READY` or one `FAILED` |

  `BIND` names the device and carries no handle. Each `RESOURCE` carries one, and the set is larger
  than this item first said: `launch_one` sends `DEVICE`, `IRQ`, `KEYS`, `SYSPOWER` and `CONSOLE`
  today, and which of them a given driver gets depends on the driver. So the sequence has no length a
  driver could infer, and `BIND` states it - `resource_count`, which is the length of the list the
  manager has ALREADY assembled for this device, not a number read out of the registry entry: the
  entry has no resource list to read one from. It is a promise the manager makes about what it is
  about to send, which is the only kind it can keep. Each `RESOURCE` carries a typed `kind` from that
  closed set. Without both, a
  driver either waits forever for a resource it will never be sent or starts before one it needs has
  arrived, which is a race no amount of care at the call site removes. A
  provider handle crosses in `OFFER`, because today's drivers hand one back and the system needs a
  working intermediate state; the offers are held UNPUBLISHED until `READY`, and closed on `FAILED`,
  so a driver that dies half way through announcing itself announces nothing. "Any number" is not a
  bound and M5 requires one - and it cannot be the registry's, because the `provides` count is
  P02M0164's and this milestone has to be implementable before it. So the bound here is one
  protocol-wide `MAX_INITIAL_OFFERS`, which P02M0164 later narrows per entry; an offer past it is
  refused with its handle closed rather than accumulated. The
  `resource_count` in `BIND` is the manager's OWN count of the list it is about to send - the
  registry `Entry` has no resource list to read it from - so it is a promise the manager keeps to
  itself, which is the only kind it can keep. `READY` and `FAILED`
  are terminal for the handshake: a second one, or an `OFFER` after either, is refused. Dynamic
  `ADD`/`REMOVE` is P02M0164's and `STOP`/`STOPPED` is P02M0165's, entirely. An unknown opcode is
  refused rather than accepted as "some message arrived", which is the whole of what happens today.

- [x] **M3 - the version is known before the claim, from the artifact - and the note has to survive
  the build to be there.** A fixed ELF note `{magic, protocol_version}` in the staged driver, read
  before `device_acquire`; the handshake then confirms what the note claimed. Refusing after the claim
  means taking a device back from something that should never have held it.

  THE NOTE AS SPECIFIED WOULD NOT REACH THE STAGED FILE, and this was checked rather than assumed. All
  three linker scripts end with the same discard:

  ```
  /DISCARD/ : {
      *(.eh_frame*)
      *(.note .note.*)
  }
  ```

  `src/user/user.ld`, `src/user/user-aarch64.ld` and `src/user/user-riscv64.ld` each throw away every
  note section, and `mkpackages` then runs `llvm-strip --strip-all` over what is left. A note emitted
  by the compiler would be gone twice over, and the failure is silent: every driver would read as
  having no note, which is indistinguishable from a driver that declares no version. So the item is
  not only "emit a note" - it is a section this build keeps: named, `KEEP`-ed in all three scripts,
  and `SHF_ALLOC` so that `--strip-all` leaves it. And the gate is that it is still there in the
  PACKAGED bytes, not in the linker's output: a check against the artifact `mkpackages` staged, for
  every driver in the image, because a note that survives on one architecture and not another would
  make the version refusal an architecture-dependent accident.

  THE DRIVER EMITS IT, FROM THE SAME CONSTANT THE RUNTIME SPEAKS. A note written by the packager
  would be the packager's opinion of the driver's version rather than the driver's own, and the two
  could differ for exactly the reason this milestone exists: nothing checks them against each other.
  The note and the `version` field of every frame come from one shared constant, the packager only
  VERIFIES that the staged artifact carries one, and a test binary whose note disagrees with what it
  puts on the wire is refused - which is the only way to know the confirmation in the handshake is
  confirming anything.

- [x] **M4 - the generation is on every frame, and an old one is dropped.** A `READY`, a failure or an
  offer stamped with a generation that is no longer current is dropped and its handles closed. A
  process being replaced cannot touch its replacement's state.

- [x] **M5 - the message is hostile input.** Every length, count, name and handle count is bounded and
  validated before use. A driver is a separate process that may be wrong or malicious.

- [x] **M6 - a driver's report is not a sentence.** The human line stays and stops being load-bearing:
  the manager acts on the typed frame and prints its own line. Changing a boot line's wording must
  not be able to break binding.

## Definition of done

- One handshake serves every driver in the image, and no per-family string is read on the binding
  path.
- An unknown opcode, a malformed length and an oversized field are each refused, with a host test per
  case - and a refused frame leaves no capability behind.
- A driver whose ELF note declares an unimplemented protocol version is refused before any claim -
  and the note is present in the PACKAGED artifact of every driver in the image, on all three
  architectures, asserted by a gate rather than by the linker having been asked nicely.
- A handshake ends in exactly one `READY` or one `FAILED`; a second terminal frame, or an offer after
  one, is refused, and offers made before a `FAILED` are closed rather than published.
- A frame carrying a stale generation is dropped and its handles closed, proved by replaying one from
  a replaced process.
- Changing the wording of a driver's boot line breaks nothing.

## What this milestone refuses, and why

- **The artifact digest in the registry.** The registry is generated when the services are built; the
  staged driver's final bytes exist only after stripping and packaging. Checking one against the
  other here is a build-order cycle, and closing it means reordering the pipeline so the staged
  drivers exist first - which is artifact integrity, not a protocol, and belongs with the work that
  owns staging.
- **Process exit as a protocol message.** It arrives on the process handle, not on the channel.
  Correlating it with a generation is the state machine's job, so it is P02M0162's.
- **A general IPC schema or an IDL for drivers.** The tree has LSIDL for services; the driver
  handshake is a handful of messages on one channel and does not need a language.
- **Designing the power and watchdog messages now.** They are named in P02M0165 and will be added by
  the milestone that has a caller for them. A protocol with unused verbs is a protocol nobody has
  tested.
- **Migrating drivers to new capabilities.** This changes how a driver is started and answers, not
  what it is given. The resources are P02M0098's and the binding unit is P02M0163's.

## What the 2026-08-28 audit found

Five findings. Four fixed, one REJECTED.

FIXED:
- **DeviceManager never read the protocol note before claiming.** The note's own definition says it
  exists for this moment - "refusing a driver AFTER the claim would mean taking a device back from
  something that should never have held it" - and nothing read it: `declared_version` answers for the
  RUNNING binary and `handshake` calls it after the spawn. `declared_version_in(elf)` reads an
  arbitrary staged artifact by the note's fixed 28-byte prefix, and `begin_bind` refuses before the
  claim with `FailureCause::ProtocolMismatch` - the variant that had no producer. No note is refused
  too: not an artifact this build made.
- **A frame could carry bytes its `payload_len` did not declare.** `decode` bounded only from below;
  every caller passes the exact received message, so the bound is now an equality with
  `FrameError::TrailingBytes`.
- **A malformed `FAILED` became a valid `internal-error` report.** It manufactured the FACT
  `DriverReported(InternalError)` from input that contained no code, and applied that code's
  non-retryable policy. It is now refused and dropped like any other malformed frame.
- **A second terminal frame was acted on.** The `Ready` arm discarded `move_to`'s result, so a
  second `READY` on an online binding republished offers and re-armed supervision. It now reads the
  refusal the table already computes.

REJECTED - **bump `VERSION` for the added opcodes and the wider `OFFER`.** The observations are
right and the conclusion does not hold here: every driver, the manager and the note constant are
built from ONE tree by one build, and `check-driver-protocol-note.sh` verifies that all 21 artifacts
across three architectures carry the same version. The version-1 driver the finding reasons about
cannot exist. A version is a message to an artifact built at a different time; there is no such
artifact, and burning the signal now costs the one thing it will be needed for at the first release.
