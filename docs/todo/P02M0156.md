# P02M0156 - A check that skips what it cannot read has already answered yes

Status: REOPENED (2026-08-26). An independent audit of the closed milestones found 3 verified defects; they are the last section of this file. Was COMPLETE (2026-08-26). VERIFICATION INTEGRITY. NOT A NEW FEATURE.

Every check this milestone names now fails when it cannot answer, and each one has been watched
doing it.

## Goal

Make every check in this tree fail when it cannot answer, rather than pass. Two outside audits read
the verification surface and found the same shape in four different places: a check that meets input
it does not understand skips it and reaches its success line, and the line says the thing was
verified.

This milestone owns the checks; the code they were pointed at is owned by the milestone that wrote
it. What changes here is the ORACLE - what a gate accepts as evidence, and what it does with input it
cannot read.

The claim this milestone may make is narrow and worth stating: after it, a check in this tree either
proves what its success line says or it fails. It does not make the underlying properties stronger,
and none of the fixes below is allowed to be presented as new coverage.

## What is there now

Measured on 2026-08-26, against `fd9c1620`.

- **THE STAGED-TREE VERIFIER SKIPS FOUR KINDS OF BAD INPUT AND THEN SAYS EVERYTHING MATCHES.**
  `verify_staged_provider_chains` ([build-shared.sh:238](../../src/tools/build-shared.sh)) has three
  fail-open branches on one screen:

  ```bash
  staged_digests[$artifact]="$(staged_identity_digest "$file" "$note" || true)"   # :244
  llvm-objcopy --dump-section .note.liber.identity="$note" "$file" /dev/null 2>/dev/null || continue  # :248
  [[ -n "$expected" ]] || continue                                               # :254
  ```

  A provider whose identity cannot be read becomes an empty digest; a consumer whose note cannot be
  dumped is skipped; a provider that is missing from the map is skipped. Delete a provider a consumer
  records and the verifier exits zero saying every library matches the providers staged beside it.
  The note is additionally parsed by taking `descsz` bytes at offset 20 without checking that
  `descsz` fits inside the section that was dumped.

- **THE RECOVERY COMMAND IT PRINTS DOES NOT EXIST ON ONE ARCHITECTURE.**
  [build-shared.sh:264](../../src/tools/build-shared.sh) builds it as `./build.sh --arch
  ${target%%-*}`. For `riscv64gc-unknown-none-elf` that is `--arch riscv64gc`; the public name is
  `riscv64`. The one message printed to somebody whose build just failed names a command that fails
  differently.

- **`arch-surface` SCANS FOR TWO OF THE THREE THINGS ITS MILESTONE NAMES.** The sentence it exists to
  enforce is "no production architecture contract member whose answer is `todo!`, `unimplemented!` or
  an unconditional placeholder panic". [check-arch-surface.sh:25](../../src/tools/check-arch-surface.sh)
  matches `todo!(` and `unimplemented!(`. A function whose entire production body is `panic!("not on
  this port")` passes.

- **`qemu-numa` REFUSES A STRING THE TEST DOES NOT PRINT.** The gate's own comment says the weaker
  outcome "is a `numa-fixture:` line, which the check below refuses"
  ([check-qemu-numa.sh:90-97](../../src/tools/check-qemu-numa.sh)); the check below greps for
  `numa-fixture: skipped`. The weaker outcome prints `numa-fixture: the thread was queued on cpu N of
  node M and that core drains its own queue` ([smp/numa/tests.rs:100](../../src/kernel/smp/numa/tests.rs)),
  which does not match. A run where no placed thread ever ran on its target core is green.

- **THE NAMED INTERRUPT AND SMP PROFILES HAVE A RUNNER KNOB AND NO REGISTERED GATE.** `check.sh`
  registers `arch-surface`, and nothing for the GICv2, GICv3-without-ITS, GICv3-with-ITS or AIA/IMSIC
  profiles at one and four cores. Their results exist as historical log excerpts inside a milestone
  document. A knob that can be turned by hand is not a check that runs.

## Work

- [x] **M1 - the staged verifier becomes fail-closed.** Every expected dynamic library must have a
  readable, well-formed identity note; anything else is a refusal that names the artifact and what
  was wrong with it. Validate the whole note header - `namesz`, `descsz`, type, the name itself, the
  dumped section's real length and the padding - rather than trusting the declared length. Compare
  the provider edge set against the manifest as a SET: no missing provider, no unexpected one, no
  duplicate, and every digest equal. Keep the packager's independent assertion exactly as strict; it
  is the only thing that noticed the original defect and it stays the second layer.

- [x] **M2 - a mutation test per fail-open branch.** The existing identity mutation changes a valid
  `profile=release` inside one artifact and requires the packager to refuse. Add one per branch M1
  closes: a missing `.note.liber.identity` section, `descsz` of zero, `descsz` past the end of the
  section, a provider named by a consumer and absent from the staged tree, a consumer whose note
  cannot be dumped, and a duplicate provider row. Each must fail the staging phase, not the packager.

- [x] **M3 - the recovery command names a real architecture.** Map the target triple to the public
  architecture name rather than cutting at the first dash, and cover all three in a test so the next
  target added does not reintroduce it.

- [x] **M4 - `arch-surface` covers the third construct without banning legitimate panics.** A
  validation that panics deliberately - a firmware value this port cannot address, a state the
  machine must not be in - is correct code and must keep passing. What must fail is a production
  function whose entire body is an unconditional panic, which is a stub wearing a different macro.
  The line-oriented `awk` filter cannot tell those apart and should not be asked to: use a real parse
  of the item, and keep a self-test that feeds it both shapes plus the `cfg` forms the current filter
  mishandles (attribute items without a braced block, nested `cfg`, `cfg_attr`).

- [x] **M5 - `qemu-numa` refuses every weaker outcome, not one spelling of it.** Require the strong
  line for each placement test, and fail on any `numa-fixture:` line reporting a fallback, a skip or
  a queued-but-not-run result. Then verify the gate can fail: run it once against a log with the
  weaker line and require a non-zero exit.

- [x] **M6 - the named QEMU profiles become registered gates.** One gate per profile in `check.sh`,
  each with its own positive oracles rather than a shared "it booted": the interrupt controller the
  kernel says it discovered, a timer tick count above a required floor, a remote IPI acknowledged,
  a TLB shootdown acknowledged, and on the four-core profiles a secondary that entered the scheduler.
  The timer oracle in particular must assert a MINIMUM DELTA - a boot that delivered zero ticks and
  printed a count is the same false green as the two above.

- [x] **M7 - the gates prove they can fail.** Each gate this milestone touches gets a recorded run
  against deliberately broken input showing the refusal, in the same style as the existing
  `--self-test` in the trace checker. A gate whose failure path has never executed is a gate whose
  failure path is untested code.

## Dependency order

M1 and M3 are one file and can go first. M2 depends on M1. M4 and M5 are independent of both. M6 is
the largest item and depends on nothing here; it may be split off if it grows. M7 closes each of the
others as they land, rather than at the end.

## Definition of done

- No check in this tree reaches a success line after skipping input it could not read; each such
  input is a named refusal.
- Every gate this milestone touches has a recorded run in which it fails, produced by feeding it
  input it must refuse.
- The staged-tree verifier compares the provider edge set as a set and validates the whole ELF note
  header; each of its former fail-open branches has a mutation test.
- `arch-surface` refuses a production function whose entire body is an unconditional panic and
  accepts a deliberate validation panic, with a self-test covering both.
- `qemu-numa` refuses every weaker placement outcome, proved by a run against a log carrying one.
- Every named interrupt and SMP profile is a registered gate with its own oracles, and the timer
  oracle requires a minimum tick count rather than reporting whatever it counted.

## What this milestone refuses, and why

- **Making the underlying properties stronger.** Fixing an oracle is not new coverage, and none of
  these fixes may be described as one. Where a fixed gate now fails, the failure belongs to whichever
  milestone owns that code.
- **A blanket ban on `panic!` in architecture code.** A validation that refuses a firmware value it
  cannot address must panic; banning the macro would push those refusals into silent fallbacks, which
  is the failure mode this tree keeps finding.
- **Deleting a staged tree automatically on a mismatch.** Unchanged from the milestone that wrote the
  verifier: a builder that discards the evidence of its own inconsistency is how a mechanism stays
  unknown.
- **A generic "all gates must be able to fail" harness.** Each gate refuses different input for
  different reasons; a framework that generated the broken input would be a second implementation of
  every check, and it would be the one nobody verified.

### One claim these audits raised that is not a defect

- **"A trailing `&` on a governed interactive tool is silently ignored."** True, and deliberate:
  [shell.rs:897-899](../../src/user/services/core/src/shell.rs) says in as many words that a governed
  tool is a foreground launch and the caller's `bg` does not apply. A full-screen tool is handed
  `CONTROL` of the terminal, so backgrounding it has no meaning to give. The only thing worth
  considering is telling the user that the `&` was dropped instead of dropping it quietly, and that
  belongs to whoever next touches the shell's job control rather than here.

## Results

### M1/M2 - the staged verifier, and seven ways to make it refuse

`verify_staged_provider_chains` had three fail-open branches on one screen and the note it read was
validated by one field. Both are closed, and the closing is proved by a gate that applies each
failure to the REAL staged tree and puts it back:

```
staged-consistency: adpcm records lsrt
staged-consistency: the unmutated tree verifies
staged-consistency:   refused: a provider a consumer records is missing from the staged tree
staged-consistency:   refused: a staged provider carrying no identity note
staged-consistency:   refused: a staged library carrying no identity note
staged-consistency:   refused: an identity note declaring a zero-length record
staged-consistency:   refused: an identity note whose declared record runs past the section
staged-consistency:   refused: an identity note carrying another format's name
staged-consistency:   refused: a provider whose identity changed while its consumers were not rebuilt
staged-consistency: seven mutations refused, and the tree verifies again afterwards
```

The last line is not decoration: every case restores the file it broke, and a gate that left the
staged tree mutated would break the next build for a reason nothing explains.

Found while writing it: the reader validated `descsz` and nothing else, so the name it depends on to
locate the record was never checked - and the first attempt at validating it read the name from
offset 8 rather than 12, which the tree's own artifacts caught immediately.

### M3 - and the architecture that does not exist

`${target%%-*}` is right for two targets and wrong for the one whose triple carries an extension:
`riscv64gc-unknown-none-elf` became `./build.sh --arch riscv64gc`. The one message printed to
somebody whose build has just failed named a command that fails differently. `public_arch` maps all
three.

### M4 - the third construct, and why the scan stopped being a scan

The sentence the gate enforces names three answers and it searched for two. Adding `panic!` to the
pattern was not available: a panic in architecture code is very often correct - a firmware value this
port cannot address, a table that contradicts itself - and banning the macro would push those
refusals into silent fallbacks, which is the failure this tree keeps finding.

Telling a refusal from a stub needs the ITEM. The scan is now a small Rust program that walks the
file as tokens: it knows what is inside a comment, a string or a character literal, so a brace in any
of them does not move its depth, and it matches a `#[cfg(test)]` item by its real extent instead of
guessing where a block ends - which the line filter could not do, and which is why it also mishandled
`cfg_attr` and any attributed item without a braced body.

Fifteen sources in its self-test: six that must be reported, nine that must not.

```
arch-surface: the scanner refuses every shape it is meant to and accepts every shape it is not
arch-surface: 61 file(s), no production contract member answers with a placeholder
```

Watched to fail, with a stub planted in `src/kernel/arch/mod.rs`:

```
arch-surface: src/kernel/arch/mod.rs:108: planted_stub - its whole body is an unconditional panic!(), which is a stub wearing a different macro
```

### M5 - the string the test does not print

The `qemu-numa` comment said the weaker placement outcome "is a `numa-fixture:` line, which the check
below refuses", and the check looked for `numa-fixture: skipped`. What the test prints is
`numa-fixture: the thread was queued on cpu N of node M and that core drains its own queue`. The one
outcome the gate exists to reject was the one it let through. Any `numa-fixture:` line is now the
refusal, on the x86_64 profile and on both device-tree ports.

Watched to fail, against a log carrying exactly the line the test prints:

```
qemu-numa: a placement test could not make its full claim on the a crafted profile
kernel.smp.numa.a_thread_placed_on_a_node_runs_on_a_core_of_that_node...	numa-fixture: the thread was queued on cpu 2 of node 1 and that core drains its own queue
```

The old check finds zero matches in that same file, which is what "it let it through" means measured
rather than asserted. And on the real run the strong outcome IS reached - all three placement tests
pass on the two-node profile with no `numa-fixture:` line anywhere - so the gate is demanding
something the kernel actually delivers rather than something it cannot.

While there, the aarch64 timer oracle: it printed whatever it had counted, including zero, so a boot
that delivered no timer interrupt at all produced a line shaped exactly like one that delivered five.
Zero is now named as what it is, and the profile gate requires a floor rather than a count.

### M6 - a knob is not a check

Every named interrupt and SMP profile is a registered gate: GICv2, GICv3 without its ITS, GICv3 with
one, and the RISC-V AIA, at one core and at four. Each requires the kernel to NAME the controller it
discovered - a boot that fell back to a compiled descriptor prints a different line and a boot that
found nothing prints none, and both pass an "it booted" check - a timer that delivered at least five
ticks, and on the four-core profiles every declared core online rather than "more than one". The ITS
profile additionally must not report a reason it could not hand out an MSI, because `GICv3 from the
device tree` is the same line the ITS-less profile prints.

```
arch-profiles: aarch64 gicv2, 4 core(s)
arch-profiles:     discovered: GICv2 from the device tree - distributor 0x8000000+0x10000, cpu interface 0x8010000+0x10000
arch-profiles:     timer delivered 5 ticks
arch-profiles:     SMP - 4 of 4 declared cores online
arch-profiles:   the ITS profile reported no reason it could not hand out an MSI
arch-profiles: riscv64 aia, 4 core(s)
arch-profiles:     discovered: IMSIC S-mode files from the device tree at 0x28000000+0x4000, 4 hart(s)
arch-profiles:     timer delivered 5 ticks
arch-profiles:     SMP - 4 of 4 declared harts online
arch-profiles: every named profile booted, named the controller it has, delivered timer interrupts and brought up every declared core
```

**Its first version was wrong twice, and the runs said so.** It forced `UEFI=0`, which is not how the
suite boots the device-tree ports - "they have no other way in since the packaged bootstrap archive
and the magic scan that found it were retired" - so the loader never handed the kernel the PSCI
conduit it reads out of the tree, no secondary started, and a four-core profile came up on one core.
And it passed a second `-machine` to add the RISC-V AIA, which this runner's only riscv64 machine
already has. A gate that boots differently from the thing it is a gate for is testing a machine
nobody runs.

### What this milestone found on the way, and fixed

- **A compile error reported as a build-system fault.** `build-consumer-object` expects rustc to stop
  at a link collision and emit an object; when rustc stops EARLIER, at an ordinary compile error, the
  message said "cargo did not re-invoke rustc, so --emit never ran". That sent a reader looking at the
  build system for a borrow-check error, twice, on a change to one line of a service. A compile error
  is now named as one and its errors are printed.

### Two more checks that reported the wrong failure, found by running them

Both were found by this milestone's own verification pass rather than by an audit, and both are the
shape it exists to remove: a check that could not make its claim, and said something else.

- **`signed-boot` reported a build-order problem as a trust-chain failure.** The loader selects a
  system volume by the uuid the medium names, and `./image.sh` and `./build.sh --part volume` write
  over each other's half of `.build/boot` - so building them in the wrong order leaves the medium
  paired with a volume that is not there. The loader then refuses that volume as unpaired, the
  damaged-manifest case never reaches its manifest at all, and the gate printed "a damaged signed
  manifest on the selected volume did NOT stop the boot" - a sentence about the trust chain, said
  about the build order. Three diagnosis cycles in this round went to it. The gate now compares the
  medium's pairing with the volume's superblock before the case and names the real reason.

- **`capability-trace --require-live` took the newest guest log rather than the newest log with a
  trace in it.** Any gate that runs `./test.sh --tags something` leaves a log with no trace, and this
  then reported that a tree with a perfectly good trace in the log before it had none. It now chooses
  a log for CARRYING a trace, and requires that log to be newer than the kernel beside it - because a
  trace from a kernel that has since been rebuilt is evidence about a system that is no longer here,
  which is the same failure as no evidence dressed as some.

- **And the harness reported the same build-order problem as a guest crash.** `./image.sh` puts a
  kernel on the system volume and the loader prefers it, so a suite run after one boots the SHIPPING
  kernel: userspace comes up, the guest sits at a shell, no test runs, nothing writes the debug-exit
  port, and QEMU is killed - which is indistinguishable from a triple fault to everything downstream.
  `test-kernel.sh` had the right diagnosis and fired it only on a TIMEOUT, while the same cause
  reaches the reset branch just as often. FIVE separate investigations in this round started from
  `GUEST RESET` and ended at the build order. The diagnosis is now asked FIRST on both paths, because
  if the wrong kernel booted there was no crash to investigate:

  ```
  [test-x86_64] NOTHING ran: the loader took its kernel off the SYSTEM VOLUME, not the medium this suite staged.
  [test-x86_64] A volume carrying a kernel is what `./image.sh` produces; rebuild the test-shaped one with:  ./build.sh --arch x86_64 --part volume
  ```

  Watched to say it, on the run that had just reported `GUEST RESET` for the same reason.

### What this milestone found and did not fix

- **`./image.sh` and `./build.sh --part volume` still write over each other's half of `.build/boot`.**
  The diagnosis above tells a reader what happened and how to undo it, which is what this milestone
  is for; it does not stop the two commands fighting. A build system where the order of two commands
  decides whether a gate can make its claim is a real problem, and it is a build-system problem
  rather than a checking one.
- **`EL2=1` in `test.sh` is an environment variable where everything else is a flag.** The same shape
  as `IOMMU=1`, which was fixed elsewhere in this round.

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED. A milestone about checks that answer yes to what they cannot read has two of its
own, plus one mutation it promised and did not write.

- [x] **`arch-surface` walks past production code.** `read_attribute` answers "test-only" for any
  attribute containing both the word `cfg` and the word `test`
  ([arch-surface/main.rs](../../src/tools/arch-surface/src/main.rs)). `#[cfg(not(test))]` contains
  both, and so does `#[cfg(any(test, feature = "..."))]` - so the scanner skips the production half of
  every item written either way and reports no architecture tokens in it. The selftest contains
  neither form. Its `cfg_attr` fixture carries a plain `#[cfg(test)]` on the line below it
  ([arch-surface/main.rs](../../src/tools/arch-surface/src/main.rs)), so it passes on that attribute
  and never exercises the one it is named for - and `cfg_attr(test, ..)` is not a test gate at all:
  `#[cfg_attr(test, allow(dead_code))] fn f()` is ordinary production code with one attribute applied
  under test, and the scanner skips the whole item. Read the predicate instead of the words in it -
  `test` and `all(test, ..)` gate on tests, a `not` around either does the opposite, and `cfg_attr`
  gates an ATTRIBUTE rather than the item. Cover all three shapes in the selftest.

- [x] **The identity note's type field is never read.** `staged_identity_digest` validates `namesz`,
  the name bytes, a non-zero `descsz`, and that the record fits inside the section it came out of
  ([build-shared.sh](../../src/tools/build-shared.sh)) - every field of the twenty-byte header except
  the one at offset 8 that says what kind of note this is. It is one more `od` beside the four that
  are already there.

- [x] **M2 names six mutations and the gate has five of them.** Seven cases run and the duplicate
  provider row is not among them ([check-staged-consistency.sh](../../src/tools/check-staged-consistency.sh)).
  It is worth writing because the check it would exercise is genuinely partial: only rows that
  DISAGREE are reported, so a note recording one provider twice with the same digest passes today.

Not accepted: comparing a consumer's provider set against an expected manifest set. There is no
second source of truth for that set - the note IS the record of what the link consumed - so the check
would need a separate dependency oracle built alongside the linker. That is a larger mechanism than
the gap justifies. The one-directional nature of the check is a stated limit of it, not a defect in
it. The note's padding bytes are in the same category and are not worth reading.

## Results (2026-08-26)

**`arch-surface` READS THE PREDICATE NOW.** It answered "test-only" for any attribute containing the
words `cfg` and `test`, which took `#[cfg(not(test))]`, `#[cfg(any(test, target_arch = ..))]` and
`#[cfg_attr(test, ..)]` out of the scan - three ordinary shapes, all of them production code, in a
gate whose entire job is finding placeholders in production code. `cfg_attr` is not a gate at all: it
applies an attribute conditionally and leaves the item compiled. The predicate is walked - `test`,
`all` needing one test arm, `any` needing every arm, `not` inverting - and all three shapes are in the
selftest's `must_find` list. The old `cfg_attr` fixture carried a `#[cfg(test)]` on the line below it,
so it passed on that and never exercised the attribute it was named for.

The identity note's type field is read, which was the one field of the twenty-byte header nobody
looked at. The exact padded length and the zero padding are not checked here and do not need to be:
the packager's own reader asserts both on every artifact, and a trailing byte cannot change a digest
taken over exactly `descsz` bytes.

M2 named six mutations and the gate had five. The duplicate provider row is written, and the check it
exercises was genuinely partial - only rows that DISAGREED were reported, so a note recording one
provider twice with the same digest went through. Twice is twice now, whether or not the two agree.

**AND ONE MORE, FOUND BY WATCHING A GATE RUN RATHER THAN BY READING IT.** `check-signed-boot.sh`'s
damaged-manifest case greped for "cannot be read - refusing to boot from it rather than falling back"
- which is the message `assemble_bootstrap` prints about the BOOTSTRAP SET. So the case went green on
a boot where the bootstrap set was refused and the KERNEL on the same volume fell through to the text
manifest and booted unauthenticated. The gate was asserting that SOMETHING refused, not that the
thing it is named for did, and that is how the loader defect it exists to catch survived it.

The oracle is now two assertions: no kernel was loaded, and the reason named the manifest. The first
is what "stops the boot" means; the second is what says why. A message from an adjacent code path
satisfies neither.

Not done, and deliberately: comparing a consumer's provider set against an expected manifest set.
There is no second source of truth for that set - the note IS the record of what the link consumed -
so the check would need a dependency oracle built alongside the linker, which is a larger mechanism
than the gap justifies.
