# M0147 - A wait set the kernel keeps

Every service in this system is one loop around `wait_any`, and `wait_any` takes a fresh set of
handles on every call. The kernel therefore registers a waiter on every channel in that set, waits,
and unregisters all of them again - once per pass, for as long as the service runs. The cost of one
pass is linear in how many things the service is listening to, and nothing the service does can make
it otherwise.

This was measured rather than suspected. While bounding StorageService's replies (M0139) a test was
written to connect until the service refused, and finding a client ceiling the test could actually
REACH took several attempts: forty-eight connections cost nothing measurable, and a ceiling of 256
could not be reached inside fifteen minutes of emulated time. `MAX_CLIENTS` was set to 64 because
that is where the service is still brisk - a number chosen around the defect rather than on its
merits.

A service that slows down in proportion to how many peers are talking to it is bounded in the wrong
sense: the ceiling limits the damage a connection flood does, and does not remove it. Every service
that grows a client table will meet the same wall, and each will pick its own number for the same
wrong reason.

## What this is not

Not a defect in StorageService, and not fixable there. The loop already allocates its wait set once
and clears it rather than rebuilding it - that copy is a memcpy of at most 66 words and costs
nothing. What costs is the registration on the far side of the syscall.

## What is wanted

- [x] **A wait set as an OBJECT, registered once and waited on many times.** A service creates one,
  adds the handles it cares about, and waits on that object - so adding a client costs one
  registration rather than one per pass forever after. The shape every event-notification interface
  converges on, for the same reason.

- [x] **A registration lifetime that is defined where it is awkward.** What happens when a
  registered channel is closed - by this process, or by the peer - is the question that decides
  whether the interface is usable. Silent removal, an explicit revocation event, and a stale
  registration that reports once are all defensible; leaving it undefined is not, and a stale
  registration that reports FOREVER is the failure mode that makes such interfaces infamous.

- [x] **A per-Domain bound on registrations.** The set is kernel memory a userspace caller decides
  the size of, which is the shape of every quota in this kernel and needs the same treatment.

  **This was ticked before it was true, and is true now.** What follows is what was actually there
  when the sixth audit round looked. What exists is `MAX_WAIT_SET_MEMBERS`, a
  PER-SET ceiling of 256, and the handle quota that bounds how many sets a Domain may hold. Neither
  is a bound on registrations: `ResourceAccount` carries `memory`, `handles`, `threads`, `dma`,
  `ipc_queue` and `stack`, and no counter for these. One set is 256 `Arc` references plus 256
  scheduler observer entries, and the Domain is charged **one handle** for the lot. Multiply by the
  handle limit and the quota that is supposed to bound this bounds it by nothing that resembles the
  cost. The work is in "What is still open" below.

- [x] **Tests for the parts that are not the happy path.** A registered channel closed by its peer
  while the waiter sleeps; a channel registered twice; a set outliving the handles in it; a set
  waited on by two threads; and the measurement that started this - a service with hundreds of
  clients answering at the same speed as one with three.

- [x] **StorageService's `MAX_CLIENTS` reconsidered afterwards.** It is 64 because of this defect,
  with the measurement recorded beside it in the source. Once a pass no longer costs what it costs
  today, the number should be chosen on what the system actually needs and what a handle table can
  hold - and the comment explaining the old reason should go with it.

## Where this came from

M0139's fourth audit round, as the one item that could not be answered inside the service. The
account of the measurement is in `M0139.md` under "Reopened: a fourth audit"; this file exists so
that it is not carried as an open item against a milestone whose work is finished.

## What was built

`WaitSet` is an object like any other: created by a syscall, held by a handle, counted against the
Domain's handle quota, and destroyed when the last reference goes.

The mechanism is one new kind of entry in the scheduler's wait buckets. A `BucketWaiter` is
registered when a thread parks and removed when it wakes; a `SetObserver` is registered when a member
JOINS a set and removed when it leaves. `wake_object` collects both: the threads it wakes and
removes as before, and the sets it forwards to without removing. Waking a set wakes whatever is
parked on the set's own koid, which is one registration per pass rather than one per member per pass.

One level, never a chain: a set may not contain a set, and `WaitSet::add` refuses it. A wake would
otherwise have to chase a graph, and nothing a flat set cannot serve wants that.

### The registration lifetime, decided

The set holds a REFERENCE to each member, so a member does not vanish because the handle that
introduced it was closed. Of the three defensible answers - silent removal, a revocation event, or a
stale registration that keeps reporting - this is the one that cannot lose an edge: a channel whose
peer closes becomes ready, the waiter is told, and what to do about it is a decision made with the
whole picture rather than one the kernel makes by dropping the member at the moment it became
interesting. Leaving is explicit, through `remove`, and there is a test that says so.

### Bounds

`MAX_WAIT_SET_MEMBERS` is 256, matching `MAX_WAIT_HANDLES` - a set is the persistent form of the
same question. A ceiling first, then `try_reserve`, then a refusal: the same three steps every other
caller-sized allocation in this kernel takes.

## What is still open

Three of these are blockers rather than polish: the object can today report a successful `add` for a
membership that will never be woken, which is the exact failure mode the "registration lifetime"
item above was written to rule out. They came from the sixth outside audit round, verified against
the code.

- [x] **`register_set_observer` must be fallible, and a failed registration must fail the `add`.**
  It returns `()`. When `observers.try_reserve(1)` fails it prints a warning and returns, and
  `WaitSet::add` - which called it after `members.push` - returns `Ok(())`. So `SYS_WAITSET_ADD`
  answers success for a member whose wakes will never reach the set, and a thread that then calls
  `sys_waitset_wait` with no deadline parks on the set's koid with nothing left to rouse it. The
  readiness scan the warning appeals to only runs when something wakes the set, so it does not
  rescue this: the scan is what happens after a wake, not instead of one.

  It must return `Result`, `add` must roll back the `members.push` and answer `ERR_RESOURCE_EXHAUSTED`,
  and the test is deterministic - a member whose registration is refused must not be in the set
  afterwards. **A warning plus success is the worst of the three answers**: the caller cannot see it,
  cannot retry, and the fault presents as a service that is merely slow.

- [x] **`MAX_SETS_PER_OBJECT` must be enforced where the registration is made, not where the wake
  is delivered.** `wake_object` copies at most four set koids into a stack array and warns that the
  rest will not be woken; `register_set_observer` never counts what is already registered for that
  member. Five sets may therefore each add the same channel and each be told it worked, and the
  fifth waits forever. The limit exists for a good reason - it is what keeps the forwarding off the
  heap, and the allocation it replaced was measured at 433,645 ns against a 188,821 ns baseline - so
  the fix is to refuse the fifth `add`, not to raise the ceiling.

  A deterministic regression test, and a cheap one: add one channel to five sets, assert the fifth
  is refused, assert a wake reaches all four that were admitted.

- [x] **A `wait_registrations` counter on `ResourceAccount`, charged where the registration is
  made.** `try_charge` in `WaitSet::add`, uncharge in `remove` and in `Drop`, and a default limit
  chosen the way the others were. This is the item mis-ticked in "What is wanted" above; it is
  listed here because it is where the work is.

- [x] **Answer with the koid, then migrate the caller.** All five steps are done. The third attempt
  is the one that paid; the numbers and what it cost are at the end of this file. The shape, in
  order:

  1. `sys_waitset_wait` returns the ready member's koid instead of its index. Koids come from a
     counter that starts at 1 and only increases, so one always fits in the `i64` a syscall returns
     with negatives reserved for errors - worth saying because the index it replaces could not have
     collided with an error code either, and the property should not be assumed a second time.
  2. `sys_waitset_add` returns the added member's koid instead of `0`, so a caller learns it at the
     moment it joins rather than paying `SYS_OBJECT_INFO_GET` per member to find out. Userspace CAN
     ask - `ObjectInfo` carries `koid` - and should not have to.
  3. Update the three kernel tests in `test_suites/kernel.rs`
     (`a_wait_set_registers_its_members_once_and_wakes_on_any_of_them`,
     `..._member_whose_peer_closes_reports_rather_than_vanishing`, `..._has_a_ceiling_and_says_so`)
     and `rt::waitset_wait`'s signature. There are no other callers, which is the whole reason this
     is being done now.
  4. Migrate StorageService's serve loop: add on join, remove on departure, and map the returned koid
     to a client through the table it already keeps. No per-pass reconcile - that is the thing the
     measurement killed.
  5. Measure against the three recorded figures below (4 / 32 / 62 clients) and write the result
     here, INCLUDING if it is another regression. Two attempts have been backed out on measurement;
     a third that is not measured would be worse than either.

  *(Two earlier attempts, both backed out; the second one measured. See below.)* StorageService's serve loop is the caller the measurement came from,
  and moving it over is a separate change with its own test - the point of which is the measurement
  that motivated this milestone: a service with hundreds of clients answering at the same speed as
  one with three. Until that exists, this is a mechanism with tests rather than a fix with evidence.

  **Attempted and BACKED OUT, 2026-08-08.** Written and reverted the same hour, and what it cost is
  worth more than the change would have been.

  The design was right and is worth keeping for the next attempt: a `WaitMembers` struct owning both
  the kernel set and this service's picture of its membership, because `waitset_wait` answers with an
  INDEX and the kernel removes a member by retaining the others - so the index only means anything to
  a caller whose own list is ordered and edited the same way. Putting that correspondence in one
  place, where nothing else adds and nothing else removes, is what stops it drifting silently.

  What happened is that the migrated service HUNG the storage suite, at
  `the_memory_volumes_bound_and_answer_streams` - the test carrying the client-table ceiling and the
  two flood cases. It was backed out rather than chased, for a reason that is about this session
  rather than about the code: three regressions had already been self-inflicted that day (a
  per-frame shootdown that stopped riscv64 finishing, a second lock on the scheduler's hottest path
  that turned a microsecond cross-core wake into seven milliseconds, and an arch API change that only
  broke on the two architectures the local build was not covering). A fourth, guessed at rather than
  measured, in the loop every service in the system depends on, at that hour, is how a subtle one
  gets committed.

  What the next attempt needs FIRST, before touching the loop:

  - **A measurement.** DONE, and it says what the milestone claimed:

    | clients | ns per round trip |
    |---|---|
    | 4 | 85,794 |
    | 32 | 135,483 |
    | 62 | 188,821 |

    About 1,780 ns per additional client, straight-line - answering one client at 62 takes more than
    twice what it takes at 4, and none of those other clients asked for anything. That is the cost
    `MAX_CLIENTS = 64` was chosen around, now a number rather than a feeling.

    `a_services_round_trip_against_its_client_count`, tagged `Stress` so it stays out of the default
    suite, and it PRINTS rather than asserts: a wall-clock figure on an emulated guest is not
    something to fail a build over, and this round has already retired three tests that asserted
    numbers they did not own. The point is that a change to the loop can be judged against these
    three lines instead of guessed at.
  - **The suspect named.** `OBSERVER_COUNT` is zero today, so `wake_object` skips the observer bucket
    entirely - and the moment a service uses a set it is not zero any more, and every wake in the
    system takes a second per-bucket lock. That is the same shape as the seven-millisecond regression
    above, and it is the first thing to measure rather than the first thing to assume.
  - **The membership sync reconsidered.** The reverted version rebuilt a `wanted` list every pass and
    compared it against the set's, which is quadratic in the client count in userspace - cheap in
    absolute terms and precisely the wrong direction for a change whose entire purpose is to remove a
    per-pass per-client cost. Membership should be edited where it CHANGES (a client joins, one is
    dropped, a stream begins or ends), not reconciled on every pass.

  **Attempted a SECOND time and backed out again, same night - and this time it was measured rather
  than guessed at, which is the whole difference.** It did not hang. It was just slower, and the
  measurement said so immediately:

  | clients | `wait_any` (baseline) | through the set |
  |---|---|---|
  | 4 | 85,794 | 92,288 |
  | 32 | 135,483 | 216,024 |
  | 62 | 188,821 | 433,645 |

  Two and a third times worse at sixty-two clients, on the change whose entire purpose was to be
  cheaper there. Four experiments then found out why, each eliminating a candidate:

  1. **`WaitSet::snapshot` allocated.** It returned a fresh `Vec` of `Arc`s - one heap allocation and
     sixty-two atomic increments, twice per pass, on the path being sold as the cheap one. Replaced
     with `with_members`, which runs the readiness scan and the earliest-deadline scan under one lock
     and allocates nothing. 433,645 -> 363,245 ns. Better, still far worse than the baseline. **Kept**
     - it is a straight improvement to the mechanism whatever calls it.
  2. **The userspace reconcile allocated.** `sync` collected the departed members into a `Vec` before
     removing them; `retain` with the syscall inside the predicate does it in place. 363,245 ->
     357,045. Barely moved. **Kept**, same reason.
  3. **The set populated but NOT waited on.** The decisive one. Membership synced every pass, waiting
     still through `wait_any`: **425,281 ns**, worse than either. So the cost is not the waiting
     mechanism at all - it is on the path that runs whether or not anything waits on the set.
  4. **`sync` disabled entirely, set created and empty.** 201,940 ns - the baseline back, within the
     noise of an emulated guest.

  So it is the reconcile, and the third bullet above had already named it as a design smell without
  suspecting it of being the whole cost. What makes it the whole cost is the build: services are
  built unoptimised, and `wanted.contains` over sixty-two members for each of sixty-two members is
  3,844 comparisons per pass with nothing folded away. The kernel-side theory was fine. The
  userspace bookkeeping around it was quadratic, and quadratic in a debug build is not a rounding
  error.

  **What was blocking the third attempt** was one design decision. `waitset_wait` answers with an
  INDEX into the kernel's membership, so the caller must keep a list in exactly the kernel's order -
  and the service's client table uses `swap_remove`, which permutes. That mismatch is what forced a
  reconcile instead of an edit.

  **DECIDED, 2026-08-08: the kernel answers with the member's KOID, not its index.** The caller then
  needs no ordered mirror at all and maps the koid to a client however it already indexes them. The
  alternative - editing membership at the six places it changes, and keeping the mirror ordered by
  construction - needs no kernel change and was rejected: a missed call site is a silently stale set
  that serves the WRONG client, which is a correctness bug wearing a performance change's clothes.

  It is cheap to decide now and expensive later, because the syscall has exactly one wrapper
  (`rt::waitset_wait`) and no userspace caller. The next one to arrive would have to be changed too.

  The mechanism, its tests, and the two allocation fixes are in the tree and paid for. What is not
  done is the caller, and it now has numbers to be judged against instead of a hope.



## The three blockers, built

**`register_set_observer` returns `Result<(), ObserveError>`** and `WaitSet::add` rolls back on
failure: the `members.push` is undone, the registration quota is given back, and the caller gets
`ERR_RESOURCE_EXHAUSTED`. Success now means the member will be woken, which is what it was supposed
to mean all along - the old warning-plus-`Ok` was the worst of the three defensible answers, because
the caller could not see it, could not retry, and the fault presented as a service that was merely
slow.

**`MAX_SETS_PER_OBJECT` is enforced at the registration**, by counting what is already registered
for that member, as well as where the wake is delivered. Five sets could each add one channel and
each be told it worked; the fifth then waited forever. Raising the ceiling was never the answer -
four is what keeps the wake forwarding on the stack, and the heap allocation it replaced measured
433,645 ns against a 188,821 ns baseline.

**`ResourceAccount` has `wait_registrations`**, defaulting to 1024, charged in `WaitSet::add` and
given back in `remove` and in `Drop`. A `WaitSet` created through the syscall carries the Domain
that pays for it; one created inside the kernel carries none, like everything else the kernel makes
for itself.

Two tests, both in the guest suite and both watched to fail:
`a_set_that_was_told_it_joined_is_a_set_that_will_be_woken` - which also asserts that all four
admitted sets ARE woken, so the refusal is a limit rather than an off-by-one - and
`a_wait_set_registration_is_charged_to_the_domain_that_holds_it`, which sets the ceiling to four and
checks both that the fifth is refused and that dropping the set returns every registration.

The KOID-based API and the StorageService migration below are unchanged and still open: they are a
design decision that has been made and a measurement that has to be taken, not a defect.


## The KOID change, built (steps 1-3)

`sys_waitset_wait` answers the ready member's koid; `sys_waitset_add` answers the koid the member
joined under, so a caller learns it where it joins rather than paying `SYS_OBJECT_INFO_GET` per
member. `rt::waitset_wait` and `rt::waitset_add` say so, and the four kernel tests that asserted an
index now assert the koid the add gave them.

Cheap now and expensive later, exactly as the decision said: the syscall has one wrapper and no
userspace caller, so this is a change to five call sites, all of them tests.

## Why the migration is not in this change

Steps 4 and 5 - StorageService's serve loop, and the measurement against 4 / 32 / 62 clients - are
deliberately left, and the reason is written above in this file by the two attempts that were backed
out. The second one was measured and was **2.3x worse**; the first HUNG the storage suite and was
reverted rather than chased, for a reason stated at the time:

> three regressions had already been self-inflicted that day [...] A fourth, guessed at rather than
> measured, in the loop every service in the system depends on, at that hour, is how a subtle one
> gets committed.

That argument applies unchanged to an unattended session. The blocker the migration was waiting on
is now gone - the caller no longer needs a mirror of the kernel's ordering - so the next attempt has
what it needs, and what it needs after that is somebody watching the three numbers.


## The third attempt, and it paid

| clients | `wait_any` (2026-08-08) | `wait_any` (2026-08-09, same host as below) | through the set |
|---|---|---|---|
| 4 | 85,794 | 56,974 | **54,016** |
| 32 | 135,483 | 95,844 | **64,241** |
| 62 | 188,821 | 133,811 | **84,590** |

Read the last two columns, not the first: the 2026-08-08 figures were taken on a differently loaded
host and every path is about 30% faster today, which says nothing about the change. Measured back to
back on one host, the same day, the same binary except for the loop:

**The slope fell from 1,325 ns per additional client to 526.** At sixty-two clients a round trip
costs 84,590 ns instead of 133,811 - **37% off** - and what remains is work the loop does for
itself rather than tax the kernel charges for the other sixty-one connections nobody asked about.

The blocker was gone before this started: the kernel answers with a koid, so the caller keeps no
mirror of the kernel's ordering and the quadratic userspace reconcile that sank the second attempt
has nothing to reconcile.

### It hung at the same test as the first attempt, and this time the cause is known

`the_memory_volumes_bound_and_answer_streams` - the exact test M0147 records the first attempt
hanging at, reverted then without a diagnosis. It hung here too.

**A closed member never leaves the set.** `waitset_remove` names a member by the handle it joined
under, so closing that handle first hands the removal a dead handle and the member stays. A channel
whose peer has closed is permanently READABLE, so the set wakes, no client owns that koid, the loop
continues - and wakes again immediately. A livelock, which is why it presents as a suite that never
finishes rather than one that fails.

It was found by instrumenting the one branch it must reach: a wake for a koid no member owns.
**12,917 of them in three minutes.** Guessing had already produced one wrong answer before that.

Two places closed a handle before removing it. The client paths were reordered. The STREAM could not
be fixed by ordering, because its handle is closed inside `abandon_pending` and `finish_stream` -
two functions the loop calls from six places - while the per-pass reconcile only notices the stream
is gone afterwards, when the handle is already dead. So leaving the set became part of closing it:
`leave_stream` does both, in that order, and is the only place either happens.

**Joining can be noticed late; leaving cannot.** That is the rule the reconcile violated, and it is
why the reconcile now only ever adds.

### Membership has one owner per kind

`admit_client` and `release_client` are the only places a client joins or leaves - table and set
together, because a client the set does not know about is never served and a member with no table
entry is a wake nobody can answer. `leave_stream` is the same for the stream. That is M0147's own
prescription from the first attempt ("putting that correspondence in one place, where nothing else
adds and nothing else removes, is what stops it drifting silently"), and it earned its keep: the
livelock was a drift the compiler could not see.


## `MAX_CLIENTS`, chosen on its merits

It is `MAX_WAIT_SET_MEMBERS - 2` - **254** - derived rather than picked, and the two are the admin
channel and the write stream. `MAX_WAIT_SET_MEMBERS` moved into `abi` so the service reads the
kernel's stated limit instead of duplicating it.

Measured at the new ceiling before setting it there, because extrapolating a slope is not measuring:

| clients | before M0147 | after |
|---|---|---|
| 4 | 56,974 | 46,849 |
| 32 | 95,844 | 64,715 |
| 62 | 133,811 | 85,226 |
| 254 | *unreachable - the old ceiling was 64* | **209,481** |

**At 254 clients the service now costs about what it cost at 62 before.** Four times the ceiling for
the same responsiveness, which is the trade this milestone was for, in numbers rather than in hope.

What the ceiling MEANS also changed. Sixty-four was a performance number: the point where the loop
was still brisk. 254 is a structural one - a client is a member of the set, and the set holds what
it holds. Nothing in this system opens anywhere near either figure (a handful of services and one
per directory grant), so the ceiling has only ever been a bound on what a connection flood can do,
and it is now bounded by the mechanism rather than by a measurement that will drift.

The slope is halved, not gone: 526 ns per additional client between 4 and 62, 647 between 62 and
254. What remains is a scan - the kernel's `waitset_wait` walks the membership for a ready member
and the earliest deadline, and the service walks its client table to map the koid back. Both are
O(members) per pass. Removing that would need the set to keep a ready LIST rather than scan, which
is a different milestone and worth costing before assuming it pays.
