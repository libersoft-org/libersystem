# M0147 - A wait set the kernel keeps

Every service in this system is one loop around `wait_any`, and `wait_any` takes a fresh set of
handles on every call. The kernel therefore registers a waiter on every channel in that set, waits,
and unregisters all of them again - once per pass, for as long as the service runs. The cost of one
pass is linear in how many things the service is listening to, and nothing the service does can make
it otherwise.

This was measured rather than suspected. While bounding StorageService's replies (M0139) a test was
written to connect until the service refused, and finding a client ceiling the test could actually
REACH took several attempts: forty-eight connections cost nothing measurable, and a ceiling of 256
could not be reached inside fifteen minutes of emulated time. `MAX_CLIENTS` was set to 64 because
that is where the service is still brisk - a number chosen around the defect rather than on its
merits.

A service that slows down in proportion to how many peers are talking to it is bounded in the wrong
sense: the ceiling limits the damage a connection flood does, and does not remove it. Every service
that grows a client table will meet the same wall, and each will pick its own number for the same
wrong reason.

## What this is not

Not a defect in StorageService, and not fixable there. The loop already allocates its wait set once
and clears it rather than rebuilding it - that copy is a memcpy of at most 66 words and costs
nothing. What costs is the registration on the far side of the syscall.

## What is wanted

- [x] **A wait set as an OBJECT, registered once and waited on many times.** A service creates one,
  adds the handles it cares about, and waits on that object - so adding a client costs one
  registration rather than one per pass forever after. The shape every event-notification interface
  converges on, for the same reason.

- [x] **A registration lifetime that is defined where it is awkward.** What happens when a
  registered channel is closed - by this process, or by the peer - is the question that decides
  whether the interface is usable. Silent removal, an explicit revocation event, and a stale
  registration that reports once are all defensible; leaving it undefined is not, and a stale
  registration that reports FOREVER is the failure mode that makes such interfaces infamous.

- [x] **A per-Domain bound on registrations.** The set is kernel memory a userspace caller decides
  the size of, which is the shape of every quota in this kernel and needs the same treatment.

- [x] **Tests for the parts that are not the happy path.** A registered channel closed by its peer
  while the waiter sleeps; a channel registered twice; a set outliving the handles in it; a set
  waited on by two threads; and the measurement that started this - a service with hundreds of
  clients answering at the same speed as one with three.

- [ ] **StorageService's `MAX_CLIENTS` reconsidered afterwards.** It is 64 because of this defect,
  with the measurement recorded beside it in the source. Once a pass no longer costs what it costs
  today, the number should be chosen on what the system actually needs and what a handle table can
  hold - and the comment explaining the old reason should go with it.

## Where this came from

M0139's fourth audit round, as the one item that could not be answered inside the service. The
account of the measurement is in `M0139.md` under "Reopened: a fourth audit"; this file exists so

## What was built

`WaitSet` is an object like any other: created by a syscall, held by a handle, counted against the
Domain's handle quota, and destroyed when the last reference goes.

The mechanism is one new kind of entry in the scheduler's wait buckets. A `BucketWaiter` is
registered when a thread parks and removed when it wakes; a `SetObserver` is registered when a member
JOINS a set and removed when it leaves. `wake_object` collects both: the threads it wakes and
removes as before, and the sets it forwards to without removing. Waking a set wakes whatever is
parked on the set's own koid, which is one registration per pass rather than one per member per pass.

One level, never a chain: a set may not contain a set, and `WaitSet::add` refuses it. A wake would
otherwise have to chase a graph, and nothing a flat set cannot serve wants that.

### The registration lifetime, decided

The set holds a REFERENCE to each member, so a member does not vanish because the handle that
introduced it was closed. Of the three defensible answers - silent removal, a revocation event, or a
stale registration that keeps reporting - this is the one that cannot lose an edge: a channel whose
peer closes becomes ready, the waiter is told, and what to do about it is a decision made with the
whole picture rather than one the kernel makes by dropping the member at the moment it became
interesting. Leaving is explicit, through `remove`, and there is a test that says so.

### Bounds

`MAX_WAIT_SET_MEMBERS` is 256, matching `MAX_WAIT_HANDLES` - a set is the persistent form of the
same question. A ceiling first, then `try_reserve`, then a refusal: the same three steps every other
caller-sized allocation in this kernel takes.

## What is still open

- [ ] **Nothing uses it yet.** *(Two attempts, both backed out; the second one measured. See below.)* StorageService's serve loop is the caller the measurement came from,
  and moving it over is a separate change with its own test - the point of which is the measurement
  that motivated this milestone: a service with hundreds of clients answering at the same speed as
  one with three. Until that exists, this is a mechanism with tests rather than a fix with evidence.

  **Attempted and BACKED OUT, 2026-08-08.** Written and reverted the same hour, and what it cost is
  worth more than the change would have been.

  The design was right and is worth keeping for the next attempt: a `WaitMembers` struct owning both
  the kernel set and this service's picture of its membership, because `waitset_wait` answers with an
  INDEX and the kernel removes a member by retaining the others - so the index only means anything to
  a caller whose own list is ordered and edited the same way. Putting that correspondence in one
  place, where nothing else adds and nothing else removes, is what stops it drifting silently.

  What happened is that the migrated service HUNG the storage suite, at
  `the_memory_volumes_bound_and_answer_streams` - the test carrying the client-table ceiling and the
  two flood cases. It was backed out rather than chased, for a reason that is about this session
  rather than about the code: three regressions had already been self-inflicted that day (a
  per-frame shootdown that stopped riscv64 finishing, a second lock on the scheduler's hottest path
  that turned a microsecond cross-core wake into seven milliseconds, and an arch API change that only
  broke on the two architectures the local build was not covering). A fourth, guessed at rather than
  measured, in the loop every service in the system depends on, at that hour, is how a subtle one
  gets committed.

  What the next attempt needs FIRST, before touching the loop:

  - **A measurement.** DONE, and it says what the milestone claimed:

    | clients | ns per round trip |
    |---|---|
    | 4 | 85,794 |
    | 32 | 135,483 |
    | 62 | 188,821 |

    About 1,780 ns per additional client, straight-line - answering one client at 62 takes more than
    twice what it takes at 4, and none of those other clients asked for anything. That is the cost
    `MAX_CLIENTS = 64` was chosen around, now a number rather than a feeling.

    `a_services_round_trip_against_its_client_count`, tagged `Stress` so it stays out of the default
    suite, and it PRINTS rather than asserts: a wall-clock figure on an emulated guest is not
    something to fail a build over, and this round has already retired three tests that asserted
    numbers they did not own. The point is that a change to the loop can be judged against these
    three lines instead of guessed at.
  - **The suspect named.** `OBSERVER_COUNT` is zero today, so `wake_object` skips the observer bucket
    entirely - and the moment a service uses a set it is not zero any more, and every wake in the
    system takes a second per-bucket lock. That is the same shape as the seven-millisecond regression
    above, and it is the first thing to measure rather than the first thing to assume.
  - **The membership sync reconsidered.** The reverted version rebuilt a `wanted` list every pass and
    compared it against the set's, which is quadratic in the client count in userspace - cheap in
    absolute terms and precisely the wrong direction for a change whose entire purpose is to remove a
    per-pass per-client cost. Membership should be edited where it CHANGES (a client joins, one is
    dropped, a stream begins or ends), not reconciled on every pass.

  **Attempted a SECOND time and backed out again, same night - and this time it was measured rather
  than guessed at, which is the whole difference.** It did not hang. It was just slower, and the
  measurement said so immediately:

  | clients | `wait_any` (baseline) | through the set |
  |---|---|---|
  | 4 | 85,794 | 92,288 |
  | 32 | 135,483 | 216,024 |
  | 62 | 188,821 | 433,645 |

  Two and a third times worse at sixty-two clients, on the change whose entire purpose was to be
  cheaper there. Four experiments then found out why, each eliminating a candidate:

  1. **`WaitSet::snapshot` allocated.** It returned a fresh `Vec` of `Arc`s - one heap allocation and
     sixty-two atomic increments, twice per pass, on the path being sold as the cheap one. Replaced
     with `with_members`, which runs the readiness scan and the earliest-deadline scan under one lock
     and allocates nothing. 433,645 -> 363,245 ns. Better, still far worse than the baseline. **Kept**
     - it is a straight improvement to the mechanism whatever calls it.
  2. **The userspace reconcile allocated.** `sync` collected the departed members into a `Vec` before
     removing them; `retain` with the syscall inside the predicate does it in place. 363,245 ->
     357,045. Barely moved. **Kept**, same reason.
  3. **The set populated but NOT waited on.** The decisive one. Membership synced every pass, waiting
     still through `wait_any`: **425,281 ns**, worse than either. So the cost is not the waiting
     mechanism at all - it is on the path that runs whether or not anything waits on the set.
  4. **`sync` disabled entirely, set created and empty.** 201,940 ns - the baseline back, within the
     noise of an emulated guest.

  So it is the reconcile, and the third bullet above had already named it as a design smell without
  suspecting it of being the whole cost. What makes it the whole cost is the build: services are
  built unoptimised, and `wanted.contains` over sixty-two members for each of sixty-two members is
  3,844 comparisons per pass with nothing folded away. The kernel-side theory was fine. The
  userspace bookkeeping around it was quadratic, and quadratic in a debug build is not a rounding
  error.

  **What is genuinely blocking the third attempt** is one design decision, and it is worth daylight
  rather than another 3am pass. `waitset_wait` answers with an INDEX into the kernel's membership, so
  the caller must keep a list in exactly the kernel's order - and the service's client table uses
  `swap_remove`, which permutes. That mismatch is what forced a reconcile instead of an edit. Two
  ways out:

  - **Answer with the member's koid instead of its index**, so the caller needs no ordered mirror at
    all and can map koid to client however it already indexes them. This is the clean one; it changes
    the syscall's contract, which is cheap now and expensive later.
  - **Edit membership at the six places it changes** (admit, drop-stalled, peer-closed, admin lost,
    stream begun, stream ended) and keep the mirror ordered by construction. No kernel change, but a
    missed call site is a silently stale set that serves the WRONG client - a correctness bug wearing
    a performance change's clothes, which is the argument for the first option.

  The mechanism, its tests, and the two allocation fixes are in the tree and paid for. What is not
  done is the caller, and it now has numbers to be judged against instead of a hope.

- [ ] **`MAX_CLIENTS` reconsidered afterwards.** It is 64 because of the defect this milestone
  removes, with the measurement recorded beside it in the source. Once a pass no longer costs what
  it costs today the number should be chosen on what the system needs, and the comment explaining
  the old reason should go with it.
