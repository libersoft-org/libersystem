# P02M0204 - Restart policy for services and drivers, and `restartctl` to set and show it

Status: PLANNED (2026-10-14) - the owner's decision and his agreement with this plan are recorded below; nothing is
implemented yet, by his instruction ("zatim neimplementuj").

THE OWNER'S DECISION (2026-10-14). The proposal was one rule for a failed start and a crash, permanent failures not
retried, and a fixed "fast, then slow for ever" schedule. The owner agreed with all of it but the fixed schedule:
"it seems nonsense to try fast and then slow and for ever... make a tool with which this can be set: how many times
to try / for ever, how fast and so on. The tool sets it and also shows the current settings - human-readable, and
with `--json`."

WHAT IS WRONG TODAY (read from the tree on 2026-10-14):
  - A SERVICE WHOSE START FAILS IS NEVER TRIED AGAIN. ServiceManager prints `FAILED to start` and its reason, and the
    services waiting on it print `never started - waiting for`; nothing asks again (P02M0099 names the gap).
  - A CRASHED SERVICE IS RESTARTED AT MOST `service.restart-budget` TIMES (default 3) PER BOOT. The count never goes
    back down: a service that crashes once a week is dead from the third week until a reboot.
  - THE BACK-OFF IS A `sleep_ticks` INSIDE THE SUPERVISOR (100, 200, 300 ms): while it waits, ServiceManager answers
    no other crash, no `stop`, no shutdown.
  - THE POLICY IS READ ONCE PER BOOT from ConfigService, has one value for every service, and nothing shows it.
  - DRIVERS (DeviceManager) are better: three attempts per incident with a 100/200 ms back-off inside the incident's
    time budget, then `failed`, and an operator `retry`. They have no configurable policy either.
  - `escalate` services are not restarted at all - not a policy but a limit: their clients hold the channels they
    were handed at bring-up, and a replacement would leave those dead. Only `transparent` services can be restarted.

THE RULES THE POLICY WORKS INSIDE - fixed, not settable:
  - A FAILED START IS A FAILURE LIKE A CRASH: the same policy, the same counter.
  - A PERMANENT FAILURE IS NEVER RETRIED AUTOMATICALLY: an artifact missing or refused (signature, manifest), a
    configuration the service rejects, a role or grant that cannot be minted. The service is `failed` with the reason,
    and is tried again when its input changes - a new package generation, a configuration change - or when an
    operator starts it. Retrying it would only spend time and fill the log.
  - Everything else is transient (a crash, a missed handshake or heartbeat, exhausted resources, a dependency that is
    not there yet) and is retried under the policy.
  - Waiting between attempts is a deadline in the supervisor's event loop, never a sleep.
  - The log says the first failure, and then only when the count doubles - as the heartbeat already does.
  - A service that is not restartable (`escalate`) shows as such, with the reason, and takes no policy; a driver
    binding that holds `vol://system` takes none either (P02M0203).

THE SETTINGS - one set of parameters, a default for services, a default for drivers, and an override for any one
service or driver by name:
  - `attempts`     how many automatic restarts in a row: a number, or `unlimited`.
  - `delay`        the wait before the first restart.
  - `backoff`      what the wait is multiplied by after each failed attempt (`1` keeps it constant).
  - `max-delay`    the longest the wait may grow to.
  - `reset-after`  how long a service must run without failing before its count starts again from zero - so
                   `attempts 3` means three in a row, not three per boot.
  - `then`         what happens when the attempts are spent: `stop` (leave it failed until an operator or a change
                   starts it) or `reboot` (for a service the system cannot run without).
  THE DEFAULTS, AGREED BY THE OWNER WITH THE PLAN (2026-10-14, "OK, souhlasim"): services - attempts 5, delay 1 s,
  backoff 2, max-delay 1 min, reset-after 10 min, then stop; drivers - attempts 3, delay 100 ms, backoff 2, max-delay
  1 s, reset-after 10 min, then stop (today's behaviour, now settable). Which services get `then reboot` by default
  is named when the item starts (the candidates: StorageService, PermissionManager, ConfigService) - all of them can
  be changed with `restartctl` anyway.

THE TOOL, `restartctl`:
  - `restartctl` / `restartctl show [NAME]` - the defaults and every override, and for each service and driver its
    effective policy, its state, the attempts spent, the reason of the last failure and when the next attempt is due.
    Human-readable by default; `--json` prints the same as one JSON document.
  - `restartctl set [--service NAME | --driver NAME] PARAMETER VALUE ...` - without a name, the default for services
    or drivers (`--services` / `--drivers`); with one, an override. Values are checked before anything is stored, and a
    refusal says which value and why.
  - `restartctl reset [NAME]` - remove an override (or the changed defaults), back to what is shipped.
  - Settings are stored in ConfigService on the system volume, survive a reboot, and apply at once, without a reboot.
  - Reading is open to anyone who may list services; changing takes an operator grant (`restart-policy`), minted by
    PermissionManager like the other operator roots (`powerctl`'s `processor-power`).

- [ ] Host-tested policy core (a `driver_binding`-style library): the schedule (delay, backoff, cap), `unlimited`,
  the count reset after `reset-after`, `then`, and the permanent/transient classification of every failure cause the
  two supervisors report today.
- [ ] ServiceManager: a failed start enters the policy; back-off as an event-loop deadline; the policy read from
  ConfigService and re-read on change; per-service overrides; `then reboot` through the existing recovery path.
- [ ] DeviceManager: the same policy for driver bindings, inside the boot window's own budget during bring-up.
- [ ] The wire: a `restart-policy` interface on ServiceManager (read and set), the operator role in the manifest and
  PermissionManager, and a read view over driver bindings from DeviceManager.
- [ ] `restartctl`, with `--json`.
- [ ] THE ORACLE, in QEMU (x86_64 first, the ports at the end of the job), with development fixtures:
  a service that fails its first N starts and then comes up (it comes up, after the configured delays);
  a service that crashes in a loop (the schedule measured on the guest's clock, `attempts` respected, `unlimited`
  never giving up, the log rate-limited); a service whose start fails permanently (never retried, and started again
  after its configuration changes); `reset-after` (a crash after a long healthy run starts from attempt one); a driver
  fixture failing its bind the same ways; `restartctl show --json` parsed by the gate; `restartctl set` refused
  without the grant; the settings surviving a reboot and applying without one.
