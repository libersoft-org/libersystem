# P02M0200 - Hardware watchdogs: a provider contract, the emulated timers, WDAT, and who keeps them fed

Status: OPEN. Created 2026-09-25 under the owner's approval of P02M0196 - "yes, do all of it; where a
milestone is missing, create it". NOTHING HERE IS STARTED: the owner asked for plans only until he says
otherwise, and no part starts without its own written plan.

WHAT IT IS, AND WHAT IT IS NOT. ServiceManager's watchdog is SOFTWARE: in a test boot it proves a heartbeat
on one managed canary and restarts it, and its standing loop runs no heartbeat at all. A HARDWARE watchdog is
a timer outside the processor that resets the machine unless it is told, in time, that the system is alive -
so it catches what software cannot: a kernel that stopped scheduling, a supervisor that deadlocked, a machine
nobody is sitting at. P02M0099 lists the ACPI WDAT watchdog with NO destination ("a hardware timer that resets
the machine, which is a different thing wearing the same word"). This milestone is that destination, and the
drivers that feed it.

WHAT QEMU OFFERS, checked on this machine (10.0.11, `-device help` and `-help`) and in QEMU 10.0's sources:
  - `i6300esb` (8086:25ab, class 0x0880 "other system peripheral"), a PCI device in the x86_64, aarch64 and
    riscv64 builds. It is ARMED AND STOPPED ONLY THROUGH CONFIGURATION REGISTERS: 0x60 (reboot enable, clock
    scale, stage-one interrupt type) answered only as a WORD, and 0x68 (enable, lock, free-run) answered only as
    a BYTE - a dword access to either falls through to the generic handler and does nothing. Its 16-byte
    memory BAR 0 holds the two stage preloads and the reload register behind an unlock sequence. It runs two
    stages and acts at the end of the second; the stage-one interrupt is not emulated. A "previous reboot" flag
    (BAR 0 + 0xC, bit 9) survives the reset it caused.
  - The TCO timer inside q35's ICH9 LPC bridge (8086:2918; `enable_tco` is on by default): 32 bytes at the
    PM base (LPC configuration 0x40) + 0x60, a 0.6 s tick and a 10-bit count. It resets the machine only on
    its SECOND expiry, and only while the `noreboot` strap is off and GCS's No-Reboot bit is clear - GCS being
    a dword at the root-complex base (LPC configuration 0xF0) + 0x3410, in MEMORY. QEMU's v10.0.11 source
    resets GCS to 0x20, No-Reboot SET (later upstream sources clear it unless the strap is set), so a driver
    must clear it. OVMF programs the PM base (0x600) and enables the root-complex base (0xFED1C000). The
    second-timeout status bit survives the reset.
  - `ib700`, an ISA card (EXCLUDES).
  - The simulated BMC (`ipmi-bmc-sim`, P02M0201) has a watchdog that SURVIVES the host's reset (the device has
    no reset handler) and resets the machine as a CHASSIS reset - not a QEMU watchdog action.
  - `-action watchdog=reset|shutdown|poweroff|inject-nmi|pause|debug|none` (default `reset`; `-watchdog-action`
    is the older spelling) chooses what an expiry of the first two devices does. QMP's `WATCHDOG` event reaches
    only a client connected at that moment; `pause` stops the guest with the run state `watchdog`, which
    `query-status` reports until `cont` - a DURABLE record of an expiry.
  - QEMU emits no WDAT, but WDAT is a static table, so one supplied with `-acpitable` can describe the TCO
    registers QEMU does emulate.

## P02M0200a - The contract, and who keeps it fed

- [ ] A `watchdog` PROVIDER KIND in `liber:device@1` (a `provider-kind` value and a `watchdog` interface,
  additive, version 1), admitting ONE consumer and PUBLISHED UNDER THE DEVICE'S NAME - `wdat`, `tco`,
  `i6300esb` or `bmc`, as the publication name the catalogue already carries - which is what the policy key
  `watchdog.device` (below) names. The provider states: the timeout range and granularity the device
  supports; whether it can be disarmed (a locked timer cannot); whether it SURVIVES the platform's reset (the
  BMC's does, the chipset timers do not); whether it stops counting in suspend to idle and in S3; whether the
  timer was running when the driver bound; and whether the LAST reset was the watchdog's - read and cleared
  by the driver at bind, and a line in the system graph, because a machine that reset itself in the night
  should say so in the morning. Operations: arm with a timeout (answering the effective one; the count starts
  at the arm, so an arm is also a pet), pet, disarm (`unsupported` where the device cannot). The driver pets
  ONLY when its consumer asks - never on a timer of its own, except the bounded takeover bridge below - and
  does NOT disarm when its consumer's channel closes. Only the driver binding that holds the device publishes
  the provider, as every catalogue publication is.
- [ ] THE TIMEOUT IS ONE NUMBER: the time from the last pet to the reset. Each driver divides it across its
  device's stages: the `i6300esb` into two equal preloads (a stage unit is 32768 PCI clocks of 30 ns, about
  0.98 ms, in 20 bits); the TCO into a count of T / 1.2 s, because both expiries run the same count (2 to
  1023, so 2.4 s to 1227.6 s); WDAT as the table's timer period times its count (the table describes the time
  to its action, so a WDAT over the TCO states 1200 ms per count); the BMC as one countdown in 100 ms units. A
  request is rounded DOWN to the device's granularity and refused below its minimum. There is no pre-timeout
  warning in the contract (EXCLUDES).
- [ ] WHO KEEPS IT FED - ONE LIVENESS EXCHANGE. One watchdog service (`watchdog_service`, the kind's one
  consumer) pets each period P ONLY after ServiceManager has answered a liveness request within a deadline D.
  The request is a one-operation interface `supervisor-liveness` (`alive`, answering a sequence number) in
  `liber:observability@1` beside `supervisor`, served by ServiceManager from its STANDING supervise loop's
  wait set on a channel the plan delivers to the watchdog service as a role. An answer proves that the kernel
  schedules and delivers messages, that ServiceManager's standing loop is not deadlocked, and - because the
  watchdog service asked - that its own loop runs; no answer within D skips that pet, and the hardware decides
  after T. THE FIRST ANSWER STARTS IT: the service arms, or takes a running timer over, at its FIRST `alive`
  answered within D, never when it starts. ServiceManager enters its standing loop only after bring-up - every
  service started, a test boot's drills run, its online report sent - which takes minutes on an emulated
  aarch64 or riscv64 guest, so a timer armed at the service's start would expire before anything answered;
  until the first answer a timer found running is its driver's (the bridge below). THE LOOP ANSWERS NO `alive`
  WHILE IT RUNS A SEQUENCE: the orderly shutdown and P02M0197's suspend transaction both run inside it, so
  each carries a step of its own for the watchdog - the shutdown notice and the sleep notice below. How the
  loop answers every other request meanwhile is P02M0197's and P02M0198d's to state, and they state it - a
  second sleep request refused as a transaction already running, a power-off ending a sleep transaction, and
  one during the shutdown answered as already under way. WHAT COUNTS IS SERVICEMANAGER ALONE: its standing
  loop runs no heartbeat on any service (the canary heartbeat is a bring-up self-test of test boots), and a
  standing heartbeat for managed services is not this milestone. SYSTEMMANAGER IS NOT IN THE CONDITION: its
  death already reboots the machine through the kernel (`resident_manager_lost`), and it serves only
  `system-power` and boot reports - an operation added to prove it responds would widen an interface whose
  point is that its client can do nothing else; a hung SystemManager shows as a power request with no answer,
  which ServiceManager already reports. T, P and D are config keys with T at least 3P, so one late round never
  resets the machine; the proposed defaults - T 60 s, P 15 s, D 5 s - are asked of the owner when the part
  starts. A development-build hook makes ServiceManager stop answering `alive` and nothing else, for the gate.
- [ ] ARMING IS POLICY: the service arms only when `watchdog.enabled` says so. DEVELOPMENT IMAGES AND TEST
  BOOTS DEFAULT TO OFF. A test boot is not a development image - `test.sh` and `test-kernel.sh` build without
  the `development` feature, and test mode refuses the development profile - yet the kernel suite brings every
  manifest service up inside its boot and runs the rest of the suite in that boot, the watchdog service and
  the watchdog drivers included, where an armed timer's expiry would end the suite as a `GUEST RESET`.
  ServiceManager already receives the boot mode; it hands it to the watchdog service as a payload role the
  plan resolves, so a relaunched instance gets it again, and the default follows it. So every harness boot but
  the watchdog cases runs unarmed, and the default of a shipping image booted as one is asked of the owner
  when the part starts (proposed: on). With the policy off the service disarms, as it attaches, a timer found
  running where the device allows it, and keeps feeding one it cannot disarm - at the configured timeout, from
  its first answered `alive` - because leaving that unfed is a reset.
- [ ] SEVERAL PROVIDERS, ONE ARMED. Every q35 boot without a WDAT publishes the TCO, so a second device is the
  ordinary case. The service takes every published `watchdog` provider, at most four (a fifth is logged and
  not opened). With the policy on it ARMS ONE, at its first answered `alive`: the device the policy key
  `watchdog.device` names or, with the key unset, the first in the order WDAT, TCO, `i6300esb`, BMC whose arm
  succeeds (a TCO whose No-Reboot stays set answers `unsupported`, and the next is tried) - the default order
  is asked of the owner when the part starts, with T, P and D. A named device that is absent or refuses the
  arm is reported, and nothing is armed in its place. Every other provider is disarmed where the device
  allows it and otherwise kept fed on the same schedule, at the configured timeout. A provider published
  later is taken the same way - armed if nothing is armed and it would have been chosen, otherwise disarmed
  or kept fed - and an armed timer is never switched for another. The log names the device armed and what
  was done with each other one. ONE PROVIDER PER DEVICE NAME: a provider published under a name the service
  already holds - two interfaces to one BMC publish two `bmc` providers for ONE timer - is left unopened and
  reported, never disarmed, because a disarm through it would stop what was armed through the other;
  P02M0201's BMC service reports such a pair and names the interface an operator may disable.
- [ ] ONCE ARMED, IT STAYS ARMED. The watchdog service is declared `restart = transparent` and is one of the
  plan-relaunchable services - every role it has is plan-resolved: a catalogue connection restricted to
  `watchdog`, its `supervisor-liveness` channel, its config client and the boot mode's payload - and its
  manifest row declares the orderly-shutdown notice and P02M0197's sleep notice. Its catalogue role takes two
  of the manifest's catalogue-client slots, as every transparent service's minting role does; if that pushes
  the demand past the bound's 32, the same change raises the bound to 64 in the system-manifest crate and in
  DeviceManager's table. ServiceManager restarts it within the ordinary budget (`service.restart-budget`,
  default 3, back-off 0.1 s times the attempt), far inside any timeout, and mints its `supervisor-liveness`
  channel again, the new end replacing the old one in the standing loop's wait set; the replacement takes the
  providers again and chooses as the first instance did, at its first answered `alive`, which the standing
  loop gives at once. When the budget is spent nobody pets and the machine resets within one timeout: a system
  that cannot keep its watchdog service alive is the case the watchdog exists for, and the graph has already
  recorded the spent budget. THE DRIVER'S DEATH is the same property one level down: the claim's release
  revokes the driver's registers and WRITES NOTHING to the timer (no disarm, No-Reboot not restored);
  DeviceManager rebinds it, and the new instance takes the running timer over at bind. A rebind that does not
  come back within the timeout resets the machine, which is the watchdog working.
- [ ] TAKEOVER AT BIND, NOT A RACE: a driver's first acts are to read and clear the last-reset record and to
  read whether the timer runs and whether it is locked. A running timer that CAN reset the machine is petted
  at once, never stopped during bind, and kept fed by the driver until its consumer's first pet (an arm is
  one) or disarm - not until the consumer attaches, because the consumer pets only after its first answered
  `alive`, after bring-up - for at most THE BRIDGE BOUND, 120 s, a constant in the driver equal to the
  proposed boot bound below, which a boot must beat from the driver's bind to its consumer's first pet.
  After it the driver stops, so a boot that never brings the watchdog service up still resets the machine;
  the provider says the timer was running. A timer that cannot reset the machine (the TCO with No-Reboot set)
  is halted instead, because counting it would only record expiries that reset nothing. The same path serves
  a timer the firmware left running and one a crashed driver left armed.
- [ ] THE ORDERLY SHUTDOWN NOTICE - owned here; P02M0201's shutdown event uses it. WHAT EXISTS:
  ServiceManager's orderly `!poweroff` / `!reboot` sends LogService `FLUSH` without waiting for it, then
  SIG_KILLs every running service in reverse-dependency order - a service's orderly stop is a kill, so NO
  SERVICE IS TOLD - and SystemManager's `reboot` and `power-off` are one `SYS_SYSTEM_POWER` call each. So a
  bounded notice step is added INSIDE THAT ONE SEQUENCE - the one the shell's verbs run and P02M0198d's
  `system-shutdown` `power-off` reaches, so there is no second shutdown path - BEFORE the reverse-dependency
  kills: ServiceManager sends `prepare(action)` (power-off or reboot) on a one-operation interface
  `shutdown-notice` in `liber:process@1`, beside `system-power` and not inside it, to every service whose
  manifest row declares the notice - on the control channel ServiceManager holds for it, the one LogService's
  `FLUSH` travels on - all at once, and waits for the answers under ONE bound
  (`service.shutdown-notice-ticks`, proposed 2 s, asked when the part starts), never past a forced power-off
  deadline already armed; a service that does not answer is killed with the rest. Immediate `system-power`
  calls - the Power key and Ctrl+Alt+Delete in the keyboard drivers, DeviceManager's power-button path,
  P02M0198d's `power-off-within` - stay notice-free by design. THE SHUTDOWN'S OWN BOUND is that notice bound
  plus the kills, and for a critical shutdown the forced power-off deadline P02M0198d arms
  (`power-off-within`, ten seconds proposed there). The watchdog service's answer, for each running timer it
  holds: for a provider reset with the platform, disarm where the device allows it, otherwise the longest
  timeout and a last pet - past the shutdown's own bound, because a hardware reset is not one of the kernel
  paths that deadline turns into a power-off; for one that SURVIVES the reset (the BMC's), disarm at
  power-off, and at reboot arm the BOOT BOUND (policy, proposed 120 s) and pet a last time, so a boot that
  hangs is still caught and the next boot's watchdog service takes the timer over.
- [ ] ACROSS A SLEEP - defined here, called by P02M0197's suspend transaction. THE SERVICE'S STEP:
  ServiceManager runs the transaction and answers no `alive` until it ends, so at the sleep ANNOUNCEMENT (the
  sleep notice its manifest row declares) the service sets the longest timeout on every running timer it
  holds and pets each once - the announcement itself comes from ServiceManager - and answers at once,
  inhibiting nothing; on the RESUME NOTICE, or at its first answered `alive` after the announcement if a sleep
  unwinds without one, it restores the configured timeout on each and pets once. It is a service, not an
  application, so the transaction never freezes it. THE DRIVER'S STEP in P02M0197's driver contract applies
  to EVERY binding that publishes a `watchdog`: each is suspended LAST and resumed FIRST. At suspend it
  disarms where the device allows it; otherwise it sets the longest timeout, pets a last time and answers an
  "awake by" bound on P02M0197's boot-time clock - that pet plus the longest timeout, less a margin - and
  P02M0197 caps the sleep's timed wake below the earliest such bound, because nothing pets a device while the
  cores are parked. A device that stops counting in the requested state answers no bound: a chipset timer
  that loses power in S3, and a WDAT with its `STOPPED` flag, which is the firmware stopping the timer in the
  ACPI sleep states - of those this system enters, S3 and deeper - and NEVER in suspend to idle, where no
  firmware runs; so for suspend to idle a WDAT that cannot be disarmed answers its bound, as Linux's
  `wdat_wdt` stops the timer for suspend to idle whatever the flag says. At RESUME a binding whose timer was
  running when its suspend step began is re-armed with the bridge bound and petted, so a resume that hangs is
  caught within it and a slow one is given the time a boot is given; a WDAT runs `SET_REBOOT` again. THE GATE
  CASE HAS BOTH HALVES, as P02M0197 states it - `running` after a suspend to idle longer than the timeout, and
  `watchdog` after a resume a test hook makes hang (P02M0200c) - and is carried by whichever of P02M0197 and
  P02M0200 lands SECOND; the first to land records that it is owed.

## P02M0200b - The devices

- [ ] DECLARED REGISTERS - A KERNEL MECHANISM, OWNED HERE. A ring-3 driver cannot reach configuration space
  and the kernel's resolver is a class-triple table with no vendor or device key, so a second kernel table
  beside `RESOURCED` is keyed by (vendor, device) - added by whichever of this milestone and P02M0201 lands
  first - and each row names the BAR to resolve, the DECLARED REGISTERS, and any chipset derivation. A
  declared register is a space, an offset, a width and a write mask; the spaces are the claimed function's
  configuration space and a chipset memory register located through a configuration register of the claimed
  function, which the kernel reaches through a mapping of its own. The registers are handed to the driver with
  the claim as one capability stamped with the claim key; a syscall reads or writes ONE declared register at
  EXACTLY its declared width - on x86 the address to 0xCF8 and an 8-, 16- or 32-bit access at 0xCFC + (offset
  & 3), on the ECAM targets an access of that width - with the write mask applied; any other offset or width
  is refused; release revokes the capability and writes nothing. The dword read-modify-write path (`update32`,
  and `read16`/`read8` cut out of a dword) is NOT used for these, because the device answers only the exact
  width. Drivers match through the manifest's existing `pci-vendor` and `pci-product` narrowing of a class
  rule. The same object carries a WDAT's system-memory registers (below).
- [ ] `i6300esb`: the row 8086:25ab resolves BAR 0 - only when no other function's BAR shares its page, checked
  against the boot scan (OVMF places the BARs on x86; the kernel's own allocator already rounds to a page on
  aarch64 and riscv64) - and declares 0x60 as a word and 0x68 as a byte. A plain PCI driver with DMA policy
  `none` on all three architectures: arming writes 0x60 (reboot enabled, 1 kHz scale, stage-one interrupt
  disabled), both preloads through the unlock sequence, then 0x68's enable; a pet is the unlock sequence and
  the reload bit; disarm clears 0x68's enable, unless the lock bit is set - which this driver never sets, and
  which makes the timer one that cannot be disarmed; the last reset is BAR 0 + 0xC bit 9, cleared after reading.
- [ ] THE ICH9 TCO, THROUGH THE LPC/TCO DERIVATION ROW - P02M0191's mint source (c) provides the source, and
  this is its ICH9 row. The row 8086:2918: during the boot scan the kernel reads the PM base (0x40), the ACPI
  enable (0x44 bit 7) and the root-complex base (0xF0) through the configuration mechanism it keeps, and
  refuses the row, with a line, unless ACPI decode is on and the PM base equals the FADT's PM1a event block.
  It records EXACTLY PM base + 0x60..0x7F on the function's row, minted with the claim as a `PortRange` after
  P02M0191's reserved-set and existing-grant checks, and nothing else of the PM block - PM1 (whose control
  register the kernel writes to power off), the PM timer, GPE0 and SMI_EN stay the kernel's. GCS (root-complex
  base + 0x3410) is a DECLARED REGISTER with a write mask of the No-Reboot bit alone, present only when the
  root-complex base is enabled - NOT a mapping, because the page that holds it also holds the
  interrupt-routing registers (+0x3140..0x3150) and a page is the smallest thing a mapping can hand over. The
  claim has DMA policy `none`, enables no bus mastering and changes no decode bit of the LPC function at claim
  or release, because the kernel's own PM1 and reset paths depend on its decode. WHEN A WDAT IS PRESENT THE
  ROW IS NOT APPLIED - the ACPI watchdog wins, as it does in Linux's `lpc_ich` - so the LPC function stays an
  inventory row, the TCO driver's claim of it is refused, and no TCO provider appears. The TCO has no running
  bit, so at bind a clear halt bit with No-Reboot clear counts as running and is taken over, and with
  No-Reboot set the driver sets the halt bit (QEMU starts the count at the first reload, and a count nobody
  armed would record expiries). Arming clears No-Reboot and READS IT BACK before it writes the count and
  clears the halt bit - if No-Reboot stays set (a strap, a locked firmware setting) the arm fails as
  `unsupported` and the log says the device cannot reset the machine; a pet writes the reload register; disarm
  sets the halt bit and reads it back, answering `unsupported` if it did not stay set (the check Linux's
  `iTCO_wdt` makes); the last reset is TCO2_STS's second-timeout bit. GCS's reset value on this machine's
  Debian build is read at the part's first boot (the upstream v10.0.11 source sets No-Reboot).
- [ ] WDAT, read by P02M0196a as a static table and never running AML: the header's timer period, count range
  and flags (ENABLED, and `STOPPED` - the firmware stops the timer in the ACPI sleep states, never in suspend
  to idle - which the sleep step reads), and the action entries executed as the register reads and writes
  they list (read value, read countdown, write value, write countdown, with preserve-register). THE ACTIONS:
  `RESET` (the pet), `GET_COUNTDOWN`, `GET_CURRENT_COUNTDOWN` and `SET_COUNTDOWN`, `GET_RUNNING_STATE` and
  `SET_RUNNING_STATE` (start), `GET_STOPPED_STATE` and `SET_STOPPED_STATE` (disarm), `GET_REBOOT` and
  `SET_REBOOT` - run at bind and on every resume, and on a WDAT over this QEMU's TCO the only action that
  clears No-Reboot - `GET_SHUTDOWN` read and `SET_SHUTDOWN` never run (this contract resets), and
  `GET_STATUS` / `SET_STATUS` (the last reset was the watchdog's, cleared after reading). A table with ENABLED
  clear, or without `RESET`, `SET_COUNTDOWN`, `SET_RUNNING_STATE` and `GET_RUNNING_STATE`, is not a watchdog.
  THE RANGES HAVE A SOURCE OF THEIR OWN: the WDAT platform device's port ranges are what the KERNEL MINTS from
  the table's register list through P02M0191's static-table source, after refusing every range in the
  reserved set or already claimed; its system-memory registers are declared registers, after the kernel
  refuses RAM, kernel-held ranges, PCI windows and existing claims. An action whose instruction names a
  register outside what was minted is refused, not executed - and if it is one of the four required actions
  or a `SET_REBOOT` the table lists, the device is not a watchdog. Overlapping mints are refused (P02M0196a's
  reconciliation rule), and a WDAT suppresses the TCO row (above).
- [ ] The BMC's watchdog as a provider, published by P02M0201's TRANSPORT DRIVER - the binding that holds the
  KCS or BT device, ISA or PCI, since only a driver binding publishes into the catalogue; never the SSIF form,
  because a watchdog binding is suspended last and resumed first, which a child of the SMBus controller's
  binding cannot be - over IPMI's Set, Get and Reset Watchdog Timer: one stage in 100 ms units, action hard
  reset, pre-timeout none, the timer use "OS"; it survives the platform's reset; the last reset is Get
  Watchdog Timer's expiration flags, cleared after reading.

## P02M0200c - Verification

- [ ] THE ORACLE IS DURABLE: `-action watchdog=pause` and `query-status`. An expiry stops the guest in the run
  state `watchdog` until `cont`, so a case that ends `running` proves no expiry happened at ANY point - with no
  standing QMP listener, which the harness does not have (it connects per batch and skips events, and QMP sends
  an event only to a client connected when it happens). So every case below is a boot with a QMP socket - a
  `lab.py` boot or a scenario run - with `watchdog.device` naming the device under test, and each reads the
  service's line naming the device it armed. EVERY OTHER HARNESS BOOT WITH A QMP SOCKET passes
  `-action watchdog=pause` as well, so a stray expiry is a paused guest `query-status` names rather than a
  silent reset; those boots use development images, whose watchdog policy is off. TEST-MODE RUNS KEEP THE
  DEFAULT `reset`: they have no QMP socket - x86_64's test branch passes `-no-reboot` and exits before one is
  created, and aarch64 and riscv64 create one only under the development profile, which test mode refuses -
  and under `-no-reboot` a reset is QEMU's exit, which the kernel test runner already reports at once as a
  `GUEST RESET`, the guest log's last line naming the test it happened in; `pause` would turn that into a
  stall nothing reads until the run's timeout.
- [ ] With `pause`, on x86_64 with an `i6300esb` beside q35's TCO and the policy on (the expiry case last in
  its boot): the service's line naming the `i6300esb` armed and the TCO disarmed; a healthy system petting
  through three timeouts, still `running`; ServiceManager's hook stops answering `alive` at T0, the guest
  `running` at T0 + T - P - D less a stated margin and `watchdog` by T0 + T plus that margin (T being the
  effective timeout the arm answered), polled with `query-status`; the watchdog service killed and restarted,
  and the watchdog driver killed and rebound, each still `running` after three timeouts; an orderly `!reboot`
  with the timer armed, the notice delivered, answered and the timer disarmed within its bound, named in the
  log BEFORE the first service is stopped. (For a timer reset with the platform nothing else about an orderly
  shutdown can fail - QEMU resets the `i6300esb` and exits at power-off - so the case that can fail is the
  BMC's, below.)
- [ ] With `-action watchdog=reset` and WITHOUT `-no-reboot` (which would turn the reset into an exit), so on
  x86_64 - its non-test boots pass none, while the harness passes it to every aarch64 and riscv64 boot: the
  reset on the serial log as a second boot, and in that boot the provider of the device `watchdog.device` names
  reporting that the last reset was its watchdog's, and no other provider reporting one.
- [ ] Each device through the same gate: the `i6300esb` on all three targets (the reset case on x86_64 only);
  the TCO on x86_64 q35; WDAT over the TCO's registers from an `-acpitable` fixture written by the harness's
  own generator (1200 ms per count, `SET_REBOOT` clearing No-Reboot, the addresses OVMF assigns), with no TCO
  provider in that boot.
- [ ] The BMC's watchdog through P02M0201's transport driver and `ipmi-bmc-sim`, beside q35's TCO. Its expiry
  is a chassis reset, not a QEMU watchdog action - no `WATCHDOG` event, `-action watchdog=` does not apply -
  so its oracle is the BMC's own record, GET WATCHDOG TIMER AS THE NEXT BOOT'S DRIVER READS IT AT BIND - the
  expiration flags and the INITIAL COUNTDOWN, which that driver's bind line names - and the serial log's boot
  count: an expiry resets the machine and the next boot reports it as the BMC's, the TCO reporting none; an
  ORDERLY REBOOT with the BMC timer armed short finds, at the next bind, no expiry flag and the boot bound as
  the initial countdown, because the notice extended it; and the same reboot with the notice step skipped by a
  development hook finds the short timeout as the initial countdown, or the expiry flag if the timer ran out
  first - so this case can fail, whichever of the timer and the next boot's bind comes first. An expiry flag
  alone could not be the oracle: the takeover pets a running timer at once, the simulator's timer keeps
  counting across the host's reset, and the shortest timeout the BMC takes is 15 s, so a boot that reaches the
  `ipmi` bind inside it leaves no flag although the notice was skipped.
- [ ] The sleep case, with both halves as P02M0197 states it: `running` after a suspend to idle longer than
  the timeout; and `watchdog` after a resume that a development hook stops between the watchdog binding's
  re-arm and the resume notice, within the bridge bound of that re-arm plus the margin - the half that proves
  the re-arm, since a driver that disarms at suspend and never re-arms passes the first. Carried by whichever
  of P02M0197 and P02M0200 lands second; the first to land records that it is owed.
- [ ] Host suites: the WDAT interpreter against hostile tables - a register outside the minted ranges (PM1a
  control, the PIT, a claimed range), an unknown action, an instruction count past the table, a required action
  missing, ENABLED clear; the LPC derivation against fixtures - a PM base that does not match the FADT, the
  root-complex base disabled, a WDAT present; the declared-register checks - an undeclared offset, a wrong
  width, a masked bit; the watchdog service's choice against scripted providers - the named device, the
  default order, an arm answering `unsupported`, a named device absent, a provider published later, a fifth
  provider; each device's timeout division.
- [ ] Kernel tests: 0x60 as a word and 0x68 as a byte reaching an `i6300esb` on each target, an undeclared
  offset and a wrong width refused, the capability gone after release; on x86_64 q35 the LPC row minting exactly
  the TCO block and refusing PM1, the PM timer and GPE0. The three cross-builds.

EXCLUDES: `ib700`, an ISA card nothing describes - it can only be found by probing ports, which this system
does not do; the SBSA generic watchdog of ARM servers, which QEMU emulates only on its `sbsa-ref` machine and
this system does not boot that machine - so it waits, as P02M0195's laptop controllers do, for a machine to
prove it on; SoC-specific watchdogs on boards; TCO rows for chipsets after ICH9, which keep No-Reboot
elsewhere, until a machine is named; THE PRE-TIMEOUT WARNING, whose one use is writing a crash record, which
waits for somewhere to write it that survives a reset - QEMU does not deliver the `i6300esb`'s stage-one
interrupt, and the TCO's first expiry raises only an SMI, which is the firmware's; the drivers leave both off,
and the BMC's pre-timeout is set to none; a standing heartbeat on managed services, which ServiceManager's
liveness answer does not provide and this milestone does not add.
