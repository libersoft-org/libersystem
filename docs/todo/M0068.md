# M0068 - GPU framebuffer realloc on resize (no resolution ceiling)

Status: COMPLETE.

The driver allocated its framebuffer once, floored at 1920x1080, so anything larger than the initial
window was clamped. **The fix is not a bigger constant** - displays outgrow any constant - but
reallocating for whatever geometry the host reports. The floor is gone entirely; the display's own
reported limit is the only bound.

*Condensed 2026-08-08.*

A change within the current allocation stays the cheap path. A change beyond it reallocates: a new
backing at the new geometry, the scanout re-attached, the old resource detached and released, and a
message hands ConsoleService the replacement. The console maps it, swaps every display VT's renderer
onto it - **the grid models survive**, and the whole grid is marked dirty so the next flush repaints
in full - reflows, and closes its old handle, which is the last reference.

**A failed reallocation clamps to the standing allocation instead of blanking the screen.** Running
out of memory during a resize must not cost you the display you already had.

## Two enabling fixes that surfaced

- **Attaching the backing now coalesces physically contiguous frame runs into single memory
  entries.** Per-page entries overflowed the 16-descriptor control queue at 2560x1440 and beyond, so
  the resize failed for a reason that had nothing to do with the resize.
- **The frame allocator sorts its returned pages ascending.** The LIFO free list handed back a
  just-freed buffer in reverse order, which defeated the coalescing above after the very first
  reallocation - so the fix worked once and then stopped.

Validation drove the real host path over VNC desktop-resize rather than a simulated event: boot at
1280x800, grow past the old ceiling to 2560x1440, shrink to 1024x768, grow to 3840x2160, each step
confirmed by the host-side scanout size.
