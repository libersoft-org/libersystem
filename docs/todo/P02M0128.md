# P02M0128 - The terminal's state machine, and the one safe function that is not safe

Status: PLANNED. An outside audit of `src/term` against its two callers - the kernel boot console
and ConsoleService - pinned to `0a46ff6`. Every finding was checked against the tree and every one
held; a few are worse than the audit stated and are written up here at their measured size.

The L1/L2/L3 split is the right shape and the reason this crate is worth hardening rather than
rewriting: `RawSink` taps the byte stream, `Screen` owns the grid with no pixel in it, and the
renderer is a pure consumer of a damage/scroll diff that the kernel and ConsoleService share
unchanged. The damage tracking is genuinely good - a selection drag repaints the band between the
old and the new end rather than the span, and a scroll moves pixels in one bulk copy instead of
re-blitting the frame.

What has drifted is that the terminal's STATE stopped being one state machine. Pending wrap lives in
an out-of-range cursor column; soft-wrap metadata is one vector shared by two screen buffers; resize
throws away everything it cannot copy; the scroll queue is drained by the renderer, so a terminal
nobody is rendering never drains it. Each of those is a small local decision, and together they are
the reason resize, alternate screen and line editing are the three places this terminal misbehaves.

And one finding is not about the terminal at all: `Raster::new` is a safe function that takes an
integer and reads and writes memory at it.

## The soundness bug

- [x] **`Raster::new(addr: u64, &Geometry)` is safe and its object dereferences that address.**
  `put_pixel` and `read_pixel` do `write_volatile`/`read_volatile` at `addr + y * pitch + x * bpp`,
  and every one of them is reachable through the safe `Surface` trait. No length is stored, no
  lifetime ties the object to a mapping, and nothing proves the framebuffer exists. Safe Rust can
  write `Raster::new(1, &g)` and then `fill()`. Both current callers - `kernel/console.rs` and
  ConsoleService's `make_surface` - take the address from a trusted mapping, so this is not a live
  exploit; it is a real soundness bug in a public API, and it is the only thing in this crate that
  breaks a language guarantee rather than a terminal one.

  FIXED 2026-08-11. `Raster::new` is `unsafe fn` with the contract written out - the mapping's size,
  its lifetime, and that nothing else aliases it - and returns `Option`, so a geometry this renderer
  cannot address is a refusal rather than a value that panics later. Both callers pass their
  mapping's provenance in a `SAFETY:` comment: the kernel's comes from the boot protocol's
  framebuffer record, the service's from the display protocol call that just mapped it.

  It still carries a `u64` rather than `NonNull<u8>` plus a length. The length is now VALIDATED
  against the geometry, which is the part that was doing no work; carrying the pointer as
  `NonNull` would make the struct non-`Send` by default and both callers hand it across a `Box<dyn
  Surface>` boundary, so that is a change to the trait rather than to this constructor.

  Make the constructor `unsafe fn` with a written contract, and have it carry `NonNull<u8>` plus a
  byte length instead of a `u64`.

- [x] **The geometry is never validated, and two of its fields panic on ordinary bad input.**
  `put_pixel` writes `bytes[i]` for `i in 0..bytes_per_pixel` over a `[u8; 4]`, so a
  `bytes_per_pixel` of 5 is an index panic, not a refusal; `channel()` does `<< shift` on a `u32`,
  so a `red_shift` of 32 or more panics in a debug build. Neither value is checked anywhere.

  FIXED 2026-08-11, once, where the numbers arrive: `bytes_per_pixel` in `1..=4`, `pitch >= width *
  bytes_per_pixel`, every channel size at most 8 and every shift plus its size within 32, and
  `pitch * height` not overflowing.

  `a_geometry_the_renderer_cannot_address_is_refused_rather_than_panicking` covers six ways to get
  it wrong and asserts the sane geometry is accepted first, so each one is a change rather than a
  coincidence. The per-pixel path still bounds-checks; dropping those is a separate optimisation and
  wants a benchmark rather than an argument.

  The consequence for a caller is what the finding wanted: a display backend reporting a format
  this renderer does not implement gets a VT with no terminal, not a crash on the first glyph.

  Validate at construction, once, where the numbers arrive: `bytes_per_pixel` in `1..=4`,
  `pitch >= width * bytes_per_pixel`, every shift plus its size within 32, and
  `pitch * height <= len`. Then the per-pixel path can drop its bounds checks and be faster than it
  is now.

## The state that should be one state machine

- [ ] **`resize()` does not reflow - it crops, and discards everything it cannot copy.** The
  comment says "reflowing the screen"; the code copies the `min(cols) x min(rows)` overlapping
  rectangle bottom-anchored and reallocates the rest. Narrowing the window destroys the text right
  of the new width instead of flowing it onto the next line. In the same call the scrollback is
  emptied, the wrap metadata is dropped, the alternate screen is reallocated, selection and mouse
  are cleared, and `alt_active` is forced to `false`.

  This is not dead code: `handle_display_resize` calls `resize_vt` for every VT on a real
  resolution change, so a full-screen program in the alternate screen is thrown back into the
  primary buffer by a host window resize. Reflow is the natural consequence of holding logical lines
  rather than a rectangle of cells; the wrap flags this crate already maintains are most of the
  information needed. At minimum, alternate-screen state and scrollback must survive a resize.

- [x] **Pending wrap is encoded as an out-of-range cursor.** `put_glyph` ends with `self.col += 1`,
  so after a glyph lands in the last column the cursor sits at `col == cols`, and only the NEXT
  glyph interprets that as a wrap. Two things follow. The renderer draws the caret only when
  `cursor_col() < cols`, so filling a line exactly makes the caret vanish. And a CSI that moves only
  the row - `CSI B` - leaves `col == cols` intact, so the next glyph both wraps and line-feeds, and
  lands a row below where it belongs.
  FIXED 2026-08-11. `pending_wrap` is a flag, the cursor always names a real cell, and a control
  byte or a CSI clears it - cleared at those two entry points rather than at each of the eighteen
  places that assign `col`, so a nineteenth cannot forget. A printable byte does NOT clear it, which
  is the one distinction the first attempt got wrong: it cleared on every byte, so nothing ever
  wrapped and four existing tests said so immediately.

  `a_full_line_keeps_its_caret_and_a_row_move_does_not_wrap` asserts both consequences the finding
  names - the caret still on screen after a line is filled exactly, and a glyph after `CSI B`
  landing on the row the move chose rather than one below it.

  The fix is the standard one: keep the cursor in `0..cols` and hold `wrap_pending: bool` beside it,
  cleared by every absolute and horizontal cursor movement.

- [x] **One `wrap` vector serves both screen buffers.** `enter_alt` switches the cell buffer and
  leaves the wrap metadata alone, so a full-screen program edits the PRIMARY screen's soft-wrap
  flags; after it exits, `TextSink` joins rows that have nothing to do with each other. And erasing
  does not clear them: `CSI J` / `CSI K` go through `fill_cells`, which blanks cells and leaves
  `wrap` untouched, so a soft-wrap flag survives the complete erasure of the row it describes.
  (`clear()` does clear them, which is why this is easy to miss.)
  FIXED 2026-08-11, both halves. `alt_wrap` holds the alternate screen's flags and `enter_alt` /
  `leave_alt` swap the two, so the metadata follows the buffer it describes; and `fill_cells` clears
  the soft-wrap flag of any row whose last cell it erased, which is what `CSI J` and `CSI K` both go
  through.

  `the_alternate_screen_keeps_its_own_soft_wrap_flags` and `erasing_a_row_clears_the_soft_wrap_it_described`,
  each watched to fail. Both assert the fixture actually soft-wraps first, because a test of wrap
  metadata on a screen that never wrapped is a test of nothing.

  Cells, dirty marks and wrap flags are three parallel arrays describing one grid. They should be
  one `ScreenBuffer` struct held twice, primary and alternate, so switching screens cannot switch
  two of the three.

- [ ] **A background VT's scroll queue grows without bound.** Every `region_up`/`region_down` pushes
  a `ScrollOp`, and the only drain is `take_scrolls()` inside the renderer's flush - which
  ConsoleService calls only for the foreground VT. A program on VT 2 while the user watches VT 1
  accumulates one `ScrollOp` per scrolled line, forever. Switching to it then calls `repaint`, which
  marks the whole grid dirty and flushes - replaying every accumulated bulk pixel copy first, all of
  them overwritten by the full repaint that follows.

  A model that is not being rendered should not be recording pixel operations. Either bound the
  queue and mark it overflowed (a full repaint is the correct response to overflow anyway), or let
  the console tell the model it is not being displayed.

## The line editor

- [ ] **`EchoBuf` is 512 bytes and drops the rest of the echo silently.** A line is up to
  `LD_LINE_MAX` = 4096 bytes, and `replace_line` - Ctrl+U, and every history recall - echoes the
  tail, then three bytes per column to erase it, then the new line: past 20 kB for a full line, into
  a 512-byte buffer whose `push` simply stops. The framebuffer echo is live and stays correct, so
  the local display looks right while the serial mirror and the PTY master - which are fed exactly
  this buffer - receive a truncated escape stream and lose sync. A sink that cannot hold what it is
  given must say so; this one needs chunked drainage, not a bigger fixed buffer.

- [ ] **The editor breaks as soon as the edited line wraps.** It moves the cursor by repeating
  `\x08`, and `Screen`'s backspace stops at column 0 - it never steps back onto the previous row.
  So on an 80-column terminal, a command long enough to wrap leaves Home, Backspace and mid-line
  editing moving `Ld.cursor` while the caret stays stuck on the last physical row: buffer and screen
  diverge, and every subsequent edit is drawn in the wrong place.

  A line editor cannot be display-agnostic. It needs the terminal width and the prompt's start
  column so it can address the logical line as a rectangle - which is also what makes a correct
  redraw after a resize possible.

- [ ] **Cooked mode accepts only `0x20..=0x7e`.** Everything from `0x80` up is dropped by
  `Ld::feed`, so this terminal renders Czech perfectly and cannot accept a single accented character
  as INPUT. It already shows: an unbracketed paste is delivered byte by byte through the same path,
  so pasting `příliš žluťoučký kůň` silently loses every non-ASCII byte. Admitting bytes over 0x7f
  is not enough - the editor must know UTF-8 boundaries, or Backspace deletes one third of a
  character.

- [ ] **Three small robustness edges in the input parser.** `Ld.csi_param` is a `u8` accumulated
  with `wrapping_mul`/`wrapping_add`, so `CSI 259~` becomes 3 and executes Delete. `Ld::new(0)` is a
  legal public call and its first `commit` runs `history.remove(0)` on an empty vector - the config
  path filters zero today, which is protection by coincidence. And the history is a `Vec` with
  `remove(0)`, which is O(n) per commit where a `VecDeque` is the obvious shape.

## Escape sequences that reach past the terminal

- [ ] **Program output can change the tty's raw and echo modes.** `ESC[?9001h/l` and `ESC[?9002h/l`
  set `tty_raw_req`/`tty_echo_req`, and ConsoleService writes them straight into `ld.cooked` and
  `ld.echo`. So `cat` on a file containing those bytes reconfigures the terminal: the data a program
  prints is indistinguishable from a request the program makes.

  This is narrower than it first looks - the effect is confined to the VT the program already owns,
  and that program could ask for raw mode through an API if one existed. That is the actual finding:
  there is no API, so an escape sequence is doing the job of `tcsetattr`. Mode control belongs in
  the console protocol, addressed to the tty by its foreground owner, and the private sequences
  should then be dropped rather than kept as a second path to the same state.

- [ ] **OSC 52 from a background VT rewrites the console-wide clipboard.** `render_output` drains
  `take_clipboard_set()` and assigns `console.clipboard` OUTSIDE its `if fg` guard, so a program on
  a terminal the user is not looking at replaces what the next paste will insert. Restrict it to the
  foreground VT, and treat writing the user's clipboard as something a program is granted rather
  than something it can do by printing.

- [ ] **The OSC buffer is 256 bytes and truncates in silence.** `osc_byte` drops every byte past the
  buffer and then dispatches whatever it kept, so an OSC 52 payload longer than the buffer decodes
  to a PREFIX of the intended clipboard text rather than being refused. Truncation must set an
  overflow flag that makes the dispatch fail; a control string that did not arrive whole was not
  received.

## ANSI and xterm behaviour

- [x] **The UTF-8 decoder validates shape, not encoding.** It checks lead and continuation bit
  patterns and nothing else: overlong encodings, the surrogate range and everything above U+10FFFF
  all pass into a cell. A broken continuation byte drops the partial sequence and reinterprets the
  byte, with no U+FFFD emitted - so a truncated sequence disappears rather than becoming a
  replacement character, and the invalid codepoint that reaches `push_utf8` renders as `?`, not
  U+FFFD. Decode strictly and emit U+FFFD on every malformed sequence, which is what the crate's
  own comments already promise.
  FIXED 2026-08-11. `begin_utf8` records the smallest codepoint its length may legally encode, and
  the completed value is checked against that, against the surrogate range and against U+10FFFF -
  so an overlong form, a surrogate half and a codepoint past the end of Unicode are each one U+FFFD
  instead of a cell that renders as `?` because the font lookup rejected what the decoder accepted.
  A truncated sequence emits one U+FFFD and then reinterprets the interrupting byte, where it used
  to vanish in silence.

  `a_malformed_utf8_sequence_becomes_one_replacement_character` covers five malformed shapes, the
  truncation, and a legal sequence - the last so the strictness is not simply refusing. Both halves
  watched to fail.

- [x] **`CSI 3 J` erases the screen, and every unknown erase mode erases everything.**
  `erase_display` maps 0 and 1 explicitly and `_` to the whole screen; xterm's 3 clears the SAVED
  lines - the scrollback - and leaves the display alone. So the one sequence a program uses to drop
  history instead wipes what the user is reading, and `CSI 99J` does the same. `erase_line` has the
  identical `_` arm. An unsupported mode should be ignored.

  FIXED 2026-08-11. `CSI 3 J` drops the scrollback and leaves the display, and an erase mode neither
  function implements erases nothing - in both `erase_display` and `erase_line`, which had the same
  catch-all. `an_erase_mode_this_terminal_does_not_implement_erases_nothing` covers `CSI 99J`,
  `CSI 7K` and `CSI 3J`, and asserts `CSI 2J` still clears, so the rule is not "refuse everything".

- [ ] **A scroll region anchored at row 0 pollutes the scrollback.** `scroll_up` pushes rows to
  history whenever `scroll_top == 0`, never checking `scroll_bottom == rows - 1`, though the comment
  directly above says a region scroll must not reach history. `CSI 1;10r` therefore fills the
  scrollback with the top ten rows of a status pane. The row count pushed is clamped to `rows`
  rather than the region height, so `CSI 999S` in a small region can push rows that were never in
  it.

- [ ] **`ESC c` is not a reset.** RIS restores SGR, cursor visibility, margins, mouse modes and
  bracketed paste, and leaves the OSC-modified palette, `default_fg`/`default_bg`, the DECSCUSR
  shape and blink, and the saved-cursor state exactly as the previous program left them. A terminal
  after a full reset should be indistinguishable from a fresh `Screen`; that is the whole purpose of
  the sequence, and it is what a shell relies on after a program crashes.

- [ ] **`?47`, `?1047` and `?1049` are one code path.** All three enter and leave the alternate
  screen with the same save/restore and clear. xterm distinguishes them - which one saves the
  cursor, which one clears on exit - and ported full-screen programs depend on the difference. Also
  in `set_mode`: disabling `?1002` or `?1003` sets `mouse_mode = 0` outright, cancelling a `?1000`
  that is still notionally on.

- [ ] **There is no reply path, so every query sequence is silently ignored.** `csi_dispatch`
  handles no `n` (DSR/CPR) and no `c` (DA), and the OSC 52 query case says outright that a
  write-back path is missing. A program asking where the cursor is waits forever. The model needs a
  reply queue the console drains into the program's input, the same shape `clipboard_set` and the
  tty mode requests already use.

  (Related and already deliberate: only SGR-encoded mouse reports are produced, so a program that
  enables `?1000` without `?1006` receives nothing. The code says so; this milestone should decide
  whether to implement the X10 encoding or state the requirement in the terminal's documentation.)

## The renderer

- [x] **Bold brightens the background.** `cell_colors` passes `c.bold` to `resolve` for both
  foreground and background, so bold text on ANSI background 40-47 silently moves to the bright
  palette entry 8-15. Intensity applies to the foreground.

  FIXED 2026-08-11: `cell_colors` passes `false` for the background. Intensity is a foreground
  property, and passing `c.bold` to both meant the same ANSI background changed colour depending on
  whether the text over it was bold.

- [ ] **`cursor_blink` is recorded and cannot be read.** DECSCUSR correctly separates blinking from
  steady and stores the flag - and `Screen` exposes no getter for it, so `blink_caret` cannot
  consult it and toggles whenever the cursor is visible. `CSI 4 SP q` (steady underline) blinks, and
  so does the default cursor, whose flag is `false`. The comments in `screen.rs` compound it by
  saying the caret is drawn solid, which stopped being true when the blink timer landed.

- [ ] **An OSC palette or default-colour change repaints nothing.** Cells hold `Color::Idx` and
  `Color::Default` and resolve to RGB at draw time - the right design - so changing the palette
  changes what every existing cell should look like, and OSC 4/10/11 do not call `mark_all_dirty`.
  The screen keeps the old colours until something else happens to dirty it.

- [ ] **The scrollback fast path drags the mouse block with it.** `flush_view_scroll` bulk-copies
  the framebuffer and repairs the text caret's ghost, but not the mouse cursor's inverted block:
  the pointer stays on its viewport cell while the wheel moves the view, so the block's pixels ride
  the copy to another row and no repaint removes them. The live `flush` path already solves exactly
  this by dirtying both the tracked cell and the current one; the paging path needs the same two
  lines.

## Bounds

- [ ] **Grid and scrollback allocations are unbounded and unchecked.** `Screen::new` computes
  `cols * rows` and `scrollback * cols` with no `checked_mul`, and `console.scrollback` accepts any
  positive integer from the config tree with no ceiling. `Term::new` divides the framebuffer by the
  cell size, so a surface smaller than 8x16 produces a 0x0 `Screen` - and the first `put_glyph` then
  indexes an empty `wrap` vector. The kernel checks for 0x0 after constructing one; the public API
  should not require its callers to know that. `Screen::cell` is public and indexes without bounds
  checks too, where `set_cell` returns quietly.

- [ ] **State the real per-VT cost, and cap something.** `SCROLLBACK_ROWS` is 1000 and a `Cell` is
  16 bytes, so at 1024x768 (128 columns) the scrollback ring alone is 1.95 MB and a VT costs
  **2.15 MB**; at 1920x1080 it is **4.17 MB**. VTs are created on demand with no cap - the code says
  so deliberately - so console memory is unbounded in a service whose heap starts at 1 MB and grows.
  The comment in `screen.rs` still describes a four-VT cap and a fixed 1 MB heap, and `P02M0006` still
  documents `SCROLLBACK_ROWS = 100` and "about 196 kB per VT"; both were true and are not. Decide
  the policy - a VT ceiling, a scrollback ceiling, or an explicit statement that this memory is
  operator-configured - and make the three places agree.

## Unicode beyond the codepoint

- [ ] **The cell model assumes one codepoint is one cell.** Every decoded codepoint goes to
  `put_glyph` and advances one column, which is correct for the precomposed Latin the font covers
  and wrong for combining marks, zero-width characters and East Asian wide characters. This is the
  one finding that is a design decision rather than a defect: a `wcwidth` equivalent plus a
  representation for a base glyph with combining marks is real work, and a bitmap-font VT console
  may reasonably decide not to do it.

  What is not reasonable is leaving it unsaid. Either implement width handling, or document the
  supported subset the way the ISO9660 backend documents its 2048-byte block size - as a product
  decision, not an omission.

## Tests

- [ ] **The suite covers the model's calm paths and none of its sharp ones.** Twenty-one tests over
  text, soft wrap, scrollback, OSC 52, selection and Tab completion; the renderer has exactly one,
  for the font cache. Not one test mentions resize, the alternate screen, invalid UTF-8, the
  palette, or the cursor.

  Add, and write each one so it fails first: a resize that must not lose the alternate screen; a
  narrowing resize (reflow, or the documented crop); a scroll region at row 0 that must not touch
  the scrollback; overlong, surrogate and truncated UTF-8; a palette change repainting; bold on a
  coloured background; a line filled to exactly `cols` leaving the caret visible and `CSI B` not
  double-feeding; an `Ld` edit whose echo exceeds 512 bytes; a Unicode paste; steady versus blinking
  DECSCUSR; OSC 52 from a background VT; an over-long OSC string being refused rather than
  truncated; `CSI 3 J` sparing the display; RIS restoring the palette; a background VT's scroll
  queue staying bounded; and a `Raster` built on an invalid geometry being refused at construction.

## Order

`Raster` first: it is the only finding that breaks a Rust guarantee rather than a terminal
convention, and it is a contained change to a constructor and its two callers.

Then the state model, as one piece of work rather than four: `wrap_pending` as a field, cells and
dirty marks and wrap flags as one `ScreenBuffer` held twice, and a resize that preserves what it
should. Doing these together is what makes them small; done separately, each has to work around the
other two.

Then the three failures a user meets in ordinary use - the unbounded background scroll queue, the
truncated echo buffer, and the line editor on a wrapped line - and after them the tty mode control
API, which is what lets the private escape sequences be deleted rather than merely guarded.

ANSI and xterm conformance last, in the order a ported program notices it: strict UTF-8, the reply
path, ED 3, RIS, the alternate-screen variants, then the renderer's colour and caret details.
