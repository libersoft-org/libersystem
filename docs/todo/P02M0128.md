The L1/L2/L3 split is the right shape and the reason this crate is worth hardening rather than
rewriting: `RawSink` taps the byte stream, `Screen` owns the grid with no pixel in it, and the
renderer is a pure consumer of a damage/scroll diff that the kernel and ConsoleService share
unchanged. The damage tracking is genuinely good - a selection drag repaints the band between the
old and the new end rather than the span, and a scroll moves pixels in one bulk copy instead of
re-blitting the frame.

What has drifted is that the terminal's STATE stopped being one state machine. Pending wrap lives in
an out-of-range cursor column; soft-wrap metadata is one vector shared by two screen buffers; resize
throws away everything it cannot copy; the scroll queue is drained by the renderer, so a terminal
nobody is rendering never drains it. Each of those is a small local decision, and together they are
the reason resize, alternate screen and line editing are the three places this terminal misbehaves.

And one finding is not about the terminal at all: `Raster::new` is a safe function that takes an
integer and reads and writes memory at it.

## The soundness bug

- [x] **`Raster::new(addr: u64, &Geometry)` is safe and its object dereferences that address.**
  `put_pixel` and `read_pixel` do `write_volatile`/`read_volatile` at `addr + y * pitch + x * bpp`,
  and every one of them is reachable through the safe `Surface` trait. No length is stored, no
  lifetime ties the object to a mapping, and nothing proves the framebuffer exists. Safe Rust can
  write `Raster::new(1, &g)` and then `fill()`. Both current callers - `kernel/console.rs` and
  ConsoleService's `make_surface` - take the address from a trusted mapping, so this is not a live
  exploit; it is a real soundness bug in a public API, and it is the only thing in this crate that
  breaks a language guarantee rather than a terminal one.

  FIXED 2026-08-11. `Raster::new` is `unsafe fn` with the contract written out - the mapping's size,
  its lifetime, and that nothing else aliases it - and returns `Option`, so a geometry this renderer
  cannot address is a refusal rather than a value that panics later. Both callers pass their
  mapping's provenance in a `SAFETY:` comment: the kernel's comes from the boot protocol's
  framebuffer record, the service's from the display protocol call that just mapped it.

  It still carries a `u64` rather than `NonNull<u8>` plus a length. The length is now VALIDATED
  against the geometry, which is the part that was doing no work; carrying the pointer as
  `NonNull` would make the struct non-`Send` by default and both callers hand it across a `Box<dyn
  Surface>` boundary, so that is a change to the trait rather than to this constructor.

  Make the constructor `unsafe fn` with a written contract, and have it carry `NonNull<u8>` plus a
  byte length instead of a `u64`.

- [x] **The geometry is never validated, and two of its fields panic on ordinary bad input.**
  `put_pixel` writes `bytes[i]` for `i in 0..bytes_per_pixel` over a `[u8; 4]`, so a
  `bytes_per_pixel` of 5 is an index panic, not a refusal; `channel()` does `<< shift` on a `u32`,
  so a `red_shift` of 32 or more panics in a debug build. Neither value is checked anywhere.

  FIXED 2026-08-11, once, where the numbers arrive: `bytes_per_pixel` in `1..=4`, `pitch >= width *
  bytes_per_pixel`, every channel size at most 8 and every shift plus its size within 32, and
  `pitch * height` not overflowing.

  `a_geometry_the_renderer_cannot_address_is_refused_rather_than_panicking` covers six ways to get
  it wrong and asserts the sane geometry is accepted first, so each one is a change rather than a
  coincidence. The per-pixel path still bounds-checks; dropping those is a separate optimisation and
  wants a benchmark rather than an argument.

  The consequence for a caller is what the finding wanted: a display backend reporting a format
  this renderer does not implement gets a VT with no terminal, not a crash on the first glyph.

  Validate at construction, once, where the numbers arrive: `bytes_per_pixel` in `1..=4`,
  `pitch >= width * bytes_per_pixel`, every shift plus its size within 32, and
  `pitch * height <= len`. Then the per-pixel path can drop its bounds checks and be faster than it
  is now.

## The state that should be one state machine

- [x] **`resize()` does not reflow - it crops, and discards everything it cannot copy.** The
  comment says "reflowing the screen"; the code copies the `min(cols) x min(rows)` overlapping
  rectangle bottom-anchored and reallocates the rest. Narrowing the window destroys the text right
  of the new width instead of flowing it onto the next line. In the same call the scrollback is
  emptied, the wrap metadata is dropped, the alternate screen is reallocated, selection and mouse
  are cleared, and `alt_active` is forced to `false`.
  FIXED 2026-08-11, with the reflow rather than the minimum. The information was already here: the
  soft-wrap flags say which rows are continuations, so the scrollback and the screen together are a
  sequence of LOGICAL lines. `resize` rebuilds those, trims the padding a fixed-width grid adds at a
  hard line end, lays them out at the new width with the same wrap encoding, and takes the last
  `new_rows` rows as the screen and the rest as scrollback. The cursor is tracked by its logical
  position and found again afterwards.

  The alternate screen survives as a rectangle - a full-screen program redraws it on a resize, so
  reflowing it would be wrong - and `alt_active` stays what it was instead of being forced back to
  the primary buffer mid-session.

  `narrowing_the_window_reflows_instead_of_destroying_text` narrows and widens again and requires
  the text back, which is the property that makes the wrap encoding worth having;
  `a_resize_does_not_throw_a_full_screen_program_out_of_the_alternate_buffer` reads the alternate
  buffer through `cell` - `TextSink` serializes the primary and its scrollback, which is what a
  scrollback view IS.

  This is not dead code: `handle_display_resize` calls `resize_vt` for every VT on a real
  resolution change, so a full-screen program in the alternate screen is thrown back into the
  primary buffer by a host window resize. Reflow is the natural consequence of holding logical lines
  rather than a rectangle of cells; the wrap flags this crate already maintains are most of the
  information needed. At minimum, alternate-screen state and scrollback must survive a resize.

- [x] **Pending wrap is encoded as an out-of-range cursor.** `put_glyph` ends with `self.col += 1`,
  so after a glyph lands in the last column the cursor sits at `col == cols`, and only the NEXT
  glyph interprets that as a wrap. Two things follow. The renderer draws the caret only when
  `cursor_col() < cols`, so filling a line exactly makes the caret vanish. And a CSI that moves only
  the row - `CSI B` - leaves `col == cols` intact, so the next glyph both wraps and line-feeds, and
  lands a row below where it belongs.
  FIXED 2026-08-11. `pending_wrap` is a flag, the cursor always names a real cell, and a control
  byte or a CSI clears it - cleared at those two entry points rather than at each of the eighteen
  places that assign `col`, so a nineteenth cannot forget. A printable byte does NOT clear it, which
  is the one distinction the first attempt got wrong: it cleared on every byte, so nothing ever
  wrapped and four existing tests said so immediately.

  `a_full_line_keeps_its_caret_and_a_row_move_does_not_wrap` asserts both consequences the finding
  names - the caret still on screen after a line is filled exactly, and a glyph after `CSI B`
  landing on the row the move chose rather than one below it.

  The fix is the standard one: keep the cursor in `0..cols` and hold `wrap_pending: bool` beside it,
  cleared by every absolute and horizontal cursor movement.

- [x] **One `wrap` vector serves both screen buffers.** `enter_alt` switches the cell buffer and
  leaves the wrap metadata alone, so a full-screen program edits the PRIMARY screen's soft-wrap
  flags; after it exits, `TextSink` joins rows that have nothing to do with each other. And erasing
  does not clear them: `CSI J` / `CSI K` go through `fill_cells`, which blanks cells and leaves
  `wrap` untouched, so a soft-wrap flag survives the complete erasure of the row it describes.
  (`clear()` does clear them, which is why this is easy to miss.)
  FIXED 2026-08-11, both halves. `alt_wrap` holds the alternate screen's flags and `enter_alt` /
  `leave_alt` swap the two, so the metadata follows the buffer it describes; and `fill_cells` clears
  the soft-wrap flag of any row whose last cell it erased, which is what `CSI J` and `CSI K` both go
  through.

  `the_alternate_screen_keeps_its_own_soft_wrap_flags` and `erasing_a_row_clears_the_soft_wrap_it_described`,
  each watched to fail. Both assert the fixture actually soft-wraps first, because a test of wrap
  metadata on a screen that never wrapped is a test of nothing.

  Cells, dirty marks and wrap flags are three parallel arrays describing one grid. They should be
  one `ScreenBuffer` struct held twice, primary and alternate, so switching screens cannot switch
  two of the three.

- [x] **A background VT's scroll queue grows without bound.** Every `region_up`/`region_down` pushes
  a `ScrollOp`, and the only drain is `take_scrolls()` inside the renderer's flush - which
  ConsoleService calls only for the foreground VT. A program on VT 2 while the user watches VT 1
  accumulates one `ScrollOp` per scrolled line, forever. Switching to it then calls `repaint`, which
  marks the whole grid dirty and flushes - replaying every accumulated bulk pixel copy first, all of
  them overwritten by the full repaint that follows.
  FIXED 2026-08-11. `record_scroll` caps the queue at 64; past that it is dropped and the whole grid
  marked dirty, which is the same answer `repaint` gives and a strictly cheaper one - a scroll diff
  longer than the screen carries no information a full repaint does not, and keeping it costs memory
  that grows with how long nobody looked.

  `an_unflushed_scroll_queue_stops_growing_and_asks_for_a_repaint` scrolls ten thousand lines
  without a flush and requires the queue to stay bounded, then writes one more line to show the
  bound is not losing content.

  A model that is not being rendered should not be recording pixel operations. Either bound the
  queue and mark it overflowed (a full repaint is the correct response to overflow anyway), or let
  the console tell the model it is not being displayed.

## The line editor

- [x] **`EchoBuf` is 512 bytes and drops the rest of the echo silently.** A line is up to
  `LD_LINE_MAX` = 4096 bytes, and `replace_line` - Ctrl+U, and every history recall - echoes the
  tail, then three bytes per column to erase it, then the new line: past 20 kB for a full line, into
  a 512-byte buffer whose `push` simply stops. The framebuffer echo is live and stays correct, so
  the local display looks right while the serial mirror and the PTY master - which are fed exactly
  this buffer - receive a truncated escape stream and lose sync. A sink that cannot hold what it is
  given must say so; this one needs chunked drainage, not a bigger fixed buffer.
  FIXED 2026-08-11 by removing the fixed buffer rather than by chunking it. `EchoBuf` holds a `Vec`
  now: one keystroke's echo, drained by the caller immediately after `feed` returns, so the
  allocation is short-lived and bounded by what the editor can emit for one edit. Chunked drainage
  is the right shape for a sink that must not allocate; this one already lives in a crate that
  allocates its history, and a buffer that silently truncated an escape stream was the actual harm.

  `a_full_line_recall_reaches_the_serial_mirror_whole` types a thousand columns and presses Ctrl+U.

- [x] **The editor breaks as soon as the edited line wraps.** It moves the cursor by repeating
  `\x08`, and `Screen`'s backspace stops at column 0 - it never steps back onto the previous row.
  So on an 80-column terminal, a command long enough to wrap leaves Home, Backspace and mid-line
  editing moving `Ld.cursor` while the caret stays stuck on the last physical row: buffer and screen
  diverge, and every subsequent edit is drawn in the wrong place.
  FIXED 2026-08-11 in the screen rather than the editor, which is where the information is. A
  backspace at column 0 steps onto the previous row when THIS SCREEN marked that row as continuing
  into this one - reverse wrap over a soft wrap, and only over a soft wrap, so a backspace at the
  start of a real line still stops where the line starts.

  That fixes Home, Backspace and mid-line editing together, because all of them move the caret by
  repeating `\x08`. `backspace_steps_back_over_a_soft_wrap` checks both directions of the rule.

  A line editor cannot be display-agnostic. It needs the terminal width and the prompt's start
  column so it can address the logical line as a rectangle - which is also what makes a correct
  redraw after a resize possible.

- [x] **Cooked mode accepts only `0x20..=0x7e`.** Everything from `0x80` up is dropped by
  `Ld::feed`, so this terminal renders Czech perfectly and cannot accept a single accented character
  as INPUT. It already shows: an unbracketed paste is delivered byte by byte through the same path,
  so pasting `příliš žluťoučký kůň` silently loses every non-ASCII byte. Admitting bytes over 0x7f
  is not enough - the editor must know UTF-8 boundaries, or Backspace deletes one third of a
  character.

  FIXED 2026-08-11, both halves - admitting the bytes was not enough and the finding says so.
  `feed` takes `0x80..=0xff` as well, and the EDITOR knows UTF-8 boundaries: `backspace` and
  `delete` remove a whole character, `left` and `right` step over one, and the echo counts COLUMNS
  rather than bytes, so one character is one cell however many bytes it took. `char_start` stops
  after four steps, because a lone continuation byte is something the medium can produce.

  `cooked_mode_accepts_the_characters_the_screen_can_show` types `příliš žluťoučký kůň` and requires
  every byte to arrive, then presses Backspace once and requires the whole `ň` to go and the line to
  still be text.

- [x] **Three small robustness edges in the input parser.** `Ld.csi_param` is a `u8` accumulated
  with `wrapping_mul`/`wrapping_add`, so `CSI 259~` becomes 3 and executes Delete. `Ld::new(0)` is a
  legal public call and its first `commit` runs `history.remove(0)` on an empty vector - the config
  path filters zero today, which is protection by coincidence. And the history is a `Vec` with
  `remove(0)`, which is O(n) per commit where a `VecDeque` is the obvious shape.

  TWO FIXED 2026-08-11, one deliberately left.

  `csi_param` is a `u16` accumulated with saturating arithmetic, so `CSI 259~` is a parameter this
  terminal cannot mean rather than 3 - which executed Delete, a key nobody pressed.
  `a_csi_parameter_too_large_to_mean_anything_does_not_wrap_into_a_key` checks both that and that
  `CSI 3~` still deletes.

  `Ld::new` clamps the history bound to at least one, so the public constructor cannot be handed a
  zero that panics on the first `commit`. `a_zero_history_bound_is_not_a_panic_waiting_for_the_first_line`
  commits two lines through it.

  The `Vec` with `remove(0)` stays. It is O(n) per commit over a history of at most a few hundred
  short lines, once per Enter - a `VecDeque` is the better shape and this is not the cost that makes
  it worth changing an API for.

## Escape sequences that reach past the terminal

- [x] **Program output can change the tty's raw and echo modes.** `ESC[?9001h/l` and `ESC[?9002h/l`
  set `tty_raw_req`/`tty_echo_req`, and ConsoleService writes them straight into `ld.cooked` and
  `ld.echo`. So `cat` on a file containing those bytes reconfigures the terminal: the data a program
  prints is indistinguishable from a request the program makes.
  NOT FIXED 2026-08-11, and the reason is that a half-rule here would look like protection without
  being any. The harm is exactly as stated - `cat` on a file containing those bytes reconfigures the
  terminal - and no filter on the OUTPUT stream can fix it, because the byte stream is the one place
  where a program's data and a program's request are the same thing. Restricting it to the
  foreground process does not help: `cat` is the foreground process.

  The fix is out-of-band, and the pieces exist: every VT already has a `control` channel in
  `console_service`, which is where a mode change belongs, the way a real system uses an ioctl
  rather than stdout. What makes it more than a patch is that `lico` (`libs/terminal/lico/session.rs`)
  is the only in-tree emitter and two kernel tests assert the escape bytes appear in the output -
  `services.rs:1297` and `1300` - so the change spans the terminal library, the service protocol and
  those assertions, and should land as one piece.

  This is narrower than it first looks - the effect is confined to the VT the program already owns,
  and that program could ask for raw mode through an API if one existed. That is the actual finding:
  there is no API, so an escape sequence is doing the job of `tcsetattr`. Mode control belongs in
  the console protocol, addressed to the tty by its foreground owner, and the private sequences
  should then be dropped rather than kept as a second path to the same state.

  THE DESIGN, worked out 2026-08-11 so the next attempt starts from one. Three cheaper shapes were
  followed to the end first, and each fails for a reason worth writing down:

  - A tag on the console client channel. `render_output` takes the WHOLE message as output bytes,
    so tagging means framing every write from every program - a change to the hot path, and any
    program writing to the channel without the framing breaks.
  - A distinct IPC tag word. There is none: a message carries bytes and at most one handle
    (`Polled::Message { len, handle }`), and the handle slot is already how a capability arrives.
  - Restricting the escape to the foreground process. `cat` IS the foreground process.

  So it needs the capability the finding says does not exist. The shape that fits this system: the
  shell already holds the VT's `control` channel and already tells the console who the foreground
  job is (`SET_FG`), so it can pass a send-only control capability in the LaunchContext beside
  stdin and stdout. Then `rt` exposes `tty_set_mode(raw, echo)`, `lico` calls it instead of writing
  `ESC[?9001h` / `ESC[?9002l`, `console_service` handles `SET_MODE` next to `SET_FG` (it touches
  only that terminal's line discipline, so it belongs in `tty_fg_winsize`), `screen.rs` drops 9001 /
  9002 and the two `take_tty_*_req` accessors, and the assertions in `services.rs:1297` and `1300`
  assert the control message instead of the bytes.

  FIXED 2026-08-11, as the one piece the design says it has to be. There is now no path from a byte
  stream to the tty's modes.

  `rt::tty_set_mode(raw, echo)` sends `SET_MODE` over a send-only control capability the shell puts
  in the LaunchContext (`CAP_CONTROL`) beside stdin and stdout, and only for an INTERACTIVE
  FOREGROUND job - a pipeline stage or a background job gets no control capability, so it cannot
  reconfigure a terminal it is not driving. `console_service` handles `SET_MODE` next to `SET_FG` in
  `tty_fg_winsize`, where it touches only that VT's line discipline. `screen.rs` no longer knows
  9001 or 9002 and both `take_tty_*_req` accessors are gone, so the sequences do not set state, do
  not reach ConsoleService, and are not quietly tolerated as a second path. The four programs that
  used them - `lico`, `licoview`, `licoedit`, `ps` - and `imgview`, which the design's own list
  missed, now ask; each takes the answer as "is there a terminal to ask", and runs cooked rather
  than failing when there is not.

  `lico` stays dependency-free: mode control belongs to the PROGRAM, not to the terminal library, so
  `TerminalOptions` still describes the screen it draws on and the tools call `tty_set_mode`
  themselves. Putting it in the library was tried first and it was the wrong place twice over - it
  would have made a leaf library depend on `rt`, and it broke the dynamic build's provider set.

  The kernel test asserts the control message and, more usefully, asserts the NEGATIVE: no program's
  output ever contains `9001` or `9002` (`tests.rs:3945`). The alternate screen and the cursor stay
  escapes - those are the terminal's own state, and a program printing them affects only the screen
  it was given.

- [x] **OSC 52 from a background VT rewrites the console-wide clipboard.** `render_output` drains
  `take_clipboard_set()` and assigns `console.clipboard` OUTSIDE its `if fg` guard, so a program on
  a terminal the user is not looking at replaces what the next paste will insert. Restrict it to the
  foreground VT, and treat writing the user's clipboard as something a program is granted rather
  than something it can do by printing.

  FIXED 2026-08-11: the adoption moved inside the `if fg` guard. The clipboard is the user's, and
  the VT they are watching is the only one they could have meant. Treating it as a granted
  capability rather than something any program can do by printing is the larger version of the same
  point and belongs with the out-of-band tty-mode change above - both are "a program printed a
  request" and both want the same answer.

- [x] **The OSC buffer is 256 bytes and truncates in silence.** `osc_byte` drops every byte past the
  buffer and then dispatches whatever it kept, so an OSC 52 payload longer than the buffer decodes
  to a PREFIX of the intended clipboard text rather than being refused. Truncation must set an
  overflow flag that makes the dispatch fail; a control string that did not arrive whole was not
  received.

  FIXED 2026-08-11. Overrunning the buffer sets `osc_overflow`, and `osc_dispatch` acts on nothing
  when it is set: a control string that did not arrive whole was not received. Truncating an OSC 52
  is worse than losing it, because a clipboard set to a prefix of the intended text looks like a
  successful copy.

  `a_control_string_that_did_not_arrive_whole_is_not_acted_on` sends 400 bytes and then a payload
  that fits, so the rule is not "OSC 52 never works".

## ANSI and xterm behaviour

- [x] **The UTF-8 decoder validates shape, not encoding.** It checks lead and continuation bit
  patterns and nothing else: overlong encodings, the surrogate range and everything above U+10FFFF
  all pass into a cell. A broken continuation byte drops the partial sequence and reinterprets the
  byte, with no U+FFFD emitted - so a truncated sequence disappears rather than becoming a
  replacement character, and the invalid codepoint that reaches `push_utf8` renders as `?`, not
  U+FFFD. Decode strictly and emit U+FFFD on every malformed sequence, which is what the crate's
  own comments already promise.
  FIXED 2026-08-11. `begin_utf8` records the smallest codepoint its length may legally encode, and
  the completed value is checked against that, against the surrogate range and against U+10FFFF -
  so an overlong form, a surrogate half and a codepoint past the end of Unicode are each one U+FFFD
  instead of a cell that renders as `?` because the font lookup rejected what the decoder accepted.
  A truncated sequence emits one U+FFFD and then reinterprets the interrupting byte, where it used
  to vanish in silence.

  `a_malformed_utf8_sequence_becomes_one_replacement_character` covers five malformed shapes, the
  truncation, and a legal sequence - the last so the strictness is not simply refusing. Both halves
  watched to fail.

- [x] **`CSI 3 J` erases the screen, and every unknown erase mode erases everything.**
  `erase_display` maps 0 and 1 explicitly and `_` to the whole screen; xterm's 3 clears the SAVED
  lines - the scrollback - and leaves the display alone. So the one sequence a program uses to drop
  history instead wipes what the user is reading, and `CSI 99J` does the same. `erase_line` has the
  identical `_` arm. An unsupported mode should be ignored.

  FIXED 2026-08-11. `CSI 3 J` drops the scrollback and leaves the display, and an erase mode neither
  function implements erases nothing - in both `erase_display` and `erase_line`, which had the same
  catch-all. `an_erase_mode_this_terminal_does_not_implement_erases_nothing` covers `CSI 99J`,
  `CSI 7K` and `CSI 3J`, and asserts `CSI 2J` still clears, so the rule is not "refuse everything".

- [x] **A scroll region anchored at row 0 pollutes the scrollback.** `scroll_up` pushes rows to
  history whenever `scroll_top == 0`, never checking `scroll_bottom == rows - 1`, though the comment
  directly above says a region scroll must not reach history. `CSI 1;10r` therefore fills the
  scrollback with the top ten rows of a status pane. The row count pushed is clamped to `rows`
  rather than the region height, so `CSI 999S` in a small region can push rows that were never in
  it.

  FIXED 2026-08-11. History is reached only when the region is the WHOLE screen - `scroll_top == 0`
  and `scroll_bottom + 1 == rows` - and the count pushed is clamped to the region's height rather
  than the screen's, so `CSI 999S` in a small region can no longer push rows that were never in it.
  `a_scroll_region_does_not_reach_the_scrollback` scrolls ten lines through a three-row region and
  requires the history empty, then does the same full-screen and requires it not.

- [x] **`ESC c` is not a reset.** RIS restores SGR, cursor visibility, margins, mouse modes and
  bracketed paste, and leaves the OSC-modified palette, `default_fg`/`default_bg`, the DECSCUSR
  shape and blink, and the saved-cursor state exactly as the previous program left them. A terminal
  after a full reset should be indistinguishable from a fresh `Screen`; that is the whole purpose of
  the sequence, and it is what a shell relies on after a program crashes.

  FIXED 2026-08-11. RIS now also restores the palette and the default colours an OSC changed, the
  DECSCUSR shape and blink, the whole saved-cursor state - so a later DECRC cannot restore a
  position from before the reset - the mouse highlight, the pending wrap, and any half-parsed escape,
  CSI, OSC or UTF-8 sequence. A terminal after RIS is what a fresh `Screen` is, which is the whole

- [x] **`?47`, `?1047` and `?1049` are one code path.** All three enter and leave the alternate
  screen with the same save/restore and clear. xterm distinguishes them - which one saves the
  cursor, which one clears on exit - and ported full-screen programs depend on the difference. Also
  in `set_mode`: disabling `?1002` or `?1003` sets `mouse_mode = 0` outright, cancelling a `?1000`
  that is still notionally on.

  FIXED 2026-08-11, both halves. The buffer switch (`enter_alt_buffer` / `leave_alt_buffer`) is now
  separate from the CURSOR AND CLEARING POLICY, which is the only thing the three modes differ in:
  `?47` switches and nothing else, `?1047` clears on the way out, `?1049` saves the cursor and
  blanks the buffer on entry and restores and clears on exit. Entry-clearing was happening for all
  three, which is what stopped a `?47` program leaving and re-entering without redrawing.

  The clear on exit runs AFTER the buffer swap, because while the alternate screen is active `wrap`
  holds its flags and `alt_wrap` holds the primary's parked ones - clearing before the swap wiped
  the primary's, and the soft-wrap test said so immediately.

  The mouse modes are three booleans with the effective mode derived from them, so `?1002l` no
  longer cancels a `?1000` the program never disabled. The existing test pinned the old behaviour
  and now walks the modes off one at a time.

  `the_three_alternate_screen_modes_are_not_one_mode` covers the cursor for `?1049` and `?47` and
  the clearing for `?1047` and `?47`.

- [x] **There is no reply path, so every query sequence is silently ignored.** `csi_dispatch`

  write-back path is missing. A program asking where the cursor is waits forever. The model needs a
  reply queue the console drains into the program's input, the same shape `clipboard_set` and the

  FIXED 2026-08-11 with the reply queue the finding describes, in the shape it names. `Screen`
  records what it owes and `take_reply` drains it; ConsoleService delivers it to the VT's client as
  though the user had typed it, which is where the program asked for it. `CSI 5n`, `CSI 6n` (CPR,
  one-based) and `CSI c` (DA, answering VT102) are answered.

  The queue is bounded at 256 bytes: a program that queries faster than the console drains is asking
  for the same answer twice, and a reply nobody collects must not grow.

  `a_query_sequence_is_answered_instead_of_ignored` checks each sequence, that the reply is drained
  rather than repeated, and the bound. OSC 52's query form still answers nothing - it needs the
  clipboard, which the console holds and the model does not, so it belongs with the console-side
  half of the clipboard work above.

  whether to implement the X10 encoding or state the requirement in the terminal's documentation.)

- [x] **Bold brightens the background.** `cell_colors` passes `c.bold` to `resolve` for both

## Bounds

- [x] **Grid and scrollback allocations are unbounded and unchecked.** `Screen::new` computes
  `cols * rows` and `scrollback * cols` with no `checked_mul`, and `console.scrollback` accepts any
  positive integer from the config tree with no ceiling. `Term::new` divides the framebuffer by the
  cell size, so a surface smaller than 8x16 produces a 0x0 `Screen` - and the first `put_glyph` then
  indexes an empty `wrap` vector. The kernel checks for 0x0 after constructing one; the public API
  should not require its callers to know that. `Screen::cell` is public and indexes without bounds
  checks too, where `set_cell` returns quietly.

  FIXED 2026-08-11. `Screen::new` clamps the grid to at least one cell and at most `MAX_COLS` x
  `MAX_ROWS`, so a surface smaller than one cell is a small screen rather than a 0x0 grid whose
  first `put_glyph` indexes an empty vector, and no multiplication can overflow. `Screen::cell`
  answers a blank outside the grid instead of panicking - `set_cell` already returned quietly for
  the same coordinates.

  `a_degenerate_geometry_is_a_small_screen_rather_than_a_panic` builds a 0x0 and a `usize::MAX`.

- [x] **State the real per-VT cost, and cap something.** `SCROLLBACK_ROWS` is 1000 and a `Cell` is
  16 bytes, so at 1024x768 (128 columns) the scrollback ring alone is 1.95 MB and a VT costs
  **2.15 MB**; at 1920x1080 it is **4.17 MB**. VTs are created on demand with no cap - the code says
  so deliberately - so console memory is unbounded in a service whose heap starts at 1 MB and grows.
  The comment in `screen.rs` still describes a four-VT cap and a fixed 1 MB heap, and `P02M0006` still
  documents `SCROLLBACK_ROWS = 100` and "about 196 kB per VT"; both were true and are not. Decide
  the policy - a VT ceiling, a scrollback ceiling, or an explicit statement that this memory is
  operator-configured - and make the three places agree.

  ANSWERED 2026-08-11 by capping the thing that grows: `MAX_SCROLLBACK_BYTES` is 2 MB per VT and the
  configured row count is clamped to what fits it AT THE CURRENT WIDTH. The per-VT cost therefore no
  longer depends on the display's resolution - it was 2.15 MB at 1024x768 and 4.17 MB at 1920x1080
  for the same configuration, which is what made the figure unanswerable.

  A VT ceiling is the other half and is deliberately not added here: it is a console policy, not a
  grid one, and belongs where VTs are created. What this fixes is that each one now has a stated
  price.

## Unicode beyond the codepoint

- [x] **The cell model assumes one codepoint is one cell.** Every decoded codepoint goes to
  `put_glyph` and advances one column, which is correct for the precomposed Latin the font covers
  and wrong for combining marks, zero-width characters and East Asian wide characters. This is the
  one finding that is a design decision rather than a defect: a `wcwidth` equivalent plus a
  representation for a base glyph with combining marks is real work, and a bitmap-font VT console
  may reasonably decide not to do it.

  NOT DONE 2026-08-11, deliberately, and the finding says why better than a fix would: it is a
  design decision rather than a defect, and a bitmap-font VT console may reasonably decide not to
  do it. Combining marks need a representation for a base glyph plus its marks - a `Cell` is
  currently one codepoint and 16 bytes, and the scrollback's per-VT cost is a number this milestone
  has just pinned down - and East Asian width needs a `wcwidth` table, which is a data file this
  tree does not have and a font that cannot render what it would admit.

  What HAS changed around it: the decoder is strict, so a malformed sequence is one U+FFFD rather
  than an invented codepoint, and the line discipline counts characters rather than bytes. The gap
  that remains is real and is now the only one of its kind here.

  What is not reasonable is leaving it unsaid. Either implement width handling, or document the
  supported subset the way the ISO9660 backend documents its 2048-byte block size - as a product
  decision, not an omission.

## Order

`Raster` first: it is the only finding that breaks a Rust guarantee rather than a terminal
convention, and it is a contained change to a constructor and its two callers.

Then the state model, as one piece of work rather than four: `wrap_pending` as a field, cells and
dirty marks and wrap flags as one `ScreenBuffer` held twice, and a resize that preserves what it
should. Doing these together is what makes them small; done separately, each has to work around the
other two.

Then the three failures a user meets in ordinary use - the unbounded background scroll queue, the
truncated echo buffer, and the line editor on a wrapped line - and after them the tty mode control
API, which is what lets the private escape sequences be deleted rather than merely guarded.

ANSI and xterm conformance last, in the order a ported program notices it: strict UTF-8, the reply
path, ED 3, RIS, the alternate-screen variants, then the renderer's colour and caret details.

## Reopened: three new invariants, and the code that does not hold them

A second audit - 2026-08-12, against this tree at `fcb821b` - reading the repairs rather than the
finding list. Every claim below was checked against the code first.

The architecture is no longer the finding, and that is the headline. `Raster::new` is `unsafe` with
a written contract and validates the mode line; the tty modes moved out of band onto the control
capability and the private escapes are gone; the scroll queue has a bound and a full-repaint
fallback; `EchoBuf` no longer truncates; the UTF-8 decoder checks overlong forms, surrogates and the
upper bound; OSC 52 refuses an overflowed payload instead of accepting a shortened one; `resize`
rebuilds logical lines and lays them out at the new width, which is what the comment had always
claimed and the code had never done. The suite roughly doubled.

What follows is what the new invariants do not yet cover.

### `pending_wrap` is cleared by sequences that move nothing, and kept by ones that move

The model is right: the cursor stays inside the grid and the last column sets a deferred wrap. Two
things clear it wrongly.

`csi_dispatch` clears it unconditionally, before the dispatch
(`src/term/src/screen.rs:1150`), under a comment saying "a sequence that moves or repositions the
cursor ends any deferred wrap". Most CSI sequences do not move the cursor. `CSI m` (SGR), `CSI n`
(DSR), `CSI c` (DA), `CSI q` (cursor style) and the mode sets all pass through it. So on an
eight-column screen:

```
12345678   ESC [ 31 m   X
```

the `X` belongs at the start of the next row, and lands over the `8` instead. Colour changes between
a full line and the next character are not exotic - that is what a prompt does.

The other direction: `ESC D` calls `line_feed()` (`src/term/src/screen.rs:1073`) and `line_feed`
does not touch `pending_wrap` (`src/term/src/screen.rs:892`). So a full line followed by `ESC D`
followed by a glyph feeds twice and the character lands two rows down. `ESC M`, `ESC E` and
`enter_alt_buffer` - which sets `row` and `col` to zero at `src/term/src/screen.rs:1496` - have the
same shape.

The test written for this finding covers a full line and a cursor-move CSI, which is the case that
works.

- [x] **Name the rule, then apply it in one place.** Clearing `pending_wrap` belongs to the
  operations that actually change the cursor position or explicitly reset autowrap - not to the
  entry of `csi_dispatch`, and not omitted from `line_feed` and the ESC cursor moves. A helper the
  cursor-moving paths call is what makes the two sides agree.

  DONE 2026-08-12. `cursor_moved()` is the rule, and it is called by the operations that actually
  assign `row` or `col` - the CSI cursor moves, DECRC, `line_feed`, `reverse_line_feed` and the
  alternate-screen switch - and by nothing else. The unconditional clear at the entry of
  `csi_dispatch` is gone.

- [x] **Tests for the two shapes the current one misses**: a non-moving CSI between the last column
  and the next glyph, and `ESC D` / `ESC M` / `ESC E` after a full line.

  DONE 2026-08-12. `a_sequence_that_moves_nothing_does_not_end_a_deferred_wrap` covers SGR, DSR, DA,
  the cursor style and a mode set between a full line and the next glyph;
  `an_esc_cursor_move_after_a_full_line_feeds_once` covers `ESC D`, `ESC E` and `ESC M`. Both were
  watched to fail with the old behaviour put back.

  One correction the tests forced: IND and RI keep the COLUMN, so the character lands at (7, 1) and
  (7, 0) rather than at the start of the row. The defect was the second feed, not the column.

### One defect with three symptoms: the accessors do not know which screen is active

`global_glyph` reads `self.primary[...]` for live rows (`src/term/src/screen.rs:1778`).
`global_wrap` reads `self.wrap[...]` (`src/term/src/screen.rs:1788`). `enter_alt_buffer` swaps
`wrap` with `alt_wrap` (`src/term/src/screen.rs:1488`). So while the alternate screen is active,
those two functions describe different screens - primary glyphs, alternate wrap flags - and every
caller of both inherits the contradiction:

- **`selection_text`** calls `global_glyph` (`src/term/src/screen.rs:500`) and nothing else, so a
  selection made over a full-screen program highlights the alternate cells and copies the shell text
  underneath them. What is seen and what is copied are different, which is the original finding,
  unchanged.
- **`resize`'s reflow** reads primary cells with `self.wrap.get(r)`
  (`src/term/src/screen.rs:612`), so during alt it reflows the primary buffer according to the
  alternate screen's line structure - and finds the cursor with `self.row`/`self.col`
  (`src/term/src/screen.rs:613`), which is the full-screen program's cursor mapped onto primary
  logical lines. It then assigns `self.wrap = new_wrap` and `self.alt_wrap = vec![false; new_rows]`
  unconditionally (`src/term/src/screen.rs:700`), so after a resize during alt the two vectors have
  swapped meanings.
- **`reset` (RIS)** sets `self.alt_active = false` directly (`src/term/src/screen.rs:1567`) instead
  of going through `leave_alt_buffer`, which is the only place that swaps the vectors back. A RIS
  arriving while alt is active therefore leaves `wrap` holding alternate flags with the primary
  screen live, and `clear()` then runs against them.

And `?47` has a fourth: the cell buffer is deliberately preserved across leave and re-enter
(`src/term/src/screen.rs:1492`) while its wrap flags are cleared on every entry
(`src/term/src/screen.rs:1489`), so a program that leaves and returns gets its characters back
without their line structure.

- [x] **Make the two screens two objects.** A `ScreenBuffer { cells, wrap }` and an `active`
  selector, so `global_glyph` and `global_wrap` read the same buffer by construction and nothing
  swaps vectors by hand. Every symptom above is the same missing question - which screen is this? -
  and one type answers it once.

  DONE 2026-08-12. `ScreenBuffer { cells, wrap }`, with `primary`, `alt` and `alt_active`, and
  `screen()` / `screen_mut()` picking the live one. Nothing swaps a vector by hand any more, which
  is what all four symptoms came from - and `clear_alt_active` / `clear_alt`, which differed only in
  which vector they reached through the swap, collapsed into one function.

- [x] **Then fix the three call sites that had to know**: `selection_text` reads the active screen;
  `resize` reflows the primary buffer with the primary flags whichever screen is showing, and maps
  the cursor to whichever buffer it belongs to; `reset` goes through `leave_alt_buffer` and clears
  the alternate cells as well as the primary ones.

  DONE 2026-08-12. `view_cell` and `global_glyph` read the ACTIVE screen, so a selection over a
  full-screen program copies what is shown; the reflow reads the primary buffer with the PRIMARY
  flags whichever screen is up, and maps the cursor only when it is the primary's; and RIS goes
  through `leave_alt_buffer` and then `clear_alt`, so it returns a clean primary and a clean
  alternate.

- [x] **Tests for what the current alt tests do not assert**: that a resize during alt leaves the
  primary intact when the program exits, that RIS during alt returns a clean primary and a clean
  alternate, and that `?47` preserves wrap flags along with cells.

  DONE 2026-08-12: `a_resize_during_the_alternate_screen_leaves_the_primary_intact`,
  `a_reset_during_the_alternate_screen_returns_a_clean_primary_and_a_clean_alternate`,
  `mode_47_preserves_wrap_flags_along_with_cells` and
  `a_selection_over_the_alternate_screen_copies_what_is_shown`. All four watched to fail.

  The resize one needed its fixture strengthened before it proved anything: with both screens
  soft-wrapping the same way, reading the wrong screen's flags produced the same answer. The
  alternate screen now has two hard-broken lines against the primary's one wrapped one.

### The line discipline is character-aware in some places and byte-aware in others

The decoder half is done - bytes at or above `0x80` reach the line, and Backspace, Delete, Left and
Right respect UTF-8 boundaries. The cursor arithmetic did not follow.

- **Home** moves left by `self.cursor`, a byte offset, so `čau` (four bytes, three cells) moves the
  cursor four columns.
- **`replace_line`** erases with `for _ in 0..self.len { e.put(b"\x08 \x08") }`, again bytes - so
  Ctrl+U or a history recall over a line containing any multi-byte character erases past the start
  of the line and into the prompt.
- **Mid-line insertion** echoes the suffix immediately and then moves back by `self.len -
  self.cursor` bytes; and because the echo happens per byte, the screen can receive a lead byte
  followed by the suffix before the continuation byte arrives - a valid line in the editor's buffer
  and a replacement character on the display.
- **Tab completion** computes its longest common prefix over bytes, so two names whose first
  multi-byte character shares a lead byte can produce a prefix ending inside a code point.

- [x] **One unit for the editor: the cell.** Cursor distances, erase counts and redraw widths all
  measured in display cells, with byte offsets kept only where the buffer is indexed. The helper
  that counts columns already exists; what is missing is every remaining use of `self.len` and
  `self.cursor` as though they were column counts.

  DONE 2026-08-12. Home steps back `columns(0, cursor)`, `replace_line` erases `columns(0, len)`
  times, mid-line insertion moves back by `columns(cursor, len)`, and tab completion backs its
  common prefix off to a character boundary - two names whose first multi-byte character shares a
  lead byte used to produce a prefix ending inside a code point. Byte offsets remain only where the
  buffer is indexed.

- [x] **Echo a character, not a byte.** Hold an incomplete sequence until it is complete before
  anything reaches the screen.

  DONE 2026-08-12. `char_is_complete` reads the lead byte's own length and nothing is echoed until
  the character under the cursor is whole - so a mid-line insertion no longer puts a lead byte on
  the display, then the suffix, then the continuation bytes.
  `a_multi_byte_character_reaches_the_screen_whole` asserts the lead byte alone draws nothing.

### `CSI 3J` returns to the live screen without repainting it

The erase logic is right - mode 3 clears the scrollback and an unimplemented mode erases nothing
(`src/term/src/screen.rs:1245`). What it also does is `self.view_offset = 0` and return, with no
`mark_all_dirty()`. `snap_live`, which makes the same transition, does mark.

So a user reading history with Shift+PageUp when a program sends `CSI 3J` gets the model switched
to the live screen while the renderer still believes the visible cells are clean, and the
framebuffer keeps showing pieces of the scrollback view.

- [x] **Repaint when the view moves.** Leaving history is what requires it, wherever it happens -
  which is an argument for `3J` calling the same helper `snap_live` does rather than open-coding the
  three assignments.

  DONE 2026-08-12. `CSI 3 J` calls `snap_live`, which is the helper `Shift+PageUp`'s exit already
  used, rather than open-coding `view_offset = 0` with no `mark_all_dirty`.

### `resize` is not bound by the limits `new` is

`Screen::new` clamps to `MAX_COLS` and `MAX_ROWS` and sizes the scrollback from
`MAX_SCROLLBACK_BYTES / row_bytes` (`src/term/src/screen.rs:217`). `Screen::resize` clamps to the
`max_cols`/`max_rows` its caller passes (`src/term/src/screen.rs:582`), and `Term::resize` derives
those from the surface geometry (`src/term/src/render.rs:355`) - so the ceiling after a resize is
whatever the framebuffer is, not what the module declares. The scrollback is then reallocated as
`sb_cap * new_cols`, so the byte budget computed once at construction stops holding the moment the
width changes: a terminal created narrow keeps its generous row count and multiplies it by a much
larger width.

- [x] **One function for geometry and budget**, called by the constructor and by `resize`, so the
  declared maximums mean the same thing at both ends of a terminal's life.

  DONE 2026-08-12. `geometry(cols, rows, scrollback, max_cols, max_rows)` is called by the
  constructor and by `resize`, which now also clamps to the module's `MAX_COLS`/`MAX_ROWS` on top of
  the caller's and recomputes `sb_cap` from the new width - the byte budget stopped holding the
  moment a terminal changed width, because `sb_cap` was carried over and multiplied by `new_cols`.

### The reply path exists and two things still do not use it

`reply: Vec<u8>` and `take_reply` are real (`src/term/src/screen.rs:158`, `:396`), and DSR and DA

### The `pending_wrap` rule is stated in one place and broken in three

`cursor_moved` (`src/term/src/screen.rs:1247`) states it as plainly as it can be stated: "every path

### A resize during the alternate screen gives the program the wrong buffer's cursor

The cell half is fixed - the reflow reads `self.primary` explicitly (`src/term/src/screen.rs:695`),
and the alternate is copied as the rectangle it is. The cursor half is not.

`cursor_at` is recorded only when `!self.alt_active` (`:700`), which is right: during alt, `row`/`col`
belong to the full-screen program and mapping them onto the shell's logical lines would be nonsense.
But nothing takes the other branch. `cursor_row_out` stays `None`, so the fallback at `:766` fires -
"the end of the content, which is where a shell prompt is" - and `:798` assigns it to `self.row` and
`self.col`, which during alt ARE the program's cursor. A window resize therefore teleports a
full-screen program's cursor to a position computed from the shell's scrollback.

The second half is `?1049`. It saves the primary cursor on entry (`:1578`), the resize reflows the
primary and does not touch `saved_row`/`saved_col`, and `restore_cursor` (`:1536`) only clamps to the
new size. After a width change the shell comes back to a cell that is no longer where its prompt is.

The root cause is one thing and it should be named as such: `Screen` has ONE cursor - `col`, `row`,
`saved_col`, `saved_row` - shared by two buffers that are otherwise now properly separate. The
`ScreenBuffer` split stopped at the cells and the wrap flags. Every symptom above is that split being
incomplete.

- [x] **Move the cursor into `ScreenBuffer`,** so each screen owns its own position and the switch is
  a selector rather than a save/restore. That is the same change that closed the wrap-flag class and
  it closes this one for the same reason.

  live one did not. Parking the live cursor per buffer was written first and then reverted, because
  it silently changed `?47`: the `?47` case in `the_three_alternate_screen_modes_are_not_one_mode`

  program using `?47` relies on, since it saves and restores the cursor itself. xterm shares the
  live cursor between the screens and indexes the SAVED one by screen (`sc[]`), and that split is
  what both symptoms here needed: the resize half is fixed by clamping the live cursor during alt
  rather than deriving one from the primary, and the `?1049` half by giving each buffer its own

  better than a position from a buffer it cannot see.

  DONE 2026-08-13. During alt the live cursor is clamped to the new geometry instead of taking the

### A terminal reply can stall the entire console loop

- [x] **Bound the reply send.** `try_send_outcome` and drop the reply on `Stalled` is defensible - a

- [x] **Say what the console's rule is for writing to a client, once.** Three call shapes exist today

### The scrollback depth ratchets down and never comes back

`try_send` while user input keeps its deadline, so a client that never reads cannot freeze the
console; the alternate screen's saved cursor is per-buffer and reflows correctly; the scrollback
ratchet is gone; and `RawSink` no longer memmoves on every partial drain. Those are closed.

What this pass finds is a repair that made the caret computable and then computed it in a case where
the answer is a column that does not exist yet.

### `move_left(0)` addresses the cell after a deferred wrap, and CUP cancels the wrap

`Ld::insert` echoes the character and then steps the caret back over whatever follows the cursor
(`src/term/src/ld.rs:396`):

```rust
self.move_left(self.columns(self.cursor, self.len), e);
```

Typing at the END of a line - which is most typing - has `self.cursor == self.len`, so that count is
zero. `Echo::move_left(0)` pushes no backspaces and calls `move_left_screen(0)`, which has no
early return for zero (`:146-158`):

```rust
let here: usize = t.screen.caret_index();
let target: usize = here - n;
self.cup(target / cols, target % cols);
```

`caret_index` deliberately includes the deferred wrap (`src/term/src/screen.rs:415`), and its comment
says why: "a glyph that filled the last column leaves the caret parked on it with the wrap owed, and
the editor has already counted that column as printed". That is the right definition for MEASURING.
It is the wrong thing to feed back into an absolute move, because CUP is a cursor movement and
`csi_dispatch`'s `b'H'` arm calls `cursor_moved()` (`:1444-1450`), which clears `pending_wrap`.

On an eight-column screen, typing `12345678`:

```
put_glyph('8')      -> col = 7, pending_wrap = true          (correct)
move_left(0)        -> caret_index() = 0*8 + 7 + 1 = 8
                    -> CUP(row 1, col 0)                      (cursor_moved: wrap cancelled)
put_glyph('9')      -> prints at row 1 col 0
```

The glyph lands where it would have landed, and `wrap[0]` is never set - because only `put_glyph`'s
own deferred-wrap branch sets it, and that branch no longer runs. So the row is not marked as
soft-wrapped: `TextSink` renders a hard newline where the user typed one continuous line, and
reverse-wrap backspace has no row to step onto.

On the LAST row it is worse. `target / cols` is `rows`, which the CUP arm clamps to `rows - 1`, so
the caret returns to the start of the row it is already on and the screen never scrolls. Subsequent
characters overwrite the last row instead of scrolling the terminal.

- [x] **Make `move_left_screen(0)` a no-op.** Zero cells to the left is the caret where it already is,
  and the only way to express that without disturbing the screen is to not emit anything. Everything
  else about the absolute-addressing repair is right and stays.

- [x] **A test that types past the width with no `Home` in it.** The long-line test added last round
  writes fifty characters into an 8x4 grid and then presses `Home`, and `Home` sets `self.cursor = 0`
  before moving - so `back` is zero and neither of this section's two defects is on its path. What is
  missing is the ordinary case: type nine characters on an eight-column screen and assert `wrap[0]`,
  then type past `rows * cols` and assert the screen scrolled.

### `repaint` walks back two characters per column

The long-line fallback opens its window one screenful behind the cursor (`ld.rs:572-576`):

```rust
let back: usize = self.columns(0, self.cursor).min(cols);
let mut start: usize = self.cursor;
for _ in 0..back {
    start = self.char_start(start.saturating_sub(1));
}
```

`char_start` decrements before it tests (`:453-464`), so it already steps back one whole character -
which is what its other four callers want, `self.cursor = self.char_start(self.cursor)` in the
backspace path among them. Subtracting one more before calling it steps back two.

With an ASCII line, `cursor = 100` and `cols = 80`: `back` is 80, the window should open at byte 20,
and the loop reaches 0 after fifty iterations and stays there. The reprint then starts a screenful
earlier than intended and `e.cup(back / cols, back % cols)` puts the caret `back` cells from the
start of the reprint - so the rendered caret and `self.cursor` disagree, which is the exact invariant
this fallback was written to restore.

- [x] **`start = self.char_start(start);`** - one character per column, the way every other caller
  uses it. Worth a line in the comment too, because the doc comment above `char_start` describes it
  as returning "`at` itself unless the byte before it is a UTF-8 continuation", and it never returns
  `at`: it always steps back one character. Four callers depend on the behaviour and the fifth was
  written against the comment.

### `Screen::clear` leaves a deferred wrap behind

`cursor_moved`'s comment states the invariant in the strongest terms the file has (`screen.rs:1403`):

> So every path that actually assigns `row` or `col` calls this, and nothing else does.

`Screen::clear` assigns both and does not (`:732-746`). It is reachable from production, not only from
the public API: `ConsoleService` calls `t.screen.clear()` when a VT is reused for a fresh shell
(`src/user/services/core/src/console_service.rs:1657` and `:1814`). So a shell whose last output
filled the final column leaves the wrap owed, `clear` resets the cursor to the origin, and the new
shell's first prompt character takes `put_glyph`'s deferred-wrap branch and starts on row 1.

- [x] **Call `cursor_moved()` in `clear`,** after the two assignments. One line, and it restores the
  invariant its own comment claims - which is worth more than the bug, since the next path that
  assigns `row` will be written against that sentence.

- [x] **Audit the other assignments to `row` and `col` against that sentence** while it is being
  fixed, since the claim is universal and has now been wrong twice. A test that drives every public
  method which can move the cursor and asserts `pending_wrap` afterwards would make the sentence
  checkable rather than asserted.

## Fifth audit (2026-08-15)

An outside review of `src/term` after the fourth audit's fixes. It confirms all three - the
`move_left(0)` regression, the `repaint` double step and `Screen::clear` - as properly implemented,
notes that `restore_cursor` was found and fixed beyond what was asked, and raises one correctness
finding plus two tidyings. All hold.

- [x] **Arrowing left off the top of a long line still separated the buffer from the caret.**

  DONE 2026-08-15. `move_left` was added last round precisely because a reverse-wrap backspace steps
  onto the previous physical row only while there IS one: once a command line's first row has
  scrolled into the scrollback the caret reaches the top-left and stops, so a bare backspace moves
  nothing while the buffer moves anyway. `home` was given that path. `left` was not, and CSI `D`
  goes straight to it.

  So the slower way to reach the same place still had the defect - and it is the more likely way,
  because holding Left is what somebody does when they are looking for a character rather than
  jumping to the start. `left` now moves the buffer first and calls `move_left(1)`, which is
  `home`'s shape and `home`'s stated reason: a repaint prints the line from the cursor, so the
  cursor has to be where the caret is going before it runs.

  MEASURED RATHER THAN ASSUMED, and the first attempt at the test proves why that matters. Thirty-
  five presses on the fixture land the caret EXACTLY on the top-left - the last press before the
  one that fails - so a test written to that number passed on the broken code. Instrumenting it
  showed the real behaviour: with the defect the caret reads (0,0) for every press past the top
  while the cursor drops 15, 14, 13, 12, 11, 10; with the fix the repaint re-opens the window and
  the caret tracks. The test presses forty times and asserts both that the caret is not pinned and
  that the cell before it holds the character before the cursor. Watched failing on the old `left`.

  It also closes the coverage gap the audit names: this is the first test to reach `repaint` with a
  NON-ZERO step back. `home` sets the cursor to zero before moving, so the backwards walk whose
  off-by-one was fixed last round ran zero times on the only path that reached it.

- [x] **Two internals were public for the tests' benefit.**

  DONE 2026-08-15. `wrap_pending` and `row_wrapped` are `pub(crate)`: the tests that need them live
  in this crate, and a consumer that could read the deferred-wrap flag would be writing against how
  wrapping is implemented rather than against what the terminal displays.

- [x] **The invariant was written more absolutely than it is true.**

  DONE 2026-08-15. "Every path that actually assigns `row` or `col` calls this, and nothing else
  does" is falsified by a path that is CORRECT: `resize` assigns both and then settles the wrap
  itself, because a reflow is not a cursor movement and what it owes depends on where the text ended
  up. The rule is now written as the distinction that matters - a printable advance is where a
  deferred wrap comes from and must not cancel it; anything that puts the cursor somewhere must -
  which is what the code needs and what a new mover should be checked against.
