# M0139 - LiberMemFS: a writable filesystem that lives in memory

Every volume this system can mount is backed by a medium: LiberFS on a disk, FAT on removable
media, ISO9660 and UDF on optical images. There is nowhere to write that does not survive a
reboot and does not cost a disk write - no `/tmp`, and no place for state a service needs only
while it is running.

`LiberMemFS` is that place: files held directly on the heap, no block layer, no on-disk format,
rebuilt empty on every boot.

- Done when: `vol://ram` and `vol://tmp` mount and serve reads, writes, directories and deletes
  through the same `FileSystem` trait as every other backend; the two differ only in how their
  memory is charged; both appear in the test system beside the ISO and UDF volumes; and the
  suite is green on all three architectures.

## Why not LiberFS on a RAM block device

The cheap answer was to implement `BlockDevice` over a memory buffer and format LiberFS onto it -
maybe fifty lines, and everything already works. It was the recommendation here until the code
was actually measured on 2026-08-02, and the measurement changed the answer:

| LiberFS module | lines | needed in RAM? |
| --- | --- | --- |
| `blkalloc` | 970 | no - the heap allocates |
| `txn` | 810 | no - there is no crash to recover from |
| `lib` | 796 | mostly no - superblock, on-disk structures, checksums |
| `dir` | 543 | the idea, but a map rather than a B+tree |
| `fsops` | 511 | the idea, simpler |
| `snapshot` | 329 | no |
| `fsck` | 220 | no - it is rebuilt every boot |
| `inode` | 167 | the idea, simpler |

LiberFS is 4346 lines of implementation (plus 2495 of tests). Reusing it in RAM means carrying a
block allocator, a transaction log and a checker that protect against a medium that is not
there, to reach data the CPU can already address. The "free, already tested" argument is thinner
than it looks: much of that test suite covers durability, which is not a property RAM has.

A native implementation is estimated at 400-700 lines against a nine-method trait, plus tests.

The other difference is what the fixed size means. A RAM DISK reserves its whole size whether or
not anything is stored in it. A memory filesystem holds only what is in it, and a limit is a CAP
rather than a reservation - which is the distinction this milestone builds on below.

## One filesystem, two allocation policies

`vol://ram` and `vol://tmp` are NOT two implementations. Files, directories, path resolution and
every trait method are identical; the only difference is when their memory is charged, and the
system already has the mechanism for that in per-Domain accounting (`Domain::memory()`, and
`PROP_MEMORY_LIMIT`).

| | `vol://ram` - reserved | `vol://tmp` - capped |
| --- | --- | --- |
| charged | at mount | at write |
| guarantees | the space is there | the space may be there |
| when memory is short | the MOUNT fails | the WRITE fails |
| unused space | held | not taken in the first place |
| suits | state that must not fail because something else took the memory | scratch, where waste is worse than an occasional refusal |

Two separate implementations would duplicate directories, paths, reads and writes to express one
condition. The policy belongs at mount time, and the accounting belongs to the Domain that owns
the volume - not to a second filesystem.

## M0139a - The filesystem

- [x] Implement `LiberMemFS` in `src/fs/libermemfs` as `no_std` + `alloc`: a file is a heap allocation, a
  directory is a map of names, and nothing is encoded for a medium. It implements the storage
  service's `FileSystem` trait directly, not `fs_core::BlockDevice` - there is no block device
  under it.

- [x] Bound it deliberately: a maximum file size, a maximum entry count and a maximum path depth,
  refusing past each rather than growing without limit. A filesystem that can exhaust the kernel heap is a
  denial of service.

- [x] Cover the cases a fresh implementation gets wrong: writing into the middle of a file,
  truncating, deleting an open file, a directory that is not empty, a path that walks past the
  root, and names that collide only after normalisation.

## M0139b - The two policies

- [x] Charge a reserved volume at mount and a capped volume at write, both against the owning
  Domain's memory counter.

- [x] Prove the difference rather than assert it: mounting a reserved volume larger than the
  Domain's remaining budget must FAIL AT MOUNT, and a capped volume of the same size must mount
  and then fail at the write that crosses the limit.

## M0139c - In the test system

- [x] Mount both beside the existing volumes in the scenario harness, the way `vol://iso` and
  `vol://udf` already are: `vol://ram` reserved and `vol://tmp` capped, granted through the same
  `volumes` capability bundle with their own tags (`RAM`, `TMP`) so the bundle keeps sending a
  fixed number of messages in a fixed order.

- [x] One end-to-end test that writes through a tool, reads it back, and proves the volume is
  EMPTY after a restart - the property that distinguishes it from
  every other volume.

Done 2026-08-02, about 260 lines of implementation against a nine-method trait plus 9 unit
tests - under the 400-700 estimate, and the difference is exactly what RAM does not need.

Wiring the two volumes into the boot chain cost far more than the filesystem did, and the
reason is worth recording. Growing the `volumes` capability bundle from five entries to seven
required changes in SEVEN independent places: the sender in PermissionManager, the shared
`VolumeSet`, twelve tools that read the bundle without it, three harnesses in `tests.rs`, eight
sites in `dynamic.rs`, and the expected service count in `boot.rs`. None of them knows about
the others, and each carries the message count implicitly. Every miss surfaced somewhere else
entirely - a hung `imgconv`, an `imgview` with no surface, a missing `mkdir` confirmation. The
fix for the underlying problem is recorded as an item in M0132: the bootstrap sequence needs a
length or a terminator.

## Verified

- [x] Green on all three architectures, and the boot chain comes up on each: x86_64 153,
  aarch64 145, riscv64 146.

Two defects were found by re-reading the finished implementation rather than by any test, and
both were in the properties this milestone promises:

- A write whose allocation failed had ALREADY replaced the entry with an empty file, so a
  refused write destroyed what was there. The bytes are now built first and inserted once they
  exist, so no ordering remains where a failure can truncate the previous contents.
- The reservation could only shrink. Deleting or shrinking a file returned its memory to the
  heap instead of to the reservation, so a reserved volume kept reporting its capacity while no
  longer holding it - and a later write could fail for memory something else had taken. That is
  the ONLY thing separating the two policies, so losing it silently made the reserved volume
  worse than not having one. The reservation is now resynced after every mutation.

Two further reviews found two more, both in the accounting rather than the tree:

- `resync_reservation` regrew the buffer with `Vec::resize`, which ABORTS on allocation failure
  rather than reporting it - a crash in the storage service where a degraded guarantee would do.
  It now uses `try_reserve_exact` and leaves the volume holding less, visibly, if the memory
  cannot be had.
- A write allocated the file bytes BEFORE releasing the reservation, so both were outstanding at
  once and a volume at its capacity needed twice its capacity to write into itself. That is the
  precise failure the reservation exists to prevent, so the guarantee did not hold at all. The
  bytes are now released first, and the release is undone if the write is then refused.

A fourth review found a fifth, and it was a hole in the fix for the fourth: the reservation is
released before the file is allocated, but `parent_mut` can still refuse afterwards - an absent
parent, or a file used as a path component - and returning through `?` there walked past the
resync. The volume then held less than its capacity permanently, with nothing stored to account
for it.

Five defects across four reviews, three of them in the reservation accounting, and each of the
last three was found only after the previous one was fixed. None would have been caught by the
tests written alongside the code, because those were written from the same picture of it.

What changed the return was the test written for the fifth: instead of one test per known
defect, it asserts the INVARIANT - `footprint + reserved == capacity` - across six different ways an
operation can be refused. That form catches defects nobody thought of, and it immediately did.
Verified to have teeth by reverting the fix and watching it fail.

A fifth review found a sixth defect, of a different kind: `shrink_to_fit` reallocates and COPIES
what it keeps, so every write to a reserved volume was memcpying what remained of the
reservation - megabytes per write, to preserve zeros nothing reads. The reservation is now
dropped and reallocated rather than resized, which also stops the old and new blocks from being
outstanding together. The same pass strengthened the write path: it now releases the WHOLE
reservation rather than the difference, so how much is held stops mattering to whether a write
can proceed - it could fall short after a best-effort regrow.

A sixth review found a seventh, and this one was a hole in the bound itself: names were not
counted against the capacity. Only file contents were, so a volume could be filled with long
names holding nothing - a megabyte in the worst case, a QUARTER of a 4 MiB reserved volume - and
`mkdir` had no capacity check at all, a directory storing no data. The capacity now bounds the
footprint (data plus names); `used()` still reports data, because that is what the word means to
a caller, and `free()` subtracts both. Ten test expectations had to be recomputed, which is the
clearest evidence the change was real rather than cosmetic.

A seventh review found an eighth, and it was a hole opened by the seventh fix itself. Counting
names made `mkdir` and `rmdir` reservation-affecting operations, which they had never been, and
neither was updated: `mkdir` allocated a name while the reservation still held those bytes, and
`rmdir` freed one without giving it back. So the invariant broke in BOTH directions on ordinary
directory work - the first time any defect here did. The existing invariant test could not see it
because it exercised only files, and the name-accounting test used a capped volume, which has no
reservation at all. Both now follow the write path's rule, and the new test asserts the invariant
across `mkdir`, `rmdir` and a refused `mkdir`.

The lesson is narrower than the earlier ones and worth keeping separate: an invariant test is only
as good as the operations it drives through. Asserting the right property over an incomplete set
of operations reads as coverage and is not.

An eighth review found no functional defect - the first round that did not - but two things worth
recording. The depth limit was enforced after the path had been split rather than while splitting
it, so a path of ten thousand segments was parsed in full before being refused for being too deep:
an allocation the caller sizes, charged to no volume, on every operation including reads. Same
refusal, bounded work. The test added with it guards only that the limit did not move; the
allocation itself is not observable without a hook into the allocator, and the test is not claimed
to prove the fix.

The second is a gap left OPEN on purpose: per-entry overhead - the map node and vector header
behind each entry, tens of bytes each - is not charged to the capacity. Charging it would write a
guess about allocator internals into the capacity semantics and be wrong on the next allocator,
and `MAX_ENTRIES` already bounds it to a few hundred kilobytes whatever the capacity. It is
documented in `docs/LIBERMEMFS.md` rather than papered over: the capacity bounds stored bytes and
names, not the volume's total cost to the heap.

A ninth review found a ninth defect, and it was the fix for the sixth wearing a different hat.
Dropping `shrink_to_fit` removed the memcpy but left `Vec::resize` filling the fresh reservation
with zeros - a memset of the whole remaining reservation on every mutation, megabytes per
operation on a large volume, the same price as the copy it replaced. It bought nothing: this
kernel allocates and charges physical frames when a memory object is CREATED, not when a page is
first touched (`MemoryObject::create_in` charges the Domain and calls `allocate_pages` up front),
so the frames behind the heap are committed the moment it maps them. Owning the allocation is the
reservation; writing into it holds nothing extra. Only the capacity is now taken, and the size
held is tracked in its own field. Nothing observable changed, which is why seven reviews walked
past it - the defect was in what the code COST, not in what it computed, and every test asserted
the latter.

That is the lesson worth keeping from this one: a test suite built entirely on observable state
cannot see a performance defect, and the reservation is the one part of this filesystem whose
whole purpose is a side effect rather than a value. Both defects of this kind here were found by
reading the code and asking what it costs, not by running it.

A tenth review left the tree alone and looked at the crate instead, which turned up the largest
gap of the series: **none of these tests ran in any gate.** No recipe invoked `cargo test` for any
filesystem - not LiberFS, FAT, ISO9660, UDF or LiberMemFS - so 217 host tests, including the 18
written for the defects above, were reachable only by hand. Nine defects were found by reading;
nothing was stopping any of them coming back. `just fs-host-test` now runs all six crates and is
wired into `release` beside the other host-test recipes. LiberMemFS was also the only filesystem
without a `rust-toolchain.toml`, so its host tests built with whatever toolchain was ambient while
its siblings pinned nightly - the source-hygiene gate checks that scaffolding for `src/user` crates
only, which is how it went unnoticed. Both fixed, and the crate is now in `fmt` and `fmt-check`
too.

The same review found one wrong claim in the code: `free()` documented itself as not promising room
that the next name would take, which is false. It subtracts the names ALREADY held, so it is exact
for rewriting a file and one name short for creating one - unavoidably, since the length of a name
that does not exist yet is not knowable. The contract is now stated correctly in both the code and
`docs/LIBERMEMFS.md`, and pinned by a test. It matters because a wrong belief of exactly this kind
produced two of the defects above.

An eleventh review checked the claims this milestone makes rather than the tree, since the tenth
had just shown one of them was hollow. The end-to-end test is real, tagged and does assert the
restart property. Two suspected defects were investigated and REJECTED, both by reading the code
rather than reasoning about it: a directory listing cannot overflow an IPC reply, because the
service streams one entry per frame over its own channel rather than packing a message; and
`NoSpace` mapping to `Error::Again` is not a mislabelled permanent failure, because the wire enum
has five variants and none of them means "full" - a volume that is full now may accept the same
write after a delete, so `Again` is the least wrong of what exists.

It found one defect, and it was introduced by the ninth fix: inserting `release_reservation` left
`resync_reservation`'s comment stranded above it, so one function carried two descriptions - one of
them about its neighbour - and the other carried none. That is the same failure mode as defects 8
and 9, which both grew out of a comment that no longer described the code beneath it.

A twelfth review found the last of the scaffolding gaps the tenth had started turning up: the
storage service pins `opt-level = 2` in dev builds for every filesystem crate it links - LiberFS,
FAT, ISO9660, UDF - and LiberMemFS was not among them. This one was measured rather than assumed,
because the others cite a measured cost and adding an override for symmetry would be guesswork:
2000 rewrites into a 2000-entry volume take 1.03 s unoptimized against 79 ms optimized, 13x on the
path every write takes. The dev build is what both test suites and the shipping dev configuration
run.

The measurement also pinned down a design property worth stating rather than fixing: a mutation is
O(entries), because the footprint is recomputed by walking the tree three times. A running total
would make it O(depth) and is deliberately refused - the footprint and the reservation are already
two copies of one fact, and five of the nine defects here were those copies drifting apart. A cache
would add a third copy on the path that has gone wrong most often, and `MAX_ENTRIES` already caps
the walk.

A thirteenth review checked two claims this milestone makes about memory, and one of them was
false. The true one first: a reserved volume really is charged to its Domain, because the heap
grows through `SYS_MEMORY_OBJECT_CREATE`, which the kernel services with
`MemoryObject::create_in(thread.domain(), ...)` - so a mount that cannot get its capacity fails at
mount, as promised.

The false one was the row justifying the capped policy's existence: unused space was described as
"available to everyone else". It is not. The userspace heap maps regions and never unmaps one, so
freeing a file returns its bytes to the storage service's own free list and the Domain stays
charged at the high-water mark. A capped volume that has once been full costs the system exactly
what a reserved volume of the same size costs, permanently. The policy is still worth having - it
never takes what it never needs, so a `vol://tmp` that stays small is nearly free - but the reason
is "never taken" rather than "given back", and both tables now say so. Giving memory back would
need the heap to unmap regions, which is a runtime change and not a filesystem one.

The same pass verified that the twelfth review's own fix was not a no-op: cargo silently ignores a
`[profile.dev.package.X]` whose spec matches nothing, so the override was checked with `cargo
build -v` and does emit `-C opt-level=2` for the crate.

A fourteenth review used a lens none of the previous thirteen had: `cargo clippy`. It reported
four warnings, all of them in the tests written during this series and none in the filesystem
itself; they are fixed and the crate is now clean. Clippy turns out to run nowhere - it appears in
no recipe - and the sibling filesystems carry 24 warnings between them (LiberFS 19, ISO9660 3, FAT
2), so making it a gate is a tree-wide policy change with pre-existing work behind it rather than a
fix, and is left as a decision rather than taken.

Two more claims were checked and held: the volume-layout gate does not apply to memory volumes,
which ship in no package, and the scoped-client rules are generic over the volume name and already
cover `OP_MKDIR` and `OP_RMDIR`, so the memory volumes are constrained exactly like the others.

Worth knowing before the volumes are sized for anything real: NOTHING in the shipping system writes
to `vol://ram` or `vol://tmp` yet - the only non-test references are comments. The capped volume
costs nothing until something does, but the reserved one takes its 4 MiB at every boot on all three
architectures whether or not it is ever read. That is a provisioning decision rather than a defect,
but it is a standing cost with no consumer, and it should be revisited when M0138 gives the memory
volumes their first real job.

A fifteenth review found no new defect in the code and instead attacked the reason so many were
missed. Ten of the defects here were found by READING, and five of them were the footprint and the
reservation drifting apart - a failure with a mechanical shape that every test written alongside
the code failed to catch, because each checked a hand-picked sequence and so only ever asked a
question its author had already thought of.

The nineteenth test asks it mechanically: ten thousand pseudo-random operations against a
deliberately tiny volume, asserting after EVERY one - successful or refused - that
`footprint + reserved` is still the capacity. The sequence is a fixed LCG, so a failure is
reproducible rather than a story about a machine that saw it once, and it asserts that both
outcomes actually occurred, since a run that never stored or never refused anything would pass
while proving nothing.

It was verified against the real defects by reintroducing them one at a time. It catches the
shrink-only reservation at step 1, the late refusal that walked past the resync at step 1, and
`rmdir` failing to give a name back at step 27. The middle one took four review rounds to find by
reading. That is the strongest argument in this milestone for property-style tests over
one-test-per-known-bug, and it is worth applying to LiberFS, where the same class of accounting
exists against a medium.

Miri would be the other lens worth having and is not installed on this toolchain.

One suspected defect was investigated and rejected: `read_file` clones the whole file and would
abort on allocation failure. LiberFS does not use `try_reserve` anywhere, so infallible
allocation is the convention across this tree; changing it here would be a tree-wide convention
change rather than a fix. `docs/LIBERMEMFS.md` records the design.

## The outside review

An independent review on 2026-08-02, after fifteen self-reviews had stopped finding anything in the
tree, went through the same code and the integration path around it. Its findings were checked
against the source one by one; what follows is only what was CONFIRMED. Three of its claims were
overstated and are not carried here: the reservation loss is repaired by the next mutation rather
than permanent, the storage service's "zero-copy read" comment refers to the client side and is
true, and its worked example needs a file larger than a volume that could hold it.

The finding that matters most is the first, and the reason fifteen passes walked past it is worth
recording: every one of them checked that `resync_reservation` is CALLED on each way out. None
asked what was still alive when it ran.

## M0139d - The reservation

- [x] **A late refusal resyncs while the new file is still allocated.** In `write_file`, `written`
  is moved into the tree only on the `Ok` branch; on the `Err` branch from `parent_mut` it is still
  live when `resync_reservation()` runs, so the volume tries to take its capacity back while
  holding a copy of the data it just refused to store. The regrow can fall short for exactly the
  memory the refused write is sitting on. `drop(written)` before the resync is the one-line fix;
  resolving the parent BEFORE allocating is the fix that stops the state arising.

- [x] **Rewriting a file needs room for both copies at once.** The capacity check subtracts the
  existing file, but the allocation does not: `written` is built while the old `Node::File` is
  still in the tree, and the old bytes are dropped only at `insert`. The comment saying a rewrite
  "does not need room for both copies" is about the capacity check and reads as a claim about
  memory. Through the storage service the peak is higher again - the transferred buffer is copied
  into a `Vec` and copied once more here, so a rewrite can hold three copies of a file.

- [x] **Decide what `Reserved` promises, then make the code and the document agree.** The
  reservation is a single contiguous `Vec`, so a regrow needs one contiguous block: after a delete
  that fragments the heap, the total free memory can cover the reservation while no single block
  does. The volume then silently holds less and `remove()` still returns `Ok`. The document says
  the space "is there" AND that regrow is best effort; both cannot be true. Either make it a real
  guarantee - one arena taken at mount, files and names allocated from it, nothing handed back to
  the global heap - or keep best effort, rename accordingly, and surface the degradation:
  `reserved_bytes()` exists only in the backend, and `MemFs::status()` does not report it, so no
  client can see a volume that stopped guaranteeing its space.

- [x] **Charge what an entry really costs, or stop calling the capacity a memory bound.** Resolved
  by stopping the claim rather than inventing a number: `docs/LIBERMEMFS.md` now says plainly that
  the capacity bounds stored bytes and names, that `Reserved` guarantees the memory is taken at
  mount but not that it can always be taken back, and that the map node behind an entry stays
  infallible because `BTreeMap` has no fallible insert. An arena the volume allocates everything
  from would fix the charge and the abort together, and is recorded below as the design change it
  is rather than smuggled in as a constant. Originally: Already
  documented as a deliberate gap: `footprint()` counts data and names, not the map node, the
  vector header or the allocator's own metadata - on the order of a hundred bytes an entry, so a
  few thousand small files cost multiples of what they declare. `mkdir` is the sharpest case: it
  charges the name and then allocates a node several times larger. The gap is bounded by
  `MAX_ENTRIES`, which is why it was left; the review's point that it undercuts the word
  "reserved" is fair and better than the reasoning for leaving it.

## M0139e - Allocation that cannot fail

- [x] **Most allocations here abort instead of returning `NoSpace`.** `try_reserve_exact` guards
  the file bytes and the reservation; `String::from`, `BTreeMap::insert`, `data.clone()`,
  `collect()` and `parts.push()` do not, and in `no_std` + `alloc` those abort the process. Reading
  a 64 MiB file allocates 64 MiB infallibly inside the storage service. This was investigated
  during the self-reviews and rejected on the grounds that LiberFS uses `try_reserve` nowhere, so
  fallibility here would be a tree-wide convention change rather than a fix - which is true, and
  is the decision to revisit rather than the reasoning to repeat.

- [x] **A read makes three copies of the file.** `read_file` clones the stored bytes, the service
  holds that `Vec`, and `make_file_buffer` copies it again into a MemoryObject. For a memory
  filesystem the stored bytes could be handed to the buffer directly, or files could live in
  MemoryObjects to begin with.

## M0139f - Errors and resolution order

- [x] **`lookup` cannot tell "not found" from "a file used as a directory".** It returns `Option`,
  so `read_file("f/child")` answers `NotFound` while `write_file("f/child")` answers `NotDir`
  through `parent_mut` - the same wrong path, two different errors, and `FsError::NotDir` exists
  precisely for this. Returning `Result<&Node, FsError>` fixes both.

- [x] **The capacity is checked before the parent is known to exist.** On a full volume
  `write_file("missing/f", "")` answers `NoSpace` rather than `NotFound`, and
  `write_file("a_file/child", "")` answers `NoSpace` rather than `NotDir`. Worse than the wrong
  code: a large write to a path that cannot exist releases the reservation, allocates and copies
  the whole payload, and only then discovers there is no parent. Resolve the parent read-only
  first, then check the entry count, then the capacity, then allocate.

- [x] **The depth limit does not bound the work the parser does.** `from_utf8` walks the entire
  input before a single segment is examined, and a path made only of separators has no non-empty
  segments, so `MAX_PATH_DEPTH` never trips however long it is. The earlier fix bounded the vector,
  not the scan, and `docs/LIBERMEMFS.md` claims more than the code does. A `MAX_PATH_BYTES` checked
  before the UTF-8 pass would make the claim true.

## M0139g - Tests under memory pressure

- [x] **Nothing here tests behaviour under memory pressure**, which is the property the whole
  reserved policy exists for. Every test runs on a host heap with room to spare, so the transient
  peaks above are invisible: the rewrite test checks the accounting after the operation, never the
  moment both copies exist; `a_write_after_a_short_regrow_still_reaches_the_capacity` never
  actually makes a regrow fall short; and the late-refusal test cannot see the drop-order defect
  because the resync succeeds anyway. A fault-injecting allocator capped near the volume's capacity
  would exercise all three.

- [x] **The property test shares its accounting with the implementation.** It asserts
  `footprint + reserved == capacity` while `resync_reservation` computes its target from
  `footprint()` - so a systematic error in `footprint()`, which the overhead gap above IS, keeps
  the test passing. A reference model held beside the filesystem - paths, expected contents,
  expected errors, entry count, an independently computed footprint - would not agree with a wrong
  implementation.

- [x] Add the cases nobody wrote: `read_file`/`list_entries` through a file as a directory
  component, a full volume with a missing parent and with a file as parent, a path of only
  separators, a same-size rewrite under an allocator limited to the capacity, a late parent failure
  under allocator pressure, and reads and listings large enough that they should return `NoSpace`
  rather than abort.

## M0139i - The arena, if the guarantee has to be absolute

Everything above makes `Reserved` honest. Making it ABSOLUTE is a different design and is left as
one item so it is chosen rather than drifted into: take one arena at mount and allocate files,
names and nodes from it, handing nothing back to the global heap. That fixes at once the three
things the fixes above could only bound - a regrow that cannot fail because nothing is ever
returned, an entry whose real cost is charged because the node comes from the arena, and the last
infallible allocation, since `BTreeMap` is no longer in the path.

- [x] Decided 2026-08-02: NOT NOW, and the trigger for revisiting is written down rather than
  left to memory.

  Against doing it: an arena does not abolish fragmentation, it relocates it. The volume would own
  the fragmentation instead of competing for a shared heap - which is worth real money when there
  is a consumer whose writes must not fail, and nothing at all when there is not. Today nothing in
  the shipping system writes to `vol://ram`; the only writer is `vol://tmp`, which is capped and
  promises nothing. Building a second allocator inside a filesystem, in `no_std`, to protect a
  promise no caller is relying on is speculative work of exactly the kind that produced the nine
  defects above - each of them in code written ahead of its use.

  What makes it acceptable to wait is that the promise is no longer overstated. `Reserved` says
  what it does (the memory is taken at mount) and what it does not (it may not come back),
  `reservation_intact()` answers the question directly, and `free()` reports the smaller figure so
  a degraded volume shows up as less free space everywhere free space is reported - including
  through the storage service, without a wire change. A degraded volume is visible, which is the
  part that was actually broken.

  The trigger: a consumer that keeps state in `vol://ram` and cannot tolerate a refused write.
  M0138's LiveCD is the likely first one - if its system volume lives in LiberMemFS and is written
  to during a session, this stops being theoretical and the arena becomes the next piece of work.
  Also worth revisiting if the entry overhead ever needs charging, or if the last infallible
  allocation (`BTreeMap`'s insert) has to go: an arena fixes all three at once, which is why they
  are one item and not three.

- [x] `read_file` and `list_entries` take `&mut self` while changing nothing.

- [x] `docs/LIBERMEMFS.md` is stale: it says ~320 lines and 17 tests where there are 437 and 19,
  and it says the crate implements the storage service's `FileSystem` trait, which the `MemFs`

## The second outside review

The same reviewer went over the fixes on 2026-08-02 and confirmed most of them landed. Its findings
were again checked against the source one by one, and this time NOTHING it reported was wrong -
only two numeric examples are impossible, for the same reason as last time: they need a file larger

The headline finding is a regression introduced by the fix above, and it is worse than what it

## M0139j - Account for what a file holds, not what it stores

- [x] **Charge `Vec::capacity()`, not `Vec::len()`.** `used()` should stay the stored bytes, which
  is what the word means to a caller, but the capacity check, `free()`, the reservation target and
  `reservation_intact()` all have to work from what is actually allocated. Until they do, `Capped`
  is not a memory cap in any sense - a grow-and-shrink cycle across several files can hold
  multiples of the volume while the volume reports itself empty - and a reserved volume can hold
  its files' historical capacity AND a full reservation at once, with `reservation_intact()`
  answering true throughout.

- [x] **Decide what a shrink does with the freed capacity.** Reporting it as free while the file
  still owns it is the defect above. The options are to shrink the allocation (which `Vec` cannot
  do fallibly - `shrink_to_fit` may reallocate), to keep charging it until the file is removed, or
  to store files as chunks so the tail can be released a block at a time. The third is the one that
  also fixes the growth case below, and is the same answer as the arena in M0139i.

- [x] **Growing past a file's historical capacity can still need both blocks.** True, and left
  standing on purpose: `try_reserve_exact` reallocates when the capacity is short, and the old
  block has to stay valid until the new one exists, so no arrangement of a single `Vec` avoids it.
  The two ways out are chunked file storage and the arena, and they are the same piece of work -
  recorded in M0139i, which is where the decision about a hard guarantee already lives. Putting a
  second copy of it here would split one decision across two places.

  What has changed is that the volume no longer lies about it: the capacity check counts held
  allocations, so a reserved volume knows what it actually has, and a write that cannot be
  satisfied is refused rather than aborting.

- [x] Test the cases the current tests miss, all of which need the budget allocator: a large file
  shrunk to nothing followed by another large write, a grow-shrink cycle across several files
  measured against outstanding allocation, and a genuine growth past a file's historical maximum
  (16 KiB to 48 KiB, not 48 to 1 to 48, which only reuses what was kept).

## M0139k - The path the storage service actually takes

Every guarantee above is about calling the library directly. Through `Storage.Volume`, which is how
the filesystem is really used, the picture is different and worse.

- [x] **`read_buffer` copies the whole input infallibly before LiberMemFS is called.**
  `alloc::vec![0u8; len]` in the service allocates the client's payload while the volume's
  reservation is still held, so a 63 MiB write into a 64 MiB reserved volume needs both at once -
  and being infallible it aborts the service rather than answering `again`. The reservation logic
  is correct and unreachable. Hand the mapped buffer to `write_file` as a borrowed slice instead,
  so the volume releases before it copies.

- [x] **`MemFs::list_entries` undoes the backend's care.** The backend now reserves fallibly and
  copies each name once; the adapter then `collect()`s infallibly and `file_info` builds every
  name again. `Entry` already owns its `String`, so the adapter should move it and reserve its
  output vector fallibly.

- [x] **`write_stream` accumulates an unbounded infallible `Vec`.** Chunks are appended with
  `extend_from_slice` and neither `MAX_FILE_BYTES` nor the volume's capacity is checked until the
  stream ends - and the path is validated after that. A client can spend the service's whole heap
  streaming to a path that does not exist. Validate the path first, take the limit from the volume,
  and refuse the chunk that crosses it.

- [x] **A read still makes three copies.** Confirmed and left, with the reason written down rather
  than the count quietly reduced. Removing the middle copy means `read_file` handing out a borrow
  of the stored bytes, which cannot outlive the borrow of the volume the service holds while it
  fills the MemoryObject - so it needs either a callback taking the slice, or files stored as
  MemoryObjects to begin with. The second is the same change as the arena again.

  What is fixed is the part that could kill the service: every one of those copies is now fallible,
  so a read too large for the heap answers `NoSpace` or `again` instead of aborting. Three copies
  of a 64 MiB file is a cost; aborting the storage service was a defect.

## M0139l - The reservation, and saying so honestly

- [x] **A failed regrow loses the reservation entirely.** `resync_reservation` releases and then
  tries, so when the new size cannot be had the volume ends holding nothing rather than what it had.
  Keeping the old block until the new one exists is not free - that is the double-holding this code
  deliberately avoids - so the answer is a reservation held as several smaller chunks, which also
  makes fragmentation far less likely to defeat it.

- [x] **Three documentation claims are now false.** `docs/LIBERMEMFS.md` still states the invariant
  absolutely ("`footprint + reserved` always equals the capacity") beside the admission that a
  regrow may fall short - it holds only while `reservation_intact()`. It says a capped volume that
  was once full costs what a reserved one costs, which retained capacity makes untrue. And it puts
  the unaccounted overhead at a few hundred kilobytes, which was right for map nodes and is wrong
  now that a single file can hold tens of megabytes the accounting cannot see.

## M0139m - Make the failures reachable

- [x] **`rt`'s allocator must return null instead of exiting.** `GlobalAlloc::alloc` already
  computes `ptr::null_mut()` when no region fits and then throws it away by calling
  `alloc_failure()`. Returning it is what the trait's contract says and what makes every fallible
  path in this filesystem - and everywhere else in userspace - actually reachable. Infallible
  allocations still abort, through Rust's own handler, which is the behaviour they are supposed to
  have. Nothing else in M0139m is worth doing before this.

- [x] Prove it where it matters. `the_memory_volumes_serve_files_and_keep_nothing_across_a_restart`
  now writes a payload that fills a reserved volume through the PUBLIC path - a transferred buffer,
  the way every real client writes - and reads it back whole, then checks the next write is
  refused. Before the service stopped copying the payload into its own heap, filling a 4 KiB
  reserved volume needed 8 KiB and the guarantee the volume had taken was unreachable from
  outside.

  What this does NOT do is cap the service's heap: the storage service grows its own heap from the
  frame pool and a kernel test cannot bound it, so the assertion is that the path works rather
  than that it works under pressure. Capping a service's heap from outside is its own piece of
  work - a Domain memory limit low enough to bite - and pretending this test does it would be the
  same mistake as the budget allocator: proving something about an environment nobody runs in.

- [x] `reservation_intact()` subtracts without saturating (`capacity() - footprint()`).
  `try_reserve_exact` guarantees AT LEAST the requested capacity, so a generous allocator can put
  the footprint over the capacity and underflow this - a panic in debug, a wrapped comparison in
  release.

## M0139n - The write path through the service

- [x] **Hand `write_file` the mapped buffer, do not copy it first.** This was ticked in M0139k and
  not done: the copy was made fallible and left where it was. `read_buffer` still builds the whole

  63 MiB write into a 64 MiB reserved volume needs both at once and the reservation it was given

- [x] Validate before accepting: the path and `MAX_FILE_BYTES` are both checked after the payload
  has been copied, so a client can spend the service's heap on a write that was never going to be
  accepted.

- [x] An out-of-memory `read_buffer` reports `Invalid`. It should report `Again`: the request was
  fine, the moment was not.

## M0139o - The streaming path

The limit added in M0139k guards the accumulation and not the reception, which is where the
unbounded allocation is.

- [x] **`recv_vec_blocking` allocates `vec![0u8; pending]` infallibly with no cap.** One large
  chunk ends the service before any check in `write_stream` runs. It needs a bounded receive - a
  fixed buffer, or a variant that refuses a message larger than a caller-supplied maximum without
  allocating for it.

- [x] The limit is `fs.capacity()`: the whole volume, not `MAX_FILE_BYTES`, not the free space, and
  on a disk backend not even the volume. The backend should answer what a single write may be.

- [x] The stream's channel handle leaks when the path is invalid: `writable_name(&path)?` returns
  before `close(data)`, and the generated dispatch has already handed ownership over. Repeating the
  call with a bad path exhausts the handle table.

- [x] Handles transferred alongside chunks are dropped as numbers without being closed. The
  protocol expects plain messages; a client that does not follow it should not leak the service's
  table.

- [x] A client that keeps the channel open after the limit is crossed keeps `write_stream` running,
  because it drains to be polite to the sender. Blocking a hostile sender is a smaller harm than
  blocking the storage service: close the channel and return.

- [x] The parent directory is not checked before the stream is accepted, only the volume name.

## M0139p - The reservation, again

- [x] **A regrow can leave the volume worse than before it ran.** The old reservation is released
  first and the halving search then keeps the first size that fits - so a volume holding 32 MiB,
  asked for 33 MiB, can end up with 16 MiB. "Best effort" has to mean at least what it already
  had, which needs the reservation held as several chunks so a regrow adds to it rather than
  replacing it.

- [x] A rewrite that fits inside the file's existing allocation releases the reservation anyway,
  and then has to find it again. Nothing was allocated, so nothing needed releasing.

- [x] `BTreeMap` is gone: a directory is a `Vec<(String, Node)>` kept sorted, so lookup is a binary
  search, a listing is already in order, and the slot for a new entry is reserved with
  `try_reserve` before anything moves into it. It was the last allocation that could end the
  process after every check had passed - the volume had checked its capacity, reserved the data
  and reserved the name, and could still die allocating the node to put them in.

## M0139q - Say true things

- [x] `docs/LIBERMEMFS.md` says fallible allocations answer `NoSpace` instead of aborting. True of

## M0139r - Silent truncation (fix before anything else)

- [x] **An out-of-memory during a streamed write is reported as end-of-file, and the partial
  prefix is saved.** `recv_vec_bounded` answers `Closed` when its `try_reserve_exact` fails;
  `receive_stream` treats `Closed` as a clean end, returns what it has, and `write_stream` writes
  it. A client sends a file, memory runs short, and the service replaces the old contents with a
  truncated prefix and reports success.

  It is the same property this milestone already fixed once, in the backend: a write that cannot be
  satisfied must leave the file as it was. Fixed there, reintroduced one layer up. Any negative
  result from the receive syscall becomes `Closed` too, so a channel error can also end as a
  successful short write.

  `BoundedVec` needs to say WHICH ending it is - peer closed, out of memory, too large, receive
  error - and only the first may be read as end-of-file.

- [x] Tested, and the test has teeth: a streamed write whose sender ends abnormally must leave the
  destination as it was. Reintroducing the defect - every ending breaking the collect loop - fails
  it on `a stream that ends abnormally is refused`.

  The kernel harness had no way to drive a streamed write, so `StorageHarness::write_stream` was
  added. What the framing needs, for whoever writes the next one: `u16` opcode 16, `u32`
  correlation, length-prefixed path, then a `u32` slot marker before the transferred channel
  handle - and the harness must pump after sending the request so the service takes delivery of
  the channel before anything is written to the other end.

  Out of memory is the ending that motivated the fix and cannot be forced from a kernel test,
  because the service grows its own heap from the frame pool. An oversized chunk reaches the same
  decision and is the reachable substitute; the test says so rather than implying it covers OOM.

  Worth recording about the first attempt: it was abandoned after five guesses at the framing, and
  the note left behind said the harness could not be built. One diagnostic print showed the request
  was arriving fine and the path worked - the guessing, not the problem, was what had stalled it.

## M0139s - The chunked reservation is not finished

- [x] **Shrinking subtracts `chunk.len()`, which is always zero.** The chunks hold capacity and no
  length on purpose, so `self.reserved` never falls: the loop pops every chunk it has, frees them
  all, and leaves the accounting claiming the memory is still reserved. Each chunk has to carry its
  own recorded size.

- [x] **The outer `Vec` of chunks is filled infallibly.** `reservation.push(...)` in `mount` and in
  `reserve_chunk` can abort now that the allocator returns null - the chunk itself is reserved
  fallibly and the slot to put it in is not. Reserve the slot before taking the chunk.

- [x] Nothing bounds the number of chunks. A fragmented heap can leave a 64 MiB volume holding
  thousands of small ones, whose outer vector and allocator headers are themselves unaccounted.

- [x] Tried, and worth recording as a NEGATIVE result: the shrink branch cannot be reached through
  the public API. Every operation that grows the footprint releases the whole reservation first, so
  the resync always takes the grow path. The accounting test added here guards ordinary use and
  says plainly that it does not cover the branch - which is why the defect sat there, and why it
  will surface the first time an operation changes the footprint without releasing.

## M0139t - The write paths, again

- [x] **`max_write_len` is wrong for a rewrite.** It reports `free()`, which excludes the capacity
  the target file already holds - so on a full volume a streamed rewrite of an existing file is
  refused at zero bytes, while the ordinary write succeeds. For a new file it is wrong the other
  way: it does not subtract the name. The limit has to be derived from the target path, which means
  asking the backend about that path rather than about the volume.

- [x] **The parent is still not validated before a stream is accepted**, only the volume name -
  ticked in M0139o and not done. A stream to `missing/parent/file` is read to completion first.

- [x] **The ordinary write maps the buffer before validating the path**, and the comment above it
  claims the opposite. Parse, validate, check the declared length, then map.

- [x] The stream hands its buffer to the backend by OWNERSHIP rather than copying it in.
  `write_file_owned` adopts the collected allocation as the file's own storage, so a streamed
  write needs the memory once instead of twice and a reserved volume no longer accepts a file
  through `write` while refusing the identical file through `write_stream`. Backends that must
  copy anyway - a disk - keep the borrowing default.

- [x] The accumulator grows with `try_reserve` rather than `try_reserve_exact`, and a single chunk
  may be as large as the whole file, so the transient cost is well above the limit being enforced.

## M0139u - Errors the client never sees

- [x] A failed listing is NOT delivered as an empty directory, and this is the one place across
  four reviews where a finding did not hold. The `unwrap_or_default()` is real and sits in
  `Volume::list` - but nothing calls it: the generated dispatch for `list` is unused, and the serve
  loop does its own listing, where a failure sends the reply WITHOUT a channel handle. A client
  can tell that from an empty listing, which is a channel that opens and closes with nothing on it.

  Trying to make the operation fallible in the IDL turned up two things worth keeping. First, the
  generator does not support `result<stream<T>, error>`: it accepted the declaration, emitted
  nothing for the operation, and reported no error - a silently dropped method is worse than a
  refused one, and is its own bug. Second, `just gen-accept-breaking` and `just gen-check` had
  drifted from `just gen`: they omitted `--external-rust-package liber:resources@1` for
  `process-proto`, so running either silently deleted a re-export and broke the build. Both
  recipes now match `gen`, which is how the drift was found at all.

  The `unwrap_or_default()` should still go, because a vestigial path that swallows errors is a
  trap for whoever wires the generated dispatch up later. It is not the data-loss defect the review
  described.

- [x] The capacity invariant still rests on `try_reserve_exact` returning exactly what was asked
  for. `saturating_sub` removed the panic, not the cause: a generous allocator can put the
  footprint over the capacity, and `reservation_intact()` will then say the volume is fine.

- [x] `docs/LIBERMEMFS.md` describes a reservation that no longer exists - "one contiguous
  allocation", a `BTreeMap` that was replaced, 29 tests where there are 30, and ~490 lines where

## M0139v - Regressions from the last round

- [x] **The ordinary write leaks the transferred handle.** Validating before mapping was the last

- [x] **The 16 MiB default write limit now applies to every backend.** `Volume::write` refuses

## M0139w - The live import accepts a broken system

- [x] **`copy_tree` discards every error and reports success anyway.** A failed listing returns

  It must return a result, stop at the first failure, and refuse to serve a partial volume. The

- [x] `ImageDevice` computes `index as usize * buf.len()` unchecked. A crafted or damaged image can

## M0139x - The service can be stopped by one client

- [x] **An idle stream no longer blocks the service indefinitely**, and the remaining exposure is
  stated rather than hidden. `recv_vec_deadline` gives the receive an absolute deadline and the
  storage service passes one, so a client that opens a stream and says nothing is dropped after
  five seconds instead of holding the serve loop for as long as it likes.

  A deadline BOUNDS the harm; it does not remove it. The service is still unavailable for those
  five seconds, because the receive still runs synchronously inside the serve loop. Streams
  belonging in the event loop as pending operations - request creates one, readable takes a chunk,
  close commits, timeout aborts - is the structural answer and a larger change than this milestone
  should absorb. Recorded here so the next person does not read a deadline as a solution.

  Originally: **An idle stream blocks the whole service.** `receive_stream` runs synchronously inside the
  serve loop and waits with no timeout, so a client that opens a write stream, sends nothing and
  keeps the channel open holds the storage service for every other client - no opens, no status,
  no other volume, no admin. The previous round stopped a hostile sender from draining the service
  forever; it did not stop one from doing nothing forever.

  The fix is structural: streams belong in the event loop as pending operations - request creates
  one, readable takes a chunk, close commits, error or timeout aborts - rather than as a blocking
  call inside the dispatch.

## M0139y - Contracts that still disagree

- [x] An ordinary rewrite keeps the file's old allocation; an owned rewrite (`*file = data`) drops
  it. The same logical shrink therefore accounts differently depending on which API was used, and
  the document states the first behaviour as general.

- [x] `recv_vec_blocking` still folds `NoMemory`, `TooLarge` and `ReceiveError` back into `Closed`
  for its callers. The storage write no longer uses it, so the data-loss defect is gone from that
  path - but any other stream consumer can still read an out-of-memory as a clean end and return a
  prefix.

  `ReceivedVec` gained a third ending, `Failed`. The earlier note here - that a separate
  `BoundedVec` was justified because "eight callers set no ceiling, so the case cannot arise" -
  was only half right: `TooLarge` and `Idle` indeed cannot arise without a ceiling or a deadline,
  but `NoMemory` and `ReceiveError` can arise at any time, and those were the two being silently
  read as end-of-file.

  `drain_stream` now returns `Option`, discarding a partial listing rather than handing back a
  vector no caller can tell apart from a complete one. Each of the ten consumers now states its
  own reading: `ls` and `perm` print that the listing is incomplete, `du` treats it like an
  unreadable directory, `lsvol` refuses to count it, and shell/console name-completion degrades
  to no names - which claims nothing to the user and is the one place where degrading is honest.

  Found while doing this, NOT fixed here: `log_service::prune` answers "no boots" when a listing
  fails, so the next boot reuses a journal number and overwrites the existing one. It predates
  this milestone and needs its own entry.

- [x] `writable_len` adds `existing.capacity() + free` without saturating.

- [x] The same refusal reports `Again` through the ordinary write and `Invalid` through the stream.

- [x] `docs/LIBERMEMFS.md` contradicts itself: the reservation is "several CHUNKS" in one paragraph
  and "one contiguous allocation" a hundred lines later.

## Explicit non-goals

No persistence, no snapshots, no copy-on-write, no checksums - all four protect against a medium
that is not present. No overlay or union mount: composing a read-only volume with a writable one
is a separate idea, needed for a live system booted from read-only media, and it belongs with
that work rather than here. No swap.

## M0139z - The deadline does not bound a stream, only a silence

Verified against the code on 2026-08-03. The previous round called a deadline "a bound on the
harm"; it bounds less than that.

- [x] The deadline is rebuilt from `clock()` INSIDE the receive loop, so it times a gap between
  chunks and not the operation. A sender that emits one byte before each window expires renews it
  forever and holds the serve loop for as long as it likes - every other client, every volume, the
  admin endpoint. Silence is bounded; slowness is not. Needs a TOTAL deadline for the operation
  beside the idle one, and ultimately the pending-stream model recorded in M0139x.

  Fixed 2026-08-03 with TWO bounds, because this framing turned out to be the smaller half of the
  problem. `STREAM_TOTAL_TICKS` (five minutes) is fixed when the request arrives, cannot be pushed
  back by anything the sender does, and the receive takes the earlier of it and the idle window.

  But a deadline is the wrong SHAPE for this attack, and trying to test it is what showed why. A
  slowloris is a pattern of work, not of time: never idle, never finished, a byte at a time. So the
  real bound is on the pattern - after 256 chunks a stream must average at least 64 bytes per
  chunk, or it is refused as `Invalid` rather than `Again`, because a sender behaving this way will
  behave the same way next time. The allowance is loose on purpose: a small file sent in small
  pieces never reaches 256 chunks, and a client sending 4 KiB chunks is 64x clear.

  Recorded rather than glossed: the time-based deadlines are NOT exercised by the suite. Measured
  2026-08-03, 1000 chunks advance the guest clock by 32 ticks - a periodic wait no longer makes
  `run_until_idle` halt to a deadline - so reaching five minutes would take roughly a million
  chunks. The work-based bound is what the test drives, verified by disabling it: the suite then
  fails.

- [x] The constant and the prose disagree: `STREAM_IDLE_TICKS` is 3000 ticks at 100 Hz - thirty
  seconds - and this document says five. One of them is wrong wherever it is read.

- [x] `recv_vec_deadline` discards what `wait_periodic` returns. A channel handed over with READ
  but without the WAIT right lets `channel_peek` work while the wait fails immediately, and the
  loop then spins at full speed until the deadline instead of sleeping. Reachable by a client,
  because the handle is whatever it transferred.

## M0139aa - The outbound listing has no bound at all

The inbound stream got a deadline. The one going the other way never had one.

- [x] `stream_list` sends each entry with `send_blocking(producer, ...)`, which loops on
  WOULD_BLOCK with no deadline. A client that takes the consumer handle and then stops reading
  fills the sub-channel queue and stops StorageService PERMANENTLY - the same defect as the
  inbound stream, in the opposite direction, and without even the partial mitigation.

- [x] `send_blocking(service, &corr_bytes, consumer)` ignores its result. If the client closed the
  main channel just after asking, the consumer handle is never delivered and never closed: it
  leaks, and because it stays open inside this process the producer keeps a live peer nobody
  reads, so the next send blocks forever. Closing both ends on a failed hand-off is the minimum;
  it does not address the client that takes the handle and stops reading.

## M0139ab - The owned pre-check guards a write it does not describe

- [x] `write_file_owned` computes the future footprint from `data.capacity()` unconditionally,
  but `adopt` KEEPS the file's existing buffer whenever `data.len() <= previous` and copies into
  it. So a rewrite that would fit the old allocation is refused when the incoming vector merely
  over-allocated - exactly the over-allocation this filesystem elsewhere takes care to respect.
  The check must branch the same way the write does.

  This is a regression from the previous round's fix, which unified owned and ordinary shrink
  accounting and left the guard describing the other branch.

  Fixed 2026-08-03, and it is the first test `write_file_owned` has ever had -
  `an_owned_rewrite_is_judged_by_the_write_it_will_actually_do` seeds a file that fills the volume
  and rewrites it from an over-allocated vector. Verified by reverting the fix: the test then
  fails with `NoSpace`, which is exactly the refusal a caller would have met.

  `rt` gained `send_deadline`, the outbound twin of `recv_vec_deadline`, and both now give up when
  the wait itself cannot be performed rather than spinning to the deadline.

## M0139ac - What "the filesystem decides the limit" still is not

- [x] A backend that answers `None` to `writable_len` gets a 64 MiB ceiling that belongs to no
  filesystem and no protocol - it is `LiberMemFs::MAX_FILE_BYTES` used as a global default. An
  ordinary write of 80 MiB to LiberFS succeeds while the same file through a stream is refused.
  Either the protocol declares this limit in the IDL, or every writable backend answers for
  itself.

- [x] `None` currently means three different things at once: "no cheap limit", "read-only", and
  "cannot validate the path yet". So a stream to an ISO or UDF volume accepts up to 64 MiB before
  the refusal, and a LiberFS stream to a missing parent does the same - while the code comment
  claims the destination is validated before the first byte. It is, for MemFs only. A three-way
  answer (writable with a limit / read-only / invalid path) would say what is meant.

  Done 2026-08-03 as `WritePlan` - two variants, not three: `Allowed { max_len: Option<usize> }`
  or `Refused(Error)`. A refusal is an answer, so a read-only medium, a policy refusal and a bad
  destination are all reported before a byte is accepted, and the default is a refusal so a
  backend that never implemented writing cannot read as writable-with-unknown-limit.

  The 64 MiB ceiling did not disappear; it stopped pretending to be a filesystem's. It is
  `STREAM_ACCUMULATION`, documented as the RECEIVER's policy - what a stream may hold before the
  filesystem sees it - and applied to streams only, never to an ordinary write whose payload
  already exists. Stating it in the contract is not possible today: LSIDL has no constant
  declarations, so that needs generator work and is recorded rather than claimed.

  LiberFS deliberately gives `max_len: None`. Its free blocks are a LOWER bound on what fits,
  because it compresses, so quoting them as a maximum would refuse writes that would have
  succeeded - the regression this milestone fixed one round ago.

  Tested by `stream_refused_before_sending`: the sender holds its end open and sends nothing, so
  the reply can only be a decision about the destination. The first version used an empty stream
  and would have passed WITHOUT the fix, because dropping the sender ends the stream cleanly and
  the refusal then comes from the write at the end. Verified by reverting: with the archive volume
  answering `Allowed`, the test fails. The harness gained `start_archive` for it - there was no
  read-only volume in it at all.

- [x] A stream still accumulates the whole file before the backend sees it, so a reserved volume
  holds the reservation, the old file, the accumulator and the current chunk at once. Owned writes
  removed the backend's copy and lowered the peak; they did not remove the conflict, and an
  ordinary write can still succeed where the identical stream fails.

  Fixed 2026-08-04 by moving the accumulation INTO the filesystem. The conflict was never really
  about the peak - it was about WHO ACCOUNTS for the memory. The service accumulated in its own
  heap, which the volume knows nothing about, so `free()` kept reporting room that was already
  spent and the reserved volume's guarantee did not cover the operation that needed it most.

  `LiberMemFs` gained `stream_begin` / `stream_push` / `stream_commit` / `stream_abort`. The
  pending buffer is the volume's own, counted in `footprint()`, so it is charged as it arrives:
  a stream that will not fit is refused at the chunk that crosses the line, by the volume, instead
  of by the allocator later. A reserved volume releases its reservation BEFORE each growth, so the
  two are never outstanding together.

  The trait's default is "not supported", and a backend that declines keeps accumulating in the
  service - which is right for a disk, where the bytes are bound for a medium with its own space
  and this heap is only staging.

  `receive_stream` now receives AND stores, rather than returning bytes for the caller to store.
  With a pending write in the filesystem, every path out has to commit or abandon it, and a caller
  that does the storing separately can leave one open.

  Tested by `a_stream_is_charged_to_the_volume_while_it_arrives`: a 64 KiB volume in an 80 KiB
  heap, where two 40 KiB streams both "fit" under the old accounting and the second ran the heap
  out. The volume now refuses the second, and the file already stored is untouched.

- [x] A hard ceiling and a transient shortage both report `Again`, so a client cannot tell whether
  retrying is pointless. The previous round unified these deliberately, to stop the same refusal
  reading as permanent through one transport and retryable through the other - the answer is a
  distinct code for the hard limit on BOTH transports, not a return to disagreeing.

  Done: `receive_stream` now knows WHERE its ceiling came from. A filesystem's ceiling is the space
  it has, so exceeding it stays `Again`; `STREAM_ACCUMULATION` is this service's own policy and no
  amount of waiting changes it, so exceeding that is `Invalid`.

## M0139ad - Failures that still allocate infallibly

- [x] `drain_stream` propagates a failed RECEIVE but grows its result with `items.push`, which
  aborts through the allocation error handler instead of returning `None`. The same is true of the
  decoded records themselves: `Reader::string_lp` builds its `String` with `bytes.to_vec()`.

- [x] A frame that fails to decode is SKIPPED and the stream still ends as complete - in
  `drain_stream` and in `list_volume_directory` both. The last round moved "a short listing looks
  complete" out of the transport; it still lives in the decoder. A parse failure has to end the
  stream as `Failed`.

- [x] The live volume's target capacity is computed as `bytes + bytes / 4 + 4 MiB` in plain
  arithmetic, after `measure` was careful to use checked sums. Corrupt metadata that produces a
  huge total panics in debug and wraps in release, and a wrapped total sizes the volume far too
  small.

- [x] `measure` and `copy_tree` recurse without a depth limit. A source image nested deeper than
  the destination allows recurses all the way down before the destination refuses the path.

## M0139af - What the pending-stream model brought back

Order of work, by risk rather than by the order they were found:

1. `try_reserve_exact`, and the test that would have caught it. An infallible allocation on the
   write path is the one failure this milestone exists to prevent.
2. Handle rights, and aborting a pending operation when the wait itself cannot be performed. Both
   are reachable by a client, and the second spins the loop.
3. The listing's terminal frame. "Short listing looks complete" for the third time needs the
   protocol fixed rather than another patch to the producer.
4. The accounting mistakes that are contained: capacity at `stream_begin`, the resync in
   `stream_commit`, the double close, the dropped entry.
5. Destination validation for the writable disk backends.
6. `try_send` telling a closed peer from a full queue.
7. The two that are design work rather than fixes: receiving into the pending buffer without a
   transport copy, and a `stream_plan` that admits what a streamed rewrite costs.
8. The two that are tidying: merging the duplicate implementation, and the crate documentation.


Verified against the code on 2026-08-04, after M0141 made streams pending operations. The
architecture is right; the transactional accounting written to support it is not.

- [x] **`stream_push` reserves the wrong amount, so growth can allocate INFALLIBLY.** It computes
  `extra = want - capacity` and calls `try_reserve_exact(extra)`, but that API guarantees
  `len + additional`, not `capacity + additional`.

  Fixed: `try_reserve_exact(chunk.len())`, which asks for exactly what is appended and is correct
  whatever the capacity happens to be.

  ONE CORRECTION to the finding, established by trying to reproduce it. It is LATENT rather than
  reachable: this path reserves exactly what it appends, so `len` and `capacity` move together and
  the gap the bug needs never opens unless the allocator returns more than it was asked for. The
  severity - an abort under memory pressure - is right in principle and the fix is worth making
  unconditionally, but a client could not have triggered it.

- [x] A test for `len < capacity < want`. The existing one never enters that state.

  Written, and it does NOT reproduce the defect - recorded in the test itself rather than papered
  over. Forcing `len < capacity` needs control of the allocator this harness does not have. What it
  does cover is the fallible path: a volume with room for the data and a heap without it refuses
  rather than aborts.

- [x] **The transport chunk still lives beside the reservation.** `recv_vec_bounded` allocates the
  whole message as its own `Vec`, and only then is it copied into the volume's pending buffer. So a
  reserved volume still cannot promise to take one chunk near its capacity: the reservation, the
  transport chunk, the pending buffer and - during growth - its old and new allocations can all be
  outstanding. Receiving directly into the pending buffer's spare capacity would remove both the
  second allocation and the copy.

  Done. `stream_spare` hands out room inside the volume's pending buffer and `recv_into` writes the
  message straight into it; `stream_advance` keeps what arrived. The space is zeroed rather than
  exposed uninitialised - a memset costs far less than the allocation it replaces, and the
  alternative is unsafe code on the receive path of a service that reads from untrusted peers.

  The new test measures it: a 64 KiB volume in a 96 KiB heap taking a 48 KiB chunk, with the
  allocation INSIDE the budgeted block. Two copies would not fit.

- [x] The unit test does not measure this: its chunk is built OUTSIDE the budgeted block, so the
  transport allocation is not counted.

- [x] **A stream to a full volume is allowed by the preflight and refused by its first chunk.**
  `write_plan` answers with `existing.capacity() + free`, which is right for an ordinary write that
  rewrites in place. An incremental stream keeps the old file until commit and builds the new
  contents beside it, and `stream_push` does not subtract the old capacity. So the ordinary write
  still succeeds where the identical stream cannot take a single byte - the same asymmetry this
  milestone has now failed to close twice, from opposite ends. It needs either a separate
  `stream_plan` that admits a streamed rewrite costs extra memory, or a staging model that does not
  hold both.

  Done, as `stream_plan`. `LiberMemFs::stream_len` answers with what is genuinely FREE, where
  `writable_len` may add what the file already holds - correct for an in-place rewrite, wrong for a
  stream that keeps the old contents until the commit. The trait defaults `stream_plan` to
  `write_plan`, which is right for every backend whose bytes are bound for a medium; only the
  memory filesystem pays for holding both versions.

  The asymmetry is not removed, because it is real: an atomic replace needs room for both versions
  at once. What changed is that the preflight now says so instead of promising otherwise. The test
  asserts both figures and then that the stream is refused exactly where its own plan predicted.

- [x] **A stream handle without WAIT can spin the serve loop.** `begin_stream` checks neither the
  object type nor READ/WAIT rights before putting the handle into the shared `wait_any_periodic`.
  A wait that cannot be performed returns an error, and the loop's `ready < 0` branch only checks
  the deadline and continues - so it retries at full speed until the deadline passes, serving
  nobody. This is the same defect fixed in `recv_vec_deadline` the same morning, reintroduced one
  layer up when the wait moved into the loop. The test uses `Rights::ALL` and cannot see it.

- [x] **An abandoned listing looks like a completed one.** When `pump_list` gives up at its
  deadline the loop closes the producer, and a closed channel is exactly what a finished listing
  looks like: `drain_stream` returns the prefix it collected as the whole directory. A client can
  receive the first 64 entries of a large directory and believe that is all of it. This is "a short
  listing looks complete" for the third time, from a third cause. The stream needs an explicit
  terminal frame - done, or failed - because closing cannot distinguish the two.

  Done: the producer sends an EMPTY message after the last entry, and closing without it now means
  the listing stopped early. `drain_stream_complete` in the runtime treats the empty frame as the
  end and a bare close as truncation; the six volume-listing consumers use it, and the panel
  listing, which has its own loop, learned the same rule.

  Scoped to volume listings deliberately. There are eight stream producers and ten consumers in the
  tree, and changing what "closed" means for all of them is a system-wide protocol change; this
  defect is in one of them. Producers that do not send the marker keep using `drain_stream`.

  Verified by dropping the terminal frame: the suite fails.

- [x] **`stream_begin` can push the volume over its capacity.** It allocates a copy of the path and
  installs the pending entry, which `footprint()` counts, without checking that the volume has room
  for it. On a full volume, opening a stream costs capacity before a single file byte arrives. The
  path is also stored twice - as a `String` in the service's `PendingWrite` and as a `Vec<u8>` in
  the filesystem's `Pending`.

- [x] **`stream_commit` resyncs the reservation at the wrong moment.** It takes the pending entry,
  resyncs while the data and path are still alive in a local, and only then adopts them. The regrow
  therefore competes with memory that is about to be handed to the file. One adoption and one final
  resync is the right shape.

- [x] **`DiskFs` and `FatBacking` still do not validate the destination.** Both ignore the `name`
  they are given and answer `Allowed`, so a stream to a missing parent on LiberFS accepts up to
  64 MiB before failing at commit. The comment claiming the destination is checked before the first
  byte holds for MemFs and the read-only backends only.

- [x] **`pump_list` drops an entry that will not encode** and still ends the listing cleanly, and
  the generated reader ignores the sequence number, so a client cannot see the gap either.

- [x] **A malformed write-stream request closes its handle twice.** The parse-failure branch closes
  what it finds and returns without clearing the list, and the serve loop then closes the same
  handles again as unclaimed. Harmless today; wrong ownership, and dangerous if handle slots are
  ever reused.

- [x] **Final replies still use `send_blocking`.** A stream no longer blocks the loop while it
  transfers, but `finish_stream` and the ordinary dispatch answer through an unbounded send, so a
  client that fills its reply queue and stops reading can still stop the service.

  This was the LAST place one client could stop the service, and M0141 missed it: the transfer was
  unblocked and the answer left blocking. `send_caps_deadline` bounds a reply at ten seconds, and a
  client that will not take one in that time is dropped - it has stopped reading, and the
  alternative is holding everyone else for it. The root client is never dropped: ending the service
  is not a way to resolve a stalled boot chain.

- [x] **`try_send` cannot tell a full queue from a closed peer.** A listing whose consumer is gone
  stays active until its deadline, waking the loop every tick and refusing a second listing, for no
  reason. The runtime needs `Delivered / WouldBlock / PeerClosed / Failed`.

- [x] **Two implementations of the same protocol.** The serve loop uses the pending model; the
  generated trait still carries the synchronous `receive_stream` / `receive_body`. Kept deliberately
  so the direct-dispatch test still behaves, but it is a drift risk - the two orderings are already
  different.

  Deleted. The reason for keeping it did not survive checking: the only direct dispatch in the tree
  is a STUB in the protocol tests, so the storage service's synchronous path was reachable from
  nothing at all. The trait method stays because the generated trait requires it, closes the handle
  it is given, and refuses - which is what "nothing routes here" should look like from the outside.

- [x] **The crate documentation still describes the reservation as "one contiguous allocation".**
  It has been a `Vec<Chunk>` bounded by `MAX_RESERVATION_CHUNKS` since the chunked reservation
  landed. The external document was corrected; this one was not.
