# M0139 - LiberMemFS: a writable filesystem that lives in memory

Every volume this system can mount is backed by a medium: LiberFS on a disk, FAT on removable
media, ISO9660 and UDF on optical images. There is nowhere to write that does not survive a
reboot and does not cost a disk write - no `/tmp`, and no place for state a service needs only
while it is running.

`LiberMemFS` is that place: files held directly on the heap, no block layer, no on-disk format,
rebuilt empty on every boot.

- Done when: `vol://ram` and `vol://tmp` mount and serve reads, writes, directories and deletes
  through the same `FileSystem` trait as every other backend; the two differ only in how their
  memory is charged; both appear in the test system beside the ISO and UDF volumes; and the
  suite is green on all three architectures.

## Why not LiberFS on a RAM block device

The cheap answer was to implement `BlockDevice` over a memory buffer and format LiberFS onto it -
maybe fifty lines, and everything already works. It was the recommendation here until the code
was actually measured on 2026-08-02, and the measurement changed the answer:

| LiberFS module | lines | needed in RAM? |
| --- | --- | --- |
| `blkalloc` | 970 | no - the heap allocates |
| `txn` | 810 | no - there is no crash to recover from |
| `lib` | 796 | mostly no - superblock, on-disk structures, checksums |
| `dir` | 543 | the idea, but a map rather than a B+tree |
| `fsops` | 511 | the idea, simpler |
| `snapshot` | 329 | no |
| `fsck` | 220 | no - it is rebuilt every boot |
| `inode` | 167 | the idea, simpler |

LiberFS is 4346 lines of implementation (plus 2495 of tests). Reusing it in RAM means carrying a
block allocator, a transaction log and a checker that protect against a medium that is not
there, to reach data the CPU can already address. The "free, already tested" argument is thinner
than it looks: much of that test suite covers durability, which is not a property RAM has.

A native implementation is estimated at 400-700 lines against a nine-method trait, plus tests.

The other difference is what the fixed size means. A RAM DISK reserves its whole size whether or
not anything is stored in it. A memory filesystem holds only what is in it, and a limit is a CAP
rather than a reservation - which is the distinction this milestone builds on below.

## One filesystem, two allocation policies

`vol://ram` and `vol://tmp` are NOT two implementations. Files, directories, path resolution and
every trait method are identical; the only difference is when their memory is charged, and the
system already has the mechanism for that in per-Domain accounting (`Domain::memory()`, and
`PROP_MEMORY_LIMIT`).

| | `vol://ram` - reserved | `vol://tmp` - capped |
| --- | --- | --- |
| charged | at mount | at write |
| guarantees | the space is there | the space may be there |
| when memory is short | the MOUNT fails | the WRITE fails |
| unused space | held | not taken in the first place |
| suits | state that must not fail because something else took the memory | scratch, where waste is worse than an occasional refusal |

Two separate implementations would duplicate directories, paths, reads and writes to express one
condition. The policy belongs at mount time, and the accounting belongs to the Domain that owns
the volume - not to a second filesystem.

## M0139a - The filesystem

- [x] Implement `LiberMemFS` in `src/fs/libermemfs` as `no_std` + `alloc`: a file is a heap allocation, a
  directory is a map of names, and nothing is encoded for a medium. It implements the storage
  service's `FileSystem` trait directly, not `fs_core::BlockDevice` - there is no block device
  under it.

- [x] Bound it deliberately: a maximum file size, a maximum entry count and a maximum path depth,
  refusing past each rather than growing without limit. A filesystem that can exhaust the kernel heap is a
  denial of service.

- [x] Cover the cases a fresh implementation gets wrong: writing into the middle of a file,
  truncating, deleting an open file, a directory that is not empty, a path that walks past the
  root, and names that collide only after normalisation.

## M0139b - The two policies

- [x] Charge a reserved volume at mount and a capped volume at write, both against the owning
  Domain's memory counter.

- [x] Prove the difference rather than assert it: mounting a reserved volume larger than the
  Domain's remaining budget must FAIL AT MOUNT, and a capped volume of the same size must mount
  and then fail at the write that crosses the limit.

## M0139c - In the test system

- [x] Mount both beside the existing volumes in the scenario harness, the way `vol://iso` and
  `vol://udf` already are: `vol://ram` reserved and `vol://tmp` capped, granted through the same
  `volumes` capability bundle with their own tags (`RAM`, `TMP`) so the bundle keeps sending a
  fixed number of messages in a fixed order.

- [x] One end-to-end test that writes through a tool, reads it back, and proves the volume is
  EMPTY after a restart - the property that distinguishes it from
  every other volume.

Done 2026-08-02, about 260 lines of implementation against a nine-method trait plus 9 unit
tests - under the 400-700 estimate, and the difference is exactly what RAM does not need.

Wiring the two volumes into the boot chain cost far more than the filesystem did, and the
reason is worth recording. Growing the `volumes` capability bundle from five entries to seven
required changes in SEVEN independent places: the sender in PermissionManager, the shared
`VolumeSet`, twelve tools that read the bundle without it, three harnesses in `tests.rs`, eight
sites in `dynamic.rs`, and the expected service count in `boot.rs`. None of them knows about
the others, and each carries the message count implicitly. Every miss surfaced somewhere else
entirely - a hung `imgconv`, an `imgview` with no surface, a missing `mkdir` confirmation. The
fix for the underlying problem is recorded as an item in M0132: the bootstrap sequence needs a
length or a terminator.

## Verified

- [x] Green on all three architectures, and the boot chain comes up on each: x86_64 153,
  aarch64 145, riscv64 146.

Two defects were found by re-reading the finished implementation rather than by any test, and
both were in the properties this milestone promises:

- A write whose allocation failed had ALREADY replaced the entry with an empty file, so a
  refused write destroyed what was there. The bytes are now built first and inserted once they
  exist, so no ordering remains where a failure can truncate the previous contents.
- The reservation could only shrink. Deleting or shrinking a file returned its memory to the
  heap instead of to the reservation, so a reserved volume kept reporting its capacity while no
  longer holding it - and a later write could fail for memory something else had taken. That is
  the ONLY thing separating the two policies, so losing it silently made the reserved volume
  worse than not having one. The reservation is now resynced after every mutation.

Two further reviews found two more, both in the accounting rather than the tree:

- `resync_reservation` regrew the buffer with `Vec::resize`, which ABORTS on allocation failure
  rather than reporting it - a crash in the storage service where a degraded guarantee would do.
  It now uses `try_reserve_exact` and leaves the volume holding less, visibly, if the memory
  cannot be had.
- A write allocated the file bytes BEFORE releasing the reservation, so both were outstanding at
  once and a volume at its capacity needed twice its capacity to write into itself. That is the
  precise failure the reservation exists to prevent, so the guarantee did not hold at all. The
  bytes are now released first, and the release is undone if the write is then refused.

A fourth review found a fifth, and it was a hole in the fix for the fourth: the reservation is
released before the file is allocated, but `parent_mut` can still refuse afterwards - an absent
parent, or a file used as a path component - and returning through `?` there walked past the
resync. The volume then held less than its capacity permanently, with nothing stored to account
for it.

Five defects across four reviews, three of them in the reservation accounting, and each of the
last three was found only after the previous one was fixed. None would have been caught by the
tests written alongside the code, because those were written from the same picture of it.

What changed the return was the test written for the fifth: instead of one test per known
defect, it asserts the INVARIANT - `footprint + reserved == capacity` - across six different ways an
operation can be refused. That form catches defects nobody thought of, and it immediately did.
Verified to have teeth by reverting the fix and watching it fail.

A fifth review found a sixth defect, of a different kind: `shrink_to_fit` reallocates and COPIES
what it keeps, so every write to a reserved volume was memcpying what remained of the
reservation - megabytes per write, to preserve zeros nothing reads. The reservation is now
dropped and reallocated rather than resized, which also stops the old and new blocks from being
outstanding together. The same pass strengthened the write path: it now releases the WHOLE
reservation rather than the difference, so how much is held stops mattering to whether a write
can proceed - it could fall short after a best-effort regrow.

A sixth review found a seventh, and this one was a hole in the bound itself: names were not
counted against the capacity. Only file contents were, so a volume could be filled with long
names holding nothing - a megabyte in the worst case, a QUARTER of a 4 MiB reserved volume - and
`mkdir` had no capacity check at all, a directory storing no data. The capacity now bounds the
footprint (data plus names); `used()` still reports data, because that is what the word means to
a caller, and `free()` subtracts both. Ten test expectations had to be recomputed, which is the
clearest evidence the change was real rather than cosmetic.

A seventh review found an eighth, and it was a hole opened by the seventh fix itself. Counting
names made `mkdir` and `rmdir` reservation-affecting operations, which they had never been, and
neither was updated: `mkdir` allocated a name while the reservation still held those bytes, and
`rmdir` freed one without giving it back. So the invariant broke in BOTH directions on ordinary
directory work - the first time any defect here did. The existing invariant test could not see it
because it exercised only files, and the name-accounting test used a capped volume, which has no
reservation at all. Both now follow the write path's rule, and the new test asserts the invariant
across `mkdir`, `rmdir` and a refused `mkdir`.

The lesson is narrower than the earlier ones and worth keeping separate: an invariant test is only
as good as the operations it drives through. Asserting the right property over an incomplete set
of operations reads as coverage and is not.

An eighth review found no functional defect - the first round that did not - but two things worth
recording. The depth limit was enforced after the path had been split rather than while splitting
it, so a path of ten thousand segments was parsed in full before being refused for being too deep:
an allocation the caller sizes, charged to no volume, on every operation including reads. Same
refusal, bounded work. The test added with it guards only that the limit did not move; the
allocation itself is not observable without a hook into the allocator, and the test is not claimed
to prove the fix.

The second is a gap left OPEN on purpose: per-entry overhead - the map node and vector header
behind each entry, tens of bytes each - is not charged to the capacity. Charging it would write a
guess about allocator internals into the capacity semantics and be wrong on the next allocator,
and `MAX_ENTRIES` already bounds it to a few hundred kilobytes whatever the capacity. It is
documented in `docs/LIBERMEMFS.md` rather than papered over: the capacity bounds stored bytes and
names, not the volume's total cost to the heap.

A ninth review found a ninth defect, and it was the fix for the sixth wearing a different hat.
Dropping `shrink_to_fit` removed the memcpy but left `Vec::resize` filling the fresh reservation
with zeros - a memset of the whole remaining reservation on every mutation, megabytes per
operation on a large volume, the same price as the copy it replaced. It bought nothing: this
kernel allocates and charges physical frames when a memory object is CREATED, not when a page is
first touched (`MemoryObject::create_in` charges the Domain and calls `allocate_pages` up front),
so the frames behind the heap are committed the moment it maps them. Owning the allocation is the
reservation; writing into it holds nothing extra. Only the capacity is now taken, and the size
held is tracked in its own field. Nothing observable changed, which is why seven reviews walked
past it - the defect was in what the code COST, not in what it computed, and every test asserted
the latter.

That is the lesson worth keeping from this one: a test suite built entirely on observable state
cannot see a performance defect, and the reservation is the one part of this filesystem whose
whole purpose is a side effect rather than a value. Both defects of this kind here were found by
reading the code and asking what it costs, not by running it.

A tenth review left the tree alone and looked at the crate instead, which turned up the largest
gap of the series: **none of these tests ran in any gate.** No recipe invoked `cargo test` for any
filesystem - not LiberFS, FAT, ISO9660, UDF or LiberMemFS - so 217 host tests, including the 18
written for the defects above, were reachable only by hand. Nine defects were found by reading;
nothing was stopping any of them coming back. `just fs-host-test` now runs all six crates and is
wired into `release` beside the other host-test recipes. LiberMemFS was also the only filesystem
without a `rust-toolchain.toml`, so its host tests built with whatever toolchain was ambient while
its siblings pinned nightly - the source-hygiene gate checks that scaffolding for `src/user` crates
only, which is how it went unnoticed. Both fixed, and the crate is now in `fmt` and `fmt-check`
too.

The same review found one wrong claim in the code: `free()` documented itself as not promising room
that the next name would take, which is false. It subtracts the names ALREADY held, so it is exact
for rewriting a file and one name short for creating one - unavoidably, since the length of a name
that does not exist yet is not knowable. The contract is now stated correctly in both the code and
`docs/LIBERMEMFS.md`, and pinned by a test. It matters because a wrong belief of exactly this kind
produced two of the defects above.

An eleventh review checked the claims this milestone makes rather than the tree, since the tenth
had just shown one of them was hollow. The end-to-end test is real, tagged and does assert the
restart property. Two suspected defects were investigated and REJECTED, both by reading the code
rather than reasoning about it: a directory listing cannot overflow an IPC reply, because the
service streams one entry per frame over its own channel rather than packing a message; and
`NoSpace` mapping to `Error::Again` is not a mislabelled permanent failure, because the wire enum
has five variants and none of them means "full" - a volume that is full now may accept the same
write after a delete, so `Again` is the least wrong of what exists.

It found one defect, and it was introduced by the ninth fix: inserting `release_reservation` left
`resync_reservation`'s comment stranded above it, so one function carried two descriptions - one of
them about its neighbour - and the other carried none. That is the same failure mode as defects 8
and 9, which both grew out of a comment that no longer described the code beneath it.

A twelfth review found the last of the scaffolding gaps the tenth had started turning up: the
storage service pins `opt-level = 2` in dev builds for every filesystem crate it links - LiberFS,
FAT, ISO9660, UDF - and LiberMemFS was not among them. This one was measured rather than assumed,
because the others cite a measured cost and adding an override for symmetry would be guesswork:
2000 rewrites into a 2000-entry volume take 1.03 s unoptimized against 79 ms optimized, 13x on the
path every write takes. The dev build is what both test suites and the shipping dev configuration
run.

The measurement also pinned down a design property worth stating rather than fixing: a mutation is
O(entries), because the footprint is recomputed by walking the tree three times. A running total
would make it O(depth) and is deliberately refused - the footprint and the reservation are already
two copies of one fact, and five of the nine defects here were those copies drifting apart. A cache
would add a third copy on the path that has gone wrong most often, and `MAX_ENTRIES` already caps
the walk.

A thirteenth review checked two claims this milestone makes about memory, and one of them was
false. The true one first: a reserved volume really is charged to its Domain, because the heap
grows through `SYS_MEMORY_OBJECT_CREATE`, which the kernel services with
`MemoryObject::create_in(thread.domain(), ...)` - so a mount that cannot get its capacity fails at
mount, as promised.

The false one was the row justifying the capped policy's existence: unused space was described as
"available to everyone else". It is not. The userspace heap maps regions and never unmaps one, so
freeing a file returns its bytes to the storage service's own free list and the Domain stays
charged at the high-water mark. A capped volume that has once been full costs the system exactly
what a reserved volume of the same size costs, permanently. The policy is still worth having - it
never takes what it never needs, so a `vol://tmp` that stays small is nearly free - but the reason
is "never taken" rather than "given back", and both tables now say so. Giving memory back would
need the heap to unmap regions, which is a runtime change and not a filesystem one.

The same pass verified that the twelfth review's own fix was not a no-op: cargo silently ignores a
`[profile.dev.package.X]` whose spec matches nothing, so the override was checked with `cargo
build -v` and does emit `-C opt-level=2` for the crate.

A fourteenth review used a lens none of the previous thirteen had: `cargo clippy`. It reported
four warnings, all of them in the tests written during this series and none in the filesystem
itself; they are fixed and the crate is now clean. Clippy turns out to run nowhere - it appears in
no recipe - and the sibling filesystems carry 24 warnings between them (LiberFS 19, ISO9660 3, FAT
2), so making it a gate is a tree-wide policy change with pre-existing work behind it rather than a
fix, and is left as a decision rather than taken.

Two more claims were checked and held: the volume-layout gate does not apply to memory volumes,
which ship in no package, and the scoped-client rules are generic over the volume name and already
cover `OP_MKDIR` and `OP_RMDIR`, so the memory volumes are constrained exactly like the others.

Worth knowing before the volumes are sized for anything real: NOTHING in the shipping system writes
to `vol://ram` or `vol://tmp` yet - the only non-test references are comments. The capped volume
costs nothing until something does, but the reserved one takes its 4 MiB at every boot on all three
architectures whether or not it is ever read. That is a provisioning decision rather than a defect,
but it is a standing cost with no consumer, and it should be revisited when M0138 gives the memory
volumes their first real job.

A fifteenth review found no new defect in the code and instead attacked the reason so many were
missed. Ten of the defects here were found by READING, and five of them were the footprint and the
reservation drifting apart - a failure with a mechanical shape that every test written alongside
the code failed to catch, because each checked a hand-picked sequence and so only ever asked a
question its author had already thought of.

The nineteenth test asks it mechanically: ten thousand pseudo-random operations against a
deliberately tiny volume, asserting after EVERY one - successful or refused - that
`footprint + reserved` is still the capacity. The sequence is a fixed LCG, so a failure is
reproducible rather than a story about a machine that saw it once, and it asserts that both
outcomes actually occurred, since a run that never stored or never refused anything would pass
while proving nothing.

It was verified against the real defects by reintroducing them one at a time. It catches the
shrink-only reservation at step 1, the late refusal that walked past the resync at step 1, and
`rmdir` failing to give a name back at step 27. The middle one took four review rounds to find by
reading. That is the strongest argument in this milestone for property-style tests over
one-test-per-known-bug, and it is worth applying to LiberFS, where the same class of accounting
exists against a medium.

Miri would be the other lens worth having and is not installed on this toolchain.

One suspected defect was investigated and rejected: `read_file` clones the whole file and would
abort on allocation failure. LiberFS does not use `try_reserve` anywhere, so infallible
allocation is the convention across this tree; changing it here would be a tree-wide convention
change rather than a fix. `docs/LIBERMEMFS.md` records the design.

## The outside review

An independent review on 2026-08-02, after fifteen self-reviews had stopped finding anything in the
tree, went through the same code and the integration path around it. Its findings were checked
against the source one by one; what follows is only what was CONFIRMED. Three of its claims were
overstated and are not carried here: the reservation loss is repaired by the next mutation rather
than permanent, the storage service's "zero-copy read" comment refers to the client side and is
true, and its worked example needs a file larger than a volume that could hold it.

The finding that matters most is the first, and the reason fifteen passes walked past it is worth
recording: every one of them checked that `resync_reservation` is CALLED on each way out. None
asked what was still alive when it ran.

## M0139d - The reservation

- [x] **A late refusal resyncs while the new file is still allocated.** In `write_file`, `written`
  is moved into the tree only on the `Ok` branch; on the `Err` branch from `parent_mut` it is still
  live when `resync_reservation()` runs, so the volume tries to take its capacity back while
  holding a copy of the data it just refused to store. The regrow can fall short for exactly the
  memory the refused write is sitting on. `drop(written)` before the resync is the one-line fix;
  resolving the parent BEFORE allocating is the fix that stops the state arising.

- [x] **Rewriting a file needs room for both copies at once.** The capacity check subtracts the
  existing file, but the allocation does not: `written` is built while the old `Node::File` is
  still in the tree, and the old bytes are dropped only at `insert`. The comment saying a rewrite
  "does not need room for both copies" is about the capacity check and reads as a claim about
  memory. Through the storage service the peak is higher again - the transferred buffer is copied
  into a `Vec` and copied once more here, so a rewrite can hold three copies of a file.

- [x] **Decide what `Reserved` promises, then make the code and the document agree.** The
  reservation is a single contiguous `Vec`, so a regrow needs one contiguous block: after a delete
  that fragments the heap, the total free memory can cover the reservation while no single block
  does. The volume then silently holds less and `remove()` still returns `Ok`. The document says
  the space "is there" AND that regrow is best effort; both cannot be true. Either make it a real
  guarantee - one arena taken at mount, files and names allocated from it, nothing handed back to
  the global heap - or keep best effort, rename accordingly, and surface the degradation:
  `reserved_bytes()` exists only in the backend, and `MemFs::status()` does not report it, so no
  client can see a volume that stopped guaranteeing its space.

- [x] **Charge what an entry really costs, or stop calling the capacity a memory bound.** Resolved
  by stopping the claim rather than inventing a number: `docs/LIBERMEMFS.md` now says plainly that
  the capacity bounds stored bytes and names, that `Reserved` guarantees the memory is taken at
  mount but not that it can always be taken back, and that the map node behind an entry stays
  infallible because `BTreeMap` has no fallible insert. An arena the volume allocates everything
  from would fix the charge and the abort together, and is recorded below as the design change it
  is rather than smuggled in as a constant. Originally: Already
  documented as a deliberate gap: `footprint()` counts data and names, not the map node, the
  vector header or the allocator's own metadata - on the order of a hundred bytes an entry, so a
  few thousand small files cost multiples of what they declare. `mkdir` is the sharpest case: it
  charges the name and then allocates a node several times larger. The gap is bounded by
  `MAX_ENTRIES`, which is why it was left; the review's point that it undercuts the word
  "reserved" is fair and better than the reasoning for leaving it.

## M0139e - Allocation that cannot fail

- [x] **Most allocations here abort instead of returning `NoSpace`.** `try_reserve_exact` guards
  the file bytes and the reservation; `String::from`, `BTreeMap::insert`, `data.clone()`,
  `collect()` and `parts.push()` do not, and in `no_std` + `alloc` those abort the process. Reading
  a 64 MiB file allocates 64 MiB infallibly inside the storage service. This was investigated
  during the self-reviews and rejected on the grounds that LiberFS uses `try_reserve` nowhere, so
  fallibility here would be a tree-wide convention change rather than a fix - which is true, and
  is the decision to revisit rather than the reasoning to repeat.

- [x] **A read makes three copies of the file.** `read_file` clones the stored bytes, the service
  holds that `Vec`, and `make_file_buffer` copies it again into a MemoryObject. For a memory
  filesystem the stored bytes could be handed to the buffer directly, or files could live in
  MemoryObjects to begin with.

## M0139f - Errors and resolution order

- [x] **`lookup` cannot tell "not found" from "a file used as a directory".** It returns `Option`,
  so `read_file("f/child")` answers `NotFound` while `write_file("f/child")` answers `NotDir`
  through `parent_mut` - the same wrong path, two different errors, and `FsError::NotDir` exists
  precisely for this. Returning `Result<&Node, FsError>` fixes both.

- [x] **The capacity is checked before the parent is known to exist.** On a full volume
  `write_file("missing/f", "")` answers `NoSpace` rather than `NotFound`, and
  `write_file("a_file/child", "")` answers `NoSpace` rather than `NotDir`. Worse than the wrong
  code: a large write to a path that cannot exist releases the reservation, allocates and copies
  the whole payload, and only then discovers there is no parent. Resolve the parent read-only
  first, then check the entry count, then the capacity, then allocate.

- [x] **The depth limit does not bound the work the parser does.** `from_utf8` walks the entire
  input before a single segment is examined, and a path made only of separators has no non-empty
  segments, so `MAX_PATH_DEPTH` never trips however long it is. The earlier fix bounded the vector,
  not the scan, and `docs/LIBERMEMFS.md` claims more than the code does. A `MAX_PATH_BYTES` checked
  before the UTF-8 pass would make the claim true.

## M0139g - Tests under memory pressure

- [x] **Nothing here tests behaviour under memory pressure**, which is the property the whole
  reserved policy exists for. Every test runs on a host heap with room to spare, so the transient
  peaks above are invisible: the rewrite test checks the accounting after the operation, never the
  moment both copies exist; `a_write_after_a_short_regrow_still_reaches_the_capacity` never
  actually makes a regrow fall short; and the late-refusal test cannot see the drop-order defect
  because the resync succeeds anyway. A fault-injecting allocator capped near the volume's capacity
  would exercise all three.

- [x] **The property test shares its accounting with the implementation.** It asserts
  `footprint + reserved == capacity` while `resync_reservation` computes its target from
  `footprint()` - so a systematic error in `footprint()`, which the overhead gap above IS, keeps
  the test passing. A reference model held beside the filesystem - paths, expected contents,
  expected errors, entry count, an independently computed footprint - would not agree with a wrong
  implementation.

- [x] Add the cases nobody wrote: `read_file`/`list_entries` through a file as a directory
  component, a full volume with a missing parent and with a file as parent, a path of only
  separators, a same-size rewrite under an allocator limited to the capacity, a late parent failure
  under allocator pressure, and reads and listings large enough that they should return `NoSpace`
  rather than abort.

## M0139i - The arena, if the guarantee has to be absolute

Everything above makes `Reserved` honest. Making it ABSOLUTE is a different design and is left as
one item so it is chosen rather than drifted into: take one arena at mount and allocate files,
names and nodes from it, handing nothing back to the global heap. That fixes at once the three
things the fixes above could only bound - a regrow that cannot fail because nothing is ever
returned, an entry whose real cost is charged because the node comes from the arena, and the last
infallible allocation, since `BTreeMap` is no longer in the path.

- [ ] Decide whether the system needs a memory volume that cannot degrade. Nothing writes to
  `vol://ram` yet, so the question is really about what M0138's LiveCD will put there.

## M0139h - Smaller

- [x] `read_file` and `list_entries` take `&mut self` while changing nothing.

- [x] `docs/LIBERMEMFS.md` is stale: it says ~320 lines and 17 tests where there are 437 and 19,
  and it says the crate implements the storage service's `FileSystem` trait, which the `MemFs`

## Explicit non-goals

No persistence, no snapshots, no copy-on-write, no checksums - all four protect against a medium
that is not present. No overlay or union mount: composing a read-only volume with a writable one
is a separate idea, needed for a live system booted from read-only media, and it belongs with
that work rather than here. No swap.
