# P02M0196 - Devices the firmware describes: identity, static tables, the device tree and ACPI's AML

Status: PROPOSED (2026-09-25) - WRITTEN FOR THE OWNER'S DECISION AND NOT APPROVED. Nothing here is scheduled
and nothing is started. It is written whole because the owner asked what the steps are and said he does not
want anything done half-way; P02M0190 (TPM) and P02M0195 (I2C) both depend on it.

WHAT THE PROBLEM IS. A driver in this system is an ordinary process, and it reaches hardware only through a
device DeviceManager has handed it: the claim is what gives it the device's registers and interrupts. That
works for every device that ANNOUNCES itself - PCI functions and USB devices answer "who is there?" with a
vendor, a product and an address. It does not work for the devices soldered to the board that announce
nothing, which the firmware alone knows about and describes in a map it hands the operating system at boot:
  - on PCs, ACPI - partly as TABLES of fixed shape ("the TPM is at 0xFED40000", "the debug serial port is
    here") and mostly as a PROGRAM in AML bytecode ("to read the battery, run method `_BST`"; "the touchpad
    is at address 0x2C on I2C controller 1, interrupt on GPIO pin 17");
  - on ARM and RISC-V boards, the DEVICE TREE - a plain tree of named nodes with addresses and interrupts.
This system reads that map only for what the kernel needs to boot - the FADT, the MADT, SRAT and SLIT, and
the device tree's memory, CPUs, interrupt controller and PCI host - and has NO IDENTITY for any other device
it describes: no name DeviceManager lists it under, no set of resources that belong to it, no rule for who may
claim it. So none of them can have a driver.

WHAT DEPENDS ON IT: the TPM driver (P02M0190), the ARM PL011 and 16550 UARTs, the ACPI battery, AC adapter,
thermal zones, lid and buttons (P02M0181's real producers), HID over I2C (P02M0195), the ACPI time-and-alarm
device, backlight, and system sleep.

## P02M0196a - Step 1: identity, and the devices static descriptions name

- [ ] A PLATFORM DEVICE in the device graph beside PCI and USB: a stable identity - for ACPI the namespace
  path with `_HID`, `_CID` and `_UID`, for a device tree the node path with its `compatible` and unit address -
  the resources that belong to it (MMIO ranges, interrupts, port ranges through P02M0191, GPIO and serial-bus
  connections), and a claim through DeviceManager exactly as a PCI function is claimed, with generations
  across a rebind.
- [ ] Drivers match on those identities (`_HID`/`_CID`, `compatible`) the way they match PCI IDs today.
- [ ] The static sources, which need no interpreter: ACPI tables of fixed shape (`TPM2`, `SPCR`, `DBG2`,
  `HPET`, `BGRT`) and, on ARM and RISC-V, every device-tree node with a `compatible` and resources.
- [ ] WHAT STEP 1 UNBLOCKS: the TPM driver on x86 (and on ARM through the tree), PL011 and 16550, the ARM RTC,
  and every simple device on a board.

## P02M0196b - Step 2: AML and the ACPI namespace

- [ ] An AML interpreter: the DSDT and every SSDT loaded into one namespace; method execution BOUNDED - time,
  recursion, memory, loop counts - because it is firmware code and it can be wrong; operation regions for
  system memory, system I/O (through P02M0191), PCI configuration, the embedded controller and the generic
  serial bus; `Notify` delivered as events. WHERE IT RUNS IS DECIDED FIRST, and the default proposal is a
  userspace ACPI service holding only the authorities its operation regions need, rather than the kernel.
- [ ] Namespace devices enumerated through `_STA`, `_INI` and `_CRS` into the platform devices of step 1, and
  `_DSM` and `_DSD` answered for the drivers that ask.
- [ ] The embedded controller driver, and the ACPI device classes on top of it: battery (`_BIF`/`_BIX`,
  `_BST`), AC adapter (`_PSR`), thermal zones with their trip points, lid, power/sleep buttons, backlight
  (`_BCL`/`_BCM`) and the time-and-alarm device - delivered to the power-state service (P02M0181) and the
  services that consume them.
- [ ] WHAT STEP 2 UNBLOCKS: laptops - battery, charging, temperatures, lid, backlight, and the I2C devices of
  P02M0195.

## P02M0196c - Step 3: power management through ACPI

- [ ] System sleep: suspend to RAM (S3) with `_PTS` and `_WAK`, every driver's suspend and resume, and resume
  proved to bring the machine back to where it was; soft-off (S5) through the same path the power button
  already reaches.
- [ ] Processor power: performance states (`_PSS`, `_PCT`, `_PPC`) and idle states (`_CST`, `_LPI`), under
  a policy the owner states.
- [ ] WHAT STEP 3 UNBLOCKS: a laptop that sleeps and wakes, and a CPU that does not run at full clock while
  idle.

## P02M0196d - Verification

- [ ] Host suites: the static-table readers against hostile fixtures; the interpreter against the ACPI
  specification's examples and ACPICA's AML test suite, as far as its licence permits using it; the device
  classes against scripted namespaces.
- [ ] In QEMU: its own DSDT enumerated and every device in it accounted for; extra SSDTs loaded with
  `-acpitable` that describe a battery, an AC adapter, a thermal zone and a lid whose methods read a memory
  region the harness controls - so a test can discharge the battery and open the lid; the TPM through its
  table; the device tree of `virt` on aarch64 and riscv64 with every node accounted for; S3 and resume in
  QEMU on x86_64.
- [ ] Recorded runs on real hardware where the owner provides it, never in place of an oracle.

EXCLUDES: firmware update (UEFI capsules); ACPI's platform error interfaces (APEI); vendor-specific WMI
methods; ARM's SCMI and power domains beyond what the device tree states.
