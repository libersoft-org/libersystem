## Goal

Give developers useful feedback within minutes while preserving every verification obligation.
Catch ordering and lifecycle defects in fast host tests, split ordinary verification into an inner
run and a merge run, and remove unnecessary waiting from guest checks.

The active requirements are below. Earlier proposals, withdrawn approaches and the exact previous
version are preserved in the [audit history](../../AI/audit/audit-P02M0177.md#2026-09-05-readability-and-implementation-readiness-revision).

## M1 - Host regressions for the three observed defects

- [x] Add one regression for each defect, driving the production decision or its production inputs.

| Defect | Required regression |
| --- | --- |
| A queued timeout disconnects an already ready driver | Apply `Ready`, then an already-generated `TimedOut` on the same binding generation. The first moves to `Online`; the second is refused, with no state move or failure cause. Also apply the opposite order: `TimedOut` ends the attempt with `HandshakeTimeout`, then late `Ready` is refused. |
| Disk probing and role hand-off disagree about provider order | Feed provider identities whose publication order differs from bus order through the two production derivations. Assert that both outputs name the same provider at every index. Comparing the same helper's output with itself is insufficient. |
| Volume services start before the service they depend on | Load the production manifest through its generator and drive the dependency scheduler. Require `iso_storage`, `media_storage` and `udf_storage` to start after `storage_service`, even though the generated manifest is sorted by name. Remove those dependency edges in the negative fixture and require failure. A synthetic manifest with correct dependencies alone is insufficient. |

Both timeout compositions drive the same pure reducer used by production and assert its entire
decision. Testing the queue's FIFO behaviour or `accepts_terminal_frame` alone does not meet this
requirement. The existing control is named
`a_ready_that_arrives_after_the_deadline_does_not_undo_the_timeout` in `driver-binding`.

Each regression names a reproducible pre-fix revision or carries an explicit negative mutation that
restores the corresponding defect. It must fail against that case. For startup ordering, the repair
in `ad3e28c7` added the manifest dependencies; the scheduler already obeyed declared dependencies.

## M2 - One tested decision before production effects

- [x] Extract the event reducer into `driver-binding` and route production through it once.

The reducer takes the binding state and one event. It decides admission, the next state if any,
and, for an ending attempt, its `FailureCause` and whether it is a planned stop. These types and the
transition table already belong to `driver-binding`; this extraction requires no new dependency.

The admitted outcome carries the event and the whole decision. The refusing outcome carries no
event. Preserve the existing classifications: `Stopped` means `FailureCause::Stopped`, `Exited` and
`Closed` mean `DriverExited`, `TimedOut` means `HandshakeTimeout`, and `Failed { code }` means
`DriverReported(code)`. Preserve planned-stop classification too.

`advance` consults the reducer on the unconditional normal event path before matching per-event
effects, preserving the existing teardown redirect. Refused events never reach an effect arm.
Publication, logging, supervision, teardown and spawning remain effects in `advance`. It consumes
the reducer's state, cause and planned-stop fields instead of recomputing them.

The effect match must receive its event only through the admitted outcome. Keep the original popped
event outside the scope of those arms, including any temporary used for the teardown redirect.
`BindingEvent` is `Copy`: passing an existing binding to a function alone does not consume it.
The chosen scope must make simply discarding or inverting the dispatch result fail to compile;
deleting the dispatch and introducing a new raw-event path is guarded by the source check below.
The reducer matches `BindingEvent` exhaustively, without a wildcard.

- [x] Add a source check over `device_manager.rs` and prove that it detects broken wiring.

Check the unconditional dispatch before the effect match, the admitted result as the source of that
match's event, and the absence of a raw event available to bypass it. No terminal arm may add its own
state predicate, choose a state for `move_to`, construct a `FailureCause`, or re-derive planned stop.
Run the check against five mutated source copies and require it to reject each:

1. Delete the dispatch and match the popped event directly.
2. Move the dispatch into one event arm.
3. Discard its result and match the raw event underneath it.
4. Reintroduce an arm-local state predicate.
5. Recompute a carried state transition or failure cause in an arm.

The timing regression supplies events in a chosen order; the reducer takes no clock. No shortened
deadline feature, runner profile or guest timing gate is required.

## M3 - Two verification tiers with a checked handoff

Implement M3.1-M3.5 in order, adding the corresponding M3.6 regressions with each step.

| Entry point | Responsibility |
| --- | --- |
| `./verify.sh` | Default inner tier: host work and x86_64 work assigned to it; reports its results and writes a handoff. It does not boot emulated targets. |
| `./verify.sh --merge FILE` | Complete the handoff at the proposed commit, including deferred emulated targets and guest-booting gates. |
| `./verify.sh --release` and `./verify.sh --sweep` | Existing flat paths, outside the partition, independent of the planner and unchanged by this milestone. |

Merge is run by the person proposing the change, after committing exactly the content tested by the
inner run. The runner does not create commits, check out revisions or provide a CI/timer service.
Release remains cumulative: it repeats work from both tiers and performs its own exhaustive work.

### M3.1 - Source and model identities

- [x] Add a commit-stable effective-tree identity and a separate source model hash.

The effective-tree identity describes files the build reads, independently of the index and commit
history. Use a canonical digest with these rules:

- Enumerate tracked and non-ignored untracked paths with `git ls-files -co --exclude-standard -z`.
  Read content and mode from disk. Cached paths absent from disk contribute nothing.
- Deduplicate entries, sort by path bytes, and keep paths NUL-safe throughout.
- Include path, file kind and content. For regular files include only the executable bit from the
  mode; for symlinks include the link target. Match the mode domain recorded by a git tree.
- Exclude ignored build outputs. Reject gitlinks: this repository has no submodules.
- Compute the same digest over a commit's tree using `git ls-tree -r -z` and its object content.

This identity survives committing unchanged content, including additions, deletions and unstaged
renames. It does not distinguish commits sharing a tree; M3.4 binds the revision separately.
Build inputs hidden by ignore rules are an ignore-rule defect, outside this mechanism.

The source model hash covers the selector sources, registry, configurations, graph, feature
meanings, architecture-risk scan and source-defined catalog facts. For kernel tests, hash the
complete set of IDs and `covers` read directly from `scan_source`, including tests absent from every
existing binary. Exclude binary-discovered applicability and the binary-dependent presence or absence
of kernel catalog rows. Merely omitting `variants` from today's catalog hash is insufficient.

Keep the existing `model_hash` unchanged for history and shadow records. Record it beside the new
source hash for diagnostics. At fixed source content, the source hash must remain identical before
and after first compilation, with missing or stale binaries, while source model edits still change it.
Keep `shadow::source_digest` unchanged too. This milestone precedes P02M0170; its stronger immutable
evidence identity replaces this minimum when that milestone lands.

### M3.3 - Inner partition, outcomes and handoff

- [x] Partition one selected plan and execute its inner share with honest status reporting.

Let `P0` be the original selected `PlanItemKey` set, `I` the inner-owned keys and `D` the deferred
keys. Check `I ∩ D = ∅` and `I ∪ D = P0`. Partition the existing selection; do not select fewer tests
by tag. Architecture-risk rules remain widening-only. Any future narrowing still requires
P02M0167's frozen candidate, shadow evidence and activation process.

Execution uses prerequisite-closed sets of `Step`s. A prerequisite needed by both tiers may run in
both, but its keys are accounted to exactly one tier. A step with no keys is valid only as a
prerequisite. Place work requiring deferred guest output in a tier where its dependencies can run.

Take the effective-tree identity before planning and revalidate it after the final inner step.
If it moved, report both values and do not emit a usable handoff. The handoff carries:

- Effective-tree identity, source model hash and diagnostic `model_hash`.
- Original plan digest, per-key outcomes for the inner share, and the exact deferred set.

Missing or failed inner outcomes cannot count as successful verification. The mutable history/cache
is not a substitute for these outcomes and is not frozen into the handoff as authoritative evidence.

Every dirty inner run owes merge, even when `D` is empty. A passing inner share reports `INCOMPLETE`
and exits 6, names the remaining obligation and prints its handoff path and merge command. It cannot
report `FULL` or complete verification. Preserve failure reporting and the distinct nonzero meanings
of `INCOMPLETE`, `SHADOW` and `STALE`; a tier verdict cannot override them. Completion exit zero is
reserved for a completed merge or a completed flat verification path. Planning/display commands keep
their existing non-verification meaning.

`--budget` remains available for inner. Tools that define or judge the system, including the harness,
`mkpackages`, `system-manifest`, `lsidl-gen` and `verify-model`, retain full-selection escalation.

### M3.4 - Pin merge and refresh its inventory

- [x] Validate the handoff and prepare current test discovery before lowering executable steps.

Reject `--budget` before any inventory build. Resolve `HEAD` once to commit object ID `REV`; require
exactly one parent. Require agreement between the inner snapshot, current effective tree and the
canonical tree of `REV`. Require the source model hash to agree and `I` and `D` to be disjoint.
Name the disagreeing values when refusing a handoff.

Regenerate `P1` using `changes::range(parent(REV)..REV)` and `Model::plan` with live verification
history. A plan digest or artifact-only `model_hash` difference is reported, not grounds for refusal.
An ordinary dirty-to-commit transition must work; `Untracked` versus `Added` does not change selection.

Determine inventory targets from the full relevant plans, not just merge's remaining work: take the
concrete architecture targets in `I ∪ D ∪ P1` and the build/boot targets required by those plans'
architecture policy. Include x86_64 even if all its visible keys already belong to `I`. Host-only
work with no concrete target does not imply a kernel inventory build.

Build each target's test inventory from the proposed source via M3.2. Re-derive discovery and
regenerate `P1'` from the same pinned commit delta, then reconcile as M3.5 specifies. This is one
inventory phase and one reconciliation, with no discovery fixpoint or mid-execution plan extension.
There must still be one steps file and one lowering, after inventory preparation.

After inventory preparation and after the final executable step, recheck the effective-tree identity
and that `HEAD` still resolves to `REV`. Report both values and refuse completion if either moved.
A different-parent commit with the same tree must still be rejected if it replaces `HEAD` mid-run.

On a cold checkout the inventory phase moves the required test compilation earlier. The later
selected run may compile again because `TEST_SELECTION` is baked in through `option_env!`; measure
that incremental overhead separately from cold compilation.

### M3.5 - Reconcile obligations and account for completion

- [x] Preserve deferred work, add newly selected work and explicitly account for missing variants.

Use set union for `∪` and set difference for `−`:

```text
P0 = I ∪ D
W0 = D ∪ (P1 − (I ∪ D))
R  = keys in W0 whose variants the refreshed catalog proves absent
A  = P1' − (I ∪ D ∪ P1)
W  = (W0 − R) ∪ A
```

Every deferred key remains owed even if the live cost cache stops selecting it: `D − P1` still runs
when its variants exist. A new build proving a test no longer exists on that target permits retirement
instead. Retirements may come from `D` or from the extra keys in `P1 − (I ∪ D)`; name their reasons
and count. Retirement requires agreement of the source model hash and a refreshed catalog unable to
lower that variant. An unrelated lowering error is a refusal, not retirement.

Perform this reconciliation before lowering `W` into prerequisite-closed steps. No unlowerable key
may reach execution. Newly discovered keys must run and receive their own recorded outcomes; an
unattributed whole-suite pass does not answer for them. A deferred whole-suite fallback remains owed
alongside newly discovered specific keys if the catalog still supports it.

Every obligation must be accounted for. A key is discharged by passing or by a justified retirement;
a failed key is never discharged. Merge claims completion only with both shares present and every
required key discharged, including additions. Plan/cache drift alone cannot erase promised work.

A changed base is not itself a refusal. If the resulting tree matches the tested tree, regenerate
against the new parent and run any additional keys. If the resulting tree differs, refuse the
snapshot mismatch. Root and merge commits remain unsupported by this entry point.

### M3.6 - Acceptance corpus

- [x] Cover the following cases through the actual tier entry points or their shared production seams.

| Case | Required result |
| --- | --- |
| Ordinary dirty change committed exactly as tested | Accept the handoff, with no added work when the inputs and selected keys agree. Repeat for a new file, deletion and unstaged rename. |
| Partial staging: tested worktree B, committed staged content A | Refuse. An index/worktree disagreement is acceptable only if the proposed commit ultimately contains the tested content. |
| Path content, mode, deletion or rename changes after inner | Refuse the changed tree and name the disagreement. |
| Same final tree proposed over a different parent | Find and run any keys added by the changed delta. Test with both empty and non-empty `D`; accept when no extra keys are needed too. |
| Verification history crosses the 0.9 escalation threshold | Drive both directions between inner and merge, including inner step recording. Added keys run; cost contraction still runs every applicable key of `D − P1`. |
| First build discovers previously unavailable tests | Accept artifact-only drift. The source hash agrees before and after compilation, including with no binaries at all or a newly declared test absent from all old binaries. Changed source model facts still cause refusal. |
| Old aarch64/riscv64 binaries hide new applicable tests | Refresh them; every newly selected test runs on every applicable deferred target and has its own key outcome. |
| All visible x86_64 keys are in `I`, stale merge inventory hides a new x86_64 test, `D` contains only ports | Refresh x86_64 too; discover and execute the missing obligation. |
| A test keeps its ID/coverage but its target `cfg` removes a variant | Retire and name it without handing an unknown ID to a guest. Test separately for a key from `D` and one from `P1 − (I ∪ D)`. Combine with cost contraction and keep the other `D − P1` work. |
| A normal `.rs` edit occurs during execution without changing the source model hash | Inner emits no usable handoff; merge refuses completion. Exercise both tiers. |
| `HEAD` moves mid-merge to a different-parent, same-tree commit selecting extra keys | Refuse even though content digests still agree. |
| Passing inner share with empty deferred work | `if ./verify.sh; then publish; fi` must not publish; report incomplete and exit 6. |
| An inner-only run started from a full plan | Never report `FULL` or complete verification. Preserve nonzero evidence statuses and reject missing/failed inner evidence. |
| Merge with `--budget` on a fresh checkout | Reject before any inventory build, including a zero or tiny budget. |
| Prerequisite shared by tiers | Execute where required, account its keys once, and preserve dependency failure handling. |
| A genuinely scopeable host-tool change | Run inner then merge and observe every deferred key accounted for. A docs-only or already-scoped service fixture is insufficient for this tiering acceptance case. |

For each case record the launcher, final success/refusal signal, required failure checks, observation

| Case type | Earliest permitted successful end |
| --- | --- |
| Loader-only | Its final loader verdict, or a hand-off after which no required assertion remains. |
| Altered system volume | The refusal after the volume is read; `loader: kernel loaded` is an intermediate signal. |
| Guest health | Final positive signal plus the required late-failure observation. Preserve checks for later panic, reset/reboot, driver restart, fault and retracted success, including the IOMMU gate's existing observation. |
| Silent firmware refusal | A positive external oracle; otherwise retain the calibrated timeout backstop. Silence alone cannot justify an earlier successful end. |

Require failures for early success followed by panic, reset, or retraction. A shared implementation
may serve multiple cases, but one global success-marker list cannot replace their distinct verdicts.

## M5 - Safe default concurrency in merge

- [x] Make ordinary `./verify.sh --merge FILE` request two guest slots by default.

An explicit `--jobs` overrides the default in either direction. `verify.sh --jobs` remains the only
scheduler; the flat release and sweep paths remain serial. On a scenario selecting both emulated
targets, demonstrate their guests overlap without supplying `--jobs 2` explicitly.

- [ ] Preserve correctness of every guest step enabled by this default, including shared build inputs.

Private producer acquisition, writable media and the contention regressions are implemented and
passed. This broader validation item remains open because the IOMMU traffic gate is still failing
and its baseline comparison did not reach runtime. Real aarch64/riscv64 guests passed 13 tests each
and overlapped for 194.217 seconds through the production scheduler without an explicit `--jobs`.

The scheduler can overlap guest-booting gates and profile rows as well as architecture suites.
Audit their shared producer outputs. In particular, `signed-boot` builds a trust-profile loader under
the shared lock but copies `LOADER_OUT` after releasing it. Acquire a run-private copy while still
holding the producer lock, or provide equivalent serialization through the existing scheduling and
locking mechanisms. Guests must receive the profile intended by their own case.

Add a deterministic regression that places a competing loader-profile build between the first
build and its former unprotected copy point. Require the first run to retain its intended loader
and verdict, and show that the regression detects the old sequence. Preserve private writable media
and run-specific log ownership throughout overlapping runs.

## Performance acceptance protocol

Use separate disposable workspaces for the pre-implementation revision and the completed milestone
revision on the same otherwise idle machine. Record both revisions, CPU, RAM, toolchain, QEMU,
acceleration settings, selected profiles and background load.

The service-change fixture is this exact one-line change in
`src/user/services/core/src/log_service.rs`:

```diff
-const JOURNAL_CAP: usize = 4096;
+const JOURNAL_CAP: usize = 8192;
```

It changes an in-memory journal limit and is a measurement fixture only, not a requested product
change. Keep it as the only uncommitted change at the start of each measurement. This performance
scenario is separate from M3.6's host-tool coverage test.

Measure two cache conditions:

- **Warm incremental:** prepare each revision's unmodified tree with the artifacts required by the
  scenario on all selected targets. Save that starting state, then apply the patch. Restore the
  starting state before each repetition; do not reuse artifacts built from the patched source.
- **Cold workspace:** start without repository build outputs or shared compiled artifacts. Installed
  toolchains and downloaded dependencies may remain; record them explicitly. Keep the initial
  verification history and trust/evidence conditions reproducible per revision and record them
  separately from compiler caches. Do not manufacture trusted evidence to obtain a passing time.

Measure the old `./verify.sh --for-change`. For the new workflow measure inner, commit exactly the
tested content, and measure `./verify.sh --merge FILE` using its default concurrency. Exclude manual
commit time; report inner, merge and their sum. Record any prerequisite preparation outside the timed
commands so cold-workspace costs cannot disappear from the comparison.

Run three warm repetitions and one cold repetition per revision. Preserve individual durations,
warm median/range, exits, per-step times, selected/deferred/completed/retired keys, evidence status,
plan changes and fallback decisions. Explain coverage differences before claiming a speedup.
Early failure or an incomplete merge is not a successful verification timing; inner exit 6 is the
expected handoff status.

The acceptance goal is an inner service-change loop measured in minutes and a merge run measured in
tens of minutes under the warm conditions above. Report cold results separately. Time the complete
