# P02M0175 - Dual-stack transports, DNS and NetworkService

Status: PLANNED AFTER P02M0174. FUTURE-TRACK NETWORKING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Carry P02M0174's IPv6 addresses through UDP, TCP, DNS, the public NetworkService contract and the
network tools, producing one coherent IPv4/IPv6 dual-stack appliance rather than a private L3 feature
which applications cannot name.

TLS is not part of this milestone. It authenticates and protects application transports and should
be designed after the address/socket contract is correct, not hidden inside an IPv6 rollout.

**The UDP deliverable is decided here rather than left to implementation.** UDP in this milestone
means the named INTERNAL operations: DHCPv4, and DNS and SNTP over BOTH address families. "Plus
their IPv6 equivalents" was the previous wording and it was wrong about DHCP: this file refuses
DHCPv6 by name and M0174 assigns IPv6 configuration to SLAAC and RDNSS, so there is no IPv6
equivalent of the DHCP client and the test matrix must not imply one (corrected 2026-08-30).

There is NO public datagram bind/send/receive API. Adding one would be a second unplanned
public contract on top of a transmit-side TCP implementation this milestone already has to build,
and the tools this milestone migrates do not need it. If an application ever needs datagrams, it is
its own reviewed requirement with scoped endpoints, conflict rules and queue budgets.

## What is there now, and what it forces

- There is NO transmit-side TCP. `TcpConn` holds sequence counters and a receive buffer; it stores
  no unacknowledged bytes, no peer MSS and no send window. `tcp_build_data` advances `snd_nxt` past
  a one-shot frame and retains nothing, and `socket.send` truncates the caller's buffer to one
  segment, transmits once, closes the buffer and reports success. Only SYN has a retransmission
  loop. So "resegment and retransmit outstanding data after a PTB" cannot be implemented as an
  addition - there is no outstanding data to resegment, and loss is currently unrecoverable.
- DNS is uncorrelated. Any UDP datagram whose SOURCE port is 53 is handed to the parser; the
  destination port, the server address, the UDP length and checksum are unchecked, and the parser
  ignores the transaction ID, QR/opcode/rcode, the question section, the answer owner and CNAME
  chain, returning the first A record. `resolve` collapses every failure to `NotFound`.
- An inbound SYN allocates a TCB BEFORE any socket channel exists. `tcp_alloc` reuses a free slot or
  unconditionally pushes a new one - the pool has no cap - and every fresh TCB allocates 65,535
  receive bytes, growing to 262,140 when the peer offers window scaling. P02M0080's claim that the
  domain handle budget is the true ceiling does not hold for this path, because a half-open TCB
  consumes no handle.
- The public contract is IPv4-shaped and unbounded: `endpoint` is an `ipv4-addr` and a port,
  `net-info` carries one address and one gateway with an unbounded neighbour list, `listen` takes a
  bare `u16`, and `network.lsidl` contains no `@bound` at all - so the schema advertises requests
  larger than the service's 1024-byte request and 4096-byte reply buffers can receive.
- Boot blocks on DHCPv4 before entering the serve loop and then installs a hard-coded IPv4 fallback.
  The loop schedules only the lease deadline, and the synchronous helpers discard unrelated events.
  An IPv6-only profile would still wait for DHCPv4 and silently acquire v4 state.
- `service-logic` is the host-testable boundary; the `services` binary links `rt` and cannot be
  host-tested. Every pure decision added here goes there.

## Work

- [ ] **M1 - the IDL represents either address without ambiguity, with stated fields and bounds.**
  Enumerate the exact records, variants and operation signatures BEFORE implementation; a list of
  record names is not a wire contract and two reasonable implementers will produce incompatible ones.

  Add an exact 16-octet IPv6 wire value as a fixed positional record (matching the current
  four-octet IPv4 record), not `list<u8>` plus `@bound(16)`, which permits shorter values. Add a
  closed `ip-address` variant and a distinct interface-qualified/scoped address form. Define:

  - a stable INTERFACE IDENTITY with a generation, so a scoped value cannot silently refer to a
    replaced interface, and the valid and invalid scope combinations for each address class;
  - ADDRESS STATE (tentative, preferred, deprecated, invalid) with prefix and lifetimes;
  - ROUTE, ROUTER and DNS-SERVER entries as their own records, plural, replacing the single gateway
    and DNS fields;
  - a LISTENER BIND MODE - IPv4-only, IPv6-only, dual-stack wildcard - and a local scoped endpoint,
    with the conflict and reuse rules for two binds on the same port. `listen(port)` cannot express
    any of the three cases M3 implements and M9 tests; and
  - LOCAL AND REMOTE endpoints on accepted and live sockets, so `ss` can report what a socket
    actually is.

  **AND THE BOUNDS ARE NUMBERS, CHOSEN HERE** (corrected 2026-08-31). A previous version said to
  assign an explicit `@bound(n)` to every variable-length occurrence and named no `n`, and said to
  define aggregate budgets and named no budget. Those are POLICY choices - nothing derives them, two
  implementers pick differently, and the wire-size gate has nothing to check against. They are also
  the choices that decide whether the service's existing 1024-byte request and 4096-byte reply
  buffers survive the migration, which is a question this file may not leave open:

        MAC address                       6      fixed, not a bound
        interface name                    16
        host name / qname                 253    the DNS maximum, so a legal name is never refused
        neighbour list                    64
        address list per interface        16
        route list                        32
        router list                       8      matches P02M0174's bounded default-router list
        DNS-server list                   4
        socket list                       256
        TCP request string                1024
        fetch chunk                       4096   ONE chunk per reply - see the fetch shape below
        traceroute hops                   32
        ping sequence                     64

    AND THE FRAMING FOLLOWS FROM THEM RATHER THAN THE OTHER WAY ROUND. The largest single reply is
    the socket list, and 256 entries of a local plus a remote scoped endpoint do not fit in 4096
    bytes - so the reply buffer becomes 65536 and the request buffer 8192, both stated here so the
    migration cannot land a wire the service cannot receive. A list whose bound would exceed the
    reply buffer is a bound to lower or a buffer to raise, decided here and not discovered at run
    time.

    AND THE FETCH IS A STREAM, BECAUSE "65536 IN CHUNKS OF 4096" WAS NOT A SHAPE THE WIRE HAS
    (corrected 2026-09-01). That line named a total and a chunk size and no operation that carries
    them: `fetch` today returns one inline `list<u8>`, and LSIDL caps a `list` length prefix at
    `u16`, so 65536 is not merely large - it is one more than the encoding can express. The number
    and the shape were both wrong, and a bound that cannot be encoded is worse than an unstated one.
    The operation returns a `stream<chunk>`, the same shape `listener` already uses to hand back a
    channel: the client reads chunks of at most 4096 bytes until the stream ends. Nothing inline
    carries a body, so no total needs to fit a list length, and the per-flow receive budget below is
    what bounds how much a client may have outstanding. A body that exceeds that budget ends the
    stream with the explicit truncation signal rather than refusing, which is the one place
    truncation is allowed and is unchanged.

    PER-CLIENT AND PER-FLOW BUDGETS, in the same spirit: 16 concurrent sockets per client, 64 in
    total; 4 in-flight DNS queries per client and 16 in total; 256 KiB of unacknowledged TCP data per
    flow and 4 MiB across the service. Overflow is a typed refusal everywhere except the fetch body,
    which carries the truncation signal above.

    AND THE SEMANTIC FIELDS THE MIGRATION CHANGES ARE NAMED, since a bound on a record nobody has
    described is a bound on nothing (added 2026-09-01). Field ORDER, ordinals and exact spelling stay
    in the reviewed IDL - that division is unchanged - but WHICH fields exist is a decision this file
    owes:

      interface identity   an opaque `u32` index plus a `u64` generation. The generation is what makes
                             a scoped address refuse after the interface is replaced, which is the
                             whole reason the identity is not just the index
      route                destination prefix and length, next-hop `ip-address`, the interface
                             identity, a preference, and the lifetime remaining
      router               its `ip-address`, the interface identity, preference, reachability state
                             and lifetime remaining - the fields P02M0174's default-router list keeps
      DNS server           its `ip-address` and the interface identity, which is what makes an
                             interface-qualified RDNSS expressible at all
      listen               takes a bind mode (IPv4-only, IPv6-only, dual-stack wildcard), a local
                             scoped endpoint and a backlog, and returns the listener channel
      accept               returns the accepted socket channel plus BOTH endpoints, local and remote,
                             each scoped
      live socket          local and remote scoped endpoints and the connection state, which is what
                             makes `ss` able to report what a socket is rather than only that it
                             exists

  What this file does NOT freeze, deliberately: the field ORDER, the ordinals and the exact LSIDL
  spelling of each declaration. Those live in `src/idl/network.lsidl`, which is the reviewed artifact
  and the one a generator reads; copying them into a plan creates a second source of truth that will
  disagree with the first the moment either is edited. What a plan owes is the decisions a reader
  cannot derive - which records exist, which fields they carry, and the numbers above - and those are
  here.

  Reconcile the bounds with the service's framing buffers: the wire may not advertise a request the
  service cannot receive. Define per-client and per-flow aggregate budgets, typed overflow versus
  deterministic truncation with an explicit truncation signal where truncation is allowed, and
  fallible allocation. Test exact-bound and over-bound encodings and the rollback and accounting on
  refusal.

  Migrate endpoint, neighbour, route, DNS-server, interface, ping, traceroute and socket-information
  records to the appropriate form. Every stored or transmitted link-local value, including RDNSS,
  carries its interface; scope is rejected where nonsensical. Because the current protocol generation
  is not frozen as a third-party ABI, make one reviewed compatibility-manifest update and migrate all
  first-party callers atomically rather than maintaining two indefinite parallel APIs, and add
  encode/decode/layout and cross-caller migration fixtures.

- [ ] **M2 - TCP acquires a bounded transmit side.** This is new implementation, not a family
  parameter added to existing code, and everything else in this milestone that mentions
  retransmission depends on it:

  - an owned per-connection queue of UNACKNOWLEDGED bytes, with a hard per-flow and aggregate byte
    budget;
  - peer MSS from the SYN, an effective MSS derived from interface and path MTU, and a tracked send
    window;
  - segmentation of a caller's buffer across several segments, and partial-write backpressure with
    a defined contract for whether `send` reports bytes ACCEPTED or bytes acknowledged - the current
    silent truncation to one segment is a data-loss bug reported as success;
  - ACK retirement with wraparound handling;
  - resegmentation and retransmission of outstanding data within a smaller MSS after a validated
    Packet Too Big; and
  - FIN IS SEQUENCE SPACE AND IS RETRANSMITTED LIKE DATA (restored 2026-08-31). This was accepted and
    promised in an earlier round - "an RTO for data and FIN" - and then went missing from this item,
    which describes only unacknowledged data and segments. It is not a detail: FIN consumes a
    sequence number, so the connection owns it exactly as it owns a byte, and the current teardown
    shows what its absence costs - it builds one FIN, sends it once, pumps briefly for the peer's
    FIN and then frees the control block, so a lost FIN or a lost final ACK ends the connection
    half-open on the peer with nothing left to retransmit from. The transmit side therefore RETAINS
    the FIN's sequence position in the same unacknowledged queue as data, retransmits it under the
    same RTO and backoff, closes under the same retry limit, and the control block survives until the
    closing handshake is acknowledged or that limit is reached - a typed expiry rather than a fixed
    brief wait.

  **AND A BOUNDED BASIC SENDER PROFILE, BECAUSE "AN RTO AND A RETRY LIMIT" IS NOT ONE** (corrected
  2026-08-30). A fixed timeout with no backoff and no flight limit is a retransmit loop, not a TCP
  sender: it collapses under a changed path and it can congest one. These are BASIC requirements and
  are distinct from the advanced congestion control this milestone refuses. The profile is:

    the profile       RFC 6298 for the RTO and RFC 5681 for the loss response and windows. Named,
                        because "standard" is not a specification and two implementations can satisfy
                        every qualitative test below while disagreeing about every number in it
                        (added 2026-09-01)
    RTT and RTO       RTT sampling with Karn's rule (no sample from a retransmitted segment),
                        smoothed RTT and variance per RFC 6298, initial RTO 1 s until the first
                        measurement, a floor of 200 ms and a ceiling of 60 s. Exponential backoff -
                        doubling - on each retransmission of the same segment, reset when a new
                        measurement arrives
    flight limit      a congestion window with slow start and congestion avoidance per RFC 5681: an
                        initial window of 10 segments, a loss response that halves the window and
                        sets the slow-start threshold to the halved value, and the standard
                        additive increase in congestion avoidance. The sender never has more
                        unacknowledged bytes in flight than the smaller of the congestion window and
                        the peer's advertised window
    ZERO WINDOW       PERSIST is its own mechanism, not a retransmission. When the peer advertises a
                        zero window the sender starts a persist timer and probes; without it a lost
                        window update deadlocks the connection permanently, which is a correctness
                        failure rather than a performance one
    retry limit       8 retransmissions of one segment before the connection is closed with a typed
                        error, and 5 for a SYN. With the backoff and ceiling above that is roughly
                        ten minutes for an established connection, which is the order RFC 1122's
                        R2 asks for without inheriting its exact arithmetic

  Explicitly still refused, and unchanged: CUBIC, BBR or any modern congestion-control algorithm,
  SACK, ECN, pacing, and delayed-ACK tuning. The line is that a sender must not deadlock, must not
  ignore loss and must not ignore the peer's window; how fast it goes otherwise is not this
  milestone's subject.

  Test: a changing RTT moving the RTO, backoff across successive retransmissions of one segment, the
  congestion window limiting bytes in flight, a peer window closing to zero and reopening, and a LOST
  window update recovered by persist rather than by timeout.

  Test partial ACK, loss, sequence wraparound, PTB resegmentation, close with data in flight, and
  budget refusal, alongside the sender-profile cases above. And the two FIN cases specifically, which
  "close with data in flight" does not reach: a LOST FIN, retransmitted until acknowledged, and a LOST
  FINAL ACK, where the peer's retransmitted FIN is answered rather than arriving at a control block
  that has already been freed.

- [ ] **M5 - source and destination selection follow a pinned algorithm, OVER M0174's CANDIDATES.**
  "IPv6 first" is not an algorithm and will not survive multiple prefixes, deprecated addresses or a
  candidate with no route.

  **THE OWNERSHIP BOUNDARY IS M0174'S AND IS NOT RESTATED HERE** (corrected 2026-08-30). A previous
  version had this milestone owning route and neighbour lookup, PMTU refusal and source selection
  while also saying it only consumes a frozen seam - and M0174 said its egress returns the selected
  source, route, next hop and PMTU and that this milestone adds nothing. Both could not be true. The
  division is now stated once, in M0174: that layer owns the tables and ENUMERATES candidates; this
  one CHOOSES among them. So this item does not implement route or neighbour lookup and does not own
  the PMTU cache - it queries them - and what it owns is the choice.

  Pin the applicable RFC 6724 profile for both default source-address selection and
  destination-address ordering, including the policy table, the tie-breaks this appliance uses, and
  any RFC 8028 route/interface update it adopts. Define candidate filtering, scoped-zone handling,
  explicit caller overrides, failure and fallback TIMING, and behaviour after an address or route is
  invalidated.

  DEPRECATED IS A PREFERENCE, NOT AN EXCLUSION (corrected 2026-08-31). A previous version said "never
  choose a deprecated source for a new connection", which contradicts the RFC 6724 profile pinned in
  the same paragraph and the caller override named beside it. RFC 6724 section 5 rule 3 PREFERS a
  non-deprecated source between two candidates; it does not remove a still-valid deprecated address
  from the candidate set, and the specification expressly does not override a caller's legal explicit
  choice. Implemented as an exclusion, new connectivity ends at PREFERRED-lifetime expiry instead of
  at VALID-lifetime expiry - so an appliance whose only remaining address is deprecated stops being
  able to open connections while its address is still usable, which is a self-inflicted outage rather
  than a policy. The rule is therefore: prefer a non-deprecated candidate; use a deprecated but still
  valid one when it is the only candidate; and honour an explicit caller choice of one. Only
  TENTATIVE addresses are excluded from the candidate set outright, as the same section requires.

  Test mixed A/AAAA answers, multiple prefixes and routers, tentative addresses excluded, link-local
  scope, and a candidate with no usable route - plus the two cases the old exclusion rule would have
  failed: a deprecated address that is the ONLY candidate, which must be selected and must carry
  traffic, and an explicit caller override naming a deprecated address while a preferred one exists,
  which must be honoured.

- [ ] **M6 - DNS is correlated, validated and bounded.** Validate UDP framing, length and checksum,
  and correlate a response by family, the scoped server it was sent to, the local and destination
  ports, the transaction ID, the normalized qname, the qtype and the qclass - today any datagram
  with source port 53 is accepted, so a spoofed or cross-query answer is indistinguishable from the
  real one.

  **AND THE MATCHED TUPLE MUST BE UNGUESSABLE, OR MATCHING IT PROVES NOTHING** (added 2026-08-31).
  Correlation was specified as a set of fields to COMPARE and never as a requirement on how they are
  GENERATED, which leaves the spoof-rejection claim in this milestone's Definition of done false: the
  current resolver sends from a fixed source port `0x9876` and increments its transaction ID by one
  per query, so an off-path forgery that guesses the tuple satisfies every rule above and is accepted
  as the real answer. RFC 5452 section 9.2 requires unpredictable query IDs AND unpredictable source
  ports, spread over the available ranges, because those two fields are the whole of a stub
  resolver's off-path defence. So: a fresh unpredictable transaction ID and a fresh unpredictable
  ephemeral source port PER QUERY, both drawn from the same randomness the SNTP and DHCP items below
  already require; in-flight queries are bounded and a drawn tuple that collides with a live one is
  redrawn rather than reused; and the tuple is retired when its query completes or expires, so a
  late answer to a finished query matches nothing.

  Its negative fixtures are the discriminating ones: an answer carrying the NEXT sequential
  transaction ID and the previously used source port is REFUSED, and so is a correctly formed answer
  arriving after its query has been retired - neither of which a resolver with a predictable tuple
  can reject. Validate QR, opcode, rcode and the section counts; validate the answer owner and the
  CNAME chain; bound name-compression traversal and reject compression loops; respect TTLs.

  Return a bounded ordered list of typed addresses rather than one IPv4 address. Any link-local
  result carries its interface provenance in M1's scoped form, or is rejected when the resolver
  cannot determine it; it may not escape as a bare `ip-address`. Preserve distinct timeout,
  malformed, no-record and transport errors instead of collapsing them.

  On a truncated response, retry over DNS/TCP with two-byte length framing, as RFC 7766 section 5
  requires of a general-purpose stub resolver - AAAA and CNAME sets are exactly the answers that
  overflow. This depends on M2 and is ordered after it. An IPv6-only boot can use interface-qualified
  RDNSS from P02M0174; dual-stack boots retain the IPv4 DNS path. Test spoofed answers, cross-query
  answers, compression loops and the TCP retry.

- [ ] **M8 - EVERY internal UDP operation is correlated and validated, not only DNS** (added
  2026-08-30). M6 gives DNS a full correlation and validation contract and a previous version left
  SNTP as "migrate it" and DHCP as "remains green". Both are the same class of defect as the DNS one,
  and both are worse in effect:

    SNTP   the client's request is 48 bytes with only the first set, so its TRANSMIT TIMESTAMP IS
             ZERO - there is no per-request value at all - and the reply is accepted on source port
             123 alone, parsed for a transmit timestamp, and used to SET THE WALL CLOCK. A single
             forged datagram moves system time. So: a random non-zero transmit timestamp per request,
             recorded and matched against the reply's ORIGINATE timestamp; full tuple, UDP length and
             checksum validation; and mode, version, leap-indicator and stratum validated, with
             leap-indicator "alarm" refused as unsynchronised.

             AND THE SERVER'S OWN TRANSMIT TIMESTAMP IS VALIDATED, WHICH IS THE FIELD THAT MOVES THE
             CLOCK (corrected 2026-08-31). The rules above validate the ORIGINATE field - the echo of
             what this client sent - and left the reply's TRANSMIT field, the one `parse_sntp` reads
             at offset 40 and hands to TimeService as wall-clock time, entirely unchecked. Two
             requirements, both from RFC 5905's packet sanity checks: it must be NON-ZERO, because a
             zero transmit timestamp names a server that never set it; and it must DIFFER from the
             last accepted reply's transmit timestamp, because an identical one is a replayed
             datagram and not a second reading of the same clock.

             STRATUM IS `1..=15`, NOT "NOT 0 AND NOT 16" (corrected 2026-08-31). The previous rule
             refused 0 and 16 and accepted 17 through 255, which are reserved and are not valid
             server strata at all - so a forged reply carrying stratum 200 passed a check written to
             catch exactly that. 1 is a primary server, 2 through 15 are secondary, 0 is unspecified
             or a kiss-o'-death, 16 is unsynchronised, and everything above is reserved.

             Fixtures: a spoofed reply, a replayed reply (byte-identical, proving the duplicate
             transmit timestamp is what rejects it), a reply answering a different request, a reply
             with a zero transmit timestamp, and replies at strata 0, 16 and 17 - each proving the
             stored wall clock is UNCHANGED, because a validation that rejects a reply after
             TimeService has already applied it is not one
    DHCP   the client uses a FIXED transaction ID - its own comment says "SLIRP is the only DHCP
             source" - and accepts the first OFFER or ACK of the expected type without checking
             `xid` or `chaddr`. A random `xid` per exchange and `chaddr` matching are necessary and
             NOT SUFFICIENT, which an earlier version stopped at (corrected 2026-08-31): every
             legitimate server answering the same discover shares that `xid` and that `chaddr`, so
             those two fields cannot pick the offer the client selected. And the ordering is worse
             than the matching: `parse_dhcp` writes the parsed lease into the stack BEFORE its caller
             looks at the message type or the client's state, so a late or losing reply mutates
             stored lease data even when the caller then ignores the event.

             So DHCP becomes a STAGED, STATE-SPECIFIC TRANSACTION:
               framing     full UDP validation like SNTP's - source and DESTINATION port, length and
                             checksum - rather than dispatch on source port alone
               selection   the client SELECTS one offer and freezes the server identifier and the
                             requested address; from then on a reply is admissible only if it comes
                             from that server for that address
               state       which message is admissible is a function of the phase: SELECTING takes
                             OFFERs and nothing else; REQUESTING takes an ACK or NAK from the
                             selected server; RENEWING takes an ACK or NAK from it; REBINDING
                             takes one from any server, which is the one phase where a new server is
                             legitimate and the phase that says so
               destination ACK AND NAK HAVE DIFFERENT DESTINATION FORMS AND THE PHASE DOES NOT DECIDE
                             THEM (corrected 2026-08-31). A previous version had RENEWING take "a
                             unicast ACK or NAK", which is wrong for half of it: RFC 2131 section 4.1
                             requires a server to BROADCAST every DHCPNAK to `0xffffffff` whenever
                             `giaddr` is zero - a renewal whose REQUEST was unicast included.
                             Implemented literally, the client discards the conforming NAK for a
                             lease the server has just declared invalid and goes on using it, which
                             is the one outcome the whole staged transaction exists to prevent. So
                             the two are frozen separately: an ACK is admitted in the destination
                             form its phase implies - unicast to `ciaddr` while RENEWING, and the
                             broadcast-flag/`yiaddr` rules otherwise - while a NAK is admitted
                             BROADCAST in every phase, and the framing check above must therefore
                             accept a datagram addressed to the broadcast address on the client port
               commit      the lease is validated COMPLETELY and only then committed, atomically. A
                             frame that is not admissible in the current phase changes nothing at
                             all, which is the property the current write-then-check order cannot
                             have

             Fixtures: a foreign `xid`, a foreign `chaddr`, a competing valid OFFER from a second
             server, a valid ACK from a server that was not selected, a NAK in each phase, and a LATE
             reply arriving after the phase moved on - each proving the stored lease is unchanged.
             Plus the case the generic per-phase NAK does not reach: a BROADCAST NAK answering a
             UNICAST renewal request, which must be ACCEPTED and must invalidate the lease. A client
             that admits only unicast replies while RENEWING passes every other fixture here and
             fails this one

  These belong here rather than in a later milestone because this milestone rebuilds the event and
  pending-operation model that correlation needs, and preserving the current behaviour as "green"
  would carry an unauthenticated clock and lease path across the rebuild.

  `traceroute`, `nslookup`, `nc`, `tcp`, `httpd` and every other current consumer selected by the

  common interface view or a clearly named ND view. Permission manifests do not gain raw NIC access.

  Textual forms are THREE separate grammars, not one parser decision:

  - RFC 5952 canonical rendering for display;
  - a bounded RFC 4007 `%zone` UI convention for input, mapped to M1's stable interface identity.
    A zone identifier is local UI scope: it is not part of an origin and is never transmitted; and
  - bracketed `[address]:port` and RFC 3986 URL authority WITHOUT a zone. A scoped URL authority is
    rejected. RFC 6874's zone-in-URI extension is deprecated and is not implemented; following its
    `%25` advice would produce non-standard URLs, origin ambiguity and leakage of local interface
    names.

  Parsers and renderers round-trip within each grammar and reject ambiguous IPv4-style splitting.

- [ ] **M10 - dual-stack behavior is tested as a matrix.** Host fixtures over `service-logic` cover
  UDP/TCP checksum vectors, address-family demultiplexing, same-port v4/v6 listeners in all three
  bind modes, RFC 6724 selection cases, PMTU and resegmentation, AAAA/A answers, DNS correlation and
  spoof rejection, CNAME and answer bounds, exact-bound and over-bound encodings, the three textual
  grammars and their round trips, and deterministic fallback.

  QEMU gates use an explicit reviewed global-unicast /64 and EXTEND P02M0174's socket-netdev peer
  fixture with DNS, UDP and TCP peers; the IPv6-only row also disables IPv4 rather than accepting an
  incidental DHCPv4 path. Exercise IPv6-only and dual-stack AAAA lookup, outbound and inbound TCP,
  UDP/DNS, `ping -6` (or the equivalent typed-address invocation), traceroute errors, a truncated
  DNS answer retried over TCP, and a failed preferred-family connection followed by the declared
  fallback. Hostile fixtures quote a second live flow when delivering each ICMPv6 transport error and
  prove it remains untouched, and flood the listener with SYNs and unaccepted connections in both
  families to prove M4's budgets hold. A reduced-MTU path proves TCP MSS and resegmentation of real
  outstanding data rather than only completing the handshake. Existing DHCPv4, IPv4 DNS, TCP and
  tools remain green in the same release matrix.

## Dependencies

- P02M0004 owns UDP/TCP/DNS and capability-scoped NetworkService.
- P02M0080 owns elastic service pools and their capacity reporting; M4 corrects its ceiling claim
  for inbound TCBs.
- P02M0174 owns the IPv6 address, prefix, route, router, neighbour and PMTU TABLES and enumerates
  candidates; this milestone owns the SELECTION POLICY over them. It also supplies the frozen L3
  notification contract M7 consumes and the socket-netdev peer fixture M10 extends. The boundary is
  stated once, in M0174, and this file does not restate it in different words.
- **A SECURE ENTROPY SOURCE - NOT A BLOCKING DEPENDENCY, A GATE ON ONE CLAUSE. THIS MILESTONE DOES
  NOT HAVE ONE ON TWO OF ITS THREE TARGETS** (added 2026-08-31, scoped 2026-09-01). M6 and M8 require unpredictable DNS transaction IDs and source ports, a random
  non-zero SNTP transmit timestamp and a random DHCP `xid`, and the Definition of done says the
  resulting tuples cannot be guessed. That property is exactly as good as the randomness under it,
  and the kernel's is architecture-dependent: x86_64 has a real source, while aarch64 and riscv64
  both hard-code `secure_available()` to false and expose only a clock-seeded SplitMix stream their
  own comments call non-cryptographic and never secret. `SYS_RANDOM_GET` therefore REFUSES on those
  two, which leaves this milestone's requirement with no correct implementation there: drawing from
  the insecure stream makes the unguessability claim false, and refusing every query fails the
  positive DNS gates the same file requires on those profiles.
  IT BLOCKS THE UNGUESSABILITY GATE AND NOT THE MILESTONE, and the previous version said both
  (corrected 2026-09-01). It called secure entropy "a prerequisite" and said this milestone is
  "waiting on it", and then permitted a degraded mode until it exists - which the Definition of done
  also accepted. A prerequisite that can be shipped without is not one, and a reader could take
  either sentence as the release condition. One answer: M0175 does NOT wait. Everything it owns is
  implementable and testable today, the correlation contract lands on all three targets, and what
  secure entropy gates is the stronger CLAIM on top of it.
  It is named here so whoever adds FEAT_RNG (aarch64) or the Zkr `seed` CSR (riscv64) knows which
  clause turns on when they do. Until then:
    - the CORRELATION contract lands everywhere - the full tuple, the bounds, retirement of a
      finished query - because matching is worth having whatever the randomness is;
    - the UNGUESSABILITY claim and its gate are made on profiles where `secure_available()` is true,
      and on the others the service enters a VISIBLE degraded state, named in the boot log and in
      this milestone's matrix, saying its query identities are predictable. That is the same loud
      degraded shape the DMA policy uses, and it is preferred to a silent weakening or to an
      appliance that cannot resolve a name;
    - the Definition of done's spoof/replay clause is narrowed to say so explicitly rather than
      claiming a property two of three targets cannot hold;
    - and the release matrix carries the same one answer: an x86_64 row claims unguessable query
      identities, the aarch64 and riscv64 rows record the degraded mode as a KNOWN and visible
      limitation of those profiles, and no row is blocked by it. When a secure source lands on a
      target, that target's row moves and nothing else in this milestone changes - which is what
      makes this a gate on one clause rather than a dependency of the whole.

## Definition of done

- First-party applications can resolve, connect, listen, inspect and diagnose IPv4 and IPv6 through
  one typed capability-scoped API whose records, bind modes and bounds are stated in the schema.
- The TCP sender measures RTT, backs off, bounds its flight and probes a zero window, so a changed
  path or a lost window update does not deadlock or flood it.
- Every internal UDP operation - DHCPv4, DNS and SNTP - correlates its replies to its own requests
  through the full tuple, and a spoofed or replayed datagram can neither resolve a name, set the
  clock, nor complete or invalidate a lease. The stronger half - that the tuple cannot be GUESSED by
  an off-path attacker - is claimed on profiles with a secure entropy source, and on the others the
  service says out loud that its query identities are predictable. See the entropy dependency: this
  is narrowed because two of three architectures have no secure source, not because guessability is
  acceptable.
- TCP owns its outstanding data AND ITS FIN: loss, a lost FIN, a lost final ACK and a reduced path
  MTU are recovered rather than silently dropped, and `send` reports what it actually accepted.
- DNS answers are correlated and validated, distinct errors survive, and a truncated answer is
  retried over TCP.
- Inbound TCP state is charged against declared budgets before publication, and a SYN or backlog
  flood in either family cannot grow the service heap past them.
- IPv4-only, IPv6-only and dual-stack QEMU profiles have positive traffic oracles and hostile parser
  coverage against a controllable peer, with bounded resources and no family aliasing.
- IPv4 behavior remains available; IPv6 support is not represented as TLS or general Internet
  hardening.

## What this milestone refuses

- TLS/HTTPS, certificate validation, QUIC, IPsec, VPN, firewall/NAT and advanced congestion control.
  M2 builds reliable delivery, not a congestion-control implementation beyond what a bounded
  appliance needs.
- A public datagram socket API. UDP here is the named internal DHCP, DNS and SNTP operations.
- DHCPv6 or privacy addresses unless P02M0174's SLAAC/RDNSS QEMU profile proves insufficient and a
  separate reviewed requirement is opened.
- Zone identifiers in URLs or in any transmitted authority.
- POSIX raw sockets or ambient packet authority for tools.
