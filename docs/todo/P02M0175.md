# P02M0175 - Dual-stack transports, DNS and NetworkService

Status: PLANNED AFTER P02M0174. FUTURE-TRACK NETWORKING. NOT A PHASE-2 COMPLETION GATE.

## Goal

Carry P02M0174's IPv6 addresses through UDP, TCP, DNS, the public NetworkService contract and the
network tools, producing one coherent IPv4/IPv6 dual-stack appliance rather than a private L3 feature
which applications cannot name.

TLS is not part of this milestone. It authenticates and protects application transports and should
be designed after the address/socket contract is correct, not hidden inside an IPv6 rollout.

**The UDP deliverable is decided here rather than left to implementation.** UDP in this milestone
means the named INTERNAL operations: DHCPv4, and DNS and SNTP over BOTH address families. "Plus
their IPv6 equivalents" was the previous wording and it was wrong about DHCP: this file refuses
DHCPv6 by name and M0174 assigns IPv6 configuration to SLAAC and RDNSS, so there is no IPv6
equivalent of the DHCP client and the test matrix must not imply one (corrected 2026-08-30).

There is NO public datagram bind/send/receive API. Adding one would be a second unplanned
public contract on top of a transmit-side TCP implementation this milestone already has to build,
and the tools this milestone migrates do not need it. If an application ever needs datagrams, it is
its own reviewed requirement with scoped endpoints, conflict rules and queue budgets.

## What is there now, and what it forces

- There is NO transmit-side TCP. `TcpConn` holds sequence counters and a receive buffer; it stores
  no unacknowledged bytes, no peer MSS and no send window. `tcp_build_data` advances `snd_nxt` past
  a one-shot frame and retains nothing, and `socket.send` truncates the caller's buffer to one
  segment, transmits once, closes the buffer and reports success. Only SYN has a retransmission
  loop. So "resegment and retransmit outstanding data after a PTB" cannot be implemented as an
  addition - there is no outstanding data to resegment, and loss is currently unrecoverable.
- DNS is uncorrelated. Any UDP datagram whose SOURCE port is 53 is handed to the parser; the
  destination port, the server address, the UDP length and checksum are unchecked, and the parser
  ignores the transaction ID, QR/opcode/rcode, the question section, the answer owner and CNAME
  chain, returning the first A record. `resolve` collapses every failure to `NotFound`.
- An inbound SYN allocates a TCB BEFORE any socket channel exists. `tcp_alloc` reuses a free slot or
  unconditionally pushes a new one - the pool has no cap - and every fresh TCB allocates 65,535
  receive bytes, growing to 262,140 when the peer offers window scaling. P02M0080's claim that the
  domain handle budget is the true ceiling does not hold for this path, because a half-open TCB
  consumes no handle.
- The public contract is IPv4-shaped and unbounded: `endpoint` is an `ipv4-addr` and a port,
  `net-info` carries one address and one gateway with an unbounded neighbour list, `listen` takes a
  bare `u16`, and `network.lsidl` contains no `@bound` at all - so the schema advertises requests
  larger than the service's 1024-byte request and 4096-byte reply buffers can receive.
- Boot blocks on DHCPv4 before entering the serve loop and then installs a hard-coded IPv4 fallback.
  The loop schedules only the lease deadline, and the synchronous helpers discard unrelated events.
  An IPv6-only profile would still wait for DHCPv4 and silently acquire v4 state.
- `service-logic` is the host-testable boundary; the `services` binary links `rt` and cannot be
  host-tested. Every pure decision added here goes there.

    AND THE FRAMING FOLLOWS FROM THEM RATHER THAN THE OTHER WAY ROUND. The largest single reply is
    the socket list, and 256 entries of a local plus a remote scoped endpoint do not fit in 4096
    bytes - so the reply buffer becomes 65536 and the request buffer 8192, both stated here so the
    migration cannot land a wire the service cannot receive. A list whose bound would exceed the
    reply buffer is a bound to lower or a buffer to raise, decided here and not discovered at run
    time.

    AND THE FETCH IS A STREAM, BECAUSE "65536 IN CHUNKS OF 4096" WAS NOT A SHAPE THE WIRE HAS
    (corrected 2026-09-01). That line named a total and a chunk size and no operation that carries
    them: `fetch` today returns one inline `list<u8>`, and LSIDL caps a `list` length prefix at
    `u16`, so 65536 is not merely large - it is one more than the encoding can express. The number
    and the shape were both wrong, and a bound that cannot be encoded is worse than an unstated one.
    The operation returns a `result<stream<chunk>, error>`, the same shape `listener` already uses to
    hand back a channel: the client reads chunks of at most 4096 bytes until the stream ends. Nothing inline
    carries a body, so no total needs to fit a list length, and the per-flow receive budget below is
    what bounds how much a client may have outstanding. A body that exceeds that budget ends the
    stream with the explicit truncation signal rather than refusing, which is the one place
    truncation is allowed and is unchanged.

    AND THE FETCH BODY'S OWN BUDGET IS A NUMBER, NOT A CROSS-REFERENCE (added 2026-09-01). The stream
    clause above bounds a body by "the per-flow receive budget below" and no such budget followed:
    the 256 KiB is UNACKNOWLEDGED TRANSMIT data, which is a different direction and a different
    question, and M4's 2 MiB is an aggregate across inbound state rather than a per-flow receive
    bound. So the one number the truncation rule depends on did not exist. It is:

      MAX_FETCH_BODY_BYTES   256 KiB per fetch

    The number is derived rather than picked: it is the same order as the per-flow unacknowledged
    TRANSMIT budget above, and eight concurrent full-size bodies fit inside M4's 2 MiB aggregate
    receive cap - so one flow's bound cannot by itself exhaust the service's, which is the property a
    per-flow budget under an aggregate one has to have. A megabyte would have let two fetches take
    the whole aggregate.

    A body reaching that bound ends the stream with the truncation terminal rather than a refusal -
    the caller keeps what it received, which is what makes this the one place truncation is allowed.

    AND THE STREAM SAYS WHICH OF THE THREE ENDINGS IT REACHED. `fetch` returns
    `result<stream<chunk>, error>`: OPENING is guarded, so a refusal before any body exists - an
    unresolvable name, a budget already spent, a connection refused - is the typed error every other
    operation here uses, and not a zero-length stream the caller has to interpret. Once open, the
    stream ends in exactly one of three ways, and they are distinguishable because a caller that
    cannot tell them apart cannot know whether it holds the whole resource:
      - COMPLETE: the body ended where the peer said it would
      - TRUNCATED: the body reached `MAX_FETCH_BODY_BYTES` and this service stopped reading
      - FAILED: the transport or the peer ended it early
    `chunk` carries only data today, so carrying the outcome is a field this milestone adds; whether
    it rides on the final element or on a terminal frame is IDL spelling and is the generator's, but
    the THREE OUTCOMES and the guarded open are semantics and are frozen here.

- [ ] **M2 - TCP acquires a bounded transmit side.** This is new implementation, not a family
  parameter added to existing code, and everything else in this milestone that mentions
  retransmission depends on it:

  - an owned per-connection queue of UNACKNOWLEDGED bytes, with a hard per-flow and aggregate byte
    budget;
  - peer MSS from the SYN, an effective MSS derived from interface and path MTU, and a tracked send
    window;
  - segmentation of a caller's buffer across several segments, and partial-write backpressure with
    a defined contract for whether `send` reports bytes ACCEPTED or bytes acknowledged - the current
    silent truncation to one segment is a data-loss bug reported as success;
  - ACK retirement with wraparound handling;
  - resegmentation and retransmission of outstanding data within a smaller MSS after a validated
    Packet Too Big; and
  - FIN IS SEQUENCE SPACE AND IS RETRANSMITTED LIKE DATA (restored 2026-08-31). This was accepted and
    promised in an earlier round - "an RTO for data and FIN" - and then went missing from this item,
    which describes only unacknowledged data and segments. It is not a detail: FIN consumes a
    sequence number, so the connection owns it exactly as it owns a byte, and the current teardown
    shows what its absence costs - it builds one FIN, sends it once, pumps briefly for the peer's
    FIN and then frees the control block, so a lost FIN or a lost final ACK ends the connection
    half-open on the peer with nothing left to retransmit from. The transmit side therefore RETAINS
    the FIN's sequence position in the same unacknowledged queue as data, retransmits it under the
    same RTO and backoff, closes under the same retry limit, and the control block survives until the
    closing handshake is acknowledged or that limit is reached - a typed expiry rather than a fixed
    brief wait.

  **AND A BOUNDED BASIC SENDER PROFILE, BECAUSE "AN RTO AND A RETRY LIMIT" IS NOT ONE** (corrected
  2026-08-30). A fixed timeout with no backoff and no flight limit is a retransmit loop, not a TCP
  sender: it collapses under a changed path and it can congest one. These are BASIC requirements and
  are distinct from the advanced congestion control this milestone refuses. The profile is:

    the profile       RFC 6298 for the RTO and RFC 5681 for the loss response and windows. Named,
                        because "standard" is not a specification and two implementations can satisfy
                        every qualitative test below while disagreeing about every number in it
                        (added 2026-09-01)
    RTT and RTO       RTT sampling with Karn's rule (no sample from a retransmitted segment),
                        smoothed RTT and variance per RFC 6298, initial RTO 1 s until the first
                        measurement, a floor of 200 ms and a ceiling of 60 s. Exponential backoff -
                        doubling - on each retransmission of the same segment, reset when a new
                        measurement arrives.
                        THE 200 ms FLOOR IS A DECLARED DEVIATION FROM RFC 6298 (2026-09-01). Its
                        section 2, rule 2.4, says a computed RTO below one second SHOULD be rounded
                        up to one second, and the row named the RFC while contradicting it silently -
                        which is the one thing naming a standard is supposed to prevent. The RFC's
                        own note for that rule says the large minimum is a conservative choice made
                        for coarse-grained clocks and anticipates a smaller one being justified. This
                        is a bounded appliance on an emulated link with a millisecond clock, where a
                        one-second minimum turns every ordinary loss into a one-second stall. So the
                        floor is 200 ms, it is a deviation, and it is written here as one
    flight limit      slow start and congestion avoidance per RFC 5681, with the initial window from
                        RFC 6928 and the two loss responses kept APART (corrected 2026-09-01). The
                        previous row said "an initial window of 10 segments" under RFC 5681, whose
                        own section 3.1 gives two to four; and it gave ONE "loss response that halves
                        the window", which is the FAST-RECOVERY shape applied to timeouts as well -
                        so after a retransmission timeout a sender following this file would put half
                        a window back on a path that had just stopped delivering, which is the
                        opposite of what a timeout means. The three numbers, each with the document
                        that supplies it:
                          - INITIAL WINDOW, RFC 6928 section 2: `min(10*SMSS, max(2*SMSS, 14600))`.
                            The byte cap is part of it - ten segments of a large MSS is not what that
                            document specifies
                          - RETRANSMISSION TIMEOUT, RFC 5681 section 3.1:
                            `ssthresh = max(FlightSize/2, 2*SMSS)` and then `cwnd = 1*SMSS`, so
                            recovery re-enters slow start from one segment
                          - THREE DUPLICATE ACKs, RFC 5681 section 3.2: fast retransmit, then fast
                            recovery - `ssthresh = max(FlightSize/2, 2*SMSS)`,
                            `cwnd = ssthresh + 3*SMSS`, inflated by one SMSS per further duplicate,
                            and `cwnd = ssthresh` on the ACK that covers the recovery point
                        This is RFC 5681's own core and is NOT the "advanced congestion control" this
                        milestone refuses - that refusal is about CUBIC, BBR, ECN and SACK-based
                        recovery, none of which appear here.
                        The sender never has more unacknowledged bytes in flight than the smaller of
                        the congestion window and the peer's advertised window.
                        AND THE NUMERIC TESTS ASSERT THIS POLICY rather than "a window shrank": after
                        a timeout `cwnd` is one SMSS and not half of anything, after three duplicate
                        ACKs it is `ssthresh + 3*SMSS`, and the initial window is the RFC 6928
                        formula evaluated at the fixture's SMSS
    ZERO WINDOW       PERSIST is its own mechanism, not a retransmission. When the peer advertises a
                        zero window the sender starts a persist timer and probes; without it a lost
                        window update deadlocks the connection permanently, which is a correctness
                        failure rather than a performance one
    retry limit       8 retransmissions of one segment before the connection is closed with a typed
                        error, and 5 for a SYN. With the backoff and ceiling above that is roughly
                        ten minutes for an established connection, which is the order RFC 1122's
                        R2 asks for without inheriting its exact arithmetic

  Explicitly still refused, and unchanged: CUBIC, BBR or any modern congestion-control algorithm,
  SACK, ECN, pacing, and delayed-ACK tuning. The line is that a sender must not deadlock, must not
  ignore loss and must not ignore the peer's window; how fast it goes otherwise is not this
  milestone's subject.

  Test: a changing RTT moving the RTO, backoff across successive retransmissions of one segment, the
  congestion window limiting bytes in flight, a peer window closing to zero and reopening, and a LOST
  window update recovered by persist rather than by timeout.

  Test partial ACK, loss, sequence wraparound, PTB resegmentation, close with data in flight, and
  budget refusal, alongside the sender-profile cases above. And the two FIN cases specifically, which
  "close with data in flight" does not reach: a LOST FIN, retransmitted until acknowledged, and a LOST
  FINAL ACK, where the peer's retransmitted FIN is answered rather than arriving at a control block
  that has already been freed.

  DEPRECATED IS A PREFERENCE, NOT AN EXCLUSION (corrected 2026-08-31). A previous version said "never
  choose a deprecated source for a new connection", which contradicts the RFC 6724 profile pinned in

  non-deprecated source between two candidates; it does not remove a still-valid deprecated address
  from the candidate set, and the specification expressly does not override a caller's legal explicit
  choice. Implemented as an exclusion, new connectivity ends at PREFERRED-lifetime expiry instead of

  able to open connections while its address is still usable, which is a self-inflicted outage rather
  than a policy. The rule is therefore: prefer a non-deprecated candidate; use a deprecated but still
  valid one when it is the only candidate; and honour an explicit caller choice of one. Only
  TENTATIVE addresses are excluded from the candidate set outright, as the same section requires.

  entry and tell whoever asked" answers a question the timer partition never gets asked, and the
  no-starvation promise in the sentence above could not hold inside the milestone's own capacities.

  So the timers are not entries at all. ONE DEADLINE PER CONNECTION AND ONE PER OTHER OWNER, and what
  a connection owes is computed rather than queued: a TCB has at most one entry in the scheduler,
  carrying the EARLIEST of the deadlines it owns, and when that fires the connection recomputes which
  of its timers were due and re-arms for the next one. That is the standard shape and it is the one
  that makes the bound structural: the partition holds at most one entry per TCB plus the fixed set
  of protocol owners - DHCP, ND, DAD, RA and PMTU - so 128 + a small constant, and it is sized as
  160 rather than 64. A partition that cannot overflow needs no overflow rule, which is why this
  replaces the refusal rather than adding a case to it.
  ADMISSION IS WHERE THE BOUND IS ENFORCED, and it already exists: a connection that cannot be given
  its one scheduler entry is a connection that is not admitted, which is M4's TCB budget refusing at
  the point that HAS a caller. Nothing is dropped after admission, and no deadline is starved,
  because every admitted owner holds exactly one entry for as long as it lives.
  Its gates: 128 established connections each owing several timers occupy 128 entries and not more,
  and every one of their deadlines fires; and a connection whose earliest deadline is re-armed while
  another of its timers is already due is served for both without a second entry.

    SNTP   the client's request is 48 bytes with only the first set, so its TRANSMIT TIMESTAMP IS
             ZERO - there is no per-request value at all - and the reply is accepted on source port

             forged datagram moves system time. So: a random non-zero transmit timestamp per request,
             recorded and matched against the reply's ORIGINATE timestamp; full tuple, UDP length and
             checksum validation; and mode, version, leap-indicator and stratum validated, with
             leap-indicator "alarm" refused as unsynchronised.

             AND THE SERVER'S OWN TRANSMIT TIMESTAMP IS VALIDATED, WHICH IS THE FIELD THAT MOVES THE
             CLOCK (corrected 2026-08-31). The rules above validate the ORIGINATE field - the echo of
             what this client sent - and left the reply's TRANSMIT field, the one `parse_sntp` reads
             at offset 40 and hands to TimeService as wall-clock time, entirely unchecked. Two
             requirements, both from RFC 5905's packet sanity checks: it must be NON-ZERO, because a
             zero transmit timestamp names a server that never set it; and it must DIFFER from the
             last accepted reply's transmit timestamp, because an identical one is a replayed
             datagram and not a second reading of the same clock.

             refused 0 and 16 and accepted 17 through 255, which are reserved and are not valid
             server strata at all - so a forged reply carrying stratum 200 passed a check written to
             catch exactly that. 1 is a primary server, 2 through 15 are secondary, 0 is unspecified
             or a kiss-o'-death, 16 is unsynchronised, and everything above is reserved.

             Fixtures: a spoofed reply, a replayed reply (byte-identical, proving the duplicate
             transmit timestamp is what rejects it), a reply answering a different request, a reply
             with a zero transmit timestamp, and replies at strata 0, 16 and 17 - each proving the
             stored wall clock is UNCHANGED, because a validation that rejects a reply after
             TimeService has already applied it is not one

             source" - and accepts the first OFFER or ACK of the expected type without checking

               framing     full UDP validation like SNTP's - source and DESTINATION port, length and

      finished query - because matching is worth having whatever the randomness is;
    - the UNGUESSABILITY claim and its gate are made on profiles where `secure_available()` is true,
      and on the others the service enters a VISIBLE degraded state, named in the boot log and in
      this milestone's matrix, saying its query identities are predictable. That is the same loud
      degraded shape the DMA policy uses, and it is preferred to a silent weakening or to an
      appliance that cannot resolve a name;
    - the Definition of done's spoof/replay clause is narrowed to say so explicitly rather than
      claiming a property two of three targets cannot hold;
    - and the release matrix carries the same one answer: an x86_64 row claims unguessable query
      identities, the aarch64 and riscv64 rows record the degraded mode as a KNOWN and visible
      limitation of those profiles, and no row is blocked by it. When a secure source lands on a
      target, that target's row moves and nothing else in this milestone changes - which is what
      makes this a gate on one clause rather than a dependency of the whole.

## Definition of done

- First-party applications can resolve, connect, listen, inspect and diagnose IPv4 and IPv6 through
  one typed capability-scoped API whose records, bind modes and bounds are stated in the schema.
- The TCP sender measures RTT, backs off, bounds its flight and probes a zero window, so a changed
  path or a lost window update does not deadlock or flood it.
- Every internal UDP operation - DHCPv4, DNS and SNTP - correlates its replies to its own requests
  through the full tuple. ON EVERY PROFILE: a datagram whose tuple does not match a live request is
  rejected, and one arriving after its request completed or expired matches nothing, so a MISMATCHED,
  STALE or REPLAYED datagram can neither resolve a name, set the clock, nor complete or invalidate a
  lease. ON PROFILES WITH A SECURE ENTROPY SOURCE, and only there: an OFF-PATH attacker cannot
  produce a matching tuple either, so a spoofed datagram is rejected as well; on the others the
  service says out loud that its query identities are predictable, and an off-path forgery carrying
  the predicted tuple would be accepted.
  (This clause was absolute until 2026-09-01 - "a spoofed or replayed datagram can neither..." - and
  the sentence after it carved out the very case that makes it false. A profile whose transaction IDs
  and source ports are predictable can be handed a forged datagram bearing the predicted tuple, and
  that datagram IS spoofed and DOES resolve a name. What every profile can promise is rejection of
  what does not match; what only a seeded profile can promise is that an off-path attacker cannot
  make one match.) See the entropy dependency: this
  is narrowed because two of three architectures have no secure source, not because guessability is
  acceptable.
- TCP owns its outstanding data AND ITS FIN: loss, a lost FIN, a lost final ACK and a reduced path
  MTU are recovered rather than silently dropped, and `send` reports what it actually accepted.
- DNS answers are correlated and validated, distinct errors survive, and a truncated answer is
  retried over TCP.
- Inbound TCP state is charged against declared budgets before publication, and a SYN or backlog
  flood in either family cannot grow the service heap past them.
- IPv4-only, IPv6-only and dual-stack QEMU profiles have positive traffic oracles and hostile parser
  coverage against a controllable peer, with bounded resources and no family aliasing.
- IPv4 behavior remains available; IPv6 support is not represented as TLS or general Internet
  hardening.

## What this milestone refuses

- TLS/HTTPS, certificate validation, QUIC, IPsec, VPN, firewall/NAT and advanced congestion control.
  M2 builds reliable delivery, not a congestion-control implementation beyond what a bounded
  appliance needs.
- A public datagram socket API. UDP here is the named internal DHCP, DNS and SNTP operations.
- DHCPv6 or privacy addresses unless P02M0174's SLAAC/RDNSS QEMU profile proves insufficient and a
  separate reviewed requirement is opened.
- Zone identifiers in URLs or in any transmitted authority.
- POSIX raw sockets or ambient packet authority for tools.
