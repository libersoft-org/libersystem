# P02M0115 - The kernel's lowest layers do not yet keep the promises the upper ones make

Status: REOPENED (2026-08-16) by a fourth-party audit round, recorded in AI/audit/kernel.md (core findings). The findings are appended as open tasks in the section at the end of this file; each was checked against the tree before being written down, and where a check contradicted the audit that is recorded with the task rather than dropped. Previously: COMPLETE. A code-level audit of the kernel by an outside party, verified claim by claim
against the code, plus a fifth round on the work itself. Sixty findings; essentially all held.

The theme is one sentence: the capability model, the process model and the service architecture are
sound, and **underneath them the mechanisms that make those models true had gaps** - a check that is
not atomic with the act it guards, a publication that happens before the state it announces, a
reclamation that happens before every core has stopped using the page.

*Condensed 2026-08-08: each finding is stated once, with its resolution folded in, instead of once as
a complaint and again as a result.*

## Phase 1 - the userspace/kernel boundary

- **An `ET_EXEC` image was not confined to userspace**, and the syscall entry trusted an address it
  had not proved was one.
- **User pointer access checked the wrong things and was not fault-safe.** The permission checks are
  right now; the window between checking and accessing is not closed, and that half is carried out
  to **[P02M0119](P02M0119.md)** because it needs an exception table and per-architecture trap entry.
- **The mapper overwrote a live leaf PTE without a word.** Mapping over a mapped address now reports
  `AlreadyMapped` instead of silently orphaning a frame.
- **A syscall could ask the kernel for an unbounded allocation**, and `read_bytes` turned an
  allocation failure into an empty message - a send that delivered nothing while reporting success.
- **`MemoryObject` and `DmaBuffer` accepted any size**, with no ABI ceiling and infallible metadata.
- **The privileged console and display syscalls were not capability-gated**, and
  **`SYS_DEVICE_ACQUIRE` minted a `DeviceMemory` capability to any caller that named an index.**
- **`SYS_RANDOM_GET` fell back to a non-cryptographic PRNG** without saying so. Userspace saw one
  syscall and one contract; anything generating keys through it had no way to know. The honest answer
  for a machine that cannot produce cryptographic randomness is an error.

## Phase 2 - physical memory and SMP

- **There was no TLB shootdown.** Every architecture invalidated locally only, so a page unmapped on
  one CPU stayed reachable from another. Physical reclamation is centralised behind a completed
  shootdown now, and **a shootdown that times out may not be treated as one that happened**.
- **The frame allocator could deadlock on the heap it feeds.** The fix bounded its run table, which
  introduced the next problem: **a freed span that does not fit is not tracked**, so under enough
  fragmentation a free silently loses the memory. Carried out to **[P02M0120](P02M0120.md)**.
- **The loader left live PTEs pointing at freed frames.**
- **Kernel thread stacks had no guard page** - a `Box<[u8]>` from the heap, so an overflow quietly
  corrupts whatever is next to it.
- **`kstack_ptr` was written both atomically and not**, and **`SpinLockGuard` could be moved to
  another CPU**, which makes the lock's promise untrue in a way nothing would report.
- **A late AP could take another AP's identity and stack**, because x86 bring-up used single global
  variables for the handover.
- **The heap lost the alignment prefix of every region it aligned up in.**
- **`USER_VMAP` was one global pool for every process.**
- **MMIO mapping ignored a non-page-aligned physical base**, and **RISC-V ignored `NO_CACHE`
  entirely**, so a device mapping was cacheable on that target.
- **ACPI parsing trusted firmware lengths and addresses.**
- **AArch64 NX reporting did not match the mapper** - the code set execute-never and reported
  otherwise.
- **Raw frame deallocation was a safe function** taking a bare `u64`.

## Phase 3 - capability and lifecycle transactions

The pattern in this phase is one thing said three ways: **a check followed by an act is not a
transaction.**

- **A capability transfer was a clone followed by a close whose result was ignored** - so a failed
  close left the capability duplicated without `DUPLICATE` rights. `SYS_CHANNEL_SEND` did this on its
  multi-cap path.
- **`RECV_CAPS` decided the shape of a message it did not then receive**, so the buffer the kernel
  wrote into was sized for a different message than the one it dequeued - reachable from ring 3.
- **Receive removed the message before it knew it could deliver it.**
- **`SYS_HANDLE_DUPLICATE` walked past the handle limit.**
- **A failed thread creation could lose the bootstrap capability**, and **`sys_thread_create`
  checked the wrong process** - the caller's `is_terminating`, not the target's.
- **The exit status was published before it was written**, and **a terminal state was published
  before the cleanup it promises**.
- **`mark_exited` did not unmap what `terminate` unmaps**, so a clean exit left mappings alive.
- **Two last threads could both decide they were not the last.**
- **Mapping an object was a check followed by an act**; `DeviceMemory` needed the same
  reserve-then-commit its siblings got, and **did not know which address space it was mapped in**.
- **Dynamic modules reserved a count, not a slot.**
- **A domain could outlive its parent**, and `Domain::new_child` pushed into a parent it never
  checked.
- **Introspection ignored revocation** - `lookup` checked validity, `info` did not.
- **Generations are 32-bit and wrap.**
- **Resource accounting could wrap and hid underflow.**

## Phase 4 - the wait subsystem

- **Arming a timer woke nobody**: `Timer::set` stored the deadline and the flag and left an already
  waiting thread asleep.
- **`WAIT_ANY` ignored timer deadlines in its set**, so a wait could sleep past the timer that was
  supposed to end it.
- **A process group was not told when its members die.**

## What the audit did not say, and what the tests had to be

Nothing was reproduced at runtime; the audit was static and so was the verification.

The test list this milestone wrote for itself is worth more than the individual fixes, because it
names the shapes that need a test rather than the lines: two threads transferring one handle and the
same handle listed twice in one send; mapping over a mapped VA; two threads of one process on two
CPUs where A unmaps and B still holds the TLB entry; deterministic OOM injection at the first ELF
data frame and at each subsequent one; two last threads exiting together; a thread woken onto a
different CPU; a timer unarmed at the start of a wait and armed later; and fuzzing of ELF headers,
relocation tables and syscall arguments.

**The scheduler migrates threads while parts of the code assume it does not.** That assumption is not
written down anywhere, which is why it survived - and it is the reason several of the phase-3 items
exist at all.

## Fourth audit (2026-08-16): `AI/audit/kernel.md`, core findings

An external audit of `src/kernel/` reported twenty-one architecture-independent findings. Every one
listed here was checked against the tree before being written down, and the two that were checked
line by line are recorded with what the check showed.

- [x] **A `MAP` capability is mapped WRITABLE whether or not it carries `WRITE` (KERN-CORE-007).**
  Verified: `sys_memory_map` resolves the object with `current_typed::<MemoryObject>(handle,
  ObjectType::MemoryObject, Rights::MAP)` and then builds `flags = PRESENT | WRITABLE | NO_EXECUTE
  | USER` unconditionally. A capability deliberately attenuated to `READ | MAP` therefore yields a
  writable mapping, which is the whole of what attenuation was for - and the kernel hands out
  exactly such capabilities for the read-only bootstrap package and the ramdisk. The DMA and
  device-memory mapping paths take the same shape. Set the writable bit only for a capability that
  carries `WRITE`, require `READ` for a readable mapping, and state MMIO/DMA policy separately if it
  differs. The test has to transfer each object class with `MAP` and no `WRITE` and prove no
  writable mapping can be obtained, plus the positive `WRITE | MAP` case.
- [x] **Explicit unmap can steal an in-progress mapping reservation and orphan live PTEs
  (KERN-CORE-004, reported Critical).** Confirm the window, then make the reservation own the range
  for the whole operation rather than for its first instruction - the shape `begin_extend` already
  uses for process teardown.
- [x] **Infallible allocation on user-reachable paths (KERN-CORE-001, -002, -009, -019).** Closing a
  handle grows the free-slot vector infallibly; the ELF shared-page cache allocates infallibly on a
  user-triggered load; heap growth calls an infallible page-table mapper under OOM; console readlog
  reaches infallible terminal allocations from ring 3. Each is a ring-3-reachable abort of the
  kernel. They need `try_reserve` and a refusal, not a larger heap.
- [ ] **Accounting and reservation defects (KERN-CORE-003, -005, -006, -012, -013).** Thread
  started-state disagrees with live-thread accounting across creation paths; scheduler wait
  reservations are not exclusive; handle reservations promise capacity without owning slots; a plain
  receive reserves a handle even when the caller discards capabilities; a never-started process can
  leave a ProcessGroup with no terminal record.
- [ ] **`SIG_STOP` is not enforced for runnable user code (KERN-CORE-011).** A stopped process whose
  thread is already running keeps running until it next reaches a scheduling point that checks.
- [ ] **A WaitSet containing a ProcessGroup can sleep forever (KERN-CORE-008).** The set registers
  on the group and nothing wakes it for a member transition.
- [ ] **Domain memory limits cover only MemoryObjects, not total process memory (KERN-CORE-014).**
  The limit is therefore not the bound its name claims.
- [ ] **`sys_thread_start` can race process termination, and channel authority and badge are read
  from separate handle-table snapshots (KERN-CORE-016, -017).**
- [ ] **Framebuffer takeover is check-then-act (KERN-CORE-018); MSI retire and device quiesce can
  strand a vector permanently (KERN-CORE-021); teardown from a fault can force the full
  TLB-shootdown timeout (KERN-CORE-015).**
- [ ] **SystemManager spawn failure is treated as successful supervision (KERN-CORE-010).** The
  recovery ladder's own gate: `supervise` returns true when the spawn returned koid 0.
- [ ] **DMA has no IOMMU isolation and exposes raw physical addresses (KERN-CORE-020).** A design
  risk to be written down as a stated threat-model limit if it is not going to be closed, rather
  than left implicit. `AI/audit/drivers.md` reports the same boundary from the driver side
  (DRV-015).

### Resolution of KERN-CORE-007 (2026-08-16)

`sys_memory_map` and `sys_dma_buffer_map` set the writable PTE bit from `Rights::WRITE` instead of
unconditionally. `MAP` says WHETHER an object may be mapped; `WRITE` says what may be done through
it, and collapsing the two made the three rights mean one thing for a direct operation and another
for a mapping. The kernel hands out `READ | MAP` capabilities for the bootstrap package and the
ramdisk, and a holder of either could write to them.

`handle_rights_allow` asks the second question about a handle `current_typed` has already resolved,
and answers false for anything that does not resolve - which is safe by construction, since the
caller has already failed in that case.

THREE GRANTS IN THE TREE WERE RELYING ON THE COLLAPSE, and finding them is the evidence the fix
reaches real code rather than a hypothetical: `virtio_gpu` handed ConsoleService its framebuffer
with `MAP | TRANSFER`, and two display fixtures handed DisplayService a scanout the same way. All
three are surfaces the receiver DRAWS into, so the grants now say `READ | WRITE | MAP | TRANSFER` -
the intent was always write access and nothing had ever had to state it. The GPU test failed with
`PeerClosed` until they did.

WATCHED TO FAIL: restoring the unconditional `WRITABLE` turns
`kernel.kernel.syscall_object_and_handle_ops` red on "a capability without WRITE must not produce a
writable mapping". The test asserts the PTE rather than attempting a write, because a refused write
is a page fault and the asserting thread would die rather than report; it also pins that
`WRITE | MAP` still maps writable, so this is a rights check and not a refusal of writable mappings.

Measured: x86_64 263/263.


### Resolution of KERN-CORE-001, -002, -004, -009 and -019 (2026-08-17)

**KERN-CORE-004 was real, and worse than orphaned PTEs.** `remove_mapping` selected by `cr3` alone,
so it also matched the `(cr3, 0)` a mapper records before dropping the object lock to build its page
tables. A sibling thread's unmap in that window took the reservation and then unmapped
`0 + page * PAGE_SIZE` - the FIRST PAGES OF THE ADDRESS SPACE, belonging to whatever else is mapped
low, not to this object. The original mapper then installed its real PTEs and found no reservation to
commit into, leaving a mapping that existed in the page tables and in no registry: teardown could not
find it and the frames were retired with live translations still pointing at them.

Selection now requires a committed base, so an unmap racing a map answers "not mapped" - the truth at
that instant - and `abandon_reservation` remains the only way a reservation goes. `commit_mapping`
matches the reservation slot specifically and returns whether it was still there; both syscall call
sites undo the map if it was not, because a mapping no registry describes is exactly the state that
lets teardown retire live frames. Both hazards are mirrored in `DmaBuffer`, which had the same shape.

The audit asked for a two-CPU test that pauses after reservation. The window is a LOCK DROP rather
than a schedule, so the rule is checkable without racing anything: `take_committed_mapping` is the
selection `remove_mapping` performs, and the test reserves and then asks what an unmap sees. Watched
to fail against the old `cr3`-only match.

**KERN-CORE-001: the comment was the defect.** Every `free.push` carried "the free list shrank by one
on the way in, so the push reuses that capacity" - true only for a RECYCLED slot. `try_place`
reserved `slots` and not `free`, so a freshly appended slot left no room for the index it would carry
when closed, and a ring-3 process could exhaust the heap, CLOSE a handle, and end the kernel; bulk
teardown could do it where there is least left to recover with. The first attempt at the fix -
`free.try_reserve(1)` - was wrong and the test caught it: `free` is usually EMPTY while slots are
appended, so `try_reserve(1)` is satisfied immediately and the capacity lags for ever after. The
reservation is against `slots.len()`, which is what a full teardown pushes.

**KERN-CORE-002 could not be fixed at the call site.** `alloc::BTreeMap` has no fallible insert, so
`cache.entry(hash).or_default()` was an infallible allocation inside an operation contracted to
return `OutOfMemory`, with the page hashes chosen by whoever supplies the image. The cache is now a
sorted `Vec`, which has `try_reserve`. Lookup stays O(log n); an insertion at a new key memmoves the
tail, at most about half a megabyte at `MAX_SHARED_CACHE_KEYS`. A reservation that fails means the
page is produced and returned but not offered to a later load - degrading the cache is the right
answer to memory pressure.

**KERN-CORE-009: heap growth used the panicking mapper.** `map_page` aborts when an intermediate
table cannot be allocated, and the only reason to be in `grow` is that memory is short. It now uses
`try_map_page`, returns the leaf frame directly (it never reached a page table, so not through
retirement) and unwinds. `init` keeps the panicking form deliberately: a kernel that cannot map its
first heap region has nothing to degrade to. The audit's other half - "on AArch64 it intentionally
reserves nothing" - is not a defect: aarch64's kernel top level lives in TTBR1, which every address
space SHARES rather than copies, so an entry created later is already visible. That is written at
`reserve_kernel_top_level` and it is correct.

NOT TESTED, said plainly: forcing `try_map_page` to fail needs the frame pool drained, and the
existing rollback test records why that is unacceptable here - the pool is shared with three running
cores and draining it destabilised unrelated subsystems. The change is covered by the existing
rollback test and by compilation; the new failure branch itself is not exercised.

**KERN-CORE-019 was already closed** by the TERM-001 work: `TextSink::capture` is fallible and
`boot_log_text` reports an absent log rather than aborting.

Measured: x86_64 `handle` 22/22, `object,memory,dma,paging,process` 179/179, all 67 host suites, and
the `kernel-allocations` gate - which caught a `Vec` clone in a test-only helper added for this work
and was right to.
