# P02M0166 - Everything that went wrong is reported as `failed`

Status: COMPLETE (2026-08-29). Every finding of the 2026-08-28 audit is closed - see the audit sections at the end of this file.

Previously: Status: COMPLETE (2026-08-27). OBSERVABILITY, TYPED FAILURES AND OPERATOR POLICY. LAST OF SEVEN - see P02M0098.

Proved by the boot with every surface reading one snapshot, by forty `driver-binding` tests
including that every state and every cause has exactly one name and no two share one, and by four
gates: `forwarded-abi` (which caught a `&String`/`&str` mismatch in this milestone's own client),
`declared-interfaces`, `no-suppression` and `bootstrap-plan`.

## Goal

Make the state of every binding readable from outside, with one vocabulary for why something is not
running, and let an operator choose among the drivers a device already declared - without being able
to widen what any of them may do.

## What is there now

- **TWO CAUSES CAN BE TOLD APART AND THE REST CANNOT.** `STATE_UNBOUND` and `STATE_DRIVER_MISSING`
  were separated under P02M0098 on 2026-08-12, and they are DeviceManager's own states, printed.
  Everything else - a claim that failed, a protocol mismatch, a dependency not met, a driver that
  hung - has nowhere to be said.
- **`lsdev` AND THE SYSTEM GRAPH SHOW WHAT WAS TRUE AT BOOT.** They do not show the selected artifact,
  the match rule, the generation, the granted resources or the published providers.
- **THERE IS NO OPERATOR CONTROL AT ALL.** Which driver binds a device is decided entirely by the
  compiled registry.
- **THE GRAPH REPORTS A CONSTANT WHERE A STATE SHOULD BE.** Every device node it emits carries
  `ComponentState::Running` whatever its binding is doing, so the surface that looks most like a
  status display is the one showing none.

  this milestone renders them and adds exactly one variant of its own. WHERE a binding is:
  `Unbound`, `Binding`, `Online`, `Stopping`, `Backoff`, `Failed`, `Quarantined`, plus

  off, which is not `Unbound` because `Unbound` invites a rebind. WHY it got there: `driver-missing`,
  `protocol-mismatch`, `claim-refused`, `iommu-required`, `resource-exhausted`,
  `spawn-failed`, `handshake-timeout`, `driver-exited`, `driver-reported-failure`,

  `Disabled` needs its rows in P02M0162's table, added here because this is where an operator first
  has a way to reach it - a state with nothing entering it and nothing leaving it is one every reader
  has to guess at:

  | from | to | on |
  | --- | --- | --- |
  | `Online` | `Stopping` | disable, on a binding that is running: it goes through the teardown like any other stop, carrying P02M0165's stop intent so it does not rebind |
  | `Binding` | `Disabled` | disable BEFORE the claim was taken - there is nothing to tear down |
  | `Binding` | `Stopping` | disable AFTER it was taken, with `intent = disable` |
  | `Stopping` | `Disabled` | that teardown confirmed |
  | `Unbound`, `Backoff`, `Failed`, `DependencyPending` | `Disabled` | disable, on a binding that is not running - there is nothing to tear down |
  | `Disabled` | `Unbound` | enable |

  BOTH IN-FLIGHT STATES USE THE TEARDOWN (fixed 2026-09-03). `apply_policy` started an operator stop
  only for `Online` and moved every other state straight to `Disabled`. Two of those are neither
  online nor holding nothing: a node in `Binding` past the commit has a live process and a claimed
  device on its binding, so the direct move left both attached to a record reported disabled with no
  `STOP` sent; and a teardown already under way took the same move - legal, because
  `Stopping -> Disabled` is the edge for a teardown that CONFIRMED - before either confirmation
  arrived, after which an unconfirmed resolution could no longer quarantine an already-`Disabled`
  record. The three cases are `driver_binding::disable_action`, where a test drives them, and a
  second disable replaces the in-flight intent and its landing rather than queueing a teardown.

  An `enable` that arrives while a disable's teardown is still in flight is REFUSED as busy, and the
  operator retries once the node reaches `Disabled`. The alternative - cancelling the intent so the
  teardown lands in `Unbound` - means a device that was never observed to be disabled at all, which
  is worse to explain than a refusal that says why.

  A disable arriving while a `Stopping` is already under way REPLACES the intent rather than queueing
  a second teardown: the teardown in flight is the one that completes, and what changes is where it
  lands.

  `Quarantined` IS OUT OF REACH OF ALL FOUR VERBS, for this boot. Its resources are charged and out
  of circulation precisely because nothing confirmed the device was quiet, and an operator saying so
  does not make it so - `retry` is refused with that reason. `disable`, `enable` and `select` are
  still accepted, because they are policy and policy is about the NEXT bind: what persists is the
  EFFECT, so `disable` and `select` write a record and `enable` deletes one - saying all three are
  "stored" would make enable a third stored state, which M4 spends a paragraph saying it is not.
  None of them changes anything now; they apply after a reboot or whenever the device is bound
  again. One rule,
  and it needs no state of its own.

  And a `retry` out of `Failed` re-evaluates the entry's `requires` first, which is why P02M0162's
  table gives it two destinations rather than one.

  Which means the API is disable AND enable. This item first had only disable, and a state nothing
  can leave is not a policy - it is a way to lose a device until the next boot.

  Two members moved out of the lists this item first gave. `Removed` is gone entirely - nothing
  rescans, so nothing produces it. And `dependency-pending` was in the CAUSE list and is a STATE:
  a binding waiting for a provider has not failed, and rendering it as a failure would report a
  machine without a NIC as a broken image. One list holding both kinds makes "quarantined" and "hung"
  look like alternatives when they are two halves of one answer. Every surface renders both without
  collapsing either.

  BUILT 2026-08-27. `Disabled` is in P02M0162's enum with its seven rows in the table, and
  `StopIntent::OperatorDisable` now lands there rather than at `Failed` - which is where it landed

  AND ONE CAUSE SPLIT IN TWO, which this milestone found by having to render them. `hung` and

  ONE STATE MAY REACH `Unbound` AND IT IS NOT A FAILURE: `Disabled`, on an `enable`. The test that

  THREE DEFECTS ON THE WAY, each of which cost a boot:

  ONE: `serve_catalogue_once` answered typed requests only. `service_connect` - which is how every

  first thing that asked for the catalogue hung the boot. It is a multi-client server now, with a

  TWO: the role was declared `client`, which hands over a DUPLICATE - so ServiceManager, DeviceService

  consumer.

  THREE: the role was added BEFORE `SERVE` in the manifest. Roles are read positionally from the
  generated list, so DeviceService swapped its own serve root with the catalogue connection: it
  served nobody, and the first client to reach for it hung the boot again. Additions go at the END -
  the same rule this tree has already written down three times, learned a fourth.

- [x] **M4 - operator policy, bounded by the registry, decided by DeviceManager and STORED in
  ConfigService.** FOUR verbs: disable, enable, select among the candidates the registry already
  declared, and retry one now. This item said three and then grew a fourth in M1's transition table,
  which is how an API ends up with a state nothing can leave. Selecting something the registry did not
  declare is refused,
  because policy narrows and never widens. The division matters and is the whole of the authority
  question here: DeviceManager owns the decision and exposes the four verbs, ConfigService holds the
  bytes. A component that can write the config file therefore cannot change a binding - it can only
  propose a record DeviceManager will re-check on the next load, which is the same check it applies to
  one an operator typed. Only disable and select are PERSISTENT - a retry is an action, not a stored
  preference - and `enable` is not a third stored state but the REMOVAL of the disable record, so a
  device that was never disabled and one that was enabled again are the same device. `ConfigService`
  offers `get`, `list` and `set` and no way to remove a key, so this needs one narrow `remove`
  restricted to the reserved prefix - not a general delete, and not a rule that `set ""` means absent,
  which is how an empty string becomes a third state nobody declared.

  `select` APPLIES AT THE NEXT BIND, not to the binding that is running. Rebinding a live device
  because a preference changed would take a working driver away at a moment nobody chose, and the
  operator who wants that has `disable` followed by `enable`. Said here because "it is stored and
  re-checked on every load" does not answer it, and two implementers would answer it differently.

  What is stored is a stable device identity plus a registry entry id, and every load re-checks that the entry is still
  among that device's candidates, so a stored choice naming an entry that no longer matches is stale
  rather than an override. Boot-critical bindings are OUT: the policy lives on a volume that is not
  mounted when those bindings are made, which is a dependency the wrong way round.

  **THE RE-CHECK BOUNDS WHAT, NOT WHO, AND BOTH ARE NEEDED.** This item first said DeviceManager owns
  the decision and ConfigService only holds the bytes, and nothing in the tree makes that true:
  `ConfigService::set` accepts any key from any client holding a connection, and `CAP_CONFIG` is
  granted to `watchdog_probe`, `permission_manager` and `console_service` today. Any of them can
  store a WELL-FORMED disable or select - one naming a candidate the registry really did declare -
  and the load-time re-check passes it, because that check was written to catch staleness and not to
  ask who wrote the record. So the smallest thing that makes the sentence true: the four verbs live
  on one narrow `DevicePolicyAdmin` endpoint of DeviceManager's, and the key prefix they persist
  under is writable by DeviceManager alone. The endpoint is reached the way every other operator
  authority in this tree is reached - PermissionManager mints it for the operator path and for
  nothing else - so holding `CAP_CONFIG`, or holding the read-only binding snapshot M3 defines, gets
  a component no closer to it. No general ACL and no policy language - one endpoint and
  one reserved path.

  BUILT 2026-08-27. `device-policy-admin` carries the four verbs and DeviceManager serves it; the
  outcomes are typed - `not-a-candidate`, `quarantined`, `busy`, `refused`, `not-stored` - because
  each is a refusal an operator can act on differently. `ConfigService` grew one narrow `remove`,
  restricted to `device.policy.`, because an `enable` is the REMOVAL of a disable record and not a
  third stored state.

  TWO PERSISTENT VERBS ARE TWO RECORDS (fixed 2026-09-03). `disable` and `select` both wrote the one
  `device.policy.<bdf>` scalar, so each overwrote the other: selecting a driver while a device was
  disabled dropped the disable at the next load, disabling after a selection dropped the preference,
  and `enable` - which removes the disable - took any selection stored in the same slot with it. The
  contract says both persist independently. The selection has its own key under the same reserved
  prefix, so no new authority is needed and `remove` still refuses everything outside it, and the
  load reads the two independently.

  AND `Accepted` MEANS THE RECORD IS STORED (fixed 2026-09-03). The endpoint tested only whether the
  RPC returned an outer `Some`, so a refusal from ConfigService - a denied namespace, a volume that
  could not be written - read as a successful store: the live effect was applied and the operator was
  told the preference was kept. ConfigService made that reachable by discarding its own write-through
  result and answering `Ok(())` whatever the volume did. It answers `io` for a write-through that did
  not land, the endpoint reads the inner result, and `not-stored` is what an operator sees - which is
  the outcome the protocol defined for exactly this and had no producer for.

  THE AUTHORITY IS A SEPARATE CAPABILITY, and that is the half the item was written to get right.
  `device` is the READ that renders a device list; `device-policy` is the WRITE that changes a
  binding. `lsdev` holds both because it is the device operator command, and nothing else holds the
  second - PermissionManager mints it from the one endpoint ServiceManager holds solely to hand on.

  THE ORDERING WAS THE HARD PART AND IT IS NOT WHERE THE ITEM EXPECTED. DeviceManager cannot take a
  ConfigService client at its own bootstrap: ConfigService depends on StorageService, which depends
  on the block driver DeviceManager binds. So the endpoint is minted the moment DeviceManager reads
  as Ready - PermissionManager starts near the END of bring-up and is the only thing allowed to hand
  the connection on, so one created afterwards would have nobody to give it to - and its ConfigService
  connection arrives later still. The policy is about the NEXT bind and boot-critical bindings are
  explicitly out of it, so arriving late costs nothing.

  AND `serve_policy_once` HAD THE CATALOGUE'S DEFECT AGAIN: it answered typed requests only, and
  `service_connect` sends the reserved CONNECT opcode and waits. PermissionManager asked before
  anything else could, so the boot hung - the same failure, in the same shape, one endpoint later.

  TWO GATES EARNED THEIR KEEP HERE. `forwarded-abi` caught `&String` declared against a `&str`
  implementation - a bare jump with mismatched argument registers, which compiles without a warning.
  And `bootstrap-plan` caught the new role being handed to PermissionManager by its hand-written
  ladder while the declared plan said nothing about it: the ladder and the plan are two descriptions
  of one sequence, and a role in only one of them is exactly the drift those two lists exist to
  catch.

## Definition of done

- Every state and every failure cause has one name, and `lsdev` and the System Graph render both from
  the same snapshot - no surface reports a constant where a state belongs.
- `lsdev` shows the artifact, rule, unit, generation, state and cause, resources and providers of
  every binding.
- A `select` leaves a running binding running and takes effect at its next bind, under test - the
  case that separates a preference from a forced restart nobody asked for.
- A `retry` of a `Failed` binding whose declared requirement is still missing lands in
  `DependencyPending` rather than `Binding`, and an operator `retry` grants exactly one attempt
  rather than resetting the automatic budget.
  AND THE PARK DOES NOT GIVE THE BUDGET BACK (fixed 2026-09-03): a granted retry starts one below the
  automatic bound with a flag beside it, and the arrival of the missing provider reset the counter
  unconditionally - so the operator's one attempt became the whole budget. The rule is
  `driver_binding::budget_after_nothing_ran`, which all three places that "reset because nothing ran"
  now share.
- A STORED selection is the same operation as a live one (fixed 2026-09-03). Both set the cursor and
  the preference; only the live one set the flag that stops the next teardown advancing past it, and
  stored policy arrives AFTER bring-up - so a stored choice naming the running candidate, or one
  before it while a fallback ran, was advanced past instead of being tried next.
- On a `Quarantined` binding, `retry` is refused with that reason, and `disable`, `enable` and
  `select` are accepted without changing its state or returning any of its resources - the two halves
  of "policy is about the next bind" tested separately, because they fail separately.

  THE RULES BEHIND THESE THREE MOVED TO WHERE A TEST CAN DRIVE THEM (2026-09-02). They lived in
  DeviceManager's `decide_policy` and `apply_policy`, in a `no_std` binary nobody can run on a host,
  and both had been wrong: a retry after exhaustion once handed back the WHOLE automatic budget
  because it subtracted from a counter `Step::NextCandidate` had already reset to zero, and a retry
  once rewound the cursor to the registry order rather than to the operator's stored choice. Each was
  found by READING. `driver_binding::decide_retry`, `one_more_attempt` and `selected_candidate` are
  those rules now - which states admit a retry, where the cursor and the budget land, and that a
  selection narrows to what the image declared - and
  `an_operator_retry_grants_exactly_one_attempt_and_a_quarantine_refuses_it` drives every branch,
  including the quarantine refusal being its own answer rather than a busy one. What stays in the
  manager is the mapping onto this protocol's outcomes and the effects on the node, neither of which
  is a decision.
- An operator can disable a device, ENABLE it again, choose among declared candidates, and retry a
  failed binding once without that retry being stored; cannot grant a driver anything the registry did not; and a stored
  choice that no longer matches is reported as stale rather than applied.
- A component holding `CAP_CONFIG` but not the policy endpoint cannot change a binding, under test -
  neither by writing a malformed record nor by writing a perfectly valid one.
  DONE 2026-09-02:
  `kernel.volume_layout.the_reserved_device_policy_namespace_answers_only_its_owner` sends a
  well-formed `device.policy.<bdf>` write down an ordinary `CAP_CONFIG` connection and down the
  seeded owner's, against the LIVE service on a real volume: refused on one, accepted on the other,
  with the record read back both times so the refusal is a statement about the stored state and not
  only about the reply. The removal an `enable` performs is asked the same way. Reading a stored
  policy stays open to any holder - seeing that a device is disabled is not disabling one - and the
  test pins that too, so the rule cannot drift into "the namespace is invisible".
- No boot-critical binding depends on a policy stored on a volume that binding has to mount.
- An operator verb driven through a real launch reaches the policy endpoint AND COMPLETES.
  MET 2026-09-02, and it took two fixes, because until that day no operator disable had ever
  finished on any machine:

  1. THE GRANT WAS NEVER SENT. PermissionManager hands a launched program its capabilities by walking
     `VOCABULARY`, and `Capability::DevicePolicy` was not in that array - so `lsdev`, which has held
     the grant since these verbs were built, received the CONFIGURATION client under the policy tag
     (it reads its grants positionally) and answered "this boot granted no device-policy authority".
     Every operator verb in the system was unreachable. `Capability::Session` was missing the same
     way, which the file had recorded in a comment and left; `kill` could end nothing. Both are in
     the array now, `DevicePolicy` between `Device` and `Config` because that is the order `lsdev`
     reads them in, and `check-grant-vocabulary` compares the array against the IDL enum so a
     capability cannot be declared without being deliverable.
  2. THE STOP NEVER COMPLETED. DeviceManager's standing loop read a bound driver's channel only for a
     node in `Online`, and a disable moves the node to `Stopping` and THEN asks the driver to stop -
     so from the moment the question was asked nothing read the answer. The `STOPPED` frame sat in
     the channel for ever: the node stayed `Stopping`, no rollback ran, the claim's resources stayed
     charged, and the device could never be enabled again. Measured on a live machine, `state=stopping,
     resources=2` for as long as it was watched. The drain is gated on there being a BINDING now, and
     only the heartbeat is gated on `Online` - which is the same correction this loop already carries
     one state earlier, where a node's `PONG` sat unread for exactly the same reason.

  Proved by `dev-gpu-restart` on the enforcing machine: the disable is accepted, the node reaches
  `disabled`, `lsdev --incident` says nothing has gone wrong on that binding, the enable is accepted,
  and `virtio_gpu` comes back ONLINE ON CLAIM GENERATION 2 having republished its provider - with no
  `iommu: FAULT` and one boot throughout. That check is the only thing in this tree that executes an
  operator verb end to end, and it is now the guard for both fixes.
- A failed or hung binding's snapshot is visible after the driver and DeviceManager have both died.

## What this milestone refuses, and why

- **Owning the system volume's identity.** Which volume is the system one is a boot-correctness
  question, not an observability one, and it is an item in P02M0164 where deleting the block slots
  first needs it. It is also smaller than it looks: P02M0150 put the paired volume's uuid in the boot medium's
  signed manifest and the loader verifies and reads it, so what is left is carrying it past the
  loader and probing block providers against it.
- **A monitoring or metrics subsystem.** These are three existing surfaces showing state that already
  exists in one place.
- **An operator policy language.** Disable, retry and choose-among-declared is the whole of it. A
  policy that can express more than the registry declared is a way to widen authority from a
  configuration file.
- **Persistent history.** The snapshot is about the failure that just happened. Keeping a record over
  time is a logging question and this tree has one.

## What the 2026-08-28 audit found

Six findings. One fixed, two comments corrected, five open.

FIXED:
- **`driver-missing` was never recorded and the artifact was lost after exhaustion.** A `read_driver`
  failure updated only the old byte-state array, so a node whose every candidate was absent stayed
  `Unbound` with no cause on the served record. Exhaustion now moves it to `Failed` with
  `FailureCause::DriverMissing`. And `driver_name()` read `candidates[candidate]` after both
  exhaustion paths had incremented past the last entry, serving an EMPTY artifact on exactly the
  failure an operator is diagnosing; it falls back to the last candidate tried.

COMMENTS CORRECTED, because both asserted the property the finding disproves:
- `config_service.rs` claimed a `CAP_CONFIG` holder "can neither write a policy record nor delete
  one". True of `remove`, which refuses every key outside the prefix; FALSE of `set`, which checks
  nothing. The comment now states the hole.
- `system_graph_service.rs` claimed bindings are "matched to the device nodes by index, so the graph
  renders what DeviceManager decided". The two vectors are not positionally equivalent and the graph
  reports another device's state.

OPEN: the four operator verbs do not perform the work they report as accepted (`disable` leaves the
driver online, `enable` starts nothing, `retry` grants zero attempts); persistent policy is
write-only, so a stored disable is never applied and a selected artifact never preferred; the
reserved namespace is writable by any `CAP_CONFIG` client and ConfigService cannot tell its callers
apart to fix it; the graph's positional match needs the address or the kernel table index added to
`DeviceEntry` in the IDL; and the incident snapshot dies with DeviceManager.

## What the 2026-08-30 audit found

Two findings, both accepted and both fixed.

1. **A stored disable spent the candidate list, and enabling an online device spent it again.** The
   refusal was made where a bind starts and answered `false` - the same answer a refused claim and a
   failed spawn give - so the caller read it as "this candidate did not work" and walked the whole
   list. A policy disable is a property of the NODE, so it is answered before the list is consulted
   and the cursor is untouched. And enabling read the answer of its own transition: it attempted a
   move no table entry allows on a running device, ignored the refusal, and asked for a restart
   anyway - which spent the candidates against a state no bind can start from. The desire is lifted
   either way; only a node that actually reached the state that invites a bind gets an attempt. The
   standing loop's restart seam refuses a node that still has a binding, for the same reason.

2. **The incident interface answered the wrong question and cost too much authority.** The stored
   lookup discarded the index and printed every stored incident, so asking about one device reported
   unrelated ones and could not say whether that device had an incident at all. The record stays
   keyed by the device's address, which is its identity across boots, and now carries the row number
   this boot gave it, which is what the operator's question is asked by.

   And the tool was granted a full configuration client to read one record - authority over unrelated
   system configuration, to answer a question about a device. A connection can now be SEALED: it may
   read and may not write, irreversibly, and the granting authority seals it before handing it over.
   So what the tool receives can only read, and asking again produces another sealed connection
   rather than a writable one. That is a restriction rather than a promise the holder makes about
   itself.
