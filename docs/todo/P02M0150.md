# P02M0150 - A digest beside a payload is not a boot trust chain

Status: COMPLETE again (2026-08-26). Every finding of the two outside audits is closed. The manifest's
signed content is now policy - product, architecture, source kind and volume identity are compared
with the boot before anything is loaded, and two sources from two releases do not compose - and the
downgrade that needed no forgery, deleting one file, is refused by a release build and named by a
test-trust one. Previously REOPENED (2026-08-26) by two outside audits; the findings and what each
turned out to be are in the two sections at the end of this file. Previously: COMPLETE (2026-08-25).
BOOT TRUST. HOST/QEMU-CLOSABLE. NOT A PHYSICAL-HARDWARE OR RELEASE GATE.

## Goal

Authenticate the exact bytes the loader is about to execute or hand to the kernel, and root that
authentication in a loader which an emulated UEFI firmware authenticated first.

The claim this milestone is allowed to make is deliberately narrow:

> Given a firmware trust database and manifest public key which the attacker cannot replace, an
> attacker who controls the boot or system medium cannot alter, mix or substitute a kernel or early
> boot artifact and still reach the kernel entry point as that release. Removing an unavailable
> source may reach only a different, explicitly authorised signed fallback; it can never turn a
> present-but-invalid source into a fallback decision.

The intended QEMU chain is:

```text
OVMF Secure Boot
    -> Authenticode-signed EFI loader
    -> signed canonical boot manifest
    -> length + SHA-256 of every boot payload
    -> placement and hand-off only after every check succeeds
```

This is authenticated boot, not freshness. A correctly signed old release still passes; enforcing a
trusted minimum version is anti-rollback and is explicitly outside this milestone.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b`.

- `src/boot/protocol/src/boot_manifest.rs` defines `liberboot-manifest 1`: a version line followed
  by SHA-256 and path rows. The loader checks the kernel, `etc/bootstrap.list` and the programs the
  list names, and a staging gate asks the same digest question of the built media.
- The format proves integrity against the manifest beside the bytes. It proves neither origin nor
  age. Whoever can replace a payload can replace its manifest, and an old image agrees with its old
  manifest. The source says both facts explicitly.
- The build copies an unsigned EFI image to the ESP. There is no PE/COFF signing step, enrolled
  project trust root or Secure-Boot QEMU profile, so firmware currently authenticates neither the
  loader nor the public key a future loader might contain.
- `blockio::assemble_bootstrap` returns one `Option` for both "there is no list on this source" and
  "this source was selected and its manifest is invalid". Its callers can consequently continue to
  a live image or boot medium after the function printed that it was refusing the selected source.
  That contradicts the fail-closed rule written beside the code.
- A live `system-volume.img` and its pairing file are staged after the boot-medium manifest. They can
  be passed as modules without the outer medium authenticating those exact bytes.
- P02M0143 intentionally stopped at corruption detection: it explicitly excluded signing, keys,
  anti-rollback, A/B slots and TPM. This milestone builds on that work rather than relabelling it.

Host tests can exercise the format, signature and source-selection state machine. This repository's
QEMU installation carries Secure-Boot-capable OVMF/AAVMF images; firmware authentication is made a
gate on x86_64 OVMF here because it is one reproducible chain, while manifest authentication itself
must run in the shared loader on all three targets.

## Work

- [x] **M1 - Manifest v2 has one bounded canonical representation.**
  - Add a binary, length-delimited v2 envelope in `bootproto`; the loader and host tools use the same
    parser and verifier. Do not give a shell script a second interpretation of the format.
  - The signed payload names product, architecture, source kind, release identity and expected
    system-volume UUID. Every artifact row names its kind, canonical path, exact length and SHA-256.
  - The envelope names a signature algorithm and key id. Ed25519 over a domain-separated canonical
    payload is the initial algorithm; use an established `no_std` verifier and do not implement
    curve or signature arithmetic in this tree.
  - Bound total manifest size, row count and path length before allocation. Refuse duplicates,
    unknown required enum values, invalid paths, overflow, unsorted/non-canonical rows, trailing
    bytes, truncation and a signature that does not cover the complete canonical payload.
  - Keep the old parser only as an explicitly development-only migration reader if an existing
    image actually needs it. A production boot never silently treats v1 as authenticated.

- [x] **M2 - Signing happens over final staged bytes, and keys have distinct lives.**
  - The host signing tool consumes the artifacts after stripping and staging, produces the v2
    manifest, and can independently verify what it wrote using the shared parser.
  - The loader contains public trust roots only. Unknown key ids and algorithms are refusals; a
    manifest cannot nominate a replacement public key for itself.
  - THERE ARE TWO SIGNER CONTRACTS, AND NO IMPLIED THIRD ONE:
    - `test-trust` is the host/QEMU-closing profile. A deterministic private key may live under test
      fixtures and is accepted only in this profile; the matching loader and image carry an
      unmistakable TEST TRUST identity and print it before loading a payload.
    - `external-release` fixes a public key + key id in the loader and invokes one configured signer
      executable. The builder writes the exact canonical payload to the signer's stdin and accepts
      exactly one raw signature on stdout, then verifies that signature itself before packaging.
      The executable path is configuration, not a secret; private-key access belongs wholly to that
      executable and never appears in this tree's arguments, environment or output.
  - `external-release` without its public-key identity or signer executable fails before an image is
    written. This is the complete release-facing contract in this milestone: defining a release
    command, HSM service, certificate authority or operator procedure is explicitly not work here.
  - A gate proves that the test public key, key id and TEST TRUST marker cannot enter an
    `external-release` loader or image.
  - Key id creates the format boundary needed for later rotation. Production rotation, revocation
    and HSM operation are not pretended into existence here.

- [x] **M3 - The manifest covers every byte the loader executes or hands off.**
  - Cover the kernel, `etc/bootstrap.list`, every program it names, and legacy `init.pkg` or
    `volume.pkg` whenever a supported boot path still carries either.
  - When a boot medium passes `system-volume.img` as a module, its outer signed manifest covers that
    complete image and the pairing UUID. An installed system volume carries its own signed manifest;
    the selected kernel and bootstrap must come from the same signed release/source identity.
  - Reading untrusted bytes into scratch storage in order to hash them is necessary and permitted.
    Verify the manifest signature and each artifact's length and digest before parsing that artifact
    as an ELF/package, deriving a destination from it, calling `reserve_kernel`, publishing a module,
    copying to a fixed address or transferring control.
  - Do not extend `BootInfo`: the kernel does not need trust metadata to enforce this loader-owned
    decision. The loader records the verified release identity, key id and manifest digest, and the
    host/QEMU harness asserts them. There are no speculative slot or update fields.

- [x] **M4 - Source selection distinguishes absence from betrayal.**
  - Replace the `Option` collapse with a typed result carrying at least:

    ```text
    Unavailable  source was not present and policy may consider another
    Verified     one authenticated source owns both kernel and bootstrap
    Invalid      a selected/present source failed; boot stops
    ```

  - Once a manifest or paired system volume selects a source, malformed metadata, a missing named
    file, an I/O failure or a signature/digest mismatch is `Invalid`; none falls through to another
    disk, embedded image or ESP copy.
  - A fallback is another signed source explicitly permitted by signed boot-medium policy. "Try
    everything until something boots" is not a policy and is removed from authenticated mode.
  - The state machine is host-tested independently of UEFI I/O, including two disks in either
    enumeration order and a valid fallback beside an invalid selected source.

- [x] **M5 - The EFI loader itself is authenticated in an isolated OVMF profile.**
  - Add an x86_64 QEMU profile with Secure-Boot-capable OVMF CODE, a private per-run VARS copy and an
    enrolled test PK/KEK/db. Never mutate the distribution VARS template in place.
  - Make the host prerequisites explicit and preflighted: `openssl`, `sbsign`, `sbverify` and one
    pinned VARS-enrolment tool (`virt-fw-vars`) are required by this dedicated profile. A missing
    command reports its name and skips nothing; ordinary non-Secure-Boot tests do not acquire these
    dependencies accidentally.
  - Sign the final EFI loader with a test Authenticode certificate after its bytes are final. The
    build records and independently checks that PE signature.
  - Type only the UEFI Runtime Services `GetVariable` entry needed to read `SetupMode` and
    `SecureBoot`, put the query behind the host-tested UEFI crate, and have the guest report both.
    The gate requires `SetupMode=0` and `SecureBoot=1`. An unsigned or bit-modified loader must not
    print the loader banner; a signed loader with a bad manifest may print only its loader refusal
    and must not print a kernel banner.
  - The same manifest verifier and mutation cases run through the aarch64 and riscv64 loader paths.
    Firmware Secure Boot on those two is not a completion gate here and the documentation must not
    imply otherwise.

- [x] **M6 - Negative evidence is the gate, not one successful signed boot.**
  - Host mutations cover every header field, artifact path/kind/length/digest, source, architecture,
    release id, UUID, key id, algorithm, duplicate, truncation, trailing byte and configured bound.
  - Signatures from another product/architecture or an unknown key fail. A payload modified after
    signing fails. A manifest modified without changing a payload also fails.
  - QEMU covers: a valid signed boot; OVMF rejection of unsigned and altered loaders; loader
    rejection of unsigned, altered and wrong-architecture manifests; an invalid selected volume
    beside a valid fallback; a genuinely absent source with an explicitly permitted fallback; and a
    modified live image or optional package.
  - Include a positive test showing that an older correctly signed release still boots. That test is
    evidence that this milestone does not provide anti-rollback, and prevents later documentation
    from acquiring a freshness claim the mechanism does not enforce.

## Results

Measured on 2026-08-24.

- **M1 - THE FORMAT IS BINARY, LENGTH-DELIMITED AND HAS EXACTLY ONE ENCODING.**
  `bootproto::manifest` is the whole of it - the same module the loader parses with and a host tool
  writes with, because two readings of one format is how a signed thing and a verified thing stop
  being the same thing. The signed payload names the product, the architecture, the source kind, the
  release identity and the expected system-volume UUID; every row names its kind, its canonical
  path, its exact length and its SHA-256. Every field's extent is stated before its content, so a
  reader knows what it is about to read before it reads it - which a text format parsed by scanning
  for delimiters cannot say.

- **AND THE ROWS ARE SORTED BY THE FORMAT RATHER THAN BY THE WRITER.** A manifest whose rows can be
  reordered has more than one byte encoding, and a signature over one encoding says nothing about
  the other - so the reader refuses any order but ascending by kind and path, with no repeats, and
  the writer produces exactly that. Ten host tests: a round trip, the row walk, every prefix of a
  manifest refused as truncated, a byte after the signature refused as a second record, each enum
  field given a value this version does not define, rows swapped by hand, six paths that name
  something outside the source, and a writer refusing everything a reader would have to. Fifty-four
  tests pass in `bootproto`.

- **A SIGNATURE CANNOT COVER PART OF A MANIFEST, BY CONSTRUCTION.** `payload()` is the only accessor
  that returns bytes to verify and it returns all of them; there is no shorter prefix to ask for.
  That is the one refusal the milestone names which is better answered by an API than by a check.

- **THE VERIFIER IS THE BOOT CHAIN'S FIRST EXTERNAL DEPENDENCY, and it is fenced off.** `bootsig` -
  `ed25519-dalek` with `verify_strict`, which rejects the small-order keys and non-canonical
  encodings that let one signature verify under more than one key - is its own crate, so `bootproto`
  stays dependency-free and the KERNEL, which links it, compiles none of this. The milestone says
  why: "use an established `no_std` verifier and do not implement curve or signature arithmetic in
  this tree". Four tests, including the one that matters: a signature over the payload WITHOUT the
  domain string does not verify.

- **AND IT COST TWO BUILD KNOBS, both named where they are set.** `sha2` is a direct dependency only
  so its `force-soft` feature applies - without it a bare-metal build stops at "rustc-LLVM ERROR: Do
  not know how to split the result of this operator!" - and `x86_64-unknown-uefi` needs
  `curve25519_dalek_backend="serial"`, because that dependency picks a SIMD backend on a nightly
  compiler and a UEFI application has no AVX2 to lower it onto. Set per target rather than in
  `[build] rustflags`, which would also reach `build-std`'s `core`. All three loader targets build.

- **V1 IS STILL THE LIVE PATH**, because the loader does not read v2 yet: moving it is M3, and until
  then a production boot verifies exactly what it verified before. Nothing treats v1 as
  authenticated - it never was, and the text format's own comment says so.

- **M2 - THE TOOL SIGNS THE STAGED BYTES AND THEN VERIFIES WHAT IT WROTE.** `tools/sign-manifest`
  takes the artifacts as they are staged - after stripping, which is the point: a manifest made from
  what a compiler produced describes bytes the loader will never read - hashes them, encodes with
  `bootproto::manifest`, signs, and then RE-READS its own output with the same parser and the same
  verifier the loader carries. A signing tool that cannot check its own output moves every one of
  its failures to a boot.

- **TWO SIGNER CONTRACTS, AND THE SECOND ONE IS SOMEBODY ELSE'S PROGRAM.** `test-trust` uses a
  published fixture key - published so a build is reproducible and cannot be mistaken for a release.
  `external-release` invokes ONE configured executable: the canonical message on its stdin, exactly
  one raw 64-byte signature on its stdout, nothing else. Watched to refuse, four ways: without
  `--public-key`, without `--signer`, and without `--key-id` it stops before reading an artifact;
  and given a signer that prints a banner first (71 bytes, and a signature is 64), one that exits
  non-zero, or one that signs with a different key, it refuses and writes nothing. That last is why
  the tool verifies rather than trusts - a release signer is a program this tree does not own.

- **THE LOADER CARRIES PUBLIC HALVES AND A PROFILE, AND THE PROFILE IS IN THE BINARY.** `trust.rs`
  compiles in one or more `(key_id, public key)` roots; a manifest names a KEY ID, so it can never
  nominate a key, and an id this loader does not carry is a refusal rather than a fallback to the
  next root. A test-trust build says `TEST TRUST (published key)` on the console BEFORE it loads
  anything. AND AN `external-release` BUILD WITHOUT ITS KEY DOES NOT COMPILE - `LIBER_TRUST_KEY` and
  `LIBER_TRUST_KEY_ID` are read in a `const`, so "fails before an image is written" is as early as
  a failure can be.

- **AND A GATE PROVES THE TWO BUILDS DIFFER IN THE BINARY.** `check.sh --gate trust-profile` (32
  gates now) builds both and greps them: the release loader contains neither the published key, nor
  its key id, nor the marker, and does contain the key it was built for. It asserts the test-trust
  loader DOES carry all three first - a gate that only checks the release build cannot tell "the
  test key is absent" from "this grep finds nothing".

- **AND THE WALK STOPPED OWNING THE CHOICE OF MANIFEST.** `abi::bootstrap::assemble` used to read
  `etc/boot.manifest` itself, which made the text format part of the state machine. It now takes a
  predicate - is this the content recorded for this path - and the CALLER decides which manifest
  answers it. That is what lets a source carrying a signed manifest be checked against the signed
  one, and it is where the policy belongs.

- **M3 (IN PROGRESS) - THE LOADER PREFERS THE SIGNED MANIFEST AND CHECKS BEFORE IT ACTS.** Where a
  source carries `etc/boot.manifest2` the loader verifies its signature against a compiled-in key
  and checks the kernel, the bootstrap list and every program the list names against its rows -
  BEFORE the kernel bytes are parsed as an ELF, before a destination is derived from them and before
  anything is copied anywhere. A header read out of an unverified image is a decision made on an
  attacker's numbers. A source with only the text manifest keeps the behaviour it had, which proves
  integrity and nothing about origin, and says which of the two it used.

- **WHAT WAS VERIFIED IS SAID OUT LOUD RATHER THAN PUT IN `BootInfo`.** The kernel does not need
  trust metadata - this is a loader-owned decision taken before the kernel exists, and a field it
  could read is a field something would later be tempted to re-derive a decision from. The line
  carries the release the manifest names, the key that signed it and the digest of the record, which
  is what makes two boots comparable.

- **AND THE BUILD WRITES ONE, SO THE PATH IS EXERCISED RATHER THAN MERELY PRESENT.** `mkpackages`
  signs the staged set - it is where the staged bytes are, and a manifest made anywhere else
  describes files that have been copied, stripped or re-linked since - and `mkimage` signs the boot
  medium's, over the STRIPPED kernel that was actually copied onto it. Both stage the signed
  manifest beside the text one, so a loader built before signing existed still boots the same media.

- **MEASURED, x86_64 END TO END:** `loader: TEST TRUST (published key)` before anything is loaded,
  then `loader: signed manifest verified - release 0.0.1, key 7e570001, manifest f735350375fc9ab0`,
  the bootstrap set verified against the signed manifest too, four of four cores online and a shell.

- **AND THE FIRST BOOT WITH IT REFUSED, WHICH IS THE RESULT WORTH KEEPING.** `loader: a boot file is
  not named in the signed manifest - refusing to boot`. The kernel was in the manifest under
  `program` while the loader looked it up as `kernel`: the KIND IS PART OF THE NAME, and a kernel
  filed as a program is a kernel the loader cannot find. Exactly the refusal the format's `find`
  exists to produce, arriving on the first boot rather than as an accepted mismatch.

- **AND THE MEDIUM'S PAYLOAD IS COVERED BEFORE IT IS MOUNTED OR PUBLISHED.** A boot medium carries
  its system volume as a FILE, which the loader reads as a filesystem and hands the kernel as a
  module - two decisions taken on its contents - so the medium's signed manifest now has a row for
  the whole image, under its own kind. The check happens before either. A medium carrying the
  factory archive instead gets a `package` row for that, on the same rule.

- **AND THE TWO SOURCES NAMED DIFFERENT RELEASES, which a boot printed and nothing else would
  have.** The volume's signed manifest said `0.0.0` and the medium's said `0.0.1`: `mkpackages` used
  `CARGO_PKG_VERSION`, and that crate has no version because this tree's rule is that the product
  version lives only in `product.conf`. A boot made of two release identities is exactly what "the
  selected kernel and bootstrap must come from the same signed release" forbids. Both read
  `product.conf` now, and a boot reports one release.

- **M4 - ABSENCE AND BETRAYAL STOPPED BEING THE SAME ANSWER.** `assemble_bootstrap` returned
  `Option<Vec<u8>>`, and `None` meant both "there is no bootstrap list here, try the next disk" and
  "this source was selected and its manifest refused it". No caller could tell them apart, so all
  four did the same thing with both - went on to the next source. That turns a detected tampering
  into a silent fallback, which is the opposite of what the check is for. It now answers
  `Unavailable | Verified(archive) | Invalid(Refusal)`, with the refusal naming which fact refused
  it: no manifest beside the list, a list the manifest does not vouch for, a named program the
  source lacks, a program that does not match, a malformed list, or a set that verified and could
  not be packed.

- **AND `Invalid` ENDS THE BOOT RATHER THAN THE SEARCH.** Every call site stops looking, and the
  loader refuses to hand off at all - the same shape as the kernel's own manifest failure a couple
  of hundred lines above it, where the panic handler writes to serial and hangs. "Try everything
  until something boots" is not a policy, and it is gone from this path.

- **THE STATE MACHINE IS WHERE A HOST CAN DRIVE IT.** `abi::bootstrap::assemble` sits beside the
  list parser it uses and the archive writer it ends with; the loader keeps only the reading and the
  reporting, because it is a UEFI binary and nothing inside one can be tested. It takes the source
  and the manifest check as CLOSURES rather than traits - the loader's two filesystems are types it
  does not own, and the orphan rule does not let it implement somebody else's trait for them.

- **SIX HOST TESTS, WATCHED TO FAIL.** No list is `Unavailable`; a list with no manifest is
  `Invalid`; a list the manifest does not vouch for, a missing named program and a program that does
  not match are each their own refusal; a source that vouches for everything it names produces the
  archive the kernel unpacks, with both programs under the names the list gave them. And the
  policy over two sources in either order: a source that refuses is refused wherever it appears in
  the enumeration, and one that is merely absent never is. Collapsing "no manifest" back into
  `Unavailable` fails exactly the two tests that are about that distinction.

- **NOT PROVEN ON A BOOT YET.** All three loader targets build; the guest evidence belongs with the
  end-of-batch runs.

- **M5 - THE FIRMWARE VERIFIES THE LOADER, OR THE LOADER DOES NOT RUN.** `check.sh --gate
  secure-boot` (34 gates) generates a test platform key into `.build` - generated rather than
  committed, so nothing in this repository is a key-shaped file anybody could mistake for one that
  matters - signs the loader with `sbsign` after its bytes are final, and checks that signature back
  with `sbverify`, which is a different program than the one that made it. It enrols PK/KEK/db into
  a PRIVATE copy of the variable store; the distribution template is never written, because a gate
  that enrols into it changes what every other boot on the machine trusts.

- **AND THE LOADER READS WHAT THE FIRMWARE SAYS ABOUT ITSELF, through one typed entry.** `uefi::
  variables` types `GetVariable` and nothing else in Runtime Services: a loader that could SET a
  variable could enrol its own key. It reads BOTH `SecureBoot` and `SetupMode`, because "secure boot
  is on" is three states rather than two - firmware in setup mode accepts enrolments from anybody,
  so it is not enforcing whatever it says about `SecureBoot`, and firmware defining neither variable
  has no Secure Boot at all. A check that read only the one would call setup-mode firmware
  enforcing, which is exactly backwards. Three host tests, including the offset of `get_variable`
  inside the table.

- **FOUR BOOTS, AND THREE OF THEM MUST NOT HAPPEN.** A signed loader runs and reports `SecureBoot=1
  SetupMode=0 (enforcing)`. An UNSIGNED loader does not reach its own first line - the firmware is
  what refuses it, so the assertion is absence of the banner rather than a refusal message. A signed
  loader with one bit changed does not run either, which is the difference between a signature that
  covers the file and a signature that is merely present. And a signed loader under enforcing
  firmware, carrying a manifest altered after signing, refuses on its own and loads no kernel -
  which is the two links of the chain doing their own jobs in one boot.

- **THE FOUR HOST TOOLS ARE PREFLIGHTED BY NAME AND NOTHING IS SKIPPED.** `openssl`, `sbsign`,
  `sbverify`, `virt-fw-vars`. A verification that quietly does not run when a tool is missing passes
  and proves nothing, which is the failure this milestone is named for. They are in `setup.sh` under
  their own heading, stated as NOT build dependencies: `./build.sh` never touches them.

- **WHAT THIS DOES NOT CLAIM.** aarch64 and riscv64 run the same MANIFEST verifier, and firmware
  Secure Boot on those two is not a gate here - their loaders' mutation cases belong with the
  end-of-batch runs, and the documentation says so rather than implying a chain that was not tested.

- **M6 (IN PROGRESS) - THE MUTATION SWEEP IS EVERY BYTE, NOT EVERY FIELD.** A field a test forgot to
  name is a field nothing would have checked, so `sign-manifest`'s tests flip EVERY byte of a signed
  manifest's payload one at a time, and every byte of its signature, and require each one to be
  refused - by the parser or by the signature, it does not matter which, only that nothing gets
  through. Beside it: a signature from another key, a manifest edited to name different content, a
  correctly signed manifest for another product and architecture, and a signature made over a PREFIX
  of the payload, which is the refusal the API makes impossible and which is asserted anyway.

- **AND THE POSITIVE TEST THAT EXISTS TO STOP A CLAIM.** An older correctly signed release still
  verifies, and must: this milestone authenticates and does not enforce freshness. Without that test
  written down, the documentation acquires an anti-rollback property the mechanism does not have.

- **THE BOOT THAT MUST NOT HAPPEN IS A GATE.** `check.sh --gate signed-boot` (33 gates) flips one
  byte of the medium's signed manifest - where a tamperer would, after the build - and requires the
  loader to refuse before it loads a kernel. IT BOOTS THE UNALTERED MEDIUM FIRST and requires a
  kernel there: a gate that only boots the tampered one passes identically whether the loader
  refused or the machine never booted at all, and the second is the quieter of the two.

- **THREE QEMU CASES HOLD:** the unaltered medium boots with NO system volume attached, which is the
  genuinely-absent-source-with-a-permitted-fallback case seen from outside; a medium whose signed
  manifest was altered stops the boot before a kernel is loaded; and a system volume image the
  manifest no longer describes is refused rather than mounted and handed over.

- **AND THE FOURTH CASE FOUND A DEFECT INSTEAD OF PASSING - THEN CLOSED IT.** "An invalid SELECTED
  volume beside a valid fallback" was written, and writing it showed the loader did not do that: a
  `boot.manifest2` that cannot be READ was indistinguishable from one that is absent, so a manifest
  corrupted inside a LiberFS image made the loader fall back to the TEXT manifest and boot happily.
  The same collapse M4 is named for, one level up - and a downgrade an attacker performs by damaging
  one file rather than forging anything.

- **THE FIX IS A THIRD ANSWER FROM THE READ LAYER.** `FileRead::{Bytes, Absent, Unreadable}`:
  LiberFS and FAT both distinguish `FsError::NotFound` from every other error, so "the path names
  nothing" and "something is there and I could not read it" stop arriving as one `None`. A source
  whose signed manifest is present and unreadable is refused rather than downgraded. THE FIRMWARE
  BACKEND CANNOT TELL THE TWO APART - the Simple File System reader does not carry the status back -
  and it says so where it answers, rather than letting a caller assume all three backends are
  equally sharp. Measured: the fourth boot now stops on the damaged volume instead of falling back.

## Dependency order

```text
P02M0143 M4 -> M1 -> M2 -> M3 -> M4 -> M6
                         \-> M5 -----^
```

M1 and M2 define what authenticity means. Coverage and source selection must use that definition;
OVMF can be brought up in parallel once the final loader-signing order is known. M6 closes only when
both the firmware and payload halves have independently failed in the expected place.

## Definition of done

- Every supported UEFI loader path authenticates every kernel and early module before placement or
  hand-off, using the same bounded parser and trust-root policy.
- Kernel and bootstrap cannot be mixed across signed releases or sources.
- A present but invalid selected source stops; only an unavailable source can enter a signed
  fallback policy.
- The x86_64 OVMF Secure Boot gate distinguishes firmware refusal, loader refusal and kernel entry.
- Signed-manifest positive and negative boots run on x86_64, aarch64 and riscv64 QEMU targets; the
  firmware-authentication claim remains explicitly x86_64-only in this milestone.
- `test-trust` and `external-release` are mechanically separated; the latter accepts only the
  stdin/stdout signer contract above, and no release private key or secret signing material exists
  in the repository or staged outputs.
- `docs/THREAT_MODEL.md` and boot documentation state exactly: authenticity is enforced; freshness,
  measured boot, physical-firmware qualification and production key operations are not.
- The ordinary checks and the dedicated signed-boot/OVMF gates are green from a clean staged image.

## What this milestone refuses, and why

- **Anti-rollback, A/B updates and health commit.** QEMU can exercise those mechanisms later, but a
  trusted monotonic backend and update/recovery policy are a separate state machine. A signed old
  image remains accepted here by design. This milestone defines no slot identifier, selector or
  state transition for them.
- **TPM measurements, PCR policy, attestation and sealed secrets.** They answer who can observe or
  release state, not whether this manifest signature is valid.
- **A home-grown signature implementation.** Boot code is not an excuse to implement cryptography.
- **A signature over a manifest beside an unauthenticated replaceable loader.** That protects
  against accidental corruption with a more complicated checksum; OVMF closes the demonstrated
  loader-root half for the profile this milestone claims.
- **Production key rotation/revocation, Microsoft signing, shim/MOK or an HSM operating procedure.**
  The format has a key-id boundary, but release operations require owners and infrastructure this
  repository cannot prove in QEMU.
- **A physical-hardware claim.** Firmware enrollment UI, NVRAM persistence and board recovery are
  not represented by OVMF and are not smuggled into the definition of done.
- **Authentication of mutable post-boot state.** The system image/root trust policy above early boot
  is a separate problem; this milestone covers bytes the loader executes or hands off.

## Reopened by two outside audits (2026-08-26): the signature is checked, the sentence it signs is not

Two independent audits of this tree, read against this milestone's own Definition of done. Every
claim below was checked against the source before being written down; the claims that did not
survive that check are recorded at the end of this section rather than dropped, so a later round
does not raise them again.

The finding that reopens this milestone is one sentence: **the manifest's signature is verified and
almost nothing the manifest SAYS is used as policy.** `trust::verify`
([trust.rs:141](../../src/boot/loader/src/trust.rs)) decodes the format, finds the key id in the
compiled roots and checks the Ed25519 signature - and returns. It never asks whether the manifest
was written for this product, this architecture, this kind of source or this volume, and no caller
asks either. A correctly signed manifest for a different machine passes.

- [x] **`docs/THREAT_MODEL.md` still says the opposite of what this milestone built, which is a
  Definition-of-done line failing directly.** The DoD requires the document to state "exactly:
  authenticity is enforced; freshness, measured boot, physical-firmware qualification and production
  key operations are not." What it says today, at
  [THREAT_MODEL.md:230-236](../THREAT_MODEL.md), is:

  > Secure Boot verifies the LOADER BINARY and stops there. Nothing verifies the kernel, the
  > bootstrap list, the early modules, or the system volume they come from, and nothing binds them to
  > the loader that read them.

  That was true before this milestone and is false after it. A threat model that understates what is
  enforced is the same class of defect as one that overstates it: a reader plans around it. Rewrite
  the paragraph to name what IS enforced (bounded parser, compiled trust root, Ed25519 over a
  canonical payload, every kernel and early module covered before placement) and to keep the four
  named non-goals as non-goals.

- [x] **Deleting `etc/boot.manifest2` drops the boot to the unsigned v1 text manifest.** Both kernel
  paths take it: the system volume at [main.rs:186-193](../../src/boot/loader/src/main.rs) and the
  boot medium at the matching arm below it. The v1 manifest is a checksum list an attacker recomputes
  along with the payload, so the whole authenticity claim is removed by DELETING one file rather than
  by forging anything.

  The nuance that must not be lost when this is fixed: a manifest that is PRESENT and unreadable is
  already handled correctly - `assemble_bootstrap`
  ([blockio.rs:127-131](../../src/boot/loader/src/blockio.rs)) refuses rather than falling back, and
  says why. Absence is the only hole, and the hole exists because "a medium made before signing" was
  treated as a case to keep working. Make it a build profile: `external-release` requires v2 and
  treats its absence as fatal; `test-trust` may accept v1 and must say on the serial line that the
  boot it is about to perform is not authenticated. A profile that can silently be either is not a
  trust decision.

- [x] **The signed context fields are decoded and never compared with the machine.** `product`,
  `arch`, `source_kind` and `volume_uuid` are signed by `mkpackages` and parsed by `bootproto`, and
  `grep` over the whole loader finds no comparison of any of them against the running boot. What the
  signature currently asserts is "a key this loader carries signed this manifest". What the milestone
  claims it asserts is "…and this manifest was written for THIS machine, THIS architecture and THIS
  source". Close it with an expected-context value built by the caller before verification, and make
  `verify` take it - a signature check that cannot be called without stating what it is checking
  against.

- [x] **The pairing UUID is not part of anything signed.** `etc/system-volume.uuid` is read as plain
  text by `read_pairing` and decides which volume is selected, while the signed manifests carry a
  `volume_uuid` that is zero on both the system-volume and boot-medium manifests
  ([mkpackages/src/main.rs:543](../../src/tools/mkpackages/src/main.rs),
  [mkimage.sh:276](../../src/harness/mkimage.sh)). An attacker who can write the medium changes which
  volume is chosen without touching a signature. Sign the pairing value and compare it with the
  selected volume's real identity.

- [x] **The kernel and the bootstrap set are verified separately and are never bound to ONE release.**
  `announce_release` is called at both verification sites
  ([main.rs:184](../../src/boot/loader/src/main.rs) and
  [main.rs:724](../../src/boot/loader/src/main.rs)) and prints the release; nothing compares the two.
  The DoD line "Kernel and bootstrap cannot be mixed across signed releases or sources" is met for
  SOURCES - `BOOTSTRAP_REFUSED` stops a second source being tried - and not for RELEASES. Two
  individually valid manifests from two releases still compose. Record the first verified release
  identity and require every later verification in the same boot to match it.

- [x] **`signed-boot` is x86_64-only, against a Definition-of-done line that names three
  architectures.** The DoD says "Signed-manifest positive and negative boots run on x86_64, aarch64
  and riscv64 QEMU targets; the firmware-authentication claim remains explicitly x86_64-only in this
  milestone" - two separate claims, and the gate's own header
  ([check-signed-boot.sh:9](../../src/tools/check-signed-boot.sh)) collapses them into one by
  declaring the whole file x86_64-only. The Secure Boot half is correctly x86_64-only and stays that
  way; the MANIFEST half has to run on all three. The aarch64 and riscv64 loaders run the same
  verifier, so this is harness work rather than loader work.

- [x] **The negative matrix has no case for any of the above.** Once the fixes land, the gate must
  boot and refuse: a medium with `boot.manifest2` removed under the release profile, a validly signed
  manifest naming another product, another architecture, another `source_kind`, another volume UUID,
  and a kernel and bootstrap taken from two different signed releases. A refusal that is not in the
  gate is a refusal the next change may remove without anything noticing.

- [x] **The console shows the release binding is missing, and shows it in two different formats.**
  From the same interactive boot on 2026-08-26:

  ```
  loader: bootstrap set verified against a SIGNED etc/boot.manifest2
  loader: kernel read from the system volume
  loader: signed manifest verified - release 0.0.1, key 7e570001, manifest 9bdef7eb0e02dd7e
  ```

  One event, two shapes: the kernel's verification names the release, the key and the manifest
  digest, and the bootstrap set's names none of the three. A reader can tell which release the
  kernel is and cannot tell which release the bootstrap set is - which is the item above, made
  visible. When the two are bound to one verified release, they say so in ONE format, and the second
  line becomes the confirmation that it is the same release rather than a differently-worded claim
  about a different one.

  While there: the ordering reads backwards. `bootstrap set verified` prints above `kernel read from
  the system volume`, and `bootstrap set assembled` prints below `kernel loaded` - so the set is
  announced as verified two lines before it is announced as assembled.

### Two claims from the audits that did not survive checking

- **"After a source is selected, the loader can still fall back to another source."** Checked and
  contradicted. `assemble_bootstrap` returns `Selection::Invalid` rather than `None` precisely so a
  refusal cannot read as an absence, both call sites latch `BOOTSTRAP_REFUSED`, and the existing
  gate log carries the line "a selected volume whose signed manifest is damaged stops the boot
  instead of falling back to the text one". The audit conflated a DAMAGED manifest with a DELETED
  one; only the second is a hole, and it is the item above.

- **"`external-release` is not wired into the image pipeline, so the gate only covers the loader
  binary."** Factually true - `mkimage.sh` always passes `--profile test-trust` - and not a
  Definition-of-done gap. The DoD requires the two profiles to be MECHANICALLY SEPARATED and the
  release one to accept only the stdin/stdout signer contract, which
  [check-trust-profile.sh](../../src/tools/check-trust-profile.sh) builds both ways and proves.
  Producing a real release image requires a real private key, which the same DoD forbids this
  repository to hold. Nothing to do here.

## Results of the reopen (2026-08-26)

### The signature is now checked against something

`trust::verify` decoded the product, the architecture, the kind of source and the volume identity and
then returned - so what it asserted was "a key this loader carries signed this manifest", and what it
was read as asserting was "…and this manifest was written for THIS machine". A correctly signed
release for another product, another port or another medium passed, with no signature broken and no
key needed.

A caller now has to say what it expects before it can ask:

```rust
pub(crate) struct Expected {
    pub product: &'static [u8],
    pub arch: u8,
    pub source_kind: u8,
    pub volume_uuid: VolumeIdentity,
}
```

The architecture is a `cfg` rather than a value passed in: a loader cannot be wrong about which port
it is, and nothing should be able to tell it otherwise.

**The volume identity has THREE states, because there are three situations** and two of them are not
"no uuid". A boot medium is not a volume and its manifest must name none; a paired volume must be the
one the medium named; and a volume reached without a pairing file is a volume this boot cannot put a
name to - which is a weaker claim than either and is stated as one rather than folded into a wildcard
or a refusal.

Two things had to be true for that to work at all, and neither was:

- **The volume's manifest carried a zero uuid.** The identity was derived from the whole staged set,
  manifests included, so a manifest naming it would have changed it. Taken over the PAYLOAD the two
  stop being circular - and a volume's identity is what it holds rather than what it says about what
  it holds. The same number formats the filesystem, so the superblock and the signed manifest are one
  value from one place.
- **The boot medium's fallback bootstrap set was signed `system-volume`.** The one field saying which
  source a manifest is for was wrong for half of what `mkpackages` produces, which nothing noticed
  while nothing compared it.

### And the release is latched by the first thing verified

Every manifest was verified on its own and none was compared with any other, so a kernel from one
signed release and a bootstrap set from another - each valid, each signed by the same key - composed
into a system nobody ever built or tested. The first verification in a boot fixes which release this
is; every later one has to agree.

The console showed it and nobody read it: the kernel's verification printed the release, the key and
the manifest digest, and the bootstrap set's printed none of the three. One event, two formats, and
the reader could tell which release the kernel was and not which release the bootstrap set was.

### The downgrade that needed no forgery

A signed manifest that was ABSENT dropped the source to `etc/boot.manifest` - a checksum list an
attacker recomputes along with the payload. The whole authenticity claim came off by DELETING one
file. A present-but-damaged manifest was already refused correctly, which is what made this easy to
miss: the case that had been tested was the harder one.

It is now a profile, in all three places the fallback existed (the system volume's kernel, the boot
medium's kernel, and any source's bootstrap set). A release build refuses and names what it refused.
A `test-trust` build may take it - a medium made before signing is a real thing to be able to boot
while developing - and says `THIS KERNEL IS NOT AUTHENTICATED` rather than letting a boot that is not
authenticated look like one that is.

### The negative matrix

```
signed-boot: the unaltered medium boots and loads a kernel (with no system volume attached, which is the absent-source case)
signed-boot: the loader refused an altered signed manifest and loaded no kernel
signed-boot: the loader refused a live system volume the manifest does not describe
signed-boot: a selected volume whose signed manifest is damaged stops the boot instead of falling back to the text one
signed-boot: a manifest signed for another product is refused
signed-boot: a manifest signed for another architecture is refused
signed-boot: a manifest signed for another kind of source is refused
signed-boot: a manifest signed for a different volume is refused
signed-boot: two sources from two signed releases do not compose into a system
signed-boot: with the signed manifest removed, a test-trust build boots and SAYS the kernel is not authenticated
signed-boot: and a release build refuses it, naming the missing signed manifest
```

Every wrong-context case is signed WITH THE REAL TEST KEY over the real rows and differs from the
medium's own manifest in exactly one header field - so a boot that accepts one is not accepting a
forgery, it is accepting a valid release that was not made for it, which is the whole point.

**The release case was written wrong the first time and the gate said so.** A lone manifest naming
another release is not a violation: nothing in the loader knows which release it is until something
tells it, and the first thing verified is what tells it. The rule is that the SECOND source has to
agree with the first, so the case now keeps the volume's release and re-signs the medium's.

### And the other two ports

The Definition of done names three architectures for the MANIFEST claim and one for the firmware one,
and the gate collapsed both into "x86_64 only, and by design" - so the verifier, which is the same
code on all three, was proved on one. `aarch64` and `riscv64` have no shipping ISO: their medium is
the ESP the runner assembles, so the tamper happens there, behind a harness knob named beside the
others and used by this gate alone.

```
signed-boot: booting aarch64 through its own UEFI loader
signed-boot:   aarch64: the unaltered medium loads a kernel
signed-boot:   aarch64: an altered signed manifest is refused and no kernel is loaded
signed-boot: booting riscv64 through its own UEFI loader
signed-boot:   riscv64: the unaltered medium loads a kernel
signed-boot:   riscv64: an altered signed manifest is refused and no kernel is loaded
```

The unaltered boot on each port is not ceremony: a gate that only boots the tampered medium passes
identically whether the loader refused the alteration or the machine never booted at all, and the
second is the more likely of the two to happen quietly on an emulated port.

### One thing the gate itself needed fixing for

Its first version reported a build-order problem as a trust-chain failure. `./image.sh` and
`./build.sh --part volume` write over each other's half of `.build/boot`, so building them in the
wrong order leaves the medium paired with a volume that is not there; the loader then refuses that
volume as unpaired and the damaged-manifest case never reaches its manifest - and the gate said "a
damaged signed manifest on the selected volume did NOT stop the boot", which is a sentence about this
milestone's subject and was a sentence about the build. It now compares the medium's pairing with the
volume's superblock BEFORE the case, and names the real reason and the order to rebuild in.

### What this reopen found and did not fix

- **The product's name is now in four places.** `product.conf` is the single source of truth and
  `mkpackages`, `mkimage.sh` and the loader all hold the literal. They agree today, and the failure
  mode if they ever did not is nasty: every boot refuses, for a reason that reads like tampering. The
  loader has no build script; giving it one that reads `product.conf` removes its copy, and is a
  small piece of work with no place in this milestone. Named in the code beside the constant.

### What this reopen refuses, and why

- **Anti-rollback.** Unchanged: a validly signed OLD image is still accepted, and this milestone
  defines no slot identifier, selector or state transition for one.
- **Making `external-release` produce an image.** Also unchanged, and for the reason the milestone
  already gave: a release image needs a real private key, which the same Definition of done forbids
  this repository to hold. What the profiles owe each other is that they are mechanically separated
  and that the release one takes no test identity, which its own gate proves and which the new
  removed-manifest case now proves from the other side - the two profiles differ on exactly the
  downgrade.
