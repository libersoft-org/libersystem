# P02M0150 - A digest beside a payload is not a boot trust chain

Status: OPEN. BOOT TRUST. HOST/QEMU-CLOSABLE. NOT A PHYSICAL-HARDWARE OR RELEASE GATE.

## Goal

Authenticate the exact bytes the loader is about to execute or hand to the kernel, and root that
authentication in a loader which an emulated UEFI firmware authenticated first.

The claim this milestone is allowed to make is deliberately narrow:

> Given a firmware trust database and manifest public key which the attacker cannot replace, an
> attacker who controls the boot or system medium cannot alter, mix or substitute a kernel or early
> boot artifact and still reach the kernel entry point as that release. Removing an unavailable
> source may reach only a different, explicitly authorised signed fallback; it can never turn a
> present-but-invalid source into a fallback decision.

The intended QEMU chain is:

```text
OVMF Secure Boot
    -> Authenticode-signed EFI loader
    -> signed canonical boot manifest
    -> length + SHA-256 of every boot payload
    -> placement and hand-off only after every check succeeds
```

This is authenticated boot, not freshness. A correctly signed old release still passes; enforcing a
trusted minimum version is anti-rollback and is explicitly outside this milestone.

## What is there now

Measured on 2026-08-24 against HEAD `5ee76d9b`.

- `src/boot/protocol/src/boot_manifest.rs` defines `liberboot-manifest 1`: a version line followed
  by SHA-256 and path rows. The loader checks the kernel, `etc/bootstrap.list` and the programs the
  list names, and a staging gate asks the same digest question of the built media.
- The format proves integrity against the manifest beside the bytes. It proves neither origin nor
  age. Whoever can replace a payload can replace its manifest, and an old image agrees with its old
  manifest. The source says both facts explicitly.
- The build copies an unsigned EFI image to the ESP. There is no PE/COFF signing step, enrolled
  project trust root or Secure-Boot QEMU profile, so firmware currently authenticates neither the
  loader nor the public key a future loader might contain.
- `blockio::assemble_bootstrap` returns one `Option` for both "there is no list on this source" and
  "this source was selected and its manifest is invalid". Its callers can consequently continue to
  a live image or boot medium after the function printed that it was refusing the selected source.
  That contradicts the fail-closed rule written beside the code.
- A live `system-volume.img` and its pairing file are staged after the boot-medium manifest. They can
  be passed as modules without the outer medium authenticating those exact bytes.
- P02M0143 intentionally stopped at corruption detection: it explicitly excluded signing, keys,
  anti-rollback, A/B slots and TPM. This milestone builds on that work rather than relabelling it.

Host tests can exercise the format, signature and source-selection state machine. This repository's
QEMU installation carries Secure-Boot-capable OVMF/AAVMF images; firmware authentication is made a
gate on x86_64 OVMF here because it is one reproducible chain, while manifest authentication itself
must run in the shared loader on all three targets.

## Work

- [x] **M1 - Manifest v2 has one bounded canonical representation.**
  - Add a binary, length-delimited v2 envelope in `bootproto`; the loader and host tools use the same
    parser and verifier. Do not give a shell script a second interpretation of the format.
  - The signed payload names product, architecture, source kind, release identity and expected
    system-volume UUID. Every artifact row names its kind, canonical path, exact length and SHA-256.
  - The envelope names a signature algorithm and key id. Ed25519 over a domain-separated canonical
    payload is the initial algorithm; use an established `no_std` verifier and do not implement
    curve or signature arithmetic in this tree.
  - Bound total manifest size, row count and path length before allocation. Refuse duplicates,
    unknown required enum values, invalid paths, overflow, unsorted/non-canonical rows, trailing
    bytes, truncation and a signature that does not cover the complete canonical payload.
  - Keep the old parser only as an explicitly development-only migration reader if an existing
    image actually needs it. A production boot never silently treats v1 as authenticated.

- [x] **M2 - Signing happens over final staged bytes, and keys have distinct lives.**
  - The host signing tool consumes the artifacts after stripping and staging, produces the v2
    manifest, and can independently verify what it wrote using the shared parser.
  - The loader contains public trust roots only. Unknown key ids and algorithms are refusals; a
    manifest cannot nominate a replacement public key for itself.
  - THERE ARE TWO SIGNER CONTRACTS, AND NO IMPLIED THIRD ONE:
    - `test-trust` is the host/QEMU-closing profile. A deterministic private key may live under test
      fixtures and is accepted only in this profile; the matching loader and image carry an
      unmistakable TEST TRUST identity and print it before loading a payload.
    - `external-release` fixes a public key + key id in the loader and invokes one configured signer
      executable. The builder writes the exact canonical payload to the signer's stdin and accepts
      exactly one raw signature on stdout, then verifies that signature itself before packaging.
      The executable path is configuration, not a secret; private-key access belongs wholly to that
      executable and never appears in this tree's arguments, environment or output.
  - `external-release` without its public-key identity or signer executable fails before an image is
    written. This is the complete release-facing contract in this milestone: defining a release
    command, HSM service, certificate authority or operator procedure is explicitly not work here.
  - A gate proves that the test public key, key id and TEST TRUST marker cannot enter an
    `external-release` loader or image.
  - Key id creates the format boundary needed for later rotation. Production rotation, revocation
    and HSM operation are not pretended into existence here.

- [x] **M3 - The manifest covers every byte the loader executes or hands off.**
  - Cover the kernel, `etc/bootstrap.list`, every program it names, and legacy `init.pkg` or
    `volume.pkg` whenever a supported boot path still carries either.
  - When a boot medium passes `system-volume.img` as a module, its outer signed manifest covers that
    complete image and the pairing UUID. An installed system volume carries its own signed manifest;
    the selected kernel and bootstrap must come from the same signed release/source identity.
  - Reading untrusted bytes into scratch storage in order to hash them is necessary and permitted.
    Verify the manifest signature and each artifact's length and digest before parsing that artifact
    as an ELF/package, deriving a destination from it, calling `reserve_kernel`, publishing a module,
    copying to a fixed address or transferring control.
  - Do not extend `BootInfo`: the kernel does not need trust metadata to enforce this loader-owned
    decision. The loader records the verified release identity, key id and manifest digest, and the
    host/QEMU harness asserts them. There are no speculative slot or update fields.

- [x] **M4 - Source selection distinguishes absence from betrayal.**
  - Replace the `Option` collapse with a typed result carrying at least:

    ```text
    Unavailable  source was not present and policy may consider another
    Verified     one authenticated source owns both kernel and bootstrap
    Invalid      a selected/present source failed; boot stops
    ```

  - Once a manifest or paired system volume selects a source, malformed metadata, a missing named
    file, an I/O failure or a signature/digest mismatch is `Invalid`; none falls through to another
    disk, embedded image or ESP copy.
  - A fallback is another signed source explicitly permitted by signed boot-medium policy. "Try
    everything until something boots" is not a policy and is removed from authenticated mode.
  - The state machine is host-tested independently of UEFI I/O, including two disks in either
    enumeration order and a valid fallback beside an invalid selected source.

- [ ] **M5 - The EFI loader itself is authenticated in an isolated OVMF profile.**
  - Add an x86_64 QEMU profile with Secure-Boot-capable OVMF CODE, a private per-run VARS copy and an
    enrolled test PK/KEK/db. Never mutate the distribution VARS template in place.
  - Make the host prerequisites explicit and preflighted: `openssl`, `sbsign`, `sbverify` and one
    pinned VARS-enrolment tool (`virt-fw-vars`) are required by this dedicated profile. A missing
    command reports its name and skips nothing; ordinary non-Secure-Boot tests do not acquire these
    dependencies accidentally.
  - Sign the final EFI loader with a test Authenticode certificate after its bytes are final. The
    build records and independently checks that PE signature.
  - Type only the UEFI Runtime Services `GetVariable` entry needed to read `SetupMode` and
    `SecureBoot`, put the query behind the host-tested UEFI crate, and have the guest report both.
    The gate requires `SetupMode=0` and `SecureBoot=1`. An unsigned or bit-modified loader must not
    print the loader banner; a signed loader with a bad manifest may print only its loader refusal
    and must not print a kernel banner.
  - The same manifest verifier and mutation cases run through the aarch64 and riscv64 loader paths.
    Firmware Secure Boot on those two is not a completion gate here and the documentation must not
    imply otherwise.

- [ ] **M6 - Negative evidence is the gate, not one successful signed boot.**
  - Host mutations cover every header field, artifact path/kind/length/digest, source, architecture,
    release id, UUID, key id, algorithm, duplicate, truncation, trailing byte and configured bound.
  - Signatures from another product/architecture or an unknown key fail. A payload modified after
    signing fails. A manifest modified without changing a payload also fails.
  - QEMU covers: a valid signed boot; OVMF rejection of unsigned and altered loaders; loader
    rejection of unsigned, altered and wrong-architecture manifests; an invalid selected volume
    beside a valid fallback; a genuinely absent source with an explicitly permitted fallback; and a
    modified live image or optional package.
  - Include a positive test showing that an older correctly signed release still boots. That test is
    evidence that this milestone does not provide anti-rollback, and prevents later documentation
    from acquiring a freshness claim the mechanism does not enforce.

## Results

Measured on 2026-08-24.

- **M1 - THE FORMAT IS BINARY, LENGTH-DELIMITED AND HAS EXACTLY ONE ENCODING.**
  `bootproto::manifest` is the whole of it - the same module the loader parses with and a host tool
  writes with, because two readings of one format is how a signed thing and a verified thing stop
  being the same thing. The signed payload names the product, the architecture, the source kind, the
  release identity and the expected system-volume UUID; every row names its kind, its canonical
  path, its exact length and its SHA-256. Every field's extent is stated before its content, so a
  reader knows what it is about to read before it reads it - which a text format parsed by scanning
  for delimiters cannot say.

- **AND THE ROWS ARE SORTED BY THE FORMAT RATHER THAN BY THE WRITER.** A manifest whose rows can be
  reordered has more than one byte encoding, and a signature over one encoding says nothing about
  the other - so the reader refuses any order but ascending by kind and path, with no repeats, and
  the writer produces exactly that. Ten host tests: a round trip, the row walk, every prefix of a
  manifest refused as truncated, a byte after the signature refused as a second record, each enum
  field given a value this version does not define, rows swapped by hand, six paths that name
  something outside the source, and a writer refusing everything a reader would have to. Fifty-four
  tests pass in `bootproto`.

- **A SIGNATURE CANNOT COVER PART OF A MANIFEST, BY CONSTRUCTION.** `payload()` is the only accessor
  that returns bytes to verify and it returns all of them; there is no shorter prefix to ask for.
  That is the one refusal the milestone names which is better answered by an API than by a check.

- **THE VERIFIER IS THE BOOT CHAIN'S FIRST EXTERNAL DEPENDENCY, and it is fenced off.** `bootsig` -
  `ed25519-dalek` with `verify_strict`, which rejects the small-order keys and non-canonical
  encodings that let one signature verify under more than one key - is its own crate, so `bootproto`
  stays dependency-free and the KERNEL, which links it, compiles none of this. The milestone says
  why: "use an established `no_std` verifier and do not implement curve or signature arithmetic in
  this tree". Four tests, including the one that matters: a signature over the payload WITHOUT the
  domain string does not verify.

- **AND IT COST TWO BUILD KNOBS, both named where they are set.** `sha2` is a direct dependency only
  so its `force-soft` feature applies - without it a bare-metal build stops at "rustc-LLVM ERROR: Do
  not know how to split the result of this operator!" - and `x86_64-unknown-uefi` needs
  `curve25519_dalek_backend="serial"`, because that dependency picks a SIMD backend on a nightly
  compiler and a UEFI application has no AVX2 to lower it onto. Set per target rather than in
  `[build] rustflags`, which would also reach `build-std`'s `core`. All three loader targets build.

- **V1 IS STILL THE LIVE PATH**, because the loader does not read v2 yet: moving it is M3, and until
  then a production boot verifies exactly what it verified before. Nothing treats v1 as
  authenticated - it never was, and the text format's own comment says so.

- **M2 - THE TOOL SIGNS THE STAGED BYTES AND THEN VERIFIES WHAT IT WROTE.** `tools/sign-manifest`
  takes the artifacts as they are staged - after stripping, which is the point: a manifest made from
  what a compiler produced describes bytes the loader will never read - hashes them, encodes with
  `bootproto::manifest`, signs, and then RE-READS its own output with the same parser and the same
  verifier the loader carries. A signing tool that cannot check its own output moves every one of
  its failures to a boot.

- **TWO SIGNER CONTRACTS, AND THE SECOND ONE IS SOMEBODY ELSE'S PROGRAM.** `test-trust` uses a
  published fixture key - published so a build is reproducible and cannot be mistaken for a release.
  `external-release` invokes ONE configured executable: the canonical message on its stdin, exactly
  one raw 64-byte signature on its stdout, nothing else. Watched to refuse, four ways: without
  `--public-key`, without `--signer`, and without `--key-id` it stops before reading an artifact;
  and given a signer that prints a banner first (71 bytes, and a signature is 64), one that exits
  non-zero, or one that signs with a different key, it refuses and writes nothing. That last is why
  the tool verifies rather than trusts - a release signer is a program this tree does not own.

- **THE LOADER CARRIES PUBLIC HALVES AND A PROFILE, AND THE PROFILE IS IN THE BINARY.** `trust.rs`
  compiles in one or more `(key_id, public key)` roots; a manifest names a KEY ID, so it can never
  nominate a key, and an id this loader does not carry is a refusal rather than a fallback to the
  next root. A test-trust build says `TEST TRUST (published key)` on the console BEFORE it loads
  anything. AND AN `external-release` BUILD WITHOUT ITS KEY DOES NOT COMPILE - `LIBER_TRUST_KEY` and
  `LIBER_TRUST_KEY_ID` are read in a `const`, so "fails before an image is written" is as early as
  a failure can be.

- **AND A GATE PROVES THE TWO BUILDS DIFFER IN THE BINARY.** `check.sh --gate trust-profile` (32
  gates now) builds both and greps them: the release loader contains neither the published key, nor
  its key id, nor the marker, and does contain the key it was built for. It asserts the test-trust
  loader DOES carry all three first - a gate that only checks the release build cannot tell "the
  test key is absent" from "this grep finds nothing".

- **AND THE WALK STOPPED OWNING THE CHOICE OF MANIFEST.** `abi::bootstrap::assemble` used to read
  `etc/boot.manifest` itself, which made the text format part of the state machine. It now takes a
  predicate - is this the content recorded for this path - and the CALLER decides which manifest
  answers it. That is what lets a source carrying a signed manifest be checked against the signed
  one, and it is where the policy belongs.

- **M3 (IN PROGRESS) - THE LOADER PREFERS THE SIGNED MANIFEST AND CHECKS BEFORE IT ACTS.** Where a
  source carries `etc/boot.manifest2` the loader verifies its signature against a compiled-in key
  and checks the kernel, the bootstrap list and every program the list names against its rows -
  BEFORE the kernel bytes are parsed as an ELF, before a destination is derived from them and before
  anything is copied anywhere. A header read out of an unverified image is a decision made on an
  attacker's numbers. A source with only the text manifest keeps the behaviour it had, which proves
  integrity and nothing about origin, and says which of the two it used.

- **WHAT WAS VERIFIED IS SAID OUT LOUD RATHER THAN PUT IN `BootInfo`.** The kernel does not need
  trust metadata - this is a loader-owned decision taken before the kernel exists, and a field it
  could read is a field something would later be tempted to re-derive a decision from. The line
  carries the release the manifest names, the key that signed it and the digest of the record, which
  is what makes two boots comparable.

- **AND THE BUILD WRITES ONE, SO THE PATH IS EXERCISED RATHER THAN MERELY PRESENT.** `mkpackages`
  signs the staged set - it is where the staged bytes are, and a manifest made anywhere else
  describes files that have been copied, stripped or re-linked since - and `mkimage` signs the boot
  medium's, over the STRIPPED kernel that was actually copied onto it. Both stage the signed
  manifest beside the text one, so a loader built before signing existed still boots the same media.

- **MEASURED, x86_64 END TO END:** `loader: TEST TRUST (published key)` before anything is loaded,
  then `loader: signed manifest verified - release 0.0.1, key 7e570001, manifest f735350375fc9ab0`,
  the bootstrap set verified against the signed manifest too, four of four cores online and a shell.

- **AND THE FIRST BOOT WITH IT REFUSED, WHICH IS THE RESULT WORTH KEEPING.** `loader: a boot file is
  not named in the signed manifest - refusing to boot`. The kernel was in the manifest under
  `program` while the loader looked it up as `kernel`: the KIND IS PART OF THE NAME, and a kernel
  filed as a program is a kernel the loader cannot find. Exactly the refusal the format's `find`
  exists to produce, arriving on the first boot rather than as an accepted mismatch.

- **WHAT REMAINS:** the `system-volume.img` rule - a boot medium's outer manifest covering that
  whole image and its pairing UUID - which is the one artifact of the four the milestone names that
  is still covered only by the text manifest.

- **M4 - ABSENCE AND BETRAYAL STOPPED BEING THE SAME ANSWER.** `assemble_bootstrap` returned
  `Option<Vec<u8>>`, and `None` meant both "there is no bootstrap list here, try the next disk" and
  "this source was selected and its manifest refused it". No caller could tell them apart, so all
  four did the same thing with both - went on to the next source. That turns a detected tampering
  into a silent fallback, which is the opposite of what the check is for. It now answers
  `Unavailable | Verified(archive) | Invalid(Refusal)`, with the refusal naming which fact refused
  it: no manifest beside the list, a list the manifest does not vouch for, a named program the
  source lacks, a program that does not match, a malformed list, or a set that verified and could
  not be packed.

- **AND `Invalid` ENDS THE BOOT RATHER THAN THE SEARCH.** Every call site stops looking, and the
  loader refuses to hand off at all - the same shape as the kernel's own manifest failure a couple
  of hundred lines above it, where the panic handler writes to serial and hangs. "Try everything
  until something boots" is not a policy, and it is gone from this path.

- **THE STATE MACHINE IS WHERE A HOST CAN DRIVE IT.** `abi::bootstrap::assemble` sits beside the
  list parser it uses and the archive writer it ends with; the loader keeps only the reading and the
  reporting, because it is a UEFI binary and nothing inside one can be tested. It takes the source
  and the manifest check as CLOSURES rather than traits - the loader's two filesystems are types it
  does not own, and the orphan rule does not let it implement somebody else's trait for them.

- **SIX HOST TESTS, WATCHED TO FAIL.** No list is `Unavailable`; a list with no manifest is
  `Invalid`; a list the manifest does not vouch for, a missing named program and a program that does
  not match are each their own refusal; a source that vouches for everything it names produces the
  archive the kernel unpacks, with both programs under the names the list gave them. And the
  policy over two sources in either order: a source that refuses is refused wherever it appears in
  the enumeration, and one that is merely absent never is. Collapsing "no manifest" back into
  `Unavailable` fails exactly the two tests that are about that distinction.

- **NOT PROVEN ON A BOOT YET.** All three loader targets build; the guest evidence belongs with the
  end-of-batch runs.

## Dependency order

```text
P02M0143 M4 -> M1 -> M2 -> M3 -> M4 -> M6
                         \-> M5 -----^
```

M1 and M2 define what authenticity means. Coverage and source selection must use that definition;
OVMF can be brought up in parallel once the final loader-signing order is known. M6 closes only when
both the firmware and payload halves have independently failed in the expected place.

## Definition of done

- Every supported UEFI loader path authenticates every kernel and early module before placement or
  hand-off, using the same bounded parser and trust-root policy.
- Kernel and bootstrap cannot be mixed across signed releases or sources.
- A present but invalid selected source stops; only an unavailable source can enter a signed
  fallback policy.
- The x86_64 OVMF Secure Boot gate distinguishes firmware refusal, loader refusal and kernel entry.
- Signed-manifest positive and negative boots run on x86_64, aarch64 and riscv64 QEMU targets; the
  firmware-authentication claim remains explicitly x86_64-only in this milestone.
- `test-trust` and `external-release` are mechanically separated; the latter accepts only the
  stdin/stdout signer contract above, and no release private key or secret signing material exists
  in the repository or staged outputs.
- `docs/THREAT_MODEL.md` and boot documentation state exactly: authenticity is enforced; freshness,
  measured boot, physical-firmware qualification and production key operations are not.
- The ordinary checks and the dedicated signed-boot/OVMF gates are green from a clean staged image.

## What this milestone refuses, and why

- **Anti-rollback, A/B updates and health commit.** QEMU can exercise those mechanisms later, but a
  trusted monotonic backend and update/recovery policy are a separate state machine. A signed old
  image remains accepted here by design. This milestone defines no slot identifier, selector or
  state transition for them.
- **TPM measurements, PCR policy, attestation and sealed secrets.** They answer who can observe or
  release state, not whether this manifest signature is valid.
- **A home-grown signature implementation.** Boot code is not an excuse to implement cryptography.
- **A signature over a manifest beside an unauthenticated replaceable loader.** That protects
  against accidental corruption with a more complicated checksum; OVMF closes the demonstrated
  loader-root half for the profile this milestone claims.
- **Production key rotation/revocation, Microsoft signing, shim/MOK or an HSM operating procedure.**
  The format has a key-id boundary, but release operations require owners and infrastructure this
  repository cannot prove in QEMU.
- **A physical-hardware claim.** Firmware enrollment UI, NVRAM persistence and board recovery are
  not represented by OVMF and are not smuggled into the definition of done.
- **Authentication of mutable post-boot state.** The system image/root trust policy above early boot
  is a separate problem; this milestone covers bytes the loader executes or hands off.
