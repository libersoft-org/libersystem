# P02M0157 - The firmware described something the tables cannot hold, and the kernel used it anyway

Status: REOPENED (2026-08-26). An independent audit of the closed milestones found 3 verified defects; they are the last section of this file. Was COMPLETE (2026-08-26). FIRMWARE VALIDATION AND BRING-UP CORRECTNESS. NOT A PHYSICAL-HARDWARE CLAIM.

## Goal

Take the firmware-described topology and the secondary bring-up state machine from "refuses the
shapes that were thought of" to "refuses every shape it cannot represent, and represents every shape
that is legal".

Two outside audits found eight places where a legal firmware description is either refused, silently
truncated, or accepted with a value the kernel then uses as if it meant something. They cluster into
one subject: the boundary where a firmware number becomes a kernel decision. That boundary is worth
one milestone rather than eight scattered fixes, because the same fixture work covers all of them.

None of this is a physical-hardware claim. Every fixture below is a synthesized table or tree; the
milestone proves the parser and the bring-up state machine, not a board.

## What is there now

Measured on 2026-08-26, against `fd9c1620`. Every item was read in the source before being written
down.

- **A LEGAL TWO-NODE TREE WITH SPARSE IDS IS REFUSED AS TOO MANY NODES.** `from_device_tree`
  ([topology/src/lib.rs:267-270](../../src/topology/src/lib.rs)) sizes the distance matrix from the
  largest raw node id:

  ```rust
  size = size.max(*from as usize + 1).max(*to as usize + 1);
  ```

  `MAX_NODES` is 16, so a tree whose two nodes are numbered 0 and 16 - which the `numa-node-id`
  binding permits and real firmware produces - builds a 17x17 matrix and returns `TooManyNodes`. The
  internal matrix must be indexed by a dense index, with a map from the raw `NodeId`.

- **A NODE THAT ONLY THE DISTANCE MAP MENTIONS IS LOST, AND THE COMMENT SAYS IT IS NOT.** Directly
  above the loop, [topology/src/lib.rs:263-266](../../src/topology/src/lib.rs) states "a triple naming
  a node no bank or processor mentions still defines the node, because a memoryless CPU-less node is
  a legal topology". The loop sets matrix cells and never calls `note_node`, so such a node is absent
  from `self.nodes` and from the built topology.

- **A DISTANCE BELOW LOCAL IS ACCEPTED AND SORTS A REMOTE NODE AHEAD OF THE LOCAL ONE.** The ACPI
  path checks the diagonal and nothing else
  ([acpi.rs:158-160](../../src/topology/src/acpi.rs)); the FDT path defaults every off-diagonal cell
  to `REMOTE_DISTANCE` - correctly, and its comment explains why - and then writes each stated triple
  into the cell unchecked. Firmware stating `distance(node0, node1) = 0` produces a fallback order in
  which node 1 is nearer than local. That is a malformed table and must be refused, not preferred.

- **TWO TRIPLES FOR THE SAME PAIR: THE LAST ONE WINS.** The same loop writes each cell
  unconditionally. Two records that disagree about one distance are a firmware contradiction, and
  `Builder::build` already refuses contradictions of exactly this kind elsewhere - a memory range
  claimed by two nodes is `ContradictoryOverlap`, a CPU placed on two nodes is `DuplicateCpu`. The
  distance table is the one place where the later record silently replaces the earlier one.

- **A KNOWN SRAT RECORD THAT IS TOO SHORT IS TREATED AS AN UNKNOWN EXTENSION.**
  [acpi.rs:80-123](../../src/topology/src/acpi.rs) matches each known type with a length guard and
  ends with `_ => {}`, so `SRAT_PROCESSOR_LOCAL_APIC` with a length of 12 falls through the guard
  into the catch-all and is skipped in silence. Firmware saying "this is a processor record" and not
  supplying the fields a processor record has is a truncated table, and a dropped CPU is exactly the
  outcome that is hardest to notice afterwards.

- **A REFUSED DEVICE TREE KEEPS THE COMPILED QEMU DESCRIPTOR, WHICH THE ARCHITECTURE MILESTONE
  FORBIDS.** Its Definition of done says static QEMU descriptors "cannot be selected by a boot which
  has a DT". On riscv64, `imsic::configure` returns an error for every layout this port cannot
  address and deliberately leaves the previous value alone
  ([imsic.rs:54-72](../../src/kernel/arch/riscv64/imsic.rs)), and the caller keeps the compiled
  `qemu-virt-aia` descriptor and says so
  ([boot.rs:466](../../src/kernel/arch/riscv64/boot.rs)). Naming it is much better than defaulting
  silently, and it is still a boot that HAS a tree, read that tree, refused it, and then used
  hardcoded addresses. A machine whose IMSIC this port cannot address is a machine this port must not
  drive MSIs on.

  The aarch64 side is NOT this defect: `QEMU_VIRT_GICV2` is chosen when `tree.is_none()`, which is
  the no-DT case the same sentence explicitly permits. One audit called that a violation; it is not.

- **A SECONDARY THAT ARRIVED IS RECORDED AS ABANDONED.** The arriving core takes its id with a
  compare-exchange from `SLOT_PENDING` to `SLOT_ONLINE`
  ([smpboot/src/lib.rs:199](../../src/smpboot/src/lib.rs)); the boot core, on a timeout, writes
  `SLOT_ABANDONED` unconditionally ([smpboot/src/lib.rs:238](../../src/smpboot/src/lib.rs)). A core
  that claimed its id in the window between the last poll and the timeout keeps running and using
  per-CPU state under an id the table now says was abandoned, and `Outcome.online` does not count it.
  The id is not handed out twice - `next_id` still advances - so this is a bookkeeping divergence
  rather than a collision, and everything downstream that reads the slot state is reading a lie about
  a running core.

- **A CORE WHOSE HARDWARE ID IS ZERO IS TREATED AS NOT ONLINE.** The NUMA binding pass uses the
  hardware id as a proxy for "this core reported in"
  ([smp/numa/mod.rs:43-47](../../src/kernel/smp/numa/mod.rs)):

  ```rust
  if cpu > 0 && hardware == 0 { continue; }
  ```

  The comment is honest that this is a stand-in for a mask. On riscv64 the SBI boot hart is not
  necessarily hart 0, so hart 0 can be a perfectly ordinary online secondary - and it gets no node
  binding.

## Work

- [x] **M1 - dense internal node indexing.** A map from raw `NodeId` to a dense index built once, the
  distance matrix sized by the number of distinct nodes rather than by the largest id, and every
  lookup routed through the map. `MAX_NODES` then bounds what it was written to bound - how many
  nodes the kernel supports - rather than how large a node may be numbered.

- [x] **M2 - a distance triple defines its nodes.** Call `note_node` for both ends, so the comment
  above the loop describes the loop.

- [x] **M3 - reject a distance table that cannot be true.** Diagonal exactly `LOCAL_DISTANCE`;
  off-diagonal at least `LOCAL_DISTANCE`; two records for one pair that disagree are a refusal in the
  same class as `ContradictoryOverlap`. Apply it to both the ACPI and the FDT path - they are two
  readers of one contract and only one of them checks anything today.

- [x] **M4 - a known ACPI record that is too short is `Truncated`, not unknown.** Separate "a type
  this parser does not know" from "a type it knows, whose length contradicts its own definition".
  Only the first may be skipped.

- [x] **M5 - a boot that read a device tree does not fall back to a compiled descriptor.** On
  riscv64, a tree that describes an IMSIC this port cannot address stops the MSI path rather than
  pointing it at `qemu-virt-aia`: no interrupt files are configured, no MSI is armed, and the kernel
  says which fact refused it. A machine with no supervisor IMSIC in its tree - plain `virt` routing
  through a PLIC - is unaffected and keeps its current path, and so does a boot with no tree at all.

- [x] **M6 - the timeout may not overwrite a slot that has already been claimed.** Compare-exchange
  `SLOT_PENDING` to `SLOT_ABANDONED`; if the exchange fails because the slot is `SLOT_ONLINE`, the
  core arrived late and is running - count it online and record the late arrival as its own event.
  The existing `attempts` host tests already model timeout-then-late-arrival and are where this is
  proved.

- [x] **M7 - online detection stops using a hardware id as a sentinel.** Give bring-up an explicit
  record of which logical ids came up, and have the NUMA binding pass read that instead of inferring
  it. This is the same fact `Outcome` and the slot table already hold; what is missing is a reader.

- [x] **M8 - fixtures for every shape above.** Raw node ids that are sparse and large (3 and 257, not
  0 and 1), a node mentioned only by a distance triple, an off-diagonal distance below local, two
  contradicting triples for one pair, a short `SRAT_PROCESSOR_LOCAL_APIC`, a short
  `SRAT_MEMORY`, an IMSIC node with guest-index bits and one outside the direct map, and a timeout
  followed by a late claim. Host tests, because none of these is a shape QEMU emits on request.

## Dependency order

M1 comes first; M2 and M3 are written against the dense index. M4 is independent. M5 is independent
and touches one port. M6 and M7 are one subject and should land together - M7 is what makes M6's
distinction visible to a caller. M8 accompanies each of the others rather than following them.

## Definition of done

- A legal topology is refused only for a reason the kernel can name, and node numbering is not one of
  them: sparse and large raw ids build the same topology as dense ones.
- A node mentioned only in the distance map is present in the built topology.
- A distance table whose diagonal is not local, whose off-diagonal is below local, or which
  contradicts itself, is refused by both the ACPI and the FDT reader.
- A known ACPI record whose length contradicts its type is a refusal; only genuinely unknown types
  are skipped.
- A riscv64 boot that read a device tree never drives interrupt files at a compiled address; a boot
  with no tree keeps its current behaviour.
- A secondary that claims its id after the boot core timed out is recorded as online and as a late
  arrival, never as abandoned, and the host tests show both orderings.
- Node binding covers every core that came up, including one whose hardware id is zero.
- Documentation says no physical NUMA or AIA machine was validated; every fixture is synthesized.

## What this milestone refuses, and why

- **A physical-hardware claim.** Every table and tree here is synthesized. Firmware quirks, errata and
  board wiring are not represented and are not implied.
- **HMAT, CXL tiers, memory hotplug or any new firmware table.** The subject is the tables already
  read, and whether what they say survives the trip into a kernel decision.
- **Moving the strict/preferred/contiguous placement API out of `#[cfg(test)]`.** One audit called
  this a contract violation. It is not a defect: this tree forbids dead code and forbids suppressing
  the warning, so a public production API with no production caller could not exist here, and the
  comment at [frame/mod.rs:1404](../../src/kernel/mem/frame/mod.rs) says exactly that. The real
  question - whether a kernel stack for a thread being placed on another node should come from that
  node's pool - is a placement policy with its own call site, and it belongs to whichever milestone
  writes that call site. Written down here so it is not raised again as a bug.
- **Requiring the boot CPU to be declared exactly once, as a refusal.** Also raised by both audits,
  and also not a defect: `Topology::resolve` records `boot_declared` and `duplicates`
  ([smpboot/src/lib.rs:59-86](../../src/smpboot/src/lib.rs)), both DT ports read them and print them
  ([aarch64/boot.rs:719](../../src/kernel/arch/aarch64/boot.rs),
  [riscv64/boot.rs:442](../../src/kernel/arch/riscv64/boot.rs)), and a duplicate is never started
  twice. A tree that names the running core zero times or twice is odd, not fatal, and turning a
  named diagnostic into a refusal would stop boots that work.
- **The aarch64 no-DT descriptor.** Selecting a static descriptor when there is no device tree is the
  case the architecture milestone's own sentence permits, and the regression profiles depend on it.
  Only a boot that HAS a tree is in scope for M5.

## Results

### M1/M2/M3 - the distance table, and what a firmware number is allowed to mean

The rows of the matrix now CARRY the nodes they are for. A SLIT is dense by construction - row N is
proximity domain N - so for that reader nothing changed; a device tree's is not, and the reader that
rebuilt a square from its triples sized it by the LARGEST id it saw. Two nodes numbered 0 and 16
needed a seventeen-row square, and `MAX_NODES` refused it as too many nodes: a legal two-node
topology turned away over its numbering.

Three refusals were added to the same walk, each of which the builder already made for a different
kind of contradiction:

- a distance below local anywhere off the diagonal, which sorted a REMOTE node ahead of the local one
  in every fallback order - every allocation steered away from the memory it was steering towards;
- two triples for one pair that disagree, which was last-writer-wins in the one place the builder
  refuses a contradiction everywhere else (`ContradictoryOverlap` for memory, `DuplicateCpu` for
  processors);
- and the comment that had always said a triple defines its nodes was made true, by telling the
  builder about them.

### M4 - a known record that is too short

`SRAT_PROCESSOR_LOCAL_APIC` with a length of twelve fell past its guard into the catch-all and was
skipped in the same silence as a structure type this reader has never heard of. Those are opposite
facts: firmware describing more than this reads is entitled to; firmware saying "this is a processor
record" without a processor record's fields is a damaged table, and the CPU it drops is exactly the
loss nothing downstream can notice. The length check now comes before the match, and a type this
reader genuinely does not know is still skipped - which the fixture asserts from both sides.

### M5 - a boot that read a tree does not use a compiled address

`imsic::configure` refuses every layout this port cannot address and deliberately leaves the previous
value alone, so a machine whose IMSIC this kernel cannot reach kept the `qemu-virt-aia` address and
started writing MSIs into it - a static descriptor selected by a boot which HAS a tree, which the
architecture contract forbids in as many words. It named the refusal, which is much better than
defaulting silently, and it was still hardcoded addresses on a machine that had said otherwise.

The MSI path is now taken out of service instead: `init_hart` arms nothing, `program_acquired` hands
out no vector, and the boot says which fact refused it and that the compiled address is NOT being
used. Fewer working devices on a machine this kernel cannot drive, rather than writes into an address
the firmware never claimed. A machine with no supervisor IMSIC in its tree - plain `virt`, routing
through a PLIC - and a boot with no tree at all are both unaffected.

It has also now been seen on a live boot, by accident: a first version of the profile gate passed a
second `-machine` on the riscv64 command line, and the kernel read the resulting tree as describing
group-indexed interrupt files - which this port does not address. It said so, armed no MSI, did not
touch the compiled address, and came up and ran its tests. That is the whole of what this item asked
for, demonstrated by a machine rather than argued for.

The refusal is also driven from the other end, because QEMU cannot be asked for such a machine on
purpose: a riscv64 kernel test disarms the path and requires `acquire_msi` to hand out nothing, then
re-arms and requires the same acquire to work - which also proves a refusal does not consume an EID,
because a refusal that ran the machine out of vectors would be a second bug on the path that never
delivers one. Re-arming is `#[cfg(test)]`: a production build has no way to un-refuse a machine it
refused, and a test that disarmed without being able to put it back would take every interrupt-driven
case after it on the same boot.

### M6/M7 - a core that arrived, and a core that is online

The arriving core takes its id with a compare-exchange from `PENDING` to `ONLINE`; the boot core's
timeout wrote `ABANDONED` over whatever was there. A core that claimed its id in the window between
the last poll and that store kept running - under an id the table then said had been abandoned, and
uncounted by `online`. No id was ever handed out twice, so it was never a collision: it was a working
core the boot did not know it had, and every reader of that state was wrong about it. The timeout is
now a compare-exchange, and losing it is a `LateArrival` - counted online, reported as late.

The reader that was most wrong about it was the NUMA binding pass, which asked whether a core was
online by reading its controller id and treating zero as "never answered". That is right on a machine
whose boot core is APIC 0 and wrong on one where the SBI boot hart is not hart zero, because hart 0 is
then an ordinary online secondary. `smp::is_online` is the fact itself, set by the same code that
records the id so the two cannot disagree.

### And one asymmetry the profile gate found by asking both ports the same question

`aarch64` has counted its timer interrupts at boot and reported them for as long as its prologue has
existed. `riscv64` armed the S-mode timer and said nothing - so on that port a boot carried no
evidence at all that the interrupt path delivers the one interrupt everything timed is measured
against. That is not a difference between the machines; it is a difference between what was written
down, and it only became visible when a gate tried to require the same fact of both and found there
was nothing to read.

`riscv64` now reports it in the same words, zero included:

```
riscv64: NO TIMER IRQ WAS DELIVERED in {spins} spins - the interrupt path is not carrying the S-mode
timer, and everything timed on this machine is on a clock that does not tick
```

### M8 - and the fixtures that would have caught all of it

The readers had been exercised with nodes numbered 0 and 1, which is the one numbering where a raw
firmware id and a dense index are the same number - so every place that confused the two passed. The
new fixtures use 3 and 257.

Host tests: `topology` 37 (was 32), `smpboot` 18 (was 16). Watched to fail: with all four table fixes
mutated away, four topology tests fail with the sentences they are named for; with the compare-exchange
turned back into a store, `a_core_that_claims_its_id_after_the_timeout_is_online_and_late` fails on
"a core that is running is online".

## Independent audit of the closed milestone (2026-08-26)

Status: REOPENED. Two bring-up defects a QEMU machine cannot show, and one fixture that does not
cross the boundary it is named for.

- [x] **A core that arrives late gets no NUMA binding, for the life of the boot.** The
  compare-exchange this milestone added correctly keeps a late core online and counts it
  ([smpboot/lib.rs](../../src/smpboot/src/lib.rs)) - but the portable online bit is set by the core
  itself, in `secondary_idle` ([psci.rs](../../src/kernel/arch/aarch64/psci.rs)), after bring-up has
  moved on. `bind_online` runs once and returns early forever afterwards
  ([numa/mod.rs](../../src/kernel/smp/numa/mod.rs)), skipping every core `is_online` says no to. A
  core landing in that window is online, is scheduled on, and belongs to no node for the rest of the
  boot. Bind a core when it comes online rather than binding the set once.

- [x] **The portable CPU-id table on aarch64 holds indices, and the NUMA join reads it.**
  `set_cpu_count` fills `LAPIC_IDS[i] = i` ([smp/mod.rs](../../src/kernel/smp/mod.rs)); the real
  MPIDR is stored in the arch-private `SEC_MPIDR`
  ([psci.rs](../../src/kernel/arch/aarch64/psci.rs)). `bind_online` reads `smp::lapic_id(cpu)` and
  asks the firmware topology which node that hardware id belongs to
  ([numa/mod.rs](../../src/kernel/smp/numa/mod.rs)). The comment beside the table says outright that
  the id is the index because QEMU's `virt` makes it so. Any machine whose MPIDR affinities are not
  `0..N` - which is most of them - binds the wrong node or none at all. Publish the real id into the
  portable table when the core reports in; `SEC_MPIDR` already holds it.

- [x] **The IMSIC refusal fixture flips the flag instead of driving the refusal.** The test sets
  `set_usable_for_test(false)` and checks that no vector is handed out
  ([interrupts/tests.rs](../../src/kernel/arch/riscv64/interrupts/tests.rs)). What that proves is
  that `usable()` gates `acquire_msi`. What it is named for is that a tree describing a layout this
  port cannot address takes the MSI path out of service - and nothing drives `imsic::configure` with
  such a layout and then reads `usable()`.

## Results (2026-08-26)

**A CORE BINDS ITSELF WHEN IT ARRIVES.** The sweep ran once and returned early on every later call,
and the portable online bit is set by the core ITSELF after bring-up has moved on - so a core landing
in the timeout/arrival window that `smpboot`'s compare-exchange exists to keep online was not online
when the sweep looked, and belonged to no node for the rest of the boot while being scheduled on and
allocating memory. `mark_online` and the x86 AP entry both bind now, so "online" and "placed" are one
transition rather than two with a window between them.

**AND THE PORTABLE CPU-ID TABLE HOLDS IDS RATHER THAN SUBSCRIPTS.** `set_cpu_count` filled it with
`0..N`, and the comment beside it said why: on QEMU's `virt` the MPIDR affinity happens to be the
linear core index. `bind_online` reads that table and asks the firmware topology which node that
HARDWARE id belongs to, so on any machine whose affinities are not dense - which is most real ones,
where cluster and core sit in different fields - the lookup used a number no firmware table has ever
been keyed on. The table is sized here and filled by each core as it reports in, boot core included.

The IMSIC refusal fixture drives `configure` now. `configure` reads seven fields of a much larger
`BootInfo`, so those became a `Layout` a test can build one field at a time: each of the seven
refusals is this machine's accepted layout with ONE thing changed, and the test then drives the
boot's answer to a refusal - `disarm` - and checks that no vector is handed out.
