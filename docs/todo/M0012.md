# M0012 - Fault isolation and crashed-process cleanup

- [x] A userspace page fault / GPF terminates only the faulting `Process`, not the kernel
- [x] Process teardown: close all handles, free frames + address space, refund Domain accounting
- [x] `fault_info_get`: record and expose basic fault info for the killed process
- [x] Other cores and the scheduler keep running across the kill
- [x] **Find the process a booted system kills on every boot.** Right after the shell prints
  the banner the kernel reports `fault: ring-3 page fault (code 0x6) at 0x20173f, CR2 = 0x0
  - terminating process`: a userspace write through a null pointer. Fault isolation does its
  job (the system carries on and the suite stays green), which is exactly why nobody has
  noticed - it happens inside `init_package_starts_system_manager` on a fully green x86_64
  run of 145 tests. Found while diagnosing the M0062 xhci test, where it was first mistaken
  for the driver's own death because the two sat next to each other in the log; the driver is
  not involved. Identify the process, find the write, and decide whether a test should refuse
  a boot that kills anything.
  Result (2026-07-31): it is `watchdog_probe`, ServiceManager's managed canary, and the write
  is deliberate. Its `CRASH` handler is `(0 as *mut u8).write_volatile(0)` - a write to the
  unmapped null page, which is exactly `code 0x6` (write, user, not-present) at `CR2 = 0x0` -
  and ServiceManager's boot self-test commands it: `send_blocking(canary_ctrl, b"CRASH", 0)`,
  then it observes the peer-close and restarts per policy, then commands `HANG` to drive the
  watchdog path as well. So a booted system kills a process on every boot because that is the
  proof that killing one works, and fault isolation "doing its job" was the feature and not
  the reason nobody noticed.
  How it was found is the point, and it is why the item below had to come first: not by
  deciding which image `0x20173f` falls in. That guess is what sent the earlier investigation
  to the xhci driver for hours, and the entry-point list was on screen this time too. Instead
  the fault line was made to name its process, and the answer arrived in three readings - the
  address is outside the dynamic load base, so a static init-package program; those carry no
  identity note, so the kernel could not name it; and it reported `unnamed` even after
  ProcessService began labelling its launches, which left only the programs the supervisor
  spawns itself. There is exactly one.
  On whether a test should refuse a boot that kills anything: no, and the reason is this
  finding. Such a rule would fail on the very test that proves fault isolation works. The
  useful rule is the weaker one the item below implements - a kill must be attributable - so
  a deliberate one names itself and an unexplained one stands out instead of blending in.
- [x] **Name the faulting process in the fault message.** The report carries the instruction
  pointer and CR2 but not the koid or the program, and every EXEC image shares a load base, so
  a fault in a booted system cannot be attributed without guessing which image the address
  falls in and disassembling it - a guess that already sent one investigation down the wrong
  path for hours. `FaultInfo` is recorded on the `Process`, so the name and koid are in hand at
  the point the message is printed.
  Reporting is also not uniform across architectures, which is the same item: a full riscv64
  suite run prints no fault line at all, even though the deliberate crash tests clearly fault
  there (their recovery messages follow in order). x86_64 prints one per fault. So on riscv64 a
  process can die in a booted system and leave nothing in the log - which is also why the null
  write above cannot be confirmed or ruled out on that architecture from its run log. Whatever
  the message becomes, all three backends should emit it.
  Result (2026-07-31): the message is now
  `fault: ring-3 <kind> (code 0x6) at 0x20173f, addr 0x0 - terminating process koid=4935 (watchdog_probe)`
  and it is emitted from `fault::terminate_user`, the one path all three architectures reach.
  That placement answers both halves at once: only x86_64 printed anything before, so a process
  could die on riscv64 and leave nothing in the log, and only there is the process in hand, so
  only there can the line say which one it was. The two per-architecture prints in the x86_64
  IDT are gone rather than duplicated.
  One premise of this item was wrong and it was the whole difficulty. "`FaultInfo` is recorded
  on the `Process`, so the name and koid are in hand" - the koid was, the name was not. In the
  entire kernel `set_name` had one caller, the property syscall, so every process in a booted
  system was anonymous. This was never a message that omitted a name; it was a name that did
  not exist.
  Naming therefore had to be built, and it took four routes because each covers a set the
  others cannot. The kernel loader reads `artifact=` out of an image's own identity note, which
  covers everything staged on the volume, on both load paths and all three architectures, with
  no new parameter - the ELF is already parsed there. The static init-package programs carry no
  note at all, so ProcessService labels what it launches from the package entry it looked the
  program up by. `system_manager` is launched by the kernel itself, so the kernel labels that
  one. And ServiceManager's canary is spawned directly rather than through ProcessService, so
  the supervisor labels it - which is the case that mattered, since that is the process the
  item above was about.
  Labelling is best effort everywhere: a process that could not be labelled is still a process,
  and refusing a launch over a log label would trade a working system for a better message. An
  image with no note simply reports `unnamed`, which is itself informative - it is what
  narrowed the search above.
  Measured on each architecture rather than argued from the placement, because a shared code
  path is a reason to expect all three to print and not evidence that they do. Under the
  `kernel` tag every one of them emits three lines across the deliberate crash tests, where
  riscv64 emitted none at all before:
    x86_64   fault: ring-3 page fault (code 0x6) at 0x40000007, addr 0xdead000 - ... koid=1101 (unnamed)
    aarch64  fault: ring-3 page fault (code 0x92000045) at 0x40000008, addr 0xdead000 - ... koid=1101 (unnamed)
    riscv64  fault: ring-3 page fault (code 0xf) at 0x40000004, addr 0xdead000 - ... koid=1101 (unnamed)
  and on x86_64 the boot self-test crash names `watchdog_probe`. Those kernel-test faults
  report `unnamed` correctly: they are hand-laid ring-3 fixtures with no ELF and so no note,
  which is the case the fallback exists for.
  Three things cost a run each here and are worth passing on. The `boot` tag contains no fault
  at all, so a run of it showing no fault line proves nothing in either direction - it was the
  first thing tried and it was silent for that reason rather than for the one under
  investigation. The `process` tag on an emulated target times out inside the imgconv tests
  before it reaches the crash tests, so the deliberate ones want the `kernel` tag with
  `TEST_TIMEOUT` raised past the three-minute default a tag run gets. And the fault line goes
  to the guest log, not the run log - reading the wrong one reports zero faults on an
  architecture that emitted three.
- Done when: a userspace process that dereferences a bad pointer is killed and fully cleaned up, the kernel survives, and a test asserts the Domain's accounting returns to zero.
- Result: the page-fault and #GP handlers check the saved code selector's CPL; a ring-3 fault records a `FaultInfo` on the running `Process` and longjmps back into the kernel thread that entered ring 3 (reusing `usermode::exit_to_kernel`, the same one-way return as a clean `SYS_USER_EXIT`), so the kernel and every other core keep running. A ring-0 fault still halts loudly. The kernel thread resumes after its `enter` call and unwinds normally; dropping the thread tears the process down, and Drop-based refunds return the Domain's memory/handle/thread quotas (`HandleTable::drop` refunds open handles, `MemoryObject::drop` frees frames + refunds memory). New `fault.rs` (`FaultInfo`, `terminate_user`); `SYS_FAULT_INFO_GET` copies the recorded fault to a user buffer. `enter` now restores the caller's interrupt flag after the excursion (the `ret`-based longjmp does not, unlike `iretq`). `fault_isolation_kills_only_process` test: a ring-3 thread in a bounded Domain writes to an unmapped address; the kernel records the page fault (addr `0xdead000`), terminates the process, survives, and the Domain's memory/handle/thread accounting all return to zero.
