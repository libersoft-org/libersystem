# P02M0146 - The scenarios run on one architecture, and the runner says they run on three

Status: COMPLETE (2026-08-23). TEST COVERAGE. NOT A PHASE-2 COMPLETION GATE.

## Goal

Make `scenario-cold` on aarch64 and riscv64 do what it says it does, and run the scenario set there.

`lab.py scenario-cold` takes a target argument, accepts all three, and carries a comment saying the
only thing that ever tied a scenario to x86_64 was that no other target had a guest that would
answer - "now they do, and this is the command that starts one". The guest exists. THE COMMAND DOES
NOT COMPLETE ON EITHER OF THE OTHER TWO, and it fails before it boots anything, so nothing that
would have followed has ever been observed.

This matters beyond tidiness. `harness/scenarios/` is where behaviour that only a booted system can
show is checked - the launcher granting one capability and not another, a recording arriving on a
volume, a terminal that gives itself back - and the two architectures it has never run on are the
two whose PCI backends assign their own BARs and deliver their interrupts differently. P02M0101
closed with exactly that gap named: its capture path was proven on all three by kernel tests, and
joined up end to end on ONE.

## What is there now

Measured on 2026-08-23 by running the command and by counting bytes in the staged images.

- **THE FIXTURE RECIPE REFUSES EVERY NON-x86 TARGET, and it never reaches the guest.**
  `lab.py scenario-cold aarch64 ...` builds the system (nine minutes), then stops with `the aarch64
  scenario fixtures could not be built`. No guest is started. `harness/scenarios/make-fixtures.py`
  patches the byte string `koid` in `lib/protocol/process-proto.lslib` and insists it occurs exactly
  twice. It occurs **twice on x86_64, three times on aarch64 and once on riscv64**:

  | target  | `bin/uname`: `LiberSystem` | `process-proto`: `koid` | `process-proto`: `features=shared-image` |
  | ------- | -------------------------- | ----------------------- | ---------------------------------------- |
  | x86_64  | 1                          | 2                       | 1                                        |
  | aarch64 | 1                          | 3                       | 1                                        |
  | riscv64 | 1                          | 1                       | 1                                        |

  Three of the four substitutions the recipe makes have the same count everywhere, because they are
  data the program carries. The fourth is a compiled literal, and its count is where the compiler
  chose to put it: on x86_64 the packed string table plus one immediate stored by the text renderer;
  on aarch64 the packed table plus `"koid":` and `koid=` as separate literals; on riscv64 the packed
  table alone. The recipe's own comment says the count is stated rather than tolerated so that a
  rebuild which moves the string fails loudly - and the number it states is a fact about one
  compiler backend, so on two targets it fails loudly at something that is not wrong.

- **THE RUNNER THREW AWAY THE REASON.** `cmd_scenario_cold` runs the recipe with
  `stderr=subprocess.PIPE` and never looks at the pipe, then dies with a sentence naming no cause.
  The message above is what a caller sees; `process-proto: b'koid' occurs 3 times, expected 2` is
  what the recipe said, and it had to be re-run by hand to be read. This file says the opposite
  about its other child twenty lines further down: "The runner's own diagnosis goes into the serial
  log's neighbour rather than into /dev/null: it is the process that says `loader EFI not found`,
  and discarding that left every startup failure looking like a guest that never answered."

- **THE COLD GUEST AND THE RUNNER DISAGREE ABOUT WHERE QMP IS, on aarch64 and riscv64.**
  `qemu-run.sh` gives the x86_64 development guest `qemu-monitor-cold-$TARGET_ARCH.sock` and
  `qemu-qmp-cold-$TARGET_ARCH.sock` when `COLD=1`, which is what `cmd_scenario_cold` sets
  `MON_OVERRIDE` and `QMP_OVERRIDE` to. The aarch64 and riscv64 development blocks hard-code
  `qemu-monitor-$TARGET_ARCH.sock` and `qemu-qmp-$TARGET_ARCH.sock` and never consult `COLD`. A
  `key` or `pointer` step on those targets therefore reaches a socket the guest is not listening on:
  `qmp_command` dies with "no QEMU QMP socket", `send_keys` catches that and answers False, and the
  step fails. `input-events.toml` is entirely `key` steps.

- What is NOT known: nothing past the fixtures. No cold aarch64 or riscv64 guest has been driven, so
  whether the chain comes up, whether the agent answers, and what a scenario costs on an emulated
  target are all unmeasured. This milestone's evidence is the run, not the reading.

## Work

- [x] **M1 - The fixture recipe patches what is there, on the target it is building for.**
  - The count that varies is one substitution out of four, and what the fixture actually needs is
    that EVERY copy of the field name is patched, so no rendering of a process record disagrees with
    another. That is the invariant; "exactly two" was a proxy for it that only holds on one backend.
  - `substitute` gains a mode that requires at least one occurrence, replaces all of them, and
    asserts none survives. The other three call sites keep their exact counts, because their counts
    are properties of the data and not of the code generator - and a change in those IS a fixture
    that has stopped patching what it names.
  - THE LOUDNESS IS NOT LOST. A recipe that patched nothing still fails (zero occurrences), one that
    patched one of two still fails (a leftover survives), and the manifest still records the digest
    of every staged file the recipe read, so a set built from a different image is refused whatever
    the counts were.

- [x] **M2 - A child that refuses says why.**
  - `cmd_scenario_cold` prints what the fixture builder wrote to stderr before it dies. One line of
    plumbing, and it is the difference between "could not be built" and the sentence that names the
    string, the count and the file.

- [x] **M3 - One name for the cold guest's control sockets, on every target.**
  - The aarch64 and riscv64 development blocks take the same `COLD=1` suffix the x86_64 block
    already takes, so the guest binds what the runner connects to. Same rule as the control channel
    and the media images, which both got theirs when a cold run destroyed a persistent instance's.

- [x] **M4 - The set runs on both, and what it costs is written down.**
  - TWO SCENARIOS ARE BLOCKED ELSEWHERE, and named here rather than counted as a portability
    failure: `terminal-lifecycle` and `input-events` need a full-screen program to answer a key, and
    no full-screen program in this tree is given its terminal - `permission.run` cannot carry a tty
    control channel, so every one of them runs cooked with its keys going to the line editor. That
    is [P02M0147](P02M0147.md), it fails identically on x86_64, and it is not something a second
    architecture made true.
  - `lab.py scenario-cold aarch64 <every scenario>` and the same for riscv64, in one invocation per
    target because one invocation is one guest: the boot is paid once and each scenario adds only
    its own time.
  - Whatever those runs find is fixed here or refused by name here. That is the point of the
    milestone; the three items above are what has to be true before the runs can start.
  - The per-scenario times go into the Result, per target. An emulated scenario is minutes, and a
    number nobody recorded is the reason "run it on all three" keeps being deferred.

## Results

Measured on 2026-08-23 on this host (Linux 6.12.100+deb13-amd64, QEMU 10.0.11, KVM available for
x86_64; aarch64 and riscv64 emulated). Every scenario in `harness/scenarios/` was run against a cold
guest of each target, one invocation per target, one boot each.

| scenario            | x86_64  | aarch64 | riscv64 |
| ------------------- | ------- | ------- | ------- |
| shell basics        | 13.3 s  | 8.8 s   | 12.7 s  |
| launch a program    | 14.3 s  | 10.3 s  | 14.3 s  |
| fixture area        | 7.1 s   | 4.5 s   | 7.2 s   |
| registry publish    | 13.9 s  | 10.6 s  | 16.0 s  |
| registry shadow     | 12.7 s  | 7.9 s   | 11.7 s  |
| registry provider   | 21.2 s  | 14.6 s  | FAILS   |
| service restart     | 18.2 s  | 15.4 s  | 21.3 s  |
| agent restart       | 29.8 s  | 16.8 s  | 24.3 s  |
| audio capture       | 65.5 s  | 45.4 s  | 66.6 s  |
| terminal lifecycle  | FAILS   | FAILS   | FAILS   |
| input events        | FAILS   | FAILS   | FAILS   |

Nine of eleven on x86_64 and aarch64, eight on riscv64. An emulated guest is not the order of
magnitude slower the runner's ten-times scale factor assumes for these scenarios - most of them are
console round trips, and aarch64 is consistently the FASTEST of the three.

- **M1.** `substitute_every` replaces every copy and refuses a substitution that patches nothing or
  leaves one behind; the three substitutions whose counts are properties of the data keep their
  exact counts. Fixture sets now build for all three targets. Watched to fail both ways: a string
  that does not occur gives `does not occur; this fixture would patch nothing` on all three, and
  patching only the first copy gives `still occurs 1 times after patching` on x86_64 and `2 times`
  on aarch64 - and passes on riscv64, where there is only one copy, which is worth knowing.

- **M2.** The runner prints the recipe's own stderr before it dies. Proven by breaking the recipe
  and running `scenario-cold`: `lab: process-proto: b'kOId' does not occur; this fixture would
  patch nothing` now precedes `the x86_64 scenario fixtures could not be built`.

- **M3.** Both device-tree targets take the `COLD=1` suffix. Proven by the aarch64 run: `input
  events` typed `uname` on the EMULATED KEYBOARD and the guest answered - the QMP path reaches the
  guest it is driving, which it could not before.

- **M4 FOUND A DEFECT THAT WAS NOT ABOUT ARCHITECTURE AT ALL, and it is the reason this milestone is
  worth more than its title.** Six scenarios failed on the first aarch64 run. FOUR OF THEM FAILED
  IDENTICALLY ON x86_64 when the same four were run there - so they were not portability failures,
  they were scenarios nobody had run. What they were hiding:

  - **A PUBLISHED GENERATION WAS NEVER LOADED, ON ANY TARGET.** `registry-shadow`,
    `registry-provider` and `agent-restart` all failed waiting for a shadowed artifact to answer.
    The registry accepted the publication, listed it, and reported it `hot-publishable` - and every
    launch read the volume. ServiceManager made a resolution channel pair before any service
    started and sent DeviceManager one end of it, while the plan-based bootstrap made a SECOND pair
    for ProcessService's `REGISTRY` role and overwrote the variable holding the first pair's other
    end. The agent announced itself into a channel nobody held; ProcessService never armed; every
    launch skipped the registry in silence. A P02M0141 migration defect, and the whole development
    registry has been decorative since. Fixed by deleting the premature pair: the end the agent gets
    is the one the bootstrap recorded when it handed ProcessService its half. Proven live -
    `dev-publish uname` then `uname` prints `SHADOWEDsys`.
  - **A SCENARIO WAITING FOR A STRING NOTHING PRINTS.** `input-events` expected
    `arrows/page scroll` from `licoview`. That text appears NOWHERE IN THE TREE; the hint line was
    rewritten and the scenario was not, so it had been failing at the same step on every
    architecture. It now quotes what the program writes.
  - **A RESTORE VOCABULARY WORD THAT CANNOT MATCH.** `RESTORED['raw']` is `ESC[?9001l`, which was
    deliberately removed when raw mode became a request over a control channel. Three scenarios
    expected it. Removed, with the reason recorded where the table is.
  - **A TEARDOWN THAT LEFT A KEYSTROKE IN THE LINE EDITOR.** The escalation ladder types `q` to quit
    a full-screen program; at a prompt that `q` stays in the buffer, and the NEXT scenario's first
    command was typed onto the end of it - the guest answered `unknown command: qaudiorec`. The
    ladder now clears the line when it escalated past Ctrl+C.
  - **A DRIVEN x86_64 GUEST WITH A HUNDRED CORES.** `qemu-run.sh` defaults x86_64 to `nproc`, and
    the kernel tracks 64 for shootdowns: the cold guest printed `100 cores are online and this
    tracks 64` and then a RETIRED-page warning per page, into the console a scenario reads its
    answers from. The cold runner now asks for four, like the test profile, on every target.

- **WHAT STILL FAILS, AND WHY IT IS NOT THIS MILESTONE'S TO FIX.**
  - `terminal-lifecycle` and `input-events`, on all three, at the first step that needs a
    full-screen program to answer a key. No such program is given its terminal: `permission.run`
    cannot carry a tty control channel, so `tty_set_mode` answers false and every key is echoed and
    buffered by the line editor. Measured directly - `licoview` rendered, and neither a `q` typed
    over the console nor one injected through the emulated keyboard reached it. That is
    [P02M0147](P02M0147.md). The half of it that IS here: the shell's `CONTROL` role gained
    `handed_on = true`, the same right its `CONSOLE` role needed, without which the shell cannot
    duplicate the channel at all.
  - `registry-provider` on riscv64 ONLY, and the reason is the fixture rather than the guest. The
    scenario proves a provider generation was used by patching the four-character field name `koid`
    and reading it back out of `ps`. On riscv64 that name is not in the file as four contiguous
    bytes anywhere the renderers read: the packed string table is the only copy, and both the text
    and JSON renderings still printed `koid` after a generation that patched it was loaded. THE
    REGISTRY IS BEING CONSULTED THERE - proven by publishing the incompatible fixture, after which
    the `ps` launch is refused exactly as the scenario's second half requires. What is missing is an
    observable the fixture can move on a target whose compiler builds a short string from
    instruction immediates; a longer name, or an observable that is data by construction, is what
    would carry it.

## Definition of done

- `harness/scenarios/make-fixtures.py` builds a fixture set for all three targets, and a recipe that
  patches nothing still fails.
- A cold run that cannot build its fixtures prints the builder's own diagnosis.
- The cold guest and the runner agree on the monitor and QMP socket names on all three targets.
- Every scenario in `harness/scenarios/` runs against a cold aarch64 guest and a cold riscv64 guest,
  and the ones that do not pass are named in the Result with what they need - not left as a number.
- The times are recorded per scenario per target.

## What this milestone refuses, and why

- **A scenario gate in `check.sh`.** These are minutes per scenario on an emulated target, and
  `check.sh` is the set of checks that cost seconds. When a scenario run belongs in a gate it will
  be because something made it cheap, and that is a different milestone with a different argument.
- **Per-target counts in the fixture recipe.** A table of "two here, three there, one on the third"
  is a codegen detail written down as a rule, and it would have to be re-measured on every compiler
  bump for three targets. The invariant that survives a compiler is that every copy is patched.
- **Making the persistent instance multi-architecture.** `dev-up` is x86_64 and exists to be fast by
  staying up. Cold runs are how the other two are driven, and that is the shape being finished here.
- **Rewriting a scenario so it passes on a slow target.** If a step needs longer than its deadline
  on an emulated guest, the runner's time scale is what carries that - the document says what the
  behaviour is, not how fast the machine is.
