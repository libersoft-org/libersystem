# P02M0146 - The scenarios run on one architecture, and the runner says they run on three

Status: OPEN. TEST COVERAGE. NOT A PHASE-2 COMPLETION GATE.

## Goal

Make `scenario-cold` on aarch64 and riscv64 do what it says it does, and run the scenario set there.

`lab.py scenario-cold` takes a target argument, accepts all three, and carries a comment saying the
only thing that ever tied a scenario to x86_64 was that no other target had a guest that would
answer - "now they do, and this is the command that starts one". The guest exists. THE COMMAND DOES
NOT COMPLETE ON EITHER OF THE OTHER TWO, and it fails before it boots anything, so nothing that
would have followed has ever been observed.

This matters beyond tidiness. `boot/scenarios/` is where behaviour that only a booted system can
show is checked - the launcher granting one capability and not another, a recording arriving on a
volume, a terminal that gives itself back - and the two architectures it has never run on are the
two whose PCI backends assign their own BARs and deliver their interrupts differently. P02M0101
closed with exactly that gap named: its capture path was proven on all three by kernel tests, and
joined up end to end on ONE.

## What is there now

Measured on 2026-08-23 by running the command and by counting bytes in the staged images.

- **THE FIXTURE RECIPE REFUSES EVERY NON-x86 TARGET, and it never reaches the guest.**
  `lab.py scenario-cold aarch64 ...` builds the system (nine minutes), then stops with `the aarch64
  scenario fixtures could not be built`. No guest is started. `boot/scenarios/make-fixtures.py`
  patches the byte string `koid` in `lib/protocol/process-proto.lslib` and insists it occurs exactly
  twice. It occurs **twice on x86_64, three times on aarch64 and once on riscv64**:

  | target  | `bin/uname`: `LiberSystem` | `process-proto`: `koid` | `process-proto`: `features=shared-image` |
  | ------- | -------------------------- | ----------------------- | ---------------------------------------- |
  | x86_64  | 1                          | 2                       | 1                                        |
  | aarch64 | 1                          | 3                       | 1                                        |
  | riscv64 | 1                          | 1                       | 1                                        |

  Three of the four substitutions the recipe makes have the same count everywhere, because they are
  data the program carries. The fourth is a compiled literal, and its count is where the compiler
  chose to put it: on x86_64 the packed string table plus one immediate stored by the text renderer;
  on aarch64 the packed table plus `"koid":` and `koid=` as separate literals; on riscv64 the packed
  table alone. The recipe's own comment says the count is stated rather than tolerated so that a
  rebuild which moves the string fails loudly - and the number it states is a fact about one
  compiler backend, so on two targets it fails loudly at something that is not wrong.

- **THE RUNNER THREW AWAY THE REASON.** `cmd_scenario_cold` runs the recipe with
  `stderr=subprocess.PIPE` and never looks at the pipe, then dies with a sentence naming no cause.
  The message above is what a caller sees; `process-proto: b'koid' occurs 3 times, expected 2` is
  what the recipe said, and it had to be re-run by hand to be read. This file says the opposite
  about its other child twenty lines further down: "The runner's own diagnosis goes into the serial
  log's neighbour rather than into /dev/null: it is the process that says `loader EFI not found`,
  and discarding that left every startup failure looking like a guest that never answered."

- **THE COLD GUEST AND THE RUNNER DISAGREE ABOUT WHERE QMP IS, on aarch64 and riscv64.**
  `qemu-run.sh` gives the x86_64 development guest `qemu-monitor-cold-$TARGET_ARCH.sock` and
  `qemu-qmp-cold-$TARGET_ARCH.sock` when `COLD=1`, which is what `cmd_scenario_cold` sets
  `MON_OVERRIDE` and `QMP_OVERRIDE` to. The aarch64 and riscv64 development blocks hard-code
  `qemu-monitor-$TARGET_ARCH.sock` and `qemu-qmp-$TARGET_ARCH.sock` and never consult `COLD`. A
  `key` or `pointer` step on those targets therefore reaches a socket the guest is not listening on:
  `qmp_command` dies with "no QEMU QMP socket", `send_keys` catches that and answers False, and the
  step fails. `input-events.toml` is entirely `key` steps.

- What is NOT known: nothing past the fixtures. No cold aarch64 or riscv64 guest has been driven, so
  whether the chain comes up, whether the agent answers, and what a scenario costs on an emulated
  target are all unmeasured. This milestone's evidence is the run, not the reading.

## Work

- [ ] **M1 - The fixture recipe patches what is there, on the target it is building for.**
  - The count that varies is one substitution out of four, and what the fixture actually needs is
    that EVERY copy of the field name is patched, so no rendering of a process record disagrees with
    another. That is the invariant; "exactly two" was a proxy for it that only holds on one backend.
  - `substitute` gains a mode that requires at least one occurrence, replaces all of them, and
    asserts none survives. The other three call sites keep their exact counts, because their counts
    are properties of the data and not of the code generator - and a change in those IS a fixture
    that has stopped patching what it names.
  - THE LOUDNESS IS NOT LOST. A recipe that patched nothing still fails (zero occurrences), one that
    patched one of two still fails (a leftover survives), and the manifest still records the digest
    of every staged file the recipe read, so a set built from a different image is refused whatever
    the counts were.

- [ ] **M2 - A child that refuses says why.**
  - `cmd_scenario_cold` prints what the fixture builder wrote to stderr before it dies. One line of
    plumbing, and it is the difference between "could not be built" and the sentence that names the
    string, the count and the file.

- [ ] **M3 - One name for the cold guest's control sockets, on every target.**
  - The aarch64 and riscv64 development blocks take the same `COLD=1` suffix the x86_64 block
    already takes, so the guest binds what the runner connects to. Same rule as the control channel
    and the media images, which both got theirs when a cold run destroyed a persistent instance's.

- [ ] **M4 - The set runs on both, and what it costs is written down.**
  - `lab.py scenario-cold aarch64 <every scenario>` and the same for riscv64, in one invocation per
    target because one invocation is one guest: the boot is paid once and each scenario adds only
    its own time.
  - Whatever those runs find is fixed here or refused by name here. That is the point of the
    milestone; the three items above are what has to be true before the runs can start.
  - The per-scenario times go into the Result, per target. An emulated scenario is minutes, and a
    number nobody recorded is the reason "run it on all three" keeps being deferred.

## Dependency order

```text
M1 -> M4
M2        independent; it is why M1 took a build to find
M3 -> M4  (the key and pointer scenarios only)
```

## Definition of done

- `boot/scenarios/make-fixtures.py` builds a fixture set for all three targets, and a recipe that
  patches nothing still fails.
- A cold run that cannot build its fixtures prints the builder's own diagnosis.
- The cold guest and the runner agree on the monitor and QMP socket names on all three targets.
- Every scenario in `boot/scenarios/` runs against a cold aarch64 guest and a cold riscv64 guest,
  and the ones that do not pass are named in the Result with what they need - not left as a number.
- The times are recorded per scenario per target.

## What this milestone refuses, and why

- **A scenario gate in `check.sh`.** These are minutes per scenario on an emulated target, and
  `check.sh` is the set of checks that cost seconds. When a scenario run belongs in a gate it will
  be because something made it cheap, and that is a different milestone with a different argument.
- **Per-target counts in the fixture recipe.** A table of "two here, three there, one on the third"
  is a codegen detail written down as a rule, and it would have to be re-measured on every compiler
  bump for three targets. The invariant that survives a compiler is that every copy is patched.
- **Making the persistent instance multi-architecture.** `dev-up` is x86_64 and exists to be fast by
  staying up. Cold runs are how the other two are driven, and that is the shape being finished here.
- **Rewriting a scenario so it passes on a slow target.** If a step needs longer than its deadline
  on an emulated guest, the runner's time scale is what carries that - the document says what the
  behaviour is, not how fast the machine is.
