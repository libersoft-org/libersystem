# P02M0164 - One NIC, one disk, one screen: a second of anything has nowhere to go

Status: OPEN (2026-09-09). The latest re-audit, 2026-09-08T19:53:43Z, identifies two confirmed
remaining defects: a retired publication's token can alias its replacement's connection accounting,
and the system storage report truncates format classifications after provider 218. M1, M2 and M7
are reopened below. This is the complete current implementation plan; the corrections are planned,
not implemented or verified as fixed by this planning review.

## Goal and scope

A driver publishes typed provider instances with independent consumer connections. Services discover
them through the catalogue, and drivers wait for their declared provider dependencies. Additional
valid bindings and publications grow the catalogue and its block handoff; they do not require new
fixed slots. A second NIC has a second catalogue entry, without adding multi-interface network policy.

P02M0098 owns kernel device claims; P02M0161 owns the existing driver protocol; P02M0162 owns ordered
binding transitions and transactional teardown; P02M0165 owns supervision and stop/quiesce. This
milestone owns provider publication, consumer accounting/discovery, dependency integration and the
storage routing decision lost when the original four block slots were removed. DeviceManager owns
provider identity and authority. StorageService alone parses filesystem contents; ServiceManager
routes its classification result and does not probe filesystems itself.

## Current architecture verified for this plan

- `Catalogue` in `src/user/services/core/src/device_manager.rs` grows as valid bindings publish.
  The registry limits kinds, publications and concurrent consumers per binding. Its `ProviderId`
  contains the exact `BindingId`, catalogue slot and manager-assigned provider generation.
- Offers carry a publisher-local `u16` token. Initial offers reject duplicates and `publish_all`
  rejects live duplicates across kinds in one binding, but `withdraw` forgets a retired token.
  `Disconnect` contains only the binding generation and token, and `disconnected` refunds the
  matching live entry. The provider generation cannot distinguish the two publications on that path.
- The offered endpoint is handed out first; later consumers receive independently minted `CONNECT`
  channels. `take`, `take_from`, `mint_connection` and public `open` account for handed-out consumers;
  mint admission also counts a retained offered endpoint. Failed replies close undelivered handles;
  failed root CONNECT replies retire the allocated catalogue-client slot.
- DeviceManager serves subscriptions from one standing wait set. The opening queues the complete
  kind snapshot and registers its stream before returning it, with snapshot capacity plus 64 live
  event slots. Closed clients/subscribers release their slots. Audio and Display retain provider
  streams; Network and Input use startup subscriptions and preserve their single-device behavior.
  USB StorageService and PermissionManager retain live subscriptions.
- The boot handoff carries all offered block endpoints and independent probes in matching order.
  ServiceManager retains their vectors until the system StorageService classifies every probe.
  Both `BLOCK` and `LIVEVOL` carry explicit probe counts. The system instance reports text followed
  by a NUL and one format byte per probe. ServiceManager currently reads that message into its
  shared 256-byte scratch buffer: a 37-byte system report leaves room for only 218 classifications.
  The kernel's single-capability receive truncates rather than refusing an oversized payload.
- Dependency-pending boot nodes remain in the node set. Every new attempt, including both boot
  retry paths, rechecks `requires`; arrival resumes binding and dependency loss uses the existing
  ordered stop path. The existing gates pass narrower cases but do not cover the two new failures.

## Work

- [ ] **M1 - metadata, manager identity and a per-consumer connection factory.** Preserve all
  existing provider kinds and their checked IDL/protocol agreement: `block`, `net`, `display`,
  `audio`, `input`, `usb-bus`, `pointer` and `console-bytes`. Only DeviceManager assigns global identities;
  a driver names only its own publications. Removing or replacing one provider leaves siblings
  and other bindings' publications usable. Complete the following token-lifetime correction.

  **Accepted finding 1: tokens are unique for the complete exact binding generation.** An accepted
  token cannot be published again by that same `BindingId`, including after withdrawal. Replacement
  within a live binding uses a fresh token and receives a fresh manager `ProviderId`. Another binding
  or a later binding generation may use the same numeric token. This specifies the lifetime of M1's
  existing within-driver uniqueness requirement; it replaces the previous plan and regression's
  permission to reuse a token immediately after withdrawal. The driver wire layout is unchanged.

  1. Add a used-token set owned by the binding lifetime (it may reside in Catalogue keyed by exact
     `BindingId`). `Catalogue::publish_all` checks it for both initial and later offers, across all
     kinds. Retain `Offers::push` duplicate validation for the initial unpublished batch.
  2. Reserve both the publication slot and token-history storage fallibly before committing a
     publication or announcing it. Record only accepted publications. Refuse and close an offer if
     its token was already used, its declaration is invalid, or required storage cannot be reserved;
     never publish an entry whose token history could not be retained. Live publication counts
     continue to use live entries, so retired tokens do not consume the declared `most` allowance.
  3. Keep history after `withdraw`, after all current publications disappear, and while teardown
     can still dispatch frames/events from that generation. Release it only when that binding is
     finally retired and its old-generation channel/events can no longer publish. Do not clear it
     merely because `withdraw_binding` removed live entries. Memory grows only with accepted tokens,
     naturally bounded by the 65,536-value token namespace per exact binding; exhausted tokens or
     memory cause refusal, never token wrap/reuse. No global counter or connection-ID protocol is
     needed.
  4. Preserve token-specific accounting for live providers. A departure for a retired token finds
     no live publication and cannot decrement a fresh-token replacement; binding-generation checks
     also prevent old-binding events from reaching a new binding. Counts still release on ordinary
     disconnect and on the existing failed-delivery cleanup path. Preserve retained-offer accounting
     and all declared consumer limits; avoid touching sibling counters or outstanding handles.
  5. Update token-lifetime comments in `device_manager.rs`, driver protocol documentation in
     `src/user/libs/driver/protocol/src/lib.rs`, and the publisher helpers in
     `src/user/drivers/core/src/common.rs` when implementing. Current production drivers do not call
     the withdrawal helper to republish the same token; no consumer policy migration is required.
     Update the explicitly contradictory after-withdrawal reuse test in
     `src/tools/check-provider-catalogue.py` and add the M7 regressions before closing M1.

- [ ] **M2 - preserve complete block classification through role selection.** The routing inputs
  remain format, manager-owned origin and the loader's `RootSelection`:

  | Input | Decision |
  | --- | --- |
  | Format | StorageService classifies LiberFS, FAT, ISO9660 and UDF through their checked parsers. Unknown is an explicit classification, never a bus-position fallback. |
  | Origin | The exact binding shared by Block and UsbBus distinguishes USB FAT from non-USB FAT media. The driver cannot choose a trusted volume role. |
  | `RootSelection` | `Block(uuid)` selects exactly one matching distinct LiberFS provider; missing and duplicate UUIDs are typed refusals. `Embedded(module)` names the loader-selected verified `system-volume.img`, not `volume.pkg`. `None` promotes nothing. |

  Preserve the loader's actual choice: the verified paired block volume wins when used; otherwise
  the selected embedded module is recorded with its actual index and zero UUID. Do not re-derive that
  decision downstream or change the current BootInfo version/wire layout. Keep root selection inside
  the existing backing message so legacy direct service fixtures do not owe a new positional role.

  The system storage instance owns an independent probe for its selected root and preserves that
  connection. Every distinct candidate, including index zero and providers beyond four, stays
  available until classification. Media instances depend on `storage_service` in the manifest;
  alphabetic manifest order is insufficient. The role selector takes the first matching format in
  the shared ordered list and closes only unknown, unused or duplicate role candidates after a
  complete valid table. USB follows the matching-binding subscription path.

  **Accepted finding 2: size and validate the existing report using the announced probe count.**
  Keep the single text + NUL + format-table report, the ordinary service report ordering and the
  existing IPC receive contract. A larger fixed provider limit or a new report-stream protocol
  would not be justified by this defect.

  1. In `src/user/services/core/src/service_manager/bootstrap.rs::start_service`, capture the system
     instance's expected probe count before `core::mem::take(probe_blocks)` transfers its vector.
     Retain that count outside the role-delivery block through the shared report receive for both
     `BLOCK` and `LIVEVOL`; do not recalculate it from an emptied vector or from a fixed registry
     program count. Preserve one table position per announced probe, including unknown/zero handles.
  2. Allocate a local system-report receive buffer fallibly from the existing 256-byte text reserve
     plus the expected count, with checked arithmetic and the existing `abi::MAX_MESSAGE_BYTES`
     ceiling. Use it for the receive, failure decoding, text extraction and table parsing. Leave
     ordinary service report reads on the existing scratch buffer. The admitted 128 nodes and
     eight-endpoint declaration bound fit well within the 1 MiB message ceiling; no chunking or
     kernel ABI change is required.
  3. Before publishing the service as online, updating `block_formats`, or closing role candidates,
     require exactly the expected number of format bytes and the known format vocabulary (0 through
     4). For a nonzero expected count, missing NUL, missing/short/extra table or invalid codes fail
     bootstrap with a specific classification-report reason. Zero expected probes keep the current
     text-only report valid. Build the validated table before committing it; do not interpret an
     absent tail as genuine unknown-media answers or retain an earlier attempt's table on failure.
  4. Make StorageService's corresponding table/report allocations complete or fail explicitly using
     the existing `rt::fail_bootstrap` path. Its current conditional `try_reserve` must not silently
     turn classification/report allocation failure into a successful text-only report when probes
     were announced. Preserve `BLOCK` and `LIVEVOL` count compatibility and the zero-probe direct
     bootstrap fixtures. On count, allocation, receive or parse failure, use the existing failed
     bootstrap/process cleanup path and close retained role/probe capabilities exactly once; the
     dependent media instances must not start from partial data.
  5. Relay only the text prefix to SystemManager as today, keep the bootstrap/control endpoint
     ownership and message ordering, and run M7's actual transport/cleanup/selector regressions.
     This correction includes only the system report and classification seam, not a generic
     variable-size bootstrap framework or additional mount policy.

- [x] **M3 - subscription returns its snapshot and live stream as one operation.** Preserve the
  existing ordering and sufficient snapshot capacity, add/withdrawal delivery, late-subscriber
  discovery, closed-client/subscriber reaping and independent `open` connections. Audio watches its
  driver even while idle, so an old closed connection cannot cause it to discard a replacement
  publication. All service waits use the existing built wait set, including development control.
  Network/Input startup discovery remains sufficient for their existing single-device behavior.
  USB StorageService watches Block/UsbBus from the same binding, closes the old channel and clears
  its mount on replacement; PermissionManager watches UsbBus and opens one connection per grant.

- [x] **M4 - driver readiness and provider readiness are separate.** `READY` commits the binding's
  initial unpublished offers. A live driver may publish providers later, including after initially
  publishing none. A child's failed probe or withdrawal leaves a healthy controller and siblings
  running. A provider withdrawal is not a driver `FAILED` event or a new binding transition.

- [x] **M5 - withdraw honestly and preserve teardown ownership.** Individual token withdrawal
  removes and announces only that live publication; ending a binding removes all of its live
  publications. Consumers receive the disappearance, and forced removal never implies accepted
  work was confirmed complete. P02M0165's single stop/quiesce protocol owns draining. The M1 repair
  retains identity history after visibility ends without delaying withdrawal or adding allocation
  to the withdrawal path.

- [x] **M6 - declared dependencies and per-binding bounds.** Registry validation rejects unknown
  provider kinds, zero publication bounds, impossible endpoint totals, orphan requirements,
  self-dependencies and structural cycles. Current driver serving capacity is eight endpoints per
  binding, so the sum of `most * consumers` must fit it. This is a driver resource bound, not a
  global count of published devices. Live admission still enforces each kind's declared limits;
  M1 supplies the outstanding token-accounting repair. Preserve these P02M0162 transitions:

  | From | To | Trigger |
  | --- | --- | --- |
  | Unbound | DependencyPending | A declared requirement is absent. |
  | DependencyPending | Binding | Every declared requirement is published. |
  | Binding | DependencyPending | Requirement lost before a claim exists. |
  | Backoff | DependencyPending | A due retry rechecks requirements and finds one absent. |
  | Binding or Online | Stopping | Requirement lost after claim, with dependency-lost intent. |
  | Stopping | DependencyPending | Dependency-loss teardown confirmed. |

  Keep pending boot nodes, recheck requirements before every attempt and either boot retry path,
  and settle dependencies after publication/withdrawal. Absence is a waiting state, not a failure
  or a spent attempt. There is no `DependencyPending -> Unbound` shortcut and no acyclic-boot
  dependency ban.

   actual outcomes and limitations. Do not waive or regenerate unrelated dynamic-report/performance
   baselines. Mark M1/M2/M7 and the milestone index complete only after both fixes and their required
   evidence pass. This planning pass edits documentation only.

The definition of done includes all existing M1–M7 behavior and the following explicit closure
conditions: no fixed provider slots or program-sum publication ceiling; no retired-token departure
can refund a replacement; the entire announced classification table survives transport on block and
embedded boots; role identity uses format/origin/loader choice, never arrival order; independent
providers and late/live subscriptions work without disturbing siblings; dependency waiting and
recovery use the single existing state machine; forced withdrawal is reported honestly. Available
memory, token/identity representation and declared resource limits remain real refusal boundaries.

## Exclusions

No general publish/subscribe broker, new connection-generation protocol, multipath/failover policy,
multi-interface network support or generic bootstrap transport framework. Consumer changes stay at
the discovery seam except for M2's existing StorageService format-probe responsibility. No filesystem
parsing moves into DeviceManager or ServiceManager. These two findings require no kernel/loader ABI
change, new stop protocol, additional boot roles or arbitrary provider-count cap.
