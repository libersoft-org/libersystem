## Goal

Let a driver publish typed provider instances that services subscribe to, so a machine with two
disks, two NICs or two sound devices has somewhere to put the second of each - and let a registry
entry wait for something it needs instead of failing because it was tried too early. What a service
then DOES with a second one is that service's own work: this milestone gives the catalogue a second
entry, not NetworkService a second interface.

## What is there now

- **PROVIDERS ARE FOUR NAMED LOCALS, FILLED IN ARRIVAL ORDER.** `block_client`, `block2_client`,
  `block3_client` and `block4_client` are four variables in DeviceManager, each routed by hand to the
  service that owns that kind. So a second disk DOES have somewhere to go and a fifth does not, and
  which volume is which depends on which driver finished first. The defect is a fixed count with
  hand-written routing, not the absence of a second slot - and a gate satisfied by "two disks work"
  would have passed before this milestone existed.
- **A DRIVER IS ONLINE OR IT IS NOT.** There is no state between "the process started" and "the
  device is usable", so a controller with a slow child is either reported up before it is or not
  reported at all.
- **NOTHING WAITS FOR ANYTHING.** A driver that needs another provider present is launched anyway and
  fails.

  The loader has already made it, and its order is deliberate: `bootstrap_from_image` *"does nothing

  remove. And `Embedded` names `system-volume.img`, never `volume.pkg`, which is the factory archive

  P02M0150 already put the paired volume's uuid in the boot medium's signed manifest and the loader

  AND THE GATE THAT PROVES IT IS PART OF THE ITEM. The definition of done asks for a boot carrying

  second QEMU disk order in the arch-profile gate, and it is what the routing is written against.

  BUILT 2026-08-27, and the ORIGIN turned out to be simpler than this item assumed: for four
  identical virtio-blk disks it is the BDF. They run the same driver, their formats do not differ,
  and a FAT BPB cannot tell a removable medium from a USB stick - what differs is where each one is
  plugged in, and the boot scan enumerates the bus ONCE in bus order. So `Catalogue::take` picks the

  `RootSelection` is in `BootInfo` and `bootproto::VERSION` is 2. That bump is not a product version:

  a mismatched pair is reachable and is the one failure that happens before anything can report it.

  The loader records its choice AT THE BRANCH THAT USES IT, which is what stops it being re-derived:

  volume, because matching a uuid means reading a LiberFS superblock and that belongs nowhere near

  `net_client`, `gpu_client`, `input_client` and `usb_pointer` are gone from DeviceManager, and each

  because the supervisor's driver-status view is the only thing that ever used those handles. The

  AND THE USB PAIR IS OUT OF DEVICEMANAGER TOO (2026-09-03). `usb_client` and `usbq_client` were two
  singleton locals filled by a hand-written route the first time an xHCI binding reported, with
  `take_from` MOVING the offered channel out of the catalogue and `if *slot == 0` closing every later
  one - so a second controller, and the replacement providers of a controller that rebound, had
  nowhere to go and were not reachable through the catalogue either: the entry was still there and
  its handle was gone. One slot per kind is the fixed-slot defect with the number left off.

  Both publications stay in the catalogue now with their offered channels intact, and the phase-two
  hand-off MINTS a connection for the consumer at the moment it sends - the same thing the block
  probes do. Which providers are the USB controller's is asked of the catalogue rather than written
  into a branch: a `block` provider published by a binding that also publishes `usb-bus` is a USB
  volume, which is M2's origin rule stated as a query. The count travels beside the connection, so a
  machine with a second controller says so; `check-no-fixed-provider-slots` refuses a per-kind local
  coming back and requires that origin query to still be asked.

  WHAT IS LEFT IS THE CONSUMER SIDE OF THAT PAIR, and it is left deliberately. Neither consumer reads
  a `CATALOGUE` role today: the USB volume is mounted by a StorageService instance that is handed its
  block channel, and the bus-query channel reaches a TOOL through PermissionManager's grant table. For
  the first, subscribing means a catalogue role on that instance plus the controller's address to
  select on - `provider-info` already carries `bus`, `dev` and `func`, which is what makes the
  selection possible at all. For the second it means PermissionManager holding a subscription and
  opening a provider per grant, which is a change inside the grant path. Each is one more change, and
  neither is a count.

  AND WHAT MAKES IT ONE ITEM WITH ITS OWN ORACLE (added 2026-09-03). Publishing the other entries and
  reporting a count does not make them REACHABLE to these two, and neither of them discovers a
  replacement after a withdrawal - which is the property the whole catalogue exists for. The
  providers are there to subscribe to: the ordinary x86_64 boot publishes five block providers and
  one `usb-bus`, the fifth block being the USB stick the xHCI driver binds in phase two. What is
  missing is an ORACLE ON THE SEAM, and the distinction matters because the volume itself is covered
  and the ROUTE to it is not (stated precisely 2026-09-03; the first version of this paragraph said
  "nothing in any suite asserts that `vol://usb` mounted", which is not true).

  What is asserted today: `kernel.hardware` reads `vol://usb/hello.txt` off the seeded stick and
  compares the bytes - but it spawns its own StorageService instance and hands it the block channel
  DIRECTLY, so it proves the volume and skips every hop this item is about. And `kernel.boot` asserts
  `StorageService: online (vol://usb)` is in the boot's report set - which the instance prints having
  touched no media at all, because the mount is lazy and it is handed a deliberately dead stand-in
  channel on a machine with no xHCI driver. Neither can fail if the routing hands the USB instance
  the wrong provider or none.

  BUILT 2026-09-04, AND IT IS THE HALF THIS ITEM WAS BLOCKED ON. A routed provider and the stand-in
  were indistinguishable: when no controller published one the supervisor hands over a channel whose
  far end it has already closed - so the instance answers "not there" rather than waiting - and BOTH
  produced the identical `StorageService: online (vol://usb)`. The boot's assertion on that line
  therefore proved the instance had started and nothing about the route, and a boot that lost the
  stick entirely passed it. The supervisor now tags a routed provider `USBBLOCK*`, the instance
  repeats that in its report as ` routed`, and `kernel.boot` asserts the routed form. The suffix has
  exactly one producer, gated on a non-zero handle. Measured: `--tags boot` passes on the machine
  that has the stick.

  The boot assertion is per target for now - the routed form where the route works, the bare form

  rather than a target excused. Closing it means the supervisor's block-role table growing past
  four, which is the same fixed-count seam M1 removed for the catalogue and did not remove here.

  WHAT IS LEFT IS THE SUBSCRIPTION ITSELF, and it is now unblocked rather than un-started. The USB
  instance needs a `CATALOGUE` role and a `Block` subscription filtered by the controller's address -
  `provider-info` carries `bus`, `dev` and `func`, which is what makes that selection expressible -
  and the swap belongs in `serve_volume`'s waitset, which already registers one handle per member, so
  a subscription is one more registration and one more branch. `FatBacking` remounts lazily on I/O
  failure, so adopting a replacement is closing the old channel and clearing the mount rather than
  rebuilding the volume. PermissionManager's half is a subscription held across its grant table.
  Neither is started; both now have an oracle in front of them, which is the condition this item set.

  The shipping configuration booted; `./dev.sh up` stalled, deterministically, at one core and four
  alike, and every service behind the first one to ask the catalogue for a connection never started.

  The cause was in DeviceManager and was development-only. Its standing loop began with a SECOND,
  narrower wait - `wait_any(&[bootstrap, dev.bootstrap], 0)` - that every pass parked in before it
  reached the one wait this file's own comment describes. That set has no catalogue root in it, so
  from the moment the development agent existed the manager answered the supervisor and the agent and
  NOTHING ELSE. AudioService's `CATALOGUE` role is minted by the supervisor BEFORE the service reports
  online, so the supervisor blocked in `service_connect` waiting for a reply that could only be sent
  after a message the supervisor was itself blocked from sending. Traced rather than guessed: the
  standing loop ran exactly twice and stopped, with the catalogue root live and in its wait set.

  The fix is the rule this file already states. The agent's bootstrap is a handle like any other and
  goes into the one built set, dispatched by its index; `WAITING_MAX` gained the slot it needs. The
  development instance now reaches an attached shell, with DisplayService, PermissionManager and
  ConsoleService online and a frame on the display - which is this seam working in that configuration
  too.

  WHY NOTHING CAUGHT IT: no gate boots the development configuration - `development-build` proves it
  compiles and `development-gate` inspects the built volume. A booting gate would have to build that
  configuration, which is the one thing `development-gate` exists to refuse in the tree, so what
  guards it now is `one-wait`: a source gate that refuses the SHAPE the defect had - a wait written at
  the call site rather than built - and that was watched to fail against the defect reintroduced.

  The display one was taken next because it was the one another milestone was BLOCKED on: P02M0159's
  M4 asks a rebound GPU to restore a picture, and a slot filled once at bring-up is the reason it
  could not. The four remaining are the same shape - a `CATALOGUE` factory role, a subscription at
  the service's seam, the manager's slot and its routing deleted - and each is its own change because
  each is boot-critical in its own way. What is left is written here rather than in an audit, so the
  next pass starts from the list and not from a search.

- [x] **M4 - driver readiness and provider readiness are separate.** `READY` means the process is
  initialised and supervised. A provider appears when its own probe is complete. One child failing
  does not take a healthy controller or its siblings down.

  BUILT 2026-08-27. An offer BEFORE `READY` is held unpublished, which is right for a handshake -
  a driver that dies half way through announcing itself must announce nothing. An offer AFTER it is
  published at once, because there is no handshake left to be half way through: a controller reports
  in and then enumerates its bus, and its children's providers carry the same generation because it
  is the same binding.

  AND A CHILD FAILING IS SAID WITH `WITHDRAW`, NOT WITH `FAILED`. A `FAILED` frame is about the
  driver; withdrawing a provider is about one publication. The two are different facts and the
  protocol already has a word for each, so nothing new was needed - what was needed was for the
  state machine not to treat the second as the first. A withdrawal is not a transition at all, which
  is why it is not in the table.

- [x] **M5 - a withdrawal is honest about what it did not finish.** **MET AGAIN (2026-08-29)** - a withdrawal travels on the stream as a `provider-info` whose `live` is false. A provider is withdrawn from the
  catalogue and its consumers told; on a forced close the report says in-flight work was not
  confirmed rather than implying it completed. Draining gracefully - asking the driver to finish
  first - is P02M0165's, where the one stop-and-quiesce contract lives.

  BUILT 2026-08-27. Two withdrawals, because there are two ways a provider goes away and they are
  not the same fact. A LIVE driver retires one of its own publications with `Opcode::Withdraw`,
  naming the token it chose - the binding stays `Online` and its siblings stay published, so a
  controller whose child leaves is not a controller that failed. A binding that ENDS takes
  everything it published with it, and that report says the in-flight work is NOT confirmed rather
  than reporting silently, because a forced teardown cannot know whether it completed and a reader
  would otherwise assume it did.

  A provider outliving its binding is a channel whose server is gone: a consumer holding it waits on
  a driver that no longer exists, which is a failure nobody can attribute.

- [x] **M6 - `requires` and `provides` in the registry, and `provides` is a bound.** Corrected 2026-09-08: each binding is limited to its declared provider kinds and counts, and factory opens enforce its declared concurrent-consumer limit. Catalogue capacity grows with valid binding instances. A node leaves `DependencyPending` when what it requires arrives. An entry declares
  what it needs - a bus, a provider kind - and is retried when that arrives; and it declares which
  kinds it may publish AND how many, so a driver cannot publish a kind it never declared. A
  structural cycle or a manifest naming a kind no entry can produce is refused at registry-build
  time. Hardware that is simply absent at run time leaves the node in `DependencyPending`, which is a
  STATE and not a failure cause - a machine without a NIC is a machine, not a broken image. This
  milestone is where that state first has something to wait for, so it is the one that adds it to
  P02M0162's `BindingState`, in that file and not in a second enum - and it adds its rows to that
  milestone's transition table too, because a state with no way in and no way out is one every reader
  has to guess at:

  | from | to | on |
  | --- | --- | --- |
  | `Unbound` | `DependencyPending` | a declared requirement is not published yet |
  | `DependencyPending` | `Binding` | EVERY declared requirement is published - not the first one, which would start a bind that fails on the second |
  | `Binding` | `DependencyPending` | withdrawn before the claim was taken - there is nothing to tear down |
  | `Backoff` | `DependencyPending` | at the delay's expiry, a declared requirement is not published |

  RE-AUDIT CORRECTION (2026-09-08), finding 2. Boot discovery retains `DependencyPending` nodes as
  well as successfully started nodes. Each provider-pump pass can restart a waiting boot node when
  its declared requirements become present. Acyclic boot dependencies are valid registry inputs;
  validation rejects actual cycles, not every boot-stage dependency. Dependency arrival follows
  the legal `DependencyPending -> Binding` path, and loss while Binding or Online uses the existing
  dependency-stop protocol.

  THE EXPIRY RE-READS `requires`; IT DOES NOT WAIT TO BE TOLD. Reacting to a withdrawal EVENT while
  the node sits in `Backoff` is not enough, because a node can arrive in `Backoff` from `Stopping`
  after a crash - and if the requirement went away DURING that teardown, the event is spent and the
  expiry would proceed into a bind gated on a condition that no longer holds. So every backoff
  expiry asks the same question: all published, `Binding`; otherwise `DependencyPending`. One rule
  instead of an edge per way of getting there, and one test that walks crash -> `Stopping` ->
  withdrawal -> `Backoff` -> expiry.

  Rechecked 2026-09-08: both boot retry paths now call `gate_on_requirements` before reading the
  artifact or entering `begin_bind`. A requirement lost during teardown parks the due retry in
  `DependencyPending` without a claim, spawn or spent attempt. The `driver-event-dispatch` host
  gate executes both actual retry-loop branches for expired backoff, restart requests and immediate
  `Step::Again`, and separately removes each gate to verify the regression is detected.

  BUILT 2026-08-27. `requires` and `provides` are on `[programs.driver]`, both over a closed set of
  kind names, so a kind this system does not have fails to PARSE. `system-manifest` refuses four
  things at registry-build time, each watched to fail: a requirement no entry produces, a driver
  requiring what it publishes, `most = 0`, and a structural cycle across entries walked by
  reachability. At run time `publish_all` refuses a kind the entry never declared and one past its
  bound, with the handle CLOSED rather than kept - which is the half no build-time check can do.
  `gate_on_requirements` is asked at every attempt including a backoff expiry, so a requirement that
  went away during a teardown is noticed even though the event that said so is spent.

  Eight drivers now declare what they publish, and the boot proves the bound is not a formality:
  `providers published - 4 block` in phase one, from four independent bindings each declaring
  `most = 1`.
  | `Binding` | `Stopping` | withdrawn after the claim was taken, with `intent = dependency lost` |
  | `Online` | `Stopping` | the same, for a binding that had reached `Online` |
  | `Stopping` | `DependencyPending` | that teardown confirmed |

  There is no `DependencyPending -> Unbound`: this item first had one for "the requirement is
  withdrawn", which is backwards - a node waiting for a provider that goes away is waiting harder,
  not waiting less, and `Unbound` invites an immediate bind that would fail for the reason it is
  already recording.

- [x] **M7 - the tests are about there being no hardcoded count and no hand-written routing.** Not
  "unbounded": the registry bounds what each entry may publish, on purpose, and the defect is a limit
  compiled into DeviceManager rather than the existence of a limit. The four hardcoded block locals
  are absent from the source; a provider is added and removed at run time; a subscriber that starts

  catalogue.

  BUILT 2026-08-27. The four named locals are GONE from the source and a gate keeps them out:
  `check-no-fixed-provider-slots` refuses a numbered per-provider local coming back, which is the

  What is left is `BOOT_BLOCK_TAGS` - four tags the boot hand-off carries, feeding the system, media,

  The runtime properties are tested where they can be DRIVEN: `driver-binding`, on the identity

## Definition of done

- No fixed provider slot remains in DeviceManager. Publication and concurrent-consumer limits are
  checked per binding against its registry entry; the catalogue grows as additional valid instances
  publish. Available memory and the wire identity's representation remain resource limits.
  The hand-off count was implemented on 2026-09-02, replacing `BOOT_BLOCK_TAGS` and the four-entry
  arrays. The 2026-09-08 correction also removes the global program-sum bound, which could not count
  repeated instances of one driver. The report transfers the first offered provider; `BLOCKS`
  carries the total count, followed by the remaining offered channels and one independent probe per
  provider. ServiceManager retains all of them until classification. `check-no-fixed-provider-slots`
  rejects the former global bound and fixed tags and requires growing entries and an explicit count.
- Which volume is which is decided by three inputs and never by arrival order, proved by a boot where
  the drivers finish in a different order:

  | | |
  | --- | --- |
  | format | LiberFS / FAT / ISO9660 / UDF - narrows, and for the two FAT volumes decides nothing |
  | origin | which controller published it, from `BindingId` and the registry entry - this is what separates FAT media from FAT USB |
  | `RootSelection` | the loader's verified identity, and the only thing that names the SYSTEM volume |

- The gate covers all three `RootSelection` outcomes - `Block`, `Embedded` and `None` - and `None`
  promotes nothing rather than the first disk that answered. It also boots a machine carrying BOTH a
  FAT medium and a FAT USB stick, in either order, and requires each to arrive at its own mount.
- Two devices of one kind produce two independent providers, and removing one leaves the other
  working, under test.
- A subscriber that arrives after a provider was published still sees it, and one that arrives
  between a snapshot and a subscribe misses nothing.
- A service subscribing after boot sees the providers that already exist.
- A driver can be online with no providers and add one later.
- A registry entry waits for what it declared and binds when it arrives; a cycle is refused at
  registry-build time.
- A forced removal is reported as forced and never claims the in-flight work completed.

## What this milestone refuses, and why

- **A general publish/subscribe bus.** Providers are typed, few, and owned by a binding. A message
  broker would be a larger thing than the problem.
- **Reworking the services that consume them.** Each service changes at one seam - where it used to
  receive a handle, it subscribes. What a service does with a disk is not this milestone's, with ONE
  named exception: StorageService gains the format probe in M2, because deleting the four block slots
  deletes the routing that decided which volume was which, and nothing else in the system knows how
  to tell a LiberFS volume from a FAT one. That is the exception, and it is not a licence for a
  second.
- **Multi-path or failover policy.** Two providers of a kind is what this makes possible; deciding
  which one something should use is a policy question and belongs to whoever has the use case.

## What the 2026-08-28 audit found

Five findings, ALL ACCEPTED AND ALL OPEN, and they are ONE absence seen from
five sides: the catalogue is not a subscription mechanism.

1. There is no per-consumer connection factory. A `Provider` holds the one channel the driver
   transferred and `Catalogue::take` moves it to the first internal consumer and zeroes the handle.
   Existing services still receive channels through DeviceManager's internal hand-offs.
2. `provider-catalogue.subscribe` is not served: the generated dispatcher returns `None` for
   `OP_SUBSCRIBE` and nothing calls `subscribe_open`/`subscribe_frame`. There is no stream producer
   and no subscriber cursor, so even the snapshot cannot be requested through the server.
3. Nothing releases a node from `DependencyPending` when a provider arrives, and nothing tears one
   down when a provider leaves. The shipping manifest declares no `requires` row, so the ordinary
   boot cannot exercise it.
4. Block roles are assigned by ascending BDF into fixed system/FAT/ISO/UDF slots rather than by
   format and loader selection, and `RootSelection::None` still mounts and serves the first `BLOCK`.
   `bootstrap_from_image` also records `ROOT_EMBEDDED` with `module: 0` and a non-zero UUID where
   `RootSelection` defines the index of `system-volume.img` with a zero UUID.
5. `MAX_PROVIDERS = 32` is compiled into DeviceManager and the manifest validator does not constrain
   the declared `provides` against it. The `no-fixed-provider-slots` gate REQUIRES the symbol, so it
   can never catch this.

Adding any one of these alone produces a system that is differently wrong - in particular, building a
private probe-and-select path for 4 beside the mechanism meant to replace it is how the internal
hand-offs got here.

## What the 2026-08-30 audit found

One finding, accepted and NOT fixed. This is an open item, not a rejection.

**The catalogue is still not the discovery path any production consumer uses.** No consumer
subscribes; the two services holding a catalogue connection ask only for the binding snapshot, and
the per-kind injection is intact. That is this milestone's own requirement - each service changes at
one seam, where it used to receive a handle it subscribes - and it is unmet.

The smallest complete instance is the sound service, whose handle has one consumer and one oracle. It
was started and stopped when the shape became clear, because a half-done seam is worse than an
untouched one: a service that both receives a fixed handle and subscribes is exactly the state the
finding rejects. What it takes, end to end:

- the offer routing must stop taking the audio provider into a slot of its own, so it stays in the
  catalogue - and with it the first offer's consumer count, which otherwise makes the subscriber's
  connect the SECOND ask against a kind that admits one;
- the slot must leave DeviceManager's bootstrap to ServiceManager, which is read POSITIONALLY at
  every hop, so both sides move together;
- the bootstrap role and the manifest role go with them;
- the service subscribes, holds the stream in its wait set, and connects to a provider that arrives -
  which is also the late-subscriber and the arrives-later case, since a subscription answers with
  what is published now and continues as the stream;
- and ServiceManager's driver status view, which answers "is the sound driver online" from that
  handle, needs another source. The comment beside it already says this is the provider-routing item
  and not its own.

That is a boot-path change across four files plus a status surface, and it was not made in the same
pass as ten other milestones' fixes and immediately before their verification run: a failure there
could not have been attributed, and the failure mode of getting this wrong is a machine that does not
boot. Nothing half-finished was left in the tree.
