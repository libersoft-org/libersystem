# P02M0164 - One NIC, one disk, one screen: a second of anything has nowhere to go

Status: PLANNED AFTER P02M0163. PROVIDERS AND DEPENDENCIES. FIFTH OF SEVEN - see P02M0098.

## Goal

Let a driver publish typed provider instances that services subscribe to, so a machine with two
disks, two NICs or two sound devices has somewhere to put the second of each - and let a registry
entry wait for something it needs instead of failing because it was tried too early. What a service
then DOES with a second one is that service's own work: this milestone gives the catalogue a second
entry, not NetworkService a second interface.

## What is there now

- **PROVIDERS ARE FOUR NAMED LOCALS, FILLED IN ARRIVAL ORDER.** `block_client`, `block2_client`,
  `block3_client` and `block4_client` are four variables in DeviceManager, each routed by hand to the
  service that owns that kind. So a second disk DOES have somewhere to go and a fifth does not, and
  which volume is which depends on which driver finished first. The defect is a fixed count with
  hand-written routing, not the absence of a second slot - and a gate satisfied by "two disks work"
  would have passed before this milestone existed.
- **A DRIVER IS ONLINE OR IT IS NOT.** There is no state between "the process started" and "the
  device is usable", so a controller with a slow child is either reported up before it is or not
  reported at all.
- **NOTHING WAITS FOR ANYTHING.** A driver that needs another provider present is launched anyway and
  fails.

## Work

- [ ] **M1 - a provider is metadata plus a connection factory, and the manager mints its id.**
  `block`, `frame`, `display`, `input`, `serial`, `pcm`, `usb-bus` - the last because the xHCI driver
  already hands up a `USBBUS` channel for the `lsusb` inventory and DeviceManager routes it by hand
  today, so leaving it out would keep one hand-written route alive in the milestone that exists to
  delete them. Each with a kind and a
  `ProviderId (BindingId, local_slot, provider_generation)` the MANAGER assigns. Handing one channel
  to two subscribers is not two connections - it is two consumers competing over one reply queue - so
  a connection is minted per consumer, and a kind that admits only one consumer says so in its
  declaration rather than discovering it at the second subscriber. A driver may not choose a global
  identity, or a compromised one advertises itself as the system disk.

  BUT IT HAS TO BE ABLE TO NAME ITS OWN. A driver publishing two providers of one kind must later be
  able to say WHICH of them is going away, and it cannot name a `ProviderId` it never sees. So the
  driver labels each offer with a publisher-local token of its own choosing - unique only within that
  driver - and the manager keeps the mapping from `(BindingId, token)` to the `ProviderId` it minted.
  A withdrawal names the token. The manager still owns the global identity, and the driver still
  cannot forge or guess another binding's, which is the property this item is for; what it gains is a
  handle on its own publications.

- [ ] **M2 - the four block slots carry a ROLE, and something has to carry it after they go.**
  `block_client`, `block2_client`, `block3_client` and `block4_client` are not only a fixed count -
  they are how the system currently decides which disk is the writable system volume and which are
  the read-only FAT, ISO9660 and UDF media, by the order the drivers finished. Delete them and that
  decision has no home, so a boot with two disks mounts whichever answered first as the root. The
  **AND THE CONTENT CANNOT ANSWER IT.** This item first said StorageService would identify each
  provider by what is ON it, and that is wrong for the two volumes it matters most for: `FATBLOCK`
  and `USBBLOCK` both become a `FatBacking`, differing only in the name the manager gives them -
  `vol://media` and `vol://usb`. A FAT BPB cannot tell them apart, so a probe by format would collapse
  two roles into one and pick by arrival order again, which is the defect this item exists to remove.

  So the ORIGIN comes from the manager, not from the medium: the binding's `BindingId` and the
  registry entry that matched it say which controller published this provider, and the manager
  attaches that as provider metadata. A driver may not choose its own role, for exactly the reason M1
  already gives for provider ids - a compromised one would advertise itself as the system disk.

  Content still does the work it can do, and it is more than the last sentence gave it: the probe
  reads each provider and says which of LiberFS, FAT, ISO9660 and UDF is on it, which settles the ISO
  and the UDF media outright because only one provider carries each. What it cannot settle is the two
  FAT volumes, and that is where origin decides. Format narrows; origin separates what format left
  tied. And a
  format is not enough for the SYSTEM volume either, because two LiberFS volumes are told apart by
  uuid and by nothing else, so that identity comes from the loader:

  `BootInfo` gains one small field, a `RootSelection` with three cases and no more - `Block(uuid)`,
  `Embedded(module)`, `None`.

  **AND IT RECORDS WHAT THE LOADER CHOSE, RATHER THAN DESCRIBING HOW TO CHOOSE.** The first draft of
  this item gave the three cases as rules to evaluate later, and two of them can be true of one
  medium: a shipping ISO carries `system-volume.img` as a file AND a signed pairing, because
  `mkimage.sh` stages the pairing for exactly the medium that carries the volume. A reader deciding
  between them afterwards is re-deriving a decision that was already made, and can decide differently.

  The loader has already made it, and its order is deliberate: `bootstrap_from_image` *"does nothing
  when a disk already answered - an installed system's own volume wins over an image that happens to
  be lying on the boot medium beside it"*. So the field is set where that choice happens - a paired
  block volume was found and used, `Block(uuid)`; otherwise the verified module was used,
  `Embedded(module)`; otherwise `None`. `None` means nothing is promoted, and that is an answer - not
  a licence to fall back to the first disk that answered, which is the defect this item exists to
  remove. And `Embedded` names `system-volume.img`, never `volume.pkg`, which is the factory archive
  a test medium carries and is not a volume at all.

  P02M0150 already put the paired volume's uuid in the boot medium's signed manifest and the loader
  verifies and reads it; what is missing is carrying its own conclusion past itself. `BootInfo` is a
  versioned structure the kernel refuses on mismatch, so adding a field means bumping
  `bootproto::VERSION` - a loader and a kernel disagreeing about the shape of this struct is the one
  failure that happens before anything can report it. The PROBE belongs to
  StorageService and not to DeviceManager: matching a `Block(uuid)` means reading a LiberFS superblock,
  `src/fs/liberfs` is what parses one, and keeping a filesystem out of the process that hands out
  device authority is worth the one hand-off it costs. No match and more than one match are both typed
  refusals. No multipath, no failover, no policy engine.

- [ ] **M3 - `subscribe(kind)` returns a snapshot and the stream in one step.** Registering the event
  stream and reading what is already there must be one operation with a sequence or cursor, or a
  provider added between the two is lost - which is the same race as a service started later seeing
  nothing. Removing one provider does not disturb the others.

- [ ] **M4 - driver readiness and provider readiness are separate.** `READY` means the process is
  initialised and supervised. A provider appears when its own probe is complete. One child failing
  does not take a healthy controller or its siblings down.

- [ ] **M5 - a withdrawal is honest about what it did not finish.** A provider is withdrawn from the
  catalogue and its consumers told; on a forced close the report says in-flight work was not
  confirmed rather than implying it completed. Draining gracefully - asking the driver to finish
  first - is P02M0165's, where the one stop-and-quiesce contract lives.

- [ ] **M6 - `requires` and `provides` in the registry, and `provides` is a bound.** An entry declares
  what it needs - a bus, a provider kind - and is retried when that arrives; and it declares which
  kinds it may publish AND how many, so a driver cannot publish a kind it never declared. A
  structural cycle or a manifest naming a kind no entry can produce is refused at registry-build
  time. Hardware that is simply absent at run time leaves the node in `DependencyPending`, which is a
  STATE and not a failure cause - a machine without a NIC is a machine, not a broken image. This
  milestone is where that state first has something to wait for, so it is the one that adds it to
  P02M0162's `BindingState`, in that file and not in a second enum - and it adds its rows to that
  milestone's transition table too, because a state with no way in and no way out is one every reader
  has to guess at:

  | from | to | on |
  | --- | --- | --- |
  | `Unbound` | `DependencyPending` | a declared requirement is not published yet |
  | `DependencyPending` | `Binding` | EVERY declared requirement is published - not the first one, which would start a bind that fails on the second |
  | `Binding` | `DependencyPending` | withdrawn before the claim was taken - there is nothing to tear down |
  | `Backoff` | `DependencyPending` | at the delay's expiry, a declared requirement is not published |

  THE EXPIRY RE-READS `requires`; IT DOES NOT WAIT TO BE TOLD. Reacting to a withdrawal EVENT while
  the node sits in `Backoff` is not enough, because a node can arrive in `Backoff` from `Stopping`
  after a crash - and if the requirement went away DURING that teardown, the event is spent and the
  expiry would proceed into a bind gated on a condition that no longer holds. So every backoff
  expiry asks the same question: all published, `Binding`; otherwise `DependencyPending`. One rule
  instead of an edge per way of getting there, and one test that walks crash -> `Stopping` ->
  withdrawal -> `Backoff` -> expiry.
  | `Binding` | `Stopping` | withdrawn after the claim was taken, with `intent = dependency lost` |
  | `Online` | `Stopping` | the same, for a binding that had reached `Online` |
  | `Stopping` | `DependencyPending` | that teardown confirmed |

  There is no `DependencyPending -> Unbound`: this item first had one for "the requirement is
  withdrawn", which is backwards - a node waiting for a provider that goes away is waiting harder,
  not waiting less, and `Unbound` invites an immediate bind that would fail for the reason it is
  already recording.

- [ ] **M7 - the tests are about there being no hardcoded count and no hand-written routing.** Not
  "unbounded": the registry bounds what each entry may publish, on purpose, and the defect is a limit
  compiled into DeviceManager rather than the existence of a limit. The four hardcoded block locals
  are absent from the source; a provider is added and removed at run time; a subscriber that starts
  AFTER publication still finds it; and a boot with the four volumes mounts each as the right one
  without depending on which driver finished first. Block providers are the integration
  evidence because the machine has four of them. Two NICs are NOT the test: NetworkService accepts
  one `FRAMES` channel, so multi-interface networking is its own work and not a way of proving a
  catalogue.

## Definition of done

- No fixed provider slot remains in DeviceManager, and the number of providers of a kind is bounded
  by what the registry allows a driver to declare and by nothing compiled into the manager.
- Which volume is which is decided by three inputs and never by arrival order, proved by a boot where
  the drivers finish in a different order:

  | | |
  | --- | --- |
  | format | LiberFS / FAT / ISO9660 / UDF - narrows, and for the two FAT volumes decides nothing |
  | origin | which controller published it, from `BindingId` and the registry entry - this is what separates FAT media from FAT USB |
  | `RootSelection` | the loader's verified identity, and the only thing that names the SYSTEM volume |

- The gate covers all three `RootSelection` outcomes - `Block`, `Embedded` and `None` - and `None`
  promotes nothing rather than the first disk that answered. It also boots a machine carrying BOTH a
  FAT medium and a FAT USB stick, in either order, and requires each to arrive at its own mount.
- Two devices of one kind produce two independent providers, and removing one leaves the other
  working, under test.
- A subscriber that arrives after a provider was published still sees it, and one that arrives
  between a snapshot and a subscribe misses nothing.
- A service subscribing after boot sees the providers that already exist.
- A driver can be online with no providers and add one later.
- A registry entry waits for what it declared and binds when it arrives; a cycle is refused at
  registry-build time.
- A forced removal is reported as forced and never claims the in-flight work completed.

## What this milestone refuses, and why

- **A general publish/subscribe bus.** Providers are typed, few, and owned by a binding. A message
  broker would be a larger thing than the problem.
- **Reworking the services that consume them.** Each service changes at one seam - where it used to
  receive a handle, it subscribes. What a service does with a disk is not this milestone's, with ONE
  named exception: StorageService gains the format probe in M2, because deleting the four block slots
  deletes the routing that decided which volume was which, and nothing else in the system knows how
  to tell a LiberFS volume from a FAT one. That is the exception, and it is not a licence for a
  second.
- **Multi-path or failover policy.** Two providers of a kind is what this makes possible; deciding
  which one something should use is a policy question and belongs to whoever has the use case.
