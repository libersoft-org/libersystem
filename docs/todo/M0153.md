# M0153 - What a mount allocates, and what a write may assume about what it found

M0143 and M0144 established two rules for LiberFS and then applied them where the audit rounds were
looking. Both rules are right and both are now incompletely applied:

1. **Every allocation sized from the medium is fallible.** `read_file`, `read_range`, the free maps
   and the GPT parser all obey it. The two metadata chain walks - snapshots and extent spill - do
   not, and both run at mount.
2. **A checksum proves integrity, not sanity, so a write must validate the structure it is about
   to mutate.** `leaf_is_whole` applies it to one invariant of one node kind. `fsck` knows nine
   more, and the write path consults none of them.

There is also one place where a protection introduced by the last round can silently fail to happen.

## The two mount-time allocations

Both are bounded, and both bounds scale with the volume rather than with anything a mount should
spend.

**`read_snapshot_table`** grows `out: Vec<Snapshot>` with a plain `push`, once per record. The chain
is bounded at `num_blocks` steps and each block holds `SNAPS_PER_BLOCK` records - about 48 - so on a
one-gigabyte volume a checksum-valid forged table can name roughly twelve million snapshots. That is
an allocation abort in the storage service where `MountError::NoMemory` is the answer that exists
for it.

The duplicate-name check is the sharper half:

```rust
if out.iter().any(|s: &Snapshot| s.name == name) {
```

O(N²) over the same twelve million, which is on the order of 10^14 comparisons. **The mount hangs
long before it runs out of memory**, and a hang at mount is a system that does not boot with no
message saying why. The check itself is correct and was added for a good reason; the shape is what
needs replacing.

**`load_spill`** does `inode.extents.push(...)` per extent, bounded by the inode's `extent_count`
(a `u32` off the medium) and by the chain length. It is reached from `derive_free` at mount - twice,
at `txn.rs:350` and `txn.rs:372` - so this is not confined to reading a hostile file. A volume whose
inode tree contains one inode with a long spill chain costs that allocation before the mount
finishes.

Note that both walks already refuse the impossible correctly: a count above what a block can hold,
a pointer outside the pool, a chain longer than the pool, a count above what the inode is still
missing. The bound they lack is on the TOTAL, and the growth they lack is fallible.

## What is wanted

- [x] **A ceiling and a fallible reserve on the snapshot table, and a duplicate check that is not
  quadratic.**

  A `MAX_SNAPSHOTS` the format states, checked as the walk goes rather than after; `try_reserve`
  before each push, mapping failure to `FsError::NoMemory` and so to `MountError::NoMemory`; and the
  uniqueness check done against a structure that is not a linear scan. A sorted `Vec` of name
  hashes with a `binary_search` keeps it allocation-light and needs no map; whichever is chosen, the
  ceiling has to come first, because a ceiling makes the rest cheap and the rest does not make the
  ceiling unnecessary.

  Pick the ceiling on what a snapshot table is FOR rather than on what memory allows - this is a
  system volume's named generations, not a log.

- [x] **`load_spill` must reserve fallibly, and `extent_count` needs a ceiling that means
  something.**

  `try_reserve` on `inode.extents` before the per-block loop, sized by the block's validated count,
  returning `NoMemory`. The `u32` in the header is not a bound anybody chose; a limit derived from
  the volume - an inode cannot hold more extents than the pool has blocks - is one the format can
  state and `fsck` can check.

- [x] **The unknown-inode protection must not be skipped when its scratch map cannot be allocated.**

  ```rust
  let speculative = try_zeroed(map.len()).ok();
  if let Some(mut scratch) = speculative {
  ```

  The `.ok()` throws away the allocation error, and the `if let` then skips the whole speculative
  directory walk. `derive_free` returns `Ok`, the mount stays writable, and if that unknown type
  byte really was a directory, none of its tree blocks are reserved and the allocator may hand them
  out. That is precisely the loss the union-of-both-readings was built to prevent, and it disappears
  under memory pressure without a word.

  The distinction the code needs is one it almost makes already. **A failure to PARSE the guess is
  correctly ignored** - one of the two readings is nonsense by construction, and the surrounding
  comment explains at length why a walk that fails there is telling the truth about the guess rather
  than about the volume. **A failure to ALLOCATE the protection map is not the guess failing**; it
  is the protection not happening. `let mut scratch = try_zeroed(map.len())?;` is the whole fix, and
  `NoMemory` at mount is an answer this crate already carries everywhere else.

- [x] **Validate the node a write is about to mutate, with the rules `fsck` already knows.**

  `leaf_is_whole` checks `recs.len() != node_count(buf)` - a truncated leaf, which was the finding
  it was written for. `check_structure` additionally knows: ascending `(hash, name)` order,
  `stored_hash == name_hash(name)`, duplicate names, the name policy, separator ordering,
  parent/child routing ranges, null children, directory size and node type. A writable mount checks
  none of them before editing.

  The reachable case is ordering. `dir_recs_search` is `recs.binary_search_by(...)`, and a
  checksum-valid leaf holding hashes in the order 900, 100, 500 is not sorted - so the search
  answers arbitrarily. `dir_insert_node` then takes that answer as either "the name is here, replace
  its child" or "insert at this position", writes the leaf back with `dir_leaf_write`, and
  `write_node_to` computes a fresh CRC over it. **The result is a new generation, correctly
  checksummed, built on a structure the format cannot produce** - a name that existed and is now
  duplicated, or one that is now unreachable, with nothing left to indicate which.

  `tree_insert_node` has the same shape on the generic inode B+tree: `leaf_count` and
  `internal_count` clamp their values rather than validating them, and no structural check runs
  before the mutation.

  The fix is not a full `fsck` at mount - that cost was rejected for a good reason and the reason
  still holds. It is to lift `validate_leaf` / `validate_internal` out of `check_structure` as
  functions both callers share, and call them on each node as it is read for mutation. That is a
  pass over a block already in memory, on the write path only, which is the same trade `leaf_is_whole`
  already makes and the same argument its comment already gives.

- [x] **Two unfinished edges in the snapshot validator.**

  `check_structure` re-reads the snapshot table and compares it against the in-memory one on
  `name`, `inode_root` and `generation` - **not `inode_root_crc`** (`fsck.rs:167`). A table whose
  stored root CRC drifted from the loaded one is exactly the sort of disagreement this comparison
  exists to catch.

  And the snapshot name loader uses `name_in`, which stops at the first NUL and looks no further.
  `read_superblock` was taught the other half of that rule for the volume label - *"the field AFTER
  the terminator has to be the zero padding the writer lays down [...] `system\0\xff\xffgarbage` is
  not something any writer of this format produces"* - and the same argument applies unchanged to a
  `SNAP_NAME_MAX` field. Same rule, one of two places.

- [x] **A test for each, and each watched to fail.**

  The two allocation ceilings and the two validator edges are ordinary image fixtures, which
  `src/fs/liberfs/src/tests.rs` builds by the hundred. The unsorted-leaf case is the one worth
  writing carefully: build a leaf whose records are out of order, checksum it correctly, mount
  writable, insert a name that already exists, and assert `Corrupt` rather than a silently
  duplicated entry. The scratch-map failure needs the allocation to fail on demand, which is what
  the existing OOM fixtures already arrange.

## Where this came from

The seventh outside audit round on this tree, 2026-08-09, verified claim by claim against the code.
It read an older revision (`b7693b63`) and its partition findings are duplicates of what M0152
already carries; these five are new and all of them still stand at `7e250f9`.

Two of them are the same shape as findings this project has already recorded twice - **a rule
applied where the last audit was looking, and not to the other path that shares its assumption**.
M0146 wrote that lesson down about the disk probe. M0151 found it again in the two channel receives.
Here it is in the fallible-allocation discipline (`read_file` yes, the two chain walks no) and in
the write-path validation (`leaf_is_whole` yes, the nine other invariants no). It is worth treating
as the default question after any fix in this tree rather than as a coincidence: **what else assumed
what this used to assume?**


## What was built

**`MAX_SNAPSHOTS = 256`, stated once and enforced at both ends.** The reader refuses a table
claiming more, checked as the walk goes rather than after it; `create_snapshot` refuses the 257th,
because what a mount cannot read a write must not create. The number is chosen on what a snapshot
table is FOR - a system volume's named generations, each pinning a whole generation's blocks - not
on what memory allows.

**The duplicate-name check stopped being quadratic.** It is a sorted `Vec` of name hashes with a
binary search, and a hash match is confirmed against the names, since a collision is not a
duplicate. The check itself was right; the shape was the problem, and the shape was the more urgent
half: twelve million records is around 10^14 comparisons, so the mount would hang long before it ran
out of memory - and a hang at mount is a system that does not boot with nothing said about why.

**`load_spill` reserves fallibly and has a bound that means something.** An extent names a run of
blocks, so an inode cannot hold more extents than the pool holds blocks. The `u32` in the header is
a width, not a limit anybody chose.

**`try_zeroed(map.len())?` for the speculative directory map.** One character, and it closes the
data-loss path. The distinction the surrounding code almost made: a failure to PARSE the guess is
correctly ignored, because one of the two readings is nonsense by construction; a failure to
ALLOCATE the protection map is not the guess failing, it is the protection not happening.

**`NodeFault` and three shared validators.** `validate_internal`, `validate_fixed_leaf` and
`validate_dir_leaf` hold the local invariants - counts, ordering, the stored hash, the name policy,
separators, null children - and BOTH the write path and `check_structure` call them. The write path
turns a fault into `Corrupt` and refuses the mutation; `fsck` turns it into a sentence. The
whole-tree checks that need the walk (routing intervals, duplicate names across a directory, a block
appearing twice) stayed where they were.

Refusing to mutate a damaged node takes a repair verb away, and that is the trade this makes
deliberately: `remove` on a directory holding a bad record now fails. It is the same trade the
truncated-leaf check already made, and the alternative is a mutation that makes the damage
authoritative and correctly checksummed, which no later pass can tell from a volume that was always
that way.

**`check_structure` compares `inode_root_crc`**, and a snapshot name's field must be zero-padded
past its terminator - the rule `read_superblock` already applied to the volume label, which the
snapshot record had only half of.

### The injector had to be extended before one test could prove anything

`inject::fail_after(n)` fails every allocation after the nth. That cannot distinguish a refusal
being PROPAGATED from one being SWALLOWED: a walk that discarded the scratch map's failure hits the
next allocation and answers `NoMemory` anyway. The first version of the speculative-map test passed
under a deliberate revert, which is the same defect as the thing it was testing.

`inject::fail_once_after(n)` refuses exactly one and lets the rest through. With it the test fails
under the revert, on its own assertion.

### Watched to fail

All six reverted in one pass: four tests failed immediately, and the fifth failed once the injector
could express a single refusal.

## Still open

- **A forged snapshot chain longer than the ceiling.** The writer's half of `MAX_SNAPSHOTS` is
  tested; the reader's is not, because building a chain of 300 checksum-valid records by hand needs
  a fixture the crate does not have yet. They share the constant, which is why this is a gap in
  evidence rather than in behaviour.
- **`check_structure`'s `inode_root_crc` comparison has no test.** It fires when the disk disagrees
  with memory, and the harness has no way to make them differ - a remount reloads memory from disk.
  It needs a hook that mutates the in-memory table, which is more machinery than the one-field
  change is worth on its own.
