# M0138 - The loader reads the filesystem: retire the bootstrap archive

Nine programs run on every boot that exist nowhere the user can look. `system_manager`,
`service_manager`, `device_manager`, `virtio_blk`, `storage_service`, `process_service`,
`log_service` and the two probes are staged `pinned`, which means their only copy is an entry
inside `init.pkg` - `system_manager.lsexe` in an archive, not `libexec/system_manager.lsexe` on
the volume. Browse the system volume and they are absent; list the running processes and they
are there.

That is the defect this milestone removes. Not a leak, not a crash - a running system whose
most privileged components cannot be seen, replaced, checked or backed up through the same
interface as everything else, and whose archive copy can silently drift from what the volume
says the system contains.

The cause is a real constraint rather than an oversight. After `ExitBootServices` the firmware
and its disk access are gone, and in a microkernel the disk driver is a USERSPACE PROGRAM - so
the driver needed to read the volume cannot itself be read from that volume. Something has to
arrive in memory first. Linux answers this with an initramfs, MINIX 3 and QNX with a boot image;
`init.pkg` is the same answer to the same problem.

The other answer is the one GRUB, the FreeBSD loader and Solaris use: give the LOADER a
filesystem driver and let it read the bootstrap set out of the real volume. The bytes still
arrive in memory before the disk is reachable, but they arrive FROM the place the user can see,
so nothing runs without a counterpart on disk.

That is what this milestone does. `init.pkg` stops being an artifact and becomes what it always
described - a list, in the manifest, of which programs are needed early.

- Done when: the loader reads the system volume directly on all three architectures, every
  program that runs has a file on that volume, `init.pkg` and `volume.pkg` no longer exist as
  build artifacts, and the boot chain comes up green on x86_64, aarch64 and riscv64.

## Why this is cheaper here than the GRUB comparison suggests

GRUB's filesystem drivers are a maintenance burden because they REIMPLEMENT other people's
formats and must chase them. This tree is in the opposite position, verified 2026-08-02:

| backend | lines | `no_std` |
| --- | --- | --- |
| `fs/liberfs` | 6841 | yes |
| `fs/fat` (FAT12/16/32 + exFAT) | 3680 | yes |
| `fs/udf` | 811 | yes |
| `fs/iso9660` | 702 | yes |

All four are already `no_std` and already read their medium through ONE shared trait,
`fs_core::BlockDevice`, whose write and flush have refusing defaults so a read-only backend
implements only `read_block`. The loader does not need a second implementation of anything - it
needs to link the crates it already has and provide a `BlockDevice` over firmware disk I/O.

That is the whole trick: the split is not loader-code vs kernel-code, it is who supplies the
BLOCK DEVICE. Before `ExitBootServices` the firmware does; afterwards `virtio_blk` does. The
filesystem code above that line is the same code.

## What goes in the loader

Read-only, and only until `ExitBootServices`:

- A `BlockDevice` implementation over the firmware's disk protocol (UEFI Block I/O), so the
  existing filesystem crates work unchanged above it.
- TWO filesystem backends, linked read-only: LiberFS for the system volume and FAT/exFAT for the
  ESP and removable media. Reading FAT matters beyond tidiness: it is how an installer image or a
  rescue stick boots before a LiberFS volume exists.
- NOT ISO9660 and NOT UDF. A hybrid ISO boots through a FAT El Torito image and the kernel and
  packages live on that FAT (`mkimage.sh`: "OVMF has no ISO9660 driver"), so the firmware never
  reads ISO9660 during boot and neither does the loader. Both stay in the storage service, which
  is where data discs are read after boot.
- Volume discovery: find the system volume rather than assume a fixed device, and fall back to
  the medium the loader was itself started from.
- Reading the kernel, and reading the bootstrap set the manifest names.
- The hand-off: each program passed as a named blob, exactly as today, so the kernel side does
  not change at all.

Explicitly NOT in the loader: writing, any filesystem repair, a shell or menu, network, drivers
for anything but the boot medium. It reads files and stops.

## What stays on the disk

Everything else, and now that means everything:

- The kernel.
- Every userspace program, INCLUDING the nine that are pinned today, each at a real path on the
  system volume, staged from the same manifest that stages the rest.
- The libraries, the factory files, the configuration.

The manifest keeps a `stage`-like marker, but it stops meaning "lives in a different artifact"
and starts meaning only "the loader must hand this one over before the volume is readable".
One list, one location, no second copy.

## M0138a - The loader gains a filesystem

- [x] Give the loader a `fs_core::BlockDevice` over the firmware disk protocol and link LiberFS
  read-only (`src/loader/src/blockio.rs`). Proven on x86_64 on 2026-08-02: booted with a LiberFS
  image attached as a second disk, the loader reports `kernel read from the system volume` and the
  kernel starts from those bytes. FAT is NOT linked yet - see the item below.

- [ ] Link the FAT backend read-only as well. Lower value than it looks and therefore left last:
  the firmware already exposes the ESP through Simple File System, which is what the loader reads
  today, so linking FAT buys reading a FAT medium the firmware will not mount for us - an installer
  or rescue stick on unusual firmware. Worth having, not worth blocking on.

- [x] Discover the system volume rather than hard-code it: every block device the firmware reports
  is tried and LiberFS is identified by `LiberFs::mount` succeeding - by its superblock, not by
  device order. Verified by the proof above, where the volume was the second drive behind the CD.
  Partitions are deliberately included: on a GPT disk the firmware exposes both the whole disk and
  each partition, and the system volume is a partition, so skipping them would find nothing on
  exactly the layout `just img` produces.

## What M0138a turned up that this milestone had not accounted for

Two prerequisites, neither of them mentioned above before the work started:

- **The loader had no allocator.** LiberFS and FAT are `no_std` but not allocation-free - between
  them they use `Vec`, `Box` and `String` in nearly two hundred places, because a directory walk
  and a file read are sized at runtime. `src/loader/src/heap.rs` is a bump allocator over firmware
  pages that never reuses memory, which is the right shape rather than a shortcut: the loader runs
  once and ceases to exist at `ExitBootServices`, so a free list would cost code and bugs to
  reclaim memory nothing lives long enough to need. It is retired at `ExitBootServices` on all
  three architectures, so an allocation after that point fails loudly instead of handing out memory
  the loader no longer owns. `build-std` gained `alloc`.

- **There is no LiberFS volume on the disk at boot.** The system disk carries `volume.pkg`, a
  factory ARCHIVE at LBA 0, and the storage service formats a volume and seeds it from that archive
  after boot. At the moment the loader runs there is no filesystem to read - which is why the first
  boot with this work reported `no LiberFS volume on any block device` and fell back to the ESP.
  `src/tools/mkvolume` now builds a LiberFS image on the host from the same `liberfs` crate the
  loader and the storage service use, so a built image and a runtime-formatted volume are the same
  format because they are the same code. It verifies the image mounts and reads back every file it
  wrote before writing it out, because a volume that formats but does not mount is worth catching
  on the build host rather than on a machine that will not boot.

Also found, and not caused by this work (verified by stashing): `just loader-riscv64` does not
build at HEAD. M0138c below says both aarch64 and riscv64 "already have a UEFI loader"; aarch64
does, riscv64 does not.

## M0138b - The bootstrap set comes from the volume

- [x] Replace `init.pkg` with a manifest-named list the loader reads file by file from the
  volume. Done 2026-08-02 and proven by boot: the loader reports `bootstrap set assembled from
  the system volume`, having read `etc/bootstrap.list`, read each program it names out of
  `libexec/`, and packed them into the archive format the kernel already unpacks.

  The archive is assembled IN MEMORY rather than passed as N modules, and that is the design
  decision worth recording. Passing each program as its own module would have meant rewriting the
  kernel's module lookup - it finds one blob named `init.pkg` - and SystemManager, which receives
  that archive as a shared buffer. This milestone promises the kernel is untouched, and assembling
  in memory keeps that promise literally: the same bytes arrive, built from files that exist on
  the volume rather than from a package built beside it. `init.pkg` becomes what the milestone
  said it always described - a list.

  Both sources are reported on the serial log. A boot that silently fell back to the archive would
  otherwise look identical to one that read the volume, which is not a distinction to lose in a
  change to how the system starts.

- [x] Stage the nine pinned programs onto the system volume at real paths (`libexec/<name>`),
  built by `mkpackages` from the same manifest rows that fill the init package. Every program that
  runs now has a file on the volume.

- [x] Attach the system volume in the test harness so the suite exercises the volume path rather
  than the fallback. Added to `qemu-run.sh` as a SEPARATE disk, last in PCI order because the boot
  chain's device inventory follows that order and a disk inserted earlier would renumber what the
  chain expects. x86_64 green at 153 with the suite's own guest log showing both `kernel read from
  the system volume` and `bootstrap set assembled from the system volume` - the tests now boot the
  new path rather than the fallback.

- [x] Retire `volume.pkg` from the boot path. Done 2026-08-02, x86_64 green at 153. The disk now
  carries the system VOLUME rather than a package to make one from: `FS_START_SECTOR` drops from
  65536 to 0 (the 32 MiB offset existed only to clear the archive), the seeding path and its two
  helpers are deleted, and `qemu_prepare_system_disk` lays the LiberFS image instead of the
  archive. A disk with no filesystem still gets an empty volume formatted - a genuinely fresh disk
  has to be usable - but it now SAYS SO, because a silently formatted empty volume looks exactly
  like a working install.

  Four things had to move with it, and three were tests asserting the retired layout:

  - The fixture volume is formatted STRAIGHT INTO the harness's sector map. Building it as one
    contiguous image and then chopping it into sectors put two copies of a multi-megabyte volume
    in the kernel heap, and the contiguous one is the expensive half: the kernel allocator grows
    in 2 MiB regions and first-fits within them, so a single 8 MiB request needs eight coalesced
    regions. That held on x86_64 and did not on aarch64, whose binaries - and therefore whose
    volume - are close to twice the size, where it surfaced as an unhandled exception rather than
    as a failed allocation. Two wrong explanations were tried first, that the image was simply too
    big and that the kernel heap was fixed; the heap grows, and the real cost was the shape of the
    allocation rather than its size.
  - `StorageHarness::start` served two purposes - the system volume and raw media images (FAT,
    ISO, UDF). Formatting a volume in it broke the media fixtures, which are images already.
    Split into `start` (verbatim) and `start_system` (builds a LiberFS volume from the scenario
    archive), with the fixture proving it mounts before handing it over.
  - `FACTORY_START_SECTOR` became `FALLBACK_START_SECTOR = 0`. The GPT case had to change shape
    too: the fallback offset is LBA 0, which on a GPT disk carries the protective MBR, so the
    check is "no volume was laid there" rather than "nothing is there".
  - `existing_system_volume_preserves_owned_state_when_factory_seed_changes` corrupted the archive
    between two runs to prove an existing volume was not reformatted. Those bytes are the
    SUPERBLOCK now, so the test destroyed what it was checking. Renamed to
    `..._across_a_restart` and the corruption step dropped; the surviving property - owner state
    lives through a restart - is the half that still exists.
  - `a_lying_seed_archive_cannot_kill_the_storage_service` was written for one attack: an archive
    header claiming a 137 GB entry table, used to size a read buffer. That code is deleted.
    Renamed to `garbage_where_the_superblock_should_be_cannot_kill_the_storage_service`, which is
    the general property it now guards - keeping the old name would have left the suite lying
    about what it covers.

- [ ] Stop SHIPPING `volume.pkg`. It is off the boot disk and nothing seeds from it, but it is
  still built and still handed to the kernel as a module, because the test suite uses it twice:
  as the archive its fixture volume is built from, and as the table of expected file contents.
  That is precisely the "needs a ramdisk fixture of its own rather than an artifact in every
  image" this milestone predicted, and it is a build-level split rather than a code change. It is already dead weight in the boot path - `ServiceManager` drops
  the ramdisk capability rather than delegating it, because StorageService reads the volume from
  virtio-blk instead (`service_manager.rs:196`). It survives only for one kernel test, which
  needs a ramdisk fixture of its own rather than an artifact in every image.

## M0138c - The same path on every architecture

- [ ] Bring aarch64 and riscv64 onto the loader path. Both already have a UEFI loader
  (`just loader-aarch64`, `just loader-riscv64`), so this is about making it the DEFAULT rather
  than the alternative to a direct `-kernel` boot.

- [ ] Retire the `boot-packages-<arch>.pkg` wrapper and the magic scan that finds it. Both were
  added on 2026-08-01 only because a machine with no loader can be handed exactly one blob; a
  loader that reads the volume needs neither. Note for whoever does this: the kernel currently
  clamps its frame pool below the archive so the allocator cannot overwrite it - that clamp goes
  away with the scan, and removing one without the other is a memory-corruption bug that will
  look like random userspace faults.

## Verified

- [ ] Green on all three architectures, and the boot chain comes up on each. A change to how the
  system starts cannot be signed off on one target.

## Risks worth naming

- The loader becomes privileged code that parses on-disk structures. In a system whose whole
  argument is that drivers are isolated userspace processes, this is a genuine concession. It is
  bounded - read-only, no writes, and it ceases to exist at `ExitBootServices` - but a malformed
  filesystem is now parsed by the most privileged code in the boot.
- Boot cost: reading nine files from LiberFS is more work than reading one archive. Measure it
  rather than assume; the archive exists partly because it is one contiguous read.
- A volume the loader cannot read is now an unbootable system, where today the archive would
  still bring the machine up far enough to say so. The failure message matters more than usual.

## M0138d - Two images, two purposes

Scoped 2026-08-02. An installer is deliberately NOT part of this: it needs a partition manager
and locales, neither of which exists. Two build outputs, and they differ in where the system
volume lives rather than in what is on it.

- [ ] **LiveCD ISO.** The system volume is `LiberMemFS` in memory, so the medium is never
  written to and the machine needs no disk at all. M0139 built the filesystem this depends on:
  a writable volume that holds only what is put in it and disappears at power off. What has to
  be decided here is what a live session keeps - today `vol://ram` is 4 MiB reserved and
  `vol://tmp` 16 MiB capped, which are scratch sizes, not "the whole system volume" sizes.

- [ ] **Disk image, IMG and QCOW2.** The system volume is LiberFS on the disk, which is what a
  running installed system uses. `just img` already writes a raw GPT disk with an ESP; QCOW2 is
  the same content through `qemu-img convert`, which is worth having because a raw 64 MiB image
  is 64 MiB whether or not it is used, and a QCOW2 of the same system is a fraction of that to
  store and to move.

- [ ] Decide whether ISO is built for aarch64 and riscv64 at all. `mkimage.sh` is x86_64-only
  today and not by accident: it hard-codes `BOOTX64.EFI` and the x86_64 loader path. Optical
  boot on those targets is rare to the point of being theoretical, while a disk image is what
  both actually boot from. The honest default is IMG/QCOW2 everywhere and ISO on x86_64 only,
  unless there is a reason to carry a per-architecture El Torito path nobody uses.

## Explicit non-goals

No installer - it needs a partition manager and locales, and neither exists yet; deferred with
that dependency stated rather than left as an assumption. No writing from the loader, no boot
menu, no multi-OS chaining, no network boot, no filesystem repair. Not a change to the kernel's hand-off protocol - the kernel keeps receiving named blobs
and does not learn what a filesystem is.
