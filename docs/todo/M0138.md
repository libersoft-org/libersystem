# M0138 - The loader reads the filesystem: retire the bootstrap archive

Nine programs run on every boot that exist nowhere the user can look. `system_manager`,
`service_manager`, `device_manager`, `virtio_blk`, `storage_service`, `process_service`,
`log_service` and the two probes are staged `pinned`, which means their only copy is an entry
inside `init.pkg` - `system_manager.lsexe` in an archive, not `libexec/system_manager.lsexe` on
the volume. Browse the system volume and they are absent; list the running processes and they
are there.

That is the defect this milestone removes. Not a leak, not a crash - a running system whose
most privileged components cannot be seen, replaced, checked or backed up through the same
interface as everything else, and whose archive copy can silently drift from what the volume
says the system contains.

The cause is a real constraint rather than an oversight. After `ExitBootServices` the firmware
and its disk access are gone, and in a microkernel the disk driver is a USERSPACE PROGRAM - so
the driver needed to read the volume cannot itself be read from that volume. Something has to
arrive in memory first. Linux answers this with an initramfs, MINIX 3 and QNX with a boot image;
`init.pkg` is the same answer to the same problem.

The other answer is the one GRUB, the FreeBSD loader and Solaris use: give the LOADER a
filesystem driver and let it read the bootstrap set out of the real volume. The bytes still
arrive in memory before the disk is reachable, but they arrive FROM the place the user can see,
so nothing runs without a counterpart on disk.

That is what this milestone does. `init.pkg` stops being an artifact and becomes what it always
described - a list, in the manifest, of which programs are needed early.

- Done when: the loader reads the system volume directly on all three architectures, every
  program that runs has a file on that volume, `init.pkg` and `volume.pkg` no longer exist as
  build artifacts, and the boot chain comes up green on x86_64, aarch64 and riscv64.

## Why this is cheaper here than the GRUB comparison suggests

GRUB's filesystem drivers are a maintenance burden because they REIMPLEMENT other people's
formats and must chase them. This tree is in the opposite position, verified 2026-08-02:

| backend | lines | `no_std` |
| --- | --- | --- |
| `fs/liberfs` | 6841 | yes |
| `fs/fat` (FAT12/16/32 + exFAT) | 3680 | yes |
| `fs/udf` | 811 | yes |
| `fs/iso9660` | 702 | yes |

All four are already `no_std` and already read their medium through ONE shared trait,
`fs_core::BlockDevice`, whose write and flush have refusing defaults so a read-only backend
implements only `read_block`. The loader does not need a second implementation of anything - it
needs to link the crates it already has and provide a `BlockDevice` over firmware disk I/O.

That is the whole trick: the split is not loader-code vs kernel-code, it is who supplies the
BLOCK DEVICE. Before `ExitBootServices` the firmware does; afterwards `virtio_blk` does. The
filesystem code above that line is the same code.

## What goes in the loader

Read-only, and only until `ExitBootServices`:

- A `BlockDevice` implementation over the firmware's disk protocol (UEFI Block I/O), so the
  existing filesystem crates work unchanged above it.
- TWO filesystem backends, linked read-only: LiberFS for the system volume and FAT/exFAT for the
  ESP and removable media. Reading FAT matters beyond tidiness: it is how an installer image or a
  rescue stick boots before a LiberFS volume exists.
- NOT ISO9660 and NOT UDF. A hybrid ISO boots through a FAT El Torito image and the kernel and
  packages live on that FAT (`mkimage.sh`: "OVMF has no ISO9660 driver"), so the firmware never
  reads ISO9660 during boot and neither does the loader. Both stay in the storage service, which
  is where data discs are read after boot.
- Volume discovery: find the system volume rather than assume a fixed device, and fall back to
  the medium the loader was itself started from.
- Reading the kernel, and reading the bootstrap set the manifest names.
- The hand-off: each program passed as a named blob, exactly as today, so the kernel side does
  not change at all.

Explicitly NOT in the loader: writing, any filesystem repair, a shell or menu, network, drivers
for anything but the boot medium. It reads files and stops.

## What stays on the disk

Everything else, and now that means everything:

- The kernel.
- Every userspace program, INCLUDING the nine that are pinned today, each at a real path on the
  system volume, staged from the same manifest that stages the rest.
- The libraries, the factory files, the configuration.

The manifest keeps a `stage`-like marker, but it stops meaning "lives in a different artifact"
and starts meaning only "the loader must hand this one over before the volume is readable".
One list, one location, no second copy.

## M0138a - The loader gains a filesystem

- [ ] Give the loader a `fs_core::BlockDevice` over the firmware disk protocol and link the two
  boot backends (LiberFS and FAT) read-only. Prove it by reading the kernel from the system volume rather than from the
  ESP, on x86_64 first.

- [ ] Discover the system volume rather than hard-code it: try the medium the loader was started
  from, then the other block devices, and identify LiberFS by its superblock rather than by
  device order - a machine with two disks must not boot the wrong one.

## M0138b - The bootstrap set comes from the volume

- [ ] Replace `init.pkg` with a manifest-named list the loader reads file by file from the
  volume and hands over as named blobs. The kernel's hand-off protocol does not change; only
  where the bytes came from does.

- [ ] Stage the nine pinned programs onto the system volume at real paths, so every running
  program has a file. This is the point of the milestone; everything else is machinery.

- [ ] Retire `volume.pkg`. It is already dead weight in the boot path - `ServiceManager` drops
  the ramdisk capability rather than delegating it, because StorageService reads the volume from
  virtio-blk instead (`service_manager.rs:196`). It survives only for one kernel test, which
  needs a ramdisk fixture of its own rather than an artifact in every image.

## M0138c - The same path on every architecture

- [ ] Bring aarch64 and riscv64 onto the loader path. Both already have a UEFI loader
  (`just loader-aarch64`, `just loader-riscv64`), so this is about making it the DEFAULT rather
  than the alternative to a direct `-kernel` boot.

- [ ] Retire the `boot-packages-<arch>.pkg` wrapper and the magic scan that finds it. Both were
  added on 2026-08-01 only because a machine with no loader can be handed exactly one blob; a
  loader that reads the volume needs neither. Note for whoever does this: the kernel currently
  clamps its frame pool below the archive so the allocator cannot overwrite it - that clamp goes
  away with the scan, and removing one without the other is a memory-corruption bug that will
  look like random userspace faults.

## Verified

- [ ] Green on all three architectures, and the boot chain comes up on each. A change to how the
  system starts cannot be signed off on one target.

## Risks worth naming

- The loader becomes privileged code that parses on-disk structures. In a system whose whole
  argument is that drivers are isolated userspace processes, this is a genuine concession. It is
  bounded - read-only, no writes, and it ceases to exist at `ExitBootServices` - but a malformed
  filesystem is now parsed by the most privileged code in the boot.
- Boot cost: reading nine files from LiberFS is more work than reading one archive. Measure it
  rather than assume; the archive exists partly because it is one contiguous read.
- A volume the loader cannot read is now an unbootable system, where today the archive would
  still bring the machine up far enough to say so. The failure message matters more than usual.

## Explicit non-goals

No writing from the loader, no boot menu, no multi-OS chaining, no network boot, no filesystem
repair. Not a change to the kernel's hand-off protocol - the kernel keeps receiving named blobs
and does not learn what a filesystem is.
