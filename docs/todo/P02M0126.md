The audit's own order held up. Memory first - the sector-at-a-time directory walk removed the

The recurring lesson is about the fixtures rather than the parser: the builder wrote media no
mastering tool produces - a terminator with no version, records with no volume sequence number - so
an internal round trip agreed with itself. Every strictness added here had to correct the builder
first, which is exactly why the missing golden image is the one thing still worth having.

An outside audit of `src/fs/iso9660` against ECMA-119, pinned to `d309476`. Every
finding was checked against the tree and every one held.

The crate's own header says a hostile or corrupt disc "errors, never crashes or exhausts the mounting
service". Against an ISO from `xorriso` or `mkisofs` the parser is short, readable and better
defended than most small ISO readers - forged extents, XAR, associated files, interleaving and
multi-extent reads are all refused rather than misparsed, and every one of those has a regression
test. What the header claims and what the code does part company in three places:

- **exhaust**: an extent's size is bounded by the VOLUME and then allocated in one `Vec`, so a
  four-gigabyte directory is a four-gigabyte allocation - and the comment directly above the
  allocation says a forged length "can neither allocate without bound";
- **accept**: ISO9660 records every critical number twice, little-endian and big-endian, and this
  parser reads only the little half of all four of them, so internally contradictory metadata passes;
- **interpret**: Rock Ridge names are read out of any System Use Area that happens to contain `NM`,
  with no SUSP negotiation at all - and a non-Rock-Ridge volume is entitled to put other extensions'
  data there.

## Memory, which is the one that is reachable from a listing

- [x] **Every extent becomes one `Vec` sized from the medium.** `read_extent` proves the extent lies
  inside the volume and then does `vec![0u8; size as usize]`. `size` is a `u32`, so a volume that
  declares a large enough block count can ask for close to four gigabytes. It is not only files:
  `find_entry` and `read_dir` both read the whole directory extent first, so `ls` on a crafted disc
  is enough - the caller never opens anything.

  The integration doubles it. `IsoFs::read_file` hands that `Vec` to StorageService, which creates a
  `MemoryObject` of the same size to stage it for the client, so a large file is briefly resident
  twice.

  Two changes, and the first is the one that matters: **directories should never be read whole.** A
  sector-at-a-time iterator removes the exhaustion path, removes several copies, and makes the
  boundary rule below natural to enforce rather than an extra check. For files, either a ceiling on
  `read_file` or - better, and what `Storage.Volume` already does elsewhere - a chunked read. Every
  allocation sized from the medium should be fallible.


  DONE for directories 2026-08-11, which is the half that is reachable from a listing.
  `for_each_record` walks a directory extent one SECTOR at a time and hands each record to its
  caller, so `find_entry` and `read_dir` allocate nothing proportional to the medium's claim. `ls`
  on a crafted disc no longer asks for close to four gigabytes.

  `read_file` still reads a whole file into one `Vec` and still has the StorageService staging copy
  beside it. That is the chunked-read half and it is not done.

- [x] **`read_blocks` is never used, and a path walk re-reads every directory it passes through.**
  `fs-core` offers `read_blocks(index, count, buf)` so a contiguous extent can be one device round
  trip; `read_extent` loops a block at a time. And `resolve_dir("A/B/C")` calls `find_entry` per
  segment, each of which allocates and reads that directory's whole extent again. Behind the
  IPC-backed `IsoBlockDevice` that is an expensive shape. The sector iterator above fixes most of it.

  PARTLY DONE 2026-08-11. `read_extent` now takes the whole contiguous run through `read_blocks` -
  one device round trip rather than a message per 2 KiB behind the IPC-backed block device - with a
  single tail read when the size is not a whole number of sectors.

  The re-reading half is gone by construction rather than by caching: the sector-at-a-time directory
  walk means `resolve_dir` no longer allocates and copies each directory's whole extent per segment.
  What is left is that it still READS each directory it passes through, which a cache would answer
  and is a different piece of work.

## Metadata that is accepted without being checked

- [x] **The both-endian halves are never compared.** ECMA-119 records volume space size, the root
  extent, each file's extent and each file's length in both byte orders, in one field. This parser
  calls `le32` on all of them and ignores the big-endian half entirely - five `le32`/`le16` call
  sites and no `be32` anywhere. A volume claiming a little-endian length of 1000 and a big-endian
  length of `0xFFFFFFFF` is internally contradictory and is accepted. `both_u16`/`both_u32` helpers
  that read both and refuse a mismatch are the cheapest hardening available here.

- [x] **A directory record may cross a logical sector boundary.** The parser knows half the rule: a
  zero length means "skip to the next sector", and it does. What it does not check is the other half
  - that a record which STARTS in a sector also ends in it. `off + rec_len > data.len()` bounds
  against the whole extent, not against the 2048-byte sector, and ECMA-119 says plainly that a
  Directory Record shall not cross the boundary.


  DONE 2026-08-11, and it fell out of the sector walk rather than being another check to remember:
  a record must start and END inside the sector it is in, which is what ECMA-119 requires. Pinned by
  a test that declares a 200-byte root extent and plants a record at 148 claiming 100.

- [x] **A malformed record becomes a missing file or a short listing.** Both loops `break` on a
  record they cannot use: `find_entry` then answers `NotFound`, and `read_dir` returns `Ok` with
  whatever it had collected. So a corrupt directory is indistinguishable from one that does not hold
  the name, and a listing can be short with nothing to say so. `FsError::Corrupt` is what fs-core has
  for this.


  DONE 2026-08-11. A record too short to be one, or one that runs past its sector, is
  `FsError::Corrupt` rather than a `break` - so a damaged directory stops being indistinguishable
  from one that does not hold the name.


  DONE 2026-08-11. `both32` and `both16` read the little half, the big half, and refuse a mismatch;
  the volume space size, the logical block size and the root record's extent and length all go
  through them. Watched to fail: removing the comparison makes
  `a_contradictory_both_endian_field_is_refused` pass a volume whose two halves disagree.

- [x] **The Root Directory Record is taken on trust.** `root_extent` reads bytes 156..190 of the
  descriptor, pulls the little-endian extent and length out, and returns. It is a standard 34-byte
  Directory Record and none of its structure is checked - not the record length, not the directory
  flag, not the single-byte identifier `0`, not the volume sequence number, not the big-endian
  halves. A malformed descriptor can therefore nominate any region of the volume as the root, as
  long as the extent survives the bounds check.


  DONE 2026-08-11. Its own length, the directory flag, the single-byte identifier `0`, and both
  halves of the extent and the size are all checked, and the XAR skip uses `checked_add` rather than
  `saturating_add` - clamping to `u32::MAX` invented a value the medium never gave.

- [x] **`saturating_add` hides an overflow in the XAR skip.** Both `root_extent` and `parse_record`
  compute `extent.saturating_add(xar_len)`. If those numbers overflow, the honest answer from a
  parser of untrusted media is `Corrupt` - clamping to `u32::MAX` invents a value the medium did not
  give. `checked_add` and a refusal.

  DONE 2026-08-11. `checked_add` in both places, and both halves of the extent and the length go
  through `both32` on the way.

## The volume descriptor set

- [x] **A volume with no Primary Volume Descriptor mounts.** The final match is
  `(Some(joliet), _) => (true, joliet)`, so a recognised Joliet SVD alone is enough and `pvd_root`
  being `None` is not an obstacle. ECMA-119 requires a PVD in the Volume Descriptor Set. Require a
  valid PVD first, and only then let a valid Joliet SVD supply the namespace and root.


  DONE 2026-08-11. A Joliet SVD supplies the namespace on top of a valid PVD and is not a volume on
  its own; the absence of a PVD is now a refusal.

- [x] **The descriptor version is never read.** `block[1..6] == "CD001"` and `block[0]` are checked;
  `block[6]`, the version, is not. It matters most for the type-2 descriptors, where the parser then
  decides from a few bytes that it is looking at Joliet.


  DONE 2026-08-11, and it needed the descriptor TYPE to be decided first: a terminator carries none
  of the fields around it, so validating them before recognising it refused the very descriptor that
  says the set is complete. The test builder had to gain a version byte on its terminator, which no
  mastering tool omits.

- [x] **Joliet is detected by searching the whole escape field.** `is_joliet` takes
  `desc[88..120]` and accepts `%/@`, `%/C` or `%/E` occurring anywhere inside it, via
  `windows(3).any(..)`. Joliet defines those three sequences for its UCS-2 levels and the field is
  written from the start, contiguously. A test - `a_joliet_escape_later_in_the_field_is_recognized`
  - currently pins the loose behaviour; it should be rewritten rather than preserved, because it
  asserts something that is not a Joliet layout.

- [x] **The Volume Descriptor Set Terminator is not required, and 32 is a magic number.** The scan
  runs `for i in 0..32` and `break`s on type 255. Nothing records whether the terminator was ever
  seen, so a set that simply stops mounts anyway; and a legal but unusual set whose Joliet descriptor
  sits past the thirty-second sector is silently missed. Keep the safety limit - it is a good one -
  and make reaching it an explicit refusal, and make the terminator a requirement.


  DONE 2026-08-11 for the terminator: a set that stops without one does not mount, and reaching the
  thirty-second sector without seeing one is the same refusal rather than a silent end to the search.

  DONE 2026-08-11. The escape sequence must be at the START of the field, which is where Joliet
  writes it - `starts_with` rather than `windows(3).any`. The test that pinned the loose behaviour
  was rewritten rather than preserved, as the finding asked: it now asserts that a descriptor whose
  escape sits later in the field does NOT supply the namespace.

- [x] **Multi-volume sets are neither supported nor refused.** Each Directory Record carries a Volume
  Sequence Number naming the volume its extent lives on, and this parser ignores the field. With one
  `BlockDevice` behind it, an extent belonging to volume 2 is read at that LBA on whichever disc is
  in the drive. Until multi-volume is supported, require `volume_set_size == 1` at mount and the
  matching sequence number on every record.

  DONE 2026-08-11 by refusing: a record whose Volume Sequence Number is not 1 does not parse. With
  one `BlockDevice` behind this reader, an extent belonging to volume 2 would otherwise be read at
  that LBA on whichever disc happens to be in the drive.

## Rock Ridge, which is currently guessed at

- [x] **Rock Ridge is used without SUSP being negotiated at all.** `decode_name` passes every
  non-Joliet record's System Use Area to `rock_ridge_name`, which walks it looking for an `NM` entry.
  There is no `SP` check, no skip value, no `ER` and no RRIP identification anywhere in the crate.
  SUSP exists precisely so independent extensions can share that area, so a valid non-Rock-Ridge
  volume whose System Use Area happens to contain those two bytes has its filenames replaced by
  whatever follows them.

  Detect SUSP at the root through `SP`, take its skip value, read `ER` to establish RRIP, and record
  the result in `Geometry`. Interpret `NM` and its relatives only when RRIP is actually present.

  DONE 2026-08-11. `SP` is read from the ROOT directory's own record - check bytes and skip - and
  `ER` in the same area is what says RRIP is actually in use; both are recorded in `Geometry` and
  `NM` is read only when they are present. Watched to fail: removing the gate makes an unannounced
  `NM` become a filename again, which is the finding.

- [x] **The partial implementation does not "degrade cleanly" - it can answer with a different
  name.** `CE`, `ST`, `CL`, `PL` and `RE` are all unhandled, and the header calls that a clean
  degradation. An `NM` continued through `CE` yields the prefix only, so two long names that differ
  late become the same name; `CL`/`PL`/`RE` are how Rock Ridge relocates deep directories, so
  ignoring them dismantles the very structure they express; and ignoring `ST` means the walk runs on
  into bytes that are no longer SUSP entries.

  Either implement them or be fail-closed: when a continuation or a relocation is found that this
  parser cannot follow, fall back to the ISO9660 identifier or refuse - do not synthesise a name.

  DONE 2026-08-11, fail-closed. `CE`, `CL`, `PL` and `RE` - and an `NM` carrying the CONTINUE flag -
  make the Rock Ridge path return nothing, so the ISO9660 identifier stands: a name the medium
  really carries rather than the first half of one. `ST` ends the walk, instead of running on into
  bytes that are no longer SUSP entries.

- [x] **One case-insensitive comparison is applied to every namespace.** `eq_ci` ASCII-folds
  everything, including a Rock Ridge `NM` name and a Joliet name. For a bare `FOO.TXT;1` that is the
  right convenience. Rock Ridge exists to express POSIX semantics, where `Makefile` and `makefile`
  are two files - and `find_entry` returns the first match, making the second unreachable by its own
  name. An `Entry` should know where its name came from, and the comparison should follow from that.

  DONE 2026-08-11. An `Entry` records which namespace its name came from, and `name_matches`
  follows it: a Rock Ridge or Joliet name is preserved-case and compares exactly, a bare ISO9660
  identifier folds. `Makefile` and `makefile` on a Rock Ridge disc are two files again - before,
  `find_entry` returned the first and the second was unreachable by its own name.

## Smaller, and one that misreports

- [x] **A multi-extent file is listed with the size of its first section.** `read_file` refuses it,
  correctly, on `entry.unsupported`. But `read_dir` adds the first record as an ordinary `FileInfo`
  and de-duplicates the rest by name, so the listing shows a size that is neither the file's nor
  anything else's - for a file the backend then refuses to read. Either assemble the sections or
  mark the entry unsupported in the listing.

  DONE 2026-08-11. An entry the reader will refuse to open is left out of the listing rather than
  described with a size that is neither the file's nor anything else's.

- [x] **`unsupported` is checked when reading a file and not when entering a directory.**
  `parse_record` sets it for the multi-extent bit and for interleaving; `resolve_dir` tests only
  `is_dir`. ECMA-119 is stricter for directories than for files - they may not be interleaved and
  are a single file section - so a directory record carrying either should be refused on descent.

  DONE 2026-08-11. `resolve_dir` refuses a directory record carrying the multi-extent or interleave
  bits - ECMA-119 is stricter for directories than for files, and the descent was the looser path.

- [x] **The Joliet decoder turns malformed identifiers into different names.** `chunks_exact(2)`
  silently drops a trailing odd byte, and an invalid UCS-2 unit becomes `'?'`, so two distinct
  corrupt identifiers can collide on one name. An odd length is corruption and an invalid unit is
  corruption; a lossy rendering, if wanted at all, must not be the lookup key.

  DONE 2026-08-11. An odd identifier length and an invalid UCS-2 unit both refuse the record;
  `decode_name` is fallible end to end. A lossy rendering can collide two damaged identifiers on one
  name, and the name is the lookup key.

- [x] **The error vocabulary drifts from fs-core's.** Reading a directory answers `NotFound`, and so
  does treating a file as one, though `FsError` has `IsDir` and `NotDir`; empty path segments are
  filtered and a test requires `SUB/..` to resolve, though fs-core's own documentation calls `.` and
  `..` malformed components. One of the two documents is wrong and this milestone should say which -
  the drift between backends is the defect, not either behaviour on its own.

  PARTLY DONE 2026-08-11: reading a directory answers `IsDir` and a file used as a path component
  answers `NotDir`, which is what fs-core has for both. The `.`/`..` question - fs-core's docs call
  them malformed while this backend filters empty segments and a test requires `SUB/..` to resolve -
  is a decision about which document is wrong, and is left open deliberately.

- [x] **Say that the supported subset is the subset.** The backend reads volumes with a 2048-byte
  logical block size and refuses the rest, openly and deliberately. ECMA-119 permits other sizes up
  to the logical sector size. That is a fine product decision and the header should describe it as
  one rather than as ISO9660 support.

  DONE 2026-08-11, in the crate header where a reader meets the claim: the 2048-byte block size,
  multi-volume sets, multi-extent and interleaved files, and the Rock Ridge entries this parser
  will not follow are all named as deliberate boundaries rather than left to be discovered from a
  refusal.

## Order

Memory first, because it is reachable from a listing and it is what the header promises: the
sector-at-a-time directory iterator removes the exhaustion path and makes the boundary rule fall out
of the structure rather than being another check to remember. Then the metadata that is accepted
without being checked - both-endian, the root record, the descriptor set. Then SUSP detection, which
is what makes the Rock Ridge path honest, and fail-closed handling of what it cannot follow. Joliet,
the error vocabulary and the performance work after that.

  MOSTLY DONE 2026-08-11: 14 tests became 28, and the images the finding asked for now exist -
  mismatched little/big-endian halves, an absent PVD, an absent terminator, a wrong descriptor
  version, an invalid root record, a record crossing a sector boundary, a record too short to be
  one, an odd-length Joliet identifier, a surrogate UCS-2 unit, a System Use Area with SUSP but no
  RRIP, a nonzero SUSP skip, a continued `NM`, and a record naming another volume of a set.

  `a_joliet_escape_later_in_the_field_is_recognized` was rewritten rather than preserved: it now
  asserts the refusal, because the layout it pinned is one Joliet does not produce.

  What is left is the part with no generator here: golden images from `xorriso` and `genisoimage`.
  This reader has still never been pointed at an image this repository did not write, and every
  fixture correction this milestone forced - a terminator with no version, records with no volume
  sequence number, exFAT's terminator next door - is an argument for having one.

## Reopened: the directory half was repaired and the file half was described

A second audit - 2026-08-12, against this tree at `fcb821b` - reading the implementation rather than
the checklist. Every claim below was checked against the code first, and one was settled by
compiling the crate rather than by reasoning about it.

The directory work deserves its reputation. `for_each_record` reading a sector at a time is a
change of shape, not a patch, and it closed the enormous temporary buffer and the record-crossing-a-
sector-boundary check with one idea. `both32`/`both16` comparing halves, the PVD requirement, the
mandatory terminator, the descriptor version, the strict root record, `checked_add` on the XAR skip
and `case_sensitive` per namespace are all straightforwardly right. So is rewriting the Joliet test
that had been confirming the wrong reading rather than keeping it green.

What follows is what the checklist counted as closed and the code does not do.

### The whole-file allocation is unchanged

```
let mut out = vec![0u8; size as usize];
```

`src/fs/iso9660/src/lib.rs:372`. `size` comes off the medium, up to `u32::MAX`, and the bound above
it (`src/fs/iso9660/src/lib.rs:369`) proves only that the extent lies inside the declared volume -
not that four gigabytes may be allocated to hold it. The allocation is also infallible, so a disc
that asks for more than the service has does not get an error, it takes the service down.

This milestone's first finding is the multi-gigabyte allocation, and its own status admitted the
chunked-read half was not done while the header above the crate says a hostile disc "never crashes
or exhausts the mounting service". `StorageService` compounds it: `self.fs.read_file(...)` returns
the whole file as a `Vec` (`src/user/services/storage/src/service.rs:1514`), so the whole-file shape
goes all the way up.

- [x] **A ceiling and a fallible allocation, today.**

  DONE 2026-08-12: `MAX_READ_BYTES` is 64 MB, a file past it is `TooLarge` - which `fs-core`
  documents as "the answer does not fit in one buffer; a ranged read is the solution", which is
  exactly the state of affairs - and the buffer itself goes through `try_reserve_exact`, so an
  allocation the service cannot make is `NoMemory` rather than an abort.
- [x] **A ranged read after it.** `read_file_into(offset, buffer)` or the streaming volume API, so
  the size of a file stops being the size of an allocation. The directory half proved the shape
  works; the file half is the same idea applied to the other reader.

  DONE 2026-08-12. `read_file_into(path, offset, buffer) -> Result<usize, FsError>` reads through one
  scratch sector rather than a whole-file allocation, so the size of a file stops being the size of
  an allocation and the caller says how much it is willing to take. A short answer is end of file
  rather than an error, which is what a caller looping over a large file needs.

  `read_file` keeps its ceiling and stays the whole-file shape, because most callers want it and the
  ceiling is what makes "a hostile disc never exhausts the mounting service" true for them.

### Rock Ridge is negotiated by finding two bytes

The SUSP half is right: `susp_skip_of(sys)` validates the `SP` entry and yields the skip offset. The
next line is not:

```
rrip = sys.windows(2).any(|w| w == b"ER");
```

`src/fs/iso9660/src/lib.rs:189`. Any occurrence of `E` followed by `R` anywhere in the system-use
area - inside another extension's payload, inside a name, inside padding - announces Rock Ridge. An
`ER` entry has a structure: length, version, `LEN_ID`, `LEN_DES`, `LEN_SRC`, extension version, then
the identifier, and it is the IDENTIFIER that says which extension is present. None of that is read.

The fixture added for this proves the point rather than the fix. `src/fs/iso9660/src/tests.rs:425`
appends

```
[b'E', b'R', 8, 1, 1, 0, 0, 0]
```

an entry declaring `LEN_ID = 1` inside a total length of 8 - which is exactly the header, so the
identifier it promises does not exist. It carries no `RRIP_1991A`, no identifier of any kind, and it
is internally inconsistent. The parser turns Rock Ridge on for it.

So the finding moved from "the parser guesses that data is Rock Ridge" to "the parser checks SUSP
and then guesses". That is progress and it is not the finding closed.

- [x] **One SUSP entry iterator, and read `ER` through it.**

  DONE 2026-08-12: `for_each_susp` walks `sig(2) len version body` and stops at `ST`, at a length
  below the header, or at one that runs past the area. `announces_rockridge` reads `ER`'s `LEN_ID`,
  requires the identifier to BE there rather than merely be declared, and compares it against the
  RRIP versions this reader implements.

  `NM`, `CE`, `CL`, `PL` and `RE` still have their own scan; moving them onto the iterator is the
  remaining half and is not needed for the negotiation to be right.
- [x] **Rewrite the fixture to be a real `ER`**, and add a negative one.

  DONE 2026-08-12. The fixture was `[b'E', b'R', 8, 1, 1, 0, 0, 0]` - a declared identifier length of
  one inside a total length of eight, which is exactly the header, so the identifier it promised did
  not exist. It is now a real `ER` carrying `RRIP_1991A`, and the builder takes the identifier as a
  parameter so `an_er_this_reader_does_not_implement_does_not_turn_rock_ridge_on` can announce
  `XA_SOMETHING` and assert the ISO identifier stands.

  It moved a third test on the way, and the fix there is worth keeping: `a_nonzero_susp_skip_is_honoured`
  located `SP` by arithmetic - `root + dot_len - 15`, encoding "ER is 8 bytes and SP is 7" - so a
  real `ER` broke a test that is about neither length. It searches for `SP` now.

### A record's semantic failures are still indistinguishable from "not a record"

`parse_record` returns `Option<Entry>` (`src/fs/iso9660/src/lib.rs:453`) and both callers write
`if let Some(e) = parse_record(...)` (`src/fs/iso9660/src/lib.rs:263`, `:282`). Inside it, every
check that fails uses `?`:

- both-endian halves disagreeing on the extent or the size,
- the XAR skip overflowing the extent,
- a Volume Sequence Number other than 1,
- a Joliet identifier of odd length or containing a surrogate.

All of them produce `None`, and `None` means the entry is skipped. So `list()` returns a SHORT
listing and reports success, and `find_entry` answers `NotFound` for a file whose record is present
and damaged. That is the original finding - a corrupt directory becoming a missing file - closed for
the record's outer length and still open for everything inside it.

- [x] **`Result<Option<Entry>, FsError>`.**

  DONE 2026-08-12, and it moved two tests, which is the change being real. Both had asserted the
  skipping: one built a record with `id_len == 0` and expected it to be absent from the listing, the
  other a record naming volume 2 and expected the same. Both now make the directory `Corrupt`,
  because a listing that quietly omits what it could not read reports success over a directory it
  did not read - which is the finding, in its smallest form.

  `id_len == 0` is refused with them: a record with no identifier is malformed, and it was the
  example the milestone used for "the strict parser still tolerates some dubious shapes".

### Multi-volume is refused by one check out of three

The crate header states multi-volume sets are outside the implemented subset and refused
(`src/fs/iso9660/src/lib.rs:23`). What enforces it is a single line in `parse_record`:
`if both16(&rec[28..32])? != 1` (`src/fs/iso9660/src/lib.rs:468`).

Two places do not ask. `root_extent` validates the root record's length, directory flag, identifier,
both-endian extent and size, and the XAR overflow (`src/fs/iso9660/src/lib.rs:422`) - and not its
Volume Sequence Number. And nothing anywhere reads the Volume Set Size out of the PVD.

- [x] **Check the volume set at the descriptor, and the root's own sequence number.**

  DONE 2026-08-12: the PVD's Volume Set Size is read and a set larger than one is refused at mount,
  and `root_extent` checks the root record's own sequence number - the one record that decides where
  the whole namespace begins, and the only one that was exempt from the rule every other record
  obeyed. `a_multi_volume_set_is_refused_at_the_mount` covers both.

### The device that reads the discs cannot read more than one block

`read_extent` calls `read_blocks` for the whole contiguous run and the comment beside it says a
contiguous extent is one device round trip (`src/fs/iso9660/src/lib.rs:373`). The default
`read_blocks` in `fs-core` is a loop over `read_block`, and `IsoBlockDevice`
(`src/user/services/storage/src/service.rs:2414`) implements `read_block` only. So behind the IPC
block device the storage service hands over, a thousand-block extent is still a thousand messages.

This is the same defect as the one recorded in [P02M0124](P02M0124.md) for `UdfBlockDevice`, in the
same file, and both should be fixed together.

- [x] **Implement `read_blocks` on `IsoBlockDevice`**, chunked to the block service's maximum request
  size, so the batching the reader already asks for exists somewhere.

  DONE 2026-08-12, for both optical backends at once - they are the same defect in the same file.
  `read_blocks_chunked` issues one `block_read` per 64 logical blocks (128 kB), so an extent that
  was a thousand messages is now sixteen.

  Chunked rather than passed through whole, and the reason is on the other side of the channel: the
  driver's `Span::fit` GROWS its DMA buffer to whatever a request asks for, so handing it a
  hundred-megabyte extent asks it to allocate one. 64 blocks is a large win over a block at a time
  and a size the driver was already sized for.

### The listing is bounded per record and not in aggregate

`read_dir` no longer allocates the extent, which was the finding. It does still build a
`Vec<FileInfo>` with an owned `String` per entry, and `StorageService` copies that into a listing of
its own. `try_reserve` makes the growth fallible, which is the right half; what is missing is any
bound on how much a hostile directory may legitimately ask for before the failure.

- [x] **Bound or page the listing.**

  DONE 2026-08-12 by the first: `MAX_DIR_ENTRIES` is 65536 and a directory past it is `TooLarge`.
  Paging is the better answer and is a read-API design rather than a bound; the bound is what makes
  the header's sentence true today.

### The tidying, one of which the compiler is already complaining about

- [x] **`le32` is dead, and it warns.**

  DONE 2026-08-12: removed, and the crate now builds with ZERO warnings - measured the same way the
  finding was.
- [x] **Two stale comments, and both were created the same way.**

  DONE 2026-08-12: in both places the stale half is gone and the accurate one stands alone. The
  pattern is worth naming for next time - a new explanation added BELOW an old one leaves the file
  asserting both, and the stale half is the one a reader meets first.
- [x] **A record with `id_len == 0` is skipped rather than refused.**

  DONE 2026-08-12 with the `Result` change, which is what made it expressible.

### Still deliberately open

Golden images from `xorriso` and `genisoimage` remain the one piece this milestone left on purpose,
and the reasoning holds. It is worth noting what the `ER` fixture above demonstrates: an independent
mastering tool writes a real `ER` with a real identifier, so a golden image is the test that would
have refused to agree with the two-byte scan. The two items reinforce each other.

- [x] **A golden image from an independent tool**, listed and read back, with Rock Ridge names
  compared against what the tool was told to write.

  DONE 2026-08-12, and IT FOUND A LIVE DEFECT ON ITS FIRST RUN - which is the whole argument for
  golden images, made by the thing itself rather than by this document.

  `an_image_from_an_independent_tool_lists_and_reads_back` masters an ISO with `xorriso -as mkisofs
  -rational-rock`, mounts it, and asks for `A-Long.Name.txt` and `sub/nested.txt`. It came back
  `["A_LONG_N.TXT", "SUB"]`: Rock Ridge was not on.

  The reason is the one this milestone predicted in shape and not in detail. `announces_rockridge`
  scans the root record's OWN system-use area, and a directory record is 255 bytes - `SP`, `PX` and
  `TF` fill it, so SUSP puts a `CE` Continuation Entry there and the `ER` naming `IEEE_P1282` goes
  in the block it points at. Every disc a real mastering tool produces looks like that. The
  synthetic fixtures put `ER` in the record because the parser read it there, which is the
  fixture-and-parser agreement this project has now been bitten by in three different filesystems.

  `continuation_of` follows the chain, bounded to four hops with the offset and length checked
  against the block, and the test also exercises `read_file_into` over the same real file.

  `genisoimage` is not installed on this machine, so the second tool is still not covered; the test
  skips LOUDLY rather than passing when `xorriso` is absent.

### Order

The fallible allocation with a ceiling first: it is the smallest change here and it is the one that
turns a documented crash into an error.

Then `parse_record` returning a `Result`, because three other items - the zero-length identifier,
the multi-volume checks and the honest short-listing behaviour - are all expressible only once it
does.

Then the SUSP iterator and real `ER` parsing, with its fixture rewritten and a negative case added.

Then `read_blocks` on `IsoBlockDevice`, together with the identical item in
[P02M0124](P02M0124.md).

Then the volume-set checks, the listing bound, and the ranged read.

The dead function and the two doubled comments at any point - the `le32` one first, since something
is already telling us about it on every build.

## Reopened again: the new code is where the new findings are

A third audit, against this tree at `8df720c` - 2026-08-12. Eight findings, every one read in the
code first. Two places where the audit named a symptom are extended here to what this file already
says about it, because in both the comment beside the defect is either the argument for the fix or a
statement that is no longer true.

The audit's own conclusion was that these belong in a new hardening milestone rather than here. They
are recorded here instead, and the reason is the pattern: five of the eight are in code this
milestone ADDED. `read_file_into`, `continuation_of` and `announces_rockridge` are all deliverables
of the reopened round, and each is missing a check the reader already performs elsewhere. That is not
a new surface; it is this milestone's own work, one layer in.

What the round genuinely closed stays closed and is listed at the end so the next audit does not
re-derive it.

### The ranged reader does not bound the extent its whole-file sibling bounds

`read_extent` opens with the check that makes a forged size safe
(`src/fs/iso9660/src/lib.rs:478`):

```rust
if lba as u64 + (size as u64).div_ceil(SECTOR_SIZE as u64) > self.geo.blocks as u64 {
    return Err(FsError::Invalid);
}
```

`read_file_into` (`:294`) has no equivalent. It checks the block it is about to read
(`:316`) and nothing about whether the file's extent as a whole lies inside the volume.

So one record is invalid through one API and partially valid through the other. A volume of blocks
`0..22` with a file at LBA 22 declaring 4096 bytes needs blocks 22 and 23 and is refused by
`read_file`; `read_file_into(path, 0, &mut [0u8; 1])` returns the first byte of block 22 as success.

The reader's own rule is that a record describing something outside the volume is corrupt, decided
once, before anything is read. The ranged path decides it per block, which is a different rule.

- [ ] **One extent validator, called by every path that trusts an extent.**
  `validate_extent(lba, size)` used by `read_extent`, `read_file_into` and the directory walk, so the
  answer to "is this record inside the volume" cannot depend on which entry point asked.

- [ ] **A test that reads the same over-running file both ways** and asserts both refuse. One API
  answering `Invalid` and the other answering `Ok(1)` for one record is the assertion.

### The SUSP continuation reads one half of a both-endian pair, and says that is what the reader does

`continuation_of` (`src/fs/iso9660/src/lib.rs:776`) reads CE's block, offset and length with a local
little-endian closure (`:782`), leaving the big-endian copies at `body[4..8]`, `[12..16]` and
`[20..24]` uncompared.

The comment above it (`:774`) explains the choice: "The fields are both-endian pairs; the
little-endian half is read, like every other both-endian field in this reader."

That sentence is false. `both32` and `both16` (`:850`, `:857`) return `None` unless the two halves
AGREE, and they are used at eight call sites - the volume block count, the logical block size, the
volume set size, the root extent and size, the root's volume sequence number, and an ordinary
record's extent, size and sequence number. Reading one half is what this reader does NOWHERE else.

The consequence is a pointer: a disc whose CE says block 42 little-endian and `0xFFFFFFFF`
big-endian is followed to block 42 with no disagreement noticed, and what is read there decides
whether Rock Ridge is announced and therefore what every file on the disc is called.

- [ ] **Use `both32` for all three CE fields,** and refuse the continuation when a pair disagrees -
  which is what `for_each_susp`'s callback can already express by leaving `found` unset.

- [ ] **Delete the sentence in the comment,** or replace it with the true one. A comment that
  justifies a weaker check by claiming it is the house style is worse than no comment: it tells the
  next reader not to look.

### The `ER` parser is strict about the identifier and about nothing else

`announces_rockridge` (`:800`) is a real improvement over the two-byte scan it replaced: it reads
`LEN_ID`, requires the identifier to be present rather than merely declared, and compares it against
the three extension names this reader implements.

What it does not read is the rest of the entry. `ER` is `LEN_ID, LEN_DES, LEN_SRC, EXT_VER` and then
the identifier, description and source in that order; `body[1]`, `body[2]` and `body[3]` are never
looked at, and neither is whether the description and source the entry declares are actually there.
So an `ER` carrying `RRIP_1991A` and nonsense in every other field switches the whole disc's name
source.

The same gap is one level down. `for_each_susp` (`:754`) reads a signature and a length and hands the
callback `sys[at + 4..at + len]` - so the SUSP entry VERSION at `sys[at + 3]` is skipped rather than
validated, for `ER`, `CE`, `NM` and `SP` alike. `susp_skip_of` checks `SP`'s magic bytes and its skip
value and not its version either.

- [ ] **One strict SUSP entry parser.** `SuspEntry { signature, version, body }`, with the version
  checked against the version this reader implements, and `SP`, `ER`, `CE` and `NM` built from it.
  The walker exists; what it hands out should be a validated entry rather than a slice.

- [ ] **Validate `ER`'s declared lengths against its body:** `4 + LEN_ID + LEN_DES + LEN_SRC` must
  fit, or the entry is malformed and announces nothing.

### A malformed SUSP entry can still produce a partial Rock Ridge name

`rock_ridge_name` (`:690`) makes the fail-closed argument itself, and makes it well (`:703`): "FAIL
CLOSED on what this parser cannot follow, rather than answering with a different name than the medium
records... Falling back to the ISO9660 identifier is a name the medium really carries; a truncated
`NM` is not."

Two paths through the same function produce exactly that truncated `NM`:

- A malformed entry mid-walk - `len < 4`, or a length running past the area - `break`s the loop
  (`:699`). If an `NM` was already accumulated, `Some(out)` is returned at `:731`, and it is a prefix.
- An `NM` whose payload is not UTF-8 goes through `unwrap_or("")` (`:727`), contributing nothing and
  leaving whatever the other fragments held.

`CE`, `CL`, `PL`, `RE` and a continued `NM` all `return None` for precisely this reason. A structurally
broken area is the same case and takes the other branch.

- [ ] **`return None` on a malformed entry and on non-UTF-8,** so the fallback to the ISO9660
  identifier happens for every reason the name cannot be trusted rather than for the five that were
  enumerated.

- [ ] **A test per path**: a truncated SUSP entry after a valid `NM`, and an `NM` carrying invalid
  UTF-8, each asserting the 8.3 identifier is what comes back.

### The ranged reader has no caller, so a large file on a legitimate ISO cannot be opened

`MAX_READ_BYTES` at 64 MiB with a fallible allocation is the right security answer, and
`read_file_into` is the right way to lift it. `grep -rn read_file_into src/user/services/storage`
returns nothing: StorageService opens ISO files through `read_file`, so a 100 MiB file on an install
medium answers `TooLarge` through `vol://iso` while the backend beneath it can read it perfectly.

For a reader whose stated subject is optical and install media, that is a size an ordinary disc
carries.

- [ ] **Route the ISO volume's reads through `read_file_into`** in StorageService, in whatever
  chunking its reply path already uses for other backends, so the ceiling bounds the WORKING SET
  rather than the file.

- [ ] **Then decide what `MAX_READ_BYTES` is for.** With a ranged path in production it becomes the
  bound on a single whole-file convenience call rather than on the volume's contents, and saying so
  where it is defined is what stops it being raised for the wrong reason later.

### Three smaller ones

- [ ] **A Volume Set Size of zero passes.** `if set_size > 1 { return None }` (`:163`) admits `0`,
  which is not a legal set size. The check is at the right place - at mount, before anything is read,
  as its comment argues - and it should be `!= 1`. The PVD's own Volume Sequence Number is not
  checked at all, while the root record's and every ordinary record's are (`:556`, `:612`).

- [ ] **The padding byte after an even-length File Identifier is not required.** `sys_off` is
  computed as `33 + id_len + padding`, and a record ending immediately after an even-length
  identifier simply has no System Use Area rather than being malformed. A regression test currently
  builds exactly that record and expects the name to parse. Memory safety is not at stake; the strict
  reading is.

- [ ] **The golden test passes when the tool is absent.** `xorriso_image` returns `None` and
  `an_xorriso_image_is_read` returns (`src/fs/iso9660/src/tests.rs:677`), printing `SKIPPED` and
  counting as a pass. `xorriso` IS installed on this machine, so the test runs today - and nothing
  guarantees it runs on the next one. A conformance gate whose absence is indistinguishable from its
  success is the shape this tree has a check-script gate for elsewhere; the tool belongs in the
  environment and its absence belongs in the failure column. `genisoimage` as a second masterer is
  the same item and is not installed.

### Confirmed and staying closed

Not to be re-derived. `parse_record` returning `Result<Option<Entry>, FsError>`, with `Ok(None)`
reserved for the associated file it deliberately ignores and every structural fault becoming
`Corrupt` - the change that removed the whole "corruption looks like a missing entry" class.
`id_len == 0` as corruption. The 64 MiB ceiling with `try_reserve_exact` on the whole-file path.
`MAX_DIR_ENTRIES` and a fallible outer vector. The root record's volume sequence number. Rock Ridge
announced by a real `ER` identifier rather than by two bytes, and found through a `CE` chain, which
is what a real mastering tool actually writes - the finding the xorriso fixture earned its place by
producing. `IsoBlockDevice::read_blocks` going through `read_blocks_chunked`, sixty-four blocks per
request, which was API-only last round and is integrated now. `le32` and the contradictory comments,
gone.

The `.`/`..` contract drift with `fs-core::validate_name_segment` is unchanged and stays open as a
question for fs-core rather than for this backend: ISO resolves `SUB/..` and the shared validator
calls `..` malformed. One of the two is wrong and deciding which is not this file's call.

### Order

The extent validator first: it is one helper and two call sites, and it is the only finding here
where two APIs disagree about whether a record is valid.

Then the CE both-endian read, which is three `both32` calls and a comment deletion, and which decides
what every file on a Rock Ridge disc is called.

Then the strict SUSP entry, which subsumes the `ER` lengths and the version checks and should be done
once rather than per entry type.

Then `rock_ridge_name`'s two remaining partial-name paths.

Then the StorageService ranged read, which is the largest and is product work rather than hardening.

The volume-set zero, the padding byte and the golden-test gate at any point.
