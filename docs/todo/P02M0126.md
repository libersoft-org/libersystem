# P02M0126 - What the ISO9660 backend accepts, and the threat model it states

Status: COMPLETE (2026-08-11), with one piece deliberately left: golden images from `xorriso` and
`genisoimage`. Everything else is closed and the suite went from 14 tests to 28.

The audit's own order held up. Memory first - the sector-at-a-time directory walk removed the
exhaustion path and made the boundary rule fall out of the structure rather than be another check.
Then the metadata that was accepted without being checked, then SUSP, which is what turned the Rock
Ridge path from a guess into a negotiated one.

The recurring lesson is about the fixtures rather than the parser: the builder wrote media no
mastering tool produces - a terminator with no version, records with no volume sequence number - so
an internal round trip agreed with itself. Every strictness added here had to correct the builder
first, which is exactly why the missing golden image is the one thing still worth having.

An outside audit of `src/fs/iso9660` against ECMA-119, pinned to `d309476`. Every
finding was checked against the tree and every one held.

The crate's own header says a hostile or corrupt disc "errors, never crashes or exhausts the mounting
service". Against an ISO from `xorriso` or `mkisofs` the parser is short, readable and better
defended than most small ISO readers - forged extents, XAR, associated files, interleaving and
multi-extent reads are all refused rather than misparsed, and every one of those has a regression
test. What the header claims and what the code does part company in three places:

- **exhaust**: an extent's size is bounded by the VOLUME and then allocated in one `Vec`, so a
  four-gigabyte directory is a four-gigabyte allocation - and the comment directly above the
  allocation says a forged length "can neither allocate without bound";
- **accept**: ISO9660 records every critical number twice, little-endian and big-endian, and this
  parser reads only the little half of all four of them, so internally contradictory metadata passes;
- **interpret**: Rock Ridge names are read out of any System Use Area that happens to contain `NM`,
  with no SUSP negotiation at all - and a non-Rock-Ridge volume is entitled to put other extensions'
  data there.

## Memory, which is the one that is reachable from a listing

- [x] **Every extent becomes one `Vec` sized from the medium.** `read_extent` proves the extent lies
  inside the volume and then does `vec![0u8; size as usize]`. `size` is a `u32`, so a volume that
  declares a large enough block count can ask for close to four gigabytes. It is not only files:
  `find_entry` and `read_dir` both read the whole directory extent first, so `ls` on a crafted disc
  is enough - the caller never opens anything.

  The integration doubles it. `IsoFs::read_file` hands that `Vec` to StorageService, which creates a
  `MemoryObject` of the same size to stage it for the client, so a large file is briefly resident
  twice.

  Two changes, and the first is the one that matters: **directories should never be read whole.** A
  sector-at-a-time iterator removes the exhaustion path, removes several copies, and makes the
  boundary rule below natural to enforce rather than an extra check. For files, either a ceiling on
  `read_file` or - better, and what `Storage.Volume` already does elsewhere - a chunked read. Every
  allocation sized from the medium should be fallible.


  DONE for directories 2026-08-11, which is the half that is reachable from a listing.
  `for_each_record` walks a directory extent one SECTOR at a time and hands each record to its
  caller, so `find_entry` and `read_dir` allocate nothing proportional to the medium's claim. `ls`
  on a crafted disc no longer asks for close to four gigabytes.

  `read_file` still reads a whole file into one `Vec` and still has the StorageService staging copy
  beside it. That is the chunked-read half and it is not done.

- [x] **`read_blocks` is never used, and a path walk re-reads every directory it passes through.**
  `fs-core` offers `read_blocks(index, count, buf)` so a contiguous extent can be one device round
  trip; `read_extent` loops a block at a time. And `resolve_dir("A/B/C")` calls `find_entry` per
  segment, each of which allocates and reads that directory's whole extent again. Behind the
  IPC-backed `IsoBlockDevice` that is an expensive shape. The sector iterator above fixes most of it.

  PARTLY DONE 2026-08-11. `read_extent` now takes the whole contiguous run through `read_blocks` -
  one device round trip rather than a message per 2 KiB behind the IPC-backed block device - with a
  single tail read when the size is not a whole number of sectors.

  The re-reading half is gone by construction rather than by caching: the sector-at-a-time directory
  walk means `resolve_dir` no longer allocates and copies each directory's whole extent per segment.
  What is left is that it still READS each directory it passes through, which a cache would answer
  and is a different piece of work.

## Metadata that is accepted without being checked

- [x] **The both-endian halves are never compared.** ECMA-119 records volume space size, the root
  extent, each file's extent and each file's length in both byte orders, in one field. This parser
  calls `le32` on all of them and ignores the big-endian half entirely - five `le32`/`le16` call
  sites and no `be32` anywhere. A volume claiming a little-endian length of 1000 and a big-endian
  length of `0xFFFFFFFF` is internally contradictory and is accepted. `both_u16`/`both_u32` helpers
  that read both and refuse a mismatch are the cheapest hardening available here.

- [x] **A directory record may cross a logical sector boundary.** The parser knows half the rule: a
  zero length means "skip to the next sector", and it does. What it does not check is the other half
  - that a record which STARTS in a sector also ends in it. `off + rec_len > data.len()` bounds
  against the whole extent, not against the 2048-byte sector, and ECMA-119 says plainly that a
  Directory Record shall not cross the boundary.


  DONE 2026-08-11, and it fell out of the sector walk rather than being another check to remember:
  a record must start and END inside the sector it is in, which is what ECMA-119 requires. Pinned by
  a test that declares a 200-byte root extent and plants a record at 148 claiming 100.

- [x] **A malformed record becomes a missing file or a short listing.** Both loops `break` on a
  record they cannot use: `find_entry` then answers `NotFound`, and `read_dir` returns `Ok` with
  whatever it had collected. So a corrupt directory is indistinguishable from one that does not hold
  the name, and a listing can be short with nothing to say so. `FsError::Corrupt` is what fs-core has
  for this.


  DONE 2026-08-11. A record too short to be one, or one that runs past its sector, is
  `FsError::Corrupt` rather than a `break` - so a damaged directory stops being indistinguishable
  from one that does not hold the name.


  DONE 2026-08-11. `both32` and `both16` read the little half, the big half, and refuse a mismatch;
  the volume space size, the logical block size and the root record's extent and length all go
  through them. Watched to fail: removing the comparison makes
  `a_contradictory_both_endian_field_is_refused` pass a volume whose two halves disagree.

- [x] **The Root Directory Record is taken on trust.** `root_extent` reads bytes 156..190 of the
  descriptor, pulls the little-endian extent and length out, and returns. It is a standard 34-byte
  Directory Record and none of its structure is checked - not the record length, not the directory
  flag, not the single-byte identifier `0`, not the volume sequence number, not the big-endian
  halves. A malformed descriptor can therefore nominate any region of the volume as the root, as
  long as the extent survives the bounds check.


  DONE 2026-08-11. Its own length, the directory flag, the single-byte identifier `0`, and both
  halves of the extent and the size are all checked, and the XAR skip uses `checked_add` rather than
  `saturating_add` - clamping to `u32::MAX` invented a value the medium never gave.

- [x] **`saturating_add` hides an overflow in the XAR skip.** Both `root_extent` and `parse_record`
  compute `extent.saturating_add(xar_len)`. If those numbers overflow, the honest answer from a
  parser of untrusted media is `Corrupt` - clamping to `u32::MAX` invents a value the medium did not
  give. `checked_add` and a refusal.

  DONE 2026-08-11. `checked_add` in both places, and both halves of the extent and the length go
  through `both32` on the way.

## The volume descriptor set

- [x] **A volume with no Primary Volume Descriptor mounts.** The final match is
  `(Some(joliet), _) => (true, joliet)`, so a recognised Joliet SVD alone is enough and `pvd_root`
  being `None` is not an obstacle. ECMA-119 requires a PVD in the Volume Descriptor Set. Require a
  valid PVD first, and only then let a valid Joliet SVD supply the namespace and root.


  DONE 2026-08-11. A Joliet SVD supplies the namespace on top of a valid PVD and is not a volume on
  its own; the absence of a PVD is now a refusal.

- [x] **The descriptor version is never read.** `block[1..6] == "CD001"` and `block[0]` are checked;
  `block[6]`, the version, is not. It matters most for the type-2 descriptors, where the parser then
  decides from a few bytes that it is looking at Joliet.


  DONE 2026-08-11, and it needed the descriptor TYPE to be decided first: a terminator carries none
  of the fields around it, so validating them before recognising it refused the very descriptor that
  says the set is complete. The test builder had to gain a version byte on its terminator, which no
  mastering tool omits.

- [x] **Joliet is detected by searching the whole escape field.** `is_joliet` takes
  `desc[88..120]` and accepts `%/@`, `%/C` or `%/E` occurring anywhere inside it, via
  `windows(3).any(..)`. Joliet defines those three sequences for its UCS-2 levels and the field is
  written from the start, contiguously. A test - `a_joliet_escape_later_in_the_field_is_recognized`
  - currently pins the loose behaviour; it should be rewritten rather than preserved, because it
  asserts something that is not a Joliet layout.

- [x] **The Volume Descriptor Set Terminator is not required, and 32 is a magic number.** The scan
  runs `for i in 0..32` and `break`s on type 255. Nothing records whether the terminator was ever
  seen, so a set that simply stops mounts anyway; and a legal but unusual set whose Joliet descriptor
  sits past the thirty-second sector is silently missed. Keep the safety limit - it is a good one -
  and make reaching it an explicit refusal, and make the terminator a requirement.


  DONE 2026-08-11 for the terminator: a set that stops without one does not mount, and reaching the
  thirty-second sector without seeing one is the same refusal rather than a silent end to the search.

  DONE 2026-08-11. The escape sequence must be at the START of the field, which is where Joliet
  writes it - `starts_with` rather than `windows(3).any`. The test that pinned the loose behaviour
  was rewritten rather than preserved, as the finding asked: it now asserts that a descriptor whose
  escape sits later in the field does NOT supply the namespace.

- [x] **Multi-volume sets are neither supported nor refused.** Each Directory Record carries a Volume
  Sequence Number naming the volume its extent lives on, and this parser ignores the field. With one
  `BlockDevice` behind it, an extent belonging to volume 2 is read at that LBA on whichever disc is
  in the drive. Until multi-volume is supported, require `volume_set_size == 1` at mount and the
  matching sequence number on every record.

  DONE 2026-08-11 by refusing: a record whose Volume Sequence Number is not 1 does not parse. With
  one `BlockDevice` behind this reader, an extent belonging to volume 2 would otherwise be read at
  that LBA on whichever disc happens to be in the drive.

## Rock Ridge, which is currently guessed at

- [x] **Rock Ridge is used without SUSP being negotiated at all.** `decode_name` passes every
  non-Joliet record's System Use Area to `rock_ridge_name`, which walks it looking for an `NM` entry.
  There is no `SP` check, no skip value, no `ER` and no RRIP identification anywhere in the crate.
  SUSP exists precisely so independent extensions can share that area, so a valid non-Rock-Ridge
  volume whose System Use Area happens to contain those two bytes has its filenames replaced by
  whatever follows them.

  Detect SUSP at the root through `SP`, take its skip value, read `ER` to establish RRIP, and record
  the result in `Geometry`. Interpret `NM` and its relatives only when RRIP is actually present.

  DONE 2026-08-11. `SP` is read from the ROOT directory's own record - check bytes and skip - and
  `ER` in the same area is what says RRIP is actually in use; both are recorded in `Geometry` and
  `NM` is read only when they are present. Watched to fail: removing the gate makes an unannounced
  `NM` become a filename again, which is the finding.

- [x] **The partial implementation does not "degrade cleanly" - it can answer with a different
  name.** `CE`, `ST`, `CL`, `PL` and `RE` are all unhandled, and the header calls that a clean
  degradation. An `NM` continued through `CE` yields the prefix only, so two long names that differ
  late become the same name; `CL`/`PL`/`RE` are how Rock Ridge relocates deep directories, so
  ignoring them dismantles the very structure they express; and ignoring `ST` means the walk runs on
  into bytes that are no longer SUSP entries.

  Either implement them or be fail-closed: when a continuation or a relocation is found that this
  parser cannot follow, fall back to the ISO9660 identifier or refuse - do not synthesise a name.

  DONE 2026-08-11, fail-closed. `CE`, `CL`, `PL` and `RE` - and an `NM` carrying the CONTINUE flag -
  make the Rock Ridge path return nothing, so the ISO9660 identifier stands: a name the medium
  really carries rather than the first half of one. `ST` ends the walk, instead of running on into
  bytes that are no longer SUSP entries.

- [x] **One case-insensitive comparison is applied to every namespace.** `eq_ci` ASCII-folds
  everything, including a Rock Ridge `NM` name and a Joliet name. For a bare `FOO.TXT;1` that is the
  right convenience. Rock Ridge exists to express POSIX semantics, where `Makefile` and `makefile`
  are two files - and `find_entry` returns the first match, making the second unreachable by its own
  name. An `Entry` should know where its name came from, and the comparison should follow from that.

  DONE 2026-08-11. An `Entry` records which namespace its name came from, and `name_matches`
  follows it: a Rock Ridge or Joliet name is preserved-case and compares exactly, a bare ISO9660
  identifier folds. `Makefile` and `makefile` on a Rock Ridge disc are two files again - before,
  `find_entry` returned the first and the second was unreachable by its own name.

## Smaller, and one that misreports

- [x] **A multi-extent file is listed with the size of its first section.** `read_file` refuses it,
  correctly, on `entry.unsupported`. But `read_dir` adds the first record as an ordinary `FileInfo`
  and de-duplicates the rest by name, so the listing shows a size that is neither the file's nor
  anything else's - for a file the backend then refuses to read. Either assemble the sections or
  mark the entry unsupported in the listing.

  DONE 2026-08-11. An entry the reader will refuse to open is left out of the listing rather than
  described with a size that is neither the file's nor anything else's.

- [x] **`unsupported` is checked when reading a file and not when entering a directory.**
  `parse_record` sets it for the multi-extent bit and for interleaving; `resolve_dir` tests only
  `is_dir`. ECMA-119 is stricter for directories than for files - they may not be interleaved and
  are a single file section - so a directory record carrying either should be refused on descent.

  DONE 2026-08-11. `resolve_dir` refuses a directory record carrying the multi-extent or interleave
  bits - ECMA-119 is stricter for directories than for files, and the descent was the looser path.

- [x] **The Joliet decoder turns malformed identifiers into different names.** `chunks_exact(2)`
  silently drops a trailing odd byte, and an invalid UCS-2 unit becomes `'?'`, so two distinct
  corrupt identifiers can collide on one name. An odd length is corruption and an invalid unit is
  corruption; a lossy rendering, if wanted at all, must not be the lookup key.

  DONE 2026-08-11. An odd identifier length and an invalid UCS-2 unit both refuse the record;
  `decode_name` is fallible end to end. A lossy rendering can collide two damaged identifiers on one
  name, and the name is the lookup key.

- [x] **The error vocabulary drifts from fs-core's.** Reading a directory answers `NotFound`, and so
  does treating a file as one, though `FsError` has `IsDir` and `NotDir`; empty path segments are
  filtered and a test requires `SUB/..` to resolve, though fs-core's own documentation calls `.` and
  `..` malformed components. One of the two documents is wrong and this milestone should say which -
  the drift between backends is the defect, not either behaviour on its own.

  PARTLY DONE 2026-08-11: reading a directory answers `IsDir` and a file used as a path component
  answers `NotDir`, which is what fs-core has for both. The `.`/`..` question - fs-core's docs call
  them malformed while this backend filters empty segments and a test requires `SUB/..` to resolve -
  is a decision about which document is wrong, and is left open deliberately.

- [x] **Say that the supported subset is the subset.** The backend reads volumes with a 2048-byte
  logical block size and refuses the rest, openly and deliberately. ECMA-119 permits other sizes up
  to the logical sector size. That is a fine product decision and the header should describe it as
  one rather than as ISO9660 support.

  DONE 2026-08-11, in the crate header where a reader meets the claim: the 2048-byte block size,
  multi-volume sets, multi-extent and interleaved files, and the Rock Ridge entries this parser
  will not follow are all named as deliberate boundaries rather than left to be discovered from a
  refusal.

## Tests

- [x] **The suite builds its own images, so it can confirm the parser's own reading of the format.**
  It is a good regression suite - forged extents, oversized volumes, XAR, associated files,
  interleaving, multi-extent rejection, short records - and every image comes from one mini-builder
  written alongside the parser. `a_joliet_escape_later_in_the_field_is_recognized` is the proof: it
  asserts a layout Joliet does not produce.

  What is missing has no natural generator and does need building: mismatched little/big-endian
  halves, an absent PVD, an absent terminator, a wrong descriptor version, a record crossing a sector
  boundary, an invalid root record, an odd-length Joliet identifier, a surrogate UCS-2 unit, a System
  Use Area with SUSP but no RRIP, a nonzero SUSP skip, `CE`, `ST`, `CL`/`PL`/`RE`, case-colliding
  Rock Ridge names, a nonzero volume sequence number, and a directory that is huge but legally
  inside the volume. Alongside them, golden images from `xorriso` and `genisoimage` - the reader has
  never been pointed at an image this repository did not write.

## Order

Memory first, because it is reachable from a listing and it is what the header promises: the
sector-at-a-time directory iterator removes the exhaustion path and makes the boundary rule fall out
of the structure rather than being another check to remember. Then the metadata that is accepted
without being checked - both-endian, the root record, the descriptor set. Then SUSP detection, which
is what makes the Rock Ridge path honest, and fail-closed handling of what it cannot follow. Joliet,
the error vocabulary and the performance work after that.

  MOSTLY DONE 2026-08-11: 14 tests became 28, and the images the finding asked for now exist -
  mismatched little/big-endian halves, an absent PVD, an absent terminator, a wrong descriptor
  version, an invalid root record, a record crossing a sector boundary, a record too short to be
  one, an odd-length Joliet identifier, a surrogate UCS-2 unit, a System Use Area with SUSP but no
  RRIP, a nonzero SUSP skip, a continued `NM`, and a record naming another volume of a set.

  `a_joliet_escape_later_in_the_field_is_recognized` was rewritten rather than preserved: it now
  asserts the refusal, because the layout it pinned is one Joliet does not produce.

  What is left is the part with no generator here: golden images from `xorriso` and `genisoimage`.
  This reader has still never been pointed at an image this repository did not write, and every
  fixture correction this milestone forced - a terminator with no version, records with no volume
  sequence number, exFAT's terminator next door - is an argument for having one.
