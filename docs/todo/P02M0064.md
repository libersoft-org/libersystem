# P02M0064 - FAT: seventh-pass findings (the ValidDataLength read rule)

Status: COMPLETE. The seventh full source pass (2026-07-04). One real read-side interop rule.

*Condensed 2026-08-08.*

**Reads ignored the exFAT ValidDataLength and served the full DataLength off the disk** - but the
range between them is **undefined on disk by specification**, and Windows serves it as zeros. A file
Windows legitimately wrote with a preallocated tail (SetEndOfFile, download managers) read back with
stale cluster content instead: wrong bytes for the application, and **a stale-data disclosure** - the
tail can hold content of files deleted by another owner of the medium.

Our own writes set the two equal, so only foreign media were affected. Reads now take
`min(VDL, size)` off the disk and zero-fill to size, on both the chained and the contiguous path,
with the tail bounded by the cluster heap so a forged DataLength cannot inflate the read.

**A chained exFAT directory was read by its whole FAT chain, ignoring its recorded DataLength** -
Windows reads by the record. Where the two disagree on foreign media we saw entries Windows does not.
Bounded by the lesser of the two now.

Recorded rather than implemented: maintaining exFAT's `PercentInUse` would cost a boot-sector write
plus a boot-region checksum restamp per operation. The field is advisory and the spec allows an
"unknown" value, so the boot region is never rewritten and the trade-off is written down.

The delete-plus-create torn window inside one directory write is **inherent to unjournaled FAT** -
reference drivers share it - and stays by design.
