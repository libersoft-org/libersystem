# M134 - Incremental development and persistent QEMU test loop

Status: PRIORITY INFRASTRUCTURE MILESTONE, DELIVERED IN FOUR INDEPENDENTLY USEFUL PHASES.
Ordinary work on one leaf tool currently pays the cost of the whole system: a focused run
reassembles the volume package, restages the boot image, boots a fresh guest and prints
the complete build and boot transcript. This milestone removes that coupling in
increasing order of implementation cost, so the cheapest reductions land first and no
phase has to wait for the one after it. M134a is a pure workflow-cost phase that changes
no system architecture and must not be blocked behind the later phases.

Two structural facts constrain the design and must be respected rather than rediscovered.
First, the staged artifact set reaches the guest differently per architecture: on x86_64
the init and volume packages are separate boot modules, while the aarch64 and riscv64
boot paths embed them into the kernel binary with `include_bytes!`. Any claim that an
artifact change avoids a kernel rebuild is therefore architecture-specific and must be
verified per target, not assumed. Second, application scenarios are compiled into the
kernel test binary today, so adding or fixing one is a kernel change by construction;
until that is undone, no build-cache work can make application iteration cheap.

The transport is a development-only channel on existing devices, not a filesystem. This
milestone does not implement or depend on virtio-fs. The planned development-only
virtio-fs volume may later expose host files and large test data through StorageService,
but executable replacement continues to use the validated artifact publication protocol
below. No 9P, SMB, NFS, FTP or ambient host-directory mount is introduced. A host-writable
disk shared with a live guest filesystem is rejected outright: concurrent host and guest
writes to one mounted image corrupt it.

## M134a - Immediate cost reduction, no architecture change

- [x] Make successful runs quiet and failures informative. The kernel test driver
  currently prints the full cargo transcript and the full guest boot log on every run,
  including successful ones, which is the single largest source of per-iteration output.
  Write both transcripts to named files under `.build` and print, on success, only the
  tag selection, pass and fail counts and total time; on failure print the failing test,
  its diagnostic block and a bounded tail. Add `--verbose` for the full stream. Set and
  enforce an explicit budget: a successful focused run emits at most a few dozen lines
  and never a complete boot transcript.
  Result: `test-kernel.sh` now retains cargo and guest transcripts under
  `.build/test-logs`, prints a two-line mode and result summary on success, accepts
  `--verbose` for complete transcripts, and emits at most the configured bounded tail of
  each relevant log on failure. Focused validation covered a successful build-only run,
  a seven-test x86_64 QEMU run and a forced timeout preserving exit status 124.
- [ ] Cap test-mode parallelism on x86_64. Test runs default to the host core count, so a
  large host emits one bring-up line per core on every boot and pays bring-up cost that
  the already capped aarch64 and riscv64 runs show is unnecessary for ordinary coverage.
  Default focused x86_64 test runs to a small fixed core count, keep an explicit
  override, retain one high-core-count configuration in the checkpoint suite so SMP
  scaling stays covered, and collapse per-core bring-up reporting into one summary line
  at the default log level.
- [ ] Reduce per-artifact chatter in the build and validation recipes. The shared-image
  builder, format check, manifest check and hygiene check print one line per crate or
  artifact even when nothing was rebuilt. Print per-item lines only for items actually
  rebuilt or failing, otherwise a single summary with counts and cache hit and miss
  totals, with full detail behind `--verbose`.
- [ ] Fold generated dynamic-report regeneration into the ordinary path. Adding or
  removing a governed executable changes the checked provider and consumer reports, which
  currently surfaces later as a separate failing check after the expensive work is done.
  Detect the drift during the shared-image build, name the exact refresh command, and
  keep the committed reports authoritative at checkpoints.
- [ ] Establish a reproducible baseline before the later phases change anything. Add one
  timed command that records source hashing, Cargo compilation, provider linking,
  consumer linking, ELF/identity audit, system-image staging, package/image assembly,
  kernel compilation, QEMU startup, guest boot, scenario execution and shutdown
  separately. Capture cold, warm-no-change, one-leaf-tool edit and one-shared-provider
  edit on the documented x86_64 QEMU/KVM host. Record output volume per run as well, so
  the budget above is measured rather than assumed. Store machine-readable samples under
  `.build` and a concise table in `docs/PERF.md`; do not infer optimization wins from
  total wall time alone.

## M134b - Builds proportional to the change

- [ ] Split the shared-image builder into a manifest-derived artifact graph with public
  single-target operations. A command such as `just dev-build lico` resolves the
  canonical program, compiles and links only `lico.lsexe`, runs its relocation, W^X,
  identity, provider-order and undeclared-import audits, and leaves every unrelated
  provider/consumer untouched. Building a `.lslib` rebuilds that provider plus only the
  transitive consumers whose ABI/image identity requires relinking. Preserve the full
  `just shared-libs` rebuild/audit as the authoritative checkpoint path.
- [ ] Make cache decisions explainable and content-based. Every artifact records source,
  toolchain, target, linker script, manifest metadata, direct provider identities and
  build-mode inputs; `dev-build --explain` reports the first invalidating edge. A
  no-change build performs no Cargo compile, relink, system-image rewrite or package
  assembly. Failed builds never replace the last valid artifact, and dependency changes
  cannot be hidden by timestamps or stale generated manifest paths.
- [ ] Decouple package and boot-image assembly from unrelated artifacts. The kernel build
  script currently declares a rebuild edge on every staged executable, so any tool edit
  reassembles the volume package and restages the boot image, and on the architectures
  that embed the packages it relinks the kernel as well. Reassembly must not rewrite
  entries whose staged bytes are unchanged, and an unchanged package must not trigger
  image restaging or a kernel relink. Document per architecture which path embeds and
  which loads a boot module, and make the fast path report a fallback to the full rebuild
  instead of taking it silently.
- [ ] Stop whole-tree hashing from defeating the existing fast recipes. The test
  preflight stamp digests essentially all of `src`, so editing one leaf tool invalidates
  it and forces the slow path even when the fast recipes were selected. Narrow the stamp
  to the inputs that actually affect the artifact under test, keep the broad stamp for
  checkpoint validation, and make any widening of the invalidation set explicit.
- [ ] Investigate and fix the slow cache-verification path. The quick shared-cache check
  is currently slow enough to discourage use. Measure it against the M134a baseline,
  remove redundant hashing or relinking, and give it a bounded runtime target consistent
  with its role as a fast guard.

## M134c - Persistent guest and hot artifact publication

- [ ] Add an explicit x86_64 QEMU development profile to `qemu-run.sh` and `lab.py`.
  `just dev-up` boots once, keeps QEMU and the system volume alive, reports readiness over
  the control plane and reuses the instance across commands; `dev-status`, `dev-log` and
  graceful `dev-down` are deterministic. The profile is opt-in, visibly reported by the
  guest and absent from normal, test and production boot paths. Existing UART,
  framebuffer, monitor and QMP channels retain their current ownership.
- [ ] Attach the development channel as a second single-port virtio-serial device rather
  than negotiating MULTIPORT. The existing driver already binds one console port per
  device, and the device manager already binds a driver per matching device, so a second
  `virtio-serial` instance carrying one port backed by a host Unix socket needs no feature
  negotiation change, no control-queue port discovery and no change to emergency console
  behavior. Bind the new port to the dedicated development service rather than to the
  console, keep console traffic isolated and usable if the development port fails, and
  keep the framing above the port independent of the device topology so the later general
  multiport driver can host the same protocol on a named port without changing anything
  above the transport. If a second device instance proves infeasible, fall back to the
  minimum specification-compliant multiport negotiation, but treat that as the expensive
  option and record why it was needed.
- [ ] Define one versioned bounded development-control protocol over that port. Frames
  carry explicit opcode, request ID, generation, checked payload length and artifact
  digest; partial frames, duplicate IDs, oversized chunks, unknown versions/opcodes,
  disconnects and cancellation fail deterministically. Required operations are
  handshake/capabilities, ping, begin/chunk/commit/abort artifact publication, query/list
  active generations, launch/stop a scenario, terminal input/output events, scenario
  result and guest-state reset. The protocol transfers bytes and typed metadata only: it
  accepts no host path, shell command, arbitrary guest path or capability request.
- [ ] Add a development agent and volatile artifact registry available only in the
  development profile. Publication is transactional: stream into a bounded candidate,
  verify complete length, digest, ELF kind, target architecture, canonical image identity,
  manifest ownership, declared providers and dynamic metadata, then atomically expose a
  new immutable generation. Store candidates outside the canonical system volume, abort
  them on error/disconnect and retain the previous valid generation until no process or
  loader reference uses it. Enforce configured byte, artifact and retained-generation
  limits.
- [ ] Integrate the registry with ProcessService without creating a second launch path.
  PermissionManager remains the only ordinary program launcher and its installed
  manifest remains the authority for executable names and grants. In the explicit
  development profile only, a canonical declared `.lsexe` or `.lslib` may resolve to a
  compatible registry generation before its installed artifact. New launches receive one
  self-consistent executable/provider generation set; running processes retain their
  mappings, provider caches cannot return mixed generations, and rollback restores the
  prior set atomically. Undeclared artifacts, changed grants and incompatible provider
  identities are rejected.
- [ ] Harden the development boundary. The host Unix socket uses owner-only permissions
  and a per-boot handshake; the guest refuses publication outside the explicit profile;
  malformed or fuzzed frames cannot allocate without bounds, escape the registry, change
  manifests or keep Domains and handles alive. Host disconnect aborts in-flight
  publication and scenarios. Test stale generations, digest mismatch, interrupted upload,
  provider rollback, concurrent requests, registry exhaustion, process crash and
  development-agent restart without altering the installed system artifacts.

## M134d - Application scenarios outside the kernel image

- [ ] Move application-level interaction scenarios out of the kernel test binary. Add a
  bounded declarative scenario format and host runner for: publish fixture artifacts,
  launch a canonical program through PermissionManager, provide arguments/cwd and scoped
  test fixtures, wait for terminal bytes or lifecycle events, send key/pointer/control
  input, disconnect selected services, assert output/exit/restoration, and impose step and
  total deadlines. Scenario data cannot execute host or guest shell commands. Kernel
  tests remain the owner of kernel mechanisms; application tests no longer require a
  kernel relink, boot-image rebuild or QEMU restart.
- [ ] Provide deterministic per-scenario isolation and reset. Each run gets a fresh child
  Domain, terminal endpoints and bounded ephemeral fixture volume or namespace; completion,
  timeout or disconnect kills the whole scenario scope, closes transferred handles,
  removes unpublished artifacts/fixtures and verifies resource counters return to their
  baseline. Reset service-local test state through typed hooks only where necessary.
  A failed tool or scenario must not poison the persistent VM or require a reboot before
  the next run.
- [ ] Migrate representative existing governed-application tests first, including a
  simple non-interactive tool, one dynamically linked provider consumer and the
  `lico`/`licoedit`/`licoview` terminal lifecycle scenarios. Prove byte-for-byte terminal
  assertions, raw/alternate-screen/mouse restoration, service disconnect and process
  cleanup through the persistent runner. Keep equivalent cold QEMU coverage until the new
  runner has demonstrated parity; then retain one focused cold end-to-end sample instead
  of duplicating every fast scenario in the kernel image.
- [ ] Expose one ergonomic command family: `dev-up`, `dev-build <artifact>`,
  `dev-publish <artifact>`, `dev-test <scenario>`, `dev-loop <artifact> <scenario>`,
  `dev-status`, `dev-reset` and `dev-down`. `dev-loop` performs build -> audit -> publish
  -> run and stops at the failing phase; rerunning after a source edit repeats only the
  invalidated phases. Commands detect a stale socket, dead guest, changed kernel/driver/
  boot contract or incompatible protocol and explain the required recovery rather than
  silently launching another QEMU instance. Apply the M134a output budget to the whole
  family: a successful warm iteration prints one phase and timing summary plus the
  scenario result, and reports cache hits, misses and bytes transferred so an
  unexpectedly broad rebuild is immediately visible.

## Gates and completion

- [ ] Add an explicit invalidation and recovery matrix. Leaf executable and compatible
  provider changes use hot publication; manifest grants/ownership, protocol ABI,
  ProcessService/PermissionManager, driver, kernel, loader, package layout and QEMU device
  topology require a cold rebuild/reboot. Support a clean baseline QMP snapshot or an
  equivalent fast deterministic restart after initial boot for corrupted guest state,
  but do not use snapshots during a normal successful iteration or hide persistence bugs.
  Detect incompatible snapshots from kernel, volume and device-topology identities.
- [ ] Define and enforce the performance gate on the baseline host: after one `dev-up`, a
  one-line leaf-tool edit must complete build, audit, publication and one focused scenario
  without compiling the kernel, assembling boot/package/system images, traversing
  unrelated consumers or restarting QEMU. The warm no-change path performs no artifact
  transfer. Set measured per-phase budgets from the baseline and fail a regression that
  unexpectedly selects the cold path. Full shared-image, fresh-boot focused QEMU and
  x86_64/aarch64/riscv64 build gates still run once at a commit checkpoint or when the
  invalidation matrix requires them, not after each local edit.
- [ ] Document the workflow and ownership boundaries in `docs/DEBUG.md`: normal fast loop,
  when cold validation is mandatory, artifact/provider generation semantics, scenario
  schema, log locations, troubleshooting and cleanup. Add automated self-tests that boot
  one development VM, run at least three successive publish/test generations without
  reboot, inject one failed generation and rollback, then perform a final cold checkpoint
  build to prove the optimized path has not diverged from the shipped image.
- Done when: M134a has measurably cut per-run output volume and boot cost with no
  architectural change; single-artifact builds are proportional and explainable; one
  persistent QEMU instance can accept repeated independently audited `.lsexe` and
  compatible `.lslib` generations, launch them only through existing policy, execute
  isolated declarative application scenarios and return bounded structured results
  without rebuilding the kernel or system image or rebooting; failures roll back and
  leave the next run usable; successful output is concise; measured warm iteration cost
  reflects only the changed dependency closure; and all existing cold release gates
  remain available and authoritative.
- Explicitly deferred: virtio-fs, 9P, SMB, NFS, FTP, arbitrary host-directory access,
  host-writable mounted guest filesystems, production remote deployment, general dynamic
  virtio-serial multiport and provisioning ports, replacing kernel-unit tests,
  hot-swapping kernel, services or drivers, weakening image or manifest identity, and
  skipping cold checkpoint validation.
- Concept: the existing `lab.py` persistent shell/monitor harness, shared-image identity
  and dependency cache, governed `.lsexe` launch path, ProcessService dynamic resolver,
  Domain cleanup, QEMU monitor/QMP support, the planned general virtio-serial multiport
  driver and the planned capability-scoped development-only virtio-fs backend.
