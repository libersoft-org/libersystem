# M0134 - Incremental development and persistent QEMU test loop

Status: PRIORITY INFRASTRUCTURE MILESTONE, DELIVERED IN FOUR INDEPENDENTLY USEFUL PHASES.
Ordinary work on one leaf tool pays the cost of the whole system: before M0134a a focused
run reassembled the volume package, restaged the boot image, booted a fresh guest and
printed the complete build and boot transcript. M0134a removed the transcript and part of
the boot cost, but the build and boot coupling itself remains. This milestone removes that
coupling in increasing order of implementation cost, so the cheapest reductions land first
and no phase has to wait for the one after it. M0134a is a pure workflow-cost phase that
changes no system architecture and must not be blocked behind the later phases.

Two structural facts constrain the design and must be respected rather than rediscovered.
First, the staged artifact set reaches the guest differently per architecture: on x86_64
the init and volume packages are separate boot modules, while the aarch64 and riscv64
boot paths embed them into the kernel binary with `include_bytes!`. Any claim that an
artifact change avoids a kernel rebuild is therefore architecture-specific and must be
verified per target, not assumed. Second, application scenarios are compiled into the
kernel test binary today, so adding or fixing one is a kernel change by construction;
until that is undone, no build-cache work can make application iteration cheap.

The transport is a development-only channel on existing devices, not a filesystem. This
milestone does not implement or depend on virtio-fs. The planned development-only
virtio-fs volume may later expose host files and large test data through StorageService,
but executable replacement continues to use the validated artifact publication protocol
below. No 9P, SMB, NFS, FTP or ambient host-directory mount is introduced. A host-writable
disk shared with a live guest filesystem is rejected outright: concurrent host and guest
writes to one mounted image corrupt it.

## M0134a - Immediate cost reduction, no architecture change

- [x] Make successful runs quiet and failures informative. The kernel test driver
  currently prints the full cargo transcript and the full guest boot log on every run,
  including successful ones, which is the single largest source of per-iteration output.
  Write both transcripts to named files under `.build` and print, on success, only the
  tag selection, pass and fail counts and total time; on failure print the failing test,
  its diagnostic block and a bounded tail. Add `--verbose` for the full stream. Set and
  enforce an explicit budget: a successful focused run emits at most a few dozen lines
  and never a complete boot transcript.
  Result: `test-kernel.sh` now retains cargo and guest transcripts under
  `.build/test-logs`, prints a two-line mode and result summary on success, accepts
  `--verbose` for complete transcripts, and emits at most the configured bounded tail of
  each relevant log on failure. Focused validation covered a successful build-only run,
  a seven-test x86_64 QEMU run and a forced timeout preserving exit status 124.
- [x] Cap test-mode parallelism on x86_64. Test runs default to the host core count, so a
  large host emits one bring-up line per core on every boot and pays bring-up cost that
  the already capped aarch64 and riscv64 runs show is unnecessary for ordinary coverage.
  Default focused x86_64 test runs to a small fixed core count, keep an explicit
  override, retain one high-core-count configuration in the checkpoint suite so SMP
  scaling stays covered, and collapse per-core bring-up reporting into one summary line
  at the default log level.
  Result: x86_64 QEMU test mode now defaults to four CPUs while ordinary interactive
  boots retain the host core count and `SMP` remains an explicit override. Kernel SMP
  bring-up records topology without per-core serial lines and emits one `N of N` summary;
  `just test-smp-checkpoint` runs the focused SMP coverage with `SMP=$(nproc)`. A focused
  default run passed all seven selected tests in six seconds and its guest log contained
  exactly one `4 of 4` summary.
- [x] Reduce per-artifact chatter in the build and validation recipes. The shared-image
  builder, format check, manifest check and hygiene check print one line per crate or
  artifact even when nothing was rebuilt. Print per-item lines only for items actually
  rebuilt or failing, otherwise a single summary with counts and cache hit and miss
  totals, with full detail behind `--verbose`.
  Result: warm shared-image builds now print one measured summary line with stage timing
  and provider, object and executable cache totals; rebuilt artifacts still print one
  result line each. `--verbose` or `LIBER_VERBOSE=1` restores cache decisions and warm
  snapshot diagnostics. `fmt-check` suppresses all successful per-crate command echo and
  produced zero output bytes in validation while preserving formatter diagnostics and
  exit status. Manifest, artifact-metadata and source-hygiene checks were already
  summary-only and required no behavior change.
- [x] Fold generated dynamic-report regeneration into the ordinary path. Adding or
  removing a governed executable changes the checked provider and consumer reports, which
  currently surfaces later as a separate failing check after the expensive work is done.
  Detect the drift during the shared-image build, name the exact refresh command, and
  keep the committed reports authoritative at checkpoints.
  Result: every successful shared-image build now runs a sub-second inventory-only check
  between the manifest, report wave classification and checked executable report. Drift
  prints the exact `just dynamic-report-update` command without blocking the first target
  build, allowing the remaining target graphs to become current; verbose mode also prints
  the inventory diff. Full ELF metrics remain in the explicit blocking checkpoint because
  measuring all three graphs took 23 to 127 seconds per invocation. The report generator
  now includes the three LiberCommander tools in wave 5, derives row counts from the
  manifest, and regenerated 51-tool reports that pass the full three-target check.
- [x] Establish a reproducible baseline before the later phases change anything. Add one
  timed command that records source hashing, Cargo compilation, provider linking,
  consumer linking, ELF/identity audit, system-image staging, package/image assembly,
  kernel compilation, QEMU startup, guest boot, scenario execution and shutdown
  separately. Capture cold, warm-no-change, one-leaf-tool edit and one-shared-provider
  edit on the documented x86_64 QEMU/KVM host. Record output volume per run as well, so
  the budget above is measured rather than assumed. Store machine-readable samples under
  `.build` and a concise table in `docs/PERF.md`; do not infer optimization wins from
  total wall time alone.
  Result: `just dev-baseline <cold|warm|leaf|provider> [tags]` records raw host-nanosecond
  events, full command logs and one cumulative TSV row under `.build/dev-baseline` without
  mutating sources. Instrumentation separates shared-image source, graph, provider,
  consumer and report stages; init and volume package assembly; total Cargo work; image
  assembly; QEMU startup; guest boot; scenario execution and shutdown. The documented
  x86_64 baseline measured 414.63 seconds cold, 10.21 seconds warm, 101.67 seconds for one
  leaf and 94.73 seconds for one provider, while the seven-test guest scenario itself took
  only 24 to 40 ms. Output fell from 136 lines cold to three lines warm.

## M0134b - Builds proportional to the change

- [x] Split the shared-image builder into a manifest-derived artifact graph with public
  single-target operations. A command such as `just dev-build lico` resolves the
  canonical program, compiles and links only `lico.lsexe`, runs its relocation, W^X,
  identity, provider-order and undeclared-import audits, and leaves every unrelated
  provider/consumer untouched. Every `.lslib` and intermediate object is an independently
  cached build unit shared by all consumers: if its sources, toolchain, flags, manifest
  row and transitive provider identities are unchanged, another application reuses the
  existing audited bytes without invoking Cargo, compiling or linking that dependency
  again. Building a changed `.lslib` rebuilds that provider plus only the transitive
  consumers whose ABI/image identity requires relinking. Concurrent requests for the
  same missing unit coalesce behind one build rather than compiling duplicate copies.
  Name the target explicitly: `dev-build` defaults to x86_64, accepts an explicit target
  selector for aarch64 and riscv64, and keeps its cache per target so switching
  architecture does not invalidate the other. Preserve the full `just shared-libs`
  rebuild/audit as the authoritative checkpoint path.
  Result: `just dev-build <artifact> [x86_64|aarch64|riscv64]` now resolves the
  canonical manifest artifact and builds only its dependency closure. Bare colliding
  names prefer the executable while explicit `.lsexe` and `.lslib` suffixes select the
  required kind. A provider operation adds only transitive dependent providers and
  consumers plus every provider needed to audit that closure. Target-specific build
  locks coalesce concurrent work, targeted mode never prunes or globally audits unrelated
  outputs and the existing full build remains authoritative. Validation rebuilt one
  edited `lico` object and executable with seven provider hits, reused its restored
  content-addressed object, left every unrelated program mtime unchanged, passed a
  26-provider and three-consumer `pix.lslib` closure, passed the aarch64 `lico` closure,
  and completed a full 61-provider and 70-executable x86_64 audit followed by a one-second
  warm snapshot hit.
- [x] Make cache validation cost proportional to the change, not to the inventory. The
  M0134a baseline measured a one-leaf-tool edit at 101.67 seconds with 61 of 61 provider
  cache hits and a single object and executable miss, yet the provider and consumer stages
  still spent 39 and 40 seconds. Almost none of that is compilation. On the cache-hit path
  the shared builder resolves one manifest row per artifact in a separate query process,
  digests each crate source tree, rehashes each intermediate archive and re-reads each
  output ELF, so the cost scales with all 131 artifacts instead of with the change, and
  the single whole-image warm snapshot removes it only for a literal no-change build and
  is discarded as soon as anything moves. Resolving or validating one artifact must not
  spawn a process per unrelated artifact, digest an unrelated source tree, rehash an
  unrelated archive or re-read an unrelated ELF. Derive every manifest row in one query,
  keep per-artifact validation state instead of one whole-image snapshot, and use a cheap
  size and timestamp fast path that escalates to content hashing only for entries that
  actually moved. Budget: a no-op single-artifact build completes within one second on the
  documented host, independent of the artifact count, matching the warm no-change budget
  of the performance gate below, and stays correct when a file is restored with an
  unchanged timestamp.
  Result: every targeted program or provider now records an atomic state containing its
  manifest-derived plan and the exact source, tool, cache and output paths in its selected
  closure. A single batched `stat` check over size, inode, mtime and ctime accepts a no-op
  before source hashing, Cargo graph work or ELF audits; any mismatch falls back to the
  complete targeted path. Manifest source, library and destination rows are loaded in one
  query, while targeted source inventories, output prehashing and Cargo graph keys cover
  only the selected closure. Justfile source paths are lazy command substitutions rather
  than 50 eager manifest-tool processes, with a separately locked and invalidated source
  map for recipes that use them. Five successive public `just dev-build lico` no-op runs
  measured 359 to 380 ms with every stage at zero. Touching an unrelated staged program
  retained the hit; changing one source byte with identical size and restored mtime forced
  a miss through ctime, rebuilt only the `lico` object and executable with seven provider
  hits, and restoring the original bytes reused the content-addressed object.
- [x] Make cache decisions explainable and content-based. Every artifact records source,
  toolchain, target, linker script, manifest metadata, direct provider identities and
  build-mode inputs; `dev-build --explain` reports the first invalidating edge. A
  no-change build performs no Cargo compile, relink, system-image rewrite or package
  assembly. Failed builds never replace the last valid artifact, and dependency changes
  cannot be hidden by timestamps or stale generated manifest paths.
  Result: `just dev-build --explain <artifact> [target]` now reports `unchanged` on a
  state hit or the first changed named plan, tool or filesystem edge before taking the
  targeted fallback. The state stores versioned target, build mode, resolved tool paths
  and individual manifest library/program rows rather than one opaque plan hash. Every
  provider, executable and ET_REL object cache also persists the exact structured input
  record whose bytes form its key, including source identity, rustc/tool digests, target,
  flags, manifest row, linker/start input and direct provider identities. Validation
  named exact `lico.rs` and staged `bin/lico` changes and a substituted `llvm-strip` tool,
  while a no-change run reported no invalidating edge. Provider, executable and probe
  linking now writes a PID-scoped candidate, performs strip, ELF, W^X, dependency,
  symbol and identity audits there and atomically replaces the canonical artifact only
  after success. Injected post-link `llvm-strip` failures preserved the previous provider
  and executable SHA values, returned the original failure status and left no candidate.
- [x] Decouple package and boot-image assembly from unrelated artifacts. The kernel build
  script currently declares a rebuild edge on every staged executable, so any tool edit
  reassembles the volume package and restages the boot image, and on the architectures
  that embed the packages it relinks the kernel as well. Reassembly must not rewrite
  entries whose staged bytes are unchanged, and an unchanged package must not trigger
  image restaging or a kernel relink. Document per architecture which path embeds and
  which loads a boot module, and make the fast path report a fallback to the full rebuild
  instead of taking it silently.
  Result: kernel package assembly now compares the complete deterministic package bytes
  and atomically publishes only changed init or volume packages; identical bytes preserve
  inode and mtime. The same helper governs the stable AArch64/RISC-V volume exports.
  x86_64 continues to load separate boot modules, while AArch64 and RISC-V embed OUT_DIR
  packages, so preserving those files also avoids an embedded kernel relink. `mkimage.sh`
  now locks the shared image workspace and keys ISO/IMG assembly on mode, size, strip
  policy, recipe, product metadata, kernel, loader and both packages. A hit reports itself
  and leaves the image untouched; a miss reports the cold fallback, builds a PID-scoped
  candidate and publishes atomically. Two x86_64 package builds and repeated ISO/IMG
  assembly preserved inode, mtime, size and SHA. Touching an unchanged staged `lico`
  reran package assembly without rewriting either package or ISO. A real factory-file
  edit changed the volume package and ISO and restoring it returned both original hashes.
  Repeated AArch64 and RISC-V builds completed in zero seconds with unchanged embedded
  packages, exported volumes and kernel ELFs. An injected post-assembly `xorriso` failure
  preserved the prior ISO and build key and left no candidate.
- [x] Stop whole-tree hashing from defeating the existing fast recipes. The test
  preflight stamp digests essentially all of `src`, so editing one leaf tool invalidates
  it and forces the slow path even when the fast recipes were selected. Narrow the stamp
  to the inputs that actually affect the artifact under test, keep the broad stamp for
  checkpoint validation, and make any widening of the invalidation set explicit.
  Result: hashing the tree was never the cost. The 733-file input set digests in 86 ms
  when batched, while the stamp spawned a hash and an `awk` process per file, so a check
  cost 7,100 ms; one batched pass brought it to 315 ms and `test-tags-build-fast smoke`
  now completes in 8.7 seconds. Inputs are split into named toolchain, product,
  kernel-build and image classes, and an invalid stamp names the class that changed. The
  narrow scope excludes only host-only tooling that no staged crate depends on: the
  conformance suites, both benches, the mutation harness, the LSIDL generator,
  `normalize-ogg` and `src/idl`, whose generated bindings reach an artifact only through
  checked-in output. The x86_64 UEFI loader stays included because test mode still boots
  through the assembled ISO. The exclusion list is recorded in the stamp, so changing it
  invalidates every stamp and reports an invalidation-set change rather than silently
  widening or narrowing coverage. Preparation writes both scopes, keeping the broad stamp
  available for checkpoint validation through `--scope full` or `TEST_PREFLIGHT_SCOPE`.
  Validation covered a host-only edit accepted by the narrow scope and rejected by the
  broad one, staged leaf, `product.conf` and kernel build-script edits each naming their
  class, a missing stamp, an edited exclusion list and aarch64 preparation. Preparing an
  invalid stamp costs 8.2 seconds warm, of which 6.4 is the existing `test-tags-check`
  gate rather than the userspace build.
- [x] Investigate and fix the slow cache-verification path. The quick shared-cache check
  is currently slow enough to discourage use. Measure it against the M0134a baseline,
  remove redundant hashing or relinking, and give it a bounded runtime target consistent
  with its role as a fast guard.
  Result: the guard was not slow, it was broken. It asserted on cache decisions that had
  moved behind verbose logging, so it failed in 1.7 seconds without running; requesting the
  detail explicitly restored it. That exposed the real defect. Verifying a warm graph
  republished it: `llvm-objcopy --dump-section` given one file edits that file in place, so
  reading the identity note out of each staged artifact rewrote all 131 of them with
  identical bytes under a new inode and mtime, defeating every stat-keyed cache below.
  Naming an explicit output makes verification read-only. With outputs stable, the full path
  gained the per-artifact state the targeted path already had: a plan record and a stat
  signature per input file, all settled against one batched `stat` of the whole graph, so an
  unchanged artifact needs no cache key, no identity dump and no ELF audit. Consumers demand
  that every provider prove itself first, since a relinked provider changes the identity its
  consumers embed, and the export index and ownership audit are skipped only when no artifact
  moved. A forced rebuild records fresh state without trusting any. Warm full-graph
  verification fell from 47 to 9 seconds, one leaf edit from 46.8 to 11 seconds, preflight
  after a leaf edit from 56 to 17, and the run after a forced rebuild from 47 to 9. The quick
  guard now passes in 63 seconds rather than 277. Validation covered both guard modes, a
  staged-provider byte mutation that was caught, relinked and restored while its consumers
  correctly fell back to the full proof, the targeted `dev-build` path and its `--explain`
  decision, `test-preflight`, and `static-image-check` across all three targets.

## M0134c - Persistent guest and hot artifact publication

- [x] Add an explicit x86_64 QEMU development profile to `qemu-run.sh` and `lab.py`.
  `just dev-up` boots once, keeps QEMU and the system volume alive, reports readiness over
  the control plane and reuses the instance across commands; `dev-status`, `dev-log` and
  graceful `dev-down` are deterministic. Exactly one development instance owns the profile
  at a time: `dev-up` takes an instance lock, and a second invocation from another
  worktree or shell fails with the owning instance identity and the command that releases
  it rather than racing over the same socket, system volume and build outputs. The profile
  is opt-in, visibly reported by the guest and absent from normal, test and production
  boot paths. Existing UART, framebuffer, monitor and QMP channels retain their current
  ownership.
  Result: the host names the profile over QEMU `fw_cfg` rather than through the boot
  protocol or the boot image, so selecting one changes no bytes the guest is built from
  and needs no rebuild. A new `boot_profile` entry on the architecture contract reads that
  key; x86_64 implements it over the port interface behind a signature check, and both
  other backends answer `None` because the persistent instance is x86_64-only. The guest
  prints one line only when a profile is named. `DEV_PROFILE=1` is refused for any other
  architecture and alongside `TEST`, and it is applied below the test early-exit so test
  mode cannot reach it by construction. Ownership is an flock held by the broker across
  the fork, so the kernel releases it when the broker dies and there is no stale lock to
  break by hand; the lock file carries the owning worktree, host, broker pid and process
  group, and a conflict names the owner and the worktree to release it from. `dev-status`
  reports exactly one of down, starting, ready, stale or foreign and exits 0 only when
  ready. The instance keeps its own serial, control and log paths so an ad-hoc `lab boot`
  cannot steal its console, while the monitor and QMP sockets keep their existing owners.
  Three defects surfaced during validation and were fixed: waiting on the control plane
  could only observe bytes yet to arrive, so an already-idle guest timed out instead of
  reporting ready; the forked broker inherited its caller's stdout, so any pipe around
  `dev-up` waited for an end-of-file that never came; and `dev-down` skipped the shutdown
  path for a stale instance, leaving its guest running. A fourth was pre-existing and
  adjacent: `boot/lab.py` was committed without its executable bit, so `just lab` could
  not run at all. Validation covered boot in 14.5 s to a ready prompt reporting the
  development profile, a repeated `dev-up` returning in 0 s without disturbing the guest,
  `lab sh uname` and `lab sh ls` reusing the running instance, a simulated second owner
  rejected by all three commands while the guest kept running, graceful teardown in one
  second leaving no socket, lock or QEMU behind, a stale instance cleared together with
  its guest, a normal boot carrying neither the fw_cfg key nor the guest line, and the
  smoke suite passing with no profile line in its guest log.
- [x] Give the persistent instance a detachable human serial console. QEMU exposes it
  through a stable owner-only Unix socket rather than tying it to the terminal that
  started `dev-up`. The existing `lab.py` broker continuously drains that socket into a
  bounded replay log so a disconnected client cannot stall QEMU; `just dev-console`
  attaches an interactive terminal, replays the recent tail and may detach and reconnect
  without stopping the guest or shell. Exactly one client owns serial input at a time,
  while additional `dev-console --read-only` clients and `dev-log` may observe output.
  Client death releases writer ownership, and broker death is detected rather than
  silently stalling the guest on a full socket buffer: `dev-status` reports the missing
  broker as a recoverable state and names the command that restores it. Human serial
  bytes never share framing, sockets or broker state with the binary artifact-control
  channel, QMP or monitor. Scenario terminal traffic never competes for the human writer
  slot: scenario input and output travel through the scenario's own endpoints on the
  control protocol, so an attached `dev-console` neither blocks a scenario nor silently
  absorbs its output.
  Result: the broker is the only reader of the guest UART, which is what makes the console
  detachable at all: it drains QEMU whether or not anyone is watching, so no absent or slow
  terminal can back the socket up. Terminals attach over a separate socket carrying raw
  bytes and nothing else, sharing no framing, socket or state with the control channel, the
  monitor or QMP; occupancy is asked over the control channel so querying it never touches
  the byte stream. One handshake line grants the single writer slot, every other client
  observes, and a reader's keystrokes are discarded rather than interleaved. A bounded
  256 kB replay is delivered on attach, so a reconnecting terminal picks up where it left
  off while the searchable history stays in the log file. Sends to clients are
  non-blocking: a terminal that stopped reading loses bytes rather than stalling the guest.
  Writer ownership is released by client death, and scripted commands share the same drain,
  so an attached console keeps seeing the guest while `lab sh` runs. Broker death is now a
  named recoverable state rather than a stall: `dev-status` reports `detached` when the
  guest outlives its broker and names `just dev-up`, which reconnects a new broker to the
  same UART instead of rebooting. Two defects surfaced and were fixed: the handshake used a
  buffered reader that swallowed the replay following it, and an observer's Ctrl-C printed
  a traceback instead of detaching. Validation covered replay on attach ending at the
  prompt, a second writer refused and downgraded, a read-only client observing while its
  input never reached the guest, the writer slot released on client death, occupancy
  reported as `writer=1 readers=0` and back, a scripted `lab sh` succeeding with a console
  attached, broker kill leaving the guest alive and reported as `detached`, reattachment in
  one second preserving the guest process group and uptime, and the ad-hoc `lab boot`
  family unaffected by the broker rewrite. Not delivered here, because it is the next
  items' contract: scenario traffic still shares the one UART with the human console, so
  the promise that scenario endpoints never compete for the writer slot holds only once the
  development port and its control protocol land.
- [x] Detect a stale instance from identity rather than from symptoms. `dev-status`
  compares the running instance identity with current kernel, loader, boot packages,
  protocol and QEMU topology inputs and reports the exact required action. A kernel-only
  change recompiles the kernel and reassembles the image without recompiling an unchanged
  loader; a loader-only change does the converse. A boot-image recipe or packaged-module
  change reassembles the image without recompiling unchanged binaries. A QEMU-only device
  topology change restarts the VM without rebuilding the image unless the guest-visible
  boot payload also changed. A shared boot-protocol change rebuilds every binary that
  consumes that contract. None of these cold invalidations may be silently mistaken for
  a hot-publishable application change.
  Result: `dev-up` records what the guest is actually running as six separately named
  input classes - protocol, kernel, loader, packages, image and topology - and `dev-status`
  recomputes them and names the class that moved together with the scope of its rebuild.
  Each class spans both its sources and its built artifacts, so an edit that has not been
  built yet and a build that has not been booted yet are both caught; the shared boot
  contract is its own class precisely because its rebuild scope is every binary that
  consumes it rather than one of them. Comparison is by content, not by timestamp, so a
  rebuild producing identical bytes does not read as a change. A reattach deliberately
  keeps the recorded fingerprint: the broker changed, the guest did not, so a stale
  instance cannot be laundered by putting a new broker on it. Every report ends by saying
  the invalidation is cold and not a hot-publishable application change, which is the
  confusion the item exists to prevent, and `dev-status` now exits 0 only when the instance
  is both ready and running current inputs. The fingerprint costs 173 ms. Validation drove
  each class in isolation and saw exactly it reported: a kernel edit naming the kernel
  recompile with the loader left alone, a loader edit naming the converse, a `bootproto`
  edit naming the shared contract and both consumers, a packaged-module change and an
  `mkimage.sh` edit naming image reassembly from unchanged binaries, and a `qemu-run.sh`
  edit naming a VM restart with no image rebuild. It also covered two classes changing at
  once and being listed together, `touch` on three inputs leaving the verdict current,
  a killed broker reattaching without clearing a pending kernel change, and a full cold
  cycle in 31 seconds turning a stale verdict current and back again when reverted.
- [x] Attach the development channel as a second single-port virtio-serial device rather
  than negotiating MULTIPORT. The existing driver already binds one console port per
  device, and the device manager already binds a driver per matching device, so a second
  `virtio-serial` instance carrying one port backed by a host Unix socket needs no feature
  negotiation change, no control-queue port discovery and no change to emergency console
  behavior. Bind the new port to the dedicated development service rather than to the
  console, keep console traffic isolated and usable if the development port fails, and
  keep the framing above the port independent of the device topology so the later general
  multiport driver can host the same protocol on a named port without changing anything
  above the transport. The persistent profile is x86_64-only, but this device and the
  protocol above it are not: the same second port is available in the cold test
  configuration of all three targets, so the scenario runner can drive an aarch64 or
  riscv64 boot at the checkpoint over identical framing. If a second device instance
  proves infeasible, fall back to the minimum specification-compliant multiport
  negotiation, but treat that as the expensive option and record why it was needed.
  Result: a second device instance was feasible, so the expensive fallback was not needed.
  The host attaches a second `virtio-serial-pci` carrying one port backed by a Unix socket,
  and the guest binds a dedicated `dev_channel` program to it instead of the console driver.
  Two devices of one type were previously indistinguishable to userspace, so `DeviceInfo`
  now carries the PCI address and the host pins the channel to a fixed slot: the binding
  matches that address rather than enumeration order, which keeps the real console bound to
  the console driver whatever order the bus is walked in. No feature negotiation, control
  queue or emergency console behaviour changed, and the two ports are independent devices,
  so either can fail without the other. The framing above the port is carried in the port's
  own byte stream and knows nothing about how the port was discovered, so a later multiport
  driver can host the same protocol on a named port unchanged. One measured finding shaped
  the design: a generic `virtserialport` is never opened without MULTIPORT, so the guest's
  writes vanished entirely; a console port is required, and its cost is that UEFI firmware
  writes its console output to every console-class device it enumerates, leaving a firmware
  preamble on the x86_64 channel before the guest owns the port. Guest console traffic never
  appears there, so framing simply begins at the guest's first byte rather than paying for
  MULTIPORT to remove a preamble. Validation confirmed the two devices at distinct pinned
  and auto-assigned PCI addresses, both drivers reporting online with all twelve devices
  bound, the guest's marker read from the host socket end while kernel console output stayed
  off it, and the smoke suite passing on x86_64, aarch64 and riscv64 with the same second
  port present in each cold test configuration.
- [x] Define one versioned bounded development-control protocol over that port. Frames
  carry explicit opcode, request ID, generation, checked payload length and artifact
  digest; partial frames, duplicate IDs, oversized chunks, unknown versions/opcodes,
  disconnects and cancellation fail deterministically. Frames are bounded by construction:
  at most 64 kB per frame and at most 16 outstanding requests, with both maxima reported
  in the handshake so each side fails early instead of at the first oversized payload.
  Required operations are handshake/capabilities, ping, begin/chunk/commit/abort artifact
  publication, query/list active generations, launch/stop a scenario, terminal

  this build decides it from content, deliberately - two authorities on what needs rebuilding is
  how a build system becomes unexplainable, and this milestone already recorded one incident
  where a stat-keyed cache was silently defeated. Writing a scheduler by hand would avoid that,
  but the hard half of a build system is change detection, which exists here already, so buying
  a scheduler while keeping that half is a poor trade against simply letting cargo schedule.
